## 00. От ответа сервера к просьбе клиента

В прошлом занятии мы читали ответ сервера: статус сообщал результат, а заголовки и body помогали понять данные. Но откуда сервер знает, чего от него хотели? Вернёмся к началу обмена.

Представьте список задач в браузере. Одна кнопка открывает задачу, другая добавляет новую, третья снимает отметку о выполнении. Все три действия относятся к задачам, но ожидаемые последствия разные. В HTTP клиент сообщает намерение с помощью **метода** (method). Метод записывается в запросе перед адресом.

~~~text
GET  /tasks     → попросить список
POST /tasks     → передать данные для создания задачи
~~~

Это примеры формы запроса, а не маршруты, которые нужно сейчас написать на FastAPI. В этом занятии разберём смысл пяти методов. Затем сможем осмысленно выбрать метод для действия Planner. Адреса ресурсов подробно составим в следующем занятии.

## 01. Метод, адрес и договор API

Адрес отвечает на вопрос «с чем работаем?», метод отвечает на вопрос «что просим сделать?». В паре они помогают серверу выбрать подходящую операцию. Один адрес может использоваться с разными методами: например, чтение списка и добавление задачи обращаются к коллекции tasks, но делают с ней разное.

**Ресурсом** (resource) называют данные, доступные через API: список задач или отдельную задачу. **Представление ресурса** означает форму данных, которую клиент получает или передаёт, например JSON-объект. Метод не говорит, в каком Python-файле лежит обработчик и хранится ли задача в памяти или базе данных.

**Договор API** задаёт, какие сочетания метода и адреса допустимы, какие данные передавать и какого результата ожидать. Поэтому английское название метода само по себе не является готовым серверным кодом.

Различаем HTTP-метод и имя Python-функции. Внутри сервера обработчик может называться `show_tasks` или `read_list`. Клиент не импортирует его, а отправляет HTTP-запрос. Сервер сам связывает внешний запрос со своим кодом. Этот внешний договор полезен разным клиентам: браузеру, мобильному приложению и программе командной строки.

Методы, которые понадобятся Planner API:

- GET просит прочитать данные.
- POST передаёт данные на обработку. В нашем договоре он создаёт задачу.
- PUT передаёт полное изменяемое представление выбранной задачи.
- PATCH передаёт частичное изменение.
- DELETE просит убрать выбранную задачу из доступного состояния.

### Проверьте смысл

Для каждого действия сначала назовите намерение обычными словами: показать расписание, добавить встречу, заменить всю анкету, исправить один телефон, удалить бронь. Какую разницу между третьим и четвёртым действием нельзя потерять при выборе метода?

Ответ: в одном случае клиент передаёт полную новую форму, в другом сообщает только изменение части формы. Именно эта разница понадобится для PUT и PATCH.

## 02. GET: прочитать, не изменить

GET нужен, когда клиент хочет получить текущее представление. Для Planner API это может быть список задач или одна задача. Чтение не должно само отмечать задачу выполненной, создавать её или удалять.

~~~text
GET /tasks    → список задач
GET /tasks/7  → задача с id 7
~~~

**Безопасный по назначению** (safe) метод означает, что клиент запрашивает чтение, а не изменение предметного состояния. Это слово не относится к паролям и правам доступа. Сервер может записать технический журнал запроса, но запрошенное действие над задачей остаётся чтением.

Почему это важно? Браузер может повторно загрузить страницу, а предварительный просмотр ссылки иногда сам делает запрос. Если GET изменяет задачу, результат зависит от такого технического повтора.

На практике GET применяют для списков, карточек и сводок. Системы иногда сохраняют полученное представление в кэше, чтобы быстрее обслуживать повторное чтение. Поэтому GET должен сообщать о чтении предсказуемо. Это не гарантия, что данные никогда не изменятся: другой клиент может исправить задачу после этого запроса.

Независимый Python-пример показывает подготовку данных для просмотра:

~~~python
appointments = [{"time": "10:00", "free": True}]
visible = [item.copy() for item in appointments]
print(visible[0]["free"], appointments[0]["free"])
~~~

**Что напечатает код?** Сначала зафиксируем прогноз. Ответ: `True True`. Программа подготовила данные для просмотра, не изменила исходную запись. Новое значение другого пользователя между двумя GET-запросами возможно: безопасное чтение не обещает одинаковый ответ навсегда.

В следующем примере ошибка чтения:

~~~python
def read_appointment(item):
    item["free"] = False
    return item

slot = {"free": True}
print(read_appointment(slot)["free"], slot["free"])
~~~

Код напечатает `False False`. Функция вернула данные, но перед этим поменяла исходный словарь. Если привязать такое действие к GET, один просмотр забронирует время. Исправление состоит в том, чтобы не менять запись при чтении; бронирование должно быть отдельной изменяющей операцией.

Тело запроса GET обычно не требуется. У GET-body нет общего смысла, определённого HTTP; если конкретный API его не описывает, не рассчитываем, что сервер и промежуточные системы одинаково его обработают. Главный признак GET здесь состоит в намерении прочитать данные.

## 03. POST: передать новую работу серверу

POST отправляет данные на обработку. Он не обязан означать создание во всех API, но в договоре Planner API команда POST к коллекции создаёт новую задачу. Клиент передаёт её начальные данные, сервер проверяет их, назначает новый `id` и возвращает результат.

~~~text
POST /tasks
body: {"title": "Изучить HTTP", "priority": 4}

сервер → новая задача с назначенным id
~~~

Эта запись показывает направление данных, а не полную реализацию маршрута. Клиент не выбирает `id` сам: иначе два клиента могли бы назначить один и тот же идентификатор.

В успешном сценарии сервер может ответить статусом `201 Created` и вернуть созданную запись с `id`. Это связывает нынешнюю тему с прошлой: POST выражает просьбу, а response сообщает, что получилось. При ошибке проверки данных новой задачи быть не должно. Само наличие body в запросе ещё не означает успеха.

Представьте, что сервер создал задачу, но ответ потерялся в сети. Клиент знает лишь то, что ответа нет. Если он без дополнительного механизма повторит тот же POST, сервер может создать вторую запись. Поэтому POST для создания нельзя автоматически повторять как безобидное чтение.

**Проверьте себя.** После потери ответа клиент видит задачу на экране или нет? Может ли он по одному таймауту доказать, что сервер ничего не создал? Нет: отсутствие ответа не сообщает, на каком этапе произошёл сбой. В реальных системах для защиты повтора создания иногда передают специальную метку операции. Сервер узнаёт её при повторе; такую метку называют ключом идемпотентности. Сейчас этот механизм реализовывать не нужно.

## 04. PUT: заменить полную изменяемую форму

PUT удобно понимать как просьбу «сделай выбранный ресурс вот таким». В нашем Planner API клиент передаст все изменяемые поля существующей задачи: `title`, `priority` и `is_done`. Серверный `id` останется идентичностью той же задачи.

~~~text
было:   id=7, title="HTTP", priority=3, is_done=false
PUT:          title="API",  priority=5, is_done=true
стало:  id=7, title="API",  priority=5, is_done=true
~~~

Здесь PUT описывает полную замену изменяемой формы. HTTP допускает и создание через PUT в других договорах, когда клиент заранее знает адрес будущего ресурса. В нашем проекте сервер назначает новый `id`, поэтому создание вынесено в POST.

Что будет, если в полной форме пропущено поле? На этот вопрос нельзя отвечать догадкой. Договор API должен решить: отклонить запрос, задать значение по умолчанию или очистить поле. Для нашей учебной формы предполагаются все три изменяемых поля.

В реальном интерфейсе для PUT часто собирают всю редактируемую форму на экране. Это удобно, когда клиент видит её целиком и намерен заменить целиком. Но если с момента чтения другой человек изменил одно поле, старая полная форма может затереть его новое значение. Такую конкуренцию обычно решают отдельными правилами версий или условных запросов. Сейчас достаточно понимать риск: PUT передаёт полную форму, а не «любое обновление».

Рассмотрим независимый пример с настройками уведомлений. Если клиент заменяет весь набор `{"email": true, "push": false}`, вторая отправка того же набора оставит настройки в том же состоянии. Это **идемпотентный эффект**: итог после нескольких одинаковых запросов совпадает с итогом после одного. Сервер при этом может обработать оба запроса и записать оба в журнал. Даже HTTP-ответы не обязаны быть одинаковыми.

**Сравните формы.** Для задачи с полями `title`, `priority`, `is_done` какая передача ближе к полной замене: `{"priority": 5}` или `{"title": "API", "priority": 5, "is_done": true}`? Вторая описывает всю изменяемую форму. Первая сообщает только одно изменение.

## 05. PATCH: изменить часть и сохранить остальное

PATCH нужен, когда клиент сообщает изменение только некоторых полей. В нашей модели пропущенное поле сохраняет прежнее значение. Это полезно, если человек поменял один флаг, а клиент не хочет повторно передавать всю карточку.

~~~text
было:  title="HTTP", priority=3, is_done=true
PATCH:                priority=5
стало: title="HTTP", priority=5, is_done=true
~~~

Перед применением изменений сервер проверяет, существует ли задача, разрешены ли переданные поля и допустимы ли значения. PATCH не означает «без проверки вызвать update() у словаря». Клиент не может менять серверный `id` только потому, что положил его в body.

Порядок имеет значение: сначала проверить вход и найти ресурс, затем построить новое состояние и сохранить его. Если проверка не прошла, не нужно оставлять половину применённых изменений. Позже мы реализуем это правило в настоящем API, а сейчас изучаем внешний смысл частичного запроса.

### Отсутствует, false или null?

Это три разных ситуации. Мы различаем пропущенный ключ, `false` и `null`. В договоре Planner API пропуск и `null` сохраняют прежнюю отметку `is_done`, а `false` снимает её. Механизм обработки разберём при реализации PATCH.

Посмотрите на маленькую Python-модель. Это не HTTP-обработчик, а способ увидеть проверку наличия поля:

~~~python
settings = {"email": True, "push": True}
change = {"push": False}

if "push" in change:
    settings["push"] = change["push"]

print(settings)
~~~

**Что получится?** `{"email": True, "push": False}`. Поле `email` сохранилось. Проверка `if change["push"]` была бы ошибкой: `False` не выполняет условие, хотя ключ передан. В API то же различие нужно закрепить в схеме и проверках.

Если заменить проверку наличия ключа на `if change["push"]:`, присваивание не выполнится и `push` останется `True`. Это ошибка результата, а не синтаксиса. Для частичного запроса нужно сначала выяснить, передавал ли клиент поле, и только потом работать с его значением.

PATCH как метод не обещает идемпотентности для любого документа изменений. Команда «установи priority в 5» оставит одинаковый итог после повтора. Команда «увеличь счётчик на 1» при повторе изменит его снова. Формат и правила изменения должны быть описаны в договоре конкретного API.

## 06. DELETE: убрать выбранную задачу

DELETE сообщает, что выбранный ресурс нужно убрать из доступного состояния. В Persistent Planner удаление записывается в JSON, поэтому задача остаётся удалённой и после перезапуска. В других сервисах тот же внешний смысл может быть реализован архивированием или скрытием записи.

~~~text
DELETE /tasks/7
→ после успешного удаления задача 7 недоступна для обычного чтения
~~~

Первый DELETE может вернуть `204 No Content`: успех без body. Если отправить тот же запрос ещё раз, задачи уже нет; договор API может вернуть `404 Not Found`. Это не нарушает идемпотентность: итоговое доступное состояние ресурса одинаково. Задача отсутствует. Статус двух ответов может различаться.

У удаления есть и другая граница. Метод DELETE не подтверждает, что пользователь имеет право удалять запись. Проверка доступа остаётся отдельной обязанностью сервера.

Успех без тела ответа отличается от `{}`: при `204` body отсутствует, а пустой JSON-объект всё равно является body. Мы уже встречали это различие в занятии об ответах. При удалении оно помогает клиенту не пытаться разобрать несуществующий JSON.

**Неверное ожидание.** «Повторный DELETE обязан вернуть тот же 204, иначе сервер удалил что-то дважды». Неверна первая часть: идемпотентность относится к задуманному эффекту, а не к одинаковым статусам.

## 07. Как рассуждать о повторе запроса

Когда клиент не получил response, он не всегда знает, выполнил ли сервер действие. Для выбора поведения полезны два разных вопроса:

1. **Безопасен ли метод по назначению?** GET просит чтение. Остальные методы в этой теме могут менять задачу.
2. **Идемпотентен ли задуманный эффект повтора?** GET, PUT и DELETE имеют такое свойство. POST-создание обычно может создать дубль. Для PATCH ответ зависит от операции внутри документа изменений.

Безопасность метода по назначению не означает авторизацию. Идемпотентность не означает «код выполнился ровно один раз» и не требует одинакового response.

Четыре ситуации показывают последствия повтора: чтение списка; создание задачи после потери ответа; замена полной карточки; удаление уже исчезнувшей задачи. В каждом случае важно определить возможное изменение состояния и причину, по которой ответ может отличаться. Название метода само по себе не объясняет эффект: нужно учитывать действие над ресурсом.

Две версии PATCH показывают зависимость от содержания операции: повтор команды «установить priority в 5» не меняет итог после первого применения, а повтор команды «прибавить к priority 1» снова меняет значение. Нельзя объявить все запросы PATCH идемпотентными или все неидемпотентными без знания содержания операции.

## 08. Что мы будем делать в практике

Сейчас мы не запускаем сервер и не меняем Persistent Planner. В редакторе платформы будет небольшая функция `solve(action)`. Она получает название одного известного действия над задачами и возвращает HTTP-метод в верхнем регистре. Входы охватывают чтение списка и одной задачи, создание, полную замену, частичное изменение и удаление.

В решении нужен словарь соответствий `methods`; функция возвращает из него значение для переданного `action`. Сначала определяется смысл действия, затем выбирается метод. Полная замена и изменение переданных полей требуют разных методов. Сеть, URL, body, статусы и обработка неизвестных действий в этом упражнении не нужны.

Платформа проверит все шесть известных входов. Успешная проверка означает, что каждое действие связано с подходящим HTTP-намерением. В следующем занятии к выбранному методу добавим адрес ресурса и различим запрос к списку и конкретной задаче.

Перед практикой важно различать четыре вещи: чтение не меняет данные; повтор POST может создать дубль; PUT передаёт полную форму, а PATCH только изменения; повтор DELETE может получить другой статус при том же итоговом состоянии. Эти различия помогают выбирать метод по смыслу операции, а не по английскому названию.
