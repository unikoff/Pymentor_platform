## 00. От действия к адресу

В прошлом занятии мы научились выбирать HTTP-метод по действию: прочитать, создать, заменить, частично изменить или удалить задачу. Но одного метода недостаточно. Серверу ещё нужно понять, с каким объектом работает клиент.

Представим библиотеку. Сначала называем раздел, например «книги», а затем при необходимости указываем конкретную книгу. API решает похожую задачу через ресурс и адрес. Метод говорит, что сделать, а path помогает определить, с чем это сделать.

В этом занятии мы соберём понятную карту адресов Planner API. Это проектирование внешнего интерфейса, а не запуск сервера и не работа с файлами хранения.

> **Вспомним.** Что различается в запросах `GET /tasks/7` и `DELETE /tasks/7`, если path у них одинаковый?

## 01. REST и соглашения для API

REST расшифровывается как Representational State Transfer. Это архитектурный стиль для взаимодействия распределённых систем, а не Python-библиотека и не формат JSON.

Одно из важных ограничений REST называют **stateless**, то есть каждый запрос несёт контекст, нужный для текущего действия. Сервер не должен угадывать его по предыдущему запросу клиента.

Представим службу обращений:

```text
GET /tickets/42
→ прочитать обращение с id 42
```

Серверу не нужно помнить, что тот же клиент раньше открывал список обращений: метод и выбранный item уже указаны в новом запросе. При этом сами обращения по-прежнему хранятся на сервере. Stateless описывает контекст обмена, а не отсутствие постоянных данных.

У REST есть и другие ограничения. Здесь достаточно общего представления о них:

- клиент и сервер разделяют обязанности;
- кэширование позволяет повторно использовать ответы, если это разрешено их свойствами;
- слои допускают промежуточные узлы, например прокси или шлюз;
- единый интерфейс помогает клиентам одинаково находить ресурсы и обращаться к ним;
- гипермедиа может сообщать ссылками, какие действия доступны дальше.

Одного JSON поверх HTTP недостаточно, чтобы автоматически получить полный REST. Но команде полезно договориться об одном стиле: как называть предметы, как адресовать набор и отдельный объект и как сочетать path с HTTP-методом. Так API легче читать, проверять и расширять.

В рабочих проектах часто используют REST-подобную модель ресурсов, чтобы разные клиенты могли работать с единым внешним интерфейсом и не зависеть от Python-функций или файлов сервера. В Planner мы изучаем именно эту практическую часть. Не будем утверждать, что учебная карта реализует все формальные ограничения REST.

**Проверим миф.** Если REST предполагает stateless-запросы, значит ли это, что серверу запрещено сохранять задачи?

Нет. Сервер может хранить состояние приложения. Самостоятельным должен быть контекст каждого запроса.

**Сравним записи:**

- `/get-tasks` помещает действие в адрес. Для каждой операции пришлось бы придумывать отдельный путь.
- `GET /tasks` называет предмет и отдельно задаёт действие методом.

**Интерактив.** Выбираем более предсказуемый вариант. Какую часть смысла сообщает path, а какую метод?

## 02. Ресурс и его представление

Ресурс это предмет или понятие, о котором клиент может запросить информацию или с которым может выполнить действие. В Planner таким ресурсом будут задачи, а в карте API мы называем его `tasks`.

Ресурс не равен строке таблицы базы данных, Python-классу или файлу. Это внешнее понятие, доступное клиенту. Сервер сам выбирает, как его представить и где хранить.

Когда клиент получает задачу, он получает не внутренний объект сервера, а его представление, например JSON:

```json
{
  "id": 7,
  "title": "Изучить REST",
  "priority": 4,
  "is_done": false
}
```

Представление описывает публичные поля задачи. Внутри проекта она может быть объектом класса, словарём или записью базы данных. Клиенту не нужно знать об этих деталях. Если способ хранения изменится, внешний интерфейс может остаться прежним.

Поле `tags` остаётся в существующей `Task` и сохраняется в JSON, но не публикуется в HTTP-представлении Planner API. Внешнее представление содержит `id`, `title`, `priority` и `is_done`.

**Различаем уровни:**

- ресурс: задача как предметная сущность;
- представление: данные, которые сервер отправляет клиенту;
- реализация: класс, база или файл на стороне сервера.

**Проверим понимание.** Что должен получить внешний клиент: экземпляр Python-класса `Task` или согласованное представление задачи?

## 03. Collection и отдельный item

Один ресурс можно адресовать в разном масштабе. Collection означает набор задач, а item означает одну выбранную задачу внутри набора.

| Область | Пример path | Что выбрано |
| --- | --- | --- |
| Collection | `/tasks` | список задач |
| Item | `/tasks/7` | задача с id 7 |

Число в item path указывает, какую запись просит клиент. Оно не подтверждает, что задача действительно есть. Серверу ещё предстоит проверить данные и решить, какой ответ вернуть. Сейчас мы строим адрес, а не проверяем хранилище.

Один path может принимать несколько методов. Например, `GET /tasks` читает collection, а `POST /tasks` создаёт в ней задачу. Path один, но метод задаёт разные действия.

Для item сохраняется форма `/tasks/{task_id}`. Чтение, замена, частичное изменение и удаление используют адрес выбранной задачи, а нужный метод мы уже разобрали раньше.

**Сопоставляем намерение и масштаб адреса:**

- показать все задачи относится к collection;
- открыть задачу с id 7 относится к item;
- создать задачу относится к collection;
- удалить задачу с id 7 относится к item.

## 04. Имена ресурсов и специальные адреса

В path обычно называют ресурс существительным. Так адрес отражает предметную область, а метод описывает действие.

```text
GET    /tasks
POST   /tasks
GET    /tasks/7
PATCH  /tasks/7
DELETE /tasks/7
```

Пути вроде `/create-task` или `/delete-task/7` связывают адрес с кнопкой или названием операции. По мере роста API такой стиль становится непоследовательным. В нашей карте действие уже задаёт method, поэтому дублировать его в названии path не нужно.

Это соглашение, а не запрет на любой глагол в path. Некоторые операции не укладываются в обычную работу с ресурсом. В Planner есть два специальных примера:

- `GET /health` сообщает, отвечает ли сервис на техническую проверку;
- `GET /stats` возвращает агрегаты по задачам.

Это служебные операции, а не новые сущности `Health` и `Stats`. Для них не нужно придумывать CRUD-набор.

**Отладка карты.** Находим запись, которая выбивается из выбранного стиля:

```text
GET    /tasks
POST   /tasks
GET    /tasks/7
DELETE /delete-task/7
```

Подумаем, какой адрес должен остаться у удаления и какую роль выполняет метод.

## 05. URL, path и endpoint

URL это полный адрес ресурса. Например:

```text
https://api.planner.example/tasks?is_done=false
```

В нём можно выделить схему `https`, имя узла `api.planner.example`, path `/tasks` и query-часть `is_done=false`. Адрес выбирает collection, а query задаёт фильтр списка. В следующем занятии мы отдельно разберём, какие значения передают в path, query и body.

Для наглядности:

- схема: `https`;
- имя узла: `api.planner.example`;
- path: `/tasks`;
- query: `is_done=false`.

Path это часть адреса после имени узла. Здесь он указывает на collection задач; отдельный item выбирался бы адресом вида `/tasks/42`.

Для практической карты будем считать endpoint сочетанием HTTP-метода и path. Например, `GET /tasks/42` и `DELETE /tasks/42` используют один path, но обозначают разные операции. Если смотреть только на адрес, можно не понять, что клиент просит сделать.

Термин endpoint иногда используют свободнее, называя им весь адрес или маршрут. Для этого курса зафиксируем рабочее значение: endpoint это пара `method + path`.

**Интерактив.** Что различается между `GET /tasks/42` и `PATCH /tasks/42`: path, выбранный item или действие?

## 06. Собираем карту Planner API

Карта начинается с намерения клиента. Сначала решаем, работает ли он со всем набором или с одним item. Затем выбираем method, который выражает действие, и path, который указывает область.

| Намерение клиента | Method | Path |
| --- | --- | --- |
| показать список задач | GET | `/tasks` |
| создать задачу | POST | `/tasks` |
| открыть задачу 7 | GET | `/tasks/7` |
| проверить доступность сервиса | GET | `/health` |

Для изменения и удаления item используется форма `/tasks/{task_id}`, а конкретный HTTP-метод задаёт операцию. В Planner `POST /tasks` выбран для создания. Это решение нашего API, а не правило, что POST во всех системах обязан выполнять одну и ту же операцию.

Перед реализацией карта помогает заметить несогласованность. Если рядом с `/tasks` внезапно возникает `/remove-task/7`, команда может обсудить интерфейс до появления кода.

Проверяем карту по трём вопросам:

1. Path называет понятный ресурс, а не внутренний Python-файл?
2. Path указывает на collection или конкретный item?
3. Method и path вместе описывают операцию?

Настоящего маршрутизатора FastAPI здесь пока нет. Мы не проверяем наличие задачи, не читаем базу и не формируем ответ сервера. Это отдельные темы следующих этапов.

**Что напечатает код?** Сначала называем обе строки, затем сверяем ответ.

```python
routes = {
    "GET /tasks": "список",
    "GET /tasks/7": "одна задача",
}

print(routes["GET /tasks"])
print(routes["GET /tasks/7"])
```

Получатся строки «список» и «одна задача». Вторая запись отличается path, а не названием Python-функции.

## 07. Что мы будем делать в практике

Заготовка интерпретатора уже содержит `methods` для шести действий над задачами из прошлого занятия и добавляет `GET` для `health` и `stats`. Переписывать таблицу не нужно.

Нужно реализовать функцию:

```python
def solve(action, task_id):
    ...
```

Функция получает одно из восьми заранее известных действий. Для item передаётся целый `task_id`, для остальных операций он равен `None`. Проходим три связанных шага:

1. **Область операции.** `list` и `create` выбирают collection; `get`, `replace`, `update` и `delete` выбирают item; `health` и `stats` используют отдельные технические path.
2. **Результат.** Функция возвращает словарь с ключами `method` и `path`. Метод берётся из готовой таблицы, а адрес item строится с переданным `task_id`.
3. **Границы упражнения.** Функция выбирает адрес, но не отправляет запрос, не проверяет наличие задачи и не обрабатывает неизвестные действия.

Интерпретатор проверит все восемь действий и несколько разных id, чтобы правило выбора адреса не сработало случайно лишь на одном примере.

Цель не в том, чтобы выучить строки наизусть. Важно увидеть правило, которое связывает предметную область, масштаб адреса и HTTP-метод.

## 08. Главное и переход дальше

Метод и path отвечают на разные вопросы. Метод сообщает, что клиент хочет сделать. Path показывает, какой ресурс или его часть выбраны. Вместе они задают понятный адрес операции.

Ресурс API не раскрывает устройство Python-класса или хранилища. Collection обозначает набор, item выбирает один элемент, а специальные path вроде `/health` могут описывать технические действия.

В следующем занятии мы разберём, где передавать идентификатор, фильтр и данные новой задачи. Карта адресов станет основой для более полного контракта запроса и ожидаемого ответа.
