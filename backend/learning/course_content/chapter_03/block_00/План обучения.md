# Глава 3 · От консольного Planner к своему REST API

<!-- youtube: -->

Знакомый планировщик задач получит новый способ общения с пользователем. За 24 занятия вы разберётесь в HTTP, подключите FastAPI к существующему проекту, добавите создание и изменение задач, а затем покроете API тестами и подготовите его к выпуску.

## Маршрут главы

| --- | --- | --- |
| **9 · Поймём HTTP** · занятия 45–50 | Разберём роли клиента и сервера, устройство запросов и ответов, методы, адреса и передачу данных. | Сможем прочитать контракт API и понять, как клиент просит Planner выполнить операцию. |
| **10 · Подключим FastAPI** · занятия 51–56 | Отправим запросы через Postman, запустим сервер и подключим чтение и создание задач к существующему проекту. | Получим работающие GET и POST-маршруты, связанные с PlannerService и JSON-хранилищем. |
| **11 · Завершим цикл задач** · занятия 57–62 | Настроим валидацию и публичные схемы, проверим сохранение, добавим PUT, PATCH и DELETE. | API будет предсказуемо создавать, читать, обновлять и удалять задачи, включая корректные ошибки. |

## Блок 9 · Поймите, как устроен HTTP

До FastAPI разберём сам обмен между программами. Это поможет понимать, что именно позже автоматизирует фреймворк.

**К концу блока вы сможете:**
- объяснить роли клиента и сервера на примере Planner;
- читать запросы и ответы по их частям;
- выбирать метод, адрес и место передачи данных для операции.

### Занятия

- [45 · Почему CLI недостаточно: клиент и сервер](../block_09/45%20-%20Почему%20CLI%20недостаточно,%20клиент%20и%20сервер.md) — сравним работу в терминале и обращение к приложению по сети.
- [46 · HTTP request: адрес, метод, headers и body](../block_09/46%20-%20HTTP%20request,%20адрес,%20метод,%20headers%20и%20body.md) — соберём запрос из его частей и поймём, где передаются данные.
- [47 · HTTP response: status, headers, body и Content-Type](../block_09/47%20-%20HTTP%20response,%20status,%20headers,%20body%20и%20Content-Type.md) — научимся читать результат, который сервер возвращает клиенту.
- [48 · Методы GET, POST, PUT, PATCH, DELETE](../block_09/48%20-%20Методы%20GET,%20POST,%20PUT,%20PATCH,%20DELETE.md) — свяжем намерение с чтением, созданием, обновлением или удалением.
- [49 · REST, ресурс, endpoint и URL](../block_09/49%20-%20REST,%20ресурс,%20endpoint%20и%20URL.md) — построим карту адресов для коллекции и отдельной задачи.
- [50 · Path, query, body и контракт API](../block_09/50%20-%20Path,%20query,%20body%20и%20контракт%20API.md) — распределим значения по запросу и определим ожидаемый ответ.

**Результат блока**

1. Понимаете, что именно отправил клиент.
2. Можете объяснить статус и содержимое ответа сервера.
3. Выбираете маршрут и способ передачи данных по смыслу операции.

## Блок 10 · Подключите FastAPI к Planner

Перенесём понятную модель HTTP в работающий проект. Вместо нового учебного хранилища подключим маршруты к уже существующим данным и сервису.

**К концу блока вы сможете:**
- отправлять и проверять запросы через Postman и Swagger;
- запускать FastAPI рядом с привычным CLI;
- читать и создавать настоящие задачи через API.

### Занятия

- [52 · Первое FastAPI-приложение, Uvicorn и Swagger](../block_10/52%20-%20Первое%20FastAPI-приложение,%20Uvicorn%20и%20Swagger.md) — запустим сервер и добавим HTTP-точку входа, сохранив CLI.
- [53 · GET-endpoints и ответы FastAPI](../block_10/53%20-%20GET-endpoints%20и%20ответы%20FastAPI.md) — подключим чтение списка и статистики к существующему сервису.
- [54 · Path-параметры и поиск объекта](../block_10/54%20-%20Path-параметры%20и%20поиск%20объекта.md) — найдём задачу по id и обработаем отсутствие объекта.
- [55 · Query-параметры, фильтрация, сортировка и границы](../block_10/55%20-%20Query-параметры,%20фильтрация,%20сортировка%20и%20границы.md) — добавим фильтры и ограничения выборки без изменения данных.
- [56 · Pydantic BaseModel и request body](../block_10/56%20-%20Pydantic%20BaseModel%20и%20request%20body.md) — создадим и сохраним задачу из JSON-запроса.

**Результат блока**

1. Сервер запускается и принимает запросы.
2. API читает подлинные данные Planner через общий сервис.
3. Новая задача создаётся через HTTP и сохраняется в проекте.

## Блок 11 · Сделайте операции надёжными

Доведём контракт до полного жизненного цикла задачи: от проверки входа до сохранения обновлений и корректного удаления.

**К концу блока вы сможете:**
- задавать границы входных данных и предсказуемо отвечать на ошибки;
- отделять схему запроса от публичного формата ответа;
- обновлять и удалять ресурс через существующее прикладное ядро.

- [58 · Разные схемы, TaskCreate, TaskUpdate, TaskRead](../block_11/58%20-%20Разные%20схемы,%20TaskCreate,%20TaskUpdate,%20TaskRead.md) — зададим отдельную форму входа и публичного ответа.
- [59 · Хранилище в памяти и генерация идентификатора](../block_11/59%20-%20Хранилище%20в%20памяти%20и%20генерация%20идентификатора.md) — проследим сохранение данных и назначение серверного id в существующем хранилище.
- [60 · CRUD, создать, получить список и найти по id](../block_11/60%20-%20CRUD,%20создать,%20получить%20список%20и%20найти%20по%20id.md) — проверим единые правила чтения и создания для CLI и API.

- [62 · DELETE, 204 и HTTPException](../block_11/62%20-%20DELETE,%20204%20и%20HTTPException.md) — подключим настоящее удаление и проверим ответ для отсутствующей задачи.

**Результат блока**

1. Неверный ввод не меняет сохранённые задачи.
2. Клиент получает только согласованные публичные поля.
3. API поддерживает полный CRUD с понятными статусами и ошибками.

**К концу блока вы сможете:**
- проверять API на независимом тестовом состоянии;
- отделять маршруты ресурса от точки входа приложения;
- подтвердить сквозной сценарий и подготовить воспроизводимый выпуск.

3. Planner API можно установить, проверить и передать другому разработчику.
