## 00. Маршруты уже работают. Теперь соберём их в понятную часть приложения

В предыдущем блоке мы подключили к HTTP готовые операции PlannerService и сохранили их договор: адреса, схемы, query-параметры и ответы. Теперь можно изменить расположение маршрутов, не меняя того, что видит клиент. Сначала разберём, какую роль берёт на себя новый модуль и как приложение узнаёт о его маршрутах.

1. **Точка старта.** В FastAPI-приложении работают шесть операций `/tasks`; запросы используют выбранный сервис из `app.state.planner`.
2. **Новый вопрос.** Как вынести связанные обработчики в отдельный модуль, не создавая второе приложение и не меняя публичные URL?
3. **Результат.** Сгруппируем операции задач в `APIRouter` и подключим его к прежнему FastAPI-приложению с теми же ответами.

Такой переход меняет внутреннюю организацию, а не продукт. Мы не начинаем CRUD заново: сервис, схема ответа, ограничения запроса и проверки остаются прежними. Сначала поймём регистрацию маршрутов на независимом примере, затем перенесём существующие обработчики.

## 01. APIRouter группирует обработчики, но не создаёт приложение

FastAPI-приложение отвечает за регистрацию доступных HTTP-маршрутов. Пока проект небольшой, мы можем объявить их рядом с созданием `app`. Когда маршрутов становится больше, связанные операции удобнее держать в отдельных Python-модулях. Для этого FastAPI предоставляет `APIRouter`: объект хранит регистрации обработчиков и настройки, общие для их группы.

Вызов декоратора `@router.get(...)` связывает метод и локальный путь с функцией. Функция всё ещё выполняется как обработчик HTTP-запроса; сам `APIRouter` не запускает сервер, не хранит список задач и не заменяет PlannerService. Он не является вторым `FastAPI()`. Позже приложение подключает зарегистрированную группу через `include_router`.

Представим `APIRouter` как папку с карточками маршрутов. Карточка описывает, на какой HTTP-запрос отвечает функция, а папка собирает карточки одной области. FastAPI-приложение подключает эту папку и делает маршруты частью общего API. Граница сравнения: папка лишь помогает представить группировку; настоящий router является программным объектом и участвует в регистрации маршрутов.

Проверим идею на независимом примере отчётов. Это полный небольшой модуль приложения, а не решение задачи Planner:

```python
from fastapi import APIRouter, FastAPI

router = APIRouter(prefix="/reports", tags=["reports"])


@router.get("/daily")
def read_daily_report():
    return {"ready": True}


app = FastAPI()
app.include_router(router)
```

Когда модуль загружается, декоратор добавляет обработчик к router. Затем `app.include_router(router)` включает его в приложение. Клиент получает один путь `GET /reports/daily`; отдельный сервер или копия приложения не появляются. Удалим строку подключения и маршрут больше не будет частью этого приложения, даже если функция осталась в Python-модуле.

На схеме связь читается слева направо: файл `app/api.py` создаёт приложение и подключает группу; файл `app/routers/tasks.py` описывает операции; FastAPI регистрирует их в том же API. Здесь нет новой стрелки к хранилищу: за состояние по-прежнему отвечает выбранный PlannerService.

## 02. Prefix и локальный путь складываются в публичный URL

У группы маршрутов обычно есть общая часть адреса. Параметр `prefix` позволяет задать её один раз на router. Внутри декоратора остаётся локальный путь конкретного действия. FastAPI соединяет обе части при регистрации маршрута.

Это похоже на адрес здания и номер комнаты: общий адрес помогает найти корпус, локальная часть уточняет нужную дверь. Для Planner общая часть будет `/tasks`, а адрес конкретной задачи дополняется `/{task_id}`. Граница аналогии: это не пересылка письма и не отдельный сетевой узел, а единый HTTP-путь, собранный из настроек router и декоратора.

Сначала разберём путь на коротком примере. Если `prefix="/reports"`, а локальный путь равен `/daily`, итоговый адрес будет `/reports/daily`. Важен и крайний случай: для коллекции `/tasks` локальный путь задаётся пустой строкой `""`. Если написать `"/"`, получится `/tasks/`. Для клиента это другой URL; запрос без завершающего слеша может получить перенаправление. В проверке переноса маршрутов мы отключим автоматическое следование redirect, чтобы увидеть точный первый ответ.

Для списка и создания задачи используется один адрес коллекции, но разные HTTP-методы:

```text
GET    /tasks
POST   /tasks
GET    /tasks/{task_id}
PUT    /tasks/{task_id}
PATCH  /tasks/{task_id}
DELETE /tasks/{task_id}
```

С `prefix="/tasks"` декораторы коллекции используют `""`, а операции над одной задачей используют `"/{task_id}"`. Не повторяем `/tasks` в локальном пути. Иначе `prefix="/tasks"` вместе с `"/tasks"` даст лишний сегмент: `/tasks/tasks`.
Метод и путь описывают операцию совместно. `GET /tasks` и `POST /tasks` используют одну коллекцию, но имеют разные действия; четыре метода для `/tasks/{task_id}` тоже остаются отдельными операциями. Перенос сохраняет обе части этой пары и не оставляет прежнюю регистрацию рядом с новой.

Кроме пути, router принимает `tags=["tasks"]`. Здесь `tags` - метаданные документации OpenAPI: Swagger UI группирует операции под общей подписью. Это не поле `Task.tags`, не фильтр, не разрешение доступа и не часть URL. Мы используем одинаковое слово для двух разных ролей: одно находится в модели Planner, другое помогает читать описание API.

Проверим вычисление адреса на самостоятельном Python-примере. Значение здесь строковое, а не новый серверный маршрут:

```python
prefix = "/reports"
local_path = "/daily"
print(prefix + local_path)
```

Предскажем вывод: `/reports/daily`. FastAPI использует эти части при регистрации route, но приложение не просит нас вручную собирать URL внутри каждого обработчика.

## 03. Подключение оставляет один FastAPI и один PlannerService

`APIRouter` хранит описания обработчиков, а `include_router` подключает их к приложению. Поэтому после переноса `app/api.py` по-прежнему создаёт единственный `FastAPI`, выбирает сервис и оставляет короткие общие маршруты `/health` и `/stats`. Группа задач находится отдельно, но обслуживается тем же приложением и тем же сервисом.

У маршрутизатора есть собственные методы регистрации: вместо `@app.get(...)` обработчик объявляется через `@router.get(...)`. Меняется объект, которому принадлежит регистрация, а не тело функции. Вход по-прежнему описывают прежние схемы; query-параметры, response_model, статус и вызов операции сервиса остаются на месте. `APIRouter` не реализует вторую версию `list_tasks` или `delete_task`.

Чтобы обработчик использовал сервис именно того приложения, которое приняло запрос, он может принять параметр `request: Request` и обратиться к `request.app.state.planner`. FastAPI распознаёт тип `Request` и передаёт объект запроса автоматически. Клиент не отправляет этот объект в query или body: это информация о текущем HTTP-запросе и приложении, которое его обслуживает.

В прошлых занятиях сервис получался из `app.state.planner`. После выноса модуль router не должен импортировать готовый `app` из `app/api.py`: сам `api.py` уже импортирует router для подключения. Если оба файла импортируют друг друга, Python может начать загрузку одного модуля до того, как второй создал нужное имя. Через `Request` мы получаем актуальный app во время запроса и не создаём этот цикл.

Эта связь похожа на получение ключа через текущую стойку регистрации: сотруднику не нужно импортировать стойку в комнату, из которой она сама собирает список сотрудников. В приложении `request.app` указывает на принимающий запрос FastAPI, а `state.planner` хранит выбранный экземпляр сервиса. Граница аналогии: это не поиск глобальной переменной и не новый контейнер; объект передаётся FastAPI на время обработки запроса.

У подключения есть ещё один практический эффект: маршруты router становятся частью общей схемы OpenAPI. Если забыть `include_router`, файл с функциями импортируется, но запросы приложения до них не доходят. Если подключить router дважды или оставить прежние регистрации рядом с новыми, мы создадим дублирующую организацию пути. Поэтому переносим функции по одной и удаляем прежнюю регистрацию после проверки.

## 04. Переносим HTTP-границу без повторного написания CRUD

Перед переносом зафиксируем исходное поведение тестами. Они уже проверяют путь запроса через реальное приложение: успешные ответы, отсутствие задачи, схему данных и сохранённое состояние. При каждом переносе повторим эти тесты. Если ответ изменился, сначала найдём расхождение в пути или регистрации, а не станем переписывать PlannerService.

Создадим пакет `app/routers` и модуль `tasks.py`. В нём объявим `router = APIRouter(prefix="/tasks", tags=["tasks"])`, затем перенесём шесть обработчиков из `app/api.py`. Функции останутся теми же по смыслу: список, чтение одной задачи, создание, полная замена, частичное обновление и удаление. Их схемы входа и ответа, query-правила, HTTP-коды и обращения к PlannerService не меняются.

В `app/api.py` импортируем router из нового модуля и подключим ровно один раз. Маршруты здоровья и общей статистики остаются там же. Это похоже на переезд рабочего стола в другую комнату: меняется расположение, но мы переносим те же инструменты и продолжаем выполнять те же действия. Граница аналогии: код не перемещает физические предметы; при переносе мы сохраняем регистрации в действующем приложении и проверяем публичный результат.

После каждого обработчика сверим таблицу путей и методов, откроем `/docs` и повторим сохранённые запросы. `GET /tasks` и `POST /tasks` должны отвечать прямо, без скрытого перехода на адрес со слешем. Остальные четыре метода продолжают использовать `/tasks/{task_id}`. Мы не считаем зелёный импорт достаточным доказательством: он подтверждает только, что Python смог загрузить модули.

Если обработчик использует общий `Request`, передадим его параметром и возьмём тот же сервис через `request.app.state.planner`. Ошибки отсутствующей задачи продолжат переводиться на прежний HTTP-ответ в узкой обработке доменной ошибки; ответ `404` не должен скрывать сбой JsonStorage. Это поведение уже подготовлено раньше, поэтому перенос не меняет обработку исключений.

Не добавляем app-factory, слой Depends, новое хранилище или второй CRUD. Не переносим `health` и `stats` только ради симметрии. Наша цель уже: сгруппировать существующие tasks-маршруты и убедиться, что OpenAPI, тесты и ручные запросы всё ещё описывают один прежний Planner API.

## Что мы будем делать в практике

Подготовленные тесты дадут исходную опору для переноса. Пройдём три шага и на каждом сравним результат с тем же HTTP-договором.

1. **Создадим router задач.** В отдельном модуле появится общий prefix и тег; маршруты соберутся в одном месте.
2. **Перенесём обработчики без переписывания.** Метод, URL, входные и ответные схемы и вызовы PlannerService сохранятся.
3. **Повторим автоматическую и ручную проверку.** Тесты, OpenAPI и запросы подтвердят точные адреса без redirect и прежние ответы.

Получим понятную границу между сборкой приложения и группой HTTP-операций. Проверка докажет сохранность поведения, а не станет поводом создавать новый CRUD или отдельный список данных. На следующем шаге расширим тесты от основных ответов до важных границ входа и ошибок.
