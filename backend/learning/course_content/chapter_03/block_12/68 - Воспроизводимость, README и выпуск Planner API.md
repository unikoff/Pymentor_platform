## 00. От локального запуска к проверяемой передаче

Planner уже принимает HTTP-запросы, выполняет операции над задачами и сохраняет их в общем JSON-файле. Мы проверяли отдельные маршруты и работали с Postman на своей машине. Но локальный успех ещё не отвечает на вопрос, сможет ли новый разработчик повторить те же шаги в чистом окружении и получить тот же результат.

1. **Точка старта.** У нас есть рабочие API и CLI, общий `PlannerService`, `JsonStorage`, HTTP-договор и знакомый `pytest`.
2. **Новый вопрос.** Как проверить, что установка, запуск, тесты и инструкция относятся к одному состоянию проекта и не зависят от личной `.venv` или локальных данных?
3. **Результат.** Мы передаём проверенный Planner API с инструкцией, сохранёнными запросами и версией, которую можно воспроизвести.

В финале не появляется новый CRUD и не заменяется JSON. Мы проверяем уже созданный продукт с начала: находим проверяемый commit, устанавливаем объявленные зависимости в отдельном окружении, выполняем автоматические и ручные проверки, сверяем README с реальным запуском и только потом помечаем проверенную версию.

## 01. Разные проверки дают разные доказательства

Один зелёный тест не доказывает, что все части проекта готовы к передаче. Unit-тест проверяет правило `PlannerService` или `JsonStorage` обычным вызовом Python. `TestClient` вызывает настоящее FastAPI-приложение через ASGI (Asynchronous Server Gateway Interface), интерфейс между приложением и веб-сервером. Он проверяет HTTP-ответ без запуска Uvicorn и открытия TCP-порта. HTTPX обеспечивает клиентский транспорт, который использует TestClient. Это удобно для повторяемых проверок, но такой тест не подтверждает, что сервер доступен через сеть.

Postman отправляет запросы работающему Uvicorn и проверяет внешний путь клиента: адрес, метод, body, status, ответ и изменение общего JSON. Успешный ответ `201` сам по себе не доказывает сохранение: следующий GET и повторное чтение после перезапуска подтверждают разные части результата. В collection удобно хранить запросы и переменную `base_url`; ожидаемые id берём из фактических ответов, а не задаём заранее.

Для автоматических тестов мы создаём отдельное состояние. Function-scoped fixture получает собственный путь `tmp_path`, собирает прежний `PlannerService` с `JsonStorage` для этого пути и временно устанавливает его в `app.state.planner`. Несколько запросов одного теста продолжают работать с одним файлом, а следующий тест получает другой. После завершения клиент закрывается, затем восстанавливается рабочий сервис. Тесты не очищают `data/tasks.json` и не подменяют файловое хранилище списком.

Это похоже на два испытания автомобиля. `TestClient` проверяет двигатель на стенде вместе с системой управления, а Postman проверяет машину на дороге через настоящий HTTP-сервер. Стенд помогает повторять условия, дорожный выезд подтверждает реальное соединение. Ни один из них не заменяет другой, а оба опираются на один договор продукта.

OpenAPI и `/docs` помогают сверить зарегистрированные пути, методы, схемы и заявленные статусы. Это описание интерфейса, а не свидетельство, что запись действительно сохранилась или неверный запрос оставил данные без изменений. Поэтому документацию, автоматические тесты и запросы мы читаем как разные доказательства.

### Фрагмент conftest.py: подготовим проверку состояния

Удобнее всего проверять сначала известный вход, затем HTTP-ответ и только потом состояние после запроса. Fixture задаёт путь для одного теста до создания `TestClient`; клиентская fixture зависит от неё и закрывает клиент раньше, чем восстанавливается прежний сервис. Так несколько запросов одного сценария работают согласованно, а другой тест не наследует его задачи.

```python
@pytest.fixture
def planner(tmp_path):
    previous = app.state.planner
    app.state.planner = build_service(JsonStorage(tmp_path / "tasks.json"))
    try:
        yield
    finally:
        app.state.planner = previous

@pytest.fixture
def client(planner):
    with TestClient(app) as client:
        yield client
```

Эта подготовка не очищает общий список и не создаёт второй интерфейс хранения. Она временно подключает уже знакомый JSON-storage к отдельному пути. Между request внутри одного теста состояние сохраняется; для следующего теста pytest выдаёт новую временную папку.

## 02. Чистое окружение проверяет установку

Локальная `.venv` может содержать пакет, которого нет в зависимостях проекта. Тогда приложение запустится только на компьютере автора. Чистая копия убирает такую скрытую опору: в ней нет старого окружения и личного `data/tasks.json`, поэтому нужные действия должны быть описаны в репозитории.

`requirements.txt` содержит пакеты, нужные запущенному приложению. `requirements-dev.txt` подключает этот набор и инструменты проверки, включая `pytest` и `httpx` для TestClient. HTTPX отправляет запросы к приложению в процессе теста. Установка фиксируется файлами проекта, а `python -m` запускает пакет тем же интерпретатором, куда эти зависимости установлены.

Например, из корня чистой копии команды для Windows PowerShell выглядят так:

```powershell
python -m venv .venv
.\.venv\Scripts\Activate.ps1
python -m pip install -r requirements-dev.txt
python -m pytest -q
python -m uvicorn app.api:app --reload
```

README указывает версию Python, рабочую папку и каждую команду. Если новый рабочий JSON создаётся через CLI, инструкция сначала запускает CLI и показывает этот шаг. API и CLI используют один настроенный путь хранения; тесты при этом продолжают работать со своими файлами в `tmp_path`.

README можно сравнить с рецептом. В нём указаны инструменты и точный порядок действий, а чистая копия играет роль кухни, где ещё нет подготовленных продуктов. Если рецепт опирается на пакет или файл, который автор добавил только у себя, повторить блюдо не получится. Граница аналогии проста: запуск по рецепту подтверждает воспроизводимость шагов, но качество самого API всё ещё нужно проверять отдельно.

Из репозитория исключаются `.venv`, кэши, личные данные и локальные секреты. Не публикуется авторский JSON как демонстрационная база и не создаётся фиктивный `.env.example`, если приложение не использует переменные окружения. Чистый checkout должен получать свои данные через уже существующий CLI.

Два последовательных запуска pytest полезны, но одной этой проверки недостаточно. Мы также запускаем сквозной тест отдельно и в другом порядке: так проверяем, что независимость обеспечена fixtures, а не случайным порядком запуска.

## 03. README описывает проверяемый путь

README нужен человеку, который не видел историю разработки. В нём мы называем назначение Planner, структуру приложения, команды установки, запуска и тестов, корневую папку команд и адреса `/docs` и `/openapi.json`. Инструкция должна соответствовать нынешнему коду: если точкой запуска служит `app.api:app`, именно она указана в примерах.

В разделе API перечисляются восемь текущих операций: `GET /health`, список `GET /tasks`, получение `GET /tasks/{task_id}`, `GET /stats`, создание `POST`, полная замена `PUT`, частичное изменение `PATCH` и `DELETE`. Для продукта сохраняются знакомые ответы: создание даёт `201`, чтение и обновления дают `200`, успешное удаление даёт пустой `204`, корректный отсутствующий id даёт `404`, неподходящий вход даёт `422`.

Описание данных также остаётся точным. CLI и API используют один JSON, задачи переживают перезапуск, а функция списка применяет фильтр, сортировку и limit без изменения исходного хранилища. В README названы границы: здесь нет SQL-базы, авторизации и гарантий безопасной параллельной записи в JSON. Честное ограничение помогает следующему этапу курса понять, какую именно задачу решает SQLAlchemy.

Мы проверяем README действием, а не редакторским просмотром. Новая копия выполняет команды по порядку. Если путь неверен, пакет не установлен или маршрут отличается от текста, исправляем инструкцию либо проект и повторяем проверку. Красиво оформленная страница, которая не запускает приложение, не является проверенной передачей.

## 04. TestClient и Postman проходят разные границы

Перед ручной проверкой мы запускаем весь набор тестов из чистого окружения, затем отдельно запускаем сквозной сценарий и проверяем, что выборочные тесты не зависят от порядка. Каждый тест начинает со своего файла, а несколько запросов одного жизненного цикла используют общий файл этого теста.

В Postman мы импортируем существующую collection и environment. Переменная `base_url` хранит корень адреса сервера, а каждый request добавляет к нему путь операции. Затем проходим сохранённый сценарий через Uvicorn. Перед изменениями записываем текущую статистику из CLI. Затем создаём контрольную задачу и основную задачу, берём их id из ответов, меняем основную через PUT и PATCH, проверяем отказы, удаляем её и читаем снова. Соседняя задача остаётся неизменной, статистика соответствует сохранённым данным, а DELETE возвращает пустое тело.

Этот ручной сценарий работает с рабочим JSON и потому не очищается перед каждым запросом. Тесты, наоборот, используют изолированный `tmp_path`. Смешивание этих поверхностей опасно: очистка тестового файла не должна затронуть реальные данные, а созданная в Postman запись не должна стать скрытой предпосылкой автоматического теста.

Проверим различие на выборе инструмента. Если вызов проходит через `TestClient(app)`, мы проверяем приложение без отдельного сервера. Если запрос отправляется из Postman на адрес работающего Uvicorn, мы проверяем полный HTTP-путь. У обоих результатов есть место в приёмке, но выводы из них различаются.

## 05. Версия указывает на проверенный commit

До выпуска мы сверяем, что приложение, README, зависимости, тесты и collection относятся к одному состоянию. Сначала исправления попадают в commit, снимок подготовленного состояния файлов проекта. Hash служит его идентификатором. Затем этот commit проверяется в отдельной чистой копии. После успешного запуска тестов, API и сохранённых запросов сверяем hash проверенного commit и создаём различимый тег `planner-api-v1.0.0`. Это имя не перезаписывает прежний CLI-тег `v1.0.0`.

Тег похож на ярлык, прикреплённый к конкретному экземпляру проекта. Он помогает найти нужный commit, но сам не запускает тесты и не удостоверяет содержимое. Например, запуск тестов, затем исправление README и создание commit оставят README вне того тестового запуска. Поэтому мы сначала включаем все правки в commit, проверяем именно его из чистой копии и только потом создаём тег. Если код или README меняются после проверки, появляется новый commit; затронутые проверки нужно выполнить снова, а тег должен указывать на новое проверенное состояние.

GitHub Release создаётся из этого тега, когда доступен соответствующий репозиторий. В release notes кратко перечисляются возможности и ограничения версии; при необходимости прикладываются экспортированная collection и инструкция. Локальный тег остаётся локальным, пока публикация действительно не произошла. Учебный release подтверждает передачу версии, но не развёртывание в production.

### Последовательность проверки

Эта цепочка связывает действия и подтверждение результата. Сначала мы фиксируем код, README и зависимости в commit; затем проверяем чистый checkout по README. TestClient подтверждает договор на временном JSON, а Uvicorn и Postman подтверждают внешний HTTP-путь и работу с общим файлом. Только после этого тег planner-api-v1.0.0 указывает на тот же проверенный commit.

## 06. Что мы будем делать в практике

В практике мы пройдём тот же маршрут на уже существующем Planner:

1. **Подготовим чистый запуск:** команды README установят зависимости и запустят приложение из нового окружения.
2. **Проверим API автоматически:** TestClient выполнит независимые сценарии на отдельных JSON-файлах.
3. **Пройдём внешний путь:** Postman отправит запросы настоящему серверу и подтвердит сохранение общего состояния.
4. **Сверим передачу:** README совпадёт с фактическими командами, версия укажет на проверенный commit.

Каждый шаг даёт отдельное наблюдение, поэтому мы не заменяем проверку продукта оформлением release. Итогом остаётся тот же Planner с CLI, API и JSON, но его запуск, прежний HTTP-договор и ограничения сможет проверить другой человек. Существующие возможности не переписываются ради финальной работы.
