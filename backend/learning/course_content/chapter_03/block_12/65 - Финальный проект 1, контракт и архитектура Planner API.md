# 65. Контракт API: границы, ошибки и регрессия

## 00. От базовых тестов к проверке границ

1. **Точка старта**: мы уже отправляем запросы в настоящее FastAPI-приложение через **TestClient** и проверяем обычные ответы.
2. **Новый вопрос**: мы проверяем граничные значения и выясняем, что остаётся в JSON после отказа.
3. **Результат**: мы получаем тесты действующего HTTP-договора, не создавая новых маршрутов или второго Planner.

TestClient обращается к ASGI-приложению напрямую. Для такой проверки не нужно вручную запускать Uvicorn, но приложение, обработчики, схемы и сервис остаются настоящими. Поэтому HTTP-тест проверяет не только отдельную Python-функцию.

Перед каждым тестом нужно известное состояние. Если запросы используют рабочий JSON, ошибка или порядок запуска могут изменить результат. Для тестового клиента мы временно выбираем отдельный сервис с собственным файлом. Рабочий Planner, его маршруты и данные остаются прежними.

## 01. Ответ и состояние доказывают разные вещи

У HTTP-ответа есть несколько наблюдаемых частей:

- **status_code** сообщает, принял ли сервер запрос, обнаружил ли ошибку входа или не нашёл ресурс.
- **response.json()** показывает JSON-поля. Для **DELETE** с **204** проверяется пустой **response.content**.
- Повторный GET и **stats** показывают, что действительно сохранилось после действия.

Допустимый **POST /tasks** возвращает **201** и четыре публичных поля **TaskRead**: **id**, **title**, **priority**, **is_done**. Сервер назначает **id** и устанавливает **is_done=False**. Следующий GET по полученному id подтверждает, что запись осталась в хранилище. Поле **tags** может быть в доменной Task и JSON-файле, но не входит в публичный ответ.

Fixture задаёт сервис и жизненный цикл клиента для теста. **tmp_path** даёт каждой тестовой функции свой временный каталог. Запросы в рамках одного теста используют общий файл, поэтому связанный сценарий видит собственные изменения. Другой тест получает новое состояние.

Фрагмент **tests/conftest.py**:

```python
import pytest
from fastapi.testclient import TestClient

from app.api import app
from app.main import build_service
from app.storage import JsonStorage


@pytest.fixture(scope="function")
def planner_service(tmp_path):
    return build_service(JsonStorage(tmp_path / "tasks.json"))


@pytest.fixture(scope="function")
def client(planner_service):
    previous = app.state.planner
    app.state.planner = planner_service
    try:
        with TestClient(app) as test_client:
            yield test_client
    finally:
        app.state.planner = previous
```

Контекстный менеджер закрывает TestClient перед тем, как fixture восстановит прежний **app.state.planner**. Все обработчики получают выбранный сейчас сервис. Тесты не очищают рабочий **data/tasks.json** и не подменяют файловую границу глобальным списком.

## 02. Каждую границу проверяем отдельно

Для проверки границы меняется одно условие, а остальные входные поля остаются допустимыми. Тогда тест указывает на конкретное правило. Для создания **title** очищается от краевых пробелов, после этого его длина должна быть от 1 до 120 символов. Значения 1 и 120 допустимы. Пустая строка, пробелы, очищенная длина 121 и **priority** вне диапазона от 1 до 5 получают **422**.

Проверка похожа на пропускной пункт: **title** и **priority** являются полями, которые сверяют с условиями входа; **201** означает, что запрос принят, а **422** показывает отказ на границе. Но аналогия не описывает состояние хранилища. HTTP-тест дополнительно читает ответ и при необходимости проверяет запись после запроса.

Корректный целочисленный id, которого нет в хранилище, даёт **404**. Path id, который нельзя разобрать как целое число, даёт **422**. Эти ответы говорят о разных причинах, поэтому в тестах они разделены.

Проверяем status и смысловую часть **detail.loc**, например, что ошибка относится к body и полю **title**. Полный текст ошибки Pydantic не является договором и может поменяться. Обычная схема Pydantic может преобразовывать некоторые значения; strict-режим здесь не вводится. Для неверного типа priority подходит заведомо нечисловая строка **high**.

## 03. Параметризация делает матрицу читаемой

**pytest.mark.parametrize** получает имена параметров и набор значений. Pytest запускает каждый набор как отдельный случай. Ниже меняется только title, а priority остаётся допустимым. Проверяются обе включённые границы и значение за ними.

```python
@pytest.mark.parametrize(
    ("title", "expected_status"),
    [("", 422), ("A", 201), ("A" * 120, 201), ("A" * 121, 422)],
)
def test_title_boundaries(client, title, expected_status):
    response = client.post(
        "/tasks",
        json={"title": title, "priority": 1},
    )
    assert response.status_code == expected_status
    if expected_status == 201:
        assert response.json()["title"] == title.strip()
    else:
        assert response.json()["detail"][0]["loc"][-1] == "title"
```

Набор параметров похож на карточки одного эксперимента: на каждой указаны вход и ожидаемый ответ. Меняется одна строка, а сама проверка повторяется. Граница аналогии в том, что каждая строка здесь вызывает настоящий HTTP-запрос и проверяет результат, а не просто описывает пример.

Для priority отдельные случаи проверяют 1 и 5 как допустимые значения, а 0, 6 и нечисловую строку как ошибочные. Для limit мы аналогично проверяем нижнюю и верхнюю границы, выход за них и значение, которое нельзя разобрать. При смешении нескольких неверных полей тест может зависеть от порядка валидации, который контракт не задаёт.

## 04. Отказ должен оставить состояние прежним

Ответ **422** подтверждает отказ на HTTP-границе, но сам по себе не доказывает, что данные не изменились. В тесте мы создаём задачу через API, читаем полную **TaskRead** и stats, отправляем ошибочный PUT или PATCH, а затем снова читаем ту же запись. Сравнение всего объекта обнаружит замену title или **is_done**, которую общий total не заметил бы.

Это похоже на снимок состояния до и после запроса. Но тестовый снимок точнее фотографии: мы сравниваем поля JSON и счётчики. Для поиска отсутствующего ресурса используются отдельные сценарии с корректным body; иначе неверное тело смешало бы две причины ошибки.

Невалидный вход проверяется до выполнения endpoint. Поэтому **422** из-за title не должен добавлять или менять задачу. Это не обещает транзакционность **JsonStorage**: если ошибка проверки ответа возникнет после **save**, она не откатит уже записанные данные.

## 05. PUT и PATCH проверяют разные обещания

Полный PUT требует **title**, **priority** и **is_done**. При успешном обновлении id остаётся прежним. Если поле пропущено, ответом будет **422**; корректный PUT по отсутствующему id получает **404**, а не создаёт запись.

PATCH принимает только часть полей. Пропущенное значение и **null** не меняют поле; пустой PATCH допустим. Явный **false** является значением и должен примениться. Проверка только статуса **200** слишком слаба: мы проверяем false в ответе и читаем задачу ещё раз, одновременно убеждаясь, что остальные поля сохранились.

Для этих случаев не требуется новая реализация операций. Тесты защищают уже выбранный договор: в них не добавляются upsert или историческая уникальность id после удаления максимальной записи.

## 06. Query проверяется по всей цепочке

У **GET /tasks** значения по умолчанию такие: **is_done=None**, **sort_desc=False**, **limit=10**. Сервер сначала фильтрует задачи, затем сортирует результат по id и после этого применяет **limit** от 1 до 50. Для запроса параметров используем **params**, а не собираем URL вручную.

Задачи готовятся в текущем тесте через POST, а ожидаемые id берутся из ответов. Например, для двух открытых задач и одной завершённой можно проверить сортировку открытых id по убыванию и limit в один элемент. Не используем id из другого теста и не сохраняем перестановку или обрезанный список обратно в JSON.

Stats считает весь источник, независимо от фильтра списка. Поэтому после запроса с **is_done=False** в stats по-прежнему видна завершённая запись. Чтение списка, сортировка и limit не меняют файл и не уменьшают общие счётчики.

## 07. OpenAPI описывает форму, тесты проверяют действие

OpenAPI показывает зарегистрированные пути, схемы и успешные статусы. В **TaskCreate** обязательны **title** и **priority**. **TaskUpdate** требует все три изменяемых поля. **TaskRead** содержит четыре публичных поля. У **TaskPatch** нет обязательных полей. Создание отвечает **201**, удаление отвечает пустым **204**.

Спецификация похожа на этикетку прибора: она сообщает заявленные входы и ответы, но не доказывает, что действие изменило хранилище. OpenAPI формируется по зарегистрированным схемам; проверка поведения отправляет запрос и наблюдает ответ и состояние.

```python
document = client.get("/openapi.json").json()
schemas = document["components"]["schemas"]

assert set(schemas["TaskCreate"]["required"]) == {"title", "priority"}
assert set(schemas["TaskUpdate"]["required"]) == {"title", "priority", "is_done"}
assert set(schemas["TaskRead"]["required"]) == {"id", "title", "priority", "is_done"}
assert schemas["TaskPatch"].get("required", []) == []
assert "201" in document["paths"]["/tasks"]["post"]["responses"]
```

Мы сверяем только важные поля и статусы, а не весь JSON OpenAPI и его внутренние ссылки. Тесты запросов отдельно подтверждают фактическую запись, ошибки и сохранность состояния.

## 08. Что мы будем делать в практике

1. **Изолируем данные**: отдельный JsonStorage позволяет тестам работать, не меняя рабочий файл.
2. **Проверим входы**: допустимые границы, 404 и 422 связаны с разными причинами.
3. **Сравним состояние**: отказ не меняет запись, а PUT и PATCH сохраняют разные правила.
4. **Сверим выдачу**: query и OpenAPI подтверждают те же правила без нового CRUD и нового договора.

В центре практики будет **tests/test_contract.py** с настоящими маршрутами приложения. Мы создадим нужные записи в тестовом хранилище, возьмём их id из ответов и сопоставим status, body и повторное чтение.

Результатом станет регрессионный набор, который ловит конкретные нарушения, а не просто увеличивает число assert. Следующий шаг по паспорту проверит прикладное ядро и направление импортов. Операции и HTTP-договор останутся прежними.
