## 00. От чтения к созданию

В прошлом занятии запрос к `GET /tasks` выбирал, какие задачи показать. Данные оставались прежними. Теперь клиент впервые отправит Planner новую задачу.

Для этого нужен не только адрес. Клиент передаёт содержимое в **теле запроса**, или `request body`. В этом занятии тело будет JSON:

```http
POST /tasks
Content-Type: application/json
```

```json
{
  "title": "Повторить HTTP",
  "priority": 4
}
```

Метод `POST` просит сервер выполнить действие с переданными данными. Заголовок `Content-Type` сообщает, что тело записано в формате JSON. Само тело содержит поля новой задачи.

Но сетевые данные нельзя считать готовой задачей. Клиент может пропустить обязательное поле, передать текст вместо числа или прислать значение, которое не подходит правилам Planner. Серверу нужно проверить форму, применить знакомые правила задачи, сохранить результат и только после этого сообщить об успехе.

### Проверим понимание

Клиент прислал запрос на `POST /tasks`, но сервер ещё не обработал его. Создалась ли задача?

- Нет. Пока сервер не принял запрос и не выполнил создание, запись не появилась.
- Да. Сам факт отправки уже меняет Planner.

## 01. Три формы данных, три разные роли

У нас уже есть предметная модель `Task`. Она описывает задачу внутри проекта: с серверным `id`, названием, приоритетом, состоянием выполнения и другими полями модели. Она проверяет правила самой задачи.

HTTP-клиент не должен присылать все внутренние поля. Для Planner отдельная входная схема `TaskCreate` примет название и приоритет. Сначала разберём механику Pydantic на независимой форме отзыва:

```python
from pydantic import BaseModel


class FeedbackCreate(BaseModel):
    text: str
    rating: int
```

`BaseModel` это базовый класс Pydantic. Наследник описывает ожидаемые поля и их типы. FastAPI использует описание, чтобы разобрать JSON, построить объект модели и показать контракт в Swagger UI.

Поля без значения по умолчанию обязательны. Поэтому для отзыва нужны и `text`, и `rating`. Аннотация `int` требует целое число после разбора, но сама не задаёт допустимый диапазон. В обычном режиме Pydantic может преобразовать строку `"4"` в число 4, а слово `"высокий"` разобрать не сможет. В Planner такую же границу разделяют типы полей `TaskCreate` и правила предметной модели `Task`.

`TaskCreate` не включает `id` и `is_done`. Идентификатор и начальное состояние назначает сервер при создании. Входная схема, внутренняя `Task` и публичный JSON-ответ могут иметь разные поля. Это нормальное разделение ответственности, а не дублирование одной модели.

Для ясности сравним роли:

| Форма | Что описывает | Кто отвечает |
| --- | --- | --- |
| `TaskCreate` | Поля, которые клиент передаёт при создании | HTTP-контракт |
| `Task` | Предметную задачу и её правила | Planner |
| JSON-ответ | Данные, которые сервер показывает клиенту | API |

По умолчанию Pydantic игнорирует неизвестные поля. Настройка `extra="forbid"` могла бы превратить их в ошибку, но мы её не добавляем и не требуем отвергать такие ключи. Маршрут передаёт в сервис только `title` и `priority`, поэтому клиентские `id` и `is_done` не управляют создаваемой записью. Также пока не вводим `Field`, строгий режим или валидаторы.

### Что получится после разбора?

```python
payload = FeedbackCreate(text="Полезный пример", rating="4")
print(payload.rating, type(payload.rating).__name__)
```

До раскрытия ответа предскажем результат. На входе было текстовое значение, а что окажется в проверенном объекте?

**Ответ:** `4 int`. Pydantic может преобразовать строку из цифр в целое число. Это не строгий режим. При этом `priority: int` всё ещё не означает, что любое целое число разрешено правилами Planner.

## 02. FastAPI ставит проверку на входе

Модель сама не читает сеть. Чтобы связать её с HTTP, у параметра функции маршрута указывают тип модели:

```python
@app.post("/feedback")
def create_feedback(payload: FeedbackCreate):
    ...
```

FastAPI понимает: `payload` нужно получить из JSON-тела. До вызова функции он читает JSON и просит Pydantic построить модель. Если всё подходит, внутри маршрута уже есть объект с доступом к `payload.text` и `payload.rating`. В Planner тот же механизм наполнит `TaskCreate` значениями из body.

Последовательность важна:

1. Клиент отправляет JSON.
2. FastAPI читает тело и передаёт значения Pydantic.
3. Pydantic проверяет обязательные поля и типы, затем строит модель.
4. Только после успешной проверки FastAPI вызывает функцию маршрута.

Если обязательного поля нет, тело не является ожидаемым объектом или значение нельзя разобрать, FastAPI отвечает `422 Unprocessable Entity`. Это ошибка входных данных. Функция маршрута в таком запросе не запускается, поэтому ни сервис, ни хранилище не вызываются.

```json
{"text": "Полезный пример"}
```

Здесь отсутствует обязательный `rating`.

```json
{
  "text": "Полезный пример",
  "rating": "высокий"
}
```

Здесь поле есть, но текст нельзя разобрать как `int`. Оба запроса получают `422` ещё до бизнес-логики. В Planner так же проверяются наличие `priority` и возможность разобрать его как число.

### Как читать автоматически собранный 422

FastAPI помещает ошибки проверки body в список `detail`. Каждая запись описывает одну проблему. В коротком примере оставим только два важных поля:

```json
{
  "detail": [
    {"loc": ["body", "rating"], "msg": "Field required"}
  ]
}
```

`loc` показывает место ошибки. `body` означает тело запроса, `rating` указывает на конкретное поле. `msg` объясняет, что именно не подошло. Полный ответ может содержать и другие диагностические данные, например тип ошибки и полученное значение.

У `422` после предметной проверки может быть другая форма. Если маршрут сам создаёт `HTTPException`, значение `detail` задаёт приложение. Например, оно может быть одной строкой, а не списком ошибок полей:

```json
{"detail": "Правило предметной модели не выполнено"}
```

Одинаковый статус не означает одинаковый этап отказа: список с `loc` и `msg` указывает на проверку входа, строковое `detail` в этом примере возвращает обработчик после вызова предметной операции.

### Найдём причину ошибки

```python
def create_feedback(payload: FeedbackCreate):
    ...
```

Почему обработчик не обязан отдельно проверять, что `rating` вообще пришёл?

- FastAPI и Pydantic проверяют обязательность до вызова обработчика.
- Параметр функции всегда автоматически получает значение по умолчанию.
- `add_task` читает JSON напрямую из сети.

**Разбор:** первое верно. Если `rating` отсутствует или не разбирается в целое число, объект `FeedbackCreate` не будет создан и функция не начнёт работу. В Planner правила допустимого приоритета всё равно останутся за моделью `Task` и сервисом.

## 03. Входная схема не заменяет Planner

После проверки у нас пока есть только объект `TaskCreate`. Это ещё не сохранённая задача. Входная схема не знает, как устроены постоянный идентификатор, начальный статус, список задач и JSON-файл.

В проекте эти действия уже собраны в `PlannerService.add_task`. Маршрут должен передать сервису только два клиентских поля. Сервис применит правила `Task`, создаст объект, а настроенный `JsonStorage` сохранит его в общий файл. CLI запускает свой экземпляр сервиса отдельно, но тоже работает с этим JSON.

Метод `payload.model_dump()` превращает проверенную модель в обычный словарь Python. Это удобно, когда нужно представить поля, но словарь не становится предметной `Task`, не вызывает сервис и не записывает JSON. Если вернуть его из маршрута, получится только отражение входа, а не создание задачи.

```text
JSON body
   ↓
TaskCreate: форма и тип входа
   ↓
PlannerService.add_task(title, priority)
   ↓
Task: правила, id и начальное состояние
   ↓
JsonStorage: запись в общий файл Planner
   ↓
публичный JSON-ответ
```

В `app.state.planner` лежит уже выбранный сервис. Это не новая копия списка задач. Если обработчик сам добавит запись в отдельный список или вызовет `JsonStorage.save`, API обойдёт существующую архитектуру. Тогда CLI и API могут начать работать с разными источниками данных.

### Соединим роль и ответственность

| Часть | Ответственность |
| --- | --- |
| `TaskCreate` | Прочитать `title` и `priority` из тела запроса |
| `PlannerService` | Выполнить существующий сценарий создания |
| `Task` | Проверить предметные правила и хранить состояние задачи |
| `JsonStorage` | Сохранить результат в общий JSON Planner |

## 04. Успешный POST означает созданный ресурс

Если операция вернула созданную запись, маршрут может собрать публичный ответ. В Planner это четыре знакомых поля: `id`, `title`, `priority` и `is_done`. Входной объект не содержит `id`, потому что его назначает сервер.

Отдельный endpoint отзывов покажет только связь модели с body и успешный код. Обработка и сохранение там пропущены:

```python
@app.post("/feedback", status_code=201)
def create_feedback(payload: FeedbackCreate):
    ...
```

`201 Created` означает, что успешная операция создала ресурс. Здесь показаны только привязка модели к body и настройка кода успешного ответа. Многоточие скрывает обработку отзыва: декоратор сам ничего не сохраняет и не гарантирует `201`, если операция завершилась ошибкой.

В Planner входная схема `TaskCreate` передаст `title` и `priority` уже существующему сценарию `PlannerService.add_task`. После успешного создания API вернёт публичные поля назначенной сервером `Task`. Полную проектную связку мы соберём в практике.

После сохранения ответ можно проверить другими уже готовыми путями проекта:

- `GET /tasks/{task_id}` находит её по id из ответа `POST`;
- `GET /tasks?sort_desc=true&limit=1` показывает запись с наибольшим id первой;
- `GET /stats` учитывает её в статистике;
- CLI читает ту же запись;
- после перезапуска API запись остаётся в JSON.

Обычный `GET /tasks` по умолчанию показывает первые десять id по возрастанию. Поэтому новая запись может не попасть в этот ограниченный список. Её отсутствие там само по себе не доказывает, что создание не сработало. Так мы проверяем не просто красивый ответ, а весь путь до общего постоянного состояния.

### Расставим этапы создания

Соберём реальный порядок одного успешного запроса:

- Маршрут формирует публичный ответ с серверным id.
- Клиент отправляет POST с JSON.
- Сервис создаёт Task и сохраняет её.
- FastAPI и Pydantic разбирают и проверяют тело.

**Ответ:** клиент отправляет запрос → FastAPI и Pydantic проверяют тело → сервис создаёт и сохраняет задачу → маршрут возвращает публичный ответ. `201` появляется только после успешного вызова создания.

## 05. Два вида ошибки, два места проверки

Не всякая ошибка относится к форме JSON. Pydantic проверяет структуру и типы. Но `title: str` допускает строку из пробелов, а `priority: int` не знает, что Planner разрешает значения от 1 до 5. Это правила предметной модели, которые уже существуют в `Task`.

Если значение нарушает правило модели, `add_task` сообщает об ожидаемой ошибке `ValueError`. Для клиента это тоже неверные данные, поэтому маршрут переводит только эту известную ошибку в HTTP `422`. Механизм покажем на независимой операции каталога, чтобы не подменять объяснение готовым маршрутом Planner:

```python
from fastapi import HTTPException


try:
    saved = catalog.add_feedback(payload.text, payload.rating)
except ValueError as error:
    raise HTTPException(status_code=422, detail=str(error)) from error
```

В Planner тот же принцип применяется только вокруг существующего вызова `add_task`: ожидаемый `ValueError` от правил `Task` становится клиентским `422`. Не добавляем `except Exception`: ошибка записи файла, ошибка программирования или повреждённые данные хранилища не должны притворяться неверным запросом. Неуспешный вызов не должен завершаться ответом `201`.

Ошибки формы и предметного правила различаются по месту:

| Случай | Кто замечает | Результат |
| --- | --- | --- |
| Нет `priority` | Pydantic до маршрута | `422`, сервис не вызван |
| `priority` равно `"высокий"` | Pydantic до маршрута | `422`, сервис не вызван |
| `title` из пробелов | `Task` внутри сервиса | `ValueError` превращается в `422` |
| `priority` равно 0 или 6 | `Task` внутри сервиса | `ValueError` превращается в `422` |
| Ошибка записи JSON | Хранилище | Не маскируется как ошибка клиента |

Отсутствующее или неверно типизированное поле отклоняется до запуска маршрута. Известное нарушение правил `Task` также обнаруживается до сохранения. Эти проверки не добавляют новую запись. Ошибка самого хранилища остаётся серверной: текущая запись через `write_text` не даёт гарантии атомарной замены или отката файла, поэтому обещать неизменность JSON при сбое записи нельзя. Для корректного запроса сервис завершает создание, сохраняет задачу и возвращает её маршруту.

### Какой перехват безопаснее?

```python
try:
    saved = catalog.add_feedback(payload.text, payload.rating)
except Exception:
    raise HTTPException(status_code=422, detail="Неверная задача")
```

Это намеренно широкий перехват в независимом примере. Почему он опасен?

**Ответ:** `Exception` поймает не только ожидаемое нарушение предметного правила, но и сбой хранилища, ошибку кода и другие серверные проблемы. Клиент получит ложный `422`, хотя проблема не в его запросе. Перехватываем только ожидаемый `ValueError` вокруг предметной операции.

## 06. Как проверить, что задача действительно появилась

Откроем `/docs` и найдём `POST /tasks`. Схема должна показывать обязательные `title` и `priority`. Через Swagger UI или сохранённую Planner collection отправим JSON:

```json
{
  "title": "Повторить HTTP",
  "priority": 4
}
```

Успешный ответ имеет статус `201` и содержит публичные поля, включая назначенные сервером `id` и `is_done`. Возьмём id прямо из ответа и запросим `GET /tasks/{task_id}`. Для списка зададим явные параметры `GET /tasks?sort_desc=true&limit=1`: новая запись с наибольшим id окажется первой. Обычный `GET /tasks` показывает только первые десять id по возрастанию и может её не включить. Затем сравним запись, статистику и вывод CLI. Повторим чтение после перезапуска API.

Отдельно отправим тело без `priority`, значение `"высокий"`, заголовок из пробелов и приоритет за пределами 1–5. Все эти проверки должны закончиться `422`, но по разным причинам. Для этих validation-отказов новая запись не создаётся. Сбой записи JSON здесь не моделируем и гарантии отката файла не предполагаем.

Можно передать в запросе `id` или `is_done`, чтобы проверить границу доверия. Они не описаны в `TaskCreate`, а маршрут вызывает сервис только с `title` и `priority`. Не требуем отдельной ошибки на неизвестные поля: такая политика настраивается отдельно. Важен результат: клиент не выбирает постоянный id и начальное состояние задачи.

### Самопроверка

- Какой ответ получает запрос без обязательного `priority`?
- В какой момент срабатывает правило «приоритет от 1 до 5»?
- Какая часть проекта назначает id и сохраняет запись?
- Почему недостаточно увидеть `201` и тело ответа?

**Разбор:** первое тело останавливается на проверке Pydantic до маршрута. Диапазон проверяет предметная модель при вызове сервиса. Сервис создаёт задачу и передаёт её хранилищу. Поэтому результат подтверждаем точным чтением по id, списком с явными сортировкой и лимитом, а также через CLI и после перезапуска.

## 07. Что мы будем делать в практике

Мы добавим первую настоящую операцию создания в уже работающий Planner API. Сначала опишем `TaskCreate` с обязательными `title` и `priority`. Затем подключим тело к `POST /tasks`, передадим поля в `app.state.planner.add_task` и вернём публичную запись со статусом `201`. Реальный запрос сохраним в Planner collection и повторим: второй POST должен создать ещё одну задачу, а не вернуть прежний результат.

Проверка пройдёт по двум границам. Отсутствующее или неразбираемое поле отклонит FastAPI до вызова маршрута. Пустой заголовок и приоритет вне диапазона отклонит уже знакомая модель задачи. Маршрут преобразует ожидаемый `ValueError` в `422`, но не скроет ошибки хранилища.

В конце мы проследим созданную запись через `GET /tasks/{task_id}` с id из ответа, список `GET /tasks?sort_desc=true&limit=1`, статистику, CLI и перезапуск сервера. Так мы подтвердим создание и сохранение в том же проекте.

**Граница работы:** не добавляем ограничение длины через `Field`, отдельные модели ответа и обновления, новые поля задачи или собственный механизм сохранения. Это будут следующие шаги курса.
