## 00. От контракта на бумаге к настоящему сообщению

В прошлом блоке мы описали, как клиент и сервер должны общаться. У Planner API появились методы, адреса, входные данные, ожидаемые ответы и ошибки. Но пока это был договор на бумаге. Мы ещё не отправляли по нему ни одного настоящего запроса.

Теперь возьмём HTTP-клиент и пройдём путь сообщения руками. Выберем метод, укажем адрес, добавим параметры или тело, отправим запрос и прочитаем ответ. Для первого опыта собственный сервер не нужен. Мы воспользуемся Postman Echo. Он принимает запрос и возвращает сведения о том, что получил.

К концу практики у нас будет сохранённая коллекция Postman с двумя запросами и проверками ответа. Позже мы сможем использовать тот же подход для Planner API, но сначала сопоставим пути, тело и ожидаемый ответ с его контрактом. Одной замены адреса Echo будет недостаточно.

После занятия вы сможете:

- объяснить, где Postman находится в цепочке клиент-сервер;
- собрать GET-запрос и передать ему query-параметры;
- собрать POST-запрос с JSON body;
- прочитать status, headers и body ответа;
- добавить простые проверки, сохранить запросы и экспортировать их.

## 01. Postman занимает место HTTP-клиента

HTTP-клиент начинает обмен. Он формирует request и отправляет его на адрес сервера. Сервер получает сообщение, выполняет свою работу и возвращает response. Клиент показывает результат.

Представьте стойку выдачи заказов и посетителя с бланком. Посетитель указывает, что нужно, и передаёт бланк. Стойка принимает его и возвращает результат. Postman играет роль посетителя и бланка. Он не становится стойкой и не придумывает ответ за сервер.

Сетевой путь выглядит так:

```text
Postman
  → HTTP request
  → сервер
  ← HTTP response
Postman показывает ответ
```

Postman не является сервером, базой данных или frontend-приложением. Он не запускает Planner API и не исправляет ошибки автоматически. Он даёт разработчику управляемую форму, чтобы проверить request отдельно от кнопок сайта.

Это разделение полезно при отладке. Если запрос, отправленный из Postman, уже неверен, незачем искать проблему в интерфейсе. Если request составлен правильно, но сервер отвечает неожиданно, можно исследовать серверную сторону.

В production разработчики используют API-клиенты для ручного исследования endpoint, проверки нового контракта и воспроизведения бага. Это не отменяет автоматические тесты. Postman помогает быстро исследовать сценарий, а тестовый набор позже повторяет выбранные проверки систематически.

## 02. Собираем request из видимых частей

Рабочая область Postman показывает отдельные поля одного HTTP-сообщения. Интерфейс может менять расположение кнопок между версиями, но роли частей сообщения остаются прежними.

- **Method** сообщает тип операции. GET обычно используют для чтения, а POST передаёт данные и просит сервер выполнить операцию, часто создание resource. Точный результат зависит от endpoint и его контракта.
- **URL** указывает адрес назначения.
- **Params** добавляет query-параметры к URL.
- **Headers** передаёт метаданные request. Например, Content-Type описывает формат body.
- **Body** содержит данные сообщения, если операция их передаёт.
- **Scripts** позволяет выполнить проверки после получения response.
- **Send** отправляет собранный request.
- **Response** показывает то, что сервер вернул: status, headers и body.

Свяжем интерфейс с моделью HTTP:

| Поле в клиенте | Часть HTTP | Вопрос |
| --- | --- | --- |
| Method | method | Какое действие запрашиваем? |
| URL | адрес и path | Куда отправляем request? |
| Params | query | Какие настройки передаём в URL? |
| Headers | headers | Какие сведения о формате или контексте нужны? |
| Body | request body | Какие данные отправляем серверу? |
| Response | response | Что вернул сервер? |

Пока ничего не отправлено, сервер ещё не получил новое сообщение. Изменение полей создаёт черновик request в рабочей области. Кнопка Send запускает сетевой обмен.

### Проверьте понимание

Соедините поле с его ролью:

| Поле | Роль |
| --- | --- |
| Params | query-параметры |
| Body | данные запроса |
| Send | отправка request |
| Response | результат сервера |

Не путайте вкладку Body с response body. Первая относится к сообщению, которое отправляет клиент. Вторая относится к сообщению, которое возвращает сервер.

## 03. Первый GET: знакомимся с Echo-сервисом

Postman Echo это учебный сервис Postman. Он помогает изучать клиент без подключения к реальному API. Сервис отражает сведения о полученном request в JSON-ответе. Для этого ему не нужны наши ключи или данные Planner.

Создайте новый HTTP request и отправьте:

```http
GET https://postman-echo.com/get
```

Адрес состоит из нескольких частей:

| Часть URL | Значение | Роль |
| --- | --- | --- |
| Схема | https | Защищённый транспорт |
| Host | postman-echo.com | Имя сервера назначения |
| Path | /get | Endpoint Echo-сервиса |

После Send Postman показывает response. Успешный ответ Echo обычно имеет status 200 и JSON body. Если query ещё нет, объект args будет пустым. Ответ также включает URL, по которому сервис получил request.

Упрощённый пример:

```json
{
  "args": {},
  "url": "https://postman-echo.com/get"
}
```

Это ответ Echo, а не Planner. Он подтверждает, что request дошёл до учебного сервера и тот вернул response. Echo не создаёт Task, не сохраняет её и не доказывает, что наш будущий API работает.

Различайте две ситуации:

1. **Сервер вернул HTTP response.** У него есть status, headers и body. Даже status 404 является ответом.
2. **Ответ не получен.** Например, адрес ошибочен или сеть недоступна. HTTP status может отсутствовать, потому что обмен не дошёл до получения ответа.

Если запрос не сработал, проверьте URL, выбранный method и подключение к сети. Не исправляйте body, если отправляете пустой GET, а сервер вообще не ответил.

### Найдите причину

В адресе https://postman-echo.invalid/get host заведомо неверный. Какой результат ожидаем: HTTP status от Echo endpoint или сообщение о том, что ответ не удалось получить? Объясните, почему случаи различаются.

## 04. Query-параметры через Params

Query-параметр настраивает запрос через URL. Он подходит, когда клиент уточняет чтение: просит фильтр, сортировку или ограничивает размер списка. В прошлой работе такую роль выполняли course, block, is_done и limit.

Например:

```http
GET https://postman-echo.com/get?course=python&block=10
```

Знак вопроса начинает query-часть URL. Символ & разделяет пары key и value. Вручную собирать строку можно, но легко забыть символ или ошибиться при кодировании специальных знаков.

Для этого в Postman есть таблица Params:

| Key | Value |
| --- | --- |
| course | python |
| block | 10 |

Добавьте две строки в Params. Postman обновит адрес и отправит серверу query в составе URL. Echo вернёт значения в поле args:

```json
{
  "args": {
    "course": "python",
    "block": "10"
  },
  "url": "https://postman-echo.com/get?course=python&block=10"
}
```

Значения query на уровне URL передаются как текст. Будущий сервер может преобразовать block=10 в целое число и проверить его допустимость. Сам Postman не знает, что block должен быть числом. Его задача сейчас состоит в том, чтобы передать пару так, как вы её настроили.

Не добавляйте query в Body. Query является частью URL, body является отдельной частью request. Имена в Params должны совпадать с тем, что ожидает API: course и Course могут считаться разными параметрами.

Запросы часто сохраняют в истории и логах. Не передавайте в URL пароли, секретные токены или личные данные. Для таких значений существуют специальные способы передачи, которые появятся отдельно.

### Интерактивная проверка

Куда попадёт limit=5, если добавить его в Params: в query, request body или response body?

## 05. POST и JSON body

GET из предыдущей части не отправлял данные новой задачи. Теперь соберём POST request и передадим JSON в body. Echo-сервис получит сообщение и вернёт его части обратно.

```http
POST https://postman-echo.com/post
Content-Type: application/json

{
  "title": "Изучить HTTP",
  "priority": 4
}
```

В Postman выберите method POST, откройте Body, выберите raw и формат JSON. Введите корректный JSON-объект. Для raw JSON Postman сам добавляет подходящий заголовок `Content-Type: application/json`. Проверьте его среди заголовков request, но не создавайте второй такой же вручную.

Content-Type описывает отправляемое body. Это не то же самое, что Accept. Content-Type отвечает на вопрос «в каком формате отправлены данные?». Accept сообщает, какой формат ответа предпочитает клиент. В текущем примере Echo возвращает JSON.

JSON требует двойных кавычек вокруг имён полей и текстовых значений. Число 4 записывается числом, без кавычек. Лишняя запятая в конце объекта делает JSON некорректным.

В response Echo вернёт отражённый JSON в поле json:

```json
{
  "json": {
    "title": "Изучить HTTP",
    "priority": 4
  }
}
```

Обратите внимание на границу примера. Запрос отправляется методом POST, но Echo не создаёт Task в Planner. Echo лишь показывает, что получил. Когда Planner API появится, POST /tasks будет иметь собственный смысл и собственный ожидаемый ответ.

Не думайте, что вкладка Body означает только один формат. HTTP body может содержать разные типы данных. Здесь мы используем JSON, потому что Planner API будет обмениваться JSON-представлением Task.

### Сравните два варианта

Вариант A передаёт title=Изучить HTTP в Params. Вариант B передаёт JSON-объект с title в Body. Для создания Task какой источник данных описывает тело будущего resource? Вариант B. Query настраивает request, а body несёт данные объекта.

## 06. Читаем response и добавляем проверки

После Send смотрите на ответ в таком порядке:

1. **Status.** Получен ли HTTP-ответ и какой исход сообщает сервер?
2. **Content-Type.** В каком формате представлен response body?
3. **Body.** Какие данные или описание ошибки вернул сервер?
4. **Headers и дополнительные сведения.** Какие детали полезны для диагностики?
5. **Time и Size.** Сколько занял обмен и сколько данных вернулось?

Status 200 говорит, что этот Echo-сценарий обработан успешно. Но он ничего не говорит о создании Task, потому что Echo не является Planner API. Успешный status и ожидаемое значение body это две отдельные проверки.

Postman может запускать JavaScript-код после того, как пришёл response. Такой код называется post-response script. В нём можно проверить status или значение в JSON. Результат появится в Test Results.

В GET с course=python простая проверка может выглядеть так:

```javascript
const responseData = pm.response.json();

pm.test("Echo вернул курс из query", function () {
  pm.expect(responseData.args.course).to.eql("python");
});
```

Разберём пример:

- pm.response.json() читает JSON body и превращает его в значение, доступное по ключам;
- responseData.args.course указывает на course внутри отражённых query-параметров;
- pm.test создаёт именованную проверку;
- pm.expect(...).to.eql(...) сравнивает фактическое значение с ожидаемым.

Функция внутри pm.test задаёт, что именно нужно проверить. Здесь не нужно запускать JavaScript отдельно или писать сервер. Postman выполняет небольшой скрипт после ответа.

Проверка статуса выглядит короче:

```javascript
pm.test("Status is 200", function () {
  pm.response.to.have.status(200);
});
```

Если ожидание не совпало с реальностью, Postman пометит проверку как failed. Это полезнее, чем бегло посмотреть на JSON и решить, что всё хорошо. Но проверки подтверждают только записанные ожидания. Они не доказывают поведение, для которого мы не отправили запрос.

Если проверка не прошла, найдите её название в Test Results и сравните ожидание с фактическим body. Не меняйте ожидание только ради зелёного результата. Сначала выясните, кто ошибся: request, проверка или endpoint.

Postman-тесты не заменяют unit-тесты Python. Сейчас они наблюдают реальный ответ внешнего сервиса. Позже pytest будет проверять внутреннюю логику нашего приложения.

## 07. Коллекции, окружения и повторяемость

Один request полезен для эксперимента. Но проекту нужны сохранённые сценарии, которые можно открыть снова или передать другому разработчику.

**Collection** группирует связанные requests. В ней можно дать понятные имена, например Read query from Echo и Send JSON to Echo. При сохранении Postman хранит method, URL, параметры, headers, body и проверки.

**Environment** хранит значения, которые меняются в зависимости от цели. Например, адрес сервера может отличаться между учебным Echo и локальным Planner API. Вместо полного адреса используйте переменную base_url:

```text
base_url = https://postman-echo.com
request URL = {{base_url}}/get
```

Активное окружение сообщает Postman, какое значение подставить вместо {{base_url}}. После выбора Echo проверьте итоговый адрес: `{{base_url}}/get` должен превратиться в `https://postman-echo.com/get`. Тогда базовый адрес можно сменить в одном месте.

Переменная меняет только базовую часть URL. Путь `/get` или `/post`, тело запроса и проверки ответа остаются прежними. Поэтому нельзя просто подставить адрес Planner и ожидать, что Echo-сценарии станут проверками Planner: сначала нужно адаптировать их к реальным маршрутам и ответам API.

Collection отвечает на вопрос «какие запросы мы сохраняем?». Environment отвечает на вопрос «какие значения зависят от выбранной цели?». Это разные вещи, даже если они экспортируются рядом.

Сохраняйте коллекцию и окружение в JSON-файлы. Такой экспорт можно импортировать в другой экземпляр Postman и повторить запросы. Экспортируйте только учебные значения. Не кладите в общий файл пароли, приватные токены или реальные персональные данные.

Для отправки запроса через Lightweight API Client аккаунт Postman не обязателен. Но в этой практике мы сохраняем collection и environment в рабочей области, а затем экспортируем их. Для этого сценария нужно войти в личный Postman workspace. Это авторизация в инструменте, а не на Echo-сервисе: самому Echo ключи и credentials не нужны.

Реальная команда может хранить коллекции в репозитории, использовать их для ручных smoke-проверок и запускать в автоматизированном процессе. Крупные проверки дополняют отдельными тестами и подходящими инструментами. Одна коллекция Postman не заменяет всю систему проверки API.

Интерфейс Postman меняется, поэтому полезно узнавать не координаты кнопок, а роль действия. Сохранить request значит добавить его в collection. Подставить базовый адрес значит использовать variable. Экспортировать значит получить переносимый файл.

## 08. Что мы будем делать в практике

В практической работе появится переносимый набор ручных проверок. Сначала мы подготовим папку `studyhub-api/postman` в своей учебной рабочей папке. Это только место для файлов, не исходники платформы и пока не приложение. Затем создадим collection StudyHub HTTP Lab и environment Echo, сохраним GET с query-параметрами и POST с JSON body.

После экспорта в папке должны лежать два разных файла:

```text
studyhub-api/
└── postman/
    ├── http-lab.collection.json
    └── echo.environment.json
```

Postman будет отвечать за сборку и отправку HTTP-сообщений. Echo-сервис будет принимать их и отражать полученные данные. Postman-тесты будут сравнивать части response с ожиданиями. Окружение будет хранить базовый адрес, а экспорт сохранит collection и environment как файлы проекта.

Работа завершена, когда оба запроса можно снова открыть и отправить, GET показывает обе переданные query-пары, POST возвращает отражённый JSON, проверки проходят, а collection и environment экспортированы в заранее подготовленную папку проекта. В следующем занятии мы добавим приложение в тот же `studyhub-api`, не перемещая экспорты.

Это учебный стенд для клиента. В нём пока нет локального Planner API, собственной базы и FastAPI-кода. Мы не выдаём ответ Echo за созданную задачу и не добавляем credentials, потому что сервису они не нужны.

Начните с ролей участников. Postman отправляет request. Echo возвращает response. Проверка сравнивает фактический ответ с ожиданием. Collection и environment сохраняют сценарий для следующего запуска.

В следующей работе мы поднимем собственный сервер и проверим `GET /health` через браузер и Swagger UI. Экспорты Postman останутся в `studyhub-api/postman` без изменений. Позже, когда у Planner появятся подходящие маршруты, мы адаптируем пути и ожидания запросов, а затем направим их на локальный сервер через `base_url`.
