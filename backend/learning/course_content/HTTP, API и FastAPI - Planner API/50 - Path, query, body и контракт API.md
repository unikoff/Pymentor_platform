## 00. Карта уже есть. Теперь нужен подробный договор

В прошлом занятии мы назвали resource tasks, разделили collection и item и составили карту endpoints. Мы уже можем сказать, что /tasks обозначает набор задач, а /tasks/{task_id} выбирает одну Task. Мы также понимаем, какой method нужен для чтения, создания, изменения и удаления.

Но разработчику всё ещё не хватает деталей. Например:

- где передать идентификатор задачи;
- как попросить только открытые задачи;
- где указать лимит списка;
- куда положить title и priority новой Task;
- какой status считать успешным;
- что увидит клиент, если задача не найдена.

Представьте бланк доставки. Адрес отделения говорит, куда пришла посылка. Но для обработки нужны ещё номер заказа, параметры доставки и содержимое посылки. Если каждое значение положить в случайное место, разные сотрудники будут заполнять бланк по-разному.

HTTP request также имеет разные места для разных ролей:

~~~text
path  → какой resource выбрать
query → как настроить чтение
body  → какие данные передать
headers → как понимать сообщение
~~~

А полный контракт описывает не только вход:

~~~text
method + path
входные значения
success status
response
ожидаемые ошибки
~~~

### Небольшой прогноз

~~~python
request = {
    "path": {"task_id": 7},
    "query": {"is_done": False, "limit": 10},
    "body": {"title": "HTTP", "priority": 4},
}

print(request["path"]["task_id"])
print(request["query"]["limit"])
print(request["body"]["title"])
~~~

**Что напечатает код?**

Ожидаемый вывод: 7, 10, HTTP. Здесь значения не смешиваются. Идентификатор выбирает item, query настраивает выборку, body описывает данные Task.

### Что добавляется сейчас

Нам нужно научиться отвечать на один вопрос для каждого значения:

> Оно выбирает resource, настраивает выборку или описывает данные resource?

После этого мы дополним route map Planner API:

- источником входных данных;
- success status;
- формой response;
- ожидаемыми ошибками;
- короткими примерами request и response.

### Чего пока не будет

В этой теме не нужно:

- писать серверные обработчики;
- создавать schemas;
- запускать приложение;
- изучать декораторы;
- реализовывать валидацию в коде;
- подключать storage;
- отправлять настоящий HTTP request.

Сейчас мы проектируем договор. Реализация имеет смысл только после того, как понятно, что именно она должна принимать и возвращать.

## 01. Контракт API является обещанием между клиентом и сервером

Контракт API можно представить как договор между двумя командами. Клиент обещает отправить данные в согласованной форме. Сервер обещает обработать их по определённому правилу и вернуть понятный response.

Если договор неполный, обе стороны начинают додумывать:

- клиент не знает, где передать id;
- сервер не знает, какое поле обязательно;
- клиент не отличает пустой список от ошибки;
- тесты проверяют случайные формулировки;
- изменение одной детали ломает несколько клиентов.

### Из чего состоит минимальный контракт

Для одной операции нужно описать:

1. намерение пользователя;
2. method;
3. path;
4. входные значения и их источники;
5. обязательность значений;
6. success status;
7. форму успешного response;
8. ожидаемые ошибки;
9. пример обращения.

Это не бюрократия. Каждая часть отвечает на свой вопрос.

~~~text
method → что делаем
path → с каким resource
inputs → какие данные получил сервер
success → чем закончился успех
response → что увидел клиент
errors → какие ожидаемые проблемы возможны
~~~

### Почему контракт записывают до кода

Когда разработчик сразу открывает файл с обработчиком, он легко принимает первое удобное решение. Например, кладёт task_id в body, потому что body уже существует. Позже выясняется, что path должен выбирать item, а body описывает только изменяемые поля.

Таблица заставляет сначала объяснить смысл, а потом писать синтаксис. Это похоже на чертёж перед ремонтом: стены можно двигать, но сначала нужно решить, где будет вход и что он должен соединять.

### Независимый пример

Для сервиса бронирования неполный договор может выглядеть так:

~~~text
POST /bookings
данные: какие-то поля
ответ: успех
~~~

Такой документ не отвечает на важные вопросы. Где указать комнату? Какой status означает создание? Что делать, если время занято?

Более полезный вариант:

~~~text
POST /bookings
body: room, starts_at
201: созданное бронирование
409: время занято
~~~

Он ещё не является кодом, но уже задаёт направление реализации и тестов.

### Что контрактом не является

Контрактом не является:

- имя Python-функции;
- путь к файлу storage;
- комментарий, который видит только автор;
- случайный пример без описания правил;
- обещание «вернём что-нибудь».

Контракт должен быть доступен всем участникам, которые отправляют или принимают request.

### Интерактив. Найдите пропуск

~~~text
PATCH /tasks/{task_id}
body: данные
success: 200
~~~

Каких минимум двух деталей не хватает клиенту? Возможные ответы: какие именно поля разрешены, что вернётся в body, какой status при отсутствии Task, где находится id и обязательны ли значения.

### Production-контекст

В production contract используют frontend-разработчики, backend-разработчики, QA, авторы SDK, аналитика и support. Изменение публичного поля или status может требовать согласованного релиза нескольких команд.

Поэтому сначала полезно иметь короткий человекочитаемый договор. Позже его можно дополнить автоматической схемой, но схема не заменяет понимание смысла.

## 02. Path выбирает конкретный ресурс

Path является частью URL, которая показывает расположение resource внутри API. Если операция относится к одному item, идентификатор должен быть виден в path.

~~~text
item path:
/tasks/7
       ↑
       конкретный task_id
~~~

В шаблоне документа мы пишем:

~~~text
/tasks/{task_id}
~~~

В настоящем обращении вместо placeholder будет конкретное значение:

~~~text
/tasks/7
/tasks/42
~~~

### Почему task_id относится к path

До чтения или изменения одной задачи сервер должен понять, какой item выбран. Это вопрос идентичности, а не содержания Task.

Сравните два вопроса:

~~~text
какую задачу выбрать? → task_id
что изменить в задаче? → поля body
~~~

Если смешать их, один и тот же id может оказаться в двух местах и привести к противоречию.

### Path parameter является обязательной частью item

Для item path значение обычно обязательно:

~~~text
/tasks/{task_id}
~~~

Без task_id получится collection /tasks, а не конкретный item. Это не означает, что каждый API обязан использовать числовой id. В качестве идентификатора может быть UUID, slug или другой устойчивый ключ. Важно, что path выбирает один объект.

### Path не является фильтром

Сравните:

~~~text
/tasks/7
~~~

и:

~~~text
/tasks?is_done=false
~~~

Первый вариант выбирает одну задачу. Второй позже будет означать настройку чтения коллекции. Если открытые задачи записать как /tasks/open, путь начинает смешивать фильтр с именем resource.

### Path и права доступа

Path не проверяет права сам по себе. Он только передаёт идентичность выбранного item. Сервер всё равно должен проверить, может ли текущий пользователь прочитать или изменить этот resource.

Это важная граница: видимый id не означает разрешённый доступ.

### Интерактив. Куда положить значение?

У клиента есть значения:

- task_id = 7;
- is_done = false;
- limit = 10;
- title = "HTTP";
- priority = 4.

Какое из них выбирает item? Какое отвечает за содержимое Task? Какие значения относятся к настройке списка? Объясните каждое решение одним предложением.

### С чем путают path

Path путают с полным URL. Полный URL может включать host и port, а path является только внутренней частью адреса:

~~~text
URL:
http://localhost:8000/tasks/7

path:
/tasks/7
~~~

Path также путают с именем Python-параметра. В документе task_id обозначает часть внешнего адреса, а не конкретную переменную в коде сервера.

### Production-контекст

Path-параметры нужны в профилях, заказах, сообщениях, курсах и любых API, где клиент обращается к одному объекту. Они помогают логам, трассировке, правам и кэшу понять, с какой сущностью выполнялась операция.

### Связь с Planner

В Planner task_id нужен для операций с одной Task: чтения, полной замены, частичного изменения и удаления. В карте мы фиксируем только его роль и форму path. Способ преобразовать строку в тип и проверить существование появится при реализации.

## 03. Query настраивает чтение коллекции

Query-параметры идут после знака ? и уточняют запрос к collection. Они не меняют сам тип resource. /tasks остаётся коллекцией задач, а query задаёт условия её чтения.

~~~text
GET /tasks
GET /tasks?is_done=false
GET /tasks?is_done=false&limit=10
~~~

Во всех трёх случаях клиент читает collection tasks. Отличается только настройка выборки.

### Для чего нужен query

Query удобно использовать для:

- фильтра;
- поиска;
- сортировки;
- ограничения количества;
- страницы результата;
- выбора дополнительных опций чтения.

В нашем первом примере:

~~~text
is_done → оставить задачи с нужным статусом
limit → ограничить размер списка
~~~

### Почему query обычно optional

Клиент может не передать фильтр:

~~~text
GET /tasks
~~~

Тогда сервер применяет значение по умолчанию и возвращает обычную collection. Отсутствие необязательного query не должно превращать нормальное чтение в ошибку.

Если параметр передан, сервер проверяет его формат и допустимость. Optional не означает «принимаем любое значение».

### Query не должен скрывать изменение состояния

Фильтр относится к чтению:

~~~text
GET /tasks?is_done=false
~~~

Он не должен помечать задачи невыполненными. Query уточняет, что показать, а method всё ещё выражает GET.

### Query и path отвечают на разные вопросы

~~~text
path:
какой item выбрать?

query:
как посмотреть collection?
~~~

Если клиент хочет получить одну Task, её id остаётся в path. Если клиент хочет получить подмножество списка, настройки чтения идут в query.

### Query и порядок результата

Сортировка также относится к представлению collection:

~~~text
GET /tasks?sort=priority
~~~

Сервер должен определить, какие значения sort разрешены. Нельзя считать, что query превращает пользовательский текст в произвольное имя поля базы данных.

### Query и pagination

Большие collection нельзя всегда возвращать целиком. Query может передать limit и offset или номер страницы:

~~~text
GET /tasks?limit=20&page=2
~~~

Это не меняет сущность tasks. Меняется размер и часть представления коллекции.

### Интерактив. Что изменилось?

Сравните:

~~~text
GET /tasks
GET /tasks?is_done=true
~~~

Ответьте:

1. Изменился ли resource?
2. Изменился ли method?
3. Что должен сделать сервер с результатом?

Меняется условие выборки, но не сущность, к которой обращается клиент.

### С чем путают query

Query путают с body, потому что оба могут содержать пары «имя и значение». Отличие задаёт роль:

- query виден как настройка обращения и часто используется для чтения;
- body передаёт структуру данных, которую сервер должен создать или изменить.

Одинаковое имя поля ещё не делает источник одинаковым. is_done может быть фильтром в GET или изменяемым полем в PATCH.

### Production-контекст

Query влияет на кэширование, лимиты, производительность и стоимость запроса. Для каждого параметра нужно определить тип, default, допустимые значения и поведение при ошибке.

### Связь с Planner

В карте Planner is_done и limit будут примерами query для чтения collection. Мы не проектируем сейчас полный фильтр и не пишем SQL. Фиксируем только роль входных значений и ожидаемую форму запроса.

## 04. Body передаёт данные ресурса

Body содержит основное содержимое request. Он нужен, когда клиент передаёт данные для создания или изменения представления resource.

~~~text
POST /tasks
body:
title
priority
~~~

Здесь body описывает новую Task. Id обычно назначит сервер после проверки и сохранения.

### Body при создании

Для POST body может выглядеть так:

~~~text
{
  "title": "Контракт API",
  "priority": 4
}
~~~

Клиент передаёт управляемые поля. Сервер может добавить id, default для is_done и другие значения, предусмотренные договором.

### Body при полном изменении

PUT обычно получает полное редактируемое представление:

~~~text
PUT /tasks/7
body:
title
priority
is_done
tags
~~~

В договоре нужно явно сказать, какие поля входят в полную форму. Иначе слово «полная» остаётся непонятным.

### Body при частичном изменении

PATCH может передать только изменяемое поле:

~~~text
PATCH /tasks/7
body:
is_done: true
~~~

Остальные поля должны сохраниться по правилам PATCH. Маленький body не означает отсутствие валидации.

### Почему id не нужно дублировать в body

В обращении:

~~~text
PATCH /tasks/7
body:
{
  "task_id": 9,
  "is_done": true
}
~~~

Появились два возможных идентификатора. Серверу придётся решать, какой из них главный. Для простого договора лучше оставить выбор item в path, а body использовать для данных изменения.

### Body не равен внутреннему объекту

Клиент может отправить JSON, а сервер превратить его в dataclass, словарь или другой внутренний объект. Между внешней формой и внутренней реализацией существует граница.

~~~text
body JSON → проверка → внутренняя модель → service
~~~

В обратную сторону:

~~~text
внутренняя модель → представление → response body
~~~

### Content-Type

Header Content-Type сообщает, как читать body:

~~~text
Content-Type: application/json
~~~

Это служебное описание сообщения, а не часть самих данных Task. title и priority относятся к body, а Content-Type относится к способу его разбора.

### Отсутствие поля и null

Для частичного обновления важно отличать:

~~~text
поле отсутствует → не менять
поле есть и равно null → очистить, если это разрешено
~~~

Конкретная политика должна быть частью договора. Нельзя заставлять сервер угадывать намерение клиента.

### Интерактив. Найдите источник ошибки

~~~text
PATCH /tasks/7
body:
{
  "task_id": 9,
  "priority": 5
}
~~~

Почему это неоднозначно? Какую минимальную правку нужно сделать, чтобы path был единственным источником идентичности?

### С чем путают body

Body путают с query, потому что оба могут содержать пользовательские значения. Помогает вопрос:

> Значение настраивает чтение уже существующей collection или описывает данные, с которыми нужно выполнить операцию?

В первом случае смотрим на query. Во втором смотрим на body.

### Production-контекст

Размер body влияет на лимиты, время обработки, безопасность и стоимость. Сервер должен ограничивать размер, проверять типы, не доверять клиентскому id и не принимать внутренние поля без явного правила.

### Связь с Planner

В текущем договоре title и priority будут body-полями для создания. Для PATCH body может содержать разрешённые изменения. Реализацию проверки полей мы не пишем, но должны заранее назвать их роль.

## 05. Одно значение должно иметь понятный источник

Path, query и body не являются тремя случайными контейнерами. У каждого есть задача. Полезно выбирать источник по роли значения, а не по тому, где оказалось свободное место.

### Три диагностических вопроса

Для значения спросите:

1. Оно выбирает конкретный item?
2. Оно настраивает чтение collection?
3. Оно описывает данные resource?

Ответы ведут к разным источникам:

~~~text
выбирает item → path
настраивает collection → query
описывает resource → body
~~~

### Пример с Task

~~~text
task_id → path
is_done в GET → query
limit в GET → query
title в POST → body
priority в POST → body
~~~

Здесь is_done особенно полезен как пример. В GET он отвечает на вопрос «какие задачи показать». В PATCH тот же предметный атрибут может отвечать на вопрос «какое значение записать».

Одинаковое имя не означает одинаковую роль.

### Headers находятся на другом уровне

Header описывает само сообщение:

~~~text
Content-Type → как читать body
X-Request-ID → как связать обращение с логами
~~~

Header не должен подменять id resource или бизнес-поле Task.

### Не нужно передавать всё везде

Плохая привычка выглядит так:

~~~text
path: task_id
query: task_id
body: task_id
~~~

Три копии создают риск расхождения. Дублирование может быть оправдано в сложной интеграции, но тогда правило сравнения и источник истины должны быть описаны отдельно.

### Интерактив. Проверьте пять значений

Распределите значения:

~~~text
task_id
is_done
limit
title
priority
~~~

Дополнительное условие:

- рассматриваем GET collection для is_done и limit;
- рассматриваем POST создания для title и priority;
- рассматриваем item-операцию для task_id.

Запишите не только контейнер, но и причину.

### Типичная ошибка: body для фильтра

~~~text
GET /tasks
body: {"is_done": false}
~~~

Такой формат может встречаться в отдельных системах, но для простого чтения collection он делает контракт менее предсказуемым. Фильтр лучше выразить query, если не существует отдельного обоснованного правила.

### Типичная ошибка: query для новой Task

~~~text
POST /tasks?title=HTTP&priority=4
~~~

Небольшие значения технически можно передать так, но структура создания должна быть согласованной. Для body-данных лучше использовать body и явно описать их форму.

### Production-контекст

Единообразное распределение входов облегчает документацию, клиентские библиотеки, тестирование и поддержку. Когда значение всегда выполняет одну роль, его легче валидировать и логировать.

## 06. Контракт описывает response и ошибки

Даже идеальный вход не делает контракт завершённым. Клиенту нужно знать, что он получит после обработки.

Для каждой операции нужно описать:

- success status;
- форму успешного body;
- отсутствие body, если это важно;
- ожидаемые ошибки;
- смысл каждой ошибки.

### Success status

Для Planner подходят уже знакомые варианты:

~~~text
200 → успешное чтение или изменение с response
201 → новая Task создана
204 → операция успешна, body отсутствует
~~~

Status помогает клиенту выбрать ветку поведения. Body затем передаёт данные.

### Ошибка 404

Если item не существует:

~~~text
GET /tasks/999
→ 404
→ Task not found
~~~

То же смысловое правило может применяться к PUT, PATCH и DELETE для неизвестного item. Клиент должен понимать, что сервер доступен, но выбранный resource не найден.

### Ошибка 400

400 можно использовать как общий пример некорректного request. На этом уровне не нужно описывать все виды валидации. Важно отделить:

~~~text
400 → request нельзя принять по общему договору
404 → выбранного item нет
~~~

Не превращайте 400 в «любая проблема вообще». У ошибки должна быть понятная причина.

### Почему пока не добавляем 422

Детальная валидация полей потребует отдельной темы о схемах и правилах данных. Сейчас достаточно зафиксировать границу:

~~~text
текущий этап:
method, path, query, body, success и базовые ошибки

позже:
подробные схемы и field validation
~~~

Так документ остаётся честным и не делает вид, что все правила уже спроектированы.

### Форма response

Клиенту важно знать, что вернётся:

~~~text
GET /tasks
200 → список Task

POST /tasks
201 → созданная Task

GET /tasks/7
200 → одна Task

DELETE /tasks/7
204 → body отсутствует
~~~

Пустой список и отсутствие item имеют разные формы:

~~~text
collection пуста → 200 + []
item не найден → 404 + ошибка
~~~

### Интерактив. Что напечатает клиент?

У клиента есть два response:

~~~text
A: status 200, body []
B: status 404, body {"detail": "Task not found"}
~~~

Ответьте:

1. В каком случае collection существует, но сейчас пуста?
2. В каком случае отсутствует выбранный item?
3. Почему нельзя заменить B на пустой список?

### С чем путают status

Status путают с текстом body. Клиент не должен искать слово «ошибка» внутри произвольной строки, чтобы понять исход. Status задаёт категорию, body добавляет детали.

### Production-контекст

Стабильные response и ошибки помогают frontend не строить догадки. Они также нужны для retry, мониторинга, аналитики и поддержки. Если 404 иногда означает «нет item», а иногда «сервер упал», клиентская логика становится хрупкой.

### Связь с Planner

В документе мы укажем 200 для чтения и изменения с представлением, 201 для создания и 204 для удаления без body. Для item-операций добавим 404, а 400 оставим общим примером некорректного request.

## 07. Собираем полный договор Planner API

Теперь соединяем всё в одну последовательность. Одна строка карты должна читаться как законченная мысль:

~~~text
намерение
→ method
→ path
→ входы
→ success status
→ response
→ ожидаемые ошибки
~~~

### Health

GET /health является технической проверкой. Он не принимает данные Task, не выбирает collection и не создаёт item.

~~~text
GET /health
inputs: none
success: 200
response: health status
~~~

### Чтение collection

Клиент просит список задач. Optional query может настроить фильтр и размер результата:

~~~text
GET /tasks
query: is_done?, limit?
success: 200
response: list[Task]
~~~

### Создание

Клиент передаёт body новой Task:

~~~text
POST /tasks
body: title, priority
success: 201
response: created Task
~~~

### Чтение item

Клиент выбирает задачу через path:

~~~text
GET /tasks/{task_id}
path: task_id
success: 200
response: Task
error: 404
~~~

### Полная и частичная замена

Обе операции работают с item, но body имеет разный смысл:

~~~text
PUT /tasks/{task_id}
path: task_id
body: full editable Task
success: 200

PATCH /tasks/{task_id}
path: task_id
body: partial update
success: 200
~~~

Для обеих операций неизвестный item должен быть понятным failure path.

### Удаление

~~~text
DELETE /tasks/{task_id}
path: task_id
success: 204
response: no body
error: 404
~~~

### Три коротких сценария

Контракт становится легче проверить на примерах.

#### Фильтр collection

~~~text
намерение: показать открытые задачи
request: GET /tasks?is_done=false&limit=10
response: 200 + список Task
~~~

#### Создание

~~~text
намерение: создать новую задачу
request: POST /tasks
body: {"title": "Контракт API", "priority": 4}
response: 201 + {"id": 8, "title": "Контракт API", "priority": 4}
~~~

#### Частичное изменение

~~~text
намерение: отметить Task 8 выполненной
request: PATCH /tasks/8
body: {"is_done": true}
response: 200 + обновлённая Task
~~~

### Типичные ошибки в полном договоре

Проверьте карту вопросами:

- есть ли id в path, если операция относится к item;
- не спрятан ли фильтр в имени path;
- не отправляются ли данные Task в query без причины;
- различаются ли PUT и PATCH;
- описан ли status создания;
- понятно ли, что возвращает DELETE;
- отделён ли 404 от пустой collection;
- не выдан ли storage за публичный resource.

### Что не нужно решать сейчас

Пока не нужно выбирать:

- конкретный декоратор;
- тип Python-параметра;
- способ подключения базы;
- точные схемы валидации;
- формат OpenAPI;
- способ запуска приложения.

Эти решения будут строиться поверх договора, а не заменять его.

## 08. Что мы будем делать в практике

Практика будет ручной. Мы продолжим редактировать docs/planner-api-v1.md, созданный в предыдущем занятии. Теперь документ превратится из route map в применимый контракт.

### Глобальный результат

После практики в одном файле будет видно:

- что такое resource tasks;
- где находятся collection и item paths;
- где передаётся task_id;
- какие значения идут в query;
- какие данные идут в body;
- какой success status обещает каждый route;
- какая форма response ожидается;
- что происходит при неизвестном item;
- какие темы пока намеренно не раскрыты.

### Последовательность работы

Практика состоит из четырёх карточек, которые дополняют один документ:

1. разнести значения по path, query и body;
2. дополнить route map источниками входов и success status;
3. добавить три коротких примера request и response;
4. зафиксировать ошибки и границы текущего контракта.

Это не четыре независимых файла. Каждая карточка использует результат предыдущей.

### Какой результат считается доказанным

Документ готов, если:

- пять учебных значений распределены по ролям с объяснением;
- все routes из карты имеют входы и success status;
- PUT и PATCH различаются объёмом body;
- есть примеры GET collection, POST создания и PATCH item;
- 404 связан с отсутствующим task_id;
- 400 указан как общий некорректный request;
- 204 не обещает body;
- optional query не назван обязательным;
- path, query и body не дублируют одну и ту же идентичность;
- границы будущих schemas и серверной реализации записаны явно.

### Чего практика не требует

Не нужно:

- запускать сервер;
- писать Python;
- отправлять настоящий request;
- создавать базы и таблицы;
- писать валидацию;
- добавлять декораторы;
- редактировать внутренний Planner.

Сейчас проверяется качество договора. Хороший договор должен быть понятен до реализации.

### Подготовка к следующему шагу

После этой работы мы сможем перейти к реальному HTTP-клиенту. Ученик будет знать, какой request отправлять, куда положить каждое значение и какой response ожидать. Это позволит отличить ошибку клиента от ошибки сервера.

### Короткий итог

~~~text
path → идентичность resource
query → настройка чтения
body → данные resource
headers → описание сообщения
success → обещанный исход
response → результат для клиента
errors → ожидаемые failure paths
~~~

В Planner task_id выбирает item, is_done и limit настраивают чтение collection, а title и priority описывают данные Task. Практика зафиксирует эти роли и завершит контракт до перехода к настоящему клиенту и серверу.
