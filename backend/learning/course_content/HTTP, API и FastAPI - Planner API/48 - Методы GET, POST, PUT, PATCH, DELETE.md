## 00. Один request может означать разные действия

В прошлом занятии мы разобрали ответ сервера. Теперь вернёмся к запросу (request) и сосредоточимся на HTTP-методе (method): он показывает, какое действие клиент просит выполнить. В следующем занятии мы начнём собирать более целостный договор API.

Между этими двумя темами нужен ещё один слой. Одного адреса недостаточно, чтобы понять намерение клиента. Запрос к одной и той же коллекции может:

- попросить список;
- создать новую задачу;
- заменить уже существующую задачу;
- изменить только один параметр;
- удалить задачу.

Представьте шкаф с папкой заявлений. Адрес шкафа говорит, куда пришли. Но сама записка должна сообщить, что сделать: показать папку, добавить лист, заменить лист, поправить одну строку или убрать лист. В HTTP эту роль выполняет метод (method).

~~~text
адрес → с каким объектом работаем
метод (method) → какое действие просим выполнить
заголовки (headers) → как понимать сообщение
тело запроса (body) → какие данные передаём
~~~

### Небольшой прогноз

Посмотрите на обычную Python-функцию:

~~~python
def read_title(task):
    return task["title"]

task = {"title": "Изучить HTTP"}
print(read_title(task))
~~~

**Что напечатает код?**

Ответьте до чтения дальше. Здесь функция только читает значение. Она не меняет словарь и не создаёт новую задачу. Это полезная модель для GET: сначала понять действие, а потом выбрать сетевую форму.

### Что добавляется сейчас

Мы разберём пять стандартных методов:

- GET для чтения;
- POST для создания или передачи новой операции на обработку;
- PUT для полной замены представления;
- PATCH для частичного изменения;
- DELETE для удаления.

Отдельно разберём несколько терминов, которые пригодятся дальше:

- **Ресурс** (resource): данные, к которым обращается API, например список задач или одна задача. В следующем занятии мы разберём, как называть ресурсы и строить карту API.
- **Договор API**: понятные клиенту правила о том, какие запросы принимает сервис, что он делает и какие ответы возвращает.
- **Безопасный по назначению метод** (`safe`) означает, что клиент просит прочитать данные, а не изменить их. Это не защита от взлома.
- **Идемпотентный метод** (`idempotent`) при нескольких одинаковых запросах оказывает на ресурс тот же задуманный эффект, что и один запрос. Ответы и записи в журнале при этом могут отличаться.

### Чего пока не будет

В этой теме не нужны:

- синтаксис маршрутов FastAPI;
- FastAPI;
- параметры адреса;
- база данных;
- настоящая отправка запросов;
- полная реализация операций создания, чтения, изменения и удаления задач.

Сначала нужно научиться видеть смысл метода. Потом этот смысл будет привязан к ресурсу, адресу и коду сервера.

## 01. HTTP-метод выражает намерение клиента

HTTP-метод можно представить как глагол в короткой фразе. Адрес называет объект, а метод говорит, что с ним сделать.

~~~text
GET    задачи       → прочитать задачи
POST   задачи       → создать задачу
PUT    задача 7     → заменить задачу 7 целиком
PATCH  задача 7     → изменить часть задачи 7
DELETE задача 7     → удалить задачу 7
~~~

Здесь важно не заучить пять английских слов отдельно, а увидеть причинную связь:

1. Клиент выбирает объект или группу объектов.
2. Клиент формулирует намерение через метод.
3. Сервер проверяет, разрешено ли такое действие.
4. Сервер возвращает response с результатом.

### Один адрес, разный смысл

Один и тот же адрес может принимать разные методы. Это не противоречие. Адрес отвечает на вопрос «где находится область работы», а метод отвечает на вопрос «что сделать».

~~~text
GET  /tasks → прочитать коллекцию
POST /tasks → попросить создать новую Task
~~~

Если бы мы записывали действие только в тексте адреса, получилось бы много похожих вариантов:

~~~text
/tasks/list
/tasks/create
/tasks/update
/tasks/delete
~~~

Такой стиль иногда встречается в старых или внутренних системах, но стандартные методы HTTP дают клиентам более единый язык.

### Метод не равен имени Python-функции

На сервере могут быть функции list_tasks, create_task и update_task. Это внутренние имена. Клиент не вызывает их напрямую.

~~~text
клиент выбирает HTTP-метод
    ↓
сервер находит подходящее правило
    ↓
внутри может вызвать Python-функцию
    ↓
сервер формирует response
~~~

Поэтому нельзя выбирать HTTP-метод только по названию функции на сервере. Сначала определите смысл операции. Её внутреннее имя может быть любым.

### Интерактив. Найдите глагол

Для каждой фразы назовите действие обычными словами:

1. «Покажи все задачи».
2. «Добавь новую задачу».
3. «Замени карточку задачи полной новой карточкой».
4. «Поменяй только флаг готовности».
5. «Убери задачу из списка».

Проверьте себя по порядку: чтение, создание, полная замена, частичное изменение, удаление. В следующих разделах мы разберём, почему для этих смыслов используются разные методы.

### Где проходит граница

HTTP-метод описывает намерение клиента на внешней границе. Он не говорит, как именно сервер хранит данные. После GET сервер может читать JSON-файл, таблицу базы данных или кэш (временно сохранённые данные или ответ, чтобы быстрее обслуживать повторные чтения). После DELETE он может физически удалить запись или пометить её удалённой по внутренней политике.

Для клиента важен устойчивый внешний договор, а не конкретная технология внутри.

## 02. GET: прочитать текущее состояние

GET предназначен для получения представления ресурса или коллекции. Слово «представление» здесь означает данные в форме, которую сервер отдаёт клиенту. Это может быть список задач, одна задача или сводка.

~~~text
GET /tasks
→ попросить список задач

GET /tasks/7
→ попросить данные задачи с id 7
~~~

### Почему GET не должен изменять данные

Пользователь может открыть страницу несколько раз. Браузер или другая часть системы могут повторить запрос после временной сетевой ошибки. Кэш тоже может запросить данные снова. Если каждое чтение неожиданно меняет задачу, результат зависит от технических повторов, а не от действия пользователя.

Хорошая модель выглядит так:

~~~text
GET → прочитать → вернуть response
GET → прочитать ещё раз → не менять ресурс
~~~

Повторное чтение не обязано вернуть побайтно такой же ответ. Например, другой пользователь мог изменить задачу между запросами. Важно, что сам GET не выполняет запрошенное изменение ресурса.

Повторный GET не должен:

- отмечать задачу выполненной;
- удалять запись;
- создавать новую запись;

Журналы, служебные счётчики и внутренний кэш могут обновляться как побочные эффекты. Когда говорят, что GET безопасен, имеют в виду отсутствие намеренного изменения предметного состояния ресурса.

### Независимый пример

Сервис расписания получает список свободных аудиторий:

~~~text
GET /rooms/free
→ список аудиторий
~~~

Запрос не бронирует аудиторию. Для бронирования нужны другой смысл и отдельный договор API. Клиент может обновлять экран расписания, не опасаясь создать бронь случайным повтором чтения.

### GET и body

Для простого чтения тело запроса обычно не нужно. Всё необходимое для поиска позже можно разместить в адресе или в дополнительных параметрах запроса. Но сейчас нам важнее не синтаксис адреса, а правило: GET сообщает о чтении.

У GET-тела нет общего смысла, определённого HTTP. Поэтому клиенту не стоит отправлять body с GET, если конкретный API явно не описал такое поведение: серверы и промежуточные системы могут его не обработать или отклонить. Наличие body всё равно не превращает GET в метод изменения.

### Где GET полезен в реальных сервисах

GET часто кэшируется, повторяется и вызывается разными клиентами. Это делает его удобным для:

- загрузки страниц;
- получения списков;
- поиска данных;
- проверки текущего состояния;
- работы мобильного приложения при повторном открытии экрана.

Если GET запускает изменение, система становится непредсказуемой. Например, ссылка «/mark-read» в виде GET может сработать из предпросмотра сообщения, поискового робота или фоновой проверки ссылки.

### Интерактив. Что напечатает код?

~~~python
task = {"title": "Прочитать договор", "is_done": False}

def get_task(task):
    return task.copy()

first = get_task(task)
second = get_task(task)
print(task["is_done"], first == second, first is second)
~~~

Сначала предскажите три значения. Затем объясните, что здесь повторяется чтение, а не изменение исходного словаря. Ожидаемый вывод: False True False.

### С чем путают GET

GET иногда путают с «самым простым методом, значит им можно сделать всё». Это опасная привычка. Удобство вызова не заменяет смысл. Если операция меняет состояние, нужно выбрать подходящий метод изменения и описать его договор API.

## 03. POST: создать новый ресурс или передать новую операцию

POST используется, когда клиент передаёт серверу новую информацию для обработки. Частый сценарий в нашем проекте: создать новую задачу внутри коллекции.

~~~text
POST /tasks
body: данные новой задачи
→ сервер проверяет данные
→ сервер назначает id
→ сервер возвращает созданную Task
~~~

### Почему POST подходит для создания

До создания у новой задачи ещё нет серверного id. Клиент обращается к области, где должны появиться задачи, и передаёт данные. Сервер решает:

- допустимы ли значения;
- какой id назначить;
- какие значения выставить по умолчанию;
- как сохранить результат;
- какой response вернуть.

Это похоже на заявление в регистратуре. Человек сообщает сведения, а система регистрирует новую запись и выдаёт номер.

### POST не обещает безопасный повтор

Два одинаковых POST обычно означают две попытки создать запись:

~~~text
POST «создай задачу SQL»
POST «создай задачу SQL»
→ могут появиться две разные задачи
~~~

Это не обязательно ошибка самого HTTP. Возможно, пользователь действительно дважды нажал кнопку. Но клиент может повторить отправку, если истёк срок ожидания ответа (таймаут), и не знать, успел ли сервер создать запись.

В реальных сервисах для денежных операций, заказов и других чувствительных действий используют ключ идемпотентности (`idempotency key`). Это уникальная метка одной операции: при повторной отправке клиент передаёт ту же метку, а сервер по ней распознаёт повтор вместо создания второго заказа. Точные правила такой защиты задаёт договор конкретного API; подробно мы их разберём отдельно.

### POST и уже известный id

Обычно создание отправляется в коллекцию, потому что id назначает сервер. Если система принимает внешний id, это отдельное правило и его нужно явно описать. Нельзя делать вывод «POST всегда сам выбирает id» для всех API, но для учебного Planner это наша модель.

### Где POST применяют в реальных сервисах

POST подходит не только для создания Task. В реальных системах он может:

- зарегистрировать пользователя;
- создать заказ;
- отправить комментарий;
- запустить длительную обработку;
- принять событие от другого сервиса.

Общая идея одна: клиент передаёт новую работу или новую сущность, а сервер принимает решение, как создать результат.

### Интерактив. Найдите риск повтора

Есть кнопка «Создать заказ». Пользователь нажал её один раз, но ответ не пришёл из-за обрыва сети. Клиент отправляет тот же POST второй раз.

Ответьте:

1. Почему клиент не может по одному таймауту понять, был ли создан заказ?
2. Почему два заказа могут быть опаснее, чем два чтения?
3. Какой вопрос нужно добавить в договор API до реализации повтора?

Наводка: нужно спросить, как система узнаёт, что две попытки относятся к одной операции.

### С чем путают POST

POST путают с универсальным «сделать действие». Иногда POST действительно используют для отдельной команды. Но если API построено вокруг ресурсов, сначала проверьте, не выражает ли операция создание, полную замену, частичное изменение или удаление. Точный HTTP-метод помогает клиенту предсказать ответ.

## 04. PUT: заменить полное представление

PUT выражает замену ресурса целиком согласно договору API. Клиент сообщает серверу, каким должно стать полное редактируемое представление.

HTTP допускает и создание через PUT, если клиент заранее знает адрес нового ресурса. В нашем Planner новый `id` назначает сервер, поэтому для создания задачи используется POST к коллекции, а PUT рассматривается как замена уже выбранной задачи.

Представьте анкету на бумаге. Если вы говорите «замените анкету новой версией», система должна получить всю форму, а не только одну строку. Иначе непонятно, случайно ли остальные поля пропущены или их нужно стереть.

### Механика полной замены

~~~text
текущее представление
    ↓ PUT с полной формой
новое представление ресурса
~~~

Пусть у Task есть такие поля:

~~~text
title
priority
is_done
tags
~~~

Полная замена может передать все четыре поля:

~~~text
PUT
title: «Изучить HTTP»
priority: 4
is_done: false
tags: [«backend»]
~~~

Что произойдёт с отсутствующим полем, зависит от договора конкретного API. В одном API оно считается ошибкой. В другом получает значение по умолчанию. В третьем отсутствие означает удаление значения. Поэтому слова «полная замена» не отменяют необходимость чётких правил.

### Почему PUT считается идемпотентным

Если один и тот же полный документ отправить два раза, итоговое состояние должно быть тем же, что после одного такого PUT:

~~~text
PUT → Task стала полной формой X
PUT → Task снова стала полной формой X
итог → Task имеет форму X
~~~

Это не означает, что в журнале будет одна запись или что сервер ничего не делает при повторе. Речь идёт об итоговом состоянии ресурса.

Может отличаться и ответ: например, первый PUT создал ресурс, а следующий обновил уже существующий. Идемпотентность описывает задуманный эффект над ресурсом, а не одинаковый статус ответа.

### Независимый пример

Сервис профилей получает полную карточку настроек:

~~~text
PUT /profiles/12
language: «ru»
theme: «dark»
notifications: true
~~~

Если клиент отправляет эту же полную карточку повторно, профиль остаётся с теми же настройками.

### Где PUT удобен в реальных сервисах

PUT полезен, когда:

- клиент действительно владеет полной формой;
- объект можно описать целиком;
- повторная отправка должна приводить к одному итоговому состоянию;
- серверу удобно заменить одну версию представления другой.

Он менее удобен, когда форма большая, а пользователь меняет одно поле. Передача всей карточки увеличивает риск потерять изменения, сделанные другим клиентом между чтением и обновлением.

### Интерактив. Полная ли это форма?

У Task есть поля title, priority, is_done и tags. Сравните два body:

~~~text
A: {title, priority, is_done, tags}
B: {is_done}
~~~

Ответьте:

1. Какой body ближе к PUT?
2. Какое правило договора API нужно проверить, если пришло только is_done?
3. Почему нельзя молча назвать B полной заменой?

Правильная мысль: B сообщает одно изменение и больше похож на PATCH. Но окончательное правило задаёт договор конкретного API.

### С чем путают PUT

PUT путают с PATCH, потому что оба меняют существующий объект. Различие не в том, что один «сильнее», а другой «слабее». Различие в объёме представления: PUT описывает полную замену, PATCH описывает изменение части.

## 05. PATCH: изменить часть представления

PATCH нужен, когда клиент не хочет передавать всю карточку. Он передаёт описание частичного изменения, а остальные поля должны сохраниться по договору API. Сам метод PATCH не гарантирует идемпотентность: повтор команды «увеличить счётчик на один» снова увеличит счётчик. Но конкретное частичное изменение, например «установить priority в 5», можно спроектировать так, чтобы повтор оставлял то же значение.

~~~text
текущая Task:
title: «Изучить HTTP»
priority: 4
is_done: false
tags: [«backend»]

PATCH:
is_done: true

результат:
title: «Изучить HTTP»
priority: 4
is_done: true
tags: [«backend»]
~~~

### Как сервер понимает PATCH

Упрощённая причинная цепочка выглядит так:

1. Сервер получает частичный набор полей.
2. Проверяет, что эти поля разрешены для изменения.
3. Проверяет типы и значения.
4. Находит текущий ресурс.
5. Накладывает изменения на текущую форму.
6. Сохраняет новую форму и возвращает response.

PATCH не означает «разрешить любые ключи». Если клиент передаст неизвестное поле или попытается изменить серверный id, договор API должен отклонить такой request.

### Почему PATCH удобен для интерфейса

В приложении пользователь часто меняет одну настройку: флаг готовности, приоритет, название. Отправлять всю карточку каждый раз не обязательно. Частичный request:

- меньше по размеру;
- проще сформировать на экране;
- меньше повторяет уже известные данные;
- явно показывает, что именно меняется.

Но маленький body не отменяет конкуренцию изменений. Если два клиента почти одновременно меняют разные поля, договор API должен определить, как объединять изменения и в каком порядке их обрабатывать.

### PATCH и null

В JSON значение `null` означает, что значения нет. API может трактовать его как просьбу очистить поле, если такое правило явно задано. Это отличается от ситуации, когда поле вообще не передано:

~~~text
поле отсутствует → не менять
поле есть и равно null → очистить, если договор API это разрешает
~~~

Это важная граница частичного обновления. Нельзя автоматически считать отсутствие и null одним и тем же. В обычной Python-функции различие можно выразить через наличие ключа. Во внешнем API это должно быть закреплено документацией и валидацией.

### PATCH бывает разным по формату

В реальных сервисах существуют разные соглашения о документах PATCH. Одни передают словарь изменяемых полей, другие описывают список операций `add`, `remove`, `replace` (добавить, удалить, заменить). Для нашего учебного проекта достаточно простой модели: словарь с разрешёнными изменениями. Не нужно вводить более сложный формат, пока не возникла его задача.

### Интерактив. Что сохранится?

Текущая запись:

~~~text
title: «HTTP methods»
priority: 3
is_done: false
tags: [«api»]
~~~

Пришёл PATCH только с priority: 5.

Запишите без кода, какими станут все четыре поля. Затем ответьте, почему сервер не должен заменить отсутствующие title, is_done и tags на пустые значения.

Наводка: PATCH сообщает список намеренных изменений, а не новую полную карточку.

### С чем путают PATCH

PATCH путают с локальным присваиванием без проверки:

~~~python
task.update(incoming)
~~~

Такой код может быть частью реализации, но сам по себе не задаёт надёжные правила API. Сервис должен отдельно проверить разрешённые поля, типы, бизнес-правила и наличие ресурса. HTTP-метод задаёт смысл внешней операции, а не отменяет серверную проверку данных.

## 06. DELETE: попросить удалить ресурс

DELETE выражает намерение удалить конкретный ресурс или убрать его из доступного представления.

~~~text
DELETE /tasks/7
→ сервер находит Task 7
→ применяет политику удаления
→ возвращает response
~~~

### Удаление не всегда означает физическое стирание

В учебном JSON-файле можно удалить объект из списка. В реальном сервисе система может выбрать:

- физическое удаление строки;
- мягкое удаление (`soft delete`): пометить запись как удалённую или скрытую, не стирая её сразу;
- перенос в архив;
- событие для отдельного сервиса хранения.

Снаружи клиенту нужно сообщить, считается ли ресурс удалённым. Внутренний способ хранения является отдельной архитектурной деталью.

### Что делать при повторном DELETE

После первого успешного удаления ресурс отсутствует. Если тот же запрос приходит снова, возможны разные договоры:

~~~text
первый DELETE → 204
второй DELETE → 404
~~~

или:

~~~text
первый DELETE → 204
второй DELETE → 204
~~~

DELETE идемпотентен по стандарту HTTP: задуманный результат повторных запросов тот же, объект остаётся удалённым. Но ответы могут различаться: первый запрос вернёт 204, а повторный, например, 404 или снова 204. Сервер также может отдельно записать каждый запрос в журнал действий, не меняя этим смысл операции.

### Что важно при удалении в реальном сервисе

Удаление требует особой осторожности:

- нужны права пользователя;
- действие может быть необратимым;
- иногда требуется подтверждение;
- полезно вести журнал действий;
- связанные объекты могут потребовать отдельного правила.

HTTP-метод сам по себе не проверяет права и не гарантирует восстановление. Он только выражает смысл запроса.

### Интерактив. Найдите ошибку в ожидании

Разработчик пишет: «Если DELETE вернул 204, значит файл на диске точно уничтожен навсегда».

Почему это слишком сильное утверждение? Назовите минимум две причины. Подсказка: подумайте о мягком удалении, архиве и договоре API.

## 07. Безопасность метода и идемпотентность: два разных вопроса

Теперь соберём два свойства в одну картину. Они отвечают на разные вопросы.

### Безопасность метода по назначению

Безопасный по назначению HTTP-метод не должен изменять состояние ресурса.

Вопрос для проверки:

> Если клиент только хочет узнать текущее состояние, может ли сам факт запроса изменить задачу?

Для GET ответ должен быть «нет» в смысле предметного состояния.

Безопасность метода по назначению не означает отсутствие всех технических эффектов. Сервер всё ещё может записать данные в журнал, обновить служебный счётчик или внутренний кэш.

### Идемпотентность

Метод или операция идемпотентны, если несколько одинаковых запросов оказывают на целевой ресурс тот же задуманный эффект, что и один запрос. Речь о состоянии ресурса, а не о том, сколько раз сервер выполнил внутренний код. Ответы и записи в журналах могут отличаться.

Вопрос для проверки:

> Если сеть повторит тот же request, будет ли итоговое состояние таким же, как после одной обработки?

Это свойство про итог, а не про количество запусков кода или записей в журнале.

### Сравнение методов

| Метод | Намерение | Просит изменить ресурс | Повтор сохраняет тот же задуманный эффект |
| --- | --- | --- | --- |
| GET | прочитать | нет | да |
| POST | создать или принять новую работу | да | обычно нет |
| PUT | полностью заменить | да | да |
| PATCH | частично изменить | да | нет по умолчанию; конкретную операцию можно сделать идемпотентной |
| DELETE | удалить | да | да |

Повторный DELETE может вернуть другой код состояния, чем первый, и всё равно оставлять тот же задуманный эффект. Для PATCH всё решает содержание частичного изменения: повторная установка значения оставляет его прежним, а повторное увеличение меняет его снова.

### Четыре ситуации

~~~text
GET  → не меняет ресурс по назначению; повтор оставляет тот же эффект
POST → меняет ресурс; повтор обычно может создать ещё одну запись
PUT  → меняет ресурс; повтор оставляет тот же эффект
PATCH → меняет ресурс; повтор не всегда оставляет тот же эффект
DELETE → меняет ресурс; повтор оставляет тот же задуманный эффект
~~~

HTTP относит DELETE к идемпотентным методам. Повтор может иметь другой код состояния, но задуманный эффект остаётся тем же: ресурс удалён. Это не запрещает серверу отдельно учитывать каждый запрос в журнале.

### Интерактив. Выберите свойство

Для каждой фразы определите, о чём она: о том, меняет ли запрос данные по назначению, или о последствиях повтора:

1. «Запрос списка не должен менять задачу».
2. «Повторная полная замена оставляет тот же документ».
3. «Два создания могут добавить две записи».
4. «Повторное частичное увеличение счётчика снова увеличит его».

Ответы для проверки: 1 описывает безопасность метода по назначению; 2 описывает идемпотентность; 3 показывает, что повтор POST обычно может создать ещё одну запись; 4 показывает, что последствия повтора PATCH зависят от самой операции.

### Почему это важно для сети

Сеть может терять response, хотя сервер уже обработал request. Клиент видит таймаут и решает повторить вызов. Для чтения и полной замены последствия обычно предсказуемее. Для создания и операций вроде «увеличить на один» нужен дополнительный механизм защиты.

Это одна из причин, почему HTTP-метод является частью договора API. Он помогает заранее обсудить повторы, кэширование, восстановление и ошибки связи.

## 08. Как методы соединяются в одном Planner-сценарии

Теперь соберём не код сервера, а карту смыслов. У нас есть список задач и отдельная задача. Для каждой операции сначала задаём вопрос «что хочет сделать клиент», затем выбираем HTTP-метод.

### Чтение коллекции

Клиент хочет показать список. Он не создаёт и не меняет Task. Значит, нужен GET.

### Чтение одной Task

Клиент хочет показать конкретную задачу. Это всё ещё чтение, даже если объект выбирается по id. Значит, нужен GET.

### Создание

Клиент сообщает данные новой задачи. Id ещё назначает сервер. Значит, нужен POST.

### Полная замена

Клиент передаёт полную форму существующей задачи. Значит, смысл выражает PUT.

### Частичное изменение

Клиент меняет только один или несколько разрешённых параметров и сохраняет остальные. Значит, смысл выражает PATCH.

### Удаление

Клиент просит убрать конкретную задачу из доступного состояния. Значит, нужен DELETE.

### Что именно будет в практике

В практике в редакторе кода мы не будем запускать сервер. Нужно будет написать одну маленькую функцию. Она получает `action`, то есть название операции, и возвращает подходящий HTTP-метод. `list` и `get` означают чтение списка и одной задачи. `create` означает создание, `replace` означает полную замену, `update` в этой задаче означает частичное изменение, а `delete` означает удаление.

Функция будет проверяться на шести смысловых сценариях:

- чтение коллекции;
- чтение одного объекта;
- создание;
- полная замена;
- частичное изменение;
- удаление.

Практика нужна не для механического запоминания английских слов. Она проверяет, умеете ли вы перевести предметное действие в правило взаимодействия по сети. Особенно важно не спутать две операции обновления: полную замену и изменение части.

### Граница упражнения

В этом упражнении нет:

- словаря данных Planner;
- чтения и записи файла;
- HTTP-клиента;
- обработки запросов сервером;
- обработки response.

Это намеренная граница. Сначала фиксируем смысл HTTP-методов. В следующих темах он будет соединён с ресурсом, адресом и полным договором API.
