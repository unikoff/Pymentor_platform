## 00. От готового CLI к новой границе

Persistent Planner уже умеет решать свою предметную задачу. Пользователь может добавить задачу, посмотреть список, изменить состояние и сохранить данные. Модель, прикладной сервис, хранилище и CLI (интерфейс командной строки) разделены, а готовый проект можно запустить из терминала.

На этом месте легко сделать неправильный вывод: «Теперь просто откроем main.py из браузера». Но браузер не является ещё одним способом нажать input() в Python. Он живёт отдельно и обращается к приложению через внешний договор.

В этом уроке **клиент** означает программу, которая начинает обращение, а **сервер** означает программу, которая его принимает и отвечает. `request` (запрос) это сообщение клиента серверу, `response` (ответ) это сообщение сервера клиенту. **API**, или программный интерфейс, задаёт согласованный способ, которым программы просят друг друга о действиях. Это роли в конкретном обмене, а не названия устройств: командная программа тоже может быть клиентом.

Важно не смешивать два проекта. Persistent Planner остаётся прежним приложением с собственными Python-модулями и `tasks.json`. Дальше мы создадим отдельный `studyhub-api` со своей реализацией и своим состоянием. Предыдущий проект нужен как знакомый пример предметных правил и ролей. Его файлы и JSON-хранилище новый API импортировать не будет. В первых версиях нового API состояние будет находиться в оперативной памяти сервера, пока он запущен. После остановки сервера это состояние исчезнет. Такое ограничение запланировано намеренно и не связано со старым файлом `tasks.json`.

Это занятие начинается не с написания серверных функций. Сначала нужно понять, какую проблему решает внешняя граница.

Представьте мастерскую. Внутри находятся инструменты, мастер и склад материалов. Раньше заказчик сам заходил в мастерскую, брал форму и разговаривал с мастером напрямую. Теперь заказчик может оставить заявку через сайт. Мастерская остаётся владельцем работы и материалов, а сайт становится отдельным способом обратиться к ней.

С Persistent Planner происходит похожий переход:

~~~text
сейчас, Persistent Planner:
пользователь → локальный CLI → PlannerService → Task и правила
                                └→ JsonStorage ↔ tasks.json

дальше, отдельный studyhub-api:
пользователь → клиент → request → новый сервер → своя логика и своё хранилище
              клиент ← response ← сервер
~~~

Предметная задача остаётся той же. Меняется граница доступа к ней.

### Почему одного CLI становится мало

У текущего локального CLI есть ограничения, если он остаётся единственным способом пользоваться приложением:

- человеку нужно получить исходный код;
- Python должен быть установлен на его компьютере;
- пользователь должен знать команду запуска;
- локальная копия программы работает рядом со своим файлом данных;
- разные локальные копии обычно не синхронизируют свои файлы автоматически;
- браузер или мобильное приложение работают отдельно и не получают доступ к Python-модулям локального Persistent Planner.

Это не означает, что CLI плохой или что командная строка не может быть сетевым клиентом. Ограничение относится к нынешнему CLI: он напрямую вызывает код Persistent Planner и работает с его локальными данными.

### Что мы узнаем

К концу занятия нужно уметь:

- объяснить разницу между локальным CLI и клиентом;
- назвать роли клиента и сервера;
- показать, где находится источник истины;
- провести путь создания задачи от пользователя до хранилища нового API и обратно;
- объяснить, почему клиент нового API не должен читать `tasks.json` прежнего проекта;
- показать, что клиент и сервер могут находиться на одном компьютере;
- подготовить границу для будущего Planner API.

### Что сознательно не изучаем сейчас

В этом занятии не нужно писать серверный код, запускать реальный сетевой обмен или разбирать адреса и состав сетевых сообщений. Это появится в следующих занятиях. Базу данных мы тоже не подключаем: новый API начнёт с состояния в памяти запущенного сервера, а Persistent Planner продолжит отдельно использовать `tasks.json`.

Эти темы появятся после того, как станет ясна сама граница. Если начать с синтаксиса, можно написать рабочую функцию сервера и всё равно не понимать, кто должен владеть правилами.

**Остановитесь на минуту.** Если завтра появится мобильное приложение, нужно ли копировать в него код Task, PlannerService и чтения JSON? Нет. Мобильному приложению нужен внешний договор с новым сервером. Сам сервер будет отдельной реализацией, а не копией старых файлов.

## 01. Что делает локальный CLI

CLI, или command-line interface, это интерфейс командной строки. Пользователь вводит команду в терминале, а программа читает ввод, вызывает прикладную логику и печатает результат.

### Текущий путь

~~~text
человек
  ↓ ввод
CLI
  ↓ прямой вызов Python
PlannerService
  ├── применяет правила и работает с Task
  └── читает или записывает через JsonStorage ↔ tasks.json
  ↓ результат
CLI
  ↓ вывод
человек
~~~

В текущем варианте части находятся в одном приложении и обычно в одном процессе, то есть в одной запущенной программе. CLI напрямую вызывает `PlannerService`, потому что они принадлежат одному проекту. Это свойство именно нынешней реализации, а не всех программ командной строки.

### Что в CLI удобно

CLI хорош, когда:

- разработчик проверяет новую операцию;
- приложение используется локально;
- важна быстрая автоматизация;
- команда запускается из скрипта;
- не нужен отдельный экран;
- данные принадлежат одному окружению.

Такой интерфейс не нужно выбрасывать после появления API. Его можно оставить для администрирования, отладки или автоматических сценариев. При желании отдельная командная программа тоже может обращаться к серверу как клиент.

### Где появляется ограничение

Представим нового пользователя. Ему нужно:

1. получить репозиторий;
2. установить Python;
3. установить зависимости;
4. понять, какую команду запускать;
5. разобраться, где лежит файл данных;
6. научиться пользоваться меню.

Для учебного проекта это допустимо. Для сервиса, которым пользуются разные клиенты, неудобно.

Главная проблема не в том, что терминал выглядит просто. Проблема в том, что интерфейс находится слишком близко к внутреннему коду и локальному состоянию.

### CLI не является источником истины

CLI должен передавать намерение пользователя и показывать результат. Он не должен становиться владельцем правил.

Например, правило «priority находится в диапазоне от 1 до 5» не должно существовать только в разборе команды. Если завтра появится браузер, он может отправить значение напрямую на сервер. Сервер всё равно обязан проверить его сам.

### Независимый пример

~~~python
def show_temperature(value):
    if value < -50 or value > 60:
        raise ValueError("temperature is outside the sensor range")
    return f"{value} C"
~~~

Если эту функцию вызывает только CLI, это не делает CLI владельцем правила. Правило относится к самой предметной операции и должно оставаться доступным для других входов.

### В реальном сервисе

В реальном сервисе разные способы обращения могут вести к общей прикладной логике: например, запрос через API, фоновая задача, команда администратора или тест. Интерфейсы отличаются, а правила предметной области не должны копироваться в каждый из них. В нашем учебном пути новый API будет отдельным проектом, поэтому мы переносим понимание ролей, а не импортируем старые модули.

Это одна из причин, по которой мы разделяли CLI и service в предыдущем проекте. Теперь эта граница становится внешней.

**Проверьте себя.** Что нужно заменить, если вместо терминала появится браузер: сами правила задач или способ общения с пользователем? Меняется способ общения. Правила остаются на серверной стороне, но новый API реализует их в собственном проекте и работает со своим хранилищем.

### Связь с текущей работой

Persistent Planner уже показывает, как отделять правила задач от интерфейса. Но новый `studyhub-api` не будет обращаться к старому `PlannerService` и `JsonStorage`: он получит собственные модули. Сейчас мы переносим архитектурную идею, а не код.

## 02. Клиент формулирует намерение

Клиент это роль программы, которая начинает обращение к серверу в конкретном обмене. Чаще всего такая программа действует от имени пользователя. Та же программа может обращаться к одному серверу как клиент, а сама предоставлять услуги другой программе.

Клиентом может быть:

- браузер;
- мобильное приложение;
- программа для компьютера;
- командная программа, если она отправляет запрос серверу;
- другой сервис или Python-скрипт.

Человек может сидеть перед браузером, но в сетевом смысле запрос отправляет программа-клиент.

### Клиентский путь

~~~text
пользователь нажал «Показать задачи»
    ↓
клиент понял намерение
    ↓
клиент подготовил request
    ↓
клиент отправил обращение серверу
    ↓
клиент получил response
    ↓
клиент показал результат человеку
~~~

Клиент отвечает за взаимодействие со своим пользователем. Он знает, как выглядит кнопка, где находится поле ввода и как показать ответ на экране.

### Что клиент может делать

Клиент может:

- показать форму;
- собрать введённые значения;
- выбрать, какую операцию попросить;
- отправить запрос;
- показать успешный результат;
- показать понятное сообщение о проблеме;
- временно сохранить состояние экрана;
- повторить запрос по правилам интерфейса.

Это не означает, что клиент может доверять собственным проверкам. Удобная проверка на экране помогает человеку, но не заменяет серверную защиту.

### Чего клиент не должен делать

Клиент не должен:

- читать tasks.json напрямую;
- напрямую импортировать PlannerService из старого Persistent Planner;
- самостоятельно выдавать окончательный id;
- решать, существует ли задача;
- единолично проверять предметные правила;
- изменять файл источника истины;
- считать статистику из устаревшей локальной копии;
- объявлять операцию выполненной до ответа сервера.

Почему? Потому что завтра появится второй клиент. Если каждый клиент повторяет правила, они со временем разойдутся.

### Аналогия с кассой

Покупатель может проверить, что в корзине есть нужный товар. Но именно касса и склад подтверждают остаток, цену и успешную оплату.

Клиент похож на корзину и экран заказа. Сервер похож на кассу и склад. Экран может быть удобным, но он не становится источником истины.

### Независимый пример

~~~text
клиент:
  «Пользователь хочет открыть задачу с id 7»

сервер:
  «Я проверю, есть ли задача 7, и верну результат»

клиент:
  «Покажу результат или понятную ошибку»
~~~

Клиент не говорит: «Я решил, что задача 7 существует». Он просит сервер проверить состояние.

### Что происходит в реальном сервисе

Клиент может быть недоверенным. Пользователь способен изменить код браузера, отправить запрос вручную или написать собственный скрипт. Поэтому сервер повторно проверяет всё, что важно для данных и правил.

### Интерактив

**Найдите нарушение.**

Ниже схематичный псевдокод. Вспомогательные функции чтения и записи не показаны, а для примера предполагается, что список уже содержит задачу.

~~~python
# код браузерного клиента
tasks = read_json("tasks.json")
next_id = max(task["id"] for task in tasks) + 1
tasks.append(new_task)
write_json("tasks.json", tasks)
~~~

Такой клиент стал вторым сервером. Он читает источник истины, выдаёт id и меняет данные напрямую. Правильная граница отправляет намерение серверу.

### Связь с текущей работой

В практическом документе нужно явно записать, что клиент формирует request и показывает response. Также нужно перечислить запрещённые обязанности клиента, чтобы будущий API не превратился в удалённую копию CLI с доступом к файлам.

## 03. Сервер хранит правила и источник истины

Сервер это процесс, который принимает обращения клиентов, выполняет прикладную работу и возвращает результаты.

Слово «сервер» не означает обязательно отдельный физический компьютер. Сейчас сервер может работать на том же ноутбуке, что и браузер. Важны роли и направление общения.

### Серверный путь

~~~text
сервер запущен
    ↓
ждёт обращение
    ↓
понимает намерение
    ↓
проверяет данные
    ↓
вызывает прикладное правило
    ↓
читает или меняет источник истины
    ↓
формирует response
~~~

В нашей будущей модели API-сервер будет ждать новые обращения и обслуживать их по одному внешнему договору. Здесь важно не то, сколько длится процесс, а то, что он принимает сообщения и отвечает на них.

### Что сервер должен делать

Сервер должен:

- принять request;
- проверить входные данные;
- выбрать нужную прикладную операцию;
- применить правила задач в собственной прикладной логике нового API;
- обратиться к собственному хранилищу;
- вернуть успешный результат или понятную ошибку;
- не раскрывать клиенту внутреннюю структуру файлов без необходимости.

### Источник истины

Источником истины называют место, которому система доверяет при определении текущего состояния.

В нынешнем Persistent Planner сохранённое состояние находится в `JsonStorage` и файле `tasks.json`. Новый API будет отдельно владеть своим состоянием в памяти запущенного процесса. Пока процесс работает, серверная сторона определяет актуальное состояние; после остановки память очищается. Это не долговременное сохранение, которое обеспечивает `JsonStorage` в Persistent Planner. Клиент может временно показывать полученную копию, но не должен считать её главным состоянием и менять файл напрямую.

~~~text
клиентская копия экрана
        ≠ источник истины

серверные правила
        ↓ читают и изменяют
состояние нового API в памяти процесса = актуальное состояние
~~~

Клиент может временно хранить копию ответа для быстрого повторного показа. Такую копию называют кэшем. Она не должна незаметно заменять актуальное состояние сервера.

### Сервер не должен знать интерфейс

Серверной прикладной логике не нужно зависеть от деталей экрана:

- цвет кнопки;
- расположение формы;
- название вкладки;
- размер шрифта;
- покажет ли интерфейс ошибку в модальном окне или в строке.

Серверу важно знать смысл операции, данные и правила. При этом внешний договор может сообщать тип клиента, если это нужно, например, для прав доступа или совместимости версий. Главное, чтобы предметные правила не зависели от цвета кнопки или расположения формы. Так можно менять интерфейс без переноса прикладной логики.

### Аналогия с библиотекой

Читатель приходит не к конкретному библиотекарю домой и не забирает базу книг. Он делает запрос библиотеке. Библиотека проверяет каталог, находит книгу и сообщает результат.

Клиент это читательский интерфейс. Сервер это библиотека с правилами и каталогом. Файл или база данных находятся ещё глубже.

### В реальном сервисе

Один сервер может обслуживать браузер, мобильное приложение, интеграцию и автоматическую фоновую задачу. Это особенно важно, когда правила оплаты, доступа или изменения данных нельзя размножать по интерфейсам.

**Верно или неверно.** Сервер обязан находиться на другом компьютере. Неверно. Если браузер отправляет запрос Python-приложению и получает ответ, они могут играть роли клиента и сервера на одном компьютере. Само наличие двух процессов ещё не делает их клиентом и сервером.

### Связь с текущей работой

В документе нужно закрепить, что новый сервер проверяет данные, выполняет правило и обращается к собственному хранилищу. Сейчас мы фиксируем владельца ответственности, а не реализуем сервер.

## 04. Клиент и сервер могут быть на одном компьютере

На этапе разработки часто используются:

- браузер как клиент;
- Python-процесс как сервер;
- один ноутбук как физическая машина.

Это не отменяет границу. Браузер не импортирует Python-класс напрямую. Он обращается к процессу сервера и получает ответ по согласованному сетевому протоколу. Роли определяет обмен сообщениями, а не то, что процессы просто запущены рядом.

### Две роли

~~~text
один ноутбук
├── процесс браузера
│     └── клиент
└── процесс Planner API
      └── сервер
~~~

Сервер слушает адрес. Клиент знает, куда отправить обращение. Между ними существует сообщение, а не прямой вызов метода в памяти клиента.

### localhost

Во время локальной разработки часто используется имя localhost. Оно означает «этот же компьютер».

Это полезно для обучения:

- запрос не уходит во внешний интернет;
- сервер можно запускать локально;
- клиент и сервер удобно проверять рядом;
- ошибка видна сразу.

Но localhost не означает «весь интернет» и не делает приложение публичным для другого компьютера.

### Порт как простая аналогия

У одного компьютера много процессов. Порт можно представить как номер двери, через которую клиент ищет нужный сервер.

~~~text
компьютер: localhost
дверь 8000: Planner API
~~~

Подробные адреса и реальные сетевые запросы будут в следующих материалах. Сейчас достаточно понимать, что клиенту нужен адрес запущенного сервера. Число 8000 служит примером порта.

### Что нельзя перепутать

- один компьютер не означает один процесс;
- localhost не означает внешний адрес;
- браузер не получает доступ к памяти Python;
- сервер не видит автоматически все данные на компьютере клиента;
- запрос не является прямым вызовом PlannerService из браузера.

### Независимая проверка

~~~text
браузер нажал кнопку
    ↓
сообщение покинуло процесс браузера
    ↓
сервер принял сообщение
    ↓
сервер выполнил Python-код
    ↓
ответ вернулся в браузер
~~~

Спросите себя: где находился Task до ответа? В серверном процессе. Браузер получил только внешнее представление результата.

### В реальном сервисе

Сервер и клиент часто находятся на разных машинах или в разных облачных средах. Но локальная модель полезна, потому что показывает роли без лишней инфраструктуры.

## 05. Request и response связывают две стороны

Request это обращение клиента к серверу. Response это результат, который сервер возвращает клиенту.

Пока не нужно разбирать все поля request. Важно понять направление и отличие сообщения от внутреннего вызова функции.

### Request

Request сообщает:

- кто обращается;
- какое намерение нужно выполнить;
- к какому ресурсу относится действие;
- какие данные нужны для операции.

В следующем занятии мы подробнее разберём, из каких частей состоит request. Сейчас его можно представить как заполненный бланк обращения.

### Response

Response сообщает:

- получилось ли действие;
- какой результат нужно показать;
- есть ли проблема;
- какие данные можно отобразить клиенту.

Это не обязан быть объект Task из памяти Python. Сервер формирует внешнее представление, пригодное для передачи.

### Полный цикл

~~~text
клиент
  ↓ request: «создать задачу»
сервер
  ↓ проверка и прикладная операция
хранилище нового API
  ↑ текущее состояние
сервер
  ↑ response: «задача создана»
клиент
  ↑ показывает результат
~~~

Внешний клиент нового API не знает, как тот хранит данные внутри. Он получает согласованный результат. В первой версии сервер использует собственное состояние в памяти процесса, а Persistent Planner продолжает отдельно сохранять данные через `JsonStorage`.

### Request не равен вызову функции

Внутри одного Python-процесса можно написать:

~~~python
service.add_task("Закончить главу", priority=3)
~~~

Это прямой вызов метода. Клиент-серверная модель выглядит иначе:

~~~text
клиент отправил request
сервер принял request
сервер внутри вызвал прикладной код
сервер отправил response
~~~

Клиент не должен знать имя Python-метода. Иначе внешний договор окажется связан с внутренней реализацией.

### Ошибка тоже является response

Если задача не найдена, сервер не должен молча вернуть случайный список. Он формирует понятный результат ошибки, а клиент решает, как показать его человеку.

Так разделяются:

~~~text
сервер: определяет смысл ошибки
клиент: выбирает представление ошибки
~~~

Правило «задача с таким id отсутствует» относится к серверной предметной области. Правило «покажем красную плашку» относится к клиенту.

### В реальном сервисе

Разные клиенты могут по-разному отображать один response. Браузер покажет карточку, мобильное приложение обновит экран, а другая серверная программа обработает машинный результат. Это возможно при стабильном внешнем договоре.

**Соберите порядок.**

~~~text
response → состояние → клиент → серверная операция → request → клиент
~~~

Соберите порядок от первого действия до последнего: клиент формирует request, сервер принимает его и выполняет операцию, при необходимости читает или обновляет своё состояние, затем отправляет response клиенту.

### Связь с текущей работой

В практике запрос и ответ будут частью диаграммы создания задачи. Это пока концептуальная схема. Состав реального запроса появится позже.

## 06. Один сценарий создания задачи через все границы

Чтобы проверить понимание, возьмём одно действие: пользователь хочет создать задачу.

### Шаг 1. Намерение

Пользователь вводит заголовок и выбирает создание задачи. Клиент понимает намерение и готовит обращение.

Клиент не должен сразу считать задачу созданной. До ответа сервера это только намерение.

### Шаг 2. Request

Клиент отправляет request на сервер. Внутри request будут данные, которые нужны операции. Их точное место мы разберём дальше.

Сейчас важно, что request пересекает границу процесса.

### Шаг 3. Серверная проверка

Сервер принимает данные и передаёт их в подходящую прикладную операцию. Проверка должна выполняться на сервере, даже если клиент уже подсветил поле.

Почему? Клиент может быть изменён, сломан или заменён другим клиентом.

### Шаг 4. Предметные правила на сервере

В старом проекте `PlannerService` координирует операцию, а `Task` описывает данные и правила одной задачи. Это помогает понять роли, но новый API не импортирует эти классы. В нём появятся собственные модули, которые реализуют тот же предметный смысл.

### Шаг 5. Хранилище нового API

Если операция успешна, серверная логика обновляет актуальное состояние в хранилище нового проекта. В первой версии это состояние находится в памяти процесса и не переживает его остановку. В Persistent Planner файл `tasks.json` обслуживает `JsonStorage`; новый API не будет читать или менять этот файл. Конкретный способ хранения не становится частью договора с клиентом.

~~~text
клиент нового API не знает:
  где и в каком виде хранит данные новый сервер
  как устроены его внутренние Python-модули

старый Persistent Planner отдельно использует JsonStorage и tasks.json

сервер знает:
  как применить правило
  как обновить состояние в памяти процесса
  как сообщить результат
~~~

### Шаг 6. Response

Сервер формирует внешний результат. Клиент получает его и показывает пользователю.

Если операция не удалась, response сообщает ошибку. Клиент не исправляет состояние файла сам.

### Полная схема

~~~text
пользователь: «создать задачу»
    ↓
клиент формирует request
    ↓
новый API-сервер проверяет вход
    ↓
собственная прикладная логика API применяет правило
    └── собственная логика обновляет состояние в оперативной памяти
    ↓
сервер формирует response
    ↓
клиент показывает результат
~~~

### Почему эта схема важнее кода

Пока мы не написали серверный код, уже можно понять:

- где будет внешний вход;
- где останутся правила;
- где находится источник истины;
- что должен получить клиент;
- почему клиент не должен читать файл.

Хорошая архитектура сначала отвечает на эти вопросы, а потом выбирает синтаксис.

### Ошибочный путь

~~~text
клиент
  ↓ читает tasks.json
клиент сам создаёт id
  ↓
клиент пишет файл
  ↓
сервер получает уже изменённое состояние
~~~

Здесь сервер больше не владеет данными. Два клиента могут одновременно создать одинаковый id или применить разные правила.

### В реальном сервисе

Такое разделение важно при одновременной работе, безопасности и росте нагрузки. Когда несколько клиентов изменяют одни данные, решение должно приниматься в одном доверенном месте.

**Найдите границу.** Кто читает и записывает `tasks.json` в нынешнем Persistent Planner? Серверная сторона через `JsonStorage`, а не браузер. Это не значит, что любой код JSON принадлежит хранилищу: чтение файла и представление данных в сетевом сообщении решают разные задачи и будут разобраны отдельно. Новый `studyhub-api` не будет читать этот старый файл.

### Связь с текущей работой

В практике нужно нарисовать путь: client → request → новый API-сервер → его собственная прикладная логика и хранилище → response → client. Старые `PlannerService`, `Task` и `JsonStorage` можно упомянуть как знакомые примеры ролей, но не изображать импортированными модулями нового проекта.

## 07. Спроектируем границу до реализации

Практика этого занятия является проектной. Её результатом станет документ docs/client-server-boundary.md, а не работающее серверное приложение.

### Пять действий пользователя

Граница должна покрыть пять знакомых действий:

1. показать список задач;
2. получить одну задачу;
3. создать задачу;
4. обновить задачу;
5. удалить задачу.

Для каждого действия полезно описать:

- намерение пользователя;
- работу клиента;
- работу сервера;
- чтение или изменение состояния в памяти процесса;
- результат, который увидит клиент.

### Матрица ответственности

| Действие | Клиент | Сервер |
| --- | --- | --- |
| Показать список | просит список и показывает response | читает актуальные задачи |
| Получить одну | передаёт выбранный идентификатор | проверяет id и возвращает задачу или ошибку |
| Создать | отправляет введённые данные | проверяет, создаёт и добавляет задачу в своё состояние |
| Обновить | отправляет изменение | применяет правило и меняет своё состояние |
| Удалить | просит удалить выбранную задачу | проверяет id и меняет своё состояние |

Эта таблица не является готовой реализацией сервера. Она фиксирует смысл до написания кода.

### Запреты клиента

В документе нужно отдельно записать, что клиент:

- не читает tasks.json;
- не импортирует PlannerService;
- не выдаёт окончательный id;
- не решает, существует ли задача;
- не является владельцем правил Task;
- не объявляет успех до ответа сервера.

Рядом добавьте причину каждого запрета. Например, прямое чтение файла создаёт второй источник истины.

### Запреты сервера

Серверная прикладная логика не должна зависеть от:

- расположение кнопки;
- цвет интерфейса;
- название вкладки;
- вид модального окна;
- способ локального отображения сообщения.

Сервер отвечает за смысл и данные, а не за дизайн. При необходимости внешний слой может различать клиентов для проверки доступа или версии договора.

### Два клиента и один сервер

Полезно представить браузер и Python-скрипт. Они могут отличаться интерфейсом и быть написаны независимо, но оба используют один договор нового API.

~~~text
браузер ───────┐
               ├── новый сервер Planner API ── своя логика и своё хранилище
Python-скрипт ─┘
~~~

Если клиенту нужно читать `tasks.json` или копировать правила старого `PlannerService`, граница спроектирована неправильно.

### Что не входит в документ

Не нужно добавлять код работающего сервера, подробные адреса, параметры запроса или устройство частей сетевого сообщения. Эти темы появятся позже. Сейчас мы только фиксируем роли и границу.

### В реальном сервисе

Документы границ полезны до реализации, потому что помогают нескольким разработчикам одинаково понимать систему. Позже этот документ станет опорой для договора запросов, тестов и архитектурной проверки.

## 08. Что мы будем делать в практике

Практика не меняет Persistent Planner и не встраивает его модули в новый API. Мы используем старый проект как знакомый пример предметных правил, а затем проектируем границу для отдельного `studyhub-api`.

### Общий результат

В конце появится docs/client-server-boundary.md. По нему другой разработчик сможет понять:

- что сейчас делает CLI;
- зачем нужен отдельный клиент;
- какие роли у клиента и сервера;
- где находится источник истины;
- как проходит создание задачи;
- что клиенту запрещено делать и от каких деталей экрана зависит серверная логика;
- почему состояние нового API не переживает остановку процесса;
- почему JSON-файл старого проекта не является сетевым сообщением;
- почему код сервера появится позже.

### Карточки практики

Карточки здесь не отдельные вопросы с ответами, а последовательные этапы сборки одного файла `docs/client-server-boundary.md`. Не создавайте отдельные документы: результат каждой карточки становится частью этого же файла и опорой для следующей.

1. **Исходная точка и цель.**
   Откройте документ описанием текущего CLI, затем объясните, зачем нужен отдельный `studyhub-api`.

2. **Карта пяти операций.**
   Добавьте матрицу списка, чтения одной задачи, создания, обновления и удаления. Для каждой операции укажите работу клиента и нового сервера.

3. **Правила границы.**
   Выведите из матрицы, что клиенту нельзя делать и почему. Объясните, что интерфейс может проверять форму для удобства, но окончательные правила принадлежат серверу. Укажите, от каких деталей экрана серверная логика не зависит.

4. **Путь создания задачи.**
   Используйте строку «Создать» из матрицы. Проследите request через собственную логику API до response и покажите временное состояние в памяти. Отдельно отметьте старый `JsonStorage` и файл `tasks.json`.

5. **Второй клиент и приёмка документа.**
   Проверьте ту же операцию на примере браузера и отдельного Python-скрипта. Затем прочитайте весь документ и устраните противоречия между матрицей, правилами границы и схемой.

### Доказательства готовности

Практика выполнена, если:

- документ существует и читается без устного объяснения;
- пять действий описаны отдельно;
- роли клиента и сервера не дублируются;
- состояние нового API находится в памяти его серверного процесса и исчезает после остановки, отдельно от `tasks.json` прежнего проекта;
- путь создания задачи виден от намерения до response;
- два разных клиента могут использовать один серверный договор;
- Persistent Planner не изменён;
- детали реализации сервера оставлены следующим занятиям.

### Границы результата

Сейчас мы не строим работающий сервер. Не нужно писать код только для того, чтобы документ выглядел техническим. На этом этапе архитектурная ясность является самостоятельным результатом.

Следующая работа разберёт части request. Для неё уже будут готовы роли, общий путь и причина существования внешнего интерфейса.

### Перед переходом
