## 00. От готового CLI к новой границе

Persistent Planner уже умеет решать свою предметную задачу. Пользователь может добавить задачу, посмотреть список, изменить состояние и сохранить данные. Модель, service, storage и CLI разделены, а готовый проект можно запустить из терминала.

На этом месте легко сделать неправильный вывод: «Теперь просто откроем main.py из браузера». Но браузер не является ещё одним способом нажать input() в Python. Он живёт в другом процессе и общается с приложением по другому договору.

Это занятие начинается не с FastAPI и не с написания route-функций. Сначала нужно понять, какую проблему решает сетевой интерфейс.

Представьте мастерскую. Внутри находятся инструменты, мастер и склад материалов. Раньше заказчик сам заходил в мастерскую, брал форму и разговаривал с мастером напрямую. Теперь заказчик может оставить заявку через сайт. Мастерская остаётся владельцем работы и материалов, а сайт становится отдельным способом обратиться к ней.

С Persistent Planner происходит похожий переход:

~~~text
сейчас:
пользователь → CLI → PlannerService → storage

дальше:
пользователь → клиент → request → сервер
                              ↓
                       PlannerService → storage
                              ↓
                         response → клиент
~~~

Предметная задача остаётся той же. Меняется граница доступа к ней.

### Почему одного CLI становится мало

Локальный CLI хорош для разработки и первых проверок. Но у него есть ограничения:

- человеку нужно получить исходный код;
- Python должен быть установлен на его компьютере;
- пользователь должен знать команду запуска;
- локальный процесс работает рядом с локальным файлом данных;
- два пользователя не обращаются к одному источнику состояния;
- браузер или мобильное приложение не могут удобно импортировать PlannerService.

Это не означает, что CLI плохой. Он просто решает задачу локального интерфейса.

### Что мы узнаем

К концу занятия нужно уметь:

- объяснить разницу между локальным CLI и клиентом;
- назвать роли клиента и сервера;
- показать, где находится источник истины;
- провести путь создания задачи от пользователя до storage и обратно;
- объяснить, почему клиент не должен читать JSON;
- показать, что клиент и сервер могут находиться на одном компьютере;
- подготовить границу для будущего Planner API.

### Что сознательно не изучаем сейчас

В этом занятии не нужны:

- FastAPI;
- декораторы маршрутов;
- Pydantic;
- Postman;
- реальные HTTP-запросы;
- детальная структура URL;
- headers и body;
- база данных;
- новая реализация Persistent Planner.

Эти темы появятся после того, как станет ясна сама граница. Если начать с синтаксиса, можно написать рабочий endpoint и всё равно не понимать, кто должен владеть правилами.

**Остановитесь на минуту.** Если завтра появится мобильное приложение, нужно ли копировать в него Task, PlannerService и чтение JSON? Нет. Мобильному приложению нужен внешний договор с сервером, а не копия внутреннего проекта.

## 01. Что делает локальный CLI

CLI, или command-line interface, это интерфейс командной строки. Пользователь вводит команду в терминале, а программа читает ввод, вызывает прикладную логику и печатает результат.

### Текущий путь

~~~text
человек
  ↓ ввод
CLI
  ↓ прямой вызов Python
PlannerService
  ↓
Task и storage
  ↓
CLI
  ↓ вывод
человек
~~~

Все части находятся в одном приложении и обычно в одном процессе. CLI может напрямую импортировать service, потому что они принадлежат одному проекту.

### Что в CLI удобно

CLI хорош, когда:

- разработчик проверяет новую операцию;
- приложение используется локально;
- важна быстрая автоматизация;
- команда запускается из скрипта;
- не нужен отдельный экран;
- данные принадлежат одному окружению.

Такой интерфейс не нужно выбрасывать после появления API. Его можно оставить для администрирования, отладки или автоматических сценариев.

### Где появляется ограничение

Представим нового пользователя. Ему нужно:

1. получить репозиторий;
2. установить Python;
3. установить зависимости;
4. понять, какую команду запускать;
5. разобраться, где лежит файл данных;
6. научиться пользоваться меню.

Для учебного проекта это допустимо. Для сервиса, которым пользуются разные клиенты, неудобно.

Главная проблема не в том, что терминал выглядит просто. Проблема в том, что интерфейс находится слишком близко к внутреннему коду и локальному состоянию.

### CLI не является источником истины

CLI должен передавать намерение пользователя и показывать результат. Он не должен становиться владельцем правил.

Например, правило «priority находится в диапазоне от 1 до 5» не должно существовать только в разборе команды. Если завтра появится браузер, он может отправить значение напрямую на сервер. Сервер всё равно обязан проверить его сам.

### Независимый пример

~~~python
def show_temperature(value):
    if value < -50 or value > 60:
        raise ValueError("temperature is outside the sensor range")
    return f"{value} C"
~~~

Если эту функцию вызывает только CLI, это не делает CLI владельцем правила. Правило относится к самой предметной операции и должно оставаться доступным для других входов.

### Production-контекст

В production один и тот же service может вызываться из HTTP-обработчика, фоновой задачи, команды администратора или теста. Интерфейсы отличаются, а прикладные правила должны оставаться общими.

Это одна из причин, по которой мы разделяли CLI и service в предыдущем проекте. Теперь эта граница становится внешней.

**Проверьте себя.** Что нужно заменить, если вместо терминала появится браузер: правила Task или способ общения с пользователем? Меняется способ общения. Правила и storage остаются внутри приложения.

### Связь с текущей работой

Persistent Planner уже является хорошей серверной внутренностью. Его не нужно переписывать. Нужно понять, какой внешний слой сможет обращаться к нему без прямого импорта из клиента.

## 02. Клиент формулирует намерение

Клиент это сторона, которая начинает обращение к серверу. Чаще всего это программа, работающая от имени пользователя.

Клиентом может быть:

- браузер;
- мобильное приложение;
- desktop-программа;
- Postman;
- Swagger UI;
- Python-скрипт;
- другой backend;
- автоматический job.

Человек может сидеть перед браузером, но в сетевом смысле запрос отправляет программа-клиент.

### Клиентский путь

~~~text
пользователь нажал «Показать задачи»
    ↓
клиент понял намерение
    ↓
клиент подготовил request
    ↓
клиент отправил обращение серверу
    ↓
клиент получил response
    ↓
клиент показал результат человеку
~~~

Клиент отвечает за взаимодействие со своим пользователем. Он знает, как выглядит кнопка, где находится поле ввода и как показать ответ на экране.

### Что клиент может делать

Клиент может:

- показать форму;
- собрать введённые значения;
- выбрать, какую операцию попросить;
- отправить запрос;
- показать успешный результат;
- показать понятное сообщение о проблеме;
- временно сохранить состояние экрана;
- повторить запрос по правилам интерфейса.

Это не означает, что клиент может доверять собственным проверкам. Удобная проверка на экране помогает человеку, но не заменяет серверную защиту.

### Чего клиент не должен делать

Клиент не должен:

- читать tasks.json напрямую;
- импортировать PlannerService из серверного проекта;
- самостоятельно выдавать окончательный id;
- решать, существует ли задача;
- единолично проверять предметные правила;
- изменять файл источника истины;
- считать статистику из устаревшей локальной копии;
- объявлять операцию выполненной до ответа сервера.

Почему? Потому что завтра появится второй клиент. Если каждый клиент повторяет правила, они со временем разойдутся.

### Аналогия с кассой

Покупатель может проверить, что в корзине есть нужный товар. Но именно касса и склад подтверждают остаток, цену и успешную оплату.

Клиент похож на корзину и экран заказа. Сервер похож на кассу и склад. Экран может быть удобным, но он не становится источником истины.

### Независимый пример

~~~text
клиент:
  «Пользователь хочет открыть задачу с id 7»

сервер:
  «Я проверю, есть ли задача 7, и верну результат»

клиент:
  «Покажу результат или понятную ошибку»
~~~

Клиент не говорит: «Я решил, что задача 7 существует». Он просит сервер проверить состояние.

### Что происходит в production

В production клиент может быть недоверенным. Пользователь способен изменить код браузера, отправить запрос вручную или написать собственный скрипт. Поэтому сервер повторно проверяет всё, что важно для данных и правил.

### Интерактив

**Найдите нарушение.**

~~~python
# код браузерного клиента
tasks = read_json("tasks.json")
next_id = max(task["id"] for task in tasks) + 1
tasks.append(new_task)
write_json("tasks.json", tasks)
~~~

Такой клиент стал вторым сервером. Он читает источник истины, выдаёт id и меняет данные напрямую. Правильная граница отправляет намерение серверу.

### Связь с текущей работой

В практическом документе нужно явно записать, что клиент формирует request и показывает response. Также нужно перечислить запрещённые обязанности клиента, чтобы будущий API не превратился в удалённую копию CLI с доступом к файлам.

## 03. Сервер хранит правила и источник истины

Сервер это процесс, который принимает обращения клиентов, выполняет прикладную работу и возвращает результаты.

Слово «сервер» не означает обязательно отдельный физический компьютер. Сейчас сервер может работать на том же ноутбуке, что и браузер. Важны роли и направление общения.

### Серверный путь

~~~text
сервер запущен
    ↓
ждёт обращение
    ↓
понимает намерение
    ↓
проверяет данные
    ↓
вызывает прикладное правило
    ↓
читает или меняет источник истины
    ↓
формирует response
~~~

Серверный процесс обычно живёт дольше одной команды CLI. Он ждёт новые обращения и обслуживает их по одному договору.

### Что сервер должен делать

Сервер должен:

- принять request;
- проверить входные данные;
- выбрать нужную прикладную операцию;
- применить правила Task и PlannerService;
- обратиться к storage;
- вернуть успешный результат или понятную ошибку;
- не раскрывать клиенту внутреннюю структуру файлов без необходимости.

### Источник истины

Источник истины это место, которому система доверяет при определении текущего состояния.

Для текущего Persistent Planner им является storage и данные, которые он хранит. В следующей архитектуре клиент не должен создавать собственную конкурирующую копию. Сервер принимает решение на основании актуального состояния.

~~~text
клиентская копия экрана
        ≠ источник истины

серверные правила + storage
        = источник истины
~~~

Клиент может кэшировать ответ для удобства, но кэш не должен незаметно заменять сервер.

### Сервер не должен знать интерфейс

Серверу не нужно знать:

- цвет кнопки;
- расположение формы;
- название вкладки;
- размер шрифта;
- будет ли клиент браузером или мобильным приложением;
- покажет ли UI ошибку в модальном окне или в строке.

Серверу важно знать смысл операции, данные и правила. Так можно заменить интерфейс без переноса прикладной логики.

### Аналогия с библиотекой

Читатель приходит не к конкретному библиотекарю домой и не забирает базу книг. Он делает запрос библиотеке. Библиотека проверяет каталог, находит книгу и сообщает результат.

Клиент это читательский интерфейс. Сервер это библиотека с правилами и каталогом. Файл или база данных находятся ещё глубже.

### Production-контекст

Один сервер может обслуживать браузер, мобильное приложение, интеграцию и внутренний job. Это особенно важно, когда правила оплаты, доступа или изменения данных нельзя размножать по интерфейсам.

**True или false.** Сервер обязан находиться на другом компьютере. False. Два процесса на одном компьютере уже имеют разные роли клиента и сервера.

### Связь с текущей работой

В документе нужно закрепить, что сервер проверяет данные, выполняет правило и обращается к storage. Это не означает реализацию FastAPI. Это означает фиксацию владельца ответственности.

## 04. Клиент и сервер могут быть на одном компьютере

На этапе разработки часто используются:

- браузер как клиент;
- Python-процесс как сервер;
- один ноутбук как физическая машина.

Это не отменяет границу. Браузер не импортирует Python-класс напрямую. Он обращается к адресу процесса и получает ответ по согласованному сетевому протоколу.

### Две роли

~~~text
один ноутбук
├── процесс браузера
│     └── клиент
└── процесс Planner API
      └── сервер
~~~

Сервер слушает адрес. Клиент знает, куда отправить обращение. Между ними существует сообщение, а не прямой вызов метода в памяти клиента.

### localhost

Во время локальной разработки часто используется имя localhost. Оно означает «этот же компьютер».

Это полезно для обучения:

- запрос не уходит во внешний интернет;
- сервер можно запускать локально;
- клиент и сервер удобно проверять рядом;
- ошибка видна сразу.

Но localhost не означает «весь интернет» и не делает приложение публичным для другого компьютера.

### Порт как простая аналогия

У одного компьютера много процессов. Порт можно представить как номер двери, через которую клиент ищет нужный сервер.

~~~text
компьютер: localhost
дверь 8000: Planner API
дверь 3000: frontend позже
~~~

Подробные URL, ports и реальные HTTP-запросы будут в следующих материалах. Сейчас достаточно понимать, что клиенту нужен адрес серверного процесса.

### Что нельзя перепутать

- один компьютер не означает один процесс;
- localhost не означает внешний адрес;
- браузер не получает доступ к памяти Python;
- сервер не видит автоматически все данные на компьютере клиента;
- запрос не является прямым вызовом PlannerService из браузера.

### Независимая проверка

~~~text
браузер нажал кнопку
    ↓
сообщение покинуло процесс браузера
    ↓
сервер принял сообщение
    ↓
сервер выполнил Python-код
    ↓
ответ вернулся в браузер
~~~

Спросите себя: где находился Task до ответа? В серверном процессе. Браузер получил только внешнее представление результата.

### Production-контекст

На production сервер и клиент часто находятся на разных машинах или в разных облачных средах. Но локальная модель полезна, потому что показывает роли без лишней инфраструктуры.

## 05. Request и response связывают две стороны

Request это обращение клиента к серверу. Response это результат, который сервер возвращает клиенту.

Пока не нужно разбирать все поля request. Важно понять направление и отличие сообщения от внутреннего вызова функции.

### Request

Request сообщает:

- кто обращается;
- какое намерение нужно выполнить;
- к какому ресурсу относится действие;
- какие данные нужны для операции.

На следующем занятии мы подробно разберём method, адрес, headers и body. Сейчас request можно представить как заполненный бланк обращения.

### Response

Response сообщает:

- получилось ли действие;
- какой результат нужно показать;
- есть ли проблема;
- какие данные можно отобразить клиенту.

Это не обязан быть объект Task из памяти Python. Сервер формирует внешнее представление, пригодное для передачи.

### Полный цикл

~~~text
клиент
  ↓ request: «создать задачу»
сервер
  ↓ проверка и прикладная операция
storage
  ↑ сохранённое состояние
сервер
  ↑ response: «задача создана»
клиент
  ↑ показывает результат
~~~

Внешний клиент не знает, был ли внутри JSON-файл, база данных или другой storage. Он получает согласованный результат.

### Request не равен вызову функции

Внутри одного Python-процесса можно написать:

~~~python
service.add_task("Изучить HTTP")
~~~

Это прямой вызов метода. Клиент-серверная модель выглядит иначе:

~~~text
клиент отправил request
сервер принял request
сервер внутри вызвал прикладной код
сервер отправил response
~~~

Клиент не должен знать имя Python-метода. Иначе внешний договор окажется связан с внутренней реализацией.

### Ошибка тоже является response

Если задача не найдена, сервер не должен молча вернуть случайный список. Он формирует понятный результат ошибки, а клиент решает, как показать его человеку.

Так разделяются:

~~~text
сервер: определяет смысл ошибки
клиент: выбирает представление ошибки
~~~

Правило «задача с таким id отсутствует» относится к серверной предметной области. Правило «покажем красную плашку» относится к клиенту.

### Production-контекст

Разные клиенты могут по-разному отображать один response. Браузер покажет карточку, мобильное приложение обновит экран, а другой backend обработает машинный результат. Это возможно только при стабильном внешнем договоре.

**Соберите порядок.**

~~~text
ответ → прикладная операция → request → storage → клиент
~~~

Правильный путь начинается с клиента и request, затем сервер выполняет операцию, storage участвует в сохранении или чтении, после чего клиент получает response.

### Связь с текущей работой

В практике request-response будет частью диаграммы создания задачи. Это пока концептуальная схема. Настоящие части request появятся позже.

## 06. Один сценарий создания задачи через все границы

Чтобы проверить понимание, возьмём одно действие: пользователь хочет создать задачу.

### Шаг 1. Намерение

Пользователь вводит заголовок и выбирает создание задачи. Клиент понимает намерение и готовит обращение.

Клиент не должен сразу считать задачу созданной. До ответа сервера это только намерение.

### Шаг 2. Request

Клиент отправляет request на сервер. Внутри request будут данные, которые нужны операции. Их точное место мы разберём дальше.

Сейчас важно, что request пересекает границу процесса.

### Шаг 3. Серверная проверка

Сервер принимает данные и передаёт их в подходящую прикладную операцию. Проверка должна выполняться на сервере, даже если клиент уже подсветил поле.

Почему? Клиент может быть изменён, сломан или заменён другим клиентом.

### Шаг 4. Модель и service

PlannerService применяет знакомое правило. Task остаётся владельцем своих инвариантов. Service координирует прикладное действие. Клиент не знает этих внутренних деталей.

### Шаг 5. Storage

Если операция успешна, service сохраняет актуальное состояние через storage. Конкретный файл не становится частью клиентского договора.

~~~text
клиент не знает:
  где лежит tasks.json
  какой метод Path вызывается
  как storage сериализует данные

сервер знает:
  как применить правило
  как сохранить состояние
  как сообщить результат
~~~

### Шаг 6. Response

Сервер формирует внешний результат. Клиент получает его и показывает пользователю.

Если операция не удалась, response сообщает ошибку. Клиент не исправляет состояние файла сам.

### Полная схема

~~~text
пользователь: «создать задачу»
    ↓
клиент формирует request
    ↓
сервер принимает request
    ↓
сервер проверяет вход
    ↓
PlannerService выполняет действие
    ↓
Task и storage сохраняют результат
    ↓
сервер формирует response
    ↓
клиент показывает созданную задачу
~~~

### Почему эта схема важнее кода

Пока мы не написали FastAPI, уже можно понять:

- где будет внешний вход;
- где останутся правила;
- где находится источник истины;
- что должен получить клиент;
- почему клиент не должен читать файл.

Хорошая архитектура сначала отвечает на эти вопросы, а потом выбирает синтаксис.

### Ошибочный путь

~~~text
клиент
  ↓ читает tasks.json
клиент сам создаёт id
  ↓
клиент пишет файл
  ↓
сервер получает уже изменённое состояние
~~~

Здесь сервер больше не владеет данными. Два клиента могут одновременно создать одинаковый id или применить разные правила.

### Production-контекст

Такое разделение важно при конкуренции, безопасности и масштабировании. Когда несколько клиентов изменяют одни данные, решение должно приниматься в одном доверенном месте.

**Найдите границу.** В каком месте схемы должен находиться JSON-код? Внутри серверного storage. Не в браузере, не в CLI-клиенте и не в документе внешнего API.

### Связь с текущей работой

В практике нужно нарисовать именно этот путь: client → request → server → storage → response → client. PlannerService и Task можно показать внутри серверной части, но не превращать их в прямой API клиента.

## 07. Спроектируем границу до реализации

Практика этого занятия является проектной. Её результатом станет документ docs/client-server-boundary.md, а не FastAPI-приложение.

### Пять действий пользователя

Граница должна покрыть пять знакомых действий:

1. показать список задач;
2. получить одну задачу;
3. создать задачу;
4. обновить задачу;
5. удалить задачу.

Для каждого действия полезно описать:

- намерение пользователя;
- работу клиента;
- работу сервера;
- обращение к storage;
- результат, который увидит клиент.

### Матрица ответственности

| Действие | Клиент | Сервер |
| --- | --- | --- |
| Показать список | просит список и показывает response | читает актуальные задачи |
| Получить одну | передаёт выбранный идентификатор | проверяет id и возвращает задачу или ошибку |
| Создать | отправляет введённые данные | проверяет, создаёт и сохраняет задачу |
| Обновить | отправляет изменение | применяет правило и сохраняет состояние |
| Удалить | просит удалить выбранную задачу | проверяет id и изменяет источник истины |

Эта таблица не является готовым роутером. Она фиксирует смысл до написания кода.

### Запреты клиента

В документе нужно отдельно записать, что клиент:

- не читает tasks.json;
- не импортирует PlannerService;
- не выдаёт окончательный id;
- не решает, существует ли задача;
- не является владельцем правил Task;
- не объявляет успех до ответа сервера.

Рядом добавьте причину каждого запрета. Например, прямое чтение файла создаёт второй источник истины.

### Запреты сервера

Сервер не должен знать:

- расположение кнопки;
- цвет интерфейса;
- название вкладки;
- вид модального окна;
- выбор браузера или мобильного приложения;
- способ локального отображения сообщения.

Сервер отвечает за смысл и данные, а не за дизайн.

### Два клиента и один сервер

Полезно представить браузер и Python-скрипт. Они могут отличаться интерфейсом, но оба используют один серверный договор.

~~~text
браузер ───────┐
               ├── общий сервер Planner API ── Task и storage
Python-скрипт ─┘
~~~

Если для второго клиента нужно копировать JSON или PlannerService, граница спроектирована неправильно.

### Что не входит в документ

Не нужно добавлять:

- код FastAPI;
- decorators;
- реальные endpoint-функции;
- подробный URL;
- query-параметры;
- headers;
- body;
- Pydantic-схемы;
- Postman collection.

Это не недостающие части. Это следующие шаги программы.

### Production-контекст

Документы границ полезны до реализации, потому что помогают нескольким разработчикам одинаково понимать систему. Позже этот документ станет опорой для request-контракта, тестов и архитектурного ревью.

## 08. Что мы будем делать в практике

Практика не меняет Persistent Planner. Мы используем его как уже знакомый серверный внутренний сценарий и проектируем внешнюю границу для будущего API.

### Общий результат

В конце появится docs/client-server-boundary.md. По нему другой разработчик сможет понять:

- что сейчас делает CLI;
- зачем нужен отдельный клиент;
- какие роли у клиента и сервера;
- где находится источник истины;
- как проходит создание задачи;
- что каждый слой не должен делать;
- почему реализация FastAPI начинается позже.

### Карточки практики

1. **Исходная точка CLI.**
   Зафиксируйте готовый Persistent Planner и ограничение локального запуска.

2. **Пять пользовательских действий.**
   Опишите показать список, получить одну задачу, создать, обновить и удалить.

3. **Ответственность клиента и сервера.**
   Для каждой операции разделите request, response, правила, storage и отображение.

4. **Источник истины.**
   Перечислите, что клиенту запрещено делать, и объясните риск каждого запрета.

5. **Полный путь создания.**
   Нарисуйте client → request → server → PlannerService → storage → response → client.

6. **Финальный аудит.**
   Проверьте документ как новый разработчик, запустите прежний CLI и убедитесь, что FastAPI пока не добавлен.

### Доказательства готовности

Практика выполнена, если:

- документ существует и читается без устного объяснения;
- пять действий описаны отдельно;
- роли клиента и сервера не дублируются;
- source of truth находится на серверной стороне;
- путь создания задачи виден от намерения до response;
- два разных клиента могут использовать один серверный договор;
- Persistent Planner не изменён;
- детали FastAPI оставлены следующему блоку.

### Границы результата

Сейчас мы не строим работающий сервер. Не нужно писать код только для того, чтобы документ выглядел техническим. На этом этапе архитектурная ясность является самостоятельным результатом.

Следующая работа начнётся с request как сообщения. Для неё уже будут готовы роли, путь и причина существования внешнего интерфейса.

### Перед переходом

Проверьте себя:

- сможете ли вы объяснить, почему CLI недостаточно;
- сможете ли назвать пять действий;
- сможете ли сказать, где хранится источник истины;
- сможете ли объяснить, почему клиент не читает JSON;
- сможете ли провести одну задачу через все границы.

Если на эти вопросы есть короткий ответ, можно переходить к практике.

### Главное

- CLI является локальным интерфейсом, а не плохой версией API.
- Клиент формулирует намерение и показывает response.
- Сервер проверяет данные, выполняет правила и обращается к storage.
- Источник истины должен находиться на серверной стороне.
- Клиент и сервер могут быть двумя процессами на одном компьютере.
- Request и response являются сообщениями между границами, а не прямым вызовом Python-метода.
- Один сервер может обслуживать браузер, мобильное приложение и Python-скрипт.
- В текущей практике проектируется граница, а FastAPI и детали HTTP остаются дальше.

После самопроверки переходите к карточкам практики. Сначала зафиксируйте известный CLI. Затем разделите роли и запреты. В конце нарисуйте полный путь создания задачи и проверьте, что исходный Persistent Planner не пришлось переписывать.
