## 00. Один список, разные полезные виды

В прошлом занятии мы научились адресовать одну задачу: например, `GET /tasks/7` просит задачу с `id = 7`. Но в приложении чаще нужен не один объект, а удобный вид всего списка. На экране могут быть только невыполненные задачи, сначала самые новые или лишь небольшая часть длинного списка.

Можно было бы придумать отдельный адрес для каждой комбинации: `/open-tasks`, `/recent-tasks`, `/first-ten-open-tasks` и так далее. Но число таких адресов быстро растёт, а правила чтения списка остаются почти одинаковыми. У API есть более гибкий способ: оставить маршрут списка `/tasks`, а дополнительные настройки передавать в query-параметрах.

**Query-параметр** это дополнительное значение в URL, которое настраивает запрос. В этом занятии мы разберём три настройки: фильтр по выполнению, порядок сортировки и максимальное количество результатов. Они меняют то, какой список сервер вернёт, но не меняют сами сохранённые задачи.

> **Новые слова.** `collection` означает коллекцию, то есть список объектов одного вида. `filter` означает фильтр, который оставляет подходящие записи. `sort` означает сортировку, то есть упорядочивание записей. `limit` означает предел количества результатов. `pipeline` означает последовательность нескольких шагов обработки.

## 01. Path выбирает, query настраивает

Сравните три запроса:

```text
GET /tasks
GET /tasks?is_done=false
GET /tasks/7
```

Первый просит список задач. Второй просит тот же список, но только с задачами, у которых `is_done` равно `false`. Третий просит одну задачу с идентификатором 7. Path `/tasks/7` выбирает конкретную запись; query после знака `?` задаёт условия для списка.

После `?` URL содержит пары «имя=значение». Несколько параметров соединяются амперсандом `&`:

```text
GET /tasks?is_done=false&sort_desc=true&limit=10
```

Порядок query-параметров в URL не определяет порядок обработки. `limit=10&is_done=false` описывает те же настройки. Как именно приложение применит их, задаёт серверная логика.

В адресе все значения записаны текстом. Например, `false` в URL сначала является текстом. FastAPI смотрит на тип параметра и преобразует это значение в Python-значение `False`. Если вместо целого числа для `limit` отправить `many`, FastAPI не сможет выполнить преобразование и вернёт ошибку проверки запроса. Самостоятельная функция из практики уже получает готовые значения `bool`, `int` и `None`, поэтому разбор URL там не нужен.

### Проверьте различие

Какой запрос выбирает одну конкретную задачу: `GET /tasks/7` или `GET /tasks?is_done=false`? Во втором запросе число результатов может измениться, но адрес всё ещё обозначает коллекцию.

## 02. Необязательный фильтр и важное значение False

У фильтра по статусу есть три осмысленных состояния:

| Значение `is_done` | Что означает |
| --- | --- |
| `True` | оставить только выполненные задачи |
| `False` | оставить только невыполненные задачи |
| `None` | фильтр не передан, оставить оба статуса |

FastAPI может принять такое query-значение через параметр функции с типом `bool | None` и значением по умолчанию `None`:

```python
@app.get("/tasks")
def read_tasks(is_done: bool | None = None):
    ...
```

Вертикальная черта в `bool | None` читается как «либо bool, либо None». Значение по умолчанию делает настройку необязательной. Если клиент её не передал, функция получает `None`; запрос `?is_done=false` даёт настоящее Python-значение `False`.

Поэтому отсутствие настройки проверяют явно:

```python
if is_done is not None:
    # здесь фильтр задан, даже если его значение False
    ...
```

Условие `if is_done:` здесь ошибочно. В Python `False` считается ложным значением, поэтому такая проверка перепутала бы «фильтр задан как False» с «фильтра нет». Сравнение с `None` сохраняет все три состояния.

### Найдите ошибку в рассуждении

Разработчик говорит: «`is_done` ложный, значит параметр не пришёл». Это неверно. Запрос `?is_done=false` передаёт фильтр, который нужно применить к невыполненным задачам.

## 03. Сначала отберите, затем упорядочьте, потом ограничьте

Когда у списка несколько настроек, их удобно представлять как цепочку преобразований. Возьмём книжный каталог. Сначала оставим книги нужного жанра, затем поставим их по году публикации, затем вернём первые десять. Нельзя сначала взять первые десять произвольных книг, а потом искать жанр: нужные книги могут находиться дальше, и итоговая подборка окажется неполной.

Для задач порядок такой же:

1. **Фильтр** оставляет записи, которые соответствуют `is_done`, если условие задано.
2. **Сортировка** располагает прошедшие фильтр записи по выбранному правилу.
3. **Ограничение** берёт не больше `limit` первых записей готовой выборки.

Это и есть pipeline, или цепочка обработки: каждый следующий этап принимает результат предыдущего. Если ограничить список до фильтра, часть подходящих задач может не попасть в выбранную часть. Если сначала взять первые элементы, а потом сортировать, вы упорядочите только случайный фрагмент, а не весь подходящий результат.

Важно также отделить результат запроса от источника данных. GET формирует представление для ответа. Он не должен переставлять задачи внутри общего хранилища или удалять те, что не подошли под фильтр. Представьте полку библиотеки: читатель запрашивает подборку и порядок книг, но каталог и сами книги от этого не меняются.

### Наблюдение

Визуальная схема в теории показывает неизменный исходный список и отдельную цепочку результата: фильтр, сортировка, ограничение. Читайте её как путь временной выборки для ответа, а не как изменение хранилища.

## 04. Сортировка результата не обязана менять исходный список

В Python есть два похожих способа упорядочить список, но они ведут себя по-разному:

- `sorted(values)` возвращает новый список в нужном порядке;
- `values.sort()` меняет сам список `values` и возвращает `None`, а не новый список.

Для подготовки ответа обычно проще явно получить новое значение через `sorted`. Направление можно задавать параметром `reverse`: `False` означает обычный порядок, `True` означает обратный.

В нашей функции параметр `sort_desc` задаёт это направление: `False` значит сортировать `id` по возрастанию, а `True` значит по убыванию. Имя `desc` это сокращение от английского `descending`, «по убыванию». Вызов `sorted` принимает логическое направление через `reverse`.

Чтобы сортировать словари, нужно объяснить Python, какое значение сравнивать у каждого словаря. Для этого у `sorted` есть параметр `key`. В него передают функцию без скобок: Python сам вызывает её для каждого элемента, а функция возвращает значение для сравнения. Посмотрим на независимый пример с книгами:

```python
books = [
    {"title": "Ночная смена", "year": 2022},
    {"title": "Первая запись", "year": 2018},
]

def publication_year(book):
    return book["year"]

sorted(books, key=publication_year)
# сначала книга 2018 года, затем книга 2022 года
```

`key` здесь означает функцию, которая извлекает год, а не имя поля в словаре. Позже тот же механизм позволит сравнивать задачи по их `id`, не меняя сами словари.

Даже `sorted` создаёт новый список, но не копирует автоматически словари внутри него. Если элементы исходного списка это словари, новый список может содержать ссылки на те же словари. В предыдущем занятии мы уже видели `dict.copy()`: он создаёт отдельный внешний словарь с теми же полями. В нашей модели поля задачи содержат числа, строки и логические значения, поэтому отдельной копии внешнего словаря достаточно. Вложенные списки и словари мы здесь не рассматриваем.

Отдельные копии полезны, когда результат будут дальше обрабатывать: случайное изменение выбранной задачи не должно незаметно изменить объект из исходного списка. В текущей практике мы проверим и равенство полей, и отдельную идентичность словарей, и неизменность входных данных.

## 05. Limit защищает размер ответа

Если в списке несколько тысяч записей, клиенту редко нужно получить их все за один раз. `limit` задаёт максимальное количество элементов в одном ответе. Это экономит сеть и память клиента, а также не позволяет одному запросу заставить сервер формировать чрезмерно большой ответ.

После сортировки нужно взять начало списка, а не просто число элементов откуда угодно. **Срез** задаёт часть списка. Например, `values[:2]` возвращает элементы с начала до позиции 2, не включая саму позицию 2. Значит, в результате будут первые два элемента. Если список короче двух, срез вернёт всё, что есть. Для `limit` тот же принцип записывается как «взять начало до значения limit».

Одного типа `int` недостаточно: он разрешает ноль и отрицательные значения, а клиент может прислать чрезмерно большое число. Приложение должно явно определить границы. Есть две разные политики:

- **Отклонить недопустимое значение.** В FastAPI для этого можно задать ограничения `Query(ge=1, le=50)`. Значение вне диапазона будет отклонено при проверке запроса, обычно с ответом `422`.
- **Привести значение к диапазону.** Например, ноль трактовать как 1, а число больше 50 как 50.

Для Planner API выберем строгую политику: `limit` по умолчанию равен 10, а допустимый диапазон составляет от 1 до 50 включительно. FastAPI проверит это до вызова обработчика. Если передать 0 или 51, запрос получит `422`; сервер не будет молча менять значение.

```python
from fastapi import Query

def read_tasks(
    is_done: bool | None = None,
    sort_desc: bool = False,
    limit: int = Query(default=10, ge=1, le=50),
):
    ...
```

`ge=1` означает «не меньше 1», а `le=50` — «не больше 50». В публичном договоре `is_done` необязателен и при отсутствии равен `None`, `sort_desc` по умолчанию равен `False` (сортировка `id` по возрастанию). HTTP-маршрут проверяет вход. Функция из лабораторной получает уже проверенное целое значение от 1 до 50 и просто применяет его как длину среза. Она не должна нормализовать неподходящее число.

## 06. Как это расширяют в рабочем API

Три настройки из занятия встречаются в реальных API повсеместно, но у больших систем появляются дополнительные решения.

**Постраничная выдача** (pagination, возврат данных небольшими порциями) может опираться на номер страницы и смещение (`offset`) или на курсор, который указывает продолжение чтения. У каждого способа есть компромиссы. Смещение легко объяснить, но при частых изменениях списка страницы могут сдвигаться. Курсор сложнее, зато при устойчивой сортировке с уникальным последним ключом обычно удобнее для последовательного просмотра меняющегося списка. В этой практике пагинацию не реализуем: здесь только безопасный предел количества.

**Разрешённые поля сортировки** задают явный список вариантов. Клиенту не следует разрешать сортировку по любому имени поля: часть полей может быть внутренней или дорогой для вычисления. **Белый список** (allow-list, перечень разрешённых значений) ограничивает запрос понятными вариантами. В упражнении поле только одно, `id`, поэтому отдельный выбор поля не нужен.

**Предсказуемый порядок в API** важен, если у разных записей совпадает главное поле сортировки. Python сохраняет исходный порядок элементов с одинаковым ключом. Это называют устойчивостью сортировки. Но исходное расположение записей может отличаться между запросами, особенно когда их выдаёт база данных. Чтобы порядок API не зависел от такого расположения, добавляют уникальный дополнительный ключ, например `id`. Его называют tie-breaker, то есть правилом разрешения равенства. В нашей модели `id` уже уникален, поэтому отдельный второй ключ не нужен.

Для больших баз данных сервер обычно передаёт фильтр, сортировку и лимит самой базе, а не загружает весь набор в Python. Индексы помогают быстрее найти и упорядочить нужные записи. Это важная производственная тема, но она появится позже вместе с базой данных. Сейчас мы закрепляем только смысл и порядок операций над обычным списком.

### Короткая проверка

`limit=50` разрешает вернуть до 50 задач; при 51 сервер отклонит запрос с `422`. Это не означает, что сервер хранит только первые 50: ограничивается конкретный ответ, а неверный запрос не меняет состояние.

## 07. Границы сегодняшнего решения

В запросе к коллекции могут быть и другие настройки, например текстовый поиск по заголовку, поле сортировки, номер страницы или направление в виде строки. Это полезные возможности, но каждая требует собственного договора: как разобрать значение, какие значения разрешены и что показать при ошибке.

В этом занятии мы не добавляем поиск `q`, `offset`, динамическое поле `sort_by`, SQL-запросы или сложную модель query-параметров. Они не нужны, чтобы понять основную идею, и потребовали бы отдельных условий и проверок. Наш маршрут остаётся один: отбор по `is_done`, сортировка по уникальному `id`, ограничение количества.

В следующем занятии мы перейдём от чтения списка к входным данным POST-запроса. Там появится JSON body и модель, которая проверяет его форму. Здесь же клиент только настраивает представление уже существующей коллекции.

## 08. Что мы будем делать в практике

Автопроверка вызовет чистую Python-функцию `solve(tasks, is_done, sort_desc, limit)`. Она получает список задач с полями `id`, `title`, `priority`, `is_done`; `id` уникален, а значения уже имеют типы Python. Сервер и разбор URL в этом упражнении не участвуют.

Нужно подготовить отдельное представление задач. `None` означает, что статусный фильтр не передан; `True` и `False` выбирают соответствующие задачи. Для прошедших фильтр записей нужно создать отдельные словари, отсортировать их по `id` в заданном направлении и вернуть начало готового результата длиной `limit`. В функцию передаются только допустимые значения от 1 до 50.

Проверки охватывают:

- список без фильтра, фильтрацию по `True` и `False`, в том числе результат без совпадений;
- оба направления сортировки;
- допустимая нижняя граница `limit=1`;
- допустимая верхняя граница `limit=50` на наборе, который содержит больше 50 задач;
- отдельный сценарий, который ловит применение `limit` к исходному списку до подготовки нужной выборки;
- пустой входной список;
- неизменность входного списка и его словарей;
- отдельную идентичность каждого словаря в результате.

В каждой задаче поля `title` и `priority` сохраняются как есть. Они не участвуют ни в фильтре, ни в сортировке: для этого запроса фильтр использует `is_done`, а порядок задаёт `id`.

Можно опираться на уже знакомые цикл, условие, `dict.copy()`, `sorted()` и срез списка. В этой функции не нужны FastAPI, HTTPException, Query, база данных, `q` или `offset`: обработчик API проверит `limit` отдельно до её вызова. Верните значение функцией, не печатайте его.

Результат станет проверяемой моделью поведения GET `/tasks`: один и тот же источник может дать отфильтрованный, упорядоченный и ограниченный ответ. В следующем занятии мы сохраним этот взгляд на границы API, но начнём разбирать данные, которые клиент отправляет серверу в JSON body.
