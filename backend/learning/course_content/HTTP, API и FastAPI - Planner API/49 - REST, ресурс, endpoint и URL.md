## 00. От отдельных методов к понятной карте

В прошлом занятии мы разобрали смысл HTTP methods. GET используют для чтения; POST передаёт данные на обработку и в нашем договоре Planner будет создавать Task; PUT передаёт полное представление целевого ресурса и в нашей карте заменяет выбранную Task целиком; PATCH меняет часть; DELETE запрашивает удаление. Это уже хороший словарь действий, но пока не хватает ответа на другой вопрос: с каким именно объектом работает запрос?

Представьте библиотеку. Фраза «выдайте» описывает действие, но не называет книгу. Фраза «книга» называет объект, но не сообщает, что с ним сделать. Понятная команда соединяет обе части: «выдайте книгу», «добавьте книгу», «замените карточку книги».

В API такую предметную сущность называют **resource**, или ресурсом. Адрес обычно показывает, к какому resource обращается клиент, а method говорит, какое действие он запрашивает.

~~~text
resource → о чём говорим
path → где найти resource
method → что сделать
response → чем закончилась операция
~~~

### Почему одной пары method и случайного пути мало

Технически можно придумать отдельный путь под каждую кнопку:

~~~text
/getTasks
/createTask
/finishTask
/deleteTask
~~~

Но другой разработчик должен каждый раз запоминать правила автора. По одному адресу трудно понять, относится ли он ко всей collection или к одной задаче. Неясно, какое действие уже выражено method, а какое спрятано в тексте пути.

При проектировании API с ориентацией на REST используют повторяемые соглашения. Смысл не в том, чтобы сделать интерфейс красивым ради красоты. Смысл в том, чтобы новый клиент мог предположить его форму по нескольким устойчивым правилам.

### Маленький прогноз

~~~python
routes = {
    "GET /tasks": "collection",
    "GET /tasks/7": "item",
}

print(routes["GET /tasks"])
print(routes["GET /tasks/7"])
~~~

**Что напечатает код?**

Здесь два ключа начинаются с одного resource, но обозначают разные области: всю collection и один item. Внутри Python это просто строки и словарь. В API такая запись помогает увидеть форму будущей карты.

### Что добавляется сейчас

Мы разберём:

- что такое архитектурный стиль REST и чем он шире нашей ресурсной карты;
- что считать resource;
- чем внешнее представление отличается от внутреннего объекта;
- как отличать collection и item;
- чем отличаются URL, path, endpoint и method;
- почему путь обычно называет resource существительным;
- зачем сервису нужен GET /health и почему это не resource tasks.

### Чего пока не будет

Здесь мы не будем:

- писать код обработчиков и регистрировать маршруты;
- запускать серверное приложение;
- распределять значения между path, query и body;
- подключать FastAPI;
- реализовывать создание, чтение, изменение и удаление задач;
- описывать правила проверки входных данных.

Сначала зафиксируем карту внешних операций. Детали входных данных и код сервера появятся после того, как карта станет понятной.

## 01. REST: архитектурный стиль и практические соглашения

REST расшифровывается как Representational State Transfer, примерно «передача состояния через представления». Это архитектурный стиль взаимодействия сетевых компонентов, а не библиотека или функция Python. Здесь state означает состояние ресурса или приложения, а не HTTP status-код ответа.

В обычной разработке REST часто связывают с ресурсными путями и стандартными HTTP methods. Это полезная часть подхода, но одной таблицы маршрутов недостаточно, чтобы объявить всю систему REST-архитектурой. Формальное определение задаёт более широкие правила взаимодействия компонентов.

Наша цель уже: спроектировать ясную ресурсную карту Planner API.

В нашей карте мы используем практическую часть этой идеи: path указывает на ресурс, HTTP method задаёт смысл запроса, а клиент получает или передаёт представление ресурса. Это упрощённая модель для проектирования API, а не полное описание всех ограничений REST. Сервер не обязан раскрывать клиенту внутренние классы, файлы и функции.

### Что ещё входит в формальный REST

Чтобы не сводить REST только к названиям путей, полезно знать и остальные ограничения стиля:

- **Клиент и сервер разделены.** Клиент отвечает за интерфейс и запросы, сервер за данные и правила. Их можно развивать независимо, пока внешний договор сохраняется.
- **Запрос самодостаточен.** В каждом запросе есть сведения, нужные для его обработки. Сервер не должен угадывать смысл по истории предыдущих запросов. Это не запрещает серверу хранить задачи или другие данные.
- **Ответ может разрешать кэширование.** Кэш это временно сохранённая копия ответа. Если её можно безопасно использовать повторно, сервер сообщает об этом клиенту и промежуточным системам.
- **Система может состоять из слоёв.** Между клиентом и приложением могут находиться прокси или шлюз, то есть промежуточные серверы. Клиенту не обязательно знать внутреннюю схему этих посредников.
- **Единый интерфейс задаёт общие правила взаимодействия.** Адрес позволяет выбрать ресурс, представление передаёт его данные, а сообщение само объясняет, как его понимать. Ссылки в ответе могут подсказывать клиенту доступные следующие действия; этот подход называют гипермедиа.
- **Передача исполняемого кода клиенту необязательна.** Это ограничение называют «код по запросу» (code on demand); обычному API оно не требуется.

В этом блоке мы проектируем только ресурсную карту и представления. Мы не будем заявлять, что один этот документ делает Planner полностью соответствующим REST.

Первоисточник формального описания: [диссертация Роя Филдинга о REST](https://ics.uci.edu/~fielding/pubs/dissertation/rest_arch_style.htm). Для практики достаточно объяснений выше.

### Проблема без общих договорённостей

Допустим, один разработчик называет путь /tasks, второй пишет /get-all-tasks, а третий использует /task-items. Все варианты могут технически работать. Но клиенту приходится знать историю каждого решения.

Такая система похожа на город, где каждый магазин сам придумал номера улиц. До нужного места можно добраться, но только после отдельного изучения карты.

REST-подход уменьшает количество случайных решений:

~~~text
path называет resource
method называет действие
форма collection повторяется
форма item повторяется
представление полей остаётся стабильным
~~~

### REST не означает идеальную универсальность

REST не запрещает все нестандартные операции. В рабочих API могут существовать:

- health-проверки;
- загрузка файла;
- запуск длительной операции;
- команда, которую трудно представить как обычное изменение resource.

Важно не превращать отдельное исключение в правило для всего API. Для Planner сейчас достаточно ресурсоориентированной карты задач. Если появится особая команда, её смысл нужно объяснить отдельно.

### Как REST связан с HTTP methods

REST и HTTP methods не являются синонимами. HTTP задаёт механизм сообщений и стандартные methods. REST использует эти возможности в определённой манере:

~~~text
resource: tasks
method: GET
намерение: прочитать задачи
~~~

REST помогает выбрать понятную форму. Но он не хранит данные, не проверяет права и не отвечает за бизнес-правила.

### Интерактив. Что здесь предсказуемо?

Сравните две группы:

~~~text
A:
GET /tasks
POST /tasks
GET /tasks/7
DELETE /tasks/7

B:
/showAllTasks
/makeNewTask
/removeTaskByIdentifier
/readOneTask
~~~

Ответьте:

1. В какой группе действие видно из method?
2. В какой группе одна и та же основа path явно повторяется для collection и item?
3. Почему группе B потребуется больше документации?

Группа A сама по себе ещё не доказывает полное соответствие REST, но её правила легче продолжить для новых ресурсов.

### Где проходит граница REST

REST описывает форму взаимодействия между клиентом и сервером. Он не требует:

- конкретной базы данных;
- конкретного языка;
- обязательного JSON;
- обязательного фреймворка;
- прямого совпадения сетевого resource и Python-класса.

В одном и том же REST-подходе внутреннее хранение может измениться с JSON на SQLite или PostgreSQL, а внешний смысл resources остаться прежним.

### В рабочем сервисе

Понятная карта особенно важна, когда один API используют несколько клиентов. Браузер, мобильное приложение, CLI и другой backend могут быть написаны разными командами. Если каждый клиент угадывает смысл пути, любое изменение превращается в риск поломки.

В рабочем сервисе договор обычно дополняют документацией, описанием формы ответов, правилами ошибок, версиями и ограничениями доступа. Но эти дополнительные слои не заменяют базовую ясность resource, path и method.

## 02. Resource: сущность, о которой говорит API

Resource можно перевести как «ресурс», но для обучения полезнее понимать его как сущность предметной области, доступную через внешний договор.

В нашем проекте такой сущностью является Task. Пользователь думает о задаче: у неё есть заголовок, приоритет, статус выполнения, идентификатор и метки. API представляет эту задачу так, чтобы клиент мог её прочитать или изменить через договор.

### Ресурс не равен файлу

Одна Task может храниться:

- в списке Python;
- в JSON-файле;
- в строке SQLite;
- в таблице PostgreSQL;
- в кэше на короткое время.

Во всех случаях предметный смысл может остаться одним: это задача пользователя. Поэтому path API не должен повторять внутреннюю структуру storage.

~~~text
внутри:
tasks.json → список словарей → PlannerService

снаружи:
resource tasks → представление Task
~~~

Клиенту не нужно знать, где лежит файл. Иначе замена способа хранения (storage) заставит переписывать все клиенты, хотя пользовательская сущность не изменилась.

### Ресурс и представление ресурса

Resource является смыслом. Представление является его внешним описанием в конкретном response.

~~~text
ресурс:
задача «Изучить REST»

представление:
{
  "id": 7,
  "title": "Изучить REST",
  "priority": 4,
  "is_done": false
}
~~~

Это пример представления уже созданной Task в ответе клиенту. Идентификатор назначает сервер. Какие данные клиент отправляет при создании и изменении, будет зафиксировано отдельно.

В модели Persistent Planner у Task есть также поле tags. Для учебного договора Planner API v1 мы намеренно выберем компактное публичное представление из четырёх полей выше и пока не включим tags. Это решение о составе конкретного API, а не утверждение, что меток нет в самой предметной модели.

Сервер может хранить больше полей, чем отдаёт. Например, внутреннюю временную отметку, служебный флаг или путь к журналу не обязаны включать в публичное представление.

### Почему представление должно быть стабильным

Клиент строит экран по именам полей. Если сегодня сервер возвращает is_done, завтра done, а послезавтра completed, клиенту приходится угадывать. Это не улучшение API, а скрытая миграция для всех потребителей.

Стабильность не означает, что API никогда нельзя изменить. Изменение должно быть явным: новая версия, переходный период или согласованный план перехода.

### Независимый пример

Сервис бронирования имеет resource booking. Внутри он хранит несколько технических полей, но наружу показывает:

~~~text
{
  "id": 18,
  "room": "A12",
  "starts_at": "2026-09-11T10:00:00+03:00",
  "is_confirmed": true
}
~~~

Клиенту важны номер бронирования, время и факт подтверждения. Способ хранения журнала изменений остаётся на сервере.

### Интерактив. Ресурс, представление или внутренняя деталь?

Распределите примеры по трём группам: сам resource, его публичное представление или идентификатор, внутренняя деталь реализации.

1. Task пользователя.
2. tasks.json.
3. PlannerService.
4. JSON-представление задачи.
5. SQLite-таблица.
6. id, который клиент использует для выбора item.

Подсказка: сам resource это предметная сущность. Представление и идентификатор помогают клиенту работать с ней через договор. Файл, таблица и Python-класс описывают устройство сервера, а не публичную сущность.

### С чем путают resource

Resource путают с endpoint. Resource отвечает на вопрос «какая сущность предметной области?». Endpoint отвечает на вопрос «какая конкретная операция доступна по method и path?».

У одного resource может быть несколько endpoints. Например, сервис бронирований может предложить:

~~~text
GET /bookings/18
DELETE /bookings/18
~~~

Это разные операции над одним выбранным бронированием. Для Planner в практике вы сами составите полный набор строк.

### В рабочем сервисе

В большой системе один resource может иметь разные представления для разных клиентов. Например, список возвращает короткую карточку, а детальный запрос добавляет описание. Это не повод менять смысл resource. Нужно просто документировать, какие поля входят в каждый response.

### Связь с Planner

В карте Planner мы назовём resource tasks. Внешнее представление Task останется согласованным с уже существующей предметной моделью Persistent Planner. Мы не будем переносить в публичный договор имена файлов и прямые вызовы service.

## 03. Collection и item: много объектов и один объект

Один resource может быть представлен как collection или как отдельный item. Это две разные области действия.

~~~text
collection:
/tasks
много задач

item:
/tasks/7
одна задача с идентификатором 7
~~~

### Collection

Collection обозначает набор ресурсов одного типа. Она нужна, когда клиент работает с множеством задач:

- получить список;
- создать новую Task;
- позже отфильтровать или отсортировать список.

В договоре Planner идентификатор новой Task назначает сервер. Поэтому клиент не может заранее выбрать её item path и отправляет запрос на collection. В этой карте мы выберем POST /tasks для создания. Это решение именно нашего договора: HTTP определяет POST как передачу целевому ресурсу данных для обработки по его правилам, а создание является одним из распространённых вариантов, но не единственным. Подробно: [RFC 9110, раздел POST](https://www.rfc-editor.org/rfc/rfc9110.html#name-post).

### Item

Item обозначает один выбранный объект. Идентификатор является частью формы item path:

~~~text
/tasks/7
       ↑
       идентификатор item
~~~

Item нужен, когда клиент хочет:

- прочитать одну задачу;
- заменить её целиком;
- изменить её часть;
- удалить её.

### Почему нельзя смешивать области

Сравните:

~~~text
GET /tasks
GET /tasks/7
~~~

Оба запроса читают, но response имеет разный масштаб. В первом случае клиент ожидает collection. Во втором он ожидает одну Task или понятную ошибку отсутствия.

Если сервер иногда возвращает список по /tasks/7, а иногда объект, клиенту приходится угадывать форму ответа. У path должна быть предсказуемая область действия.

### Method зависит от области и действия

Посмотрим на независимый пример сервиса бронирований:

~~~text
GET /bookings      → прочитать набор бронирований
GET /bookings/18   → прочитать одно бронирование
~~~

В первом случае method выбирает чтение collection. Во втором тот же method читает выбранный item. Для создания и изменения нужно учесть, кто назначает идентификатор и меняется ли существующий item. Смысл HTTP methods вы уже разбирали в прошлом занятии; в практике примените его к Planner, не копируя готовую таблицу.

### Интерактив. Определите масштаб

Для каждой строки ответьте: collection или item?

1. /tasks
2. /tasks/12
3. /courses
4. /courses/3

Дополнительный вопрос: что в строках /tasks/12 и /courses/3 сообщает, что речь идёт об одном объекте? В обоих случаях после основы collection стоит значение идентификатора.

### Именование идентификатора

В публичной карте лучше использовать понятное обозначение task_id, а не внутреннее имя переменной вроде x или row_number. На этом уровне мы только фиксируем форму пути. Как сервер получит и проверит значение, будет разобрано позже.

Важно отличать placeholder от настоящего текста:

~~~text
/tasks/{task_id}
~~~

Это шаблон item path. В реальном URL фигурирует конкретное значение, например /tasks/7.

### С чем путают collection

Collection путают со страницей интерфейса. /tasks не обязан означать экран со списком. Это внешний адрес набора ресурсов. Один клиент может показать его таблицей, другой карточками, третий использовать для фоновой синхронизации.

### В рабочем сервисе

Различие collection и item помогает согласовать кэширование, права, ошибки и форму response. Для отсутствующего item обычно нужен один понятный сценарий, а пустая collection может быть успешным результатом с пустым списком.

## 04. Имена path: существительные вместо кнопок

В ресурсоориентированной карте path обычно называет сущность существительным. Method уже сообщает действие.

~~~text
POST /tasks
а не
POST /create-task
~~~

В договоре Planner POST /tasks выбран для создания Task. Path называет тип ресурса, а method выражает выбранное для него намерение. Во втором варианте действие повторено дважды: в POST и в слове create.

### Почему множественное число удобно

Множественное число помогает сразу увидеть collection:

~~~text
/tasks
/courses
/lessons
/categories
~~~

Item строится от той же основы:

~~~text
/tasks
/tasks/7
~~~

Такой стиль проще продолжить для новых ресурсов и объяснить другому разработчику.

### Нужен один стиль

Проблема возникает, когда одна часть API использует множественное число, другая единственное, а третья смешивает snake_case и CamelCase:

~~~text
/tasks
/course
/LessonItems
/get_categories
~~~

Каждый вариант может быть обработан сервером. Но карта становится менее предсказуемой. Соглашение нужно выбрать один раз и соблюдать последовательно.

### Не все пути являются ресурсами

GET /health является хорошим примером технического пути. Он сообщает о состоянии сервиса, а не адресует collection задач. Не нужно притворяться, что health является Task только ради единого шаблона.

Другие специальные пути тоже возможны. Важно назвать их специальными и не смешивать с resources без причины.

### Интерактив. Найдите лишнее действие

~~~text
POST /create-task
GET /get-bookings
DELETE /delete-booking/18
~~~

Ответьте:

1. Какие слова дублируют method?
2. Какой базовый resource можно оставить в каждой строке?
3. Какая строка должна обращаться к item?

Наводка: сначала уберите глаголы из path, затем решите, есть ли у операции конкретный идентификатор.

### Когда глагольный путь всё же допустим

Операции вроде /health, /login или /search не всегда являются обычными ресурсами с базовыми действиями создания, чтения, изменения и удаления. Их нельзя автоматически объявить ошибкой. Нужно спросить:

- является ли объект самостоятельной сущностью;
- есть ли у него стабильное представление;
- можно ли выразить действие стандартным method;
- не создаём ли мы искусственную сущность только ради привычного слова.

Для Planner базовые задачи хорошо описываются как resource tasks, поэтому отдельные /create-task и /delete-task нам не нужны.

### В рабочем сервисе

Единое именование уменьшает количество ошибок в клиентских библиотеках, документации, тестах и мониторинге. Когда маршрут добавляется в рабочий сервис, его название становится частью публичного договора и может жить дольше конкретного разработчика.

## 05. URL, path, endpoint и method

Эти термины связаны, но не являются одним и тем же. Чёткое различие помогает читать документацию и не путать полный адрес с частью запроса.

### URL

URL расшифровывается как Uniform Resource Locator, «унифицированный указатель ресурса». Для HTTP API это полный сетевой адрес. В нём могут быть схема, host, port, path и другие части:

~~~text
https://studyhub.example/tasks/7
└────────────────────────────┘
             полный URL
~~~

В локальной разработке host и port могут выглядеть так:

~~~text
http://localhost:8000/tasks/7
~~~

URL отвечает на вопрос, куда отправить request целиком.

### Path

Path является частью URL, которая задаёт расположение внутри API. Например, здесь это `/tasks/7`:

~~~text
URL:
http://localhost:8000/tasks/7

path:
/tasks/7
~~~

Path описывает расположение resource внутри конкретного API, но сам по себе не говорит, что сделать. Для этого нужен method.

### Method

Method выбирает смысл действия:

~~~text
GET /tasks/7
DELETE /tasks/7
~~~

Path одинаковый, но endpoints разные, потому что method различается.

### Endpoint (конечная точка API)

В рамках курса endpoint удобно понимать как конкретную пару method и path:

~~~text
GET /tasks/7
~~~

Это уже не просто path и не полный URL. Это конкретная операция, которую клиент может описать в карте API.

### Три уровня одного адреса

~~~text
полный URL:
http://localhost:8000/tasks/7

path:
/tasks/7

endpoint:
GET /tasks/7
~~~

Если заменить GET на DELETE, URL и path могут остаться теми же, но endpoint и contract изменятся.

### Интерактив. Разложите выражение

В документации API часто рядом записывают method и полный URL. Это удобная запись для человека, но не строка HTTP/1.1-запроса:

~~~text
POST https://api.example.com/tasks
~~~

Для прямого HTTP/1.1-запроса строка запроса содержит path, а host передаётся отдельно в заголовке:

~~~text
POST /tasks HTTP/1.1
Host: api.example.com
~~~

Ответьте:

1. Что здесь является method?
2. Что является полным URL?
3. Какой path останется после host?
4. Какая конкретная операция получится из пары method и path?

Не нужно пока писать HTTP-клиент. Важно различать полный URL и path, который попадает в строку запроса. В прямом запросе host передаётся отдельно от строки запроса.

### С чем путают endpoint

Endpoint иногда называют только path, а иногда только функцией обработчика. В разных командах слово действительно используется свободнее. В этом курсе для карты фиксируем точное правило: endpoint это method плюс path.

Такое правило нужно не ради терминологии. Оно не даёт случайно описать GET /tasks и POST /tasks как одну и ту же операцию.

### В рабочем сервисе

Полный URL зависит от среды. При локальной разработке host и port одни, в тестовой среде другие, в рабочей среде третьи. Path и method обычно являются устойчивой частью договора, а базовый URL задаётся настройками клиента.

Поэтому документация часто отдельно описывает базовый URL и карту маршрутов. Это позволяет менять домен или порт без переписывания смысла каждого endpoint.

## 06. GET /health: техническая проверка, а не Task

Сервису нужно проверять не только предметные resources. Иногда важно узнать, запущен ли процесс и может ли он принять request. Для этого часто используют технический путь /health.

~~~text
GET /health
→ приложение отвечает на проверочный запрос
~~~

### Почему health не является resource tasks

Health не обозначает одну задачу и не обозначает collection задач. Он отвечает на инфраструктурный вопрос: «жив ли процесс или доступен ли минимальный сервисный слой?»

Если включить /health в таблицу tasks, мы смешаем две разные области:

- бизнес-данные пользователя;
- техническое состояние приложения.

Такой route может вернуть короткий JSON или простой status. Его задача не показать список и не создать сущность.

### Что проверяет health

Минимальная проверка может означать, что процесс отвечает. Более глубокая readiness-проверка может дополнительно проверить обязательные зависимости. Эти понятия важно не смешивать:

~~~text
liveness (проверка активности процесса):
процесс отвечает

readiness (проверка готовности сервиса):
сервис готов принимать рабочий трафик
~~~

На этом уровне нам не нужно реализовывать проверки базы данных. Достаточно понимать, что технический route имеет другой смысл.

### Почему method здесь GET

Клиент хочет прочитать состояние сервиса, а не создать или изменить Task. Поэтому GET естественно выражает намерение. Сам факт health-запроса не должен создавать запись или менять пользовательские данные.

### Интерактив. Ошибка классификации

Разработчик записал:

~~~text
Resource: tasks
GET /health → получить одну Task
~~~

Что здесь нужно исправить? Назовите две ошибки. Правильное направление: /health является технической проверкой, а не item path задач.

### В рабочем сервисе

Health и readiness используют балансировщики, оркестраторы, системы мониторинга и проверки после развёртывания. Такой route должен быть быстрым и предсказуемым. Он не должен запускать тяжёлую бизнес-операцию только ради ответа «жив».

## 07. Согласованная карта и типичные ошибки

Теперь объединим понятия. Под картой маршрутов (route map) будем понимать таблицу, в которой для каждой операции указаны method, path и понятная цель. Хорошая карта отвечает на четыре вопроса для каждой строки:

1. Это предметный resource или техническая проверка?
2. Работаем с collection или item?
3. Какой method выражает действие?
4. Какую короткую цель поймёт другой разработчик?

### Как выглядит карта на уровне смысла

Для Planner карта должна включать:

- техническую проверку доступности;
- чтение collection tasks;
- создание Task;
- чтение одного item;
- полную замену item;
- частичное изменение item;
- удаление item.

Точная таблица будет собрана в практике. До её записи важно понимать, почему строки разделены именно так.

### Типичная ошибка 1. Глаголы в path

~~~text
POST /create-task
~~~

Вопрос для диагностики: какое слово уже сообщает method? Ответ помогает увидеть лишнюю часть create.

### Типичная ошибка 2. Collection и item перепутаны

~~~text
DELETE /tasks
~~~

Такой контракт может означать удаление всей collection, если это явно разрешено. Но если разработчик хотел удалить одну Task, в path не хватает идентификатора item. Ошибка возникает, когда не задали область действия до выбора method.

### Типичная ошибка 3. Одинаковый path считают одним endpoint

~~~text
GET /tasks/7
PATCH /tasks/7
~~~

Path совпадает, но операции разные. Их нужно описать отдельно, потому что method меняет смысл, body и response contract.

### Типичная ошибка 4. Resource смешивают со storage

~~~text
GET /tasks-json-file
~~~

Клиенту не нужна публичная сущность «JSON-файл». Такой путь раскрывает внутреннюю деталь и делает будущую замену storage дорогой.

### Типичная ошибка 5. Вложенность без причины

~~~text
/users/4/courses/8/modules/3/lessons/2/tasks/7
~~~

Глубокий путь может быть оправдан, если каждая связь нужна клиенту. Но иногда он просто переносит внутреннюю структуру базы данных в URL. Если карта становится длиннее, спросите, какой resource действительно выбирается и нельзя ли отделить связь отдельным правилом.

### Интерактив. Соберите рассуждение

Расположите вопросы в полезном порядке:

~~~text
A. выбрать method
B. назвать resource
C. определить collection или item
D. проверить, нужен ли технический route
E. записать endpoint
~~~

Подумайте, почему выбор method не всегда должен быть первым. Сначала нужно понять объект и область действия, иначе легко выбрать DELETE для всей collection вместо удаления одного item.

### Ограничения REST

REST не решает автоматически:

- кто имеет доступ;
- как валидировать body;
- какой status вернуть в каждой ошибке;
- как хранить данные;
- как делать транзакции;
- как версионировать изменения;
- как защищать endpoint.

Он даёт читаемую форму взаимодействия. Остальные инженерные решения должны быть описаны отдельными слоями.

## 08. Что мы будем делать в практике

Практика будет ручной и проектной. Мы не будем писать серверный код. Результатом станет начало документа docs/planner-api-v1.md с картой операций внешнего Planner API до реализации.

### Глобальный результат

После практики у проекта появится один документ, где новый разработчик сможет увидеть:

- какой resource является главным для Planner;
- чем collection отличается от item;
- какие path используются для набора и одной Task;
- какие endpoints относятся к health и к tasks;
- какой method выражает каждую операцию;
- где находится граница между публичным API и внутренним storage.

### Что нужно будет сделать

В одном документе мы сначала зафиксируем предметный смысл tasks и компактное представление, видимое клиенту. Затем отличим адрес всей collection от адреса одного item. На этой основе составим карту операций для health и задач, а в конце обозначим ожидаемый ответ для неизвестного item и детали, которые пока не входят в договор. Каждая карточка добавляет следующий слой к тому же документу.

### Какой результат считается доказанным

Документ готов, если:

- resource описан предметными словами;
- storage не выдан за часть публичного API;
- collection и item не смешаны;
- method и path образуют отдельные endpoints;
- PUT и PATCH имеют разный смысл;
- GET /health проверяет, отвечает ли приложение, и отделён от tasks;
- неизвестный item связан с ожидаемым 404;
- отсутствуют глагольные path для обычных действий над ресурсом;
- карту можно прочитать без устного объяснения автора.

### Границы практики

В работе намеренно не будет:

- декораторов;
- FastAPI-кода;
- подробного распределения параметров и данных между path, query и body;
- схем данных;
- реализации хранения;
- запуска реального HTTP-сервера.

Карта нужна перед кодом. Если сразу писать обработчики, можно получить работающие функции с противоречащим друг другу публичным договором.

### Подготовка к следующему шагу

После этой карты мы сможем задавать для каждого endpoint следующий набор вопросов: где находится идентификатор, какие значения приходят в query, что лежит в body, какой status считается успехом и как выглядит ошибка. Эти вопросы будут разобраны отдельно, поэтому сейчас не нужно заполнять их заранее.

### Короткий итог

Запомните связку:

~~~text
resource → предметная сущность
collection → набор сущностей
item → одна сущность по идентификатору
path → расположение внутри API
method → действие
endpoint → method + path
URL → полный адрес
~~~

В Planner API ресурсом является Task, collection является набором tasks, а отдельный item выбирается по task id. Практика зафиксирует эту модель в документе, чтобы следующий код строился на одном понятном договоре.
