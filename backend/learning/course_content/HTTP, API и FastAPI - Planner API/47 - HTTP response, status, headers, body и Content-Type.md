## 00. Request отправлен. Что получает клиент?

В прошлом занятии мы разобрали сообщение клиента. В нём были адрес, method, headers и возможный body. Теперь представим, что сервер уже получил это сообщение и выполнил работу.

Клиенту недостаточно узнать, что соединение завершилось. Ему нужно понять результат:

- задача создана;
- задача найдена;
- задача не существует;
- данные не прошли проверку;
- сервер не смог выполнить операцию.

Для этого сервер возвращает HTTP response.

Представьте пункт выдачи заказа. Клиент передал бланк и теперь получает квитанцию. На ней есть краткий итог, служебные отметки и, если нужно, содержимое заказа. Квитанция должна быть понятна и человеку, и программе.

~~~text
request:
клиент → сервер
«сделай или покажи»

response:
сервер → клиент
«вот результат или причина отказа»
~~~

### Что уже известно

Мы уже понимаем:

- клиент отправляет request;
- сервер владеет правилами и источником истины;
- request имеет несколько разных частей;
- body может отсутствовать;
- внешний обмен не равен прямому вызову Python-метода.

### Что добавляется сейчас

Response также является составным сообщением. У него есть:

- status, то есть числовой исход;
- headers, то есть служебное описание;
- body, то есть данные результата или ошибки.

Эти части отвечают на другие вопросы:

~~~text
чем закончилась операция?
как описано сообщение?
какие данные или детали вернуть?
~~~

### Главная идея

Status и body не конкурируют между собой.

Status быстро сообщает категорию результата. Body объясняет конкретные данные. Например, 404 говорит, что ресурс не найден, а body может сообщить, какой именно идентификатор отсутствует.

### Чего пока не будет

В этом занятии не нужны:

- FastAPI;
- HTTPException;
- реальные запросы;
- middleware;
- сложная обработка исключений;
- logging;
- база данных;
- интеграция с Planner API.

Сначала соберём учебную модель response в обычном словаре Python. Она позволит проверить смысл каждой части без запуска сервера.

**Остановитесь на минуту.** Если сервер вернул body с текстом «Task not found», почему клиенту всё равно нужен status? Потому что программа не должна угадывать исход по человеческой фразе. Для этого есть стандартный числовой сигнал.

## 01. Response является результатом обработки

Response появляется после того, как сервер прочитал request и выполнил или отклонил операцию.

~~~text
request
    ↓
сервер понимает намерение
    ↓
сервер проверяет данные
    ↓
сервер применяет правило
    ↓
response
~~~

Внутри сервера может работать знакомый PlannerService:

~~~text
клиент
  ↓ request
сервер
  ↓
PlannerService
  ↓
storage
  ↑
сервер формирует response
  ↑
клиент
~~~

Клиент видит только response. Он не видит внутренний объект Task, путь к JSON-файлу или traceback.

### Response не равен print

В локальном CLI программа может напечатать:

~~~text
Task created
~~~

Такой текст удобен человеку, но другому клиенту сложно надёжно понять:

- создана ли задача;
- какой у неё id;
- можно ли считать операцию успешной;
- является ли это сообщением об ошибке.

Response делает результат структурированным:

~~~text
status: 201
body: созданная задача
~~~

### Response не равен return обычной функции

Внутри одного процесса:

~~~python
task = service.add_task("Изучить HTTP")
~~~

Переменная task сразу доступна вызывающему коду.

На внешней границе:

~~~text
сервер формирует response
клиент получает response
клиент разбирает его части
~~~

Между сторонами нет общей переменной в памяти. Результат должен быть представлен так, чтобы другой процесс смог его понять.

### Три части ответа

| Часть | На какой вопрос отвечает | Пример |
| --- | --- | --- |
| status | чем закончилась обработка | 200, 404 |
| headers | как описано сообщение | Content-Type |
| body | какие данные или детали вернуть | Task или detail |

Не нужно заставлять одну часть выполнять работу другой.

### Независимый пример

Сервис бронирования может ответить:

~~~text
status: 201
headers:
  Content-Type: application/json
body:
  {
    "booking_id": 18,
    "seat": "A12"
  }
~~~

Status сообщает, что новая запись создана. Body содержит её представление. Клиент может показать номер бронирования, а не искать его в строке.

### Production-контекст

В production один response могут читать:

- браузер;
- мобильное приложение;
- другой backend;
- фоновый job;
- система мониторинга.

Каждому нужна стабильная структура. Если один endpoint иногда возвращает список, иногда строку и иногда внутренний traceback, клиентский код становится хрупким.

### Интерактив. Что изменилось?

Сравните два результата:

~~~text
«Задача создана»
~~~

и:

~~~text
status: 201
body: {"id": 7, "title": "Изучить HTTP"}
~~~

Второй вариант полезнее для программы, потому что в нём отдельно выражены исход и данные. Человек тоже может получить понятное сообщение, но интерфейс строится уже на структурированном ответе.

### Связь с текущей практикой

В учебной функции response будет обычным словарём. Она не создаёт Task и не меняет storage. Её задача состоит в том, чтобы представить готовые status, body и request id в согласованной форме.

## 02. Status сообщает исход операции

Status code является коротким числовым сигналом. По первой цифре клиент понимает общую категорию, а по всему числу уточняет смысл.

### Группы status

~~~text
2xx → операция успешна
4xx → проблема в request или доступном ресурсе
5xx → сервер не смог выполнить работу
~~~

Это не оценка качества клиента или сервера. Это классификация результата конкретного обращения.

### Почему не хватает только body

Представьте два body:

~~~text
{"message": "Task not found"}
{"message": "Task created"}
~~~

Если клиент должен анализировать произвольные фразы, ему придётся знать язык, варианты формулировок и регистр букв. Status избавляет от такой догадки:

~~~text
404 → ресурс не найден
201 → ресурс создан
~~~

Body дополняет status деталями.

### Status не говорит всё

Код 2xx не означает, что клиент получил именно тот экран, который хотел пользователь. Он сообщает, что сервер обработал request по договору.

Код 4xx не означает, что приложение сломалось. Это может быть ожидаемый случай: пользователь запросил задачу с неизвестным id.

Код 5xx указывает на проблему на серверной стороне. Подробности должны остаться в логах, а не утечь клиенту.

### Небольшой независимый пример

~~~python
def result_kind(status):
    if 200 <= status < 300:
        return "success"
    if 400 <= status < 500:
        return "client_problem"
    if 500 <= status < 600:
        return "server_problem"
    return "other"
~~~

Разбор:

- status 201 попадает в success;
- status 404 попадает в client_problem;
- status 503 попадает в server_problem;
- функция классифицирует число, но не знает, как показать результат в UI.

### Интерактив. Что напечатает код?

~~~python
print(result_kind(404))
~~~

Ответ:

~~~text
client_problem
~~~

Значение этого примера в том, что клиент может выбрать ветку по status, не разбирая текст body.

### Что не нужно делать

Не нужно:

- возвращать 200 для любой ситуации;
- объявлять ошибку только по слову error;
- использовать 500 для неизвестной задачи;
- считать, что любой JSON body означает успех;
- подменять status текстом из body.

### Связь с текущим проектом

Для Planner status будет связывать знакомые операции с внешним договором. Получение существующей задачи и ошибка неизвестного id являются разными исходами, даже если оба response содержат JSON.

## 03. Успешные status: 200, 201 и 204

Успешная операция не всегда означает одно и то же. Код помогает точнее описать, что произошло.

### 200 OK

200 означает, что операция успешно выполнена и клиент обычно получает body.

Пример:

~~~text
GET /tasks
status: 200
body: список задач
~~~

Сервер прочитал данные и вернул результат.

### 201 Created

201 означает, что создан новый ресурс.

Пример:

~~~text
POST /tasks
status: 201
body: созданная Task
~~~

Клиент получает не только подтверждение, но и представление созданного ресурса. В нём может быть id, который назначил сервер.

### 204 No Content

204 означает, что операция успешна, но response не содержит body.

Пример:

~~~text
DELETE /tasks/7
status: 204
body: отсутствует
~~~

Это не ошибка и не «пустой JSON». Это отдельный договор: клиенту достаточно самого факта успешного завершения.

### Почему 204 не должен содержать body

Status уже говорит, что содержимого нет. Если одновременно заявить 204 и положить в response JSON, разные клиенты могут обработать это по-разному.

Сравните:

~~~text
204 + body отсутствует
~~~

и:

~~~text
204 + {"message": "deleted"}
~~~

Первый вариант согласован. Во втором status противоречит содержимому.

### Сравнение

| Сценарий | Status | Body |
| --- | --- | --- |
| прочитать список | 200 | список |
| создать ресурс | 201 | созданный ресурс |
| успешно удалить без результата | 204 | нет body |

### Независимый пример

Сервис заметок может отвечать:

~~~text
GET /notes
200 + коллекция заметок

POST /notes
201 + новая заметка

DELETE /notes/3
204 + без body
~~~

Одна предметная область использует разные status, потому что операции имеют разный результат.

### Интерактив. Выберите код

Ситуация: сервер создал новую задачу и возвращает её id.

Варианты:

- 200;
- 201;
- 204.

Лучшее направление: 201. Он сообщает не только об успехе, но и о создании ресурса.

### Связь с текущей практикой

В автопроверке будет сценарий 200 с body и сценарий 204 без body. Задача не просит выбрать status по действию. Она проверяет, что готовый status не теряется и согласуется с body.

## 04. Ошибочные status: 400, 404, 422 и 500

Ошибки тоже являются частью договора. Пользовательский интерфейс должен понимать, что можно исправить, а что требует работы разработчика.

### 400 Bad Request

400 означает, что request нельзя корректно обработать как обращение по договору.

Примером может быть повреждённый формат сообщения или несовместимые данные, если сервер не может разобрать их как допустимый request.

### 404 Not Found

404 означает, что нужный ресурс не найден.

Для Planner:

~~~text
GET /tasks/999
status: 404
body: {"detail": "Task 999 not found"}
~~~

Здесь сервер работает, request понятен, но задача с таким id отсутствует.

### 422 Unprocessable Content

422 используют, когда структура request понятна, но значения не проходят предметную или схематическую проверку.

~~~text
POST /tasks
body: {"title": "", "priority": 9}
status: 422
~~~

Сервер понял, что клиент хотел создать задачу, но данные не соответствуют ограничениям.

### 500 Internal Server Error

500 означает неожиданную проблему внутри сервера.

~~~text
request понятен
данные допустимы
внутри сервера возник дефект
status: 500
~~~

Клиенту не нужно видеть traceback. Он получает стабильное внешнее сообщение, а разработчик ищет причину по серверным логам.

### Как различать ошибки

Задайте вопросы:

1. Сервер смог понять request?
2. Значения прошли проверку?
3. Нужный ресурс существует?
4. Не произошёл ли неожиданный сбой внутри сервера?

Ответы помогают выбрать смысл ошибки. Не нужно использовать один код для всех ситуаций.

### Типичная ошибка

Плохой сервер может ответить так:

~~~text
status: 200
body: {"error": "Task not found"}
~~~

Клиент видит 200 и может показать успех, хотя операция не выполнена. Текст body противоречит status.

Лучше:

~~~text
status: 404
body: {"detail": "Task not found"}
~~~

### Production-контекст

Клиенты часто по-разному реагируют на категории:

- 4xx показывают пользователю исправимую проблему;
- 5xx предлагают повторить позже или обращаются к поддержке;
- 2xx обновляют экран и локальное состояние.

Это возможно только при согласованном status.

### Интерактив. Найдите ошибку

~~~text
status: 204
body: {"message": "deleted"}
~~~

Проблема в том, что 204 обещает отсутствие body. Если нужен текстовый или JSON-результат, следует выбрать подходящий status с body. Если body не нужен, оставить 204 без него.

### Связь с текущей практикой

Один из тестов передаст body ошибки для status 404. Учебная функция не должна превращать ошибку в успех и не должна удалять её детали.

## 05. Body ответа представляет результат

Body response содержит представление того, что сервер решил вернуть клиенту. Это не обязательно внутренний объект Python.

### Три распространённых формы

#### Один ресурс

~~~text
{
  "id": 7,
  "title": "Изучить HTTP",
  "priority": 4,
  "is_done": false
}
~~~

Так можно представить одну Task.

#### Коллекция

~~~text
[
  {
    "id": 7,
    "title": "Изучить HTTP"
  },
  {
    "id": 8,
    "title": "Разобрать response"
  }
]
~~~

Так сервер представляет список.

#### Ошибка

~~~text
{
  "detail": "Task 7 not found"
}
~~~

Ошибка тоже может иметь структурированный body.

### Представление не равно сущности

Внутри сервера может быть объект:

~~~text
Task(id=7, title="Изучить HTTP")
~~~

Снаружи клиент получает представление:

~~~text
{"id": 7, "title": "Изучить HTTP"}
~~~

Клиенту не нужно знать методы объекта, приватные поля и storage.

Это разделение позволяет менять внутреннюю модель, не заставляя браузер повторять её устройство.

### Что вернуть после создания

Если сервер создал Task, клиенту часто нужен результат:

- назначенный id;
- title;
- priority;
- текущий статус выполнения.

Текст «created» может быть недостаточен, если интерфейсу нужно открыть созданную запись.

### Что вернуть при ошибке

Body ошибки должен быть:

- понятным;
- стабильным;
- безопасным;
- достаточно подробным для реакции клиента.

Traceback, путь к файлу и секреты не являются хорошим внешним body.

### Body и status работают вместе

~~~text
201 + Task
404 + detail
204 + нет body
~~~

Нельзя читать body отдельно от status. Даже корректный JSON может быть ответом об ошибке.

### Независимый пример

API каталога может вернуть:

~~~text
status: 200
body: {"id": 3, "name": "Book"}
~~~

или:

~~~text
status: 404
body: {"detail": "Book 3 not found"}
~~~

Форма body похожа, но смысл результата определяет status.

### Интерактив. Что показать пользователю?

Response:

~~~text
status: 404
body: {"detail": "Task 999 not found"}
~~~

Клиент должен показать проблему с отсутствующей задачей. Он не должен добавить такую задачу в локальный список и не должен считать операцию успешной.

### Связь с текущей практикой

Body передаётся в функцию готовым значением. Его нужно сохранить без подмены. Это позволяет проверить и обычный словарь результата, и словарь ошибки, и отсутствие body.

## 06. Headers ответа и Content-Type

Response headers описывают сообщение так же, как headers request описывали обращение клиента.

Главный header для текущей темы:

~~~text
Content-Type
~~~

Он сообщает клиенту, как читать body.

### JSON response

~~~text
Content-Type: application/json

{"id": 7, "title": "HTTP"}
~~~

Клиент понимает, что body нужно разобрать как JSON.

### Текстовый response

~~~text
Content-Type: text/plain; charset=utf-8

Server is running
~~~

Здесь body является текстом.

### Content-Type и отсутствие body

Если body отсутствует, не нужно делать вид, что сервер отправил JSON-объект.

~~~text
204
body отсутствует
Content-Type для body не добавляется
~~~

Это продолжение правила из прошлого занятия: описывать нужно реально присутствующее тело.

### Headers и тело не смешиваются

Content-Type не содержит сам body. Он только сообщает его формат.

~~~text
Content-Type: application/json
        ↓
объясняет формат
        ↓
body содержит JSON
~~~

Если в body лежит строка с JSON, но header говорит text/plain, договор становится противоречивым.

### Независимый пример

~~~text
Content-Type: image/png
~~~

Такой header сообщает формат изображения. Само изображение должно быть передано отдельно, в body.

### X-Request-ID

В production к response часто добавляют идентификатор обращения:

~~~text
X-Request-ID: req-101
~~~

Он помогает связать сообщение клиента с записью в серверных логах. Пользователь может не видеть этот id, но поддержка сможет найти конкретный запрос.

В нашей учебной модели X-Request-ID нужен, чтобы показать ещё одну служебную часть response. Мы не строим систему логирования и не проверяем уникальность id.

### Типичная ошибка

~~~text
status: 200
Content-Type: application/json
body: Server is running
~~~

Header обещает JSON, а body содержит обычный текст. Клиент может попытаться разобрать строку как объект и получить ошибку.

### Production-контекст

В реальных системах headers также участвуют в:

- кэшировании;
- авторизации;
- ограничении доступа;
- трассировке;
- выборе языка;
- согласовании формата.

Не нужно изучать все заголовки сразу. Сейчас важны Content-Type и идея служебных метаданных.

### Связь с текущей практикой

Практика всегда добавляет X-Request-ID из готового request_id. Content-Type добавляется только тогда, когда body не равен None. Это правило будет проверено отдельным сценарием 204.

## 07. Request и response образуют одну пару

Request и response нельзя проектировать в отрыве друг от друга.

~~~text
request:
method + path + headers + body

response:
status + headers + body
~~~

Клиент отправляет первую половину пары. Сервер возвращает вторую.

### Успешная пара

~~~text
REQUEST
POST /tasks
body: {"title": "Изучить HTTP", "priority": 4}

RESPONSE
201 Created
body: {"id": 7, "title": "Изучить HTTP", "priority": 4}
~~~

Путь данных:

1. клиент сформулировал создание;
2. сервер проверил request;
3. PlannerService создал Task;
4. storage сохранил состояние;
5. сервер вернул представление новой Task;
6. клиент обновил экран.

### Ошибочная пара

~~~text
REQUEST
GET /tasks/999

RESPONSE
404 Not Found
body: {"detail": "Task 999 not found"}
~~~

Здесь сервер не нашёл ресурс. Это не неожиданный сбой и не причина возвращать 500.

### Пара без body

~~~text
REQUEST
DELETE /tasks/7

RESPONSE
204 No Content
body отсутствует
~~~

Клиенту не нужна дополнительная структура, если договор говорит, что успешное удаление не возвращает содержимое.

### Как клиент использует response

Упрощённо:

~~~text
получить response
    ↓
прочитать status
    ↓
выбрать ветку успеха или ошибки
    ↓
если body есть, разобрать его по Content-Type
    ↓
обновить интерфейс
~~~

Клиент не должен сначала безусловно разбирать body, а потом выяснять, что status был 404 или 204.

### Типичная ошибка

Разработчик проверяет только наличие ключа id в body. Тогда:

- ошибка 404 может быть принята за пустой результат;
- response 204 вызовет ошибку разбора;
- серверный статус останется без внимания.

Правильный порядок начинается со status.

### Production-контекст

Такой порядок позволяет единому клиентскому слою обрабатывать много endpoints. Для каждого endpoint меняются детали body, но базовый алгоритм остаётся похожим: status, headers, body, реакция интерфейса.

## 08. Что мы будем делать в практике

Практика проверит одну изолированную функцию в редакторе. Она не подключается к сети, не запускает сервер и не создаёт реальные HTTP-объекты.

### Общий результат

Нужно представить response обычным словарём Python. В модели будут:

- status;
- headers;
- body.

Функция должна сохранить смысл готового результата, а не выполнять запрос заново.

### Что дано

Функция получает:

- status, то есть целое число HTTP-исхода;
- body, то есть словарь или None;
- request_id, то есть идентификатор обращения.

Значения уже подготовлены автопроверкой. Не нужно придумывать их внутри функции.

### Что требуется понять

До редактора ответьте:

1. Какой header добавляется всегда?
2. Когда появляется Content-Type?
3. Почему None нельзя заменить пустым словарём?
4. Почему status и body возвращаются без изменения?
5. Почему функция не должна печатать результат?

### Как будет проверен результат

Автопроверка использует три сценария:

- успешный response 200 с JSON body;
- ошибка 404 с JSON body;
- успешный response 204 без body.

Проверяется весь словарь. Будут замечены:

- пропущенный X-Request-ID;
- лишний Content-Type у 204;
- подмена None;
- изменение status;
- изменение body;
- печать вместо return.

### Чего делать не нужно

Не нужно:

- запускать FastAPI;
- отправлять request;
- вызывать PlannerService;
- читать storage;
- писать HTTPException;
- создавать middleware;
- подключать logging;
- сериализовать словарь вручную;
- угадывать status по тексту body.

Это отдельная проверка структуры response. Реальный сервер появится позже, когда request и response будут встроены в настоящий контракт.

### Как начать

Сначала создайте headers с постоянным служебным значением. Затем проверьте наличие body. Только при наличии body добавьте Content-Type. После этого соберите status, headers и body в итоговый словарь.

Проверьте контраст:

~~~text
body = {"id": 1}
body = None
~~~

Второй вариант должен сохранить отсутствие тела.

### Доказательство результата

Функция готова, если:

- возвращает словарь;
- использует точные ключи status, headers и body;
- переносит request_id в X-Request-ID;
- добавляет Content-Type только при body;
- сохраняет None;
- проходит 200, 404 и 204.

После выполнения ученик сможет отличить результат операции от его представления и перейти к method.

### Проверьте себя на трёх ответах

~~~text
A:
status: 200
body: {"id": 1}

B:
status: 404
body: {"detail": "Task not found"}

C:

~~~

Для каждого ответа назовите:

- исход операции;
- есть ли body;
- должен ли понадобиться Content-Type;
- какую реакцию выберет клиент.

### Главное

- Response сообщает результат обработки request.
- Status даёт машинно читаемую категорию исхода.
- 200 обычно возвращает успешный body.
- 201 сообщает о создании ресурса.
- 204 означает успех без body.
- 4xx описывает понятную проблему request или ресурса.
- 5xx сообщает о внутренней проблеме сервера.
- Body содержит представление результата или детали ошибки.
- Content-Type объясняет формат body.
- X-Request-ID помогает связать response с обращением.
- None и пустой словарь не равны автоматически.
- Учебная функция проверяет модель response без сети.
- Следующая работа свяжет method с CRUD-действиями.

После самопроверки открывайте редактор. Сначала отделите постоянный header от условного, затем верните status, headers и body одной структурой. Ваша цель не написать сервер, а показать, что результат операции и данные ответа не перепутаны.
