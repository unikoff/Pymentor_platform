## 00. Request отправлен. Что получает клиент?

В прошлом занятии мы разобрали сообщение клиента. В нём были адрес, method, headers и возможный body. Теперь представим, что сервер получил это сообщение и определил, какой исход вернуть. Иногда работа уже завершена, а иногда запрос только принят для дальнейшей обработки. Точный смысл сообщает status.

Клиенту недостаточно узнать, что соединение завершилось. Ему нужно понять результат:

- задача создана;
- задача найдена;
- задача не существует;
- данные не прошли проверку;
- сервер не смог выполнить операцию.

Для этого сервер возвращает HTTP response (ответ сервера).

Представьте пункт выдачи заказа. Клиент передал бланк и теперь получает квитанцию. На ней есть краткий итог, служебные отметки и, если нужно, содержимое заказа. Квитанция должна быть понятна и человеку, и программе.

~~~text
request:
клиент → сервер
«сделай или покажи»

response:
сервер → клиент
«вот результат или причина отказа»
~~~

### Что уже известно

Мы уже понимаем:

- клиент отправляет request;
- сервер владеет правилами и источником истины;
- request имеет несколько разных частей;
- body может отсутствовать;
- внешний обмен не равен прямому вызову Python-метода.

### Что добавляется сейчас

Response также является составным сообщением. У него есть:

- status, то есть числовой исход;
- headers, то есть служебное описание;
- body, то есть данные результата или ошибки.

В API ресурсом называют объект, с которым работает программа. В нашем примере это задача Planner: её можно получить, создать или удалить.

Эти части отвечают на другие вопросы:

~~~text
чем закончилась операция?
как описано сообщение?
какие данные или детали вернуть?
~~~

### Главная идея

Status и body не конкурируют между собой.

Status быстро сообщает категорию результата. Body объясняет конкретные данные. Например, 404 говорит, что ресурс не найден, а body может сообщить, какой именно идентификатор отсутствует.

### Чего пока не будет

В этом занятии мы не запускаем настоящий сервер, не отправляем сообщения по сети, не подключаем задачу к Planner и не разбираем автоматическую проверку входных данных. Сначала соберём учебную модель response в обычном словаре Python. Она позволит проверить смысл каждой части без сетевого обмена.

**Остановитесь на минуту.** Если сервер вернул body с текстом «Task not found», почему клиенту всё равно нужен status? Потому что программа не должна угадывать исход по человеческой фразе. Для этого есть стандартный числовой сигнал.

## 01. Response является результатом обработки

Response появляется после того, как сервер прочитал request и определил результат текущего этапа обработки. Некоторые операции к этому моменту уже завершены, а другие могут продолжиться позже.

~~~text
request
    ↓
сервер понимает намерение
    ↓
сервер проверяет данные
    ↓
сервер применяет правило
    ↓
response
~~~

Внутри сервера может работать знакомый PlannerService:

~~~text
клиент
  ↓ request
сервер
  ↓
PlannerService
  ↓
storage
  ↑
сервер формирует response
  ↑
клиент
~~~

Клиент видит только response. Внешний ответ не должен раскрывать внутренний объект Task, путь к JSON-файлу или технические подробности сбоя.

### Response не равен print

В локальном CLI программа может напечатать:

~~~text
Task created
~~~

Такой текст удобен человеку, но другому клиенту сложно надёжно понять:

- создана ли задача;
- какой у неё id;
- можно ли считать операцию успешной;
- является ли это сообщением об ошибке.

Response делает результат структурированным:

~~~text
status: 201
body: созданная задача
~~~

### Response не равен return обычной функции

Внутри одного процесса:

~~~python
task = service.add_task("Изучить HTTP")
~~~

Переменная task сразу доступна вызывающему коду.

На внешней границе:

~~~text
сервер формирует response
клиент получает response
клиент разбирает его части
~~~

Между сторонами нет общей переменной в памяти. Результат должен быть представлен так, чтобы другой процесс смог его понять.

### Три части ответа

| Часть | На какой вопрос отвечает | Пример |
| --- | --- | --- |
| status | чем закончилась обработка | 200, 404 |
| headers | как описано сообщение | Content-Type |
| body | какие данные или детали вернуть | Task или detail |

Не нужно заставлять одну часть выполнять работу другой.

### Независимый пример

Сервис бронирования может ответить:

~~~text
status: 201
headers:
  Content-Type: application/json
body:
  {
    "booking_id": 18,
    "seat": "A12"
  }
~~~

Status сообщает, что новая запись создана. Body содержит её представление. Клиент может показать номер бронирования, а не искать его в строке.

### Как это используют в работе

В реальном сервисе один response могут читать:

- браузер;
- мобильное приложение;
- другой backend;
- другая автоматически запущенная задача;
- система мониторинга.

Каждому нужна стабильная структура. Если одна и та же операция API иногда возвращает список, иногда строку и иногда внутренние подробности сбоя, код клиента становится хрупким.

### Интерактив. Что изменилось?

Сравните два результата:

~~~text
«Задача создана»
~~~

и:

~~~text
status: 201
body: {"id": 7, "title": "Изучить HTTP"}
~~~

Второй вариант полезнее для программы, потому что в нём отдельно выражены исход и данные. Человек тоже может получить понятное сообщение, но интерфейс строится уже на структурированном ответе.

### Связь с текущей практикой

В учебной функции response будет обычным словарём. Она не создаёт Task и не меняет storage. Её задача состоит в том, чтобы представить готовые status, body и request id в согласованной форме.

## 02. Status сообщает исход операции

Status code является коротким числовым сигналом. По первой цифре клиент понимает общую категорию, а по всему числу уточняет смысл.

### Группы status

~~~text
1xx → информационный ответ о ходе запроса или соединения
2xx → успешный исход в смысле точного status
3xx → клиенту нужно выполнить дополнительное действие
4xx → запрос нельзя выполнить в отправленном виде или недоступен ресурс
5xx → сервер не смог выполнить корректный на вид запрос
~~~

Первая цифра задаёт класс результата, а не оценку качества клиента или сервера. Точный смысл сообщает всё число. Например, клиент может получить 1xx до окончательного ответа, 3xx может потребовать дополнительного действия, а 404 говорит, что нужный ресурс не найден. Код 101 отдельно сообщает о смене протокола, поэтому одной фразы «1xx всегда временный» недостаточно.

Есть тонкость у группы 2xx. Статус 202 означает, что сервер принял запрос для дальнейшей обработки, но ещё не завершил её. Поэтому сначала смотрите точный status, а не только первую цифру. Здесь подробно разберём 200, 201 и 204.

### Почему не хватает только body

Представьте два body:

~~~text
{"message": "Task not found"}
{"message": "Task created"}
~~~

Если клиент должен анализировать произвольные фразы, ему придётся знать язык, варианты формулировок и регистр букв. Status избавляет от такой догадки:

~~~text
404 → ресурс не найден
201 → ресурс создан
~~~

Body дополняет status деталями.

### Status не говорит всё

Код 2xx сообщает об успешном исходе в смысле точного status, но не всегда означает, что вся работа закончена. Например, 202 означает, что запрос приняли для обработки, которая может продолжиться позже.

Код 4xx не означает, что приложение сломалось. Это может быть ожидаемый случай: пользователь запросил задачу с неизвестным id.

Код 5xx указывает на проблему на серверной стороне. Подробности должны остаться в логах, а не утечь клиенту.

### Небольшой независимый пример

~~~python
def status_group(status):
    if 100 <= status < 200:
        return "информация"
    if 200 <= status < 300:
        return "успех"
    if 300 <= status < 400:
        return "переход"
    if 400 <= status < 500:
        return "проблема_запроса"
    if 500 <= status < 600:
        return "проблема_сервера"
    return "другая_категория"
~~~

Разбор:

- status 101 попадает в информационную категорию и сообщает о смене протокола;
- status 201 попадает в категорию успешных исходов;
- status 302 попадает в категорию, где требуется дополнительное действие;
- status 404 попадает в категорию проблемы запроса или ресурса;
- status 503 попадает в категорию проблемы сервера;
- функция определяет только класс. По одному классу она не выбирает точную реакцию интерфейса.

### Интерактив. Что напечатает код?

~~~python
print(status_group(302))
~~~

Ответ:

~~~text
переход
~~~

Значение этого примера в том, что клиент может определить общий класс по status, не разбирая текст body.

### Что не нужно делать

Не нужно:

- возвращать 200 для любой ситуации;
- объявлять ошибку только по слову error;
- использовать 500 для неизвестной задачи;
- считать, что любой JSON body означает успех;
- подменять status текстом из body.

### Связь с текущим проектом

Для Planner status будет связывать знакомые операции с внешним договором. Получение существующей задачи и ошибка неизвестного id являются разными исходами, даже если оба response содержат JSON.

## 03. Успешные status: 200, 201 и 204

Успешная операция не всегда означает одно и то же. Код помогает точнее описать, что произошло.

### 200 OK

200 означает, что операция успешно выполнена и клиент обычно получает body.

Пример:

~~~text
GET /tasks
status: 200
body: список задач
~~~

Сервер прочитал данные и вернул результат.

### 201 Created

201 означает, что создан новый ресурс.

Пример:

~~~text
POST /tasks
status: 201
body: созданная Task
~~~

Клиент получает не только подтверждение, но и представление созданного ресурса. В нём может быть id, который назначил сервер.

В HTTP созданный ресурс может быть указан заголовком `Location`. Если его нет, стандарт связывает основной созданный ресурс с адресом запроса. `Location` означает адрес ресурса, а не его содержимое. В нашей учебной практике этот заголовок не нужен.

При желании можно открыть [официальную спецификацию HTTP 9110 о статусе 201](https://www.rfc-editor.org/rfc/rfc9110.html#section-15.3.2). Практический смысл кода и заголовка уже разобран выше.

### 204 No Content

204 означает, что сервер успешно выполнил запрос и не отправляет в ответе содержимое.

Пример:

~~~text
DELETE /tasks/7
status: 204
body: отсутствует
~~~

Это не ошибка и не «пустой JSON». Это отдельный договор: клиенту достаточно самого факта успешного завершения.

### Почему 204 не должен содержать body

По смыслу HTTP статус 204 завершается без содержимого. Это не пустой JSON-объект `{}`: он сам был бы содержимым. В нашей учебной модели этому отсутствию соответствует значение Python `None`.

Сравните:

~~~text
204 + body отсутствует
~~~

и:

~~~text
204 + {"message": "deleted"}
~~~

Первый вариант согласован. Второй нарушает смысл 204: этот статус сообщает, что содержимого ответа нет.

### Сравнение

| Сценарий | Status | Body |
| --- | --- | --- |
| прочитать список | 200 | список |
| создать ресурс | 201 | созданный ресурс |
| успешно удалить без результата | 204 | нет body |

### Независимый пример

Сервис заметок может отвечать:

~~~text
GET /notes
200 + коллекция заметок

POST /notes
201 + новая заметка

DELETE /notes/3
204 + без body
~~~

Одна предметная область использует разные status, потому что операции имеют разный результат.

### Интерактив. Выберите код

Ситуация: сервер создал новую задачу и возвращает её id.

Варианты:

- 200;
- 201;
- 204.

Лучшее направление: 201. Он сообщает не только об успехе, но и о создании ресурса.

### Интерактив. Найдите противоречие

~~~text
status: 204
body: {"message": "deleted"}
~~~

204 означает успешный ответ без содержимого. Если клиенту нужно получить сообщение или JSON, сервер должен выбрать status и договор, которые допускают body. Если содержимое не нужно, оставляем 204 без него.

### Связь с текущей практикой

Автопроверка получает status готовым и не просит выбирать его по действию. Она проверяет, что функция не меняет этот статус и правильно различает четыре случая: обычное JSON-содержимое, JSON-ошибку, отсутствие содержимого и пустой JSON-объект.

## 04. Ошибочные status: 400, 404 и 500

Ошибки тоже являются частью договора. Пользовательский интерфейс должен понимать, что можно исправить, а что требует работы разработчика.

### 400 Bad Request

400 означает, что сервер считает запрос некорректным и не может обработать его в текущем виде.

Например, сообщение повреждено или его формат не подходит для ожидаемого обращения. Конкретные случаи задаёт контракт API.

### 404 Not Found

404 означает, что нужный ресурс не найден.

Для Planner:

~~~text
GET /tasks/999
status: 404
body: {"detail": "Task 999 not found"}
~~~

Здесь сервер работает, request понятен, но задача с таким id отсутствует.

### 500 Internal Server Error

500 означает неожиданную проблему внутри сервера.

~~~text
request понятен
данные допустимы
внутри сервера возник дефект
status: 500
~~~

Клиенту не нужно видеть внутреннее техническое описание ошибки и цепочку вызовов Python, приведшую к ней. Клиент получает стабильное внешнее сообщение, а разработчик ищет причину в журнале ошибок сервера.

### Как различать ошибки

Задайте вопросы:

1. Сервер смог понять request?
2. Нужный ресурс существует?
3. Не произошёл ли неожиданный сбой внутри сервера?

Ответы помогают выбрать смысл ошибки. Не нужно использовать один код для всех ситуаций.

### Типичная ошибка

Плохой сервер может ответить так:

~~~text
status: 200
body: {"error": "Task not found"}
~~~

Клиент видит 200 и может показать успех, хотя операция не выполнена. Текст body противоречит status.

Лучше:

~~~text
status: 404
body: {"detail": "Task not found"}
~~~

### Как клиент реагирует на исход

Клиент учитывает не только первую цифру, но и конкретный status:

- 200 и 201 позволяют обновить экран данными из body;
- 204 сообщает об успехе без body, поэтому клиент не пытается его разобрать;
- 202 означает, что запрос принят для обработки, но результат ещё не получен;
- 4xx сообщают о проблеме запроса, доступа или ресурса;
- 5xx указывают на серверную проблему. Возможность повтора зависит от конкретной операции и status.

Это возможно только при согласованном status.

### Связь с текущей практикой

Один из тестов передаст body ошибки для status 404. Учебная функция не должна превращать ошибку в успех и не должна удалять её детали.

## 05. Body ответа представляет результат

Body response содержит представление того, что сервер решил вернуть клиенту. Это не обязательно внутренний объект Python.

### Три распространённых формы

#### Один ресурс

~~~text
{
  "id": 7,
  "title": "Изучить HTTP",
  "priority": 4,
  "is_done": false
}
~~~

Так можно представить одну Task.

#### Коллекция

~~~text
[
  {
    "id": 7,
    "title": "Изучить HTTP"
  },
  {
    "id": 8,
    "title": "Разобрать response"
  }
]
~~~

Так сервер представляет список.

#### Ошибка

~~~text
{
  "detail": "Task 7 not found"
}
~~~

Ошибка тоже может иметь структурированный body.

### Представление не равно сущности

Внутри сервера может быть объект:

~~~text
Task(id=7, title="Изучить HTTP")
~~~

Снаружи клиент получает представление:

~~~text
{"id": 7, "title": "Изучить HTTP"}
~~~

Клиенту не нужно знать методы объекта, приватные поля и storage.

Это разделение позволяет менять внутреннюю модель, не заставляя браузер повторять её устройство.

### Что вернуть после создания

Если сервер создал Task, клиенту часто нужен результат:

- назначенный id;
- title;
- priority;
- текущий статус выполнения.

Текст «created» может быть недостаточен, если интерфейсу нужно открыть созданную запись.

### Что вернуть при ошибке

Body ошибки должен быть:

- понятным;
- стабильным;
- безопасным;
- достаточно подробным для реакции клиента.

Путь к файлу, секреты и подробная техническая цепочка вызовов, приведшая к ошибке, не должны попадать во внешний body.

### Body и status работают вместе

~~~text
201 + Task
404 + detail
204 + нет body
~~~

Нельзя читать body отдельно от status. Даже корректный JSON может быть ответом об ошибке.

### Независимый пример

API каталога может вернуть:

~~~text
status: 200
body: {"id": 3, "name": "Book"}
~~~

или:

~~~text
status: 404
body: {"detail": "Book 3 not found"}
~~~

Форма body похожа, но смысл результата определяет status.

### Интерактив. Что показать пользователю?

Response:

~~~text
status: 404
body: {"detail": "Task 999 not found"}
~~~

Клиент должен показать проблему с отсутствующей задачей. Он не должен добавить такую задачу в локальный список и не должен считать операцию успешной.

### Связь с текущей практикой

Body передаётся в функцию готовым значением. Его нужно сохранить без подмены. Это позволяет проверить и обычный словарь результата, и словарь ошибки, и отсутствие body.

## 06. Headers ответа и Content-Type

Response headers описывают сообщение так же, как headers request описывали обращение клиента.

Главный header для текущей темы:

~~~text
Content-Type
~~~

Он сообщает клиенту, как читать body.

### JSON response

~~~text
Content-Type: application/json

{"id": 7, "title": "HTTP"}
~~~

Клиент понимает, что body нужно разобрать как JSON.

### Текстовый response

~~~text
Content-Type: text/plain

Server is running
~~~

Здесь body является текстом.

### Content-Type и отсутствие body

Ответ 204 не содержит тела. В учебной модели значение Python `None` означает, что передаваемого содержимого нет. Поэтому мы не добавляем `Content-Type`, который здесь описывает формат имеющегося body. Другие headers, например `X-Request-ID`, при этом могут остаться.

~~~text
204
body отсутствует
в этой модели Content-Type не добавляется
~~~

Это правило нашей учебной модели, а не утверждение, что ответ 204 обязан быть без любых headers.

### Headers и тело не смешиваются

Content-Type не содержит сам body. Он только сообщает его формат.

~~~text
Content-Type: application/json
        ↓
объясняет формат
        ↓
body содержит JSON
~~~

Если в body лежит строка с JSON, но header говорит text/plain, договор становится противоречивым.

### Независимый пример

~~~text
Content-Type: image/png
~~~

Такой header сообщает формат изображения. Само изображение должно быть передано отдельно, в body.

### X-Request-ID

Некоторые приложения добавляют к response дополнительный заголовок с идентификатором обращения:

~~~text
X-Request-ID: req-101
~~~

`X-Request-ID` не является обязательным для каждого HTTP-ответа. Если приложение использует такой заголовок, его значение помогает найти запись об этом обращении в журнале сервера.

В нашей учебной модели имя `X-Request-ID` задано условием, а значение приходит в аргументе `request_id`. Мы не создаём этот идентификатор и не настраиваем журнал сервера.

В реальном HTTP регистр букв в названиях headers не важен. Но в этом упражнении мы возвращаем обычный словарь Python, где ключи различаются по регистру. Поэтому напишите ключ ровно так, как указано в условии.

### Типичная ошибка

~~~text
status: 200
Content-Type: application/json
body: Server is running
~~~

Header обещает JSON, а body содержит обычный текст. Клиент может попытаться разобрать строку как объект и получить ошибку.

### Где применяются другие headers

Кроме формата тела, заголовки могут передавать сведения о языке ответа или о проверке доступа. Сейчас они не нужны: мы разбираем только формат содержимого и один дополнительный идентификатор обращения.

### Связь с текущей практикой

Практика всегда переносит значение `request_id` в ключ `X-Request-ID`. В рамках этой модели `Content-Type` добавляется, когда body существует, в том числе если это пустой словарь `{}`. При `None` содержимого нет, поэтому для 204 этот ключ не добавляется.

## 07. Python-словарь ещё не является HTTP response

В предыдущих примерах мы использовали словари Python. Они удобны внутри программы, но сами по себе не пересылаются другому компьютеру. Сетевое сообщение содержит данные в согласованном формате.

Например, Python использует `True`, а JSON записывает то же логическое значение как `true`:

~~~text
значение Python:
{"available": True}

представление JSON:
{"available": true}
~~~

Преобразование значения программы в формат передачи данных называют сериализацией. Обратное преобразование полученных данных в значение программы называют разбором или десериализацией. Здесь важно не запоминать новые названия, а видеть границу: словарь живёт в памяти Python, а JSON-представление можно передать между системами.

Когда сервер отправляет JSON, он формирует его представление и помещает его в body ответа. Заголовок `Content-Type: application/json` сообщает получателю формат этого body. Сам заголовок не преобразует данные и не содержит их.

В рабочем сервере сериализацию может выполнять отдельная часть программы, которая связывает Python-код с HTTP-сообщением. Она берёт результат кода, представляет его в выбранном формате и помогает собрать ответ. Если сервер настроен на JSON, преобразование может происходить автоматически. Конкретный механизм зависит от используемого инструмента. В этой практике такого компонента нет.

### Независимый пример

Представьте программу учёта запасов. Внутри Python она хранит `{"available": True}`. Передача JSON требует формата `{"available": true}`. Клиент прочитает это значение только если сервер действительно отправил JSON-тело и сообщил его формат. Одной надписи `Content-Type` недостаточно, чтобы создать body.

### Как собрать модель

Status и headers задают служебную часть ответа. Значение приложения отдельно преобразуется в формат body. Затем эти части входят в одно сообщение:

~~~text
значение Python → JSON-представление → body

status + headers + body → HTTP response → client
~~~

В интерфейсе это разделение показано схемой: данные для body проходят сериализацию, а status и headers остаются отдельными частями response.

### Учебная модель в практике

Функция практики вернёт словарь Python с ключами `status`, `headers` и `body`. Это не реальный HTTP response и не отправка по сети. Такая модель позволяет проверить, что части ответа собраны согласованно, не запуская сервер.

В условии `None` означает, что body отсутствует. Пустой словарь `{}` остаётся существующим body. Это различие относится к модели упражнения: настоящий сервер не передаёт значение Python `None` клиенту как специальный признак отсутствия содержимого.

**Интерактив.** Если функция вернула Python-словарь с ключами `status`, `headers` и `body`, получил ли клиент HTTP response? Нет. Пока программа лишь вернула значение вызывающему коду. Чтобы возникло сетевое сообщение, его должен сформировать HTTP-инструмент или сервер.

### Связь с текущей практикой

Практика проверит только структуру словаря. Она не проверяет JSON-кодирование, работу сервера или отправку по сети. Content-Type добавляется по условию учебной модели, когда передано любое body, включая пустой словарь.

## 08. Как клиент читает response

Клиенту важно не начать разбирать данные, пока он не понял исход. Например, ответ 204 не содержит body, поэтому попытка прочитать из него JSON не имеет смысла.

Упрощённый порядок такой:

~~~text
получить response
    ↓
прочитать status
    ↓
выбрать реакцию: успех, ошибка или дополнительный шаг
    ↓
если body существует, посмотреть Content-Type
    ↓
разобрать body и обновить интерфейс
~~~

Последний шаг зависит от ситуации. При 204 клиент завершает обработку без разбора body. При 201 он может разобрать представление созданной задачи и показать её. При 404 он показывает ошибку, а не добавляет отсутствующую задачу в список.

Это не универсальный программный код. Это порядок принятия решения. Реальный клиент может использовать библиотеку, которая часть работы выполнит автоматически, но смысл status и body остаётся тем же.

### Интерактив. Выберите правильную реакцию

~~~text
status: 204
body отсутствует
~~~

Клиенту не нужно вызывать разборщик JSON. Он должен обработать успешное завершение без содержимого. Если клиент безусловно ожидает JSON от каждого ответа, сценарий 204 может завершиться ошибкой уже на стороне клиента.

### Связь с текущей практикой

Наша функция не выбирает реакцию клиента. Она получает готовые status и body и сохраняет их. Но понимание порядка объясняет, почему нельзя превратить `None` в `{}` или заменить status текстом из body.

## 09. Request и response образуют одну пару

Request и response нельзя проектировать в отрыве друг от друга.

~~~text
request:
method + path + headers + body

response:
status + headers + body
~~~

Клиент отправляет первую половину пары. Сервер возвращает вторую.

### Успешная пара

~~~text
REQUEST
POST /tasks
body: {"title": "Изучить HTTP", "priority": 4}

RESPONSE
201 Created
body: {"id": 7, "title": "Изучить HTTP", "priority": 4}
~~~

Путь данных:

1. клиент сформулировал создание;
2. сервер проверил request;
3. PlannerService создал Task;
4. storage сохранил состояние;
5. сервер вернул представление новой Task;
6. клиент обновил экран.

### Ошибочная пара

~~~text
REQUEST
GET /tasks/999

RESPONSE
404 Not Found
body: {"detail": "Task 999 not found"}
~~~

Здесь сервер не нашёл ресурс. Это не неожиданный сбой и не причина возвращать 500.

### Пара без body

~~~text
REQUEST
DELETE /tasks/7

RESPONSE
204 No Content
body отсутствует
~~~

Клиенту не нужна дополнительная структура, если договор говорит, что успешное удаление не возвращает содержимое.

### Типичная ошибка

Разработчик проверяет только наличие ключа id в body. Тогда:

- ошибка 404 может быть принята за пустой результат;
- response 204 вызовет ошибку разбора;
- серверный статус останется без внимания.

Правильный порядок начинается со status.

### Как это используют в работе

Такой порядок позволяет одной части клиентской программы обрабатывать ответы многих операций API. Детали body меняются, но общий ход похож: прочитать status, учесть headers, при наличии разобрать body и выбрать реакцию интерфейса.

## 10. Что мы будем делать в практике

Практика проверит одну изолированную функцию в редакторе. Она не подключается к сети, не запускает сервер и не создаёт реальные HTTP-объекты.

### Общий результат

Нужно представить response обычным словарём Python. В модели будут:

- status;
- headers;
- body.

Функция должна сохранить смысл готового результата, а не выполнять запрос заново.

### Что дано

Функция получает:

- status, то есть целое число HTTP-исхода;
- body, то есть словарь Python, который в этой модели представляет JSON-объект, или None;
- request_id, то есть идентификатор обращения.

Значения уже подготовлены автопроверкой. Пара status и body согласована заранее: не нужно выбирать status или проверять смысл операции.

### Что требуется понять

До редактора ответьте:

1. Какой header добавляется всегда?
2. Когда появляется Content-Type?
3. Почему None нельзя заменить пустым словарём?
4. Почему status и body возвращаются без изменения?
5. Почему функция не должна печатать результат?

### Как будет проверен результат

Автопроверка использует пять сценариев:

- успешный response 200 с JSON body;
- созданный ресурс: response 201 с JSON body;
- ошибка 404 с JSON body;
- успешный response 204 без body;
- пустой JSON-объект `{}` как существующий body.

Проверяется весь словарь. Будут замечены:

- пропуск X-Request-ID;
- ошибку в условии для Content-Type: в этой модели он нужен при `body = {}`, но пропускается при `body = None`;
- подмена None;
- изменение status или body;
- печать вместо возврата результата.

### Чего делать не нужно

Не нужно:

- запускать настоящий сервер;
- отправлять сообщения по сети;
- вызывать PlannerService;
- читать хранилище задач;
- настраивать автоматическую проверку входных данных;
- записывать ошибки в журнал сервера;
- превращать словарь Python в текст JSON вручную;
- угадывать status по тексту body.

Это отдельная проверка структуры response. Реальный сервер появится позже, когда request и response будут встроены в настоящий контракт.

### Как начать

Сначала создайте словарь `headers` и добавьте в него ключ `X-Request-ID` со значением `request_id`. Затем определите, передано ли body. При наличии содержимого добавьте `Content-Type`, после чего соберите status, headers и body в итоговый словарь.

Проверьте контраст:

~~~text
body = {"id": 1}
body = {}
body = None
~~~

В этой модели `None` означает, что body отсутствует. Словарь `{}` тоже является переданным body, хотя он пустой. Поэтому проверяйте наличие значения, а не то, пустой ли словарь.

### Доказательство результата

Функция готова, если:

- возвращает словарь;
- использует точные ключи status, headers и body;
- переносит request_id в X-Request-ID;
- добавляет Content-Type для любого существующего body, даже пустого словаря;
- сохраняет None;
- проходит 200, 201, 404, 204 и пустой JSON-объект.

После выполнения ученик сможет отличить результат операции от его представления и перейти к method.
