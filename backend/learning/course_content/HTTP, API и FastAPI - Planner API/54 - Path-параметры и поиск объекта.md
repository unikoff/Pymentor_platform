## 00. От всего списка к одной задаче

В предыдущем занятии у Planner API появился список задач. По адресу `GET /tasks` клиент получает всю коллекцию: одну, несколько или ни одной записи. Это уже полезно, но представьте обычный экран списка. Человек нажимает на одну строку и ожидает увидеть именно эту задачу, а не весь список целиком.

Для такого запроса адресу нужно указать, какой именно объект нас интересует. Например, `/tasks/4` указывает на задачу с идентификатором 4. Слово `id` здесь означает устойчивый номер записи. Адрес `/tasks/{task_id}` будет шаблоном маршрута, а `/tasks/4` будет конкретным запросом.

Сегодня разберём весь путь от адреса до найденной записи. Сначала FastAPI проверит, что значение в адресе можно представить как целое число. Затем обычная Python-функция попробует найти задачу. Эти две проверки отвечают на разные вопросы:

1. Можно ли прочитать значение как число?
2. Есть ли задача с таким числом среди данных?

Если разделять вопросы, клиент получит точную причину неудачи, а поиск можно будет проверить без запуска сервера.

> **Новые слова.** `collection` означает коллекцию, то есть набор записей. `item` означает один элемент этого набора. `path` означает путь в URL после домена и порта, например `/tasks/4`.

### Сначала предскажите

В списке есть задача с `id = 4`. Что должен показать запрос `GET /tasks/4`: весь список или только одну запись? А что должно произойти с запросом `GET /tasks/abc`, если идентификатор ожидается как число?

## 01. Два адреса, два масштаба

Маршрут `GET /tasks` обозначает коллекцию. Он отвечает на вопрос «какие задачи есть?». Маршрут `GET /tasks/4` обозначает один item. Он отвечает на вопрос «что известно о задаче с id 4?». Оба запроса читают данные, поэтому используют GET. Отличается путь и объект чтения.

Похожая пара есть у книжного каталога:

```text
GET /books       → коллекция книг
GET /books/17    → одна книга с id 17
```

Ресурс в API это объект, к которому обращается запрос, например отдельная книга. Такая форма адреса помогает клиенту попросить именно нужный ресурс. Без неё приложению пришлось бы отправлять весь каталог, а клиент искал бы запись у себя. Это лишняя передача данных и дублирование поиска в каждом клиенте.

В приложении маршрут обычно объявляют с переменной частью:

```text
/books/{book_id}
```

Фигурные скобки показывают место, значение которого меняется от запроса к запросу. В реальном запросе фигурных скобок нет. Клиент передаст, например, `/books/17`.

> **Небольшое уточнение.** Endpoint, или маршрут, это сочетание HTTP-метода, пути и функции приложения, которая обработает запрос. `GET /books/17` и `GET /books/18` используют один маршрут-шаблон, но передают ему разные значения.

### Соедините смысл и адрес

Сопоставьте адрес с тем, что он обозначает:

| Адрес | Масштаб запроса |
| --- | --- |
| `GET /books` | ? |
| `GET /books/17` | ? |

Подсказка: наличие номера в конце адреса сужает выбор до одной книги.

## 02. Значение из URL попадает в функцию

Переменную часть пути называют **path-параметром**. В маршруте `/books/{book_id}` параметр называется `book_id`. FastAPI передаёт значение из соответствующего фрагмента адреса в функцию Python.

Следующий фрагмент предполагает, что объект приложения уже создан, как в проекте из предыдущей работы.

```python
@app.get("/books/{book_id}")
def read_book(book_id: int):
    return {"requested_id": book_id}
```

В объявлении маршрута имя в фигурных скобках совпадает с именем аргумента функции. Поэтому запрос `GET /books/17` передаст в `book_id` значение `17`. Функция вернёт словарь, а FastAPI сформирует из него ответ.

В этом примере пока не ищем книгу. Он показывает только передачу значения из URL в Python. Маршрут задаёт место параметра, имя аргумента связывает его с функцией, а аннотация `: int` сообщает FastAPI ожидаемый тип.

### Соберите порядок

Что происходит после запроса к `/books/17`?

1. Функция получает значение аргумента `book_id`.
2. FastAPI находит значение в части URL, отмеченной `{book_id}`.
3. FastAPI проверяет и преобразует его согласно типу `int`.

Расставьте пункты в порядке выполнения.

### Что аннотация типа делает, а чего не делает

Аннотация `: int` помогает FastAPI разобрать входное значение и проверить его тип. В данном случае строку `"17"` из URL можно представить как целое число `17`. Если в адресе будет `abc`, преобразование не получится.

Но тип `int` не доказывает, что задача существует. Число `999` является корректным целым числом даже тогда, когда в списке нет задачи с таким id. Проверка формы значения и проверка наличия записи должны оставаться разными шагами.

## 03. Номер в адресе не является позицией в списке

У записи есть идентификатор, а у элемента списка есть позиция. Это связанные, но не одинаковые понятия.

```python
books = [
    {"id": 17, "title": "Python"},
    {"id": 4, "title": "HTTP"},
]
```

У первой записи `id` равен 17, но её позиция в списке равна 0. У второй записи `id` равен 4, а позиция равна 1. Если удалить первую запись, позиция второй станет 0, но её идентификатор останется 4.

Идентификатор отвечает на вопрос «какая это запись?». Позиция отвечает на вопрос «где она сейчас расположена в этом списке?». Позиция может меняться после добавления, удаления или сортировки. Идентификатор должен продолжать обозначать ту же запись.

Внутри одной коллекции идентификаторы должны быть уникальными. Если две задачи имеют одинаковый id, адрес /tasks/4 не объяснит, какую именно из них вернуть. Позже база данных сможет обеспечить уникальность такого поля автоматически.

Поэтому запрос `/books/4` означает «найди запись, у которой поле `id` равно 4», а не «возьми элемент с позицией 4». Чтобы найти запись в обычном списке, нужно сравнить её поле `id` с запрошенным значением.

> **Важно.** В небольшом учебном списке поиск может идти по элементам один за другим. В базе данных для такого обращения обычно используют индекс, то есть дополнительную структуру, которая помогает быстрее найти запись по значению поля и не просматривать всю таблицу. Внешний смысл не меняется: клиент всё так же спрашивает запись по её устойчивому id.

В нашем примере всего две книги, поэтому попытка взять элемент с позицией 4 завершится ошибкой: такой позиции нет. Если список станет длиннее, Python возьмёт пятую запись, которая всё равно не обязана иметь id 4.

### Найдите неверное предположение

Клиент попросил `/books/4`. Разработчик взял `books[4]`. Почему это не одно и то же? Вспомните, что индекс списка начинается с нуля и зависит от порядка элементов.

## 04. 422 и 404 отвечают на разные вопросы

Теперь сравним три запроса:

| Запрос | Что проверяется | Ожидаемый результат |
| --- | --- | --- |
| `GET /tasks/1`, задача с id 1 есть | Тип корректен, запись найдена | `200 OK` |
| `GET /tasks/999`, такой задачи нет | Тип корректен, записи нет | `404 Not Found` |
| `GET /tasks/abc` | Значение нельзя преобразовать в `int` | `422` |

Числовой статус ответа называют кодом состояния HTTP. `422` в ответе FastAPI означает, что значение запроса не прошло проверку ожидаемого типа. До функции, которая ищет задачу, выполнение в таком случае не доходит. Это не означает, что задача отсутствует. Приложение ещё не получило целочисленный id, с которым можно было бы выполнить поиск.

`404 Not Found` означает другое: маршрут и тип значения допустимы, но конкретного ресурса по этому адресу нет. `999` корректное число. Отсутствие задачи с таким номером обнаруживается только после поиска.

Успешный результат `200 OK` появляется, когда значение допустимо и запись нашлась. Здесь статус описывает результат HTTP-запроса, а не значение поля внутри задачи.

### Найдите причину сбоя

```text
GET /tasks/abc
→ приложение пытается найти задачу с id "abc"
→ задача не найдена
→ 404
```

Какая часть рассуждения неверна?

1. FastAPI не сможет преобразовать `abc` в `int`, поэтому до поиска дело не дойдёт.
2. Любое значение в адресе можно без проверки сравнить с целым id.
3. Правильный статус обязательно 404.

### Запомните границу

Ответьте своими словами: какой вопрос приложения приводит к 422, а какой приводит к 404? Если заменить один статус другим, клиент потеряет полезную информацию о том, что именно нужно исправить.

## 05. Поиск в списке остаётся обычной логикой Python

Получить число из URL ещё не значит получить сам объект. Приложению нужно пройти по записям, сравнить идентификатор и выбрать совпадение.

В независимом примере есть станции с короткими кодами:

```python
stations = [
    {"code": "N1", "name": "Северная"},
    {"code": "S2", "name": "Южная"},
]

requested_code = "S2"
selected_station = None

for station in stations:
    if station["code"] == requested_code:
        selected_station = station
        break
```

Цикл берёт по одной станции. Условие сравнивает код текущей записи с запрошенным кодом. При совпадении переменная `selected_station` получает запись, а `break` прекращает цикл: продолжать искать уже незачем.

Если ни одна запись не совпала, `selected_station` остаётся равной `None`. В Python `None` означает отсутствие значения. Здесь это понятный сигнал «совпадение не найдено», а не ошибка типа и не пустой список.

Такой последовательный поиск подходит маленькому списку. В худшем случае программа проверит каждую запись. Если записей стало во много раз больше, отдельный индекс или запрос к базе данных обычно ищет быстрее. Контракт поиска означает договор функции: какие значения она принимает и какой результат возвращает. Здесь на вход приходит критерий, на выходе найденный объект или явное отсутствие.

### Где заканчивается поиск?

Если запрошенный код не встретился ни в одной станции, чему равна переменная `selected_station`? Почему нельзя вернуть последнюю проверенную станцию как будто это совпадение?

## 06. Функция поиска не должна решать за HTTP

Поиск можно вынести в отдельную функцию. Такая функция получает список и нужный id, а затем возвращает найденную запись либо `None`. Она не знает, был ли вызван сервер, какой статус нужно отправить и как выглядит HTTP-ответ.

Это разделение ответственности важно. Одна часть программы отвечает на вопрос «какая запись соответствует этому id?». Другая часть, маршрут FastAPI, решает «какой HTTP-ответ отправить клиенту?». Если соединить всё в одной большой функции, поиск сложнее повторно использовать и отдельно проверять.

> **Чистая функция.** Она использует только переданные значения, не меняет входные данные и возвращает результат. В нашей лабораторной работе поиск читает список и id, не обращается к серверу, файлам или общим данным. Одинаковые входные значения дают одинаковый результат, поэтому такую функцию удобно проверять отдельно.

В будущем маршрут сможет использовать результат поиска так:

```text
найдена запись → вернуть данные клиенту
получено None → сообщить клиенту, что ресурс отсутствует
```

Это направление не меняется, когда вместо списка появится база данных. Способ получить запись может стать другим, но договор с вызывающим кодом остаётся ясным: найден объект или его нет.

### Почему вернуть копию

Словарь Python изменяемый. Если функция вернёт исходный словарь напрямую, вызывающий код сможет поменять его поле и тем самым изменить запись внутри исходного списка.

```python
profile = {"name": "Лена", "city": "Казань"}
view = profile.copy()

view["city"] = "Пермь"
print(profile["city"])  # Казань
```

После изменения `view` в исходном `profile` останется город «Казань». Метод `.copy()` создаёт новый словарь с теми же текущими полями. Поэтому вызывающий код получает отдельную запись для чтения или последующей работы.

> **Поверхностная копия.** Метод `.copy()` создаёт новый внешний словарь, но не копирует вложенные изменяемые значения. В текущей форме задачи поля `id`, `title`, `priority` и `is_done` содержат числа, строки и логические значения, поэтому отдельной копии словаря достаточно. Если внутри появится вложенный список или словарь, он останется общим для исходной записи и копии.

Функция поиска не должна менять входной список. Она только читает его и возвращает результат. Проверка должна подтвердить не только равенство полей, но и то, что результат не является тем же словарём из списка. Иначе функция могла бы вернуть исходную запись, а последующее изменение результата затронуло бы данные приложения.

### Проверьте понимание

Что произойдёт с исходной записью, если поменять поле в отдельном словаре, созданном через `.copy()`? А что изменилось бы, если бы поле содержало вложенный список? Объясните разницу между внешним словарём и вложенным объектом.

## 07. Складываем путь данных и проверяем типичные ошибки

Один запрос проходит несколько последовательных проверок. Их удобно представлять как маленький маршрут внутри приложения:

```text
URL: /tasks/4
  ↓
FastAPI берёт значение из {task_id} и проверяет int
  ↓
Python-функция ищет запись с таким id
  ↓
найдена копия записи или None
  ↓
маршрут возвращает данные или ответ 404
```

Если на шаге преобразования встретился текст `abc`, поиск не начинается и FastAPI сообщает о 422. Если преобразование прошло, но id отсутствует, функция возвращает `None`, а маршрут отвечает 404. Важная мысль: поиск не обязан знать про HTTP, а маршрут не должен придумывать заново, как сравнивать id.

Частые ошибки возникают, когда эти этапы смешивают:

- **Любое отсутствие называют 422.** Но целое число 999 имеет правильный тип. Если задачи с ним нет, это 404.
- **Любой неудачный поиск называют 404.** Строка `abc` ещё не стала id, поэтому сначала возникает ошибка проверки типа.
- **Считают id индексом.** Удаление или сортировка меняет позицию, но не идентификатор записи.
- **Возвращают исходный словарь.** Тогда изменение результата может задеть исходные данные. Копия отделяет внешний словарь результата.
- **Помещают HTTP-логику в помощник поиска.** Эта функция должна работать со списком Python. Решение о статусе принимает маршрут.
- **Проверяют только найденную запись.** Пустой список и неизвестный корректный id тоже должны иметь определённый результат.

В рабочем API сначала проверьте форму значения, затем существование ресурса. Такая последовательность позволяет API сообщать клиенту точную причину и не смешивать транспортный слой с обычным поиском.

## 08. Что мы будем делать в практике

Практика проверит самую важную Python-часть этого пути отдельно от сервера. Автоматическая проверка вызовет функцию `solve(tasks, task_id)` со списком словарей и целым числом, которое уже прошло границу URL и FastAPI.

Ваша функция должна пройти по списку, найти запись с совпадающим `id`, вернуть её отдельную копию, а при отсутствии совпадения вернуть `None`. Проверка пройдёт для первого элемента, элемента в середине, неизвестного id и пустого списка. В найденных случаях она дополнительно убедится, что возвращён отдельный словарь, а не исходная запись, и что аргументы не изменились. Для решения не нужны FastAPI или запущенный сервер.

Это ограничение сделано намеренно. Практика здесь не создаёт маршрут и не отправляет HTTP-статусы. Она доказывает, что правило поиска работает само по себе. Затем эту логику можно будет подключить к маршруту: найденная запись станет успешным ответом, а отсутствие записи станет основанием для 404. Проверка преобразования текста вроде `abc` в число остаётся ответственностью FastAPI.

| Что проверяем | Зачем |
| --- | --- |
| Совпадение поля `id` | Адрес указывает на идентификатор, а не на позицию списка |
| Возврат найденной записи | Вызывающему коду нужен один конкретный объект |
| Отдельная копия словаря | Изменение результата не должно менять исходную запись; проверяется и отличие объекта по идентичности |
| `None`, если записи нет | Маршрут сможет отличить отсутствие от успешного результата |
| Пустой список и неизменность входа | Отсутствие элементов обрабатывается явно, а список не меняется ни в одном сценарии |
| Результат возвращается, а не печатается | Вызывающий код должен получить значение функции, а не текст в консоли |

Результат практики будет небольшим, но важным контрактом для будущей логики чтения, изменения и удаления одной задачи. Пока мы закрепляем только поиск. Логика обработки HTTP-запроса остаётся за пределами упражнения.
