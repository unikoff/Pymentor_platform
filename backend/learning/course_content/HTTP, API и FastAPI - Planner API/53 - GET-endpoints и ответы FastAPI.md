## 00. От проверки запуска к первым данным

В предыдущем занятии мы запустили FastAPI, проверили `GET /health` и увидели ответ через браузер и Swagger UI. Сервер уже умеет принимать HTTP-запросы. Пока, однако, он сообщает только короткий статус. Теперь добавим две полезные операции чтения: одна покажет задачи, другая кратко подсчитает их состояние.

Мы продолжаем тот же каталог `studyhub-api` и существующее приложение. Список задач пока будет обычным списком Python в памяти работающего процесса. Это временная модель. Она нужна, чтобы сначала понять чтение данных через API, не отвлекаясь на базу, формы ввода и сохранение.

На протяжении главы слово `endpoint` означает доступную через HTTP операцию, которую задают методом и путём и связывают с функцией Python. Например, `GET /tasks` означает запрос чтения по адресу `/tasks`. Слово `response` означает ответ сервера на этот запрос.

```text
уже есть:  GET /health  → короткий ответ о работе приложения
добавим:  GET /tasks   → текущий список задач
добавим:  GET /stats   → сводка, посчитанная по списку
```

У этого небольшого расширения есть важная граница: новые операции только читают текущее состояние. Они не добавляют, не редактируют и не удаляют задачу. Входные данные от клиента тоже пока не нужны.

### Сначала предскажите

Если запрос `GET /tasks` отправить дважды подряд, должен ли второй ответ сам по себе содержать новую задачу? Объясните, откуда такая задача могла бы появиться.

## 01. GET читает состояние

Метод HTTP сообщает серверу намерение клиента. `GET` используют, когда клиент просит представить текущие данные: например, список задач или короткую сводку. В этой главе GET не должен менять список задач.

Это свойство называют безопасностью метода: клиент просит прочитать данные, а не изменить их. Например, открытие списка в браузере не должно случайно создать задачу. Сервер всё ещё может записать технический журнал о запросе, но это не считается изменением данных, ради которого клиент вызвал GET.

Сравните два намерения:

| Запрос | Что просит клиент | Меняется список задач? |
| --- | --- | --- |
| `GET /tasks` | показать текущие задачи | нет |
| `GET /stats` | показать подсчёт по текущим задачам | нет |

Обе операции возвращают данные. Их путь различается, поэтому клиент заранее понимает, какой вид ответа запросить. Позже появятся методы, которые действительно создают или изменяют задачу. Сейчас мы не смешиваем эти действия с чтением.

## 02. Где живёт временный список

Приложение из прошлого занятия состоит из Python-кода и объекта `app`. Добавим рядом со способом создания приложения список задач. Пока это обычный список словарей, как в предыдущих упражнениях по Python.

```python
notices = [
    {"text": "Проверить расписание", "active": True},
    {"text": "Обновить страницу", "active": False},
]
```

Список `notices` существует в оперативной памяти компьютера, пока работает процесс Python. Процесс здесь означает запущенную программу. Если приложение остановить, а затем запустить снова, Python выполнит файл заново и создаст список из начальных значений.

Это не база данных и не постоянное хранилище. Если позднее приложение научится добавлять задачу только в этот список, новое значение тоже исчезнет после перезапуска. В текущей практике мы не добавляем задачу через API, а используем заранее записанные примеры для предсказуемой проверки чтения.

Когда в прошлом занятии был включён режим `--reload`, изменение файла запускало приложение заново. Поэтому при проверке начальных данных редактирование файла возвращает процесс к значениям, записанным в коде. Это удобный учебный эффект, но не способ хранения данных.

## 03. Python-значение становится JSON-ответом

Функция FastAPI возвращает значение Python. FastAPI формирует из него HTTP-ответ и представляет совместимые данные в формате JSON. Это преобразование делает ответ пригодным для браузера, Postman и других клиентов.

Для нас особенно важны две пары:

| Python | JSON | Как читать |
| --- | --- | --- |
| словарь (`dict`) | объект `{...}` | именованные поля и значения |
| список (`list`) | массив `[...]` | упорядоченный набор элементов |

Логические значения тоже записываются по-разному: Python использует `True` и `False`, JSON использует `true` и `false`. Python-значение `None` становится JSON-значением `null`. FastAPI выполняет преобразование сам. Функция `json.dumps` вручную превращает значение в строку JSON. В маршруте FastAPI обычно возвращают исходный список или словарь, чтобы сохранить их структуру как массив или объект.

Например, независимая функция может вернуть:

```python
def read_notices():
    return [{"text": "Проверить расписание", "active": True}]
```

Клиент получит массив JSON:

```json
[{"text": "Проверить расписание", "active": true}]
```

Скобки важны. Список превращается в JSON-массив, даже если в нём пока нет элементов: пустой список `[]` остаётся массивом. Если вместо списка превратить данные в строку через `str(...)`, клиент получит текст, а не структурированный массив.

У успешного GET FastAPI по умолчанию возвращает HTTP-статус `200 OK`. Заголовок `Content-Type: application/json` сообщает клиенту, что тело ответа записано как JSON. HTTP-статус и поля внутри JSON являются разными частями сообщения.

### Сопоставьте форму

Соедините значение Python с тем, что увидит клиент:

| Значение | Представление JSON |
| --- | --- |
| `{"active": True}` | ? |
| `[1, 2]` | ? |
| `[]` | ? |

Подсказка: фигурные скобки обозначают объект, квадратные скобки обозначают массив, а `True` меняет написание на `true`.

## 04. GET /tasks возвращает целую коллекцию

`GET /tasks` будет возвращать весь текущий список. Здесь `tasks` это имя списка в Python и понятная часть адреса API. Функция маршрута возвращает список; FastAPI преобразует его в JSON-массив. У каждой записи есть согласованный набор полей:

| Поле | Тип значения | Назначение |
| --- | --- | --- |
| `id` | целое число (`int`) | различает задачи |
| `title` | текст (`str`) | содержит название |
| `priority` | целое число (`int`) | задаёт важность |
| `is_done` | логическое значение (`bool`) | показывает, завершена ли задача |

Тип важен не меньше имени. Например, `is_done` хранит именно `true` или `false`, а не строки `"да"` и `"нет"`. Тогда код может однозначно проверить состояние задачи.

Форма ответа должна оставаться одинаковой при любом количестве задач:

```json
[
  {"id": 1, "title": "Повторить HTTP", "priority": 4, "is_done": false},
  {"id": 2, "title": "Запустить FastAPI", "priority": 5, "is_done": true}
]
```

Если список пуст, ответ всё равно имеет форму массива:

```json
[]
```

Пустой список не означает, что адрес неверен. Маршрут найден, запрос выполнен, просто элементов пока нет. Поэтому успешное чтение пустой коллекции обычно возвращает `200 OK` и `[]`, а не текст «задач нет» и не другой тип данных.

Это стабильный контракт: клиенту не приходится угадывать, придёт ли массив, строка или объект в зависимости от количества задач. Тело ответа содержит данные. Статус `200` отдельно сообщает, что запрос обработан успешно.

## 05. GET /stats считает сводку из тех же задач

Второй маршрут не возвращает сами задачи. Он сообщает, сколько всего задач и сколько из них завершено или ещё открыто. Названия полей сводки будут `total`, `open` и `done`:

- `total` это общее количество задач;
- `open` это количество задач с `is_done == False`;
- `done` это количество задач с `is_done == True`.

Для списка из двух задач, где одна завершена, а другая ещё открыта, ответ выглядит так:

```json
{"total": 2, "open": 1, "done": 1}
```

Это JSON-объект с именованными числами. Если список пуст, форма не меняется: все три значения равны нулю.

Сводка должна отражать сам список, а не отдельные числа, записанные заранее. Иначе после изменения исходных данных `/tasks` покажет новое состояние, а `/stats` начнёт сообщать старые цифры. Источник истины здесь один: список задач. На каждом запросе сводку можно вычислить по его текущим элементам.

Чтобы получить такую сводку, программе нужно пройти по списку. Для каждого элемента она проверяет одно и то же поле состояния и относит запись ровно к одной группе. Такой повторный проход по элементам называется циклом. Это обычный инструмент Python, а не особенность FastAPI.

На знакомом примере отметок можно описать ход вычисления так:

```text
начать оба счётчика с нуля
для каждой записи:
  если отметка завершения есть → увеличить счётчик завершённых
  иначе → увеличить счётчик открытых
общее количество взять из длины списка
```

В нашем приложении состояние записано в `is_done`. На практике вы примените эту логику к задачам и вернёте получившиеся числа как JSON-объект. Важно пересчитывать значения по текущему списку при каждом запросе, а не держать рядом отдельные числа, которые легко забыть обновить.

Для двоичного признака `is_done` полезно проверить равенство `total = open + done`. Если оно не выполняется, часть записей не попала в подсчёт или была учтена дважды.

## 06. Проверяем один ответ разными клиентами

Браузер, Swagger UI и Postman выступают клиентами. Они отправляют HTTP-запрос к одному и тому же запущенному FastAPI-приложению. Различается интерфейс отправки, но не маршрут и не ожидаемое тело ответа.

В браузере удобно быстро открыть `GET /tasks` или `GET /stats`. В Swagger UI можно увидеть зарегистрированные операции, выполнить запрос и отдельно проверить статус и тело. В Postman можно сохранить два новых запроса к локальному адресу. Укажите для них локальную основу `http://127.0.0.1:8000`, затем используйте пути `/tasks` и `/stats`.

Ранее сохранённые запросы Postman направлены на Echo и используют пути `/get` и `/post`. Замена одного базового адреса не превращает их в запросы к Planner: путь и ожидания тоже должны соответствовать новой операции. Сохраните исходные учебные запросы Echo, а для локального Planner добавьте отдельные запросы.

Для каждого локального запроса проверьте три наблюдения:

1. HTTP-статус равен `200`.
2. `Content-Type` сообщает `application/json`.
3. Тело соответствует своей форме: список для `/tasks`, объект со счётчиками для `/stats`.

Если запрос к серверу вообще не проходит, сначала убедитесь, что Uvicorn запущен. Если сервер ответил, но содержимое не то, сравните тело ответа с текущим списком. Не делайте вывод о сохранении данных только по успешному статусу.

## 07. Что мы будем делать в практике

Мы продолжим существующий `studyhub-api`, сохраним `GET /health` и добавим один временный список задач. Затем создадим два маршрута чтения: один вернёт список, другой покажет вычисленную по нему сводку. Так мы увидим, как разные ответы могут опираться на один источник данных.

После запуска сервера проверим оба ответа через Swagger UI и Postman. Затем временно изменим исходный список и заранее предскажем, как это повлияет на ответы. Отдельно посмотрим на пустую коллекцию и в конце вернём начальные данные.

Практика не добавляет создание задач, поиск одной задачи, параметры адреса, проверку входа, базу данных или отдельный слой хранения. Её результатом будет небольшой API для чтения, в котором два маршрута используют один источник данных и не меняют его по запросу GET. Успех проверяется не только запуском сервера: ответы должны сохранять правильную форму и согласовываться с текущим содержимым списка.

### Карта результата

```text
один список в памяти
  ├── GET /tasks → JSON-массив задач
  └── GET /stats → JSON-объект со сводкой по этому списку
```
