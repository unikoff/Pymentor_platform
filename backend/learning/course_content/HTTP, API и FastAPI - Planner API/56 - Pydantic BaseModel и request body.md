## 00. От чтения к отправке данных

В прошлом занятии мы написали и проверили в интерпретаторе функцию, которая отбирает и упорядочивает задачи. Она ещё не была частью маршрута `GET /tasks`. Теперь перейдём от чтения к другой стороне обмена: клиент передаёт серверу данные новой задачи.

Представьте, что вы заполняете короткую карточку заказа. Вы вписываете название и количество, а сервер должен понять, что именно ему передали. В HTTP эти данные обычно кладут в **тело запроса**, или `request body`. Тело это часть запроса, в которой клиент передаёт содержимое, а не адрес и не заголовки.
Например, клиент отправляет запрос:

```http
POST /tasks
Content-Type: application/json
```

```json
{
  "title": "Повторить HTTP",
  "priority": 4
}
```

Заголовок `Content-Type` сообщает формат тела. Здесь `application/json` означает, что дальше идёт JSON. Сам JSON выглядит знакомо: это объект с названием и приоритетом. Но клиент может забыть `priority`, отправить вместо числа слово или передать тело совсем другой формы. Серверу нужно решить, готов ли он передать данные своей функции маршрута.

**Новые слова.** `schema`, или схема, описывает ожидаемую форму данных: имена полей и их типы. `API-контрактом` называют договор клиента и сервера о принимаемых и возвращаемых данных. `Pydantic` это Python-библиотека, которая строит объекты и проверяет их по схеме. `BaseModel` это базовый класс Pydantic, от которого наследуется наша модель.

### Предскажите

Если в примере убрать `priority`, сможет ли функция маршрута безопасно прочитать значение приоритета? Запишите, на каком этапе лучше заметить проблему: внутри прикладной функции или до её запуска.

## 01. Почему одного словаря мало

В Python JSON-объект можно представить обычным словарём:

```python
data = {
    "title": "Повторить HTTP",
    "priority": 4,
}
```

Словарь удобен, но сам по себе не обещает, что в нём есть нужные ключи и что значения имеют нужный тип. Если `priority` отсутствует, выражение `data["priority"]` вызовет `KeyError`, то есть ошибку обращения к отсутствующему ключу, уже внутри функции. Если же мы принимаем словарь и вручную проверяем каждое поле, такую проверку приходится проектировать и поддерживать самим.

Это похоже на передачу сотруднику коробки без списка содержимого. Он может начать работу, а затем обнаружить, что нужной детали нет. Схема играет роль списка: до начала работы она позволяет описать, что должно приехать.

Проверим форму данных на двух примерах:

```json
{"title": "Повторить HTTP", "priority": 4}
```

```json
{"title": "Повторить HTTP"}
```

Первый объект содержит оба поля. Во втором нет `priority`. Если объявить его обязательным в схеме, сервер может сообщить об ошибке до вызова функции маршрута.

Pydantic связывает объявленные поля с реальными входными данными. FastAPI использует эту модель, чтобы понять, что прочитать из тела запроса, проверить данные, подготовить объект для Python-кода и показать ожидаемую форму в автоматической документации API.

**Важно.** Тип `int` говорит, что после разбора нужно получить целое число. Он сам по себе не задаёт допустимый диапазон. Значения `0` или `900` всё ещё являются целыми числами. Ограничения длины и диапазона мы добавим в следующем занятии, чтобы разделить проверку типа и правила нашего продукта.

### Что выберет схема?

Какой из вариантов уже позволяет обратиться к обоим полям?

1. `{"title": "Повторить HTTP", "priority": 4}`
2. `{"title": "Повторить HTTP"}`

Вспомните договор: если поле обязательное и не имеет значения по умолчанию, оно должно прийти в запросе.

## 02. Описываем вход через BaseModel

В Pydantic описание данных обычно делают классом, который наследуется от `BaseModel`. Такой класс называют моделью. Он перечисляет поля, которые код ожидает получить, и тип каждого поля. Класс назовём `TaskCreate`: слово `Create` означает «создать». Эта модель описывает сведения, которые клиент присылает для создания задачи, а не всю сохранённую задачу.

```python
from pydantic import BaseModel


class TaskCreate(BaseModel):
    title: str
    priority: int
```

Читаем модель сверху вниз:

- `TaskCreate` это имя нового класса. Оно подсказывает, что модель описывает данные для создания задачи.
- `BaseModel` даёт классу возможности Pydantic: построить объект по входным значениям и проверить их.
- `title: str` означает, что поле `title` должно быть строкой.
- `priority: int` означает, что поле `priority` должно быть целым числом после разбора.

Оба поля обязательны. У них нет значений по умолчанию после `=`, поэтому клиент должен прислать их. В Python эта запись справа от двоеточия называется аннотацией типа. Здесь она одновременно помогает редактору и участвует в описании полей модели.

**Обязательное поле не равно полю с идеальным значением.** В этой модели `title: str` допускает пустую строку: пустая строка всё ещё строка. Чтобы требовать хотя бы один символ, понадобилось бы отдельное ограничение. Пока мы его не добавляем.

Для `int` тоже важно не обещать слишком строгого поведения. Pydantic обычно умеет привести строку с числом, например `"4"`, к целому `4`. Строку `"высокий"` так преобразовать нельзя, поэтому она не проходит проверку. Диапазон допустимого приоритета мы здесь не задаём.

### Что напечатает этот код?

```python
task = TaskCreate(title="Повторить HTTP", priority="4")
print(task.priority, type(task.priority).__name__)
```

До раскрытия ответа предскажите тип `task.priority`. Он создаётся по входной записи или по модели после разбора?

Имена `id` и `is_done` в `TaskCreate` не включены. При создании клиент сообщает сведения о самой новой задаче. Идентификатор и начальное состояние назначает сервер, потому что сервер отвечает за идентичность и жизненный цикл записей. Не добавляйте эти поля в запрос только потому, что они есть у сохранённой задачи.

Здесь мы перечислили ожидаемые поля, но пока не задаём отдельную политику для посторонних ключей. Не следует делать вывод, что каждый неизвестный ключ автоматически даст ошибку: такое поведение настраивается отдельно и будет проверено при разделении схем в следующих занятиях.

## 03. FastAPI связывает модель с телом запроса

Одна модель сама по себе ничего не принимает из сети. FastAPI нужно сообщить, какой маршрут использует эти данные. Для этого параметр функции объявляют с типом `TaskCreate`:

Перед примером разберём две детали. Если маршрут только возвращает проверенные входные поля и не создаёт ресурс, успешный ответ имеет обычный статус `200`. `model_dump()` в используемой здесь версии Pydantic 2 превращает поля проверенной модели в словарь Python. Он не сохраняет задачу.
Имя параметра `payload` выберем сами. Здесь оно означает проверенные данные запроса, уже собранные в объект модели.

Ниже фрагмент для уже созданного приложения: считаем, что объект `app` объявлен раньше, а класс `TaskCreate` расположен выше в том же файле.

```python
@app.post("/tasks")
def create_task(payload: TaskCreate):
    return payload.model_dump()
```

FastAPI видит Pydantic-модель в параметре `payload` и понимает, что её нужно построить из JSON-тела. Это и называется **связать тело с параметром**. Внутри функции `payload` уже объект `TaskCreate`, поэтому поля читаются через точку: `payload.title` и `payload.priority`.

Параметр, аннотированный простой величиной вроде `int` или `str`, обычно FastAPI рассматривает иначе. В зависимости от объявления это может быть значение из адреса или строки запроса. Класс Pydantic явно говорит: «здесь ожидается структурированный объект из тела».

По объявленной модели FastAPI также формирует описание входа для OpenAPI. OpenAPI это машиночитаемое описание путей, параметров и форм данных API. Swagger UI показывает это описание как страницу, где можно посмотреть маршрут и отправить пробный запрос. Значит, одна модель помогает и серверному коду, и клиенту, который изучает документацию.

### Соберите путь данных

Расположите события в правильном порядке:

1. Функция маршрута получает объект `TaskCreate`.
2. Клиент отправляет JSON в теле запроса.
3. FastAPI читает тело и передаёт данные на проверку модели.
4. Модель проверяет нужные поля и готовит значения Python.

Главное здесь не запомнить названия классов, а понять границу: функция маршрута не должна первой узнавать, что обязательного поля не оказалось.

## 04. Проверка до входа в функцию

Когда в запросе есть нужные поля и их можно разобрать по типам, Pydantic создаёт объект модели. Тогда FastAPI вызывает функцию маршрута. Если обязательного поля нет или значение нельзя привести к нужному типу, FastAPI возвращает стандартную ошибку запроса с кодом `422`.

Код `422` в этом сценарии говорит: сервер получил запрос, но его содержимое не соответствует ожидаемой форме. Это ошибка входных данных клиента. В частности, она отличается от ошибки `500`, которая означает сбой на стороне сервера.

Рассмотрим два неверных тела. Первое пропускает обязательное поле. Второе содержит строку, которую нельзя разобрать как целое число:

```json
{
  "title": "Повторить HTTP"
}
```

```json
{
  "title": "Повторить HTTP",
  "priority": "высокий"
}
```

В обоих случаях проверка останавливает запрос до тела `create_task`. Функция маршрута не запускается, поэтому её прикладная логика не успевает работать с неподходящими значениями. Это полезная граница: вместо случайного `KeyError` мы получаем объяснение, какое поле не прошло проверку.

FastAPI сначала читает JSON, затем Pydantic проверяет поля и готовит объект. При успехе вызывается функция маршрута и возвращает временный ответ. При ошибке клиент получает `422` до вызова функции. Ни одна из этих операций пока не записывает задачу в хранилище.

### Верно или неверно?

«Если в запросе не хватает `priority`, функция маршрута всё равно запускается, но получает пустое значение». Обоснуйте ответ по пути данных, а не по внешнему виду Swagger.

## 05. Превращаем модель в словарь и различаем ответы

Функция маршрута может работать с объектом модели. Иногда следующему слою приложения удобнее получить обычный словарь. В проекте используется Pydantic 2. В этой версии для превращения полей модели в словарь есть метод `model_dump()`:

```python
payload = TaskCreate(title="Повторить HTTP", priority=4)
data = payload.model_dump()

print(data)
# {'title': 'Повторить HTTP', 'priority': 4}
```

`model_dump()` возвращает Python-словарь, а не текст JSON и не файл на диске. FastAPI умеет сам превратить возвращённый словарь в JSON-ответ. Позже приложение сможет дополнить входные данные серверными полями, присвоить задаче `id` и передать её в хранилище. Сейчас этого шага нет. `model_dump()` не сохраняет данные и не создаёт запись.

Теперь отделим код ответа от тела ответа:

- `200 OK` сообщает, что временный маршрут успешно обработал запрос и вернул проверенные поля. В этой практике запись не создаётся.
- `201 Created` уместен после того, как сервер действительно создал новый ресурс.
- `422 Unprocessable Entity` сообщает, что данные запроса не прошли проверку.

Код `201` не выбирается автоматически из-за `POST`. В этой контрольной точке маршрут только принимает и возвращает проверенный объект, поэтому отвечает `200`. Позже, когда приложение добавит полную задачу с серверным `id` в хранилище, POST сможет честно вернуть `201`.

### Проверьте различие

Если запрос получил `201`, что ещё нужно проверить, прежде чем утверждать, что задача переживёт перезапуск сервера? Подсказка: код ответа ничего не записывает сам по себе.

## 06. Где заканчиваются возможности Pydantic

Pydantic отвечает на вопросы о форме входа: есть ли требуемое поле, похоже ли значение на нужный тип, можно ли построить объект модели. Это снимает с каждой функции маршрута повторяющуюся проверку структуры.

Но Pydantic не знает автоматически правил именно нашего приложения. Он не решает, какой приоритет считается допустимым по правилам продукта, может ли конкретный пользователь создать задачу или существует ли такая запись в базе. Тип `int` не заменяет диапазон, проверка модели не заменяет авторизацию, а успешное построение объекта не означает, что данные сохранены.

В проектах схемы входа помогают нескольким участникам работать по одному договору. Клиент формирует ожидаемое тело, сервер проверяет его, документация описывает форму, а код получает атрибуты с понятными типами. По мере роста проекта обычно разделяют модели для создания, изменения и ответа. Причина проста: для каждого направления нужны разные поля и разные права владения данными.

В этом проекте мы пока делаем только первую модель `TaskCreate` и подключаем её к одному `POST /tasks`. Мы не задаём дополнительные ограничения, не создаём собственные проверки, отдельную модель ответа или запись в хранилище. Это отдельные шаги, и у каждого будет своя задача.

## 07. Что мы будем делать в практике

К концу практики у маршрута `POST /tasks` появится понятная граница входа. Клиент передаст JSON с `title` и `priority`. Модель `TaskCreate` станет единственным местом, где мы объявим обязательность этих полей и их простые типы. FastAPI передаст модели только запрос, который удалось разобрать.

Работа пойдёт от формы к поведению. Сначала появится модель без `id`, `is_done` и дополнительных ограничений. Затем маршрут свяжет модель с телом запроса и вернёт временное представление данных с кодом `200`. После этого мы отправим корректное тело и два некорректных: одно без `priority`, другое с неразбираемым значением приоритета. Временная отметка в консоли поможет увидеть, что при ошибке функция маршрута не запускалась; после проверки отладочную строку нужно удалить.

Роли разделены так: клиент сообщает только поля новой задачи, Pydantic проверяет вход и строит объект, FastAPI вызывает функцию маршрута после проверки, а функция возвращает учебный ответ. Постоянного хранилища здесь ещё нет. Поэтому доказательство результата состоит не в том, что запись сохранилась, а в наблюдаемой разнице между принятым телом и отказом `422` до запуска функции.

Начните с вопроса: какие сведения клиент вправе сообщить о новой задаче, а какие сервер должен назначить сам? Теория уже дала нужные опоры: обязательные поля, типы, модель `BaseModel`, привязка к телу, преобразование через `model_dump()` и порядок проверки. Практика закрепит только этот входной контракт. Ограничения длины и диапазона, постоянный `id` и реальная запись появятся позже.
