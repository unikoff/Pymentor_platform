## 00. От границы клиента и сервера к самому сообщению

В прошлом занятии разбирали, чем отличаются роли клиента и сервера и кто отвечает за правила и состояние нового API. На общей схеме `request` появился как сообщение между ними, но его устройство мы ещё не разбирали. Теперь выясним, какие сведения клиент передаёт серверу и как они помогают понять обращение.

Представьте пункт выдачи заказов. Посетитель не заходит на склад и не вызывает кладовщика по имени. Он передаёт бланк. В бланке указано, куда обратиться, что нужно сделать, какие есть служебные отметки и какие данные приложены. Сотрудник склада читает этот бланк и уже внутри выполняет свою работу.

HTTP request выполняет похожую роль. Это сообщение от клиента к серверу.

HTTP расшифровывается как Hypertext Transfer Protocol, протокол передачи гипертекста. Он задаёт правила обмена сообщениями. Request означает запрос клиента к серверу, response означает ответ сервера клиенту.

Важно различать два уровня:

~~~text
намерение пользователя:
создать задачу

внешнее сообщение:
request

внутренняя работа сервера:
PlannerService и хранилище
~~~

Request не является вызовом метода PlannerService. Клиент не отправляет серверу имя Python-функции и не получает доступ к его объектам. Он передаёт сообщение по внешнему договору.

### Что уже известно

Мы уже знаем:

- клиент начинает обращение;
- сервер принимает его;
- сервер владеет правилами и источником истины;
- Persistent Planner остаётся внутренним ядром;
- request и response связывают две стороны.

### Что добавляется сейчас

Для учебной модели мы выделим в request четыре смысловые части:

- адрес назначения;
- method, то есть метод HTTP, выражающий действие;
- headers, то есть заголовки со служебными сведениями;
- body, то есть тело сообщения с дополнительными данными, если они нужны.

Это разбор ролей, а не полный формат HTTP-сообщения, которое передаётся по сети.

Эти части отвечают на разные вопросы:

~~~text
куда обратиться?
что попросить?
как описать сообщение?
какие данные передать?
~~~

### Чего пока не будет

Сейчас не нужно связывать адреса с обработчиками на сервере, запускать сервер или отправлять настоящее сообщение по сети. Сначала мы соберём модель request в Python и разберём роль каждой части отдельно от подключения.

**Остановитесь на минуту.** Если клиент отправил строку «создай задачу», это ещё не значит, что сервер получил полноценный request. Нужно определить адрес, method и, при необходимости, данные задачи.

## 01. Request является сообщением, а не вызовом функции

В одном Python-процессе можно обратиться к объекту напрямую:

~~~python
service.add_task("Изучить HTTP")
~~~

Здесь Python находит объект service в памяти и вызывает его метод. Никакой внешней границы нет.

В клиент-серверной модели клиент не видит этот объект:

~~~text
клиент
  ↓ request
сервер
  ↓ внутренняя работа
PlannerService
  ↓
хранилище
  ↑
сервер
  ↑ response
клиент
~~~

Сервер может внутри вызвать PlannerService, но клиент об этом не знает. Для клиента существует только внешний договор сообщения и результат.

### Почему это разделение важно

Если внешний клиент зависит от имени Python-метода, внутренняя замена становится опасной. Переименовали add_task в create_task, и все внешние клиенты сломались бы, хотя смысл операции не изменился.

Внешний договор должен описывать смысл:

~~~text
«создать задачу»
~~~

а не деталь реализации:

~~~text
«вызвать метод add_task объекта PlannerService»
~~~

Так можно:

- заменить JSON-хранилище на базу данных;
- изменить внутреннюю структуру service;
- добавить другой клиент;
- оставить внешний способ обращения прежним.

### Независимый пример

Рассмотрим не задачи, а доставку книги.

~~~text
внутри программы:
library.reserve(book_id)

между клиентом и сервером:
клиент → request: «забронировать книгу»
сервер → response: «книга забронирована»
~~~

Клиенту не нужно знать, хранит ли библиотека книги в словаре, файле или базе данных. Он знает только смысл операции и правила сообщения.

### Что входит в обязанность клиента

Клиент:

1. получает намерение пользователя;
2. выбирает подходящий адрес;
3. выбирает method;
4. добавляет необходимые headers;
5. прикладывает body, если операция передаёт данные;
6. отправляет request;
7. ждёт response.

Клиент может делать удобные проверки формы. Например, подсветить пустой заголовок до отправки. Но это не превращает клиентскую проверку в окончательное правило сервера.

### Что входит в обязанность сервера

Сервер:

1. принимает request;
2. понимает его части;
3. проверяет допустимость данных;
4. выбирает прикладную операцию;
5. обращается к Task, PlannerService и хранилищу;
6. формирует response.

В этом занятии мы не реализуем сервер. Нам нужно научиться читать и собирать его входное сообщение.

**Проверьте себя.** Если request содержит method и path, это ещё не означает, что сервер уже выполнил операцию. Сначала сообщение должно попасть на сервер, пройти проверку и быть обработано.

## 02. Адрес сообщает, куда обратиться

Любое сообщение нужно направить получателю. URL, или полный адрес, указывает сервер и путь к нужной области. Например, в `https://api.example.test/tasks` путь равен `/tasks`. Сейчас разбираем только этот путь. Имя сервера и остальные части адреса понадобятся, когда появится реальное подключение.

Например:

~~~text
/tasks
/tasks/7
~~~

Здесь:

- /tasks обозначает область задач;
- /tasks/7 обозначает один объект с идентификатором 7;
- адрес не является именем Python-файла;
- адрес не сообщает, какой внутренний метод будет вызван.

Внешний адрес говорит, куда направлено обращение. Он ещё не говорит, что именно нужно сделать. Один и тот же path может использоваться с разными method.

~~~text
GET  /tasks
POST /tasks
~~~

Путь одинаковый, а намерения разные. В первом случае клиент просит существующие данные. Во втором примере нашего Planner API клиент передаёт данные для создания задачи.

### Адрес и внутренний путь

Не путайте внешний path с расположением файла:

~~~text
внешний path:
 /tasks

внутренние детали:
 app/services/planner.py
 data/tasks.json
~~~

Клиенту нужен внешний адрес. Сервер сам решает, какие внутренние модули и хранилище использовать.

Это похоже на адрес кабинета в здании. Посетителю не нужно знать, в каком шкафу лежит журнал и по какой лестнице сотрудник попадёт к нему.

### Что адрес не должен делать

Адрес не должен:

- превращаться в длинное имя действия;
- раскрывать путь к JSON-файлу;
- заставлять клиента знать имя service;
- содержать всю предметную логику;
- подменять method.

Плохо:

~~~text
/tasks/create-new-task
/tasks/delete-task-7
~~~

Такие пути смешивают объект и действие. Подходящий внешний адрес называет область или ресурс, а смысл действия передаётся отдельной частью request. Полное распределение методов мы разберём позже.

### Небольшой пример

~~~text
клиент хочет открыть одну книгу:
path = /books/12

клиент хочет получить список книг:
path = /books
~~~

Изменился объект обращения, поэтому изменился path. Но вопрос «прочитать или изменить» всё ещё относится к method.

### Интерактив. Что изменилось?

Сравните:

~~~text
GET  /books
GET  /books/12
~~~

Ответ:

- method остался тем же;
- path изменился;
- первый request относится к коллекции;
- второй request адресует одну задачу.

Это важное разделение пригодится дальше, когда мы будем проектировать ресурсы Planner API.

### Связь с текущей практикой

В практической функции path уже будет передан готовым аргументом. Ученик не строит адрес из кусочков и не подключается к серверу. Нужно сохранить полученный path внутри учебной модели request, потому что адрес является частью внешнего сообщения.

## 03. Method выражает намерение клиента

Method отвечает на вопрос: что клиент хочет сделать с адресованной областью?

В обычной речи мы различаем:

- показать;
- создать;
- заменить;
- изменить;
- удалить.

HTTP переносит подобный смысл в отдельное поле method.

~~~text
GET  /tasks
POST /tasks
PATCH /tasks/7
~~~

В этом примере:

- GET просит прочитать данные;
- POST просит целевой ресурс обработать переданные данные. В нашем Planner API такой запрос будет создавать задачу;
- PATCH здесь только пример другого имени метода. Его роль в API разберём отдельно.

Полный разговор о GET, POST, PUT, PATCH и DELETE будет позже, в отдельном разборе методов. Сейчас важно увидеть сам принцип: path и method работают вместе, но выполняют разные роли.

### Method не является названием функции

Клиент отправляет:

~~~text
POST /tasks
~~~

Он не отправляет:

~~~text
PlannerService.add_task()
~~~

Сервер связывает внешний method и path с внутренней операцией. Такая связь является ответственностью серверной стороны.

### Заглавные буквы и смысл method

Имена стандартных HTTP-методов по соглашению записывают заглавными буквами:

~~~text
GET
POST
PATCH
~~~

При этом method чувствителен к регистру: заглавные и строчные буквы различаются. Для HTTP `GET` и `get` не одно и то же имя метода.

В практике `solve` получает короткую запись метода до сборки сообщения. Входы `get`, `post` и `patch` специально передаются строчными буквами, а учебная функция приводит их к принятой форме через строковый метод `upper()`. Это правило нашей функции, а не автоматическое исправление со стороны HTTP. Настоящий клиент должен отправить стандартный method в нужном регистре.

### Независимый пример

~~~python
print("GET" == "get")
~~~

Сравнение напечатает `False`: Python тоже различает регистр букв. Поэтому нельзя считать строчную запись готового HTTP-метода эквивалентной заглавной.

Метод строки `upper()` возвращает её с буквами в верхнем регистре. Например, `"get".upper()` даёт `"GET"`. Нормализация означает приведение значения к заранее выбранной форме. В практике это действие учебной функции перед сборкой модели request, а не поведение самого протокола.

### Method и body

Method также подсказывает, нужно ли ожидать данные в body:

~~~text
GET  /books
обычно только чтение

POST /books
обычно есть данные новой книги
~~~

Слово «обычно» важно. В реальных системах встречаются специальные случаи, но на базовом уровне request нужно читать по смыслу операции.

### Ошибочная мысль

Иногда пытаются выразить действие только в path:

~~~text
/tasks/create
~~~

Такой путь уже содержит глагол create, а method становится второстепенным. В более последовательном договоре path обозначает область задач, а method выражает действие.

### Интерактив. Выберите method

Ситуация: клиент хочет только получить список существующих задач.

Варианты:

- GET;
- POST;
- PATCH.

Правильное направление: GET. Клиент просит данные и не сообщает об изменении состояния.

### Связь с текущей практикой

В практической функции method приходит как предварительная запись от вызывающего кода. Практика проверяет отдельное правило сборщика: привести одну из трёх заданных коротких записей к стандартному написанию до возврата модели сообщения. На проводе HTTP не следует полагаться на такую замену регистра.
## 04. Headers описывают сообщение

Headers можно представить как служебные отметки на конверте. Они не являются основной посылкой, но помогают получателю правильно её обработать.

Каждый header состоит из:

~~~text
имя: значение
~~~

Примеры:

~~~text
Accept: application/json
Content-Type: application/json
Planner-Client-Version: 1.0
~~~

Здесь:

- Accept сообщает, какой формат ответа клиент ожидает;
- Content-Type сообщает, в каком формате передано body;
- Planner-Client-Version передаёт дополнительные сведения о клиенте. Это придуманное для примера поле приложения, а не стандартное поле HTTP.

Имена полей заголовков в HTTP не зависят от регистра: `Content-Type` и `content-type` обозначают одно поле. В Python-словаре строки сравниваются с учётом регистра, поэтому в учебной модели используйте написание, указанное в задании.

### Headers не заменяют body

Поля задачи относятся к предметным данным:

~~~text
title
priority
is_done
~~~

Их обычно передают в body, а не прячут в служебные headers.

Headers описывают сообщение. Body несёт данные операции.

~~~text
служебное:
Content-Type: application/json

предметное:
{
  "title": "Изучить HTTP",
  "priority": 4
}
~~~

### Accept и Content-Type отвечают на разные вопросы

Их легко перепутать.

Accept:

~~~text
«Какой формат ответа мне удобен?»
~~~

Content-Type:

~~~text
«В каком формате я отправил тело?»
~~~

Если клиент отправляет JSON и хочет получить JSON, у request могут быть оба header. Но их смысл остаётся разным.

### Что делать, если body нет

Если body отсутствует, описывать формат отсутствующего тела не нужно. Нельзя делать вид, что пустой словарь и отсутствие body всегда одно и то же.

Сравните:

~~~text
body = None
~~~

и:

~~~text
body = {}
~~~

Первое означает, что тела нет. Второе означает, что тело есть и оно содержит пустой объект. Для сервера это могут быть разные ситуации.

В учебной модели это различие нужно сохранить.

### Независимый пример

Представьте отправку фотографии в сервис печати:

~~~text
Content-Type: image/png
Accept: application/json
~~~

Заголовки сообщают формат отправленного файла и желаемый формат ответа. Сама фотография находится отдельно, в body.

### Заголовки в рабочем сервисе

В рабочем сервисе headers часто несут:

- формат данных;
- язык ответа;
- данные для проверки права доступа;
- идентификатор запроса;
- правила временного хранения ответа;
- версию клиента;
- сведения для диагностики пути запроса через компоненты сервиса.

Это не значит, что нужно запомнить все headers. Важно понимать принцип: заголовки сопровождают сообщение и помогают серверу и окружающим его компонентам понять, как с ним работать.

По мере роста системы появляются общие обработчики запросов и дополнительные правила безопасности. Сервис также может записывать путь запроса через свои компоненты, чтобы проще находить сбои. Но основная граница сохраняется: служебные сведения не должны незаметно становиться предметными полями Task.

### Интерактив. Найдите ошибку

~~~text
Priority: 4
Title: Изучить HTTP
~~~

Проблема не в синтаксисе записи. Проблема в распределении ответственности. Предметные поля оказались в служебной области. Их разумнее передать через body, а headers оставить для описания сообщения.

### Связь с текущей практикой

Практика создаёт headers в двух случаях:

- постоянные служебные сведения добавляются всегда;
- Content-Type добавляется только при наличии body.

Это условие проверяет, понял ли ученик разницу между сообщением с телом и сообщением без тела.
## 05. Body передаёт данные операции

Body, или тело request, содержит данные, которые клиент прикладывает к обращению. Оно нужно не каждому запросу.

Для чтения уже существующего списка обычно достаточно:

~~~text
GET /tasks
~~~

Клиент выражает просьбу получить данные. Новую задачу передавать не нужно.

Для создания ресурса нужны поля новой задачи:

~~~text
POST /tasks

body:
{
  "title": "Изучить HTTP",
  "priority": 4
}
~~~

Для изменения конкретной задачи body может содержать изменяемые поля:

~~~text
PATCH /tasks/7

body:
{
  "is_done": true
}
~~~

### Body является optional

У request может быть:

~~~python
body = None
~~~

или:

~~~python
body = {
    "title": "Изучить HTTP",
    "priority": 4,
}
~~~

В первом случае дополнительные данные не переданы. Во втором клиент прикладывает структуру данных.

Важно не заменять None пустым словарём автоматически. Это меняет смысл сообщения.

### Body и адрес работают вместе

Адрес отвечает на вопрос «с каким ресурсом работаем», а body отвечает на вопрос «какие данные передаём для операции».

~~~text
PATCH /tasks/7

path:
  выбирает задачу 7

body:
  сообщает новое значение is_done
~~~

Не нужно помещать всё в body. Если идентификатор уже является частью адреса, дублирование может создать противоречие.

### Body и headers работают вместе

В нашем договоре словарь Python означает будущий JSON body. Поле `Content-Type` явно сообщает формат этого тела:

~~~text
Content-Type: application/json
~~~

Получается связка:

~~~text
body содержит данные
Content-Type объясняет формат body
~~~

Для тела другого формата нужен другой `Content-Type`. Сам HTTP не требует, чтобы каждое тело было JSON. В этой учебной модели `Content-Type: application/json` добавляется для JSON-тела, а без тела это поле опускается.

### JSON уже знаком, но граница меняется

Во втором курсе JSON использовался как формат сохранения. Здесь JSON может быть форматом передачи между процессами.

Смысл похожий:

~~~text
Python-структура → текстовый JSON → другая сторона
~~~

Но задачи разные:

- хранилище сохраняет состояние;
- HTTP body переносит данные операции.

JSON не становится базой данных и не становится источником истины только потому, что находится в body.

### Форматы в реальном HTTP

В реальном HTTP body может содержать:

- JSON для обычного API;
- форму с полями и файлами;
- текст;
- бинарное содержимое;
- пустое тело.

Формат зависит от договора. Клиент и сервер должны одинаково понимать, что лежит в body и как это читать. Названия разных кодировок файлов и форм здесь пока не нужны.

В нашем первом упражнении используется словарь Python как учебное представление. Мы не сериализуем его в байты и не отправляем по сети. Так мы сосредотачиваемся на роли body.

### Интерактив. Сравните два request

~~~text
GET /tasks
body = None
~~~

и:

~~~text
POST /tasks
body = {
  "title": "Новая задача",
  "priority": 3
}
~~~

Разница не только в наличии словаря. Изменились:

- method;
- смысл операции;
- необходимость Content-Type;
- набор данных, который должен прочитать сервер.

### Связь с текущей практикой

В практическую функцию body передаётся готовым аргументом. Его не нужно создавать, менять или превращать в JSON. Модель request должна сохранить полученное значение, чтобы было видно, какие данные клиент отправлял.

## 06. Условная часть request

Теперь объединим headers и body. Некоторые части сообщения постоянны, а некоторые зависят от ситуации.

Постоянные сведения можно представить так:

~~~text
Accept: application/json
Planner-Client-Version: версия клиента
~~~

В упражнении body может быть словарём JSON или значением `None`. Если это словарь, в том числе пустой, добавляется ещё одна отметка:

~~~text
Content-Type: application/json
~~~

Логика словами:

~~~text
если body существует:
    описать формат body
иначе:
    не создавать Content-Type только ради полноты
~~~

### Почему условие важно

Серверу важно отличать отсутствие body от пустого JSON-объекта. Это два разных входа, и договор может обрабатывать их по-разному.

Похожая ситуация встречается в обычной форме:

- если к письму приложен файл, указывают его тип;
- если файла нет, не пишут, что письмо содержит файл;
- пустая папка не то же самое, что отсутствие папки.

### Проверьте разницу между отсутствием и пустым значением

~~~python
print(None is not None, bool(None))
print({} is not None, bool({}))
print({"title": "Книга"} is not None, bool({"title": "Книга"}))
~~~

`bool(value)` показывает, как Python оценит значение в условии `if`. Первые две проверки дадут соответственно `False False` и `True False`: пустой словарь есть, но считается ложным в таком условии. Третья пара даст `True True`.

### Частая ошибка

Проверить, пустой ли словарь, вместо того чтобы проверить, отсутствует ли значение:

~~~python
body = {}
if body:
    print("Тело передано")
else:
    print("Тело отсутствует")
~~~

Этот фрагмент напечатает «Тело отсутствует», хотя в переменной находится пустой словарь. Для непустого словаря ветка if сработала бы. Но пустой словарь тоже является существующим body, хотя в нём нет полей.

В нашей учебной модели правило сформулировано явно: `None` означает отсутствие body, а любой словарь, даже `{}`, означает, что JSON body есть. Поэтому проверка должна различать эти состояния, а не только проверять, пустой ли словарь.

### Связь с текущей практикой

Это центральный механизм упражнения. Автопроверка сравнит request без body, с пустым JSON-объектом и с заполненным объектом. Она должна увидеть не просто разные данные, а правильное наличие или отсутствие `Content-Type`.

## 07. Как request выглядит в HTTP/1.1

Четыре части помогают понять смысл сообщения. Теперь посмотрим, как похожие сведения располагаются в читаемом примере HTTP/1.1. Это не новый формат задания, а следующий уровень той же модели.

В обычном обращении к серверу первая строка содержит method, путь запроса и версию протокола. Эту строку называют строкой запроса. Ниже идут headers. Пустая строка отделяет их от body. Если тело не нужно, после разделителя данных может не быть.

~~~http
POST /tasks HTTP/1.1
Host: api.example.test
Accept: application/json
Content-Type: application/json
Planner-Client-Version: 1.0

{"title": "Изучить HTTP"}
~~~

Здесь видны разные роли:

- `POST` сообщает намерение клиента;
- `/tasks` является путём запроса;
- `HTTP/1.1` указывает версию протокола;
- `Host` сообщает имя сервера, которому адресовано сообщение;
- остальные строки до пустой строки являются headers;
- JSON после пустой строки является body.

Поле `Host` обязательно в запросах HTTP/1.1. Имена полей headers при этом не зависят от регистра. В словаре Python регистр ключей имеет значение, поэтому учебное задание проверяет точное написание, указанное в контракте.

Пример выше показывает читаемую форму HTTP/1.1. Это не универсальный вид передачи всех версий HTTP. Клиентская библиотека скрывает детали конкретного соединения и представления данных.

### Почему в практике нет Host и HTTP/1.1

Функция `solve` получает `path`, а не полный URL, и не получает имя сервера. Поэтому она не может добавить `Host` из входных данных. Задание намеренно возвращает упрощённую модель с четырьмя ключами `method`, `path`, `headers` и `body`.

Модель помогает проверить смысл частей сообщения, но не является готовым HTTP-запросом. В ней нет строки запроса, имени сервера, разделителя строк и сериализации body. Эти детали обычно обрабатывает клиентская библиотека.

### Интерактив. Где проходит граница?

Можно ли заменить `Host: api.example.test` на `/tasks`?

Нет. `Host` выбирает сервер, а path указывает область внутри API. Это разные части адреса.

Можно ли читать JSON body как продолжение headers?

Нет. Пустая строка завершает область headers. Следующие данные относятся к body.

### Связь с практикой

Практика намеренно не возвращает `Host` и `HTTP/1.1`: функция получает только path и проверяет упрощённую модель из четырёх частей. Поэтому её результат ещё не является готовым сообщением для отправки.

## 08. Что делает HTTP-клиент за разработчика

В реальном приложении программист обычно работает с удобными значениями: URL, method, словарём headers и объектом body. HTTP-клиент берёт на себя подготовку и передачу сообщения. Это позволяет сосредоточиться на договоре, а не вручную собирать сетевое соединение.

### Сериализация

Сериализация превращает структуру данных в согласованное представление для передачи. Например, словарь Python можно закодировать как JSON, а затем передать как последовательность байтов. Байты являются числовым представлением данных, которое можно передать по соединению.

Когда разработчик передаёт объект в HTTP-клиент, клиентская библиотека может выполнить сериализацию автоматически. Без библиотеки пришлось бы отдельно подготовить представление body и согласовать его формат с `Content-Type`.

### Соединение и транспорт

Транспортом здесь называют передачу данных между процессами через сеть. Клиентская библиотека использует соединение, чтобы отправить сообщение серверу и получить ответ. Соединение может переиспользоваться для нескольких запросов, поэтому не обязательно открывать новое перед каждой операцией.

Клиентская библиотека не решает, можно ли создавать задачу, и не заменяет правила `PlannerService` на сервере. Она помогает выполнить обмен. Прикладные решения остаются на серверной стороне.

### Путь реального request

~~~text
подготовить URL, method, headers и body
    ↓
закодировать body в согласованный формат
    ↓
передать HTTP request через соединение
    ↓
получить и разобрать HTTP response
~~~

Сначала клиент определяет договор сообщения, затем подготавливает данные к передаче. Ответ появляется после отправки и обработки на сервере. Status, headers и body ответа мы разберём в следующем занятии.

### Граница этого занятия

Сейчас мы изучаем форму request, а не пишем HTTP-клиент. Не нужно устанавливать библиотеку, настраивать адрес или выполнять сетевой вызов. В практике все данные уже переданы аргументами функции.

## 09. Учебная модель и настоящий HTTP

В практике мы не отправляем request по сети. Мы собираем обычный словарь Python.

Это решение сделано специально.

### Почему не настоящая сеть

Для настоящего HTTP нужны:

- работающий сервер;
- адрес и доступность процесса;
- библиотека клиента;
- обработка соединения;
- преобразование body в текст и байты для передачи;
- разбор response;
- обработка сетевых ошибок.

Эти детали полезны, но они смешали бы несколько новых тем в одной маленькой задаче.

### Что проверяет учебная модель

Она проверяет только понимание структуры:

~~~text
входные значения
    ↓
учебная модель request
    ↓
сравнение с ожидаемым результатом
~~~

Ученик должен увидеть:

- method в единой форме;
- path без случайной перестройки;
- headers с нужными служебными значениями;
- body без подмены.

### Внешняя и внутренняя граница

Учебный сборщик похож на конструктор сообщения. Он не выполняет предметную операцию.

~~~text
сборщик request:
  описывает намерение

PlannerService:
  выполняет предметное правило

хранилище:
  сохраняет или читает состояние
~~~

Так сохраняется архитектурная граница из прошлого занятия.

### Не путайте словарь и JSON

Словарь Python:

~~~python
{"title": "HTTP", "is_done": False}
~~~

и JSON-текст:

~~~text
{"title": "HTTP", "is_done": false}
~~~

связаны, но не одинаковы:

- у них разные правила записи;
- Python использует True и False;
- JSON использует true и false;
- словарь живёт в памяти;
- JSON является текстовым представлением.

Текущая практика не просит выполнять это преобразование. Body нужно вернуть как полученное учебное значение.

### Как сообщение отправляется в рабочем приложении

В настоящем клиенте библиотека обычно:

1. принимает структуру данных;
2. преобразует её в согласованный формат, например в текст JSON и байты для передачи. Это называется сериализацией;
3. добавляет нужные служебные сведения;
4. передаёт сообщение по сети;
5. получает response.

В настоящем сервере обратная сторона читает request и превращает его части в данные для прикладной операции.

Наш маленький сборщик изолирует первый слой понимания. Когда появится настоящий клиент, ученик уже будет знать, что библиотека собирает не магию, а знакомые части сообщения.
## 10. Что мы будем делать в практике

Практика проверит одну изолированную функцию в редакторе. Сервер запускать не нужно. Сеть подключать не нужно. Всё необходимое передаётся в аргументах.

### Общий результат

Нужно вернуть словарь, который представляет учебную модель HTTP request. В нём должны быть четыре части:

- method;
- path;
- headers;
- body.

Короткая запись метода приводится к стандартному написанию по правилу этой функции. Path и body сохраняются без изменения. Headers собираются по договору.

### Что дано

Функция получает:

- method, одна из коротких записей `get`, `post` или `patch` до сборки сообщения;
- path, например /tasks или /tasks/7;
- client_version, то есть версию клиента;
- body, то есть словарь или None.

Значения не нужно изобретать заново. Они уже являются входом функции.

### Что требуется понять

До редактора ответьте на четыре вопроса:

1. Какие headers присутствуют в каждом request?
2. Какое поле зависит от наличия body?
3. Что нужно привести к верхнему регистру?
4. Какие входные значения нельзя менять?

Если на них есть ответ, задача становится небольшой сборкой, а не поиском неизвестной технологии.

### Как будет проверен результат

Автопроверка использует четыре сценария:

- GET без body;
- POST с пустым JSON-объектом;
- POST с JSON body;
- короткая запись patch с другим path и переданным body.

В последнем тесте запись patch нужна только для проверки преобразования имени метода и сохранения входных значений. Её смысл для API здесь не требуется. Сценарий с POST и пустым JSON проверяет только структуру модели, а не обещает, что сервер примет пустую задачу.

Она сравнивает весь словарь. Поэтому будут замечены:

- лишний Content-Type у request без body;
- отсутствие Content-Type у пустого, но существующего JSON body;
- пропущенный Accept;
- пропущенная версия клиента;
- method в нижнем регистре;
- изменённый path;
- подмена body или None.

### Чего делать не нужно

Не нужно запускать сервер или отправлять данные по сети. Также не нужно читать файлы проекта, вызывать PlannerService или вручную превращать словарь в текст HTTP-сообщения. Мы проверяем только структуру будущего сообщения до его отправки.

### Подсказка к началу

Сначала отделите постоянные части от условной. Затем соберите headers. После этого верните все четыре части в одном словаре.

Проверяйте не только успешный POST. Самый полезный контраст в этой задаче: `None` и пустой словарь `{}`. Первый означает отсутствие body, второй является пустым JSON body.

### Доказательство результата

Работа готова, если одна функция:

- возвращает словарь, а не печатает его;
- приводит короткую запись method к стандартному написанию для учебной модели;
- сохраняет path;
- сохраняет body;
- добавляет Content-Type только при body;
- проходит все четыре сценария проверки.

После этого мы сможем перейти к response. Там появится обратная сторона того же обмена.
