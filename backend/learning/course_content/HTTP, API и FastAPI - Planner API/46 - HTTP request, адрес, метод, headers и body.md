## 00. От границы клиента и сервера к самому сообщению

В прошлом занятии мы провели главную архитектурную границу. Клиент формулирует намерение, сервер хранит правила и источник истины. Теперь появился естественный вопрос: в каком виде клиент передаёт это намерение серверу?

Представьте пункт выдачи заказов. Посетитель не заходит на склад и не вызывает кладовщика по имени. Он передаёт бланк. В бланке указано, куда обратиться, что нужно сделать, какие есть служебные отметки и какие данные приложены. Сотрудник склада читает этот бланк и уже внутри выполняет свою работу.

HTTP request выполняет похожую роль. Это сообщение от клиента к серверу.

Важно различать два уровня:

~~~text
намерение пользователя:
создать задачу

внешнее сообщение:
request

внутренняя работа сервера:
PlannerService и storage
~~~

Request не является вызовом метода PlannerService. Клиент не отправляет серверу имя Python-функции и не получает доступ к его объектам. Он передаёт сообщение по внешнему договору.

### Что уже известно

Мы уже знаем:

- клиент начинает обращение;
- сервер принимает его;
- сервер владеет правилами и источником истины;
- Persistent Planner остаётся внутренним ядром;
- request и response связывают две стороны.

### Что добавляется сейчас

В этом занятии request рассматривается как составное сообщение. У него есть:

- адрес назначения;
- method, то есть выраженное действие;
- headers, то есть служебные сведения;
- body, то есть дополнительные данные, если они нужны.

Эти части отвечают на разные вопросы:

~~~text
куда обратиться?
что попросить?
как описать сообщение?
какие данные передать?
~~~

### Чего пока не будет

Сейчас не нужны:

- FastAPI;
- route-декораторы;
- запущенный сервер;
- Postman;
- настоящая отправка по сети;
- query-параметры;
- авторизация;
- сложная сериализация.

Сначала мы соберём спокойную модель сообщения в Python. Это учебный макет request. Он помогает проверить смысл частей отдельно от сети.

**Остановитесь на минуту.** Если клиент отправил строку «создай задачу», это ещё не значит, что сервер получил полноценный request. Нужно определить адрес, method и, при необходимости, данные задачи.

## 01. Request является сообщением, а не вызовом функции

В одном Python-процессе можно обратиться к объекту напрямую:

~~~python
service.add_task("Изучить HTTP")
~~~

Здесь Python находит объект service в памяти и вызывает его метод. Никакой внешней границы нет.

В клиент-серверной модели клиент не видит этот объект:

~~~text
клиент
  ↓ request
сервер
  ↓ внутренняя работа
PlannerService
  ↓
storage
  ↑
сервер
  ↑ response
клиент
~~~

Сервер может внутри вызвать PlannerService, но клиент об этом не знает. Для клиента существует только внешний договор сообщения и результат.

### Почему это разделение важно

Если внешний клиент зависит от имени Python-метода, внутренняя замена становится опасной. Переименовали add_task в create_task, и все внешние клиенты сломались бы, хотя смысл операции не изменился.

Внешний договор должен описывать смысл:

~~~text
«создать задачу»
~~~

а не деталь реализации:

~~~text
«вызвать метод add_task объекта PlannerService»
~~~

Так можно:

- заменить JSON storage на базу данных;
- изменить внутреннюю структуру service;
- добавить другой клиент;
- оставить внешний способ обращения прежним.

### Независимый пример

Рассмотрим не задачи, а доставку книги.

~~~text
внутри программы:
library.reserve(book_id)

между клиентом и сервером:
клиент → request: «забронировать книгу»
сервер → response: «книга забронирована»
~~~

Клиенту не нужно знать, хранит ли библиотека книги в словаре, файле или базе данных. Он знает только смысл операции и правила сообщения.

### Что входит в обязанность клиента

Клиент:

1. получает намерение пользователя;
2. выбирает подходящий адрес;
3. выбирает method;
4. добавляет необходимые headers;
5. прикладывает body, если операция передаёт данные;
6. отправляет request;
7. ждёт response.

Клиент может делать удобные проверки формы. Например, подсветить пустой заголовок до отправки. Но это не превращает клиентскую проверку в окончательное правило сервера.

### Что входит в обязанность сервера

Сервер:

1. принимает request;
2. понимает его части;
3. проверяет допустимость данных;
4. выбирает прикладную операцию;
5. обращается к Task, PlannerService и storage;
6. формирует response.

В этом занятии мы не реализуем сервер. Нам нужно научиться читать и собирать его входное сообщение.

**Проверьте себя.** Если request содержит method и path, это ещё не означает, что сервер уже выполнил операцию. Сначала сообщение должно попасть на сервер, пройти проверку и быть обработано.

## 02. Адрес сообщает, куда обратиться

Любое сообщение нужно направить получателю. В HTTP адрес назначения обычно записывается в виде URL. Для текущей темы достаточно воспринимать его как внешний адрес сервера и нужной области приложения.

Например:

~~~text
/tasks
/tasks/7
~~~

Здесь:

- /tasks обозначает область задач;
- /tasks/7 обозначает одну задачу с идентификатором 7;
- адрес не является именем Python-файла;
- адрес не сообщает, какой внутренний метод будет вызван.

Внешний адрес говорит, куда направлено обращение. Он ещё не говорит, что именно нужно сделать. Один и тот же path может использоваться с разными method.

~~~text
GET  /tasks
POST /tasks
~~~

Путь одинаковый, а намерения разные. В первом случае клиент просит существующие данные. Во втором он передаёт данные для создания.

### Адрес и внутренний путь

Не путайте внешний path с расположением файла:

~~~text
внешний path:
 /tasks

внутренние детали:
 app/services/planner.py
 data/tasks.json
~~~

Клиенту нужен внешний адрес. Сервер сам решает, какие внутренние модули и storage использовать.

Это похоже на адрес кабинета в здании. Посетителю не нужно знать, в каком шкафу лежит журнал и по какой лестнице сотрудник попадёт к нему.

### Что адрес не должен делать

Адрес не должен:

- превращаться в длинное имя действия;
- раскрывать путь к JSON-файлу;
- заставлять клиента знать имя service;
- содержать всю предметную логику;
- подменять method.

Плохо:

~~~text
/tasks/create-new-task
/tasks/delete-task-7
~~~

Такие пути смешивают объект и действие. Подходящий внешний адрес называет область или ресурс, а смысл действия передаётся отдельной частью request. Полное распределение методов мы разберём позже.

### Небольшой пример

~~~text
клиент хочет открыть одну книгу:
path = /books/12

клиент хочет получить список книг:
path = /books
~~~

Изменился объект обращения, поэтому изменился path. Но вопрос «прочитать или изменить» всё ещё относится к method.

### Интерактив. Что изменилось?

Сравните:

~~~text
GET  /books
GET  /books/12
~~~

Ответ:

- method остался тем же;
- path изменился;
- первый request относится к коллекции;
- второй request адресует один item.

Это важное разделение пригодится дальше, когда мы будем проектировать ресурсы Planner API.

### Связь с текущей практикой

В практической функции path уже будет передан готовым аргументом. Ученик не строит адрес из кусочков и не подключается к серверу. Нужно сохранить полученный path внутри учебной модели request, потому что адрес является частью внешнего сообщения.

## 03. Method выражает намерение клиента

Method отвечает на вопрос: что клиент хочет сделать с адресованной областью?

В обычной речи мы различаем:

- показать;
- создать;
- заменить;
- изменить;
- удалить.

HTTP переносит подобный смысл в отдельное поле method.

~~~text
GET  /tasks
POST /tasks
PATCH /tasks/7
~~~

В этом примере:

- GET просит прочитать данные;
- POST сообщает о создании нового ресурса;
- PATCH просит частично изменить известный ресурс.

Полный разговор о GET, POST, PUT, PATCH и DELETE будет в следующем занятии. Сейчас важно увидеть сам принцип: path и method работают вместе, но выполняют разные роли.

### Method не является названием функции

Клиент отправляет:

~~~text
POST /tasks
~~~

Он не отправляет:

~~~text
PlannerService.add_task()
~~~

Сервер связывает внешний method и path с внутренней операцией. Такая связь является ответственностью серверной стороны.

### Почему method обычно пишут заглавными

HTTP method принято записывать в верхнем регистре:

~~~text
GET
POST
PATCH
~~~

В учебной функции вход может прийти в нижнем регистре, например get. Если наша модель должна быть канонической, она переводит значение в верхний регистр.

Это не превращает функцию в настоящий HTTP-клиент. Мы только приводим часть учебного сообщения к единому виду.

### Независимый пример

~~~python
def canonical_action(action):
    return action.upper()

print(canonical_action("borrow"))
~~~

Что напечатает код?

~~~text
BORROW
~~~

Функция не выполняет бронирование. Она только приводит обозначение действия к единой форме. Такой маленький механизм помогает разным источникам использовать согласованные значения.

### Method и body

Method также подсказывает, нужно ли ожидать данные в body:

~~~text
GET  /books
обычно только чтение

POST /books
обычно есть данные новой книги
~~~

Слово «обычно» важно. В реальных системах встречаются специальные случаи, но на базовом уровне request нужно читать по смыслу операции.

### Ошибочная мысль

Иногда пытаются выразить действие только в path:

~~~text
/tasks/create
~~~

Такой путь уже содержит глагол create, а method становится второстепенным. В более последовательном договоре path обозначает область задач, а method выражает действие.

### Интерактив. Выберите method

Ситуация: клиент хочет только получить список существующих задач.

Варианты:

- GET;
- POST;
- PATCH.

Правильное направление: GET. Клиент просит данные и не сообщает об изменении состояния.

### Связь с текущей практикой

В учебной функции method приходит в аргументе. Практика проверяет, что модель сообщения приводит его к верхнему регистру. Это маленькая, но наблюдаемая часть договора: разные записи одного method получают одну каноническую форму.
## 04. Headers описывают сообщение

Headers можно представить как служебные отметки на конверте. Они не являются основной посылкой, но помогают получателю правильно её обработать.

Каждый header состоит из:

~~~text
имя: значение
~~~

Примеры:

~~~text
Accept: application/json
Content-Type: application/json
X-Client-Version: 1.0
~~~

Здесь:

- Accept сообщает, какой формат ответа клиент ожидает;
- Content-Type сообщает, в каком формате передано body;
- X-Client-Version передаёт дополнительную метаинформацию о клиенте.

### Headers не заменяют body

Поля задачи относятся к предметным данным:

~~~text
title
priority
is_done
~~~

Их обычно передают в body, а не прячут в служебные headers.

Headers описывают сообщение. Body несёт данные операции.

~~~text
служебное:
Content-Type: application/json

предметное:
{
  "title": "Изучить HTTP",
  "priority": 4
}
~~~

### Accept и Content-Type отвечают на разные вопросы

Их легко перепутать.

Accept:

~~~text
«Какой формат ответа мне удобен?»
~~~

Content-Type:

~~~text
«В каком формате я отправил тело?»
~~~

Если клиент отправляет JSON и хочет получить JSON, у request могут быть оба header. Но их смысл остаётся разным.

### Что делать, если body нет

Если body отсутствует, описывать формат отсутствующего тела не нужно. Нельзя делать вид, что пустой словарь и отсутствие body всегда одно и то же.

Сравните:

~~~text
body = None
~~~

и:

~~~text
body = {}
~~~

Первое означает, что тела нет. Второе означает, что тело есть и оно содержит пустой объект. Для сервера это могут быть разные ситуации.

В учебной модели это различие нужно сохранить.

### Независимый пример

Представьте отправку фотографии в сервис печати:

~~~text
Content-Type: image/png
Accept: application/json
X-Client-Version: kiosk-2
~~~

Headers сообщают формат файла, желаемый формат ответа и версию терминала. Сама фотография находится отдельно, в body.

### Production-контекст

В production headers часто несут:

- формат данных;
- язык ответа;
- авторизационные сведения;
- идентификатор запроса;
- кэш-политику;
- версию клиента;
- технические признаки трассировки.

Это не значит, что нужно запомнить все headers. Важно понимать принцип: headers сопровождают сообщение и помогают инфраструктуре или серверу его интерпретировать.

С ростом системы появляются общие middleware, правила безопасности и трассировка. Но основная граница сохраняется: служебные сведения не должны незаметно становиться предметными полями Task.

### Интерактив. Найдите ошибку

~~~text
Priority: 4
Title: Изучить HTTP
~~~

Проблема не в синтаксисе записи. Проблема в распределении ответственности. Предметные поля оказались в служебной области. Их разумнее передать через body, а headers оставить для описания сообщения.

### Связь с текущей практикой

Практика создаёт headers в двух случаях:

- постоянные служебные сведения добавляются всегда;
- Content-Type добавляется только при наличии body.

Это условие проверяет, понял ли ученик разницу между сообщением с телом и сообщением без тела.
## 05. Body передаёт данные операции

Body, или тело request, содержит данные, которые клиент прикладывает к обращению. Оно нужно не каждому запросу.

Для чтения уже существующего списка обычно достаточно:

~~~text
GET /tasks
~~~

Клиент выражает просьбу получить данные. Новую задачу передавать не нужно.

Для создания ресурса нужны поля новой задачи:

~~~text
POST /tasks

body:
{
  "title": "Изучить HTTP",
  "priority": 4
}
~~~

Для изменения конкретной задачи body может содержать изменяемые поля:

~~~text
PATCH /tasks/7

body:
{
  "is_done": true
}
~~~

### Body является optional

У request может быть:

~~~python
body = None
~~~

или:

~~~python
body = {
    "title": "Изучить HTTP",
    "priority": 4,
}
~~~

В первом случае дополнительные данные не переданы. Во втором клиент прикладывает структуру данных.

Важно не заменять None пустым словарём автоматически. Это меняет смысл сообщения.

### Body и адрес работают вместе

Адрес отвечает на вопрос «с каким ресурсом работаем», а body отвечает на вопрос «какие данные передаём для операции».

~~~text
PATCH /tasks/7

path:
  выбирает задачу 7

body:
  сообщает новое значение is_done
~~~

Не нужно помещать всё в body. Если идентификатор уже является частью адреса, дублирование может создать противоречие.

### Body и headers работают вместе

Серверу нужно понять, как читать body. Для JSON этому помогает:

~~~text
Content-Type: application/json
~~~

Получается связка:

~~~text
body содержит данные
Content-Type объясняет формат body
~~~

Если body есть, а его формат не описан, серверу сложнее надёжно понять сообщение. Если Content-Type есть, но body отсутствует, служебная отметка не описывает реальное содержимое.

### JSON уже знаком, но граница меняется

Во втором курсе JSON использовался как формат сохранения. Здесь JSON может быть форматом передачи между процессами.

Смысл похожий:

~~~text
Python-структура → текстовый JSON → другая сторона
~~~

Но задачи разные:

- storage сохраняет состояние;
- HTTP body переносит данные операции.

JSON не становится базой данных и не становится источником истины только потому, что находится в body.

### Production-контекст

В production body может быть:

- JSON для обычного API;
- multipart-данные для файлов;
- текст;
- бинарное содержимое;
- пустое тело.

Формат зависит от договора. Клиент и сервер должны одинаково понимать, что лежит в body и как это читать.

В нашем первом упражнении используется словарь Python как учебное представление. Мы не сериализуем его в байты и не отправляем по сети. Так мы сосредотачиваемся на роли body.

### Интерактив. Сравните два request

~~~text
GET /tasks
body = None
~~~

и:

~~~text
POST /tasks
body = {
  "title": "Новая задача",
  "priority": 3
}
~~~

Разница не только в наличии словаря. Изменились:

- method;
- смысл операции;
- необходимость Content-Type;
- набор данных, который должен прочитать сервер.

### Связь с текущей практикой

В практическую функцию body передаётся готовым аргументом. Его не нужно создавать, менять или превращать в JSON. Модель request должна сохранить полученное значение, чтобы было видно, какие данные клиент отправлял.

## 06. Условная часть request

Теперь объединим headers и body. Некоторые части сообщения постоянны, а некоторые зависят от ситуации.

Постоянные сведения можно представить так:

~~~text
Accept: application/json
X-Client-Version: версия клиента
~~~

Если клиент действительно приложил body, добавляется ещё одна отметка:

~~~text
Content-Type: application/json
~~~

Логика словами:

~~~text
если body существует:
    описать формат body
иначе:
    не создавать Content-Type только ради полноты
~~~

### Почему условие важно

Сервер читает не только значения, но и отсутствие значения. Request без body не должен выглядеть так, будто в нём есть JSON-объект.

Похожая ситуация встречается в обычной форме:

- если к письму приложен файл, указывают его тип;
- если файла нет, не пишут, что письмо содержит файл;
- пустая папка не то же самое, что отсутствие папки.

### Минимальный независимый пример

~~~python
def describe_payload(payload):
    headers = {"Accept": "application/json"}

    if payload is not None:
        headers["Content-Type"] = "application/json"

    return headers
~~~

Разберём его:

1. создаётся словарь постоянных headers;
2. проверяется именно отсутствие значения;
3. при наличии payload добавляется описание формата;
4. возвращается служебная часть сообщения.

Функция не отправляет запрос и не изменяет payload. Она только строит описание.

Что вернётся для None?

~~~text
{"Accept": "application/json"}
~~~

Что изменится для словаря?

~~~text
появится Content-Type
~~~

### Частая ошибка

Проверить условие payload truthiness вместо проверки отсутствия:

~~~python
if payload:
    headers["Content-Type"] = "application/json"
~~~

Для обычного непустого словаря это сработает. Но пустой словарь является существующим body, хотя он логически пуст. Поэтому выбор условия зависит от договора.

В нашей учебной модели правило сформулировано явно: Content-Type зависит от того, равен ли body значению None.

### Связь с текущей практикой

Это центральный механизм упражнения. Автопроверка сравнит request без body и request с body. Она должна увидеть не просто разные данные, а разную структуру headers.

## 07. Учебная модель и настоящий HTTP

В практике мы не отправляем request по сети. Мы собираем обычный словарь Python.

Это решение сделано специально.

### Почему не настоящая сеть

Для настоящего HTTP нужны:

- работающий сервер;
- адрес и доступность процесса;
- библиотека клиента;
- обработка соединения;
- сериализация body;
- разбор response;
- обработка сетевых ошибок.

Эти детали полезны, но они смешали бы несколько новых тем в одной маленькой задаче.

### Что проверяет учебная модель

Она проверяет только понимание структуры:

~~~text
входные значения
    ↓
учебная модель request
    ↓
сравнение с ожидаемым результатом
~~~

Ученик должен увидеть:

- method в единой форме;
- path без случайной перестройки;
- headers с нужными служебными значениями;
- body без подмены.

### Внешняя и внутренняя граница

Учебный сборщик похож на конструктор сообщения. Он не выполняет предметную операцию.

~~~text
сборщик request:
  описывает намерение

PlannerService:
  выполняет предметное правило

storage:
  сохраняет или читает состояние
~~~

Так сохраняется архитектурная граница из прошлого занятия.

### Не путайте словарь и JSON

Словарь Python:

~~~python
{"title": "HTTP", "is_done": False}
~~~

и JSON-текст:

~~~text
{"title": "HTTP", "is_done": false}
~~~

связаны, но не одинаковы:

- у них разные правила записи;
- Python использует True и False;
- JSON использует true и false;
- словарь живёт в памяти;
- JSON является текстовым представлением.

Текущая практика не просит выполнять это преобразование. Body нужно вернуть как полученное учебное значение.

### Production-контекст

В настоящем клиенте библиотека обычно:

1. принимает структуру данных;
2. сериализует её в согласованный формат;
3. добавляет нужные служебные сведения;
4. передаёт сообщение по сети;
5. получает response.

В настоящем сервере обратная сторона читает request и превращает его части в данные для прикладной операции.

Наш маленький сборщик изолирует первый слой понимания. Когда появится настоящий клиент, ученик уже будет знать, что библиотека собирает не магию, а знакомые части сообщения.
## 08. Что мы будем делать в практике

Практика проверит одну изолированную функцию в редакторе. Сервер запускать не нужно. Сеть подключать не нужно. Всё необходимое передаётся в аргументах.

### Общий результат

Нужно вернуть словарь, который представляет HTTP request. В нём должны быть четыре части:

- method;
- path;
- headers;
- body.

Метод приводится к верхнему регистру. Path и body сохраняются без изменения. Headers собираются по договору.

### Что дано

Функция получает:

- method, например get;
- path, например /tasks или /tasks/7;
- client_version, то есть версию клиента;
- body, то есть словарь или None.

Значения не нужно изобретать заново. Они уже являются входом функции.

### Что требуется понять

До редактора ответьте на четыре вопроса:

1. Какие headers присутствуют в каждом request?
2. Какое поле зависит от наличия body?
3. Что нужно привести к верхнему регистру?
4. Какие входные значения нельзя менять?

Если на них есть ответ, задача становится небольшой сборкой, а не поиском неизвестной технологии.

### Как будет проверен результат

Автопроверка использует три сценария:

- GET без body;
- POST с JSON body;
- PATCH с другим path и body изменения.

Она сравнивает весь словарь. Поэтому будут замечены:

- лишний Content-Type у request без body;
- пропущенный Accept;
- пропущенная версия клиента;
- method в нижнем регистре;
- изменённый path;
- подмена body или None.

### Чего делать не нужно

Не нужно:

- открывать браузер;
- запускать FastAPI;
- вызывать requests;
- подключать Postman;
- читать tasks.json;
- вызывать PlannerService;
- сериализовать body;
- собирать raw HTTP-строку.

Это не упрощённая версия настоящего задания. Это отдельная проверка структуры сообщения перед сетевым слоем.

### Подсказка к началу

Сначала отделите постоянные части от условной. Затем соберите headers. После этого верните все четыре части в одном словаре.

Проверяйте не только успешный POST. Самый полезный контраст в этой задаче: GET без body и POST с body.

### Доказательство результата

Работа готова, если одна функция:

- возвращает словарь, а не печатает его;
- канонизирует method;
- сохраняет path;
- сохраняет body;
- добавляет Content-Type только при body;
- проходит все три сценария проверки.

После этого мы сможем перейти к response. Там появится обратная сторона того же обмена.

### Главное

- Request является сообщением клиента к серверу.
- Method выражает намерение.
- Path сообщает адрес назначения.
- Headers описывают сообщение.
- Body передаёт данные операции, если они нужны.
- Accept описывает желаемый формат response.
- Content-Type сообщает формат body.
- Версия клиента является служебной метаинформацией.
- Отсутствие body не равно пустому словарю.
- Учебная модель request помогает проверить структуру без сети.
- Клиент не знает имён внутренних Python-методов.
- PlannerService и storage остаются на серверной стороне.
- Следующая работа будет разбирать response.
