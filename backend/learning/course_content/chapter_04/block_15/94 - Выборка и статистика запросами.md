## Место в маршруте

Занятие переводит прежние выборку и статистику Planner с JSON-адаптера на SQL-репозиторий. Оно опирается на SQL CRUD из занятий 90–93, не меняя маршруты и публичный договор API. Результат нужен занятию 95: SQL-поиск будет добавлен к уже работающей выборке, но его смысл и реализация здесь не рассматриваются.

Источник журнала обучения StudyHub подтверждает занятия 78–89, в том числе SQL-чтение и импорт.

SQL-репозиторий и сервисный контракт подготовлены, но в проверенной рабочей копии SQL-репозиторий ещё содержит только `list/get`; `select/statistics` не готовы. HTTP по-прежнему работает через JSON.

## Точка B: результат занятия

- Ученик сможет объяснить: как SQL выполняет фильтрацию, упорядочивание и ограничение; чем `None` отличается от `False`; чем скалярный агрегат отличается от списка предметных объектов.
- Ученик сможет сделать: реализовать SQL-выборку по `is_done`, направлению сортировки и `limit`, а также статистику без загрузки всех задач в память.
- Результат в проекте: прежний SQL-репозиторий выполняет `select` и `statistics`; существующий сервис и `GET /tasks`, `GET /stats` получают результат по прежнему пути. Сборка приложения по-прежнему использует JSON.
- Как подтвердим: прямой вызов сервиса и существующие HTTP-маршруты возвращают ожидаемые данные; пустая база даёт нулевые счётчики; смешанные состояния и границы `limit` совпадают с прежним договором; SQL-статистика не материализует `Task` для каждой строки.

## Границы и передача дальше

- Передаём следующему занятию: готовые SQL-выборку и статистику, устойчивую сортировку по id и существующую колонку `title_normalized`; поиск по-прежнему предстоит реализовать, JSON остаётся штатным источником.

## 00. Вступление

Сервис уже умеет менять отдельные SQL-записи, а JSON-версия Planner сохраняет привычные фильтр, порядок и статистику. Теперь нужно получить те же результаты запросами к базе, не загружая весь список ради каждого чтения.

1. **Точка старта:** SQL-запросы и `select/scalars` уже применялись; прежние API и сервис задают ожидаемую семантику выборки.
2. **Новый вопрос:** как перенести фильтр, порядок, лимит и подсчёты в SQL так, чтобы результат не изменился?
3. **Результат:** существующие GET-маршруты читают из SQL-репозитория с прежним договором, а JSON-сборка остаётся рабочей до общего переключения.

Сначала восстановим точный смысл старых операций, затем разберём SQL-выражения и их порядок. После этого ученик изменит одну границу хранения и проверит результат через уже существующие сервис и маршруты.

## 01. Прежняя выборка как договор

- Что и зачем объяснить: `select_tasks` принимает `is_done`, `sort_desc` и `limit`; это параметры уже существующей операции, не новый endpoint. Проследить путь `get_selected_tasks → PlannerService.select_tasks → repository.select` и отдельно путь `/stats` через сервис.
- Механизм и порядок: сначала отбираются подходящие задачи, затем результат упорядочивается по id и ограничивается. Публичный ответ остаётся прежним; сервис не должен дублировать логику в HTTP-обработчике.
- Пример и типичная путаница: на небольшом наборе id со смешанным статусом сравнить результат JSON-адаптера и SQL. Наличие выборки не означает, что весь список нужно держать в сервисе или endpoint.
- Переход к следующему шагу: определить, как каждый аргумент выражается в SQL и что означает отсутствие фильтра.

## 02. Необязательный фильтр `is_done`

- Что и зачем объяснить: `WHERE` ограничивает строки до их возврата приложению; значения передаются параметрами выражения.
- Механизм и порядок: `None` означает не добавлять условие по статусу, `False` выбирает открытые задачи, `True` — завершённые. Условие не должно зависеть от истинности самого значения.
- Пример и типичная путаница: проверить одинаковые данные с `None`, `False` и `True`; не спутать отсутствие фильтра с запросом только открытых задач и не собирать SQL строковой конкатенацией.
- Переход к следующему шагу: после фильтрации результату нужен предсказуемый порядок.

## 03. Устойчивый порядок по id

- Что и зачем объяснить: реляционная таблица не обещает порядок строк без явного `ORDER BY`; порядок является частью результата Planner.
- Механизм и порядок: сортировать по `TaskRow.id` по возрастанию либо убыванию в зависимости от `sort_desc`. Идентификатор задаёт однозначный порядок без нового критерия сортировки.
- Пример и типичная путаница: на разреженных id проверить оба направления и связь с прежним `sorted(..., reverse=sort_desc)`. Физический порядок вставки не является гарантией.
- Переход к следующему шагу: ограничение можно применять только к уже отфильтрованному и упорядоченному набору.

## 04. LIMIT и границы двух интерфейсов

- Что и зачем объяснить: `LIMIT` ограничивает количество строк, возвращаемых БД; он не заменяет фильтр и сортировку.
- Механизм и порядок: SQL применяет условие, порядок и затем лимит. В сервисном вызове `limit=None` сохраняет отсутствие ограничения; HTTP отдельно задаёт default 10 и диапазон 1–50.
- Пример и типичная путаница: подобрать данные, где фильтр до лимита отличается от фильтра после лимита; проверить `limit=1`, HTTP-границы 1/50 и прямой вызов сервиса без лимита. Не добавлять offset.
- Переход к следующему шагу: выборка возвращает `Task`, но статистике не нужен список этих объектов.

## 05. Статистика как скалярный агрегат

- Что и зачем объяснить: агрегат вычисляет числа над строками в БД и возвращает скалярные значения вместо набора `Task`.
- Механизм и порядок: разобрать `COUNT` и один ясный способ условного подсчёта через `CASE`/условное выражение. Получить `all`, `open`, `done` в целочисленном виде; пустая таблица должна дать нули. HTTP-слой переводит внутренний ключ `all` в прежнее поле `total`.
- Пример и типичная путаница: сравнить статистику пустой таблицы и набора со смешанным статусом; проверить `open + done == all`. Не считать `len(repository.list())` SQL-агрегатом и не создавать модели для каждой строки.
- Переход к следующему шагу: реализовать оба запроса внутри существующего репозитория и оставить сервис владельцем прикладного договора.

## 06. SQL-репозиторий в существующем пути приложения

- Что и зачем объяснить: `select` и `statistics` — операции границы хранения. Репозиторий возвращает обычные `Task` для выборки и числа для статистики; сервис и FastAPI не содержат SQL.
- Механизм и порядок: для выборки преобразовать строки через существующий mapping до закрытия Session; для чтения не делать commit. Использовать существующие методы сервиса и endpoint, не создавать новые модели ответа или маршруты. Для HTTP-проверки использовать SQL-provider из занятия 88: он собирает репозиторий с Session текущего запроса через `get_db`; подменить `get_planner` на отдельной фикстуре и восстановить overrides после проверки. Не хранить SQL-сервис с одной Session между запросами. JSON остаётся default до занятия 98.
- Пример и типичная путаница: проследить одну строку от SQL-запроса через repository/service к GET-ответу; различить внутренний `all` и внешний `total`. Частичная готовность SQL не даёт оснований менять default на SQL.
- Переход к практике: подготовить изолированную БД с задачами известных id и проверить оба пути чтения на том же договоре.

## 07. Что мы будем делать в практике

**Формат и исходная опора:** изменение существующего Planner на отдельной файловой SQLite-фикстуре; начинаем с подтверждённых SQL CRUD-операций из 90–93 и набора задач с известными id и обоими значениями `is_done`. Рабочий JSON и обычный default не затрагиваем.

1. **Подготовить контрольный набор:** создать через существующий SQL-сервис задачи с разными id и статусами; расположить их так, чтобы при выборе `is_done=False, sort_desc=False, limit=1` первая строка по id не подходила, а следующая подходила. Это обнаружит ошибочный лимит до фильтра. Зафиксировать ожидаемые результаты для обоих направлений и лимитов. Опора — SQL create и Session из 90–93.
2. **Реализовать выборку репозитория:** добавить `select` в существующий SQL-репозиторий, используя условный `WHERE`, `ORDER BY id` и `LIMIT`; вернуть прежние `Task`. Опора — блоки 01–04 и mapping из 84/87.
3. **Проверить сервис и GET:** вызвать прежний сервис для `None`/`False`/`True`, обоих направлений и `limit=None`; проверить существующий GET с SQL-provider через override `get_planner` на отдельной фикстуре, создавая Session на запрос, восстановить overrides и сверить прежний default, границы HTTP-limit и 422 для некорректных query-параметров. Наблюдаемый результат — прежний порядок и состав выбранных задач при прежней HTTP-валидации.
4. **Реализовать статистику репозитория:** получить `all/open/done` агрегатным SQL-запросом и сохранить прежний сервисный результат. Опора — блок 05.
5. **Проверить `/stats` и отсутствие полной загрузки:** проверить пустую базу, смешанный набор и последствия add/done/delete; удостовериться, что HTTP возвращает `total/open/done`, а выборка и подсчёт не вызывают полный `list` для обработки в Python.

Предыдущие занятия дают SQL-выражения, Session, mapping и CRUD для контрольных данных. Теория этого занятия готовит каждый новый механизм до изменения репозитория; проверки используют существующий сервис и GET-маршруты. После практики готова запросная основа для поиска в занятии 95, но SQL-поиск ещё не считается реализованным.
