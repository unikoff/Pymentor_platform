## Место в маршруте

Занятие следует за переносом поиска в SQL и завершает подготовку CLI к общей приёмке в 97. Предыдущий шаг должен оставить полный SQL-репозиторий за прежним PlannerService; здесь меняется владение ресурсом в долгоживущем командном цикле. CLI получает новый SQL-сервис на одну распознанную команду, а не удерживает одну Session, пока ждёт следующие команды. Следующее занятие проверит API и CLI вместе на одной изолированной базе. Обычный запуск приложения до финального переключения в 98 остаётся на JSON.

## Точка B: результат занятия

- Ученик сможет объяснить: почему интерактивный run не должен удерживать одну Session; чем фабрика ресурсного контекста отличается от уже созданного сервиса; почему Session и транзакция имеют разные границы.
- Ученик сможет сделать: передать CLI фабрику контекста, распознавать команду до обращения к БД, выполнять существующий handler внутри отдельного контекста и освобождать Session после команды либо ошибки.
- Результат в проекте: существующие run, execute_command и сборка CLI используют тот же PlannerService и handlers с коротким SQL-ресурсом на команду. Временный JSON-контекст сохраняет штатный запуск до переключения в 98.
- Как подтвердим: последовательность CLI-команд изменяет реальные строки изолированной SQLite; следующая команда читает результат через новую Session. Счётчик или наблюдаемая фикстура подтверждает отдельный ресурс на действие, а неизвестная команда и exit не создают Session.

## Границы и передача дальше

- Пока не требуем: переключение default на SQLite, перенос актуальных пользовательских данных, удаление JSON-backend, новый CLI или команды PUT/PATCH, FastAPI Depends, async, универсальный контейнер ресурсов либо новую систему ошибок. Подробная диагностика отказа БД относится к 100.
- Передаём следующему занятию: полный SQL-сервис и CLI, который получает отдельный ресурс на распознанную команду; оба интерфейса ещё можно проверить на общей тестовой базе до переключения рабочих данных.

## 00. Вступление

CLI остаётся запущенным между командами: он снова показывает меню и ждёт ввод. Если передать этому циклу SQL-сервис, связанный с одной Session, ресурс проживёт дольше отдельного действия и может оказаться закрытым или устаревшим к следующему обращению. При этом пересобирать Planner и его handlers не нужно: достаточно изменить границу, на которой CLI получает сервис.

1. **Точка старта:** существующий CLI вызывает один PlannerService, а SQL-контекст на короткий вызов уже подготовлен в занятии 88.
2. **Новый вопрос:** как выдавать сервис только распознанной команде и не открывать Session на время всего меню?
3. **Результат:** знакомые команды работают через общий сервис, но каждая SQL-команда получает собственную Session; обычный запуск пока остаётся JSON.

Эти пункты связывают длительный цикл интерфейса с коротким действием хранения. Сначала разберём границы ресурса и транзакции, затем изменим передачу сервиса и проверим результат на изолированной базе.

## 01. Долгий цикл CLI и короткое действие

- Что и зачем объяснить: run многократно показывает меню, читает команду и передаёт её диспетчеру. Session принадлежит одному действию, а не процессу CLI; иначе она будет простаивать во время ожидания следующих команд.
- Механизм и порядок: различить долговечные Engine и SessionFactory, которые можно переиспользовать, и создаваемую из фабрики Session. Внутри короткого действия сервис использует репозиторий; после выхода из ресурсной области Session закрывается. Транзакция начинается при операции сервиса, а не автоматически на всё время существования Session.
- Пример и типичная путаница: короткий опыт с несколькими последовательными вызовами фабрики показывает разные Session при общей фабрике. Не приравнивать закрытие Session к commit и не создавать новую Engine на каждую команду.
- Переход к следующему шагу: чтобы выдать ресурс только нужной команде, CLI должен принимать способ создать ресурс, а не один готовый SQL-сервис.

## 02. Фабрика ресурсного контекста

- Что и зачем объяснить: известный contextmanager может ограничить один вызов так же, как with ограничивает ресурс. Фабрика вызывается повторно и при каждом входе строит сервис поверх новой Session.
- Механизм и порядок: показать связи SessionFactory → Session → SqlTaskRepository → PlannerService. Контекст выдаёт сервис вызывающему коду и в finally закрывает Session; исключение проходит наружу. Commit остаётся в транзакционном сценарии сервиса, контекст не подтверждает запись самостоятельно.
- Пример и типичная путаница: независимый пример с двумя входами в контекст и двумя идентификаторами Session. Не возвращать наружу ORM-строку, зависящую от закрытого ресурса, и не хранить один сервис в замыкании для всех входов.
- Переход к следующему шагу: фабрика готова, но диспетчер должен сначала выяснить, есть ли для ввода предметная команда.

## 03. Распознавание до открытия ресурса

- Что и зачем объяснить: exit завершает цикл, неизвестная команда только сообщает об ошибке ввода, а известная команда вызывает существующий handler. Ни выход, ни ошибка распознавания не нуждаются в базе.
- Механизм и порядок: run передаёт фабрику контекста в существующий путь execute_command. Диспетчер сохраняет нормализацию и COMMAND_HANDLERS, проверяет exit и наличие handler, а затем открывает ресурс для вызова выбранного handler. Не дублировать таблицу команд. Ввод аргументов конкретной команды остаётся частью её handler; транзакционная операция начинается позднее, при вызове сервиса.
- Пример и типичная путаница: сравнить подсчёт созданных Session при list, неизвестной команде и exit. Session может быть открыта для распознанной команды, пока handler собирает её аргументы, но транзакцию не следует открывать на ожидание всего следующего меню.
- Переход к следующему шагу: после входа в handler результат действия и сообщение CLI должны оставаться согласованными.

## 04. Завершение команды, ошибка и сообщение

- Что и зачем объяснить: пользовательское сообщение об успехе подтверждает успешно завершившийся вызов сервиса, а не только то, что handler был запущен. Ошибка внутри контекста также должна приводить к освобождению Session.
- Механизм и порядок: проследить вход в контекст, вызов существующего метода сервиса, выход из него и закрытие ресурса. Транзакционный результат подтверждается прежней областью сервиса; менеджер ресурса не добавляет поздний commit. Сохранить имеющиеся валидацию, обработку известных ошибок и тексты CLI.
- Пример и типичная путаница: контролируемая ошибка операции должна закрыть Session и не выводить сообщение об успешном изменении. Не добавлять широкий except, ложный успех или новое преобразование всех SQL-ошибок: классификация отказов рассматривается в 100.
- Переход к следующему шагу: новая область ресурса требует обновить контракт самого run и его потребителей.

## 05. Контракт run и прежний JSON-запуск

- Что и зачем объяснить: старый run возвращал переданный ему service, пригодный для повторного использования. В SQL-пути такой возврат мог бы отдать сервис, привязанный к уже закрытой Session.
- Механизм и порядок: передавать в run фабрику контекста; после каждой команды выходить из контекста; при завершении run не возвращать SQL-сервис с закрытым ресурсом. Обновить тесты и потребителей нового контракта, не оставляя параллельный legacy-run.
- Пример и типичная путаница: JSON-контекст может выдавать сервис, собранный через прежнюю build_service для того же настроенного JSON-файла. Он поддерживает штатный main до 98 и не становится пользовательским backend-флагом. Не создавать второй файл данных ради теста совместимости.
- Переход к следующему шагу: обе ресурсные области готовы; теперь проверяется один и тот же командный маршрут на SQL и прежнем JSON.

## 06. Изолированная проверка CLI-пути

- Что и зачем объяснить: пользовательский run проверяет переходы меню, а SQLite-fixture и учёт Session проверяют сохранение между командами и короткую жизнь ресурса. Одного успешного вывода недостаточно, чтобы доказать запись.
- Механизм и порядок: существующая схема и SessionFactory подключаются к отдельной файловой SQLite. SQL-контекст открывает новую Session на предметную команду; новая Session следующей команды читает подтверждённое изменение. Для прежнего запуска отдельный контекст строится на том же временном JSON-пути.
- Пример и типичная путаница: пройти add → list → find → done → stats → search → delete и повторное чтение. Не использовать один подготовленный список вместо репозитория и не менять рабочий DATABASE_URL или JSON.
- Переход к следующему шагу: результаты изолированного пути задают практическую переработку run без переключения приложения.

## 07. Что мы будем делать в практике

**Формат и исходная опора:** проектная работа в существующих app/cli.py и app/main.py. Используем знакомые COMMAND_HANDLERS, execute_command, чтение/вывод через переданные функции, SessionFactory, SQL-контекст из 88 и полный SQL-сервис из 90–95. Последняя зависимость пока не подтверждена журналом обучения и должна быть проверена до выполнения зависимой части.

Общий результат — тот же интерактивный Planner с областью SQL-ресурса на распознанную команду и прежним JSON-default до занятия 98.

1. **Изменить передачу сервиса между main.py и run:** передавать фабрику ресурсного контекста вместо одной Session-bound службы; run завершает цикл без возврата закрытого SQL-сервиса. Наблюдаемый результат — обработчики продолжают работать через прежний PlannerService и без второго CLI-механизма; опора на блоки 01–02 и 05.
2. **Связать распознанную команду с контекстом в существующем диспетчере:** для известной команды открыть контекст, вызвать существующий handler и закрыть ресурс при успехе или исключении; exit и неизвестный ввод обработать до открытия Session. Наблюдаемый результат — счётчик Session меняется только для предметных команд; опора на блоки 02–04.
3. **Выполнить полный командный сценарий на изолированной SQLite:** через внедрённые read/write пройти добавление, чтение, поиск, завершение, статистику и удаление. Наблюдаемый результат — каждая следующая команда через новую Session видит предыдущее подтверждённое состояние, а сообщения и правила команд не изменились; опора на блоки 03–04 и подтверждённый SQL-договор 90–95.
4. **Проверить границы и отказ:** отдельно пройти повторное done, неизвестный id, ошибочный ввод, неизвестную команду и exit; сравнить число открытых/закрытых Session и отсутствие ложного сообщения об успехе. Наблюдаемый результат — контекст освобождается, незатронутые данные сохранены, неизвестная команда и exit не обращаются к БД; опора на блоки 01, 03–04 и прежние навыки проверки CLI.
5. **Сохранить переходный JSON-run:** прогнать привычные команды через временный JSON-контекст, не переключая обычный default и не используя рабочие данные. Наблюдаемый результат — существующий источник и поведение API/CLI остаются прежними до отдельного переключения в 98; опора на блок 05 и прежний навык изоляции через временный путь.

Блоки 01–05 подготавливают изменение жизненного цикла и контракта run; блок 06 задаёт проверяемый SQL-сценарий. Успех SQL-практики нельзя утверждать без принятой реализации полного SQL-репозитория из 90–95. После её подтверждения результаты 96 передаются в 97 для совместной приёмки API и CLI на одной тестовой базе. Обычный запуск и JSON-данные в этой практике не переключаются.
