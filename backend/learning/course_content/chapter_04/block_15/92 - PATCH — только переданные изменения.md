# 92. PATCH: только переданные изменения

> Тип документа: внутренний план занятия, этап 2

## Место в маршруте

После SQL-создания в занятии 90 и замены через PUT в 91 существующий PATCH должен начать сохранять частичные изменения в SQL. Меняется реализация репозитория за прежним сервисом и HTTP-маршрутом; договор API и обычная JSON-сборка пока сохраняются. В 93 к тому же SQL-пути добавятся завершение и удаление.

## Точка A: подтверждённая опора

- Уже изучено: HTTP PATCH передаёт только выбранные поля. TaskPatch и преобразование model_dump(exclude_unset=True, exclude_none=True) отличают пропуск и null от False. Предметный PlannerService.patch_task строит новую Task из текущего состояния, сохраняет id и копию tags, а пустое изменение не вызывает запись. Ученик знаком с ORM-строкой, Session, mapping в обычную Task, SQL-чтением и отдельной ресурсной областью.
- Состояние проекта: по журналу и HEAD StudyHub подтверждены занятия по 89 включительно. API и CLI штатно используют JSON; SQL-репозиторий читает список и задачу, отдельный импорт переносит копию. PlannerService.patch_task и JSON-реализация PATCH уже существуют, SQL update ещё не реализован. В текущем рабочем дереве StudyHub модуль SQL-репозитория перемещается; практику привязать к месту класса SqlTaskRepository после завершения предыдущих занятий.
- Планируемая опора или неясность: концепт задаёт создание в 90 и SQL PUT в 91, однако их результат пока не подтверждён ни журналом, ни checkpoint. До выдачи практики нужно подтвердить SQL-запись, общую транзакционную область сервиса и адрес репозитория после этих изменений. Без этого не подтверждены предпосылки реализации PATCH; не считать их изученными только по концепту.

## Точка B: результат занятия

- Ученик сможет объяснить: как HTTP payload превращается в частичное изменение, почему False нужно применять, а пропущенное поле и null — игнорировать, и почему пустой PATCH всё равно проверяет существование id.
- Ученик сможет сделать: реализовать операцию update в существующем SqlTaskRepository и подключить её к прежнему PlannerService.patch_task, сохранив значения полей, которые не пришли в PATCH.
- Результат в проекте: существующий PATCH работает с SQL-репозиторием на отдельной тестовой базе. Штатные API и CLI по-прежнему используют JSON до общего переключения в занятии 98.
- Как подтвердим: существующий HTTP-маршрут возвращает прежний ответ; независимая Session видит изменённую задачу. Проверены отдельные поля, is_done=False, пропуск/null, пустое изменение, неизвестный id, неверный ввод, сохранность id и tags, согласованность title_normalized и сценарии PATCH вместе с PUT.

## Границы и передача дальше

- Пока не требуем: очистку поля через null, новый merge-patch протокол, редактирование tags по HTTP, новый маршрут done, полный SQL CRUD, поиск/статистику запросами и переключение рабочего backend.
- Передаём следующему занятию: проверенный SQL PATCH, который меняет только разрешённые переданные поля и оставляет задачу доступной как обычную Task; занятие 93 применит существующее предметное поведение для завершения и удаления.

## 00. Вступление

В прошлых занятиях мы научились сохранять задачу целиком и читать её из базы. Теперь нужно изменить только один выбранный признак и не затронуть остальные данные.

1. **Точка старта:** сервис уже умеет трактовать PATCH поверх JSON, а SQL-репозиторий — находить и возвращать обычную Task.
2. **Новый вопрос:** как перенести частичное изменение на SQL, чтобы False не потерялся, пустой PATCH не менял строку, а непереданные значения сохранились?
3. **Результат:** прежний маршрут PATCH работает с SQL-репозиторием и подтверждает изменение после завершения транзакции.

Сначала восстановим смысл входного payload, затем проследим построение нового состояния и адресную запись строки. После этого проверим результат через новый ресурс и убедимся, что соседние данные и прежний HTTP-договор остались прежними.

## 01. PATCH передаёт изменения, а не новую полную задачу

- Что и зачем объяснить: PATCH использует существующую схему и маршрут. Разобрать путь от полей body к словарю изменений, который роутер передаёт сервису.
- Механизм и порядок: exclude_unset убирает непереданные поля; exclude_none убирает явные null; переданный False остаётся. Эти правила уже применяются в API и не должны заново проектироваться для SQL.
- Пример и типичная путаница: в payload {} нет изменений; в payload с is_done=False есть реальное изменение. Не проверять булево значение через truthiness и не принимать пропуск за False.
- Переход к следующему шагу: словарь изменений нужно наложить на сохранённое состояние, а не превратить в новую задачу с default-значениями.

## 02. Сначала получить текущее предметное состояние

- Что и зачем объяснить: PATCH не несёт полного представления задачи, поэтому основой служит существующая Task, полученная по id.
- Механизм и порядок: сервис сначала проверяет id и получает текущую задачу, затем строит проверенную задачу из старых значений и только переданных ненулевых изменений. Валидация Task выполняется до изменения SQL-строки.
- Пример и типичная путаница: изменение только priority сохраняет title, is_done и tags; переданный False заменяет прежнее True. Не создавать состояние только из полей payload.
- Переход к следующему шагу: полная проверенная Task поступает в репозиторий для адресного сохранения.

## 03. Реализовать update на границе SQL-репозитория

- Что и зачем объяснить: сервис сохраняет предметный сценарий, а SQL-репозиторий отвечает за запись переданной задачи в строку с тем же id.
- Механизм и порядок: использовать текущую Session и ORM-модель; найти выбранную строку, перенести в неё проверенные значения и вернуть обычную Task по уже принятому mapping-контракту. Отсутствующая строка сохраняет договор None для репозитория и прежнюю предметную ошибку выше по слою.
- Пример и типичная путаница: обновить выбранную строку, а не загружать и сохранять всю таблицу. Репозиторий не закрывает переданную Session и не подтверждает транзакцию самостоятельно.
- Переход к следующему шагу: изменение строки должно входить в общую область записи, установленную в предыдущем SQL-занятии.

## 04. Связать чтение, проверку и запись одной транзакцией

- Что и зачем объяснить: успешный HTTP-ответ должен означать, что запись уже подтверждена; открытая Session или успешный flush этого ещё не доказывают.
- Механизм и порядок: применить существующую область изменения сервиса до чтения текущей строки, выполнить предметную проверку и SQL-запись в ней, дождаться её успешного завершения до возврата ответа. Репозиторий не делает отдельный commit.
- Пример и типичная путаница: исключение до commit не оставляет частичное PATCH; выход ресурса и commit — разные обязанности. Не переносить подтверждение записи в yield-очистку зависимости.
- Переход к следующему шагу: вместе с пользовательскими полями нужно правильно поддержать связанные данные строки.

## 05. Сохранить tags и производное поле заголовка

- Что и зачем объяснить: SQL-модель содержит внутренние tags и title_normalized, которых нет в публичном PATCH-body.
- Механизм и порядок: сервисная задача сохраняет существующий список тегов; репозиторий не заменяет его данными из HTTP. При изменении title обновляется техническое значение по тому же Python lower(), что используется остальным проектом; при изменении другого поля оно остаётся согласованным.
- Пример и типичная путаница: изменение is_done не должно очищать теги или менять поисковый заголовок. Не добавлять tags в схему запроса и не путать JSON-колонку тегов с файловым JSON-хранилищем.
- Переход к следующему шагу: теперь можно проверить не только код ответа, но и полное состояние после нового чтения.

## 06. Различить запись, no-op и отказ

- Что и зачем объяснить: одинаковый ответ на PATCH сам по себе не доказывает, что нужное состояние сохранено или что пустое действие ничего не записало.
- Механизм и порядок: отдельно рассмотреть изменение одного поля, несколько полей, False, пустой payload, только null, неизвестный id и невалидное значение. Пустое изменение сначала подтверждает наличие задачи и возвращает её текущую версию без SQL UPDATE.
- Пример и типичная путаница: пустой PATCH существующего id — допустимый no-op; пустой PATCH неизвестного id по-прежнему приводит к 404. Ошибка валидации/записи не должна менять данные.
- Переход к следующему шагу: проверять результат новой Session и повторное чтение, а не только объект из текущего identity map.

## 07. Что мы будем делать в практике

**Формат и исходная опора:** изменение существующего Planner на отдельной файловой SQLite-fixture; начинаем с готовых SQL create/PUT, SqlTaskRepository.list/get и прежнего PATCH в сервисе. Создаём SQL-путь частичного обновления, не новый endpoint или второй сервис.

1. **Дополнить SqlTaskRepository.update:** адресно сохранить переданную валидную Task в существующую ORM-строку и вернуть результат в прежнем mapping-контракте; опора — блок 03 и SQL-чтение из блока 14.
2. **Провести PATCH через существующий сервис и область записи:** оставить схему, маршрут и публичные ответы прежними; опора — блоки 01–04 и реализация сервиса из прежних занятий.
3. **Проверить одиночные изменения:** отдельно обновить title, priority и is_done=False, после каждого изменения сравнить полную задачу в новой Session; опора — блоки 02, 03 и 05.
4. **Проверить no-op и ошибочные входы:** отправить пустой payload, только null и сочетание null с False; проверить известный/неизвестный id, неверный title/priority и отсутствие побочной записи; опора — блоки 01, 02 и 06.
5. **Сверить связанные данные и соседние сценарии:** убедиться, что id, tags, title_normalized и непереданные поля согласованы, затем выполнить PUT → PATCH и PATCH → PUT и перечитать результат; опора — блоки 03, 05, 06 и подтверждённый результат занятия 91.
6. **Подтвердить границу продукта:** пройти существующий HTTP PATCH через SQL-провайдер теста, восстановить overrides, проверить прежний JSON-сценарий после этого; убедиться, что основная API/CLI-сборка и рабочие данные остаются JSON до занятия 98; опора — блоки 04, 06 и практика занятия 88.

Блоки 01–02 подготавливают преобразование PATCH в предметное состояние; 03–05 — адресную SQL-запись в общей транзакции с сохранением внутренних данных; 06 — доказательства для успеха, no-op и отказа. Занятие 91 должно быть реально завершено до проверки совместных PUT/PATCH сценариев. Для проекта прежние API/CLI-сценарии продолжают работать, а штатное хранение пока не переключается.
