## Точка B: результат занятия

- Ученик сможет объяснить: как SQLite назначает целочисленный primary key при вставке без id; почему явные id при импорте отличаются от обычного создания; почему нельзя подменять назначение базы выражением max(id) + 1; чем flush отличается от commit и как сервис задаёт границу всей операции.
- Ученик сможет сделать: провести существующий сценарий add_task через SQL-реализацию create, используя прежнюю валидацию и договор репозитория; вернуть предметную Task с реальным id и проверить её отдельной Session.
- Результат в проекте: Существующий SqlTaskRepository расположен в целевом app/DBase/repositories.py (при необходимости класс переносится туда без дублирования) и реализует create с title, priority, is_done=False, отдельными tags и title_normalized. Сервис охватывает действие переданной фабрикой write_scope; SQL-сборка связывает её с Session.begin, временная JSON-сборка сохраняет прежний путь через nullcontext. Репозиторий не делает commit/close. Штатный default API и CLI остаётся JSON.
- Как подтвердим: прежний POST с SQL-provider на изолированной файловой базе отвечает 201 и прежними четырьмя полями; новая Session читает запись и все пять предметных полей вместе с техническим title_normalized. Проверены положительные реальные id, tags при прямом вызове сервиса, отказ до commit без строки и сохранность JSON default.

## 00. Вступление

У Planner уже есть рабочее добавление задачи и отдельно подготовлен SQL-путь чтения. Теперь нужно соединить их так, чтобы базу использовал тот же продукт, сервер назначал id, а HTTP подтверждал успех только после сохранения.

1. **Точка старта:** существующий POST проходит через PlannerService.add_task; JSON-репозиторий создаёт задачи, SQL-репозиторий пока читает список и id.
2. **Новый вопрос:** как получить настоящий id от SQLite и сохранить новую запись как целую операцию, если проверка или запись завершается ошибкой?
3. **Результат:** тот же POST можно направить через тестовую подмену на SQL create и независимо подтвердить его результат, не переключая приложение с JSON.

Сначала восстановим путь и прежние правила создания, затем разберём назначение ключа и жизненный цикл записи. После этого свяжем валидацию, репозиторий и границу транзакции, чтобы проверить результат на временной базе и оставить штатную сборку нетронутой.

## 01. Прежний сценарий добавления и его контракт

- Что и зачем объяснить: TaskCreate, PlannerService.add_task, repository.create и TaskRead уже образуют одну цепочку. Разделить вход HTTP, предметную задачу и строку БД; показать, что изменяется в persistence-слое, а что остаётся прежним.
- Механизм и порядок: клиент передаёт обязательные title и priority; TaskCreate проверяет HTTP-ограничения; сервис сохраняет прежнюю предметную валидацию; создание задаёт is_done=False, не принимает id от клиента и не добавляет tags в публичный ответ. Прямой вызов сервиса может передать существующие внутренние tags.
- Пример и типичная путаница: Task.priority имеет предметный default, но это не делает поле необязательным в уже существующей HTTP-схеме. Совпадающие названия раньше разрешены; SQL-переход не добавляет уникальность.
- Переход к следующему шагу: контракт определяет, какие данные должны попасть в таблицу, а id остаётся ответственностью источника хранения.

## 02. Primary key и назначение серверного id

- Что и зачем объяснить: первичный ключ адресует строку, а SQLite назначает значение целочисленного INTEGER PRIMARY KEY, когда обычная вставка не передаёт id. Импорт исторических записей с их явными id — отдельная операция с другими входными условиями.
- Механизм и порядок: сопоставить новую строку без id с импортированной строкой, где id сохранён намеренно; пояснить, что база выдаёт положительный ключ, не обещая непрерывности последовательности. Конфликт с уже имеющимися id недопустим.
- Пример и типичная путаница: max(id)+1 требует лишнего чтения и сам по себе не защищает от параллельной вставки. AUTOINCREMENT и запрет повторного использования удалённого номера не были договором Planner и не вводятся.
- Переход к следующему шагу: репозиторий должен вставить подготовленные значения без фиктивного id, получить назначенный ключ и только тогда материализовать Task.

## 03. Валидация до записи и предметная Task после flush

- Что и зачем объяснить: Task требует целый id в конструкторе, поэтому нельзя сначала создать заглушку с id=0 ради проверки остальных полей. Уже существующие валидаторы позволяют проверить title, priority и tags до вставки.
- Механизм и порядок: до изменения БД нормализовать и проверить предметные входы теми же правилами, что применяет модель; сформировать TaskRow с is_done=False и вычисленным title_normalized; не применять к прямым CLI/сервисным данным HTTP-лимит, которого предметный валидатор не устанавливает.
- Пример и типичная путаница: отбрасывание tags или повторное применение иной нормализации создаёт расхождение с JSON. Техническая колонка поиска не становится полем Task/TaskRead.
- Переход к следующему шагу: для получения настоящего id ORM должен отправить INSERT, но это пока ещё не означает подтверждённую запись.

## 04. INSERT, flush и создание результата

- Что и зачем объяснить: Session.add ставит ORM-строку под наблюдение, flush отправляет INSERT в текущую транзакцию и позволяет прочитать выданный базой id. Commit подтверждает транзакцию; до него результат может быть отменён.
- Механизм и порядок: создать TaskRow без назначенного id, выполнить flush, затем преобразовать строку в обычную Task с реальным id и копией tags. Материализовать результат, пока Session доступна, не возвращать ORM-объект наружу.
- Пример и типичная путаница: наличие id после flush доказывает INSERT в незавершённой транзакции, а не сохранение для другой Session. Формирование ответа до завершения транзакционного контекста может сообщить ложный успех.
- Переход к следующему шагу: чтобы commit/rollback охватывал всё действие, транзакцию должен владеть один понятный слой.

## 05. Область изменения принадлежит сервисному сценарию

- Что и зачем объяснить: отдельные методы репозитория составляют один предметный сценарий; репозиторий выполняет операции и flush, но не подтверждает части сценария и не закрывает переданную Session.
- Механизм и порядок: передать в PlannerService небольшой write_scope; сервис входит в контекст до работы с SQL и выходит только после готовой предметной операции. SQL-сборка связывает контекст с Session.begin: нормальный выход подтверждает операцию, исключение до подтверждения откатывает её. Для прежней JSON-сборки допустим nullcontext, который сохраняет совместимость и не изображает транзакцию.
- Пример и типичная путаница: get_db освобождает Session после запроса, но не должен служить запоздалым местом commit после ответа. flush внутри репозитория не является commit; общая архитектура Unit of Work здесь не нужна.
- Переход к следующему шагу: после этой границы можно подменить только готовый provider в POST-тесте, сохранив default приложения.

## 06. SQL-provider, прежний POST и независимое чтение

- Что и зачем объяснить: dependency override направляет существующий маршрут на подготовленную SQL-сборку и временную Session, не создавая новый endpoint и не меняя обычный backend.
- Механизм и порядок: связать тестовый provider с изолированной файловой SQLite, готовыми TaskRow/SessionFactory и SQL-репозиторием; восстановить overrides после сценария. Ответ HTTP проверять отдельно от сохранённого внутреннего состояния.
- Пример и типичная путаница: неполные SQL-методы не получают JSON-fallback. POST без priority по-прежнему отклоняется; отсутствие SQL PUT или статистики не повод включать SQL-сервис во всю сборку.
- Переход к следующему шагу: одного ответа 201 недостаточно — запись надо перечитать новым ресурсом и проверить, что отказ не оставил строки.

## 07. Доказательство успеха и граница занятия

- Что и зачем объяснить: проверка должна отличить ответ обработчика от устойчивого состояния, а новый id — от подставленного значения.
- Механизм и порядок: после запроса создать независимую Session и прочитать запись через готовый SQL get; сверить id, предметные поля, tags и title_normalized. Отдельно проверить контролируемый отказ до commit, старые JSON-сценарии и взаимодействие с импортированными id.
- Пример и типичная путаница: одинаковое число строк не подтверждает их содержимое; успешный SQL POST на fixture не означает переключение API/CLI.
- Переход к практике: ученик знает все звенья создания и может изменить ровно один путь хранения, оставив остальные возможности на текущем default.

## 08. Что мы будем делать в практике

**Формат и исходная опора:** переработка существующего StudyHub Planner; исходный контракт add_task/POST и SQL list/get на локальной контрольной точке после 89. Проверки работают на отдельной файловой SQLite; обычные API и CLI остаются на JSON.

Общий результат: существующий сценарий добавления умеет работать через SQL-подмену, возвращает предметную задачу после подтверждённой записи и не меняет публичный контракт или штатное хранилище.

1. **Выровняем расположение SQL-репозитория:** при необходимости перенесём существующий SqlTaskRepository в app/DBase/repositories.py, сохранив там list/get и не создавая второй класс; проверим, что обе операции чтения доступны по одному пути. Опора: изученные границы репозитория из 85–87 и расхождение точки A.
2. **Добавим создание в SQL-репозиторий и сервисный сценарий:** передадим проверенные title, priority и tags, сохраним is_done=False и title_normalized, получим id от БД через flush и вернём обычную Task после выхода из write_scope. Опора: блоки 01–05 и прежний add_task.
3. **Проверим создание существующим POST на изолированной базе:** применим узкий SQL-provider override и убедимся, что ответ остаётся 201 с четырьмя прежними полями; прямой сервисный вызов дополнительно сохраняет внутренние tags. Опора: блок 06 и знакомые overrides.
4. **Подтвердим данные и правила:** прочитаем запись новой Session, сверим все предметные поля, служебный заголовок, положительный id и отсутствие конфликта после тестового импорта; проверим обязательность priority, прежнюю валидацию и допустимость одинаковых title. Опора: блоки 02–04 и навыки 78–89.
5. **Проверим отказ и сохранность прежнего пути:** смоделируем ошибку до commit и подтвердим отсутствие строки/успешного ответа; восстановим overrides и проверим, что штатная JSON-сборка и прежние сценарии работают. Опора: блоки 05–07 и изученные rollback/resource.

Блоки 01–04 подготавливают правила и механику вставки; 05 объясняет владельца commit/rollback; 06–07 готовят изоляцию и независимое доказательство. Изменяются расположение уже изученного SQL-репозитория (только если требуется) и путь SQL create для существующего продукта. SQL replace/update/delete/select/search/statistics, CLI-переключение и рабочий default остаются будущими шагами.
