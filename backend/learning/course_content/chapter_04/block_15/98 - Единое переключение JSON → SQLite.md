# 98. Переход на SQLite

## Место в маршруте

Занятие завершает переход от JSON к SQLite, подготовленный в занятиях 80–97. В 89 импорт уже проверялся как отдельная репетиция на копии; теперь переносится актуальный снимок, после остановки записей в JSON. API и CLI переключаются вместе и используют одну базу. Следующее занятие 99 удалит неиспользуемый переходный код, поэтому здесь его не очищаем.

Соседние планы 97 и 99 и TSX-занятия пока содержат только заготовки. Связность проверена по паспортам 97–99 в концепте; готовые соседние занятия для проверки передачи результата недоступны.

## Точка A: подтверждённая опора

- Уже изучено: к занятию 89 подтверждены работа с постоянным JSON-хранилищем, предметная модель `Task` с внутренними `tags`, SQLAlchemy Engine/ORM/Session, mapping, транзакционная отмена, ресурс на запрос/команду и отдельный импорт проверенного JSON-снимка. Импорт в 89 был репетицией на копии, а не переключением приложения.
- Состояние проекта: контрольная версия `StudyHub` с коммитом `22d0229` сохраняет штатные API и CLI на JSON; импортёр существует отдельно. Обычные интерфейсы ещё не переключены на SQLite. Незакоммиченные изменения рабочей копии не считаю принятым результатом следующих занятий.
- Планируемая опора или неясность: концепт требует принять занятие 97 до начала 98, но доступный `STUDYHUB_LEARNINGS.md` и `HEAD` подтверждают только занятие 89. Поэтому B97 и наличие готового SQL-пути для всех операций здесь не подтверждены. Перед практикой нужно сверить актуальный проект с критериями 97; если допуск не пройден, переключение не выполнять и вернуть недостающий сценарий на доработку в рамках 97.

## Точка B: результат занятия

- Ученик сможет объяснить: чем репетиционный импорт отличается от переноса окончательного снимка; почему перед снимком останавливают все записи; когда старый JSON перестаёт быть безопасным источником восстановления.
- Ученик сможет сделать: сохранить и проверить актуальную копию JSON, перенести её в подготовленную пустую SQLite-базу одной транзакцией, сверить все предметные данные и согласованно переключить штатные сборки API и CLI.
- Результат в проекте: оба интерфейса используют один `DATABASE_URL` и SQL-репозиторий. Старый JSON-файл остаётся архивом; переходный код пока может лежать в проекте без активных потребителей.
- Как подтвердим: API создаёт задачу, CLI находит и завершает её, новый API-запрос читает обновлённое состояние; после нового запуска результат сохраняется. Исторические `id`, `title`, `priority`, `is_done`, `tags` и технический `title_normalized` совпадают с проверенным снимком; новые действия не меняют JSON-файл.

## Границы и передача дальше

- Пока не требуем: заново писать CRUD, репозиторий, зависимости или импортёр; менять HTTP-маршруты, схемы, команды и смысл операций; менять схему БД, вводить Alembic, автоматически удалять непустую цель или синхронизировать JSON и SQLite. Старые классы и настройки хранения не удаляем — это работа 99.
- Передаём следующему занятию: уже работающий DB Planner с точными данными и обеими штатными сборками на SQLite; остаточные JSON-адаптеры и неиспользуемые настройки можно находить и удалять после проверки потребителей.

## 00. Вступление

В 89 база получила проверенную копию задач, но рабочий Planner продолжил читать и изменять JSON. С тех пор исходный файл мог измениться, поэтому прежняя репетиционная база не доказывает, что переносит актуальные данные. Теперь нужно согласовать момент остановки записей, сам перенос и переключение двух интерфейсов.

1. **Точка старта:** приложение хранит задачи в JSON; импортёр и SQL-путь подготовлены раньше, если подтверждён допуск 97.
2. **Новый вопрос:** как сменить источник данных так, чтобы API и CLI увидели один актуальный набор без окна, где они записывают в разные хранилища?
3. **Результат:** перенести последний проверенный снимок и направить обе штатные сборки на одну SQLite-базу.

Это один переход состояния приложения. Сначала обеспечиваем неизменность исходных данных и проверяем перенос, затем переключаем владельцев ресурсов и проверяем общую работу. Удаление старой реализации оставляем следующему занятию.

## 01. Репетиция и окончательный снимок — разные источники

- Что и зачем объяснить: пробная база из 89 проверяла инструмент переноса, но не обновлялась вместе с рабочим JSON. Для cutover авторитетен текущий JSON непосредственно перед остановкой записей.
- Механизм и порядок: отделить тестовую копию от источника истины; назвать источник окончательного снимка и момент его создания; не использовать результаты вчерашней репетиции вместо актуальных данных.
- Пример и типичная путаница: две копии файла — импортированная вчера и рабочая сегодня. Одинаковое число строк не доказывает совпадение записей.
- Переход к следующему шагу: актуальность можно сохранить только после остановки всех писателей.

## 02. Остановка записей, резервная копия и явные адреса

- Что и зачем объяснить: пока API или CLI могут писать в JSON, снимок может устареть уже во время переноса. До запуска нужно понимать, какой файл является источником и какая пустая база — целью.
- Механизм и порядок: остановить оба интерфейса; убедиться, что писатели завершены; сделать отдельную копию JSON и записать её происхождение; проверить адрес SQLite и наличие ожидаемой исходной схемы. Непустая цель или несовместимая схема означают остановку и выяснение причины, а не очистку.
- Пример и типичная путаница: адрес из другой рабочей папки может указать на другую SQLite. Нельзя считать базу пустой по имени файла или создавать её поверх неизвестных данных.
- Переход к следующему шагу: только подтверждённая пара «снимок → пустая подготовленная цель» допускается к импорту.

## 03. Импорт и доказательство сохранности данных

- Что и зачем объяснить: число перенесённых строк показывает объём, но не сохранность набора. Значения `tags` важны, хотя HTTP-схема их не выдаёт; `title_normalized` — служебное представление для поиска.
- Механизм и порядок: повторно использовать готовый импортёр; проверка источника должна предшествовать записи, а вставка полного снимка — оставаться одной транзакцией. После импорта новой Session сравнить набор `id` и каждую запись по `title`, `priority`, `is_done`, `tags`; отдельно проверить `title_normalized`.
- Пример и типичная путаница: одинаковые `id` или число строк при отличающемся `tags` не означают точный перенос. Старый допустимый формат без `tags` сохраняет установленный смысл пустого списка; не вводить новый HTTP-лимит для исторических записей.
- Переход к следующему шагу: после проверки переноса можно менять сборки, не смешивая её с работой импортёра.

## 04. Одновременное переключение API и CLI

- Что и зачем объяснить: смена только одного интерфейса создаёт два источника истины. API получает SQL-сервис с Session на запрос, CLI — контекст с Session на команду; общими являются настройки и фабрика, а не живой Session.
- Механизм и порядок: направить существующий API provider и CLI default на общий SQL-путь и тот же `DATABASE_URL`; сохранить текущие `build_service`, маршруты, схемы, команды, selection и preferences. В `app.state` можно хранить настройки или фабрику, но не сервис, привязанный к Session, для будущих запросов.
- Пример и типичная путаница: два разных краткоживущих ресурса могут обращаться к одной базе; один общий адрес не требует общей Session. Не оставлять JSON-сборку активным default ни в одном интерфейсе.
- Переход к следующему шагу: смена считается рабочей, когда оба входа читают изменения друг друга через новые ресурсы.

## 05. Проверка на новых ресурсах и запусках

- Что и зачем объяснить: объект, прочитанный старой Session, не доказывает, что новая сборка или процесс видит commit. Успешный ответ на запись должен следовать за подтверждением SQL-сценария.
- Механизм и порядок: провести короткий сквозной сценарий через реальные API и CLI-точки входа; повторно читать через новый запрос/команду и после нового запуска. Убедиться, что прежний JSON остаётся неизменным, а используемый путь не включает fallback.
- Пример и типичная путаница: выполнение теста на изолированной копии доказывает готовность, но не переключение штатных сборок. Один объект в памяти не заменяет повторное чтение базы.
- Переход к следующему шагу: после первой новой SQL-записи меняется допустимый путь восстановления.

## 06. Граница восстановления и следующий шаг

- Что и зачем объяснить: архив JSON отражает состояние до переключения. После новых записей в SQLite его простое повторное включение потеряет эти изменения; автоматической синхронизации между источниками нет.
- Механизм и порядок: до первой записи в SQLite можно остановить незавершённую процедуру, сохранив исходный архив и выяснив причину. После появления новых SQL-изменений нельзя объявлять старый JSON актуальным; отдельная процедура восстановления потребовала бы согласования и переноса новых данных, она не входит в этот урок.
- Пример и типичная путаница: «вернуть прежний `JSON_PATH`» не является откатом уже подтверждённых записей.
- Переход к следующему шагу: остаточные классы можно удалить в 99 только после проверки, что runtime-потребителей у них больше нет.

## 07. Что мы будем делать в практике

**Формат и исходная опора:** проектная работа с существующим Planner; начинаем с проверки допуска 97, актуального рабочего JSON и подготовленной пустой SQLite-цели.  
Общий результат — один точный перенос и согласованное переключение API и CLI на общий SQL-источник, без изменения публичного договора продукта.

1. **Проверить вход к переключению:** по принятому результату 97 подтвердить SQL CRUD, API override, CLI-ресурс на команду и импортёр; выбрать фактический JSON-источник, остановить API/CLI и убедиться, что новых записей больше нет. Если допуск не подтверждён, переключение не выполнять и вернуть недостающую проверку в 97.
2. **Сохранить окончательный снимок:** скопировать именно рабочий JSON, зафиксировать его путь/происхождение и убедиться, что выбранная цель — ожидаемая пустая база с уже созданной схемой; при неизвестной или непустой цели не продолжать.
3. **Перенести и сравнить:** запустить готовый импортёр из 89 на снимке и целевой базе; новой Session сравнить все `id` и пять предметных полей, включая внутренние `tags`, а также `title_normalized`. При отказе не считать перенос завершённым.
4. **Переключить обе сборки:** изменить обычное получение сервиса для существующего API и CLI так, чтобы оба использовали один `DATABASE_URL` через уже подготовленные ресурсы; не менять публичные маршруты/команды и не удалять переходные классы.
5. **Проверить общий путь:** на отдельной приёмочной задаче выполнить API add → CLI find/done → API get/stats и CLI search; проверить существующие PUT/PATCH/delete на тестовой записи, повторное чтение через новые ресурсы и новый запуск. Убедиться, что JSON не изменился после cutover.
6. **Зафиксировать границу передачи:** отметить момент первой SQL-записи, после которого архив не является актуальным возвратом; оставить удаление legacy-кода следующему плану.

Пункты 1–3 опираются на механизм снимка, валидации и транзакционного импорта, объяснённый в блоках 01–03 и подготовленный в 89. Пункт 4 применяет ресурсные области из 88 и контракт, уже проверенный в 90–97; пункты 5–6 используют объяснённые новые ресурсы и границу восстановления. Они сохраняют существующие API/CLI-возможности и показывают общий источник данных, а не только успешный импорт.
