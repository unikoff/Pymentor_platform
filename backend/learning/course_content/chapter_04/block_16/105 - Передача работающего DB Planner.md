## 00. Вступление

На прошлом занятии мы принимали целостность и поведение продукта в его обычной среде. Теперь проверим, может ли другой разработчик получить тот же результат без нашей локальной папки, старой виртуальной среды и случайных настроек. Договоримся считать успешной передачу только тогда, когда команды из документации приводят к работающим API, CLI и тестам.

1. **Точка старта:** у нас есть принятый Planner на SQLite, его обычные операции и тесты; инструменты Git, venv, requirements и настройки уже встречались ранее.
2. **Новый вопрос:** какие скрытые локальные условия могут сделать инструкцию запуска невоспроизводимой?
3. **Результат:** чистая копия проекта запускается по проверенной документации и показывает точную границу следующего этапа.

Сначала отделим состояние репозитория от локального окружения, затем проверим каждую ступень README на свежей копии: зависимости, настройки, схема, два интерфейса и тесты. Это повторное применение знакомых механизмов в новом контексте, а не первое знакомство с базой или создание Planner.

## 01. Что означает воспроизводимый checkpoint

- Что и зачем объяснить: разницу между checkout известной ревизии, рабочим деревом и локальными файлами, которые не попали в Git; почему успешный запуск в привычной папке сам по себе ничего не доказывает.
- Механизм и порядок: выбрать именно ревизию, соответствующую принятому результату 104; создать отдельный clone/checkout; проверить, что код и нужные тестовые файлы действительно tracked, а локальная база, .env и .venv не служат скрытыми входами. Не создавать новую историю репозитория ради упражнения.
- Пример и типичная путаница: два checkout одной ревизии, где в одном есть случайный локальный .env или старая БД; успешный запуск только там не является воспроизводимостью.
- Переход к следующему шагу: зафиксировав источник кода, можно проверить, описывает ли README точный способ создать окружение.

## 02. README как последовательность проверяемых действий

- Что и зачем объяснить: документация запуска является контрактом между автором и новым пользователем; список общих слов «установить зависимости и запустить» не заменяет команды и ожидаемые результаты.
- Механизм и порядок: сверить README с актуальными файлами проекта и разделить шаги на получение кода, Python/venv, зависимости, пример настроек, схему, тесты, API/CLI и ограничения. Каждую команду запускать в том порядке и из той директории, которые указаны.
- Пример и типичная путаница: присутствие requirements.txt не доказывает, что он содержит необходимую для запуска или тестов зависимость; наличие README не доказывает его актуальность.
- Переход к следующему шагу: после определения входов README проверяем, действительно ли чистая среда устанавливает заявленный набор без помощи пакетов из старой .venv.

## 03. Python, виртуальная среда и зависимости

- Что и зачем объяснить: системный интерпретатор и проектная .venv имеют разные установленные пакеты; requirements фиксирует используемые проектом версии, а не все пакеты случайной машины.
- Механизм и порядок: взять Python-версию и команды из проекта, создать новое окружение, установить объявленные файлы зависимостей и выполнить заявленную команду тестов. Сверить реально используемую библиотеку с импортами и тестовым клиентом.
- Пример и типичная путаница: команда pytest может случайно находить пакет в глобальной среде; запуск через Python именно из новой .venv проверяет воспроизводимость зависимостей.
- Переход к следующему шагу: чистая среда ещё не определяет, к какой базе подключится приложение; далее отдельно проверяются конфигурация и адрес.

## 04. Настройки, .env.example и адрес БД

- Что и зачем объяснить: пример конфигурации описывает имена и безопасные значения, а личный .env задаёт локальную среду и не должен переноситься в репозиторий; переменная текущего процесса может переопределить .env.
- Механизм и порядок: по коду Settings выяснить имя переменной, поведение default, разрешение пути и требуемый формат DATABASE_URL; в отдельной копии задать адрес новой тестовой SQLite и убедиться, что API и CLI получают один и тот же адрес.
- Пример и типичная путаница: существующий файл БД из рабочего checkout или переменная из прежнего PowerShell-сеанса направляет приложение мимо новой тестовой базы. Не исправлять это удалением файлов или выводом значений секретов.
- Переход к следующему шагу: подтвердив выбранный файл базы, можно объяснить, как явно подготовить его исходную структуру.

## 05. Явная инициализация исходной схемы

- Что и зачем объяснить: пустой файл SQLite ещё не содержит таблиц; явная команда инициализации создаёт исходные таблицы. create_all не обновляет уже существующую схему и не заменяет миграции.
- Механизм и порядок: запустить документированную init-команду на новой пустой базе, затем повторить её на той же согласованной схеме и проверить, что сохранённая запись остаётся. Разделить запуск приложения и создание схемы: старт API/CLI не должен незаметно создавать или импортировать данные.
- Пример и типичная путаница: повторная инициализация совпадающей таблицы безопасна, но это не означает безопасное преобразование несовместимой старой таблицы. Рабочую базу не очищать для эксперимента.
- Переход к следующему шагу: когда база подготовлена явно, проверяем, действительно ли два интерфейса используют её совместно и сохраняют состояние.

## 06. Два интерфейса, тесты и честная передача

- Что и зачем объяснить: API и CLI являются двумя входами в один сервис и одну базу; сквозная проверка связывает код, настройки, ресурсы и сохранение между процессами. Тестовая база должна быть изолирована от рабочих данных.
- Механизм и порядок: запустить тесты из новой копии, затем CLI и API на одном DATABASE_URL; создать задачу одним интерфейсом, прочитать другим, перезапустить процесс и проверить сохранение. Отдельно подтвердить внутренние tags чтением БД/CLI, потому что публичный HTTP-ответ их не показывает. Сверить .gitignore, не печатая секреты и параметры SQL.
- Пример и типичная путаница: ответ API после записи в текущей Session не доказывает, что новый процесс или другой интерфейс увидит строку; для этого выполняется новое чтение после перезапуска.
- Переход к практике: все шаги складываются в проверенный путь передачи, а не в новую реализацию CRUD.

## 07. Что мы будем делать в практике

**Формат и исходная опора:** проектная работа с существующим DB Planner; в качестве входа нужна чистая ревизия, соответствующая фактически принятому результату 104, и отдельное тестовое место для новой базы. Git, venv, requirements, Settings, init-команда и B15 подтверждены по занятиям 80–99. Занятия 100–104 пока не подтверждены, поэтому нынешний checkpoint нельзя использовать как практическую A105.

Общий результат: документация и пример конфигурации ведут нового пользователя к работающим тестам, API и CLI без локальных скрытых файлов; найденные инструкции проверены на копии и не обещают будущие функции.

1. **Сверить README, пример настроек, requirements и ignore с фактическим SQL-проектом:** исправить только подтверждённые расхождения; результатом будет точная цепочка команд без старого JSON-default, секретов или лишних требований. Опора: блоки 02–04 и уже изученные Settings/requirements.
2. **Получить чистую копию выбранного checkpoint и создать новую виртуальную среду:** пройти установку именно объявленных зависимостей; результатом будет доказательство, что старые пакеты и локальные файлы не нужны. Опора: блоки 01 и 03.
3. **Настроить новую тестовую SQLite и выполнить явную инициализацию:** повторить инициализацию на той же схеме и проверить сохранность созданной записи; результатом будет подтверждённый запуск базы без авто-DDL и миграций. Опора: блоки 04–05 и прежние знания об Engine/Session.
4. **Пройти README от тестов до API и CLI на общем DATABASE_URL:** выполнить короткий сквозной сценарий между интерфейсами и после нового процесса, проверить tags независимым способом; результатом будут работающие интерфейсы и сохранённые данные. Опора: блоки 02, 04 и 06 и только фактически принятый продукт 104.
5. **Проверить состав репозитория и оформить передачу:** убедиться, что секреты, локальная БД и персональные данные не включены, указать ревизию, команды и фактически проверенные ограничения; результатом будет точный handoff следующей главе. Опора: блоки 01–02 и 06.

README и пример настроек задают проверяемую работу с уже существующим продуктом. Если инструкция уже верна, менять её ради формального diff не нужно; передача всё равно должна опираться на реальный чистый запуск. В результате сохраняются общий SQL-путь и данные, а граница следующей главы явно оставляет миграции схемы и пользовательскую авторизацию впереди.
