# Глава 4 · От FastAPI с JSON к Planner на SQLite

Ваш Planner API уже работает. За 37 занятий вы подготовите приложение, перенесёте работу с задачами на SQLite и научитесь проверять запросы и ошибки — постепенно, сохраняя знакомый проект и его HTTP-контракт.

В карте четыре последовательных блока. Сначала разберём устройство FastAPI, затем подключим базу и SQLAlchemy, переведём на них все операции Planner и в конце проверим надёжность и запуск проекта в чистой копии.

## Четыре шага одного проекта

- **Блок 13 — Подготовьте FastAPI к росту.** Разложите ресурс по понятным границам, настройте окружение и зависимости. Добавите настройки представления через HTTP и cookie, не затрагивая права доступа.
- **Блок 14 — Разберитесь, как работает SQLite.** Создадите таблицу задач, сохраните первую запись и подготовите SQL-путь рядом с действующим JSON-хранилищем. Приложение продолжит работать, пока мы проверяем переход.
- **Блок 15 — Переведите Planner на SQL-запросы.** Подключите к базе создание, обновление, поиск, выборки и статистику. После общей проверки API и CLI переключите на SQLite и перенесёте прежние задачи.
- **Блок 16 — Проверьте и передайте проект.** Разберёте отказы и реальные SQL-запросы, проверите работу после перезапуска и воспроизведёте запуск из чистой копии проекта.

## Подробный маршрут

### Блок 13. Подготовьте FastAPI к работе с базой

Начнём с уже знакомого Planner API. Наведём порядок в структуре, конфигурации и зависимостях, затем расширим HTTP-возможности настройкой представления. Это создаст понятный путь запроса, к которому позже подключим базу.

- **[69. Пакет ресурса tasks](../block_13/69%20-%20Путь%20HTTP-запроса%20внутри%20FastAPI.md)**. Соберём маршруты и схемы задач в пакет одного ресурса, обновим импорты и проверим знакомые сценарии API и CLI.
- **[70. Настройки окружения](../block_13/70%20-%20Окружение%20и%20.env.md)**. Вынесем путь к JSON в настройку окружения, проверим значение по умолчанию и исключим локальный .env из Git.
- **[71. Общие настройки](../block_13/71%20-%20Централизованные%20настройки.md)**. Соберём настройки в одном месте для API и CLI. Проверим значения и понятную реакцию на ошибочную конфигурацию.
- **[72. Сервис через Depends](../block_13/72%20-%20Depends%20—%20получение%20готового%20сервиса.md)**. Подключим PlannerService через Depends к маршрутам задач и статистики, сохранив общий сервис и прежнее хранилище.
- **[73. Annotated: параметры](../block_13/73%20-%20Заголовки,%20cookies%20и%20Response.md)**. Перепишем объявления Path, Query и Depends в читаемом виде, не меняя ограничения, схемы и ответы API.
- **[74. Зависимости и тесты](../block_13/74%20-%20Middleware%20и%20CORS.md)**. Соберём параметры выборки и сервис в понятные зависимости. В тесте подменим провайдер и проверим отказ на отдельном JSON-файле.
- **[75. Заголовки и Response](../block_13/75%20-%20Headers%20и%20Response.md)**. Добавим GET /preferences с настройкой по умолчанию и проверим входной и ответный HTTP-заголовки, не меняя контракт задач.
- **[76. Cookie и вид ответа](../block_13/76%20-%20Cookie-настройка%20представления.md)**. Научим API читать и менять настройку compact или detailed через GET, PUT и DELETE. Проверим повторный запрос с cookie и без неё.
- **[77. Безопасность cookie](../block_13/77%20-%20Границы%20доверия%20и%20безопасность%20cookie.md)**. Ограничим допустимые значения cookie и настроим её атрибуты. Убедимся, что выбор представления не выдаёт клиенту никаких прав.

**После блока вы сможете:**

- Разложить HTTP-ресурс по модулям, не меняя работу API и CLI.
- Передавать настройки и сервис через понятные зависимости.
- Настроить предпочтение представления и объяснить, почему cookie не является авторизацией.

Это подготовит приложение к подключению базы и сохранит знакомые операции с задачами.

### Блок 14. Создайте SQLite-хранилище по шагам

Сначала разберём, почему файловый JSON неудобен для запросов, затем познакомимся с SQL, Engine, ORM и Session. Подготовим чтение и запись через новую границу хранения, не переключая рабочие API и CLI раньше времени.

- **[78. JSON и его пределы](../block_14/78%20-%20Почему%20одного%20JSON%20становится%20мало.md)**. Проследим, как Planner читает и перезаписывает весь список. На небольшом опыте увидим ограничение такого способа, не рискуя рабочими данными.
- **[79. SQLite и основы SQL](../block_14/79%20-%20SQLite%20и%20минимальный%20SQL.md)**. Создадим временную таблицу и выполним параметризованные INSERT и SELECT. Увидим, как база хранит и выбирает отдельные записи.
- **[80. Engine и путь к базе](../block_14/80%20-%20Engine%20и%20адрес%20базы.md)**. Настроим DATABASE_URL и общий Engine. Проверим подключение и убедимся, что проект находит одну и ту же базу из разных текущих папок.
- **[81. Модель ORM и таблица](../block_14/81%20-%20ORM-модель%20и%20исходная%20схема.md)**. Опишем TaskRow и поля таблицы, создадим исходную схему отдельной командой и сверим Python-атрибуты с колонками SQLite.
- **[82. Запись через Session](../block_14/82%20-%20Session%20—%20первая%20сохранённая%20запись.md)**. Откроем Session, добавим задачу и разберём flush, commit и refresh. Прочитаем запись новой Session и подтвердим, что она сохранена.
- **[83. Транзакция и откат](../block_14/83%20-%20Транзакция,%20отмена%20и%20закрытие.md)**. Вызовем реальное ограничение, выполним rollback и проверим следующую успешную операцию. Различим отмену изменений и закрытие ресурса.
- **[84. Чтение через SELECT](../block_14/84%20-%20SELECT%20и%20преобразование%20результата.md)**. Прочитаем список и задачу по id через SELECT, обработаем отсутствие записи и преобразуем ORM-объект в знакомую предметную модель.
- **[85. Граница чтения данных](../block_14/85%20-%20Новая%20граница%20хранения%20—%20чтение.md)**. Добавим JSON-адаптер и переведём чтение сервиса на операции по смыслу, сохранив прежний файл и поведение Planner.
- **[86. Граница записи данных](../block_14/86%20-%20Новая%20граница%20хранения%20—%20изменения.md)**. Переведём существующие изменения на новый контракт и уберём прямые load/save из сервиса, не переписывая CRUD заново.
- **[87. Чтение через SQL-репо](../block_14/87%20-%20SQL-репозиторий%20чтения.md)**. Реализуем получение списка и задачи из SQLite через SQL-репозиторий. Проверим, что чтение не фиксирует транзакцию записи.
- **[88. Ресурс на один запрос](../block_14/88%20-%20Ресурс%20на%20запрос%20и%20ресурс%20на%20команду.md)**. Ограничим время жизни Session одним HTTP-запросом или CLI-командой и проверим закрытие ресурса при успехе и ошибке.
- **[89. Импорт задач в SQLite](../block_14/89%20-%20Однократный%20перенос%20прежних%20задач.md)**. Импортируем копию JSON в пустую тестовую базу одной транзакцией, сохранив id и внутренние поля. Исходный файл останется нетронутым.

**После блока вы сможете:**

- Создать Engine, ORM-модель и исходную таблицу SQLite.
- Сохранить задачу, прочитать её новой Session и объяснить commit и rollback.
- Подготовить SQL-чтение и импорт прежних данных, не переключая рабочие API и CLI раньше времени.

Так переход на базу останется проверяемым: текущий Planner продолжает работать, пока новая граница хранения готовится отдельно.

### Блок 15. Переведите Planner на SQL-запросы

Когда понятны Session и чтение из базы, подключим к SQL все действия Planner. Сначала проверим операции отдельно, затем убедимся, что API и CLI готовы перейти на SQLite одновременно и без потери старых задач.

- **[90. Создание и ID из БД](../block_15/90%20-%20Создание%20и%20серверный%20id%20из%20базы.md)**. Подключим создание через SQL-репозиторий и получим id от базы. Перечитаем новую задачу и проверим, что сервис фиксирует завершённую операцию.
- **[91. PUT: замена задачи](../block_15/91%20-%20PUT%20—%20замена%20без%20потери%20внутренних%20данных.md)**. Обновим публичные поля через PUT, сохранив id и внутренние tags. Проверим найденную и отсутствующую задачу, включая отказ без частичного изменения.
- **[92. PATCH: выбор полей](../block_15/92%20-%20PATCH%20—%20только%20переданные%20изменения.md)**. Применим только переданные поля: False меняет значение, null и отсутствие поля его сохраняют. Убедимся, что пустой PATCH не создаёт запись.
- **[93. Задача: done и delete](../block_15/93%20-%20Завершение%20и%20удаление.md)**. Подключим done и delete к SQL-хранилищу. Проверим повторное завершение, ответ DELETE 204 и последующий ответ 404.
- **[94. SQL-фильтр и сводка](../block_15/94%20-%20Выборка%20и%20статистика%20запросами.md)**. Соберём фильтрацию, порядок и limit в SQL-запросе, а статистику получим агрегатами базы. Сохраним прежнюю форму ответов.
- **[95. Поиск в SQL-базе](../block_15/95%20-%20Поиск%20в%20базе%20без%20смены%20его%20смысла.md)**. Переведём поиск в SQL и сравним результат до и после обновления или импорта. Проверим буквальное совпадение и русский регистр.
- **[96. CLI и ресурс команды](../block_15/96%20-%20CLI%20—%20отдельный%20ресурс%20на%20команду.md)**. Подключим SQL-ресурс к обработчикам CLI и откроем его на одну команду. Проверим, что интерактивный цикл не удерживает закрытую Session.
- **[97. Готовность к переходу](../block_15/97%20-%20Готовность%20к%20переключению.md)**. Проверим API и CLI на одной тестовой базе, включая импорт и новый id. Закроем пробелы до переключения рабочего приложения.
- **[98. Переход на SQLite](../block_15/98%20-%20Единое%20переключение%20JSON%20%E2%86%92%20SQLite.md)**. Остановим записи, перенесём финальное состояние JSON и переключим сборку API и CLI вместе. Повторно проверим сохранность прежних задач.
- **[99. Убираем JSON-backend](../block_15/99%20-%20Удаление%20JSON-backend%20и%20проверка%20независимости.md)**. Уберём рабочий JSON-backend, его настройки и fallback. Запустим API и CLI без прежнего файла, сохранив JSON только как формат импорта.

**После блока вы сможете:**

- Выполнять через SQL создание, обновление, завершение и удаление задач с прежними правилами API.
- Получать выборки, поиск и статистику запросами к базе.
- Переключить API и CLI на одну SQLite, перенести задачи и проверить работу без JSON-backend.

Сначала переход проверяется на общей тестовой базе, и только потом оба интерфейса переключаются вместе.

### Блок 16. Проверьте надёжность и передайте Planner

Planner уже работает на SQLite. Теперь разберём безопасные отказы, посмотрим на SQL реальных сценариев и проверим весь проект вместе. Улучшать будем только то, для чего нашли подтверждение.

- **[100. Сбой БД: API и CLI](../block_16/100%20-%20Ошибка%20БД%20и%20граница%20ответственности.md)**. Отделим недоступность хранения от неверного ввода, отсутствующей задачи и внутренней ошибки. Вернём понятный отказ API и CLI без ложного успеха.
- **[101. Rollback и повтор](../block_16/101%20-%20Проверки%20отказов%20и%20восстановление%20работы.md)**. Проверим реальный отказ до commit, rollback и следующую независимую операцию. Убедимся, что уже подтверждённая запись не объявляется отменённой.
- **[102. SQL-запросы Planner](../block_16/102%20-%20Какие%20SQL-запросы%20делает%20Planner.md)**. Проследим запросы для списка, одной задачи, статистики и поиска. Свяжем SQL с действием Planner, не раскрывая данные пользователей в логах.
- **[103. Улучшаем SQL-запрос](../block_16/103%20-%20Обоснованное%20улучшение%20запросов.md)**. Найдём лишнюю работу по наблюдениям и исправим один участок либо защитим уже достаточный запрос проверкой. Сравним поведение без обещаний ускорения на глаз.
- **[104. Сквозная проверка](../block_16/104%20-%20Сквозная%20проверка%20готового%20продукта.md)**. Пройдём связанную историю API и CLI на одной базе: обычные действия, отказ, повторный запуск и сохранность данных.
- **[105. Передача DB Planner](../block_16/105%20-%20Передача%20работающего%20DB%20Planner.md)**. Подготовим чистую копию, настройки и README, затем запустим API и CLI по инструкции. Проверим тесты и обозначим, какие темы будут следующими.

**После блока вы сможете:**

- Различать ошибки хранения, пользовательский ввод и внутренние сбои, возвращая безопасный результат.
- Связывать действия Planner с SQL и улучшать запросы только по наблюдаемым причинам.
- Запустить API и CLI из чистой копии и показать, что данные сохраняются после перезапуска.

Изменение уже созданной схемы и миграции остаются темой следующей главы.

## Как пройти маршрут

В каждом занятии сначала разберитесь, какую проблему решает новый механизм. До запуска предположите ожидаемый SQL или ответ, затем проверьте результат, измените один участок и повторите знакомые сценарии. Так вы научитесь не только подключать SQLAlchemy, но и объяснять путь данных и границы ответственности в собственном Planner.
