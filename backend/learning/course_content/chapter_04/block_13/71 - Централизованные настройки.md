## 00. Вступление

Planner запускается через API и CLI. После урока 70 путь к JSON стал параметром запуска, но обе точки не должны трактовать его по-разному.

1. **Точка старта:** один JSON Planner и две точки запуска; `JSON_PATH` уже читается из окружения и `.env`.
2. **Новый вопрос:** как собрать и проверить настройки один раз, чтобы API и CLI использовали одинаковые значения?
3. **Результат:** единый `Settings`, явные правила проверки и согласованная сборка без смены поведения Planner.

Маршрут идёт от значения окружения к объекту настроек, затем к его применению и изолированной проверке. Сервис и его JSON-операции не переписываются.

## 01. От одного значения к общей конфигурации

- **Что и зачем объяснить:** кроме `JSON_PATH` нужно имя FastAPI и одинаковые правила для API/CLI. Независимое чтение создаёт риск разных значений.
- **Механизм и порядок:** сравнить отдельную строку с подготовленным набором; отделить конфигурацию от HTTP-параметров и данных задачи.
- **Пример или типичная путаница:** API и CLI не должны выбирать разные файлы; новая настройка не означает новый режим Planner.
- **Переход:** связанные значения удобно передать простым объектом.

## 02. `Settings` как объект данных, а не автоматический валидатор

- **Что и зачем объяснить:** знакомая `dataclass` задаёт форму `json_path` и `app_name`, но сама не решает, допустимы ли пустая строка или путь к каталогу.
- **Механизм и порядок:** прочитать строки, преобразовать типы, отдельно проверить правила и лишь затем передать объект сборке.
- **Пример или типичная путаница:** аннотация поля не превращает обычную `dataclass` в `BaseSettings` и не выполняет валидацию.
- **Переход:** преобразования и правила нужно собрать в загрузчике.

## 03. `load_settings`: default, пустое значение и устойчивый путь

- **Что и зачем объяснить:** отсутствие отличается от явно пустого значения. Без `APP_NAME` остаётся `StudyHub Planner`; пустые `APP_NAME` и `JSON_PATH` не включают default молча.
- **Механизм и порядок:** собрать `Settings` в `load_settings`, преобразовать `JSON_PATH` в `Path` и проверить до создания storage. Абсолютный путь сохраняет смысл; относительный разрешается от корня проекта, не от cwd. Каталог вместо файла отклоняется до записи.
- **Пример или типичная путаница:** `Path("data/tasks.json")` зависит от cwd, пока приложение явно не привяжет его к корню; каталог не является файлом задач.
- **Переход:** после проверки можно отделить ошибку конфигурации от ошибки запроса.

## 04. Ошибка конфигурации при сборке и HTTP 422

- **Что и зачем объяснить:** неверная настройка указывает на проблему запуска, а не невалидное поле запроса.
- **Механизм и порядок:** проверить настройки до создания зависимых объектов и записи; завершить сборку с понятной ошибкой, не создавать JSON и не переключаться молча на default. HTTP 422 остаётся ответом работающего API на ошибочный запрос.
- **Пример или типичная путаница:** повторный запрос не исправляет неверный `JSON_PATH`; запуск с другим файлом не является безопасным fallback.
- **Переход:** проверенный объект можно передать обеим точкам запуска.

## 05. Одна подготовленная конфигурация для API и CLI

- **Что и зачем объяснить:** API и CLI остаются интерфейсами одного `PlannerService` и JSON-storage; настройки собираются на границе запуска, не в обработчике.
- **Механизм и порядок:** показать общую `build_service`, передачу настроек либо default только в штатной ветке; сохранить переданный тестовый `storage`. API хранит настройки и сервис в `app.state.settings` и `app.state.planner`; CLI использует те же настройки без FastAPI-механизмов.
- **Пример или типичная путаница:** новый storage в каждой ветке, настройка только API или чтение на каждый запрос создают разные источники правды. Новый процесс перечитывает настройки; hot reload и кэширование не вводятся.
- **Переход:** общую конфигурацию можно проверить на изолированных данных.

## 06. Изолированная проверка настроек и прежнего поведения

- **Что и зачем объяснить:** проверка подтверждает конфигурацию и сохранность продукта, не затрагивая рабочий `data/tasks.json` и не наследуя случайное окружение.
- **Механизм и порядок:** отделить тестовые значения среды и `Settings`; использовать временный JSON и переданный storage; восстановить окружение и `app.state`. Сверить default, явные настройки, пустые значения, путь к каталогу и один относительный путь из разных cwd.
- **Пример или типичная путаница:** `.gitignore` не изолирует тест; тестовый storage не должен уступить хранилищу из рабочей среды.
- **Переход:** проверки связывают загрузчик с API и CLI и готовят урок 72, не вводя его `Depends` заранее.

## 07. Что мы будем делать в практике

**Формат и исходная опора:** изменение существующего StudyHub Planner после обновлённого урока 70; один `build_service`, `JsonStorage`, API и CLI.

Итог: централизовать две настройки, сохранив HTTP-контракт задач и единственный путь сборки.

1. **Соберём `Settings` и загрузку конфигурации:** значения преобразуются и проверяются до использования, default сохраняет прежнее поведение.
2. **Подключим объект к API и CLI:** обе точки используют согласованные настройки, API хранит их рядом с прежним сервисом, переданный storage сохраняется.
3. **Проверим конфигурации на изолированных путях:** рабочий JSON не меняется, неверный путь не создаёт запись и не подменяется default.
4. **Сверим разные cwd и прежние операции Planner:** один относительный путь указывает на один файл, API и CLI продолжают работать.

`dataclass` объясняет форму объекта, `load_settings` подготавливает его, а общая сборка связывает API и CLI. Результат даёт уроку 72 готовые `app.state.settings` и `app.state.planner`; провайдера `Depends` здесь ещё не создаём.
