## 00. Вступление

Вернуться к знакомому Planner: его JSON сохраняет задачи между запусками, а чтение и изменение используют общий снимок. Теперь перед созданием нового слоя хранения нужно понять, как адресоваться к отдельной строке и какие команды для этого существуют.

1. **Точка старта:** существующая Task и JSON-файл Planner; ожидаемый вывод занятия 78 о цене полного снимка — только если он уже подтверждён.
2. **Новый вопрос:** как таблица позволяет описать и прочитать отдельные строки, не разбирая все задачи в Python?
3. **Результат:** небольшая таблица в памяти, параметризованные изменения и выборки, которые можно сверить с предсказанием.

Это исследование механизма SQL на изолированных данных. Оно даёт словарь и опыт для следующего подключения, но не заменяет действующий JSON и не создаёт будущий backend раньше времени.

## 01. SQLite, база и соединение

- Что и зачем объяснить: SQLite — встроенная реляционная БД; для короткого эксперимента :memory: создаёт базу, доступную через открытое соединение и не сохраняемую как файл проекта.
- Механизм и порядок: сначала соединение через стандартный модуль sqlite3, затем выполнение SQL через API соединения/курсора и получение результата. Отделить соединение с базой от файлового объекта Python и от экземпляра Task.
- Пример и типичная путаница: одна открытая база в памяти живёт на протяжении эксперимента; закрытие соединения завершает её. Это не общий пул подключений и не сервис приложения.
- Переход к следующему шагу: соединение даёт место для учебной таблицы; до запросов нужно задать её строки и столбцы.

## 02. Таблица, строка, колонка, тип и NULL

- Что и зачем объяснить: таблица хранит строки по колонкам, а не список объектов с атрибутами. id, title, priority и is_done будут учебным срезом знакомой Task, но сама таблица не является моделью Planner.
- Механизм и порядок: разобрать CREATE TABLE, целочисленный первичный ключ, текстовые и целочисленные значения, NOT NULL и смысл SQL NULL; показать, что NULL, пустой текст, ноль и Python False не взаимозаменяемы. Объяснить, что ограничения относятся к значениям столбцов.
- Пример и типичная путаница: строка результата будет отдельной записью с колонками, а не автоматически собранным объектом Task. Использовать только небольшую таблицу с четырьмя указанными полями, без полной схемы приложения.
- Переход к следующему шагу: после создания схемы можно прочитать строки и рассмотреть форму результата.

## 03. SELECT и результат запроса

- Что и зачем объяснить: SELECT задаёт нужные колонки из таблицы; чтение возвращает ноль или больше строк, которые sqlite3 предоставляет как результат запроса.
- Механизм и порядок: показать SELECT ... FROM ..., получение всех строк и одной строки, затем сопоставить значения и их позиции с колонками. Не превращать их в Task и не вводить ORM mapping.
- Пример и типичная путаница: неизвестный id даёт пустой результат/отсутствующую строку, а не фиктивную задачу; порядок полей в строке соответствует проекции запроса.
- Переход к следующему шагу: чтобы прочитать только нужную запись или ограниченное число строк, добавить условия и порядок.

## 04. WHERE, ORDER BY и LIMIT

- Что и зачем объяснить: фильтр выбирает подходящие строки, сортировка задаёт порядок, лимит ограничивает число возвращённых строк.
- Механизм и порядок: объяснить последовательность частей SELECT и значение каждого условия; показать сортировку по колонке и ограничение выборки. Отдельно проговорить: без явного ORDER BY нельзя обещать порядок строк.
- Пример и типичная путаница: LIMIT не задаёт условие фильтра, а ORDER BY не меняет сохранённые строки. Проверить направление сортировки и выбор нескольких строк.
- Переход к следующему шагу: чтение уже адресно; далее изменить набор строк командами записи.

## 05. Значения SQL и параметры sqlite3

- Что и зачем объяснить: значения для запроса передаются отдельно от текста SQL, чтобы кавычки и ввод не меняли структуру команды.
- Механизм и порядок: сначала текст с позиционными плейсхолдерами ?, затем отдельная последовательность значений в execute; связать порядок значений с плейсхолдерами. SQL-имена таблиц и колонок здесь не рассматриваем как передаваемые значения.
- Пример и типичная путаница: title с апострофом остаётся обычным текстом, когда передан параметром. Не собирать SQL f-строкой и не ставить кавычки вокруг ?.
- Переход к следующему шагу: параметризация применяется и к добавлению, и к адресным изменениям строк.

## 06. INSERT, UPDATE и DELETE

- Что и зачем объяснить: отдельные команды добавляют строку, меняют значения существующих строк или удаляют строку; это операции над учебной таблицей, не над Planner.
- Механизм и порядок: объяснить INSERT, затем UPDATE ... SET ... WHERE ... и DELETE ... WHERE ...; для каждого обозначить изменяемую таблицу, колонки или строки, условия и значения-параметры.
- Пример и типичная путаница: WHERE id = ? ограничивает действие одной строкой; пропуск WHERE в UPDATE меняет все строки, а в DELETE удаляет все строки. Сначала предсказать охват небезопасного примера, не запускать его на данных вне одноразовой базы.
- Переход к следующему шагу: изменения нужно увидеть и решить, оставить ли их; для этого разберём завершение и отмену транзакции.

## 07. Фиксация, отмена и закрытие соединения

- Что и зачем объяснить: выполненная команда и зафиксованное изменение — разные этапы; commit подтверждает текущие изменения, rollback отменяет незавершённые, close завершает работу с соединением.
- Механизм и порядок: на уже созданной таблице наблюдать изменение до и после фиксации, затем отменить отдельную временную операцию и повторно прочитать данные. Явно закрыть соединение. Контекстный менеджер sqlite3.Connection управляет commit/rollback, но сам по себе не закрывает соединение.
- Пример и типичная путаница: close не является подтверждением записи и не заменяет rollback; подробный жизненный цикл SQLAlchemy Session будет темой 82–83.
- Переход к следующему шагу: все операции готовы к одному короткому эксперименту на данных в памяти.

## 08. Что мы будем делать в практике

**Формат и исходная опора:** исследование в интерпретаторе на стандартном sqlite3 и отдельной базе :memory:. Используем знакомые значения задач; не читаем рабочий JSON и не изменяем проект.

Ученик получит небольшую таблицу, прочитает её выбранными запросами, безопасно изменит две записи и подтвердит, что параметры и условия действуют ожидаемо.

1. **Открыть соединение и создать таблицу tasks с полями id, title, priority, is_done:** получить изолированную схему в памяти и объяснить первичный ключ, типы и NULL (теория 01–02).
2. **Добавить несколько строк параметризованными INSERT, включая title с апострофом:** увидеть, что значение передаётся отдельно и строка хранится целиком (теория 05–06).
3. **Предсказать и выполнить выборки с SELECT, WHERE, ORDER BY, LIMIT; запросить неизвестный id:** сверить список строк, отсутствие результата и отсутствие гарантии порядка без сортировки (теория 03–04).
4. **Изменить одну строку и удалить другую по id; разобрать предложение UPDATE без WHERE, не исполняя его:** увидеть только адресные изменения и объяснить, почему пропущенное условие затронуло бы всю таблицу (теория 05–06).
5. **Зафиксировать основные изменения, выполнить отдельное временное изменение и отменить его; перечитать строки и закрыть соединение:** наблюдать commit/rollback и подтвердить, что таблица существовала только в эксперименте (теория 01 и 07).

Практика использует только механизмы, предварительно объяснённые в блоках 01–07. На выходе остаётся вывод о том, как SQL обращается к строкам; в Planner не появляются таблица, новый storage или второй источник данных.
