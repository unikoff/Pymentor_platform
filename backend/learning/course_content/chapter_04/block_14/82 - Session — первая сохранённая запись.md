## Место в маршруте

Занятие следует за проектированием исходной таблицы и её явным созданием в 81. Здесь появляется первая сохранённая через ORM запись: ученик создаёт фабрику короткоживущих Session, прослеживает успешный путь объекта и подтверждает результат независимым чтением. В 83 отдельно изучаются отказ, rollback и восстановление Session. API и CLI на всём протяжении блока пока используют прежний JSON.

Текущие планы 81 и 83 содержат только заголовки, поэтому связность соседей проверена по полным паспортам блока 14, а не по готовым планам.

Существуют предметная Task, PlannerService, API и CLI с устойчивым JSON-хранением; изучены настройки, FastAPI-зависимости, изоляция API-тестов и контекст HTTP. JSON уже сохраняет задачи между запусками — это не первое знакомство с сохранением данных.
- Состояние проекта: локальный StudyHub находится на коммите e879436, «пройдено занятие 77». API и CLI продолжают работать через JSON; каталога app/DBase и SQLAlchemy-пути ещё нет. Это фактический снимок при подготовке плана, до занятий 78–81.
- Планируемая опора: журнал обучения пока не подтверждает занятия 78–81. Согласно маршруту, до этого занятия ученик должен исследовать SQLite/SQL, настроить Engine, создать TaskRow и явно подготовить исходную таблицу. Этот результат пока запланирован, а не изучен. План рассчитан на применение после приёмки 81; без Engine, TaskRow и созданной схемы практику 82 принять нельзя.

## Точка B: результат занятия

- Ученик сможет объяснить: зачем Session создаётся из фабрики на одну операцию; чем add, flush, commit и refresh отличаются друг от друга; почему выданный после flush id ещё не доказывает зафиксированную запись; почему refresh не заменяет commit.
- Ученик сможет сделать: создать одну корректную строку TaskRow в изолированной SQLite-базе, получить её id и повторно прочитать её через новую Session.
- Результат в проекте: в app/DBase/session.py добавлена фабрика на основе sessionmaker для переданного Engine. Глобального экземпляра Session нет; открытие Session не создаёт таблицы. Штатные API и CLI продолжают использовать JSON.
- Как подтвердим: после закрытия первой ресурсной области новая Session читает из файла базы те же id, title, priority, is_done, tags и title_normalized. Отдельная проверка двух записей показывает, что их списки tags независимы.

## 00. Вступление

Задачи уже переживают перезапуск благодаря JSON. Теперь подготовлены Engine и таблица, но ORM ещё не сохраняла в неё ни одной задачи. Нужно проследить путь одного ORM-объекта и установить, на каком шаге база действительно подтверждает запись.

1. **Точка старта:** после завершения запланированных занятий 78–81 есть Engine, TaskRow и исходная таблица; приложение всё ещё работает с JSON.
2. **Новый вопрос:** что именно делает объект доступным в базе — add, flush, commit или refresh?
3. **Результат:** одна запись сохранена через Session, а её поля прочитаны из независимой Session.

Маршрут проходит от фабрики Session к короткой ресурсной области, затем к постановке ORM-объекта на учёт, отправке INSERT, фиксации транзакции и независимой проверке. Это первый успешный сценарий ORM; ошибки и отмена будут разобраны отдельно.

## 01. Фабрика Session и рабочая область ORM

- Что и зачем объяснить: Engine переиспользуется как инфраструктура подключения; sessionmaker создаёт отдельные Session для конкретных операций. Session отслеживает ORM-объекты и координирует работу с транзакцией, но не является ни файлом базы, ни предметным PlannerService.
- Механизм и порядок: передать настроенный Engine фабрике; открыть Session для одной ограниченной операции; закрыть её и при необходимости открыть следующую. Не хранить экземпляр Session в глобальном состоянии приложения.
- Пример и типичная путаница: сравнить одну фабрику с двумя последовательными Session. Общий Engine не означает, что сами Session нужно разделять между независимыми действиями.
- Переход к следующему шагу: после создания Session определить, где заканчивается её ресурсная область.

## 02. Ресурсная область и with

- Что и зачем объяснить: Session использует ресурс, который нужно освободить даже после успешной операции. Вспомнить работу контекстного менеджера и показать, что завершение with закрывает Session, но само по себе не подтверждает транзакцию.
- Механизм и порядок: фабрика создаёт Session; код выполняет работу внутри области; при выходе освобождается ресурс. Commit остаётся отдельным явным шагом этой практики.
- Пример и типичная путаница: успешный выход из with без commit не следует называть сохранением. Close не равен commit; детальная отмена незавершённой работы относится к 83.
- Переход к следующему шагу: с готовой областью можно создать ORM-объект и передать его Session.

## 03. TaskRow и add

- Что и зачем объяснить: использовать ORM-модель из 81, не создавая новую предметную Task или HTTP-схему. Объект соответствует строке таблицы; Session должна начать отслеживать его изменения.
- Механизм и порядок: создать корректный TaskRow с предметными полями, tags и title_normalized; вызвать add; объяснить, что объект включён в рабочую область Session, но это ещё не доказательство сохранённой строки.
- Пример и типичная путаница: наблюдать состояние объекта до и после add. Add не назначает гарантированно готовый к использованию id и не является commit.
- Переход к следующему шагу: чтобы передать ожидающие изменения базе внутри текущей транзакции, нужен flush.

## 04. Flush и назначение id

- Что и зачем объяснить: Session может отправить накопленные изменения до окончательной фиксации транзакции. Это позволяет получить сгенерированный базой первичный ключ и наблюдать реальный INSERT.
- Механизм и порядок: add регистрирует объект; flush отправляет SQL; БД может вернуть id. Транзакция всё ещё не подтверждена, поэтому другая независимая Session не должна считаться доказательством уже сохранённого результата.
- Пример и типичная путаница: сравнить id до и после flush. Полученный id показывает результат INSERT в текущей транзакции, но не гарантирует, что эта транзакция зафиксирована.
- Переход к следующему шагу: успешное завершение требует отдельно подтвердить транзакцию.

## 05. Commit и состояние объекта после фиксации

- Что и зачем объяснить: commit завершает текущую транзакцию и делает её запись доступной после её подтверждения. Commit не закрывает Session; настройки фабрики могут влиять на истечение ORM-состояния после commit.
- Механизм и порядок: commit при необходимости сначала выполняет flush, затем подтверждает транзакцию. Объяснить поведение выбранного expire_on_commit, не менять его только ради упрощения наблюдения.
- Пример и типичная путаница: повторно обратиться к полю объекта после commit и разобрать, читается ли оно из уже загруженного состояния или обновляется. Сам факт возврата commit не подменять проверкой через ту же Session.
- Переход к следующему шагу: refresh и новая Session показывают две разные формы чтения из базы.

## 06. Refresh и независимое чтение

- Что и зачем объяснить: refresh повторно загружает состояние объекта из базы в текущую Session; он не фиксирует транзакцию. Для доказательства долговечности нужно завершить первую область и прочитать запись новым экземпляром Session.
- Механизм и порядок: после успешного commit при необходимости вызвать refresh; затем во второй ресурсной области получить запись по первичному ключу через Session.get и сравнить поля. Служебный title_normalized остаётся внутренней колонкой.
- Пример и типичная путаница: сравнить refresh объекта в первой Session и get в новой. Только чтение после завершения первой области доказывает, что проверка не опирается на тот же объект в identity map.
- Переход к практике: применить шаги к изолированной базе и проверить сохранённую запись по её полному состоянию.

## 07. Что мы будем делать в практике

**Формат и исходная опора:** проектная работа на отдельной SQLite-базе во временном каталоге. Исходными считаются Engine, модель TaskRow и схема, подготовленные в принятых занятиях 80–81. Рабочая JSON-база и штатные API/CLI не используются для записи.

Общий результат — отдельная фабрика Session и доказанный успешный ORM-сценарий, который сохраняет все поля задачи и доступен после закрытия первой Session.

1. **Подготовить изолированную фабрику и ресурсную область:** подключить её к Engine из предыдущего шага и уже созданной временной схеме; убедиться, что открытие Session само не создаёт таблицу. Опора: 01–02 и принятые 80–81.
2. **Создать TaskRow и выполнить add:** использовать согласованные поля, включая tags и title_normalized; зафиксировать, что изменилось в состоянии объекта, а запись ещё не подтверждена. Опора: 03.
3. **Выполнить flush и наблюдать id:** проверить, что INSERT отправлен в текущей транзакции и первичный ключ получен до commit. Опора: 04.
4. **Подтвердить запись и применить refresh:** отдельно объяснить границу commit и роль refresh; не трактовать ни один из этих шагов как закрытие Session. Опора: 02 и 05–06.
5. **Прочитать задачу в новой Session:** сравнить все сохранённые предметные и служебные поля с исходным объектом после закрытия первой области. Опора: 01–02 и 06.
6. **Проверить независимость списков tags:** создать вторую строку с предусмотренным моделью default и убедиться после сохранения/чтения, что список одной записи не разделяет состояние с другой. Не делать вывод о сохранении JSON-мутации на месте без отдельного механизма. Опора: объяснение модели в 03 и независимого чтения в 06.

Эти действия дают одну завершённую успешную операцию и подготавливают базу для 83. Ошибку ограничения, rollback и повторное использование Session после отказа здесь не разбирать. Проверки используют только временную БД; существующие JSON-задачи, API-договор и CLI остаются рабочими без изменений.
