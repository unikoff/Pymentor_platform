## 00. Вступление

SQL-репозиторий уже умеет читать запись, но Session должна иметь ясного владельца и ограниченный срок жизни. На HTTP-пути таким владельцем становится запрос; в CLI — одна команда.

1. **Точка старта:** приложение по умолчанию использует полный JSON-путь, а по паспорту 87 ожидаются отдельная Session и SQL-чтение.
2. **Новый вопрос:** кто открывает и закрывает Session для одного запроса или команды?
3. **Результат:** ресурс освобождается при успехе и ошибке; SQL GET проверяется изолированно, а JSON остаётся штатным путём.

Сначала разбирается механизм выдачи и завершения ресурса, затем его владелец в FastAPI, тесте и CLI. Это подготавливает импортёр 89, не изображая готовность остальных SQL-операций.

## 01. Обычный return и генераторный yield

- Что и зачем объяснить: обычная функция возвращает готовое значение; генераторная функция может выдать значение, приостановиться и выполнить завершающий код, когда потребитель закончил работу.
- Механизм и порядок: на независимом коротком примере проследить код до yield, выданный ресурс, возобновление функции и завершающее действие; разделить создание генератора и его использование контекстом.
- Пример и типичная путаница: yield не равен return и сам по себе не означает commit. Не вызывать yield-provider вручную через next() для обычной операции.
- Переход: связать завершающую часть с закрытием Session при исключении.

## 02. Ресурсная область и транзакция

- Что и зачем объяснить: Session нужно закрыть после использования; commit и rollback управляют изменениями и не заменяются закрытием.
- Механизм и порядок: восстановить try/finally и with, проследить cleanup при нормальном выходе и исключении, затем отделить это от уже изученных commit/rollback. В этом шаге выполняется только SQL-чтение.
- Пример и типичная путаница: закрытие не подтверждает запись и cleanup не должен становиться скрытой точкой commit.
- Переход: выдать ограниченный ресурс через существующий граф FastAPI-зависимостей.

## 03. Session через FastAPI и проверка срока жизни

- Что и зачем объяснить: Depends получает callable, а yield-зависимость связывает подготовку ресурса и его освобождение с областью запроса.
- Механизм и порядок: SessionFactory создаёт новую Session; get_db выдаёт её и закрывает в завершающей части; тестовый SQL-provider передаёт Session репозиторию и сервису. Сборка сервиса принимает явно переданный репозиторий, не копируя предметные правила. Сверить детали с [документацией FastAPI о yield-зависимостях](https://fastapi.tiangolo.com/tutorial/dependencies/dependencies-with-yield/) и [разделом о scope](https://fastapi.tiangolo.com/advanced/advanced-dependencies/).
- Пример и типичная путаница: SQL-сервис с Session текущего запроса нельзя хранить в общем app.state; обычный get_planner продолжает выдавать JSON-сервис.
- Переход: подключить SQL-provider только к существующему GET по id и проверить через отдельную файловую SQLite fixture.
- Дополнение: момент cleanup относительно отправки ответа зависит от версии FastAPI и scope. В requirements текущего checkout указана fastapi==0.142.2; перед практикой сверить версию целевого окружения и документацию установленной версии; не обещать универсальное «после ответа» и не делить одну Session между потоками TestClient/SQLite.

## 04. Override и проверка отказа

- Что и зачем объяснить: override подменяет зависимость для теста; Engine и данные должны быть отделены от рабочей БД и JSON.
- Механизм и порядок: подменить provider сервиса, вызвать существующий GET с известным и неизвестным id, затем проверить cleanup при успехе и контролируемой ошибке. Восстановить прежний словарь overrides даже при сбое.
- Пример и типичная путаница: успешный GET подтверждает только SQL-чтение по id; он не делает SQL-путь default и не подтверждает операции, которых ещё нет.
- Переход: после теста проверить, что следующий запрос через JSON-provider работает.

## 05. Отдельный ресурс для одной CLI-команды

- Что и зачем объяснить: CLI не использует HTTP Depends, но также не должен удерживать Session на весь интерактивный цикл.
- Механизм и порядок: если применяется contextlib.contextmanager, сначала разобрать его протокол по [документации Python](https://docs.python.org/3/library/contextlib.html); открыть контекст SQL-сервиса на один get или list, закрыть его и только затем перейти к независимой операции.
- Пример и типичная путаница: не менять основной run() и его JSON-сборку; не хранить одну Session весь запуск и не продвигать yield-provider через next().
- Переход: зафиксировать область CLI как подготовку для самостоятельной команды импорта в 70.2.

## 06. Что мы будем делать в практике

**Формат и исходная опора:** проектная работа в StudyHub после подтверждённого результата 70; проверки работают на отдельной файловой SQLite fixture. Штатные API и CLI всё ещё используют полный JSON-путь.

Общий результат — проверить срок жизни Session на SQL GET и подготовить контекстный ресурс для одного CLI-вызова.

1. **Добавить get_db и явную сборку SQL-сервиса:** Session выдаётся из SessionFactory и закрывается; JSON-provider остаётся штатным. Подготовлено блоками 01–03 и прежними Depends/сборкой сервиса.
2. **Подменить provider существующего GET /tasks/{id}:** прочитать известную запись с внутренними tags, подтвердить их сохранение в Task и прежний публичный TaskRead без новых полей; проверить прежний 404 для неизвестного id. Использовать отдельную базу. Подготовлено блоками 03–04 и прежними навыками API.
3. **Проверить cleanup и восстановление теста:** наблюдать закрытие Session после успеха и контролируемой ошибки; восстановить overrides и проверить следующий JSON-запрос на изолированном fixture. Подготовлено блоками 02–04 и прежним навыком изоляции API-тестов.
4. **Подготовить CLI-контекст на одно чтение:** выполнить get или list в отдельной ресурсной области, закрыть её и подтвердить новую область для следующего вызова. Не менять основной CLI-цикл. Подготовлено блоком 05 и прежним навыком работы с CLI.

Порядок ведёт от выдачи ресурса к тесту существующего HTTP-контракта, затем к CLI-контексту. Рабочая БД и файлы данных не изменяются: SQL-проверка использует отдельную SQLite-базу, JSON-регрессия — изолированный fixture. SQL-запись и переключение приложения относятся к следующим этапам.
