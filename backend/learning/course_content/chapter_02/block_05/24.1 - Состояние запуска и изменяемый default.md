## 00. Откуда берётся состояние одного запуска

В предыдущих занятиях мы разбирали, как функция получает объекты через параметры и как изменение списка видно через разные имена. Теперь используем это понимание в жизненном цикле знакомого Planner. Пока `run()` сам создаёт список задач внутри функции, поэтому вызывающий код не может передать ему уже подготовленное состояние и получить итоговый список после выхода.

1. **Точка старта:** мы знаем ссылки, мутацию списков и словарей, параметры и `return`; `run` пока создаёт собственный список.
2. **Новый вопрос:** как отличить отсутствие списка от намеренно пустого списка и не разделить один список по умолчанию между запусками?
3. **Результат:** мы изменим договор `run`, чтобы передавать состояние, сохранять тот же контейнер во всех командах и получать его после обычного `exit`.

Эти шаги связывают уже знакомые ссылки с конкретным владельцем состояния. Сначала разберём, когда Python создаёт значение по умолчанию; затем отделим отсутствующее состояние от пустого и проследим путь одного списка через команды и завершение цикла.

## 01. Изменяемое значение по умолчанию создаётся один раз

Default, то есть значение по умолчанию, Python подставляет, когда аргумент пропущен. Выражение справа от `=` вычисляется при выполнении определения `def`. Если это список, в default сохраняется один объект. Каждый вызов без аргумента получает ссылку на него, а не новый список.

```python
def remember_tag(tag, tags=[]):
    tags.append(tag)
    return tags

print(remember_tag("SQL"))
print(remember_tag("Git"))
```

Здесь сначала появится `['SQL']`, затем `['SQL', 'Git']`. Вторая команда меняет тот же список, который использовался в первом вызове. Если бы функция вернула результат вызова и мы сохранили его в `first`, поздняя мутация была бы видна и через `first`: обе переменные указывали бы на один объект.

Представим общую чашу для канцелярии, которую поставили на рабочий стол при открытии комнаты. Каждый посетитель, не принося свою, берёт ручку из той же чаши; новая ручка автоматически не появляется к его приходу. В примере определение функции создаёт чашу, а вызовы без `tags` пользуются ею. Аналогия объясняет повторное использование одного объекта, но не описывает все детали памяти Python.

Изменяемый default не всегда ошибка. Если функция намеренно накапливает общее состояние между вызовами, это может быть её договором. Ошибка возникает, когда мы ожидаем независимые вызовы, а список меняется. Для приоритета `2` такое поведение не опасно: число не меняется на месте. Для списка задач независимость обычно важна, поэтому общий default не подходит.

Важно, что default не переписывается после вызова. Python не выполняет выражение [] заново при каждом пропущенном аргументе: один объект связан с определением функции. Явно переданный список используется вместо него только в этом вызове. Например, вызов с новым [] получает отдельный контейнер и не очищает общий список, который будут получать следующие вызовы без аргумента. Так мы можем точно проследить, откуда возникло общее состояние.

## 02. `None` обозначает, что состояние не передали

Чтобы отделить «аргумента нет» от «передали пустой список», параметр можно связать с `None`. В нашем договоре это специальное значение означает отсутствие входного контейнера. Сама функция при каждом таком вызове создаёт новый список.

```python
def add_label(label, labels=None):
    if labels is None:
        labels = []
    labels.append(label)
    return labels

first = add_label("draft")
second = add_label("review")
provided = []
result = add_label("release", provided)
```

`first` и `second` теперь относятся к отдельным спискам. В последнем вызове функция получает именно `provided`, добавляет значение в него и возвращает ту же ссылку: `result is provided` будет `True`. `None` здесь не хранит задачи и не заменяет список; это понятный сигнал, по которому функция решает, нужно ли создать контейнер.

Можно представить форму заказа на коробку. Если поле не заполнено, служба выдаёт новую коробку для этого заказа. Если поле заполнено существующей, даже пока пустой коробкой, служба кладёт товар именно туда. Здесь незаполненное поле соответствует `None`, а переданный пустой список остаётся объектом вызывающей стороны. В реальном коде решения принимает условие, а не форма и не служба.

Проверка `if labels is None` точнее показывает смысл: мы спрашиваем, отсутствует ли входное состояние. Условие `labels == []` спрашивало бы о содержимом списка, а не об отсутствии аргумента. Эти вопросы нельзя подменять друг другом.

Это работает потому, что `None` означает отсутствие начального списка, а тело создаёт свежий контейнер при каждом таком вызове. Если список передан, условие пропускается: локальное имя `labels` продолжает указывать на входной объект. `append` меняет его, а `return labels` возвращает ту же ссылку. Само локальное имя завершит жизнь вместе с вызовом, но переданный объект останется доступен через внешнее имя.

В сигнатуре labels=None вызов без аргумента и явная передача None приводят к одному значению. Для нашего договора это намеренно: оба варианта означают, что входного списка нет, поэтому функция начинает с нового. Список задач не может быть равен None, он всегда является списком или отсутствует. В другой задаче, где None само было бы допустимыми данными, пришлось бы выбрать другой способ отличать пропуск; здесь такое усложнение не нужно.

## 03. Пустой список тоже является переданным состоянием

Пустой контейнер может быть намеренным. Вызывающий код мог подготовить список для нового запуска, сохранить на него ссылку и ожидать, что Planner заполнит именно этот объект. Условие `if not labels` объединяет `None` и пустой список, потому что оба значения считаются ложными в условии.

```python
def add_label(label, labels=None):
    if not labels:
        labels = []
    labels.append(label)
    return labels

provided = []
result = add_label("new", provided)
print(result is provided, provided)
```

Вывод будет `False []`. Функция заменила локальное имя `labels` новым списком, добавила туда `"new"` и вернула новый объект. Исходный `provided` остался пустым. Выражение `labels or []` имеет ту же проблему: для пустого списка оно выберет новый список.

Сначала мы можем предсказать исход: аргумент передан, но проверка оценивает его пустоту и теряет связь с намерением вызывающей стороны. Затем запускаем пример и сравниваем идентичность через `is`. Оператор `is` отвечает, один ли это объект; `==` сравнивает содержимое. Два пустых списка равны по содержимому, но не являются одним контейнером.

Поэтому договор `run(tasks=None)` проверяет именно `tasks is None`. Если условие истинно, создаётся новый список для обычного запуска. Иначе функция сохраняет переданный объект, в том числе `[]`. Мы не пытаемся угадать намерение по числу задач в контейнере.

Условие истинности проверяет, есть ли элементы, а не был ли передан объект. Поэтому оно иногда кажется рабочим: заполненный список остаётся на месте, а ошибка проявляется только на пустом входе. Выражение tasks or [] ведёт себя так же для пустого списка. Сверим оба случая отдельно: пустой список должен вернуться тем же объектом, заполненный список должен сохранить прежние задачи и получить добавление через команду. Равенство содержимого само этого не доказывает, для этого используем `is`.

## 04. Один список проходит через весь командный цикл

`run` выбирает состояние один раз, до цикла. Каждый обработчик получает тот же контейнер. Когда `handle_add` передаёт его дальше в `add_task`, добавленная задача остаётся видна следующей команде. `handle_list` и `handle_stats` тоже читают текущее состояние, поэтому список нельзя заново создавать для каждой ветки.

Передача списка в параметр не делает копию. Локальное имя обработчика связывается с тем же объектом, который выбрал `run`. Если обработчик добавляет или меняет задачу на месте, результат будет виден в `run` и у вызывающего кода, который передал список. Это продолжает модель ссылок из прошлого занятия.

Представим одну папку с карточками задач, которую мы передаём разным людям по очереди. Новая команда может добавить карточку, но если каждый раз выдавать пустую папку, предыдущие изменения пропадут из рабочего потока. Папка здесь соответствует контейнеру `tasks`, а обработчики соответствуют командам. Аналогия не означает, что задачи копируются или что состояние переживёт завершение программы.

Схема пути короткая: вызов `run` выбирает новый или переданный список → команды работают с этим же списком → после `exit` этот список возвращается. Во время команд меняются элементы одного состояния, а не создаются отдельные хранилища для `add`, `list` и `stats`. Если внутри списка лежат словари задач, возвращение внешнего списка не копирует эти словари. Мы обещаем сохранить контейнер запуска и прежние ссылки на его элементы; независимое копирование каждой задачи в этом занятии не нужно. Такое поведение продолжает вывод прошлого шага о поверхностной копии и вложенных объектах. После возврата локальное имя `tasks` завершит жизнь вместе с run, но список останется доступен, если вызывающий код сохранил возвращённую ссылку. Это данные текущего процесса; завершение программы не сохраняет их между запусками.

Мы не вводим `global` или `nonlocal`: нужное состояние видно в параметрах функций. Мы также не добавляем сохранение на диск. После завершения процесса список остаётся только в памяти; его явная передача лишь позволяет вызывающему коду управлять текущим запуском.

Выбор выполняется один раз до цикла. Когда аргумента нет, создаётся один новый список для этого запуска; когда список передан, локальное имя run связывается с ним. Все ветви команд передают дальше это имя, поэтому обработчик добавления меняет тот же контейнер, который затем прочитает список или статистика. Мы не копируем состояние перед каждой командой и не создаём внутри ветви новый `tasks = []`. Возврат `tasks` отдаёт наружу тот же объект, а не его копию.

Возвращаемое значение само по себе ничего не печатает. Обычный конечный вызов `run()` продолжает показывать меню и сообщения командами `print`, а вызывающий код может сохранить результат явного вызова в переменную. Вывод пользователю и передача состояния наружу остаются разными частями договора. Поэтому добавление `return` после цикла даёт возможность проверить запуск, не меняя привычные сообщения.

## 05. `break` завершает цикл, `return` завершает функцию

В обработчике `exit` команда `break` прекращает ближайший цикл. После этого выполнение продолжает идти со строки сразу после цикла. Это подходящее место, чтобы вернуть итоговое состояние:

```python
def process_commands(tasks, commands):
    for command in commands:
        if command == "exit":
            break
        # Здесь выполняется очередная команда с tasks
    return tasks
```

Это фрагмент, а не самостоятельный Planner: строка с комментарием показывает место существующей обработки команд. `break` сам по себе ничего не возвращает из функции. Он только прекращает цикл. Строка `return tasks` завершает функцию и отдаёт объект вызывающему коду.

Представим, что мы вышли из коридора, но ещё можем подойти к стойке и передать папку коллеге. `break` соответствует выходу из коридора, а `return` передаче результата из функции. Если перепутать команды, `break` не отдаст список, а `return` при обычной команде преждевременно остановит весь `run`.

Команда `break` выходит из ближайшего цикла, затем выполнение остаётся внутри той же функции. Там можно завершить общую часть и выполнить один `return`. Сам `return` немедленно завершил бы весь вызов и не позволил обработать следующие команды, если поставить его после обычного действия в цикле. В реальном маршруте `exit` должен спокойно закончить цикл и вернуть один итоговый список. Штатный вызов `run()` без аргумента продолжает запускать консольный интерфейс (CLI) как раньше. Его возвращаемое значение может быть не использовано обычным запуском, но при явном вызове функция отдаёт состояние тестирующему коду.

## 06. Что мы будем делать в практике

Теперь используем короткий эксперимент, чтобы увидеть общий изменяемый список по умолчанию, а затем применим безопасный договор к уже существующему `run` в проекте StudyHub. Мы сохраним знакомые операции Planner и изменим только жизненный цикл списка.

1. **Исследуем изменяемый default:** увидим повторное использование одного объекта и объясним разницу между отсутствующим аргументом и пустым списком.
2. **Обновим `run`:** начнём запуск с новым списком при отсутствии состояния, сохраним переданный контейнер и отдадим его после `exit`.
3. **Проверим прежнее поведение:** сравним независимые обычные запуски, пустой и заранее заполненный переданные списки, следующий id и команды Planner.

Эксперимент объясняет, почему `[]` не должен быть default состояния запуска. Проверка `None` и передача ссылок подготавливают изменение существующей функции; команды из предыдущих занятий показывают, что состояние проходит по одному маршруту. Импорт `main.py`, JSON, глобальный список и файловое хранение в этой работе не появляются.
