## 00. От знакомой функции к ясному вызову

В прошлом занятии мы отделили `list` и `stats` в обработчики: `run` передаёт им общий список через параметры. Теперь используем знакомые определения и вызовы на другом участке того же Planner — фабрике задачи. Разберём, как способ передачи значений определяет, что попадёт в каждый параметр.

1. **Точка старта:** обработчики и предметные функции получают данные через параметры; фабрика получает все значения при создании задачи.
2. **Новый вопрос:** как сделать приоритет необязательным для вызова и сохранить привычный ввод через CLI?
3. **Результат:** мы понимаем позиционные и именованные аргументы, значения по умолчанию и ошибки неверной привязки.

Сначала разберём, как Python связывает значения с именами в определении. Затем отделим допустимые сочетания от ошибок и применим эти правила к настоящей фабрике, не меняя устройство задачи и команды Planner.

## 01. Параметр и аргумент находятся по разные стороны вызова

В определении функции параметр задаёт имя для входного значения. В вызове аргументом называют само переданное значение. Например, в `def badge(name, label):` имена `name` и `label` являются параметрами, а в `badge("SQL", "курсы")` строки служат аргументами. Когда функция начинает работать, Python связывает аргументы с параметрами, а код тела обращается уже к параметрам.

Эту связь можно представить как форму с подписанными полями. Определение перечисляет поля, а вызов передаёт значения. Пока мы не заполнили поле, функция не знает, какое значение использовать. Граница аналогии в том, что Python не читает смысл строки или числа: если два значения переставить, он не догадается о намерении и будет следовать правилам вызова.

```python
def make_badge(name, label):
    return f"{label}: {name}"

result = make_badge("SQL", "курс")
print(result)
```

Здесь `name` получает первую строку, `label` вторую, поэтому функция возвращает `курс: SQL`. Аргументы не являются частью определения, а параметры не являются переменными, которые нужно объявить отдельно в месте вызова. Это две стороны одного договора: функция задаёт имена входов, вызывающий код предоставляет значения.

Параметры не заполняются заранее, когда Python читает определение функции. Связь создаётся отдельно для каждого вызова. Если вызвать одну функцию дважды с разными значениями, её параметры получают значения текущего вызова. Поэтому сигнатуру мы читаем в определении, а аргументы ищем там, где функцию вызывают.

## 02. Позиционные аргументы связываются по порядку

Когда аргументы записаны без имён, Python сопоставляет их параметрам слева направо. Первое значение предназначено первому параметру, второе второму. Этот способ компактен и подходит, если порядок параметров хорошо известен и сами значения легко различить.

```python
def route_label(start, finish):
    return f"{start} -> {finish}"

print(route_label("Центр", "Парк"))
print(route_label("Парк", "Центр"))
```

Оба вызова допустимы. Во втором Python не обнаруживает ошибку: значения строковые и подходят по количеству. Но смысл маршрута меняется, потому что поменялись местами аргументы. Позиционная привязка проверяет расположение, а не смысл и тип значения. Поэтому вызов может быть синтаксически корректным, но выражать не то, что задумал автор.

Так же передавались значения в прежней `create_task`: сначала идентификатор, затем заголовок, затем приоритет. Читая позиционный вызов, мы восстанавливаем назначение каждого аргумента по сигнатуре функции. При длинном вызове или нескольких числах легко ошибиться в порядке. Тогда можно записать имена рядом со значениями.

## 03. Именованные аргументы показывают назначение значения

Именованный аргумент записывается как `имя_параметра=значение`. Python ищет параметр с таким именем и связывает с ним значение независимо от места этого аргумента среди других именованных аргументов.

```python
def route_label(start, finish):
    return f"{start} -> {finish}"

print(route_label(start="Центр", finish="Парк"))
print(route_label(finish="Парк", start="Центр"))
```

Результаты совпадают, хотя именованные аргументы во втором вызове идут в другом порядке. Связь каждого значения видна прямо в месте вызова. Это особенно полезно, когда несколько параметров принимают похожие значения или флаг записан как `True` либо `False`.

Здесь помогает аналогия с адресом на посылке: подпись сообщает, к какому полю относится содержимое. Но подпись должна совпасть с параметром в определении. Если написать имя, которого у функции нет, Python не угадывает ближайшее и не создаёт новое поле. Именование уточняет вызов, но не меняет набор параметров и алгоритм функции.

Именованный аргумент можно сочетать с позиционными. Сначала мы разберём порядок такого сочетания, чтобы один параметр не получил два разных значения и вызов оставался однозначным.

## 04. Сочетание форм не должно дублировать параметр

В обычном вызове позиционные аргументы записываются раньше именованных. После перехода к именам оставшиеся значения тоже указываются с именами. Например, `route_label("Центр", finish="Парк")` допустим: позиционное значение заполняет `start`, именованное заполняет `finish`.

Обратная форма `route_label(start="Центр", "Парк")` недопустима: позиционный аргумент стоит после именованного. Python отклоняет такую запись ещё при разборе кода, поэтому тело функции не запускается. Это синтаксическая ошибка, а не неправильный результат функции.

Есть ещё правило однократной привязки. Если первый параметр уже получил позиционное значение, нельзя передать ему другое именованное значение: `route_label("Центр", start="Парк")`. Для человека оба значения видны, но один параметр не может одновременно означать две точки отправления. Сначала Python связывает аргументы и сообщает о конфликте, затем только при успешной привязке начинает выполнять тело.

Когда часть значений разрешено не передавать, эту возможность задают в определении функции. Она не отменяет перечисленные правила: именованный параметр должен существовать, один параметр заполняется один раз, обязательные значения остаются обязательными.

## 05. Значение по умолчанию используется только при пропуске

Параметр со значением по умолчанию можно не указывать в вызове. Python использует это значение, только если соответствующий аргумент отсутствует. Если значение передано явно, используется оно.

```python
def notice(text, prefix="ЗАДАЧА"):
    return f"[{prefix}] {text}"

print(notice("Проверить тесты"))
print(notice("Проверить тесты", prefix="ВАЖНО"))
```

В первом вызове `prefix` получает настройку из определения. Во втором он получает явную строку `ВАЖНО`. Значение по умолчанию не является проверкой ввода и не исправляет неподходящий аргумент. Оно описывает обычный вариант, который допустимо выбрать автоматически, если вызывающий код ничего не уточнил.

Обязательные параметры в обычной сигнатуре перечисляются до параметров со значениями по умолчанию. Иначе определение неоднозначно: Python не сможет понять, какое пропущенное позиционное значение относится к параметру без default. Поэтому сначала указывают необходимые данные, после них настройки, которые разрешено опустить.

Хороший default соответствует нормальному поведению функции. Не стоит делать необязательным важное значение только ради короткой записи: функция тогда может успешно выполниться, хотя в ней не хватает данных. В Planner приоритет уже имеет согласованное обычное значение `2`, но интерфейс продолжает спрашивать его у человека. Если CLI передаёт введённый приоритет, именно он и используется.

Пропуск аргумента отличается от явной передачи `None`, нуля или пустой строки. Если значение указано, Python не применяет default, даже если оно пустое или равно нулю. Функция получает именно переданное значение; отдельные проверки его смысла, если они нужны, относятся к правилам самой функции.

## 06. `TypeError` показывает, что вызов не связан с сигнатурой

Если обязательный аргумент пропущен, имя аргумента неизвестно или один параметр получил два значения, Python сообщает `TypeError`. Для этих ошибок тело функции ещё не выполнялось: отказ произошёл при попытке сопоставить аргументы параметрам.

Например, `route_label(start="Центр")` не передаёт обязательный `finish`; `route_label(origin="Центр", finish="Парк")` указывает неизвестное имя; `route_label("Центр", start="Парк", finish="Парк")` дважды заполняет `start`. Каждый случай нарушает отдельное правило привязки. Мы можем прочитать сигнатуру и найти причину, не меняя тело функции.

Значение по умолчанию помогает только при пропуске того параметра, у которого оно задано. Оно не заполняет другой обязательный параметр и не делает неизвестное имя допустимым. Ошибки вроде некорректного значения внутри тела относятся к другому этапу выполнения. Здесь нам нужно распознать неправильный вызов; перехватывать или проектировать обработчик ошибки мы пока не будем.

Мы различаем и момент отказа. Позиционный аргумент после именованного не образует корректную запись вызова, поэтому Python сообщает синтаксическую ошибку при разборе. Пропущенный параметр, неизвестное имя или повторная привязка находятся позже: запись построена, но её значения нельзя согласовать с сигнатурой. В обоих случаях тело не выполняется, однако причина различается.

## 07. Уточняем договор настоящей фабрики Planner

В существующем проекте задача остаётся словарём с полями `id`, `title`, `priority` и `is_done`. `create_task` принимает идентификатор, заголовок и приоритет. Вызывающая операция назначает идентификатор, передаёт фабрике заголовок и приоритет, а обработчик CLI до этого получает оба значения от пользователя.

Мы меняем только договор приоритета: идентификатор и заголовок по-прежнему обязательны, а для `priority` задаётся default `2`. Это позволяет вызвать реальную фабрику без указания приоритета там, где подходит обычное значение. Структура словаря, начальное `is_done=False` и назначение идентификатора остаются прежними.

Важно проследить весь путь значения. Обработчик добавления читает приоритет, передаёт его операции добавления, а та передаёт его фабрике. Явное значение продолжает побеждать default, поэтому привычная команда не теряет ввод. Мы не убираем вопрос из CLI, не создаём вторую фабрику и не переносим расчёт id.

Существующий вызов из `add_task` передаёт три значения, поэтому после уточнения сигнатуры он остаётся допустимым. Новая возможность нужна только вызовам, которые намеренно пропускают `priority`. Мы сохраняем прежний путь команды и одновременно задаём полезное значение для такого сокращённого вызова.

Чтобы проверить именно исходную функцию отдельно, в Windows мы запускаем `python -i main.py` из папки проекта. Файл сначала выполняет обычный CLI; после команды `exit` Python оставляет определения в интерактивном режиме с приглашением `>>>`. Так мы вызываем настоящую фабрику без импорта файла и без временной копии функции.

Перед правкой ищем реальные вызовы `create_task`, чтобы знать, на какую сигнатуру они опираются. После правки проверяем пропуск приоритета, явно переданное значение и именованный вызов отдельно. Затем повторяем добавление через CLI и убеждаемся, что новая задача получает тот же id, введённый приоритет, прежние поля и статус незавершённой.

## Что мы будем делать в практике

В практике мы продолжаем существующий StudyHub Planner и используем короткие вызовы в интерпретаторе, чтобы увидеть правила связывания на настоящей функции.

1. **Проследим вызовы:** найдём цепочку от обработчика добавления до `create_task`; подтвердим текущих потребителей и их аргументы.
2. **Проверим правила вызова:** исследуем позиционные, именованные и ошибочные сочетания; различим отказ связывания и выполнение тела.
3. **Уточним сигнатуру:** зададим default только для приоритета; сохраним обязательные id и заголовок, а также четыре поля задачи.
4. **Сравним default и явный ввод:** вызов без приоритета использует `2`, а вызов с приоритетом сохраняет его значение.
5. **Повторим CLI-сценарий:** добавим задачу обычной командой; подтвердим прежний ввод, назначение id, отображение и состояние задачи.

Так мы связываем правило Python с конкретной функцией проекта и проверяем не только короткий вызов, но и привычный путь пользователя. В следующем занятии проследим, что именно связывается с параметром, когда это список или другой изменяемый объект. Фабрика остаётся частью проекта с ясным договором.
