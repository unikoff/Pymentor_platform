## 00. Вступление

В 37.2 Planner получил законченный путь от команды до сохранённого результата. Теперь подготовим для этого же проекта отдельный Python перед первой внешней зависимостью.

1. **Точка старта:** готовое приложение запускается установленным системным Python и использует только стандартную библиотеку.
2. **Новый вопрос:** как добавить инструмент разработки так, чтобы он устанавливался для нужного проекта и не менял Python других проектов?
3. **Результат:** у Planner есть собственный выбранный интерпретатор; приложение продолжает запускаться, а 38 может установить в эту среду pytest.

Это промежуточная настройка уже работающего продукта: его команды и архитектура остаются прежними. Сначала различим сам проект и среду, из которой Python его запускает.

## 01. Проект, интерпретатор и пакеты

- Что и зачем объяснить: исходный код — файлы Planner, интерпретатор — программа Python, а установленные библиотеки — инструменты, которые он может импортировать. Виртуальная среда отделяет набор пакетов одного проекта от системного Python и других проектов.
- Механизм и порядок: сравнить системный Python со стандартной библиотекой и локальную `.venv`, куда позже можно установить сторонний пакет. Папка среды хранит свой интерпретатор и пакеты; она не копирует приложение и не становится вторым репозиторием.
- Пример и типичная путаница: два проекта используют один Python-код, но могут иметь разные наборы сторонних библиотек. Наличие папки `.venv` ещё не означает, что VS Code или команда `python` выбрали её интерпретатор.
- Первое самостоятельное действие: по схеме проекта показать, где остаются `app/` и данные, а где будут находиться локальные инструменты; ученик объясняет, почему `.venv` не заменяет исходники.
- Переход: после понимания назначения среды создать её рядом с существующим проектом.

## 02. Создать `.venv` в корне Planner

- Что и зачем объяснить: среда создаётся из установленного Python для текущего проекта. Папка `.venv` находится рядом с исходниками и сохраняется локально.
- Механизм и порядок: из корня проекта выполнить `py -3.12 -m venv .venv`. Разобрать `py -3.12` как выбор Python 3.12, `-m venv` как запуск стандартного модуля создания среды, `.venv` как имя целевой папки. Проверить появление локального интерпретатора и каталога пакетов.
- Пример и типичная путаница: команда запускается из корня существующего Planner, а не создаёт новый проект. Если `.venv` уже есть, сначала проверить её версию и путь; не удалять и не пересоздавать среду автоматически.
- Первое самостоятельное действие: проверить рабочую папку и создать среду, только если её нет; наблюдаемый результат — локальный Python по пути `.venv\Scripts\python.exe`.
- Опора для повторного обращения: `-m venv` подготавливает среду, а не запускает Planner и не устанавливает pytest.
- Переход: наличие интерпретатора ещё не выбирает его для VS Code.

## 03. Выбрать и проверить Python в VS Code

- Что и зачем объяснить: редактор, терминал и отдельный процесс Python могут использовать разные интерпретаторы. Проверка только номера версии не показывает, откуда именно запущен процесс.
- Механизм и порядок: выбрать `.venv\Scripts\python.exe` через `Python: Select Interpreter`. Затем открыть новый Python REPL выбранным интерпретатором, объяснить стандартный модуль `sys` и его атрибут `executable`, выполнить `import sys` и `print(sys.executable)`.
- Пример и типичная путаница: ожидаемый полный путь содержит корень проекта и `.venv\Scripts\python.exe`. Выбор другого Python в VS Code не удаляет среду, но пакеты окажутся не там, где их ожидает проект.
- Первое самостоятельное действие: выбрать интерпретатор Planner и прочитать напечатанный путь; результат подтверждает локальный Python, а не только совпадение версии.
- Опора для повторного обращения: `sys.executable` показывает интерпретатор текущего процесса; для следующей установки пакета важно выбрать тот же Python.
- Переход: после проверки пути запустить существующий Planner этим интерпретатором.

## 04. Запустить приложение без изменения поведения

- Что и зачем объяснить: приложение и выбор интерпретатора — разные части запуска. Переход на `.venv` сам по себе не требует переписывать импорты, сервис или хранение.
- Механизм и порядок: выполнить принятую команду Planner из README, явно вызвав локальный Python: `.\.venv\Scripts\python.exe -m app.main`. Сопоставить её с прежним запуском: меняется только исполняемый файл Python.
- Пример и типичная путаница: создание среды не запускает код и не создаёт второй Planner. Если приложение открывает меню, достаточно проверить его и выйти; не менять задачи в рабочем JSON ради проверки.
- Первое самостоятельное действие: запустить тот же Planner из корня через `.venv`, увидеть привычное меню и завершить приложение; критерий — поведение и сохранённые данные не изменились.
- Переход: локальный интерпретатор работает; теперь нужно исключить его файлы из истории и записать способ восстановления.

## 05. Оставить среду локальной и подготовить следующий шаг

- Что и зачем объяснить: `.venv` зависит от машины и не передаётся как часть исходников. Git игнорирует папку по сохранённому правилу, а README объясняет, как восстановить среду.
- Механизм и порядок: добавить `.venv/` в корневой `.gitignore`, сохранив правила `__pycache__/` и `*.pyc`; проверить через `git check-ignore`. Обновить README командами создания среды и запуска Planner. Коротко объяснить `python -m pip`: так pip запускается выбранным Python и ставит пакет для него.
- Пример и типичная путаница: ignore не удаляет файлы и не отменяет уже отслеживаемый путь. Здесь не устанавливать pytest и не добавлять `requirements-dev.txt`; это сделает следующее занятие для выбранной `.venv`.
- Первое самостоятельное действие: проверить, что файл внутри `.venv` игнорируется, и записать команды восстановления и запуска в README; результат можно повторить на новой копии проекта.
- Переход к практике: приложение подготовлено к инструменту разработки, но на этом шаге не получает новых пакетов и тестов.

## 06. Что мы будем делать в практике

**Формат и исходная опора:** информационная настройка в том же StudyHub Planner; начинаем с ожидаемого результата 37.2 и системного Python 3.12. Перед действиями сверяем рабочую папку, README, `.gitignore` и наличие локальной `.venv`.

Общий результат — тот же Planner запускается предсказуемым Python из собственного окружения, а инструкции позволяют восстановить настройку без передачи папки среды.

1. **Проверим входное состояние:** подтвердим корень, текущую команду запуска, версию системного Python и правила `.gitignore`. Если `.venv` уже существует, проверим её, не удаляя локальные файлы.
2. **Создадим или выберем среду:** при отсутствии выполним `py -3.12 -m venv .venv`, выберем её в VS Code и проверим `sys.executable`. Критерий — путь ведёт в `.venv` этого проекта.
3. **Повторим запуск:** запустим Planner его локальным Python и выйдем без изменения задач. Критерий — привычное меню работает, данные и поведение приложения сохранены.
4. **Оформим восстановление:** добавим `.venv/` в `.gitignore`, проверим игнорирование, дополним README командами создания среды и запуска. Критерий — среда остаётся локальной, инструкции повторимы; pytest, тесты и код приложения не затронуты.

Теория отвечает на три практических вопроса: где находится среда, какой Python запускает проект и как восстановить настройку. 37.2 передаёт готовое приложение, а 38 использует выбранную среду для первой внешней зависимости и тестов; повторной сборки Planner между ними нет.
## Уточнения настройки и самостоятельной проверки

- Команды PowerShell и код REPL разделены по приглашениям PS …> и >>>. Перед запуском приложения нужно exit() из REPL; ошибки No module named app и SyntaxError на команду терминала ведут к конкретной проверке корня и оболочки.
- Перед созданием: Get-Location, Get-ChildItem -Force -Name, py -3.12 --version, Test-Path .venv. Нет новой синтаксической конструкции if/else PowerShell: ученик выбирает действие по результату проверки. Версия ожидается 3.12.x.
- Если существующая среда не запускается или имеет другую версию, закрыть её процессы, сохранить папку под свободным резервным именем через Проводник, исключить точное имя из Git и создать новую .venv. Резервная папка не используется как переносимая среда и не удаляется. Готовая рабочая .venv используется без пересоздания.
- Если py отсутствует при установленном Python 3.12, выбрать его полный путь и вызвать через & "путь\python.exe" сначала --version, затем -m venv .venv. Если принятой версии нет, завершить первоначальную установку Python.
- Различить выбор редактора и работающий процесс: сначала прямой запуск .venv\Scripts\python.exe, затем отдельный новый Python: Start Terminal REPL. В каждом сеансе заново import sys и print(sys.executable). Выбор Python не переключает старый REPL.
- Активация объяснена как сокращение пути; прямой вызов интерпретатора работает без изменения политики PowerShell. Среда зависит от базового Python и не переносится копированием каталога.
- Итоговая самостоятельная задача: повторить проверку пути и запуск в новом терминале по своему README. Объяснить, почему одинаковая версия Python не гарантирует общий набор пакетов и почему в 38 нужен локальный Python -m pip. Пакет пока не устанавливается.
- Актуальное имя команды REPL сверено с документацией Microsoft: https://code.visualstudio.com/docs/languages/python/ .
