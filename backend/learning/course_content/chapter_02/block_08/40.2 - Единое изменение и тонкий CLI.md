- Результат в проекте: один PlannerService выполняет все предметные действия; CLI получает только сервис; build_service использует переданную зависимость или по умолчанию выбирает JsonStorage. Переходные CRUD-функции, callback сохранения и второй вход storage в CLI удалены.

## 00. Вступление

В предыдущем шаге сервис уже отвечает за чтение, а изменения пока распределены между несколькими путями. Теперь нужно довести переход до единой модели работы и сохранить поведение привычного Planner.

1. **Точка старта:** чтение проходит через PlannerService, но add и done ещё выполняют переходные функции с тем же storage.
2. **Новый вопрос:** как распределить ответственность, чтобы каждая команда проходила через одни и те же объекты и правила?
3. **Результат:** все действия выполняет один сервис, CLI только общается с пользователем, а новое удаление сохраняет прежние данные и команды.

Эти пункты связаны движением от смешанного состояния к законченному продукту. Чтобы оно не выглядело механическим переносом функций по файлам, сначала нужно понять сотрудничество объектов.

## 01. Схема взаимодействия как модель ООП

- Что и зачем объяснить: продолжить схему из плана 40.1, где CLI обращается к сервису, а сервис читает список через storage. Теперь она охватывает создание зависимостей и полный цикл изменения, чтобы увидеть в ООП сотрудничество объектов и владение ответственностью.
- Механизм и порядок: связать сборку: build_service выбирает или получает один storage и передаёт его в PlannerService; CLI получает готовый сервис. Затем проследить действие: команда CLI → метод сервиса → storage.load() → изменение Task или набора → storage.save() → результат обратно в CLI. Отметить, что сервис хранит ссылку на storage и использует его публичный договор.
- Пример или типичная путаница: JsonStorage и MemoryStorage занимают одну роль и выбираются по одному; передача storage сервису — отношение «использует», а не наследование. CLI не меняет Task напрямую и не обращается к файлу.
- Переход к следующему шагу: после схемы сотрудничества объектов разобрать порядок успешного изменения и отказа.

## 02. Путь успешного изменения и путь отказа

- Что и зачем объяснить: показать, почему сервису нужны актуальные данные перед действием и почему сохранение должно следовать только за допустимым изменением.
- Механизм и порядок: получить текущий набор через storage; проверить вход и найти нужную Task, если операция адресная; выполнить предметное изменение; сохранить новый набор; вернуть согласованный результат. Сопоставить с чтением, которое не сохраняет данные, и с отказом, который не должен менять набор или вызывать save.
- Пример или типичная путаница: возврат успешного результата после save; повторное done уже завершённой задачи возвращает Task без лишней записи. Не обещать откат памяти, если сама операция save завершилась ошибкой.
- Переход к следующему шагу: применить этот порядок сначала к знакомым add и done.

## 03. Перенос add и done в PlannerService

- Что и зачем объяснить: перенести существующую предметную работу, а не создавать второй CRUD. Сервис использует готовую Task, прежние валидаторы и один storage.
- Механизм и порядок: для add опираться на текущий набор при выборе id, создать незавершённую Task с независимыми tags, сохранить результат и вернуть объект. Для done проверить тот же договор id, изменить одну найденную Task её методом и сохранить только реальный переход.
- Пример или типичная путаница: метод сервиса возвращает Task, а не старый булев результат «найдена ли задача». Повторное завершение не меняет пользовательский смысл команды и не требует нового сохранения.
- Переход к следующему шагу: после переноса прежних изменений в сервис добавить единственную новую пользовательскую операцию занятия.

## 04. Удаление как действие над набором

- Что и зачем объяснить: отделить проверку допустимого id от ситуации, когда корректный id не найден; связать удаление с уже знакомыми списками и прикладной ошибкой.
- Механизм и порядок: найти существующую задачу по id, удалить только её из текущего набора, сохранить оставшиеся задачи и вернуть None. Объяснить, что остальные id сохраняются, а новый id по-прежнему вычисляется по текущему набору.
- Пример или типичная путаница: неизвестный id даёт TaskNotFoundError без изменения и save; удаление не перенумеровывает соседей и не обещает пожизненную уникальность уже освобождённого номера.
- Переход к следующему шагу: когда сервис содержит все действия, CLI можно свести к одному способу их вызова.

## 05. Один путь команды через тонкий CLI

- Что и зачем объяснить: CLI отвечает за ввод, разбор, вызов подходящего метода сервиса, форматирование и сообщения; предметные правила, CRUD и файловое хранение ему не принадлежат.
- Механизм и порядок: для каждой команды сопоставить ввод с методом сервиса и его результатом; сохранить существующее поведение сообщений и ожидаемых ошибок. Удалить переходные функции после переключения всех потребителей, а не раньше.
- Пример или типичная путаница: не оставлять скрытый второй путь через callback, старую функцию или storage, переданный в CLI. ValueError и TaskNotFoundError превращаются в понятное сообщение; StorageError сохраняет прежнюю границу остановки сессии. Не перехватывать неожиданную программную ошибку общим обработчиком. Успех сообщается только после успешного save.
- Переход к следующему шагу: рассмотреть, кто создаёт объекты для этого единого пути и откуда сервис получает storage.

## 06. Сборка и явная зависимость

- Что и зачем объяснить: закрепить композицию в точке сборки и показать, почему переданная реализация storage остаётся заменяемой.
- Механизм и порядок: build_service при отсутствии аргумента создаёт JsonStorage для принятого пути; при явном аргументе использует именно его и собирает PlannerService. CLI получает готовый сервис. Различить создание объекта и начало пользовательского сценария.
- Пример или типичная путаница: проверять отсутствие зависимости через None, а не через истинность объекта: пустой MemoryStorage является намеренно переданным storage. Импорт и сборка не должны запускать input, load или запись.
- Переход к следующему шагу: проверить, что переход на новую схему объектов сохранил возможности и границы прежнего Planner.

## 07. Регрессия прежних возможностей

- Что и зачем объяснить: после архитектурного переноса проверить наблюдаемое поведение всего накопленного продукта, а не только новые методы сервиса.
- Механизм и порядок: пройти знакомые команды вместе с delete на памяти и JSON; отдельно проверить восстановление при новом запуске, отказы по данным и id, повтор done и отсутствие лишнего сохранения. Тестовый фреймворк ещё не вводить: следующая тема — первые проверки через pytest.
- Пример или типичная путаница: успешная команда подтверждается и результатом для пользователя, и правильным состоянием; ошибка storage не должна выглядеть как ложный успех. Прежний рабочий файл не используется для разрушительных проверок.
- Переход к следующему шагу: готовые методы и продуктовые договоры станут основой автоматических тестов занятия 41.

## 08. Что мы будем делать в практике

**Формат и исходная опора:** проектная работа в том же Planner; начинаем с состояния после 40.1, где сервис обслуживает чтение, а изменения ещё подключены переходными функциями к тому же storage.

Общий результат — законченный пользовательский путь, в котором все действия проходят через один PlannerService, а привычный CLI продолжает работать с тем же JSON.

1. **Перенесём изменения в сервис и добавим удаление:** получим один набор предметных действий и понятное поведение для отсутствующего id.
2. **Переключим команды и сборку на единые объекты:** получим CLI без собственного CRUD и проверим, что переданная зависимость сохраняется, а обычный запуск выбирает JsonStorage.
3. **Проверим старые и новые сценарии на обоих storage:** подтвердим прежние команды, удаление, сохранение успешных изменений, безопасные отказы и восстановление данных после запуска.

Разобранная схема сотрудничества объектов объясняет, куда относится каждый вызов; порядок load → проверка → изменение → save связывает эту схему с поведением сервиса. Поэтому практика закрепляет не только новую команду, но и цельный ООП-путь приложения перед автоматизацией проверок в следующем занятии.
