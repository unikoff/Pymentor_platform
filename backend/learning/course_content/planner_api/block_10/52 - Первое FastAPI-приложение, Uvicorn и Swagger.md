## 00. От проверки чужого сервера к своему

В прошлом занятии мы отправляли запросы в Postman Echo. Echo показывал, что получил, но не выполнял правила Planner. Теперь запрос будет обрабатывать наше Python-приложение.

У нас уже есть Persistent Planner: CLI, модель задачи, сервис и JSON-хранилище. Мы не создаём вторую копию проекта. CLI остаётся на месте. Рядом с ним появится HTTP-интерфейс в `app/api.py`, который пока умеет только сообщить, что приложение отвечает.

Для этого встретятся три роли:

- **Клиент** отправляет запрос. Это может быть браузер, Postman или Swagger UI.
- **Uvicorn** запускает процесс сервера, принимает HTTP-соединение и передаёт запрос приложению.
- **FastAPI** описывает приложение и связывает запрос с нужной Python-функцией.

Путь одного запроса выглядит так:

```text
Браузер или Postman
    → HTTP request
Uvicorn
    → приложение FastAPI
    → функция маршрута
    ← HTTP response
Uvicorn
    ← ответ клиенту
```

В практике мы добавим `GET /health` в существующий проект, запустим его локально и проверим снаружи. Маршрут не будет читать или менять задачи. Сейчас важно научиться отделять код приложения от процесса сервера.

**Вспомните:** если Echo возвращал `200`, создал ли он задачу Planner? Нет. Он подтверждал ответ Echo. В этом занятии мы запустим собственное приложение и проверим именно его ответ.

## 01. FastAPI задаёт поведение приложения

FastAPI это Python-фреймворк для создания HTTP API. Фреймворк даёт общие механизмы, а мы описываем маршруты и поведение для запросов. В других проектах такие маршруты связывают веб-клиент с аккаунтами, заказами, файлами или внутренними сервисами.

Создание объекта `FastAPI` ещё не включает сетевой сервер:

```python
from fastapi import FastAPI

app = FastAPI(title="Уведомления")
```

`FastAPI` здесь имя класса. Вызов `FastAPI(...)` создаёт его экземпляр, а переменная `app` хранит этот объект. В него FastAPI добавляет настройки и зарегистрированные маршруты. Название `title` попадёт в документацию, но не изменит адреса запросов.

Пока этот код просто описывает приложение. Порт никто не слушает. Для работы по сети приложение позже запустит Uvicorn.

**Верно или неверно?** После выполнения `app = FastAPI()` браузер уже может подключиться к порту 8000.

**Ответ:** неверно. Создан объект приложения, но серверный процесс ещё не запущен.

## 02. Маршрут соединяет HTTP-запрос с функцией

Маршрут, или endpoint, задаётся парой **HTTP-метод + path**. Например, `GET /status` и `POST /status` это разные операции. В FastAPI декоратор указывает, какую функцию вызвать для такой пары.

Рассмотрим независимый пример:

```python
from fastapi import FastAPI

app = FastAPI()

@app.get("/status")
def read_status():
    return {"service": "notifications", "active": True}
```

Строка `@app.get("/status")` регистрирует обработчик для GET по path `/status`. `def read_status()` задаёт функцию, которую вызовут при подходящем запросе. Функция не выполняется в момент чтения файла. FastAPI вызывает её позже, когда запрос совпадёт с маршрутом.

В нашем проекте появится другая пара: `GET /health`. Её задача не показать Planner целиком, а вернуть короткий сигнал, что приложение смогло обработать запрос.

### Соедините части маршрута

Сопоставьте фрагмент с его ролью:

- `@app.get("/status")` задаёт метод и path;
- `def read_status():` объявляет обработчик;
- `return {...}` задаёт значение ответа.

Декоратор не запускает сервер, а функция не выбирается только по имени. Нужны совпадающие метод и path.

## 03. Значение Python становится HTTP-ответом

Обработчик может вернуть словарь Python. FastAPI преобразует его в JSON и формирует HTTP-ответ. Для обычного успешного маршрута используется статус `200 OK`.

Для предыдущего примера клиент увидит JSON body:

```json
{
  "service": "notifications",
  "active": true
}
```

В Python значение `True` записывается с большой буквы. В JSON логическое значение выглядит как `true`. FastAPI выполняет это преобразование.

У проверки `health` узкая задача. Ответ `{"status": "ok"}` подтверждает, что приложение обработало этот запрос. Он не проверяет JSON-файл Planner, базу данных или почтовую систему. Таких проверок в этом маршруте нет.

**Проверьте вывод.** Если `GET /health` вернул `200` и `{"status": "ok"}`, что мы знаем?

**Ответ:** приложение приняло этот запрос и сформировало ответ. Мы ещё ничего не знаем о работе операций с задачами.

## 04. Uvicorn принимает запросы и передаёт их FastAPI

Uvicorn это ASGI-сервер. Он запускает приложение, слушает сетевой адрес и передаёт запросы FastAPI. После работы обработчика Uvicorn отправляет HTTP-ответ клиенту.

ASGI задаёт общий интерфейс между сервером и Python web-приложением. Его можно представить как стандартный разъём: Uvicorn не должен знать правила Planner, а FastAPI не обязан управлять сетевым портом. На этом шаге достаточно понимать направление запроса и ответа. Внутреннее устройство ASGI и асинхронность сейчас не изучаем.

```text
Клиент → Uvicorn → FastAPI → функция маршрута
Клиент ← Uvicorn ← FastAPI ← результат функции
```

Если в файле описан маршрут, но Uvicorn не запущен, запросу некому принять соединение. Если Uvicorn работает, но подходящего маршрута нет, сервер всё равно ответит, но сообщит об ошибке маршрутизации.

## 05. Строка запуска указывает модуль и объект

Чтобы запустить приложение, Uvicorn нужно сообщить, где его найти. Команда использует строку из двух частей, разделённых двоеточием:

```powershell
python -m uvicorn app.api:app --reload
```

- `python -m uvicorn` запускает Uvicorn через выбранный интерпретатор Python. Это помогает не смешивать пакеты разных окружений.
- `app.api` означает модуль `app/api.py`.
- часть после двоеточия, `app`, означает объект FastAPI внутри модуля.
- `--reload` перезапускает сервер при изменениях кода. Это удобно во время разработки, но не является настройкой рабочего сервера.

Команду выполняют из корня существующего проекта, чтобы Python видел пакет `app`. Наша структура дополняется одним модулем. Остальные файлы не нужно перемещать: каждый остаётся в своей папке и сохраняет прежнюю ответственность.

```text
studyhub/
├── app/
│   ├── __init__.py
│   ├── main.py
│   ├── cli.py
│   ├── services.py
│   ├── models.py
│   ├── storage.py
│   ├── validators.py
│   ├── exceptions.py
│   └── api.py
├── data/
│   └── tasks.json
├── docs/
├── labs/
├── tests/
├── requirements.txt
├── postman/
│   ├── HTTP collection
│   └── Echo environment
├── .gitignore
└── README.md
```

Внутри `app/` остаются Python-модули проекта. `services.py` содержит правила `PlannerService`, `storage.py` читает и сохраняет данные, `models.py` описывает `Task`. Новый HTTP-вход появится в `api.py`, а `main.py` продолжит запускать CLI. Данные, документация и тесты остаются в корне на своих местах.

Файлы клиента лежат отдельно в `postman/`: `planner-http-lab.postman_collection.json` и `echo.postman_environment.json`. В присланной копии репозитория этой папки и корневого `requirements.txt` пока нет, поэтому создайте их в `studyhub/`, если они ещё не появились после прошлого занятия. В `requirements.txt` добавьте FastAPI и Uvicorn, сохранив остальные зависимости. Сейчас API отвечает только на `health` и ещё не вызывает `PlannerService`.

`app/main.py` не заменяем. CLI и HTTP API это два входа в тот же проект. На этом шаге API пока не вызывает PlannerService: сначала проверим запуск и маршрут отдельно от данных.

**Сверка с репозиторием ученика.** В текущем `app/main.py` путь к JSON строится относительно каталога `app`, поэтому фактическое место сохранения получается `app/data/tasks.json`. При этом в GitHub уже есть отдельный `data/tasks.json` в корне. `GET /health` не затрагивает эту разницу, но перед подключением задач в следующей практике нужно будет согласовать один рабочий путь. Не создавайте второй файл только ради API.

В этой же копии `.gitignore` содержит правило `*.json`. Поэтому экспортированные Postman-файлы тоже останутся вне Git, а уже отслеживаемый `data/tasks.json` это правило не перестанет отслеживать. Не публикуйте реальные задачи; если экспорты нужно хранить в Git, правило игнорирования следует уточнить отдельно.

### Расставьте запуск по порядку

1. Uvicorn импортирует `app.api`.
2. Python создаёт объект `app` и регистрирует маршруты.
3. Uvicorn начинает принимать соединения.
4. Клиент отправляет `GET /health`.
5. FastAPI вызывает обработчик и возвращает его результат через Uvicorn.

Если модуль или объект не удалось импортировать, сервер не дойдёт до шага приёма запросов.

## 06. Ошибки запуска и HTTP-ответы означают разное

При диагностике сначала спросите себя: клиент получил HTTP-статус от сервера?

| Наблюдение | Что произошло |
| --- | --- |
| Ошибка импорта при запуске | Uvicorn не нашёл модуль или объект приложения. HTTP-запрос ещё не обрабатывался. |
| `Connection refused` | По указанному адресу и порту никто не принимает соединение. Возможно, сервер остановлен. |
| `404 Not Found` | Сервер ответил, но такого path в приложении нет. |
| `405 Method Not Allowed` | Path существует, но для него не зарегистрирован отправленный метод. |
| `200 OK` | Маршрут обработал запрос. Body всё ещё нужно сверить с ожиданием. |

Когда зарегистрирован только `GET /health`, адрес `GET /unknown` может вернуть 404, а `POST /health` вернёт 405. Это не поломка Uvicorn. Для каждого маршрута должны совпасть метод и path.

**Отладка:** команда `python -m uvicorn app.api:app --reload` запущена из папки `app`, и Python сообщает, что не находит пакет `app`. Сначала проверьте текущую директорию. Обычно эту команду нужно запускать из корня проекта. Пока сервер не загрузился, искать причину в JSON body рано.

## 07. OpenAPI описывает маршруты, Swagger UI их показывает

FastAPI собирает сведения о зарегистрированных операциях в описание OpenAPI. В нём указаны маршруты и методы, которые реально известны приложению. Планируемый в будущем `GET /tasks` там не появится, пока мы его не добавили.

FastAPI предоставляет три локальных адреса:

```text
http://127.0.0.1:8000/health      ответ приложения
http://127.0.0.1:8000/docs        интерактивный Swagger UI
http://127.0.0.1:8000/openapi.json описание OpenAPI в JSON
```

В Swagger UI кнопка **Try it out** подготавливает запрос, а **Execute** отправляет его. Это ещё один клиент. Маршрут всё равно живёт в Python-коде, а OpenAPI описывает то, что FastAPI зарегистрировал. `/docs` помогает исследовать API, но не проверяет бизнес-правила и не заменяет автоматические тесты.

**Выберите верное утверждение:** кто создаёт маршрут `GET /health`?

- FastAPI регистрирует его по декоратору в Python-коде.
- Uvicorn создаёт все маршруты при старте.
- Swagger UI добавляет маршрут после нажатия Execute.

**Ответ:** первый вариант. Uvicorn запускает приложение, а Swagger UI показывает и вызывает зарегистрированные операции.

## 08. Что мы будем делать в практике

Мы продолжим существующий Planner. В его окружение добавим FastAPI и Uvicorn, запишем их в `requirements.txt` в корне проекта и при необходимости создадим этот файл. В `app/api.py` опишем объект приложения и один `GET /health`. CLI в `app/main.py`, сервис, модель, хранилище и данные останутся нетронутыми.

Затем запустим Uvicorn из корня проекта и проверим один ответ в браузере, Swagger UI и Postman. В Postman создадим отдельное окружение `Local` с адресом `http://127.0.0.1:8000`. Echo-запросы `/get` и `/post` останутся в своём окружении: смена host сама по себе не превратит их в запросы Planner.

В конце проверим `404` для неизвестного path, `405` для неподдерживаемого метода и прежнюю команду CLI. Список задач, подключение PlannerService и работу с JSON API начнёт в следующем занятии.

**Практика достигла цели**, когда существующий CLI по-прежнему работает, а новый API отдельно отвечает на `GET /health` со статусом `200` и ожидаемым JSON. В Swagger UI виден только фактически зарегистрированный маршрут, а ошибки запуска не путаются с HTTP-ответами.
