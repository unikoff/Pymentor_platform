## 00. От ответа о запуске к данным Planner

В прошлом занятии мы создали HTTP-точку входа в существующий Persistent Planner и проверили GET /health. Этот запрос подтвердил, что приложение отвечает. Он пока ничего не сказал о задачах: health-маршрут не читает JSON и не проверяет работу PlannerService.

Теперь подключим к HTTP-интерфейсу уже знакомые данные. CLI умеет работать с задачами через PlannerService, а JsonStorage сохраняет их в файл. API станет ещё одним способом прочитать этот результат.

~~~text
CLI → PlannerService → JsonStorage → data/tasks.json
HTTP → FastAPI → app.state.planner → JsonStorage → тот же файл
~~~

Слово «тот же» относится к проекту и настроенному пути к данным, а не к одному Python-объекту. CLI и Uvicorn обычно работают в разных процессах. У каждого своя память и свой экземпляр сервиса. Оба используют прежние правила Planner и обращаются к одному файлу.

**Сначала предскажите:** если добавить задачу только в переменную Python внутри процесса CLI, сможет ли процесс Uvicorn увидеть эту переменную напрямую? Что должно связать эти два интерфейса?

## 01. Один файл переживает два процесса

Оперативная память принадлежит конкретному процессу. Когда CLI завершился, его переменные исчезли. При следующем запуске команда создаёт новый процесс. Uvicorn запускает свой процесс отдельно, поэтому список, созданный в CLI, не появляется в памяти API автоматически.

Файл на диске решает именно эту задачу. JsonStorage читает сохранённые данные и записывает изменения. Новый процесс может снова открыть этот файл. В нашем проекте готовая фабрика build_service выбирает настроенное хранилище и путь. Поэтому мы продолжаем пользоваться ею, а не вычисляем расположение JSON от текущей папки.

| Где находятся данные | После остановки процесса | Видит ли другой процесс напрямую |
| --- | --- | --- |
| список Python в RAM | исчезает | нет |
| задачи в data/tasks.json | остаются на диске | да, через настроенный JsonStorage |

Операции CLI идут через существующий сервис:

~~~text
команда CLI
  → PlannerService применяет правило
  → JsonStorage сохраняет изменение
  → data/tasks.json
~~~

Например, после add задача должна попасть в рабочее хранилище. После перезапуска CLI операция list должна прочитать её снова. Это не специальное поведение FastAPI, а свойство постоянного хранения.

Не создавайте учебный seed-файл рядом с рабочими данными и не редактируйте JSON руками. Добавьте задачи обычными командами CLI. Тогда id и исходная статистика будут настоящими, а не подогнанными под пример.

## 02. Приложение хранит сервис, а не копию задач

FastAPI вызывает обработчик, когда получает подходящие метод и путь. Обработчику нужен доступ к уже созданному PlannerService. У экземпляра приложения есть state, где можно хранить связанные с этим приложением объекты. Здесь это готовый сервис:

~~~python
app.state.planner = build_service()
~~~

app.state не является хранилищем на диске. Если остановить Uvicorn, сам объект приложения и его state исчезнут вместе с процессом. Новый запуск снова создаст сервис. Данные не пропадут, потому что сервис использует прежний JsonStorage.

Представьте полку инструментов приложения. На ней лежит сервис, который знает, как обратиться к данным. Сами задачи не нужно перекладывать на эту полку и поддерживать в отдельном глобальном списке.

Такой код читает задачи слишком рано:

~~~python
tasks = app.state.planner.list_tasks()

@app.get("/tasks")
def read_tasks():
    return tasks
~~~

Первая строка выполняется при создании приложения, а не при каждом запросе. Если CLI позже изменит JSON, переменная tasks останется старым снимком в памяти Uvicorn. Вызывайте list_tasks() внутри обработчика, чтобы операция сервиса прочитала актуальное состояние.

У каждого приложения достаточно одного выбранного app.state.planner. Обработчики получают сервис оттуда, а не строят отдельное хранилище или собственную копию бизнес-логики.

## 03. GET /tasks возвращает публичную проекцию

PlannerService.list_tasks() возвращает доменные объекты Task. Клиенту API не обязательно видеть все внутренние атрибуты модели. В этом контракте каждый элемент ответа содержит четыре поля:

- id отличает одну задачу от другой;
- title содержит её название;
- priority показывает приоритет;
- is_done показывает, завершена ли задача.

У Task также есть tags. Они продолжают жить в модели и JSON-файле, но не входят в текущую публичную форму. Выбор нужных полей называется проекцией. Это не отдельная модель хранения и не новая копия задач. Это представление для клиента.

Например, внутри проекта может быть такая задача:

~~~text
Task(id=12, title="Повторить HTTP", priority=3,
     is_done=False, tags=["учёба"])
~~~

Публичный JSON-элемент выглядит так:

~~~json
{
  "id": 12,
  "title": "Повторить HTTP",
  "priority": 3,
  "is_done": false
}
~~~

Форма ответа списка остаётся одной и той же. Одна задача, десять задач или ни одной всё равно образуют JSON-массив:

~~~json
[]
~~~

FastAPI умеет преобразовывать Python-списки и словари в JSON-ответы. Поэтому обработчик возвращает структурированные Python-значения, а не строку, заранее собранную через str(...) или json.dumps(...). В ответе пустой список не превращается в текст "[]".

## 04. GET /stats использует готовую статистику

В PlannerService уже есть get_statistics(). Он считает состояние проекта и возвращает значения all, open и done. Для HTTP-контракта общее число называется total. Маршрут меняет имя ключа all на total, а значения open и done берёт из готового результата.

Для примера, если в файле четыре задачи, три открыты, а одна завершена, преобразование выглядит так:

~~~text
результат сервиса:  all=4, open=3, done=1
ответ GET /stats:   total=4, open=3, done=1
~~~

Это пример формы, а не фиксированный результат практики. Счётчики ученика зависят от его файла. Если HTTP-обработчик начнёт отдельно обходить задачи и повторять подсчёт, появятся два алгоритма. Их можно случайно рассинхронизировать. Правила остаются в PlannerService, а HTTP-слой подстраивает название поля под контракт.

Полезная проверка для двоичного состояния: total должен равняться сумме open и done. Каждая задача относится ровно к одной группе.

**Проверьте понимание:** если в ответе сервиса all равно 7, какое число должно попасть в total? Меняет ли переименование ключа само число?

## 05. GET читает и не переписывает состояние

Повторный GET /tasks должен показать то же сохранённое состояние, если никто его не менял. GET /stats вычисляет представление того же состояния. Оба запроса только читают: они не добавляют задачу и не записывают её обратно в файл.

Пустой список тоже является корректным состоянием:

~~~text
GET /tasks → HTTP 200 и []
GET /stats → HTTP 200 и {"total": 0, "open": 0, "done": 0}
~~~

Пустое хранилище нельзя путать с повреждённым JSON. Если файл не удаётся прочитать, это ошибка хранилища, а не доказательство, что задач нет. Нельзя молча подменить такую ошибку пустым списком и сохранить его поверх исходных данных. В этой работе не добавляется новый обработчик ошибок: сохраняется поведение существующего storage.

Проверку удобно вести по отдельным наблюдениям:

1. HTTP-статус показывает результат обработки запроса.
2. Content-Type сообщает формат ответа.
3. JSON-тело показывает данные.
4. CLI даёт независимое подтверждение содержимого того же файла.
5. Сравнение файла до и после GET показывает, что чтение не записывало данные.

Swagger UI из прошлого занятия позволяет быстро выполнить запрос. В Postman сохраните отдельные запросы к Planner. Запросы Echo /get и /post не меняйте: у них другой host, путь и ожидаемый ответ.

## 07. Что мы будем делать в практике

Сначала через готовый CLI добавим несколько задач в рабочий JSON. Завершим часть задач, затем посмотрим реальные id, список и статистику. Перезапуск CLI подтвердит, что данные переживают завершение процесса. Существующие записи не удаляем и файл руками не редактируем.

Затем в app/api.py подключим готовый build_service через app.state.planner. GET /tasks будет читать свежие задачи и возвращать только четыре публичных поля. GET /stats вызовет готовый get_statistics() и представит all как total.

Результат проверим через Swagger UI или Postman, сверим с CLI, повторим чтение после последовательного изменения данных и после перезапуска API. Сами GET-запросы не должны изменять JSON. GET /health и CLI останутся рабочими. Новый storage, доменная модель, список tasks в модуле и отдельный подсчёт статистики не нужны.

~~~text
реальные данные CLI
  → тот же JsonStorage
  → GET /tasks и GET /stats
  → сверка HTTP-ответов с CLI
~~~
