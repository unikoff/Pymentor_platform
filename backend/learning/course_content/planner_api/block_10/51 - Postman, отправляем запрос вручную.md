## 00. От контракта к настоящему запросу

В прошлом блоке мы описали договор Planner API. Мы выбрали методы, адреса, данные запроса и ожидаемые ответы. Но пока это была карта, а не сетевой обмен.

Теперь соберём настоящее HTTP-сообщение в Postman, отправим его серверу и прочитаем ответ. Собственного сервера у Planner пока нет, поэтому сначала воспользуемся Postman Echo. Он показывает сведения о полученном запросе, но не выполняет правила Planner и не хранит задачи.

В практике будут два запроса:

1. GET передаст параметры в адресе, то есть в query.
2. POST отправит JSON с полями в body.

Затем мы сохраним оба сценария и положим экспорт Postman в папку `postman/` уже существующего проекта Planner. Новый проект или копия Planner не нужны.

После занятия вы сможете объяснить, где собирается request, что показывает response и почему успешный ответ Echo ещё не подтверждает работу Planner.

## 01. Postman отправляет, Echo отвечает

**Postman** это HTTP-клиент. Он помогает вручную сформировать request и отправить его серверу. **Echo** в этой работе выступает сервером: принимает сообщение и возвращает сведения о нём.

Путь обмена простой:

```text
Postman собирает request
→ Echo получает request
→ Echo возвращает response
→ Postman показывает результат
```

Представьте почтовое отделение и адресата. Postman заполняет и отправляет письмо. Сервер его получает и отвечает. Клиент не выполняет работу за сервер.

Разработчики используют API-клиент, чтобы проверить отдельный запрос независимо от кнопок сайта. Если запрос уже не работает из Postman, искать проблему в интерфейсе сайта рано. Позже таким же способом можно будет отдельно проверить собственный Planner API.

Здесь важно точно называть наблюдение. Успешный ответ Echo доказывает, что Echo получил сообщение и ответил. Он не доказывает, что Planner создал задачу: Planner этот request не получал.

## 02. Соберите сообщение до отправки

В окне Postman части HTTP-сообщения находятся в отдельных полях. Точные вкладки могут немного меняться между версиями приложения, но их назначение остаётся тем же.

| Поле | Что задаёт |
| --- | --- |
| `Method` | Действие, например GET или POST. |
| `URL` | Адрес сервера и путь к endpoint. |
| `Params` | Query-пары, которые дополняют URL. |
| `Headers` | Служебные сведения о сообщении, например его формат. |
| `Body` | Данные, которые клиент отправляет серверу. |
| `Send` | Отправляет собранный request. |
| `Response` | Показывает ответ: status, headers и body. |

До нажатия `Send` вы меняете черновик запроса. Сервер ещё ничего не получил.

```text
REQUEST
method + URL + query + headers + body
                  ↓ Send
                 сервер
                  ↓
RESPONSE
status + headers + body
```

Вкладка `Body` относится к исходящему запросу. Поле body в `Response` содержит данные, которые вернул сервер. Это две стороны обмена.

## 03. Первый обмен: GET к Echo

Начнём с запроса без параметров:

```http
GET https://postman-echo.com/get
```

В адресе:

- `https` задаёт схему соединения;
- `postman-echo.com` это `host`, имя сервера;
- `/get` это `path`, путь внутри сервера.

Метод GET вместе с path задаёт конкретный `endpoint`, то есть операцию API. Здесь мы обращаемся к учебному endpoint Echo, а не к списку задач Planner.

После `Send` Postman показывает `response`. Успешный запрос обычно возвращает status `200` и JSON в body. JSON это текстовый формат, в котором значения записаны рядом с именами полей. Пока query нет, поле `args` пустое:

```json
{
  "args": {},
  "url": "https://postman-echo.com/get"
}
```

Status, headers и body отвечают на разные вопросы:

- **Status** показывает итог HTTP-обмена.
- **Headers** описывают ответ, например сообщают формат body.
- **Body** содержит данные, которые вернул сервер.

Если в URL опечатка в имени host, Postman может не получить HTTP-ответ. Это не то же самое, что status `404`. При `404` сервер ответил сообщением, а при ошибке соединения response может отсутствовать.

**Найдите причину.** Что ожидать от `https://postman-echo.invalid/get`: status от Echo или сообщение о том, что ответ не получен? Подумайте, дошёл ли запрос до нужного сервера.

## 04. Query передаёт настройки, а не выполняет фильтрацию

Query добавляет к адресу пары «имя и значение». В Postman их можно ввести во вкладке `Params`, не собирая URL вручную.

```http
GET https://postman-echo.com/get?is_done=false&limit=2
```

Знак `?` отделяет query от path. Символ `&` разделяет пары. В `Params` добавьте:

| Key | Value |
| --- | --- |
| `is_done` | `false` |
| `limit` | `2` |

Echo отразит полученные значения в `args`:

```json
{
  "args": {
    "is_done": "false",
    "limit": "2"
  }
}
```

Обратите внимание на кавычки: URL передал значения как текст. Echo не знает, что `false` должен означать булево значение, а `2` может означать целый лимит. Он только показывает, что получил.

Когда запрос будет принимать Planner API, сервер сможет преобразовать и проверить значения по своему контракту. Но Echo не располагает задачами Planner, поэтому `is_done=false` не запускает фильтрацию, а `limit=2` не ограничивает список.

**Проверьте себя.** Если `limit=2` добавлен через `Params`, где он окажется: в query URL, в исходящем JSON body или в response body?

## 05. POST передаёт JSON в body

GET подходит для чтения и его настроек. Для передачи полей новой задачи договор Planner использует POST с JSON body. На Echo мы проверим только форму сообщения.

```http
POST https://postman-echo.com/post
Content-Type: application/json

{
  "title": "Изучить HTTP",
  "priority": 4
}
```

В Postman выберите `POST`, откройте `Body`, выберите `raw` и формат `JSON`. `Raw` означает, что body вводится как текст. `Content-Type` это заголовок, который сообщает серверу формат отправленных данных. Для JSON Postman выставляет `application/json`; не добавляйте второй такой же заголовок вручную.

В JSON имена полей и текстовые значения записываются в двойных кавычках. Число пишется без кавычек. Поэтому `"priority": 4` содержит число, а `"priority": "4"` содержит строку. Echo может отразить оба варианта, но только будущий Planner API будет проверять свой контракт.

В ответе Echo отправленный объект находится внутри `json`:

```json
{
  "json": {
    "title": "Изучить HTTP",
    "priority": 4
  }
}
```

Это response Echo со status `200`. Он не означает, что создана Task или изменён файл Planner. Echo только вернул полученные значения.

**Найдите отличие.** В примере ниже priority стал строкой из-за кавычек. Почему зелёный status не покажет эту смысловую ошибку сам по себе?

```json
{
  "title": "Изучить HTTP",
  "priority": "4"
}
```

## 06. Читайте status, headers и body вместе

Status `200` сообщает, что Echo успешно обработал HTTP-запрос. Но одного status недостаточно, чтобы подтвердить, что сервер получил нужные значения.

Проверяйте ответ по частям:

1. Прочитайте status.
2. Посмотрите headers и определите формат ответа.
3. Найдите нужные поля в body.
4. Сравните фактические значения с теми, которые отправили.

Например, GET может получить status `200`, но не показать ожидаемый `limit` в `args`. Значит, обмен состоялся, но query нужно проверить отдельно. После POST сравните содержимое `response.json` с исходным JSON body.

В Postman можно писать `post-response scripts`, то есть короткие проверки после ответа. В этой работе писать JavaScript не требуется: достаточно вручную сравнить status и поля response с ожиданием. Автоматические проверки полезны, когда нужно много раз повторять один и тот же сценарий. Для нашей первой практики они добавили бы отдельный язык и не нужны для понимания HTTP.

Если сервер вернул `404`, вы получили HTTP response и можете изучить его status и body. Если Postman сообщил, что не смог подключиться или разрешить host, response может не быть вовсе. Ошибку связи с Echo не следует называть ошибкой Planner.

## 07. Collection и environment сохраняют разные вещи

Открытая вкладка годится для разового опыта. Чтобы отправить тот же запрос позже, сохраните его в **collection**, набор запросов. В collection остаются method, URL, Params, headers и body.

**Environment**, окружение, хранит значения, которые меняются вместе с целью запроса. Здесь мы используем переменную `base_url`:

```text
Environment Echo
base_url = https://postman-echo.com

GET {{base_url}}/get
```

После выбора environment `Echo` Postman подставит значение переменной, и URL станет `https://postman-echo.com/get`. Так host хранится в одном месте.

Но `base_url` меняет только начало URL. Путь `/get` или `/post`, метод, body и ожидания остаются прежними. Поэтому одного изменения адреса недостаточно, чтобы Echo-запрос стал проверкой Planner. Перед таким переходом нужно согласовать с договором Planner маршруты и ожидаемые ответы.

Чтобы создать collection, войдите в Postman. Самому Echo логин или токен не нужен. После сохранения экспортируйте collection и environment отдельно как JSON:

1. В списке `Collections` откройте меню рядом с нужной collection, выберите экспорт и сохраните JSON.
2. В списке `Environments` откройте меню рядом с `Echo` и выберите `Export`.

Названия пунктов могут немного отличаться в разных версиях Postman. Важно получить два отдельных файла: один с запросами, другой с `base_url`. Не помещайте туда пароли, приватные токены или реальные персональные данные.

## 08. Что мы будем делать в практике

Мы продолжаем существующий проект Planner. В его корне добавим только папку `postman/`. Исходники, CLI, данные и ранее подготовленные документы не копируем и не перезаписываем. FastAPI-сервер в этой практике ещё не создаём.

Путь практики:

1. Подготовить `postman/` в существующем Planner.
2. Создать collection `Planner HTTP Lab` и environment `Echo` с `base_url=https://postman-echo.com`.
3. Отправить GET `/get` с query `is_done=false` и `limit=2`. Найти в `args` обе строки.
4. Отправить POST `/post` с JSON body, содержащим `title` и `priority`. Проверить status и отражённые поля в `json`.
5. Сохранить оба request, отправить их повторно и экспортировать collection и environment в `postman/`.

Итоговые файлы будут лежать рядом с прежним проектом:

```text
Planner/
├── прежние файлы проекта
└── postman/
    ├── planner-http-lab.postman_collection.json
    └── echo.postman_environment.json
```

После повторной отправки запросов должно быть понятно, какие именно значения Echo получил. Сохранённые JSON-файлы должны позволять открыть и восстановить сценарии. Если Echo недоступен, различайте сетевую ошибку и HTTP-ответ; это не доказывает неисправность Planner.

В следующем занятии мы добавим FastAPI к тому же проекту. Коллекция Echo останется отдельной учебной проверкой. Для Planner появятся собственные маршруты и отдельные ожидания.
