# 54. Path-параметры и чтение одной задачи

## 00. Из списка открываем нужную задачу

В прошлом занятии Planner API научился показывать реальные данные проекта через <code>GET /tasks</code>. Представьте экран планировщика: человек видит список и выбирает одну строку. Ему не нужен весь список ещё раз. Нужна именно выбранная задача.

У каждой записи есть устойчивый <code>id</code>. Поэтому клиент может попросить конкретную задачу по адресу, например <code>GET /tasks/17</code>. Число здесь только пример. В проекте мы будем брать id из реального ответа Planner.

Сегодня проследим полный путь такого запроса: URL, проверка входного значения, вызов готового сервиса и ответ клиенту. По дороге разберём два разных отказа. В одном случае id вообще нельзя разобрать как число. В другом число верное, но задачи с ним нет.

### Сначала подумайте

В ответе <code>GET /tasks</code> есть задача с id 17. Что должен вернуть <code>GET /tasks/17</code>? А можно ли считать id равным номеру строки в текущем списке?

## 01. Адрес коллекции и адрес одного ресурса

Маршрут <code>GET /tasks</code> обозначает коллекцию задач. Он отвечает на вопрос «какие задачи есть?». Адрес <code>GET /tasks/17</code> обозначает одну задачу. Такое отдельное представление называют item, то есть элементом коллекции.

Тот же приём работает в каталоге книг:

~~~text
GET /books       → коллекция книг
GET /books/17    → одна книга с id 17
~~~

Вторая форма не заставляет клиента скачать весь каталог и искать запись у себя. Сервер получает точный запрос и сам обращается к своим данным.

Collection, или коллекция, это набор задач. Item это один элемент набора. Ресурс API может обозначать и коллекцию, и отдельную Task.

Не путайте path с query. Path находится в маршруте и указывает, какой ресурс нужен. Query обычно настраивает чтение коллекции.

~~~text
/tasks/17                 одна конкретная задача
/tasks?is_done=false      коллекция с условием выборки
~~~

Идентификатор не является позицией. Если задача с id 17 сейчас третья в списке, после сортировки она может стать первой. Сам id при этом не изменится. Для маршрута нужна идентичность записи, а не её место на экране.

**Проверьте себя.** Какой адрес остаётся запросом коллекции: <code>/tasks/17</code> или <code>/tasks?is_done=false</code>? Во втором случае меняется выборка, но клиент всё ещё просит набор задач.

## 02. Path-параметр связывает адрес с аргументом

Часть маршрута, которая меняется от запроса к запросу, называется path-параметром. В шаблоне маршрута FastAPI её записывают в фигурных скобках:

~~~python
@app.get("/books/{book_id}")
def read_book(book_id: int):
    return {"requested_id": book_id}
~~~

Шаблон <code>/books/{book_id}</code> и аргумент <code>book_id</code> связаны по имени. Для запроса <code>GET /books/17</code> FastAPI передаст в функцию целое число 17. Фигурные скобки в реальный адрес не отправляются.

Аннотация <code>int</code> нужна не только редактору. FastAPI получает значение из URL как текст, сверяет его с ожидаемым типом и вызывает функцию только после успешного разбора. Валидация до обработчика защищает код от значений неожиданной формы.

Путь запроса выглядит так:

~~~text
URL: /books/17
  ↓
FastAPI находит значение в {book_id}
  ↓
проверяет и преобразует его в int
  ↓
вызывает read_book(book_id=17)
~~~

Если вместо числа пришло <code>abc</code>, обработчик не получает строку и не начинает поиск. FastAPI сам возвращает <code>422 Unprocessable Entity</code>: запрос не подходит объявленному типу параметра. Это отказ на границе HTTP, а не сообщение о том, что задачи нет.

### Поставьте события по порядку

Для <code>GET /books/17</code> расположите в голове три шага: функция получает число, значение извлекается из URL, значение проверяется как <code>int</code>. Какой шаг должен завершиться первым?

**Ответ.** Сначала FastAPI извлекает часть URL, затем проверяет тип, и лишь после этого вызывает функцию.

## 03. Ищет готовый PlannerService

После проверки FastAPI передаёт целое число обработчику. Но маршрут не должен заново реализовывать поиск по файлу. В существующем Planner за поиск уже отвечает <code>PlannerService.get_task(task_id)</code>. Он получает актуальную задачу через настроенное хранилище.

Участники отвечают за разные части:

- FastAPI связывает URL и Python-аргумент.
- PlannerService находит доменную Task по id.
- Маршрут превращает результат операции в понятный HTTP-ответ.

Такое разделение похоже на ресепшен в мастерской. Сотрудник принимает номер заказа, передаёт запрос нужному специалисту и сообщает клиенту результат. Он не ремонтирует заказ сам и не заводит второй журнал учёта.

Маршрут связывает уже готовые части:

~~~python
@app.get("/tasks/{task_id}")
def read_task(task_id: int):
    task = app.state.planner.get_task(task_id)
    # Ниже маршрут подготовит публичный ответ.
~~~

Сервис хранится в <code>app.state.planner</code>, как и в прошлом занятии. Не создавайте новый список задач при импорте модуля. Не читайте JSON вручную. Иначе API начнёт использовать второй источник вместо проекта.

В рабочем коде метода и класса важен не только «счастливый путь». Нужно определить, как сервис сообщает об отсутствии задачи. По концепту Planner это исключение <code>TaskNotFoundError</code>. Оно означает конкретно ожидаемый случай: корректный id был передан, но записи с таким id нет.

## 04. Отсутствующая задача и неверный тип дают разные ответы

Сравним три адреса:

| Запрос | Что произошло | Результат |
| --- | --- | --- |
| <code>/tasks/17</code>, задача существует | Тип верный, сервис нашёл Task | <code>200 OK</code> |
| <code>/tasks/99999</code>, такого id нет | Тип верный, сервис сообщил TaskNotFoundError | <code>404 Not Found</code> |
| <code>/tasks/abc</code> | FastAPI не смог разобрать int до вызова маршрута | <code>422</code> |

Число 99999 здесь пример отсутствующего id. Перед проверкой в проекте убедитесь, что выбранный номер действительно не используется.

HTTP-ответ 404 создаёт маршрут через <code>HTTPException</code>. Это исключение FastAPI со статусом и описанием ошибки. Его поднимают через <code>raise</code>, после чего FastAPI формирует ответ и прекращает обычный путь обработчика. Сервис не обязан знать о HTTP. Он сообщает о доменном результате, а маршрут адаптирует его для клиента:

~~~python
try:
    task = app.state.planner.get_task(task_id)
except TaskNotFoundError as error:
    raise HTTPException(
        status_code=404,
        detail="Task not found",
    ) from error
~~~

<code>raise</code> прекращает обычный путь обработчика и передаёт FastAPI сведения для ответа. Клиент получает статус и поле <code>detail</code>. Здесь важно ловить именно <code>TaskNotFoundError</code>, а не все исключения подряд.

Почему не ловить <code>Exception</code>? Вызов может завершиться из-за повреждённого JSON, недоступного файла или ошибки в коде. Это не значит, что задачи просто нет. Если превратить любую проблему в 404, система скроет настоящую поломку и сообщит клиенту неверную причину.

**Разберите сценарии.** Почему <code>/tasks/abc</code> не превращается в 404? Почему <code>/tasks/99999</code> может дать 404, хотя число распознано верно?

## 05. HTTP-ответ не обязан раскрывать всю доменную модель

Сервис возвращает доменный объект Task. Это внутреннее представление Planner. Клиенту API нужна согласованная внешняя форма, а не все детали реализации хранилища.

В этом API публичная задача содержит четыре поля. Проекция это выбранное представление объекта для конкретного ответа. Маршрут собирает её явно:

~~~json
{
  "id": 17,
  "title": "Изучить path-параметры",
  "priority": 3,
  "is_done": false
}
~~~

Маршрут собирает проекцию из этих полей. Например, <code>tags</code> остаётся частью внутренней модели и файла, но не входит в этот публичный ответ. Явная проекция помогает менять внутреннюю реализацию, не меняя случайно договор с клиентом.

~~~python
return {
    "id": task.id,
    "title": task.title,
    "priority": task.priority,
    "is_done": task.is_done,
}
~~~

Это чтение. Оно не должно менять Task, вызывать операцию записи или сохранять JSON. Повторный запрос к существующему id возвращает тот же объект, если данные никто не изменял. По этой причине после проверки полезно сравнить list и файл до и после запроса.

Важное уточнение: здесь мы не добавляем новую модель ответа и не переписываем сервис. Мы используем уже существующие Task и PlannerService, а на HTTP-границе явно выбираем четыре поля.

### Выберите надёжную проекцию

Представьте, что завтра во внутреннюю Task добавят поле с настройками напоминаний. Должно ли оно автоматически появиться в API-ответе?

**Ответ.** Нет. Явная проекция сохраняет прежний публичный договор, пока команда отдельно не решит его изменить.

## 06. От URL до исхода и проверка границ

В обычном сценарии путь запроса разветвляется только после проверки типа:

~~~text
GET /tasks/17
  → FastAPI проверяет task_id: int
  → app.state.planner.get_task(17)
  → Task найдена
  → маршрут возвращает четыре поля, HTTP 200
~~~

Если значение не является числом, FastAPI возвращает 422 до вызова маршрута. Если число допустимо, но записи нет, сервис сообщает <code>TaskNotFoundError</code>, а обработчик переводит его в 404. Если во время чтения сломалось хранилище, это отдельная ошибка. Нельзя выдавать её за 404.

Частые ошибки возникают, если перепутать границы:

- Считать id индексом списка. Позиция может меняться, id должен указывать на ту же запись.
- Отправлять неизвестный числовой id со статусом 422. Значение уже прошло проверку типа, но ресурс отсутствует.
- Переводить <code>TaskNotFoundError</code> в 422. Для отсутствующей записи подходит 404.
- Ловить любое исключение как отсутствие задачи. Так ошибка хранилища становится незаметной.
- Возвращать все внутренние поля через <code>to_dict()</code>. Публичный ответ должен следовать оговорённой проекции.
- Загружать список при запуске сервера и искать в нём. Прошлый урок уже подключил сервис к рабочим данным.

### Найдите ошибку

В обработчике для неизвестного числового id программист ловит <code>TaskNotFoundError</code> и отправляет 422. Сбой находится в поиске или в выборе HTTP-статуса?

**Ответ.** Поиск сообщил верную причину. Ошибка в статусе: корректный по типу id отсутствует в данных, поэтому клиенту нужен 404.

### Проверка на данных проекта

Проверяйте не только удачный адрес. Три запроса проверяют три части пути:

1. Реальный существующий id. Обработчик получает Task и возвращает публичный JSON со статусом 200.
2. Корректное число, которого нет в списке. Сервис сообщает об отсутствии, обработчик возвращает 404.
3. Текст вместо числа. FastAPI возвращает 422 до вызова обработчика.

Для первого запроса берите id из текущего <code>GET /tasks</code>, а не из примера в учебнике. Это связывает маршрут с реальными данными проекта. Для второго выберите отсутствующее целое число. Третий можно проверить, указав в адресе <code>abc</code>.

Читайте статус и тело вместе. Для успешного чтения проверьте поля задачи. Для 404 проверьте <code>detail</code>. Для 422 выясните, что причиной стал тип path-параметра. После запросов повторно прочитайте список и убедитесь, что GET ничего не сохранил и не изменил.

## 07. Что мы будем делать в практике

Мы продолжим тот же Planner API, который уже читает коллекцию задач и статистику. В <code>app/api.py</code> появится маршрут <code>GET /tasks/{task_id}</code>. Он примет id из адреса, вызовет существующий <code>app.state.planner.get_task(task_id)</code> и вернёт четыре публичных поля Task.

Сначала проверим найденную задачу по id из реального списка. Затем разберём два разных отказа: отсутствующий числовой id даст 404, а текст вместо числа получит 422 до входа в функцию маршрута. Ожидаемое отсутствие будет обработано через <code>TaskNotFoundError</code>. Другие сбои не маскируются как 404.

В конце сравним ответы с существующим <code>GET /tasks</code>, проверим, что JSON и статистика не изменились, и сохраним запросы в прежней Planner collection. Новое хранилище, второй поиск, временный список и отдельная модель ответа не нужны.

~~~text
id из реального списка
  → path-параметр и проверка int
  → готовый PlannerService.get_task
  → публичная Task или точный HTTP-отказ
~~~
