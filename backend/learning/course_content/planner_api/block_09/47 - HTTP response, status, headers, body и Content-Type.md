## 00. Request отправлен. Что получает клиент?

В прошлом занятии мы собрали request: клиент сообщил серверу, чего хочет и какие данные передаёт. Теперь посмотрим на обратную сторону обмена. После обработки сервер возвращает response, то есть ответ с результатом.

Представьте заказ в кафе. Request похож на заказ, а response на то, что кафе сообщает после его обработки: блюдо готово, позиции нет или возникла проблема. Программа тоже не должна угадывать результат по случайной фразе. Для этого ответ разделён на несколько частей.

1. **Request:** клиент → сервер. Клиент сообщает о нужном действии.
2. **Обработка:** сервер проверяет запрос и применяет правила приложения.
3. **Response:** сервер → клиент. Сервер сообщает исход и, когда нужно, передаёт данные.

Например, клиент просит показать задачу с номером 8. Сервер может найти её и вернуть ответ с кодом **200** и данными задачи. Если такой задачи нет, он вернёт **404** и может добавить описание ошибки.

## 01. Ответ программы и HTTP response

Команда **print()** показывает текст человеку в терминале. Она не создаёт ответ для другого приложения. Обычный **return** передаёт значение вызывающему коду внутри процесса Python. Клиент и сервер могут работать в разных процессах, поэтому результат между ними передают в виде HTTP response.

У такого ответа есть три основные части:

- **status** сообщает исход обработки;
- **headers** содержат служебные сведения об ответе;
- **body** содержит данные результата или описание ошибки, если они нужны.

Условный HTTP response может выглядеть так:

~~~http
HTTP/1.1 201 Created
Content-Type: application/json
X-Request-ID: req-a91

{"id": 7, "title": "Изучить HTTP", "priority": 4, "is_done": false}
~~~

Строка **201 Created** сообщает, что ресурс создан. Заголовок **Content-Type** указывает формат тела, а **X-Request-ID** помогает связать обращение с его записью в журналах. После пустой строки идёт body с данными созданной задачи. Здесь **id: 7** относится к задаче, а **req-a91** к одному HTTP-обращению.

Это представление показывает смысл сообщения. Настоящий HTTP-клиент получает сетевые данные и декодирует их, а не общается с сервером через общий словарь Python.

**Интерактив. Соедините часть ответа с её ролью.**

- **status** → исход обработки;
- **headers** → служебные сведения;
- **body** → данные результата или ошибка.

Status и body отвечают на разные вопросы. Код **404** сообщает, что ресурс не найден. Body может уточнить, какой именно ресурс искали. Клиент не должен определять исход, разыскивая слова вроде **not found** в тексте.

## 02. Status задаёт ветку результата

Status code, или код состояния, это число, которое сервер включает в ответ. Первая цифра помогает быстро сориентироваться, а полный код уточняет конкретный исход.

- **1xx**: информационный ответ о ходе обмена.
- **2xx**: запрос обработан успешно.
- **3xx**: клиенту может понадобиться дополнительное действие, например переход по другому адресу.
- **4xx**: запрос не удалось выполнить в текущем виде или ресурс недоступен.
- **5xx**: сервер не смог выполнить запрос из-за внутренней проблемы.

Класс даёт общий ориентир, но не заменяет точный код. В этом блоке важны следующие варианты:

- **200 OK**: запрос выполнен. Например, сервер вернул запрошенный список или задачу.
- **201 Created**: ресурс создан. Ответ может содержать его данные.
- **204 No Content**: действие успешно, но содержимого в ответе нет.
- **400 Bad Request**: сервер не смог обработать запрос в текущем виде. Это общий код для такой ситуации, а не название любой ошибки поля.
- **404 Not Found**: запрошенный ресурс не найден.
- **500 Internal Server Error**: сервер столкнулся с неожиданной внутренней проблемой.

Код **400** не следует автоматически ставить на любое некорректное значение. Для ошибок проверки конкретных полей в нашем маршруте будет отдельное занятие. Сейчас достаточно понимать: status сообщает общую ветку результата, а конкретные данные об ошибке могут находиться в body.

**Интерактив. Что напечатает код?**

~~~python
status = 201

if 200 <= status < 300:
    print("операция выполнена успешно")
else:
    print("нужна другая обработка")
~~~

Функция увидит, что **201** входит в диапазон **200–299**, и напечатает **операция выполнена успешно**. Но одного класса недостаточно для всех решений: клиенту может быть важно различить обычное чтение **200**, создание ресурса **201** и отсутствие содержимого при **204**.

## 03. Body содержит данные, а не сам исход

Body, или тело ответа, может содержать найденную задачу, список задач или описание ожидаемой ошибки. Сервер выбирает форму данных по договору API. Например, у объекта задачи есть поля, а список содержит несколько таких объектов.

~~~json
{
  "id": 8,
  "title": "Изучить HTTP",
  "priority": 4,
  "is_done": false
}
~~~

JSON похож на запись словаря, но это формат передачи данных, а не объект Python. В Python логическое значение записывается как **True**, а в JSON как **true**. При сериализации программа преобразует значение Python в текст допустимого формата.

~~~python
import json

payload = {"available": True}
body_text = json.dumps(payload, ensure_ascii=False)
print(body_text)
~~~

Результат:

~~~json
{"available": true}
~~~

Само преобразование не происходит от одного заголовка. **Content-Type: application/json** сообщает получателю, что body представлен в формате JSON. Заголовок описывает уже существующее содержимое, но не создаёт и не сериализует его.

Здесь есть важное различие между отсутствующим телом и пустым JSON-объектом:

- **None** в Python может означать, что body отсутствует;
- **{}** означает, что body есть и содержит пустой JSON-объект.

При сериализации Python-значение **None** обычно превращается в JSON **null**. Но в практике этого занятия мы заранее договоримся использовать **None** как специальную отметку «body отсутствует». Функция не сериализует значение и не отправляет его по сети. В настоящем HTTP body со значением **null** и полностью отсутствующее body являются разными вариантами.

**Отладка. Найдите противоречие.**

~~~python
status = 204
body = {}
~~~

Код **204 No Content** означает успешный ответ без содержимого. Но **{}** это присутствующий пустой JSON-объект, а не отсутствие тела. Если сервер возвращает **204**, в этой модели body должен отсутствовать. Если нужно передать **{}**, выбирают ответ с телом, например подходящий **200**.

## 04. Headers описывают сообщение

Заголовки не заменяют status и не содержат сами данные body. Они помогают участникам обмена одинаково прочитать сообщение.

Клиент может заранее сообщить, какой формат ему подходит:

~~~http
Accept: application/json
~~~

Сервер указывает формат, который действительно использовал в ответе:

~~~http
Content-Type: application/json
~~~

В ответе **Content-Type** нужен, когда сервер передаёт содержимое соответствующего формата. Если body отсутствует, разбирать формат нечего. Поэтому при **204** клиент не запускает JSON-разбор.

Текст, похожий на JSON, не запрещено передавать как **text/plain**. Несоответствие возникает только тогда, когда договор API обещает клиенту JSON, а сервер объявляет содержимое как **text/plain**. Заголовок сообщает получателю заявленный формат и способ обработки содержимого.

Некоторые приложения также передают идентификатор обращения:

~~~http
X-Request-ID: req-81
~~~

Он помогает связать клиентское обращение с записями разных частей сервиса и быстрее найти его при разборе проблемы. Это не идентификатор задачи: номер задачи может быть в URL или body, а request ID относится к конкретному обмену. В практике значение request ID уже передаётся функции. Создавать его и настраивать журналы не нужно.

## 05. Клиент читает ответ по порядку

Удобно разбирать response в три шага:

1. Прочитать status и выбрать ветку результата.
2. Проверить, есть ли body.
3. Если тело есть, посмотреть на **Content-Type** и разобрать данные в нужном формате.

Порядок важен. При **204** клиент завершает обработку по status и не пытается читать JSON, которого нет. При **404** клиент понимает, что запрошенный ресурс не найден, а JSON body может дать детали для сообщения пользователю. При **201** клиент может прочитать данные созданной задачи и показать её номер.

~~~python
if status == 204:
    result = "успех без содержимого"
elif 200 <= status < 300:
    result = "успешная операция"
elif 300 <= status < 400:
    result = "выполнить дополнительное действие"
elif 400 <= status < 500:
    result = "обработать проблему запроса"
elif 500 <= status < 600:
    result = "обработать проблему сервера"
else:
    result = "свериться с договором API"

if body is None:
    details = "body отсутствует"
elif content_type == "application/json":
    details = "разобрать JSON"
else:
    details = "проверить другой формат"
~~~

Это упрощённая схема, а не готовый универсальный HTTP-клиент. В реальном API клиент учитывает договор конкретного маршрута, а библиотека может сама читать заголовки и разбирать JSON.

**Три сценария для проверки порядка обработки.**

- **404** и JSON с описанием ошибки: клиент идёт в ветку отказа, а затем может разобрать body и показать детали.
- **204** и отсутствующий body: клиент завершает операцию без разбора данных.
- **200**, body равен **{}**, **Content-Type** равен **application/json**: тело существует, его можно разобрать как пустой объект.

Клиент не должен угадывать статус по словам в body. Сначала он определяет исход, затем решает, ожидается ли содержимое, и только после этого выбирает формат разбора.

## 06. Request и response образуют пару

Ответ относится к конкретному запросу. Посмотрим на три сценария Planner:

~~~text
GET /tasks/8
→ 200 OK
→ {"id": 8, "title": "Изучить HTTP", "priority": 4, "is_done": false}
~~~

Существующая задача найдена. Код сообщает об успешном чтении, body передаёт данные задачи.

~~~text
POST /tasks
body: {"title": "Проверить ответ", "priority": 4}
→ 201 Created
→ {"id": 9, "title": "Проверить ответ", "priority": 4, "is_done": false}
~~~

Новая задача создана. Клиенту возвращаются данные результата, включая назначенный сервером номер.

~~~text
GET /tasks/999
→ 404 Not Found
→ {"detail": "Task not found"}
~~~

Запрос обработан, но такого ресурса нет. Body может объяснить причину. Это ожидаемый результат работы API, а не обязательно сбой сервера.

Для успешного удаления договор API может предусматривать **204** без body. Клиент понимает, что действие завершено, и обновляет экран, не ожидая JSON. В следующем занятии мы разберём HTTP-методы, чтобы связать намерение клиента с видом request.

## 07. Что мы будем делать в практике

Практическая функция получает несколько уже подготовленных ответов и возвращает их в одной учебной модели. Так видны отдельные части response: исход операции, служебные сведения и содержимое. Входные status и body остаются без изменений.

Задание не отправляет настоящий HTTP-запрос и не реализует сервер Planner. Оно проверяет только модель ответа. Отдельный случай с пустым объектом поможет не спутать его с отсутствующим body. В этой задаче отсутствие обозначается значением **None**; это договор упражнения, а не JSON-значение **null**.
