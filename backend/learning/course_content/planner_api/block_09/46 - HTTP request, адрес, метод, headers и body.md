## 00. От разговора клиента с сервером к самому сообщению

В прошлом занятии мы разделили роли клиента и сервера. Клиент начинает обращение, сервер принимает решение и возвращает результат. Но что именно клиент передаёт серверу? Одного намерения «покажи задачи» недостаточно: приложению нужен понятный формат сообщения.

HTTP расшифровывается как Hypertext Transfer Protocol, протокол передачи гипертекста. Он задаёт правила обмена сообщениями между клиентом и сервером. **Request** означает запрос клиента. **Response** означает ответ сервера.

Удобная аналогия — бланк заказа. В нём есть адрес отдела, просьба, служебные отметки и сам заказ. Сервер читает сообщение и уже внутри запускает нужную работу.

~~~text
клиент → request → сервер → внутренняя логика
клиент ← response ← сервер
~~~

В этом занятии разберём четыре части учебной модели: адрес, **method**, **headers** и необязательный **body**. Это поможет читать запрос и собирать его представление в Python. Мы пока не запускаем API и не отправляем данные по сети.

**Вопрос на понимание.** Если клиент написал «создай задачу», получил ли сервер уже полноценный HTTP request?

Нет. Это только человеческое намерение. Чтобы обратиться к приложению, клиенту нужны данные по установленному договору.

## 01. Сообщение не вызывает Python-функцию напрямую

В знакомой локальной программе одна функция может вызвать другую:

Сокращённый фрагмент локального вызова, не самостоятельная программа:

~~~python
service.add_task("Изучить HTTP")
~~~

Python находит service в памяти этой программы и вызывает его метод. Отдельный браузер не может обратиться к этому объекту по имени: это другая программа со своей памятью.

Для внешнего клиента договор выглядит иначе:

Смысловая схема HTTP-обмена, не исполняемый код:

~~~text
браузер → request → сервер → PlannerService → хранилище
браузер ← response ← сервер
~~~

Клиент передаёт сообщение. Сервер разбирает его и сам выбирает внутреннюю работу. Поэтому сервер может заменить JsonStorage на базу данных, не заставляя браузер узнавать имя нового класса. Внешний договор и внутреннее устройство решают разные задачи.

Путь локального Persistent Planner остаётся таким, каким был: команда CLI вызывает локальный код, а JsonStorage работает с файлом. HTTP-модель описывает будущую границу приложения, а не заменяет уже сделанную программу.

## 02. Адрес отвечает на вопрос «куда?»

Полный URL содержит адрес сервиса и путь к ресурсу. Например:

~~~text
https://api.example.test:8000/tasks/7
\___/   \__________________/ \___/
схема       host и порт      path
~~~

- **Схема** https указывает способ обращения.
- **Host** api.example.test называет сервер.
- **Порт** 8000 помогает выбрать сетевой вход сервиса, если он указан.
- **Path** /tasks/7 указывает ресурс внутри API.

В нашей практике функция получает только path. Для списка задач это может быть /tasks, для одной задачи /tasks/7. Это адрес внешнего ресурса, а не путь к tasks.json на диске и не имя метода PlannerService.

**Проверка понимания: адрес и ресурс.**

| Адрес | Куда ведёт path |
| --- | --- |
| /tasks | Коллекция задач |
| /tasks/7 | Одна задача |
| /books/12 | Одна книга |

URL помогает клиенту выбрать сервер и путь. path в учебной модели хранит только путь. Эти понятия важно различать.

## 03. Method отвечает на вопрос «что сделать?»

Method добавляет намерение к адресу. Например, GET /tasks просит прочитать список, а POST /tasks передаёт данные для обработки. В нашем будущем Planner API этот POST будет создавать задачу.

~~~http
GET /tasks
POST /tasks
~~~

Адрес один, намерения разные. GET и POST здесь показывают два базовых случая. Другие методы встретятся дальше; сейчас достаточно понимать, что method и path несут разные сведения.

В настоящем HTTP имена методов чувствительны к регистру. Принято писать GET, а не get. Однако редактор этого занятия получает короткую строчную запись метода как исходное значение для учебной функции. Функция должна нормализовать его до верхнего регистра. Это условие упражнения, а не автоматическое правило отправки HTTP.

**Вопрос.** Если path в обоих случаях /tasks, означает ли это, что GET /tasks и POST /tasks делают одно и то же?

Нет. Path указывает область API, а method выражает намерение клиента.

## 04. Headers описывают сообщение, body содержит данные

**Headers** (заголовки) несут служебные сведения о сообщении. Они не заменяют данные задачи. В этом занятии важны два заголовка:

- Accept: application/json сообщает, что клиент хочет получить ответ в формате JSON.
- Content-Type: application/json сообщает, что тело отправленного сообщения содержит JSON.

Иными словами, Accept относится к желаемому ответу, а Content-Type описывает отправленное тело. Это разные направления.

В практике будет ещё Planner-Client-Version. Он нужен только как обычный пример пользовательского заголовка: в него попадёт версия клиента. Это не стандартное поле HTTP и не обязательное требование будущего Planner API.

Тело сообщения называется **body**. Если клиент создаёт задачу, в нём могут находиться поля задачи:

~~~http
POST /tasks
Accept: application/json
Content-Type: application/json

{"title": "Изучить HTTP", "priority": 4}
~~~

Здесь пустая строка отделяет заголовки от тела. Заголовки отвечают за описание сообщения, а title и priority являются данными операции. Не нужно помещать содержимое задачи в Accept.

`application/json` обозначает формат тела, но сам заголовок не преобразует Python-словарь в JSON. Перед отправкой это делает клиентская библиотека.

**Проверка понимания: части сообщения.**

| Сведение | На какой вопрос отвечает |
| --- | --- |
| Accept | В каком формате клиент хочет получить ответ? |
| Content-Type | В каком формате передано тело? |
| body | Какие данные операции отправлены? |

## 05. Отсутствующее тело не равно пустому объекту

Иногда тело не требуется. Например, чтение списка в нашей учебной модели выполняется без данных:

~~~text
GET /tasks
body = None
~~~

None означает, что тела нет. Пустой словарь {} означает, что тело есть, но в JSON-объекте пока нет полей. В зависимости от договора API эти ситуации могут обрабатываться по-разному.

В Python это видно через проверку на отсутствие:

~~~python
for body in (None, {}, {"title": "Изучить HTTP"}):
    print(body is not None)
~~~

Результат:

~~~text
False
True
True
~~~

Пустой словарь существует, хотя в нём нет записей. Поэтому проверка if body здесь ненадёжна: Python считает пустой словарь ложным значением.

~~~python
body = {}
if body:
    print("Тело передано")
else:
    print("Тела нет")
~~~

Этот код напечатает «Тела нет», хотя переменная содержит {}. Ошибка не в Python. Условие проверяет «не пусто ли значение», а нам нужно проверить «не равно ли оно None».

В контракте упражнения именно это различие определяет заголовок Content-Type: для None его нет, а для {} он есть. Когда body присутствует, функция возвращает его без изменения и не меняет исходный аргумент.

**Отладка. В чём ошибка?** Почему проверка выше неверно определяет наличие пустого тела?

Потому что истинность пустого словаря и наличие тела отвечают на разные вопросы. Для проверки отсутствия используют сравнение с None, а не проверку истинности.

## 06. Как части выглядят вместе и что делает клиентская библиотека

Ниже приведён сокращённый фрагмент HTTP/1.1. Он показывает расположение знакомых частей, но не является полным примером передачи тела по сети:

~~~http
POST /tasks HTTP/1.1
Host: api.example.test
Accept: application/json
Content-Type: application/json

{"title": "Изучить HTTP", "priority": 4}
~~~

В первой строке указаны method, path и версия протокола. Ниже идут headers. Host называет сервер. Пустая строка отделяет заголовки от body. В сокращённом фрагменте опущено оформление границ тела. Реальный HTTP/1.1 запрос с телом передаёт его длину через `Content-Length` либо использует `Transfer-Encoding: chunked`. Клиентская библиотека формирует эти транспортные детали. Вручную составлять HTTP в нашей практике не требуется.

**Проверка понимания: граница сервера и API.** Может ли Host: api.example.test заменить path /tasks?

Нет. Host выбирает сервер, а path указывает ресурс внутри него.

В реальном приложении клиентская библиотека обычно сериализует данные в нужный формат, оформляет сетевые детали и выполняет обмен. В этой практике мы не используем такую библиотеку. Функция вернёт обычный Python-словарь с четырьмя ключами:

~~~python
{
    "method": "GET",
    "path": "/tasks",
    "headers": {
        "Accept": "application/json",
        "Planner-Client-Version": "1.0",
    },
    "body": None,
}
~~~

Это **учебное описание request**, а не сериализованный HTTP-текст и не отправка по сети. В нём отдельно хранится path, поэтому здесь нет полного URL и Host. Словарь помогает сосредоточиться на смысле частей, не смешивая его с транспортом.

## 07. Что будем делать в практике

Мы напишем solve(method, path, client_version, body). На вход уже поступят готовые значения. Функция только соберёт их в словарь, который описывает request.

Постоянные заголовки будут включать Accept и Planner-Client-Version. method придёт в короткой строчной записи, а path останется без изменения. Тело тоже сохраняется таким, каким пришло.

Главная развилка связана с наличием body. Для None тело отсутствует и Content-Type не добавляется. Для любого словаря, даже пустого, тело есть и заголовок формата нужен. Практика проверит оба случая, а также обычный заполненный объект.

Сеть, изменения Planner, создание API и преобразование словаря в JSON-строку не входят в задачу. Результат занятия скромнее и точнее: различать части сообщения и собирать их представление, не путая пустое значение с отсутствующим.

Когда эта модель станет понятной, в следующем занятии мы разберём другую сторону обмена: как клиент читает HTTP response.
