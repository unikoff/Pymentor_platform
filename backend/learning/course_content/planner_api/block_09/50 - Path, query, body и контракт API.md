## 00. От знакомой карты к понятному запросу

В предыдущем занятии мы выбрали method и path для операций Planner API. Например, `GET /tasks` читает коллекцию, а `GET /tasks/7` выбирает одну задачу. Этого уже достаточно, чтобы увидеть маршрут. Но клиенту пока неясно, где передать фильтр, какие данные нужны для создания и что именно вернётся.

Представьте форму заказа. Адрес выбирает место назначения, параметры уточняют заказ, а содержимое описывает саму покупку. Если положить всё в одно поле, получатель не поймёт, что с этим делать. HTTP-запрос тоже разделяет значения по роли.

Путь занятия такой:

1. Вспомним, что уже выражают method и path.
2. Разберём, где разместить id, настройки списка и данные Task.
3. Сравним создание, полную замену и частичное изменение.
4. Уточним, какие ответы клиент ожидает от сервера.
5. Соберём учебную модель запроса в интерпретаторе.

Сейчас мы не запускаем сервер и не пишем его внутренние модели. Сначала разберём внешний договор, которым смогут пользоваться обе стороны.

```text
method + path → какое действие и над каким ресурсом
query         → как настроить чтение коллекции
body          → какие данные передать
response      → какой результат получит клиент
```

### Небольшой прогноз

```python
request = {
    "path": {"task_id": 7},
    "query": {"limit": 10},
    "body": {"title": "HTTP"},
}

print(request["path"]["task_id"], request["query"]["limit"], request["body"]["title"])
```

Что напечатает код?

**Разбор.** На экран попадёт `7 10 HTTP`. Значения находятся в разных частях модели. Path выбирает item, query настраивает чтение, body содержит данные Task.

## 01. Контракт API связывает клиента и сервер

Контракт API описывает согласованный обмен. Клиент по нему собирает request. Разработчик сервера понимает, какие данные принять и какой response вернуть.

В реальном проекте над API часто работают разные люди и команды. Клиент может быть сайтом, мобильным приложением или ботом. Сервер при этом остаётся один. Контракт позволяет писать и проверять обе стороны независимо.

Для одной операции договор отвечает на несколько простых вопросов:

- какое действие выполняет method;
- какой resource выбирает path;
- какие данные получает сервер и откуда;
- какой status и response означают успех;
- какие ожидаемые ошибки нужно обработать.

```text
PATCH /tasks/{task_id}
body: переданные изменяемые поля
200: полная Task
404: item не найден
```

Сравните это с фразой «отправьте изменения и получите успех». Во втором описании клиент не знает, какие поля можно отправить, какая форма результата придёт и что делать, если item отсутствует.

Контракт не требует заранее знать, как написан сервер. Он описывает видимую границу между программами. Внутри сервер может использовать Python-класс, JSON-файл или базу, если внешние обещания остаются теми же.

### Интерактив. Соедините часть договора с вопросом

Соедините method с вопросом «что сделать?», path с «с каким ресурсом?», inputs с «что передать?», success с «как выглядит успех?», errors с «как сообщить об отказе?».

**Разбор.** Method и path задают операцию. Inputs описывают вход. Success и errors определяют, как клиент прочитает исход обмена.

## 02. Разделите места для данных

В HTTP-сообщении есть разные части. Их назначение важнее того, в каком формате записано значение.

- **Path** выбирает ресурс или item. Например, `/tasks/7` указывает на задачу 7.
- **Query** настраивает чтение коллекции. Например, `is_done=false` отбирает незавершённые задачи.
- **Body** содержит данные действия. При создании Task это `title` и `priority`.
- **Headers** описывают сообщение. Например, `Content-Type` сообщает формат body.

Посмотрите на два примера:

```text
GET /tasks?is_done=false&limit=10
Accept: application/json
```

Здесь фильтр и ограничение списка находятся в query. Заголовок `Accept` сообщает, какой формат ответа предпочитает клиент.

```text
POST /tasks
Content-Type: application/json

{"title": "Изучить HTTP", "priority": 4}
```

Здесь body содержит данные задачи, а `Content-Type` сообщает серверу, как прочитать это тело. Он не является полем Task.

Не пытайтесь выбрать место только по типу значения. Строка может быть частью path, query или body. Спросите себя, какую роль она выполняет в этой операции.

### Отладка: фильтр оказался в неверном месте

```text
GET /tasks
body: {"is_done": false}
response: одна Task
```

Что не сходится? Для GET списка фильтр должен настраивать чтение коллекции, а ответ должен содержать список, не один item.

**Исправление:** передайте `is_done=false` в query и опишите результат как список задач.

## 03. Path выбирает объект, query настраивает список

Path помогает назвать область действия. `/tasks` указывает на коллекцию. `/tasks/7` выбирает конкретный item с идентификатором 7.

```text
GET /tasks
GET /tasks/7
```

Идентификатор в path сообщает серверу, какую задачу имеет в виду клиент. Он ещё не доказывает, что запись существует. Проверить наличие item сможет сервер во время обработки запроса.

Query добавляет настройки к чтению коллекции. Для Planner это:

- `is_done` задаёт фильтр по состоянию;
- `sort_desc` выбирает порядок по id, от меньшего к большему или наоборот;
- `limit` ограничивает количество возвращаемых задач.

Параметры необязательные. Если клиент их не передал, сервер применяет значения по умолчанию: `is_done=None`, `sort_desc=False`, `limit=10`. Допустимый limit от 1 до 50.

Сравните:

```text
GET /tasks
```

Клиент не задал условие по `is_done`. Сервер применит обычное поведение по умолчанию.

```text
GET /tasks?is_done=false
```

Клиент явно попросил задачи, у которых `is_done` равно `false`. Это не отсутствие значения, а конкретный фильтр.

### Что произойдёт без optional query?

Выберите верное объяснение: сервер применит договорные defaults; клиент запросил только незавершённые задачи; path автоматически выберет первую задачу.

**Ответ:** применяются defaults. Только явно переданное `is_done=false` задаёт фильтр по незавершённым задачам.

Query меняет результат чтения коллекции, но не меняет сами задачи. В частности, фильтр списка не влияет на статистику: `GET /stats` считает значения по всему хранилищу.

## 04. Body содержит данные создания или изменения

Когда клиент создаёт задачу, он передаёт значения, которыми может управлять: `title` и `priority`.

```http
POST /tasks
Content-Type: application/json

{
  "title": "Изучить HTTP",
  "priority": 4
}
```

Клиент не назначает `id`. Сервер также задаёт начальное `is_done=false`. После успешного создания договор обещает ответ `201 Created` и полное публичное представление:

```http
201 Created
Content-Type: application/json

{
  "id": 8,
  "title": "Изучить HTTP",
  "priority": 4,
  "is_done": false
}
```

Вход и ответ связаны, но не обязаны совпадать. Вход говорит, что создать. Ответ описывает созданную запись, включая поля, добавленные сервером.

Внутри сервера JSON может превратиться в dataclass, словарь или объект другой модели. Клиенту не нужно знать это устройство.

```text
JSON body → серверная проверка → внутренняя модель
внутренняя модель → публичное представление → response body
```

### Подумайте

Почему клиенту не нужно присылать id при создании?

**Ответ.** Id назначается для новой записи сервером. Если клиент выберет его сам, разные клиенты смогут предложить конфликтующие значения.

## 05. PUT и PATCH передают разный объём изменений

Для полной замены выбранной Task договор принимает всю изменяемую форму:

```http
PUT /tasks/8
Content-Type: application/json

{
  "title": "Изучить HTTP",
  "priority": 4,
  "is_done": false
}
```

Здесь перечислены все изменяемые поля: `title`, `priority`, `is_done`. Идентификатор уже выбран через path.

PATCH нужен, когда клиент меняет только часть данных:

```http
PATCH /tasks/8
Content-Type: application/json

{"is_done": true}
```

В этом запросе остальные поля не перечислены, поэтому сохраняются. Отсутствующий ключ и ключ со значением `false` имеют разный смысл:

```text
is_done отсутствует → не менять это поле
is_done передан как false → снять отметку
```

Именно здесь часто возникает ошибка в коде. Проверка истинности теряет переданный `false`:

```python
if values.get("is_done"):
    body["is_done"] = values["is_done"]
```

Такой код добавит поле только для `true`. Для частичного обновления надо проверить, передан ли ключ:

```python
if "is_done" in values:
    body["is_done"] = values["is_done"]
```

Явный `null` может означать очистку поля, но только если это разрешает конкретный договор. В текущем упражнении такого значения нет. Мы учимся сохранять различие между отсутствующим ключом и переданным `false`.

Не дублируйте `task_id` в body. Если path указывает на `/tasks/8`, а body содержит другой id, серверу пришлось бы угадывать, какой из них использовать.

## 06. Ответ и ожидаемая ошибка тоже часть договора

После обработки request сервер возвращает response. Status помогает клиенту понять результат, а body содержит объект, список, статистику или отсутствует, если договор не предусматривает тело.

- `GET /health` возвращает `200` и короткий статус сервиса.
- `GET /tasks` возвращает `200` и список. Он может быть пустым.
- `GET /tasks/{task_id}` возвращает `200` и одну Task, если item найден.
- `GET /stats` возвращает `200` и сводку по хранилищу.
- `POST /tasks` возвращает `201` и созданную Task.
- `PUT /tasks/{task_id}` и `PATCH /tasks/{task_id}` возвращают `200` и полную Task.
- `DELETE /tasks/{task_id}` возвращает `204` без body.

Пустая коллекция не является ошибкой:

```text
GET /tasks
→ 200 OK
→ []
```

Но если клиент запросил конкретную задачу, которой нет, сервер отвечает `404 Not Found`. Операции имеют разную область: первая читает коллекцию, вторая выбирает один item.

Удаление отличается от чтения и изменения. Успешный ответ `204 No Content` не содержит body. Клиент не должен пытаться вызывать разбор JSON для этого ответа.

`400 Bad Request` можно использовать как общий пример request, который не соответствует договору. Здесь не нужно придумывать им все ошибки полей. В следующих занятиях мы разберём валидацию FastAPI/Pydantic и ответ `422`.

`GET /health` проверяет, отвечает ли сервис. `GET /stats` возвращает сводку по всему хранилищу. Статистика не зависит от query фильтров списка. Эти два технических маршрута не требуют параметров списка.

### Соедините сценарий и ответ

- Пустой список: `200` и `[]`.
- Неизвестный item: `404`.
- Созданная задача: `201` и полное представление.
- Успешное удаление: `204` без body.

Status и форма ответа помогают клиенту выбрать следующее действие. Одна только строка «успех» для этого недостаточна.

## 07. Что будем делать в практике

В интерпретаторе функция `solve(action, task_id, values)` соберёт учебную модель запроса Planner API. Готовая часть уже выбирает method и path. Вам останется распределить значения.

1. Для `list` скопируйте в query только переданные `is_done`, `sort_desc`, `limit`. Не добавляйте отсутствующие ключи со значениями по умолчанию.
2. Для `create` соберите body из `title` и `priority`. Для `replace` передайте полную изменяемую форму. Для `update` скопируйте только переданные поля.
3. Верните словарь с точными ключами `method`, `path`, `query`, `body`. Для операций без таких входов оставьте query пустым, body равным `None`.

Упражнение получает только известные действия и допустимые значения. Не нужно проверять существование Task, фильтровать данные, отправлять HTTP, запускать FastAPI или менять исходный словарь `values`. Query остаётся словарём Python. Преобразование его значений в текст URL появится в реальном HTTP-клиенте.

### Как проверить ход мысли

Автотесты рассмотрят список с параметрами и без них, создание, PUT, PATCH только с `is_done=False`, чтение и удаление item, а также `health` и `stats`. Они проверят, что явный `false` не пропал и исходный `values` не изменился.

Отдельно объясните два ответа:

- `GET /tasks` без задач возвращает `200` и пустой список;
- `GET /tasks/999` для отсутствующего item возвращает `404`.

А затем сравните успешное создание с удалением: создание возвращает `201` и новую Task, удаление возвращает `204` без JSON body.

Так мы завершим модель обмена до настоящего HTTP. В следующем блоке Postman Echo покажет, как выглядят отправленные query-параметры и JSON body. Echo только отражает запрос, он не создаёт Planner Task.

## 08. Главное

- Path выбирает ресурс или конкретный item.
- Query настраивает чтение коллекции и может отсутствовать.
- Body содержит данные создания или изменения.
- Headers описывают само сообщение.
- POST принимает `title` и `priority`; сервер назначает `id` и начальное `is_done`.
- PUT передаёт полную изменяемую форму, PATCH только переданные поля.
- Явный `false` не равен отсутствующему ключу.
- Контракт описывает вход, status, форму ответа и ожидаемые ошибки.
- Пустой список означает `200`, неизвестный item означает `404`, успешное удаление означает `204` без body.

Один вопрос для самопроверки: почему method и path ещё не описывают весь запрос? Потому что клиенту также нужно знать, где передать значения и какой результат обещан сервером.
