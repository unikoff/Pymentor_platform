## 00. Мы уже проверяем вход. Теперь нужно договориться об ответе

- **Прежняя опора.** POST принимает проверенный `TaskCreate`. Существующий `PlannerService` создаёт `Task` и сохраняет её в общем `JsonStorage`.
- **Новый вопрос.** Как описать ответ клиенту, не смешивая его с входным body и полным внутренним объектом?
- **Результат.** Добавим `TaskRead` и подключим `response_model` к действующим GET и POST. Сервис, хранилище и CLI останутся прежними.

Создание задачи не заканчивается проверкой входа. Сначала сервер принимает разрешённые данные, затем создаёт ресурс и возвращает клиенту результат. В предыдущем занятии `TaskCreate` стала проверяемым входом настоящего POST. При успехе существующий `PlannerService` создаёт `Task`, назначает серверные поля и сохраняет её через `JsonStorage`.

Клиент может отправить такой body:

```json
{
  "title": "Разобрать response_model",
  "priority": 4
}
```

Но успешный ответ создания выглядит иначе:

```json
{
  "id": 7,
  "title": "Разобрать response_model",
  "priority": 4,
  "is_done": false
}
```

На входе было два поля. На выходе стало четыре. Внутренняя доменная `Task` при этом содержит ещё и поле `tags`, которого нет в публичном HTTP-ответе.

Request и response связаны одной операцией, но описывают разные стороны обмена. Если поручить одной схеме обе роли, станет неясно, какими полями управляет клиент, а какие принадлежат уже созданной задаче.

## 01. Одна задача существует в нескольких представлениях

Когда мы говорим «задача», легко представить один объект с одним набором полей. В работающем приложении это слишком грубое описание.

Одна и та же предметная задача проходит через несколько границ, и на каждой границе важен свой набор данных.

### HTTP request

Клиент сообщает только то, чем он управляет при создании:

```json
{
  "title": "Повторить FastAPI",
  "priority": 3
}
```

На этой границе нам не нужен готовый `id`: новой записи ещё нет. Начальное `is_done` тоже не выбирает клиент.

### Входная Pydantic-схема

`TaskCreate` описывает допустимую форму request body.

Она отвечает на вопрос:

> Какие данные клиент может передать, когда просит создать задачу?

В текущем договоре это `title` и `priority`.

### Доменная модель

После проверки входа приложение вызывает существующую операцию Planner. Внутри проекта уже работает доменная `Task`.

Она относится не только к HTTP. Ей пользуются сервис, CLI и хранилище.

У неё есть предметные данные проекта:

```text
id
title
priority
is_done
tags
```

Доменная модель отвечает за состояние задачи внутри Planner. Она не должна становиться HTTP-схемой только потому, что часть её полей видна клиенту.

### JSON-хранилище

`JsonStorage` сохраняет полную доменную запись в прежнем формате проекта. Старый CLI тоже должен продолжать читать эти данные.

В нашем курсе `tags` сохраняется внутри `Task` и JSON. Добавление API не должно незаметно удалить поле из существующего проекта.

### HTTP response

Клиенту мы публикуем только согласованное представление:

```text
id
title
priority
is_done
```

Для этой границы нужна отдельная схема `TaskRead`.

Получается четыре разных роли:

- `TaskCreate` описывает, что клиент может прислать: `title` и `priority`.
- Доменная `Task` описывает объект, с которым работает Planner: `id`, `title`, `priority`, `is_done` и `tags`.
- `JsonStorage` сохраняет полную доменную запись между запусками.
- `TaskRead` описывает, что API обещает показать клиенту: `id`, `title`, `priority` и `is_done`.

Это не четыре случайные копии одной структуры. У каждой формы своя ответственность.

### Интерактив. Соедините роль и вопрос

Соедините элементы:

- `TaskCreate`
- `Task`
- `JsonStorage`
- `TaskRead`

с вопросами:

- что клиент может передать;
- с чем работает прикладная логика;
- что переживает перезапуск;
- что клиент получает наружу.

**Разбор.**

`TaskCreate` относится к request. `Task` относится к предметной модели. `JsonStorage` отвечает за сохранение. `TaskRead` относится к response.

Если эти роли смешать, изменение HTTP-контракта начнёт неожиданно менять доменную модель или формат файла.

## 02. TaskCreate остаётся схемой входа

В этом занятии мы не проектируем `TaskCreate` заново.

В прошлом шаге она уже получила правила HTTP-входа. Эти правила нужно сохранить целиком при дальнейшем переносе схем в отдельный модуль.

Смысл `TaskCreate` теперь важнее её синтаксиса:

> `TaskCreate` описывает данные, которыми клиент управляет в операции создания.

Поэтому в ней есть:

```text
title
priority
```

и нет:

```text
id
is_done
tags
```

### Почему в request нет id

До создания новой записи сервер ещё не назначил идентификатор.

Если позволить каждому клиенту самостоятельно выбирать постоянный `id`, два разных клиента могут предложить одно и то же значение. Тогда правило идентичности ресурса окажется распределено между внешними программами.

В нашем Planner это серверная обязанность.

```text
клиент:
"title", "priority"

сервер:
назначает "id"
задаёт начальный "is_done"
сохраняет полную Task
```

### Почему в request нет is_done

При создании новая задача получает начальное состояние по правилам существующего `PlannerService`. Клиент не должен подменять это правило входным body.

Позже изменение `is_done` появится в операциях обновления. Но это другой HTTP-договор, а не причина расширять `TaskCreate`.

### Почему в request нет tags

`tags` существует в старой доменной модели и JSON, но текущий Planner API его не публикует.

Это принципиальная граница курса:

> Поле может существовать внутри приложения, не являясь частью публичного API.

Если завтра внутренняя модель получит ещё одно служебное поле, это не означает, что клиент автоматически получает право отправлять его.

### Что если клиент всё равно передаст лишний id

Представим request:

```json
{
  "title": "Изучить схемы",
  "priority": 4,
  "id": 999
}
```

Наличие лишнего ключа не превращает его в серверный идентификатор.

HTTP-операция создания всё равно должна вызвать существующий сценарий с теми данными, которые принадлежат `TaskCreate`: `title` и `priority`.

Мы не вводим в этом занятии отдельную политику запрета всех extra-полей. Без специальной настройки Pydantic лишние входные поля не обязаны давать `422`. Для нас важнее другое: клиентский `id` не должен управлять реальным id созданной `Task`.

### Небольшая самопроверка

Что из перечисленного относится к `TaskCreate`?

1. Выбрать следующий `id`.
2. Проверить HTTP-вход `title` и `priority`.
3. Сохранить JSON.
4. Описать все поля доменной `Task`.

**Ответ:** только второй пункт.

Создание id, предметное действие и сохранение находятся дальше по цепочке.

## 03. Зачем появляется TaskRead

Теперь посмотрим на другую сторону обмена.

После успешного создания сервер уже располагает полноценной задачей. Клиенту нужно получить стабильный публичный результат.

Мы можем просто вернуть словарь:

```python
return {
    "id": task.id,
    "title": task.title,
    "priority": task.priority,
    "is_done": task.is_done,
}
```

Такой ответ может быть правильным. Но пока форма существует только как договорённость внутри нашего кода.

FastAPI не знает из этой функции, что именно эти четыре поля являются обещанной публичной моделью ответа.

Нам нужна отдельная HTTP-схема, которая отвечает на вопрос:

> Как выглядит одна задача, когда API отдаёт её клиенту?

Эту роль выполняет `TaskRead`.

У неё должны быть четыре публичных поля:

- `id`;
- `title`;
- `priority`;
- `is_done`.

Обратите внимание на направление:

```text
TaskCreate
request → server

TaskRead
server → response
```

Названия похожи, часть полей совпадает, но смысл противоположный.

### Почему id есть в TaskRead

На момент response ресурс уже существует. Сервер назначил id, и клиенту нужен этот идентификатор для следующих операций:

```text
GET /tasks/{task_id}
```

Позже по тому же id будут выполняться операции изменения и удаления.

### Почему is_done есть в TaskRead

Состояние задачи является частью публичного представления ресурса.

Даже если при создании клиент его не выбирает, после создания клиент должен видеть фактическое состояние.

### Почему tags нет в TaskRead

Потому что публичный договор этого курса содержит четыре поля.

Это не означает, что `tags` больше не существует.

```text
Task:
id, title, priority, is_done, tags

TaskRead:
id, title, priority, is_done
```

`TaskRead` описывает внешний срез данных. Она не редактирует доменную модель и не переписывает JSON.

### Почему не сделать один универсальный TaskSchema

Можно было бы создать модель вроде:

```python
class TaskSchema(BaseModel):
    id: int | None = None
    title: str
    priority: int
    is_done: bool = False
```

Сначала это кажется удобным: один класс подходит почти везде.

Но договор становится менее точным.

Для POST внезапно оказывается допустимым `id`, хотя сервер должен назначать его сам. `is_done` выглядит как клиентское поле создания, хотя это не так. А optional `id` скрывает важную разницу между «объект ещё не создан» и «сервер возвращает существующий ресурс».

Раздельные схемы делают направление данных явным:

```text
создание:
TaskCreate

публичное чтение:
TaskRead
```

Позже отдельная операция обновления получит свою схему тогда, когда она действительно появится в проекте.

### Интерактив. Какая схема отвечает на вопрос?

Сопоставьте:

- «Что клиент может прислать при POST?»
- «Как выглядит задача в успешном GET?»
- «Какие поля сохраняет старый Planner?»

с:

- `TaskCreate`
- `TaskRead`
- доменная `Task` / `JsonStorage`

**Разбор.** HTTP-схемы не заменяют доменную модель. Они описывают внешнюю границу в конкретном направлении.

## 04. TaskRead не заменяет доменную Task

После появления новой Pydantic-схемы легко сделать неправильный вывод:

> Раз `TaskRead` уже содержит почти все поля задачи, может быть теперь весь сервис должен работать с ней?

Нет.

Посмотрим на роли ещё раз.

### Доменная Task

`Task` существовала до появления FastAPI.

Ей уже пользуются:

- `PlannerService`;
- CLI;
- `JsonStorage`;
- существующие тесты;
- предметные правила проекта.

Она является частью ядра Planner.

### TaskRead

`TaskRead` появляется только потому, что у проекта появилась HTTP-граница.

Она нужна FastAPI для публичного ответа.

Если сделать `PlannerService` зависимым от `TaskRead`, прикладной слой начнёт зависеть от формы конкретного интерфейса. Тогда изменение API сможет заставить нас менять сервис даже при неизменных предметных правилах.

Нужное направление выглядит так:

```text
HTTP request
    ↓
HTTP schema
    ↓
PlannerService
    ↓
domain Task
    ↓
JsonStorage

и обратно:

domain Task
    ↓
public projection
    ↓
HTTP response schema
    ↓
HTTP response
```

А не так:

```text
HTTP schema
    ↓
PlannerService
    ↓
JsonStorage
```

где Pydantic-схема неожиданно становится моделью всего приложения.

### Независимый пример

Представим приложение каталога.

Внутренний объект товара содержит:

```text
id
name
price
supplier_code
purchase_price
```

Публичный API может отдавать:

```text
id
name
price
```

Если публичная модель ответа не содержит `supplier_code`, это не повод удалить код поставщика из внутреннего объекта.

То же происходит с `tags` в Planner.

### Интерактив. Сравните два решения

**Решение A**

`PlannerService` начинает принимать и возвращать `TaskRead`, а `JsonStorage` сохраняет `TaskRead.model_dump()`.

**Решение B**

`PlannerService` продолжает работать с доменной `Task`, `JsonStorage` сохраняет прежний формат, а HTTP-слой использует `TaskRead` только для внешнего ответа.

Какое решение соответствует текущей архитектуре?

**Разбор:** решение B.

Новая HTTP-схема уточняет внешний договор, но не заменяет уже работающие модель и хранилище.

## 05. response_model: явный договор ответа

Теперь мы готовы к главной новой механике занятия.

FastAPI позволяет указать ожидаемую форму успешного ответа через `response_model`.

Разберём механизм на независимом примере, чтобы не выдавать готовую реализацию Planner.

```python
from fastapi import FastAPI
from pydantic import BaseModel

app = FastAPI()


class ArticleRead(BaseModel):
    id: int
    title: str


@app.get("/article", response_model=ArticleRead)
def get_article():
    return {
        "id": 3,
        "title": "HTTP response",
        "internal_note": "draft",
    }
```

Функция возвращает три поля:

```text
id
title
internal_note
```

Но публичная модель ответа содержит два:

```text
id
title
```

Клиент получает форму, объявленную как `ArticleRead`.

```json
{
  "id": 3,
  "title": "HTTP response"
}
```

Поле `internal_note` осталось внутренней частью результата функции и не вошло в HTTP-представление.

### Что делает response_model

Для текущего занятия важно понимать три основные роли.

1. **Проверяет возвращаемые данные.**

   FastAPI ожидает, что успешный результат можно представить в форме объявленной модели.

2. **Описывает response в OpenAPI.**

   Swagger UI может показать клиенту, какой JSON ожидается в успешном ответе.

3. **Ограничивает публичную форму данных.**

   Поля, которых нет в модели ответа, не должны случайно стать частью публичного response.

Это направление противоположно входной модели.

```text
request body
    ↓
TaskCreate
    ↓
handler
```

и:

```text
handler result
    ↓
TaskRead / response_model
    ↓
response body
```

### response_model находится в декораторе

Обратите внимание на место записи:

```python
@app.get("/article", response_model=ArticleRead)
def get_article():
    ...
```

`response_model` относится не к параметрам функции, а к результату path operation.

Сравните:

```python
def create_article(payload: ArticleCreate):
```

`payload: ArticleCreate` описывает вход.

```python
@app.post("/articles", response_model=ArticleRead)
```

`response_model=ArticleRead` описывает выход.

Это два независимых направления одного HTTP-обмена.

### response_model для списка

Если endpoint возвращает коллекцию объектов, схема описывает элемент списка:

```python
@app.get("/articles", response_model=list[ArticleRead])
def list_articles():
    ...
```

Теперь успешный response должен быть массивом, где каждый элемент соответствует `ArticleRead`.

Для Planner эта идея понадобится при чтении коллекции задач.

### Интерактив. Пройдём путь ответа по шагам

Есть функция:

```python
@app.get("/article", response_model=ArticleRead)
def get_article():
    return {
        "id": 5,
        "title": "FastAPI",
        "internal_note": "do not publish",
    }
```

Расположите этапы:

- FastAPI получает Python-результат функции.
- Проверяется объявленная модель ответа.
- Лишняя часть не входит в публичную форму.
- Клиент получает JSON response.

**Разбор:**

```text
handler
   ↓
Python result
   ↓
response_model
   ↓
validation / filtering
   ↓
JSON response
```

`response_model` не меняет значение в storage. Он работает на границе формируемого ответа.

## 06. Что происходит с tags

Вернёмся к Planner.

Допустим, внутри приложения есть такая доменная запись:

```python
task_data = {
    "id": 12,
    "title": "FastAPI",
    "priority": 4,
    "is_done": False,
    "tags": ["backend", "api"],
}
```

Публичный договор `TaskRead` содержит:

```text
id
title
priority
is_done
```

`tags` в него не входит.

Что должен увидеть клиент?

```json
{
  "id": 12,
  "title": "FastAPI",
  "priority": 4,
  "is_done": false
}
```

Теперь главный вопрос раздела:

> Что произошло с tags внутри Task и JSON?

Ничего.

Поле перестало быть видимым в конкретном HTTP response, но не исчезло из приложения.

Это разные действия:

```text
не публиковать поле
≠ удалить поле из объекта

не публиковать поле
≠ изменить JsonStorage

не публиковать поле
≠ вызвать save()

не публиковать поле
≠ изменить формат старого Planner
```

### Почему это важно

Представьте объект пользователя:

```text
id
name
email
password_hash
```

Публичный ответ профиля может содержать:

```text
id
name
email
```

То, что `password_hash` не попал в response, не означает, что система удалила его из хранилища.

Разделение внутренней и публичной формы защищает границу API.

В Planner поле `tags` не является секретом уровня пароля, но принцип тот же: внутренние данные и публичный договор не обязаны совпадать.

### Predict output

Функция возвращает:

```python
{
    "id": 4,
    "title": "Schemas",
    "priority": 2,
    "is_done": True,
    "tags": ["python"],
}
```

Модель ответа содержит только четыре публичных поля Planner.

Что попадёт в JSON response?

**Разбор.** В публичный ответ попадут `id`, `title`, `priority` и `is_done`. `tags` не становится частью HTTP response. Это не доказывает изменение исходной `Task` или JSON-файла.

### Два уровня защиты

В текущем проекте ответы уже собирают явную четырёхпольную проекцию Task. Это полезно: HTTP-слой явно выбирает публичные поля.

`TaskRead` добавляет ещё одну проверяемую границу поверх этого результата.

Получается:

```text
domain Task
    ↓
явная публичная проекция
    ↓
TaskRead как response_model
    ↓
HTTP response
```

Не нужно специально возвращать все внутренние поля только ради демонстрации фильтрации. Механизм мы уже увидели на независимом примере.

В проекте важнее сохранить понятную явную проекцию и добавить к ней формальную схему ответа.

## 07. Неправильный response: ошибка сервера, а не 422 клиента

В прошлом занятии мы много работали с `422`.

Там проблема находилась во входе:

```text
client request
    ↓
TaskCreate
    ✕
данные не прошли проверку
```

Теперь посмотрим на другую ситуацию.

```python
from pydantic import BaseModel


class ArticleRead(BaseModel):
    id: int
    title: str
```

Маршрут обещает `ArticleRead`:

```python
@app.get("/article", response_model=ArticleRead)
def get_article():
    return {
        "title": "HTTP",
    }
```

В response отсутствует обязательный `id`.

Клиент ничего не сделал неправильно. Он просто вызвал GET.

Ошибка появилась потому, что сервер обещал одну форму результата, а его код сформировал другую.

```text
правильный request
    ↓
handler
    ↓
неправильный result
    ↓
response validation error
```

Такую проблему нельзя описывать как обычный клиентский `422`.

### Сравним две ситуации

- Если request не соответствует `TaskCreate`, проблема во входе клиента.
- Если результат handler не соответствует `TaskRead`, проблема в коде сервера.

Это очень важное разделение.

`422` из прошлого занятия не означает «любая Pydantic-ошибка всегда превращается в 422».

Направление имеет значение.

### Bug Hunt. Где ошибка?

```python
class ProfileRead(BaseModel):
    id: int
    username: str


@app.get("/profile", response_model=ProfileRead)
def get_profile():
    return {"username": "nikita"}
```

Выберите причину:

1. Клиент забыл отправить id в GET body.
2. Сервер вернул результат, который не соответствует обещанной форме.
3. Pydantic должен автоматически придумать id.

**Ответ:** второй вариант.

У GET нет причины получать server-owned id из request body. Если `response_model` требует `id`, его должен сформировать серверный код.

### Почему response validation не откатывает уже выполненное действие

Есть ещё одна важная граница.

Представим последовательность:

```text
service.add(...)
    ↓
JsonStorage.save(...)
    ↓
handler формирует неправильный response
    ↓
response validation error
```

Если сохранение уже произошло, ошибка проверки ответа сама по себе не является транзакцией и не отменяет запись назад.

Поэтому `response_model` нужно воспринимать как защиту внешней формы, а не как механизм отката состояния.

В нашем учебном проекте мы стараемся строить правильный ответ из результата успешной операции. Но важно понимать ответственность инструмента: проверка response не заменяет транзакцию storage.

## 08. model_dump() не сохраняет задачу

`model_dump()` легко спутать с переходом от модели к данным приложения.

Например:

```python
from pydantic import BaseModel


class FeedbackInput(BaseModel):
    text: str
    rating: int


payload = FeedbackInput(text="Полезно", rating=5)
data = payload.model_dump()
```

Теперь `data` становится обычным словарём Python:

```python
{
    "text": "Полезно",
    "rating": 5,
}
```

Что произошло?

Pydantic представил значения модели как словарь.

Что не произошло?

- не была создана доменная сущность;
- не был вызван сервис;
- не был назначен id;
- не был вызван `JsonStorage.save()`;
- не изменился файл;
- не появилась постоянная запись.

То же относится к `TaskCreate`.

```text
TaskCreate
    ↓ model_dump()
dict
```

Это преобразование представления.

А создание задачи в Planner выглядит иначе:

```text
TaskCreate
    ↓
PlannerService.add_task(...)
    ↓
Task
    ↓
JsonStorage.save(...)
```

### Почему это разделение важно

Если написать endpoint, который просто возвращает:

```python
return payload.model_dump()
```

клиент действительно увидит JSON.

Но красивый JSON response ещё не доказывает, что задача существует в Planner.

Такой handler может оказаться обычным echo.

В нашем проекте настоящий POST уже проходит через существующий `PlannerService` и сохраняет задачу в общий JSON. В 58-м занятии мы не переписываем этот путь.

### True / False

> `model_dump()` записывает Pydantic-модель в `data/tasks.json`.

**Ответ:** false.

`model_dump()` создаёт Python-представление. За постоянное хранение отвечает `JsonStorage` через существующий путь приложения.

### Ещё одна частая путаница

`TaskRead` тоже не сохраняет данные.

Даже если создать объект:

```python
article = ArticleRead(id=1, title="HTTP")
```

мы лишь получили Pydantic-модель.

Никакой файл не изменится, пока приложение явно не выполнит свою операцию сохранения.

## 09. schemas.py: отдельное место для HTTP-схем

До этого первая Pydantic-схема могла находиться рядом с маршрутом. Когда HTTP-моделей становится несколько, полезно отделить их от сборки приложения.

В существующем Planner мы не создаём новый проект. Мы продолжаем текущее дерево:

```text
app/
├── main.py
├── api.py
├── cli.py
├── models.py
├── services.py
├── storage.py
└── schemas.py
```

Новый `schemas.py` относится только к внешним форматам HTTP.

### Что остаётся в models.py

Доменная `Task`.

Она существовала до API и продолжает описывать предметную сущность Planner.

### Что находится в schemas.py

HTTP-схемы текущего этапа:

```text
TaskCreate
TaskRead
```

`TaskCreate` переносится вместе со всеми действующими правилами предыдущего занятия. При переносе нельзя потерять нормализацию, ограничения или другой уже согласованный механизм проверки.

`TaskRead` добавляется как отдельный публичный договор ответа.

### Что остаётся в services.py

Операции `PlannerService`.

`schemas.py` не должен забирать на себя создание, поиск, сохранение или генерацию id.

### Что остаётся в storage.py

Работа с постоянным JSON.

Pydantic-схемы не должны начать напрямую открывать файл.

### Что остаётся в api.py

FastAPI-приложение и HTTP-граница текущего этапа.

Маршруты импортируют нужные HTTP-схемы и используют существующий сервис.

Получается простое направление:

```text
api.py
 ├─ использует schemas.py
 └─ вызывает PlannerService

PlannerService
 └─ работает с Task и storage
```

`services.py` не должен импортировать FastAPI только потому, что API теперь использует схемы.

### Почему не создаём TaskUpdate заранее

На этом этапе PUT ещё не является новой работой занятия.

Если добавить `TaskUpdate` только потому, что «когда-нибудь пригодится», у нас появится класс без текущего применения. Ученик увидит новую сущность раньше задачи, которую она решает.

Мы добавим отдельные схемы обновления вместе с реальными PUT/PATCH в соответствующем занятии.

Правило здесь простое:

> Схема появляется тогда, когда появляется реальная граница данных, которую она описывает.

Сейчас таких новых направлений два: создание и публичное чтение.

## 10. Как TaskRead подключается к уже работающему API

До начала этого занятия API уже умеет:

- получить список задач;
- получить одну задачу по id;
- создать настоящую задачу через POST;
- сохранить её в общий JSON;
- вернуть после создания `201`;
- читать эти же данные через CLI и после перезапуска.

Мы не меняем смысл этих операций.

Мы делаем их внешний response явным.

### Коллекция

`GET /tasks` возвращает список публичных задач.

Поэтому response model относится не к одному объекту, а к списку объектов одного типа.

На независимом примере это выглядит так:

```python
@app.get("/articles", response_model=list[ArticleRead])
def list_articles():
    ...
```

Для Planner используется тот же принцип с его публичной схемой.

### Один item

`GET /tasks/{task_id}` возвращает одну публичную задачу.

Поэтому успешный response описывается одной моделью чтения.

Невалидный path и отсутствующий id продолжают работать по уже установленному договору. Добавление `response_model` не должно превращать существующий `404` в другую операцию и не меняет path.

### Создание

POST принимает данные одной формы, а возвращает другую.

Это главный пример занятия:

```text
POST request
TaskCreate

POST successful response
TaskRead
```

Клиент передаёт:

```json
{
  "title": "HTTP schemas",
  "priority": 4
}
```

а получает после настоящего создания:

```json
{
  "id": 15,
  "title": "HTTP schemas",
  "priority": 4,
  "is_done": false
}
```

`201 Created` остаётся прежним успешным статусом.

Добавление `TaskRead` не должно вернуть POST к `200` и не должно превращать операцию обратно в echo.

### Что не меняется

После подключения схемы ответа по-прежнему верно:

```text
POST
    ↓
TaskCreate
    ↓
PlannerService.add_task
    ↓
Task
    ↓
JsonStorage
    ↓
public projection
    ↓
TaskRead
    ↓
201 response
```

`TaskRead` находится ближе к внешней границе. Она не заменяет середину этого пути.

## 11. OpenAPI показывает направление моделей

Одно из преимуществ явных схем можно увидеть без чтения реализации endpoint.

Откроем `/docs`.

Для POST клиент должен увидеть два разных контракта.

```text
Request body
└── TaskCreate

Successful response: 201
└── TaskRead
```

Это очень важный визуальный результат.

До появления отдельных схем легко мыслить так:

> POST работает с задачей.

OpenAPI заставляет уточнить:

> Что именно клиент отправляет и что именно получает?

### Для GET /tasks

Response должен быть представлен как массив публичных задач.

```text
GET /tasks

200
[
  TaskRead,
  TaskRead,
  ...
]
```

Query-параметры списка при этом не исчезают. Схема ответа не заменяет фильтр, сортировку или `limit`.

### Для GET /tasks/{task_id}

Успешный ответ:

```text
200
TaskRead
```

А `404` остаётся отдельным ошибочным исходом.

### Почему TaskUpdate здесь не должно быть

OpenAPI описывает реальные зарегистрированные операции.

Если PUT ещё не добавлен на этом этапе, отдельная модель полного обновления не должна появляться только ради будущего плана.

Мы не проектируем весь API вперёд. Мы делаем явным уже существующий договор.

### OpenAPI не является доказательством сохранения

Документация может показать правильные схемы, даже если handler внутри реализован неправильно.

Поэтому после просмотра `/docs` всё равно нужны настоящие запросы.

```text
OpenAPI
→ показывает обещанный контракт

реальный POST / GET
→ показывает фактическое поведение

CLI / restart
→ подтверждают сохранение в существующем проекте
```

Схема документации и поведение приложения дополняют друг друга.

## 12. Проверим границы на конкретных сценариях

Перед практикой полезно пройти несколько ситуаций и определить, какая часть системы за них отвечает.

### Сценарий 1. Клиент не передал priority

```json
{
  "title": "Schemas"
}
```

Это проблема request.

`TaskCreate` должна отклонить вход согласно действующему договору. Основная операция создания не должна выполняться.

### Сценарий 2. Клиент передал лишний id

```json
{
  "title": "Schemas",
  "priority": 4,
  "id": 999
}
```

Мы не вводили политику `extra="forbid"`.

Нельзя автоматически требовать `422` только за наличие дополнительного ключа.

Главная гарантия другая: клиентское значение не становится реальным id созданной задачи. Сервер продолжает владеть идентификатором.

### Сценарий 3. Внутренняя Task содержит tags

```text
id=7
title="Schemas"
priority=4
is_done=False
tags=["api"]
```

Клиент получает только четыре публичных поля.

После response нужно проверить, что `tags` не исчез из постоянной записи.

### Сценарий 4. Handler не сформировал обязательный id

Request был корректным, но ответ не соответствует `TaskRead`.

Это проблема сервера, а не входа клиента.

### Сценарий 5. model_dump() вернул правильный словарь

Сам по себе этот факт не говорит, что данные сохранены.

Нужен реальный вызов сервиса и storage-путь.

### Сценарий 6. В Swagger всё выглядит правильно

Это подтверждает OpenAPI-договор, но не доказывает, что после перезапуска задача остаётся в JSON.

Для persistence нужны отдельные наблюдения через существующий проект.

### Самопроверка без подсказки

Попробуйте объяснить одним предложением каждую роль:

- `TaskCreate`;
- `TaskRead`;
- доменная `Task`;
- `JsonStorage`;
- `response_model`;
- `model_dump()`.

**Один вариант разбора.** `TaskCreate` проверяет вход создания. `TaskRead` описывает публичную форму задачи в ответе. Доменная `Task` представляет предметную сущность Planner. `JsonStorage` сохраняет её между запусками. `response_model` задаёт проверяемый HTTP-договор ответа. `model_dump()` только создаёт Python-представление Pydantic-модели и ничего не сохраняет сам.

## 13. Что мы будем делать в практике

Мы не будем заново писать Planner, CRUD или JsonStorage. Работа продолжает действующие маршруты и общий файл проекта.

1. Создадим `app/schemas.py`, перенесём туда прежнюю `TaskCreate` без потери правил и добавим `TaskRead`.
2. Укажем `response_model` у списка, item и настоящего POST. Вход POST останется `TaskCreate`, а успешный ответ сохранит код `201`.
3. Проверим OpenAPI и реальные ответы. Сверим задачу по фактическому id, а полную JSON-запись и CLI проверим отдельно.

В `/docs` должны быть различимы:

```text
POST request  → TaskCreate
POST 201      → TaskRead

GET /tasks    → list[TaskRead]
GET item      → TaskRead
```

Отдельной `TaskUpdate` здесь нет: PUT и PATCH появятся вместе с реальными операциями обновления. Не ожидаем `422` только за лишний ключ, пока не задана отдельная политика extra-полей.

### Когда работа считается завершённой

К концу практики мы можем проследить две разные цепочки:

```text
request:
JSON → TaskCreate → PlannerService
```

и:

```text
response:
Task → public projection → TaskRead → HTTP JSON body
```

При этом:

- CLI продолжает работать;
- `JsonStorage` продолжает хранить прежний формат;
- `tags` не потерян;
- POST остаётся настоящим созданием с `201`;
- GET и POST имеют явные response models;
- OpenAPI показывает реальное направление данных;
- новые схемы не заменяют доменную `Task`.

## 14. Главное из занятия

Мы не создавали новую бизнес-логику. Мы сделали границу API точнее.

`TaskCreate` и `TaskRead` похожи полями, но отвечают на разные вопросы:

```text
TaskCreate:
что клиент может отправить?

TaskRead:
что сервер обещает вернуть?
```

Доменная `Task` отвечает на третий вопрос:

```text
с каким объектом работает сам Planner?
```

А `JsonStorage` отвечает на четвёртый:

```text
что сохраняется между запусками?
```

`response_model` помогает FastAPI проверить, документировать и ограничивать внешний результат. Он не сохраняет данные и не заменяет доменную модель.

`model_dump()` превращает Pydantic-модель в обычные Python-данные, но не создаёт постоянную запись.

Поле `tags` может оставаться внутри `Task` и JSON, даже если его нет в публичном response.

Ошибочный request и ошибочный response находятся по разные стороны handler:

```text
неверный request
→ проблема входа клиента

неверный server result
→ проблема реализации сервера
```

После этого шага HTTP-граница Planner становится явной:

```text
HTTP request
    ↓
TaskCreate
    ↓
PlannerService
    ↓
Task
    ↓
JsonStorage
    ↓
public projection
    ↓
TaskRead
    ↓
HTTP JSON response
```

Следующий шаг курса не будет снова проектировать эти схемы. Мы сможем сосредоточиться на том, как существующий сервис назначает серверные идентификаторы и как доказать, что изменения действительно сохраняются в общем JSON.
