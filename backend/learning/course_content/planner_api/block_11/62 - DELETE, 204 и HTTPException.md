## 00. От изменения к удалению

- **Прежняя опора.** CLI и API создают, читают и обновляют Task через PlannerService и общий JsonStorage.
- **Новый вопрос.** Как подтвердить удаление, если после него серверу нечего возвращать в теле ответа?
- **Результат.** DELETE вызовет готовый сервис, сохранит отсутствие Task и ответит пустым 204.

В предыдущем занятии мы изменяли поля найденной задачи. Теперь меняется её существование в Planner. Удаление уже работает для CLI. Мы добавим только HTTP-маршрут к той же операции и проверим постоянное состояние.

## 01. Удаляем ресурс, а не позицию в списке

Запрос DELETE указывает на конкретную задачу через её id. PlannerService уже умеет найти её, удалить и сохранить оставшиеся Task.

Это важно, потому что id и позиция элемента не совпадают. После удаления список сдвигается, а id соседних задач остаются прежними. API не должен открывать JSON или придумывать отдельный алгоритм. Он передаёт id готовому сервису:

```python
app.state.planner.delete_task(task_id)
```

Это похоже на выдачу книги в библиотеке. Запрос указывает номер книги, а не номер строки на экране. Сервис находит нужную запись и выполняет операцию над ней. Если записи нет, он сообщает об этом через знакомый `TaskNotFoundError`.

**Сравните решения.** Где должен находиться поиск и удаление?

```python
# Вызвать готовую операцию
app.state.planner.delete_task(task_id)

# Или открыть JSON и повторить поиск с удалением в endpoint
```

**Разбор.** Первый вариант сохраняет единый путь данных для CLI и API. Во втором появляется отдельная реализация, которая может забыть правило Planner или изменить файл не так, как CLI.

## 02. Ожидаемое отсутствие и настоящая ошибка

`HTTPException` позволяет endpoint остановить обычное выполнение и вернуть ожидаемый HTTP-статус. Переводить нужно только ошибку, смысл которой известен клиенту.

Если в адресе написан текст вместо целого `task_id`, FastAPI отклоняет path до вызова endpoint и возвращает 422. Если id корректен, но задачи нет, сервис поднимает `TaskNotFoundError`. Endpoint переводит именно это отсутствие в 404. Ошибка чтения или записи JSON не означает, что задачи нет.

Найдите проблему в обработчике:

```python
try:
    app.state.planner.delete_task(task_id)
except Exception:
    raise HTTPException(status_code=404, detail="Task not found")
```

**Разбор.** `except Exception` превращает любую причину в 404. Например, `StorageError` говорит, что приложение не прочитало или не сохранило JSON. Исправьте границу так, чтобы только `TaskNotFoundError` становилась 404. Ошибка storage должна остаться заметной.

Разделите три ситуации:

- **422.** Path не преобразовался в `int`; операция удаления не запускалась.
- **404.** Path корректен, но PlannerService не нашёл такой Task.
- **Сбой storage.** JSON не удалось прочитать или сохранить; это не отсутствие задачи.

## 03. 204 сообщает об успехе без представления

После успешного удаления клиенту не нужна копия уже удалённой задачи. Для этого DELETE отвечает `204 No Content`, то есть «успешно, без содержимого».

У этого статуса нет тела. Маршрут не возвращает `TaskRead`, JSON-объект или `null`. Он возвращает пустой `Response` со статусом 204. Поэтому клиент проверяет статус и не вызывает `json()` для этого ответа.

Ниже фрагмент независимого endpoint для отмены бронирования. Сервисная операция уже существует; фрагмент показывает только HTTP-границу:

```python
@app.delete("/bookings/{booking_id}", status_code=204)
def cancel_booking(booking_id: int):
    try:
        booking_service.cancel(booking_id)
    except BookingNotFoundError:
        raise HTTPException(status_code=404)
    return Response(status_code=204)
```

Декоратор задаёт успешный статус. `Response` возвращает пустое тело. Здесь нет `response_model`, потому что сервер не отправляет представление бронирования.

**Верно или неверно?** После 204 клиент должен разобрать JSON и получить удалённую Task.

**Разбор.** Неверно. У 204 пустое тело. Клиент проверяет статус, а чтобы увидеть текущее состояние, делает отдельный GET.

Ответ 204 сам по себе не доказывает, что данные сохранены. Последующий GET, CLI или новое чтение JSON покажут, исчезла ли запись на самом деле.

## 04. Путь запроса до сохранённого удаления

Операция проходит несколько границ. Поставьте шаги в порядке от запроса до ответа:

1. Запрос `DELETE /tasks/{task_id}` приходит в API.
2. FastAPI преобразует path-параметр и проверяет его тип.
3. `app.state.planner.delete_task(task_id)` удаляет задачу и сохраняет оставшийся список.
4. API возвращает пустой `Response` со статусом 204.

Если сервис поднимает `TaskNotFoundError`, обычный успешный путь прерывается и endpoint возвращает 404. Если JSON не удалось сохранить, нельзя отправлять 204: иначе клиенту сообщат об успехе, которого приложение не подтвердило.

## 05. Повторное обращение не возвращает удалённую запись

Важно проверить не только первый ответ, но и состояние после него.

- **Первый DELETE.** Task существовала. Сервис удаляет её и сохраняет список, API отвечает 204 без тела.
- **Повторный запрос.** Задачи уже нет. Новый GET и DELETE по тому же id получают 404.
- **Постоянное состояние.** Свежий `load` подтверждает отсутствие; остальные задачи и их `tags` остаются на месте.

Статусы первого и повторного DELETE различаются, но эффект сохраняется: ресурса с этим id нет. Повторный запрос не создаёт запись заново и не удаляет соседнюю задачу.

Не создавайте новую задачу между проверками отсутствующего id. Генератор может снова выдать удалённый максимальный id. Тогда GET найдёт уже другую Task, и проверка станет неверной.

## 06. Как доказать, что удаление пережило перезапуск

Сначала выберите фактический id задачи, созданной через POST. После PUT или PATCH удалите именно этот id. Затем проверьте пустое тело ответа, повторный GET и CLI. Перезапустите API или создайте новый PlannerService с тем же настроенным путём, чтобы убедиться, что отсутствие не осталось только в памяти.

```text
до удаления: GET /tasks/{task_id} → TaskRead
DELETE /tasks/{task_id} → 204, тело пустое
после удаления: GET /tasks/{task_id} → 404
повторный DELETE → 404
```

Остальные записи не должны измениться. Статистика пересчитывается по реальному JSON. Удаление открытой Task уменьшает `total` и `open`; удаление завершённой меняет `total` и `done`.

Не вызывайте `json()` для ответа DELETE. Пустое содержимое подтверждает сам ответ, а сохранённые данные проверяются отдельным GET или CLI.

## 07. Что мы будем делать в практике

Подключим готовое удаление к FastAPI и проверим его на задаче из настоящего Planner.

1. Добавим DELETE-маршрут, который вызывает `app.state.planner.delete_task`.
2. Проверим пустой 204 и отдельно ошибки 404 и 422. StorageError не превращаем в 404.
3. Создадим учебную Task через POST, выполним знакомые PUT и PATCH, затем удалим её по выданному id.
4. Сверим GET, CLI, статистику и JSON. Не создадим новую задачу между проверкой 404 и повторным DELETE. Сохраним цепочку запросов в прежней Planner collection.

Практика завершена, когда DELETE существующей Task возвращает пустой 204, а новый `load`, GET и CLI подтверждают её отсутствие. Повторный запрос даёт 404, неверный тип id даёт 422, а остальные задачи и их `tags` сохраняются.

Следующая работа перенесёт готовые маршруты в APIRouter. Она не будет переписывать DELETE или менять его HTTP-контракт.
