# 57. Pydantic-валидация и ошибка 422

## 00. От настоящего POST к точным правилам входа

Предыдущий шаг уже связал запрос с существующим Planner. Теперь посмотрим, что происходит, когда JSON прочитать можно, но значения в нём не подходят приложению.

1. **Точка старта.** Проверенный запрос создаёт `Task` через `PlannerService`, а `JsonStorage` сохраняет её в общем файле.
2. **Новый вопрос.** Как не пропустить неподходящее название или приоритет к действию, не переписывая уже работающий POST?
3. **Результат.** Уточним `TaskCreate`: сначала очистим `title`, затем проверим длину и диапазон `priority`; ошибочный body остановится до endpoint.

Проверка входа похожа на контроль перед посадкой: билет должен быть читаемым, а пассажир и рейс должны соответствовать правилам. Проверка билета ещё не перевозит пассажира. Так же и Pydantic готовит допустимые данные, но сам не создаёт и не сохраняет задачу. Сначала разберём проверки на независимом примере, потом проследим путь Planner.

## 01. JSON можно прочитать, но данные ещё не подходят

JSON-парсер проверяет синтаксис сообщения: например, что объект и строка записаны правильно. Он не знает, какое название подходит Planner. Pydantic получает разобранные значения и строит объект входной модели, если поля и значения соответствуют описанию.

Такой body синтаксически верен:

```json
{
  "title": "   ",
  "priority": 4
}
```

Но после удаления пробелов название окажется пустым. Одного типа `str` недостаточно, чтобы это заметить. Валидация относится к форме и простым ограничениям входа; предметные правила задачи по-прежнему принадлежат модели и сервису Planner.

В FastAPI проверка body происходит до вызова функции endpoint. Поэтому невалидный `TaskCreate` не попадает в обработчик, не вызывает `add_task` и не доходит до сохранения. Эта граница подходит для обязательных полей, типов и простых пределов. Она не переносит туда весь алгоритм проекта. При обычной конфигурации Pydantic выполняет разрешённые преобразования типов: например, строку «4» может разобрать как целое число. Это не отменяет границы priority и не включает строгий режим. Тип задаёт ожидаемую форму значения, Field задаёт предел, а схема соединяет эти правила. Мы не добавляем strict=True без такого требования в договоре.

**Что произойдёт с body без `priority`?**

- Pydantic не сможет построить обязательную входную модель; FastAPI вернёт `422`, endpoint не запустится.
- Planner создаст задачу с приоритетом по умолчанию, потому что любое поле body необязательно.

**Разбор.** Поле без значения по умолчанию обязательно. Обработчик не должен выдумывать `priority`: отказ происходит до его вызова. Так мы отделяем разбор транспортного формата от смысла значения. Успешный разбор JSON ещё не означает, что клиентское значение подходит правилам API.

## 02. Field задаёт границы, но не меняет значение

Аннотация `str` задаёт тип, а `Field` позволяет описать простые допустимые пределы рядом с полем. Для числа используются `ge` («больше или равно») и `le` («меньше или равно»). Для строки `min_length` и `max_length` задают длину. Границы включены.

Рассмотрим независимую форму отзыва:

```python
from pydantic import BaseModel, Field

class SurveyInput(BaseModel):
    comment: str = Field(min_length=2, max_length=80)
    score: int = Field(ge=1, le=5)
```

Допустимый комментарий содержит от 2 до 80 символов, а оценка лежит от 1 до 5. `Field` измеряет переданную строку и не меняет её. Три пробела имеют длину три, поэтому одна проверка `min_length=1` пропустит их. Если важно содержимое, сначала нужна нормализация, затем ограничение. В FastAPI эти ограничения также становятся частью описания body в OpenAPI и Swagger UI. Это помогает увидеть договор запроса, но не проверяет форму на устройстве клиента: решающее отклонение всё равно выполняет сервер. Field и документация не делают title необязательным, потому что у поля нет значения по умолчанию.

Представим линейку и карандаш: `Field` измеряет уже предъявленную длину, но не стирает отметки по краям. Проверка значения и его подготовка решают разные задачи. В Planner мы сперва удалим внешние пробелы, а потом проверим, что итоговый `title` содержит от 1 до 120 символов. `priority` примет целое значение от 1 до 5 включительно.

**Верно ли утверждение?** `Field(min_length=1)` самостоятельно превращает строку из пробелов в пустое значение.

**Разбор.** Это неверно. `Field` проверяет длину текущего значения и не вызывает `strip`. Без отдельной очистки строка из пробелов имеет ненулевую длину.

## 03. Before-validator готовит исходное значение

В Pydantic v2 `field_validator` с режимом `before` получает исходное значение до обычной проверки поля. Мы можем нормализовать строку, а затем отдать результат проверке типа и `Field`. Пример не зависит от Planner: приведём код региона к единой форме.

```python
from pydantic import BaseModel, field_validator

class RegionInput(BaseModel):
    code: str

    @field_validator("code", mode="before")
    @classmethod
    def normalize_code(cls, value: object) -> object:
        if isinstance(value, str):
            return value.strip().upper()
        return value
```

Валидатор принимает `object`, потому что на этапе `before` нельзя заранее считать сырое значение строкой. Проверка `isinstance` разрешает вызвать строковые методы только для строки. Число возвращается без изменений, после чего Pydantic сам сообщает о неверном типе. Так мы избегаем `AttributeError`, который возник бы при безусловном вызове `strip`. Валидатор должен вернуть значение: нормализованную строку или исходный объект для последующей проверки. Он не вызывает PlannerService и не записывает файл. Это сохраняет границу схемы: она готовит вход, а действие начинается позже. Тип object честно показывает, что сырое значение ещё не прошло обычную проверку str.

Проследим значения по шагам:

1. На вход приходит `code = "  nw  "`.
2. Before-validator получает исходную строку и возвращает `"NW"`.
3. Обычная проверка видит результат нормализации и строит `RegionInput`.
4. Если вместо строки пришло `42`, валидатор возвращает число; проверка типа отклоняет его.

Это похоже на сортировочный стол: работник убирает упаковку, но не подменяет содержимое. Следующий контролёр решает, подходит ли предмет по размеру и типу. Сравнение полезно только до этой границы: нормализация и валидация идут последовательно, но выполняют разные обязанности.

## 04. Порядок: нормализовать, затем ограничить

Для `TaskCreate` порядок имеет наблюдаемое значение. Если сначала измерить исходную строку, внешние пробелы увеличат её длину. Если сначала очистить строку, ограничения проверят то название, которое действительно получит Planner.

- `"  API  "` превращается в `"API"` и проходит проверку длины.
- Строка из пробелов превращается в `""` и не проходит `min_length=1`.
- Строка длиннее 120 символов после очистки не проходит `max_length=120`.
- Значение `42` не получает строковый метод; его тип отклоняет Pydantic.

**Найдём ошибку в валидаторе.**

```python
@field_validator("title", mode="before")
@classmethod
def strip_title(cls, value: object) -> object:
    return value.strip()
```

**Почему этот код ненадёжен?**

- `value` может быть числом или другим типом; вызов `strip` тогда завершится `AttributeError`, а не обычной ошибкой проверки.
- `mode="before"` запрещает обращаться к любым методам значения.
- Pydantic автоматически вызовет `strip` ещё раз после этого метода.

**Исправление и причина.** Сначала проверяем `isinstance(value, str)`. Для строки возвращаем `value.strip()`, а прочие значения возвращаем без изменений. Тогда ошибку типа формирует Pydantic. Before-validator подготавливает вход, но не должен скрывать типовую проверку.

У `422` есть два места возникновения. Ошибка построения body случается до функции маршрута: FastAPI сообщает о ней как об ошибке Pydantic, обычно с путём `loc` к `body` и полю. Другая уже знакомая причина появляется внутри endpoint, если существующий сервис отклоняет значение через ожидаемый `ValueError`, а маршрут переводит его в `HTTPException(422)`. Статус одинаков, но этапы разные.

Поэтому мы читаем структуру ответа и проблемное поле, а не запоминаем дословный `msg`: формулировка может зависеть от версии библиотеки. Поле loc помогает отличить пропущенный priority от неверного title: путь может указывать на body и соответствующее имя. Детали msg и type полезны при чтении ответа, но текст msg меняется между версиями библиотек, поэтому проверки не должны закреплять его дословно. Сбой `JsonStorage` не является ошибкой входа и не должен маскироваться под `422` или `404`. Проверка body до endpoint доказывает отсутствие вызова сервиса для этой ошибки; она не обещает откат файла при произвольном сбое записи.

## 05. Planner продолжает создавать настоящую задачу

В практике мы изменим существующую схему `TaskCreate`, а не добавим новую. Её поля останутся `title` и `priority`; `id` и `is_done` сервер создаёт сам. Настройку запрета неизвестных полей мы здесь не добавляем, поэтому не будем ожидать отдельный `422` лишь за лишний ключ. Маршрут передаёт сервису только объявленные поля. TaskCreate защищает HTTP-границу, но не заменяет правила доменной Task. PlannerService может вызываться и через CLI, где эта схема не участвует. Поэтому сервис и модель сохраняют свои проверки, а новая схема добавляет ранний ответ сетевому клиенту. Ограничения API не становятся незаметным изменением командной строки.

Успешный путь остаётся тем же:

```python
@app.post("/tasks", status_code=201)
def create_task(payload: TaskCreate):
    task = app.state.planner.add_task(
        payload.title,
        priority=payload.priority,
    )
    return {
        "id": task.id,
        "title": task.title,
        "priority": task.priority,
        "is_done": task.is_done,
    }
```

Сначала FastAPI строит `TaskCreate`. Если проверка не проходит, endpoint не начинается. Если она проходит, endpoint вызывает знакомый `PlannerService`; тот создаёт доменную `Task` и сохраняет её через общий `JsonStorage`. Затем маршрут возвращает публичные поля с кодом `201`. Ни экземпляр входной схемы, ни его словарь сами по себе не являются сохранённой задачей.

Схема в TSX показывает два выхода: ошибочный вход останавливается до endpoint, а допустимый продолжает прежний путь проекта. Сохранённая запись подтверждается независимым чтением через API и CLI, а не одним ответом POST. При ошибке самой файловой записи мы не заявляем автоматическое восстановление прежнего файла.

После отказа входной схемы существующие задачи, `stats` и рабочий JSON остаются без изменений, потому что `add_task` не вызывался. После успешного запроса берём настоящий `id` из ответа, читаем задачу через `GET /tasks/{task_id}`, сверяем CLI и повторяем чтение после перезапуска API. Так мы проверяем отдельно границу валидации и сохранение результата.

## 06. Что мы будем делать в практике

Теперь применим границы к настоящему POST. Сначала уточним `TaskCreate`, затем отправим допустимые и ошибочные запросы и сравним результат с исходным состоянием Planner.

1. **Настроим вход.** `title` очищается до проверки длины от 1 до 120 символов; `priority` проверяется в пределах от 1 до 5.
2. **Сверим границы.** Проверим обязательность, типы, допустимые края и ошибки `422`, разбирая проблемное поле.
3. **Подтвердим поведение проекта.** Ошибки body не меняют список, `stats` и JSON; успешный POST сохраняет очищенное название, которое читается через API и CLI.

Упражнение продолжает создание из предыдущего занятия и не меняет endpoint, `PlannerService`, `Task`, JSON-формат или публичный ответ. В следующем занятии мы разделим входную схему и схему ответа.
