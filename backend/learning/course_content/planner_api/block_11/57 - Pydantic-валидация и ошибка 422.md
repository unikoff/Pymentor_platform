## Проверка до действия

В предыдущем занятии запрос с корректным `title` и `priority` стал настоящей задачей Planner. Маршрут передаёт данные в `PlannerService`, а сервис сохраняет задачу через общий `JsonStorage`. Но не каждый корректный JSON содержит данные, с которыми приложению стоит работать.

Представьте форму с полем названия. Пользователь может отправить пустую строку, строку из пробелов или текст длиной в несколько страниц. JSON при этом синтаксически верен. Значит, серверу нужно проверить не только форму сообщения, но и допустимые значения до запуска операции.

В этом занятии мы уточним уже существующую входную схему `TaskCreate`. Успешный `POST /tasks` останется настоящим созданием. Новые правила будут отклонять неподходящий вход до вызова маршрута, а не заменят `PlannerService`, модель `Task` или сохранение.

## Синтаксис JSON не равен допустимым данным

JSON-парсер отвечает на вопрос: можно ли прочитать сообщение как JSON? Pydantic отвечает на следующий вопрос: соответствует ли полученное значение объявленной модели?

Например, это синтаксически корректный JSON:

```json
{
  "title": "   ",
  "priority": 4
}
```

Но название состоит только из пробелов. Если передать его дальше, предметная модель всё равно должна отказать. Лучше привести простое правило к входной границе: очистить пробелы по краям и проверить, что после этого осталось допустимое название.

Валидация до endpoint особенно полезна для ошибок формы и простых ограничений: отсутствующего поля, неправильного типа, пустого значения или числа вне диапазона. Она не переносит в Pydantic всю логику Planner. Сервис и `Task` продолжают отвечать за предметные правила и создание задачи.

## Ограничения рядом с полем

Аннотация `str` говорит, что ожидается строка. Она не говорит, насколько длинной может быть строка. Для простых границ Pydantic предоставляет `Field`:

```python
from pydantic import BaseModel, Field


class SurveyInput(BaseModel):
    comment: str = Field(min_length=2, max_length=80)
    score: int = Field(ge=1, le=5)
```

`min_length` и `max_length` задают допустимую длину строки. `ge` означает «больше или равно», а `le` — «меньше или равно». Границы включены: здесь допустимы длина от 2 до 80 символов и оценка от 1 до 5.

Ограничение проверяет значение, которое дошло до этого этапа. Оно не очищает строку и не превращает её в другой тип. Например, строка пробелов длиннее нуля, поэтому одна только проверка `min_length=1` не решает задачу с пустым по смыслу названием.

## Преобразовать, затем проверить

Иногда нужно сначала привести вход к единой форме. В Pydantic v2 для этого подходит `field_validator` с режимом `before`. Он получает исходное значение до обычной проверки поля. Если значение строковое, его можно нормализовать; неподходящий тип нужно оставить Pydantic, чтобы тот выдал понятную ошибку типа, а не случайный `AttributeError`.

Рассмотрим независимый пример: приложение принимает код региона в верхнем регистре.

```python
from pydantic import BaseModel, field_validator


class RegionInput(BaseModel):
    code: str

    @field_validator("code", mode="before")
    @classmethod
    def normalize_code(cls, value: object) -> object:
        if isinstance(value, str):
            return value.strip().upper()
        return value
```

Вход `"  nw  "` превратится в `"NW"` до обычной проверки строки. Число не получит метод `strip`: оно останется исходным значением, и Pydantic сам сообщит, что поле имеет неверный тип.

Порядок важен. Если проверять длину сырой строки раньше нормализации, пробелы по краям могут повлиять на результат. Если нормализовать, а потом проверять `Field`, ограничение применяется к итоговому значению. Это не особенность Planner, а общий способ разделить подготовку входа и проверку его формы.

## Что означает 422

Когда FastAPI связывает body с Pydantic-моделью, валидация выполняется до тела endpoint. Если данные не подходят, обработчик не начинает работу, и FastAPI возвращает `422 Unprocessable Entity` со сведениями об ошибке.

В `detail` обычно есть путь к полю и описание проблемы. Не нужно запоминать английский текст сообщения: он может зависеть от версии Pydantic. Важно уметь определить, где возник отказ и какое правило нарушено.

У 422 есть и другой источник. В предыдущем занятии ожидаемый `ValueError` от `PlannerService.add_task` переводился в HTTP-ошибку маршрутом. Там обработчик уже начал работу и вызвал предметную операцию. В этом занятии ограничения входной схемы отсекают данные раньше. Один статус может описывать разные этапы отказа.

При проверке записывайте статус, поле и причину, но не привязывайте тест к дословной формулировке `msg`. Стабильнее проверить, что `loc` указывает на ожидаемое поле, ответ имеет 422 и никакая задача не была добавлена.

## Проверка входа не создаёт задачу

После успешной проверки FastAPI передаёт в endpoint объект `TaskCreate`. Но объект входной модели ещё не сохранённая `Task`. Его словарь также не является записью в JSON.

В Planner успешный путь остаётся прежним:

```text
JSON body
  → TaskCreate проверяет и подготавливает вход
  → endpoint вызывает PlannerService.add_task
  → Task получает id и начальный статус
  → JsonStorage сохраняет задачу
  → API возвращает созданный ресурс с кодом 201
```

При отказе на первом переходе вызов `add_task` не происходит. Поэтому файл, список задач и статистика остаются такими же, как до ошибочного запроса. Это важное свойство: не только ответ корректен, но и состояние приложения не изменилось.

При успешном запросе мы по-прежнему проверяем весь путь: полученный `id` читается через API, запись видна CLI и остаётся после перезапуска. Так различаются три вещи: проверка входа, предметная операция и сохранение.

## Перед практикой

Мы усилим текущую `TaskCreate` в `app/api.py`, не создавая вторую схему и не переписывая маршрут. Простые границы будут заданы через `Field`, а `title` очистится до проверки своей итоговой длины. Затем мы сравним допустимые края и ошибочные запросы.

Практика заканчивается не на получении 422. Нужно доказать, что ошибочный запрос остановился до изменения Planner, а нормализованное название прошло через существующий `POST /tasks` и сохранилось в общем проекте. Мы не меняем публичный ответ, способ выдачи `id`, модель `Task` или правила CLI.
