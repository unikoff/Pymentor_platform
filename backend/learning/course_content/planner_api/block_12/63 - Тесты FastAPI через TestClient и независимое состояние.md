## 00. От ручной проверки к повторяемому доказательству

В прошлом занятии мы удалили задачу по её ID, получили пустой ответ `204` и отдельно убедились, что сервис больше не находит эту запись. Такой путь можно проверить вручную через Postman, но для каждого изменения заново отправлять одни и те же запросы неудобно. Перед организацией маршрутов мы закрепим уже работающее поведение автоматическими HTTP-тестами.

1. **Точка старта.** Planner API выполняет операции через готовый `PlannerService` и общий JSON; pytest и временные файлы уже знакомы.
2. **Новый вопрос.** Как повторно проверить настоящий FastAPI app, не запуская сервер и не используя рабочие данные?
3. **Результат.** Независимые тесты проверяют статусы, ответы и изменения состояния каждой HTTP-операции.

Сначала отделим проверку HTTP-границы от запуска сервера. Затем свяжем запрос с ответом и явным состоянием теста. Подготовка здесь нужна для следующего шага: когда будем перемещать обработчики, прежние проверки покажут, изменился ли договор.

## 01. TestClient обращается к приложению без запуска Uvicorn

`TestClient` из FastAPI принимает готовый объект приложения. Он отправляет запрос через ASGI-интерфейс внутри процесса Python и получает обычный объект HTTP-ответа. Поэтому в простом тесте не нужны Uvicorn, отдельное окно терминала, открытый TCP-порт или Postman. При этом FastAPI по-прежнему разбирает путь и тело запроса, вызывает зарегистрированный обработчик и формирует ответ. Мы проверяем настоящее приложение на его HTTP-границе, а не вызываем функцию маршрута напрямую.

Для первого опыта создадим маленькое независимое приложение с одним маршрутом. Оно не знает о Planner и показывает только путь от запроса до ответа:

```python
from fastapi import FastAPI
from fastapi.testclient import TestClient

demo_app = FastAPI()

@demo_app.get("/ping")
def ping():
    return {"ready": True}

client = TestClient(demo_app)
response = client.get("/ping")

assert response.status_code == 200
assert response.json() == {"ready": True}
```

Здесь `client.get` проходит через FastAPI, а не вызывает `ping()` как обычную Python-функцию. Мы видим оба слоя результата: статус и JSON. Это похоже на учебную стойку приёма внутри того же здания: запрос проходит через настоящее приложение, хотя курьер не выходит на улицу и не проходит сетевой маршрут. Граница аналогии важна: TestClient помогает проверить маршрутизацию и HTTP-ответ, но не доказывает, что Uvicorn открыл порт или что удалённая сеть доступна.

Когда приложение создаёт TestClient, он не заменяет сам FastAPI app. Это клиентский адаптер к нему. Поэтому передаём именно тот объект, в котором зарегистрированы нужные маршруты; создание нового пустого приложения проверяло бы другой набор операций.

## 02. Ответ содержит несколько проверяемых фактов

Тест не ограничивается утверждением, что запрос не вызвал исключение. В HTTP-ответе отдельно наблюдаем статус, заголовки, тело и, при необходимости, состояние, которое можно прочитать следующим запросом. Для JSON используем `response.json()`. Для ответа без представления смотрим `response.content`: у DELETE со статусом `204` оно пустое, и вызывать `json()` не нужно.

Сценарий обычно строится в трёх частях. В Arrange мы подготавливаем известное состояние. В Act отправляем HTTP-запрос. В Assert проверяем ответ и последствия. Эти части не требуют отдельных функций или специальной библиотеки. Они помогают увидеть, что именно мы доказали. Проверка только `status_code == 200` может пропустить неверный объект в теле; проверка только тела не заметит неправильный статус.

Рассмотрим независимый фрагмент проверки заметки. Это фрагмент теста, в котором приложение и клиент уже подготовлены:

```python
response = client.post("/notes", json={"title": "Draft"})
assert response.status_code == 201
created = response.json()
assert created["title"] == "Draft"
assert client.get(f"/notes/{created['id']}").status_code == 200
```

Параметр `json=` передаёт словарь как JSON-тело, а `params=` задаёт query-параметры URL. В ответе `status_code` описывает HTTP-результат, `json()` разбирает структуру тела, а последующее чтение проверяет, что операция заметна через приложение. ID в примере берётся из фактического ответа. Так тест не угадывает внутренний алгоритм выдачи идентификатора.

Один HTTP-ответ ещё не всегда доказывает сохранение. Обработчик может вернуть объект, который он только что изменил в памяти, тогда как файл останется прежним. Поэтому для операции с состоянием мы читаем ресурс повторно и сравниваем наблюдаемое значение с ожидаемым. Тест остаётся клиентом: он не должен проверять внутренний список напрямую, если публичный маршрут способен показать результат.

## 03. Fixture подготавливает явное состояние

Pytest находит функции, имена которых начинаются с `test_`, и запускает их как обычные Python-вызовы. Fixture описывает повторяемую подготовку и очистку вокруг теста. Знакомый `tmp_path` даёт отдельный временный каталог для каждого теста. Если внутри него создать JSON-файл, два теста не будут читать одну и ту же запись или зависеть от того, какой тест запускался раньше.

В Planner обработчики обращаются к текущему сервису через `app.state.planner`. Это выбранный объект `PlannerService`, а не копия задач. Тестовая fixture может собрать такой сервис прежней точкой `build_service` с `JsonStorage`, направленным на путь внутри `tmp_path`. Перед HTTP-запросами fixture сохраняет прежнее значение `app.state.planner`, временно устанавливает тестовый сервис, а при завершении возвращает прежний объект.

Fixture клиента зависит от fixture сервиса. Pytest сначала готовит сервис, затем открывает `TestClient`; при завершении закрывает клиент и только после этого выполняет восстановление состояния. Для восстановления используем `try/finally`, чтобы прежний сервис вернулся и при обычном завершении, и при ошибке теста. Это важно, потому что один и тот же импортированный `app` может использоваться несколькими тестами подряд.
Pytest связывает fixture и тест по имени параметра: функция с аргументом `client` получает fixture клиента, а клиент запрашивает `planner_service`. Мы не вызываем fixture вручную и не храним TestClient в глобальной переменной модуля. Область `function` используется по умолчанию: завершился тест — завершаются его клиент и сервис, а следующая функция получает отдельный `tmp_path`. Так понятно, кто владеет JSON и когда его состояние перестаёт использоваться. Мы не расширяем срок жизни такого сервиса до `module` или `session`: отдельный файл на функцию позволяет запускать тест самостоятельно, повторно, в любом порядке и без общего изменяемого состояния.

На схеме порядок относится к жизненному циклу одной функции теста. Создание нового клиента само по себе не создаёт новый JSON и не стирает прошлые изменения. Источник изоляции здесь `tmp_path` и новый тестовый сервис, а не визуально новый объект клиента.

```python
@pytest.fixture
def test_service(tmp_path):
    path = tmp_path / "tasks.json"
    return build_service(JsonStorage(path))
```

Это пример настройки пути, а не готовая fixture клиента: в практике мы свяжем сервис с `app.state.planner`, откроем TestClient и вернём прежнее состояние. Конкретные импорты берём из уже существующего проекта, а не создаём вторые модель, сервис или хранилище.

## 04. Один тест сохраняет состояние между своими запросами

Изоляция не означает очистку перед каждым запросом. Если один тест сначала создаёт задачу, затем читает её и проверяет статистику, эти запросы должны работать с одним тестовым JSON. Новый файл нужен следующему тесту, а не следующему запросу. Иначе мы случайно разорвём сценарий на несколько несвязанных состояний и не проверим взаимодействие операций.

Это похоже на отдельный поднос для каждого лабораторного опыта: другой опыт получает чистый поднос, а внутри одного опыта образец остаётся на месте до следующего измерения. Сравнение помогает понять границу, но `tmp_path` не делает файловое хранилище транзакционным и не защищает от параллельных писателей. Здесь мы проверяем последовательные тесты и не меняем ограничения `JsonStorage`.

В тесте неверного POST полезно снять состояние до запроса и снова прочитать его после ответа `422`. Если данные совпали, мы доказали отсутствие частичного эффекта для этого случая. Одного счётчика `total` недостаточно для всех ошибок: значение может остаться прежним, хотя поле существующей задачи уже было изменено. Поэтому рядом с отказом мы сравниваем именно те публичные данные, которые могли пострадать.

Отсутствие ресурса и неверный запрос тоже различаются. Корректный целый ID, которого нет в новом тестовом JSON, приводит к `404`. Текст вместо целого ID или неверная форма входного JSON отклоняется до действия маршрута и приводит к `422`. В сообщениях теста лучше проверять статус и смысловой источник отказа, а не целиком внутренний текст ошибки библиотеки.

## 05. Независимость проверяется порядком запуска

Фиксированные ID допустимы только если тест сам подготовил нужную задачу и получил этот ID. Нельзя рассчитывать на запись, созданную соседней функцией, или на содержимое рабочего `data/tasks.json`. Тест должен выполнять Arrange явно и только затем проверять собственный сценарий. Так мы можем запустить его отдельно, в общем наборе и после другого теста.

Два успешных запуска `pytest -q` подряд подтверждают, что после полного завершения набора файлы снова подготовлены. Они не доказывают, что отдельные тесты независимы в одном процессе: один тест может оставить состояние, которое случайно подходит следующему. Поэтому запускаем выбранные pytest node IDs отдельно, вместе, и меняем их порядок. Каждый тест должен пройти при собственном Arrange.

Свяжем наблюдение с конкретной проверкой:

- `response.status_code` подтверждает выбранный HTTP-статус.
- `response.json()` подтверждает форму JSON-ответа и его значения.
- `response.content` подтверждает, что у ответа `204` нет байтов тела.
- Последующий GET показывает, что изменение видно через внешний договор API.

Fixture закрывает клиент явно через контекстный менеджер или гарантированный teardown. Это завершает используемый TestClient до восстановления выбранного сервиса. Мы не очищаем рабочий файл и не подменяем JSON списком или `MemoryStorage`: проверяется прежняя граница приложения с временным путём.

## 06. Что мы будем делать в практике

Подключим pytest и HTTPX в окружении проекта и будем запускать тесты командой `python -m pytest`. Затем создадим function-scoped fixture сервиса на `tmp_path` и fixture TestClient, которая временно устанавливает тестовый Planner в `app.state.planner` и восстанавливает прежний сервис.

1. **Проверим базовую границу:** health, пустой список и статистику через настоящий FastAPI app.
2. **Проверим изменение:** создадим задачу, сохраним ID ответа и прочитаем её тем же клиентом; отдельно проверим PUT, PATCH с явным `false` и пустой DELETE.
3. **Проверим отказ и независимость:** подтвердим `404` и `422` без порчи данных, затем запустим отдельные тесты, общий набор и иной порядок.

Каждая функция получает собственный JSON, а запросы внутри сценария используют один файл. Это закрепляет текущий договор и подготавливает безопасное перемещение обработчиков в следующий модуль. Ручная проверка через Postman остаётся полезной для запущенного сервера, но автоматический TestClient быстрее повторяет одну и ту же проверку.
