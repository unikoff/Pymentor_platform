# 67. Сквозная приёмка: один ресурс через весь API

## 00. От отдельных гарантий к одной истории

У нас уже есть работающий Planner API и проверки отдельных операций, границ и прикладного ядра. Теперь свяжем эти гарантии во времени и проверим, что одна задача остаётся согласованной от создания до удаления.

1. **Точка старта.** Восемь HTTP-операций используют прежние Task, PlannerService и JsonStorage; базовые тесты и проверки отдельных правил уже существуют.
2. **Новый вопрос.** Сохраняется ли правильное поведение, когда несколько запросов меняют один и тот же ресурс, а между ними происходит отказ?
3. **Результат.** Мы проверим одну задачу сквозным HTTP-сценарием, сравним её с соседней задачей и повторим путь через настоящий сервер.

Начнём не с нового API и не с повторного CRUD. Мы используем то же приложение, те же маршруты и общий источник состояния. Связанность здесь означает, что следующий запрос наблюдает результат предыдущего, а не получает заново подготовленный список.

Сначала разберём примеры на независимой записи бронирования. Затем перенесём способ рассуждения в Planner. Так новый материал объясняет доказательство целого пути, но не подменяет практику готовым тестом.

## 01. Тест операции и сквозной сценарий отвечают на разные вопросы

Тест отдельной операции проверяет локальное правило: например, что обновление сохраняет идентификатор или что ошибочный ввод отклоняется до записи. Такой тест короток и точно указывает на сломанное правило. Он обычно готовит одно состояние и проверяет один результат.

Сквозной сценарий отвечает на другой вопрос: могут ли настоящие HTTP-операции пройти одну историю через то же приложение и один источник данных? Он проверяет не только отдельные ответы, но и переходы между ними. Если POST создал ресурс, последующий GET должен найти его, PUT заменить нужные поля, а PATCH изменить только переданные.

Представим маршрут поездки. Проверка отдельных станций подтверждает, что каждая станция работает. Сквозной тест похож на поездку пассажира от начала до конца: порядок остановок и один билет связывают их в общий путь. Здесь остановки соответствуют запросам, билет соответствует идентификатору ресурса, а порядок запросов сохраняет историю изменения. У аналогии есть граница: тест проходит в изолированном приложении, а не проверяет реальную сеть или доступность сервера по TCP.

Оставим оба вида доказательств. Сквозной тест не заменяет проверки границ из предыдущего занятия и не обязан повторять каждый вариант каждого поля. Он показывает, что проверенные части не потеряли связь при совместной работе.

## 02. Одна история использует одно тестовое состояние

Сквозной тест подготавливает исходную точку один раз и выполняет запросы последовательно. Между запросами одного сценария состояние сохраняется. Поэтому следующая операция получает тот же идентификатор, а список и stats отражают уже накопленные изменения.

В примере с бронированием сервер возвращает идентификатор при создании записи. Следующий запрос использует его для изменения, а чтение после изменения показывает актуальное состояние. Мы не переустанавливаем исходные данные перед каждым запросом: так мы бы превратили одну историю в набор несвязанных эпизодов.

Порядок в независимом примере такой:

1. Создать бронь и получить ответ сервера.
2. Взять идентификатор из этого ответа.
3. Изменить бронь по тому же идентификатору.
4. Прочитать тот же ресурс и проверить новое состояние.

В Planner маршрут главной задачи будет похожим, но со своим HTTP-договором: создание, чтение, полная замена, частичное изменение, удаление и подтверждение отсутствия. Между действиями мы не сбрасываем тестовый файл, не создаём второе приложение и не повторяем CRUD в отдельной функции. Диаграмма показывает именно последовательность действий над одним ресурсом.

## 03. Идентификатор приходит из ответа сервера

Идентификатор создаваемой задачи назначает сервер. Даже если пустое тестовое хранилище сейчас обычно выдаёт первое значение, тест не должен называть его заранее. Такой тест случайно связывает себя с порядком запуска или начальным содержимым и может обращаться не к той записи.

В отдельном примере с каталогом книг мы читаем id из ответа POST и передаём его следующему GET. Это подтверждает не позицию в списке, а адрес именно созданного ресурса. После удаления максимального id может быть использован повторно, поэтому отсутствие проверяем отдельным запросом и не создаём после него новую задачу с предположением об исторической уникальности.

Главная задача не должна быть единственной. Мы создаём ещё одну контрольную задачу и сохраняем оба фактических id. Контрольная запись помогает увидеть, если update или delete случайно затронул соседа. Если проверять только число элементов, потеря одной задачи и случайное добавление другой могут дать то же количество.

## 04. Ответ запроса и новое чтение дают разные доказательства

Статус и body ответа подтверждают, что маршрут вернул обещанную форму. Последующее чтение подтверждает, что изменение доступно следующему запросу. Для POST это отдельный GET созданного id; для PUT и PATCH это GET после обновления. При DELETE успешный ответ имеет статус 204 и пустое тело, поэтому JSON из такого ответа читать не нужно.

Это похоже на чек после покупки. Чек показывает, что касса оформила операцию. Но чтобы подтвердить, что товар появился в заказе, мы отдельно открываем сам заказ. Граница аналогии в том, что HTTP-ответ всё равно остаётся важной частью договора: проверка чтения не заменяет проверку статуса и body.

В изолированном примере две переменные могут показать разные значения:

```python
tasks = [{"id": 4, "title": "Draft"}]
saved_view = tasks[0].copy()
response_body = {"id": 4, "title": "Reviewed"}
print(response_body["title"], saved_view["title"], tasks[0]["title"])
```

Вывод: Reviewed Draft Draft. Это пример работы с обычными словарями, не запуск Planner API. Он показывает, почему одного правдоподобного response body недостаточно, если сервис вернул объект, который не сохранился в общем состоянии.

В тесте мы сопоставляем контракт ответа, новое чтение и наблюдаемое общее состояние. Запрос к списку показывает выбранные записи, а GET /stats считает полный источник независимо от фильтра списка. Эти представления помогают найти расхождение, но не являются отдельными хранилищами.

## 05. Контрольная задача обнаруживает слишком широкое изменение

Для PUT мы отправляем полную схему изменяемых полей, сохраняем прежний id и проверяем целевую задачу повторным чтением. Для PATCH мы передаём только is_done=False. Это значение должно примениться, хотя оно ложное: проверка наличия поля отличается от проверки истинности значения. Название и приоритет при этом остаются прежними.

После каждой важной точки мы проверяем контрольную запись целиком. Сравнение только stats может пропустить замену не той задачи, потерю title или изменение приоритета. Полная запись соседа даёт более точный ответ о побочном эффекте. Сами stats полезны как независимое наблюдение общего состояния: total, open и done должны совпасть с известными переходами.

В независимом примере склада проверка общего количества может не заметить, что заказали не ту коробку. Чтение выбранного заказа и проверка контрольного заказа отвечают на вопрос о конкретных ресурсах. Это не требует создавать новые endpoints: мы используем чтение и stats, уже предусмотренные договором Planner API.

## 06. Ожидаемая ошибка не должна обрывать проверку состояния

Ошибка может быть правильным результатом запроса. Невалидное тело получает 422 до изменения существующей задачи. Корректный запрос к отсутствующему id получает 404. Эти ответы различают неподходящий ввод и отсутствие ресурса. Ошибка программы или хранилища не должна маскироваться под ожидаемый 404.

В середине сценария мы отправляем невалидное частичное изменение и неполный PUT. После каждого отказа повторное чтение должно вернуть ту же полную задачу, список соседа не меняется, а stats остаются прежними. Если проверить только статус 422, тест не заметит частичную запись, произошедшую до ответа.

После отказа сценарий продолжается. Валидный PATCH с false должен сработать, затем DELETE главной задачи должен вернуть пустой 204. Повторное чтение и подходящие запросы к уже отсутствующему id должны дать 404, а контрольная задача должна остаться доступной. Ожидаемый отказ стал частью успешной истории, потому что состояние сохранилось и дальнейшие действия работают.

## 07. TestClient и Postman проходят разные границы

TestClient отправляет запросы приложению напрямую через ASGI-интерфейс. Для такого теста не нужно запускать Uvicorn и открывать TCP-порт. Это надёжная проверка HTTP-маршрутов и взаимодействия с тестовым сервисом, но она не доказывает, что запущенный сервер доступен клиенту через сеть.

В каждом тесте используем знакомую function-scoped fixture с отдельным JsonStorage в tmp_path. Все запросы одного workflow обращаются к одному тестовому файлу, а следующий тест получает чистое состояние. Fixture временно подключает тестовый PlannerService через app.state.planner и восстанавливает прежний сервис после завершения. Клиент закрывается до восстановления. Рабочий data/tasks.json не очищается и не используется автотестом.

Postman проверяет работающий Uvicorn и рабочий JSON, который уже может содержать задачи. Поэтому сначала читаем baseline stats N/O/D, где N это total, O это open, D это done. Затем считаем относительное изменение: два новых открытых элемента дают N+2/O+2/D; перевод главного в done даёт N+2/O+1/D+1; PATCH с false возвращает N+2/O+2/D; удаление главного даёт N+1/O+1/D. Числа исходного файла и идентификаторы заранее не задаём.

## 08. Что мы будем делать в практике

В практике мы добавим связанную проверку к существующему приложению и отдельно повторим наблюдаемый путь через Postman.

1. **Напишем.** tests/test_workflow.py пройдет через настоящее приложение, сохраняя общий тестовый JsonStorage между запросами одного сценария.
2. **Сверим.** Один фактический id пройдет через GET, PUT, PATCH и DELETE; список, stats и контрольная задача подтвердят границы изменений.
3. **Повторим.** Postman пройдет те же операции через работающий сервер, используя baseline рабочего файла и относительные значения stats.

Эта работа дополняет проверки отдельных маршрутов и правил, а не заменяет их. Успехом будет один прослеживаемый HTTP-сценарий с ожидаемыми ответами, сохранёнными данными до отказа и корректным состоянием после каждого перехода.

На следующем шаге мы проверим передачу всего проекта из чистого окружения. Там мы подтвердим запуск по README и воспроизводимость версии; создавать CRUD заново не потребуется.
