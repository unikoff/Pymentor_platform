# Состояния файлов, staging и diff

В предыдущем занятии мы создали локальные коммиты и отправили их на GitHub. Теперь продолжим ту же историю и разберёмся, как выбрать содержимое следующего коммита. Этот шаг пригодится перед каждой записью новой версии.

## 00. От выполненного цикла к выбору версии

В прошлом занятии мы уже разобрали полный цикл: сохранили файл, подготовили содержимое, создали коммит и отправили его. Теперь приблизим один участок этого пути: выясним, почему после новой правки подготовленная версия не обновляется сама и как увидеть обе версии отдельно.

1. **Точка старта:** Мы продолжаем работать с прежним main.py и историей, которую уже видим на GitHub.
2. **Новый вопрос:** Как проверить, какие строки попадут в следующий коммит, а какие останутся только в файле?
3. **Результат:** Мы сравним рабочую и подготовленную версии, безопасно снимем подготовку и запишем проверенные локальные коммиты.

Папку проекта и историю не создаём заново. Базовые роли команд уже знакомы; теперь разберём составные состояния одного файла, проверим две границы сравнения и безопасно снимем подготовку. Следующее занятие отправит локальные коммиты на GitHub.

## 01. Коммит остаётся прежним, пока мы не создадим следующий

Подготовка, или staging, выбирает содержимое для будущего коммита. Когда мы сохраняем файл в редакторе, меняется текст на диске, но уже записанный коммит не переписывается: новая правка становится кандидатом для следующей версии.

Перед коммитом полезно запустить программу и убедиться, что она работает. Но запуск и Git отвечают на разные вопросы: Python показывает поведение программы, а diff, вывод сравнения двух версий, помогает увидеть изменение текста.

Посмотрим на подготовленный фрагмент diff из независимого примера:

~~~diff
-print("Заявка принята")
+print("План сохранён")
~~~

Знак минус отмечает строку предыдущей версии, а плюс показывает новую строку. Это описание различия, а не оценка качества: Git не знает, какую фразу мы хотели написать. Перед коммитом мы проверяем смысл изменения по программе и по задаче.

В полном выводе обычно видны путь к файлу, номера строк и несколько строк вокруг правки. Строки контекста помогают найти место изменения. Заголовок фрагмента вида `@@ ... @@` обозначает диапазоны строк в старой и новой версиях. Это подготовленный пример вывода, а не обещание, что Git запустил программу.

## 02. Три версии одного файла

Чтобы понимать результаты сравнения, различим три места, где находится содержимое:

1. **Последний коммит.** Уже записанный снимок. HEAD указывает на текущий коммит.
2. **Индекс.** Содержимое, подготовленное для следующего коммита. Его также называют staging area, областью подготовки.
3. **Рабочая папка.** Сохранённые на диске файлы, которые мы редактируем и запускаем; в Git её также называют working tree.

Представим три версии текста как редакционные экземпляры. Последний коммит похож на уже выпущенную редакцию. Индекс можно представить как экземпляр, выбранный для следующего выпуска, а рабочую папку как текущую рукопись. Если мы исправим рукопись после подготовки, выбранный вариант сам не обновится. Граница аналогии в том, что Git не создаёт буквальную распечатку или отдельную папку: индекс хранит выбранное содержимое в служебной структуре.

Так проще увидеть назначение двух сравнений. Команда `git diff` сравнит рабочую папку с индексом. Команда `git diff --staged` сравнит индекс с последней записанной редакцией. Оба сравнения могут быть полезны одновременно: они отвечают на разные вопросы о том же файле. Схема в видимой версии занятия показывает эти пары; связи на ней обозначают сравнение, а не перенос содержимого.

## 03. Состояние файла видно в git status --short

Короткий статус показывает два места, где может находиться правка. В каждой строке первая позиция относится к индексу, вторая к рабочей папке. Для читаемости заменим пробел в этих двух позициях на подчёркивание:

~~~text
?? notes.txt
_M main.py
M_ main.py
MM main.py
~~~

- **?? notes.txt:** новый файл ещё не отслеживается Git.
- **_M main.py:** отслеживаемый файл изменён на диске, но не подготовлен.
- **M_ main.py:** изменение подготовлено, более новой правки на диске нет.
- **MM main.py:** содержимое подготовлено, а затем файл снова изменён.
- **!! .venv/:** путь подходит под правило игнорирования; эта строка появляется с флагом `--ignored`.
- **_D old.txt:** ранее отслеживаемый файл удалён из рабочей папки.

Файл может одновременно отличаться от индекса и от последнего коммита. Поэтому статусы не являются четырьмя взаимоисключающими ярлыками. Код показывает, в каком направлении есть различие; для понимания самих строк посмотрим на соответствующий diff.

В записи `_M` отличается только рабочая папка, в `M_` только индекс, а в `MM` обе границы сразу. Метка `??` не означает две правки: так Git отмечает новый путь, которого пока нет в индексе. Чтобы выбрать следующее действие, мы связываем позицию статуса с парой версий на схеме, а не угадываем по слову «изменён».

Если отслеживаемый `main.py` не менялся, `git status --short` не выводит его строку: рабочая папка совпадает с индексом, а индекс с HEAD. Для уже известного файла это чистое состояние; пустой список статуса сам по себе не рассказывает, есть ли в папке игнорируемые или отсутствующие пути.

Сравним три похожие ситуации с учётом в библиотеке. Новая книга, которую ещё не внесли в каталог, похожа на untracked файл, то есть на файл, который Git ещё не отслеживает. Книга, которая лежит отдельно по правилу «не включать в каталог», похожа на файл, подходящий под правило .gitignore. Отсутствующая книга похожа на путь, для которого файла нет на диске. Но Git не библиотекарь: правила ignore сопоставляют пути, а не удаляют файл.

Обычный `git status --short` скрывает игнорируемые пути. Команда `git status --short --ignored` показывает их с отметкой `!!`. Если ранее отслеживаемый файл удалён с диска, status показывает `D` во второй позиции. Путь, которого никогда не было среди отслеживаемых файлов, не появится в выводе. Окружение `.venv` может оставаться на компьютере, хотя Git не предлагает добавить его. Обычный `git diff` не показывает содержимое нового untracked файла, а правило `.gitignore` само по себе не исключает уже отслеживаемый файл из истории.

## 04. git add выбирает содержимое на этот момент

Сначала сохраним нужный текст в редакторе. Затем git add прочитает содержимое файла на диске и подготовит его в индексе:

~~~console
git add main.py
~~~

Команда не создаёт коммит и не отправляет данные на GitHub. Она также не связывает индекс с файлом, который мы будем менять позже. Можно представить это как отправку текущего экземпляра документа на проверку: следующая правка исходного текста не меняет уже отправленный экземпляр. Здесь тоже есть граница аналогии: Git хранит содержимое в индексе, а не создаёт вторую папку с файлом.

Если после git add мы снова сохраним main.py, в индексе останется прежняя подготовленная версия, а новая появится в рабочей папке. Для индекса потребуется ещё один git add. Это нормальная ситуация: так можно отделить две правки и решить, какую записать первой.

## 05. Два diff показывают разные границы

Обычный git diff сравнивает рабочую папку с индексом. Он отвечает на вопрос: что мы изменили на диске после подготовки?

~~~console
git diff -- main.py
~~~

Команда git diff --staged сравнивает индекс с последним коммитом. Она отвечает на вопрос: что обычный git commit запишет сейчас?

~~~console
git diff --staged -- main.py
~~~

Уточнение -- main.py ограничивает просмотр нужным файлом. Сам двойной дефис отделяет параметры команды от пути. Можно убрать путь, чтобы увидеть все подготовленные изменения, но перед конкретной учебной записью удобнее проверить только main.py.

Если мы изменили файл, но ещё не подготовили, обычный diff покажет строки, а staged diff останется пустым. После подготовки, когда новой правки нет, обычный diff для этого файла будет пустым, а staged diff покажет выбранные строки. Пустой вывод означает только то, что на этой границе версии совпали. Он сам по себе не говорит, что правка потеряна или что файл чистый.

Если вывод пустой, сверим git status и второе сравнение. Для нового untracked файла обычного diff тоже недостаточно: сначала нужно подготовить файл, и только тогда Git покажет его содержимое в staged diff.

## 06. Правка после add остаётся в рабочей версии

Проследим один файл по шагам. Сначала подготовим замену знакомого сообщения, а затем добавим и сохраним комментарий:

~~~console
git add main.py
# Добавим комментарий в main.py и сохраним файл
git status --short
git diff --staged -- main.py
git diff -- main.py
~~~

Если после подготовки main.py изменён снова, status покажет MM. Staged diff содержит подготовленную замену относительно HEAD. Обычный diff содержит более поздний комментарий относительно индекса. Вместе эти сравнения показывают обе правки, но не смешивают их.

Если комментарий нужен в том же коммите, ещё раз выполним git add main.py и просмотрим staged diff. После этого в индексе будут и замена, и комментарий. Если хотим оставить комментарий на потом, сохраним его в рабочей папке отдельно. Перед коммитом проверим, что индекс содержит именно выбранный набор строк.

## 07. Снимем подготовку, сохранив файл

Если мы решили убрать подготовленное содержимое из индекса, выполним команду только для отслеживаемого main.py:

~~~console
git restore --staged main.py
~~~

После команды индекс для этого файла вернётся к последнему коммиту. Рабочую папку команда не меняет: и заменённое сообщение, и новый комментарий останутся на диске. Обычный diff теперь покажет обе правки относительно HEAD, а staged diff для файла будет пуст.

Здесь важно оставить флаг --staged и указать нужный путь. Команда git restore main.py без этого флага может заменить рабочую версию содержимым индекса и убрать ещё не записанную правку. Такой опасный вариант нам не нужен. Перед любой командой восстановления мы сначала проверим статус и поймём, какую версию она заменит.

После снятия подготовки прочитаем файл и status. Если решили включить обе правки, повторим git add main.py, снова прочитаем staged diff и только потом создадим коммит. Снятие подготовки и стирание текста являются разными действиями.

## 08. Запишем проверенную версию локально

Перед коммитом запустим main.py и прочитаем git diff --staged -- main.py. В индексе должны быть только выбранные строки. Тогда короткое сообщение к коммиту назовёт реальное изменение:

~~~console
git commit -m "review StudyHub screen"
git log --oneline -3
git rev-parse --short HEAD
~~~

Коммит добавляет в локальную историю снимок подготовленного содержимого. git log показывает новые записи, а сокращённый идентификатор HEAD помогает убедиться, какая версия стала текущей. Если рабочий файл после коммита изменён снова, status покажет это отдельно: более поздняя правка не вошла в уже созданный коммит.

Коммит и отправка на GitHub остаются двумя действиями. Здесь мы сохраняем локальные записи. В следующем занятии проверим адрес удалённого репозитория и отправим выбранную историю.

## 09. Что мы будем делать в практике

Продолжим работу в прежнем studyhub-console. Сохраним знакомый экран, проверим содержимое индекса и запишем две локальные версии.

1. **Проверим исходное состояние:** сверим status и последний коммит, разберём подготовленные строки для untracked, ignored, modified, staged и staged+modified, затем изменим знакомую строку и запустим main.py.
2. **Сравним версии:** подготовим файл, добавим более позднюю правку, прочитаем два diff и снимем подготовку, не теряя текст.
3. **Продолжим историю:** повторно подготовим выбранное содержимое, запустим программу, создадим два осмысленных коммита и посмотрим log.

Если status показывает посторонние изменения, оставим их вне учебной подготовки. Если main.py уже изменён до начала практики, не будем править его поверх этой работы или снимать его с подготовки: сначала отдельно разберём существующее состояние. Так мы продолжаем свою историю и сохраняем чужие или личные изменения нетронутыми.

После коммитов проверим, что знакомый экран запускается, новые записи видны в локальной истории и ни один коммит не отправлен преждевременно. Следующий шаг отдельно займётся публикацией этой истории на GitHub.
