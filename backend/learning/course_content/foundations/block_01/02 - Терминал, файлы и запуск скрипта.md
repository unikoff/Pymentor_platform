# Терминал, репозиторий и первый запуск

Сохраним знакомый экран в файл на компьютере, запустим его Python и проверим первую публикацию.

## 00. От экрана платформы к своему проекту

В прошлом занятии мы написали стартовый экран из трёх строк в платформе. Теперь сохраним его как Python-файл `main.py`, запустим на компьютере и опубликуем первую версию.

1. **Точка старта:** Знакомый экран работает в редакторе платформы.
2. **Новый вопрос:** Как сохранить свой файл и запустить его на компьютере?
3. **Результат:** `main.py` запускается на компьютере, а первая запись версии, коммит, опубликована в GitHub.

Git хранит историю версий проекта. Репозиторием назовём проект вместе с этой историей. GitHub размещает удалённый репозиторий, доступный через сеть. В этом занятии команды публикации выполним по готовой инструкции, а их устройство разберём дальше.

## 01. Разделим роли инструментов

В платформе несколько действий происходят рядом. На компьютере разделим их по ролям. Редактор меняет и сохраняет текст. PowerShell служит командной оболочкой Windows: он принимает команды и запускает программы. Интерпретатор Python читает сохранённый файл `.py` и выполняет его инструкции.

- **Проводник:** Создаёт папки и показывает, какие файлы сохранены.
- **Редактор:** Меняет текст программы и записывает его в файл.
- **PowerShell:** Принимает команды и запускает программы из текущей папки.
- **Python:** Читает выбранный файл и выполняет его инструкции.
- **GitHub:** Хранит удалённый репозиторий проекта, доступный через сеть.

Команду `python main.py` вводим в PowerShell. Строку `print("Привет")` сохраняем в Python-файл. PowerShell запускает интерпретатор с именем файла, а Python читает текст с диска и выполняет его. Если перепутаем места, команда запуска окажется в исходнике или строка Python будет введена как команда PowerShell.

**Сопоставим действие и инструмент.**

- Сохранить текст main.py: Редактор.
- Ввести python main.py: PowerShell.
- Выполнить print: Python.

Редактор записывает файл, PowerShell запускает интерпретатор, а Python выполняет инструкции.

**Где проверим, виден ли Python системе?**

- В PowerShell командой python --version.
- Внутри main.py.
- В адресной строке GitHub.

Ответ: в PowerShell. Версию Python мы проверяем командой терминала. В Python-файл записываем инструкции программы.

## 02. Подготовим Python, редактор и Git

Для локального запуска понадобятся Python и редактор, для публикации нужен Git for Windows. Его Git Credential Manager может открыть браузер для авторизации GitHub и сохранить учётные данные в хранилище Windows Credential Manager. Это не то же самое, что имя и email автора, которые зададим для коммита.

Если Python ещё не установлен, откроем официальную инструкцию для Windows и установим Python Install Manager с python.org или из Microsoft Store. При первом запуске менеджер может предложить установить среду выполнения Python, то есть сам интерпретатор. Затем откроем новое окно PowerShell и проверим команду:

**Проверить Python**

~~~text
python --version
~~~

Ответ с номером версии означает, что команда нашла интерпретатор. Если команда не найдена, вернёмся к инструкции по установке. Выберем один редактор: Visual Studio Code с расширением Python от Microsoft или PyCharm.

Установим Git for Windows и оставим включённым Git Credential Manager. После установки откроем новое окно PowerShell и проверим Git:

**Проверить Git**

~~~text
git --version
~~~

Официальные инструкции: [Python для Windows](https://docs.python.org/3/using/windows.html), [Git for Windows](https://git-scm.com/install/windows) и [вход Git Credential Manager](https://docs.github.com/en/get-started/git-basics/caching-your-github-credentials-in-git). Если инструмент уже работает, используем его установленную версию.

## 03. Создадим репозиторий до файла

В новом проекте подготовим пустой репозиторий GitHub и локальную папку. После первой отправки в удалённой истории появится созданный нами коммит. Файл `main.py` добавим после настройки, чтобы публикация включала именно подготовленные нами файлы.

Войдём в GitHub или зарегистрируемся, если аккаунта ещё нет. Создадим пустой репозиторий `studyhub-console` и выберем видимость, подходящую проекту. README служит кратким описанием проекта, `.gitignore` задаёт правила исключения локальных файлов, а лицензия описывает условия использования. Пока не будем создавать их автоматически: сначала подготовим и отправим свою первую версию. Затем скопируем адрес репозитория.

В Проводнике создадим папку **studyhub-console**. Откроем её как проект в редакторе и запустим PowerShell в этой папке. Команда `Set-Location` меняет текущую папку PowerShell, а `Get-Location` показывает её. Если в пути есть пробелы, заключим полный путь в кавычки:

**Перейти в локальную папку**

~~~text
Set-Location "C:\Users\Anna Smith\Documents\studyhub-console"
Get-Location
~~~

Для нового проекта выполним готовые команды до создания `main.py`. Ветка `main` будет именем первой линии истории. Вместо примеров подставим своё имя и email: Git запишет их как подпись автора, а не как пароль для GitHub. Если личный email скрыт, возьмём noreply-адрес из настроек аккаунта.

**Подготовить новый локальный репозиторий**

~~~text
git init -b main
git config --local user.name "ИМЯ_АВТОРА"
git config --local user.email "EMAIL_АВТОРА"
~~~

Если папка и история проекта уже существуют, не создадим второй проект поверх них. Сначала проверим фактическую папку, ветку и адрес командами `git status`, `git branch --show-current` и `git remote -v`, затем продолжим в той же истории. Значение этих Git-команд разберём дальше.

## 04. Создадим и сохраним main.py

Перенесём знакомый экран в файл с расширением .py. При запуске Python читает сохранённую копию файла.

Представим вкладку редактора как черновик, а сохранённый файл как экземпляр, лежащий в папке проекта. Черновик соответствует несохранённому тексту, экземпляр на диске соответствует версии, которую открывает Python. Граница аналогии: Python не читает содержимое вкладки, он получает текст из файла на диске.

В отдельном примере в редакторе мы изменили сообщение, но ещё не сохранили файл. На диске осталась строка:

**Сохранённое содержимое файла**

~~~python
print("План на завтра")
~~~

Что покажет запуск сохранённого файла?

~~~text
План на завтра
~~~

Подсказка: проследим, где сейчас находится новая версия текста: во вкладке или в файле на диске.

Python покажет `План на завтра`, потому что новая правка осталась в черновике. Сохраним файл и запустим его снова. Если включено автосохранение, сверим путь открытого файла и выбранный интерпретатор, чтобы не запустить другую копию.

Создадим в корне `studyhub-console` файл `main.py`, запишем три знакомые команды и сохраним их в UTF-8. Это способ записать русский текст так, чтобы редактор и Python прочитали одинаковые символы:

**Содержимое main.py**

~~~python
print("StudyHub")
print("Начинаем обучение")
print("Программа запущена")
~~~

Расширение **.py** обозначает исходный файл Python, но не запускает его. Если Проводник скрывает расширения, включим их отображение и проверим полное имя. Иначе файл может называться **main.py.txt**, и команда запуска не найдёт **main.py**.

## 05. Текущая папка задаёт короткий путь

PowerShell ищет короткий адрес `main.py` относительно своей текущей папки. Эту папку также называют рабочей: команды с относительным путём начинают поиск именно от неё. Путь проекта, открытый в редакторе, сам по себе не меняет папку PowerShell.

Представим текущую папку как точку старта на карте. Она соответствует месту, откуда PowerShell разрешает короткий адрес `main.py`; полный путь похож на маршрут от известного начала, а относительный начинается от текущего места. Граница аналогии: рабочую папку хранит окно PowerShell, а не редактор и не сам файл.

Соберём роли инструментов в один путь: редактор сохраняет `main.py`, PowerShell передаёт его имя интерпретатору, а Python читает файл и возвращает вывод в терминал.

`Get-Location` показывает текущую папку, `Get-ChildItem` показывает её содержимое, а `Set-Location` меняет папку. Короткие варианты этих команд в PowerShell: `pwd`, `dir` и `cd`.

Полный путь начинается с диска, например `C:\Users\Anna Smith\Documents\studyhub-console`. Из-за пробела такой адрес в PowerShell заключим в кавычки. Относительный путь `.\studyhub-console` строится от текущей папки `Documents`: точка означает «здесь», а обратная косая черта ведёт во вложенную папку. Перед переходом проверим начальную точку через `Get-Location`, а после него убедимся по списку, что оказались в каталоге проекта.

**Проверим путь и файлы**

~~~text
Get-Location
Get-ChildItem
~~~

В независимом примере предположим, что в папке `weather-board` уже сохранён файл `forecast.py`. Если PowerShell открыт в `Documents`, команда `python forecast.py` ищет файл прямо там и не заглядывает во вложенную папку. Сначала перейдём в `weather-board`, затем запустим сохранённый файл:

~~~text
Set-Location .\weather-board
Get-Location
Get-ChildItem
python forecast.py
~~~

Команды здесь показывают маршрут примера, а не запуск, который мы выполнили в этой среде. В своём проекте применим ту же связь к `studyhub-console/main.py`.

Если список показывает файл `main.py`, запустим его Python-командой:

**Запуск из корня проекта**

~~~text
python main.py
~~~

Разберём случай, когда PowerShell открыт в родительской папке Documents, а файл лежит в **studyhub-console**:

~~~text
Get-Location
Get-ChildItem
Set-Location .\studyhub-console
python main.py
~~~

1. PowerShell открыт в Documents, родительской папке проекта. Проверим это место.
2. В списке видна папка studyhub-console. Сам main.py лежит внутри неё.
3. Переходим в папку проекта. Теперь короткий адрес считается от неё.
4. Python читает сохранённый main.py из текущей папки и выводит три строки.

После перехода команда `python main.py` находит файл. В своей работе укажем фактический путь. Текст приглашения PowerShell вида `PS C:\...` не копируем как часть команды.

## 06. Исправим запуск из другой папки

Сообщение `can't open file` означает, что команда `python` нашла интерпретатор и запустила его, но тот не нашёл файл по указанному пути.

~~~text
PS C:\Users\Anna> python main.py
can't open file 'C:\Users\Anna\main.py': [Errno 2] No such file or directory
~~~

main.py лежит в **Documents\studyhub-console**. Почему запуск не нашёл его?

- PowerShell открыт в другой папке.
- Команде print нужен GitHub.
- Нужно заново создать .venv.

Ответ: PowerShell открыт в другой папке. Короткое имя указывает на текущую папку `C:\Users\Anna`. Перейдём к каталогу, где действительно лежит файл:

~~~text
Set-Location "C:\Users\Anna\Documents\studyhub-console"
Get-ChildItem
python main.py
~~~

Не создадим второй проект и не будем менять код наугад. Сначала проверим путь и список файлов, затем перейдём к существующему main.py и повторим команду.

Команда не найдена, файл не найден и старый вывод указывают на три разные границы. Проверим запуск Python, расположение `main.py` и сохранённое содержимое в таком порядке.

Сопоставим три случая, когда результат не совпал с ожиданием:

- **Команда не найдена:** PowerShell не запустил Python; проверим установку и откроем новое окно после настройки.
- **Неправильная папка:** Короткий адрес указывает на текущий каталог, в котором нет main.py.
- **Несохранённая правка:** Файл найден, но на диске осталось прежнее содержимое; сохраним вкладку и повторим запуск.

Начнём с видимых признаков: путь терминала, список файлов и текст сохранённой версии. Так мы исправим причину, не пересоздавая проект.

## 07. Выберем Python проекта

Папка `.venv` служит виртуальным окружением проекта: внутри неё находятся отдельный интерпретатор Python и его библиотеки. Сейчас дополнительных библиотек не нужно, но это окружение даст проекту собственное место для них по мере развития. Сам `main.py` остаётся рядом с `.venv`, а не внутри неё.

Представим `.venv` как ящик с инструментами одного проекта. Ящику соответствуют интерпретатор и его библиотеки; файл `main.py` остаётся на рабочем столе рядом. Граница аналогии: окружение не хранит код проекта, не сохраняет правки и не заменяет Git.

Создадим окружение один раз из корня проекта:

**Создать окружение**

~~~text
python -m venv .venv
~~~

В первой команде уже доступный Python запускает модуль `venv` и создаёт папку `.venv`. Во второй мы указываем исполняемый файл Python внутри неё и передаём ему имя того же `main.py`:

**Запустить Python из .venv**

~~~text
.\.venv\Scripts\python.exe --version
.\.venv\Scripts\python.exe main.py
~~~

В Visual Studio Code выберем Python: Select Interpreter и укажем `.venv\Scripts\python.exe` текущего проекта. В PyCharm выберем тот же путь в настройках Python Interpreter. Кнопка редактора и команда PowerShell должны запускать один Python.

Активация позволяет писать короткую команду **python** в текущем терминале, но она не обязательна. Если PowerShell блокирует **Activate.ps1**, не будем менять системную политику ради урока: запустим интерпретатор по полному пути.

**Вспомним:** Нужно ли создавать .venv снова после открытия PowerShell?

Ответ: нет. Окружение уже хранится в папке проекта. Выберем его Python в редакторе или вызовем его прямым путём.

Эту локальную папку позже исключим из отправки в GitHub. Файл **.gitignore** задаст нужное правило.

## 08. Опубликуем проект по готовым командам

Локальный экран уже запускается через Python проекта. Теперь создадим `.gitignore`, добавим файлы и выполним команды первого коммита и отправки как готовую последовательность. Подробно разбирать устройство истории будем дальше.

В корне проекта создадим файл `.gitignore` с правилами для окружения и служебных файлов Python:

**Содержимое .gitignore**

~~~text
.venv/
__pycache__/
*.pyc
~~~

Правило `.venv/` указывает папку окружения, `__pycache__/` указывает папку кэша. В `*.pyc` звёздочка заменяет любое начало имени, поэтому правило подходит к файлам с окончанием `.pyc`. `.gitignore` не удаляет их с компьютера, а помогает Git пропускать совпавшие неотслеживаемые файлы. Сам файл правил мы добавим в репозиторий.

Выполним следующие строки по одной из корня проекта. Здесь `git add` готовит выбранные файлы, `git commit` создаёт локальную запись, а `git push` отправляет её на GitHub. Полную механику этих действий разберём в следующем занятии.

**Записать первый коммит**

~~~text
git status
git add main.py .gitignore
git commit -m "start StudyHub project"
~~~

Для нового подключения заменим пример целиком на скопированный адрес своего репозитория. Имя `origin` станет коротким обозначением этого адреса. Затем отправим ветку `main`:

**Подключить GitHub и отправить**

~~~text
git remote add origin https://github.com/OWNER/studyhub-console.git
git push -u origin main
~~~

Когда GitHub впервые запросит вход для отправки, Git Credential Manager может открыть браузер. Войдём в нужный аккаунт, подтвердим доступ приложения и второй фактор, если он включён. Вернёмся в PowerShell и дождёмся завершения отправки. Если вход уже сохранён, новое окно может не появиться. Не вставляем пароль или токен в команду.

Если мы продолжаем существующий проект, не добавим origin повторно. Проверим его фактический адрес, сохраним текущую ветку и подставим её имя вместо main, если оно отличается. Если экран и .gitignore уже закоммичены и изменений нет, не создадим пустой коммит.

При отказе отправки прочитаем сообщение, проверим адрес и доступ к репозиторию, затем повторим только `push`. Не будем вставлять пароль или токен в команду.

## 09. Проверим опубликованные файлы

Подтвердим, что GitHub получил нужный коммит. Успешный вход и ссылка на репозиторий ещё не показывают, какие файлы отправлены.

Команда `git rev-parse HEAD` печатает полный идентификатор текущего локального коммита. Сверим его с записью на GitHub, затем откроем свой репозиторий и ту ветку, которую отправляли:

**Идентификатор коммита**

~~~text
git rev-parse HEAD
~~~

1. Откроем последний коммит в выбранной ветке и сравним полный идентификатор с результатом команды.
2. Откроем main.py и .gitignore и сравним содержимое с локальными файлами.
3. Убедимся, что .venv не опубликована, но осталась на компьютере.

Если появилась ошибка **remote origin already exists**, проверим сохранённый адрес и пропустим повторное подключение. Если репозиторий не найден или доступ отклонён, сверим адрес и аккаунт с правом записи. После исправления причины повторим отправку.

Различим три результата: Python запустил файл, Git создал локальную запись, GitHub получил её. Один факт не подтверждает два других. После сверки вернёмся к локальному запуску и убедимся, что знакомый экран по-прежнему выводится из `main.py`.

## 10. Что мы будем делать в практике

Продолжим путь от стартового экрана до проекта, который запускается на компьютере и опубликован в репозитории GitHub.

1. **Подготовим:** Python, Git и пустой репозиторий готовы, локальная папка открыта в редакторе и PowerShell.
2. **Перенесём и запустим:** Сохранённый `main.py` выводит знакомый экран, а PowerShell находит его из корня проекта.
3. **Выберем окружение:** `main.py` запускается через Python из `.venv`, выбранный и в редакторе.
4. **Опубликуем и сверим:** На GitHub видны `main.py`, `.gitignore` и коммит с тем же идентификатором, а `.venv` остаётся на компьютере.
