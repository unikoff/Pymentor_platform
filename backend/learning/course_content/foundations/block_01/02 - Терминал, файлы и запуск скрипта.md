# Терминал, репозиторий и первый запуск

Перенесём знакомый экран в файл на компьютере, запустим его Python проекта и опубликуем первую версию в своём репозитории.

## 00. От экрана платформы к своему проекту

В прошлом занятии мы написали стартовый экран из трёх строк в платформе. Теперь сохраним его на компьютере, запустим через Python и проверим первую публикацию.

1. **Точка старта:** Знакомый экран работает в редакторе платформы.
2. **Новый вопрос:** Как сохранить свой файл и запустить его на компьютере?
3. **Результат:** **main.py** работает через Python проекта, а первый коммит виден в своём репозитории GitHub.

Разберём четыре роли: редактор сохраняет файл, PowerShell передаёт имя файла, Python выполняет код, а GitHub показывает опубликованный результат. Git-команды пока выполним по готовой инструкции и разберём в следующем занятии.

## 01. Разделим роли инструментов

В платформе несколько действий происходят рядом. На компьютере удобно различать инструмент, который редактирует файл, и программу, которая его запускает.

- **Проводник:** Создаёт папки и показывает, какие файлы сохранены.
- **Редактор:** Меняет текст программы и записывает его в файл.
- **PowerShell:** Принимает команды и запускает программы из текущей папки.
- **Python:** Читает выбранный файл и выполняет его инструкции.

Команду **python main.py** вводим в PowerShell. Строку **print("Привет")** записываем в файл Python. Терминал передаёт Python имя файла, а интерпретатор выполняет код. Если мы перепутаем места, команда запуска окажется в исходнике или строка Python будет введена как команда PowerShell.

**Сопоставим действие и инструмент.**

- Сохранить текст main.py: Редактор.
- Ввести python main.py: PowerShell.
- Выполнить print: Python.

Редактор записывает файл, PowerShell запускает интерпретатор, а Python выполняет инструкции.

**Где проверим, виден ли Python системе?**

- В PowerShell командой python --version.
- Внутри main.py.
- В адресной строке GitHub.

Ответ: в PowerShell. Версию Python мы проверяем командой терминала. В Python-файл записываем инструкции программы.

## 02. Подготовим Python, редактор и Git

Для локального запуска нам понадобятся Python и редактор. Для первой публикации добавим Git for Windows с Git Credential Manager.

Если Python ещё не установлен, откроем официальную инструкцию для Windows и установим Python Install Manager с python.org или из Microsoft Store. Если менеджер предложит установить среду выполнения Python, завершим этот шаг. Затем откроем новое окно PowerShell и проверим команду:

**Проверить Python**

~~~text
python --version
~~~

Ответ с номером версии означает, что команда нашла интерпретатор. Если команда не найдена, вернёмся к инструкции по установке. Выберем один редактор: VS Code с расширением Python от Microsoft или PyCharm.

Установим Git for Windows и оставим включённым Git Credential Manager. После установки откроем новое окно PowerShell и проверим Git:

**Проверить Git**

~~~text
git --version
~~~

Официальные инструкции: [Python для Windows](https://docs.python.org/3/using/windows.html), [Git for Windows](https://git-scm.com/install/windows) и [вход Git Credential Manager](https://docs.github.com/en/get-started/git-basics/caching-your-github-credentials-in-git). Если инструмент уже работает, используем его установленную версию.

## 03. Создадим репозиторий до файла

Сначала подготовим пустое место для публикации и локальную папку проекта. Файл main.py создадим после этой настройки.

Войдём в GitHub или зарегистрируемся, если аккаунта ещё нет. Создадим пустой репозиторий **studyhub-console** и выберем видимость, подходящую проекту. Оставим выключенными создание README, .gitignore и лицензии, затем скопируем HTTPS-адрес репозитория.

В Проводнике создадим папку **studyhub-console**. Откроем её как проект в редакторе и запустим PowerShell в этой папке. Если в пути есть пробелы, заключим полный путь в кавычки:

**Перейти в локальную папку**

~~~text
Set-Location "C:\Users\Anna Smith\Documents\studyhub-console"
Get-Location
~~~

Для нового проекта выполним готовые команды до создания main.py. Вместо примеров подставим своё имя и email. Эти значения станут подписью автора, а не паролем для GitHub. Если личный email скрыт, возьмём noreply-адрес из настроек аккаунта.

**Подготовить новый локальный репозиторий**

~~~text
git init -b main
git config --local user.name "ИМЯ_АВТОРА"
git config --local user.email "EMAIL_АВТОРА"
~~~

Если папка и история проекта уже существуют, не создадим новый проект поверх них. Сначала проверим фактическую папку, ветку и адрес командами **git status**, **git branch --show-current** и **git remote -v**, затем продолжим в той же истории. Значение Git-команд разберём дальше.

## 04. Создадим и сохраним main.py

Перенесём знакомый экран в файл с расширением .py. При запуске Python читает сохранённую копию файла.

Представим открытую вкладку редактора как рабочий лист. Пока мы не сохранили правку, новый текст остаётся только на этом листе. Файл на диске похож на закреплённую копию, которую Python может открыть и выполнить.

Например, в редакторе мы уже набрали **print("Новый экран")**, но сохранённый main.py пока содержит такую строку:

**Сохранённое содержимое файла**

~~~python
print("Старый экран")
~~~

Что покажет запуск?

~~~text
Старый экран
~~~

Подсказка: решим, какой текст прочитает команда запуска: из несохранённой вкладки или из файла на диске.

Python покажет сохранённое сообщение. Сохраним файл и повторим запуск, чтобы увидеть новую версию. Если включено автосохранение, сверим путь открытого файла и выбранный интерпретатор.

Создадим в корне **studyhub-console** файл **main.py**, запишем три знакомые команды и сохраним его в UTF-8:

**Содержимое main.py**

~~~python
print("StudyHub")
print("Начинаем обучение")
print("Программа запущена")
~~~

Расширение **.py** обозначает исходный файл Python, но не запускает его. Если Проводник скрывает расширения, включим их отображение и проверим полное имя. Иначе файл может называться **main.py.txt**, и команда запуска не найдёт **main.py**.

## 05. Текущая папка задаёт короткий путь

PowerShell ищет короткий адрес main.py относительно своей текущей папки. Открытая вкладка редактора не меняет это место.

Представим текущую папку как точку, откуда мы начинаем маршрут. Короткий адрес **main.py** означает «файл с таким именем здесь». Полный путь указывает весь маршрут от диска, а короткий зависит от точки старта.

**Get-Location** показывает текущую папку, **Get-ChildItem** показывает её содержимое, а **Set-Location** меняет папку. Короткие варианты этих команд в PowerShell: **pwd**, **dir** и **cd**.

Полный путь начинается с диска, например **C:\Users\Anna Smith\Documents\studyhub-console**. Из-за пробела такой адрес в PowerShell заключим в кавычки. Относительный путь **.\studyhub-console** строится от текущей папки Documents: точка означает «здесь», а обратная косая черта ведёт во вложенную папку. Перед переходом проверим начальную точку через **Get-Location**, а после него убедимся по списку, что оказались в каталоге проекта.

**Проверим путь и файлы**

~~~text
Get-Location
Get-ChildItem
~~~

Если список показывает файл main.py, запустим его Python-командой:

**Запуск из корня проекта**

~~~text
python main.py
~~~

Разберём случай, когда PowerShell открыт в родительской папке Documents, а файл лежит в **studyhub-console**:

~~~text
Get-Location
Get-ChildItem
Set-Location .\studyhub-console
python main.py
~~~

1. PowerShell открыт в Documents, родительской папке проекта. Проверим это место.
2. В списке видна папка studyhub-console. Сам main.py лежит внутри неё.
3. Переходим в папку проекта. Теперь короткий адрес считается от неё.
4. Python читает сохранённый main.py из текущей папки и выводит три строки.

После перехода команда **python main.py** находит файл. В своей работе мы укажем фактический путь. Текст приглашения PowerShell вида **PS C:\...** не копируем как часть команды.

## 06. Исправим запуск из другой папки

Сообщение «can't open file» означает, что Python запустился, но не нашёл файл по указанному пути.

~~~text
PS C:\Users\Anna> python main.py
can't open file 'C:\Users\Anna\main.py': [Errno 2] No such file or directory
~~~

main.py лежит в **Documents\studyhub-console**. Почему запуск не нашёл его?

- PowerShell открыт в другой папке.
- Команде print нужен GitHub.
- Нужно заново создать .venv.

Ответ: PowerShell открыт в другой папке. Короткое имя указывает на текущую папку Anna. Перейдём к каталогу, где действительно лежит файл:

~~~text
Set-Location "C:\Users\Anna\Documents\studyhub-console"
Get-ChildItem
python main.py
~~~

Не создадим второй проект и не будем менять код наугад. Сначала проверим путь и список файлов, затем перейдём к существующему main.py и повторим команду.

Если PowerShell не находит команду **python**, проверим установку Python и откроем новое окно терминала. Если Python сообщает, что не нашёл **main.py**, проверим текущую папку и полное имя файла. Эти сообщения указывают на разные причины.

При неправильной папке Python выдаёт «can't open file», потому что не находит запрошенный адрес. При несохранённой правке файл найден и команда завершается, но в выводе остаётся старый текст. Сначала проверим путь и список файлов, затем сверим содержимое **main.py** с открытой вкладкой и сохраним её. Эта последовательность отделяет проблему адреса от версии кода.

Сопоставим два случая, когда результат не совпал с ожиданием:

- **Неправильная папка:** Короткий адрес указывает на текущий каталог, в котором нет main.py.
- **Несохранённая правка:** Файл найден, но на диске осталось прежнее содержимое; сохраним вкладку и повторим запуск.

Начнём с видимых признаков: путь терминала, список файлов и текст сохранённой версии. Так мы исправим причину, не пересоздавая проект.

## 07. Выберем Python проекта

Окружение .venv содержит отдельный Python и библиотеки одного проекта. Оно не переносит исходный файл и не заменяет редактор.

Представим **.venv** как отдельный ящик с инструментами для проекта. Нужные ему библиотеки лежат отдельно от библиотек других проектов. Сам **main.py** остаётся в корне папки, а Python окружения находится внутри **.venv**.

Создадим окружение один раз из корня проекта:

**Создать окружение**

~~~text
python -m venv .venv
~~~

В этой команде установленный Python запускает модуль **venv**, который создаёт папку окружения с именем **.venv**. Затем вызовем интерпретатор из этой папки и передадим ему тот же файл:

**Запустить Python из .venv**

~~~text
.\.venv\Scripts\python.exe --version
.\.venv\Scripts\python.exe main.py
~~~

В VS Code выберем Python: Select Interpreter и укажем **.venv\Scripts\python.exe** текущего проекта. В PyCharm выберем тот же путь в настройках Python Interpreter. Кнопка редактора и команда PowerShell должны запускать один Python.

Активация позволяет писать короткую команду **python** в текущем терминале, но она не обязательна. Если PowerShell блокирует **Activate.ps1**, не будем менять системную политику ради урока: запустим интерпретатор по полному пути.

**Вспомним:** Нужно ли создавать .venv снова после открытия PowerShell?

Ответ: нет. Окружение уже хранится в папке проекта. Выберем его Python в редакторе или вызовем его прямым путём.

Эту локальную папку позже исключим из отправки в GitHub. Файл **.gitignore** задаст нужное правило.

## 08. Опубликуем проект по готовым командам

Локальный экран уже запускается. Теперь создадим .gitignore и выполним последовательность Git-команд, не разбирая пока устройство истории.

В корне проекта создадим файл **.gitignore** с правилами для окружения и служебных файлов Python:

**Содержимое .gitignore**

~~~text
.venv/
__pycache__/
*.pyc
~~~

Выполним следующие строки по одной из корня проекта. Назначение команд разберём в следующем занятии.

**Записать первый коммит**

~~~text
git status
git add main.py .gitignore
git commit -m "start StudyHub project"
~~~

Для нового подключения заменим пример целиком на скопированный HTTPS-адрес своего репозитория и отправим ветку main:

**Подключить GitHub и отправить**

~~~text
git remote add origin https://github.com/OWNER/studyhub-console.git
git push -u origin main
~~~

При первом push Git Credential Manager может предложить Sign in with your browser. Войдём в нужный аккаунт GitHub, подтвердим доступ приложения и второй фактор, если он включён. Вернёмся в PowerShell и дождёмся завершения отправки. Если вход сохранён, новое окно может не появиться.

Если мы продолжаем существующий проект, не добавим origin повторно. Проверим его фактический адрес, сохраним текущую ветку и подставим её имя вместо main, если оно отличается. Если экран и .gitignore уже закоммичены и изменений нет, не создадим пустой коммит.

При отказе отправки прочитаем сообщение, проверим адрес и доступ к репозиторию, затем повторим только push. Не будем вставлять пароль или токен в команду.

## 09. Проверим опубликованные файлы

Подтвердим, что GitHub получил нужный коммит. Успешный вход и ссылка на репозиторий ещё не показывают, какие файлы отправлены.

Получим полный идентификатор последнего локального коммита, затем откроем на GitHub свой репозиторий и отправленную ветку:

**Идентификатор коммита**

~~~text
git rev-parse HEAD
~~~

1. Откроем последний коммит в выбранной ветке и сравним полный ID с результатом команды.
2. Откроем main.py и .gitignore и сравним содержимое с локальными файлами.
3. Убедимся, что .venv не опубликована, но осталась на компьютере.

Если появилась ошибка **remote origin already exists**, проверим сохранённый адрес и пропустим повторное подключение. Если репозиторий не найден или доступ отклонён, сверим HTTPS-адрес и аккаунт с правом записи. После исправления причины повторим отправку.

Различим три отдельных результата: Python запустил файл, Git создал коммит, GitHub получил эту версию. Один факт не подтверждает два других.

## 10. Что мы будем делать в практике

Продолжим путь от стартового экрана до проекта, который запускается на компьютере и проверяется в репозитории GitHub.

1. **Подготовим:** Проверим Python и Git, создадим локальную папку и пустой репозиторий.
2. **Перенесём и запустим:** Сохраним экран в main.py и проверим путь от PowerShell до файла.
3. **Выберем окружение:** Создадим .venv и запустим тот же файл её Python.
4. **Опубликуем и сверим:** По готовым командам отправим main.py и .gitignore, затем сравним файлы и ID коммита в браузере.

Будем работать в одном проекте и сохраним его фактическую папку, ветку и историю, если проект уже существует. Подтвердим запуск и опубликованный коммит, а устройство Git-команд разберём дальше.

Откроем практику: перенесём экран в main.py, запустим его через .venv и проверим первую публикацию.
