# Git и GitHub: разберём первую публикацию

В прошлом занятии мы уже создали репозиторий, запустили `main.py` и отправили первую версию на GitHub. Теперь разберём каждое звено этого пути и повторим его на знакомом файле, чтобы следующий коммит продолжил тот же проект.

## 00. От первой публикации к следующей версии

1. **Точка старта:** У нас есть `main.py`, `.venv`, `.gitignore`, локальный и опубликованный коммит, ветка `main`, настроенный `origin` и выполненный вход.
2. **Новый вопрос:** Почему сохранённый файл, коммит и версия на GitHub могут различаться?
3. **Результат:** Мы объясняем прежние команды и самостоятельно публикуем проверенную правку в той же истории.

Сравнение двух состояний поможет понять, где остановилось изменение. Мы проследим одну знакомую строку: от файла на компьютере до записи в локальной истории и её копии на GitHub. Новую папку и новый репозиторий для этого не создаём.

## 01. Что именно мы создали

**Git** работает с файлами проекта и их историей на нашем компьютере. **GitHub** хранит удалённую копию истории, которую мы отправили. **Python** запускает `main.py`; Git не исполняет Python-код и не подтверждает, что программа работает.

Репозиторием называют проект вместе с историей Git. В прошлом занятии на сайте мы создали пустой удалённый репозиторий, а в папке проекта запустили `git init -b main`. Команда `init` создала служебную папку `.git`. В ней Git хранит свою историю и настройки. Флаг `-b main` задал имя начальной ветки.

Ветка `main` не является папкой с отдельной копией файлов. Это имя текущей ветки в истории. Такое же имя может быть на GitHub, но локальная и удалённая ветки меняются отдельными действиями. Поэтому локальный `init` не отправил `main.py`, а пустой проект на GitHub не получил файлы автоматически.

**Аналогия с двумя тетрадями.** Локальный репозиторий похож на нашу рабочую тетрадь с закреплёнными версиями, а репозиторий GitHub на отдельную тетрадь в хранилище. `git init` заводит первую тетрадь в папке проекта, но не переносит её во вторую. Граница аналогии: Git хранит связанные снимки файлов и служебные данные, а не страницы с рукописным текстом.

~~~text
studyhub-console/
├── .git/       история и настройки Git на компьютере
├── .gitignore  правила для будущей подготовки файлов
├── main.py     исходный код программы
└── .venv/      локальное окружение Python
~~~

**Проверим вывод:** папка содержит `.git` и `main.py`, но на GitHub их пока нет. Что мы узнали?

1. Создан локальный репозиторий
2. Файлы уже опубликованы
3. Python-код проверен Git

Ответ: **1**. Папка `.git` подтверждает наличие локального репозитория. Публикацию и запуск проверяют отдельно.

## 02. Подпись автора не даёт доступ

В первом коммите мы задали имя и email автора. Git записал эти значения в сведения о коммите. Настройка `--local` относится только к текущему репозиторию: соседний проект может иметь другую подпись.

~~~text
git config --local user.name "ИМЯ_АВТОРА"
git config --local user.email "EMAIL_АВТОРА"
~~~

Во время отправки Git Credential Manager открыл вход через браузер. Он подтвердил учётную запись и доступ к GitHub. Это отдельное действие: имя автора не является паролем, а вход через браузер не меняет подпись в уже созданном коммите. Git может записать локальный коммит без интернета; отправить его на сайт без сети нельзя.

Сопоставим три настройки. Имя и email попадут в подпись коммита. Браузерный вход разрешает обратиться к нужному репозиторию. Выбранный в редакторе Python запускает файл. Эти настройки отвечают на разные вопросы.

**Проверим различие:** что должно измениться, если на GitHub виден чужой проект, хотя локальный коммит создался?

- Подпись автора
- Адрес удалённого репозитория
- Версия Python

Ответ: **адрес удалённого репозитория**. Локальный коммит возможен без GitHub, а отправка зависит от настроенного адреса и прав доступа. Для входа GitHub использует отдельный Credential Manager.

## 03. Почему `.venv` не отправилась

Файл `.gitignore` содержит образцы путей, которые Git не должен предлагать для добавления, пока он их ещё не отслеживает. В нашем проекте есть такие правила:

~~~text
.venv/
__pycache__/
*.pyc
~~~

Первое правило подходит к папке `.venv`, второе к папкам кэша Python, а звёздочка в `*.pyc` заменяет любую последовательность символов в имени файла. Например, правило подходит к `main.pyc` и `cache.pyc`. `.gitignore` сам остаётся обычным файлом проекта и входит в коммит.

Игнорирование не удаляет файл с компьютера. Поэтому локальный Python из `.venv` продолжает запускать программу, хотя окружение не отправлено на GitHub. Если файл уже попал в историю, одно добавление правила не прекращает его отслеживание. Это важно отличать от случая, когда правило заранее исключило ещё не добавленный файл.

**Вспомним:** отсутствие `.venv` на GitHub означает, что локальная `.venv` удалена?

Ответ: **нет**. Правило исключает окружение из последующей подготовки, а не удаляет папку с компьютера. При получении проекта в другой папке окружение создаётся заново.

## 04. Между файлом и историей есть подготовка

Когда мы сохраняем файл в редакторе, на диске появляется его новая версия. Git не записывает каждое сохранение в историю. Сначала мы выбираем содержимое для следующего коммита.

1. **Рабочий файл:** то, что сейчас сохранено на диске.
2. **Индекс:** подготовленное содержимое, которое команда `git add` выбрала для будущего коммита.
3. **История:** уже записанные коммиты, которые видны через `git log`.

**Аналогия с рабочим столом.** Изменённый файл лежит на столе, через `git add` мы кладём выбранный снимок в лоток, а `git commit` подшивает содержимое лотка в журнал версий. Стол соответствует рабочим файлам, лоток соответствует индексу, журнал соответствует истории. Граница аналогии: лоток не обновляется сам. После новой правки нужно снова выбрать актуальный снимок.

Посмотрим на отдельный учебный файл `banner.py`, который печатает название чайной и часы работы. В прежней версии вторая строка была «Скоро открытие», теперь мы сохранили вариант «Открыто».

~~~python
print("Чайная")
print("Открыто")
~~~

Прочитаем текущую правку, выберем её для следующей записи, проверим выбор и создадим коммит.

~~~text
git status
git diff -- banner.py
git add banner.py
git diff --staged -- banner.py
git commit -m "change opening message"
~~~

Разберём этапы. `git status` перечисляет изменённые и новые файлы и показывает различия между рабочей папкой, индексом и последним коммитом. До добавления обычный `git diff` показывает строки, изменённые на диске. Команда `git add banner.py` помещает в индекс содержимое этого файла на данный момент. Команда `git diff --staged` сравнивает подготовленную версию с последним коммитом. `git commit` создаёт новую запись из подготовленного содержимого.

**Пройдём последовательность:** какой шаг проверяет выбранную версию перед записью?

1. `git diff --staged`
2. `git init -b main`
3. `git remote -v`

Ответ: **1**. До коммита staged diff показывает, какие подготовленные строки попадут в запись. Он не сообщает, отправлена ли версия на GitHub.

Если после `git add` сохранить ещё одну правку, в индексе останется предыдущий снимок, а рабочий файл уже будет другим. Чтобы новая строка тоже попала в коммит, сначала сверим обычный и staged diff, затем снова выполним `git add`.

**Верно или неверно:** после `git add banner.py` любые будущие изменения этого файла сразу оказываются в индексе.

Ответ: **неверно**. Git подготовил содержимое только на момент команды. Новая сохранённая правка остаётся рабочим изменением, и её нужно добавить ещё раз.

## 05. Как `status` и `diff` показывают изменения

В сокращённом статусе `M` означает изменённый файл, а две позиции показывают, где именно есть различие. Например, пробел и `M` говорят о правке в рабочей папке; `M` и пробел говорят о подготовленной правке. Если подготовить файл, затем отредактировать его ещё раз, обе позиции могут быть заняты.

Команда `git diff -- banner.py` сравнивает рабочую версию с индексом. Команда `git diff --staged -- banner.py` сравнивает индекс с последним коммитом. Так мы задаём Git два разных вопроса: что изменилось после подготовки и что именно будет записано сейчас.

В строках diff минус показывает прежний текст, плюс новый. Эти знаки обозначают направление изменения, но не качество программы. Путь файла над строками помогает проверить, что мы читаем нужный `main.py`, а не случайно созданную копию. Новый файл может показываться как `??`: обычный diff не раскроет его содержимое, пока Git не знает о нём через подготовку.

**Разберём короткий случай:** после `git add` обычный diff пуст, а staged diff показывает новую строку. Какая версия подготовлена?

- Изменение потерялось
- Изменение выбрано для коммита
- GitHub уже обновлён

Ответ: **изменение выбрано для коммита**. Обычное сравнение пусто, потому что рабочий файл и индекс совпадают. На GitHub запись появится после commit и push.

## 06. Коммит сохраняет подготовленную версию

Команда `git commit -m "change opening message"` записывает подготовленное содержимое в локальную историю. Флаг `-m` добавляет короткое сообщение о цели изменения. Git не запускает Python, поэтому перед коммитом мы сами проверяем вывод программы и строки diff.

Команда `git log --oneline -2` показывает последние записи: короткий идентификатор и сообщение. `git rev-parse HEAD` выводит полный идентификатор текущего коммита. `HEAD` указывает на выбранную текущую версию истории. Если рабочее состояние чистое, у Git нет незаписанных различий среди отслеживаемых файлов. Это не означает, что программа запустилась без ошибки или что GitHub получил запись.

Коммит удобно представлять как снимок проекта, а не архив только новых строк. Подготовленная версия содержит выбранные изменения, а отслеживаемые файлы без правок сохраняют прежнее содержимое. Поэтому короткий diff может вести к новой версии всего проекта. Каждый новый коммит связан с предыдущим. `git log` показывает порядок записей, `HEAD` указывает на текущую точку. Идентификатор отличает коммиты, а сообщение объясняет замысел; совпадение сообщений не доказывает совпадение содержимого.

Расположим действия для учебной правки: сохранить файл и проверить запуск; посмотреть статус и рабочий diff; выполнить `git add`; проверить staged diff; создать коммит. Такая последовательность сначала проверяет файл, затем содержимое записи и только после этого добавляет новую версию в историю.

## 07. Как коммит попадает на GitHub

Чтобы отправить историю, проект хранит адрес удалённого репозитория. Его короткое имя часто бывает `origin`. Команда `git remote -v` показывает адреса, а `git branch --show-current` сообщает имя локальной ветки. Перед отправкой мы убеждаемся, что открыт прежний проект и выбран правильный адрес.

**Аналогия с отправкой посылки.** Локальные коммиты похожи на уже запечатанные посылки в нашем отделении, а GitHub на указанное хранилище. Команда `git push` передаёт туда ещё не отправленные коммиты выбранной ветки. Граница аналогии: рабочая правка без коммита ещё не запечатана, поэтому push не может отправить её как новую запись.

При первой настройке `git push -u origin main` отправил ветку `main` и запомнил её удалённую связь, которую называют upstream. Для последующих отправок этой ветки обычно достаточно `git push`. В нашем занятии адрес и связь уже настроены, поэтому повторный `git init` или `git remote add origin` не нужен.

1. **Сохранение:** новый текст находится в файле на диске.
2. **Commit:** выбранное содержимое записано в локальную историю.
3. **Push:** новые коммиты переданы на GitHub.

**Проверим прогноз:** коммит уже виден в локальном `git log`, статус чистый, но на GitHub прежний текст. Какого звена не хватает?

1. Отправки коммита через `git push`
2. Повторного `git init`
3. Повторного создания `.venv`

Ответ: **1**. Локальная версия уже записана, но публикация ещё не подтверждена. Чистый статус относится к локальным файлам, а не к удалённому репозиторию.

## 08. Как доказать, что версия опубликована

После push проверим не только ответ терминала. Сначала сверим адрес владельца и имя репозитория с `git remote -v`, затем откроем на GitHub ту же ветку, куда отправляли коммит. Для продолжения чужую ветку или репозиторий по похожему названию не выбираем.

Сравним полный ID последнего коммита из GitHub с `git rev-parse HEAD`. Совпадение означает, что на сайте доступна та же запись истории. Затем откроем `main.py` внутри этого коммита и проверим изменённую строку. Один знакомый текст не заменяет совпадение идентификаторов: похожая строка могла быть в другой версии или ветке.

**Вспомним:** браузерный вход успешно завершился. Это уже доказательство, что новая версия опубликована?

Ответ: **нет**. Вход подтверждает доступ учётной записи. Отдельно проверим выбранный репозиторий, ветку, идентификатор коммита и сам файл на GitHub.

## 09. Найдём место, где остановился путь

Если новое сообщение есть в сохранённом файле, но не появилось на сайте, проверим этапы по порядку. Сначала `git status` и `git diff`, затем наличие staged diff и нового коммита. Если нового коммита нет, `git push` отправлять пока нечего. Если коммит есть, сравним текущую ветку и remote, после отправки проверим GitHub.

**Найдём пропуск:** рабочий `banner.py` изменён, а `git push` отвечает `Everything up-to-date`. Что нужно сделать до отправки?

1. Подготовить правку и записать коммит
2. Создать второй репозиторий
3. Установить Python повторно

Ответ: **1**. Push передаёт существующие коммиты, а не сохранённые строки напрямую. После подготовки и локальной записи мы сможем отправить новую версию. На следующем шаге отдельно разберём сочетания состояний после повторного изменения и способы безопасно снять подготовку.

Ошибки пути, подписи и адреса дают разные подсказки: `not a git repository` просит проверить папку; `Author identity unknown` просит проверить имя и email; `remote origin already exists` означает, что адрес уже записан. Если сервер отказал в доступе, сверим адрес и выполненный вход. Детальную диагностику remote и авторизации продолжим в отдельном занятии.

## 10. Что мы будем делать в практике

Мы объясним первую публикацию по данным настоящего проекта и самостоятельно продолжим его историю.

1. **Разберём первую запись:** посмотрим историю, подпись, текущую ветку, `origin` и правила `.gitignore`, затем назовём роль прежних команд.
2. **Проверим новую правку:** изменим одну знакомую строку в том же `main.py`, запустим проект, подготовим файл и прочитаем рабочий и staged diff.
3. **Подтвердим публикацию:** создадим следующий коммит, убедимся, что GitHub пока показывает прежнюю версию, отправим правку и сравним ID вместе с содержимым файла.

Исходная папка, первый коммит, ветка и адрес репозитория сохраняются. После публикации повторно запустим программу и проверим знакомый экран. Новую возможность Planner пока не добавляем: практика оставляет проверенную версию того же проекта и объяснение уже выполненных команд.
