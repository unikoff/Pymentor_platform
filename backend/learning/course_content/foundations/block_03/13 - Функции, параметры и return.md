# Функции, параметры и return

В прошлых занятиях мы описали полную задачу словарём и собрали несколько таких записей в список. Теперь дадим имя повторяемому действию: передадим ему одну задачу и получим готовую строку для показа.

## 00. От данных к именованному действию

Мы умеем читать поля записи по ключам, проверять значения и обходить список. Пока повторяемое правило приходится писать там, где оно понадобилось. Как отделить его от остального сценария, не теряя входные данные и результат?

- **Точка старта.** Полная задача хранит `id`, `title`, `priority` и `is_done`. Список хранит несколько таких словарей.
- **Новый вопрос.** Как назвать преобразование одной задачи и передать его результат коду, который покажет строку?
- **Результат.** Мы определим и вызовем `format_task(task)`, получим строку через `return` и выведем её снаружи функции.

Функция здесь станет небольшим инструментом с понятным входом и выходом. Мы не будем собирать всё меню приложения.
Полезно сравнить определение с рецептом. Имя функции похоже на название рецепта, параметры на места для входных данных, аргументы на выбранные продукты, а вызов на приготовление одной порции. Рецепт можно прочитать, но блюдо не появится, пока мы не начнём готовить; так и тело после `def` ждёт вызова. Граница сравнения в том, что функция исполняет точные инструкции Python и может вернуть программный результат через `return`.

## 01. Определение не запускает тело

Ключевое слово `def` определяет функцию: связывает имя с набором инструкций. Python читает заголовок и тело, но выполняет тело только при вызове функции.

~~~python
def greet(name):
    return f"Привет, {name}!"

message = greet("Анна")
print(message)
~~~

Разделение видно по шагам:

1. Строки с `def` создают функцию с именем `greet`.
2. Двоеточие начинает тело, а отступ показывает, какие строки в него входят.
3. Вызов `greet("Анна")` запускает тело. Значение `"Анна"` попадает внутрь.
4. `return` передаёт строку из функции вызывающему коду.
5. Переменная `message` получает строку, а `print` показывает её.

Вызов всегда записывается со скобками. Функция без входных значений тоже вызывается со скобками:

~~~python
def app_name():
    return "Planner"

label = app_name()
print(label)
~~~

Без скобок `app_name` обозначает саму функцию. Со скобками `app_name()` запускается её тело. Пример выводит `Planner`.
Имя функции отделяет правило от места, где мы его применяем. Одна функция может получить разные аргументы в нескольких вызовах; если правило изменится, мы поправим одно определение, а не несколько похожих копий. Функция при этом остаётся частью того же файла и выполняется только тогда, когда управление доходит до вызова. В примере `greet` не хранит историю: каждый вызов возвращает новую строку для своего значения `name`.

**Предскажем, что выполнится:**

~~~python
def announce(value):
    print(value)

announce
announce("Готово")
~~~

При одном определении ничего не печатается. Строка `announce` без скобок тоже не запускает тело. Только `announce("Готово")` вызывает функцию и печатает текст.

## 02. Параметр принимает аргумент

Параметр задаёт имя входного значения в определении. Аргумент передаёт конкретное значение при вызове.

~~~python
def subtract(total, completed):
    return total - completed

left = subtract(10, 3)
print(left)
~~~

В определении `total` и `completed` являются параметрами. В вызове числа `10` и `3` являются аргументами. Поскольку вызов позиционный, Python сопоставляет их слева направо:

1. `total` получает `10`.
2. `completed` получает `3`.

Если переставить аргументы, значения попадут в другие параметры. Python не угадывает их смысл по содержимому.

- `total` в `def subtract(total, completed)` это параметр.
- `10` в `subtract(10, 3)` это аргумент.
- `subtract(10, 3)` это вызов функции.
- `left =` перед вызовом сохраняет результат.

Число аргументов должно соответствовать числу обязательных параметров. Если обязательного значения не хватает, Python сообщит `TypeError` при вызове, до выполнения тела.

~~~python
def task_label(title, priority):
    return f"{title}: {priority}"

task_label("SQL")
~~~

Здесь параметр `priority` не получил аргумент. Исправим только вызов:

~~~python
task_label("SQL", 3)
~~~

Теперь у каждого параметра есть значение. В практике мы сначала проверим эту механику на коротком примере, а затем передадим функции полный словарь задачи.
Параметры дают телу функции понятные имена для значений, полученных в конкретном вызове. Снаружи тела имя `total` не появится само: программа продолжает работать с именами вызывающей стороны и с тем, что вызов вернул. Аргументом может быть готовое значение или выражение; пока для нас достаточно чисел, строк и одного полного словаря.

## 03. return возвращает значение, print показывает его человеку

Вызов передаёт управление в тело. Когда Python встречает `return`, текущий вызов заканчивается и возвращает значение в место вызова. Остальная программа продолжает работу оттуда.

~~~python
def double_minutes(minutes):
    return minutes * 2

result = double_minutes(25)
print(result)
~~~

Функция вернула число `50`. Оно сохранилось в `result`, поэтому его можно использовать в следующем выражении.

`return` и `print` решают разные задачи. `return` передаёт значение программе. `print` показывает его человеку, но сам по себе не возвращает его вызывающему коду.
Представим табло для человека и записку, которую мы передаём следующей части программы. `print` выводит число на табло: мы видим его в терминале, но вызов не получает это число как результат. `return` передаёт значение прямо в место вызова, где мы можем присвоить его переменной или передать дальше. Граница аналогии: возврат не сохраняет значение сам и не печатает его; он завершает только текущий вызов, после чего выполнение продолжается снаружи.

~~~python
def show_minutes(minutes):
    print(minutes)

result = show_minutes(25)
print(result)
~~~

Вывод будет таким:

~~~text
25
None
~~~

Первое число напечатала функция. Так как в ней не было `return` с результатом, вызов вернул `None`, то есть отсутствие полезного возвращённого значения. В нашем formatter печать будет снаружи, чтобы строку можно было сохранить или использовать дальше.

Параметры и переменные вроде `left` существуют внутри текущего вызова. Снаружи мы можем использовать только значение, которое функция явно вернула и которое вызывающий код сохранил, например, в `result`.

`return` завершает текущий вызов функции. `break` завершает текущий цикл. Эти команды управляют разными конструкциями.

**Найдём причину ошибки:**

~~~python
def calculate_left(total, completed):
    left = total - completed
    print(left)

result = calculate_left(10, 4)
print(result * 2)
~~~

Человек увидит число `6`, но затем умножение завершится `TypeError`. Переменная `result` получила `None`, потому что функция ничего не вернула. Исправление начинается с возвращения вычисленного значения, а вывод остаётся в вызывающем коде.
В опыте с `show_minutes(25)` сначала появится `25`, а затем вызов вернёт `None`; второй `print` покажет именно его. `None` не всегда означает ошибку: это честный результат функции, у которой нет полезного возвращаемого значения. Нашему formatter, напротив, по контракту нужна строка, поэтому одного вывода на экран недостаточно.

Когда Python выполняет `return`, он не переходит к следующей строке тела этой функции. Текущий вызов заканчивается, значение приходит к месту вызова, и уже вызывающий код продолжает следующую строку. Поэтому `return` не завершает меню или всё приложение. Для цикла у нас есть отдельный `break`, который ведёт за его границу.

Схема вызова помогает увидеть две стороны одной границы: вызывающий код передаёт словарь в `format_task`, а возвращённая строка приходит обратно к месту вызова. Внешний `print(message)` остаётся отдельным действием вызывающего сценария.

## 04. Форматируем полную задачу

Параметр может получить уже знакомый словарь, а не только строку или число. Тогда функция читает нужные значения по ключам модели.

~~~python
def task_title(task):
    return task["title"]

task = {
    "id": 10,
    "title": "Изучить SQL",
    "priority": 3,
    "is_done": False,
}
title = task_title(task)
print(title)
~~~

Вывод: `Изучить SQL`. Словарь передан целиком, а функция прочитала из него поле по ключу.
Этот независимый пример отделяет механику функции от большого форматирования: один словарь входит как один аргумент, функция возвращает одно поле, а вызывающий код сохраняет его и решает, что делать дальше. В постоянном formatter вход тот же, но результат собирается из четырёх полей.

В вызове `task_title(task)` весь словарь передан одним аргументом. Внутри функции параметр `task` даёт доступ к полям записи.

В этом занятии мы зададим formatter один полный договор. Он принимает словарь с четырьмя уже известными ключами и возвращает строку следующей формы:

~~~text
[10] Изучить SQL | приоритет: 3 | открыта
~~~

Каждая часть строки берётся из поля записи:

- `id` задаёт номер в квадратных скобках. Это идентификатор задачи, не её позиция в списке.
- `title` задаёт название.
- `priority` задаёт число после подписи «приоритет».
- `is_done` задаёт понятное человеку состояние: `False` превращается в «открыта», а `True` в «выполнена».
Идентификатор `id` не меняется от перестановки записи в списке; позиция отвечает только за её текущее место. Поэтому в строку включаем именно значение `task['id']`. Приоритет остаётся числом в данных и становится частью текста только при построении результата.

Мы уже знаем `if` и `else`, поэтому выберем текст состояния обычным ветвлением. Не добавляем в модель ключ `status`: состояние для показа вычисляется из существующего `is_done`.

Функция форматирования только читает словарь и возвращает строку. Она не меняет поля и не вызывает `print`. После определения formatter вызывающий код может сохранить результат `format_task(task)` в `message` и показать его через `print(message)`. Это фрагмент вызывающего кода, а не второе определение функции. Весь вход приходит в параметре `task`:

~~~python
message = format_task(task)
print(message)
~~~

Эти две строки показывают границу ответственности: formatter готовит значение, а внешний сценарий управляет выводом. Функция не должна зависеть от скрытой глобальной переменной `title`.
Так выглядит граница ответственности: полный словарь приходит на вход, одна строка возвращается наружу, исходные поля остаются прежними. Formatter не создаёт ключ состояния, не решает, куда сохранять задачу, и не выводит текст. Эти действия останутся у уже существующего сценария.

**Проверим контракт на разных записях.** Мы используем задачи с разными id, заголовками, приоритетами 1 и 5, а также обоими значениями `is_done`. После вызова перечитаем исходный словарь: все четыре поля должны остаться прежними. Если в строке появился индекс элемента списка или словарь изменился, formatter нарушил договор.

## 05. Проверяем функцию в прежнем проекте

Постоянное определение функции размещается в уже существующем `main.py` до командного сценария. Мы добавляем одну функцию для нового правила. Цикл команд, калькулятор и команда выхода остаются частью прежней программы.

Чтобы отдельно проверить определение из файла, запускаем Python в интерактивном режиме после выполнения скрипта. Флаг `-i` оставляет интерпретатор открытым, когда сценарий штатно завершился:

~~~text
python -i main.py
~~~

Сначала приложение покажет своё меню. Вводим прежнюю команду выхода. После завершения файла появится приглашение `>>>`. Теперь мы уже вводим Python-код, а не команду терминала:

~~~python
sample = {"id": 42, "title": "Повторить Python", "priority": 1, "is_done": True}
format_task(sample)
format_task({"id": 7, "title": "Сохранить заметки", "priority": 5, "is_done": False})
exit()
~~~

Интерактивная оболочка показывает результат последнего выражения. Два вызова проверяют разные записи без добавления учебных данных в рабочий код. Команда запуска вводится в терминале, вызов функции и `exit()` вводятся после приглашения `>>>`.
С флагом `-i` Python выполняет файл и затем оставляет тот же процесс открытым. Определённые в `main.py` имена остаются доступны после штатного выхода из меню, поэтому мы можем вызвать `format_task` в приглашении оболочки. При обычном запуске процесс завершился бы сразу после сценария. Временные словари создаём уже после `>>>`, не записывая их в рабочий файл.

Здесь встречаются два разных выхода. Сначала команда `exit` обрабатывается старым циклом приложения и выводит нас к приглашению `>>>`. После проверок вызов `exit()` завершает уже интерактивную оболочку Python. Если перепутать терминал и приглашение, синтаксически верную команду можно ввести не в тот режим.

Платформа проверяет то же предметное правило через адаптер `solve(task)`. Адаптер уже вызывает единственную функцию `format_task(task)`; мы не создаём второй formatter с другой моделью.

Следующее занятие 13.1 продолжит маршрут: мы проследим локальные значения и результаты нескольких вызовов и отдельно исследуем изменение переданного объекта. Здесь нам достаточно первого понятного вызова без скрытых зависимостей.

## 06. Что мы будем делать в практике

1. **Предскажем:** почему определение функции не запускает её тело, и вызовем короткую функцию с разными аргументами.
2. **Сопоставим:** параметр и аргумент, затем исправим вызов, которому не хватает значения.
3. **Реализуем:** один предметный formatter `format_task(task)` для полной модели задачи. Вернём строку, а не будем печатать её из функции.
4. **Проверим:** открытые и выполненные задачи, приоритеты 1 и 5, точный `id` и неизменность исходного словаря.
5. **Перенесём:** ту же функцию в прежний `main.py` перед командным сценарием. После штатной команды выхода проверим два вызова через `python -i main.py`, не меняя работу калькулятора и выхода.

Отдельные редакторские опыты помогают понять вызовы, параметры и результат до проверки полной модели. Затем редакторское задание проверяет контракт formatter, а ручная часть переносит ту же функцию в прежний проект.

Мы подтвердим результат несколькими значениями и сохраним старые команды без нового меню или тестовых данных в файле.
