# Декомпозиция и чистые функции

В прежнем проекте уже есть рабочие команды calc и exit, список длительностей одной сессии и функции для модели задачи. Теперь распределим обязанности по понятным функциям, не меняя поведение приложения и не запрещая осознанные изменения данных.

**Темы:** декомпозиция по ответственности · контракт функции · композиция · чистый результат и видимый эффект

## 00. Продолжаем работающий calc

В предыдущем занятии мы добавили в main.py функции create_task и format_task. В блоке 2 уже появился калькулятор: команда calc собирает длительности, считает итог с одним перерывом и показывает результат. Список durations относится к одному запуску расчёта.

- **Точка старта.** Мы умеем вызывать функцию, использовать её результат и отличать его от вывода. Переданный словарь может оставаться общим объектом.
- **Новый вопрос.** Как соединить знакомые правила так, чтобы каждое отвечало за одну понятную часть, а прежние calc и exit продолжали работать?
- **Результат.** В main.py появятся normalize_title и calculate_study_minutes, а прежний calc будет использовать их. На подготовленных значениях мы отдельно соединим существующие create_task и format_task.

Мы не создаём новое меню задач, не назначаем следующий id автоматически и не переписываем уже работающие функции. Задача занятия состоит в том, чтобы выделить правила из существующего сценария и проверить, что границы функций понятны.

## 01. Декомпозиция начинается с ответственности

Декомпозиция означает, что мы делим действие на части с отдельным смыслом. Мы не создаём функцию для каждой строки. Сначала находим разные причины изменить код: ввод, очистка значения, проверка правила, вычисление, создание записи, изменение списка и вывод.

Например, calc получает название и числа, обходит список durations, складывает длительности, один раз добавляет перерыв, вычисляет часы и остаток, затем показывает результат. Ввод относится к сценарию приложения, сумма является правилом расчёта, а показ результата остаётся рядом с тем местом, где приложение общается с человеком.

Представим кухню кафе: один человек принимает заказ, другой готовит блюдо, третий подаёт его. Координатор задаёт порядок и передаёт результат между этапами, но не превращает каждое движение повара в отдельную роль. Так и в calc: отдельное правило получает имя, а сценарий соединяет шаги. Код не догадывается о передаваемых данных, поэтому входы функции мы указываем явно.

Разметим ту же работу по границам:

- **Получить значения:** сценарий читает название и длительности через input.
- **Очистить название:** отдельное правило возвращает строку без пробелов по краям.
- **Посчитать минуты:** функция получает список и возвращает сумму, не меняя его.
- **Добавить перерыв:** calc использует сумму и один раз применяет прежнее правило.
- **Показать итог:** сценарий переводит минуты в часы и выводит готовые значения.

### Сравним границы

**Вопрос:** почему не стоит объединять ввод, подсчёт и печать в одной функции без описания её договора?

**Вариант A.** По вызову неясно, откуда придут данные, что функция вернёт и какое состояние она изменит.

**Вариант B.** Назначение каждой части можно назвать и проверить отдельно, а управляющий сценарий показывает порядок действий.

**Вывод:** вариант B помогает менять и проверять правила по отдельности. Само количество функций не является целью.

### Расположим работу calc

Поставим этапы в порядке выполнения:

1. Получить название и длительности в текущем calc.
2. Очистить только края названия.
3. Посчитать учебные минуты по сохранённому списку.
4. Один раз добавить перерыв и вычислить часы с остатком.
5. Показать готовые значения.

Интерактивная оболочка программы остаётся владельцем input и print. Функция вычисления получает уже собранный список как аргумент.

## 02. Контракт объясняет одну функцию

Контракт функции описывает, что она принимает, что возвращает и что меняет. Он также называет границы, которые должны быть допустимы.

- **normalize_title(title):** принимает строку, возвращает результат strip(); не читает ввод, не меняет регистр и не решает, принимать ли пустое название.
- **calculate_study_minutes(durations):** принимает список минут и возвращает сумму; не меняет список, не добавляет перерыв и ничего не печатает.
- **create_task(task_id, title, priority):** получает назначенные и проверенные значения, возвращает полный словарь; не выбирает id, не читает ввод и не добавляет запись в список.
- **format_task(task):** получает полную задачу, возвращает строку; не меняет словарь и не печатает.

Контракт похож на карточку заказа в мастерской: в ней записано, что мы передаём и какой результат хотим получить. Если функция меняет общий объект, это тоже часть обещания. Но карточка не управляет работой мастера: Python не сверяет тело функции с контрактом автоматически, поэтому обещание нужно подтвердить вызовами.

Функция normalize_title вызывает strip() и возвращает очищенную строку. Пробельная строка после очистки остаётся пустой. Функция не должна подменять её выдуманным названием. Если приложению нельзя принять пустое название, вызывающий сценарий проверяет результат и решает, что показать.

```python
raw_title = "  SQL и README  "
clean_title = raw_title.strip()
print(clean_title)
```

Регистр внутри названия сохраняется. Например, SQL и README не должны неожиданно превращаться в Sql и Readme. Метод title() меняет регистр слов, а в нашем проекте такой обязанности у нормализации нет.

Когда функция получает аргумент, мы можем проверить её на конкретной строке без диалога с терминалом. Если она сама вызывает input, её работа зависит от скрытого источника данных. А print показывает значение человеку, но не передаёт напечатанную строку вызывающему коду. Поэтому вычисление возвращает результат, а сценарий отдельно получает ввод и показывает ответ.

### Проследим вычисление

Функция суммы возвращает значение и оставляет список прежним:

```python
def total_points(points):
    total = 0
    for point in points:
        total = total + point
    return total

points = [4, 6]
result = total_points(points)
print(result)
print(points)
```

Сначала создаётся локальный накопитель total со значением 0. Цикл читает 4, затем 6 и прибавляет каждое число. После цикла return передаёт 10 вызывающему коду. Список points не менялся, поэтому его содержимое остаётся [4, 6]. В практике мы перенесём тот же принцип на длительности.

### Предскажем результат

```python
print(total_points([]))
print(total_points([12, 18]))
```

**Ожидаемый вывод**

```text
0
30
```

Перерыв не входит в функцию. Его добавляет внешний сценарий один раз после результата расчёта. Это сохраняет прежнее бизнес-правило calc и позволяет отдельно проверить сумму длительностей.

## 03. Несколько функций образуют один сценарий

Композиция означает, что результат одной функции становится входом следующей. Мы не дублируем их тела в новом месте, а соединяем уже известные контракты.

Как значение становится входом следующей функции? Посмотрим на независимый пример с подписью темы.

```python
def clean_tag(raw_tag):
    return raw_tag.strip()

def make_caption(tag):
    return f"Тема: {tag}"

cleaned_tag = clean_tag("  Python  ")
caption = make_caption(cleaned_tag)
print(caption)
```

clean_tag получает строку с пробелами и возвращает Python. Мы сохраняем результат, передаём его в make_caption и получаем Тема: Python. Затем print показывает готовую строку. Каждая функция выполняет своё правило, а промежуточное имя помогает увидеть, что именно переходит к следующему шагу.

Такой порядок похож на эстафету: одна часть передаёт следующей свой результат. Но Python не передаёт значение только потому, что определения стоят рядом. Мы явно вызываем функцию и передаём её результат аргументом.

Промежуточные имена дают контрольные точки: мы можем проверить очищенное название до фабрики и полный словарь перед форматтером. Если на одном шаге значение неверное, сначала проверяем функцию, которая его создала, а не дублируем правило в другом месте. Так каждый контракт можно проверить отдельно и затем снова использовать вместе.

```text
исходная строка
    → normalize_title
очищенное название и проверенные id/priority
    → create_task
полный словарь задачи
    → format_task
строка для показа
    → print во внешнем сценарии
```

Перед create_task вызывающий код проверяет уже знакомые условия: очищенное название не пустое, priority находится от 1 до 5, назначенный id положительный. Если проверка не прошла, создание записи не начинается. В этом занятии мы показываем отказ по правилу без исключений и без создания списка задач.

Модель задачи остаётся полной: id, title, priority и is_done. Значение id является назначенным идентификатором, а не позицией записи в списке. Функция форматирования возвращает строку; только внешний сценарий решает, когда её показать.

### Восстановим порядок вызовов

1. Очистить название.
2. Проверить название, приоритет и назначенный id.
3. Передать очищенное название в существующую create_task.
4. Передать полученную запись в существующую format_task.
5. Показать возвращённую строку снаружи.

Проверка должна быть раньше фабрики. Так неправильные значения не превращаются в принятую запись, а фабрика остаётся простой: она создаёт один словарь из уже проверенных аргументов.

## 04. Чистый результат и видимые эффекты

Чистая функция зависит от явных аргументов, при одинаковом входе даёт одинаковый результат и не меняет внешнее состояние. calculate_study_minutes подходит под этот договор: одинаковый список чисел даёт одинаковую сумму, а сам список сохраняется.

Если функция читает переменную, объявленную снаружи и не переданную параметром, текущее время или ввод из терминала, одного списка аргументов уже недостаточно, чтобы объяснить результат вызова. Если она печатает или меняет объект, появляется видимый эффект. Такие действия нужны приложению, но их место и договор должны быть понятны вызывающему коду.

Но приложение не может состоять только из чистых вычислений. Оно получает input, показывает print и иногда намеренно меняет общий список. Побочный эффект не делает функцию автоматически ошибочной. Важно, чтобы эффект соответствовал договору и был понятен по границе вызова. Переданный список можно представить общим листом регистрации: если функция добавляет в него имя, запись увидят все, кто пользуется тем же списком. Параметр показывает, какой лист меняется, но append всё равно оставляет эффект.

Различим четыре действия:

- return total передаёт значение месту вызова.
- input(...) получает внешний ввод.
- print(message) показывает сообщение человеку.
- durations.append(value) меняет переданный список.

Следующий add_guest служит короткой иллюстрацией контракта, а не новая команда проекта. Если функция добавляет значение в переданный список, аргумент явно показывает, какой объект она меняет. Передача списка параметром делает зависимость заметной, но не отменяет сам эффект. Функция, меняющая список по договору, отличается от функции, которая должна только рассчитать число.

```python
guests = []

def add_default_guest():
    guests.append("Анна")

add_default_guest()
print(guests)

def add_guest(guests, name):
    guests.append(name)

add_guest(guests, "Марк")
print(guests)
```

В первом вызове список скрыт вне параметров add_default_guest, и по вызову не видно, какой объект будет изменён. Во втором guests передаётся явно, но append всё равно меняет тот же список. Аргумент раскрывает зависимость, а контракт объясняет эффект.

### Проверим предположение

**Верно или неверно:** любое изменение списка внутри функции нужно заменять копией.

**Ответ:** неверно. Когда контракт обещает изменить общий список, изменение на месте уместно. Когда контракт обещает вернуть отдельную обновлённую запись, нужна копия и использование возвращённого объекта.

## 05. Копия нужна только для контракта с отдельным результатом

Когда функция обещает отдельную обновлённую версию, мы копируем внешний контейнер, меняем копию и возвращаем её. Поверхностную копию можно сравнить с новой обложкой папки: сама папка отделена, но вложенные листы остаются общими.

```python
queue = ["черновик"]

def add_review(queue):
    queue.append("проверить")

def with_review(queue):
    updated = queue.copy()
    updated.append("проверить")
    return updated

add_review(queue)
print(queue)

queue = ["черновик"]
reviewed = with_review(queue)
print(queue)
print(reviewed)
print(queue is reviewed)
```

Первый вызов меняет исходный список. Второй возвращает отдельный список, а исходная очередь остаётся прежней. Оператор is проверяет, указывают ли два имени на один объект; он отвечает на другой вопрос, чем сравнение содержимого через ==.

Поверхностная копия создаёт новый контейнер только на верхнем уровне. Если внутри списка лежит другой список, оба внешних списка продолжают ссылаться на него:

```python
source = [["Python"]]
copy = source.copy()
copy[0].append("API")
print(source[0])
print(source is copy)
```

**Ожидаемый вывод**

```text
['Python', 'API']
False
```

Внешние списки разные, но вложенный изменился через обе ссылки. Для плоской модели задачи достаточно копии словаря верхнего уровня, потому что её поля содержат числа, строки и флаг. Если контракт требует независимости вложенных изменяемых значений, поверхностной копии недостаточно; глубокое копирование в этой работе не рассматриваем.

### Найдём ошибочное ожидание

```python
profile = {"name": "Анна", "topics": ["Python"]}
updated = profile.copy()
updated["name"] = "Вера"
updated["topics"].append("API")
```

**Вопрос:** почему после изменения updated["topics"] список topics в profile тоже содержит API?

**Ответ:** внешний словарь скопирован, но оба словаря ссылаются на один список topics. Изменение вложенного списка видно через обе записи.

## 06. Переносим правила в существующий main.py

Новые определения normalize_title и calculate_study_minutes располагаются до командного сценария в прежнем main.py. Внутри calc мы используем normalize_title при каждом чтении названия, в том числе при повторе пустого ввода. Вместо второго цикла сложения вызываем calculate_study_minutes(durations), а вычисление перерыва и вывод оставляем снаружи.

При каждом повторе мы очищаем новое название до прежней проверки пустоты. Если после strip() строка всё ещё пуста, сценарий запрашивает её снова; normalize_title не придумывает запасной текст и не запускает создание задачи. Сумма пустого списка равна 0. Перерыв по-прежнему добавляется снаружи ровно один раз, а перевод в часы, остаток и показ результата остаются прежними.

Существующие create_task и format_task остаются единственными функциями для создания и отображения модели. Подготовленные значения для проверки вводятся в интерактивную оболочку, а не сохраняются как тестовая база в рабочем файле.

Если запуск с флагом -i уже знаком, после сохранения мы можем проверить определения так:

```text
python -i main.py
```

Сначала завершаем обычный сценарий прежней командой exit. После приглашения >>> вводим Python-вызовы. Команду запуска вводим в терминале, а выражения Python вводим только после >>>.

```python
normalize_title("  SQL и README  ")
calculate_study_minutes([20, 35])
calculate_study_minutes([])
exit()
```

Затем отдельно запускаем calc два раза и проверяем прежний результат, порядок длительностей и один перерыв. После проверки сохраняем в main.py только рабочие функции и сценарий, без временных диагностических вызовов.

В следующем занятии мы продолжим маршрут: найдём причину ошибки в цепочке функций и подтвердим исправление повторным запуском.

## 07. Что мы будем делать в практике

1. **Разметим обязанности.** Отделим ввод, вычисление, создание записи и вывод; решим, какое правило стоит вынести в функцию.
2. **Выделим правила.** Добавим normalize_title и calculate_study_minutes, сохраним повтор пустого ввода и удалим прежний цикл суммы.
3. **Соединим компоненты.** Проверим значения до создания записи, вызовем существующие create_task и format_task и покажем строку снаружи.
4. **Сверим состояние.** Сравним намеренное изменение с возвращаемой копией и проверим исходный объект после вызова.
5. **Проверим проект.** Дважды запустим calc, сверим сумму и один перерыв, проверим exit и удалим временную диагностику.

В конце мы объясним результат по цепочке: прежний ввод, новое правило, изменённая часть проекта и повторная проверка старых сценариев.
