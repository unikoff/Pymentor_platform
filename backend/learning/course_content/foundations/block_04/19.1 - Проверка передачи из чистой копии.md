# 19.1. Проверка передачи из чистой копии

Убедимся, что опубликованный Planner запускается отдельно от каталога разработки.

**Темы:** проверочная копия · независимое окружение · воспроизводимость по README

## 00. От опубликованной версии к независимому запуску

В занятии 19 мы проверили команды готового Planner, описали запуск в README и нашли опубликованный commit. Теперь проверим, что та же версия работает без файлов основного каталога.

1. **Точка старта.** У нас есть основной проект, точная инструкция, опубликованная версия и опыт работы с clone.
2. **Новый вопрос.** Пройдёт ли полный путь команд из опубликованной копии с новым окружением, если исходный каталог недоступен?
3. **Результат.** Мы запускаем отдельный clone строго по README, проверяем весь сценарий и различаем причины возможного отказа.

README задаёт порядок действий, а commit связывает этот порядок с конкретной версией файлов. Поэтому проверим опубликованный источник в соседней папке, создадим для него отдельное окружение и будем запускать только копию. Это покажет, хватает ли инструкции и опубликованного проекта для самостоятельной работы.

## 01. Что доказывает независимый запуск

Независимая проверка передачи означает, что полученная из опубликованной истории копия запускается без доступа к исходным файлам основного каталога. Мы проверяем весь путь от выбранной версии к реальному поведению приложения.

Успешное открытие страницы репозитория доказывает, что на сервере видны файлы. Успешный запуск из основного каталога доказывает работу этого каталога. Ни одно из этих наблюдений отдельно не подтверждает, что другому запуску хватит опубликованных исходников, README и указанных требований к Python. Например, основной проект может случайно зависеть от локального файла, который не попал в историю, или инструкция может пропускать переход в корень проекта.

Представим, что мы передаём знакомому инструкцию и набор деталей для сборки простой полки. Новый набор соответствует клону, а шаги инструкции соответствуют README. Если сборка получается только благодаря инструменту, оставленному в мастерской автора, передача неполная. Аналогия помогает увидеть скрытые предпосылки, но у программного запуска есть ещё точная версия кода и выбранный интерпретатор. Один домашний запуск также не доказывает работу на каждой операционной системе и любом компьютере.

Проверка здесь ограничена проектом из паспорта: мы подтверждаем известный опубликованный снимок на выбранной Windows-среде, отдельной копией и командами собственного README. Мы не добавляем функции, внешние библиотеки или сохранение задач. Если условия копии отличаются от условий инструкции, сначала фиксируем различие, а не объявляем приложение неисправным.

Сравним два запуска. В каком случае мы проверяем именно передачу, а не только знакомый рабочий каталог?

**Какой вариант проверяет доступность проекта из опубликованной копии?**

- **Запускаем основной каталог.** Команды `cd <основной проект>` и `python main.py` используют привычные исходники и окружение автора.
- **Получаем соседний clone.** Команды `git clone <существующий origin>` и `cd <проверочная копия>` начинают с опубликованных файлов и отдельной папки; затем выполняем README.

**Разбор.** Для проверки передачи источник должен быть опубликованной историей, а рабочий каталог должен быть отдельным. Запуск основного проекта остаётся полезной проверкой, но отвечает на другой вопрос.

## 02. Разделяем основной проект и проверочную копию

Основной каталог остаётся местом разработки. Проверочную копию размещаем рядом с ним, но за пределами его репозитория.

Если clone находится внутри основного проекта, вторая папка может случайно попасть в обзор Git, а команды из терминала легко выполнить не там. Если же мы открываем ещё одно окно, но оставляем его в прежней папке, новый терминал не создаёт независимую копию. Поэтому сначала называем полный текущий путь и проверяем расположение обоих каталогов.

Полезная аналогия здесь похожа на две рабочие поверхности: на первой храним оригинальные записи и делаем исправления, на второй проводим проверку копии. Если на проверочной поверхности появляется замечание, мы переносим его в рабочий журнал, а не незаметно правим только контрольный лист. Сходство заканчивается на организации работы: Git дополнительно связывает копию с адресом remote, веткой и конкретным commit.

Clone создаёт папку с отслеживаемыми файлами и историей выбранного репозитория. Он не делает эту папку продолжением исходной рабочей директории и не переносит локальное окружение автора. Нам не нужно снова выполнять `git init` или создавать новый `origin`: адрес существующего проекта передаётся команде получения копии. Файлы Проводником тоже не переносим, потому что тогда источник версии нельзя надёжно связать с опубликованной историей.

До запуска сверим четыре факта: полный путь показывает проверочную папку; `git remote -v` показывает ожидаемый источник; `git branch --show-current` показывает нужную ветку; `git log --oneline -1` показывает опубликованный commit. Чистый `git status` полезен, но не доказывает правильность адреса и версии. Commit id в этом уроке работает как номер точного снимка, а имя ветки показывает линию изменений, на которой этот снимок найден. Сверим id из локальной истории с опубликованным id, который мы записали в занятии 19: одного адреса remote мало, если в нужной ветке уже появился другой commit.

Сопоставим команду или факт с вопросом, на который он отвечает.

**Какая проверка подтверждает нужное свойство копии?**

- Команда `Get-Location` показывает, где выполняются команды.
- Команда `git remote -v` показывает, откуда получена история.
- Команда `git branch --show-current` показывает, какая ветка выбрана.
- Команда `git log --oneline -1` показывает, какой commit сейчас проверяется.

**Разбор.** Надёжная проверка версии соединяет путь, источник, ветку и commit. Один только чистый статус отвечает лишь на вопрос о локальных изменениях.

Если хотя бы один факт расходится с ожидаемым, останавливаем запуск и выясняем причину. Иначе можно получить обнадёживающий вывод от старого кода, другого проекта или основной папки и ошибочно приписать его опубликованной версии.

## 03. Восстанавливаем окружение по инструкции

Код клонируется из Git, а локальное Python-окружение создаётся отдельно в проверочной папке.

Виртуальное окружение `.venv` связывает проект с выбранным интерпретатором Python и местом для установленных пакетов. Это часть рабочего запуска на компьютере, а не копия исходников. В нашем Planner README сообщает, какая версия Python нужна и есть ли внешние зависимости. Мы создаём окружение заново командой из этой инструкции; переносить папку `.venv` автора не следует, поскольку в ней записаны локальные пути и параметры его компьютера.

Можно сравнить окружение с набором инструментов, который мы подготавливаем для конкретной мастерской. Инструменты помогают выполнить работу с теми же чертежами, но не заменяют сами чертежи и собранную по ним вещь. В программном проекте исходный код остаётся в клоне, а интерпретатор и пакеты берутся из отдельной `.venv`. Эта аналогия тоже имеет границу: виртуальное окружение может использовать базовую установку Python компьютера и само по себе не гарантирует одинаковую работу на всех платформах.

В README уже выбран прямой вызов Python из окружения, поэтому обязательная активация не нужна. Важен путь выполнения: сначала переходим в корень клона, создаём там .venv, затем запускаем тот же локальный `main.py` указанным интерпретатором. Если в инструкции названа только команда, требующая скрытой папки или окружения автора, это недостающий шаг документации.

Соберём знакомые команды в последовательность получения и запуска копии.

**Расставим команды так, чтобы окружение и приложение появились в проверочной папке.**

```powershell
git clone <адрес существующего origin> <имя проверочной папки>
cd <папка клона>
python -m venv .venv
.\.venv\Scripts\python.exe main.py
```

**Разбор.** Сначала получаем опубликованные файлы, затем работаем из их корня. Окружение и запуск относятся к этому каталогу; в реальной проверке используем именно команды README.

Последовательность показывает роли, а не заменяет проектную инструкцию. В реальной проверке адрес, имя папки, версию Python и другие необходимые действия берём из собственного README. Если опубликованному проекту не нужны дополнительные пакеты, не устанавливаем их «на всякий случай»: успешность должна объясняться документированными требованиями.

## 04. Проверяем полный путь, а не только запуск

Окно меню подтверждает лишь старт программы. Передача считается воспроизводимой после полного пользовательского сценария и проверки известной границы хранения.

Проверка использует уже знакомые команды Planner. Сначала пустые `list` и `stats` должны показывать понятное пустое состояние. Затем мы проверяем неизвестную команду, создаём задачу, исправляем недопустимое название и приоритет, добавляем вторую запись и используем id, напечатанные программой. По этим значениям выполняем `find` и `done`, по части названия запускаем `search`, повторяем `done` и смотрим сводку. Ошибочный ввод должен возвращать к ожидаемому запросу, не стирая уже принятые записи.

Для двух записей, где одна отмечена завершённой, числа должны быть согласованы: две всего, одна выполненная и одна открытая. Процент равен пятидесяти. Вывод может оформляться другой строкой, поэтому сверяем сами значения и то, что повторное завершение не увеличило счётчик. Перед завершением проверяем отсутствующий id и штатную команду выхода.

Предскажем независимый расчёт сводки для двух записей, одна из которых завершена.

```python
total = 2
completed = 1
left = total - completed
percent = completed / total * 100
print(total, completed, left, percent)
```

**Ожидаемый вывод:** `2 1 1 50.0`.

Сначала найдём оставшееся количество, затем разделим число завершённых на общее. Этот короткий расчёт лишь помогает проверить взаимосвязь чисел. В приложении статистику получаем командой `stats`, которая читает текущее состояние самого Planner. Файлы задач в этом занятии не создаём.

После `exit` открываем программу в новом процессе. Список снова пуст, а статистика равна нулю: это известное ограничение хранения в памяти, а не исчезновение исходников или Git-истории. Так независимо проверяются и рабочий сценарий, и честность инструкции об ограничениях.

## 05. Разбираем отказ по наблюдаемым фактам

Ошибка во время независимого запуска не сразу указывает на дефект Python-кода. Сначала закрепим версию, путь и способ запуска.

Диагностика начинается с места выполнения: действительно ли мы стоим в корне клона? Затем смотрим, правильны ли remote, ветка и commit id. После этого сверяем выбранный Python и каждую команду README. Лишь когда условия совпали, повторяем вход и сравниваем фактическое поведение приложения с ожидаемым. Такая последовательность отделяет неверный каталог и старый снимок от недостающего шага инструкции и ошибки программы.

Например, если clone содержит ожидаемый commit и запускается только после перехода в другую папку, вероятна неточность пути в README. Если версия правильна и команда из README приводит к traceback на известных данных, сохраняем текст ошибки и проверяем соответствующий участок приложения. Если данные не совпадают с ожидаемым commit, поведение этого запуска пока ничего не говорит о новой публикации. Поэтому записываем точную команду и ввод, а не только фразу «не работает».

Найдём недостающую проверку в коротком протоколе.

**Чего недостаточно, чтобы доказать запуск именно проверочной копии нужной версии?**

```powershell
git status
python main.py
```

1. Чистого статуса достаточно, потому что он показывает, что каталог новый.
2. Нужно сверить полный путь, remote, ветку и commit id.
3. Нужно заново выполнить `git init` и вручную добавить `origin`.

**Разбор.** Чистый статус описывает отсутствие локальных изменений. Правильный ответ включает путь, remote, ветку и commit id: только так мы подтвердим каталог и выбранный снимок.

Команды для сверки из корня клона:

```powershell
Get-Location
git remote -v
git branch --show-current
git log --oneline -1
```

Если README неточен, правку делаем в основном каталоге и проверяем команды повторно. Если сломан код, сначала воспроизводим тот же сценарий в основном проекте, затем вносим минимальное исправление и повторяем прежние проверки. Только после этого сохраняем изменение в знакомой Git-истории и публикуем. Проверочная копия остаётся способом независимого подтверждения, а не вторым местом разработки.

Когда исправление опубликовано, получаем его в clone обычным fast-forward обновлением, сверяем новый commit и повторяем как первоначально неудачный шаг, так и полный сценарий. Fast-forward продвигает копию по той же истории, если в ней нет отдельной расходящейся правки. Ручное исправление только клона обходит публикацию и оставляет основной проект сломанным. Если первая проверка проходит полностью, создавать пустое изменение ради коммита не нужно.

## 06. Проверим границы доказательства

Результат проверки сильнее, когда мы отдельно называем установленный факт и вопрос, на который он не отвечает.

Одинаковый README в браузере и успешный запуск локальной программы могут относиться к разным снимкам. Commit id соединяет файл и историю, путь подтверждает каталог, а команда запуска показывает выбранный интерпретатор. Согласованность этих фактов поддерживает вывод о конкретной передаче. Она не обещает, что приложение будет хранить задачи после закрытия, и не подтверждает все возможные сочетания систем и версий Python.

Перед тем как перейти к практике, ответим на вопрос о границе проверки: какой вывод допустимо сделать после успешного запуска полного сценария из clone?

**Что подтверждает успешный полный сценарий из проверочной копии?**

1. Опубликованный снимок запускается по README в выбранной среде и поддерживает проверенный сценарий.
2. Задачи Planner теперь сохраняются в Git после закрытия программы.
3. Программа гарантированно работает на любой операционной системе без дополнительных условий.

**Разбор.** Мы доказали воспроизводимость конкретной версии в проверенной среде. Сохранение задач и универсальная совместимость потребовали бы отдельных механизмов и проверок.

Если сценарий полностью прошёл, записываем версию, среду, команды и фактические результаты. Если нет, оставляем дефект открытым до исправления в основном проекте и повторной проверки опубликованной версии. Следующее занятие использует уже принятую передачу, чтобы проверить понимание проекта и выполнить самостоятельную правку. Полный clone не будет для него новой темой.

## 07. Что мы будем делать в практике

Проверим готовый продукт в роли пользователя, который получает только опубликованный проект и его README.

1. **Подготовим копию.** Выберем новую соседнюю папку и сверим источник, ветку и опубликованный commit.
2. **Восстановим запуск.** Создадим локальное окружение и выполним команды README из корня clone.
3. **Проверим поведение.** Пройдём команды Planner, отказные случаи, статистику и новый запуск.
4. **Повторим после исправления.** Если найдём дефект, исправим его в основном каталоге и проверим новую публикацию.

Результатом станет проверяемая запись о том, какая опубликованная версия запускалась, каким интерпретатором, по каким шагам README и с каким итогом полного сценария. Практика использует знакомые clone и Git, не создаёт новую функциональность и сохраняет основной проект единственным местом исправлений.
