# Контрольная точка и самостоятельная правка

Проверим готовый Planner, объясним путь данных и безопасно изменим знакомое представление.

## 00. От проверенной передачи к самостоятельной правке

1. **Точка старта.** В предыдущем занятии мы получили отдельную копию опубликованного Planner, создали для неё своё окружение и проверили запуск по README.
2. **Новый вопрос.** Как доказать, что мы понимаем готовую программу, и изменить её вид, не меняя правила работы и данные?
3. **Результат.** Мы принимаем проект полным сценарием, объясняем путь одной задачи, меняем только её отображение и сохраняем проверенную версию в прежней истории.

Раньше мы по частям создавали и проверяли команды Planner. Независимый запуск подтвердил, что опубликованная версия не зависит от файлов исходной папки. Теперь используем этот готовый результат как целое: сначала сверяем поведение, затем прослеживаем ответственность знакомых функций и выполняем одну небольшую правку. Следующая глава получит тот же проект и его проверенную историю, а не новую заготовку.

## 01. Проверяем поведение, а не снимок экрана

Готовую программу нельзя принять по одному удобному выводу. Проверка начинается с ожидания: называем исходное состояние, действие, ожидаемое изменение и ответ интерфейса, а затем сравниваем их с запуском. Так замечаем не только удачный ответ, но и данные, которые могли измениться после отказа.

Представим маршрут с несколькими контрольными пунктами. Фотография у финиша подтверждает только то, что машина туда доехала. Чтобы проверить весь путь, сверим начало, остановки и возврат после сбоя. В Planner такими пунктами будут пустое состояние, добавленные записи, поиск, смена статуса, сводка и штатный выход. Сравнение ожидания с наблюдением показывает, на каком действии поведение разошлось.

Сначала зафиксируем ожидаемое состояние до ввода. При пустом запуске список пуст и сводка нулевая. Если поле отклонено, новая запись не появляется. После добавления проверим её по фактическому id. Для каждого отказа проверим, что уже принятые записи и их порядок сохранились.

Свяжем сценарий с наблюдаемым доказательством:

- Пустой запуск: пустое сообщение и нулевые счётчики.
- Неизвестная команда: меню продолжает работу, записи сохранены.
- Повторное done: статус и сводка не меняются второй раз.
- Новый процесс: задачи пусты, файлы проекта остаются.

Каждая проверка отвечает на отдельный вопрос о поведении. Один удачный вывод не доказывает весь сценарий. Такое сравнение не требует запоминать заранее подготовленный ответ. Мы записываем, что должно остаться неизменным, и проверяем именно это. Для отказа ввода важны не только сообщение об ошибке, но и отсутствие лишней задачи. Для завершения важны выбранный id и сохранность соседней карточки.

## 02. Прослеживаем путь одной задачи

Команда add связывает знакомые части программы в определённом порядке. Ввод сначала проверяется, потому что фабрика должна получить полный допустимый набор значений, а список должен измениться только после этой проверки.

Путь похож на передачу посылки через несколько рабочих мест: приёмщик проверяет адрес, сборщик оформляет содержимое, журнал отмечает принятую посылку, а принтер выпускает наклейку. В Planner ввод играет роль приёмки, проверка полей отсеивает отказ, фабрика создаёт словарь, общий список принимает запись, а formatter готовит строку. Аналогия помогает увидеть порядок, но в Python функции передают значения и ссылки на объекты, а не физическую коробку по конвейеру.

Расположим этапы add от команды до первого отображения принятой задачи:

- Получаем команду через `input()`.
- Проверяем команду, title и priority.
- Получаем следующий id.
- Создаём словарь через `create_task()`.
- Добавляем одну запись в `tasks`.
- Формируем строку и показываем её.

Пока поля не приняты, задача не создаётся. После проверки фабрика готовит полную запись, а список меняется один раз. Внутри проекта меню управляет сценарием, обработчик связывает ввод с операциями, а отдельные функции выполняют известные правила. Функция форматирования, formatter, готовит строку. `create_task()` собирает поля, но не выбирает команду меню. `add_task()` меняет общий список, но не решает, какие данные спросить. `format_task()` возвращает представление одной записи, а вызывающая сторона решает, когда вызвать `print()`. Такое разделение помогает найти место для небольшой правки и не дублировать одну обязанность.

**Вопрос.** Что должно произойти с `tasks`, если проверка приоритета отклонила ввод?

**Разбор.** Новую запись пока не создаём и не добавляем. После исправления значения продолжаем тот же запрос, а уже принятые карточки остаются в прежнем порядке.

## 03. Объясняем функцию через вход, результат и эффект

Имя функции ещё не объясняет, как она работает. Для выбранной операции назовём аргументы, результат, возможное изменение общего состояния, то есть побочный эффект, и место, где появляется сообщение. Это позволяет проверить причинную цепочку, а не перечислить знакомые слова.

`find_task(tasks, task_id)` получает список и id. Она возвращает найденный словарь или `None`, когда совпадения нет, и сама не меняет список. Возвращённый словарь при этом является той же записью, что лежит внутри списка. Поэтому другая функция может изменить его поле, если получила эту ссылку.

`mark_task_done()` использует поиск, сначала обрабатывает отсутствие записи, затем устанавливает `is_done` в `True` и возвращает логический результат. Возврат не отменяет побочный эффект: функция может одновременно сообщить об успехе и изменить найденный словарь. Печать остаётся отдельным действием обработчика. Повторное присваивание `True` не переключает карточку обратно.

Проследим независимый учебный фрагмент, который показывает общую ссылку на словарь:

```python
tasks = [{"id": 7, "is_done": False}]
found = tasks[0]
if found is not None:
    found["is_done"] = True
    result = True
```

В списке хранится одна запись. Имя `found` ссылается на тот же словарь, поэтому после присваивания в списке тоже видно `True`. В реальном коде `find_task()` находит эту запись по id. Фрагмент показывает связь ссылки и словаря, но не заменяет функцию поиска или обработчик меню. Если поиск вернул `None`, до доступа к полю дело не доходит.

**Поиск ошибки.** Что произойдёт, если не проверить результат перед обращением к полю?

Фрагмент обработчика после поиска:

```python
task = find_task(tasks, task_id)
task["is_done"] = True
print(format_task(task))
```

**Разбор.** Для отсутствующего id `find_task()` возвращает `None`. Обращение к `task["is_done"]` вызовет ошибку, поэтому до чтения и изменения полей нужна проверка. Найденную запись можно изменить, а при отсутствии функция должна вернуть отказ без изменения списка.

Ошибочный пользовательский ввод, неизвестный id и программный дефект означают разные вещи. При неправильном тексте или диапазоне программа повторяет запрос. При положительном id без совпадения операция сообщает, что запись не найдена. Обращение к полю у `None` уже является дефектом в коде, который мы локализуем по traceback и исправляем проверкой до изменения.

`build_statistics()` читает все текущие записи и их флаги, затем возвращает сводные значения. Она не добавляет отдельный список выполненных задач и не должна менять исходные карточки. При двух записях, одна из которых выполнена, проверяем `total = 2`, `completed = 1`, `left = 1` и 50 процентов. Повторное завершение уже найденной карточки не создаёт третью запись и не меняет эту сводку.

## 04. Меняем представление, сохраняя запись

Небольшая правка должна менять ровно ту обязанность, которую мы выбрали. В финальном шаге это формат строки, а не структура словаря, поиск, диапазон приоритета или поведение статуса.

Представим бумажную наклейку на коробке. На наклейке видны номер, название, приоритет и состояние, но её замена не меняет содержимое коробки. В Planner словарь остаётся данными, а `format_task()` создаёт читаемую строку. Граница сравнения важна: строка не становится вторым источником состояния, и изменение текста в ней не должно присваивать новое значение `is_done`.

В независимом примере функция форматирует короткую подпись для записи о посылке. Что напечатается и сохранится ли исходный словарь?

```python
parcel = {"city": "Тверь", "fragile": True}

def parcel_label(parcel):
    if parcel["fragile"]:
        kind = "осторожно"
    else:
        kind = "обычно"
    return f'{parcel["city"]}: {kind}'

before = parcel.copy()
print(parcel_label(parcel))
print(parcel == before)
```

**Ожидаемый вывод:**

```text
Тверь: осторожно
True
```

Функция читает поля и возвращает строку; словарь после вызова равен копии. Аналогия с наклейкой объясняет разницу между представлением и записью, но не означает, что программа потом может надёжно восстановить словарь из произвольной строки.

На карточке Planner formatter показывает четыре смысла: id, title, priority и состояние. Мы меняем только понятную подпись открытого состояния; значение `is_done` остаётся логическим флагом. Та же функция вызывается после добавления, в общем просмотре, при поиске по id и при поиске по названию. Если эти места форматируют запись по-разному, небольшой текст придётся исправлять в нескольких обработчиках.

Сравним два решения: повторять разные f-строки в `add`, `list`, `find` и `search` или передавать запись в общий `format_task(task)`. Общий formatter отвечает за представление одной записи; состояние и выбор команды остаются у других функций. Одна правка вида применяется во всех существующих командах.

До изменения запишем оба ожидаемых результата: открытая и выполненная карточки сохраняют все четыре поля, но отличаются состоянием. При проверке сравним не только строку, но и исходные значения id, title, priority, `is_done`, длину списка и его порядок. Это отделяет изменение отображения от изменения данных.

## 05. Повторяем старые гарантии и сохраняем изменение

Регрессией называют ситуацию, когда новая правка ломает то, что раньше работало. После изменения форматтера проверим новую подпись в add, list, find и search, а затем повторим знакомые сценарии ввода, статусов и статистики.

Одной удачной строки мало. Мы проверим обе ветки состояния, повторное завершение, неизвестный id, пустой поиск и сохранность названия с пользовательским регистром. Количество карточек, их порядок и числовая сводка должны остаться прежними. Если поведение разошлось, запишем вход, ожидание и фактический ответ, воспроизведём причину и только затем изменим код.

Поиск и сводка отвечают на разные вопросы. Поиск выбирает для показа подходящие названия, но не удаляет остальные записи из общего списка `tasks`. `stats` считает все задачи, включая те, которые не подошли текущему запросу. После `done` мы проверяем изменённую карточку через `find` и `search`, а затем сверяем сводку по всему списку. Полные счётчики и остальные записи должны сохраниться. Значение `total` не уменьшается из-за поиска: фильтр результата не меняет модель. Поиск помогает найти запись, но не становится новым источником состояния.

Здесь Git помогает сохранить именно проверенную версию кода. `git diff` показывает незаписанные изменения, а `git diff --cached` помогает отдельно осмотреть подготовленный снимок. После проверки нужных файлов создадим коммит в прежнем репозитории и отправим его в уже настроенный remote. Новой истории через `git init` не начинаем и проверочную копию не превращаем во второй основной каталог.

Чистый `git status` сообщает, что рабочие файлы не отличаются от последнего коммита. Он не подтверждает правильность поведения. Коммит и push сохраняют и передают файлы программы, но не карточки `tasks`, которые существовали только в завершившемся процессе.

**Проверим утверждение.** Чистый `git status` сам по себе доказывает, что поиск по отсутствующему id не меняет список.

**Разбор.** Это неверно. Git показывает состояние файлов относительно истории. Поведение поиска подтверждают соответствующий запуск и сравнение данных.

Если правка меняет пример вывода в README, обновим только эту строку, чтобы инструкция не расходилась с программой. Полное описание проекта не переписываем: задача занятия в том, чтобы изменить знакомое представление и подтвердить прежние гарантии.

## 06. Различаем программу и данные одного запуска

После штатного `exit` завершается процесс, в котором жил список задач. При новом запуске `tasks` создаётся заново, поэтому пустой список не означает потерю исходников, коммита или истории.

Код в `main.py` и Git-история остаются на диске. Задачи, которые существовали лишь в памяти процесса, не восстанавливаются. Мы ожидаем пустой просмотр и нулевую статистику после перезапуска и не объявляем сохранение состояния, которого в проекте пока нет. Новое файловое хранилище не добавляем.

**Вопрос.** Что мы передадим следующей главе после завершения процесса?

- Тот же проверенный проект и его историю.
- Карточки из завершившегося списка `tasks`.
- Новый репозиторий с переписанными командами.

**Разбор.** Передаём тот же проект, README и commit. В следующей главе мы сначала сравним поведение с исходной версией, затем безопасно переработаем существующий код. Временные записи процесса в Git не попали.

В курсе Foundations это завершает проектный маршрут. Следующее занятие отдельного курса Python глубже использует Console Planner как исходную версию для аудита и плана конкретной переработки. Сегодня мы проверяем и передаём результат; будущую переработку не начинаем.

1. **Подтвердим готовую версию.** Сверим README, каталог, историю и поведение полного пользовательского сценария.

Практика завершится не новой функцией, а доказанным владением имеющимся продуктом. Мы передадим следующей работе проверенную версию и точное понимание её границы: программа хранит код и историю, текущий процесс хранит временные задачи.
