# 18.1. Поиск по части названия

**Темы:** строковый фрагмент · поиск без учёта регистра · все совпадения · пустой запрос · общий список карточек

## 00. От адреса задачи к её названию

1. **Точка старта.** В проекте есть общий список карточек, поиск по id, команды list и done, а show_tasks показывает записи.
2. **Новый вопрос.** Как найти задачи, если мы помним часть названия, но не id?
3. **Результат.** Поиск покажет все подходящие карточки по порядку, сохранит названия и статусы, а пустой запрос и отсутствие совпадений обработает отдельно.

В прошлом шаге мы нашли карточку по точному id и изменили её флаг через done. Теперь начнём поиск не с адреса одной записи, а с текста, который может встречаться в нескольких названиях. Мы добавим эту возможность к тому же списку: новая команда будет читать данные, а не создавать второй набор карточек.

## 01. Фрагмент строки отличается от элемента списка

Поиск по id возвращает одну запись. Поиск по части названия может найти ноль, одну или несколько записей. Оператор `in` для строк проверяет, встречается ли один непрерывный фрагмент символов внутри другой строки. Он не ищет только целое слово: фрагмент может стоять в начале, середине или конце.

Представим коробку с ярлыками. Отдельный `title` похож на надпись на одном ярлыке, а список `titles` похож на коробку, где лежит много целых ярлыков. Выражение `"Python" in title` ищет последовательность букв внутри одной надписи. Выражение `"Python" in titles` проверяет, есть ли в коробке ярлык, целиком равный слову `Python`. Граница сравнения простая: в настоящем Python смысл `in` зависит от типа значения справа, а не от того, как мы представили коробку.

Проверим фрагмент в названиях файлов. Этот пример показывает поведение строк отдельно от карточек Planner.

~~~python
filenames = ["notes_2026.txt", "map.png", "final_notes.md"]
fragment = "notes"
for filename in filenames:
    print(fragment in filename)
~~~

Результат:

~~~text
True
False
True
~~~

Мы проверили каждое имя, поэтому совпадение в первой строке не остановило перебор. Порядок проверки совпадает с порядком списка. Если сравнить `"notes" in filenames`, Python проверит наличие целого элемента `"notes"`, а не части каждого имени.

**Сравним проверки:**

- **Строка справа от `in`.** Ищем непрерывный фрагмент внутри неё, с учётом регистра.
- **Список справа от `in`.** Ищем в коллекции целый элемент, равный значению слева.
- **Край строки.** Начальный или конечный фрагмент тоже подходит, если символы стоят подряд.

Что мы получим, если фрагмент совпадает только с краем имени?

~~~python
filename = "notes_2026.txt"
print("notes" in filename)
print(".txt" in filename)
~~~

Обе проверки дают `True`. Поиск фрагмента не обязан совпадать с границами слова или части имени.

Оператор проверяет буквальную последовательность символов, а не смысл текста. Он не исправляет опечатки, не переставляет буквы и не считает разные формы одного слова одинаковыми. Поэтому запрос должен содержать те же соседние символы, которые есть в названии. Когда в проекте понадобится поиск по похожим словам, это будет отдельное правило, которого сейчас нет.

## 02. Сравниваем без учёта регистра

Строки сравниваются с учётом заглавных и строчных букв. Поэтому `"notes" in "NOTES_2026.txt"` даст `False`, а `"NOTES" in "NOTES_2026.txt"` даст `True`. Если мы хотим считать `Notes` и `NOTES` одинаковыми для поиска, временно приведём сравниваемые строки к одному регистру.

Метод `lower()` возвращает новую строку в нижнем регистре. Он не переписывает исходную строку. Метод `strip()` возвращает строку без пробелов по краям: с его помощью мы убираем случайные пробелы до и после запроса, не меняя пробелы внутри названия. Затем поиск сравнивает очищенный запрос и временное представление названия. Само поле карточки остаётся в том виде, в каком его ввели.

Можно представить, что у нас есть карточка с названием, а для сравнения мы кладём рядом временную бумажную копию, где буквы приведены к одному виду. Мы сверяем запрос с этой копией, а исходную карточку не переписываем. Предел аналогии: `lower()` не создаёт копию всей задачи, а возвращает новую строку; другие поля словаря вообще не затрагиваются.

**Сравним два подхода:**

- **Записать результат обратно в `task["title"]`.** Исходное название изменится и дальше отобразится в нижнем регистре.
- **Сохранить результат в `comparison_title`.** Временная строка используется для проверки, поле карточки остаётся прежним.

Найдём строку, которая нарушает условие сохранить исходное название:

~~~python
task["title"] = task["title"].lower()
~~~

Здесь мы заменили значение поля. Для сравнения подготовим отдельную строку:

~~~python
comparison_title = task["title"].lower()
~~~

В целевом поиске запрос `"  PyThOn  "` сначала станет `"python"`, а временное представление названия тоже будет приведено к нижнему регистру. Пробелы по краям удаляются у запроса; запись в `task["title"]` не выполняется. Метод `strip()` не сжимает пробелы внутри текста и не удаляет знаки пунктуации. Например, `"Py thon"` и `"Python"` останутся разными запросами. Нормализация ограничена регистром и случайными пробелами по краям, поэтому мы сохраняем предсказуемое правило поиска.

## 03. Пустой запрос обрабатывается отдельно

В Python пустая строка является подстрокой любой строки: `"" in "StudyHub"` даёт `True`. Кроме того, `strip()` превращает ввод из одних пробелов в пустую строку. Если сразу перебрать карточки с таким запросом, каждая запись совпадёт и программа покажет весь список. Для поиска это неожиданное и слишком широкое поведение.

Мы зададим отдельное правило проекта: после `strip()` пустой запрос даёт пустой список совпадений и подсказку в меню. Непустой запрос без совпадений тоже даёт пустой список, но получает другое сообщение. Причина разная: в первом случае мы не запускали поиск по карточкам, во втором проверили текст и не нашли совпадений.

Поэтому обработчик должен проверить `query.strip()` до вызова поиска. Нельзя полагаться только на пустой результат `search_tasks()`, чтобы понять причину: сама функция возвращает пустой список в обоих случаях. Если мы сохраним исходный текст ввода, то сможем отдельно объяснить пользователю пустой запрос и обычный результат без совпадений.

Что мы проверим для пустого ввода?

~~~python
raw_query = "   "
query = raw_query.strip()
print(query == "")
print("" in "StudyHub")
~~~

Результат:

~~~text
True
True
~~~

Первое значение показывает, что запрос пуст после очистки. Второе объясняет поведение оператора `in`: прежде чем сравнивать текст с карточками, мы должны применить правило проекта.

## 04. Собираем все совпадения по порядку

Поиск по названию отличается от `find_task()`. Поиск по id останавливается после единственной нужной записи. Текстовый поиск должен проверить все карточки, потому что общий фрагмент может встретиться несколько раз. Если мы выйдем из цикла при первом совпадении, пользователь не увидит остальные подходящие задачи.

Похожую работу с отдельным результатом можно увидеть на коробках разного назначения. Здесь мы выбираем записи не по подстроке, а по точному типу, поэтому пример не решает задачу поиска Planner:

~~~python
boxes = [
    {"id": "A1", "kind": "tool"},
    {"id": "A2", "kind": "paper"},
    {"id": "A3", "kind": "tool"},
]
tool_boxes = []
for box in boxes:
    if box["kind"] == "tool":
        tool_boxes.append(box)
print(len(tool_boxes), tool_boxes[0]["id"], tool_boxes[1]["id"])
print(tool_boxes[0] is boxes[0])
~~~

Результат: `2 A1 A3`, затем `True`. Мы прошли список от начала до конца. Обе выбранные записи остались в исходном порядке; одинаковый тип не превращает их в одну запись. Проверка `is` подтверждает, что первая запись результата является тем же словарём, что и первая запись источника.

В проекте мы создадим новый внешний список результата и будем добавлять в него найденные исходные словари. Это можно представить как поднос, на который мы временно положили нужные карточки с общей полки. Поднос новый, а карточки на нём те же самые, не бумажные копии. Предел аналогии: список Python хранит ссылки на словари, а не физические карточки. Поэтому `matches.append(task)` добавляет ссылку в результат, но не добавляет новую задачу в общий `tasks`.

Это важно для уже работающей команды `done`. Поиск не изменяет поля, длину или порядок `tasks`. Но найденный словарь в результате является той же записью. После того как `done` поменяет её `is_done`, следующий поиск и прежний `show_tasks()` прочитают обновлённое состояние. Мы не замораживаем старую копию и не создаём отдельную модель поиска. Это различие можно подтвердить двумя наблюдениями: длина и порядок общего `tasks` не меняются, а найденная запись остаётся тем же словарём. Новый список отвечает только за отбор для показа. Его можно отбросить после вывода, не теряя и не копируя данные приложения.

Если названия двух задач совпадают, каждая из них всё равно остаётся отдельной карточкой со своим id. Мы добавим обе записи, а не схлопнем результат по тексту. Пустой исходный список естественно даст пустой результат: цикл не выполнит ни одной проверки.

Проследим, как из общего списка получается отдельный результат с теми же карточками.

## 05. Подключаем поиск к меню

Функция поиска должна отвечать за сравнение и возвращать список, но не читать ввод и не печатать результат. Такой разделённый контракт позволяет отдельно проверить функцию и затем подключить её к интерфейсу. Пункт меню `search` отвечает за запрос, а `search_tasks(tasks, query)` получает уже прочитанные значения.

Возврат списка даёт функции один понятный результат при любом числе совпадений: пустой список, одну запись или несколько. Вызывающий код получает одну и ту же форму данных и не должен менять контракт ради вывода. Это упрощает повторное использование функции и сохраняет границу между поиском и интерфейсом.

Для поиска нам не подходит `read_title()`. Она создана для нового названия карточки и отклоняет пустую строку. У запроса поиска другое правило: обработчик должен увидеть пустой ввод и показать подходящую подсказку. Мы читаем обычную строку, проверяем её после `strip()` и только затем ищем. Имя `search` будет командой меню, `search_tasks()` будет нашей проектной функцией, а поиск подстроки выполняет оператор `in`. Это три разные роли. У строки нет встроенного метода `search()` для этой операции, поэтому мы не должны путать название команды с языковым механизмом.

Путь команды выглядит так:

1. Сначала мы читаем исходный текст; теперь обработчик знает, что ввёл пользователь.
2. Если после `strip()` запрос пуст, показываем подсказку и возвращаемся в меню без поиска.
3. Для непустого текста находим все совпадения в общем списке и сохраняем исходный порядок.
4. Если результат пуст, сообщаем об отсутствии совпадений; иначе передаём карточки прежнему `show_tasks()`.

Отдельный formatter, второй список Planner или новая команда чтения не нужны. Команда возвращается в то же меню, что и остальные операции. Проверяя интеграцию, мы убедимся, что поиск не ломает `add`, `list`, `find`, `done` и `exit`.

## 06. Что мы будем делать в практике

Продолжим прежний `main.py` и подключим поиск к общему списку карточек. Сначала закрепим механику на независимых примерах, затем встроим её в существующий проект.

1. **Разберём границы поиска.** Предскажем результаты для фрагмента строки, целого элемента списка, разного регистра и пустого запроса.
2. **Добавим поиск всех совпадений.** Напишем `search_tasks()` и проверим порядок, повторяющиеся названия и неизменность исходных карточек.
3. **Подключим команду.** Добавим `search` в существующее меню и разделим пустой запрос и непустой запрос без совпадений.
4. **Проверим Planner целиком.** Через `add` создадим несколько карточек, проверим порядок и написание в результате, после `done` повторим поиск и прежние команды.

После поиска мы передадим следующему занятию тот же актуальный список. Статистика будет читаться из полного `tasks`, а не из временного списка найденных карточек. Так мы добавим новую возможность без сброса проекта и одновременно проверим, что прежние команды продолжают работать.
