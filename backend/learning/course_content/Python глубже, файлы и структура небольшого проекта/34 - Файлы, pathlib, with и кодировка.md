## 00. От списка в памяти к данным на диске

В предыдущей работе мы разделили приложение на модули. У каждого файла появилась своя ответственность, а storage пока был только границей на будущее. Теперь этой границе нужно дать первое настоящее поведение.

До сих пор список задач жил внутри процесса Python. Пока программа работает, список доступен. После завершения процесса оперативная память освобождается, и следующий запуск не знает, что было раньше. Для маленького учебного проекта естественный следующий шаг это текстовый файл.

Представьте записную книжку. Пока она открыта на столе, вы видите записи. Если закрыть глаза, записи не исчезли, потому что они находятся на бумаге. Файл выполняет похожую роль: он сохраняет данные вне текущего процесса.

При этом файл не становится вторым списком Python. Между приложением и диском есть граница:

~~~text
список Python
    ↓ преобразование в текст
файл на диске
    ↓ чтение и разбор текста
список Python
~~~

В этой работе мы разберём инструменты, из которых строится такая граница:

- Path для представления пути;
- операции существования, создания папки и соединения частей пути;
- with для безопасной работы с открытым файлом;
- режимы r, w и a;
- явную кодировку UTF-8;
- аккуратную обработку первого запуска;
- проверку того, что смена рабочей папки не создаёт второй файл.

### Что уже есть

В проекте уже определены пакет studyhub, точка запуска, модель и разделение ответственности. Нам не нужно возвращать в storage меню или правила задачи.

### Что появится после работы

В storage появятся функции, которые:

- знают, где находится один файл данных;
- записывают список заголовков по одному на строку;
- читают эти заголовки обратно;
- создают отсутствующую папку data;
- не ломают русские символы;
- начинают с пустого списка при первом запуске.

JSON и восстановление полноценных объектов будут разобраны дальше. Сейчас важно научиться уверенно работать с самой файловой границей.

**Проверьте себя.** Что именно исчезает после завершения процесса: код, правила Task или список, который был только в памяти? Исчезает состояние списка. Значит, новый слой должен сохранить состояние, а не переписать модель.

## 01. Persistence: чем память отличается от файла

Persistence означает, что состояние переживает завершение текущего процесса. Это не отдельная команда Python, а свойство всей цепочки сохранения и восстановления.

### Два состояния одного приложения

~~~text
пока работает процесс
    tasks = ["Изучить pathlib"]
    данные находятся в RAM

после завершения процесса
    RAM очищена
    данные останутся только там, куда их записали
~~~

Список в переменной не является persistence. Он может быть удобным рабочим состоянием, но не долговременным источником.

Файл становится частью persistence только тогда, когда приложение выполняет обе операции:

1. записывает актуальное состояние;
2. при следующем запуске читает его обратно.

Если есть только запись, пользователь может сохранить данные, но не получить их. Если есть только чтение, приложение умеет находить старый файл, но не умеет создавать новое состояние.

### Что такое текстовый формат

Текстовый файл хранит символы в определённой последовательности. Для простого списка заголовков удобно договориться:

- один заголовок занимает одну строку;
- перевод строки разделяет элементы;
- пустая строка не является задачей;
- кодировка записи и чтения одинаковая.

Например:

~~~text
Изучить pathlib
Проверить кодировку
README для проекта
~~~

Это простой формат. Он не хранит priority, id или is_done. Поэтому он подходит для первого знакомства с диском, но не решает задачу полноценной сериализации. На следующем этапе JSON добавит структуру.

### Storage как граница

Остальные части приложения не должны каждый раз сами открывать файл. Иначе путь, режим и кодировка начнут повторяться в разных местах.

Вместо этого они используют небольшой договор:

~~~text
save_titles(titles)
load_titles() -> list[str]
~~~

Service может передать список в storage. Storage решает, как представить этот список на диске. Позже формат можно заменить, не заставляя CLI разбираться в файловых деталях.

### Production-контекст

В настоящих приложениях persistence реализуется файлами, базами данных, объектными хранилищами или удалёнными сервисами. Инструмент меняется, но вопрос остаётся тем же: где находится состояние после завершения процесса и как другой запуск его восстановит.

Текстовый файл хорош для настроек, небольших журналов и учебных примеров. Для конкурентной записи, поиска по большим объёмам и нескольких пользователей позже понадобится другой storage.

**Мини-проверка.** Если вызвать save, а потом в том же процессе посмотреть старую переменную tasks, что именно мы проверили? Только состояние памяти. Настоящая проверка persistence требует снова прочитать внешний источник.

## 02. Path представляет адрес, а не обычную строку

Путь можно записать строкой, но строка плохо объясняет намерение. В ней легко перепутать разделители, имя файла и папку.

pathlib даёт объект Path. Он умеет соединять части пути и выполнять операции файловой системы.

### Независимый пример

Представим модуль, который хранит заметки:

~~~python
from pathlib import Path

MODULE_DIR = Path(__file__).resolve().parent
NOTE_FILE = MODULE_DIR / "data" / "notes.txt"

print(NOTE_FILE)
print(NOTE_FILE.name)
print(NOTE_FILE.parent)
~~~

Здесь происходит несколько разных действий:

- __file__ обозначает файл текущего модуля;
- resolve() получает полный путь;
- parent выбирает папку, в которой лежит модуль;
- оператор / добавляет следующий сегмент;
- name возвращает имя последнего объекта;
- parent у NOTE_FILE возвращает папку data.

Оператор / в выражении с Path не означает деление. Path использует его для понятного соединения частей адреса.

### Папка и файл

У пути к файлу есть два разных смысла:

~~~text
NOTE_FILE
    └── data/notes.txt

NOTE_FILE.parent
    └── data/
~~~

Если нужно создать каталог, вызывайте mkdir у parent, а не у полного пути к файлу.

~~~python
NOTE_FILE.parent.mkdir(parents=True, exist_ok=True)
~~~

parents=True создаёт недостающую цепочку папок. exist_ok=True не считает ошибкой ситуацию, когда папка уже существует.

### Операции Path

| Выражение | Что оно отвечает |
| --- | --- |
| path.exists() | существует ли объект |
| path.is_file() | является ли объект файлом |
| path.is_dir() | является ли объектом папкой |
| path.parent | какая папка содержит объект |
| path.name | какое имя у последнего сегмента |
| path.resolve() | какой абсолютный путь используется |
| path.open(...) | открыть файл с выбранными параметрами |

Эти методы не заменяют понимание границы. Они просто делают намерение видимым в коде.

### Независимый опыт

~~~python
from pathlib import Path

root = Path("reports")
report = root / "today.txt"

print(report.name)
print(report.suffix)
print(report.parent)
~~~

До запуска предположите, какие три строки напечатаются. Здесь ничего не записывается на диск. Пример показывает, что объект Path можно исследовать как адрес, ещё не открывая файл.

### Production-контекст

Path полезен не только для текста. Через него приложения находят конфигурацию, шаблоны, миграции, изображения, временные каталоги и результаты обработки. Объект пути помогает не смешивать адрес ресурса с его содержимым.

**Вопрос.** Почему Path("data") / "notes.txt" лучше, чем ручное склеивание "data/" + "notes.txt"? Выражение с Path явно показывает части адреса и оставляет библиотеке работу с разделителями.

### Связь с текущей работой

В storage нужен один DATA_FILE. Он должен быть Path и описывать файл внутри studyhub/data. Остальные функции будут использовать этот объект, а не собирать адрес заново.

## 03. Рабочая папка и папка модуля это разные вещи

Одна из самых частых ошибок в файловом коде связана с относительным путём.

### Что такое cwd

Текущая рабочая папка, или cwd, это каталог, из которого запущен процесс. Относительный путь отсчитывается именно от него.

Если выполнить:

~~~python
from pathlib import Path

path = Path("data") / "notes.txt"
print(path.resolve())
~~~

результат зависит от того, где была запущена команда.

~~~text
cwd = C:/projects/studyhub
data/notes.txt
↓
C:/projects/studyhub/data/notes.txt

cwd = C:/projects
data/notes.txt
↓
C:/projects/data/notes.txt
~~~

Одна строка кода может привести к двум разным файлам. Это опасно: приложение выглядит рабочим, но данные оказываются в разных местах.

### Путь от __file__

Если файл должен находиться рядом с кодом приложения, основу лучше строить от расположения модуля:

~~~python
from pathlib import Path

BASE_DIR = Path(__file__).resolve().parent
DATA_FILE = BASE_DIR / "data" / "notes.txt"
~~~

Теперь адрес зависит от самого модуля. Смена cwd не меняет DATA_FILE.

Это как шкаф с приклеенной этикеткой. Если переставить человека в другую комнату, шкаф всё равно находится по своему адресу. Относительный путь без основы похож на записку «положи в соседнюю комнату». Смысл зависит от того, где стоишь.

### Важная граница: путь к файлу и путь поиска пакета

Здесь встречаются две независимые настройки:

1. куда Python смотрит, когда ищет пакет studyhub;
2. где storage ищет файл data/tasks.txt.

В дереве:

~~~text
project/
└── studyhub/
    ├── __init__.py
    ├── main.py
    └── storage.py
~~~

команда python -m studyhub.main обычно запускается из project, потому что именно там Python видит папку studyhub как пакет.

Если перейти в project-parent, пакет может перестать находиться. Это даст ModuleNotFoundError. Такая ошибка говорит о пути импорта, а не о неправильном DATA_FILE.

Чтобы проверить смену cwd отдельно от импорта, нужно временно оставить project в PYTHONPATH. Тогда Python найдёт пакет, а storage сможет показать, какой файл он выбрал.

### Понятная проверка из двух каталогов

Сначала из project, где находится папка studyhub:

~~~text
python -c "from studyhub.storage import DATA_FILE; print(DATA_FILE.resolve())"
~~~

Получите первый абсолютный путь.

Затем сохраните путь к project, перейдите на уровень выше и временно добавьте project в PYTHONPATH. В PowerShell это выглядит так:

~~~powershell
$project = (Get-Location).Path
Set-Location ..
$env:PYTHONPATH = $project
python -c "from studyhub.storage import DATA_FILE; print(DATA_FILE.resolve())"
Remove-Item Env:PYTHONPATH
~~~

Если первый cwd был project, переменная $project содержит путь к нему. После перехода выше пакет всё ещё доступен Python через PYTHONPATH, а текущая папка процесса уже другая.

Оба вывода DATA_FILE.resolve() должны совпасть:

~~~text
C:/.../project/studyhub/data/tasks.txt
C:/.../project/studyhub/data/tasks.txt
~~~

Так мы проверяем именно устойчивость адреса.

### Почему нельзя просто требовать одну команду из любой папки

python -m studyhub.main не является магией, которая находит пакет в любой точке диска. Команда зависит от путей импорта. Установка пакета, PYTHONPATH или запуск из каталога, содержащего studyhub, меняют эту настройку.

Поэтому корректная учебная проверка должна разделять:

- запуск модуля там, где пакет доступен;
- диагностический импорт при временно настроенном пути;
- сравнение абсолютного адреса файла.

Если python -m не запускается из project-parent, сначала объясните проблему поиска пакета. Не называйте её ошибкой pathlib.

### Production-контекст

В production приложения часто устанавливаются как пакеты. Тогда импорт не зависит от случайной папки терминала. Но даже установленное приложение всё равно должно осознанно выбирать место для данных: рядом с пакетом, в пользовательском каталоге или в каталоге, переданном конфигурацией.

### Связь с текущей работой

DATA_FILE строится от storage.py. В практике последняя проверка специально разделяет cwd и PYTHONPATH. Её цель не заставить запомнить команду, а доказать, что два запуска используют один файл.

**Остановитесь.** Если во втором запуске появилась ModuleNotFoundError, что нужно диагностировать первым? Сначала доступность пакета studyhub. Только после исправления пути импорта можно сравнивать DATA_FILE.

## 04. with управляет жизнью открытого файла

Открытый файл это ресурс операционной системы. Пока он открыт, процесс удерживает файловый дескриптор. При записи данные могут находиться в буфере, а не сразу на диске.

### Ручное закрытие

~~~python
file = open("notes.txt", "r", encoding="utf-8")
text = file.read()
file.close()
~~~

Если read() выбросит исключение, строка file.close() может не выполниться. Ресурс останется открытым дольше, чем нужно.

Можно писать try/finally, но Python предлагает более ясный инструмент.

### Контекстный менеджер

~~~python
from pathlib import Path

path = Path("notes.txt")

with path.open("r", encoding="utf-8") as file:
    text = file.read()

print(text)
~~~

Вход в блок открывает файл. Выход из блока закрывает его и при обычном завершении, и при исключении внутри блока.

with не читает файл сам и не выбирает кодировку за вас. Он отвечает за границу жизни ресурса.

### Что остаётся после with

После блока объект file закрыт. Но переменная text остаётся обычной строкой Python:

~~~text
файл открыт
    ↓ read()
text находится в памяти
    ↓ выход из with
файл закрыт, text доступен
~~~

Это удобно. Мы быстро читаем ресурс, закрываем его и дальше работаем с уже полученными данными.

### Ручная аналогия

with похож на аренду переговорной комнаты:

1. вход оформляет доступ;
2. внутри выполняется работа;
3. выход возвращает комнату системе;
4. даже если разговор прервался ошибкой, помещение освобождается.

Без такого правила легко оставить занятые ресурсы.

### Production-контекст

Контекстные менеджеры применяются не только к файлам. Они управляют соединениями с базой, сетевыми ресурсами, блокировками и временными директориями. Общая идея одна: ресурс должен иметь ясное начало и конец.

**Предскажите результат.** Что будет доступно после блока with: file или text? Читать через закрытый file нельзя, но уже полученная строка text остаётся доступной.

### Связь с текущей работой

И save_titles(), и load_titles() должны открывать файл внутри with. Это делает закрытие частью структуры функции, а не надеждой на то, что команда дойдёт до последней строки.

## 05. Режимы r, w и a задают намерение операции

Режим открытия это часть договора с файлом. Неправильный режим может изменить данные ещё до выполнения тела with.

### Режим r

r означает чтение.

- файл должен существовать;
- указатель начинается с начала;
- содержимое не заменяется;
- запись через такой дескриптор не является целью операции.

Этот режим подходит для load_titles().

### Режим w

w означает запись нового снимка.

- отсутствующий файл будет создан;
- существующий файл будет очищен при открытии;
- новое содержимое начнёт записываться с начала.

Это важное ограничение. Вызов open(..., "w") уже разрушает прежнее содержимое. Режим нужно выбирать только тогда, когда полная замена действительно задумана.

Для save_titles() это разумный выбор: функция сохраняет актуальный список целиком.

### Режим a

a означает добавление в конец.

- старое содержимое сохраняется;
- новые данные записываются после него;
- режим удобен для журнала событий.

Для полного снимка списка a может создать дубликаты. Если сохранить один и тот же список дважды, его строки появятся в файле дважды.

### Сравнение

| Режим | Аналогия | Типичная задача |
| --- | --- | --- |
| r | открыть тетрадь и читать | load_titles |
| w | заменить страницу новой версией | save_titles |
| a | дописать новую строку в журнал | event log |

### Независимый пример

~~~python
from pathlib import Path

path = Path("message.txt")
path.write_text("первая версия", encoding="utf-8")
path.write_text("вторая версия", encoding="utf-8")

print(path.read_text(encoding="utf-8"))
~~~

Что напечатает код? write_text() использует запись нового содержимого, поэтому останется вторая версия.

Если нужна добавка, используйте явное открытие в режиме a:

~~~python
with path.open("a", encoding="utf-8") as file:
    file.write("\nтретья версия")
~~~

### Production-контекст

Режимы становятся особенно важными, когда файл содержит настройки, журнал или кэш. Ошибка выбора w может стереть конфигурацию. Ошибка выбора a может бесконечно раздувать журнал или повторять данные.

**Найдите проблему.** Почему такой порядок опасен?

~~~python
with path.open("w", encoding="utf-8") as file:
    old_text = file.read()
~~~

Режим w очищает файл и не предназначен для чтения. Сначала выбирайте режим по намерению операции.

### Связь с текущей работой

Практика просит отдельно описать r, w и a. Это не лишний документ. Он помогает объяснить, почему чтение и запись в storage используют разные режимы, а полный снимок не строится через добавление в конец.

## 06. UTF-8 связывает байты файла и символы Python

Человек видит буквы. Диск хранит байты. Кодировка описывает правило, по которому символы превращаются в байты при записи и обратно в символы при чтении.

### Почему проблема заметна на кириллице

Латинские символы часто случайно читаются одинаково в разных настройках. Русский текст быстрее показывает, что договор нарушен.

~~~text
строка Python
    ↓ encoding="utf-8"
байты файла
    ↓ encoding="utf-8"
та же строка Python
~~~

Если запись и чтение используют разные правила, возможны:

- UnicodeDecodeError;
- нечитаемые символы;
- разные результаты на разных компьютерах.

### Явная кодировка

~~~python
from pathlib import Path

path = Path("data") / "note.txt"
path.parent.mkdir(parents=True, exist_ok=True)
path.write_text("Проверить кодировку", encoding="utf-8")

text = path.read_text(encoding="utf-8")
print(text)
~~~

Обе операции явно используют UTF-8. Код не полагается на настройки Windows, Linux, IDE или терминала.

### Независимый пример с open

~~~python
from pathlib import Path

path = Path("greeting.txt")

with path.open("w", encoding="utf-8") as file:
    file.write("Привет, Python")

with path.open("r", encoding="utf-8") as file:
    greeting = file.read()

assert greeting == "Привет, Python"
~~~

Проверка сравнивает точное содержимое. Проверки «файл существует» недостаточно: файл может существовать, но содержать испорченный текст.

### Где хранится кодировка

Кодировку нужно указать на границе между строкой Python и байтами файла. Не нужно отдельно чинить кириллицу после чтения. Нужно использовать один договор на обеих сторонах.

### Production-контекст

UTF-8 является обычным выбором для современных текстовых форматов, API и конфигураций. Явная настройка особенно важна для переносимого кода, CI и обмена данными между системами.

**Соедините части.**

| Уровень | Представление |
| --- | --- |
| переменная text | строка Python |
| файл на диске | байты |
| read_text(..., encoding="utf-8") | байты превращаются в строку |
| write_text(text, encoding="utf-8") | строка превращается в байты |

### Связь с текущей работой

Три контрольных заголовка в практике содержат кириллицу. Это намеренно. Так ученик проверяет реальную границу, а не только английские символы, которые иногда скрывают ошибку настройки.

## 07. Первый запуск и ошибки должны иметь разные смыслы

Когда файл ещё не существует, приложение может считать это нормальным начальным состоянием. Но нельзя превращать любую ошибку чтения в пустой список.

### Нормальное отсутствие

На первом запуске DATA_FILE нет. Правило может быть простым:

~~~text
файла нет
    → приложение начинает с []
    → после первой записи папка и файл появляются
~~~

Такой результат удобен пользователю. Ему не нужно вручную создавать пустой файл.

### Что нельзя скрывать

Следующие ситуации не равны отсутствию файла:

- нет прав на чтение;
- файл повреждён;
- путь указывает не туда;
- произошла ошибка программирования;
- файл оказался директорией.

Если всё обработать так:

~~~python
try:
    return DATA_FILE.read_text(encoding="utf-8")
except Exception:
    return ""
~~~

приложение потеряет смысл ошибки. Пользователь увидит пустое состояние и может решить, что данных никогда не было.

### Узкая граница обработки

Сначала явно обрабатывайте ожидаемое отсутствие. Остальные проблемы должны быть видимыми, пока у проекта нет отдельного договора на них.

В будущем storage сможет переводить низкоуровневые ошибки в собственный StorageError. Сейчас важно не маскировать проблему широким except.

### Пустые строки

Текстовый файл может содержать перевод строки в конце или случайную пустую строку между записями. load_titles() должен вернуть только непустые заголовки без символов перевода строки.

Это не означает, что нужно бездумно менять пробелы внутри заголовка. Удаляйте то, что относится к формату строки, и отдельно решайте правила самой задачи.

### Production-контекст

Различение «ресурс ещё не создан» и «ресурс повреждён» важно для конфигурации, кэша, базы данных и очередей. Тихое восстановление может помочь приложению стартовать, но одновременно скрыть потерю данных.

**Проверьте понимание.** Почему отсутствие файла можно превратить в [], а повреждённый файл нельзя? В первом случае состояние ещё не создавалось. Во втором программа не смогла безопасно прочитать уже существующее состояние.

### Связь с текущей работой

В практике первый вызов load_titles() проверяется до записи. Отдельно проверяется реальный файл после записи. Так нормальный первый запуск не смешивается с доказательством round trip.

## 08. Что мы будем делать в практике

Практика собирает один небольшой файловый слой. Она не добавляет JSON и не меняет доменную модель. Мы последовательно получим путь, запись, чтение, проверяемый сценарий и доказательство устойчивости.

### Общий результат

Готово, если:

- DATA_FILE является Path и строится от storage.py;
- папка studyhub/data создаётся сама;
- save_titles() пишет один заголовок на строку через with и UTF-8;
- load_titles() возвращает [] при первом запуске;
- существующий файл читается без переводов строк и пустых элементов;
- русский текст сохраняется без искажений;
- режимы r, w и a объяснены;
- новый запуск видит тот же файл;
- смена cwd не создаёт второй tasks.txt.

### Порядок работы

~~~text
путь от __file__
    ↓
save_titles()
    ↓
load_titles()
    ↓
UTF-8 и round trip
    ↓
режимы r, w, a
    ↓
смена cwd и проверка DATA_FILE
~~~

Каждый результат подготавливает следующий. Пока storage не знает правильный путь, бессмысленно проверять persistence. Пока чтение и запись не используют один формат, смена рабочей папки не даст полезного вывода.

### Разбор последней проверки

Последняя карточка нужна для проверки архитектурного обещания: файл принадлежит приложению, а не случайному терминалу.

В ней есть два разных действия:

1. обеспечить, чтобы Python нашёл пакет studyhub из обеих точек запуска;
2. сравнить абсолютный путь DATA_FILE.

Первое действие связано с импортом. Второе связано с pathlib. Их нельзя смешивать.

Если из project команда импорта работает, а из project-parent появляется ModuleNotFoundError, это ещё не означает, что DATA_FILE неправильный. Временно добавьте project в PYTHONPATH, повторите импорт и только потом сравнивайте пути.

Проверка считается успешной, когда вывод одинаковый:

~~~text
project/studyhub/data/tasks.txt
project/studyhub/data/tasks.txt
~~~

Если вывод различается, ищите в storage относительный путь, os.getcwd() или другую зависимость от cwd.

### Что зафиксировать после проверки

В docs/storage-path-check.md запишите:

- дерево project и studyhub;
- из какого каталога выполнялась каждая команда;
- как временно обеспечивался поиск пакета;
- два абсолютных результата DATA_FILE;
- короткий вывод о том, почему пути совпали;
- пояснение, чем ModuleNotFoundError отличается от неверного адреса данных.

Так следующий человек поймёт не только команду, но и смысл проверки.

### Границы практики

Сейчас мы не:

- превращаем строки в Task;
- добавляем JSON;
- создаём базу данных;
- реализуем новый CLI;
- скрываем ошибки широким except;
- требуем запуск python -m studyhub.main из произвольной папки без настройки импорта.

Следующий слой сможет использовать этот файловый фундамент. Но сначала нужно доказать простой и честный договор.

### Главное

- Список в памяти исчезает вместе с процессом, файл сохраняет состояние между запусками.
- Path описывает адрес и помогает не склеивать пути вручную.
- Путь от __file__ привязывает данные к приложению, а относительный путь зависит от cwd.
- Поиск пакета Python и выбор DATA_FILE это разные проблемы.
- with закрывает файловый ресурс после блока.
- r читает, w заменяет содержимое, a дописывает в конец.
- UTF-8 фиксирует переносимый договор между строками и байтами.
- Отсутствие файла на первом запуске не равно повреждённому файлу.
- Практика заканчивается сравнением одного абсолютного DATA_FILE из разных рабочих каталогов.

После самопроверки переходите к практике по карточкам. Сначала получите правильный путь. Затем проверьте запись и чтение. После этого отдельно разберите режимы и сравните адрес файла при смене cwd.
