## 00. От рабочего к принятому проекту

Persistent Planner уже умеет работать с задачами и сохранять их после перезапуска. В предыдущей работе мы собрали его прикладное ядро: модель знает правила задачи, storage хранит состояние, сервис выполняет операции, а CLI даёт человеку вход в приложение.

Теперь полезно на минуту остановиться и посмотреть на проект глазами человека, который получил его из репозитория. Он не видел нашу переписку. Он не знает, какой файл мы открывали первым. Он не помнит, почему одна ошибка должна быть исключением, а другая считается обычным первым запуском. Ему нужно запустить приложение, понять его назначение, проверить основные сценарии и увидеть, какая версия действительно принята.

Это и есть смысл финальной работы. Мы не добавляем ещё один функциональный слой и не переписываем уже готовый код ради количества строк. Мы превращаем рабочий набор файлов в проект, которому можно доверять.

Представьте кофейню перед открытием. Кофе уже умеют готовить. Но этого недостаточно: нужно проверить кассу, заказ, оплату, инструкцию для нового сотрудника и план действий при ошибке. Финальная проверка не изобретает новый напиток. Она убеждается, что весь путь от заказа до результата работает для разных людей и в разных ситуациях.

### Рабочий код и принятый проект

Рабочий код отвечает на вопрос: «Срабатывает ли этот сценарий сейчас на моей машине?»

Принятый проект отвечает на более широкий набор вопросов:

- что именно делает приложение;
- как его запустить с чистой копии;
- какие правила защищены тестами;
- что произойдёт при обычной ошибке;
- как понять, что данные действительно пережили перезапуск;
- где заканчивается ответственность каждого слоя;
- какая версия прошла проверку;
- что получит следующий разработчик после клонирования.

Эти вопросы связаны. Хороший тест без инструкции трудно повторить. Хорошая инструкция без проверенного запуска может обмануть. Красивый release без зелёных проверок просто прикрепляет ярлык к неизвестному состоянию.

### Исходная точка

К началу текущей работы в проекте уже есть:

- модель Task с полями и инвариантами;
- независимое поле tags;
- методы изменения состояния задачи;
- MemoryStorage для быстрого in-memory сценария;
- JsonStorage для сохранения состояния между процессами;
- PlannerService с прикладными операциями;
- тонкий CLI;
- unit-тесты отдельных правил и компонентов;
- договор между service и storage.

Это важно не только для удобства. Если снова переписать готовую модель, мы начнём проверять новую версию вместо результата предыдущей работы. Сейчас нужно проверить связку и упаковку проекта.

### Карта работы

~~~text
готовые компоненты
    ↓
матрица рисков
    ↓
integration и acceptance проверки
    ↓
проверка ожидаемых ошибок
    ↓
README и архитектурная схема
    ↓
чистый Git и версия
    ↓
защита решений
~~~

Сначала мы учимся выбирать доказательства. Потом запускаем сквозной сценарий. После этого делаем проект понятным другому человеку и только затем фиксируем версию.

**Остановитесь на минуту.** Если локальная команда добавления задачи сработала один раз, что она ещё не доказала? Она не доказала сохранение после нового запуска, понятность инструкции и корректную реакцию на повреждённый файл. Значит, финальная проверка должна смотреть шире одного happy path.

## 01. Unit, integration и acceptance отвечают на разные вопросы

Слово «тест» часто используют как будто это один инструмент с одной задачей. На деле тесты отличаются масштабом вопроса.

### Unit-тест проверяет одну роль

Unit-тест берёт небольшой компонент и проверяет его правило независимо от остальных частей.

Если функция получает цену и процент скидки, unit-тест может проверить:

- обычную цену;
- нулевую скидку;
- недопустимый процент;
- точный формат результата.

Если такой тест упал, область поиска небольшая. Скорее всего, проблема находится в самой функции или в её входных данных.

В нашем проекте unit-уровень подходит для таких вопросов:

- отклоняет ли Task пустой заголовок;
- не делят ли две задачи один изменяемый список;
- возвращает ли MemoryStorage независимую копию списка;
- правильно ли отдельная операция service меняет задачу.

Unit-тест не обязан открывать JSON-файл и запускать CLI. Чем меньше окружение, тем проще понять причину сбоя.

### Integration-тест проверяет границу

Integration-тест соединяет несколько настоящих компонентов. Он отвечает на вопрос: «Согласуются ли их договоры?»

Небольшой независимый пример можно представить так:

~~~python
class MemoryCatalog:
    def __init__(self):
        self.items = []

    def save(self, items):
        self.items = list(items)

    def load(self):
        return list(self.items)


class CatalogService:
    def __init__(self, catalog):
        self.catalog = catalog

    def add(self, name):
        items = self.catalog.load()
        items.append(name)
        self.catalog.save(items)
~~~

Здесь отдельный unit-тест может проверить копирование списка, а integration-тест проверяет, что service действительно вызывает load, изменяет результат и передаёт его обратно в save.

В Persistent Planner такой границей является связка PlannerService и JsonStorage. Сервис работает с задачами и прикладными действиями. Storage знает, как представить их состояние во внешнем формате. Integration-проверка показывает, что эти два договора действительно совместимы.

### Acceptance-тест проходит путь пользователя

Acceptance-тест задаёт вопрос ещё крупнее: «Получил ли пользователь ожидаемый результат через весь продукт?»

Он может пройти путь:

~~~text
создать задачу
    ↓
изменить её состояние
    ↓
сохранить данные
    ↓
создать новое приложение
    ↓
увидеть сохранённый результат
~~~

В таком сценарии участвуют несколько слоёв. Если он проходит, мы получаем полезное доказательство продукта. Но если он падает, причина может быть в модели, service, storage, сборке зависимостей или CLI. Поэтому acceptance не заменяет маленькие тесты.

### Три уровня рядом

| Уровень | Главный вопрос | Подходящий объект проверки |
| --- | --- | --- |
| Unit | Правильно ли работает одна роль? | Task или MemoryStorage |
| Integration | Согласованы ли соседние роли? | PlannerService и JsonStorage |
| Acceptance | Получается ли пользовательский результат? | CLI и новый запуск приложения |

Не нужно выбирать один «самый правильный» уровень. Это разные линзы. Unit похож на проверку отдельной детали, integration на проверку соединения деталей, acceptance на пробную поездку автомобиля.

### Что происходит в production

В реальном проекте эти уровни часто живут рядом:

- unit-тесты запускаются часто и быстро;
- integration-тесты проверяют базу, файловую систему или внешний адаптер;
- acceptance или end-to-end-тесты проходят важные бизнес-сценарии;
- CI запускает набор перед слиянием изменений;
- отдельные smoke-проверки подтверждают, что приложение вообще поднимается.

Количество тестов само по себе не говорит о качестве. Десять тестов, проверяющих одну и ту же строку, могут оставить без внимания потерю данных. Важнее покрыть разные риски и написать понятные наблюдаемые результаты.

**Проверьте понимание.** Тест с двумя объектами Task и тест с новым JsonStorage могут оба содержать assert. Почему они не доказывают одно и то же? Первый проверяет локальную изоляцию состояния. Второй проверяет границу процесса и внешнего файла.

### Связь с текущей работой

Unit-тесты ядра уже являются фундаментом. Мы не заменяем их длинным сквозным тестом. Мы добавляем несколько проверок связей и пользовательского результата, чтобы увидеть, что готовые части не только хороши по отдельности, но и правильно работают вместе.

## 02. Матрица рисков превращает опасности в проверки

Перед добавлением теста полезно назвать риск. Риск здесь не означает обязательно сложную аварию. Это любое событие, из-за которого пользователь может получить неверные данные, потерять результат или не понять, что делать дальше.

### Почему список функций недостаточен

Если смотреть только на функции, получится список вроде:

- проверить add;
- проверить list;
- проверить done;
- проверить delete;
- проверить stats.

Такой список не говорит, зачем существует каждый тест. Он также легко пропускает важные границы. Например, команда add может работать, но данные всё равно исчезнут после перезапуска.

Вместо перечня функций задайте четыре вопроса:

1. Что может сломаться?
2. Где проявится проблема?
3. Какой уровень проверки её увидит?
4. Что именно мы должны наблюдать?

Ответы удобно собрать в матрицу.

### Пример матрицы

| Риск | Где находится граница | Проверка | Наблюдаемый результат |
| --- | --- | --- | --- |
| Заголовок задачи нарушает правило | Task | unit | понятное исключение |
| Два объекта делят один tags | Task | unit | изменение одного списка не меняет второй |
| Storage возвращает внутренний список | MemoryStorage | unit | внешний код не ломает состояние storage |
| Данные не переживают процесс | JsonStorage | integration | новый экземпляр видит сохранённую задачу |
| JSON повреждён | JsonStorage | integration | возникает StorageError, а не тихий [] |
| id неизвестен | PlannerService | unit или integration | TaskNotFoundError, состояние не изменилось |
| CLI обходит service | CLI | acceptance или smoke | команда идёт через service |
| Новый человек не может запустить проект | README | чистый запуск | команды из инструкции выполняются |

Матрица не является бюрократией. Она похожа на список контрольных точек перед полётом. Пилот не проверяет все детали самолёта одинаково долго. Он сначала убеждается, что проверены самые опасные места.

### Вероятность и цена ошибки

Иногда полезно оценить риск по двум простым признакам:

- насколько вероятно, что проблема появится;
- насколько дорого её обнаружить после публикации.

Потеря задач после перезапуска может быть не самой частой ошибкой, но цена доверия высока. Поэтому для неё нужен отдельный сценарий. Незначительный пробел в форматировании сообщения CLI может иметь меньший приоритет, если смысл сообщения остаётся ясным.

Это не значит, что ошибки интерфейса не важны. Это значит, что порядок проверки должен помогать принимать решения.

### Наблюдаемый результат важнее внутреннего вызова

Проверка service.save() сама по себе не доказывает, что данные сохранены правильно. Важнее наблюдение: другой экземпляр прочитал ожидаемое состояние из того же внешнего источника.

Точно так же проверка «функция вызвала load» не всегда достаточна для пользовательского сценария. Нужно увидеть результат операции.

Хорошая строка матрицы связывает риск с наблюдением:

~~~text
риск: данные теряются после закрытия процесса
    ↓
проверка: создать первый service, изменить данные, создать второй service
    ↓
наблюдение: второй service видит ожидаемую задачу
~~~

### Ошибочный способ выбирать тесты

Плохой подход:

~~~text
добавлю ещё десять assert, чтобы тестов стало больше
~~~

Он создаёт шум, но не обязательно добавляет защиту. Если несколько assert проверяют одну причину, падение может быть длинным, а понимание не станет глубже.

Лучший подход:

~~~text
назову отдельный риск
    ↓
выберу минимальную проверку
    ↓
запишу ожидаемое состояние
    ↓
проверю, что ошибка не меняет данные
~~~

### Production-контекст

В больших командах матрица рисков помогает обсуждать качество до написания тестов. Продуктовый сценарий, техническая граница и ошибка пользователя могут требовать разных проверок. Такая матрица полезна на ревью, в CI и при расследовании дефекта.

**Мини-интерактив.** Представьте, что тест проверяет только: «после load() список не пуст». Какое наблюдение здесь отсутствует? Важно знать, какие именно задачи восстановились, что они снова являются объектами доменной модели и что данные были получены после нового источника, а не остались в памяти.

### Связь с текущей работой

В практике матрица станет коротким документом studyhub/docs/test-matrix.md. Она поможет не смешать уже имеющиеся unit-проверки с новыми integration- и acceptance-проверками и объяснит, зачем каждая новая проверка нужна.

## 03. Приёмочный сценарий проходит путь пользователя

Acceptance-сценарий полезен тогда, когда он похож на реальное действие пользователя, но остаётся повторяемым для теста.

### Сценарий как история

Сценарий можно рассказать без названий функций:

1. приложение начинает работу с новым хранилищем;
2. пользователь добавляет две задачи;
3. одну задачу отмечает выполненной;
4. вторую удаляет;
5. приложение завершается;
6. приложение запускается снова;
7. пользователь видит одну сохранённую выполненную задачу;
8. статистика соответствует этому состоянию.

Это уже не проверка одной кнопки. Это маленькая история жизни данных.

### Почему нужен новый экземпляр

Если после сохранения вызвать load() на том же объекте, можно случайно проверить память старого процесса. Внутри объекта уже мог остаться список, поэтому результат будет выглядеть правильным даже при ошибке записи.

Новый экземпляр с тем же путём задаёт более строгий вопрос:

~~~text
состояние старого объекта больше недоступно
    ↓
новый объект читает внешний источник
    ↓
восстановлены ли данные и их типы
~~~

В реальном приложении это соответствует перезапуску процесса. В тесте не нужно действительно закрывать операционную систему. Достаточно создать новый storage или новый service с тем же временным путём.

### Зачем нужен временный путь

Тест не должен работать с настоящим data/tasks.json. Такой файл может содержать личные данные, зависеть от предыдущего запуска и испортиться после неудачного теста.

tmp_path в pytest даёт отдельную временную папку. Она:

- создаётся для теста;
- не зависит от текущей рабочей директории;
- не смешивает тестовые данные с пользовательскими;
- удаляется после завершения тестового окружения;
- подходит для локального запуска и CI.

Это тот же принцип, что и отдельный чистый стол для эксперимента. Если положить все опыты на один стол, трудно понять, откуда взялся результат.

### Arrange, Act, Assert

Один из удобных способов читать сценарий состоит из трёх частей:

- Arrange: подготовить путь, storage и service;
- Act: выполнить действия пользователя;
- Assert: проверить наблюдаемый итог.

Сквозной тест может быть длиннее unit-теста, но его всё равно стоит держать читаемым. Пусть в нём будет одна ясная история, а не десять несвязанных экспериментов.

### Что должен доказывать сценарий

Хороший acceptance-сценарий показывает не только наличие файла. Он доказывает:

- что service использует storage;
- что операции изменяют доменное состояние;
- что storage сохраняет актуальное представление;
- что новый экземпляр восстанавливает Task;
- что после операций удаления и завершения остаётся ожидаемый результат;
- что статистика строится по восстановленному состоянию.

При этом тест не обязан повторять каждое условие модели. Для этого уже существуют unit-тесты.

### Что сценарий не должен делать

Не стоит:

- читать JSON напрямую из теста вместо публичного API;
- зависеть от файла автора;
- проверять внутренние приватные поля вместо результата;
- полагаться на порядок запуска других тестов;
- превращать один сценарий в огромный набор случайных команд;
- исправлять состояние вручную после ошибки, чтобы тест прошёл.

Тест должен пользоваться теми же границами, которыми пользуется продукт.

### Production-контекст

Acceptance-проверки особенно полезны для критического пути. В web-приложении это может быть регистрация пользователя или создание заказа. В CLI это добавление, изменение и повторное чтение задачи. В обоих случаях ценен не отдельный вызов, а результат для пользователя.

**Вопрос для себя.** Почему новый объект с тем же путём сильнее, чем повторный load() в старом объекте? Он исключает состояние, которое могло остаться в памяти, и проверяет именно persistence.

### Связь с текущей работой

В практике появится один persistent-сценарий через tmp_path. Он соединит уже созданные PlannerService и JsonStorage, но не будет копировать их реализацию внутрь теста.

## 04. Ошибки тоже являются частью договора

Продукт проверяется не только в счастливом случае. Пользователь может указать несуществующий id, файл может оказаться повреждённым, а команда может быть написана с ошибкой.

Если на такие ситуации нет договора, приложение начинает угадывать. Оно может вернуть пустой список вместо ошибки или показать трассировку там, где нужна короткая подсказка.

### Нормальное отсутствие и повреждение

Отсутствующий файл при самом первом запуске может быть нормальным состоянием. Приложение ещё не сохраняло задачи, поэтому пустой список понятен.

Повреждённый файл имеет другой смысл. В нём могли быть сохранённые данные, но программа не может безопасно их прочитать. Превратить такую проблему в [] значит скрыть возможную потерю данных.

Сравните две ситуации:

~~~text
нет файла
    → начать с пустого состояния

есть файл, но JSON не разбирается
    → сообщить StorageError
~~~

Похожая разница есть между пустым почтовым ящиком и ящиком, который не удалось открыть. Это не один и тот же результат.

### Ошибка неизвестного id

TaskNotFoundError относится к прикладному смыслу. Service получил просьбу изменить или удалить задачу, но такой задачи нет.

Правильная реакция обычно включает три свойства:

- ошибка имеет понятный тип;
- состояние списка не меняется;
- сохранение не запускается с ошибочным результатом.

Последний пункт важен. Если после неудачного поиска записать изменённый или пустой список, ошибка превратится в потерю данных.

### Ошибка storage

StorageError сообщает, что проблема находится на границе внешнего хранения. Это может быть повреждённый формат, невозможность чтения или проблема записи.

Сервису не нужно знать все детали JSON-библиотеки. Ему важно получить договорённый тип ошибки. CLI уже решает, как показать её человеку.

Так слои говорят на своих языках:

| Слой | Его смысл ошибки |
| --- | --- |
| Task | вход нарушает правило модели |
| PlannerService | задача не найдена или операция невозможна |
| Storage | внешнее состояние небезопасно прочитать или записать |
| CLI | пользователю нужна понятная реакция |

### Почему except Exception опасен

Широкий обработчик выглядит удобным:

~~~python
try:
    data = read_data()
except Exception:
    return []
~~~

Но он объединяет разные ситуации. Ошибка диска, повреждённый JSON, ошибка программиста и неверная структура начинают выглядеть как пустой проект.

Тише не значит надёжнее. Пользователь может продолжить работу, а следующее сохранение перезапишет важные данные.

Надёжная граница ловит только ожидаемые ошибки, переводит их в понятный договор и оставляет неожиданные дефекты видимыми разработчику.

### Состояние после отказа

Для изменяющей операции полезно проверять не только сам exception:

1. запомнить исходное состояние;
2. выполнить операцию с неизвестным id;
3. ожидать TaskNotFoundError;
4. сравнить состояние после отказа с исходным;
5. убедиться, что ошибочный путь не вызвал сохранение.

Это общий принцип. Если команда не выполнена, данные не должны случайно измениться.

### Ошибки на границе CLI

CLI не должен показывать пользователю внутренний traceback для известной ошибки. Но это не означает, что CLI должен ловить абсолютно всё.

Ожидаемую ошибку можно перевести в сообщение:

~~~text
Задача с таким id не найдена
Файл данных повреждён, восстановление остановлено
Неизвестная команда, используйте help
~~~

Неожиданная ошибка должна оставаться заметной во время разработки. Иначе команда может сообщить «готово», хотя приложение фактически не выполнило действие.

### Production-контекст

В production ошибки часто разделяют на:

- ошибки ввода;
- ошибки бизнес-правил;
- ошибки внешней системы;
- неожиданные дефекты.

Такое разделение помогает выбрать логирование, код ответа HTTP, повтор операции или сообщение пользователю. Для нашего CLI принцип тот же, только интерфейс проще.

**Найдите нарушение.** Если повреждённый JSON обрабатывается как пустой список, какое опасное действие может произойти позже? При следующем сохранении пустой результат способен затереть сведения, которые программа не смогла прочитать.

### Связь с текущей работой

Практика проверяет неизвестный id для операций service и повреждённый JSON для storage. Эти проверки нужны не ради дополнительных исключений. Они доказывают, что отказ не маскируется и не разрушает сохранённое состояние.

## 05. README и architecture.md передают проект новому человеку

Документация является частью интерфейса проекта. Для нового разработчика README играет ту же роль, что экран приветствия для нового пользователя: он объясняет, куда смотреть и какое действие выполнить первым.

### README отвечает на вопрос «как запустить»

Минимальный README должен дать путь от чистого клона до первого результата:

1. что делает проект;
2. кому и для какой задачи он нужен;
3. какая версия Python требуется;
4. как создать окружение и установить зависимости;
5. как запустить приложение;
6. какие команды CLI доступны;
7. как запустить тесты;
8. где хранится файл данных;
9. какие ограничения известны.

Порядок важен. Человек не должен сначала читать историю разработки, чтобы найти команду запуска.

### Проверенная команда и предположение

В документации легко написать команду, которая выглядит правдоподобно, но не работает из корня репозитория. Поэтому README нужно читать как исполняемый сценарий:

~~~text
чистый клон
    ↓
установка
    ↓
запуск тестов
    ↓
запуск CLI
    ↓
контрольный результат
~~~

Каждую команду следует выполнить до публикации. Если путь зависит от личной папки автора, его нужно заменить на переносимую команду.

### README и данные

Документ должен объяснять, что происходит на первом запуске. Отсутствие файла может означать пустое начальное состояние. Но пользовательский JSON может содержать личные задачи, поэтому рабочие данные не должны попадать в репозиторий.

README должен отделять:

- пример данных, который можно безопасно показать;
- локальный файл пользователя;
- шаблон конфигурации без секретов;
- реальные секреты, которые нельзя публиковать.

Документация не должна обещать, что JSON подходит для любого масштаба. Честное ограничение повышает доверие.

### architecture.md отвечает на вопрос «почему так связано»

README помогает запустить проект. Архитектурный документ помогает понять решение.

Простая схема может выглядеть так:

~~~text
CLI
  ↓
PlannerService
  ↓          ↓
Task    Storage contract
             ↓
    MemoryStorage / JsonStorage
~~~

Рядом нужно коротко пояснить роли:

- Task владеет правилами самой задачи;
- PlannerService владеет прикладными операциями;
- storage владеет загрузкой и сохранением;
- CLI переводит команды и результаты;
- main собирает конкретные зависимости.

Такая схема защищает проект от случайного переноса логики в неправильный файл.

### Почему полезно объяснить два storage

MemoryStorage удобен для быстрых unit-тестов: он не требует файловой системы и быстро создаёт изолированное состояние.

JsonStorage нужен в обычном запуске, потому что данные должны пережить завершение процесса.

У них разная реализация, но общий договор. Это пример зависимости от абстракции: service не должен переписывать свою логику при замене способа хранения.

### Документация как проверяемый артефакт

Документацию можно проверять вопросами:

- сможет ли новый человек установить зависимости;
- поймёт ли он, где находится точка входа;
- повторит ли контрольный сценарий;
- найдёт ли команду тестов;
- поймёт ли, куда не следует добавлять JSON-логику;
- увидит ли известное ограничение.

Если ответ отрицательный, проблема находится не в ученике, а в инструкции.

### Production-контекст

В рабочих репозиториях рядом с README часто живут:

- архитектурные решения;
- инструкция для локальной разработки;
- runbook для поддержки;
- описание миграций;
- changelog и release notes.

Не каждый документ нужен маленькому проекту. Но принцип одинаков: повторяющееся устное объяснение стоит превратить в короткую проверяемую запись.

**Мини-интерактив.** Куда поместить описание команды запуска: в README или только в architecture.md? Команда запуска должна быть в README. Архитектурный документ может объяснить, почему запускается конкретная точка сборки.

### Связь с текущей работой

В практике нужно обновить README и создать docs/architecture.md. Текст должен описывать фактически существующие роли и команды, а не желаемую будущую архитектуру.

## 06. Git, версия и GitHub Release фиксируют доказанный результат

Когда проект готов, нужно зафиксировать не только файлы, но и состояние, которое прошло проверку. Здесь встречаются три разных понятия: commit, tag и release.

### Commit

Коммит фиксирует набор изменений в истории Git. Хороший коммит отвечает на вопрос: «Какое законченное изменение здесь принято?»

В финальной работе важно видеть, какие файлы относятся к продукту, а какие являются локальным шумом:

- кэш;
- временный JSON;
- виртуальное окружение;
- логи;
- секреты;
- личные настройки редактора.

Коммит не должен случайно включать их только потому, что они лежат рядом с кодом.

### Tag

Тег указывает на конкретный коммит. Он похож на закладку в книге: если позже появятся новые страницы, закладка всё равно указывает на прежнее место.

Тег не проверяет код и не создаёт качество. Он только даёт имя уже выбранному состоянию. Поэтому ставить версию нужно после проверок.

### GitHub Release

Release является опубликованным описанием версии. В нём полезно написать:

- что готово;
- как запустить;
- какие сценарии проверены;
- какие ограничения остаются;
- к какому тегу относится версия.

Release не должен обещать функцию, которой нет в коммите. Он также не должен содержать секреты или рабочие данные.

### Чистота перед выпуском

Перед созданием версии полезно пройти контрольный список:

- тесты проходят;
- persistent-сценарий проходит;
- README соответствует реальным командам;
- рабочий JSON не отслеживается Git;
- в истории нет токенов и личных путей;
- git status --short показывает ожидаемое состояние;
- git diff --check не находит проблем в изменениях;
- тег связан с проверенным коммитом;
- release notes описывают фактический результат.

### Версии без магии

Номер версии не делает программу стабильной. Он помогает людям договориться, о каком состоянии говорят.

Перед release нужно спросить:

- что изменилось с прошлого состояния;
- совместим ли запуск;
- добавилась ли новая возможность;
- исправлена ли ошибка;
- есть ли ограничение, которое нужно вынести в notes.

Если проверка ещё не завершена, красивый номер лучше отложить.

### Production-контекст

В CI тег часто запускает сборку, публикацию пакета или подготовку deployment. Поэтому ошибка в момент release может стать внешней ошибкой для пользователей. Даже маленький проект полезно приучать к правилу: сначала доказательство, потом публикация.

**Предскажите результат.** Что появится в удалённом репозитории после отправки тега? Появится ссылка на конкретное состояние с этим тегом, но полноценный GitHub Release всё равно нужно создать или оформить отдельно.

### Связь с текущей работой

В практике сначала выполняется чистая приёмка, затем проверяется Git, и только после этого подготавливаются тег, release notes и защита. Если команда из README не работает в чистой копии, release откладывается до исправления причины.

## 07. Защита объясняет решения, а не пересказывает файлы

Защита проекта нужна не для чтения названий файлов. Она показывает, понимает ли автор путь данных и может ли объяснить границы ответственности.

### История одной задачи

Самый понятный формат демонстрации начинается с одной задачи:

~~~text
команда CLI
    ↓
PlannerService
    ↓
Task проверяет правила
    ↓
storage сохраняет состояние
    ↓
JSON-файл
    ↓
новый запуск
    ↓
Task снова доступна
~~~

Эта схема связывает код с наблюдаемым результатом. Если показать только список файлов, будет трудно понять, где на самом деле выполняется правило.

### Три решения, которые стоит объяснить

Первое: почему правила Task находятся в модели. Если заголовок проверяется только в CLI, другой источник данных сможет обойти ограничение. Модель является общей границей инварианта.

Второе: почему service получает storage снаружи. Тогда прикладная логика не зависит от JSON и может работать с MemoryStorage в быстрых тестах или с JsonStorage в обычном запуске.

Третье: почему повреждённый JSON не равен пустому первому запуску. Невозможность прочитать существующие данные не доказывает, что данных нет.

### Как говорить о тестах

Для каждого показанного теста назовите:

- риск;
- уровень проверки;
- действие;
- ожидаемый результат.

Например: «Риск в потере данных после перезапуска. Это acceptance-сценарий. Мы меняем задачу через service, создаём новый экземпляр и проверяем, что восстановилось ожидаемое состояние».

Такой ответ показывает понимание причин, а не память о синтаксисе.

### Что делать, если проверка падает

Падение не нужно скрывать ручным изменением данных. Сначала определите слой:

- неверное правило модели;
- нарушение договора storage;
- ошибка последовательности service;
- проблема CLI;
- команда документации не воспроизводится.

Затем исправление возвращается в этот слой и снова проходит проверку. На защите полезно честно назвать ограничение, если оно не входит в текущую работу.

### Короткий маршрут защиты

За несколько минут можно показать:

1. назначение Persistent Planner;
2. обычное добавление и чтение задачи;
3. сохранение и новый запуск;
4. одну проверку ошибки;
5. различие MemoryStorage и JsonStorage;
6. схему зависимостей;
7. команду тестов и README;
8. известное ограничение JSON.

Не нужно демонстрировать каждую строку. Нужно сделать видимыми решения и доказательства.

### Production-контекст

В рабочих командах объяснение архитектуры происходит на code review, onboarding и incident review. Способность сказать «это правило принадлежит этому слою, потому что...» помогает поддерживать систему, когда автор первоначального кода уже не рядом.

**Восстановите своими словами.** Что важнее на защите: показать много команд или объяснить один путь данных от CLI до сохранённого результата? Один понятный путь обычно даёт больше доказательств, потому что связывает все основные слои.

### Связь с текущей работой

Финальная карточка практики просит подготовить пятиминутную защиту. Её основой станет не новый код, а матрица рисков, acceptance-тест, README и архитектурная схема.

## 08. Что мы будем делать в практике

Эта практика принимает уже созданный Persistent Planner как единый продукт. Мы не добавляем новую бизнес-функцию и не повторяем начальные unit-тесты. Наша задача состоит в том, чтобы доказать качество связки, сделать запуск воспроизводимым и подготовить честную версию.

### Общий результат

В конце должен быть проект, который:

- проходит точечные unit-проверки;
- имеет integration-проверку persistence;
- проходит acceptance-сценарий через новый экземпляр;
- предсказуемо сообщает ожидаемые ошибки;
- имеет тонкий CLI;
- объяснён в README и docs/architecture.md;
- запускается из чистой копии;
- имеет подготовленные release notes и понятную защиту.

### Шесть инженерных результатов

1. **Матрица рисков.**
   В studyhub/docs/test-matrix.md связываются риск, уровень проверки, сценарий и результат. Здесь видно, какие проверки уже существуют и какие добавляются сейчас.

2. **Persistent-сценарий.**
   Через tmp_path создаётся изолированное хранилище. Сценарий проходит через публичные методы готового service, меняет состояние, создаёт новый экземпляр и проверяет итог.

3. **Границы ошибок.**
   Неизвестный id даёт TaskNotFoundError и не меняет состояние. Повреждённый JSON даёт StorageError и не превращается в пустой список.

4. **CLI smoke-приёмка.**
   Проверяются основные команды и понятные сообщения. CLI остаётся переводчиком между вводом пользователя и service, а не вторым местом для JSON-логики.

5. **Документация.**
   README отвечает на вопрос «как запустить и проверить». docs/architecture.md отвечает на вопрос «почему слои связаны именно так». В документации есть контрольный путь и честное ограничение JSON.

6. **Чистая приёмка и release.**
   Из чистого окружения запускаются тесты и сценарии, проверяется статус Git, исключаются временные данные, затем подготавливаются тег, заметки и пятиминутная защита.

### Порядок выполнения

~~~text
матрица рисков
    ↓
persistent acceptance
    ↓
ошибочные состояния
    ↓
CLI smoke
    ↓
README и architecture.md
    ↓
чистый запуск
    ↓
Git tag, release notes и защита
~~~

Порядок не случайный. Матрица помогает понять, что проверять. Сквозной сценарий показывает поведение продукта. Ошибки защищают границы. Документы объясняют запуск. Чистая приёмка проверяет переносимость. Release фиксирует только доказанный результат.

### Где искать каждое правило

- models.py отвечает за модель и её инварианты;
- storage.py отвечает за контракт хранения и ошибки внешнего состояния;
- services.py отвечает за прикладные операции;
- cli.py отвечает за ввод и сообщения;
- main.py собирает конкретные зависимости;
- tests/ показывает наблюдаемые доказательства;
- README отвечает за воспроизводимый запуск;
- docs/architecture.md объясняет связи и границы.

Если во время практики хочется добавить правило в CLI, сначала спросите, кому оно принадлежит. Если правило описывает саму задачу, оно должно жить на границе модели. Если оно описывает сохранение, его место рядом с storage. Если это пользовательский перевод ошибки, его место на границе CLI.

### Доказательства готовности

После практики должны быть видны не только новые файлы, но и наблюдения:

- новый service получает ранее сохранённое состояние;
- ошибка неизвестного id не меняет список;
- повреждённый JSON не скрывается за пустым результатом;
- CLI выполняет команды через service;
- команды README повторяются из чистого окружения;
- Git не содержит рабочего JSON, кэша и секретов;
- release описывает именно проверенный коммит;
- автор может объяснить путь данных без чтения каждой строки.

### Границы текущей работы

Сейчас не добавляются:

- FastAPI;
- база данных и ORM;
- авторизация;
- новые бизнес-функции;
- новая система миграций;
- сложный deployment pipeline.

База данных позже сможет реализовать похожий storage-контракт. Но текущая цель уже завершённой части проекта состоит в том, чтобы научиться принимать, проверять и передавать небольшое приложение другому человеку.

## 09. Самопроверка перед практикой

Ответьте своими словами, не открывая код.

1. Чем unit-тест отличается от integration-теста?
2. Какой вопрос отвечает acceptance-сценарий?
3. Почему список функций не заменяет матрицу рисков?
4. Какой результат нужно наблюдать, чтобы доказать persistence?
5. Почему новый экземпляр service сильнее повторного чтения в старом объекте?
6. Зачем в тесте использовать tmp_path?
7. Почему отсутствие файла и повреждённый JSON имеют разные реакции?
8. Где должен появиться TaskNotFoundError?
9. Почему ошибочный путь не должен вызывать сохранение?
10. Чем StorageError отличается от ошибки пользовательского ввода?
11. Что опасного в except Exception: return []?
12. Какую задачу решает README?
13. Зачем нужен отдельный docs/architecture.md?
14. Почему MemoryStorage удобен для unit-тестов?
15. Что фиксирует Git-тег?
16. Почему release создаётся после чистой приёмки?
17. Как показать путь одной задачи на защите?
18. Где проходит граница текущей работы?

### Главное

- Рабочий запуск и принятый проект отвечают на разные вопросы.
- Unit, integration и acceptance проверяют разные масштабы поведения.
- Матрица рисков связывает опасность, проверку и наблюдаемый результат.
- Новый экземпляр с тем же временным путём даёт сильное доказательство persistence.
- Ожидаемая ошибка должна быть видимой, понятной и безопасной для состояния.
- README помогает запустить проект, а архитектурная схема объясняет его границы.
- Commit, tag и release фиксируют разные части истории результата.
- Защита показывает причины решений и путь данных.
- Текущая практика принимает готовый Persistent Planner, а не создаёт новый функциональный слой.

После этой самопроверки переходите к практике по одной границе за раз. Сначала выберите риски. Затем докажите сквозной путь и ошибки. После этого проверьте документацию и чистый запуск. Так финальный release станет следствием проверок, а не заменой им.
