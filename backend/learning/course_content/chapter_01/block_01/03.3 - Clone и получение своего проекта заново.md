# Clone и получение своего проекта заново

В основной папке уже есть опубликованный `studyhub-console`, история Git и локальная `.venv`. Теперь мы проверим, можно ли получить те же исходники в соседнюю папку, восстановить там окружение и запустить именно эту копию. Затем проведём новую правку через GitHub до проверочной папки, не превращая её во второе место разработки.

## 00. Проверим, можно ли восстановить проект

После прошлых занятий у нас есть опубликованный репозиторий и привычный основной каталог. Ссылка на GitHub ещё не доказывает, что мы можем получить проект заново, запустить чистую копию и обновить её после следующей публикации.

1. **Точка старта:** в `studyhub-console` есть запущенный `main.py`, настроенный `origin`, ветка `main` и собственная `.venv`.
2. **Новый вопрос:** как получить опубликованную историю в другой папке и проверить обновление, не затрагивая исходный проект?
3. **Результат:** рядом появится работающая проверочная копия, которая после линейного обновления запустит новую опубликованную версию.

Мы оставим `studyhub-console` единственным местом, где продолжается разработка. Проверочную папку разместим рядом, а не внутри него. Перед запуском и Git-командой будем сверять активный путь, чтобы не принять работу старого каталога за проверку нового.

## 01. Clone получает опубликованные файлы и историю

Команда `git clone` получает репозиторий с опубликованными файлами и историей коммитов. Это не то же самое, что `git init`: clone связывает новую рабочую папку с существующим источником, а init начинает отдельный локальный репозиторий. Копирование папки Проводником тоже не заменяет clone: в зависимости от выбранных файлов оно может захватить локальные правки или оставить копию без истории и адреса источника.

Для начала разберём форму команды на другом проекте. Это схема, а не команда для запуска: имя `OWNER` и репозитория условные.

```console
git clone https://github.com/OWNER/reading-list.git reading-list-copy
```

Первый аргумент после `clone` задаёт адрес проекта, последний задаёт имя папки на компьютере. Clone создаёт эту папку, помещает в неё опубликованные файлы и получает историю. Отправленные на сервер коммиты попадут в копию; незакоммиченные или неотправленные изменения основного каталога туда не попадут.

Если скопировать весь каталог проекта вместе с `.git`, новая папка получит его локальную историю и рабочие файлы, включая возможные незакоммиченные изменения. Если перенести только исходники без `.git`, копия не будет знать историю и remote. Clone получает опубликованную историю по выбранному адресу, поэтому мы можем независимо запустить и проверить версию, которую отправили.

Можно представить clone как отдельный рабочий стол, подготовленный по опубликованному чертежу, вместе с журналом прежних изменений. Исходный стол остаётся на месте, а копия не превращается в живое зеркало: новые коммиты сами туда не приходят. У этой аналогии есть граница: реальный clone создаёт Git-репозиторий, настраивает адрес источника и получает историю, но не переносит весь компьютер с программами и локальными файлами.

Если имя новой папки уже занято файлами, Git откажется перезаписывать их. Мы проверим содержимое и выберем свободное имя рядом с проектом. Не будем удалять существующую папку наугад.

## 02. Две папки имеют разные роли

На время проверки рядом окажутся две рабочие папки одной истории:

- `studyhub-console` остаётся основным каталогом. Здесь мы меняем программу и публикуем проверенные коммиты.
- `studyhub-console-check` служит только для независимого запуска и получения обновления. Здесь мы не начинаем отдельную разработку.

В настройках репозитория `origin` служит коротким именем сохранённого URL; clone создаёт его автоматически. Название папки studyhub-console-check остаётся только путём на компьютере: оно не меняет адрес удалённого проекта и не переименовывает ветку. Для этой истории локальная ветка называется `main`.

Путь важен потому, что команды терминала работают относительно текущего каталога. Если окно терминала осталось в `studyhub-console`, запуск `main.py` всё ещё относится к исходной копии. Команда `Get-Location` показывает активную папку PowerShell.

`Set-Location` меняет активный путь только в окне PowerShell, а не перемещает файлы. Clone создаёт папку внутри текущего каталога, но сам не переходит в неё. Поэтому мы сверим путь до clone, затем отдельно откроем новую папку и проверим его ещё раз.

Сначала прочитаем адрес уже настроенного источника из основного проекта и вернёмся в родительский каталог:

```powershell
Set-Location "C:\work\studyhub-console"
git remote get-url origin
Set-Location ..
Get-Location
```

Заменим примерный путь на путь нашего проекта, а `OWNER` в следующей команде на владельца опубликованного репозитория. Clone выполняется из родительской папки, поэтому проверочная копия окажется рядом:

```console
git clone https://github.com/OWNER/studyhub-console.git studyhub-console-check
Set-Location .\studyhub-console-check
Get-Location
```

При clone Git сохраняет адрес источника под именем `origin`. Добавлять тот же remote повторно не нужно. Проверим, что получили ожидаемый репозиторий и его опубликованную ветку:

```console
git remote -v
git branch --show-current
git status -sb
git log -1 --format=%H
```

`git remote -v` показывает адрес для получения и отправки. `git branch --show-current` называет открытую ветку. `git status -sb` показывает рабочее состояние и связь с известной удалённой веткой. `git log -1 --format=%H` выводит полный ID последнего локально известного коммита. Мы сверим владельца, имя репозитория, `main` и ID с опубликованной версией.

В нашем проекте адреса для получения и отправки должны вести к нужному репозиторию. Если `git remote -v` показывает неожиданного владельца или имя, мы остановимся и сверим адрес с GitHub, прежде чем продолжать.

Для частного репозитория может понадобиться вход через Git Credential Manager и право чтения. Если Git отказывает, проверим адрес проекта и активный аккаунт. Пароль или токен не помещаем в команду и не отправляем в сообщении.

## 03. Окружение создаётся отдельно

После clone появится `main.py` и история проекта, но `.venv` не появится. Она исключена через `.gitignore`, потому что содержит локальную установку Python для конкретного компьютера. Репозиторий хранит исходный код и правила проекта, а не готовую папку окружения.

Окружение можно представить как набор инструментов рядом с каждым рабочим столом: новый стол получает чертёж, но инструменты нужно подготовить отдельно. Граница аналогии в том, что `.venv` создаётся командами Python и не является частью Git-истории.

Убедимся, что находимся в `studyhub-console-check`, создадим там собственную `.venv` и запустим файл именно из этой папки:

```powershell
Get-Location
python -m venv .venv
.\.venv\Scripts\python.exe --version
.\.venv\Scripts\python.exe main.py
```

Мы вызываем Python из проверочной `.venv` напрямую, поэтому активация окружения для этого примера не требуется. В редакторе выберем интерпретатор из `studyhub-console-check\.venv`. Успешный запуск подтверждает проверку только в том случае, если активная папка и путь к `main.py` действительно относятся к clone.

Найдём ошибку в подготовленной команде. Мы хотим проверить clone, но сначала открыли основной каталог:

```powershell
Set-Location C:\work\studyhub-console
.\.venv\Scripts\python.exe main.py
```

Интерпретатор запустил корректный файл, но не ту копию. Сначала перейдём в `studyhub-console-check` и проверим `Get-Location`, затем повторим запуск через локальную `.venv`. Копировать окружение и повторно выполнять `git init` не нужно.

## 04. Новую версию публикуем из основного каталога

Теперь изменим одно видимое стартовое сообщение в `studyhub-console\main.py`, запустим программу и посмотрим diff. Комментария недостаточно: после последующего обновления мы должны увидеть в выводе, что проверочный файл действительно поменялся.

Вернёмся к знакомому циклу из прошлого занятия. В основном каталоге мы проверим незавершённые изменения, подготовим только `main.py`, просмотрим staged diff и список подготовленных файлов. Если там есть другие файлы, сначала разберёмся с ними и не создадим коммит с чужой правкой. Когда подготовлено только ожидаемое изменение, создадим коммит и отправим его в уже настроенный `origin`.

После отправки новая версия находится на GitHub, но файлы в `studyhub-console-check` всё ещё старые. Публикация обновляет серверную историю, а не все локальные клоны автоматически.

Если новая строка не появилась там, где мы её ждём, проследим путь изменения по состояниям. Рабочий diff показывает сохранённую правку, staged diff показывает подготовленное содержимое, а локальная история и `git status -sb` помогают найти коммит, который ещё не отправлен. Затем сверим `git remote -v`, ветку и страницу GitHub: commit мог попасть в другой репозиторий или остаться локальным.

1. Если `git diff -- main.py` показывает правку, а staged diff её не показывает, подготовим только нужный файл.
2. Если `git status -sb` показывает ahead 1, коммит существует локально, но ещё не отправлен.
3. Если ID на GitHub не совпал, сверим `git remote -v`, владельца и ветку.

Ahead 1 означает, что локальная ветка содержит коммит сверх известной `origin/main`. Мы сверим адрес и ветку, затем отправим уже проверенный коммит; заново создавать проект не нужно.

## 05. Fetch получает сведения, но не заменяет рабочие файлы

В clone команда `git fetch origin` узнаёт о новых коммитах опубликованной ветки. Она обновляет локальные сведения об удалённой истории, но не передвигает текущую `main` и не меняет рабочий `main.py`.

После fetch ссылка `origin/main` показывает последнее состояние сервера, которое мы получили этим обменом. Это удалённая отслеживаемая ветка: локальная запись о последнем известном состоянии GitHub, а не прямое соединение, которое обновляется само. До fetch она может быть устаревшей.

Тут поможет образ двух указателей на дорожной карте: `main` показывает версию, с которой работает наш каталог, а `origin/main` после fetch отмечает версию, найденную на сервере. Аналогия упрощает механизм ссылок: Git хранит историю коммитов и имена ссылок, а не карту с отметками.

На схеме сравним опубликованную историю и состояние clone после каждого шага. Так мы отдельно проследим удалённую ветку, локальные ссылки и файл, который открыт для работы. После fetch удалённая отслеживаемая ветка уже видит C, но запуск всё ещё читает файл B. После pull локальная `main` и рабочий файл доходят до C, если локальная история продолжает ту же линию.

Получим сведения и сравним ожидающий коммит с текущим файлом:

```console
git fetch origin
git status -sb
git log --oneline HEAD..origin/main
git diff HEAD..origin/main -- main.py
git diff HEAD -- main.py
```

`git status -sb` может показать, что локальная `main` отстаёт от `origin/main`. `git log HEAD..origin/main` перечислит коммиты, которых ещё нет в локальной ветке. `git diff HEAD..origin/main -- main.py` покажет опубликованную правку. `git diff HEAD -- main.py` при этом остаётся пустым, если мы не меняли рабочий файл вручную.

Fetch не проверяет сервер постоянно. Чистое состояние до обмена не доказывает, что на GitHub нет новой версии: оно говорит только об отсутствии локальных правок относительно известных Git данных.

## 06. Pull применяет только линейное обновление

Когда мы проверили полученную историю, можем применить её к рабочим файлам. Команда `git pull --ff-only` сначала получает актуальные сведения, затем передвигает локальную ветку только если это продолжение одной линии истории.

```text
До fetch:
main        A -> B
origin/main A -> B
GitHub      A -> B -> C

После fetch:
main        A -> B
origin/main A -> B -> C

После pull --ff-only:
main        A -> B -> C
origin/main A -> B -> C
```

Fast-forward похож на продвижение указателя по уже готовой линейной дорожке: локальная ветка не содержит отдельной работы, которая расходится с опубликованной. Pull передвигает `main` и обновляет рабочие файлы, но не создаёт нового коммита за скачивание. Ограничение `--ff-only` важно: если истории разошлись, команда откажет, вместо того чтобы автоматически создавать merge-коммит.

Например, если локальная `main` продолжилась от B к своему коммиту D, а GitHub от B к C, одной линии уже нет. `--ff-only` откажет и оставит файлы как есть. В этом опыте clone не содержит собственной разработки, поэтому мы ожидаем простой переход от B к опубликованному C.

После успешного обновления сравним `git rev-parse HEAD` и `git rev-parse origin/main`. Совпавшие ID подтверждают, что локальная ветка пришла к тому коммиту, который она получила с сервера. Затем запустим `main.py` из `.venv` clone и проверим новое сообщение. Если `--ff-only` отказывает, мы остановимся и разберём состояние; force, очистка файлов и обучение конфликтам не входят в это занятие.

## 07. Возвращаемся в основной проект

Проверочная папка помогла убедиться, что опубликованный код можно получить и обновить отдельно от основного каталога. Продолжать работу будем в `studyhub-console`, где остаются основной `main.py`, привычная `.venv` и рабочая история.

Перед следующим шагом вернёмся в основной каталог и проверим `Get-Location`. В занятии 4 мы дадим значениям в том же `main.py` понятные имена. Проверочный clone не заменяет основной проект и не становится второй линией разработки.

## 08. Что мы будем делать в практике

Свяжем изученное различие между историей и рабочими файлами с одним контролируемым обновлением:

1. **Клонируем проект:** получим рядом с основным каталогом копию с той же опубликованной историей.
2. **Запустим clone:** создадим отдельную `.venv` и подтвердим путь до проверочного `main.py`.
3. **Опубликуем правку:** изменим видимое сообщение в основном каталоге и сверим commit на GitHub.
4. **Сравним состояния:** после fetch увидим новую `origin/main` при прежних `main.py` и локальной `main`.
5. **Применим fast-forward:** после pull проверим новый ID и запуск обновлённого файла, затем вернёмся в основной каталог.

Мы будем идти от основной папки к clone и обратно, не создавая второй рабочий проект. Адрес и ID коммита, самостоятельный запуск обеих версий и возврат в исходный каталог подтвердят результат.

Если имя папки занято или Git сообщает об отказе в доступе, сначала проверим путь, адрес и аккаунт. Существующие файлы не удаляем, а секреты не помещаем в команду или сообщение.
