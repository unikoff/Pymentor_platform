# 3.2. GitHub, remote, авторизация и push

## 00. Старт и результат

В прошлом занятии мы создали локальные коммиты, но ещё не проверяли, что именно хранит сервер. Сначала разберём направление отправки и границу между локальной историей и GitHub.

**Точка старта.** В знакомом `studyhub-console` уже есть локальные коммиты из прошлого занятия. Связь с репозиторием GitHub и направление для отправки настроены.

**Новый вопрос.** Как проверить адрес отправки, опубликовать локальную историю и доказать, что GitHub получил именно нужный коммит?

**Результат.** Мы опубликуем прежние записи, затем создадим следующую проверенную версию и сверим её на GitHub по ветке, ID и содержимому файла.

Мы уже умеем выбирать содержимое и записывать его в локальную историю. Теперь проверим адрес, ветку, аккаунт и условия публикации, затем отправим прежние коммиты и сравним ответ команды с фактической страницей репозитория. После этого пройдём тот же путь для следующей проверенной правки `main.py`.

## 01. Коммит и публикация происходят отдельно

Сохранение файла меняет рабочую копию на компьютере. `git add` выбирает содержимое для следующей записи, а `git commit` сохраняет подготовленную версию в локальной истории. Команда `git push` передаёт уже созданные коммиты в удалённый репозиторий. Это разные шаги: один не выполняется автоматически вслед за другим.

Можно представить локальную папку как рабочий стол, а GitHub как полку с опубликованными снимками проекта. На рабочем столе мы продолжаем менять файлы, а на полке появляется новая версия после отправки коммита. У этой аналогии есть граница: GitHub хранит историю коммитов, но не запускает нашу программу и не обновляет открытый файл в редакторе. Новая строка сначала остаётся только на компьютере.

У пути есть четыре заметные точки: сохранённый файл, выбранное содержимое после `git add`, запись после `git commit` и публикация после `git push`. Если остановиться между шагами, следующий этап ещё не произошёл. Например, редактор может показывать новый текст, хотя локальная история и страница GitHub всё ещё содержат старую версию. Вспомним это различие, когда будем предсказывать, что увидим на сайте.

На схеме в видимой версии сплошная стрелка показывает отправку созданных коммитов, а пунктирная возвращает результат команды в тот же локальный проект. Ответ терминала подтверждает ход операции; опубликованную версию мы отдельно сверим на странице GitHub.

Перед первой публикацией важно проверить, кто может видеть репозиторий. Публичный проект доступен всем, а доступ к частному проекту получают владелец и люди или команды с выданными правами. Также коммит содержит сведения об авторе, включая настроенный email. Проверим, что видимость проекта и адрес автора выбраны осознанно. Если адрес не подходит выбранной политике приватности, остановимся до публикации и разберёмся с настройкой. Не будем прикладывать email, пароль или токен к общему скриншоту.

Перед отправкой разведём три настройки: `user.name` и `user.email` подписывают коммит, Git Credential Manager (GCM) подтверждает аккаунт для защищённого HTTPS-соединения, а public или private определяет, кому доступны файлы репозитория. Ни одна из этих настроек не заменяет две другие.

## 02. `origin` хранит адрес проекта

Remote, или удалённый репозиторий, связывает локальную папку с адресом проекта на сервере. Имя `origin` обычно дают основному GitHub-адресу. Его удобно представить как подпись в адресной книге: по короткой метке Git находит сохранённый URL. Но подпись не является аккаунтом, веткой, папкой или подтверждением, что на сервере уже есть наша последняя версия.

Посмотрим, что сохранено в проекте:

~~~console
git remote -v
~~~

~~~text
origin  https://github.com/OWNER/studyhub-console.git (fetch)
origin  https://github.com/OWNER/studyhub-console.git (push)
~~~

Вместо `OWNER` указан владелец нашего репозитория. Сверим владельца и имя `studyhub-console`. Git может вывести две строки: адрес для получения и адрес для отправки. Они часто совпадают, но проверять нужно фактическое значение.

Репозиторий на GitHub изначально создали пустым, чтобы его история началась с уже существующих локальных коммитов. Если при создании сайта добавить отдельный README или файл `.gitignore`, сервер может получить независимый первый коммит. Тогда локальная и удалённая истории начнутся по-разному, и придётся разбирать их объединение. В этом занятии мы продолжаем один существующий проект, поэтому новый репозиторий и вторую историю не создаём.

Команда `git remote add origin ...` нужна, когда адрес ещё не сохранён. В нашей папке `origin` уже существует, поэтому не повторяем добавление. Если появляется `remote origin already exists`, сначала читаем `git remote -v`. Не удаляем remote и не заменяем URL догадкой: сначала убеждаемся, что понимаем, на какой проект указывает текущая настройка.

В URL указываются владелец и репозиторий. Сам адрес не должен содержать пароль или токен: URL отвечает на вопрос «куда обращаться», а GCM отдельно помогает подтвердить аккаунт. Git показывает адреса для получения и отправки, поэтому сверим обе строки, если они различаются. Не будем менять сохранённые значения, пока не выясним, какой из них используется и какой адрес должен быть у проекта.

## 03. `main` и `origin/main` показывают две стороны истории

`main` обозначает локальную ветку, где находятся наши коммиты. `origin/main` обозначает последнюю известную Git запись о ветке `main` на сервере. Это не вторая рабочая папка и не экран GitHub. Git обновляет такие записи во время сетевых операций; пока мы не обратились к серверу, они могут не отражать его самое новое состояние.

Upstream-связь задаёт соответствие между локальной веткой и удалённой. Она говорит Git, с какой веткой сравнивать локальную работу и куда направлять короткую команду `git push`. Посмотрим на ветку, связь и состояние:

~~~console
git branch --show-current
git branch -vv
git status -sb
~~~

Если в прошлом занятии локально созданы два коммита, а известная Git запись удалённой ветки ещё позади, статус может выглядеть так:

~~~text
## main...origin/main [ahead 2]
~~~

Метка `ahead 2` означает, что локальная ветка содержит два коммита сверх сохранённой Git записи `origin/main`. Это полезная подсказка, но не живая проверка сайта: удалённая ветка могла измениться с момента последнего обмена.

Представим `origin/main` как последнюю полученную фотографию серверной ветки. Мы можем сравнить с ней локальную `main`, но фотография не обновится от редактирования файла. Эта аналогия помогает помнить о возможной устарелости, но сама по себе не объясняет все правила ветвления Git. Для текущей задачи достаточно проверить имя ветки и уже настроенное направление.

Короткий `git status -sb` удобен для сравнения, но его результат зависит от настроенного upstream и известной Git записи удалённой ветки. Он не подтверждает, какой аккаунт открыт в браузере, и не показывает содержимое страницы. Сначала убедимся, что сравниваем нужную пару `main` и `origin/main`, затем после отправки отдельно проверим сам репозиторий на сайте.

В `studyhub-console` направление для отправки уже настроено. При первой отправке `git push -u origin main` передаёт ветку и сохраняет upstream. Если Git сообщает `no upstream branch`, сперва проверим `git branch -vv`, текущую ветку и URL `origin`; не будем направлять проект по догадке.

## 04. Вход и подпись отвечают на разные вопросы

Настройки `user.name` и `user.email` задают подпись автора в создаваемых коммитах. Они не открывают аккаунт GitHub и не дают право записи в репозиторий. Посмотреть текущие локальные настройки можно так:

~~~console
git config --get user.name
git config --get user.email
~~~

Перед публикацией проверим и авторские сведения уже созданных коммитов. Адрес автора становится частью истории, когда мы отправляем эти коммиты. Для будущих записей можно заранее выбрать адрес, совместимый с настройками приватности GitHub, например предложенный GitHub адрес `noreply`. Не будем менять автора старых коммитов в рамках этой практики или публиковать личные адреса в отчётах.

Для обмена по HTTPS используем Git Credential Manager (GCM). Если менеджер запросит вход, выберем аккаунт с правом записи и подтвердим запрос в браузере. Если GitHub попросит дополнительную проверку, завершим её и вернёмся в терминал. При сохранённом входе окно может не появиться. В Windows GCM обычно хранит подтверждённые данные в Windows Credential Manager.

GitHub не принимает обычный пароль аккаунта как пароль HTTPS-команды Git. В этом сценарии не создаём токен вручную и не настраиваем SSH как параллельный путь. Успешный вход подтверждает аккаунт, но ещё не доказывает, что нужный коммит отправлен в нужную ветку.

Если сервер отказывает в доступе, проверим, какой аккаунт выбран в браузере и есть ли у него право записи именно в `studyhub-console`. Изменение `user.name` или `user.email` не исправит отсутствие разрешения. Не помещаем пароль, токен или содержимое окна авторизации в URL, исходный код, коммит или скриншот.

## 05. Сначала отправим прежние коммиты

Перед отправкой посмотрим на локальные записи и состояние ветки:

~~~console
git log --oneline -3
git status -sb
git rev-parse --short HEAD
~~~

Если ожидаемые коммиты из прошлого занятия указаны как локальные и направление подтверждено, выполним:

~~~console
git push
~~~

Когда upstream настроен, Git отправляет новые локальные коммиты в связанную ветку. Сохранённые, но не закоммиченные строки команда не отправляет. Поэтому повторный `push` не может опубликовать текст, который остался только в редакторе.

После успешной команды откроем страницу своего репозитория на GitHub. Проверим владельца, имя `studyhub-console` и ветку `main`, затем сравним короткий ID последнего коммита, его сообщение и изменённую строку `main.py`. Терминал подтверждает, что команда завершилась; страница правильной ветки показывает, какую запись сервер действительно хранит.

Чистый `git status --short` означает, что в рабочей папке и индексе нет незакоммиченных изменений. Он не доказывает публикацию коммитов. И наоборот, локальные файлы могут быть чистыми, хотя локальная ветка всё ещё впереди известной удалённой. Для доказательства результата сопоставим фактический ID и содержимое на GitHub.

Если `git push` сообщает `Everything up-to-date`, Git не нашёл новых коммитов для отправки в настроенное направление. Возможно, изменение ещё не закоммичено, уже отправлено или мы проверяем не тот локальный проект. Сверим diff, историю, remote и страницу GitHub вместо повторения команды вслепую.

Чистый статус похож на проверку рабочего стола: он сообщает, остались ли незаписанные в истории изменения в локальной папке. Но чистый стол ничего не говорит о том, что лежит на удалённой полке. Граница аналогии в том, что Git также сравнивает файлы с индексом и локальной историей, а не просто показывает содержимое папки. Поэтому доказательством публикации служит сверка серверного коммита и файла.

## 06. Создадим и опубликуем следующую версию

После проверки прежней истории изменим одну знакомую строку или комментарий в `main.py`. Сначала сохраним файл, запустим программу и посмотрим рабочий diff:

~~~console
.\.venv\Scripts\python.exe main.py
git status -sb
git diff -- main.py
~~~

Затем выберем только эту правку и прочитаем подготовленное содержимое до создания записи:

~~~console
git add main.py
git diff --staged -- main.py
git commit -m "update StudyHub message"
git rev-parse --short HEAD
~~~

Рабочий diff показывает сохранённое изменение, staged diff показывает выбранное для коммита содержимое, а новая запись появляется в локальной истории. Между этими шагами мы сравниваем результат и не добавляем посторонние файлы.

До `push` сформулируем проверяемое ожидание: локальный `HEAD` уже новый, а опубликованный ID ещё старый. После отправки проверим, что ожидаемый ID стал последним на GitHub и в файлах видна выбранная строка. Такое сравнение до и после отделяет действие от результата и помогает заметить ошибку адреса, ветки или аккаунта.

До следующего `push` на странице GitHub по-прежнему ожидается прежняя опубликованная версия. После проверки отправим новый коммит и снова откроем правильные владельца, проект и ветку. Сверим ID из `git rev-parse --short HEAD`, сообщение и изменённую строку файла. ID коммита не меняется при отправке; меняется то, что этот коммит теперь доступен в удалённой ветке.

Так мы проверяем полный цикл: правка, запуск, выбранный diff, локальный коммит, отправка и подтверждение серверной копии. Если после коммита в рабочем дереве остались другие изменения, они не попадут на GitHub от команды `push`, пока не будут отдельно записаны в коммит.

## 07. Подберём проверку к сообщению Git

Сообщение Git указывает на конкретный этап: сохранённый адрес, связь ветки, доступ к репозиторию или наличие новых коммитов. Сначала определим этот этап, затем проверим соответствующую настройку.

- `remote origin already exists`: прочитать `git remote -v` и сверить владельца с проектом.
- `no upstream branch`: проверить текущую ветку, remote и предполагаемое направление.
- Ошибка авторизации или доступа: проверить браузерный аккаунт и право записи в нужный репозиторий.
- `Everything up-to-date`, но сайт не обновился: сопоставить локальный diff и историю с веткой, ID и файлом на GitHub.

У этих ситуаций разные причины: сохранённый адрес, связь веток, право доступа или отсутствие нового коммита. Сначала читаем сообщение и проверяем именно соответствующую часть пути. Не применяем `git push --force`, не удаляем remote и не передаём секреты как способ «починить» публикацию. Если удалённая ветка неожиданно изменилась, остановимся и разберём её состояние до следующих команд.

## 08. Что мы будем делать в практике

1. **Проверим направление.** Сверим адрес `origin`, локальную ветку, upstream, аккаунт и условия публикации.
2. **Опубликуем прежнюю историю.** Отправим уже созданные коммиты и найдём на GitHub правильную ветку, ID и строку `main.py`.
3. **Проверим полный цикл.** Создадим следующий локальный коммит, сравним версии до отправки, выполним `push` и подтвердим новую запись на сайте.

В практике продолжаем тот же `studyhub-console`. Если в других файлах есть личные правки, оставим их вне учебного коммита. Если `main.py` уже изменён до занятия, сначала отдельно завершим эту правку, чтобы случайно не включить её в учебную историю.

В следующем занятии получим эту опубликованную историю в соседнюю папку и запустим копию проекта. Тогда мы проверим, что именно эта версия доступна для копирования.
