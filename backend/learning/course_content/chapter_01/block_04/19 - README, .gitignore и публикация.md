# 19. README, .gitignore и публикация

Опишем готовый Planner точно и опубликуем проверенную версию в его прежней Git-истории.

**Темы:** фактическая документация · воспроизводимый запуск · проверка ignore и публикация

## 00. От готового Planner к проверенной инструкции

1. **Точка старта.** Команды `add`, `list`, `find`, `done`, `search`, `stats` и `exit` работают в одном проекте; мы уже пользовались Git и существующим удалённым репозиторием.
2. **Новый вопрос.** Как точно описать запуск и ограничения, а затем опубликовать проверенную версию, не создавая новый репозиторий?
3. **Результат.** README соответствует реальным командам, `.gitignore` проверен, а нужный коммит найден в прежнем удалённом репозитории.

Мы переходим от работающей программы к её внешнему договору: что она умеет, что нужно для запуска и чего от неё пока не следует ожидать. Git уже знаком по первому блоку, поэтому применим прежние команды к документации и отправим ту же историю. Независимый запуск из новой копии будет отдельной проверкой в следующем занятии.

## 01. Сначала соберём факты о проекте

README начинается не с рекламы, а с наблюдений. Перед текстом мы запускаем приложение, проходим меню и сверяем каждое обещание с результатом. Команды и их назначение должны совпадать с существующими обработчиками, а не с планом будущего развития.

У каждой команды своя роль. `add` принимает название и приоритет и добавляет запись; `list` показывает список; `find` ищет запись по id; `done` меняет её состояние. `search` находит записи по части названия, `stats` показывает числа total, completed, left и процент, а `exit` завершает текущий запуск. Название очищается от внешних пробелов, приоритет ограничен диапазоном от 1 до 5, id является положительным целым числом.

**Сопоставим команды и результаты.** Какую команду связать с каждым результатом?

- **add:** создаёт запись с названием и приоритетом.
- **find:** находит запись по её id.
- **search:** показывает совпадения по части названия.
- **list:** показывает текущие записи.
- **done:** меняет состояние записи по id.
- **stats:** считает total, completed, left и процент.
- **exit:** завершает текущий процесс.

**Разбор.** README описывает проверяемый эффект команды. Git хранит историю файлов, но не введённые задачи: список существует в памяти одного запуска.

Проверим статистику независимо от оформления меню. В примере две записи, и только одна отмечена выполненной. Сначала предскажем total, completed, left и процент, затем сверим значения с `stats`.

```python
tasks = [
    {"id": 31, "title": "Изучить SQL", "priority": 1, "is_done": False},
    {"id": 32, "title": "Повторить Python", "priority": 5, "is_done": True},
]
completed = 0
for task in tasks:
    if task["is_done"]:
        completed += 1
percent = round(completed / len(tasks) * 100, 1)
print(len(tasks), completed, len(tasks) - completed, percent)
```

**Предсказание:** `2 1 1 50.0`.

Формат сообщения реального меню может отличаться, но три числа должны совпасть. В сценарии мы добавим две задачи, возьмём фактические id из вывода, найдём запись, выполним её, проверим частичный поиск и вызовем статистику. После `exit` новый запуск начинается с пустого списка: это ограничение версии, а не потеря исходного кода или истории Git.

## 02. README объясняет договор проекта

README в корне репозитория помогает без устного контекста понять назначение Planner, требования, запуск, команды и ограничения. Он похож на карточку-инструкцию рядом с устройством: заголовки помогают найти раздел, команды задают порядок действий, ограничения показывают границы. Но программа не помещается в карточку, а после изменения проекта её инструкции могут устареть.

Для такого документа достаточно нескольких правил Markdown, простого текстового формата с видимыми маркерами. Один знак `#` задаёт главный заголовок, два знака `##` начинают подраздел, пустая строка отделяет абзацы, а дефис начинает пункт списка. Одна пара обратных кавычек выделяет короткую команду внутри строки. Три обратные кавычки открывают и закрывают блок из нескольких строк, например команд для терминала. Маркеры управляют оформлением, а не поведением программы.

```markdown
# Настольная игра

Партия состоит из нескольких раундов.

## Перед началом

- подготовить карточки
- выбрать первого игрока

`rounds = 3`
```

**Проверим понимание. Какой маркер начинает заголовок второго уровня?**

- `# Результат`
- `## Результат`
- `` `## Результат` ``

**Разбор.** Два знака `#` перед названием начинают подраздел; обратные кавычки вокруг текста показывают его как код.

```markdown
# Название проекта

Краткое назначение и результат.

## Возможности

- Команда и её фактический эффект

## Требования

## Запуск в Windows PowerShell

## Контрольный сценарий

## Ограничения
```

Markdown задаёт структуру текста, но разметка не подтверждает, что команда работает. Например, если окружить `## Возможности` обратными кавычками, Markdown покажет эти знаки как код, а не оформит заголовок. Команды и обещания в README мы всё равно сверяем с проектом.

**Сравним описания. Какое сообщает полезный и проверяемый факт?**

- Непроверенное обещание: «Planner сохраняет задачи после перезапуска».
- Факт текущей версии: «Задачи доступны в одном запуске и очищаются после его завершения».

**Разбор.** Вторую формулировку можно проверить повторным запуском. README соответствует действующим командам и состоянию данных. Возможности будущих версий не добавляем заранее.

Описание возможностей должно называть команды, принимаемые значения и наблюдаемые последствия. В требованиях указываем только необходимое. Если используются стандартные средства Python, не придумываем зависимость или файл требований. Ограничение памяти называем прямо, а не скрываем общей фразой о «сохранении в приложении».

Структуру расположим по вопросам читателя: что это за проект, что нужно заранее, как получить файлы и запустить их, что попробовать после запуска и каких свойств пока нет. Это внешний договор приложения: README обещает только наблюдаемое поведение и понятный маршрут, а не внутренний код. Если не указать нужную версию Python или скрыть обязательный пакет, команда сработает только на машине автора. Поэтому мы проверяем не красоту текста, а точность и достаточность каждого раздела.

## 03. Запуск должен обходиться без догадок

Инструкция запуска похожа на маршрут с подписанными поворотами: получаем проект, переходим в созданную папку, создаём окружение, запускаем программу. Аналогия показывает порядок, но компьютер не угадывает пропущенный адрес. Поэтому указываем URL прежнего репозитория и заменяемое имя каталога, а не чужой локальный путь.

Перед командами фиксируем версию Python, на которой действительно проверен проект, и отмечаем, нужны ли дополнительные пакеты. Команда `python --version` показывает, какой интерпретатор создаст `.venv`. В Windows PowerShell команда создания `.venv` подготавливает окружение. Прямой запуск интерпретатора из этой папки не требует активации. Команды в README описывают шаги будущего запуска; в этом занятии мы проверяем исходный проект, а не принимаем чистый clone.

```powershell
git clone <адрес существующего origin>
cd <имя папки, созданной clone>
python --version
python -m venv .venv
.\.venv\Scripts\python.exe main.py
```

Порядок такой: clone создаёт копию, cd выбирает её корень, python --version сверяет версию для требований, команда Python создаёт окружение, а его интерпретатор запускает main.py. Угловые скобки обозначают заменяемый текст, а не часть команды. В README мы подставляем URL из `git remote -v` и реальное имя папки после clone.

В этом занятии мы документируем маршрут и проверяем исходный каталог; получение клона и независимая проверка инструкции пройдут следующим этапом.

Здесь важны два разных шага. `git clone` получает файлы из удалённой истории, а `cd` меняет текущую папку терминала. Python ищет `main.py` относительно этой папки, поэтому пропуск перехода в корень клона даст ошибку пути даже при правильном коде. Команда создания `.venv` подготавливает отдельный интерпретатор, а последняя строка запускает именно его. Окружение создаётся заново в клоне; оно не переносит список `tasks` из рабочего запуска и не делает данные постоянными.

## 04. .gitignore помогает проверить состав репозитория

Файл `.gitignore` содержит шаблоны для окружения и технических файлов Python. Аналогия: это список того, что не кладём в посылку с проектом. Каждое правило соответствует классу файлов, который можно создать заново или который не относится к исходникам. Но список упаковки не может отменить уже отправленную посылку: новое правило само не убирает отслеживаемый файл из индекса или истории.

```gitignore
.venv/
__pycache__/
*.pyc
.env
```

Мы не заменяем прежний `.gitignore` без чтения. Сначала сохраняем полезные исключения, затем добавляем только обоснованное правило. Исходники и README остаются видимыми Git. Файл `.env` может хранить секреты, но создавать его ради занятия не нужно.

**Сопоставим команды и результаты.**

- **.venv/**: локальное окружение, которое создаётся заново.
- **__pycache__/**: служебный каталог Python.
- `*.pyc`: сгенерированный байткод.
- **.env**: локальная конфигурация, где могут быть секреты.


**Разбор.** Маска влияет на подходящие файлы, которые ещё не отслеживаются. Для уже отслеживаемого файла проверяем состояние отдельно; секрет из истории требует замены, а не только строки ignore.

**Верно или неверно:** если файл уже был закоммичен, новая строка в `.gitignore` удалит его из прежней истории.

**Ответ: неверно.** Ignore не переписывает коммиты и автоматически не отменяет отслеживание. Сначала изучаем Git-состояние.

Ignore применяется к файлам, которые Git ещё не отслеживает. Если README уже подготовлен или `main.py` отслеживается, правило не скроет его изменения: `git status` продолжит их показывать. И наоборот, отсутствие `.venv` на странице репозитория не доказывает, что окружение нельзя добавить случайно; перед публикацией сверяем конкретный состав коммита. Если секрет уже попал в историю, одной строки ignore недостаточно: открытые учётные данные заменяют отдельно. В этом упражнении секреты мы не создаём.

## 05. Публикуем только проверенный коммит

Рабочие изменения, подготовленный список и коммит это разные состояния Git. `git status` показывает новые и изменённые файлы, `git diff` показывает неподготовленный текст, а `git diff --staged` показывает содержимое следующего коммита. Перед staging открываем сам новый README: обычный diff не показывает содержимое неотслеживаемого файла.

Сначала повторяем локальный запуск после текстовых изменений, затем проверяем статус, готовим нужные пути и читаем staged diff целиком. Если в подготовленном наборе есть неожиданная строка, исправляем staging до коммита. Такое разделение снижает риск опубликовать окружение, случайный файл или неверную инструкцию.

**Расположим действия:** локальный запуск, status, подготовка нужных файлов, staged diff, commit, push.

```powershell
.\.venv\Scripts\python.exe main.py
git status
git add README.md .gitignore
git diff --staged
git commit -m "docs: describe Planner"
git push
```

**Разбор.** Push передаёт уже созданный коммит в настроенную ветку. Он не включает несохранённые изменения и не исправляет ошибку README.

До отправки проверяем адрес прежнего `origin` через `git remote -v` и текущую ветку через `git branch --show-current`. История остаётся прежней: новый пустой репозиторий и повторная настройка remote не нужны. Если push отклонён, сохраняем локальный коммит и проверяем адрес, права или направление. `--force` не служит способом исправить обычный отказ.

Перед разбором последовательности ниже определим, какие проверки пропущены и почему добавлять все файлы сразу рискованно.

Различим четыре состояния. Изменения находятся в рабочих файлах; `git add` выбирает, что войдёт в подготовленный снимок; `git commit` сохраняет его в локальную историю; `git push` отправляет готовый коммит в настроенную удалённую ветку. Например, если мы изменили только подпись в `main.py`, `git diff` покажет незаписанное в коммит отличие. После `git add main.py` команда `git diff --staged` покажет выбранную версию. Сохранение файла в редакторе не выполняет ни подготовку, ни коммит.

```text
git add .
git commit -m "final"
git push --force
```

**Вопрос:** что проверим перед публикацией?

- Локальный запуск, статус, staged diff, прежний remote и ветку
- Удалим README и заново создадим репозиторий
- Добавим всё через force и пропустим проверку

**Разбор.** Массовое добавление может захватить лишнее, а force может перезаписать удалённую историю. Сначала запускаем проект, читаем новый README отдельно, проверяем статус и направление, затем готовим нужные файлы, читаем staged diff, создаём коммит и только после этого выполняем обычный push.

## 06. Различим публикацию и независимую проверку

После push находим commit id в локальной истории и сверяем его с нужной веткой прежнего удалённого репозитория. На странице проекта проверяем README, исходники и ожидаемые файлы, а также отсутствие окружения и временных файлов. Это подтверждает, что нужный снимок дошёл до сервера.

Не приписываем доказательству лишнее: наличие README на сервере не показывает, что команды выполнены на другом компьютере, а push не проверяет их автоматически. В следующем занятии мы возьмём опубликованный адрес и проверим новую копию отдельно. Если инструкция не сработает, исправление внесём в основной проект, опубликуем новую версию и повторим проверку.

**Проверим вывод. Что подтверждает только публикация в этом занятии?**

- Нужный commit id и README есть в прежней ветке сервера
- Новая копия запускается строго по README
- Задачи Planner сохраняются после выхода

**Ответ.** Первое. Публикация подтверждает наличие коммита на сервере. Независимый запуск относится к следующему этапу, а список задач пока хранится в памяти.

## 07. Что мы будем делать в практике

1. **Проверим поведение.** Пройдём семь команд с фактическими id; запишем результаты и границу хранения задач в памяти.
2. **Подготовим README.** Сверим возможности, требования, запуск, контрольный сценарий и ограничения с проектом; получим инструкцию без чужих локальных путей.
3. **Проверим файлы и снимок.** Прочитаем прежний .gitignore, локальный статус и staged diff; в подготовке останутся только README и нужные изменения ignore.
4. **Опубликуем ту же историю.** Создадим коммит, выполним обычный push и сверим id в прежней ветке; запуск чистой копии оставим следующему занятию.

Запуск подтверждает факты для README, а staged diff показывает, какие файлы войдут в коммит. Совпавший commit id подтверждает публикацию. Этого ещё недостаточно, чтобы доказать работу инструкции на новой машине: такую проверку мы выполним отдельно и не меняем набор возможностей Planner.
