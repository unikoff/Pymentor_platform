## 00. Вступление

Предыдущие занятия готовят нас добавлять задачи, находить их и отмечать выполненными. Теперь посмотрим на список целиком: отдельная карточка отвечает на вопрос о себе, а команда `stats` должна показать состояние всего списка. Для ответа мало помнить команды, которые мы вводили; нужно заново посчитать, что содержится в `tasks` сейчас.

1. **Точка старта:** по плану предыдущих занятий работают `add`, `list`, `find`, `done` и `search`, а каждая карточка хранит собственный `is_done`.
2. **Новый вопрос:** как получить согласованные числа по всем задачам и процент выполнения, включая пустой список?
3. **Результат:** команда `stats` показывает актуальные `total`, `completed`, `left` и процент, не меняя задачи.

Сначала отделим состояние карточек от действий, которые к нему привели, затем посчитаем счётчики проходом по списку, отдельно разберём долю и пустой знаменатель, после чего свяжем вычисления с уже существующей ветвью меню. Так новый итог опирается на готовые данные и компоненты, а проверка не создаёт вторую версию Planner.

## 01. Состояние задачи и событие команды — разные вещи

- **Что и зачем объяснить:** поле `is_done` описывает текущее состояние каждой записи. Ввод `done` — действие пользователя; его количество само по себе не сообщает, сколько задач завершено. Статистика отвечает о списке сейчас, а не ведёт историю команд.
- **Механизм и порядок:** найти задачу и прочитать `is_done`; команда `done` может установить `True`; затем повторное выполнение оставляет поле `True`. При подсчёте каждая запись учитывается по своему полю один раз за проход. Результат не зависит от того, однажды или несколько раз вызвали `done` для одной и той же задачи.
- **Независимый пример и путаница:** в списке проверок две строки отмечены флажками. Количество нажатий на одну и ту же уже отмеченную строку не превращает её в две выполненные. Не смешивать «сколько было действий» с «сколько элементов сейчас имеет состояние выполнено».
- **Первое самостоятельное действие:** сравнить две истории с одинаковым конечным набором карточек, где одну задачу отмечали один раз или повторно; предсказать, должны ли совпасть `completed` и объяснить почему.
- **Опора для практики:** «Состояние читаем из `task["is_done"]`; событие `done` не добавляем в накопитель отдельно».
- **Переход:** чтобы получить сводку всего списка, пройдём по карточкам и будем обновлять счётчики из их состояний.

## 02. Согласованные счётчики за один проход

- **Что и зачем объяснить:** `total` — число всех задач, `completed` — число задач со значением `is_done == True`, `left` — число остальных. Эти величины связаны: `total = completed + left`; `left` можно получить вычитанием после прохода.
- **Механизм и порядок:** перед циклом начать `total` и `completed` с нуля. Для каждой записи увеличить `total` на один; только при истинном `task["is_done"]` увеличить `completed`. После цикла вычислить `left = total - completed`. Каждый счётчик относится ко всему списку, поэтому его нельзя заново обнулять внутри цикла. Значение `True` добавляет к `completed` единицу, а не присваивает туда постоянное `1`.
- **Независимый пример и путаница:** на коротком списке из трёх заявок проследить начальные значения и обновление после каждой строки, включая две выполненные. Отдельно заметить, что список без записей оставляет все три счётчика равными нулю. Не считать `left` по числу итераций и не использовать одно условие как общий счётчик всех элементов.
- **Первое самостоятельное действие:** заполнить небольшую трассировку для пустого, смешанного и полностью выполненного набора. Критерий — после каждого элемента видны изменения `total` и условного `completed`, а итог удовлетворяет равенству.
- **Опора для практики:** таблица «карточка → `is_done` → `total` после шага → `completed` после шага» и инвариант `total = completed + left`.
- **Переход:** счётчики можно вернуть отдельно от вывода; затем из двух счётчиков вычислить долю выполненных.

## 03. Функция сводки возвращает данные

- **Что и зачем объяснить:** `build_statistics(tasks)` получает актуальный список задач и возвращает словарь со счётчиками `total`, `completed`, `left`. Он отделяет вычисление от отображения: функция не печатает строки меню и не переписывает карточки.
- **Механизм и порядок:** локальные счётчики создаются заново при каждом вызове, цикл читает записи, затем функция собирает рассчитанные значения в один результат через `return`. Следующий вызов снова читает переданный список. Изменения между вызовами видны, потому что список задач меняет `add` или `done`, а не потому что функция копит прежнюю статистику.
- **Независимый пример и путаница:** взять явный маленький аргумент для функции и отдельно показать возвращённый словарь; сравнить с `calculate_study_minutes`, которая тоже возвращает число, но суммирует длительности. `print` показывает значение человеку, `return` передаёт значение вызывающей функции. Не вводить постоянное хранилище статистики и не заменять текущие данные счётчиками событий.
- **Первое самостоятельное действие:** проследить, что функция возвращает согласованные поля на тестовом аргументе и оставляет исходные `is_done` без изменений.
- **Опора для практики:** перечень ключей результата и трасса одного прохода; для проверки вызывать готовую функцию с явно заданным аргументом, не раскрывать список через `run()` и не менять его договор.
- **Переход:** процент использует часть и целое из этой сводки, но остаётся отдельным вычислением.

## 04. Доля и процент на понятной числовой модели

- **Что и зачем объяснить:** процент показывает, сколько составляет часть от целого на шкале из ста. Для задач частью является `completed`, целым — `total`: сначала сравниваем часть с полным количеством, затем выражаем эту долю «на сто». Не предполагать, что формула знакома из математики.
- **Механизм и порядок:** при `total > 0` обе записи корректны: `completed / total * 100` и `completed * 100 / total`. Первая сначала получает долю, вторая сначала умножает числитель; обе затем делят на полное число. В Python оператор `/` даёт дробное деление. Для реализации можно сохранить порядок целевого snapshot: сначала получить отношение, умножить на 100, затем округлить итоговый процент через `round(..., 1)`. Округление применяется один раз к проценту, а не к исходным счётчикам или промежуточной доле.
- **Независимый пример и типичная путаница:** представить 1 заполненную клетку из 4 как четверть, затем 25 из ста. Обе записи `1 / 4 * 100` и `1 * 100 / 4` дают `25.0`; перестановка части и целого `4 / 1 * 100` даёт неверные `400.0`, а `1 // 4 * 100` теряет дробную часть и даёт `0`. Преждевременное округление `round(1 / 3, 1) * 100` даёт `30.0`, а не `33.3`. Не объявлять умножение до деления ошибкой: `completed * 100 / total` также корректно при положительном `total`.
- **Первое самостоятельное действие:** для отношений 1/2 и 1/3 сначала назвать часть и целое, затем спрогнозировать процент при обеих корректных расстановках умножения и деления. Сравнить с ошибочными вариантами `total / completed`, `//` и округлением доли до умножения; объяснить, почему итоговое округление выполняется после перевода доли в проценты.
- **Опора для практики:** «выполнено / всего → доля → доля × 100 → округление до 1 знака».
- **Переход:** прежде чем делить, нужно определить, существует ли целое для этой доли.

## 05. Пустой список проверяем до деления

- **Что и зачем объяснить:** при `total == 0` отношение `completed / total` вычислить нельзя. Для договора Planner пустой список имеет процент `0.0`; это отдельное согласованное значение, а не результат деления на ноль.
- **Механизм и порядок:** `completion_percent(statistics)` сначала получает `total`. Если он равен нулю, функция немедленно возвращает `0.0`; только в другой ветви читает `completed`, вычисляет процент и округляет до одного знака. Порядок условия важен: проверка после деления не защищает пустой случай.
- **Независимый пример и путаница:** пустая корзина не имеет доли «яблок от всех фруктов»; договор приложения всё равно выбирает нулевое отображение. Не объяснять `0.0` как процент, автоматически полученный арифметикой, и не подменять пустой список делением на условную единицу.
- **Первое самостоятельное действие:** расположить проверку `total == 0` до вычисления дроби и предсказать результаты для пустого набора, половины и трети. Результат должен согласоваться с математическим смыслом и договором интерфейса.
- **Опора для практики:** «сначала `total == 0` → `0.0`; иначе `completed / total * 100`, затем `round(..., 1)`».
- **Переход:** теперь две функции имеют ясные входы и результаты; можно подключить их к существующей команде.

## 06. Команда stats соединяет расчёт и вывод

- **Что и зачем объяснить:** `run()` владеет одним полным `tasks` в течение запуска программы. План 19 уже задаёт `search_tasks` как источник выборки для показа, не заменяющий основной список. Ветка `stats` должна передать в `build_statistics` именно полный `tasks`, затем передать словарь в `completion_percent` и вывести четыре показателя; отдельный постоянный `handle_stats` не нужен.
- **Механизм и порядок:** команда уже нормализована известным `strip().lower()`. После `search` список совпадений существует только для результата поиска; он не становится состоянием Planner и не меняет `tasks`. В ветви `stats` заново считаются все карточки из полного списка, затем вычисляется процент и печатаются подписи «Всего», «Выполнено», «Осталось», «Процент выполнения». Функции расчёта возвращают значения, печатает интерфейсная ветвь. Не передавать `matches` в статистику, не возвращать наружу список из `run()` и не создавать второй `tasks`.
- **Независимый пример и типичная путаница:** в списке две задачи, поиск находит только одну, и затем вызывается `stats`. Верная статистика остаётся по двум карточкам; если посчитать только выборку, получится ложная сводка для одной. Повторный `stats` без изменения списка не меняет значения; после `add` или `done` следующий вызов отражает новое состояние. Не превращать `calculate_study_minutes` в команду `calc` или статистику задач.
- **Первое самостоятельное действие:** спрогнозировать `search` по фрагменту одной из двух задач, затем полный `stats`; назвать ожидаемые `2/1/1/50.0` и ошибочные `1/1/0/100.0`, если в статистику передана только найденная карточка. После этого спрогнозировать повторный `done` и добавление третьей задачи.
- **Опора для практики:** цепочка вызовов `run → build_statistics(tasks) → completion_percent(statistics) → print`; отдельно проверять поля возвращённой сводки и строки вывода.
- **Переход к практике:** реализовать обе вычислительные функции, подключить последнюю команду и проверить её на настоящем списке, полученном через знакомые действия.

2. **Получить процент из результата сводки:** после блоков 04–05 реализовать `completion_percent(statistics)`, используя результат первой функции. Проверить пустой случай, половину, треть и полностью выполненный список. Наблюдаемый результат: соответственно получаются договорные значения `0.0`, `50.0`, `33.3` и `100.0`; пустой знаменатель не делится, счётчики не меняются.
3. **Подключить stats к текущему меню и проверить полный список после search:** после блока 06 добавить расчёт в ветвь `stats` существующего `run()`, не создавать отдельный обработчик. Добавить две задачи с разными названиями, выполнить одну, затем найти фрагмент только её названия командой `search`. Поиск должен показать одну карточку; сразу после него запросить `stats`. Наблюдаемый результат: статистика охватывает обе задачи и даёт `2/1/1/50.0`, тогда как расчёт только по поисковой выборке ошибочно дал бы `1/1/0/100.0`. Проверить, что `list` всё ещё показывает обе исходные записи и что поиск не изменил их. Повторно выполнить `done` для уже выполненной задачи и запросить статистику ещё раз: счётчики остаются `2/1/1/50.0`. Добавить третью задачу и повторить сводку: `3/1/2/33.3`.

Каждая часть начинается после объяснения соответствующего механизма; примерные данные для объяснения отличаются от проверочных данных. Если переданная точка A не обнаружена, нельзя подменять отсутствующие `add`/`done` готовым финальным кодом или объявлять интеграцию принятой: независимое объяснение и проверка логики функций остаются возможными, а зависимость от предыдущей практики фиксируется до её подтверждения. После содержательного изменения сверить запуск и `git status`/diff; сохранение проекта следует уже объяснённому ученику порядку и выбранному формату курса.

**Итоговый критерий B:** по команде `stats` один и тот же список даёт четыре актуальных значения; функции отдельно возвращают счётчики и процент, пустой список даёт `0.0`, повторное `done` не ведёт себя как новое завершённое состояние, новые задачи отражаются в следующей сводке. Никакие новые команды, постоянное хранение или функции вне договора не добавляются.
