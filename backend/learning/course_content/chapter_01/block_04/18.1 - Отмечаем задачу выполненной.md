## Место в маршруте

Занятие продолжает готовый поиск задачи по id: из пользовательского ввода получается положительное число, `find_task` возвращает исходную запись или `None`. Теперь добавляется одно действие, меняющее состояние найденной задачи. Следующее занятие использует обновлённый Planner для поиска нескольких задач по названию. Не добавляем второй цикл поиска и не меняем модель задачи.

## Точка A: подтверждённая опора

- **Уже изучено:** В доступных записях есть знания о функциях, словарях, булевых значениях, условиях, ссылках и мутации, но эти записи относятся к прежней карте курса. Методичка запрещает считать другой вариант курса подтверждением освоения в текущем маршруте. Поэтому фактическое освоение соответствующих тем по новой карте отдельно не подтверждено; в теории предусмотрено короткое восстановление нужных связей до применения.
- **Состояние проекта:** По концепту к занятию 18.1 в основном StudyHub уже должны быть `read_task_id` и `find_task` из занятия 18, прежние компоненты B3 и общий список `tasks`. Найденная запись — словарь из этого списка. Это целевая опора маршрута, а не подтверждённое состояние локального проекта: план занятия 18 заполнен и описывает `read_task_id`, `find_task` и `handle_find`, но наличие плана не подтверждает его прохождение или фактический checkpoint ученика. В локальной истории StudyHub есть кандидат на B3 — commit `45d0096fe4a1b66bce6a0a3557e9712c598ee965`, с четырьмя компонентами и старым демонстрационным циклом; он не подтверждает фактический checkpoint после занятия 18. Текущая вершина репозитория значительно позднее, а snapshot финала главы уже содержит `done`, поэтому ни один из них не выдаётся за вход занятия.
- **Планируемая опора или неясность:** Использовать как предпосылку описанный в BLOCK_4 результат занятия 18: reader id и поиск исходной записи/`None`. Перед практикой требуется сверить реальный файл с этой опорой. Если в фактической версии `find_task` не возвращает запись либо `read_task_id` не готов, зависимую практику нельзя считать подготовленной; сначала нужен соответствующий предыдущий результат. Цель и порядок блока не меняются.

## Точка B: результат занятия

- **Ученик сможет объяснить:** почему результат `find_task` связан с записью в `tasks`; почему изменение копии не меняет состояние приложения; как отличить булев результат «запись найдена» от значения поля `is_done`; почему повторная команда не создаёт новое событие.
- **Ученик сможет сделать:** повторно использовать поиск, проверить отсутствие записи до доступа к её полям, изменить только `is_done` найденной задачи и передать результат в handler.
- **Результат в проекте:** `mark_task_done` и `handle_done` подключены к команде `done`; найденная задача получает состояние выполнения, остальные записи и поля остаются прежними.
- **Как подтвердим:** изменение видно через прежние `list` и `find`; неизвестный id не меняет список; повторное `done` оставляет статус True и не меняет число записей.

## Границы и передача дальше

- **Пока не требуем:** новый алгоритм поиска, поиск по названию, копирование списка/записи, отдельную функцию для события перехода, хранение между запусками, классы или новую архитектуру. Не перехватываем широким `except` ожидаемый `None`.
- **Передаём следующему занятию:** рабочие add/list/find/done и общее состояние задач; готовый done остаётся без повторного поиска и не повреждает другие карточки. Занятие 19 добавит поиск совпадений по названию.

## 00. Вступление

Когда запись уже найдена, следующий шаг — применить к ней намерение пользователя и проверить, что приложение изменило именно нужные данные. Одного сравнения id недостаточно: мы должны понять, что возвращает поиск, где живёт запись и какой результат сообщает операция.

1. **Точка старта:** после занятия 18 поиск по id возвращает исходную задачу либо `None`; список задач уже принадлежит текущему запуску.
2. **Новый вопрос:** как отметить выбранную запись выполненной, не повторяя поиск и не затрагивая соседние задачи?
3. **Результат:** команда `done` адресно меняет `is_done`, сообщает об исходе и сохраняет работоспособность list/find.

Поэтому сначала восстановим путь найденного словаря через локальные имена, затем разберём мутацию исходной записи и смысл True/False. В конце свяжем эти части в одном пользовательском действии.

## 01. Одно действие, несколько ролей

- **Что и зачем объяснить:** отделить предметную операцию от диалога. Модельная функция получает общий список и id, handler отвечает за чтение и сообщение, а `run` выбирает команду. Это не три копии одной логики.
- **Механизм и порядок:** проследить поток от команды `done` к `handle_done`, reader id, `mark_task_done`, уже существующему `find_task` и обратно к результату для handler. Все вызовы используют тот же `tasks`, который создал `run`; новый поиск внутри модели не вводится.
- **Пример и типичная путаница:** на схеме изолировать путь одного id через уже имеющиеся роли. Не считать, что `handle_done` сам ищет и меняет задачу, или что вызов `find_task` создаёт копию словаря.
- **Первое самостоятельное действие:** по короткой трассе назвать, кто читает id, кто находит запись, кто меняет поле и кто сообщает пользователю результат. Наблюдаемый итог — роли названы без дополнительного цикла.
- **Опора для повторного обращения:** восстановить цепочку «команда → handler → reader → модельная операция → поиск → результат → сообщение» и проверить, что общий `tasks` передаётся явно.
- **Переход к следующему шагу:** модельная операция может опираться на поиск только после того, как обработан его второй допустимый исход — отсутствие задачи.

## 02. Найденная запись или None

- **Что и зачем объяснить:** напомнить договор `find_task`: найденный словарь или `None`. Показать, зачем проверить отсутствие до обращения к `is_done` и почему второй цикл поиска создаст лишнюю реализацию.
- **Механизм и порядок:** reader сначала обеспечивает положительный целый id; наличие такого id в списке — отдельный вопрос. Модельная операция вызывает готовый поиск один раз. Если записи нет, она возвращает False, не читая и не меняя поля. Если запись есть, дальнейшая операция работает с результатом поиска.
- **Пример и типичная путаница:** сравнить положительный, но отсутствующий id с найденным id. Положительное число ещё не означает существование задачи. Нельзя читать поле у `None`, а «не найдено» не требует фиктивной пустой записи.
- **Первое самостоятельное действие:** предсказать исход операции для двух исходов поиска до просмотра результата, затем объяснить, в какой ветви доступ к полю безопасен. Результат — корректный отсутствующий id распознан без обращения к полям.
- **Опора для повторного обращения:** сначала выяснить, вернул ли поиск словарь или `None`; только для словаря переходить к состоянию. Не смешивать проверку формата id с проверкой его наличия.
- **Переход к следующему шагу:** когда найдена исходная запись, нужно понять, почему изменение её поля заметно через список и другие команды.

## 03. Ссылка ведёт к общей записи

- **Что и зачем объяснить:** восстановить различие между ссылкой на тот же изменяемый словарь и отдельной копией. `find_task` возвращает исходную запись, которая уже находится внутри `tasks`.
- **Механизм и порядок:** проследить один и тот же объект под двумя именами: элемент списка и локальный результат поиска. Присваивание нового значения полю словаря меняет общий объект; последующее чтение через list/find видит его новое состояние. Копия была бы отдельной записью и не обновила бы приложение.
- **Пример и типичная путаница:** использовать независимую карточку с двумя именами и одним изменяемым полем. Сравнить изменение исходного словаря с изменением его копии; не переносить это правило на неизменяемые значения или глубокое копирование вложенных структур.
- **Первое самостоятельное действие:** самостоятельно проследить, какое из двух имён увидит присваивание поля, и сопоставить ожидаемое состояние с коротким наблюдением. Итог — назван исходный общий объект, а не только одинаковое содержимое.
- **Опора для повторного обращения:** перед операцией назвать объект, который вернул поиск; после неё прочитать ту же запись через список. Равенство содержимого само по себе не подтверждает идентичность.
- **Переход к следующему шагу:** изменение общего объекта задаёт эффект, но функция отдельно сообщает вызывающему коду, найден ли адресат.

## 04. Меняем только состояние задачи

- **Что и зачем объяснить:** показать адресное изменение одного поля `is_done` на найденной записи. Различить статус карточки и все остальные её данные.
- **Механизм и порядок:** после успешного поиска присвоить полю состояния значение True. Не создавать новую задачу и не менять id, title, priority, порядок или число элементов. Уже True остаётся True: операция устанавливает состояние, а не переключает его туда и обратно.
- **Пример и типичная путаница:** на двух разных карточках сначала изменить одну, затем прочитать обе. Различить «установить выполнена» и «переключить флаг»: повторное действие не должно возвращать её в незавершённое состояние.
- **Первое самостоятельное действие:** на трассе с двумя самостоятельными записями определить ожидаемое изменение полей выбранной и соседней. Затем сверить только затронутые данные. Результат — ровно одно поле одной записи стало True.
- **Опора для повторного обращения:** сверить выбранный id, состояние до и после, затем неизменность остальных полей и соседних записей. Для уже True операция сохраняет True.
- **Переход к следующему шагу:** handler должен сообщить результат операции, не выводя из булева ответа, произошло ли новое изменение именно сейчас.

## 05. Булев ответ означает наличие записи

- **Что и зачем объяснить:** определить договор `mark_task_done`: False означает, что поиск не нашёл запись; True — запись найдена и обработана. Это не счётчик новых завершений и не копия поля `is_done`.
- **Механизм и порядок:** после успешного поиска функция обновляет состояние и возвращает True. Повторный вызов на той же задаче тоже возвращает True, потому что запись существует; поле остаётся True. Handler выбирает сообщение по результату операции. Не добавлять отдельный контракт «поменялось ли значение».
- **Пример и типичная путаница:** сопоставить найденную незавершённую, найденную уже завершённую и отсутствующую задачу. Не путать `True` как ответ «задача найдена» с True в `is_done`, хотя на успешном пути оба значения совпадают.
- **Первое самостоятельное действие:** объяснить значение результата для каждого из трёх случаев, отдельно предсказав значение поля и булев ответ. Критерий — повторное действие не представлено как второе событие завершения.
- **Опора для повторного обращения:** сначала прочитать договор функции — «найдена/не найдена», затем проверить состояние задачи отдельным чтением через list/find.
- **Переход к следующему шагу:** связываем возвращаемый результат с готовым reader и ветвью команды, сохраняя границу handler/model.

## 06. Команда done в существующем цикле

- **Что и зачем объяснить:** встроить handler в существующее меню без дублирования предметного действия. Reader повторяет вопрос только для некорректного числового ввода; корректный, но отсутствующий id обрабатывает операция.
- **Механизм и порядок:** handler читает id через готовый reader, вызывает `mark_task_done` и по bool выводит подходящее сообщение. Ветка `done` в `run` вызывает handler; общие `tasks` остаются теми же для add/list/find/done. Не ловить общий `Exception` для ожидаемого отсутствия.
- **Пример и типичная путаница:** пройти две трассы CLI: найденная задача и корректный положительный id без совпадения. После каждой вернуться к list/find. Не добавлять поиск в handler, не использовать статус поля вместо результата операции и не менять прежние сообщения/команды без причины.
- **Первое самостоятельное действие:** по готовой схеме объяснить порядок вызовов для обеих трасс и предсказать видимый результат следующего list/find. Затем самостоятельно связать роли в проекте. Итог — `done` использует существующий reader и поиск.
- **Опора для повторного обращения:** reader проверяет положительный int; `find_task` проверяет наличие; bool операции выбирает сообщение; прежние list/find показывают данные.
- **Переход к практике:** механизм и интерфейс готовы; теперь ученик вносит операцию в ту же историю StudyHub и проверяет сохранность прежней работы.

## 07. Что мы будем делать в практике

**Формат и исходная опора:** основной локальный StudyHub. Начинаем с проекта после блока 3 и занятия 18: четыре сохранённых компонента B3, общий список задач, готовый `read_task_id` и `find_task`. Последние два шага по концепту ожидаются, но их фактический checkpoint до начала занятия не подтверждён; перед выполнением зависимой практики сверить опору. Всё исследование проводится в этом же проекте и истории.

Подключим действие завершения как один новый путь через уже готовый поиск. Работа идёт от модельного изменения к handler и наблюдению результата через имеющиеся команды.

1. **Добавить адресную модельную операцию:** начать с готового `find_task` и двух независимых задач; опора — разделы 02–05 и прежние знания о словаре/ссылках, если подтверждены текущим маршрутом. Ученик самостоятельно применяет поиск к переданному id, обновляет только найденную запись и возвращает bool по договору. Наблюдаемый результат: выбрана вторая запись, её `is_done` стало True, первая и остальные поля сохранились; отсутствующий id не изменил данные.
2. **Подключить пользовательское действие:** от готового reader и меню добавить `handle_done` и ветвь команды, не создавая второго поиска. Опора — разделы 01, 02, 05 и 06. Ученик связывает ввод, операцию и сообщение. Наблюдаемый результат: найденная задача получает подтверждение, корректный отсутствующий id обрабатывается без падения, list/find читают тот же общий объект.
3. **Проверить повтор и сохранность продукта:** на той же паре задач повторить `done`, прочитать обе записи и проверить обычные прежние команды. Опора — разделы 03–06 и существующие add/list/find. Ученик объясняет bool отдельно от изменения статуса. Наблюдаемый результат: повтор не переключил True обратно, не добавил запись и не изменил соседа; прежние возможности работают.

Пояснение после связанного списка: сначала появляется чистое модельное действие с готовым договором поиска, затем пользовательский handler, который использует его результат, затем проверяется совместное состояние через прежний интерфейс. Так мы отделяем причину изменения от сообщения и не дублируем уже изучаемый поиск.

Итоговый критерий всей практики: в одном локальном Planner команда `done` адресно завершает найденную задачу; `find_task` повторно не реализован; для отсутствующего id состояние остаётся неизменным; повторная команда сохраняет True; list/find показывают обновлённую задачу и прежнюю соседнюю без изменений. Прежние add/list/find продолжают работать. Не требуем поиска по названию из следующего занятия.

**Передача дальше:** к занятию 19 передаём реально изменяемое состояние задачи и работающий `done`. Фактическое начало зависимой практики остаётся условным до сверки реализации предыдущего занятия 18 с заявленной точкой A.
