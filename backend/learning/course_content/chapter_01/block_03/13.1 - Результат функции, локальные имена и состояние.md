# Результат функции, локальные имена и состояние

В предыдущем занятии мы определили `format_task(task)` и передали результат вызова коду снаружи. Теперь посмотрим, что ещё происходит во время вызова: какие имена остаются внутри функции, что именно возвращается и может ли функция изменить переданный объект.

## 00. От первого вызова к состоянию после вызова

У нас уже есть полная задача со словарём и функция, которая возвращает строку для показа. Но одной строки недостаточно, чтобы понять весь вызов: функция могла напечатать текст, изменить общий словарь или создать новый объект.

1. **Точка старта.** `format_task(task)` получает одну задачу и возвращает строку; модель задачи содержит `id`, `title`, `priority` и `is_done`.
2. **Новый вопрос.** Как различить результат функции, её вывод, локальные имена и изменение переданного объекта?
3. **Результат.** Мы объясним несколько отдельных вызовов и сохраним в `main.py` фабрику `create_task`, которая каждый раз возвращает независимый словарь полной задачи.

Мы начинаем со знакомого formatter и идём от одного вызова к объекту, который можно передать дальше. Сначала отделим видимый текст от значения и локальных имён, затем проверим, где остаются изменения. Фабрика станет итогом: она вернёт одну запись, а решение добавить её в общий список останется у кода приложения.

## 01. Место вызова получает значение из return

Когда функция выполняет `return value`, Python завершает текущий вызов и передаёт `value` туда, где функцию вызвали. Вызвавший код может сохранить это значение, передать дальше или показать его через `print`.

Представим вызов как заказ в мастерской: аргумент описывает работу, а `return` передаёт готовый результат обратно к месту вызова. `print` похож на объявление на стенде: мы видим текст, но вызывающий код не получает объявление вместо значения. Граница аналогии: функцию исполняет Python, а не мастер; `return` сам не сохраняет результат, поэтому мы присваиваем его имени или передаём дальше.

```python
def double(value):
    answer = value * 2
    return answer

result = double(4)
print(result)
```

В `double(4)` параметр `value` получает `4`, локальное имя `answer` получает `8`, а `return` передаёт `8` в присваивание `result`. Последняя строка выводит `8`. `return` завершает этот вызов `double`, после чего выполнение продолжается со строки после вызова.

`print` выполняет другую работу: показывает значение человеку. Сам вызов `print` не передаёт напечатанное значение вызывающему коду. Поэтому функция, которая только печатает, при присваивании результата вернёт `None`:

```python
def show_title(title):
    print(title)

printed_result = show_title("Изучить SQL")
print(printed_result is None)
```

Сначала появится `Изучить SQL`, затем `True`. Текст виден в терминале, а `printed_result` содержит `None`. Если у функции нет `return` или выполнение доходит до конца без `return`, результатом этого вызова будет `None`. Запись `return` без значения тоже возвращает `None`.

Если значение возвращается только в одной ветке, другая ветка тоже доходит до конца функции:

```python
def state_text(is_done):
    if is_done:
        return "выполнена"
    return "открыта"
```

Обе ветки здесь возвращают строку. Если убрать `return "открыта"`, вызов с `False` вернёт `None`. `None` означает отсутствие результата. Это не то же самое, что пустая строка, пустой список, пустой словарь или число `0`. Если строка нужна по договору, нужно исправить путь возврата, а не подставлять случайное запасное значение.

При `True` первый `return` завершает вызов сразу, поэтому до нижнего `return` выполнение не доходит. При `False` условие пропускается и срабатывает нижний возврат.

Наличие `return` в одной ветке ещё не обещает строку для всех входов. Если строка нужна по договору, мы прослеживаем каждую достижимую ветку до возврата. Когда функция заканчивается без значения, вызывающий код получает `None`; это сигнал, что результата нет, а не пустая допустимая задача. Для проверки пишем `value is None` и сначала решаем, как вызывающий код должен обработать отсутствие результата.

## 02. Каждый вызов получает свои локальные имена

Параметр и имена, созданные внутри функции, относятся к текущему вызову. При следующем вызове с тем же исходным кодом появляются новые локальные имена:

```python
def make_label(task):
    label = task["title"].strip()
    return label

first = make_label({"title": "  Изучить SQL  "})
second = make_label({"title": "Повторить цикл"})
print(first)
print(second)
```

Первый вызов создаёт свои `task` и `label`, второй вызов создаёт другие локальные `task` и `label`. Снаружи доступны имена `first` и `second`, потому что мы сами присвоили им результаты. Внутреннее имя `label` автоматически наружу не переносится. Если попытаться прочитать такое имя снаружи и до этого не создать его там, Python сообщит `NameError`.

Одинаковые написания не делают внутреннее и внешнее имя одной переменной. Присваивание параметру нового значения меняет только локальную связь текущего вызова. Чтобы использовать вычисленное значение снаружи, функция возвращает его, а вызывающий код сохраняет результат.

Мы отделяем время жизни имени от времени жизни объекта. После завершения вызова локальные имена больше нельзя прочитать снаружи, но переданный список или словарь может остаться доступен через другое имя. Следующий вызов получает собственные локальные связи, даже если мы снова используем слова `task` и `label`. Это не означает, что Python скопировал каждый переданный объект.

Представим каждый вызов как отдельный рабочий стол: на нём есть свои карточки с именами `task` и `label`. Если мы явно вернули значение, вызывающий код получает его; остальные локальные имена наружу сами не переносятся. Граница аналогии: в Python нет настоящих столов, а переданное имя может указывать на общий объект.

## 03. Параметр связывается с объектом, а не с его копией

При вызове с изменяемым значением параметр получает ссылку на переданный объект. Python автоматически не создаёт копию словаря или списка. Поэтому важно отличать переприсваивание параметра от изменения самого объекта.

```python
def rebind_local(task):
    task = {"title": "Черновик"}

def edit_shared(task):
    task["title"] = "Черновик"

task = {"title": "Изучить SQL"}
rebind_local(task)
print(task["title"])
edit_shared(task)
print(task["title"])
```

После `rebind_local(task)` снаружи всё ещё хранится `Изучить SQL`: новое значение получил только локальный параметр. `edit_shared(task)` изменяет поле того же словаря, поэтому после вызова снаружи видно `Черновик`.

Представим словарь как карточку в общем бумажном каталоге, а параметр как временную метку, указывающую на ту же карточку. Переклеить метку внутри функции не значит заменить карточку в каталоге; изменить надпись на самой карточке увидят те, кто использует этот объект. Граница аналогии: в Python нет бумажных меток, но она помогает отличить новую связь имени от изменения объекта.

Если изменение должно стать отдельным результатом, можно сначала сделать поверхностную копию, изменить её и вернуть:

```python
def with_new_title(task):
    updated = task.copy()
    updated["title"] = "Черновик"
    return updated
```

Тогда вызывающий код должен сохранить возвращённый словарь. Исходный словарь останется прежним, а `updated` будет отдельным верхним объектом. `copy()` не обещает глубокое клонирование вложенных изменяемых объектов. Модель задачи в этом курсе плоская, поэтому для показанного изменения поля достаточно копии верхнего словаря.

После вызова мы сохраняем отдельный результат, например `updated = with_new_title(task)`. Если просто вызвать функцию и отбросить возврат, новый словарь не заменит исходный. Копия отделяет верхний словарь, но вложенный список или словарь мог бы остаться общим для обеих записей. Поэтому мы обещаем поверхностную копию и проверяем именно те поля, которые изменяем, а не полную независимость на любой глубине.

Функция может намеренно изменить общий список или словарь и при этом вернуть `None`. Это допустимый договор для действия, которое меняет объект на месте. Другая функция может вернуть новый объект и оставить исходный без изменений. Один канал не подменяет другой: отдельно проверяем значение из `return` и состояние объекта после вызова.

## 04. Фабрика возвращает отдельную запись

Функция-фабрика создаёт и возвращает новый объект. Например, два вызова небольшой фабрики могут вернуть словари с одинаковым содержимым, но это будут разные словари:

```python
def make_note(text):
    return {"text": text}

first = make_note("проверить задачу")
second = make_note("проверить задачу")
print(first == second)
print(first is second)
first["text"] = "изменено"
print(second["text"])
```

Сначала выводятся `True` и `False`: `==` сравнивает содержимое, `is` проверяет, указывают ли два имени на один объект. Изменение `first` не меняет `second`, потому что вызовы создали разные словари. Для сравнения идентичности объектов используем `is`; для обычного сравнения значений используем `==`.

В нашем проекте постоянная фабрика называется `create_task(task_id, title, priority)`. Она получает уже проверенные значения и возвращает полную задачу с полями `id`, `title`, `priority` и `is_done`, где начальное состояние равно `False`. Фабрика создаёт один новый словарь за вызов. Она не читает `input`, не выбирает следующий id, не печатает сообщение и не добавляет запись в список. Решение, принять ли готовую задачу в список, остаётся у вызывающего кода.

Если функция поиска в будущем не найдёт запись, она сможет вернуть `None`. Это будет означать «объект не найден», а не «найдена пустая задача». Перед чтением полей вызывающий код должен учитывать такой договор. Пустой словарь всё равно является объектом, а `None` обозначает отсутствие результата; алгоритм поиска в этом занятии не реализуем.

Значения для фабрики уже подготовил вызывающий сценарий. Поэтому она не очищает заголовок и не подставляет название по умолчанию, если вход оказался неверным. Иначе правило пришлось бы искать внутри создания объекта, а не в месте проверки данных. Прозрачный контракт позволяет проверить два разных набора входов, затем повторить один набор: содержимое совпадёт, но каждый вызов создаст новый словарь.

Тело фабрики выполняется заново при каждом вызове, поэтому словарь создаётся заново, а не берётся из скрытой общей записи. Список задач не передаётся в фабрику и внутри неё не меняется. Если приложение принимает запись, отдельный вызывающий код решает, куда её сохранить; создание объекта само по себе не добавляет его в коллекцию.

Проследим два вызова от общего входа до результата: каждый возвращает отдельную запись. Изменение поля первой задачи остаётся в ней, а вторая сохраняет своё состояние.

## 05. Ошибка: напечатанное значение приняли за результат

Рассмотрим вызов, который печатает название, но ничего не возвращает:

```python
def show_label(label):
    print(label)

result = show_label("Повторить Python")
print(result.upper())
```

Первая строка видна, но `result` равен `None`. У `None` нет метода `upper`, поэтому возникает `AttributeError`. Ошибка появляется не потому, что печать не сработала, а потому, что вызывающий код ожидал от неё возвращённую строку. Исправление зависит от нужного договора: если дальше нужна строка, производитель должен её вернуть; если функция только показывает текст, её результат не нужно использовать как строку.

Проследим границу сбоя по шагам: `show_label` печатает строку, затем присваивание получает `None`, а последняя строка ищет `upper` у значения без этого метода. Ошибка видна у потребителя, хотя несовпадение началось раньше: вызывающий код ожидал строку, а функция не вернула её. Мы исправляем договор производителя или потребителя, не маскируем отсутствие результата запасной строкой.

Мы проверяем два независимых вопроса: что функция вернула и что стало с переданными объектами. Правильный вывод сам по себе не доказывает, что состояние осталось неизменным.

## 06. Переносим фабрику в прежний проект

`format_task(task)` из прошлого занятия остаётся в `main.py`. Рядом с ней мы добавим `create_task`, но не будем переписывать форматирование или помещать исследовательские функции изменения объектов в рабочий сценарий.

После сохранения файла запускаем знакомую оболочку:

```text
python -i main.py
```

Сначала завершаем обычный сценарий приложения его прежней командой выхода. После появления приглашения `>>>` проверяем функцию несколькими наборами уже подготовленных значений. Затем вызываем её повторно с теми же значениями, сравниваем содержимое и идентичность двух результатов, меняем состояние первой задачи и проверяем вторую. В фабрике остаётся только создание одной полной записи; добавление в общий список выполняет вызывающий код.

Команду `python -i main.py` запускаем в терминале. Приложение сначала выполняется как раньше; после штатного выхода появится приглашение `>>>`, где мы вводим уже Python-код, а не команды меню или терминала. Проверочные вызовы остаются временными, если мы сами не добавили их в файл. Так мы проверим фабрику, не превращая исследование в новую возможность Planner.

## 07. Что мы будем делать в практике

Сначала разберём поведение вызова, затем применим его к прежнему проекту.

1. **Предскажем.** Запишем точный вывод и значения вызовов, отдельно отметим, что напечатано, а что вернулось.
2. **Проследим.** Проверим локальное имя, общий словарь и копию, затем сохраним результат вызова снаружи функции.
3. **Создадим.** Добавим в прежний `main.py` фабрику `create_task(task_id, title, priority)` с четырьмя полями задачи.
4. **Проверим.** Сравним несколько вызовов, независимость двух записей и работу прежних `calc` и `format_task`.

Так мы сначала получим объяснимую модель вызова, а затем применим её к одной постоянной функции проекта. Проверка состояния подтвердит, что фабрика создаёт отдельную задачу, не читает ввод, не печатает и не добавляет запись в список. Следующее занятие соединит эти правила по обязанностям.
