# 15. Ошибки, traceback и отладка

## 00. От работающих функций к поиску причины

В предыдущей работе мы соединили `normalize_title`, `create_task`, `format_task` и `calculate_study_minutes` с прежним сценарием `calc`. Теперь посмотрим, что делать, когда одна функция передала другой значение не по договору.

Traceback (трассировка) показывает путь вызовов к ошибке, её тип и сообщение.

1. **Прежняя опора.** В `main.py` есть постоянные функции, данные и рабочие сценарии `calc` и `exit`.
2. **Новый вопрос.** Как понять, в какой части цепочки появилось неверное значение, и исправить причину, а не скрыть сообщение об ошибке?
3. **Проверяемый результат.** Мы читаем traceback, воспроизводим дефект на коротком примере, меняем одну причину и проверяем ошибочный, обычный и граничный сценарии.

В следующей работе мы будем строить меню поверх этих компонентов. Поэтому к её началу `main.py` должен остаться рабочим, без временной диагностической печати и подавленных дефектов.

## 01. Ошибки бывают разными

**Вопрос:** Если программа ведёт себя неверно, всегда ли появится traceback?

Нет. Сначала определим, какой именно результат наблюдаем.

- **`SyntaxError`, синтаксическая ошибка.** Python не может разобрать структуру файла. Проверяем двоеточие, скобки, кавычки, отступ и строку выше указателя.
- **Ошибка выполнения.** Программа остановилась во время работы. Читаем последнюю строку traceback, кадры вызовов и фактические данные.
- **Логическая ошибка.** Программа завершилась, но получила неверный результат. Сравниваем результат и состояние с правилом задачи.

**Предскажем выполнение:** успеет ли выполниться первый `print`, если ниже пропущено двоеточие?

```python
print("Старт")
if 5 > 3
    print("Условие истинно")
```

**Ответ:** нет. Python сначала разбирает структуру всего файла. Из-за `SyntaxError` исполнение файла не начинается, поэтому мы не увидим даже `Старт`. Указатель ошибки может находиться на следующей строке, а причина быть в строке выше.

Логическая ошибка устроена иначе. Например, функция может без ошибки заменить пользовательское название на строку в нижнем регистре. В таком случае traceback не появится: сравним фактический результат с обещанием сохранить регистр.

## 02. Traceback показывает путь к месту проявления

Traceback содержит кадры вызовов, по которым программа дошла до места ошибки. Каждый кадр показывает один вызов. Сначала посмотрим на краткий пример с заметкой. Создатель вернул текст, а функция заголовка ожидает ещё и имя автора.

```python
def make_note():
    return {"text": "Проверить список"}

def note_heading(note):
    return f"{note['author']}: {note['text']}"

def show_note():
    note = make_note()
    print(note_heading(note))

show_note()
```

Упрощённый traceback:

```text
Traceback (most recent call last):
  File "main.py", line 11, in <module>
    show_note()
  File "main.py", line 9, in show_note
    print(note_heading(note))
  File "main.py", line 5, in note_heading
    return f"{note['author']}: {note['text']}"
KeyError: 'author'
```

Последняя строка называет тип и причину, замеченную Python: ключа `author` нет. Кадры выше показывают путь вызовов. Строка в `note_heading` показывает место проявления, а `make_note` создал неполную заметку. Если поле обязательно, восстанавливаем модель в источнике. Мы не меняем чтение на случайное запасное значение только ради исчезновения ошибки.

**Порядок чтения:**

1. Читаем последнюю строку и называем тип ошибки.
2. Находим ближайшую строку нашего файла, где она проявилась.
3. Поднимаемся по кадрам вызовов и ищем, откуда пришло значение.
4. Проверяем данные и формулируем нарушенное предположение.

Traceback сужает поиск, но сам по себе не доказывает, что строка проявления содержит первопричину. Ошибка потребителя часто начинается с неполного результата производителя.

## 03. Тип ошибки задаёт следующий вопрос

Тип ошибки помогает выбрать, что проверить. Он не является готовым исправлением.

- **`SyntaxError`.** Проверяем структуру строки и соседние скобки, кавычки, отступы. Например, в `if` нет двоеточия.
- **`NameError`.** Проверяем опечатку, регистр и доступность имени в функции. Например, написали `Title`, хотя переменная называется `title`.
- **`TypeError`.** Проверяем типы операндов и допустимость операции или вызова. Например, складываем строку и число.
- **`ValueError`.** Проверяем содержимое значения допустимого типа. Строка `"семь"` не преобразуется в целое число.
- **`IndexError`.** Проверяем длину последовательности и существование позиции. Например, читаем `items[0]` из пустого списка.
- **`KeyError`.** Проверяем фактические ключи и место, где создан словарь. Например, читаем обязательный ключ, которого нет в записи.

Сравним два ошибочных выражения:

```python
"18" + 1
int("восемнадцать")
```

Первое вызывает `TypeError`: операция сложения не подходит строке и числу. Второе вызывает `ValueError`: строка является допустимым аргументом `int`, но её содержимое не записывает целое число. Эти ошибки не говорят, что одно из выражений является предпочтительным способом работы.

**Сопоставим пример и первый вопрос для проверки:**

- `print(Title)`: где и под каким именем создано значение?
- `"18" + 1`: каковы типы обоих значений?
- `int("семь")`: можно ли преобразовать это содержимое?
- `["SQL"][1]`: есть ли в списке такой индекс?
- `{"title": "SQL"}["priority"]`: обязательно ли поле и кто должен его создать?

## 04. Проверим значение и уменьшим пример

Когда сообщение не объясняет всю цепочку, временно посмотрим на значение, его тип и ключи словаря.

Для временной диагностической печати добавим метку `DEBUG`, то есть служебную строку отладки.

```python
task = {"id": 7, "title": "Изучить SQL"}
print("DEBUG task:", task)
print("DEBUG type:", type(task))
print("DEBUG keys:", list(task.keys()))
```

Такая печать отвечает на конкретные вопросы: что передали, какого оно типа и какие поля есть. После проверки диагностические строки удаляем. Они не являются форматом задачи или постоянным результатом программы.

Если пример велик, оставим только данные и вызовы, которые сохраняют ошибку. Такой короткий сценарий называется минимальным воспроизведением. Он помогает проверить одну гипотезу и не заставляет заново собирать Planner.

**Проверим гипотезу по шагам:**

1. Снова получить ту же ошибку на известном входе.
2. Наблюдать тип, значение или ключи перед местом проявления.
3. Назвать одно предположение, которое не совпало с фактом.
4. Изменить одну причину и повторить тот же вход.

Если сообщение поменялось, первая правка могла открыть ошибку, до которой программа раньше не доходила. Это новое наблюдение. Мы читаем его отдельно, а не откатываем причинное исправление наугад.

## 05. Обязательные поля не заменяем догадкой

`dict.get()` возвращает значение по ключу, а если ключа нет, может вернуть `None` или явно заданный запасной результат. Это удобно для необязательного поля. Для обязательного поля сначала сверяемся с моделью.

```python
task = {"id": 7, "title": "Изучить SQL"}
priority = task.get("priority")
print(priority + 1)
```

Здесь `KeyError` исчез, но `priority` стал равен `None`. Сложение всё равно нарушает правило. Если `priority` обязателен, создатель задачи должен вернуть его вместе с остальными полями. Если поле действительно необязательно, правило отсутствия и его результат должны быть определены заранее.

Для модели Planner мы проверяем четыре поля: `id`, `title`, `priority` и `is_done`. Если `format_task` сообщает о пропущенном ключе, смотрим на словарь, который получила функция форматирования, а затем на функцию или участок кода, создавший этот словарь. `format_task` не обязан угадывать недостающие данные.

## 06. Имя внутри функции и результат вызова

У локального имени есть своя область: оно доступно внутри вызова, где присвоено. Чтобы передать вычисленное значение вызывающему коду, функция должна его вернуть.

```python
def show_topic(topic):
    label = f"Тема: {topic}"
    print(label)

show_topic("Python")
print(label)
```

Здесь возникнет `NameError`: `label` создан внутри `show_topic` и не существует в вызывающем коде. Функция может пользоваться локальным именем и передать нужное значение снаружи через `return`.

```python
def rectangle_area(width, height):
    area = width * height
    return area

area_value = rectangle_area(4, 3)
print(area_value)
```

Функция считает число и возвращает его. `print` остаётся снаружи и показывает результат. Если удалить `return`, вызов даст `None`, даже если локальное имя `area` получило правильное число. `None` не является запасным нулём и не исправляет контракт функции.

**Предскажем результат, если убрать `return area`:**

```python
def rectangle_area(width, height):
    area = width * height

print(rectangle_area(4, 3))
```

**Ответ:** напечатается `None`. Локальное вычисление завершилось, но функция не передала площадь наружу.

Такую проверку используем и для уже знакомых функций. Проверяем `calculate_study_minutes([])`, чтобы получить ноль, и `calculate_study_minutes([20, 35])`, чтобы получить сумму. Затем убеждаемся, что функция не меняет переданный список.

## 07. Логическая ошибка может не дать traceback

Логическая ошибка может оставить программу работающей, но нарушить обещанное правило. Например, если название должно сохранить написание, перевод в нижний регистр даёт неверный результат без traceback.

```python
def make_display_title(title):
    return title.lower()

title = "Изучить SQL"
display_title = make_display_title(title)
print(title)
print(display_title)
```

Здесь исходная строка остаётся прежней, но показанное название теряет регистр. Сверяем результат с правилом, а не только проверяем, завершилась ли функция.

Если функция обещает отдельную обновлённую запись, отдельно проверяем её поля, исходный словарь после вызова и то, что исходный и новый объекты различаются. Для плоской модели достаточно отделить верхний словарь. Похожим образом проверяем `create_task`: два одинаковых вызова должны дать равные по полям, но независимые словари. Изменение первой записи не должно менять вторую. Это проверка состояния, а не только строки, которую показал `print`.

## 08. После одной правки проверим прежние сценарии

Повторная проверка после исправления называется регрессией. Недостаточно увидеть, что исчезло сообщение об ошибке: убеждаемся, что дефект устранён и прежние рабочие сценарии сохранились.

1. Снова запускаем вход, на котором проявлялась ошибка.
2. Проверяем обычный рабочий вход.
3. Проверяем пустое или граничное значение.
4. Повторяем соседнее поведение, которого могла коснуться правка.
5. Удаляем временные `DEBUG`-строки, просматриваем изменение и ещё раз запускаем программу.

В существующем `main.py` сохраняем `calc` и `exit`. Проверяем расчёт для нуля, одной и двух длительностей, два независимых расчёта в одном процессе, пустое название, неизвестную команду и штатный выход. Для числовых полей используем прежний ограниченный договор проекта. Это не обещание обработать любое содержимое ввода.

Не исправляем непонятный дефект случайным значением и не прячем его молчанием. Явный отказ по известному правилу отличается от значения, которое скрывает поломанную модель. Перехват исключений в этой работе не нужен.

## 09. Что мы будем делать в практике

Повторим исполняемый пример `show_note` из теории: зафиксируем единственный `KeyError: 'author'`, восстановим поле `author` у `make_note` и повторим тот же запуск. Затем отдельно разберём локальное имя снаружи функции и потерянный `return`, проверим отдельную копию без мутации исходного объекта.

Последний шаг перенесёт тот же порядок диагностики в наш постоянный `main.py`. Мы проверим известные функции и сценарии `calc` и `exit`, включая граничные случаи, удалим временную печать и сохраним рабочий файл. Готовый результат можно объяснить по цепочке: фактический вход, место проявления, причина, одна правка и повторная проверка.
