## Место в маршруте

Урок продолжает локальную историю, которую по паспортам 27–28 ученик должен был создать до этого шага: собственный пустой GitHub-репозиторий с clone, запускаемыми main.py и .gitignore, затем первый локальный commit. Результат становится входом занятия 13.2: в опубликованный Hello world-проект добавится normalize_title, а различие рабочей и подготовленной правки будет изучаться на реальном файле.

## Точка A: подтверждённая опора

- Уже изучено: доступные записи не подтверждают выполнение предыдущих занятий именно в новой версии курса. Журнал STUDYHUB_LEARNINGS.md фиксирует практику remote, push и сверки опубликованного commit в прежнем варианте; это лишь дополнительный знакомый контекст, не доказательство A текущего маршрута.
- Состояние проекта: по паспорту перед уроком должны существовать один собственный clone пустого remote, main.py с работающим Hello world, .gitignore с правилами для __pycache__/ и *.pyc, локальный commit и известные origin/текущая ветка. Самостоятельный проект ученика в новой последовательности здесь не подтверждён.
- Планируемая опора или неясность: планы, TSX и ручные практики занятий 12.1–13 заполнены; они описывают маршрут, но не доказывают выполнение учеником, а доступный журнал относится к прежней версии. Поэтому эту A считать ожидаемой по паспортам, а не доказанно освоенной. До зависимых действий проверить адрес, ветку и наличие commit. Если эти предпосылки отсутствуют, независимые объяснения можно пройти на безопасных примерах, но проектный push и подтверждение B заблокированы завершением занятий 12.1–13; не создавать remote или commit молча и не подменять проект авторским репозиторием C:/Project Python/studyhub.

## Точка B: результат занятия

- Ученик сможет объяснить: чем публикация commit отличается от сохранения файла и локального commit; что означают remote origin, текущая ветка и upstream; почему подпись автора, GitHub-учётная запись и право записи — разные вещи.
- Ученик сможет сделать: проверить свой remote и ветку, выполнить первый push с явным направлением для собственной ветки и подтвердить серверный результат.
- Результат в проекте: существующий локальный commit опубликован в собственном удалённом репозитории; файлы проекта не меняются.
- Как подтвердим: commit ID и ветка на GitHub соответствуют локальному HEAD, а серверные main.py и .gitignore содержат ожидаемую версию. Одного успешного сообщения push или чистого git status для подтверждения недостаточно.

## Границы и передача дальше

- Пока не требуем: повторно создавать репозиторий или clone, выполнять init, менять файлы проекта, создавать второй commit, добавлять normalize_title, клонировать опубликованный проект заново или чинить историю через force push. Не просим вставлять токены или другие секреты в команду, файлы или переписку.
- Передаём следующему занятию: тот же проект и опубликованный Hello world-коммит, подтверждённый remote и известную ветку. Занятие 13.2 добавит полезную функцию, затем будет прослеживать статус и diff; публикация текущего шага не заменяет будущую работу с изменениями.

## 00. Вступление

Ожидаемая точка A — рабочий файл и первый локальный commit в собственном clone. До проектной части ученик проверяет, что эта опора действительно есть. Затем разбирается, почему локальной истории недостаточно, чтобы увидеть версию на GitHub, и как проверить, что публикация относится к своему проекту и своей ветке.

1. **Точка старта:** ожидаемая опора занятий 12.1–13 — локальный commit с main.py и .gitignore, адрес origin и фактическая ветка; реальное состояние проверяется в начале занятия.
2. **Новый вопрос:** как передать именно эту версию на сервер и различить локальную готовность, вход в аккаунт и разрешение записи?
3. **Результат:** ученик публикует текущий commit в правильный remote и подтверждает его по серверной истории и файлам.

Весь маршрут использует один clone и один remote. Проверка адреса и ветки предшествует push; затем ученик устанавливает связь с удалённой веткой и проходит штатную авторизацию. В конце он сверяет фактический серверный commit, а не делает вывод по одному сообщению терминала.

## 01. Сохранённый файл, локальный commit и серверная копия

- Что и зачем объяснить: показать три разных состояния — изменения в файле, сохранённый локально commit и опубликованная серверная копия. Начать с безопасного примера, затем вернуться к main.py, если наличие clone подтверждено: запись файла не создаёт commit, commit сам по себе не меняет GitHub.
- Механизм и порядок: Git хранит локальную историю, GitHub хранит удалённую копию этой истории; push передаёт уже созданные commits. Незакоммиченные строки не становятся частью отправки автоматически. Не повторять весь урок про stage и commit — восстановить только различие, нужное для вопроса «что именно отправляется?».
- Пример и типичная путаница: локальный commit можно увидеть в истории при пустой или отстающей серверной ветке. git status описывает локальное состояние, а не доказывает публикацию.
- Первое самостоятельное действие: по короткой временной шкале ученик определяет, есть ли лишь сохранённый файл, локальный commit или уже подтверждённая серверная версия. Результат — называет недостающий шаг без запуска команд.
- Опора для повторного обращения: три состояния и вопрос к каждому — «файл сохранён?», «commit создан?», «серверная версия проверена?». Если push ещё не выполнялся, не делать вывод о публикации по локальному логу.
- Переход: чтобы передать нужный commit, сначала точно определить удалённый адрес и исходную ветку.

## 02. Проверяем origin и фактическую ветку

- Что и зачем объяснить: перед первой отправкой убедиться, что команды относятся к clone ученика и адресу его собственного пустого репозитория, созданного в занятии 12.1.
- Механизм и порядок: origin — привычное локальное имя remote, за которым стоит адрес; имя не гарантирует, что адрес правильный. Активная локальная ветка определяется в самом clone. Не считать, что она обязательно называется main, и не заменять её догадкой о ветке на GitHub.
- Пример и типичная путаница: origin может указывать на чужой или неверный проект; имя remote и имя ветки отвечают на разные вопросы. Сначала проверить путь открытого проекта, затем адрес origin и активную ветку, после этого сверить локальный commit.
- Первое самостоятельное действие: на подготовленном безопасном примере ученик сопоставляет alias, URL, локальную ветку и адрес назначения. Затем в своём проекте самостоятельно находит те же значения; наблюдаемый результат — может назвать точный проект и ветку для публикации.
- Опора для повторного обращения: где увидеть текущую ветку и адрес remote; характерная ошибка — воспринимать origin как имя аккаунта или без проверки использовать main.
- Переход: адрес и источник выбраны; теперь надо объяснить, как первый push задаёт направление и дальнейшую связь веток.

## 03. Первый push и upstream

- Что и зачем объяснить: дать смысл явному направлению первой публикации, прежде чем ученик запускает push.
- Механизм и порядок: сопоставить локальную ветку с веткой собственного remote и объяснить upstream как сохранённую связь, по которой Git дальше понимает обычное направление обмена. Для первого push явно назвать remote и обе стороны ветвления, используя фактическое имя локальной ветки. Это отправка commits, не копирование несохранённых файлов и не создание нового commit.
- Пример и типичная путаница: локальная ветка может называться не main; удалённая цель не должна выбираться автоматически по примеру. Upstream не является ещё одной копией проекта и не заменяет commit.
- Первое самостоятельное действие: ученик на карточке с двумя возможными ветками указывает источник, remote и назначение; затем по выводу собственного проекта формулирует направление своей отправки. Критерий — выбраны ветка, которую он проверил, и его remote, а не значения из чужого примера.
- Опора для повторного обращения: перед отправкой восстановить последовательность «свой clone → активная ветка → origin → удалённая ветка». При сообщении об отсутствующем upstream сначала проверить имя и назначение ветки.
- Переход: направление готово; перед отправкой отделить сведения об авторе commit от входа и прав на сервере.

## 04. Автор commit, вход в GitHub и право записи

- Что и зачем объяснить: разложить на три независимые роли, почему правильная локальная подпись не даёт автоматически доступ к remote.
- Механизм и порядок: user.name и user.email записаны в метаданных commit и описывают автора; HTTPS-авторизация подтверждает GitHub-аккаунт, которым выполняется сетевой запрос; право записи определяется доступом этой учётной записи к конкретному репозиторию. Публичность репозитория не означает право менять его. Для HTTPS использовать штатный менеджер учётных данных и переход в браузер, если он предлагается; секреты не копировать в команду.
- Пример и типичная путаница: commit может быть создан одним авторским именем, а push подтверждён другим аккаунтом. Это не одно и то же и не требует переписывать автора в локальной истории.
- Первое самостоятельное действие: по трём коротким ситуациям ученик определяет, что известно о подписи commit, кто проходит авторизацию и где проверять право записи. Критерий — не называет имя автора доказательством входа или доступа.
- Опора для повторного обращения: «кто указан автором?», «какой аккаунт подтверждает запрос?», «может ли он писать в этот remote?». Не просить сообщать секрет или вставлять его в материал.
- Переход: после штатного входа ученик выполняет запланированную публикацию, не меняя авторство уже созданного commit.

## 05. Разные причины отказа требуют разных проверок

- Что и зачем объяснить: показать, как читать отказ по его смыслу, а не подбирать случайные Git-команды.
- Механизм и порядок: различить неверный адрес/не тот репозиторий, отсутствие local commit или неверный refspec/ветку, проблему аутентификации и отсутствие права записи. Начать с безопасных сведений о проекте, URL и ветке; затем связать тип сообщения с соответствующей проверкой. Ошибка входа не исправляется переименованием автора, а отказ в правах — повторным созданием remote.
- Пример и типичная путаница: сообщение про вход и сообщение про запрет записи относятся к разным границам. Если remote неожиданно не пустой или адрес не совпадает с ожидаемым, остановить отправку и перепроверить целевой проект; не переписывать и не форсировать историю.
- Первое самостоятельное действие: ученик разбирает подготовленные фрагменты сообщений, выбирает безопасную следующую проверку и объясняет причину. Ничего намеренно не ломать в живом remote.
- Опора для повторного обращения: классификация «адрес/ветка и commit/аутентификация/право». При диагностике не подменять одну причину другой и не использовать destructive-команды.
- Переход: успешный push тоже нуждается в предметном доказательстве — проверке того, что сервер получил нужную версию.

## 06. Подтверждаем опубликованную версию

- Что и зачем объяснить: критерий завершения — соответствие локальной и удалённой версии, а не сам факт запуска команды.
- Механизм и порядок: найти опубликованную ветку и commit на странице собственного GitHub-репозитория; сравнить полный commit ID с локальным HEAD; открыть main.py и .gitignore и сопоставить их с ожидаемым содержимым. В этой точке удалённый репозиторий по A должен быть пуст до первого push, поэтому не ожидать слияния чужого README или иной начальной истории.
- Пример и типичная путаница: зелёный текст об успехе или чистый локальный status не подтверждает, что проверен нужный репозиторий и нужный commit. Укороченный ID полезен для ориентира, но финальная сверка должна однозначно указывать на текущий локальный commit.
- Первое самостоятельное действие: на примере двух веток ученик выбирает ту, где лежит отправленный commit, и сопоставляет ID и содержимое файла. Критерий — серверная версия совпадает с локальной по commit и двум файлам.
- Опора для повторного обращения: сверить адрес репозитория → ветку → commit ID → содержимое. Если любой элемент расходится, публикация ещё не подтверждена.
- Переход: ученик готов выполнить весь маршрут на собственном StudyHub и объяснить, что именно доказало результат.

## 07. Что мы будем делать в практике

**Формат и исходная опора:** локальный проект StudyHub, созданный в занятии 12.1 и имеющий первый локальный commit после занятия 13. Работа продолжается в том же clone и remote; файловый результат программы не меняется. Обязательный результат — опубликовать этот commit и проверить серверную версию.

1. **Сверить исходное состояние проекта:** в clone, созданном в занятии 12.1, определить активную ветку, адрес origin, локальный commit и ожидаемые main.py/.gitignore; опора — блоки 01–02 и планируемые навыки занятий 12.1–13. Ученик самостоятельно решает, соответствует ли проект A. Наблюдаемый результат — он указывает свой remote, ветку и commit, а не полагается на пример или название папки. Если такого clone нет, зависимый push откладывается до выполнения пропущенной предпосылки.
2. **Выполнить первый push:** после блока 03 выбрать явное направление для фактической ветки; пройти штатную HTTPS-авторизацию из блока 04 и отправить уже созданный commit. Наблюдаемый результат — remote принял commit и Git знает связь upstream. Если не хватает локального commit, адреса или доступа, не создавать новую историю в этой практике; зафиксировать неподтверждённую предпосылку.
3. **Сверить серверную копию:** по блоку 06 открыть свой репозиторий и самостоятельно сопоставить ветку, полный ID commit, main.py и .gitignore с локальной версией. Наблюдаемый результат — на сервере доступен именно ожидаемый локальный commit и его файлы.
4. **Разобрать ошибки публикации:** на подготовленных безопасных примерах из блока 05 различить неверный адрес, направление/ветку, отсутствие commit, вход и право записи; назвать ближайшую проверку для каждого случая. Наблюдаемый результат — ученик объясняет разные причины, не изменяет удалённую историю ради «починки» и не раскрывает секреты.

Первые части опираются на понятную локальную историю и проверенные Git-наблюдения; затем ученик сам выбирает направление, выполняет публикацию и проверяет её в двух местах. Ошибки разбираются после рабочего успешного примера и не заменяют его.

**Итоговый критерий всей практики:** в собственном GitHub remote находится commit, чей ID совпадает с локальным HEAD, а main.py и .gitignore соответствуют созданной ранее версии. Ученик своими словами отличает сохранение файла, local commit и push, а также автора commit, вошедший аккаунт и право записи. Это подтверждает B и передаёт занятию 13.2 опубликованную исходную точку.
