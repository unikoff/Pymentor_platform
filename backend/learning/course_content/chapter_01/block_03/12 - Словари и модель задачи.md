# Словарь и договор одной задачи

Опишем одну задачу именованными полями. Разберём ключи и значения, обязательные поля, чтение и изменение записи, а также разницу между допустимым отсутствием настройки и дефектом модели.

**Темы:** словарь · ключ и значение · договор полей · get() · изменение записи · копия одного словаря

## 00. От знакомых структур к новой записи

1. **Точка старта.** Мы храним значения в структурах, проверяем `in` и распаковываем пары.
2. **Новый вопрос.** Как назвать поля одной задачи и понять, когда пропуск значения является ошибкой?
3. **Результат.** Мы создаём полную запись, читаем обязательный ключ, меняем поле и сохраняем договор данных.

Раньше мы выбирали коллекцию по её поведению и распаковывали пары на отдельные имена. Теперь ключ назовёт поле и его смысл, а доступ к записи будет опираться на этот договор.

Пока рассматриваем одну задачу. Список словарей и связи между списком и его записями разберём в занятии 12.1.

## 01. Имя поля вместо позиции

Список отвечает на вопрос «что стоит на позиции 0?». Словарь отвечает на вопрос «что хранится под именем title?». Словарь хранит пары **ключ: значение**. Ключ обозначает поле, значение содержит его данные.

Сравним два варианта одной учебной карточки:

```python
book_by_position = ["Python", 3]
print(book_by_position[1])
```

Второй элемент здесь означает приоритет, но это приходится помнить отдельно. Именованное поле показывает смысл прямо в коде:

```python
book = {"title": "Python", "priority": 3}
print(book["priority"])
```

Вывод второго примера равен 3. Выражение book["priority"] явно называет поле, поэтому нам не нужно восстанавливать смысл позиции.

Квадратные скобки у списка и словаря похожи внешне, но внутри у них разные способы поиска. Для списка мы передаём целую позицию, например 1. Для словаря передаём точный ключ, здесь строку "priority". Для списка ошибка обычно связана с неподходящей позицией. У словаря причина может быть в том, что запрошенное имя поля отсутствует.

Словарь записывается в фигурных скобках. Внутри идут ключ, двоеточие и значение; пары разделяются запятыми. В примерах курса ключи полей являются строками.

Представим бланк анкеты: подпись «Название» задаёт ключ, вписанный текст задаёт значение, а заполненный бланк напоминает словарь. Аналогия помогает увидеть смысл поля, но ограничена: Python сам не проверяет, заполнены ли обязательные строки и подходит ли ответ по типу.

### Строковый ключ и переменная

Ключ "title" является текстовым именем поля. Переменная title может хранить значение, которое мы поместим под этим ключом:

```python
title = "Повторить SQL"
card = {"title": title}
print(card["title"])
```

Вывод: Повторить SQL. Строка "title" не обращается к переменной. Значение берётся из переменной справа от двоеточия.

Ключи одного словаря уникальны. Если ключ записать повторно, новое значение заменит предыдущее, а второй одноимённой пары не появится.

**Предскажем результат до запуска:**

```python
counts = {"items": 2, "items": 5}
print(counts)
```

Результат:

```text
{'items': 5}
```

Повторный ключ не создаёт второе поле. В словаре останется последнее значение.

Уникальность ключа действует внутри одного словаря. Повторная пара не сохраняет историю значений. В других словарях могут быть такие же ключи: каждое имя связывает значение только в своём объекте. Позже список будет хранить отдельные задачи одинаковой формы. Сейчас мы остаёмся на одной записи.

## 02. Договор одной задачи

Поле должно одинаково называться у того, кто создаёт запись, и у того, кто её читает. Это договор модели. Для одной задачи мы используем четыре обязательных поля:

1. **id** хранит положительное целое число, явно назначенное записи. Это отдельное значение, а не позиция задачи.
2. **title** хранит непустую текстовую строку с названием задачи.
3. **priority** хранит целое число от 1 до 5.
4. **is_done** хранит True или False; у новой задачи значение равно False.



Имена ключей чувствительны к написанию: "is_done" не совпадает с "done". Тип и диапазон значения тоже часть договора. Например, строка "urgent" не является допустимым приоритетом, хотя словарь может её сохранить.

Словарь сам не проверяет обязательность ключей, типы или диапазоны. Он хранит то, что мы положили. В этом занятии мы создаём согласованную запись, но не добавляем функции проверки или генерацию id.

Соберём одну запись целиком и проверим, что изменение одного поля не стирает остальные:

```python
task = {"id": 31, "title": "Повторить пример", "priority": 2, "is_done": False}
print(task["id"], task["title"])
task["is_done"] = True
print(task)
```

Словарь содержит все четыре поля договора. Первое чтение получает обязательные данные, а присваивание меняет только `is_done`; `id`, `title` и `priority` остаются на месте. Мы явно задаём `id` и состояние, не полагаясь на позицию или автоматическое создание записи.

Эти четыре поля образуют договор для будущих частей программы. Если создание записывает `is_done`, а чтение запрашивает `done`, Python считает их разными ключами. Переименование меняет точное имя данных; два параллельных ключа могут разойтись по значениям. Число `id` задаётся явно, а не выводится из позиции. Позже позиция задачи в списке сможет измениться, а её `id` останется частью записи. Поиск и выдача уникальных номеров появятся в следующих темах. Правильная запись потребует отдельной проверки: синтаксически допустимый словарь ещё не обязательно подходит модели Planner.

Сведём запись к четырём парам: точное имя поля выбирает связанное с ним значение, а не позицию. Например, `task["priority"]` обращается к приоритету по имени. Успешное чтение подтверждает только наличие ключа; соответствие значения типу и диапазону проверяется отдельно.

Python синтаксически допускает такой пример, хотя договор модели его запрещает:

```python
task_preview = {"id": 31, "title": "Повторить пример", "priority": "urgent", "is_done": False}
print(task_preview["priority"])
```

Код выведет urgent. Чтение прошло, потому что ключ существует. Но успешное чтение не доказывает, что значение соответствует договору.

Здесь важно различать наличие ключа, тип значения и допустимый диапазон. Квадратные скобки проверяют только, можно ли найти имя поля; они не подтверждают два следующих условия. Поэтому мы сначала читаем фактическое значение, а затем сопоставляем его с договором. Проверки типов и границ появятся отдельно.

## 03. Обязательный ключ и KeyError

Квадратные скобки подходят, когда ключ обязан быть в словаре. Если ключа нет, Python сообщает об ошибке KeyError. Так мы замечаем, что запись создана с неправильным полем.

```python
prices = {"cofee": 140}
print(prices["coffee"])
```

Здесь создатель записал cofee, а чтение требует coffee. Исправлять нужно имя в месте создания данных. Если поле обязательно, подстановка случайного значения скроет дефект.

`KeyError` означает, что точного ключа нет. Это отличается от неверного значения: в предыдущем примере `priority` существовал и читался, хотя его строка не подходила договору. Traceback показывает место, где несовпадение проявилось, но источник данных может быть раньше. Сверим имена при создании и чтении и исправим первое, а не добавим догадочный запасной ключ.

**Найдём причину ошибки:**

- A. Словарь не может хранить строковые значения.
- B. Создатель записал ключ с опечаткой, а чтение требует coffee.
- C. print() не умеет выводить поле словаря.

Правильное объяснение: B. Ключи должны совпадать во всех местах, где запись создаётся и читается.

Оператор in проверяет наличие **ключа**, а не значения:

```python
metadata = {"language": "ru"}
print("language" in metadata)
print("ru" in metadata)
```

Результат:

```text
True
False
```

Ключ language есть. Значение ru само по себе не является ключом. Так мы проверяем форму словаря, не перебирая значения.



**Проверим понимание:** что вернёт выражение `"mentor" in course`, если `course = {"mentor": "Anna"}`? Мы получим `True`, потому что mentor является ключом. Выражение `"Anna" in course` вернёт `False`, потому что Anna является значением.

## 04. Ключи, значения и пары

Словарь можно перебирать по ключам, значениям или парам. Метод keys() даёт ключи, values() даёт значения, а items() даёт пару «ключ, значение». Пару из items() мы уже умеем распаковать в два имени.

```python
stock = {"tea": 12, "coffee": 4}

for product, quantity in stock.items():
    print(product, quantity)
```

Сначала выводятся tea 12, затем coffee 4. В каждой итерации product и quantity получают элементы одной пары. Python сохраняет порядок добавления ключей, но ключ не становится индексом списка. Для конкретного продукта мы читаем известный ключ; перебор удобен, чтобы осмотреть все пары.

### Сопоставим способ обхода с результатом шага

- for key in stock даёт ключ.
- for value in stock.values() даёт значение.
- for key, value in stock.items() даёт пару ключ и значение.

Обход полезен для диагностики и общей обработки. Для фиксированного договора задачи обычно яснее явно прочитать известные поля.

Прямой цикл `for key in stock` тоже выдаёт ключ на каждом шаге. `keys()`, `values()` и `items()` позволяют выбрать часть пары; `items()` нужен, когда нам нужны обе. Порядок словаря не превращает поля в позиции или id. Для вывода задачи в заданной форме явное чтение ключей сохраняет понятный порядок независимо от записи пар.

Обход и доступ к одному полю решают разные задачи. Цикл просматривает пары по очереди, а `task["priority"]` сразу получает известное значение. Если нам не нужна общая обработка всех полей, прямое чтение проще проверить и не меняет содержимое словаря.

## 05. Дополнительные данные и get()

Дополнительная настройка может отсутствовать, если программа заранее знает, что делать в таком случае. Метод get() читает значение, не меняя словарь.

```python
delivery_settings = {"sms": False}

print(delivery_settings.get("sms", True))
print(delivery_settings.get("method", "courier"))
print(delivery_settings.get("comment"))
print(delivery_settings)
```

Вывод:

```text
False
courier
None
{'sms': False}
```

Если ключ есть, get() возвращает записанное значение, даже когда это False или 0. Если ключа нет, метод возвращает переданное значение по умолчанию. Без второго аргумента он возвращает None. Чтение не добавляет поле в словарь.

Сравним это с необязательной галочкой в настройках. Если поле уведомлений есть и хранит False, это явный выбор «не включать». Если ключа нет, get() может вернуть заранее выбранный запасной вариант. Аналогия помогает различить отсутствие поля и сохранённый ответ, но get() не записывает этот вариант обратно и сам не решает, допустимо ли отсутствие для конкретной модели.

Например, словарь настроек доставки может хранить необязательный способ доставки с вариантом "courier". Но id, title, priority и is_done обязательны в модели задачи. Если ключ пропущен или записан с ошибкой, get() не должен маскировать нарушение договора.

Запасное значение возвращается только для текущего чтения и не сохраняется в словаре. При следующем обращении ключ останется отсутствующим, пока мы сами его не добавим. `get()` не проверяет найденное значение: если ключ есть, метод вернёт его, даже если тип не подходит. Значит, запасной вариант нужен только там, где мы заранее выбрали допустимое поведение для отсутствующего поля.

Проверим, что отсутствие не равно False: delivery_settings.get("sms", True) возвращает False, потому что ключ существует и в нём явно хранится False. Запасное значение используется только при отсутствующем ключе.

## 06. Изменение словаря и копия одной записи

Присваивание по ключу добавляет новое поле или заменяет значение. Метод pop() удаляет поле и возвращает удалённое значение. Удалять обязательное поле задачи нельзя: запись перестанет соответствовать договору.

```python
preferences = {"theme": "light", "legacy_mode": True}
preferences["language"] = "ru"
preferences["theme"] = "dark"
removed = preferences.pop("legacy_mode")
print(removed, preferences)
```

Вывод:

```text
True {'theme': 'dark', 'language': 'ru'}
```

Сначала появилось поле language, затем изменилось значение theme. Вызов pop() удалил только legacy_mode и вернул прежнее значение в removed.

Словарь позволяет добавить ключ, которого нет в модели: например, `task["urgent"] = True` создаст новую пару, но не заменит обязательное поле `priority`. Такая пара не становится частью согласованного договора автоматически. Синтаксически успешное изменение ещё не гарантирует, что запись подходит следующей части программы.

Так мы различаем три действия: `get()` только читает, присваивание по ключу добавляет пару или заменяет её значение, а `pop()` удаляет пару и возвращает прежнее значение. Изменение видно всем именам, указывающим на тот же словарь. В записи задачи мы сохраняем обязательные поля, а удаление применяем только к дополнительным данным. Если убрать `priority`, последующее чтение `task["priority"]` завершится `KeyError`, даже когда остальные поля останутся на месте. Поэтому допустимость операции зависит от роли ключа: `pop()` подходит устаревшей настройке, но не обязательному полю задачи.

Имя переменной не копирует словарь. Если присвоить тот же объект другому имени, оба имени указывают на одну запись. Метод copy() создаёт отдельный внешний словарь. Для плоской записи из простых значений копия позволяет менять поле отдельно.

```python
task = {"id": 10, "title": "Проверить план", "priority": 3, "is_done": False}
alias = task
draft = task.copy()
same_values = task.copy()
draft["is_done"] = True
print(task["is_done"], alias["is_done"], draft["is_done"])
print(task == same_values, task is same_values)
```

Результат: `False False True`, затем `True False`. `alias` указывает на исходную запись, тогда как `draft` и `same_values` являются отдельными внешними словарями.

Представим бумажную карточку и её копию: `alias` служит вторым ярлыком на том же листе, а `copy()` создаёт отдельный внешний лист. Словари `task` и `same_values` содержат одинаковые поля, поэтому `==` даёт `True`, но это разные объекты и `is` даёт `False`. `copy()` не клонирует вложенные объекты; этот случай разберём отдельно в следующем занятии.

Как мы уже видели на списках, `==` сравнивает содержимое, а `is` проверяет идентичность объектов. Две записи могут иметь одинаковые поля, но оставаться разными словарями. Поэтому одинаковый вывод сам по себе не доказывает общую ссылку; после изменения мы отдельно проверяем, какое состояние изменилось. Для вложенных значений одной внешней копии будет недостаточно.

## 07. Договор понадобится будущим частям проекта

Когда позже одна часть программы будет создавать задачу, а другая читать её, обе должны использовать одинаковые ключи. Запись с `is_done` нельзя читать через `done`, а `id` нельзя выводить из позиции. Хранилища задач в текущем проекте пока нет: сейчас мы изучаем форму одной записи и заранее согласуем её договор.

- **Создание.** Задаём обязательные поля и соблюдаем типы и границы.
- **Чтение.** Берём поле по точному ключу, а не по догадке или позиции.
- **Изменение.** Меняем нужное значение и сохраняем остальные части записи.

Сейчас мы сосредоточимся на одной полной записи и её полях. Следующее занятие положит несколько таких записей в список и отдельно разберёт позицию, id и общие ссылки. Функции для повторяемых операций появятся позднее.

## 08. Что мы будем делать в практике

В редакторе пройдём от создания одной записи к чтению её полей и изменению состояния.

1. **Создадим запись.** Выведем четыре поля, изменим только `is_done` и проверим, что остальные значения сохранились.
2. **Проверим ключи и чтение.** Предскажем результат повторного ключа, выясним, что находит `in`, исправим опечатку у создателя данных и сравним `[]` с `get()` на словаре настроек.
3. **Сравним ссылки.** Изменим `is_done` через alias и через копию; по трём значениям увидим, какой словарь изменился.

В первом задании платформа задаст `task_id`, `title`, `priority` и `new_done`. Первые три значения попадут в поля `id`, `title` и `priority`, а начальное `is_done` будет равно `False`; затем мы подставим в него `new_done`.

Остальные примеры используют отдельные учебные данные и не меняют `main.py`. Мы завершим практику на одной записи; список задач и функция создания появятся позже.
