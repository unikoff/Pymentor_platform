## 00. От архитектурного договора к проверке

В предыдущем занятии появился первый работающий путь Persistent Planner: модель `Task`, `MemoryStorage` и `PlannerService` с добавлением и просмотром задач. Теперь нужно научиться защищать эти договорённости от случайных изменений.

Пока проект маленький, легко открыть терминал, ввести несколько значений и решить, что всё работает. Такой ручной запуск полезен для первого знакомства, но он быстро становится ненадёжным. После изменения модели нужно снова проверять модель. После изменения storage нужно повторять сценарий с файлом. После рефакторинга сервисов нужно помнить все граничные случаи.

Тест берёт эту повторяемую работу на себя. Он заранее описывает сценарий, запускает код и сравнивает наблюдаемый результат с ожиданием. Тест не заменяет понимание архитектуры. Он делает архитектурный договор исполняемым.

Представьте список дел на бумаге. Запись «проверить замок» полезна, но ещё лучше иметь простой способ каждый вечер проверить дверь одинаково. Тест похож на такой чек. Он не доказывает, что в доме нет всех возможных проблем, но быстро показывает, если конкретный замок перестал закрываться.

### Что уже известно

- Task хранит предметные правила;
- PlannerService выполняет прикладной сценарий;
- MemoryStorage владеет состоянием;
- композиция передаёт storage в PlannerService;
- контракт описывает ожидаемый вход и результат.

### Что добавляется сейчас

- pytest как инструмент запуска тестов;
- схема Arrange, Act, Assert;
- имена тестов как короткая документация;
- проверка ожидаемых исключений;
- parameterization для нескольких похожих случаев;
- fixtures для повторяемой подготовки;
- понимание `tmp_path` как будущего инструмента для файловых тестов.

**Перед чтением дальше.** Что должен проверить один тест: весь проект целиком или одно важное наблюдаемое поведение? Второе. Большой сценарий тоже нужен, но его полезно собирать из маленьких проверок с понятной причиной падения.

## 01. Тест как исполняемое ожидание

Ожидание в разговоре звучит так: «пустой заголовок нельзя принять». Тест превращает его в сценарий. Он создаёт вход, вызывает код и проверяет, что возникает нужная ошибка.

```python
def test_empty_title_is_rejected():
    with pytest.raises(ValueError):
        make_task("   ")
```

Важна не длина примера. Важна структура обещания. Если правило изменится случайно, тест станет сигналом. Если команда сознательно меняет договор, тест заставит обновить и проверку.

### Что тест действительно доказывает

Тест доказывает только тот сценарий, который в нём записан. Проверка `task.title == "Python"` не доказывает, что JSON сохраняется. Проверка round trip JSON не доказывает, что сервис правильно считает статистику.

Это ограничение полезно. Небольшой тест легче читать и диагностировать. Вместо сообщения «что-то сломалось» мы получаем точное обещание, которое перестало выполняться.

### Тест как документация

Хороший тест показывает способ использования кода. По нему видно, какие аргументы нужны, какой результат считается нормальным и что делать с ошибкой. Будущий разработчик читает тест перед тем, как менять реализацию.

В production тесты защищают не только разработчика. Они помогают команде безопаснее проводить рефакторинг, обновлять зависимости и замечать изменение контракта до выпуска.

### Что тест не делает

Тест не доказывает отсутствие всех ошибок. Он не заменяет логи, мониторинг, ручную проверку интерфейса или review. Он защищает выбранные договорённости и уменьшает вероятность повторить уже найденную проблему.

**Проверьте понимание.** Если один тест зелёный, можно ли сказать, что вся функция идеальна? Нет. Можно сказать только, что записанный сценарий сейчас даёт ожидаемый результат.

## 02. Pytest, соглашения и запуск

Pytest: это тестовый раннер для Python. Он ищет файлы и функции по соглашениям, запускает их и собирает результат. Благодаря соглашениям не нужно вручную перечислять каждую функцию в командной строке.

Обычно тесты лежат в каталоге `tests`, файлы называются `test_*.py` или `*_test.py`, а функции начинаются с `test_`. Названия не являются украшением. Это часть механики обнаружения.

### Установка и выбор Python

Устанавливайте pytest в то же виртуальное окружение, из которого запускается проект:

```text
python -m pip install pytest
python -m pytest -q
```

Форма `python -m pytest` полезна тем, что запускает pytest выбранным интерпретатором Python. Так меньше риска установить пакет в одно окружение, а запустить тесты в другом.

### Минимальная структура тестов

```text
studyhub/
├── app/
│   ├── models.py
│   ├── services.py
│   └── storage.py
└── tests/
    ├── test_models.py
    ├── test_services.py
    └── test_storage.py
```

Разделение по предметной области помогает понять, где искать падение. Это не жёсткое требование на все времена. Если тест проверяет несколько слоёв, его можно назвать по сценарию, но причина всё равно должна оставаться ясной.

### Как читать вывод

`PASSED` означает, что сценарий выполнил ожидание. `FAILED` означает, что наблюдение отличается от ожидания. `ERROR` часто означает проблему подготовки, импорта или фикстуры до самого assert.

```text
FAILED tests/test_models.py::test_task_strips_title
E       AssertionError: assert '  Python  ' == 'Python'
```

Такой вывод уже подсказывает направление поиска. Нужно сравнить фактическое значение с ожидаемым и решить, нарушен код или неверно записано ожидание.

**True или false.** Если pytest завершился с ошибкой импорта, это обычное падение бизнес-теста. False. Сначала сломан путь или каркас, поэтому до предметной проверки дело могло не дойти.

## 03. Arrange, Act, Assert

AAA: это простой ритм теста. Сначала подготовить данные, затем выполнить одно действие, затем проверить результат. Такая схема не обязательна синтаксически, но помогает не смешивать причины.

### Arrange: подготовка

Создайте объект, входные значения и безопасные зависимости. Для сервиса это может быть MemoryStorage. Для файлового теста путь должен быть временным.

### Act: действие

Вызовите одну функцию или один метод, который проверяется. Если тест одновременно добавляет, ищет, удаляет и считает статистику, при падении трудно понять, где возникла причина.

### Assert: проверка

Проверьте наблюдаемый результат. Это может быть возвращённый Task, состояние storage, количество элементов или исключение.

```python
def test_add_task_returns_created_task():
    storage = MemoryStorage()
    service = PlannerService(storage)

    task = service.add_task("Python", priority=3)

    assert task.title == "Python"
    assert task.priority == 3
    assert storage.load() == [task]
```

В этом примере `Arrange`: storage и service. `Act`: add_task. `Assert`: поля результата и состояние хранилища. Если сервис начнёт возвращать задачу, но перестанет сохранять её, последняя проверка покажет это отдельно.

### Один тест, одна мысль

Правило «одна мысль» не означает «один assert». Несколько assert могут проверять один результат с разными сторонами. Но если тест проверяет сразу нормальный вход, ошибку, JSON и статистику, его нужно разделить.

Плохой тест похож на один вопрос с пятью ответами. Если ученик ошибся в одном месте, непонятно, какой именно смысл он не понял. Хороший тест локализует наблюдение.

### Проверяем публичное поведение

В тестах сервиса лучше вызывать публичный `add_task`, чем внутреннюю вспомогательную функцию. Внутренний helper можно изменить без изменения пользовательского результата. Публичный метод является частью договора.

Это не запрещает тестировать небольшие функции напрямую. Важно понимать, что именно вы защищаете: внутреннюю механику или обещание слоя.

**Попробуйте предсказать.** Если убрать последний assert из примера, может ли тест пройти, даже если задача не сохранилась? Да. Тест проверит возвращённый объект, но не состояние storage.

## 04. Имена тестов и диагностическая ценность

Имя теста показывается в выводе pytest. Поэтому оно должно сообщать действие и ожидаемый результат. `test_task` почти бесполезен. `test_task_strips_title` уже подсказывает, какую договорённость нарушили.

Удобная форма имени:

`test_<действие>_<ожидаемое поведение>`

Примеры:

- `test_new_task_is_not_done`;
- `test_task_rejects_empty_title`;
- `test_missing_json_returns_empty_list`;
- `test_unknown_task_id_raises_error`;
- `test_json_storage_round_trip_preserves_tasks`.

Имя не должно описывать случайную деталь реализации. Если тест называется `test_private_items_length`, он может стать бесполезным после нормального рефакторинга. Лучше назвать наблюдаемое поведение пользователя или публичного контракта.

### Assert тоже должен быть точным

Сравнивайте конкретный результат, а не только факт, что функция не упала.

```python
task = service.add_task("  SQL  ", priority=2)

assert task.title == "SQL"
assert task.done is False
```

`assert task is not None` слишком слабый, если договор обещает нормализованный заголовок и начальный статус.

### Сообщение падения как подсказка

Понятное имя и точный assert сокращают время диагностики. Разработчик видит не «тесты красные», а «пустой JSON не вернул пустой список» или «новая задача оказалась выполненной».

В production это снижает стоимость поддержки. Ошибка быстрее попадает к нужному слою и не заставляет читать весь проект.

**Найдите слабое место.** Что не так с тестом `def test_task(): assert task`? Он не сообщает, какой сценарий проверяет и какой результат важен. Имя и assert нужно связать с договором.

## 05. Ожидаемые исключения через pytest.raises

Ошибка является частью контракта. Если пустой title запрещён, тест должен проверить не только то, что код не создал задачу, но и то, что он сообщил правильный тип ошибки.

`pytest.raises` временно ожидает исключение внутри блока:

```python
import pytest


def test_task_rejects_empty_title():
    with pytest.raises(ValueError):
        Task(1, "   ", priority=3)
```

Если исключение возникло, проверка проходит. Если не возникло, тест падает. Если возник другой тип, тест тоже падает, потому что договор не совпал.

### Проверяем причину, когда это важно

Иногда одного типа недостаточно. Можно проверить текст или атрибут исключения, если сообщение является частью пользовательского или программного договора. Не сравнивайте текст без необходимости: слишком точная проверка может сделать тест хрупким.

Для ошибки отсутствующей задачи полезно отличать `TaskNotFoundError` от обычного `KeyError`. Это помогает CLI и будущему API обработать ситуацию осмысленно.

### Не прячьте исключения

Плохой тест:

```python
try:
    service.get_task(999)
except Exception:
    pass
```

Он может пройти из-за любой ошибки и не докажет, что возник нужный контракт. Общий `except` скрывает источник проблемы.

### Где проверять ошибку

Если правило принадлежит Task, тестируйте его рядом с моделью. Если ошибка означает отсутствие объекта в сценарии, проверяйте PlannerService. Если файл повреждён, проверяйте storage. Такое размещение отражает архитектурную границу.

**Проверьте понимание.** Почему `pytest.raises(ValueError)` лучше, чем проверка «метод просто не вернул объект»? Потому что отсутствие результата может быть случайным, а тип ошибки явно фиксирует обещанное поведение.

## 06. Параметризация границ

Часто один и тот же сценарий нужно проверить на нескольких значениях. Например, priority должен принимать несколько валидных вариантов и отклонять значения за пределами диапазона.

Без параметризации тесты будут почти одинаковыми. Это увеличивает объём и риск, что один случай случайно начнёт отличаться.

```python
import pytest


@pytest.mark.parametrize("priority", [1, 3, 5])
def test_task_accepts_valid_priority(priority):
    task = Task(1, "Python", priority=priority)

    assert task.priority == priority
```

Pytest запустит один тестовый сценарий с каждым значением. При падении он покажет конкретный набор данных.

### Границы важнее случайных чисел

Если допустимы значения от 1 до 5, полезны 1 и 5. Затем можно проверить значения за границей: 0 и 6. Такой набор связан с правилом. Случайные 2 и 4 не заменяют проверки краёв.

Параметризация полезна и для строк: пустая строка, пробелы, обычный title и строка с Unicode. Набор должен помогать увидеть разные ветки поведения, а не создавать длинный список ради количества.

### Один параметр или несколько

Можно передавать несколько параметров, если они описывают одну мысль:

```python
@pytest.mark.parametrize(
    ("title", "expected"),
    [("  SQL  ", "SQL"), ("Python", "Python")],
)
def test_task_normalizes_title(title, expected):
    assert Task(1, title, priority=3).title == expected
```

Если комбинаций становится много и каждая требует отдельного объяснения, лучше сделать несколько явных тестов. Параметризация не должна скрывать разные сценарии.

**Вопрос.** Что полезнее проверить для диапазона: только обычное значение 3 или 1, 5, 0 и 6? Второй набор. Он показывает допустимые края и отказ за пределами.

## 07. Fixtures и изолированное in-memory состояние

Fixture это повторяемая подготовка для теста. Она может создать модель, storage или сервис. Fixture не должна прятать смысл сценария. Её задача убрать технический шум, который одинаков для нескольких проверок.

```python
import pytest


@pytest.fixture
def service():
    return PlannerService(MemoryStorage())
```

У этого урока нет файлового хранилища. Это сознательная граница. Поэтому сервис проверяется через `MemoryStorage`, а не через `tasks.json`. Каждый тест получает новое состояние и не зависит от порядка запуска.

```python
def test_add_task_saves_through_storage(service):
    created = service.add_task("Python", priority=3)

    assert created.title == "Python"
    assert service.list_tasks() == [created]
```

Позже, когда появится JSON, для файловых тестов понадобится `tmp_path`. Он выдаёт отдельный временный каталог и не позволяет тесту читать рабочий файл пользователя. Сейчас важно запомнить принцип: тест должен управлять своими зависимостями и не брать скрытое состояние из окружающего мира.

## 08. Что мы будем делать в практике

Практика превратит уже работающий in-memory путь в повторяемые проверки. К концу работы у проекта будет небольшой, но ясный набор тестов, который защищает модель, контракт storage и первые действия сервиса.

### Общий результат

Мы создадим тесты для `Task`, `MemoryStorage` и базовых методов `PlannerService`. Проверим нормализацию и инварианты модели, независимость тегов, защитные копии storage, добавление задачи и чтение списка.

### Крупный путь работы

1. Подготовить каталог тестов и убедиться, что pytest находит файлы.
2. Проверить правила `Task` по схеме Arrange, Act, Assert.
3. Проверить, что `MemoryStorage` не отдаёт внутренний список.
4. Проверить `add_task()` и `list_tasks()` через новый in-memory storage.
5. Прочитать одно диагностическое падение, исправить причину и сохранить зелёный набор.

### Границы практики

Мы пока не тестируем JSON, CLI, persistence после перезапуска, полный CRUD, HTTP-интерфейс и базу данных. Это появится после архитектурной контрольной точки и реализации файлового хранилища. Нельзя писать тест на поведение, которое проект ещё не обязан поддерживать.

Перед переходом назовите: какая проверка относится к модели, какая к storage, а какая к сервису. Если роли понятны, практика начинается с подготовки, а не с угадывания.

### Главное

- Тест делает важное ожидание исполняемым.
- Один тест должен защищать одно понятное наблюдаемое поведение.
- AAA разделяет подготовку, действие и проверку.
