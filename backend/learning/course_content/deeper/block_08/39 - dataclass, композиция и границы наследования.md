## 00. С чего начинается живой проект

Persistent Planner будет расти постепенно. В нём появятся хранение в памяти, сервис, тесты, JSON-файл и консольный интерфейс. Но любой из этих слоёв будет работать с одной сущностью: задачей.

Поэтому начинаем не с меню, файла или списка всех задач. Сначала опишем, какой бывает одна корректная Task. Если модель принимает пустое название, случайно делит tags между объектами или хранит неясный статус, поздние слои только разнесут проблему дальше.

На этом этапе мы:

- создаём Task через dataclass;
- защищаем её правила;
- разбираемся с изменяемым списком tags;
- выражаем изменение статуса через mark_done;
- знакомимся с композицией на независимом примере;
- оставляем storage, JSON, service, CLI и pytest на следующие работы.

    Task с правилами
    -> MemoryStorage и PlannerService
    -> pytest для in-memory ядра
    -> структура и контракт persistence
    -> JsonStorage, CLI и приёмка

### Граница текущей работы

Сейчас нет контейнера задач и нет хранилища. Это сознательно. Первая коллекция задач должна появиться только тогда, когда мы сможем сразу дать ей точную роль и договор load/save. Такой порядок не добавляет временный класс, который придётся забыть в следующем уроке.

## 01. Dataclass: когда класс прежде всего описывает данные

Python-класс может быть клиентом API, обработчиком файла, калькулятором или моделью одной сущности. Dataclass особенно удобен, когда класс прежде всего хранит понятные данные.

Примеры таких объектов встречаются в любом продукте:

- товар в корзине;
- пользовательский профиль;
- запись календаря;
- настройка приложения;
- задача планировщика.

Декоратор dataclass создаёт шаблонный код конструктора, понятного представления и сравнения по полям. Но он не делает объект правильным сам по себе.

~~~python
from dataclasses import dataclass


@dataclass
class Book:
    title: str
    pages: int
    is_read: bool = False
~~~

Book легко создать, но dataclass не знает, допустимы ли ноль страниц или пустое название. Такие решения принадлежат автору модели.

### Тип и правило имеют разный смысл

Аннотация title: str сообщает, что ожидается строка. Но строка может быть пустой или состоять только из пробелов. Аннотация priority: int сообщает, что ожидается число, но не определяет допустимый диапазон.

Условие, которое должно быть верным у каждого корректного объекта, называют инвариантом. Для Task это:

- title после очистки не пустой;
- priority находится в диапазоне от 1 до 5;
- tags принадлежит конкретной задаче;
- is_done хранит понятный статус.

В production похожие модели встречаются на разных границах: доменная модель внутри приложения, Pydantic-схема HTTP и ORM-модель базы. Поля могут быть похожи, но роли у них разные. Сейчас мы строим доменную модель, не зависящую от будущего файла или интерфейса.

## 02. Изменяемые поля и личное состояние объекта

Список tags можно менять после создания задачи. Именно здесь легко создать незаметную общую память.

~~~python
class Playlist:
    tags = []


first = Playlist()
second = Playlist()
first.tags.append("study")

print(second.tags)
print(first.tags is second.tags)
~~~

Список создан у класса, поэтому оба объекта используют один и тот же контейнер. Изменение первой коллекции видно второй.

### Default factory

Dataclass не разрешает обычный изменяемый список как значение по умолчанию поля. Вместо этого нужен field с default_factory.

~~~python
from dataclasses import dataclass, field


@dataclass
class Playlist:
    name: str
    tags: list[str] = field(default_factory=list)
~~~

Default factory вызывает list заново для каждого объекта. Это похоже на выдачу новой тетради каждому ученику: тетради одинаковы, но записи одного человека не появляются у другого.

Оператор == сравнивает содержимое. Оператор is отвечает, один ли это объект в памяти. В smoke-сценарии понадобятся оба вопроса: второй список остаётся пустым, а сами списки физически различаются.

## 03. Инварианты и понятные действия модели

Инвариант полезен только тогда, когда его нельзя случайно обойти через другой путь. Если проверка пустого title живёт около input, то тест, импорт данных или будущий HTTP-запрос создаст плохую задачу напрямую.

Dataclass вызывает __post_init__ после заполнения полей. Это подходящее место для нормализации и проверки.

~~~python
from dataclasses import dataclass


@dataclass
class Temperature:
    value: int

    def __post_init__(self):
        if not -80 <= self.value <= 60:
            raise ValueError("temperature outside allowed range")
~~~

Для Task сначала нужно очистить title через strip, затем проверить пустоту. Строка из трёх пробелов не должна пройти проверку только потому, что она была непустой до нормализации.

Метод mark_done лучше, чем одинаковое присваивание поля в разных местах. Сегодня он меняет is_done на True. Позже внутри него может появиться дата, аудит или дополнительное правило, а внешний код сохранит понятный вызов.

## 04. Композиция: важный принцип без лишней сущности

Композиция описывает связь «содержит» или «использует». Коробка содержит предметы, но не является предметом. Папка содержит документы, но не является документом.

~~~python
class Library:
    def __init__(self, books):
        self.books = list(books)
~~~

Library содержит книги. Она не должна наследоваться от Book, потому что библиотека не является одной книгой.

~~~python
class Library(Book):
    pass
~~~

Такой код означал бы неверное отношение. У библиотеки и книги разные данные, правила и причины изменения.

Этот принцип пригодится в следующей работе. MemoryStorage будет содержать список Task, а PlannerService будет использовать storage через его договор. Сейчас не нужно создавать отдельный учебный контейнер только ради демонстрации. Достаточно понять вопрос: объект является другим объектом или содержит его?

## 05. Границы первого этапа

Сейчас проект должен уметь:

- создать корректную Task;
- очистить title и проверить priority;
- хранить независимые tags;
- отметить одну Task выполненной;
- пройти короткий smoke-сценарий модели.

Сейчас проект не должен уметь:

- хранить список всех задач;
- читать и писать JSON;
- переживать перезапуск программы;
- принимать команды пользователя;
- искать, удалять и считать статистику;
- запускать pytest.

PlannerService будет координировать пользовательские действия: загрузить список, создать Task, сохранить изменения и вернуть результат. Для этой роли сначала нужен договор хранения. Он появится в следующей работе вместе с MemoryStorage.

JSON относится к внешней границе. Он требует сериализации, кодировки, ошибок файла и проверки формата. Если добавить его до устойчивой модели, трудно понять, где сломалось состояние: в Task, в файле или в сценарии.

## 06. Как идея развивается в настоящих продуктах

| Вопрос | Сейчас | Позже в учебном проекте | Большой продукт |
| --- | --- | --- | --- |
| Что такое корректная сущность? | Task и её инварианты | та же Task | доменная модель и правила |
| Где живёт список объектов? | пока нигде | MemoryStorage | repository, database или внешний сервис |
| Кто выполняет сценарий? | пока никто | PlannerService | application service или use case |
| Кто показывает результат? | пока никто | CLI | web, API или mobile-клиент |
| Где лежат данные после перезапуска? | пока нигде | JsonStorage | база данных или другой persistence слой |

Нам не нужно копировать сложную архитектуру большого сервиса. Достаточно сохранить причинную связь: модель не должна знать интерфейс, а интерфейс не должен быть владельцем предметных правил.

## 07. Минимальная проверка до следующего слоя

На этом этапе проверка будет простой: отдельный smoke-скрипт с assert. Pytest появится позже, когда будет готов первый in-memory сценарий.

Проверка должна подтвердить:

1. Task нормализует title.
2. Некорректный title или priority отклоняется.
3. Две Task не делят tags.
4. mark_done меняет статус выбранной задачи.

Если какой-то assert не проходит, не добавляйте новый слой поверх ошибки. Сначала найдите владельца правила: Task или её изменяемое поле tags.

## 08. Что мы будем делать в практике

Практика создаст первую контрольную точку одного Persistent Planner.

Сначала вы подготовите пакет app и модель Task с полями id, title, priority, is_done и tags. Затем добавите инварианты и метод mark_done. Отдельным smoke-сценарием докажете нормализацию, ошибки границ, независимость tags и изменение статуса.

В конце вы запишете границы проекта в project-path.md. В документе будет видно, что уже работает, а что осознанно отложено: MemoryStorage, PlannerService, pytest, JSON и CLI.

### Доказательство результата

- smoke-скрипт завершается без AssertionError;
- Task создаётся только в корректном состоянии;
- тег первой задачи не появляется у второй;
- статус меняет только метод модели;
- в проекте ещё нет storage, JSON-файла и прикладного сервиса.
