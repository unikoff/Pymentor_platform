## 00. От готового ядра к сохранённому приложению

В предыдущей работе Persistent Planner уже получил рабочее in-memory ядро. Модель Task описывает задачу и проверяет её правила. MemoryStorage умеет принять список и вернуть его. PlannerService уже может добавить задачу и показать список. Эти части не нужно собирать заново.

Но у такого приложения есть очевидное ограничение. Закройте процесс, и список исчезнет. Откройте программу завтра, и она не вспомнит ни одной задачи. Следующий естественный шаг не требует нового набора бизнес-правил. Нужно научить существующее ядро переводить состояние во внешний формат, сохранять его и восстанавливать при новом запуске.

Представьте записную книжку. Пока вы держите страницу в памяти, запись доступна. Чтобы вернуться к ней завтра, нужна форма, которая переживёт закрытие блокнота. В программе такой формой станет JSON-файл. Task останется понятным объектом внутри приложения, а файл будет хранить простые данные.

### Исходная точка

У нас уже есть:

- Task и её инварианты;
- независимое поле tags;
- mark_done();
- MemoryStorage с договором load() и save();
- PlannerService с добавлением и чтением списка;
- in-memory тесты для уже готового поведения;
- каркас проекта, точка сборки и ожидающий тест для persistence.

Теперь впервые появляется новый слой:

- to_dict() и from_dict() на границе модели;
- JsonStorage для состояния между запусками;
- явные ошибки формата файла;
- оставшиеся операции сервиса;
- тонкий CLI, который использует сервис.

### Карта нового пути

~~~text
готовая Task
    ↓ to_dict()
простые данные
    ↓ json.dumps()
JSON-файл
    ↓ json.loads()
простые данные
    ↓ from_dict()
Task
    ↓
PlannerService
    ↓
CLI
~~~

В этой работе важно не повторить уже сделанное, а провести одну новую границу. MemoryStorage остаётся полезным для быстрых проверок. JsonStorage добавляет persistence. Сервис должен работать с обоими хранилищами по одному договору.

**Проверка понимания.** Что исчезает после закрытия процесса: правила класса Task, код PlannerService или список объектов, который находился только в памяти? Исчезает состояние в памяти. Значит, новый слой должен научиться сохранять состояние, а не переписывать модель.

## 01. Сериализация как перевод между представлениями

Внутри Python программа работает с объектами. Внешняя система обычно понимает более простой набор значений: строки, числа, логические значения, списки и словари. Перевод объекта в такой набор называют сериализацией. Обратное восстановление объекта называют десериализацией.

Это похоже на перевод книги в каталог библиотеки. Каталог не является самой книгой, но в нём есть данные, по которым её можно найти и восстановить нужную информацию. Каталог удобен для хранения и обмена. Внутри читатель всё равно работает с книгой, а не со строкой из каталога.

### Небольшой независимый пример

~~~python
from dataclasses import asdict, dataclass
import json


@dataclass
class Bookmark:
    title: str
    url: str


bookmark = Bookmark("Python", "https://python.org")
plain_data = asdict(bookmark)
text = json.dumps(plain_data)
restored_data = json.loads(text)

print(type(plain_data).__name__)
print(type(restored_data).__name__)
~~~

Здесь происходят четыре разных действия:

1. bookmark является объектом Bookmark;
2. asdict() создаёт обычный словарь;
3. json.dumps() превращает словарь в текст;
4. json.loads() возвращает обычные данные.

Последняя строка не создаёт Bookmark автоматически. JSON не знает, какой класс должен стоять за словарём. Если приложению снова нужен объект с методами и правилами, оно должно явно вызвать фабрику или метод восстановления.

### Почему не работать с dict повсюду

Можно передавать словарь между всеми функциями, но тогда каждая функция начинает самостоятельно решать:

- какие ключи обязательны;
- как очистить строку;
- что считать допустимым числом;
- что делать с отсутствующим ключом;
- является ли список новым или общим.

В маленьком примере это терпимо. В приложении с несколькими входами такая неопределённость быстро создаёт разные версии одной и той же задачи. Сериализация нужна не для того, чтобы заменить модель словарём. Она нужна, чтобы ясно обозначить внешний формат.

### Где это используют в production

Сериализация встречается в HTTP-ответах, очередях сообщений, кешах, файлах конфигурации, логах и обмене между сервисами. Объект заказа превращается в JSON для API. Сообщение события превращается в байты для очереди. Настройки превращаются в словарь при чтении конфигурации.

При росте системы появляются дополнительные вопросы:

- совместим ли новый формат со старыми данными;
- как обрабатывать необязательные поля;
- как версионировать схему;
- где проверять вход;
- как не отправить наружу внутреннее поле.

Эти вопросы относятся к границе представления. Они не означают, что доменная модель должна знать о каждом конкретном протоколе.

### Связь с текущей работой

В нашем проекте внешний формат одной задачи будет задаваться методами Task.to_dict() и Task.from_dict(). До этой границы сервис продолжит получать объекты Task. После неё storage сможет работать с JSON-совместимыми данными.

**Мини-проверка.** Какой объект должен получить сервис после json.loads(), если внутри приложения нужны методы mark_done()? Сам результат json.loads() это ещё не Task. Нужен явный переход через Task.from_dict().

## 02. Сериализация Task без изменения её прежних правил

В этом слое модель уже существует. Мы не переписываем её dataclass, инварианты, tags и mark_done(). Мы добавляем к готовому объекту внешний способ представления.

### Что входит в формат

Для задачи проект использует поля:

- id;
- title;
- priority;
- is_done;
- tags.

to_dict() отвечает за путь из объекта наружу. Его результат должен содержать только JSON-совместимые значения. from_dict() отвечает за путь внутрь. Он должен создать настоящую Task, а не вернуть входной словарь.

~~~python
payload = {
    "title": "Повторить сериализацию",
    "url": "https://example.com",
}


def normalise_bookmark(data):
    return Bookmark(
        title=data["title"].strip(),
        url=data["url"],
    )
~~~

Это независимый пример роли фабрики. Функция не возвращает data, потому что вызывающему коду нужен объект с понятными полями и поведением. В проекте аналогичную роль будет выполнять Task.from_dict().

### Граница должна сохранять инварианты

Данные из файла нельзя считать доверенными только потому, что их когда-то создала наша программа. Файл могли изменить вручную, перенести из старой версии или повредить. Поэтому from_dict() должен создавать объект через обычный конструктор Task.

Так правила модели сработают для нескольких источников:

- задачу добавили через CLI;
- задачу восстановили из JSON;
- задачу создал тест;
- задачу в будущем прислал HTTP-обработчик.

Если проверять значения только при добавлении через CLI, восстановление из файла сможет обойти защиту.

### Почему tags требуют копии

Списки изменяемы. Если to_dict() положит в словарь сам внутренний self.tags, внешний код получит ссылку на состояние Task:

~~~python
saved = task.to_dict()
saved["tags"].append("external-change")
~~~

Теперь изменение словаря может неожиданно изменить модель. Безопаснее вернуть list(self.tags). При восстановлении полезно также создать новый список из входных данных. Тогда Task и внешний payload не владеют одним и тем же изменяемым объектом.

Это не особенность JSON. Это общее правило границ с изменяемыми данными. Такая же проблема возникает с настройками, списками фильтров, кешами и вложенными структурами.

### Что проверять

Для этой границы нужны три наблюдения:

1. to_dict() возвращает обычный словарь;
2. from_dict() возвращает объект Task;
3. изменение списка в сохранённом представлении не меняет исходную Task.

Отдельно проверьте round trip:

~~~text
Task → dict → Task
~~~

Смысл данных должен сохраниться. Это не означает, что два экземпляра обязаны быть одним объектом в памяти. Важно, что поля и правила восстановлены корректно.

### Production-контекст

В web-приложении рядом с доменной моделью могут использоваться Pydantic-схемы. В ORM-проекте объект может преобразовываться в строку базы данных. Эти инструменты помогают на других границах, но общий принцип остаётся тем же: формат обмена не должен бесконтрольно проникать во внутреннюю логику.

**Проверьте предположение.** Если from_dict() просто возвращает входной словарь, где будут находиться методы mark_done() и проверки priority? Их не будет. Значит, такой метод не восстановил модель.

## 03. Persistence и JsonStorage

Persistence означает, что состояние переживает завершение текущего процесса. Переменная и список в памяти этого не обеспечивают. Файл, база данных или удалённое хранилище обеспечивают, если приложение умеет записать данные и потом восстановить их.

### Storage как контракт

Уже знакомый MemoryStorage показывает минимальную роль storage:

~~~python
class Storage:
    def load(self):
        ...

    def save(self, tasks):
        ...
~~~

Сервису важен смысл операций:

- load() возвращает текущее состояние как список Task;
- save(tasks) принимает новое состояние;
- способ хранения скрыт за этим договором.

MemoryStorage выполняет его внутри процесса. JsonStorage выполняет его через файл. Позже ту же роль может выполнять DatabaseStorage. Сервису не нужно переписывать пользовательские сценарии при каждой замене реализации.

### Почему путь передаётся снаружи

Если JsonStorage сам зашивает строку data/tasks.json, его трудно проверить в изолированном тесте. Тесты начнут зависеть от настоящего файла проекта. Передача Path через конструктор делает место хранения явной зависимостью:

~~~python
storage = JsonStorage(Path("data/tasks.json"))
~~~

В обычном запуске выбран постоянный путь. В тесте можно передать путь из tmp_path. На сервере путь может прийти из конфигурации. Одна и та же реализация не должна знать, кто её создал.

### Что делает save

Общий путь сохранения выглядит так:

~~~text
list[Task]
    ↓ to_dict()
list[dict]
    ↓ json.dumps()
JSON-текст
    ↓ write_text(..., encoding="utf-8")
файл
~~~

JsonStorage знает формат файла, кодировку и создание каталога. Он не знает, почему пользователь добавил задачу и можно ли у неё priority 4. Эти правила принадлежат модели и сервису.

ensure_ascii=False сохраняет кириллицу в читаемом виде. indent=2 помогает открыть файл глазами и проверить его при ревью. Это не делает JSON базой данных, но для небольшого локального проекта даёт понятный снимок состояния.

### Что делает load

Обратный путь выглядит так:

~~~text
файл
    ↓ read_text(..., encoding="utf-8")
JSON-текст
    ↓ json.loads()
list[dict]
    ↓ Task.from_dict()
list[Task]
~~~

Первый запуск требует отдельного решения. Если файла нет, естественный результат для нового проекта это пустой список. После save() файл появляется. Новый экземпляр JsonStorage должен прочитать его и вернуть объекты Task.

Проверка через новый экземпляр важна. Повторный вызов load() у одного объекта ещё не доказывает, что данные пережили перезапуск. Нужно пройти границу между старым и новым объектом storage.

### Где это используют в production

JSON-файл удобен для локальных инструментов, небольших конфигураций и переносимых снимков. Он становится слабым вариантом, когда несколько процессов пишут одновременно, данных становится много, нужен сложный поиск или требуется транзакция.

Тогда появляется база данных. Она меняет механику хранения, но не отменяет смысл границы: прикладной сервис всё ещё должен работать с задачами и действиями, а не с SQL-строками внутри каждой команды.

**Проверка порядка.** Что должно произойти раньше: json.dumps() или Task.to_dict()? Сначала объект нужно перевести в простые данные, и только потом сериализовать список в JSON-текст.

## 04. Состояния файла и ошибки целостности

Надёжное storage различает отсутствие данных и невозможность прочитать существующие данные. Иначе ошибка может выглядеть как пустой проект и привести к потере состояния.

| Состояние | Что это значит | Реакция |
| --- | --- | --- |
| файла нет | приложение запускается впервые | вернуть [] |
| файл содержит [] | задач пока нет | вернуть пустой список |
| JSON синтаксически повреждён | существующее состояние нельзя прочитать | поднять StorageError |
| корень не является списком | формат не соответствует договору | поднять StorageError |
| запись не создаёт Task | нарушен формат одной задачи | поднять StorageError |

Пустой шкаф и шкаф с застрявшей дверью выглядят похоже только из коридора. В первом нет вещей. Во втором вещи могут быть, но мы не смогли их безопасно достать. Возвращать [] в обоих случаях опасно: следующий save() способен затереть старое состояние.

### Узкая обработка исключений

Низкоуровневый json.JSONDecodeError полезен для диагностики, но наружу проекту может быть удобнее отдавать собственный StorageError:

~~~python
try:
    data = json.loads(text)
except json.JSONDecodeError as error:
    raise StorageError("Файл задач повреждён") from error
~~~

Конструкция from error сохраняет исходную причину. Пользовательский слой получает понятный тип ошибки, а разработчик не теряет traceback.

Не стоит писать:

~~~python
try:
    data = json.loads(text)
except Exception:
    return []
~~~

Такой код скрывает ошибки доступа, ошибки программирования и неожиданные типы данных. Обработчик должен покрывать только состояния, которые автор действительно понимает.

### Проверка структуры после разбора

Правильный JSON ещё не обязательно является правильным файлом задач. Например, JSON может содержать словарь настроек вместо списка задач. Или список может содержать запись без priority. Поэтому после json.loads() нужны проверки структуры, а затем создание Task через from_dict().

Ошибки формата должны происходить до успешного сохранения нового состояния. Если load() не смог прочитать старый файл, сервис не должен продолжать сценарий так, будто список был пустым.

### Безопасность записи

Обычная запись в целевой файл может прерваться. Компьютер выключился, процесс завершился, диск сообщил ошибку. Тогда файл способен остаться неполным.

Для более надёжной записи используют последовательность:

1. подготовить новый JSON-текст;
2. записать его во временный файл рядом с целью;
3. закрыть и проверить запись;
4. заменить старый файл готовым временным результатом.

Это не решает все проблемы конкурентной записи, но уменьшает риск оставить половину JSON. В учебной реализации важнее понять, почему такая граница существует, чем механически добавить сложный код без проверки.

**Разбор ошибки.** Если повреждённый JSON превращается в [], что увидит CLI? Он решит, что задач нет. Если после этого добавить новую задачу и сохранить список, что может произойти со старыми данными? Они могут быть заменены новым неполным состоянием.

## 05. Как расширять PlannerService, не ломая ядро

Существующие add_task() и list_tasks() уже показывают основной договор: service загружает состояние через storage, выполняет прикладное действие и возвращает результат. Теперь добавятся операции чтения и изменения, но принцип останется тем же.

### Чтение и изменение

Операции можно разделить по побочному эффекту:

| Операция | Читает состояние | Меняет состояние | Нужен save() |
| --- | --- | --- | --- |
| list_tasks() | да | нет | нет |
| get_task() | да | нет | нет |
| search_tasks() | да | нет | нет |
| get_statistics() | да | нет | нет |
| mark_done() | да | да | да |
| delete_task() | да | да | да |

Таблица помогает увидеть важную границу. Поиск и статистика не должны случайно переписывать файл. Завершение и удаление не должны оставаться только изменением объекта в памяти.

### Ошибка отсутствующей задачи

Если get_task(999) ничего не нашёл, сервис должен использовать согласованный TaskNotFoundError. Возврат None иногда, False в другой функции и пустого объекта в третьей заставляет каждый интерфейс угадывать смысл результата.

Единая ошибка полезна сразу нескольким клиентам:

- CLI может показать сообщение «задача не найдена»;
- тест может использовать pytest.raises;
- будущий HTTP-слой сможет преобразовать её в 404;
- вызывающий код не перепутает ошибку с пустым результатом поиска.

### Изменение состояния

mark_done() должен пройти понятную последовательность:

~~~text
load → найти Task → вызвать mark_done() → save → вернуть Task
~~~

Если задача не найдена, save() не нужен. Если задача найдена и статус изменён, новое состояние нужно передать storage. Это делает поведение одинаковым для памяти и файла.

delete_task() использует похожий путь:

~~~text
load → найти позицию → удалить → save → вернуть удалённую Task
~~~

Если удаление не найдено, список не должен измениться.

### Правило поиска и статистики

В каждом прикладном проекте нужно явно выбрать, что означает поиск. Например, можно искать по вхождению нормализованного запроса в заголовке:

~~~python
query.casefold() in task.title.casefold()
~~~

Это только один вариант. Важно зафиксировать правило, чтобы тест, CLI и будущий интерфейс не трактовали слово «поиск» по-разному.

Статистика также является прикладным результатом. Сервис может вернуть количество всех задач, открытых и выполненных. CLI не должен пересчитывать эти значения самостоятельно, иначе другой клиент получит другую логику.

### Почему service не знает JSON

Если в services.py появляются json.loads(), json.dumps() и ручной Path.write_text(), service присваивает себе чужую роль. Тогда замена JSON на базу данных потребует менять все методы. Правильная зависимость выглядит проще: service получает объект с load() и save() и не спрашивает, что внутри.

MemoryStorage здесь остаётся проверочным инструментом. Один и тот же сервис можно запустить с памятью в unit-тесте и с JSON в обычном приложении.

**Проверка владельца правила.** Кто должен решить, можно ли завершить задачу с таким id: CLI, Task или PlannerService? CLI только передаёт id. Task меняет собственный статус. Поиск задачи и сценарий операции принадлежат service.

## 06. Тонкий CLI и точка сборки

CLI является переводчиком между текстовой командой и прикладным сервисом. Пользователь вводит строку. CLI разбирает её, вызывает метод service и превращает результат в сообщение.

### Что делает CLI

Для команды done 3 CLI может:

1. разобрать текст done и число 3;
2. вызвать service.mark_done(3);
3. показать пользователю обновлённую задачу или сообщение об ошибке.

CLI не должен:

- открывать JSON-файл напрямую;
- искать задачу в словарях;
- самостоятельно считать статистику;
- вычислять следующий id;
- менять is_done в обход метода модели;
- решать, когда вызывать save().

Такой интерфейс остаётся маленьким даже при добавлении нового клиента. Web-обработчик или тестовый скрипт смогут вызвать тот же service без копирования логики меню.

### Точка сборки

Конкретные реализации соединяются в одном месте:

~~~python
def build_service():
    storage = make_storage()
    return PlannerService(storage)
~~~

Для обычного запуска make_storage() выбирает JsonStorage с постоянным путём. Для теста можно передать MemoryStorage или временный JsonStorage. Точка сборки знает конкретный класс. Service знает только роль зависимости.

### Путь относительно файла приложения

Путь, зависящий от текущей папки терминала, может вести к разным файлам при одинаковой команде. Для устойчивого локального запуска путь обычно строят относительно __file__:

~~~python
from pathlib import Path

base_dir = Path(__file__).resolve().parent.parent
data_file = base_dir / "data" / "tasks.json"
~~~

Фрагмент показывает идею расположения. Он не означает, что каждая функция должна сама вычислять путь. Вычисление остаётся в точке сборки, а путь передаётся в JsonStorage.

### Импорт не должен запускать меню

Модуль можно импортировать ради build_service() или отдельной функции. Если меню запускается прямо при импорте, тесты внезапно начинают ждать input().

Безопасная граница выглядит так:

~~~python
if __name__ == "__main__":
    main()
~~~

Она отделяет импортируемый код от обычного запуска процесса. Это особенно важно теперь, когда нужно тестировать storage и CLI в изоляции.

**Найдите нарушение.** В функции команды есть Path.read_text(), ручной цикл по JSON и Path.write_text(). Какая часть исчезнет из CLI после исправления? Работа с форматом и сохранением уйдёт в JsonStorage, поиск и изменение уйдут в PlannerService.

## 07. Отдельные проверки и один вертикальный сценарий

Новый слой стоит проверять по границам, а не только одним большим запуском.

### От модели к файлу

Сначала проверяется round trip модели. Затем JsonStorage проверяется через временный путь. Это разные доказательства:

- модель умеет переводить себя в внешний формат;
- storage умеет сохранить список;
- новый storage умеет восстановить объекты;
- ошибки файла не маскируются пустым результатом.

tmp_path нужен не ради модного инструмента. Он даёт изолированное место, которое не зависит от настоящего data/tasks.json и не загрязняет проект тестовыми данными.

### От сервиса к двум storage

После файловых тестов нужно убедиться, что service не зависит от реализации. Запустите один прикладной сценарий через MemoryStorage, затем аналогичный сценарий через временный JsonStorage. Результат должен быть согласованным, хотя внутренняя механика различается.

### Что делать с xfail

В каркасе уже может быть тест, который честно отмечен как ожидающий будущую persistence-реализацию. Такой xfail является указателем работы, а не способом скрыть любую ошибку.

Сначала проверьте:

- импорт модулей;
- существующее in-memory поведение;
- правильный временный путь;
- причину ожидаемого падения.

Снимайте xfail только после того, как тот же сценарий проходит через новый экземпляр JsonStorage. Если тест падает из-за импорта или пути, это ещё не доказательство готового storage.

### Вертикальный сценарий

После локальных проверок соедините части:

~~~text
отсутствующий файл
    ↓
добавить Python и README
    ↓
найти README
    ↓
завершить Python
    ↓
получить статистику
    ↓
удалить README
    ↓
создать новый service
    ↓
увидеть сохранённую Python
~~~

Этот сценарий показывает работу продукта, но не заменяет unit-тесты. Он нужен, чтобы увидеть, как границы работают вместе. Тесты помогают локализовать проблему, сценарий доказывает пользовательский результат.

**Вопрос.** Почему повторный вызов load() в том же экземпляре недостаточен для проверки persistence? Потому что состояние могло остаться в памяти. Новый экземпляр с тем же Path проверяет именно внешний файл.

## 08. Что мы будем делать в практике

Практика продолжит уже готовое in-memory ядро. К концу работы Persistent Planner должен уметь сохранять задачи между запусками и предоставлять оставшиеся операции через service и CLI.

### Общий результат

Мы добавим сериализацию к существующей Task, реализуем JsonStorage, сделаем ошибки файла видимыми, расширим PlannerService, подключим CLI и пройдём один пользовательский сценарий от отсутствующего файла до нового запуска.

### Роли и границы

- models.py добавляет только переход Task в dict и обратно, не становясь файловым адаптером;
- storage.py реализует JSON-файл и переводит ошибки формата в StorageError;
- MemoryStorage остаётся готовой реализацией для быстрых тестов;
- services.py добавляет операции чтения и изменения, но не знает JSON;
- cli.py разбирает команды и показывает результаты;
- main.py выбирает JsonStorage и соединяет зависимости;
- tests/ доказывает round trip, ошибки, сервисные операции и persistence.

### Крупный путь

Сначала расширьте существующую модель сериализацией. Затем снимите ожидающий тест и подключите реальный файл. После этого отделите повреждённые данные от первого запуска. Далее добавьте оставшиеся операции сервиса и подключите тонкий CLI. В конце проверьте новый экземпляр приложения и обновите README.

Не переписывайте готовые dataclass, инварианты, tags, mark_done(), MemoryStorage, add_task() и list_tasks() без причины. Это не новые результаты текущей работы.

### Доказательство результата

Готовность будет видна по нескольким наблюдениям:

- round trip возвращает Task;
- новый JsonStorage читает сохранённые задачи;
- отсутствие файла даёт пустой список;
- повреждённый файл даёт StorageError;
- сервис одинаково работает с памятью и временным JSON;
- CLI не открывает JSON сам;
- после удаления и нового запуска остаётся ожидаемая задача;
- pytest проходит, README объясняет запуск, в Git нет временных данных.

### Границы

В этой работе не добавляем FastAPI, базу данных, ORM, авторизацию и новую архитектурную подсистему. База данных будет естественным следующим вариантом storage, но сейчас достаточно понять и проверить границу persistence на JSON.

### Главное

- сериализация переводит объект в простые данные, а десериализация восстанавливает модель;
