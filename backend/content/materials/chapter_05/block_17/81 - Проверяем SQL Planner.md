## Маршрут объяснения для Stage 3

### 00. От работающего проекта к проверяемой точке

Во вступлении `LinkedNotes variant="connected"` связать общую SQLite для двух интерфейсов с задачей получить наблюдаемую точку перед исследованием схемы. Уточнить разницу между принятой версией, наличием возможности и фактически воспроизведённым действием. Проверить входную диагностику из A; не подменять её успешным `/health`, который не проверяет базу.

### 01. Какая база получит запись

Показать на отдельном демонстрационном пути происхождение настройки: `load_settings` читает `DATABASE_URL` из окружения, `.env` загружается без замены уже заданной переменной, при отсутствии используется `project/data/planner.sqlite3`; относительный путь разрешается от корня `project/`, а не от случайной папки терминала. Одна директория и одинаковый порт API не доказывают общий файл. Привести понятный пример URL и его разрешённого абсолютного пути, отдельно объяснить, что `sqlite:///` является URL, а не именем файла. Настройку задают **до** старта каждого процесса; изменение переменной в другом окне не перенастроит уже запущенный процесс.

Первая проба: в двух терминалах из `project/` ученик задаёт одинаковый учебный URL, тем же Python выводит `load_settings().database_url`, сопоставляет нормализованный путь с выбранным файлом и объясняет отличие от рабочего пути. Сначала показать результат на другом пути. Если адрес не определён, база уже занята неизвестными данными или процессы смотрят в разные файлы, остановиться до записи и исправить конфигурацию; не удалять и не перезаписывать чужую базу.

### 02. Явная подготовка и переход между процессами

На отдельной демонстрационной базе показать выбор нового каталога и пути, явную команду `python -m app.DBase.init_db` из `project/` тем же интерпретатором окружения, запуск локального API и CLI из README. Дать ориентиры: POST `/tasks` возвращает 201 и ID, GET `/tasks/{id}` читает публичные поля; команды `find`, `done`, `exit` вводят в меню CLI, а не в оболочку. После изменения нужен новый процесс и повторное чтение: короткая SQL Session открывается на запрос или распознанную команду, но данные сохраняются в файле. Сравнить фактические ID и значения, не только HTTP-статусы.

Независимый пример: преподаватель создаёт синтетическую задачу «Разобрать карты» с приоритетом 2 через API в демонстрационной базе, завершает её CLI и новым процессом перечитывает статус. Первая проба ученика использует другую задачу и отдельный пробный файл: создать через один интерфейс, изменить через другой, закрыть его и перечитать в новом процессе. Это не набор данных основной практики. Объяснить, что непустую неизвестную базу нельзя считать чистой, а `create_all` создаёт отсутствующие таблицы и не исправляет существующую схему.

### 03. Внутренние поля и наблюдение без подмены интерфейса

Объяснить, что публичный ответ содержит `id`, `title`, `priority`, `is_done`, но не `tags` или `title_normalized`. На отдельном учебном SQLite-образце с другими строками показать подготовку JSON-массива tags через SQL `UPDATE` с ограничением по ID, проверку числа затронутых строк и чтение `SELECT`; сравнить данные до и после. Отсутствующий ID обновит ноль строк, а отсутствие `WHERE` изменит все строки. Ученик сначала сам пробует изменение одной другой строки и проверяет соседа до переноса приёма в Planner.

Для Stage 3 подготовить полный независимый пример с Python 3.12 `sqlite3` из стандартной библиотеки: открыть **уже существующий** разрешённый файл через URI `mode=rw`, `uri=True`, передать значения параметрами, сериализовать список как JSON, выполнить явный `commit` только после проверки и `rollback` при ошибке, закрыть соединение и заново прочитать значения. Показать, как получить корректный URI из абсолютного пути, включая пробелы; не смешивать его с SQLAlchemy URL. Проверка пути и ID предшествует `UPDATE`. Это синтетическая подготовка данных, а не новый публичный способ управления tags.

### 04. Ошибка и свидетельство результата

На других данных показать недопустимый POST с приоритетом вне диапазона 1–5: 422 сам по себе ещё не доказывает отсутствие записи, поэтому сравнить количество и ID до и после. Объяснить разницу между проверкой пользовательского сценария, изолированными тестами и исходным историческим прогоном: ни одна из них не заменяет остальные. Подготовить переход к собственной диагностике: хранить только синтетические названия, адрес и наблюдаемые значения, а при расхождении сначала восстановить предпосылку.

## Проектная практика

**Старт.** У ученика доступен принятый `project/`, рабочее Python-окружение с зависимостями из README и два терминала. Не устанавливать зависимости внутри задания без восстановления окружения по README. В `project/` выбрать новый отдельный каталог, например `data/lesson81/`, и отсутствующий файл `planner.sqlite3`; создать каталог, но не подменять рабочую базу. Для этого примера указать в обоих терминалах `DATABASE_URL=sqlite:///data/lesson81/planner.sqlite3`, вывести фактический разрешённый URL через настройки и сверить с выбранным новым путём. Примеры команд PowerShell в Stage 3 должны явно показывать установку `$env:DATABASE_URL` в каждом терминале и один и тот же `.venv/Scripts/python.exe`. Если файл уже существует или путь не совпадает, выбрать новый путь, соответственно изменить URL в обоих терминалах и повторить проверку, не очищая существующий.

**Действие.** После проверки пути создать пустую схему исходной командой из раздела 02 и проверить успешное завершение. Запустить API согласно `project/README.md` на свободном локальном порту, убедиться, что ответ принадлежит собственному процессу, и проверить пустой список. Создать через POST две задачи с разными названиями и приоритетами из диапазона, записать возвращённые ID и все публичные поля. Подготовить для каждой разные синтетические непустые JSON-массивы tags SQL-приёмом из раздела 03, проверить ровно по одной строке и сохранить исходные значения всех шести столбцов `tasks`.

Найти одну задачу GET по её ID, открыть CLI с тем же адресом, найти её по ID и завершить командой `done`; закрыть CLI через `exit`. В новом процессе CLI перечитать обе записи, затем запросить обе через API и отдельно через SQL прочитать `id`, `title`, `priority`, `is_done`, `tags`, `title_normalized`. Сопоставить со снимком до изменения: у выбранной задачи изменился только статус, у соседа все поля прежние; оба ID, tags и нормализованные названия сохранены. Проба раздела 02 подготавливает переход интерфейсов, раздел 03 подготавливает безопасное наблюдение внутренних полей.

**Отказ и тесты.** Отправить POST с недопустимым приоритетом, зафиксировать 422 и повторно сравнить число строк и ID с состоянием перед запросом; новая запись не появилась. Если SQL-запрос попал не в одну строку или чтение расходится с ожиданием, остановиться, откатить незавершённую транзакцию, проверить путь и ID; не объявлять сценарий пройденным. Запустить существующий набор изолированных тестов командой из `project/README.md` тем же интерпретатором, записать итог и возможную ошибку. Тесты работают на своих временных базах и не заменяют ручную проверку именно выбранного файла; исторические 176 тестов не являются результатом нового запуска.

**Подсказка и разбор для автора.** Подсказка направляет проверить разрешённый путь в обоих процессах, фактический ID и `WHERE`, не выдавая последовательность готовых запросов. В разборе объяснить причинную связь общей настройки, сохранения транзакции и повторного чтения; отдельно разобрать расхождение адресов, ноль затронутых строк и 422 без проверки данных. Готовое решение или реализацию тестов в план не включать.

## Критерии и передача

- Путь отдельной базы и адрес обоих процессов подтверждены до записи; начальное состояние пустое. Две записи получены через API, различаются приоритетами, имеют разные внутренние tags; SQL setup изменил только нужные строки.
- До и после сохранены ID и все шесть существующих столбцов. Новый процесс видит завершённую задачу и неизменённого соседа; API и SQL подтверждают соответствующие публичные и внутренние поля. 422 сопровождается доказательством отсутствия новой записи.
- Записаны собственный результат тестов и ограничения проверки. При отсутствии контракта или несовпадении вернуться к настройке/предпосылке и повторить сценарий, не считать ошибку успехом.
- Следующей теме «Сверяем реальную схему» передать абсолютный путь исходной учебной базы и URL, число строк и упорядоченную по ID опись всех шести полей после сценария, включая обе записи и их tags, снимок до изменения и результат тестов без личных данных. Остановить API и CLI и закрыть соединения перед исследованием файла. База остаётся исходной; резервной, восстановленной и upgrade-копий ещё нет, история и revision отсутствуют, metadata остаётся исходной `Base`/`TaskRow`. Фактическую схему и её соответствие metadata следующий этап проверяет отдельно.
