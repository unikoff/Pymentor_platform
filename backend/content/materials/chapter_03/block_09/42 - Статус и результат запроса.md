## 00. Вступление

В `41.1` ученик собрал **модель request**: сообщение о том, что клиент хочет сделать. Здесь рассматривается следующий этап: сервер обработал обращение и возвращает **response** с числовой отметкой результата — status. Ученик сначала научится различать конкретные исходы, затем увидит группы статусов и сам напишет выбор числа по известной метке.

1. **Точка старта:** знакомы роли клиента и сервера; предыдущий шаг маршрута собирает request и различает отсутствие тела и пустой объект.
2. **Новый вопрос:** чем отличаются успешное чтение пустого списка, создание задачи, успешное удаление без данных и отсутствие конкретной задачи?
3. **Результат:** ученик объясняет эти исходы отдельно от содержимого ответа, затем сам выбирает точный код в `solve(outcome)`.

Первая учебная проверка после входа из `41.1`: по схеме «клиент → request → сервер → response → клиент» ученик указывает, **кто** сообщает status и почему запись Python-словаря request не является отправкой по сети. К содержимому response вернёмся в `42.1`.

## 01. Response сообщает результат между программами

- Что и зачем объяснить: сервер формирует HTTP response для клиента; `print()` показывает текст в терминале, а `return` передаёт значение вызывающему коду внутри Python. Ни то ни другое само по себе не является сообщением через HTTP.
- Механизм и порядок: сначала по схеме из `00` вспомнить границу клиент/сервер, затем назвать response и выделить в нём status как **трёхзначное целое число** — сигнал исхода. В Python-примерах код — учебная модель статуса, реального обмена нет. Не переходить к структуре headers и body.
- Пример и типичная путаница: готовая ситуация «внутренняя функция вернула число» против «сервер ответил клиенту». Результат `return` не следует принимать за status ответа.
- Первое самостоятельное действие: в схеме обмена указать, **где** status увидит клиент; затем отличить её от похожей картинки «функция вернула число вызывающей функции». Наблюдаемый результат — ученик объясняет направление response и не выдаёт `print()` за HTTP-ответ. Схема нужна как опора для предсказания, не как украшение.
- Переход к следующему шагу: разобрать конкретные результаты обращения, прежде чем обобщать их по группам.

## 02. Четыре конкретных результата: 200, 201, 204, 404

- **Механизм для новичка:** сначала сервер выясняет, чем завершилась обработка; **потом** выбирает status. `200 OK` — успешно получен результат чтения (список может быть пустым); `201 Created` — создан новый ресурс; `204 No Content` — операция успешно завершена и содержимого ответа нет (в нашем договоре — успешное удаление); `404 Not Found` — запрошенный **конкретный** ресурс не найден. Код относится к **результату обращения**, не к количеству объектов внутри списка.
- **Независимый объяснённый пример:** клиент просил перечень задач, сервер его успешно получил и обнаружил `[]`: результат чтения существует, значит `200`. Другой клиент запросил задачу с определённым id, но такой задачи нет: `404`. Здесь не обсуждать формат JSON или сборку response; `[]` служит только наглядным обозначением пустого списка.
- **Безопасная проба без кода:** после этих двух случаев предложить ученику новый контраст: «задачу только что создали» против «задачу успешно удалили и не возвращают содержимое». Ученик **сначала** словами называет исход, **затем** выбирает между `201` и `204` и объясняет, почему оба статуса означают успех, но не одно и то же. Критерий: не выдаёт `200` для любого успеха и не обещает JSON при `204`.
- **Возврат при затруднении:** маленькая таблица смыслов «прочитали — 200; создали — 201; завершили без содержимого — 204; нужного item нет — 404»; таблица служит справочником, а не заранее записанным кодом `solve`.
- **Переход:** понять, почему разные числа можно объединять в общие классы, не теряя точного смысла каждого.

## 03. Класс кода даёт ориентир, но не заменяет точный status

- **Механизм:** у трёхзначных статусов первая цифра обозначает класс: `2xx` — успешная обработка, `4xx` — запрос не может быть выполнен по причине на стороне клиента/запрошенного ресурса, `5xx` — непредвиденная проблема на стороне сервера. Это ориентиры, **не** новые коды для возврата: функция возвращает целое `200`, а не текст `2xx`.
- **Разбор примера из 02:** `200`, `201`, `204` относятся к `2xx`, хотя означают разные успешные исходы; `404` относится к `4xx`. Первая цифра отвечает на вопрос «какая группа?», оставшиеся цифры уточняют «что произошло?». `4xx` не означает, что программа клиента обязательно сломана: запрошенного item могло просто не быть.
- **Первое самостоятельное действие:** разложить четыре ранее объяснённых кода по группам и сравнить `200`/`204`: одинаковый класс, разные ожидания относительно содержимого. Наблюдаемый результат — ученик умеет прочесть группу, но для конкретной ситуации называет **полный** код.
- **Возврат:** при сомнении назвать исход обычными словами → найти точный код → проверить, согласуется ли его первая цифра с исходом. Не определять status по телу или видимости сообщения.
- **Переход:** расширить карту на два учебных отказа и научиться отделять их от `404`.

## 04. Различаем ошибочный запрос, отсутствие item и сбой сервера

- **Механизм:** `400 Bad Request` — общий пример запроса, который нельзя обработать в его текущем виде; `404 Not Found` — запрошенного отдельного ресурса нет; `500 Internal Server Error` — внутренняя проблема сервера. `400` и `404` относятся к `4xx`, `500` — к `5xx`. Источник проблемы устанавливаем по описанию **результата обработки**, а не по тому, показал ли экран текст ошибки.
- **Точный учебный контраст:** сервер смог обработать запрос списка и вернул пустой список — `200`; сервер не нашёл **запрошенную задачу** — `404`; запрос в целом нельзя обработать в текущем виде — учебный `400`; внутри сервера возникла непредвиденная проблема — `500`. Для будущего Planner неверное поле тела проверяется по отдельному контракту `422`: **не предлагать** подставлять туда `400` как универсальную ошибку валидации.
- **Самостоятельное действие:** ученик получает **новые короткие описания** «обратились к отсутствующему item», «сервер столкнулся с внутренним сбоем» и «запрос отклонён как некорректный»; называет вид причины, выбирает `404`/`500`/`400` и отдельно обосновывает выбор класса. Условие успеха — не подменяет `404` ошибкой сервера и не считает любой `4xx` одинаковым.
- **Опора и переход:** вопрос «обработка успешна? нужного ресурса нет? сам запрос отвергнут? сервер не справился?» готовит шесть исходов для кодовой функции. HTTPException и обработчики ошибок здесь не нужны.

## 05. Исход обработки превращается в точный status

- Что и зачем объяснить: функция получает одну метку известного исхода и возвращает соответствующее целое число. Это выбор по закрытому набору значений, а не построение HTTP-ответа.
- Механизм и порядок: на малом **независимом от HTTP** примере «режим уведомления → числовой уровень» объяснить заголовок `def`, строковый параметр, двоеточие, отступ, точное `==`, цепочку `if`/`elif` и `return` целого числа. Показать различие `return` и `print()`, проследить один вход и результат, затем дать ученику самому записать ещё одну ветку **для этого независимого сюжета**. Только после этого перейти к пустому телу `solve(outcome)`; значения HTTP в готовое ветвление не подставлять. Если синтаксис уже уверенно выполнен на пробе, эту опору пройти кратко.
- Пример и типичная путаница: `read_ok` и `not_found` нельзя объединять как «результат чтения»; метка `created` возвращает код, а не строку с названием. В отличие от прежней функции сборки `status/headers/body`, новая функция только выбирает status. Она не печатает ответ и не изменяет вход.
- Первое самостоятельное действие: после собственной ветви в независимом примере в заготовке `def solve(outcome):` с пустым телом самостоятельно записать выбор для чтения, создания и завершения без содержимого. Для каждой метки проследить одну исполненную ветку и целый результат. **Сначала** имя исхода и объяснение его смысла, **потом** код и Python-синтаксис; в заготовке нет готовой цепочки условий.
- Опора для повторного обращения: при каждом вызове сверить имя исхода с его смыслом и вернуть целое значение; не подменять `return` на `print()`.
- Переход к следующему шагу: добавить оставшиеся исходы отказа и проверить смысловое применение всей таблицы.

## 06. Один ресурс, разные исходы в разные моменты

- **Что и зачем:** шесть веток `solve` проверяют знание таблицы, но при реальном чтении ситуации нужно сначала определить **факт обработки**. Статус нельзя вывести из id задачи, наличия текста ответа или пустого списка без контекста.
- **Короткая трассировка на новом сюжете:** в учебной истории задача с id `7` существует; клиент успешно прочитал её, затем задача была успешно удалена без содержимого ответа, а позже клиент снова попытался прочитать **этот же** id и не нашёл задачу. Без написания клиента/методов/API ученик отмечает три разных результата: `read_ok`/`200` → `deleted`/`204` → `not_found`/`404`. Подчеркнуть: одинаковый id не означает одинаковый outcome, статус описывает итог **конкретного** обращения.
- **Различающий вопрос:** отдельно прочитан список задач, в котором сейчас нет элементов. Ученик объясняет, почему это `read_ok`/`200`, а не `not_found`/`404` и не `deleted`/`204`; отсутствие элементов списка отличается от отсутствия запрошенного item и от успешного действия без body.
- **Первое самостоятельное действие:** предложить **изменённую** историю с другой задачей и переставленным порядком событий: сначала безуспешно ищут конкретную задачу, затем её создают, затем успешно читают список. Ученик самостоятельно называет метки и статусы по шагам, обосновывает каждый исход. Критерий — правильные переходы `404 → 201 → 200`, а не одно число на весь рассказ; эта история служит устным переносом, её не превращать во вторую кодовую задачу.
- **Переход:** функция проверит шесть точных меток, а короткий разбор истории — умение определить метку по смыслу без подсказки названия.

## 07. Что мы будем делать в практике

**Обязательный формат по принятому паспорту `42`:** одна автопроверяемая редакторская задача `solve(outcome)` и короткое устное объяснение различающего случая. MAIN предоставляет только точку входа и место для записи тела; готовых условий выбора и возвращаемых статусов в заготовке нет. Аргумент — одна из шести **точных строковых меток** `read_ok`, `created`, `deleted`, `bad_request`, `not_found`, `server_error`; ответ — целое число HTTP status, без печати и изменения данных. Входы вне этого закрытого набора не проверяются и специального поведения не требуют. Здесь не нужны отправка HTTP-запросов, чтение JSON или код проекта Planner.

Практика движется от самостоятельной записи успешных ветвей к дополнению функции отказами, а затем к переносу на незнакомую историю:

1. **Самостоятельно сопоставить успешные исходы.** Вход: предоставленная MAIN сигнатура `solve(outcome)` с незаполненным телом и метки `read_ok`, `created`, `deleted` из общего договора. Объект: тело **этой** функции. Опоры: смысл 200/201/204 в разделе 03; запись `if`/`elif`, `==` и `return`, отдельно восстановленная в разделе 05. Ученик сам пишет ветви выбора и возврата целого числа, не дополняя готовый алгоритм. **Проверка сразу:** вызовы `solve("read_ok")`, `solve("created")` и `solve("deleted")` в редакторе/интерпретаторе дают соответственно 200, 201 и 204; результат можно посмотреть отдельно для каждого вызова, не дожидаясь остальных ветвей.
2. **Добавить отказ и ошибку сервера.** Вход: собственная функция после шага 1 и три оставшиеся метки `bad_request`, `not_found`, `server_error`. Объект: дополнительные ветви **той же** функции с сохранением работающих успешных ветвей. Опоры: различие 4xx/5xx в разделе 02, причины в разделе 04 и техника выбора в 05. Ученик сам записывает условия и возвраты, не получая готового фрагмента решения. **Проверка сразу:** отдельные вызовы с новыми метками возвращают 400, 404 и 500, а повторные вызовы с тремя прежними метками сохраняют 200, 201 и 204; значения имеют тип `int` и не требуют `print()` внутри `solve`.
3. **Перенести правило на новый рассказ без готовой метки.** Вход: проверенная функция шага 2 и **другая история, чем в разделе 06**: клиент успешно получает пустой список задач; затем запрашивает отдельную задачу `id=24`, которой нет; после этого задачу с этим id создают, а позднее успешно удаляют без содержимого ответа. Объект: **устное рассуждение** по четырём последовательным событиям, без новой кодовой задачи. Опоры: разница списка и item из раздела 02, исход и класс из 03–04, смена состояния из 06. Ученик **до подсказки с метками** самостоятельно выводит для каждого события outcome и status и объясняет, почему пустой список не является 404 и почему успешное удаление без содержимого — 204, а не 200. **Проверка сразу:** получены `read_ok`/200 → `not_found`/404 → `created`/201 → `deleted`/204, при этом ученик объясняет каждый переход; на одном коротком дополнительном описании отличает общий `bad_request`/400 от `server_error`/500. В реальном Planner ошибку валидации не объявлять 400: это будущий отдельный контракт 422.

**Критерий всей практики:** шаг 1 сам возвращает правильные три успешных `int`; шаг 2 добавляет три отказа и сохраняет предыдущие ветви; шаг 3 проверяет, что статус выбирается по **исходу обращения**, а не по видимому содержимому или одному лишь id. При затруднении ученик возвращается к шагам 02–04 за смыслом, к 05 за ветвлением, к 06 за изменением результата во времени. Полный обязательный закрытый набор — шесть известных исходов; устный перенос — одно новое сочетание ситуаций. Неизвестные входы, HTTP-body, заголовки, методы и фактический обмен с сервером не входят в условие завершения.
