## Точка B: наблюдаемый результат

Ученик **самостоятельно** составляет для всех восьми действий `list`, `get`, `create`, `replace`, `update`, `delete`, `health`, `stats` словарь с правильными `method` и `path` с помощью `solve(action, task_id)`. Он берёт метод из готовой таблицы `methods`, но **сам решает**, какой нужен путь: `/tasks` для коллекции, `/tasks/{task_id}` для одной задачи или `/health` и `/stats` для служебных операций.

В объяснении ученик отделяет ресурс от Python-класса и файла хранения, называет collection и item, понимает endpoint как пару `method + path` по договорённости курса и не объявляет задачу существующей лишь потому, что получил её id. Для двух разных id получаются разные адреса item. Программа ничего не печатает, не отправляет и не меняет.

## Границы и передача

- **Обязательно:** публичная задача имеет поля `id`, `title`, `priority`, `is_done`; внутренние `tags` не появляются в публичной модели. Ресурс — то, с чем работает API, представление — данные для клиента, хранение — внутренняя реализация. Один path может участвовать в нескольких операциях с разными методами.
- **Пока не требуем:** реализацию FastAPI/роутера, работающий сервер, сетевые запросы, проверку существования id, вычисление статуса/`404`, работу с JSON-файлом, query/body, валидацию, авторизацию и полный набор архитектурных ограничений REST. Термины REST и stateless можно пояснить одной границей: здесь проектируется ресурсный стиль адресов, а не доказывается «полная REST-совместимость».
- **Передаём `45`:** готовое умение получить пару `method/path` и понять, когда id является частью path. На входе `45` дать новое действие с новым id и проверить объяснение пары; `route_for` следующей практики будет дана отдельно. Не объявлять перенос кода из `44` обязательным.

## 01. Ресурс — что доступно через API

- **Объяснение:** ресурс — то, к чему клиент обращается через API. В нашем случае это задачи. Клиенту не нужно знать, лежит ли задача в `data/tasks.json` или позже будет храниться иначе. Внешнее представление — набор данных, который API согласился показать: `id/title/priority/is_done`. Внутренний `Task` может содержать `tags`, но это не даёт права добавлять их в публичный ответ.
- **Независимый пример:** библиотека показывает посетителю карточку книги (название и автор), а у библиотекаря хранится дополнительный служебный инвентарный номер и заметки. Книга — предмет обращения; карточка — представление; складской учёт — внутренняя реализация. **Предел аналогии:** API передаёт данные, а не физическую книгу; разные операции могут возвращать разные представления.
- **Первая проба:** разложить «задача», «публичные поля задачи» и «класс `Task` / JSON-файл» по трём ролям. Проверка: ученик не предлагает путь вида `/data/tasks.json` как публичный адрес задачи.
- **Для MAIN:** короткая схема «клиент → представление ← сервер → внутреннее хранение» и вопрос на объяснение, что останется неизменным при замене JSON на другое хранилище. Схема нужна для причинного различения, не как украшение.
- **Переход:** если клиент обращается к задачам, надо различить весь набор и одну конкретную задачу.

## 02. Collection и item — набор или одна задача

- **Объяснение:** `collection` — адрес набора однотипных объектов, у Planner это `/tasks`. `item` — адрес одного элемента по его идентификатору, шаблон `/tasks/{task_id}`; фигурные скобки здесь обозначают **место для конкретного id**, а не часть конечного адреса. Например, при `task_id = 7` конечный путь `/tasks/7`. Слово «коллекция» здесь относится к ресурсу API, а не обязательно к типу `list` в Python.
- **Второй независимый пример:** архив обращений: `/tickets` называет набор, `/tickets/28` — обращение с номером 28. Номер не означает «28-й элемент списка» и не гарантирует, что запись с таким номером существует. **Предел аналогии:** это соглашение об адресах, а не проверка архива.
- **Первая проба:** показать `/tasks`, `/tasks/12` и `/tickets/28`; ученик указывает, где набор, где отдельный элемент, и называет id. Затем объясняет, почему создание новой задачи обращается к набору, хотя результатом будет один новый элемент.
- **Для MAIN:** интерактив на *предсказание масштаба*, затем короткая расшифровка ответа. Не повторять дважды одну классификацию в соседних карточках.
- **Переход:** item-адрес зависит от значения id; нужно уметь подставить его самостоятельно.

## 03. Адрес с id: шаблон и конкретное значение

- **Объяснение:** `{task_id}` в схеме — переменная часть пути. В реальном строковом path вместо неё стоит переданное значение. `task_id` — идентификатор задачи, **не индекс списка**, не новое вычисляемое число и не доказательство существования записи. Выбор и проверка записи будут задачей будущего сервера.
- **Механизм на другом сюжете до практики:** при `book_id = 12` выражение `f"/books/{book_id}"` даёт строку `/books/12`. Две точки внимания: буква `f` перед кавычками позволяет подставить значение, а фигурные скобки в *f-строке* содержат имя переменной. Без `f` получается буквальный текст с фигурными скобками. Связать это с `return` строки, `if` и готовой таблицей словаря, если входная проба выявила пробел.
- **Первая проба:** предсказать `/books/5` и `/books/91` при двух значениях `book_id`; затем в Planner назвать, какая часть `/tasks/7` изменится при новом id. Проверка: меняется только последний сегмент item-пути; `/tasks` и `/health` не зависят от id.
- **Для MAIN:** небольшая наглядная стрелка «шаблон → подстановка → строка» и одно действие с переносом на новое число, без кода полного `solve`.
- **Переход:** не каждое действие вообще требует номера конкретной задачи.

## 04. Служебные пути — `/health` и `/stats`

- **Объяснение:** `/health` нужен для проверки состояния сервиса, `/stats` — для агрегированных сведений о задачах. Эти пути входят в API, но не являются адресами отдельной задачи. Для них не нужен `task_id`, и не следует придумывать `/tasks/{task_id}/stats`. Здесь они имеют метод GET из готовой таблицы.
- **Сравнение:** `/tasks` — набор задач; `/tasks/7` — конкретный item; `/health` — состояние сервиса; `/stats` — сводка. Все четыре являются **шаблонами адресов**, на которых строятся восемь операций. У `/tasks/{task_id}` конкретных строк может быть много.
- **Первая проба:** среди четырёх запросов найти тот, где нужен id, и два технических пути; отдельно объяснить, почему сводка обо всех задачах не является item. Проверка не требует вычислять саму статистику.
- **Для MAIN:** одно сопоставление маршрута с назначением и отдельная короткая причина для `/stats`; не добавлять вторую карточку с тем же выбором.
- **Переход:** выбранный path показывает, *к чему* обращаются. Метод показывает, *что делают*.

## 05. URL, path и endpoint — не смешивать адрес и действие

- **Объяснение:** полный URL может выглядеть как `https://api.example.test/tasks/7`. Его path здесь — `/tasks/7`; протокол и имя сервиса не входят в path. Если в URL есть `?limit=10`, это query-часть, а не часть path; значения query ученик распределит в `45`.
- **Объяснение endpoint:** в рамках этого курса endpoint — **сочетание HTTP-метода и шаблона path**. Например, два запроса к `/tasks` с разными методами могут выполнять разные операции. У термина бывают более широкие значения в документации; для задачи `44` важна рабочая пара `method/path`, которую возвращает `solve`. Конкретный id подставляется в строку path.
- **Независимая проба:** для архива `GET /tickets/28` и `DELETE /tickets/28` спросить: одинаковый ли объект выбран и одинаковое ли намерение? Ответ проверяет разницу *адреса* и *действия*. Затем выделить path из знакомого URL, не обсуждая серверный обработчик.
- **Для MAIN:** визуально показать рядом две пары с одним path и разными методами, предложить предсказать различие и пояснить причину. После визуала — не больше двух читаемых абзацев до следующего осмысленного действия.
- **Переход:** применить оба выбора к Planner, где методы уже определены прежним занятием.

## 06. Как выбрать адрес для Planner

- **Правило, которое учим выводить:** сначала узнать действие (`action`), затем решить, нужен ли **набор** (`list`/`create`), **один item** (`get`/`replace`/`update`/`delete`) либо **служебная информация** (`health`/`stats`). Только для item требуется подставить `task_id`. Метод берётся из уже данной таблицы `methods`, составлять её заново не нужно.
- **Короткий разбор до практики:** на намерении «создать задачу» объяснить, почему адресуют коллекцию, а не ещё не существующий id; на «проверить состояние сервиса» показать, почему не нужен путь к задаче. Не разбирать полную готовую функцию и не выдавать восемь окончательных ответов: остальные варианты ученик выбирает в редакторе самостоятельно.
- **Различающий случай:** `GET` к item и `DELETE` к тому же item используют один конкретный path, но разные методы. Передача id 999 не равна утверждению, что в хранилище есть задача 999; задача `solve` — только описать адрес запроса.
- **Первая проба:** из трёх новых намерений ученик сам выбирает область и объясняет её одним предложением. Проверить отдельно, не превращён ли `create` в item и не получил ли `stats` чужой id.
- **Для MAIN:** связанная цепочка «намерение → область → method/path» с прогнозом на двух контрастах, затем переход к написанию функции. Не дублировать предыдущие викторины; учащийся впервые самостоятельно применяет правило к новым действиям.

## 07. Что мы будем делать в практике

**Формат:** автопроверяемая задача в редакторе `CODE_TASKS[44]`, функция `solve(action, task_id)`. По существующей заготовке ученик получает готовый словарь `methods` для всех восьми действий и заголовок функции с `pass`. Сам пишет **всё тело функции**: выбирает path, берёт `methods[action]` и возвращает словарь ровно с ключами `method` и `path`. Не давать в теории или стартере готового ветвления для выбора path. Устное объяснение дополняет, но не заменяет автопроверку.

**Договор:** `action` — одна из восьми известных строк. Для `get`, `replace`, `update`, `delete` приходит целый `task_id`; для `list`, `create`, `health`, `stats` — `None`. Неизвестные действия, невалидные id и реальное содержимое хранилища здесь не рассматриваются. Результат — две строки в словаре; никакого `print`, внешней сети, запросов или изменения данных. Этот договор совпадает с паспортом BLOCK_9 и фактическим стартером `CODE_TASKS[44]`.

1. **Предсказать адрес до кода.** Вход: восемь названий действий, объяснения `02`/`04`/`06` и готовые методы из `43`. Объект: выбор области у каждого действия. Самостоятельно: отметить collection, item либо служебный адрес и обосновать спорные `create` и `stats`. Локальный результат: 2 действия обращаются к collection, 4 — к item, 2 — к специальным путям; при ошибке вернуть к `02` и `04`. Это классификация, а не готовое решение функции.
2. **Проверить подстановку id.** Вход: `('get', 7)`, `('get', 34)`, `('list', None)` и `('health', None)`; значение id приходит из аргумента, а не вычисляется. Объект: конкретные строки path до написания `solve`. Опора: `02–03` (шаблон, id, f-строка), `04` (служебные адреса). Самостоятельно: предсказать четыре строки и объяснить, почему меняется только путь item. Локальный результат: два разных item-адреса, неизменный `/tasks` для collection и `/health` без id; ошибка `"/tasks/{task_id}"` вместо подстановки ведёт обратно к `03`.
3. **Написать и проверить `solve`.** Вход: готовые `methods` и сигнатура; результаты шагов 1–2. Объект: тело одной функции и возвращаемый словарь. Опора: `05–06`, проверенные перед началом `if/elif/else`, словарь, `return` и f-строка. Самостоятельно: построить выбор path для трёх типов области, применить аргумент `task_id` только там, где нужен item, взять метод из `methods`, вернуть точные два поля. Локальный результат: для каждой из восьми операций пара правильна; для каждого item-действия проверены **минимум два разных id**; одинаковый `/tasks` у list/create сочетается с разными методами, а `health` и `stats` не содержат id. Проверка не требует будущего сервера. Если ошибочен метод — перечитать таблицу; если путь — вернуться к классификации или подстановке.
4. **Объяснить перенос на новое значение.** Вход: уже полученная функция и неизвестный заранее id, например `256`, для `get` и `delete`. Объект: прогноз пары и причинный разбор. Опора: `01–06`. Самостоятельно: назвать одну и ту же область item, разные намерения и отсутствие гарантии существования id. Локальный результат: ученик предсказывает изменение только конкретного id в адресе, объясняет разные методы и не приписывает `solve` сетевых действий/проверок хранения. Это новая ситуация, а не повторение восьми входов из автопроверки.

**Итог B:** ученик сам написал выбор path и возвращает точный `method/path` для восьми операций и разных id; смысл выбранного адреса объясняет на новом примере. Задание `45` отдельно добавит распределение данных по path/query/body. В MAIN создавать конкретные карточки, подсказки и тесты после этого плана; закрытый эталон `solve` в теорию не переносить.
