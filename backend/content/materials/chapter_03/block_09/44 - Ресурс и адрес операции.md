## 01. Ресурс, представление и реализация

- Что и зачем объяснить: ресурс — предмет, доступный через API; для Planner это задачи. Клиент обращается к согласованному внешнему представлению задачи, а не к объекту Python или месту хранения.
- Механизм и порядок: различить три уровня: предмет задачи как ресурс; публичные поля, передаваемые клиенту; внутренняя модель, файл или будущая база на стороне сервера. Для Planner публичное представление включает `id`, `title`, `priority`, `is_done`; внутренний `Task` также хранит `tags`, но клиентский договор их здесь не публикует.
- Пример и типичная путаница: на независимом примере книги в каталоге показать ресурс, карточку с выбранными полями и внутреннюю строку хранилища. Аналогия с витриной помогает отделить видимую карточку от учёта на складе, **но** карточка не заменяет все способы представления одной книги. Не называть ресурсом Python-класс или запись JSON; не считать публичное представление полной внутренней моделью.
- Первое самостоятельное действие: для примеров Planner распределить названия «задачи», «публичные четыре поля», «класс Task / файл» по трём уровням. Результат — ученик может указать, что видит клиент и что остаётся реализацией сервера.
- Опора для повторного обращения: ресурс — предмет; представление — согласованные внешние данные; реализация — внутренний способ работы. В практике адрес выбирается для первого уровня, а не для файла или класса.
- Переход к следующему шагу: если клиент обращается к ресурсу независимо от реализации, выяснить, какие общие соглашения помогают разным клиентам одинаково понимать интерфейс.

## 02. REST как контекст соглашений

- Что и зачем объяснить: REST — архитектурный стиль, а не библиотека и не синоним JSON. HTTP-запрос с JSON сам по себе не доказывает полную реализацию REST; в этой главе используются практические ресурсные соглашения.
- Механизм и порядок: кратко раскрыть stateless: запрос содержит контекст текущего действия, поэтому серверу не нужно угадывать его по предыдущему запросу клиента. Отделить это от хранения состояния самого приложения: задачи могут сохраняться на сервере. Упомянуть остальные ограничения REST только как обзор, без самостоятельной цели и без подробного курса.
- Пример и типичная путаница: на независимом примере службы обращений сравнить чтение обращения с указанным id и вопрос «серверу запрещено хранить обращения?». Наблюдение: самодостаточность запроса не означает отсутствие сохранённых данных.
- Первое самостоятельное действие: ученик объясняет, почему запрос к обращению может содержать всё для выбора нужного объекта, хотя данные остаются на сервере. Результат — stateless не смешан с отсутствием постоянного состояния.
- Переход к следующему шагу: общие соглашения становятся видны в адресе, когда сначала выбирают набор или отдельный элемент.

## 03. Collection и item

- Что и зачем объяснить: адрес одного ресурса может обозначать collection — набор задач — или item — отдельную задачу. Это разные масштабы выбора внутри одного ресурса.
- Механизм и порядок: сопоставить `/tasks` с набором и `/tasks/{task_id}` с задачей по id. Уточнить, что id задаёт, какой item просит клиент, но не подтверждает наличие такой записи. Связать это с уже освоенным методом: один path может сочетаться с разными методами и обозначать разные действия.
- Пример и типичная путаница: сначала независимая аналогия адреса зала библиотеки и отдельного тома по каталожному номеру, затем чтение списка задач и задачи с id 7. Номер выделяет предмет запроса, **но** физический адрес на полке не равен HTTP-path и аналогия не доказывает существование книги. Не трактовать номер в path как позицию списка и не обещать проверку существования до реализации сервера.
- Первое самостоятельное действие: определить масштаб выбора по нескольким готовым path и назвать, где присутствует item-id. Результат — collection и item различены без вычисления позиции или проверки хранилища.
- Опора для повторного обращения: `/tasks` выбирает набор; `/tasks/{task_id}` выбирает один item; идентификатор — указание, а не доказательство существования. В практике переданный id используется только при сборке item-path.
- Переход к следующему шагу: имея область ресурса, выбрать единый стиль именования пути и отделить обычные операции от технических маршрутов.

## 04. Имя ресурса и технические маршруты

- Что и зачем объяснить: в обычной карте path называет ресурс, а method уже сообщает действие. Повторять действие в адресе не нужно.
- Механизм и порядок: сравнить ресурсный адрес item с адресом, в котором имя действия встроено в path. Пояснить, что это рабочее соглашение данного API, а не абсолютный запрет на глаголы или специальные пути.
- Пример и типичная путаница: на независимом примере удаления обращения выбрать между общим ресурсным path с методом DELETE и путём с `delete` в имени. Затем разобрать `/health` как техническую проверку и `/stats` как агрегированный ответ: это маршруты интерфейса, не новые доменные сущности и не требование CRUD.
- Первое самостоятельное действие: найти в короткой готовой карте путь, который дублирует действие, и предложить ресурсный вариант; отдельно определить, почему health и stats остаются специальными маршрутами. Результат — ученик сохраняет единый ресурсный стиль, не превращая соглашение в безусловный запрет.
- Переход к следующему шагу: перед картой Planner нужно точно выделить path внутри полного URL и определить, что вместе с ним задаёт операцию.

## 05. URL, path и endpoint

- Что и зачем объяснить: URL — полный адрес; path — часть после узла сервиса. На занятии 41 ученик уже выделял path в готовом URL; здесь достаточно кратко восстановить это различие и перейти к endpoint, не повторяя разбор URL.
- Механизм и порядок: на одном URL кратко показать схему, узел, path и наличие query-части. Query обозначить как отдельную часть URL и передать её подробное назначение занятию 45. Сравнить две операции с одинаковым path и разными методами; отметить, что термин endpoint в документации используют неодинаково, а в этом курсе закрепляется конкретное рабочее значение.
- Пример и типичная путаница: на URL списка выделить `/tasks` как path, не включая в него query. На паре запросов к одному item показать, что выбранный объект совпадает, а действие различается. Не смешивать URL целиком с path и не называть endpoint только доменным адресом.
- Первое самостоятельное действие: в готовом URL указать path и отделить query; затем объяснить, какую информацию теряют, если читать только path без method. Результат — ученик восстанавливает пару операции и не забегает в правила разбора query.
- Опора для повторного обращения: URL — полный адрес; path — область ресурса; endpoint по договору курса — method + path. Query существует отдельно и будет разобран в следующем занятии.
- Переход к следующему шагу: применить ресурс, масштаб, технические адреса и рабочее определение endpoint к Planner.

## 06. Карта операций Planner

- Что и зачем объяснить: перед кодом карту читают с точки зрения клиента: предмет и масштаб выбираются path, действие — методом. В карте Planner есть collection, item и два технических маршрута.
- Механизм и порядок: вывести карту из намерений и результата занятия 43: list/create направлены на collection; get/replace/update/delete — на item; health/stats — на отдельные служебные адреса. Шесть операций над задачами используют готовые методы из 43; две технические записи health и stats впервые появляются здесь и их GET уже указан в `methods`. Уточнить, что восемь операций используют четыре шаблона path. Для публичного представления сохранить четыре поля и не добавлять `tags`.
- Пример и типичная путаница: сопоставить один метод для collection и другой метод для того же path, затем один item с двумя разными методами. Не смешивать число операций с числом уникальных путей и не считать, что карта проверяет наличие задачи.
- Первое самостоятельное действие: на нескольких намерениях выбрать collection, item или технический маршрут и объяснить выбор. Результат — ученик может применить общее правило, а не только запомнить строку одного адреса.
- Опора для повторного обращения: сначала классифицировать действие и область; затем взять метод из готовой таблицы и построить path. Для item подставляется данный id; для остальных действие не получает item-id. Таблица методов уже готова, новые методы не создаются.
- Переход к практике: теперь можно самостоятельно связать заданное действие с методом из заготовки и подходящим path, не отправляя запрос.

## 07. Что мы будем делать в практике

**Формат и исходная опора:** редакторская code-практика `solve(action, task_id)` с коротким устным пояснением; это фактическая форма `CODE_TASKS[44]` (также есть в исторической задаче 49), пока обязательность не сверена с недоступным паспортом. В стартовом коде ученику уже дана таблица `methods` для восьми допустимых `action` и заголовок функции с `pass`; таблицу и саму сигнатуру переписывать не нужно. Результат прежней карточки не импортируется. Для `get`, `replace`, `update`, `delete` передан целый `task_id`, для `list`, `create`, `health`, `stats` передан `None`. Проект, API и локальный JSON не меняются.

**Договор входа и выхода:** `action` принимает только восемь перечисленных строк; неизвестные действия и некорректный тип `task_id` не входят в упражнение.
