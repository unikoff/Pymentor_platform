Ученик предлагает, что должно находиться в двух пробелах; в §01 получит названия «request/server/response». Схемы изображают предполагаемый обмен, а не уже созданный HTTP-интерфейс Planner. ## 01. От локального вызова к обращению клиента

- **Объяснить с нуля, по шагам:** *клиент* — программа, начинающая обращение; *сервер* — программа, принимающая обращение и формирующая результат. *Request* — сообщение клиента серверу, *response* — ответное сообщение сервера клиенту. Человек может нажимать кнопку браузера, но сообщение отправляет клиентская программа. Сервер по правилам приложения может обратиться к своим функциям и данным; сервер хранит/изменяет состояние, а клиент обычно не читает серверный файл напрямую. Два процесса могут находиться на **одном компьютере**: роли определяет направление обращения, а не физическая удалённость.
- **Механизм в порядке событий:** клиент создаёт request → отправляет серверу → сервер разбирает запрос → обращается к своей внутренней логике (при необходимости к JSON) → формирует response → клиент получает результат. Объяснить, что наличие запроса ещё не означает успех: response нужен и чтобы узнать о проблеме; подробные HTTP-статусы изучаются в `42`. Здесь не вводить реализацию сети/роутера.
- **Контраст на знакомой операции:** в локальном CLI команда «показать задачи» приводит к вызову Python-функции **внутри Planner**; при обращении из браузера к будущему API программа-клиент направит request программе-серверу, и **сервер** уже сможет вызвать PlannerService. Браузер не умеет по имени вызывать чужую Python-функцию и не получает прямого доступа к `data/tasks.json`. Это объяснение возможной архитектуры, пока HTTP API не написан.
- **Учебный визуал до проверки:** две дорожки `CLI → PlannerService → JSON → результат в CLI` и `клиент (браузер) → request → сервер → PlannerService/JSON → сервер → response → клиент`. Вторая дорожка гипотетическая; границу между клиентом и сервером показать отдельно от вызова функции *внутри* сервера. Схемы использовать для трассировки, не как декоративные стрелки.
- **Первая собственная проба (без подсказок на схеме):** дать новый сюжет «отдельная программа на том же ноутбуке запрашивает список задач». Ученик указывает две программы, стрелкой обозначает, кто посылает request, кто response, и в чьей зоне находятся правила/JSON. Критерий: инициатор — клиент, обработчик — сервер, response идёт обратно, JSON не становится файлом клиента. При ошибке сначала вернуть к стрелкам, затем предложить новый сценарий «клиент спрашивает о задаче 7».
- **Опора для возврата:** четыре роли/события на схеме и одно различие: локальный вызов функции происходит *в программе*, request/response — *между программами*. После ответа на вопрос «кто общается?» переходим к «куда клиент адресует request?».

## 02. URL выбирает сервис

- Что и зачем объяснить: URL — строка адреса, по которой клиент может найти точку обращения к сервису. На учебном примере показать только **схему**, **host** и **необязательный порт**, затем следующую часть — path. `localhost` обозначает текущую машину **для программы, которая использует этот адрес**; сам по себе не запускает сервер.
- Механизм и порядок: сначала выделить часть, выбирающую сервис, затем отделить следующий за ней path. Не углубляться в DNS, сетевые протоколы, настройку порта или query.
- Пример и типичная путаница: разобрать вымышленный `https://demo.example.test:8443/notes/7`: `https` — схема, `demo.example.test` — host, `8443` — указанный порт, `/notes/7` — path. Для сравнения показать `http://localhost:8000/tasks`, пояснив, что `localhost` относится к машине, на которой открывают адрес, и не означает «сервер уже запущен». Оба адреса — только учебные строки.
- Первое самостоятельное действие: после размеченного первого адреса самостоятельно разделить `http://localhost:8000/tasks` на четыре части; затем решить, есть ли явный порт в `https://demo.example.test/notes`. Критерий: `/tasks` и `/notes` обозначены как path, `localhost` — host, порт на втором адресе **не указан**, а не равен части path. Это **визуальное чтение** готовых строк, не требование программно разбирать URL в `solve`.
- Учебный визуал: одна размеченная строка `схема://host:порт/path` с цветовым/текстовым разделением частей, затем такая же строка без подписей для самостоятельной разметки. Это модель строения URL, без объяснения DNS и соединения.
- Опора для повторного обращения: схема задаёт способ обращения, host и необязательный порт помогают указать сервис, path обозначает место обращения внутри него.
- Переход к следующему шагу: сервис выбран, теперь отделяем ресурс внутри его внешнего адреса от локального файла проекта.

## 03. Path указывает место внутри сервиса

- Что и зачем объяснить: path — часть URL после адреса сервиса, указывающая путь внутри API; в упражнении это готовая строка, которую функция возвращает. Достаточно примеров `/tasks` и `/tasks/7`, не вводя карту ресурсов.
- Механизм и порядок: отделить host и порт от path, затем сравнить path с путём к локальному файлу и с именем Python-функции. Path относится к внешнему адресу API, файл — к локальному хранению проекта.
- Пример и типичная путаница: сопоставить `http://localhost:8000/tasks/7` (path `/tasks/7`) и локальный путь `data/tasks.json`; они отвечают на разные вопросы: «куда клиент обращается в API?» и «где проект хранит данные?». Сервер *может* обслуживать `/tasks/7` без одноимённого файла, каталога `tasks/7` или Python-функции с этим именем. Path определяют правила сервера, которые будем изучать позже.
- Аналогия с границами: адрес здания помогает найти организацию, номер кабинета — точку обращения внутри неё. Но path — не обязательный реальный «кабинет» или каталог на диске, а внешний адрес, смысл которого определяет сервер.
- Первое самостоятельное действие: после модели с `/tasks/7` дать новую пару `https://demo.example.test:8443/events/17` и `data/events.json`; ученик указывает **точный** path `/events/17`, файл и отвечает, можно ли по одному path определить имя Python-функции (нет). Критерий — не включает host и порт в path, не подменяет адрес файлом. Если перепутал, показать запрос к URL и чтение файла как **разные** действия, затем повторить на `/tasks`.
- Учебный визуал: рядом две подписанные цепочки `URL → /notes/7` и `локальное хранилище → data/notes.json`; ученик проводит связь только с верным типом пути.
- Опора для повторного обращения: правило «host выбирает сервис, path — место внутри него; путь API не равен пути файла».
- Переход к следующему шагу: path показывает, куда направлено обращение, но ещё не объясняет его намерение.

## 04. Method выражает намерение

- Что и зачем объяснить: method — отдельное поле запроса, обозначающее **вид запрошенного действия**, а path показывает точку обращения внутри сервиса. Метод не гарантирует, что операция успешно выполнится: сервер сначала должен обработать сообщение. На одном и том же path возможны разные методы — без таблицы всех CRUD-операций.
- Механизм и порядок: сравнить готовые пары с GET и POST на одном path только как пример разного намерения. Не обучать здесь полному выбору метода для CRUD — это отдельное занятие 43.
- Пример и типичная путаница: `GET /tasks` и `POST /tasks` имеют одинаковый `/tasks`, но разное обозначенное намерение (например, получить список или попросить создать запись). Здесь это **готовые подписи запроса**, а не доказательство работы сервера. `GET` не является частью path или URL и не вычисляется из имени Python-метода Planner. Пока ученик **узнаёт данное значение**, а не выбирает метод для операции: выбор будет в `43`.
- Аналогия с границами: в заявке есть отдельные поля «куда обращаемся» и «какой вид обращения». Так и method хранится отдельно от path. Аналогия не определяет, какие методы сервер поддерживает, и не заменяет точную семантику HTTP.
- Первое самостоятельное действие: дать две новые карточки `GET /notes` и `POST /notes`: ученик заполняет два поля каждой карточки, указывает одинаковую и изменившуюся части и объясняет, почему одна строка не становится другой при смене path. Критерий — `GET`/`POST` подписаны как method, `/notes` как path; порядок действий на сервере **не угадывается** по этой паре.
- Учебный визуал: две карточки запроса с одинаковым полем `path` и различным `method`, затем пара карточек с пустыми подписями для самостоятельного распределения готовых значений.
- Опора для повторного обращения: краткая пара вопросов «что сделать? — method» и «куда обратиться? — path». Входной method дан заранее; ученик не угадывает его по действию.
- Переход к следующему шагу: теперь method и path можно соединить в учебное представление без отправки сообщения по сети.

## 05. Учебная пара method/path

- Что и зачем объяснить: отделить смысловую модель от реального сетевого обмена. В 41 учебный словарь намеренно содержит только `method` и `path`; в 41.1 к нему будут добавлены headers/body.
- Механизм и порядок: Python-функция получает два **готовых** строковых аргумента. Для учебной модели строит словарь с ключами `method` и `path` и **возвращает** его вызывающему коду. Значение под ключом `method` в действующем упражнении должно быть записано прописными буквами, а под ключом `path` — посимвольно та же входная строка. Код **не** должен разбирать URL, делать сетевой запрос или менять аргументы.
- Независимый пример **до** функции `solve`: показать результат выражения `"post".upper()` → `"POST"`, затем `original = "post"; changed = original.upper()` и спросить, какая строка хранится в `original` (по-прежнему `"post"`). `.upper()` возвращает **новое значение**, а не меняет существующий аргумент. Отдельно показать, что в `/Tasks/07` важны прописная `T` и ноль перед `7`: `path.upper()` или `.lower()` здесь нарушит условие.
- Перед самостоятельным кодом: таблица **преобразований, не готовой реализации**: вход `method="get"` → поле `method` со значением `"GET"`; вход `path="/Tasks/07"` → поле `path` со значением `"/Tasks/07"`. Напомнить структуру словаря `{ключ: значение}` и смысл `return` (отдаёт результат вызывающему) против `print` (лишь печатает в консоль). Ввод и `input()` не нужны, аргументы переданы автопроверкой.
- Первая собственная проба перед редактором: дать **другую** пару `method="patch"`, `path="/notes/7"`; ученик без подсказки называет **ровно два ключа**, отмечает поле для преобразования и поле для дословного переноса, прогнозирует, изменится ли входной `method`. Критерий: ожидает `PATCH`, `/notes/7` и неизменные аргументы, а не создание/отправку HTTP-запроса.
- Учебный интерактив: показать два ошибочных решения **на уровне результата**, без кода `solve`: `{method: "patch", path: "/notes/7"}` (некорректно указан тип ключей и регистр значения) и «на экране напечатан верный словарь, но функция вернула `None`». Ученик объясняет, что именно исправить, не получая готовое тело функции.
- Опора для повторного обращения: **два входа → два точных ключа → значение method в верхнем регистре → path без изменений → return**; это учебный договор, не нормализатор реальных HTTP-запросов.
- Переход к практике: ученик самостоятельно соберёт словарь, а в `41.1` тот же принцип готовой пары дополнят headers и body; реализации `solve` из карточки `41` новый редактор не наследует.

## 06. Что мы будем делать в практике

**Формат из паспорта `41`:** кодовая задача в редакторе с автопроверкой `solve(method, path)` (существующий ключ `41` в `code_tasks.py`). Преподаватель коротко проверяет планируемые опоры (функция, строки, `.upper()`, словарь, `return`) и при пробеле восстанавливает их на *другом* маленьком примере до задания. Стартовый код содержит заголовок функции и `pass`; тело пишет ученик. Входы — готовые строки, выбор метода, разбор URL и сетевое обращение **не требуются**. До редактора — короткая смысловая модель, после — устное объяснение, но автопроверяемый код обязателен.

**Итоговый договор:** функция возвращает словарь **ровно** с ключами-строками `"method"` и `"path"`: значение method в верхнем регистре, значение path в точности как на входе. Входной метод может быть `"get"`, `"post"` или `"patch"`; входные строки не изменяются, stdout пуст. На примере `"get"`, `"/tasks/12"` результат должен быть `{"method": "GET", "path": "/tasks/12"}`. Это **ожидаемое значение**, а не раскрытие кода решения. Оба входа уже даны; здесь не разрабатывают маршрут, не выбирают действие Planner, не запускают API.

1. **Проследить обращение и выделить пару (не автотест).** Вход: новый сюжет «программа-клиент просит у будущего сервера запись» и карточка `POST https://sample.example.test:8443/boards/8`; рядом локальный файл `data/boards.json`. **Объект:** стрелки обмена и подписи, не программный парсер. **Опора:** схема §01, размеченный URL §02 и различение путей §03. **Самостоятельное действие:** ученик обозначает, кто создаёт request, кто response, отдельно подписывает `method=POST` и `path=/boards/8`, отличает URL от файла. **Локальная проверка:** response направлен обратно клиенту, `POST` не попал внутрь URL, `/boards/8` не содержит host, файл не назван частью API. Если ошибка в стрелке, вернуть к §01; если перепутан path, сопоставить две цепочки §03. Подробный разбор полного URL в дальнейшем **не нужен** для `solve`.
2. **Самостоятельно написать тело `solve` (автопроверяемое действие).** Вход: данная редактором сигнатура `solve(method, path)` и аргументы `("get", "/tasks/12")`; **объект:** возвращаемый словарь, не сообщение консоли. **Опора:** независимый пример `.upper()`, таблица двух полей и `return` из §05. **Самостоятельное действие:** написать код, который сохраняет готовый path, отдельно обрабатывает значение method и возвращает словарь **ровно** с двумя строковыми ключами; готового тела `solve` в плане и на предварительной карточке нет. **Проверка:** сравнить вызов с `{"method": "GET", "path": "/tasks/12"}`; проверить, что ввод не меняется и `print` не используется. При `None` вернуться к отличию `return`/`print`, при `"get"` в результате — к смыслу `.upper()`, при третьем ключе — к точному договору.
3. **Перенести логику, не подменяя path (различающие входы).** Вход: та же функция и **независимые** пары `("post", "/tasks/9")`, `("patch", "/tasks/3")`; затем дополнительная самостоятельная самопроверка `("get", "/Tasks/07")`. **Объект:** выходы одного кода для новых данных. **Опора:** правило §05 «меняем только регистр значения method, путь переносим дословно». **Самостоятельное действие:** до запуска записать прогноз для каждой пары, запустить код, сравнить с точными значениями; при несовпадении найти первое нарушенное поле и исправить своё решение. **Критерии:** автотесты действующего `code_tasks.py` ожидают `{"method": "POST", "path": "/tasks/9"}` и `{"method": "PATCH", "path": "/tasks/3"}`; ручная различающая самопроверка ожидает `{"method": "GET", "path": "/Tasks/07"}` (заглавная `T` и `0` сохранены). Обязательные автотесты также проверяют сохранность входов и отсутствие stdout; **дополнительный** пример не заявлен существующим автотестом.

**Итоговая проверка B и передача:** на **другой** ситуации ученик сам показывает client → request → server → response, называет разницу между `/tasks/12` и `data/tasks.json`, объясняет смысл пары method/path и предъявляет возвращённый словарь для обычного и различающего примеров. Он отдельно проговаривает: «это результат Python-функции, запрос по сети не отправлен». Если роли путаются, вернуться к §01; если path меняется — к §03/05 и повторить отличающийся вход. Для `41.1` подготовлена концептуальная пара method/path; следующая карточка получает готовые аргументы, добавляет headers/body и не зависит от сохранения кода этой задачи. Состояние Planner/CLI не изменено; HTTP-сервер не объявлен созданным.
