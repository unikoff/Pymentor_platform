## 01. От локального вызова к обращению клиента

- Что и зачем объяснить: коротко восстановить границу между локальным вызовом внутри CLI и обращением отдельного клиента. Роли уже есть в историческом занятии 45; здесь это входная опора, не новая большая тема.
- Механизм и порядок: ученик сначала называет клиента и сервер в готовой ситуации, затем связывает отдельного клиента с сообщением, которое сервер разбирает прежде, чем вызвать внутреннюю логику. При затруднении дать краткое повторное объяснение до новых терминов.
- Пример и типичная путаница: сопоставить знакомый локальный Planner/CLI и отдельный браузер, который просит показать задачи. Браузер не вызывает Python-метод по его имени и не открывает серверный `tasks.json` напрямую.
- Первое самостоятельное действие: в готовой паре ситуаций указать, где локальный вызов, а где обращение отдельного клиента; наблюдаемый результат — роли восстановлены и HTTP-сообщение не названо прямым вызовом функции.
- Конкретный материал для действия: ситуация А — CLI Planner вызывает локальный `PlannerService`; ситуация Б — открытый отдельно браузер обращается к адресу сервиса за списком. Ученик подписывает «клиент», «принимающая сторона», «внутренний вызов» только там, где это уместно, и объясняет, почему адрес браузера нельзя заменить именем Python-функции.
- Учебный визуал: две короткие стрелочные схемы `CLI → функция сервиса` и `браузер → запрос → сервер → функция сервиса`; ученик сам отмечает границу между программами. Схемы не утверждают, что сервер уже реализован в Planner.
- Опора для повторного обращения: кто начинает обращение, кто его принимает и где выполняется внутренняя работа; локальный вызов функции принадлежит одной программе.
- Переход к следующему шагу: после восстановления участников выясняем, какой адрес выбирает клиент.

## 02. URL выбирает сервис

- Что и зачем объяснить: на примере URL показать схему, host и необязательный порт как адрес сервиса. `localhost` назвать адресом текущей машины в примере; рабочий сервер и порт в этом занятии не запускаются.
- Механизм и порядок: сначала выделить часть, выбирающую сервис, затем отделить следующий за ней path. Не углубляться в DNS, сетевые протоколы, настройку порта или query.
- Пример и типичная путаница: разобрать вымышленный `https://demo.example.test:8443/notes/7`: `https` — схема, `demo.example.test` — host, `8443` — указанный порт, `/notes/7` — path. Для сравнения показать `http://localhost:8000/tasks`, пояснив, что `localhost` относится к машине, на которой открывают адрес, и не означает «сервер уже запущен». Оба адреса — только учебные строки.
- Первое самостоятельное действие: на втором адресе без подсказанных границ отдельно отметить схему, host, порт и оставшуюся часть; критерий — `/tasks` не попадает в host/порт, а `localhost` не назван именем файла.
- Учебный визуал: одна размеченная строка `схема://host:порт/path` с цветовым/текстовым разделением частей, затем такая же строка без подписей для самостоятельной разметки. Это модель строения URL, без объяснения DNS и соединения.
- Опора для повторного обращения: схема задаёт способ обращения, host и необязательный порт помогают указать сервис, path обозначает место обращения внутри него.
- Переход к следующему шагу: сервис выбран, теперь отделяем ресурс внутри его внешнего адреса от локального файла проекта.

## 03. Path указывает место внутри сервиса

- Что и зачем объяснить: path — часть URL после адреса сервиса, указывающая путь внутри API; в упражнении это готовая строка, которую функция возвращает. Достаточно примеров `/tasks` и `/tasks/7`, не вводя карту ресурсов.
- Механизм и порядок: отделить host и порт от path, затем сравнить path с путём к локальному файлу и с именем Python-функции. Path относится к внешнему адресу API, файл — к локальному хранению проекта.
- Пример и типичная путаница: сопоставить `http://localhost:8000/tasks/7` (path `/tasks/7`) и локальный путь `data/tasks.json`; они отвечают на разные вопросы. Сервер *может* обслуживать `/tasks/7` без одноимённого файла или Python-функции.
- Аналогия с границами: адрес здания помогает найти организацию, номер кабинета — точку обращения внутри неё. Но path — не обязательный реальный «кабинет» или каталог на диске, а внешний адрес, смысл которого определяет сервер.
- Первое самостоятельное действие: по новому `https://demo.example.test:8443/notes/7` выделить path и отдельно выбрать, какая из строк `/notes/7` или `data/notes.json` принадлежит URL, а какая обозначает локальный файл. Критерий — точное `/notes/7` без префикса host и без подмены на файловый путь.
- Учебный визуал: рядом две подписанные цепочки `URL → /notes/7` и `локальное хранилище → data/notes.json`; ученик проводит связь только с верным типом пути.
- Опора для повторного обращения: правило «host выбирает сервис, path — место внутри него; путь API не равен пути файла».
- Переход к следующему шагу: path показывает, куда направлено обращение, но ещё не объясняет его намерение.

## 04. Method выражает намерение

- Что и зачем объяснить: method отвечает на вопрос о намерении клиента; path отвечает, куда направлено обращение. На одном и том же path показать разные методы, не превращая занятие в таблицу CRUD.
- Механизм и порядок: сравнить готовые пары с GET и POST на одном path только как пример разного намерения. Не обучать здесь полному выбору метода для CRUD — это отдельное занятие 43.
- Пример и типичная путаница: GET `/tasks` и POST `/tasks` имеют один path, но это не одно и то же сообщение. Метод не является частью path и не выводится из имени локального метода Planner. Пока методы **даны**, а не выбираются учеником по сценарию.
- Аналогия с границами: в заявке есть отдельные поля «куда обращаемся» и «какой вид обращения». Так и method хранится отдельно от path. Аналогия не определяет, какие методы сервер поддерживает, и не заменяет точную семантику HTTP.
- Первое самостоятельное действие: сравнить две новые готовые строки `GET /notes` и `POST /notes`, отдельно подписать method/path и указать неизменную часть; критерий — ученик не считает GET частью `/notes` и не пытается угадать метод по операции Planner.
- Учебный визуал: две карточки запроса с одинаковым полем `path` и различным `method`, затем пара карточек с пустыми подписями для самостоятельного распределения готовых значений.
- Опора для повторного обращения: краткая пара вопросов «что сделать? — method» и «куда обратиться? — path». Входной method дан заранее; ученик не угадывает его по действию.
- Переход к следующему шагу: теперь method и path можно соединить в учебное представление без отправки сообщения по сети.

## 05. Учебная пара method/path

- Что и зачем объяснить: отделить смысловую модель от реального сетевого обмена. В 41 учебный словарь намеренно содержит только `method` и `path`; в 41.1 к нему будут добавлены headers/body.
- Механизм и порядок: функция получает готовые `method` и `path`, возвращает словарь с этими двумя ключами, применяет знакомый `.upper()` только к method и сохраняет path без изменения. Это договор редакторского упражнения, а не автоматическое исправление реального HTTP-запроса.
- Пример и типичная путаница: метод приводится к верхнему регистру по условию упражнения; это не отправка запроса и не автоматическое исправление произвольного HTTP-клиента. Не добавлять headers, body, сериализацию JSON или `print`.
- Перед самостоятельным кодом: показать таблицу «входная строка `method` → поле `method` (верхний регистр)» и «входная строка `path` → поле `path` (символ в символ)»; отдельно напомнить различие `return` и `print` из занятия 13. Таблица объясняет правила преобразования без раскрытия реализации `solve`.
- Первое самостоятельное действие: на переданных `method="post"`, `path="/notes/7"` устно предсказать, какое значение изменится и какое сохранится, а затем самостоятельно собрать словарь в редакторе для другой пары. Критерий — два точных поля, изменён только регистр method, `path` не нормализуется.
- Учебный интерактив: перед показом сверки ученик помечает для каждого поля «сохранить» или «преобразовать» и объясняет, почему прямой `print` не удовлетворяет возвращаемому результату. Эта проверка предшествует финальному коду.
- Опора для повторного обращения: method хранит намерение и нормализуется; path хранит адресную часть и возвращается без изменения.
- Переход к практике: готовый словарь станет самостоятельным результатом упражнения и смысловой опорой для 41.1; следующий кодовый редактор получит готовые method/path в своей заготовке.

## 06. Что мы будем делать в практике

**Формат и исходная опора:** в текущем плане предусмотрена исследовательская редакторская code-задача `solve(method, path)` с автопроверкой и коротким устным разбором; отнесение к формату И сверить с отсутствующим каноническим паспортом. Основа — подтверждённые функции, строки и словари. В редакторе дана сигнатура `solve(method, path)` и два готовых строковых аргумента при вызове; код внутри функции ученик пишет самостоятельно. Карточка самодостаточна: решение не передаётся в 41.1 автоматически. Сетевую библиотеку не подключаем, Planner не меняем.

Общий результат — функция возвращает словарь ровно с ключами `method` и `path`: method в верхнем регистре, path без изменения. Входной method дан строкой (`get`, `post` или `patch`), path дан готовой строкой; ученик не выбирает метод по действию, не меняет входы и не отправляет реальный HTTP-запрос.

1. **Распознать части запроса.** Вход: текстовая карточка `POST https://demo.example.test:8443/notes/7` и для сравнения локальное `data/notes.json`. Объект работы: подписи к частям запроса до редакторского кода. Опора: размеченный URL и карточки из разделов 01–04, но текущий пример оставлен без подписей. Самостоятельно указать схему/host/порт/path и отдельно method. Локальная проверка: `POST` не включён в URL, path назван точно `/notes/7`, локальный путь не назван частью адреса сервиса. Дать исправить ошибку на карточке до следующего шага; текстовая разметка не выдаётся за автотест Python.
2. **Собрать учебный словарь.** Вход: заготовка `solve(method, path)` и переданные строки, например `"get"` и `"/tasks/7"`. Объект: возвращаемое значение функции, не распечатка. Опора: таблица преобразований и знакомые `.upper()`, словарь, `return` из раздела 05; готовой реализации `solve` в условии нет. Самостоятельно написать тело функции с ровно двумя заданными полями. Локальная проверка: вызов возвращает словарь с ключами `method`, `path`, первый содержит верхний регистр, второй исходную строку; аргументы не меняются и консольный вывод отсутствует. При неверном числе ключей или `None` ученик исправляет собственный код.
3. **Перенести правило на изменённые входы.** Вход: независимые вызовы `("post", "/tasks")`, `("patch", "/tasks/7")` и различающий случай `("get", "/Tasks/07")`; последний нужен, чтобы поймать непрошеное изменение регистра или сегмента path. Объект: та же функция из шага 2. Опора: формула из двух отдельных полей, без выбора метода по смыслу действия. Ученик сначала прогнозирует, какое поле изменится, затем выполняет вызовы и сверяет результат; автопроверка проверяет точные ключи, регистр method, посимвольное сохранение path, отсутствие побочных эффектов. Локальный критерий: все три вызова удовлетворяют одному договору независимо от вида path; ученик объясняет, почему изменение входных строк не требует менять логику функции.

Переход от исторического занятия 45 плавный: роли уже встречались, но здесь сначала быстро проверяются; новое начинается с формы адреса и намерения. Затем распознавание переходит в самостоятельную сборку словаря, а изменённые входы подтверждают перенос без введения выбора метода. Итог подтверждает B только для чтения и представления method/path. В 41.1 тот же смысл расширится headers/body на готовых входных method/path; завершённый Planner и его CLI остаются без изменений, HTTP-интерфейс не объявляется созданным.
