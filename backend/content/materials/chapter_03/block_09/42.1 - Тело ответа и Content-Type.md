## 01. Заголовки принадлежат сообщению response

- Что и зачем объяснить: заголовки — метаданные сообщения; ответные headers описывают передаваемый response и не заменяют status или body. Кратко сопоставить `Accept` из request, `Content-Type` передаваемого request-body и `Content-Type` ответа, не возвращаясь к полному построению request.
- Механизм и порядок: в принятом для упражнения договоре сервер добавляет `X-Request-ID` как идентификатор обращения, по которому сообщение можно соотнести с диагностической записью. Это не `Task.id`, который относится к предметной записи и может находиться в URL или body.
- Независимый пример и наглядность: в условной службе доставки номер посылки `parcel-7` — предметный идентификатор внутри данных, а номер обращения к поддержке `call-29` — метка самого обмена; нарисовать два вложенных прямоугольника «response (headers)» и «body (данные)» с разными метками. Предел аналогии: `X-Request-ID` **дополнительный заголовок принятого учебного договора**, HTTP не обязывает любой сервер добавлять его.
- Типичная путаница: один response содержит request ID и объект с собственным `id`; значения отвечают за разные сущности. Не называть request ID новым полем объекта и не приписывать ему выбор результата.
- Первое самостоятельное действие: показать учебное сообщение с `X-Request-ID: call-30` и `body={"id": "parcel-8"}`; ученик сам указывает, какой идентификатор помогает искать обращение и какой — посылку. Локальная проверка: две метки верно размещены в визуале, ни одна не заменена другой; затем повторить для новой пары меток.
- Опора для повторного обращения: при сборке ответа восстановить роль `X-Request-ID` и проверить, что в него попало переданное значение обращения, а не номер Task.
- Переход к следующему шагу: служебные сведения отделены от данных; теперь нужно определить формат данных body.

## 02. Body передаёт содержимое, а не исход

- Что и зачем объяснить: body может содержать данные успешного результата или детали ошибки. Наличие JSON само по себе не означает успех: исход уже задаёт переданный status.
- Механизм и порядок: в задаче Python-словарь моделирует JSON-объект в теле, но не является JSON-текстом, отправленным по сети. `print()` показывает данные человеку, а `return` передаёт их внутри программы; ни то ни другое не заменяет HTTP-response. Сериализацию обозначить как отдельное действие отправляющей системы, не обучать её реализации.
- Независимый пример: служба проката велосипедов отвечает на поиск свободного транспорта: `status=200, body={"dock": "C4"}` и `status=404, body={"detail": "Велосипед отсутствует"}`. В обоих случаях body есть, но из наличия словаря нельзя вывести успех. Для отличия `print`/`return` показать маленькую функцию, которая печатает `готово`, но возвращает словарь `{"found": False}`; ученик предсказывает видимый вывод и возвращаемое значение отдельно.
- Типичная путаница: поле `detail` — описание ошибки, а не замена status; модель Python не является сериализованным сетевым сообщением.
- Первое самостоятельное действие: для другого пункта проката ученик получает `status=404` и `body={"detail": "Место выдачи не найдено"}`, самостоятельно объясняет, чем подтверждена ошибка и для чего служит body; наблюдаемая проверка — называет status источником исхода, body источником подробностей, а `print` не считает отправкой HTTP.
- Опора для повторного обращения: перед сборкой проверить, что body остаётся переданным содержимым и не заменяется строкой, выводом или новым решением о статусе.
- Переход к следующему шагу: содержимое задано; заголовок теперь должен сообщить получателю его формат.

## 03. Content-Type описывает фактический формат body

- Что и зачем объяснить: `Content-Type: application/json` сообщает клиенту, как читать существующее тело. Заголовок не создаёт содержимое и не превращает Python-словарь в JSON.
- Механизм и порядок: сначала определить, передаётся ли body; если да — согласовать объявленный тип с форматом содержимого. **В контракте этой `solve`** при `body=None` заголовок `Content-Type` отсутствует. В реальном HTTP возможны сообщения, где метаданные описывают представление даже без передаваемого тела; подробности остаются за границами урока. Не превращать правило учебной функции в универсальный запрет заголовка. Заголовок — часть договора между отправителем и получателем.
- Независимый пример и вторая наглядная опора: этикетка на коробке сообщает получателю вид содержимого, но не кладёт предмет внутрь. Сравнить `Content-Type: application/json` с JSON-данными каталога и `Content-Type: text/plain` с обычным текстом; показать на схеме «фактическое содержимое → заявленный тип → как клиент интерпретирует». Предел аналогии: реальное HTTP-body — байты; заголовок не преобразует байты и не гарантирует, что отправитель честно указал формат.
- Типичная путаница: `Accept` заявляет предпочтение клиента в request, `Content-Type` описывает тело конкретного сообщения; два одинаково названных `Content-Type` в request и response относятся к разным сообщениям. В учебной `solve` формат всех существующих body заранее оговорён как JSON.
- Первое самостоятельное действие: ученик сравнивает два готовых сообщения проката — JSON-объект и строку обычного текста — и сам выбирает подходящую подпись типа, объясняя причину. Результат: тип соответствует телу, не зависит от того, успешен status или ошибочен; затем повторить на новом JSON-body ошибки.
- Опора для повторного обращения: восстановить правило «формат описывает содержимое; заголовок не сериализует его» и применить его до сборки `headers`.
- Переход к следующему шагу: для применения правила нужно точно различать отсутствие тела и тело с нулём элементов.

## 04. Отсутствующее тело, пустой объект и JSON null

- Что и зачем объяснить: различить три состояния: в контракте упражнения `None` обозначает отсутствующий body; `{}` — присутствующий пустой JSON-объект; JSON `null` — отдельное переданное значение, а не отсутствие HTTP-body.
- Механизм и порядок: проверка наличия выполняется по `body is not None`, а не по истинности значения. Поэтому пустой объект остаётся телом и получает `Content-Type`; `None` не получает JSON-заголовок. Не переносить учебную условность `None` на сериализованный JSON `null`.
- Независимый пример: для складской системы сопоставить «после команды не передали никакого отчёта» (`None`) и «передали пустой список обнаруженных товаров» (`[]`). В живом JSON тело с пустым массивом всё ещё существует; при этом текущая `solve` по контракту получает лишь словарь или `None`. Разобрать, почему проверка `if body` ошибочно объединяет эти случаи. В учебной модели ответ 204 имеет `body=None`, а `body={}` обозначает существующий JSON-объект.
- Типичная путаница: JSON `null` — это **байты тела со значением null**, тогда как Python `None` в данных учебной функции специально означает отсутствие тела; для текущей задачи `null` не является отдельным допустимым входом.
- Первое самостоятельное действие: ученик самостоятельно предсказывает для `body=None` и `body={}` условие `body is not None` и наличие JSON-заголовка. Наблюдаемая проверка: для `None` условие ложно, для `{}` истинно; затем сравнить с заведомо ошибочным `if body`, который потеряет пустой объект. Вернуться к этому правилу перед сборкой headers.
- Опора для повторного обращения: «None — нет body по условию упражнения; `{}` — есть пустой JSON; `null` — значение JSON»; перед проверкой заголовка выяснить, какое из состояний дано.
- Переход к следующему шагу: status уже известен; теперь клиент применит три части ответа в правильном порядке.

## 05. Клиент читает ответ по договору

- Что и зачем объяснить: опереться на статус из занятия 42, не повторяя каталог кодов. Показать последовательность: прочитать status, определить по договору, ожидается ли body, затем при наличии содержимого ориентироваться на `Content-Type`.
- Механизм и порядок: 204 завершает разбор без чтения JSON; JSON-body ошибки не превращает 404 в успех; пустой JSON-объект можно разобрать как существующее тело. В реальном клиенте часть этих шагов может выполнить HTTP-библиотека, но модель нужна для понимания договора.
- Независимый пример и учебный визуал: таблица из трёх строк для ответов пункта проката — «204/нет тела», «200/пустой JSON-объект», «404/JSON-детали ошибки»; три столбца показывают, что клиент узнал из status, что из наличия body и что из его типа. Это схема **чтения**, а не код будущей `solve`.
- Типичная путаница: 404 с JSON-телом не становится успешным только потому, что содержимое читается корректно; у 204 не следует пытаться декодировать несуществующее тело.
- Первое самостоятельное действие: ученик на новом ответе `status=404` и JSON-деталях о недоступной точке выдачи сам называет порядок чтения и объясняет, почему ошибка остаётся ошибкой. Локальная проверка — исход извлечён из status, декодирование разрешено только при наличии body, заголовок соответствует формату; после этого повторить с 204 и отсутствием тела.
- Опора для повторного обращения: status → наличие body → формат. Если возникает ошибка, проверить, не пытался ли клиент разобрать тело, которого нет, или определить исход по тексту body.
- Переход к практике: все нужные части ответа определены; теперь ученик соединит их в модель из переданных значений.

Локальный результат сразу после размечивания: у каждой части назван свой источник, переданный status признан готовым, значения не перепутаны; проверка возможна по заполненной схеме и устному объяснению **до написания функции**. Различающий случай: body описывает ошибку, но источник исхода остаётся status. Помощь ограничивается возвратом к визуалу 01, готовой разметки конечного примера не давать.
2. **Самостоятельно сформировать headers.** Вход: распознанные `body` и `request_id` шага 1, новый пример существующего JSON-body и вариант без body, предоставленные карточкой. Локальный результат **до сборки response**: на черновой схеме/при просмотре значения словаря headers видно обязательный `X-Request-ID`, у словаря-body появляется JSON `Content-Type`, у `None` его нет; для `{}` заголовок должен присутствовать. Проверить три разных значения body, не обращаясь к будущему результату функции. Затруднение: `if body` теряет `{}`; направить к различающему примеру 04 без выдачи готового кода.
