## 01. Заголовки принадлежат сообщению response

- Что и зачем объяснить: заголовки — метаданные сообщения; ответные headers описывают передаваемый response и не заменяют status или body. Кратко сопоставить `Accept` из request, `Content-Type` передаваемого request-body и `Content-Type` ответа, не возвращаясь к полному построению request.
- Механизм и порядок: в принятом для упражнения договоре сервер добавляет `X-Request-ID` как идентификатор обращения, по которому сообщение можно соотнести с диагностической записью. Это не `Task.id`, который относится к предметной записи и может находиться в URL или body.
- Независимый пример и наглядность: в условной службе доставки номер посылки `parcel-7` — предметный идентификатор внутри данных, а номер обращения к поддержке `call-29` — метка самого обмена; нарисовать два вложенных прямоугольника «response (headers)» и «body (данные)» с разными метками. Предел аналогии: `X-Request-ID` **дополнительный заголовок принятого учебного договора**, HTTP не обязывает любой сервер добавлять его.
- Типичная путаница: один response содержит request ID и объект с собственным `id`; значения отвечают за разные сущности. Не называть request ID новым полем объекта и не приписывать ему выбор результата.
- Первое самостоятельное действие: показать учебное сообщение с `X-Request-ID: call-30` и `body={"id": "parcel-8"}`; ученик сам указывает, какой идентификатор помогает искать обращение и какой — посылку. Локальная проверка: две метки верно размещены в визуале, ни одна не заменена другой; затем повторить для новой пары меток.
- Опора для повторного обращения: при сборке ответа восстановить роль `X-Request-ID` и проверить, что в него попало переданное значение обращения, а не номер Task.
- Переход к следующему шагу: служебные сведения отделены от данных; теперь нужно определить формат данных body.

## 02. Body передаёт содержимое, а не исход

- Что и зачем объяснить: body может содержать данные успешного результата (включая пустой список `[]` при успешном чтении) или детали ошибки. Наличие JSON само по себе не означает успех: исход уже задаёт переданный status. `[]` здесь помогает понять настоящий HTTP, но вход `solve` по контракту ограничен словарём или `None`.
- Механизм и порядок: в задаче Python-словарь **обозначает** JSON-объект в теле, но сам по себе не является отправленным HTTP-сообщением. На маленькой функции без HTTP показать, что `print()` лишь выводит текст, а `return` отдаёт значение вызывающему коду. В редакторе требуется `return`; настоящая отправка и преобразование JSON остаются за границей.
- Независимый пример: служба проката велосипедов отвечает на поиск: `status=200, body={"dock": "C4"}` и `status=404, body={"detail": "Велосипед отсутствует"}`. В обоих случаях body есть, однако успех определяется status. Отдельно на функции с `print("готово")` и `return {"found": False}` ученик предсказывает, что появится в консоли и какое значение получит вызывающий код.
- Типичная путаница: поле `detail` — описание ошибки, а не замена status; модель Python не является сериализованным сетевым сообщением.
- Первое самостоятельное действие: для другого пункта проката ученик получает `status=404` и `body={"detail": "Место выдачи не найдено"}`, самостоятельно объясняет, чем подтверждена ошибка и для чего служит body; наблюдаемая проверка — называет status источником исхода, body источником подробностей, а `print` не считает отправкой HTTP.
- Опора для повторного обращения: перед сборкой проверить, что body остаётся переданным содержимым и не заменяется строкой, выводом или новым решением о статусе.
- Переход к следующему шагу: содержимое задано; заголовок теперь должен сообщить получателю его формат.

## 03. Content-Type описывает фактический формат body

- Что и зачем объяснить: `Content-Type: application/json` сообщает клиенту, как читать существующее тело. Заголовок не создаёт содержимое и не превращает Python-словарь в JSON.
- Механизм и порядок: сначала определить, передаётся ли body; если да — согласовать объявленный тип с форматом содержимого. **В контракте этой `solve`** при `body=None` заголовок `Content-Type` отсутствует. В реальном HTTP возможны сообщения, где метаданные описывают представление даже без передаваемого тела; подробности остаются за границами урока. Не превращать правило учебной функции в универсальный запрет заголовка. Заголовок — часть договора между отправителем и получателем.
- Независимый пример и вторая наглядная опора: этикетка на коробке сообщает получателю вид содержимого, но не кладёт предмет внутрь. Сравнить `Content-Type: application/json` с JSON-данными каталога и `Content-Type: text/plain` с обычным текстом; показать на схеме «фактическое содержимое → заявленный тип → как клиент интерпретирует». Предел аналогии: реальное HTTP-body — байты; заголовок не преобразует байты и не гарантирует, что отправитель честно указал формат.
- Типичная путаница: `Accept` заявляет предпочтение клиента в request, `Content-Type` описывает тело конкретного сообщения; два одинаково названных `Content-Type` в request и response относятся к разным сообщениям. В учебной `solve` формат всех существующих body заранее оговорён как JSON.
- Первое самостоятельное действие: ученик сравнивает два готовых сообщения проката — JSON-объект и строку обычного текста — и сам выбирает подходящую подпись типа, объясняя причину. Результат: тип соответствует телу, не зависит от того, успешен status или ошибочен; затем повторить на новом JSON-body ошибки.
- Опора для повторного обращения: восстановить правило «формат описывает содержимое; заголовок не сериализует его» и применить его до сборки `headers`.
- Переход к следующему шагу: для применения правила нужно точно различать отсутствие тела и тело с нулём элементов.

## 04. Отсутствующее тело, пустой объект и JSON null

- Что и зачем объяснить: различить три состояния: в контракте упражнения `None` обозначает отсутствующий body; `{}` — присутствующий пустой JSON-объект; JSON `null` — отдельное переданное значение, а не отсутствие HTTP-body.
- Механизм и порядок: проверка наличия выполняется по `body is not None`, а не по истинности значения. Поэтому пустой объект остаётся телом и получает `Content-Type`; `None` не получает JSON-заголовок. Не переносить учебную условность `None` на сериализованный JSON `null`.
- Независимый пример: для службы проката после возврата велосипеда передали `body=None` («отчёта нет»), а при поиске свободных мест — `body={}` («отчёт есть, но данных в объекте нет»). В реальном HTTP второй случай всё равно имеет JSON-тело. Пусть ученик вслух сравнит `if body` с `if body is not None`: первая проверка принимает пустой словарь за отсутствие тела, вторая точно соответствует договору задачи. Здесь же кратко восстановить `if`, отступ, обращение к ключу словаря и присваивание значения по ключу на **независимом** примере метки товара, не выдавая реализацию `headers`.
- Типичная путаница: JSON `null` — это **байты тела со значением null**, тогда как Python `None` в данных учебной функции специально означает отсутствие тела; для текущей задачи `null` не является отдельным допустимым входом.
- Первое самостоятельное действие: **без кода будущей `solve`** ученик для `None`, `{}` и `{"dock": "C4"}` заполняет две колонки «результат `body is not None`» и «нужен ли `Content-Type`»; затем обнаруживает и объясняет расхождение с `if body` на `{}`. Локальная проверка: `None` даёт ложь/нет заголовка; оба словаря дают истину/нужен JSON-заголовок. После исправления ученик переносит правило на новый пустой словарь с другим status.
- Опора для повторного обращения: «None — нет body по условию упражнения; `{}` — есть пустой JSON; `null` — значение JSON»; перед проверкой заголовка выяснить, какое из состояний дано.
- Переход к следующему шагу: status уже известен; теперь клиент применит три части ответа в правильном порядке.

## 05. Клиент читает ответ по договору

- Что и зачем объяснить: опереться на статус из занятия 42, не повторяя каталог кодов. Показать последовательность: прочитать status, определить по договору, ожидается ли body, затем при наличии содержимого ориентироваться на `Content-Type`.
- Механизм и порядок: 204 завершает разбор без чтения JSON; JSON-body ошибки не превращает 404 в успех; пустой JSON-объект можно разобрать как существующее тело. В реальном клиенте часть этих шагов может выполнить HTTP-библиотека, но модель нужна для понимания договора.
- Независимый пример и учебный визуал: таблица из **четырёх** ответов службы проката: `200`/объект с местом, `200`/`{}`, `404`/`{"detail": "Место не найдено"}`, `204`/`None`. Для каждого отдельно показать: (а) исход по status, (б) есть ли тело, (в) нужно ли читать JSON. Не пропустить, что оба `200` успешны, `404` остаётся ошибкой с читаемыми подробностями, а у `204` тела нет. Это схема чтения, без готового словаря из будущей практики.
- Типичная путаница: 404 с JSON-телом не становится успешным только потому, что содержимое читается корректно; у 204 не следует пытаться декодировать несуществующее тело.
- Первое самостоятельное действие: на **изменённом** ответе `status=404` с JSON-деталями о недоступной точке выдачи ученик сам называет три шага чтения и объясняет, почему ошибка остаётся ошибкой. Затем без подсказки сравнивает `204`/`None` и `200`/`{}`. Локальная проверка — три разных объяснения, отсутствие попытки разобрать тело при `204` и самостоятельный выбор JSON-формата для `{}`.
- Опора для повторного обращения: status → наличие body → формат. Если возникает ошибка, проверить, не пытался ли клиент разобрать тело, которого нет, или определить исход по тексту body.
- Переход к практике: все нужные части ответа определены; теперь ученик соединит их в модель из переданных значений.

## 06. Что мы будем делать в практике

**Обязательный формат по принятому паспорту:** автопроверяемая редакторская функция `solve(status, body, request_id)` по существующему ключу `"42.1"` в `code_tasks.py`, затем устное объяснение нового случая. Статусы и тела переданы согласованными; ученик не отправляет запрос, не выбирает status и не конструирует предметную задачу Planner.

**Происхождение входа и подготовка:** текущий `starter_code` предоставляет только сигнатуру `def solve(status, body, request_id)` и точку `pass`; это не готовое решение. Вызов передаёт целое `status`, Python-словарь `body` (включая `{}`) либо `None`, готовую строку `request_id`. Перед редактором выполнить безопасную пробу из раздела 04: различить входы по условию наличия тела и объяснить отдельные роли `status` и `request_id`. Если `def`, словарь, запись по ключу, `if` или `return` не освоены, сначала дать короткое упражнение с независимым словарём; затем ученик полностью пишет собственные headers и итоговую модель. Не давать законченный фрагмент `solve` ни в теории, ни в подсказке.

Общий результат — словарь response с ключами `status`, `headers`, `body`, в котором status/body сохранены, `X-Request-ID` получает исходный request ID, а `Content-Type: application/json` добавляется только при наличии body.

1. **Различить части входа.** Вход: три готовых аргумента `solve` и **новый** учебный ответ с идентификатором обращения и предметным `id`. Объект: `status`, `body`, `request_id` без создания Task. Опора: 01 различает два ID, 02 отделяет исход от содержимого; выбор status планируется в B `42` и проверяется перед выдачей. Самостоятельно: ученик на схеме размещает status, headers и body; показывает источник `X-Request-ID` и объясняет, почему предметный `id` из body ему не подходит. Локальный результат **до кода**: все три части размечены, status не выводится из body. Различающий случай: body описывает ошибку при status 404. При затруднении вернуться к рисунку 01, но не давать готовую разметку нового случая.
2. **Самостоятельно сформировать headers.** Вход: распознанные `body` и `request_id` шага 1, уже проверенные случаи `None`, `{}` и непустого JSON-объекта. Объект: словарь `headers` внутри новой функции, заготовки самого словаря нет. Опора: 01 объясняет `X-Request-ID`, 03 — `Content-Type`, 04 — проверку наличия тела и синтаксические действия над словарём. Самостоятельно: ученик записывает создание headers и условное добавление JSON-заголовка; status/body не меняет. **Промежуточная локальная проверка до сборки ответа:** отдельно посмотреть содержимое headers для всех трёх body; `X-Request-ID` всегда содержит переданную строку, `Content-Type` есть для обоих словарей, отсутствует для `None`. При ошибке на `{}` вернуть ученика к независимой таблице из 04 и предложить найти ошибочное условие самому.
3. **Самостоятельно собрать и вернуть response-модель.** Вход: готовые аргументы, собственные headers из шага 2 и пустая сигнатура `solve`. Объект: один возвращаемый словарь **ровно** с ключами `status`, `headers`, `body`. Опора: в 02 показано различие `print`/`return`, в 04 безопасно восстановлены словарь/условие, синтаксис функции проверен во входной диагностике. Самостоятельно: ученик записывает возвращаемую форму, оставляет status/body неизменными и ничего не печатает. Локальный результат после **собственного вызова на открытом входе**: возвращён именно словарь с тремя полями; status и body сохранены, входы не изменены и лишнего вывода нет. На двух локальных вызовах (`200`/словарь, `204`/`None`) можно отдельно увидеть результат до общей автопроверки; автоматическая проверка дополнительно охватывает `201`/словарь, `404`/ошибку и `200`/`{}`. Для MAIN предусмотреть просмотр результата без эталонного кода.
4. **Объяснить граничные случаи и выполнить небольшой перенос.** Вход: собственная модель шага 3 и **новый** случай `status=404`, JSON-словарь подробностей о не найденной книге, другой `request_id` (по договору действующей задачи). Объект: устный разбор и прогноз **значений headers**, без второй функции. Опора: 02 отделяет статус от body, 03–04 показывают тип/наличие, 05 — порядок чтения. Самостоятельно: сравнить 204/`None` и 200/`{}`, затем объяснить новый 404/JSON по трём шагам, указать, откуда в ответе берётся ID обращения. Локальный результат: ученик различает отсутствие/пустоту, у 404 сохраняет смысл ошибки при JSON-body и прогнозирует JSON `Content-Type` и **новый** `X-Request-ID` без копирования результата предыдущего вызова. При затруднении вернуться к таблице 05, не подставляя готовый ответ.

**Связность и граница самостоятельности:** блоки 01–02 готовят шаг 1 и возврат значения на шаге 3; блоки 03–04 — решение о заголовке в шаге 2; блок 05 — объяснение на шаге 4. Шаг 1 даёт распознанные входы шагу 2, шаг 2 даёт собственные headers шагу 3, шаг 3 даёт модель шагу 4. Каждый локальный критерий наблюдаем сразу, до следующего шага. Помощь уменьшается от схемы к собственному написанию словаря и `return`, затем к независимому объяснению. Точные карточки, подсказки, набор тестов и эталонное решение остаются материалом этапа 3.

**Итоговый критерий по паспорту:** функция сохраняет переданные status/body и request ID, создаёт точную форму response и ставит JSON Content-Type только для существующего body; ученик объясняет различие `None` и `{}`, успешный `204` без тела и ошибочный `404` с JSON-описанием. Автопроверка проверяет возвращённое значение, ключи, отсутствие вывода и сохранность входов; устный перенос на новом ID/теле отдельно подтверждает, что решение понято, а не угадано по исходному примеру. Готовые ответы, тест-кейсы MAIN и реализация сети остаются за Stage 3.
