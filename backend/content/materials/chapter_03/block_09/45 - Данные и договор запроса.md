## 00. Вступление

Начать с результата занятия 44: для восьми операций уже выбрана пара `method + path`, различены collection и item, а адресная карта не проверяет существование задачи. Напомнить, что карта говорит, какое действие и над каким ресурсом выполняется, но ещё не показывает передаваемые значения и ожидаемый ответ. Дальше восстановить нужные части request/response, не повторяя объяснение метода и адреса.

1. **Точка старта:** ученик выбирает метод и адрес по известному действию и различает collection `/tasks` и item `/tasks/{task_id}`.
2. **Новый вопрос:** где находятся настройки чтения, данные изменения и обещание результата, чтобы обе стороны поняли один запрос одинаково?
3. **Результат:** ученик распределяет переданные значения по частям сообщения, обозначает ожидаемую форму ответа и объясняет границы учебной модели.

Пункты продолжают результат 44: известная пара `method + path` задаёт действие и область, затем мы распределяем входы, уточняем ответ и собираем учебный договор. Это подготавливает следующий шаг без скачка к серверу: в 46 готовая модель впервые станет реальным GET с query к Echo, а JSON body будет проверен в 46.1. Словарь здесь не отправляет запрос и не доказывает работу API.

## 01. Договор API описывает видимую границу

- **Что и зачем объяснить:** договор согласует действие, адрес, входные значения, успешный результат и ожидаемое отсутствие ресурса. Он помогает клиенту сформировать запрос и прочитать ответ, не раскрывая Python-класс, файл или внутреннюю функцию сервера.
- **Механизм и порядок:** восстановить `method + path` из предыдущего занятия; добавить вопрос о входных данных; завершить вопросом о status и форме ответа. Отличить описанный договор от реализованного сервера.
- **Независимая аналогия и её предел:** адрес отдела библиотеки задаёт место, а пометка «взять» или «вернуть» — действие; это помогает отделить path от method, но библиотечная записка не описывает всю структуру HTTP. Для Planner одна запись `/tasks/7` может обозначать чтение или удаление в зависимости от метода. Сам адрес не показывает существование задачи и не доказывает отправку запроса.
- **Первое самостоятельное действие:** по двум готовым парам `GET /books/3` и `DELETE /books/3` назвать одинаковый ресурс, разные действия и пока не описанные данные/ожидаемые ответы. Проверка — ученик не принимает совпадающий адрес за совпадающий результат и не считает карту адресов реальным запросом.
- **Опора для повторного обращения:** при сборке возвращаться к четырём вопросам договора: действие, выбранный ресурс, передаваемые данные, ожидаемый результат.
- **Переход:** чтобы продолжить договор, сначала нужно разделить значения, выбирающие объект, и настройки чтения.

## 02. Path выбирает ресурс, query настраивает чтение

- **Что и зачем объяснить:** path обозначает collection или конкретный item; query передаёт настройки чтения коллекции. Query может быть пустым. В учебной задаче `CODE_TASKS[50]` для списка предусмотрены ключи `is_done`, `sort_desc` и `limit`; передавать следует только реально присутствующие ключи. Значения серверных defaults `None`, `False` и `10`, а также диапазон `limit` от 1 до 50 — ориентиры прежней редакции плана, которые требуют сверки с восстановленным паспортом; `solve` не подставляет их за клиента.
- **Механизм и порядок:** сначала определить масштаб (`/tasks` или `/tasks/{task_id}`), затем поместить настройки списка в query. Пояснить, что отсутствие параметра оставляет выбор серверному договору; отправленное `False` является конкретным значением. Значения в модели остаются Python-значениями, не текстовым кодированием URL.
- **Независимый пример и путаница:** на каталоге книг различить `/books/7` (выбранный экземпляр) и `/books?available=false` (настройка выборки). Отсутствие `available` и переданное `false` различаются по смыслу договора; в Python-модели они представлены отсутствующим ключом и значением `False`. Аналогия каталога не гарантирует, что сервер уже фильтрует данные. В Planner id в path не подтверждает существование item; query-фильтр не изменяет Task и не распространяется на `GET /stats`.
- **Первое самостоятельное действие:** по двум готовым намерениям — открыть `/books/7` и показать в `/books` только недоступные книги — ученик самостоятельно выбирает место `id` и настройки, затем объясняет разницу «параметр не передан»/«передан `False`». Проверка — id не назван query-фильтром, фильтр не представлен изменением книги.
- **Опора для повторного обращения:** при работе со списком проверить, какой ресурс выбран path, какие query-ключи действительно переданы и чем явно переданный `False` отличается от отсутствующего ключа.
- **Переход:** после адреса и настроек чтения нужно определить, какие значения клиент передаёт для создания или изменения.

## 03. Body содержит клиентские данные операции

- **Что и зачем объяснить:** headers описывают сообщение; `Content-Type` сообщает формат отправленного body, а не является полем Task. Body содержит данные создания или изменения. `POST` принимает `title` и `priority`; сервер назначает `id` и начальное `is_done`. Внутреннее поле `tags` не добавляется в публичный договор.
- **Механизм и порядок:** связать метод и path с изменяемыми данными; отделить клиентские поля от серверных; показать полный ответ создания как представление, которое может содержать добавленные сервером значения. Знакомые `Accept` и `Content-Type` применить к их разным ролям, не повторяя урок о headers.
- **Независимый пример и путаница:** в заявке на библиотечный билет посетитель вводит имя и контакт, а номер билета назначает библиотека. Пример объясняет ответственность сторон, но не задаёт поля Planner. В Planner клиент не выбирает id и начальный `is_done` при создании. JSON body и Python-словарь могут содержать похожие поля, но учебная модель ещё не является JSON-текстом или сетевым сообщением.
- **Первое самостоятельное действие:** на карточке нового библиотечного билета ученик отделяет введённые посетителем значения от номера, присвоенного системой, затем на готовом описании создания Task отмечает поля `title`, `priority` как клиентские и `id`, начальный `is_done` как серверные. Проверка — в ожидаемом body остаются только разрешённые клиенту поля; headers с `Content-Type` не перепутаны с полями ресурса.
- **Опора для повторного обращения:** при создании проверить поле и его назначение; при чтении/удалении вспомнить, что body отсутствует и в модели обозначается `None`.
- **Переход:** состав body зависит от объёма изменения; это требует различить полную форму и переданные изменения.

## 04. Полная и частичная формы сохраняют разный смысл

- **Что и зачем объяснить:** `PUT` передаёт полную изменяемую форму `title`, `priority`, `is_done`; `PATCH` передаёт только изменяемые поля. В `GET /tasks` поле `is_done` является фильтром, а в `PUT`/`PATCH` — новым состоянием Task.
- **Механизм и порядок:** сопоставить три места и три роли значения: query-фильтр, полное значение поля при PUT, частичное значение при PATCH. Отдельно показать разницу между отсутствующим ключом и явным `False`; наличие нельзя проверять только по истинности. В упражнении все значения допустимы, неизвестных полей и явного `None` во входе нет.
- **Независимый пример и путаница:** на анкете профиля сравнить полную обновлённую анкету с запиской «изменить только уведомления на выключено». Отсутствие поля в записке означает «не трогать», явное `False` — конкретный выбор. Аналогия не означает, что любой HTTP PUT/PATCH на любом сервисе реализован именно так: формат задаёт договор конкретного API. В Planner отсутствие `is_done` в PATCH — «не передано», а `is_done=False` — «снять отметку»; фильтр GET не меняет состояние.
- **Первое самостоятельное действие:** из трёх описаний изменений анкеты самостоятельно выбрать полную форму или только переданные изменения, объяснить случай с явным `False`, после этого перенести различие на PUT/PATCH для Task. Проверка — PUT содержит весь предусмотренный набор изменяемых полей, PATCH сохраняет только переданные, включая `False`.
- **Опора для повторного обращения:** при `replace` восстановить полный набор изменяемых полей; при `update` — только присутствующие разрешённые ключи; передача не изменяет исходный словарь `values`.
- **Переход:** когда вход согласован, договор завершается не словом «успех», а конкретной формой ответа.

## 05. Status и форма ответа задают ожидаемый результат

- **Что и зачем объяснить:** status сообщает исход обмена, body содержит объект, список, статистику или отсутствует. Для обсуждения используется **планируемый договор Planner**, реконструированный по историческим исходникам: `GET /health` — `200` и состояние сервиса; `GET /tasks` — `200` и список, в том числе пустой; `GET /tasks/{task_id}` — `200` и объект; `GET /stats` — `200` и сводка по всему хранилищу. В этом договоре PUT/PATCH существующего item дают `200`, POST — `201`; ответы с ресурсом содержат публичные поля `id`, `title`, `priority`, `is_done`, без внутреннего `tags`; DELETE даёт `204` без body, а корректный положительный id отсутствующего item — `404`. Все ожидания подлежат сверке с каноническим паспортом и не доказывают наличие реализованного HTTP API.
- **Механизм и порядок:** сначала связать операцию с успехом и телом, затем разобрать отсутствие выбранного item. Отделить пустую collection от отсутствующего item и `201` с новой записью от `204` без содержимого.
- **Независимый пример и путаница:** в библиотечном каталоге пустой результат поиска означает «список существует, совпадений нет», а открытие карточки несуществующей книги — «item не найден»; это смысловое сравнение, конкретные status назначает договор сервиса. В Planner пустой список — успех (`200` и `[]`), а не `404`. После `204` нельзя разбирать JSON-body. `400` остаётся общим HTTP-примером; ошибки валидации будущего API и `422` здесь не вводятся.
- **Первое самостоятельное действие:** на отдельных карточках «пустая коллекция», «несуществующий item», «создан объект», «удалён item» ученик выбирает ожидаемые status и форму body и объясняет две различающие пары. Проверка — причина названа для `200`/`404` и `201`/`204`, а не только воспроизведена цифра.
- **Опора для повторного обращения:** проверить три признака ответа: операция, status, наличие и форма body. У `204` содержимого нет; `GET /stats` не наследует фильтр collection.
- **Переход:** теперь договор можно собрать в одну учебную модель и проговорить, что именно она подтверждает.

## 06. Учебная модель не является реальным запросом

- **Что и зачем объяснить:** в кодовом упражнении Python-словарь представляет результат выбора частей сообщения. Готовая `route_for` уже даёт method и path; ученик дополняет только query и body. Для всех действий выход имеет одинаковые ключи `method`, `path`, `query`, `body`.
- **Механизм и порядок:** пройти от известного действия к готовой паре method/path, выбрать только относящиеся к нему входы и вернуть договорную структуру. Для действий без query оставить пустой словарь; для операций без body передать `None`. Значения query не сериализуются, запрос не отправляется.
- **Пример и типичная путаница:** правильный учебный словарь не подтверждает существование маршрута, наличие Task, фильтрацию, сохранение или получение status от настоящего сервера.
- **Цельный разобранный пример на другом сюжете:** пройти заявку на выдачу книги от `POST /loans` с данными книги в body до ответа `201` с созданной заявкой и назначенным сервером id. Это только пример хода договора; он не добавляется в Planner и не заменяет практику.
- **Первое самостоятельное действие:** устно проследить один путь от action до места его данных и ожидаемого ответа. Результат — ученик объясняет последовательность и не выполняет серверное действие внутри модели.
- **Опора для повторного обращения:** готовую пару method/path брать из заготовки; самостоятельно определять распределение значений по договору; при проверке отдельно сравнивать структуру ответа упражнения и ожидаемый HTTP-response.
- **Переход:** практика закрепляет полный разбор, а устные сравнения проверяют понимание результата.

## 07. Что мы будем делать в практике

**Рабочий формат и вход:** редакторская `solve(action, task_id, values)` с возвращаемым словарём и короткий устный разбор. Это подтверждено исходной задачей `CODE_TASKS[50]` и старым журналом, но паспортная обязательность пока не проверена. Техническая заготовка даёт таблицу `methods`, работающую `route_for(action, task_id)` и незаполненное тело `solve`. Ученик получает один из восьми `action`: `list`, `get`, `create`, `replace`, `update`, `delete`, `health`, `stats`; для item-действий `task_id` — переданный положительный id, иначе `None`. `values` содержит только допустимые поля без неизвестных ключей и явного `None`; у `create` есть `title`/`priority`, у `replace` вся изменяемая форма, у `update` хотя бы одно изменение. Знакомые по историческому маршруту функции, ветвления, членство ключа в словаре и независимое копирование `dict` требуется сверить по реальной A нового маршрута перед выдачей. При пробеле пояснить синтаксис проверки наличия ключа и создания нового словаря **до** редакторской работы, не переносить объяснение в скрытые тесты.

**Что остаётся самостоятельным:** ученик пишет логику распределения по `query` и `body` и собирает возвращаемую модель. Готовая `route_for` избавляет только от повторного выбора метода и адреса из 44. `solve` не делает HTTP-запрос, не меняет Planner и не вызывает хранилище. Результат каждого шага можно просмотреть по возвращаемому значению функции/локальному запуску на известном входе без ожидания следующего шага или скрытого runner.

1. **Настройки списка в query.** **Вход/объект:** `action='list'`, `task_id=None`, сначала `values={}`, затем `values={'is_done': False, 'limit': 5}`; изменяем только результат `solve`, входной словарь не трогаем. **Опора:** раздел 02 (назначение query, присутствие ключа и `False`), подготовленная словарная конструкция из A с проверкой до выдачи. **Самостоятельно:** создать отдельный словарь настроек и выбрать только реально переданные `is_done`, `sort_desc`, `limit`, без автоматической вставки `None`/`False`/`10` как server defaults. **Локальная проверка:** в пустом случае query пустой, в другом есть именно два указанных ключа и сохранён `False`; `method=GET`, `path=/tasks`, body отсутствует. Различающий дополнительный случай — только `sort_desc=False`, который должен присутствовать, хотя ложен.
2. **Данные создания в body.** **Вход/объект:** `action='create'`, `task_id=None`, `values={'title': 'Изучить HTTP', 'priority': 4}`; результатом служит новый body в модели, а не изменение данных Planner. **Опора:** раздел 03 (клиентские/серверные поля, body и роль headers), прежняя запись словарей со статусом A. **Самостоятельно:** выбрать поля, которые клиент имеет право передать при создании; не придумывать `id` и начальный `is_done`, не добавлять их в `values`. **Локальная проверка:** body содержит оба клиентских поля с их значениями; query пустой, метод/адрес из заготовки равны `POST /tasks`, исходный `values` остался прежним. Отличающий случай на обсуждение: номер новой записи присваивает сервер **после** запроса, и задача `solve` не должна вычислять его.
3. **Полная и частичная формы.** **Вход/объект:** два независимых вызова — `replace` с `task_id=12` и полной формой `{'title': 'Planner API', 'priority': 3, 'is_done': True}`, затем `update` с `task_id=7` и `{'is_done': False}`. **Опора:** раздел 04 (PUT/PATCH, отсутствие поля против явного `False`, неизменность входа), раздел 02 (item-id относится к path). **Самостоятельно:** сформировать новое body для полного набора переданных изменяемых полей при `replace` и только присутствующих при `update`, не помещая `task_id` внутрь body и не мутируя `values`. **Локальная проверка:** готовые `route_for` дают соответственно `PUT /tasks/12` и `PATCH /tasks/7`; в первом body три поля, во втором только `is_done=False`, оба query пусты; изменение body после вызова не должно менять исходный словарь. Различающий случай: PATCH только одного `title` или нескольких полей сохраняет ровно переданное.
4. **Остальные действия и общий договор результата.** **Вход/объект:** `get`/`delete` с `task_id=7`, `health`/`stats` с `task_id=None` и пустым `values`; объект — единый выходной словарь `solve`. **Опора:** разделы 01, 02, 05–06, готовая `route_for`; синтаксис `None` и словаря закреплён до самостоятельной записи. **Самостоятельно:** объединить готовые `method`/`path` с выбранными query/body так, чтобы во всех восьми действиях структура результата оставалась одинаковой. **Локальная проверка:** у этих четырёх действий query пуст, body равен `None`, есть **ровно** `method`, `path`, `query`, `body`; `get/delete` используют `/tasks/7`, `health` — `/health`, `stats` — `/stats`, `values` неизменён. Общая проверка различает `None` (тела нет) и `{}` (пустой словарь), а query остаётся Python-словарём без URL-кодирования.
5. **Устный разбор ответа.** **Вход/объект:** две пары ситуаций без сервера: GET пустой коллекции против GET отсутствующего item; POST успешного создания против DELETE успешного удаления. **Опора:** раздел 05 объясняет status и форму response; раздел 06 отделяет ожидание от фактического обмена. **Самостоятельно:** обосновать для каждого случая ожидаемый status и наличие/форму response body, не опираясь на успешный вызов `solve`. **Локальная проверка:** ученик объясняет `200` с `[]` против `404`, `201` с публичным представлением новой задачи против `204` без body, отдельно произносит, почему `204` не предполагает JSON-разбор и почему учебная модель не проверяет реальный сервер.

Порядок намеренно снижает помощь: сначала различить отсутствие ключа и `False` (раздел 02), затем самостоятельно выбрать поля создания (03), различить полное и частичное изменение (04), собрать общий выход и объяснить ожидаемые ответы (05–06). Каждый шаг имеет локальный результат без будущей сети; при ошибке возвращаемся к указанному разделу и пробуем другой малый вход. Нормальные и различающие случаи выше задают **смысл** проверки для MAIN; точные задания, автотесты и подсказки оформляются в Stage 3 без раскрытия готового алгоритма `solve` в теории.

**Суммарная проверка B:** для каждого из восьми действий модель содержит согласованные готовые `method/path`, корректное размещение реально переданных значений по `query/body`, не приписывает серверные defaults клиенту и сохраняет исходные `values`; ученик объясняет обе пары HTTP-результатов. Это доказывает умение моделировать договор, а не существование API. Планируемый переход 45 → 46 использует query в реальном GET к Echo; в 46.1 добавляется POST с JSON body. Echo не доказывает фильтрацию, создание или хранение Task в Planner; до выдачи нового маршрута проверить его согласованную очередность по восстановленному паспорту.
