## 00. Вступление

3. **Результат:** ученик распределяет переданные значения по частям сообщения, обозначает ожидаемую форму ответа и объясняет границы учебной модели.

Пункты продолжают результат 44: известная пара `method + path` задаёт действие и область, затем мы распределяем входы, уточняем ответ и собираем учебный договор. Это подготавливает следующий шаг без скачка к серверу: в 46 готовая модель впервые станет реальным GET с query к Echo, а JSON body будет проверен в 46.1. ## 01. Договор API описывает видимую границу

- **Что и зачем объяснить:** договор согласует действие, адрес, входные значения, успешный результат и ожидаемое отсутствие ресурса. Он помогает клиенту сформировать запрос и прочитать ответ, не раскрывая Python-класс, файл или внутреннюю функцию сервера.
- **Механизм и порядок:** восстановить `method + path` из предыдущего занятия; добавить вопрос о входных данных; завершить вопросом о status и форме ответа. Отличить описанный договор от реализованного сервера.
- **Независимая аналогия и её предел:** адрес отдела библиотеки задаёт место, а пометка «взять» или «вернуть» — действие; это помогает отделить path от method, но библиотечная записка не описывает всю структуру HTTP. Для Planner одна запись `/tasks/7` может обозначать чтение или удаление в зависимости от метода. Сам адрес не показывает существование задачи и не доказывает отправку запроса.
- **Первое самостоятельное действие:** по двум готовым парам `GET /books/3` и `DELETE /books/3` назвать одинаковый ресурс, разные действия и пока не описанные данные/ожидаемые ответы. Проверка — ученик не принимает совпадающий адрес за совпадающий результат и не считает карту адресов реальным запросом.
- **Опора для повторного обращения:** при сборке возвращаться к четырём вопросам договора: действие, выбранный ресурс, передаваемые данные, ожидаемый результат.
- **Переход:** чтобы продолжить договор, сначала нужно разделить значения, выбирающие объект, и настройки чтения.

## 02. Path выбирает ресурс, query настраивает чтение

- **Сначала разделить роли:** `/tasks` обозначает весь список (collection), `/tasks/7` — адрес задачи с id 7 (item). Наличие `7` в адресе ещё не значит, что задача найдена. Query — дополнительные настройки чтения **списка**. Они не меняют сами задачи.
- **Точный договор списка Planner:** `is_done` оставляет завершённые/незавершённые задачи, `sort_desc` задаёт обратный порядок по `id`, `limit` ограничивает количество после отбора и сортировки. Сервер при отсутствии ключей использует `is_done=None` (без фильтра), `sort_desc=False`, `limit=10`; допустимый `limit` — от 1 до 50. **Эти значения принадлежат серверу:** в `solve` не добавляем их в запрос, если клиент не передал ключ. `GET /stats` не принимает параметры списка и считает по всем задачам.
- **Независимый пример, который следует показать:** `GET /books/7` выбирает карточку книги, `GET /books?available=false` запрашивает выборку недоступных книг. В учебном Python-словаре это `{'available': False}`; отсутствие `'available'` означает «условие не отправляли». Реальный URL передаёт текст, но его кодирование изучат позднее. Эта аналогия не означает, что учебная программа уже умеет искать книги.
- **Первая проба до Planner:** дать три карточки — «открыть книгу 7», «показать только недоступные», «показать все без фильтра». Ученик сам отмечает, где находится id, где query, а где параметра вообще нет; затем объясняет, почему `False` нельзя удалить из query. Проверка: конкретный id помещён в path; пустой фильтр обозначен отсутствием ключа, а не ключом со значением `False`.
- **Опора на возврат:** сначала выбираем список или item в path; при чтении списка передаём **только указанные** настройки в query. Ни query, ни id в адресе не создают и не изменяют Task.
- **Переход:** настройки чтения определили; теперь рассмотрим значения, которые клиент отправляет для создания и изменения.

## 03. Body содержит клиентские данные операции

- **Назначение:** body — значения, которые клиент передаёт для создания/изменения. Headers описывают сообщение: `Content-Type` сообщает формат передаваемого тела, `Accept` — желательный формат ответа. Ни один из этих заголовков не является полем Task.
- **Кто задаёт значения при POST `/tasks`:** клиент передаёт `title` и `priority`; сервер **после** создания назначает `id` и устанавливает `is_done=False`. Внешняя задача содержит `id/title/priority/is_done`; внутренний `tags` не включаем в публичное тело. Важно не путать **запрос на создание** с **ответом о созданной задаче**.
- **Второй независимый пример:** посетитель пишет в заявлении на библиотечный билет имя и контакт, а номер билета выдаёт библиотека. Ученик помечает эти поля на двух карточках «заявление» и «выданный билет». Перенос на Planner: `id` нельзя вписывать в клиентское body создания, даже если он появится в ответе. Наглядная схема «клиент → поля заявления → сервер → номер и полный объект» полезнее второй словесной формулировки.
- **Первая проба:** среди `title`, `priority`, `id`, `is_done`, `Content-Type`, `tags` ученик самостоятельно выбирает поля входного body для создания. Проверка: выбраны **ровно** `title/priority`; `Content-Type` остался заголовком, серверные значения не внесены. У `GET` и `DELETE` в нашем договоре body нет: это `None` в учебной модели, а не `{}`.
- **Опора на возврат:** при `POST` спросить «кто создаёт это значение?». `title/priority` — клиент; id и исходное состояние — сервер. Учебный словарь пока не является отправленным JSON.
- **Переход:** при изменении существующей задачи набор клиентских полей зависит от выбранного метода.

## 04. Полная и частичная формы сохраняют разный смысл

- **Три разных смысла одного поля `is_done`:** `GET /tasks` + query `is_done=False` просит показать незавершённые задачи; `PUT /tasks/7` + body `is_done=False` задаёт состояние в **полной** форме изменения; `PATCH /tasks/7` + body `is_done=False` изменяет **только** переданное поле. Настройка чтения не меняет данные в хранилище.
- **Полный и частичный вход:** `PUT` требует все изменяемые поля `title`, `priority`, `is_done`, но **не id** (он уже в path). `PATCH` содержит лишь указанные изменяемые поля; если `title` пропущен, менять его не просили. Именно так устроен **этот** API, не любой сервер в мире.
- **Наглядный контраст для новичка:** две записки — «полностью заменить анкету» и «отключить уведомления». Для второй записки `{'notifications': False}` означает конкретное изменение, `{}` не сообщает изменения. Дать учащемуся прогноз: какие поля останутся нетронутыми и почему.
- **Подготовка синтаксиса до практики:** показать на словаре анкеты, что проверка `if 'notifications' in changes:` обнаруживает ключ и при значении `False`, а `if changes.get('notifications'):` ошибочно пропустит его. Попросить самостоятельно объяснить два случая: ключ отсутствует / ключ присутствует с `False`. Не давать здесь полную реализацию `solve`.
- **Первая проба:** дать полную анкету и записку с одним выключенным флагом; ученик выбирает PUT/PATCH и состав полей, затем переносит принцип на `title/priority/is_done` Planner. Проверка: у PUT весь набор, у PATCH только переданные поля и не потерян `False`.
- **Опора на возврат:** `replace` — вся изменяемая форма, `update` — только присутствующие поля; наличие ключа определяем через `in`, а не через истинность значения. Исходный `values` остаётся без изменений.
- **Переход:** места данных согласованы; осталось предсказать, какой ответ должен дать сервер в разных исходах.

## 05. Status и форма ответа задают ожидаемый результат

- **Зачем нужен ответ в договоре:** метод, адрес и вход говорят, что клиент **просит**; HTTP status и тело ответа говорят, что **получилось**. Это ожидаемый результат согласно принятому паспорту Planner, а не ответ работающего сервера. Возвращаемый из учебной `solve` словарь — модель **запроса**, поэтому status в него не добавляется.
- **Чтение и изменение в принятом договоре:** `GET /health` — `200` и краткое состояние сервиса; `GET /tasks` — `200` и список; `GET /tasks/{task_id}` — `200` и одна задача; `GET /stats` — `200` и сводка **по всем** задачам, независимо от параметров чтения списка. `POST /tasks` — `201` и новая полная публичная задача; `PUT`/`PATCH /tasks/{task_id}` для существующей задачи — `200` и её полное представление, у `PUT` id сохраняется. Публичные поля задачи: `id`, `title`, `priority`, `is_done`, без внутреннего `tags`.
- **Первый контраст — «никого нет» и «этого нет»:** `GET /tasks` может успешно вернуть пустой список `[]` с `200`. Запрос конкретной задачи по существующему адресу `/tasks/7`, когда задачи 7 нет, даёт `404`: адрес составлен правильно, но запись не найдена. На примере библиотеки ученик различает «поиск вернул пустой каталог» и «карточки книги 7 не существует». Проверить объяснение причины, а не угадывание статуса.
- **Второй контраст — создание и удаление:** после успешного POST сервер создал задачу и возвращает `201` вместе с её публичными полями, включая назначенные сервером `id` и `is_done=False`. После успешного `DELETE /tasks/7` сервер возвращает `204` **без тела**: разбирать JSON в таком ответе нечего. Попросить ученика объяснить, почему «успешно» не означает один status и одну форму body.
- **Проба до практики:** дать четыре карточки без цифр («пустой список», «отсутствующая задача», «успешно создали», «успешно удалили»). Ученик самостоятельно сопоставляет `200` + `[]`, `404`, `201` + объект, `204` + отсутствие тела и обосновывает обе пары. Ошибки валидации и `422` пока не разбираем: значения на входе упражнения допустимы.
- **Опора на возврат:** проверить, какой ресурс запрашивали, что произошло, какой status и какое тело обещает договор. Реальные ответы начнём наблюдать в следующих занятиях; здесь только предсказываем.
- **Переход:** теперь можно собрать описание запроса в одном словаре и отдельно проговорить ожидаемый ответ.

## 06. Учебная модель не является реальным запросом

- **Что именно пишет ученик:** `solve(action, task_id, values)` возвращает Python-словарь с **ровно четырьмя** ключами: `method`, `path`, `query` и `body`. Первые два уже выбирает готовая `route_for(action, task_id)`: она возвращает словарь, из которого можно прочитать `route['method']` и `route['path']`. Ученик самостоятельно решает, какие переданные значения относятся к query и body; `route_for` не переписывается.
- **Маленькое повторение Python перед редактором:** `if 'enabled' in settings:` проверяет **наличие ключа**, даже если его значение `False`. Выражение `settings.get('enabled')` в условии не различит отсутствующий ключ и `False`. `dict(settings)` или `settings.copy()` создают **новый словарь**: его можно передать в результате, не меняя исходный `settings`. Показать это на настройках настольного будильника, не на готовом решении `solve`; предложить ученику самостоятельно объяснить поведение при `{}` и `{'enabled': False}`.
- **Два обозначения отсутствия:** `query={}` означает «ни одного параметра чтения не передали» и остаётся словарём **для всех восьми действий**. `body=None` означает «тела запроса нет»; это нужно для list/get/delete/health/stats. Пустой словарь `{}` вместо `None` ошибочно сообщает другой тип значения. Для POST/PUT/PATCH body — **отдельный** словарь клиентских данных.
- **Сборка без подмены задачи:** по `action` берём готовый method/path, решаем, нужны ли настройки списка или клиентские поля, оставляем ненужные части пустыми/отсутствующими, возвращаем словарь. `values` не изменяем; defaults сервера в него и в query не подставляем. В модели `False` остаётся логическим значением Python, а кодирование URL, JSON-сериализация и реальная отправка ещё не происходят.
- **Цельный пример на другом сюжете:** для `POST /loans` в библиотеке составляют **заявку** с данными книги в body; при успехе **сервер** присваивает номер заявки и мог бы вернуть `201` с объектом. Разделить на доске два прямоугольника: «что отправили» / «что получили». Не переносить эту библиотечную реализацию в Planner и не показывать готовый алгоритм `solve`.
- **Самостоятельная контрольная проба:** взять известную `health`: ученик объясняет, почему `route_for('health', None)` определяет `GET /health`, а модель всё равно обязана вернуть `query={}` и `body=None`. Затем на карточке запроса библиотеки называет отдельно его body и предсказанный response. Проверка: не добавляет status или созданный id внутрь словаря запроса.
- **Опора на возврат:** method/path берём из `route_for`; query/body выбираем по договору; сохраняем `False`, типы и исходный `values`. В редакторе проверяем структуру **модели**; устно проверяем ожидаемый **HTTP-ответ**.
- **Переход:** теперь один и тот же механизм нужно применить ко всем восьми действиям самостоятельно.

## 07. Что мы будем делать в практике

**Обязательный формат из принятого BLOCK_9, §3:** автопроверяемый редактор `solve(action, task_id, values)` и отдельный устный разбор двух контрастов ответа. Историческая реализация `CODE_TASKS[50]` подтверждает пригодность стартера и различающих тестов; регистрацию упражнения под ключом `45` выполняет Stage 3. В стартере уже есть таблица `methods` и действующая `route_for(action, task_id)`; тело `solve` ученик пишет сам. Один из восьми `action`: `list`, `get`, `create`, `replace`, `update`, `delete`, `health`, `stats`. Для get/replace/update/delete `task_id` — положительный id, иначе `None`. `values` содержит только допустимые поля без неизвестных ключей и явного `None`; для create задана пара `title`/`priority`, для replace — вся изменяемая форма, для update — хотя бы одно изменение. Перед выдачей проверить навыки ветвления, работы со словарём и `return` из главы 2; при пробеле дать отдельную пробу на ином сюжете по §04/§06 **до** редактора.

**Что остаётся самостоятельным:** ученик пишет логику распределения по `query` и `body` и собирает возвращаемую модель. Готовая `route_for` избавляет только от повторного выбора метода и адреса из 44. `solve` не делает HTTP-запрос, не меняет Planner и не вызывает хранилище. Результат каждого шага можно просмотреть по возвращаемому значению функции/локальному запуску на известном входе без ожидания следующего шага или скрытого runner.

1. **Настройки списка в query.** **Вход/объект:** `action='list'`, `task_id=None`, сначала `values={}`, затем `values={'is_done': False, 'limit': 5}`; изменяем только результат `solve`, входной словарь не трогаем. **Опора:** раздел 02 (назначение query, присутствие ключа и `False`), подготовленная словарная конструкция из A с проверкой до выдачи. **Самостоятельно:** создать отдельный словарь настроек и выбрать только реально переданные `is_done`, `sort_desc`, `limit`, без автоматической вставки `None`/`False`/`10` как server defaults. **Локальная проверка:** в пустом случае query пустой, в другом есть именно два указанных ключа и сохранён `False`; `method=GET`, `path=/tasks`, body отсутствует. Различающий дополнительный случай — только `sort_desc=False`, который должен присутствовать, хотя ложен.
2. **Данные создания в body.** **Вход/объект:** `action='create'`, `task_id=None`, `values={'title': 'Изучить HTTP', 'priority': 4}`; результатом служит новый body в модели, а не изменение данных Planner. **Опора:** раздел 03 (клиентские/серверные поля, body и роль headers), прежняя запись словарей со статусом A. **Самостоятельно:** выбрать поля, которые клиент имеет право передать при создании; не придумывать `id` и начальный `is_done`, не добавлять их в `values`. **Локальная проверка:** body содержит оба клиентских поля с их значениями; query пустой, метод/адрес из заготовки равны `POST /tasks`, исходный `values` остался прежним. Отличающий случай на обсуждение: номер новой записи присваивает сервер **после** запроса, и задача `solve` не должна вычислять его.
3. **Полная и частичная формы.** **Вход/объект:** два независимых вызова — `replace` с `task_id=12` и полной формой `{'title': 'Planner API', 'priority': 3, 'is_done': True}`, затем `update` с `task_id=7` и `{'is_done': False}`. **Опора:** раздел 04 (PUT/PATCH, отсутствие поля против явного `False`, неизменность входа), раздел 02 (item-id относится к path). **Самостоятельно:** сформировать новое body для полного набора переданных изменяемых полей при `replace` и только присутствующих при `update`, не помещая `task_id` внутрь body и не мутируя `values`. **Локальная проверка:** готовые `route_for` дают соответственно `PUT /tasks/12` и `PATCH /tasks/7`; в первом body три поля, во втором только `is_done=False`, оба query пусты; изменение body после вызова не должно менять исходный словарь. Различающий случай: PATCH только одного `title` или нескольких полей сохраняет ровно переданное.
4. **Остальные действия и общий договор результата.** **Вход/объект:** `get`/`delete` с `task_id=7`, `health`/`stats` с `task_id=None` и пустым `values`; объект — единый выходной словарь `solve`. **Опора:** разделы 01, 02, 05–06, готовая `route_for`; синтаксис `None` и словаря закреплён до самостоятельной записи. **Самостоятельно:** объединить готовые `method`/`path` с выбранными query/body так, чтобы во всех восьми действиях структура результата оставалась одинаковой. **Локальная проверка:** у этих четырёх действий query пуст, body равен `None`, есть **ровно** `method`, `path`, `query`, `body`; `get/delete` используют `/tasks/7`, `health` — `/health`, `stats` — `/stats`, `values` неизменён. Общая проверка различает `None` (тела нет) и `{}` (пустой словарь), а query остаётся Python-словарём без URL-кодирования.
5. **Устный разбор ответа.** **Вход/объект:** две пары ситуаций без сервера: GET пустой коллекции против GET отсутствующего item; POST успешного создания против DELETE успешного удаления. **Опора:** раздел 05 объясняет status и форму response; раздел 06 отделяет ожидание от фактического обмена. **Самостоятельно:** обосновать для каждого случая ожидаемый status и наличие/форму response body, не опираясь на успешный вызов `solve`. **Локальная проверка:** ученик объясняет `200` с `[]` против `404`, `201` с публичным представлением новой задачи против `204` без body, отдельно произносит, почему `204` не предполагает JSON-разбор и почему учебная модель не проверяет реальный сервер.

Порядок намеренно снижает помощь: сначала различить отсутствие ключа и `False` (раздел 02), затем самостоятельно выбрать поля создания (03), различить полное и частичное изменение (04), собрать общий выход и объяснить ожидаемые ответы (05–06). Каждый шаг имеет локальный результат без будущей сети; при ошибке возвращаемся к указанному разделу и пробуем другой малый вход. Нормальные и различающие случаи выше задают **смысл** проверки для MAIN; точные задания, автотесты и подсказки оформляются в Stage 3 без раскрытия готового алгоритма `solve` в теории.

**Суммарная проверка B:** для каждого из восьми действий модель содержит согласованные готовые `method/path`, корректное размещение реально переданных значений по `query/body`, не приписывает серверные defaults клиенту и сохраняет исходные `values`; ученик объясняет обе пары HTTP-результатов. Это доказывает умение моделировать договор, а не существование API. По принятому COURSE и BLOCK_9 следующий шаг 46 — реальный GET с query в Echo; 46.1 — POST с JSON body. На входе BLOCK_10 повторить новый самостоятельный пример и, если обнаружился пробел, адресно вернуться к query, body, `False` или форме ответа. Echo не доказывает фильтрацию, создание или хранение Task в Planner.
