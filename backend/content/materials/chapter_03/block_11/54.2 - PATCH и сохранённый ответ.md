## 00. Вступление

Task уже можно менять на уровне сервиса, а Pydantic-схема умеет описать частичный набор входных полей. Новый вопрос теперь не в повторной реализации обновления: как соединить эти готовые части с HTTP так, чтобы клиент изменил выбранную Task и получил её сохранённое представление?

1. **Точка старта:** сервис `patch_task` и схема `TaskPatch` уже подготовлены предыдущими шагами нового маршрута.
2. **Новый вопрос:** как маршрут превращает HTTP-body в именованные изменения, передаёт их существующему сервису и обрабатывает его результат?
3. **Результат:** появляется один PATCH-маршрут; его ответ, свежий GET и чтение через CLI подтверждают сохранённое состояние.

Эти пункты задают последовательность занятия: восстановить договор входа, собрать HTTP-границу вокруг готового действия, затем проверить внешний ответ и данные после нового чтения. Планируемые предпосылки нужно подтвердить перед использованием; старый урок 61 остаётся источником содержания, а не доказательством готовности новой A.

## 01. PATCH связывает запрос с существующим действием

- **Что и зачем объяснить:** коротко восстановить отличие PATCH от PUT: первый передаёт выборочные изменения, второй требует полный редактируемый набор. В этом занятии PATCH не создаёт ресурс и не реализует второй алгоритм обновления. Он открывает для клиента уже готовую операцию Planner.
- **Механизм и порядок:** проследить роли клиента, FastAPI-маршрута, схемы, `PlannerService` и JSON по цепочке «запрос → проверка → передача изменений → сохранение → публичный ответ». Отдельно показать на независимом примере обновления настройки уведомлений, что HTTP-handler связывает договор с существующей функцией сервиса, а не меняет файл самостоятельно.
- **Пример и типичная путаница:** сравнить PATCH к существующему объекту с вызовом сервисного метода внутри приложения. Название HTTP-метода не заменяет имя функции `patch_task`; endpoint не должен повторять поиск, конструирование Task или `save`.
- **Первое самостоятельное действие:** после разбора примера ученик располагает карточки участников цепочки и объясняет, где проверяется body, где применяется изменение и кто сохраняет данные. Наблюдаемый результат: ни одна операция сервиса или JSON не приписана HTTP-клиенту.
- **Переход:** договор участников станет основой чтения path и body конкретного запроса.

## 02. Path выбирает Task, body задаёт изменения

- **Что и зачем объяснить:** восстановить знакомую форму `PATCH /tasks/{task_id}`: положительный целый ID выбирается в path, `TaskPatch` приходит обязательным JSON-body. `Request` нужен, чтобы получить сервис из текущего `request.app.state.planner`, а не захватить отдельный глобальный alias.
- **Механизм и порядок:** сначала распознать ресурс по адресу, затем отделить проверку `task_id` от проверки body. Напомнить ранее введённые `Annotated[int, Path(gt=0)]` и передачу `Request`; новые варианты аннотаций не добавлять. Запрос с корректным ID всё ещё может содержать неверный body, и наоборот.
- **Пример и типичная путаница:** разобрать существующую Task с положительным ID и телом, в котором передано только одно поле. Не смешивать ID с полем обновления и не помещать `id` или `tags` в схему клиента.
- **Первое самостоятельное действие:** ученик классифицирует готовые запросы по path и body, определяя, какая часть FastAPI проверит до вызова сервиса. Критерий: положительный ID направляет к конкретному ресурсу, но не подтверждает, что Task существует.
- **Опора для повторного обращения:** перед практикой восстановить форму path, роль `Request` и различие 422 при ошибке разбора и 404 при корректном положительном, но отсутствующем ID.
- **Переход:** после выделения входов можно определить, какие поля действительно переданы для изменения.

## 03. TaskPatch превращается в набор эффективных изменений

- **Что и зачем объяснить:** не повторять устройство схемы из 54.1, а восстановить, как сериализация уже проверенной `TaskPatch` сохраняет намерение клиента.
- **Механизм и порядок:** вспомнить `model_dump(exclude_unset=True, exclude_none=True)`: сначала исключаются поля, которых не было во входе, затем значения `None`; явный `False` остаётся. Сопоставить четыре ситуации: пустой объект, одно обычное значение, `null` отдельного поля и `is_done=False`. Различить отсутствие body, весь JSON `null` и допустимый JSON-объект `{}`.
- **Пример и типичная путаница:** использовать на независимой схеме настроек пару `{}` и `{"enabled": false}`. Не считать условие по истинности значения заменой проверки присутствия: оно потеряет `False`. Не применять `exclude_defaults` вместо двух договорных флагов.
- **Первое самостоятельное действие:** до использования в маршруте ученик сам определяет, что останется в `changes` для каждого из четырёх входов, и объясняет результат. Критерий: `False` передаётся сервису, пропуск и `null` не создают команду изменения.
- **Опора для повторного обращения:** рядом с практическим использованием напомнить назначение обоих dump-флагов и характерную ошибку `if value`, теряющую ложное значение. Полное объяснение схемы остаётся в 54.1.
- **Переход:** сформированный словарь `changes` получает сервис, уже отвечающий за состояние Planner.

## 04. Handler вызывает текущий Planner и возвращает TaskRead

- **Что и зачем объяснить:** маршрут должен делегировать частичное изменение тому же объекту Planner, который используют остальные HTTP-операции и CLI.
- **Механизм и порядок:** объяснить последовательность без готового решения: FastAPI передаёт `Request`, `task_id` и `TaskPatch`; handler извлекает сервис из `request.app.state.planner`, получает эффективные `changes`, вызывает `patch_task` с ID и именованными значениями через готовый `_call_with_task_not_found_as_404(operation, *args, **kwargs)`, затем отдаёт полученную доменную Task в `TaskRead`. Helper 48.1 преобразует только `TaskNotFoundError` в 404.
- **Пример и типичная путаница:** показать границу между полным доменным объектом и публичной проекцией. `TaskRead` возвращает `id`, `title`, `priority`, `is_done`; `tags` остаётся в JSON и не становится частью HTTP-ответа.
- **Первое самостоятельное действие:** ученик самостоятельно дописывает один PATCH-handler в существующий `app/api.py`, комбинируя готовые компоненты без повторного объявления схемы или метода сервиса. Результат: запрос к известному ID даёт 200 и актуальную публичную Task.
- **Опора для повторного обращения:** перед самостоятельным кодированием восстановить ответственность `Request.app.state`, `patch_task`, `_call_with_task_not_found_as_404` и `response_model=TaskRead`; форму вызова описать словами, не давать готовый handler.
- **Переход:** после первого успешного вызова проверить пустое изменение и границы ошибок.

## 05. Успех, no-op и ошибки имеют разные признаки

- **Что и зачем объяснить:** 200 означает успешное обновление и содержит TaskRead; отсутствие изменяемых полей не означает отсутствие самой Task. Разделить ошибку входа, отсутствие ресурса и сбой хранения.
- **Механизм и порядок:** пустой `{}` и `null` отдельного поля дают no-op для существующей Task. Пустое изменение для неизвестного корректного ID всё равно проходит через сервис и даёт 404. Body без значения, весь JSON `null`, неверная длина title или неподдерживаемый тип не подменяют пустой объект и дают 422. Ошибка `StorageError` не переводится в 404 или 422.
- **Пример и типичная путаница:** сопоставить существующую Task с пустым PATCH и отсутствующий ID с тем же PATCH. Если handler пропускает сервис при пустом `changes`, второй случай ошибочно перестаёт давать 404. Широкий `except Exception` также скрывает сбой сохранения.
- **Первое самостоятельное действие:** после изучения границ ученик классифицирует обычный запрос, no-op, неверный body, неверный path, отсутствие и storage-сбой. Критерий: HTTP-статус определяется источником результата, а не общим перехватом.
- **Опора для повторного обращения:** перечислить, что валидируется до handler, какая ошибка приходит из сервиса и какая остаётся серверным сбоем. Не вводить правило приоритета для запроса, где одновременно неверны path и body.
- **Переход:** наблюдаемые HTTP-ответы нужно сверить с сохранённым состоянием, а не принимать статус за доказательство JSON-записи.

## 06. Свежее чтение подтверждает сохранённое состояние

- **Что и зачем объяснить:** ответ PATCH показывает публичную Task, но не должен быть единственным доказательством. Новый GET, CLI или новый экземпляр сервиса с тем же путём подтверждает, что изменение сохранилось в общей JSON-основе.
- **Механизм и порядок:** сохранить фактические ID, значения, `tags` и статистику до запроса; после успешного PATCH перечитать Task и общий счётчик. Сравнивать полный внутренний JSON для `tags`, так как публичный `TaskRead` их не содержит. При ошибках сверять снимок до и после, а не только `total`.
- **Пример и типичная путаница:** показать, что неизменившийся `total` не доказывает отказ, если другое поле изменилось; сравнить конкретную Task и статистику только для изменения `is_done`.
- **Первое самостоятельное действие:** ученик объясняет, какой источник нужен для подтверждения каждого свойства: ответ для формы HTTP, новый GET/CLI для свежести, JSON для сохранности `tags` и соседей.
- **Опора для повторного обращения:** при проверке восстановить ожидаемые четыре публичных поля, место `tags` и правило чтения того же настроенного JSON. Не создавать новую задачу между проверкой отсутствия и повторным запросом.
- **Переход:** накопленные проверки собираются в ручную практику одного маршрута.

## 07. Что мы будем делать в практике

**Формат и исходная опора:** ручная практика в существующем Planner API через уже подключённый HTTP-клиент и CLI. Начинаем с реальных данных общего JSON, существующих `TaskPatch`, `patch_task`, `TaskRead` и прежних GET/PUT. Не используем TestClient: fixtures и HTTP-тесты вводятся позже.

1. **Снимем состояние конкретной Task:** исходные значения берём из списка/статистики API и CLI, выбираем реально существующий положительный ID и фиксируем нужные поля, ID, `tags` и соседа. Для различения `False` и отсутствия выбираем уже завершённую Task; если такой нет, сначала используем готовый PUT на существующей записи, сохраняя её текущие `title` и `priority`, и только затем фиксируем baseline. Если JSON пуст, подготовим одну запись уже работающим POST и возьмём фактический ID. Опора: блоки 02 и 06, прежний навык GET/PUT/POST. Критерий: доступен проверяемый baseline, подготовка не меняет посторонние записи.
2. **Самостоятельно добавим один HTTP-маршрут:** в существующий `app/api.py` ученик подключает готовый `TaskPatch` к текущему Planner через `Request`, положительный path и `_call_with_task_not_found_as_404`; `changes` передаются готовому `patch_task`, результат оформляется `TaskRead`. Опора: блоки 02–04. Проверяем одно обычное поле: ответ 200 имеет четыре публичных поля, свежий GET показывает новое значение, ID и скрытые от ответа `tags` сохранены.
3. **Различим применение и no-op:** на подготовленной завершённой Task самостоятельно отправляем `is_done=False`, затем `{}` и `null` отдельного поля. Опора: блоки 03–06. Критерий: `False` переводит Task в открытое состояние, сохраняя `total` и меняя `open/done`; пустое тело-объект и `null` не меняют значения существующей Task.
4. **Проверим границы и прежние возможности:** отправляем неверный title или тип, запрос с отсутствующим целым положительным ID и пустой PATCH на такой ID; отдельно убеждаемся, что весь body отсутствующий или равный JSON `null` не принят как `{}`. Опора: блок 05 и прежняя проверка HTTP-ошибок. Критерий: неверный вход даёт 422 без изменения записи, отсутствующий ресурс даёт 404 даже при no-op; широкого перехвата storage-ошибки нет. Повторно проверяем GET item/list, stats, прежний PUT и CLI, не переписывая их.

Каждый результат относится к уже выполненному действию: после добавления handler проверяется обычный PATCH, после no-op и `False` сверяются значения и статистика, после ошибок сравнивается исходная запись с новой. Итог практики подтверждает B: существующая Task обновляется через тот же Planner и JSON; ошибки не создают upsert и не оставляют частичных изменений; `id`, `tags` и соседи сохранены. Удаление не выполняется, чтобы передать следующему занятию ресурс с подтверждённым PATCH-состоянием.
