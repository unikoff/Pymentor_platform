## 00. Вступление

Task уже можно менять на уровне сервиса, а Pydantic-схема умеет описать частичный набор входных полей. Новый вопрос теперь не в повторной реализации обновления: как соединить эти готовые части с HTTP так, чтобы клиент изменил выбранную Task и получил её сохранённое представление?

1. **Точка старта:** по маршруту предыдущие шаги должны подготовить сервис `patch_task` и схему `TaskPatch`; перед работой ученик показывает их и объясняет различие пропуска, `null` и `False`.
2. **Новый вопрос:** как маршрут превращает HTTP-body в именованные изменения, передаёт их существующему сервису и обрабатывает его результат?
3. **Результат:** появляется один PATCH-маршрут; его ответ, свежий GET и чтение через CLI подтверждают сохранённое состояние.

Эти пункты задают последовательность занятия: восстановить договор входа, собрать HTTP-границу вокруг готового действия, затем проверить внешний ответ и данные после нового чтения. Планируемые предпосылки нужно подтвердить перед использованием; старый урок 61 остаётся источником содержания, а не доказательством готовности новой A.

## 01. PATCH связывает запрос с существующим действием

- **Что и зачем объяснить:** коротко восстановить отличие PATCH от PUT: первый передаёт выборочные изменения, второй требует полный редактируемый набор. В этом занятии PATCH не создаёт ресурс и не реализует второй алгоритм обновления. Он открывает для клиента уже готовую операцию Planner.
- **Механизм и порядок:** простыми словами развести роли: клиент отправляет запрос; маршрут (route) сопоставляет адрес и HTTP-метод с функцией приложения; handler — эта функция, которая связывает вход с готовой операцией; `TaskPatch` проверяет форму body; `PlannerService` меняет данные; JSON остаётся общим хранилищем. Проследить цепочку «запрос → проверка → передача изменений → сохранение → публичный ответ» и назвать, кто выполняет каждый переход.
- **Пример и типичная путаница:** на настройке уведомлений сопоставить `PATCH /settings/42` с body `{"email_enabled": false}` и прямым изменением файла. Адрес выбирает запись, body задаёт изменение; handler передаёт его сервису, а не повторяет поиск, создание объекта или `save`. Название HTTP-метода не заменяет имя функции `patch_task`.
- **Первое самостоятельное действие:** на отдельном примере с настройкой напоминаний ученик отмечает, где проверяется body, какая функция меняет запись и какой слой сохраняет её. Затем объясняет ту же цепочку для Planner без написания кода. Критерий: ученик не приписывает HTTP-клиенту работу сервиса или JSON.
- **Переход:** договор участников станет основой чтения path и body конкретного запроса.

## 02. Path выбирает Task, body задаёт изменения

- **Что и зачем объяснить:** показать форму `PATCH /tasks/{task_id}`. Path — часть адреса, которая выбирает Task по ID; JSON-body содержит только запрошенные изменения. Объяснить, что `Request` позволяет получить тот же Planner приложения, которым пользуются остальные маршруты.
- **Механизм и порядок:** показать запрос `PATCH /tasks/12` с JSON-body `{"title":"Купить молоко"}`. Path — часть адреса; здесь он выбирает ID 12. Body — данные запроса; здесь в нём только новое название. `Request` — объект текущего запроса, через который handler получает Planner приложения. FastAPI разбирает path по ранее введённой форме `Annotated[int, Path(gt=0)]`, затем body как `TaskPatch`. Это разные входы: положительный ID ещё не доказывает, что Task существует; неверный ID и неверное поле body — отдельные причины 422. Новые варианты аннотаций не добавлять.
- **Пример и типичная путаница:** разобрать `PATCH /tasks/12` с body `{"title":"Купить молоко"}`: ID находится в адресе, новое название — в JSON. Не смешивать эти части запроса и не помещать `id` или внутренний `tags` в клиентскую схему.
- **Первое самостоятельное действие:** ученик классифицирует готовые запросы по path и body, определяя, какая часть FastAPI проверит до вызова сервиса. Критерий: положительный ID направляет к конкретному ресурсу, но не подтверждает, что Task существует.
- **Опора для повторного обращения:** перед практикой восстановить форму path, роль `Request` и различие 422 при ошибке разбора и 404 при корректном положительном, но отсутствующем ID.
- **Переход:** после выделения входов можно определить, какие поля действительно переданы для изменения.

## 03. TaskPatch превращается в набор эффективных изменений

- **Что и зачем объяснить:** не повторять устройство схемы из 54.1, а восстановить, как сериализация уже проверенной `TaskPatch` сохраняет намерение клиента.
- **Механизм и порядок:** объяснить, что `model_dump` превращает проверенную схему в обычный словарь. `exclude_unset=True` убирает поля, которых клиент не присылал; `exclude_none=True` убирает присланные `null`. Явный `False` — значение, поэтому остаётся. На `TaskPatch` сопоставить `{}`, `{"title":"Новая запись"}`, `{"title":null}` и `{"is_done":false}`. Отдельно различить пустой объект `{}`, отсутствие body и весь JSON `null`: по принятому договору допустим `{}`, а два последних входа не подменяются пустым объектом.
- **Пример и типичная путаница:** использовать на независимой схеме настроек пару `{}` и `{"enabled": false}`. Не считать условие по истинности значения заменой проверки присутствия: оно потеряет `False`. Не применять `exclude_defaults` вместо двух договорных флагов.
- **Первое самостоятельное действие:** до использования в маршруте ученик предсказывает, какие ключи останутся в `changes` для каждого из четырёх тел, и объясняет результат. Критерий: `False` передаётся сервису, пропуск и `null` не создают команды изменения; пустой объект даёт пустой словарь.
- **Опора для повторного обращения:** рядом с практическим использованием напомнить назначение обоих dump-флагов и характерную ошибку `if value`, теряющую ложное значение. Полное объяснение схемы остаётся в 54.1.
- **Переход:** сформированный словарь `changes` получает сервис, уже отвечающий за состояние Planner.

## 04. Handler вызывает текущий Planner и возвращает TaskRead

- **Что и зачем объяснить:** маршрут должен делегировать частичное изменение тому же объекту Planner, который используют остальные HTTP-операции и CLI.
- **Механизм и порядок:** разобрать маршрут как последовательность вопросов, не как готовый код: что FastAPI передал (`Request`, `task_id`, `TaskPatch`); откуда взять общий Planner (`request.app.state.planner`); как получить словарь эффективных изменений `changes`; какую готовую операцию вызвать (`patch_task`); как передать ей ID и поля именованными аргументами через `_call_with_task_not_found_as_404(operation, *args, **kwargs)`; какой объект вернуть и как ограничить публичный ответ через `response_model=TaskRead`. Helper из 48.1 превращает только `TaskNotFoundError` в 404. Сначала ученик трассирует такую цепочку на схеме, затем собирает собственный handler без готового кода.
- **Пример и типичная путаница:** показать границу между полным доменным объектом и публичной проекцией. `TaskRead` возвращает `id`, `title`, `priority`, `is_done`; `tags` остаётся в JSON и не становится частью HTTP-ответа.
- **Первое самостоятельное действие:** ученик самостоятельно дописывает один PATCH-handler в существующий `app/api.py`, комбинируя готовые компоненты без повторного объявления схемы или метода сервиса. Результат: запрос к известному ID даёт 200 и актуальную публичную Task.
- **Опора для повторного обращения:** перед самостоятельным кодированием восстановить ответственность `Request.app.state`, `patch_task`, `_call_with_task_not_found_as_404` и `response_model=TaskRead`; форму вызова описать словами, не давать готовый handler.
- **Переход:** после первого успешного вызова проверить пустое изменение и границы ошибок.

## 05. Успех, no-op и ошибки имеют разные признаки

- **Что и зачем объяснить:** 200 означает успешное обновление и содержит TaskRead; отсутствие изменяемых полей не означает отсутствие самой Task. Разделить ошибку входа, отсутствие ресурса и сбой хранения.
- **Механизм и порядок:** пустой `{}` и `null` отдельного поля дают no-op для существующей Task, то есть сохраняют прежние значения. Для неизвестного корректного ID сервис всё равно вызывается даже с пустым `changes`, чтобы вернуть 404, а не ложный 200. Отсутствующий body, весь JSON `null`, неверное значение или тип дают 422 и не подменяются пустым объектом. Ошибка `StorageError` остаётся ошибкой приложения и не переводится в 404 или 422.
- **Пример и типичная путаница:** сопоставить существующую Task с пустым PATCH и отсутствующий ID с тем же PATCH. Если handler пропускает сервис при пустом `changes`, второй случай ошибочно перестаёт давать 404. Широкий `except Exception` также скрывает сбой сохранения.
- **Первое самостоятельное действие:** ученик разбирает по этапам четыре случая: неверный path, корректный ID без записи, неверное поле и сбой JSON. Затем сравнивает пустой PATCH существующей и отсутствующей Task. Критерий: 422 относится к неверному входу, 404 — к отсутствующему ресурсу, а сбой хранения не маскируется общим перехватом.
- **Опора для повторного обращения:** перечислить, что валидируется до handler, какая ошибка приходит из сервиса и какая остаётся серверным сбоем. Не вводить правило приоритета для запроса, где одновременно неверны path и body.
- **Переход:** наблюдаемые HTTP-ответы нужно сверить с сохранённым состоянием, а не принимать статус за доказательство JSON-записи.

## 06. Свежее чтение подтверждает сохранённое состояние

- **Что и зачем объяснить:** ответ PATCH показывает публичную Task, но не должен быть единственным доказательством. Новый GET, CLI или новый экземпляр сервиса с тем же путём подтверждает, что изменение сохранилось в общей JSON-основе.
- **Механизм и порядок:** сохранить фактические ID, значения, `tags` и статистику до запроса; после успешного PATCH перечитать Task и общий счётчик через свежий GET, CLI и новый экземпляр сервиса/повторную загрузку того же JSON. Сравнивать полный внутренний JSON для `tags`, так как публичный `TaskRead` их не содержит. При ошибках сверять снимок до и после, а не только `total`.
- **Пример и типичная путаница:** показать, что неизменившийся `total` не доказывает отказ, если другое поле изменилось; сравнить конкретную Task и статистику только для изменения `is_done`.
- **Первое самостоятельное действие:** до практики ученик выбирает, чем подтвердить четыре свойства: тело HTTP-ответа, актуальность после нового чтения, сохранность `tags` и сохранность соседней записи. Критерий: для каждого свойства назван соответствующий источник, и один статус 200 не считается доказательством всего состояния.
- **Опора для повторного обращения:** при проверке восстановить ожидаемые четыре публичных поля, место `tags` и правило чтения того же настроенного JSON. Не создавать новую задачу между проверкой отсутствия и повторным запросом.
- **Переход:** накопленные проверки собираются в ручную практику одного маршрута.

## 07. Что мы будем делать в практике

**Формат и исходная опора:** ручная практика в существующем Planner API через уже используемый HTTP-клиент и CLI. Сначала ученик показывает готовые `TaskPatch`, `patch_task`, `TaskRead` и прежние GET/PUT; преподаватель сверяет их с входным состоянием проекта. Затем используется реальная запись общего JSON. Если предпосылки или нужная версия не подтверждены, API-практику не начинают и не переписывают эти части в рамках занятия. TestClient не используется: fixtures и HTTP-тесты относятся к следующему блоку.

1. **Зафиксировать исходное состояние:** по GET/CLI выбрать существующий положительный ID и записать его `title`, `priority`, `is_done`, внутренний `tags` и одну соседнюю запись. Для теста `False` нужна завершённая Task. Если такой нет, подготовить её уже изученным PUT на существующей записи, сохранив остальные поля, и только после этого снять baseline. Если JSON пуст, создать одну запись готовым POST и использовать возвращённый фактический ID. Опора: GET/CLI и прежние PUT/POST. Критерий: до изменения есть конкретные значения для сравнения, а подготовка не затрагивает посторонние записи.
2. **Собрать маршрут по шагам:** в существующем `app/api.py` ученик самостоятельно соединяет `Request`, положительный path, `TaskPatch`, `changes`, готовый `patch_task`, helper 404 и `response_model=TaskRead`. До запуска он объясняет, что делает каждый параметр и почему handler не пишет в JSON. Опора: блоки 01–04. Критерий: запрос к существующему ID возвращает 200 и четыре публичных поля.
3. **Проверить изменение и отсутствие команды:** отправить обычное изменение одного поля и сверить ответ, свежий GET, CLI и чтение после перезапуска API/создания нового экземпляра сервиса с тем же JSON; затем на завершённой Task передать `is_done=False`, после чего отправить `{}` и `{"title":null}`. Опора: блоки 03–06. Критерий: явный `False` применён; пропуск и `null` оставили значения прежними; `id`, `tags` и соседняя запись сохранились. Для изменения статуса сверить `open/done`; один лишь `total` не считать доказательством.
4. **Проверить отказы без мутации:** отправить плохое значение поля и убедиться в 422 со сравнением состояния до/после; затем корректный положительный ID отсутствующей Task и пустой `{}` — ожидать 404. Отдельно проверить отсутствие body и весь JSON `null`: оба не трактуются как `{}` и дают 422. Опора: блок 05. Критерий: нет upsert и частичной записи; причина отказа распознана по этапу. Повторно проверить GET item/list, stats, прежний PUT и CLI; storage-сбой не имитировать изменением инфраструктуры.

Каждый результат относится к уже выполненному действию: после добавления handler проверяется обычный PATCH, после no-op и `False` сверяются значения и статистика, после ошибок сравнивается исходная запись с новой. Итог практики подтверждает B: существующая Task обновляется через тот же Planner и JSON; ошибки не создают upsert и не оставляют частичных изменений; `id`, `tags` и соседи сохранены. Удаление не выполняется, чтобы передать следующему занятию ресурс с подтверждённым PATCH-состоянием.
