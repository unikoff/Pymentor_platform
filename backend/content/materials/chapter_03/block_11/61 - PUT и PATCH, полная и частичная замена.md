# 61. PUT и PATCH: полная и частичная замена

<!-- youtube: -->

## 00. От чтения к изменению

- **Прежняя опора.** Planner уже создаёт и читает Task через API, PlannerService и общий JsonStorage.
- **Новый вопрос.** Как изменить одну сохранённую задачу, не создать дубликат и не потерять её внутренние данные?
- **Результат.** PUT заменит все редактируемые поля, а PATCH изменит только выбранные.

В предыдущем занятии мы убедились, что CLI и API обращаются к одному Planner. Теперь продолжим тот же путь: найдём Task, построим её новое состояние и сохраним его через существующие слои. Временный список задач здесь не нужен.

## 01. Полная замена и точечная поправка

Представьте карточку бронирования. Если клиент меняет все доступные ему поля, он отправляет полный набор. Если переносит только дату, он присылает одну поправку.

В HTTP это разные договорённости. **PUT** получает полный набор редактируемых данных. Если забыть обязательное поле, сервер не должен угадывать, оставить старое значение или заменить его пустым. **PATCH** получает только поля, которые клиент хочет изменить. Остальные значения остаются прежними.

Клиенту нужно перенести дату бронирования. Какое тело соответствует частичному изменению?

```http
PATCH /bookings/18
Content-Type: application/json

{
  "date": "2026-10-12"
}
```

Так сервер получает точное намерение. Пустая строка, ноль и `false` тоже могут быть настоящими значениями, поэтому нельзя обозначать пропуск такими заменителями.

Короткое тело само по себе не делает запрос PATCH. Важны HTTP-метод и его договорённость. В Planner PUT заменит полный редактируемый набор `title`, `priority` и `is_done`. PATCH изменит только переданные значения из этого набора.

**Проверьте себя.** Клиент прислал PUT с новым `title`, но пропустил `priority`. Может ли сервер молча оставить старый приоритет?

**Разбор.** Нет. PUT требует весь набор редактируемых полей. Схема должна отклонить неполное тело. Иначе клиент и сервер по-разному поймут значение «заменить».

## 02. Что именно можно заменить у Task

HTTP-клиент меняет публичные свойства задачи, но не переписывает всю доменную модель.

У ресурса есть постоянная идентичность. Адрес `/tasks/18` выбирает конкретную Task. Клиент может заменить `title`, `priority` и `is_done`. Сам `id` остаётся прежним. Внутренние `tags` тоже сохраняются, потому что в этом API клиенту не разрешено ими управлять.

- **Адрес** выбирает задачу по `task_id`; идентификатор не входит в тело обновления.
- **Редактируемая часть** состоит из `title`, `priority` и `is_done`; каждое значение проходит проверку.
- **Состояние Planner** сохраняет `id` и `tags` исходной доменной Task.

Это похоже на редактирование профиля. Форма позволяет поменять имя и настройки, но не даёт человеку переписать внутренний номер учётной записи. На HTTP-границе схемы описывают вход. PlannerService возвращает полноценный Task. Знакомая TaskRead готовит публичный ответ.

**Верно или неверно?** Если PUT получил все три редактируемых поля, сервис должен заменить также `id` и `tags`.

**Разбор.** Неверно. Полный здесь означает весь набор полей формы обновления, а не каждое поле доменной Task. Идентичность и `tags` сохраняются из найденной записи.

## 03. Две схемы описывают два намерения

Схема входа заранее задаёт обещание клиента: полный набор для PUT или отдельные изменения для PATCH.

Условная схема полного обновления могла бы выглядеть так:

```python
from pydantic import BaseModel


class BookingUpdate(BaseModel):
    date: str
    guest_count: int
    confirmed: bool
```

Все поля обязательны. Если одно пропущено, Pydantic остановит запрос с 422 до вызова маршрута. Сервер не угадывает, что клиент хотел сделать.

Для частичного изменения все поля становятся необязательными:

```python
class BookingPatch(BaseModel):
    date: str | None = None
    guest_count: int | None = None
    confirmed: bool | None = None
```

Переданное значение всё равно проверяется. Например, частичное тело не делает отрицательное число допустимым, если договор ограничивает его снизу нулём.

`None` означает, что поле отсутствует или клиент передал `null`. В нашем договоре оба случая означают «оставить прежнее значение». Это не способ очистить поле. Если продукту понадобится отдельное действие для очистки, его нужно определить в контракте явно.

## 04. Отсутствие, null и False не одно и то же

Для PATCH важны и значение, и то, отправлял ли его клиент. Без параметров `model_dump()` Pydantic может добавить значения по умолчанию. Сервер тогда примет их за команды перезаписать данные.

Посмотрим на независимую схему настроек уведомлений:

```python
from pydantic import BaseModel


class AlertsPatch(BaseModel):
    email: bool | None = None
    sms: bool | None = None

changes = AlertsPatch(email=False).model_dump(
    exclude_unset=True,
    exclude_none=True,
)
print(changes)
```

Вывод:

```text
{'email': False}
```

`exclude_unset=True` оставляет поля, которые действительно пришли во входном теле. `exclude_none=True` убирает `null` по нашему договору. `False` не равен `None`, поэтому остаётся явной командой выключить уведомления.

Сравните три входа:

```python
print(AlertsPatch(email=False).model_dump(exclude_unset=True, exclude_none=True))
# {'email': False}

print(AlertsPatch(email=None).model_dump(exclude_unset=True, exclude_none=True))
# {}

print(AlertsPatch().model_dump(exclude_unset=True, exclude_none=True))
# {}
```

Первые три строки означают соответственно: выключить email, не менять email и ничего не менять. В выбранном контракте `null` и пропуск приводят к пустому словарю изменений, но сами входы различаются. JSON-тело `{}` тоже даёт пустой словарь. Если отправить вообще без тела, FastAPI может отклонить запрос, потому что параметр body обязателен.

Не заменяйте эту проверку на условие `if patch.email`: оно потеряет `False`. Не полагайтесь и на `exclude_defaults`: этот режим сравнивает значение с default, а не проверяет, присылал ли его клиент. Если default поля станет `False`, явно отправленное `False` может исчезнуть из результата.

**Предскажите результат.** Что останется в словаре для `AlertsPatch(sms=False)`? А для `AlertsPatch(sms=None)`?

**Разбор.** В первом случае получится `{'sms': False}`. Во втором поле удалится параметром `exclude_none`, результат будет `{}`. Пустой JSON-объект PATCH тоже не меняет Task.

## 05. PlannerService меняет Task и сохраняет её

Схема проверяет HTTP-вход, но не сохраняет Planner. Это по-прежнему ответственность существующего сервиса и JsonStorage.

Обновление проходит знакомый путь: сервис загружает список, находит задачу, строит новую корректную версию, заменяет запись и сохраняет весь список. При PUT новые `title`, `priority` и `is_done` берутся из полного тела. При PATCH каждое переданное значение накладывается на старое, остальные поля остаются прежними.

Перед сохранением создаётся новый объект Task. Так его предметные правила могут проверить результат до записи. При создании новой версии перенесите исходные `id` и копию `tags`. Если построение Task завершится ошибкой, `save` ещё не вызывался.

Найдите проблему в таком порядке операций:

```python
current.title = title
storage.save(tasks)
current.priority = priority
current.is_done = is_done
```

**Разбор.** Файл сохраняется сразу после изменения названия. Если последующая проверка или операция завершится ошибкой, JSON уже будет содержать частично обновлённую задачу. Сначала создайте и проверьте новую Task, затем замените элемент списка и вызовите `save` один раз.

PlannerService не импортирует FastAPI и не выбирает 200, 404 или 422. Он знает Task, правила Planner и storage. Поэтому те же операции доступны и API, и другим интерфейсам.

## 06. HTTP связывает контракт с сервисом

PUT и PATCH работают с одним адресом задачи и одним публичным ответом. Отличаются схемы входа и метод PlannerService:

```text
PUT /tasks/{task_id} + TaskUpdate
    → PlannerService.replace_task(...)
    → TaskRead

PATCH /tasks/{task_id} + TaskPatch
    → только явно присланные поля
    → PlannerService.patch_task(...)
    → TaskRead
```

Маршрут передаёт операцию через `app.state.planner`. Он не открывает JSON, не создаёт второй список и не обновляет копию только ради красивого ответа. Сервис возвращает полноценную доменную Task, а `response_model=TaskRead` формирует знакомое публичное представление.

У ошибок разные причины и ответственные части:

- **422**. Pydantic не принял тело либо FastAPI не смог преобразовать `task_id`.
- **404**. Запрос и тело корректны, но PlannerService не нашёл задачу с таким id. HTTP-граница переводит `TaskNotFoundError` в ответ 404.
- **Ошибка storage**. Сервис не смог прочитать или сохранить JSON. Это не отсутствие Task и не должно маскироваться под 404.

Создание задачи остаётся операцией POST. PUT и PATCH не добавляют запись, когда id не найден. Это обновления, а не upsert.

**Проверьте себя.** Что должен вернуть PATCH с корректным телом для неизвестного id? А если тело содержит неверный `priority`?

**Разбор.** Корректное тело и отсутствующий ресурс дают 404. Неверное значение тела не проходит Pydantic и даёт 422 до вызова сервиса. Если одновременно ошибочны и id, и тело, занятие не вводит отдельное правило приоритета этих ошибок.

## 07. Что мы будем делать в практике

Мы добавим два способа обновить существующую задачу в том же Planner и докажем, что изменение переживает новое чтение.

1. В существующем `schemas.py` опишем полный `TaskUpdate` и частичный `TaskPatch`.
2. В текущем `PlannerService` добавим `replace_task` и `patch_task`. Новая Task должна пройти свои правила до сохранения; `id` и `tags` останутся прежними.
3. Подключим PUT и PATCH к `app.state.planner`. Неполный или неверный вход остановится с 422, а корректный запрос к отсутствующему id даст 404.
4. Проверим полный PUT, частичный PATCH с явным `is_done=False`, пустое тело и `null`. Сверим результат по новому чтению, общей статистике, CLI и JSON.

Практика завершена, когда новое чтение того же JSON показывает версию Task с ожидаемыми изменениями, прежними `id` и `tags`. PATCH с `is_done=False` возвращает её в открытые и отражается в общей статистике. Ошибки 422 и 404 не создают и не меняют записи.

Следующий шаг подключит к этому же Planner существующую операцию удаления. Новое хранилище, второй CRUD и работа с временным списком в этой практике не нужны.
