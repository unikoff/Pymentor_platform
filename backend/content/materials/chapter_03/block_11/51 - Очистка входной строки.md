## 01. Где заканчивается разбор запроса и начинается действие

- **Что и зачем:** JSON может быть написан правильно, но поле `title` в нём может иметь неправильный тип. Объяснить простыми словами: `TaskCreate` принимает и проверяет тело запроса **до** запуска функции POST; `add_task` выполняет действие **после** проверки схемы. Нельзя считать успешный разбор JSON созданной задачей.
- **Механизм и учебный визуал:** проследить одну строку из пяти звеньев `JSON body → TaskCreate → POST endpoint → PlannerService.add_task → JSON storage`. На каждом звене показать вопрос «прошли дальше или остановились?», а не пять несвязанных определений. До endpoint — ошибки входной схемы; в доменной `Task` внутри сервиса — предметные ограничения.
- **Независимый случай:** модель доставки с полем `recipient: str` получает `42`: JSON корректен, но поле не проходит проверку строкового типа, код отправки посылки не вызывается. Аналогия «проверка адреса перед отправкой» объясняет порядок, но сама по себе не определяет конкретный HTTP-статус.
- **Первое действие:** ученик рисует две трассы: `recipient="Анна"` и `recipient=42`, ставит точку остановки и объясняет, почему во втором случае действие не произошло. Проверить выбор на схеме, затем соотнести с `TaskCreate` и `add_task`. Отдельно пояснить, что `422` возможен и позже — от прежнего преобразования доменного `ValueError` в endpoint; место ошибки определяет **порядок**, а не одно число статуса.
- **Переход:** теперь понятно, где остановить неверные данные; разберём, что можно безопасно изменить в подходящей строке до проверки.

## 02. Нормализация и проверка решают разные задачи

- **Что и зачем:** «очистить» означает изменить представление значения, а «проверить» — решить, разрешено ли оно. `strip()` у строки убирает пробелы, табуляции и переводы строк **по краям**, возвращая новую строку. Он не меняет регистр, не удаляет пробелы внутри и не проверяет допустимую длину.
- **Независимый пример и визуал:** не использовать готовый `title`. На табличке адреса доставки `" \tСевер  2  "` выделить *края* и *середину*; после `strip()` получится `"Север  2"` (двойной пробел в середине остаётся). Второй ввод `" \t "` даёт `""`. Таблица «сырой ввод → после очистки → что осталось проверить» показывает, что пустота не превращается автоматически в допустимое значение. Аналогия с обрезанием краёв этикетки работает только для удаления краёв, не как проверка содержимого.
- **Первое действие:** до показа результата ученик предсказывает `"  North  Zone \t".strip()` и `"  \t".strip()`, указывает сохранённые внутренние пробелы и объясняет, почему нормализация сама не запрещает пустую строку. После сверки предложить вход с другим регистром для переноса правила.
- **Опора:** `strip()` — операция **только над строкой**; она отвечает «как выглядит после очистки?». Доменные правила отвечают «можно ли создать такую задачу?».
- **Переход:** нужно вызвать очистку до штатной проверки `TaskCreate`, а не внутри endpoint после создания.

## 03. Before-validator получает исходное значение

- **Что и зачем:** в Pydantic v2 `@field_validator(..., mode="before")` вызывает нашу функцию, когда поле ещё содержит **сырое** значение из JSON. «До» означает «до обычной проверки типа», поэтому нельзя считать вход строкой только потому, что ниже написано `code: str`.
- **Порядок на отдельной модели:** на схеме `RegionInput(code: str)` из примера доставки показать `"  north " → before-validator → "north" → проверка str → code`. Для `42` показать `42 → before-validator (значение не меняем) → проверка str → отказ`. Исходный тип и результат возврата — разные позиции схемы; `before` не отключает проверку Pydantic.
- **Первое действие:** ученик завершает две незаполненные трассы при `" West "` и `42`, выбирая, что возвращает функция в каждом случае; затем по новому входу с внутренним пробелом объясняет, почему он сохраняется. Проверка — число не достигает никакого строкового метода и не становится `"42"`.
- **Опора:** `raw → before → проверка типа → готовое поле`; при ошибке Python от `.strip()` до типовой ошибки вернуться к тому, *какое значение* поступает до проверки.
- **Переход:** теперь разберём запись функции для Pydantic: что означают декораторы, `cls`, аргумент и `return`.

## 04. Сигнатура и порядок декораторов

- **Объяснение на независимом примере:** в `RegionInput` поле `code: str` и функция `strip_code` внутри модели. Показать читаемый образец (это **не** решение для `TaskCreate`):

  ```python
  from pydantic import BaseModel, field_validator

  class RegionInput(BaseModel):
      code: str

      @field_validator("code", mode="before")
      @classmethod
      def strip_code(cls, raw: object) -> object:
          if isinstance(raw, str):
              return raw.strip()
          return raw
  ```

- **Разобрать каждую часть по назначению:** `field_validator("code", ...)` выбирает поле, `mode="before"` — момент вызова, `@classmethod` позволяет объявить метод класса, `cls` — ссылка на модель (в данном примере её не используем), `raw: object` предупреждает, что вход ещё не проверен. Оба `return` передают значение **дальше в Pydantic**; без `return` функция отдала бы `None`. Показать порядок двух декораторов именно как в образце, без темы других режимов.
- **Первое действие:** убрать подписи с частей образца и дать ученику восстановить `code`, `mode`, `cls`, `raw` и место возврата; затем самому объяснить, что произойдёт, если убрать нижний `return`. Критерий — предсказан некорректный `None` на нестроковом вводе, а не только назван декоратор.
- **Опора:** «какое поле → когда вызов → какое сырое значение → что возвращается»; при затруднении вернуться к этому образцу, не копируя в проект код целиком.
- **Переход:** выбор ветки `if isinstance(...)` теперь разберём отдельно на ошибке, которую предотвращаем.

## 05. Защита строки от неверного типа

- **Проблема:** на сыром числе `42` попытка выполнить `42.strip()` вызовет `AttributeError` в пользовательском коде. Это ошибка нашего валидатора, а не штатное сообщение Pydantic о типе поля.
- **Решение и смысл:** `isinstance(raw, str)` проверяет тип **до** операции. Для строки — `return raw.strip()`, иначе — `return raw`. Здесь «вернуть число» означает **дать Pydantic проверить его далее**, а не разрешить числовой `title`; вручную делать `str(raw)` тоже нельзя.
- **Первое действие:** ученик получает неправильный независимый валидатор с безусловным `.strip()` и указывает точную строку сбоя на `42`. Исправляет порядок: сначала `isinstance`, затем вызов метода, вторая ветка возвращает исходный объект. Затем предсказывает три исхода: `" West "` → `"West"`, `42` → обычная ошибка типа, `"  "` → `""` (пока **строковый** тип допустим).
- **Опора и перенос:** если при POST вместо body-ошибки случился `AttributeError`/500, проверить защиту внутри before-validator. Если пришёл `422` из схемы, endpoint не запускался; если `422` возник из доменного `ValueError`, endpoint и сервис уже вызывались. Точный текст `msg` и `loc` доменного ответа не закреплять.
- **Переход:** после независимой проверки готова логика для настоящей `TaskCreate`.

## 06. Очистка в существующей TaskCreate

- **Точка изменения:** показать в рабочем `app/api.py` существующий класс `TaskCreate` с двумя обязательными полями. Ученик добавляет **свой** `field_validator` для `"title"` по механизму разделов 03–05; не переносит туда код `RegionInput` целиком. `priority`, сигнатура POST, ответ, сервис и формат файла не меняются.
- **Две границы на одной схеме:** `HTTP → TaskCreate (убрать края) → endpoint → PlannerService → Task (проверить доменные правила) → JSON`. Визуально отметить, где наблюдаем уже очищенное имя и где только начинается сохранение. Доменная модель продолжает проверять вызовы из CLI и кода без HTTP; её защита нужна даже при чистом входе через API.
- **Различить два отказа:** числовой `title` не проходит **тип** в Pydantic до маршрута; строка `" \t "` после `strip()` становится `""`, формально остаётся строкой, но не проходит существующее правило доменной `Task`. До `51.1` пустоту не проверяет `Field` в HTTP-схеме. Успешный POST проверять по `201`, фактическому `id`, GET и JSON, а не только по статусу.
- **Первое действие до практики:** по схеме ученик размещает карточки «удалены края», «проверен тип», «запущен сервис», «записано в JSON» и объясняет, почему менять `Task` для HTTP-нормализации не нужно. Критерий — при числовом вводе «запущен сервис» и «записано» не наступают.
- **Переход:** механизм понятен отдельно от Planner; практика проверит собственную запись валидатора на живом POST, его ошибки и сохранение прежнего поведения.

## 07. Что мы будем делать в практике

**Формат:** `manual`, изменение существующего проекта в `app/api.py`, без отдельного учебного сервиса. **Исходная опора планируемая:** B `50.1` (рабочие `TaskCreate`, `POST /tasks`, сервис и общий JSON); перед началом проверить её фактически. Задачи в хранилище не стирать и не редактировать руками. Если в checkout уже есть валидатор из исторического `57`, сначала восстановить его логику, проверить ниже отличающиеся случаи и не добавлять дубль. Независимый образец `RegionInput` из блока 04 служит подсказкой по форме, но код для `TaskCreate` ученик составляет сам.

**Цель:** ученик самостоятельно выбирает поле, порядок декораторов, проверку типа и два возврата, затем доказывает на реальных данных, что очистка происходит до endpoint и не нарушает работу Planner.

1. **Проверить точку входа** (опора — `50.1` и блок 01): ученик находит `TaskCreate` в `app/api.py`, прослеживает вызов `add_task` от POST и проверяет ранее созданную запись через GET/CLI/JSON после нового запуска. **Локальный результат:** есть один действующий путь `POST → существующий сервис → общий JSON`; при отсутствии результата `50.1` его сначала восстанавливают, а новый маршрут здесь не пишут.
2. **Самостоятельно написать очистку `title`** (блоки 02–05): в найденной `TaskCreate` ученик без готового кода для Planner выбирает `field_validator("title", mode="before")`, `@classmethod`, аргумент сырого значения, условие `isinstance` и оба `return`; сохраняет обязательность `title/priority`. Если валидатор уже существует, ученик **сам объясняет каждую ветку и корректирует только обнаруженное расхождение**. **Локальный результат:** краевые пробелы убираются у строк, другие типы не вызывают `.strip()`, `priority` и соседние части проекта не затронуты.
3. **Доказать очистку до HTTP-сервиса и после сохранения** (блоки 03 и 06): сначала самостоятельно создать `TaskCreate` с `title=" \tРазобрать API  "` и допустимым `priority`, посмотреть `model.title` — ожидается `"Разобрать API"` **без обращения к endpoint**. Затем отправить эти данные через прежний POST, взять **выданный** `id` из ответа и прочитать объект через GET и общий JSON. **Локальный результат:** POST `201`, очищенное имя совпадает в схеме, ответе и хранилище; нет изменений `priority`, публичных полей и соседних записей.
4. **Различить два отказа без новой записи** (блоки 01, 05, 06): сохранить исходное состояние задач, затем отдельно отправить `{"title": 42, "priority": 3}` и `{"title": " \t ", "priority": 3}`. Ученик **до запроса** предсказывает точку отказа и после сравнивает реальные записи до/после по `id` и значениям. **Локальный результат:** оба запроса дают `422` и не создают/изменяют задачи; число отвергается Pydantic до endpoint, без `AttributeError`/500, а пустая после очистки строка — прежней доменной проверкой уже при вызове сервиса. Не требовать одинаковый `detail`/`loc` у этих ответов.
5. **Проверить перенос на отличающемся вводе** (блок 02): ученик сам предсказывает, что даст `" \tПлан  на вечер \t"`, затем проверяет через `TaskCreate` и POST/GET. **Локальный результат:** сохранено `"План  на вечер"` с **двумя внутренними пробелами** и неизменным регистром; это обнаруживает ошибочное удаление всех пробелов или приведение к нижнему регистру. Ненужную запись при проверке не удалять из чужих данных.

Проверка входа предшествует изменению; самостоятельная запись валидатора предшествует запросам; прямой вызов схемы позволяет отделить её эффект от доменной очистки. Если возник сбой, ученик возвращается в конкретный блок: трасса запроса — 01, края строки — 02, `before` — 03, декораторы — 04, защита типа — 05, разные места отказа — 06. Финальный перенос на двойные пробелы доказывает **что именно** изменилось. Сохранённая схема становится опорой `51.1`, где впервые добавляются ограничения длины и `priority`; здесь они не нужны.
