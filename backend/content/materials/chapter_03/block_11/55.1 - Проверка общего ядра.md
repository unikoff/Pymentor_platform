## Место в маршруте

Это итоговая ручная проверка уже созданных операций, а не новый этап реализации CRUD. Ученик сам составляет и проводит smoke-сценарий, сверяет ответы API с CLI и общим JSON, а затем передаёт BLOCK_12 воспроизводимый набор запросов и найденные расхождения. TestClient и автоматические тесты относятся к следующему блоку.

Планируемая A — результаты `51`–`55`: очистка и ограничения входа, схемы, сохранение и серверный ID, PUT, PATCH и DELETE. До практики ученик повторяет соответствующий ручной smoke и показывает, что проект запускается, API и CLI видят одно состояние. Личное прохождение этих шагов и фактический снимок проекта заранее не подтверждены. Если вход отсутствует или проект не запускается, сначала восстановить его; не считать этот план доказательством готовности.

Непосредственно перед этим планируется [55 — Удаление и пустой ответ](<55 - Удаление и пустой ответ.md>): DELETE должен возвращать пустой 204, а повторное чтение — подтверждать удаление. Следом паспорт [BLOCK_12.md, занятие 56](../../../../../docs/make%20les%20stage/1%20stage/concept/chapter_03/BLOCK_12.md) вводит первый HTTP-тест. План занятия 56 ещё не создан; передача здесь — планируемая: ручная матрица станет исходным состоянием для автоматизации.

## Точка A: статус и источник опоры

- **Подтверждённый прежний опыт:** `STUDYHUB_LEARNINGS.md` фиксирует pytest, `tmp_path`, прямые проверки `PlannerService` и `JsonStorage`, повторную загрузку и сохранность `id`/`tags`. Это свидетельство о прежнем маршруте, но не подтверждение прохождения новых шагов `51`–`55`.
- **Планируемая опора:** паспорта `51`–`55` задают последовательные выходы к POST, PUT, PATCH и DELETE. Перед началом ученик повторяет их ручные проверки, запускает проект, находит его рабочий JSON и сверяет API с CLI. Для каждого шага он подтверждает фактическое состояние, а не предполагает освоение по номеру занятия.
- **Не входит в A:** TestClient, HTTP-fixtures и автоматизация API из BLOCK_12. План не требует от ученика этих знаний.

## Точка B: наблюдаемый результат

- **Объяснить:** как читать контракт endpoint по методу и адресу, статусу, телу ответа и эффекту для данных; почему 204 не имеет JSON-тела; как отличить ожидаемый отказ от частичного изменения; почему ручной smoke проверяет уже собранные части вместе.
- **Самостоятельно сделать:** без готового сценария составить и провести smoke для всех восьми endpoint: `GET /health`, `GET /tasks`, `GET /tasks/{task_id}`, `GET /stats`, `POST /tasks`, `PUT /tasks/{task_id}`, `PATCH /tasks/{task_id}`, `DELETE /tasks/{task_id}`. В последовательность входят заведомо неверный запрос с 422 без изменения данных, корректный запрос к отсутствующему item с 404, прежние `id`/`tags` после PUT, пропуск/`null`/`false` в PATCH и пустое тело при DELETE 204. Затем сверить состояние через API, CLI и JSON после повторного запуска.
- **Изменение проекта:** новых endpoint, runtime-кода и тестового слоя нет. Используются уже собранные API, PlannerService, CLI и общее хранилище.
- **Подтверждение:** все запросы имеют объяснённые ожидания; отказ не меняет состояние; успешные операции отражены в общем хранилище; `id`, внутренние `tags` и соседняя запись сохранены; API и CLI согласованы после нового запуска. Ошибочные запросы и пустое тело 204 проверены без попытки разбирать несуществующий JSON.

## Границы и передача дальше

- **Не повторять:** реализацию POST/PUT/PATCH/DELETE, проверку выборки из прежних занятий, настройку TestClient, pytest-fixtures и автоматизацию. Если найден дефект, зафиксировать запрос, фактический и ожидаемый результат; не чинить код в рамках этого плана.
- **Безопасность данных:** не очищать и не сбрасывать пользовательский JSON, не предполагать фиксированное число задач и не создавать второй storage. Зафиксировать исходную статистику, полный снимок выбранной задачи и контрольной соседней записи. Для изменяющих запросов использовать учебную запись и фактический ID; после сценария удалить только созданную для него запись и проверить возврат исходного состояния.
- **Особенность схемы:** не считать неизвестное дополнительное поле гарантированным поводом для 422, если действующая модель его игнорирует. Для негативного запроса выбрать нарушение установленного ограничения, например неверный тип или выход за разрешённый диапазон.
- **Передача в 56:** ручная последовательность запросов, ожидаемые статусы/эффекты и конкретные дефекты; BLOCK_12 затем превращает выбранные проверки в автоматические HTTP-тесты.

## 00. Зачем проверять общий путь

Если предыдущие шаги действительно подготовлены, теперь можно проверить их вместе. Цель — не написать ещё один CRUD, а убедиться, что запрос проходит через API к прежнему сервису и общему файлу, а CLI после запуска видит те же данные.

1. **Старт:** ученик подтверждает запуск проекта и работу уже изученных операций. Если это не так, практика останавливается до восстановления соответствующей опоры.
2. **Вопрос:** совпадают ли обещанный HTTP-ответ, изменение JSON и состояние, которое показывает CLI?
3. **Итог:** воспроизводимый ручной smoke покрывает ключевые успехи и отказы; система возвращена к состоянию до учебного сценария.

Сначала зафиксировать исходные данные, затем проверить запросы в безопасном порядке и после каждого шага сравнить результат с ожиданием. Не копировать готовый алгоритм из плана в практику: ученик сам выбирает порядок и объясняет, что доказывает каждая проверка.

## 01. Снять исходное состояние и составить матрицу

- **Объяснить:** одна проверка состоит из запроса, ожидаемого статуса и тела, ожидаемого эффекта и способа независимо увидеть этот эффект. До изменения нужно знать исходное состояние.
- **Порядок:** запустить StudyHub; проверить доступность `GET /health`, получить список (`GET /tasks`) и статистику (`GET /stats`); выбрать учебную задачу и отдельную контрольную запись; сохранить их полный исходный вид из JSON, включая внутренние `tags`; прочитать выбранную запись через `GET /tasks/{task_id}` и CLI. Не использовать номер задачи как постоянную величину.
- **Пример различия:** равное число записей не доказывает, что выбранная задача не изменилась. Сравниваются нужные поля обеих записей и статистика.
- **Самостоятельное действие:** ученик сам оформляет таблицу «запрос → ожидаемый ответ → ожидаемое изменение → где перепроверю» для всех следующих запросов. Результат — у каждого шага есть критерий до отправки запроса.
- **Переход:** исходная задача и контрольная запись читаются одинаково через доступные границы; иначе сначала записать конкретное расхождение и не продолжать изменяющий сценарий.

## 02. Проверить создание и отказ без мутации

- **Объяснить:** успешный POST создаёт запись через существующий сервис; сервер назначает фактический `id`. Ответ 422 означает, что запрос отклонён, но сам статус ещё не доказывает отсутствие побочного изменения.
- **Порядок:** отправить допустимый POST и сохранить выданный `id`; затем отправить запрос с известным нарушением ограничения. До и после отказа сравнить статистику и выбранные данные. Перечитать успешную запись через API и CLI.
- **Не делать:** не использовать неизвестное дополнительное поле как гарантированный негативный пример; при обычной настройке модели оно может быть проигнорировано. Не редактировать JSON вручную.
- **Самостоятельное действие:** выбрать нарушение типа или ограничения длины/диапазона, объяснить ожидаемый 422 и показать, что число и данные записей не изменились из-за отказа.
- **Критерий и переход:** у успешной записи есть серверный `id`, а запрос с 422 не добавил и не изменил данные. Если результат не совпал, зафиксировать точный вход и наблюдение.

## 03. Сверить полную замену PUT

- **Объяснить:** PUT передаёт полную форму изменяемых полей. Идентичность задачи остаётся прежней; внутренние `tags` могут отсутствовать в публичном ответе, поэтому их сохранность проверяется в JSON.
- **Порядок:** использовать собственный фактический `id`, отправить полную допустимую форму с отличающимся значением; сверить публичный ответ, прежний `id`, JSON и соседнюю запись. Через CLI проверить то же состояние.
- **Самостоятельное действие:** ученик сам выбирает одно различающее значение, заранее записывает ожидание и показывает, что изменилось только предусмотренное, а задача не превратилась в новую.
- **Критерий и переход:** `id` и `tags` сохранены, нужные поля соответствуют PUT, контрольная запись не затронута; повторная загрузка подтверждает сохранённый результат. Затем можно проверять PATCH на этой же учебной задаче.

## 04. Различить пропуск, null и false в PATCH

- **Объяснить:** PATCH меняет переданные поля. Пропуск поля и переданный `null` по договору этого проекта сохраняют прежнее значение, а `false` является конкретным значением и должен примениться.
- **Порядок:** выбрать булево поле с исходным `true`; отправить PATCH с `false` и проверить сохранение; отдельным запросом проверить пропуск другого поля и `null` в разрешённом поле; после каждого шага перечитать объект.
- **Самостоятельное действие:** до отправки каждого запроса ученик прогнозирует итоговое значение, затем сверяет API, полный JSON и CLI. Он объясняет, почему `false` нельзя спутать с отсутствующим полем.
- **Критерий и переход:** `false` сохранён как `false`; пропущенное и `null`-поле сохранили прежнее значение; `id`, `tags` и соседняя запись не потеряны. Не приписывать пустому PATCH поведение, не подтверждённое действующим контрактом.

## 05. Проверить DELETE, 404 и повторный запуск

- **Объяснить:** успешный DELETE возвращает 204 без тела, поэтому JSON-декодер для ответа вызывать не нужно. Корректный запрос к отсутствующему `id` даёт 404; оба исхода отличаются от ошибки хранилища.
- **Порядок:** удалить созданную для сценария задачу; проверить статус и пустое тело; повторно запросить её и получить 404; проверить статистику, контрольную запись и CLI. Перезапустить приложение и подтвердить сохранённое состояние через новый запрос.
- **Самостоятельное действие:** ученик сам проводит последовательность и объясняет, почему сначала фиксирует `id`, а затем не создаёт новую запись до проверки отсутствия удалённой.
- **Критерий:** удалена только учебная запись; повторный GET и повторный DELETE подтверждают отсутствие; 204 пустой; контрольная запись и остальные исходные данные сохранены. Статистика и CLI согласуются после перезапуска.

## 06. Разобрать расхождение и определить передачу

- **Объяснить:** один ручной smoke даёт свидетельство о конкретных запросах и состоянии, но не заменяет автоматические тесты и не доказывает внутреннее устройство каждого слоя. Следующий блок будет автоматизировать выбранные проверки через HTTP-клиент.
- **Самостоятельное действие:** ученик проходит свою матрицу сверху вниз и для каждого пункта отмечает запрос, ожидаемое/фактическое значение, источник наблюдения и совпадение. Если есть дефект, сохраняет воспроизводимые входные данные и шаг, на котором результат разошёлся; не исправляет runtime в рамках этого занятия.
- **Критерий завершения:** запросы охватывают POST, отказ 422 без мутации, item 404, PUT, PATCH с пропуском/null/false, DELETE 204 без тела; статистика и состояние после перезапуска согласуются между API, CLI и JSON; временная учебная запись удалена.
- **Передача:** передать BLOCK_12 проверяемую матрицу и конкретные расхождения. Дополнительное исследование структуры приложения не требуется.

## 07. Самостоятельная практика

**Формат:** manual, проектная практика в существующем StudyHub. Используются Postman, CLI и настроенный JSON-файл; новые тесты, fixtures, storage и runtime-код не создаются.

1. Убедиться, что входные результаты `51`–`55` доступны; запустить проект и проверить `GET /health`, `GET /tasks`, `GET /stats`, чтение выбранной записи через `GET /tasks/{task_id}` и CLI. Если опора не готова, записать условие восстановления и не выдавать её за выполненную.
2. Выбрать учебную задачу и контрольную соседнюю запись, сохранить полный исходный вид и статистику; составить собственную матрицу запросов и ожидаемых наблюдений.
3. Создать учебную запись через POST, сохранить фактический `id`; выполнить отрицательный запрос с ожидаемым 422 и доказать отсутствие изменения.
4. На созданной записи проверить полную замену PUT и PATCH с `false`, пропуском и `null`. После каждого запроса сверять публичный ответ, JSON и CLI; отдельно следить за `id`, `tags` и контрольной записью.
5. Удалить только созданную учебную запись; проверить пустой 204, повторное отсутствие через 404, статистику и состояние после нового запуска. Не сбрасывать пользовательский файл.
6. Сопоставить факты с матрицей и передать в следующий блок последовательность запросов и конкретные дефекты, если они обнаружены.

**Самостоятельность и суммарный критерий:** готовый порядок запросов заранее не выдаётся. Ученик должен сам выбрать безопасную последовательность, до каждого запроса предсказать наблюдение и объяснить результат. Практика завершена, когда проверены все восемь endpoint, обязательные статусы и эффекты; ошибочный запрос не изменил состояние; прежний `id`/`tags` и соседняя запись сохранены; API и CLI совпали после перезапуска; созданная учебная запись удалена. Ошибка реализации фиксируется как дефект для владельца следующего шага, а не исправляется расширением scope этого плана.

Планируемая передача к занятию 56: ручная матрица становится набором кандидатов для TestClient. Фактическое прохождение и готовность проекта проверяются непосредственно перед выдачей; этот план их не утверждает.
