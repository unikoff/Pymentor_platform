Новый маршрут разделяет [прежнее занятие 61](<61 - PUT и PATCH, полная и частичная замена.md>): здесь ученик подключает к HTTP уже проверенную операцию полной замены; прикладное частичное изменение и PATCH остаются следующим шагом. Занятие **планируется после** результата 53: предметный `replace_task` и его прямые проверки должны быть готовы до добавления HTTP-маршрута. ## Точка B: результат занятия

- Ученик сможет объяснить: PUT требует полный набор редактируемых полей, а не всю доменную запись; неполное тело не должно молча сохранять старые значения. Адрес выбирает существующую Task, а `id` и внутренние `tags` не задаются клиентом.
- Ученик сможет сделать: добавить обязательную схему `TaskUpdate` и единственный PUT-маршрут, который делегирует готовому `replace_task` и возвращает публичный `TaskRead`.
- Результат в проекте: `PUT /tasks/{task_id}` обновляет существующую задачу через общий Planner, возвращает 200 и сохраняет `id`/`tags`; новая задача при неизвестном id не создаётся.
- Как подтвердим: успешное обновление видно при повторном GET и через CLI/JSON; неполное или недопустимое тело даёт 422 без изменения записи; корректное тело для отсутствующего положительного id даёт 404 без upsert. Ответ содержит публичные четыре поля, а `tags` остаётся в доменной записи.

## Границы и передача дальше

- Пока не требуем: PATCH, `TaskPatch`, различия omission/null/false на HTTP-границе, `model_dump` с флагами и `patch_task`. Не создаём сервисную операцию повторно, не рассчитываем `id` в маршруте и не добавляем upsert.
- Передаём следующему занятию: работающий PUT над существующей Task и уже проверенный полный replace; следующий шаг отдельно строит частичную операцию сервиса, сохраняя остальной договор.

## 00. Вступление

Начать с знакомой ситуации: задача уже есть в Planner, а пользователь хочет исправить название, приоритет и отметку выполнения одним запросом. Сервис умеет заменять эти три значения (это проверяется по B `53`), но HTTP пока не умеет получать для него полную форму. Нельзя доверять ответу «готово», пока не проверены поля, найден исходный id и сохранена запись.

1. **Точка старта:** ожидается проверенный полный replace на уровне PlannerService, а API уже читает и создаёт задачи; фактическую готовность подтвердить входной пробой.
2. **Новый вопрос:** как передать замену существующей задачи и не потерять её идентичность, если клиент пропустил обязательное поле?
3. **Результат:** валидировать полную форму до маршрута, вызвать готовый replace и подтвердить сохранённый ответ.

Связь трёх пунктов для будущей `LinkedNotes variant="connected"`: старый метод сервиса работает с готовыми значениями, клиент присылает JSON, а FastAPI должен проверить его и передать значения нужной задаче. Разбор и первая короткая попытка предшествуют самостоятельному написанию модели и маршрута. Учебный визуал: одна линия «клиент → проверка JSON → PUT handler → прежний PlannerService → прежний JSON», с отметкой места отказа 422 и 404; после линии ученик объясняет, почему ошибки возникают на разных границах.

## 01. Полная форма PUT

- **Что и зачем объяснить:** в **этом API** PUT меняет сразу все редактируемые поля найденной задачи: `title`, `priority`, `is_done`. «Полная форма» описывает договор этого endpoint, а не общее обещание, что любой PUT в интернете должен работать именно так. `id` — идентичность объекта, `tags` — внутренние данные; они не входят в форму и не теряются при замене.
- **Механизм и порядок:** клиент выбирает существующую задачу адресом; отправляет все три новых значения телом JSON; FastAPI проверяет форму, после чего сервис заменяет изменяемую часть и сохраняет целую Task. Пропуск обязательного значения — ошибка запроса, а не просьба оставить его прежним. PUT **здесь не создаёт** отсутствующую задачу (не upsert).
- **Независимый пример и наглядная опора № 1:** «заменить анкету настройки уведомлений» с полями «время, канал, включены». Три заполненных поля позволяют заменить настройки; бланк без канала неполон, даже если старый канал известен серверу. Показать таблицу «было/прислано/станет» и отдельно неполный бланк с отметкой «не применять». Граница аналогии: HTTP проверяет точную схему, а бумажный бланк сам по себе не объясняет HTTP-статусы.
- **Первое самостоятельное действие:** по двум новым бланкам для настроек ученик решает, какой можно принять целиком, а какой должен быть отвергнут, и предсказывает, поменяется ли сохранённая настройка. Требуемый вывод: отсутствующий обязательный пункт не подставляется из старой записи. Это **проверка правила**, ещё не написание PUT-кода.
- **Опора для возврата:** краткая схема «путь выбирает старый объект / JSON задаёт все три новых поля / id и tags остаются у сервиса / неполная форма не применяется». Не преподавать механизм PATCH вперёд; слово «частичное» достаточно для сравнения.
- **Переход:** полный договор можно выразить обязательной HTTP-схемой.

## 02. TaskUpdate как входная схема

- **Что и зачем объяснить:** `TaskUpdate` — отдельный Pydantic-вход **для полной замены**, `TaskCreate` — вход создания, `TaskRead` — форма ответа, а доменная `Task` включает дополнительные внутренние сведения. В `TaskUpdate` обязательны `title: str`, `priority: int`, `is_done: bool` без значений по умолчанию. Ни клиентский `id`, ни `tags` в схему не добавлять.
- **Механизм и порядок:** разобрать на уже знакомой `TaskCreate`, где происходят очистка краевых пробелов `title`, проверка длины **после очистки** (1–120) и диапазона `priority` (1–5); эти же правила действуют и здесь. Объяснить отдельно: наличие типа `bool` и отсутствие default — два разных свойства; обязательный `is_done` может иметь значение `false`, оно не означает «поле отсутствует». Не обещать, что любые посторонние JSON-поля автоматически дают 422: это зависит от настройки схемы.
- **Независимое сравнение:** визуал из трёх колонок «создание / обновление / ответ» с направлением стрелок: `TaskCreate` — `title, priority`; `TaskUpdate` — `title, priority, is_done`; `TaskRead` — `id, title, priority, is_done`. Под каждой — кто назначает `id`, почему `is_done` при POST назначает сервер и почему `tags` не видны в публичном ответе. Не показывать полный готовый код `TaskUpdate` для переписывания.
- **Первое самостоятельное действие:** ученик составляет таблицу для трёх форм и самостоятельно записывает Pydantic-модель обновления в тренировочном фрагменте с названиями полей, правилами и **без default**. Затем пробует создать модель в Python с полным набором и с пропущенным `is_done`; в Python наблюдает ошибку валидации, а будущий HTTP 422 появится только после подключения handler. Также сравнивает `is_done=False` и отсутствие аргумента, объясняет отличие.
- **Опора для возврата:** форма `TaskUpdate` — три поля, все обязательные; `title` trim → 1–120, `priority` 1–5, `is_done` bool; `id` из path, `tags` внутри Planner; при неполной схеме искать default/Optional и ошибку переноса правил `TaskCreate`.
- **Переход:** готовая схема отделяет проверку тела от выбора задачи по адресу.

## 03. Адрес и тело в PUT-маршруте

- **Что и зачем объяснить:** клиент обращается к **конкретному адресу** `PUT /tasks/{task_id}`, а тело содержит значения `TaskUpdate`. Это два разных источника данных. `task_id` сообщает, **какую** запись заменить; `title`, `priority`, `is_done` сообщают, **чем** заменить редактируемую часть.
- **Механизм и порядок:** в знакомом item-route повторить форму `task_id: Annotated[int, Path(gt=0)]` и `Request`, с которым сервис берётся из `request.app.state.planner` (из маршрутов блока 10). Входная модель — тип параметра тела; FastAPI разбирает JSON и проверяет path/body **до входа в обработчик**, и только потом исполняет код handler. Показать последовательность «разобрать JSON → проверить id/body → вызвать handler» и объяснить, что id не должен записываться из JSON.
- **Наглядная опора № 2:** номер ячейки хранения определяет, **куда** положить новый заполненный бланк, а сам бланк описывает **что** положить. Номер ячейки не переписывают содержимым бланка. Граница аналогии: реальная проверка существования Task происходит в сервисе, а номер без ячейки не создаёт её автоматически.
- **Первое самостоятельное действие:** на независимых карточках запросов ученик подчёркивает path-id и body-поля и предсказывает, дойдёт ли вызов до handler: id `0` с полным телом → ошибка проверки пути; положительный id с отсутствующим `priority` → ошибка проверки тела; корректная форма с неизвестным положительным id → до handler дойдёт, но сервис сообщит об отсутствии. Объяснить, почему все эти запросы не должны изменить JSON; 404 для последнего появится только после поиска.
- **Опора для возврата:** таблица «path-id → положительный int; body → три обязательных поля; проверка формата → 422 до handler; поиск отсутствующего id → 404 позже». Синтаксис `Annotated`/`Path` возвращать к его конкретной подготовке в BLOCK_10, а не вводить как новый язык Python.
- **Переход:** после двух входных проверок маршрут может передать уже валидированные поля прикладному сервису.

## 04. Делегирование готовому replace_task

- **Что и зачем объяснить:** маршрут принимает уже проверенные значения, вызывает знакомый `PlannerService.replace_task` и возвращает результат. Именно сервис, а не HTTP handler, ищет запись и сохраняет **целую Task** через прежнее хранилище. Это сохраняет общий источник для CLI и API.
- **Механизм и порядок:** взять ранее подключённый Planner из `Request`; разобрать **фактическую сигнатуру** service operation из занятия 53 и передать `task_id`, `title`, `priority`, `is_done` явными аргументами. До HTTP-правки сверить сервисную пробу: он переносит старые `id`/`tags`, валидирует доменную модель до save и сообщает `TaskNotFoundError` при отсутствии задачи. Объяснить существующий узкий helper обработки этой ошибки как HTTP 404, не глушить `StorageError` широким `except`.
- **Независимый разбор:** в отдельной схеме «контролёр формы / диспетчер / мастер по хранению» распределить обязанности: схема обнаруживает пропуск, handler выбирает операцию, сервис проверяет существование и сохраняет. Показывать **границы**, не подсовывать целиком готовый PUT handler как ответ к практике. Различающий случай: при ошибке записи сервиса нельзя объявлять «задача не найдена» или успешный 200.
- **Первое самостоятельное действие:** по перемешанным операциям ученик восстанавливает порядок вызовов и отмечает, на какой границе возможны 422, 404 и ошибка хранения. Затем сам подключает вызов готового `replace_task` в собственном маршруте, не реализуя сервис повторно; локально проверяет успешный путь по ответу, после чего проверяет сохранение отдельным чтением.
- **Опора для возврата:** «request state → прежний Planner → replace_task(id, три значения) → save → результат; только TaskNotFoundError превращается в 404». Если сигнатура фактического метода отличается от паспортной, согласовать с результатом 53 **до** задания, а не писать параллельную операцию.
- **Переход:** сервис возвращает полную доменную Task; внешний ответ должен сохранить установленную публичную форму.

## 05. Ответ, статусы и доказательство результата

- **Что и зачем объяснить:** успешный PUT возвращает HTTP 200 и `response_model=TaskRead`: четыре публичных поля `id/title/priority/is_done`. Это формат HTTP-ответа, **не перезапись доменной Task**; `tags` остаются в JSON/CLI. Сам статус 200 не доказывает, что запись пережила новую загрузку.
- **Механизм и порядок:** различать причины в фиксированном порядке. Отсутствующее `is_done`, очищенный пустой `title` или `priority=6` → Pydantic/FastAPI отказывает 422 до service, состояние не меняется. Полный допустимый body с положительным, но отсутствующим id → сервис сообщает «не найдено», helper отдаёт 404 без создания. Полный допустимый body для существующей Task → `replace_task` сохраняет и отдаёт 200 с `TaskRead`; после этого необходим новый GET и чтение файла. Уточнить отдельно: JSON `false` — **переданное** значение для обязательного bool, а не пустое поле.
- **Независимое сопоставление:** ученику предложить три коротких протокола «запрос → HTTP-статус → был ли вызван сервис? → изменился ли JSON?», один с неполным body, один с отсутствующим id, один успешный. Визуал подсвечивает разные места остановки, затем словами связывает их с правилами схемы и поиска.
- **Первое самостоятельное действие:** ученик предсказывает статус и границу отказа для каждого протокола, выбирает *разные доказательства* для результата (HTTP ответ для формы, GET/CLI/JSON для факта сохранения) и объясняет, почему 404 не должен означать создание записи.
- **Опора для возврата:** «422 — некорректный path/body до handler; 404 — id допустим, задачи нет; 200 — найдена и сохранена, затем подтвердить повторным чтением». При сомнении в сохранении сравнить `id`, все три поля и `tags` до/после в настоящем JSON, не требовать `tags` в `TaskRead`.
- **Переход:** теперь можно выполнить полный самостоятельный путь от схемы до проверяемого результата.

## 06. Что мы будем делать в практике

**Формат:** `manual`, обязательная проектная практика **в том же Planner**. Ученик сам редактирует существующие `schemas.py` и `api.py`, отправляет запросы через уже освоенный Postman/Swagger и сверяет данные через CLI и фактический `data/tasks.json` (уточнить путь из входного проекта). Готового тела `TaskUpdate` или PUT-handler в стартовой заготовке нет. Не создавать отдельную демонстрационную базу, сервис, in-memory-список, второй JSON или новую копию CRUD.

**Общий результат:** один работающий `PUT /tasks/{task_id}` для существующей Task: три поля заменены, `id` и `tags` сохранены, верный ответ — 200 с `TaskRead`, отсутствующий id — 404, неверная форма — 422 без записи. Каждый пункт ниже — вход → объект → опора → действие ученика → локально видимый результат; проверка последнего пункта собирает B.

Самостоятельно: повторить позитивную и негативную сервисную пробу `replace_task` до редактирования API, не подменяя её чтением красивой страницы документации; затем зафиксировать **новый исходный снимок для PUT**, вернув `is_done=True` при необходимости. **Локально:** замена в сервисе уже работает, id/tags и соседняя запись остаются неизменными, неизвестный id не добавляется; при провале восстановить A из 53 до следующего шага.

Если регистрация/входная схема не совпадают, вернуться к § 02–04 до отправки запросов.
4. **Доказать успешную полную замену одним различающим запросом.** Вход: фактический положительный id учебной записи из шага 1, где `is_done=True`; объект: `PUT /tasks/{id}` в Postman/Swagger. **Проверка переноса (короткая, без второго проекта):** дать ученику уже готовое описание запроса с `is_done=false`, но без `title`. Он без исполнения объясняет, почему никакой PUT-замены не будет, хотя `false` допустимо, и какой один недостающий элемент делает форму полной.
