## Место в маршруте

После частичного обновления Task в [плане 54.2](<54.2 - PATCH и сохранённый ответ.md>) ученик подключает к тому же Planner последнюю HTTP-операцию CRUD. Удаление уже умеет выполнять `PlannerService`; занятие добавляет только HTTP-границу и проверяет, что пустой ответ следует за сохранённым действием. Следующий шаг — [план 55.1 «Проверка общего ядра»](<55.1 - Проверка общего ядра.md>): он добавляет прямые регрессионные проверки ядра и не повторяет HTTP-практику DELETE. ## Точка A: планируемая опора, которую нужно подтвердить

- **Учебная A, планируется:** занятие 48.1 планирует разобрать числовой `task_id` в пути, различить отсутствующий ID (`404`) и неразбираемое значение (`422`); занятие 54.2 готовит подключение `PATCH` к Planner. Эти паспорта показывают, где опора должна быть объяснена и применена. Они не подтверждают, что ученик уже прошёл занятия.
- **Проектная A, планируется и проверяется перед практикой:** по паспорту к началу 55 сервис `PlannerService` уже удаляет Task через `delete_task`, CLI и HTTP API используют общий Planner/JSON, а API имеет прежние маршруты. Сам HTTP `DELETE` ещё предстоит добавить. Текущее состояние проекта отдельным snapshot здесь не подтверждено.
- **Условие начала проектной части:** до редактирования проверить фактические `delete_task`, общий источник данных, CLI и нужные маршруты. Если что-то отсутствует, записать конкретный пробел и остановить только зависящие от него действия. Не объявлять планируемую опору освоенной и не восстанавливать в этом уроке предыдущие сервисы или маршруты.

## Точка B: результат занятия

- **Ученик объяснит:** почему Task выбирают по ID; чем отличаются `204` без тела, `404` для отсутствующего ресурса, `422` для неподходящего значения пути и сбой хранилища.
- **Ученик самостоятельно сделает:** добавит в `app/api.py` HTTP `DELETE`, который передаёт ID существующему `delete_task` через текущий Planner и возвращает пустой `Response` со статусом `204` только после успешного удаления.
- **Изменение проекта:** одна выбранная Task удаляется через общий `PlannerService`; CLI, JSON и остальные маршруты сохраняют прежнее поведение.
- **Наблюдаемое подтверждение:** Postman показывает `204` и пустой `content`; затем `GET` и повторный `DELETE` того же фактического ID дают `404`; чтение после перезапуска подтверждает отсутствие этой Task и сохранность соседних данных.

## Границы и передача дальше

- Пока не требуем: повторную реализацию удаления или прямой доступ handler к JSON; новый helper; новую схему, service-метод или `response_model` для DELETE; TestClient, fixture и APIRouter; полный цикл POST→PUT→PATCH→DELETE. Положительная граница path и узкая обработка отсутствия уже введены раньше. Полный жизненный цикл относится к 59.1.
- Передаём следующему занятию: готовый HTTP DELETE с пустым 204, сохранённым удалением и раздельными исходами 422/404/storage. Паспорт 55.1 проверяет ядро и отсутствие частичного эффекта. Эта передача сверена с готовым планом 55.1 и его паспортом: там добавляются только прямые сервисные регрессии, без повтора HTTP-практики DELETE.

## 00. Вступление

В Planner уже есть операция `delete_task`: она удаляет задачу из общего хранилища. В этом занятии мы подключим её к HTTP API. Сначала проверим, что нужные прежние части действительно доступны в учебном проекте; только потом будем менять маршрут.

1. **Точка старта:** по плану курса ранее подготовлены положительный `task_id`, обработка отсутствующей задачи и `PATCH`; сервис `PlannerService` должен уже уметь удалять Task. Это планируемая опора, а не подтверждение фактического прохождения или состояния установленного проекта.
2. **Новый вопрос:** как сообщить клиенту «удалено», если самой задачи в ответе уже нет, и как отличить успех от неверного адреса, отсутствующей задачи и сбоя хранилища?
3. **Результат:** маршрут `DELETE` вызывает существующий сервис, возвращает `204 No Content` без тела после успешного сохранения, а чтение после перезапуска подтверждает отсутствие удалённой Task.

Порядок такой: сначала определяем объект и слой, затем разбираем ответы, после этого проверяем настоящее удаление. Если входной проект не содержит ожидаемого сервиса или прежних маршрутов, зависимую практику останавливаем и фиксируем, чего не хватает; не реализуем эти части заново в уроке 55.

## 01. Выбираем задачу по её ID и поручаем удаление сервису

- **Что и зачем объяснить:** `DELETE` удаляет один ресурс. В нашем API ресурс — Task, а `task_id` указывает, какую именно задачу выбрать. ID — устойчивый адрес записи; номер строки в списке может измениться после удаления другой записи.
- **Механизм и порядок:** запрос приходит на item-path с ID → FastAPI передаёт его обработчику маршрута → обработчик вызывает `delete_task` у уже созданного `PlannerService` → сервис удаляет Task и сохраняет общий Planner. Сервис отвечает за изменение данных; HTTP-маршрут — за перевод запроса и результата в HTTP.
- **Пример и типичная путаница:** в каталоге библиотека удаляет книгу по инвентарному номеру. Если удалить «третью строку», сортировка изменит цель; если передать номер книги готовому сервису, цель остаётся той же. Аналогично, обработчик не должен сам искать индекс или открывать JSON.
- **Первое самостоятельное применение:** по схеме «запрос → маршрут → сервис → хранилище» для отмены бронирования отметить, какой слой выбирает HTTP-ответ, а какой меняет бронь. Результат: ученик не помещает работу с данными в HTTP-обработчик.
- **Опора для повторного обращения:** при реализации назвать фактический ID и проследить один вызов от item-path до готового сервиса; проверить, что соседняя Task не выбрана.
- **Переход:** действие выполняет правильный слой. Теперь нужно различить причины, по которым запрос может не завершиться успехом.

## 02. Отличаем неверный адрес, отсутствие Task и сбой данных

- **Что и зачем объяснить:** похожие неуспешные запросы означают разное. `422` — путь не прошёл проверку; `404` — путь корректен, но Task с таким ID нет; ошибка хранилища — приложение не смогло прочитать или сохранить данные. Последняя не означает «не найдено» и не должна маскироваться как успех.
- **Механизм и порядок:** `Path(gt=0)` проверяет, что ID в пути — положительное целое, до вызова маршрута. Здесь `gt` означает «больше»: `0` и отрицательное число не проходят проверку; текст вместо числа тоже не доходит до обработчика. Для корректного положительного, но неизвестного ID сервис выдаёт `TaskNotFoundError`; существующий `_call_with_task_not_found_as_404` переводит именно эту ошибку в `404`. Ошибки `JsonStorage` этот helper не перехватывает. Не добавляем общий `except Exception`: он смешал бы разные причины.
- **Независимый пример:** для адреса книги `abc` отклоняется сам формат; для номера `42`, которого нет в каталоге, запрос понятен, но объект отсутствует; отказ диска означает проблему приложения. В Planner это соответственно неверный ID, отсутствующий `task_id` и сбой JSON-хранилища.
- **Первое самостоятельное применение:** сопоставить эти три исхода с этапом, где они возникают, и назвать ожидаемый результат. Ученик различает проверку пути, поиск ресурса и работу хранилища, не придумывая новый обработчик ошибок.
- **Опора для повторного обращения:** сверять значение ID, факт наличия Task и место ошибки; проверять, что перевод в `404` ограничен `TaskNotFoundError`.
- **Переход:** мы знаем, как выглядят отказы. Осталось определить, что получает клиент при успешном удалении.

## 03. Возвращаем `204 No Content` без JSON-тела

- **Что и зачем объяснить:** после удаления отдавать копию Task бессмысленно: клиент просит удалить её, а не получить представление. `204 No Content` означает успешное действие без тела ответа. Пустое тело — это не `{}` и не JSON-значение `null`.
- **Механизм и порядок:** маршрут объявляет статус `204`, вызывает сервис, и только после успешного возврата отдаёт пустой `Response`. Для него не нужна `response_model`. В Postman проверяют статус и пустое содержимое; JSON-разбор не вызывают. Если сервис или сохранение завершились ошибкой, успешный ответ не формируется.
- **Независимый пример и путаница:** при отмене бронирования клиенту может быть достаточно подтверждения без копии брони. Статус `200` часто несёт представление, а `204` — нет. Нельзя считать `{}`, `null` или вызов `.json()` эквивалентом пустого ответа.
- **Первое самостоятельное применение:** для удаления книги выбрать, нужно ли вернуть саму книгу. Наблюдаемый результат: выбран ответ без тела, и проверка читает статус и содержимое, а не пытается декодировать JSON.
- **Опора для повторного обращения:** отдельно проверять `status_code == 204` и пустой `content`; это доказывает HTTP-ответ, но не постоянное удаление.
- **Переход:** внешний ответ определён; теперь отдельно проверим сохранённое состояние.

## 04. Доказываем изменение новым чтением

- **Что и зачем объяснить:** HTTP-ответ описывает конкретный запрос. Новое чтение Planner показывает, что осталось в хранилище. Нужны оба наблюдения: пустой `204` сам по себе не доказывает, что удаление пережило перезапуск.
- **Механизм и порядок:** обработчик вызывает сервис → сервис сохраняет список без выбранной Task → маршрут возвращает `204` → после перезапуска API или CLI читает то же общее хранилище. При сбое сохранения нельзя сообщать об успешном удалении.
- **Независимый пример:** после удаления книги библиотекарь получает подтверждение, затем заново открывает каталог. Подтверждение показывает исход запроса; обновлённый каталог — текущее состояние. Одно не заменяет другое.
- **Первое самостоятельное применение:** упорядочить эти два наблюдения и объяснить, что каждое подтверждает. Для Planner ученик фиксирует ID и соседнюю запись до операции, а после перезапуска проверяет отсутствие первой и сохранность второй.
- **Опора для повторного обращения:** сравнивать фактические ID, число записей, данные соседней Task и её `tags` до и после; читать состояние после перезапуска, а не только ответ маршрута.
- **Переход:** повторное чтение подтверждает результат. Проверим, как API отвечает на следующий запрос к уже удалённому ID.

## 05. Проверяем отсутствие и не допускаем подмену ID

- **Что и зачем объяснить:** первый `DELETE` существующей Task завершается `204`. После него `GET` и повторный `DELETE` того же отсутствующего ID дают `404`. Это не отменяет успех первого запроса: второй запрос проверяет уже другое состояние.
- **Механизм и порядок:** сначала удалить Task и сохранить её фактический ID → проверить `GET` → повторить `DELETE` → только после обеих проверок создавать следующую запись. Если генератор выдаёт ID на основе текущих данных, новая Task может получить удалённый максимальный номер и сделать проверку неоднозначной.
- **Независимый пример и путаница:** удалили книгу №42 — первый запрос успешен; затем поиск №42 и повторное удаление сообщают, что её нет. Нельзя заключать, что первый запрос провалился, только потому что второй вернул `404`.
- **Первое самостоятельное применение:** предсказать ответы для существующего ID, того же ID после удаления и неверного формата пути. Результат: `204`, затем `404`/`404`, а неверный путь отдельно даёт `422`.
- **Опора для повторного обращения:** использовать ID из ответа на создание, не вычислять его из длины списка; не создавать записи между проверками отсутствия.
- **Переход:** порядок запросов и ожидаемые ответы ясны. Теперь можно выполнить ограниченную ручную практику.

## 06. Что мы будем делать в практике

**Формат и исходная опора:** manual в основном Planner-проекте с существующей Postman collection. Рабочие данные не очищаем. Паспорт планирует готовые CLI, общий JSON, `delete_task`, положительный path и прежние HTTP-маршруты; до изменения ученик проверяет их фактическое наличие. Новые сервис, схема и хранилище в этой практике не создаются.

Практика добавляет только HTTP `DELETE`. Создание отдельной учебной Task через уже работающий `POST` нужно для безопасного получения её фактического ID; это не полный сценарий `POST → PUT → PATCH → DELETE`.

1. **Проверим вход и сохраним исходное состояние.** Убедиться по текущему проекту, что API и CLI обращаются к одному Planner, а сервис уже умеет удалить Task. В Postman или CLI записать все текущие ID, общую статистику и поля одной соседней записи, включая `tags`. Если обязательная опора отсутствует, остановиться до изменения `app/api.py` и передать точный недостающий вход. Иначе создать одну отдельную открытую Task готовым `POST` и записать ID из ответа. **Результат:** известны исходные данные и однозначный объект для удаления; существующие данные не очищены.
2. **Подключим HTTP-маршрут.** В `app/api.py` добавить только `DELETE` для item-path; передать `task_id` готовому Planner из `request.app.state.planner`, использовать существующую узкую обработку `TaskNotFoundError`, а после успешного `delete_task` вернуть пустой `Response` со статусом `204`. Опора: шаги 01–03 и ранее подготовленный маршрут 48.1. **Результат:** изменена HTTP-граница, сервис и JSON не переписаны.
3. **Проверим HTTP-контракт и различающие ответы.** Отправить `DELETE` для созданной Task. Проверить `204` и пустой `content`, не запускать JSON-разбор. До любого нового `POST` выполнить `GET` и повторный `DELETE` по тому же ID; оба должны показать `404`. Отдельно проверить неверный формат и неположительное значение пути (`422`), а в коде убедиться, что helper не поглощает `StorageError`. **Результат:** успех, отсутствие и неверный путь различены; ошибки хранилища не превращены в `404` или успех.
4. **Подтвердим сохранение и отсутствие побочных изменений.** Перезапустить приложение и проверить тот же ID через API и CLI. Сверить полный набор ID и статистику с исходными данными; количество Task должно вернуться к исходному, созданная для проверки запись отсутствует, выбранная соседняя запись и её `tags` не изменились. **Результат:** эффект пережил перезапуск, а посторонние записи сохранены.

Шаг 1 проверяет планируемые предпосылки и готовит безопасный контрольный объект. Шаг 2 меняет только требуемый маршрут. Шаги 3 и 4 независимо доказывают HTTP-контракт и состояние хранилища. Сбой входной опоры блокирует только зависимую проектную практику; его нельзя заменять повторной реализацией прежних занятий. Полная CRUD-матрица и прямые сервисные регрессии остаются для 55.1/59.1 по паспорту.
