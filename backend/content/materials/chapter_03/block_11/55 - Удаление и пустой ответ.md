## Место в маршруте

После частичного обновления Task в [плане 54.2](<54.2 - PATCH и сохранённый ответ.md>) ученик подключает к тому же Planner последнюю HTTP-операцию CRUD. Удаление уже умеет выполнять `PlannerService`; занятие добавляет только HTTP-границу и проверяет, что пустой ответ следует за сохранённым действием. Следующий шаг — [план 55.1 «Проверка общего ядра»](<55.1 - Проверка общего ядра.md>): он добавляет прямые регрессионные проверки ядра и не повторяет HTTP-практику DELETE. Полный сквозной сценарий остаётся в 59.1.

## Точка A: подтверждённая опора

- Уже изучено: по новому маршруту занятие 48.1 объясняет положительный `task_id`, `Path(gt=0)`, `Annotated` и перевод ожидаемого `TaskNotFoundError` в 404. Занятие 54.2 подключает `TaskPatch` и готовый `patch_task` к существующему API. Это предпосылки курса, а не доказательство фактического прохождения учеником новой версии.
- Состояние проекта: по паспорту перед 55 в `app/api.py` уже работают HTTP-чтение, создание, PUT и PATCH через `app.state.planner`; в `PlannerService` уже есть `delete_task`, используемый прежним CLI. Один `JsonStorage` хранит общий Planner. HTTP DELETE ещё не подключён.
- Планируемая опора или неясность: точный snapshot проекта после исторического занятия 45 не найден в доступных refs; COURSE прямо оставляет A открытой до подтверждения. Старые материалы 61/62 подтверждают содержание прежней версии, но не подтверждают прохождение новой последовательности. План исходит из входного контракта COURSE и паспортов 48.1/54.2. Перед запуском зависимой практики нужно сверить реальный проект с их ожидаемым состоянием; если `delete_task`, общий JSON или предыдущие маршруты отсутствуют, не маскировать пробел и не дописывать их в этом занятии.

## Точка B: результат занятия

- Ученик сможет объяснить: почему DELETE выбирает Task по устойчивому ID; чем отличаются 204 без тела, 404 при корректном отсутствии, 422 при неверном path и ошибка хранилища.
- Ученик сможет сделать: добавить в `app/api.py` HTTP DELETE, который вызывает готовый `delete_task` через уже созданный `_call_with_task_not_found_as_404` и возвращает пустой `Response` со статусом 204 только после успеха.
- Результат в проекте: существующая Task удаляется через общий `PlannerService`; JSON, CLI и другие маршруты продолжают работать.
- Как подтвердим: проверим 204 и пустое содержимое, затем отсутствие того же фактического ID после нового чтения, ответы на повторные запросы, сохранность прежних записей и статистики.

## Границы и передача дальше

- Пока не требуем: повторную реализацию удаления или прямой доступ handler к JSON; новый helper; новую схему, service-метод или `response_model` для DELETE; TestClient, fixture и APIRouter; полный цикл POST→PUT→PATCH→DELETE. Положительная граница path и узкая обработка отсутствия уже введены раньше. Полный жизненный цикл относится к 59.1.
- Передаём следующему занятию: готовый HTTP DELETE с пустым 204, сохранённым удалением и раздельными исходами 422/404/storage. Паспорт 55.1 проверяет ядро и отсутствие частичного эффекта. Эта передача сверена с готовым планом 55.1 и его паспортом: там добавляются только прямые сервисные регрессии, без повтора HTTP-практики DELETE.

## 00. Вступление

После PUT и PATCH мы умеем менять состояние задачи, не создавая второй Planner. Теперь нужно убрать одну существующую Task так, чтобы клиент получил ясный ответ, а соседние записи остались нетронутыми. В CLI удаление уже выполняется через сервис; новый вопрос — как подключить его к HTTP и доказать сохранение результата.

1. **Точка старта:** API уже читает и меняет Task, а `PlannerService` умеет найти и удалить её по ID.
2. **Новый вопрос:** как сообщить об успешном удалении, если возвращать удалённую модель не нужно, и как отличить его от отсутствующей записи или сбоя JSON?
3. **Результат:** HTTP-маршрут делегирует действие готовому сервису, отдаёт пустой 204 и подтверждает удаление повторным чтением.

Пункты задают путь от знакомого сервиса к новому внешнему контракту. Сначала выбираем правильный объект и слой, затем разбираем причины отказа и форму ответа, после чего связываем HTTP-результат с постоянным состоянием проекта.

## 01. Удаляем ресурс по ID через готовый Planner

- Что и зачем объяснить: DELETE относится к существующей Task, адресованной её ID, а не к строке или позиции в текущем списке. Сортировка и удаление соседей меняют позиции, но не идентичность Task.
- Механизм и порядок: FastAPI получает `task_id` из item-path; handler передаёт работу существующему `PlannerService.delete_task`; сервис выполняет предметное удаление и сохранение через общий storage. Handler не ищет и не удаляет элемент сам, не открывает JSON и не создаёт параллельное состояние.
- Пример и типичная путаница: на независимом примере каталога сравнить удаление книги по инвентарному номеру с удалением «третьей строки». Показать, почему путь к записи в API не превращается в индекс списка и почему HTTP handler не заменяет сервис.
- Первое самостоятельное действие: после объяснения дать готовую схему слоёв для другого ресурса и попросить определить, какая готовая операция должна выполнить удаление и какая часть отвечает за HTTP-ответ. Результат — ученик выбирает предметный сервис и не переносит работу с хранилищем в handler.
- Опора для повторного обращения: при добавлении маршрута восстановить цепочку «item ID → существующий PlannerService → сохранённый список» и проверить, что соседние записи не входят в объект удаления.
- Переход к следующему шагу: действие делегировано, но внешнее сообщение и ожидаемое отсутствие ещё нужно сформировать.

## 02. Различаем неверный путь, отсутствие и сбой хранилища

- Что и зачем объяснить: 422, 404 и StorageError описывают разные этапы. Клиент должен понимать, был ли адрес непригоден для вызова, корректный ресурс отсутствовал или приложение не смогло работать с данными.
- Механизм и порядок: ранее объяснённый `Path(gt=0)` отклоняет текстовый, нулевой и отрицательный ID до handler. Корректный положительный, но неизвестный ID вызывает `TaskNotFoundError`, который уже знакомый `_call_with_task_not_found_as_404` переводит в 404. Ошибки `JsonStorage` не перехватываются этим helper и не становятся ни 404, ни успехом.
- Пример и типичная путаница: сравнить некорректный адрес, корректный адрес отсутствующей Task и отказ чтения/сохранения файла. Не использовать общий `except Exception`: он стирает причину ошибки и может ложно подтвердить удаление.
- Первое самостоятельное действие: по нескольким готовым исходам определить, сработал ли разбор path, сервисный поиск или хранилище, и выбрать уже изученный ответ для каждого случая. Результат — верно различены 422, 404 и серверный сбой; новый способ обработки исключений не вводится.
- Опора для повторного обращения: при проверке DELETE сопоставлять формат ID, наличие записи и результат операции; проверять, что `_call_with_task_not_found_as_404` ловит только `TaskNotFoundError`.
- Переход к следующему шагу: успешный возврат сервиса ещё не объясняет, должно ли HTTP-сообщение содержать удалённую Task.

## 03. Возвращаем пустой Response со статусом 204

- Что и зачем объяснить: после удаления клиенту не требуется копия исчезнувшей Task. `204 No Content` фиксирует успех без представления и тела. Это не пустой JSON-объект `{}` и не JSON-значение `null`.
- Механизм и порядок: маршрут объявляет статус 204 и после успешного вызова сервиса возвращает пустой `Response`. Для операции не задаётся `response_model`; при 204 клиент проверяет статус и пустое содержимое, но не вызывает JSON-разбор. Сопоставить с ответом 200, который может нести публичное представление.
- Пример и типичная путаница: взять независимое действие отмены бронирования и решить, нужно ли клиенту тело с объектом брони. Не смешивать успешное выполнение операции с доказательством записи на диск: это разные проверки.
- Первое самостоятельное действие: для готовых исходов выбрать ответ с представлением или без него и объяснить, что должен читать клиент после 204. Результат — ученик выбирает отсутствие тела и не ожидает `TaskRead`, `null` или успешный `json()`.
- Опора для повторного обращения: у успешного DELETE сверять отдельно `status` и `content`; наличие 204 не заменяет GET для чтения нового состояния.
- Переход к следующему шагу: форма ответа определена; теперь нужно показать, что он отправляется только после успешного изменения постоянного состояния.

## 04. Связываем ответ с сохранённым состоянием

- Что и зачем объяснить: HTTP-ответ показывает исход запроса, а новое чтение того же источника — состояние Planner после действия. Для уверенной проверки нужны оба наблюдения.
- Механизм и порядок: запрос доходит до handler, handler вызывает `delete_task`, сервис сохраняет оставшиеся данные, и только затем маршрут возвращает 204. Если сохранение не удалось, успешный ответ не отправляется. API и CLI используют прежний настроенный JSON; handler не добавляет свою файловую операцию.
- Пример и типичная путаница: сравнить пустой 204 с новым `GET` той же Task и свежим чтением через CLI или новым экземпляром сервиса. Не считать пустое тело доказательством персистентности и не считать неизменность списка доказательством самого HTTP-контракта.
- Первое самостоятельное действие: после объяснения расположить наблюдения для одного удаления в правильном порядке и назвать, какой результат подтверждает HTTP, а какой — сохранённое состояние. Результат — проверка различает внешнее сообщение и новый load.
- Опора для повторного обращения: при проверке сохранить реальные исходные ID, значения статистики и данные хотя бы одной прежней записи; сравнить их после нового чтения.
- Переход к следующему шагу: новая загрузка подтверждает результат, но повторный DELETE может вернуть другой статус при том же конечном отсутствии.

## 05. Проверяем повторное обращение и границу ID

- Что и зачем объяснить: первый DELETE существующей Task завершается 204; GET и повторный DELETE этого же отсутствующего ID отвечают 404. Эффект остаётся достигнутым, хотя статус описывает уже другой запрос.
- Механизм и порядок: после удаления не создавать другую Task до проверок отсутствия. Генерация ID может повторно выдать удалённый максимальный номер; тогда новый объект с тем же числом сделает проверку старого ID двусмысленной. Считать статистику по всему Planner, а не по ограниченной выборке.
- Пример и типичная путаница: проследить фактический ID созданной для проверки записи через первый DELETE, GET и повторный DELETE; отдельно указать, что «404 после удаления» не означает, что первый DELETE не сохранился.
- Первое самостоятельное действие: предсказать последовательность ответов для существующего, затем отсутствующего ресурса и для следующего POST, если он сделан слишком рано. Результат — ученик понимает, почему сначала выполняются все проверки отсутствия, а после можно продолжить работу.
- Опора для повторного обращения: не подменять фактический ID длиной списка или заранее выбранным числом; в проверки отсутствия не вставлять новый POST.
- Переход к практике: известны действие, точная форма успеха, границы отказов и способ подтвердить результат без полного повторения предыдущего CRUD.

## 06. Что мы будем делать в практике

**Формат и исходная опора:** manual в основном Planner-проекте; начинаем с уже работающих CLI, POST, GET и stats, общего JSON и существующей Postman collection. Рабочие данные не очищаем.

Практика добавит только HTTP DELETE. Подготовительные запросы нужны, чтобы получить фактический ID отдельной записи для удаления; полный сценарий POST→PUT→PATCH→DELETE здесь не проводится.

1. **Подготовим контрольное состояние:** с опорой на прежние навыки CLI/API, POST, GET и stats, через CLI или готовый API запишем текущие реальные ID, общую статистику и данные прежних записей; создадим отдельную открытую Task существующим POST и возьмём ID из ответа. Критерий: есть проверяемый объект удаления и исходное состояние, без предположений о номерах.
2. **Подключим DELETE:** в `app/api.py` добавим маршрут для item-path, с опорой на блоки 01–03 и 48.1 используем `request.app.state.planner`, существующий `_call_with_task_not_found_as_404` и `delete_task`; применим знакомый положительный path и пустой `Response` 204. Критерий: удаление подготовленной Task возвращает 204 с пустым `content`; ответ не разбирается как JSON.
3. **Различим исходы:** с опорой на блоки 02 и 05 до нового POST проверим GET и повторный DELETE по удалённому фактическому ID, а также неверный формат и неположительный path. Критерий: существующая запись удалена, повторное отсутствие даёт 404, неверный path — 422; по коду ранее созданного helper сверим, что в 404 переводится только `TaskNotFoundError`, а `StorageError` им не перехватывается.
4. **Подтвердим сохранение и регрессию:** с опорой на блок 04 и прежние навыки чтения через CLI после перезапуска проверим тот же ID через API и CLI, сравним stats с начальным состоянием и убедимся, что прежние записи и их `tags` не изменились. Критерий: удалённая Task отсутствует в JSON, соседние данные сохранены, а ранее работавшие чтение и stats отвечают по-прежнему.

Блоки 01–03 готовят делегирование, границы ошибки и пустую форму ответа. Блоки 04–05 задают порядок проверки сохранения и повторного запроса. Ученик сам добавляет маршрут и выбирает наблюдения после обращения к опорам; практика не даёт готового endpoint и не повторяет прикладную реализацию. Итог подтверждён только при одновременном выполнении HTTP-контракта и сохранённом результате. Между проверками отсутствия не создаётся новая Task; полная проверка цепочки операций остаётся для 59.1.
