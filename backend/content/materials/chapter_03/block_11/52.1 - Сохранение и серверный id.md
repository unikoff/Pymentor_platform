## 00. Вступление

По плану предыдущих занятий POST уже вызывает существующий Planner. Представим: API вернул `201`, а после нового запуска CLI задачу найти не удалось. Ученик должен выяснить, где мог разойтись путь данных; реальный проект перед практикой проверяем по точке A, не предполагаем готовность по одному плану.

1. **Точка старта:** из 50.1 и 52 планируются POST, две HTTP-схемы и общие PlannerService/JsonStorage; их наличие мы сначала подтвердим в checkout ученика.
2. **Новый вопрос:** как отличить красивый ответ сервера от данных, записанных в файл, и проверить, кто выбрал `id`?
3. **Результат:** проследить создание, проверить server-owned поля и прочитать две новые Task через GET и CLI после перезапуска; при пробеле в тестах подтвердить правило `id` изолированно.

Сначала различим вход, доменную запись и ответ, затем предскажем id и найдём точку `save`. После этого сравним сильное доказательство сохранения с недостаточным и проведём проверку через два интерфейса. В MAIN три пункта оформляются одной связанной группой с этим пояснением после неё.

## 01. От HTTP-входа до сохранённой Task

- Что и зачем объяснить: входной `TaskCreate` принимает клиентские `title`/`priority`, доменная `Task` содержит также серверные `id`/`is_done` и `tags`, а `TaskRead` ограничивает успешный ответ четырьмя публичными полями `id`, `title`, `priority`, `is_done`. Это три формы одних данных на **разных этапах**, а не три хранилища. Сначала восстановить разницу из 52, а не заново учить JSON.
- Механизм и порядок: для независимого запроса `{"title":"Отправить письмо","priority":3}` маршрут валидирует тело через `TaskCreate` → передаёт данные `PlannerService.add_task` → сервис формирует полную `Task` и вызывает `JsonStorage.save` → только после успешной операции маршрут отдаёт `TaskRead` и HTTP `201`. `response_model` определяет **видимые поля ответа**, а не содержимое дискового JSON и не момент сохранения. Конкретный объект и вызов найти в коде ученика, не подменять реализацию готовым вымышленным фрагментом.
- Независимая наглядная опора: «анкета → запись в журнале → квитанция»: квитанция может показывать меньше полей, чем журнал, но **сам журнал** меняется только при отдельной операции записи. Предел аналогии: в программе мы проверяем реальный вызов `save`, а не доверяем бумажной квитанции. Схема для MAIN — стрелки с меткой места записи и полями каждой формы; не смешивать `TaskRead` и сериализованную `Task`.
- Путаница и различающий случай: в файле у старой Task `tags=["важно"]`, а GET отдаёт только четыре поля. Это **нормально**: отсутствие `tags` в HTTP не означает их исчезновения из сохранённого объекта. Если же после создания полный JSON потерял прежние `tags`, это дефект сохранения; 201 сам по себе его не исключает.
- Первое самостоятельное действие: без готовой схемы ученик расставляет пять этапов (приём тела, проверка схемы, построение Task, save, формирование ответа), отмечает единственную точку записи и предсказывает, где впервые могут появиться `id` и `is_done`. Проверяет порядок по функциям своего проекта; критерий — `TaskRead` не «сохраняет» и `201` возможен только после успешного возврата сервиса.
- Опора для возврата: «HTTP-тело → `TaskCreate` → `add_task` → полная `Task`/`JsonStorage.save` → `TaskRead`/201»; `tags` проверяются в JSON/доменной Task, а не в публичном ответе. Переход: теперь разберём выбор серверных полей до записи.

## 02. Сервер назначает id по текущим записям

- Что и зачем объяснить: `id` — номер **записи**, который назначает сервис; `is_done=False` — начальное состояние новой задачи. Клиент выбирает `title` и `priority`, но не эти два поля. `id` нужен для последующего GET по известному номеру, поэтому при ручной проверке его обязательно **получают из ответа**, а не угадывают.
- Механизм и порядок: на независимых данных с текущими `id` 4 и 12 сервис использует `max(текущих id) + 1` и выдаёт 13; `len(записей) + 1` ошибочно дал бы 3. После удаления наибольшего id из текущего множества то же правило может использовать удалённый номер вновь: гарантируется выбор следующего относительно **нынешних**, а не всех исторических записей.
- Независимый пример/наглядность: на полке стоят папки с ярлыками № 4 и № 12. Третьей назначают № 13, даже если папок всего две. Предел аналогии: бумажный архив сам не выдаёт номер; в коде конкретный `PlannerService` вычисляет его по данным storage. В MAIN показать бок о бок две формулы и разные результаты, а не просто два одинаковых вопроса «кто задаёт id?».
- Различающий случай: если клиент добавил к телу `"id":999` и `"is_done":true`, они **не становятся** серверными значениями. В предусмотренной на текущем шаге конфигурации `TaskCreate` дополнительные поля игнорируются; отсутствие отдельного запрета `extra` не позволяет обещать 422. Реальное поведение сверяем с вынесенной в 52 схемой и тем, что вызов сервиса использует только `title`/`priority`.
- Первое самостоятельное действие: ученик для набора 4 и 12 предсказывает 13 и `False`, объясняет ошибку варианта 3, затем на новом **другом** наборе после удаления максимума прогнозирует возможное повторное использование номера. Результат: правило связано с текущим состоянием, клиентский `id` отделён от серверного. Позже тест использует набор 2 и 7, чтобы прогноз не был скопирован из теории.
- Опора для возврата: «прочитай текущие id → максимум + 1 → `is_done=False` → полная Task → save»; GET ищет задачу по **фактическому** id. Переход: проверим выполнение этого правила на существующем сервисе и отдельном экземпляре чтения.

## 03. Новый сервис проверяет постоянный файл

- Что и зачем объяснить: старый объект Python может держать данные в памяти. Поэтому чтение «сразу после добавления в том же сервисе» слабее, чем создание **нового** `JsonStorage` и **нового** `PlannerService`, которые открывают тот же путь к JSON. `tmp_path` из знакомого pytest — временная директория **тестового** файла, не рабочий каталог пользователя.
- Механизм и порядок: если в имеющихся сервисных тестах нет эквивалентного доказательства, создать в `tests/test_services.py` один прямой тест. Через реальный `JsonStorage` во временном пути подготовить **полные** Task с id 2 и 7 и различимыми `tags`, вызвать настоящий `PlannerService.add_task`, затем открыть **этот же путь** другим `JsonStorage`/`PlannerService` и прочитать три объекта. Ожидаются `id=8`, `is_done=False`, сохранённые `title`/`priority` новой Task и неизменные старые `id`/`tags`. Если test 59 уже эквивалентен и остаётся актуальным, объяснить его достаточность и не создавать копию.
- Независимая наглядная опора: две отдельные тетради-«читателя» используют один общий шкаф-файл. Чтобы второй увидел изменения, первый обязан положить запись в шкаф (`save`); второй экземпляр не наследует память первого. Предел: это объясняет **последовательное** чтение после записи, не защиту от параллельного изменения файла. В MAIN визуализировать два объекта, направленных к **одному пути**, не к одному объекту `JsonStorage` в памяти.
- Типичная ошибка и различающий случай: новый `PlannerService` с **тем же старым объектом storage** слабее, чем новое хранилище по тому же пути. Проверка только новой задачи слабее: ошибочная перезапись файла могла удалить обе старые Task или их `tags`. Если `id` вычисляют повторным кодом прямо в тесте, мы не тестируем настоящий сервис.
- Первое самостоятельное действие: ученик выбирает между проверкой старым сервисом, новым сервисом со старым storage и новой парой service/storage с тем же путём; объясняет, какая действительно исключает случай «сохранили только в памяти». Затем предсказывает id 8 и набор полей трёх записей **до запуска** теста; критерий — тест выявляет как потерю новой, так и старых записей.
- Опора для возврата: `tmp_path` → подготовленные полные Task → старый service.add_task → **новые** JsonStorage/PlannerService с тем же путём → сравнение всех записей и tags. Переход: даже корректный тест сохранения не должен скрывать повреждённый файл как пустое состояние.

## 04. StorageError не означает пустое состояние

- Что и зачем объяснить: «задачи с данным id нет» и «файл нельзя прочитать» — **разные причины**. Нет файла при первом старте (до первой записи) тоже отличается от повреждённого файла. Для новичка это три состояния, у которых разные ожидаемые последствия.
- Механизм и порядок: поиск отсутствующего id после корректного чтения приводит к `TaskNotFoundError` (HTTP item ранее сопоставляли с 404); отсутствие ещё не созданного файла обрабатывается предусмотренным storage как пустое начальное состояние; некорректный JSON или сбой чтения/записи — `StorageError`. Нельзя молча заменить повреждённый файл пустым списком, выдать за 404/422 или создать вместо прежнего JSON новый: так можно уничтожить данные. Не обещать конкретный HTTP-код для `StorageError`, пока не проверено сопоставление ошибок в API.
- Независимый различающий случай: «папка ещё не заведена» — допустимое начало; «в папке нет задачи №5» — успешное чтение с неудачным поиском; «папка разорвана и прочесть записи нельзя» — ошибка хранения. Аналогия поясняет причины, но фактическое отличие задают реализации `load` и сервиса. В MAIN — короткая развилка по наблюдаемой причине и реакции, без повторного quiz о 201.
- Первое самостоятельное действие: по трём описаниям ученик выбирает ожидаемый тип состояния и **проверку**, которая это доказывает в имеющемся `tests/test_persistence.py`: отсутствующий файл, неизвестный id без изменения JSON и malformed JSON без перезаписи. Критерий — при сбое чтения тест не считает хранилище пустым и файл остаётся нетронутым.
- Опора для возврата: «нет файла при первом старте → пустой старт; нет id в читаемом файле → `TaskNotFoundError`; файл нечитаем → `StorageError`». Переход: теперь докажем, что настоящие API и CLI по очереди работают с тем же файлом, а не только с тестовым `tmp_path`.

## 05. API и CLI читают один путь последовательно

- Что и зачем объяснить: API и CLI запускаются по отдельности и создают собственные объекты. Общим состоянием для них служит **настроенный одинаковый путь** к одному JSON. Проверяем путь в `build_service`/настройках запуска, не предполагаем автоматически, что два процесса прочитали один файл.
- Механизм и порядок: **до** запросов записать текущий перечень задач и их id через CLI и путь к JSON; после остановки CLI выполнить два последовательных POST к API, сохранить **фактический id каждого ответа**, получить обе Task через GET, остановить/перезапустить API, заново запустить CLI с тем же путем и сверить исходные + новые записи и исходные `tags` по полному JSON. `201` подтверждает только ответ обработки запроса; чтение новым процессом — отдельное наблюдение.
- Независимый пример: две программы работают с папкой по разным путям — обе могут успешно создавать записи, но в разных файлах. Даже одинаковое имя файла не означает одинаковый **полный путь**. Схема для MAIN — две стрелки `API → файл ← CLI`, затем вариант с двумя разными файлами и диагностикой, без повторной карточки «да/нет».
- Типичная путаница и различающий случай: для живого файла нельзя ожидать абсолютные id 8 или 13 — там уже могут быть другие задачи. В одном HTTP-теле клиент может предложить произвольный `id` и `is_done=True`, но сравниваем их с **фактическим ответом**, где должны быть серверные значения; четыре поля `TaskRead` не включают `tags`, полную сохранность проверяем отдельно. Различение неверного пути и неверного id: GET по **ответному** id и CLI по тому же пути должны находить запись.
- Первое самостоятельное действие: ученик набрасывает последовательность «сначала снимок и путь → два POST и фактические id → GET → перезапуск → CLI/JSON», выбирает, где фиксировать доказательства и как отличить несохранённую Task от открытия другого файла. Критерий — по каждому id есть след и после перезапуска, исходные записи и tags присутствуют, а не только 201.
- Опора для возврата: «один абсолютный путь; один за другим; id из реального ответа; GET; новый запуск CLI; сравнить старое и новое». Граница: это проверка **последовательных** операций, не доказательство параллельной безопасности. Переход к практике: маршрут объяснён, ученик сам соберёт доказательство без переписывания сохранения.

## 06. Что мы будем делать в практике

**Формат и вход:** ручная проектная практика в существующем Planner, без CODE_TASKS. До работы сверяем фактическую B из 49/50.1/52: есть `tests/test_services.py`, маршруты POST/GET, `TaskCreate`/`TaskRead`, `PlannerService.add_task`, `JsonStorage` и CLI. При отсутствии этих компонентов восстанавливаем соответствующий предыдущий урок; не конструируем новые сервис, хранилище или API внутри 52.1. Самостоятельная часть здесь — диагностика, точечный сервисный тест **при пробеле** и проверка общего состояния реальными запросами.

1. **Обозначим путь сохранения (раздел 01).** Вход: готовые `app/api.py`/`app/schemas.py`, сервис и storage после 52; объект — существующий POST и цепь вызовов. Ученик **сам** отмечает, где появляются серверные поля и где вызывается `save`, затем отделяет полную доменную Task от четырёх полей `TaskRead`. 2. **Установим, нужна ли новая проверка сервиса (разделы 02–03).** Вход: имеющиеся тесты 49 и исторический тест 59, если он есть в текущем checkout; объект — только `tests/test_services.py` и **временный** `JsonStorage(tmp_path)`. Ученик **сам** сопоставляет проверяемые факты с покрытиями. Различающий сбой: сохранение только в памяти или перезапись файла теряет хотя бы одну проверку. 4. **Создадим две задачи и проверим реальные ответы (разделы 01–02 и 05).** Вход: работающие API/CLI **с одним заранее сверенным путём**, исходный список задач/id и их `tags`, сохранённый до запросов; объект — действующий POST и GET. Ученик **сам** отправляет **два последовательных POST** с различающимися названиями. В одном дополнительно предлагает `id`, заведомо не равный следующему ожидаемому номеру, и `is_done=true`; в стандартной схеме 52 дополнительные поля игнорируются, поэтому проверяет реальный контракт, не объявляя их причиной 422. 5. **Проверим новое чтение и сохранность соседей (разделы 03 и 05).** Вход: зафиксированный исходный список и фактические id шага 4; объект — тот же JSON, новый запуск API/CLI и полные Task. Локальный результат: оба новых id снова доступны, старые записи не исчезли и не поменяли `tags`. Шаг 1 даёт карту вызовов, шаги 2–3 используют её для проверки прямого сервисного контракта и уже существующих гарантий файла, шаги 4–5 переносят вывод на реальные API и CLI.
