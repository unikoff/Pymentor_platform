## 00. Вступление

POST уже проходит через API к существующему Planner. Успешный ответ сообщает, что операция завершилась, но сам по себе не показывает, что сохранено в общем файле и что прочитает другой экземпляр приложения.

1. **Точка старта:** API и CLI используют существующий PlannerService; add_task создаёт Task и работает через JsonStorage.
2. **Новый вопрос:** как проверить, что id назначен сервером, а новая запись действительно пережила прежний объект или процесс?
3. **Результат:** проследить создание, проверить правило id изолированным тестом и увидеть те же задачи через API и CLI после перезапуска.

Сначала восстановим уже готовую цепочку слоёв, затем разберём серверные значения и выберем доказательства для памяти процесса и постоянного файла. Практика не добавляет новую бизнес-логику: она усиливает уверенность в существующем Planner.

## 01. От HTTP-входа до сохранённой Task

- Что и зачем объяснить: TaskCreate описывает допустимые поля клиента, доменная Task — полную запись Planner, а TaskRead — публичный ответ. Эти формы связаны, но выполняют разные обязанности.
- Механизм и порядок: API принимает проверенные title/priority и передаёт их существующему add_task; сервис формирует Task, JsonStorage сохраняет полный объект; после успешного вызова API формирует TaskRead и возвращает 201. Сохранение выполняет сервис через storage, а не response_model.
- Пример и типичная путаница: коротко восстановить аналогию «форма запроса → запись в реестре → квитанция»: TaskCreate задаёт поля клиента, полный JSON хранит Task, TaskRead показывает публичную часть. Граница: ни форма, ни квитанция сами не сохраняют данные. TaskRead не содержит tags, но это не повод записывать в JSON сокращённый HTTP-ответ.
- Первое самостоятельное действие: по готовой структуре API назвать, какой слой принимает вход, назначает поля, пишет файл и ограничивает ответ. Наблюдаемый результат — каждый шаг отнесён к правильному компоненту, а 201 стоит после успешного сохранения.
- Опора для повторного обращения: краткая цепочка «TaskCreate → add_task → Task → JsonStorage → TaskRead/201»; характерная ошибка — считать схему ответа механизмом записи.
- Переход к следующему шагу: после определения границы сохранения можно проверить, кто назначает идентификатор и начальный статус.

## 02. Сервер назначает id по текущим записям

- Что и зачем объяснить: значение id зависит от существующих идентификаторов, а не от количества записей. Клиент передаёт title/priority; id и начальный is_done=False принадлежат сервису.
- Механизм и порядок: на независимом примере с id 4 и 12 показать, что следующий id равен 13, а не числу записей плюс один. Объяснить, что при удалении текущего максимума правило max(текущих id)+1 может выдать его снова: вечную уникальность истории не обещаем.
- Пример и типичная путаница: использовать аналогию с метками занятых ячеек архива: следующий номер зависит от самой большой метки, а не от количества ячеек; после удаления верхней метки она может появиться снова. Сравнить «максимальный id плюс один» с «число записей плюс один» на независимых данных. Отдельно разобрать запрос, в котором клиент прислал свои id и is_done: они не должны управлять серверными полями. При стандартной конфигурации B лишние поля игнорируются; не объявлять их автоматически ошибкой 422.
- Первое самостоятельное действие: по независимому примеру назвать следующий id и объяснить, почему подсчёт записей неверен. Затем назвать ожидаемый is_done, даже если клиент предложил True. Результат — правило объяснено до применения к тестовому набору 2 и 7.
- Опора для повторного обращения: «сначала фактические id → максимум → следующий номер»; отдельно восстановить серверные значения и проверить политику лишних полей в TaskCreate.
- Переход к следующему шагу: правило нужно проверить не на копии алгоритма, а вызовом существующего сервиса.

## 03. Новый сервис проверяет постоянный файл

- Что и зачем объяснить: повторное чтение тем же объектом слабее проверки новым PlannerService: прежний объект может сохранить состояние в памяти, даже если файл не обновлён.
- Механизм и порядок: тест в tests/test_services.py использует JsonStorage(tmp_path), готовые Task и PlannerService. Он подготавливает две записи с id 2 и 7, вызывает существующий add_task, затем создаёт новый сервис с тем же путём. Тест сравнивает новую запись и соседние данные, включая tags.
- Пример и типичная путаница: объяснить сохранение через аналогию с записью в тетрадь: новый сервис открывает тот же путь и восстанавливает данные из файла, а не получает память старого объекта. Граница: это подтверждает последовательное сохранение после успешной записи, но не безопасность одновременных писателей. Это прямой тест слоя сервиса, поэтому TestClient, Uvicorn и второй алгоритм id здесь не нужны. Фиксированные id допустимы в изолированном временном файле; их нельзя переносить на пользовательский JSON.
- Первое самостоятельное действие: определить, какие факты отличают проверку нового сервиса от повторного чтения старым: id 8, is_done=False, восстановление трёх записей, tags прежних Task. Результат — проверка ловит запись только в памяти и потерю соседних данных.
- Опора для повторного обращения: где задаётся tmp_path, какой готовый сервис вызывается, какой же путь передаётся новому сервису и какие поля полного объекта сравниваются.
- Переход к следующему шагу: знакомые гарантии persistence следует повторно запустить, а не копировать в новый тестовый модуль.

## 04. StorageError не означает пустое состояние

- Что и зачем объяснить: отсутствие одной Task, пустой или ещё не созданный файл и невозможность прочитать повреждённое хранилище — разные состояния.
- Механизм и порядок: TaskNotFoundError относится к отсутствующему id после чтения; StorageError сообщает, что данные не удалось прочитать или сохранить. Нельзя превращать ошибку чтения в пустой список, 404 или успешное создание: это скроет состояние файла и может привести к потере данных.
- Пример и типичная путаница: использовать уже существующий tests/test_persistence.py как источник доказательств: восстановление после нового сервиса, пустой отсутствующий файл до первой записи, неизвестный id без изменения JSON и malformed JSON без перезаписи. Не добавлять копии этих сценариев в tests/test_services.py.
- Первое самостоятельное действие: соотнести каждую готовую проверку с гарантией, которую она подтверждает, и отделить её от нового теста id. Результат — существующие границы переиспользованы, новая проверка отвечает только на пробел о max+1 и новом сервисе.
- Опора для повторного обращения: три причины — нет записи, файла ещё нет, файл нечитаем; характерная ошибка — скрыть StorageError под пустым результатом.
- Переход к следующему шагу: изолированный тест доказывает сервис и файл; теперь проверим передачу состояния между реальными интерфейсами.

## 05. API и CLI читают один путь последовательно

- Что и зачем объяснить: API и CLI могут создавать разные объекты и работать в отдельных процессах. Для общего состояния им нужен один настроенный путь JsonStorage, а не общий объект Python.
- Механизм и порядок: проследить build_service и настройки запуска; после успешного POST сервис завершает сохранение, API возвращает фактический id, GET читает задачу, а CLI после перезапуска открывает тот же файл. Не считать один ответ 201 доказательством доступности данных новому процессу.
- Пример и типичная путаница: реальные id зависят от данных ученика, поэтому брать их из ответов и не требовать фиксированных номеров в рабочем JSON. Сценарий последовательный; он не доказывает координацию одновременных писателей.
- Первое самостоятельное действие: по фактическим ответам двух POST сверить GET по полученным id и CLI после перезапуска. Результат — обе новые задачи и прежние записи доступны, клиентские id/is_done не заменили серверные значения.
- Опора для повторного обращения: «ответ POST → фактический id → GET → остановка/новый запуск → CLI»; для теста состояния использовать изолированный tmp_path, для ручной проверки — существующий рабочий файл без очистки.
- Переход к практике: после различения проектной проверки и изолированного теста ученик сможет дополнить только недостающие доказательства.

## 06. Что мы будем делать в практике

**Формат и исходная опора:** ручная проектная практика. Начинаем с существующих TaskCreate/TaskRead, POST, GET, PlannerService.add_task, JsonStorage и CLI; код создания и хранения уже работает.

1. **Проследим готовое создание:** найдём передачу title/priority из API в add_task и точку сохранения JsonStorage. Ученик самостоятельно называет роли схемы, сервиса, полной Task и ответа; результат — объяснена цепочка и порядок перед 201.
2. **Проверим прямой тест сервиса:** в стандартном новом маршруте дополним `tests/test_services.py`, созданный в занятии 49, проверкой `add_task` на записях с id 2 и 7 и перечитаем тем же путём новым `PlannerService`. Результат — id 8, `is_done=False`, обе соседние Task и их tags сохранены. У текущего ученика эквивалентный тест уже пройден в старом занятии 59: сначала сверим его имеющееся покрытие, затем добавим только отсутствующую гарантию, если она действительно появилась после переноса кода.
3. **Переиспользуем файловые гарантии:** запустим новый тест вместе с нужными существующими проверками tests/test_persistence.py. Не создаём повторные проверки пустого источника, restart, неизвестного id или повреждённого JSON; результат — новый тест дополняет, а не дублирует покрытие.
4. **Проверим реальный путь API и CLI:** в стандартном маршруте до запросов зафиксируем состояние и текущие id полным списком CLI, затем отправим два POST с различимыми title. В одном запросе предложим id, отличный от ожидаемого следующего номера, и `is_done=True`; возьмём фактические id из ответов и проверим четыре поля `TaskRead`, прочитаем задачи через GET, убедимся, что полные записи и `tags` сохранились, перезапустим API и проверим их через CLI. Для текущего ученика такой сценарий уже пройден в старом занятии 59, поэтому после шага 52 повторим только проверку, затронутую переносом схем, взяв прежний результат за исходное доказательство. Результат нового маршрута — новые задачи видны обоим интерфейсам, серверные поля назначены сервисом, прежние записи сохранены.

Первые три действия опираются на готовые компоненты и проверяют их по отдельности; последнее соединяет API, файл и CLI на реальных данных. Для этого ученика подобный сквозной сценарий уже выполнен в прежнем занятии 59: после переноса схем в занятии 52 повторяем только проверки, затронутые этим изменением, и называем их регрессией, а не новым результатом обучения. Для рабочего файла не задаём ожидаемый абсолютный id и не удаляем записи для удобства проверки. Автотесты работают только с `tmp_path`.

**Итоговый критерий всей практики:** прямой тест отличает максимум id от количества записей и подтверждает повторную загрузку полной Task новым сервисом; ручной сценарий подтверждает фактические серверные поля и последовательную видимость двух POST через API и CLI после перезапуска. Хранилище, старые операции и JSON-формат не переписаны.
