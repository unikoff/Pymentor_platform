## 00. Вступление

Начать с известного пути сохранения: сервис читает актуальный список через storage, выполняет действие и сохраняет успешное новое состояние. Теперь нужно определить, как заменить редактируемую часть одной существующей Task так, чтобы не создать дубликат и не стереть данные, которыми клиент управлять не может.

1. **Точка старта:** PlannerService, Task, _find_task, JsonStorage и прямые проверки сохранения уже существуют в целевом маршруте после 52.1.
2. **Новый вопрос:** как заменить title, priority и is_done у найденной Task, сохранив её идентичность, внутренние tags и соседние записи?
3. **Результат:** один сервисный replace_task строит допустимое новое состояние до сохранения, а прямые тесты подтверждают эффект и границы отказа.

Сначала объяснить смысл полного набора редактируемых полей и постоянной идентичности, затем пройти путь операции внутри PlannerService, после этого разобрать порядок проверки и сохранения и завершить прямой проверкой сервиса. HTTP здесь не добавляет поведение и появится только после готового предметного метода.

## 01. Полная замена как предметное действие

- Что и зачем объяснить: полная замена означает передачу всех полей, которыми разрешено управлять, а не создание новой записи и не переписывание всей доменной Task. Сопоставить её с частичным изменением только на уровне намерения; алгоритм PATCH подробно не вводить.
- Механизм и порядок: запрос будущего клиента идентифицирует одну Task по task_id; операция заменяет title, priority и is_done. id задаёт идентичность записи, а tags остаются внутренними данными, не входящими в эту редактируемую форму.
- Пример и типичная путаница: на карточке существующей задачи сравнить замену её названия/приоритета/статуса с созданием новой карточки. Полный набор полей формы не означает замену id или tags.
- Первое самостоятельное действие: по нескольким описаниям определить, какие значения должны измениться, а какие должны сохраниться. Результат — явный перечень полей операции до обсуждения кода.
- Переход к следующему шагу: определить, как сервис находит именно эту запись и получает актуальное состояние.

## 02. Найти запись в существующем PlannerService

- Что и зачем объяснить: сервис отвечает за предметное изменение, а JsonStorage — за актуальную загрузку и сохранение списка. Повторно не вводить структуру проекта и не переносить работу с JSON в API.
- Механизм и порядок: получить актуальный список через storage.load(), найти задачу существующим _find_task и опираться на проверенное поведение TaskNotFoundError. Отличить валидный, но отсутствующий id от ошибки чтения хранилища: последняя остаётся StorageError и не превращается в отсутствие задачи.
- Пример и типичная путаница: одинаковый id-путь приводит либо к найденной записи, либо к TaskNotFoundError; повреждённый JSON означает отказ хранилища, а не пустой список и не неизвестную задачу.
- Первое самостоятельное действие: проследить входы и результат для найденного и отсутствующего id по готовым границам сервиса. Критерий — ученик может назвать, где завершается поиск и какая ошибка передаётся вызывающему коду.
- Опора для повторного обращения: роль load и _find_task; результат поиска — существующая Task; TaskNotFoundError означает отсутствие; StorageError означает сбой чтения.
- Переход к следующему шагу: имея найденную Task, построить проверенную замену, не меняя исходную запись заранее.

## 03. Построить новую проверенную Task

- Что и зачем объяснить: доменная модель продолжает защищать свои инварианты. Новые title, priority и is_done нельзя сначала записать в существующее состояние, а проверить потом.
- Механизм и порядок: из найденной записи и полного набора новых значений подготовить новый объект Task; перенести исходный id и отдельную копию tags; перед дальнейшей заменой дать конструктору Task проверить новые поля. Сравнить это с изменением исходного объекта на месте: если создание новой Task не удалось, список ещё не должен содержать частичную замену.
- Пример и типичная путаница: изменить доступные поля карточки, оставив номер и закрытые отметки. Различить данные, присланные для замены, и поля, которые должны быть перенесены из исходной записи.
- Первое самостоятельное действие: для валидного набора и набора, нарушающего известное правило Task, предсказать, будет ли получена новая версия. Критерий — допустимая запись сохраняет id/tags; недопустимая не подменяет старую.
- Опора для повторного обращения: состав новой Task, поля-источники для id/tags, инварианты конструктора и ожидаемая ошибка до сохранения.
- Переход к следующему шагу: после успешной проверки новой Task сервис может заменить ровно один элемент и сохранить список.

## 04. Сначала подготовить состояние, затем сохранить

- Что и зачем объяснить: граница изменения и сохранения должна быть ясна. Одна успешная полная замена проходит через одно сохранение после поиска и построения допустимой Task.
- Механизм и порядок: в актуальном списке заменить элемент с найденной идентичностью, затем передать обновлённый список storage.save(); вернуть новую Task вызывающему коду. Не добавлять запись при отсутствии id и не сохранять список до успешной проверки новой модели.
- Пример и типичная путаница: на отдельной карточке библиотечной выдачи пройти путь от найденной записи до результата: заменить срок и статус, сохранить инвентарный номер и внутреннюю заметку, проверить новую карточку и только затем записать её. Сравнить последовательность «изменить старую Task — проверить — записать» с «построить валидную Task — заменить элемент — сохранить»; в первом варианте ошибка проверки может оставить частичное состояние. Это объяснительный пример, не код и не задание по Planner.
- Первое самостоятельное действие: расположить поиск, построение Task, замену элемента и save в безопасном порядке для успеха, неизвестного id и ошибки валидации. Критерий — только успешный валидный вариант достигает обновлённого сохранённого состояния.
- Опора для повторного обращения: операция начинается с актуального load; одна запись заменяется на месте по идентичности; save следует после построения валидной Task. Ошибка StorageError не обещает файловый rollback.
- Переход к следующему шагу: сформулированный контракт можно независимо проверить на настоящем сервисе и изолированном файле.

## 05. Прямые проверки сервисной границы

- Что и зачем объяснить: тест должен проверять PlannerService напрямую, поскольку новый метод живёт в сервисе. Это доказательство не заменяется HTTP-вызовом и не требует TestClient.
- Механизм и порядок: использовать JsonStorage на tmp_path и явные тестовые данные; вызвать replace_task, проверить возвращённую Task, затем перечитать тот же путь новым сервисом. Отдельно проверить сохранение id/tags, неизменность соседней записи, отказ для отсутствующего id и недопустимую замену без изменения прежнего состояния.
- Пример и типичная путаница: непрерывные и разреженные id не меняют идентичность найденной записи; нельзя путать новый объект результата с новой записью в списке.
- Первое самостоятельное действие: выбрать проверки, отличающие корректную замену от случайного добавления или перезаписи всех задач. Критерий — набор наблюдений покрывает все заменяемые поля, сохранённые поля, соседа и чтение новым экземпляром.
- Опора для повторного обращения: сервисный тест задаёт изолированное хранилище; успешный результат сравнивается после нового load; отказ сравнивается с прежним полным состоянием. Тесты не используют пользовательский JSON.
- Переход к практике: тесты закрепляют новую операцию без повторной реализации add/list/get/delete и без HTTP-обвязки.

## 06. Что мы будем делать в практике

**Формат и исходная опора:** manual; начинаем с целевого состояния после 52.1 — существующих Task, PlannerService, JsonStorage, _find_task и сервисных тестов. Тестовые данные создаются только в JsonStorage(tmp_path). В текущем журнале ученика историческое занятие 61 уже содержит эту операцию, поэтому перед применением плана как личной новой работы сначала требуется подтвердить точку A и сопоставление старого progress с новой картой.

Практика добавляет только полную замену в существующий PlannerService и доказывает, что она не ломает прежние возможности. Начинаем с понимания контракта и наблюдения за исходным/соседним объектом, затем самостоятельно меняем сервис и последовательно проверяем успех и отказы.

1. **Определить договор замены:** на исходном состоянии с целевой и соседней Task назвать три поля, которые меняются, и поля, которые обязаны сохраниться. Опора — разделы 01 и 03; ученик самостоятельно проводит границу редактируемых данных. Результат — критерий отличает замену существующей Task от создания новой.
2. **Добавить replace_task в PlannerService:** использовать существующий load и _find_task, построить допустимую новую Task до изменения списка, сохранить id и tags, заменить найденный элемент и сохранить успешное состояние. Опора — разделы 02–04; ученик самостоятельно выбирает порядок операции. Результат этого шага — метод возвращает новую Task и не содержит HTTP-логики.
3. **Проверить успешную замену:** прямым тестом с JsonStorage(tmp_path) изменить все разрешённые поля; после вызова перечитать файл новым сервисом и проверить id, tags и соседа. Опора — раздел 05; ученик сам выбирает наблюдения, отличающие обновление от дубликата. Результат — сохранённая Task соответствует новому набору полей, другие записи не изменились.
4. **Проверить границы отказа и прежнюю работу:** отдельно проверить корректный неизвестный id и данные, нарушающие правила Task; убедиться, что upsert не произошёл и прежнее состояние не получило частичного обновления. Запустить релевантные существующие сервисные и persistence-проверки, подтвердив, что создание, чтение и CLI продолжают пользоваться тем же Planner/JSON. Опора — разделы 02–05 и прежние тесты; критерий — причина отказа не маскируется и сохранённое состояние соответствует исходному.

Эти шаги подготавливают самостоятельную сервисную операцию, но не требуют преждевременно создавать TaskUpdate или PUT. Итог практики подтверждён, когда валидная полная замена сохраняется в том же JSON через новый экземпляр, id и tags цели остаются прежними, соседняя запись сохранена, а отсутствие или ошибка построения Task не создают частичное изменение. Следующему занятию передаётся готовая предметная операция; проверка HTTP-пути будет отдельным шагом.
