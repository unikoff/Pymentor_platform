## 00. Вступление

POST уже принимает данные через проверенную схему и сохраняет настоящую задачу. Но отправленные клиентом поля и поля успешного ответа не совпадают: часть данных назначает сервер, а полная внутренняя запись содержит данные, которые наружу не публикуются.

1. **Точка старта:** TaskCreate и настоящий POST с проверкой title и priority; GET уже умеет читать Planner.
2. **Новый вопрос:** как явно описать клиенту успешный ответ, не смешав его с входом, доменной моделью и JSON-файлом?
3. **Результат:** вынести HTTP-схемы в отдельный модуль и закрепить форму ответа через TaskRead и response_model.

Сначала ученик восстановит путь одной задачи через систему, затем различит роли входной и выходной схем. После этого перенесёт уже знакомую TaskCreate без изменения поведения, добавит форму публичного ответа и увидит её как в реальном API, так и в OpenAPI.

## 01. Одна задача проходит через несколько представлений

- Что и зачем объяснить: одна предметная задача отображается в request body, HTTP-схеме входа, доменной модели, полном JSON-хранилище и публичном ответе. Разделение нужно, чтобы изменение внешнего договора не переписывало предметную модель или формат данных CLI.
- Механизм и порядок: пройти цепочку от title и priority в запросе через PlannerService к Task и JsonStorage, затем к публичному представлению ответа. Для одной записи показать различие полной Task с tags и ответа API из четырёх полей.
- Пример и типичная путаница: взять одну задачу, например с id 7, и проследить, что клиент прислал, что назначил сервер и что сохранил Planner. Не называть словарь ответа полной доменной записью.
- Первое самостоятельное действие: распределить известные поля между запросом, Task, JSON и публичным ответом; ученик сам объясняет, почему id не присылается при создании и почему отсутствие tags в response не означает удаление из проекта.
- Опора для повторного обращения: рядом с практикой оставить краткую схему направлений «клиент → TaskCreate → Planner» и «Task → публичная проекция → TaskRead → клиент»; отдельно напомнить, что JSON содержит полную Task.
- Переход к следующему шагу: когда роли разделены, можно перенести существующую входную схему, не меняя её назначение.

## 02. TaskCreate остаётся схемой входа

- Что и зачем объяснить: TaskCreate уже описывает разрешённые данные создания, а не всю задачу. Её title и priority остаются клиентским вводом; id и начальное is_done назначает сервер. Правила очистки и ограничений пришли из предыдущего маршрута и не разрабатываются заново.
- Механизм и порядок: восстановить, что аннотация TaskCreate относится к request body, а response_model — к результату маршрута. Обычное поведение Pydantic по дополнительным полям сохраняется; один только лишний ключ не превращается в обещанную ошибку 422.
- Пример и типичная путаница: сравнить создание задачи и её последующее чтение. Не добавлять id или is_done в TaskCreate ради совпадения полей; не использовать одну универсальную модель для входа и выхода.
- Первое самостоятельное действие: до переноса ученик сам перечисляет поля TaskCreate и называет сохранённые проверки title/priority. Наблюдаемый результат — он может объяснить, какие части схемы нужно перенести без изменений.
- Опора для повторного обращения: напоминание о входе: title очищается до Field-проверки; допустимая длина чистой строки — 1–120, priority — 1–5; правила остаются в той же последовательности.
- Переход к следующему шагу: существующую форму можно разместить рядом с новой публичной схемой, не перенося туда бизнес-логику.

## 03. HTTP-схемы получают свой модуль

- Что и зачем объяснить: app/schemas.py становится местом моделей HTTP-границы, тогда как models.py остаётся доменной моделью, services.py — операциями Planner, storage.py — работой с JSON, а api.py — приложением и маршрутами.
- Механизм и порядок: объяснить перемещение класса между модулями и импорт по имени. Вынести TaskCreate целиком вместе с BaseModel, Field, before-validator и всеми текущими правилами; изменить только место определения и соответствующий импорт в api.py.
- Пример и типичная путаница: сравнить HTTP-схемы с Task в models.py. Создание schemas.py не означает новый проект или слой сервиса; оно не должно заставить services.py импортировать FastAPI.
- Первое самостоятельное действие: ученик переносит TaskCreate из api.py в app/schemas.py и обновляет импорт в API. Критерий — приложение по-прежнему принимает тот же POST, нормализует title и сохраняет прежние границы входа.
- Опора для повторного обращения: держать рядом карту ответственности модулей и короткое правило: schema описывает форму данных, service выполняет действие, storage сохраняет запись.
- Переход к следующему шагу: после переноса входа модуль получает вторую схему для обратного направления — успешного ответа.

## 04. TaskRead описывает публичный ответ

- Что и зачем объяснить: клиенту нужна стабильная форма уже созданной задачи, отличная от данных создания и от внутренней записи Planner.
- Механизм и порядок: в TaskRead входят id типа int, title типа str, priority типа int и is_done типа bool. id и is_done видны после создания, хотя клиент не назначает их при POST. tags остаётся частью Task и JSON, но не входит в публичный договор этого курса.
- Пример и типичная путаница: сопоставить TaskCreate и TaskRead по направлению. Не сводить их к одному TaskSchema с необязательным id и значением is_done по умолчанию: такая модель размывает ответственность клиента и сервера.
- Первое самостоятельное действие: ученик сам формулирует набор и типы полей TaskRead, используя существующие BaseModel и типы модели. Проверяемый результат — ровно четыре публичных поля, без tags.
- Опора для повторного обращения: при выборе схемы спрашивать, кто формирует данные и в какую сторону они проходят; если это ответ API, проверить, что видны серверные id и состояние, но нет внутреннего tags.
- Переход к следующему шагу: отдельная модель готова; теперь маршрут может объявить её договором успешного ответа.

## 05. response_model закрепляет форму ответа

- Что и зачем объяснить: response_model указывает FastAPI форму результата маршрута. Это выходной договор, не параметр body и не вызов сохранения.
- Механизм и порядок: разобрать на независимом примере статьи, как модель ответа задаёт успешную форму и описывается в OpenAPI; затем перенести идею на Task. Для GET коллекции ответ является списком TaskRead, для GET item и POST — одной TaskRead.
- Пример и типичная путаница: сравнить тип параметра POST с `response_model` того же маршрута. Первый проверяет вход; второй описывает успешный выход и публикует его форму в OpenAPI. Неподходящий успешный результат — ошибка на стороне сервера, а проверка ответа не откатывает уже выполненное сохранение.
- Первое самостоятельное действие: сначала подключить `TaskRead` к одному существующему item-маршруту и сравнить публичный JSON и запись `Task`; затем распространить тот же контракт на список и POST. Наблюдаемый результат — уже четырёхпольный ответ явно проверяется моделью, а прежние query, 404 и статус 201 POST сохранены.
- Опора для повторного обращения: у каждого маршрута восстановить пару «какая схема принимает данные — какая схема описывает успешный ответ» и ожидаемую форму результата: одна TaskRead или список.
- Переход к следующему шагу: код уже объявляет контракт; нужно отдельно проверить, что документация и настоящее сохранённое состояние ему соответствуют.

## 06. Документация и сохранённое состояние дают разные доказательства

- Что и зачем объяснить: OpenAPI показывает объявленную форму, реальный запрос показывает фактический ответ, а JSON и CLI — сохранность внутренней записи. Ни одно из этих свидетельств не заменяет остальные.
- Механизм и порядок: в /docs различить TaskCreate в request POST и TaskRead в успешном response; затем проверить GET списка, GET item и настоящий POST. Сопоставить публичные четыре поля с полной Task и tags в JSON/CLI.
- Пример и типичная путаница: `response_model` закрепляет и проверяет внешний договор, но не должна удалять `tags` из сохранённой записи или обходить сохранение через `PlannerService`.
- Первое самостоятельное действие: после POST ученик использует полученный фактический id для GET item и сверяет задачу в CLI или JSON после перезапуска. Критерий — API выдаёт четыре поля, а сохранённая запись и прежние возможности Planner остаются целыми.
- Опора для повторного обращения: при расхождении сначала назвать слой, который проверяется: OpenAPI — обещание; HTTP — выдача; JSON/CLI — внутреннее сохранение и совместимость.
- Переход к практике: все проверки относятся к уже объяснённым схемам и действующим маршрутам; новые сервисные операции и тестовая инфраструктура не нужны.

## 07. Что мы будем делать в практике

**Формат и исходная опора:** ручная практика в существующем StudyHub. Начинаем с состояния после целевого занятия 51.1: API читает задачи и создаёт их через проверенный TaskCreate; данные проходят через общий Planner и JSON.

1. **Перенести TaskCreate в app/schemas.py:** исходное состояние — проверенная схема находится рядом с маршрутами в app/api.py; опора — блоки 02–03 и прежние знания о BaseModel/валидаторе. Ученик сам переносит класс и меняет импорт, не переписывая правила. Результат — приложение запускается, прежний POST сохраняет успешный ответ и прежние границы входа.
2. **Добавить TaskRead:** исходное состояние — отдельного публичного ответа в модуле схем ещё нет; опора — блоки 01 и 04. Ученик сам выбирает четыре поля и их предметные типы. Результат — схема включает id, title, priority, is_done и не включает tags.
3. **Подключить response_model к трём готовым маршрутам:** исходное состояние — GET списка, GET item и POST уже работают; опора — блок 05. Ученик сам задаёт форму списка или одной записи, не создавая новый маршрут. Результат — GET возвращает прежний набор задач с публичной проекцией, GET item сохраняет поведение 404, POST сохраняет 201.
4. **Сверить документацию, HTTP и файл:** исходное состояние — схемы и маршруты уже связаны; опора — блок 06. Ученик сам проводит успешный POST, использует id из ответа для чтения и сопоставляет ответ с JSON/CLI и /docs. Результат — OpenAPI отражает направление моделей, API отдаёт четыре поля, а полная запись с tags и прежняя работа CLI сохранены.

Эти действия завершаются одной связной проверкой существующего Planner. Мы не меняем Task, services.py, storage.py или формат JSON; не создаём TaskUpdate, PUT/PATCH и отдельную тестовую инфраструктуру.

**Итоговый критерий практики:** TaskCreate по-прежнему проверяет вход, TaskRead явно задаёт успешный внешний ответ, GET списка/item и POST используют response_model, статус POST и поведение прежних операций сохранены. Одна и та же задача прослеживается от request до ответа и сохранённой записи без потери внутренних tags.
