## 00. Вступление

После полной замены задача уже может получить новое состояние через готовый сервис и PUT. Теперь нужно выразить более узкое намерение: поменять одно свойство, сохранив остальные и внутренние данные Planner.

1. **Точка старта:** полный `replace_task` проверяет и сохраняет новую Task; модель и сервис уже существуют.
2. **Новый вопрос:** как передать сервису только нужное изменение, не переписать поля, которые не менялись, и не потерять `False`?
3. **Результат:** самостоятельная сервисная операция строит проверенную версию задачи и сохраняет её только при действительном изменении.

Маршрут идёт от смысла выборочного изменения к значению аргументов, затем к построению новой Task, порядку записи и проверкам. Сначала изучается сервисный контракт; HTTP-форма будет добавлена позже.

## 01. Полная замена и выборочное изменение

- Что и зачем объяснить: после полной операции из 53 различить замену всей изменяемой формы и изменение одного или нескольких полей на уровне `PlannerService`. Не считать HTTP PATCH знакомой предпосылкой: он появится только после `TaskPatch` в 54.2.
- Механизм и порядок: после `replace_task` и полного PUT из планируемых B 53/53.1 сравнить полную замену с выборочной операцией сервиса: `replace_task` получает все редактируемые значения, `patch_task` — только заданные и сохраняет остальные значения найденной Task. HTTP PATCH появится позже и здесь не предполагается известным.
- Пример и типичная путаница: на независимой карточке настроек смена только названия оставляет приоритет и статус. Передача `False` — осмысленное отключение, а не отсутствие команды.
- Первое самостоятельное действие: для одной Task определить, какие поля изменятся и какие останутся; результатом служит явное разделение «новое значение / прежнее значение».
- Опора для повторного обращения: назначение аргументов `patch_task` и правило сохранения прежнего значения кратко указываются рядом с объяснением; точную HTTP-форму не планировать.
- Переход: различие операций требует разобрать значение каждого аргумента.

## 02. `None` не заменяет `False`

- Что и зачем объяснить: в сервисном договоре `None` означает «оставить прежнее», а любое допустимое не-`None` значение становится кандидатом на изменение. Для `is_done` явное `False` должно закрыть задачу, а не исчезнуть.
- Механизм и порядок: сначала отдельно рассмотреть `None`, `False` и обычное новое значение; затем показать, как проверка на отсутствие отличается от проверки истинности. Не вводить здесь nullable-поля Pydantic или `exclude_unset`.
- Пример и типичная путаница: при прежнем `is_done=True` значение `None` оставляет `True`, а `False` меняет состояние. Условие «если значение истинно» потеряет допустимый `False`.
- Первое самостоятельное действие: предсказать итог для `title=None` и `is_done=False`; наблюдаемый результат — только статус меняется во втором случае.
- Опора для повторного обращения: короткая таблица «аргумент / действие / ожидаемое состояние» для `None`, `False` и нового текста; рядом указать характерную ошибку проверки истинности.
- Переход: определив изменения, сервис должен безопасно применить их к настоящей Task.

## 03. Найти Task и подготовить новую версию

- Что и зачем объяснить: сервис владеет прикладным изменением; он не должен обновлять JSON напрямую из HTTP или повторять уже готовую логику маршрута.
- Механизм и порядок: загрузить актуальное состояние через прежнее хранилище, найти Task, выбрать для каждого поля старое или новое значение, создать проверенную новую Task и только после этого заменить запись.
- Пример и типичная путаница: частичное изменение `title` не должно сбрасывать `priority`, `is_done` или внутренние `tags`. Не путать выборочные поля клиента с полной доменной моделью.
- Первое самостоятельное действие: проследить, какое состояние новой Task получится после изменения только названия; результат включает прежние статус, id, tags и соседнюю запись.
- Опора для повторного обращения: перечислить источник прежних значений, допустимые изменяемые поля и сохраняемые поля; указать, что проверка новой Task происходит до `save`.
- Переход: безопасное построение состояния задаёт порядок сохранения.

## 04. Проверить до сохранения

- Что и зачем объяснить: ошибка валидации не должна оставлять частично изменённый файл. Существующая модель Task остаётся границей проверки.
- Механизм и порядок: подготовить все итоговые значения → создать и проверить новую Task → подменить элемент списка → сохранить один раз. Если проверка не проходит, исходное состояние остаётся прежним.
- Пример и типичная путаница: последовательное изменение полей исходного объекта перед проверкой может оставить часть изменений при сбое. Не мутировать сохранённую Task шаг за шагом.
- Первое самостоятельное действие: расставить подготовленные этапы операции в безопасном порядке; критерий — `save` возможен только после успешной проверки новой Task.
- Опора для повторного обращения: список этапов до записи и ожидаемое состояние при отказе; не добавлять транзакции, файловый rollback или новое хранилище.
- Переход: остаётся определить поведение операции, когда менять нечего или id неизвестен.

## 05. Пустое изменение и отсутствующая задача

- Что и зачем объяснить: пустой набор изменений и неизвестная Task — разные случаи. Сначала сервис обязан найти адресуемую запись.
- Механизм и порядок: сначала найти Task; если её нет — сохранить существующий `TaskNotFoundError`; если запись есть, применить допустимые значения; при пустом изменении вернуть её без вызова `save`.
- Пример и типичная путаница: пустое изменение для существующего id является no-op, но пустое изменение для отсутствующего id не скрывает ошибку поиска. Не превращать отсутствие в создание новой записи.
- Первое самостоятельное действие: сравнить эти два случая; результатом является no-op без записи для существующего id и `TaskNotFoundError` для отсутствующего.
- Опора для повторного обращения: порядок «поиск раньше no-op», ожидаемая ошибка сервиса и ранний возврат до записи. Не выдавать неизменившиеся байты файла за доказательство отсутствия вызова `save`; счётчик вызовов появится в 55.1.
- Переход: теперь можно проверить контракт без HTTP-клиента.

## 06. Прямые проверки сервисного контракта

- Что и зачем объяснить: тесты должны вызывать известный слой напрямую и работать на отдельном `JsonStorage(tmp_path)`. Временный файл изолирует проверку от пользовательских данных.
- Механизм и порядок: подготовить исходную Task и соседнюю запись; вызвать сервис; прочитать состояние новым экземпляром сервиса; сравнить no-op и отказные случаи с исходным состоянием.
- Пример и типичная путаница: неизменившийся JSON подтверждает отсутствие изменения данных, но сам по себе не доказывает, что `save` не вызывался. Здесь это подтверждают возврат до `save` в потоке сервиса и сравнение состояния; точный счётчик вызовов `save` оставлен последующей проверке общего ядра.
- Первое самостоятельное действие: выбрать различающие случаи для изменения одного поля, нескольких полей, перехода `True → False`, `None`, пустого изменения и отсутствующего id; результат — наблюдения покрывают запрошенные изменения, сохранённые поля и ошибки.
- Опора для повторного обращения: краткая матрица «вход сервисного метода / эффект / ожидаемая запись» и правило чтения результата новым сервисом. Счётчик вызовов `save` в этой практике не добавлять.
- Переход: успешные прямые тесты подтверждают B; HTTP-схема остаётся следующим отдельным шагом.

## 07. Что мы будем делать в практике

**Формат и вход:** manual; прямые проверки `PlannerService` на `JsonStorage(tmp_path)`, без доступа к рабочему JSON. Перед выдачей сверить фактическое прохождение B `53`/`53.1`, доступные файлы и способ запуска сервисных проверок именно в этой версии проекта. Текущий HEAD StudyHub позже планируемой точки A и не подтверждает её; фиксированный путь вроде `tests/test_services.py` не предполагать. Для ученика, ранее прошедшего старое занятие 61, это восстановление и перенос уже встречавшегося механизма, а не первое знакомство.

**Цель практики:** самостоятельно добавить либо, при подтверждённом прежнем прохождении, восстановить и проверить частичное изменение в существующем сервисе; доказать изменение только заданных полей, сохранность всей остальной Task и безопасный отказ без HTTP-слоя.

1. **Предсказать выборочное изменение.** **Вход:** две тестовые Task, подготовленные в `tmp_path` штатным для целевой версии способом; входная версия проекта после проверенной B `53`/`53.1`. Для примера целевая запись имеет `id=12`, `title="Черновик"`, `priority=2`, `is_done=True`, `tags=["курс"]`, соседняя — `id=35` и собственные значения. **Объект:** обе записи в тестовом JSON. **Опора:** `00`, `01`–`03` и конкретная B `53.1`; до выдачи проверить полный replace/PUT и доступность указанного состояния. **Самостоятельно:** для изменения только `title`, только `priority`, только `is_done=True → False` и совместного изменения `title` с `priority` заполнить «до → после», отметив неизменяемые поля. **Локальный результат:** прогноз меняет только переданные значения; `id`, `tags`, непереданные поля и соседняя Task остаются прежними.
2. **Добавить сервисную операцию.** **Вход:** та же проверенная версия `PlannerService`, в которой уже работает полный `replace_task`; изолированное хранилище и подготовленные записи. **Объект:** метод `patch_task` в существующем сервисе с допустимыми полями `title`, `priority`, `is_done`. **Опора:** `01`–`04` (различие операций, `None`/`False`, поиск и сбор новой Task, проверка до записи). **Самостоятельно:** выбрать и записать последовательность поиска, выбора прежних/новых значений, валидации и сохранения; не мутировать текущую Task по частям и не добавлять `TaskPatch`, HTTP-маршрут или второй storage. **Локальный результат:** сервисная операция принимает только разрешённые изменения; невалидная новая Task не заменяет исходную.
3. **Проверить одно и несколько полей.** **Вход:** метод из шага 2 и исходные целевая Task/сосед в `JsonStorage(tmp_path)`; каждый сценарий начинает с одной и той же исходной записи. **Объект:** прямые сервисные проверки для `title` отдельно, `priority` отдельно, `is_done=False` отдельно и сочетания `title` + `priority`. **Опора:** `02`–`04`, прогноз шага 1. **Самостоятельно:** выполнить случаи и после каждого сравнить результат с прогнозом; затем прочитать файл новым экземпляром сервиса. **Локальный результат:** `False` применяется, изменяются все и только переданные поля, `id`/`tags` и соседняя запись совпадают с исходными; перезагрузка возвращает то же сохранённое состояние.
4. **Различить no-op, отсутствие и валидационный отказ.** **Вход:** сохранённая целевая Task; отдельные тестовые случаи на существующий и неизвестный id и на недопустимое значение по правилам имеющейся модели `Task`. **Объект:** результаты вызова, исключение сервиса и содержимое временного JSON. **Опора:** `05`–`06`; перед практикой подтвердить прежний контракт `TaskNotFoundError` и валидации в целевой версии. **Самостоятельно:** проверить `None` и пустой набор на существующем id, затем пустой набор на отсутствующем id и невалидное изменение, например `priority=0`; проследить порядок поиска/no-op/валидации/`save`. **Локальный результат:** существующий id остаётся без изменений; неизвестный id даёт `TaskNotFoundError`; невалидное изменение отклонено; ни один отказ не оставляет частичную запись. Для no-op возврат до `save` устанавливается по потоку сервиса, не по одному совпадению байтов файла; точный счётчик вызовов относится к следующей общей проверке.
5. **Проверить сохранённые возможности Planner.** **Вход:** прошедшая прямые случаи новая операция и существующие проверки прежних service/storage-функций. **Объект:** создание, чтение, полный `replace_task`, повторная загрузка и соседняя запись. **Опора:** B `52.1`, B `53`/`53.1` и локальные результаты шагов 2–4. **Самостоятельно:** выполнить применимые проверки в выбранной целевой версии и сопоставить поведение до/после добавления метода; при регрессии назвать нарушенный контракт. **Локальный результат:** частичное изменение использует существующую сервисную границу и JSON, а прежние create/read/full replace продолжают работать.

Шаги образуют прогрессию от прогноза состояния к самостоятельной сервисной операции, затем к различающим успешным и отказным случаям и регрессионной проверке. К блокам `02`–`04` возвращаются при ошибке с `False`, потере неизменённого поля или записи до валидации; к `05`–`06` — при смешении пустого изменения с отсутствующей задачей или при проверке результата только по возврату метода. B доказана, когда тест на одном поле, тест на нескольких полях и повторное чтение новым сервисом дают ожидаемое сохранённое состояние, а no-op/отказы не меняют данные. Точный счётчик `save` не заявляется частью этой практики. План `54.1` отдельно формирует `TaskPatch`; план `54.2` соединяет готовую схему и сервис с HTTP PATCH.
