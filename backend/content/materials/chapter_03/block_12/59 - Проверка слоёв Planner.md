## 00. Вступление

После проверки query и описания OpenAPI остаётся вопрос о внутреннем состоянии Planner. Хороший HTTP-ответ показывает результат для клиента, но не сообщает сам по себе, сохранился ли полный объект, не изменился ли сосед и использовали ли CLI и API одно прикладное ядро.

1. **Точка старта:** в предыдущем шаге HTTP-контракт списка и OpenAPI проверяются на изолированных тестовых данных.
2. **Новый вопрос:** какие внутренние гарантии уже подтверждены отдельными тестами, а какие только кажутся верными по внешнему ответу?
3. **Результат:** сопоставим тесты с моделью, хранилищем и сервисом, добавим только недостающие доказательства и подготовим основу для сквозной истории.

Сначала отделим внешнее поведение, уже переданное из 58.2, от внутренних вопросов. Затем проследим одну гарантию на каждом нужном уровне и зафиксируем фактические результаты в матрице. Так в 59.1 можно будет проверять взаимодействие операций, не подменяя длинным сценарием отдельные проверки слоёв.

## 01. У теста есть граница и конкретный вопрос

- Что и зачем объяснить: один и тот же сценарий можно проверить через модель, storage, сервис или HTTP, но каждый способ подтверждает разную часть поведения. Число тестов и имя файла не говорят, какое обещание они проверяют.
- Механизм и порядок: назвать объект проверки, его входные данные, наблюдаемое состояние и границу вывода. Прямой вызов сервиса изолирует прикладное правило; HTTP-тест проходит через разбор запроса и маршрут; проверка persistence перечитывает сохранённое состояние. Связать эту классификацию с матрицей, не повторяя тему из 58.2.
- Пример и типичная путаница: один и тот же отказ можно увидеть как HTTP-статус или как исключение сервиса, но это разные границы. Маленький список после запроса не доказывает сохранность полной записи; HTTP-ответ с четырьмя публичными полями не показывает tags доменной Task.
- Первое самостоятельное действие: взять существующие строки матрицы и реальные тесты, соотнести каждую гарантию с тем, что тест действительно вызывает и наблюдает. Результат: перечень подтверждённого покрытия и вопросов, которые ещё нельзя закрыть имеющимся свидетельством.
- Опора для повторного обращения: перед добавлением проверки восстановить гарантию, границу вызова и наблюдаемое состояние; не считать похожее имя теста доказательством нужного поведения.
- Переход к следующему шагу: после инвентаризации станет видно, какие пробелы относятся к самой модели, а не к HTTP-ответу.

## 02. Task сохраняет собственное состояние

- Что и зачем объяснить: Task является доменной записью с id, title, priority, is_done и tags. Проверка одного экземпляра не доказывает независимость изменяемых значений разных экземпляров или сохранность всей записи при преобразовании.
- Механизм и порядок: различить новую изменяемую коллекцию внутри каждой Task и ссылки на объект Task, которые может хранить контейнер. Затем проследить полное представление записи и восстановление полей; отдельно отметить, что публичная HTTP-проекция TaskRead не заменяет формат хранения.
- Пример и типичная путаница: две задачи получают одинаковые значения tags, но их списки не должны становиться одним общим списком. При этом копия списка MemoryStorage может содержать те же ссылки на Task: изменение состава контейнера и изменение объекта внутри него имеют разные последствия.
- Первое самостоятельное действие: выбрать в тестах Task отсутствующую гарантию независимости изменяемого поля или сохранения полного состояния после отказа конструктора/операции. Результат: тест подтверждает только обещанное моделью свойство и не навязывает глубокое копирование всех объектов.
- Опора для повторного обращения: перечень полей полной Task и снимок значений до/после операции; при проверке тегов отличать копию списка от копии самой задачи.
- Переход к следующему шагу: после модели можно проверить, какие свойства добавляет контейнер памяти, а какие даёт сериализация в файл.

## 03. MemoryStorage и JsonStorage имеют разные границы

- Что и зачем объяснить: оба хранилища поддерживают договор load/save, но их поведение различается. MemoryStorage отделяет списки-контейнеры, сохраняя ссылки на содержащиеся задачи; JsonStorage переводит записи в файл и восстанавливает их при новом чтении.
- Механизм и порядок: показать копирование списка при load/save у MemoryStorage и отдельно границу общей ссылки на Task. Для JsonStorage проследить сохранение полной записи с tags и повторное чтение. Ошибка чтения остаётся ошибкой и не должна трактоваться как пустой файл с последующей перезаписью.
- Пример и типичная путаница: удаление элемента из полученного списка не обязано менять внутренний список MemoryStorage без save; изменение общего Task может быть видно через обе ссылки. Для JsonStorage сравнить восстановленную запись с полным исходным состоянием, а не только с числом задач.
- Первое самостоятельное действие: сопоставить тесты storage и persistence с обещаниями этих двух реализаций. На собственных временных данных добавить только отсутствующую проверку копии контейнера, полного JSON round-trip либо сохранности файла при ошибке чтения. Результат: у теста ровно одна понятная граница.
- Опора для повторного обращения: для MemoryStorage восстановить, что копируется и что остаётся общей ссылкой; для JSON проверить полную Task и исходное состояние файла при неуспешном чтении. Уже существующие гарантии test_persistence.py переиспользовать.
- Переход к следующему шагу: теперь можно проверить не только хранилище отдельно, но и то, как сервис читает и сохраняет данные через выбранный путь.

## 04. Сервисное чтение и сохранение проверяются разными свидетельствами

- Что и зачем объяснить: PlannerService связывает прикладную операцию с переданным storage. Возвращённый объект не доказывает, что данные записаны; равные байты файла после чтения сами по себе не доказывают, что save вообще не вызывался.
- Механизм и порядок: использовать существующую сборку сервиса на JsonStorage с временным путём. Чтобы подтвердить read-only гарантию, наблюдать вызов save через уже введённую в 55.1 счётную обёртку или переиспользовать эквивалентную существующую проверку. Чтобы подтвердить сохранение обновления, открыть новый сервис на том же пути и прочитать полную Task вместе с id, tags и контрольной записью.
- Пример и типичная путаница: ответ PATCH может выглядеть правильно, пока файл не перечитан; сравнение только общего количества может скрыть замену или потерю соседней задачи. Сопоставить ответ операции с повторным чтением, не добавляя в урок новый CRUD.
- Первое самостоятельное действие: после сверки тестов 49, 52.1 и 55.1 выбрать только отсутствующее доказательство чтения без save или повторного чтения обновления. Результат: адресная проверка на том же временном пути, без TestClient и без использования рабочего JSON.
- Опора для повторного обращения: какой service и путь использует тест, что уже было сохранено, какое поле изменено и что должно сохраниться у соседа; для read-only проверки использовать свидетельство факта вызова save, а не только неизменность файла.
- Переход к следующему шагу: после доказательства поведения сервиса проверить, что модули и интерфейсы обращаются к нему через предусмотренные границы.

## 05. Границы модулей и фактическая матрица

- Что и зачем объяснить: API и CLI используют один PlannerService; сервис зависит от storage и предметной модели, но не от FastAPI. Проверка импортов помогает найти нарушение ответственности, однако не является поводом перестраивать работающий проект ради схемы.
- Механизм и порядок: проследить один путь чтения и один путь изменения от интерфейса через сервис к storage. Сверить импорты, фактические тесты и запись docs/test-matrix.md; отличить подтверждённый дефект от допустимой структуры, не определённой контрактом.
- Пример и типичная путаница: порядок выполнения вызовов не всегда совпадает с направлением импортов. Важно установить, какой модуль принимает решение, кто владеет HTTP-ответом и кто сохраняет данные; само наличие общих модулей этого не доказывает.
- Первое самостоятельное действие: самостоятельно пройти по именам существующих модулей выбранный read-only путь и путь изменения, затем указать, какой уже имеющийся тест подтверждает каждую границу. Результат: актуальная карта тестов и конкретное нарушение, если оно действительно обнаружено.
- Опора для повторного обращения: роли моделей, storage, сервиса, CLI и router; для каждой найденной связи указать её направление и подтверждающий тест.
- Переход к практике: карта превращает список потенциальных улучшений в короткую работу только с реально неподтверждёнными гарантиями.

## 06. Что мы будем делать в практике

**Формат и исходная опора:** manual, проектная проверка готового Planner после ожидаемых результатов 55.1 и 58.2. Начинаем с фактического checkout, уже имеющихся тестов и docs/test-matrix.md. Автотесты работают только на собственном временном JSON; рабочий data/tasks.json не используем.

Итог практики: матрица показывает, какие значимые гарантии модели, storage, сервиса и HTTP подтверждены и где оставался пробел. Изменения ограничиваются отсутствующими проверками и синхронизацией матрицы; готовые API-маршруты, договор и прикладное поведение сохраняются.

1. **Сопоставим гарантию и существующее доказательство:** исходно есть фактические тесты проекта и матрица. Ученик самостоятельно определит слой, который вызывает каждый релевантный тест, и состояние, которое он наблюдает. Критерий шага: по каждой гарантии из паспорта указан конкретный тест либо явно записано, что её нельзя подтвердить текущим входом. Уже покрытые HTTP-договор, выборка, id и CRUD не переносятся в новые дубли.
2. **Закроем только модельные и storage-пробелы:** исходно доступны настоящие Task, MemoryStorage, JsonStorage и изолированный путь. Опираясь на блоки 02–03, ученик выберет отсутствующие гарантии независимости состояния Task, границы копии MemoryStorage, полного JSON round-trip или поведения при ошибке чтения. Критерий шага: фактический тест подтверждает выбранную гарантию на собственных данных и не предполагает глубокого копирования.
3. **Подтвердим недостающие persistence-гарантии сервиса:** исходно есть готовые операции, результаты тестов 49/52.1/55.1 и реальный JsonStorage на временном пути. По блоку 04 ученик повторно использует существующее доказательство либо добавит только недостающее: отсутствие save при чтении или сохранённое обновление, видимое новому сервису, с сохранёнными id, tags и соседом. Счётчик save берётся из обёртки, введённой ранее; если она и эквивалентная проверка отсутствуют, зависимость отмечается как неподтверждённая, а сравнение байтов не объявляется заменой. Критерий шага: имеющаяся гарантия используется один раз и подтверждена подходящим прямым тестом.
4. **Сверим границы и обновим матрицу:** исходно есть карта покрытия и тесты предыдущих действий. Ученик самостоятельно проследит общий путь через CLI/API, сервис и storage, устранит только конкретное подтверждённое нарушение и приведёт docs/test-matrix.md в соответствие фактическим тестам. Критерий шага: нижние слои не зависят от HTTP, интерфейсы используют общее ядро, матрица не перечисляет несуществующие или дублирующие проверки, прежний договор не изменён.

Действия идут от инвентаризации к узким изменениям: каждый следующий шаг использует только уже найденный пробел и доступные данные. Если запланированный результат 55.1 или 58.2 отсутствует, это отмечается как неподтверждённая входная опора; план не предлагает незаметно переносить их задания в 59.

**Итоговый критерий всей практики:** фактические тесты подтверждают значимые гарантии Task, MemoryStorage, JsonStorage и PlannerService; HTTP-покрытие из 58.2 и существующие проверки предыдущих шагов не продублированы; тесты используют изолированные данные; docs/test-matrix.md совпадает с реальной структурой и доказательствами; продуктовые операции и поведение CLI/API сохранены.

**Передача в 59.1:** матрица показывает исходные и дополненные проверки по слоям. Следующий урок добавит отдельный workflow-тест, где одна задача проходит последовательные HTTP-операции рядом с контрольной записью; этот временной сценарий не заменяет и не переписывает доказательства, созданные здесь.
