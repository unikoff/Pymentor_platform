## Место в маршруте

Занятие проверяет, можно ли повторить запуск уже собранного Planner в отдельной чистой копии проекта. Паспорт планирует передать сюда результат сквозного workflow после 59.1; поскольку переработанный маршрут ещё не внедрён, это проектируемая опора, а не подтверждение фактического прохождения. Здесь проверяются установка и воспроизводимость, а CRUD не проходится заново. В 60.1 по фактическим результатам этой проверки будут завершены README, тестовая матрица, release notes и фиксация проверенной версии.

## Точка B: результат занятия

- Ученик сможет объяснить: чем чистый checkout отличается от рабочей папки с локальной `.venv` и данными; почему важны точный commit и корень проекта; как README и файлы зависимостей задают воспроизводимый запуск; чем автоматическая проверка приложения отличается от ручного HTTP-пути.
- Ученик сможет сделать: в отдельном checkout точного входного commit создать окружение проекта, установить объявленные и закреплённые зависимости, запустить полный набор pytest, затем вручную проверить CLI и API на одной задаче из JSON этой копии и импортировать готовые Postman collection и environment.
- Результат в проекте: прикладные возможности не меняются. Исправляются только обнаруженные несоответствия инструкции или объявленных зависимостей в изолированной копии; личная рабочая копия и её данные не очищаются.

Импорт подтверждает доступность артефактов, но не повторяет весь HTTP-workflow.

## 00. Вступление

Мы уже проверяли отдельные части Planner и проходили связанный HTTP-сценарий. Теперь проверим, можно ли получить такой же рабочий проект в новой копии без скрытой помощи старой среды или локального файла данных.

1. **Точка старта:** по входному паспорту в проверяемом checkout ожидаются приложение, CLI, JSON, тесты и сохранённые Postman-файлы. Ранний опыт с Git-клоном и локальным Python-окружением отмечен в журнале, а его актуальную самостоятельность при необходимости проверяют до выдачи.
2. **Новый вопрос:** можно ли установить и запустить именно этот проверенный снимок проекта только по его README и объявленным зависимостям?
3. **Результат:** новая копия проходит установку, тесты и запуск CLI/API, а готовые Postman-артефакты импортируются.

Мы отделим версионируемые файлы от локального окружения и пользовательских данных, выберем точный входной commit, а затем будем повторять документированные шаги в новой папке. Это проверяет переносимость текущего продукта; итоговые release-документы и версия будут оформлены следующим занятием.

## 01. Что делает checkout чистым

- Что и зачем объяснить: отдельная копия начинает с отслеживаемых файлов выбранного снимка. Локальная `.venv`, кэш и `data/tasks.json` не переносятся как часть Git-клона; `.gitignore` исключает их из Git, но сам по себе не удаляет их из исходной папки.
- Механизм и порядок: сначала различить основной рабочий каталог и новый checkout, затем проверить корень и наличие локальных артефактов до создания окружения. Новые данные в проверочной копии создаются учебным CLI.
- Пример и типичная путаница: новый checkout похож на отдельную чистую рабочую поверхность, а не на очистку стола пользователя. `.gitignore` не удаляет файлы, а только исключает их из Git; отсутствие `.venv` в копии означает, что окружение нужно создать и наполнить заново.
- Первое самостоятельное действие: вход — основной каталог и SHA из результата 59.1; объект — отдельный checkout и его локальные файлы; опора — объяснение различия между версионируемым снимком и локальными данными; действие — ученик выбирает отдельную папку и осматривает её до установки; результат — основной каталог не затронут, а отсутствие старой `.venv` и личного JSON в проверочной копии установлено.
- Опора для повторного обращения: перед запуском сверить путь корня проекта, состояние `.venv` и наличие локального JSON; не удалять эти файлы в исходной копии ради «чистоты».
- Переход к следующему шагу: чистота папки имеет смысл только относительно конкретного снимка проекта, поэтому далее фиксируется commit.

## 02. Какой снимок проверяем

- Что и зачем объяснить: имя ветки может указывать на меняющееся состояние, а commit фиксирует конкретный набор файлов. Проверять следует вход проекта после 59.1; текущий HEAD StudyHub содержит более поздний SQL-маршрут и не заменяет этот вход.
- Механизм и порядок: определить SHA из результата предыдущего этапа, создать отдельный checkout этого снимка, убедиться в его корне и сверить идентификатор перед установкой. В уже знакомые основы Git не углубляться.
- Пример и типичная путаница: HEAD текущей рабочей копии — не автоматически входной commit курса. Также нельзя взять исторический эталон B после занятия 68 как будто он является ещё не созданным checkpoint нового 59.1.
- Первое самостоятельное действие: вход — переданный результат 59.1; объект — SHA и отдельный checkout; опора — разница между изменяемым указателем ветки и зафиксированным commit; действие — ученик сверяет SHA и корень checkout до запуска команд; результат — источник проверки однозначен. Различающий случай: если SHA отсутствует или checkout указывает на другой commit, проверку останавливают и запрашивают корректный вход, не подменяя его текущим HEAD.
- Опора для повторного обращения: перед командами сверять SHA, путь и каталог, из которого выполняется шаг; при несовпадении остановить именно проверку этого снимка, а не подменять его текущей веткой.
- Переход к следующему шагу: после подтверждения версии можно исследовать зависимости, не полагаясь на пакеты старого компьютера.

## 03. Новое окружение и объявленные зависимости

- Что и зачем объяснить: `.venv` принадлежит конкретному checkout; runtime-набор нужен приложению, а dev-набор добавляет инструменты проверки и включает runtime. README задаёт порядок установки и запуска из корня проекта.
- Механизм и порядок: создать окружение новым Python проекта, установить зависимости из объявленных файлов, затем выполнять команды установки, CLI, API и pytest тем же интерпретатором. В целевом B сохраняются закреплённые версии; `httpx2` уже объявлен в dev-наборе и не требует отдельной замены на `httpx`.
- Пример и типичная путаница: команда системного Python может успешно импортировать пакет, установленный глобально, хотя новая `.venv` его не содержит. Успех в старой среде тогда не доказывает, что зависимости описаны в репозитории.
- Первое самостоятельное действие: вход — чистый checkout и его README; объект — новая `.venv`, `requirements.txt` и `requirements-dev.txt`; опора — различие runtime-зависимостей приложения и dev-зависимостей проверок; действие — ученик сверяет документированный порядок и устанавливает объявленные закреплённые наборы тем же интерпретатором; результат — установка опирается на файлы проекта. Различающий случай: если команда проходит только в системном Python или требует незаписанный пакет, это свидетельство неполной инструкции/декларации, а не повод молча менять версию зависимости.
- Опора для повторного обращения: для каждой команды проверять три вещи — корень проекта, Python именно этой `.venv`, источник пакетов в requirements; версии не обновлять ради прохождения.
- Переход к следующему шагу: установленный набор подтверждается полным тестовым запуском, который использует изолированные данные.

## 04. Автоматические проверки в новой копии

- Что и зачем объяснить: полный pytest-набор проверяет зафиксированную тестовую поверхность; он не подтверждает сетевую доступность Uvicorn. Тестовые fixtures используют собственные `tmp_path`, поэтому рабочий JSON не должен быть подготовкой тестов.
- Механизм и порядок: запускать набор из корня и установленным Python проекта. При сбое сначала отделить ошибку установки, импорта, теста или окружения; менять только подтверждённую причину, после правки повторить затронутую проверку.
- Пример и типичная путаница: зеленый `TestClient` проверяет FastAPI-приложение в тесте без отдельного сервера; это не равно запросу Postman к Uvicorn. Неустойчивость из-за порядка тестов нельзя лечить передачей данных из одного теста в другой.
- Первое самостоятельное действие: вход — только что созданное окружение; объект — полный набор pytest и его вывод; опора — команда из README и объяснение изоляции тестовых fixtures от рабочего JSON; действие — ученик запускает весь набор из корня checkout и классифицирует сбой по выводу; результат — весь набор завершён успешно либо зафиксирована конкретная воспроизводимая причина. Различающий случай: успешный `TestClient` не доказывает доступность Uvicorn, а сбой импорта не следует лечить изменением тестового контракта.
- Опора для повторного обращения: если падает тест, сначала определить его границу и входные данные; не заменять JsonStorage на общий список и не трогать личный `data/tasks.json`.
- Переход к следующему шагу: автоматическая проверка доказывает изолированный контракт; теперь отдельно воспроизводится запуск приложения и общий файл CLI/API.

## 05. CLI и API используют одну проверочную копию

- Что и зачем объяснить: CLI и API — два входа в тот же Planner и JSON. Ручной запуск подтверждает команды README и рабочий процесс, которых один тест через ASGI не показывает.
- Механизм и порядок: запустить CLI из чистого checkout, создать собственную задачу, затем запустить API по README и прочитать её по фактическому id. После перезапуска процесса проверить повторное чтение и соответствие CLI; не брать id из заранее заданной таблицы.
- Пример и типичная путаница: health подтверждает доступность одного маршрута, но не чтение задачи или сохранение. Аналогично успешный ответ POST сам по себе не подтверждает, что следующая команда увидит ту же запись.
- Первое самостоятельное действие: вход — проверочная копия с установленными зависимостями; объект — созданная учеником задача в JSON этой копии; опора — README, команды CLI/API и объяснение общего `JsonStorage`; действие — ученик создаёт задачу через CLI, берёт фактический id, читает её через API и повторно проверяет после перезапуска; результат — оба интерфейса читают одну запись, сохранившуюся после завершения процесса. Различающий случай: успешный `/health` без чтения созданной задачи не подтверждает общий файл данных.
- Опора для повторного обращения: записать фактический id и исходное состояние; сравнивать запись через следующий GET/CLI, а не только статус ответа. Личный JSON из основной копии не используется.
- Переход к следующему шагу: после воспроизведения проекта проверяются переносимые файлы запросов из того же снимка.

## 06. Импорт Postman и сверка инструкции

- Что и зачем объяснить: collection хранит запросы, environment — параметры адреса; их импорт показывает, что проект передаёт необходимые ручные артефакты. Эта проверка не повторяет полный HTTP-workflow, пройденный в 59.1.
- Механизм и порядок: импортировать collection Planner API и Local environment из новой копии, убедиться, что клиент распознал оба файла и адрес указывает на API проверочной копии. Секреты и локальные пользовательские данные не экспортировать.
- Пример и типичная путаница: успешный импорт не доказывает работу всех запросов, а существование JSON-файлов в старой рабочей папке не доказывает, что они входят в выбранный commit.
- Первое самостоятельное действие: вход — SHA проверочной копии; объект — поставляемые ею collection и environment; опора — различие между импортом запросов и выполнением HTTP-сценария; действие — ученик импортирует оба файла и проверяет распознанное содержимое и базовый адрес; результат — артефакты доступны из проверяемой копии и указывают на её API. Различающий случай: успешный импорт не засчитывается как проверка всех запросов или полного workflow.
- Опора для повторного обращения: сверить SHA checkout, имена файлов и активный Local environment; если импортируется устаревшая копия, проверить путь источника, не создавать дубликаты с неясным происхождением.
- Переход к следующему шагу: сопоставить наблюдённый путь с README и передать фактические результаты занятию 60.1.

## 07. Что мы будем делать в практике

**Формат и исходная опора:** manual-проверка в отдельном чистом checkout точного commit, переданного после 59.1. Паспорт планирует в нём CLI, API, общий JSON, тесты, requirements, README и Postman-артефакты; перед занятием проверить фактический состав. Основной каталог участника не переключается, не сбрасывается и не очищается.

1. **Подготовить чистую копию.** Вход — SHA результата 59.1; объект — новый отдельный checkout; опора — раздел 01 о различии версионируемых файлов и локальных данных; действие — ученик выбирает отдельный путь, получает checkout этого SHA и сверяет путь/commit до запуска; результат — правильный снимок отделён от рабочей папки, в копии нет унаследованной `.venv` и личного `data/tasks.json`. Если SHA или снимок не совпадает, ученик останавливает проверку и фиксирует недостающий вход.
2. **Установить по README.** Вход — чистый checkout; объект — новая `.venv` и закреплённые файлы зависимостей; опора — раздел 03; действие — ученик создаёт окружение и устанавливает runtime/dev-набор только командами, указанными проектом; результат — используется интерпретатор новой `.venv`, а установка не зависит от глобальных пакетов. Если README или requirements расходятся с фактом, записать точную команду и ошибку; версии не обновлять наугад.
3. **Запустить полный набор pytest.** Вход — установленная чистая копия; объект — весь набор тестов и их вывод; опора — раздел 04 и тестовые fixtures с независимыми данными; действие — ученик запускает полный набор из корня; результат — набор проходит без обращения к рабочему JSON. Различающий случай — отделить нехватку зависимости от провала утверждения теста; исправлять лишь подтверждённое расхождение в изолированной копии.
4. **Сверить CLI и API на одной записи.** Вход — работающая проверочная копия; объект — задача в её JSON; опора — раздел 05 и команды README; действие — ученик создаёт задачу CLI, использует фактический id в API, затем повторно читает её после перезапуска; результат — оба входа видят одну сохранённую запись. Одного успешного health-check недостаточно.
5. **Импортировать Postman-артефакты.** Вход — файлы из того же SHA; объект — collection и Local environment; опора — раздел 06; действие — ученик импортирует их и сверяет базовый адрес; результат — оба файла распознаны и направлены на проверочную копию. Это проверка наличия и импорта, не повтор полного workflow.
