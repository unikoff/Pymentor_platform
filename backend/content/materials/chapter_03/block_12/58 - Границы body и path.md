## 00. Вступление

До проверки API ученик уже может отправить обычный запрос через тестовый клиент и увидеть ожидаемый ответ. Теперь вопрос не в том, существует ли маршрут, а в том, выдерживает ли его вход договор на границах значений. Для этого сначала задаётся корректный обычный случай, затем по одному меняются title, priority или path id. Так причина отказа остаётся различимой.

1. **Точка старта:** настоящее FastAPI-приложение, прежние маршруты и function-scoped `api_client` из ожидаемой опоры новой карты.
2. **Новый вопрос:** как автоматически различить допустимую границу, выход за неё и корректное отсутствие ресурса, не меняя сам API?
3. **Результат:** новая часть `tests/test_contract.py` проверяет body и path на настоящем приложении; её тесты не затрагивают рабочие данные.

Связь простая: известный маршрут задаёт исходный случай, разные входы показывают границу его контракта, а автоматизация закрепляет поведение до будущих изменений. Сначала ученик отделит причины проверки, затем соберёт небольшую параметризованную матрицу и прочитает статус вместе с полем ошибки.

## 01. Изолированное состояние и обычный случай

- Что и зачем объяснить: тесту нужен повторяемый исходный объект. `api_client` уже подменяет сервис на отдельный `JsonStorage` для каждого теста; запросы одного теста используют общий файл, новый тест получает свежее состояние.
- Механизм и порядок: внутри каждого тестового вызова создать Task через готовый API, взять настоящий id из этого ответа, затем прочитать её по item-route. Сначала убедиться, что обычный корректный запрос проходит, и только потом менять один вход.
- Пример и типичная путаница: успешный `PUT` по существующему id с полным корректным body — контроль для дальнейших проверок. Не использовать id из рабочего файла и не считать новый вызов fixture на каждый request.
- Первое самостоятельное действие: после короткого восстановления fixture самостоятельно создать запись в текущем тесте, получить её id и подтвердить обычный ответ item-маршрута; результат — известный положительный path для этой проверки.
- Опора для повторного обращения: роль function scope, временного JSON и возвращаемого `api_client`; ошибка настройки изоляции отличается от ошибки HTTP-контракта.
- Переход к следующему шагу: с проверенным обычным случаем можно исследовать значение на границе, не смешивая его с отсутствующим ресурсом.

## 02. Один тест — одна причина отказа

- Что и зачем объяснить: набор должен показывать, какое именно правило сработало. Для body остальные поля остаются допустимыми и id — существующим положительным числом; для path body целиком корректен. Тогда 422 не маскирует другую ошибку входа.
- Механизм и порядок: сопоставить обычное значение, допустимый край, ближайшее недопустимое значение и отдельный неверный тип. В каждом body-вызове создать целевую запись в его собственной fixture; для отсутствия ресурса использовать корректный положительный integer id, которого нет в этом тестовом хранилище.
- Пример и типичная путаница: неверный title при корректном `task_id` показывает body-ошибку; тот же корректный body с path `0` показывает ограничение пути. Не отправлять одновременно неверный body и неверный id, а затем угадывать, какая проверка должна выполниться первой.
- Первое самостоятельное действие: распределить подготовленные сценарии на «валидный край», «вне границы», «неверный тип» и «валидный, но отсутствующий id»; наблюдаемый результат — каждый сценарий изменяет только одну причину отказа.
- Переход к следующему шагу: когда таблица случаев различает причины, повторяющиеся входы можно записать компактно через pytest.

## 03. Простая параметризация pytest

- Что и зачем объяснить: `pytest.mark.parametrize` связывает имена аргументов теста с последовательностью наборов значений. Pytest запускает тот же тест отдельно для каждой строки; это один сценарий с несколькими входами, а не один запрос со всеми значениями.
- Механизм и порядок: разобрать форму «поля входа и ожидаемый статус» на маленькой матрице; показать, как тест получает каждый вариант, почему проверка остаётся одной и как отдельный вызов теста для каждой строки заново получает function-scoped `api_client`. Целевую запись надо создавать внутри этого вызова, а не повторно использовать id из предыдущей строки. Не вводить динамическую генерацию наборов, декартово произведение или сложные `ids`.
- Пример и типичная путаница: для title меняется только title, priority и положительный id остаются корректными; ожидаемый статус задаётся рядом с каждым вариантом. Не писать отдельный почти одинаковый тест на каждую длину и не помещать все проверки в один общий сценарий.
- Первое самостоятельное действие: ученик самостоятельно задаёт простую матрицу для одного правила и связывает вход с ожидаемым status; результат — pytest показывает отдельные случаи, а ошибка указывает на конкретную строку набора.
- Опора для повторного обращения: имена аргументов должны совпасть с тестовой функцией; в строке случая значения идут в том же порядке. При ошибке проверить, какая именно строка параметров запустилась.
- Переход к следующему шагу: тот же приём применяется отдельно к строковым и числовым ограничениям, не меняя runtime-код.

## 04. Границы title после нормализации

- Что и зачем объяснить: длина проверяется у очищенного title. Краевые пробелы удаляются до `Field`-ограничения; поэтому сравнивать нужно валидную минимальную и максимальную длину с пустым результатом и длиной за пределом.
- Механизм и порядок: на существующей Task выполнить полный `PUT` с корректными `priority` и `is_done`; варьировать только title. Проверить короткую и максимальную допустимую длину, пустую/пробельную строку, превышение максимума, а также нестроковое JSON-значение. Дополнительно разобрать строку с внешними пробелами, чистая длина которой ровно допустима.
- Пример и типичная путаница: длина сырой строки может превышать лимит за счёт внешних пробелов, но после очистки значение проходит. Не переносить проверку на сырой размер и не превращать обычное Pydantic-преобразование в strict.
- Первое самостоятельное действие: самостоятельно составить title-набор, где только один параметр меняется между случаями, и подготовить цель для каждого вызова; для разрешённых входов наблюдать 200 и title после очистки, для отклонённых — 422 с `title` в `detail.loc`.
- Опора для повторного обращения: порядок «строка → strip краёв → проверка чистой длины»; характерная ошибка — считать длину до strip или проверять только статус без поля причины.
- Переход к следующему шагу: после проверки строки тем же способом проверяется числовая граница, сохраняя валидный title.

## 05. Границы priority и обычное преобразование

- Что и зачем объяснить: поле priority принимает целые значения от 1 до 5 включительно. Внешние значения ниже/выше диапазона и непринимаемый текст отклоняются схемой до обработчика.
- Механизм и порядок: держать title валидным и положительный id существующим; отдельно проверить оба допустимых края, ближайшие значения за ними и нечисловую строку. Объяснить, что схема сохраняет обычное преобразование Pydantic; урок не обещает строгий отказ для любого значения, пришедшего строкой.
- Пример и типичная путаница: корректная строка title исключает конкурирующую ошибку; `high` показывает неверный тип, тогда как допустимая числовая строка иллюстрирует сохранённое преобразование, если её используют в объяснении. Не добавлять strict, новые поля или запрет extra.
- Первое самостоятельное действие: самостоятельно составить отдельный набор priority и ожиданий, подготовив целевую запись в каждом вызове и оставив остальные поля неизменными; наблюдаемый результат — успешные края отражены в ответе, а 422 для выходов сопровождается `detail.loc` с priority.
- Опора для повторного обращения: держать в уме допустимый интервал и различать ошибку типа от ошибки диапазона; точный текст сообщения Pydantic не фиксировать.
- Переход к следующему шагу: body-проверки разобраны независимо от path; теперь тот же принцип используется для id.

## 06. Положительный path: неверное значение и отсутствие

- Что и зачем объяснить: FastAPI разбирает path до вызова обработчика, а `Path(gt=0)` допускает только положительный integer. Корректный положительный id, которого нет в хранилище, доходит до поиска и даёт 404; неразбираемое, нулевое и отрицательное значение дают 422.
- Механизм и порядок: в каждом вызове создать контрольную Task и на item-маршруте обновления передать полный корректный body. Изолированно проверить текст, 0 и отрицательное значение, затем вычисленный положительный id, отсутствующий в том же тестовом хранилище.
- Пример и типичная путаница: для отсутствия не подставлять заведомо неверный формат или невалидный body. Не путать 404 предметного поиска с 422 проверки входа и не требовать нового ручного валидатора в handler.
- Первое самостоятельное действие: ученик сам подготавливает корректную Task и body, затем разделяет случаи path на «не может быть принят» и «принят, но запись отсутствует»; критерий — разные статусы, а `detail.loc` для path-422 указывает на `task_id`.
- Опора для повторного обращения: контракт `Path(gt=0)` уже объяснён в 48.1; здесь восстановить его границу и путь выполнения до поиска. Полный текст ошибки и несвязанные поля ответа не закреплять.
- Переход к практике: матрица body и path готова; следующий урок добавит сравнение полного состояния до и после отказа.

## 07. Что мы будем делать в практике

**Формат и исходная опора:** manual в существующем проекте; начинаем с готовых `api_service`/`api_client`, `APIRouter`, схем `TaskCreate`/`TaskUpdate` и работающих HTTP-маршрутов. Добавляется только `tests/test_contract.py`; точный код решений и условия карточек разрабатываются на этапе 3.

Общий результат — отдельные, читаемые тесты обычных случаев и границ body/path. В каждом параметризованном варианте меняется один фактор, а ожидаемый критерий известен заранее.

1. **Подготовить контрольный случай:** с опорой на блок 01 самостоятельно написать один обычный тестовый вызов: создать Task через готовый API, сохранить возвращённый положительный id и подтвердить чтение; результат — образец подготовки исходного состояния. Последующие параметры создают свои записи внутри своих вызовов, потому что function-scoped fixture не переносит данные между ними.
2. **Проверить title:** применить этот порядок подготовки и объяснение блоков 03–04; в каждом параметризованном вызове получить собственную Task и выполнить полный PUT с прочими допустимыми значениями. Самостоятельно прогнать очищенную минимальную/максимальную длину, строку с внешними пробелами и допустимой чистой длиной, пустой результат, выход за предел и неверный тип. Результат каждого случая различим по 200/422 и `loc` для title; успешный ответ показывает очищенное значение.
3. **Проверить priority:** применить блоки 03 и 05; в каждом отдельном вызове получить собственную Task, оставить title допустимым и прогнать оба края, выходы и непринимаемый текст. Результат — status и поле priority в успешном ответе подтверждают именно числовое правило, а неверный вход отклонён по нужному полю.
4. **Проверить path:** применить разбор случаев из блока 02 и правило блока 06; в каждом вызове создать контрольную запись и передавать полный корректный body, меняя только id между текстом, нулём, отрицательным значением и корректным отсутствующим положительным id. Результат — 422 с `task_id` для недопустимого пути и 404 для отсутствующего ресурса.

Сначала создаётся известное состояние на текущей fixture, потом автоматически проверяются три независимые группы границ. Теория заранее объясняет повторный запуск теста, очистку title, диапазон priority и разделение Path-проверки с поиском записи. Успешный body-кейс может обновить только изолированную Task; полные снимки состояния после отказов, контроль соседней записи и статистики здесь не являются условием шага — это результат 58.1. Итог практики подтверждает B, когда новая матрица запускается с существующими fixtures, различает граничные ответы и оставляет маршруты и рабочий JSON нетронутыми.
