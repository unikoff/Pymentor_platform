## Точка A: подтверждённая опора

- Подтверждённая опора: ранее ученик применял pytest, вызывал готовый сервис в тестах и готовил временные данные через `tmp_path`/`JsonStorage` (журнал предыдущей главы). Это основание работать с известными тестовыми данными, но само по себе не подтверждает знание HTTP-клиента.
- Планируемая опора: новая карта ставит перед уроком ручную HTTP-матрицу блока 11, первый TestClient-тест (56) и изолированные fixtures (56.1). Перед выдачей проверить успешные ручные сценарии, серверный ID при POST и сохранение прежнего ID при PUT; подтвердить, что ученик прошёл 56 и 56.1 и может пользоваться готовыми fixtures. Если это не подтверждается, не объявлять эти знания освоенными и сначала обеспечить их в предшествующих шагах.
- Состояние проекта по целевому A: приложение предоставляет CRUD-операции; `tests/test_api.py` содержит исходный `/health`-тест, а готовые `api_client`/`api_service` и изоляция тестовых данных относятся к планируемой опоре 56.1. Здесь изменяются тесты, а не приложение, handlers, схемы или сервис.

## Точка B: результат занятия

- Ученик сможет объяснить, почему успешный HTTP-статус сам по себе не доказывает нужное изменение данных, и выбрать между проверкой ответа и последующим чтением.
- Ученик сможет сделать: самостоятельно выбрать тестовые данные и написать пять различимых сценариев для чтения, создания, полной замены, частичного изменения и удаления.
- Результат в проекте: добавлены автоматические проверки; приложение, маршруты, схемы, сервис и рабочий JSON не меняются.
- Как подтвердим: сценарии проверяют ответ и нужные публичные поля, а для записи — фактическое состояние через последующий GET/список. POST использует назначенный сервером ID; PUT сохраняет прежний ID; PATCH применяет переданное `false` и сохраняет непереданные поля; DELETE возвращает пустой `204`, после чего ресурс отсутствует. Тесты используют изолированное состояние и проходят по отдельности и вместе.

## 00. Вступление

В целевом маршруте 56 знакомит с запросом через настоящий app, а 56.1 готовит fixtures и отдельное начальное состояние для каждой тестовой функции. До выдачи нужно подтвердить, что эти шаги действительно пройдены. Здесь ученик не пересоздаёт клиент: он использует готовые fixtures, чтобы проверить пять CRUD-сценариев и увидеть, какое наблюдение доказывает результат операции.

1. **Точка старта:** API предоставляет CRUD-операции; готовые `api_client` и изолированное состояние — планируемая опора после 56–56.1.
2. **Новый вопрос:** какие наблюдения подтверждают не только успешный ответ, но и нужное изменение данных?
3. **Результат:** tests/test_api.py содержит пять самостоятельных сценариев CRUD, где ответ сопоставлен с реальными данными, а не только с кодом статуса.

Начать с Arrange → Act → Assert: выбрать данные, отправить запрос через готовый HTTP-клиент, проверить ответ и при необходимости прочитать состояние снова. Так ученик увидит разницу между «сервер ответил успешно» и «нужные данные действительно изменились»; этот договор защитит последующий перенос маршрутов.

## 01. Что доказывает HTTP-тест

- Что и зачем объяснить: запрос через готовый `api_client` проходит через настоящий FastAPI app и наблюдает внешний договор: статус и публичный ответ. Это не прямой вызов Python-функции и не проверка запущенного Uvicorn или внешней сети.
- Механизм и порядок: вспомнить Arrange → Act → Assert. Arrange задаёт известные данные через `api_service`; Act отправляет запрос через `api_client`; Assert проверяет статус и нужные поля ответа. Весь JSON сравнивают только если весь ответ является договором; обычно достаточно важных публичных полей.
- Пример и типичная путаница: если `/health` возвращает `200`, но неверное сообщение, проверка только статуса пропустит дефект. Нужны отдельные проверки статуса и содержимого. Успешный вызов сервиса не заменяет HTTP-проверку.
- Первое самостоятельное действие: прочитать health-тест и объяснить, что доказывает каждая его проверка.
- Опора для повторного обращения: готовый тест и fixtures 56–56.1; клиент и fixtures заново не создавать.
- Переход: применить тот же шаблон к GET, сначала задав данные для сравнения.

## 02. Чтение сверяется с известными данными

- Что и зачем объяснить: чтение проще проверить, когда тест заранее знает ожидаемые данные. Публичный ответ показывает договор API, а не внутреннее устройство сервиса или хранилища.
- Механизм и порядок: подготовить различимые задачи через `api_service`, отправить GET через `api_client`, сверить статус, нужный объект и его публичные поля.
- Пример и типичная путаница: утверждение «список не пуст» пройдёт даже при неправильном объекте. Проверка выбранного `title` отличает его от соседней задачи; приватное поле не является частью публичного ответа.
- Первое самостоятельное действие: выбрать данные и написать GET-сценарий, который отличает ожидаемый объект от другого.
- Опора для повторного обращения: готовый сервис задаёт данные; одна функция сохраняет состояние на протяжении своих запросов.
- Переход: при создании тест ещё не знает серверный ID и возьмёт его из ответа POST.

## 03. Создание связывает ответ и последующее чтение

- Что и зачем объяснить: сервер назначает новый ID, поэтому ожидаемое значение нельзя угадать заранее. Проверку успешного статуса нужно дополнить проверкой созданных данных.
- Механизм и порядок: отправить POST с допустимыми данными; проверить статус и публичные поля JSON; сохранить `id` из ответа; выполнить GET этого ID и сравнить поля. Оба запроса остаются в одном тесте и видят общее состояние.
- Пример и типичная путаница: заранее вычисленный ID может случайно работать локально и сломаться в другом запуске. Значение из ответа проверяет настоящий договор; последующий GET подтверждает доступность созданного объекта.
- Первое самостоятельное действие: написать POST→GET сценарий с выбранными данными и связать запросы только через полученный ID.
- Опора для повторного обращения: знакомые JSON-данные, тело ответа и готовые fixtures; алгоритм генерации ID не нужен.
- Переход: проверить две разные семантики обновления существующей задачи.

## 04. PUT и PATCH оставляют разные состояния

- Что и зачем объяснить: PUT отправляет полную форму и обновляет задачу по её настоящему ID; PATCH меняет только переданные поля. Это разные результаты, которые нужно различить наблюдениями.
- Механизм и порядок: подготовить задачу. Для PUT отправить полную форму по её фактическому ID, проверить ответ и прежний ID. Для PATCH передать выбранные поля, включая явное `false`; перечитать задачу и проверить изменение и сохранность непереданного поля.
- Пример и типичная путаница: при PATCH с `is_done: false` одна проверка статуса не заметит, что значение осталось `true`; проверка только нового значения не заметит потери `title`. Проверить оба факта — значит подтвердить применение и сохранение данных.
- Первое самостоятельное действие: написать отдельные PUT- и PATCH-тесты с собственным исходным состоянием.
- Опора для повторного обращения: известные значения до запроса и фактический ID; смысл PUT/PATCH изучен ранее.
- Переход: DELETE не возвращает объект, поэтому результат подтвердит последующее чтение.

## 05. Удаление проверяется без тела ответа

- Что и зачем объяснить: `204 No Content` означает успешный ответ без тела, а не JSON `null` и не пустой объект. Сам код не доказывает, что удалён нужный ресурс.
- Механизм и порядок: подготовить задачу и сохранить её фактический ID; отправить DELETE; проверить `204` и пустое содержимое; выполнить GET прежнего ID и проверить отсутствие ресурса.
- Пример и типичная путаница: разбор JSON у ответа без тела не проверяет удаление. Последующий GET подтверждает эффект через публичную границу API.
- Первое самостоятельное действие: написать DELETE-тест, который отличает реальное удаление выбранного объекта от пустого ответа без эффекта.
- Опора для повторного обращения: известный объект и его ID; GET разобран ранее.
- Переход: запустить сценарии отдельно и вместе, сохранив независимость функций.

## 06. Независимость тестов и передача дальше

- Что и зачем объяснить: разные тестовые функции независимы, но запросы внутри одного сценария должны видеть изменения друг друга.
- Механизм и порядок: POST→GET использует один временный набор состояния; каждый следующий тест получает своё исходное состояние. Запуск отдельно и в общем файле должен давать одинаковый результат.
- Пример и типичная путаница: если GET после POST не находит задачу, между запросами могло ошибочно создаться новое состояние. Если тест проходит только после другого теста, он зависит от чужих данных.
- Первое самостоятельное действие: запустить один сценарий отдельно, затем все пять вместе и проверить независимость от порядка.
- Опора для повторного обращения: готовые fixtures 56.1; отдельное начальное состояние на функцию и общее состояние запросов внутри неё.
- Переход: базовые тесты закрепляют договор перед переносом обработчиков в `APIRouter` в 57.1.

## 07. Что ученик делает в практике

**Формат и исходная опора:** ручная проектная практика в `tests/test_api.py`. Сохраняем health-тест и используем готовые `api_client`/`api_service` fixtures. До выдачи подтвердить прохождение 56, 56.1 и ручной матрицы блока 11; неподтверждённые знания не считать освоенными. Каждая тестовая функция получает своё состояние, её запросы используют один временный JSON.

Ученик сам выбирает различимые данные и дополняет файл пятью CRUD-сценариями. Приложение, handlers, схемы, сервис и рабочий JSON не меняются.

1. **Чтение:** подготовить задачу с выбранными полями и запросить её через HTTP. Критерий: статус и публичные поля совпадают с ожидаемым объектом, отличая его от соседней задачи.
2. **Создание:** отправить POST, взять ID из ответа и выполнить GET этого ID. Критерий: созданный объект доступен по серверному ID и содержит ожидаемые публичные поля.
3. **Полная замена:** отправить PUT для подготовленной задачи по фактическому ID. Критерий: новые значения видны, ID сохранился.
4. **Частичное изменение:** отправить PATCH с выбранными полями, включая явное `false`, и перечитать задачу. Критерий: переданное значение изменилось, непереданное поле сохранилось.
5. **Удаление:** удалить подготовленную задачу и прочитать прежний ID. Критерий: ответ `204` пустой, ресурс отсутствует.

В каждом сценарии ученик сам выбирает входные данные и записывает локальный критерий до выполнения. Сначала запускает новый тест отдельно, затем весь файл; различающий случай обновлений — прежний ID при PUT и сохранение непереданного поля при PATCH. Совместный запуск подтверждает независимость функций. Матрица отказов, границы query/body/path и полный workflow остаются за пределами этого занятия.

**Итоговый критерий практики:** пять тестов различают чтение, POST, PUT, PATCH и DELETE; проверяют нужные данные и эффекты, используют фактический ID, подтверждают прежний ID при PUT и сохранение непереданных полей при PATCH. Отдельный и общий запуск не зависят от порядка тестов.

**Передача дальше:** приложение сохраняет прежние handlers в `api.py`. В 57.1 их можно переносить под защитой этих тестов; новый router, маршруты или fixtures в текущей практике не создаются.
