## 01. Собираем фактический результат шага 60

- Что и зачем объяснить: README и release notes могут содержать правдоподобные, но устаревшие инструкции. Эталоном для этого занятия является записанный в шаге 60 commit и его проверка, а не текст документов и не более поздняя рабочая ветка.
- Механизм и порядок: сначала объяснить простыми словами: commit — сохранённый снимок файлов, SHA — его уникальный идентификатор, а чистый checkout — отдельная копия проекта на выбранном снимке. Затем сопоставить SHA, окружение и команду установки, исход pytest, результат CLI/API и состояние Postman. Разделить автоматическую проверку через TestClient, внешний запуск API и ручную проверку коллекции: это разные свидетельства.
- Пример и типичная путаница: историческая запись о 134 тестах относится к commit 19e1157, а в release notes другого снимка указано 135. Число тестов само по себе не задаёт истину без конкретного commit. Аналогично, ответ API через PowerShell не доказывает, что Postman-коллекция импортировалась.
- Первое самостоятельное действие: ученик находит в результате шага 60 SHA и фактические исходы проверок, затем сверяет ID с выбранным checkout и отличает завершённое от ожидающего. Критерий — один набор свидетельств для следующих разделов, без переноса числа или результата с другой версии.
- Опора для повторного обращения: рядом с планируемой практикой оставить перечень: проверенный SHA; версия Python и команда установки; фактический результат тестов; CLI/API; импорт и запуск Postman, если они действительно выполнены. При сомнении проверять журнал шага 60 и состояние именно этого checkout.
- Переход к следующему шагу: зафиксированные свидетельства становятся основой для правки README.

## 02. Сверяем README с проверенным запуском

- Что и зачем объяснить: README — воспроизводимый путь к проекту, а не обзор желаемого состояния. Команды должны соответствовать проверенной копии и запускаться из указанной корневой папки тем интерпретатором, куда установлены зависимости.

Перед сверкой назвать, что именно делает команда: CLI принимает команды пользователя, Uvicorn запускает HTTP-сервер, pytest выполняет автоматические тесты, а `/docs` показывает описание API. Проверить, что инструкция не обещает SQL-базу, авторизацию или безопасную параллельную запись.

Критерий — каждая команда, версия и заявленная возможность подтверждена результатом или соответствующим файлом; не появляется инструкция для ещё не реализованной функции.
- Опора для повторного обращения: при проверке команды сверять рабочую папку, выбранный Python и точный файл зависимостей; при описании API возвращаться к фактическому контракту проекта и не расширять список полей за пределы B.

## 03. Проверяем, что команда README доказывает нужный результат

- Что и зачем объяснить: команда тестов и ручной запуск отвечают на разные вопросы. Успешный pytest подтверждает только те гарантии, которые проверяют существующие тесты; запуск API подтверждает, что сервер стартовал и отвечает, но сам по себе не доказывает весь HTTP-контракт.
- Механизм и порядок: для каждой обязательной команды README определить действие, наблюдаемый признак успеха и источник результата. Сопоставить имя тестового файла с реально существующим тестом в целевом commit; затем отдельно отметить ручные команды CLI/API. Не обещать покрытие, которого команда не проверяет.
- Пример и типичная путаница: `tests/test_api.py` может проверять ответ через приложение без запуска Uvicorn; успешный старт Uvicorn не доказывает, что коллекция Postman импортирована. Это разные свидетельства, поэтому в README команда и её значение описываются отдельно.
- Первое самостоятельное действие: ученик проходит тестовую команду и команды запуска, указанные в README, на чистой копии и сверяет фактический исход с формулировками. Критерий — каждое утверждение о запуске подкреплено своим наблюдением; несуществующая команда или тест не заявлены.
- Опора для повторного обращения: для pytest открыть названный файл и сопоставить проверяемое поведение с текстом; для CLI/API выполнить именно записанную команду и зафиксировать фактический результат. Если существующая `docs/test-matrix.md` используется как справочник, сверить её, но не превращать её редактирование или расширение тестов в обязательную B этого занятия.
- Переход к следующему шагу: подтверждённые команды и их результаты дают точные сведения для краткого описания версии.

## 04. Описываем версию без неподтверждённых обещаний

- Что и зачем объяснить: заметка о версии должна называть конкретное состояние проекта и подтверждённые проверки. Commit — снимок исходников; локальный тег — имя для commit; GitHub Release — отдельная публикация. Одно не следует автоматически из другого.
- Механизм и порядок: взять исходный SHA и результаты из шага 60; объяснить, что тег — короткое имя-указатель на commit, а не копия проекта. После изменения README сохранить новый commit по правилам проекта, проверить обновлённые команды в чистой копии и привязать локальную версию к commit, который включает README и эти результаты. Опора — раздел 04 и объяснение commit/tag/release. Ученик проверяет цель commit и занятость тега; не перемещает существующий тег. Результат — локальная версия указывает на точный проверенный commit. GitHub Release и push не выполняются и не заявляются.

Действия идут от свидетельств к изменению инструкции, затем к её проверке и только потом к версии. README принимается, если новый читатель может выполнить команды в указанном порядке и отличить проверенные действия от непроверенных; версия — если локальный тег указывает на тот же commit, который включает README и прошёл относящиеся к нему проверки. Результаты pytest и ручного запуска не взаимозаменяемы. Изменение только README требует повторить инструкции и задокументированные проверки в чистой копии; изменение кода или зависимостей требует повторить также затронутые тесты. Если вход шага 60 отсутствует, планируемая A не превращается в факт и версия не закрепляется. Матрица тестов, release notes и Postman exports могут служить справочными материалами, если они есть, но их редактирование и публикация не являются обязательными действиями этой B.
