## Место в маршруте

Это заключительный шаг главы и передача в главу 4. Здесь связываются три последовательных результата:

- **59.1 → 60:** 59.1 передаёт проверенный workflow одной задачи и ручной сценарий Postman. Занятие 60 воспроизводит их в отдельном чистом checkout, проверяя установку, CLI/API, pytest и импорт экспортов, без повторной реализации CRUD.
- **60 → 60.1:** точный SHA, команды и фактические исходы проверок из 60 становятся входными свидетельствами. По ним приводим README, матрицу, release notes и экспорты в соответствие; полный прогон 60 не повторяем без причины.
- **60.1 → глава 4:** передаём тот же JSON-backed Planner с CLI, FastAPI, сервисом и тестами. Глава 4 сначала приводит структуру API в порядок и вводит настройки с зависимостями; к SQLite переходит позже. Поэтому здесь точно фиксируем ограничения JSON и не описываем БД как уже существующую.

Новый API, слой хранения, тестовая инфраструктура или миграция данных здесь не появляются. Версия должна указывать на подтверждённый результат, а непроверенные действия остаются явно непроверенными.

## 00. Вступление

В прошлой части мы проверяли проект в чистой копии: это позволило увидеть, какие команды и зависимости действительно нужны. Теперь соберём результаты проверки в материалы, по которым следующий человек поймёт, что именно было проверено и где проходят границы продукта.

1. **Точка старта:** есть результат clean checkout из шага 60 и несколько документов, которые уже описывают проект.
2. **Новый вопрос:** как доказать, что README, матрица, заметки и версия относятся к одному и тому же состоянию кода?
3. **Результат:** документы отражают фактическую проверку, а отдельная локальная версия указывает на подтверждённый commit.

Сначала восстанавливаем исходные свидетельства, затем сверяем с ними каждый документ и только после этого закрепляем версию. Так финальная передача сообщает ровно то, что выполнено, и оставляет работу следующей главы на том же приложении.

## 01. Собираем фактический результат шага 60

- Что и зачем объяснить: README и release notes могут содержать правдоподобные, но устаревшие инструкции. Эталоном для этого занятия является записанный в шаге 60 commit и его проверка, а не текст документов и не более поздняя рабочая ветка.
- Механизм и порядок: сопоставить SHA commit, окружение и команду установки, исход pytest, результат CLI/API и состояние Postman. Разделить автоматическую проверку через TestClient, внешний запуск API и ручную проверку коллекции: это разные свидетельства.
- Пример и типичная путаница: историческая запись о 134 тестах относится к commit 19e1157, а в release notes другого снимка указано 135. Число тестов само по себе не задаёт истину без конкретного commit. Аналогично, ответ API через PowerShell не доказывает, что Postman-коллекция импортировалась.
- Первое самостоятельное действие: ученик находит в результате шага 60 точный SHA и реальные исходы проверок, затем отличает завершённое от непроверенного. Критерий — один набор свидетельств для следующих разделов, без переноса непроверенных чисел или действий из старой записи.
- Опора для повторного обращения: рядом с планируемой практикой оставить перечень: проверенный SHA; версия Python и команда установки; фактический результат тестов; CLI/API; импорт и запуск Postman, если они действительно выполнены. При сомнении проверять журнал шага 60 и состояние именно этого checkout.
- Переход к следующему шагу: зафиксированные свидетельства становятся основой для правки README.

## 02. Сверяем README с проверенным запуском

- Что и зачем объяснить: README — воспроизводимый путь к проекту, а не обзор желаемого состояния. Команды должны соответствовать проверенной копии и запускаться из указанной корневой папки тем интерпретатором, куда установлены зависимости.
- Механизм и порядок: сопоставить требования Python и пакетов, команды установки, запуска CLI/API и pytest, адреса /docs и /openapi.json, краткое описание восьми HTTP-операций и правила работы с локальным JSON. Проверить, что инструкция не обещает SQL-базу, авторизацию или безопасную параллельную запись.
- Пример и типичная путаница: установленный в локальной .venv пакет ещё не означает, что он указан в requirements. Успешный запуск из старого окружения не заменяет команду, повторённую в чистой копии.
- Первое самостоятельное действие: после разбора источников ученик проходит разделы README по результатам 60 и исправляет обнаруженные расхождения. Критерий — каждая команда, версия и заявленная возможность подтверждена результатом или соответствующим файлом; не появляется инструкция для ещё не реализованной функции.
- Опора для повторного обращения: при проверке команды сверять рабочую папку, выбранный Python и точный файл зависимостей; при описании API возвращаться к фактическому контракту проекта и не расширять список полей за пределы B.
- Переход к следующему шагу: после README сверяем, что тестовая матрица доказывает именно эти гарантии.

## 03. Согласуем матрицу тестов с существующими проверками

- Что и зачем объяснить: матрица распределяет гарантии по имеющимся тестовым слоям. Она не является обещанием покрытия и не должна превращаться в задание на создание дублирующих тестов.
- Механизм и порядок: для каждой строки сопоставить риск, название проверочного файла и наблюдаемый результат с фактическим тестом в проверенном commit. Сохранить разницу между моделью, storage, сервисом, CLI, HTTP-контрактом и сквозным workflow.
- Пример и типичная путаница: tests/test_api.py подтверждает HTTP-ответы через приложение; это не доказывает запуск Uvicorn. tests/test_workflow.py подтверждает последовательное состояние внутри одного изолированного сценария; это не означает, что каждый тест использует один общий JSON.
- Первое самостоятельное действие: ученик выбирает строки docs/test-matrix.md и сверяет их с существующими тестами и фактическим запуском 60. Критерий — у каждой заявленной гарантии есть корректное место проверки; нет обещания отсутствующего теста, неверного имени файла или числа из другого commit.
- Опора для повторного обращения: если строка утверждает сохранность или отсутствие побочного эффекта, искать именно тест и состояние до/после, а не выводить гарантию только из статус-кода. Не редактировать сами тесты ради совпадения с матрицей в этом занятии.
- Переход к следующему шагу: согласованная матрица и README дают факты для кратких заметок о версии.

## 04. Финализируем release notes и экспорты

- Что и зачем объяснить: release notes описывают состав конкретной версии и её известные пределы. Экспорты Postman — переносимые запросы и environment, а не доказательство, что коллекция была выполнена.
- Механизм и порядок: сверить в docs/release-notes-draft.md состав B, результат проверок из точного checkout, статус импорта/запуска Postman и ограничения JSON. Сверить имена collection/environment и их адрес назначения с фактическими Postman exports. Убедиться, что в экспортах нет личных секретов.
- Пример и типичная путаница: заметка «135 passed» допустима только если это результат запуска указанного commit; фраза «Postman пройден» не подходит, если проверен лишь такой же URL другим клиентом. Ожидающая ручная проверка остаётся ожидающей, пока её действительно не выполнили.
- Первое самостоятельное действие: ученик исправляет только несоответствующие сведения в draft и экспортах. Критерий — заметки описывают результат шага 60, а экспортируемые файлы относятся к Planner API и не содержат секретов; новое доказательство выполнения не приписано документам.
- Опора для повторного обращения: для каждого числа, версии или статуса возвращаться к свидетельству шага 60; для каждого имени файла сверять содержимое и пару collection/environment. Повторный запуск Postman относится к проверке из 60 и добавляется здесь только если сами экспорты пришлось менять.
- Переход к следующему шагу: после согласования содержимого можно присвоить локальное имя проверенной версии.

## 05. Привязываем версию к commit и передаём Planner дальше

- Что и зачем объяснить: commit — точный снимок файлов; локальный Git-тег — имя, указывающее на этот снимок; GitHub Release — отдельная публикация. Тег сам по себе не запускает тесты и не превращает локальное состояние в опубликованный релиз.
- Механизм и порядок: сначала удостовериться, что выбранный commit совпадает с зафиксированным в результате 60 и описанными документами. Проверить существующие теги. Старый CLI-тег v1.0.0 не перезаписывать; для API можно использовать planner-api-v1.0.0, если имя свободно. Если документы или экспорты изменились после проверки 60, включить их в отдельный commit и проверить затронутые команды и материалы передачи; тегировать только commit, для которого результат и нужные проверки подтверждены.
- Пример и типичная путаница: если HEAD отличается от SHA из 60, тег на HEAD сам по себе не подтверждает результат. Если API-тег уже существует и указывает на целевой SHA, достаточно сверить это соответствие; если он указывает на другой commit, не перемещать и не переписывать его молча, а отметить это как незакрытую часть приёмки.
- Первое самостоятельное действие: ученик сверяет commit и существующие имена, затем применяет выбранный свободный API-тег. Критерий — проверка показывает точный целевой SHA и сохранность прежнего CLI-тега. Создание GitHub Release и push не являются обязательными действиями.
- Опора для повторного обращения: перед закреплением повторно прочитать SHA шага 60 и проверить, на какой commit указывает тег. Если менялись только поясняющие документы, их согласованность подтверждается сопоставлением с уже полученными результатами; если менялись команды или зависимости, повторить затронутую проверку перед тегом.
- Переход к следующему шагу: следующая глава получает тот же JSON Planner и начинается с замены способа хранения; SQL и миграции не входят в текущую передачу.

## 06. Что мы будем делать в практике

**Формат и исходная опора:** ручная практика на чистом checkout и материалах передачи, прошедших проверку в занятии 60. Начинаем с точного SHA и записанных результатов clean install, CLI/API, pytest и Postman. Старую рабочую папку и её пользовательские данные не используем как подмену контрольного checkout.

Общий результат — согласованный комплект материалов и локальная отметка версии, соответствующие одному проверенному commit. Существующее поведение Planner сохраняется; новый runtime или проверочный слой не создаётся.

1. **Восстановить baseline передачи:** исходное состояние — результаты проверки шага 60 и точный commit; объект исследования — список фактически выполненных проверок и команда установки; опора — блок 01 и предыдущий навык чтения журнала/commit. Ученик самостоятельно отделяет выполненное от ожидающего. Наблюдаемый результат — записаны точный SHA и подтверждённые результаты; старые числа и непроведённый Postman-сценарий не выданы за текущие.
2. **Сверить README и тестовую матрицу:** исходное состояние — существующие README и docs/test-matrix.md; объект изменения — команды запуска, ограничения продукта и строки гарантий; опора — блоки 02–03 и фактическая проверка из 60. Ученик сам находит расхождения, после обращения к описанию контракта исправляет только их. Наблюдаемый результат — команды соответствуют checkout, а каждая гарантия матрицы ведёт к существующему проверочному слою и результату.
3. **Согласовать заметки и экспорты:** исходное состояние — docs/release-notes-draft.md, collection и environment; объект изменения — описание версии, результаты и ограничения; опора — блок 04. Ученик выбирает формулировку по подтверждённым свидетельствам и сверяет экспортные файлы. Наблюдаемый результат — один набор точных release notes и экспортов без неподтверждённых заявлений и личных секретов.
4. **Закрепить локальную версию:** исходное состояние — итоговые файлы и SHA проверенного commit; объект изменения — локальное имя версии, указывающее на этот commit; опора — блок 05 и объяснение различия commit/tag/release до применения. Ученик сам проверяет занятость имён и выбирает API-тег, не затрагивая CLI-тег. Наблюдаемый результат — тег ссылается на подтверждённый commit; внешняя публикация не заявляется.

Последовательность уменьшает помощь: сначала ученик собирает свидетельства о выполненной проверке, затем сверяет документы по готовым требованиям, после чего самостоятельно связывает версию с commit. Итог практики принимается, когда README, матрица, заметки и экспорты описывают одну и ту же проверенную версию и ни одна ссылка на тест или результат не выходит за имеющиеся доказательства. При любом изменении инструкции или экспорта повторно проверяется соответствующая часть; повтор полного тестового набора нужен только если изменение затрагивает продуктовый код или зависимости. Если подтверждения шага 60 отсутствуют, независимую сверку файлов можно подготовить, но нельзя утверждать результат тестов, финализировать относящиеся к нему заметки или создавать тег; препятствие — отсутствие проверенного SHA и фактических результатов, включая статус Postman.
