## 00. Вступление

Отдельные тесты уже отвечают на вопросы о маршрутах, ошибках и прикладных гарантиях. Теперь важно увидеть, как эти операции ведут себя вместе, когда один запрос меняет состояние, следующий читает его результат, а отказ не должен прервать историю.

1. **Точка старта:** существующие проверки CRUD и слоёв Planner, TestClient с изолированным JsonStorage и сохранённая коллекция запросов.
2. **Новый вопрос:** остаётся ли одна задача согласованной через последовательные запросы и сохраняется ли контрольная запись после ожидаемого отказа?
3. **Результат:** один workflow проходит от создания двух задач до удаления главной; TestClient и Postman подтверждают его на разных источниках состояния.

Связь простая: сначала используем уже проверенные операции, затем удерживаем общий id и состояние между запросами, после чего сравниваем ответ, повторное чтение и контрольную задачу. Это подготовит передачу проекта без повторной реализации CRUD.

## 01. Изолированная проверка и workflow

- Что и зачем объяснить: отдельный тест локализует одно правило; workflow проверяет временную связь нескольких правил на одной истории. Он дополняет тесты операций и границ, но не заменяет их.
- Механизм и порядок: один сценарий задаёт исходное состояние, выполняет запросы по порядку и наблюдает состояние после каждого значимого перехода. Ожидаемый отказ может быть корректным шагом успешного теста.
- Пример и типичная путаница: на примере бронирования показать разницу между проверкой отдельной отмены и маршрутом «создали → прочитали → изменили → отменили». Не объявлять длинный сценарий заменой независимых проверок.
- Первое самостоятельное действие: по короткой истории бронирования ученик отмечает, какие результаты требуют общего состояния, а какие уже подтверждаются отдельным тестом.
- Переход: для общей истории нужно понять границу состояния теста и запроса.

## 02. Одно состояние на весь тест

- Что и зачем объяснить: запросы одного workflow должны видеть изменения друг друга, но следующий тест должен начинаться с независимых данных.
- Механизм и порядок: использовать готовые api_service/api_client fixtures. Function scope задаёт отдельный JsonStorage на тест; клиент закрывается, затем восстанавливается прежний app.state.planner. Между запросами одного теста файл не пересоздаётся.
- Пример и типичная путаница: сравнить один тест с несколькими запросами к одной временной папке и два отдельных теста с разными папками. Не создавать новую fixture и не очищать JSON после каждого HTTP-запроса.
- Первое самостоятельное действие: ученик по готовой последовательности fixtures определяет, где создаётся тестовый сервис, сколько запросов разделяют его файл и когда состояние сбрасывается.
- Опора для повторного обращения: имя fixture, область действия, путь временного JSON и порядок закрытия клиента/восстановления state; характерная ошибка — ожидать чистое состояние на каждом request.
- Переход: при общем состоянии нужно прослеживать одну конкретную запись.

## 03. Фактический id и контрольная задача

- Что и зачем объяснить: id создаёт сервис, поэтому продолжение сценария связывается с id из ответа POST, а не с номером строки или предполагаемым порядком.
- Механизм и порядок: создать контрольную и главную задачи; сохранить оба фактических id; обращаться к ним через item-маршрут. Контрольная запись показывает побочный эффект, который общее число задач может скрыть.
- Пример и типичная путаница: на примере двух посылок показать, что неизменность общего количества не доказывает, что изменили правильную посылку. Не считать id постоянным счётчиком без пропусков.
- Первое самостоятельное действие: по двум готовым ответам POST выбрать id главной и контрольной записи для следующих запросов.
- Опора для повторного обращения: брать id из ответа создания, после изменения снова читать именно этот item; не подставлять заранее известное число и не полагаться на позицию в списке.
- Переход: id связывает запросы, а сохранность перехода надо доказывать несколькими наблюдениями.

## 04. Ответ, повторное чтение и stats

- Что и зачем объяснить: HTTP-ответ доказывает статус и публичную форму результата; новый GET проверяет сохранённое состояние; контрольная запись выявляет изменение соседа; stats показывают общий источник.
- Механизм и порядок: после POST, PUT и PATCH читать фактический id, сверять изменённые и сохранённые поля, состояние контрольной задачи и total/open/done. После DELETE проверять пустой 204 отдельно от последующего 404.
- Пример и типичная путаница: чек об операции не заменяет чтение обновлённого заказа. Список с фильтром не равен общей stats, а публичный ответ TaskRead не содержит tags.
- Первое самостоятельное действие: на готовом изменении ученик выбирает наблюдение, которое подтвердит ответ, сохранение главной записи и неизменность соседа.
- Опора для повторного обращения: статус и body ответа → новый GET → контрольная задача → общая stats; для 204 не читать JSON. Критерий каждой проверки ограничивается уже завершённым действием.
- Переход: следующий шаг показывает, как отказ входит в ту же последовательность без повреждения состояния.

## 05. Ожидаемый отказ и продолжение истории

- Что и зачем объяснить: 422 может быть правильным ответом на невалидный PATCH; workflow должен доказать отсутствие изменения и продолжить валидными действиями.
- Механизм и порядок: сохранить наблюдаемое состояние существующей главной и контрольной записей, отправить один заведомо невалидный PATCH, проверить 422 и повторно прочитать состояние, затем продолжить успешным PATCH.
- Пример и типичная путаница: не считать ожидаемый 422 падением приложения и не ограничиваться статусом. Отказ handler не должен стать условием, которое скрывает последующие проверки.
- Первое самостоятельное действие: ученик выбирает подтверждения до и после одного ожидаемого отказа и объясняет, как они выявляют частичный эффект.
- Опора для повторного обращения: корректный существующий id и неверное поле дают одну причину 422; после ответа повторно проверить главную задачу, контрольную запись и stats. Не добавлять сюда новый контракт ошибок.
- Переход: ту же историю нужно подтвердить на тестовой и рабочей HTTP-границе, не смешивая их данные.

## 06. TestClient и Postman

- Что и зачем объяснить: TestClient вызывает настоящее приложение через ASGI без отдельного Uvicorn; Postman обращается к работающему серверу и рабочему JSON. Это разные подтверждения.
- Механизм и порядок: автоматический workflow использует собственный tmp_path и запускается отдельно/в составе набора. Ручной сценарий начинает с фактической stats N/O/D, использует id из POST и считает изменения относительно baseline, не очищая файл.
- Пример и типичная путаница: не считать TestClient сетевым запросом и не использовать общий JSON в автотесте. Не считать список с limit полной статистикой.
- Первое самостоятельное действие: по baseline и планируемому изменению ученик предсказывает направление изменения total/open/done, затем сверяет фактическое значение.
- Опора для повторного обращения: два новых открытых элемента дают N+2/O+2/D; PUT главной задачи в done — N+2/O+1/D+1; PATCH с false возвращает N+2/O+2/D; удаление главной — N+1/O+1/D. В Postman значения и id берутся из реального запуска; скрипты коллекции не являются обязательной предпосылкой.
- Переход: практика собирает эти доказательства в порядке одной истории.

## 07. Что мы будем делать в практике

**Формат и исходная опора:** manual. Начинаем с существующего FastAPI-приложения, CRUD, api_service/api_client fixtures и сохранённой коллекции Postman. В код добавляется только новый workflow-тест.

1. **Создадим две задачи в одном тестовом состоянии:** исходно готовая function-scoped fixture даёт пустой временный JSON. По опорам блоков 02–03 ученик самостоятельно использует POST и сохранит фактические id главной и контрольной задач; результат — два ответа 201 с публичными полями и одно общее состояние теста.
2. **Прочитаем и полностью изменим главную:** исходно обе задачи созданы и имеют полученные id. На основе блоков 03–04 ученик использует GET и PUT, самостоятельно выбирает id из POST и проверяет обновлённую публичную запись, прежний id, контрольную задачу и соответствующую stats.
3. **Проверим ожидаемый отказ:** исходно главная задача успешно прошла PUT и доступна по своему id. По опоре блока 05 ученик отправляет один невалидный PATCH; после 422 повторно проверяет запись, соседа и stats. Критерий шага — состояние до и после отказа совпало.
4. **Применим частичное изменение:** исходно главная задача завершена PUT, а ожидаемый отказ не изменил её. После обращения к блокам 04–05 ученик передаёт только is_done=false и сверяет, что false применён, title/priority не изменились, а stats отражают переход.
5. **Удалим главную задачу:** исходно главная задача снова открыта, контрольная существует. По опоре блока 04 ученик вызывает DELETE, проверяет пустой 204 и GET с 404; контрольная задача остаётся доступной, stats учитывают только оставшийся ресурс.
6. **Повторим историю через Postman:** исходно рабочий JSON может содержать задачи, поэтому сначала читается baseline N/O/D. По опоре блока 06 ученик повторяет действия с id из фактических ответов; относительные stats соответствуют каждому переходу, исходные записи не очищены и контрольная задача сохранена.
7. **Проверим независимость теста:** исходно workflow-тест завершает историю на собственном временном JSON. Опираясь на прежний pytest и блок 02, ученик запускает workflow отдельно, затем вместе с набором; результат не зависит от порядка и рабочий JSON не затронут.

Эти шаги используют уже созданные операции и fixtures: ученик сам связывает их общей историей, обращается к опоре у соответствующего механизма и после каждой записи проверяет только текущий переход. Итог подтверждает B, если один фактический id проходит все этапы, ожидаемый отказ не меняет состояние, сосед сохранён, а TestClient и Postman показывают договор на своих источниках данных.

Следующая передача — чистое воспроизведение проекта по README. Там проверяются установка, запуск, полный набор и импорт коллекции; повторно реализовывать workflow не нужно.
