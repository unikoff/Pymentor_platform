## 00. Вступление

На API уже проверяли допустимые входы и последствия отказа. Теперь посмотрим на обычное чтение списка: несколько параметров меняют выдачу, а документация сообщает клиенту, какие операции и формы ответа заявлены.

1. **Точка старта:** GET /tasks уже умеет фильтровать, сортировать и ограничивать результат; TestClient и изолированные fixtures знакомы по прежней работе.
2. **Новый вопрос:** как убедиться, что параметры применились в верном порядке, общий источник и stats не изменились, а OpenAPI описывает те же формы и статусы?
3. **Результат:** целевые проверки tests/test_contract.py подтверждают query-контракт и существенную форму опубликованной спецификации.

Маршрут идёт от одного управляемого набора задач к наблюдаемой HTTP-выдаче, затем к описанию API. Сначала создаём данные, достаточные для различения порядка действий и default limit; затем отдельно сверяем общую статистику и документированные схемы. Спецификация описывает контракт, а запросы показывают фактическое поведение.

## 01. Query управляет чтением списка

- Что и зачем объяснить: освежить назначение query-параметров в GET /tasks и связь HTTP-запроса с уже готовым select_tasks. Этот шаг проверяет существующее поведение, а не добавляет новый алгоритм.
- Механизм и порядок: клиент передаёт is_done, sort_desc и limit через params; приложение разбирает значения, применяет defaults и передаёт параметры сервису. Отсутствующий фильтр is_done=None отличается от явного is_done=False; sort_desc по умолчанию выключен, HTTP-limit по умолчанию равен 10.
- Пример и типичная путаница: список без фильтра включает оба статуса; фильтр False оставляет только открытые задачи. Не смешивать None с False и не путать ограниченный ответ списка с ограничением всей статистики.
- Первое самостоятельное действие: по знакомому запросу и ожидаемым данным определить, какие параметры присутствуют, какие defaults сработают и какая группа задач останется до сортировки.
- Опора для повторного обращения: значения defaults, смысл None/False и назначение каждого query-параметра; возвращаться к ней перед построением ожидаемого набора id.
- Переход к следующему шагу: чтобы проверить default limit и порядок операций, нужен тестовый набор больше десяти записей.

## 02. Набор данных должен различать правила

- Что и зачем объяснить: показать, почему тест на одном-двух объектах не доказывает default=10, порядок filter/sort/limit или независимость stats.
- Механизм и порядок: внутри одного function-scoped теста подготовить через существующий api_service более десяти задач; сохранить фактические id ответов/объектов, отметить одну задачу завершённой и зафиксировать stats и состояние тестового JSON до query. Все запросы одного теста используют один fixture-файл; другой тест начинает с отдельного состояния.
- Пример и типичная путаница: разместить завершённую задачу так, чтобы фильтрация до limit давала другой результат, чем limit до фильтра. Не рассчитывать на жёсткий id из чужого теста и не подготавливать рабочий data/tasks.json.
- Первое самостоятельное действие: выбрать данные, на которых видны оба статуса, больше десяти записей, разница направлений сортировки и влияние limit; записать фактические id до проверки.
- Опора для повторного обращения: какие данные созданы в текущем тесте, какой id завершён и какие исходные stats/байты нужно сравнить после чтения.
- Переход к следующему шагу: набор теперь позволяет проверить не только итоговый список, но и порядок его получения.

## 03. Порядок filter → sort → limit виден по результату

- Что и зачем объяснить: связать выборку сервиса с наблюдаемым списком в HTTP-ответе и показать, что каждое преобразование применяется к результату предыдущего.
- Механизм и порядок: сначала оставить записи подходящего статуса, затем упорядочить выбранные записи по id в нужном направлении, затем взять limit. GET-ответ остаётся проекцией выбранных задач, а не новым хранилищем.
- Пример и типичная путаница: если завершённая задача расположена среди последних id, фильтр до limit должен вернуть ожидаемые открытые id даже при убывающей сортировке и limit=1. Нельзя проверять только число элементов: разные ошибочные порядки могут дать одинаковую длину.
- Первое самостоятельное действие: сравнить обычную выдачу без query, выборку каждого статуса и различающий запрос с фильтром, обратным порядком и малым limit; ожидания вывести из текущего тестового набора.
- Опора для повторного обращения: таблица фактических id по статусу; порядок фильтрации, сортировки по id и ограничения результата; отличие списка от общего источника.
- Переход к следующему шагу: после результата выборки отдельно проверяются defaults, граничные значения limit и отсутствие побочного эффекта чтения.

## 04. Defaults и границы не меняют общий источник

- Что и зачем объяснить: проверить параметры списка целиком и развести три наблюдения — ответ GET /tasks, общую статистику и сохранённый JSON.
- Механизм и порядок: запрос без параметров использует is_done=None, sort_desc=False и limit=10; limit принимает значения от 1 до 50 включительно. Для limit 0, 51 и нечислового значения ожидается 422 до вызова полезной операции. Stats считает весь источник и не зависит от фильтрации или обрезания списка.
- Пример и типичная путаница: при одиннадцати задачах default-ответ содержит десять, но stats по-прежнему считает одиннадцать. Успешный GET и ошибка в query не должны переписывать файл или сохранять порядок ответа.
- Первое самостоятельное действие: проверить default-выдачу, limit=1 и limit=50, затем значения за границами и неверный тип; сравнить stats и байты тестового JSON до и после чтений.
- Опора для повторного обращения: defaults HTTP, включённые границы 1/50, ожидаемый status/поле limit при ошибке и исходный snapshot статистики/файла.
- Переход к следующему шагу: поведение маршрутов доказано запросами; теперь можно проверить, что API объявляет клиенту в OpenAPI.

## 05. OpenAPI фиксирует формы схем

- Что и зачем объяснить: показать, как зарегистрированные Pydantic-схемы становятся документированной формой входов и ответов, и зачем выбирать устойчивые поля для проверки.
- Механизм и порядок: получить /openapi.json через тестовый клиент, найти components.schemas и сверить значимые required-поля: TaskCreate требует title и priority; TaskUpdate требует title, priority и is_done; TaskRead содержит четыре публичных поля; TaskPatch не требует полей.
- Пример и типичная путаница: документация может показать, что поле обязательно, но сама по себе не доказывает, что запрос сохранил задачу. TaskRead не включает tags, хотя tags остаются в доменной записи. Не проверять весь JSON или внутренние ссылки $ref как неизменяемый текст.
- Первое самостоятельное действие: составить соответствие «схема → роль → обязательные поля» и выбрать минимальные assertions, подтверждающие контракт без фиксации случайной структуры документа.
- Опора для повторного обращения: четыре схемы, их назначение и required-набор; отличие публичного ответа от полной доменной Task.
- Переход к следующему шагу: после форм схем проверить адреса, параметры и статусы, зарегистрированные приложением.

## 06. Операции и статусы в спецификации

- Что и зачем объяснить: развести path-шаблоны и операции method+path; проверить важные HTTP-параметры в OpenAPI и сопоставить документ с уже работающими запросами.
- Механизм и порядок: в документе четыре path-шаблона — /health, /tasks, /tasks/{task_id}, /stats — и восемь операций. Сверить методы и статусы: GET /health, GET /tasks, GET /tasks/{task_id} и GET /stats отвечают 200; POST /tasks — 201; PUT и PATCH item — 200; DELETE item — 204. Для списка проверить параметры: is_done необязателен, sort_desc имеет default=False, limit имеет default=10 и границы 1–50; item id ограничен положительными значениями.
- Пример и типичная путаница: /tasks обслуживает GET и POST, а item path — GET/PUT/PATCH/DELETE; это восемь операций, но не восемь разных адресов. OpenAPI сообщает ожидаемые статусы 200/201/204, а проверка запросами подтверждает фактическое поведение.
- Первое самостоятельное действие: по документу построить компактное соответствие method+path → успешный status, затем сравнить выбранные случаи с тестами предыдущих шагов.
- Опора для повторного обращения: четыре path-шаблона, восемь методов, успешные статусы, query-defaults и ограничения; при расхождении начать с зарегистрированного маршрута и точного параметра.
- Переход к практике: значимые части спецификации и ответы уже имеют отдельные критерии; теперь проверки можно собрать в один целевой проход без полного snapshot документа.

## 07. Что мы будем делать в практике

**Формат и исходная опора:** manual; существующие api_client/api_service fixtures и тесты границ из tests/test_contract.py. Начинаем с тестового JsonStorage, не с рабочего файла и не с нового приложения.

1. **Подготовим различающий набор задач:** в одном тесте создадим более десяти задач, одну завершим и запишем фактические id; используем изученные fixtures и сервис. Результат — достаточно данных для default limit, обоих статусов и различения порядка операций.
2. **Проверим query-выдачу:** самостоятельно сопоставим defaults, фильтр, оба направления сортировки и limit с ожидаемыми id; отдельно проверим включённые границы и ошибочные значения limit. Результат — HTTP-ответ подтверждает filter → sort → limit и корректные 422 без зависимости от фиксированных id.
3. **Подтвердим отсутствие записи при чтении:** сравним stats всего источника и сохранённый тестовый JSON до/после query. Результат — выдача списка не ограничивает stats и не меняет файл.
4. **Сверим OpenAPI:** проверим required-наборы четырёх схем, query-параметры, path-шаблоны, восемь операций и успешные статусы; сопоставим документацию с уже работающим поведением. Результат — проверена существенная форма контракта без сравнения полного документа или порядка его ключей.

Пройденные блоки дают теорию о query и OpenAPI, а предыдущие занятия обеспечивают готовые маршруты и изоляцию тестов. При наличии уже готовой проверки сохраняем её и усиливаем только конкретный пробел, не дублируя assertions старого занятия 65. Итог подтверждает B: тесты query и спецификации проходят отдельно и вместе, stats и JSON остаются прежними, продуктовые routes и schemas не изменяются.
