## 00. Вступление

Ранее мы проверяли неверный запрос и убеждались, что данные не испортились. Теперь проверим обычное чтение списка. Адрес GET `/tasks` может получить дополнительные параметры после `?`: они выбирают задачи, задают порядок и ограничивают число строк. Отдельно посмотрим, как API описывает свои адреса и формы данных.

1. **Точка старта:** маршрут GET `/tasks` и тестовый клиент заданы предыдущими занятиями; перед практикой проверяем их наличие в проекте.
2. **Новый вопрос:** как отличить правильный порядок отбора от ошибочного и проверить, что чтение не меняет сохранённые задачи?
3. **Результат:** собственные тесты в `tests/test_contract.py` подтверждают выдачу списка и соответствие OpenAPI маршрутам и схемам.

Сначала на маленьком списке разберём один параметр за раз, затем подготовим собственные тестовые задачи и проверим их фактические id в HTTP-ответе. После этого отдельно сравним общий счётчик и файл, а в конце прочитаем описание API. OpenAPI показывает заявленный контракт; только запрос к маршруту показывает фактический ответ.

## 01. Параметры после `?` уточняют запрос списка

- Что объяснить: часть адреса после `?` называется query-параметрами. Для GET `/tasks` это `is_done`, `sort_desc` и `limit`; они меняют только выдачу списка.
- Механизм: если `is_done` не передан, подходят задачи обоих статусов. В адресе `GET /tasks?is_done=false` параметр после `?` оставляет только незавершённые задачи. Если не передать `sort_desc`, порядок по умолчанию возрастающий; если не передать `limit`, вернутся первые 10 подходящих задач.
- Различающий пример: в списке есть открытые задачи A и C и завершённая B. Без `is_done` видны все три; с `is_done=false` остаются A и C. Отсутствующий параметр значит «не фильтровать», а `false` значит конкретное значение статуса.
- Первое действие ученика: для двух готовых адресов GET выписать, какие параметры переданы и какие defaults применятся. Критерий: ученик верно предсказывает, какие записи допускаются к следующему шагу.
- Опора: таблица «параметр / значение по умолчанию / эффект». Не вводить Python `None` как отдельную тему; достаточно объяснить отсутствие параметра на уровне запроса.
- Переход: чтобы проверить ограничение по умолчанию и порядок операций, понадобится больше десяти собственных записей.

## 02. Подготовим данные, на которых видна ошибка порядка

- Что объяснить: проверка должна отличать правильный алгоритм от типичной ошибки. Если все задачи одинаковы или их меньше десяти, такой набор ничего не говорит о фильтре или стандартном лимите.
- Подготовка: в одном тесте через существующий `api_service` создать 12 задач и записать возвращённые id. Оставить первые 11 открытыми и завершить только задачу с наибольшим id. Использовать уже имеющийся тестовый JSON; рабочий `data/tasks.json` не трогать.
- Различающий пример: запросить только открытые задачи с убывающей сортировкой и `limit=1`. Верный порядок сначала отбрасывает завершённую задачу, затем возвращает наибольший из открытых id. При ошибочном порядке `limit → filter` сначала выбирается завершённая задача с наибольшим id, поэтому после фильтрации ответ пуст. Так два порядка дают разные наблюдаемые ответы.
- Первое действие ученика: выписать фактические id и статусы своих 12 задач, заранее назвать наибольший открытый id и предсказать ответ при обоих порядках. Критерий: ожидаемый ответ — наибольший открытый id; пустой список однозначно выявляет ошибочный порядок.
- Опора: таблица id/статус, снимок `/stats` и байты тестового файла до запросов. Fixtures изолируют каждый тест, поэтому тест не зависит от порядка запуска.
- Переход: теперь сравним предсказание с реальным ответом.

## 03. Проверим порядок «фильтр → сортировка → лимит»

- Объяснить на коротком списке: сначала убрать записи неподходящего статуса, затем отсортировать оставшиеся по id, потом взять первые `limit`. Каждый шаг получает результат предыдущего.
- Независимый пример: id `2` (готово), `5` (открыта), `9` (открыта). Запрос открытых задач по убыванию с `limit=1` возвращает id `9`. Так проверяется конкретный id, а не только длина ответа.
- Первое применение: ученик пишет запросы без фильтра, с каждым статусом и с обратным порядком. Затем сам составляет один запрос, где неверный порядок дал бы другой id. Критерий: объясняет каждый переход от исходных id к итоговому ответу.
- Типичная ошибка: проверять лишь, что ответ содержит одну задачу. Любой алгоритм может вернуть одну строку; ожидаемый id различает правильный порядок.
- Опора: таблица созданных id и промежуточные множества после фильтра и сортировки. Не использовать фиксированные id в assertions.
- Переход: проверим defaults, допустимые границы и то, что запрос чтения не меняет источник.

## 04. Defaults, границы и общая статистика

- Развести три результата: GET `/tasks` возвращает часть списка; GET `/stats` считает весь набор; JSON-файл хранит исходные задачи. Фильтр и `limit` не должны уменьшать общий счётчик или менять файл.
- Механизм: без параметров список идёт по возрастанию, включает оба статуса и ограничен 10 строками. `limit` допускает значения от 1 до 50 включительно; значения 0, 51 и текст вместо числа должны дать 422.
- Пример: при 11 задачах обычный GET возвращает 10, а `/stats` по-прежнему сообщает 11. Сравнение файла до и после чтения подтверждает отсутствие записи.
- Первое действие: проверить без параметров, `limit=1`, `limit=50`, затем `0`, `51` и текст. После каждого запроса проверить статус и ожидаемые id; в конце сравнить stats и тестовый JSON с исходными. Критерий: успешные и ошибочные чтения не меняют сохранённые задачи.
- Опора: паспортные defaults и границы; снимки stats/файла, сделанные до первого запроса.
- Переход: реальные ответы проверены; теперь сравним их с описанием API.

## 05. OpenAPI описывает формы данных

- Сначала объяснить: OpenAPI — автоматически сформированное описание того, какие адреса, параметры и формы данных предлагает API. Оно помогает клиенту понять договор, но не доказывает, что запрос действительно работает.
- Показать один путь: запросить `/openapi.json` тестовым клиентом, открыть `components.schemas` и найти описание `TaskCreate`. Затем объяснить `required`: это имена полей, которые описание считает обязательными.
- Самостоятельное действие: ученик сверяет `required` у `TaskCreate` (title, priority), `TaskUpdate` (title, priority, is_done), `TaskRead` (публичные поля id, title, priority, is_done) и `TaskPatch` (нет обязательных полей). Критерий: может связать каждую схему с назначением и не включает внутренний `tags` в публичный ответ.
- Различие: OpenAPI показывает объявленное требование; HTTP-тест отдельно проверяет реальный ответ. Не сравнивать весь JSON документа: порядок и служебные ссылки могут меняться.
- Опора: таблица «схема / где используется / обязательные поля». Сверять структурированные поля, а не текст `$ref`.
- Переход: после форм данных проверим, какие адреса и методы зарегистрированы.

## 06. Адреса, методы и успешные статусы

- Объяснить различие: путь `/tasks` один, но с методом GET он читает список, а с POST создаёт запись. Поэтому считаем пары «метод + путь», а не только адреса.
- По OpenAPI ученик находит четыре пути `/health`, `/tasks`, `/tasks/{task_id}`, `/stats` и восемь операций. Затем сверяет успешные статусы: GET — 200, POST `/tasks` — 201, PUT/PATCH задачи — 200, DELETE — 204. Для GET `/tasks` находит необязательный `is_done`, defaults `sort_desc=false`, `limit=10` и пределы 1–50.
- Первое действие: заполнить таблицу «метод + путь → успешный код» по документу и сверить один GET и один изменяющий запрос с HTTP-проверками предыдущих занятий. Критерий: различает объявленный код и реально полученный код.
- Типичная путаница: один путь не означает одну операцию; OpenAPI описывает зарегистрированное, а не фактически проверенное поведение.
- Опора: таблица маршрутов, методов, кодов и параметров из паспорта. При расхождении фиксировать точную пару метода и пути.
- Переход: соберём отдельные наблюдения в самостоятельные проверки.

## 07. Что мы будем делать в практике

**Формат и исходная опора:** manual; существующие pytest-fixtures `api_client` и `api_service` в `tests/test_contract.py`. Fixture — готовый для теста объект: клиент отправляет HTTP-запросы, сервис подготавливает данные; тест получает изолированный JSON. До работы проверить их наличие. Рабочий файл и приложение не изменяются.

1. **Подготовим собственные данные:** через имеющийся `api_service` создать 12 задач и получить их реальные id; оставить первые 11 открытыми, завершить только задачу с максимальным id. Результат: таблица id/статус и начальный снимок stats и JSON; рабочий файл не затронут.
2. **Проверим один различающий запрос:** отправить GET только для открытых задач с `sort_desc=True` и `limit=1`. Результат: правильный `filter → sort → limit` возвращает наибольший открытый id; при ошибочном `limit → filter` ответ пуст. Проверка использует id созданных задач и различает эти два результата.
3. **Проверим defaults и границы:** сравнить ответ без параметров с ожидаемыми десятью id; проверить `limit=1`, `50`, `0`, `51` и текст вместо числа. Результат: успешные случаи возвращают ожидаемые id, ошибочные дают 422.
4. **Проверим отсутствие побочного эффекта:** запросить `/stats` до и после выборок и сравнить байты тестового JSON. Результат: stats считает все записи, файл не изменён.
5. **Сверим OpenAPI:** проверить четыре схемы, четыре пути, восемь операций, статусы и query-параметры; сопоставить выбранные случаи с фактическими запросами. Результат: проверены устойчивые поля контракта без snapshot всего документа.

Объяснение идёт от знакомого адреса к одному параметру, затем к различающему набору, проверке порядка, общим данным и описанию API. Каждый новый термин получает короткое объяснение и пример до самостоятельного шага. Практика накапливает доказательства B: точные id подтверждают выборку, сравнения подтверждают неизменность stats/JSON, а структурные assertions сверяют объявленный контракт с ответами. Существующие проверки сохраняются; добавляются только отсутствующие утверждения. Маршруты и схемы приложения не меняются.
