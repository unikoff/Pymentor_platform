## Место в маршруте

Занятие впервые подключает HTTP-чтение к тому же Planner и тому же настроенному JSON-файлу, которыми пользуется CLI. Оно не создаёт новые правила хранения или подсчёта: FastAPI получает существующий сервис, вызывает его операции чтения и формирует согласованный публичный ответ.

На входе используем B нового шага 47.1: созданные в 47 `app/api.py` и `GET /health`, запускаемый из корня Uvicorn, проверенные `/docs` и `/openapi.json`, запрос в Postman Local и подтверждение, что CLI остаётся отдельным входом. Это планируемое состояние новой последовательности, пока не подтверждённое прохождением готового занятия; открытый вопрос точного snapshot A после исторического 45 сохраняется. Внутри 48 идём постепенно: от знакомых CLI и JSON через получение сервиса в обработчике (`Request` и `app.state.planner`), затем к публичной проекции Task, коллекции и общей статистике. Следующее занятие 48.1 использует ту же точку доступа и `_task_read_data`, берёт реальный id из списка и добавляет `Path(gt=0)`/`Annotated`, item-чтение и различение 422/404; здесь заканчиваем на коллекции и статистике.

## Точка A: подтверждённая опора

- Уже изучено: журнал StudyHub подтверждает работу с JsonStorage(path), чтение актуальных данных, PlannerService, list_tasks, get_statistics, build_service и CLI в предыдущей части учебного маршрута. Не считаем прежние занятия 46–53 доказательством прохождения новой переработанной последовательности HTTP.
- Состояние проекта: требуемая исходная опора — существующие Task, PlannerService, JsonStorage и CLI с фабрикой build_service(). Доступный снимок до HTTP-изменений связан с историческим занятием 44; точного SHA после требуемого исторического занятия 45 в доступных refs нет. Снимок 44 и последующий diff дают условное подтверждение, но не заменяют отсутствующий снимок A.
- Планируемая опора или неясность: по новому маршруту перед занятием должны быть созданы app/api.py, GET /health и проверка Swagger/Postman из 47/47.1. Эти результаты пока подтверждены только паспортами. До реализации этого плана нужно сверить фактические файлы и закрыть вопрос исходного снимка A; иначе нельзя считать API-состояние уже существующим или выдавать историческую гипотезу за установленный факт.

## Точка B: результат занятия

- Ученик сможет объяснить: почему CLI и Uvicorn не делят память одного процесса, как оба получают актуальные данные через настроенный JsonStorage, что хранится в app.state.planner и почему данные нельзя загружать в общий список при импорте.
- Ученик сможет сделать: подключить в app/api.py существующий сервис через app.state.planner, получить его в обработчиках через Request, добавить GET /tasks и GET /stats.
- Результат в проекте: два новых GET-маршрута читают прежний Planner. Список выдаёт только id, title, priority, is_done; статистика использует get_statistics(), представляя all как total, а open и done сохраняя.
- Как подтвердим: HTTP-ответы совпадают с фактическим выводом CLI; после последовательного изменения через CLI оба GET показывают актуальные данные без перезапуска Uvicorn и после его перезапуска. GET не изменяют JSON, /health и CLI продолжают работать.

## Границы и передача дальше

- Пока не требуем: path-параметр и GET /tasks/{task_id}, Path, Annotated, обработку 404/422, query-фильтры, сортировку и limit, POST или Pydantic, response_model, тестовые fixtures, новые хранилища, кэш списка, конкурентные записи или файловые транзакции.
- Передаём следующему занятию: работающие `GET /tasks` и `GET /stats`, реальные id из ответа коллекции, общую проекцию `_task_read_data(task)` с четырьмя публичными полями и способ получить выбранный сервис через `Request` из `request.app.state.planner`. Занятие 48.1 использует эту готовую связку для item-маршрута, затем добавляет положительную границу path и перевод только `TaskNotFoundError` в 404; list, stats и источник данных остаются прежними.

## 00. Вступление

Начать с уже знакомой работы CLI: задачи проходят через PlannerService и остаются в JSON после завершения процесса. Health из предыдущего шага доказывает только, что приложение отвечает; он ещё не показывает данные Planner. Вопрос занятия — как HTTP-интерфейс прочитает те же актуальные данные и представит их внешнему клиенту.

1. **Точка старта:** CLI, build_service(), PlannerService и JsonStorage уже существуют; новый маршрут 47.1 должен отвечать на /health.
2. **Новый вопрос:** как FastAPI получает тот же настроенный сервис, какие данные разрешено выдать через HTTP и как отразить статистику Planner?
3. **Результат:** два маршрута читают актуальные задачи и общую статистику, не создавая второй источник данных и не меняя сохранённое состояние.

CLI и Uvicorn работают в отдельных процессах, поэтому не могут разделить переменные Python. Связь между ними обеспечивает существующий файл и одинаковая проектная конфигурация хранилища. В занятии пройдём от этого источника через сервис к двум публичным HTTP-ответам.

## 01. Отдельные процессы читают один настроенный файл

- Что и зачем объяснить: память CLI исчезает с процессом, память Uvicorn принадлежит другому процессу. Данные переживают запуск благодаря JsonStorage; новый процесс обращается к тому же настроенному файлу через сервис.
- Механизм и порядок: проследить CLI → build_service() → PlannerService → JsonStorage → путь к JSON; определить фактическую настройку, не выводя расположение из текущего каталога и не создавая seed-файл. Связать знакомый load/save с выполнением команды и повторным запуском.
- Пример и типичная путаница: положить два списка в разные процессы и объяснить, почему совпадение кода не разделяет RAM. Отдельно сравнить память app.state с файлом на диске: первая исчезает при остановке API, второй сохраняет состояние.
- Первое самостоятельное действие: по существующему build_service() найти конкретную конфигурацию JsonStorage и объяснить, какой файл использует CLI. Наблюдаемый результат — путь взят из кода проекта и подтверждён повторным чтением CLI.
- Переход к следующему шагу: файл является общим источником, но обработчику нужен доступ к сервису, который знает правила чтения.

## 02. FastAPI получает выбранный Planner через Request

- Что и зачем объяснить: приложение связывает обработчики с уже существующей логикой через app.state.planner. State хранит сервис как объект приложения, но не хранит задачи и не заменяет JsonStorage.
- Механизм и порядок: создать сервис через знакомую build_service() при настройке приложения; показать, как FastAPI передаёт объект Request обработчику и как из request.app.state.planner получить выбранный сервис на каждый запрос. Не создавать новую фабрику или вторую логику предметных операций.
- Пример и типичная путаница: сравнить получение сервиса через Request при обработке запроса с глобальным tasks = list_tasks() во время импорта. Глобальный список становится устаревшим снимком после изменения файла через CLI; app.state — ссылка на сервис, не список.
- Первое самостоятельное действие: проследить путь от Request до существующего метода сервиса и определить, где выполняется чтение JSON. Критерий — обработчик получает Planner из текущего приложения, а не держит отдельный кэш или второе хранилище.
- Опора для повторного обращения: при добавлении каждого GET восстановить, что Request даёт доступ к приложению, app.state.planner содержит выбранный сервис, а свежие данные запрашиваются его методом внутри обработчика.
- Переход к следующему шагу: вызов возвращает доменные Task; для внешнего ответа нужно выбрать поля публичного договора.

## 03. Публичная проекция отделяет ответ от доменной Task

- Что и зачем объяснить: доменная Task содержит поля для работы Planner, но внешний HTTP-ответ намеренно ограничен id, title, priority, is_done. tags остаются частью модели и JSON, хотя в текущем публичном контракте их нет.
- Механизм и порядок: на независимом простом объекте показать выбор нескольких атрибутов в словарь; затем объяснить преобразование каждой Task в один словарь ответа. Ввести одну HTTP-функцию _task_read_data(task), чтобы список и будущие item/CRUD-маршруты использовали одну проекцию.
- Пример и типичная путаница: сравнить полный доменный объект с его публичным словарём и с сохранённой JSON-записью. Убрать поле из ответа — не значит удалить его из хранилища; вернуть словарь — не значит создавать вторую Task.
- Первое самостоятельное действие: по одной Task выбрать поля, которые входят в публичный ответ, и объяснить исключение tags. Наблюдаемый результат — проекция содержит ровно четыре поля и не меняет исходный объект.
- Опора для повторного обращения: при работе с ответом восстановить четыре публичных поля и роль _task_read_data; не добавлять tags и не собирать JSON вручную строкой.
- Переход к следующему шагу: готовая проекция применяется к каждому объекту из list_tasks().

## 04. GET /tasks возвращает актуальную коллекцию

- Что и зачем объяснить: маршрут коллекции вызывает существующий list_tasks() и преобразует результат в список публичных словарей. FastAPI сериализует возвращённые Python-списки и словари в JSON.
- Механизм и порядок: внутри обработчика получить Planner через Request, вызвать чтение при запросе и применить _task_read_data к каждой Task. Зафиксировать, что здесь нет фильтров или HTTP-параметров: выборка остаётся полной, как в готовом CLI-list.
- Пример и типичная путаница: сравнить список из нескольких задач и пустую коллекцию. Пустой результат имеет форму JSON-массива []; это не строка «[]» и не ошибка отсутствия одной Task.
- Первое самостоятельное действие: самостоятельно связать уже знакомое чтение сервиса с публичной проекцией списка. Критерий — HTTP возвращает реальные записи из настроенного JSON, только с четырьмя полями и их настоящими id.
- Опора для повторного обращения: назначение list_tasks(), один словарь на Task, полный список и форма [] для пустой коллекции.
- Переход к следующему шагу: отдельный маршрут статистики должен переиспользовать готовый подсчёт, а не выводить его из HTTP-списка.

## 05. GET /stats использует готовую статистику

- Что и зачем объяснить: единственный подсчёт принадлежит PlannerService. get_statistics() возвращает all, open, done; API адаптирует только имя all к публичному total.
- Механизм и порядок: получить сервис через Request, вызвать get_statistics() для всего источника и вернуть значения в форме договора. Пояснить, что общая статистика не ограничивается выборкой и не пересчитывается отдельным циклом в обработчике.
- Пример и типичная путаница: на небольшом словарном примере сопоставить all=4, open=3, done=1 с total=4, open=3, done=1. Переименование ключа меняет форму ответа, не значение; total не означает размер ограниченного списка.
- Первое самостоятельное действие: объяснить преобразование имён и проверить на реальном выводе, что total соответствует полному числу задач и равно сумме open и done.
- Опора для повторного обращения: get_statistics() возвращает всю статистику; all → total, open и done сохраняют названия и значения.
- Переход к следующему шагу: оба маршрута готовы к проверке свежести и отсутствия побочного изменения.

## 06. Чтение обновляет представление, но не состояние

- Что и зачем объяснить: каждый GET запрашивает актуальные данные через сервис; вызов при импорте модуля создаёт устаревающий снимок. Чтение не вызывает изменение или сохранение.
- Механизм и порядок: различить пустое корректное хранилище и ошибку чтения повреждённого JSON; не преобразовывать StorageError в пустой список, 404 или успешную статистику. Сопоставить наблюдения API и CLI до и после последовательного изменения.
- Пример и типичная путаница: пустой JSON-проект может дать [] и нулевые счётчики, а файл, который невозможно прочитать, остаётся ошибкой storage. Общий путь к файлу не обеспечивает блокировки и безопасной параллельной записи.
- Первое самостоятельное действие: объяснить, какие изменения должны быть видны после завершения команды CLI, пока Uvicorn работает, и после нового запуска API. Критерий — оба GET отражают новое сохранённое состояние, а сами GET не меняют файл.
- Опора для повторного обращения: чтение происходит внутри запроса; пустое состояние допустимо; ошибку storage не маскируют; изменения выполняются только последовательно.
- Переход к практике: проверить весь путь на реальных данных проекта, не меняя контракт и не добавляя слой синхронизации.

## 07. Что мы будем делать в практике

**Формат и исходная опора:** обязательная manual-практика в существующем Planner. Начинаем с результата целевых занятий 47/47.1: GET /health и приложение уже работают; существующие CLI, build_service(), PlannerService и JsonStorage остаются на месте. Если фактическая опора ещё не подтверждена, сначала фиксируем это ограничение и не заявляем, что новый API уже существует.

Общий результат — два HTTP-маршрута, согласованные с теми же задачами и статистикой, которые видит CLI.

1. **Установить источник данных:** от исходного состояния существующего проекта ученик прослеживает build_service() до JsonStorage и фактического пути, затем использует CLI для изменения данных. Опора — блок 01 и прежнее знание CLI/storage. Ученик сам выбирает проектные данные через CLI; после повторного запуска список и статистика остаются доступными, реальные id не выдуманы и рабочий файл не заменён.
2. **Подключить коллекцию:** при работающем health-маршруте ученик использует объяснения блоков 02–04, помещает выбранный Planner в app.state, получает его через Request и добавляет чтение GET /tasks. Критерий — ответ совпадает с текущим CLI-list и содержит только четыре публичных поля; знакомый /health продолжает отвечать.
3. **Подключить статистику:** опираясь на блок 05 и готовый результат первого GET, ученик добавляет GET /stats через get_statistics(). Критерий — значения совпадают с CLI, all представлен как total, а статистика охватывает весь источник, а не ограниченную выдачу.
4. **Проверить свежесть и сохранность:** опираясь на блок 06, ученик оставляет Uvicorn работающим, последовательно меняет данные через CLI, затем проверяет оба GET; после перезапуска API повторяет чтение. Критерий — новое сохранённое состояние видно без перезапуска сервера и сохраняется после его перезапуска; GET не переписывает JSON, прежний CLI и /health работают.

Блоки 01–06 подготавливают путь данных, получение сервиса, публичную форму, повторное использование статистики и границу read-only. Все действия проверяются по фактическому состоянию собственного проекта; не задаём ожидаемые id и числа заранее. Параллельную запись не запускаем, транзакции и обработчики StorageError не добавляем.

**Итоговый критерий практики:** GET /tasks и GET /stats представляют одно актуальное состояние Planner, совпадают с последовательными действиями CLI до и после перезапуска API, не меняют JSON и сохраняют прежние возможности проекта. Это подтверждает B и передаёт следующему занятию коллекцию и реальные идентификаторы для чтения одной Task.
