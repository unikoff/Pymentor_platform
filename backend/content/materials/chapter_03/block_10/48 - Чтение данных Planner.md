## Место в маршруте

Занятие впервые подключает HTTP-чтение к **тому же проекту Planner**, в котором CLI уже пользуется `PlannerService` и настроенным `JsonStorage`. Новый маршрут — вход в готовые операции, а не новая реализация хранения или подсчёта. Центральная учебная цепочка: **HTTP-запрос → обработчик → выбранный `PlannerService` → прежний `JsonStorage` → существующий JSON → публичный HTTP-ответ**.

На входе условно используем B шагов **47** (работающее приложение `app/api.py`, `/health`) и **47.1** (запуск Uvicorn, проверка `/docs`/`/openapi.json` и Postman Local). До выдачи 48 необходимо **фактически открыть проект и повторить успешный `/health`**, а также убедиться, что доступен прежний CLI. Паспорта предыдущих шагов описывают будущие результаты, но ещё не доказывают их выдачу. После 48 занятие 48.1 возьмёт реальный id из `/tasks` и добавит чтение одного объекта; текущая B заканчивается на коллекции и статистике.

## Точка B: результат занятия

- Ученик сможет объяснить: почему CLI и Uvicorn не делят память, каким путём оба доходят до одного настроенного JSON, почему `app.state.planner` хранит ссылку на сервис, а вызов `list_tasks()` нельзя один раз выполнить при импорте модуля.
- Ученик сможет сделать: подключить в app/api.py существующий сервис через app.state.planner, получить его в обработчиках через Request, добавить GET /tasks и GET /stats.
- Результат в проекте: два новых GET-маршрута читают прежний Planner. Список выдаёт только id, title, priority, is_done; статистика использует get_statistics(), представляя all как total, а open и done сохраняя.

GET не изменяют JSON, `/health` и CLI продолжают работать.

## 00. Вступление: от рабочего health к данным

Сценка: ученик добавил задачу через CLI, закончил команду, запустил FastAPI и видит `{"status": "ok"}` от `/health`. Попросить предположить: **можно ли по `/health` узнать задачи?** Нет: health доказывает доступность сервера, но не связь с Planner. Показать цель на экране: клиент вызывает `GET /tasks` и получает массив задач; вызывает `GET /stats` и получает их общие счётчики. Это уже новый вход к старой программе.

После короткого прогноза ученик рисует путь **CLI → service → storage → файл** и отмечает место HTTP перед service. Не выдавать готовое построение двух маршрутов: сперва ученик научится получать сервис и преобразовывать безопасный ответ, затем сам свяжет операции. Связующий вопрос: «Если CLI закрылся, откуда работающий Uvicorn получит добавленную задачу?» — ведёт к разделу 01.

## 01. Отдельные процессы читают один настроенный файл

**Механизм в простых словах.** Процесс — запущенная программа со своей памятью. При запуске CLI создаётся свой `PlannerService`; при запуске Uvicorn — свой. Даже если обе программы импортируют один класс, переменная или список в оперативной памяти CLI не становится переменной Uvicorn. Общее состояние хранится в файле, путь к которому берут из **одинаковой настройки** `JsonStorage`, а не из «общей памяти Python». После выполнения команды CLI данные должны быть сохранены, после чего другой процесс сможет их прочитать через свой service/storage.

**Наглядная схема №1 (два процесса, один файл):**

```text
процесс CLI:      команда → PlannerService ─┐
                                           ├→ JsonStorage(тот же путь) ↔ data/tasks.json
процесс Uvicorn:  HTTP → PlannerService ────┘
```

Схема **концептуальна**: подпись `data/tasks.json` берётся из рамки COURSE; фактический путь, способ его разрешения и момент чтения в конкретном checkout надо найти в коде. Пояснить отличие сохранённого файла от объекта `app.state` в RAM и от списка, заранее загруженного в Python: остановка Uvicorn уничтожает объекты процесса, но сама по себе не стирает файл.

**Различающий пример и действие до проекта.** Представить два отдельных процесса с локальными переменными `tasks = []`. В одном добавили элемент. Спросить, изменился ли список в другом (нет); затем представить запись в файл и **новое чтение** файла вторым процессом (да, после сохранения). Ученик самостоятельно дорисовывает стрелки записи и чтения и объясняет, почему совпадение имён переменных ничего не решает. Это проверка понимания, а не ещё одна задача на синтаксис списков.

**Первая опора на реальный проект.** Ученик открывает существующий `build_service()` и без правок выписывает, какой `JsonStorage` он создаёт, откуда получает путь и какая команда CLI читает задачи. Затем запускает прежний CLI list/stats: результат должен соответствовать реальному файлу, а не придуманным данным. Если файл или методы не обнаружены, остановить HTTP-часть и вернуть зависимость на подготовку Planner из A; не создавать запасное хранилище внутри API.

**Переход.** Одинаковый файл решает вопрос сохранения, но не объясняет, **как обработчик запроса найдёт** нужный сервис. Это задача раздела 02.

## 02. FastAPI получает выбранный Planner через Request

**Зачем новая связка.** HTTP-обработчик не должен знать, как открыть JSON, создать storage или посчитать задачи. Он получает собранный `PlannerService` и вызывает его существующие методы. В плане показать две **разные операции**: при конфигурации приложения сервис размещают в `app.state.planner = build_service()`; при входящем запросе FastAPI передаёт в функцию параметр `request: Request`, через который читают `request.app.state.planner`. Разобрать каждую точку: `request` — конкретный запрос, `.app` — его приложение, `.state` — место хранения объектов приложения, `.planner` — выбранное нами имя ссылки на сервис. `Request` импортируется из `fastapi`.

**Независимый пример.** До работы с Planner положить в `app.state` безобидное значение `app.state.label = "planner-api"` и в учебном обработчике показать получение `request.app.state.label`. Попросить ученика предсказать значение; затем заменить мысленно `label` на ссылку на сервис. Это объясняет новый синтаксис без готового решения `/tasks` и `/stats`.

**Критически различить хранение объекта и снимка данных.** Сравнить две надписи на доске: `app.state.planner = build_service()` (сохранена ссылка на объект с правилами/настройкой) и `tasks = build_service().list_tasks()` вне обработчика (сохранён снимок списка на момент импорта). Если CLI добавит задачу позже, второй вариант продолжит выдавать старый снимок. Сохранение сервиса само по себе не обещает свежесть при произвольной реализации: **внутри каждого GET** нужно вызывать соответствующий метод и по фактическому коду убедиться, что он читает текущий storage.

**Мини-трассировка ученика.** На схеме ученик ставит в правильном порядке `GET`, `Request`, `request.app`, `app.state.planner`, `list_tasks()` и `JsonStorage` и указывает, какое звено владеет предметной логикой (service). На реальном `app/api.py` находит место настройки `app`, отмечает точку для `build_service()`; пока не пишет оба итоговых маршрута. Наблюдаемый ответ — сервис выбирается из приложения, storage остаётся внутри него. Это пригодится отдельно в двух самостоятельных реализациях практики.

**Переход.** Сервис возвращает доменные объекты `Task`. Прежде чем отвечать браузеру, определяем, какие их поля вообще входят в публичный договор.

## 03. Публичная проекция отделяет ответ от доменной Task

**Разделить внутреннее и внешнее.** `Task` — модель программы, у неё есть и внутренние данные, включая `tags`; HTTP-ответ — договор с клиентом. В этом уроке договор фиксирован: **`id`, `title`, `priority`, `is_done`**, без `tags`. Объяснить слово «проекция» как создание **нового словаря только с выбранными полями**; отбор полей не меняет исходную задачу и не удаляет поле из JSON. `priority` передаётся в формате существующей модели, его значение не придумываем без просмотра проекта.

**Наглядная схема №2 (состояние, модель, ответ):**

```text
файл JSON → JsonStorage → Task(id, title, priority, is_done, tags, ...)
                                     │  выбор полей, без изменения Task
                                     ↓
                         {id, title, priority, is_done} → JSON HTTP
```

**Независимое действие до итоговой функции.** Взять вымышленную карточку участника с полями `name`, `city`, `secret_note`. Предложить ученику самому создать публичный словарь из `name` и `city`, а потом проверить, что `secret_note` осталась в исходной карточке. Обсудить разницу между словарём Python и строкой с JSON: обработчик возвращает обычные Python-данные, сериализацию делает FastAPI. На новой доменной карточке `Task` ученик **выбирает**, какие ключи оставить; преподаватель лишь называет итоговый договор, не пишет за него готовую `_task_read_data`.

**Сборка механизма в плане MAIN.** Одна небольшая вспомогательная `_task_read_data(task)` должна брать поля у **переданного объекта** и возвращать новый словарь. В последующей практике её создаст ученик; в уроке 48.1 эта же функция пригодится для одной Task. Контрольные случаи: одна реальная Task с `tags` → ровно четыре ключа в ответе и неизменные `tags` в файле; отсутствие дополнительных полей в HTTP **не** означает пустую или урезанную Task.

**Переход.** Один словарь готов по смыслу. Теперь надо преобразовать **каждую** задачу, полученную через `list_tasks()`, и вернуть массив.

## 04. GET /tasks возвращает актуальную коллекцию

**Разобрать запрос от входа до выхода.** Браузер или Postman отправляет `GET /tasks`; FastAPI выбирает соответствующий обработчик из уже знакомого приложения. Внутри функции нужно получить сервис через `Request`, вызвать **существующий `list_tasks()` в момент запроса**, преобразовать каждую возвращённую `Task` через `_task_read_data` и вернуть Python-список словарей. FastAPI представляет его JSON-массивом. Это полный список из Planner: пока без фильтра, сортировки, limit, path-аргумента и пересчёта данных в route.

**Контраст до написания маршрута.** Дать два независимых входа: `[Task А, Task Б]` и `[]`. Ученик без готового кода изображает результат: два словаря с четырьмя ключами и настоящий массив `[]` соответственно. Показать различие между **пустым списком задач** (`200` с `[]`), строкой `"[]"` (ошибочная форма ответа) и отсутствием конкретной задачи (отложено до 48.1). Подчеркнуть, что не нужно придумывать идентификаторы или возвращать фиктивную запись ради непустого примера.

**Первая собственная сборка без спойлера.** Предложить ученику на бумаге составить четыре операции обработчика из уже объяснённых деталей разделов 02–03; затем написать маршрут в проекте на практике. Микроконтроль: ответ на запрос **после** добавления записи через CLI должен включать её реальный id, а `tags` не должны попасть наружу. Если `list_tasks()` уже умеет прочитать JSON, обработчик не открывает файл через `open()` и не создаёт отдельную копию модели.

**Переход.** Список описывает сами объекты; для общих счётчиков в сервисе уже есть отдельная операция. Следующий обработчик должен к ней обратиться.

## 05. GET /stats использует готовую статистику

**Граница ответственности.** `PlannerService.get_statistics()` уже знает, какие задачи выполнены; route не должен заново считать `is_done` обходом HTTP-списка. Обработчик `GET /stats` получает тот же сервис через `Request`, обращается к `get_statistics()` в момент запроса и **переводит только имя** внутреннего счётчика `all` в публичный `total`. Имена и значения `open` и `done` сохраняются. Подсчёт относится ко **всему** настроенному хранилищу, даже если в следующих уроках появятся ограниченные представления списка.

**Различающий пример без готового обработчика:**

```text
ответ сервиса: {all: 4, open: 3, done: 1}
ответ HTTP:    {total: 4, open: 3, done: 1}
инвариант:     total = open + done = 4
```

Попросить ученика самому переименовать один ключ в другом словаре: значения не должны поменяться. Затем предложить ошибочный вариант `total = len(публичного_списка)` и найти нарушенную ответственность: route дублирует правило предметного слоя и рискует считать не ту выборку. Проверка на реальном проекте — сравнение всех трёх чисел с выводом CLI, в том числе после добавления или завершения задачи через **существующую CLI-команду**. Если тип/название фактического результата `get_statistics()` отличается от паспорта, сверить код до написания route; не подменять отсутствующий сервисный контракт реализацией в HTTP.

**Переход.** Осталось проверить важное свойство двух GET: каждый видит последнее **сохранённое** состояние и сам не выполняет запись.

## 06. Чтение обновляет представление, но не состояние

**Три состояния, которые нельзя путать.** (1) В корректном хранилище нет задач: `GET /tasks` возвращает `[]`, `GET /stats` — нулевые значения. (2) Список был загружен **до** CLI-изменения и сохранён в глобальной переменной: ответ технически успешен, но устарел; виноват момент чтения. (3) JSON повреждён или чтение завершилось ошибкой storage: это не «ноль задач». Не предлагать перехватывать `StorageError` с возвратом `[]`, `404` или `{"total": 0, ...}`; контракт ошибок и отдельные обработчики вне этого занятия.

**Прогноз перед экспериментом.** Показать последовательность: HTTP-список → CLI сохраняет изменение и завершается → HTTP-список ещё раз → перезапуск Uvicorn → HTTP-список ещё раз. Ученик предсказывает, какие данные должны совпасть с CLI на каждом шаге, и объясняет, почему вторая HTTP-проверка не требует рестарта. Отдельно спросить, какой маршрут потенциально может изменить файл; ответ — **ни один из этих GET**, оба обращаются только к чтению. Для контроля можно сравнить байты или хэш файла **до и после только серии GET**, не включая между ними изменяющую команду CLI.

**Границы честной гарантии.** Общее имя файла не означает синхронизацию процессов, блокировки или атомарную запись. Проверяем **последовательные** действия: CLI завершился и сохранил данные, после этого пришёл новый GET. Не обещать корректность конкурентного редактирования; не строить здесь дополнительную систему транзакций. Пустой случай проверять на отдельной копии конфигурации и JSON только при доступной безопасной изоляции, без очистки рабочего файла.

**Переход к практике.** Самостоятельно собрать два route в исходном `app/api.py` и проверить все существенные наблюдения на реальном Planner, пользуясь пройденными механизмами, а не готовым кодом ответов.

## 07. Что мы будем делать в практике

**Формат: `manual`, изменение существующего проекта.** Рабочий объект — `app/api.py`, уже созданный в занятии 47; `GET /health`, Uvicorn, `/docs` и Postman Local от 47/47.1 должны реально запускаться. CLI, `build_service()`, `PlannerService`, `JsonStorage` и рабочий JSON остаются теми же; новый файл хранилища для API не создаём. Ученик сам пишет связку сервиса, функцию проекции и **два** route. Названия `GET /tasks`, `GET /stats`, `app.state.planner`, `_task_read_data`, четыре ключа и маппинг статистики заданы договором; внутреннюю форму циклов и переменных внутри обработчиков выбирает ученик. В теории изучены все новые операции, но полного решения маршрутов заранее нет.

1. **Проверить реальный вход A и записать исходные наблюдения (разделы 00–01).** Открыть `app/api.py` и проверить `GET /health` через запущенный Uvicorn, Swagger и Postman Local. Найти **существующую** `build_service()` и её путь к `JsonStorage`, убедиться в наличии `list_tasks()`/`get_statistics()` и запустить доступные команды CLI для списка и статистики. **Собственное решение ученика:** указать реальный путь и объяснить, какой объект отвечает за чтение. **Локальный результат:** успешные `/health` и CLI, записаны текущие реальные id/счётчики. Если нет API — вернуться к 47/47.1; если нет необходимых методов/storage — к исходному Planner. Не подменять отсутствие A примером или новой реализацией в route.
2. **Создать различающиеся реальные данные прежним CLI (раздел 01).** Используя **существующий синтаксис CLI**, добавить минимум две учебные задачи в рабочий Planner без удаления прежних пользовательских задач. Если CLI поддерживает изменение статуса, завершить одну новую задачу, чтобы в результате было что сравнить для `open`/`done`; иначе использовать уже имеющиеся статусы и зафиксировать ограничение входных данных. Самостоятельно выбрать названия и прочитать реальные id обратно командой CLI. **Локальный результат:** известен конкретный набор записей и актуальные общие счётчики; файл остаётся доступен после завершения CLI. Эти данные — **вход** проверок HTTP, поэтому не задавать ожидаемые числа заранее.
3. **Самостоятельно подключить чтение списка (разделы 02–04).** В том же `app/api.py` разместить существующий собранный Planner в `app.state.planner`; написать `_task_read_data(task)`, выбирающую четыре поля; затем добавить `GET /tasks`, который получает сервис через `request: Request`, вызывает `list_tasks()` **во время запроса** и преобразует каждую Task. **Локальная проверка сразу после шага:** вызвать маршрут в Swagger или Postman, сравнить набор реальных id и задач с CLI; проверить для каждого элемента **ровно** `id/title/priority/is_done`, отсутствие `tags` и сохранность этих `tags` в исходной модели/файле. Не сравнивать порядок, если его не гарантирует сервис. Результат шага — работающая коллекция для сравнения со статистикой и будущего item-route.
4. **Самостоятельно подключить агрегаты (раздел 05).** На том же сервисе через `Request` написать `GET /stats`; получить готовые значения из `get_statistics()` и изменить только имя `all` на `total`. **Локальная проверка:** сопоставить `total`, `open`, `done` с CLI и проверить `total = open + done` для **всех** задач хранилища; у ответа нет внутреннего ключа `all`. Проверка относится к текущему сохранённому состоянию, а не к числу элементов воображаемой фильтрованной выдачи. Результат — оба готовых GET с единым источником данных.
5. **Проверить свежесть и отсутствие записи (раздел 06).** Сначала записать хэш фактического JSON, выполнить **только** оба GET несколько раз и сравнить хэш: значение не должно измениться. Затем, **отдельно от проверки хэша**, оставить Uvicorn работающим, через CLI последовательно добавить или изменить задачу и дождаться завершения команды; снова вызвать `/tasks` и `/stats`. **Локальный результат:** видны новая реальная запись/статус и согласованные счётчики без перезапуска. Перезапустить Uvicorn и повторить оба GET — результат сохраняется. В конце повторить `/health` и CLI-list/stats, чтобы доказать отсутствие регрессии.
6. **Отличить пустое состояние от сбоя (разделы 04 и 06).** Ученик объясняет на конкретных входах: корректный пустой проект возвращает `[]` и нули; недоступный/повреждённый storage — ошибка, которую нельзя маскировать пустотой. **Если есть безопасно изолированная копия проекта со своей конфигурацией JSON**, проверить пустой случай на ней; в противном случае выполнить только прогноз и разбор формы ответа. Не очищать и не перезаписывать рабочий JSON ради граничного случая; повреждение файла не устраивать как обязательный эксперимент. Точное HTTP-поведение ошибок вне текущей B.

**Связка результатов:** шаг 1 подтверждает A и путь к файлу; шаг 2 создаёт входные данные; шаг 3 показывает их через публичный список; шаг 4 подтверждает общие счётчики; шаг 5 доказывает свежесть и read-only; шаг 6 фиксирует смысл важной границы без риска для рабочего JSON. При затруднении возвращаться к соответствующему разделу 01–06 и **повторно выполнить действие самому**, не подставлять эталонный маршрут. Все проверки используют реальные данные и завершённые последовательные действия, без предположений об атомарности или конкурентной записи.

**Приёмка B:** ученик без готового кода собрал `GET /tasks` и `GET /stats` в прежнем приложении, может проследить `route → service → storage → JSON`, видит реальные id и четыре публичных поля без `tags`, подтвердил равенство статистики и CLI, изменение данных без рестарта, сохранность после рестарта, отсутствие записи GET, работоспособность CLI и `/health`. В 48.1 передаются эти маршруты, `_task_read_data`, доступ к `request.app.state.planner` и реальные id; обработка item/404/422 остаётся для следующего урока.
