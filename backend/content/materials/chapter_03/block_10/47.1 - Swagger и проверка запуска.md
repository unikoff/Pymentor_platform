## 00. Вступление

В предыдущем занятии мы научились получать ответ от `/health`. Теперь нужно выяснить, как сервер сообщает клиентам о доступных операциях. Мы прочитаем этот список, отправим реальный запрос из Swagger и сравним его с Postman. Затем ненадолго изменим адрес операции, чтобы увидеть, что список строится из кода, и обязательно вернём его обратно.

1. **Точка старта:** после фактической проверки 47 уже запущен Planner API с `GET /health`; в Postman знаком запрос к Echo.
2. **Новый вопрос:** где увидеть объявленные маршруты и как убедиться, что кнопка в документации отправила настоящий запрос?
3. **Результат:** ученик сам проверит health двумя клиентами, увидит изменение пути в документации и восстановит исходный маршрут.

Список операций, отправка запроса и ответ — три разных наблюдения. Их сравнение позволит проверить маршрут, не приписывая ему функции работы с задачами.

## 01. Восстановить исходное состояние

- Что объяснить: Uvicorn запускает FastAPI как отдельный серверный процесс. Для локального запроса нужны схема (`http://`), адрес компьютера (`127.0.0.1`), порт из команды 47 и путь (`/health`). `GET /health` проверяет ответ приложения, а не доступность списка задач или JSON.
- Механизм и независимая проба: показать два учебных URL с одинаковыми host/портом, но разными путями, например `/health` и `/not-here`. Ученик до отправки определяет, какая часть адреса изменена и где искать причину возможного 404. Число порта из примера не объявлять действующим портом проекта.
- Первое самостоятельное действие: найти в README команду 47, показать работающий процесс Uvicorn, собрать **свой** URL health и получить ответ. Если сервер не запущен, восстановить шаг 47; не переустанавливать пакеты и не создавать второй `app/api.py`.
- Типичная путаница и опора: работающий CLI не равен запущенному HTTP-серверу; `200` от health не означает исправного хранения задач. Перед любым вызовом сверить процесс, host, порт и путь.
- Переход: теперь можно спросить у самого приложения, какие операции оно объявляет.

## 02. OpenAPI показывает зарегистрированные операции

- Что объяснить: OpenAPI — описание того, **какие HTTP-операции объявлены**: путь, метод и возможные ответы. FastAPI строит JSON по зарегистрированным декораторам, а не по названиям функций в проекте. `/openapi.json` отдаёт описание инструментам; сам JSON не исполняет операции.
- Независимый пример до Planner: для воображаемого сервера с `GET /menu` и `POST /order` попросить выбрать, какой из двух методов и путей следует искать в описании, чтобы **прочитать меню**, и почему описание само по себе не подтверждает выдачу меню. Аналогия со списком услуг помогает найти операцию, но список услуг не гарантирует успешного обслуживания.
- Механизм на проекте: показать в `app/api.py` декоратор `@app.get("/health")`; открыть `/openapi.json`, найти `paths` → `/health` → `get`. Объяснить, что `/docs` — интерфейс документации и сам не обязан быть в перечне прикладных операций OpenAPI; `/tasks` и `/stats` здесь пока отсутствуют.
- Первое самостоятельное действие: без готового выделения нужной строки ученик находит path и метод health, сопоставляет с декоратором, объясняет отсутствие `/tasks`. Локальный критерий — названо **одно соответствие код ↔ спецификация**, без выдуманных будущих маршрутов.
- Опора и переход: при сомнении сверять `paths` и метод с декоратором; следующий шаг покажет это описание на странице с кнопкой отправки запроса.

## 03. Swagger UI выступает HTTP-клиентом

- Что объяснить: Swagger UI — страница `/docs`, которая читает OpenAPI и показывает операции понятнее, чем JSON. `Try it out` подготавливает запрос, `Execute` **отправляет** его серверу. Само открытие документации или пример ответа на странице не доказывают, что запрос состоялся.
- Механизм и маленькая проверка: прежде чем нажать `Execute`, предложить ученику предсказать метод, путь и ожидаемый статус health. Затем показать разницу между примером ответа в описании и результатом в **Server response** после отправки; указать `Request URL`, `Response code`, `Response body`.
- Применение: найти `GET /health` → `Try it out` → `Execute`; проверить фактический `200` и `{"status":"ok"}`. `200` — HTTP-статус, объект JSON — тело ответа; ни один из них не проверяет работу `PlannerService`.
- Первое самостоятельное действие: ученик без повторного показа нажимает нужные кнопки и называет, **что реально ушло и что вернулось**. Критерий — совпадают метод/path из OpenAPI, `Request URL` и статус/body в реальном ответе. Если кнопка недоступна из-за соединения, не выдавать пример на странице за ответ.
- Опора и переход: перечитать разделы 01–02, если URL или операция неясны; затем отправить **тот же запрос** из независимого клиента Postman.

## 04. Postman хранит локальную проверку отдельно от Echo

- Что объяснить: клиент можно сменить, **операция на сервере остаётся той же**. В Postman collection сохраняет запросы, Local environment — переменную `base_url` с проверенной схемой, host и портом **без** `/health`; путь прибавляется в запросе. Echo и Planner API должны оставаться разными настройками.
- Независимое сравнение: показать две формы **одного адреса** — полный URL в Swagger и `{{base_url}}/health` в Postman. Попросить предсказать, почему при правильном environment оба клиента должны получить одинаковый status/body, а при выборе Echo environment — нет. Сетевые ошибки не объяснять отличием JSON-формата.
- Механизм: использовать существующую Planner API collection либо завести её, если отсутствует; выбрать Local environment, локальный Desktop Agent и `GET {{base_url}}/health`. Cloud Agent не обращается к `127.0.0.1` на устройстве ученика.
- Первое самостоятельное действие: отправить health из Postman и **самому сравнить** с предыдущим Server response Swagger три поля — метод/path, status `200`, body `{"status":"ok"}`. Критерий — оба клиента получили ответ от одного запущенного процесса; экспорт collection/environment в `postman/` полезен для 48, но не доказывает Swagger-B сам по себе.
- Опора и переход: сверять агент, environment и реальный `base_url`; теперь можно проверить, насколько список операций зависит от строки маршрута в Python-коде.

## 05. Изменить маршрут и восстановить договор

- Что объяснить: OpenAPI отображает **текущую регистрацию маршрута**. Изменение строки пути в декораторе меняет, по какому адресу FastAPI может вызвать функцию; старый адрес после применения изменения перестаёт подходить. Документация при этом не редактируется вручную.
- Независимый пример: у воображаемой операции `GET /ping` временно становится `GET /alive`. Предложить предсказать, что произойдёт со старым запросом и какой путь появится в новом OpenAPI. Это демонстрирует механизм, но не подставляет итоговый путь решения.
- План безопасной пробы: ученик **сам выбирает временный уникальный путь** для health в декораторе `app/api.py`, сохраняет изменение, дожидается reload Uvicorn либо перезапускает сервер той же командой, затем **обновляет страницу** `/docs` и `/openapi.json`. До наблюдения сверяет, что процесс снова принимает запросы.
- Первое самостоятельное действие: в обновлённой документации найти новый путь, запустить его через Swagger и проверить `200` с прежним JSON; отправить старый `GET /health` и увидеть `404`. Ученик объясняет, почему изменился доступный путь, а тело ответа осталось прежним. Критерий — соответствие нового декоратора, списка и двух фактических ответов.
- Обязательное восстановление: вернуть **точно** `@app.get("/health")`, дождаться применения изменения, обновить `/docs` и повторно получить `200` по `/health`; временный путь исчезает из OpenAPI. Если сохранение не подхватилось, проверить reload/перезапуск прежде, чем делать выводы об OpenAPI.
- Переход: видимый `404` означает полученный ответ сервера; отделим его от ошибки метода и отсутствия связи.

## 06. Разобрать сбои и сохранить прежние возможности

- Что объяснить: `404` значит «сервер ответил, но такого пути не нашёл»; `405` — «путь есть, но этот метод для него не объявлен». Если Uvicorn остановлен и соединиться некому, HTTP-статус **вообще не получен**. Это разные причины, для которых требуются разные проверки.
- Независимый разбор: дать три коротких наблюдения — работающий сервер и неверный путь, работающий сервер и `POST` к GET-маршруту, остановленный процесс. Ученик до проверки выбирает: искать путь, метод или процесс/порт. Объяснить, почему браузерная страница Swagger, открытая ранее, не доказывает, что сервер всё ещё запущен.
- Механизм диагностики: сначала установить наличие **фактического** HTTP-ответа; если нет — проверить Uvicorn, host и порт; если есть 404 — путь по OpenAPI; 405 — метод; `200` — затем сверить JSON-body с ожидаемым. После раздела 05 все пробы проводить на **восстановленном** `GET /health`.
- Первое самостоятельное действие: ученик отличает три случая по наблюдаемым статусам/сообщениям и объясняет, почему отправка к остановленному серверу не может дать 404 или 405.
- Сохранить KEEP из прежнего маршрута как **дополнительную проверку совместимости**: отдельно импортировать `app.main` без запуска меню и отдельно запустить/закрыть CLI; если проверки выполняются, зафиксировать в README только подтверждённые адреса `/docs`, `/openapi.json` и смысл health. Импорт сам по себе не доказывает работу CLI; это не условие для нахождения health в Swagger.
- Переход к практике: ученик сможет самостоятельно подтвердить путь `код → OpenAPI → Swagger → ответ` и вернуть проект к состоянию, нужному для 48.

## 07. Что мы будем делать в практике

**Формат и исходная опора:** UI-практика в существующем Planner после 47; вход — фактически запущенное FastAPI-приложение с `GET /health` и знакомый Postman из 46/46.1. Если сервер/health недоступны, сначала вернуться к проверке 47. Ученик действует в интерфейсах `/docs`, `/openapi.json`, Postman; **только для проверки влияния декоратора** ненадолго меняет строку пути в `app/api.py` и восстанавливает её. Не создавать новые endpoints и не править JSON OpenAPI вручную.

1. **Самостоятельно найти объявленный маршрут.** Вход: работающий сервер и исходный `app/api.py` из 47. Объект: `/openapi.json` и `/docs`. Опора: разделы 01–02. Действие ученика: по сохранённой команде определить базовый адрес, найти в `paths`/Swagger метод и путь health, сопоставить с декоратором. **Сразу видимый результат:** найден `GET /health`, а `/tasks` и `/stats` отсутствуют; ученик объясняет, почему список будущих операций не появляется автоматически. Список или точное место строки заранее не подсвечивать.
2. **Отправить, а не только посмотреть запрос.** Вход: найденный в шаге 1 маршрут. Объект: Swagger `/docs`. Опора: раздел 03. Действие: предсказать статус/body, затем самостоятельно открыть `Try it out` и нажать `Execute`, прочитать `Request URL` и **Server response**. **Локальный результат:** реальный `200` и `{"status":"ok"}` для `GET /health`; ученик отличает их от примера в документации и может указать, что проверено — ответ HTTP, не работа с задачами.
3. **Сравнить второй клиент на том же запросе.** Вход: успешный ответ шага 2 и настройки Postman из 46/46.1; при отсутствии Planner API collection ученик создаёт её с Local environment. Объект: `GET {{base_url}}/health`, активный локальный агент. Опора: раздел 04. Действие: выбрать правильный environment/агент, отправить запрос и **самому** сравнить метод/путь, статус и JSON со Swagger. **Локальный результат:** оба клиента обращаются к одному серверу и возвращают `200` с тем же body; ученик объясняет, почему успешный Echo или Cloud Agent не заменяет эту проверку.
4. **Доказать связь декоратора с документацией.** Вход: исходный `GET /health` из 47, сервер с возможностью перезапуска. Объект: только временная строка пути в `@app.get(...)` файла `app/api.py`. Опора: раздел 05 с независимым примером `/ping` → `/alive`. Действие: ученик выбирает **другой временный путь**, применяет изменение через reload/перезапуск, обновляет `/docs`, находит новую операцию и вызывает её; проверяет старый адрес, затем возвращает исходный `"/health"` и повторяет обе проверки. **Локальный результат:** новый путь отвечает `200`, старый после изменения — `404`; после восстановления снова работает исходный `/health`, а временный путь исчезает из OpenAPI. Без этого возврата шаг не принят; данные Planner не меняются.
5. **Объяснить диагностический исход и подтвердить передачу.** Вход: восстановленное приложение после шага 4. Объект: запросы к правильному/неправильному пути и разными методами, работающий и остановленный Uvicorn. Опора: раздел 06. Действие: ученик по очереди предсказывает, а затем проверяет 404 для неизвестного пути, 405 для `POST /health`, отсутствие HTTP-статуса после остановки; снова запускает сервер и выполняет `GET /health`. **Локальный результат:** он различает проблему path, method и соединения и возвращает приложение в состояние с работающим health для 48. В обязательном результате нет чтения или изменения задач.

Шаги идут от наблюдения без изменения к самостоятельному отправлению, сравнению двух клиентов и **проверке изменённого случая**.
