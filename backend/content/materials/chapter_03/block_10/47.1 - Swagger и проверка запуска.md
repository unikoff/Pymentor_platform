## Место в маршруте

Занятие связывает два результата предыдущих шагов. В 46.1 в существующей Postman collection сохранён запрос к Echo и проверен экспорт с повторным импортом; Echo подтверждает форму сообщения, но не работу Planner. Здесь мы используем уже созданный сервер: проверяем его регистрацию и ответ из Swagger UI и Postman, затем сохраняем локальную настройку для повторного вызова. Сервер и маршрут заново не создаём.

Результат 47.1 нужен занятию 48 как готовая и проверенная HTTP-точка входа: приложение запускается прежней командой, `/health` виден в OpenAPI и отвечает ожидаемым JSON, а Local environment отделён от Echo. В 48 этот сервер получит `app.state.planner` и маршруты чтения задач и статистики; установка FastAPI, создание приложения и повторное изучение Postman для этого не понадобятся. До того шага `/tasks` и `/stats` ещё не зарегистрированы.

Это прежняя учебная опора, не подтверждение прохождения новых занятий 46, 46.1 и 47. Знание Swagger или OpenAPI не предполагается. Запрос к локальному Planner из Postman Cloud Agent ранее не получил ответа; Echo и новый Local environment остаются разными настройками.
- Состояние проекта: ожидаемый вход нового маршрута задан паспортом занятия 47: в том же Planner созданы `app/api.py`, FastAPI-приложение и `GET /health`; runtime-зависимости и команда запуска находятся в проекте, `app/main.py` по-прежнему запускает CLI. Health не читает задачи. Это планируемое состояние после 47, а не утверждение о любом текущем checkout; перед прохождением его нужно сверить с фактическими файлами и запуском.
- Планируемая опора или неясность: старый урок 52 объединял создание сервера и проверку через Swagger, Postman и диагностику. Журнал подтверждает старое прохождение, но не отдельное выполнение новых 46, 46.1 и 47. В `REWORK_PLAN.md` также отмечено, что точный исторический снимок после занятия 45 не установлен. Для проверки localhost в Postman требуется Desktop Agent. Если он недоступен, конкретно вызов из Postman остаётся неподтверждённым, а не считается ошибкой приложения.

## Точка B: результат занятия

- Ученик сможет объяснить: OpenAPI отражает зарегистрированные операции; Swagger UI отправляет HTTP-запросы как клиент; HTTP-ответ с 404/405 отличается от отсутствия соединения.
- Ученик сможет сделать: проверить `GET /health` через Swagger UI и Postman, определить список зарегистрированных операций, проверить безопасный импорт CLI-модуля и отдельно запустить прежний CLI.
- Результат в проекте: сохранены и экспортированы `postman/planner-api.postman_collection.json` и `postman/local.postman_environment.json`; README дополнен проверенными адресами `/docs`, `/openapi.json` и описанием health. Echo-файлы и Python-маршруты не меняются.
- Как подтвердим: в OpenAPI есть только действующий `GET /health`, запрос возвращает HTTP 200 и `{"status":"ok"}`, неверный path даёт 404, неверный метод на health даёт 405, а остановленный сервер не выдаёт HTTP-статус. Экспорты содержат сохранённый локальный запрос и environment; импорт `app.main` не запускает меню, а отдельный запуск CLI работает прежним способом.

## 00. Вступление

Сервер уже отвечает на короткую проверку, но это ещё не говорит, какие операции он предлагает и как проверить их через интерфейс клиента. Сначала посмотрим, что FastAPI зарегистрировал, затем вызовем единственный готовый маршрут и сравним ответ с тем, что видят разные клиенты. В конце проверим, что диагностика не путает остановленный сервер с HTTP-ошибкой и что старый CLI не изменился.

1. **Точка старта:** существующий Planner и его `GET /health`, Postman с опытом отправки запросов к Echo.
2. **Новый вопрос:** как узнать, какой маршрут реально доступен, и как понять, где возникла ошибка — в соединении или в ответе приложения?
3. **Результат:** ученик проверит зарегистрированный health через Swagger и Postman, сохранит повторяемые настройки, различит 404/405 и отсутствие соединения, затем подтвердит работу CLI.

Это один путь от уже запущенного приложения к воспроизводимой проверке. Ни документация, ни клиент не создают маршруты: их источником остаётся Python-приложение.

## 01. Восстановить исходное состояние

- Что и зачем объяснить: кратко восстановить договор прошлого шага: Uvicorn запускает приложение из корня, FastAPI отвечает на `GET /health`, а этот маршрут проверяет только способность обработать запрос. Он ничего не сообщает о состоянии JSON и не доказывает работу операций Planner.
- Механизм и порядок: сначала проверить, что сервер запущен командой, уже записанной в README; затем определить схему, локальный host, порт и path health. Не повторять установку пакетов или создание `app/api.py`.
- Пример и типичная путаница: работающий CLI сам по себе не означает, что Uvicorn принимает HTTP; работающий health также не означает, что API уже читает задачи.
- Первое самостоятельное действие: по README и состоянию терминала ученик определяет, какой адрес относится к локальному серверу и какой результат относится к health. Наблюдаемый результат — адрес собирается из актуальной команды и не содержит случайного старого порта.
- Опора для повторного обращения: перед вызовом восстановить части адреса — схема, host, порт, path — и отдельно отметить, какой процесс сейчас принимает соединение.
- Переход к следующему шагу: когда исходное состояние подтверждено, можно читать список операций, который опубликовало приложение.

## 02. OpenAPI показывает зарегистрированные операции

- Что и зачем объяснить: FastAPI собирает OpenAPI из реально зарегистрированных маршрутов. `/openapi.json` — структурированное описание для инструментов; оно не является исходным кодом и не добавляет поведение в приложение.
- Механизм и порядок: от path и HTTP-метода перейти к списку `paths` в спецификации; сопоставить его с декоратором health из предыдущего шага. На этой точке в приложении есть `GET /health`; `/tasks` ещё не реализован.
- Пример и типичная путаница: наличие `/docs` и `/openapi.json` не означает наличие `/tasks`; запланированный маршрут появится в спецификации только после регистрации в коде.
- Первое самостоятельное действие: ученик находит health в OpenAPI и называет метод и path, затем объясняет отсутствие ещё не созданного `/tasks`. Результат — список спецификации не расширяется ожиданиями из будущего урока.
- Опора для повторного обращения: чтобы выяснить, существует ли операция, проверить её path и метод в OpenAPI; не делать вывод по имени функции или будущему плану.
- Переход к следующему шагу: теперь то же зарегистрированное описание можно открыть в читаемом интерфейсе Swagger UI.

## 03. Swagger UI выступает HTTP-клиентом

- Что и зачем объяснить: `/docs` показывает Swagger UI, построенный по OpenAPI. Кнопки подготовки и отправки запроса вызывают существующий маршрут; интерфейс не меняет Python-код и не создаёт endpoint.
- Механизм и порядок: найти `GET /health`, подготовить вызов, отправить его и отдельно прочитать HTTP-статус и JSON-body. Сопоставить их с заявленным результатом прошлого шага.
- Пример и типичная путаница: статус `200` — часть HTTP-ответа, а `{"status": "ok"}` — его body. Swagger не проверяет JSON-хранилище, CLI или бизнес-логику Planner.
- Первое самостоятельное действие: ученик выполняет health из Swagger и своими словами связывает отправленный метод/path со статусом и телом. Результат — один реальный запрос к зарегистрированной операции, а не только просмотр страницы.
- Опора для повторного обращения: при проверке фиксировать четыре вещи: метод и path, полученный HTTP-статус, body и процесс, которому был отправлен запрос.
- Переход к следующему шагу: для той же операции настроим отдельный, сохраняемый запрос в Postman.

## 04. Postman хранит локальную проверку отдельно от Echo

- Что и зачем объяснить: collection хранит запросы, environment — значения для их повторного использования. `base_url` задаёт локальную основу адреса без path; Echo и Planner API — разные серверы и должны оставаться отдельными ресурсами.
- Механизм и порядок: создать collection Planner API, отдельный environment Local, добавить туда адрес из проверенной команды 47 и сохранить запрос health. Затем экспортировать оба JSON-файла в `postman/`, не заменяя существующие Echo collection/environment.
- Пример и типичная путаница: успешный ответ Echo лишь отражает запрос и не доказывает работу Planner; сохранённый запрос к `127.0.0.1` должен отправляться локальным агентом Postman, а не Cloud Agent, который не может обратиться к loopback компьютера.
- Первое самостоятельное действие: ученик связывает сохранённый health-запрос с правильным Local environment, отправляет его и экспортирует collection/environment. Результат — запрос достигает того же локального сервера, а файлы содержат адрес и запрос для повторного использования.
- Опора для повторного обращения: перед отправкой проверить активное environment, значение основы URL, path, метод и выбранный агент. Не исправлять отказ Cloud Agent изменением адреса приложения.
- Переход к следующему шагу: с двумя клиентами можно сравнить ответы и научиться классифицировать неудачный вызов.

## 05. Отделить HTTP-ошибку от ошибки соединения

- Что и зачем объяснить: HTTP-статус существует только после того, как соединение принято сервером. 404 означает ответ сервера для неизвестного path; 405 — ответ для существующего path с неподдерживаемым методом; отказ соединения означает, что клиент не получил HTTP-ответ.
- Механизм и порядок: сперва проверить, запущен ли Uvicorn и верны ли host/порт; затем убедиться, что метод и path совпадают с OpenAPI; после этого прочитать статус и body. Сопоставить это с сообщениями терминала, не начиная с переустановки зависимостей.
- Пример и типичная путаница: неизвестный path при работающем сервере даёт 404, а отправка `POST` на health — 405. Если процесс остановлен, нет ни 404, ни 405. Ошибка соединения не является статусом приложения.
- Первое самостоятельное действие: по коротким наблюдениям ученик выбирает, проверять ли процесс/адрес или регистрацию метода/path. Результат — 404, 405 и отказ соединения не смешиваются.
- Опора для повторного обращения: нет ответа — проверить процесс, host и порт; есть 404 — path; есть 405 — метод; есть ожидаемый статус — сопоставить body.
- Переход к следующему шагу: когда внешняя проверка завершена, остаётся убедиться, что новые HTTP-запуски не нарушили старый CLI.

## 06. Проверить безопасный импорт и передать результат

- Что и зачем объяснить: кратко восстановить знакомую границу модуля и точки входа. Импорт `app.main` должен загрузить определения без запуска интерактивного меню; запуск CLI остаётся отдельным действием. README фиксирует только уже проверенные команды и адреса.
- Механизм и порядок: выполнить безопасную проверку импорта, отдельно запустить и завершить прежний CLI, затем дополнить README подтверждёнными адресами `/docs`, `/openapi.json` и назначением health. Не переносить запуск CLI в `app/api.py`.
- Пример и типичная путаница: импорт без меню не доказывает, что CLI завершился успешно; для этого его запускают отдельно. Успех `/health` не заменяет проверку CLI.
- Первое самостоятельное действие: ученик выбирает две раздельные проверки — импорт модуля и запуск CLI — и объясняет, какое свойство подтверждает каждая. Результат — обе точки входа сохраняют свои роли.
- Опора для повторного обращения: если импорт неожиданно ждёт ввода, проверить точку запуска CLI; если запускается сервер, проверить выбранный модуль и уже записанную команду. README изменять после проверки, не до неё.
- Переход к практике: теперь ученик может повторить весь путь без создания нового приложения и без изменения данных Planner.

## 07. Что мы будем делать в практике

**Формат и исходная опора:** manual, продолжение проекта после 47; запущенный FastAPI с `GET /health`, прежний CLI, Postman с опытом работы с Echo.

Ученик самостоятельно проверяет готовую точку входа, её описание, вызовы из двух клиентов и сохранность старого режима работы. Подсказки к подготовке ограничиваются ссылкой на README, краткой схемой частей локального URL и порядком диагностики из блоков 02–06.

1. **Проверить описание зарегистрированного API:** начать с сервера и команды из 47; открыть `/docs` и `/openapi.json`, сопоставить список методов и path с текущим health. Результат — подтверждено, что сейчас опубликован только health, а операции с задачами ещё не заявлены.
2. **Вызвать health из Swagger:** использовать опору блока 03; самостоятельно отправить запрос и сравнить status/body с результатом предыдущего шага. Результат — зарегистрированная операция действительно обрабатывает запрос и возвращает ожидаемое подтверждение.
3. **Сохранить запрос Postman:** в Planner API создать Local environment и health-запрос, сохранить collection/environment в предназначенные JSON-файлы и отправить запрос через локальный Desktop Agent. Echo-файлы остаются на месте. Результат — Postman получает ответ от Planner API, а экспорты содержат запрос и environment для повторного использования.
4. **Диагностировать разные исходы:** применить блок 05 к неизвестному path, неподдерживаемому методу и остановленному серверу. Результат — получены и объяснены 404, 405 и отсутствие HTTP-ответа; успешный health не подменяется ими.
5. **Проверить CLI и обновить передачу:** по блоку 06 проверить импорт `app.main`, отдельно запустить CLI и дополнить README адресами документации и проверенным health. Результат — CLI доступен прежним способом, а README описывает только выполненные проверки.

Блоки 02–03 готовят проверку регистрации и успешного вызова; блок 04 сохраняет её для повторения; блок 05 учит локализовать сбой; блок 06 подтверждает совместимость входов в приложение. Итог занятия — локальная API-точка health проверена через Swagger и Postman, OpenAPI соответствует текущему коду, диагностические результаты различаются, а CLI остаётся рабочим. Именно это передаётся в 48: тот же запущенный API и его health сохраняются, а следующий шаг подключает к ним чтение задач и статистики. Изменение данных, дополнительное исследование и новые endpoints в обязательный результат 47.1 не входят.
