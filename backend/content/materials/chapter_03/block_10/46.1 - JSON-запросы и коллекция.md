## 00. Вступление

В занятии 46 ученик должен был сохранить GET к Echo с параметрами в адресе (query). Сначала повторим этот запрос. Теперь отправим другой набор данных: небольшой JSON-объект **внутри** POST-запроса (body). Echo вернёт присланные значения, а сохранение и повторный импорт позволят отправить оба запроса ещё раз без сборки с нуля.

1. **Точка старта:** готовый GET с query в Planner HTTP Lab и знакомые JSON-объекты.
2. **Новый вопрос:** как отправить JSON-body и сохранить этот запрос так, чтобы его можно было воспроизвести позже?
3. **Результат:** рабочая collection с GET и POST, экспортированная вместе с Echo environment и проверенная после импорта.

Сначала выясним, **где находятся данные** запроса, затем **как записать JSON** и сообщить серверу его формат. После проверки ответа сохраним POST рядом с GET и восстановим оба запроса из файлов. Echo показывает полученное сообщение, но не создаёт задачу Planner.

## 01. Body передаёт данные запроса

- Что и зачем объяснить: **query** — пары ключ/значение после `?` в адресе, **body** — содержимое самого запроса. Здесь GET передаёт `is_done`/`limit` в query, а учебный POST — `title`/`priority` в JSON-body. Это разные места передачи данных, которые можно увидеть в Postman.
- Механизм и порядок: начать с уже сохранённого GET; сопоставить место query в URL с отдельной вкладкой Body; связать новый body с намерением отправить данные серверу. Не повторять настройку клиента или полный обзор HTTP.
- Независимый пример и типичная путаница: `/books?genre=history&limit=3` просит выбрать три книги, а JSON-отзыв о книге содержит текст и оценку. Ученик видит, что query — часть URL, body — отдельное поле запроса. **POST тоже может содержать query**; это не правило «GET = query, POST = body». Само наличие JSON не означает сохранение данных.
- Первое самостоятельное действие: для двух новых ситуаций — «показать книги одного автора» и «отправить отзыв с оценкой» — ученик выбирает query либо body и объясняет по назначению данных. Затем на знакомом GET находит Params, а на черновике POST — Body. Успех: может указать **место**, где сервер получит каждое значение, и не путает его с ответом.
- Опора для повторного обращения: для настройки списка искать Params/query; для передачи объекта открыть Body. Ожидаемое наблюдение POST — отправленные поля видны в json ответа Echo.
- Переход к следующему шагу: после выбора body нужно задать его содержимое и формат.

## 02. POST и JSON в режиме raw

- Что и зачем объяснить: метод POST задаёт отправку сообщения; режим raw позволяет ввести тело как JSON-текст. JSON уже знаком по прежней работе с объектами и значениями, поэтому достаточно восстановить имена полей, кавычки у строк и запись числа без кавычек.
- Механизм и порядок: на **непроектном** объекте `{"city": "Казань", "visits": 3}` разобрать запись по частям: `{}` ограничивают объект, `:` отделяет ключ от значения, `,` разделяет пары, ключи и строки заключены в двойные кавычки, число — без кавычек. Пояснить: JSON — текст с правилами записи, а не Python-словарь; Postman отправляет этот текст в Body → raw → JSON. Для практики ученик сам создаст **другой объект** с `title` и `priority`, не копируя готовое тело.
- Независимый пример и типичная путаница: `"visits": 3` — число, `"visits": "3"` — строка; в учебном POST нужен формат поля `"priority": 4`, где имя заключено в кавычки, а числовое значение — нет. Echo может отразить оба синтаксически корректных значения, не проверяя ограничения модели Planner; неправильный синтаксис тела не следует путать с ошибкой договора задачи.
- Первое самостоятельное действие: на другом сюжете ученик **без шаблона** записывает JSON с `item` (строка) и `count` (число), проверяет `:` и `,`, сравнивает число с вариантом `"count": "3"` и предсказывает различие типов. Затем самостоятельно выбирает в Postman POST `{{base_url}}/post`, raw → JSON и готовит своё тело с `title`/`priority`; результат — корректная форма Body, понятная до отправки.
- Опора для повторного обращения: перед отправкой сверить, что body выбран как raw/JSON, имена полей совпадают с договором упражнения, строка заключена в кавычки, число записано без кавычек.
- Переход к следующему шагу: тело подготовлено; теперь запрос должен сообщить серверу, что отправленный текст имеет формат JSON.

## 03. Content-Type и отражённый ответ Echo

- Что и зачем объяснить: Content-Type описывает формат исходящего body. При выборе JSON Postman выставляет application/json; не нужно добавлять второй одинаковый заголовок вручную. Заголовок запроса относится к отправляемому body, а headers ответа описывают уже ответ.
- Механизм и порядок: до отправки проверить JSON-режим и заголовок; отправить POST; прочитать status и body ответа; найти отправленный объект в json. Сопоставить это с прежним GET, где параметры видны в args.
- Независимый пример и типичная путаница: один и тот же текст `{"note": "готово"}` в raw/Text и raw/JSON может выглядеть одинаково. Но `Content-Type: text/plain` сообщает «простой текст», а `application/json` — «JSON». Поэтому проверяем **заголовок запроса**, а не похожие headers ответа. Статус 200 от Echo означает получение ответа Echo; Echo не вызывает `POST /tasks` и не создаёт задачу. Ошибка подключения не является HTTP-ответом со статусом.
- Первое самостоятельное действие: ученик предсказывает, чем отличаются отправка тела как Text и как JSON, выбирает raw/JSON, находит `Content-Type: application/json` именно в request headers; после Send сам открывает ответ и указывает status, `json.title`, **числовой** `json.priority`. Успех — все значения совпали и ученик объясняет, почему это ещё не означает сохранения задачи. При сетевой ошибке проверка ответа остаётся незавершённой.
- Опора для повторного обращения: для POST проверить status, Content-Type запроса и объект json ответа; не выводить сохранение в Planner из зелёного status.
- Переход к следующему шагу: после проверки запрос нужно сохранить в существующей collection, а не оставлять только в открытой вкладке.

## 04. Сохранить POST в существующей collection

- Что и зачем объяснить: collection хранит воспроизводимую конфигурацию запросов; environment содержит переменные окружения, в этом случае базовый адрес Echo. Это разделение уже было введено в 46 и здесь только применяется.
- Механизм и порядок: перед сохранением показать различие вкладки незаписанного запроса и записи внутри collection. Сохранить новый POST **в существующую** Planner HTTP Lab; проверить, что прежний GET не перезаписан, а Echo environment всё ещё содержит `base_url` и выбрано. Для POST имя запроса должно ясно отличаться от GET.
- Независимый пример и типичная путаница: представить **две строки** в collection — `GET {{base_url}}/get` и `POST {{base_url}}/post`, а рядом **одну настройку** в Echo environment — `base_url = https://postman-echo.com`. Закрыть вкладку запроса и предсказать, что останется в collection; переключить environment и предсказать, раскроется ли `{{base_url}}`. Если создать другую collection или оставить POST как черновик, два сценария не будут сохранены вместе.
- Первое самостоятельное действие: ученик проверяет, что GET из 46 **уже сохранён** (если остался черновиком — сохраняет), добавляет POST в ту же `Planner HTTP Lab`, закрывает черновую вкладку и открывает POST **из collection**. Результат — в ней два отдельных запроса, старый GET работает как прежде, у POST сохранились метод, путь и тело.
- Опора для повторного обращения: запросы находятся в collection, изменяемый базовый адрес — в environment; путь /get или /post и содержимое запроса остаются частью соответствующего сценария.
- Переход к следующему шагу: проверить переносимость можно экспортом обоих артефактов и последующим импортом.

## 05. Экспорт, импорт и повторная проверка

- Что и зачем объяснить: экспорт создаёт файлы для переноса сохранённых запросов и окружения; импорт проверяет, что они восстанавливаются отдельно от открытого состояния Postman. В экспорте остаются только безопасные учебные значения, без паролей, токенов и личных данных.
- Механизм и порядок: **экспорт collection** сохраняет два шаблона запросов в `postman/planner-http-lab.postman_collection.json`, **экспорт environment** — настройку адреса в `postman/echo.postman_environment.json`. Проверить оба файла, затем импортировать **копии обоих ресурсов**. Явно выбрать импортированную collection и импортированный Echo (при совпадении имён отличить их от оригиналов), убедиться, что `base_url` раскрывается в `https://postman-echo.com`; отправить GET и POST заново. Если интерфейс предлагает заменить оригиналы, выбрать импорт отдельной копии без потери исходных запросов.
- Независимый пример и типичная путаница: два рецепта можно перенести в другой блокнот, но адрес магазина к ним не приложится сам — аналогично collection и environment экспортируются **отдельно**. Наличие `base_url` в рабочем Postman ещё не гарантирует, что его значение **экспортировано**: открыть второй файл и проверить значение до импорта. Если его нет, настроить экспорт несекретного значения средствами текущей версии Postman, экспортировать заново и повторить проверку. Ручной ввод адреса только после импорта не доказывает переносимость файлов.
- Первое самостоятельное действие: ученик экспортирует оба ресурса, импортирует их и **открывает запросы из импортированной collection**; с выбранным импортированным Echo выполняет GET и POST. Локальный критерий — GET повторяет `is_done=false` и `limit=2` в `args` как строки, POST отражает выбранный учеником `title` и числовой `priority` в `json`. Если `{{base_url}}` не раскрылся, сначала проверить выбранный environment и экспортированное значение; если ответ не получен, отличить сетевую ошибку от HTTP-status и зафиксировать, что подтверждение повторяемости пока отсутствует.
- Опора для повторного обращения: после импорта сначала активировать Echo environment, затем проверить полный адрес и содержание каждого ответа; не считать открытие файлов доказательством повторяемости.
- Переход к практике: теперь можно выполнить полный маршрут — добавить один POST к готовому GET, сохранить оба артефакта и доказать восстановление сценариев.

## 06. Что мы будем делать в практике

**Формат и исходная опора:** обязательная **UI-практика в Postman** (BLOCK_10 §4, паспорт 46.1, п. 5). Вход — **планируемая B занятия 46**: существующая `Planner HTTP Lab` с сохранённым GET `{{base_url}}/get`, query `is_done=false`, `limit=2`, а также `Echo` с `base_url=https://postman-echo.com`. Перед практикой ученик открывает **сохранённый** GET, выбирает окружение, отправляет запрос и показывает `args.is_done = "false"` и `args.limit = "2"`. При отсутствии опоры восстановить её по разделам 03–05 плана 46 и повторить проверку; факт выдачи 46 пока не подтверждён.

В той же collection появится POST к Postman Echo с JSON-объектом, затем collection и environment будут экспортированы в `postman/` существующего проекта и восстановлены импортом. Ученик проверит повторяемость запросов и объяснит границу между отражённым сообщением и поведением Planner.

1. **Самостоятельно собрать и проверить POST-body:** **вход** — работающий сохранённый GET из 46 и выбранное `Echo`; **объект** — новый POST `{{base_url}}/post` в Postman; **опора** — разделы 01–03, различие query/body, синтаксис объекта, raw/JSON и заголовок запроса. **Действие ученика** — придумать собственный `title`, выбрать числовой `priority` (1–5), записать JSON-body, проверить `Content-Type: application/json`, отправить запрос. **Локальный результат** — при доступном Echo получен HTTP-ответ (обычно status 200), `json.title` совпадает с введённой строкой, `json.priority` остаётся числом. **Различающий случай:** до Send объяснить, почему кавычки вокруг числа сделали бы его строкой; GET с query не заменяется POST. При отсутствии ответа ученик проверяет URL/environment/сеть, не подменяет успех цветом индикатора.
2. **Сохранить оба запроса и получить два файла:** **вход** — отправленный POST и существующий GET; **объект** — `Planner HTTP Lab` и `Echo`; **опора** — разделы 04–05. **Действие ученика** — убедиться, что GET записан в collection; сохранить POST **отдельной записью** рядом с ним, закрыть вкладку черновика и повторно отправить POST из collection. Затем самостоятельно экспортировать collection в `postman/planner-http-lab.postman_collection.json` и environment в `postman/echo.postman_environment.json`. **Локальный результат** — два запроса в первом файле и `base_url` с переносимым адресом во втором. **Различающий случай:** экспорт одной collection не переносит значение переменной; при отсутствии `base_url` в файле окружения исправить экспорт и проверить файл повторно. Секреты в файлы не добавлять.
3. **Повторно импортировать и воспроизвести:** **вход** — два экспортированных файла из шага 2; **объект** — **импортированные** collection и environment; **опора** — раздел 05 и ранее освоенная проверка частей HTTP-ответа из занятия 46. **Действие ученика** — импортировать оба файла, в случае совпадения имён однозначно выбрать импортированную копию, активировать её Echo, проверить раскрытый URL и отправить оба запроса из неё. **Локальный результат** — GET отражает `is_done="false"`, `limit="2"` в `args`, POST отражает выбранные `title`/числовой `priority` в `json`; метод, path и body не пришлось вводить повторно. **Различающий случай:** неверно выбранное окружение или отсутствующее экспортируемое значение `base_url` выявляются до Send; сетевой отказ не считается HTTP-ответом и не засчитывается как успешное восстановление.

Последовательность наращивает самостоятельность: составить JSON самому (опоры 01–03) → сохранить запрос и проверить файлы (04–05) → без ручной пересборки воспроизвести **оба** запроса из импортированных копий. Если не получается, вернуться к 02–03 для JSON/заголовка, к 04 для сохранения, к 05 для импорта и `base_url`. Каждый локальный результат проверяется до следующего шага.

Итоговый критерий: из импортированных артефактов повторно выполняются GET и POST с ожидаемыми значениями в разных частях Echo-ответа. Это подтверждает воспроизводимость HTTP-сценариев, но не работу Planner API и не появление Task. В занятии 47 ученик использует Postman для собственного `/health`, а в 47.1 сравнивает его с вызовом через Swagger UI; это **планируемая** передача по паспортам, не подтверждение проведённых занятий.
