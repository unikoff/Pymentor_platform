## 00. Вступление

В плане занятия 46 предусмотрен сохранённый GET к Echo с query. Сначала мы проверим, что он повторяется и выбран `Echo` environment. Затем передадим не параметры списка в адресе, а структурированный объект в теле запроса и сохраним оба сценария для повторного использования. Postman отправит POST к Echo, Echo отразит полученный объект, а импортированные файлы подтвердят, что запросы можно восстановить.

1. **Точка старта:** готовый GET с query в Planner HTTP Lab и знакомые JSON-объекты.
2. **Новый вопрос:** как отправить JSON-body и сохранить этот запрос так, чтобы его можно было воспроизвести позже?
3. **Результат:** рабочая collection с GET и POST, экспортированная вместе с Echo environment и проверенная после импорта.

Эти три точки связаны одним маршрутом: сначала ученик различит body и query, затем разберёт JSON и его заголовок формата. После отправки POST он проверит отражённое тело ответа, добавит запрос в уже созданную collection и проверит переносимость обоих запросов. В проверке различаются ответ Echo и сохранённое состояние Planner.

## 01. Body передаёт данные запроса

- Что и зачем объяснить: query добавляет параметры к адресу, а body передаёт содержимое сообщения. Для нового POST договора Planner поля title и priority располагаются в JSON-body; GET из прошлого занятия остаётся примером параметров в адресе.
- Механизм и порядок: начать с уже сохранённого GET; сопоставить место query в URL с отдельной вкладкой Body; связать новый body с намерением отправить данные серверу. Не повторять настройку клиента или полный обзор HTTP.
- Независимый пример и типичная путаница: поиск книг `/books?genre=history&limit=3` передаёт критерии отбора в query; отзыв о книге мог бы передавать JSON-body с названием и оценкой. Аналогия «надпись на конверте / содержимое вложенного письма» показывает две области, но не закрепляет их за GET или POST навсегда: POST тоже может иметь query, а JSON-body сам по себе не создаёт запись. В Echo GET-параметры отражены в `args`, JSON POST — в `json`.
- Первое самостоятельное действие: по независимым карточкам «отбор трёх книг» и «отзыв с оценкой» ученик выбирает область request для каждой группы данных и обосновывает выбор; затем на знакомой паре GET/POST показывает их в Params и Body. Критерий — значения не переносятся из body в query только потому, что оба доступны в Postman.
- Опора для повторного обращения: для настройки списка искать Params/query; для передачи объекта открыть Body. Ожидаемое наблюдение POST — отправленные поля видны в json ответа Echo.
- Переход к следующему шагу: после выбора body нужно задать его содержимое и формат.

## 02. POST и JSON в режиме raw

- Что и зачем объяснить: метод POST задаёт отправку сообщения; режим raw позволяет ввести тело как JSON-текст. JSON уже знаком по прежней работе с объектами и значениями, поэтому достаточно восстановить имена полей, кавычки у строк и запись числа без кавычек.
- Механизм и порядок: показать безопасный **непроектный** JSON-объект `{"city": "Казань", "visits": 3}`, указать фигурные скобки, двойные кавычки у ключей и строк, двоеточие между именем и значением. Затем в Postman выбрать POST, `{{base_url}}/post`, Body → raw → JSON; ученик **сам** переносит известную форму на поля предметного упражнения `title` и `priority`. Отделить интерфейсную настройку от проверки правил Planner.
- Независимый пример и типичная путаница: `"visits": 3` — число, `"visits": "3"` — строка; в учебном POST нужен формат поля `"priority": 4`, где имя заключено в кавычки, а числовое значение — нет. Echo может отразить оба синтаксически корректных значения, не проверяя ограничения модели Planner; неправильный синтаксис тела не следует путать с ошибкой договора задачи.
- Первое самостоятельное действие: ученик сам задаёт новое `title` и числовой `priority` (например, в пределах знакомого диапазона 1–5), вводит полноценный JSON-object в raw/JSON и до Send объясняет, почему поле `priority` останется числом; результат — корректное тело в Body без переноса полей в Params.
- Опора для повторного обращения: перед отправкой сверить, что body выбран как raw/JSON, имена полей совпадают с договором упражнения, строка заключена в кавычки, число записано без кавычек.
- Переход к следующему шагу: чтобы сервер прочитал тело в нужном формате, запрос должен сообщить тип содержимого.

## 03. Content-Type и отражённый ответ Echo

- Что и зачем объяснить: Content-Type описывает формат исходящего body. При выборе JSON Postman выставляет application/json; не нужно добавлять второй одинаковый заголовок вручную. Заголовок запроса относится к отправляемому body, а headers ответа описывают уже ответ.
- Механизм и порядок: до отправки проверить JSON-режим и заголовок; отправить POST; прочитать status и body ответа; найти отправленный объект в json. Сопоставить это с прежним GET, где параметры видны в args.
- Независимый пример и типичная путаница: в условном сообщении `{"note": "готово"}` с заголовком `Content-Type: text/plain` байты могут быть похожи на JSON, но заголовок заявляет **текст**, а не JSON; выбор raw/JSON в Postman должен привести к `application/json` в **request headers**. Не путать этот заголовок с `Content-Type` ответа. Полученный status 200 относится к Echo, не к созданию Task: Echo не подключён к JSON-файлу Planner, не назначает id и не исполняет `POST /tasks`. Ошибка соединения также не является HTTP-ответом со status.
- Первое самостоятельное действие: до Send ученик находит фактически отправляемый `Content-Type` и объясняет его роль; после Send сверяет status, поле `json.title` и **тип** `json.priority` с собственным запросом. Критерий — значения совпадают, при нормальном сетевом ответе отражаются Echo, ученик не делает вывод о сохранении в Planner. Если ответа нет, отдельно проверяются активное окружение, раскрытый URL и сеть; без успешного ответа шаг не засчитывается.
- Опора для повторного обращения: для POST проверить status, Content-Type запроса и объект json ответа; не выводить сохранение в Planner из зелёного status.
- Переход к следующему шагу: после проверки запрос нужно сохранить в существующей collection, а не оставлять только в открытой вкладке.

## 04. Сохранить POST в существующей collection

- Что и зачем объяснить: collection хранит воспроизводимую конфигурацию запросов; environment содержит переменные окружения, в этом случае базовый адрес Echo. Это разделение уже было введено в 46 и здесь только применяется.
- Механизм и порядок: перед сохранением показать различие вкладки незаписанного запроса и записи внутри collection. Сохранить новый POST **в существующую** Planner HTTP Lab; проверить, что прежний GET не перезаписан, а Echo environment всё ещё содержит `base_url` и выбрано. Для POST имя запроса должно ясно отличаться от GET.
- Независимый пример и типичная путаница: как список рецептов хранит шаги приготовления, а отдельная карточка адреса указывает, где получить ингредиенты, collection хранит методы, URL-шаблоны и body запросов, а environment — значения переменных. Аналогия не гарантирует подстановку: без выбранного Echo `{{base_url}}` может остаться неразрешённым. Создание второй collection вместо выбора Planner HTTP Lab разносит два учебных сценария.
- Первое самостоятельное действие: ученик сохраняет POST в уже существующую Planner HTTP Lab, возвращается к **сохранённой** записи и повторно отправляет её. Результат — в одной collection два различимых запроса, GET не изменился, метод/путь/body POST восстанавливаются после закрытия вкладки. Если сохранён только открытый черновик, локальный критерий не выполнен.
- Опора для повторного обращения: запросы находятся в collection, изменяемый базовый адрес — в environment; путь /get или /post и содержимое запроса остаются частью соответствующего сценария.
- Переход к следующему шагу: проверить переносимость можно экспортом обоих артефактов и последующим импортом.

## 05. Экспорт, импорт и повторная проверка

- Что и зачем объяснить: экспорт создаёт файлы для переноса сохранённых запросов и окружения; импорт проверяет, что они восстанавливаются отдельно от открытого состояния Postman. В экспорте остаются только безопасные учебные значения, без паролей, токенов и личных данных.
- Механизм и порядок: по очереди экспортировать collection и `Echo` environment в каталог `postman/` существующего проекта под именами `planner-http-lab.postman_collection.json` и `echo.postman_environment.json`; проверить, что файлы существуют и содержат **два разных типа ресурса** (запросы GET/POST в collection, переменную `base_url` в environment). Затем импортировать **оба файла** и выбрать именно импортированные объекты, даже если Postman сохранил рядом одноимённые исходники; явно выбрать импортированное Echo, проверить адрес `https://postman-echo.com`, снова отправить GET/POST и сравнить отражённые данные. При возникновении вопроса о замене существующих ресурсов использовать безопасный отдельный экземпляр/копию в интерфейсе, не стирать проверенный источник.
- Независимый пример и типичная путаница: перенос одной папки с шаблонами без отдельной адресной карточки не восстанавливает конечный адрес. Экспорт collection сам по себе не экспортирует environment. Сохранённое локально значение переменной не следует **предполагать** присутствующим в переносимом JSON: проверить `base_url` в экспортированном файле и после импорта. Если оно отсутствует, решить средствами доступной версии Postman, как включить несекретное учебное значение в экспорт, затем повторить экспорт/импорт; одной ручной подстановки **после импорта** недостаточно для доказательства переносимости.
- Первое самостоятельное действие: ученик экспортирует оба ресурса, импортирует их и **открывает запросы из импортированной collection**; с выбранным импортированным Echo выполняет GET и POST. Локальный критерий — GET повторяет `is_done=false` и `limit=2` в `args` как строки, POST отражает выбранный учеником `title` и числовой `priority` в `json`. Если `{{base_url}}` не раскрылся, сначала проверить выбранный environment и экспортированное значение; если ответ не получен, отличить сетевую ошибку от HTTP-status и зафиксировать, что подтверждение повторяемости пока отсутствует.
- Опора для повторного обращения: после импорта сначала активировать Echo environment, затем проверить полный адрес и содержание каждого ответа; не считать открытие файлов доказательством повторяемости.
- Переход к практике: теперь можно выполнить полный маршрут — добавить один POST к готовому GET, сохранить оба артефакта и доказать восстановление сценариев.

## 06. Что мы будем делать в практике

**Формат и исходная опора:** manual по текущему плану (обязательность по отсутствующему паспорту ещё не подтверждена). Работа в Postman. Начинаем с **планируемой B занятия 46**: `Planner HTTP Lab` с сохранённым GET `{{base_url}}/get` и query `is_done=false`, `limit=2`, `Echo` с `base_url=https://postman-echo.com`. До самостоятельных действий открыть **сохранённый** GET, проверить активное окружение и фактический ответ (при доступной сети status 200 и `args` со строковыми значениями). Если передача не сложилась, восстановить её по разделам 03–05 предыдущего плана, не выдавая восстановление за результат текущего упражнения.

В той же collection появится POST к Postman Echo с JSON-объектом, затем collection и environment будут экспортированы в `postman/` существующего проекта и восстановлены импортом. Ученик проверит повторяемость запросов и объяснит границу между отражённым сообщением и поведением Planner.

1. **Самостоятельно собрать и проверить POST-body:** **вход** — работающий сохранённый GET из 46 и выбранное `Echo`; **объект** — новый POST `{{base_url}}/post` в Postman; **опора** — разделы 01–03, различие query/body, синтаксис объекта, raw/JSON и заголовок запроса. **Действие ученика** — придумать собственный `title`, выбрать числовой `priority` (1–5), записать JSON-body, проверить `Content-Type: application/json`, отправить запрос. **Локальный результат** — при доступном Echo получен HTTP-ответ (обычно status 200), `json.title` совпадает с введённой строкой, `json.priority` остаётся числом. **Различающий случай:** до Send объяснить, почему кавычки вокруг числа сделали бы его строкой; GET с query не заменяется POST. При отсутствии ответа ученик проверяет URL/environment/сеть, не подменяет успех цветом индикатора.
2. **Сохранить запрос и получить два файла:** **вход** — выполненный POST из шага 1 и прежний GET; **объект** — существующая collection `Planner HTTP Lab` и environment `Echo`; **опора** — разделы 04–05. **Действие ученика** — сохранить POST **как отдельную запись** в той же collection, повторно открыть и отправить именно сохранённый POST; экспортировать collection в `postman/planner-http-lab.postman_collection.json` и environment в `postman/echo.postman_environment.json`. **Локальный результат** — в collection остаются GET и POST, в export collection присутствуют оба запроса, а export environment содержит `base_url` с переносимым учебным значением. **Различающий случай:** одного JSON-файла collection без environment недостаточно; при отсутствующем в export значении base_url скорректировать экспорт средствами интерфейса и перепроверить файл, не заносить секреты.
3. **Повторно импортировать и воспроизвести:** **вход** — два экспортированных файла из шага 2; **объект** — **импортированные** collection и environment; **опора** — раздел 05 и ранее освоенная проверка частей HTTP-ответа из занятия 46. **Действие ученика** — импортировать оба файла, в случае совпадения имён однозначно выбрать импортированную копию, активировать её Echo, проверить раскрытый URL и отправить оба запроса из неё. **Локальный результат** — GET отражает `is_done="false"`, `limit="2"` в `args`, POST отражает выбранные `title`/числовой `priority` в `json`; метод, path и body не пришлось вводить повторно. **Различающий случай:** неверно выбранное окружение или отсутствующее экспортируемое значение `base_url` выявляются до Send; сетевой отказ не считается HTTP-ответом и не засчитывается как успешное восстановление.

Эти три действия образуют связанный маршрут: разделы 01–03 готовят форму POST и чтение результата, разделы 04–05 — сохранение и переносимость. После первого объяснения ученик самостоятельно формирует JSON, затем самостоятельно сохраняет запросы и восстанавливает их из файлов. Если ошибка возникла в формате тела, он возвращается к 02–03; если не найден запрос — к 04; если не подставился `base_url` — к 05. Каждая проверка выполняется до следующего шага.

Итоговый критерий: из импортированных артефактов повторно выполняются GET и POST с ожидаемыми значениями в разных частях Echo-ответа. Это подтверждает воспроизводимость HTTP-сценариев, но не работу Planner API и не появление Task. В занятии 47 эта клиентская опора сопровождает создание собственного health-маршрута; в 47.1 настройки Planner API сохраняются отдельно, рядом с новым `Local` environment.

В приложении меняются только два экспортированных Postman-файла в postman/. CLI, JSON-хранилище, Python-код и будущий FastAPI-сервер остаются прежними. Дальше коллекция Echo служит учебным образцом, а занятие 47 отдельно добавляет собственный health-маршрут Planner.
