## 00. Вступление

В Planner уже есть полный список задач и сервисная операция, которая умеет подготовить нужную часть списка. Теперь клиенту нужно задать условия чтения, не создавая отдельный адрес для каждой комбинации.

1. **Точка старта:** Существующий `GET /tasks` читает задачи через Planner; сервисная выборка готова и проверена отдельно.
2. **Новый вопрос:** Как клиент передаёт фильтр, направление сортировки и предел списка, и где FastAPI проверяет эти значения?
3. **Результат:** Параметры URL попадают в прежний маршрут, затем в `select_tasks`; контракт ответа и состояние Planner сохраняются.

Сначала разберём место и типы параметров, затем их значения по умолчанию и границы. После этого подключим их к существующему маршруту и проверим, что HTTP только формирует представление списка, а не меняет источник данных.

## 01. Query настраивает чтение коллекции

- **Что и зачем объяснить:** Путь (`path`) указывает ресурс; пары после `?` уточняют условия одного запроса к нему. В `/tasks?is_done=false&limit=10` адрес коллекции остаётся `/tasks`, а query содержит две пары `имя=значение`, разделённые `&`. Это настройки чтения, не часть имени файла, не JSON body и не новый endpoint.
- **Независимая опора и наглядное сравнение:** В библиотечном каталоге `/books/7` — конкретная книга, `/books?limit=7` — до семи книг из общего каталога. Аналогия «полка книг и условия поиска» помогает отличить *что читаем* от *как отображаем*; в HTTP реально передаются текст и значения параметров, сама полка не определяет формат запроса. Наглядно подсветить на одной строке URL путь, `?`, пары и `&`; порядок пар не меняет значение разных параметров.
- **Пример и путаница:** `GET /tasks/7` выбирает item с идентификатором 7, `GET /tasks?limit=7` — коллекцию с максимум семью элементами. Если семи задач нет, limit не создаёт недостающие. Не путать `?` с `/` и не писать `limit` как path-id.
- **Первое действие ученика:** На готовых `GET /books/3`, `GET /books?available=false&limit=3` самостоятельно подчеркнуть путь, выписать имена и текстовые значения query, сказать «item или collection» и объяснить причину. Локальная проверка: в первом случае query нет, во втором есть две пары, обе относятся к списку; затем ученик строит другой URL с тем же путём и переставленными парами. При затруднении вернуться к разметке URL, не к готовому коду Planner.
- **Переход к следующему шагу:** После определения места параметра выяснить, как текст из URL становится значением Python.

## 02. FastAPI преобразует query в типизированные значения

- **Что и зачем объяснить:** URL содержит текст: символы `false` ещё не Python-значение `False`, а `12` ещё не `int`. FastAPI при обращении к обработчику читает query по имени параметра, пытается привести текст к типу из аннотации (`bool`, `int`) и только после успешной проверки вызывает функцию. Неудачный разбор даёт HTTP 422 с описанием ошибки; тело обработчика и `select_tasks` в этом случае не выполняются.
- **Порядок и опора:** Напомнить `имя: тип = значение_по_умолчанию` на знакомой функции; для query показать соответствие `?sort_desc=true&limit=12` → аргументы `True` и `12`. `Request` по-прежнему нужен для `request.app.state.planner`, но не является источником вручную разбираемых строк. Сделать схему «URL-текст → FastAPI: имя, тип, проверка → аргументы Python → обработчик».
- **Независимый пример и путаница:** У каталога `?available=false&limit=3` текст становится `False` и `3`; `?available=maybe&limit=three` содержит неподходящие типам значения, запрос отклоняется до функции. `422` здесь означает неверные данные запроса, а `404` из предыдущего урока — конкретный item не найден после разбора корректного id. Не учить ручному `bool("false")`: в Python эта запись дала бы `True`, что как раз объясняет необходимость FastAPI-проверки.
- **Первое действие ученика:** Для трёх URL каталога — валидного, с `limit=many` и с `available=maybe` — самому заполнить колонки «сырой текст / ожидаемый Python-тип и значение / будет ли вызвана функция». Локальный результат: для неверного поля указан 422 и отсутствие вызова; на изменённом URL с `limit=5` ученик повторяет прогноз без подсказки. При ошибке вернуться к схеме преобразования.
- **Переход к следующему шагу:** Для корректных типов важно сохранить различие между отсутствующим фильтром и явно переданной логической величиной.

## 03. Пропуск, True и False; HTTP-default и сервисный default

- **Что и зачем объяснить:** `is_done: bool | None = None` различает три запроса: параметра нет → `None` (все статусы), `is_done=true` → `True` (готовые), `is_done=false` → `False` (неготовые). Проверка `if is_done:` ошибочно отбросила бы явное `False`; готовый сервис умеет отличать его от `None`. `sort_desc: bool = False` оставляет возрастание `id`, если направление не передали.
- **Независимый пример:** На четырёх книгах каталога с ID 2, 5, 8, 11 и признаками `available = True, False, True, False` показать три разных результата: без `available` все четыре, с `true` ID 2/8, с `false` ID 5/11. Это модель трёх состояний, не решение проектной задачи. На схеме «отбор → порядок → ограничение» подчеркнуть, что `limit=1` после фильтра `false` выберет 5, а ограничение до фильтра ошибочно даст пустой список.
- **Два независимых значения по умолчанию:** Для HTTP `limit` без параметра равен `10`; прямой вызов сервисного `select_tasks(..., limit=None)` по договору 49 не обрезает список. API передаёт сервису конкретное число, CLI продолжает получать весь список через `list_tasks`. Если фильтру не соответствует ни одна запись, это корректные `200` и `[]`, а не 404.
- **Первое действие ученика:** На четырёх книгах самостоятельно записать три строки «пропуск/true/false → аргумент → ID после фильтра»; для `available=false&limit=1` объяснить, почему результат не пуст. Затем сравнить `GET /tasks` без `limit` и прямой сервисный вызов без `limit`, назвать ожидаемую границу каждого. Ошибка «False значит нет фильтра» возвращает к таблице, ошибка «сервис тоже ограничивает до 10» — к двум сигнатурам.
- **Опора для повторного обращения:** При запросах восстановить таблицу трёх значений `is_done` и правило «HTTP без limit → 10; прямой вызов сервиса с None → полный результат»; характерная ошибка — принять False за пропуск либо показать CLI только десять задач.
- **Переход к следующему шагу:** Смысл значений определён; теперь зададим серверные границы для `limit`.

## 04. Query задаёт включительные границы limit

- **Что и зачем объяснить:** `Query` из `fastapi` описывает один параметр HTTP-запроса. В форме `limit: int = Query(default=10, ge=1, le=50)` двоеточие задаёт требуемый тип, `default` — число при пропуске, `ge` означает «больше либо равно», `le` — «меньше либо равно». Обе границы **включены**; допустимы 1 и 50, а 0, 51 и нечисловой текст приводят к 422 до запуска handler.
- **Порядок:** Восстановить знакомый импорт `from fastapi import Query`, разобрать сигнатуру слева направо, затем показать путь «строка → int → проверка 1 ≤ limit ≤ 50 → вызов функции». Для новичка вторая наглядная опора — контролёр билетов: на вход допускается только корректное число мест в разрешённых пределах; это лишь образ проверки, реальный FastAPI отвечает HTTP 422, а не меняет число на ближайшую границу.
- **Пример и путаница:** В независимом каталоге допустимо попросить 1 или 50 записей, а 0 и 51 отвергаются, даже если каталог маленький. Число фактически возвращённых записей может быть меньше limit: это верхняя граница размера ответа, не обещание заполнить ответ до 50. Проверка принадлежит HTTP-границе, а не `PlannerService` или классу Task.
- **Первое действие ученика:** По сигнатуре и значениям «параметр отсутствует / 1 / 50 / 0 / 51 / many» самостоятельно отметить принятое число либо 422 и назвать проверку, которая сработала. Критерий: 1 и 50 включены, пропуск даёт 10, недопустимое значение не исправляется автоматически. Если ученик путает `ge` и `le`, вернуться к числовой прямой с отмеченными краями.
- **Переход к следующему шагу:** После объяснения типов и ограничений можно связать query с готовой сервисной операцией.

## 05. Подключить параметры к существующему GET /tasks

- **Что и зачем объяснить:** В `app/api.py` меняется **существующий** обработчик `GET /tasks`: объявленные `is_done`, `sort_desc`, `limit` FastAPI подаст ему уже как Python-значения. Обработчик передаёт их в `request.app.state.planner.select_tasks` по именам и применяет уже существующее формирование четырёх публичных полей. Новая логика фильтрации, сортировки, чтения JSON или отдельный endpoint здесь не нужны.
- **Механизм и схема:** Сопоставить две цепочки на одном реальном состоянии: CLI → `list_tasks()` → полный список; HTTP URL → FastAPI → handler → `select_tasks(...)` → прежняя проекция → ограниченный JSON. Указать место общего `PlannerService` в обеих цепочках. Из 48 повторить доступ через `Request.app.state.planner` только в объёме, необходимом для самостоятельной записи вызова.
- **Путаница и сохранённое поведение:** `limit` ограничивает только HTTP-ответ. `GET /stats` продолжает считать все задачи, item-чтение не зависит от query списка, CLI выдаёт полный набор; `tags` живёт в Task/JSON, но не публикуется, ответ содержит `id`, `title`, `priority`, `is_done`.
- **Первое действие ученика:** В знакомом обработчике самостоятельно выбрать место трёх аргументов и именованного вызова сервиса; до написания предсказать, что вернёт URL без параметров и URL с `is_done=false&limit=1`. После изменения отправить оба запроса, сравнить `id` с заранее рассчитанными для своих данных и четыре поля JSON. Критерий: результат отличается там, где условия отличаются, а CLI остаётся полным. При ошибке вернуться к таблице defaults в 03 и цепочке вызова в 05, не переносить алгоритм из 49 в endpoint.
- **Опора для повторного обращения:** Перед вызовом восстановить три параметра и их значения по умолчанию; после ответа сверить фильтр, направление по `id`, limit и четыре поля. Характерная ошибка — снова вызвать `list_tasks`, применить сервисный `None` к HTTP-default либо обрезать данные в маршруте.
- **Переход к практике:** Маршрут подключён; теперь проверяются обычный запрос, различающие значения, границы и сохранность проекта.

1. **Разобрать вход до кода:** на знакомом Echo из 46 (или на записи уже отправленного там запроса) ученик сам составляет URL с двумя текстовыми параметрами, отмечает путь/пары и объясняет, что сервер получит как текст (раздел 01). Затем на маленьком наборе с `id` и состояниями из 49 сам рассчитывает «фильтр → сортировка по ID → начало длины limit» для пропущенного фильтра, `false` и изменённого направления (разделы 02–03). **Критерий:** самостоятельная строка URL и два объяснимо разных списка ID; если нет, вернуть конкретную опору 46/49 до правки API.
2. **Зафиксировать исходное состояние Planner:** в прежнем CLI ученик получает полный список и проверяет, что в нём **больше 10 задач**, встречаются оба `is_done` и есть задача со статусом, противоположным статусу минимального ID. Если данных хватает, ничего не добавляет; иначе добавляет недостающие реальные записи **через CLI в тот же JSON**, не удаляя и не переписывая старые, проверяет сохранение после повторного запуска. **После** такой подготовки фиксирует исходный полный CLI-list, JSON (включая внутренние `tags`), `GET /stats` и один существующий item для будущего сравнения. **Критерий:** контрольный набор позволяет различить HTTP-default 10, фильтр `False` и ошибочный порядок limit/фильтра; именно это состояние станет базой проверки неизменности.
3. **Самостоятельно подключить query в существующем GET:** по разделам 02–05 ученик меняет лишь обработчик `GET /tasks` в `app/api.py`: объявляет `is_done` с пропуском `None`, `sort_desc=False` и `limit` через `Query` с default 10 и включительными границами 1/50; передаёт три Python-значения **по именам** в уже реализованный `request.app.state.planner.select_tasks`. Существующее формирование JSON из `id/title/priority/is_done` сохраняет, `list_tasks`, CLI, item, stats и storage не редактирует. **Критерий:** URL без query отвечает 200 прежней формой, допустимый фильтр меняет выбранные ID; сами правила выборки заново не написаны.
4. **Проверить обычные запросы на собственных данных:** до отправки каждого запроса ученик выписывает ожидаемые ID из **полного** CLI-list; отправляет запрос без query (при >10 элементах это ровно первые 10 ID по возрастанию), отдельно `is_done=true`, `is_done=false`, оба `sort_desc` и `limit=1`, `limit=50`. Сопоставляет каждый HTTP-ответ с ручной последовательностью «фильтр → сортировка по id → limit», причём `limit=50` может вернуть меньше пятидесяти элементов. **Критерий:** у каждого успешного ответа 200, нужный порядок и лишь четыре публичных поля. Отдельно ученик объясняет гипотетический случай нуля совпадений: это `200` и `[]`; ради него не удаляем задачи из рабочего JSON.
5. **Поймать отличие `False` от пропуска и неправильный порядок операций:** выбрать статус, **противоположный** статусу задачи с минимальным ID, и вручную найти минимальный ID среди задач этого статуса. Ученик сам составляет запрос с этим фильтром, `sort_desc=false&limit=1`, сначала прогнозирует один ID, затем сравнивает с ответом. Отдельно без фильтра при `limit=1` ожидается глобальный минимальный ID — другой результат. **Критерий:** первый запрос не пуст, возвращает первый ID *после* фильтра; ученик объясняет, почему нельзя обрезать список до фильтра и почему `False` нельзя считать «параметра нет».
6. **Проверить отказы у HTTP-границы:** без исправления сервиса самостоятельно отправить `limit=0`, `limit=51`, `limit=many`, `is_done=maybe`; перед каждым запросом указать, какой тип или предел нарушен (разделы 02, 04). **Критерий:** в каждом случае FastAPI возвращает 422, код handler не должен вызываться; 0 и 51 не превращаются в 1/50. Если конкретное значение не отвергнуто, сверить аннотацию и `Query` в существующем GET.
7. **Сверить сохранность и перенос:** после допустимых и ошибочных GET повторить полный CLI-list, `GET /stats`, тот же item и содержимое исходного JSON из шага 2. **Критерий:** одинаковы все записи, внутренние `tags`, число и статусы задач, статистика и item; чтение не сохраняет отфильтрованный набор. Ученик кратко объясняет, почему HTTP без `limit` означает 10, а CLI остаётся полным. **Дополнительный перенос (необязателен):** предсказать результат нового сочетания `sort_desc=true&limit=2` до запроса.

Практика идёт от самостоятельного чтения URL и ручной выборки (шаг 1) к подготовленному наблюдаемому состоянию (2), собственному подключению handler (3) и проверкам двух видов: правильные значения (4–5), отказ до маршрута (6). Если расчёт расходится с ответом, сначала вернуться к трём состояниям из раздела 03, затем проверить границы из 04 и цепочку обработчика из 05. Завершающая регрессия (7) доказывает, что новое представление списка не изменило общий Planner. До следующего занятия ученик должен суметь повторить объяснение на других ID.

**Итоговый критерий всей практики:** корректный запрос возвращает ровно выбранную часть данных по цепочке «фильтр → сортировка по `id` → limit»; без параметров действует HTTP-limit 10, неверный тип или предел даёт 422, пустой результат остаётся 200/`[]`. После всех GET полный список, item, stats и JSON совпадают с исходным состоянием. Проектные возможности, полученные ранее, сохраняются. Занятие 50 получает стабильное чтение как опору при создании `TaskCreate`; подключение схемы к JSON body и POST отложено до 50.1.
