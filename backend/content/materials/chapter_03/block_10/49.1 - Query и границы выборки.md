## 00. Вступление

В Planner уже есть полный список задач и сервисная операция, которая умеет подготовить нужную часть списка. Теперь клиенту нужно задать условия чтения, не создавая отдельный адрес для каждой комбинации.

1. **Точка старта:** Существующий `GET /tasks` читает задачи через Planner; сервисная выборка готова и проверена отдельно.
2. **Новый вопрос:** Как клиент передаёт фильтр, направление сортировки и предел списка, и где FastAPI проверяет эти значения?
3. **Результат:** Параметры URL попадают в прежний маршрут, затем в `select_tasks`; контракт ответа и состояние Planner сохраняются.

Сначала разберём место и типы параметров, затем их значения по умолчанию и границы. После этого подключим их к существующему маршруту и проверим, что HTTP только формирует представление списка, а не меняет источник данных.

## 01. Query настраивает чтение коллекции

- **Что и зачем объяснить:** Query-параметры идут после `?` и передают настройки запроса. `/tasks` остаётся collection; `/tasks/{task_id}` выбирает item. Несколько настроек разделяются `&`, а порядок записи пар в URL не меняет их смысл. Отличить query от path, JSON body и пути к файлу.
- **Механизм и порядок:** На нейтральном примере каталога показать, что один путь collection принимает разные настройки выдачи. Затем связать `/tasks?is_done=false&limit=10` с уже знакомым адресом `GET /tasks`, не вводя новый HTTP-метод или endpoint.
- **Пример и типичная путаница:** Сравнить `GET /tasks/7` и `GET /tasks?limit=7`: первое задаёт адрес item, второе ограничивает размер списка. Число после `?` не становится частью пути.
- **Первое самостоятельное действие:** В нескольких готовых URL отметить path и query, указать, запрашивается collection или item. Наблюдаемый результат — ученик не переносит параметр списка в path и не принимает его за локальный файл.
- **Переход к следующему шагу:** После определения места параметра выяснить, как текст из URL становится значением Python.

## 02. FastAPI преобразует query в типизированные значения

- **Что и зачем объяснить:** Значения query передаются строками; аннотация аргумента маршрута задаёт тип, в который FastAPI пытается их преобразовать. На примере `bool` и `int` показать разницу между `false`/`12` и `maybe`/`many`; ошибочное значение приводит к 422 до выполнения кода маршрута.
- **Механизм и порядок:** Кратко восстановить знакомые параметры функции и аннотации. Затем связать значение из URL с аргументом обработчика. Для существующего API сохраняется уже изученный `Request`; новым является не объект Request, а типизированный query-ввод.
- **Пример и типичная путаница:** Показать, что `limit=12` становится числом `12`, а `limit=many` не превращается в ближайшее число и не передаётся сервису. Не смешивать ответ 422 на неверный query с 404 для отсутствующего item.
- **Первое самостоятельное действие:** По готовым URL предсказать тип и значение аргумента либо отметить отказ до маршрута. Результат — корректные текстовые представления сопоставлены с `bool`/`int`, неверные не считаются значениями сервиса.
- **Переход к следующему шагу:** Для корректных типов важно сохранить различие между отсутствующим фильтром и явно переданной логической величиной.

## 03. Пропуск, True и False; HTTP-default и сервисный default

- **Что и зачем объяснить:** Для `is_done` три состояния: `None` — фильтр не передан, `True` — только завершённые, `False` — только открытые. Не использовать проверку истинности, которая потеряет `False`. `sort_desc=False` задаёт направление по умолчанию. В HTTP отсутствие `limit` означает 10; у сервиса `limit=None` означает не ограничивать выборку.
- **Механизм и порядок:** Сначала проследить значение `is_done` от пропущенного query к `None`, затем `true`/`false` к соответствующим `bool`. Отдельно сравнить HTTP-сигнатуру с уже изученной сигнатурой сервиса: маршрут всегда передаёт сервису конкретный limit, а `None` остаётся значением по умолчанию для прямого вызова `select_tasks`. CLI, как и прежде, получает полный список через `list_tasks`.
- **Пример и типичная путаница:** На одном подготовленном наборе различить отсутствующий фильтр и `is_done=false`. Пустое совпадение для корректного фильтра — успешный `200` с `[]`, не 404. Отсутствующий HTTP-limit не равен сервисному `limit=None`.
- **Первое самостоятельное действие:** Составить для пропуска, `true` и `false` соответствия «query → аргумент → ожидаемая группа задач», затем отдельно указать HTTP-limit и сервисный `None`. Результат — все состояния и две границы defaults объяснены без переписывания алгоритма.
- **Опора для повторного обращения:** При запросах восстановить таблицу трёх значений `is_done` и правило «HTTP без limit → 10; прямой вызов сервиса с None → полный результат»; характерная ошибка — принять False за пропуск либо показать CLI только десять задач.
- **Переход к следующему шагу:** Смысл значений определён; теперь зададим серверные границы для `limit`.

## 04. Query задаёт включительные границы limit

- **Что и зачем объяснить:** Разобрать форму `limit: int = Query(default=10, ge=1, le=50)`. `default` задаёт HTTP-значение при пропуске, `ge` включает нижнюю границу, `le` — верхнюю. Допустимы 1 и 50; 0, 51 и нецелое значение отвергаются. Аналогично неверное boolean-представление не доходит до обработчика.
- **Механизм и порядок:** Сначала восстановить импорт FastAPI и обычный аннотированный параметр функции; затем объяснить роль `Query` как описания HTTP-ввода и ограничения. Не объявлять эти проверки правилами `PlannerService` или доменной модели Task.
- **Пример и типичная путаница:** Использовать независимый пример ограничения количества книг, потом назвать границы Planner. Не подменять 422 автоматическим обрезанием к 1/50 и не путать `Query` с query-строкой клиента.
- **Первое самостоятельное действие:** На готовой сигнатуре определить значение по умолчанию и классифицировать нижнюю/верхнюю границу и значения вне диапазона. Результат — ученик верно отличает допустимые края от отказа FastAPI.
- **Переход к следующему шагу:** После объяснения типов и ограничений можно связать query с готовой сервисной операцией.

## 05. Подключить параметры к существующему GET /tasks

- **Что и зачем объяснить:** Обновляется существующий collection-handler, а не создаётся маршрут на каждый фильтр. Его значения передаются именованными аргументами готовому `request.app.state.planner.select_tasks`; формирование публичных полей остаётся прежним. `GET /stats` по-прежнему считает весь источник.
- **Механизм и порядок:** Показать путь «URL → разбор FastAPI → аргументы маршрута → select_tasks → прежняя проекция ответа». Восстановить доступ через `Request.app.state.planner` из занятия 48; не захватывать сервис глобальным alias. Не переносить в endpoint код фильтрации, сортировки или чтения JSON.
- **Пример и типичная путаница:** Сравнить ограниченный ответ collection с полным списком CLI. `limit` сокращает только ответ; он не сокращает общий источник и статистику. Сохраняются ровно `id`, `title`, `priority`, `is_done`; `tags` остаётся в Task/JSON.
- **Первое самостоятельное действие:** Изменить сигнатуру и делегирование существующего GET после объяснения каждого аргумента. Сначала проверить отсутствие query, затем один допустимый фильтр и limit. Наблюдаемый результат — маршрут использует готовый сервис, возвращает прежнюю форму и не добавляет новый URL.
- **Опора для повторного обращения:** Перед вызовом восстановить три параметра и их значения по умолчанию; после ответа сверить фильтр, направление по `id`, limit и четыре поля. Характерная ошибка — снова вызвать `list_tasks`, применить сервисный `None` к HTTP-default либо обрезать данные в маршруте.
- **Переход к практике:** Маршрут подключён; теперь проверяются обычный запрос, различающие значения, границы и сохранность проекта.

Затем сохранить полный CLI-list, stats, выбранный существующий item и JSON; критерий — реальные данные переживают перезапуск CLI и позволяют проверить значение по умолчанию и фильтрацию.
2. **Расширить существующий GET:** добавить типизированные `is_done`, `sort_desc` и `limit` с паспортными defaults и границами, передать их в `select_tasks` через `request.app.state.planner`, оставить прежнюю проекцию. 3. **Проверить допустимые варианты:** запрос без query при количестве больше десяти должен вернуть ровно первые десять ID по возрастанию; отдельно проверить отсутствие фильтра, `true`/`false`, оба направления, `limit=1` и `limit=50`. 4. **Проверить различающий случай и отказы:** на подготовленном до исходного состояния наборе выбрать фильтрованный статус, отличный от статуса задачи с минимальным ID, и при `sort_desc=false` и `limit=1` получить минимальный ID среди совпадений. Последовательность практики повторяет путь данных: реальные записи → HTTP-параметры → готовая сервисная выборка → публичный ответ. Первые действия подготавливают сравнение и проверяют подключение, затем ученик самостоятельно выбирает значения и объясняет различие между отсутствующим фильтром и `False`. Итог подтверждает B по реальному Planner, не по временному списку.

**Итоговый критерий всей практики:** корректный запрос возвращает ровно выбранную часть данных по цепочке «фильтр → сортировка по `id` → limit»; без параметров действует HTTP-limit 10, неверный тип или предел даёт 422, пустой результат остаётся 200/`[]`. После всех GET полный список, item, stats и JSON совпадают с исходным состоянием. Проектные возможности, полученные ранее, сохраняются. Занятие 50 получает стабильное чтение как опору при создании `TaskCreate`; подключение схемы к JSON body и POST отложено до 50.1.
