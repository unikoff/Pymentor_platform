## 00. Вступление

После выполнения занятий 48 и 48.1 по маршруту GET /tasks возвращает полный список реальных задач Planner, а GET /stats и item-маршрут уже работают. Пока клиент не управляет выборкой через query. Сначала нужно решить, какой слой отвечает за отбор и как фильтр, порядок и ограничение работают независимо от HTTP.

1. **Точка старта:** существующие Task и PlannerService.list_tasks(), который получает полный список из общего хранилища.
2. **Новый вопрос:** как вернуть выбранные задачи, не меняя источник и не превращая CLI-список в ограниченный HTTP-список?
3. **Результат:** новый прямой вызов PlannerService умеет фильтровать по статусу, сортировать по id и ограничивать уже подготовленный результат.

Сначала разберём состояния фильтра и механизм сортировки, затем порядок применения limit. После этого те же шаги будут собраны в одном сервисном методе и проверены без HTTP. Это сохранит границу между новой логикой сервиса и следующей HTTP-настройкой: только после подтверждения select_tasks клиентский query сможет безопасно передать ему проверенные значения.

## 01. От полного списка к отдельной операции сервиса

- Что и зачем объяснить: list_tasks остаётся прежним способом получить все задачи. Новая операция нужна для выборки, не для замены общего списка. Размещение логики в PlannerService сохраняет единый путь к данным для API и CLI; handler не должен читать JSON напрямую или копировать алгоритм.
- Механизм и порядок: select_tasks начинает с существующего list_tasks и готовит новый результат. Фильтр и сортировка относятся к возвращаемой выборке, не к хранилищу. Его прикладные значения по умолчанию: is_done=None, sort_desc=False, limit=None.
- Пример и типичная путаница: на каталоге книг показать разницу между «вернуть все книги» и «вернуть результат по условию». Не превращать list_tasks в метод с HTTP-лимитом и не менять общий порядок источника ради одного запроса.
- Первое самостоятельное действие: по описанию роли двух операций объяснить, какой метод нужен CLI для полного списка и какой метод будет вызывать API при выборке; наблюдаемый результат — прежняя возможность полного чтения остаётся отдельной.
- Опора для повторного обращения: назначение каждого аргумента и ожидаемая граница между сервисом и HTTP; возвращаться сюда, если при проверке меняется CLI или в сервис попадает параметр Query.
- Переход к следующему шагу: теперь можно определить, какое подмножество задач нужно получить до сортировки.

## 02. Необязательный фильтр и три состояния

- Что и зачем объяснить: статус задачи — условие отбора. Нужно различать отсутствие условия, выбор True и выбор False.
- Механизм и порядок: None означает оставить оба статуса; True выбирает завершённые задачи; False выбирает открытые. Проверку наличия условия объяснить отдельно от значения самого условия: False не означает «не передано».
- Пример и типичная путаница: использовать независимый каталог товаров с has_discount. Показать, что None оставляет товары со скидкой и без неё, а False оставляет товары без скидки. Типичная ошибка — проверять параметр на истинность и тем самым пропускать явное False.
- Первое самостоятельное действие: для небольшого набора готовых Task определить состав результата при None, True и False. Наблюдаемый результат — None включает обе группы, а False возвращает ровно открытые задачи.
- Опора для повторного обращения: таблица трех состояний параметра; при ошибке сверить, проверяется ли отсутствие через отличие от None и не потеряно ли False.
- Переход к следующему шагу: когда состав выборки определён, расположим оставшиеся задачи в требуемом порядке.

## 03. Сортировка по id и направление

- Что и зачем объяснить: предметы Task не нужно сравнивать целиком; порядок выборки Planner определяется устойчивым id.
- Механизм и порядок: sorted строит новый список; key задаёт значение, по которому сравниваются элементы. На примере отдельной коллекции книг объяснить именованную функцию и короткую lambda, после чего связать key с id задачи. Направление задаёт reverse: False — возрастание, True — убывание; аргумент sort_desc передаёт это намерение сервису.
- Пример и типичная путаница: у книг сравнивается год, у задач — id, а не title или весь объект. Не использовать изменяющий исходный список метод сортировки; reverse меняет направление того же порядка, а не фильтрует элементы.
- Первое самостоятельное действие: расположить заданные задачи по id в обоих направлениях и сравнить исходный список с результатом. Наблюдаемый критерий — порядок результата совпадает с id, а исходная последовательность сохранена.
- Опора для повторного обращения: роль key, значение id, направление reverse и ожидаемый первый/последний id; при ошибке проверить, что сортируется новый список и применяется правильное направление.
- Переход к следующему шагу: после фильтра и сортировки можно взять начало результата, не теряя нужные совпадения.

## 04. Limit и порядок действий

- Что и зачем объяснить: limit ограничивает количество возвращаемых записей, а не множество совпадений до фильтра.
- Механизм и порядок: обязательная последовательность — фильтр → сортировка по id → limit. limit=None оставляет весь подготовленный список; числовой limit берёт его начало. Порядок фильтра и сортировки задаёт, какие именно элементы попадут в ограниченный результат.
- Пример и типичная путаница: показать коллекцию, где задача с минимальным id имеет другой статус, чем задачи нужного фильтра. При limit=1 фильтр, затем сортировка и ограничение дают минимальную задачу среди совпадений; преждевременный limit может оставить только элемент неподходящего статуса.
- Первое самостоятельное действие: проследить состав списка после каждого шага для обычного случая и различающего набора с разрывами id. Наблюдаемый результат — limit=1 возвращает первый элемент уже отсортированной выборки, а None не обрезает её.
- Опора для повторного обращения: краткая схема фильтр → сортировка → limit и смысл None; если результат пустой, проверить исходные совпадения до ограничения и порядок операций.
- Переход к следующему шагу: алгоритм готов к переносу в PlannerService и прямой проверке.

## 05. Прямая проверка сервиса без изменения состояния

- Что и зачем объяснить: проверка новой прикладной операции проводится через PlannerService, а не через TestClient. Для изоляции данных используется JsonStorage с временным путём pytest tmp_path.
- Механизм и порядок: в tests/test_services.py подготовить Task с обоими статусами и разрывами id, вызвать select_tasks и сравнить полученную выборку с договором. Работа идёт с отдельным JSON; метод чтения не должен сохранять данные. Здесь не вводятся новые pytest-fixtures или HTTP-механизмы.
- Пример и типичная путаница: сравнить вызов сервиса с запросом к API: HTTP ещё не меняется, Query/defaults здесь не проверяются. Изменённый результат выборки не означает изменение порядка в хранилище.
- Первое самостоятельное действие: по подготовленному тестовому состоянию выбрать обычный случай и различающий случай для фильтра, порядка и limit; наблюдаемый критерий — каждый случай проверяет названную часть договора без зависимости от рабочего JSON.
- Опора для повторного обращения: список проверок: None/True/False, id с разрывами, возрастание/убывание, None/1 для limit, сохранность файла и полный list_tasks.
- Переход к практике: ученик сможет самостоятельно собрать эти части в существующем классе и показать результат прямым тестом.

## 06. Что мы будем делать в практике

**Формат и исходная опора:** ручная проектная практика в StudyHub. Начинаем с существующего PlannerService, Task, JsonStorage и полного list_tasks. Для прямых тестов создаём отдельное состояние в JsonStorage(tmp_path); рабочий JSON не используется.

Общий результат — новый сервисный метод выборки, который сохраняет прежнее поведение полного списка и даёт проверяемый результат для фильтра, сортировки и ограничения.

1. **Подготовить различающие данные и тестовую границу:** на базе знакомых Task/JsonStorage создать для tests/test_services.py изолированный набор с обоими статусами и непоследовательными id. Ученик сам выбирает данные, по которым видны порядок и фильтр; результат — baseline полного списка и отдельный тестовый путь готовы.
2. **Добавить выборку по статусу:** в app/services.py самостоятельно добавить select_tasks в существующий PlannerService и опереться на list_tasks. После объяснения блока 02 проверить None, True и False на том же наборе; результат — отсутствие фильтра и оба явных статуса дают различающиеся ожидаемые выборки, исходное хранилище не меняется.
3. **Собрать порядок, направление и limit:** самостоятельно соединить механизмы блоков 03–04. Прямыми вызовами проверить оба направления сортировки по id, limit=None и limit=1, а также различающий набор, где раннее ограничение дало бы иной ответ. Результат — limit применяется к уже отфильтрованному и отсортированному списку.
4. **Закрыть договор чтения:** повторно получить полный list_tasks() и get_statistics() того же тестового Planner, затем сверить содержимое JSON после всех вызовов выборки. Результат — полный список, статистика и все записи прежние, чтение не меняет файл, а select_tasks возвращает только ожидаемый новый результат.

Объяснение связано с практикой по шагам: фильтр подготавливает состав, sorted задаёт новый порядок, limit определяет длину результата; сервис объединяет их, а изолированные прямые тесты подтверждают результат без сетевого слоя. Итог практики подтверждает B. HTTP-default 10, Query и проверки диапазона появятся только в следующем занятии.

Для передачи дальше сохраняется обычный договор сервиса: limit=None не ограничивает выборку. Следующий урок отдельно добавит HTTP-default 10 и допустимые query-границы 1–50; он не меняет прежний полный CLI-list.
