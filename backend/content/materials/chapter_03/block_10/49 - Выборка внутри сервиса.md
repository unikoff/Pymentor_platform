## 00. Вступление

Представим Planner с двадцатью задачами. Обычный `list_tasks()` нужен, чтобы увидеть **все** задачи: это по-прежнему важно для CLI и статистики. Но иногда нам нужна только часть: например, незавершённые задачи в порядке номеров. Ради такого ответа не нужно удалять записи, переписывать JSON или менять прежний способ полного чтения.

1. **Точка старта:** по планируемой B занятия 48 существующий `PlannerService.list_tasks()` читает полный набор `Task` из того же хранилища, что и CLI; перед началом проверяем это на фактическом проекте.
2. **Новый вопрос:** как построить из полного списка нужную выборку, одновременно сохранив источник данных, полный список CLI и общую статистику?
3. **Результат:** отдельный `select_tasks(is_done=None, sort_desc=False, limit=None)` возвращает новый список после **фильтра → сортировки по `id` → ограничения**, а исходные данные остаются прежними.

От полного чтения перейдём к трём небольшим операциям. Сначала разберём их на самостоятельных, не связанных с Planner данных, затем сравним два порядка вычислений, и только после этого ученик напишет новый метод сервиса. В будущем MAIN вступительная триада оформляется как одна связанная группа `LinkedNotes variant="connected"`.

## 01. Источник данных и временное представление — разные вещи

- **Что объяснить:** `list_tasks()` отвечает за получение всех задач; `select_tasks()` отвечает за способ **показать часть уже полученных**. Аналогия: исходный каталог библиотеки не исчезает, если на экране включили показ книг определённого жанра. Предел аналогии: в программе отдельный результат существует как список в памяти; состояние JSON нужно проверить отдельно, сам по себе экран ничего не гарантирует.
- **Механизм и форма:** новый метод вызывается у прежнего `PlannerService`, первым получает данные через `self.list_tasks()` и возвращает результат. Значения по умолчанию имеют предметный смысл: `is_done=None` — любой статус, `sort_desc=False` — порядок по возрастанию ID, `limit=None` — без ограничения. Это обычные аргументы Python-функции, а не параметры HTTP.
- **Независимый пример:** каталог товаров целиком содержит четыре позиции, а «показать только товары без скидки» возвращает отдельный результат из двух позиций. Обсудить, почему поиск/представление не должен менять исходный каталог.
- **Первая самостоятельная попытка:** ученик выбирает, какую операцию следует использовать для полного списка CLI, а какую — для временного отбора, и объясняет, почему не нужно создавать второй `JsonStorage`. Критерий: сохранён один источник, а новый метод только читает и возвращает список.
- **Возврат и переход:** вернуться к разнице «источник / результат» при ошибочном `save()` или изменении CLI. Следующий шаг определяет, **какие элементы** попадут во временный результат.

## 02. Три состояния необязательного фильтра

- **Что объяснить:** `True` и `False` — два реальных значения статуса. `None` означает «условие не задано». Нельзя писать «если значение истинное, тогда фильтровать»: такая проверка пропустит запрос «только незавершённые», где значение `False`.
- **Форма и порядок:** на независимом флаге `has_discount` разобрать `if wanted is not None:` и сравнение `item["has_discount"] == wanted`. Сначала решить, нужно ли фильтровать, затем сравнивать состояние каждого элемента с требуемым. Запись `is not None` проверяет **наличие** условия; она не заменяется на `if wanted:`. Отсутствие совпадений возвращает пустой список, а не ошибку.
- **Независимый случай:** товары `A` (со скидкой), `B` (без), `C` (со скидкой). Для `wanted=None` → `A,B,C`, для `True` → `A,C`, для `False` → `B`. Предел аналогии: в Planner выбираем по `Task.is_done`, не по полю товара.
- **Самостоятельное действие:** до сервисного кода ученик предсказывает результат для всех трёх значений на новом коротком наборе и объясняет, почему `if wanted:` даёт неверный ответ при `False`. Локальный критерий: `False` исключает завершённые задачи, `None` ничего не исключает.
- **Возврат и переход:** правило `is not None` и сравнение статусов нужны при записи фильтра в практике. Теперь известен **состав** выборки; можно определить её **порядок**.

## 03. Упорядочивание по ключу и неизменность исходного списка

- **Что объяснить:** `id` — номер задачи, а не её место в списке. После удаления старых задач ID могут иметь разрывы: `3, 8, 17` не становятся `1, 2, 3`. Сортировка по позиции или названию не выполняет паспортную B.
- **Форма и механизм:** на независимых словарях разобрать `sorted(records, key=lambda record: record["number"], reverse=False)`: `sorted` возвращает новый список, `key` сообщает, по какому значению сравнивать элементы, `lambda` называет текущий элемент и берёт его поле. Показать, что то же правило можно записать отдельно именованной функцией; обе формы сравнивают одно поле. `reverse=False` даёт возрастание, `True` — убывание. В проекте поле ключа — `task.id`, аргумент направления — `sort_desc`. Не путать с `list.sort()`, которая переставляет элементы текущего списка.
- **Независимый случай:** записи с номерами `9, 2, 11` в этом исходном порядке. Результат по возрастанию — `2, 9, 11`, по убыванию — `11, 9, 2`, а исходный список остаётся `9, 2, 11`.
- **Самостоятельное действие:** ученик составляет собственное выражение `sorted(..., key=..., reverse=...)` для списка словарей с полем `number`, проверяет оба направления и повторно выводит исходный список. Критерий: порядок нового списка определяется номером, исходный список не переставлен.
- **Возврат и переход:** если объект сравнивается целиком или меняется исходная последовательность, вернуться к `key` и различию `sorted` / `sort`. Следующий шаг оставит только нужное количество элементов **после** сортировки.

## 04. Ограничение — начало подготовленной выборки

- **Что объяснить:** `limit` — число элементов в возвращаемом результате. Срез `items[:n]` берёт первые `n` элементов текущего списка; он не проверяет статус и не сортирует. `limit=None` на уровне сервиса означает, что шаг обрезки **не выполняется**. До HTTP-валидации в 49.1 используем только понятные корректные положительные значения.
- **Механизм и форма:** сначала решить, задано ли ограничение (`limit is not None`); при отсутствии вернуть весь подготовленный результат, при наличии взять начало `[:limit]`. Если совпадений меньше, чем `limit`, результат содержит все совпадения; при отсутствии — `[]`.
- **Независимый случай:** список чисел `[11, 4, 9]` даёт `[11]` после `[:1]` без сортировки, но `[4]` после сортировки по возрастанию. Это две разные операции, и их нельзя подменять друг другом.
- **Самостоятельное действие:** для `[6, 2, 10]` ученик предсказывает результат после сортировки и среза `[:1]`, а затем после одного только среза; проверяет оба в редакторе. Критерий: ответы различаются, при `None` на сервисном уровне обрезки нет.
- **Возврат и переход:** срез берёт начало **уже подготовленной** последовательности. Дальше сравним весь порядок действий на наборе, где ошибку нельзя скрыть удачным расположением элементов.

## 05. Контрпример: почему порядок операций обязателен

- **Что объяснить:** работающая выборка — последовательность из трёх вопросов: «какие подходят?» → «в каком порядке?» → «сколько первых показать?». Нельзя сначала брать один исходный элемент: он может оказаться неподходящим; нельзя брать первый после сортировки *всех* задач до фильтра: подходящий элемент может стоять вторым.
- **Независимый пример, отличный от проектной практики:** заявки на мероприятия в исходном порядке: `(id=12, confirmed=False)`, `(id=4, confirmed=True)`, `(id=9, confirmed=False)`, `(id=2, confirmed=True)`. Нужно получить **одну неподтверждённую** заявку с минимальным `id`. Правильная цепочка: отбор → `12, 9`; сортировка по `id` → `9, 12`; срез `[:1]` → `9`. Ошибка «ограничить исходный список заранее» вернёт `12`; ошибка «отсортировать всё, взять один, потом фильтровать» даст пустой список, поскольку самый маленький `id=2` имеет другой статус.
- **Первое самостоятельное действие:** ученик без кода решает похожий случай с другим набором чисел и `limit=1`, записывает промежуточные ID после каждого этапа, затем объясняет, на каком шаге два неправильных порядка расходятся с правильным. Критерий: получен **первый ID среди совпадений**, а не первый исходный ID.
- **Возврат и переход:** формула `filter → sorted(id, reverse=sort_desc) → limit` — краткая опора при отладке метода; полный проектный код здесь не показан. После прогноза ученик готов самостоятельно собрать алгоритм в сервисе.

## 06. Выборка не должна менять Planner и статистику

- **Что объяснить:** список, возвращённый для показа, и содержимое хранилища — разные наблюдаемые вещи. `get_statistics()` продолжает считать **все** задачи, даже если временная выборка содержит одну. Вызовы чтения не должны вызывать `save()` или менять `is_done`/`id` объектов. Новый список после `sorted` не даёт разрешения менять сами `Task`.
- **Как проверять:** запомнить полный порядок и пары `(id, is_done)` до вызова, записать показания прежней команды CLI и `get_statistics()`. Выполнить несколько прямых вызовов `select_tasks` и снова прочитать полный список и те же данные JSON. Сравнивать именно **значения и порядок полного списка, количество и статусы**, а не предполагать, что успешный новый ответ гарантирует отсутствие побочного эффекта. Если для безопасной проверки нужно дополнить данные, использовать учебную копию/отдельный JSON и считать состоянием «до» снимок **после** подготовки, не переписывать пользовательский файл.
- **Независимый пример:** библиотечный каталог из четырёх книг и временное отображение двух доступных; счётчик всех книг остаётся `4`. Аналогия ограничена: в Planner общая статистика дополнительно учитывает состояния выполнения, поэтому сверяем и число по каждому статусу.
- **Самостоятельное действие:** ученик объясняет, почему `get_statistics()` нельзя пересчитывать из `select_tasks(limit=1)`, и выбирает две проверки: значение полного списка и неизменность JSON. Критерий: выборка меняется в зависимости от аргументов, постоянные данные и общая статистика — нет.
- **Переход:** осталось самостоятельно записать сервисный метод и показать эти же свойства на существующем Planner через редактор и прежний CLI.

## 07. Что мы будем делать в практике

**Формат и исходная опора:** **кодовая практика в редакторе** существующего проекта Planner. Вход: `Task` с полями `id`/`is_done`, `PlannerService.list_tasks()`, `get_statistics()`, прежний CLI и `JsonStorage` по планируемой B 48 и предметной базе главы 2. Перед выдачей проверить реальные имена методов, конфигурацию JSON и выполненный полный просмотр через CLI; если вход недоступен, восстановить именно его. Готовыми остаются прежний класс, storage и CLI; **новый метод и решения по трём операциям пишет ученик**. Никакого готового `select_tasks` в starter и никакой обязательной pytest-задачи.

Цель — создать сервисную выборку, которая правильно выбирает задачи при любом из трёх состояний фильтра и двух направлениях сортировки, обрезает **только после** них, а все старые данные и чтения сохраняет.

1. **Рассчитать эталон до кода.** Вход: объяснения 02–05 и независимый набор `Task`, где в исходном порядке ID `8` (открыта), `3` (завершена), `17` (завершена), `5` (открыта); статус и ID заранее известны, запись в JSON не требуется. Объект: ожидаемый список ID после каждого этапа. Самостоятельно: ученик вычисляет `is_done=False, sort_desc=False, limit=1` → `[5]`, `is_done=True, sort_desc=True, limit=1` → `[17]`, `is_done=None, sort_desc=False, limit=None` → `[3, 5, 8, 17]` и объясняет, почему ранний `limit=1` сломает первый случай. Локальный результат: есть ручные прогнозы на нормальном и различающем входах, по которым можно затем проверить код; они получены без готовой реализации.
2. **Написать фильтр в существующем сервисе.** Вход: фактический `PlannerService` с `list_tasks()` (A от 48, проверена до практики), учебный список из шага 1 как ориентир; опора 01–02. Объект: `app/services.py` или подтверждённый эквивалент в checkout. Самостоятельно: ученик создаёт **весь метод** с указанной сигнатурой, берёт результат прежнего `list_tasks()` и записывает логику трёх состояний фильтра, без копирования полного решения. Локальный результат до добавления сортировки: прямыми вызовами `select_tasks(is_done=None/True/False)` ученик сравнивает **состав** возвращённых ID с ожидаемым; порядок на этом промежуточном шаге ещё не оценивается. Различающий случай — явное `False`, которое нельзя принять за отсутствие фильтра.
3. **Добавить сортировку и ограничение.** Вход: работающий фильтр шага 2, опоры 03–05 и ручной эталон шага 1. Объект: тот же метод. Самостоятельно: ученик записывает `sorted` с ключом `id`, связывает направление с `sort_desc` и добавляет применение положительного `limit` **после** сортировки; `None` оставляет всю выборку. Локальный результат: прямые вызовы в редакторе совпадают с прогнозами `[5]`, `[17]`, `[3, 5, 8, 17]` на соответствующем учебном наборе; проверить также `limit=1` при недостатке совпадений и оба направления для ID с разрывами. Если данные проектного JSON не совпадают с примером, использовать **ожидания для фактических данных**, не заменяя ими файл пользователя; прогнать проектный `select_tasks` на собственном допустимом учебном наборе в отдельной конфигурации.
4. **Проверить сохранность полного источника.** Вход: готовый `select_tasks` и зафиксированное **после подготовки данных** исходное состояние; опора 06. Объект: прежние `list_tasks()`, `get_statistics()`, CLI и конкретный JSON, с которым работает проверяемый сервис. Самостоятельно: ученик повторяет полное чтение, выводит статистику и сверяет JSON/пары `(id, is_done)` до и после нескольких выборок. Локальный результат: исходные ID, их порядок и статусы, общая статистика и содержимое файла совпадают; новый результат существует только в памяти. Если данные намеренно подготавливались CLI до проверки, сохранить снимок **после** подготовки и сравнивать только чтения.
5. **Самостоятельный перенос на изменённый случай.** Вход: проверенный метод и новый небольшой набор с иными ID/статусами; опоры 02–06. Объект: прогноз и вызов `select_tasks`, без переписывания алгоритма. Самостоятельно: ученик подбирает такой `is_done` и `limit=1`, чтобы «сортировать всё → ограничить → фильтровать» ошибочно дало пустой результат; обосновывает правильный первый ID среди совпадений и сравнивает с фактом. Локальный результат: объяснение причины верного результата на **новом** вводе, а не только повторение прежних трёх ответов.

Эти действия образуют второй связанный маршрут `LinkedNotes variant="connected"` для MAIN: сначала ручной прогноз → затем собственная запись фильтра → соединение с сортировкой и limit → проверка прежнего поведения → перенос на новый ввод. При ошибке возврат к 02 (три состояния), 03 (ключ и направление), 04–05 (порядок операций) или 06 (сохранность). **Наблюдаемая B:** есть самостоятельно написанный `select_tasks`, совпадение с ручным расчётом на различающих случаях и подтверждение, что полный CLI-list/статистика/JSON не изменены.
