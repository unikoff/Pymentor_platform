## Точка B: проверяемый результат

Ученик **объясняет**: что означает переменная часть URL, когда FastAPI разбирает `int` и проверяет положительность, почему неверное значение отклоняется до обработчика (422), а допустимый отсутствующий `id` обнаруживает сервис (404).

Ученик **самостоятельно изменяет существующий проект**: добавляет один `GET /tasks/{task_id}` с положительным целым `task_id`, получает прежний сервис из `Request`, вызывает `get_task`, переводит **только** `TaskNotFoundError` в `HTTPException(status_code=404, detail="Task not found")` и возвращает `_task_read_data(task)`.

**Наблюдение:** существующий положительный `id` → 200 и `id/title/priority/is_done`; отсутствующий положительный → 404; текст, ноль и отрицательный → 422. Сбой чтения storage не маскируется 404. Список, статистика, CLI и рабочий JSON после GET не меняются.

## 00. Вступление

В ответе `GET /tasks` виден список задач. Пользователь выбирает одну: для её адреса нужен **id**, а не номер строки (при сортировке строки могут поменяться местами). Новый вопрос — как получить одну задачу и объяснить клиенту, почему это не удалось.

1. **Точка старта:** список и статистика из 48 отвечают через общий Planner; в списке видны реальные `id`.
2. **Новый вопрос:** что произойдёт, если в адресе передать существующий `id`, буквы или номер, которого в данных нет?
3. **Результат:** один новый route правильно различает 200, 422 и 404 и не меняет данные.

После этой триады запланировать краткий прогноз по трём адресам, а затем разбор пути запроса. Проверка нужна для поиска исходного заблуждения; ответы до объяснения не считать освоением.

## 01. Адрес одной записи и идентификатор

**Объяснить.** `/tasks` — коллекция, `/tasks/7` — конкретный ресурс, `7` — значение идентификатора. Запись `{task_id}` в определении маршрута — место для переменной части адреса, клиент **не пишет фигурные скобки**. Path отличается от query: `/tasks?is_done=false` по-прежнему адресует список и лишь задаёт условие, которое будет изучено позже.

**Независимая опора:** библиотека книг. `/books` означает все книги, `/books/7` — книгу с `id=7`. Если поменять порядок выдачи книг, идентификатор не меняется. Предел аналогии: число на адресе ещё не гарантирует, что книга действительно есть в каталоге.

**Первое действие ученика:** без кода распределить `/books`, `/books/7`, `/books?genre=history` по «коллекция / item / коллекция с параметром» и объяснить, почему `/books/7` не означает «седьмой элемент списка». Обратная связь — выбран правильный ресурс, а не угадано число.

**Переход:** после выбора адреса нужно научить приложение извлекать его переменную часть.

## 02. Как FastAPI получает число из path

**Механизм.** Маршрут `/books/{book_id}` соответствует адресу `/books/7`. Аргумент обработчика `book_id: int` получает значение после проверки и преобразования сегмента URL. В адресе всё приходит как текст; `int` означает, что FastAPI должен получить число. Если приходит `abc`, значение нельзя преобразовать в `int`; FastAPI возвращает **422 до вызова обработчика**. Сам сервис в этот момент не вызывается.

**Визуальная трассировка для MAIN:** `URL → сопоставление маршрута → разбор int → обработчик → сервис`. Для `/books/abc` поток останавливается на «разбор int», для `/books/7` продолжается. На схеме отдельно отметить, что формат числа и наличие книги — два независимых вопроса.

**Первое действие:** ученик отмечает место остановки для `/books/abc` и `/books/7`; затем объясняет, почему 422 не говорит ничего о наличии записи в базе. Ответ аргументируется шагами обработки, а не только запоминанием статуса.

**Переход:** тип `int` допускает и `0`, и отрицательные числа, а идентификаторы Planner должны быть положительными.

## 03. Условие положительного id: Path и Annotated

**Сначала объяснить синтаксис, затем применить.** `Annotated[int, Path(gt=0)]` означает: значение по-прежнему типа `int`, но для **path-параметра** добавлено требование `gt=0` («строго больше нуля»). `Annotated` связывает тип с дополнительной информацией, `Path` описывает HTTP-ограничение. Перед первым примером показать происхождение имён: `Annotated` импортируется из `typing`, `Path` — из `fastapi`; `int` уже знакомый тип. Это не проверка существования записи и не новый тип задачи.

**Мини-пример с книгами:** `book_id: Annotated[int, Path(gt=0)]`. Ученик предсказывает: `/books/0` и `/books/-2` → 422; `/books/7` проходит проверку формы и может попасть в поиск. Пояснить порядок: извлечь сегмент → разобрать `int` → проверить `>0` → вызвать функцию. FastAPI оформляет ошибку до handler. Не писать дополнительную проверку `if book_id <= 0` в сервисе ради этого маршрута.

**Первое действие:** для адресов с `7`, `0`, `-2`, `abc` ученик строит таблицу «разбор int / условие gt=0 / достигнут ли обработчик». Правильный критерий: только положительное целое доходит до route; наличие записи пока неизвестно.

**Переход:** допустимый id теперь можно передать сервису, который умеет искать задачу в настоящих данных.

## 04. Где находится поиск: route → service → storage

**Восстановить из 48.** В обработчике `Request` даёт доступ к `request.app.state.planner`. Там хранится **ссылка на сервис**, а не отдельная копия списка. Метод `get_task(task_id)` уже отвечает за поиск в Planner и при отсутствии поднимает `TaskNotFoundError`. Обработчик не читает JSON, не создаёт `build_service()` при каждом запросе и не ищет id вручную по списку.

**Схема для MAIN:** клиент → FastAPI route → прежний `PlannerService.get_task` → прежнее хранилище → найденная `Task` либо предметное исключение. Сверить с 48: изменилось только то, какой метод сервиса вызывается, общий источник данных тот же.

**Первое действие:** ученик находит в собственном `app/api.py` доступ к `request.app.state.planner`, в `PlannerService` — `get_task`; вслух указывает, какую часть цепочки будет писать сам. Наблюдение — одна понятная точка вызова без дублированного поиска.

**Переход:** найденную задачу можно представить клиенту; отсутствие нужно превратить в понятный HTTP-ответ.

## 05. 404 только для предметного отсутствия

**Объяснить две границы.** 422 появляется **до обработчика**, когда id нельзя разобрать или он не положительный. 404 в этом занятии появляется **после входа в обработчик**, когда сервис получил допустимый id, но поднял именно `TaskNotFoundError`. `HTTPException` создаёт HTTP-ответ, не меняя поведения доменного сервиса.

**Показать принцип `try/except` без готового целевого handler:** на независимом примере поиска книги напомнить: внутри `try` выполняется поиск; часть `except` срабатывает лишь для названного исключения; `raise` передаёт новое исключение FastAPI. Затем сопоставить с Planner: узко обернуть *вызов поиска*, ловить только `TaskNotFoundError` и поднять `HTTPException(status_code=404, detail="Task not found")`, импортировав `HTTPException` из `fastapi`. Проверить, что `_task_read_data` вызывается для найденной задачи. Не использовать `except Exception` и не ловить исключение storage как «объект не найден».

**Контраст для новичка:** «книги с номером 7 нет» — корректно прочитанный каталог и отсутствие записи; «каталог недоступен» — каталог вообще нельзя прочесть. Второй случай не доказывает отсутствия книги. Доменная ошибка и инфраструктурная ошибка имеют разные причины и не должны давать одинаковый 404.

**Первое действие:** для четырёх ситуаций (положительный существующий id, положительный отсутствующий id, текстовый id, отказ чтения хранилища) ученик отмечает, где возникла причина и может ли сработать `except TaskNotFoundError`. Ожидаемая классификация: 200/404/422/сбой хранения соответственно; точный HTTP-код сбоя хранения здесь не устанавливаем.

**Переход:** даже при успешном поиске нужно вернуть клиенту только публичные поля.

## 06. Одна публичная форма и отсутствие побочного эффекта

**Объяснить.** `get_task` возвращает доменную `Task`, но её поля не равны публичному контракту API. Из 48 используем `_task_read_data(task)`: `id`, `title`, `priority`, `is_done`. Поле `tags` остаётся внутри модели/JSON. Для клиента запись из item должна иметь **те же четыре поля и значения**, что строка из `GET /tasks` с тем же id.

**Независимый прогноз:** у книги может быть внутреннее поле `internal_note`, которое библиотечный клиент не видит. Аналогия заканчивается на выборе публичных данных: здесь конкретный договор фиксируется реальными четырьмя полями Planner.

**Первое действие:** ученик сопоставляет проектируемый item-ответ с реально полученным list-элементом, отмечает четыре совпавших поля и отсутствие `tags`; затем предсказывает, будут ли меняться счётчики `GET /stats` после GET. Верный вывод: запрос чтения не сохраняет изменений.

**Переход:** все механизмы разобраны отдельно; далее ученик самостоятельно собирает один маршрут и проверяет каждый существенный исход.

## 07. Что мы будем делать в практике

**Формат:** ручная проектная практика в существующем `app/api.py`, запросы через Postman/Swagger; никаких `script`/`solve`, готовых эталонов, новых API-файлов и TestClient. **Вход:** результаты 48 (list/stats, сервис в app.state, проекция) и наличие `get_task`/`TaskNotFoundError` подтверждены по фактической копии. Если список пуст, подготовить **учебную копию** данных с одной задачей через существующий CLI, сохраняя рабочий JSON; baseline снять после подготовки. Все дальнейшие проверки проводить на той же копии/текущем контролируемом наборе.

1. **Подготовить доказуемый baseline (разделы 00, 01, A из 48).** Самостоятельно отправить `GET /tasks` и `GET /stats`, выбрать **реальный положительный id** из полного списка, записать его четыре поля и полный список/statistics; зафиксировать содержимое JSON до опыта. **Локальный результат:** есть реальная запись для 200 и исходные данные для проверки read-only. Если прежние GET не работают, сначала вернуть результат занятия 48, не имитировать его в 48.1.
2. **Собрать один item-route (разделы 02–06).** В существующем `app/api.py` ученик **сам пишет** объявление `GET /tasks/{task_id}`, параметры `Request` и `Annotated[int, Path(gt=0)]`, передаёт id в прежний `get_task`, оформляет узкий `except TaskNotFoundError` → HTTP 404 и применяет готовую `_task_read_data`. Дать сигнатуры уже существующих сервисных функций, но **не выдавать готовый handler**. **Локальный результат:** запрос по выбранному id даёт 200 и совпадает с записью из list; в приложении нет второго маршрута с тем же методом и path.
3. **Отличить ошибки входа от отсутствия (разделы 02, 03, 05).** Отправить `/tasks/abc`, `/tasks/0`, `/tasks/-2`; перед каждым запросом предсказать, дойдёт ли он до `get_task`, и объяснить результат по ответу HTTP. Затем выбрать **фактически отсутствующий положительный id** (по полному списку и данным), запросить его и объяснить работу узкого исключения. **Локальный результат:** 422/422/422 до handler и 404 с `detail: "Task not found"` для отсутствующего id. Для сбоя storage проверить узость `except` по коду; если делать пробу, только на безопасной копии и без требования конкретного HTTP-кода сбоя.
4. **Проверить обратную совместимость и read-only (разделы 04, 06).** Снова вызвать list, stats и item для реального id, сверить с baseline и содержимым JSON; проверить доступность прежнего CLI. **Локальный результат:** прежние ответы и файл не изменились после чтений, `tags` не попали в API, значение item соответствует элементу списка.
5. **Перенести понимание (без новой темы).** Для другого существующего id самостоятельно объяснить, какие части URL, проверки и вызова сервиса меняются, а какие остаются прежними; затем сформулировать различие «недопустимый id» и «допустимый, но отсутствующий». **Локальный результат:** ученик может объяснить разные причины 422 и 404 без подсказки про конкретное число.

**Связь действий:** сначала получаем реальный объект и точку сравнения; после самостоятельной сборки route проверяем успех, ошибки до обработчика и ожидаемое отсутствие из сервиса; затем доказываем отсутствие изменений прежнего Planner. При затруднении с адресом вернуться к 01–03, с поиском — к 04, с 404 — к 05, с JSON ответа — к 06. Для MAIN предусмотреть содержательную схему пути запроса, прогноз по адресам и самостоятельную сборку: не более двух читаемых абзацев подряд без учебного действия/визуала, без серии однотипных проверок.

**Итог приёмки практики:** один новый `GET /tasks/{task_id}` возвращает публичные поля с кодом 200 по существующему положительному id, 404 по отсутствующему положительному, 422 по невалидному path; сбой storage не превращается в 404. Прежний CLI/list/stats и JSON сохраняют состояние. Результат передаётся в **49** как уже проверенный item-route; реализация `select_tasks` и query-фильтрации остаётся на следующих шагах.
