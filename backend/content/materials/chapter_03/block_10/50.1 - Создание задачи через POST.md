## Точка B: результат занятия

- Ученик сможет объяснить: FastAPI получает JSON в параметр `TaskCreate` и проверяет его до вызова маршрута; предметная проверка `Task` срабатывает позже внутри `add_task`. Эти два отказа могут дать 422, но возникают на разных этапах.
- Ученик сможет сделать: самостоятельно добавить в существующий `app/api.py` один `POST /tasks`, передать из готового `TaskCreate` в прежний сервис только клиентские `title` и `priority`, узко преобразовать ожидаемый `ValueError` в HTTP 422 и вернуть запись через имеющийся `_task_read_data`.
- Результат в проекте: успешный POST сохраняет новую задачу через существующий `PlannerService` и возвращает статус 201 с публичными `id`, `title`, `priority` и `is_done`. Сервер назначает id и начальное `is_done=False`.
- Как подтвердим: один корректный запрос возвращает 201 и ровно четыре публичных поля; `id` и `is_done=False` назначает Planner. По фактическому `id` прочитаем запись через item и явную выборку, проверим прирост `GET /stats` (`total` и `open` увеличились на 1, `done` не изменился), затем найдём её через CLI и повторим чтение после перезапуска API. Отсутствующее/неразбираемое поле и отдельно нарушение правила `Task` дают 422 на разных этапах; после каждого отказа счётчики и записи остаются прежними. Повторный успешный POST создаёт другую задачу. Сбой хранилища не моделируем и откат файла не обещаем.

## 00. Вступление

В предыдущем шаге мы подготовили `TaskCreate` с обязательными `title` и `priority` и проверили, как Pydantic строит эту модель. Но сама модель ещё не связана с запросом, не вызывает сервис и не создаёт запись. Теперь соединяем её с уже работающим API чтения и существующим `add_task`, чтобы POST стал продолжением того же Planner.

1. **Точка старта:** после 49.1 API читает выборку из общего Planner; после 50 в `app/api.py` есть проверенная `TaskCreate`, но ещё нет POST.
2. **Новый вопрос:** как связать готовое тело запроса с существующим созданием, не повторяя код сервиса и хранилища, и где различаются два отказа с кодом 422?
3. **Результат:** настоящий `POST /tasks` возвращает сохранённую задачу и подтверждается чтением по выданному `id`, статистикой и CLI.

Пойдём от уже подготовленной схемы: сначала проследим, как FastAPI связывает JSON с `TaskCreate`, затем отделим её роль от предметного создания и подключим POST. После успеха разберём два места отказа и подтвердим сохранение существующими средствами Planner. Результат станет точной опорой для следующего шага, который добавит нормализацию входа, не меняя маршрут.

## 01. Тело запроса становится проверенной схемой

- Что и зачем объяснить: как FastAPI связывает параметр типа Pydantic-схемы с JSON body; не пересказывать BaseModel, который подготовлен в 50.
- Механизм и порядок: клиент передаёт объект → FastAPI разбирает тело → Pydantic строит `TaskCreate` и проверяет обязательные поля/типы → только затем запускается функция маршрута. Обычное преобразование Pydantic сохраняется (например, разбираемая строка приоритета становится числом); здесь ещё нет `Field` или строгого режима.
- Пример и типичная путаница: на независимой схеме отзыва показать разницу между JSON-объектом и готовым Python-объектом параметра. Затем сравнить `{"title":"Купить хлеб","priority":"3"}` (обычное преобразование строки в число) с `{"title":"Купить хлеб","priority":"срочно"}` (неразбираемый тип, 422 до маршрута). Пропуск `priority` тоже останавливает запрос до маршрута. Аннотация `int` пока не проверяет диапазон предметного приоритета.
- Первое самостоятельное действие: по нескольким вариантам тела проследить, будет ли построена готовая схема и дойдёт ли запрос до обработчика; опереться на готовую в 50 `TaskCreate`, не объявляя её создание частью этой практики.
- Опора для повторного обращения: «body → TaskCreate → маршрут»; для ошибок формы восстановить, что обработчик и сервис ещё не вызваны.
- Переход к следующему шагу: проверенная входная схема задаёт форму клиентских данных, но пока ничего не создала и не сохранила.

## 02. Входная схема и задача отвечают за разное

- Что и зачем объяснить: почему `TaskCreate` — форма HTTP-входа, а не доменная `Task` и не замена `PlannerService`.
- Механизм и порядок: из схемы в существующий `request.app.state.planner.add_task` передаются только `title` и `priority`; сервис применяет правила `Task`, назначает id и `is_done=False`, затем сохраняет результат через выбранный storage. API не строит второй список и не пишет файл самостоятельно.
- Пример и типичная путаница: проследить существующий CLI-сценарий добавления и тот же сервисный контракт для HTTP. `model_dump` или словарь сами по себе не создают задачу и не сохраняют её; передавать в `add_task` нужно только два поля готовой схемы. Даже если клиент прислал `id` или `is_done`, эти поля не управляют созданной записью; новую политику запрета extra-полей не вводим.
- Первое самостоятельное действие: по контракту готовой `TaskCreate` и `add_task` отделить поля клиента от полей, которые создаёт Planner; получить карту передачи данных до написания обработчика. Критерий — названы `title` и `priority` на входе и назначаемые Planner `id` и `is_done=False`.
- Опора для повторного обращения: для успешного запроса держать рядом три роли — схема читает поля, сервис создаёт, storage сохраняет.
- Переход к следующему шагу: когда границы данных ясны, можно связать известный метод POST и адрес коллекции с реальным действием сервиса.

## 03. POST создаёт ресурс и возвращает 201

- Что и зачем объяснить: как подключить уже известные HTTP-договор, маршрут FastAPI и сервис без временного echo или новой операции Planner.
- Механизм и порядок: обработчик `POST /tasks` получает готовую `TaskCreate`, вызывает существующий сервис, а после успешного создания передаёт результат в `_task_read_data` из 48. Успех создания обозначается 201; статус не означает, что декоратор сам сохранил данные. До 52 проекция остаётся явной, `response_model` не вводится.
- Пример и типичная путаница: на независимом маршруте каталога показать связку typed body и 201; отдельно проговорить, что декоратор и статус не создают ресурс без вызова предметной операции. Не включать `tags` в публичный ответ, хотя они остаются частью доменной записи.
- Первое самостоятельное действие: определить в существующем приложении метод и path операции создания, затем самостоятельно связать готовую схему с `add_task` и прежним helper проекции, сохранив GET-маршруты. Локальный критерий этого шага — корректное тело возвращает 201 и публичные поля созданной Task; фактическое сохранение будет доказано отдельно.
- Опора для повторного обращения: после любого POST восстановить цепочку «проверенная схема → сервис → сохранение → публичный ответ»; 201 ожидается только после успешного создания.
- Переход к следующему шагу: корректный запрос работает; теперь нужно разобрать, на каком этапе останавливаются два вида неверных входов.

## 04. Два отказа с одним статусом 422

- Что и зачем объяснить: чем автоматическая проверка body отличается от отказа предметной модели внутри сервиса.
- Механизм и порядок: Pydantic отклоняет отсутствующее обязательное поле или неразбираемый тип до обработчика. Если корректно разобранное значение нарушает правила `Task`, `add_task` сообщает ожидаемый `ValueError`; только его узкий участок вызова переводит в 422. Формы `detail` могут различаться. Ошибка storage и ошибка программы не должны маскироваться как неверный запрос.
- Пример и типичная путаница: `{"title":"Купить хлеб"}` не содержит обязательного поля и даёт автоматический 422; `{"title":"","priority":3}` подходит по простой схеме `TaskCreate`, но нарушает предметное правило непустого названия в `Task` — ожидаемый `ValueError` преобразуется в 422 внутри обработчика. Уточнить, что `try/except ValueError` охватывает только вызов `add_task`: так ошибка другого кода не превращается в сообщение о плохом вводе. Не перехватывать общую `Exception`; не утверждать, что сбой записи JSON атомарно откатывает файл.
- Первое самостоятельное действие: классифицировать предложенные случаи по этапу отказа, форме ответа, вызван ли сервис и может ли появиться новая запись; применить эту границу к обработчику.
- Опора для повторного обращения: «ошибка формы — до функции; `ValueError` модели — вокруг вызова сервиса; storage-сбой — не 422». Для каждого отказа проверять состояние после запроса.
- Переход к следующему шагу: различие отказов подготовлено; осталось доказать, что успешный ответ соответствует новой записи в общем источнике данных.

## 05. Ответ проверяется через существующие чтения

- Что и зачем объяснить: почему 201 и JSON-ответ сами по себе не доказывают, что Planner сохранил задачу.
- Механизм и порядок: id берётся из ответа POST; им запрашивается item. `GET /stats` считает все задачи, поэтому при создании открытой задачи `total` и `open` растут на 1, `done` не меняется. Обычный список ограничен первыми десятью id по возрастанию, поэтому для поиска последней записи нужна уже изученная явная сортировка/граница. CLI и API читают один JSON; повторное чтение после перезапуска подтверждает сохранение.
- Пример и типичная путаница: отсутствие новой записи в коротком default-списке не равно ошибке POST; не сравнивать с выдуманными id и не требовать фиксированного количества прежних задач.
- Первое самостоятельное действие: записать реальные `total/open/done` до запроса, по ответу POST взять выданный `id`, прочитать именно этот item и сверить разницу счётчиков с CLI. Для проверки коллекции явно запросить `GET /tasks?sort_desc=true&limit=1` и сравнить `id`; обычный список по умолчанию может не включить новую запись.
- Опора для повторного обращения: после создания сверить фактический id, четыре публичных поля и актуальное состояние; данные рабочего файла не очищать ради ожидаемой таблицы.
- Переход к практике: ученик готов внести одно изменение в существующий API и проверить его по независимым чтениям.

## 06. Что мы будем делать в практике

**Формат и исходная опора:** manual в существующем StudyHub: `TaskCreate` из шага 50, работающие GET, `request.app.state.planner`, прежний сервис `add_task`, `_task_read_data`, JsonStorage и CLI. До проектной правки отдельно убедиться, что входная схема действительно подготовлена; если нет, остановить зависимую часть и зафиксировать отсутствующий результат 50. Начинаем с действующего JSON и сохраняем его данные.

Общий результат — один рабочий `POST /tasks`, который принимает тело, использует прежний сервис, назначает серверные поля, сохраняет задачу и возвращает контракт 201.

1. **Проверить вход и зафиксировать baseline (разделы 00–02).** Вход — существующий `app/api.py` и рабочий файл Planner. Если `TaskCreate`, общий storage или `add_task` отсутствуют, восстановить соответствующую предпосылку прежнего занятия, не писать обходную реализацию POST.
2. **Самостоятельно подключить создание (разделы 01–03).** Вход — проверенная схема и два клиентских поля. В том же `app/api.py` ученик пишет один обработчик `POST /tasks`: принимает `TaskCreate`, обращается к прежнему `request.app.state.planner.add_task`, узко переводит ожидаемый `ValueError` в 422 и возвращает результат прежнего `_task_read_data` со статусом 201. Записать этот `id` для дальнейших проверок.
3. **Самостоятельно различить отказы (разделы 01, 02 и 04).** Вход — сначала тело без `priority`, затем `{"title":"Купить хлеб","priority":"срочно"}`, после — подходящее по типам `{"title":"","priority":3}`, нарушающее правило `Task`. Ученик отправляет три отдельных POST и определяет, какие из них остановлены FastAPI до обработчика, а какой дошёл до `add_task` и вызвал `ValueError`. **Локальный результат:** каждый ответ имеет 422; после **каждой** попытки `total/open/done` сохраняются на уровне после успешного POST, созданный ранее `id` по-прежнему читается.
