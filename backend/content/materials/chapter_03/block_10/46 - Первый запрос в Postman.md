## Место в маршруте

Занятие переводит учебную схему HTTP в первый настоящий обмен: ученик сам отправляет GET из Postman на публичный сервер Echo и проверяет, какие параметры до него дошли. Не требуется писать Python-код или запускать Planner API.

## Точка B: результат занятия

- **Объясняет:** Postman — клиент, Echo — отдельный учебный сервер; method/URL/query принадлежат запросу, status/headers/body — ответу; Echo показывает полученные значения, но не выполняет операции Planner.
- **Делает сам:** выбирает environment `Echo` с `base_url=https://postman-echo.com`, собирает `GET {{base_url}}/get`, вносит через Params `is_done=false` и `limit=2`, отправляет запрос и находит оба значения в ответе.
- **Наблюдаемая проверка:** при доступном Echo получен HTTP 200 и в body по ключу `args` находятся **строки** `"false"` и `"2"`. Ученик называет фактический status и отличает HTTP-ответ с ошибочным status от сбоя до получения ответа. Получить 200 без нужных `args` недостаточно.
- **Проект:** код, CLI и рабочий JSON Planner остаются без изменений. Рабочий GET можно сохранить для 46.1, но запись в collection сама по себе не доказывает отправку.

## 00. Вступление

До этого ученик собирал запрос на бумаге или в учебной модели. Здесь он впервые нажмёт Send и увидит, какие данные действительно дошли до сервера. Сначала — входная проверка на `GET /books?limit=3`: method `GET`, path `/books`, query `limit=3`, request body отсутствует; статус и содержимое ответа до отправки неизвестны. Это диагностическая опора, а не готовая инструкция для целевого Echo-запроса.

1. **Точка старта:** ученик различает method, path, query и response после входной проверки 45; опыт работы с Postman не предполагается.
2. **Новый вопрос:** как отправить настоящий GET и убедиться по ответу, что сервер увидел обе query-пары?
3. **Результат:** настроенный Echo environment, отправленный GET и проверенные значения ответа; при необходимости рабочий запрос сохраняется для 46.1.

После входной пробы ученик отделяет клиент от сервера, находит поля request/response, настраивает адрес, отправляет GET, добавляет query и сам проверяет ответ. Никакое из этих действий не запускает Planner.

## 01. Postman как клиент, Echo как сервер

- Что объяснить: **Postman** — программа-клиент, в которой человек собирает и отправляет HTTP-запрос. **Echo** — отдельный учебный сервер: он получает запрос и возвращает сведения о нём. Схема `Postman → сеть → Echo → ответ → Postman` показывает два направления, а не один словарь Python.
- Независимый пример: запрос погоды к сервису погоды ничего не сообщает о задачах Planner. Так же Echo может показать, что параметр `limit` дошёл, но **не** ограничивает список задач и не подтверждает наличие Planner API.
- Первое самостоятельное действие: на схеме подписать, кто составляет URL, кто получает запрос и кто показывает ответ; назвать момент, когда вообще можно говорить «получен ответ сервера». Критерий: редактирование до Send не принимается за отправку, а `200` от Echo не приписывается Planner.
- Переход: теперь надо научиться отличать области отправки и получения в интерфейсе.

## 02. Поля запроса и ответа в Postman

- Что объяснить: до Send в области **request** выбирают Method (`GET`), вводят URL и пары Params; после отправки в области **response** смотрят status, headers и body. Вкладки Headers/Body есть с обеих сторон, поэтому подчёркиваем, какому сообщению принадлежит поле. В этом GET **не отправляем body**, но сервер может вернуть JSON в **response body**.
- Механизм: схема двух колонок «отправляем: method + URL + Params → Send | получаем: status + response headers + response body». Status — числовой код ответа HTTP; `Content-Type` в response headers описывает тип возвращённых данных; body содержит сам результат, в котором позже ищем `args`.
- Независимый пример и первая попытка: на условном GET справочной статьи отметить, где указан адрес запроса и где виден JSON ответа; объяснить, почему пустой request Body не запрещает непустой response body. Критерий: ученик не принимает за ответ черновик запроса и не путает вкладки с одинаковыми именами.
- Переход: перед настоящим Send нужно определить адрес Echo, не вводя его целиком каждый раз.

## 03. Environment и подстановка адреса

- Что и зачем объяснить: **environment** (окружение) — выбранный набор именованных значений; в нём `base_url` хранит адрес сервера. Запись `{{base_url}}/get` в Postman перед отправкой превращается в `https://postman-echo.com/get`. `base_url` — не команда Python, а подстановка Postman; она не создаёт сервер.
- Механизм и порядок: найти доступное окружение `Echo`, либо создать его; установить `base_url=https://postman-echo.com` в используемое для запросов значение переменной, сохранить доступным в данной версии Postman способом; **выбрать Echo активным**. До Send проверить разрешённый адрес, включая `https://` и `/get`. В UI расположение выбора окружения может отличаться по версии.
- Независимый пример и путаница: для условного окружения `Demo` с `base_url=https://example.org` запись `{{base_url}}/catalog` означает `https://example.org/catalog`, но если выбрано другое окружение, адрес поменяется. Одно только имя `Echo` в списке не гарантирует, что оно активно или что значение переменной заполнено.
- Первое самостоятельное действие: по двум условным вариантам окружения предсказать итоговый URL, затем проверить своё существующее/новое окружение `Echo` и подстановку `{{base_url}}/get`. Критерий — нацеливание на `postman-echo.com`; незаменённые `{{...}}` или пустое значение требуют исправления до Send.
- Короткая граница на будущее: **collection** — место, где можно сохранить запрос; полное объяснение сохранения, экспорта и импорта будет в 46.1. Если workspace требует авторизации или не даёт сохранить настройки, отдельно отметить ограничение среды и не выдавать его за ошибку HTTP.
- Переход: когда адрес раскрывается корректно, можно отправлять первый запрос без параметров и читать ответ.

## 04. Первый GET и адрес endpoint

- Что объяснить: в полном `https://postman-echo.com/get` часть `https://postman-echo.com` называет сервер, а `/get` — **path** (путь нужной операции) на нём; GET — метод запроса. Это не путь к файлу и не название Python-функции.
- Механизм: выбрать `GET`, указать `{{base_url}}/get`, убедиться, что выбран `Echo` и подставлен правильный сервер. Отправить **первый GET без Params**: так начинающий видит рабочую отправку прежде, чем разбираться с query. При доступном сервисе ожидается status 200; фактическое значение надо прочитать, не назначать заранее.
- Независимый пример: в `https://example.org/catalog` определить сервер и path. Самостоятельная первая проба: собрать Echo GET без Params, предсказать, что `args` будет пустым, нажать Send и проверить результат. Критерий: виден response Echo либо честно зафиксирован сбой связи; незаполненную переменную исправляют до отправки.
- Переход: когда запрос доходит до Echo, добавим **данные**, которые можно увидеть в его ответе.

## 05. Query как переданные текстовые значения

- Что объяснить: **query** — параметры после `?` в URL. Postman строит их через таблицу Params: первая строка — имя/значение, вторая — другая пара. Например, `color=blue` станет `?color=blue`; следующая пара присоединяется через `&`. Не нужно требовать ручного написания URL с символами.
- Механизм и пример: Echo показывает полученные query в объекте `args` ответа, для `?color=blue` ожидается `"args": {"color": "blue"}`. Значения из URL приходят как **текст**: `"2"` в Echo — не JSON-число `2`, а `"false"` — не булево `false`. Как их трактовать, решит будущий сервер Planner.
- Первое самостоятельное действие: предсказать `args` для нового условного `?size=4&color=red`, затем без подставленного решения заполнить в Postman **две строки** Params: `is_done=false` и `limit=2`, предсказать и сверить отражение. Критерий: обе пары присутствуют в итоговом URL и в `args` строками; `200` с отсутствующим `limit` не проходит.
- Опора для возврата: при несовпадении открыть Params, проверить каждую пару и итоговый URL; не утверждать, что Echo отфильтровал задачи.
- Переход: проверим результат целиком, включая ситуации, когда HTTP-ответа вообще нет.

## 06. Проверка ответа и границы вывода

- Что объяснить: успешная **проверка запроса** требует двух наблюдений: сервер ответил (например, 200) **и** вернул ожидаемые `args`. Response headers (в частности, `Content-Type`, если он есть) описывают ответ; содержимое `args` ищем именно в **response body**.
- Механизм диагностики: `был ли HTTP response? → какой status? → какой response body? → есть ли обе пары в args?`. `404` с ответом — это HTTP-ответ с ошибочным кодом; `connection failed` без response — сетевая/адресная проблема, у неё нет HTTP-status. `200` с пустыми `args` означает, что сервер ответил, но нужный запрос ещё не подтверждён.
- Независимая попытка: по трём карточкам («200, args пуст», «404, body есть», «connection failed, status отсутствует») для каждой определить наличие ответа и можно ли утверждать, что query дошёл. Затем самостоятельно применить ту же проверку к собственному GET. Критерий: status не приписывается сетевой ошибке, а успех не выводится из одного `200`.
- Опора для возврата: если `args` неверны, проверить Params и URL (§§03–05); если ответа нет — активное окружение, URL и доступность сети (§03–04). Не объявлять Echo ошибкой Planner.
- Переход к практике: ученик применяет весь маршрут на своём GET и проверяет ещё один изменённый набор параметров.

## 07. Что мы будем делать в практике

**Формат по паспорту:** UI-практика в Postman (`BLOCK_10.md`, §46, п. 5). На входе — самостоятельно разобранная HTTP-модель из 45 (перед выдачей проверить), доступный Postman и публичный Echo. Никакого FastAPI-приложения и файлов Planner для упражнения не требуется. Настройку и сетевую отправку оцениваем отдельно.

**Итог:** ученик самостоятельно отправляет `GET {{base_url}}/get?is_done=false&limit=2`, показывает method/адрес/query, фактический status и обе текстовые записи в `response.body.args`; объясняет, что это ответ Echo, а не Planner. Подсказка убывает от разбора одного условного URL к собственному запросу и проверке нового значения.

1. **Выбрать правильный сервер.** **Вход:** Postman и имеющийся либо пустой список environments. **Объект:** environment `Echo`, переменная `base_url`. **Опора:** §03 — переменная и выбор активного окружения. **Самостоятельно:** найти подходящее окружение или создать недостающее, задать `https://postman-echo.com`, активировать его и проверить итоговый адрес `{{base_url}}/get`. **Локальная проверка:** подстановка даёт именно `https://postman-echo.com/get`. **Различающий случай:** окружение с правильным именем существует, но не выбрано, или переменная пуста — шаг ещё не выполнен; вернуться к §03, дубликаты не создавать.
2. **Отправить первый GET без параметров.** **Вход:** рабочий `base_url` из шага 1. **Объект:** новый request, method `GET`, URL `{{base_url}}/get`, пустая вкладка Params. **Опора:** §§01, 02, 04 — стороны обмена, части адреса, Send. **Самостоятельно:** предсказать, есть ли query и что Echo покажет в `args`, отправить GET, найти status и body ответа. **Локальная проверка:** при доступном Echo получен ответ, обычно `200`, и нет отправленных query-пар. **Различающий случай:** ошибка подключения без response не превращается в «status 404»; проверить подстановку и связь, не идти к следующему шагу, будто запрос прошёл.
3. **Собрать целевой query без готового URL.** **Вход:** рабочий GET шага 2 и предварительный разбор **другого** случая `size=4&color=red`. **Объект:** две строки Params. **Опора:** §05 — имя/значение, `?`, `&`, текст в Echo `args`. **Самостоятельно:** ввести `is_done=false` и `limit=2`, предсказать их вид в `args` **до Send**, затем отправить. **Локальная проверка:** оба параметра в URL; в response body по `args` стоят строки `"false"` и `"2"`, при нормальной работе Echo — status 200. **Различающий случай:** status 200, но `args.limit` отсутствует — запрос нельзя зачесть, нужно проверить заполнение Params; Echo не отбирает задачи Planner.
4. **Самостоятельно разобрать ответ.** **Вход:** фактический response из шага 3 либо конкретная ошибка отправки. **Объект:** отдельная область ответа: status, response headers и response body/`args`. **Опора:** §§02, 06 — четыре проверки результата. **Самостоятельно:** указать факт наличия HTTP-response, прочитать status, найти `Content-Type`, если есть, показать обе пары в `args`; своими словами пояснить, чей это ответ и чего он **не** доказывает о Planner. **Локальная проверка:** назван действительный код и показаны две записи в body, а не только произнесено «200». **Различающий случай:** сравнить предложенные `404` с body и `connection failed` без response; во втором случае HTTP-status неизвестен.
5. **Перенести способ проверки на изменённый запрос.** **Вход:** проверенный GET шага 3. **Объект:** значение Params `limit` у того же Echo GET. **Опора:** §§05–06, но без готового ответа для нового значения. **Самостоятельно:** заменить только `limit=2` на `limit=5`, **до Send** предсказать, как изменится `args`; отправить, сверить две строки, затем вернуть `limit=2` и ещё раз убедиться, что исходный запрос работает. **Локальная проверка:** `args.is_done` осталось `"false"`, а `args.limit` стало `"5"`, после возврата — `"2"`. **Различающий случай:** если `200` есть, но значение осталось `"2"`, ученик находит несохранённое/неотправленное изменение Params. Для передачи 46.1 при доступном workspace сохранить возвращённый GET в collection `Planner HTTP Lab`; экспорт/импорт сейчас не выполнять.

Шаги наращивают наблюдаемый результат: правильный host → GET без query → самостоятельно собранные Params → доказательство по response → перенос на другое значение. Возврат к конкретной опоре указан для ошибки настройки, отправки и данных. Сохранение запроса облегчает переход в 46.1, но **B занятия 46 проверяется реальным HTTP-обменом и объяснением ответа**, а не наличием коллекции. В 46.1 ученик при необходимости сохранит GET и проверит восстановление из экспорта.

**P4-критерий для MAIN:** при доступной сети ученик без готового целевого URL отправляет GET к Echo, доказывает `200 + args.is_done == "false" + args.limit == "2"`, объясняет роли клиента/сервера и верно классифицирует отсутствие ответа; на `limit=5` сам прогнозирует изменение и проверяет его. Если Echo недоступен, допускается учебный разбор образца для подготовки, однако фактический запрос и B **не засчитываются**, пока не получен проверяемый HTTP-ответ. Исходные CLI/JSON Planner не изменяются.
