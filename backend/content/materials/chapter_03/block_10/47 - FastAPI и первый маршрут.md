## 00. Вступление

После запросов к Echo уже есть HTTP-клиент, но ещё нет собственного сервера Planner. CLI продолжает работать через существующий проект; новая точка входа должна появиться рядом с ним и не перехватывать его роль.

1. **Точка старта:** Postman отправляет request, Echo отвечает, а CLI Planner по-прежнему работает с задачами.
2. **Новый вопрос:** как принять HTTP-запрос внутри нашего проекта, не заменяя CLI и не создавая второй Planner?
3. **Результат:** FastAPI-приложение с GET /health запускается через Uvicorn и возвращает короткий проверяемый ответ.

Связь проста: Echo показал обмен с чужим сервером; теперь добавим собственную точку входа. Сначала отделим объект приложения от работающего процесса, затем зарегистрируем маршрут и запустим сервер. При подготовке MAIN оформить эту триаду одной `LinkedNotes variant="connected"` и объяснением после неё.

## 01. Приложение и сервер выполняют разные роли

- Что и зачем объяснить: FastAPI — фреймворк, объект приложения хранит настройки и зарегистрированные маршруты. Uvicorn — отдельный ASGI-сервер, который запускает приложение, слушает порт и передаёт ему запросы.
- Механизм и порядок: вызов конструктора FastAPI создаёт объект; сетевой процесс появляется только после запуска Uvicorn. На независимом примере сервиса уведомлений показать эту границу без Task и файлов Planner.
- Наглядная опора 1: «расписание приёма» (объект приложения знает, какая операция доступна) и «открытая стойка» (процесс сервера физически принимает посетителей). Предел: приложение является Python-объектом и может существовать без запущенного сетевого процесса; аналогия не описывает механизм запуска.
- Пример и типичная путаница: после создания app запрос ещё некому принять; наличие маршрута в коде не означает, что порт уже слушает сервер.
- Первое самостоятельное действие: ученик предсказывает состояние порта при «объект создан, Uvicorn не запущен» и после старта сервера; объясняет, почему в первом случае сетевого ответа нет. Визуал: стрелки `клиент → Uvicorn → приложение`, отдельно отмеченный незапущенный процесс. Это не проверка 404/405.
- Опора для повторного обращения: различать объект FastAPI, процесс Uvicorn и HTTP-клиент по их ролям и наблюдаемому действию.
- Переход к следующему шагу: приложению нужен зарегистрированный маршрут, который сможет вызвать сервер.

## 02. Маршрут связывает метод и path с обработчиком

- Что и зачем объяснить: декоратор FastAPI регистрирует пару HTTP-метод + path и связывает её с функцией. Имя функции не становится URL и объявление функции не запускает её при чтении модуля.
- Механизм и порядок: если работа с `@` не подтверждена, **до первой самостоятельной записи** пояснить форму `@app.get("/status")` над `def status():` на независимом примере уведомлений. `@` применяет декоратор к следующей функции; `app` — заранее созданный объект; `.get(...)` указывает метод GET и строку пути; двоеточие после `def` и отступ формируют тело обработчика. Показать, что регистрация выполняется при импорте модуля, а **тело обработчика** вызывается при подходящем HTTP-запросе. Готовый `/health` не писать.
- Наглядная опора 2: небольшая таблица соответствий `метод + path → функция` для службы уведомлений (например, `GET /status`). Предел: запись в таблице не исполняет функцию заранее; реальный HTTP-запрос проходит через работающий Uvicorn.
- Пример и типичная путаница: два разных метода на одном path обозначают разные операции; декоратор описывает регистрацию, но не запускает Uvicorn.
- Первое самостоятельное действие: из двух пар `GET /status` и `POST /status` ученик выбирает, какая совпадает с показанной регистрацией, и объясняет выбор; затем самостоятельно называет тройку «метод, path, обработчик» для будущего health без получения готового решения.
- Опора для повторного обращения: восстановить порядок «метод + path → зарегистрированный обработчик → результат»; проверить, что функция не выполняется только из-за импорта.
- Переход к следующему шагу: обработчик должен вернуть результат, который FastAPI отправит клиенту.

## 03. Возвращаемое значение становится HTTP-ответом

- Что и зачем объяснить: handler возвращает структурированное значение; FastAPI сериализует словарь в JSON и формирует успешный HTTP-ответ со статусом 200 по умолчанию.
- Механизм и порядок: на независимом обработчике статуса сравнить `print("ready")` с `return {"state": "ready"}`. Показать последовательность `return` словаря → преобразование FastAPI в JSON body → стандартный статус 200; отдельно объяснить, что `200` не является полем возвращённого словаря. Health сообщает, что запрос дошёл до обработчика, но не проверяет JSON-файл, сервис или будущие операции.
- Пример и типичная путаница: для независимого status-маршрута сопоставить словарь ответа и отображаемый JSON; не приравнивать 200 к доказательству работы всего Planner.
- Первое самостоятельное действие: ученик предсказывает, появится ли `ready` в JSON body при `print` и при `return`, и отдельно указывает ожидаемый 200; сверяет с разбором ответа другого сервиса. Визуал: рядом Python-значение, JSON body и строка HTTP-статуса, без подсказки к итоговому `/health`.
- Опора для повторного обращения: при проверке развести три наблюдения — HTTP-статус, JSON-тело и фактический scope health.
- Переход к следующему шагу: чтобы проверить результат, нужны установленные зависимости в том же Python-окружении, где работает проект.

## 04. Зависимости устанавливаются в окружение проекта

- Что и зачем объяснить: FastAPI и Uvicorn добавляются как runtime-зависимости существующего проекта; requirements.txt фиксирует набор для повторного запуска. Предыдущие зависимости сохраняются.
- Механизм и порядок: подтвердить корень, `.venv` и выбранный интерпретатор; объяснить `python -m pip install -r requirements.txt` и `python -m pip show fastapi uvicorn`: `-m` запускает модуль выбранным Python, `-r` читает список пакетов. В runtime-списке сохранить имеющиеся зависимости и добавить совместимые FastAPI/Uvicorn, подтвердив фактически установленные версии. Паспорт не требует фиксированных номеров; старые пины без проверки не копировать. `requirements-dev.txt` и соседние пакеты не перезаписывать.
- Пример и типичная путаница: установка через системный pip может попасть в другой Python, чем команда запуска сервера; поэтому install и run обращаются к выбранному python.
- Первое самостоятельное действие: ученик сравнивает два обозначенных пути к Python и выбирает, каким выполнит install и run, чтобы использовать одно окружение; затем на учебном списке зависимостей определяет, что сохранить, а что добавить. Локальная проверка — вывод `pip show` относится к выбранному Python. Визуал: схема «один interpreter → install → uvicorn» с перечёркнутой установкой в чужое окружение.
- Опора для повторного обращения: перед запуском сверить корень проекта, выбранный python и наличие обоих пакетов в его окружении.
- Переход к следующему шагу: установленный серверу пакет нужен для импорта модуля приложения и запуска объекта по его адресу.

## 05. Uvicorn загружает модуль и запускает объект приложения

- Что и зачем объяснить: строка app.api:app состоит из пути к Python-модулю и имени объекта FastAPI. Команду запускают из корня, чтобы импорт app.api нашёл пакет проекта.
- Механизм и порядок: разобрать `python -m uvicorn app.api:app --reload --host 127.0.0.1 --port 8000`: тот же выбранный Python, корень проекта как рабочая папка, Python-модуль `app.api` до двоеточия, имя объекта `app` после, адрес localhost и порт 8000, `--reload` для разработки. Сначала на независимом модуле уведомлений разобрать смысл `модуль:объект`; затем ученик сам сопоставляет его с `app/api.py`. ASGI — интерфейс передачи HTTP-запросов приложению, подробности async не нужны.
- Пример и типичная путаница: `app.api` — модуль, второй `app` — объект; URL `/health` не является путём к файлу. Uvicorn занимает запущенный терминал, пишет там журнал и останавливается через Ctrl+C; `--reload` может создавать процесс перезагрузки. Отсутствие сервера не порождает HTTP-статус, но диагностика 404/405 остаётся в 47.1.
- Первое самостоятельное действие: ученик выделяет из команды модуль, объект, рабочий каталог и адрес `http://127.0.0.1:8000/`, затем **сам составляет URL `/health` для Postman**. Восстановить знакомые из 46.1 элементы интерфейса: метод GET, поле URL, Send, HTTP-status и JSON-body; для localhost проверить доступность локального агента Postman, иначе нельзя объявлять запрос выполненным. Различающий случай: правильный URL при остановленном сервере даёт **ошибку соединения без HTTP-статуса**, а 200 с JSON бывает только после успешного вызова обработчика. Визуал: «импорт модуля → сервер слушает порт → Postman GET → JSON-ответ → Ctrl+C», с конкретным адресом из запущенной команды.
- Опора для повторного обращения: при невозможности соединения проверить живой процесс, host/port, выбранный Python и локальный агент Postman; при ошибке импорта — корень и `app.api:app`. Отдельную диагностику 404/405 оставить 47.1.
- Переход к следующему шагу: можно создать реальный health-маршрут и проверить, что новый web-вход не заменил CLI.

Если `app/api.py` уже есть после старого 52, используем согласованный снимок до API, **не стирая** готовые файлы. Из 46.1 нужна работоспособная отправка запросов в Postman; Echo-коллекцию сохраняем отдельно. Далее `python` во всех командах — **один и тот же выбранный Python**.

1. **Убедиться, что входной Planner работает → получить исходную точку сравнения.** **Вход:** выбранная учебная копия до API и инструкция запуска CLI из главы 2. **Объект:** `app/main.py`, рабочий JSON, интерпретатор, `.venv` и имеющиеся файлы зависимостей. **Опора:** проверяемая перед выдачей B главы 2 и раздел 01 (CLI и сервер — разные входы). **Самостоятельно:** ученик из корня запускает привычный CLI, просматривает список задач без изменений, выходит, определяет его данные и проверяет наличие `app/api.py`. **Локальный результат:** меню и чтение работают, сохранено наблюдение «список с задачами / корректно пустой список» для сравнения после запуска API. **Различающий случай:** готовый API в найденной копии запрещает создавать его поверх без согласования учебного снимка; неисправный CLI сначала восстанавливается как входная опора.
2. **Добавить зависимости → подготовить один воспроизводимый Python.** **Вход:** результат шага 1, выбранный интерпретатор и существующий список пакетов. **Объект:** корневой runtime `requirements.txt` (создать, если отсутствует; дополнить, если есть) и без изменения `requirements-dev.txt`. **Опора:** раздел 04. **Самостоятельно:** ученик определяет, какие строки сохранить, добавляет совместимые FastAPI/Uvicorn с проверенными версиями, устанавливает через `python -m pip install -r requirements.txt` и проверяет через `python -m pip show fastapi uvicorn`. **Локальный результат:** обе библиотеки находятся **в выбранном Python**, прежние зависимости сохранены; установленная версия соответствует внесённой записи. **Различающий случай:** наличие пакета в другом интерпретаторе не подтверждает готовность среды, а уже существующий файл нужно дополнить, не обнулить.
3. **Самостоятельно создать HTTP-вход → получить импортируемое приложение.** **Вход:** шаг 2, подтверждённый пакет `app/`, проект до API. **Объект:** новый `app/api.py`; `app/main.py` и предметный сервис остаются прежними. **Опора:** разделы 01–03 (импорт, `FastAPI()`, `@app.get(...)`, `def`, `return` словаря). **Самостоятельно:** ученик **пишет** создание объекта `app`, регистрацию только `GET /health` и обработчик, возвращающий JSON-совместимый словарь со строкой `status` = `ok`; готовой реализации health в starter нет. **Локальный результат:** `python -c "from app.api import app; print(type(app).__name__)"` из корня выводит `FastAPI` без появления меню CLI и без запуска сервера. **Различающий случай:** один импорт создаёт объект и регистрирует маршрут, но ещё не принимает HTTP; `print("ok")` внутри handler не становится JSON-ответом.
4. **Запустить Uvicorn и отправить GET через Postman → увидеть настоящий HTTP-ответ.** **Вход:** импортируемый `app/api.py`, рабочий Python и знакомые элементы Postman из 46.1. **Объект:** Uvicorn из корня проекта, запрос `GET http://127.0.0.1:8000/health` (или согласованный фактический порт) и вывод Postman. **Опора:** разделы 03 и 05; сам POST Echo из 46.1 не нужен. **Самостоятельно:** ученик составляет команду `python -m uvicorn app.api:app --reload --host 127.0.0.1 --port 8000`, проверяет локальный агент Postman, задаёт **GET** и адрес, нажимает Send, отдельно сверяет status/body, записывает подтверждённую команду запуска в README и завершает сервер Ctrl+C. **Локальный результат:** при работающем сервере Postman показывает **HTTP 200** и JSON **ровно `{"status":"ok"}`**, Uvicorn пишет запись о GET, после Ctrl+C процесс остановлен. **Различающий случай:** повторный Send при остановленном сервере даёт ошибку **соединения без HTTP-статуса**, а не 200; если локальный агент Postman недоступен, запрос отмечается «не проверен», даже если похожая страница открылась в браузере. Диагностика 404/405 относится к 47.1.
5. **Повторить запуск и проверить сохранность CLI → доказать воспроизводимость.** **Вход:** остановленный Uvicorn, записанная самим учеником команда в README и наблюдение из шага 1. **Объект:** README, тот же `app/api.py` и прежние CLI/JSON. **Опора:** разделы 01, 04–05. **Самостоятельно:** ученик по своей инструкции повторно запускает Uvicorn и снова отправляет GET из Postman, останавливает сервер, затем запускает CLI, читает список и выходит. **Локальный результат:** повторный запрос опять даёт **200 + нужный JSON**, CLI показывает те же задачи (или тот же пустой список), а JSON не был изменён. **Различающий случай:** повторный импорт и запуск API не должен показывать CLI-меню, а штатно закрытый сервер не мешает отдельному запуску старого интерфейса.

Эта последовательность связана наблюдаемыми состояниями **«исходный CLI → зависимости → импортируемое приложение → Postman-ответ → повтор запуска + тот же CLI»**. На MAIN это вторая `LinkedNotes variant="connected"`, **с пояснением после списка**. Первая проверка выявляет исходное состояние, третья отличает создание app от запуска порта, четвёртая доказывает реальный ответ, пятая — повторяемость и отсутствие регрессии. При ошибке ученик возвращается к конкретной опоре 01–05 и повторяет только соответствующую локальную проверку; готовую реализацию health не выдаём.

**Итоговый критерий B:** ученик объясняет связь app → method/path → handler → JSON и роль Uvicorn; сам написал FastAPI app и health, из того же Python дважды запустил сервер, из **Postman** получил **HTTP 200** и JSON-объект `{"status":"ok"}`, остановил процесс и сравнил старый CLI с исходным чтением без изменения JSON. Одна установка пакетов в другом Python, вывод `print` или успешный запрос только в браузере обязательный Postman-результат не заменяют. Health сам по себе не доказывает работоспособность PlannerService.

В 47.1 проверят OpenAPI/Swagger, оформят локальную коллекцию Postman и разберут HTTP 404/405; в 48 впервые подключат чтение Planner через service.
