## 00. Вступление

После запросов к Echo уже есть HTTP-клиент, но ещё нет собственного сервера Planner. CLI продолжает работать через существующий проект; новая точка входа должна появиться рядом с ним и не перехватывать его роль.

1. **Точка старта:** Postman отправляет request, Echo отвечает, а CLI Planner по-прежнему работает с задачами.
2. **Новый вопрос:** как принять HTTP-запрос внутри нашего проекта, не заменяя CLI и не создавая второй Planner?
3. **Результат:** FastAPI-приложение с GET /health запускается через Uvicorn и возвращает короткий проверяемый ответ.

Связь проста: Echo показал обмен с чужим сервером; теперь добавим собственную точку входа. Сначала отделим объект приложения от работающего процесса, затем зарегистрируем маршрут и запустим сервер. При подготовке MAIN оформить эту триаду одной `LinkedNotes variant="connected"` и объяснением после неё.

## 01. Приложение и сервер выполняют разные роли

- Что и зачем объяснить: FastAPI — фреймворк, объект приложения хранит настройки и зарегистрированные маршруты. Uvicorn — отдельный ASGI-сервер, который запускает приложение, слушает порт и передаёт ему запросы.
- Механизм и порядок: вызов конструктора FastAPI создаёт объект; сетевой процесс появляется только после запуска Uvicorn. На независимом примере сервиса уведомлений показать эту границу без Task и файлов Planner.
- Наглядная опора 1: «расписание приёма» (объект приложения знает, какая операция доступна) и «открытая стойка» (процесс сервера физически принимает посетителей). Предел: приложение является Python-объектом и может существовать без запущенного сетевого процесса; аналогия не описывает механизм запуска.
- Пример и типичная путаница: после создания app запрос ещё некому принять; наличие маршрута в коде не означает, что порт уже слушает сервер.
- Первое самостоятельное действие: ученик предсказывает состояние порта при «объект создан, Uvicorn не запущен» и после старта сервера; объясняет, почему в первом случае сетевого ответа нет. Визуал: стрелки `клиент → Uvicorn → приложение`, отдельно отмеченный незапущенный процесс. Это не проверка 404/405.
- Опора для повторного обращения: различать объект FastAPI, процесс Uvicorn и HTTP-клиент по их ролям и наблюдаемому действию.
- Переход к следующему шагу: приложению нужен зарегистрированный маршрут, который сможет вызвать сервер.

## 02. Маршрут связывает метод и path с обработчиком

- Что и зачем объяснить: декоратор FastAPI регистрирует пару HTTP-метод + path и связывает её с функцией. Имя функции не становится URL и объявление функции не запускает её при чтении модуля.
- Механизм и порядок: восстановить форму `@` из исторического 27.1, а если она не подтверждена в новой выдаче — дать здесь минимальное объяснение применения декоратора; на независимом `@app.get("/status")` и `def status():` разобрать скобки, строковый path, связь с функцией и вызов по запросу. Не вставлять готовый код `/health`.
- Наглядная опора 2: небольшая таблица соответствий `метод + path → функция` для службы уведомлений (например, `GET /status`). Предел: запись в таблице не исполняет функцию заранее; реальный HTTP-запрос проходит через работающий Uvicorn.
- Пример и типичная путаница: два разных метода на одном path обозначают разные операции; декоратор описывает регистрацию, но не запускает Uvicorn.
- Первое самостоятельное действие: из двух пар `GET /status` и `POST /status` ученик выбирает, какая совпадает с показанной регистрацией, и объясняет выбор; затем самостоятельно называет тройку «метод, path, обработчик» для будущего health без получения готового решения.
- Опора для повторного обращения: восстановить порядок «метод + path → зарегистрированный обработчик → результат»; проверить, что функция не выполняется только из-за импорта.
- Переход к следующему шагу: обработчик должен вернуть результат, который FastAPI отправит клиенту.

## 03. Возвращаемое значение становится HTTP-ответом

- Что и зачем объяснить: handler возвращает структурированное значение; FastAPI сериализует словарь в JSON и формирует успешный HTTP-ответ со статусом 200 по умолчанию.
- Механизм и порядок: на независимом обработчике статуса сравнить `print("ready")` с `return {"state": "ready"}`. Показать последовательность `return` словаря → преобразование FastAPI в JSON body → стандартный статус 200; отдельно объяснить, что `200` не является полем возвращённого словаря. Health сообщает, что запрос дошёл до обработчика, но не проверяет JSON-файл, сервис или будущие операции.
- Пример и типичная путаница: для независимого status-маршрута сопоставить словарь ответа и отображаемый JSON; не приравнивать 200 к доказательству работы всего Planner.
- Первое самостоятельное действие: ученик предсказывает, появится ли `ready` в JSON body при `print` и при `return`, и отдельно указывает ожидаемый 200; сверяет с разбором ответа другого сервиса. Визуал: рядом Python-значение, JSON body и строка HTTP-статуса, без подсказки к итоговому `/health`.
- Опора для повторного обращения: при проверке развести три наблюдения — HTTP-статус, JSON-тело и фактический scope health.
- Переход к следующему шагу: чтобы проверить результат, нужны установленные зависимости в том же Python-окружении, где работает проект.

## 04. Зависимости устанавливаются в окружение проекта

- Что и зачем объяснить: FastAPI и Uvicorn добавляются как runtime-зависимости существующего проекта; requirements.txt фиксирует набор для повторного запуска. Предыдущие зависимости сохраняются.
- Механизм и порядок: сначала подтвердить выбранный интерпретатор и корень проекта; затем объяснить `python -m pip install -r requirements.txt` и `python -m pip show fastapi uvicorn`, смысл `-m`, `-r`, имён пакетов и установки в конкретный Python. Показать, что в новом runtime-списке сохраняются уже имеющиеся зависимости; точные версии подтверждаются восстановленным паспортом до выдачи, соседние пакеты автоматически не обновляются.
- Пример и типичная путаница: установка через системный pip может попасть в другой Python, чем команда запуска сервера; поэтому install и run обращаются к выбранному python.
- Первое самостоятельное действие: ученик сравнивает два обозначенных пути к Python и выбирает, каким выполнит install и run, чтобы использовать одно окружение; затем на учебном списке зависимостей определяет, что сохранить, а что добавить. Локальная проверка — вывод `pip show` относится к выбранному Python. Визуал: схема «один interpreter → install → uvicorn» с перечёркнутой установкой в чужое окружение.
- Опора для повторного обращения: перед запуском сверить корень проекта, выбранный python и наличие обоих пакетов в его окружении.
- Переход к следующему шагу: установленный серверу пакет нужен для импорта модуля приложения и запуска объекта по его адресу.

## 05. Uvicorn загружает модуль и запускает объект приложения

- Что и зачем объяснить: строка app.api:app состоит из пути к Python-модулю и имени объекта FastAPI. Команду запускают из корня, чтобы импорт app.api нашёл пакет проекта.
- Механизм и порядок: разобрать `python -m uvicorn app.api:app --reload --host 127.0.0.1 --port 8000`, включая выбранный Python, рабочую папку, модуль до двоеточия, объект после него, host/port и `--reload` как режим разработки. Учебный пример с модулем уведомлений использует другое имя, чем `app.api:app`; ASGI обозначить как интерфейс передачи request/response, без async и внутреннего протокола.
- Пример и типичная путаница: `app.api` — модуль, второй `app` — объект; URL `/health` не является путём к файлу. Uvicorn занимает запущенный терминал, пишет там журнал и останавливается через Ctrl+C; `--reload` может создавать процесс перезагрузки. Отсутствие сервера не порождает HTTP-статус, но диагностика 404/405 остаётся в 47.1.
- Первое самостоятельное действие: ученик из команды выделяет модуль, объект, рабочий каталог и адрес `http://127.0.0.1:8000/`; определяет порядок «запуск → запрос → ответ → Ctrl+C». Различающий случай: если запустить из чужой рабочей папки, импорт `app.api` может не разрешиться. Визуал: последовательность четырёх наблюдаемых состояний с отметкой, что порт 8000 — выбранный пример, фактический порт проверки должен совпадать с командой.
- Опора для повторного обращения: если запрос не отвечает, проверить, что сервер запущен из корня и на ожидаемом порту; различие HTTP-ошибок маршрута изучается в 47.1.
- Переход к следующему шагу: можно создать реальный health-маршрут и проверить, что новый web-вход не заменил CLI.

1. **Подготовить зависимости → получить воспроизводимую среду.** **Вход:** проверенный корень Planner, выбранный Python и существующие списки зависимостей. **Объект:** корневой runtime `requirements.txt` и команда запуска в `README.md`; `requirements-dev.txt` и имеющиеся пакеты не удаляем. **Опора:** раздел 04 (окружение, `python -m pip`, версии) и прежний проверенный запуск CLI. **Самостоятельно:** ученик определяет, нужен новый runtime-файл или дополнение существующего; записывает FastAPI/Uvicorn с согласованными точными версиями, устанавливает зависимости через тот же Python и описывает команду будущего запуска. **Локальный результат:** `python -m pip show fastapi uvicorn` показывает обе библиотеки и требуемые версии до создания приложения; прежний список зависимостей сохранён. **Различающий случай:** если runtime-файл уже существует, его дополняют, а не заменяют; установка в другой интерпретатор не подтверждает готовность выбранного окружения.
2. **Создать HTTP-вход → получить импортируемый модуль без запуска CLI.** **Вход:** результат шага 1, наличие пакета `app/`, подтверждённое отсутствие нового API в исходной учебной копии. **Объект:** один `app/api.py`; `app/main.py` и сервис не трогаем. **Опора:** разделы 01–03 (объект FastAPI, форма `@app.get`, функция-обработчик, `return` словаря) и знакомые импорты/функции. **Самостоятельно:** ученик пишет создание объекта приложения, регистрацию **только** `GET /health` и возврат статуса `ok`; готовую целевую конструкцию в starter не выдавать, можно предоставить имена файлов и договор ответа. **Локальный результат:** запуск `python -m app.api` из корня завершается без ошибок и без меню CLI или открытия порта; исходник содержит ровно один написанный учеником health-обработчик. **Различающий случай:** `print` внутри обработчика не заменяет `return` HTTP-тела; точную JSON-выдачу проверим следующим шагом.
3. **Запустить сервер → наблюдать ответ health и штатную остановку.** **Вход:** импортируемый `app/api.py` и установленный Uvicorn; порт выбираем явно (для учебного примера — `127.0.0.1:8000`). **Объект:** процесс Uvicorn и запрос браузера к `/health`; JSON Planner не используется. **Опора:** разделы 03 и 05 (ответ, команда `модуль:объект`, адрес, Ctrl+C). **Самостоятельно:** ученик составляет и выполняет команду запуска через **тот же Python** с указанием `app.api:app`, затем открывает полный адрес health и останавливает процесс. **Локальный результат:** пока сервер работает, браузер получает HTTP 200 с JSON `{"status":"ok"}`, а терминал показывает обработанный GET; Ctrl+C завершает сервер. **Различающий случай:** создание объекта в шаге 2 не открывало порт; здесь он становится доступен только при работающем процессе. Объяснение 404/405 и тесты неизвестных путей оставляем 47.1.
4. **Вернуться к CLI → подтвердить сохранение прежнего входа.** **Вход:** сервер после Ctrl+C остановлен, исходные `app/main.py` и данные Planner оставались нетронутыми. **Объект:** прежняя команда CLI из README/проверенного снимка, команды чтения списка и выхода. **Опора:** точка A и раздел 01 (CLI и HTTP — разные входы в один проект). **Самостоятельно:** ученик запускает CLI привычным способом, выполняет только чтение и выход, сравнивает поведение со стартовым состоянием без создания или редактирования задач. **Локальный результат:** меню CLI доступно, команда чтения показывает прежние задачи **либо корректный пустой список** (в зависимости от входных данных), выход завершает процесс, пользовательский JSON не изменён. **Различающий случай:** запуск FastAPI не должен требовать изменения `app/main.py` или перевода CLI на HTTP; остановка Uvicorn не мешает самостоятельному запуску CLI.

Действия образуют учебную связку **«зависимости → импортируемый HTTP-вход → живой ответ → сохранённый CLI»**. При подготовке MAIN оформить этот список второй `LinkedNotes variant="connected"` с пояснением после группы. Для любой ошибки ученик возвращается к соответствующему разделу 04, 01–03 или 05, исправляет свой шаг и повторяет **его** локальную проверку, не получая готовую реализацию `/health`. На переходе от шага 2 к шагу 3 отдельно объяснить, почему импорт успешен, но HTTP-ответ появляется лишь после запуска сервера.

**Итоговый критерий всей практики:** через один выбранный Python воспроизводятся установка и команда запуска из README; `GET /health` возвращает HTTP 200 и **объект JSON** с полем `status` равным строке `ok` (не обычный `print`, не текст вне JSON); Uvicorn корректно останавливается; старый CLI выполняет чтение и выход без изменения данных. Порядок полей JSON здесь не задан и проверке не нужен. Health не доказывает исправность JSON-хранилища или готовность операций Planner.

**Для проекта и передачи 47.1:** по проектному маршруту добавлены только отдельный HTTP-вход, runtime-зависимости и воспроизводимая команда; `app/main.py`, PlannerService, модель, JsonStorage и пользовательский JSON остаются прежними. Занятие 47.1 проверит уже готовый `/health` в Swagger/Postman Local и объяснит HTTP 404/405; занятие 48 впервые подключит данные Planner. Никаких готовых `/tasks` или `/stats` в стартовом коде 47 нет.
