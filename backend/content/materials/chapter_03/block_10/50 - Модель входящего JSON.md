## Точка B: результат занятия

- **Объясняет:** клиент посылает только `title` и `priority`; `Task` дополнительно содержит серверные `id`, `is_done` и внутренние `tags`. Понимает, как Pydantic строит объект, почему оба поля обязательны и где заканчивается проверка типов.
- **Самостоятельно делает:** объявляет в существующем `app/api.py` `TaskCreate(BaseModel)` с `title: str`, `priority: int` без defaults; проверяет модель прямым вызовом из `.venv` на валидном JSON, пропущенном поле и неверном типе. Умеет указать поле и причину ошибки.
- **Состояние проекта:** один пригодный класс `TaskCreate`; старые GET/CLI/service/storage/JSON работают по-прежнему, POST не регистрируется. Создание экземпляра модели **не создаёт** `Task`.
- **Наблюдение:** JSON с двумя корректными значениями даёт экземпляр с доступными атрибутами; отсутствие `priority` и `"priority":"много"` приводят к `ValidationError`, до handler и `add_task`. Преобразуемая строка `"4"` становится `int`; аннотация `int` сама по себе не гарантирует диапазон приоритета 1–5.

## 00. Вступление

После `49.1` клиент умеет **запрашивать** задачи, но пока не создавать их через API. Для будущего создания нужны данные от клиента; они составляют только часть внутренней `Task`. Перед POST научимся отличать эти данные и проверять их отдельно от записи.

1. **Точка старта:** запланированы знание JSON-body из `46.1`, `Task` из главы 2 и работающие GET после `49.1`; фактическую готовность проверяем перед занятием.
2. **Новый вопрос:** как принять только `title` и `priority` и заранее обнаружить неправильный тип/пропущенное поле?
3. **Результат:** самостоятельно созданная `TaskCreate` и три проверенных исхода: корректный объект, обязательное поле отсутствует, тип неподходящий.

Знакомая запись задачи нужна, чтобы понять, **каких** полей нет у клиента. После этого на отдельном примере объясняем механизм Pydantic, самостоятельно записываем схему Planner и проверяем её на разных входах. Сохранение в JSON будет отдельным, следующим действием в `50.1`.

## 01. Данные клиента и внутренняя задача

- **Зачем:** пользователь будущего API указывает название и важность, но не должен назначать номер задачи или пометку выполнения. Вернуться только к нужным полям `Task` из главы 2: `id/title/priority/is_done`, внутренним `tags` и операции `add_task`.
- **Механизм:** сопоставить короткий JSON клиента (`title`, `priority`) и внутреннюю `Task` с `id`, `is_done` и `tags`. Клиент задаёт два значения; остальное появится позже через сервис. JSON-body сам по себе не сохраняет запись.
- **Наглядная опора №1:** анкета на новую задачу и готовая запись с номером в учёте. Аналогия описывает роли полей, но не требует создавать новый storage.
- **Первая самостоятельная попытка:** из пяти перечисленных полей ученик выбирает два клиентских и объясняет, почему клиентский `id` не должен стать серверным. Результат: граница входных данных понятна до первого Pydantic-кода.
- **Опора на возврат:** схема «JSON клиента → входная схема → [позже] сервис → внутренняя Task». Последние шаги сейчас не выполняются.

## 02. Как `BaseModel` создаёт объект

- **Зачем:** Python-аннотация `count: int` внутри простого класса сама по себе не проверяет данные. `pydantic.BaseModel` использует объявленные поля для разбора входа **при создании экземпляра**.
- **Порядок:** повторить `class`, наследование, импорт `from pydantic import BaseModel`; разобрать **независимую** модель `Review(BaseModel)` с `message: str` и `stars: int`. Показать объявленные поля, создание из словаря, чтение `review.message` и `review.stars`. Объяснить, что `:` указывает тип, а отсутствие `=` означает, что поле нужно передать.
- **Наглядная опора №2:** проверка анкеты до передачи сотруднику. Граница аналогии: Pydantic проверяет форму и типы, но сам не записывает объект и не знает предметных правил Planner без дополнительных проверок.
- **Различающий случай:** при обычном классе аннотация не создаёт автоматическую проверку, у `BaseModel` отсутствие обязательного поля вызывает ошибку. Не подменять первую механику новой темой `dataclass`, `Field` или validators.
- **Первая проба:** ученик сам предсказывает оба атрибута при корректных значениях `Review`, создаёт объект и проверяет прогноз. Опора для возврата: «объявление поля → значение при создании → атрибут объекта».
- **Переход:** механизм проверен вне Planner; теперь применить его к настоящим двум входным полям.

## 03. Самостоятельное объявление `TaskCreate`

- **Зачем:** клиент передаёт `title` как строку и `priority` как целое число; ни одному полю не задан default. Поля `id`, `is_done` и `tags` относятся к внутренней `Task`.
- **Порядок:** найти реальный `app/api.py` рядом с уже работающими GET → удостовериться, что используется проектная `.venv` с Pydantic → добавить импорт `BaseModel` → самостоятельно объявить `TaskCreate` с двумя обязательными аннотациями. Разграничить объявление класса и создание экземпляра; никакой handler здесь не создаётся.
- **Путаница:** демонстрационная `Review` не должна превращаться в готовый код итоговой `TaskCreate`. Не копировать всю `Task` и не добавлять `POST`, `response_model` или новую систему хранения. Если точная схема уже существует в ученическом checkout, сверить её и оставить один класс.
- **Самостоятельное действие:** ученик записывает класс в редакторе, проверяет импорт модуля и называет обязательность каждого поля. **Локальный результат:** класс доступен из `app/api.py`, маршрутная таблица не меняется; при ошибке импорта вернуться к месту модуля и `.venv`.
- **Опора:** независимая `Review` из 02 и правило «поле без default обязательно». Далее проверим фактические значения.

## 04. Что Pydantic делает с JSON-числом

- **Зачем:** в JSON `"priority": 4` — число, а `"priority": "4"` — строка. В обычном режиме Pydantic может разобрать числовую строку как `int`; не каждую строку.
- **Механизм:** сначала сравнить JSON-текст и Python-словарь. Для текста показать `TaskCreate.model_validate_json(...)`, для словаря — `TaskCreate.model_validate(...)` или создание с именованными аргументами. Оба пути получают объект `TaskCreate`; формат входа различается. Объяснить синтаксис метода перед первой самостоятельной попыткой.
- **Самостоятельное действие:** ученик передаёт корректный JSON, затем меняет `priority` с числа `4` на строку `"4"`; до запуска прогнозирует тип поля, после сравнивает `type(model.priority)`. Оба корректных случая дают `int`.
- **Контрпримеры:** строка `"много"` не преобразуется в целое; `99` проходит текущую **проверку типа**, хотя позже будет недопустимо по предметным правилам. Здесь не добавляем `Field` или диапазон 1–5.
- **Учебный визуал:** таблица «JSON-значение → итоговый тип/ошибка → причина», различающая `4`, `"4"`, `"много"`. Вывод: форма и доменная допустимость — разные проверки.

## 05. Ошибка модели до вызова сервиса

- **Зачем:** если поле отсутствует или не может стать объявленным типом, Pydantic не создаёт экземпляр. В интерпретаторе появляется `ValidationError`, а не HTTP `422`; последний появится при подключении модели к FastAPI в `50.1`.
- **Механизм:** на независимой `Review` показать пропуск `stars`, затем сравнить два ошибочных входа для `TaskCreate`: JSON без `priority` (обязательное поле не передано) и JSON с `"priority": "много"` (значение невозможно разобрать как `int`). У ошибки выделять имя поля и причину; точный англоязычный текст может отличаться между версиями. Дополнительное сравнение `"title": 123` в Pydantic 2 показывает отказ типа `str`.
- **Самостоятельное действие:** ученик до каждого запуска говорит, какое поле вызовет отказ, затем видит `ValidationError` и называет его причину; меняет только неверное поле и повторяет успешное создание. При необходимости показать `errors()` и `loc`, но не требовать нового универсального `try/except`.
- **Опора:** схема «вход → объект либо ошибка с полем»; `add_task` и JSON-файл не вызываются. Вывод: готовы три обязательные проверки модели до работы с POST.

## 06. Что мы будем делать в практике

**Обязательный формат:** ученик **сам пишет код** в редакторе существующего Planner (`app/api.py`) и **сам исследует результат** в интерпретаторе активированной проектной `.venv`. Это ручная проектная практика без платформенной `solve/script`-задачи. **Вход:** подтверждены занятия `46.1` (JSON string/number), глава 2 (`Task`, `add_task`), `47–49.1` (текущий API с GET). Отдельно проверить их реальную выдачу и используемую копию проекта; старый или более новый checkout не считать автоматически целевой точкой.

**Цель:** одна входная `TaskCreate` с обязательными `title: str` и `priority: int`; ученик сам может создать экземпляр из JSON, отличить допустимый тип от невозможного и объяснить, почему ошибки возникают до любой записи. Подготовлены блоки 01–05; учебная `Review` использована только как независимый пример, готового определения `TaskCreate` в пояснениях нет.

1. **Подготовить место для схемы и назвать поля.** Вход: существующий `app/api.py` с GET, известная `Task` из главы 2 и два поля клиентского JSON. Объект: публичный запрос на создание, пока без handler. Опора: разделы 01–02; до начала ученик распределяет поля `title`, `priority`, `id`, `is_done`, `tags` между клиентом и сервером. **Сам:** открывает реальный модуль, проверяет доступность `pydantic` в проектной `.venv`, сам выбирает две аннотации и записывает `TaskCreate(BaseModel)` без defaults. **Результат:** класс импортируется и содержит только объявленные клиентские поля, прежние маршруты не затронуты. Различающий случай: попытка включить `id` в обязательный вход обнаруживается сравнением с полями внутренней `Task`, а не одобряется как третье поле.

2. **Получить экземпляр из JSON.** Вход: JSON-текст `{"title":"Купить билет","priority":3}`; объект: написанная в шаге 1 `TaskCreate`. Опора: разделы 02–04, объяснение отличия текста JSON от Python-словаря. **Сам:** в интерпретаторе импортирует реальную `TaskCreate`, предсказывает, что получится, применяет разобранный `model_validate_json` и читает два атрибута. **Результат:** объект с заданными `title` и целочисленным `priority`; `Task` не создаётся, вызова `add_task` нет. Различающий случай: не принимать сам исходный JSON-текст за экземпляр Python с атрибутами.

3. **Проверить обычное преобразование типа.** Вход: тот же JSON, но `priority` теперь строка `"3"`. Объект: та же модель, без изменений кода схемы. Опора: блок 04. **Сам:** до выполнения предсказывает итоговый тип, подаёт изменённый JSON, проверяет значение и `type(model.priority)`; для проверки границы смысла отдельно объясняет, почему целое `99` само по себе не проверяет доменный диапазон 1–5. **Результат:** строка с числом преобразуется в `int`, а предметная проверка ещё не выполнялась. Если ученик решает, что любой текст допустим, вернуться к таблице из 04.

4. **Разобрать два разных отказа.** Входы: `{"title":"Купить билет"}` без `priority` и `{"title":"Купить билет","priority":"высокий"}`. Объект: `TaskCreate` из первого шага; опора: блок 05 и статус обязательности из 03. **Сам:** перед каждым вызовом называет поле и ожидаемую причину отказа, запускает в интерпретаторе, по `ValidationError` показывает, где именно ошибка, затем самостоятельно исправляет **только** проблемное поле и повторяет успешное создание. **Результат:** отличает «отсутствует поле» от «нельзя разобрать тип», ни один отказ не вызывает handler или service; не называет локальный `ValidationError` HTTP-ответом `422`. Если среда прекращает выполнение на исключении, новую попытку запускает отдельно; универсальный перехват исключений писать не нужно.

5. **Проверить сохранность прежнего поведения и сформулировать передачу.** Вход: прежние данные Planner и работающий GET, проверенный до занятия. Объект: `app/api.py` после добавления класса. Опора: входная проверка `49.1` и схема из 01. **Сам:** убеждается, что ранее доступный health/GET по-прежнему возвращает данные, а список/JSON и прежний CLI не изменились; объясняет вслух путь «текст JSON → экземпляр входной модели» и место будущего вызова `add_task`. **Результат:** один подготовленный класс, без нового `POST /tasks`, без записей в хранилище и без потери чтения. Если API на входе ещё не работал, сначала восстановить запланированную A; неисправный исходный GET не считать дефектом `TaskCreate`.

Связь шагов: сначала ученик **выбирает** клиентские поля, затем **пишет** модель, **наблюдает** создание и преобразование, **диагностирует** два отказа и **сверяет** сохранность проекта. При ошибке возвращается к конкретному разделу 01 (роли полей), 02–03 (тип/обязательность), 04 (преобразование) или 05 (причина отказа). **Итоговый критерий B:** ученик без готового образца определяет `TaskCreate` и получает три различающихся исхода: валидный объект, ошибка пропуска поля и ошибка неправильного типа; старый JSON не меняется.

**Дополнительный перенос (не обязательное условие для `50.1`):** изменить у валидного JSON только `title` и объяснить, почему новый экземпляр имеет другое название, но сама база Planner по-прежнему не изменилась. В `50.1` подготовленную схему подключат к `POST /tasks` и существующему `add_task`; это отдельная будущая практика со статусом `201` и сохранением.
