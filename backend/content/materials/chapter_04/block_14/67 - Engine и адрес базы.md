## 00. Вступление

В Planner уже есть сохранение данных после перезапуска: сервис использует JSON-файл. Предыдущее исследование должно было показать, как SQLite выполняет простой SQL. Теперь задача уже: научиться предсказуемо подключаться к SQLite из существующего приложения, прежде чем описывать в ней таблицу.

1. **Точка старта:** настройки приложения собираются один раз, а API и CLI используют один JSON-файл.
2. **Новый вопрос:** как приложению выбрать нужный файл SQLite и получить безопасно ограниченное соединение с ним?
3. **Результат:** отдельный Engine и проверенное соединение готовы для будущей ORM-схемы, а рабочий Planner ещё остаётся на JSON.

Сначала различим адрес, Engine и Connection, затем добавим адрес в уже знакомую систему настроек. После этого проверим путь и выполним короткий запрос на изолированной базе. Такой результат готовит следующий урок, но не притворяется уже работающим DB-хранилищем.

## 01. SQLAlchemy как инструмент подключения

- Что и зачем объяснить: SQLAlchemy предоставляет Core для работы с соединениями и ORM для отображения объектов на таблицы. В этом уроке нужен только Core-уровень; ORM не является обязательным способом выполнить каждый SQL-запрос.
- Механизм и порядок: Engine хранит правила подключения и управляет получением соединений; сам по себе не является открытой сессией с данными и не означает, что таблицы уже созданы. Connection представляет конкретную область взаимодействия с базой.
- Пример и типичная путаница: сравнить Engine с повторно используемой фабрикой/диспетчером подключений и Connection с временно занятым ресурсом. Не называть Engine соединением, Session или таблицей.
- Переход к следующему шагу: чтобы Engine открыл нужный файл, приложению нужен однозначный адрес SQLite.

## 02. URL базы и путь к файлу

- Что и зачем объяснить: SQLAlchemy URL — адрес подключения с диалектом/драйвером и местом базы; это не то же самое, что объект `Path` и не обычный путь, переданный сам по себе.
- Механизм и порядок: разобрать файловую SQLite-базу и относительный против абсолютного пути. Относительный адрес без опоры на корень может разрешиться от текущей рабочей папки процесса; смена `cwd` тогда создаст впечатление второй пустой базы. Зафиксировать корневую точку проекта и безопасное построение URL для Windows.
- Пример и типичная путаница: один и тот же настроенный путь при запуске из корня проекта и другой папки. Не подменять файл базы `:memory:` и не исправлять путь добавлением слешей наугад.
- Переход к следующему шагу: адрес следует хранить в общей конфигурации рядом с существующими настройками.

## 03. Расширение Settings без смены приложения

- Что и зачем объяснить: существующий `Settings` уже объединяет проверенные значения; новое поле добавляется в тот же механизм, а не читается заново каждым handler.
- Механизм и порядок: `DATABASE_URL` поступает из среды с прежним приоритетом над `.env`; при отсутствии используется заранее определённый SQLite default, привязанный к корню проекта. Пустое или неподдерживаемое значение должно давать ясную ошибку вместо незаметного возврата к другой базе. Существующие `JSON_PATH`, `APP_NAME` и `COOKIE_SECURE` сохраняют смысл.
- Пример и типичная путаница: отдельный адрес можно передать тестовой конфигурации; новая настройка не становится переключателем хранения. Не записывать секреты и не печатать целиком окружение.
- Переход к следующему шагу: готовый адрес можно передать фабрике Engine, не связывая её с HTTP или глобальной конфигурацией.

## 04. Engine и короткая область Connection

- Что и зачем объяснить: `create_engine` создаёт настраиваемый Engine для работы с выбранным URL; явная фабрика позволяет подставить изолированный адрес в проверке.
- Механизм и порядок: создание Engine само по себе не выполняет подключение или DDL; подключение возникает при запросе Connection. Connection ограничивается контекстом одной операции и освобождается при выходе, в том числе при исключении. Engine может переиспользоваться, отдельный Connection — нет.
- Пример и типичная путаница: наметить поток Settings → фабрика Engine → контекст Connection. Не создавать глобальное открытое соединение; не делать таблицу и не путать закрытие соединения с commit/rollback Session.
- Переход к следующему шагу: жизненный цикл можно проверить самым коротким запросом, не создавая схему Planner.

## 05. Проверка подключения простым SQL

- Что и зачем объяснить: `SELECT 1` проверяет, что SQLAlchemy выполнил команду через выбранное соединение и вернул скалярный результат; он не проверяет наличие таблиц, ORM или готовность приложения к CRUD.
- Механизм и порядок: запрос выполняется внутри открытого Connection через актуальный SQLAlchemy Core-интерфейс; строковое SQL-выражение оформляется как текстовая SQL-команда. Результат читается и проверяется до выхода из контекста, после чего ресурс закрывается.
- Пример и типичная путаница: использовать `SELECT 1` как smoke check на отдельном адресе. Не заявлять, что по нему создана таблица, проверена запись задачи или доказано подключение API к SQLite.
- Переход к следующему шагу: после успешного smoke check нужно подтвердить изоляцию теста и сохранение прежнего JSON-пути.

## 06. Граница нового компонента и прежнего Planner

- Что и зачем объяснить: инфраструктура может появиться раньше, чем приложение начнёт её использовать для предметных операций. Этот порядок позволяет проверять адрес отдельно и не создавать два источника данных.
- Механизм и порядок: `app/DBase/engine.py` получает адрес явно; Settings остаётся общей конфигурацией. Тестовая база находится в отдельном временном пути. Ни API, ни CLI не получают новую зависимость от Engine на этом шаге.
- Пример и типичная путаница: показать, что обычный GET/POST по-прежнему обслуживается прежним сервисом с JSON, тогда как проверка Engine использует только свой тестовый адрес. Не добавлять fallback между базами.
- Переход к практике: все новые действия ограничены настройкой подключения и его проверкой; предметная схема остаётся задачей следующего занятия.

## 07. Что мы будем делать в практике

**Формат и исходная опора:** проектное изменение существующего StudyHub после занятия 65.2; используем знакомые Python-модули, `.venv`, `requirements.txt`, проверенный Settings и корень проекта. Минимальный SQL из 79 считаем планируемой опорой и при необходимости кратко восстанавливаем до действия.

Подготовим подключение SQLite для будущей работы, не переводя действующие API и CLI на новую базу.

1. **Добавить SQLAlchemy и адрес базы в конфигурацию:** сохранить прежние настройки, добавить DATABASE_URL с устойчивым default, дополнить `.env.example` и проверить приоритет среды, тестовый адрес и отказ на пустом значении; опора — блоки 01–03 и прежний навык настройки среды.
2. **Создать фабрику Engine:** добавить `app/DBase/engine.py`, принимающий URL явно, и собирать Engine из настроек без открытия глобального Connection; опора — блоки 01, 02 и 04.
3. **Проверить соединение отдельно от Planner:** на файловой SQLite в `tmp_path` открыть Connection, выполнить `SELECT 1`, проверить результат и освобождение ресурса; опора — блоки 04–05 и минимальный SQL из 79.
4. **Проверить воспроизводимость и сохранение прежнего пути:** вызвать проверку из другой рабочей папки и подтвердить тот же default-путь; запустить узкие прежние проверки Settings и JSON-сборки, убедиться, что API/CLI не переключились и рабочий JSON не затронут; опора — блоки 02–03 и 06.

Объяснение Engine/Connection подготавливает фабрику и ограниченную область ресурса; знакомые Settings подготавливают добавление DATABASE_URL; новый блок про текстовый SQL подготавливает smoke check. Проверки используют временную файловую базу, а не создают второе постоянное хранилище. На выходе прежние JSON-операции сохраняют поведение; таблица и Session ещё не созданы.
