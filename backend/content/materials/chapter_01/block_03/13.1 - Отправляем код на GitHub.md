## Место в маршруте

Урок продолжает локальную историю занятий **12.1 → 13**: собственный пустой GitHub-репозиторий и его clone, запускаемый `main.py`, `.gitignore`, затем первый локальный commit. Эти результаты **запланированы**, но не подтверждены фактической практикой ученика. После проверки входа ученик публикует **тот же commit в `main`** и находит его на GitHub. Не создавать второй репозиторий или новый локальный commit: предмет этого шага — безопасно выбрать направление отправки, выполнить push и независимо проверить результат.

Результат становится входом занятия 13.2: в опубликованный Hello world-проект добавится normalize_title, а различие рабочей и подготовленной правки будет изучаться на реальном файле.

## Точка A: планируемая опора, не подтверждённая прохождением

- **Планируется в 12.1:** ученик сам создаёт один пустой собственный GitHub-репозиторий, клонирует его, добавляет запускаемый `main.py` с Hello world и `.gitignore` для `__pycache__/` и `*.pyc`, проверяет путь проекта и `origin`. Перед уроком 13.1 проверить наличие проекта, адрес `origin` и два файла; наличие плана 12.1 не доказывает выполнения.
- **Планируется в 13:** ученик проверяет содержимое staging, создаёт **первый локальный commit** двух файлов, умеет посмотреть его ID, автора и текущую ветку. Перед 13.1 проверить `HEAD` и состав commit; существующий commit без проверки состава не подтверждает пригодность входа.
- **Не проверено:** прохождение 12.1–13 конкретным учеником и состояние его локального StudyHub в новой последовательности. Исторический журнал и репозиторий автора курса не подтверждают личный результат. Если нет собственного clone/нужного commit, проектный push откладывается до завершения соответствующего шага 12.1 или 13; теоретические сравнения можно выполнить без отправки.

## Точка B: результат занятия

- Ученик сможет объяснить: чем публикация commit отличается от сохранения файла и локального commit; что означают remote origin, текущая ветка и upstream; почему подпись автора, GitHub-учётная запись и право записи — разные вещи.
- Ученик сможет сделать: проверить свой remote и фактическую локальную ветку; при необходимости безопасно переименовать **неопубликованную** ветку в `main`; выполнить первый `git push -u origin main` через штатную авторизацию; подтвердить серверный результат.
- Результат в проекте: существующий локальный commit опубликован в **`origin/main`** собственного удалённого репозитория; `main.py` и `.gitignore` не меняются и новый commit не создаётся.
- Как подтвердим: **полный** ID commit в удалённой `main` совпадает с локальным `HEAD`, а серверные `main.py` и `.gitignore` содержат ожидаемую версию. Одного успешного сообщения push, чистого `git status` или совпадения коротких ID недостаточно.

## Границы и передача дальше

- Пока не требуем: повторно создавать репозиторий или clone, выполнять `git init`, менять файлы проекта, создавать второй commit, добавлять `normalize_title`, вводить `develop`/PR, клонировать опубликованный проект заново или чинить историю через force push. Если `main` уже существует с другой историей или удалённый репозиторий неожиданно непустой, остановиться и выяснить причину без переименования с перезаписью и без `--force`.

## 00. Вступление

Ожидаемая точка A — рабочий файл и первый локальный commit в собственном clone. До проектной части ученик проверяет эту опору. Затем разбирается, почему локальная история ещё не видна на GitHub, как безопасно привести неопубликованную учебную ветку к `main` и как проверить фактическую публикацию.

1. **Точка старта:** ожидаемая опора занятий 12.1–13 — локальный commit с main.py и .gitignore, адрес origin и фактическая ветка; реальное состояние проверяется в начале занятия.
2. **Новый вопрос:** как передать именно эту версию в `origin/main` и различить готовый локальный commit, вход в аккаунт и разрешение записи?
3. **Результат:** ученик публикует текущий commit в `main` своего GitHub-репозитория и подтверждает его по серверной истории и файлам.

Весь маршрут использует один clone и один remote. Сначала отличаем три состояния сохранения, проверяем адрес/ветку/commit, при необходимости объясняем безопасное переименование ещё не опубликованной ветки, затем разбираем направление push и авторизацию. После отправки независимо сверяем серверный commit. **Для будущей MAIN-подачи:** между двумя читаемыми абзацами и следующими используемыми абзацами включать осмысленную схему, сравнение или короткое предсказание; не вставлять подряд похожие карточки ради ритма.

## 01. Сохранённый файл, локальный commit и серверная копия

- Что и зачем объяснить: показать три разных состояния — изменения в файле, сохранённый локально commit и опубликованная серверная копия. Начать с безопасного примера, затем вернуться к main.py, если наличие clone подтверждено: запись файла не создаёт commit, commit сам по себе не меняет GitHub.
- Механизм и порядок: Git хранит локальную историю, GitHub хранит удалённую копию этой истории; push передаёт уже созданные commits. Незакоммиченные строки не становятся частью отправки автоматически. Не повторять весь урок про stage и commit — восстановить только различие, нужное для вопроса «что именно отправляется?».
- Пример и типичная путаница: на схеме «диск → локальный commit → удалённая `main`» показать два различных снимка: в первом есть изменённая, но незакоммиченная строка `print`, во втором — уже существующий commit с `Hello world`. При push уйдёт содержимое **commit**, а новая строка останется локальной; чистый `git status` сам по себе не доказывает публикацию.
- Первое самостоятельное действие: дать два других состояния (есть только сохранённый файл; есть commit, но remote ещё пустой) и попросить указать, какое звено отсутствует и что окажется на GitHub при push. Результат — объясняет выбор без заучивания команд.
- Опора для повторного обращения: три состояния и вопрос к каждому — «файл сохранён?», «commit создан?», «серверная версия проверена?». Если push ещё не выполнялся, не делать вывод о публикации по локальному логу.
- Форма MAIN: **одна** схема с прогнозом о составе отправки; не дублировать её отдельным True/False с тем же смыслом.
- Переход: чтобы передать нужный commit, сначала точно определить удалённый адрес, HEAD и исходную ветку.

## 02. Проверяем origin и фактическую ветку

- Что и зачем объяснить: перед первой отправкой убедиться, что команды относятся к clone ученика и адресу его собственного пустого репозитория, созданного в занятии 12.1.
- Механизм и порядок: `origin` — локальное короткое имя для адреса удалённого репозитория, а `main` — имя ветки, то есть линии commits. Сначала объяснить смысл каждой команды, **после этого** дать наблюдения в собственном clone: `git rev-parse --show-toplevel` (корень текущего репозитория), `git remote -v` (адреса fetch/push у `origin`), `git branch --show-current` (фактическая текущая ветка), `git log -1 --format=%H` (полный ID локального `HEAD`), `git status --short` (есть ли неожиданные изменения). Адрес сверить со страницей **своего** пустого GitHub-репозитория; проверить первый commit с `main.py` и `.gitignore` средствами, изученными в 13.
- Различающий пример: `origin` указывает на свой репозиторий, но ветка называется `master`; и другой случай — ветка `main`, но URL `origin` принадлежит чужому проекту. В первом случае учимся безопасно привести имя к учебному `main`; во втором **не отправляем** и возвращаемся к настройке `origin` из 12.1. Совпадение слова `origin` в выводе обоих примеров не делает адреса одинаковыми.
- Переименование объяснить **до команды**: `git branch -m main` меняет имя *текущей локальной ветки*, а не содержимое commit. Оно допустимо здесь только если текущая ветка ещё не опубликована, `main` локально не занята другой веткой и удалённый учебный репозиторий всё ещё пуст. Если уже `main` — не переименовывать; если существует другая `main`, есть чужая история либо ветка опубликована — остановиться для адресной проверки без `-M`, force push или перезаписи. Повторно вывести `git branch --show-current`; ожидается `main`.
- Первое самостоятельное действие: на паре готовых выводов ученик указывает «можно переименовать» или «остановиться», называет проверку, затем читает собственные значения. Критерий — называет **свой URL, полный HEAD и локальную `main`**, а не переносит их из примера.
- Форма MAIN: один подписанный фрагмент терминала + сравнение двух случаев с решением; не две одинаковые викторины.
- Переход: источник `main` и адрес `origin` подтверждены; теперь связать их явной командой публикации.

## 03. Первый push и upstream

- Что и зачем объяснить: дать смысл явному направлению первой публикации, прежде чем ученик запускает push.
- Механизм и порядок: `git push -u origin main` берёт commits из **локальной `main`**, отправляет их в ветку `main` удалённого `origin`, а `-u` устанавливает для локальной ветки upstream `origin/main` (связь для последующих обменов). Пояснить по частям: `push` — действие, `-u` — запомнить связь, `origin` — адрес, `main` — источник/одноимённое назначение. До команды нужна локальная `main` из блока 02; после неё связь можно увидеть через `git branch -vv`. Первый push не создаёт новый commit и не добавляет незакоммиченные строки.
- Пример и типичная путаница: противопоставить `git push` без ранее настроенного upstream (Git может не знать нужное направление) и осмысленный первый `git push -u origin main`. `origin/main` — обозначение отслеживаемой удалённой ветки, не второй каталог и не отдельный commit. Не советовать `git push --force` при расхождении историй.
- Первое самостоятельное действие: на схеме с одной локальной `main` и двумя именами remotes ученик предсказывает, куда отправит `git push -u origin main` и какую связь покажет `git branch -vv` после успеха. Затем составляет команду для своего проверенного `origin/main`; выполнение — только в практике после блока 04.
- Опора для повторного обращения: «свой clone → проверенный URL `origin` → локальная `main` → `push -u` → `origin/main`». При сообщении об отсутствующем upstream проверить, успешен ли был первый push.
- Переход: направление готово; перед отправкой отделить сведения об авторе commit от входа и прав на сервере.

## 04. Автор commit, вход в GitHub и право записи

- Что и зачем объяснить: разложить на три независимые роли, почему правильная локальная подпись не даёт автоматически доступ к remote.
- Механизм и порядок: `user.name`/`user.email` — данные **автора локального commit**, заданные до его создания (13); при сетевом HTTPS-запросе GitHub проверяет **аккаунт, под которым выполнен вход**; право записи в **конкретный** репозиторий зависит от доступа этого аккаунта. Даже публичный репозиторий не разрешает всем push. Сначала показать различия на знакомой карточке commit и странице владельца repo; только после этого описать безопасный сценарий: выполнить предусмотренный push, дождаться запроса Git Credential Manager/браузера, войти в свой GitHub-аккаунт, вернуться к результату команды. Фактический способ диалога зависит от настроенной системы. Пароль/токен не помещать в URL, командную строку, учебный ответ или скриншот.
- Пример и типичная путаница: commit подписан именем «Аня», а менеджер предлагает аккаунт «Борис», у которого нет доступа к репозиторию Ани. Изменение `git config user.name` не исправит отказ сервера и не перепишет автора существующего commit. Надо проверить учётную запись при входе и её права на **свой** repo.
- Первое самостоятельное действие: в трёх коротких ситуациях различить «подпись не совпадает», «вход ещё не выполнен» и «вход выполнен, но нет права записи»; выбрать соответствующую проверку, не называя секретов и не меняя автора commit. На собственном шаге ученик называет ожидаемый аккаунт/репозиторий, но не демонстрирует приватные данные.
- Опора для повторного обращения: «кто указан автором?», «какой аккаунт подтверждает запрос?», «может ли он писать в этот remote?». Не просить сообщать секрет или вставлять его в материал.
- Форма MAIN: сравнение трёх подписанных ролей с одной самостоятельной классификацией; без повторения её соседним опросом.
- Переход: после штатного входа ученик выполняет запланированную публикацию, не меняя авторство уже созданного commit.

## 05. Разные причины отказа требуют разных проверок

- Что и зачем объяснить: показать, как читать отказ по его смыслу, а не подбирать случайные Git-команды.
- Механизм и порядок: сначала читать **точное сообщение** и выбрать только соответствующую проверку. `src refspec main does not match any` → проверить `git branch --show-current` и `git log -1 --format=%H` (возможны неверная ветка или отсутствие commit); ошибка поиска repository/URL → сверить `git remote -v` с собственным repo, помня, что сервер может также скрывать приватный репозиторий при недостаточном доступе; `Authentication failed` → проверить штатный вход в нужный аккаунт; `403`/permission denied → проверить право записи; `non-fast-forward` → удалённая ветка уже содержит другую историю, остановить самостоятельную отправку и выяснить причину. Это **варианты для анализа**, а не однозначный диагноз по одному слову.
- Пример и типичная путаница: при `Repository not found` нельзя автоматически решить, что URL ошибочный: у приватного repo может быть неверный аккаунт. При `non-fast-forward` не исправлять проблему `--force`, `-f`, `reset --hard`, удалением repo или созданием нового.
- Первое самостоятельное действие: по двум независимым сообщениям ученик выбирает следующую **читающую** команду или проверку доступа и объясняет, какой факт подтвердит/опровергнет гипотезу. Ничего намеренно не ломать в реальном remote.
- Опора для повторного обращения: дерево решений «URL/существование repo → ветка+HEAD → вход → разрешение → несовпадение историй», с остановкой при чужой истории.
- Форма MAIN: один компактный разбор двух разных причин, затем отдельное самостоятельное применение к третьей; без последовательности одинаковых True/False.
- Переход: успешный push тоже нуждается в предметном доказательстве — проверке того, что сервер получил нужную версию.

## 06. Подтверждаем опубликованную версию

- Что и зачем объяснить: критерий завершения — соответствие локальной и удалённой версии, а не сам факт запуска команды.
- Механизм и порядок: после успешного `git push -u origin main` сначала увидеть связь через `git branch -vv` (`main` отслеживает `origin/main`). Для независимой проверки снова получить полный локальный SHA командой `git log -1 --format=%H`, открыть страницу **собственного** repo, выбрать ветку **main**, открыть сведения о commit и сравнить полный SHA. Дополнительный контроль, если веб-интерфейс показывает лишь сокращение: `git ls-remote origin refs/heads/main` возвращает полный ID удалённой ветки (сетевая команда чтения, ничего не публикует). На GitHub открыть `main.py` (Hello world) и `.gitignore` (точные правила `__pycache__/` и `*.pyc`). До первого push по A удалённый репозиторий пуст: README из другой истории не должен внезапно участвовать в отправке.
- Пример и типичная путаница: зелёный текст об успехе или чистый локальный status не подтверждает, что проверен нужный репозиторий и нужный commit. Укороченный ID полезен для ориентира, но финальная сверка должна однозначно указывать на текущий локальный commit.
- Первое самостоятельное действие: на примере «локальный HEAD = `a1…`, удалённая `main` = `a1…`, удалённая `develop` = `b2…`» (обозначения условные, для реальной проверки нужны полные ID) ученик выбирает верную ветку и поясняет, почему успех push сам по себе не заменяет проверку файлов. В собственном проекте независимо предъявляет четыре признака: URL, ветка `main`, полный SHA и две версии файлов.
- Опора для повторного обращения: сверить адрес репозитория → `main` → полный commit ID → содержимое. Если любой элемент расходится, публикация ещё не подтверждена; проверить выбранную страницу/ветку, а не повторять push вслепую.
- Форма MAIN: сопоставление локального и удалённого идентификаторов и двух файлов на одном читаемом визуале; действие — найти намеренно неверную ветку в примере, без декоративных скриншотов.
- Переход: ученик готов выполнить весь маршрут на собственном StudyHub и объяснить, что именно доказало результат.

## 07. Что мы будем делать в практике

**Обязательный формат:** одна проектная ручная практика в **том же локальном StudyHub**, который ученик создал в 12.1 и впервые закоммитил в 13. На входе ожидаются `main.py` с Hello world и `.gitignore` с `__pycache__/` и `*.pyc`; remote до публикации пуст. Учебное задание не создаёт файлы, второй репозиторий или новый commit. Ученик самостоятельно выбирает следующие действия по **собственным** выводам; примеры теории используют другой условный URL/ветку и не могут служить готовыми ответами. Перед проектной частью проверяется наличие A; её отсутствие — возврат в конкретное занятие 12.1 или 13, а не автоматическая «починка» чужой историей.

1. **Допуск: определить собственный источник и назначение.** Вход: открытый терминал в папке предполагаемого clone. Самостоятельное действие после 01–02: выяснить корень repo (`git rev-parse --show-toplevel`), адрес `origin` (`git remote -v`), текущую ветку (`git branch --show-current`), полный ID `HEAD` (`git log -1 --format=%H`), рабочее состояние (`git status --short`), состав первого commit и запуск сохранённого `main.py` с помощью уже знакомого Python 3.12. Сверить URL с созданным в 12.1 **своим пустым** repo. **Локальный критерий:** ученик называет URL, полный SHA, два файла commit и реальную ветку, показывает Hello world; нет неожиданной новой истории и незапланированных изменений. Если имя ветки отличается от `main`, он сначала объясняет условия безопасного переименования из 02, только затем выполняет `git branch -m main` при **свободном имени `main` и неопубликованной ветке** и повторно проверяет имя. Если repo, commit или право на безопасное переименование не подтверждены, остановиться на этом шаге и назвать конкретную зависимость. **Куда вернуться:** 01–02 и 12.1/13 по недостающему элементу A.
2. **Опубликовать имеющийся commit в main.** Вход: подтверждённый свой `origin`, локальная `main` и первый commit из шага 1, предварительно разобраны 03–04. Перед командой ученик своими словами расшифровывает `git push -u origin main`, указывает отправляемый SHA и предсказывает связь upstream; затем самостоятельно выполняет её и при необходимости проходит штатный HTTPS-вход через менеджер/браузер. **Локальный критерий:** Git сообщает об успешной публикации, `git branch -vv` показывает отслеживание `origin/main`, новый commit не создавался и файлы не менялись. При отказе применяется только соответствующая безопасная диагностика из 05; не сообщать токены/пароли и не обходить конфликт историй силовыми командами. **Куда вернуться:** 03–05.
3. **Независимо доказать результат на GitHub.** Вход: попытка push шага 2. Ученик самостоятельно открывает **свой** репозиторий, выбирает именно `main` и находит полный SHA опубликованного commit; сравнивает его с локальным `git log -1 --format=%H`. Если в UI видна только короткая часть, проверяет полный удалённый SHA через объяснённый `git ls-remote origin refs/heads/main`. Открывает серверные `main.py` и `.gitignore`, сопоставляет Hello world и оба правила игнорирования. **Локальный критерий:** совпадают собственный URL, имя `main`, **полный** SHA `HEAD` и содержимое обоих файлов; ученик объясняет, почему зелёный вывод push/чистый локальный status сами по себе недостаточны. При несоответствии сначала проверяет страницу и ветку, затем возвращается к 02–06; не повторяет push вслепую. **Куда вернуться:** 01, 06.
4. **Самостоятельный перенос на ошибку (без порчи проекта).** После реального результата ученику дают **новые**, отличные от теоретического примера, фрагменты: (а) `src refspec main does not match any` при ветке с другим именем; (б) `Repository not found` у приватного remote; (в) `non-fast-forward` при неожиданной серверной истории. Для каждого он определяет, что **пока неизвестно**, выбирает одну следующую безопасную проверку и объясняет, при каком результате остановится за помощью. **Локальный критерий:** не путает refspec с входом, не объявляет любой `Repository not found` точно неправильным URL и при конфликте историй не применяет force push. Это работа с готовыми сообщениями, живой remote специально не ломать. **Куда вернуться:** 02 и 05.

**Различающий контроль самостоятельности:** перед публикацией ученик получает выбор «ветка уже `main` / ветка `topic` ещё не опубликована / `main` уже занята другой локальной историей» и объясняет три **разных** решения: продолжить без переименования / после проверки переименовать безопасно / остановиться. После публикации он сам выбирает, что доказывает наличие версии на сервере: локальный `status`, сообщение push или совпадение полного серверного SHA и файлов. Выбор с объяснением предшествует демонстрации ответа. Для MAIN: связать три шага проекта одной маршрутной схемой «наблюдение → решение → команда → свидетельство»; в каждом содержательном отрезке не оставлять более двух подряд читаемых абзацев без действия/сравнения/учебной схемы и не устраивать цепь из повторных карточек.

**Итоговый критерий всей практики:** один прежний commit опубликован в `origin/main` собственного GitHub-репозитория; серверный SHA совпадает с локальным HEAD, `main.py` и `.gitignore` соответствуют версии занятия 13. Ученик отдельно объясняет «save → commit → push» и «автор commit → аккаунт входа → право записи», показывает upstream и на изменённом безопасном примере выбирает действие без подсказки. Это B занятия 13.1 и точка A занятия 13.2 для дальнейшей правки `normalize_title`.
