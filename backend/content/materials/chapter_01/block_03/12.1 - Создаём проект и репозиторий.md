**Содержательный визуал для MAIN:** одна схема «GitHub (private remote с HTTPS-адресом) → `git clone` → папка StudyHub на ПК → `main.py`»; будущие `commit` и `push` показать пунктиром, без исполнения. Вопрос на прогноз: какой объект появится после `clone` и появится ли `main.py` автоматически при клонировании *пустого* репозитория? Ответ нужен перед следующим разделом.

## 01. Git, GitHub и действия с проектом

- **Разобрать две стороны на одном примере:** Git — программа на компьютере, которая умеет учитывать версии файлов; GitHub — сайт, где хранится удалённый репозиторий. `remote` означает сохранённую в локальном Git связь с удалённым адресом; `origin` — обычное имя этой связи, автоматически созданное при `clone`. Private ограничивает доступ к удалённому репозиторию, но не меняет сам механизм `clone`.
- **До команд объяснить четыре разных действия:** `Save` записывает файл на диск; `clone` создаёт локальную копию репозитория и связь `origin`; будущий `commit` сохранит версию изменений *в локальной истории*; будущий `push` передаст такие версии на GitHub. После `Save` GitHub сам не обновится; на текущем уроке `commit` и `push` не выполняются.
- **Осмысленная вставка для MAIN:** таблица с колонками «действие / где появится результат / выполняем сегодня?» для `Save`, `clone`, `commit`, `push`. Ученик самостоятельно объясняет случай «файл уже виден в VS Code, но его нет на GitHub» и выбирает, достаточно ли `Save` для публикации. Критерий: может объяснить разницу без выполнения следующих уроков.
- **Опора:** «VS Code сохраняет файл → Git видит локальное состояние → `clone` связывает папку с GitHub». После этого можно создавать первый remote.

## 02. Пустой remote и единственный clone

- **До действий:** показать на экране три разные вещи: страницу GitHub, HTTPS URL репозитория (`https://github.com/ACCOUNT/StudyHub.git`) и папку на ПК. `ACCOUNT` в примере — заменяемое имя собственного аккаунта, а не текст для копирования как есть. Все команды ниже вводятся в **PowerShell** (`PS ...>`), не в Python (`>>>`). Команда исполняется относительно текущей папки; `pwd` показывает её путь, `ls` — содержимое. В MAIN показать адресную строку сайта рядом с результатом `pwd`: места разные.
- **Проверка инструментов до первого Git-действия:** `git --version` должен вывести версию Git; `py -3.12 --version` — Python 3.12 (если launcher `py` недоступен, проверить `python --version` и выбрать именно системный Python 3.12). Для Git Credential Manager (GCM) попробовать `git credential-manager --version`: ожидается версия менеджера; при отсутствии команды или настроенного helper проверить установку/настройку по [официальной инструкции GitHub для HTTPS/GCM](https://docs.github.com/en/get-started/git-basics/caching-your-github-credentials-in-git?platform=windows) и повторить именно неудачную проверку. Отсутствие команды — вопрос подготовки среды, не ошибка проекта. GCM помогает пройти браузерную авторизацию, если Git запросит её; открытый в браузере GitHub не означает, что терминал уже авторизован.
- **Создание remote на GitHub:** в своём аккаунте открыть **New repository**, имя `StudyHub`, видимость **Private**; не выбирать **Add a README file**, `.gitignore` и License, чтобы remote остался пустым. После создания открыть **Code → HTTPS**, скопировать показанный адрес. Ни пароль, ни token не вставлять в URL, команды или проект. Свой private remote — единственный источник clone; чужой готовый StudyHub здесь служит ориентиром, но не целью клонирования.
- **Единственный clone:** выбрать и проверить *родительскую* папку для проектов, например `C:\Users\<имя>\Projects`; открыть в ней PowerShell и сверить путь через `pwd`. Если папки StudyHub там ещё нет, исполнить `git clone https://github.com/ACCOUNT/StudyHub.git StudyHub` с **реальным URL, скопированным с GitHub**. Последний `StudyHub` — имя создаваемой локальной папки. Если GCM предлагает войти, выбрать свой аккаунт и закончить штатный вход в браузере; успешный clone подтверждает только доступ на чтение. Сообщение `You appear to have cloned an empty repository` ожидаемо для пустого remote.
- **Проверка результата до создания файлов:** `cd StudyHub` переводит PowerShell *внутрь* клона; `pwd` теперь оканчивается на `StudyHub`, а `git remote -v` показывает `origin` с тем же HTTPS URL (для fetch и push). Наличие строки `push` в адресах не доказывает право push. `git status` безопасно читает состояние: для пустого clone ожидаются отсутствие commit и отсутствие пользовательских файлов; конкретное имя начальной ветки зависит от настроек. Новый `git init` не выполнять.
- **Самостоятельное различение:** ученик показывает вживую URL на GitHub, родительскую папку, локальный путь после `cd` и адрес `origin`; объясняет, почему пустой clone не содержит `main.py`. Критерий — все три указателя относятся к *одному* личному private-репозиторию, а не к готовому чужому проекту.
- Развилка восстановления папки: до clone осмотреть полный целевой путь и его содержимое. Если папка отсутствует — выбрать её как назначение; если она существует и пуста — использовать только этот проверенный путь, не создавать внутри ещё одну папку clone. Если в ней уже есть корректный clone с `origin` на ожидаемый remote — открыть и продолжить его, повторно не клонировать. Если clone был прерван или содержимое неожиданно, проверить путь, файлы, наличие Git-метаданных и `origin`; ничего не удалять. При неполном или неоднозначном состоянии оставить каталог нетронутым и выбрать отдельную свободную соседнюю папку для единственного рабочего clone либо остановить зависимый шаг до выяснения. Не запускать clone внутрь существующего каталога наугад.
- **При ошибке доступа:** если GitHub отвечает `Repository not found`, проверить точность URL, видимость репозитория под тем же аккаунтом и завершённость GCM-входа; не создавать второй репозиторий и не подбирать URL наугад. **Опора восстановления:** проверить путь и содержимое → найти имеющийся clone или свободную цель → сверить `origin` → продолжить из этой папки. Подробности авторства commit, права записи и push оставить занятию 13.1.
- Переход к следующему шагу: внутри найденной папки можно создать первый сохранённый файл проекта.

## 03. Файл проекта и его расположение

- **Путь до файла:** открыть в VS Code **File → Open Folder → папка StudyHub, найденная через `pwd`**. Корень проекта — сама открытая папка клона; `main.py` лежит непосредственно в ней, рядом с будущим `.gitignore`, а не в `StudyHub/StudyHub` и не в соседней папке. Дерево файлов VS Code помогает увидеть расположение, а `pwd` — текущую папку терминала; вкладка редактора и терминал могут указывать в разные места.
- **Первый файл:** ученик сам выбирает **New File → `main.py`** и вводит уже известный `print("Hello world")`; объяснить, что `print` выводит строку, а Save (`Ctrl+S`) переносит изменения из вкладки на диск. Не добавлять пока ни функций, ни ввода, ни дополнительных модулей. До запуска показать на схеме один путь `.../StudyHub/main.py` и соответствующий ему файл в проводнике VS Code.
- **Проверка понимания без готового решения:** ученик называет полный путь файла и находит значок несохранённых изменений; прогнозирует, какой текст выйдет после замены строки на `print("Привет из StudyHub")` и сохранения. После запуска из следующего раздела он **сам** возвращает `print("Hello world")`, сохраняет и перепроверяет вывод. Критерий — может сопоставить *конкретный сохранённый файл* и наблюдаемый результат, даже если в редакторе открыты две вкладки с одинаковым именем.
- **Опора:** «открытая папка VS Code → `main.py` в корне → Save → запуск из этой же папки». Если путь или сохранение расходятся, исправлять это до команды исполнения.

## 04. Запуск сохранённого файла выбранным Python

- **Перед запуском:** системный Python 3.12 выполняет код, VS Code лишь помогает его записать. Терминал **PowerShell** обычно показывает `PS ...>`; `>>>` означает интерактивную оболочку Python, где `git`, `cd` и команда `py -3.12 main.py` не выполняются как команды PowerShell. Если ученик видит `>>>`, сначала `exit()`, затем продолжает в PowerShell.
- **Проверенный путь:** в интегрированном PowerShell VS Code выполнить `pwd` и убедиться, что это именно папка клона StudyHub. Если нет, перейти `cd` по найденному пути или открыть новый терминал из правильной папки. Команда `py -3.12 main.py` запускает **сохранённый** файл установленным Python 3.12; при отсутствии `py`, но доступном `python --version` = 3.12, применить `python main.py`. Ожидаемый stdout — одна строка `Hello world`, без кавычек. Никаких venv и пакетов для этого файла не требуется.
- **Различающие случаи для MAIN:** в первой попытке ученик видит `can't open file` — диагностирует текущую папку и наличие `main.py`, а не переустанавливает Python; после смены строки в редакторе вывод старый — сперва проверяет сохранение; `py` не распознана — проверяет доступный системный интерпретатор и его версию, а не устанавливает случайные зависимости. Не выдавать эти ошибки как обязательные для воспроизведения. Видимое изменение строки после Save подтверждает исполнение нужного файла.
- **Самостоятельное применение:** ученик меняет приветствие из раздела 03, **предсказывает stdout до запуска**, сохраняет, выполняет команду, сравнивает с прогнозом; затем возвращает `Hello world`, сохраняет и запускает снова. Критерий — оба наблюдения связаны с содержимым именно `.../StudyHub/main.py`.
- **Опора:** «PowerShell → `pwd` → Save → системный Python 3.12 → сверить stdout». Затем можно научиться отличать исходники от возможных служебных файлов Python.

## 05. `.gitignore` и чтение состояния

- **Зачем правило:** `main.py` — наш исходный код. Папки `__pycache__/` и файлы с расширением `.pyc` *могут* возникнуть при работе Python, но не являются тем кодом, который ученик редактирует. В корне StudyHub ученик сам создаёт `.gitignore` (имя начинается с точки) с **двумя отдельными строками**:

  ```gitignore
  __pycache__/
  *.pyc
  ```

- **До ввода команды объяснить:** `git status` читает состояние Git *в текущей папке*, но не сохраняет версию и не отправляет её на GitHub. Из папки StudyHub выполнить `git status`: до первого commit ожидаются незакоммиченные `main.py` и `.gitignore` как untracked; слово untracked означает «Git видит файл, но он ещё не добавлен в историю». Название ветки и формат сообщений могут отличаться. Игнорируемые пути обычный `git status` не перечисляет, даже если они есть.
- **Различение на конкретных примерах:** из `main.py`, `.gitignore`, `__pycache__/cache.pyc` и `notes.pyc` ученик выбирает, что должно остаться видимым Git и что игнорируется; объясняет, почему `.gitignore` не удаляет файлы и не отменяет отслеживание файлов, попавших в историю ранее. Сами артефакты специально создавать и импортировать модули не нужно; отсутствие `__pycache__` после простого скрипта допустимо.
- **Последняя проверка после последнего изменения:** сохранить `.gitignore`, удостовериться, что обе строки в корне клона, снова выполнить `py -3.12 main.py` (либо уже проверенную команду `python main.py`) и убедиться в `Hello world`; затем `git status` из StudyHub. Ученик объясняет, что нет staging и commit, а `status` только показывает состояние. **Опора:** «сохранить `.gitignore` → повторить запуск → прочитать status → остановиться до `git add`».

## 06. Что мы будем делать в практике

**Формат по паспорту:** один локальный проект StudyHub, ручная проверка результата (`MANUAL_PRACTICE`). Старт: собственного remote/clone нет; Python 3.12, VS Code и запуск сохранённого файла должны быть реально подтверждены после урока 12. Ученик делает операции сам после короткой демонстрации механизма на экране, преподаватель проверяет наблюдаемые состояния, не делает действия за него. Личный GitHub-аккаунт, доступ к сети, Git/GCM нужны для клонирования; сбой доступа фиксируется отдельно и не подменяется созданием другого проекта.

1. **Создать remote и найти свой clone (проверка связи).** Дан GitHub-аккаунт и показан принцип `clone`, но репозиторий ученик создаёт сам: `StudyHub` → **Private** → без README, License и готового `.gitignore`. Ученик копирует **свой** HTTPS URL, выбирает родительскую папку, смотрит `pwd`/`ls` и только после этого выполняет **один** `git clone https://github.com/ACCOUNT/StudyHub.git StudyHub`, заменив примерный URL на адрес с GitHub; через GCM входит при необходимости. Затем самостоятельно находит получившуюся папку, входит в неё и объясняет `git remote -v`. **Критерий:** путь оканчивается на StudyHub, `origin` совпадает с URL именно его private-репозитория, clone пока пуст. При уже существующем корректном clone нужно открыть его и не клонировать повторно; при неизвестном содержимом — сохранить всё нетронутым и согласовать свободный путь. Не проверять push-доступ.
2. **Создать работающий файл (проверка сохранения).** Исходное состояние — рабочий пустой clone. Без готового файла-заготовки ученик в VS Code создаёт *в его корне* `main.py`, записывает известный вызов `print` с Hello world и сохраняет. Сначала прогнозирует stdout, затем через PowerShell из этого каталога запускает файл системным Python 3.12. Для отличающегося случая сам меняет строку на своё приветствие, *до запуска* записывает прогноз, сохраняет и объясняет расхождение, если увидел старый вывод. В завершение восстанавливает `print("Hello world")`, сохраняет и запускает ещё раз. **Критерий:** путь файла и `pwd` относятся к одному clone; две разные сохранённые строки дают предсказанные результаты, финальный stdout — `Hello world`.
3. **Решить, что игнорировать (проверка состояния Git).** Даны четыре пути: `main.py`, `.gitignore`, `__pycache__/example.pyc`, `module.pyc`. Ученик обосновывает, почему два последних относятся к артефактам, а первые два — к нужным файлам проекта, затем сам записывает в корневой `.gitignore` правила `__pycache__/` и `*.pyc`, **каждое с новой строки**. Сохраняет, повторно запускает `main.py` и читает `git status`. **Критерий:** `main.py` работает после последней правки, `.gitignore` содержит оба правила, Git показывает два новых файла как untracked; отсутствие реального кэша не считается ошибкой. Ученик объясняет, почему статус ничего не закоммитил и почему игнорирование не удаляет файлы.

**Отдельная диагностическая проверка без подсказки команды:** преподаватель показывает ситуацию «в VS Code новая строка, терминал всё ещё печатает Hello world; `pwd` показывает родительскую папку Projects». Ученик должен назвать **две независимые проверки** — сохранено ли новое содержимое и из какой папки запускается файл — и выбрать порядок устранения. Другой случай: `origin` указывает на чужой GitHub URL при удачном запуске `main.py`: ученик распознаёт, что Python работает, но B по связи с личным remote не выполнена, и не предлагает второй `git init`/слепой повторный clone. Это диагностика на словах/в учебном макете, без изменения правильного рабочего проекта.

**Суммарная приёмка B:** ученик показывает private remote с пустым стартом, единственную локальную копию с верным `origin`, сохранённый и запускаемый Python 3.12 файл `main.py` с `Hello world`, корневой `.gitignore` ровно с нужными правилами и `git status` без staging/commit. Для `main.py` подтверждается конечный вывод **после последней правки `.gitignore`**. Если Git/доступ/GCM/сеть не работают, это точный внешний blocker для clone и итог ещё не принят; проверенную подготовку инструментов и объяснения можно зачесть, но **не создавать запасной проект** и не изображать связь с remote. Никаких `git add`, `git diff`, `git init`, commit, push и проверки права записи: первый локальный commit — занятие 13, авторство и первый push — 13.1.
