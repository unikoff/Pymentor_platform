## 00. Вступление

Маршрут предполагает, что ученик может редактировать и запускать знакомый Python-код локально; это проверяется перед работой, так как фактическое освоение новой карты не подтверждено. Теперь ему нужен один понятный дом для проекта и его дальнейших изменений. Сначала появится пустой удалённый репозиторий и его локальная копия, затем первый запускаемый файл и правило для служебных файлов Python.

1. **Точка старта:** по паспорту 26 Python 3.12 и VS Code доступны; у ученика ещё нет Git-репозитория или проекта.
2. **Новый вопрос:** как безопасно получить свою копию private-репозитория и убедиться, что запускается именно сохранённый файл из clone?
3. **Результат:** один пустой remote и один clone с запускаемым `main.py`, `.gitignore` и понятным состоянием незакоммиченной работы.

Переход идёт от уже знакомой работы с файлом к новой модели двух связанных мест — локальной папки и remote. По пути ученик впервые запускает файл внутри clone. На этом занятии он подготовит рабочую папку; история изменений появится позже.

## 01. Git, GitHub и действия с проектом

- Что и зачем объяснить: Git хранит историю локальных изменений, GitHub размещает удалённый репозиторий, а remote — адрес связанного удалённого источника. До действий разобрать роль установленного Git, учётной записи, владельца, адреса и видимости репозитория. Пояснить отдельно, что выбор видимости не меняет назначение clone.
- Механизм и порядок: сохранить файл означает записать его в папку; clone получает репозиторий и настраивает связь с remote; commit позже создаст локальную версию; push позже отправит уже созданную версию на GitHub. На этом занятии используются создание remote и clone, сохранение файла; commit и push только обозначены как последующие действия.
- Пример и типичная путаница: различить редактор, который сохраняет файл, Git, который ведёт локальную историю, и GitHub, где размещена копия истории. Сохранение не равно commit, а commit не равен push.
- Первое самостоятельное действие: по схеме действий ученик определяет, где находится файл после сохранения, clone, commit и push; отдельно указывает, какие из этих действий реально выполняются сейчас. Наблюдаемый результат — роли не смешиваются и будущий commit не выдаётся за публикацию.
- Опора для повторного обращения: краткая связка «редактор → файл; Git → локальная история; GitHub → remote; clone → локальная копия» и различие «сохранить / зафиксировать / отправить».
- Переход к следующему шагу: с понятными ролями можно создать один пустой remote и получить связанную с ним рабочую папку.

## 02. Пустой remote и единственный clone

- Что и зачем объяснить: собственный пустой private-репозиторий нужен, чтобы дальнейшая работа шла в одной истории ученика и была видна только тем, кому владелец предоставил доступ. Для минимального сценария ученик создаёт его в своём GitHub-аккаунте: это убирает отдельное приглашение владельца. Объяснить URL как адрес репозитория и HTTPS как выбранный способ соединения, не углубляясь в устройство протокола. Репозиторий оставляют пустым, без автоматически добавленных README, LICENSE и других файлов.
- Механизм и порядок: проверить установленный Git и наличие Git Credential Manager (GCM); если чего-то не хватает, пройти объяснённый официальный путь установки до clone. GCM — менеджер учётных данных для GitHub: при необходимости он открывает браузерный вход и сохраняет вход штатным системным способом. Скопировать HTTPS URL именно со страницы созданного репозитория. Ученик входит в тот же GitHub-аккаунт, в котором создал private-репозиторий; это подтверждает доступ для чтения/clone. Не вводить пароль или токен в команду, код либо `.gitignore`; не разбирать право записи. Затем клонировать пустой репозиторий в проверенную целевую папку. `origin` — локальное имя, с которым clone сохраняет адрес этого remote; повторный `git init` не нужен. Предупреждение о пустом remote само по себе не означает ошибку. Подробная настройка — в [официальной инструкции GitHub по HTTPS и GCM](https://docs.github.com/en/get-started/git-basics/caching-your-github-credentials-in-git?platform=windows).
- Пример и типичная путаница: различить страницу private remote на GitHub и локальную папку clone. Успешный вход в браузере не доказывает, что выбран правильный URL; успешный clone подтверждает доступ к чтению, но не проверяет будущую публикацию. Готовый StudyHub не подменяет личный пустой репозиторий.
- Первое самостоятельное действие: ученик создаёт собственный пустой private-репозиторий, копирует HTTPS URL и клонирует один раз; если GCM просит вход, входит через браузер тем же аккаунтом. Затем называет точную папку и проверяет, что `origin` ведёт к созданному репозиторию. Критерий — clone доступен локально и связан с ожидаемым private remote; права push не проверяются.
- Опора для повторного обращения: «private repo моего аккаунта → скопировать HTTPS URL → при запросе войти через GCM в браузере → проверить целевую папку и origin». Если GitHub сообщает, что репозиторий не найден, сначала сверить скопированный URL и аккаунт, имеющий доступ на чтение; не менять адрес наугад.
- Развилка восстановления папки: до clone осмотреть полный целевой путь и его содержимое. Если папка отсутствует — выбрать её как назначение; если она существует и пуста — использовать только этот проверенный путь, не создавать внутри ещё одну папку clone. Если в ней уже есть корректный clone с `origin` на ожидаемый remote — открыть и продолжить его, повторно не клонировать. Если clone был прерван или содержимое неожиданно, проверить путь, файлы, наличие Git-метаданных и `origin`; ничего не удалять. При неполном или неоднозначном состоянии оставить каталог нетронутым и выбрать отдельную свободную соседнюю папку для единственного рабочего clone либо остановить зависимый шаг до выяснения. Не запускать clone внутрь существующего каталога наугад.
- Опора для повторного обращения: порядок «проверить путь и содержимое → удостовериться, что это пустая цель или нужный clone → при необходимости выбрать отдельную свободную папку → открыть именно рабочий clone → проверить origin»; при запросе доступа применить только штатный вход GCM, не помещая секреты в файлы. Подробности авторства commit, права записи и push оставить занятию 13.1.
- Переход к следующему шагу: внутри найденной папки можно создать первый сохранённый файл проекта.

## 03. Файл проекта и его расположение

- Что и зачем объяснить: `main.py` станет первым исходным файлом в clone. Расширение `.py`, путь файла, текущая папка терминала и открытая вкладка редактора обозначают разные вещи; команды проекта должны выполняться из правильной копии.
- Механизм и порядок: открыть именно clone в VS Code, создать и сохранить `main.py` в его корне. На коротком исправном примере с приветствием показать связь «сохранённый исходный текст → запуск файла → вывод». Не добавлять функции, чтение ввода или бизнес-логику Planner.
- Пример и типичная путаница: файл с тем же именем в другой папке и несохранённое содержимое вкладки не являются текущим файлом clone. Сверить путь в редакторе и расположение папки перед запуском.
- Первое самостоятельное действие: после показанного создания ученик самостоятельно сохраняет файл в clone и проверяет его расположение; затем меняет только текст приветствия, прогнозирует вывод и запускает, возвращая в итоговую версию Hello world. Результат — изменение исходного текста отражается в запуске именно этого файла.
- Опора для повторного обращения: расположение clone, путь сохранённого `main.py` и знак несохранённых изменений в редакторе.
- Переход к следующему шагу: прежде чем проверять результат, нужно выбрать тот Python, которым файл будет исполняться.

## 04. Запуск сохранённого файла выбранным Python

- Что и зачем объяснить: редактор и расширение помогают писать код, но файл исполняет установленный Python 3.12. Для запуска используется системный интерпретатор, уже настроенный в VS Code; отдельная среда и сторонние пакеты не нужны.
- Механизм и порядок: до команды различить PowerShell и Python-оболочку, пояснить, что команда запуска относится к терминалу, а Python-код — к файлу или приглашению `>>>`. Напомнить, что текущая папка определяет, какой файл найдётся. Затем запустить сохранённый `main.py` выбранным Python и сверить вывод.
- Пример и типичная путаница: автоматическое эхо выражения в Python-оболочке не является выводом программы; запуск кода из другой папки может обратиться не к тому файлу. Открытая вкладка без сохранения тоже не доказывает, что исполнен её последний текст.
- Первое самостоятельное действие: ученик из папки clone запускает файл выбранным Python, объясняет, в каком приглашении вводилась команда, и сопоставляет вывод с сохранённым текстом. Если команда, путь или интерпретатор неверны, он называет наблюдаемый признак и исправляет только этот шаг.
- Опора для повторного обращения: «сначала проверить текущую папку и сохранение; затем выбрать системный Python 3.12; после запуска сравнить ожидаемый приветственный вывод».
- Переход к следующему шагу: после первого рабочего запуска можно определить, какие файлы относятся к исходникам, а какие создаются Python.

## 05. `.gitignore` и чтение состояния

- Что и зачем объяснить: при работе Python могут появляться `__pycache__/` и `*.pyc`; это служебные артефакты, не исходный код. Файл `.gitignore` описывает пути, которые Git должен игнорировать, но не удаляет файлы и не отменяет отслеживание уже известных Git файлов.
- Механизм и порядок: до просмотра состава объяснить `git status` как чтение состояния локальной рабочей папки, которое само не меняет историю. Добавить в `.gitignore` только правила для `__pycache__/` и `*.pyc`. Не объяснять внутреннее устройство кэша и `import`; не добавлять `.venv/`, поскольку запуск этого блока использует системный Python.
- Пример и типичная путаница: отсутствие игнорируемого пути в обычном статусе не означает, что файл удалён; `.gitignore` также не заменяет сохранение исходного `main.py`. Не путать чтение status с добавлением в staging или созданием версии.
- Первое самостоятельное действие: по короткому списку файлов ученик самостоятельно выбирает Python-артефакты для игнорирования и вносит эти два правила в проект. После сохранения `.gitignore` запускает `main.py` ещё раз: это последняя правка проектных файлов и последняя проверка прежней возможности. Результат — правила находятся в корневом `.gitignore`, приветствие продолжает работать, а ученик объясняет, что status только сообщает о состоянии.
- Опора для повторного обращения: смысл двух правил, расположение `.gitignore` и роль status; к staging и commit вернуться в следующем уроке.
- Переход к практике: объединить пустой remote, clone, запускаемый файл и правила игнорирования в один рабочий результат.

## 06. Что мы будем делать в практике

**Формат и исходная опора:** проект. Начинаем без собственного remote и локального проекта; перед clone проверяем наличие Git, а перед проектной работой подтверждаем Python 3.12 и VS Code. Основной сценарий — пустой private-репозиторий ученика и clone по HTTPS через GCM. Если аккаунт не может открыть репозиторий на чтение, браузерный вход недоступен, нет сети или Git нельзя установить, это внешний блокер зависимого шага, а не непонимание Python. Право записи не проверяем.

Общий результат — один личный пустой remote и его единственный clone с сохранённым `main.py`, который запускается выбранным системным Python и показывает Hello world, а также `.gitignore` с правилами для Python-артефактов. Работа остаётся локально незакоммиченной.

1. **Создать private remote и получить clone:** исходное состояние — личного репозитория и проекта ещё нет. После объяснения ролей Git/GitHub ученик под своим аккаунтом создаёт пустой private remote без предзаполненных файлов и копирует HTTPS URL. Если clone запрашивает вход, он проходит браузерный вход через GCM тем же аккаунтом; секреты не вставляются в команду и не сохраняются в проекте. До запуска clone ученик осматривает точный целевой путь. Если папки нет — использует её; если она уже существует — проверяет содержимое: корректный clone с ожидаемым `origin` открывает и использует дальше, пустую цель выбирает без вложенного clone, а при неполном или неизвестном содержимом ничего не удаляет и выбирает отдельную свободную соседнюю папку либо останавливает зависимую часть. Критерий шага — один рабочий clone связан с нужным private remote и доступен текущему аккаунту для чтения; право записи не тестируется.
2. **Сохранить и запустить `main.py`:** исходное состояние — пустой clone. На основе знакомых файла, строки, `print` и локального Python ученик создаёт `main.py`, сохраняет приветствие, выбирает объяснённый интерпретатор и проверяет запуск из правильной папки. После разобранного запуска он меняет только сообщение и объясняет изменение результата, затем оставляет Hello world как последнюю правку, сохраняет и запускает именно это состояние. Критерий — сохранённый файл в clone под Python 3.12 показывает ожидаемое приветствие.
3. **Добавить ignore и прочитать состояние:** исходное состояние — запускаемый файл в clone. Используя объяснение Python-артефактов, ученик самостоятельно вносит последние изменения в `.gitignore` для `__pycache__/` и `*.pyc`, сохраняет файл и повторно запускает `main.py`; затем читает `git status`: распознаёт новые `main.py` и `.gitignore`, понимает, что status только описывает рабочее дерево и что обычный вывод не показывает все игнорируемые пути. Критерий — после последней правки файлы сохранены, программа запускается, правила корректно записаны, состояние прочитано без stage/commit.

Каждый следующий шаг опирается на проверяемый результат предыдущего: сначала установлен адрес и папка, затем в этой папке созданный учеником файл, после — исключения для служебных артефактов. Для изменений кода удерживаем порядок: последняя правка → сохранение → запуск сохранённого состояния → проверка diff → commit или публикация только если этого требует результат занятия. В уроке 12.1 последняя правка — `.gitignore`; после её сохранения повторно запускается `main.py`. Файлы остаются untracked, поэтому проверяем их содержимое и status, не делая вывод по пустому Git diff; staged diff будет изучен перед локальным commit в занятии 13. Авторство commit, права записи и первый push относятся к занятию 13.1. Итог подтверждает B только при совпадении clone и `origin`, успешном запуске именно сохранённого `main.py` системным Python 3.12 и наличии `.gitignore` с двумя нужными правилами. Отдельные аккаунтные/сетевые отказы фиксируются как внешняя причина незавершённого clone.
