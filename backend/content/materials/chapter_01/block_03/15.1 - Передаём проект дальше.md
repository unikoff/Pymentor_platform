## 00. Вступление

Код может работать в папке автора, но этого ещё недостаточно, чтобы передать его дальше. Следующий шаг потребует опереться на сохранённые функции, поэтому сначала нужно проверить именно опубликованную основу и увидеть, что её можно получить заново.

1. **Точка старта:** после выполнения предыдущих практик у ученика должен быть один локальный StudyHub с четырьмя функциями и коротким демо; сначала проверяем, что этот вход действительно существует.
2. **Новый вопрос:** как подготовить и отправить окончательную основу и убедиться, что свежий clone получил именно её, а не старый локальный вариант?
3. **Результат:** clone опубликованной ветки запускает основу из соседнего каталога на этом же компьютере, а ученик может предъявить совпадающие commit и четыре договора.

Сначала различим основной каталог и проверочную копию и выясним, какую версию собираемся передать. Затем приведём демо в порядок, при наличии содержательной правки отправим её в прежнюю историю и **после этого** получим свежий clone в свободную соседнюю папку. Исправление обнаруженной после clone ошибки — отдельная условная ветка: опубликованную правку подтянем в существующую проверочную копию. В конце ученик объяснит, что доказано и что получает блок 4. Это проверка передачи основы, а не сборка Planner.

## 01. Что доказывает независимая копия

- Что и зачем объяснить: успешный запуск в основном каталоге подтверждает только этот локальный файл и выбранный способ запуска. Clone из remote проверяет полноту опубликованных файлов и их запуск из другой рабочей копии на том же компьютере. Это помогает отличить работающую локальную правку от опубликованной версии; такая проверка не доказывает установку или запуск проекта на любом другом компьютере.
- Механизм и порядок: показать четыре состояния **файл в основном каталоге → сохранённый commit → отправленный commit в конкретной ветке remote → файлы нового clone**. `git status --short` показывает локальные изменения, `git diff -- main.py` — содержимое правок отслеживаемого файла, но после `git add` их надо смотреть как staged diff (`git diff --cached -- main.py`). Commit сохраняет выбранные изменения в истории, `push` отправляет commit; новый clone получает опубликованную историю, а не незакоммиченный текст и не файлы, исключённые `.gitignore`. Чистый `status` не подтверждает состоявшийся push.
- Независимый пример и типичная путаница: автор заменил строку демо «урок 14» на «урок 15», увидел её при локальном запуске, но ещё не создал commit. На сайте репозитория строка старая; в новом clone тоже будет старая. После commit без push локальная история уже новая, remote и свежий clone ещё старые. Эти два случая различаются тем, **где лежит новый commit**; это не случайная потеря файла.
- Первое самостоятельное действие: для ситуаций «файл сохранён, commit отсутствует» и «commit создан, push отсутствует» ученик заранее отмечает, какой вариант получит clone и какое наблюдение отличит состояния. Сопоставляет ответ с изображённой цепочкой передачи; при неизвестном адресе remote не делает вывод о конкретной версии.
- Содержательная вставка для MAIN: схема четырёх состояний с двумя разными остановками («до commit»/«после commit, до push»); ученик прогнозирует содержимое clone до раскрытия результата. Это одна схема причин, а не серия карточек с пересказом текста.
- Опора для повторного обращения: «что доказывает запуск» — путь проверочной папки, commit, полученный из remote, и поведение запущенного файла; локальная правка без commit в это доказательство не входит.
- Переход к следующему шагу: чтобы интерпретировать результат, нужно не перепутать две папки и знать, какую удалённую историю проверяем.

## 02. Роли основного каталога и clone

- Что и зачем объяснить: основной каталог остаётся местом разработки. Свежий clone — отдельная проверочная копия с собственным путём и настроенным `origin`; команды запуска из неё относятся к файлам clone, а не к основному проекту.
- Механизм и порядок: сначала в **основной** папке проверить текущий путь терминала, `git remote -v` (URL напротив `origin`) и `git branch --show-current` (имя текущей ветки). По странице **своего** remote уточнить, какая ветка содержит опубликованную основу: ветка по умолчанию или выбранная ветка с B3 checkpoint. После окончательной публикации выйти из основного каталога в его родительскую папку, выбрать **новое свободное имя**, например `studyhub-check`; из родительской папки `git clone <URL> studyhub-check` получает ветку по умолчанию, а `git clone --branch <имя-опубликованной-ветки> <URL> studyhub-check` сразу выбирает другую опубликованную ветку. Угловые скобки — места для собственных значений, не текст для буквального копирования. Затем перейти в `studyhub-check` и проверить путь/`origin`. Не клонировать поверх основного каталога, не удалять пользовательские файлы и не выполнять `git init` в clone.
- Независимый пример и типичная путаница: у ученика открыты терминалы `…/studyhub` и `…/studyhub-check`; в обоих `main.py`, но первый — место изменений и commit, второй — место проверки. Даже одинаковое имя ветки в двух копиях не делает файлы синхронными. `git remote -v` и показанный текущий путь полезнее заголовка окна.
- Первое самостоятельное действие: ученик на странице своего репозитория находит фактическую ветку с B3 commit (она может отличаться от ветки по умолчанию), выбирает подходящую форму команды clone, указывает два разных пути и объясняет, где разрешены исправления. Критерий — выбран тот же remote и именно опубликованная ветка; новая папка до команды отсутствует.
- Содержательная вставка для MAIN: схема двух соседних папок с подписями «изменяем / только запускаем» и коротким прогнозом «в какой папке изменится файл после редактирования?». После схемы — текстовый переход к идентификаторам commit.
- Опора для повторного обращения: две роли и два пути; после каждого перехода в терминале заново установить, какой `main.py` будет запущен и какой remote относится к этому clone.
- Переход к следующему шагу: после выбора безопасного места и точной ветки нужно сверить, что clone получил требуемый опубликованный commit, а не просто похожий репозиторий.

## 03. Как выбрать опубликованную версию

- Что и зачем объяснить: проверяется личный StudyHub, который ученик развивал по текущему маршруту, и commit, опубликованный для передачи. Канонический репозиторий или более поздняя версия проекта могут уже содержать материалы следующего блока.
- Механизм и порядок: на странице удалённого репозитория **выбрать опубликованную ветку и открыть её последний commit**: его полный ID — контрольное значение, которое следует записать вместе с URL/именем ветки. До клонирования проверить, что **текущая вершина** выбранной ветки всё ещё является нужной основой B3; более поздний Planner не подходит даже при совпадении имени репозитория. Команда `git rev-parse HEAD` внутри папки показывает полный ID текущего commit **этой локальной копии**, но сама по себе не сообщает, был ли commit отправлен. После clone в новой папке выполнить `git remote -v`, `git branch --show-current`, `git rev-parse HEAD` и сравнить URL, ветку и весь ID с опубликованными значениями. Имена папок/сообщение `clone completed` и совпадение первых символов SHA не заменяют эту сверку.
- Пример и типичная путаница: исторический snapshot `383c212b` содержит все операции Planner и потому представляет более поздний результат курса. Он помогает понять итоговые договоры, но его нельзя подменять им как ученический B3: это пропустило бы работу блока 4.
- Первое самостоятельное действие: по независимому набору «основная папка — commit A, страница remote — commit B» ученик не объявляет передачу успешной, даже если названия веток совпадают. Затем для своей истории записывает три значения «URL / опубликованная ветка / полный commit ID» и объясняет, где их перепроверит в clone. Результат — проверяемая версия, а не догадка по имени проекта.
- Содержательная вставка для MAIN: одно сравнение «URL / ветка / commit» в двух копиях с несовпадающим SHA; ученик указывает строку, из-за которой проверка не пройдена. Не повторять схему каталогов из раздела 02.
- Опора для повторного обращения: адрес remote, ветка и идентификатор отправленного commit должны относиться к одной истории. Если они не совпадают, остановить вывод о передаче и сначала найти расхождение.
- Переход к следующему шагу: сверенная версия становится основанием для запуска и проверки четырёх уже созданных компонентов.

## 04. Что означает «основа запускается»

- Что и зачем объяснить: сам факт старта не заменяет проверку договоров. В clone нужно запустить `main.py` установленным Python 3.12 и увидеть ожидаемое демо; затем проверить, что каждый из четырёх компонентов сохранил свою ответственность. Этот результат относится к опубликованным файлам и второй рабочей копии на том же компьютере; он не проверяет установку, настройку и запуск на незнакомом компьютере.
- Механизм и порядок: `normalize_title(title)` удаляет крайние пробелы, сохраняет регистр и внутренние пробелы, допускает пустой результат. `create_task(task_id, title, priority)` возвращает отдельный словарь с переданными полями и `is_done=False`, не читая ввод, не выбирая id и не добавляя запись. `format_task(task)` возвращает строку вида `[id] title | приоритет: priority | состояние`, где состояние — «не завершена» или «выполнена»; функция не печатает и не меняет задачу. `calculate_study_minutes(durations)` возвращает сумму, для пустого списка — ноль, и не меняет вход.
- Способ проверить без правки clone: сначала выполнить обычный запуск `main.py` установленным Python 3.12. Затем, **находясь в каталоге проверяемой копии**, запустить `py -3.12 -i main.py` на Windows с Python Launcher (или `python -i main.py`, если `python --version` подтверждает 3.12). Флаг `-i` означает: выполнить файл и оставить открытую оболочку Python; приглашение `>>>` ожидает **выражения Python**, например вызова функции с новым аргументом, и показывает возвращённое значение. Для проверки двух состояний можно заранее подготовить словарь, а затем отдельно поменять `is_done` в нём; неизменность после `format_task` проверяется повторным просмотром словаря. Команда `exit()` возвращает в обычный терминал. Подготовить объяснение `-i`, `>>>` и выхода **до** задания на проверку; не считать интерактивную оболочку функцией Planner.
- Независимый пример и типичная путаница: `normalize_title("  Study  Hub  ")` даёт `"Study  Hub"` (внутренние два пробела остаются); `calculate_study_minutes([20, 5])` даёт `25`, а `calculate_study_minutes([])` — `0`. Для карточки с `is_done=False` `format_task` возвращает строку с «не завершена», после изменения флага **во входном словаре для отдельного теста** — строку с «выполнена»; сама функция флаг не переключает. `print(format_task(task))` печатает результат снаружи: внутри formatter нет `print`. Не проверять только красивый вывод демо.
- Первое самостоятельное действие: после восстановления договора ученик **сам придумывает данные, отличающиеся от разобранных**, и задаёт ожидаемые ответы до запуска. Для `normalize_title` — непустое и состоящее из пробелов название; для `create_task` — два вызова и проверка отдельных словарей с `is_done=False` и отсутствием общего `tasks`; для `format_task` — оба состояния и неизменность словаря; для `calculate_study_minutes` — три значения и пустой список, вход не меняется. Ученик сопоставляет прогноз с наблюдаемым значением и исправляет несоответствие **в основном каталоге**, до публикации; одна запись результата демо не заменяет четыре самостоятельные проверки.
- Содержательная вставка для MAIN: компактная таблица «функция / вход / возвращает / не делает» с раскрываемым прогнозом для `format_task` и пустого списка; одна сравнительная работа, без четырёх одинаковых карточек подряд.
- Опора для повторного обращения: у каждой функции восстановить «вход → результат → чего функция не делает». Не использовать старые данные демо как единственное доказательство.
- Переход к следующему шагу: договоры проверяются в новом каталоге, чтобы запуск подтвердил опубликованную основу, а не только основной рабочий файл.

## 05. Исправление и повторная публикация

- Что и зачем объяснить: **обычный путь** завершается подготовкой `main.py` в основном каталоге, при необходимости commit/push и **только затем** новым clone. Если уже после clone найден реальный дефект, понадобится повторная публикация и обновление существующей копии; это отдельное условное действие.
- Механизм и порядок: в основном каталоге сохранить нужную правку `main.py`, выполнить знакомый запуск системным Python 3.12, затем `git status --short` и `git diff -- main.py`. При содержательном изменении показать подготовку **только нужного файла** (`git add main.py`), проверить `git diff --cached -- main.py` и `git diff --cached --name-only`: если в staging находятся посторонние файлы, сначала выяснить их происхождение, чтобы не включить в commit. После этого выполнить `git commit -m "Check StudyHub foundation"` и отправить **ту же ветку и remote** ранее изученным способом (`git push`, если upstream настроен и разрешён учебным режимом; иначе — ранее разобранное явное указание remote/ветки). В менторском варианте придерживаться уже выбранного в 13.2 порядка develop/PR: после PR идентификатор опубликованного commit в main может отличаться от локального commit в develop. **Истина для clone — полный ID конечной опубликованной ветки на странице remote.** Если пусты и рабочий diff, и staged diff, не создавать искусственный commit: для той же ветки сравнить локальный `git rev-parse HEAD` с опубликованной версией, выяснить расхождение при его наличии. Теперь можно делать свежий clone.
- Условное исправление **после** clone: менять `main.py` в основном каталоге, сохранять, проверять и публиковать новую версию. В **проверочной** папке сначала установить путь, remote, ветку и `git status --short`; лишь при чистой копии без собственных commit и на той же ветке допустим `git pull --ff-only` — обновление без слияния расходящихся ветвей. Затем сравнить полный SHA с remote и повторить запуск. При чужих/своих изменениях в clone или отказе fast-forward **остановиться и установить причину**, не сбрасывать файлы и не выполнять destructive-команды.
- Пример и типичная путаница: push обновляет remote, но не переписывает файлы уже существующего clone автоматически. После push clone может остаться на старом commit до `git pull --ff-only`. Исправление только в clone меняет проверочную папку, но не передаваемую историю. Чистый status в основном каталоге также не доказывает, что нужный commit опубликован.
- Первое самостоятельное действие: для трёх состояний «изменения есть до первого clone / diff пуст / ошибка обнаружена после clone» ученик выбирает продолжение. В первом — публикация и затем clone, во втором — сверка опубликованной версии без искусственного commit, в третьем — исправление в основной папке, публикация и безопасное обновление существующей проверки. Критерий — каждое действие применено к правильной папке и объяснено условием, при котором оно нужно.
- Содержательная вставка для MAIN: развилка трёх состояний с предсказанием следующего шага и объяснением, почему `push` не обновляет второй рабочий каталог автоматически. Не дублировать вопросы раздела 01 о состоянии до push.
- Опора для повторного обращения: после публикации — тот же remote и выбранная ветка; перед `git pull --ff-only` — правильный путь, правильный upstream и чистая копия без своих commit; после обновления — совпадение полного commit ID и запуск из clone.
- Переход к следующему шагу: после сверки опубликованной версии можно точно назвать, что подтверждено передачей и что получает блок 4.

## 06. Граница между B3 и будущим Planner

- Что и зачем объяснить: блок 3 передаёт понятную основу для новой возможности, а не готовый пользовательский продукт. Четыре helper-функции и демо должны сохраниться; menu, `tasks`, `run`, readers и операции начнут появляться в следующем блоке.
- Механизм и порядок: отличить функцию подготовки/представления/суммы от будущего действия пользователя. У `calculate_study_minutes` нет команды `calc`; локальное исследование ввода из занятия 15 не превращает четыре компонента в постоянный интерфейс.
- Пример и типичная путаница: отсутствие команды `add` на этом переходе — ожидаемая граница, а не незаконченная ошибка занятия 15.1. Не дописывать меню «для полноты» перед передачей.
- Первое самостоятельное действие: ученик распределяет действия «очистить заголовок», «создать один словарь из переданных значений», «показать статус», «сложить длительности», «прочитать команду пользователя», «найти запись в общем списке» по двум колонкам B3/блок 4 и обосновывает спорный случай: отдельный `input` из занятия 15 ещё не делает программу с меню. Критерий — четыре функции B3 названы и ни `run`, ни рабочий `tasks` или сохранение между запусками не приписаны текущему проекту.
- Содержательная вставка для MAIN: сравнительная таблица «есть в `main.py` сейчас / появится в Planner» с самостоятельной сортировкой **разных** действий, а не повторным тестом Git-команд. После неё текстовая связка к финальной проверке на своём репозитории.
- Опора для повторного обращения: таблица «готово в B3 / появится в блоке 4»; сверять по фактическому `main.py`, а не по названию проекта.
- Переход к практике: проверить передачу на своём remote и показать, что именно получает следующий блок.

## 07. Что мы будем делать в практике

**Формат и исходная опора:** проект, **один основной локальный StudyHub и одна проверочная копия**. На входе ученик показывает работающий `main.py` с четырьмя функциями/демо, установленный Python 3.12, свой URL remote и ветку, где планирует опубликовать B3. Если этого нет, вернуться к недостающей практике занятий 12–15; подменять вход готовым чужим Planner нельзя. Исходный SHA ученика в доступных материалах не подтверждён. Обязательное действие — проверить и при необходимости компактно исправить демо, затем опубликовать основу и сделать **свежий** clone той же истории; обновление уже существующей копии понадобится только при обнаруженной после clone ошибке.

Практика даёт один проверенный B3 checkpoint и показывает полноту опубликованных файлов и запуск из другой рабочей копии на том же компьютере. Она не доказывает переносимость настройки на любую машину.

1. **Установить, что передаём (основной каталог):** ученик находит путь к собственному `main.py`, с помощью `git remote -v` и `git branch --show-current` проверяет свой remote и рабочую ветку, а на странице репозитория выбирает ту ветку, в которую будет опубликована готовая основа (при необходимости — через прежний порядок develop/PR). Записывает URL и точное имя ветки, проверяет наличие четырёх функций и отсутствие меню/пользовательских операций. Теория 01–03, 06. **Свой результат:** поясняет, почему «локально работает» ещё не равно «доступно в remote»; не выбирает автоматически имя ветки из примера.
2. **Самостоятельно проверить четыре договора и компактность демо (основной каталог):** ученик **до запуска предсказывает** ответы своих новых примеров и запускает четыре функции через знакомый демо-код или прежний способ исследования Python. Нужны разные случаи: пробелы и пустое название; два независимых словаря с `is_done=False`; оба текстовых состояния formatter без изменения словаря; несколько длительностей и пустой список без изменения входных значений. Избыточные временные `print` для проверки убрать из финального демо; оставить короткий пример применения без меню. Если демо уже компактно и договоры соблюдены, не портить его искусственной правкой. Теория 04. **Свой результат:** таблица «мой ввод → прогноз → наблюдение → совпало/нет» для всех четырёх функций и чистый `main.py`; ошибка исправлена **здесь**, до публикации.
3. **Опубликовать именно проверенную основу (основной каталог):** после сохранения и повторного запуска `main.py` ученик смотрит `git status --short`, рабочий и staged diff. Если есть содержательная правка, добавляет только нужный `main.py`, проверяет список staged-файлов, создаёт commit без посторонних изменений и отправляет его в прежний remote по выбранному режиму работы. Если **оба diff пусты**, commit ради отчёта не нужен: для той же ветки сверить `git rev-parse HEAD` с полным ID опубликованной основы; при несовпадении выяснить, где находится нужный commit. При менторском develop/PR сверять итоговый commit опубликованной ветки после PR, не предполагая равенства SHA develop и main. Теория 01 и 05. **Свой результат:** на странице remote видны URL, фактическая ветка и полный ID **проверенной** основы; незакоммиченные изменения не выданы за публикацию.
4. **Самостоятельно получить и проверить свежий clone (новый соседний каталог):** ученик выходит в родительскую папку основного проекта и убеждается, что имени `studyhub-check` ещё нет (иначе выбирает другое свободное имя). Выполняет `git clone <свой-URL> studyhub-check` для нужной ветки по умолчанию либо `git clone --branch <имя-нужной-ветки> <свой-URL> studyhub-check` для иной ветки; затем переходит в новую папку и проверяет путь, `git remote -v`, `git branch --show-current` и `git rev-parse HEAD`. Полный ID должен совпасть с опубликованным commit шага 3. Только теперь **из папки clone** запускает `main.py` установленным Python 3.12 (на Windows при наличии launcher — `py -3.12 main.py`; иначе после проверки `python --version` показывает 3.12 — `python main.py`). После запуска ученик **без редактирования clone** использует объяснённый в 04 режим `-i`, самостоятельно вводит новые аргументы для каждой функции, наблюдает возвращённые значения/неизменность входа и выходит через `exit()`. Теория 02–04. **Свой результат:** разные пути, одинаковые URL/ветка/полный commit ID, рабочий запуск и четыре договора на своих данных в clone; отдельно фиксируется, что незакоммиченные/игнорируемые локальные файлы в clone не попали.
5. **Принять результат и вернуться к основному каталогу:** ученик объясняет, почему совпадение имён каталогов не является проверкой, что именно доказала повторная загрузка с remote **на этом компьютере** и почему она не подтверждает запуск на любом компьютере без настройки. По фактическому `main.py` раскладывает компоненты B3 и функции будущего Planner (menu, `run`, пользовательский `tasks`, операции). Теория 01, 06. **Свой результат:** список четырёх существующих договоров, список отсутствующих операций и путь основного проекта, в котором продолжится блок 4.

**Если обнаружен дефект уже после clone:** ученик не редактирует проверочную копию и не удаляет папки. Вносит исправление в основной `main.py` → снова проверяет договоры → публикует новый commit → убеждается, что в clone правильные путь/remote/ветка и нет своих изменений/commit → при отставании обновляет `git pull --ff-only` → сверяет новый полный SHA → повторяет запуск. Если fast-forward невозможен или копия не чистая, фиксирует несовпадение и останавливает обновление. Это **условная ветка**, а не обязательный второй цикл для каждого ученика (теория 05).

**Приёмка проекта:** один опубликованный B3 commit в прежней истории, компактный `main.py`, самостоятельно проверенные четыре договора на различающихся данных, новый clone из фактической ветки с совпадающим полным SHA и успешным запуском системным Python 3.12. Не принимать только скриншот `git clone`, рассказ без запуска или четыре ответы по старым данным демо. Проверка прежних возможностей сопровождает передачу и не заменяет её; при неподтверждённой A сначала закончить подготовительные практики. Для MAIN между двумя соседними читаемыми абзацами помещать по смыслу визуал, прогноз или разбор реального результата: максимум два абзаца подряд без содержательной вставки, но без механических карточек после каждой фразы и без повторных карточек подряд.
