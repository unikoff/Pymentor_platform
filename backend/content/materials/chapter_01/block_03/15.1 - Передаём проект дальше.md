## 00. Вступление

Код может работать в папке автора, но этого ещё недостаточно, чтобы передать его дальше. Следующий шаг потребует опереться на сохранённые функции, поэтому сначала нужно проверить именно опубликованную основу и увидеть, что её можно получить заново.

1. **Точка старта:** по плану есть один локальный StudyHub с четырьмя функциями и коротким демо; Git уже использовался для сохранения и отправки изменений.
2. **Новый вопрос:** какую опубликованную ветку получает clone и как проверить, что он содержит последнюю переданную основу?
3. **Результат:** clone выбранной ветки запускает опубликованную основу из соседнего каталога на этом же компьютере, а её готовые и будущие части ясно разделены.

Сначала различим основной каталог и проверочную копию, выберем реальную опубликованную ветку, затем сверим версию и запустим её. Если проект исправлялся, обновим уже существующий clone. В конце ученик объяснит, что подтверждает эта локальная проверка и что получает следующий блок. Это проверка передачи результата, а не сборка Planner.

## 01. Что доказывает независимая копия

- Что и зачем объяснить: успешный запуск в основном каталоге подтверждает только этот локальный файл и выбранный способ запуска. Clone из remote проверяет полноту опубликованных файлов и их запуск из другой рабочей копии на том же компьютере. Это помогает отличить работающую локальную правку от опубликованной версии; такая проверка не доказывает установку или запуск проекта на любом другом компьютере.
- Механизм и порядок: изменения основного файла сначала должны попасть в сохранённый commit, а commit — в нужную ветку remote. Clone получает опубликованную историю; незакоммиченный текст и локальные игнорируемые файлы в неё не входят. Пустой `git status` в основном каталоге сам по себе не доказывает, что нужная версия отправлена.
- Пример и типичная путаница: локальный `main.py` уже запускается после правки, но remote всё ещё указывает на предыдущий commit. Новый clone закономерно получает предыдущий вариант. Не объяснять это как случайную потерю файла при копировании: в clone попала именно опубликованная версия.
- Первое самостоятельное действие: до проверки ученик предсказывает, какая из двух версий окажется в clone — сохранённая в remote или последняя незакоммиченная правка. После разбора называет, какой результат подтвердит каждую версию, и ограничивает вывод этой рабочей копией на данном компьютере.
- Опора для повторного обращения: «что доказывает запуск» — путь проверочной папки, commit, полученный из remote, и поведение запущенного файла; локальная правка без commit в это доказательство не входит.
- Переход к следующему шагу: чтобы интерпретировать результат, нужно не перепутать две папки и знать, какую удалённую историю проверяем.

## 02. Роли основного каталога и clone

- Что и зачем объяснить: основной каталог остаётся местом разработки. Свежий clone — отдельная проверочная копия с собственным путём и настроенным `origin`; команды запуска из неё относятся к файлам clone, а не к основному проекту.
- Механизм и порядок: перед получением копии проверить адрес своего remote и имя ветки, где опубликован нужный checkpoint. Обычный `git clone <адрес-remote>` получает ветку, которую сам репозиторий назначил веткой по умолчанию; если checkpoint находится в другой ветке, выбрать её по фактическому имени в селекторе веток репозитория и передать это имя как `--branch <точное-имя-ветки>` при клонировании. Не подставлять `main` или другое имя только потому, что оно встречалось в примере. Затем выбрать свободный соседний каталог и проверить текущий путь терминала и целевой путь. Не выбирать существующую папку с пользовательскими файлами и не очищать основной каталог. Clone не повторяет `git init` поверх полученной истории.
- Пример и типичная путаница: два окна терминала показывают похожее имя репозитория, но находятся в разных каталогах. Само имя окна не показывает, какой файл запускается. Проверяем путь и историю каждой копии отдельно.
- Первое самостоятельное действие: по странице своего репозитория ученик находит ветку по умолчанию и ветку с требуемым checkpoint, если это разные ветки; затем по двум путям и адресу `origin` определяет, где разрешено исправлять проект, а где только проверять. Критерий — он выбирает ветку по фактическим данным и указывает основной каталог без догадки по названию папки.
- Опора для повторного обращения: две роли и два пути; после каждого перехода в терминале заново установить, какой `main.py` будет запущен и какой remote относится к этому clone.
- Переход к следующему шагу: после выбора безопасного места и точной ветки нужно сверить, что clone получил требуемый опубликованный commit, а не просто похожий репозиторий.

## 03. Как выбрать опубликованную версию

- Что и зачем объяснить: проверяется личный StudyHub, который ученик развивал по текущему маршруту, и commit, опубликованный для передачи. Канонический репозиторий или более поздняя версия проекта могут уже содержать материалы следующего блока.
- Механизм и порядок: сначала в основном каталоге установить, какой commit отправлен и в какую ветку. Для обычного clone сверить ветку по умолчанию на странице репозитория; если нужен checkpoint из другой ветки, выбрать её по точному отображаемому имени. Затем сопоставить публикацию и историю clone по адресу remote, имени ветки и полному идентификатору commit. Нужна одна и та же версия проекта, а не только совпадение названия файла или сообщение об успешном клонировании.
- Пример и типичная путаница: исторический snapshot `383c212b` содержит все операции Planner и потому представляет более поздний результат курса. Он помогает понять итоговые договоры, но его нельзя подменять им как ученический B3: это пропустило бы работу блока 4.
- Первое самостоятельное действие: ученик выбирает из двух описаний, какое относится к опубликованной основе B3, а какое — к будущему полному Planner, находит целевую ветку по её фактическому имени и объясняет, какой remote нужно проверять. Результат — выбран собственный проект и нужный checkpoint, а не чужой или будущий код.
- Опора для повторного обращения: адрес remote, ветка и идентификатор отправленного commit должны относиться к одной истории. Если они не совпадают, остановить вывод о передаче и сначала найти расхождение.
- Переход к следующему шагу: сверенная версия становится основанием для запуска и проверки четырёх уже созданных компонентов.

## 04. Что означает «основа запускается»

- Что и зачем объяснить: сам факт старта не заменяет проверку договоров. В clone нужно запустить `main.py` установленным Python 3.12 и увидеть ожидаемое демо; затем проверить, что каждый из четырёх компонентов сохранил свою ответственность. Этот результат относится к опубликованным файлам и второй рабочей копии на том же компьютере; он не проверяет установку, настройку и запуск на незнакомом компьютере.
- Механизм и порядок: `normalize_title(title)` удаляет крайние пробелы, сохраняет регистр и внутренние пробелы, допускает пустой результат. `create_task(task_id, title, priority)` возвращает отдельный словарь с переданными полями и `is_done=False`, не читая ввод, не выбирая id и не добавляя запись. `format_task(task)` возвращает строку вида `[id] title | приоритет: priority | состояние`, где состояние — «не завершена» или «выполнена»; функция не печатает и не меняет задачу. `calculate_study_minutes(durations)` возвращает сумму, для пустого списка — ноль, и не меняет вход.
- Пример и типичная путаница: печать результата formatter — действие демо, а не часть самой функции; создание записи не добавляет её в общий список; сумма минут не становится командой Planner. Проверка должна наблюдать назначенный результат и отсутствие постороннего эффекта.
- Первое самостоятельное действие: после краткого восстановления договора ученик сам выбирает новые данные для четырёх функций. Проверка включает обычный случай и различающий случай там, где он важен: пустое/обрезаемое название; два созданных словаря, которые остаются отдельными; оба состояния карточки; сумма одного и нескольких значений и пустой список длительностей. Критерий — каждый результат соответствует роли функции, входные данные не испорчены.
- Опора для повторного обращения: у каждой функции восстановить «вход → результат → чего функция не делает». Не использовать старые данные демо как единственное доказательство.
- Переход к следующему шагу: договоры проверяются в новом каталоге, чтобы запуск подтвердил опубликованную основу, а не только основной рабочий файл.

## 05. Исправление и повторная публикация

- Что и зачем объяснить: если проверка выявила дефект или демо не даёт увидеть нужный результат, исправлять нужно основной проект. После публикации существующий проверочный clone обновляется; удалять и создавать его заново не требуется.
- Механизм и порядок: последнюю правку внести в основном каталоге и сохранить файл; запустить `main.py`; затем посмотреть `status` и diff. Если diff содержит нужное содержательное изменение, подготовить только его, создать commit и отправить его в тот же remote и выбранную ветку. Если diff пуст, не придумывать правку и не создавать искусственную правку или commit: сверить полный идентификатор текущего commit с уже опубликованным commit выбранной ветки; дальше проверять именно эту опубликованную версию. Только после этого решить, нужно ли менять проверочную копию. Внутри существующего clone проверить путь, `origin`, ветку и чистое состояние; если он отстаёт от выбранной удалённой ветки и не имеет своих изменений или отдельных commit, выполнить `git pull --ff-only`. Эта команда обновляет существующую копию только прямым продвижением по той же истории. Затем сверить полный идентификатор полученного commit и запустить файл из clone. Если clone содержит изменения, свои commit или другая история, не перезаписывать его и не выполнять pull вслепую — сначала выяснить расхождение.
- Пример и типичная путаница: push обновляет remote, но не переписывает файлы уже существующего clone автоматически. После push clone может остаться на старом commit до `git pull --ff-only`. Исправление только в clone меняет проверочную папку, но не передаваемую историю. Чистый status в основном каталоге также не доказывает, что нужный commit опубликован.
- Первое самостоятельное действие: на описании с новой правкой ученик раскладывает шаги в порядке «последняя правка → сохранение файла → запуск → diff → commit/push при содержательном diff → fast-forward обновление существующего clone». Для пустого diff он выбирает проверку опубликованного commit без искусственной правки. Критерий — не перепутаны исходная и проверочная папки, а clone обновлён только при чистой линейной истории.
- Опора для повторного обращения: после публикации — тот же remote и выбранная ветка; перед `git pull --ff-only` — правильный путь, правильный upstream и чистая копия без своих commit; после обновления — совпадение полного commit ID и запуск из clone.
- Переход к следующему шагу: после сверки опубликованной версии можно точно назвать, что подтверждено передачей и что получает блок 4.

## 06. Граница между B3 и будущим Planner

- Что и зачем объяснить: блок 3 передаёт понятную основу для новой возможности, а не готовый пользовательский продукт. Четыре helper-функции и демо должны сохраниться; menu, `tasks`, `run`, readers и операции начнут появляться в следующем блоке.
- Механизм и порядок: отличить функцию подготовки/представления/суммы от будущего действия пользователя. У `calculate_study_minutes` нет команды `calc`; локальное исследование ввода из занятия 15 не превращает четыре компонента в постоянный интерфейс.
- Пример и типичная путаница: отсутствие команды `add` на этом переходе — ожидаемая граница, а не незаконченная ошибка занятия 15.1. Не дописывать меню «для полноты» перед передачей.
- Первое самостоятельное действие: ученик называет четыре готовых компонента и по одному примеру того, что появится позднее. Критерий — он не приписывает текущей версии `run`, меню, список введённых задач или сохранение между запусками.
- Опора для повторного обращения: таблица «готово в B3 / появится в блоке 4»; сверять по фактическому `main.py`, а не по названию проекта.
- Переход к практике: проверить передачу на своём remote и показать, что именно получает следующий блок.

## 07. Что мы будем делать в практике

**Формат и исходная опора:** проект. Начинаем с основного локального StudyHub, который по предыдущим паспортам должен содержать четыре компонента и компактное демо. Перед работой устанавливаем путь, remote и нужную опубликованную ветку: обычный clone берёт ветку по умолчанию, при выборе другой используем её фактическое имя, не образец `main`. Для проверки используем свободную соседнюю папку; после публикации возможной правки обновляем этот же clone. Исходный SHA ученика в доступных материалах не подтверждён.

Практика даёт один проверенный B3 checkpoint и показывает полноту опубликованных файлов и запуск из другой рабочей копии на том же компьютере. Она не доказывает переносимость настройки на любую машину.

1. **Уточнить опубликованную основу и получить проверочный clone:** в репозитории ученик находит фактическую ветку по умолчанию и опубликованный B3 commit; если целевой commit находится в другой ветке, выбирает её по имени, показанному в селекторе веток репозитория. Проверяет путь основного каталога, выбирает свободную соседнюю папку и клонирует свой remote: без параметра ветки для ветки по умолчанию либо с `--branch <точное-имя-ветки>` для другой опубликованной ветки. Теория 01–03. Наблюдаемый результат: известны адрес, имя ветки, полный commit ID и два разных пути.
2. **Проверить и при необходимости исправить основную версию:** в основном каталоге ученик сверяет четыре договора на новых данных, при необходимости сокращает только демо или исправляет обнаруженный дефект, не добавляя будущие операции. Последнюю правку сохраняет, запускает основной `main.py`, затем смотрит `status` и diff. Теория 04–05 и прежние навыки запуска. Наблюдаемый результат: основной проект запускается и результаты функций соответствуют договорам.
3. **Опубликовать только содержательное изменение:** если diff показывает нужную правку, ученик подготавливает только изменённый файл, создаёт commit и отправляет его в ту же remote-ветку. Если diff пуст, он не придумывает изменение и не создаёт искусственный commit, а сверяет полный ID уже существующего commit с публикацией выбранной ветки. Теория 05. Наблюдаемый результат: известно, какой commit должен получить clone; push не считается доказательством запуска.
4. **Обновить существующий проверочный clone и запустить его:** ученик возвращается в уже созданную соседнюю копию, сверяет путь, remote, выбранную ветку и чистое состояние; если она отстаёт, использует `git pull --ff-only`, не пересоздавая каталог. Затем сверяет полный ID commit и запускает `main.py` установленным Python 3.12. Теория 02–05. Наблюдаемый результат: копия содержит требуемый опубликованный commit и выполняет четыре договора. Если clone не чистый или история расходится, он фиксирует причину и не перезаписывает данные.
5. **Объяснить передачу и вернуться к основному каталогу:** ученик объясняет, почему clone не взял незакоммиченное/игнорируемое, что доказывает проверка на этом компьютере и чего она не доказывает. Теория 01 и 06. Наблюдаемый результат: названы четыре компонента B3, а menu, `run`, `tasks` и пользовательские операции отнесены к следующему блоку; дальнейшая работа продолжается в основном каталоге.

Порядок сохраняет одну основную историю и одну проверочную копию. При содержательном diff цепочка — последняя правка → сохранение файла → запуск → diff → commit/push → обновление существующего clone → повторный запуск. При пустом diff нового commit нет: сверяется опубликованный commit и по необходимости fast-forward-обновляется clone. Проверка прежних возможностей сопровождает передачу и не заменяет её. Итог подтверждает B только если совпали источник, выбранная ветка, commit, запуск и четыре договора; успешный запуск не доказывает, что проект запустится на любом другом компьютере без подготовки. Если входная опора занятий 12.1–15 не подтверждена, зависимую проверку нельзя объявлять выполненной без отдельного объяснения недостающего шага.
