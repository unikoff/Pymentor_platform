## 00. Вступление

По плану 12.1 у нас есть рабочий файл в собственном clone. Сохранение в редакторе меняет этот файл, но ещё не создаёт запись в истории Git. Сегодня мы научимся видеть разницу и выбирать содержимое первой локальной версии.

1. **Точка старта:** планируемый результат занятия 12.1 — собственный clone, работающий `main.py`, `.gitignore` и ещё пустая локальная история; наличие проверим перед практикой.
2. **Новый вопрос:** как проверить, что именно попадёт в первый снимок проекта, и сохранить его локально?
3. **Результат:** проверенные `main.py` и `.gitignore` находятся в истории Git на текущей ветке; отправка на GitHub остаётся следующим шагом.

Поскольку сохранённый текст сам не выбирает себя для истории, между ним и commit понадобится промежуточная подготовка. Сначала научимся распознавать три состояния и сравнивать их, затем выберем два файла, проверим авторство и запишем результат.

## 01. Сохранение файла и версия в истории — разные действия

- **Вопрос и механизм:** почему `Ctrl+S` в редакторе не сохраняет историю? Редактор записывает текущие байты на диск; Git ведёт локальную историю выбранных снимков, а GitHub хранит отдельную удалённую копию. Между рабочим файлом и новым commit есть выбор содержимого для записи. Слово «commit» обозначает локальную запись, а не действие «опубликовать».
- **Независимый пример:** человек сохранил изменённый `notes.txt`, закрыл редактор, снова открыл его — текст есть на диске, но новая запись Git от этого не возникла. Даже если `notes.txt` был сохранён десять раз, количество commit от этого не меняется. Не использовать `main.py` в качестве решённого примера будущей практики.
- **Первое применение:** из трёх карточек событий («сохранил файл», «выбрал версию для следующего снимка», «записал commit») ученик сам выстраивает хронологию и для каждого называет **где** теперь находится результат. Различающий случай: сохранённый файл есть, а истории ещё нет; ответ «уже в GitHub» ошибочен.
- **Учебная вставка для MAIN:** временная дорожка `диск → подготовлено → локальная история → GitHub (позже)`; ученик указывает, после какого шага появилась новая запись в истории. Последняя стрелка визуально отнесена к занятию 13.1.
- **Опора и переход:** сохранение отвечает за рабочий файл; подготовка отвечает за выбор будущего снимка; commit — за историю. Чтобы различать их на практике, разберём промежуточное состояние.

## 02. Рабочая папка, index и локальный commit

- **Механизм:** рабочая папка (working tree) содержит файлы, которые ученик читает и сохраняет; index (staging area) содержит подготовленную **версию содержимого** для следующего commit; commit фиксирует это подготовленное состояние в локальной истории. Index не является второй папкой с файлами, которую нужно открывать в редакторе. Подготовка не запускает программу и не создаёт commit.
- **Новый и отслеживаемый путь:** файл, которого ещё нет в index или истории, — `untracked`; после подготовки он уже известен index, после commit его версия есть в истории. Если ранее зафиксированный файл изменён, его новое сохранённое содержимое тоже не попадёт в следующий commit без подготовки. `tracked` не означает «каждое изменение сохраняется автоматически».
- **Независимый пример:** `notes.txt` на диске содержит «план А». Подготовили эту версию, затем в редакторе заменили строку на «план Б» и сохранили: рабочая папка показывает Б, index всё ещё хранит А. Если сейчас записать commit без повторной подготовки, снимок содержит А. Показать, где аналогия «лоток для выбранных листов → архив» помогает, а где заканчивается: Git фиксирует содержимое файлов, не перемещает их между физическими папками.
- **Первое применение:** на схеме двух версий ученик предсказывает, какая строка попадёт в commit и что останется в рабочей папке, после чего исправляет ошибочный прогноз «последний сохранённый текст попадёт автоматически».
- **Учебная вставка для MAIN:** три колонки `рабочая папка | index | история` с двумя разными строками виртуального `notes.txt`; ученик отмечает, какую колонку меняет сохранение и какую — повторная подготовка. После схемы пояснить, что именно делает staging необходимым.
- **Опора и переход:** для будущего commit важно содержимое index, а не только открытого файла. Теперь научимся читать состояние безопасными командами.

## 03. Статус, новые файлы и границы diff

- **Механизм и синтаксис до применения:** из терминала **в каталоге своего clone** команда `git status` показывает ветку и группы путей (в том числе `Untracked files`, позднее `Changes to be committed`); она ничего не добавляет. `git diff` без дополнительных флагов сравнивает содержимое отслеживаемых файлов в рабочей папке с index и не меняет их. Сам файл читают в редакторе; статус сообщает про его положение относительно Git, а diff — про различия содержимого.
- **Независимый пример:** в условном репозитории новый `notes.txt` содержит `план А`, но не подготовлен. Статус показывает его как `untracked`, обычный `git diff` не выводит строки этого нового файла. Это свойство сравнения, а не признак пустого или удалённого файла. Для уже подготовленного файла с новым сохранением обычный diff, напротив, может показать изменение после staging; связь с двумя версиями из раздела 02.
- **Первое применение:** ученику даны вывод с `Untracked files: notes.txt` и пустой `git diff`. Он выбирает способ проверить сам текст и объясняет, почему пока нельзя судить о будущем снимке. Затем для изменённого **после** подготовки `notes.txt` прогнозирует, какая из двух версий может появиться в обычном diff.
- **Учебная вставка для MAIN:** рядом два результата `git status` и `git diff` для одного состояния; сначала прогноз («файл пуст?»), затем пояснение роли каждой команды. Не ставить вторую карточку с той же проверкой.
- **Опора и переход:** `git status` — «в каком состоянии путь?»; `git diff` — «какие изменения на диске ещё не совпадают с index?». Перед чтением подготовленного снимка нужно явно выбрать файлы.

## 04. Подготовка только нужных файлов

- **Механизм до команды:** `git add -- <путь>` помещает текущую сохранённую версию указанного файла в index. `--` отделяет имена путей от опций команды; команда с перечисленными путями безопаснее широкого выбора, когда каталог ещё не проверен. В основном clone ученик **сам составляет** команду по образцу для двух файлов `main.py` и `.gitignore`; никаких `git add .` и `git add -A` для первого снимка.
- **Независимый пример:** есть `notes.txt` (нужен) и `scratch.txt` (временный). Выбрать `git add -- notes.txt` и предсказать: первый путь появится в группе подготовки, второй не попадёт в index. Это выбор состава, а не автоматическое перемещение всех файлов из папки.
- **Границы `.gitignore`:** правила `__pycache__/` и `*.pyc` из 12.1 помогают Git не предлагать соответствующие ещё не отслеживаемые артефакты. Они **не удаляют файлы с диска**, не защищают уже отслеживаемые пути и не заменяют просмотр index. Токены, пароли, личные данные и лишние каталоги также не включают, даже если их нет в `.gitignore`.
- **Первое применение:** на схеме с двумя нужными и одним временным файлом ученик выбирает точные аргументы `git add` и предсказывает, какие пути после этого покажет `git status`. В собственном clone проверяет получившуюся группу `Changes to be committed`. Если в ней есть неожиданный путь — до commit перейти к исправлению из раздела 05.
- **Учебная вставка для MAIN:** разбор выбора `три пути → два аргумента git add → два пути в index` с самостоятельным решением о временном файле; итог связать с тем, что `git status` показывает пути, но ещё не проверяет строки будущего снимка.
- **Опора и переход:** готовим **явно перечисленные** пути, затем независимо сверяем список и содержимое index. Теперь можно посмотреть, что Git приготовил для записи.

## 05. Staged diff показывает будущий снимок

- **Механизм и команды:** `git diff` сравнивает рабочие изменения с index, а `git diff --staged` (`--cached` — эквивалентное имя опции) сравнивает index с последним commit. В clone без истории сравнение staged diff фактически идёт с пустым начальным состоянием, поэтому после `git add` видны все новые строки. `git diff --staged --name-only` выдаёт только имена подготовленных путей, а полный `git diff --staged` — их добавляемые строки (`+`) и сведения о файлах. Обе команды только читают состояние.
- **Независимый пример со сдвигом версии:** в `notes.txt` записано «А», он подготовлен, затем на диске строка заменена на «Б». Staged diff показывает «А» как содержимое будущей записи, обычный diff — изменение от подготовленного «А» к рабочему «Б». После нового `git add -- notes.txt` staged diff уже показывает «Б». Объяснить, почему одинаковый файл на диске и в index — следствие явной подготовки, а не автоматическая синхронизация.
- **Безопасная коррекция отдельного случая:** если **до первого commit** по ошибке подготовлен посторонний **новый** `scratch.txt`, предварительно убедиться, что это действительно новый путь, и выполнить `git rm --cached -- scratch.txt`. Команда убирает его из index, **оставляет файл на диске**. После этого `git status` показывает его как untracked (если он не игнорируется), а `git diff --staged --name-only` больше его не перечисляет. Не применять рецепт бездумно к уже отслеживаемым файлам и не вводить в этот урок общие средства отката истории.
- **Первое применение:** на двух состояниях виртуального `notes.txt` ученик выбирает, какой diff покажет «А» и какой — «Б», затем указывает, какую команду повторить, чтобы подготовить «Б». После объяснения самостоятельно проверяет на своём clone **список и текст** staged-файлов; если есть лишний новый путь, выбирает адресную коррекцию и повторно проверяет две команды.
- **Учебная вставка для MAIN:** одна схема `HEAD (пусто) ← staged → рабочая папка` с двумя направленными сравнениями и прогнозом строк; рядом чтение небольшого реального staged diff с отметкой «имена»/«содержимое». Вывод после вставки: перед commit проверяем и **что**, и **какие строки** записываем.
- **Опора и переход:** `status` и `--name-only` отвечают за состав; `git diff --staged` — за точное содержимое будущего снимка. Когда оба соответствуют ожиданию, остаются подпись автора и короткое сообщение.

## 06. Авторство и сообщение commit

- **Механизм и команды до commit:** Git добавляет в запись сведения об авторе (имя и email) и текст сообщения. Внутри clone команды `git config --get user.name` и `git config --get user.email` показывают эффективные значения; отсутствие вывода означает, что значение нужно задать до commit. Если нужно, ученик задаёт **свои выбранные данные** локально для этого репозитория командами `git config --local user.name "<своё имя>"` и `git config --local user.email "<свой email>"`, затем повторяет проверку. `--local` затрагивает настройки текущего репозитория, не файлы программы и не удалённый аккаунт. Угловые обозначения — места для своих значений, не буквальный ввод.
- **Независимый пример и граница:** два человека могут указать одинаковое имя автора в своих локальных настройках; это не делает их одним аккаунтом GitHub и не подтверждает право на push. Авторство commit, вход на сайт и разрешение писать в чужой remote — разные проверки. Секреты, токены и пароли в имя, email и сообщение не вставляют.
- **Сообщение:** коротко сообщает, **что действительно зафиксировано**, например `Add first notes` для виртуального `notes.txt`; не обещает уже работающие функции будущего проекта. Ученик сам выбирает собственное сообщение для `main.py` и `.gitignore`, без продиктованного единственного ответа.
- **Первое применение:** среди «автор указан», «автор вошёл в GitHub», «автор имеет право push» ученик отмечает, какое заключение позволяют сделать две команды `git config --get`, а какое они не доказывают. Затем проверяет собственные значения и формулирует сообщение именно для проверенного снимка.
- **Учебная вставка для MAIN:** сравнительная таблица `подпись commit | вход в GitHub | право на конкретный remote` с одним вопросом «что подтверждает user.email?»; после ответа вернуть ученика к команде проверки в его clone.
- **Опора и переход:** имя/email — локальные метаданные авторства, сообщение — смысл версии; авторизация относится к 13.1. Теперь все предпосылки commit подготовлены.

## 07. Создать и найти первый локальный commit

- **Механизм и порядок:** после запуска программы, проверки списка и строк index и настройки автора команда `git commit -m "<своё краткое сообщение>"` сохраняет **текущий index** как локальный commit. `-m` передаёт сообщение прямо в команде. Нельзя считать сохранение успешным по одному факту ввода команды: Git может сообщить об ошибке или отсутствии подготовленных изменений. Название ветки не угадывать; читать его через `git branch --show-current` в своём clone (это имя текущей ветки, включая ветку до первого commit).
- **Наблюдение после успеха:** `git log -1 --oneline` показывает последнюю локальную запись и её сокращённый идентификатор; `git show --format=short HEAD` позволяет сверить автора, имена и добавленные строки именно записанного снимка; `git status` показывает оставшиеся рабочие/staged изменения либо чистое состояние. Эти команды чтения истории используют **после** удачного первого commit: раньше `HEAD` ещё не ссылается на созданную запись. Затем снова запустить `main.py`, чтобы проверить, что версия проекта работает.
- **Независимый различающий случай:** один ученик сохранил `notes.txt`, но не подготовил; другой подготовил старую строку, потом сохранил новую без повторного `git add`. Предложить предсказать, почему первому нечего записывать, а у второго в снимке будет старая строка; исправление выводится из 02 и 05, до запуска команды commit.
- **Первое применение:** по четырём коротким результатам (`status` перед записью, staged diff, сообщение об успехе, `log/show` после записи) ученик сам устанавливает, где именно появилась версия, что в неё попало и какой вывод **не** следует делать о GitHub. При ошибке «nothing to commit» возвращается к статусу и проверке index, а не повторяет commit вслепую.
- **Учебная вставка для MAIN:** короткая трасса `подготовленные два пути → commit с сообщением → HEAD в текущей ветке → log/show`, ученик находит момент изменения истории; следующая фраза разделяет локальную запись и будущий push. Не дублировать отдельной карточкой вопрос «commit = push?».
- **Опора и переход к практике:** порядок `сохранить → запустить → git status / git diff → git add нужные пути → git diff --staged → проверить автора → git commit → git log / git show / git status → запустить`. Если исходник менялся **после** staging, сначала повторить подготовку и проверку, затем commit. Все команды выполняются в **одном** clone.

## 08. Что мы будем делать в практике

**Обязательный формат:** проектная ручная практика на **основном локальном StudyHub clone** из 12.1; никакого второго учебного репозитория и новой функции Python. Исходные `main.py` с Hello world и `.gitignore` ожидаются по паспорту, но фактически подтверждаются самим учеником. Для запуска используется та же уже проверенная в 12.1 команда системного Python 3.12, без новой настройки окружения.

Практика постепенно снимает подсказки: сначала ученик **диагностирует** состояние, затем **сам выбирает** пути и сверяет содержимое index, после этого **сам принимает решение**, готов ли снимок к commit, и подтверждает результат в истории. Успех каждого шага виден сразу; одно выполненное `git commit` без проверки содержимого B не доказывает.

1. **Восстановить исходную опору (A → вход).** Вход: собственный clone, `main.py`, `.gitignore` из B занятия 12.1; опоры — 12.1 и разделы 01–03. Самостоятельно: открыть терминал в каталоге **этого** clone, убедиться, что файлы сохранены, прочитать их содержимое и два правила `.gitignore`; выполнить `git status` и `git branch --show-current`, запустить `main.py` ранее проверенным способом. Объяснить, почему новые файлы могут быть `untracked`, а обычный `git diff` пуст, хотя Hello world существует на диске. **Локальный критерий:** вывод программы соответствует тексту, статус показывает реальное исходное состояние, ветка названа из вывода, а локальных commit пока нет. Если обнаружен другой каталог, файл отсутствует, программа не запускается или история уже заполнена — не перезаписывать и не делать «ещё один первый commit»; восстановить подходящий вход занятия 12.1. **Куда вернуться:** 01–03 и паспорт/практика 12.1.
2. **Самостоятельно выбрать и проверить будущую версию (главное новое действие).** Вход: успешный шаг 1 и объяснения `git add`, `.gitignore`, обоих diff из разделов 04–05. Объект: только две сохранённые версии `main.py` и `.gitignore` в этом clone. Самостоятельно: **составить** команду `git add` с точными именами двух путей (пример синтаксиса в 04), выполнить её; затем прочитать `git status`, `git diff --staged --name-only` и **полный** `git diff --staged`. Назвать **каждый путь и важные добавленные строки**, убедиться, что отсутствуют `__pycache__/`, `*.pyc`, временные данные и секреты; объяснить, что обычный `git diff` проверяет другое сравнение. **Локальный критерий:** в index ровно два нужных пути, а их подготовленные строки соответствуют проверенному работающему файлу и правилам игнорирования. Если ученик менял файл **после** staging, он самостоятельно указывает, какой из diff покажет расхождение, заново готовит изменённый путь и проверяет оба вида diff перед дальнейшим шагом. **Куда вернуться:** различие версий в 02, команды 04–05.
3. **Отловить лишнее без потери файла (различающий случай).** Вход: результат шага 2; в основном проекте **не требуется специально создавать** лишний файл. Дано условие: до самого первого commit случайно подготовлен новый `scratch.txt`, которого нет в истории; в status он среди `Changes to be committed`. Ученик самостоятельно выбирает объяснённую в 05 безопасную адресную операцию, прогнозирует состояния **на диске** и **в index** и на учебной схеме отмечает их до/после. Если в **его реальном** index уже есть такой посторонний новый файл, после проверки его природы применяет `git rm --cached -- <имя именно этого файла>` и снова читает статус/список staged; если лишнего файла нет, оставляет проект без искусственной ошибки. **Локальный критерий:** имя лишнего пути исключено из будущего снимка, а файл на диске остался; два обязательных пути по-прежнему staged. **Различающий вывод:** `.gitignore` не отменяет уже выполненный `git add`; команда для нового файла до первого commit не считается универсальным откатом. **Куда вернуться:** 04–05.
4. **Создать ровно один локальный commit и доказать B.** Вход: index из шага 2 (с поправкой шага 3), успешный запуск и разделы 06–07. Самостоятельно: проверить `git config --get user.name` и `git config --get user.email`, при отсутствии/неверных значениях настроить **свои** данные локально способом из 06; придумать краткое сообщение о реальных двух файлах; ещё раз сверить `git diff --staged`, выполнить `git commit -m "<своё сообщение>"` (подставить своё сообщение без угловых обозначений). После успешной записи прочитать `git log -1 --oneline`, `git show --format=short HEAD`, `git branch --show-current`, `git status` и повторно запустить `main.py`. **Локальный критерий:** в истории есть один первый commit с ожидаемым автором, двумя файлами и ранее сверенными строками, текущая ветка названа по факту, после проверки нет неожиданных staged-изменений, Hello world по-прежнему запускается. Если commit отказал из-за отсутствия автора/пустого index, сначала прочитать причину и вернуться к соответствующей настройке или подготовке; не повторять команду наугад. **Куда вернуться:** 05–07.

**Смысл связанного списка:** статус и запуск из шага 1 доказывают пригодность входа A; список и строки index из шага 2 доказывают осознанный выбор; различающий случай 3 проверяет, что ученик понимает сохранность диска отдельно от staging; лишь после этого шаг 4 создаёт и независимо подтверждает B. Для MAIN: вывести на одной читаемой итоговой схеме четыре состояния «файл на диске / index / первый commit / GitHub пока без новой версии» и попросить ученика объяснить, какое наблюдение доказывает каждое; не выстраивать серию декоративных карточек и не допускать более двух читаемых абзацев подряд без осмысленной схемы/сравнения/действия.

**Итог и передача:** ученик без готового набора команд может назвать файлы и строки **подготовленного** снимка, найти их в **созданном** commit, назвать автора и фактическую ветку, показать запуск. Он отдельно произносит, что проверил локальную историю, **не** наличие версии на GitHub. Именно этот commit и ветка — вход занятия 13.1, где будут проверяться `origin`, авторизация, право записи и публикация.
