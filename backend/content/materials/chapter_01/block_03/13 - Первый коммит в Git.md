## 00. Вступление

В занятии 12.1 ученик получил работающий локальный файл, но сохранение файла ещё не оставляет его версию в истории. Сегодня мы разберём, как выбрать конкретные файлы и записать их состояние в Git на компьютере.

1. **Точка старта:** планируемый результат занятия 12.1 — clone, работающий `main.py` и `.gitignore` без commit.
2. **Новый вопрос:** как проверить, что именно попадёт в первый снимок проекта, и сохранить его локально?
3. **Результат:** проверенные `main.py` и `.gitignore` находятся в истории Git на текущей ветке; отправка на GitHub остаётся следующим шагом.

Сначала различим рабочие файлы и историю, затем разберём промежуточный index, подготовим нужные пути и прочитаем снимок до записи. Это позволяет создать commit осознанно и не спутать локальное сохранение с публикацией.

## 01. Сохранение файла и версия в истории — разные действия

- Что и зачем объяснить: сохранение меняет файл на диске; Git хранит версии в истории репозитория; GitHub размещает удалённую копию истории. Для результата этого урока нужны только локальные действия.
- Механизм и порядок: сначала существующий файл сохранён и запускается, затем выбранное содержимое подготавливается, после проверки создаётся commit. Каждый шаг меняет отдельное состояние.
- Пример и типичная путаница: знакомое изменение сообщения в `main.py` видно после сохранения и запуска, но это ещё не commit. Commit не отправляет файл на GitHub.
- Первое самостоятельное действие: ученик раскладывает знакомые операции по результатам — файл на диске, выбранная версия для истории, запись в истории. Наблюдаемый результат — объяснение, почему сохранённый файл ещё не является версией Git.
- Опора для повторного обращения: «сохранить → подготовить → создать commit»; `push` не входит в эту цепочку до следующего занятия.
- Переход к следующему шагу: чтобы понять выбор содержимого, сначала назовём места, между которыми Git сравнивает состояние.

## 02. Рабочая папка, index и локальный commit

- Что и зачем объяснить: три состояния дают ученику понятную модель управления снимком без автоматического включения всех файлов.
- Механизм и порядок: рабочая папка содержит сохранённые файлы; index/staging хранит выбранное содержимое для следующей записи; commit добавляет подготовленный снимок в локальную историю. Изменение одного состояния само по себе не заменяет остальные.
- Пример и типичная путаница: сохранение `main.py` не помещает его автоматически в index. Подготовка файла ещё не создаёт commit, а commit ещё не означает отправку на сервер.
- Первое самостоятельное действие: на схеме из трёх состояний ученик размещает сохранённый файл, выбранное содержимое и созданную историю в правильном порядке. Результат — верная последовательность до первого commit.
- Опора для повторного обращения: рабочая папка — что сохранено; index — что выбрано; commit — что уже записано в локальную историю.
- Переход к следующему шагу: состояния Git нужно сначала увидеть, не изменяя их.

## 03. Статус, новые файлы и границы diff

- Что и зачем объяснить: `git status` показывает состояние путей и не меняет историю; новые `main.py` и `.gitignore` в пустом clone будут untracked до подготовки.
- Механизм и порядок: содержание файла читают в редакторе; статус помогает увидеть, что он пока не отслеживается. Обычный diff сравнивает изменения между рабочей папкой и index, поэтому не показывает текст нового untracked-файла.
- Пример и типичная путаница: пустой обычный diff для нового файла не означает, что файл пуст или пропал. Его наличие и содержимое проверяются статусом и чтением файла; после подготовки содержимое появится в staged diff.
- Первое самостоятельное действие: по кратким состояниям ученик определяет, какие пути новые, и выбирает, где проверить их текст. Результат — untracked распознан без ошибочного вывода по пустому diff.
- Опора для повторного обращения: `status` отвечает о состоянии пути; обычный diff не раскрывает содержимое untracked-файлов; staged diff проверяется после подготовки.
- Переход к следующему шагу: теперь можно выбрать только файлы, нужные для первого снимка.

## 04. Подготовка только нужных файлов

- Что и зачем объяснить: staging даёт контроль над составом commit. Для первого результата выбраны только `main.py` и `.gitignore`.
- Механизм и порядок: `git add` принимает перечисленные пути в index. `.gitignore` задаёт правила для подходящих неотслеживаемых файлов, но не удаляет их и не отменяет уже отслеживаемое содержимое. До подготовки проверяются оба исходных файла и список того, что не должно попасть в историю.
- Пример и типичная путаница: массовое добавление каталога может захватить лишние файлы. `__pycache__/`, `*.pyc`, секреты и локальные данные не являются частью исходного снимка. Игнорирование само по себе не удаляет файл и не делает ранее отслеживаемый секрет безопасным.
- Первое самостоятельное действие: ученик выбирает два названных файла по путям и отдельно объясняет, почему служебные Python-файлы и секреты исключаются. Результат — в index помещены только два ожидаемых пути.
- Опора для повторного обращения: до commit проверить список подготовленных путей; не использовать общий выбор всех файлов, если состав ещё не проверен.
- Переход к следующему шагу: наличие нужных путей в index ещё не показывает, какие строки будут записаны; это проверяется отдельным сравнением.

## 05. Staged diff показывает будущий снимок

- Что и зачем объяснить: staged diff нужен для проверки содержимого index перед commit и отвечает на вопрос, что именно запишет следующая локальная версия.
- Механизм и порядок: обычный diff сравнивает рабочую папку с index; staged diff сравнивает index с последней версией истории. Для первого commit Git показывает подготовленные добавления относительно пустой начальной истории. Снимок фиксирует подготовленное состояние, а не будущие изменения файла.
- Пример и типичная путаница: у нового файла обычный diff может быть пустым, при этом staged diff показывает весь текст подготовленного файла. Если содержание меняют после подготовки, index сам не обновляется — изменённую версию нужно проверить и подготовить отдельно.
- Первое самостоятельное действие: ученик читает staged diff двух файлов и называет существенные строки, которые войдут в commit. Затем разбирает один безопасный случай: если новый файл случайно staged до первого commit, применяет `git rm --cached -- <path>` и проверяет, что файл сохранён на диске, стал untracked и больше не входит в staged diff. Результат — содержимое файла осталось в рабочей папке, а ошибочная запись убрана из будущего commit.
- Опора для повторного обращения: перед commit сверить staged diff и список путей; не трактовать пустой обычный diff как проверку подготовленного содержимого.
- Короткий сценарий до первого commit: `git rm --cached -- <path>` удаляет из index подготовленную запись о новом файле, но оставляет сам файл на диске. Проверить этот эффект через наличие файла, статус `untracked` и отсутствие пути в staged diff. Способ проверен в репозитории без предыдущего commit и применим только к ошибочно подготовленному новому файлу; тему общего отката не открывать.
- Переход к следующему шагу: после проверки остаётся определить, чьё имя будет связано с локальной записью и как назвать изменение.

## 06. Авторство и сообщение commit

- Что и зачем объяснить: commit содержит данные об авторе и короткое описание изменения. Имя и email в Git задают авторство; они не являются паролем, входом в GitHub или разрешением на push.
- Механизм и порядок: сначала проверить доступные настройки `user.name`/`user.email`; при необходимости установить понятные данные автора для нужного масштаба настройки. Затем выбрать короткое сообщение, соответствующее проверенному первому снимку.
- Пример и типичная путаница: подпись автора может быть корректной даже без активной авторизации на удалённом сайте; право публикации будет разбираться в занятии 13.1. Секреты или токены не вводятся в настройки автора и не добавляются в файлы проекта.
- Первое самостоятельное действие: ученик объясняет, какие значения станут авторской подписью и какое изменение описывает сообщение. Результат — авторство проверено, сообщение не обещает непроверенных функций.
- Опора для повторного обращения: авторство — метаданные commit; авторизация и права remote — отдельный следующий вопрос.
- Переход к следующему шагу: теперь подготовленное и подписанное локальное изменение можно записать и проверить в истории.

## 07. Создать и найти первый локальный commit

- Что и зачем объяснить: commit сохраняет проверенный index в локальной истории на текущей ветке. Название ветки следует прочитать из репозитория, а не предполагать заранее.
- Механизм и порядок: если проект потребовал последней правки, сначала внести её и сохранить, затем запустить программу; после этого проверить обычный и staged diff и только затем создавать один commit. Локальная история и текущая ветка показывают результат; итоговый status помогает увидеть, остались ли незаписанные изменения. Повторный запуск подтверждает, что исходная возможность сохранена.
- Пример и типичная путаница: успешный commit виден локально, но не доказывает, что GitHub получил эту версию. До следующего урока не нужны upstream, push и проверка сайта.
- Первое самостоятельное действие: ученик находит новую запись в истории, определяет текущую ветку и называет файлы и строки подготовленного снимка. Результат — самостоятельное объяснение локального результата без утверждения о публикации.
- Опора для повторного обращения: найти commit в локальной истории; проверить фактическую ветку и status; запуск относится к программе, а staged diff — к составу версии.
- Переход к практике: повторить этот путь на основном clone, используя знакомый `main.py`, без создания второго проекта.

## 08. Что мы будем делать в практике

**Формат и исходная опора:** локальный проект — основной StudyHub clone из занятия 12.1; ожидаются сохранённые `main.py` и `.gitignore`, пустая история и запуск системным Python 3.12. Это описано паспортом, заполненным планом, TSX и ручной практикой занятия 12.1; фактический результат ученика проверяется отдельно.

Ученик создаст первый проверенный локальный commit только из исходника программы и `.gitignore`, сохранит прежний запуск и сможет объяснить содержимое снимка, автора и ветку. Если clone или ожидаемые файлы отсутствуют, практика commit не начинается: это пробел входной опоры, а не задача на создание второго проекта в занятии 13.

1. **Проверить исходное состояние clone:** открыть именно рабочий каталог StudyHub, сверить наличие сохранённых `main.py` и `.gitignore`, прочитать `git status` и фактическую ветку. Опора — заполненный план 12.1 и блоки 01–03; ученик сам объясняет, почему видит untracked-файлы и что status сообщает без изменения истории. Критерий — нужный clone и два исходных файла определены, состояние до работы понятно.
2. **Подготовить и проверить содержимое:** если нужна последняя правка, сначала внести её и сохранить; затем запустить `main.py` выбранным системным Python 3.12. После запуска подготовить только `main.py` и `.gitignore`, прочитать список путей и staged diff. Ученик самостоятельно отличает обычный diff от staged diff и называет строки, которые войдут в снимок; проверяет отсутствие `__pycache__/`, `*.pyc`, секретов и иных неожиданных файлов. Если до первого commit случайно подготовлен новый файл, применить короткий сценарий из блока 05, проверить его сохранность на диске и повторно прочитать staged diff. Критерий — index содержит только два ожидаемых файла и проверенное содержимое после последней правки.
3. **Записать локальную версию:** проверить автора, составить честное короткое сообщение, создать один commit и найти его в истории. Ученик самостоятельно называет файлы и важные строки снимка, определяет фактическую ветку и объясняет, почему commit ещё не означает push. Критерий — один локальный commit содержит проверенные `main.py` и `.gitignore`, запуск после последней правки успешен, а staged diff не включает неожиданные файлы.

Каждое действие начинается только после соответствующего объяснения. Рабочая программа и clone даны из предыдущего шага; самостоятельная работа состоит в выборе точных путей, проверке снимка и создании локальной записи. Для проектного изменения сохраняется порядок: последняя правка → сохранение → запуск → diff → commit; push выполняется только когда входит в цель, а в этом занятии он относится к следующему шагу. Так опора на status и запуск из A ведёт к index, затем к commit в B.

Итог практики — наблюдаемый локальный commit с ожидаемым автором и фактической веткой, проверенный через staged diff и локальную историю. После commit повторный запуск сохраняет прежнее поведение. В следующем занятии отдельно подтверждается опубликованная серверная версия.
