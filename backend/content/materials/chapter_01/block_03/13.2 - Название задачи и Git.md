## Теория: структура будущей подачи

### 00. Стартовая ситуация

План одной connected-группы **«Точка старта → Новый вопрос → Результат»**: *опубликованный Hello world* → *как очистить название и понять, что Git сохранит?* → *проверенная функция, понятный diff и опубликованная версия*. После связки проговорить разницу между сохранением файла и сохранением Git-снимка.

### 01. Выбор режима перед первой правкой

**Зачем:** две линии работы сохраняют один проект, но приводят к разной публикации. Перед выбором ученик видит `git status`, `git branch --show-current`, `git remote -v` и проверяет, что изменения из прежнего занятия уже опубликованы в его `main`. Если каталог не чист или `main` не опубликована — сначала восстановить предпосылку с помощью предыдущего урока; не выполнять создание ветки из непонятного состояния.

**Механизм:** `main` — основная линия истории, `develop` — другая линия того же репозитория. В **самостоятельном** режиме остаёмся в `main` и не создаём PR. В **менторском** режиме, находясь на чистой опубликованной `main`, выполняем `git switch -c develop`; при уже существующей `develop` используем `git switch develop`, предварительно убеждаясь, что её история и локальные изменения понятны. Команда switch меняет активную ветку, не открывает новый каталог и не публикует изменения. При отсутствии команды на используемой версии Git дать эквивалентную штатную навигацию через интерфейс VS Code, сохранив смысл.

**Проба после объяснения:** по иллюстрации двух указателей `main` и `develop` ученик предсказывает, куда попадёт будущий commit. Затем сам называет выбранную ветку до правки и проверяет реальный ответ `git branch --show-current`. **Визуал для MAIN:** схема «один каталог → две линии истории», с реальной точкой выбора; не две повторные карточки об именах веток. **Опора при ошибке:** просмотр status и ветки.

### 02. Функция, возвращаемое значение и `strip`

**Зачем:** будущий объект Task будет получать аккуратное название, но сейчас достаточно преобразования строки, без пользовательского ввода. Восстановить из 11–11.1 `def`, аргумент, вызов, `return`; отделить `return` (значение доступно вызывающему коду) от `print` (показ текста человеку).

**Независимый пример, не готовая функция проекта:** строка `city = '  Казань  '`, выражение `city.strip()` возвращает `'Казань'`, при этом `city` как прежняя строка не изменяется. На доске трассировать выражение → новое значение → возможный `return` из знакомой функции. Точный контракт проекта: `normalize_title(title)` принимает **одну строку**, возвращает `title.strip()`; пробелы **по краям** убираются, внутренние последовательности пробелов и регистр не меняются. `strip` может вернуть `''`; эта функция **не отклоняет** пустой результат, потому что будущая проверка на непустоту будет в отдельном читателе `read_title`.

**Первая проба:** предсказать результат `'  Мой  город  '.strip()` и проверить отдельно от проекта; объяснить, почему двойной пробел в середине остался и почему использование `lower()` нарушило бы договор. Затем ученик **сам** соединяет известные `def`/`return`/`strip` в функции своего `main.py` (полного листинга готовой `normalize_title` в теоретическом примере нет). **Содержательный интерактив:** выбор между тремя значениями с обоснованием участка строки, который изменился; один различающий случай, а не серия True/False. **Опора:** «метод возвращает новое значение; печать снаружи функции».

### 03. Проверки и различающие входы

**Зачем:** один красивый вывод не подтверждает контракт. Сначала объяснить, как вызвать свою функцию, передать строковый аргумент и увидеть **возвращённое значение** через отдельный `print(normalize_title(...))`; эти `print` стоят **вне** тела функции, в конце учебного файла под уже имеющимся запуском или в выделенном временном проверочном фрагменте без добавления нового меню.

**Серия проверки с прогнозом до запуска:** `'Задача'` → `'Задача'`; `'  Задача  '` → `'Задача'`; `'   '` → `''`; `'Мой  план'` → `'Мой  план'`; `'  IT  План  '` → `'IT  План'`. Отдельно объяснить, что Python покажет пустую строку как пустой вывод при обычном `print`; для видимой диагностики можно печатать `repr(result)` **только после короткого объяснения repr**, либо воспользоваться `print('[' + result + ']')` с известной конкатенацией. Не вводить ещё не подготовленный инструмент как обязательный.

**До примеров с дополнительными пробельными символами:** пояснить на наглядной строке, что `'\t'` обозначает символ табуляции, а `'\n'` — перевод строки в Python-строке; это не две обычные буквы после обратной косой черты. `strip()` удаляет их на краях также, как пробелы; при их нахождении в середине строки не удаляет. Короткая проверка: ученик предсказывает результат `'\tТема\n'.strip()` и сверяет его до задания 2. Не делать изучение всей системы escape-последовательностей отдельной темой.

**Первая проба:** до запуска ученик отмечает две ожидаемые крайние строки и одну неизменяемую внутреннюю часть; после сравнивает свои ожидания с выводом. Типичная ошибка: функция печатает текст сама или `return` стоит внутри `print`; локальный признак — вызов функции должен предоставить строку для последующих операций, а не `None`. **Визуал:** таблица «вход → предсказание → факт → причина» с тремя контрастными случаями; остальные используются в самостоятельной практике. После проверки сохранить файл и перейти к Git.

### 04. Рабочий файл и обычный diff

**Зачем:** известный `git status` говорит, *что* изменено, но ученик должен увидеть, *какие строки*. Из прежних уроков уже известны commit и staging, здесь впервые подробно разделяются три места хранения состояния одного `main.py`: **последний commit** (зафиксированный снимок), **index** (подготовленное для следующего commit), **рабочий файл** (то, что сейчас сохранено на диске). «Сохранить» в редакторе не означает выполнить `git add` и тем более `git commit`.

**Механизм:** после записи функции и её первой проверки, до `git add`, `git diff -- main.py` показывает разницу **рабочий файл ↔ index**; поскольку index пока совпадает с последним commit, там видна новая функция. `git status` показывает изменённый файл; `git diff --staged -- main.py` пока пуст. Объяснить `--` как явный разделитель команды и имени файла, без необходимости учить весь синтаксис Git. На независимой картинке со строкой `print('Hello')` показать выделение одной добавленной строки и почему две версии сравниваются именно так.

**Первая проба:** ученик до запуска команды называет добавленную строку, затем находит её в diff своего файла и объясняет знак `+`. **Визуал:** три столбца «commit | index | рабочий файл»; подсвечивается лишь разница index ↔ рабочий файл. Терминальный diff и редактор VS Code с изменениями Source Control — два способа увидеть один и тот же Git, интерфейс не создаёт отдельного index. **Опора:** вернуться к подписанной паре сравниваемых состояний.

### 05. Снимок index и staged diff

**Зачем:** `git add main.py` копирует текущий сохранённый текст файла в **index**; он не сохраняет новый commit и не отправляет код в GitHub. После этой операции `git diff -- main.py` пуст, если рабочий файл с тех пор не меняли. `git diff --staged -- main.py` (также `git diff --cached -- main.py`) сравнивает **index ↔ последний commit** и перечисляет строки, готовые к фиксации.

**Независимая мысленная модель:** три карточки с версиями одной условной строки: commit = `v1`, index после add = `v2`, рабочий файл = `v2`; один diff пуст, другой содержит новую строку. Ошибка «`git add` уже опубликовал код» исправляется наблюдением `git status` — есть staged changes, но нового commit или push ещё нет.

**Первая проба:** ученик готовит `main.py`, выполняет оба diff, отмечает, какой из них пуст и какая именно строка попадёт в будущий commit. **Интерактив для MAIN:** на основании трёх содержательных состояний сопоставить команды с парами сравнения, затем проверить собственный проект. **Опора:** `git diff` = рабочее минус index, `git diff --staged` = index минус commit.

### 06. Поздняя правка после staging

**Зачем:** программа на диске может выполнять проверку, которой **нет** в подготовленном снимке. После первого `git add` ученик самостоятельно дописывает второй полезный краевой вызов в `main.py` (например, проверку входа из одних пробелов) и **не повторяет add**. Важно заранее попросить спрогнозировать оба diff до выполнения команд.

**Механизм и наблюдение:** index всё ещё содержит первую проверенную версию, а рабочий файл — её плюс поздний вызов. `git diff -- main.py` теперь показывает только позднюю, пока не подготовленную правку; `git diff --staged -- main.py` показывает прежний подготовленный текст без этого вызова. `git status` может показывать `main.py` **одновременно** в staged и unstaged изменениях; это две версии **того же** файла, не два разных файла. При commit в этот момент сохранится версия index, а поздняя проверка останется локальной рабочей правкой.

**Первая проба:** ученик связывает конкретный добавленный им вызов с одной из колонок на схеме «commit → index → рабочий текст», объясняет, почему вывод Python включает позднюю проверку, но будущий commit пока нет. **Интерактив:** предсказать содержимое условного commit и исправить распространённое ошибочное утверждение «всё, что запускается, автоматически войдёт в commit». Это новый тип рассуждения после команд блока 05.

### 07. Безопасное снятие и восстановление staging

**Зачем:** надо переподготовить цельную проверенную версию, не откатывая собственный код. После объяснения, что в репозитории уже есть предыдущий commit, показать команду `git restore --staged main.py`: она снимает подготовленную версию **из index**, но оставляет рабочий `main.py` с обеими правками. До команды ученик предсказывает состояние каждого места, после неё сверяет `git status`, `git diff -- main.py` и `git diff --staged -- main.py`.

**Механизм:** после снятия в index снова содержимое из последнего commit; **все** изменения лежат в рабочем файле и видны обычным diff, staged diff пуст. Затем `git add main.py` готовит **весь проверенный** файл заново: обычный diff пуст, staged diff включает и функцию, и обе проверки. Повторить запуск основных случаев перед commit. Ни `git restore main.py`, ни `git reset --hard` не учить как способ «снять stage», поскольку они рискуют потерять рабочие изменения. Частичный stage здесь не нужен.

**Первая проба:** ученик составляет два прогноза, сверяет оба diff после restore, затем сам решает, какой командой вернёт **весь** файл в index. **Визуал:** схема трёх состояний с переходами «restore --staged» и «add»; не дублировать два блока подряд одной и той же картинкой без нового предсказания. **Опора:** проверить содержимое рабочего файла перед сменой index.

### 08. Проверенный commit, публикация и единая памятка PR

**Общий для двух режимов шаг:** перед фиксацией `git status`, `git diff -- main.py`, `git diff --staged -- main.py`, контрольный запуск `main.py`. Убедиться, что staged версия содержит и функцию, и добавленный граничный случай, а рабочий текст совпадает с подготовленным. Сделать `git commit -m "Add title normalization"` (или своё осмысленное сообщение); проверить новую фиксацию и чистое рабочее состояние с `git status`. Если есть другие незнакомые изменения, не добавлять их автоматически; выяснить источник и явным `git add main.py` подготовить только нужный файл.

**Памятка PR (один цельный фрагмент MAIN на 500–800 слов + команды и интерфейс; нигде не повторять инструкцию):** начать с простой ситуации «проверенная версия готова — кому и как её предложить». `push` публикует commits конкретной ветки; **Pull Request** — просьба рассмотреть и при необходимости включить изменения **из одной ветки в другую**, с видимым diff и обсуждением. Открыть PR ≠ отправить commit в `main`; ответ ментора/merge ≠ успешная Python-проверка. Показывать **только свой StudyHub** с новой `normalize_title`, без второго тренировочного репозитория.

**Самостоятельный режим:** ученик остаётся в `main`, после проверки делает обычный `git push` (upstream был настроен в 13.1), сверяет соответствующий commit на GitHub. PR и новая ветка не обязательны, кнопка создания PR не должна быть условием завершения практики.

**Менторский режим:** ученик уже перешёл на `develop` в блоке 01, сохранил проверенный commit и для первой публикации новой ветки выполняет `git push -u origin develop`. На GitHub открыть Compare & pull request или страницу Pull requests → New pull request; выставить **base: main** (куда предлагают изменения) и **compare: develop** (откуда их предлагают), проверить ветки и diff: новая функция и её проверки, без чужих/служебных файлов. Дать короткий заголовок и объяснение, что меняет `normalize_title`, как проверена; создать PR и отправить **URL существующего PR** ментору (не хранить секреты в описании). Если кнопки нет, использовать страницу создания PR и проверить наличие отличий; не давать совет о force push. На схеме стрелкой показать **develop → main**, отдельно от стрелки **локальная develop → origin/develop**.

**Что дальше:** новые commits в `develop` после push обновят **открытый** PR; после merge для следующей отдельной задачи создаётся **новый** PR. Слияние и согласование веток сопровождает ментор, здесь не преподавать merge/rebase как обязательную работу новичка. Ответ ментора не блокирует дальнейшую учебную работу. В обеих версиях итог Python один и тот же: проверенный `main.py` с `normalize_title`.

**Осмысленное закрепление для MAIN:** показать фрагмент диффа и один вопрос «почему `push develop` ещё не меняет `main`?», затем дать мини-схему направлений base/compare; избежать нескольких подряд карточек о слове PR. Полные клики и корректные состояния будущая MAIN реализует здесь один раз; в финале практики останется только отсылка к памятке.

**Ритм будущей подачи памятки:** после двух начальных объяснительных абзацев вставить содержательное сравнение `push` и PR на одном commit; после самостоятельного/менторского сценариев — визуал двух стрелок публикации и предложения изменений; после интерфейсных шагов — прогноз «что меняется в `main` до merge?». В MAIN пересчитать реальные читаемые абзацы и не оставлять более двух подряд без новой полезной вставки; не вставлять подряд декоративные карточки.

### 09. Что мы будем делать в практике

Заключительная connected-группа **«Выбрать режим → Написать и проверить → Сравнить diff → Подготовить всю версию → Опубликовать»**. После каждой связи показать видимый результат, не заменяя им самостоятельный ввод команд. Формальный критерий успешности раскрывается в практике.

## Практика: одно ручное упражнение, пять шагов

**Формат и единый объект:** одно существующее ручное упражнение `MANUAL_PRACTICE` с пятью задачами, соответствующими имеющемуся `manual.py` для ключа `13.2`. Все работают с **собственным** репозиторием StudyHub, файлом `main.py` и существующей историей; отдельной автопроверки, второго репозитория или обязательного PR для самостоятельной группы нет. Ученик вводит команды и записывает код сам; готовые команды представлены в теории как изученные инструменты, не как скрипт полного решения практики. Для задач действуют пять полей «вход/объект/опора/самостоятельное действие/локальный результат».

**Задача 1. Подтвердить исходный checkpoint и режим.**

- **Вход:** есть опубликованный Hello world после 13.1; требуется найти **свой** проект по `main.py`, `.gitignore`, `origin` и последнему commit. Если проект не соответствует предыдущей B, ученик возвращается к 12.1–13.1.
- **Объект:** существующий репозиторий, текущая ветка, index и рабочий файл.
- **Опора:** блок 01 и прежние `status`, `remote`, `log`, `push`; узнать состояние допустимо **до** любого изменения. Обозначить, как отличить локальную ветку от её опубликованной версии, и что у новой `develop` до первого push может не быть upstream.
- **Самостоятельно:** найти нужный каталог, запустить старый `main.py` и убедиться в прежнем Hello world; назвать ветку, `origin` и локальный commit; проверить чистый index/рабочий каталог; выбрать **ровно один** режим. Для менторского — из чистой опубликованной `main` самостоятельно выполнить разобранный switch к `develop` до первой правки; без ментора остаться в `main`.
- **Локальный критерий:** старый запуск работает; `git status` не показывает собственных незавершённых изменений, нет незнакомых staged файлов; ученик верно называет активную ветку и знает будущую ветку публикации. Чужие изменения не сбрасывать. Отличающий случай: новая `develop` может ещё не отслеживать remote, что **не** равно неисправности проекта.
- **Подсказка после попытки:** сначала выясни «где я, какая ветка и что уже изменено» с помощью просмотренных команд; если каталог грязный — разберись в правках, не вызывай команды принудительного сброса. Не выдавать готовую последовательность публикации.

**Задача 2. Самостоятельно записать функцию с узким контрактом.**

- **Вход:** сохранённый старый `main.py` и изученные `def`/`return`/`strip` из 11–11.1 и блока 02. В теории показан `strip` строки на другом сюжете, но **не** полный код будущей функции.
- **Объект:** новая `normalize_title(title)` в **том же** файле; учебные вызовы после определения функции.
- **Опора:** блоки 02–03; перед первым применением `'\t'` и `'\n'` коротко объяснить как обозначения табуляции и перевода строки внутри Python-литерала, которые `strip` тоже удаляет **с краёв**. Не требовать самостоятельно угадать их смысл.
- **Самостоятельно:** написать определение, один параметр и возвращаемое значение **своими руками**, затем придумать и добавить тестовые вызовы обычного названия, текста с внешними пробелами/табуляцией/переводом строки и строки, состоящей только из пробелов. Сохранить старый Hello world; `print` для просмотра — снаружи функции. Дополнительный перенос: объяснить на собственном названии, почему двойной внутренний пробел и регистр не изменились.
- **Локальный критерий:** `normalize_title('План') == 'План'`; `normalize_title('  План  ') == 'План'`; `normalize_title(' \t\n ') == ''`; `normalize_title('IT  План') == 'IT  План'`. Сложные внешние пробельные символы также очищаются. Внутренний двойной пробел и регистр сохраняются; функция возвращает значение и не печатает. До исполнения ученик предсказывает минимум два отличающихся результата.
- **Подсказка после попытки:** проверь, где у строки края, где тело функции, чем `return` отличается от `print`; не подставлять полный код определения как подсказку к обязательному самостоятельному написанию.

**Задача 3. Проверить запуск и увидеть рабочий diff.**

- **Вход:** ученик добавил функцию и первые проверки, но `git add` для новой версии **ещё не выполнял**; исходная ветка/index были чистыми в задаче 1.
- **Объект:** сохранённый `main.py`, его вывод и **рабочие** изменения относительно index.
- **Опора:** блоки 03–04; значение `git diff -- main.py`, `git status` и знак `+` уже объяснены.
- **Самостоятельно:** сохранить файл, запустить его выбранным Python 3.12; сопоставить конкретную новую строку вывода с конкретной строкой в `git diff -- main.py`; назвать, что показывает `git status`, и проверить, что staged diff пока пуст. Задать различающий вопрос: «Если сейчас сделать commit без add, попадёт ли функция в него? Почему?».
- **Локальный критерий:** прежний Hello world не исчез, новые проверки дают ожидаемые строки; обычный diff показывает добавленные фрагменты, `git diff --staged -- main.py` пуст при исходно чистом index. Ученик различает «сохранено на диске» и «подготовлено к commit». Если diff пуст при успешном запуске, выяснить, тот ли файл/репозиторий открыт, вместо автоматического добавления.
- **Подсказка после попытки:** сначала пересохрани `main.py` и проверь текущую директорию, затем подпиши пару состояний, между которыми считает diff; полного Git-рецепта не показывать.

**Задача 4. Сравнить index и позднюю рабочую правку.**

- **Вход:** работающий вариант из задачи 3; перед операцией проверить, что нет постороннего staging. Индекс может содержать только известные учебные изменения.
- **Объект:** две версии **одного** `main.py`: подготовленная после `git add -- main.py` и позднее изменённая рабочая.
- **Опора:** блоки 05–06 и схематичные три состояния, уже разобранное `git diff --staged -- main.py`. Объяснить до применения, что add копирует содержимое в index на момент вызова.
- **Самостоятельно:** подготовить **первый** вариант, проверить staged diff; затем добавить **ещё одну полезную проверку** с отличающимся входом (например, сочетание табуляции и двойного внутреннего пробела) **без повторного add**. До следующей команды предсказать оба diff и состав гипотетического commit. Выполнить сравнение и объяснить, почему один файл одновременно staged и modified.
- **Локальный критерий:** `git diff -- main.py` показывает **только поздний** вызов относительно index, `git diff --staged -- main.py` показывает **первоначально подготовленную** функцию/проверки относительно commit. Поздний вызов есть в запускаемом файле, но его нет в текущем index. Ученик не принимает пустой обычный diff сразу после add за потерю кода.
- **Подсказка после попытки:** подпиши «последний commit / index / рабочий файл» и укажи, **когда** вторая правка попала на диск; не выполнять дополнительный add вместо анализа.

**Задача 5. Безопасно переподготовить, зафиксировать и опубликовать.**

- **Вход:** функция и обе проверки работают в `main.py`, но index намеренно отстаёт; предыдущий commit существует. Никаких чужих файлов index не содержит.
- **Объект:** тот же файл и текущая выбранная ветка; контрольный снимок должен соответствовать **последнему запущенному** варианту.
- **Опора:** блоки 07–08, памятка об общих проверках и PR. Напомнить разницу между `git restore --staged -- main.py` и восстановлением рабочего файла.
- **Самостоятельно:** **до** команды предсказать судьбу функции и поздней проверки; снять staging у `main.py` без изменения рабочего текста; сверить оба diff и вывод Python; повторно подготовить **весь** проверенный файл, убедиться, что staged diff содержит обе правки, а обычный diff пуст; сделать содержательный commit, убедиться в чистоте Git. **Самостоятельный режим:** привычный `git push` в `main` и проверка соответствующей версии на GitHub. **Менторский:** первая публикация `git push -u origin develop`, открыть PR с **base main / compare develop**, проверить вкладку Files changed и передать URL ментору по памятке **без отдельного обязательного задания на получение ответа**.
- **Локальный критерий:** после `restore --staged` весь текст остаётся на диске, обычный diff содержит **обе** правки, staged diff пуст; после повторного add — наоборот. После commit есть идентифицируемая версия с проверенной функцией и обеими проверками, старый Hello world сохранён; на GitHub видна публикация **выбранной** ветки. При менторском режиме PR показывает нужное направление и только ожидаемые изменения; критерий Python успешно достигается независимо от решения ментора. Если сеть/доступ к GitHub недоступны — локальную проверку отделить от **непроверенного push/PR**, не объявлять опубликованность.
- **Подсказка после попытки:** что делает слово `--staged` и какой снимок Git приготовил? После объяснения и собственной попытки разрешено вернуться к схеме блока 07 и командам из памятки; не советовать `reset --hard`, удаление файла или force push.

**Рост самостоятельности:** задача 1 — ориентирование в **своём** проекте; 2 — самостоятельное построение функции по договору; 3 — связь вывода с рабочим diff; 4 — **предсказание несовпадающих Git-снимков** при новой правке; 5 — самостоятельный безопасный возврат к полной проверенной версии и публикация. Задачи 4 и 5 отличаются мыслительным действием: сначала диагностировать подготовленное/неподготовленное, затем осознанно привести index к правильному содержимому.

**Переход между практикой и MAIN:** в теории не выдавать полный готовый код `normalize_title` и решение задачи 4. План допускает локальный быстрый возврат к схеме состояний. Для MAIN использовать в каждом из блоков 02–07 контентное изменение ритма после максимум двух подряд читаемых абзацев: прогноз и проверка, таблица различий, размеченный diff или схема index. Нужны **разные когнитивные действия**, а не механические соседства `Note → TrueFalse → Note`; декоративные карточки без нового знания не считать вставками.

## Границы приёмки и переход
