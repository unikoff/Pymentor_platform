## 00. Вступление

В меню уже можно выбрать добавление, а программа умеет спросить название и приоритет. Но сами вопросы ещё не создают задачу: нужен уникальный номер, единое место для записи и один понятный путь от ввода до результата. Сначала разберём, как выбрать следующий id, потом добавим одну запись и только после этого подключим действие к меню.

1. **Точка старта:** в ожидаемой основе B3 готовы фабрика и форматтер; по маршруту уроков 16–16.1 добавлены меню и readers, которые возвращают допустимые название и приоритет. Эта опора остаётся неподтверждённой, пока не сверены проект и фактическое прохождение.
2. **Новый вопрос:** как превратить два подготовленных значения в самостоятельную задачу, не теряя уже введённые записи и не создавая задачу при ошибочном вводе?
3. **Результат:** добавление в одном запуске получает следующий id, записывает ровно одну задачу в общий `tasks` и показывает её карточку; прежние компоненты продолжают работать.

Пункты образуют путь от подготовленных входных значений к наблюдаемому изменению общего состояния. Сначала нужно определить, что именно означает id и как найти следующий; затем соединить фабрику с изменением списка и передать операцию интерфейсу. Полный просмотр списка не входит в этот результат и останется задачей следующего занятия.

## 01. Id задачи — это не её место в списке

- **Что и зачем объяснить:** id — поле самой записи, по которому программа сможет ссылаться на задачу; индекс — место элемента при обходе, а `len(tasks)` — количество элементов. Это разные ответы на разные вопросы. Новая задача должна получить id, который не совпадает с уже использованными.
- **Механизм и порядок:** восстановить знакомую запись-словарь с полем `id` и список таких записей. Пройти две записи в необычном порядке и показать, что размер списка не сообщает ни id последней записи, ни свободное значение. Id читается из каждой задачи; он не вычисляется из позиции.
- **Независимый пример и типичная путаница:** представить карточки каталога с номерами 4 и 11, лежащие в списке из двух элементов. Следующий номер определяется по самим карточкам, а не как «число карточек плюс один». Перестановка карточек не должна менять их номера.
- **Первое самостоятельное действие:** ученик предсказывает, какое значение описывает количество записей, а какое — номер конкретной записи; затем объясняет, почему список из двух элементов не обязан иметь id 1 и 2. Результат — он отличает данные записи от её положения.
- **Опора для повторного обращения:** перед расчётом спросить: «Читаем поле каждой записи, позицию при обходе или количество записей?» Для поиска следующего id нужны сохранённые значения поля `id`.
- **Переход:** когда известен смысл id, можно определить правило для пустого и заполненного списка.

## 02. Как получить следующий id

- **Что и зачем объяснить:** `get_next_id(tasks)` должна возвращать новый номер, не изменяя переданный список. Здесь применяется уже знакомый обход и накопление максимума к списку словарей.
- **Механизм и порядок:** договор Planner гарантирует положительные id у существующих задач. Поэтому именно здесь 0 служит допустимой нижней границей накопителя, а не id записи: для пустого списка обход её не меняет, и следующий id равен 1. Для каждой существующей задачи прочитать `task["id"]`; если id больше накопленного, обновить максимум; после обхода вернуть число на единицу больше найденного максимума. Это частный выбор, опирающийся на положительность id и заданный пустой случай Planner, а не универсальное правило начального значения при поиске максимума.
- **Независимый пример и типичная путаница:** для id 10, 3 и 20, встреченных именно в таком порядке, максимум остаётся 20, поэтому следующий id — 21. Для пустого списка обход не меняет нулевой накопитель, и результат — 1. Не использовать длину списка, индекс цикла или id последней просмотренной записи.
- **Первое самостоятельное действие:** сначала проследить накопитель на пустом, возрастающем и перемешанном наборе; затем самостоятельно реализовать только `get_next_id`. После разбора записи функции проверить пустой список и несмежные id, созданные существующей фабрикой. Критерий: функция возвращает ожидаемый номер и не меняет записи или список.
- **Опора для повторного обращения:** форма «начальное значение → прочитать id каждой записи → обновить максимум только при большем id → прибавить один после цикла». Ошибка в пустом случае обычно начинается с неверного начального максимума; ошибка на перемешанном — с предположения, что список отсортирован.
- **Переход:** helper готов; теперь он должен стать частью одной операции создания задачи.

## 03. Операция добавления связывает helper и фабрику

- **Что и зачем объяснить:** `create_task` уже знает, как вернуть новый словарь из готовых `task_id`, `title` и `priority`, но сама фабрика не выбирает id и не добавляет запись. `add_task` связывает готовые роли в одну операцию.
- **Механизм и порядок:** `add_task` получает общий список и проверенные значения. Сначала просит `get_next_id` вычислить номер, затем передаёт три подготовленных значения фабрике, получает новый словарь, добавляет его в `tasks` одним вызовом `append` и возвращает добавленный словарь. Здесь не требуется копировать список или повторно нормализовать/валидировать значения из readers.
- **Наблюдаемый эффект и различие результатов:** `append` меняет существующий список и возвращает служебное `None`; результатом `add_task` должен быть сам словарь новой задачи. Поэтому добавление в список и значение, которое вернёт функция, — два связанных, но разных результата. Фабрика создаёт словарь, `append` сохраняет ссылку на него, а `return` отдаёт ту же запись вызывающему коду.
- **Независимый пример и типичная путаница:** при добавлении книги в общий каталог фабрика формирует карточку, операция помещает её в каталог, а вызывающий код получает карточку для следующего шага. Не приписывать фабрике изменение каталога и не считать, что результат `append` — добавленная карточка. Присваивание локальному параметру нового списка тоже не заменяет общий список у вызывающего кода.
- **Первое самостоятельное действие:** после объяснения последовательности ученик реализует `add_task`, не подключая меню. На контролируемом списке проверяет, что число записей выросло на одну, появился один новый id, а возвращённая запись — тот же объект, который добавлен в список. Использовать знакомую проверку идентичности из темы общих ссылок; не вводить копирование.
- **Опора для повторного обращения:** восстановить четыре шага «получить id → создать запись → один раз append → вернуть запись». Если операция возвращает `None`, проверить, не возвращается ли результат `append`; если список не изменился, проверить, передан ли именно общий список и вызывается ли `append`.
- **Переход:** проверенная операция уже может работать без меню; остаётся подключить к ней подготовленный пользовательский ввод.

## 04. Reader сначала, эффект после двух готовых значений

- **Что и зачем объяснить:** reader отделяет получение и проверку ввода от изменения состояния. `read_title` и `read_priority` уже возвращают допустимые значения либо повторяют свой вопрос; `add_task` начинает работу только после того, как оба результата получены.
- **Механизм и порядок:** handler вызывает сначала reader названия, затем reader приоритета. Внутренний повтор при ошибке остаётся внутри соответствующего reader. Только после успешного возврата обоих значений handler вызывает `add_task`; затем передаёт возвращённую запись в `format_task` и печатает получившуюся строку. Форматтер возвращает текст, а не печатает его сам.
- **Независимый пример и типичная путаница:** перед оплатой заказа сервис сначала собирает все обязательные данные, а затем фиксирует эффект. Если второй ввод не прошёл проверку, нельзя оставить половину заказа. В Planner это означает, что ошибочный приоритет не должен добавить задачу с частичными полями или выдать карточку.
- **Первое самостоятельное действие:** ученик словами восстанавливает цепочку `handle_add → readers → add_task → format_task`, затем подключает handler, не переписывая readers и фабрику. До запуска предсказывает, в какой момент список впервые изменится. Критерий: эффект возникает только после двух допустимых значений; успешная карточка соответствует добавленной записи.
- **Опора для повторного обращения:** «оба reader вернули значение?» — до этого вопроса `add_task` не вызывается. Сообщение о неверном приоритете и повтор вопроса сами по себе не являются частичным добавлением.
- **Переход:** теперь следует проверить, откуда handler получает общий список и как он переживает следующий выбор команды.

## 05. Один общий список принадлежит `run`

- **Что и зачем объяснить:** меню должно передавать handler тот же `tasks`, который создал `run` до цикла. Добавление меняет этот объект, поэтому следующая команда в том же запуске увидит новую задачу. Локальная переменная-параметр функции не означает автоматически отдельную копию. Для прямой проверки после завершения меню можно использовать уже разобранный в плане 16 запуск `python -i main.py`: файл выполняется, затем после штатного выхода из `run` появляется `>>>`, где доступны определения функций. Так как фактическое прохождение 36 не подтверждено, перед применением кратко восстановить эту последовательность, если ученик не может объяснить её сам.
- **Механизм и порядок:** проследить знакомые вызовы `run → handle_add(tasks) → add_task(tasks, title, priority)`. Вложенный вызов получает общий список и добавляет в него запись; `run` не создаёт новый список при каждом выборе и handler не возвращает заменённый список как обязательный контракт. При завершении процесса данные исчезают — постоянное хранение не появляется.
- **Пример и типичная путаница:** две команды `add` в одном запуске должны увидеть разные следующие id, потому что первая операция уже изменила общий список. Это не означает сохранение задач после нового запуска. Не создавать второй `tasks` внутри handler и не путать изменение общего объекта с переназначением локального имени.
- **Первое самостоятельное действие:** перед соединением меню ученик прослеживает две последовательные команды и указывает, где создаётся список и какая операция меняет его. Затем подключает handler во временную ветвь add. Результат — второй вызов использует состояние первого, а после выхода проект не обещает долговременную запись.
- **Опора для повторного обращения:** пройти стрелками один путь данных: список создаётся один раз в `run`, reader возвращает значения, операция меняет этот список, handler форматирует возвращённую запись.
- **Переход:** интеграция готова; практика проверит helper, отдельную операцию и пользовательский сценарий по очереди.
