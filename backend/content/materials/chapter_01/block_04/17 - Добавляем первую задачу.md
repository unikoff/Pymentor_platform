## Точка B: результат занятия

- `get_next_id(tasks)` возвращает 1 для пустого списка, иначе число на единицу больше наибольшего существующего id; порядок записей и промежутки между id не меняют правило.

## Границы и передача дальше

В этом занятии не реализуем полный непустой `show_tasks`, `find`, `done`, поиск названия, статистику и хранение между запусками. Не меняем модель задачи или четыре готовые функции B3. `add_task` не читает ввод, не печатает, не добавляет универсальную проверку произвольных аргументов и не создаёт копию списка. Handler использует готовые readers и formatter; `run` по-прежнему владеет одним списком. Временная непустая ветвь `show_tasks` не должна ложно говорить, что список пуст.

## 00. Вступление

В меню уже можно выбрать добавление, а программа умеет спросить название и приоритет. Но сами вопросы ещё не создают задачу: нужен уникальный номер, единое место для записи и один понятный путь от ввода до результата. Сначала разберём, как выбрать следующий id, потом добавим одну запись и только после этого подключим действие к меню.

1. **Точка старта:** в ожидаемой основе B3 готовы фабрика и форматтер; по маршруту уроков 16–16.1 добавлены меню и readers, которые возвращают допустимые название и приоритет. Эта опора остаётся неподтверждённой, пока не сверены проект и фактическое прохождение.
2. **Новый вопрос:** как превратить два подготовленных значения в самостоятельную задачу, не теряя уже введённые записи и не создавая задачу при ошибочном вводе?
3. **Результат:** добавление в одном запуске получает следующий id, записывает ровно одну задачу в общий `tasks` и показывает её карточку; прежние компоненты продолжают работать.

Пункты образуют путь от подготовленных входных значений к наблюдаемому изменению общего состояния. Сначала нужно определить, что именно означает id и как найти следующий; затем соединить фабрику с изменением списка и передать операцию интерфейсу. Полный просмотр списка не входит в этот результат и останется задачей следующего занятия. Для будущей MAIN-подачи держать объяснение в пределах 2100–2700 учитываемых слов по паспорту, выделяя основное место механизму выбора id, эффекту `append` и границе проверки ввода; каждый новый механизм сначала объяснить, затем показать на *других* данных, затем дать самостоятельное действие.

## 01. Id задачи — это не её место в списке

- **Что и зачем объяснить:** id — поле самой записи, по которому программа сможет ссылаться на задачу; индекс — место элемента при обходе, а `len(tasks)` — количество элементов. Это разные ответы на разные вопросы. Новая задача должна получить id, который не совпадает с уже использованными.
- **Механизм и порядок:** восстановить знакомую запись-словарь с полем `id` и список таких записей. Например, для двух записей с id 11 и 4 индексы при обходе равны 0 и 1, `len(tasks)` равно 2, а следующим id по принятому правилу будет 12. Поменять порядок карточек и показать, что количество и свободный id от этого не меняются. Id читается из каждой задачи; он не вычисляется из позиции.
- **Независимый пример и типичная путаница:** представить карточки каталога с номерами 6 и 14, лежащие в списке из двух элементов. Следующий номер — 15, а не «число карточек плюс один», то есть 3. Перестановка карточек не должна менять их номера.
- **Первое самостоятельное действие:** на *другой* паре id 7 и 2 ученик без подсказки определяет `len`, индексы и следующий id, а затем объясняет, почему список из двух элементов не обязан иметь id 1 и 2. Результат — он отличает данные записи от её положения.
- **Опора для повторного обращения:** перед расчётом спросить: «Читаем поле каждой записи, позицию при обходе или количество записей?» Для поиска следующего id нужны сохранённые значения поля `id`.
- **Переход:** когда известен смысл id, можно определить правило для пустого и заполненного списка.

## 02. Как получить следующий id

- **Что и зачем объяснить:** `get_next_id(tasks)` должна возвращать новый номер, не изменяя переданный список. Здесь применяется уже знакомый обход и накопление максимума к списку словарей.
- **Механизм и порядок:** договор Planner гарантирует положительные id у существующих задач. Поэтому именно здесь 0 служит допустимой нижней границей накопителя, а не id записи: для пустого списка обход её не меняет, и следующий id равен 1. Для каждой существующей задачи прочитать `task["id"]`; если id больше накопленного, обновить максимум; после обхода вернуть число на единицу больше найденного максимума. После значений 10 → 3 → 20 в трассе максимум меняется 0 → 10 → 10 → 20, а итог становится 21. Это частный выбор, опирающийся на положительность id и заданный пустой случай Planner, а не универсальное правило начального значения при поиске максимума.
- **Независимый пример и типичная путаница:** для id 4, 1 и 7 в таком порядке максимум меняется 0 → 4 → 4 → 7, поэтому ответ 8. Для пустого списка обход не меняет нулевой накопитель, и результат — 1. Не использовать длину списка, индекс цикла или id последней просмотренной записи.
- **Первое самостоятельное действие:** самостоятельно заполнить трассу накопителя для id 8 → 2 → 5 (ожидается 0 → 8 → 8 → 8, ответ 9) и пустого списка (ответ 1); затем реализовать только `get_next_id`. После разбора записи функции проверить пустой список и несмежные id, созданные существующей фабрикой. Критерий: функция возвращает ожидаемый номер и не меняет записи или список. Не давать готовое тело функции до этой попытки.
- **Опора для повторного обращения:** форма «начальное значение → прочитать id каждой записи → обновить максимум только при большем id → прибавить один после цикла». Ошибка в пустом случае обычно начинается с неверного начального максимума; ошибка на перемешанном — с предположения, что список отсортирован.
- **Переход:** helper готов; теперь он должен стать частью одной операции создания задачи.

## 03. Операция добавления связывает helper и фабрику

- **Что и зачем объяснить:** `create_task` уже знает, как вернуть новый словарь из готовых `task_id`, `title` и `priority`, но сама фабрика не выбирает id и не добавляет запись. `add_task` связывает готовые роли в одну операцию.
- **Механизм и порядок:** `add_task` получает общий список и проверенные значения. Сначала просит `get_next_id` вычислить номер, затем передаёт три подготовленных значения фабрике, получает новый словарь, добавляет его в `tasks` одним вызовом `append` и возвращает добавленный словарь. Здесь не требуется копировать список или повторно нормализовать/валидировать значения из readers.
- **Наблюдаемый эффект и различие результатов:** `append` меняет существующий список и возвращает служебное `None`; результатом `add_task` должен быть сам словарь новой задачи. Поэтому добавление в список и значение, которое вернёт функция, — два связанных, но разных результата. Фабрика создаёт словарь, `append` сохраняет ссылку на него, а `return` отдаёт ту же запись вызывающему коду. Перед проверкой идентичности кратко объяснить запись `a is b`: она показывает, являются ли `a` и `b` ссылками на один объект; `a == b` проверяет равенство значений и для этой цели недостаточно.
- **Независимый пример и типичная путаница:** при добавлении книги в общий каталог фабрика формирует карточку, операция помещает её в каталог, а вызывающий код получает карточку для следующего шага. Не приписывать фабрике изменение каталога и не считать, что результат `append` — добавленная карточка. Присваивание локальному параметру нового списка тоже не заменяет общий список у вызывающего кода.
- **Первое самостоятельное действие:** после объяснения последовательности ученик предсказывает два разных результата вызова `tasks.append(card)` (список изменится, возвращаемое значение `None`), затем реализует `add_task`, не подключая меню. На контролируемом списке с заранее известным числом записей проверяет прирост ровно на одну, новый id и выражение `added is tasks[1]` для случая с одной старой записью; для пустого списка индекс новой записи равен 0. Не вводить копирование.
- **Опора для повторного обращения:** восстановить четыре шага «получить id → создать запись → один раз append → вернуть запись». Если операция возвращает `None`, проверить, не возвращается ли результат `append`; если список не изменился, проверить, передан ли именно общий список и вызывается ли `append`.
- **Переход:** проверенная операция уже может работать без меню; остаётся подключить к ней подготовленный пользовательский ввод.

## 04. Reader сначала, эффект после двух готовых значений

- **Что и зачем объяснить:** reader отделяет получение и проверку ввода от изменения состояния. `read_title` и `read_priority` уже возвращают допустимые значения либо повторяют свой вопрос; `add_task` начинает работу только после того, как оба результата получены.
- **Механизм и порядок:** handler вызывает сначала reader названия, затем reader приоритета. Внутренний повтор при ошибке остаётся внутри соответствующего reader. Если первый приоритет недопустим, выполнение ещё находится в `read_priority` и не дошло до строки вызова `add_task`. Только после успешного возврата обоих значений handler вызывает `add_task`; затем передаёт возвращённую запись в `format_task` и печатает получившуюся строку. Форматтер возвращает текст, а не печатает его сам.
- **Независимый пример и типичная путаница:** перед оплатой заказа сервис сначала собирает все обязательные данные, а затем фиксирует эффект. Если второй ввод не прошёл проверку, нельзя оставить половину заказа. В Planner это означает, что ошибочный приоритет не должен добавить задачу с частичными полями или выдать карточку.
- **Первое самостоятельное действие:** по разветвлённой трассе «название принято → приоритет отклонён → приоритет запрошен ещё раз → приоритет принят → вызвана операция → карточка» ученик отмечает *единственное* место изменения `tasks`, затем подключает handler, не переписывая readers и фабрику. До запуска предсказывает, в какой момент список впервые изменится. Критерий: эффект возникает только после двух допустимых значений; успешная карточка соответствует добавленной записи.
- **Опора для повторного обращения:** «оба reader вернули значение?» — до этого вопроса `add_task` не вызывается. Сообщение о неверном приоритете и повтор вопроса сами по себе не являются частичным добавлением.
- **Переход:** теперь следует проверить, откуда handler получает общий список и как он переживает следующий выбор команды.

## 05. Один общий список принадлежит `run`

- **Что и зачем объяснить:** меню должно передавать handler тот же `tasks`, который создал `run` до цикла. Добавление меняет этот объект, поэтому следующая команда в том же запуске увидит новую задачу. Локальная переменная-параметр функции не означает автоматически отдельную копию. Для прямой проверки после завершения меню можно использовать уже разобранный в плане 16 запуск `python -i main.py`: файл выполняется, затем после штатного выхода из `run` появляется `>>>`, где доступны определения функций. Так как фактическое прохождение 36 не подтверждено, перед применением кратко восстановить эту последовательность, если ученик не может объяснить её сам.
- **Механизм и порядок:** проследить знакомые вызовы `run → handle_add(tasks) → add_task(tasks, title, priority)`. Вложенный вызов получает общий список и добавляет в него запись; `run` не создаёт новый список при каждом выборе и handler не возвращает заменённый список как обязательный контракт. При завершении процесса данные исчезают — постоянное хранение не появляется.
- **Пример и типичная путаница:** две команды `add` в одном запуске должны увидеть разные следующие id, потому что первая операция уже изменила общий список. Это не означает сохранение задач после нового запуска. Не создавать второй `tasks` внутри handler и не путать изменение общего объекта с переназначением локального имени.
- **Первое самостоятельное действие:** перед соединением меню ученик прослеживает две последовательные команды и указывает, где создаётся список и какая операция меняет его. Затем подключает handler во временную ветвь add. Результат — второй вызов использует состояние первого, а после выхода проект не обещает долговременную запись.
- **Опора для повторного обращения:** пройти стрелками один путь данных: список создаётся один раз в `run`, reader возвращает значения, операция меняет этот список, handler форматирует возвращённую запись.
- **Переход:** интеграция готова; практика проверит helper, отдельную операцию и пользовательский сценарий по очереди.

## 06. Что мы будем делать в практике

**Формат и исходная опора:** проект. Продолжаем один основной StudyHub в состоянии B3 плюс каркас и readers по паспортам 36–37. Перед изменением ученик предъявляет путь к своему `main.py` и воспроизводит короткую входную проверку из точки A; доступные материалы сейчас не подтверждают его фактический B3 checkpoint. Если исходный проект отсутствует или содержит более позднюю реализацию, не подменяем его локальным `studyhub` на занятии 105 или финальным snapshot: сначала выясняем и восстанавливаем правильную точку A. Проверка A является условием перехода к изменению проекта, а не оценкой по наличию чужого snapshot.

Общий результат — добавить и подключить одну работающую возможность, сохранив общий список и готовые части проекта. Работу вести по нарастающей самостоятельности: helper → операция → handler и два пользовательских добавления.

1. **Добавить расчёт id в прежний `main.py`:** после теории 01–02 вспомнить цикл, чтение поля словаря и накопление максимума, затем самостоятельно реализовать `get_next_id`. После короткого напоминания о запуске `python -i main.py` (дождаться штатного выхода из меню и приглашения `>>>`) прямо вызвать функцию на `[]` — ожидается `1`; затем на словарях с id 10, 3, 20 в таком порядке — ожидается `21`. Записи создать уже знакомой фабрикой, никаких новых функций приложения не вводить. Сравнить состав списка до и после обоих вызовов. Наблюдаемый результат: ответ зависит от максимального id, а не количества или последнего элемента; входной список не изменён.
2. **Создать операцию `add_task`:** после теории 03 самостоятельно связать helper с готовой `create_task`, одним `append` и возвратом записи. Проверить до подключения меню: для `tasks=[]` одна операция даёт длину 1 и id 1, затем ещё одна на *том же* списке — длину 2 и id 2. Отдельно проверить список с одной старой записью id 5: новый id 6, старый элемент остаётся на позиции 0, `added is tasks[1]` истинно (смысл `is` уже объяснён в теории). Если операция возвращает `None`, проверить возврат результата `append`; если id совпал с прежним, пересмотреть расчёт максимума. Наблюдаемый результат: ровно один новый словарь на вызов, возвращена та же запись и прежние данные сохранены.
3. **Подключить `handle_add` к меню:** после теории 04–05 использовать готовые `read_title`, `read_priority`, `format_task` и один `tasks` из `run`. Сначала напрямую вызвать handler на отдельном контролируемом списке с одной задачей, ввести допустимое название, недопустимый приоритет, затем допустимый. Проследить путь вызовов: первый отказ оставляет выполнение внутри `read_priority`, до `add_task` программа ещё не дошла; лишь после второго ввода операция добавляет одну запись. После возврата сверить состав списка (старая задача осталась, появилась ровно одна новая с верным приоритетом) и карточку. Итоговый состав сам по себе не доказывает промежуточное состояние: для дополнительного наблюдения при уже знакомом отладчике по 14.2 можно остановиться на повторном запросе и увидеть ещё неизменённый `tasks`; отладчик не обязателен. Затем в *одном* запуске меню дважды выбрать `add`, ввести два разных допустимых названия и приоритета, увидеть две разные карточки с id 1 и 2 при изначально пустом списке. Наблюдаемый результат: ошибка ввода не ведёт к частичной записи, оба успешных вызова меняют общий список, временная `show_tasks` честно сообщает, что полный показ пока не сделан.
4. **Проверить сохранённые возможности и передать следующий шаг:** используя ранее готовые команды, проверить пустой list, неизвестную команду и exit; убедиться, что четыре функции B3 не переписаны. Просмотреть `status` и diff; если он содержит проверенное изменение по этому уроку, подготовить только его, сохранить commit и отправить его в принятую ветку проекта. Если содержательного diff нет, не создавать искусственную правку или commit. Наблюдаемый результат: меню и выход работают, а изменение ограничено добавлением; полный list остаётся отдельной задачей урока 17.1.

**Содержательные вставки для MAIN:** после смыслового объяснения id дать одну читаемую схему «список из двух карточек → индексы/длина/id» с вопросом о следующем id; после механизма максимума — интерактивную трассу накопителя с одним пропуском для ученика; после `append`/`return` — схему двух результатов с прогнозом `None` и проверки `is`; перед handler — диаграмму ветвления неверного и верного приоритета, где ученик сам отмечает единственный момент `append`; в конце — вывод двух разных карточек из одной сессии. В каждой вставке ученик делает содержательное предсказание или проверку, а не просто смотрит на оформление. При верстке оставлять максимум два читаемых абзаца подряд без осмысленной вставки (пример, схема, вопрос, код либо результат запуска); не чередовать форматы механически и не ставить подряд повторяющиеся декоративные карточки. Не показывать финальную реализацию до самостоятельной попытки соответствующего шага.

**Приёмка практики:** первые два действия изолируют расчёт и изменение списка до ввода; третье доказывает интеграцию в цикле, четвёртое — сохранность прежнего меню. Отличать проверенное выполнение учеником от критериев *плана*: на текущем этапе наблюдалась структура ожидаемой практики, но фактический проект/выполнение не предъявлены.
