Отдельно, после выхода из run в знакомой интерактивной сессии, вызвать show_tasks на отдельном списке из двух записей, созданных фабрикой с id 20 и 3 именно в этом порядке. Отдельный вызов готового formatter показывает оба статуса, но не означает, что команда done уже реализована.

## 00. Вступление

После добавления задачи мы знаем, что она попала в список, но временный ответ `list` ещё не помогает прочитать её поля. Вспомним прямой обход знакомой коллекции и готовый formatter; затем проследим путь от пустого списка к повторному просмотру реальных задач.

1. **Точка старта:** add создаёт реальные записи, а минимальная `show_tasks` уже вызывается командой list.
2. **Новый вопрос:** как показать пустое состояние или все карточки, не меняя данные и не придумывая номер по позиции?
3. **Результат:** одна существующая `show_tasks` выводит пустое сообщение либо карточки задач по порядку.

Сначала разделим поведение на два состояния списка, затем пройдём непустой список напрямую и передадим каждую запись готовому форматтеру. Так мы сохраним разделение ответственности: чтение и вывод списка не создают, не ищут и не изменяют задачи.

## 01. Назначение существующей функции

- Что и зачем объяснить: `show_tasks(tasks)` отвечает только за показ переданного списка. Сопоставить её текущую временную ветвь для непустого списка с новой целью: выводить содержимое каждой записи, а не лишь количество.
- Механизм и порядок: сначала определить, пуст ли вход; затем выбрать один из двух путей — сообщить о пустоте и завершить функцию либо перейти к показу записей. Подчеркнуть, что команда `list` и общий список уже существуют; это изменение тела готовой функции, не новое меню или новая операция с данными.
- Пример и типичная путаница: список задач как полка карточек: пустая полка требует отдельного сообщения, а полный обход читает карточки по одной. Не смешивать пустой список с временным ограничением старой функции.
- Первое самостоятельное действие: по двум состояниям входа предсказать, какой путь выполнится и останется ли функция внутри `run`; результат — различены пустой и непустой сценарии до изменения кода.
- Переход к следующему шагу: разобрать, почему обычный цикл сам по себе не выдаёт сообщения для пустого входа.

## 02. Пустой список и раннее завершение

- Что и зачем объяснить: пустой список — допустимое состояние сразу после запуска, а не ошибка. При обходе ноль элементов означает ноль выполнений тела, поэтому пользователь не получает объяснения, почему ничего не появилось.
- Механизм и порядок: проверить длину списка на ноль, вывести предусмотренное сообщение и выполнить `return`, чтобы закончить только `show_tasks`. Вызов вернётся в командный цикл; это не выход из приложения и не команда `exit`. После этой ветви остаётся путь для непустого списка.
- Пример и типичная путаница: сравнить пустой и список из одной записи. Ранний `return` нужен после сообщения именно для прекращения этой функции; он не возвращает задачу или список и не завершает `run`. Не называть обычный нулевой проход цикла ошибкой.
- Первое самостоятельное действие: изменить существующую пустую ветвь и проверить list сразу после запуска; наблюдаемый результат — одно сообщение о пустоте, затем доступно следующее меню.
- Опора для повторного обращения: условие нулевой длины выбирает пустую ветвь; `return` после сообщения заканчивает функцию; после возврата продолжается вызвавший цикл.
- Переход к следующему шагу: на непустом пути каждый проход получит очередную запись.

## 03. Прямой обход записей

- Что и зачем объяснить: объяснить, что переменная цикла поочерёдно связывается с каждым словарём из `tasks`. Здесь не нужно создавать копию, позиционный список или второй цикл.
- Механизм и порядок: после пустой ветви выполнить один прямой `for` по исходному списку; тело получает текущую полную задачу. Один проход соответствует одной записи, а после последней программа выходит из цикла и возвращается из `show_tasks`.
- Пример и типичная путаница: на двух записях назвать текущую задачу в первом и втором проходах. Не путать словарь текущей записи с индексом в списке, количеством записей или постоянным id.
- Первое самостоятельное действие: проследить порядок двух известных задач без написания новых алгоритмов; наблюдаемый результат — ученик указывает, какая запись доступна в каждом проходе и сколько карточек должно появиться.
- Опора для повторного обращения: прямой обход даёт очередной словарь; число проходов равно числу записей; порядок проходов соответствует порядку списка.
- Переход к следующему шагу: вместо повторного форматирования полей передать текущую запись готовой функции.

## 04. Граница между format_task и выводом

- Что и зачем объяснить: восстановить знакомый договор formatter: он принимает одну задачу и возвращает строку карточки. `show_tasks` отвечает за перебор и показ; `print` отображает возвращённую строку пользователю.
- Механизм и порядок: в теле цикла вызвать прежний `format_task` для текущего словаря и вывести полученную строку. Получается цепочка «запись → строка → экран» для каждой задачи. Не переписывать внутри `show_tasks` условия статуса, приоритет или структуру карточки.
- Пример и типичная путаница: сравнить вызов, который возвращает строку, с печатью строки. Одного вызова formatter недостаточно для экранного вывода; повторно собирать карточку в другом месте тоже не нужно.
- Первое самостоятельное действие: на двух полных записях проследить аргумент, результат formatter и место вывода; наблюдаемый результат — по одной полной строке на запись, с сохранением всех её полей.
- Опора для повторного обращения: `format_task` возвращает строку одной записи; `print` показывает строку; список обходит `show_tasks`.
- Переход к следующему шагу: проверить, откуда берётся видимый id и почему чтение не переставляет данные.

## 05. Id, порядок и границы чтения

- Что и зачем объяснить: карточка показывает `id`, уже записанный в словаре. Позиция записи в списке — другое понятие; её нельзя выдать за постоянный номер задачи.
- Механизм и порядок: прямой цикл обходит список как он есть. Не сортировать его и не менять поля; форматтер уже читает нужный id из текущей записи. Показ не добавляет элементы, не меняет статус и не ищет совпадения.
- Пример и типичная путаница: в переданном списке сначала находится запись с id 20, затем с id 3. Карточки выходят в этом же порядке и сохраняют эти id; экранные номера 1 и 2 не создаются. Упорядоченность показа не означает сортировку по id. Повтор list должен сохранить тот же состав и порядок.
- Первое самостоятельное действие: после просмотра двух задач проверить повторный вывод и объяснить, почему id остаются частью исходных карточек; наблюдаемый результат — повторный list показывает те же записи в том же порядке.
- Переход к практике: изменить только прежнее определение `show_tasks`, сохранив связь с `run`, `tasks` и `format_task`.

## 06. Что мы будем делать в практике

**Формат и исходная опора:** основной локальный StudyHub после ожидаемого результата занятия 17; в `run` есть один список задач, add работает, `show_tasks` пока минимальная, formatter готов. Фактическая копия этого состояния требует подтверждения перед этапом 3.

Мы самостоятельно расширим показ списка, проверим пустое и непустое состояние, затем убедимся, что чтение не ломает прежние команды и карточку.

1. **Расширить существующую `show_tasks`:** начать с временной версии, объяснённой в блоке 01; самостоятельно добавить понятный пустой путь из блока 02. После запуска list на пустом `tasks` показывает одно сообщение и возвращается к меню.
2. **Показать реальные задачи:** добавить две записи знакомой командой add и расширить непустой путь прямым обходом из блока 03. Для каждой записи использовать готовую `format_task` и вывести строку согласно блоку 04. Результат: list показывает две полные карточки с правильными полями и реальными id в порядке `tasks`; количество вывода соответствует количеству записей. Повторить list и сравнить поля и порядок, чтобы заметить нежелательное изменение состояния.
3. **Отдельно проверить механизм порядка и id:** после выхода из run продолжить в знакомой интерактивной сессии и создать через существующую фабрику две временные записи с id 20 и 3. Передать их `show_tasks` в таком порядке, не прогоняя через обычный add с последовательной выдачей id. Наблюдаемый результат: первой показана карточка id 20, второй — id 3; ни сортировки, ни подмены id на позиции 1 и 2 нет. Это отдельная проверка механизма обхода и форматирования, а не повтор обычной проверки list.
4. **Проверить форматтер и прежние возможности:** отдельно вызвать готовый formatter для записей со статусами False и True; вывод каждой карточки соответствует её полям. Это не добавляет команду done. В основном run повторно проверить add, неизвестную команду и exit; результат — показ не меняет задачи, а прежние пути продолжают работать.
5. **Сохранить проверенную версию:** после проверки прежних навыков status/diff сопоставить изменение только с расширением показа списка; сохранить и опубликовать осмысленную версию по изученному Git-маршруту. Результат — diff не содержит нового меню, дублирующей функции или случайных изменений.

Порядок действий следует состояниям данных: сначала пустой запуск подготавливает ветвь сообщения, затем add создаёт реальные записи, после чего их чтение проверяет цикл, formatter, поля и порядок. Отдельный вызов `show_tasks` на фабричных записях с id 20 и 3 изолирует именно связь порядка списка с выводом: он отличает прямой обход от сортировки и id записи от экранной позиции. Повторный просмотр помогает заметить нежелательное изменение состояния; прямой вызов formatter проверяет карточку со статусом `True`, не добавляя незнакомую команду. Если фактический вход не совпадает с B занятия 17, практика зависит от предварительного восстановления правильного checkpoint, а не от поздней версии HEAD.

Итог B подтверждён, когда одна существующая функция показывает пустое состояние или все текущие задачи, корректно отображает каждую запись и не меняет общий список. Ранее работающие add, нормализация команды, неизвестная команда и выход продолжают работать. Поиск по id остаётся следующей темой.
