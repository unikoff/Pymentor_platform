## Точка B: результат занятия

- Ученик сможет объяснить, почему статистика считается по текущим значениям `is_done`, а не по количеству команд `done`, и как связаны `total`, `completed` и `left`.
- Ученик сможет самостоятельно написать `build_statistics(tasks)`, которая за один проход считает `total` и `completed`, выводит `left = total - completed`, возвращает словарь со всеми тремя счётчиками и не изменяет список задач.

## 00. Вступление

Предыдущие занятия готовят нас добавлять задачи, находить их и отмечать выполненными. Теперь посмотрим на список целиком: отдельная карточка отвечает на вопрос о себе, а команда `stats` должна показать состояние всего списка. Для ответа мало помнить команды, которые мы вводили; нужно заново посчитать, что содержится в `tasks` сейчас.

1. **Точка старта:** по плану предыдущих занятий работают `add`, `list`, `find`, `done` и `search`, а каждая карточка хранит собственный `is_done`.
2. **Новый вопрос:** как получить согласованные числа по всем задачам и процент выполнения, включая пустой список?
3. **Результат:** команда `stats` показывает актуальные `total`, `completed`, `left` и процент, не меняя задачи.

Сначала отделим состояние карточек от действий, которые к нему привели, затем посчитаем счётчики проходом по списку, отдельно разберём долю и пустой знаменатель, после чего свяжем вычисления с уже существующей ветвью меню. Так новый итог опирается на готовые данные и компоненты, а проверка не создаёт вторую версию Planner.

## 01. Состояние задачи и событие команды — разные вещи

- **Что и зачем объяснить:** поле `is_done` описывает текущее состояние каждой записи. Ввод `done` — действие пользователя; его количество само по себе не сообщает, сколько задач завершено. Статистика отвечает о списке сейчас, а не ведёт историю команд.
- **Механизм и порядок:** найти задачу и прочитать `is_done`; команда `done` может установить `True`; затем повторное выполнение оставляет поле `True`. При подсчёте каждая запись учитывается по своему полю один раз за проход. Результат не зависит от того, однажды или несколько раз вызвали `done` для одной и той же задачи.
- **Независимый пример и путаница:** в списке покупок есть три позиции, из них одна с флажком. Человек нажал на флажок той же позиции ещё два раза, но в конечном списке завершена всё ещё одна позиция. Показываем два пути действий с одинаковыми конечными значениями `True, False, False` и различным числом нажатий; это помогает отделить историю действий от состояния.
- **Первое самостоятельное действие:** до появления ответа сравнить две истории из визуала и указать, чему равен `completed` в каждой и почему повторное `done` не создаёт вторую завершённую задачу. Затем применить правило к изменённой истории, где отмечена ещё одна *другая* позиция: теперь `completed` должен вырасти на один.
- **Опора для практики:** «Состояние читаем из `task["is_done"]`; событие `done` не добавляем в накопитель отдельно».
- **Переход:** чтобы получить сводку всего списка, пройдём по карточкам и будем обновлять счётчики из их состояний.

## 02. Согласованные счётчики за один проход

- **Что и зачем объяснить:** `total` — число всех задач, `completed` — число задач со значением `is_done == True`, `left` — число остальных. Эти величины связаны: `total = completed + left`; `left` можно получить вычитанием после прохода.
- **Механизм и порядок:** перед циклом начать `total` и `completed` с нуля. Для каждой записи увеличить `total` на один; только при истинном `task["is_done"]` увеличить `completed`. После цикла вычислить `left = total - completed`. Каждый счётчик относится ко всему списку, поэтому его нельзя заново обнулять внутри цикла. Значение `True` добавляет к `completed` единицу, а не присваивает туда постоянное `1`.
- **Независимый пример и путаница:** на трёх заявках со статусами `False, True, True` проследить пару `(total, completed)` от `(0, 0)` через `(1, 0)`, `(2, 1)` до `(3, 2)`; только после цикла получить `left = 1`. Для `[]` цикл не выполняется ни разу, поэтому счётчики остаются `(0, 0, 0)`. Сначала показать один рабочий проход, затем сравнить его с ошибкой `completed = 1` внутри `if`: на второй выполненной карточке ошибка даёт неверное значение.
- **Первое самостоятельное действие:** до раскрытия трассы заполнить шаги для другого списка `True, False, True, False`, затем объяснить почему `(total, completed, left) = (4, 2, 2)`. На пустом и полностью выполненном наборах проверить равенство `total = completed + left`, не подставляя туда число вызовов `done`.
- **Опора для практики:** таблица «карточка → `is_done` → `total` после шага → `completed` после шага» и инвариант `total = completed + left`.
- **Переход:** счётчики можно вернуть отдельно от вывода; затем из двух счётчиков вычислить долю выполненных.

## 03. Функция сводки возвращает данные

- **Что и зачем объяснить:** `build_statistics(tasks)` получает актуальный список задач и возвращает словарь со счётчиками `total`, `completed`, `left`. Он отделяет вычисление от отображения: функция не печатает строки меню и не переписывает карточки.
- **Механизм и порядок:** локальные счётчики создаются заново при каждом вызове, цикл читает записи, затем функция собирает рассчитанные значения в один результат через `return`. Следующий вызов снова читает переданный список. Изменения между вызовами видны, потому что список задач меняет `add` или `done`, а не потому что функция копит прежнюю статистику.
- **Независимый пример и путаница:** на двух заявках `True, False` показать ожидаемый *результат вызова*, словарь `{"total": 2, "completed": 1, "left": 1}`, не раскрывая реализацию целевой функции. Сравнить с уже известной `calculate_study_minutes`: она возвращает число длительности, а здесь нужен словарь с тремя именованными полями. `print` показывает значение человеку, `return` передаёт его следующему вычислению; после `print` без `return` вызывающая сторона не получит этот словарь.
- **Первое самостоятельное действие:** по трассе из блока 02 самостоятельно определить, какие три ключа и значения нужно вернуть для нового списка; затем сравнить состояние словарей до вызова и после, чтобы доказать отсутствие изменений `is_done`. Важно, что новый вызов создаёт новые локальные счётчики, а не берёт результат прошлого запуска.
- **Опора для практики:** перечень ключей результата и трасса одного прохода; для проверки вызывать готовую функцию с явно заданным аргументом, не раскрывать список через `run()` и не менять его договор.
- **Переход:** процент использует часть и целое из этой сводки, но остаётся отдельным вычислением.

## 04. Доля и процент на понятной числовой модели

- **Что и зачем объяснить:** процент показывает, сколько составляет часть от целого на шкале из ста. Для задач частью является `completed`, целым — `total`: сначала сравниваем часть с полным количеством, затем выражаем эту долю «на сто». Не предполагать, что формула знакома из математики.
- **Механизм и порядок:** при `total > 0` обе записи корректны: `completed / total * 100` и `completed * 100 / total`. Первая сначала получает долю, вторая сначала умножает числитель; обе затем делят на полное число. В Python оператор `/` даёт дробное деление. Для реализации можно сохранить порядок целевого snapshot: сначала получить отношение, умножить на 100, затем округлить итоговый процент через `round(..., 1)`. Округление применяется один раз к проценту, а не к исходным счётчикам или промежуточной доле.
- **Независимый пример и типичная путаница:** на полоске из четырёх клеток закрасить одну: «1 из 4» означает четверть всей полоски, то есть 25 из 100 таких долей. Разобрать `1 / 4 = 0.25`, затем `0.25 * 100 = 25.0`; эквивалентная запись `1 * 100 / 4` тоже верна при положительном знаменателе. На `1 из 3` показать `1 / 3 * 100 ≈ 33.3` после `round(..., 1)`: раннее `round(1 / 3, 1) * 100` даёт ошибочные `30.0`. При перестановке части и целого `4 / 1 * 100` получается бессмысленное для этой ситуации `400.0`; `//` отбрасывает дробную часть.
- **Первое самостоятельное действие:** до показа результата ученик отмечает часть и целое на новой полоске `2 из 5`, прогнозирует процент, затем объясняет, почему `completed / total` и `completed * 100 / total` используют *те же* два числа. Для `1 из 3` самостоятельно находит место `round(..., 1)` и предсказывает отличие от преждевременного округления.
- **Опора для практики:** «выполнено / всего → доля → доля × 100 → округление до 1 знака».
- **Переход:** прежде чем делить, нужно определить, существует ли целое для этой доли.

## 05. Пустой список проверяем до деления

- **Что и зачем объяснить:** при `total == 0` отношение `completed / total` вычислить нельзя. Для договора Planner пустой список имеет процент `0.0`; это отдельное согласованное значение, а не результат деления на ноль.
- **Механизм и порядок:** `completion_percent(statistics)` сначала получает `total`. Если он равен нулю, функция немедленно возвращает `0.0`; только в другой ветви читает `completed`, вычисляет процент и округляет до одного знака. Порядок условия важен: проверка после деления не защищает пустой случай.
- **Независимый пример и путаница:** пустая корзина не имеет доли «яблок от всех фруктов»; для экрана Planner договором выбираем `0.0`. Показать две возможные дороги исполнения: `total == 0` ведёт сразу к `return 0.0`, положительный `total` ведёт к делению. `0.0` здесь заранее выбранное значение результата, а не частное `0 / 0`; не подменять его делением на условную единицу.
- **Первое самостоятельное действие:** расположить проверку `total == 0` до вычисления дроби и предсказать результаты для пустого набора, половины и трети. Результат должен согласоваться с математическим смыслом и договором интерфейса.
- **Опора для практики:** «сначала `total == 0` → `0.0`; иначе `completed / total * 100`, затем `round(..., 1)`».
- **Переход:** теперь две функции имеют ясные входы и результаты; можно подключить их к существующей команде.

## 06. Команда stats соединяет расчёт и вывод

- **Что и зачем объяснить:** `run()` владеет одним полным `tasks` в течение запуска программы. План 19 уже задаёт `search_tasks` как источник выборки для показа, не заменяющий основной список. Ветка `stats` должна передать в `build_statistics` именно полный `tasks`, затем передать словарь в `completion_percent` и вывести четыре показателя; отдельный постоянный `handle_stats` не нужен.
- **Механизм и порядок:** команда уже нормализована известным `strip().lower()`. После `search` список совпадений существует только для результата поиска; он не становится состоянием Planner и не меняет `tasks`. В ветви `stats` заново считаются все карточки из полного списка, затем вычисляется процент и печатаются подписи «Всего», «Выполнено», «Осталось», «Процент выполнения». Функции расчёта возвращают значения, печатает интерфейсная ветвь. Не передавать `matches` в статистику, не возвращать наружу список из `run()` и не создавать второй `tasks`.
- **Независимый пример и типичная путаница:** при двух задачах (`True`, `False`) `search` показывает одну выполненную, но не меняет `tasks`. Затем `stats` должен показать все четыре строки: «Всего: 2», «Выполнено: 1», «Осталось: 1», «Процент выполнения: 50.0%»; процент получает знак `%` при выводе, функция возвращает число `50.0`. Если передать список совпадений вместо `tasks`, получится ложное «Всего: 1, Выполнено: 1, Осталось: 0, Процент выполнения: 100.0%». Повторный `stats` не меняет сводку; после `add` или `done` следующий вызов отражает новое состояние. `calculate_study_minutes` остаётся прежней самостоятельной функцией, новую команду `calc` не вводить.
- **Первое самостоятельное действие:** спрогнозировать результат `search` по фрагменту одной из двух задач, затем полный `stats`; назвать ожидаемые четыре поля (`2`, `1`, `1`, `50.0%`) и ошибочные (`1`, `1`, `0`, `100.0%`) при подсчёте только найденной карточки. Объяснить, что это *подписи и значения*, а не запись арифметического деления через `/`. После этого спрогнозировать повторный `done` и добавление третьей задачи.
- **Опора для практики:** цепочка вызовов `run → build_statistics(tasks) → completion_percent(statistics) → print`; отдельно проверять поля возвращённой сводки и строки вывода.
- **Переход к практике:** реализовать обе вычислительные функции, подключить последнюю команду и проверить её на настоящем списке, полученном через знакомые действия.

**Роль содержательных вставок для будущей MAIN-подачи:** в блоке 01 сопоставить два пути `done` с одной и той же конечной картиной и попросить предсказать `completed` до раскрытия; в блоке 02 дать наглядную таблицу прохода с одной незаполненной строкой, которую ученик заполнит сам; в блоке 04 показать полосу из четырёх клеток и затем предложить перенести смысл доли на две из пяти; в блоке 05 — простую развилку `total == 0` / `total > 0` с прогнозом пути вычисления; в блоке 06 — схему потока полного `tasks` через обе функции к четырём строкам интерфейса, которую ученик сопоставит с поисковой выборкой. Между такими вставками давать объяснение и вывод, оставляя не больше двух подряд читаемых абзацев без учебного действия или осмысленного визуала. Не ставить подряд декоративные схемы и повторные вопросы на одно различие: каждый элемент должен проверять следующий шаг мысли.

## 07. Что мы будем делать в практике

**Обязательный формат — проект в том же локальном StudyHub, один `main.py`.** Для подготовки к изменению проекта предусмотрена одна короткая кодовая работа платформы `19.1` с двумя функциями и готовыми проверочными вызовами; это упражнение на их договор, а не второй Planner и не замена локальной интеграции. Общий результат: одна текущая сводка вычисляется из списка задач, безопасно обрабатывает пустой набор и показывается по команде `stats`. Состояние карточек и прежние возможности сохраняются.

1. **Одна кодовая работа платформы: получить словарь счётчиков.** После блоков 01–03 дан `tasks` со знакомыми четырьмя полями задач и стартовые вызовы *ниже* места для функций. На списках `[]`, `[False, True, False]` и `[True, True]` (показаны только значения `is_done`) сначала предсказать счётчики по трассе блока 02, затем сверить с таблицей ниже и выводом стартера. Проверка после каждого ввода: `total = completed + left`, исходный `tasks` не изменился; при повторном вызове счётчики начинают расчёт заново.
2. **В той же работе: вычислить процент из переданного словаря.** После блоков 04–05 самостоятельно написать `completion_percent(statistics)`, где входом является *словарь*, а результатом — число, не строка с `%`. Сначала проверить `total == 0`, лишь затем вычислить долю и `round(..., 1)`. Проверить пустой, наполовину выполненный, выполненный на треть и полностью выполненный наборы по таблице ниже. Стартовые вызовы должны показать три счётчика, оба процента и исходный список; его содержимое не меняется.
3. **Перенести только определения в реальный `main.py`.** После успешного самостоятельного решения первых двух шагов вставить обе функции рядом с другими вычислительными функциями Planner. В уже существующем ответвлении `stats` сначала получить словарь от `build_statistics(tasks)`, затем процент от `completion_percent(statistics)`, затем вывести четыре подписанных значения, добавив `%` лишь в строке вывода. 4. **Самостоятельный сценарий в одном запуске Planner: проверить изменение состояния, не частоту команд.** Через `add` создать две задачи с разными названиями и фактически записать выданные им id; через `done` выполнить только первую. Выделить причину отличия: новая задача увеличила `total` и `left`, а поиск и повтор `done` не изменили количество текущих выполненных карточек.
