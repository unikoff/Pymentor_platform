## Место в маршруте

Занятие продолжает готовый поиск задачи по id: из пользовательского ввода получается положительное число, `find_task` возвращает исходную запись или `None`. Теперь добавляется одно действие, меняющее состояние найденной задачи. Следующее занятие использует обновлённый Planner для поиска нескольких задач по названию. Не добавляем второй цикл поиска и не меняем модель задачи.

## Точка A: планируемая опора, требуется сверка перед практикой

- **Планируется по B занятия 18:** `read_task_id` принимает только положительный целый id, `find_task(tasks, task_id)` возвращает **тот же словарь** из `tasks` либо `None`, а `handle_find` уже вызывает их в действующем Planner. Предыдущий план содержит объяснение и самостоятельную проверку этих результатов, но сам план **не подтверждает освоение**. Перед занятием сверить, что ученик действительно выполнил поиск первой/средней/последней записи и обработал отсутствующий id.
- **Планируется по более раннему маршруту:** словарь с полями `id`, `title`, `priority`, `is_done`, присваивание значения по ключу, `True`/`False`, `if`, `return` и передача одного изменяемого объекта между функциями (паспорт указывает 4.1, 8.1, 11.1 и путь 16–17.1). Их освоение по этой версии курса **не проверено**: до первого изменения поля дать в разделах 02–04 короткую проверяемую трассу ссылки и условия; если ученик не объясняет её, выполнить подготовительный пример.
- **Проект: версия входа не подтверждена.** Нужен основной локальный `main.py` после занятия 18 с общим `tasks` внутри `run` и готовыми add/list/find. Исторический кандидат B3 `45d0096fe4a1b66bce6a0a3557e9712c598ee965` и поздний финальный снимок не доказывают этот checkpoint. Перед правкой проверить текущие сигнатуры `find_task`, reader, handler и наличие временной ветки `done`, чтобы заменить её без перестройки других команд.
- **Если вход не готов:** закончить именно B занятия 18 и проверить поиск/`None`, затем выполнять зависимые шаги 18.1. Не имитировать готовность функцией-заглушкой или новым списком задач.

## Точка B: результат занятия

- **Ученик сможет объяснить:** почему результат `find_task` связан с записью в `tasks`; почему изменение копии не меняет состояние приложения; как отличить булев результат «запись найдена» от значения поля `is_done`; почему повторная команда не создаёт новое событие.
- **Ученик сможет сделать:** повторно использовать поиск, проверить отсутствие записи до доступа к её полям, изменить только `is_done` найденной задачи и передать результат в handler.
- **Результат в проекте:** `mark_task_done` и `handle_done` подключены к команде `done`; найденная задача получает состояние выполнения, остальные записи и поля остаются прежними.
- **Как подтвердим:** изменение видно через прежние `list` и `find`; неизвестный id не меняет список; повторное `done` оставляет статус True и не меняет число записей.

## Границы и передача дальше

- **Пока не требуем:** новый алгоритм поиска, поиск по названию, копирование списка/записи, отдельную функцию для события перехода, хранение между запусками, классы или новую архитектуру. Не перехватываем широким `except` ожидаемый `None`.
- **Передаём следующему занятию:** рабочие add/list/find/done и общее состояние задач; готовый done остаётся без повторного поиска и не повреждает другие карточки. Занятие 19 добавит поиск совпадений по названию.

## 00. Вступление

Когда запись уже найдена, следующий шаг — применить к ней намерение пользователя и проверить, что приложение изменило именно нужные данные. Одного сравнения id недостаточно: мы должны понять, что возвращает поиск, где живёт запись и какой результат сообщает операция.

1. **Точка старта:** после занятия 18 поиск по id возвращает исходную задачу либо `None`; список задач уже принадлежит текущему запуску.
2. **Новый вопрос:** как отметить выбранную запись выполненной, не повторяя поиск и не затрагивая соседние задачи?
3. **Результат:** команда `done` адресно меняет `is_done`, сообщает об исходе и сохраняет работоспособность list/find.

Порядок для новичка: сначала выяснить, что вернул готовый поиск; затем увидеть, почему найденный словарь — часть общего списка; только после этого менять `is_done` и разбирать булев результат. Последний шаг — связать готовую операцию с читателем id и меню. Цепочку вызовов показывать после объяснения каждого её звена.

## 01. Исходные данные и договор нового действия

- **Что объяснить:** у каждой задачи четыре уже знакомых поля; `is_done` — состояние конкретной записи, а не счётчик команд. Задачи принадлежат одному списку `tasks` текущего запуска. Вход новой модельной операции `mark_task_done(tasks, task_id)` — этот список и уже проверенное положительное число. Выход — булево «запись существует»; эффект — установка `is_done = True` только у найденной записи.
- **Первый пример без новой функции:** на двух разных задачах с id 3 и 7, у обеих `is_done = False`, предсказать, что должно и чего не должно измениться после `done 7`. Визуал «до → после» показывает один изменённый флаг при прежнем количестве, порядке, id, названии и приоритете.
- **Самостоятельный прогноз:** для id 3, 7 и отсутствующего 99 назвать выбранную запись или отсутствие, до просмотра реализации. Только затем перейти к готовому `find_task`, объяснив почему он нужен новой операции.
- **Опора:** разделы 02–05 реализуют договор модели; раздел 06 добавляет обработчик и ветку меню. На этом шаге не показывать необъяснённый готовый `mark_task_done` как шаблон для копирования.

## 02. Найденная запись или None

- **Механизм до первого кода:** разделить два вопроса. `read_task_id` из 18 повторяет ввод, пока число не будет целым и `> 0`; `find_task` затем проверяет существование такого id **среди реальных задач**. Даже корректный ввод `99` законно даёт `None`.
- **Разбор ветви:** локальное имя `found` хранит результат одного вызова `find_task(tasks, task_id)`. Проверка `found is None` означает «поиск не нашёл запись». Только после этой проверки в успешной ветви можно обращаться к ключам словаря; в неуспешной ветви операция сразу возвращает `False` и ничего не меняет. Объяснить `is None` как проверку специального результата отсутствия (уже знакомого из 18), а `return` — как прекращение функции. Никакой новый поиск внутри операции не писать.
- **Независимый пример:** список содержит id 3 и 7. Сопоставить `find_task(tasks, 7)` → исходный словарь и `find_task(tasks, 99)` → `None`; нарисовать две дорожки с точкой выхода, пока без записи `is_done`.
- **Различающий прогноз ученика:** для id `-2` назвать ответ reader (повтор ввода), для `99` — ответ модели (`False`), для `7` — разрешённый переход к словарю. После прогноза обсудить, почему строка `found["is_done"]` недопустима при `None`. Механизм наблюдаем через разные ветви, не через второй однотипный вопрос.
- **Переход:** проверка доступа защищает от ошибки, но ещё не объясняет, какой именно объект будет изменён.

## 03. Ссылка ведёт к общей записи

- **Механизм:** `tasks` хранит словари, а `find_task` из 18 возвращает ссылку на *имеющийся* словарь. Имя `found` и `tasks[1]` в короткой демонстрации могут указывать на один объект. Выражение `found["is_done"] = True` заменяет значение по ключу **этого объекта**, поэтому следующий `list` читает новое состояние. Слова «найден», «передан» и «изменён» не означают «скопирован».
- **Независимый визуал с действием:** один прямоугольник-словарь и две стрелки (`tasks[1]`, `found`) к нему. Перед показом изменения ученик указывает, куда ведёт присваивание; затем на визуале появляется обновлённое поле и чтение через другое имя. Отдельная бледная копия на сравнении объясняет, почему изменение *самостоятельно созданного другого словаря* не обновило бы запись в списке. Не уходить в копирование вложенных структур.
- **Краевой вопрос:** `found = other_task` (где `other_task` заранее указывает на другой словарь) переназначает локальное имя; это не замена словаря внутри `tasks`. В этой паре примеров явно различить переназначение переменной и изменение значения **по ключу**. Если это знание не подготовлено в прежнем маршруте, сначала кратко разобрать стрелки и присваивание на двух словарях.
- **Самостоятельное действие:** дать схему с двумя разными id и двумя стрелками. Ученик сначала предсказывает статус после `found["is_done"] = True`, затем отмечает, что увидит прежний `list` для обеих записей; результат обосновывает общностью объекта, а не равенством id.
- **Переход:** теперь можно определить, как меняем состояние найденной записи, не затрагивая другие поля.

## 04. Меняем только состояние задачи

- **Механизм:** после ветви `None` ровно одно присваивание `found["is_done"] = True` означает «сделать выполненной». Это **установка** состояния. Не использовать `not found["is_done"]`: такое переключение сделало бы повторную команду отменой выполнения.
- **Различающий пример:** запись id 7 начинала с `False`, id 3 — с `False`. После `done 7` ожидаем `True` только у id 7; после повторного `done 7` оба состояния такие же. Число задач, `id`, `title`, `priority` и порядок не меняются в обоих случаях. Для исходного `is_done = True` первая команда также не создаёт нового эффекта.
- **Активный визуал «до/после/повтор»:** ученику предложить найти единственную изменившуюся ячейку на двух карточках; затем предсказать повтор **до** раскрытия третьего состояния. Это проверяет отличие установки флага от переключения, а не знание названия команды.
- **Переход:** поле изменено, но вызывающему коду нужен отдельный ответ о том, нашлась ли задача.

**Первая связанная группа для будущей MAIN-подачи:** `find_task` возвращает исходную запись или `None` → проверка защищает доступ к полям → изменение по ключу у найденного словаря меняет видимое состояние `tasks`. Показать как единый причинный маршрут после трёх объяснений (связанные тезисы, не ещё три повторных карточки). Ученик на новой паре id должен указать точку, где отсутствие останавливает эффект.

## 05. Булев ответ означает наличие записи

- **Договор возврата:** `False` при `None` — id в задачах отсутствует и эффект не произошёл; `True` при найденной записи — операция обработала существующую задачу и её поле теперь True. Объяснить два разных места булевых значений: **`return True` — ответ вызывающему коду**, а **`found["is_done"] = True` — сохранённый статус в словаре**. Первое не присваивает статус, второе не заменяет `return`.
- **Различение на трёх состояниях:** новая незавершённая задача → ответ `True`, статус становится True; уже выполненная → ответ тоже `True`, статус остаётся True; отсутствующий id → ответ `False`, никакая запись не меняется. Не называть второй успешный ответ «ещё одна завершённая задача».
- **Микропрогноз:** дать ученику таблицу входных состояний без столбцов «ответ/новое состояние»; он заполняет оба столбца и обосновывает, почему для повторного вызова ответ и эффект не одно и то же. Только после прогноза показать заполненную таблицу и проверить отсутствие противоречий.
- **Переход:** handler может сообщить «задача отмечена» или «задача не найдена» по ответу модели, не разбирая словарь сам.

## 06. Команда done в существующем цикле

- **Роли объяснить в порядке появления вызовов:** `run` хранит общий `tasks` и по введённой команде выбирает `handle_done(tasks)`; handler вызывает знакомый `read_task_id()`, затем `mark_task_done(tasks, task_id)`; модель использует `find_task` из 18, меняет словарь и возвращает bool; handler печатает сообщение, после чего цикл `run` снова показывает меню. Функции в текущем проекте могут иметь иной состав аргументов: при внедрении сверить реальные сигнатуры, сохранить общий объект и уже принятый способ вызова.
- **Две видимые ветви:** при недопустимом вводе (`0`, текст) reader повторяет вопрос и до модели дело не доходит; при корректном отсутствующем `99` модель отвечает `False`, handler сообщает об отсутствии, меню продолжает работать. При существующем id handler выводит подтверждение; изменение затем видно и в `list`, и в `find`. Все три случая показать на **одном** маршруте взаимодействия, чтобы не создавать три одинаковые схемы.
- **Самостоятельная трассировка:** на новом сценарии ученик расставляет номера у шагов `read_task_id`, `mark_task_done`, `find_task`, сообщения и повторного меню; затем объясняет, почему handler не должен обходить `tasks` и почему второй `find_task` внутри `handle_done` был бы дублем.
- **Содержательная вставка для MAIN:** компактная схема «`run` → handler → reader/model → поиск → возврат bool → сообщение» с подсветкой места изменения `tasks` и места только чтения результата. После схемы — самостоятельный выбор сообщения по уже рассчитанному bool, не ещё один декоративный опрос.
- **Вторая связанная группа:** `return` модели обозначает наличие → handler превращает результат в сообщение → `list/find` независимо читают изменённую запись. Показать как три связанных причинных вывода после трассы, затем вернуться к общему исходному инварианту: один объект, одно изменяемое поле.
- **Переход к практике:** в локальном Planner ученик сам пишет модельный шаг, связывает handler и проверяет наблюдаемый эффект через прежние команды. Для 1400–1900 слов видимой теории MAIN нужен один развёрнутый пример каждого нового механизма и короткие возвраты к опоре; между содержательными схемами/прогнозами не оставлять больше двух подряд читаемых абзацев, но не превращать объяснение в цепь опросов.

## 07. Что мы будем делать в практике

**Формат:** только основной локальный StudyHub/Planner, его существующий `main.py` и история Git. Это самостоятельное изменение работающего приложения, не отдельная программа `solve` и не упражнение на переписывание готовой функции. Для подготовки разрешены короткие вызовы функций с явно заданными словарями в той же среде, но итог доказывает работающий CLI. Задачи создаются через `add` **в одном запуске**; локальный `tasks` внутри `run` не обещать доступным после выхода в оболочку.

**Вход перед первым действием (A, проверка факта):** ученик в основном проекте показывает на двух задачах `list`, корректный поиск каждой через `find` и безопасный результат для отсутствующего положительного id; при необходимости создаёт их через `add`. Проверить реальные сигнатуры `find_task` и `read_task_id`; при необходимости закончить практику 18 до перехода к `done`. Убедиться, что `done` сейчас ещё временная ветка. Это проверка предыдущего результата **до редактирования**; после изменения кода заново запустить CLI и создать две задачи для итогового сценария, поскольку список текущего запуска не сохраняется. Отсутствие этих результатов — зависимость от предыдущего занятия, а не повод создавать второй список/новый reader.

**Практика 1. Самостоятельно написать модельную операцию.**

- **Дано:** `tasks` и положительный `task_id`; готовый `find_task` возвращает исходный словарь либо `None`. Ученику показан ранее *другой* пример ссылок с id 3 и 7, но не полный код `mark_task_done`.
- **Сделать самому:** спроектировать две ветви, вызвать существующий поиск один раз, безопасно обработать `None`, установить поле только у найденной записи и вернуть `bool` по договору. Выбрать место функции рядом с другими модельными действиями, не копируя карточку и не меняя контракт поиска. Опора: 02 (отсутствие) → 03 (ссылка) → 04 (установка) → 05 (ответ).
- **Локальный критерий:** для отсутствующего id возвращается `False` и все записи прежние; для существующего — `True`, нужный `is_done` равен True; второй вызов для того же id возвращает `True` без дополнительного изменения. Если применялся изолированный вызов с явными словарями, сначала объяснить входные аргументы и где именно наблюдается изменённый объект; он не заменяет CLI-проверку.

**Практика 2. Подключить операцию к пользователю.**

- **Дано:** знакомые `run`, `read_task_id` и `handle_find` как образец границы между вводом и моделью; временная команда `done` в существующем меню.
- **Сделать самому:** написать `handle_done` с вызовом готового reader и созданной модельной операции; по `bool` вывести сообщение об успехе либо об отсутствии записи, затем подключить handler к `done` в `run`.
