## 01. Что именно доказывает проверка

- **Смысл (ориентир MAIN: 250–290 слов).** Проверка — это вопрос, на который можно ответить фактом: «после этой команды вижу такой вывод, а список задач стал таким». Сначала формулируем ожидаемое поведение **до** запуска; затем запускаем; только после этого сравниваем. Существование `def search_tasks`, красивый экран и чистый `git status` говорят о разных вещах и не доказывают работу всей программы. Источник ожидания — договор из пройденных занятий; источник наблюдения — конкретный запуск. Объяснить слова «состояние» (данные в `tasks` сейчас) и «побочный эффект» (изменение данных после команды) на знакомых примерах, без новой терминологической нагрузки.
- **Механизм и независимый пример.** Воображаемая библиотечная стойка имеет две карточки: «Остров» и «Горы». Сотрудник показывает только «Остров» по запросу — это не удаляет «Горы» из каталога. Если сотрудник отмечает «Остров» как выданную, меняется отметка именно этой карточки. Граница аналогии: в Planner `search` действительно выбирает совпадения по тексту, `done` действительно изменяет `is_done`, но проверять эффект будем по собственному запуску, а не по рассказу. Связать с известными командами: `list/find/search/stats` читают, `add/done` изменяют; `exit` завершает процесс.
- **Первое самостоятельное действие.** Для другого набора из одной книжной карточки ученик сам заполняет три поля: ожидаемый видимый результат запроса, ожидаемое состояние до/после, причина отсутствия изменения. Затем различает два утверждения: «на экране одна найденная запись» и «в исходном списке одна запись». Критерий: корректно отделены показанный результат и основной список.
- **Опора и будущая подача.** Ввести мини-таблицу `ввод/команда | ожидали увидеть | ожидали в tasks | увидели | вывод`; сначала показать одну частично заполненную строку, остальные ученик заполняет позже. После объяснения — содержательная пара «предскажи вывод / предскажи состояние», а затем схема чтения/изменения с отмеченными стрелками. Не дублировать одинаковый вопрос карточками: одна вставка проверяет прогноз, другая объясняет причину. При несовпадении записываем вход и факт, пока ничего не исправляем.
- **Переход.** Для сравнения нужен известный исходный список; начинаем с пустого запуска.

## 02. Запуск от пустого состояния и порядок сценария

- **Смысл (ориентир MAIN: 210–250 слов).** Один запуск — одна история работы с `tasks`: функция `run()` создаёт список **перед** циклом меню. Внутри цикла повторные команды работают с тем же списком. Сам факт «задач ещё нет» — нормальное состояние, которое особенно хорошо выявляет деление на ноль и обращение к отсутствующей записи. На схеме показать `run() → tasks=[] → меню → следующая команда → то же tasks`, не углубляясь в новые области видимости.
- **Два разных отказа.** Когда вводят `abc` вместо id, ранее изученный reader не может принять положительное число и повторяет запрос. Когда вводят корректное число, которого нет среди id, преобразование уже прошло, а поиск должен вернуть отсутствие (`None`), которое обработчик превращает в понятное сообщение. Не выводить поля из `None`. На другой ситуации — поиск номера стола в пустой ведомости — показать разницу «номер написан неправильно» и «такого номера нет».
- **Первое самостоятельное действие.** Ученик предсказывает `list` и `stats` на пустоте (`0/0/0/0.0%`), затем результат поиска корректного отсутствующего id и поведение при текстовом id; после запуска отмечает в таблице, какой случай вернул в меню, а какой повторил ввод. Критерий: программа не падает, `tasks` пуст, ожидания не подменены фактом.
- **Визуал и возврат.** Мини-схема «reader: недопустимое значение → спросить снова / допустимое, но не найдено → сообщить и вернуться» нужна для различения причин, не для украшения. Опора: `total = completed + left`, для пустого списка доля `0.0`, новый процесс начинается пустым (проверим в §05).
- **Переход.** После проверки пустого состояния можно пробовать ввод, который прежде ломал добавление.

## 03. Ошибочный ввод и отсутствие частичного добавления

- **Смысл (ориентир MAIN: 260–310 слов).** `add` должен создать **одну целую** задачу с названием и приоритетом 1–5. Пока ученик ошибается в любом поле, никакой «недозаполненной» задачи в `tasks` быть не должно. Разделить два уже известных шага: `read_title()` и `read_priority()` собирают допустимые значения, а `add_task` добавляет запись после их получения. Не вводить новые исключения или общие механизмы транзакций.
- **Механизм до испытания.** Маршрут из кода B43: запрос названия → `strip()` → повтор при пустоте; запрос приоритета → `int()` под обработкой **только** `ValueError` → повтор при ошибке преобразования или значении вне 1–5; затем `add_task` / `append`. `"  "` превращается в пустое название; `"два"` не становится целым; `-2` становится целым, но не подходит по диапазону; `"  Звонок домой  "` сохраняется без внешних пробелов, с внутренним пробелом. Это три разные причины решения, какую просьбу повторить. Схема показывает первую точку изменения списка (`append`), чтобы слово «без частичного добавления» получило точный смысл.
- **Независимый пример и действие.** В воображаемой форме бронирования нужно заполнить место и число гостей. Известна последовательность проверки обоих полей до подтверждения. Ученик получает новые значения и сам отмечает: какое поле повторно запросить, можно ли уже добавить запись, почему. Затем переносит эту логику на вызовы собственного `main.py`: прогнозирует повторение при неверном приоритете и одну запись после принятого ввода.
- **Граница наблюдения.** Пока `read_priority()` ждёт ответ, `run()` не может одновременно принять команду `list`; нельзя заявлять, что ученик проверил `tasks` через меню **внутри** ожидания. Два доступных доказательства разной силы: просмотр порядка вызовов до `append` и последующий `list` показывают причинную цепочку и итог; непосредственное состояние во время ожидания видно только при отдельной остановке в отладчике. Автор MAIN должен обозначить эту разницу, не требуя отладки как обязательного нового навыка.
- **Прогноз и вставка.** Содержательная трассировка `неудачный ввод → reader → нет append → новый вопрос` и небольшой выбор причины ошибки; между ними дать объяснение результата. Опора для возврата: «оба значения готовы → один add_task; не готовы → ни одного append». После удачного добавления переходим к общим чтениям и изменениям.

## 04. Согласованная работа списка, поиска и статистики

- **Смысл (ориентир MAIN: 310–360 слов).** Все семь команд должны работать с **одним и тем же** `tasks` за один запуск. `list/find/search/stats` показывают сведения без изменения карточек. `add` увеличивает список, `done` меняет `is_done` одной найденной записи; повторный `done` оставляет `True`. `stats` смотрит на текущие статусы, а не считает вызовы `done`. Не требовать, чтобы ученик впервые написал поиск или вычисление процента: это B предыдущих занятий, здесь он проверяет их совместную работу.
- **Независимый пример.** В мини-каталоге книг две записи с общим словом «Путешествия», у одной есть слово «Горы», у другой — «Река». Предсказать, что поиск по общему слову показывает две, по «Горы» одну, но в исходном каталоге по-прежнему две. Показать отдельно выбранную карточку каталога до и после **условной отметки**; это аналогия результата, а не новая команда Planner. Граница: в приложении поиск учитывает регистр/пробелы запроса по договору `search_tasks`, а `done` адресует **id**, не текст.
- **Механизм сценария.** В Planner при двух незавершённых задачах первый `done` делает `completed=1`, `left=1`, `total=2`; процент `1/2 × 100 = 50.0`. Повторный `done` не меняет эти значения; третья незавершённая задача даёт `1/3 × 100 = 33.3` после округления до одного знака. Объяснить, что `total = completed + left` проверяется независимо от красивого сообщения `stats`. Пустой запрос поиска отличается от непустого без совпадений; оба не должны менять `tasks`. `find` по отсутствующему id возвращает отсутствие, не меняет карточки.
- **Первое самостоятельное действие.** На другом наборе из трёх уже заданных карточек ученик **сам выбирает** одну для изменения, прогнозирует, сколько записей найдёт по двум разным словам и что покажет сводка после `done`, затем объясняет изменение счётчиков. Ответ не сводится к угадыванию `True/False`: нужно назвать, какая карточка меняется, какие остаются прежними и почему.
- **Визуал и возврат.** Два снимка одной мини-таблицы задач («до поиска / после поиска / после done») с подсветкой реально изменённого поля; после сравнения — одна задача на восстановление пропущенной строки `total/completed/left/%`. Не ставить подряд карточки о том, что `list` и `find` «только читают». Опора: `search` возвращает набор результатов, `tasks` остаётся прежним; `done` меняет только найденный объект; процент вычисляется из текущих состояний.
- **Переход.** Теперь отделим срок жизни такого состояния от срока жизни файлов программы.

## 05. Выход и граница между кодом и данными

- **Смысл (ориентир MAIN: 180–220 слов).** `exit` заканчивает цикл и процесс; при следующем вызове `run()` создаёт новый пустой `tasks`. Код `main.py` при этом остаётся записанным файлом. Git хранит снимки **файлов**, которые добавили в commit, а не содержимое списка в оперативной памяти. Привычная аналогия: написать рецепт на бумаге и приготовить блюдо — сохранение рецепта не сохраняет приготовленную порцию. Граница аналогии: файлы проекта можно версионировать, а временные объекты процесса текущий Planner не сохраняет.
- **Различающий пример.** После двух добавлений и одного `done` ученик предсказывает четыре вещи: какие задачи увидит в прежнем процессе, что покажет новый `list`, исчезнет ли текст `main.py` и появятся ли задачи от команды `git push`. Затем объясняет, почему отсутствие задач во втором процессе — ожидаемый результат, а обещание хранения в README стало бы ошибкой.
- **Визуал и опора.** Разделённая схема «память текущего run: tasks → конец процесса» и «файлы проекта → Git commit»; одна стрелка на новый `run()` с пустым списком. Вставка нужна для предсказания, что исчезнет, а что останется. Вернуться к ней перед README: там обязателен честный пункт «задачи хранятся только до выхода».
- **Переход.** Проверенные свойства и ограничения теперь можно передать другому человеку текстом.

## 06. README как проверяемая передача

- **Смысл (ориентир MAIN: 300–360 слов).** README — инструкция для другого человека, который не присутствовал при нашем запуске. Нужен минимум Markdown **до** создания файла: `#` с пробелом — заголовок, обычные строки — описание, `-` с пробелом — пункт списка, три обратные кавычки — выделенный блок команд. Показать маленький **иной** пример («Как запустить учебный калькулятор» с вымышленной командой), не готовый README Planner. Блок команд позволяет скопировать текст, но сам по себе не подтверждает его работу.
- **Порядок документа.** (1) Назначение Planner; (2) требование реально установленного **системного Python 3.12** и отсутствие внешних библиотек (сначала проверить `python --version` для выбранной команды); (3) путь к папке проекта и буквальная команда запуска `main.py`, проверенная в этой среде (например, `python main.py`, **только если** она вызывает Python 3.12); (4) все семь изученных команд и проверенный пример 2/1/1/50.0%; (5) ограничения: отсутствие сохранения задач между запусками; (6) свой репозиторий/URL и идентификатор опубликованной версии. Путь, URL и команды подставляет ученик по своему проекту — не выдумывать их в теории. Не упоминать возможности из будущих уроков.
- **Проверяемый механизм передачи.** После написания README ученик открывает терминал в указанной папке, буквально копирует **собственную** команду запуска, сравнивает экран с инструкцией и исправляет расхождение в описании или действительно сломанном коде. Затем проверяет `.gitignore` на `__pycache__/` и `*.pyc`, `git status`, различие unstaged/staged (`git diff` / `git diff --cached`); добавляет в commit **только** проверенные относящиеся файлы и отправляет через известный предыдущим урокам `push`. Если изменений нет, не создаёт фиктивный commit, а называет точный уже опубликованный hash и проверяет его наличие в удалённом репозитории. `push` передаёт историю файлов, не задачи из памяти.
- **Первое самостоятельное действие.** На отдельной короткой инструкции ученик находит два неподтверждённых обещания (например, «данные сохраняются после выхода» или непроверенная команда запуска), исправляет текст и объясняет требуемое доказательство. Затем сам строит README для Planner по своей таблице наблюдений; MAIN не выдаёт готовый целевой файл. Локальный критерий — каждое утверждение имеет собственный факт проверки, а команды выполняются буквально.
- **Визуал и возврат.** Одна таблица соответствия «строка README → откуда взялось подтверждение», после неё упражнение на исправление обещания; не ставить две соседние карточки об одном факте. Опора: факты сценария → Markdown → буквальный запуск → status/diff → опубликованный commit. Эта цепь готовит следующую независимую проверку в чистом clone, но clone здесь не выполнять.

## 07. Что мы будем делать в практике

**Формат и исходная опора:** проект — тот же локальный StudyHub и один `main.py` после результата занятия 19.1. Планы 16–19.1 заполнены; план 19.1 задаёт B: все семь команд, две функции статистики и ветвь `stats`. До запуска ученик подтверждает собственный исходный путь, ветку и commit и сверяет фактический проект с B43. Наличие заполненного плана или позднего кода не заменяет подтверждение. Текущая доступная копия после занятия 105 не является входом A этого урока.

**Как работать новичку.** Перед вводом команды ученик сам вписывает в свою копию протокола **ожидаемый вывод** и **ожидаемое состояние `tasks`**; после ввода отдельно записывает увиденное. Состояние проверяется через доступные `list`/`stats`/`find`, а там, где состояние во время ожидания reader не видно через меню, — только по разбору порядка вызовов или необязательному наблюдению в отладчике. «Ожидал» и «наблюдал» — разные графы; не заполнять последнюю предполагаемым результатом. При несовпадении: повторить вход, записать фактическое сообщение и разницу, найти соответствующую функцию из прежних занятий, исправить только причину и повторить этот и ближайший связанный случай. Если совпадает, код менять не нужно.

Связный маршрут самостоятельной практики (MAIN оформит эту последовательность одним `LinkedNotes variant="connected"`; таблицы ниже задают подробный предметный договор):

1. **Этап 0 — вход:** установить путь, commit и соответствие своего проекта B43 → известна проверяемая версия, а отсутствие A явно обозначено.
2. **Этап 1 — пустота:** самому спрогнозировать и запустить пустой `list`/`stats`, неверную команду и отсутствующие id → список остаётся пустым, меню продолжает работу.
3. **Этап 2 — ошибка ввода:** заранее придумать пару названий для поиска, затем попробовать неправильные и допустимые значения для первого `add` → до полного ввода нет частичной записи, после него ровно одна задача.
4. **Этап 3 — поиск:** добавить второе заранее выбранное название с общим и отличающим фрагментами, предсказать количество совпадений → `search` показывает две/одну запись и сохраняет исходный список.
5. **Этап 4 — изменение:** выбрать id для `done`, повторить его и прибавить третью задачу → меняется один статус, а `stats` согласуется с текущими тремя карточками.
6. **Этап 5 — перезапуск:** предсказать, что исчезнет после `exit`, и проверить новый запуск → память задач пуста, файлы кода на месте.
7. **Этап 6 — передача:** самостоятельно написать README из фактов, буквально выполнить инструкцию и проверить опубликованную версию → другой ученик получает проверяемый путь к следующему уроку.

Каждый результат становится входом следующего этапа, кроме нового запуска после `exit`: там пустое состояние **ожидается**, а не считается потерей файла. Таблица задаёт сценарий будущего прохождения; колонка «фактическое наблюдение» остаётся пустой до настоящего запуска. Этот план не подтверждает, что приложение уже запускалось или прошло приёмку.

Общий результат — полный проверенный сценарий в основном проекте, минимальные исправления только при доказанном дефекте, README по фактическому поведению и известная опубликованная версия для чистого clone в занятии 20.1.
