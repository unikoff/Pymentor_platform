## 00. Вступление

У программы уже есть команды, но список команд ещё не доказывает, что приложение ведёт себя правильно вместе. Чтобы передать Planner дальше, сначала сравним то, что должны увидеть, с результатами настоящего запуска; затем запишем в README только то, что действительно проверили.

1. **Точка старта:** по паспорту предыдущий шаг должен передать один StudyHub с семью командами и готовой статистикой; фактический результат занятия 19.1 требуется подтвердить до практики.
2. **Новый вопрос:** как связанный запуск, включая ошибки и новый старт программы, покажет, какие свойства Planner работают и что можно честно обещать в README?
3. **Результат:** проверенный продукт, минимальные причинные исправления при необходимости, README с фактическими командами и опубликованная версия для независимой проверки в занятии 20.1.

Сначала отделим требование от наблюдения и подготовим последовательность приёмки. Затем проверим пустое состояние и ошибки ввода, проследим чтение и изменение задач, проверим статистику и повторный запуск. Только после этого опишем продукт и пройдём инструкцию README. Так документация и опубликованная версия будут опираться на результат, а не на предположения.

## 01. Что именно доказывает проверка

- Что и зачем объяснить: приёмка сопоставляет заранее определённое поведение с выводом и изменением данных. Успешный запуск, чистый `git status` или наличие функции по отдельности не доказывают весь договор. Развести три источника: паспорт задаёт ожидаемые свойства; код показывает возможный механизм; пользовательский сценарий подтверждает видимое поведение.
- Механизм и порядок: до запуска записать, какое состояние ожидается после каждого действия. Различать операции чтения (`list`, `find`, `search`, `stats`) и изменения (`add`, `done`). Статистика описывает текущие задачи, а не количество команд или событий. Просмотр, поиск и неудачный поиск не должны подменять список или менять поля.
- Пример и типичная путаница: на отдельном небольшом примере сначала предсказать результат чтения и состояние до/после отдельного изменения. Если поменялось только отображение совпадений, это не означает, что исходный список стал короче. Не подменять подтверждение вывода чтением кода.
- Первое самостоятельное действие: для нового примера с одной записью ученик заранее называет ожидаемый результат просмотра и поиска, а затем проверяет, что чтение не поменяло исходное состояние. Критерий — прогноз отделён от фактического вывода, в котором указано конкретное подтверждённое свойство.
- Опора для повторного обращения: для каждого шага держать рядом пару «ожидание → наблюдение» и отмечать, касается ли он вывода или состояния. Если результат расходится, сохранить точный вход, вывод и место проявления до исправления.
- Переход к следующему шагу: договор проверки установлен; теперь нужно начать с известного состояния, чтобы прежние данные не влияли на результат.

## 02. Запуск от пустого состояния и порядок сценария

- Что и зачем объяснить: запуск `run()` создаёт новый список `tasks`; пользовательская история живёт до выхода из этого процесса. Начальная пустота — полезный вход для list/stats и корректного отсутствующего id, а не скрытая ошибка. До проверки определить порядок действий и данные, чтобы результат одного шага был опорой для следующего.
- Механизм и порядок: запустить существующий проект как обычно, проверить пустой `list` и пустой `stats`, затем запросить допустимый, но отсутствующий id для `find` и `done`. Убедиться, что приложение остаётся в меню, не падает и не сообщает об изменённой записи. После этого добавить задачи и не запускать отдельную проверку из другого каталога — это тема следующего занятия.
- Пример и типичная путаница: корректный id, которого нет в списке, отличается от некорректного текста, который reader ещё не принял. Для первого `find_task` должен завершиться результатом отсутствия; не обращаться к полям `None`. Для второго reader должен повторить свой вопрос согласно прежнему договору.
- Первое самостоятельное действие: ученик составляет порядок небольшого контрольного запуска и предсказывает первый экран пустого проекта. После запуска он сверяет сообщения пустого списка/статистики и отсутствие побочного изменения от неизвестного id.
- Опора для повторного обращения: начало нового процесса → пустой `tasks`; допустимый отсутствующий id → понятное сообщение и возврат в меню; `total = completed + left`, пустой процент `0.0`.
- Переход к следующему шагу: пустая основа проверена; далее можно проверить, что неверный ввод не меняет её частично.

## 03. Ошибочный ввод и отсутствие частичного добавления

- Что и зачем объяснить: для `add` название и приоритет — обязательные части одной задачи. Список должен измениться только после получения обоих допустимых значений. Reader повторяет именно тот вопрос, где ввод оказался неверным; модельная функция не становится общей проверкой случайных аргументов. Отдельно различить отказ чтения и отсутствие записи после допустимого поиска.
- Механизм и порядок: в readers, которые должен передать результат занятия 19.1, проследить путь ввода до `add_task`: очистка краёв названия, отклонение пустого результата, преобразование приоритета через `int`, узкий `ValueError`, отдельная проверка диапазона 1–5. Пока хотя бы одно значение не принято, `append` ещё не выполнялся. Не скрывать ошибки общим `except` и не создавать пустую запись для последующего исправления.
- Пример и типичная путаница: текст `два` не преобразуется в целое, а целое `-2` преобразуется, но не попадает в разрешённый диапазон. Это две разные причины повторного вопроса. Аналогично, пробелы вокруг названия убираются, а внутренние пробелы и регистр не требуют изменения.
- Первое самостоятельное действие: на новом наборе вводов ученик заранее разделяет ошибку преобразования, число за пределами диапазона и пустое после очистки название; запускает по одному случаю и сверяет, что вопрос повторяется, а список до корректного ввода остаётся прежним. Затем принимает допустимые значения и наблюдает ровно одну добавленную задачу.
- Опора для повторного обращения: `title` и `priority` возвращены из readers → только после обоих значений вызывается `add_task`; до этого размер `tasks` прежний. При расхождении искать первую точку эффекта, а не добавлять компенсационное удаление.
- Переход к следующему шагу: добавление даёт реальные записи; теперь проверим, что чтение, поиск, изменение и статистика согласованы на тех же данных.

## 04. Согласованная работа списка, поиска и статистики

- Что и зачем объяснить: итоговый сценарий проходит все функции через обычное меню и один общий список. `list` выводит все записи; `find` возвращает найденную запись либо отсутствие; `search` собирает все совпадения, не меняя `tasks`; `done` меняет `is_done` найденной задачи; `stats` считает состояния. Повторное завершение уже выполненной задачи допустимо и не добавляет отдельную задачу или событие.
- Механизм и порядок: сначала создать две задачи с разными данными и сверить уникальные id, список и карточки. Найти одну по id и по фрагменту; проверить совпадение в другом регистре и несколько совпадений, если данные это позволяют. Завершить выбранную задачу, затем повторить `done` для того же id и ещё раз прочитать обе записи. После одной выполненной из двух ожидаются total 2, completed 1, left 1, 50.0%; после добавления третьей незавершённой — 3, 1, 2, 33.3%. Счётчики не задавать вручную и не накапливать по командам.
- Пример и типичная путаница: пустой поисковый запрос и непустой запрос без совпадений — разные причины пустого отображения. Поиск возвращает все исходные словари в прежнем порядке; он не обрезает основной список. `done` — изменение выбранного словаря, поэтому повторный вызов оставляет его `True`, а не переключает назад.
- Первое самостоятельное действие: после разбора отдельного примера с несколькими записями ученик сам выбирает последовательность просмотра, поиска и одного изменения, до запуска предсказывает, какое поле поменяется, затем сверяет список и счётчики. Примерные входы отличаются от контрольного сценария практики.
- Опора для повторного обращения: после каждого изменения вновь прочитать нужные записи; проверять `total = completed + left`; процент считать от текущих completed и total; сравнивать все исходные задачи до и после search/done, кроме `is_done` у выбранной.
- Переход к следующему шагу: полный сценарий даёт фактические свойства приложения; отдельно проверим, что они сохраняются только в пределах процесса, а не обещаны как долговременные данные.

## 05. Выход и граница между кодом и данными

- Что и зачем объяснить: `exit` завершает текущий `run()`, а новый запуск заново создаёт пустой `tasks`. Git сохраняет версии файлов проекта, не пользовательские задачи, хранившиеся в памяти. Это намеренное ограничение финального продукта, а не повод добавить JSON или иной storage в этом блоке.
- Механизм и порядок: закончить сценарий командой `exit`, запустить тот же `main.py` заново и проверить пустые `list`/`stats`. Отдельно объяснить, что код и README остаются в каталоге и в Git, хотя задача исчезла. Не требовать скрытую отмену вложенного ввода, резервную копию задач или сохранение между процессами.
- Пример и типичная путаница: после перезапуска отсутствие старых задач совместимо с сохранённым `main.py`. Если README обещает сохранение задач между запусками, оно противоречит фактическому B даже при успешном `git push`.
- Первое самостоятельное действие: ученик до перезапуска предсказывает, какие данные останутся в памяти процесса и какие исходники останутся в проекте, затем проверяет оба наблюдения. Критерий — не смешаны runtime-данные и версия программы.
- Опора для повторного обращения: «состояние задач — память одного запуска; история Git — файлы и commits». Указывать эту границу в README.
- Переход к следующему шагу: теперь можно писать документацию о подтверждённом, не добавляя в неё будущие возможности.

Добавлять только сведения, которые ученик лично сверил; не заявлять о clean clone до следующего урока и не документировать команды, которых нет.

- Первое самостоятельное действие: по кратким подтверждённым наблюдениям ученик самостоятельно оформляет один раздел и список команд в Markdown; затем применяет те же принципы к README своего проекта. Критерий — корректная структура, понятная последовательность и отсутствие утверждений сверх проверенного.
- Опора для повторного обращения: для каждой строки README найти свидетельство в паспорте, файле или выполненном сценарии; особенно сверить Python 3.12, команду запуска, команды меню, статистику и ограничение памяти.
- Переход к следующему шагу: применить написанную инструкцию буквально, затем проверить `.gitignore` и передаваемую версию.
