## Точка B: результат занятия

## 00. Вступление

По планируемому результату занятия 17.1 список уже показывает реальные id; это проверяется на рабочем проекте перед практикой. В занятии 10 ученик готовился искать первую подходящую запись и различать её с `None`; теперь тот же алгоритм применяется к id в StudyHub. Нужно разделить два вопроса: допустимо ли введённое положительное число и есть ли запись с таким id.

1. **Точка старта:** уроки 8.1–10 подготовили список записей, обход и поиск первой записи/`None`; уроки 11 и 16.1 — передачу результата функции и повторную проверку ввода. После занятия 17.1 в проекте видны реальные id.
2. **Новый вопрос:** как принять положительный id, найти именно соответствующий словарь и безопасно показать результат, если такого id нет?
3. **Результат:** команда `find` ищет по номеру без изменения данных и корректно обрабатывает найденную и отсутствующую задачу.

Сначала проверим рабочий `add → list` и вспомним, что id написан **в карточке**, а не определяется её местом на экране. Затем пройдём путь «прочитать номер → проверить его форму → найти словарь по полю `id` → показать карточку или отсутствие». Этот путь объясняет, почему правильный ввод ещё не гарантирует найденную задачу.

## 01. Reader принимает положительный номер

- Что и зачем объяснить: `read_task_id` получает текст, преобразует его в целое число и повторяет свой вопрос, пока значение не станет положительным. Это повторное применение уже знакомого `input`, `int`, `try/except ValueError` и `while`, а не новый механизм обработки ошибок.
- Механизм и порядок: сначала проверить, можно ли представить введённое как целое; затем отдельно проверить условие `task_id > 0`; лишь после обеих проверок вернуть число. Ошибка преобразования и неположительное число — разные причины повторить запрос. Сравнить правило с уже готовым `read_priority`: оба reader повторяют вопрос, но принимают разные диапазоны.
- Независимый разбор до проектного `find`: показать последовательность ответов `"abc" → "0" → "-2" → "7"` на один вопрос reader. `int("abc")` вызывает `ValueError`; `0` и `-2` успешно преобразуются в целые, но не проходят проверку `> 0`; `7` возвращается вызвавшему функцию коду. Важно разобрать, что `return` завершает функцию, а `print` только показывает текст.
- Типичная путаница: `"7"` — строка из ввода, `7` — целое число, а `"7.0"` нельзя напрямую преобразовать через `int`. Ни одна из этих проверок не заглядывает в `tasks`.
- Первое самостоятельное действие: после разбора предсказать, сколько раз reader спросит номер для последовательности `"" → "4"` и какое значение/тип вернёт; затем самому наметить, где в знакомом цикле `read_priority` нужно заменить проверку диапазона условием `> 0`. Критерий — два запроса, результат `int` со значением 4; возвращаемое значение не подменяется печатью.
- Содержательная вставка MAIN: короткая трасса «строка → `int` или `ValueError` → проверка `> 0` → повтор/`return`» с одним прогнозом следующего шага, затем объяснение причины повторения, а не набор одинаковых карточек «валидно/невалидно».
- Опора для повторного обращения: «преобразование → проверка знака → возврат»; отдельно помнить, что повторный запрос происходит только для некорректного ввода.
- Переход к следующему шагу: reader готовит формат id, но ещё не отвечает, соответствует ли он какой-либо задаче.

## 02. Допустимый id и существующая задача — разные проверки

- Что и зачем объяснить: положительность ограничивает форму идентификатора, существование зависит от текущего `tasks`. Reader отвечает только на первый вопрос. Иначе пришлось бы смешать чтение с обходом списка и сделать одну функцию ответственной за две разные операции.
- Механизм и порядок: `read_task_id` возвращает положительное число независимо от содержимого списка. Следующий компонент передаёт это число поиску. Положительный id, которого нет в `tasks`, является допустимым вводом и обычным исходом поиска, а не причиной повторно спрашивать id.
- Независимый пример: в коробке лежат ярлыки с номерами 3 и 8; запрос 999 — допустимый номер ярлыка, которого здесь нет. Аналогия помогает отделить **форму запроса** от **наличия вещи**, но поиск в Python всё равно требует прохода по словарям, а не догадки по числу.
- Первое самостоятельное действие: для `"нет"`, `"0"`, `"8"` и `"999"` выбрать, на каком этапе программа повторяет ввод, а где запускает поиск. Проверка: оба положительных значения (`8`, `999`) проходят reader; результат для них может быть разным после поиска.
- Содержательная вставка MAIN: схема с двумя независимыми вопросами «допустимый `int > 0`?» и «есть такой `task["id"]`?», где ученик размещает `999` и объясняет отсутствие повтора ввода. Затем текст связывает схему с обязанностями двух функций.
- Опора для повторного обращения: «reader проверяет число; поиск проверяет список».
- Переход к следующему шагу: применить известный алгоритм первого поиска к полю `id`, не объясняя цикл заново.

## 03. Переносим знакомый поиск на поле id

- Что и зачем объяснить: алгоритм первого поиска уже введён в [уроке 10](../block_02/10 - Управление циклом и поиск.md), а передача результата функцией — в [уроке 11](../block_03/11 - Функции- вход и результат.md). Здесь не нужен новый разбор `for` или алгоритма: применить известный договор к `task["id"]` и вернуть найденную исходную запись либо `None`.
- Механизм и порядок: знакомый цикл последовательно получает **сам словарь**, затем сравнивает `task["id"]` с аргументом `task_id`. При совпадении `return task` завершает функцию **внутри** цикла. `return None` должен стоять **после** цикла: он срабатывает, лишь когда все записи просмотрены. Для пустого списка цикл вообще не выполняется, результат тоже `None`. Не смешивать id с экранным номером строки или `tasks[task_id]`.
- Независимая ручная трассировка: для `[ {"id": 12}, {"id": 4} ]` и запроса 4 первая проверка `12 == 4` ложна, но поиск **продолжается**; вторая `4 == 4` истинна, возвращается второй словарь. Для запроса 1 обе проверки ложны, только после них возвращается `None`. Если поставить `return None` в `else` первой итерации, id 4 ошибочно не найдётся.
- Первое самостоятельное действие: на схеме обхода тех же двух записей ученик сам отмечает итерацию завершения для id 12, 4 и 1, а затем объясняет, почему `tasks[1]` при запросе 1 дал бы неверную карточку. Наблюдение: найденные записи различаются по полю `id`, отсутствующий запрос возвращает `None`, несмотря на существование второй позиции.
- Содержательная вставка MAIN: одна пошаговая таблица «текущий `task["id"]` → сравнение → продолжить/вернуть», где отдельно показано положение `return None` **за** циклом. Затем переход к короткому исправлению ошибочного раннего `return None`, без дублирующего опроса по тем же значениям.
- Опора для повторного обращения: контракты уроков 10 и 11 — «найденная запись либо отсутствие» и «вернуть результат вызывающему коду»; из урока 17.1 — «id записи не равен её позиции».
- Переход к следующему шагу: обработчик должен безопасно различить исходную запись и `None` до передачи formatter.

## 04. Используем исходную запись и проверяем отсутствие

- Что и зачем объяснить: [занятие 5](../block_01/05 - Значение None в программе.md) и [10](../block_02/10 - Управление циклом и поиск.md) готовят проверку `None` до чтения полей, [7](../block_02/07 - Общие ссылки и копии.md) и [8.1](../block_02/08.1 - Список записей и копии.md) — общий объект по ссылке. Здесь нужно связать эти известные идеи без новой теории копирования.
- Механизм и порядок: обработчик проверяет результат поиска на `None` до чтения полей; найденный словарь передаёт готовому `format_task`, отсутствие получает понятное сообщение. Поиск только читает общий список.
- Пример и типичная путаница: пустой список и отсутствующий id дают `None`; найденный объект — один из словарей в `tasks`. Не читать поля до проверки и не трактовать позицию списка как результат поиска.
- Первое самостоятельное действие: на записях с id 12 и 4 выбрать безопасный порядок для двух исходов поиска: «сначала `is None`, затем `format_task`» либо наоборот, и обосновать, почему проверка нужна **до** formatter. Для найденного значения сравнить результат с одним из словарей через `is` (тот же объект, не равенство текста). Результат — ни поля у `None`, ни копия записи не используются.
- Содержательная вставка MAIN: схема двух ветвей на одном найденном словаре и `None`; ученик указывает, в какой ветви допустим вызов formatter, затем текст объясняет, почему поиск остаётся операцией чтения.
- Опора для повторного обращения: ссылки на уроки 5, 7, 8.1, 10 и 17; восстановить «проверить `None` → только затем передавать найденную запись formatter».
- Переход к следующему шагу: соединить проверенные части с готовым reader и маршрутом команды.

## 05. Handler соединяет ввод, поиск и отображение

- Что и зачем объяснить: по цепочке из [урока 16.1](16.1 - Проверяем ввод задачи.md) reader отвечает за ввод, а обработчик команды соединяет готовые компоненты. `handle_find` не дублирует известный алгоритм или форматирование: получает id, вызывает `find_task`, затем выбирает сообщение об отсутствии либо готовый formatter.
- Механизм и порядок: команда вызывает handler; handler получает положительное число; поиск возвращает словарь/None; проверка результата определяет ветвь; formatter и вывод применяются только к найденной записи. Корректный неизвестный id не является исключительной ситуацией. Данные и порядок списка сохраняются.
- Пример и типичная путаница: ошибочный текст обрабатывается внутри reader до возврата; отсутствующий положительный id проходит reader и получает ответ handler. Не помещать поиск в `read_task_id` и не форматировать `None`.
- Первое самостоятельное действие: ученик без шаблона готового обработчика определяет порядок вызовов `read_task_id`/`find_task`/`format_task`, затем подключает `handle_find` к команде `find` в уже существующем `run`. Для знакомого id он наблюдает готовую карточку; для положительного отсутствующего — сообщение без исключения и без нового запроса. Отдельный повтор `list` подтверждает неизменность карточек.
- Содержательная вставка MAIN: трасса **одной** команды через меню, reader, поиск и две возможные ветви; следующий короткий прогноз применяется к другому id. Не повторять предыдущую таблицу поиска и не ставить рядом две карточки с одним вопросом «функция существует?».
- Опора для повторного обращения: цепочка «команда → reader → поиск → проверка None → formatter/сообщение».
- Переход к практике: проверить каждый новый компонент и прежний маршрут на состояниях, которые различают ошибки ввода и отсутствие задачи.

## 06. Что мы будем делать в практике

**Формат и исходная опора:** проект — продолжение **того же локального StudyHub** после планируемой B занятия **17.1**. В рабочем `main.py` уже предполагаются `run()` с общим списком `tasks`, команды `add`/`list`, `read_priority` и `format_task`. Перед правкой ученик выполняет `add → add → list` в одном запуске и сверяет реальные id в карточках: именно они будут входами `find`. Если это не работает, сначала восстановить необходимый результат 17/17.1; брать готовый финальный snapshot вместо своей копии нельзя. Техническая заготовка — существующий проект и, для отдельной проверки, явно указанные тестовые словари; готовые `read_task_id`, `find_task` и `handle_find` не выдаются.

Итог — `read_task_id`, `find_task` и подключённый `handle_find` в одном текущем Planner, с сохранением списка и прежнего поведения.

1. **Самостоятельно написать reader для id (опора: 01–02 и B16.1).** Вход: существующий `read_priority` как образец знакомого цикла и отдельная новая функция в `main.py`. Ученик **сам пишет** вопрос, `int`, обработку `ValueError`, проверку `> 0` и `return`; не получает готовый reader целиком. До подключения к меню проверить его отдельным временным вызовом из текущего файла (после проверки восстановить исходный завершающий вызов `run()`): последовательность `"abc" → "0" → "-3" → "7"` должна закончиться **возвратом целого 7**, а не аварией или принятием 0; положительное 999 reader принимает без проверки `tasks`. Эти наблюдения доступны сразу после шага. При ошибке вернуться к трассе 01 и границе 02; типичная ошибка — возвращать строку/печатать число или проверять наличие id прямо в reader.
2. **Самостоятельно перенести поиск на поле `id` (опора: 03–04 и B10/B11).** Вход: отдельный контролируемый список **двух** словарей с id **20, затем 3** (допустимы минимальные словари `{"id": 20}` и `{"id": 3}`; для этого шага formatter не нужен). Объект: новая функция `find_task(tasks, task_id)` в том же `main.py`. Ученик сам записывает обход, сравнение **поля** `id`, возврат найденной записи и `None` **за** циклом; полную функцию в заготовке не давать. Временно вызвать функцию на контролируемых аргументах, не привязывая проверку к ещё не написанному handler: запросы 20 и 3 дают соответствующие **те же объекты** (`is` с исходными элементами), запрос 1 даёт `None`, хотя `tasks[1]` существует; отдельно 999 и пустой список тоже дают `None`. Для второго элемента специально проверить ошибочное размещение `return None` внутри цикла. После вызовов сравнить оба исходных словаря и их порядок — поиск ничего не меняет.
3. **Подключить команду `find` к действующему CLI (опора: 04–05, подготовленная B17.1).** Вход: проверенные reader и поиск из шагов 1–2, существующие `run`, `tasks`, `format_task` и команды `add`/`list`. Ученик сам пишет `handle_find(tasks)` как цепочку «получить id → найти → проверить `is None` → вывести сообщение либо строку готового formatter» и подключает вызов в ветви `find` меню; нельзя создавать новый `tasks` внутри handler, дублировать алгоритм или передавать `None` в formatter. В одном запуске добавить **три** задачи и через `list` прочитать их id, затем через `find` последовательно найти первую, среднюю и последнюю: вывод каждого совпадает с соответствующей карточкой `list`, независимо от позиции. Ввести отсутствующий положительный id (например, 999, если его нет): один ответ «задача не найдена», возврат к меню **без повторного вопроса**. Ввести `"abc"`, 0 и отрицательное число: reader продолжает спрашивать до допустимого числа. Повторный `list` показывает прежние три задачи в прежнем порядке; команды `add`, `list`, неизвестная команда и `exit` остаются рабочими.

Связка действий: шаг 1 отдельно доказывает, что в поиск поступает **корректное число**; шаг 2 — что функция различает **id и позицию**, возвращает исходный словарь или `None` и не меняет список; шаг 3 — что реальный `find` безопасно использует оба результата в прежнем интерфейсе. Учебный пример 12/4 отличается от самостоятельной проверки 20/3; id 1 во втором шаге обнаруживает ошибку, которая скрылась бы на обычных последовательных id после `add`. Проверка объектов выполняется прямым вызовом с контролируемым списком (либо debugger во время `run`), поскольку локальный `tasks` не становится доступен после выхода из `run`.
