## 00. Точка входа и устройство независимой проверки

Сначала объяснить схему «основной рабочий каталог → Git remote/ветка/commit → новый соседний каталог». Назвать смысл `git status`, `git remote -v`, `git branch --show-current`, `git rev-parse HEAD` до их первого использования: вывод `status` относится к рабочему каталогу, hash обозначает конкретное состояние файлов в истории, одинаковое имя ветки в двух местах ещё не доказывает равенство версий. Проверка понимания: предсказать, попадёт ли незакоммиченная правка README в clone, затем разобрать независимый пример. Условие перехода к §01 — ученик может назвать, какой commit опубликован.

**Объясняющий пример:** в основной папке у автора локальный commit `abc...` и ещё одна несохранённая строка README; после `push` Git передаёт commit, но не эту строку. Показать три слоя отдельно: рабочий файл, локальный commit, удалённая ветка. Чтобы **доказать**, что commit уже опубликован, после объяснения `git fetch origin` (обновляет сведения об удалённых ветках, рабочие файлы не переписывает) сравнить `git rev-parse HEAD` с `git rev-parse origin/<имя-ветки>` для действительно используемой ветки; `origin/<имя-ветки>` — локальная ссылка на состояние удалённой ветки после fetch. Если отличаются, нужно разобраться с передачей в занятии 20 до новой копии. Здесь и далее вместо шаблона `<имя-ветки>` ученик подставляет своё имя, а не вводит угловые скобки буквально.

**Содержательный интерактив:** показать пару коротких состояний `status` и два hash; ученик указывает, какая из двух копий воспроизводит опубликованный вариант, и объясняет почему. Это проверка различия состояний, а не второй вопрос о той же команде.

## 04. Сверить интерфейсы и состав кода

Визуал «ввод → `run`/handler → операция → результат» показывает, почему верное число в меню ещё не подтверждает интерфейсы `build_statistics(tasks)` и `completion_percent(statistics)`. Перед прямыми проверками пояснить безопасный способ вызвать функцию без непреднамеренного меню и почему локальный `tasks` из `run` недоступен снаружи. Структуру и все 21 функции сверять с паспортом, не придумывая новые API.

**Механизм прямой проверки:** объяснить, что запуск `python -i main.py` сначала исполняет файл (в том числе `run()`), а после штатного `exit` из меню оставляет определённые функции доступными в интерактивном Python с приглашением `>>>`. Значение `tasks`, объявленное внутри `run`, туда не переносится. Перед первым применением пояснить: выражения вводят после `>>>`, а `exit()` в нём закрывает Python, не приложение. Запуск с `-i` — **диагностический способ в копии**, не изменение структуры исходного файла. В MAIN показать проверку на пустом списке; затем ученик сам проверяет словарь `{'total': 3, 'completed': 1, 'left': 2}` и получает процент `33.3`.

**Контракт и сравнение:** `build_statistics([])` даёт ровно `{'total': 0, 'completed': 0, 'left': 0}`, `completion_percent(build_statistics([]))` даёт `0.0`; функция процента принимает **один** словарь, не кортеж и не два числа. Разобрать контрпример: если меню рисует `50.0` через вычисление внутри `run`, но функция процента ожидает два аргумента, интерфейс B нарушен. При сверке 21 роли выделить группы: подготовка/создание (2), добавление (2), поиск/изменение (2), статистика (2), текстовый поиск (1), readers (3), вывод (3), handlers (4), цикл (1), `calculate_study_minutes` (1); отдельного постоянного `handle_stats` нет. `get_next_id([]) → 1`, неупорядоченные id `10/3/20 → 21`; `find_task` возвращает исходный dict или `None`, `mark_task_done` изменяет один `is_done` и сообщает bool.

**Точный список для сверки без переименований:** `normalize_title`, `create_task`; `get_next_id`, `add_task`; `find_task`, `mark_task_done`; `build_statistics`, `completion_percent`; `search_tasks`; `read_title`, `read_priority`, `read_task_id`; `format_task`, `show_tasks`, `show_menu`; `handle_add`, `handle_find`, `handle_done`, `handle_search`; `run`; `calculate_study_minutes`. Смысл карточки `format_task`: `[id] title | приоритет: priority | состояние` с `выполнена` / `не завершена`; `calculate_study_minutes` остаётся учебной функцией, не командой `calc`.

**Визуал для выбора проверки:** две колонки «проверяет меню» и «проверяет прямой вызов»; ученик распределяет `search`, `get_next_id`, `completion_percent` по тем доказательствам, которые нельзя получить одним только `stats`.

## 05. Адресно исправить и перепроверить публикацию

Разобрать три разных причины: неверный README, неотправленный commit, ошибка в `main.py`. Для каждой — сначала факт, потом исправление **в основной линии**, проверка прежних возможностей и только затем `status/diff → add/commit/push` при реальном изменении. Для повторной независимой проверки — новый clone опубликованного исправленного hash; не объявлять старый каталог «свежим». Если ошибок нет, существующий hash достаточен.

До показа действия ученик формулирует вероятную причину по признакам. После исправления он обязан повторить именно проваленную проверку, ближайший прежний успешный сценарий и только затем опубликовать новую версию. ## Практика: семь ручных действий по тому же StudyHub

Формат — **проектная ручная проверка**, каждая часть оставляет наблюдаемое доказательство в коротком протоколе ученика (вне постоянного `main.py`). До начала требуется подтверждённая A занятия 20. В каждом действии указаны **вход/объект → опора → собственная операция → локальный результат → различающий случай**. Пункты идут последовательно; если исходные условия не подтверждены, соответствующая зависимая часть не засчитывается, а ученик возвращается к указанной опоре.

### 1. Узнать, какой commit действительно опубликован

- **Вход/объект:** основной StudyHub после 20, адрес remote, ветка, hash локального `HEAD`, известные результаты README и сценария. **Опора:** §00 и B20 (планируемая, проверяется на входе).
- **Сам:** посмотреть `git status`, remote/ветку, обновить сведения об удалённой ветке через ранее объяснённый `fetch`, сравнить локальный hash с hash `origin/<ветка>`. Записать полный hash, URL и состояние незакоммиченных изменений.
- **Наблюдение:** известен конкретный опубликованный commit; если локально есть ещё неотправленное, ученик не выдаёт его за опубликованное. **Различающий случай:** локальная README изменена после commit — объяснить, почему это не содержимое будущего clone. При неподтверждённом push остановить зависимые шаги и закончить передачу из 20.

## Самостоятельное задание в редакторе платформы (сохранённое `script`)

**Назначение:** проверить перенос навыка независимо от копирования работающего Planner. В `code_tasks.py` для `20.1` уже есть одно задание «Отчёт по открытым задачам», режим `script`. Оно выполняется **отдельно от основного проекта** и не меняет `main.py`.

- **Дано:** `tasks` — список полных словарей с `id`, `title`, `priority` (целое 1–5), `is_done` (bool); данные меняются платформой между проверками, исходный список нельзя изменять.
- **Своё действие:** без готового алгоритма и предзаданной схемы функций выбрать способ подсчитать `is_done == False` и найти **максимальное числовое** значение `priority` только среди таких записей. Разрешить собственные локальные переменные и при желании помощники **в миниработе**; они не становятся новыми постоянными функциями Planner.
- **Договор вывода:** ровно три строки: число открытых; максимальный `priority` среди открытых либо `None`, если открытых нет; исходный список `tasks` в его неизменённом виде. Платформенный `print(tasks)` — проверка сохранности входа, не команда меню.
- **Прогрессия и различающие случаи:** пустой `[]` → `0`, `None`, `[]`; все выполнены → `0` и `None`; одна открытая → её приоритет; среди смешанных записей наибольший приоритет **у выполненной** — его игнорируют; максимум открытых стоит **не последним**, есть повторяющиеся значения — результат остаётся правильным; исходные словари/порядок не меняются.
- **Подсказки по запросу после попытки:** первая возвращает к вопросу «какие записи подходят и что печатать»; вторая просит вручную найти максимум при исключённой выполненной записи; третья напоминает, что до первой подходящей записи максимум отсутствует и возможен обход исходного списка или отдельной выборки. Подсказки не раскрывают готовый код.
- **Критерий самостоятельности:** проход разных наборов данных с одинаковым контрактом, без константного ответа, случайного дописывания `tasks` или опоры на внешний `main.py`. Дополнительные интерактивы здесь проверяют план отбора, а не дублируют вопрос о git/clone.

**KEEP:** отдельно проверяются `build_statistics` / `completion_percent` с точными интерфейсами; в миниработе допускается самостоятельный алгоритм и собственные временные helpers без вмешательства в `main.py`. Эти сильные элементы обнаруживают ошибки, незаметные при просмотре меню.
