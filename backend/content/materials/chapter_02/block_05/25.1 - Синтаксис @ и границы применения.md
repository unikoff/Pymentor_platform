## 00. От ручной обёртки к короткой записи

В прошлой части мы вручную передавали исходную функцию декоратору и получали обёрнутую функцию для будущих вызовов. Теперь проверим, какую знакомую операцию Python записывает короче с помощью символа `@`.

1. **Точка старта:** мы умеем получить обёртку выражением `operation = decorator(operation)` и вызвать её позднее.
2. **Новый вопрос:** что именно происходит, когда `@decorator` стоит непосредственно над определением функции?
3. **Результат:** мы свяжем обе записи, проследим порядок действий и научимся находить потерянный `return` и преждевременный вызов.

Сначала разберём договор декоратора, затем сопоставим две формы и отдельно проследим момент их выполнения. Так мы прочитаем `@` как обычную передачу функции, а не как особую команду.

## 01. Декоратор получает функцию и возвращает обёртку

Декоратор в этом занятии: функция, которая принимает другую функцию и возвращает новую функцию для дальнейшего вызова. Новая функция называется обёрткой: она может выполнить дополнительные действия до или после исходной операции. Сам алгоритм исходной функции остаётся внутри неё.

Рассмотрим операцию, которая добавляет к результату метку. Исходная функция не знает, что её результат будут оформлять:

```python
def greet():
    return "Привет"

def add_label(operation):
    def wrapped():
        value = operation()
        return f"[ответ] {value}"
    return wrapped

labeled_greet = add_label(greet)
print(labeled_greet())
```

В вызов `add_label(greet)` мы передаём имя функции без скобок. Значит, передаём саму функцию, а не результат её вызова. Декоратор определяет `wrapped` и возвращает её. Затем вызов `labeled_greet()` запускает обёртку, она вызывает сохранённую `greet()`, получает строку и возвращает оформленный результат. На экран выводится `[ответ] Привет`.

Представим исходную функцию как готовый рецепт, а обёртку как поднос, на котором мы подаём блюдо. Поднос меняет подачу, но рецепт готовки остаётся прежним. Сравнение ограничено: в Python обёртка является настоящей функцией и может менять аргументы, результат или побочные действия. Поэтому мы проверяем реальный контракт, а не полагаемся только на образ.

Не следует путать функцию и результат её вызова. `greet` обозначает объект-функцию. `greet()` выполняет её и даёт строку. Если вместо имени передать результат, декоратор получит строку, а не функцию для последующего вызова. Это та же граница, которую мы уже встречали у callbacks: без скобок мы передаём действие, со скобками выполняем его.

**Первая самостоятельная проба 01 (до основной задачи):** на другом маленьком примере `get_code()` → `"X"` ученик отмечает, что получает уже объяснённый `add_label` при `add_label(get_code)` и при ошибочном `add_label(get_code())`, затем сам делает единственный поздний вызов исправленной обёртки. Ожидаемая проверка: исходная функция не выполняется при правильной передаче ссылки, значение `"X"` появляется только при последующем вызове. Вернуться к правилу «имя без скобок — действие, со скобками — результат»; здесь не показывать код будущей `observe`.

## 02. Сначала та же операция вручную

До короткой записи посмотрим на обычное переназначение имени:

```python
def greet():
    return "Привет"

def add_label(operation):
    def wrapped():
        value = operation()
        return f"[ответ] {value}"
    return wrapped

greet = add_label(greet)
message = greet()
```

Справа от равенства Python сначала вызывает `add_label` и передаёт ей исходную `greet`. Внутри создаётся `wrapped`, доступ к исходной функции сохраняется, и декоратор возвращает саму обёртку. После присваивания имя `greet` уже связано с возвращённой функцией. В строке `message = greet()` мы позднее вызываем её.

Аналогия здесь похожа на замену закладки в книге: имя `greet` раньше указывало на исходную инструкцию, а после присваивания указывает на обёрнутую версию. Сам объект исходной функции при этом не переписан. Если другое имя заранее хранило исходную функцию, оно продолжит ссылаться на неё. Граница аналогии в том, что Python работает со ссылками на объекты, а не с бумажной закладкой.

Это можно отличить от «декоратор изменил тело функции» на наблюдении с двумя именами. Если **до** присваивания выполнить `plain_greet = greet`, а затем `greet = add_label(greet)`, вызов `plain_greet()` даст `"Привет"`, тогда как `greet()` даст `"[ответ] Привет"`. Обёртка сохраняет ссылку на исходную функцию; изменилось то, на какой объект указывает имя `greet`. Это объясняет, почему в предыдущем занятии было безопасно создавать отдельную ссылку для диагностического вызова Planner.

Скобки справа важны: `add_label(greet)` запускает декоратор. Но в этом выражении мы не вызываем `greet()` как целевую операцию. Это произойдёт позже, когда вызовут возвращённую обёртку. Поэтому выражения `greet`, `add_label(greet)` и `greet()` обозначают разные вещи: исходную функцию, результат работы декоратора и результат вызова текущей функции под именем `greet`.

**Первая самостоятельная проба 02:** для нового имени `get_status`, возвращающего `"OK"`, ученик сам сохраняет ссылку `plain_status` **до** ручного переназначения через уже объяснённую `add_label`, называет объект под каждым именем и затем вызывает обе версии. Наблюдение: старая ссылка возвращает `"OK"`, переназначенная — `"[ответ] OK"`; сам момент присваивания исходную операцию не выполняет. Если обе ссылки внезапно ведут к одной обёртке, проверить момент сохранения `plain_status`; если имя стало строкой вместо функции, вернуться к `return wrapped` в 01.

## 03. Запись `@decorator` сокращает переназначение

Теперь запишем тот же механизм над определением:

```python
def add_label(operation):
    def wrapped():
        value = operation()
        return f"[ответ] {value}"
    return wrapped

@add_label
def greet():
    return "Привет"

message = greet()
```

В этой простой форме `@add_label` означает ту же последовательность, что и определение функции, а затем `greet = add_label(greet)`. Когда выполняется определение `greet`, Python создаёт функцию и передаёт её декоратору. Имя `greet` связывается с тем, что вернул `add_label`. Здесь возвращается `wrapped`, поэтому более поздний вызов `greet()` проходит через неё.

Мы можем проверить эквивалентность, не угадывая её по внешнему виду:

```python
def add_label(operation):
    def wrapped():
        value = operation()
        return f"[ответ] {value}"
    return wrapped

# Ручная форма
def first():
    return "готово"

first = add_label(first)

# Форма с @
@add_label
def second():
    return "готово"
```

Оба имени после преобразования обозначают обёрнутые функции. Знак `@` не делает тело декоратора автоматическим и не запускает целевую операцию сам по себе. Он задаёт место, где результат декоратора связывается с именем функции.

Для первого знакомства мы рассматриваем один декоратор без параметров после имени: `@add_label`. Запись фабрики вроде `@make_trace(...)` включает дополнительный вызов при применении и пока не нужна. Несколько декораторов тоже отложим, чтобы не скрывать базовую связь.

**Первая самостоятельная проба 03:** на отдельной мини-функции `get_status()` ученик сам выбирает одну из двух записей, переписывает её во вторую и проверяет, что обе версии с `add_label` дают одинаковый возвращаемый текст. Наблюдение: результат одинаков, определение с `@` применяет декоратор без дополнительной ручной строки присваивания. Опора возврата: схема «определить функцию → вызвать декоратор с объектом функции → связать имя с возвращённой функцией».

## 04. Декорирование и вызов происходят в разные моменты

У определения с `@` есть два отдельных события. Первое происходит, когда Python выполняет строку `def`: функция создаётся, передаётся декоратору, и имя получает возвращённый объект. Второе происходит позже, когда код явно вызывает это имя. Тогда выполняется тело обёртки и, если оно так устроено, исходная функция.

В ручном варианте применение декоратора произойдёт **там, где стоит присваивание** `operation = decorator(operation)`, а в варианте с `@` — при выполнении соответствующего определения `def`. Поэтому «обе формы эквивалентны» означает одинаковое связывание имени с результатом декоратора **при одинаковом месте применения**, а не обещание одинакового порядка `print` при произвольной перестановке строк. Обе формы могут иметь видимые эффекты настройки, и их время зависит от места выполнения.

Проследим события по небольшой трассировке. Декоратор печатает одно сообщение при настройке, а обёртка сообщает другое при вызове:

```python
def announce(operation):
    print("Декоратор применён")

    def wrapped():
        print("Обёртка вызвана")
        return operation()

    return wrapped

@announce
def greet():
    print("Тело исходной функции")
    return "Привет"

print("Определение завершено")
result = greet()
print(result)
```

При выполнении определения сначала печатается `Декоратор применён`: вызов `announce` происходит при обработке `def greet`. В этот момент тело `wrapped` ещё не запускалось. Затем появляется `Определение завершено`. Только на строке `result = greet()` выполняются `Обёртка вызвана` и тело исходной функции, после чего печатается `Привет`.

Удобно думать об этом как о настройке инструмента и его последующем использовании. Установка насадки на дрель соответствует применению декоратора: мы получаем подготовленный инструмент. Нажатие на кнопку соответствует вызову функции. Но аналогия не объясняет, что имя теперь связано с новым объектом, поэтому в коде мы дополнительно отслеживаем присваивание возвращённого значения имени.

Не будем называть это «выполнением при импорте»: импорт как отдельная тема будет позже. Здесь достаточно видеть, что тело декоратора может исполниться при выполнении определения, а тело возвращённой функции ждёт отдельного вызова. Также не будем считать, что любой декоратор обязательно печатает сообщение при настройке: это происходит только потому, что в нашем примере такой `print` находится в теле `announce`.

**Первая самостоятельная проба 04:** до запуска ученик самостоятельно раскладывает на временной линии четыре события примера `announce`: применение, окончание определения, вызов обёртки, вызов исходной функции. Затем передвигает явный `greet()` ниже ещё одного `print("READY")` и проверяет прогноз. Наблюдение: настройка осталась **до** `READY`, сообщения обёртки и исходной функции переместились **после** него. **Различающий перенос:** в отдельном опыте с ручным присваиванием ученик располагает `print("МЕЖДУ")` между определением исходной функции и `name = announce(name)`, предсказывает положение `Декоратор применён` и сравнивает с вариантом, где `@announce` стоит перед `def`. Здесь применение при ручной записи произойдёт **после** `МЕЖДУ`, а при `@` — вместе с определением; это не зависит от появления скобок у позднего `name()`. Если исходная функция выполняется до `READY`, сверить `wrapped`/`wrapped()` и скобки у целевой операции.

## 05. Проверяем возврат функции, а не случайного значения

Чтобы имя после декорирования можно было вызывать, декоратор должен вернуть подходящую функцию. Если забыть `return wrapped`, Python вернёт значение `None` по умолчанию. Тогда имя функции будет связано с `None`, и последующий вызов завершится ошибкой. Ошибка появилась не потому, что у исходной функции неверный результат, а потому, что декоратор не вернул обёртку.

Другая ошибка возникает, если вернуть результат вызова обёртки вместо самой обёртки:

```python
def decorate(operation):
    def wrapped():
        return operation()
    return wrapped()

@decorate
def greet():
    return "Привет"

print(greet())
```

Выражение `wrapped()` немедленно запускает обёртку. Если исходная функция возвращает строку, имя после декорирования получит эту строку. Когда вызывающий код позже напишет `greet()`, скобки применятся к строке, а не к функции. Для будущего вызова декоратор возвращает `wrapped`, без её скобок.

Ещё одна граница проходит между печатью и возвратом. `print(value)` показывает значение человеку, но сам по себе не возвращает его из функции. Если обёртка должна сохранить контракт результата, она возвращает результат вызова исходной операции. Иногда правильным результатом исходной функции является `None`; это тоже значение, и его можно вернуть явно. Мы различаем `None`, возвращённый исходной функцией, и `None`, случайно полученный декоратором из-за отсутствующего `return`.

Эти ошибки различаются по моменту и типу значения. Потерянный `return` даёт `None` вместо функции. Лишние скобки запускают обёртку сразу и дают её результат вместо функции. При разборе мы спрашиваем: что именно справа от `return`, и должно ли это значение быть вызвано сейчас или позже?

Есть **третья, внешне похожая, но принципиально другая** ситуация: `decorate` вернул правильную функцию `wrapped`, но **внутри** `wrapped` после `value = operation()` написано `print(value)` и забыто `return value`. При определении ошибки нет, поздний вызов успешно запускает исходную операцию и даже показывает правильную строку, однако значение, полученное вызывающим кодом (`result = greet()`), равно `None`. Функция осталась вызываемой — нарушен договор результата. Добавить `return wrapped` снаружи недостаточно: он уже есть. Исправлять нужно внутренний возврат. Если исходная операция сама возвращает `None`, это иной, допустимый результат; сравнивать надо с её реальным договором, а не с фактом печати.

Для диагностики полезны три разных следа: **(а)** без внешнего `return` имя после определения — `None`, поздняя попытка `greet()` завершится ошибкой **до запуска исходной операции**; **(б)** `return wrapped()` выполняет операцию уже при определении и связывает имя с возвращённой строкой; **(в)** наружный `return wrapped` сохраняет вызываемое имя и поздний запуск, но забытый внутренний `return` теряет **только результат**. Везде анализируем два вопроса по отдельности: *что хранит имя после декорирования?* и *что возвращает поздний вызов?*

**Первая самостоятельная проба 05:** ученику предлагаются две **раздельные** сокращённые версии `decorate`: в первой у внешней функции отсутствует заключительный `return`, во второй есть `return wrapped()`. Он до исполнения предсказывает, чем будет связано имя `greet`, какой момент запускает исходную функцию и что произойдёт при позднем `greet()`, затем **сам исправляет** каждую версию. После этого исследует третий вариант, где **внешний** `return wrapped` верен, но внутри есть только `print(value)` без возврата: сначала сравнивает видимый вывод и значение `result`, затем исправляет только внутреннюю передачу результата. Наблюдение: в первых двух исправленных случаях имя остаётся вызываемой функцией и исходная операция ждёт вызова; в третьем исправление не меняет время запуска или вывод, но заменяет потерянный `None` ожидаемым значением в `result`. Возврат к различию `wrapped`/`wrapped()` и `print`/`return`, без выдачи эталонного исправленного кода.

## 06. Когда короткая запись помогает

Запись с декоратором удобна, когда мы хотим явно связать функцию с общей обёрткой при её определении. Тогда читатель сразу видит, что имя обозначает обёрнутую версию. Если преобразование важно показать как отдельный шаг или включать только иногда, ручное присваивание может быть понятнее.

Краткость не доказывает, что декоратор нужен каждой функции. Если обёртка скрывает предметное правило или неожиданно меняет входы и результаты, чтение становится сложнее. В прошлом занятии мы использовали ручной инструмент диагностики для одной реальной функции и вызывали его отдельно. Это хороший повод оставить основную логику Planner простой: не требуется массово декорировать обработчики только ради знакомства с символом `@`.

Когда читаем `@` над определением, мы можем мысленно развернуть запись и спросить, какое имя получает результат декоратора. Если вызов операции ожидается позже, этим результатом должна быть функция, которую можно вызвать. Если декоратор вернул строку или `None`, ошибка проявится позже, хотя исходная функция могла быть правильной. Поэтому при отладке мы проверяем оба договора отдельно: что вернул декоратор и что вернула обёртка.

Короткая запись полезна, когда одинаковое внешнее действие действительно нужно нескольким функциям и мы хотим видеть его применение рядом с каждым определением. Если поведение нужно только в одном месте, явный вызов помощника может легче показывать ход выполнения. Если правило предметное, например нормализация названия задачи, его обычно понятнее оставить в предметной функции, а не скрывать в обёртке. Декоратор не решает сам, что считать общим: эту границу выбирает автор кода.

Также важно помнить: в Python декоратор может вернуть и не вызываемое значение, язык не заставляет возвращать функцию. Но наш учебный договор ожидает функцию, потому что позднее имя используется со скобками. Поэтому мы не обещаем, что декоратор автоматически сохраняет поведение: именно его тело определяет дополнительные действия, передаваемые аргументы и возвращаемое значение.

В этом занятии мы не добавляем `functools.wraps`, метаданные функций, фабрики декораторов с параметрами или обработку исключений. У этих тем есть собственное место дальше. Сейчас наша цель скромнее: развернуть синтаксис в понятное присваивание, определить порядок выполнения и проверить, что имя сохранило вызываемую функцию.

**Первая самостоятельная проба 06:** ученик сравнивает две потребности: временно проследить один вызов `format_task` и постоянно помечать результат нескольких **учебных** функций. Сам выбирает отдельную ссылку, ручное переназначение либо `@` и объясняет выбранное время применения. Локальный критерий: для первого случая обычный Planner продолжает пользоваться исходным форматировщиком, для второго общее оформление видно у каждого определения. Если выбор меняет предметный результат или требует массово оборачивать обработчики Planner, вернуться к границе «диагностика по запросу ↔ постоянное общее поведение».

## 07. Что мы будем делать в практике

В коротком исследовании в интерпретаторе мы закрепим преобразование функции на небольшом примере. Planner останется без изменений. Обязательный формат паспорта — **редактор/интерпретатор (И)**; кроме самостоятельных проб ниже, действующее read-only задание `code_tasks.py` для `25.1` имеет **mode=`script`**, проверяет точный stdout и два разных набора строк. Это не задание на переписывание Planner и не готовый код решения.

**Обязательная точка входа:** ученик знает передачу функции без скобок из планируемой B 24, замыкание из B 24.1 и ручную диагностическую фабрику из B 25. До выдачи 25.1 проверить **фактически выданные объяснения и самостоятельные результаты** этих B: ученик мог отдельно создать и вызвать `traced_format_task`, а не только прочесть об этом в плане. Если этого ещё нет, соответствующую практику прежнего занятия надо завершить до выполнения зависимой части. Для маленьких примеров нужен только редактор/интерпретатор; входной `script`-стартер предоставляет имена `manual_value` и `decorated_value`, функции `manual_operation` и `decorated_operation`, а также вывод `READY`. Их значения **подменяются при проверке**, поэтому строки результата нельзя зашивать константами.

1. **Создадим простой декоратор:** увидим, что он получает функцию и возвращает обёртку. **Вход:** технический стартер `script` с уже написанными заголовками `observe(operation)` и `wrapped()`, но незаполненными **телом обёртки и внешним возвратом**; две исходные функции с метками вывода пока не вызваны. Этот стартер помогает проверить контракт конкретной автозадачи, **сам по себе он ещё не доказывает умение написать всю конструкцию с нуля**. **Объект:** `observe`, которая при применении сообщает `НАСТРОЙКА`, а во вложенной функции позднее сообщает `ОБЁРТКА`. **Опора:** разделы 01–02 о функции как значении и позднем вызове, 05 о возвращении вызываемой функции; факт прежней B 25 проверить до выдачи. **Самостоятельно:** дописать обе пустые части, вызвать исходную операцию ровно один раз, напечатать и **вернуть** её результат; сравнить ссылку и результат вызова. **Локальное наблюдение:** при применении декоратора видна настройка, но ещё нет ни метки исходной операции, ни результата; при отдельном позднем вызове появляется одна обёртка, одна исходная операция и её значение; возвращённая строка совпадает с исходной. Различающие случаи: `return wrapped()` запускает операцию слишком рано; пропущенный внешний `return` теряет вызываемость; верная вызываемость ещё не гарантирует сохранение результата внутри `wrapped`.

2. **Сравним две формы и самостоятельно воспроизведём механизм:** проследим ручное присваивание и запись `@decorator`, затем проверим порядок сообщений. **Вход:** исправленный учеником `observe`, предоставленные две исходные операции и строки-аргументы `manual_value`, `decorated_value`; `READY` уже есть в стартере. **Объект:** ручное переопределение имени `manual_operation` и определение `decorated_operation` с `@observe`; **после автозадачи** — отдельный пустой учебный файл с двумя заданными результатами `"OK"` и `"X"`, без готовых `def` для декоратора и обёртки. **Опора:** разделы 01–05 и локальная проба 1. **Самостоятельно (автозадача):** записать ручное применение к первой операции и поздние вызовы обеих функций; результаты сохранить в разные имена и вывести после вызовов. **Локальное наблюдение автозадачи:** обе строки `НАСТРОЙКА` выводятся **до** `READY`; после `READY` для каждой операции по очереди появляются `ОБЁРТКА`, соответствующая исходная метка (`ИСХОДНАЯ manual` либо `ИСХОДНАЯ decorated`) и текущее входное значение. В конце напечатаны **оба сохранённых результата**, каждый возвращён без изменений. Проверить с первым и вторым **различающимися** наборами значений: порядок меток сохраняется, меняются только переданные строки; вызовы ровно по одному. Никакой вызов исходной операции при декорировании не допускается; вывод иных диагностических меток сломает `script`-сравнение stdout.

   **Самостоятельное доказательство за пределами заполнения starter:** в новом файле ученик **с нуля пишет внешний `def` декоратора и внутренний `def` обёртки** (без параметризованной фабрики), задаёт две простые функции с результатами `"OK"` и `"X"`, **сам** ставит `@` над одной и применяет тот же декоратор через присваивание к другой. Прогнозирует, какие функции сохранят вызываемость и что окажется в двух сохранённых переменных после вызовов; проверяет, что обе строки **возвращены**, а не только напечатаны. Затем переставляет **только ручное применение** ниже промежуточной метки `"МЕЖДУ"`: вывод применения ручной формы переедет за метку, а вывод применения `@` остаётся при соответствующем `def`; исходные операции по-прежнему ждут поздних вызовов. **Различающий исход:** ученик, который просто перенёс готовую `@observe` из starter или вывел строки константами, не сможет объяснить разницу времени применения и сохранить обе новые строки при смене входов. Ошибка с `print` вместо внутреннего `return` даст верный видимый текст, но `None` в сохранённой переменной. Этот опыт проводится **в отдельном файле**, чтобы не нарушить фиксированный stdout автозадачи.

3. **Разберём три разных следа ошибки:** объясним, что изменилось, когда потерялся внешний `return`, обёртка вызвана слишком рано или забыто вернуть **её результат**. **Вход:** две независимые дефектные версии `decorate(operation)` из действующего `manual.py` и исходная `greet`, возвращающая строку; **дополнительный самостоятельный мини-опыт** с исправной внешней функцией, но внутренней обёрткой, которая печатает результат без `return`. **Объект:** сначала внешний возврат `decorate` (пропущенный или `return wrapped()`), затем внутренний возврат `wrapped`; код `observe` из шагов 1–2 служит лишь опорой, готовые исправления не выдаются. **Опора:** раздел 05 и самостоятельная проба 05. **Самостоятельно:** перед каждым запуском письменно заполнить три разных поля: **(а)** что хранится под `greet` после декорирования (функция / `None` / строка), **(б)** выполнялась ли исходная операция до явного вызова, **(в)** что окажется в `result = greet()` либо почему до присваивания результата возникнет ошибка. Самому исправить обе обязательные версии `manual.py` и проверить поздний вызов; затем найти отсутствие **внутреннего** возврата в третьем мини-опыте, где печать правильная, а `result is None`, и исправить его, не меняя внешний `return`. **Локальное наблюдение:** в первых двух исправленных версиях имя вызываемо и исходная операция не запускалась преждевременно; в третьей имя было вызываемым **до** исправления, а исправление меняет только сохранённый результат с `None` на исходную строку. Контрольный контрпример — исходная функция **законно** возвращает `None`: тогда внутренний `return` ничего не «исправляет» в данных и ошибки договора нет. По трём наблюдениям ученик указывает конкретный уровень потери (декоратор/обёртка), вместо совета «добавить любой `return`». Не выдавать готовую исправленную реализацию в условии.

4. **Проверим границу:** обоснуем, почему сам символ `@` не требует переписывать существующий проект. **Вход:** завершённая B 25 с отдельной диагностической ссылкой `traced_format_task` и известным обычным `format_task`. **Объект:** выбор способа применения общей обёртки без правок Planner. **Опора:** раздел 06, проверенная самостоятельная работа шагов 1–3 и инвариант обычного CLI из 25. **Самостоятельно:** объяснить, почему диагностику одного явно выбранного вызова разумно оставлять отдельной ссылкой, а `@` может быть читабельным для постоянно нужной общей обёртки; назвать, какой момент работы изменится при `@` на определении. **Локальное наблюдение:** аргументированный выбор сохраняет обычные вызовы и возвращаемую карточку Planner без обязательных TRACE-сообщений. Различающий случай — предложение массово декорировать все обработчики или скрыть предметное форматирование в обёртке: ученик должен объяснить, почему это меняет границу поведения и не следует из цели 25.1.

**Общий критерий B:** ученик завершил `script`-упражнение с точным порядком, единственным запуском обеих операций и сохранёнными результатами для двух наборов строк, **затем без готового starter написал собственный внешний и внутренний `def`, обе формы применения и независимый прогноз времени настройки**, исправил *два паспортных* дефекта внешнего возврата, отдельно распознал потерю результата **при исправном декорировании** и защитил границу применения к Planner. Проверка после шагов 1–2 различает «заполнил `pass`» и «умеет самостоятельно написать декоратор»: второй опыт содержит только входные значения, а преподаватель наблюдает текст написанного кода, результат и объяснение разницы времён. По ошибкам вернуться к 01 (объект функции), 02–03 (эквивалентность записей), 04 (порядок), 05 (два уровня возврата) или 06 (границы). **Необязательный перенос:** самостоятельно придумать третью исходную функцию без изменения декоратора и объяснить, почему он не зависит от конкретной строки.
