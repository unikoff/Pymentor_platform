## 00. От знакомой функции к ясному вызову

Из этого затруднения выводим правила привязки; затем вернёмся к желанию указывать приоритет не всегда.

1. **Точка старта:** обработчики и предметные функции получают данные через параметры; фабрика получает все значения при создании задачи.
2. **Новый вопрос:** как сделать приоритет необязательным для вызова и сохранить привычный ввод через CLI?

Сначала разберём, как Python связывает значения с именами в определении. Затем отделим допустимые сочетания от ошибок и применим эти правила к настоящей фабрике, не меняя устройство задачи и команды Planner.

## 01. Параметр и аргумент находятся по разные стороны вызова

В определении функции параметр задаёт имя для входного значения. В вызове аргументом называют само переданное значение. Например, в `def badge(name, label):` имена `name` и `label` являются параметрами, а в `badge("SQL", "курсы")` строки служат аргументами. Когда функция начинает работать, Python связывает аргументы с параметрами, а код тела обращается уже к параметрам.

Эту связь можно представить как форму с подписанными полями. Определение перечисляет поля, а вызов передаёт значения. Пока мы не заполнили поле, функция не знает, какое значение использовать. Граница аналогии в том, что Python не читает смысл строки или числа: если два значения переставить, он не догадается о намерении и будет следовать правилам вызова.

```python
def make_badge(name, label):
    return f"{label}: {name}"

result = make_badge("SQL", "курс")
print(result)
```

Здесь `name` получает первую строку, `label` вторую, поэтому функция возвращает `курс: SQL`. Аргументы не являются частью определения, а параметры не являются переменными, которые нужно объявить отдельно в месте вызова. Это две стороны одного договора: функция задаёт имена входов, вызывающий код предоставляет значения.

**Первая проверка (повторение подготовленной A):** до запуска ученик заполняет две колонки «имена из `def`» и «значения из вызова» для `make_badge("SQL", "курс")`, затем сам меняет только два передаваемых значения на `"Python", "язык"` и прогнозирует возвращённую строку. Проверка — значения появляются в местах, названных в `return`; при ошибке вернуться к подписи параметров внутри `def` (§01), а не искать `name` и `label` среди аргументов.

Параметры не заполняются заранее, когда Python читает определение функции. Связь создаётся отдельно для каждого вызова. Если вызвать одну функцию дважды с разными значениями, её параметры получают значения текущего вызова. Поэтому сигнатуру мы читаем в определении, а аргументы ищем там, где функцию вызываем. **Визуальная опора для MAIN:** две колонки «определение: имя параметра» и «вызов: переданное значение», одна стрелка на каждую пару; стрелки задаются правилом Python, а не смыслом слов.

## 02. Позиционные аргументы связываются по порядку

Когда аргументы записаны без имён, Python сопоставляет их параметрам слева направо. Первое значение предназначено первому параметру, второе второму. Этот способ компактен и подходит, если порядок параметров хорошо известен и сами значения легко различить.

```python
def route_label(start, finish):
    return f"{start} -> {finish}"

print(route_label("Центр", "Парк"))
print(route_label("Парк", "Центр"))
```

Оба вызова допустимы. Во втором Python не обнаруживает ошибку: значения строковые и подходят по количеству. Но смысл маршрута меняется, потому что поменялись местами аргументы. Позиционная привязка проверяет расположение, а не смысл и тип значения. Поэтому вызов может быть синтаксически корректным, но выражать не то, что задумал автор.

**Первое различающее действие:** до просмотра вывода ученик рисует две стрелки `значение → параметр` для каждого вызова `route_label`, предсказывает оба маршрута, запускает и самостоятельно составляет третий позиционный вызов с городами `"Вокзал"`/`"Школа"`, где направление важно. **Проверка и обратная связь:** оба исходных вызова успешны, но подписи противоположны; если ученик ожидал отказ для «неправильного направления», показать, что Python не знает предметного смысла строк. Для третьего вызова порядок точек должен совпасть с предсказанным текстом. В MAIN здесь уместна небольшая схема двух соответствий, а не ещё одно угадывание «верно/неверно».

Так же передавались значения в прежней `create_task`: сначала идентификатор, затем заголовок, затем приоритет. Читая позиционный вызов, мы восстанавливаем назначение каждого аргумента по сигнатуре функции. При длинном вызове или нескольких числах легко ошибиться в порядке. Тогда можно записать имена рядом со значениями.

## 03. Именованные аргументы показывают назначение значения

Именованный аргумент записывается как `имя_параметра=значение`. Python ищет параметр с таким именем и связывает с ним значение независимо от места этого аргумента среди других именованных аргументов.

```python
def route_label(start, finish):
    return f"{start} -> {finish}"

print(route_label(start="Центр", finish="Парк"))
print(route_label(finish="Парк", start="Центр"))
```

Результаты совпадают, хотя именованные аргументы во втором вызове идут в другом порядке. Связь каждого значения видна прямо в месте вызова. Это особенно полезно, когда несколько параметров принимают похожие значения или флаг записан как `True` либо `False`.

**Самостоятельный перенос на ещё один маршрут:** ученик сам записывает один вызов `route_label` с именованными `start`/`finish` для пути `"Дом" → "Музей"`, после чего меняет порядок **записанных** именованных аргументов, оставляя значения при тех же именах. Прогноз — обе строки одинаковые; если направление меняется, ученик проверяет, не переставил ли значения **между именами** вместо перестановки записей. Это проверяет понимание механизма, а не запоминание конкретных городов в образце.

Здесь помогает аналогия с адресом на посылке: подпись сообщает, к какому полю относится содержимое. Но подпись должна совпасть с параметром в определении. **Предел аналогии:** Python сопоставляет имя буквально; опечатка не доставляется «по похожему адресу». Именование уточняет вызов, но не меняет набор параметров и алгоритм функции.

Именованный аргумент можно сочетать с позиционными. Сначала мы разберём порядок такого сочетания, чтобы один параметр не получил два разных значения и вызов оставался однозначным.

## 04. Сочетание форм не должно дублировать параметр

В обычном вызове позиционные аргументы записываются раньше именованных. После перехода к именам оставшиеся значения тоже указываются с именами. Например, `route_label("Центр", finish="Парк")` допустим: позиционное значение заполняет `start`, именованное заполняет `finish`.

Обратная форма `route_label(start="Центр", "Парк")` недопустима: позиционный аргумент стоит после именованного. Python отклоняет такую запись ещё при разборе кода, поэтому тело функции не запускается. Это синтаксическая ошибка, а не неправильный результат функции.

Есть ещё правило однократной привязки. Если первый параметр уже получил позиционное значение, нельзя передать ему другое именованное значение: `route_label("Центр", start="Парк")`. Для человека оба значения видны, но один параметр не может одновременно означать две точки отправления. Сначала Python связывает аргументы и сообщает о конфликте, затем только при успешной привязке начинает выполнять тело.

**Микродиагностика до новых правил:** ученик сравнивает три записи на знакомой `route_label`: `route_label("Центр", finish="Парк")`, `route_label("Центр", start="Парк")` и `route_label(start="Центр", "Парк")`. Он самостоятельно отмечает, какая форма допустима, где параметр указан дважды, а где сам порядок аргументов делает **запись недопустимой**; только потом запускает примеры **по одному** в интерпретаторе. **Критерий:** первая строка возвращает маршрут, вторая вызывает `TypeError`, третья — `SyntaxError`, поэтому третью нельзя вставлять в сохраняемый `main.py`. При путанице вернуться к схеме §02 (занятое первое место) и сопоставлению имени §03. **Следующая попытка:** самостоятельно написать другой корректный смешанный вызов с новым направлением, не копируя первый.

Когда часть значений разрешено не передавать, эту возможность задают в определении функции. Она не отменяет перечисленные правила: именованный параметр должен существовать, один параметр заполняется один раз, обязательные значения остаются обязательными.

## 05. Значение по умолчанию используется только при пропуске

Параметр со значением по умолчанию можно не указывать в вызове. Python использует это значение, только если соответствующий аргумент отсутствует. Если значение передано явно, используется оно.

```python
def notice(text, prefix="ЗАДАЧА"):
    return f"[{prefix}] {text}"

print(notice("Проверить тесты"))
print(notice("Проверить тесты", prefix="ВАЖНО"))
```

В первом вызове `prefix` получает настройку из определения. Во втором он получает явную строку `ВАЖНО`. Значение по умолчанию не является проверкой ввода и не исправляет неподходящий аргумент. Оно описывает обычный вариант, который допустимо выбрать автоматически, если вызывающий код ничего не уточнил.

**Первая самостоятельная проверка default:** для `notice` ученик предсказывает отдельно три результата — при отсутствии `prefix`, при явном `prefix="СРОЧНО"` и при явном `prefix=""` — затем сам записывает недостающие два вызова и сравнивает их строки. **Различающий результат:** при пропуске виден `[ЗАДАЧА]`, при собственной метке — `[СРОЧНО]`, при пустой строке — `[]`; пустая строка не приводит к `[ЗАДАЧА]`. Если ученик ожидает замену пустой строки default, возвращаемся к условию «аргумент **не передан**», а не к понятию «неполезное значение».

Обязательные параметры в обычной сигнатуре перечисляются до параметров со значениями по умолчанию. Иначе определение неоднозначно: Python не сможет понять, какое пропущенное позиционное значение относится к параметру без default. Поэтому сначала указывают необходимые данные, после них настройки, которые разрешено опустить.

Хороший default соответствует нормальному поведению функции. Не стоит делать необязательным важное значение только ради короткой записи: функция тогда может успешно выполниться, хотя в ней не хватает данных. В Planner приоритет уже имеет согласованное обычное значение `2`, но интерфейс продолжает спрашивать его у человека. Если CLI передаёт введённый приоритет, именно он и используется.

Пропуск аргумента отличается от явной передачи `None`, нуля или пустой строки. Если значение указано, Python не применяет default, даже если оно пустое или равно нулю. Функция получает именно переданное значение; отдельные проверки его смысла, если они нужны, относятся к правилам самой функции. **Опора при возврате:** «нет аргумента → default; есть аргумент → переданное значение»; это правило для простого неизменяемого default `2`, а поведение изменяемого default с накоплением состояния изучается отдельно в `22.1`.

## 06. `TypeError` показывает, что вызов не связан с сигнатурой

Если обязательный аргумент пропущен, имя аргумента неизвестно или один параметр получил два значения, Python сообщает `TypeError`. Для этих ошибок тело функции ещё не выполнялось: отказ произошёл при попытке сопоставить аргументы параметрам.

Например, `route_label(start="Центр")` не передаёт обязательный `finish`; `route_label(origin="Центр", finish="Парк")` указывает неизвестное имя; `route_label("Центр", start="Парк", finish="Парк")` дважды заполняет `start`. Каждый случай нарушает отдельное правило привязки. Мы можем прочитать сигнатуру и найти причину, не меняя тело функции.

Значение по умолчанию помогает только при пропуске того параметра, у которого оно задано. Оно не заполняет другой обязательный параметр и не делает неизвестное имя допустимым. Ошибки вроде некорректного значения внутри тела относятся к другому этапу выполнения. Здесь нам нужно распознать неправильный вызов; перехватывать или проектировать обработчик ошибки мы пока не будем.

Мы различаем и момент отказа. Позиционный аргумент после именованного не образует корректную запись вызова, поэтому Python сообщает синтаксическую ошибку при разборе. Пропущенный параметр, неизвестное имя или повторная привязка находятся позже: запись построена, но её значения нельзя согласовать с сигнатурой. В обоих случаях тело не выполняется, однако причина различается.

**Самостоятельный разбор ошибки по причине:** после демонстрации первой пары из §06 ученик пишет **по одному** вызову с (а) отсутствующим `finish`, (б) опечаткой в `start`, (в) повторно заполненным `start`, а затем объясняет видимую ошибку по схеме «сигнатура → занятые параметры → нарушенное правило». Проверяет `TypeError` в каждом случае; точный текст сообщения зависит от Python и не является целью. В четвёртом случае он лишь в интерактивной строке разбирает неверный порядок позиционного и именованного аргумента, наблюдает `SyntaxError`. **Диагностическая обратная связь:** если вместо `TypeError` вышла иная ошибка из тела или вывелся результат, проверить, что использован именно `route_label(start, finish)` и ошибка находится **в вызове**, а не внутри функции. Ни один неправильный вызов не переносить в файл с CLI.

## 07. Уточняем договор настоящей фабрики Planner

В существующем проекте задача остаётся словарём с полями `id`, `title`, `priority` и `is_done`. `create_task` принимает идентификатор, заголовок и приоритет. Вызывающая операция назначает идентификатор, передаёт фабрике заголовок и приоритет, а обработчик CLI до этого получает оба значения от пользователя.

Мы меняем только договор приоритета: идентификатор и заголовок по-прежнему обязательны, а для `priority` задаётся default `2`. Это позволяет вызвать реальную фабрику без указания приоритета там, где подходит обычное значение. Структура словаря, начальное `is_done=False` и назначение идентификатора остаются прежними.

Важно проследить весь путь значения. Обработчик добавления читает приоритет, передаёт его операции добавления, а та передаёт его фабрике. Явное значение продолжает побеждать default, поэтому привычная команда не теряет ввод. Мы не убираем вопрос из CLI, не создаём вторую фабрику и не переносим расчёт id.

Существующий вызов из `add_task` передаёт три значения, поэтому после уточнения сигнатуры он остаётся допустимым. Новая возможность нужна только вызовам, которые намеренно пропускают `priority`. Мы сохраняем прежний путь команды и одновременно задаём полезное значение для такого сокращённого вызова.

Чтобы проверить именно исходную функцию отдельно, в Windows мы запускаем `python -i main.py` из папки проекта. Файл сначала выполняет обычный CLI; после команды `exit` Python оставляет определения в интерактивном режиме с приглашением `>>>`. Так мы вызываем настоящую фабрику без импорта файла и без временной копии функции.

Перед правкой ищем реальные вызовы `create_task`, чтобы знать, на какую сигнатуру они опираются. После правки проверяем пропуск приоритета, явно переданное значение и именованный вызов отдельно. Затем повторяем добавление через CLI и убеждаемся, что новая задача получает тот же id, введённый приоритет, прежние поля и статус незавершённой.

**Переход от учебных примеров к проекту:** в MAIN дать для чтения две разные трассы, которые ученик объясняет сам: прямой вызов фабрики без третьего аргумента должен использовать `2`, но путь `handle_add → add_task → create_task` передаёт **введённое** число и не использует default. Ученик перед записью кода помечает место, где появляется значение приоритета в каждой трассе, и указывает, кто назначает id. **Критерий понимания:** вторая трасса не обязана давать `2`; регрессия проверяет другой договор — сохранность явно введённого значения. Ответ в виде «CLI теперь всегда ставит 2» обнаруживает смешение интерфейса и сигнатуры.

## 08. Что мы будем делать в практике

**Формат и вход:** «Основная практика, проект и короткое исследование». Предусловие выдачи: по сохранённой работе `21.1` проверить шесть обработчиков и привычные `add/list/stats`; на коде ученика подтвердить реальную `create_task(task_id, title, priority)` и путь `handle_add → add_task → create_task` по диагностике `21`. Входом служит **его существующий `main.py`**, готовые функции и словарь `id/title/priority/is_done`, а не стартовая копия фабрики или новый проект. Новую сигнатуру и проверочные вызовы ученик пишет самостоятельно. Для изолированных проб применяется `python -i main.py`: после обычной команды `exit` при подтверждённом способе запуска открывается `>>>`; определения доступны без импорта и повторного объявления. **Цель:** одновременно доказать самостоятельное понимание связывания и расширить только договор реальной фабрики, сохранив пользовательский CLI.

1. **От чтения к карте потребителей → установлено, что изменяем.** **Вход:** проверенный код после `21.1`, известные четыре поля; **объект:** определение и все вызовы `create_task`, `get_next_id`, `add_task`, `handle_add` (планируемая B `21` и `21.1`, здесь §§01–03, 07). **Самостоятельно:** ученик находит ссылки на имя функции в своём `main.py`, рисует цепь с подписями «кто получает id / кто спрашивает priority / кто только собирает словарь», подписывает каждую пару `аргумент → параметр` в существующем вызове, отмечает потребителей до изменения. **Локальный результат без правки:** id приходит от `get_next_id`, явный приоритет проходит через CLI, фабрика получает три аргумента и возвращает четыре поля. **Диагностика:** если ученик написал «id придумывает фабрика», он должен найти именно место вызова `get_next_id`; при неожиданной сигнатуре практика зависит от восстановления входной версии, не от угадывания параметров.
2. **Собственное уточнение сигнатуры → прежний вызов всё ещё работает.** **Вход:** карта из шага 1; **объект:** существующее определение `create_task` (§§04–05, 07). **Самостоятельно:** ученик меняет только параметр `priority`, сохраняя `task_id` и `title` обязательными, не переписывая тело словаря, не меняя `add_task`; отдельно объясняет, почему вызов с тремя аргументами не изменился. **Локальный результат:** по прямому вызову в интерактивном режиме с **тремя** прежними аргументами возвращается тот же словарь с `is_done=False`, а `priority` равен третьему аргументу; до шага 3 уже видно, что совместимость старого потребителя сохранена. **Если ошибка:** проверить расположение `=2` после двух обязательных параметров и место прежнего вызова, не давать ученику целиком готовое определение.
3. **Построение четырёх разных форм вызова → найдено отличие default от явного ввода.** **Вход:** обновлённая фабрика в `>>>`, собственные новые id/заголовки, не добавляемые в рабочий список (§§02–05, 07). **Объект:** вызовы настоящей фабрики; **самостоятельно:** ученик до запуска составляет таблицу «форма → какие параметры заполнены → ожидаемое значение priority», затем сам записывает (а) два позиционных аргумента без priority, (б) три позиционных с допустимым явным значением **3**, (в) именованные аргументы в переставленном порядке с явным **1**, (г) правильное смешение позиции с именованными аргументами без дублирования параметров. **Локальный результат:** в (а) приоритет 2, в (б)/(в) 3/1 соответственно, в (г) заполняются именно указанные параметры; каждый словарь содержит прежние `id/title/priority/is_done`, где статус `False`. **Различающий случай:** в эксперименте с `notice` (§05) пустой `prefix` не включает default; ученик объясняет аналогичное правило для явного `None`, но не делает `None` разрешённым приоритетом в проекте. **Обратная связь:** если (в) ведёт себя как позиционный вызов или (г) падает, разобрать имя/занятый параметр по §§03–04; ученик исправляет свой вызов, не копируя эталон.
4. **Самостоятельная диагностика трёх отказов → ошибка связана с конкретным правилом.** **Вход:** эта же интерактивная сессия, обновлённая `create_task`, уже понятная схема вызова (§§04, 06); **объект:** отдельные экспериментальные вызовы, не строки штатного `main.py`. **Самостоятельно:** ученик придумывает и вводит по одному примеру: с одним `task_id`, но без обязательного `title`; с неверным именем вместо одного параметра; с `task_id`, заполненным и по позиции, и по имени. **Локальный результат:** каждый даёт `TypeError` до построения словаря, ученик для каждой ошибки указывает, какой параметр отсутствует/неизвестен/дублируется; точная формулировка Python не оценивается. Запись с позиционным аргументом после именованного исследуется отдельно на маленькой `route_label` из §04: получаем `SyntaxError` при разборе. **Обратная связь:** если вышел словарь, ошибка не воспроизведена — ученик перечитывает сигнатуру; если появилась ошибка *внутри* тела, она не доказывает ошибку связывания. В CLI исключения не ловятся и не генерируются намеренно.
5. **Регрессия пользовательской команды → узкая новая возможность без изменения меню.** **Вход:** сохранённое поведение после `21`/`21.1`, исправленная фабрика и обычный запуск `main.py` (§07); **объект:** `add`, `list`, `stats`, пользовательский словарь и diff. **Самостоятельно:** ученик за один обычный запуск дважды выполняет `add`, каждый раз отвечает на запрос приоритета **явными разными** допустимыми значениями (например, сначала 3, затем 1), затем смотрит `list` и `stats` и сравнивает с прежним форматом. Сопоставляет трассу каждого значения `handle_add → add_task → create_task` с правилом default и проверяет diff своей правки. **Локальный результат:** оба значения 3/1 остались именно введёнными, id по-прежнему выдаёт `get_next_id` в прежнем порядке, `is_done` обоих новых словарей `False`, четыре ключа и карточка сохранены, статистика учитывает новые задачи; diff не затрагивает ввод, обработчики и фабрику второй раз. **Диагностика:** случай с явным приоритетом `2` **не доказывает** сохранение пользовательского ввода, поэтому он не заменяет эту регрессию. Если оба значения превращаются в 2, искать потерянный аргумент в одном из существующих вызовов, а не исправлять default.

**Почему шаги связаны:** сначала фиксируем старый договор без правок (1), изменяем сигнатуру с немедленным контролем совместимости (2), сами создаём и различаем допустимые вызовы (3), по правилам диагностируем недопустимые (4), затем доказываем, что новая возможность не сломала явный выбор в реальном CLI (5). При затруднении возвращаемся к соответствующим §02 (позиция), §03 (имя), §04 (смешение), §05 (пропуск) или §06 (отказ), после чего ученик сам проверяет исправленный **другой** случай. **Общий критерий B:** у единственной реальной фабрики `priority=2` при обязательных id/title, все четыре поля сохранены, ученик объясняет причину поведения каждого проверенного вызова, а пользовательский приоритет доходит без подмены. Подготовленный выход для `22` — умение читать передачу аргумента; ссылочную семантику, копии и мутацию разберём там.
