## 00. Откуда берётся состояние одного запуска

В предыдущих занятиях мы разбирали, как функция получает объекты через параметры и как изменение списка видно через разные имена. Теперь используем это понимание в жизненном цикле знакомого Planner. Пока `run()` сам создаёт список задач внутри функции, поэтому вызывающий код не может передать ему уже подготовленное состояние и получить итоговый список после выхода.

1. **Точка старта:** мы знаем ссылки, мутацию списков и словарей, параметры и `return`; `run` пока создаёт собственный список.
2. **Новый вопрос:** как отличить отсутствие списка от намеренно пустого списка и не разделить один список по умолчанию между запусками?
3. **Результат:** мы изменим договор `run`, чтобы передавать состояние, сохранять тот же контейнер во всех командах и получать его после обычного `exit`.

Эти шаги связывают уже знакомые ссылки с конкретным владельцем состояния. Сначала разберём, когда Python создаёт значение по умолчанию; затем отделим отсутствующее состояние от пустого и проследим путь одного списка через команды и завершение цикла.

## 01. Когда появляется значение по умолчанию

**Задача ступени.** Отделить момент определения функции от момента её вызова. При выполнении `def` Python вычисляет выражения default и сохраняет полученные объекты вместе с функцией. Вызов без аргумента берёт уже сохранённый объект. Для числа `priority=2` из предыдущего занятия это обычно незаметно: число не меняют на месте. Для списка `history=[]` несколько вызовов способны изменять один общий контейнер.

Независимый от Planner сюжет — журнал отметок. В будущей ученической теории разобрать две оси времени: **один раз при `def`** создаётся список и **каждый раз при вызове** выполняется тело. Показать маленькую функцию `mark(label, history=[])`, которая добавляет метку и возвращает журнал. Код учебного опыта допускается, но проектную сигнатуру и тело `run` не показывать.

**Первая попытка после объяснения:** ученик до запуска составляет таблицу трёх вызовов: `mark("alpha")`, `mark("beta")` и `mark("own", external)` при отдельном `external=[]`. В таблице отмечает, какой список получил метку и что вернул вызов; затем сам выполняет опыт. Вторая строка должна показать накопление двух меток в default, третья — изменение `external` без изменения общего default. После этого попросить **самостоятельно изменить** пример так, чтобы явная передача `[]` не очищала общий журнал. Это отличает понимание объекта от заучивания вывода.

**Разбор ошибки и опора:** запись `def run(tasks=[])` означала бы потенциально общие задачи независимых сеансов. Предупредить, что изменяемый default сам по себе допустим при намеренном общем состоянии, но здесь нарушает B. Модель «одна доска объявлений, установленная при открытии помещения» помогает объяснить общность; предел аналогии — в Python общий именно объект, сохранённый в default функции, а не все списки программы. Вернуться сюда, если второй обычный запуск вдруг получил задачи первого.

**Переход:** нужен способ попросить новый список для запуска без смешения с уже переданным объектом.

## 02. `None` и создание списка по требованию

**Смысл.** В договоре этого занятия `None` — условный сигнал «начального контейнера нет». Это отдельное значение, не пустой список и не задача. Если аргумент опущен, default `None` передаётся в параметр; явное `None` здесь означает то же самое. Только после проверки сигнала создаётся **новый** список внутри конкретного вызова. Если список есть, параметр ссылается на него без копирования.

**Независимый пример.** На корзине с товарами объяснить короткую функцию с необязательным параметром `basket=None`: при `basket is None` создаётся пустая корзина, затем туда кладут одну позицию и возвращают корзину. Пояснить назначение каждой части формы `is None` / `=[]` в теле / `return`, не показывая готовое изменение `run`. «Новая корзина по запросу» — вторая наглядная опора; её предел: функция не создаёт постоянного хранилища, данные живут лишь пока на них ссылается код текущего процесса.

**Первое самостоятельное действие:** дать другой нейтральный объект, список участников встречи, и только входные значения. Ученик сам добавляет ветку для отсутствующего списка в небольшой функции, проверяет два вызова без аргумента и вызов со своим `attendees=[]`; объясняет, почему `result is attendees` истинно только в последнем случае. Проверка после собственного написания, а не копирование готового решения корзины. В отчёте различить возвращённый **объект** и печать его содержимого: `return` не вызывает `print`.

**Тонкая граница:** значение `None` здесь не допускается в качестве полезного списка задач; мы договорились считать его отсутствием. Если в другой программе `None` будет допустимыми данными, потребуется иной маркер, но реализовывать его сейчас не нужно. Отдельно объяснить, что локальная переменная `basket` не становится глобальной: при привязке к переданному списку она хранит ссылку на него.

**Переход:** наличие аргумента не определяется тем, пустой ли его список; это различие становится следующим самостоятельным выбором.

## 03. Три входа, два похожих условия и одна ловушка

**Механизм.** Проверка `items is None` задаёт вопрос о специальном сигнале. Проверка `if not items` задаёт другой вопрос: считается ли значение ложным. Пустой список и `None` оба ложны, хотя один — существующий контейнер вызывающего кода. Выражение `items or []` также создаст другую пустую коллекцию, когда `items=[]`. Даже если содержимое выглядит правильно, договор идентичности может быть нарушен.

Запланировать компактную **таблицу выбора состояния** с тремя входами: аргумент отсутствует/`None`; явно передан `[]`; явно передан непустой список. Ученик сам заполняет для каждого варианта колонки «нужен новый контейнер?», «что произойдёт при `if not items`?», «должно ли `result is supplied` быть истинно?». Затем дать небольшой независимый код сортировки карточек по двум коробкам и предложить найти ошибочную ветку, которая заменяет переданный пустой список. Разбор показать **после** прогноза, с проверкой `is`, а не только `==`.

**Различающий контрпример:** для переданного непустого списка ошибочное условие часто кажется правильным; для переданного пустого списка оно теряет исходный объект. Пусть ученик изменит только начальное состояние в своём эксперименте и объяснит, почему вывод сменился, хотя вызов с аргументом остался. Это полноценная диагностика неверного критерия, а не второй вопрос на узнавание `None`.

**Опора для возвращения:** «`is None` проверяет отсутствие, `if not x` — пустоту/ложность; `is` сравнивает идентичность, `==` содержимое». Если впоследствии `provided=[]` остался пуст, а возвращённый результат содержит задачу, искать новое присваивание параметру здесь и в разделе 04, а не чинить вывод списка.

**Переход:** правильная инициализация ещё не гарантирует сохранения состояния, если другие функции начнут работать с копиями.

## 04. Кто владеет состоянием во время команд

**Маршрут объекта.** `run` выбирает один контейнер **перед** циклом чтения команд: новый для `None` или уже переданный. Команда добавления передаёт его обработчику и далее существующей операции `add_task`; чтение списка, поиск, завершение и статистика видят текущее состояние. Обработчики не должны каждый заводить собственный рабочий список. Смена имени параметра внутри вызова не меняет внешнюю ссылку, но `append` и изменение словаря задачи через общую ссылку видны всем владельцам.

В MAIN дать **схему перемещения ссылок, не копии данных**: вызывающий код → параметр `tasks` в `run` → параметр нужного `handle_*` → прежняя операция над тем же списком → следующий `handle_*`. Пояснить, что стрелки означают передачу одного объекта, а не перенос/копирование файла. Два режима запуска различаются тем, есть ли первоначальный внешний владелец; внешний список не обязан существовать при обычном `run()`.

**Самостоятельная мини-трассировка:** на маленькой функции с двумя помощниками (первый добавляет запись, второй считает элементы) ученик рисует три имени и один объект; затем меняет в первом помощнике действие на `local = []`, предсказывает, какое состояние увидит второй, и проверяет. Этот пример не использует `run` и не раскрывает полное решение проектной практики. Перенос: в предъявленной версии `main.py` ученик сам отмечает, **где** создаётся список и **какая** переменная передаётся каждой ветке, прежде чем править код. Привязать места к реальным функциям только после сверки снимка проекта.

**Граница:** возвращённый список содержит прежние словари по ссылкам; глубоких копий, `global`, второго хранилища или файлового сохранения здесь нет. Идентичность контейнера важна и для пустого входа, даже когда внешне показанный список задач пуст. Если одна команда «не видит» добавление другой, диагностируем передачу аргумента или копирование, не переписываем алгоритмы поиска и id.

**Переход:** после последней команды цикл заканчивается, но результат ещё необходимо отдать вызывающему коду.

## 05. Где заканчивается цикл и где возвращается результат

`break` завершает **ближайший цикл**, а не всю функцию; исполнение продолжается за этим циклом. `return` завершает **функцию** и отдаёт значение вызывающему коду. В нейтральном примере обработки списка сигналов объяснить три случая: стоп-сигнал в середине, в начале и отсутствие стоп-сигнала. После `break` функция может вернуть накопленный объект; `return` посреди обычного шага остановил бы работу слишком рано.

**Первое действие:** по краткой схеме «до цикла → чтение элемента → `break` по сигналу → после цикла» ученик ставит отметки о достижимости строк и объясняет, что возвращает функция для трёх случаев. Затем самостоятельно переносит рассуждение на команду `exit` знакомого CLI: какой участок должен закончиться и где логично забрать итоговый список? **Не показывать полный проектный `run`**; место и запись возврата остаются за учеником.

**Различение результата и вывода:** меню продолжает выводиться командами `print`, а `return tasks` передаёт объект вызывающему коду, даже если этот код не использует результат обычного конечного `run()`. Списки не переживают выход из процесса без сохранения на диск; этот урок добавляет только управление состоянием **в памяти одного процесса**.

**Опора и диагностика:** если `run` отдаёт `None` после `exit`, проверить, не забыли ли `return` за циклом; если после добавления невозможно вызвать следующую команду, проверить, не поставлен ли `return` внутри ветки или цикла. Ошибочный ранний `return` отличается от корректного `break` не формулировкой, а наблюдаемой потерей следующих команд.

**Переход:** теперь механизмы объяснены на независимых примерах; ученик применит их к одному существующему `run` и докажет новый контракт несколькими разными состояниями.

**Обязательный формат по `BLOCK_5.md`: проектная практика, изменение существующего `main.py` Planner.** Никаких новых приложений, импорта `main.py` для теста, `global`, сохранения JSON и новой фабрики задач. Перед выдачей подтвердить учебный снимок `main.py` с обработчиками, конечным вызовом `run()`, форматом словаря `id/title/priority/is_done` и правилом следующего id; при отличии от паспортного снимка сначала согласовать фактические имена и входное состояние, не выдавать выдуманную заготовку. Отдельный короткий опыт в интерпретаторе служит опорой проекту, а не заменой основной работы.

**Лестница самостоятельности: от прогноза без проекта → к собственному условию → к маршруту данных → к полному проверяемому контракту.**

1. **Поймать утечку default до изменений проекта.** Вход: самостоятельно набранная нейтральная функция журнала меток с `history=[]`, отдельный внешний `external=[]`. Объект: список, сохранённый как default. Опора: 01 и ожидаемая A `21.2` (работа с default); ученик **предсказывает три вызова, воспроизводит их, меняет порядок аргументов/входной объект и объясняет идентичность**. Локальный результат: два вызова без аргумента накапливают данные, явный внешний список меняется независимо; ошибка распознана по **объекту**, а не только по тексту вывода. Если вывод иной, вернуться к времени вычисления default в 01.
2. **Отыскать реальные места владения списком.** Вход: предъявленный после `21.1` и `22` рабочий `main.py`. Объект: существующий `run`, создание `tasks`, ветки `add/list/find/done/search/stats/exit`, обработчики и единственный конечный вызов. Опора: будущая B `21.1` с выделенными обработчиками; раздел 04; входное состояние проекта **не проверено**, поэтому до практики сверить код и ранее выполненные задачи. Ученик **сам строит карту «создаёт → передаёт → читает/меняет → завершает»** и называет строки, где одна и та же ссылка проходит между компонентами. Локальный результат: карта указывает единственное текущее создание списка и фактические ветки, отсутствующая функция не придумывается. Ошибка/несовпадение со снимком — адресная диагностика входа до редактирования.
3. **Изменить сам контракт `run`.** Вход: тот же `main.py` и карта из шага 2. Объект: сигнатура и участок **перед** командным циклом. Опора: разделы 01–03, параметры из планируемой B `21.2`, ссылки из B `22`; наличие освоения проверить перед выдачей. Ученик **сам записывает** требуемую паспортом сигнатуру `run(tasks=None)`, выбирает условие создания контейнера и размещает его один раз вне цикла. Локальный результат после сохранения: код принимает обычный вызов без аргумента, при явном пустом списке условие не создаёт замену; в нём нет `tasks=[]` как default и подменяющего `tasks or []`. На этой ступени достаточно увидеть условия и проверить прежний обычный CLI; итоговый возврат проверяется после шага 4.
4. **Собрать единый жизненный цикл и возврат.** Вход: рабочий `run` из шага 3, карта передач и имеющиеся `handle_*`. Объект: аргументы каждой реально существующей ветки и ветка `exit`. Опора: разделы 04–05 и ожидаемая B `21.1` о передаче единого списка. Ученик **сам устраняет только обнаруженные потери ссылки**, ставит возврат выбранного состояния после завершения цикла и объясняет, почему обычное действие не должно завершать `run`. Локальный критерий уже на этом шаге: при `add → list → exit` добавление видно до выхода, цикл не заканчивается после `add`, а в сохранённом коде оператор возврата расположен за командным циклом; прежние тексты меню сохраняются. Фактическое возвращённое значение наблюдаем в следующем шаге с временным вызовом. При проблеме со связностью вернуться к схеме 04; при `None` на выходе — к 05.
5. **Организовать безопасное наблюдение нескольких запусков.** Вход: изменённый `main.py`, все определения функций выше его конечного вызова. Объект: **только временная** точка запуска в конце файла. Опора: разделы 02 и 05, знание переменных/вызовов из прежнего курса; факт автоматического запуска при импорте ещё проверить на учебном коде. Ученик **сам временно заменяет последний `run()` последовательностью присваиваний результатов нескольких вызовов и проверочных `print`**, запускает `main.py` напрямую в терминале. Для каждого вызова вводит отдельный `exit`; сравнения выполняются после возврата. Локальный результат: в **одном процессе** можно получить и сравнить несколько значений без импорта `main.py` и без перестановки/дублирования определений. Если исполняется только первый вызов, проверить, где стоит `return` и был ли введён `exit`.
6. **Пройти различающие входы и проверить id.** Вход: временный сценарий шага 5 и три заранее подготовленных тестовых состояния; заполненный список содержит **валидную задачу** `{"id": 7, "title": "Старая", "priority": 2, "is_done": False}`, остальные два пусты. Объект: результаты вызовов `run` и исходные переданные списки. Опора: разделы 02–04, прогноз идентичности из B `22` (проверить при выдаче), прежнее правило id «максимальный + 1» (проверить учебную реализацию до запуска). Ученик **сам** проверяет: (а) два `run()` подряд, в первом добавляет задачу и выходит, во втором сразу выходит; (б) `shared=[]`, через `run(shared)` добавляет одну задачу; (в) `run(filled)`, добавляет задачу к уже существующей с id 7. Отдельно объясняет, почему `==` недостаточно и требуется `is`. Локальные различающие результаты: второй обычный запуск пуст и имеет **другой объект**, `result is shared` истинно и `shared` содержит новую задачу, `result is filled` истинно, исходная задача сохранена, новая получает id **8**, если правило «max + 1» действительно действует. Ошибка только на `shared=[]` указывает на раздел 03; ошибка на обоих переданных списках — на разделы 02/04; ошибка id — на фактическую прежнюю функцию выбора id, которую здесь не переписывают без подтверждённой причины.
7. **Сохранить привычный Planner.** Вход: `main.py` со сценариями наблюдения и выполненные проверки шага 6. Объект: прежний CLI и штатная точка входа. Опора: разделы 04–05, планируемая B `21.1`; реальный набор команд — сверить с учебным снимком. Ученик **сам прогоняет** `add/list/find/done/search/stats/exit`, пустой список и статистику, повторное `done`, неизвестный id и неизвестную команду; наблюдает, что правила и сообщения не утрачены. Затем **удаляет только временные вызовы/печать** и восстанавливает единственный конечный `run()`; просматривает diff, сохраняя новый контракт и возврат. Локальный итог: обычный запуск не изменился по возможностям, временного тестового меню/потока диагностических сообщений нет; `run(tasks=None)` и возврат на `exit` остались в коде.

**Почему шаги связаны:** шаг 1 показывает причину недопустимого общего default; шаги 2–4 превращают модель из разделов 02–05 в **собственную правку реального `run`**; шаги 5–6 отличают правильный контракт от решений, которые работают только с заполненным списком; шаг 7 показывает сохранение старой B Planner. При затруднении ученик возвращается к конкретному объяснению выше и заново предсказывает изменённый случай, прежде чем читать разбор. В будущем MAIN маршрут вступления и эту цепь действий оформить двумя содержательными связанными группами; между длинными объяснениями ставить прогноз, схему ссылки или трассировку с **разными** операциями ученика, а не повторные тесты узнавания `None`.

**Проверка B:** новый список для каждого независимого обычного `run()`; тот же переданный объект как с `[]`, так и с заполненным списком; одна передача через команды; `exit` отдаёт состояние; прежние операции и правило id сохраняются. Случай `shared=[]` необходим, потому что `if not tasks` ошибочно проходит проверку с непустым списком; два обычных запуска необходимы, потому что один запуск не выявляет общность изменяемого default. Проектный договор рассчитан на один процесс; JSON, модульная структура, глобальное хранение и Stage 3 в этом занятии не реализуются.
