## 00. Вступление

В предыдущем шаге мы исследовали, как функция собирает аргументы и передаёт их дальше, сохраняя форму вызова. Теперь перенесём знакомые обработчики Planner из условий в таблицу: `run` будет выбирать функцию по команде, а затем вызывать её с общим списком задач.

1. **Точка старта:** у нас есть команды Planner, готовые обработчики с общим входом `tasks` и словари для хранения соответствий.
2. **Новый вопрос:** как сохранить функцию, чтобы вызвать её только после выбора команды?
3. **Результат:** мы свяжем рабочие команды с обработчиками и подключим выбор в `run`, сохранив прежнее поведение Planner.

Сначала разберём разницу между именем функции и её вызовом. Затем проследим, кто передаёт callback, кто его вызывает и какие условия должны совпадать. Эта опора поможет перейти от отдельных веток к таблице действий в основном проекте. Замыкания и вложенные функции оставим следующему занятию.

## 01. Имя функции, вызов и полученный результат

При выполнении `def` Python создаёт функцию и связывает с ней имя. Когда мы пишем это имя без круглых скобок, мы обращаемся к самой функции. Добавив скобки и аргументы, мы вызываем её. После вызова программа получает возвращённое значение; если функция ничего явно не возвращает, результатом становится `None`.

Представим функцию как контакт в телефоне. Имя `prepare_greeting` похоже на сохранённый контакт: оно указывает, кому можно позвонить. Запись `prepare_greeting("Python")` похожа на сам звонок. Контакт не совершает вызов автоматически, и передача контакта другому приложению тоже сама по себе никому не звонит. Граница аналогии в том, что функция при вызове выполняет точный программный код и может вернуть значение или произвести побочный эффект.

```python
def prepare_greeting(name):
    return f"Привет, {name}!"

greeting_function = prepare_greeting
message = greeting_function("Python")
print(message)
```

При присваивании `greeting_function = prepare_greeting` мы сохраняем ссылку на функцию. Её тело начнёт работать на следующей строке, когда появятся скобки и аргумент. В результате `message` получит строку `Привет, Python!`. Здесь нет отдельной копии алгоритма: оба имени указывают на одну функцию.

В Planner это различие особенно заметно на обработчиках. Выражение `handle_find` сохраняет функцию, а `handle_find(tasks)` запускает её с текущим списком. Обработчик может читать ввод и печатать карточку, а явного результата для вызывающего кода не возвращать. Тогда значение вызова равно `None`, хотя пользователь увидел действие. Поэтому при выборе функции мы учитываем и аргументы, и ожидаемые эффекты, а не только значение `return`.

Перед чтением ответа предскажем результат такого вызова:

```python
def make_tag(value):
    return "[" + value + "]"

tag_function = make_tag
print(tag_function("ready"))
```

Будет напечатано `[ready]`. Присваивание сохранило функцию, а вызов через `tag_function` передал ей строку и получил результат.

**Первая попытка:** самостоятельно заменить `tag_function = make_tag` на `tag_function = make_tag("draft")`; до запуска предсказать, что теперь хранится в переменной и что произойдёт при `tag_function("ready")`. Затем проверить прогноз и вернуть исходную строку. Критерий: различается строка-результат и вызываемый объект. При ошибке вернуться к разбору скобок и повторить опыт с другим аргументом.

## 02. Callback: переданное действие с известным моментом вызова

Callback (обратный вызов) здесь означает обычную функцию, которую мы передали другой части программы, чтобы та вызвала её в нужный момент. Особого синтаксиса у callback нет. Термин описывает роль функции во взаимодействии: одна часть кода решает, какое действие передать, другая знает, когда его запускать.

Например, `run_report(formatter, row)` может получить форматирующую функцию и применить её к строке отчёта. Тот, кто вызывает `run_report`, выбирает правило. Сам `run_report` вызывает переданную функцию, когда дошёл до строки. Так общий ход работы остаётся в одном месте, а отдельное правило можно заменить.

Это похоже на заказ в мастерской: мы передаём специалисту образец и требование, а он выполняет работу в согласованный момент. Передача задаёт ожидаемое действие, но ещё не означает, что оно уже выполнено. Граница сравнения: callback не просто описание на бумаге, а вызываемое значение; код-получатель явно обращается к нему со своими аргументами.

Чтобы такой обмен работал, нам нужен договор функции, или callback contract: ожидаемое число и смысл аргументов, а также нужный результат или эффект. В `handle_*(tasks)` каждый обработчик получает один и тот же список. При выборе команды `run` передаёт этот список выбранному обработчику. Обработчики могут по-разному спрашивать ввод и печатать сообщения, поэтому для них важен общий вход и общая роль, а не одинаковый внутренний алгоритм.

Callback может менять переданный список и при этом возвращать `None`. Другой callback может ничего не менять и вернуть строку. Сам факт передачи не гарантирует совместимость: функция `handle_add(tasks, title)` ждёт два аргумента и не подходит месту, где вызывающая сторона передаёт один `tasks`. Сначала мы сверяем договор вызова, потом сохраняем подходящую функцию.

Для первого опыта дадим маленький вызывающий код, независимый от Planner:

```python
def label(text):
    return "[" + text + "]"

def label_with_suffix(text, suffix):
    return text + suffix

def apply_once(callback, text):
    return callback(text)
```

**Первое применение:** выбрать для `apply_once`, который передаёт один `text`, совместимую функцию из двух вариантов — `label(text)` и `label_with_suffix(text, suffix)`. Сначала назвать нужное число аргументов и самостоятельно написать вызов `apply_once` с текстом `ready`, затем проверить вывод. При `TypeError` свериться с контрактом callback, исправить выбор и повторить на строке `draft`.

## 03. Таблица связывает ключ с функцией

Словарь умеет хранить пары «ключ — значение». Если значением становится функция, словарь может играть роль таблицы действий. Например, программа форматирует короткие подписи и связывает название стиля с подходящим форматтером:

```python
def short_label(text):
    return text[:3]

def upper_label(text):
    return text.upper()

formatters = {
    "short": short_label,
    "upper": upper_label,
}
```

Создание `formatters` связывает два строковых ключа с двумя функциями. При этом ни `short_label`, ни `upper_label` пока не получают входной текст. В значении каждого элемента находится вызываемая функция, потому что после имени нет скобок.

Здесь таблица похожа на указатель в помещении: по надписи мы находим нужную дверь. Сам указатель не выполняет работу за кабинетом; он помогает выбрать адрес, после чего посетитель отдельно входит. В программе так же: поиск по словарю даёт ссылку, а отдельный вызов запускает найденную функцию. Это различие позволяет строить выбор без копирования одного и того же обработчика.

Если при создании таблицы написать `upper_label("release")`, Python немедленно вызовет форматтер и запишет результат, строку `"RELEASE"`. В ячейке таблицы окажется уже готовое значение, не функция. Если обработчик выполняет `print`, эффект также случится слишком рано. Имена без скобок нужны здесь именно потому, что действие должно дождаться выбора команды.

Разберём похожую ошибку на функции уведомления:

```python
def notify(channel):
    print("Отправили в", channel)

workers = {"backup": notify("backup")}
worker = workers["backup"]
worker("daily")
```

Здесь `notify` вызывается ещё при создании словаря, поэтому сообщение печатается сразу, а в `workers` сохраняется `None`. Последняя строка пытается вызвать `None` и приводит к ошибке. В таблице должно быть записано `notify` без скобок; тогда выбранную функцию можно вызвать позже.

**Первое применение:** самостоятельно собрать по `short_label` и `upper_label` словарь для ключей `short` и `upper`, не вызывая функции при объявлении. Для текста `Report` предсказать результаты выбора обоих ключей (`Rep` и `REPORT`), проверить их. Затем **намеренно поменять функции местами в значениях словаря**: обе останутся вызываемыми с одним аргументом, но результаты перестанут соответствовать смыслу ключей. Обнаружить перестановку по выводу, исправить пары и повторить проверку. Это будущая опора для проверки шести соответствий Planner: одинаковая сигнатура не гарантирует правильного действия. Если вызов случается при создании таблицы, вернуться к примеру с `notify` и убрать преждевременные скобки.

## 04. Выбираем обработчик в Planner

В Planner таблица связывает каждую рабочую команду с уже готовой функцией: `add` с `handle_add`, `list` с `handle_list`, `find` с `handle_find`, `done` с `handle_done`, `search` с `handle_search`, `stats` с `handle_stats`. Эти обработчики уже отвечают за предметное действие. Мы меняем только способ выбора, чтобы не переписывать добавление, поиск или статистику.

`run` остаётся диспетчером: диспетчер получает команду и направляет её подходящему действию. Сначала он показывает меню и читает ввод, затем нормализует его через уже знакомые `.strip().lower()`. Команда `exit` завершает цикл отдельно: это команда управления жизненным циклом, её обработчик не лежит среди шести рабочих операций. Для другой команды мы ищем функцию в таблице. Если ключ найден, передаём ей тот же список `tasks`. Если ключа нет, показываем прежнее сообщение о неизвестной команде и продолжаем цикл.

Для известной рабочей команды путь состоит из последовательных шагов:

1. `run` читает и нормализует введённую команду.
2. Таблица находит функцию по строковому ключу.
3. `run` передаёт найденной функции текущий `tasks`.
4. Обработчик выполняет одно действие, после чего управление возвращается циклу меню.

Эта последовательность описывает только известную рабочую команду. При `exit` мы выходим из цикла до поиска функции. При неизвестном ключе обработчик не вызывается. В обоих случаях `run` сохраняет управление меню. Таблица не заменяет цикл, ввод или обработчики; она заменяет только длинный выбор между рабочими ветками.

Порядок операций помогает нам найти ошибку до запуска: нормализовать, отдельно распознать выход, найти ключ, проверить результат поиска, вызвать подходящую функцию с текущим состоянием. Если сразу вызвать результат поиска, неизвестный ключ может дать `None`, а затем программа попробует вызвать `None` как функцию. Если вызвать обработчик дважды, пользователь увидит повторный эффект или состояние изменится больше одного раза.

Посмотрим на независимый пример выбора действия. Здесь используются **обычные именованные функции**, как и обработчики Planner: каждая принимает одну строку, поэтому вызывающий код может передать любой из них один аргумент. Нам достаточно уже знакомых `def`, словаря, проверки ключа и вызова функции.

```python
def add_exclamation(message):
    return message + "!"

def add_question(message):
    return message + "?"

def render(actions, command, message):
    if command not in actions:
        return "Неизвестное действие"
    callback = actions[command]
    return callback(message)

actions = {"excited": add_exclamation, "curious": add_question}
print(render(actions, "excited", "Planner"))
```

Словарь создаётся до вызова `render` и ничего не печатает. Внутри `render` проверка `command not in actions` означает «такого ключа нет»; только при известной команде выражение `actions[command]` получает функцию. Затем `callback(message)` вызывает её ровно один раз. Для `excited` получится `Planner!`. При неизвестном ключе функция вернёт сообщение и не попытается обратиться к отсутствующему элементу словаря. Это тот же порядок, который понадобится для рабочих команд Planner, но сами операции здесь безопасны и не меняют задачи.

**Первое применение:** до запуска предсказать результат `render` с ключом `curious` и строкой `PyMentor`, затем с отсутствующим ключом; проверить оба исхода. Самостоятельно добавить третий ключ `plain` и функцию, которая возвращает сообщение без знака, не меняя `render`; проверить, что новая команда работает, а отсутствующий ключ по-прежнему не вызывает функцию. Критерий: ученик объясняет, почему выбор выполняется по ключу и добавление нового действия требует только корректной пары в таблице. При ошибке вернуться к порядку «проверить ключ → получить функцию → вызвать» и повторить на изменённой строке.

## 05. Собираем безопасный порядок диспетчеризации

При выборе команды легко спутать **три разные проверки**: существует ли ключ в словаре, какую функцию хранит известный ключ и что эта функция вернула *после вызова*. Уже знакомое `command in actions` отвечает только на вопрос о наличии ключа (`True` или `False`). Выражение `actions[command]` получает сохранённую функцию **после** проверки ключа. А успешно выполнившийся обработчик Planner может вернуть `None`: его результат не показывает, была ли команда известна. Поэтому отсутствие команды определяем до вызова, а факт выполнения проверяем по нужному эффекту.

Независимый опыт показывает различие на списке событий, без команд Planner:

```python
events = []

def mark(name):
    events.append(name)

actions = {"save": mark}
print("missing" in actions)
selected = actions["save"]
print(selected is None)
returned = selected("draft")
print(returned, events)
```

При неизвестном ключе проверка `"missing" in actions` даёт `False`; мы не обращаемся к `actions["missing"]`, поэтому не получаем ошибку поиска ключа. При известном ключе `selected is None` даёт `False`: в `selected` лежит **функция**. Вызов один раз добавляет `draft` в `events`, хотя `returned` равен `None` (нет явного `return`). Если определить успешность команды как `returned is not None`, программа ошибочно объявит известное действие неизвестным **после того, как оно уже произошло**. Для отсутствующего ключа, напротив, обработчик вообще не вызывается.

**Первое самостоятельное применение:** ученик получает тот же `events`, `mark`, `actions`, но сам дописывает выбор по переменной `command` и защиту перед вызовом, используя проверку наличия ключа и получение значения по ключу. Для двух отдельных запусков с новым пустым `events` проверить `command = "save"` (одна запись и никаких сообщений о неизвестной команде) и `command = "missing"` (ноль записей, одна ветка неизвестного ключа, без ошибки поиска ключа). Затем специально проверить неверную идею «отсутствие команды определяется по результату `mark`» и объяснить, почему при известном ключе появился ложный ответ. Если трудно, вернуться к сравнению «ключ есть? → ссылка на функцию → вызов → результат» из **01/04**, затем повторить на втором имени события.

Теперь спроецируем различие на один проход `run`: после `.strip().lower()` отдельно распознаётся `exit`; для других строк определяется наличие обработчика в таблице; при отсутствии идём в старую ветку сообщения, при наличии вызываем **одну** функцию с тем же `tasks`. Таблица создаётся один раз до цикла и не выполняет обработчиков. Проверка значения `return` **после** вызова для выбора ветки не нужна. Путаница с порядком даёт наблюдаемые дефекты: поиск до нормализации ломает `  LIST  `, вызов без проверки ломает неизвестный ключ, повторный вызов удваивает эффект `add`, а неверная пара «ключ → обработчик» запускает чужую команду, даже когда оба обработчика принимают `tasks`.

**Переход к проекту:** для последовательности `  LIST  `, `nonsense`, `exit` ученик самостоятельно обозначает в короткой трассировке «нормализованная строка → найденный обработчик или его отсутствие → число вызовов → состояние списка». Только первая команда обращается к рабочему обработчику, две другие не меняют список; `exit` дополнительно заканчивает цикл. Затем повторяет трассировку для `  StAtS  ` и сравнивает, **какое действие** выполнится, а не только факт нахождения ключа. Если `list` ведёт в статистику, вернуться к смыслу пары из **03**, если неизвестная команда или выход вызывают функцию — к разделу **04**.

## 06. Что мы будем делать в практике

**Формат:** обязательное изменение проекта в существующем `main.py`, а перед ним короткий эксперимент с функциями в интерпретаторе. **Вход:** локальная версия Planner *после* планируемых B 21.1 и 22.1 — шесть готовых обработчиков с сигнатурой `handle_*(tasks)`, работающий `run(tasks=None)` и проверяемое поведение `add/list/find/done/search/stats/exit`. Эти условия должны быть подтверждены запуском ученического проекта перед уроком; снимок из COURSE сам их не доказывает. Редактор и командная строка уже знакомы по первой главе; новых пакетов не требуется.

Практическая цель — ученик **сам** спроектирует соответствия между строками и существующими функциями, создаст таблицу внутри `run` и изменит только логику выбора обработчика. Не выдавать готовый словарь/полную новую реализацию `run` как исходный код: тогда самостоятельное действие B исчезнет.

1. **Отличим сохранённое действие от результата вызова → понятен момент выполнения.**
   - **Вход и объект:** маленькая независимая функция с наблюдаемым `print` и словарь с одним ключом (предоставляются исходные данные и сама функция; ученик задаёт значения словаря).
   - **Опора:** разделы **01** (имя и вызов) и **03** (словарь функций), опыт с `notify`.
   - **Самостоятельно:** записать по одному варианту сохранения функции и результата её вызова, предварительно предсказать момент вывода и получаемое значение; затем воспроизвести типичную ошибку преждевременного вызова в безопасном учебном фрагменте.
   - **Локальный результат:** в первом варианте определение таблицы не выводит сообщения, выбранное действие запускается только при обращении; во втором эффект происходит при создании, в ячейке оказывается результат. **Различающий случай:** функция без `return` приводит к `None`, вызов его как функции не работает. Эксперимент никак не меняет `main.py`.
2. **Установим подлинный вход Planner → известен объект изменения и контракт.**
   - **Вход и объект:** собственный `main.py` после предыдущих занятий; сравнить определения шести обработчиков, `run`, форму нормализации команды и возможность передать пустой список.
   - **Опора:** B **21.1** (единые `handle_*(tasks)`), B **22.1** (`run(tasks=None)` и тот же список), раздел **02** о договоре callback; перед выполнением нужны реальные проверки предыдущих работ.
   - **Самостоятельно:** назвать, где происходит ветвление для шести команд, какие функции реально имеются и какой объект передаётся им; зафиксировать прежнее поведение пустых `list/stats` и `exit` как базу регрессии.
   - **Локальный результат:** точно указаны существующие шесть функций с одним `tasks` и место замены выбора; переданный `[]` после штатного `exit` остаётся тем же объектом. **Пограничный случай:** если функция ожидает другое число аргументов или `run` подменяет `[]`, работа над таблицей откладывается до подтверждения/завершения прежней B, её не маскируют новым обработчиком.
3. **Создадим таблицу действий → при создании ничего не запускается.**
   - **Вход и объект:** подготовленный в шаге 2 `run`, шесть строковых рабочих команд и существующие имена `handle_*`.
   - **Опора:** разделы **01–03**, особенно различие функции и вызова и опыт с перестановкой двух подходящих по сигнатуре, но неверно привязанных действий.
   - **Самостоятельно:** внутри `run` до цикла построить **один** словарь для `add/list/find/done/search/stats`, сопоставив каждому ключу реальное имя `handle_*` без скобок; не переписывать обработчики и не добавлять `exit`. После записи не ограничиваться проверкой синтаксиса: записать собственную мини-таблицу «строка → какая именно операция должна произойти», сверить с шестью значениями словаря и найти подмену, если специально переставлены два значения. Это **самостоятельная проверка семантики соответствий**, без готового словаря в исходном задании.
   - **Локальный результат:** все шесть пар имеют нужный смысл; до первого ввода таблица существует, но не читает ввод, не печатает сообщений обработчиков и не меняет список. **Различающие случаи:** скобки в значении вызывают обработчик при создании (возможно, с `TypeError` из-за отсутствия `tasks`); перестановка `list`/`stats` оставит значения вызываемыми, но сделает действия неправильными. Проверка соответствий возможна до замены цикла, по определениям функций и значениям таблицы.
4. **Заменим рабочее ветвление → выбранный обработчик срабатывает один раз.**
   - **Вход и объект:** один словарь из шага 3 и действующий командный цикл в `run`; меню, нормализация `.strip().lower()` и выход уже существуют.
   - **Опора:** разделы **04–05** о проверке ключа, позднем вызове, отдельном `exit` и различии найденной функции и её результата; раздел **02** о договоре `handler(tasks)`.
   - **Самостоятельно:** оставить `exit` отдельным управляющим исходом; для прочих строк проверить наличие ключа через уже знакомый `in`, при неизвестной команде вывести прежнее сообщение и продолжить цикл, при известной получить функцию по ключу и вызвать её **ровно один раз** с исходным `tasks`; удалить только заменённые шесть веток. Ученик сам определяет порядок проверки и вызова, не проверяет успех по `return` обработчика; готовую целую конструкцию в starter не давать.
   - **Локальный результат:** ` ADD ` действует как `add` ровно один раз; неизвестное слово не вызывает `None` и не меняет список; `exit` прекращает цикл без обращения к таблице. **Различающие случаи:** если известный обработчик выполнился, но вернул `None`, сообщение о неизвестной команде **не появляется**; если ключа нет, вызова вообще нет; двойной `add` обнаруживается по двум новым задачам после одной команды. Проверить ветвление до полной регрессии, на одном известном действии и одном неизвестном вводе.
5. **Проверим регрессию и передачу состояния → B занятия наблюдаема в проекте.**
   - **Вход и объект:** та же версия Planner после шага 4; доступен полный исходный сценарий и отдельный переданный пустой список.
   - **Опора:** шаги **2–4**, предыдущие B **21.1/22.1**, трассировка выбора, состояния и `None` из **05**.
   - **Самостоятельно:** составить собственный протокол «ввод → ожидаемый обработчик → что видно → число задач/изменённые поля» и прогнать два коротких сценария. **Пустой:** на свежем списке `list`, `stats`, неизвестная команда и `exit`; ожидается отсутствие созданных задач и отсутствие действия на неверный ключ. **Заполненный:** один корректный `add` → ровно одна новая задача; второй `add` → ровно две; `  LiSt  `, `find` (по поддерживаемым id/названию), `search`, `stats` читают эти две задачи без добавления новых; `done` по существующему id меняет состояние одной задачи, повторное `done` не создаёт новой; неизвестная команда до `exit` ничего не меняет. Отдельно проверить ошибочный id/числовой ввод согласно уже существующему договору. При вызове `run(passed_empty)` с внешним `[]` без добавления задач после `exit` должен возвращаться тот же пустой объект; в заполненном сценарии сверить сохранность полей `id/title/priority/is_done` на реальных задачах. Сравнить наблюдаемое поведение с записью до переработки, не изобретая новых текстов сообщений.
   - **Локальный результат:** после каждого `add` количество увеличивается **ровно на один**; `list` показывает задачи, а `stats` сводные показатели — перепутанные обработчики выявляются даже при совместимых сигнатурах; операции чтения и неизвестная строка не меняют число/поля, `done` действует на нужный id, выход возвращает тот же внешний список. **Различающие ошибки:** `add` добавляет две задачи за один ввод → двойной вызов; известная команда сделала действие и напечатала «неизвестно» → проверили `return` вместо найденного обработчика; `list` показывает сводку → перепутаны ключи; внешний `[]` заменился → не подтверждена B **22.1**, исправление вне выбора команд. Локальная обратная связь предлагает перепроверить соответствующий этап, не переделывать предметные обработчики в уроке 24.

Эта последовательность сначала разделяет функцию, её вызов и результат **вне проекта**, затем заставляет ученика проверить **смысл** шести пар и самостоятельно построить связку «команда → однократный вызов → наблюдаемый эффект» в Planner. Шаг 3 сам доказывает соответствия до перестройки цикла, шаг 4 — корректность выбора без оценки `return`, шаг 5 — сохранение поведения на независимых сценариях. При слишком раннем эффекте вернуться к **01/03**; при перепутанной паре — к примеру с перестановкой в **03**; при ложном «неизвестно» после действия — к **05**; при утрате пустого переданного списка — проверить выполненную B **22.1**, не маскируя дефект новой таблицей. Пункт 5 завершает проектный результат и готовит **планируемую** опору для 24.1; факт её освоения проверяют перед выдачей следующего занятия. Точный starter, интерактивная выдача, подсказки и тесты разрабатываются позднее; наличие `manual.py` не доказывает выполнения учеником.
