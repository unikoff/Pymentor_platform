## 01. Имя параметра относится к вызову функции

Параметр становится локальным именем при вызове функции. Имя доступно в теле этого вызова и связывается с переданным аргументом. Другая функция или код после вызова не получает доступ к этой локальной переменной по одному и тому же текстовому имени.

Рассмотрим строку, которую функция получает как параметр:

~~~python
def change_direction(direction):
    direction = "восток"
    print(direction)

direction = "запад"
change_direction(direction)
print(direction)
~~~

Перед вызовом внешнее имя `direction` связано со строкой «запад». При вызове параметр получает это значение. Присваивание внутри функции связывает локальное имя `direction` со строкой «восток», поэтому внутри печатается «восток». После завершения вызова внешнее имя по-прежнему связано со строкой «запад». Вторая строка `print` выводит именно его.

Это не означает, что функция не может прочитать внешнее имя. Например, при `status = "готово"` функция `def show_status(): print(status)` прочитает внешнее `status`, если внутри функции это имя не связано локально. Чтение доступного имени и его переназначение — разные действия. Параметр также не обязан называться так же, как переменная снаружи: Python связывает аргумент с параметром по позиции или имени параметра. Не стоит проверять это по одному совпадению написания имён.

Когда вызов завершается, локальные имена этого вызова уже нельзя использовать из внешнего кода. Но из этого не следует, что исчезает каждый объект, с которым они были связаны. Если функция вернула объект и мы связали его с внешним именем, результат остаётся доступным через эту новую связь. Поэтому мы различаем имя с ограниченной областью и сам объект.

Сравним с гардеробом, где на каждом номерке написано имя владельца. Имя параметра похоже на номерок, который используют внутри одного вызова; значение, к которому оно привязано, похоже на сданную вещь. Если выдать другому вызову такой же по тексту номерок, это не сделает его локальные имена теми же самыми. Аналогия помогает различить имя и значение, но Python не создаёт буквальные бирки: это модель для рассуждения, а не описание внутренней памяти интерпретатора.

**Первая самостоятельная остановка:** до запуска предположим две строки вывода и укажем, какое имя связывает строка `tag = ...` внутри функции. Поменяется ли прогноз, если внешний аргумент будет называться `entrance`, а параметр останется `tag`? Это проверка механизма, а не названий.

~~~python
def rename_tag(tag):
    tag = "южный вход"
    print(tag)

tag = "северный вход"
rename_tag(tag)
print(tag)
~~~

Проверка прогноза: внутри печатается `"южный вход"`, снаружи `"северный вход"`. Если переименовать внешнюю переменную, результат останется тем же: присваивание `tag` происходит в локальной области функции. Если нам нужен новый результат снаружи, функция должна вернуть его, а вызывающий код должен связать результат с подходящим именем:

~~~python
def renamed_tag(tag):
    return "южный вход"

tag = "северный вход"
tag = renamed_tag(tag)
print(tag)
~~~

Теперь внешнее имя переназначается **в месте вызова**. Если выполнить только `renamed_tag(tag)` без `tag =`, функция всё равно вернёт строку, но внешний `tag` останется прежним. Опора для следующих шагов: при присваивании спрашиваем «**в какой области находится имя слева от `=`?**»; при `return` отдельно спрашиваем «**кто присвоит полученный результат?**». `global` позволяет отдельно объявить работу с именем уровня модуля, а `nonlocal` — с именем охватывающей функции; это другие механизмы областей видимости, не средство исправлять передачу списка в Planner.

## 02. Два имени могут быть связаны с одним списком

Аргументом функции является значение. Если этим значением служит список, при вызове параметр связывается с тем же самым списком: автоматическая копия контейнера не создаётся. Поэтому два имени могут вести к одному изменяемому объекту.

~~~python
def add_stop(route, stop):
    route.append(stop)

trip = ["станция"]
add_stop(trip, "музей")
print(trip)
~~~

До вызова имя `trip` связано со списком из одного пункта. Параметр `route` становится ещё одним именем этого списка. Метод `append` меняет сам список, добавляя элемент в его содержимое. Поэтому после завершения вызова через имя `trip` виден уже обновлённый список.

Представим, что две наклейки с именами прикреплены к одной коробке. Добавленный в коробку предмет увидят те, кто пользуется любой из двух наклеек: изменилось содержимое общего объекта. Но если одну наклейку переставить на другую коробку, вторая наклейка останется на прежней. В программе `append` меняет общий список, а присваивание параметру другого списка меняет только связь локального имени.

~~~python
def replace_route(route):
    route = ["парк"]

trip = ["станция"]
replace_route(trip)
print(trip)
~~~

После вызова `trip` всё ещё связано со списком `["станция"]`. Внутри функции имя `route` было связано с новым списком, но это не переназначило внешнее имя. Это и есть различие между мутацией и переназначением: мутация меняет объект, а присваивание меняет то, с чем связано конкретное имя.

Добавление или удаление элемента, очистка и замена позиции меняют список на месте. Присваивание `route = [...]` создаёт новую связь локального имени и само по себе ничего не меняет в ранее переданном списке. Сам факт передачи аргумента не выбирает действие за нас: его задают конкретные строки тела функции.

**Различающий случай в одной функции** нужен, чтобы увидеть момент, когда имена перестали вести к одному объекту. Здесь придётся проследить сразу три действия: изменение общего списка, переназначение параметра и изменение нового списка. До запуска предскажем содержимое `outside` после вызова и объясним, куда попадёт `"после"`:

~~~python
def extend_then_replace(items):
    items.append("до")
    items = ["новый"]
    items.append("после")

outside = ["старт"]
extend_then_replace(outside)
print(outside)
~~~

Проверим прогноз по строкам, удерживая отдельно **имя** и **содержимое списка**:

1. В начале `outside` и параметр `items` связаны с одним списком `["старт"]`.
2. `items.append("до")` изменяет этот общий список. Через `outside` теперь видны `["старт", "до"]`.
3. `items = ["новый"]` связывает **только локальное имя** с другим списком. Имя `outside` остаётся у первого списка.
4. `items.append("после")` меняет второй список, к которому у внешнего кода нет имени. Итоговый вывод через `outside` — `["старт", "до"]`.

Если в прогнозе появилось `"после"`, вернёмся к шагу 3 и нарисуем две стрелки: `outside → прежний список`, `items → новый список`. Такую последовательность нельзя объяснить правилом «любое изменение внутри функции остаётся внутри».

Если нужна новая версия данных без изменения исходного списка, функция создаёт результат и возвращает его; вызывающий код сам решает, связывать ли с ним своё имя. **Опора для практики:** сначала установить, какие имена ведут к одному объекту; затем на каждой строке спросить «изменён объект или переназначено имя?», и только потом делать прогноз вывода.

## 03. Равные значения и тот же объект

Оператор `==` сравнивает значения согласно правилам этих объектов. Для обычных списков сравниваются элементы и их порядок. Оператор `is` проверяет другое: связаны ли два имени с одним и тем же объектом. `is not` означает, что это разные объекты.

~~~python
first = ["карта", "компас"]
second = ["карта", "компас"]
alias = first

print(first == second)
print(first is second)
print(first is alias)
~~~

Первые две переменные связаны с разными списками, но их содержимое одинаково. Поэтому первый результат: `True`, второй: `False`. Имя `alias` присваиванием связали с тем же списком, что и `first`, поэтому последняя проверка даёт `True`.

Два распечатанных экземпляра одной карты могут выглядеть одинаково, но остаются двумя физическими листами. Это помогает помнить разницу: `==` спрашивает о совпадении содержимого, `is` спрашивает, один ли это объект. Ограничение сравнения в том, что экранная печать сама по себе не показывает, были ли объекты общими; для этого проверяем идентичность напрямую, а не угадываем по выводу.

Не используем `is` вместо `==`, когда сравниваем содержимое списка, строки или числа. Для простых списков `first == second` отвечает на вопрос о равных элементах; `first is second` проверяет совместное владение одним контейнером. Совпавшая печать двух списков не доказывает, что это один список. И наоборот, изменение общего списка может быть видно через несколько имён, хотя в коде каждое имя выглядит отдельным.

`is not` — отрицание проверки идентичности: `first is not second` в примере выше даёт `True`, поскольку списки созданы независимо. Это отличается от `first != second`: значения равны, поэтому `first != second` даёт `False`. Перед использованием любого оператора сначала называем вопрос: «одно содержимое?» или «один объект?».

**Промежуточный самостоятельный вопрос:** у двух отдельно записанных одинаковых списков `left` и `right` сначала `left == right` истинно, а `left is right` ложно. Что станет с обоими ответами, если добавить элемент **только** в `right`? Равенство изменится, но идентичность не изменится: объекты не превратятся в один. Если ответ получился неожиданным, проверяем не текст на экране, а способ создания второго списка. Для сравнения общего вложенного объекта позднее понадобится проверять именно элемент `left[0] is right[0]`, а не только внешние списки.

## 04. Поверхностная копия не копирует вложенные объекты

Метод списка `.copy()` возвращает **новый внешний список** с теми же элементами. Если внутри лежат изменяемые объекты, например словари, поверхностная копия сохраняет связи с теми же вложенными словарями. Термин «поверхностная» как раз напоминает, что копируется только внешний уровень контейнера.

~~~python
records = [{"section": "A", "pages": 12}]
mirror = records.copy()

print(records == mirror)
print(records is mirror)
print(records[0] is mirror[0])

mirror[0]["pages"] = 15
print(records[0]["pages"])
~~~

Первое сравнение даёт `True`, второе — `False`, третье — `True`: **внешние** списки различны, а **вложенный** словарь один. Изменение `pages` через `mirror[0]` видно через `records[0]`: напечатается `15`. Проверку различия внешних списков уже даёт `records is mirror`; отдельное действие над содержимым внешнего списка разберём следующим шагом, чтобы не отвлекаться на ещё один метод.

Можно представить папки-каталоги с указателями на карточки. Поверхностная копия создаёт второй каталог, но его записи всё ещё ведут к тем же карточкам. Если изменить поле общей карточки, изменение будет видно из обоих каталогов. Если же добавить или убрать запись самого каталога, изменится только выбранный список. Аналогия показывает границы копирования; реальные элементы Python-списка являются ссылками на объекты, а не бумажными карточками.

**Ещё одно различие:** заменить вложенный словарь в копии по индексу — действие над **новым внешним списком**, а не изменение старого общего словаря. Перед запуском сравним два способа записи: `copy[0]["amount"] = 20` изменяет поле общего объекта, а `copy[0] = {"amount": 20}` заменяет ссылку **в копии списка**. Для второго способа отдельный короткий опыт:

~~~python
original = [{"amount": 5}]
copy = original.copy()
copy[0] = {"amount": 20}
print(original[0]["amount"], copy[0]["amount"])
~~~

Здесь вывод `5 20`: старый вложенный словарь не изменился, а первый элемент списка-копии теперь указывает на другой словарь. Это **не** глубокое копирование и не действие специальной библиотеки. Если вместо словаря внутри списка строка, изменить её содержимое на месте нельзя; присваивание по индексу также заменяет элемент выбранного списка. Опора: на каждом уровне сначала определяем общий ли объект, затем отличаем изменение **его содержимого** от замены **ссылки на него** в отдельном контейнере.

**Короткий перенос до основной практики.** На новом, независимом от будущих заданий сюжете сначала предскажем, что выведет `print`:

~~~python
colors = ["зелёный"]
same_colors = colors
other_colors = colors.copy()
other_colors.append("синий")
print(colors, same_colors is colors, other_colors is not colors)
~~~

Изменение списка `other_colors` не добавляет цвет в `colors`: новый внешний список отделён, хотя изначально был равен исходному. `same_colors is colors` истинно, а `other_colors is not colors` тоже истинно. Здесь нет вложенного изменяемого элемента, поэтому опыт проверяет только первый уровень; отдельный случай со словарями будет в практике. Если прогноз не совпал с выводом, вернёмся к шагам «какой объект создан → какое имя связано → что меняет действие».

## 05. Что мы будем делать в практике

**Формат — интерпретатор, пять самостоятельных опытов.** Для каждого записываем «мой прогноз → фактический вывод → какая строка это объясняет». После каждого опыта заново задаём исходные переменные, чтобы вывод предыдущего запуска не влиял на следующий. Пункты ниже — план заданий для MAIN: преподаватель даёт вход и критерии, но не готовый код решения. Неудачный прогноз — повод найти конкретную смену связи, а не механически повторить пример.

1. **Локальная связь → две разные печати.** Вход: `level = 3`, функция `change_level(level)` должна внутри присвоить параметру `8` и напечатать его; вызывающий код отдельно печатает внешний `level`. Объекты: внешняя связь с целым числом и локальное имя. Опоры: вызовы из `21.2` (**A планируется**, подтвердить фактическую выдачу), раздел 01. Ученик **сам пишет тело функции и вызов**, до запуска фиксирует две ожидаемые печати; затем повторяет с внешним `backup = 11`, оставляя имя параметра `level`. Локальный результат: внутри `8`, снаружи соответственно `3` и `11` — одинаковое или разное написание внешнего и внутреннего имён не меняет области связывания. При ином выводе вернуться к вопросу «где находится имя слева от `=`?».
2. **Мутация против переназначения → состояние после каждого вызова.** Вход: `stops = ["дом"]`; нужны две самостоятельно написанные функции: первая применяет `append("сад")`, вторая присваивает параметру новый список `["парк"]`. Объекты: один переданный список и локальные параметры. Опоры: `append` (**A не проверена**, восстановить перед заданием при необходимости), раздел 02. Ученик **пишет обе функции, прогнозирует и печатает `stops` после вызова каждой**; каждый вариант стартует с новым `stops = ["дом"]`. Различающий дополнительный случай: в функции добавления после `append` переназначить параметр и проверить, что прежнее добавление остаётся видно снаружи. Локальный результат: после первого вызова `["дом", "сад"]`, после второго `["дом"]`; в дополнительном случае видно только добавление до переназначения. Ученик указывает строку изменения объекта и строку смены связи.
3. **Псевдоним и копия → проверка двух разных вопросов.** Вход: список из двух собственных меток, `alias` через присваивание этого списка и `copy` через `.copy()`. Объекты: исходный список, второе имя того же объекта, независимый внешний список. Опоры: `==`, `is`, `is not` в разделе 03, `.copy()` в разделе 04 (**новая теория здесь, не входная A**). Ученик **сам создаёт три связи, прогнозирует и выполняет `source == copy`, `source is alias`, `source is not copy`**, затем добавляет элемент **только в `copy`**, а в отдельном шаге через `alias` — в исходный объект. Локальный результат: сразу после копирования три проверки истинны; после изменения `copy` меняется только копия и равенство становится ложным; после изменения через `alias` видны изменения исходного списка, `copy` прежняя. Требуется объяснить, почему ни одна проверка `is` не изменилась.
4. **Два уровня объекта → разные эффекты в двух ветках.** Вход: `cards = [{"name": "проект", "done": False}]`, `cards_copy = cards.copy()`; обе ветки начинаются с **новых** `cards` и `cards_copy`. Объекты: два внешних списка и их первоначально общий словарь. Опоры: раздел 04; обращение по индексу и изменение поля словаря (**A не проверена**, проверить до начала). Ученик **сам выбирает порядок проверок и пишет код**, до запуска предсказывает `len(cards)`, `len(cards_copy)`, поля `done` и `cards[0] is cards_copy[0]`. В ветке А он добавляет **новый словарь только в копию**, затем меняет `cards_copy[0]["done"]`; в ветке Б на свежем входе **заменяет целиком** `cards_copy[0]` новым словарём с `done=True`. Локальный результат: А — длины `1` и `2`, поле прежнего вложенного словаря стало `True` с обеих сторон, идентичность элемента `True`; Б — длины по `1`, исходное поле `False`, поле копии `True`, идентичность элемента `False`. Ученик объясняет, почему одинаковое видимое значение в копии не означает одинакового эффекта на исходные данные.
5. **Ремонт ошибки → явное получение новой связи снаружи.** Вход: вызывающий код `tasks = ["старая"]`, функция `choose_view(items)` внутри создаёт новый список `["новая"]` присваиванием параметру; после `choose_view(tasks)` вызывающий код печатает `tasks` и ошибочно ожидает `["новая"]`. Объекты: переданный прежний список, новый список функции, внешнее имя `tasks`. Опоры: `return` из `21.1` (**A планируется, проверить выполнение возврата до выдачи**), разделы 01–02 и результат опыта 2. Ученик **сам воспроизводит дефект, исправляет функцию с помощью `return` и сам меняет строку вызова для приёма результата**. Контрольный случай — повторить исправленную функцию **без присваивания результата** на вновь заданном `tasks`. Локальный результат: до исправления `tasks == ["старая"]`; при явном приёме результата `tasks == ["новая"]`; при пропущенном приёме результат не меняет внешний `tasks`. Объяснение называет обе необходимые операции, без нового `add_task` или правок проекта.

Эта последовательность растит самостоятельность: сначала дописываем небольшую функцию, затем строим и сопоставляем свои функции, выбираем операторы проверки, исследуем вложенный уровень **на двух разных исходных состояниях** и наконец исправляем интерфейс чужой функции без готового решения. Пара «действие → локальный результат» позволяет вернуться к месту непонимания: раздел 01 для локальной связи/`return`, 02 для мутации, 03 для идентичности, 04 для двух уровней копии.

**Суммарный критерий B:** по записям **всех пяти** опытов ученик даёт верный прогноз до исполнения и объясняет вывод через конкретное имя и объект. В двух обязательных различающих проверках он отличает `append` от позднего переназначения и **изменение поля вложенного словаря** от **замены словаря в списке-копии**. Если объяснение держится только на распечатанных значениях, попросить дополнительно показать проверки `is` на обоих уровнях. Изменений в репозитории Planner нет.

Следующее проектное занятие 22.1 применит эту механику к `run(tasks=None)`: там мы различим `None` и переданный пустой список и сохраним идентичность входного объекта. Изменять Planner и разбирать изменяемый default в этом занятии не будем.
