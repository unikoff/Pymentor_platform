## 00. Вступление

В предыдущем шаге сервис уже отвечает за чтение, а изменения пока распределены между несколькими путями. Теперь нужно довести переход до единой модели работы и сохранить поведение привычного Planner.

1. **Точка старта:** чтение проходит через PlannerService, но add и done ещё выполняют переходные функции с тем же storage.
2. **Новый вопрос:** как распределить ответственность, чтобы каждая команда проходила через одни и те же объекты и правила?
3. **Результат:** все действия выполняет один сервис, CLI только общается с пользователем, а новое удаление сохраняет прежние данные и команды.

Эти пункты связаны движением от смешанного состояния к законченному продукту. Чтобы оно не выглядело механическим переносом функций по файлам, сначала нужно понять сотрудничество объектов.

**Первый вопрос без кода:** пользователь вводит `done 7`. Кто читает строку, кто проверяет наличие задачи, кто сохраняет результат? Записать три роли своими словами, затем сверить с маршрутом раздела 01. Здесь достаточно уже знакомых функций; понятие нового слоя пока не требуется.

## 01. Схема взаимодействия как модель ООП

- Что и зачем объяснить: продолжить схему из плана 37.1, где CLI обращается к сервису, а сервис читает список через storage. Теперь она охватывает создание зависимостей и полный цикл изменения, чтобы увидеть в ООП сотрудничество объектов и владение ответственностью.
- Механизм и порядок: связать сборку: build_service выбирает или получает один storage и передаёт его в PlannerService; CLI получает готовый сервис. Затем проследить действие: команда CLI → метод сервиса → storage.load() → изменение Task или набора → storage.save() → результат обратно в CLI. Отметить, что сервис хранит ссылку на storage и использует его публичный договор.
- Пример или типичная путаница: JsonStorage и MemoryStorage занимают одну роль и выбираются по одному; передача storage сервису — отношение «использует», а не наследование. CLI не меняет Task напрямую и не обращается к файлу.
- **Независимая наглядность до Planner:** в библиотеке посетитель (ввод/CLI) просит выдать книгу, библиотекарь (сервис) проверяет правило выдачи, каталог (storage) сообщает текущее наличие, книга (Task) имеет своё состояние. Подмена бумажного каталога электронным не меняет обязанности библиотекаря. **Предел аналогии:** в коде `load()` возвращает список объектов и его изменения нужно явно сохранять; библиотекарь в жизни не вызывает `save()` у каталога.
- **Первое действие:** для `list` и `done` нарисовать по одному пути стрелками и обвести `save` только у действительно изменяющего вызова. Локальный критерий: оба маршрута заканчиваются ответом CLI; `list` не пишет; `done` при новой смене состояния пишет один раз. Запланировать визуал последовательности и запрос прогноза (до показа правильных стрелок), а не повтор схематичной подписи.
- Переход к следующему шагу: после схемы сотрудничества объектов разобрать порядок успешного изменения и отказа.

## 02. Путь успешного изменения и путь отказа

- Что и зачем объяснить: показать, почему сервису нужны актуальные данные перед действием и почему сохранение должно следовать только за допустимым изменением.
- Механизм и порядок: получить текущий набор через storage; проверить вход и найти нужную Task, если операция адресная; выполнить предметное изменение; сохранить новый набор; вернуть согласованный результат. Сопоставить с чтением, которое не сохраняет данные, и с отказом, который не должен менять набор или вызывать save.
- Пример или типичная путаница: возврат успешного результата после save; повторное done уже завершённой задачи возвращает Task без лишней записи. Не обещать откат памяти, если сама операция save завершилась ошибкой.
- **Механизм на независимом наборе:** магазин получает корзину товаров, проверяет запрошенный артикул, меняет количество только у найденного товара и записывает новый список. Отдельно разыграть «артикул отсутствует» — список прежний, запись не делается; «количество уже нужное» — возвращается найденная позиция, повторное сохранение излишне. **Предел аналогии:** хранение Planner может вернуть ссылки на изменяемые Task, поэтому ошибка при `save` не обещает автоматического отката объектов в памяти.
- **Первая самостоятельная трассировка:** дать шаги в перепутанном порядке (`return`, `load`, `save`, поиск, изменение) и три состояния (`id=2` найден, `id=99` неизвестен, `id=2` уже done). Ученик расставляет порядок и отмечает вызовы save: **1 / 0 / 0** для нового изменения/неизвестного id/повтора. Затем сравнить с объяснением причины: `return Task` означает результат операции, но сообщение CLI об успешном сохранении выдаётся лишь после завершившегося `save`.
- **Точное правило для будущего кода:** проверка `id` отвергает `bool` как неподходящий тип даже при `True == 1`; существующий положительный id и отсутствующий положительный id дают разные пути (`Task` либо `TaskNotFoundError`). В текущем сервисе использовать установленный договор проверки из `get_task`, а не сочинять новый валидатор для каждой операции.
- Переход к следующему шагу: применить этот порядок сначала к знакомым add и done.

## 03. Перенос add и done в PlannerService

- Что и зачем объяснить: перенести существующую предметную работу, а не создавать второй CRUD. Сервис использует готовую Task, прежние валидаторы и один storage.
- Механизм и порядок: для add опираться на текущий набор при выборе id, создать незавершённую Task с независимыми tags, сохранить результат и вернуть объект. Для done проверить тот же договор id, изменить одну найденную Task её методом и сохранить только реальный переход.
- Пример или типичная путаница: метод сервиса возвращает Task, а не старый булев результат «найдена ли задача». Повторное завершение не меняет пользовательский смысл команды и не требует нового сохранения.
- **Разбор формы до задания (на другом списке):** для списка наклеек `[{"id": 2}, {"id": 5}]` выражение `max(item["id"] for item in stickers) + 1` даёт `6`, а пустой список требует отдельной ветки и даёт `1` (иначе `max()` не получит элементы). Ученик перед просмотром результата предсказывает новый номер при удалении наклейки `5`: максимум оставшегося списка — `2`, следующий номер — `3`. Эта игра с id показывает правило актуального набора, но **не даёт готовый метод** `PlannerService.add_task`.
- **Применяем прежние инварианты:** `title` очищается по краям, `priority` в `1..5`, новая `Task.is_done=False`; `tags=None` означает отдельный пустой список, а переданные теги не должны становиться общим изменяемым списком. Проверка полей остаётся у готовой модели `Task`: сервис не копирует её валидаторы. При невалидном `title`/`priority` не сохранять список и не выдавать Task. Сервис выбирает id по загруженному набору, создаёт Task через модель, добавляет её, делает `save` и возвращает её.
- **Первый самостоятельный прогноз:** «добавить задачу в пустой набор» → `id=1`, `is_done=False`, `save=1`; «добавить после `[2, 5]`» → `id=6`; «повторно завершить уже сделанную Task» → возвращается **та же найденная Task**, `save=0`. Для `mark_done` студент объясняет смысл раннего возврата, затем самостоятельно выбирает место `return` относительно `save`. В отличие от прежней функции, вызвавший код читает `task.is_done`, а не трактует результат как `bool`.
- **Сначала подготовить потребителя:** после изменения контракта `mark_done -> Task` найти в CLI ветвление вида `if mark_task_done(...):` и спроектировать замену по возвращённому объекту; иначе правка сервиса «проходит», а старое сообщение/условие зависит от устаревшего типа.
- Переход к следующему шагу: после переноса прежних изменений в сервис добавить единственную новую пользовательскую операцию занятия.

## 04. Удаление как действие над набором

- Что и зачем объяснить: отделить проверку допустимого id от ситуации, когда корректный id не найден; связать удаление с уже знакомыми списками и прикладной ошибкой.
- Механизм и порядок: найти существующую задачу по id, удалить только её из текущего набора, сохранить оставшиеся задачи и вернуть None. Объяснить, что остальные id сохраняются, а новый id по-прежнему вычисляется по текущему набору.
- Пример или типичная путаница: неизвестный id даёт TaskNotFoundError без изменения и save; удаление не перенумеровывает соседей и не обещает пожизненную уникальность уже освобождённого номера.
- **До написания метода — действие над обычным контейнером:** у списка `colors = ["синий", "красный", "зелёный"]` найти значение "красный" и мысленно выполнить `colors.remove("красный")`; ожидается `["синий", "зелёный"]`. Отличить `remove(значение)` от `pop(индекс)`: `id` задачи **не** является индексом списка. Это отдельный пример синтаксиса удаления, не код задания про Task.
- **Различающий случай:** задачи с id `[2, 5, 9]`, запрос удаления `5` → остаются `[2, 9]`, ровно один `save`, `return None`; запрос `7` → `TaskNotFoundError`, остаются `[2, 5, 9]`, `save=0`; запрос `-1`/`True` → ошибка входа до изменения. Пусть ученик сам отметит результат и объяснит, почему на незнакомый id нельзя безусловно сохранить отфильтрованный список.
- **Опора для будущего кода:** использовать помощник `_get_task(tasks, task_id)`, который проверяет id и ищет объект **в уже загруженном списке `tasks`**. Не вызывать отдельно публичный `get_task(task_id)`: тот может снова выполнить `load()` и вернуть объект из другого списка. После успешного поиска удалить именно найденный объект из `tasks`; порядок `load → _get_task → remove → save → return None` сохраняет различие типов отказа и не перенумеровывает id.
- Переход к следующему шагу: когда сервис содержит все действия, CLI можно свести к одному способу их вызова.

## 05. Один путь команды через тонкий CLI

- Что и зачем объяснить: CLI отвечает за ввод, разбор, вызов подходящего метода сервиса, форматирование и сообщения; предметные правила, CRUD и файловое хранение ему не принадлежат.
- Механизм и порядок: для каждой команды сопоставить ввод с методом сервиса и его результатом; сохранить существующее поведение сообщений и ожидаемых ошибок. Удалить переходные функции после переключения всех потребителей, а не раньше.
- Пример или типичная путаница: не оставлять скрытый второй путь через callback, старую функцию или storage, переданный в CLI. ValueError и TaskNotFoundError превращаются в понятное сообщение; StorageError сохраняет прежнюю границу остановки сессии. Не перехватывать неожиданную программную ошибку общим обработчиком. Успех сообщается только после успешного save.
- **Разбираем форму обработчика до практики:** `run(service)` получает готовую зависимость; обработчик читает введённую строку, преобразует id, вызывает `service.mark_done(id)`/`service.delete_task(id)` и показывает итог. `try` охватывает **одну команду**, `except (ValueError, TaskNotFoundError)` печатает понятный отказ и возвращает управление меню; `StorageError` не маскируется как неверный id. У удаления `return None` — нормальный успех, а не признак ненайденной задачи.
- **Первое независимое действие:** для условного терминала заказа билета сопоставить три выхода функции бронирования: успех, неизвестное место, отказ хранилища. Ученик решает, когда интерфейс говорит «готово», когда продолжает меню с пояснением, когда прекращает сессию. Верный критерий: успех **после** записи; ожидаемый пользовательский отказ не ломает меню; сбой записи не порождает ложного успеха.
- **Предметная проверка границы:** показать две стрелочные схемы до/после. До — `CLI → временные add/done → storage`, параллельно `CLI → service` для чтения. После — **каждая** команда `CLI → service → storage`. Попросить найти в обработчиках упоминания `storage.load/save`, `callback`, `mark_task_done`; после перехода не должно остаться самостоятельных CRUD-путей. Чистое форматирование и чтение ввода допустимы.
- Переход к следующему шагу: рассмотреть, кто создаёт объекты для этого единого пути и откуда сервис получает storage.

## 06. Сборка и явная зависимость

- Что и зачем объяснить: закрепить композицию в точке сборки и показать, почему переданная реализация storage остаётся заменяемой.
- Механизм и порядок: build_service при отсутствии аргумента создаёт JsonStorage для принятого пути; при явном аргументе использует именно его и собирает PlannerService. CLI получает готовый сервис. Различить создание объекта и начало пользовательского сценария.
- Пример или типичная путаница: проверять отсутствие зависимости через None, а не через истинность объекта: пустой MemoryStorage является намеренно переданным storage. Импорт и сборка не должны запускать input, load или запись.
- **Независимый пример формы:** сначала прочитать корректный код с отступами:

  ```python
  def choose_bag(bag=None):
      if bag is None:
          bag = []
      return bag
  ```

  При передаче `external=[]` возвращается именно `external`, при отсутствии аргумента создаётся новый. Сравнить с вариантом `if not bag: bag = []`, который теряет переданный пустой список. В настоящей сборке эта логика выбирает **объект storage**, не набор Task; `MemoryStorage()` обычно истинен, даже когда хранит пустые данные, но любой допустимый ложный объект всё равно должен сохраняться.
- **Первая проверка прогноза:** `build_service(memory)` использует идентичный `memory` внутри сервиса, `build_service()` создаёт `JsonStorage(DATA_PATH)`, где `DATA_PATH` соответствует одному `data/tasks.json`. Ни в одном варианте сам вызов сборки не читает файл и не спрашивает `input`. `main()` создаёт сервис и вызывает `run(service)` только при условии `if __name__ == "__main__"`: импорт не запускает меню. Ученик перед практикой показывает, какая ветка выполняется в трёх случаях: явная память, аргумент отсутствует, импорт модуля.
- Переход к следующему шагу: проверить, что переход на новую схему объектов сохранил возможности и границы прежнего Planner.

## 07. Регрессия прежних возможностей

- Что и зачем объяснить: после архитектурного переноса проверить наблюдаемое поведение всего накопленного продукта, а не только новые методы сервиса.
- Механизм и порядок: пройти знакомые команды вместе с delete на памяти и JSON; отдельно проверить восстановление при новом запуске, отказы по данным и id, повтор done и отсутствие лишнего сохранения. Тестовый фреймворк ещё не вводить: сначала в 37.3 появится `.venv`, затем в 38 — pytest.
- Пример или типичная путаница: успешная команда подтверждается и результатом для пользователя, и правильным состоянием; ошибка storage не должна выглядеть как ложный успех. Прежний рабочий файл не используется для разрушительных проверок.
- **Первое самостоятельное применение до практики:** на карточке ручной проверки ученик перечисляет ожидаемый результат `add → list → done → delete → новый запуск`: появление новой задачи, смена `is_done`, отсутствие удалённой задачи и восстановление остальных. Добавляет две отрицательные ветки: неизвестный `id` и повтор `done`, где не должен вызываться `save`.
- **Как проверить запись без pytest:** на время ручного запуска в учебной копии поставить временный диагностический вывод у единственной точки вызова `save` или проследить вызов по коду; после наблюдения убрать диагностику. Одинаковый JSON после отказа сам по себе не доказывает отсутствие лишней записи. Не проверять файловый сбой на рабочем `data/tasks.json`.
- Переход к следующему шагу: готовый продукт используется в 37.3 для настройки окружения, а затем станет основой тестов занятия 38.

## 08. Что мы будем делать в практике

**Формат и исходная опора:** проектная работа в том же Planner после планируемой B 37.1; `app/services.py` уже содержит методы чтения, `app/cli.py` использует сервис для чтения и временные функции для add/done, оба пути используют один storage. До работы сверяем эти файлы с checkout ученика. Ученик сам пишет перенос и новый метод по подготовленной логике, не получает вставляемый готовый `PlannerService`.

**Как увидеть промежуточный результат до переключения CLI:** для шагов 1–3 запускать короткий самостоятельный вызов метода существующего сервиса с отдельным `MemoryStorage` в знакомом интерпретаторе Python; сравнивать возвращённый объект и `storage.load()`. Прогноз записывается **до** запуска. Подсчёт вызовов `save` — по трассировке из раздела 07; консольное меню для такой проверки пока не нужно.

Общий результат — законченный пользовательский путь, в котором все действия проходят через один PlannerService, а привычный CLI продолжает работать с тем же JSON.

1. **Перенос `add_task` (опора 02–03).** Вход: существующий `PlannerService(storage)`, рабочая переходная add-функция и готовый класс `Task`. Объект: `app/services.py`. Ученик самостоятельно переносит проверяемое поведение `title/priority` через готовую валидацию модели `Task`, вычисление следующего id по актуальному `load()`, создание Task с независимыми tags, добавление/`save` и возврат Task; не создаёт вторую модель и не заменяет весь storage. **Сразу наблюдаем:** на пустом MemoryStorage новая задача имеет `id=1`, `is_done=False`; при текущих `[2,5]` следующая имеет `id=6`; некорректный `priority=0`/пустой после очистки title не меняет набор и не вызывает `save`. При затруднении вернуться к разбору инвариантов в 03, но место сохранения и возврата выбрать самому.
2. **Перенос `mark_done` и обновление потребителя (опора 02–03, 05).** Вход: существующий поиск по id и переходный done с результатом `bool`. Объекты: `app/services.py`, затем использующий результат обработчик в `app/cli.py`. Ученик сам пишет метод, возвращающий найденную Task; записывает состояние только при `False → True` и изменяет обработчик, чтобы тот не опирался на старый `bool`. **Сразу наблюдаем:** `id=2` найден → `is_done=True`, один `save`, возвращённая Task; второй вызов с `2` возвращает Task, не пишет; отсутствующий положительный id и `True` отклоняются до изменения. Сообщение CLI должно отражать смысл события и не объявлять лишнее сохранение; подсказка — правило раннего возврата из 02.
3. **Самостоятельное добавление `delete_task` (опора 02, 04).** Вход: актуальный набор задач `[2,5,9]`, общий договор поиска/id и знакомая операция `remove` над списком. Объект: существующий сервис. Ученик выбирает порядок поиска и удаления **одного объекта**, сохраняет оставшийся набор и возвращает `None`; не использует `task_id` как индекс и не пересчитывает номера. **Сразу наблюдаем:** запрос `5` оставляет `[2,9]`, делает один `save`; запрос `7` приводит к `TaskNotFoundError` и нулю записей; `-1` или `True` отвергаются проверкой формы id. Различие отсутствия и некорректного id объясняется до создания CLI-команды.
4. **Переключение *всех* команд на `run(service)` (опора 01, 05).** Вход: текущие обработчики `add/list/get/search/done/stats`, новая операция delete и их существующие сообщения. Объект: `app/cli.py`. Ученик составляет краткую таблицу «команда → метод сервиса → возвращаемое значение/сообщение», затем самостоятельно подключает каждую команду, добавляет чтение id для delete и узкую обработку `ValueError`/`TaskNotFoundError`. **Сразу наблюдаем:** после удачного `add`/`done`/`delete` вывод появляется после завершённого сервиса; неизвестный id даёт сообщение и следующее меню, неизвестная команда по-прежнему понятна, `StorageError` не становится ложным успехом. Только когда **все** команды переключены, удаляются переходные CRUD-функции, callback и второй аргумент storage; по коду нет ветки `CLI → storage.load/save`.
5. **Сборка зависимостей и вход (опора 01, 06).** Вход: готовые `PlannerService`, `MemoryStorage`, `JsonStorage`, существующий `app/main.py`; объект: `build_service(storage=None)` и защищённый вход `main`. Ученик сам записывает ветку `is None` и передаёт один выбранный storage в сервис. **Сразу наблюдаем:** переданный пустой MemoryStorage остаётся тем **же объектом**; без аргумента выбирается JsonStorage с одним рабочим `data/tasks.json`; импорт `app.main` не запускает меню или IO. Вспомнить независимый пример с пустым списком из 06, но выбрать путь и место вызова `run` самостоятельно.
6. **Регрессия и небольшой перенос (опора 02, 07).** Вход: готовый Planner, учебные данные на MemoryStorage и **отдельная копия** JSON/выделенный путь, не рабочий файл. Ученик вручную проходит `add → list → get → search → done → stats → delete`, сверяет `title/priority/is_done/tags/id`, непустой поиск и пустой запрос, счётчики `all/open/done`; после повторного открытия JsonStorage видит сохранённый снимок. Отдельно проверяет повтор done, неверный priority/id, неизвестную команду и неизвестный id. **Сразу наблюдаем:** обе реализации дают один предметный результат; чтение/отказ/повтор не вызывают save, новая запись вызывает один, данные после JSON-перезапуска прежние; файловый отказ не показывает сообщение «сохранено». **Перенос на изменённом случае:** после удаления максимального id `[2,5] → [2]` ученик **предсказывает**, какой номер получит следующая задача, и объясняет правило `max+1` по текущему набору (`3`), не добавляя новые функции. Фреймворк тестов здесь не нужен.

**Сводная приёмка B для практики:** после шага 3 все предметные операции есть у сервиса; после шага 4 CLI не владеет ими и не пишет данные; после шага 5 сборка воспроизводимо выбирает одну зависимость; после шага 6 прежнее поведение и новый delete подтверждены нормальными, повторными и ошибочными сценариями с обоими storage. Для каждого шага локальная проверка доступна сразу после записи ученика, не требует следующего задания. Краткие вопросы из разделов 01–07 проверяют понятие, затем код ученик пишет самостоятельно; весь рабочий сценарий он может объяснить от ввода до результата.

Разобранная схема сотрудничества объектов объясняет, куда относится каждый вызов; порядок `load → проверка → изменение → save` связывает эту схему с поведением сервиса. В 37.3 мы используем работающую программу для настройки среды, а в 38 переходим от этих ручных наблюдений к pytest.
