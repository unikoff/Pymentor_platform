## Точка B: результат занятия

- **Объяснить:** почему тест одной CLI-команды проверяет одновременно вывод и состояние; как callback делает ввод/вывод управляемым; как композиционная обёртка показывает `load/save`, не становясь хранилищем приложения; почему пользовательский отказ, `StorageError` и ошибка программы требуют разных ожиданий; почему сборка зависимости не должна запускать программу.
- **Самостоятельно сделать:** написать/дополнить тесты команд `add/list/find/search/done/delete/stats/exit` и неизвестной команды с управляемым вводом, выводом и новым сервисом; проверить ошибки данных, отсутствующий id, повтор `done`, вызовы `save`, отдельный отказ `load/save`, импорт и `build_service`.
- **Результат в проекте:** в существующем тестовом наборе появились CLI-регрессии и проверка безопасной сборки. Сами команды, сервисные правила, JSON-формат и рабочие данные не меняются без найденного воспроизводимого дефекта.
- **Наблюдаемое доказательство:** `pytest` проходит на независимых экземплярах; для каждой проверенной команды сопоставлены текст, состояние, сигнал продолжения, а где нужно — события `load/save`. Тест с намеренно неверным ожиданием должен падать; зелёный тест, который ничего существенного не проверяет, не доказывает B.

## Границы и передача дальше

- **В работе:** только учебные тесты к существующему проекту Planner; память или файл под `tmp_path`, никакого чтения/удаления `data/tasks.json`. Тесты не переписывают обработчики ради удобства, не отключают ветви ошибок, не держат второй список задач как источник истины. Новый `ObservedStorage` — инструмент проверки, а не третий production storage.

## 00. Вступление

Когда мы нажимаем «добавить задачу», видим сообщение, но оно ещё не доказывает, что задача сохранена. Уже знакомые тесты модели и сервиса могут быть зелёными, пока ошибка живёт в том, как CLI соединяет готовые части.

1. **Точка старта:** при выполнении запланированной B 39.1 одна команда уже вызывается отдельно, а функции ввода и вывода можно передать снаружи.
2. **Новый вопрос:** как проверить, что фраза для человека совпадает с задачами в storage и что ошибка не вызывает лишний `save` или ложное сообщение об успехе?
3. **Результат:** ученик пишет регрессионные тесты, которые воспроизводят команду без терминала, различают успешный и ошибочный путь и показывают, что сборка приложения безопасна.

Маршрут начинается с одного действия и трёх наблюдений (сообщение, данные, сохранение), затем учит управлять этим действием, следить за storage и сравнивать нормальный и ошибочный пути. В MAIN три связанных пункта оформляются первой смысловой группой `LinkedNotes variant="connected"`; после неё нужен вывод об ограничении проверки только текста.

## 01. Что проверяет регрессия одной команды

- **Что и зачем:** `execute_command` получает **готовую строку команды**, передаёт работу обработчику и сообщает `True` («меню можно продолжить») или `False` («закончить»). `run` запускает цикл, поэтому прямой вызов `execute_command` удобен для одного воспроизводимого случая. Это **интеграционная проверка связей** на границе нескольких объектов, но ещё не финальный сквозной запуск с файлом.
- **Механизм:** разделить проверку на три вопроса: **что увидел человек** (элементы собранного вывода), **что вернула функция команды** (продолжение сессии), **что стало с задачами** (поля `id/title/priority/is_done` и количество через реальный сервис/storage). `True` **не** означает успешное изменение: неизвестная команда тоже возвращает `True`. Для `exit` ожидается `False` без обращения к сервису.
- **Независимая наглядная опора:** кассир говорит «покупка оформлена», но чек и остаток товара показывают разные факты. Сообщение — наблюдение интерфейса, список после операции — состояние; аналогия не заменяет точные проверки `assert`. Показать схему «текст команды → обработчик → сервис → storage → сообщение» с подписью, где рождается каждое наблюдение.
- **Первое самостоятельное действие:** на маленьком примере «команда показала успех, но счётчик не увеличился» ученик выбирает два обязательных ожидания (`сообщение` и `счётчик`), предсказывает, какое из них найдёт ошибку, затем сравнивает результаты двух вариантов. Правильный вывод: один `assert` для текста пропустил бы дефект состояния.
- **Опора для возврата:** Arrange (подготовить данные) → Act (вызвать одну команду) → Assert (проверить независимые эффекты). **Переход:** чтобы такой тест не попросил настоящего ввода, нужно управлять `read` и `write`.

## 02. Управляемый ввод и собранный вывод

- **Что объяснить с нуля:** callback — обычная функция, **переданная в параметр** другой функции; получатель вызывает её в нужный момент. `read(prompt)` получает текст вопроса и **возвращает строку ответа**, `write(message)` получает сообщение и **записывает его для наблюдения**. `read=input` и `write=print` — значения по умолчанию для обычного запуска; тест подставляет другие функции и не изменяет глобальные `input/print`.
- **Независимый пример:** мини-опрос о любимом цвете, не про задачи Planner. Список ответов `["синий", "зелёный"]` играет очередь: каждый вызов простого `read` берёт очередную строку через `pending.pop(0)` (`pop(0)` удаляет первый элемент списка и возвращает его). Список `messages = []` собирает вывод через `messages.append`, то есть `write=messages.append` добавляет одно переданное сообщение. Разобрать аргумент `prompt` (он может не использоваться, но функция должна его **принять**), `return` и порядок извлечения; если ответы кончились раньше, это **ошибка сценария теста**, а не доказательство ошибки Planner. Готовый `read` не использовать в качестве эталона всех проектных тестов.
- **Различающий случай:** при ответах `["не число", "2"]` читающий helper вправе сообщить о неверном формате и **повторить запрос в рамках одной команды**; один вызов `execute_command` способен вызвать `read` больше одного раза. Сравнить с `["2"]`: одинаковое конечное предметное действие, разная последовательность сообщений; нельзя считать первую ошибочную строку завершённой командой.
- **Первое самостоятельное действие:** ученик сам пишет маленький ответчик для опроса из списка и writer, предсказывает количество запросов и накопленные сообщения, запускает пример и сравнивает вывод. Вариант с недостатком ответов должен выявить неверно подготовленный тест; затем ученик добавляет недостающий ответ, **не правя опрос**.
- **Опора для возврата:** «`read` принимает приглашение и отдаёт строку; `write` принимает сообщение и запоминает его; callback не вводит новые предметные данные». **Переход:** ввод и сообщения теперь видны, но вызов сохранения пока невидим.

## 03. Наблюдение за storage через композицию

- **Что объяснить:** `PlannerService` **использует** переданный storage, который умеет `load()` (получить задачи) и `save(tasks)` (сохранить новый набор). Композиция — один объект **содержит и использует** другой. Тестовый `ObservedStorage` содержит `inner: MemoryStorage`; он фиксирует «вызван `load`»/«вызван `save`», а само чтение или запись **передаёт внутреннему объекту**. Счётчик/журнал событий — у обёртки; задачи — у `inner`. Класс не наследуется от `MemoryStorage` и не копирует алгоритмы сервиса.
- **Независимый пример и граница аналогии:** счётчик посетителей у двери отмечает входы и выходы, но не хранит содержимое склада; так и обёртка наблюдает операции, а `MemoryStorage` отвечает за данные. Отметка «`save` вызывался» означает **попытку** сохранения, не гарантию успешной записи; результат выясняется отдельно.
- **Порядок объяснения:** показать, как один вызов идёт `CLI → PlannerService → ObservedStorage.load/save → MemoryStorage`; затем как ответ возвращается и CLI пишет сообщение. Объяснить, зачем тест использует **свежие** `inner`, обёртку и service на каждый независимый случай. Важно: `MemoryStorage.load()` создаёт новый **список**, но не независимые копии каждой `Task`; это не транзакционная защита от изменения объекта в памяти.
- **Первое самостоятельное действие:** в отдельном примере с «коробкой» и обёрткой ученик добавляет регистрацию двух видов обращений, заранее предсказывает журнал после одного чтения и одной записи, проверяет, что реальные данные внутри коробки совпадают с ожиданием. Затем самостоятельно объясняет, почему проверка журнала и проверка данных требуют разных `assert`.
- **Опора для возврата:** «обёртка фиксирует событие → делегирует работу → возвращает реальный результат; журнал не равен состоянию». **Переход:** теперь можно сформулировать, *когда* допустим вызов `save`.

## 04. Какие команды вправе сохранять

- **Что объяснить:** `save` — побочный эффект изменения. Запросы `list/find/search/stats` **читают** существующее, поэтому не вызывают `save`. Успешные `add`, первое `done` для открытой задачи и `delete` для существующего id изменяют набор/поле и сохраняют. Повторное `done` для уже выполненной задачи не требует `save`, даже если вывод остаётся дружелюбным. Неизвестная команда и `exit` не касаются storage.
- **Покажем сравнение:** небольшая таблица до/после для одного списка из двух задач: чтение оставляет список и число `save` неизменными; завершение открытой задачи меняет `is_done` и даёт один `save`; второй `done` сохраняет `is_done=True` и не добавляет записи события. `id` остальных задач не перенумеровываются после `delete`. Называть число `load` только там, где реальный код фиксирует его как договор: добавленный тестовым осмотром `inner.load` сам увеличит счётчик, если осматривать через обёртку.
- **Типичная ошибка:** проверка «после add есть две задачи» без журнала `save` пропустит забытый вызов сохранения, а проверка только `save` пропустит неверные поля. У `MemoryStorage` новый список может разделять ссылки на `Task` со старым; нельзя автоматически обещать откат при `StorageError` после изменения объекта.
- **Первое самостоятельное действие:** по схеме двух задач ученик **сам** заполняет ожидаемую колонку `save: 0 / 1` для `list`, `add`, первого и повторного `done`, объясняет причины, затем сравнивает прогноз с журналом наблюдательной обёртки на небольшом подготовленном объекте. После несовпадения возвращается к правилу «операция только читает или действительно меняет».
- **Опора для возврата:** проверка регрессии требует **сообщение + состояние + нужное событие сохранения**; нулевой `save` и корректный вывод вместе отличают чтение от мутации. **Переход:** отсутствие сохранения при отказе нужно проверять с учётом того, *на каком шаге* возникла ошибка.

## 05. Ошибки ввода, хранения и программы

- **Сначала разделить причины:** неверная строка числа/приоритета — **ошибка пользователя**: reader повторяет вопрос, пока не получит допустимое значение; неизвестный id — **предметный отказ** без сохранения; `StorageError` при `load/save` — **ошибка хранилища**, при которой нельзя печатать успех; неожиданный `RuntimeError` из неисправного участка — **ошибка программы**, её нельзя незаметно превращать в «неверный ввод».
- **Порядок и границы обработки:** `read_int` повторяет запрос при нечисловой строке; ввод `0` как номера/приоритета вызывает отдельное сообщение о диапазоне. Тест предоставляет **всю последовательность** до принятого значения и проверяет промежуточные сообщения. `TaskNotFoundError` от сервиса означает отсутствие id, а не сбой файла. `StorageError` из `execute_command` не превращается в успешный результат; штатная точка входа `main()` может остановить приложение с ошибкой хранения — это отдельная граница, не обещание о поведении каждого обработчика.
- **Независимое различение:** на примере выдачи книги: неверный номер читателя → попросить ввести заново; книги с таким номером нет → сообщить об отсутствии; каталог недоступен → нельзя подтвердить выдачу; ошибка в вычислении → показать дефект разработчику. Аналогия помогает классифицировать, но не означает, что неудачная запись автоматически откатывает изменение `Task` в памяти.
- **Первое самостоятельное действие:** по трём коротким ситуациям ученик выбирает, какое наблюдение должно быть в тесте: повторный запрос без изменения, сообщение «не найдено» без `save` или исключение `StorageError` без ложного успеха. После разбора получает четвёртый случай с внезапным `RuntimeError` и объясняет, почему `except Exception: write("ошибка ввода")` неверен.
- **Опора для возврата:** «ошибка до мутации → нет `save`; ошибка `load` → изменение не начато; ошибка `save` → попытка зафиксирована, успех не подтверждён; сбой записи **не доказывает откат**». **Переход:** остаётся проверить выбор зависимостей и безопасную загрузку самого приложения.

## 06. Сборка по умолчанию и безопасный импорт

- **Что объяснить:** `build_service(storage=None)` — функция **сборки**, соединяющая `PlannerService` с storage, а не команда для пользователя. Значение `None` означает «зависимость не передали — выбери `JsonStorage`». Переданная пустая `MemoryStorage()` — полноценный объект, и его нельзя заменить из-за пустоты; правильная проверка — `is None`, а не условие истинности. Важно проверить **идентичность** переданного объекта, а не только имя класса.
- **Независимый пример:** функция получает пустую коробку или `None`. Пустая коробка уже передана и должна сохраниться; `None` значит «создай коробку». У коробки может быть метод, который делает её «ложной» в логическом условии; это не повод автоматически заменить переданный объект. Граница аналогии: конкретные методы реального storage могут иметь собственные побочные эффекты, поэтому их отдельно наблюдают.
- **Безопасный импорт:** `import app.main` должен создать имена функций/классов, не запуская `run/main`. Охранное условие `if __name__ == "__main__":` выполняет `main()` только при запуске файла как программы. Сам `build_service()` не должен делать `input`, `load` или `save`; создание `JsonStorage(path)` само по себе не обязано открывать путь.
- **Различающее наблюдение:** построить сервис с переданным `ObservedStorage(MemoryStorage())`, убедиться, что внутри ровно переданный объект, а журнал пуст **ещё до вызова команд**. Для default-сборки подменить **только в тесте** путь `DATA_PATH` на `tmp_path/"tasks.json"` через заранее разъяснённую fixture `monkeypatch` (временно меняет атрибут модуля и возвращает обратно после теста); подложить в этот временный файл неверный JSON **до** сборки, чтобы любая преждевременная загрузка выявилась. Безопасная сборка возвращает сервис с `JsonStorage`, не поднимает исключение и не меняет файл. Рабочий `data/tasks.json` не использовать. Объяснить, что `monkeypatch` — техническая изоляция адреса, не новый обязательный навык курса.
- **Первое самостоятельное действие:** ученик различает два случая `storage=None` и `storage=MemoryStorage()`, предсказывает идентичность вложенного объекта, проверяет результат; затем по маленькой схеме «импорт → определения → явный main» указывает, какая операция должна быть пропущена при импорте, и делает отдельную локальную проверку отсутствия меню/ввода. Проверку реального запуска в двух процессах и чистого clone отложить к 40.1.
- **Опора для возврата:** «`None` означает отсутствие аргумента; сборка выбирает объект; импорт лишь подготавливает определения; пользовательский цикл запускается явно». **Переход:** эти правила используются вместе с CLI-регрессиями в проектной практике.

## 07. Что мы будем делать в практике

**Обязательный формат: проектная работа с существующим Persistent Planner.** На входе ученическая версия после 39.1 с готовой `execute_command` и рабочими сервисом/хранилищами, а также фактически освоенные проверки 38–39; подтвердить это перед выдачей (см. A). Используем свежую `MemoryStorage` для каждого теста; `tmp_path` — лишь для изолированного проверки default-пути. Объект изменений — **только тесты** (создать или дополнить `tests/test_cli.py` по состоянию копии). Допускается дать готовую техническую fixture для временной установки пути; ответы, проверки и собственную обёртку ученик пишет самостоятельно.

1. **Подготовить управляемую команду → проверяемые сообщения.** Вход: `execute_command` из 39.1, отдельные `PlannerService(MemoryStorage())`, список ответов и пустой список сообщений. Опора: разделы 01–02 и введённые ранее `pytest/assert`. **Самостоятельно:** написать `read(prompt)` на списке ответов, передать его и writer, вызвать `add` с корректными данными; проверить `True`, сообщение, одну задачу с нужными `title/priority/id/is_done`. **Локально:** команда не запросила терминал, данные доступны через тот же storage. **Различающий случай:** неверная строка приоритета с последующим правильным числом даёт повторный вопрос и одну, а не две задачи. Если ответы кончились — исправлять подготовку теста.
2. **Покрыть маршруты команд → раздельные эффекты каждой ветки.** Вход: **новый** сервис/хранилище на случай или осознанно подготовленные две задачи; опора: `01`, чтение/вывод `02`, прежние предметные операции 37.1–37.2. **Самостоятельно:** спланировать параметризованные либо отдельные pytest-проверки `list/find/search/stats` на реальных данных и `done/delete` на существующем id; независимо сравнить сообщения, выбранные поля/количество задач и `True`. Для `exit` ожидать `False` без изменения, для неизвестной команды — `True` и сообщение об отказе. **Локально:** чтение не меняет набор, `done` меняет `is_done`, `delete` уменьшает число без перенумерации остальных. **Различение:** `find` неизвестного id и `search` без совпадений дают разные предметные исходы. Не сочинять точные строки сообщений без сверки действующего CLI.
3. **Написать наблюдательную композицию → видеть попытки сохранения.** Вход: реальная `MemoryStorage` и `PlannerService`; опора: `03–04`. **Самостоятельно:** создать небольшой `ObservedStorage` с `inner` и журналом/счётчиком, реализовать `load/save` через делегирование и прогнать отдельно `list`, `add`, первое `done`, повтор `done` и `delete`. **Локально:** читающая команда/повтор `done` не вызывают `save`; каждое успешное изменение вызывает его один раз, а состояние соответствует выводу. **Различение:** «журнал содержит `save`» и «после вызова есть правильная Task» подтверждаются **двумя разными проверками**. Не использовать для подсчёта `load` дополнительное диагностическое чтение через обёртку, которое само меняет журнал.
4. **Проверить отказы до изменения → не сохранять лишнего.** Вход: свежий storage с одной известной `Task`, подготовленные варианты ответов; опора: `02, `04–05` и `pytest.raises` из 38. **Самостоятельно:** проверить ввод текста вместо числа с последующим корректным ответом, значения вне диапазона, неизвестный id для `find/done/delete`, пустой поиск, неизвестную команду и повтор `done` уже завершённой задачи. **Локально:** проверены текст отказа/повтора и неизменность набора там, где мутации не было; `save=0` для чтения, неизвестного id, нераспознанной команды и повторного `done`. **Различение:** если после первого неверного значения пользователь **позже ввёл верное** и `add` состоялся, ожидается **один** `save` — сам факт первоначальной опечатки не делает всю команду отказной.
5. **Разделить поломку load/save и дефект программы → не печатать ложный успех.** Вход: изолированная обёртка, которая **по выбранному тестом этапу** поднимает `StorageError`, без реального пользовательского файла; опора: `03, `05`. **Самостоятельно:** проверить отказ `load` при чтении/изменении и отказ `save` при изменении; ожидать `StorageError` и отсутствие сообщения об успешном сохранении. В отдельном варианте неожиданный `RuntimeError` не должен превращаться в пользовательскую ошибку через общий `except`. **Локально:** при `load` не начинается сохранение, при `save` зарегистрирована попытка и успех не подтверждён. **Граница:** не требовать отката уже изменённого объекта `Task` при ошибке `save`: `MemoryStorage` не даёт такого договора.
6. **Проверить сборку и импорт → никаких запросов и незапрошенных файловых действий.** Вход: `build_service`/`app.main`, пустая память и временный путь; опора: `06`. **Самостоятельно:** доказать, что явно переданный даже пустой storage остаётся тем же объектом и сборка не делает `load/save`; что default выбрал `JsonStorage` без чтения/перезаписи изолированного файла с намеренно неверным JSON; что импорт модуля не запускает меню. Разрешено дать технический пример временной подмены `DATA_PATH` через уже объяснённый `monkeypatch`. **Локально:** журнал событий пуст до команды, временный файл неизменён, вызов `build_service` не запрашивает ввод, нет вывода меню при импорте. **Различение:** `build_service(None)` выбирает default, `build_service(MemoryStorage())` сохраняет переданный объект. Отдельный процесс и воспроизводимость клона — следующий этап передачи.
7. **Подтвердить регрессию и перенос → тест обнаруживает специально внесённое расхождение.** Вход: все новые CLI-тесты и уже существующий набор 38–39; опора: `01–06`. **Самостоятельно:** выполнить адресные тесты, затем ранее существовавшие проверки; на учебном примере изменить **ожидание в копии теста** (например, ожидать `save` после `list`) и убедиться, что тест падает, после чего восстановить верное ожидание. **Локально:** все правильные проверки зелёные, искусственно неверное ожидание красное, пользовательский Planner работает с прежними командами. **Изменённый случай на перенос:** `done` по уже завершённой задаче отдельно подтверждает отсутствие лишнего `save`. Ни один проверочный сценарий не пишет в `data/tasks.json`.

Связь шагов: разделы 01–02 учат получать сообщения без терминала → разделы 03–04 связывают сообщения с состоянием и `save` → `05` различает отказы → `06` проверяет сборку → `07` проверяет способность тестов заметить неверный контракт. При затруднении ученик возвращается к конкретной опоре **до** повторной самостоятельной попытки, а не к готовому набору тестов. В MAIN этот связанный маршрут станет второй группой `LinkedNotes variant="connected"` с пояснением после списка.

**Что остаётся неизменным:** проектный набор команд, старые тесты 38–39, рабочий JSON и привычный терминальный запуск. Результат нужен для 40: теперь можно проверить **целый** пользовательский путь на новом сервисе, не вводя впервые наблюдение команд и сохранений.
