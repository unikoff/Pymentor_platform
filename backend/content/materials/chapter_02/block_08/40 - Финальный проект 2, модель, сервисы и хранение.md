## Точка B: результат занятия
- **Объясняет своими словами:** кто принимает команду, кто меняет `Task`, кто сохраняет JSON; чем отличается видимое сообщение от содержимого файла; что доказывают новый экземпляр сервиса и отдельный процесс.
- **Показывает действиями:** заранее записывает ожидаемые результаты для двух задач, проходит CLI-путь `add → list/get/search → done → delete → stats`, проверяет JSON и загружает его другим экземпляром `PlannerService` с тем же путём.
- **Показывает точные наблюдения:** после удаления задачи №2 остаётся выполненная задача №1; `stats`: всего 1, выполнено 1, открыто 0. Следующий ID по договору `max(существующие ID) + 1` равен 2; удаление задачи не меняет ID оставшейся. Повторное `done`, чтение и ошибки не должны незаметно сохранять данные.

## 00. Вступление
Представим список дел: команда «завершить задачу» показала успех, но после повторного открытия задача снова активна. Каждый класс по отдельности мог работать правильно; ошибка оказалась в связи между командой и сохранением. Сегодня выясняем, проходит ли действие весь путь от ввода до данных на диске.

1. **Точка старта:** `Task`, сервис, хранилища и CLI уже изучены; в своём проекте ученик подтверждает их наличие и проверяет тестовую базу предыдущих занятий.
2. **Новый вопрос:** совпадает ли результат команды с состоянием задачи **и** файла, включая неправильные запросы?
3. **Результат:** проверенный сквозной сценарий на отдельном учебном JSON; точечное исправление с тестом требуется лишь при реальном расхождении.

Сначала **предскажем**, что должно произойти с двумя задачами; затем выполним команды и сравним три наблюдения: ответ CLI, объекты `Task` и JSON-файл. Так практика проверяет уже изученную систему, не превращаясь в разработку второго Planner.

## 01. Что именно принимаем

**Новый термин — сквозная проверка.** Это один реальный путь через несколько уже готовых частей программы: вводим команду, выполняется действие, данные сохраняются, следующий запрос видит результат. Если проверили только функцию `done`, мы знаем о функции; если выполнили команду `done` через CLI и перечитали файл, знаем ещё и о правильном соединении частей. «Принять проект» значит подтвердить заранее сформулированные результаты, а не просто увидеть отсутствие ошибки на экране.

Перед запуском попросить ученика открыть **свой текущий** проект и показать четыре опоры: модель `Task`, действия `PlannerService`, файл, с которым работает `JsonStorage`, и место, где CLI получает `service`. Затем показать тесты для модели, сервиса, файла и CLI. Отдельно объяснить: название или исторический коммит предыдущего урока не подтверждают, что эти тесты уже существуют в актуальной копии. Если компонента нет, это предмет возврата к предыдущей теме.

**Три независимых вопроса на каждое изменение:**

| Что видим | Что это подтверждает | Чего одного этого не доказывает |
| --- | --- | --- |
| Сообщение CLI «готово» | Команда дошла до обработчика и дала ответ | Что объект действительно изменился |
| Список/статус `Task` в сервисе | Текущее состояние в памяти | Что оно записано на диск |
| Содержимое учебного JSON после действия | Что сохранено между загрузками | Что следующий экземпляр сервиса успешно прочитает файл |

**Первая самостоятельная попытка:** до запуска ученик записывает, какие из этих наблюдений нужны, чтобы доказать «задача останется завершённой после повторной загрузки». Ожидаемый ответ: увидеть итог в памяти, в JSON и после создания нового `PlannerService`. Сводить проверку к одному сообщению нельзя. **Переход:** чтобы наблюдать три точки, разберём связи готовых объектов.

## 02. Схема связей: от команды к модели и обратно

**Понятия на знакомом примере списка дел:** `Task` — объект одной задачи с ID, названием и признаком выполнения (**модель**: описание данных и относящихся к ним правил). `PlannerService` — объект, который организует действия над задачами: добавление, поиск, завершение (**сервис**: правила работы с набором моделей). `storage` — объект с методами загрузки и сохранения (**хранилище**). `CLI` — текстовое окно общения с человеком: принимает команду и показывает ответ (**интерфейс**). Один компонент получает готовый другой компонент при создании: это простая **композиция**, то есть использование объекта без наследования его класса.

Показать маршрут **одной уже существующей команды** «завершить задачу №1», не писать реализацию:

```text
человек вводит команду
        ↓
CLI разбирает ввод → PlannerService находит Task №1
                            ↓
                    Task меняет статус
                            ↓
                    storage сохраняет набор
                            ↓
CLI показывает ответ ← результат выполнения
```

В `JsonStorage` данные между запусками лежат в **JSON** — текстовом файле со структурой из списков, словарей, чисел и строк. `to_dict()` превращает объект `Task` в словарь Python; `from_dict()` восстанавливает объект из словаря. При сохранении хранилище превращает словари в JSON, при загрузке — обратно в объекты. Для наглядности сравнить схематическую запись `Task №1: «Позвонить», выполнено` и её JSON-представление; **точные ключи** ученик смотрит в своём `to_dict()`, пример не навязывает новых полей.

`MemoryStorage` держит данные в памяти программы, без JSON-файла. Он полезен для проверки поведения сервиса, но проверка через него не доказывает запись на диск. **Экземпляр** `PlannerService` — один конкретный объект, созданный из класса; другой экземпляр может получить другое состояние памяти. **Процесс** — отдельный запуск программы: два объекта в одном процессе ещё не означают два запуска. Ученик своими словами указывает стрелку, на которой данные стали JSON, и стрелку, где они снова стали `Task`. **Переход:** теперь можно различить проверку отдельной детали и полного маршрута.

## 03. Компоненты и сквозной сценарий

**Проверки различаются вопросом, на который отвечают.** Тест модели спрашивает: «умеет ли `Task` переводить свои данные в словарь?». Тест сервиса: «меняет ли `done` статус нужной задачи?». Проверка `JsonStorage`: «можно ли сохранить и восстановить задачи через файл?». Сквозной сценарий: «получатся ли все эти действия после команды человека?». Набор тестов уменьшает вероятность ошибки, но только реальный путь показывает, что компоненты подключены друг к другу верно.

**Наблюдаемый договор перед запуском:** начальный учебный файл пустой или содержит заранее согласованную пустую структуру, значит первое добавление получает ID 1, второе — ID 2. Ученик заранее записывает для каждого шага тройку «ожидаемый ответ / ожидаемые задачи / ожидаемый JSON» и лишь затем запускает команду. Для операции чтения содержимое файла должно остаться прежним; для успешного изменения — содержать новое состояние; при отказе — соответствовать явно оговорённой границе гарантии.

Мини-разбор без кода: CLI сообщил «задача выполнена», сервис показывает статус «выполнена», но JSON остался со статусом «открыта». Ошибка может быть между изменением объекта и вызовом `save`; переписывать `Task` заранее нельзя. **Проверка понимания:** назвать первое место, где результаты разошлись, и объяснить, почему именно его проверим первым. **Переход:** фиксируем начальные условия на изолированном файле и проходим нормальные команды.

## 04. Положительный путь через CLI

**Подготовка:** создать отдельный путь для учебного JSON, не использовать личный или рабочий файл. Если `JsonStorage` ожидает уже существующий файл, подготовить пустую структуру в его штатном формате; если умеет создавать файл сам, оставить путь свободным. Команды вводить **в том синтаксисе, который уже поддерживает CLI ученика**. До каждого шага сначала проговорить ожидаемый результат.

| Действие через готовый CLI | Ожидаемая картина после действия | Что сразу наблюдать |
| --- | --- | --- |
| Добавить «Позвонить» и «Купить тетрадь» | Две задачи с ID 1 и 2, обе открыты | Сообщения, список `Task`, JSON с двумя записями |
| `list`, `get` для №2, `search` по названию | Оба ID найдены ожидаемым способом; состояние **не изменилось** | Ответы и отсутствие новой записи через `save` |
| Завершить №1 | №1 выполнена, №2 открыта | Статус №1 и JSON, в котором отражено выполнение |
| Удалить №2 | Осталась **№1 со своим прежним ID** | Список и JSON содержат только №1 |
| Запросить `stats` | Всего **1**, выполнено **1**, открыто **0** | Числа CLI согласованы с оставшейся `Task` и файлом |

ID — это **идентификатор**, то есть номер, которым программа различает задачи. Удаление №2 не превращает №1 в №2: номер принадлежит конкретной задаче, а не её позиции на экране. После удаления наибольший существующий ID равен 1, поэтому **по уже изученному правилу** `max(ID) + 1` следующий добавленный объект получит ID 2; это допустимое повторное использование удалённого номера, а не перенумерация. Реальное добавление для проверки следующего ID лучше выполнить в отдельной копии, чтобы сохранить контрольное конечное состояние основного сценария.

**Контроль до продолжения:** ученик без подсказки объясняет, почему правильные числа в `stats` ещё не гарантируют восстановление после повторной загрузки. Ответ: сервис может считать данные из памяти, даже если JSON не обновлён. **Переход:** новый экземпляр сервиса должен прочитать именно сохранённый файл.

## 05. Восстановление на том же пути

**Зачем второй объект:** первый `PlannerService` помнит список задач в памяти. Если проверить только его, можно случайно принять несохранённые данные за сохранённые. Создать **другой** `JsonStorage`, указав **тот же путь к учебному JSON**, и передать его **новому** `PlannerService`. Не передавать новому сервису старый список задач; момент фактической загрузки зависит от уже реализованного интерфейса (`load()` при создании или при первом чтении).

```text
первый PlannerService → первый JsonStorage → учебный.json
                                          ↓ повторная загрузка
второй PlannerService ← второй JsonStorage ← тот же учебный.json
```

**Ожидаемое наблюдение:** через второй сервис видна ровно задача №1, статус «выполнена», статистика 1/1/0. Перед созданием следующей задачи ученик предсказывает ID **2** по существующему правилу `max + 1` и, при необходимости, подтверждает это на отдельной копии файла. Если вместо этого вновь появились две задачи или открытый статус, сначала сравнить путь и содержимое JSON, затем путь загрузки, и только потом менять код.

**Граница вывода:** новый `PlannerService` в текущем запуске — это **новый объект**, но ещё **не новый процесс**. Проверку перезапуска программы в чистой копии с README и Git проведут в 40.1. **Переход:** проверим, что программа умеет правильно отказаться от неверного действия, не скрывая ошибку.

## 06. Отказы и границы гарантий

**Отказной сценарий** — сознательная проверка неверного запроса или недоступного хранилища. Проверять её на **копии** учебного JSON, чтобы каждый случай начинался с известного состояния: одна выполненная задача №1. Для каждого случая заранее записать ожидаемое сообщение и три наблюдения: список в памяти, JSON и число вызовов `save` (последнее видно из уже существующих тестовых средств предыдущих уроков).

| Случай | Что должно стать понятно ученику | Что сверить |
| --- | --- | --- |
| Неверный ввод (например, ID не число) или неизвестная команда | CLI объясняет ошибку, не вызывает опасное действие | Сообщение, прежний JSON, отсутствие `save` |
| Неизвестный ID | Сервис не создаёт задачу взамен отсутствующей | Ответ по контракту, тот же список, отсутствие `save` |
| Повторно завершить уже завершённую №1 | Повторение не создаёт нового изменения | Тот же статус и **нет повторного `save`** |
| Сбой чтения JSON | Ошибка доступа/разбора данных видна как ошибка | Не выдавать её за «пустой список» и не перезаписывать файл |
| Сбой записи JSON | Изменение не объявляется устойчиво сохранённым | Явный отказ и состояние файла; отдельно проверить память |

Особенно проговорить различие **памяти** и **диска**. Если `Task` уже изменили в памяти, а `save` сообщил об ошибке, *нельзя автоматически обещать откат* объекта: это зависит от ранее реализованного договора сервиса. Сбой записи может не оставить корректный новый файл; на копии сравнить именно фактический результат с ожиданием соответствующего метода. Для чтения `get`, `list`, `search`, `stats` новый `save` также не нужен: чтение не является изменением.

**Самостоятельное решение:** дать ученику два наблюдения — «сообщение об ошибке; файл прежний; Task уже изменена» — и спросить, какая гарантия доказана. Доказано лишь отсутствие успешного сохранения, автоматический откат памяти не доказан. **Переход:** если результат отличается от реального договора, нужно найти первую границу расхождения и защитить её тестом.

## 07. Узкая правка и регрессия

**Дефект** — воспроизводимое отличие фактического результата от согласованного ожидаемого поведения. **Регрессионный тест** — автоматическая проверка этого конкретного случая, которая должна не дать ошибке вернуться после исправления. Пример: если `done` показывает успех, а сохранённый JSON не меняется, сначала воспроизводим случай с теми же данными и проверяем границу между сервисом и `storage.save`, а не переписываем все классы.

Маршрут при **реально найденном** дефекте: (1) записать команду, начальный файл, ожидаемое и фактическое; (2) определить первую из трёх точек — вывод, состояние в памяти или файл — где возникло несоответствие; (3) добавить минимальный тест, который воспроизводит ошибку; (4) исправить причину в существующем компоненте; (5) повторить этот сценарий и полный набор `pytest`, убедившись, что остальные правила работают. Эти шаги выполняются при работе над проектом ученика, а не являются поручением написать новую реализацию Planner в учебном тексте.

**Если расхождений нет**, никакую фиктивную ошибку, новый метод или косметическую правку не придумываем. Ученик показывает наблюдения успешных и отказных сценариев, результат восстановления, список выполненных тестов и подтверждение, что изменения кода не понадобились. **Переход к практике:** выполнить те же действия последовательно, с собственными прогнозами на каждом шаге.

## 08. Что мы будем делать в практике

**Формат — основная практика, проект.** Работаем с **готовым** Persistent Planner, а не реализуем новые классы. Вход: CLI, `Task`, `PlannerService`, `JsonStorage` и подготовленные тесты предыдущих тем; все операции — через существующие команды. Рабочие данные не трогаем: берём отдельный учебный JSON и копии для отказов. Итоговый проект должен продемонстрировать B: успешные и отрицательные пути, загрузку вторым сервисом и прохождение полного тестового набора.

Перед любым действием ученик самостоятельно заполняет короткий прогноз: **«команда → ответ CLI → состояние `Task` → содержимое JSON»**. После действия отмечает совпадение или точное место расхождения. Синтаксис команд берётся из действующего CLI, потому что придумывание новых команд не входит в занятие.

1. **Вход — имеющийся проект и тесты; опора §01.** Ученик находит точки входа CLI, используемый `PlannerService` и путь `JsonStorage`, проверяет наличие модельных, сервисных, файловых и CLI-тестов. **Сразу видно:** есть полный набор нужных компонентов либо конкретный пробел предыдущего урока, который надо устранить по его материалу до следующего шага.
2. **Вход — пустой учебный JSON и две новые задачи; опора §§02–04.** Ученик предсказывает номера, вводит через CLI добавление «Позвонить» и «Купить тетрадь», затем сверяет два сообщения, два объекта и две сохранённые записи. **Локальный результат:** №1 и №2 существуют и открыты; данные хранятся в учебном файле.
3. **Вход — эти две задачи; опора §§01, 03–04.** Самостоятельно вызывает `list`, `get` для №2 и `search` по части названия, до вызовов записывает ожидаемые ответы. **Локальный результат:** найденные задачи соответствуют двум объектам; файл и счётчик `save` не изменились от чтения.
4. **Вход — открытые №1 и №2; опора §§02–04.** Ученик завершает №1 и удаляет №2, сверяет сообщения, объекты и JSON после **каждой** операции. **Локальный результат:** остаётся выполненная №1 со своим ID; удалённая №2 отсутствует, перенумерации нет.
5. **Вход — одна выполненная №1; опора §§01, 03–04.** Запрашивает `stats` и сам вычисляет ожидаемые числа до команды. **Локальный результат:** `all=1`, `done=1`, `open=0` (или эквивалентные названия полей в готовом CLI); чтение статистики не сохраняет файл.
6. **Вход — сохранённый JSON после шага 5; опора §05.** Создаёт **новые объекты** `JsonStorage` и `PlannerService` на **том же пути**, читает список, №1 и статистику; прогнозирует следующий ID как `max(1)+1=2` и при необходимости проверяет добавление в отдельной копии. **Локальный результат:** второй сервис восстановил завершённую №1 и её статистику именно из файла, а не из старого списка в памяти.
7. **Вход — отдельная копия файла с выполненной №1; опора §06.** Ученик сам подбирает существующим CLI неверный формат ID, неизвестный ID, неизвестную команду и повторное `done №1`. Для каждого случая фиксирует ответ, память, JSON и вызовы `save`. **Локальный результат:** ошибка видима, файл не повреждён, чтение и повторное завершение не дают лишнего сохранения.
8. **Вход — изолированные копии и подготовленные средства тестирования отказов; опора §06.** Воспроизводит отказ чтения и отдельно отказ записи через имеющиеся тестовые средства/подмену storage, сверяет фактическое поведение с ранее согласованным договором. **Локальный результат:** отказ не маскируется как успех; для отказа записи отдельно зафиксировано состояние файла и памяти без недоказанного обещания отката.
9. **Вход — результаты всех наблюдений и текущая тестовая база; опора §§03, 07.** Запускает **весь `pytest`** с тестами предыдущих занятий. Если конкретное расхождение есть — сначала добавляет минимальный воспроизводящий тест, исправляет причину и повторяет затронутый сценарий вместе со всем набором. Если его нет — код оставляет без изменений. **Локальный результат:** предъявлены фактические результаты тестов, сценария и точечная регрессия только там, где понадобилась.

**Финишная самостоятельная проверка:** ученик показывает преподавателю учебный JSON, ожидаемый и полученный результат каждого шага, повторную загрузку отдельным сервисом, случаи отказов и итог `pytest`; затем своими словами проходит путь «CLI → сервис → Task → storage → JSON». Это проверяет перенос знаний об объектах и хранении в работающий проект. **Следующее занятие 40.1** использует этот результат для README, чистой копии, отдельного процесса и Git-версии.
