## 01. Различить проект, Python и установленные пакеты

**Что и зачем объяснить до применения.** `app/` — исходники Planner, `data/tasks.json` — его рабочие данные, Python — программа, которая исполняет код. `import` обращается к доступным этому Python модулям. Стандартные модули, например `sys`, входят в поставку Python; сторонние инструменты, например будущий `pytest`, устанавливаются отдельно. В `.venv` находятся локальный исполняемый Python и отдельный каталог пакетов; это **не копия** `app/`, JSON или Git-репозитория. Среда создаётся на основе установленного Python 3.12, а не заменяет его отдельной установкой всего Python с нуля.

**Независимый пример и различающий случай.** Вообразим два проекта с одинаковым `print("Привет")`. Оба работают на Python 3.12, но одному позже нужен пакет X определённой версии, другому — иной набор пакетов. Версия интерпретатора одинакова, а доступные сторонние пакеты могут различаться. Поэтому фраза «у меня Python 3.12» недостаточна для воспроизводимого запуска. Покажем схему одной папки Planner: `app/`, `data/`, `README.md`, `.gitignore`, `.venv/`. Стрелка от `.venv/Scripts/python.exe` идёт **к выполнению** `app.main`; код и данные остаются в своих папках.

**Первое самостоятельное применение.** Ученик на пустой схеме подписывает «код», «данные», «интерпретатор», «пакеты» и отвечает: изменится ли код Planner от появления `.venv`; можно ли узнать выбранный Python только по совпавшему «3.12». Локальный критерий: укажет, что проект не переносится, а подтверждение выбора потребует полного пути к исполняемому файлу.

**Опора для возврата.** Создание среды меняет локальные инструменты запуска, а не логику продукта; `.venv` нужно восстанавливать на каждом компьютере. После различения этих ролей можно объяснить команду её создания.

## 02. Найти корень и создать или проверить `.venv`

**Что и зачем объяснить.** PowerShell исполняет команды из **текущей рабочей папки**. Относительный путь `.venv` означает подпапку этой папки. Перед созданием нужно узнать, где терминал, какой Python установлен и есть ли уже подходящая среда. Команды вводятся после приглашения `PS …>`, само приглашение не копируют.

**Механизм и пример из корня действующего Planner (PowerShell):**

```powershell
Get-Location
Get-ChildItem -Force -Name
py -3.12 --version
Test-Path .venv
```

Разобрать вывод каждой команды **до** самостоятельного шага: первая печатает путь рабочей папки, вторая показывает `app` и `README.md`, третья должна дать `Python 3.12.x`, четвёртая возвращает `True` при наличии `.venv` и `False` при отсутствии. `py` — Windows Python Launcher; аргумент `-3.12` выбирает установленную версию, а не скачивает её. Если нужной версии нет, сперва установить/найти Python 3.12, иначе дальнейшая команда преждевременна. Если `py` отсутствует, но Python 3.12 есть, показать альтернативу с полным путём и оператором вызова `& "C:\путь\к\Python\python.exe" --version`; тем же путём можно выполнить `-m venv .venv`. Не делать эту ветку обязательной для исправного `py`.

**Создание только при `False`:**

```powershell
py -3.12 -m venv .venv
.\.venv\Scripts\python.exe --version
```

Здесь `-m` значит «запустить модуль выбранным Python», `venv` — стандартный модуль подготовки среды, `.venv` — каталог результата. Объяснить, что внутри Windows-окружения появятся `Scripts/python.exe`, `pyvenv.cfg` и место для пакетов. Команда создания сама не открывает Planner и не устанавливает pytest.

**Если `Test-Path .venv` вернул `True`:** **не** запускать создание поверх неё вслепую. Проверить `.\.venv\Scripts\python.exe --version` и затем фактический путь в шаге 03; если установлен корректный Python 3.12, использовать существующую папку. Если интерпретатор отсутствует/не запускается/имеет другую версию, закрыть процессы, использующие среду, сохранить папку под свободным резервным именем через Проводник, исключить именно это резервное имя из Git и лишь затем создать `.venv` заново. Не удалять резервную папку автоматически и не считать перенесённую с другого компьютера `.venv` работоспособной.

**Первое самостоятельное применение.** Ученик сам находит корень по `Get-Location` и `app/`, выбирает **одну** из веток по `Test-Path`, а затем получает `Python 3.12.x` именно от `.\.venv\Scripts\python.exe`. Локальный критерий: подготовлен существующий проект с исправной `.venv`, без нового репозитория и без затрагивания данных.

**Опора для возврата.** `py -3.12 -m venv .venv` создаёт среду; команда `.\.venv\Scripts\python.exe` обращается уже к ней. Следующий шаг проверяет, какой из двух интерпретаторов **действительно запустил** процесс.

## 03. Доказать путь интерпретатора и выбрать его в VS Code

**Что и зачем объяснить.** Терминал, редактор и уже запущенный Python REPL могут использовать разные интерпретаторы. `sys` — модуль стандартной библиотеки со сведениями о текущем Python; `sys.executable` — атрибут, содержащий путь к исполняемому файлу **текущего процесса**. `import sys` загружает модуль, `print(sys.executable)` показывает путь. Номер `3.12` один и тот же в нескольких средах, поэтому одной версии недостаточно.

**Независимый сравнительный опыт, прежде чем настраивать редактор:**

```powershell
py -3.12
```

После появления приглашения `>>>` вводится **код Python**, не команды PowerShell:

```python
import sys
print(sys.executable)
exit()
```

Затем в том же корне Planner запускается уже локальный интерпретатор:

```powershell
.\.venv\Scripts\python.exe
```

И в новом `>>>`:

```python
import sys
print(sys.executable)
exit()
```

Второй путь должен оканчиваться на `.venv\Scripts\python.exe` **этой копии Planner**; первый ведёт к установленному Python за пределами `.venv`. `exit()` возвращает из REPL в PowerShell. Отдельно пояснить, что `SyntaxError` после ввода `.\.venv\Scripts\python.exe` в `>>>` означает смешение оболочек, а не поломку среды.

**Выбор в VS Code.** Открыть именно папку Planner, вызвать `Ctrl+Shift+P → Python: Select Interpreter` и выбрать `.venv\Scripts\python.exe` из её корня; если нет в списке, указать через `Enter interpreter path`. Запустить **новый** `Python: Start Terminal REPL` (если команда доступна) и снова выполнить `import sys` / `print(sys.executable)`: путь должен совпасть с проверенным локальным. Если команда REPL в данной конфигурации VS Code отсутствует, использовать новый терминал и прямой вызов `.\.venv\Scripts\python.exe`; отдельно отметить, что такой вызов доказывает работу среды, но сам по себе не доказывает настройку редактора. Выбор в редакторе не переключает уже запущенный REPL.

**Первое самостоятельное применение.** Ученик без подсказки различает два полученных пути, выбирает локальный в VS Code и подтверждает его в новом REPL. Локальный критерий: **полный** `sys.executable` содержит текущий корень Planner и `.venv\Scripts\python.exe`; в ответе ученик объясняет, почему два `Python 3.12.x` ещё не являются одной средой.

**Опора для возврата.** Для надёжного запуска и будущей установки пакета можно прямо вызывать `.\.venv\Scripts\python.exe`: **активация необязательна**, изменять политику PowerShell не требуется. Следующий шаг использует этот путь для существующего приложения.

## 04. Запустить тот же Planner, не меняя JSON

**Что и зачем объяснить.** В `python -m app.main` модуль `app.main` запускается как точка входа установленным/выбранным Python. Для запуска из локальной среды меняется только **исполняемый файл**, а `-m app.main`, код приложения и его storage остаются прежними. Команду вводить в PowerShell **из корня проекта**, после выхода из REPL.

**Разобранный пример:**

```powershell
.\.venv\Scripts\python.exe -m app.main
```

Предсказать результат до запуска: появится прежнее меню CLI; приложение не создаёт второй Planner. Для минимальной проверки выбрать `exit` по уже известному формату меню. **Не** добавлять/удалять задачи ради доказательства корректного окружения: это изменило бы рабочий `data/tasks.json` и смешало проверку среды с регрессией продукта.

**Различающиеся отказы.** `No module named app` → сначала `Get-Location` и наличие `app/main.py`: команда выполнена не из корня либо исходники отсутствуют. `python.exe` не найден → вернуться к шагу 02, проверить `.venv`. `SyntaxError` при вводе строки запуска в `>>>` → `exit()`, затем команда из `PS …>`. Эти отказы нельзя «лечить» изменением импортов Planner без проверки пути.

**Первое самостоятельное применение.** Ученик повторяет команду самостоятельно, видит прежнее меню и штатно выходит. Локальный критерий: прежний CLI открывается локальным Python; код, команды и пользовательский JSON не редактировались. Дальше нужно оставить именно способ настройки, а не созданные машиной файлы.

## 05. Исключить среду из Git и описать восстановление

**Что и зачем объяснить.** В Git передаём исходники и инструкции, а не локальные исполняемые файлы и установленные пакеты: `.venv` зависит от компьютера и восстанавливается командой из README. `.gitignore` задаёт правила **до `git add`/staging**; игнорирование не стирает файл с диска и не перестаёт отслеживать файл, который уже был добавлен в индекс.

**Механизм и пример.** Найти корневой `.gitignore` и сохранить прежние правила (`__pycache__/`, `*.pyc` и другие). Если строки нет, добавить **ровно один** шаблон:

```gitignore
.venv/
```

До `git add` проверить игнорирование реального служебного файла среды и папки:

```powershell
git check-ignore -v .venv/pyvenv.cfg
git status --ignored --short -- .venv/
git ls-files .venv
```

Разобрать вывод: `git check-ignore -v` показывает правило и файл, из которого оно взято; `git status --ignored --short` должен помечать среду как игнорируемую (`!! .venv/`); `git ls-files .venv` должен не показывать файлов. Если файлы `.venv` уже отслеживаются, правило `.gitignore` само по себе этого не исправит: остановить передачу и отдельно разобрать текущее состояние индекса, **не** удаляя среду. Если была сохранена резервная папка, проверить отдельное правило для её точного имени и отсутствие отслеживаемых файлов; не записывать произвольный глобальный шаблон, скрывающий другие данные.

**README как инструкция, не копия локального пути.** В существующем разделе запуска объяснить версию Python 3.12, вход в корень проекта, создание `.venv` **если её нет**, прямой запуск Planner и проверку версии/пути при сомнении. Короткая проверяемая последовательность команд для README (в Windows PowerShell):

```powershell
py -3.12 --version
py -3.12 -m venv .venv
.\.venv\Scripts\python.exe --version
.\.venv\Scripts\python.exe -m app.main
```

Строку создания выполнить **только при отсутствии** `.venv`; повторное создание исправной среды не требуется. В README не вставлять абсолютный `C:\Users\...` из `sys.executable`: этот путь принадлежит одной машине. Перед записью проверить, нет ли уже нужного раздела, и дополнить его вместо дублирования.

**Связь со следующим занятием, без установки.** `pip` устанавливает сторонние пакеты, но запущенный «голый» `pip` может относиться к другому Python. В команде `.\.venv\Scripts\python.exe -m pip ...` модуль `pip` запускается **тем интерпретатором, чей путь указан перед `-m`**. Это объясняет, почему в 38 pytest поставят именно сюда; сейчас `pip install`, `requirements-dev.txt` и тесты не выполняются.

**Первое самостоятельное применение.** Ученик сам оформляет только нужные строки `.gitignore` и README и объясняет, почему `.venv` нельзя коммитить как «готовый Python». Локальный критерий: Git помечает папку как игнорируемую, README содержит воспроизводимые относительные команды, приложение и JSON не изменены.

**Опора для возврата.** Исходники хранятся в Git, локальную среду можно воссоздать; её наличие и выбранный в VS Code путь — отдельные проверки. Завершим практикой с новым терминалом, чтобы это знание не зависело от случайной старой сессии.

Практика связана накопительно: следующий шаг разрешён, только если ученик показал результат предыдущего. Ученик выполняет действия и объясняет причину; демонстрация готовых команд из теории служит опорой, но локальный выбор ветки, диагностика и проверка выполняются им самим.

1. **Сверить вход.** **Объект:** текущая папка Planner, системный Python, `.gitignore`, README и возможная `.venv`. **Самостоятельно:** найти корень, сравнить путь/содержимое папки и версию 3.12, проверить наличие `.venv`. **Наблюдаемый результат:** перед учеником именно рабочий Planner и понятна ветка «создать / использовать / сохранить неподходящую среду отдельно». При `True` и неподходящем Python ничего не перезаписывать.
2. **Подготовить Python проекта.** **Объект:** `.venv` текущего репозитория. **Самостоятельно:** создать её только при отсутствии либо безопасно проверить существующую; затем выбрать её Python в VS Code. **Наблюдаемый результат:** локальный `python.exe` запускается и сообщает 3.12.x; ученик может назвать роль `-m venv` и отличить среду от исходников.
3. **Доказать, какой Python работает.** **Объект:** новый локальный REPL и выбор редактора. **Самостоятельно:** вывести `sys.executable` сперва у системного Python, затем у Python проекта, сверить выбор VS Code в новом процессе. **Наблюдаемый результат:** два различимых полных пути; второй находится в `.venv\Scripts\python.exe` нужного Planner. При совпавшей версии, но неверном пути ученик сам возвращается к выбору интерпретатора, а не объявляет успех.
4. **Подтвердить сохранность продукта.** **Объект:** привычный `app.main` и рабочий JSON. **Самостоятельно:** из корня запустить Planner прямым путём к локальному Python, увидеть меню и выйти без CRUD-действий. **Наблюдаемый результат:** прежнее меню работает; `app/`, `data/tasks.json` и пользовательские команды не менялись. Ошибку импорта разобрать через корень/путь запуска.
5. **Оставить инструкцию вместо файлов среды.** **Объект:** `.gitignore` и существующий раздел README. **Самостоятельно:** проверить и при необходимости добавить `.venv/` до staging, показать игнорирование через `git check-ignore` и `git status --ignored`, затем записать повторяемые команды установки среды и запуска без абсолютного пути. **Наблюдаемый результат:** Git игнорирует окружение, оно не отслеживается, инструкция пригодна на другой копии проекта; pytest и dev-зависимости отсутствуют.

**Итоговый самостоятельный перенос.** Закрыть использованный REPL, открыть **новый терминал** в том же Planner и по своему README снова подтвердить путь `sys.executable` и открыть меню. Если `python --version` показывает 3.12, но `sys.executable` ведёт вне `.venv`, ученик объясняет, почему проверка не пройдена, и указывает точную команду для проверки нужного Python. Затем отвечает, почему в 38 будет использован локальный `python -m pip`, хотя пакет пока не установлен. Это проверяет перенос знания на новую сессию, а не механическое повторение одной команды.
