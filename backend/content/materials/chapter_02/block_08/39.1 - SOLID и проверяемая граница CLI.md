## 00. Вступление
До этого мы проверяли, что `PlannerService` выполняет действия с задачами, а `JsonStorage` сохраняет результат. Но даже исправный сервис не поможет, если меню передаст ему неправильную команду. **CLI** — это программа, с которой пользователь общается текстом в терминале.

Связанная тройка для вступительного визуала (`LinkedNotes variant="connected"` в MAIN):
1. **Точка старта:** модель, сервис и хранение уже подготовлены и проверены в предыдущих занятиях; команда `list` проходит через них.
2. **Новый вопрос:** как обработать ровно одну `list` или `add`, не запуская всё меню и не обращаясь к глобальным `input()` и `print()`?
3. **Результат:** `run` отвечает за повторение меню, `execute_command` — за одно действие, а ввод и вывод передаются функциями.

Связь пунктов: сначала ищем путь существующей команды, затем место, где смешались цикл и действие; только после этого меняем границу. **Одна команда** — один запрос пользователя, а **сессия** — много команд подряд до `exit`. Не начинаем с переписывания Planner.

## 01. От зелёных проверок к границе команды
- **Что и зачем:** тест `PlannerService.list_tasks()` подтверждает работу метода, но не доказывает, что ввод `list` в меню вызывает именно его. Проверяемость команды нужна, чтобы искать ошибку в нужном месте.
- **Пошаговый разбор до практики:** пользователь печатает `list` → CLI определяет действие → вызывается `service.list_tasks()` → CLI показывает полученный список. Если меню случайно вызывает `get_statistics()`, проверка самого `list_tasks()` останется зелёной, а пользователь увидит не то.
- **Первое применение в объяснении:** предложить ученику предсказать, какой участок виноват, когда прямой вызов `list_tasks()` возвращает задачи, а команда `list` печатает статистику. Затем показать путь вызова и отделить ошибку маршрутизации CLI от ошибки сервиса.
- **Опора для возврата:** «тест отдельного метода ≠ проверка соединения методов». На следующем шаге строим схему этого соединения; тестирование команды с callbacks станет предметом 39.2.

## 02. Схема ролей как опора для понимания ООП
- **Понятия до схемы:** объект `PlannerService` знает правила работы с задачами; `storage` знает, как получить и сохранить список `Task`; CLI знает, как разговаривать с пользователем. **Композиция** здесь означает «один объект использует переданный ему другой объект»; наследование для этого не требуется.
- **Визуал для MAIN — две отдельные дорожки:**
  `read("Команда: ") → run → execute_command → обработчик → PlannerService → storage.load() → Task`
  `Task/список → PlannerService → обработчик → write(сообщение)`; отдельно `execute_command → True/False → run`.
  На схеме подчеркнуть: `run` не вызывает storage и не решает, выполнена ли задача; `write` только выводит сообщение; булево `True/False` говорит **продолжать ли меню**, а не «успешен ли add».
- **Разобрать конкретные случаи:** для `list` сервис читает задачи, CLI выводит результат, изменения и `save()` нет; для `done` сервис меняет состояние существующей задачи и сохраняет лишь реальное изменение; для `exit` сервис и storage вообще не нужны — возвращается `False`. Вопрос ученику: почему `list` и `exit` не должны сохранять JSON? Ответ виден по пути вызовов: они не меняют задачи.
- **Наблюдаемые роли:** пользовательская строка принадлежит CLI; состояние задач — сервису и storage; выбор `JsonStorage`/`MemoryStorage` происходит при сборке, **до** команды. Не путать направление вызовов с деревом папок или цепочку `Task → словарь → JSON` из занятия 39 с новой командной границей.
- **Первое применение:** дать перемешанные подписи «чтение команды», «поиск Task», «вывод сообщения», «выбор storage»; ученик размещает их у `run`, `PlannerService`, writer и `build_service`, обосновывая каждый выбор. Эти роли затем используем для диагностики SOLID.

## 03. SOLID как вопросы к существующим обязанностям
- **Что такое SOLID:** пять ориентиров для кода, который проще менять, не ломая соседние части. Это вопросы к уже работающему Planner, а не требование написать пять классов. Полные названия раскрыть при первом упоминании, рядом сразу показать понятную роль из проекта.
- **SRP — Single Responsibility Principle, одна причина изменения:** у `run` причина изменения — способ вести сессию; у `execute_command` — правила выбора/обработки отдельной команды; у сервиса — правила задач; у storage — хранение. Если добавить пункт меню, зачем менять цикл `while`? Если сменить JSON на память, зачем переписывать сообщения CLI? Эти вопросы обнаруживают смешение ролей.
- **Независимый простой пример перед проектом:** одна функция и читает имя в цикле, и вычисляет длину каждого имени, и печатает ответ. Разделяем «повторять вопросы» и «посчитать длину одного полученного имени». Ученик предсказывает: изменение способа повторения затронет цикл, а правила подсчёта — отдельную функцию. Затем переносим эту мысль на `run`/`execute_command`.
- **Первое применение:** на кусочке текущего CLI указать две причины правки в одном `run` (изменение меню и изменение обработки `done`). Ученик предлагает узкую границу «одна команда» и объясняет, что сервис не переписываем. Если слой уже отделён, фиксируем **KEEP** и проверяем его договор вместо повторного создания.
- **Ограничение:** SRP не означает «одна строка кода на функцию», а SOLID не оправдывает бесполезные обёртки. Сначала находим смешение, затем меняем минимум, нужный для B.

## 04. Договор заменяемости: OCP и LSP
- **OCP — Open/Closed Principle:** новое поведение можно подключать через существующую границу, не переписывая каждый раз работающее ядро. Например, `build_service` передаёт сервису либо `MemoryStorage`, либо `JsonStorage`; алгоритм `list_tasks()` при выборе storage остаётся тем же. Это не обещает, что любой новый формат сам появится без изменений: он должен соблюдать договор.
- **LSP — Liskov Substitution Principle:** заменить один storage другим безопасно, только если сохраняется **смысл** вызовов. Для нашего проекта `load()` даёт список `Task`, а `save(tasks)` принимает актуальный список для хранения; ошибка хранения обозначается принятой ошибкой, не пустым успешным списком. Если второй класс тоже имеет `load()`, но возвращает строку JSON или молча теряет задачи, совпадение названий не делает его заменой.
- **Различающий мини-пример до проекта:** две коробки с одинаковой надписью «выдать карандаши». Одна выдаёт карандаши, другая — чек об их покупке. Названия похожи, результат для рисующего человека различен. Сразу уточнить аналогию кодом: `service.list_tasks()` ждёт `list[Task]`, а не строку.
- **Применение:** предложить две реализации `load()` (одна возвращает список задач, другая `"[]"`) и попросить выбрать совместимую и объяснить, что сломается в `PlannerService`. Затем назвать, почему сохранение через `JsonStorage` и в памяти может отличаться технически, сохраняя договор; копирование списка в MemoryStorage **не гарантирует** независимых копий самих Task и не даёт транзакционного отката.
- **Переход:** замену удобно выполнять, когда сервис зависит от небольшого договора и получает конкретный объект извне. Это ISP и DIP.

## 05. Малый интерфейс и место выбора зависимости
- **ISP — Interface Segregation Principle:** каждая часть должна получать только нужные возможности. Сервису от storage нужны `load()` и `save(tasks)`, а не методы удаления папок или печати меню. Обработчику команды нужны `read(подсказка)` и `write(сообщение)`, а не весь терминал как объект. Здесь **интерфейс** — согласованный набор операций; писать отдельный класс-интерфейс пока не требуется.
- **DIP — Dependency Inversion Principle:** сервис опирается на договор storage, а готовую конкретную зависимость получает извне. Сначала `build_service` выбирает `JsonStorage(path)` для обычного запуска или `MemoryStorage()` для временной проверки, затем создаёт `PlannerService(storage)`. Если сервис сам создаст `JsonStorage`, заменить файловый вариант без правки сервиса уже не получится.
- **Независимый пример:** функция `greet(name, write=print)` не решает, куда именно попадёт строка; вызывающий код может передать другой writer. Здесь `write` — **параметр, хранящий функцию**; вызов `write("Привет")` использует переданную функцию так же, как обычную `print`.
- **Первое применение:** дать варианты «`PlannerService()` сам открывает `data/tasks.json`» и «`build_service` создаёт storage, затем передаёт его сервису». Ученик выбирает второй вариант и называет, кто принимает решение и почему. Для CLI аналогично: настоящий `input/print` либо переданные функции выбирает вызывающий код.
- **Опора:** ISP отвечает «каких операций достаточно?», DIP — «кто выбирает конкретную реализацию?». У нас уже есть минимальные договоры; ABC, Protocol, новый DI-framework и дополнительный сервис не нужны. Теперь покажем сам механизм передаваемых функций до проектной правки.

## 06. Одна команда и цикл общения
- **Два уровня управления:** `run` читает **очередную** строку в цикле; `execute_command` получает **уже прочитанную** строку и делает только один шаг. Передаваемая функция называется *callback*, но это обычный параметр: `read` можно вызвать как `input`, `write` — как `print`. Значения по умолчанию `read=input, write=print` оставляют обычный терминальный запуск работоспособным.
- **Отдельный разобранный пример, до Planner:**

  ```python
  def ask_color(read=input, write=print):
      color = read("Цвет: ").strip()
      write("Выбрали: " + color)
      return color

  replies = ["синий"]
  messages = []

  def saved_read(prompt):
      return replies.pop(0)

  result = ask_color(read=saved_read, write=messages.append)
  # result == "синий"; messages == ["Выбрали: синий"]
  ```

  **Разъяснить каждую новую деталь до самостоятельного применения:** `saved_read` получает подсказку и возвращает заготовленную строку; `pop(0)` берёт первый ответ из списка и удаляет его; `messages.append` — уже знакомый метод списка, **переданный без скобок**, чтобы `ask_color` вызвала его позже. Настоящий терминал здесь не требуется, а результат функции и выведенное сообщение наблюдаются отдельно. Тема примера — цвет, не готовое решение CLI Planner.
- **Перенос на CLI — договор, а не эталон готовой функции:** `execute_command(service, command, read=input, write=print) -> bool`. Переданный `command` нормализуется **один раз в выбранном месте** (`strip().lower()`), далее используется существующая таблица/маршрут обработчиков. При `add` обработчику могут понадобиться дополнительные ответы `read`, для `list` — только результат сервиса и `write`. Все вложенные readers/handlers получают **те же** `read/write`, не вызывают глобальные `input/print` прямо.
- **Возврат одного бита:** `True` = меню может читать следующую команду, `False` = прекращаем сессию. `exit` возвращает `False`, неизвестная команда пишет прежнее сообщение и возвращает `True`; результат `service.add_task()` — это задача, **не** значение, управляющее циклом. Мини-трассировка `wat → сообщение → True → следующая команда → exit → False` показывает разницу. `run` использует цикл и завершает его только по возвращённому признаку.
- **Первое применение:** в коротком независимом фрагменте с двумя командами ученик предсказывает последовательность `True/False` и список собранных сообщений. Затем располагает карточки «прочитать команду → вызвать execute_command → проверить bool → повторить» и объясняет, почему `execute_command` не должна сама запускать `while`.
- **Опора для возврата:** `read` возвращает текст; сервис возвращает предметный результат; `write` фиксирует сообщение; `execute_command` возвращает решение для `run`. Эти четыре значения имеют разные роли. Далее выясним, что произойдёт при ошибке в одном шаге.

## 07. Границы отказа и сохранение прежнего поведения
- **Почему нужно различать ошибки:** если пользователь ввёл `done` с несуществующим id, можно показать понятный отказ и продолжить меню. Если storage не сумел прочесть/сохранить данные, делать вид, что всё хорошо, нельзя. Это разный смысл: ошибка команды против ошибки надёжности данных.
- **Таблица состояний до практики:**

  | Случай | Что видит пользователь | Продолжение | Изменение данных / save |
  | --- | --- | --- | --- |
  | `list` | Прежний вывод списка | `True` | Чтение; нет `save` |
  | `add` с допустимыми полями | Прежнее подтверждение | `True` | Одна успешная мутация и нужное сохранение |
  | Неверное значение / отсутствующий id | Прежнее сообщение об ошибке | `True` | Нет успешной мутации и лишнего `save` |
  | Неизвестная команда | Прежнее сообщение о неизвестной команде | `True` | Нет изменения / `save` |
  | `exit` | Прежнее сообщение о выходе, если оно было | `False` | Нет изменения / `save` |
  | `StorageError` | Сообщение существующей верхней границы обработки | Сессия завершается по прежнему договору | Успех не объявлять; не обещать откат памяти |

- **Разобрать опасный пример:** `except Exception: write("Команда выполнена"); return True` ловит и пользовательскую ошибку, и `StorageError`, и ошибку программиста. Объяснить, почему такой перехват одновременно может скрыть потерю данных и создать ложный успех. Сохраняем узкую обработку известных пользовательских ошибок (`ValueError`, `TaskNotFoundError`) в принятом месте CLI; проблемы storage оставляем прежней верхней границе, без нового `try` в сервисе.
- **Первое применение:** ученик распределяет случаи «неизвестный id», «повреждённый JSON» и «`exit`» между сообщением одной команды, верхней границей отказа и штатным завершением. Вопрос-перенос: почему после сбоя `save()` мы не вправе обещать полный откат уже изменённого объекта в памяти? Ответ: существующий учебный storage не даёт транзакции.
- **Переход к практике:** сравниваем прежние сообщения и изменения состояния, а не переписываем их ради рефакторинга. На этом уроке используем существующие тесты плюс ручной проход; новые автоматические CLI-регрессии и счётчики storage появятся в 39.2.

## 08. Что мы будем делать в практике
**Обязательный формат: проектная работа в существующем Persistent Planner.** Вход: выполненные 38–39, работающий `run` и обработчики команд, один `PlannerService` и выбранный storage; работаем с `MemoryStorage` либо **временным JSON**. Не меняем `data/tasks.json`, модель, сервисные алгоритмы и формат хранения. Если `execute_command` в учебной копии уже выделен, вместо повторного создания ученик сверяет его с договором и исправляет только выявленное расхождение.

**Связанная последовательность для `LinkedNotes variant="connected"` в MAIN** — каждый шаг выполняется учеником после объяснения выше; готовый финальный код заранее не выдаётся:

1. **Найдём реальное смешение ролей (наблюдение → диагноз).** Ученик сам запускает `list` и `done` на изолированных данных, открывает текущие `run`/обработчики и рисует два коротких пути вызова: кто читает строку, кто решает, какой метод сервиса вызвать, кто выводит ответ, кто сохраняет. Отмечает две причины изменения `run`, если цикл и отдельная команда там смешаны. **Локальная проверка:** для `list` найдено чтение без сохранения, для успешного `done` — изменение через сервис; на схеме нет прямого вызова storage из `run`. Если фактический код отличается, ученик записывает реальное отличие до правки, не подгоняет схему под желаемый результат.
2. **Выберем минимальную границу (сначала объяснение, потом код).** Ученик указывает конкретное место для `execute_command` и формулирует: `run` повторяет команды, `execute_command` выбирает один обработчик и возвращает `bool`, а `build_service` выбирает storage. Объясняет по одному настоящему случаю SRP (смешанный цикл/действие), OCP/LSP (замена хранилища без смены смысла `load/save`) и ISP/DIP (малые договоры и место выбора зависимости). **Локальная проверка:** может объяснить, какие части меняются при добавлении команды и при смене storage, и почему сервис не создаёт `JsonStorage` самостоятельно. Это диагностика своего кода, а не поиск пяти искусственных нарушений.
3. **Самостоятельно отделим одну команду от цикла (первая проектная правка).** Из существующей ветки выбора/вызова обработчика ученик выделяет `execute_command(service, command, read=input, write=print) -> bool`, оставляя таблицу команд и сообщения прежними. `run` теперь только читает очередную строку, передаёт её в `execute_command` и продолжает либо завершает цикл по возвращённому `bool`. Очистку и приведение регистра команды делают в **одном** указанном месте, чтобы `" EXIT "` имело то же значение, что `exit`. **Локальная проверка:** две последовательные команды без `exit` выполняются в одной сессии; неизвестная команда пишет прежний отказ и не завершает меню; `exit` завершает, не обращаясь к сервису. `True` не означает, что операция изменила данные.
4. **Протянем переданные функции до места реального ввода/вывода (самостоятельная сборка).** Ученик передаёт **те же** `read/write` от `run`/`execute_command` в существующие обработчики и helpers (`read_priority`, `read_task_id` и другие фактически используемые readers), заменяет прямые `input()`/`print()` **в проверяемой ветке** на вызовы параметров. Доступные сигнатуры и правила валидации сохраняются. Для ручной пробы вызывает одну команду напрямую с `MemoryStorage`, простым `read` из заранее записанных ответов и `write=messages.append` из разобранного примера про цвет. **Локальная проверка:** у `add` появилась ровно одна новая Task с прежними полями, сообщения собраны в список, команда вернула `True`; ввод из настоящего терминала для этого прямого вызова не потребовался. Затем ученик самостоятельно пробует `list` с тем же способом вывода: вывод есть, новая задача не создаётся. **Контраст:** намеренно оставленный прямой `input()` в глубоком reader выдаст лишний запрос терминалу — по этому признаку ученик находит и исправляет пропущенную передачу.
5. **Сверим сохранённое поведение и ошибки (проверка результата B).** На изолированном наборе, восстановленном в одинаковое начальное состояние до и после рефакторинга, ученик вручную проходит `add`, `list`, `find`, `search`, `done`, `delete`, `stats`, неизвестную команду и `exit` и сопоставляет прежние сообщения, значения и состояние задач. Отдельно пробует нечисловой/несуществующий id: понятный отказ, сессия продолжается, успешного изменения/лишнего save нет. По коду прослеживает `StorageError`: её нельзя поглотить широким `except Exception` и продолжить как успех; прежняя верхняя граница обрабатывает сбой. **Локальная проверка:** нет второго сервиса и списка-кеша; чтения и неверные действия не сохраняют данные, реальная мутация сохраняется; старые тесты модели, сервиса и файловой интеграции остаются зелёными. Ручной сценарий не выдаём за новый автоматический тест.

**Что именно доказывает B:** ученик может в одном предложении назвать владельца цикла, обработчика, сервиса и хранения; вызвать одну команду с переданными `read/write`; увидеть вывод без терминала и состояние через прежний сервис; объяснить `True/False` и границу `StorageError`. Это **проектная** работа, а не просмотр готовой схемы или замена одной строки.
