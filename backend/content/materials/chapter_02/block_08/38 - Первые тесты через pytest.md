## 00. Вступление

В Planner уже есть несколько взаимодействующих объектов, и их договоры пока подтверждались вручную. Тест позволит повторять эти проверки после изменений и точнее видеть, какая граница дала сбой.

1. **Точка старта:** ранее собранные Task, storage и сервис можно вызвать из Python и проверить вручную через `assert`; подготовка `.venv` должна быть подтверждена по 37.3.
2. **Новый вопрос:** если после изменения сервиса ручная проверка забыта, как автоматически заметить нарушение конкретного правила и понять, где оно произошло?
3. **Результат:** в существующем проекте запускается pytest, а написанные учеником тесты проверяют объект, контейнер памяти и пользовательские операции сервиса.

После связанного списка объяснить, что тест — обычная функция Python, которая **вызывает** знакомые объекты, а pytest находит эти функции и сообщает об их результате. План будущей подачи: одна связанная группа «старт → вопрос → результат», затем короткий прогноз «что потеряем, если вернём не ту Task»; не размещать цепочку вопросов об одинаковом определении теста.

## 01. От ручной проверки к исполняемому ожиданию

**Сначала смысл, затем термин.** Вручную ученик выбирает команду Planner, смотрит на экран и решает, всё ли правильно. Автоматический тест — функция с заранее записанным ожиданием: она сама вызывает программу, получает значение или наблюдает состояние и сообщает о расхождении. *Проверяемый договор* — конкретное правило, например «новая Task ещё не завершена», а не обещание, что ошибок никогда не будет. Для каждого правила требуется осмысленное входное значение и наблюдаемый результат.

**Независимый короткий пример до кода проекта:** знакомое выражение `2 + 3` должно дать `5`. Объяснить `assert 2 + 3 == 5`: Python вычисляет левую и правую части, оператор `==` возвращает `True`/`False`; при `False` возникает `AssertionError`. Отдельно показать `assert 2 + 3 == 6` как предсказуемый отказ и тут же вернуть правильное значение. `assert` здесь не печатает успешный результат. Отсюда появляется *тест*: функция `def test_sum():` с таким утверждением; `test_` понадобится для обнаружения, а не для вычисления суммы.

**Первая попытка ученика до pytest:** предсказать, завершится ли успешно `assert "PY".lower() == "py"`, и объяснить, что именно сравнивается; затем изменить только ожидаемую строку на неверную и назвать тип отказа. Локальный критерий — понятна разница между *фактом* и *ожиданием*, без CLI и неизвестного синтаксиса.

**Различение:** тест «после add список непустой» может оставаться зелёным даже при неверном title; число зелёных тестов не говорит, какие правила они проверили. Проверку сервисного поведения строим на публичном результате/состоянии, а не по строке, напечатанной CLI. Переход: нужен инструмент, который соберёт такие функции и покажет, какое ожидание не выполнилось.

## 02. Как pytest находит и запускает тесты

**Определить новые слова до команды.** `pytest` — устанавливаемый пакет, который ищет тестовые функции, запускает их и показывает PASS/FAIL; приложение Planner продолжает работать и без pytest. `pip` — инструмент установки Python-пакетов, *зависимость разработки* — пакет для работы над проектом, но не новая пользовательская команда. Виртуальное окружение `.venv` — уже подготовленное в 37.3 место для интерпретатора и пакетов этого проекта; *интерпретатор* выполняет Python-код. Запись `python -m имя` означает «этим конкретным Python запустить модуль по имени»; `-r путь` у pip означает «прочитать имена пакетов из файла».

**Порядок и место:** из корня имеющегося Planner сначала сверить существующий `.venv` и выбранный VS Code Python (37.3), затем выбрать совместимую версию pytest, реально проверить её установку и зафиксировать ту же **конкретную версию** в `requirements-dev.txt` строкой вида `pytest==<проверенная версия>`; угловая запись здесь пояснение, не буквальный готовый файл. Команда `.\.venv\Scripts\python.exe -m pip install -r requirements-dev.txt` устанавливает именно в этот Python; `.\.venv\Scripts\python.exe -m pytest --version` показывает версию тестового инструмента из него же. Не требовать новых команд активации PowerShell. Объяснить, почему простой `pip`/`pytest` в другом терминале может обратиться к другой среде. Планируемое дополнение к README: воспроизводимые команды создания среды из 37.3, установки dev-пакета и тестового запуска; проверить, что `.venv/` игнорируется, а `requirements-dev.txt` остаётся отслеживаемым исходным файлом.

**Обнаружение на уже написанном тесте:** каталог `tests/`, файл `test_smoke.py`, функция `def test_simple_expectation(): ...` с коротким осмысленным `assert`. Сначала создать этот файл, **потом** запускать `.\.venv\Scripts\python.exe -m pytest -q` из корня репозитория. Пояснить: имя файла `test_*.py`, имя функции `test_*` позволяют pytest найти проверку; опция `-q` сокращает отчёт, без неё смысл результата тот же. После первого запуска сменить имя функции на `check_simple_expectation` и попросить предсказать, почему тест больше не обнаружится, затем вернуть `test_` и повторить целевой запуск. Это исследование правил поиска, не отсутствие кода Planner.

**Импорт без магии:** `from app.models import Task` значит «взять настоящую Task из пакета app», а `from app.storage import MemoryStorage` — её настоящее хранилище. Запуск из корня должен обеспечивать доступ к `app`; если collection прервалась ошибкой `ModuleNotFoundError`, до выполнения `assert` дело не дошло. Сначала проверить рабочий каталог, выбранный интерпретатор и структуру `app`, не исправлять данные модели и не прятать проблему случайными манипуляциями `sys.path`. Первое действие ученика: по фрагменту отчёта различить `collected 0 items`, сбой импорта и `1 passed`. Переход: найденный тест нужен для реального вызова объекта, у которого есть вход и изменяемое состояние.

## 03. AAA как схема взаимодействия объектов

**Три слова последовательно:** Arrange («подготовь») — создай начальные объекты и вход; Act («выполни») — вызови одно проверяемое публичное действие; Assert («сравни») — проверь результат и важное состояние. Это способ читать тест, а не три команды pytest. *Публичный метод* — метод, который другие части программы уже вызывают по договору, например `add_task`; внутреннюю реализацию повторять в тесте не нужно. Передача одного объекта `MemoryStorage` в `PlannerService` — знакомая композиция: сервис использует эту зависимость, а не создаёт невидимый рабочий JSON.

**Независимый пример через известный список:** Arrange `items = []`, Act `items.append("a")`, Assert `assert items == ["a"]`. Сначала показать вход/действие/результат и только затем схему `тест → сервис → модель Task / storage → наблюдаемый результат`. Подписи схемы: тест инициирует вызов; сервис решает прикладной сценарий; модель проверяет поля одной задачи; storage отдаёт/принимает контейнер. Стрелка назад обозначает возвращённый объект; сохранённый набор можно прочитать отдельным публичным вызовом. Ни Task, ни storage не печатают меню.

**Первое применение в знакомом проекте:** разобрать *структуру*, ещё не готовое решение итогового теста: `storage = MemoryStorage()`, `service = PlannerService(storage)` — подготовка; `service.list_tasks()` — действие; ожидание для нового пустого набора — `[]`. Показать, как перенести эти три части в функцию `test_empty_planner_lists_no_tasks()`, но последующие add/done/delete оставить ученику. Критерий: ученик может подписать строки Arrange/Act/Assert, объяснить, какой объект должен оставаться тем же между действием и наблюдением, и почему новый `MemoryStorage()` внутри Assert нарушил бы смысл проверки.

**Различающий случай:** `created = service.add_task(...)` вернул объект с ожидаемым `title`, но запись могла не сохраниться. Поэтому у изменяющего действия в практике нужны **два разных наблюдения**: значение `created` и `service.list_tasks()`/`storage.load()` после вызова. В тестах без мутации нет смысла требовать сохранение. Переход: выбираем правило, которое действительно принадлежит модели, контейнеру или сервису.

## 04. Проверять договоры модели, storage и сервиса

**Task: правила одной задачи.** Напомнить форму `Task(id, title, priority=..., tags=...)`: `id` — положительное число, `title` — очищенная от внешних пробелов непустая строка, `priority` — число 1–5, `is_done` новой задачи — `False`, `tags` — список меток у *конкретного экземпляра*. До теста объяснить, что «граница» — минимальное/максимальное допустимое значение, а «независимость экземпляров» означает, что изменение списка меток одной Task не добавляет метки другой. На одном разбираемом примере `Task(1, "  Книга  ", priority=3)` прогнозировать `title == "Книга"`, после чего ученик сам выбирает **другой** title и проверяет очистку и сохранение регистра. Для разных правил — отдельные тесты с говорящими именами; нормальные значения и нарушения диапазона не смешивать в одну загадочную проверку.

**Методы Task: эффект и отказ.** Метод `mark_done()` меняет `is_done` выбранного объекта; соседний объект остаётся незавершённым. Метод изменения названия должен либо записать нормализованное допустимое значение, либо отвергнуть пустое без потери предыдущего title. Сначала проговорить: если вызов отвергнут, «состояние осталось прежним» — отдельное ожидание после проверки типа исключения. Не проверять только «метод вызвался».

**MemoryStorage: два уровня, где легко ошибиться.** `load()` возвращает **новый список** с теми же объектами `Task` внутри; `save(tasks)` сохраняет свой экземпляр контейнера. На независимом примере `source = [task]`, `outside = source.copy()`, `outside.clear()` изменяет только `outside`, длина `source` остаётся 1. Но `outside[0].mark_done()` при непустом списке может изменить общий объект `task`. Рисунок: две рамки списков → одна и та же Task внутри; это поясняет, почему `load().clear()` не удаляет запись из storage, а мутация полученного объекта может быть заметна. **Тонкая граница:** копия контейнера не означает глубокую копию, не обещает транзакцию или автоматический откат. Первое самостоятельное наблюдение — предсказать длину `storage.load()` после очистки отдельного загруженного списка и состояние общей Task после `mark_done()`; обе части нужны, чтобы не закрепить ложное правило «load полностью изолирует данные».

**PlannerService: результат плюс последствие.** Сервис получает выбранный `MemoryStorage`, вызывает правила модели и сохраняет изменённый набор. В коротком разобранном сценарии с пустой памятью объяснить два наблюдения добавления: вернувшаяся Task получает первый id `1`, а последующий `list_tasks()` возвращает её. Это *не* проверка внутреннего списка сервиса. Дальше договоры выбираются из уже знакомой таблицы курса: `get_task` возвращает найденное; `search_tasks` сопоставляет title без регистра, при отсутствии совпадений возвращает `[]`; `mark_done` завершает выбранную задачу, повтор не создаёт новую; `delete_task` убирает её, не сдвигая id остальных; `get_statistics` даёт `all/open/done` с равенством `all == open + done`. Пустой список и отсутствие задачи — разные исходы: `list_tasks() == []` допустимо, `get_task(999)` обязан сообщить об ошибке.

**Проба рассуждения:** после двух добавлений с id 1 и 2 удалить id 1. Ученик до запуска предсказывает id оставшейся задачи и следующей вновь добавленной (max текущих + 1), затем связывает каждое ожидание с договором, а не с произвольным порядком списка. Не превращать этот разбор в полную готовую практику. Переход: недопустимый вход проверяется другим инструментом, потому что вместо возвращённого значения операция должна поднять исключение.

## 05. Конкретный отказ через `pytest.raises`

**Начать со знакомого:** `raise ValueError` означает «отказать в операции из-за неверного значения». В тесте этот отказ может быть **ожидаемым правильным поведением**. `pytest.raises(ValueError)` — проверка того, что внутри указанной области кода действительно возник именно `ValueError`. Слово `with` задаёт границы этой области по отступам: после двоеточия идёт один вложенный вызов. Важно до применения объяснить, что импорт `pytest` даёт доступ к `pytest.raises`, а `TaskNotFoundError` — собственный тип ошибки сервиса для допустимого по форме, но отсутствующего id.

**Независимый пример для чтения формы:** `with pytest.raises(ValueError):` и на следующей строке с отступом `int("не число")`. Ученик называет ожидаемый тип и единственную строку, которая должна отказать; сравнить с `int("12")`, когда тест обязан стать красным, потому что исключения нет. Затем перейти к проектному случаю `Task(1, "   ", priority=3)` внутри узкого `pytest.raises(ValueError)` — отказ обязан происходить в конструкторе Task. Для `get_task(999)` с валидным id нужен отдельный `pytest.raises(TaskNotFoundError)`; неверный тип или неположительный id проверяется отдельно по `ValueError`.

**Тонкость отчёта:** если вызываемая строка завершилась без исключения или подняла другой тип, pytest отмечает неуспех. Широкое `try/except Exception: pass` не подходит: оно проглотит также `NameError` и чужие ошибки. В блок `with` не включать подготовку storage, импорт и сразу три вызова: случайный `ValueError` раньше целевого действия дал бы ложный успех. Для `rename("   ")` после узкого блока *снаружи* проверить, что исходный `title` сохранился. Первое самостоятельное действие — различить на двух карточках «ошибка не возникла» и «возникла другая ошибка», выбрать, пройдёт ли `pytest.raises`, и объяснить причину. Переход: сообщения о неуспехе нужно читать так же предметно, как сам договор.

## 06. Читать падение и различать дефект и неверное ожидание

**У отчёта есть три разных стадии.** Pytest сначала ищет тестовые файлы и функции (*обнаружение*), затем Python импортирует нужный код, после чего выполняется тело теста. `collected 0 items` значит, что проверку не нашли; `ModuleNotFoundError` во время collection — что код не удалось импортировать; `FAILED` у строки `assert` — что получили одно значение, а ожидали другое. Только третий случай пока непосредственно говорит о проверяемом поведении. Предложить схему с тремя шагами и вопросом «на каком шаге остановились?».

**Разбор на понятном числе:** тест сравнивает реальное `4` с ожидаемым `5`; сообщение вида `assert 4 == 5` показывает точку несоответствия. Сначала найти имя теста, потом строку `assert`, затем восстановить Arrange и Act: откуда взялось `4`, какое значение разрешает известный договор. Если в тесте опечатка, исправляем ожидание; если договор точно требует 5, ищем ошибку в коде. Не объявлять любой красный тест дефектом Planner и не «лечить» падение удалением `assert`.

**Контролируемый учебный эксперимент:** в одном уже прошедшем тесте Task временно заменить только ожидаемое значение (например, title вместо `"Книга"` ожидать `"Другое"`). Запустить адресно только этот тест, найти реальные/ожидаемые значения в отчёте, устно обосновать верное, вернуть правильное утверждение и проверить снова. Затем запустить весь обнаруженный набор из корня. Различающий перенос — предложить похожее падение в проверке сервиса: `created.title` верен, но `list_tasks()` пуст. Ученик должен назвать, **какое второе наблюдение** доказало нарушение хранения, а не просто сказать «pytest красный».

**Опора для MAIN:** по ходу первых объяснений предусмотрены содержательные прогнозы (`assert`), схема ролей (`AAA`), сравнение копии контейнера и общей Task, разбор узкого `pytest.raises` и мини-отчёт ошибки. Между такими вставками не более двух смысловых абзацев; не ставить соседние карточки с одним и тем же вопросом о термине. Переход: эти навыки понадобятся для собственных тестов вместо копирования готовых ответов.

## 07. Что мы будем делать в практике

**Формат:** самостоятельное изменение существующего проекта Persistent Planner. Источник входа — B 37.2 (готовые объекты и публичный сервис) и B 37.3 (настроенная `.venv`); обе опоры перед реальной выдачей подтверждаются коротким запуском. Ученик сам пишет тестовые функции и ожидания по договору, а наставник показывает только отдельные учебные примеры из разделов 01–06. Ни одного нового метода Planner ради теста; реальные `app` и `data/tasks.json` остаются прежними.

**Список связанных действий → локальных результатов для будущей connected-группы:**

1. **Проверить исходную среду →** `sys.executable` указывает в подготовленную `.venv`, старый Planner запускается, а рабочие данные не меняются. Если нет `.venv` или понимания её выбора — **зависимость от завершения 37.3**, остановить лишь команды установки/запуска тестов и завершить предыдущую подготовку.
2. **Добавить инструмент разработки →** ученик создаёт `requirements-dev.txt`, записывает одну реально проверенную версию pytest, устанавливает её через `.\.venv\Scripts\python.exe -m pip install -r requirements-dev.txt`, сверяет `-m pytest --version`. В README есть обе команды установки/запуска; `git status --ignored` показывает игнорируемую `.venv/`, а `requirements-dev.txt` — обычным файлом проекта.
3. **Написать первый обнаруживаемый тест →** в `tests/test_models.py` ученик оформляет `test_*` с AAA для знакомой Task и одним собственным значимым `assert` (например, очистка *другого*, не разобранного в теории title). Команда выбранного интерпретатора видит минимум один test и показывает `passed`; ученик объясняет, почему имя без `test_` не запускается. Пустой каталог `tests/` не запускаем как доказательство.
4. **Защитить договор Task →** отдельные тесты на допустимые границы priority `1`/`5`, отклонение `0`/`6`, пустое после очистки название и неправильный id, независимость двух списков `tags`, эффект `mark_done` у одной Task и отклонение пустого `rename` без потери прежнего title. Для ожидаемого отказа использовать узкое `pytest.raises(ValueError)`; **после него** проверить состояние. Локальный результат: успешный и ошибочный случаи различимы, нет общего изменяемого объекта между функциями-тестами. Не подменять все случаи одним параметризованным тестом: этому научит 38.1.
5. **Проверить MemoryStorage →** на собственной Task записать начальный список, сделать `load()`, изменить только возвращённый контейнер, снова вызвать `load()` и получить исходную длину. Затем в **отдельном** наблюдении изменить *объект* Task, полученный через `load()`, и увидеть изменённый `is_done` общей Task: это поясняет предел контракта. Дополнительно проверить `save()` на двух разных входных списках, где замена внешнего контейнера после `save` не меняет список внутри. Итог: тесты фиксируют копию списка и общие ссылки, не требуют несуществующего глубокого копирования.
6. **Самостоятельно покрыть публичный PlannerService →** каждый тест создаёт свой `MemoryStorage()` и `PlannerService(storage)` явно. Для `add_task` проверить id, нормализованный title, `is_done=False` и данные повторного `list_tasks`. Для `get_task` — существующий/несуществующий id; для `search_tasks` — регистр запроса и отсутствие совпадений; для `mark_done` — новую завершённость и повторный вызов без дубля; для `delete_task` — отсутствие удалённой, сохранность второй задачи и отсутствие перенумерации; для `get_statistics` — значения `all/open/done` до и после завершения. По каждому изменяющему действию указать возвращённый результат и независимое наблюдение состояния. Отдельными тестами неверный ввод сервиса должен поднимать `ValueError`, неизвестный **корректный** id — `TaskNotFoundError`; данные после отказа не должны меняться. В тестах использовать методы `service`, не внутреннюю структуру класса и не вывод CLI.
7. **Найти, объяснить и устранить одно контролируемое падение →** намеренно испортить **одно ожидание** в прошедшем тесте, запустить его адресно через `-m pytest tests/test_models.py -q` (или более точное имя теста через `::` после объяснения разделителя), определить имя теста, реальное значение и место `assert`; восстановить правильное ожидание. Затем `.\.venv\Scripts\python.exe -m pytest -q` из корня запускает весь набор, все тесты зелёные; Planner по-прежнему запускается. Не сохранять намеренно красный тест в конечной версии.

**Как шаги доказывают B:** 1–3 подтверждают один и тот же Python и обнаружение первого теста; 4–5 проверяют правила модели и границу копирования памяти; 6 показывает связь действий сервиса с результатом и состоянием; 7 демонстрирует чтение отчёта и повторяемость всех ожиданий. Последний тест не засчитывается за предыдущее проектное действие. Проверять **не только** количество `passed`, но и способность ученика объяснить, какая отдельная ошибка будет поймана каждым тестом.

**Различающие сценарии при приёмке практики:** пустой title должен дать `ValueError`, а допустимый неизвестный id — `TaskNotFoundError`; пустой поиск возвращает `[]`, а неизвестный `get_task` — исключение; очистка загруженного списка оставляет storage полным, а изменение общей Task заметно; успешный `created.title` без появления задачи в `list_tasks` — дефект сохранения. Эти пары нельзя слить в одно расплывчатое «работает».

**Передача в 38.1:** тесты с явными Arrange/Act/Assert уже проходят, но подготовка `storage = MemoryStorage(); service = PlannerService(storage)` повторяется. Это наблюдаемая причина изучать свежие fixtures и таблицы параметров **позже**. `JsonStorage`/файловые сценарии и `tmp_path` остаются занятию 39, проверка CLI — 39.2. Не переносить туда незавершённые обязательные договоры текущего урока.
