## 00. Вступление

До сих пор JSON-путь и операции работали со словарями, а подготовленная Task существовала рядом как модель одной задачи. Теперь нужно соединить их так, чтобы объект стал внутренней формой данных, а сохранение продолжило работать.

1. **Точка старта:** есть проверенный функциональный Planner на словарях и отдельно подготовленная `Task` с методами и конвертерами.
2. **Новый вопрос:** как заменить внутреннюю форму задачи, не ломая команды и сохранённые данные?
3. **Результат:** все прикладные операции работают с `Task`, а JSON остаётся совместимой внешней границей.

Дальше проследим не только замену `record["title"]` на атрибут объекта, но и обязанности разных частей программы: модель описывает одну задачу, операции работают с набором, файловые функции переводят данные через границу.

## 01. Две формы одной задачи и смысл объектной модели

- **Что и зачем:** у словаря и экземпляра `Task` могут быть одинаковые значения `id`, `title`, `priority`, `is_done`, но разные обязанности. Словарь — удобная форма записи для JSON; экземпляр — объект с атрибутами и уже подготовленными методами изменения. Аналогия: заполненная карточка при передаче между отделами и сотрудник, который выполняет действие по этой карточке. Граница аналогии: объект не «работает сам», метод вызывает программа.
- **Форма и порядок:** сначала показать независимую карточку книги: `{"title": "Атлас", "is_read": False}` и атрибуты заранее созданного `Book`. Объяснить разницу между чтением `record["title"]` и `book.title`, между изменением поля вручную и вызовом метода со своей проверкой. Затем сопоставить четыре обязательных поля Task и дополнительный `tags`. Объяснить: Python-объект нельзя напрямую передать `json.dump` как встроенный dict; для этого уже существуют `to_dict`/`from_dict`.
- **Первое действие после объяснения:** дать книгу и её словарную запись с одинаковым названием; ученик определяет, какое выражение прочитает название из каждой формы, предсказывает, какая форма пригодна для JSON без конвертера, и объясняет почему. Проверяем объяснение роли, а не запоминание названий методов.
- **Частая ошибка / опора для возврата:** замена `record["title"]` на `task.title` только в одном месте оставляет несовместимые потребители. Сам факт наличия точки не доказывает объектной модели; Task отвечает за одну задачу, а не за файл или список всех задач. Вернуться к двум ролям «внутри приложения / на границе файла».
- **Как подать в MAIN:** после объяснения — короткий прогноз по двум формам записи, затем схема «приложение ↔ граница JSON» с подписью обязанностей; схема дополняет вывод, не повторяет вопрос. Теперь можно пройти сквозной путь объекта.

## 02. Путь задачи: из JSON в объект и обратно

- **Что и зачем:** один и тот же пользовательский результат может пройти через разные формы данных. Файл хранит текст JSON; после `json.load` мы получаем встроенные списки/словари; только затем вызываем конвертер для создания Task. При сохранении путь обратный, объект не записывается в файл напрямую.
- **Механизм по шагам:** `файл JSON → список dict → проверка каждого значения и снимка целиком → Task.from_dict для каждой записи → список Task → операция/показ → Task.to_dict для каждого объекта → список dict → файл JSON`. Объяснить смысл возвращаемого `list[Task]` при load и аргумента `list[Task]` при save (обозначение уже подготовленных типов), отдельно от *внутреннего* словарного формата JSON.
- **Независимый пример:** у библиотеки одна карточка книги сначала лежит в JSON как запись, в приложении становится объектом, метод меняет `is_read`, а при сохранении появляется новый словарь с `is_read=True`. Предложить ученику расставить четыре состояния «текст файла / словарь / объект / словарь» в верном порядке и объяснить, на каком этапе произошла перемена флага.
- **Первое действие:** ученик предсказывает, что в памяти изменится после `mark_done`, что останется на диске *до вызова save* и что сохранится после вызова. Проверка — правильный порядок состояний; неверное утверждение «метод сам сохраняет файл» разбирается до проекта.
- **Путаница / опора:** `to_dict` не заменяется `str`, `repr` или `__dict__`: представление для отладки и явный контракт хранения различаются. Полезна схема «передача посылки»: внутренний объект не путешествует по файлу; передаётся его согласованная запись. Аналогия заканчивается на границе сериализации. Следом надо найти все существующие места, ожидающие dict.

## 03. Потребители словаря и согласованная замена

- **Что и зачем:** если `add` кладёт в список Task, а `find_task` продолжает читать `item["id"]`, часть команд упадёт при первом обращении к новому объекту. Один рабочий список должен содержать Task, и все его потребители должны знать новый договор.
- **Поиск по коду:** в существующих `app.models`, `app.services`/модуле с функциональными операциями, `app.cli`, `app.storage` найти создание записи, `get_next_id`, поиск `id`, `mark_done`, поиск по `title`, подсчёт `all/open/done`, форматирование и функциональные `load_tasks`/`save_tasks`. Пути сверить с реальным деревом ученика; `app.services` и названия функций не выдумывать как уже существующие. Таблица в объяснении: **было** `list[dict]` и доступ `item["priority"]` → **станет** `list[Task]` и `item.priority`; **не меняется** смысл приоритета и пользовательской команды.
- **Независимое наблюдение:** для двух карточек книги одна операция уже создаёт `Book`, другая всё ещё вызывает `row["title"]`. Ученик предсказывает место и причину ошибки, затем отмечает оставшегося потребителя без переписывания всей программы.
- **Первое действие:** на короткой схеме функций Planner ученик сам отмечает, какие вызываются при `add → list` и при `done → stats`, и где ещё может остаться словарный доступ. Критерий — обе цепочки достигают форматирования/вычисления, а не только создания объекта.
- **Опора / переход:** общий договор входов/выходов меняется согласованно; нельзя чинить ошибку созданием второй коллекции или преобразованием «как получится» внутри каждой команды. После описи отделить методы одной модели от функций над списком.

## 04. Действия одной Task и операции над набором

- **Что и зачем:** метод `Task.mark_done()` меняет состояние одной найденной задачи; функция поиска должна сначала найти нужный объект среди многих. Как один товар знает свой статус, но не знает весь склад, так и Task не отвечает за поиск по чужим id.
- **Механизм и запись:** старый обход `for task in tasks` и условия сохраняют смысл; для данных используем `task.id`, `task.title`, `task.priority`, `task.is_done`. При успешном завершении вызываем уже подготовленный метод вместо независимого изменения `is_done`. Для создания передаём проверенные значения в конструктор Task и вычисленный по прежнему правилу `id` (следующий после максимального, а не `len(tasks)+1`); загрузка старой задачи **не выдаёт ей новый id**. Если в текущей версии методы/имена отличаются, используем реально подготовленный контракт.
- **Независимый пример:** список книг, где `Book.mark_read()` меняет только одну выбранную книгу, а функция `find_book` перебирает коллекцию. Ученик определяет, где нужен `self`, а где `for`, и предсказывает эффект на второй книге без написания кода Planner.
- **Первое действие:** два объекта с разными id, завершён только один. Ученик объясняет, какой объект вернёт поиск, почему статистика пересчитывается по обоим, а повторное завершение не должно превращать `False` обратно в `True` или менять id.
- **Путаница / опора:** «ООП = перенести все функции в класс» — неверно. `PlannerService`, объект storage и delete принадлежат следующим занятиям; здесь остаются рабочие функциональные операции. После них требуется обновить единственный файловый путь.

## 05. Проверенная граница JSON и совместимость записей

- **Два масштаба проверки:** `Task.from_dict` восстанавливает *одну* допустимую запись по прежним правилам модели; проверка полного JSON-снимка удостоверяет *весь список*: корень является списком, записи допустимы и `id` не повторяются. Конвертер не может увидеть дубли у двух соседних записей. Ошибка одного элемента не должна превращаться в «загрузили только хорошие».
- **Совместимость на конкретных данных:** старая полная запись содержит ровно обязательные `id/title/priority/is_done`, поэтому отсутствие `tags` допустимо и создаёт **отдельный** пустой список. Новая запись содержит те же поля плюс `tags`, которые сохраняются в JSON через `to_dict` и не разделяют один изменяемый список между объектами. Пустой список задач `[]` — корректный пустой снимок; отсутствие обязательного `id`, дублирующийся id, `is_done=1` вместо bool, неверный тип `tags` и повреждённый JSON — разные причины отклонения.
- **Независимое наблюдение:** в библиотечном каталоге каждая книга по отдельности допустима, но две книги с одним учётным id делают *каталог* недопустимым. Ученик объясняет, почему проверка одной книги не видит конфликт; для двух записей сам находит дублирующийся id.
- **Первое действие:** ученик классифицирует четыре коротких снимка «старый без tags / новый с tags / два одинаковых id / запись без title» как допустимые и недопустимые, называет проверку для каждого. Верное объяснение не подменяет самостоятельную миграцию в практике.
- **Граница и возврат:** новый `from_dict` не должен заново вызывать словарную фабрику с генерацией id и не должен заменять обязательные поля произвольными значениями. Функциональные load/save по-прежнему владеют файлом, преобразование — моделью; отдельный `JsonStorage` появится позже.

## 06. Целостность миграции и передача в 36.1

- **Что и зачем:** итог миграции — ровно один рабочий маршрут `JSON dict ↔ Task внутри приложения`. Пока останется потребитель dict, новая задача может сломать старую команду; пока сохранение пишет объект напрямую, перезапуск не подтвердит B.
- **Порядок объяснения:** сначала на учебной копии данных согласовать создание, функции и показ; затем подключить load/save и пройти перезапуск; *только после этого* убрать заменённую словарную фабрику и обращения по строковым ключам из предметного кода. Удалять только реально неиспользуемое, сохраняя валидаторы, старые команды, ошибки и callback успешного сохранения.
- **Независимое наблюдение:** карточку книги теперь получает и список, и форматтер; однако сохранивший её код должен выпустить dict, а не печатную строку `repr`. Ученик предсказывает: один успешный `list` до перезапуска не доказывает правильного save.
- **Первое действие:** дать три наблюдения «add/list в текущем процессе работает», «после нового запуска исчезли tags», «загрузка с повтором id принята». Ученик называет разные непроверенные звенья: операции, сериализацию, целостность снимка. Для нового поведения использовать отдельный учебный JSON, а не портить единственный рабочий файл.
- **Переход:** в 36.1 готовые файловые функции станут методами `JsonStorage(path)`; это изменение организации хранения, а не повторное знакомство с JSON или добавление новой команды.

## 07. Что мы будем делать в практике

**Формат:** обязательная проектная работа в **существующем Persistent Planner**. Учебный вход — рабочий словарный CLI и файловые `load_tasks`/`save_tasks` из блока 6 плюс одна подготовленная `Task` с методами, `to_dict`/`from_dict` и независимыми `tags` из блока 7. Это **планируемая A**, а не автоматически подтверждённая выдача: перед началом проверить конкретные результаты 30.1, 33.1, 34.1 и цикл старого JSON на фактической версии ученика. Работать на копии JSON; оригинал пользователя не очищать. Технически могут быть даны пути к существующим функциям и примеры записей, **но миграцию всех потребителей и проверки их совместимости ученик делает сам**.

**Общий результат:** один список `Task` на стороне приложения; старый полный JSON читается без изменения id, новый хранит `tags`; при прежних `add/list/find/search/done/stats` и перезапуске сохраняется смысл данных. До практики разобраны формы записи (§01), путь JSON (§02), потребители (§03), разделение обязанностей (§04), правила полного снимка (§05) и миграция (§06). Места для самостоятельной работы, их непосредственные критерии и различающие случаи:

1. **Найти все места, ожидающие dict → получить полную карту замены (§03).** Вход: собственные модули и ранее рабочие команды. Объект: код создания, `get_next_id`, поиска по id/title, завершения, статистики, вывода и `load_tasks`/`save_tasks`; точные имена и расположение установить в текущем проекте. Самостоятельно: пройти два сценария `add → list` и `done → stats`, выписать для каждого вызываемого места «получает/возвращает dict сейчас → должен получать/возвращать Task» и пометить использование строковых ключей. **Проверка на этом шаге:** таблица покрывает создание, чтение, изменение, вывод и IO; ученик может указать, где сломается цепочка, если заменить только add, пока даже не меняя код.
2. **Перевести операции и показ → получить согласованное поведение *в памяти* (§01, §03, §04).** Вход: карта из шага 1 и уже проверенная модель из 34.1; объект — существующие функциональные операции/форматирование, а не новый класс сервиса. Самостоятельно: перевести создание задачи на конструктор Task с прежним правилом нового id; поиск, завершение, поиск по title, статистику и форматтер на атрибуты и подготовленный `mark_done`, согласованно обновить вызовы. **Проверка сразу:** вызвать функции на вручную созданном списке Task: добавление увеличивает количество, поиск существующего id возвращает нужный объект, неизвестного — сохраняет прежний договор отсутствия/ошибки; done меняет одну Task, поиск по title и `all = open + done` продолжают работать. Различающий случай: для учебного списка с id `2` и `5` следующий id равен `6` по прежнему правилу максимума, а не `3` по длине списка. JSON пока не требуется для этой проверки.
3. **Согласовать `load_tasks` и `save_tasks` с новой моделью → сохранить совместимый файловый снимок (§02, §05).** Вход: отдельная копия корректного старого JSON и успешно работающий в памяти список Task из шага 2. Объект: только уже существующие функциональные файловые операции; отдельный `JsonStorage` пока не создавать. Самостоятельно: использовать подготовленные `from_dict` при чтении и `to_dict` при записи, сохранить проверку структуры всего снимка и уникальности id, старые правила ошибок. **Проверка сразу:** загрузка полной старой записи даёт Task с тем же id и индивидуальным пустым `tags`; сохранённый список остаётся JSON-массивом словарей; новая Task с непустыми tags после сохранения/повторной загрузки сохраняет метки. Различающие случаи: пустой корректный `[]` допустим, две записи с одним id и запись без обязательного поля отклоняются **целиком**, а не загружаются частично; испорченный JSON не считается пустой базой.
4. **Удалить заменённую фабрику и dict-доступ → оставить один рабочий путь (§03, §06).** Вход: согласованные функции и файловая граница из шагов 2–3. Объект: фактически найденная старая словарная фабрика и обращения `task["..."]` в предметном коде (JSON-словарь на границе сохраняется). Самостоятельно: проверить её реальные вызовы, заменить оставшихся потребителей, удалить только неиспользуемую фабрику и зависшие импорты; сохранить валидаторы, функциональные load/save и текущий callback успешного изменения. **Проверка сразу:** поиск по собственному предметному коду не показывает обращения к полям Task через строковые ключи и вызовов удалённой фабрики; отдельно объяснить, почему dict внутри конвертера или файлового формата остаётся законным.
5. **Проверить миграцию и перезапуск → доказать B на реальных командах (§02, §05, §06).** Вход: копия данных из шага 3 и текущий CLI с тем же пользовательским меню. Самостоятельно: выполнить `add → list/find/search → done → stats`, выйти и запустить приложение заново на том же учебном файле, сравнить поля, количество, id и статус с ожидаемым; затем отдельно проверить старую четырёхпольную запись, новую запись с tags и отказ на неверном снимке **на другой копии**. **Критерий:** после перезапуска те же задачи с прежними id и изменённым `is_done`, у новых задач сохраняются tags, `all = open + done`; ошибочная запись не приводит к частичной загрузке, потере правильного исходного файла или ложному «успешно сохранено». Повтор `done` не должен разворачивать флаг обратно. Никакой новой команды `delete` нет.

**Связь и возврат к теории:** карта шага 1 ограничивает риск пропустить потребителя; шаг 2 проверяет новую форму *без зависимости от хранения*; шаг 3 впервые замыкает путь через JSON; шаг 4 убирает старый путь только после работоспособной замены; шаг 5 проверяет накопленный результат через новый запуск. Если ошибка проявилась в методе одной Task — вернуться к §04; если в преобразовании или старом снимке — к §02 и §05; если после команды остался словарь — к §03. Этот маршрут передаёт в 36.1 уже действующие функциональные чтение/запись для обёртки в `JsonStorage(path)`, **без** сервиса, delete и нового формата хранения.
