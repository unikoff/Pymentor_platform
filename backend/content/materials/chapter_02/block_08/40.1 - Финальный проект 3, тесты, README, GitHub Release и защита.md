## Границы и передача

- В проекте остаётся **один** `data/tasks.json` на конкретную копию. Не копировать рабочие персональные задачи в проверочный репозиторий; проверочная копия создаёт собственный файл через CLI.
- `Task` хранит правила, `PlannerService` выполняет операции, `MemoryStorage/JsonStorage` исполняют `load/save`, `app.main.build_service(storage=None)` выбирает обычное файловое хранение без запуска меню при импорте. Нельзя обещать транзакционность: при ошибке записи состояние объектов в памяти может остаться изменённым.
- Изоляция проверки: pytest использует `tmp_path`; чистая копия не удаляет и не перемещает рабочую папку. Для тестов и обучения — последовательный доступ; одновременные писатели, атомарная запись и миграции JSON здесь не реализуются.
- Подготовка текста release notes, пояснение тега и защита входят в маршрут. Создание/отправка тега, публикация GitHub Release, push и деплой не требуются для приёмки плана: их можно выполнять отдельно только на проверенной версии и при соответствующем разрешении.

**Ситуация:** Persistent Planner работает у автора. Но новый человек получает только файлы из Git — он не видит уже установленные пакеты, выбранный Python и локальные задачи автора.

Связанная группа для будущей подачи `LinkedNotes variant="connected"`:

1. **Точка старта →** готовый Planner, тесты и сквозной сценарий из 40; их фактическая готовность проверяется перед занятием.
2. **Новый вопрос →** сможет ли другая копия проекта получить тот же работающий результат, если нет нашей `.venv` и `data/tasks.json`?
3. **Результат →** проверяемая инструкция, изолированный запуск и запись точного commit, для которого тесты прошли.

**Пояснение связи:** работа «на моём компьютере» доказывает лишь состояние одной папки; новый человек повторяет действия по инструкции и тем самым выявляет скрытые зависимости. В MAIN дать мини-прогноз: «после копирования только исходников сохранится ли список ваших личных задач?» Затем показать, что код воспроизводим, а пользовательские данные создаются отдельно.

**Опора для возврата:** B проверяет не количество документов, а последовательность `чистая копия → среда → тесты → новый процесс → сохранённые данные`.

## 01. Отделяем код, зависимости и личные данные

**Зачем:** новичку трудно понять, почему часть файлов надо передать, а часть должна появиться после установки и запуска.

**Объяснения до действий:**

1. **Исходный код** — читаемые файлы приложения, например `app/cli.py` и `app/storage.py`. **Репозиторий** — каталог, историю изменений которого ведёт Git.
2. **Зависимость** — внешний пакет, необходимый для конкретной работы. В этом проекте runtime-код использует стандартную библиотеку Python (она поставляется с Python); **pytest** — внешний пакет для разработки и запуска тестов, его версия/установка фиксируется в `requirements-dev.txt`. Если файл зависимостей фактически отличается, сперва сверить его с работающей средой, а не объявлять лишние пакеты обязательными.
3. **Виртуальное окружение** `.venv` — отдельный Python с установленными пакетами для этой копии. **Интерпретатор** — программа, которая исполняет Python-код. Выбранный Python и Python, которому `pip` ставит пакеты, должны относиться к одной среде.
4. **Пользовательские данные** — задачи в `data/tasks.json`. Они создаются во время работы, не нужны как чужой готовый файл. Отсутствие файла при первом запуске означает пустой набор; файл с неправильным JSON уже означает ошибку чтения, которую нельзя выдавать за новый пустой набор.

**Независимый пример:** проект записной книжки состоит из `notes.py` (код), `requirements-dev.txt` с тестовым пакетом (зависимость) и личного `notes.json` (данные). Предсказать, какие файлы получит человек после клонирования репозитория без личных данных. Затем разобрать, почему удаление `.venv` из копии не удаляет код.

**Первое действие:** на подготовленной **учебной** папке ученик сам распределяет шесть имён (`main.py`, `test_notes.py`, `notes.json`, `.venv/`, `requirements-dev.txt`, `README.md`) по ролям и объясняет, почему локальные данные не являются зависимостью. **Критерий:** различает код/инструкцию/зависимости/данные и знает, что окружение создаётся заново. **Крайний случай:** испорченный `notes.json` не становится «отсутствующим файлом».

**Короткая опора:** «создать среду» не значит «скопировать каталог `.venv`». В практической работе проверить, что `.venv/` и реальный `data/tasks.json` не попадают в отслеживаемые файлы Git.

## 02. README как инструкция, которую можно исполнить

**Зачем:** README — текст в корне репозитория, по которому новый человек понимает назначение программы и повторяет её запуск. Недостаточно перечислить файлы.

**Порядок объяснения и будущего README:**

1. Коротко: «консольный список задач» и реально поддерживаемые add/list/get/search/done/delete/stats/exit (уточнить названия команд у существующего CLI; внутренние имена методов не выдавать за команды).
2. Требуемая версия Python, запуск из **корня репозитория** (папки, содержащей `app/` и `tests/`), создание локальной `.venv`, выбор **её** интерпретатора в терминале/VS Code.
3. Установка из действительного списка dev-зависимостей: в PowerShell пример `python -m venv .venv`, затем `.\.venv\Scripts\python.exe -m pip install -r requirements-dev.txt`. На другой ОС нужен собственный путь к Python среды; не копировать PowerShell-команду вслепую.
4. Проверка Python и пакетов той же среды: `.\.venv\Scripts\python.exe -c "import sys; print(sys.executable)"`; затем `.\.venv\Scripts\python.exe -m pytest`. `-m` просит выбранный Python выполнить модуль; это предотвращает запуск pytest из другого окружения. Проверить, что пакет установлен через тот же Python, если возник `No module named pytest`.
5. Запуск приложения из корня: `.\.venv\Scripts\python.exe -m app.main`. Команды CLI ученик вводит **после появления меню**, а не набирает как отдельные команды PowerShell.
6. Где создаётся файл и что наблюдать: при первом запуске список пуст; после добавления и завершения задачи новый процесс восстанавливает данные из **своего** `data/tasks.json`.
7. Ошибки и ограничения: неверное значение задачи, неизвестный id, ошибка хранения, отсутствие атомарной/конкурентной записи; различать ожидаемое сообщение от случая, когда tests падают.

**Независимый пример:** в README учебной утилиты `calculator` написано «запустите `python main.py`», хотя файл лежит внутри пакета `tool/main.py` и импортируется как модуль. Ученик по предоставленному дереву сам выбирает команду запуска из корня и объясняет, как проверить её на новой папке; после проверки сравнивает с реальной структурой Planner.

**Типовая путаница:** команда сработала из личной папки разработчика из-за её текущего Python или сохранённого файла. Это не проверка README. Перед будущей практикой ученик объясняет роль рабочего каталога, выбранного интерпретатора и списка зависимостей. В MAIN дать короткое упражнение на прогноз, какой Python запустится при явном пути `.venv`.

**Опора для возврата:** каждая строка README = действие нового человека + видимый эффект; в инструкции не должны быть абсолютные пользовательские пути, чужая база задач и обещания будущих возможностей.

## 03. Объясняем архитектуру на одном действии

**Зачем:** инструкции запуска недостаточно для разработчика, который будет расширять приложение. **Архитектура** здесь — способ разделить обязанности между частями кода.

**Последовательность, которую нужно объяснить до защиты:**

~~~text
человек вводит команду
        ↓
app/cli.py: прочитать, проверить форму ввода, показать ответ
        ↓
PlannerService: выбрать предметное действие
        ↓
storage.load(): получить список Task из JsonStorage
        ↓
Task: проверить правила, изменить состояние при необходимости
        ↓
storage.save(tasks): сохранить успешное изменение
        ↓
JsonStorage: data/tasks.json (обычный запуск)
~~~

Для операций чтения, например `list_tasks()`, путь заканчивается после `load()`: **`save()` не вызывается**, поскольку состояние не менялось. `build_service(storage=None)` в `app/main.py` — **сборка зависимости**: без аргумента подключается JsonStorage; с переданным объектом можно использовать MemoryStorage. **Договор** хранения — одинаковые способы `load() → list[Task]` и `save(tasks)`, а не общий родительский класс. Тонкий CLI не держит собственную «вторую базу» и не открывает JSON сам.

**Разбираемый независимый пример:** библиотечный каталог: окно выдачи принимает просьбу посетителя, сотрудник решает, какую книгу выдать, карточка книги знает её состояние, архив хранит записи. В MAIN дать схему с пустыми подписями и попросить подписать обязанности. Лишь потом соотнести с файлами Planner.

**Самостоятельный первый опыт:** дать четыре утверждения («CLI форматирует сообщение», «Task открывает файл», «сервис выбирает JsonStorage внутри каждой команды», «main может получить готовый storage») и попросить обосновать, какие согласуются с текущим договором. **Критерий:** правильно размещены роли, а для ложных утверждений назван слой-владелец. **Различающий случай:** замена JsonStorage на MemoryStorage должна менять способ хранения, но не реализацию `add_task`.

**Ограничения для объяснения:** `tags` — независимые списки разных Task; копия списка MemoryStorage не копирует сами Task, поэтому изменения общего объекта возможны без вызова `save`; запись через обычное открытие JSON не обеспечивает атомарного сохранения и не гарантирует откат при ошибке.

**Опора для возврата:** `CLI = разговор`, `Service = действие`, `Task = правила`, `Storage = загрузить/сохранить`, `main = соединить`.

## 04. Чистая копия: повторяемое доказательство

**Зачем:** в занятии 40 новое построение сервиса с тем же путём проверяло загрузку. Здесь нужна **отдельная копия Git и новый процесс Python**, чтобы исключить скрытые локальные файлы автора.

**Объяснения механизма:**

- **Коммит (commit)** — сохранённое состояние исходников в истории Git; `git rev-parse HEAD` показывает его идентификатор (SHA). **Рабочие изменения** — правки, ещё не попавшие в выбранный коммит; команда `git status --short` показывает их. Если README изменён, его надо проверить и включить в проверяемый коммит прежде, чем утверждать, что clone его воспроизводит.
- **Клонирование (clone)** — создание ещё одной рабочей копии репозитория с его Git-историей. Локальная копия в **другом каталоге** подходит для проверки коммита без публикации; удалённый clone требует, чтобы нужный коммит существовал в удалённом источнике. Привязать проверку к записанному SHA, иначе случайно проверяется другая версия.
- **Чистая копия** — копия без перенесённых `.venv` и персонального `data/tasks.json`. Учебный JSON создаётся в **этой** папке через CLI. Проверка есть только тогда, когда команды README реально выполнены в ней.
- **Процесс** — отдельный запуск Python. Выход из CLI завершает первый процесс. Новый вызов `python -m app.main` начинает второй; сохранённая Task должна быть прочитана с диска. Это сильнее, чем создать новый объект внутри прежнего Python.
- Тесты pytest, использующие `tmp_path`, работают со **своей временной директорией**, а не с рабочим `data/tasks.json`. Импорт `import app.main` не должен запускать меню, читать stdin или записывать файл.

**Независимый пример:** у учебного калькулятора меняют README, но забывают добавить изменение в commit. Clone конкретного старого SHA не содержит новой команды; ученик прогнозирует это по `git status --short` и называет способ получить воспроизводимую версию. Это готовит проверку, не подсказывая текст итогового README.

**Первое самостоятельное применение:** на предоставленном условном журнале Git ученик выбирает, какой SHA надо проверить после правки инструкции, и объясняет разницу «мой экран показывает новое» и «в проверочной копии есть это изменение». **Критерий:** версия включает инструкцию и код, `HEAD` совпадает с проверяемым SHA. **Различающий случай:** успешный clone старого SHA без новых инструкций не считается успехом.

**Опора для возврата:** `записанный SHA → отдельная папка → новое окружение → pytest → два процесса`. Не путать отсутствие рабочего JSON с повреждённым: повреждение проверяется только на отдельной копии данных, а не «лечится» удалением личных задач.

## 05. Ошибка при воспроизведении: где искать причину

**Зачем:** новичок должен уметь определить, какой шаг не сработал, прежде чем менять программу или объявлять готовность.

**Разобрать по очереди:**

1. `No module named pytest`: выбран Python без установленного pytest; проверить `sys.executable` и выполнить `<тот же Python> -m pip install -r requirements-dev.txt`. Ошибка установки и падение конкретного теста имеют разные причины.
2. `No module named app`: команда часто запущена не из корня репозитория или структура проекта отличается от README; проверить текущую папку и точный путь `app/`, не переписывать импорты без диагноза.
3. Пустой список задач в чистой копии: при **отсутствии** JSON это ожидаемый первый запуск. Пустой список после второго процесса с уже созданной задачей означает сбой маршрута сохранения либо неверную копию/путь — это причина для исследования.
4. Повреждённый JSON: если файл существует и не разбирается, ожидается `StorageError` либо предусмотренное CLI сообщение о проблеме, **не** успешный пустой список. Эксперимент проводить только над **копией** данных.
5. Тест проходит, а новый процесс не видит задачу: тесты могли проверять не тот путь; сверить `data/tasks.json` именно в проверочной копии и поведение обычного `build_service()`.

**Независимый пример:** в учебной инструкции тесты успешно запускаются из каталога `src/`, но из чистого корня команда не находит модуль. Ученик исправляет *инструкцию* либо подтверждённую структуру запуска, сравнивает результат, а не копирует случайную команду без объяснения.

**Самостоятельное применение:** дать два диагностических сообщения (`No module named pytest` и «данные не восстановились после нового запуска») и предложить разные первые проверки. **Критерий:** не пытается лечить обе проблемы переустановкой Python и не перезаписывает повреждённый файл. **Крайний случай:** `StorageError` означает остановить опасное сохранение, сохранить исходный файл и разбираться с копией.

**Опора для возврата:** записывать «команда → фактический результат → ожидание → причина/исправление → повтор»; у исправления есть узкая проверка.

## 06. Проверенная версия, tag и GitHub Release

**Зачем:** одна фраза «всё работает» не указывает, какая именно версия проверена. Git фиксирует состояние, которое можно назвать и передать другому человеку.

**Объяснить термины до использования:**

- **Commit** — одна зафиксированная версия файлов Git с SHA. Она должна включать актуальные README и список зависимостей; перед фиксацией ученик просматривает изменённые файлы, исключая `.venv`, кэши, секреты и личный JSON.
- **Tag (тег)** — отдельное имя, указывающее на конкретный commit, например `v1.0.0`; тег **не запускает тесты** и не исправляет код. До создания/отправки тега надо знать SHA, который прошёл чистую проверку.
- **GitHub Release** — опубликованная страница с описанием версии, обычно связанная с тегом. **Release notes** — короткий текст: что умеет версия, как запускать, какие проверки пройдены, что ограничено. Release не равен **деплою**: публикация исходников/описания не запускает службу на сервере.
- **Воспроизводимая версия** означает: у другого человека совпадает SHA, есть инструкция и повторены наблюдения. Красивый тег без этой цепочки ничего не доказывает.

**Независимый пример:** у небольшого `todo-list` есть коммиты A и B, но тестировали A, а тег случайно указывает на B. Ученик решает, можно ли честно назвать тег проверенным. **Критерий:** умеет сверить ссылку тега и записанный SHA. **Граничный случай:** после проверки изменился README — надо создать и проверить соответствующую новую версию, а не считать старый отчёт доказательством новых файлов.

**Первое применение:** ученик сам формулирует три строки черновика release notes («возможности», «как проверить», «ограничение») и указывает, где поставить проверенный SHA; в MAIN не давать готовое описание Planner. **Критерий:** notes не обещают HTTP или надёжную конкурентную запись, не включают личные данные.

**Опора для возврата:** `проверка коммита → соответствующий tag → описание Release`. Создание локального тега и публикация на GitHub необязательны для B этого занятия; ничто не публикуется автоматически.

## 07. Короткая защита на проверяемом пути

**Зачем:** объяснение проекта показывает владение результатом, когда автор может связать действия пользователя с конкретными компонентами и ограничениями без чтения кода по строкам.

**Подготовка 5-минутной защиты:**

1. Назначение Planner и подтверждённый SHA; показ исходной копии без личного JSON.
2. Добавить задачу через CLI, отметить выполненной и выйти; показать второй процесс с прежней задачей. Назвать, какой файл этой копии хранит данные.
3. Провести взглядом по цепочке `CLI → PlannerService → Task → JsonStorage`; объяснить, что `build_service` выбирает хранилище и почему можно подставить MemoryStorage.
4. Показать команду pytest и назвать **один защищаемый риск**, например потерю данных после перезапуска; не сочинять новый тест текущего занятия.
5. Показать README, версию, одно ограничение (последовательный доступ/неатомарная запись) и чем будущий Release отличается от работающего сервера.

**Независимый пример:** ученик объясняет другу, почему инструкция для настольного приложения должна включать запуск, а отчёт об ошибках — не скрывать повреждение файла. После объяснения предложить самостоятельно перестроить аналогичный рассказ для Planner.

**Критерий объяснения:** ученик отвечает на вопросы «почему тесты не пишут в мой JSON?», «почему два процесса сильнее двух объектов?», «почему MemoryStorage не гарантирует копии самих Task?» своими словами и показывает соответствующее наблюдение.

**Опора для возврата:** на защите достаточно **одного** достоверного пользовательского пути, подтверждённых тестов и честного ограничения. Нет требования демонстрировать каждый метод.

## 08. Что мы будем делать в практике

**Формат:** проект, самостоятельная работа с тем же репозиторием Persistent Planner. Входом служит **планируемая B занятия 40**, предварительно подтверждённая его сценариями и тестами 38–39.2. Уже есть код Planner, `app/`, `tests/`, Git-история, `requirements-dev.txt` и работающая локальная среда — каждое наличие проверить до выдачи. Никаких новых пользовательских возможностей, второго приложения, обязательной матрицы рисков, `docs/test-matrix.md` или переписывания тестов.

**Связанная последовательность для MAIN (`LinkedNotes variant="connected"`):**

1. **Уточнить README и зависимости →** новый человек получает проверяемые команды создания среды, установки, тестов и CLI без личных путей (разделы 01–02).
2. **Показать архитектуру и ограничения →** видно, кто отвечает за данные, команды, правила и ошибки; не обещана невозможная транзакционность (раздел 03).
3. **Зафиксировать проверяемую версию →** записанный SHA содержит актуальные исходники, README и dev-зависимости, но не рабочий JSON (разделы 04 и 06).
4. **Проверить отдельную чистую копию →** pytest проходит из заново установленной `.venv`, безопасный импорт не вызывает меню (разделы 02, 04–05).
5. **Проверить два запуска CLI →** задача, созданная в первом процессе, с прежним id и статусом видна во втором; в копии используется собственный JSON (разделы 03–05).
6. **Описать версию и защитить её →** черновик Release связан с проверенным SHA, ученик объясняет цепочку данных и одно ограничение (разделы 06–07).

**Почему шаги связаны:** пока README не проверен, новый человек не может повторить команды; пока SHA не включает README, clone проверяет другую версию; пока нет отдельного процесса, нельзя доказать воспроизведение хранения. Каждый шаг имеет **свой** локальный результат и может быть проверен до следующего. Если исходная тестовая база отсутствует, это незакрытая A, а не повод дописать её впервые здесь.

### Подробный договор обязательных самостоятельных действий

**Шаг 1. Исправить README по своему коду.** Вход: текущие `app/`, `requirements-dev.txt`, `README.md` (если файла нет, создать в том же репозитории); опора: 01–02, планируемая проверка окружения из 37.3/38. Ученик самостоятельно сравнивает **каждую** команду README с фактической структурой и переписывает отсутствующие/устаревшие инструкции: назначение, версии Python, создание `.venv`, установка pytest из `requirements-dev.txt`, тесты, запуск CLI из корня, поддерживаемые команды, путь JSON, первый запуск и известные ошибки. **Сразу проверить:** локально выполнить инструкции по очереди на текущем коде; ожидаем успешный запуск и pytest, а команда не требует абсолютных путей автора. **Различающий случай:** старый README содержит вызов монолитного `main.py` либо обещает готовый `data/tasks.json` — после правки обе ошибки исчезают. Не переносить личный JSON в документацию.

**Шаг 2. Объяснить архитектуру на фактических файлах.** Вход: действующие `app/models.py`, `services.py`, `storage.py`, `cli.py`, `main.py` и прежняя схема из 03. Ученик **сам** пишет короткую схему/раздел README или `docs/architecture.md` по выбору (отдельный файл необязателен): цепочка команды, метод сервиса, договор `load/save`, обычный путь JSON, вариант с MemoryStorage, роль сборки и ограничения. **Проверить до шага 3:** по схеме можно объяснить одну add-операцию и чтение после нового запуска, а CLI нигде не назначается владельцем файлового хранения. **Различающий случай:** если на схеме `Task` открывает JSON, ученик исправляет направление связи и обосновывает это. Сохранить уже удачную архитектурную схему, если она точна.

**Шаг 3. Выделить воспроизводимый commit.** Вход: проверенные изменения README/схемы и Git из первой главы; опора: 04, 06. Ученик **сам** проверяет `git status --short`, просматривает `git diff`, исключает `.venv`/кэш/секреты/`data/tasks.json` из отслеживаемых файлов, сохраняет в commit только действительно нужные изменения и фиксирует `git rev-parse HEAD`. **Локальный результат:** SHA относится к той версии README и исходников, которая будет клонироваться. **Различающий случай:** README ещё изменён, а коммит старый — шаг не принят; сначала включить согласованные изменения и зафиксировать новый SHA. Если репозиторий уже содержит подходящий проверенный commit и нет новых правок, не требовать пустой фиктивный commit.

**Шаг 4. Повторить инструкции в отдельной копии.** Вход: SHA из шага 3 и **другая папка** (не внутри рабочего проекта); опора: 01, 02, 04, 05. Ученик **сам** клонирует локальный репозиторий в эту папку или получает удалённый clone, **если** проверяемый commit доступен удалённо; сверяет SHA; не переносит свою `.venv`; создаёт новую среду и устанавливает `requirements-dev.txt` по README, запускает `python -m pytest` **через Python среды**. Далее проверяет безопасный `python -c "import app.main"` (без меню и файловых побочных эффектов) и что pytest с `tmp_path` не создал/не изменил обычный `data/tasks.json`. **Локальный результат:** команды и тесты проходят на выбранном SHA, `import` молчит. **Различающий случай:** pytest не найден — показать путь интерпретатора, исправить настройку среды и повторить только сбойную проверку; нельзя объявлять PASS по старому рабочему окружению.

**Шаг 5. Доказать сохранение двумя процессами.** Вход: чистая копия после шага 4, её собственный первый пустой набор; опора: 03–05 и приёмка 40. Ученик **сам** запускает `python -m app.main` через Python новой среды, добавляет две задачи, одну завершает, выходит; отдельно снова запускает ту же команду и проверяет list/find/stats: оба id сохраняются, одна задача выполнена, `all=2, done=1, open=1`. Не менять личный JSON основной папки. **Локальный результат:** второй процесс читает тот же файл своей копии; `all=open+done`, новая Task не создаётся при чтении. **Различающий случай:** при отсутствии файла первый запуск даёт пустой набор, а повреждённый файл на **копии** должен дать ошибку хранения без успешной перезаписи; отдельный отказный эксперимент допустим после успешного контрольного сценария и только на копии данных. Не подменять второй процесс новым объектом в том же запуске.

**Шаг 6. Подготовить передачу и защиту.** Вход: SHA, вывод тестов, демонстрация двух процессов, README и схема; опора: 06–07. Ученик **сам** готовит короткие release notes с названием проверяемого commit, составом возможностей, командой проверки и честными ограничениями; объясняет, куда будет указывать tag и чем GitHub Release отличается от развёртывания. Затем проводит 5-минутную защиту: команда → сервис → модель/storage → файл → новый запуск, плюс одно известное ограничение и доказательство тестами. **Локальный результат:** другой человек может назвать версию и воспроизвести ключевой путь, ответить на вопросы о роли двух storage. **Различающий случай:** notes называют HTTP или безопасную параллельную запись, которой нет, — исправить обещание. Публиковать тег/Release и делать push без отдельной задачи не требуется.

### Проверка итогового B и возвраты к теории

Из README и записанного SHA следует успешная проверка независимой копии. Из `pytest` следует защита прежних компонентов, а из **двух процессов** — восстановление данных пользовательским запуском. Ученик сам показывает эти доказательства и объясняет ошибки без подмены файла. Если один шаг не прошёл, фиксирует фактическую команду, ожидание и место сбоя, возвращается к соответствующему разделу 01–06 и перепроверяет только затронутое, пока итоговая цепь не станет воспроизводимой.

**Дополнительный перенос (необязательно):** дать товарищу только ссылку на нужный commit и README и попросить повторить тесты без устных подсказок. Это усиливает проверку инструкции, но не становится условием перехода в главу 3.

## 09. Самопроверка и переход

Для будущей подачи выбрать несколько **разных по действию** точек проверки, без повторения одинакового True/False:

1. **Прогноз:** почему в чистой копии `data/tasks.json` может отсутствовать и что должен показать первый запуск?
2. **Диагностика:** что проверить первым, если `python -m pytest` пишет `No module named pytest`?
3. **Трассировка:** через какие компоненты проходит команда `done` и кто записывает JSON?
4. **Сравнение:** чем новый экземпляр сервиса из 40 отличается от второго процесса в 40.1?
5. **Обоснование:** как удостовериться, что проверенный SHA действительно содержит исправленный README?
6. **Ограничение:** почему наличие JsonStorage не гарантирует безопасные конкурентные записи и откат?
7. **Версия:** что подтверждает commit, что указывает tag и что публикует GitHub Release?

Критерий передачи: ученик способен **показать** команды и результаты на своей проверочной копии и **объяснить**, почему они относятся к указанному SHA. При неполной тестовой A или проваленном чистом запуске передачу в Planner API не объявляем проверенной; восстанавливаем ровно недостающую опору.
