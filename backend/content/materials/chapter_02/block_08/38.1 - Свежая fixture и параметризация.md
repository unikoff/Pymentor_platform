## 00. Вступление

В первых тестах зависимости создавались рядом с проверяемым действием. Это делало связь заметной, но одинаковая настройка начинает повторяться, а общее состояние может незаметно связать тесты.

1. **Точка старта:** тест сам создаёт `MemoryStorage` и передаёт его в `PlannerService`; Arrange–Act–Assert и предметные проверки уже знакомы.
2. **Новый вопрос:** как убрать повтор подготовки, сохранив каждому тесту собственное состояние, и когда несколько входов стоит проверить одним тестом?
3. **Результат:** подготовка зависимостей станет явной fixture, а связанные варианты одного правила — параметрами без потери самостоятельных проверок.

Эти шаги продолжат работу с уже знакомыми объектами. По ходу занятия ученик проследит, какие экземпляры создаются, кому передаются и почему результат одного теста не должен зависеть от другого.

## 01. Найти повтор, не пряча смысл проверки

- **Сначала определение:** *подготовка теста* (Arrange) создаёт объекты и исходные данные, нужные для проверки; *действие* (Act) вызывает изучаемое поведение; *ожидание* (Assert) сравнивает наблюдение с правилом. Повтор — когда разные тесты заново пишут одинаковый Arrange, например создают пустой `MemoryStorage` и передают его в `PlannerService`. Уменьшать нужно повтор технической сборки, а не явное действие или ожидаемый результат.
- **Независимый пример до проекта:** две короткие проверки обычного списка. В одной создаётся `items = []`, выполняется `items.append("A")` и проверяется `["A"]`; во второй снова создаётся `items = []`, затем проверяется пустота. Ученик отмечает три части каждого сценария и объясняет, почему `append` нельзя спрятать в общую подготовку: для второго сценария список должен остаться пустым. Это показывает различие повторяемой подготовки и уникального Act.
- **Переход к Planner:** поставить рядом два *существующих* теста `PlannerService`, в обоих подчеркнуть создание памяти и сервиса, а разными цветами — проверяемое действие и `assert`. Мини-попытка: ученик сам подписывает, какие две строки можно вынести, а какие нельзя; локальный признак понимания — его выбор сохраняет разные предметные ожидания двух тестов. Здесь ещё не вводить запись fixture.
- **Ошибочное решение:** вынести в общую заготовку уже добавленную задачу — тогда «пустая память» перестанет проверяться. Пояснить, что «сократить тест» и «сохранить его смысл» не одно и то же.
- **Переход:** прежде чем делить подготовку между тестами, надо разобраться, чем опасно передавать им один и тот же изменяемый объект.

## 02. Проследить владение изменяемым состоянием

- **Сначала механизм:** *изменяемый объект* хранит состояние, которое можно изменить без создания нового объекта (список через `append`, `Task` через изменение `is_done`). *Ссылка* — связь имени с объектом: `second = first` не копирует значение, обе переменные указывают на один объект. *Независимость тестов* означает, что изменение данных в одном запуске не влияет на исходные данные другого. В этом уроке не требуется изучать все виды копирования.
- **Наглядность 1 — две таблички у одной коробки:** имена `first` и `second` подписаны на *одной* коробке-списке; если `first.append("A")`, `second` тоже увидит `"A"`. Условие аналогии: речь об одной ссылке на изменяемый объект; два независимо созданных списка не связаны. Первое предсказание: после `first = []; second = first; first.append("A")` ученик называет `second == ["A"]` и объясняет почему.
- **Наглядность 2 — контейнер и вложенный предмет:** показать два *разных* списка `[task]` и `list([task])` с *одной* `Task` внутри. Внешние списки разные, но `is_done` у вложенной Task меняется у обоих наблюдателей. Ученик сначала предсказывает результат изменения `task.is_done`, затем объясняет, почему копия контейнера не создаёт копии Task; не переносить это на произвольный способ реализации `MemoryStorage` без проверки его договора.
- **Проектное различие:** `MemoryStorage` — экземпляр хранилища, внутри/через него доступны контейнер и отдельные `Task`. Общий модульный `service` опасен: тест «добавить задачу» может изменить последующий тест «пустой список»; порядок запуска скрывает причину. Вместо очистки и глубокого копирования каждый тест должен **создать свои** storage и service и добавлять собственные Task.
- **Мини-попытка:** перед показом ответа предложить пары случаев: (а) два теста получают один глобальный `service`, (б) каждый создаёт новый `MemoryStorage`/`PlannerService`. Ученик выбирает случай, в котором добавление в первом не должно появиться во втором, и называет владельца состояния. При ошибке возвращаться к схеме ссылки и проверять на изменённом примере с двумя Task.
- **Переход:** теперь можно показать инструмент pytest, который повторяет такую свежую подготовку при запуске каждого теста.

## 03. Запросить fixture как зависимость теста

- **Определения до записи:** *fixture* — функция подготовки, результат которой pytest по запросу передаёт тесту; *зависимость* здесь — значение, без которого тест не может выполниться (например, пустой список или storage). *Параметр функции* — имя в круглых скобках при определении `def test_...(items):`; когда pytest вызывает тест, он подставляет туда результат fixture. Знакомый `return` передаёт значение обратно, ничего не выводя на экран.
- **Новый синтаксис построчно:** `import pytest` делает доступным пакет; `@pytest.fixture` — декоратор, пометка **следующей** функции, говорящая pytest, что она готовит зависимость; `def items(): return []` создаёт новый список при вызове fixture. В `def test_starts_empty(items): assert items == []` параметр `items` совпадает с именем fixture. Pytest сам вызывает `items()` и передаёт возвращённый список; в тесте **не** нужно писать `items()` и не нужно искать глобальную переменную.
- **Независимый пример для будущего объясняющего блока кода (ещё не задача проекта):**

  ```python
  import pytest

  @pytest.fixture
  def items():
      return []

  def test_add_item(items):
      items.append("A")
      assert items == ["A"]

  def test_empty_at_start(items):
      assert items == []
  ```

  Разобрать цепочку в первом запуске: pytest находит имя `items` в параметрах теста → вызывает функцию с декоратором → получает **новый** список → передаёт его тесту → выполняется `append` и `assert`. Во втором запуске процедура начинается заново, поэтому пустота сохраняется независимо от порядка тестов. Сама fixture не должна выполнять проверяемое `append`.
- **Время жизни:** *scope* (область действия fixture) — на какие тестовые запуски приходится один подготовленный результат; по умолчанию это `function`, то есть один запуск тестовой функции. В пределах одного запуска, если несколько fixtures запрашивают одну и ту же `items`, pytest повторно использует подготовленный для этого запуска результат; в следующем тестовом запуске создаёт новый. Более широкие scopes, `autouse` и `yield` не вводить.
- **Первое самостоятельное действие:** дать короткую заготовку `@pytest.fixture` с пропущенными `def`/`return` и тест с параметром `items`; ученик сам выбирает имя и место возвращаемого значения, затем предсказывает, чем отличаются списки двух тестов. Проверка: каждый тест видит свои данные, а ручного вызова fixture нет. Для ошибки «fixture not found» проверить совпадение имени и область видимости определения.
- **Переход:** одна fixture готовит одно значение; далее такой же запрос позволит собрать целый сервис из подготовленного storage.

## 04. Увидеть композицию объектов в подготовке

- **Сначала известная модель:** `PlannerService(storage)` принимает **экземпляр** хранения, а `MemoryStorage()` создаёт новую память. *Композиция* — сервис работает через переданный ему объект. *Цепочка fixtures* — одна функция подготовки вправе объявить параметр с именем другой fixture; pytest сначала приготовит требуемое для неё значение. Это обычная передача объекта, не новый вид storage и не изменение Planner.
- **Код-схема для последовательного разбора:**

  ```python
  @pytest.fixture
  def memory_storage():
      return MemoryStorage()

  @pytest.fixture
  def service(memory_storage):
      return PlannerService(memory_storage)

  def test_add_task(service, memory_storage):
      created = service.add_task("Python")
      assert created.title == "Python"
      assert [task.title for task in memory_storage.load()] == ["Python"]
  ```

  `test_add_task` запрашивает оба имени. Pytest видит зависимость `service(memory_storage)` и сначала создаёт **один** `MemoryStorage`; передаёт этот экземпляр в `PlannerService`, а тесту передаёт сервис и **тот же** storage. Поэтому тест способен наблюдать результат `add_task` через `memory_storage.load()`. На следующий запуск другого теста будет создана новая пара. Проверка через `load` опирается на изученный договор MemoryStorage, а не на несуществующий глобальный сервис.
- **Наглядная схема/трассировка:** `test_add_task → service → memory_storage → MemoryStorage() → PlannerService(memory_storage) → test_add_task`; стрелки «запрос» и «передача готового объекта» различаются. Ученик без просмотра решения называет порядок вызовов и количество `MemoryStorage` **в одном** тесте, даже когда он запрошен дважды; ожидаемый ответ — один. Затем изменённый пример: два разных теста с теми же именами — два разных экземпляра.
- **Путаница:** `memory_storage` в параметрах не создаёт второе хранилище только потому, что имя встречается и у fixture сервиса, и у теста. Но совместное использование экземпляра **внутри одного теста** не даёт права сделать его общим на весь модуль. Мини-действие: ученик самостоятельно записывает зависимость `service` от `memory_storage` по аналогии с простым `items` из 03, сверяет схему и получает чистое хранилище во втором тесте.
- **Переход:** зная, как создаётся граф объектов, можно безопасно заменить им повторяющийся Arrange в уже написанных проверках.

## 05. Сохранить сценарии при переходе на fixtures

- **Порядок рефакторинга:** *рефакторинг* — изменить организацию кода, сохранив проверяемое поведение. До изменения назвать исходные Act/Assert пары тестов и запустить их; затем вынести **только** `MemoryStorage()` и `PlannerService(memory_storage)` в fixtures (`04`), оставить в тестах имена предметных действий и точные ожидания. После переноса сравнить: успешное добавление/поиск остаются успешными, `TaskNotFoundError` для неизвестного id остаётся отдельным ожидаемым отказом.
- **Независимый контроль:** `test_empty_at_start(items)` из `03` должен остаться зелёным даже после `test_add_item(items)`; для проекта — два отдельных теста с `service`: первый добавляет задачу, второй проверяет пустую начальную память. Нельзя заставлять их проходить лишь в «правильном» порядке. Короткий прогноз: при глобальном `service` второй тест получит чужую запись, с function-scoped fixture — не получит.
- **Граница общего и предметного:** пустое storage — техническая подготовка, а добавление двух задач для конкретного `search_tasks` — **часть сценария поиска** и остаётся видимой в его Arrange. Проверка независимых `tags` также создаёт две **новые** `Task` и изменяет tags у первой; наблюдение «вторая по-прежнему без тегов» доказывает `default_factory` из ранее изученной модели. Fixture сервиса сама по себе не доказывает независимость tags.
- **Первое применение к проекту:** дать один ранее написанный тест с явным Arrange, попросить ученика самостоятельно заменить две строки создания зависимостей на параметр `service`, не копируя готовую финальную функцию. Сравнить до/после проверяемое правило и реально наблюдаемый `assert`; затем аналогично исправить тест с исключением. Опора: `03–04`, при разнице результата вернуть исходный Act/Assert, а не ослаблять ожидание.
- **Переход:** когда setup стал короче, одинаковые по смыслу варианты данных удобнее расположить рядом; нужно различить один договор и несколько разных договоров.

## 06. Параметризовать одно правило

- **Определение:** *параметризация* — один тестовый алгоритм, который pytest запускает **несколько раз** с разными данными. *Случай/строка набора* — один конкретный вход и, когда нужно, его ожидаемый результат. *Правило* — что именно тест доказывает, например «границы priority 1 и 5 допустимы»; объединять разрешено только случаи с общей причиной ожидания. Это другой механизм, чем fixture: fixture готовит зависимость, параметризация меняет значения тестовых входов.
- **Перед синтаксисом — независимый пример:** две проверки `assert 2 % 2 == 0` и `assert 4 % 2 == 0` следуют одному правилу «чётное число при делении на 2 даёт остаток 0». Ученик сам называет изменяемую часть (число) и постоянную (операция и ожидаемое равенство). Затем показать запись:

  ```python
  @pytest.mark.parametrize("number", [2, 4])
  def test_even_numbers(number):
      assert number % 2 == 0
  ```

  Пояснить *декоратор* по аналогии с `@pytest.fixture`, отличие `mark.parametrize` от fixture, строку `"number"` как **имя** параметра `def test_even_numbers(number)`, список `[2, 4]` как **два** значения. Pytest запустит отдельную проверку с `number=2` и затем с `number=4`; не сложит значения в один список внутри теста. Несовпадение имени в декораторе и функции — ошибка сопоставления, а не основание вводить лишний параметр.
- **Два значения на случай:** в `@pytest.mark.parametrize(("query", "expected_titles"), [("python", ["Python"]), ("readme", ["README"])])` кортеж имён `("query", "expected_titles")` описывает два параметра теста, а каждый внутренний кортеж данных задаёт **соответствующую пару** входа и ожидания. Разобрать одну строку до написания собственного теста: `"python"` станет `query`, `["Python"]` — `expected_titles`; оба входят в один вызов функции. Пояснить, почему неверно передать три значения для двух имён и почему fixture `service` — третий параметр функции, но **не** третья колонка набора.
- **Проект: три группы, три договорённости.** (1) `priority=1` и `priority=5` — принимаемые границы, `assert task.priority == priority`; (2) `priority=0` и `priority=6` — отклоняемые значения *того же правила диапазона*, с `pytest.raises(ValueError)`; (3) `query="python"` и `query="readme"` для заранее созданных задач «Python» и «README» — один договор нечувствительного к регистру поиска с парой `query/expected_titles`. Если проверяют также пустой `title` и пробелы, выделить **отдельную** группу ошибки заголовка: причиной будет правило title, а не диапазон priority. Все формы `assert` и `pytest.raises` уже подготовлены в 38.
- **Трассировка двух запусков:** для параметризованного поиска `service` запрашивается отдельно **для каждой строки**: на первом запуске свежие memory/service, подготовлены две Task → поиск «python» → результат «Python»; на втором снова свежие memory/service → поиск «readme» → результат «README». Схема «строка данных → fixture → Arrange → Act → Assert» показывает, что один и тот же тестовый код не означает одно общее изменяемое состояние. Различающий случай: если создать service вне fixture на уровне модуля, накопленные данные могут исказить результат следующей строки.
- **Самостоятельная проба:** предъявить две таблицы: `priority [0, 6]` с единым `ValueError` и смесь «пустой title / неизвестный id». Ученик сам выбирает, что параметризовать, подписывает общий договор и предсказывает количество запусков/состояние fixtures; критерий — выделен набор `[0, 6]`, а два разных отказа остались отдельными тестами. Затем ученик составляет новую пару поисковых данных и ожидаемых названий, не имея готовой полной функции.
- **Переход:** выбранные маленькие таблицы должны подтверждать прежние требования и давать понятную диагностику, а не превращать все проверки Planner в одну универсальную функцию.

## 07. Что мы будем делать в практике

Приведём **существующие in-memory тесты** к свежей подготовке без изменения предметных ожиданий. Это **проектная практика** на тестах Planner, начатых в 38; новый репозиторий, дополнительные классы, CLI-слой или файловую запись здесь не создаём. Входная A — **планируемая**: перед выдачей подтвердить, что ученик сохранил и запускает тесты `Task`, `MemoryStorage`, `PlannerService` из 38. Автор MAIN использует именно файлы этих тестов на данном этапе проекта, а не придумывает им новые пути.

1. **Зафиксируем исходные ожидания (опора 01, 05).** Вход: существующие тесты ученика и их зелёный запуск после 38; объект: тесты добавления и чтения/поиска с явным `MemoryStorage()` и `PlannerService(...)`. Самостоятельно: ученик выписывает для двух разных функций их Arrange, Act, Assert и отмечает повторяющиеся строки сборки, **не** вынося подготовку поисковых записей. Локальный критерий: ясно названы два разных защищаемых правила, старые `assert`/`pytest.raises` остаются на месте, до правки оба теста проходят; при падении сначала восстанавливается исходное B занятия 38. Если фактических исходных тестов нет, выполнение зависимых пунктов останавливается до завершения 38.
2. **Соберём свежую память и сервис (опора 02–04).** Вход: повтор Arrange из пункта 1; объект: те же тестовые файлы, две новые функции fixture. Самостоятельно: ученик пишет `memory_storage` с возвратом **нового** `MemoryStorage` и `service`, принимающую `memory_storage` и создающую `PlannerService`; затем заменяет явную сборку у выбранных тестов на имена параметров. Готовым дан только знакомый импорт pytest и точка вставки, полные тела fixtures ученик пишет сам. Локальный критерий: два теста проходят с теми же ожиданиями, проверка через `service` и `memory_storage` **внутри одного теста** видит одну задачу, соседний тест с `service` начинает с пустой памяти; не используется глобальный общий экземпляр. Различающий случай — после добавления задачи в первом тесте второй всё равно видит пустое хранилище.
3. **Объединим только варианты одного правила (опора 06).** Вход: написанные в 38 проверки `Task`/поиска и новые fixtures из пункта 2; объект: тесты диапазона priority, неверных входов и поиска. Самостоятельно: ученик **выбирает и записывает** `@pytest.mark.parametrize` для двух допустимых границ `1, 5`, отдельно для отклоняемых `0, 6` с `ValueError`, отдельно для нескольких неправильных `title` с одной причиной отказа и для двух регистронезависимых запросов с парами ожидаемых названий. Для поиска самостоятельно оставляет в Arrange добавление известных задач, тест принимает `service`; в таблицу не добавляет сам объект fixture. Локальный критерий: у каждого теста одно названное правило, число запусков равно числу строк, каждая строка даёт ожидаемый `assert` либо `pytest.raises`; `priority=1/5` принят, `0/6` отклонён, «python» и «readme» находят соответствующие задачи. Различающий случай — неверный заголовок **не** объединён с неизвестным id и не требует чужой обработки.
4. **Сохраним отдельные договоры (опора 02, 05–06).** Вход: старые проверки неизвестного id, изменяющих операций и модели `Task`; объект: **их собственные** Arrange–Act–Assert. Самостоятельно: ученик оставляет проверку `TaskNotFoundError` для несуществующего id отдельно от успеха, для изменения статуса отдельно проверяет выбранную и незатронутую Task, а для `tags` создаёт **две новые Task**, добавляет тег первой и проверяет пустой `tags` второй. Локальный критерий: неизвестный id не порождает запись/изменение состояния, изменение выбранной задачи не меняет другую, `tags` не разделяются; старые точные ожидания сохранены, нет общего списка `Task` между тестами. Различающий случай с двумя Task выявляет общее значение по ссылке, которое проверка единственной Task пропустила бы.
5. **Подтвердим порядок и прежнюю функциональность (опора 02–06).** Вход: итоговые тестовые файлы после пунктов 1–4; объект: запуски pytest из корня проекта в той же подготовленной среде, что использована в 38. Самостоятельно: ученик запускает выбранные проверки по одной через `python -m pytest путь_к_файлу::имя_теста` (двойное двоеточие выбирает одну функцию), затем те же проверки вместе и весь прежний набор через `python -m pytest`; сравнивает **результаты сценариев**, а не только число строк кода. Локальный критерий: оба способа запуска зелёные для одних и тех же ожиданий, параметризованные строки проходят каждая отдельно, `test_empty`/аналог остаётся пустым после теста с добавлением; прежние тесты модели, storage и сервиса сохранены. Если запуск падает только вместе — искать общие изменяемые данные, возвращаясь к 02 и 04, без исправления ситуации перестановкой тестов.

**Итог B:** ученик самостоятельно выделил setup в две function-scoped fixtures, сохранил прежние Arrange–Act–Assert и проверяемые отказы, составил небольшие группы однородных вариантов и показал изоляцию при отдельных/общем запусках. Для MAIN важны две содержательные точки контроля: схема «одно storage внутри теста, разные между тестами» и таблица «один договор — несколько входов». Если ученик не может объяснить их на новом случае, возвращаемся к 02–04 или 06, а не предлагаем готовую финальную реализацию. `tmp_path`, JsonStorage и восстановление из файла переходят только к занятию 39.
