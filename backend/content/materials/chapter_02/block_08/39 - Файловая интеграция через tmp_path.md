2. **Новый вопрос:** восстановит ли новый экземпляр приложения те же задачи из JSON и отличит ли повреждённую запись от корректной?

Это продолжение того же Planner: объектная модель остаётся внутри приложения, а проверяемый файловый путь показывает, как её данные проходят через запись и JSON.

## 01. Граница проверки: от вызова к взаимодействию

**Объяснить до кода.** Тест — небольшая проверка обещания программы: подготавливаем вход, выполняем действие и сравниваем наблюдаемый результат с ожиданием. В *unit*-тесте ограничиваем область, например проверяем преобразование `Task.to_dict()` или правило `PlannerService` с `MemoryStorage`. В *интеграционном* тесте оставляем несколько настоящих компонентов работать вместе. «Интеграционный» относится к тому, **что реально взаимодействует**, а не к имени функции или размеру теста.

**Знакомая аналогия.** Проверить, что карандаш пишет, — одна проверка; проверить, что составленный список попал через секретаря в архив и потом прочитан другим сотрудником, — проверка взаимодействия. Для Planner «архив» — JSON-файл, а запись и чтение выполняет `JsonStorage`.

**Проследить две цепочки на доске до практики.**

1. Запись: вызов операции `PlannerService` → передача задач в `JsonStorage` → преобразование объектов `Task` в словари → JSON-текст на диске.
2. Восстановление: существующий JSON-файл → `JsonStorage.load()` → проверка и преобразование словарей в `Task` → **новый** `PlannerService` → наблюдаемая задача через публичный метод.

Проверка `json.loads(...)` показывает лишь, что текст можно разобрать в Python-значение. Даже корректный синтаксис не подтверждает правила `Task`. Вызов сервиса с `MemoryStorage` проверяет действия в памяти, но не доказывает работу файла. Здесь наблюдаем именно завершённый путь «сервис → файл → другой сервис».

**Контрольный вопрос:** если вызвать `PlannerService` с `MemoryStorage`, какая граница останется непроверенной? Ответ: работа `JsonStorage` и файлового ввода-вывода. Чтобы проверка не затронула настоящие задачи пользователя, сначала нужен отдельный путь.

## 02. tmp_path как собственный ресурс теста

**Новый механизм.** `tmp_path` — готовая *fixture* pytest: достаточно объявить одноимённый аргумент у тестовой функции. Pytest передаст в него **свой временный каталог** типа `pathlib.Path`. Это ещё не файл. Выражение `tmp_path / "tasks.json"` собирает путь к будущему файлу внутри каталога, а запись создаёт сам файл. У другого теста будет свой каталог, даже если имя `tasks.json` совпадает. Такое разделение предотвращает зависимость тестов от порядка запуска.

**Безопасная первая проверка, не связанная с Planner:**

```python
def test_can_use_temporary_file(tmp_path):
    path = tmp_path / "notes.txt"  # Path к файлу внутри каталога теста
    assert not path.exists()       # имени файла пока нет на диске

    path.write_text("Привет, pytest", encoding="utf-8")

    assert path.exists()
    assert path.read_text(encoding="utf-8") == "Привет, pytest"
```

Разобрать по строкам: pytest подставил `tmp_path`, оператор `/` соединил части пути, `write_text` создал файл, `read_text` прочитал те же байты как строку. Здесь пока проверяем механизм `Path`; в проекте вместо `write_text` будет работать готовый `JsonStorage(path)`. У двух независимых тестов разные файлы; **внутри одного теста** два экземпляра storage намеренно получают **один и тот же** `path`, чтобы проверить восстановление.

**Ошибка новичка:** использовать `data/tasks.json` проекта «потому что он уже существует» или делить один временный путь между всеми тестами. Это грозит перезаписью данных либо зависимостью от запуска предыдущего теста. Ни чистка рабочей базы, ни переназначение текущей папки не нужны.

**Контрольный вопрос:** создаёт ли выражение `tmp_path / "tasks.json"` файл? Нет, только объект пути. На этом отдельном пути можно безопасно изучить содержимое JSON.

## 03. Запись и схема: что именно пересекает границу

**Разделить три понятия.** `Task` — объект Python с полями и правилами модели; *словарь-запись* — набор значений, пригодный для хранения; **JSON** — текстовый формат, который может представить такой словарь в файле. `Task.to_dict()` и `Task.from_dict()` отвечают за переход между объектом и записью. Кодирование/разбор JSON отвечают за текст. Проверка схемы отвечает за то, подходит ли разобранное значение модели.

Например, JSON-текст `{"id": 7, "title": "Учёба", "priority": 2, "is_done": false, "tags": ["python"]}` синтаксически корректен: `false` — запись логического значения в JSON; после разбора в Python это `False`. В коде Python для объекта `Task` пишем `True`/`False` с заглавной буквы. Если удалить `"id"` или записать `"is_done": "нет"`, JSON по-прежнему разбирается, но запись нарушает ожидаемую схему. Если две задачи в общем снимке имеют одинаковые `id`, каждую можно отдельно разобрать, однако весь набор некорректен.

**Развести обязанности конкретно:**

- `PlannerService` координирует операцию с задачами и момент сохранения; ему не нужно знать синтаксис JSON.
- `JsonStorage` привязан к `Path`, читает/записывает файл и применяет договор корректного файлового снимка.
- `Task` преобразует отдельную задачу `to_dict()/from_dict()` и проверяет поля модели; модель сама не открывает файл.

**Порядок на чтении:** открыли файл → разобрали текст в Python-значение → проверили ожидаемую структуру снимка и идентификаторы → восстановили `Task` → отдали задачи сервису. Не подменять эту работу `str(task)`, `task.__dict__` или одной проверкой `json.loads`: печатаемое представление и невалидируемый словарь не задают договор данных.

**Проверка понимания:** сможет ли корректный `json.loads` обнаружить отсутствие `id`? Нет, это задача проверки схемы. Теперь можно проверить весь круг через независимые объекты.

## 04. Round trip и восстановление новым объектом

**Round trip** («полный круг») — записать данные и восстановить их через реальную границу хранения. Сравниваем **значения**, а не то, один ли это экземпляр Python-объекта. Представим записную книжку: если второй человек увидел ту же запись, это не означает, что ему передали ту же самую память первого человека.

**Демонстрационный каркас** с интерфейсом уже созданного Planner (конкретный метод завершения задачи берётся из готового проекта):

```python
path = tmp_path / "tasks.json"
first = PlannerService(JsonStorage(path))
created = first.add_task("Чтение", priority=4, tags=["pytest"])
# Здесь выполняем готовую операцию сервиса: пометить created как выполненную.

second = PlannerService(JsonStorage(path))  # новые storage и service, прежний Path
restored = second.get_task(created.id)

assert restored.title == "Чтение"
assert restored.priority == 4
assert restored.is_done is True
assert restored.tags == ["pytest"]
```

Смысл каждого действия: `first` работает с файлом в каталоге **этого** теста; изменение статуса выполняется привычным методом сервиса; `second` получает новые экземпляры, но тот же путь к сохранённому файлу. Чтобы подтвердить восстановление, дополнительно сверяем `id` и действия публичного API: список задач, поиск, статистику и следующий свободный идентификатор (на снимке с несколькими разными id). Старый `first`, список из памяти или повторный доступ к `created` для этой проверки не подходят.

**Граница вывода:** это восстановление *внутри одного тестового процесса через файл*, а не проверка запуска отдельного процесса или CLI. Переход к следующему случаю: данные прежних версий не обязаны иметь все нынешние поля.

## 05. Совместимость старой схемы и обязательные поля

**Проблема реальных данных.** Пользователь мог сохранить задачи *до* появления меток `tags`. Старый полный объект содержит четыре поля: `id`, `title`, `priority` и `is_done`. Модель явно допускает **отсутствие только нового поля** `tags`: при восстановлении оно получает новый пустой список. Это совместимость версии данных; поля, от которых зависит идентичность и смысл задачи, нельзя молча придумывать.

**Наглядный пример старой записи:**

```json
[
  {"id": 3, "title": "Позвонить", "priority": 2, "is_done": false}
]
```

Ученик записывает этот текст *только* во временный `tasks.json`. `JsonStorage.load()` должен получить `Task` с `id == 3`, `title == "Позвонить"`, `priority == 2`, `is_done is False` и `tags == []`. Затем в отдельном временном файле убираем, например, `id`. Теперь ожидаем отказ по договору хранения, а не `id = 0`. Аналогично проверяются отсутствие других обязательных полей, недопустимый тип меток и `"tags": null`: явный `null` не равен отсутствию поля.

**Неочевидный случай:** два восстановленных объекта без `tags` не должны разделять один изменяемый список меток. Если добавить метку первому, метки второго остаются пустыми. Так становится наблюдаемой правильная обработка default для изменяемого поля.

**Переход:** совместимость объясняет один разрешённый пропуск; теперь отдельно различаем отсутствующий файл, испорченный текст и ошибочную структуру данных.

## 06. Синтаксическая ошибка, неверная схема и ошибка хранения

**Четыре разных входа — понятные последствия:**

1. Файла пока нет (`path.exists() is False`). Для первого запуска `JsonStorage.load()` по существующему договору возвращает пустой список. Это нормальный старт; пустой результат не означает, что файл прочитали.
2. Файл существует, но его текст сломан (`{сломано`). JSON-парсер не может построить Python-значение. Это ошибка синтаксиса.
3. JSON разбирается, но данные не соответствуют схеме: вместо списка задач словарь, у задачи нет `id`, неверный тип `is_done`, недопустимый статус или повторяющиеся идентификаторы. Это ошибка содержания, и её нельзя исправлять подстановкой молчаливых значений.
4. Вместо пути к файлу передан существующий **каталог**. Синтаксис и схема не при чём: читать каталог как JSON-файл невозможно. Это воспроизводимый ресурсный отказ без изменения системных разрешений.

Во всех трёх случаях с **существующим непригодным источником** внешний договор `JsonStorage` сообщает `StorageError`. Он должен сохранить понятную причину, а не выдавать пустой список: иначе дальнейшая запись может затереть исходные данные.

**Показать, как выглядит проверка сохранности.** Сначала создаём файл с плохим содержимым и запоминаем его текст, затем ожидаем `StorageError` и перечитываем его:

```python
path = tmp_path / "tasks.json"
path.write_text("{сломано", encoding="utf-8")
before = path.read_text(encoding="utf-8")

with pytest.raises(StorageError):
    JsonStorage(path).load()

assert path.read_text(encoding="utf-8") == before
```

`pytest.raises` означает: **тест проходит, только если вызов внутри блока выбросил указанное исключение**. Последнее сравнение отдельно доказывает, что неуспешная загрузка сохранила тестовый файл. Одна проверка исключения не отвечает на вопрос о сохранности содержимого. Не добавлять `except Exception: return []` — он скрывает порчу под «обычную пустоту». Не вызывать `save([])` после ошибки загрузки и не трогать реальный файл пользователя.

**Проверка понимания:** почему отсутствие файла допустимо, а битый существующий файл — нет? Отсутствие может означать первый запуск; существующий испорченный файл содержит данные, потерю которых нельзя скрывать.

## 07. Что подтверждает интеграционный тест

**Связать с известным Arrange–Act–Assert.** Arrange: тест сам создаёт путь и нужные данные (или оставляет путь без файла). Act: вызывает настоящий `JsonStorage`, при round trip — настоящий `PlannerService` и второй комплект объектов. Assert: проверяет конкретные поля восстановленной `Task`, возвращаемые операции или ожидаемый `StorageError` и состояние файла. Нельзя подменять Act самостоятельным вызовом `json.loads`, иначе тест пройдёт мимо нужной интеграции.

**Разделить ответственность проверок.** Round trip подтверждает значения и новый экземпляр, старый формат — допустимое отсутствие `tags`, ошибки — различение отсутствия файла и повреждённых данных, отдельный случай — отказ ресурса. Причины отказа можно параметризовать по уже изученному в 38.1, если для каждой понятны исходные данные и ожидаемый результат; успешное чтение и отказ лучше не смешивать в один тест с условными ветвями.

**Как наблюдаем независимость:** запустить один тест, затем все новые файловые тесты, затем полный pytest-набор. У всех тестов свои `tmp_path`, поэтому порядок исполнения не создаёт скрытых входов; ни один тест не использует `data/tasks.json`. Успешный запуск важен только вместе с предметными `assert`: тест без них может показать зелёный результат, ничего не доказав.

**Переход к практике:** ученик уже знает, зачем нужен путь, что происходит на границе storage, какие варианты JSON допустимы и какой результат проверять в каждой ветке.

## 08. Что мы будем делать в практике

**Формат:** проектная работа в существующем Planner, без нового приложения/CLI/рефакторинга. **Начальные объекты:** готовые `Task`, `JsonStorage`, `PlannerService` и pytest-fixtures из 38.1. Для каждого действия ниже указаны вход, объект, уже объяснённая опора, действие ученика и результат, который можно немедленно проверить.

1. **Первый запуск без файла.** *Вход:* `tmp_path / "tasks.json"`, на диске файла ещё нет. *Объект:* `JsonStorage`. *Опора:* разделы 02 и 06, различие `Path` и файла. *Самостоятельное действие:* написать `test_load_missing_file`, построить путь, проверить его принадлежность каталогу `tmp_path`, вызвать `load()` и проверить `assert tasks == []`. *Локальный результат:* тест отдельно зелёный; начальная загрузка возвращает пустое состояние именно для отсутствующего файла, путь остаётся внутри временного каталога.
2. **Полный круг с новым сервисом.** *Вход:* отдельный путь, задача с названием `"Учёба: тесты"`, ненулевым приоритетом, `tags=["pytest", "файлы"]`; после создания она отмечается выполненной через готовый метод сервиса. *Объекты:* `PlannerService` + `JsonStorage` + `Task`. *Опора:* разделы 01, 03, 04. *Самостоятельное действие:* создать первый сервис, выполнить добавление и завершение задачи; создать **вторые** storage/service на **том же** пути; проверить поля восстановленной задачи, `id`, кириллицу, `is_done is True`, `tags`. Добавить несколько задач с разными id и проверить чтение списка, поиск, статистику и следующий свободный `id` через публичные операции. *Локальный результат:* второй сервис восстанавливает значения и ожидаемые операции из файла, без доступа к памяти первого сервиса.
3. **Совместимость и строгие поля.** *Вход:* вручную записанный в `tmp_path` JSON-массив со старой задачей из четырёх полей, `tags` отсутствует; отдельно вариант без `id`. *Объекты:* `JsonStorage.load()` и восстановленный `Task`. *Опора:* разделы 03 и 05. *Самостоятельное действие:* получить задачу из полной старой записи; проверить четыре поля и `tags == []`, для двух старых задач проверить независимость списков меток; в отдельном тесте убрать обязательный `id` и ожидать `StorageError`. *Локальный результат:* прежние корректные данные доступны, а потеря обязательного поля явно отвергается.
4. **Ошибки, которые нельзя спрятать.** *Вход:* несколько отдельных `tmp_path`: текст `"{сломано"`; валидный JSON с неверной формой снимка, типом `is_done` или другим нарушением схемы; две записи с одним `id`; каталог, переданный как путь файла. *Объект:* реальный `JsonStorage`. *Опора:* разделы 06–07 и `pytest.raises`. *Самостоятельное действие:* сделать явные независимые/параметризованные тесты, для каждого вызвать `load()` под `pytest.raises(StorageError)`; у файловых вариантов сравнить байты или текст с состоянием *до* вызова. *Локальный результат:* каждый отказ наблюдаем как `StorageError`, повреждённый снимок остаётся на месте, содержимое не заменяется `[]`; ресурсный отказ не требует менять права ОС.
5. **Проверка независимости набора.** *Вход:* все созданные файловые тесты и существующие тесты Planner. *Объекты:* pytest и собственные `tmp_path` каждого сценария. *Опора:* разделы 02 и 07, fixtures/параметризация из 38.1. *Самостоятельное действие:* запустить конкретный тест, затем группу файловых тестов и весь проектный pytest; удостовериться по путям тестов и коду, что не открывается `data/tasks.json` приложения. *Локальный результат:* проверки проходят по отдельности и совместно, без изменения пользовательских данных и зависимости от порядка.

**Самопроверка переноса:** без подсказки объяснить, почему два хранилища одного теста делят один `path`, а разные тесты должны получать разные каталоги; почему `json.loads` недостаточно и почему `StorageError` при повреждении защищает данные. Эти объяснения показывают, что ученик понимает механизм, а не только копирует тесты.

В [занятии 38.1](<38.1 - Свежая fixture и параметризация.md>) подготовлены свежие fixtures. Здесь подтверждается файловый путь `Task → запись → файл → восстановленная Task`. В [занятии 39.1](<39.1 - SOLID и проверяемая граница CLI.md>) готовые проверки становятся опорой для работы с границей CLI и сервиса, без повторной постройки файловых сценариев.
