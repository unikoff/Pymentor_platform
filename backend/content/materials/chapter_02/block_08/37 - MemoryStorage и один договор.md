## 00. Вступление

В прошлом шаге мы собрали файловое хранение за узкой объектной границей. Теперь проверим, может ли та же цепочка действий работать с другим объектом хранения, не меняя сами операции.

1. **Точка старта:** операции уже получают `JsonStorage` и используют его `load/save`.
2. **Новый вопрос:** что должна сохранить замена файла на память, чтобы для операций она оставалась тем же storage?
3. **Результат:** добавим `MemoryStorage`, разберём владение списком и задачами и сравним поведение двух вариантов.

Сначала разберём два вызова (`load` и `save`), затем границу между списком и его элементами. Лишь после этого будем менять код Planner.

## 01. Один договор `load/save` без наследования

- **Сначала смысл.** Операции Planner знают два действия: `tasks = storage.load()` возвращает `list[Task]` с текущими задачами; `storage.save(tasks)` принимает итоговый список и заменяет хранимый набор. `save` сам не добавляет одну задачу и не вызывает `mark_done`. Операции решают *что* поменять, storage — *где* хранить.
- **Сопоставление.** `JsonStorage(path)` читает/записывает JSON на диске; `MemoryStorage` хранит список в запущенном процессе. Одинаковые имена без совпадения результата и эффекта бесполезны: вариант, у которого `load()` возвращает `None` или `save()` молча игнорирует вход, не подходит существующим операциям. Оба объекта можно передавать одному клиентскому коду без общего родительского класса.
- **Первая попытка до проекта.** Для простой операции «взять набор, добавить элемент, сохранить» предложить три последовательные команды с `storage`, затем спросить: сломается ли она, если вместо задач `load()` вернёт `None`? Ученик называет нарушенное ожидание, а не угадывает по имени класса. При ошибке записи у файлового storage существующая операция не должна заявлять об успешном сохранении; у памяти нет файловой ошибки.
- **Переход.** Теперь выясним, откуда берётся исходный список памяти и кто может его менять.

## 02. `None`, пустой список и два владельца контейнеров

- **Объяснить до кода.** Вызов `MemoryStorage()` означает «создай пустое хранилище»; `MemoryStorage([])` — «возьми мой явно переданный пустой набор»; `MemoryStorage([task])` — «начни с этой задачи». Проверка `tasks is None` отличает отсутствие аргумента от пустого значения. Запись `tasks=[]` как параметра по умолчанию создала бы один общий изменяемый список между вызовами.
- **Маленький независимый опыт.** На списке номеров: `source = [10]`, `own = list(source)`, затем `source.append(20)`. До запуска ученик предсказывает оба списка: `source` содержит 10 и 20, `own` — только 10. Это объясняет копирование **контейнера** в конструкторе, без новых терминов о задачах.
- **Смысл владельца.** Внешний код может свободно дополнять `source`; storage удерживает собственный контейнер. `None` и `[]` дают одинаковую *начальную длину* 0, но различаются как способ передать аргумент; по одной длине нельзя восстановить намерение вызывающего кода.
- **Проверка понимания.** Спросить, почему `if tasks:` теряет различие отсутствующего аргумента и пустого списка, и предложить поправить условие. Затем перейти от копирования списка к его элементам.

## 03. Два списка могут ссылаться на одну `Task`

- **Наглядная схема до применения:** `операция → MemoryStorage → внутренний список → Task(id=7)`; `load() → новый внешний список → та же Task(id=7)`. Две коробки содержат указатели на одну карточку. Копия коробки не означает копию карточки. Обязательны две разные стрелки к **одному** объекту, иначе визуал ошибочно обещает глубокое копирование.
- **Различающий опыт, сначала прогноз.** На небольшом отдельном классе `Note(title)` сделать `original = [Note('черновик')]`, `other = list(original)`. После `other.append(Note('ещё'))` длина `original` остаётся 1; после `other[0].title = 'готово'` заголовок `original[0]` тоже станет `'готово'`. Сначала объяснить *почему*, затем показать вывод. Этот опыт отделён от будущей практики с `Task`.
- **Перенос на Planner.** `load()` возвращает другую оболочку списка; добавление/удаление элемента результата требует `save()`, чтобы поменять сохранённый *состав*. Но `loaded[0].mark_done()` меняет общий объект `Task` и может быть видно в памяти до `save()`. Обязательно проговорить: **нет глубокой копии, отката и транзакции**. Не обещать, что отсутствие `save()` откатывает любые изменения.
- **Самопроверка.** Дать два действия (`loaded.pop()` и `loaded[0].mark_done()`) и попросить различить, что меняет контейнер, а что объект. Возврат к этой развилке потребуется в практике §06.

## 04. Три границы копирования `MemoryStorage`

- **Конструктор:** сохраняет свою копию входного списка; при `None` создаёт пустой. На **отдельном примере со списком чисел** заранее разобрать синтаксис `__init__(..., items=None)`, проверку `items is not None` и `list(items)`. Ученик позже перенесёт этот механизм на `Task`; полный класс из практики здесь не выдавать.
- **`load()`:** возвращает `list(self._tasks)`, то есть отдельный контейнер. Вызов `loaded.append(...)` сам по себе не изменяет состав внутреннего списка. **`save(tasks)`:** присваивает внутреннему полю `list(tasks)`, а не внешний список напрямую. После `save` последующее `tasks.clear()` не стирает сохранённый состав.
- **Порядок изменения:** получить список → изменить состав → передать результат `save`. Не обращаться к `_tasks` из операций. Показать этот порядок на мини-сценарии с числами, где до `save` длина внутри не меняется, а после `save` меняется. Затем предложить ученику самому восстановить порядок трёх вызовов.
- **Граница:** обе копии — поверхностные. Не добавлять `deepcopy`, наследование или отдельные методы `add_task`: они усложнят договор и исказят изучаемую семантику.

## 05. Проверяем замену storage по результату операций

- **Объяснить до проекта.** Сравнивать нужно одинаковые **исходные значения и действия**, а не устройство хранилища: создание задачи получает тот же id по существующему правилу, поиск по id/названию находит те же записи, `done` меняет `is_done`, статистика считает тот же набор. Для каждого прогона готовить *новые независимые* `Task`; переданная обоим storage одна изменяемая задача исказит сравнение.
- **Два отдельных опыта.** Через `MemoryStorage` выполнить последовательность переходных операций, затем повторить с `JsonStorage` на **отдельном учебном JSON-пути**, сохранив рабочий `data/tasks.json`. На обоих проверить и отказ: неизвестный id не меняет набор; повторный `done` не считается новым изменением; чтение/поиск не инициируют лишний `save` по действующему договору операций.
- **Что не одинаково.** Новый `MemoryStorage()` после завершения процесса не найдёт прежних задач, новый `JsonStorage` с тем же файлом сможет их прочитать. Ошибка диска возможна у JSON-варианта; память не открывает файл. Мутация общего `Task` без `save` может быть видна в памяти раньше, чем на диске. Поэтому сравниваем оговорённые успешные сценарии и ошибки операций, не обещаем одинаковое поведение при любом сбое.
- **Выбор в текущем шаге.** В конкретный запуск переходных операций передать **один** storage; не синхронизировать два набора и не ставить MemoryStorage кешем рядом с JSON. Штатная точка запуска остаётся на `JsonStorage`. Сервисная сборка появится позднее.

## 06. Что мы будем делать в практике

**Формат — проектная практика по паспорту 37.** Вход: версия Planner **после выполненного 36.1**, в которой `Task`, `JsonStorage(path)` и переходные операции с параметром `storage` уже работают. Перед выдачей преподаватель подтверждает эту A; готовый `MemoryStorage` ученику не предоставляем. Рабочий JSON защищаем от экспериментов. Цель — своими изменениями кода получить вторую реализацию договора и доказать её заменяемость.

1. **Создать `MemoryStorage` рядом с `JsonStorage` (§01, §02, §04).** Ученик сам дописывает в `app/storage.py` конструктор, `load()` и `save(tasks)` с копиями списков. Проверяет новый пустой экземпляр, явно переданный `[]` и набор с одной `Task`: `load()` всегда возвращает список правильных объектов, `save()` заменяет весь набор. Стартует с объяснённой формы методов, но без готового класса-решения в задании.
2. **Разделить контейнер и объект (§02–04).** На свежей задаче ученик проверяет *три независимых границы*: после конструктора добавление в **исходный** список не меняет `load()`; после `load()` добавление/удаление в **полученном** списке не меняет состав до `save()`; после `save(tasks)` очистка **переданного** списка не очищает сохранённый состав. Затем берёт свежую общую `Task` и предсказывает результат `mark_done()` через другую ссылку: поле изменилось, хотя `save()` не вызывали. Критерий — ученик объясняет различие изменения длины списка и изменения поля задачи; отсутствие rollback прямо названо.
3. **Сравнить предметные действия на независимых наборах (§01, §05).** Ученик выбирает один `MemoryStorage`, передаёт его **существующим** переходным операциям и выполняет добавление задачи, просмотр/поиск по id, поиск по названию, завершение и статистику. Записывает id, `title`, `priority`, `is_done`, число задач и выполненных. Затем повторяет **ту же последовательность** через `JsonStorage` с отдельным учебным путём и заново созданными `Task` с теми же значениями. Критерий — одинаковые предметные ответы и финальные значения на обоих вариантах, без сравнения внутреннего устройства классов и без записи в рабочий JSON.
4. **Проверить отказ и выбор зависимости (§05).** На обоих прогонах ученик проверяет отсутствующий id, повторное завершение и некорректный ввод через уже существующие проверки операций: состояние и сообщения остаются согласованными, отказ не превращается в успешное изменение. Преподаватель помогает проверить, что чтение/поиск не запускают `save` и что новый успешный `add/done` сохраняется по существующему правилу; счётчик вызовов storage можно обсуждать как способ наблюдения, без создания третьей продуктовой реализации. Затем ученик убеждается, что штатный запуск всё ещё использует `JsonStorage`, и проверяет данные после перезапуска; новый независимый `MemoryStorage` начинает без прежней сессии.

**Итог и перенос.** Ученик объясняет на незнакомом примере, почему `loaded.append(x)` до `save()` и `loaded[0].mark_done()` до `save()` ведут себя по-разному, показывает результаты двух независимых прогонов и называет, почему JSON нужен для перезапуска. Если результат расходится, он возвращается к договору §01, владельцам контейнеров §02–04 или сравнению §05. Это готовит следующий шаг — перенос чтения в `PlannerService` — без преждевременного изменения архитектуры.
