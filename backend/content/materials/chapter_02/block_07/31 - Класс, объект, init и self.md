## 00. Вступление

В Planner уже есть данные задачи и функции, которые с ними работают. Словарь остаётся нормальным представлением задачи; сегодня исследуем, как Python связывает состояние одной сущности с её устройством.

1. **Точка старта:** задача представлена словарём, а функции получают и изменяют данные по договорённости.
2. **Новый вопрос:** что именно задаёт собственный класс и что появляется при его вызове?
3. **Результат:** различить класс и экземпляр, понять, что имя указывает на объект, проследить инициализацию и найти значения в атрибутах.

Эти пункты ведут от уже знакомой записи к механике нового представления. Цель — увидеть, какую связь между полями и поведением может дать класс, не объявляя словари неправильными и не перестраивая Planner.

## 01. Данные задачи и поведение программы

- **Опора:** на примере `task = {"title": "Read", "priority": 2}` ученик называет данные записи и объясняет роль внешней функции `show_task(task)`: функция получает словарь, но связь конкретных полей и допустимых действий существует пока как соглашение между частями программы.
- **Зачем ещё один способ:** класс позволяет описать, какие данные относятся к одной сущности и какие действия могут быть доступны её экземплярам. Это полезно при усложнении модели, но словарь с функциями остаётся корректным выбором для простого случая и действующего Planner.
- **Микродействие перед новой темой:** дать другую запись с теми же ключами; ученик предсказывает, какие значения прочтёт `task["title"]` для каждой. Так фиксируется идея «одинаковое устройство, разное содержимое», которую далее перенесём на экземпляры.
- **Граница:** методы модели, поиск по общему списку, выдача id и сохранение файла пока не вводятся. Дальше описываем один объект, а не весь Planner.

## 02. Класс и отдельный экземпляр

- **Различить три сущности до синтаксиса:** `ReadingCard` — имя класса, то есть общего описания; `ReadingCard("loops", 20)` — выражение вызова класса; `first` — переменная, которая после присваивания ссылается на созданный экземпляр. Класс не является одной готовой карточкой; второй вызов может создать другую карточку с тем же устройством.
- **Первый короткий пример для объяснения**, не подменяющий будущую самостоятельную практику:

  ```python
  class ReadingCard:
      def __init__(self, topic, minutes):
          self.topic = topic
          self.minutes = minutes

  first = ReadingCard("loops", 20)
  second = ReadingCard("files", 35)
  ```

  Ученик называет, какое слово здесь обозначает **описание**, какие два выражения создают **экземпляры**, и почему `first` и `second` ссылаются на разные объекты. Пока не требовать, чтобы ученик самостоятельно написал всю конструкцию: её строки станут понятными в разделах 03–05.
- **Точность термина:** объектом в Python является и обычный список; «экземпляр нашего класса» здесь означает конкретный объект, созданный по `ReadingCard`. Переход: теперь выясним, как у каждого появились свои значения.

## 03. Создание объекта и роль `__init__`

- **Разобрать порядок исполнения на `first`:** Python получает вызов `ReadingCard("loops", 20)`, создаёт экземпляр, вызывает для его начальной настройки `__init__` и связывает входные аргументы с параметрами `topic="loops"`, `minutes=20`. Строки внутри `__init__` выполняются сверху вниз и записывают атрибуты экземпляра. После успешного завершения вызова переменная `first` получает ссылку на объект.
- **Потом повторить на `second`:** вызов с `"files", 35` запускает тот же код с другими аргументами и другим экземпляром; значения первой карточки не заменяются значениями второй.
- **Ограничить смысл:** `__init__` инициализирует уже создаваемый экземпляр и не возвращает его вручную (обычное завершение — `None`). Не объяснять создание как отдельную пользовательскую фабрику и не вводить `__new__`.
- **Вопрос до чтения кода дальше:** что должно быть у `first` после настройки, если `__init__` не получал бы доступ именно к `first`? Ответ подводит к параметру `self`.

## 04. `self` как ссылка на текущий экземпляр

- **Сопоставить заголовок и вызов:** `def __init__(self, topic, minutes)` явно перечисляет три параметра метода, а при `ReadingCard("loops", 20)` ученик передаёт только два аргумента: ссылку на настраиваемый экземпляр Python передаёт в `self` автоматически. `self` — общепринятое имя параметра, не ключевое слово Python и не глобальная переменная.
- **Трассировка-сопоставление:** в первом вызове `self` обозначает экземпляр, который позже доступен через `first`, во втором — экземпляр, который позже доступен через `second`. Имя `self` одно и то же в тексте метода, а получатели присваиваний различны.
- **Промежуточный прогноз:** спросить, изменятся ли поля первого экземпляра после второго вызова. Ученик обосновывает ответ разными ссылками `self`, затем проверяет предсказание чтением через точку в следующем разделе.

## 05. Параметр, атрибут и чтение через точку

- **Два разных места:** справа в `self.topic = topic` стоит параметр `topic`, который получает значение при вызове; слева — атрибут `topic` текущего объекта. Даже при одинаковом названии это не одно место хранения. Параметр нужен во время вызова, а `first.topic` доступен после него благодаря присваиванию через `self`.
- **Проверяемый результат примера:** до запуска ученик предсказывает `first.topic == "loops"`, `first.minutes == 20`, `second.topic == "files"`, `second.minutes == 35`; чтение `first.topic` означает «найти атрибут `topic` у объекта, на который указывает `first`». Сравнить результаты, объяснить неизменность `first` после второго вызова.
- **Различающий случай:** если ошибочно написать `minutes = minutes` вместо `self.minutes = minutes`, строка лишь присвоит значение локальному имени и **не создаст атрибут**. `first.topic` останется доступен, а `first.minutes` вызовет `AttributeError`. Исправление должно менять левую часть на атрибут текущего объекта, а не имя переменной при вызове класса.
- **Переход к самостоятельному действию:** объясняющий класс `ReadingCard` остаётся опорой; в практике ученик создаст другой небольшой класс, сначала предскажет значения и лишь затем проверит.

## 06. Что мы будем делать в практике

**Формат и исходная опора:** короткий опыт в интерпретаторе или редакторе; опираемся на знакомые параметры функций, словарь задачи и чтение значений.

**Вход и объект опыта:** ученик работает в отдельном временном файле или REPL, без импортов из Planner. По примеру разделов 02–05 самостоятельно пишет `class StudySession` с двумя полями: строковым `subject` и целочисленным `minutes`. Их имена и типы заданы, но тело `__init__`, связывание аргументов с атрибутами и выражения проверки ученик составляет сам; готовый код класса из теории нельзя просто скопировать как ответ.

1. **Самостоятельно построить класс:** описать `__init__` с параметрами для двух входных значений и сохранить оба значения у *текущего* экземпляра. Локальный критерий: ученик может указать, где в его строках параметры, где `self` и где атрибуты, и объяснить, почему `self` не передаётся при вызове класса явно.
2. **Создать две сессии и предсказать их состояние:** сделать отдельные вызовы с парами `("Python", 25)` и `("SQL", 40)`; **до исполнения** записать четыре предполагаемых значения `subject`/`minutes` и сопоставить каждый вызов со своим `self`. Локальный критерий: для первого экземпляра ожидаются `"Python", 25`, для второго — `"SQL", 40`.
3. **Проверить прогноз через точку:** прочитать по два атрибута у каждого объекта, сравнить с прогнозом и пояснить, почему второй вызов не перезаписал первый. Дополнительный различающий случай: создать третий экземпляр с `("Git", 10)` и предсказать его поля **без запуска**; сверить. Если всё прочитано верно, ученик объясняет результат передачей двух аргументов и сохранением значений в собственных атрибутах каждого объекта.
4. **Найти и исправить ошибку хранения:** во временной копии изменить только строку сохранения `minutes`, чтобы получилось `minutes = minutes` вместо атрибута. До запуска предсказать, какое чтение останется успешным и какое завершится `AttributeError`; **заново выполнить определение класса и создать новый экземпляр** (старый объект сохранил прежние атрибуты), воспроизвести ошибку, найти причину и исправить **самостоятельно**. После нового запуска обе характеристики снова читаются. Этот опыт не заменять обычной проверкой одного значения: именно отсутствие атрибута отличает ошибочное локальное присваивание от правильного `self.minutes`.
5. **Перенос смысла без изменения проекта:** по словарной задаче `id/title/priority/is_done` назвать, какие четыре поля в перспективе могли бы принадлежать **одному** экземпляру `Task` и чем такая модель отличается от списка задач. Отдельно объяснить, почему сама по себе `Task` не ищет по списку, не назначает новый id и не сохраняет JSON: эти операции пока остаются в других функциях Planner.

**Итоговый критерий B:** ученик без подсказки разделяет «класс — два разных экземпляра — имена-ссылки», устно прослеживает для обоих вызовов путь `аргумент → параметр → self.атрибут → чтение через точку`, объясняет ошибку `AttributeError` и исправляет её. Два нормальных разных набора данных и отсутствующий атрибут подтверждают понимание, а не случайное совпадение вывода.

Пункты практики готовят ровно то, что использует [план 31.1](31.1%20-%20Обычная%20Task%20в%20настоящем%20пакете.md): создавать экземпляр, прослеживать `__init__` и `self`, читать атрибуты и отличать их от локальных имён.
