## 00. Вступление

Подготовленная `Task` уже умеет сохранять и восстанавливать четыре поля через словарь. Теперь у задачи появятся метки, и важно понять не только, как задать их начальное значение, но и кому принадлежит список при создании объекта и преобразовании данных.

1. **Точка старта:** есть одна проверяемая dataclass `Task` с конвертерами и прежними четырьмя полями.
2. **Новый вопрос:** как добавить изменяемый список так, чтобы задачи и записи не делили случайно один контейнер?
3. **Результат:** подготовим независимые `tags` и совместимое чтение старой записи, сохранив действующий четырёхпольный путь приложения.

Далее последовательно зададим смысл меток, разберём создание списка для каждого экземпляра, определим проверку и владение переданными данными, а затем проследим обе границы сериализации. Это позволит развить ту же модель, не переключая прежний Planner раньше времени.

## 01. Что означают tags и какой у них договор

- Начать со знакомой задачи «подготовить доклад»: `tags` указывает темы, к которым она относится; это **список строк**, например `["python", "практика"]`, а не команда поиска и не отдельный объект. Объяснить, что **договор данных** — правило, какие входы допускаются и что получится на выходе; аннотация `list[str]` сама по себе это правило не проверяет.
- Разобрать преобразование **на уровне значений, отдельно от кода Task**: `[" python ", "повтор", "python"]` становится `["python", "повтор", "python"]`. `strip()` убирает пробелы только по краям каждой строки, не меняет регистр, порядок или повторы. `[]` допустим; `"  "` после очистки пустая и потому запрещена; `None`, строка вместо списка и число среди элементов запрещены. Проговорить разницу между «новое поле отсутствует в старой записи» и «поле дано как `None`» до раздела 05.
- **Первое действие:** ученик сам прогнозирует результат для `["  База ", "База", " практика "]` и решает, допустим ли `["ok", " "]`; сверка — порядок и повтор «База» сохраняются, второй список отклоняется. При ошибке вернуться к правилу «сначала `strip()`, затем проверка непустоты», повторить на `["ok", "  "]`.
- Переход: договор меток известен, но список можно изменять; теперь нужно исключить случайное общее начальное состояние двух задач.

## 02. Default для изменяемого поля

- Напомнить опыт разделяемого списка из прежней A: две ссылки на один контейнер видят один `append`. Современная dataclass не позволяет задавать изменяемый список через `labels: list[str] = []`; нужен способ получать **новое значение на каждый вызов конструктора**.
- Независимый пример для объяснения синтаксиса (не реализация `Task`):

  ```python
  from dataclasses import dataclass, field

  @dataclass
  class Notebook:
      labels: list[str] = field(default_factory=list)
  ```

  Разобрать по частям: `default_factory` — параметр `field`, `list` без скобок — ссылка на вызываемую функцию, а `list()` создаёт список прямо сейчас; dataclass вызывает функцию при создании каждого `Notebook`, если `labels` не передан. `[]` получается у двух объектов одинаковым **по значению**, но списки **разные**.
- **Первое действие:** ученик создаёт `first = Notebook()` и `second = Notebook()`, сам решает, каким из них добавить `"draft"` через `append`, и предсказывает `first.labels`, `second.labels`, `first.labels is second.labels`. Наблюдение: изменён только выбранный экземпляр; `is` даёт `False`. Изменить порядок создания и повторить прогноз. Наглядная опора: каждый Notebook получает собственный чистый блокнот; аналогия касается списка, но не означает независимость всех возможных вложенных объектов.
- Показать различающий случай **до перехода к практике**: `given = ["ready"]`, `third = Notebook(labels=given)` — фабрика не вызывается; `third.labels is given` истинно, изменение `given` видно у `third`. Переход: создание отдельного пустого значения решено, явно переданный список нуждается в дополнительной защите.

## 03. Проверка tags и владение входным списком

- Объяснить **владение контейнером** как практическое правило: вызывающий код может менять свой исходный список, но это не должно менять список в новой модели. Показать различие «один лист, который держат двое» и «два листа с одинаковыми надписями»: копируется сам список, не строковые объекты; строки в Python неизменяемы. У аналогии есть граница: для вложенных списков одной поверхностной копии уже недостаточно, но договор `tags` их запрещает.
- Развернуть обработку в ясной последовательности **до практики**: (1) `isinstance(value, list)` проверяет контейнер; (2) `for` обходит элементы; (3) `isinstance(item, str)` проверяет строку **до** вызова `strip()`; (4) `clean = item.strip()` удаляет внешние пробелы; (5) пустую `clean` отклоняем через `ValueError`; (6) допустимую строку добавляем в **новый** список через `append`; (7) после проверки весь новый список назначается полю в `__post_init__`. Старые проверки остальных полей в `__post_init__` сохраняются. Если проверка неудачна, конструктор поднимает ошибку и вызывающий код не получает корректную новую Task.
- Независимый мини-пример вне `Task`: `raw = [" draft "]`; `clean = []`; ученик самостоятельно выполняет `clean.append(raw[0].strip())`, меняет `raw.append("later")` и предсказывает обе длины. Наблюдение: `clean == ["draft"]`, длина `clean` осталась 1; это **копирование значений в новый контейнер**, а не переименование ссылки.
- **Первое действие:** предложить ученику выбрать порядок проверок для входов `7`, `[5]`, `[" "]`, `[" x "]` и объяснить, почему вызов `strip()` до проверки типа может завершиться другой ошибкой. На допустимом вводе результат содержит `"x"`; остальные дают контролируемый отказ. Опора для возврата: «список → каждый тип → очистка → непустота → новый список». Переход: отдельный список принадлежит модели; при выдаче `to_dict` нельзя снова разделить его со словарём.

## 04. Отдельный список в to_dict

- Назвать `to_dict()` **границей выдачи**: пользователь словаря вправе изменить полученные данные. В новой записи перечисляются именно `id`, `title`, `priority`, `is_done`, `tags`, а значение `tags` берётся из **нового списка** (`list(self.tags)` или аналогичная поверхностная копия). `__dict__` может включить внутренние детали и не является обещанным форматом записи; создание словаря ещё не вызывает `json.dump` и не пишет файл.
- Независимая от `Task` демонстрация: `original = ["first"]`; `shared = {"labels": original}`; `separate = {"labels": list(original)}`. Изменение `shared["labels"].append("second")` меняет `original`, изменение `separate["labels"]` — нет. Объяснить, почему даже два разных словаря могут ссылаться на один **внутренний** список.
- **Первое действие:** ученик сам выбирает копию в небольшом словаре заметок и предсказывает результат `record["labels"].append("new")` и проверку `record["labels"] is original`. Ожидается равенство исходных значений при выдаче и разная идентичность контейнеров; при общей ссылке сравнение идентичности выявит дефект. Переход: выдача безопасна, осталось принять и старую, и новую запись при восстановлении.

## 05. Совместимое восстановление старой и новой записи

- Дать **две допустимые формы**, без догадок: старая содержит **ровно** `id`, `title`, `priority`, `is_done`; новая — эти же четыре ключа **плюс** `tags`. В обеих прежние значения проходят прежнюю строгую проверку. Если отсутствует только `tags`, конструктор получает отдельный пустой список; если ключ есть со значением `None`, это неверное значение, а не отсутствие ключа. Отсутствующий `is_done`, лишний произвольный ключ или неверный тип также дают отказ.
- Объяснить пошаговый маршрут `from_dict`, не выдавая готовый метод: проверить, что вход — словарь; проверить допустимый набор ключей и все прежние обязательные поля; прочитать `tags` **по факту наличия ключа**, без замены `None` на `[]`; передать значения в обычный конструктор (он проверит и скопирует список); оставить исходный словарь неизменным. Конвертер — метод модели, не чтение файла.
- Если уже существующая **чистая** проверка требует ровно четыре ключа, отдельно показать на словаре заметки `draft = dict(record)` и `draft.pop("labels", None)`: копия внешнего словаря позволяет убрать **дополнительный** ключ перед старой проверкой без изменения `record`. Пояснить `dict(record)` как новый словарь, `pop` как удаление ключа только в этой копии и то, что вложенный список ещё не скопирован; его отдельно копирует проверяемый конструктор. Копию для чистой проверки создавать только после контроля новых данных, чтобы не спрятать ошибочный `tags`.
- **Первое действие:** ученик сам распределяет четыре записи по результатам: полная старая → отдельный `[]`; новая с `tags=["  bug "]` → `["bug"]`; новая с `tags=None` → отказ; запись без `is_done` → отказ. Затем сам объясняет, что произойдёт, если после `from_dict` изменить исходный `tags` в словаре; ожидается неизменность модели. Переход: значения совпадают после кругового преобразования, но объект и списки остаются новыми.

## 06. Равенство и пределы проверки после создания

- Вернуться к независимому примеру двух списков: `a = ["python"]`, `b = list(a)`; `a == b` истинно (**те же значения**), `a is b` ложно (**два объекта**). Для dataclass `Task` равенство `==` сравнивает **все** её поля, в том числе `tags` и порядок меток: одинаковые значения могут принадлежать разным экземплярам. После `to_dict` → `from_dict` равенство полей ожидается, идентичность новой Task — нет.
- Контрпример границы гарантии: `task.tags.append(" ")` после создания обходит `__post_init__` и оставляет недопустимую метку; правило проверки действует при создании через согласованный конструктор. Не обещать проверку при каждом последующем присваивании или изменении обычного списка. В рамках занятия не вводить специальную коллекцию или глубокое копирование.
- **Первое действие:** ученик прогнозирует `==` и `is` для двух одинаковых списков и затем для тех же списков после изменения второго. Наблюдение: первоначально `True`/`False`, после изменения содержимого `==` становится `False`; объяснить это значениями, а не именами переменных. Переход: практика теперь может проверять и **сохранность значений**, и **независимость контейнеров**; строгий четырёхпольный storage пока не получает `tags`.

1. **Собственное начальное состояние (опора §02).** Вход: работающая dataclass `Task` с четырьмя полями и прежними правилами. Ученик самостоятельно импортирует `field`, добавляет `tags` с `default_factory` **после обязательных полей** и создаёт две разные Task без явного аргумента меток (например, id 1 и 2). Добавляет `"study"` в `tags` первой. **Локальный результат:** у первой одна метка, у второй `[]`, списки не идентичны (`is False`). Различающий случай: поменять вторую Task, первая остаётся прежней. Если оба меняются, вернуться к разнице между общим контейнером и `default_factory`.
2. **Договор и чужой список (опора §§01, 03).** Вход: новое поле из шага 1 и сохранённая прежняя проверка полей. Ученик сам дописывает проверку `tags` и сборку **нового** нормализованного списка в `__post_init__`, затем передаёт `external = ["  python ", "review", "python"]` в `Task`. **Локальный результат:** модель получает `["python", "review", "python"]` в том же порядке и с повтором; последующий `external.append("later")` не меняет модель, `task.tags is external` ложно. **Различающие случаи:** `None`, строка вместо списка, `[3]`, `["   "]` вызывают `ValueError`, а `[]` разрешён; прежние ошибочные `id/title/priority/is_done` по-прежнему отклоняются. Входное значение не менять на месте, нормализованный список назначать только после успешной проверки.
3. **Выдача записи (опора §04).** Вход: модель с двумя корректными метками после шага 2 и существующий `to_dict`. Ученик самостоятельно добавляет **пятый** ключ `tags` через копию списка, сохранив четыре прежних значения и имена. **Локальный результат:** `record` содержит пять согласованных ключей, метки в нужном порядке; `record["tags"].append("new")` не меняет `task.tags`, контейнеры различны. **Различающий случай:** заменяем проверку содержимого проверкой идентичности; решение, возвращающее `self.tags`, должно обнаруживаться как ошибка. Не передавать пятиключевую запись в рабочий storage.
4. **Восстановление старой и новой записи (опора §05).** Вход: прежний `from_dict`, результат `to_dict` из шага 3 и полная старая запись `{ "id": 3, "title": "read", "priority": 2, "is_done": False }`. Ученик сам расширяет **существующий** `from_dict`: распознаёт ровно два формата, отделяет новое поле для прежней строгой проверки, создаёт `Task` через проверяемый конструктор, не меняет входной словарь. **Локальный результат:** старая запись даёт `tags == []`; новая — те же метки после очистки, в собственной копии. После `input_record["tags"].append("changed")` у восстановленного объекта прежние значения. **Различающие случаи:** нет `is_done`; `tags=None`; `tags=[""]`; лишний неизвестный ключ; неверный тип самого входа — явный отказ. Отсутствующий `tags` разрешён **только при полном старом наборе**; правила прежних полей и старой проверки не ослабляются.
5. **Круг и регрессия (опоры §§04–06).** Вход: обновлённые конвертеры и модель. Ученик сам выполняет `Task → to_dict → from_dict → to_dict` на данных с двумя разными метками и повтором, сравнивает все пять значений, порядок и результат `==`/`is`. **Локальный результат:** данные не теряются, восстановленная Task равна исходной по значениям, но это другой объект и другой `tags`; изменения списка по обе стороны не перетекают. **Различающий случай:** старый полный словарь проходит восстановление и даёт пустые метки, неполный старый — отказ. Отдельно запустить прежний словарный CLI на его **рабочем четырёхпольном JSON** и подтвердить прежнее чтение/операцию без пятого ключа в файле. Здесь проверяем регрессию, а не новую CLI-команду.

Эти действия связаны: **сначала собственное начальное значение → затем контроль явного аргумента → безопасная выдача → совместимый приём → проверка круга и старого пути**. Если наблюдение не совпало, вернуться к указанному параграфу и повторить на изменённом входе; следующий шаг требует результат предыдущего, но не знаний из будущего блока.
