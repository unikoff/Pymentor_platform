## 00. Вступление

По плану предыдущих занятий ученик уже построит модель как обычный класс: поля и правила заданы явно, а конвертеры подготовят будущий переход от словарной записи к объекту. После контрольной сверки этой опоры посмотрим, какую повторяющуюся часть Python способен создать по объявленным полям, сохраняя прежние правила модели.

1. **Точка старта:** после подтверждения B занятия 33.1 обычная Task проверяет поля, изменяет состояние методами и преобразуется в словарь через явные конвертеры.
2. **Новый вопрос:** какую шаблонную часть класса может сгенерировать dataclass и что автор всё равно должен определить сам?
3. **Результат:** та же Task станет короче по устройству, сохранив проверки, методы и границы данных.

Эти три пункта задают путь: сначала понять генерацию на маленьком постороннем примере, затем самостоятельно перенести существующую модель без второй версии или преждевременной миграции приложения. Словарь для старого CLI остаётся прежним, поэтому в конце можно отдельно сверить его работоспособность.

## 01. От повторяющейся модели к dataclass

- **Зачем новый инструмент:** в знакомом `__init__` мы принимаем аргументы и переписываем их в `self.*`. При добавлении поля приходится синхронно менять и список аргументов, и присваивание. `dataclass` из стандартной библиотеки делает этот шаблон автоматически, если явно перечислить поля. Это по-прежнему обычный класс с объектами; `@dataclass` — уже знакомая форма декоратора, который применяется при определении класса. Ни база данных, ни сторонняя установка не нужны.
- **Независимый пример для будущей теории (не проектная `Task`):** сначала обычный `ReadingPlan` с `__init__(self, topic, minutes=25)`, присваивающим `self.topic = topic`, `self.minutes = minutes`. Затем `from dataclasses import dataclass`, `@dataclass` над `class ReadingPlan:` и строки `topic: str`, `minutes: int = 25`. Объяснить каждую строку: первая требует значение при создании, вторая допускает пропуск; создание `ReadingPlan("Словари")` даёт поля `"Словари"` и `25`. Схема/сравнение «аргумент → атрибут» двух форм показывает, какие присваивания исчезли, а какие данные остались.
- **Существенная граница:** `minutes: int` только описывает ожидаемый тип. Python не остановит `ReadingPlan("Словари", "много")` из-за одной аннотации. Отдельные предметные проверки ещё предстоит задать. Сравнить «автоматически присвоить» и «проверить, допустимо ли» как разные действия, без обещания защиты от неверных данных.
- **Первое действие после объяснения:** до просмотра результата ученик предсказывает значения `plan.topic` и `plan.minutes` у `ReadingPlan("Циклы")`, затем сверяет в интерпретаторе. Изменяет только переданное значение `minutes` на `40`, поясняет, почему оно заменило 25. Это короткое исследование на чужом сюжете; полный код практической `Task` пока не показывать.
- **Опора для возврата:** `from dataclasses import dataclass` → `@dataclass` непосредственно над `class` → строки `поле: тип` или `поле: тип = default`. Какой текст должен быть написан *внутри класса*, а какой расположен над ним, показать на выделении строк. После знакомства с формой перейти к правилам порядка полей.

## 02. Поля и сгенерированный конструктор

- **Как работает генерация:** при определении `ReadingPlan` декоратор читает *аннотированные поля* в порядке записи и создаёт `__init__`, который принимает соответствующие аргументы и присваивает их новому объекту. Для `topic: str`, `minutes: int = 25` понятная модель вызова — `ReadingPlan(topic, minutes=25)`. Это объяснение результата генерации, а не требование вручную записать рядом ещё один `__init__`: свой пользовательский `__init__` меняет правило генерации.
- **Два разных способа вызова:** `ReadingPlan("Циклы", 40)` передаёт значения по позиции, `ReadingPlan(minutes=40, topic="Циклы")` — по именам. `ReadingPlan("Циклы")` берёт `25` только потому, что `minutes` пропущен. Установить порядок «обязательные поля слева/раньше → default-поля после них»; перестановка `minutes: int = 25` перед `topic: str` приведёт к ошибке создания dataclass из-за обязательного поля после поля с default.
- **Различающий прогноз:** сравнить `ReadingPlan("Циклы")` и `ReadingPlan("Циклы", 0)`: второе значение равно нулю, *а не* default 25. Объяснить, почему проверять `if not minutes: minutes = 25` означало бы скрыто изменить договор. Ученику дать изменённый порядок именованных аргументов и попросить самому предсказать оба поля, затем проверить.
- **Перенос на настоящую модель:** в `Task` имена аргументов обязаны остаться `id`, `title`, `priority=2`, `is_done=False` в согласованном порядке. Например, `Task(12, "  Учёба  ", 3, True)` должен сохранить явный `True`, а вызов `Task(12, "  Учёба  ")` получит defaults 2 и `False` до проверок. `task_id` старой словарной фабрики не становится новым именем поля `Task`. Сопоставить эти два контракта, не показывая перенос всей реализации.
- **Опора для практики:** `поле: тип` обязательно при создании; `поле: тип = default` можно пропустить; позиционные вызовы зависят от порядка, именованные — от названий. Сгенерированное присваивание не очищает `title` и не проверяет `priority`: следующий раздел объясняет, *когда* выполнять правила.

## 03. `__post_init__` сохраняет правила модели

- **Место проверок:** генерация `__init__` выполняет присваивания, затем автоматически вызывает `__post_init__(self)` (если он объявлен при создании класса). В этом методе автор может проверить значения и при необходимости привести *строку по уже принятому правилу* к нормализованному виду. Последовательность из трёх узлов для визуала: аргументы → присваивания полям → `__post_init__` → доступный объект; если последний шаг выбрасывает исключение, создание `Task(...)` завершается ошибкой, переменная результата вызова не получает корректный объект.
- **Независимое объяснение до проекта:** продолжить `ReadingPlan` и добавить `def __post_init__(self):`: сначала проверить, что `topic` действительно строка, затем `self.topic = self.topic.strip()` и отказать при пустой строке; отдельно для `minutes` показать проверку настоящего `int`, исключающую `bool`, и положительного числа. Прогноз: `ReadingPlan("  Списки  ", 10).topic` становится `"Списки"`; строка из пробелов вызывает `ValueError`; `minutes=True` не должен пройти как число минут. Пояснить синтаксис `self.topic` (поле текущего объекта), `raise` (отказ вызова) и метод, который Python вызывает сам после инициализации.
- **Первое самостоятельное действие:** на знакомом *отдельном* `ReadingPlan` ученик указывает точное место, где надо отклонить `minutes=0`, затем сам записывает проверку и показывает нормальный `minutes=5` и отказ для нуля. Проверку `bool` обсудить отдельно: `isinstance(True, int)` даёт `True`, поэтому при требовании целого без bool нужно сначала исключить логическое значение (например, `type(value) is int`, если наследники int не нужны). Не объявлять `int(...)` или `bool(...)` валидацией: они могут скрыть неверный вход.
- **Проектная связь:** прежние `validate_task_id`, `validate_title`, `validate_priority` повторно применяются в `Task.__post_init__`, с той же нормализацией `title` и прежними исключениями. `id` положителен и не принимает bool; `priority` строго от 1 до 5 и не принимает bool; `is_done` — именно bool, в том числе явный `True` восстановленной задачи. Не копировать условия и тексты ошибок валидаторов внутрь модели: ученик сам определит, как правильно употребить уже имеющиеся функции.
- **Проверка понимания и возврат:** предложить объяснить, почему одна аннотация `is_done: bool` допустит строку `"False"` без `__post_init__` и почему `bool("False")` даст `True`. Опора рядом: «после генерации `__init__` → `__post_init__` → прежние валидаторы и нормализация»; переносить это в проект только после успешного прогноза на чужом примере.

## 04. Что генерируется, а что остаётся автору

- **Три результата декоратора по умолчанию:** `__init__` принимает и присваивает поля (уже разобрано в 02), `__repr__` показывает класс и значения полей для диагностики, `__eq__` сравнивает экземпляры одного класса по всем полям. Написанные автором `__str__`, `rename`, `mark_done`, `set_priority`, `status_label`, `to_dict`, `from_dict` не исчезают и не возникают автоматически. Пользовательский `__init__` отдельно не копировать: он заменил бы ожидаемый способ генерации и сломал бы замысел переноса в `__post_init__`.
- **Наблюдаемый независимый случай:** для `ReadingPlan("Циклы", 40)` заранее предсказать смысл `repr(plan)` — например, `ReadingPlan(topic='Циклы', minutes=40)` — и сравнить с явным словарём `{"topic": "Циклы", "minutes": 40}`. Первый текст полезен в отладке, но его нельзя считывать как JSON или готовую запись. Функция `repr()` вызывает `__repr__`; прежний собственный `__str__` у `Task` отвечает за её отображение человеку. Уточнить, что `print(task)` использует `str(task)` и при сохранённом `__str__` продолжает показывать прежний текст, а не обязателен dataclass-repr.
- **Точное сравнение границ:** таблица на два столбца «генерирует dataclass» (`__init__`, `__repr__`, `__eq__`) / «автор сохраняет» (валидация в `__post_init__`, методы, свойство, `__str__`, конвертеры). Отдельная схема «Task → `to_dict` → четыре ключа → прежний storage» показывает, почему декоратор не открывает путь и не создаёт JSON. Визуальная аналогия «бланк с полями» объясняет шаблон конструктора, но бланк сам не проверяет допустимость содержимого; это ограничение проговорить.
- **Первое самостоятельное действие:** предложить три утверждения — «`@dataclass` создаст `__repr__`», «сохранит написанный `to_dict`», «проверит диапазон priority из одной аннотации» — попросить ученика распределить их по двум сторонам и объяснить *почему*, затем проверить одно наблюдением `repr(ReadingPlan(...))`. Не дублировать ту же викторину после раздела 05.
- **Переход:** механизм генерации уже понятен. Осталось отдельно проследить новое сравнение и проверить, что два разных объекта не становятся одним из-за равных полей.

## 05. Равенство по полям и идентичность

- **Что именно сравнивается:** `a == b` вызывает сравнение значений полей, добавленное dataclass; `a is b` отвечает на иной вопрос — «это один и тот же объект?». Предыдущая обычная `Task` не реализовывала `__eq__`, поэтому для двух отдельных экземпляров `==` не обещал равенства по полям. После перевода на dataclass равенство по четырём полям — *ожидаемое новое поведение*, а не сохранение прежнего сравнения.
- **Независимый эксперимент до практики:** `a = ReadingPlan("Списки", 20)` и `b = ReadingPlan("Списки", 20)`: прогноз `a == b` → `True`, `a is b` → `False`; затем `b.minutes = 30` даёт `False` при `a == b`, но `a.minutes` по-прежнему 20. `c = a` даёт `a is c` → `True`, поскольку переменная получила ссылку на тот же объект. Проследить по схеме из двух экземпляров и трёх имён. Наглядная опора «два блокнота с одинаковой записью» помогает отличить содержание от экземпляра, но в Python сравниваются конкретные поля, а не визуальное сходство.
- **Самостоятельное действие с изменённым случаем:** ученик без готового ответа предсказывает `==`/`is` после `c = a` и последующего `c.minutes = 35`, объясняет, что происходит с `a.minutes`, проверяет результат. Не сводить всё к двум одинаковым вопросам True/False: здесь нужна трассировка ссылок и значений до/после.
- **Перенос на `Task`:** сравнение учитывает одновременно `id`, нормализованный `title`, `priority`, `is_done`, а не только `id` или название. Отдельно сравнить `Task(..., is_done=False)` с теми же полями и `True`, а также два равных по полям, но отдельно созданных экземпляра. `to_dict`/`from_dict` создают новую Task при восстановлении, поэтому круг данных сохраняет значения, но не `is`-идентичность.
- **Опора:** `==` — одинаковые значения всех полей dataclass у объектов одного класса; `is` — один объект; присваивание `c = a` новой Task не создаёт. Это понадобится при проверке восстановления из словаря.

## 06. Границы dataclass и проверка переноса

- **Различить момент создания и последующее изменение:** `__post_init__` вызывается автоматически при конструировании `ReadingPlan`, но запись `plan.minutes = -10` позже присвоит `-10` напрямую и не вызовет эту проверку повторно. Показать двухшаговую трассировку: создание `minutes=10` → допустимый объект; прямое присваивание `-10` → поле изменено без проверки. Ни аннотация `int`, ни сам dataclass не делают поле защищённым от таких присваиваний.
- **Первое самостоятельное исправление объяснения:** показать утверждение «после добавления `__post_init__` ни один экземпляр никогда не хранит неверный minutes» и предложить контрпример с прямым присваиванием; ученик предсказывает наблюдаемое поле и исправляет утверждение до «проверяется путь создания». Для проектной `Task` сохраняются уже объяснённые методы изменения, которые проверяют ввод *до* изменения состояния, и не обещается защита любого прямого присваивания. `property` для вычисляемого `status_label` не превращается здесь в сеттер.
- **Репетиция проектного перехода без решения:** ученику показать два списка обязанностей старой Task: (а) присваивания из `__init__`; (б) валидация, нормализация, `rename`, `set_priority`, `mark_done`, `status_label`, `__str__`, `to_dict`, `from_dict`. Он сам выбирает, какая группа заменяется полями и `__post_init__`, а какая сохраняется, и объясняет, почему второй класс `LegacyTask` не нужен. Не вводить `frozen`, `slots`, `order`, hash или новый способ хранения.
- **Передача к практике:** знакомая обычная Task — вход; одно объявление dataclass с прежними методами — выход. Проверка в следующем разделе разделяет гарантии сохранения и одно намеренное отличие `==`. Последующий урок 34.1 впервые добавит `tags` и их независимые списки, сейчас только четыре прежних поля.

## 07. Что мы будем делать в практике

**Обязательный формат:** изменение существующего проекта (не задача на заполнение строки и не новая учебная программа). Вход — обычная `Task` после результата занятия 33.1 в `app.models` с `id`, `title`, `priority`, `is_done`, валидаторами, `rename`, `set_priority`, `mark_done`, `__str__`, вычисляемым `status_label`, `to_dict` и `from_dict`. Подтверждение этой планируемой A — условие выдачи: учитель сверяет код ученика и реальные прямые вызовы из раздела «Точка A». При неполном входе сначала завершается соответствующий предыдущий шаг; ниже нет готового кода модели, который мог бы его скрыть.

**Цель:** ученик **самостоятельно** переводит *одну и ту же* `Task` на dataclass и доказывает, что прежняя валидация, методы и четырёхпольный обмен сохранились, а равенство по полям стало новым явным поведением. Стартовая техническая опора — имеющийся проект и пример `ReadingPlan` из 01–06; полного нового объявления `Task` в теории и готовой заготовки `__post_init__` нет. Проверки — прямые вызовы/простые `assert`, которые уже объяснялись раньше; не вводить pytest.

1. **Зафиксируем контрольный образец ДО правки.** **Вход:** работающая обычная `Task` и прежние валидаторы; **объект:** один экземпляр `Task` и его запись. **Опора:** B 31.1/32.1/33/33.1 и их проверка перед выдачей; текущие разделы 00 и 06. **Самостоятельно:** ученик выбирает нормальный вызов `Task(12, "  Учёба  ", 3, True)` и отдельно вызов с пропущенными default-аргументами, показывает четыре поля, `to_dict()` и результат одного разрешённого метода изменения. Записывает ожидаемые значения, а не переписывает всю модель в эталон. **Локальный результат:** title становится `"Учёба"`, явно переданное `True` остаётся `True`, пропущенные поля дают 2 и `False`; конвертер выдаёт ровно четыре согласованных ключа. **Различающий случай:** неверный priority, пустое после `strip()` название и не-bool статус отклоняются. Это точка сравнения после преобразования, не новое задание повторно реализовать валидаторы.
2. **Заменим шаблонный конструктор полями.** **Вход:** единственное объявление обычной `Task` из шага 1; **объект:** код объявления модели в `app.models`, без изменения CLI/storage. **Опора:** 01–02 (синтаксис декоратора, обязательные/default-поля, порядок и имена). **Самостоятельно:** ученик импортирует `dataclass`, ставит `@dataclass`, записывает четыре аннотированных поля в согласованном порядке, удаляет ручной `__init__` и повторяющиеся присваивания, сохраняя все остальные методы. **Локальный результат:** два *обычных* вызова — позиционный `Task(12, "Учёба", 3, True)` и именованный с полями `id`/`title` — создают экземпляры; при пропуске priority/is_done сохраняются defaults 2/False. **Различающий случай:** явно переданный `is_done=True` не должен сбрасываться в False, `task_id=` здесь не заменяет `id=`. Этот шаг проверяет **только генерацию**; правильность неправильного ввода ещё нельзя подтверждать, пока не сделан шаг 3.
3. **Вернём прежние проверки при создании.** **Вход:** созданная в шаге 2 dataclass с ещё не восстановленными проверками; **объект:** собственный `__post_init__` этой же Task. **Опора:** 03 и отказы из старой модели шага 1; вызов `__post_init__` из пользовательского кода вручную не нужен. **Самостоятельно:** ученик переносит порядок нормализации и повторное использование трёх прежних валидаторов в новый метод, отдельно проверяет `is_done` как bool и не создаёт новых копий общих правил. **Локальный результат:** `Task(12, "  Учёба  ", 3, True)` снова имеет нормализованный title и истинный статус; непереданные значения остаются 2 и False. **Различающие случаи:** `id=0`, `id=True`, `priority=0/6/True`, пробельный title, `is_done="False"` или 1 не принимаются; ошибки происходят при вызове конструктора, а не в будущем CLI. Отказ должен сохранять прежний тип/смысл сообщения в рамках договора валидаторов, не выполнять `bool(value)` и не превращать неверное значение в допустимое.
4. **Сохраним методы и границу данных.** **Вход:** проверенная Task из шага 3 и прежние методы/конвертеры, уже находившиеся в том же классе; **объект:** её состояние после изменений и новый экземпляр после `from_dict`. **Опора:** B занятий 32.1, 33, 33.1 и раздел 04; **самостоятельно:** ученик выполняет `rename`, `set_priority`, `mark_done`, читает `status_label` и `str(task)`, затем проходит `Task → to_dict → Task.from_dict → to_dict`. Если при переносе что-то пропало, возвращает именно прежний метод, не переписывая задачу как сервис. **Локальный результат:** успешные изменения отображаются в свойстве/строке, после восстановления совпадают все четыре значения, в том числе нестандартный положительный `id`, кириллический title, `priority` и `True`; внешний словарь не превращается в объект сам. **Различающие случаи:** невалидный `rename`/`set_priority` оставляет прежние атрибуты, у `from_dict` с пропущенным обязательным полем/неверным типом возникает прежний отказ, а явный True не становится False. Результат шага 4 проверяется без запуска нового storage.
5. **Увидим новое поведение dataclass.** **Вход:** две независимо созданные одинаковые Task после шага 4; **объект:** их `repr`, сравнение `==`, `is` и значения после одного изменения. **Опора:** 04–05 с прогоном на независимом `ReadingPlan`; **самостоятельно:** ученик сам прогнозирует результаты и пишет прямые проверки: сначала четыре поля одинаковы, затем у второго экземпляра меняется `priority`. Сравнивает также новый объект после `from_dict` с исходным. **Локальный результат:** для равных по всем полям Task `==` истинно и `is` ложно, изменение одного поля делает `==` ложным без изменения другого экземпляра; `repr` показывает класс/поля, `str` остаётся прежним пользовательским представлением. **Различающий случай:** задачи с одинаковым `id`, но разным `is_done` не равны; при `copy = original` проверка `is` истинна, это лишь второе имя того же объекта. Отметить на словах: до dataclass обычная Task не задавала равенство по четырём полям.
6. **Проверим совместимость проекта и один итоговый класс.** **Вход:** изменён только `app.models`; **объект:** текущий модуль, импорт и старый словарный пользовательский сценарий. **Опора:** начало занятия и разделы 04/06; **самостоятельно:** ученик убеждается, что в модуле осталась одна `Task` (без `LegacyTask`), импорт модели не запускает `input`/меню и прежние команды add/list/find/done/search/stats с четырёхпольным JSON дают тот же результат на сохранённой копии данных. **Локальный результат:** создание dataclass Task и старый CLI работают по отдельным проверенным путям; все четыре поля сохраняются при полном цикле и после нового запуска CLI, новая схема `tags` ещё не используется. **Различающий случай:** готовый новый `repr` нельзя записать вместо словаря в JSON, добавление нового поля или переключение storage на Task не относится к этому уроку. Рабочий пользовательский JSON не переписывать ради эксперимента; использовать тестовые данные или безопасную копию.

**Как связаны действия:** шаг 1 даёт измеримую прежнюю норму, шаг 2 независимо проверяет новый генератор конструктора, шаг 3 возвращает инварианты, шаг 4 проверяет накопленное поведение и границу со словарём, шаг 5 отделяет намеренно новое `==` от неизменной идентичности, шаг 6 подтверждает старый пользовательский путь. Для исправления ошибок ученик возвращается именно к 02 (`__init__` и defaults), 03 (`__post_init__` и типы), 04 (методы/формат данных), 05 (`==`/`is`) или 06 (прямое присваивание). Формат — реальная правка проекта с поэтапным наблюдаемым результатом; условия и конкретный код `Task` ученик пишет сам. **Доказательство B при будущей выдаче** — все шесть наблюдаемых результатов, а не одно объявление `@dataclass`; текущий MD является планом и не подтверждает факт практики.

**Передача в 34.1:** та же dataclass Task с четырьмя полями и всеми прежними гарантиями готова к новому полю `tags`; его `default_factory`, копирование списков и расширенный формат записи нельзя требовать на этом занятии.
