## 00. Вступление

В прошлый раз Task научилась показывать себя человеку. Но на диске и на границе JSON Planner по-прежнему работает со словарными записями. Как модели обмениваться данными с этим форматом, не открывая файл изнутри класса?

1. **Точка старта:** Task хранит четыре проверенных поля и умеет их показать.
2. **Новый вопрос:** как явно представить Task словарём и восстановить объект из записи?
3. **Результат:** модель получит два преобразования, которые сохраняют данные и оставляют файловое хранение на прежнем месте.

Эти шаги связывают подготовленную модель с форматом данных проекта: **сначала** разберём, что хранится и зачем нужна граница, **потом** на другом простом объекте научимся двум направлениям преобразования, **после** объясним проверки и только тогда перейдём к изменению Task. Для MAIN это первая связанная группа `LinkedNotes variant="connected"` с коротким прогнозом: что вернётся из `to_dict` — строка, файл или словарь? Ответ опирается на объяснение в 01–02, не выносится до него.

## 01. Объект модели и запись на границе данных

- Начать с простого различия: `task.title` — поле конкретного объекта, `task.mark_done()` — его действие, а `record["title"]` — значение по ключу обычного словаря. Словарь из простых данных уже умеет передавать старый Planner и кодировать JSON. `print(task)` даёт удобный текст для человека, но по нему нельзя надёжно восстановить четыре именованных поля.
- **Механизм:** на рисунке два прямоугольника «Task: атрибуты и методы» и «запись: 4 ключа и значения», стрелки `to_dict()` (объект → запись) и `Task.from_dict(record)` (запись → **новый** объект). Отдельно, вне стрелок, `load_tasks(path)`/`save_tasks(path, records)` занимаются чтением/записью файлов. Конвертер не получает путь и не вызывает эти функции.
- **Независимая аналогия с пределом:** рабочая карточка сотрудника и бланк для передачи в другую систему описывают одного человека, но бланк не выполняет действий карточки; аналогия объясняет разницу представлений, не поведение Python по копированию объектов.
- **Первое осмысленное действие после объяснения:** на готовых выражениях `str(task)`, `task.to_dict()` (пока только обещанный вызов) и `load_tasks(path)` ученик сопоставляет «текст для человека / словарь данных / операция с файлом» и объясняет выбор. Различающий случай — `__str__` красиво показывает статус, но это не добавляет ключ `is_done` к записи. Опора для возврата: схема двух стрелок и отдельного storage.
- Переход: чтобы получить правую сторону схемы, нужен метод существующего экземпляра.

## 02. `to_dict()` как явное представление Task

- Напомнить знакомую форму `obj.method()`: Python передаёт конкретный объект в `self`. Метод `to_dict(self)` **создаёт новый словарь** и возвращает его через `return`; он ничего не печатает и не записывает на диск. Новичку явно пояснить, что выражение `record = obj.to_dict()` кладёт результат в переменную, а не меняет тип самого `obj`.
- **Независимый пример:** у простого `Badge(code, name)` с двумя атрибутами получить `{"code": 7, "name": "Лена"}`. Показать небольшой код только этого учебного метода с явными ключами `code`/`name` (не реализацию конвертера Task). Прогноз: после изменения `badge.name` повторный вызов создаст запись с новым именем; ранее полученный словарь останется прежним.
- **Перенос к Task, без готовой реализации:** четыре согласованных ключа `id`/`title`/`priority`/`is_done` сопоставляются с одноимёнными атрибутами. Важен тип `is_done`: записываем настоящий `True` или `False`, без `str(...)` и `bool(...)`. Внутренний `__dict__` не является контрактом внешних данных: при появлении дополнительного служебного атрибута он выдаст лишнее поле.
- **Первое действие:** ученик получает объект `Badge` и два ожидаемых словаря, выбирает верную структуру, затем на независимом третьем значении объясняет, почему `return` отличается от `print`. Признак понимания — объясняет все ключи и предсказывает обновление/неизменность разных словарей. Для будущего MAIN: визуал потока `self → явные пары → новый dict`, затем короткий прогноз, не два одинаковых опроса.
- Переход: словарь получен; чтобы восстановить объект без заранее существующего `self`, потребуется другой получатель метода.

## 03. Восстановление через `classmethod`

- Вызов `task.to_dict()` начинается с **имеющегося экземпляра**, а `Task.from_dict(record)` должен создать экземпляр, которого ещё нет. `@classmethod` над `def from_dict(cls, record)` означает: при вызове через `Task` Python передаёт **класс** как `cls`, а словарь — как `record`. `cls(...)` вызывает обычный `__init__`, где уже действуют проверки. `cls` не экземпляр и не переменная с новым id; `self` впервые появится внутри создаваемого объекта.
- **Независимый пример:** из двухпольного словаря бейджа создать `Badge` через маленький `@classmethod` и известный конструктор `Badge(code, name)`; прежде чем открыть код, показать порядок стрелок `запись → cls → __init__ → объект`. Дать одну разобранную форму декоратора и вызова, без полного будущего `Task.from_dict`.
- **Различающая ошибка:** вызов `cls()` без полей потеряет исходные значения, а создание `Task(...)` внутри метода жёстко привязывает его к имени класса. В рамках этого занятия использовать `cls(...)` как простой способ обратиться к классу-получателю; наследование пока не разбирать. `@staticmethod` не нужен для создания с классом-получателем.
- **Первое действие:** ученик обозначает в выражениях `badge.to_dict()`, `Badge.from_dict(record)`, `cls(...)` получателя (`self`/`cls`) и предсказывает, создаётся ли новый объект. На изменённой записи с другим `code` показывает, что сохраняется **переданное**, а не придуманное значение. Опора для возврата: таблица `метод экземпляра → self → чтение объекта` / `метод класса → cls → создание через конструктор`.
- Переход: прежде чем передать значения конструктору, нужно проверить, что запись вообще содержит ожидаемые поля.

## 04. Проверка записи и границы ответственности

- Разделить **форму** и **значения**. Форма — получен `dict` с нужными четырьмя ключами; для текущего четырёхпольного договора дополнительно сверить, нет ли неожиданных ключей (не придумывать новые поля). Только после этой проверки читать `record["id"]` и остальные элементы. Отсутствующий ключ должен привести к понятному `ValueError` с причиной, а не к случайному `KeyError` и не к умолчанию.
- Значения проверяет прежний конструктор с общими чистыми валидаторами: положительный целочисленный id, непустое после `strip()` название, допустимый приоритет 1–5, `is_done` ровно `bool`. Подчеркнуть границу Python: `True` является экземпляром `int`, поэтому проверка id/priority обязана отвергать `bool`; `bool("False")` даёт `True`, потому приведение запрещено. Не писать новую параллельную копию всех проверок внутри конвертера.
- **Пример до практики:** на двух независимых записях бейджа сравнить `{"code": 7, "name": "Лена"}` и `{"name": "Лена"}`: для второй нельзя угадать код. Затем контрпример Task со строкой `"False"` вместо логического значения: это неверный тип, даже если внешне кажется похожим на статус. После объяснения ученик предсказывает ошибку и указывает этап её возникновения (форма или значения).
- Если у проекта уже есть **чистая** `validate_task_record` в `app.validators`, использовать её; если проверка находится внутри функции хранения, выделить только чистый разбор формы в validators, сохранив старый договор storage. Нельзя импортировать `load_tasks` в `models` или решать формат через чтение файла. Ошибки IO/повреждения JSON остаются ответственностью storage.
- **Опора для возврата и первый контроль:** таблица «нет ключа → ошибка формы; неверный тип/диапазон → ошибка конструктора; верно → новая Task». Дать прогноз на записи без `is_done` и на записи с `is_done=True`, затем объяснить почему `.get("is_done", False)` скрыла бы потерю данных. Переход: теперь можно доказать, что оба преобразования сохраняют значения.

## 05. Круг преобразования и идентичность объектов

- Объяснить **round trip** как «туда и обратно»: исходный объект → простой словарь → снова объект → словарь. Проверяется совпадение **значений** четырёх полей и типов, а не совпадение ссылок; `from_dict` запускает конструктор и создаёт другой экземпляр.
- **Независимый опыт:** два бейджа с одинаковым `code/name`, но разные объекты; изменение имени одного не изменяет другой. Ограничение аналогии: для изменяемых списков это правило потребует отдельной проверки копий, но `tags` появятся лишь в 34.1. Сейчас значения Task — число, строка, число, `bool`.
- **Различающий случай:** `is_done=True` легко потерять, если при восстановлении ошибочно поставить значение по умолчанию `False`; поэтому рядом проверить завершённую и незавершённую запись. `task1 is task2` должно быть `False`; `task1 == task2` для обычной Task без своего `__eq__` не является критерием совпадения полей. Сравнивать `to_dict()` или четыре значения явно, затем изменить один объект через знакомый метод и повторно посмотреть оба.
- **Первое действие:** дать ученику две схемы результатов «те же значения / тот же объект», он объясняет, что гарантирует каждый вызов; на новом положительном id и кириллическом названии предсказывает сохранение данных. Для будущего MAIN: схема двух отдельных объектов и одной записи, после неё одно задание на объяснение причины, без повторного True/False про уже проверенный статус.
- Переход: в практике ученик перенесёт разобранные правила в настоящую Task, причём реализация останется его собственной.

## 06. Что мы будем делать в практике

**Обязательный формат:** проектная работа (П). Ученик изменяет **ту же** Task в `app.models`, не создаёт новый класс/CLI и не меняет `app.storage` без узкой необходимости вынести чистую проверку формы. **Вход:** код после 33, `load_tasks(path)` из функционального хранения (путь определяется существующей сборкой), полная четырёхпольная запись, проверенная перед началом; при отсутствии фактической записи использовать ранее подготовленную копию с честным указанием источника. Разделы 01–05 — открытая опора, но готовые конвертеры Task и полные тексты заданий не выдаём.

Постепенно уменьшаем опору: сначала объяснение схемы и известной записи, затем собственный метод, затем создание через classmethod, затем самостоятельный выбор проверок и перенос на ошибочные данные. Каждое действие имеет локальную проверку, доступную до следующего.

1. **Зафиксируем входную запись → знаем эталон четырёх значений.** Вход: одна корректная запись через существующий `load_tasks` или честно указанную резервную копию. Объект: словарь с `id/title/priority/is_done`. Опора: 01 (граница и хранение). Самостоятельно: ученик выписывает значения и типы, в том числе статус; не редактирует JSON. Критерий сразу: четыре обязательных ключа на месте; отдельно сравнить запись с `is_done=False` и подобранную завершённую `True`, не смешивая строку и `bool`.
2. **Напишем `to_dict()` → объект отдаёт новый четырёхпольный словарь.** Вход: собственная Task с рабочим конструктором. Объект: метод в том же `app.models.Task`. Опора: 02 с независимым бейджем. Самостоятельно: ученик выбирает четыре пары «ключ → атрибут» и пишет `return`, сохраняя `True/False`, без `__dict__` и IO. Критерий сразу: ключи/значения/типы совпадают; после изменения поля повторный вызов даёт актуальные данные, ранее полученный словарь остаётся прежним.
3. **Самостоятельно добавим `@classmethod from_dict` → восстановленный объект проходит конструктор.** Вход: словарь из шага 1 и `to_dict` шага 2. Объект: метод той же Task и, если необходимо, чистая проверка формы в `app.validators`. Опора: 03–04 (синтаксис декоратора, `cls`, обязательные ключи, ValueError). Самостоятельно: ученик пишет декоратор, параметры, проверку формы и вызов `cls(...)` с данными записи. Критерий сразу: корректная запись с нестандартным `id` (например, 17), кириллическим `title`, `priority=5` и `is_done=True` создаёт объект с теми же значениями; отдельно `False` также остаётся `False`.
4. **Сломаем копии входа → неправильные записи отклоняются явно.** Вход: копии корректного словаря, исходная запись нетронута. Объект: тот же `from_dict`. Опора: 04 и конструктор из 31.1. Самостоятельно: ученик выбирает, как показать отказ для отсутствующих `id` и `is_done`, статуса `"False"`, приоритета вне 1–5, `id=True` и пустого после пробелов `title`. Критерий сразу: `ValueError` с понятной причиной, ни одна ошибка не создаёт пригодную Task и не изменяет входной словарь; остальные поля не теряются через defaults или приведение типов.
5. **Проведём полный круг и сравним две Task → значения сохранены, экземпляры разные.** Вход: объект из шага 3 и запись шага 2. Объект: `Task → to_dict → Task.from_dict → to_dict`. Опора: 05 (поля против идентичности) и прежние методы изменения. Самостоятельно: ученик сравнивает оба словаря и `is`, затем меняет статус/название лишь одного экземпляра. Критерий сразу: четыре исходных значения одинаковы до изменения; `is` — `False`; после изменения второго первая Task остаётся прежней. Не использовать `==` обычной Task для проверки полей.
6. **Сверим сохранённую работу Planner → новый конвертер не поменял рабочий путь.** Вход: существующий `app.main`/CLI и прежний путь `load_tasks`; до запуска зафиксировать содержимое рабочего файла, не выполнять тестовую запись поверх него. Объект: прежний словарный путь операций. Опора: 01 (storage владеет IO) и 05 (новые объекты отдельны). Самостоятельно: ученик показывает, что существующая операция чтения по-прежнему возвращает словари и что модель можно импортировать без запуска меню; запускает известные безопасные сценарии CLI без внесения новых тестовых записей в рабочий JSON. Критерий сразу: прежние команды/формат четырёх полей доступны, конвертер сам не читает и не пишет файл; сохранённые данные не затронуты. Если безопасный сценарий не обеспечен, достаточно просмотра связей вызовов плюс запуск на временной копии данных, не заявляя проверки реального файла.

Связь результатов: запись шага 1 задаёт эталон, шаг 2 даёт прямое направление, шаг 3 — обратное, шаг 4 исключает потерю обязательных данных, шаг 5 доказывает сохранность и новую идентичность, шаг 6 защищает старый словарный путь.
