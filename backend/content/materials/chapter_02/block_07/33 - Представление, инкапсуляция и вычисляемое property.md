## 00. Вступление

У задачи уже есть число `id`, название, приоритет и флаг `is_done`. Содержимое хранится в полях; `rename(...)` и `mark_done()` меняют его. Но вызов `print(task)` должен объяснить человеку, какая это задача и завершена ли она. Для этого нужна **строка, построенная из текущих полей**, а не ещё один сохранённый статус.

1. **Точка старта:** если подтверждён результат 32.1, ученик умеет получить и изменить поля конкретной `Task`.
2. **Новый вопрос:** как показывать актуальную карточку без вручную обновляемого текста «готово/не готово»?
3. **Результат:** ученик пишет вычисляемую подпись и `__str__`, затем исследует пределы проверки присваивания.

**Связанная схема для MAIN:** `поля Task → вычисляемый status_label → строка __str__ → str/print`. Ученик сначала указывает, где именно находится значение `is_done`, затем предсказывает, что изменится в цепочке после `mark_done`; схема не должна обещать запись в JSON. Рядом достаточно одной короткой ситуации: «карточка на экране читает данные, а не хранит копию всех данных». Аналогия заканчивается там, где у реального экрана есть собственное устройство обновления: в Python новое чтение свойства выполняет код getter.

## 01. `__str__` создаёт строку для вызывающего кода

**Смысл до синтаксиса.** Если напечатать объект обычного класса без специально написанного представления, можно увидеть техническое описание с именем класса и адресом, а не полезные поля. Python вызывает `__str__(self)` при `str(obj)`; `print(obj)` получает строковое представление и выводит его в терминал. `__str__` должен **вернуть** именно `str` через `return`, а не напечатать её внутри. `repr(obj)` нужен скорее разработчику для диагностики; здесь **не** настраиваем `__repr__` и не используем оба варианта для хранения задачи.

**Независимый разобранный пример до Task:** маленький `Notice(number, message)` хранит номер и текст. В его `__str__` вернуть `f"Сообщение {self.number}: {self.message}"`; тогда `text = str(notice)` сохраняет строку в переменную, а `print(text)` показывает её. Выражения в фигурных скобках f-строки подставляют текущее значение полей; `self` — экземпляр, на котором вызван метод. Показать цепочку `str(notice) → notice.__str__() → return → text` и неправильный вариант с `print(...)` вместо `return`: такой метод возвращает `None`, поэтому `str(notice)` выдаёт `TypeError`. Сначала объяснить форму `def __str__(self)` и скобки f-строки, потом просить о прогнозе.

**Первое применение:** ученик предсказывает, что будет в `text` и что появится на экране для `Notice(4, "Отчёт")`, затем сам меняет `message` и проверяет новое представление. Отличить «значение вернулось» от «что-то напечатано». **Место визуала/трассировки:** стрелки вызова, возврата и печати вместо двух соседних текстовых карточек о `return`. **Переход:** в реальной модели формат должен содержать не абстрактное сообщение, а поля существующей задачи.

## 02. От одного флага к понятной подписи: `@property`

**Проблема:** `is_done` уже хранит `False`/`True`. Если дополнительно хранить `status_text`, при вызове `mark_done()` придётся обновлять сразу два поля. Можно забыть обновить одно и получить `is_done=True` рядом с «не завершена». **Договор по текущему примеру и учебной практике:** `False → «не завершена»`, `True → «выполнена»`; не вводить новые «open/done» или независимый формат CLI.

**Механизм с нуля:** обычный метод `def status_label(self): ...` возвращал бы текст по вызову `task.status_label()`. Декоратор `@property` над методом превращает это чтение в **обращение как к атрибуту** — `task.status_label` без круглых скобок. При каждом чтении Python запускает getter с текущим `self.is_done`; отдельное присваивание `self.status_label = ...` не нужно. Это свойство **только для чтения**, пока мы не определили setter. Не путать получение новой строки с изменением `is_done`.

**Независимый пример:** у маленького `Lamp` есть `is_on`; свойство `label` возвращает «Светит» при `True`, иначе «Выключена». Трассировка: `lamp.is_on=False` → первое чтение `lamp.label` даёт «Выключена» → изменить `is_on=True` → второе чтение возвращает «Светит». В объекте не появилось второе сохранённое поле `label`. **Первая проверка понимания:** дать этот же пример с одним изменённым условием и попросить ученика определить значение двух чтений, а затем самостоятельно объяснить, почему `lamp.label()` ошибочно: строка уже получена, вызывать её нельзя.

**Визуал:** две строки таблицы `is_done | результат чтения`, затем схема «датчик состояния → подпись-индикатор». Уточнить границу аналогии: property ничего не отслеживает в фоне, getter выполняется именно при чтении. **Переход:** теперь подпись можно встроить в строку всей `Task`.

## 03. `__str__` читает актуальные поля той же `Task`

**Что показать до самостоятельной записи:** узнаваемая карточка прежнего Planner имеет номер, название, приоритет и русскую подпись статуса. Вместо вывода внутри метода результат можно собрать одной f-строкой (либо соседними f-строками в скобках, если строка длинная). Источники частей: `self.id`, `self.title`, `self.priority`, **`self.status_label` без `()`**. Последнее чтение само смотрит на `self.is_done`. `__str__` не меняет ни одно поле; не создаёт `display_status`, `done` или кеш готового текста.

**Разобранная проверка на карточке без готового метода:** дано `Task(7, "Купить хлеб", 2, False)`. Сначала ученик сопоставляет части будущей строки с полями, затем предсказывает: после `rename("Купить молоко")` название станет новым; после `set_priority(4)` изменится число; после `mark_done()` изменится подпись. На схеме отразить состояние объекта *до и после*, а между ними только вызов и новое чтение `str(task)`. Показательный ожидаемый вид: `[7] Купить молоко | приоритет: 4 | выполнена`. Он пример требования к отображению, а не готовая реализация `__str__` для вставки.

**Первое действие:** дать ученику уже знакомую карточку со сменённым `id` и попросить самому выбрать, какие `self.*` используются для каждого фрагмента, затем сравнить две полученные строки. Если подпись не меняется после `mark_done`, сначала проверить, что getter читает `is_done` *при вызове*, а не запоминает значение в `__init__`. **Переход:** красивая строка ещё не защищает поля от произвольного присваивания — это другой вопрос.

## 04. Инкапсуляция задаёт понятную границу, но не магическую защиту

**Вопрос после карточки:** представление *читает* поля; кто определяет, какие изменения разрешены? Инкапсуляция — организация интерфейса объекта: внешнему коду предлагают понятные методы или свойства, а детали реализации отмечают как внутренние. Имя `_priority` в Python означает «не используй извне без необходимости» по соглашению авторов. Оно **не** запрещает написать `obj._priority = -5`; Python не проверяет договор по одному подчёркиванию. Не добавлять объяснение name mangling или `__priority` как якобы абсолютной защиты.

**Сначала различить два пути:** `obj.set_priority(3)` — явный вызов метода; `obj.priority = 3` — синтаксис присваивания. Само по себе присваивание обычному публичному атрибуту не вызывает `set_priority`. Для небольшого независимого учебного `Gauge` (показатель уровня от 1 до 5) можно задать внутреннее `_level` и `@property def level(self)` для чтения. Затем объяснить конструкцию `@level.setter` над `def level(self, new_value)`: при `gauge.level = 4` Python вызывает setter, передавая `new_value=4`. Имя свойства у getter и setter совпадает; внутри обоих используется `_level`, чтобы не присваивать `self.level` рекурсивно.

**Порядок безопасного setter:** сначала проверить, что значение — **точно целое** (включая отказ для `True`) и лежит в 1–5; при ошибке поднять `ValueError` **до** изменения `_level`; только после проверки выполнить присваивание. Независимая трассировка: исходное `gauge.level=2`, затем `gauge.level=4` (получили 4), затем `gauge.level=9` (ValueError; прочитали всё ещё 4). На втором прогоне передать `True` и объяснить отказ, хотя `bool` — подкласс `int`. Ошибка *после* изменения была бы слишком поздней: исключение не откатывает прежнюю запись автоматически.

**Первое самостоятельное применение:** показать два порядка строк setter и попросить выбрать, какой гарантирует 4 после отказа; ученик проверяет это на `Gauge`, затем объясняет результат `gauge._level = 9`: обошли setter, получив недопустимое состояние. Это демонстрация **предела контроля**, а не рекомендуемый способ работы. **Учебная схема:** два маршрута `gauge.level = ... → setter → проверка → _level` и `gauge._level = ... → поле напрямую`; для каждого прогноз состояния и причина. **Переход:** у Task уже есть осмысленные методы, поэтому переносить туда весь этот эксперимент не нужно.

## 05. В Task сохраняются явные методы изменения

**Решение для существующего Planner:** в `Task` остаются `mark_done()`, `rename(new_title)`, `set_priority(new_priority)`. Они уже знают, как проверять значение до изменения, и сохраняют свои прежние результаты вызова (`None` для методов изменения). Новое `status_label` **только вычисляет** текст из `is_done`; setter для `status_label` и поля `status_text` не нужны. Убирать методы, вводить `_title`/`_priority`, переименовывать конструктор или менять модель на dataclass в этом занятии нельзя.

**Сравнение с исследованием:** `gauge.level = 4` проходит через учебный setter; `task.set_priority(4)` проходит через явный метод существующей модели. А вот `task.priority = 9` обходит этот метод и может нарушить договор. Это честная граница нынешней модели, а не основание срочно переписать её целиком. Прогноз: `task.status_label = "Выполнена"` у свойства без setter вызовет `AttributeError` и **не** завершит задачу; изменение статуса происходит через `task.mark_done()`.

**Мини-выбор после объяснения:** для четырёх намерений выбрать правильный механизм: «завершить задачу» → `mark_done`; «изменить приоритет с проверкой» → `set_priority`; «узнать читаемую подпись» → чтение `status_label`; «сохранить модель в JSON» → ещё не решённая задача следующего занятия. Не повторять отдельной карточкой те же вопросы о `return`/`print`. **Переход:** человекочитаемый текст — результат показа, а сохранение должно сохранить исходные данные.

## 06. Показ объекта не является его сериализацией

**Две задачи, два вида данных:** `str(task)` возвращает строку наподобие `[7] Купить молоко | приоритет: 4 | выполнена`. Это удобно читать, но по ней не надо восстанавливать объект: изменится текст подписи или пунктуация — сломается разбор. Прежний формат хранилища — структурированный словарь с **четырьмя полями** `id`, `title`, `priority`, `is_done`, где `is_done` остаётся `True`/`False`, а не русской подписью. Даже если словарь потом записывается как JSON, само свойство `status_label` ничего не сохраняет.

**Независимое различение:** дать одну карточку «[7] … | выполнена» и одну запись `{"id": 7, "title": "…", "priority": 4, "is_done": true}` (оговорить, что `true` — JSON, в Python bool пишется `True`). Ученик определяет, что можно безопасно показать пользователю, а что годится как договор хранения; указывает, какое поле будет обновлено при `mark_done`. **Визуал:** два столбца «что видит человек» и «какие типизированные поля сохраняются», между ними ссылка на одну исходную Task. Аналогия: ценник на коробке помогает читать описание, а опись склада хранит структуру; ценник не содержит все правила восстановления и не заменяет опись.

**Граница:** сейчас не писать `to_dict`, `from_dict`, `json.dumps`, не менять обработчик `format_task` или рабочий JSON. Эти операции вводятся в 33.1, когда будет понятен отдельный договор данных. **Переход:** самостоятельная практика проверит представление на реальных переходах состояния и не тронет сохранение.

2. **Первое изменение настоящей модели (раздел 02).** Внутри существующей `Task` ученик **пишет сам** вычисляемый `status_label` с `@property`, читающий `is_done`, без `status_text`, без setter. Прямое чтение у экземпляров с `False` и `True` должно выдавать разные русские подписи; `task.status_label` читается без скобок, два экземпляра независимы. При одинаковой подписи у обоих вернуться к таблице двух значений и проверить, не запомнена ли строка в конструкторе.
3. **Второе изменение модели (раздел 03).** Ученик **сам пишет** `__str__`, возвращающий карточку с `id`, `title`, `priority`, `status_label` в уже согласованном виде; не добавляет печать в метод и не редактирует `format_task`. Проверить отдельно `isinstance(str(task), str)`, чтение сохранённого в переменной `text = str(task)` и вывод `print(task)`: оба обращения должны пользоваться тем же текущим представлением. Если Python сообщает, что `__str__` вернул `None`, вернуться к §01 и поправить границу возврата.
4. **Изменение состояния и перенос на другой случай (разделы 03 и 05).** Для исходной `Task` ученик сначала записывает прогноз строки после `rename("Купить молоко")`, `set_priority(4)`, `mark_done()` и повторного `mark_done()`. Затем выполняет эти вызовы и сверяет: название, приоритет и подпись обновились, `id` остался 7, после повтора статус не вернулся в `False`. Создаёт **вторую** Task с другим `id` и незавершённым состоянием; операции с первой не меняют вторую. Новый тестовый случай: из первой Task вызвать `set_priority(0)` и `rename("   ")`, ожидать `ValueError` и **точно ту же** карточку до/после каждого отказа. Эти вызовы уже опираются на валидаторы из 32.1, новая логика проверки здесь не пишется.
5. **Отдельное исследование setter (раздел 04).** На небольшом `Gauge` с полем `_level` ученик самостоятельно дописывает `@property` для чтения и `@level.setter` для проверяемого изменения в пределах 1–5. Сначала определить прогноз: `2 → 4 → попытка 9 → чтение 4`; после опыта проверить фактическое значение и `ValueError`. Отдельно попробовать `True` как неверный тип (должен быть отказ), затем объяснить, почему прямой доступ к `_level` технически возможен и обходит setter. **Не переносить** `Gauge` и его setter внутрь `app.models.Task` и не создавать ещё одну Task.
6. **Проверка договора с предыдущим и следующим занятиями (разделы 05–06).** Выполнить прежний CLI, показать задачи и перезапустить чтение своего рабочего JSON в установленном порядке, **не записывая** карточку `str(task)` в файл. Прежний `format_task` продолжает получать словари; новый объект пока тестируется прямыми вызовами. Ученик устно определяет, что должен содержать будущий `to_dict`: четыре поля с исходным bool, без `status_label` как сохраняемого поля. Реализация конвертеров остаётся для 33.1.

**Критерии приёмки практики:** ученик может без копирования готового `Task` объяснить и проверить `str`/`print` против `return`; `status_label` меняется после `mark_done` без присваивания подписи; `__str__` содержит четыре актуальных компонента; неверные вызовы методов не портят состояние; учебный setter проверяет значение **до** записи и честно демонстрирует обход через `_level`; старый путь CLI/JSON остаётся рабочим. Ручные проверочные вызовы/`assert` после объяснения можно выполнять отдельно от импортируемого модуля; не оставлять тестовые `print` и создание объектов на верхнем уровне `app.models`.

**Маршрут самостоятельности:** показ чтения/возврата на `Notice` → прогноз без решения → собственный getter → собственный `__str__` → серия меняющихся состояний → изменённый крайний случай → самостоятельное исследование setter → объяснение границы данных. Когда проверка не проходит, ученик возвращается к конкретному §01, §02, §04 или §06 и повторяет на изменённом входе; готовую реализацию основной `Task` не подсказывать до попытки.
