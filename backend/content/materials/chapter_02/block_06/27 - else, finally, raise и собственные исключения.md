## 00. Вступление

Reader — уже знакомая функция, которая читает ответ пользователя. Она помогает повторить ввод после ошибки, но `create_task` можно вызвать прямо из другого кода, минуя reader. Тогда пустое название или неверный приоритет может оказаться в списке задач. Покажем этот разрыв на одном конкретном вызове: `create_task(1, "   ", 3)` обходит `read_title`, поэтому защита только в меню не срабатывает.

1. **Точка старта:** после занятия 26.1 числовой reader должен переводить текст в целое число, а `read_priority` — проверять диапазон 1–5; перед началом подтверждаем этот результат.
2. **Новый вопрос:** что произойдёт при прямом вызове `create_task` и как отказать, пока список задач ещё не изменён?
3. **Результат:** проверять значения внутри создания задачи, явно останавливать недопустимый путь через `raise`, а затем различать `except`, `else` и `finally` по их действиям.

Сначала научимся различать пустой результат и ошибочное значение, затем напишем проверки до изменения списка. Отдельный короткий пример покажет ветви обработки исключения; он нужен для понимания порядка выполнения, а не для добавления бессмысленной очистки в Planner. В MAIN после каждого из этих переходов запланировать одно содержательное действие ученика: выбрать исход, найти момент изменения списка, предсказать вывод.

## 01. Пустой результат и недопустимое значение — разные исходы

- **Смысл и новые слова:** результат функции — значение после `return`. `None` обозначает отсутствие значения; здесь `find_task(tasks, 999)` возвращает `None`, когда совпадений нет: это предусмотренный ответ на поиск. **Обязательное правило данных** — условие, без которого задача не может существовать: название после удаления пробелов непустое, приоритет от 1 до 5, id положительный. Нарушение такого правила — ошибка входного значения, а не обычный результат.
- **Порядок разбора:** сначала дать два одинаково наглядных вопроса: «нашли ли задачу?» и «можем ли создать задачу?». Сопоставить `find_task([], 999) -> None` с `create_task(1, "   ", 3)`: второй вызов должен **отказать**, а не вернуть пустую/неполную запись. Затем показать вызов фабрики из кода без `input` и `read_title`; функция ввода больше не гарантирует допустимость параметров.
- **Первое самостоятельное действие:** ученик для трёх ситуаций выбирает «нормальный результат / нарушение правила» и обосновывает: не найден id при поиске; пустое название; поиск в пустом списке. Критерий — оба поиска допускают `None`, создание пустой задачи нет. Не менять текущий `find_task` и не называть отсутствие совпадений исключением.
- **Опора для возврата:** «отсутствие допускается по договору поиска → `None`; данные для новой записи недопустимы → отказ». Далее покажем, как функция сообщает об отказе.

## 02. `raise` и чистые проверки значений

- **Механизм до первого задания:** `raise` — команда «прервать обычный ход и сообщить об ошибке»; `ValueError` — встроенный тип ошибки для недопустимого значения. В `if ...: raise ValueError("...")` при выполненном условии строки успешного пути ниже не выполняются. **Валидатор** — функция проверки: при допустимом значении возвращает его, при недопустимом вызывает `raise`. **Чистая проверка** не добавляет и не меняет задачи в списке.
- **Короткий независимый пример:** перед проектом объяснить функцию `validate_seats(count)` для бронирования 1–8 мест: сначала проверка `isinstance(count, int)` (принадлежит ли значение типу целых чисел), затем `1 <= count <= 8`, при отказе `raise ValueError` с понятной причиной, при успехе `return count`. Сравнить три запуска: `3` возвращается, `0` даёт ошибку диапазона, `"3"` даёт ошибку типа. После строки с `raise` в том же вызове `return` не достигается. Не требовать новых библиотек, классов и перехвата здесь.
- **Перенос в Planner без готового решения:** напомнить существующий `normalize_title`: он приводит написание названия к согласованному виду; **сначала** проверить, что название является строкой, **затем** вызвать нормализацию и проверить, осталось ли что-то кроме пробелов. Для приоритета и id перед сравнениями проверить тип через `isinstance(..., int)`, затем диапазоны (1–5 и `> 0`). Объяснить, что `priority: int` в параметре — подсказка для читающего код, а не проверка Python. Функции `validate_title`, `validate_priority`, `validate_task_id` возвращают нормализованное/проверенное значение; неверное — `ValueError` с названием нарушенного правила. Не писать новый `normalize_title` и не расширять проверку на весь будущий JSON-снимок.
- **Первое самостоятельное действие:** на независимом примере ученик указывает, что вернётся или какая проверка остановит вызов для `3`, `0`, `"3"`; на проектном — выбирает порядок «тип → нормализация/диапазон → возврат» для названия, id и приоритета. Критерий — текстовая `"3"` не превращается в число внутри фабрики; конвертацию пользовательского ввода делает reader. Особенность `bool` как `int` пока не отдельное требование: она подробно войдёт в 30.1.
- **Опора для возврата:** «проверил тип → проверил правило → вернул допустимое / выполнил `raise`». После этого проследим, что происходит с самим списком задач.

## 03. Проверка до добавления и изменение только при успехе

- **Смысл до действия:** **изменение состояния** — действие, после которого общий список или словарь уже другой; `append` добавляет элемент в исходный список. Сам `raise` не отменяет предыдущее `append`. Сравнить два порядка на независимой очереди заявок: «добавить пустую заявку, затем проверить» оставляет мусорную запись; «проверить, затем добавить» сохраняет очередь при отказе. Показать конкретное состояние списка до/после и попросить найти строку первого изменения.
- **Маршрут в существующем Planner:** изучить действующую `create_task` и место `append` в `add_task`; сохранить единственную фабрику и четыре поля `id/title/priority/is_done`. Сначала вызвать три валидатора в `create_task` и собрать словарь **только из допустимых значений**; `add_task` получает готовую проверенную запись через фабрику и вызывает `append` только после её успешного возврата. `get_next_id` вычисляет id из списка, не ведёт скрытый счётчик. Если проверка прервала вызов, `append` не произошёл и следующий id тот же.
- **Первое самостоятельное действие:** на нарисованном списке из двух задач ученик предсказывает количество элементов и следующий id до/после успешного добавления и после отказа по названию. Затем находит в собственном коде точку, где мутация **не должна** произойти при `ValueError`. Критерий — при отказе совпадают длина, содержимое обеих прежних задач и `get_next_id(tasks)`, а допустимая запись имеет прежние поля и статус `is_done=False`.
- **Частая путаница:** перехват ошибки после `append` не возвращает список в исходное состояние. Нельзя создавать второй список в CLI «для безопасности» или менять `find_task` ради проверки фабрики. Далее разберём, какие ветви действительно выполняет `try`.

## 04. Успешная ветка `else` и безусловный `finally`

- **Ввести слова по порядку:** `try` выполняет код, где ожидается ошибка; `except ValueError` выполняется только при такой ошибке; `else` выполняется только когда весь `try` прошёл без исключения; `finally` выполняется при обоих исходах и также **перед передачей неперехваченной ошибки** вызывающему коду. `else` и `except` здесь выбирают разные ветки, `finally` следует после выбранного пути. `finally` **не** означает «операция удалась».
- **Независимый от Planner пример для трассировки:** подготовить небольшую функцию `check_number(raw)` с `try: number = int(raw)`, `except ValueError: print("Не число")`, `else: print("Число:", number)`, `finally: print("Проверка завершена")`. До демонстрации ученик предсказывает строки и порядок для `"5"` и `"пять"`; затем запускает оба вызова. Ожидается соответственно «Число: 5 → Проверка завершена» и «Не число → Проверка завершена». На схеме ветвления показать, что строки обеих веток **не** печатаются вместе.
- **Третий различающий случай:** в учебном примере допустить неперехваченную программную ошибку внутри `try` (например, обращение к неверному имени): `except ValueError` её не ловит, `else` не выполняется, но `finally` выполнится перед traceback. Коротко показать ловушку `return` из `finally`: он может скрыть даже возникшую ошибку. Не предлагать это как приём для Planner; не делать обязательным освоение сложных способов освобождения ресурсов.
- **Первое самостоятельное действие:** ученик составляет для трёх случаев маршрут `try → else → finally`, `try → except → finally`, `try → finally → неперехваченная ошибка` и объясняет, почему одинаковое завершающее сообщение не доказывает успех. В MAIN поставить после примера трассировку/предсказание, а не ещё одну одинаковую карточку с определениями.
- **Опора для возврата:** «успех `try` → `else`; ожидаемый отказ → подходящий `except`; `finally` выполняется в обоих случаях и при неперехваченном отказе». Никакой искусственный `print("CLEANUP")` и несуществующая очистка не попадают в реальный Planner. Теперь применим `except` к границе интерфейса.

## 05. Границы перехвата и сохранение прежнего договора

- **Новый термин:** **граница перехвата** — маленький участок, где ошибка превращается в понятное сообщение, а вызвавшая её операция уже остановилась. Reader ловит `ValueError` при `int(raw)` для повтора ввода; после преобразования фабрика может сама выдать `ValueError`, если значение нарушает правило. Это две разные точки проверки, обе нужны.
- **Различающий пример до проекта:** сравнить `try`, охватывающий весь цикл меню с `except Exception`, и маленький `try` вокруг операции с `except ValueError`. Первый скрывает ошибки программы под сообщением «плохой ввод»; второй перехватывает ожидаемый отказ и оставляет заметным, например, `NameError` из ошибки разработчика. Объяснить, что `as error` даёт доступ к причине для сообщения, если использовать эту уже встречавшуюся форму; показать форму записи перед самостоятельным применением.
- **Перенос в CLI:** наметить `handle_add`: вызвать `add_task` в узком `try`, в `except ValueError` вывести причину и **не** печатать карточку успешно созданной задачи; успешное подтверждение расположить на пути, где операция завершилась без исключения (после `try` с выходом из обработчика при отказе либо в `else`). Не оборачивать в общий `except` выполнение неизвестных команд и других обработчиков. Сохранить обычные сообщения, команды и существующую таблицу диспетчера.
- **Первое самостоятельное действие:** ученик сопоставляет последовательности «нечисловой ввод», «допустимое число вне диапазона», «прямой вызов фабрики с ошибочным значением» с владельцем проверки; затем объясняет, почему `handle_add` не должен печатать успех при третьем случае. Критерий — конкретный отказ понятен пользователю и не маскирует `NameError`.
- **Граница следующего шага:** не вводить `UnknownCommandError`, `TaskNotFoundError`, новый класс или изменение договора `find_task`/`mark_task_done` — собственная ошибка для обязательного получения id будет объяснена в 27.1. Теперь можно проверить полный путь на действующем Planner.

## 06. Что мы будем делать в практике

**Формат и исходная опора:** **основная проектная практика (П)** — изменение существующего `main.py` StudyHub Planner после проверки реальной B занятия 26.1. Использовать имеющиеся `normalize_title`, `create_task`, `get_next_id`, `add_task` и `handle_add`; исследование `else/finally` выполнить отдельно в маленькой функции. Ученик пишет проверки и изменяет существующий код сам; готовый проектный алгоритм ему не выдаётся.

Сценарий самостоятельного выполнения с небольшими промежуточными проверками: сначала одна проверка значения, затем существующая фабрика, затем изменение общего списка и только после этого сообщение CLI. После каждого шага ученик сверяет наблюдаемый результат, не ожидая окончания всей работы.

1. **Напишем чистые проверки.** В существующем файле ученик самостоятельно создаёт `validate_title`, `validate_priority`, `validate_task_id`; исходная опора — раздел 02 и прежний `normalize_title`. Локальный результат: название с пробелами по краям возвращается нормализованным; название только из пробелов, приоритет `0`/`6`, id `0`, а также строковые `"3"` для числовых полей дают `ValueError` с понятной причиной. Допустимые `priority=1`/`5` и положительный id проходят. Проверки ничего не добавляют в список.
2. **Защитим существующую фабрику.** Ученик найдёт место сборки четырёхпольного словаря в `create_task`, использует валидаторы **до** сборки и сохранит `id/title/priority/is_done` (статус новой задачи — `False`). Локальный результат: прямой вызов с корректным названием `"  Купить хлеб  "` даёт согласованное название и прежние поля, а прямые вызовы с каждым неверным значением прекращаются на `ValueError`. В фабрике не возникает нового reader, второй модели или подмены недопустимого значения `None`.
3. **Проверим границу изменения.** В `add_task` ученик устанавливает порядок «фабрика → полная запись → `append`»; на исходном списке из двух разных задач записывает длину, копию содержимого и `get_next_id`. Локальный результат: после отказа все три величины равны исходным, обе старые записи не меняются; после корректного добавления появляется ровно одна задача с ожидаемым id, а следующий вычисляемый id сдвигается только после успеха. Отдельно проверить прямой вызов `add_task`, минующий интерфейс.
4. **Обработаем ожидаемую ошибку в `handle_add`.** Ученик сам выбирает узкий `try/except ValueError` вокруг операции и место успешного сообщения. Локальный результат: неверное значение даёт объяснение отказа без карточки успеха, список не меняется; допустимая задача добавляется и отображается как раньше. В коротком обсуждении ученик показывает, почему `except Exception` скрыл бы программный дефект; искусственно ломать рабочий проект для демонстрации не нужно.
5. **Исследуем `else/finally` отдельно.** Ученик предсказывает, затем запускает `check_number("5")` и `check_number("пять")` из раздела 04, записывает порядок сообщений; на третьей схеме объясняет поведение при неперехваченном исключении. Локальный результат: `else` появляется только для успешного `try`, а `finally` — в обоих запусках; одинаковая завершающая строка не объявляет ввод успешным. Ни `CLEANUP`, ни фиктивный `finally` не добавляются в Planner.
6. **Проверим перенос и сохранность прежнего.** Ученик пробует допустимый минимальный и максимальный приоритет, пустое название, неверный тип, прямой вызов фабрики, корректное добавление и вызов поиска несуществующего id. Локальный результат: существующие `list/find/search/stats/done` и диспетчер продолжают работать, `find_task` по-прежнему возвращает `None`, `mark_task_done` по неизвестному id — `False`; в работе с ошибочным названием нет нового id или ложного сообщения об успехе. Дополнительный перенос: объяснить, почему одна проверка в reader не защитила бы вызов `add_task` из другого кода.

Эти шаги показывают B разными наблюдениями: валидатор отвергает плохое значение, фабрика не создаёт невалидную запись, `add_task` не меняет список при отказе, а CLI сообщает причину без ложного успеха. Исследование `else/finally` проверяет понимание ветвей и не меняет продукт.
