## 00. Вступление

Planner уже сохраняет полный снимок и проверяет его до использования. Теперь нужно определить, что приложение считает первым запуском, а что — настоящим отказом, и как оно сообщает, что изменение не удалось сохранить.

1. **Точка старта:** после 30.1 корректный снимок целиком проверяется до CLI и записи (пока это плановая опора).
2. **Новый вопрос:** как не спутать отсутствие файла с повреждением и не назвать изменение сохранённым после ошибки записи?
3. **Результат:** ожидаемые ошибки получают ясную границу и причину, а отказ не превращается в тихую потерю данных.

Сначала различим причины, затем свяжем их с поведением storage и сборки. Так мы завершим прежний функциональный Planner и передадим следующему занятию устойчивую опору на словарях и JSON.

## 01. Отсутствие файла и отказ чтения

- **Понятие до применения.** Загрузка читает выбранный `tasks.json`, затем разбирает текст как JSON и проверяет список задач. Это **три разных действия**. `FileNotFoundError` означает, что файл не найден при открытии; `JSONDecodeError` — что прочитанный текст нельзя разобрать как JSON; ошибка проверки снимка — что JSON разобрался, но не соответствует договору Planner; `OSError` при файловой операции включает, например, отказ доступа или попытку открыть каталог как файл. Только `FileNotFoundError` **именно от открытия выбранного файла на чтение** допускает первый запуск с `[]`. Объяснить, почему ловить его вокруг всей загрузки опасно: ошибка в другом месте могла бы ошибочно превратиться в пустую базу.
- **Независимый пример, ещё без storage.** Предъявить четыре карточки с одним путём `data/tasks.json`: (а) файла нет; (б) файл содержит незакрытую скобку `[`; (в) содержит корректный JSON `{}` вместо списка; (г) по пути находится каталог. До показа ответов предложить назвать этап отказа и предсказать, появится ли пустое меню. Разобрать разницу: только (а) означает законный первый запуск; (б–г) прекращают загрузку, исходное содержимое/каталог остаются без изменений.
- **Первое действие ученика:** самостоятельно отсортировать ситуации по четырём исходам «нет файла / сломан JSON / неверная форма / файловый отказ» и объяснить, почему содержимое `[]` — это *существующий* пустой снимок, а отсутствие файла — другой повод получить пустой список в памяти. Критерий: он не предлагает записать `[]` поверх повреждения.
- **Опора для возврата:** на чтении сначала спросить «файл найден?», затем «JSON разобран?», затем «валиден ли список?»; ошибка файловой операции не означает повреждённый JSON. После распознавания причины можно ввести единый тип ошибки для вызывающего кода.

## 02. StorageError сохраняет источник отказа

- **Понятие и смысл.** `StorageError` — наш подкласс `Exception` в `app.errors`: вызывающая сборка узнаёт «не удалось прочитать или сохранить состояние» по **одному типу**, независимо от системного текста ошибки. Он отличается от `TaskNotFoundError`: неизвестный id — ошибка предметной команды, с файлом всё может быть в порядке. У `raise StorageError("...") from error` слово `from` связывает новое исключение с исходным: короткое пользовательское сообщение не стирает техническую причину (`__cause__`). Имя `error` — локальная переменная из `except ... as error`, а не новая функция.
- **Независимый пример до проекта.** В уже знакомом `try/except` преобразование `int("один")` даёт `ValueError`; показать *фрагмент внутри except* `raise StorageError("Не удалось прочитать данные") from error`. До выполнения попросить предсказать верхний тип и нижнюю причину; затем разобрать цепочку «ValueError → StorageError», не представляя любое `ValueError` приложения как отказ диска.
- **Порядок на границе storage:** при **чтении** отдельно обработать `FileNotFoundError` от `open` как `[]`, прочие ожидаемые `OSError` при открытии/чтении — как `StorageError`; `JSONDecodeError` — только вокруг разбора JSON; согласованный тип ошибки от `validate_loaded_tasks` — только вокруг проверки. При **записи** создать отсутствующий родительский каталог, проверить снимок и сериализовать его до открытия `w`; ожидаемый `OSError` создания каталога/открытия/записи — `StorageError`. В каждой ветке причина остаётся через `from`. Конкретный тип ошибки валидатора сверить с договором 30.1; не ловить весь `load_tasks` через `except Exception` и не переводить случайные `NameError`/ошибки программирования в сбой файла.
- **Первое действие:** по трём коротким фрагментам «`except JSONDecodeError` вокруг разбора», «`except OSError` вокруг `open`» и «`except Exception` вокруг всего CLI» определить две допустимые узкие границы и объяснить недостаток третьей. Результат — ученик может выбрать место перехвата до правки проекта. Дальше единый `StorageError` сможет принять сборка.

## 03. Невалидное хранилище не запускает меню

- **Механизм.** `app.main` — место сборки: выбирает один путь, запрашивает `load_tasks(path)` и **только после успешного результата** вызывает прежний `run(tasks, on_change)`. Если storage выбросил `StorageError`, граница сборки выводит понятное сообщение и заканчивает запуск до `run`; команды не доступны, сохранения не происходит. Если файла просто не было, `load_tasks` возвращает `[]`, и меню запускается; это не обработка общего отказа.
- **Независимая трассировка.** Нарисовать путь «файл → чтение → разбор JSON → проверка снимка → run() → меню». Показать метку сбоя сначала на «разбор JSON», затем на «проверка снимка». Ученик сам отмечает последнюю выполненную стрелку: в обоих случаях до `run()` не доходим. На существующем корректном `[]` все проверки проходят, меню доступно.
- **Первое действие:** расположить условный обработчик `StorageError` на границе сборки вокруг загрузки и сессии, не прятать отказ внутри storage возвратом `[]`; предсказать, меняется ли файл после запуска с `{"не":"список"}`. Критерий: файл и меню не изменяются, вместо «первый запуск» видно сообщение об отказе. Переход к следующему: загрузку защитили, но во время сессии запись вызывается отдельным callback.

## 04. Отказ записи завершает текущую сессию

- **Понятия.** `on_change(tasks)` — уже введённая в 30 функция обратного вызова: её вызывает обработчик **после изменения списка в памяти**, чтобы сохранить полный снимок. *Изменено в памяти* и *записано в файл* — два события; `StorageError` не отменяет уже сделанное изменение. Сообщение «Задача добавлена/завершена» означает подтверждённый успех только после возврата из callback без ошибки.
- **Независимая трассировка:** «add меняет список → вызывает on_change → save_tasks пытается писать → возвращается без ошибки → печатаем успех». Второй сценарий отличается только на шаге записи: появляется `StorageError`; попросить указать, какие стрелки не исполнятся, и что останется в памяти. Разобрать: сообщение успеха и следующий пункт меню не появляются, память могла измениться, исходный файл может остаться прежним либо частично перезаписанным (зависит от момента отказа).
- **Первое действие:** ученик размещает вызов callback *перед* сообщением успеха и прогнозирует поведение на ошибке; сборка ловит `StorageError` на выходе из `run`, сообщает, что **сохранение не подтверждено**, и завершает сессию. Нет автоматического повторного `save` при `exit`, в `finally` или после перехвата. Для `list`, неудачного ввода, неизвестного id и повторного `done` callback не вызывается — текущий договор 30 сохраняется.
- **Опора:** порядок «изменение → подтверждение записи → сообщение успеха»; если средний шаг не удался, нельзя вести обычную сессию дальше. Различие понадобится для понимания ограничений `w`.

## 05. Режим w и пределы сохранности

- **Понятие до применения.** Режим `w` открывает файл на перезапись: прежнее содержимое может быть очищено уже при успешном открытии. `with` закрывает файл, но не делает запись неделимой. *Атомарная замена* — будущий, пока не реализуемый способ заменить старый файл целиком или не заменять его; текущий `w` этого не обещает.
- **Независимый мысленный опыт.** В файле была строка `старый снимок`; программа открыла его с `w` и после части нового JSON потеряла возможность дописать. Попросить предсказать, сохранится ли старое содержимое. Оно могло уже исчезнуть, новый JSON может быть обрезан: `StorageError` лишь сообщает проблему. В отличие от этого, отказ проверки модели **до `open(..., "w")`** сохраняет прежние байты.
- **Первое действие:** ученик объясняет, почему последовательность «валидировать → сформировать JSON-текст → открыть `w` → записать» безопаснее варианта с ранним открытием. Для опытов с отказом выбрать учебную копию и запасной сохранённый снимок; системные разрешения не менять, искусственный обрыв реального файла не требуется.
- **Граница честного обещания:** не добавлять к этому уроку транзакции, атомарное переименование, блокировку параллельных писателей, rollback или автоматическое восстановление. С этим ограничением проверяем доступные случаи без риска для единственного рабочего JSON.

## 06. Связать чтение, изменение и подтверждение

- **Сборка причин и наблюдений.** На доске две ветки одной сессии: (1) загрузка выдаёт проверенный список или прекращает запуск; (2) команда может прочитать список без записи, реально изменить его и вызвать callback либо завершиться с предметной ошибкой без callback. Успех изменения показываем после подтверждённой записи. Связать каждую ветку с опорами из 01–05, не объяснять заново JSON-формат и четырёхпольную валидацию 30.1.
- **Первое самостоятельное применение:** без запуска кода для последовательности «list → неверный приоритет → done с неизвестным id → add → первый done добавленной задачи → повторный done той же задачи → exit» предсказать число вызовов сохранения в успешном случае (**два**: на `add` и первый `done`); затем заменить успешную запись `add` отказом и предсказать оставшиеся действия (**не выполняются**, сессия завершена). Повторный `done` не сохраняет, поскольку статус уже не изменился.
- **Опора для практики:** перед каждым опытом записать три наблюдения: «показано ли меню/успех», «вызван ли save», «изменился ли JSON». Разделять фактический результат и предположение; для проверки отсутствия записи сравнить байты учебного файла до/после, а для сбоя записи проверить сообщение и отсутствие продолжения. Затем восстановить корректный снимок и выполнить штатный путь два раза.
- **Переход:** практика меняет один существующий Planner; следующему блоку передаётся функциональная версия на словарях с работающим JSON, без класса `Task`.

## 07. Что мы будем делать в практике

**Формат:** изменение существующего проекта (`MANUAL_PRACTICE`), самостоятельная запись кода и ручная проверка через прежний CLI и отдельно настроенный диагностический путь. **Исходная опора:** запланированные результаты 30/30.1 — пакет `app`, рабочий JSON, проверка всего снимка и callback после изменения. На локальном HEAD `142d81a` эти предпосылки не подтверждены: до занятия проверить код ученика на успешную загрузку/сохранение, отказ при неверной форме, порядок callback и знакомство с `raise ... from ...` из 27.1. Если отсутствуют, сначала завершить соответствующий предыдущий результат; этот план их не реализует заново.

Общий результат — один Planner различает первый запуск и реальные отказы, не объявляет неподтверждённое сохранение успехом и продолжает штатно работать после восстановления корректных данных.

1. **Самостоятельно оформить границу хранения (опора 01–02).** **Объект:** существующие `app.errors` и `app.storage`, уже готовые `load_tasks/save_tasks/validate_loaded_tasks`. **Действие:** добавить `StorageError` и узкие перехваты ожидаемых ошибок чтения, разбора, проверки и записи, сохраняя причину через `from`. Развести `FileNotFoundError` от открытия **выбранного файла для чтения** и другие `OSError`; при записи оставить создание родительского каталога. **Обычный результат:** корректный JSON читается/пишется как раньше; отсутствие файла на чтении даёт `[]`. **Различающий случай:** повреждённый JSON даёт `StorageError` с исходным `JSONDecodeError`, а случайная программная ошибка не замаскирована как «ошибка диска». Сверить тип ошибки валидатора из 30.1, прежде чем писать конкретный `except`; не перехватывать весь проект. **Сохранность:** не переписывать валидатор и существующую сериализацию.
2. **Самостоятельно защитить запуск и подтверждение записи (опора 03–04).** **Объект:** текущий `app.main` и место сообщения об успешных add/done в обработчиках. **Действие:** поставить обработку `StorageError` на границе загрузки и сессии, после ошибки заканчивать запуск; вывод успеха перенести *за* успешный callback, если он сейчас стоит раньше. **Обычный результат:** корректная загрузка открывает меню, изменение вызывает одну запись и только после неё сообщение успеха. **Различающие случаи:** неверный снимок заканчивает запуск до `run`, не пишет файл; отказ callback показывает ошибку о неподтверждённом сохранении, не печатает успеха, не открывает следующую команду и не вызывает скрытый повторный save на exit/`finally`. **Сохранность:** прежние команды, аргументы и путь штатной сборки сохраняются.
3. **Самостоятельно проверить матрицу отказов на учебной копии (опора 01, 03, 05).** **Объект:** отдельная копия каталога проекта с собственным `data/tasks.json` и заранее сохранённым корректным снимком; рабочий проект не трогать. **Действие:** по одному подготовить пять состояний: отсутствующий файл; текст `[`; валидный JSON `{}` вместо списка; каталог вместо файла для **чтения**; каталог вместо файла для **записи** (через прямой учебный вызов `save_tasks` с диагностическим путём). Не изменять права файлов. **Локальный результат:** только первый случай возвращает `[]` и допускает меню; остальные случаи дают ожидаемый `StorageError` с отличимой причиной. При неверных данных нет меню, исходный повреждённый файл не затирается. **Различающий тест записи:** чтение сделать из *корректного* файла учебной копии, а для callback в диагностическом запуске выбрать путь-каталог и затем изменить задачу; убедиться, что нет успеха, продолжения меню и повторного save. Вернуть штатный callback после опыта. Так ошибка записи проверяется после успешной загрузки, а не маскируется предыдущей ошибкой чтения.
4. **Самостоятельно доказать отсутствие лишних записей (опора 04 и 06).** **Объект:** корректная учебная копия и известный из 30 способ временно наблюдать вызовы callback. **Действие:** зафиксировать содержимое и число вызовов, пройти `list`, `find`, `search`, `stats`, неверный приоритет, неизвестный id, повторный `done`, неизвестную команду и `exit` без изменений. **Обычный результат:** данные и число сохранений не изменились; add и первое реальное done добавляют ровно по одному вызову. **Различающий случай:** повторное `done` не сохраняет даже при существующем id; при сбое записи этот эксперимент прекращается вместе с сессией. **Сохранность:** убрать временную диагностику и не добавлять запись в читающие обработчики.
5. **Самостоятельно восстановить штатный путь в двух процессах (опора 05–06).** **Объект:** возвращённый из копии корректный четырёхпольный JSON. **Действие:** в первом запуске добавить задачу с кириллицей, затем завершить её; завершить процесс.
