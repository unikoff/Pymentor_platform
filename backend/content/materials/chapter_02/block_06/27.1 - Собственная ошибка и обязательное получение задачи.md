## 00. Вступление

Planner уже умеет искать задачу и сообщать, если поиск ничего не нашёл. Но поиск и действие над обязательным объектом отвечают на разные вопросы: первому можно вернуть отсутствие, второму нужно явно сообщить, почему продолжить нельзя.

1. **Точка старта:** `find_task` возвращает задачу или `None`, а обработчик завершения различает найденный и неизвестный id.
2. **Новый вопрос:** как выразить отказ операции, которой обязательно нужна существующая задача, не смешав его с обычным пустым результатом?
3. **Результат:** ввести тип ошибки и функцию обязательного получения, сохранить прежний поиск и понятный ответ CLI.

Маршрут ведёт от известного результата и `raise` к собственному смысловому типу отказа, а затем — к его обработке на границе интерфейса.

## 01. Отсутствие как результат и как отказ

- **Что и зачем:** поиск иногда имеет честный ответ «ничего не нашлось». `None` — специальное значение Python для отсутствующего результата. Но когда действие невозможно без предмета, вызывающий код должен узнать о невозможности продолжить. Это решение зависит от обещания функции, а не только от введённого номера.
- **Независимый пример до проекта:** в библиотеке вопрос «Есть ли книга №8?» допускает ответ «нет» (`None`), а команда «Выдай книгу №8» требует существующей книги; без неё действие не выполняется. Сопоставить два исхода для известного и неизвестного номера, не вводя нового способа обхода коллекций.
- **Первое действие ученика:** перед кодом `get_task` выбрать на схеме, какой вызов вправе вернуть `None`, а какой должен остановиться с ошибкой, и объяснить выбор. Учебная вставка будущего MAIN — содержательный прогноз на двух случаях с пояснением.
- **Опора и путаница:** `None` сам по себе не исключение; даже правильно введённый числовой id может отсутствовать. Проверочный вопрос: «Можно ли продолжить без найденного предмета?» Если да — обычный поиск, если нет — обязательное получение.
- **Переход:** этот отказ полезно узнавать по типу, а не по случайным словам в сообщении.

## 02. Собственный тип прикладной ошибки

- **Что и зачем:** `ValueError` подходит к неверному значению (например, текст вместо числа), а другой тип может означать «номер допустим, но предмет с ним отсутствует». `except` проверяет тип; текст сообщения не должен управлять обработчиком.
- **Независимый пример и механизм:** на ситуации с ячейкой хранения объяснить форму `class LockerNotFoundError(Exception):` и `pass` с отступом. `class` объявляет новый тип; `Exception` даёт готовое поведение ошибки; `pass` означает, что больше команд в теле нет. Запись `LockerNotFoundError("Ячейка не найдена")` создаёт ошибку с текстом; `raise` сообщает о ней, `except LockerNotFoundError as error` перехватывает, `error` — имя пойманного значения, `str(error)` — его текст. Эти формы показать **до** первого требования написать собственный класс.
- **Первая самостоятельная попытка:** ученик предсказывает, какой из соседних `except LockerNotFoundError` / `except ValueError` сработает. Затем меняется только текст сообщения: тот же `except` продолжает срабатывать. Ученик своими словами объясняет `pass` и скобки `(Exception)`.
- **Опора и граница:** не проверять подстроку «не найдена», не ловить всё через `except Exception`. Здесь ещё не изучаются `self`, `__init__`, иерархии предметных классов и устройство модели Task.
- **Переход:** теперь смысловой тип можно применить к знакомому поиску задач.

## 03. `get_task` поверх готового поиска

- **Что и зачем:** `find_task(tasks, task_id)` уже ищет по списку и возвращает словарь или `None`. `get_task` решает, что делать с **этим** ответом: найденный словарь вернуть; при `None` поднять `TaskNotFoundError`. Повторный `for` запрещён: алгоритм поиска остаётся один.
- **Разбор механизма:** на входе `tasks = [{"id": 2, ...}]` проследить два id: 2 и 9. Оба проходят через `find_task`; для 2 `get_task` возвращает прежний объект, для 9 `raise` завершает обычное выполнение. Перед первым кодовым действием показать смысл `is None` как точного сравнения с отсутствием, не заменять его расплывчатой проверкой любого ложного значения.
- **Первая попытка:** ученик без кода заполняет таблицу «id → `find_task` → `get_task`» для 2 и 9, отмечает, где выполнение останавливается, и объясняет, почему не нужен второй цикл.
- **Опора/переход:** `find_task` сохраняет договор `dict | None`; исключение возникает **только** в обязательной операции. Далее разберём, как эта ошибка дойдёт до интерфейса.

## 04. Распространение и точный перехват в CLI

- **Что и зачем:** `raise` останавливает обычный ход функции и передаёт ошибку тому, кто её вызвал, пока не встретится подходящий `except`. `get_task` знает, что задача отсутствует; `handle_find` знает, какую фразу показать человеку. Это разные обязанности.
- **Две трассы на знакомой команде:** `handle_find → get_task → find_task` при известном id: словарь возвращается назад, печатается карточка. При неизвестном: `find_task → None → get_task → raise TaskNotFoundError → except TaskNotFoundError` в `handle_find`: выводится «Задача не найдена», затем меню принимает новую команду. Нарисовать учебную цепочку со стрелками, чтобы ученик назвал место возникновения и место обработки.
- **Форма и первое действие:** до правки обработчика объяснить `try`, `except TaskNotFoundError as error` (`as error` нужен лишь для обращения к сообщению) и расположение вывода карточки только на успешной ветке. Попросить ученика спрогнозировать вывод для двух id и объяснить, почему `except ValueError` не ловит новый тип, а `except Exception` скроет постороннюю ошибку программы.
- **Опора/граница:** пользователь видит привычную фразу, техническое имя типа остаётся в коде. Не трогать обработку неизвестной **команды**: её выбор не является поиском задачи.
- **Переход:** тот же механизм нужен команде `done`, но её прежний договор `False` меняется, поэтому придётся согласовать вызывающий код.

## 05. Согласованное изменение завершения задачи

- **Что и зачем:** прежде `mark_task_done` возвращал `False`, если id не найден. После перевода на `get_task` для отсутствующего id поднимается `TaskNotFoundError`. Поэтому `handle_done` больше не может опираться на проверку `False`: функцию и её вызов меняем вместе.
- **Различающий пример:** задача №2 активна → её `is_done` становится `True`, возвращаемый успешный результат прежний; повторное `done` для №2 → задача остаётся выполненной, нет лишней записи или отказа; неизвестный №9 → ошибка **до** изменения списка и та же привычная фраза в CLI. Показать, в какой строке три пути расходятся, и что `find_task` не меняется.
- **Первая самостоятельная попытка:** дать фрагмент старого обработчика с условием `if not mark_task_done(...)` и предложить объяснить, почему он не покажет сообщение для отсутствующего id после изменения договора; ученик выбирает место конкретного `except`, не получая готовый `handle_done` до проекта.
- **Опора/переход:** успешный путь и повторное завершение остаются прежними; при отказе длина списка, значения `is_done` и остальные команды неизменны. Следующий раздел объяснит отдельный случай, когда новая ошибка действительно возникает из старой.

## 06. Причина ошибки и границы применения

- **Что и зачем:** иногда новая ошибка вызвана уже пойманной ошибкой. `raise НовыйТип("объяснение") from error` явно сохраняет связь причин для traceback. Для обычного результата `None` предыдущего исключения **не было**.
- **Независимый опыт:** `int("три")` поднимает `ValueError`. В `except ValueError as original` поднять новый `ValueError` с понятным сообщением через `from original`; показать, что диагностика содержит две ошибки и указание на прямую причину. На варианте без `from` отметить, что явной причинной связи нет, даже если Python показывает контекст. Не заучивать весь traceback.
- **Первое действие и граница:** ученик называет первичную и добавленную ошибки и объясняет назначение `from`; сравнивает с `get_task`, где поиск вернул `None` и связывать не с чем. В Planner не добавлять искусственную причину. Преобразование ошибок хранения и `StorageError` — только в 30.2.
- **Переход:** теперь проектная практика объединит поиск, конкретное исключение, узкую обработку и сохранение прежних действий CLI.

## 07. Что мы будем делать в практике

**Обязательный формат:** изменение существующего проекта StudyHub (П), а не отдельная учебная программа. Вход — одна рабочая версия `main.py` с `find_task`, `mark_task_done`, `handle_find`, `handle_done` и меню команд. Сначала проверить фактический договор этих функций и завершение самостоятельной практики 27 с `raise` (точка A пока планируемая; раздел «Точка A»). Заданные для проверки примеры: две задачи с разными id, например 2 и 5, обе сначала `is_done=False`; 9 отсутствует. Собственная работа ученика — новый тип, новая функция и адаптация существующих обработчиков; готовых целевых реализаций в задании не давать.

**Цель:** своими руками создать обязательное получение по id, которое использует прежний поиск, и сделать отказ понятным в `find`/`done` без потери остальных возможностей Planner. После каждого шага проверять короткий конкретный исход, прежде чем соединять части.

1. **Установим прежний результат → два наблюдения.** На текущем списке ученик сам вызывает `find_task` с 2 и 9: видит словарь задачи и `None`; сверяет, что `mark_task_done` пока отвечает `False` для 9 и список не меняется. Опора — §01 и известные функции из прежнего проекта. Это исходная точка сравнения, без нового кода.
2. **Назовём отказ → ловится точный тип.** Опираясь на отдельно разобранную ячейку хранения (§02), ученик **сам пишет** минимальный `TaskNotFoundError`, кратко поднимает его в учебном вызове и перехватывает `except TaskNotFoundError`. Локальный результат: перехват выбран по типу даже при другом тексте сообщения; `ValueError` не смешивается с «не найдена». Не писать модели Task, конструктор или обработчик «на всё».
3. **Добавим `get_task(tasks, task_id)` → словарь либо `TaskNotFoundError`.** После схемы §03 ученик **сам собирает** небольшую функцию из вызова `find_task`, проверки `is None`, возврата результата и `raise` в случае отсутствия. Для 2 возвращается прежняя задача; для 9 возникает ровно собственная ошибка, а список остаётся без изменений. Проверить, что прямой `find_task(tasks, 9)` всё ещё возвращает `None`: так легко заметить случайное изменение старого договора. Не давать готовое тело `get_task` или второй цикл `for`.
4. **Переведём `handle_find` → сообщение и работающий следующий ввод.** По двум трассам §04 ученик сам заменяет старую проверку `None` на вызов `get_task` и точный `except`. В меню команда `find`, затем ввод id 2 показывает ту же карточку; команда `find`, затем id 9 показывает прежнее «Задача не найдена» ровно один раз, и следующая команда `list` срабатывает. `ValueError` другого ввода продолжает обрабатываться по прежним правилам; меню целиком не оборачивать в `except Exception`.
5. **Согласуем `mark_task_done` с `handle_done` → новое условие отказа.** По §05 ученик сам вызывает `get_task` внутри прежней операции завершения, сохраняет её успешный результат и исправляет **все** места, ожидавшие `False` при неизвестном id. Команда `done`, затем id 2 впервые меняет только `is_done` задачи 2 на `True`; повторное выполнение команды с id 2 остаётся допустимым с прежним результатом; команда `done` с id 9 выдаёт «Задача не найдена», меню не прерывается, значения и количество задач не изменяются. Проверить отсутствие устаревшего пути обработки `False` именно для неизвестного id.
6. **Проверим весь путь → доказательство B.** В одной сессии выполнить `find` для 2 и 9, `done` для 2 дважды и для 9, затем `list`/`stats` и одну ранее работавшую команду `add` или `search`; сравнить содержимое списка до и после неудачных вызовов. Результат: незнакомый id даёт прикладную ошибку внутри кода и понятный текст в интерфейсе, знакомый id работает как прежде, неизвестная команда остаётся прежним случаем выбора команды. Объяснить своими словами, где ответом служит `None`, где нужен `raise`, где стоит `except` и почему для `None` не нужен `raise ... from` (§01–06).

Порядок шагов даёт самостоятельность по нарастающей: сначала наблюдение знакомого, затем собственное объявление ошибки и функция, затем два настоящих пути CLI. При затруднении ученик возвращается к указанному разделу, но получает от него **иной пример** или схему, а не готовое решение проектной функции. Малый проверочный перенос: при другом отсутствующем id (например, 15 вместо 9) ученик предсказывает и подтверждает то же поведение без изменения кода. `raise ... from` исследуется на независимом опыте §06, не становится искусственной частью поиска задач. На следующем занятии 28 созданные функции и тип **планируется** перенести в модули; сейчас модули не создаются.
