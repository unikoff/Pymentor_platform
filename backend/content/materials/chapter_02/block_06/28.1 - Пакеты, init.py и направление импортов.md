## 00. Вступление

В предыдущем запланированном занятии код Planner разделяется на модули с сохранением поведения. После проверки этого результата файлам нужна общая граница и однозначный путь, по которому приложение найдёт их при запуске.

1. **Точка старта:** модули существуют отдельно, а безопасный импорт и точка входа уже знакомы.
2. **Новый вопрос:** как собрать эти файлы в пакет и связать их так, чтобы запуск находил нужные модули без обратных зависимостей?
3. **Результат:** существующий Planner работает как пакет app, а его импорты направлены от точки сборки к нижним правилам.

После триады ученик сравнивает два расположения одних и тех же файлов и отвечает, изменится ли работа самих предметных функций: **нет**, меняются адреса модулей. Переход к пакету не создаёт новый Planner. Сначала разберём границу пакета, затем путь импорта и запуска, после чего проследим и исправим обратную связь между модулями.

## 01. От модулей к пакету app

**Первое объяснение.** Модуль — файл `.py`; каталог (папка) организует файлы, но сам по себе ещё не объясняет, как к ним обращаться из Python. **Обычный пакет** — каталог с `__init__.py`, чьи модули получают общее начало имени. Нарисовать до/после для *независимого* примера «магазин»:

```text
до:                    после:
prices.py              shop/
discounts.py             __init__.py
                         prices.py
                         discounts.py
```

Имя `prices` внутри пакета становится `shop.prices`: точка означает вложенность имён, а не часть названия файла. Как адрес «улица → дом», `shop.prices` помогает указать место; аналогия не объясняет, как Python выбирает начальную папку — это будет в §03. Число файлов и перенос сами по себе не улучшают архитектуру.

**Первая попытка:** без подсказки в коде ученик указывает полный путь `shop.discounts` и отвечает, изменится ли смысл функции скидки при переносе (нет). **Наблюдение:** в обоих расположениях имена файлов прежние; изменился путь. Затем перейти к роли `__init__.py`, который делает границу обычного пакета явной.

## 02. Роль `__init__.py`

**Механизм.** `__init__.py` — файл внутри каталога обычного пакета; он может быть пустым. При импорте `shop.prices` Python сначала загружает пакет `shop` и выполняет содержимое его `__init__.py`, затем модуль `prices.py`. Если файл пуст, он не импортирует другие части приложения и не запускает меню. Бывают и другие виды пакетов, но для Planner нужен именно простой вариант с пустым файлом.

**Независимое наблюдение:** сравнить `shop/__init__.py` пустой и вариант с `from shop.prices import base_price` внутри: во втором варианте импорт `shop` дополнительно обращается к `prices`. **Самостоятельное решение:** ученик выбирает для Planner пустой `app/__init__.py` и объясняет почему: достаточно границы, а дополнительные импорты могут запутать зависимости. Дальше нужен точный путь от имени пакета до модуля.

## 03. Абсолютный импорт и путь поиска

**Сначала путь поиска.** Назовём *корнем проекта* папку, внутри которой лежит `shop/` (позже `app/`). В Python есть список папок для поиска модулей — `sys.path`; при рекомендованном запуске из корня нужная папка доступна. **Абсолютный импорт** указывает имя целиком от доступного пакета, а не от расположения импортирующего файла.

```python
# независимый пример: shop/discounts.py
from shop.prices import base_price  # пакет -> файл -> имя
```

Сопоставить `from shop.prices import base_price` с `from .prices import base_price`: точка во втором случае означает текущий пакет, это **относительный импорт**, он требует пакетного контекста. Стиль Planner — абсолютный `from app.validators import ...`, потому что он явно показывает связь. `from validators import ...` ищет верхнеуровневое имя `validators`, которое после переноса файлов может оказаться недоступным или чужим модулем.

**Первый прогноз:** ученик получает дерево `shop/` с `prices.py`, видит две записи `from shop.prices ...` и `from prices ...` и выбирает однозначную при запуске из корня; объясняет путь словами «корень → shop → prices». Показать, что простое нахождение файла «рядом» не обещает успеха абсолютного импорта. Чтобы путь был воспроизводим, далее вводим способ запуска.

## 04. Запуск пакета через -m

**Различающий случай.** В команде `python app/main.py` Python запускает файл как скрипт и обычно включает папку `app/` в начало пути поиска. В `python -m app.main` Python ищет модуль по *имени пакета*; если команда выполнена из корня проекта, корень участвует в поиске. Поэтому абсолютные импорты `app...` для курса проверяем командой:

```text
# терминал открыт в корне проекта, рядом виден каталог app/
python -m app.main
```

`-m` означает «выполни модуль по имени». Защита `if __name__ == "__main__":` из §A остаётся в `app/main.py`: при прямом исполнении через `-m` условие истинно, при `import app.main` ложно. Ошибка `ModuleNotFoundError: No module named 'app'` при запуске из неверной папки прежде всего требует проверить рабочую директорию, а не менять импорты наугад. У запуска файла могут быть частные исключения из-за настроек среды; учащемуся достаточно **одной** рекомендованной команды.

**Самостоятельный прогноз до исполнения:** какое действие откроет меню — `import app.main` или `python -m app.main`? Ученик обосновывает ответ через `__name__` и позже сравнивает с наблюдением на своём проекте (§07). После предсказуемого старта важно проверить, откуда модули берут правила и состояние.

## 05. Направление зависимостей внутри пакета

**Понятие до схемы:** зависимость «A → B» означает, что модулю A нужно имя из B, поэтому A импортирует B. У одностороннего пути легче найти владельца данных:

```text
app.main  ->  app.operations  ->  app.models
                         |--->  app.validators
                         `--->  app.errors (если нужна ошибка)
```

`main` владеет запуском и списком текущей сессии, `operations` выполняет действия над **переданным** списком, `models` строит данные, `validators` проверяет значения, `errors` содержит типы ошибок. Стрелки показывают *допустимые зависимости*, а не обязательный импорт каждой ветки. Как односторонние указатели в коридоре, схема показывает направление доступа; в отличие от коридора Python ещё и **исполняет** код модулей при первом импорте (§06).

**Независимый прогноз:** если модулю `shop.discounts` нужна цена, он импортирует `shop.prices`; должен ли `shop.prices` для этого импортировать `shop.discounts`? Нет. **Перенос:** в Planner нижний `app.operations` получает список аргументом функции, но не импортирует переменную со списком из `app.main`; CLI остаётся в `app.main` до 28.2. Теперь покажем, почему обратная стрелка иногда приводит к ошибке ещё до запуска функций.

## 06. Циклический импорт и его исправление

**Только теперь цикл:** A импортирует B, а B импортирует A. Python начинает выполнять A сверху вниз, встречает импорт B, начинает B; если B сразу запрашивает имя A, до которого выполнение A ещё не дошло, имя пока недоступно. «Частично инициализированный модуль» означает именно незавершённое выполнение тела модуля, а не отсутствие файла.

```python
# demo/a.py
from demo.b import second

def first():
    return 1
```

```python
# demo/b.py
from demo.a import first

def second():
    return 2
```

Трассировка **при первом `import demo.a`**: исполнение `a` приостанавливается на запросе `second` → запускается `b` → `b` сразу запрашивает `first` из ещё незаконченного `a` → `first` ещё не определена → `ImportError` с сообщением о частичной инициализации. При другом расположении определений цикл может не падать сразу; само наличие двух взаимных импортов всё равно мешает ясной ответственности. На двух колонках показать также ситуацию без обратного импорта: `b` объявляет `second` самостоятельно, `a` импортирует `second`, обе функции становятся доступны.

**Первая попытка без исправления на месте:** ученик отмечает в цепочке первый запрос к несуществующему пока имени и выбирает, какую стрелку убрать, чтобы `demo.b` не требовал ничего из `demo.a`. В реальном Planner аналогично нижний `validators` не должен импортировать `operations`. Общее правило уходит в нижний модуль, нужное состояние передаётся аргументом. Перенос `import` внутрь функции иногда откладывает ошибку, но не устраняет встречную ответственность. Теперь ученик может сам диагностировать отдельный фрагмент, сохранив рабочий пакет без намеренной ошибки.

## 07. Что мы будем делать в практике

**Формат и исходная опора:** проектная работа в существующем Console Planner **после проверки B занятия 28**; отдельно — разбор небольшого ошибочного фрагмента без включения его в рабочий проект. Исходные `main.py`, `models.py`, `validators.py`, `operations.py`, `errors.py` берутся из результата ученика; полный новый код Planner в заготовке не выдаётся.

Результатом станет тот же Planner внутри пакета app, с понятным запуском и однонаправленными импортами.

1. **Соберём пакет (опора §01–02).** Вход: реальные пять `.py` рядом с корнем и рабочие команды до переноса. Объект: каталог `app/`. Ученик сам переносит прежние файлы в `app`, создаёт **пустой** `app/__init__.py` и сохраняет корень репозитория/Git-историю; если прежний корневой `main.py` остаётся для совместимости, в нём допустима только защищённая передача запуска, без второго списка или дублированных функций. **Локальный результат:** дерево соответствует `app/{__init__,main,models,validators,operations,errors}.py`; содержимое предметных функций не переписано. Отличающий случай: внутри `__init__.py` нет импортов других модулей и запуска меню.
2. **Согласуем импорты (опора §03 и §05).** Вход: перемещённые прежние файлы. Объект: все межмодульные импорты и их стрелки. Ученик самостоятельно заменяет пути на абсолютные от `app`, рисует цепочку `main → operations → models/validators/errors`, удаляет обратные запросы к `main`, если есть, и объясняет, откуда `operations` получает рабочий список (аргумент функции). **Локальный результат:** импорт каждого нужного имени соответствует существующему файлу, нижние модули не импортируют `app.main`; `from validators ...` как верхнеуровневый путь после переноса не остаётся.
3. **Проверим импорт отдельно от запуска (опора §02–04).** Из терминала **в корне проекта** ученик сам выполняет `python -c "import app; import app.models; import app.operations; import app.main; print('imports ok')"`. **Локальный результат:** печатается `imports ok` без меню и ожидания ввода. Затем `python -m app.main` показывает привычное меню, после команды выхода процесс завершается. Отличающий случай: при запуске из другой директории `No module named 'app'` объясняется контекстом поиска, а не удалением префикса `app`.
4. **Найдём и исправим цикл (опора §05–06).** Вход: **иной** предоставленный фрагмент из двух модулей `reports.report` и `reports.formatter`: `report` запрашивает `format_title` из `formatter`, а `formatter` сверху запрашивает ещё не определённое имя `make_report` из `report`. Ученик **до просмотра исправления** отмечает порядок выполнения и первое недоступное имя, выбирает стрелку на удаление и записывает итоговое направление зависимости. **Локальный результат:** объясняет, почему возникла частичная инициализация и как изменился путь, показывает импорт исправленного отдельного примера; проектный пакет остаётся работоспособным. Отличающий случай: перенос `import` внутрь функции без изменения зависимости не засчитывается как объяснение исправления.
5. **Подтвердим сохранение поведения (опора B занятия 28 и §04–05).** Ученик запускает `python -m app.main` и повторяет прежние сценарии **add → list → find/search → done → stats → exit**, а также прежний случай неверного ввода или неизвестного ID. **Локальный результат:** список в рамках одного процесса, статусы, сообщения и команды такие же, как до переноса; безопасный импорт из шага 3 повторно подтверждается только после исправлений, если импорты менялись. Нет нового storage/JSON и второго состояния.

**Покрытие B:** дерево и пустой `__init__.py` доказывают сборку пакета; импорт без меню и запуск через `-m` различают два режима; отдельная трассировка цикла проверяет причинное объяснение; регрессионные команды подтверждают сохранение Planner. Ученик сначала предсказывает на примере `shop/demo`, затем сам меняет реальный `app`, затем объясняет пограничный случай. Следующее занятие сможет выделить CLI из `app.main`, не меняя пакет заново.
