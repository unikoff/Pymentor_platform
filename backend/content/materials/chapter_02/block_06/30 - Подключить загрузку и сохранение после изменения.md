## 00. Вступление

Сейчас Planner умеет менять задачи, но список существует только пока работает процесс. После подготовки полного JSON-представления можно связать его с обычным запуском приложения.

1. **Точка старта:** по условию после самостоятельного прохождения 28–29.1 CLI работает с одним списком, а `app.storage` переводит полный список задач в JSON и обратно. До занятия этот факт нужно проверить по проекту, пока это планируемая опора.
2. **Новый вопрос:** как загрузить этот список до начала работы и сохранить его после реального изменения, чтобы следующий процесс продолжил с того же места?
3. **Результат:** сборка задаёт единственный путь, CLI сообщает о сделанном изменении, а storage сохраняет снимок и восстанавливает его при следующем запуске.

Эти три звена должны составлять одну историю: память хранит данные во время работы, файл — между запусками, а событие изменения указывает, **когда** снимок нужно обновить. В будущей подаче разместить сразу после трёх пунктов связующую схему `первый запуск → изменение → запись → новый процесс`, затем попросить ученика предсказать, что останется после закрытия процесса **без записи**. Это диагностирует исходное представление до новых терминов; переход — к разделу 01.

## 01. Состояние процесса и сохранённый снимок

**Что впервые объясняем.** *Процесс* — один запущенный экземпляр программы; его *память* содержит изменяемый список `tasks`, пока он работает. *Файл* — данные на диске, которые доступны следующему процессу. *Снимок* — полная копия состояния списка **на момент записи**, а не живая связь с объектами в памяти. Новая сессия не получает старый Python-объект: она создаёт список заново из текста. Из 29.1 известна пара `encode_tasks`/`decode_tasks`: первая превращает список в текст, вторая восстанавливает значения, **но сама по себе ничего не пишет на диск**.

**Как объяснить по шагам.** На доске изобразить два разных прямоугольника «процесс А» и «процесс Б» и общую полоску «файл». В А есть `[задача 1]`; после добавления `[задача 1, задача 2]`; сохранение заменяет снимок на диске; завершение А убирает список из памяти. Процесс Б при старте читает **последний сохранённый** снимок, а не историю действий А. При чтении новой задачи без изменения её полей файл менять незачем. Во время одной сессии `run`, обработчики и операции должны видеть один и тот же загруженный список.

**Независимый пример, до проекта.** В блокноте в памяти написать `items = ["хлеб"]`, получить строку JSON для списка, добавить `"чай"` в `items` и восстановить список из прежней JSON-строки. Показать два разных результата: текущий список содержит чай, восстановленный — нет. Отдельно изменить JSON-строку и повторить восстановление; это аналог нового сохранения, но без файлового IO. Пояснить: копия снимка устаревает после мутации исходного списка.

**Первое действие ученика.** Перед выполнением предсказать, содержится ли `"чай"` в старой JSON-строке и что появится после повторного кодирования. Ученик самостоятельно меняет список в маленьком примере и сверяет предсказание; при затруднении возвращается к определению снимка. **Локальный результат:** объясняет, почему возврат исходных значений после рестарта возможен только при сохранении, а JSON-кодек не запускается сам.

**Различающий случай и ритм подачи.** Попросить сравнить «прочитал две записи», «добавил третью» и «вышел»: только добавление меняет состояние. Для будущего MAIN после максимум двух объясняющих абзацев использовать трассировку с выбором «память / текст снимка» и затем короткий вывод; второй идентичный вопрос не нужен. **Опора:** «список — сейчас; снимок — на момент записи; рестарт — новый список из файла». **Переход:** нужен один владелец адреса файла, иначе разные процессы могут читать разные снимки.

## 02. Один путь и разделение ответственности

**Термины до действия.** *Путь* — адрес файла, не его содержимое. `Path` — знакомый из 29 объект для работы с путями; `__file__` показывает адрес текущего модуля, `.resolve()` получает абсолютный путь, `.parent` — каталог-родитель, а `/` у `Path` соединяет части пути. *Текущая рабочая папка* (`cwd`) — каталог, из которого запущена команда; это может быть не каталог проекта. *Сборка* — место, где приложение выбирает настройки, создаёт нужные компоненты и передаёт их друг другу: здесь `app.main` из 28.2.

**Порядок и ответственность.** При штатном запуске `python -m app.main` из корня проекта сборка вычисляет корень **от расположения** `app/main.py` (подняться от `app` на один уровень), затем создаёт объект пути `корень / "data" / "tasks.json"`. Этот путь передаётся аргументом в функции `app.storage`; сам storage не строит новый независимый путь. `app.cli` получает список и функцию уведомления, но не импортирует `app.main`, не открывает JSON и не выбирает место сохранения. Операции над задачами по-прежнему отвечают только за изменение списка. Объяснить отличие «путь задаёт сборка» от «файл обязательно уже существует»: это разные факты.

**Независимый пример.** У учебного набора заметок отдельно есть модуль `notes/main.py` и папка `data`. Показать на диаграмме, почему `Path("data/notes.json")` зависит от cwd, а путь от `__file__` указывает на одну и ту же папку заметок. Это пример **без** готовой цепочки файловых функций Planner и без изменения рабочего `tasks.json`.

**Первое действие.** Дать три подписи «адрес файла», «загрузить текст», «показать меню»; ученик назначает их соответственно сборке, storage, CLI и объясняет направление стрелок `main → storage` и `main → cli`. Затем самостоятельно составляет выражение `Path` для адреса учебного файла, имея только описанное положение `main.py`, и проверяет полученный абсолютный путь. **Критерий:** смена cwd не меняет выбранный адрес; чтение/запись остаются в storage. **Различающий случай:** два места выбора пути (в CLI и в storage) могут не совпасть, даже если файл называется одинаково.

**Подача и опора.** Одна схема из трёх модулей и стрелок + короткая проверка ответственности (не дублировать схему вопросом о тех же стрелках). Для возврата: «`app.main` выбирает `path`, `app.storage` использует `path`, `app.cli` о файле ничего не знает». **Переход:** с известным путём можно получить первый список **до** отображения меню.

## 03. Загрузка до начала пользовательской сессии

**Сначала форма договора.** `load_tasks(path)` — функция `app.storage`, принимающая готовый путь и возвращающая **список словарей**, с которым работают текущие операции. Чтение текста можно выполнить через `with path.open("r", encoding="utf-8") as file: ...` и `file.read()`; `with`, режим `r` и UTF-8 были исследованы в 29. Результат строки передаётся уже изученной `decode_tasks(text)`. Пояснить разницу: `read()` возвращает строку, `decode_tasks()` создаёт данные Python, `run(tasks=...)` получает **данные**, не JSON-строку. Не появляется второй список, который отдельно нужно поддерживать в актуальном состоянии.

**Путь запуска.** Сначала `app.main` выбирает `path`; затем `load_tasks` получает и декодирует файл; только после успешного возврата список передаётся в `run`. Если изначально рабочий файл отсутствует, это первый запуск: `load_tasks` возвращает `[]` и меню работает с пустым списком. Показать форму узкого `try` с `except FileNotFoundError` **вокруг открытия выбранного файла для чтения** и отдельным `return []` для этого случая; повторить назначение `try/except` из 26.1. Не ловить весь код `except Exception`, не объявлять ошибку чтения эквивалентом отсутствию файла.

**Независимый пример.** Для временной `shopping.json` показать три входа в `load_notes`: файла нет; файл есть и содержит `[]`; файл есть, но текст `[` не закрыт. В первых двух случаях список пуст, **причина разная**; в третьем восстановление невозможно. Рассказать, что `FileNotFoundError` от чтения конкретного пути отличается от отказа доступа, каталога вместо файла или `JSONDecodeError`; в этом уроке сохраняется исходная ошибка, а единый `StorageError` будет позже в 30.2.

**Первое действие.** Ученик получает **только** текстовый алгоритм действий «открыть → прочитать → декодировать → вернуть» и самостоятельно упорядочивает четыре операции, назначает каждой форму `path.open`, `read`, `decode_tasks`, `return`. Проверяет функцию на временной учебной копии с `[]` и отсутствующим файлом, не на рабочих данных Planner. **Локальный результат:** `load_tasks` возвращает `[]` при отсутствии и полный прежний список при существующем корректном JSON; никакое меню ещё не требуется.

**Различающий случай, ритм, опора.** Сравнить три карточки «не создан», «нечитаем», «испорчен» и попросить ученика объяснить, в каком случае допустим пустой список. После объяснения и трассировки дать короткое задание на выбор ветки, без готового тела целевой `load_tasks`. Для возврата: «`r` → строка → `decode_tasks` → список; пусто только при `FileNotFoundError` для выбранного файла». **Переход:** загрузка дала актуальный список, но он ещё не будет жить после завершения процесса без записи полного снимка.

## 04. Полный снимок после изменения

**Что впервые объясняем.** `save_tasks(path, tasks)` — вторая файловая функция `app.storage`: получает **тот же** путь и **весь** список, преобразует его в JSON и записывает один актуальный снимок. Уточнить: *сериализация* означает получение текста из данных; *запись* означает помещение текста в файл. Это два действия, даже если их часто выполняют подряд. Список может быть пустым: сериализация `[]` даёт корректный снимок пустого набора, а отсутствие файла означает, что снимок ещё не записывали.

**Операции и порядок.** Сначала получить текст через `encode_tasks(tasks)` **до открытия на `w`**, чтобы ошибка преобразования сама по себе не уничтожила старый файл. Затем получить родительский каталог через `path.parent` и создать его средствами `mkdir(parents=True, exist_ok=True)` — объяснить значения обоих аргументов: `parents=True` создаёт отсутствующие промежуточные каталоги; `exist_ok=True` позволяет уже существующему каталогу остаться. После этого открыть **тот же путь** с `"w"`, кодировкой `utf-8`, записать готовый текст методом `write()`; `with` закрывает файловый ресурс при выходе из блока. Форма операций изучена в 29, но здесь важно их расположение.

**Независимый опыт.** Для учебного файла списка покупок сначала записать `["хлеб"]`, потом `["хлеб", "чай"]`. При `w` второй снимок **заменяет** первый; при `a` второй JSON-текст дописывается к первому и получится не один JSON-документ. Сначала попросить ученика предсказать строку в файле, затем проверить на отдельном пути: в рабочий `data/tasks.json` этот опыт не направлять.

**Первое самостоятельное действие.** Ученик получает перемешанные названия операций «создать папку», «сериализовать весь список», «открыть `w`», «записать текст» и обосновывает порядок; затем сам строит небольшую функцию для учебного файла с **другим** списком и проверяет повторную запись. **Локальный результат:** файл содержит ровно один JSON-массив, кириллица сохраняется, повторная запись не удваивает старые записи; при уже существующей папке запись работает без специальной ветки.

**Различающий случай и честная граница.** Поставить вопрос: «если `encode_tasks` падает, успел ли `w` обнулить файл?» — при правильном порядке нет; при отказе **во время записи** `w` может оставить частичный файл. Не обещать атомарность, транзакцию или автоматическое восстановление; это будущий курс защиты 30.2. Для MAIN чередовать схему «сначала текст — затем файл» с прогнозом двух режимов; не повторять вопрос о `w` второй карточкой. **Опора:** `encode_tasks` → `path.parent.mkdir` → `open("w", utf-8)` → `write` внутри `with`. **Переход:** функция умеет записывать, но ей нужно узнать, что список действительно изменился.

## 05. Callback связывает изменение с сохранением

**Термины до использования.** *Callback* — переданная другой функции функция, которую вызовут позже, когда случится нужное событие; здесь событие — **реальное изменение** списка. *Замыкание* — вложенная функция, которая при последующем вызове продолжает пользоваться переменной из внешней функции или области; знакомо по занятиям 24/24.1. `on_change` — понятное имя callback: его аргумент `tasks` означает **актуальный весь список**. Имя `path` не входит в его параметры, потому что путь уже известен сборке и доступен вложенной функции из внешней области.

**Независимый пример на ином сюжете.** Команда ведёт список заказов в памяти. Внешняя функция выбирает канал уведомлений, вложенная `notify(orders)` при изменении списка получает заказы и использует сохранённый канал. Отдельно продемонстрировать **разницу между ссылкой на функцию и вызовом**: `handlers["new"] = handle_new` только сохраняет функцию; `handlers["new"](orders, notify)` вызывает её. Создание таблицы не делает заказ и не вызывает уведомление. Этот пример не пишет файлы и не содержит готовый код `app.main` Planner.

**Контракт проекта и последовательность.** В сборке один раз выбирается `path`; выполняется `tasks = load_tasks(path)`; затем создаётся настроенный callback для вызова `save_tasks(path, updated_tasks)`; в CLI отправляются **оба** аргумента `run(tasks=tasks, on_change=...)`. `run(tasks=None, on_change=None)` означает: если список **не передали**, CLI создаёт начальный; если передали даже `[]`, использует его; если callback не дали (`None`), прежний запуск `run()` всё ещё работает в памяти. При выборе команды `run` вызывает сохранённый обработчик, передавая список и `on_change` в общем договоре. Читающим обработчикам допустимо принимать общий callback ради единой формы, но вызывать его им незачем.

**Первое действие ученика.** На независимой таблице из двух обработчиков «посмотреть» и «добавить» ученик самостоятельно показывает, когда значение callback существует, когда функция будет вызвана, и отслеживает число уведомлений: создание таблицы — ноль, чтение — ноль, одно успешное добавление — одно. В примере с заказами дважды вызвать **внешнюю функцию, которая возвращает вложенную `notify`**, — сначала с каналом «экран», затем с каналом «журнал» — и получить два callback с разными параметрами своих внешних вызовов. Предсказать, куда уведомит каждый; пояснить, что это две отдельные области вызова, а простое переприсваивание одной общей переменной могло бы изменить наблюдаемое значение. **Локальный результат:** ученик умеет описать и проверить передачу функции и списка без доступа CLI к `path`.

**Наблюдаемая схема и опора.** На одной трассировке стрелками `main (path)` → `run (tasks, on_change)` → `handle_*` → `on_change(tasks)` → `save_tasks(path, tasks)` дать прогноз количества вызовов для последовательности «показать, добавить». Критерий — **один** вызов после добавления; не считать само чтение событием. Подсказка для возврата: «`on_change` = функция, `on_change(tasks)` = её вызов; `path` захвачен снаружи; `None` отключает сохранение». **Переход:** обработчик должен определить, было ли успешное изменение, прежде чем уведомлять сборку.

## 06. Сохранять только завершённое изменение

**Точное правило.** *Успешная команда* и *изменившееся состояние* — не одно и то же. Чтение списка успешно, но состояние прежнее. `add` меняет список только при успешно проверенных данных и добавленной задаче. `done` меняет состояние, только если найденная задача раньше имела `is_done=False` и стала `True`. Повторный `done` по уже `True` может закончиться штатным сообщением, но новым изменением не является. Здесь полезно назвать термин *идемпотентное действие* только после наблюдения: повтор не меняет итоговое состояние.

**Почему недостаточно прежнего результата `mark_task_done`.** Известная функция `mark_task_done` в старом договоре может вернуть `True` в смысле **«id найден»**, даже когда `is_done` уже `True`. Значит, нельзя писать правило «если функция вернула True, сохранить». В 06 нужно **до вызова операции** получить прежний статус найденной задачи, затем вызвать существующее завершение, затем сравнить до и после; самостоятельный вариант возможен через уже знакомые поиск и словарь без новой модели. Не менять смысл прежнего булева результата молча ради сохранения. Неизвестный id в предметном договоре обрабатывается существующей ошибкой/сообщением и не вызывает callback.

**Честный порядок пользовательского эффекта.** `handle_add`: проверка данных → изменение списка → `on_change(tasks)` (если передан) → сообщение успеха. `handle_done`: найти задачу и прежний статус → успешно применить завершение → **если переход False → True** вызвать callback → сообщение, соответствующее исходу. Если `on_change` вызвал `save_tasks`, но запись не завершилась, сообщение «успешно сохранено» не печатается. Изменение уже могло произойти в памяти; это не откат. Обработка последствий ошибок `StorageError` в точке входа принадлежит 30.2; сейчас важно не объявить несостоявшуюся запись успехом.

**Независимый случай.** Есть список переключателей света со статусом `False/True`: первый перевод в `True` и повторное «включить» дают одинаковый **конечный** статус, но только первый реально изменил его. Ученик предсказывает число вызовов уведомления после `включить → посмотреть → включить`: один. На этой основе разъяснить отличие «найден» и «изменился», не раскрывая готовый целевой код `handle_done`.

**Первое действие.** Дать ученику короткую таблицу `команда / найден / is_done до / is_done после / вызывать on_change?`; он сам заполняет случаи `add`, первый `done`, повторный `done`, `done` по неизвестному id, `list`. **Наблюдаемый результат:** только первые два изменения вызывают запись; `find/search/stats`, неверный ввод, неизвестная команда, `exit` — ноль записей. Затем ученик проговаривает, почему успех печатается **после**, а не перед callback.

**Различающий случай и способ диагностики.** Если callback просто увеличивает счётчик, поведение легко проверить без настоящей файловой системы: после добавления 1, после чтения всё ещё 1, после первого завершения 2, после повторного завершения 2. Это независимое исследование, не дополнительный механизм производства. Для MAIN использовать трассировку статуса до/после и попросить исправить неверное утверждение «найдено = изменено». **Опора:** «изменилось → callback → успех; не изменилось → нет callback; `None` → без сохранения». **Переход:** теперь нужны практические изменения в настоящем Planner и два последовательных процесса.

## 07. Что мы будем делать в практике

**Формат:** обязательное самостоятельное **изменение существующего проекта Planner**; короткие учебные эксперименты только готовят к нему. После 28–29.1 в реальном `app` должны находиться `main.py`, `cli.py`, `operations.py`, `storage.py`, обработчики старых команд и работающие `encode_tasks`/`decode_tasks` для полного списка. При отсутствии этих результатов **остановить зависимые действия** и сначала завершить/подтвердить предыдущие B: план 30 не даёт вторую упрощённую реализацию CLI или заглушку JSON.

**Цель и правило самостоятельности:** учитель показывает механизм в 01–06 на **покупках, заметках, заказах и переключателях**. В проекте ученик **сам выбирает расположение вызовов**, записывает файловые функции и связывает callback с существующими обработчиками. Допустимы подсказки о прежних именах и контрактах; нельзя выдавать полные тела `load_tasks`, `save_tasks`, `app.main` и `handle_done` для копирования. Перед запуском сохранить отдельную резервную копию **имеющегося рабочего** `data/tasks.json`, если файл уже создан: режим `w` пока не даёт атомарной защиты. Демонстрации с повреждённым JSON вести только на учебной копии, подробная диагностика отложена.

1. **Сделаем чтение и запись отдельными функциями → получим локально работающий файловый компонент.**
   - **Вход и объект:** настоящий `app.storage` после 29.1 с `encode_tasks(tasks)`, `decode_tasks(text)` и списком двух **созданных через CLI** задач (одна уже завершена). Формат: `list[dict]`, четыре прежних поля, исходные id/приоритеты/статусы; технически дан только готовый кодек из 29.1.
   - **Опора до действия:** 01 (снимок), 03 (`r`, `with`, `decode_tasks`, отсутствие файла), 04 (`encode_tasks`, `mkdir`, `w`, UTF-8). Статус файловых операций 29 и кодеков 29.1 — **планируемая A**, подтверждение до выдачи обязательно.
   - **Действие ученика:** самостоятельно дописать `load_tasks(path)` и `save_tasks(path, tasks)` в существующем модуле, разделив чтение/декодирование и кодирование/запись. Кодировать **до** `w`, создавать папку при первом сохранении, вернуть `[]` лишь при `FileNotFoundError` открытия выбранного файла. Использовать один и тот же `path`, полученный аргументом, а не собственную константу пути внутри функций.
   - **Локальная проверка до шага 2:** вызвать обе функции из небольшого временного обращения к модулю **на учебном пути**, после записи повторно загрузить и сравнить все четыре поля, включая кириллицу; повторное сохранение списка из **трёх** задач даёт ровно три, а не пять; чтение отсутствующего учебного файла даёт `[]`. Случай «файл есть, но это неправильный JSON» **не** должен вернуть `[]`; он выявляет отказ, дальнейший разбор будет позже. Учебный путь не становится второй рабочей базой.

2. **Подготовим единый адрес и загрузку до меню → получим готовый вход для CLI.**
   - **Вход и объект:** рабочий `app/main.py` из 28.2, локально проверенные функции шага 1, структура `корень/app` и `корень/data`; `run(tasks=None)` принимает список и сохраняет прежний запуск без аргументов.
   - **Опора:** 02 (`Path`, `__file__`, корень проекта, ответственность), 03 (порядок начальной загрузки); 28.2 как **планируемая** опора сборки, проверить по фактическому коду.
   - **Действие ученика:** самому выбрать один `data/tasks.json` от местоположения `app/main.py` и поместить вызов `load_tasks` **перед** `run`. На этом шаге допустим простой временный вызов `run(tasks=loaded)` без callback: цель — убедиться, что меню начинает с реального входного списка; затем собрать окончательную сборку в шаге 4.
   - **Локальный результат:** при пустом состоянии (`data/tasks.json` ещё нет) меню начинает с `[]`; с заранее сохранённой **корректной** копией двух задач `list` сразу показывает их с исходными полями. Сравнить эти два случая до изменения обработчиков. Проверить, что `cli.py` не импортирует `main` и не конструирует путь.

3. **Научим обработчики уведомлять только об изменении → получим проверяемый callback без диска.**
   - **Вход и объект:** существующий `app/cli.py` с `run`, таблицей команд и `handle_add/handle_done/handle_list/handle_find/handle_search/handle_stats`; остальные операции и сообщения сохранить. Можно подставить **временный счётчик вызовов** callback, не писать для диагностики новый компонент Planner.
   - **Опора:** 05 (ссылка на функцию, замыкание, `None`, вызов из таблицы) и 06 (разница «найден» / «изменился», состояние до/после), callbacks 24/24.1 со статусом **планируемой A**.
   - **Действие ученика:** самостоятельно расширить `run(tasks=None, on_change=None)` и единый договор вызова обработчиков; `handle_add` уведомляет после успешной мутации, `handle_done` проверяет **предыдущее значение** `is_done` и уведомляет при первом переходе в `True`. Читающие обработчики принимают общий необязательный параметр, но его не вызывают. Сам ученик выбирает, в какую ветку поставить `on_change(tasks)`, сохраняя обработку неизвестного id.
   - **Локальный результат:** с подставленным счётчиком `add → list → done → done` для одного id даёт **два** вызова (после `add` и первого `done`); `list/find/search/stats`, неправильный ввод, неизвестный id, неизвестная команда и `exit` дают ноль дополнительных. Отдельно `run()` **без callback** продолжает работать с памятью, не пытается открыть файл. Если прежняя `mark_task_done` возвращает `True` лишь по факту найденного id, повторный `done` всё равно не увеличивает счётчик: это необходимый различающий случай.

4. **Соединим сборку и callback → получим автоматический полный снимок сразу после команды.**
   - **Вход и объект:** `app/main.py` с одним `path` и загрузкой из шага 2, `run` и обработчики из шага 3, `save_tasks` из шага 1.
   - **Опора:** 02 (владелец пути), 04 (полный снимок), 05–06 (замыкание и момент вызова), уже проверенные локальные результаты шагов 1–3.
   - **Действие ученика:** создать **в сборке** настроенный `on_change(updated_tasks)`, который использует выбранный `path` и вызывает `save_tasks`; передать этот callback и загруженный список в `run`. Не оставлять отдельное сохранение по `exit`, общий `finally` или запись в операциях. Проследить, что сообщение «задача добавлена/завершена» находится после успешного возврата из callback, а не до него.
   - **Локальный результат:** после одной успешной команды `add` файл содержит полный список **без выхода из CLI**; после `done` — прежние и изменённую задачу. В разных вызовах `save_tasks` всегда указан тот же путь. Для различающего случая подставить **диагностический** callback, который сигнализирует об ошибке: после его отказа обработчик не печатает сообщение об успешном сохранении. Сложное восстановление и завершение сессии будет в 30.2, здесь важно не маскировать отказ.

5. **Проверим реальный перезапуск → новый процесс восстанавливает смысл задач.**
   - **Вход и объект:** собранный Planner из шага 4 и рабочий путь `data/tasks.json`; запуск `python -m app.main` из корня проекта. Используются реальные CLI-команды, без вручную придуманного JSON.
   - **Опора:** 01 (два процесса), 03 (первое чтение), 04 (полная запись), 06 (успешное изменение). Обработчики и формат задач пришли из предыдущих B.
   - **Действие ученика:** **первый процесс** — добавить две задачи с кириллическими названиями и различными приоритетами, одну завершить, выйти; **второй процесс** — посмотреть `list/find/search/stats`, затем добавить третью задачу; **третий процесс** — проверить, что первая завершена, вторая и третья не завершены, id всех трёх сохранены, следующий id при добавлении третьей был `max(id) + 1`.
   - **Локальный результат:** после второго запуска начальное состояние не пустое; все четыре поля исходных задач совпадают, ни одна команда чтения не меняет их, статистика учитывает одну завершённую задачу; после третьего запуска третья задача тоже на месте. Различающий случай: две задачи с разными id и приоритетами выявляют ошибочное восстановление с новыми id или одним приоритетом. Ошибочную выдачу нельзя «исправлять» созданием нового списка вручную.

6. **Отделим чтение и отказ от настоящего изменения → подтвердим отсутствие лишней записи и сохранность старого CLI.**
   - **Вход и объект:** те же `app.cli`, операции и рабочий `data/tasks.json` после шага 5; для наблюдения числа сохранений использовать знакомый **диагностический callback-счётчик**, а содержимое файла сверять сравнением до/после. Проверка времени модификации файла может быть дополнительным признаком, но сама по себе ненадёжна из-за точности времени файловой системы.
   - **Опора:** 05–06 (условие вызова и `None`), ранее полученные проверки шага 3 и штатный запуск шага 5.
   - **Действие ученика:** самостоятельно составить и провести таблицу случаев `list`, `find`, `search`, `stats`, пустой/неверный ввод, неизвестный id, повторный `done` по завершённому id, неизвестная команда, `exit`, затем обычный `add` или первый `done`. Объяснить **до** проверки, какие действия должны вызвать запись, а какие нет. Проверить, что старые сообщения/формат карточек, поиск, статистика и обработка неверного ввода не изменились.
   - **Локальный результат:** для всех не изменяющих случаев счётчик записей остаётся на прежнем уровне и корректный файл не заменяется; после одной новой успешной мутации — ровно одна запись и корректный новый снимок. Важно отдельно показать, что найденный уже завершённый id **не** равен новому изменению. Ни `delete`, ни новая модель `Task`, ни валидация повреждённого JSON не требуются.

Эта последовательность связывает локальные результаты: **файловые функции** (1) → **восстановленный список до меню** (2) → **точное событие изменения** (3) → **запись через сборку** (4) → **накопление между процессами** (5) → **отсутствие ложных записей при прежних командах** (6). Если ученик застрял, возвращаться соответственно к 03–04, 02–03 или 05–06; готовая функция из подсказки не подменяет самостоятельное действие. Два связанных списка для будущего `LinkedNotes variant="connected"` находятся в `00` и здесь, с пояснением после каждого. В будущей теории чередовать короткие объяснения с содержательными предсказаниями, схемами данных и трассировками не чаще чем через два читаемых абзаца; повторяющиеся карточки с одним вопросом не нужны.

**Необязательный перенос, после обязательной B:** спросить, что изменится, если приложение временно будет сохранять в `data/archive.json`: ученик должен указать **одно** место настройки пути в сборке и объяснить, почему CLI и storage не нужно переписывать. Это проверка понимания границ, не вторая рабочая база и не обязательное условие следующего занятия.
