## 00. Вступление

Пока Planner помещается в одном файле, функции и запуск видны рядом. Теперь важно разделить ответственность так, чтобы любой компонент можно было импортировать отдельно и при этом случайный импорт не запускал пользовательский сценарий.

1. **Точка старта:** Planner работает через знакомые функции, обработчики и один список задач; запуск пока находится в том же файле.
2. **Новый вопрос:** как разделить этот код и соединить его импортами, не повторяя реализации и не запуская меню при импорте?
3. **Результат:** те же операции окажутся в модулях по своей ответственности, а `main` будет запускать CLI только при прямом запуске.

Сначала на **коротком независимом примере** увидим, что импорт выбирает файл и выполняет его верхний уровень. Затем проверим, как защитить запуск, и только после этого перенесём части знакомого Planner. Два первых опыта дают возможность предсказать результат ещё до большой правки.

## 01. Модуль как файл с ответственностью

- **Понятие до действия:** модуль — обычный файл `.py`. У файла есть имя (`labels.py`), а после его подключения к программе его функции и переменные доступны через имя модуля (`labels.make_label`). Точка здесь означает «найти имя внутри модуля», а не «запустить файл заново». Модель «отдельный ящик с подписанными инструментами» помогает увидеть источник имени, но не означает, что импорт копирует инструменты.
- **Независимый пример и первое применение:** в отдельном учебном `labels.py` определить простую `make_label(text)`, которая возвращает строку с меткой. До импорта ученик предсказывает, что функция не появилась сама собой в другом файле; после импорта обращается к ней через имя файла без `.py`. Это опыт знакомства с модулем, **не** готовый образец разнесённого Planner.
- **Связь с проектом:** вместе определить ответственность существующих имён: `create_task` — модель, `validate_priority` — правило (если уже подготовлено в 27), `find_task/mark_task_done` — операции, `TaskNotFoundError` — прикладная ошибка, `handle_add`/`run` — CLI. Сам ученик распределит остальные функции при практике; перенос не меняет аргументы, возврат и формат словаря.
- **Различающий случай:** два одноимённых `format_task` в разных файлах не становятся одной функцией, пока не выбрано, **из какого** модуля имя берётся. Далее нужен явный способ обращения к именам — `import`.

## 02. Импорт и пространство имён

- **Две записи на одном независимом примере:** `import labels` позволяет вызвать `labels.make_label("A")`; `from labels import make_label` позволяет написать `make_label("A")`. Объяснить, что после `from` появилось **имя функции** в текущем файле, а не новый файл или копия её кода. Имя файла указывается без `.py`; для этого занятия два файла лежат рядом и команды выполняются из их каталога.
- **Прогноз ученика:** после одного `import labels` запись `make_label("A")` без `labels.` не найдёт имя; после `from labels import make_label` сработает. Предсказать, затем проверить обе формы в коротком скрипте и объяснить вывод. Это первая самостоятельная операция с синтаксисом, ещё до импорта функций Planner.
- **Граница:** `ModuleNotFoundError` обычно означает, что указанный модуль не найден в пути поиска (например, опечатка имени или запуск из другого каталога); ошибка **внутри** найденного файла может быть другой. `import *` пока не используем: источник имени становится трудно отследить. Далее важно выяснить, какой код файла Python исполняет во время импорта.

## 03. Что выполняется при импорте

- **До эксперимента:** «верхний уровень» — инструкции файла вне `def` (и вне других ещё не выполняемых тел). При обычном первом импорте в одном процессе Python находит модуль, выполняет верхний уровень и сохраняет модуль для следующих импортов. Инструкция `def ping(): ...` создаёт функцию; её тело не выполняется, пока не вызовут `ping()`.
- **Независимый опыт:** в учебном `lesson_signal.py` рядом разместить `print("module loaded")` и `def ping(): print("ping")`. В одной сессии интерпретатора (или в одном проверочном скрипте) ученик сначала предсказывает вывод для `import lesson_signal`, повторного импорта и явного `lesson_signal.ping()`, затем сверяет. Наблюдение: первая строка печатается при первом импорте, повторный обычный импорт не печатает её ещё раз, `ping` печатает только при вызове. В новом процессе импорт начнётся заново. Имя `lesson_signal` выбрано, чтобы не совпасть со стандартным модулем `signal`.
- **Связь с проектом:** один `def run()` безопасен, а оставленный вне условий `run()` или `input()` при импорте `main` немедленно запускает взаимодействие. Применение декоратора может создать обёртку при импорте, но тело CLI не должно вызываться ею автоматически. Перед проектным импортом нужна безопасная точка запуска.

## 04. Прямой запуск и безопасная точка входа

- **Механизм и запись до применения:** Python задаёт переменную модуля `__name__`. При `python demo.py` она равна строке `"__main__"`, при `import demo` — `"demo"`. Уже знакомый `if` позволяет ограничить **только запуск программы**: `if __name__ == "__main__":` и вложенный вызов `show()`; `def show()` остаётся на верхнем уровне доступным для импорта. Двойные подчёркивания — часть точного имени, а не произвольное украшение.
- **Отдельный маленький пример:** `demo.py` содержит `def show(): print("started")` и защищённый вызов `show()`. Сначала объяснить команды: `python demo.py` запускает файл; `python -c "..."` выполняет код из строки в кавычках и завершается, не открывая меню; команды выполняются из каталога с учебным `demo.py`. Ученик объясняет и проверяет три разных действия: `python demo.py` печатает `started`; `python -c "import demo"` ничего не печатает; `python -c "import demo; demo.show()"` снова печатает `started`. Последний случай доказывает, что защита не запрещает **явный вызов** функции после импорта.
- **Граница:** правило применяем к пользовательскому запуску `main.py`, а не размножаем по всем компонентам. Условие не защищает от произвольного `print()`/`input()` вне него: их тоже надо оценить до проверки безопасного импорта. Теперь можно планировать связи между файлами.

## 05. Направление импортов при переносе кода

- **Правило, понятное без архитектурных терминов:** `main.py` знает, как разговаривать с человеком; `operations.py` знает, как менять **полученный аргументом** список задач; `models.py`, `validators.py`, `errors.py` описывают запись, правила и тип отказа. Поток зависимостей идёт от `main` к `operations` и нижним модулям, а операции не вызывают меню.
- **Независимая трассировка:** на маленьком примере `screen.py → calculate.py` ученик показывает, как `screen` передаёт число аргументом `calculate.total(...)`, а `calculate` возвращает число, не импортируя `screen`. Затем на схеме Planner сам отмечает стрелки `main → operations → models/validators/errors` и объясняет, почему `operations → main` для доступа к списку — ошибочная зависимость. Стрелка на схеме означает «левый модуль использует правый», **не** обещает, что данные всегда движутся только в одну сторону.
- **Перенос без потери поведения:** перемещать по группе (`validators`, `errors`, `models`, `operations`), сразу связывать существующих потребителей через `import`/`from`, после переключения убирать **старое определение**, а не оставлять две реализации. На каждом этапе проверять доступный отдельный импорт и затронутые функции. `cli.py`, пакет `app` и разбор циклов остаются следующим занятиям.
- **Переход:** известная обёртка может пользоваться стандартным `wraps`, но это не повод вводить новую библиотеку или менять результат операций.

## 06. Импорт помощника для знакомой обёртки

- **Объяснить до использования:** `functools` — модуль стандартной библиотеки Python, а `wraps` — имя внутри него; `from functools import wraps` использует ту же форму `from`, что разобрали в 02. Сторонний пакет устанавливается отдельно и доступен только выбранному интерпретатору/окружению; здесь установка не требуется.
- **Наблюдение на знакомом опыте:** `function.__name__` — атрибут, по которому можно увидеть имя функции (это не вызов). Уже известная ручная обёртка может заменить наблюдаемое имя на `wrapper`. С `@wraps(function)` имя и другие метаданные сохраняются как у исходной функции; `wraps` **не запускает** её тело и не изменяет предметный результат. Сначала разобрать форму декоратора, уже освоенную в блоке 5, затем предложить ученику предсказать `__name__` до/после на небольшой функции, отдельно от Planner.
- **Граница практики:** если обёртка диагностики остаётся полезной, её можно вынести в `diagnostics.py` и добавить `wraps` осмысленно; это необязательная ветка, она не блокирует безопасный импорт и не включает диагностику для всех операций. Далее проверить основной модульный проект.

## 07. Что мы будем делать в практике

**Формат и исходная опора:** проект (П). Работаем в **том же** StudyHub, с рабочим `main.py`, командами `add/list/find/done/search/stats/exit` и полями `id/title/priority/is_done`. До старта сверяем, что занятия 26–27.1 действительно дали валидаторы, `get_task` и тип ошибки; если нет, эта зависимая часть практики ждёт завершения предыдущей B, а не «дорисовывается» без объяснения. Технически готовы лишь существующие функции и их контракты — размещение новых файлов и импорты выбирает и пишет ученик.

Результат — тот же Planner в нескольких модулях, в котором **можно подключить любой компонент без меню** и отдельно запустить CLI с прежним поведением. Теоретические опоры: 01 — ответственность, 02 — синтаксис импорта, 03–04 — побочные эффекты и защита, 05 — направление связей; 06 используется, только если сохраняем диагностику.

1. **Распределить имена (01, 05):** по существующему `main.py` ученик сам составляет соответствие «функция → ответственность → модуль» и первым делом выделяет `validators.py` и `errors.py` из подготовленной A. **Сразу после:** импорт `python -c "import validators, errors"` проходит без меню; прямые вызовы валидаторов дают прежний результат для допустимого значения и прежнюю ошибку для недопустимого. Здесь допустимо свериться с теорией; куда поместить остальные функции — самостоятельное решение.
2. **Перенести модель и операции (01, 02, 05):** ученик создаёт `models.py` и `operations.py`, пишет нужные импорты, переключает потребителей и удаляет старые определения **после** переключения. **Сразу после:** `python -c "import models, operations"` завершается без вывода CLI, а прямые вызовы добавления и поиска работают на переданном списке; неверные значения/несуществующий id не меняют его. Отдельно объяснить, почему ни один из нижних модулей не импортирует `main` за списком.
3. **Защитить вход в программу (03–04):** ученик находит в `main.py` безусловный вызов `run()` и самостоятельно записывает `if __name__ == "__main__":` с вызовом внутри; оставляет `def run(...)` доступным. **Сразу после:** `python -c "import main"` возвращает управление без меню и запроса `input`, а `python main.py` открывает привычный CLI. Отличающий случай: явный вызов импортированного `main.run(...)` по-прежнему разрешён и запускает поведение функции.
4. **Проверить сохранённое поведение и перенос (02, 05):** самостоятельно проследить вызов `main → operations → нижние модули` и запустить старые `add/list/find/done/search/stats/exit`. **Сразу после:** задача добавляется с прежними четырьмя полями, поиск/показ/статистика согласованы, завершение отражается в общем списке; неизвестный id сообщает ожидаемый отказ без изменения списка, ошибочный ввод не обрывает меню, а неизвестная команда оставляет список неизменным и позволяет выбрать следующую команду. В небольшом изменённом случае ученик сам выбирает, где исправлять ошибочный импорт имени, и доказывает, что CLI после исправления работает так же. Новых команд и JSON нет.

Проверки идут по мере изменения файлов: импорт нижних модулей проверяется **до** импорта `main`, а регрессия меню — после защиты запуска. Если шаг не получается, возвращаться к указанной в нём опоре, а не копировать готовый проект. Накопленные результаты показывают обе части B: файлы вызывают друг друга через импорты, а пользователь запускает прежний CLI лишь тогда, когда намеренно стартует `main.py`. В занятии 28.1 эти плоские файлы станут пакетом `app`.
