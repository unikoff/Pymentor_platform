# M5. Авторская приёмка готового занятия

При финальной приёмке семантически проверь всю видимую теорию, практику, подписи, подсказки и обратную связь: в них нет ссылок на занятия по номеру. Формулировки «предыдущее/следующее занятие» допустимы только при проверенном соседстве; в остальных случаях используй тему. Сохраняй служебные ID, номера и пути, не запрещай предметные числа. Буквальный поиск U+2014 должен дать ноль совпадений во всём целевом TSX и точной записи практики. Конфликт с неизменяемым фрагментом фиксируй как не пройденную проверку, не изменяя его молча.

**При массовом прогоне:** автор завершает предметную приёмку и свои локальные проверки, затем может сдать `LOCAL_READY`, если остались только общая интеграция/общие технические checks. Это промежуточная сдача результата, не PASS отсутствующего уровня и не `COMPLETE`. Автор не должен занимать слот или удерживать общий файл в ожидании общей сборки. Один интегратор проверяет итоговый набор; поурочные осмотры/задачи сохраняются, общие доказательства переиспользуются только при совпадении версии, зависимостей и явном покрытии lesson ID. Coordinator закрывает M5 после всех четырёх фактических PASS. Правило одного автора на занятие сохраняется; новые авторские проходы не запускаются ради технического ожидания.

**Роль прохода:** завершающая методичка MAIN для одного конкретного занятия Pymentor. На входе имеются принятый MD-план, сохранённая TSX-теория и точная запись практики после M1–M4 либо уже существующее занятие, которое нужно принять или адресно исправить. На выходе: целевое занятие, приведённое в соответствие с планом, проверенная цепочка привязок и доказуемые статусы **четырёх независимых уровней**. M5 может исправлять разрешённые файлы, но не переписывает согласованную цель курса и не добавляет новую стадию.

**Цель ученика:** из фактически подтверждённой либо явно прослеженной будущей опоры **A** прийти к предусмотренному концептом результату **B** посредством понятной теории и самостоятельной практики. Авторская приёмка оценивает обеспеченность этого перехода материалом и работающим интерфейсом. Она не доказывает усвоение реальным учеником.

**Статусы:** `COMPLETE` только при подтверждённом выполнении всех обязательных предметных критериев и `PASS` на каждом из четырёх уровней, на одной конечной версии файлов и runtime; `PARTIAL` при незакрытом дефекте, конфликте входа либо обязательной проверке со статусом `FAIL`/`НЕ ПРОВЕРЕНО`. Каждая проверка имеет самостоятельные значения `PASS`, `FAIL`, `НЕ ПРОВЕРЕНО`: последняя означает, что проверки не было, доступ отсутствовал либо доказательство устарело. Это слова отчёта, не поля в коде продукта.

Методичка следует за [M4, визуалы и интерактивы](04_VISUAL_INTERACTIVE.md), а принятый учебный план поставляет [P4](../2%20stage/04_PLAN_ACCEPTANCE.md). Для непрерывного маршрута готового занятия входом могут быть все предыдущие M1–M4; для узкого запроса **только M5** выполни этот проход и называй его результатом M5. Уже принятый ранее урок не обязан заново проходить черновые стадии. Старый [LESSON_REVIEW_GUIDE](../../manual/LESSON_REVIEW_GUIDE.md) остаётся **отдельным внешним workflow** независимой перепроверки после авторской приёмки; REVIEW дополнительно осматривает половину контейнера/окна и границы адаптивной перестройки схем. Это не M6 и не обязательный повтор M5 по одному лишь тексту методички.

## 1. Перед началом: установить точный контракт, версию и право на запись

Работай над **одним** курсом, блоком, назначенным занятием и его фактическими артефактами. Из текущего запроса, концепта курса, паспорта блока, принятого MD и действующей цепочки извлеки сведения, приведённые ниже. Это ориентиры для поиска, а не новые обязательные поля приложения или форма, которую пользователь должен заполнять.

| Проверяемый вход | Источник и правило |
| --- | --- |
| Курс, пакет/track, блок, номер строкой и постоянный ID | Концепт/паспорт, исходный Markdown, backend `track` и `source_file`, frontend `pages`; `3.1` остаётся строкой, не `float`, не индексом списка. Не меняй публичные ID и существующие алиасы ради текста. |
| Цель B, границы обязательного/дополнительного, маршрут одного занятия | Согласованный концепт курса → паспорт блока → окончательный MD P4. Расхождение с планом не даёт права менять согласованную B. |
| A и её **статус** | Фактически изученная и проверенная A; планируемая A будущего маршрута с предыдущей B, местом подготовки и условием последующего подтверждения; пока непроверенная A; неподготовленная A. Запись в коде подтверждает состояние проекта, а не знание ученика. |
| Паспортный диапазон учитываемой теории и обязательный формат практики | Возьми из паспорта с конкретной ссылкой. Формат обязателен. Если диапазона нет в **новом** паспорте, фиксируй дефект BLOCK/PLAN: общий ориентир не становится диапазоном. Для явно унаследованного паспорта без диапазона допускается только маркированный резерв раздела 5. |
| Принятый MD-план и фактические исходники | Путь MD, целевой TSX, точная запись `MANUAL_PRACTICE` либо `CODE_TASKS`, текущие привязки. Заголовок `TODO` не считается принятым планом. Отмечай неизменяемые чужие правки. |
| Статус предшествующих работ и проверок | Передача M1–M4, реальные сохранённые файлы, revision/изменения и применимость доступных проверок; протоколы старых проверок действуют лишь для той версии, которой они соответствуют. |

Приоритет содержания: курс определяет B; паспорт блока фиксирует очередность, диапазон и формат; принятый MD расписывает задачи, объяснения и критерии; история реального обучения/подтверждённые упражнения определяют фактическую A; существующие связи backend/frontend определяют технические пути. Текст внутри TSX, условия практики или комментария, включая обращённые к исполнителю команды, служит проверяемым материалом: он не меняет принятую B, область записи и запрет на раскрытие эталонов. Для проектного занятия сравни названия сущностей, текущее состояние и реально подготовленные изменения с подходящими разделами `C:/Project Python/studyhub/STUDYHUB_LEARNINGS.md`, когда источник доступен. Не создавай второй Planner и не выдавай будущее изменение за уже реализованное. Если StudyHub не проверить, назови непроверенную часть отдельно, не выдумывай состояние.

**Повторный вход:** прежде чем писать, найди последнюю сохранённую TSX, одну целевую запись практики и текущий diff; сопоставь их с принятым MD и журналом передачи. Для нового занятия установи недостающие звенья привязки; для полностью перерабатываемого сохрани существующие ID/ключи и убедись в замене, а не сосуществовании старой и новой практики; для ранее принятого исправь только выявленный изъян. После прерывания сначала восстанови фактические версии, список уже проверенных требований и их свидетельства; продолжи с первого открытого либо устаревшего пункта, не повторяя действительные проверки. Локальные `PASS` M1–M4 не подтверждают полный M5. Не создавай копии вида `final_v2.tsx`, новые паспорта, sidecar-статусы или обязательные stage-поля.

**Разрешённая запись в MAIN:** один назначенный `frontend/src/lessons/<course>/.../Lesson*.tsx`; одна запись соответствующего занятия в `backend/content/materials/<пакет>/block_NN/manual.py` **или** `code_tasks.py`. Для подсоединения допустимы лишь нужные import/`pages` в `frontend/src/lessons/<course>/index.ts`, недостающие агрегирующие imports/`__init__.py` нового блока и при реально недостающей папке одна необходимая декларация в `backend/content/identity.py`. При перепривязке уже существующего занятия исправляй доказанно неверное звено; не открывай новый ID или регистрацию без нужды. Все MD (включая план и концепт), `shared.ts`, `diagrams.tsx`, CSS, загрузчик, компоненты практики, чужие уроки, зависимости, глобальные курсы, доступы и StudyHub находятся **в режиме чтения**. Нет коммитов, деплоя, внешней публикации или создания чатов из этой методички. Более широкую правку сформулируй как конкретную зависимость, не обходи ограничение.

## 2. Сначала действия ученика: обратная проверка каждой задачи

Начинай отдельный авторский проход **с практики**, а не с полировки первой страницы TSX. Перечитай сохранённую запись целиком, включая все упражнения, вложенные ручные карточки или редакторные задания. Затем для **каждого обязательного действия** сопоставь:

`условие и доступное исходное состояние → требуемое действие → ранее подтверждённая A или конкретное место объяснения → независимый пример и разбор ошибки → собственный ход ученика → локальный видимый результат → накопленный результат упражнения → итоговая B`.

Это маршрут смысловой проверки, не схема обязательных полей. Проверяй его в обе стороны: ни одна задача не требует непредставленного механизма, и нет длинной теории, не дающей опоры или полезного понимания. **Отдельно двигайся от B к заданиям:** разложи каждое обязательное наблюдаемое умение/результат принятого P4 на проверяемые действия; для каждого найди конкретную обязательную карточку/тест, локальное свидетельство и предшествующую опору в TSX. Убедись, что совокупность задач действительно покрывает B, а дополнительный материал не заменяет обязательного. Если требование B есть только в объяснении, необязательной карточке или эталоне, покрытие не доказано. Для понимания без написания кода самостоятельным свидетельством может быть прогноз с причиной, объяснённое различие или проверяемый эксперимент, предусмотренный планом. Пример таблицы для **внутренней рабочей заметки, если она нужна**, без нового обязательного файла:

| Самостоятельный шаг | Источник опоры | Что ученик делает сам | Локальный критерий |
| --- | --- | --- | --- |
| Различить значение на границе `limit` | Разбор `>=` на другом наборе чисел; противоположные случаи | Сам пишет проверку для новых входов | На входе, равном порогу, выбрана заявленная ветка |
| Исправить неверное сравнение | Предыдущий разбор типичной ошибки `>`/`>=` | Сам находит причину и исправляет код | Обычный и граничный входы дают объяснимо разные исходы |

Это **условный пример**, не предписание любому занятию ветвления. Убедись, что ни примеры, ни подсказки, ни starter не являются фактически готовым эталоном целевой задачи под другими именами. Если B предполагает написать конструкцию, хотя бы одно соответствующее обязательное действие требует написать её самостоятельно. Выбор ответа и замена строк в готовом `if` этого не доказывают. Ученик может открыть теорию параллельно с практикой: полезная опора должна восстанавливать правило, а не прятать обязательное знание впервые в подсказке/ответе.

**Проверка порядка:** первое упражнение начинает с уже доступных инструментов, данных и названных знаний; каждое последующее опирается на реально полученный ранее результат. Локальный критерий выполняется сразу после текущей карточки и не требует следующего коммита, запуска или публикации. Общий `exercise.result` относится ко всему упражнению, итог занятия охватывает B. При исследовательском уроке наблюдаемый результат может состоять в точном прогнозе, объяснённом различии или проверенном эксперименте; не выдумывай изменение проекта. При проектном уроке проверка должна охватывать изменённый участок существующего Planner и сохранность прежней возможности, когда это предусмотрено планом.

**Прогон по сценарию ученика (отдельно от TS/build/runner):** выбери типичного ученика с ровно подтверждённой A и без знания следующего шага. Прочти урок в фактическом видимом порядке: после объяснения он может своими словами назвать роль нового термина; перед интерактивом знает его входные данные; после верного/неверного ответа получает причину; к каждой обязательной задаче может дойти без подсказки, впервые раскрывающей необходимую конструкцию; по локальному результату понимает, сработало ли решение. Выполни мысленно и, где доступно, на странице **один обычный и один различающий/ошибочный путь**: укажи первый момент неоправданного скачка, повторного вопроса или перегрузки компонентами. Исправь источник разрыва, потом повтори затронутый путь. Экспертный walkthrough означает **оценку посильности**, не измеренный успех реального ученика.

Для **содержательной переработки** подтверди результат на сохранённом исходнике адресными парами `ДО → ПОСЛЕ` **по двум областям: объяснение/экран и самостоятельная практика**. В каждой области установи исходный недостаток, новое объяснение или действие, проверяемый результат и то, что из хорошего осталось. Если область уже качественна и соответствует B, предъяви исходное рабочее свидетельство и причину сохранения без фиктивного «улучшения»; если дефект есть в обеих, исправь обе. Недостаточно отчёта «три интерактива перемещены, четыре типа имеются» либо одного счёта слов. Пример (условный, только при подтверждённых источниках B): `ДО: TrueFalse(is_done) → несвязанная Note(run()/handle_*) → ещё один TrueFalse с тем же смыслом`; `ПОСЛЕ: объяснён по настоящему коду порядок обработки → на двух отличающихся входах разобрано состояние → ученик самостоятельно применяет/проверяет обновление в практике`. Результат оценивай по способности обосновать различие и пройти задачу, а не по смене JSX-тегов. Для нового занятия вместо придуманного «ДО» покажи цепь B → обучение → практика → критерий. Если ранее созданное занятие уже проходит её, не требуй косметических правок.

**Проверка постановок:** цель описывает законченное готовое поведение в настоящем времени: «Функция возвращает копию задачи; исходный список остаётся прежним». Исключение из голоса «мы» применяется к формальным ТЗ; подводки, подсказки и разборы пишутся от «мы». Условие раскрывает необходимые входы, поведение, ошибки, точный ожидаемый stdout, если он сравнивается. Не навязывай временные имена, порядок решения и неоговорённые ограничения. Ориентир **3–4 коротких предложения и 0–3 нужных ограничения** не механическая квота. Убери дубли между описанием, списками и проверками, но сохрани весь проверяемый договор.

**Проверка ответов:** ручная `answer.code` (когда нужен код/команда) действительно работает, `answer.explanation`/`answer.steps` объясняют важные операции и заявленную ошибку, `answer.checks` показывает наблюдение; устный ответ содержит точный вывод и причину. Подсказка ведёт к следующему посильному шагу без эталона. Стартовый код редакторной задачи содержит только знакомую обвязку, а не ключевую конструкцию; после подсказок к решению можно прийти без нерассмотренной технологии. Дополнительное исследование не становится обязательным через интерфейс, проверку, тест или критерий B. Если UI не поддерживает необязательность дополнительных карточек, оставь такое исследование в теории, не добавляй фиктивное поле.

Если противоречие можно устранить уточнением TSX или текущей практики в пределах B и существующей регистрации, исправь, затем перепроверь затронутую карточку и зависимые уровни. Если требовалась бы другая B, обязательный формат либо запись MD/соседнего урока, укажи точный конфликт и проведи независимые проверки дальше. Не проси снова уже данное в текущей задаче разрешение.

## 3. Уточнение маршрута A → B и соседних переходов

Для каждой реально задействованной A зафиксируй один из четырёх статусов: **подтверждена**, **планируема с трассой к предыдущей B/паспорту и местом подготовки**, **не проверена**, **не подготовлена**. Для **проектной приёмки ещё не пройденного курса** прослеживаемая планируемая A допустима, если нужная подготовка действительно назначена до этого занятия и показана связь с прежней B; фактическое усвоение учеником и работающее состояние ещё не созданного проекта из этого не следуют. Для **уже проходящего курс ученика** не выдавай планируемую A за подтверждённую. Если необходимая опора не проверена и не имеет надёжной плановой трассы либо вовсе не подготовлена, сохраняй соответствующий открытый дефект; одного обещания «изучим позже» недостаточно. При незначительном пробеле поясни механизм **до** первого обязательного применения в текущем TSX. Большой пробел, требующий изменения согласованной последовательности, обозначь как дефект входного плана/концепта; не меняй цель скрытно.

Сверь только связующие места ближайших соседей: `результат предыдущего → наша A`, `наша B → ближайшая потребность следующего`. Проверь отсутствие пропущенного шага, ненужного дублирования и ложного предположения о состоянии Planner. Следующее занятие, написанное лишь в плане, не подтверждает ранее выполненный материал. Не начинай аудит целой главы. Прежние проверки M1–M4, если соответствуют **текущему сохранённому состоянию**, используй как свидетельства и только адресно уточняй.

Проверяй отдельные частные утверждения: например, `>=` при равенстве даёт `True`, в отличие от `>`; `value` как значение имени не тождественно индексу; наличие ключа различается с ложным/нулевым значением, если это важно B. Сверяй показанные значения с реальным выполнением, не выдавай учебное упрощение за общее правило языка. Нужные термины вводятся до использования, с разъяснением английской кнопки/технического названия, когда оно влияет на результат. У завершённого примера есть настоящие исходные данные, работающий код, точный вывод и существенная граница; пример другой по сюжету/структуре, чем самостоятельная задача. В TSX рядом с важным механизмом остаётся короткая опора повторного обращения: когда применяется, знакомая форма, ожидаемое наблюдение или характерный признак ошибки. Не добавляй обязательное знание только в такую опору.

## 4. Проверка текущей практики по фактическому формату

Сначала установи фактический формат по **паспорту**, затем проверь его в целевом исходнике и каталоге; рекомендация автора не может заменить обязательную автопроверку ручной карточкой.

### Ручные карточки: одна точная запись `manual.py`

В списке упражнения есть `tasks` с вложенными карточками; активного внешнего legacy `steps` не остаётся. Не путай удаляемое `exercise["steps"]` с разрешённым `answer.steps` для разбора. Каждая карточка имеет понятные `title`/`task`, необходимые `requirements`, содержательную `hint`, полноценный `answer` и **поддерживаемое** поле `tasks[].result`, описывающее **локальный**, уже достигнутый результат. `exercise.result` суммирует упражнение. В текущем [SelfCheckPanel](../../../frontend/src/features/learning/practice/SelfCheckPanel.tsx) вывод использует `practiceTask.result ?? exercise.result`: при отсутствии локального поля интерфейс показывает общий итог; после добавления локального поля проверь реально открывшуюся карточку.

```python
{
    "title": "Проверка отдельного действия",
    "task": "Общая цель упражнения.",
    "tasks": [{
        "title": "Проверка границы",
        "task": "Наблюдаемый результат на новом входе.",
        "requirements": ["Заявленное поведение при равенстве"],
        "result": "На равном порогу входе получен нужный исход.",
        "hint": "Сравним поведение двух знакомых операторов.",
        "answer": {
            "explanation": "Здесь объясняется причина выбранного условия.",
            "steps": ["Разбор значимого действия"],
            "code": "# Рабочая реализация под конкретный план",
            "checks": ["Способ увидеть требуемый исход"],
        },
    }],
    "result": "Совокупный итог упражнения.",
}
```

Это **форма полей**, не готовое решение и не инструкция оставить заглушки в финальной практике. В итоговом исходнике замени примеры реальным материалом. Проверь современную навигацию, подсказки, раскрываемое решение, локальные критерии, отметку выполнения и отсутствие старого checklist на **реальной странице**. Если `tasks[].result` заполнен корректно, а страница всё равно показывает другой результат, зафиксируй дефект выдачи/компонента как внешнюю интеграционную зависимость; не меняй shared/UI-компонент, если он вне разрешённой области.

### Редактор: одна точная запись `code_tasks.py`

Все обязательные задания, указанные концептом как автопроверяемые, присутствуют в активной практике и проходят штатный runner. Для каждого сопоставь `prompt`, `contract.given/todo/check` (и предметные списки `given_items/todo_items/check_items`, если они нужны), `requirements.items`, 2–3 полезные `hints`, `starter_code`, `reference_code`, `tests`, `mode`. Стандарт `mode="solve"` задаёт функцию, аргументы, возвращаемое значение; `mode="script"` задаёт вход и **точный** stdout с поддерживаемым тестом `"assert": "stdout"` согласно действующим примерам. Не угадывай форму данных из названия поля; читай текущий runner/примеры.

Проверь на реальном runner для **каждой** обязательной задачи: эталонный `reference_code` проходит; намеренно неправильная программа с содержательной ошибкой получает отказ; значимый граничный случай и, по возможности, другой корректный подход оцениваются согласно заявленному договору. Точный формат печати, порядок, отступы, кавычки, пробелы и переводы строк объявлены **в условии этой задачи**, если tests проверяют stdout. Прогноз stdout и показываемый результат TSX должны совпадать с Python. Не сравнивай непредсказуемый порядок `set` как точную строку; выбирай смысловую проверку или уже изученную детерминированную операцию. Не вводи `sort` только ради удобного теста, если он отсутствует в A/B.

Выбирай различающие границы по теме: отсутствующий ключ против `0`/`False`/`None`, пустой набор и все отрицательные значения, одно против нескольких совпадений, повторная обработка и неизменность исходного объекта. Не добавляй все граничные случаи в каждую задачу механически. Путь от starter через подсказку к допустимому решению должен быть понятным новичку. `reference_code`, закрытые тесты, токены, реальные персональные данные и служебные значения не публикуются в API, видимой теории, подсказке, скриншоте или сообщении об ошибке. Используй вымышленные данные.

При несовместимом ограничении loader (например, редакторные задачи вытесняют ручную практику вне предусмотренного `mixed_practice_lessons`) проверь текущую конфигурацию в [backend catalog](../../../backend/content/catalog.py), пакет и фактический доступ. Не модифицируй загрузчик и не заменяй обязательный формат ради отображения.

## 5. Финальная редактура видимой теории

Проведи финальный проход **после** проверки задач. Для каждого нового механизма прочти как новичок: зачем он нужен, что значат данные/имена/операции, как вычисляется результат, какая ошибка типична, как эта механика позволит самостоятельно выполнить целевой шаг. Проверь не менее **двух содержательных аналогий** с явно очерченными пределами; не добавляй вторую метафору в ущерб точности. Полностью разобранный независимый пример показывает конкретные входы, последовательность, работающий код и точный вывод, а не подставляет готовое решение практики. При необходимости покажи два противоположных/граничных случая. Объяснения и повторные опоры не подменяют одно другое. Удали воду и дубли при сохранении всей нужной механики, локальных признаков ошибок и плавного перехода.

**Формальный итоговый подсчёт одной видимой TSX-теории:** от первого учебного `Section number="00"` до последнего содержательного раздела **перед** обзором «Что мы будем делать в практике»; сам обзор, последующий итог, hero, навигацию и практику не включать. Основной текст включает `Lead`, `p`, связную прозу, определения, аналоги, поясняющие `Callout`, `LinkedNotes.description`, поясняющие ячейки `MethodGrid`. Отдельно посчитай `explanation` интерактивов и `StepThrough.note`, исключи дубли при повторном отображении одного фрагмента. Заголовки, подписи кнопок, код/вывод, подписи схем, проверочные вопросы и варианты ответа, hints/answers/tests, видео исключи. Слово есть последовательность букв/цифр; внутренние дефис и `_` не делят его. **Не применяй `wc`/word count ко всему TSX или MD.** Запиши: `основной видимый текст N + объясняющая обратная связь M = всего N+M`, конкретный диапазон и его источник. Пересчитай **после** последних исправлений M5, если изменялся учитываемый текст.

Паспортный диапазон имеет приоритет. Если новый паспорт не содержит диапазон, это дефект BLOCK/PLAN; не «нормализуй» его резервом. Если паспорт уже обоснованно установил менее **1000** слов (цель, полное покрытие практики и подтверждённая либо документированная будущая опора), примени этот диапазон **без повторного исключения**. Если обоснование в паспорте отсутствует, укажи дефект источника, не выдумывай обоснование. Только при **доказанно унаследованном** паспорте без диапазона допустим помеченный резерв: минимум **1000 слов**, для первого знакомства ориентир **1400–2000**, верхняя граница не потолок. Уменьшение резервного минимума требует содержательного основания и полного покрытия практики. Для практики **нет квоты слов**: её качество определяется полнотой договора, ответов, проверок и самостоятельных действий. Формальная длина не оправдывает бессмысленные повторы.

**Язык:** спокойный профессиональный голос «мы»: «разберём», «сравним», «проверим». Нейтральные определения и формальное ТЗ готового поведения допустимы без «мы». Убирай «ты», «вы», «откройте», канцелярит, непояснённые термины и неверные обещания. Проверяй также `incorrectExplanation` у `CodeSequence`: существующее умолчание начинается с «Проверьте», поэтому при использовании переопредели доступным prop в **целевом TSX** либо честно сообщи об ограничении, если у конкретного компонента нет нужного prop. Пример из финального текста не должен раскрывать настоящие данные, токены, скрытые тесты. Во **всём** перерабатываемом TSX и **точной записи практики** запрещён символ **U+2014**: текст, JSX, код, выводы, комментарии, подписи, ответы, подсказки. Выполни буквальный поиск, зафиксируй ноль совпадений; отсутствие символа лишь в новых абзацах недостаточно. Не путай его с обычным дефисом в синтаксисе кода.

## 6. Финальные структурные, визуальные и интерактивные требования

**Два связующих раздела.** После hero первым учебным разделом стоит `Section number="00"`: плавная подводка к B, **ровно три** элемента `LinkedNotes variant="connected"` в порядке **«Точка старта» → «Новый вопрос» → «Результат»** и содержательное пояснение *после* списка. Первый элемент корректно называет A с её статусом, а не объявляет будущую A изученной. Не помещай `TheoryBridge` перед `00` или вместо него. Последний раздел теории назван **«Что мы будем делать в практике»**: краткая подводка, **один** `LinkedNotes variant="connected"` с парами «самостоятельное действие от лица мы → наблюдаемый результат» по настоящему плану, затем **1–2 поясняющих абзаца**, описывающих опоры, общий путь и границу обязательного. Это обзор, не пошаговое решение. Итого **две обязательные группы connected** для двух разделов. Они входят в общий лимит **не более шести** групп `LinkedNotes` всех вариантов. Для обычного списка используй `ul/li`, для реальной последовательности `ol/li`; три и более содержательные пары по умолчанию оформляй `LinkedNotes`, для параллельного сопоставления одинаковых признаков допустим `MethodGrid`. Если после устранения дублей и объединения действительно связанных пар лимит шести групп всё ещё превышается, используй семантически подходящие `ul/li`, `ol/li` либо `MethodGrid` согласно [M4 §5](04_VISUAL_INTERACTIVE.md#5-два-обязательных-связанных-списка-и-оформление-остальных), без потери содержания и ложного порядка. Две обязательные группы `connected` исключением не заменяются. Простые стрелки текстом и `h3/p` не заменяют смыслового connected-списка.

**Ритм:** в читаемой последовательности нет более **двух подряд абзацев** без **содержательного интерактива ИЛИ учебного визуала**. Считай реально читаемые блоки и состояния, включая объяснения внутри компонентов, а не только теги `<p>`. Полезный **статический** визуал засчитывается: корректная схема, осмысленное сравнение, завершённый разбор кода или иное изображение/структура, помогающее увидеть механизм. Кликабельность не обязательна. Не засчитывай один заголовок, пустую карточку, декоративную линию/подпись, голый неразобранный код, формальное слияние трёх абзацев в один или интерактив без нового действия. Добавляй визуал там, где он объясняет различие, связь или ход исполнения. Не вставляй пустые элементы ради соблюдения порога.

**Связность соседних вставок проверяется отдельно от ритма и счётчика типов.** Рядом могут находиться два визуала или интерактива, если они сравнивают общий случай либо служат последовательными шагами одного исследования: есть ясный вход, понятная роль каждого и общий вывод/перенос в самостоятельную задачу. Если соседние `TrueFalse`, `Note`, диаграммы или другие блоки повторяют один факт без нового наблюдения, фиксируй фрагментацию и исправляй связку по [критерию M4 §4](04_VISUAL_INTERACTIVE.md#4-ритм-не-более-двух-соседних-читаемых-абзацев-без-полезной-вставки). Не объявляй FAIL только за два компонента подряд и не лечи его принудительным промежуточным абзацем. Четыре разных действия считаются по результату работы ученика, а не по числу отображённых виджетов.

**Минимум четыре содержательно разных интерактива.** Считай действия, а не компоненты: прогноз, трассировка, диагностика ошибки, сопоставление, сборка порядка, воспроизведение своими словами, исследование и т. п. Четыре `QuizCard` с тем же действием всё ещё один тип. Примеры доступных компонентов в [shared.ts](../../../frontend/src/lessons/shared.ts): `PredictOutput`, `StepThrough`, `BugHunt`, `QuizCard`, `TrueFalse`, `CompareSolutions`, `MatchPairs`, `CodeSequence`, `RecallCard`, `FlipCards`, `FillBlank`, `SliceExplorer`, `BranchExplorer`, `TerminalDemo`. Используй только реальные props целевого компонента. У каждого есть объяснённая ранее опора, однозначная постановка на видимых данных, самостоятельное действие и обратная связь на ошибочный и верный ответ там, где компонент предусматривает эти состояния. Демонстрация с заранее открытым ответом не считается самостоятельной проверкой; для такого механизма добавь осмысленный перенос на другие входы. Проверяй корректность трассировки состояния, `True`/`False`, раскрытий и обратной связи. У многострочного `PredictOutput` используй действительное JSX-выражение вроде `output={'7\n2\n1'}` в JS/TSX-коде (здесь символы `\n` обозначают escape-последовательности строки), а не атрибут `output="7\n2\n1"` с отображаемыми буквальными обратными слешами. Сверь с Python и рендером.

**Схемы по содержанию, без искусственной квоты.** Если связи/движение данных/изменение состояния лучше понять визуально, создай или доведи до ясности схему в целевом TSX на существующих компонентах/стилях; если схема не помогает теме, кратко обоснуй её отсутствие. До схемы есть вопрос, после неё разбор пути и вывода. Точный API проверяй в [shared.ts](../../../frontend/src/lessons/shared.ts) и [diagrams.tsx](../../../frontend/src/lessons/components/diagrams.tsx). На 25.10.2026 `DiagramNode.shape` принимает **только** `process`, `terminator`, `decision`, `database`, `subprocess`. Старый пример со значением `input-output` недействителен: передай смысл входа/выхода через поддерживаемые узлы и пояснения, не расширяй типы и CSS. `DiagramArrow` поддерживает `direction` `forward/backward/both`, `lineStyle` `solid/dashed`; `DiagramExchange` отображает отдельные встречные пути. `DiagramBranches`/`DiagramBranch` сами не гарантируют стрелки; между каждым связанным источником и целевым узлом нужен реальный видимый соединитель.

На широком и узком экранах проверь каждый отдельный смысловой узел, порядок чтения, реальные линии и наконечники, отдельные запрос/ответ или ветви/возврат, пропорции, надписи и границы блоков: линия доходит от исходного узла к целевому, без разрыва у острия, не продолжается за него и не пересекает текст. На мобильном нет обрезания, лишней горизонтальной прокрутки, неверно перестроенных веток, мелких подписей. Доступное текстовое описание объясняет смысл без цвета/декоративных стрелок; проверь порядок DOM, семантическую подпись, `aria-describedby` там, где она действительно применима; декоративные стрелки скрываются от скринридера, значимые подписи остаются доступны. В русском тексте подписей убирай лишние точки в конце, сохраняя точки внутри кода. **Не используй SVG, canvas, координатную схему, новую библиотеку, общую CSS-правку или универсальный компонент ради одного занятия.** При непреодолимом дефекте общего CSS зафиксируй внешнюю задачу.

## 7. Точная регистрация без дублей

После смысловой проверки проследи реальную цепочку, а не выводи путь из названия курса:

`backend/content/materials/<пакет>/block_NN/<исходный файл>.md → backend track/source_file/lesson id → точный ключ MANUAL_PRACTICE или CODE_TASKS в агрегированном каталоге → frontend src/lessons/<course>/index.ts, pages → импорт назначенного TSX`.

Номер в имени MD используется как строка: целый `45`, дробный `"3.1"` и т. п. Ключ `lesson_catalog_key` и реальные правила конкретного пакета проверяй в [каталоге практики](../../../backend/content/practice/catalog.py), у некоторых маршрутов есть явные mapping по `source_file`; нельзя приравнивать числовую позицию к ключу. Для `block_00` используй реальный `OVERVIEW_PRACTICE` по точному имени MD. Для исторических пакетов `python-foundations` и `planner-api` папки могут называться соответственно `foundations` и `planner_api`: устанавливай фактически. Девять курсов в исходной конфигурации уже подключены, новый глобальный track не создавай.

Сверь на фактическом backend объекте: title, id, track, source_file, номер, нужные `tasks` или `manual_practice`, точный ключ практики и отсутствие активного наследованного двойника. Если план требует автопроверку, не допускай случайного сокрытия другой практики: изучи путь выдачи и правила `mixed_practice_lessons`, не меняй их без отдельной области правок. В frontend проверь `pages`, импорт и экспорт **существующего** компонента; для дробного занятия не строй имя TSX из округлённого номера.

Для нового занятия допиши только отсутствующие звенья разрешённой карты: `pages`/import, при совершенно новом блоке нужный диапазон/инициализацию каталога и точную декларацию в `identity.py` по доказанному отсутствию. При переработке повторно используй уже валидную цепочку. Отсутствие нового концепта/MD, требование глобального ID, загрузчика или изменение соседней страницы являются **внешней зависимостью**; опиши её отдельно. Не исправляй чужие ключи ради зелёной локальной проверки.

## 8. Четыре независимых уровня: выполнить и доказать на итоговой версии

**Версия свидетельства обязательна.** Перед проверками запиши пути и однозначный идентификатор актуальной версии затронутых TSX/практики/привязок (revision, scoped diff или существующий fingerprint; новый SHA не нужен без конкретной нужды). Для runtime укажи URL/сборку/экземпляр и **наблюдаемое основание**, связывающее его с текущими исходниками (например, идентификатор сборки/ревизии или проверенное обновление запущенного экземпляра). Одного совпадения URL недостаточно. Для каждого уровня фиксируй проверенный предмет, команду/действие, наблюдение, версию и статус: `PASS` только при выполнении всех требований уровня, `FAIL` при воспроизведённом несоответствии, `НЕ ПРОВЕРЕНО` при отсутствии проверки, недоступном инструменте либо устаревшем или несопоставимом свидетельстве. Прогон по старой сборке после изменения затронутого файла становится `НЕ ПРОВЕРЕНО` для новой версии, пока уровень не перепроверен. Успешная проверка одного уровня не заменяет остальные.

| Уровень | Что реально проверить | Доказательство `PASS` | Что не является доказательством |
| --- | --- | --- | --- |
| **1. Backend** | Импорт каталога; объект целевого занятия с верными ID, track, `source_file`, номером/заголовком и практикой по нужному ключу; отсутствие дубля. | Вывод штатного чтения/теста объекта с идентификаторами, значимыми полями и версией файлов. | Наличие записи в `manual.py` или только удачный Python import без сравнения объекта. |
| **2. Frontend** | TypeScript/build на конечном TSX, доступный экспорт и корректное `pages`-сопоставление с единственным импортом. | Успех проектных TS/build-команд и просмотр mapping, соответствующие конечному TSX. | Успешный build до последних правок, успешный backend, несвязанный TSX. |
| **3. Реальная выдача** | Запущенный backend или реальный источник платформы возвращает нужный урок и **все** обязательные задачи при подходящем доступе/Pro, актуальные поля и скрывает эталоны/закрытые тесты. | Запрос к фактической выдаче с URL/режимом доступа, ID/source_file, количеством и существенными полями задач, указанием используемой версии. | Локальный словарь, чтение каталога или снимок старого ответа. |
| **4. Открытая страница** | Открыт **именно** нужный урок: единственный правильный TSX, актуальная практика, состояния интерактивов, взаимодействие, runner, широкая/узкая раскладка и схемы. | Фактическая проверка страницы на нужной сборке: URL/ID, наблюдаемое отображение, действия и результаты, ширины/скриншоты или другой воспроизводимый артефакт осмотра. | Только HTTP 200, HTML без исполнения интерфейса, успешный build или самоутверждение модели. |

**Разделяй локальную и общую проверку.** Четыре уровня обязательны для каждого занятия, но M5 не означает запуск полной общей среды при каждом проходе редактирования. Выполни один раз локальные проверки каждого занятия и общие проверки после того, как готова согласованная итоговая revision группы. Для глобальных зависимостей (например, frontend build или общий API/runtime) разрешено ссылаться на один и тот же результат для нескольких занятий, если доказаны совпадение revision и зависимостей; в отчёте укажи охваченные пути/ключи и версию. Проверки конкретной backend-записи, фактической выдачи занятия и всех его задач остаются отдельными на каждый ключ. После последующих изменений повтори только затронутые проверки; если нельзя доказать применимость старого результата, соответствующий уровень для этой revision остаётся `НЕ ПРОВЕРЕНО`. Эта оптимизация не снимает ни один из четырёх PASS с конечного статуса.

**Если среда недоступна:** продолжай редактирование, предметный walkthrough, проверку ссылок/контрактов и доступные локальные операции. Для browser/runner один раз проверь доступность и зафиксируй точную ошибку/зависимость с конкретным следующим действием; не запускай повторный bootstrap и альтернативные способы без изменения условий. Обязательный недоступный уровень остаётся `НЕ ПРОВЕРЕНО`, поэтому M5 — `PARTIAL`.

1. **Backend.** Найди принятые проектом команды/тесты и используй их по назначению, сохраняя текущий `PYTHONPATH`/окружение проекта; не придумывай универсальную импортную команду без фактической структуры репозитория. Проверь точное число обязательных задач, исходный `source_file`, результат `tasks[].result` для ручной практики, отсутствие чужой/старой записи, формат из паспорта и реальные ID. Ошибка импорта, несоответствие ключа или отсутствие задачи означает `FAIL`, если проверка запущена; недоступное окружение означает `НЕ ПРОВЕРЕНО`, с указанием причины.
2. **Frontend.** Выполни действующие проверку типов и сборку после сохранения TSX/разрешённых регистраций; проверь разрешённый `pages` в исходнике, импорт и отсутствие второго зарегистрированного пути. Если сборка падает на доказанно чужом файле, укажи это с путём/логом отдельно; целевой TSX не называй прошедшим полную проверку без основания.
3. **Выдача.** С соответствующим доступом получи ответ **запущенного** API/источника урока; сравни точный идентификатор, `source_file`, формат, количество всех задач, локальные критерии и отсутствие `reference_code`/закрытых тестов. Ручная и редакторная практика могут различаться по видимым полям. Убедись, что доступ Pro/роль/схема выдачи соответствуют проверяемому маршруту; не меняй права/подписку ради теста. Если endpoint/доступ недоступен, зафиксируй `НЕ ПРОВЕРЕНО`, независимо от успеха уровней 1–2.
4. **Страница и поведение.** Открой страницу целевого занятия в доступном runtime. Проверь начальный вид, выбор/отправку, верную и ошибочную обратную связь, раскрытие подсказки/ответа и восстановление состояния **для тех элементов, где оно предусмотрено**; ручные nested cards без legacy-checklist; редакторные задачи с выполнением **каждой** обязательной задачи: эталон PASS, содержательно неверный ответ FAIL, релевантная граница. Подтверди, что нет пустого места, Markdown-fallback, устаревшего TSX или публичной утечки внутреннего решения. Прочти видимый текст, пройди все учебные схемы на **широкой и узкой** ширине; проверь переносы, направления, острия, доступность и отсутствие горизонтального overflow. Запрошенное поведение без наличия реального браузера/сервиса не объявляй проверенным.

Для уровня 4 и runner возможна дополнительная предметная таблица по задачам; включай её, когда она сокращает неопределённость или фиксирует исключение, без обязательного файла:

| Задача/компонент | Корректный исход | Намеренно неверный/граничный | Статус и свидетельство |
| --- | --- | --- | --- |
| `имя фактической задачи` | `эталон принят (run/id)` | `ошибочный код отклонён (run/id); граница проверена` | `PASS` при реальном выполнении, иначе `НЕ ПРОВЕРЕНО` |
| `имя интерактива` | `видим правильный разбор` | `видим содержательное сообщение об ошибке` | Привязка к странице/версии |

Статус `PASS` по **уровню** выставляется после прохождения всех обязательных проверок этого уровня; внутри него разрешено явно выделить частичные наблюдения и оставшиеся случаи. Проверенный вручную один редакторный пример не подтверждает все задачи занятия. Для настоящего `COMPLETE` нужны все четыре `PASS`, предметный чек-лист M5 и актуальный широкий/узкий осмотр. Недоступность уровня 3 или 4 не отменяет и не откладывает доступные уровни 1–2.

## 9. Адресное исправление и повторный контроль

При `FAIL` сперва локализуй источник и конкретную версию, затем исправь **только** разрешённый участок:

- Задача требует незнакомую конструкцию: проверь A, ближайший разбор TSX и место первого использования; добавь объяснение/независимый пример до требования либо зафиксируй конфликт с B. Снова пройди затронутую практику и пересчитай видимый текст.
- Критерий ручной карточки описывает будущий итог: исправь `tasks[].result`; отдельно оставь общий `exercise.result`. После этого перепроверь каталог, фактическую выдачу и UI этой карточки.
- Тест отвергает эталон: сверяй контракт, starter, reference, входные данные, порядок stdout и разные значения на границах; затем запускай runner снова с правильным/неправильным ответом. Не подгоняй тест под одну скрытую реализацию.
- Урок не появляется: иди по цепочке `source_file`/track/ключ → агрегированный каталог → `pages`/import → запущенная версия и доступ. Если отображается Markdown-fallback, проверь соответствие `pages` реальному TSX. Не добавляй вторую регистрацию вслепую.
- Схема ошибается на мобильном: проверь доступные `Diagram*`/существующую композицию и исправь её в TSX; при необходимой правке CSS вне области запиши конкретный внешний дефект. После изменения схемы снова осмотри **обе** ширины и доступное описание.
- Интерактив сообщает ошибочный вывод: проверь фактический Python/TSX-строку, затем соответствующий компонент и его обратную связь; обнови затронутый рендер и осмотри начальное/ошибочное/верное состояния.

После правки не запускай всю цепь механически: повтори те предметные и технические проверки, которые она могла изменить. Но **финальные статусы** должны относиться к одной результирующей версии. Изменение импортов требует повторной проверки соответствующего frontend/runtime; изменение практики затрагивает backend, выдачу и страницу; изменение только видимого текста/интерактива затрагивает TSX, учёт слов, сборку и страницу; исправление схемы требует повторного широкого/узкого осмотра. Неизменённый уровень может сохранить прежний `PASS` лишь когда зафиксированы его прежняя версия, релевантные зависимости и отсутствие влияния новой правки; если это сопоставление невозможно, статус для итоговой версии `НЕ ПРОВЕРЕНО`. Восстанови из текущих исходников и доступных логов последнюю доказанную матрицу четырёх уровней и отдельно перечисли недостающие действия. Нет бесконечных одинаковых попыток при неизменившихся условиях; инструментальный отказ без выполненной проверки фиксируй как `НЕ ПРОВЕРЕНО`, а не как `FAIL` продукта.

## 10. Окончательный авторский чек-лист

Отметь для конечных файлов `PASS` с предметным свидетельством, `FAIL` с исправлением или `НЕ ПРОВЕРЕНО` с основанием. Короткий отчёт может ссылаться на существующую запись проверки, чтобы не копировать логи.

- [ ] **Идентичность и путь:** ровно один урок, правильные курс/track, блок, строковый номер, стабильный ID, готовый MD, точные TSX и ключ практики. Сохранены посторонние изменения; нет legacy-дублей или необоснованной новой регистрации.
- [ ] **A → B и соседи:** статус A не преувеличен; B, формат, границы обязательного и результат P4 сохранены; ближайший предыдущий B подготавливает текущую A, наш B помогает следующему. Для Planner подтверждены подходящее состояние и сохранение уже существующего функционала либо конкретно указано, что не проверено.
- [ ] **Каждое самостоятельное действие:** посильное начало, предшествующий механизм, самостоятельная реализация нужной конструкции, локальный критерий сразу после шага, общий результат; отсутствует обязательное новое знание только в подсказке. Ответ содержит **решение и объяснение**, а не обещание разобрать; стартовый код не решает задачу.
- [ ] **Сценарий ученика и улучшение:** проверен видимый маршрут объяснение → различающий пример → понятная обратная связь → самостоятельная задача (обычный и сложный/ошибочный путь). Для переработки отдельно проверены исходник, улучшение и сохранение рабочих частей **теории и практики**: адресные `ДО → ПОСЛЕ` на выявленные дефекты; уже качественные области оставлены с обоснованием. Ни перестановка виджетов, ни технические PASS не считаются доказательством учебного улучшения. При новом уроке прослежены цель B, действия и критерии, без искусственного baseline.
- [ ] **Формат и тесты:** ручные вложенные `tasks`, `tasks[].result` и накопленный `exercise.result`, без внешнего legacy `steps`; либо все редакторные `solve`/`script` по точному договору со starter/подсказками/эталоном/tests. Фиктивные данные, границы по теме, безопасная выдача, верный и неверный runner подтверждены по факту.
- [ ] **Теория:** понятные термины, точные механизмы, причинно разобранные примеры, минимум две полезные аналогии, независимый завершённый пример, различающие случаи и ближайшие опоры; нет решения целевой практики и ненужного технического жаргона.
- [ ] **Связки:** `00` первый, подводка и стандартные три `LinkedNotes connected` с абзацем после; в конце «Что мы будем делать в практике», один connected-список действий/результатов и 1–2 абзаца после; нет `TheoryBridge` до `00`.
- [ ] **Объём:** подсчитана **одна** видимая теория по правилам раздела 5 и записано `основной текст + разборы = всего` с источником диапазона; новый паспорт без диапазона не нормализован; обоснованный диапазон ниже 1000 применён без повторного исключения; нет произвольной квоты практики.
- [ ] **Ритм и списки:** не более двух подряд абзацев без содержательного интерактива **или** статического учебного визуала; минимум четыре разных действия интерактивов; не более шести групп `LinkedNotes`; реальные списки и сравнения оформлены согласно смыслу, без ложной последовательности, дробности, декоративной накрутки и запрета оправданного соседства компонентов.
- [ ] **Язык и точность:** голос «мы» с исключением для ТЗ и нейтральных определений; слова и default-сообщения компонентов понятны; буквальных U+2014 **ноль** в целевом TSX и точной практике; выводы Python, `\n`, состояния и подписи совпадают с фактическими данными.
- [ ] **Схемы и страница:** схема там, где полезна, корректные `Diagram*` без неподдерживаемого `shape`, подписанные непрерывные стрелки и ветви, текстовая доступность, широкий и узкий рендер; если схема не нужна, отсутствие обосновано.
- [ ] **Фактическая интеграция:** уровни backend, frontend, выдачи и страницы проверены независимо на актуальных версиях, для всех обязательных задач; при отсутствии хотя бы одного `PASS` итог остаётся `PARTIAL`.
- [ ] **Scoped diff:** изменены только целевой TSX, точная практика и разрешённые минимальные регистрации; MD/CSS/shared/концепты/соседи/глобальные ID без правки, нет секретов, отладочных и непреднамеренных файлов. Существующие пользовательские изменения сохранены.

## 11. Передача результата и восстановление

Отвечай коротко, но с **полным набором доказательств**, не пересказывая текст урока. Используй сообщение или уже существующее служебное место; **новый отчётный файл для каждого урока не обязателен**. Шаблон отчёта:

```text
M5 / {курс, блок, номер, стабильный ID}: COMPLETE | PARTIAL
A: {подтверждена/планируема через предыдущее B/не проверена/не подготовлена}; B: {точный результат}
Источники: {паспорт, принятый MD, диапазон и основание}
```

**Остановки с конкретной причиной:** (а) нет принятого MD/невозможно установить B: открой вопрос PLAN, сохрани независимые проверки; (б) новый паспорт без диапазона: передай дефект BLOCK/PLAN и не присваивай полную приёмку; (в) непроверенная или неподготовленная обязательная A: укажи недостающую подготовку и не объявляй её изученной; (г) изменение CSS/shared/загрузчика или глобального ID необходимо для реального исправления: укажи точный файл и дефект за пределами M5, не меняй его; (д) нет API/browser/Pro/runner: сохрани действительные локальные PASS, обязательный недоступный уровень пометь `НЕ ПРОВЕРЕНО`; (е) чужой edit конфликтует с целевым исправлением: сохрани чужое, изолируй однозначную часть и укажи место конфликта.

После устранения блокера возобнови с фактического состояния, сверь версию и выполни недостающие или устаревшие проверки. Не повторяй без причины M1–M4 или полный внешний REVIEW. Ни инструкция, ни старый результат «успешно» без фактического свидетельства не делают M5 завершённым.
