# Stage 3: создание, содержательная переработка и приёмка занятий

**Массовая сдача без ожидания в занятом слоте:** автор завершает предметные M1–M5 и локальные проверки своего занятия. Если остаются только общая интеграция/общие технические проверки, возвращает `LOCAL_READY` и освобождает исполнение. Это не `COMPLETE` и не входит в N_accepted. Один назначенный интегратор выполняет общие проверки на итоговом наборе; после четырёх актуальных PASS с поурочным покрытием Coordinator закрывает M5 конкретного урока. Поурочный осмотр страницы и все обязательные задачи сохраняются. Подробности и доказательства — в общем `BATCH_WORKFLOW.md`; ответственность автора за содержание не переносится на другие уроки.

**Один агент = одно занятие = полный stage (P1–P4 или M1–M5).** Одному исполнителю запрещено назначать 2–3 занятия, диапазон для исполнения или личную очередь. Общая очередь массива принадлежит только Coordinator. Для каждого следующего занятия запускается отдельный агент; после результата или блокера текущий агент останавливается. Исправления/RESUME того же занятия можно вернуть его исполнителю. Опись массива принадлежит Coordinator; каждый исполнитель работает только над одним назначенным занятием и завершает его целиком. Это правило заменяет прежнюю схему постоянных очередей на агента.

**Один запуск Stage 3 охватывает заданный массив, но работа назначается по одному занятию: один исполнитель доводит его через M1–M5, затем следующее занятие назначается отдельно. Исходный чат запуска остаётся единственным Coordinator. Не создавай постоянных исполнителей, личные очереди или дополнительные параллельные контексты поверх effective task policy. Модель, усилие и лимиты бери из актуальной policy, а не из старых примеров в этом документе.**

Stage 3 запускается **индивидуально** на свой массив, например все занятия главы 2 с принятыми планами. Это отдельный запуск после stage 2. Его результат — полностью созданные, интегрированные и принятые занятия всего диапазона. Внешний REVIEW/stage 4 и StudyHub запускаются по своим задачам.

## Инструкции запуска

1. Прочитай [общий AGENTS.md](../AGENTS.md), [универсальный протокол](../BATCH_WORKFLOW.md), [локальный AGENTS.md](AGENTS.md) и этот README.
2. Coordinator подтверждает источники и зависимости в объёме, нужном для назначения. Не назначай ведущего исполнителя на отдельную очередь/интеграцию одновременно с полноценным занятием.
3. Передай исполнителю одну задачу, разрешённые пути и фактическое содержимое применимых инструкций. Нужные методики и первичные источники читаются до зависимой работы; неизменённые документы не перечитываются автоматически на каждом проходе.

Общий протокол задаёт передачу, запись общих файлов и критерии завершения. Один компактный журнал запуска ведётся по [шаблону](../RUN_TEMPLATE.md). Передавай исполнителю применимые инструкции фактическим содержимым; не создавай постоянные контексты или очереди.

## Вход и конечный результат

Вход: stage=3; точный курс/глава/блоки/строковые номера; **принятый план каждого занятия**, паспорт, статус A и состояние проекта; целевые TSX и точные ключи практики; разрешённые минимальные привязки; доступ к необходимым проверкам. При повторном запуске — прежний журнал.

Опись охватывает все основные и обязательные подзанятия заданного диапазона, даже если TSX ещё нет. Отсутствие принятого плана фиксируется как конкретная зависимость от stage 2 и не скрывается исключением занятия из N. Внутри stage 3 нельзя незаметно переписать план/паспорт и объявить вход принятым.

Выход: **N занятий из N**, каждое с результатом M5, один журнал и итог Coordinator по компактным подтверждениям. Для каждого сохранены актуальные TSX, практика и необходимые разрешённые привязки; подтверждены содержание и фактическая выдача. Исполнитель самостоятельно устраняет доступные дефекты до завершения занятия.

### Два режима: CREATE и REWORK

**CREATE — новое занятие.** По принятому B и подтверждённой A сначала определи, что ученик должен **суметь сделать** и как это проверить; затем раскрой механизм простыми словами с точными профессиональными названиями, проведи через различающий пример и предложи самостоятельную задачу с критериями успеха. Для CREATE не выдумывай исходный фрагмент и отчёт `ДО → ПОСЛЕ`: свидетельство — связь `B → объяснение → самостоятельное действие → проверяемый результат`.

**REWORK — содержательная переработка существующего занятия.** Перед M1/M2 прочитай исходный TSX в видимом порядке, вопросы, обратную связь и всю имеющуюся практику. Сопоставь её с B/A, планом и реальными контрактами, зафиксируй адресную карту: **где и в чём исходный дефект → какое действие/понимание ученика страдает → какое точное изменение нужно → чем подтвердить улучшение → что уже работает и сохраняется**. Урок с хорошим фрагментом не требует косметической переделки. После M1–M5 покажи конкретные пары `ДО → ПОСЛЕ` для действительно изменённых объяснений и заданий: например, `ДО: один и тот же факт о is_done угадывается дважды`; `ПОСЛЕ: объяснён подтверждённый исходником переход состояния, один вопрос различает два исхода, самостоятельное задание проверяет этот переход`. Конкретную роль `run()` и `handle_*` подтверждай по коду, не выводи её из названия. При отсутствии подтверждённой причины исправления не придумывай новые упражнения ради видимости прогресса.

Оба режима сохраняют пройденные нормы, ID, строки, `source_file`, скрытые тесты и требования практики. Ожидаемое изменение видно в последовательности **цель → понятное объяснение → наблюдение/проба → обратная связь → самостоятельное действие**. Оценка опытного методиста и walkthrough фиксируют посильность маршрута; измеренный прирост знаний возможен только после пилота на учениках.

## Экономный рабочий ритм M1–M5

Один M-проход — содержательная работа над текущим TSX или одной записью практики; M1–M4 не требуют отдельных полных аудитов неизменённого материала. Начинай с первого реально неполного результата, сохраняй проверенные части и используй подтверждения предыдущих проходов. Перед зависимыми действиями один раз прочитай нужные первичные источники и зафиксируй путь/версию; возвращайся к ним при изменении, конфликте или конкретном пробеле. Перед точечной записью перечитай изменённый участок, если он мог поменяться после чтения.

При REWORK сначала назови наблюдаемый дефект и ожидаемое действие/понимание ученика, затем рано исправь соответствующий текст или практику. Не готовь отдельный отчётный пакет перед изменением. Каждый проход оставляет компактную запись только по существенному исправлению или обоснованному `KEEP`; нет квоты diff и таймера.

M5 сохраняет полный предметный acceptance и все четыре обязательных PASS. Разделяй локальную приёмку артефакта и общие технические проверки: выполни backend, frontend, фактическую выдачу и страницу/runner на итоговой версии занятия. При общих зависимостях используй подтверждение, уже полученное для той же revision и того же состояния зависимости; укажи, к каким урокам/версиям оно относится, и не запускай одинаковую общую проверку заново для каждого абзаца или каждого M. После изменения повтори только проверки затронутых путей; если связь с прежним PASS доказать нельзя, отметь соответствующий уровень `НЕ ПРОВЕРЕНО` до проверки.

Редактирование и локальные доступные проверки продолжаются при недоступном backend/browser/runner. Для browser/runner выполни одну диагностику доступности; если блокер подтверждён, запиши точную причину и конкретное требуемое действие владельца среды. Не повторяй bootstrap и не перебирай альтернативные запуски без изменения условий. Недоступность не даёт PASS и не блокирует остальную работу, но при незакрытом обязательном уровне итог M5 остаётся `PARTIAL`.

## Порядок массовой работы

1. Coordinator сохраняет полную опись N, включая обязательные подзанятия и отсутствующие входы, а также зависимости и доступные проверки.
2. Назначь одному исполнителю ровно одно занятие, точные источники, разрешённые пути и владельца общей записи. Исполнитель восстанавливает состояние этого занятия и автономно проходит недостающие M1–M5.
3. Общую запись `manual.py`, `code_tasks.py`, индекса или реестра меняет один владелец за раз. Другие исполнители передают ему точечные дельты; не планируй параллельные назначения.
4. После завершения или точного блокера исполнитель возвращает краткий результат и останавливается. Только затем Coordinator выдаёт отдельное следующее назначение; нет очереди или долговременного контекста на исполнителя.
5. Общие технические проверки выполняются на согласованной итоговой revision. Доказательства с той же revision/зависимостями можно переиспользовать в пределах их области; после изменения перепроверяется только затронутое.
6. Coordinator принимает подтверждённые статусы, пути/ключи, четыре обязательных PASS и остатки без повторения M5 или чтения каждого TSX/MD. Углублённая проверка нужна при противоречии, сбое, пропущенном обязательном evidence или прямом запросе.

Сохраняй существующие ID, имена/экспорты, `source_file`, ключи и пользовательские изменения. M5 может выполнять минимальную регистрацию в уже разрешённой области. Методички не дают полномочий менять shared/CSS, загрузчик, концепты, чужие уроки и историю StudyHub. Нужное узкое подключение нового урока допустимо на раннем проходе, если уже разрешено; полная проверка цепи остаётся M5.

## Что означает «stage завершён полностью»

Для **каждого** занятия пройден предметный чек-лист M5 и подтверждены четыре независимых актуальных уровня:

| Уровень | Обязательное свидетельство |
| --- | --- |
| Backend | Сохранённые данные, точные ключи, валидная практика и все её задания. |
| Frontend | Итоговый TSX, импорты/привязки и релевантная сборка/проверка. |
| Фактическая выдача | Реальное получение нужного материала, полнота задач и отсутствие утечек закрытых тестов/эталонов. |
| Страница и runner | Открыто именно нужное занятие; проверены состояния, визуалы на широкой/узкой ширине, все обязательные задачи с верными и неверными решениями и релевантными границами. |

Сборка не подменяет открытую страницу, просмотр кода не подтверждает фактическую выдачу, одна выполненная задача не подтверждает все задачи. При недоступном обязательном уровне сохраняются независимые результаты, но занятие остаётся PARTIAL, весь запуск — STAGE_INCOMPLETE. Исполнитель продолжает все доступные действия и указывает конкретный остаток; исправимые замечания устраняет сам, не откладывая до нового запуска.

## Экономный обмен и восстановление

Исполнитель ведёт единый компактный журнал: **очередь → исполнитель → COMPLETE/PARTIAL/BLOCKED → пути/ключи → проверки/остатки**. Детали проверок привязываются к актуальной итоговой версии, отдельные отчёты и SHA на каждом M-проходе не нужны. Fingerprint записывается при конфликте совместной записи, восстановлении состояния или необходимости технически связать свидетельства. Настройки модели, инструменты и доступность проверяются по effective task policy; повторная проверка нужна при ошибке или изменении. Старые желаемые runtime-примеры не являются настройкой проекта.

После назначенного занятия или при блокере исполнитель возвращает компактную сводку по артефакту, проверкам и исключениям; обязательные факты не ограничиваются квотой слов: охват N, статусы, точные пути/ключи, четыре уровня проверок и остающиеся действия. Корневой диспетчер получает только завершения, ошибки и запросы вмешательства по курсорам. Во время активной работы он не читает промежуточные файлы/диалоги и не посылает повторные «статус?»/«продолжай». Промежуточное отсутствие сообщения не означает остановку работы.

## Договор содержания и подсчёта

Приоритет содержательных источников: утверждённый концепт/паспорт **B, формат и диапазон** → принятый MD-план → подтверждённый статус A и реальные исходники платформы → текущие TSX/практика и фактические результаты проверок → исторические заметки только для адресного восстановления контекста. Планируемая A должна указывать предыдущее B и место будущей подготовки, не называться освоенной. Важное знание вводится **до** необходимости его применять, не впервые в подсказке или решении. Сохраняй независимые примеры, по меньшей мере две содержательные аналогии по исходным требованиям и нарастающую самостоятельность.

В M1 и M2 сначала раскрывай **полное необходимое** содержание. M3 сверяет одну **видимую для ученика TSX-теорию** с диапазоном из паспорта (учитывая правило исходной методики), не считая скрытые тесты, код, практику или служебную разметку словами теории. Новый паспорт без обязательного диапазона остаётся дефектным; явно унаследованный допускает маркированный резерв. Обоснованный паспортный диапазон ниже 1000 принимается с подтверждённой/подготовленной опорой и покрытием практики. Верхнюю границу не объявляй жёстким потолком и не удаляй необходимое объяснение. **Для практики квота слов отсутствует:** убирай повторы и чрезмерное сопровождение, но сохраняй условия, локальные критерии, проверяемый ответ, разбор, эталон и тесты. В M4 пересчитай добавленные подписи и обратную связь, в M5 утверди окончательный счёт.

Практика использует точный ключ и вложенность заданий `manual.py` либо контракт `code_tasks.py`; актуальное поле `tasks[].result` с предусмотренным fallback `exercise.result`. Проверяй согласование условия, starter, hints, reference, tests, точный stdout и различающие крайние случаи. Не оставляй активное устаревшее поле `exercise.steps` у ручной практики; `mode="solve"` и `mode="script"` являются действующими режимами задач редактора. В публичной выдаче не должны появляться закрытые эталоны и скрытые тесты; нельзя спойлерить готовое решение в теории. Стиль из исходника, доступность, запрет `U+2014` в учебных материалах и единый язык интерфейса сохраняются.

## Визуальный ритм, connected-списки и проверка

К M4/M5 между содержательными интерактивами **или учебными визуалами** допускается **не более двух соседних читаемых абзацев**. Засчитывай осмысленную схему, сравнение, разбор кода или действие с обратной связью. Статический полезный визуал **не обязан быть кликабельным**. Пустая карточка, декоративная вставка, заголовок, бессодержательная строка кода или искусственное объединение абзацев не считаются. Проверяй читаемый порядок и реальные состояния, а не просто количество `p`-тегов. Требуются как минимум **четыре различных содержательных типа интерактива** с верными состояниями и обратной связью.

**Соседство не имеет слепого максимума и не требует чередования `абзац → виджет`.** Два или больше соседних компонента полезны, когда показывают общий кейс с разными условиями, образуют последовательность одного эксперимента или позволяют сравнить гипотезы; читателю понятны вход, роль каждой вставки и общий вывод, который переносится в практику. Плохо: `TrueFalse(is_done) → Note(run()/handle_*) → TrueFalse(is_done)` без простого разбора, что именно меняет состояние и зачем нужна новая проверка. Исправление может объединить повторяющиеся проверки и дать наглядный пошаговый сценарий с правильными исходами и самостоятельным применением, а может сохранить обе проверки, если они действительно различают условия. Не засчитывай механическую цепочку «карточка → карточка → карточка» за учебное разнообразие. Проверяй осмысленность в видимом порядке, а не только счётчики JSX-компонентов.

Две стандартные группы `LinkedNotes variant="connected"` обязательны **всего**: одна в `00` («Точка старта → Новый вопрос → Результат»), одна в последнем блоке (последовательность действий/результатов); перед каждой есть подводка, после — разъяснение. Все дополнительные связанные смысловые списки оформляй действующим компонентом, максимум **шесть групп LinkedNotes** на занятие. Схемы формируй через реально поддерживаемые props из `shared.ts` / `diagrams.tsx`, без SVG/canvas, нового CSS или библиотек. Не копируй несуществующий `DiagramNode.shape="input-output"`; адаптируй смысл к актуальному типу. Схемы и связи проверяй на широкой и узкой ширине, с доступной семантикой и читаемыми подписями.

Локальная приёмка M1–M4 оценивает только относящиеся к проходу результаты и безопасность черновика. Проваленную доступную проверку исправь, недоступную обозначь `НЕ ПРОВЕРЕНО`. **M5** отдельно оценивает обычный и ошибочный маршрут ученика (объяснение до применения, различающий пример, понятная обратная связь, самостоятельная задача), а при REWORK — исходный дефект и адресное `ДО → ПОСЛЕ` теории и практики. Затем подтверждает четыре слоя: backend-данные → frontend-исходники/сборка → фактическая API-выдача без утечек → открытая страница и runner, включая нужные размеры экрана и соблюдение плана. Если обязательный уровень нельзя проверить, финальный статус **частичный**, с точной зависимостью и последующим действием. В передаче фиксируй идентичность, пути/версию, выполненные проверки, недоступные уровни и следующую стадию; отдельный технический файл на каждый черновик не требуется.
