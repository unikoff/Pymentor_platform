### Зачем нужен блок

Planner уже сохраняет задачи между запусками. Здесь не учимся сохранению с нуля и не создаём второй продукт. Разбираемся, почему работа с полным файловым снимком неудобна для следующих требований, готовим SQLite и постепенно меняем договор сервиса с хранением. Сначала ученик понимает SQL, затем получает реальные таблицу, запись, отмену и чтение. Только после этого выделяет операции репозитория и готовит ресурсные области и перенос данных.

Главный принцип: **изучили механизм → изменили конкретную часть Planner → проверили прежние возможности**. Два первых исследования нужны до проектного внедрения SQLAlchemy. Дальше каждое занятие добавляет работающий компонент или перерабатывает существующую границу. Последнее занятие проверяет инструмент переноса, а не впервые собирает всю базу.

### Точка A блока = B13

**Знания и самостоятельные действия.** Ученик понимает Task как предметную модель, сервис как место сценариев, JsonStorage с load/save, модули, исключения и pytest. Знает существующие HTTP-схемы и CRUD, различие PUT/PATCH, параметры выборки, Depends/Annotated, граф зависимостей и тестовые overrides. Умеет настраивать приложение через Settings, среду и `.env`, проверять пути и cookie-настройку preferences. Наличие старого слова «контракт» не означает знакомства с контрактом SQL-репозитория.

**Проект на входе.** `app/main.py:build_service` собирает PlannerService над JsonStorage. `app/core/config.py` содержит JSON_PATH, APP_NAME и COOKIE_SECURE; путь JSON привязан к корню проекта. API получает сервис через get_planner/PlannerDep, в CLI запускается прежний run. API и CLI используют один файл и прежние предметные операции. `app/routers/tasks/crud.py` пока пустой. DBase, DATABASE_URL, ORM-модели, фабрики Session и get_db ещё нет.

**Данные и сохранённые правила.** Task содержит id, title, priority, is_done и внутренние tags. Id положительный целый, priority в диапазоне 1–5, заголовок не пустой, tags не разделяют один список между задачами. Старые четырёхпольные JSON-записи без tags поддерживаются. В HTTP tags не становятся новым публичным полем. Поиск использует буквальную подстроку после Python `strip().lower()` для запроса и `lower()` для заголовка; статистика сервиса имеет all/open/done, HTTP переводит all в total.

**Чего нельзя предполагать.** Ученик ещё не знает SQL, таблиц, Engine, ORM, Session, транзакций, генераторной зависимости с yield и жизненного цикла SQL-ресурса. Он не обязан уметь заменить файловое хранение запросами или объяснить SQLite-поиск. Всё это впервые вводится здесь до применения.

### Точка B блока = A15

**Понимание.** Ученик различает файл JSON, таблицу, предметную Task, ORM TaskRow, Engine, фабрику Session, отдельную Session и транзакцию. Может объяснить, почему flush не равен commit, почему закрытие не подтверждает запись и зачем операциям нужны rollback и явная область ресурса.

**Готовые компоненты.** Созданы DBase/engine.py, DBase/models.py, DBase/session.py и явная команда первоначального создания таблицы. Исходная схема содержит все прежние данные и технический title_normalized. Есть преобразование строки в обычную Task, SQL-чтение списка/по id, тестовая сборка SQL-сервиса, get_db и ресурсная область для будущей CLI-команды. Есть проверенный отдельный импорт старых данных в пустую базу.

**Изменение работающего проекта.** PlannerService использует операции репозитория, а не прямые load/save. Полный переходный JsonTaskRepository работает поверх того же JsonStorage, без второго файла и кеша снимка. Все прежние API/CLI-операции продолжают читать и изменять один JSON. SQL-проверки используют отдельную тестовую базу и не становятся штатным маршрутом пользователя.

**Что ещё предстоит.** Полный SQL CRUD, SQL-фильтрация/агрегаты/поиск и штатные ресурсные области CLI реализуются в блоке 15. Переключение обоих интерфейсов происходит в 75, удаление JSON-backend в 75.1. Подготовленный SqlTaskRepository в B14 намеренно неполный: его нельзя объявлять готовой заменой JSON для всего сервиса.

### Границы и решения, общие для всех паспортов

1. **Не смешивать источники.** До общего переключения обычный POST и обычный GET работают с JSON. SQL демонстрируется отдельным тестом существующего компонента, не новым «учебным» API и не скрытым backend-переключателем.
2. **Не вводить миграции схемы.** Здесь только исходная схема и create_all для отсутствующих таблиц. Не изучаем Alembic, revision, upgrade и изменение населённой таблицы. Несовпадение схемы диагностируем, не исправляем автоматическим удалением данных.
3. **Не переписывать продукт.** Сохраняем Task, PlannerService, маршруты, схемы, CLI-команды, настройки и preferences. Не добавляем TaskBoard, Category, created_at или новые пользовательские возможности ради ORM.
4. **Тестовая база является изоляцией, а не вторым проектом.** Для проектных SQL-проверок используем файл SQLite в tmp_path и созданную там исходную схему. `:memory:` нужен только короткому исследованию SQL. Не переносим его без объяснения в многосоединительный TestClient.
5. **Ресурс и транзакция имеют разные границы.** Engine и фабрика повторно используются; Session не глобальна и не разделяется между параллельными запросами. Репозиторий чтения не делает commit. В будущем запись подтверждается в предметном сценарии до успешного ответа, не отложенным commit после yield.
6. **Данные сохраняют смысл.** Не обрезаем старые CLI-заголовки под HTTP-лимит, не меняем id, не теряем tags, не вводим уникальность заголовков. title_normalized хранит Python `title.lower()`, но не появляется в Task/HTTP. Это подготовка прежнего поиска, не новая модель задачи.
7. **Реальное поведение проверяем реальным инструментом.** Симулятор Session допустим лишь как обсуждение модели; основная приёмка использует SQLAlchemy и повторное чтение из независимой Session. Не учим, что Session.close всегда делает объект навсегда непригодным: это не универсальное правило SQLAlchemy.

## 3. Подробные паспорта занятий

### 66. JSON и его пределы

#### Основная тема и назначение

Показать потребность в другом механизме хранения на уже работающем Planner. JSON не объявляется «плохим» или несохраняющим данные. Ученик понимает конкретные ограничения, прежде чем получает новый инструмент.

#### Точка A

- Есть достигнутая B13: API/CLI, Task, PlannerService, JsonStorage и одно файловое состояние. Данные сохраняются после перезапуска.
- Ученик умеет читать функции, списки, копии, исключения и тесты. Может проследить add_task, list_tasks и get_statistics, но ещё не знает таблиц и SQL.
- Изменение задачи состоит из чтения всего списка, изменения объектов и сохранения полного снимка. Поиск и статистика обрабатывают загруженный список в Python.
- Нельзя требовать Engine, транзакции БД, ORM или исправление многопользовательской конкуренции. Предмет занятия: обнаружить проблему, не решить её преждевременным новым кодом.

#### Точка B

- Ученик объясняет разницу между сохранением после перезапуска и защитой одновременных изменений. Наличие persistence не доказывает отсутствие потери обновления.
- Прослеживает стоимость полного снимка и понимает, почему выбор одной записи/подсчёт сейчас требуют прочитать всё.
- На двух независимо прочитанных снимках показывает, как последняя полная запись может затереть чужое изменение. Называет исходные и потерянные данные.
- Формулирует ожидания от следующего пути: адресная работа с записями, запросы, целостная фиксация операций. Рабочий Planner остаётся прежним, временный пример не объявляется его улучшением.

#### Необходимые темы в порядке изучения

1. Восстановить знакомый путь команды/запроса до load/save на собственных файлах.
2. Полный снимок против отдельной записи; количество прочитанных данных и повторение работы.
3. Два читателя и два изменения: порядок чтения и сохранения важнее того, что оба изменения правильные сами по себе.
4. Что ожидаем от БД и чего она не гарантирует автоматически: неверная логика всё ещё может потерять данные.
5. Граница исследования: пока нет выбора уровня изоляции, блокировок, async и решения через второй кеш/файл.

#### Основная практика

1. Разобрать существующие list/add/stats: указать, что загружается и когда сохраняется; сравнить чтение одной задачи и полного списка.
2. В интерпретаторе воспроизвести два независимых снимка формата Task.to_dict на небольшой копии, изменяя разные задачи. Сначала предсказать, затем проверить итог последовательного сохранения в учебную переменную, не в рабочий JSON.
3. Поменять порядок двух сохранений и объяснить, какие изменения исчезли и почему. Сопоставить это с собственным add/replace, не вводя новую команду Planner.

#### Выход и переход

Приёмка: ученик указывает потерянное изменение, отличает причину от ошибки валидации и не предлагает «ещё один JSON» как источник истины. Регрессия кода не нужна, потому что проект не изменялся. Следующий шаг даёт язык операций над таблицей, которых здесь ещё нет.

### 66.1. SQLite и основы SQL

#### Основная тема и назначение

Дать понятную модель таблицы и минимальный язык её чтения/изменения до знакомства с SQLAlchemy. Исследование короткое, но покрывает механизм, а не только набор команд для копирования.

#### Точка A

- Ученик понимает ограничения снимка и известные значения Task, но ещё не знает строк БД, NULL, primary key и SQL.
- Рабочий проект по-прежнему использует JSON. Изменение backend не началось.
- Знакомы Python-функции, контекстные менеджеры, списки/пары, исключения и параметризация вызова. API sqlite3 нужно объяснить впервые.
- Нельзя требовать JOIN, индексов, агрегатов, схемы ORM или установки сервера БД. SQLite здесь не сетевой сервер и не отдельный продукт.

#### Точка B

- Ученик различает файл базы, соединение, таблицу, строку, колонку и Python-объект. Объясняет первичный ключ и отличие NULL от строки/False/0.
- Самостоятельно выполняет INSERT, SELECT, UPDATE и DELETE с параметрами. Может предсказать состав и порядок результата WHERE/ORDER BY/LIMIT.
- Понимает, что значения передаются отдельно от текста SQL; кавычка в заголовке не должна ломать запрос.
- Получает проверенный эксперимент в памяти, а не новую таблицу рабочих задач. В проекте ничего не заменено; его данные не копируются в постоянный второй источник.

#### Необходимые темы в порядке изучения

1. SQLite как встроенная БД; файл и база в памяти; соединение и результат запроса.
2. Создание учебной таблицы: название, типы, primary key, обязательность поля; простое CREATE TABLE объяснить до использования.
3. SELECT и строки результата; WHERE, порядок ORDER BY и LIMIT; почему без ORDER BY нет обещанного порядка.
4. INSERT/UPDATE/DELETE; WHERE ограничивает изменение, его отсутствие влияет на все строки.
5. Плейсхолдеры sqlite3 и передача параметров; отделить значения от имён таблиц/колонок.
6. commit, отмена и завершение соединения на уровне наблюдения; контекст соединения sqlite3 сам по себе не означает close. Подробная Session будет позже.

#### Основная практика

1. Создать через объяснённый sqlite3 небольшую таблицу задач в `:memory:` с id/title/priority/is_done. Это лаборатория SQL, не полная схема будущего Planner.
2. Добавить несколько строк, включая заголовок с кавычкой; перед каждой выборкой предсказать результат и проверить фильтр, направление порядка и limit.
3. Изменить одну строку и удалить другую по id. Найти ошибку в предложенном UPDATE без WHERE, объяснить масштаб последствий, затем выполнить безопасный вариант на учебных данных.
4. Проверить пустой результат неизвестного id, завершить эксперимент и явно освободить соединение. Не создавать репозиторий и не импортировать рабочий JSON.

#### Выход и переход

Приёмка: верны результаты выборок; параметры не вклеены f-string; изменения адресные; ученик объясняет отличие строки результата от Task. Блок получает SQL-основу для Engine, но не готовое хранение Planner.

### 67.1. Модель ORM и таблица

#### Основная тема и назначение

Связать знакомую таблицу с описанием ORM, не смешивая её с предметной моделью и HTTP-схемами. Создать достаточную исходную схему один раз, без позднего добавления скрытых колонок.

#### Точка A

- Есть Settings.database_url, Engine и проверенное подключение. SQL-таблицы Planner ещё нет.
- Ученик знает обычные классы/аннотации/dataclass, Task и её пять полей. Понимает первичный ключ, обязательность значения и SQL-операции.
- Не знаком с DeclarativeBase, Mapped, mapped_column, metadata, ORM-defaults и CheckConstraint; эти механизмы объясняются до схемы.
- Штатные интерфейсы используют JSON; часть старых задач может иметь заголовки длиннее HTTP-лимита. Нельзя незаметно ограничить их при переносе.

#### Точка B

- В `app/DBase/models.py` описаны Base и TaskRow для таблицы tasks. Task остаётся прежней dataclass, TaskRead прежней HTTP-схемой.
- Таблица содержит id, title, priority, is_done, tags и title_normalized. Ученик объясняет каждую колонку и знает, какие правила сохраняет доменная модель, а какие дополнительно защищает БД.
- Есть явная команда `app/DBase/init_db.py` для создания отсутствующей схемы по переданным настройкам. Импорт приложения не создаёт и не удаляет таблицы.
- Фактическая схема проверена, повторный запуск на совпадающей схеме не теряет данные. Ученик не ожидает, что create_all исправит несовпадающую существующую таблицу.

#### Необходимые темы в порядке изучения

1. Три разных представления: Task, TaskRow и HTTP-схема; назначение каждого, направление преобразования.
2. DeclarativeBase, Mapped/mapped_column и metadata; таблица регистрируется при импорте модели, а не от одного наличия файла.
3. Primary key, nullable, типы, defaults и CheckConstraint. SQL-default не обязательно доступен уже в Python-конструкторе; domain-validation не заменяется ограничениями БД.
4. tags как JSON-колонка: сохранить список, не отдельную новую модель тегов. Независимые изменяемые значения; inplace-изменения JSON ORM не обязан заметить автоматически.
5. title_normalized как служебная копия Python lower. Прежний поиск включает русский регистр; встроенные SQLite lower/LIKE нельзя считать тем же механизмом. Полный поиск будет в 73.1.
6. Создание отсутствующих таблиц и независимая проверка DDL/PRAGMA; граница create_all. Не изучать изменение схемы и Alembic.

План исходной схемы:

| Колонка | Назначение и правило |
| --- | --- |
| id | Целочисленный первичный ключ, положительное значение; при будущем обычном создании назначает БД, при импорте сохраняется прежний id |
| title | Обязательный текст, без нового ограничения длины для старых CLI-данных; непустоту/нормализацию сохраняет Task |
| priority | Обязательное целое 1–5, соответствующее прежнему default; проверка диапазона на уровне БД |
| is_done | Обязательное логическое значение, начальное False; объяснить SQLite-представление и ограничения выбранного типа |
| tags | Обязательный JSON-список, независимый default; валидность элементов обеспечивается прежними предметными правилами |
| title_normalized | Обязательный технический текст `title.lower()`; не уникальный, не публичный, заполняется вместе с title во всех будущих путях |

#### Основная практика

1. Описать согласованную модель и команду создания схемы, используя Engine предыдущего занятия. Не писать новый Task и не добавлять created_at из старого примера.
2. На отдельной базе сравнить реальные колонки, primary key, NOT NULL и ограничения с metadata. До использования sqlite_master/PRAGMA объяснить назначение этих диагностических запросов.
3. Повторить команду; проверить, что нет второй таблицы и очистки данных. На отдельном несовпадающем учебном описании показать предел create_all без изменения или удаления рабочей схемы.
4. Проверить отсутствие побочного создания таблиц при простом импорте модулей. Исходная схема дальше используется тестами 68–70.2.

#### Выход и переход

Приёмка: реальные колонки совпадают с договором, технический поиск и tags предусмотрены до первых данных. Ни одной новой пользовательской функции не появилось. Вход следующего занятия: готовые Engine/Base/TaskRow/инициализация, но нет фабрики Session и сохранённой через ORM записи.

### 68. Запись через Session

#### Основная тема и назначение

На одном успешном сценарии показать, как ORM-объект становится сохранённой строкой. Не объединять первое знакомство с Session со всем HTTP CRUD и всеми аварийными состояниями.

#### Точка A

- Есть Engine, исходная таблица и TaskRow. Ученик понимает поля/defaults и различие ORM/Task; Session ещё не создана.
- Известны контекстные менеджеры и общий смысл фиксации sqlite3. Различие add/flush/commit/refresh вводится впервые.
- Тестовая база создаётся явно в tmp_path; рабочие JSON/API/CLI не изменены.
- Нельзя требовать get_db, SQL POST, репозиторий, массовый импорт и полную обработку исключений БД.

#### Точка B

- В `app/DBase/session.py` есть фабрика Session для переданного Engine. Нет глобального экземпляра Session и создания таблиц внутри каждого её открытия.
- Ученик наблюдает объект до add, после add, после flush и после commit/refresh; объясняет момент появления id и отличие отправленного SQL от подтверждённого результата.
- Одна корректная запись сохраняется с tags и title_normalized; новая независимая Session читает её с теми же значениями.
- Работа завершена контекстом; ни полученный id, ни объект в памяти не используются как единственное доказательство сохранения. Публичный POST остаётся прежним JSON-сценарием.

#### Необходимые темы в порядке изучения

1. Фабрика и экземпляр Session; рабочая область ORM и краткий жизненный цикл одной операции.
2. Создание TaskRow, фактические значения/defaults; add как регистрация объекта, а не готовая запись.
3. flush отправляет изменения в текущую транзакцию; сгенерированный id ещё не означает commit.
4. commit подтверждает изменение; поведение expire_on_commit выбранной фабрики объяснить явно, не скрывать конфигурацией.
5. refresh перечитывает состояние, а не фиксирует его. Session.get как простое чтение по первичному ключу объяснить до проверки новой Session.
6. with завершает ресурсную область; ошибки и rollback подробно рассматриваются следующим шагом.

#### Основная практика

1. Добавить фабрику и fixture базы, использующую уже созданную схему. Создать одну корректную ORM-запись существующего формата, включая технический заголовок.
2. Предсказать и проверить id на этапах add/flush/commit, разделяя наблюдение текущей Session и независимое чтение после завершения.
3. Прочитать запись по id в новой Session; проверить все поля, включая список tags, а не только тип id.
4. Повторить с ещё одной записью и доказать, что defaults списков не разделяют изменяемое состояние. Не превращать тестовый seed в новый источник задач приложения.

#### Выход и переход

Приёмка: файл БД содержит запись после завершения операции, новая Session видит её, ресурсы не глобальны. Следующий шаг опирается на этот успешный сценарий и показывает, что происходит при отказе до подтверждения.

### 68.1. Транзакция и откат

#### Основная тема и назначение

Сделать уже знакомую запись управляемой при исключении. Различить сохранение, отмену и освобождение ресурса, не вводя собственный универсальный UnitOfWork-framework.

#### Точка A

- Есть фабрика, реальная запись, новая Session для проверки и знание add/flush/commit/refresh.
- Ученик знаком с Python-исключениями, но ещё не понимает состояние Session после неудачного flush и явную транзакционную область ORM.
- Известны ограничения схемы; ими можно вызвать контролируемый отказ в отдельном тесте. Рабочий JSON не затрагивается.
- Не изучены уровни изоляции, retry, блокировки, вложенные транзакции и конкурирующие SQL-записи; не требовать их реализации.

#### Точка B

- Ученик объясняет атомарность простого сценария: его связанные изменения либо подтверждены вместе, либо не видны после отмены.
- Проверяет отказ после первого отправленного изменения и отсутствие частичного результата в новой Session.
- После ошибки ограничения знает, когда требуется rollback перед продолжением работы, и отличает это от открытия новой независимой Session.
- Есть понятный шаблон ресурсной/транзакционной области для будущих операций. Close не объявляется commit, refresh не объявляется восстановлением транзакции, ошибки не проглатываются.

#### Необходимые темы в порядке изучения

1. Begin/commit/rollback и уже известный flush; когда SQLAlchemy начинает транзакцию автоматически.
2. Граница сценария до первого SQL, включая чтение: нельзя без объяснения начать второй begin после уже запущенной транзакции.
3. Ограничение БД и ошибка flush; необходимый rollback, распространение понятной ошибки, отсутствие «успешного» результата.
4. Контекст Session и транзакционный контекст: освобождение против подтверждения/отмены. Один сценарий не дробится на commit каждой внутренней строки.
5. Проверка состояния новой Session. Close освобождает ресурсы; не моделировать его как безусловный вечный запрет повторного использования объекта.

#### Основная практика

1. Продолжить fixture из 68: выполнить изменение без commit и с явным rollback; независимым чтением проверить прежнее состояние.
2. В одной транзакции подготовить корректное изменение и затем вызвать нарушение согласованного ограничения. Убедиться, что первая часть не осталась в БД.
3. Продемонстрировать ошибку продолжения той же Session без rollback, затем корректное восстановление. Отдельно проверить следующую операцию с новой Session.
4. Проверить освобождение ресурса при исключении и отсутствие обращения к рабочей базе. Не строить симулятор flags вместо этих проверок.

#### Выход и переход

Приёмка: нет частичной записи и ложного успеха; последующая операция выполняется; ученик объясняет различие трёх действий. Следующий шаг использует безопасную область для чтения и получения обычных предметных объектов.

### 68.2. Чтение через SELECT

#### Основная тема и назначение

Научить читать строки через ORM и отдавать предметному слою прежнюю Task. Результат чтения должен быть пригоден после завершения Session, без скрытой зависимости пользователя от ORM.

#### Точка A

- Есть схема, фабрика, успешная запись и понимание транзакционных отказов. Session.get уже использован для простого подтверждения сохранения.
- Известны Task и TaskRow, но нет reusable-преобразования между ними и опыта select/scalars для набора строк.
- В тестовой базе можно создать известные записи, в том числе с tags и различным is_done; рабочее приложение всё ещё JSON.
- Нельзя требовать репозиторий, SQL-агрегаты, Unicode-поиск или передачу ORM-объекта прямо в существующую HTTP-схему.

#### Точка B

- Ученик различает SQLAlchemy Result, ORM-строку, список строк и Task; самостоятельно читает список и одну запись.
- Добавлено явное преобразование `task_from_row` рядом с TaskRow в DBase/models.py, возвращающее существующую Task с отдельным списком tags.
- Полученная Task сохраняет id и все предметные значения, доступна после закрытия Session; title_normalized не попадает в предметный/HTTP-договор.
- Неизвестный id даёт отсутствие результата на уровне чтения, а не фиктивный объект. Преобразование этого случая в предметную ошибку остаётся обязанностью сервиса.

#### Необходимые темы в порядке изучения

1. select(TaskRow), выполнение и scalars; одна строка против набора, явный порядок при проверке списка.
2. get по первичному ключу и отсутствие результата; не смешивать None с пустым списком.
3. Срок жизни ORM-объекта и expire/закрытие; материализация обычных значений до выхода из ресурсной области.
4. Направление mapping: DBase знает Task, но Task не импортирует SQLAlchemy. Копия tags, применение прежней валидации, служебная колонка отдельно.
5. Чтение не требует commit ради самого чтения. Фильтрация/агрегаты/поиск будут отдельными операциями позже.

#### Основная практика

1. Написать преобразование и проверки полного совпадения пяти предметных полей. Использовать существующую Task, а не её ORM-замену.
2. Прочитать пустую таблицу, затем несколько строк в определённом порядке и существующий/неизвестный id.
3. После завершения Session обратиться к полям полученных Task. Изменить tags одной возвращённой Task и доказать, что другая задача и сохранённые данные не изменились сами собой.
4. Проверить, что техническое поле не появилось в Task.to_dict и HTTP-схемах. Рабочие handlers не менять.

#### Выход и переход

Приёмка: чтение даёт прежнюю предметную модель, отсутствующий id корректно различается, нет ленивого SQL за пределами области. Теперь можно выделять контракт хранения в существующем сервисе, не заставляя его знать ORM.

### 69. Граница чтения данных

#### Основная тема и назначение

Переработать уже работающий файловый Planner малыми шагами. Сервис должен просить предметную операцию, а не каждый раз получать полный снимок; сначала меняется только чтение.

#### Точка A

- SQL-инфраструктура и mapping проверены отдельно, но штатный PlannerService всё ещё зависит от storage.load/save.
- Есть прежние list_tasks/get_task/select_tasks/search_tasks/get_statistics; изменяющие методы также читают и сохраняют один JsonStorage.
- Ученик знает композицию и контракты хранения из предыдущих глав. Новый договор адресных операций репозитория ещё не реализован.
- Не следует предполагать полный SQL-репозиторий и менять providers на БД. На этом шаге источник данных остаётся один.

#### Точка B

- Есть переходный JsonTaskRepository в существующем `app/storage.py`, оборачивающий прежний JsonStorage. Он получает актуальные данные на вызове, а не замораживает список в конструкторе.
- Читающие методы сервиса используют операции репозитория; известные фильтры, сортировка, поиск и статистика сохраняют результаты.
- Предметная проверка id и TaskNotFoundError остаются в сервисе. Репозиторий чтения неизвестного id возвращает отсутствие; не выдаёт HTTPException и не знает status codes.
- Изменяющие методы временно используют прежний storage, причём тот же экземпляр/файл, что и адаптер. Это явно ограниченное состояние до 69.1, а не архитектура с двумя backend.

#### Необходимые темы в порядке изучения

1. Запрос операции против load всего снимка; почему SQL-реализацию нельзя строить как бесконечную перезапись списка.
2. Репозиторий выполняет доступ к данным, сервис сохраняет предметный сценарий, HTTP переводит результат в ответ.
3. Договор чтения: list/get/select/search/statistics, обычные Task, None для отсутствующего id, прежние параметры и семантика результатов.
4. Adapter поверх JsonStorage как переходный мост; свежесть данных и отсутствие новых файлов/кешей.
5. Сборка зависимости и совместимость текущих fixtures. Абстрактные базовые классы, Protocol и framework не являются обязательным новым слоем.

#### Основная практика

1. Зафиксировать договор чтения на прежних публичных методах сервиса. Внутренние операции адаптера именовать `list/get/select/search/statistics`; HTTP/CLI-названия методов сервиса не менять.
2. Реализовать адаптер через существующий storage и перенести чтение сервиса. Сборка создаёт один адаптер над одним storage; старую возможность тестов передать storage сохранить через явную адаптацию на границе сборки/конструктора.
3. После add прежним кодом сразу прочитать данные через новый путь; после внешнего сохранения через тот же storage повторить чтение. Это выявляет замороженный снимок.
4. Проверить список, get/неизвестный id, фильтр/порядок/limit, буквальный поиск и all/open/done. Повторить действующие JSON API/CLI-проверки, включая preferences.

#### Выход и переход

Приёмка: чтение больше не требует прямого load в сервисе, результаты прежние, изменения через старый путь сразу видны новому. В A69.1 явно остаются прямые load/save только у изменяющих сценариев; их перевод является следующим отдельным шагом.

### 69.1. Граница записи данных

#### Основная тема и назначение

Завершить переход сервиса к операциям репозитория на прежнем JSON. Это не упражнение в повторном написании бизнес-логики, а изменение способа доступа к уже накопленному состоянию.

#### Точка A

- Чтение проходит через JsonTaskRepository, запись ещё через прежний JsonStorage; оба пути используют один файл.
- Есть готовые add_task/replace_task/patch_task/mark_done/delete_task и их прежние проверки. Task уже умеет валидировать/менять своё состояние.
- Ученик понимает назначение репозитория и отсутствие HTTP в нём. SQL-транзакции изучены, но SQL-операции записи для продукта ещё не реализованы.
- Не требовать ORM-запись через endpoint, смену алгоритма JSON-id, универсальный UnitOfWork или новый предметный объект.

#### Точка B

- Все публичные сценарии PlannerService работают через один репозиторий. Прямые load/save из сервиса удалены; временное разделение 69 завершено.
- JSON-адаптер предоставляет создание, замену/обновление и удаление отдельной задачи, используя прежний файловый механизм. Изменение одной задачи сохраняет соседей.
- Предметные правила, id, tags, PUT/PATCH, False/null/пустой payload, повторное done и ошибки сохранены. Некорректный ввод не вызывает сохранение изменённого состояния.
- build_service и fixtures собирают тот же рабочий JSON-путь через новую границу. Теперь его контракт можно реализовать SQL-операциями, не переписывая публичный сервис и маршруты.

#### Необходимые темы в порядке изучения

1. Договор изменений: входные проверенные значения, сохранённая Task на выходе, отсутствие id и ошибки; операция касается выбранной записи.
2. Размещение ответственности: Task/сервис задают предметные правила, репозиторий отвечает за доступ и способ записи; не копировать валидацию в три места.
3. Назначение id как часть создания в выбранном хранении: JSON пока сохраняет max+1, SQL позже использует БД. Не конструировать невалидную Task с id=0 ради ожидания SQL-id.
4. Полная замена против переданных изменений; внутренние tags и неизменность id. Пустая операция и повторное done сохраняют прежнюю семантику.
5. Подтверждение и отказ операции: JSON-save сейчас, SQL-транзакция в следующем блоке; не добавлять фиктивный commit к JSON ради одинаковых слов.

#### Основная практика

1. Расширить тот же адаптер операциями `create/replace/update/delete`, согласованными с существующими сценариями. Переиспользовать работающие предметные методы, а не написать новые варианты продукта.
2. Перевести методы сервиса по одному: add, PUT, PATCH, done, delete. После каждого проверить затронутый сценарий; убрать оставшуюся прямую зависимость сервиса от load/save.
3. На прежних fixtures проверить сохранение соседей/id/tags, отсутствие записи при ошибке, неизвестный id, False/null, пустой PATCH и повторное done. Проверки числа save адаптировать к новой границе, не удалять их смысл.
4. Пройти связанный цикл API создаёт → CLI читает/изменяет → API читает, используя один тестовый JSON. Это проверка текущего проекта, не переключение на БД.

#### Выход и переход

Приёмка: один сервис, один адаптер и один JSON; весь прежний набор операций сохранён; прямых load/save в сервисе нет. Следующее занятие реализует только чтение этого договора на SQL, не объявляя SQL готовым для записи.

### 70. Чтение через SQL-репо

#### Основная тема и назначение

Применить подготовленные SELECT и mapping к предметному договору репозитория. Наполнить предназначенный для SQL файл реальным чтением, не сделать из него второй router/service.

#### Точка A

- PlannerService использует репозиторий, полная JSON-реализация сохраняет рабочее поведение. `app/routers/tasks/crud.py` ещё пустой.
- Есть Session, TaskRow, task_from_row и независимые тесты чтения. SQL-реализации операций договора ещё нет.
- Ученик умеет выбирать/материализовать строки и объяснять отсутствие id. Не обязан уже знать SQL-подсчёт, поиск и все CRUD-операции.
- Текущий JSON-адаптер является полноценным default; новый частичный SQL-компонент не может заменить его для всех команд.

#### Точка B

- В `app/DBase/repositories.py` есть SqlTaskRepository, получающий отдельную Session извне. Он умеет читать список и запись по id, возвращает Task/None. `app/routers/tasks/` остаётся HTTP-пакетом для маршрута и схем.
- Mapping используется повторно, tags материализуются до завершения ресурса. Список имеет определённый порядок, отсутствие id не скрывается.
- В SQL-чтении нет commit, HTTPException, обращения к JSON или загрузки второго сервиса. Репозиторий не закрывает чужую Session.
- Проверена совместимость именно готовых операций с JSON. create/replace/update/delete, SQL-select/search/statistics ещё не реализованы; это явно неполный компонент, а не полностью взаимозаменяемый backend.

#### Необходимые темы в порядке изучения

1. Реализация общего договора поверх другой технологии; одинаковый смысл, разные внутренние действия.
2. Инъекция Session в репозиторий и ответственность владельца за её срок жизни.
3. list/get через знакомые SELECT/get и task_from_row; SQL-файл не импортирует FastAPI ради предметных ошибок.
4. Контрактные проверки реализованных операций: пустой/непустой список, порядок, id, пять полей, отсутствие записи.
5. Граница частичной реализации: нельзя направлять stats/select/write на ещё отсутствующие методы или прятать fallback в JSON.

#### Основная практика

1. Наполнить существующий crud.py двумя операциями list/get. Не создавать новые endpoints, schemas и PlannerService.
2. Использовать одну SQL-fixture и тот же набор ожидаемых предметных результатов, что для JSON-чтения. Проверить пустую таблицу, несколько записей, известный и неизвестный id.
3. Проверить, что результат остаётся пригодным после области Session и что чтение не записывает данные/не подтверждает транзакцию.
4. Оставить штатную сборку на JSON. Тесты SQL ограничить реализованными операциями, не маскировать отсутствующие методы временным списком или JSON-backend.

#### Выход и переход

Приёмка: есть настоящее SQL list/get с понятным договором и без побочного изменения данных. Следующий шаг может проверить существующий GET по id с SQL-сервисом. Он пока не может честно проверить всю HTTP-выборку/статистику/запись на SQL.

### 70.1. Ресурс на один запрос

#### Основная тема и назначение

Соединить уже изученные Depends и Session: ресурс выдаётся конкретному действию и освобождается независимо от успеха. Подготовить обе точки входа без преждевременного штатного переключения.

#### Точка A

- Есть SessionFactory, SqlTaskRepository.list/get и сервис с репозиторным договором; default приложения остаётся полным JSON-путём.
- Ученик знает get_planner, PlannerDep, overrides и обычный return-зависимости. Генератор, yield-зависимость и контекст для SQL-сервиса нужно объяснить впервые.
- TestClient уже изолирует JSON через подмену get_planner; для SQL потребуется отдельная БД и отдельная ресурсная сборка.
- Нельзя требовать SQL POST, статистику и живую SQL-Session на весь CLI-run. Полная CLI-интеграция относится к 74.

#### Точка B

- Есть get_db, получающий Session из фабрики и освобождающий её при успехе/исключении. Фабрика не превращается в глобальный экземпляр Session.
- Существующая сборка сервиса допускает явно переданный репозиторий без копирования правил. Тестовый SQL-provider создаёт сервис над репозиторием текущей Session; обычный get_planner по-прежнему выдаёт JSON-сервис.
- Существующий GET по id проверен с SQL через override: известный id возвращает прежний TaskRead, неизвестный прежний 404. Нереализованные SQL-операции не участвуют в тесте.
- Подготовлена простая контекстная область для будущей CLI-команды без FastAPI Depends. Она открывается/закрывается на одно действие; обычный CLI ещё не переключён.

#### Необходимые темы в порядке изучения

1. Обычный return против yield: приостановка функции и завершающая часть; сначала короткий объяснённый эксперимент механизма.
2. with/finally и выдача ресурса FastAPI; ресурсная область и транзакционная область не одно и то же.
3. get_db → репозиторий → сервис → существующий handler. Не хранить SQL-сервис текущей Session в общем app.state на последующие запросы.
4. Подмена get_planner/get_db в тесте, тестовый Engine, восстановление overrides и настроек. Учесть модель потоков TestClient/SQLite выбранной версии, не делить Session между потоками.
5. CLI без HTTP DI: объяснить contextlib.contextmanager, если используется, до самостоятельного задания. Не вызывать yield-provider вручную через next ради обычной команды.
6. Cleanup не является отложенным подтверждением записи. Время завершения yield-зависимости зависит от версии/области FastAPI; не обещать универсальное «после отправки ответа».

#### Основная практика

1. Добавить get_db к существующим зависимостям и согласовать сборку с явно переданным репозиторием. Не переписывать обычный JSON-provider.
2. Подменить provider для теста существующего GET `/tasks/{id}` на отдельной файловой SQLite-fixture; проверить запись с tags через прежний ответ и 404 неизвестного id.
3. Наблюдать открытие/освобождение Session в успешном сценарии и при контролируемой ошибке зависимости/сценария. Вернуть overrides после теста, проверить последующий JSON-запрос.
4. Подготовить и проверить контекст SQL-сервиса для одного вызова get/list из будущей CLI-команды. Не менять основной цикл run и не держать один ресурс между независимыми командами.

#### Выход и переход

Приёмка: ресурсы освобождаются, рабочая БД/JSON не затронуты тестом, результат существующего GET не меняет договор. Полной SQL-выборки/записи ещё нет. Для импорта далее доступны фабрика, транзакционная область и mapping, но не нужно поднимать HTTP или менять CLI default.

### 70.2. Импорт задач в SQLite

#### Основная тема и назначение

Подготовить отдельный проверяемый инструмент переноса уже накопленных данных. Ученик получает безопасную репетицию будущего перехода, а не автоматическую синхронизацию двух хранилищ.

#### Точка A

- Есть исходная схема, SessionFactory, rollback, ORM-чтение и ресурсные области. Работающее приложение продолжает изменять один JSON.
- Task.from_dict поддерживает прежний четырёхпольный формат и tags; файловое хранение дополнительно проверяет нормализацию и повторы id. Эти правила нельзя потерять при обходе JsonStorage.
- Репозиторий SQL пока только читает; импорт может писать ORM-строки напрямую как отдельная административная операция, не выдавая это за готовый POST продукта.
- Нет согласованного актуального окончательного снимка для переключения; рабочий JSON может измениться после репетиции. Не объявлять импортированную сейчас копию будущей рабочей базой без повторной подготовки.

#### Точка B

- Есть отдельная команда `app/DBase/import_tasks.py`, принимающая явно выбранные источник и адрес/настройки цели. Она не вызывается при импорте модуля, запуске API или каждом открытии Session.
- Старые записи проверяются целиком до изменения цели: формат, поля/типы, нормализация, tags и уникальные положительные id. Четырёхпольным записям назначается прежний смысл tags=[].
- В пустую целевую таблицу записи попадают одной транзакцией с прежними id и всеми предметными значениями; title_normalized вычисляется тем же Python lower. Непустая цель приводит к отказу без перезаписи/слияния.
- Проверены полный перенос и отказ; источник остаётся неизменным, новая Session подтверждает содержимое. Инструмент не зависит от JsonStorage и останется пригодным после удаления старого backend в 75.1.

#### Необходимые темы в порядке изучения

1. Перенос данных против изменения схемы и постоянной синхронизации. Схема уже создана, миграции здесь не изучаются.
2. Чтение JSON явного источника, ошибки файла/кодировки/синтаксиса и проверка корня; ничего не исправлять молча и не заменять плохой файл пустым списком.
3. Прежняя Task.from_dict плюс правила сохранённого снимка: дубли id и ненормализованные данные. Не перенести скрытую зависимость от app/storage.py в будущий импортёр.
4. Сохранение явных id, tags и заголовков; внутренний title_normalized, отсутствие нового HTTP-лимита для исторических CLI-записей.
5. Проверка пустой цели в той же транзакционной области, что запись; отсутствие промежуточных commit и rollback при ошибке БД.
6. Независимое повторное чтение, сравнение полного содержимого и отказ повторного запуска. Результат репетиции не актуализируется автоматически вслед за JSON.

#### Основная практика

1. Первое задание: выбрать копию уже существующего файла задач, созданного прежними CLI/API-операциями, и пустую изолированную SQLite-базу с согласованной схемой. Не заводить второй Planner или вручную собирать параллельный постоянный список.
2. Написать отдельную команду проверки/переноса. Источник проверяется до записи, полная загрузка укладывается в одну транзакцию; данные не «чинятся» незаметно.
3. Сравнить набор id и каждую пятёрку предметных полей после чтения новой Session; проверить title_normalized отдельно. Количество строк само по себе недостаточно. Для старого формата ожидаемые tags пустые.
4. На независимых тестовых копиях проверить плохой корень, синтаксис, повтор id, неверные поля, ненормализованный заголовок/тег и плохую последнюю запись. Ни один отказ не оставляет частичный результат.
5. Проверить отказ непустой цели и повторного запуска; исходные файлы/целевые прежние строки не меняются. Отдельно смоделировать ошибку записи БД и проверить rollback.
6. После репетиции выполнить штатную JSON-команду и объяснить, почему уже импортированная тестовая копия от неё не обновилась. Зафиксировать границу следующего блока: финальный снимок переносится только после остановки записей в 75, в подготовленную пустую цель.

#### Выход и переход

Приёмка: точность переноса доказана по данным, отказ безопасен, инструмент независим от старого backend, рабочее приложение не переключено. Повторение импорта в 74.1/75 имеет другую цель: проверка готовности и перенос окончательного снимка, а не повторное написание инструмента. Блок 15 начинает с отсутствующей SQL-операции создания, а не с нового проекта или повторного знакомства с Session.

### Проверяемые критерии B14

1. Ученик объясняет ограничения файлового снимка и читает/изменяет небольшую SQL-таблицу с параметрами. SQLite не объявляется автоматическим решением любой конкуренции.
2. Engine выбирает предсказуемый адрес, исходная таблица создаётся явно, текущие config/preferences не сломаны. Нет случайной рабочей БД от другой cwd и DDL при каждом запросе.
3. Схема сразу включает прежние пять полей и title_normalized; нет потерянных tags, новых пользовательских полей, нового ограничения исторических заголовков или подготовки миграций.
4. add/flush/commit/refresh и rollback/close различаются; независимое чтение подтверждает успех и отсутствие частичной записи при отказе. Проверка не заменена симулятором флагов.
5. Mapping возвращает обычную Task, доступную после Session. Отсутствие id и копии tags проверены; служебный заголовок не выходит в HTTP.
6. Сервис перешёл на операции репозитория без прямых load/save. Все прежние операции, ошибки, выборка, поиск, статистика и внутренние tags сохранены полным JSON-адаптером.
7. SQL list/get действительно читают SQLite; неполная реализация не включена как default и не использует JSON-fallback. Не заявлена приёмка ещё не написанных SQL search/stats/CRUD.
8. Тестовый GET по id проходит через прежние provider/service/route/schema с отдельной Session. Освобождение при успехе/ошибке и восстановление overrides проверены; CLI-контекст не зависит от FastAPI.
9. Импорт сохраняет все данные и id, требует пустой цели и одну транзакцию, не портит источник, не оставляет частичную запись. Старый формат принят по прежним правилам, плохие данные не исправляются молча.
10. Обычные API и CLI всё ещё используют один JSON. Работа без ошибок на тестовой SQL-копии не называется завершённым переходом. В концепте и будущей приёмке нет миграций схемы.

### B14 = A15: точный договор

Следующий блок получает **тот же работающий Planner на JSON с новым репозиторным договором** и подготовленную SQL-инфраструктуру. Есть таблица/модель, Engine/SessionFactory, mapping, SQL list/get, ресурсные области и самостоятельный импорт. Ничего из этого не нужно создавать повторно только ради первого SQL POST.

В следующем блоке ещё нужно реализовать SQL create с серверным id, затем PUT/PATCH/done/delete, выборку, статистику и поиск; подготовить настоящий ресурс на CLI-команду и доказать полный набор операций. SQL-сценарий записи должен подтвердиться до успешного HTTP-ответа. Это не задача get_db и не обязанность каждой мелкой операции репозитория независимо сделать commit.

В 75 записи через оба интерфейса останавливаются, выбирается актуальный снимок, выполняется перенос в согласованную пустую цель и штатная сборка обоих интерфейсов переключается вместе. Репетиционная база из 70.2 не считается актуальной автоматически; непустую цель не очищают без отдельного осознанного действия. В 75.1 удаляется переходный файловый backend, а импортёр остаётся отдельным инструментом. Эта последовательность гарантирует, что A15 не предполагает ни полного SQL CRUD, ни уже отключённого JSON.

### Опоры для последующих планов

В каждом плане использовать A/B соответствующего паспорта, а не тему файла со старым совпавшим номером. Код до/после сверять по последовательной истории StudyHub; прогнозируемый результат не выдавать за выполненный коммит. Теорию расширять до всех механизмов практики, но не заменять её рецептом задания. Проверки регрессии переиспользовать и дополнять узко, не заставлять ученика писать весь набор заново после каждого шага.

Технические детали сверять с версиями проекта и первичными источниками:

- [Python: sqlite3](https://docs.python.org/3.12/library/sqlite3.html), параметры и управление соединением для исследования SQL.
- [SQLAlchemy: Engine и URL](https://docs.sqlalchemy.org/en/20/core/engines.html), адрес и фабрика подключения.
- [SQLAlchemy: metadata и создание схемы](https://docs.sqlalchemy.org/en/20/tutorial/metadata.html), исходная таблица и граница create_all.
- [SQLAlchemy: Session basics](https://docs.sqlalchemy.org/en/20/orm/session_basics.html), flush/commit/rollback/закрытие и материализация.
- [SQLAlchemy: JSON](https://docs.sqlalchemy.org/en/20/core/type_basics.html#sqlalchemy.types.JSON), особенности ORM-изменений JSON-значения.
- [FastAPI: dependencies with yield](https://fastapi.tiangolo.com/tutorial/dependencies/dependencies-with-yield/), ресурсные области с учётом версии и выбранного scope.
