### Точка A блока: знания и рабочий проект

**Знания.** Ученик уже применял функции, словари, классы, dataclass, композицию, исключения, JSON, файловые пути, pytest/fixtures/tmp_path и Git. Он знает HTTP-методы и статусы, path/query/body, Pydantic-схемы, APIRouter, TestClient и различие API-входа, прикладной операции и хранения. Знакомые записи типов можно напомнить, но наличие Annotated в прежнем коде не доказывает самостоятельного понимания metadata или внедрения зависимостей.

**Состояние проекта перед 61.** Роутер находится в `app/routers/tasks.py`, HTTP-схемы в `app/schemas.py`. `app/api.py` создаёт FastAPI, вызывает `build_service()` из `app/main.py`, помещает результат в `app.state.planner`, подключает task-роутер и объявляет `/health`/`/stats`. `build_service(storage=None)` создаёт JsonStorage по устойчивому пути `data/tasks.json`, если storage не передан явно. CLI использует тот же сервис и файл.

**Рабочие возможности.** API читает список и задачу по id, создаёт, полностью и частично обновляет, удаляет; есть статистика и health. CLI поддерживает add/list/find/done/search/stats/exit. Сервис и JSON сохраняют состояние после перезапуска. Тесты используют отдельные данные, а API-fixture временно подменяет `app.state.planner` и восстанавливает его после проверки.

**Сохраняемый договор.** Четыре публичных поля задачи: id/title/priority/is_done. Внутренние tags уже есть и не удаляются. Path-id положительный; limit по умолчанию 10, допустимы 1–50; is_done необязателен, sort_desc по умолчанию False. PUT сохраняет tags, PATCH различает отсутствие/null/False по нынешнему договору, DELETE имеет 204 с пустым body. `/stats` переводит прикладной all в публичный total. Прежние ошибки 404/422 и отсутствие записи после неверного ввода защищаются регрессией.

**Чего в A нет.** Централизованных настроек среды, реализованного config.py, штатных провайдеров Depends, исследования графа зависимостей, preference-ресурса и cookie-настройки. SQLite, SQLAlchemy, ORM и миграции тоже отсутствуют. Не помещать их в задания как готовые предпосылки.

### Точка B блока: знания, самостоятельные действия и состояние проекта

К завершению 77 ученик:

1. Может на собственных файлах объяснить путь запроса, роль пакета ресурса, импорты, сборку, сервис и JSON. Отличает сохранение поведения при переносе от новой функции продукта.
2. Самостоятельно получает конфигурацию из среды/`.env`, сохраняет defaults, проверяет значения и передаёт подготовленные Settings при сборке. API и CLI по-прежнему используют один явно определённый JSON-путь; изменение cwd не выбирает другой файл.
3. Различает создание сервиса при сборке и получение готового сервиса через Depends. Объясняет обычный вызов, callable, внедрённый результат, Annotated, граф зависимостей и подмену в тестах без второго Planner.
4. Получает параметры списка через изученную зависимость, сохраняя прежний HTTP-договор. Может проверить успех, ошибочный query и отсутствие обращения к рабочему JSON при override.
5. Реализует небольшой ресурс `/preferences`: чтение режима, установка и сброс cookie. Использует Header/Response и может объяснить, почему значение из cookie не является доверенным источником прав.
6. Проверяет безопасные атрибуты cookie, согласованный Path удаления, настройку Secure для HTTP/HTTPS и изоляцию клиентов. Знает, какие свойства подтверждает TestClient, а какие зависят от браузера.

**Конкретный состав B:** `app/core/config.py` содержит настройку и проверку среды; `app/core/dependencies.py` содержит HTTP-провайдеры и подготовку выборки; `app/main.py` сохраняет единственную сборку `build_service`; `app/api.py` получает готовую конфигурацию и подключает роутеры. Task-роутер и его schemas находятся в `app/routers/tasks/`. Preference-роутер и его HTTP-схемы создаются в `app/routers/preferences/` только по мере появления функционала. `app/routers/tasks/crud.py` остаётся пустым до SQL-реализации следующего блока. Task/PlannerService/JsonStorage и CLI остаются одним проектом, а не переписываются новыми версиями.

### Границы и темп

Не вводим БД, DBase, JsonTaskRepository, новый контракт хранения, yield-зависимость для Session, async, Bearer/JWT, пользователей, permissions, login-сессии, Alembic, middleware/CORS и browser frontend. Штатный JSON-путь не отключается в этом блоке: его поэтапное удаление запланировано далее общей картой.

Допускаются короткие исследования в редакторе, но основная практика каждого занятия меняет или проверяет этот Planner. Не требуем отдельный клиент, сервис настроек, DI-container, lru_cache или фабрику приложения только ради термина. Готовый корректный фрагмент не переписывается второй раз для отметки о выполнении.

### 61. Пакет ресурса tasks

#### Основная тема и назначение

Показать, как безопасно организовать уже работающий ресурс и понимать его место в приложении. Не начинать заново модель, сервис, storage или CRUD. Рефакторинг здесь нужен для понятного размещения последующих настроек, зависимостей и SQL-операций.

#### Точка A

- Ученик может запустить прежние API/CLI и выполнить знакомый CRUD. Умеет читать импорты, функцию сборки и существующие HTTP-схемы; умеет сравнить Git diff и запустить прежние тесты.
- Исходное состояние соответствует коммиту ad6782a: task-роутер в app/routers/tasks.py, схемы в app/schemas.py. api.py подключает этот модуль; main.py содержит build_service(storage=None). Реальная Task и данные уже существуют.
- API использует app.state.planner; передача сервиса через Depends ещё не является частью практики. Файловой конфигурации и preference-ресурса нет.
- Прежнюю запись Annotated в path-сигнатуре можно прочитать по месту, но нельзя требовать от ученика проектирования aliases и графа зависимостей. Пакет ресурса вводится и объясняется в этом занятии, а не предполагается готовым.

#### Точка B

- Ученик различает модуль и пакет, объясняет роль __init__.py, называет источник каждого импорта и причину группировки schemas/router одного ресурса.
- Роутер перенесён в app/routers/tasks/router.py, схемы в app/routers/tasks/schemas.py. Импорт подключения в api.py и импорты схем согласованы с этими путями; активных старых дубликатов нет.
- Созданы только согласованные пустые app/core/__init__.py, config.py, dependencies.py, app/routers/tasks/__init__.py и crud.py. Пустые файлы не объявляются реализованными возможностями.
- Path(gt=0) сохраняет прежние ограничения в форме checkpoint 69; payload PUT/PATCH находится в допустимом месте сигнатуры. Ни путь, ни статус, ни форма TaskRead не изменены.
- B проверяется соответствием структуры и поведения коммиту 9298d10…, не равенством SHA. Это A70. Если ученик уже находится после этого коммита, он разбирает diff и подтверждает результат, а не повторяет перенос.

#### Темы в порядке изучения

1. Знакомый рабочий запрос как опора: что выполняют router, schema, service и storage, где собирается приложение.
2. Причина группировки ресурса; модуль/пакет, роль __init__.py и адрес импорта.
3. Перемещение файла против копирования кода; оставленные дубликаты и циклический импорт как типовые ошибки.
4. Обязательный аргумент и default в сигнатуре Python; сохранение Path-ограничения без нового механизма.
5. Рефакторинг против изменения поведения; diff и прежние проверки как доказательство.
6. Путь одного GET и одного POST через реальные файлы. Не рисовать универсальный строгий порядок validation/dependencies/middleware как полный алгоритм FastAPI.

#### Основная практика

Проектная опора: код и отдельные тестовые данные прежнего Planner. Сначала определить старые пути и сохранить доказательство рабочего состояния. Затем перенести router/schemas, обновить потребителей, добавить перечисленные пустые файлы и согласовать path-сигнатуры с контрольным diff. Полезное короткое исследование: найти ошибочный импорт после переноса и объяснить, почему редактирование старого дубликата не меняет активное приложение.

После переноса пройти тесты прежнего контракта и локальный сценарий чтение/создание/ошибочный id на изолированных данных. Проверить stats, PATCH False/null, DELETE без body и одну CLI-операцию. Не требовать настройки среды, Header, Depends, SQLite или нового build_service.

#### Выход, приёмка и переход

Существующие возможности работают через новый пакет; ученик объясняет их на своих файлах и показывает релевантный diff без новой бизнес-логики. config.py и dependencies.py пока пустые; crud.py ждёт будущего SQL-блока. Занятие 62 получает именно эту структуру и начинает наполнять config.py.

### 62. Настройки окружения

Объяснить конфигурацию процесса и заменить один настоящий hardcode настройкой. Начать с уже используемого пути JSON, а не выдумывать будущую БД или secret, для которого нет потребителя.

#### Точка A

#### Точка B

- Default API/CLI продолжают выбирать один прежний файл. Проверки настройки идут на отдельном JSON, рабочие задачи не переносятся и не удаляются. Config пока остаётся небольшим механизмом чтения одной настройки, не полной Settings-моделью.

#### Темы в порядке изучения

1. Код против параметра запуска: зачем путь хранения меняется между обычным запуском и тестом.

#### Основная практика

Начать реализацию чтения JSON_PATH в существующем config.py и подключить результат к default-сборке. Проверить три последовательных случая: нет настройки и `.env`; есть только запись в отдельном `.env`; есть запись в файле и отличающееся значение среды. Исходные JSON для проверки подготовлены существующими операциями Planner либо test-fixture, не ручным новым приложением.

После первого исследования отправить знакомый GET/POST и проверить, какой выбранный файл меняется. Использовать только изолированные пути; не заменять рабочий tasks.json пустым списком ради эксперимента. Проверить, что явно переданный storage в build_service не подменяется default-путём. Практика не должна ограничиться печатью словаря env.

#### Выход, приёмка и переход

Для каждого случая ученик показывает выбранный путь и причину выбора; значение среды не переписано `.env`. Без настройки работает прежний продукт. Изменения среды теста восстановлены, `.env` не попал в новый commit. A62.1 получает работающий механизм одной настройки, которому ещё нужны общий объект, проверка значений и единые правила сборки.

### 62.1. Общие настройки

Неверная конфигурация останавливает сборку понятно; корректная сохраняет API/CLI и данные. A63 получает готовый app.state.planner и app.state.settings; не получает ещё написанный провайдер Depends.

### 63. Сервис через Depends

#### Основная тема и назначение

Убрать из обработчиков знание о месте хранения готового сервиса. Зависимость служит границей получения ресурса, а не новым алгоритмом CRUD или способом создавать JsonStorage на каждый запрос.

#### Точка A

- B62.1 достигнута: конфигурация собрана, сервис создан через build_service и помещён в app.state.planner; API/CLI работают с согласованным JSON. dependencies.py всё ещё пустой.
- Router вызывает сервис через request.app.state.planner, `/stats` использует тот же объект. Ученик знает передачу функции как значения и вызов функции, HTTP Request, тип PlannerService и обычный helper.
- Depends как механизм FastAPI ещё не объяснён полностью. Annotated aliases, составные зависимости, overrides и cache не являются обязательными знаниями для этого первого применения.
- Никакого get_db, SQL-сервиса или закрываемого ресурса на запрос ещё нет. Нельзя использовать yield как готовую форму provider.

#### Точка B

- dependencies.py содержит get_planner, который получает Request и возвращает уже созданный PlannerService из состояния текущего приложения. Он не создаёт новый storage/сервис и не выбирает другой файл.
- Task-обработчики и `/stats` получают сервис через простую форму Depends(get_planner). Прямой доступ к app.state остаётся в сборке/provider, но не размножается в обработчиках бизнес-операций.
- Ученик различает callable и вызов: FastAPI вычисляет результат провайдера для аргумента; default в декларации не является самостоятельным вычислением результата при импорте.
- CLI продолжает использовать build_service и прямые вызовы; он не импортирует Depends и не вызывает HTTP-provider с выдуманным Request.
- После нескольких запросов состояние и прежние ответы сохраняются. Ученик не путает lifetime готового app-сервиса с количеством вызовов функции provider.

#### Темы в порядке изучения

1. Получение объекта против создания и выполнения операции над ним.
2. Provider как обычная функция, её вход и возвращаемое значение; helper против декларации Depends.
3. Callable без вызова, как FastAPI заполняет аргумент; тип результата в handler.
4. Request текущего приложения, app.state и единая граница получения сервиса.
5. Где заканчивается HTTP-механизм: отдельная сборка CLI и обычные тесты сервиса.
6. Типовые ошибки: Depends(get_planner()), возврат класса вместо экземпляра, создание свежего JsonStorage в provider, скрытая глобальная привязка к другому app.

#### Основная практика

Наполнить существующий dependencies.py и перевести task-роутер и stats на получение сервиса через provider. Переиспользовать тело нынешних операций; не писать ещё один add/get/patch. Сначала сделать один GET, затем остальные обработчики, каждый раз проверяя сохранение прежнего результата.

Через нынешнюю API-fixture подставить отдельный сервис в app.state и убедиться, что provider получает именно его. Проверить два последовательных запроса после POST, stats, 404, PATCH False и DELETE 204. Override-механизм FastAPI ещё не является обязательной частью задания; он появится в 64. Короткий разбор в редакторе может сравнить функцию как значение и её результат.

#### Выход, приёмка и переход

Task API и stats используют один provider, а штатные данные и CLI остаются прежними. Ученик объясняет получение аргумента без магического «вызови lambda». A63.1 получает рабочую простую запись Depends, которую можно сделать читаемее, не меняя поведения.

### 63.1. Annotated: параметры

#### Основная тема и назначение

Показать, как отдельно описать тип значения и способ его получения/проверки. Занятие меняет читаемость деклараций, не правила данных или количество зависимостей.

#### Точка A

- B63 достигнута: get_planner существует, handler получает готовый сервис через простую запись Depends. Path(gt=0), Query для limit и defaults работают; body-схемы прежние.

1. Обычный тип значения и сведения для библиотеки; typing.Annotated.
2. Чтение одного объявления слева направо, отличие alias от другого Python-класса.
3. Annotated с Depends и общий PlannerDep на реальном get_planner.
4. Annotated с Path/Query; required, default, optional и ограничения как разные понятия.
5. Допустимый порядок аргументов, типовая ошибка двух конфликтующих defaults.
6. Доказательство эквивалентности: OpenAPI и прежние ответы/валидация, а не субъективно «красивее».

#### Основная практика

Ввести alias и переработать сигнатуры существующих task-маршрутов/stats. Проверить id=0, нечисловой id, отсутствие limit, границы 1/50 и значения 0/51; is_done/sort_desc должны преобразовываться как прежде. Сверить HTTP-форму запроса, body PUT/PATCH и результат, не закрепляя полный текст ошибок Pydantic.

В коротком исследовании сравнить две эквивалентные формы объявления и найти пример неверного default. Не переписывать get_planner и не выдавать расширение фильтров как цель занятия.

#### Выход, приёмка и переход

Ученик объясняет, что изменилось в записи и что осталось тем же в runtime. Сервис не стал входным полем клиента, ограничения сохранились. A64 получает ясные декларации Depends/Query и готовый provider; теперь можно отдельно организовать параметры выборки и изучить короткий граф.

### 64. Зависимости и тесты

#### Основная тема и назначение

Организовать подготовку существующей выборки и научиться управлять зависимостями в проверке. Это продолжение настоящего GET /tasks, а не цепочка авторизации или создание ещё одного сервера для основного проекта.

#### Точка A

- B63.1 достигнута: get_planner и PlannerDep работают, Query/Path читаются через изученную metadata. JSON всё ещё штатный backend; GET /tasks вызывает прежний select_tasks с is_done/sort_desc/limit.
- Ученик знает dataclass, возвращаемое значение, список Task и правила фильтрации/сортировки из прежнего API. Формат ответа, default 10 и диапазон 1–50 уже защищены проверками.
- Нет SelectionParams, get_selection и get_selected_tasks. Нет оснований считать понятными граф зависимости, request-local cache и app.dependency_overrides.
- Текущая API-fixture умеет временно подменять app.state.planner. Это полезная опора, но не знание override-провайдера и не доказательство, что любая новая зависимость автоматически изолирована.

#### Точка B

- SelectionParams является небольшим контейнером только is_done/sort_desc/limit. get_selection получает и проверяет те же HTTP-параметры; значения/defaults не изменены, offset/поиск/новые фильтры не добавлены.
- Короткий граф GET /tasks имеет смысл: get_selected_tasks получает get_planner и get_selection, выполняет знакомую read-only select_tasks, возвращает задачи; handler формирует прежний ответ. Сервис по-прежнему владеет предметной операцией. Остальной CRUD не переносится внутрь зависимостей.
- Ученик может объяснить, какие результаты нужны верхнему узлу, и почему нельзя одновременно вычислить функцию до передачи результата её потребителю. Не утверждает, что у FastAPI всегда один линейный порядок всех проверок и всех независимых узлов.
- Проверка подменяет оригинальный get_planner функцией, возвращающей отдельный сервис на tmp_path. Ключ overrides относится к исходному callable, значение к provider, а не к готовому результату. После теста восстанавливается прежний словарь подмен.
- Ошибочный limit даёт прежний 422; проверяемый отказ provider останавливает обработку без изменения данных. Нет игрушечного token → client и ложной авторизации 403. Изоляция подтверждается независимыми данными, а не только сходством JSON-ответа.

#### Темы в порядке изучения

1. Знакомая подготовка query и операция выборки; что относится к HTTP, а что остаётся в сервисе.
2. Контейнер параметров и provider; get_selection, затем read-only get_selected_tasks с двумя входными зависимостями.
3. Граф и зависимость результата: разные ветви не обязаны образовывать один учебный список steps.
4. Повторное использование provider в одном запросе и request-local cache; это не lru_cache, не singleton всех приложений и не обещание одного вызова на все будущие запросы.
5. Смысл override, оригинальный callable как ключ, подготовленные тестовые данные и обязательное восстановление состояния после проверки.
6. Ошибка HTTP-входа и исключение dependency; HTTPException уже знаком, смысл 503 объяснить как недоступность для ограниченного теста, не права доступа.
7. Почему зависимости не прячут запись задач и почему глубина/число узлов должны соответствовать реальной задаче.

#### Основная практика

Сначала создать подготовку параметров и подключить её к существующей выборке; затем соединить с get_planner в небольшом read-only provider. На каждое изменение выполнить знакомые проверки GET /tasks: без query, с is_done, разным sort_desc, limit на границах и за ними. Проверить, что POST/PUT/PATCH/DELETE сохранили прежний путь через сервис, а не стали побочными эффектами dependency.

Далее переустроить API-fixture под override: отдельный JsonStorage/tmp_path, подготовленные данные через прежний сервис, исходный get_planner как точка подмены. GET должен получать только этот набор. Проверить, что состояние рабочего файла не изменилось и после удаления подмены снова используется штатный provider. Не печатать и не изменять рабочие задачи ради доказательства изоляции.

Проверку отказа выполнять подменой provider на функцию с объяснённым HTTPException(503): запрос не возвращает успех/частичный результат и не меняет задачи. Это тест механизма, не обязательный maintenance-режим продукта. Для наблюдения cache допустим короткий тестовый граф с двумя потребителями одного provider и счётчиком: один запрос использует общий результат, следующий вычисляет его заново. Не оставлять ненужные ветви/маршруты в Planner только ради счётчика; обычная последовательность Python-вызовов не доказывает cache FastAPI.

#### Выход, приёмка и переход

Есть небольшой объяснимый граф, прежний контракт выборки и fixture без протекания override. Ученик отличает границу запроса от lifetime готового сервиса. A65 получает изученные Request/Depends/Annotated, опыт независимых запросов и error-проверок. Header/Response/cookie ещё не предполагаются изученными.

### 65. Заголовки и Response

#### Основная тема и назначение

Расширить понимание HTTP за пределы body на небольшом настоящем ресурсе проекта. Preference-ресурс будет развиваться в следующих двух занятиях; это не одноразовый `/context` и не новая предметная модель Task.

#### Точка A

- B64 достигнута: структура/настройки/зависимости работают, GET /tasks имеет подготовленную выборку, API-fixtures изолированы. JSON сохраняет задачи, CLI не менялся.
- Ученик различает request/response, знает HTTP-body, response_model, APIRouter, Pydantic и Annotated. Общая идея headers могла встречаться в HTTP-главе, но использование FastAPI Header и изменение Response вводятся здесь.
- В проекте нет `/preferences`, его роутера/схем или cookie planner_view. Нельзя просить прочитать cookie до объяснения следующего занятия.
- Сервер не требует версию клиента для операций задач. Добавление диагностического header не должно внезапно сделать весь Task CRUD недоступным без него.

#### Точка B

- В app/routers/preferences/ появляется рабочий router.py с GET /preferences; пакет создаётся по необходимости, а не набором пустых файлов заранее. Роутер подключён к тому же приложению один раз.
- GET пока не хранит предпочтение: возвращает view=compact и client_version из необязательного X-Client-Version либо null. Это честный первый этап возможности, не уже реализованная пользовательская настройка.
- Для входного header задан явный alias и ограничение длины 64 символа; пустая строка, если передана, остаётся строкой, не объявляется личностью пользователя. Слишком длинное значение даёт 422. Клиентский header не меняет Task и не становится доверенным server version.
- В ответ добавляется контролируемый X-Planner-Version, например техническая версия HTTP-контракта `1`. Источник значения находится в коде, не берётся из входного header; это не утверждение о новом GitHub Release. Header нужен preference-ответу, глобальный middleware не вводится.
- Ученик различает переданный FastAPI Response для настройки метаданных и создаваемый/возвращаемый Response. При возврате другого объекта изменения первого не считаются автоматически перенесёнными.

#### Темы в порядке изучения

1. Данные ресурса против метаданных обращения; знакомое HTTP-сообщение с body/header/status.
2. Header как источник входа, alias, нечувствительность HTTP-имён к регистру, optional/default и длина.
3. Response и установка server-controlled header; отличие входного значения от собственного выхода.
4. Подключение второго небольшого APIRouter в том же приложении; prefix и точный путь без скрытого redirect.
5. Контракт первого этапа preferences: пока default, без хранения и без изменения tasks.
6. Проверка status/body/header отдельно; недопустимый вход не является credential или разрешением.

#### Основная практика

Добавить GET /preferences, default view и необязательный client_version. При успешном ответе установить X-Planner-Version. Проверить запрос без header, с одной обычной строкой и со слишком длинным значением. Отдельно показать, что публичная версия определяется сервером и не равна автоматически входной строке.

Проверить JSON-body, status и headers как разные части ответа. Сверить точный GET /preferences с follow_redirects=False; Task CRUD не получает новых входных параметров и сохранился. Короткое исследование может найти ошибку «изменили один Response, вернули другой». Не требовать Header-модель, logging, request-id generator, middleware или frontend.

#### Выход, приёмка и переход

В том же приложении есть реально подключённый preference-ресурс и проверенный HTTP-контекст. Ученик объясняет отсутствие сохранения режима на этом этапе. A65.1 получает этот роутер и форму ответа; дальше сохраняется client_version и развивается view, а не создаётся новый `/context` или второй сервер.

### 65.1. Cookie и вид ответа

#### Основная тема и назначение

Превратить уже существующий default в небольшую настройку отдельного HTTP-клиента. Cookie служит только выбору compact/detailed: никакого аккаунта, идентификатора пользователя или защищённого доступа.

#### Точка A

- B65 достигнута: GET /preferences подключён, возвращает compact/client_version, принимает Header и устанавливает свой диагностический header. Ученик умеет управлять Response и проверять его части.
- Нет сохраняемой cookie, PUT/DELETE preference-маршрутов и body-схемы режима. Само чтение предыдущего JSON-ответа не заставляет следующий запрос помнить view.
- Ученик знает Pydantic, строку, множество допустимых значений и независимые TestClient-запросы. Cookie/Set-Cookie, клиентская jar и Literal вводятся здесь до использования в практике.
- Серверные задачи по-прежнему в JSON. Cookie не выбирает файл, storage или чужую задачу; CLI не должен менять формат/команды вслед за HTTP-preference.

#### Точка B

- GET /preferences читает planner_view как необязательное входное значение. Допустимы только compact/detailed; отсутствующее или неизвестное значение даёт compact. Минимальный fallback появляется сразу: чужая cookie не должна ломать схему ответа до будущего занятия.
- PUT /preferences принимает body со строго допустимым view, устанавливает planner_view и возвращает выбранный режим вместе с прежним client_version. PreferenceUpdate/PreferenceRead в schemas.py этого ресурса не являются новыми Task/PlannerService.
- Cookie используется только для preference-ресурса: фиксированный Path=/preferences, без Domain, локально Secure=False, с понятными базовыми HttpOnly=True и SameSite=lax. Здесь объяснить назначение используемых атрибутов кратко; подробный разбор угроз и настройка Secure относятся к 65.2. Срок истечения специально не задаётся, это session-cookie, не login-сессия.
- DELETE /preferences удаляет ту же cookie с согласованным Path и возвращает 204 без body. Удаление и диагностический header выполняются на том Response, который действительно отправляется клиенту.
- Первый клиент после PUT видит свой режим в GET, другой без cookie получает compact. Неверный body даёт 422 без установки/изменения preference. Эти операции не меняют ни одной записи Task в JSON.

#### Темы в порядке изучения

1. Почему предыдущий ответ сам по себе не является состоянием следующего запроса; клиентская cookie jar.
2. Cookie во входе против Set-Cookie в ответе; запись, повторная отправка, Path и удаление.
3. Literal как ограниченный набор значений, Pydantic body и чтение строки из недоверенной cookie; ошибка body против fallback старой/чужой cookie.
4. Сохранение прежнего preference-ответа и роли Header; без смешивания настроек с task-схемами.
5. Краткий смысл фиксированных атрибутов cookie, отсутствие server-side session и секретов в значении.
6. Возвращаемый Response для DELETE 204; почему удаление другого Path или другой cookie не сбрасывает выбранное значение.
7. Два клиента, последовательность запросов и отличие TestClient от Swagger UI; браузер может ограничивать отправку Cookie в интерактивной документации.

#### Основная практика

Продолжить тот же preferences/router.py и создать необходимые schemas.py без лишних заглушек. Реализовать GET из cookie, PUT по body и DELETE; Header/client_version и диагностический server header сохранить. Объяснить каждый новый Cookie/Literal/Response-приём до требования самостоятельно его применить.

Основной сценарий: GET без cookie → PUT detailed → GET detailed → DELETE → GET compact. Проверить отдельный второй клиент, ошибочный view в body, чужую cookie и пустой DELETE-body. После ошибочного PUT первый клиент сохраняет прежний допустимый режим. Проверять реальные HTTP-запросы и jar, а не только вызывать обработчик как обычную функцию.

Отдельно прочитать задачи и статистику до/после preference-сценария: предметные данные неизменны. Не добавлять меню frontend, файл preferences.json, таблицу настроек или ветку CLI для этой cookie.

#### Выход, приёмка и переход

Есть полная локальная возможность выбора/сброса режима с минимально корректным поведением на чужом значении. Ученик может объяснить, где живёт состояние и почему другой клиент не получает его автоматически. A65.2 получает работающий ресурс и безопасные базовые фиксированные атрибуты, но ещё не получает настройку Secure по окружению и подробное понимание границ доверия.

### 65.2. Безопасность cookie

#### Основная тема и назначение

Укрепить существующую cookie-возможность и научить правильно трактовать её ограничения. Главное изменение проекта: осознанная настройка Secure и защищённый контракт ввода/удаления, а не повторное создание GET/PUT/DELETE.

#### Точка A

- B65.1 достигнута: один preference-ресурс, Literal-схемы, cookie planner_view, fallback compact, правильный DELETE Path=/preferences, два независимых клиента. Task API и CLI не меняют данные от preferences.
- Ученик понимает чтение/установку/удаление и видел базовые HttpOnly/SameSite. Не требуется ранее знать поведение HTTPS, различие JavaScript-доступа и отправки cookie, cross-site ограничения или недостаточность cookie как авторизации.
- Settings содержит json_path/app_name; Secure для локального опыта задан False. COOKIE_SECURE и соответствующий валидатор ещё отсутствуют.
- В проекте нет пользователя, login/logout, session_id, token и permissions. DELETE preferences является сбросом настройки, не logout из аккаунта.

#### Точка B

- Ученик понимает, что клиент может изменить cookie вручную. Строгий body и безопасный fallback чтения не доверяют тому, что значение раньше выдал только сервер. view не влияет на список доступных задач или права.
- Settings получает cookie_secure; COOKIE_SECURE задаётся явными true/false с понятным default False для локального HTTP. Разбор значения строгий; bool("false") не используется, неизвестная строка не превращается молча в False. Проверка появляется при сборке, не на каждом запросе.
- app/api.py уже сохраняет собранный Settings в app.state.settings. В занятии 65.2 ученик добавляет get_settings и SettingsDep в app/core/dependencies.py: provider принимает Request и возвращает request.app.state.settings. Preference-router получает тот же объект через знакомые Depends/Annotated, без чтения os.environ в handler и без второго Settings.
- HttpOnly=True, SameSite=lax, отсутствие Domain и Path=/preferences сохраняются осознанно; Secure выбирается конфигурацией. Для HTTPS-окружения он должен быть True; режим HTTP отдельно документирован. Удаление адресует ту же cookie и согласует policy.
- Проверки подтверждают атрибуты Set-Cookie, сброс и отсутствие записи/выдачи прав при подмене. HTTP/HTTPS-семантику клиента не выдают за проверку реального TLS, SameSite-политики браузера или защиту от всех атак.
- B блока достигнута: JSON-проект с конфигурацией и зависимостями готов к объяснению пределов файлового хранения в 66. Никакая БД ещё не подключена.

#### Темы в порядке изучения

1. Данные клиента против авторитетного решения сервера; что может сделать пользователь со своей cookie.
2. Недопустимый view и уже реализованный fallback; почему предпочтение нельзя превратить в role/admin.
3. HttpOnly: доступ JavaScript против автоматической отправки браузером. Secure: транспортная граница. SameSite: отдельное ограничение контекста отправки; ни один флаг не является общей системой прав.
4. Path/Domain и удаление, session-cookie против server-side session; закрытие браузера не использовать как доказательство logout.
5. Явная настройка HTTP/HTTPS-политики; строковые bool, strict parse, default и ошибка запуска.
6. Создание get_settings/SettingsDep для уже собранного app.state.settings; применение знакомых Depends/Annotated без второго объекта конфигурации.
7. Что проверяют headers/jar/TestClient, чего не доказывают; осмысленная браузерная проверка там, где доступна, без задания создать frontend.

#### Основная практика

Добавить COOKIE_SECURE в существующую конфигурацию и строго разобрать true/false. В app/core/dependencies.py создать общий get_settings/SettingsDep, который возвращает уже сохранённый app.state.settings, затем передать его в preference-операции. Осознанно проверить policy установки и удаления. Не читать окружение повторно и не переписывать Settings/get_planner/сам ресурс целиком.

На отдельных клиентах проверить default HTTP и конфигурацию Secure=True: атрибут в заголовке, отправку cookie в подходящем контексте, DELETE и последующий fallback. TestClient с HTTPS base_url может исследовать соответствующую клиентскую семантику, но не доказывает наличие настоящего HTTPS-сервера. SameSite/HttpOnly проверять как атрибуты; не утверждать, что httpx выполнил все браузерные ограничения.

Подставить неизвестный view, значение вроде admin, попытаться передать cookie вместо JSON_PATH и проверить неизменность выбора storage/задач. Неверный COOKIE_SECURE останавливает сборку понятно; успешные случаи не трогают рабочие данные тестами. Завершить короткой регрессией прежнего CRUD, stats и CLI, а не новой реализацией всего проекта.

#### Выход, приёмка и переход

Ученик показывает рабочую настройку и объясняет реальные границы доверия. Cookie не содержит секретов, не авторизует, не выбирает чужое хранилище. Блок передаёт следующему рабочий JSON Planner: config/dependencies уже реализованы и понятны, но Engine/Session/ORM ещё не изучены. Урок 66 исследует реальные load/save этого же сервиса.
