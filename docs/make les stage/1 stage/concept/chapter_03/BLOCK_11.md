## 1. Назначение, A → B и границы

**Рамка:** [COURSE.md](COURSE.md), `FRAME_ACCEPTED`, `chapter-03-frame-v1` от 2026-10-27. Позиция — блок 11 из блоков 9→10→11→12. Название и границы следуют принятой строке интерфейса BLOCK_11; цель главы и A→B не меняются.

**Роль в B главы.** На готовом срезе HTTP чтения и создания ученик укрепляет границу входа и ответа, затем добавляет PUT, PATCH и DELETE к тому же Planner. Он сохраняет доменную Task, существующий PlannerService, JsonStorage, CLI и формат файла. Результат подготавливает проверяемый ручной контракт для BLOCK_12.

**Вход A.** Принятый COURSE описывает предыдущую часть как планируемый выход BLOCK_10, а не доказанное состояние checkout или навык ученика. До первой правки ученик сверяет запуск и ручные GET/POST, route → прежний service → общий JSON, чтение через CLI и после нового запуска. Если этого нет, сначала восстанавливается недостающий вход BLOCK_10/главы 2; этот блок не создаёт второй storage, POST или сервис. HTTP, Pydantic before-validator, response_model, PUT/PATCH и TestClient не считаются известной A. Личное освоение всех предпосылок не проверено.

**Наблюдаемая B блока.** Ученик самостоятельно демонстрирует точную проверку POST-входа с 422 без изменения данных; разделённые схемы входа/ответа; существующий общий путь сохранения и серверный ID; PUT полной формы с прежними id/tags; PATCH с пропуском/null и явным `false`; DELETE с пустым 204. Чтение и все изменения проходят через прежний сервис и общий JSON. Ошибки не дают частичной мутации, CLI и API видят одно состояние.

**Инварианты продукта.** Planner API v1.0.0; фиксированные восемь endpoint из COURSE: `GET /health`, `GET /tasks`, `GET /tasks/{task_id}`, `GET /stats`, `POST /tasks`, `PUT /tasks/{task_id}`, `PATCH /tasks/{task_id}`, `DELETE /tasks/{task_id}`. Внешний объект содержит только `id/title/priority/is_done`; внутренние `tags` сохраняются в Task и JSON. Создание остаётся у `add_task`; id определяется существующим сервисом по текущим данным, а не клиентом. Входной title очищается до проверки длины 1–120; priority 1–5; обычная Pydantic-конверсия остаётся обычной. PUT требует `title/priority/is_done` и сохраняет id/tags. PATCH применяет переданные ненулевые поля; пропуск и `null` не меняют значение, `false` — применяет. Допустим пустой PATCH согласно договору. DELETE использует имеющийся `delete_task`, успех — 204 без тела. Корректный отсутствующий id даёт 404; неверное тело — 422 до мутации. StorageError не маскируется. Query, порядок filter→sort id→limit, stats всего хранилища, CLI, сериализация, путь JSON, существующие API/сервисные функции и пользовательские данные сохраняются.

**Границы.** Не добавлять DB, async, auth, Depends, APIRouter, TestClient, новый MemoryStorage, временный список, второй CRUD/service/storage, новую сущность или изменение JSON-схемы. TestClient/автотесты принадлежат следующему блоку. Здесь допустимы существующие ручные сценарии и адресные проверки уже имеющихся service tests, если это нужно для доказательства конкретной операции; новый тестовый слой не является B.

### Порядок, рост самостоятельности и условные стыки

Сначала POST-вход получает безопасную нормализацию и ограничения, после чего оформляются схемы и проверяется настоящее сохранение. Только затем создаются service-level операции PUT и PATCH; их безопасная проба предшествует HTTP-маршрутам. Отдельное подзанятие `54.1` делает семантику пропуска, `null` и `false` наблюдаемой до регистрации PATCH. DELETE использует уже имеющийся service. Финальный smoke интегрирует ранее созданное, а не впервые учит API.

**Вход от BLOCK_10 (условный, окончательно сверит F1–F3):** необходимы работающие GET/POST и ручная проверка общей записи через прежний сервис/JSON/CLI → поставщик BLOCK_10 → перед первым изменением ученик повторяет smoke и показывает тот же объект после нового запуска. Фактическая A ученика не подтверждена. При провале зависимые проектные практики ждут восстановления входа, самостоятельные схемные упражнения остаются планируемыми.

**Выход к BLOCK_12 (предложение, окончательно сверит F1–F3):** полный ручной контракт восьми endpoint, в том числе 422 без мутации, 404, PUT с прежним id, PATCH с skip/null/false и DELETE 204 без body → поставщик этот блок → BLOCK_12 воспроизводит smoke до TestClient и использует тестовый путь данных. От BLOCK_12 не требуется быть завершённым для локального B4.

### `51` · Очистка входной строки — основное занятие дня 1

**Идентичность.** Текущий физический материал `backend/content/materials/chapter_03/block_11/51 - Очистка входной строки.md`; canonical source `HTTP, API и FastAPI - Planner API/51 - Очистка входной строки.md`; вычисленный по `_stable_lesson_id()` ID `lesson-3795384d9e6fccf65e6daded`. Alias создаётся через `PLANNER_API_MODULE_LABELS`/`LESSON_SOURCE_ALIASES`.

1. **Тема и роль.** Научиться очищать только строковый `title` на HTTP-входе перед предметными ограничениями. Это первая небольшая правка к готовому POST и опора для `51.1`; не менять доменную Task или CLI.
2. **A, источник, статус.** Планируется: предыдущая B из COURSE/BLOCK_10 — POST передаёт вход в существующий Planner и сохраняет JSON. До изменения проверить маршрут, POST, CLI и реальный файл; отдельно увидеть структуру TaskCreate. Личный навык не проверен. HTTP before-validator новый.
3. **Наблюдаемая B.** Ученик объясняет, почему очистка должна предшествовать проверке длины, сам добавляет before-validator, получает сохранённый `"Разобрать API"` из ввода с краевыми пробелами и безопасно передаёт неподходящий тип стандартной проверке Pydantic.
4. **Механизмы по порядку.** Входная модель и обычная проверка типа → before-validator как преобразование сырого значения → проверка типа до `.strip()` → проба со строкой и числом → самостоятельная правка. Не добавлять здесь min/max length, priority limits, новый POST или доменную нормализацию.
5. **Самостоятельная практика и формат.** Проектная работа в существующем Planner: в TaskCreate ученик сам пишет валидатор; через прежний POST отправляет нормальную строку и строку с пробелами; затем проверяет нестроковой raw input. Он сопоставляет ответ и файл, не редактируя их напрямую и не вводя новый service.
6. **Результат, критерий и передача.** POST продолжает возвращать 201 и сохраняет очищенное название; нестроковое значение завершается обычным отказом схемы, не AttributeError/500; на `51.1` передаётся та же нормализующая схема. Если общий POST/JSON на входе не подтверждён, практику отложить до восстановления A.
7. **Видимая теория: 1200–1600 слов.** Нужны новый Pydantic before-validator, порядок сырого типа и преобразования, безопасный отказ и отличие HTTP-границы от доменных правил; одной короткой подсказки недостаточно, но длина и диапазон priority вынесены в `51.1`.

### `51.1` · Ограничения и ошибка 422 — обязательное подзанятие дня 1

**Идентичность.** Единственный текущий урок-поставщик: физический source `backend/content/materials/chapter_03/block_11/57 - Pydantic-валидация и ошибка 422.md`; canonical source `HTTP, API и FastAPI - Planner API/57 - Pydantic-валидация и ошибка 422.md`; сохранённый ID `lesson-c75ffe58ef0405d3f5a16ab8`; frontend index → `Lesson57`, display override → `51.1`. Отдельный backend companion `51.1 - Ограничения и ошибка 422.md` имеет вычисляемый ID `lesson-6b8ccebb04527f52ee095b21`, но не включён во frontend index и не считается вторым пунктом карты.

1. **Тема и роль.** Задать границы чистого title и priority и читать отказ 422 как ответ до предметного действия. Это не повтор валидации типа, а проверка значения после очистки.
2. **A, источник, статус.** Планируется: `51` самостоятельно очищает title; проверить код и граничный успешный POST до применения ограничений. Источник — этот паспорт и цель COURSE; выполнение учеником не подтверждено.
3. **Наблюдаемая B.** Ученик сам применяет длину очищенного title 1–120 и priority 1–5; предсказывает и наблюдает 422 на пустом/слишком длинном title и priority 0/6; доказывает равенство состояния до/после отказа.
4. **Механизмы по порядку.** Нормализованное значение → ограничения Field → порядок перед handler/service → HTTP 422 и чтение loc/type/msg → граничные пробы. Объяснить, что обычная Pydantic-конверсия сохраняется, а ошибки сервиса не следует объявлять ошибками формата.
5. **Самостоятельная практика и формат.** На текущем POST ученик сам задаёт границы, отправляет title длиной 1 и 120, пробельное/пустое значение, чистую длину 121 и priority 1, 5, 0, 6; учитывает raw строку, чья длина превышает 120 только за счёт краевых пробелов. Снимает список/статистику и проверяет исходный JSON до/после каждого отказа.
6. **Результат, критерий и передача.** Границы принимаются/отклоняются по очищенному значению; все невалидные запросы дают 422 до мутации, успешная запись сохраняется прежним POST. Дальше `52` переносит эти правила в TaskCreate без изменения поведения.
7. **Видимая теория: 1400–1800 слов.** Первое предметное объяснение диапазонов, порядка очистки и статуса отказа требует нескольких сравниваемых границ; практика должна включать каждый край и доказательство no-mutation.
