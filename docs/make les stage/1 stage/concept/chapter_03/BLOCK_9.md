## 1. Назначение, место, A→B и границы

Этот блок — первый из четырёх главы 3 «HTTP и FastAPI: от существующего Planner к проверенному API». Он готовит ученика понимать HTTP до запуска сервера и Postman. Принятая рамка: [COURSE.md](COURSE.md), `FRAME_ACCEPTED`, `chapter-03-frame-v1`; цель B главы сохранена: Planner API v1.0.0 в том же проекте, с теми же PlannerService, JsonStorage, CLI и `data/tasks.json`.

**A блока.** По принятому COURSE глава 2 планирует для ученика предметные действия Planner, Python и JSON: Task, CLI, функции, словари и запись задачи. Личное прохождение и checkout не предъявлены, поэтому эти навыки **не проверены**. До выдачи маршрута преподаватель проверяет, может ли ученик объяснить знакомую операцию Planner и прочитать запись Task JSON; если нет, BLOCK_10 восстанавливает только нужную опору до первого запроса. HTTP, client/server, request/response, заголовки, статусы и маршруты считаются новыми. Источники: COURSE §1 и интерфейс блока 9; планируемый выход главы 2, COURSE и BLOCK_8.

**B блока.** Ученик своими словами прослеживает сообщение от клиента до ответа сервера; самостоятельно строит и разбирает учебные модели request/response; выбирает метод по намерению, составляет путь к collection или item, размещает значения в path/query/body и объясняет ожидаемый ответ. Проверка — семь собственных коротких редакторских моделей и итоговый новый сценарий с обоснованием решений. Это учебные модели, не сетевой обмен и не реализация Planner API.

**Вклад и передача.** Блок закрывает G1 главы: самостоятельное чтение и составление договора до знакомства с Postman. BLOCK_10 получает карту всех восьми endpoint и способность предсказать расположение входов и форму ответа; перед фактической выдачей он проверит эту A на новом запросе до отправки в Postman. Входное ребро от главы 2 — планируемое: «прочитать Task и объяснить операцию → глава 2/BLOCK_8 → короткая диагностика до HTTP». Выходное ребро — планируемое: «разобрать новый request и предсказать ответ → BLOCK_9, дни 1–5 → ученик объясняет незнакомый пример до первого Postman-запроса». Соседние блоки ещё не приняты; эти договоры условны до F1–F3.

**Границы продукта.** На входе существующий Planner API кодом не подтверждён; отдельный checkout ученика не доступен. Блок не меняет код, JSON или CLI; не вводит FastAPI, Uvicorn, Postman, Pydantic, тестовый клиент, сеть, авторизацию или новое хранение. Публичное представление задачи содержит `id`, `title`, `priority`, `is_done`; внутренние `tags` остаются в Task/JSON и не выдаются наружу. Согласованный API включает `GET /health`, `GET /tasks`, `GET /tasks/{task_id}`, `GET /stats`, `POST /tasks`, `PUT /tasks/{task_id}`, `PATCH /tasks/{task_id}`, `DELETE /tasks/{task_id}`. Их детали приведены в §4; здесь они служат учебными примерами, а не утверждением, что сервер уже работает.

## 3. Семь полей паспортов

### `41`. Адрес и метод запроса

1. **Тема и роль.** Первый шаг от знакомого локального Planner к сообщению отдельному серверу. Ученик понимает стороны обмена, адрес и намерение; пока не выбирает методы для всех операций и не отправляет запрос.
2. **A и источник/статус.** Операции Planner и Python-строки планируются в главе 2, но личное выполнение не проверено: COURSE §1 и планируемые BLOCK_8/глава 2. До маршрута проверить чтение Task JSON и объяснение одной CLI-операции. В занятии восстановить только нужную знакомую операцию; HTTP считать новым.
3. **Наблюдаемая B.** Своими словами различает клиента и сервер; самостоятельно возвращает `method` и `path` из переданных строк, не меняя их и не путая URL с путём к файлу.
4. **Механизмы по порядку.** Клиент отправляет request — сообщение с намерением; сервер применяет правила к своему состоянию и возвращает response — сообщение с результатом; обе стороны могут быть программами на одном компьютере. Затем URL как адрес сервиса, path как часть адреса операции, method как метка намерения. Без сокетов, DNS и полного синтаксиса URL. Объяснение → безопасная схема обмена → первая проба на готовой паре → собственная функция.
5. **Самостоятельная практика и формат.** Кодовая задача в редакторе с автопроверкой `solve(method, path)` (текущий ключ `41`). Ученик пишет тело функции, возвращающее модель с переданными `method` и `path`, и проговаривает, что в модели пока нет реального обмена. Входы готовые; выбор метода и разбор URL не требуются. Проверить обычную и отличающуюся пару.
6. **Выход, критерий и переход.** Возвращены ровно согласованные значения, ученик объяснил, где находятся клиент, сервер и состояние Planner. `41.1` использует готовые method/path и добавляет headers/body; до этого перехода проверить, что ученик не принимает словарь за отправленный HTTP-запрос.
7. **Теория: 1100–1500 слов.** Первое знакомство требует ввести границу процессов, роли, URL/path и метод, но синтаксическая практика намеренно узкая и входы готовы. Диапазон покрывает простую модель и границы переноса, не раздувая объяснение сетевой инфраструктурой.

### `41.1`. Заголовки и тело запроса

1. **Тема и роль.** Продолжить модель request, объяснив, зачем в сообщении отдельно хранятся метаданные и содержимое.
2. **A и источник/статус.** Method/path из `41` — планируемая опора; фактическое освоение не доказано. До выдачи проверить, что ученик сам собрал учебную пару и может объяснить её поля. Python-словарь и условие проверки `None`/пустого значения заявлены в планируемом выходе главы 2, личное применение не проверено; восстановить на маленьких независимых примерах до редактора.
3. **Наблюдаемая B.** Самостоятельно формирует словарь request с правильными headers, сохраняет body и отличает отсутствующее тело от пустого JSON-объекта.
4. **Механизмы по порядку.** Request состоит из стартовой строки/метаданных и body; здесь нужен учебный словарь частей. `Accept` сообщает желаемый формат ответа, `Content-Type` — формат переданного body; их роли различны. Для `None` тело отсутствует, `{}` — передан пустой объект. Словарь Python — модель, JSON — представление, HTTP — передача; сериализацию и сеть отложить. Объяснить каждый header, показать 2 безопасных примера, затем дать самостоятельную функцию.
5. **Самостоятельная практика и формат.** Автопроверяемый редактор `solve(method, path, client_version, body)` из текущего ключа `41.1`. Ученик пишет сборку заголовков `Accept: application/json`, `Planner-Client-Version` и `Content-Type` только при наличии body; возвращает точные ключи `method`, `path`, `headers`, `body`. Сам проверяет отсутствие тела, `{}`, обычный body и другой переданный method/path; ничего не отправляет и не меняет.
6. **Выход, критерий и переход.** Заголовки соответствуют назначению, body сохранено, `None` и `{}` различимы. `42` начинает с уже собранного request и объясняет, где увидеть исход обработки; до него проверить именно различение формы тела.
7. **Теория: 1200–1600 слов.** Четыре новых части модели и сходные headers требуют контраста; знакомый Python-словарь может сократить объяснение только после входной проверки. Примеры ограничены двумя формами body, без сетевой отправки и преждевременной Pydantic.

### `42`. Статус и результат запроса

1. **Тема и роль.** Показать, что исход обработки сообщается отдельно от тела ответа. Это первое чтение результата, не построение всего response.
2. **A и источник/статус.** Request-модель `41.1` планируется и будет проверена перед выдачей; старые занятия по HTTP из исторического BLOCK не считаются подтверждением новой последовательности. Нужные Python-функции/условия тоже не подтверждены; если используются в `solve`, их коротко восстановить до практики.
3. **Наблюдаемая B.** Ученик своими словами объясняет status и по известной метке результата самостоятельно возвращает согласованный код для чтения, создания, удаления без тела, ошибочного запроса, отсутствующего ресурса или сбоя сервера.
4. **Механизмы по порядку.** Response приходит отдельно от request; status кратко сообщает исход. Объяснить `200` чтения, `201` создания, `204` успех без тела, `404` отсутствующего item; затем дать ориентир групп `2xx`, `4xx`, `5xx`. `400` — общий пример, не контракт ошибки валидации Planner; подробный `422` остаётся следующим блокам. Сначала классифицировать примеры, безопасно сопоставить один контраст, затем писать таблицу/ветвление.
5. **Самостоятельная практика и формат.** Автопроверяемый редактор `solve(outcome)` по существующему ключу `42`. Самостоятельно выбрать status для шести известных исходов, вернуть код, проверить успешное чтение, создание и удаление без тела, а также `not_found` и `server_error`. Входы заранее названы; неизвестную метку, HTTPException и мутацию не вводить.
6. **Выход, критерий и переход.** Каждый исход сопоставлен коду из договора; объяснено, почему `204` не обещает JSON. В `42.1` ученик добавит к уже заданному status форму тела и заголовки; перед переходом проверить, что он не выводит статус по наличию body.
7. **Теория: 1200–1600 слов.** Новый словарь статусов требует разложить несколько легко смешиваемых результатов. Готовые метки снижают кодовую нагрузку, но теория должна обосновать коды и пределы обобщения; статус не следует растягивать перечислением всех HTTP-кодов.

### `42.1`. Тело ответа и Content-Type

1. **Тема и роль.** Завершить первую модель response: status, headers и возможное содержимое.
2. **A и источник/статус.** Status и request из `41.1`/`42` — планируемая A; до фактической выдачи проверить самостоятельную сборку request и выбор status на новом случае. Словари и функция заявлены предыдущим маршрутом, но личная готовность не проверена; восстановить только недостающий синтаксис до действия.
3. **Наблюдаемая B.** Самостоятельно собирает `status`, `headers`, `body`, включая `Content-Type` при JSON-теле; сохраняет разницу между отсутствующим телом и `{}`.
4. **Механизмы по порядку.** `Content-Type` описывает тело ответа; код статуса не заменяет body. Успешный ответ может содержать объект, пустой список или не содержать body. Для `204` тела нет; `{}` остаётся переданным JSON-объектом. `X-Request-ID` относится к сообщению и не является id задачи. Объяснение → разбор пары примеров → безопасная проба с входом `None`/`{}` → самостоятельная функция.
5. **Самостоятельная практика и формат.** Автопроверяемый редактор `solve(status, body, request_id)` существующего ключа `42.1`. Ученик формирует headers с request ID, добавляет JSON content type только при имеющемся body, возвращает точную модель. Проверяет `200` с объектом, `200` с `{}`, `404` с телом ошибки и `204` с `None`; статус передан готовым, создавать задачу и искать item не нужно.
6. **Выход, критерий и переход.** Модель не теряет статус/body, заголовок типа добавлен только по предусмотренному правилу; ученик объясняет `None`/`{}` и неприменимость чтения JSON при `204`. `43` использует понимание сообщений для выбора метода; перед ним проверить знание difference status/body.
7. **Теория: 1200–1600 слов.** Продолжается знакомство с новыми response-полями; нужны различающие случаи `204` и пустого JSON и роль request ID. Знакомый словарь — только условная опора, поэтому диапазон не опускается ниже 1000.

### `43`. Методы и изменение задачи

1. **Тема и роль.** Выбрать HTTP-метод по смыслу действия Planner, не реализуя операцию.
2. **A и источник/статус.** Действия над задачами планируются главой 2; факт самостоятельного выполнения конкретным учеником не подтверждён. Request/response и status планируются в занятиях `41`–`42.1`; перед выдачей проверить их на новом примере. Без этой проверки сначала вернуть соответствующее короткое объяснение.
3. **Наблюдаемая B.** Для list/get/create/replace/update/delete выбирает GET/POST/PUT/PATCH/DELETE и объясняет, чем полная замена отличается от частичной и почему одинаковый эффект повторного метода не гарантирует одинаковый ответ.
4. **Механизмы по порядку.** GET читает; POST создаёт в договоре этого Planner; PUT заменяет полное изменяемое представление; PATCH передаёт только изменяемые поля; DELETE удаляет. Затем безопасность метода по назначению отличить от контроля доступа; идемпотентность — от идентичности ответов и гарантии «ровно один раз». Явное `false` — значение, а не пропуск. Сначала объяснить и сравнить по одной операции, безопасно попробовать таблицу на простых предметных глаголах, затем перенести на новый набор действий.

### `44`. Ресурс и адрес операции

1. **Тема и роль.** Построить карту путей Planner и понять масштаб адресуемого объекта.
2. **A и источник/статус.** Выбор метода планируется по `43`; string formatting и Python-словарь упомянуты в маршруте главы 2, но навык не проверен. Перед самостоятельным формированием item path дать короткую пробу подстановки переданного id и проверить её.
3. **Наблюдаемая B.** Для восьми операций возвращает согласованную пару method/path; отличает `/tasks` как collection, `/tasks/{task_id}` как item и технические пути `/health`, `/stats`. Не делает вывод, что переданный id существует.

Collection/item, path и endpoint; одна коллекция может иметь разные методы; id указывает адрес, а поиск подтверждает существование отдельно. Готовая таблица методов может быть входом из заготовки; ученик сам выбирает path для list/create, item-операций, health и stats, возвращает method/path для всех восьми действий. Проверить два разных id и общий collection path у list/create. Нельзя запускать router, проверять storage или придумывать 404 для одного лишь id.

7. **Теория: 1400–1800 слов.** Нужно объяснить ресурсный словарь, collection/item, четыре категории маршрутов и сохранить границу внутреннего хранения. REST даётся как практический ресурсный стиль, не как полный набор ограничений; несколько контрастных адресов оправдывают объём.

### `45`. Данные и договор запроса

1. **Тема и роль.** Соединить метод, адрес, данные и ожидаемый исход в полную учебную модель для передачи в BLOCK_10.
2. **A и источник/статус.** Части request/response, таблица методов и адреса планируются днями 1–4; фактическое освоение неизвестно. Перед выдачей проверить все три на новом обмене. Планируемая A из главы 2 — значения Task и словари; условия практики главы 2 должны подтвердить нужную работу с mapping до неё.
3. **Наблюдаемая B.** Самостоятельно собирает модель запроса для известной операции: значения попадают в path/query/body по роли, серверные id/defaults не выдумываются, явный `False` сохраняется; объясняет ожидаемую форму ответа на двух контрастах.
4. **Механизмы по порядку.** Path адресует ресурс; query настраивает чтение списка; body передаёт значения создания/изменения; headers остаются метаданными. Query-параметры `is_done`, `sort_desc`, `limit` и defaults/bounds из COURSE; клиент передаёт только указанные значения. POST: `title/priority`, сервер назначает id и начальное `is_done`; PUT — полная изменяемая форма; PATCH — только присутствующие поля. `False` отличается от отсутствующего ключа. Ожидания: пустой список `200`, отсутствующий item `404`, создание `201`, удаление `204` без тела. Ошибки полей и `422` изучаются позже. Объяснить три места данных отдельно, дать пробу на одну операцию, затем самостоятельное соединение.
5. **Самостоятельная практика и формат.** Автопроверяемый редактор `solve(action, task_id, values)` существующего ключа `45`; готовая route-функция в стартере уже возвращает method/path. Ученик пишет распределение значений и возвращает `method`, `path`, `query`, `body`. Проверить list без параметров, явный `False` в query, create без серверных полей, полный replace, частичный update с `False`, get/delete без body и health/stats без входов. Проверить, что исходные `values` не изменились. Затем самостоятельно объяснить пустую collection против отсутствующего item и `201` против `204`. Никаких запросов, URL-кодирования, валидации или мутаций.
6. **Выход, критерий и переход.** Все входы размещены в согласованном месте, значения не потеряны, серверные поля не присвоены клиенту, два response-контраста объяснены. BLOCK_10 до первого Postman-запроса выдаёт новый сценарий на самостоятельное предсказание и проверяет именно эти критерии; при пробеле повторяет только нужную модель.
7. **Теория: 1500–1900 слов.** Это первая интеграция нескольких ранее объяснённых частей, включая различение фильтра/изменения и пропуска/`False`. Предшествующие результаты планируются, но освоение ученика не подтверждено, поэтому занятие сохраняет достаточное объяснение и короткие раздельные пробы до сборки.

## 4. Неизменяемая карта Planner и локальная приёмка

| Метод/путь | Расположение входа | Ожидаемый исход по принятому COURSE |
|---|---|---|
| `GET /health` | нет | `200`, короткое состояние сервиса |
| `GET /tasks` | query: `is_done`, `sort_desc`, `limit` (optional) | `200` + список; пустой список тоже `200`; filter → sort id → limit; defaults `None`, `False`, `10`, limit 1–50 |
| `GET /tasks/{task_id}` | path: id | `200` + одна публичная задача; отсутствующий item — `404` |

| `POST /tasks` | body: `title`, `priority` | `201` + полная запись с назначенными сервером id и `is_done` |
| `PUT /tasks/{task_id}` | path + полный body `title`, `priority`, `is_done` | `200` + запись с прежним id |
| `PATCH /tasks/{task_id}` | path + только переданные изменяемые поля | `200` + полная запись после изменений |

Это проверка учебной модели, не API smoke и не доказательство работоспособности сервера.

Ожидаемая передача в BLOCK_10: «новый обмен → самостоятельно выбрать метод, путь и расположение входов; предсказать статус и наличие body → BLOCK_9, итог дня 5 → объяснить новый пример до первого запроса Postman». Поставщик и условие проверки указаны; стык **предлагается** до общей F-приёмки.
