### Неизменяемый API-договор

| Метод/путь | Вход и успех | Требование |
| --- | --- | --- |
| `GET /health` | без входа → `200` | Состояние сервиса |
| `GET /tasks` | optional `is_done`, `sort_desc`, `limit` → `200` + список | `is_done=None`, `sort_desc=False`, `limit=10`, диапазон 1–50; filter → sort по id → limit; пустой список — `200` |
| `GET /tasks/{task_id}` | path id → `200` + задача | Отсутствующий item — `404` |
| `GET /stats` | без входа → `200` + сводка | Всё storage, независимо от list-фильтров |
| `POST /tasks` | body `title`, `priority` → `201` | Сервер назначает id и `is_done=False` |
| `PUT /tasks/{task_id}` | полная изменяемая форма → `200` | Полная замена, прежний id; отсутствующий item — `404` |
| `PATCH /tasks/{task_id}` | только переданные изменяемые поля → `200` | Пропуск поля не равен переданному `false`; отсутствующий item — `404` |
| `DELETE /tasks/{task_id}` | path id → `204`, без тела | Удаление; отсутствующий item — `404` |

Публичный Task содержит `id/title/priority/is_done`; `tags` остаётся внутри модели/JSON. Для title: trim, непустое значение, 1–120 символов после trim; priority 1–5. Невалидный запрос — `422` без изменения состояния. API сохраняет задачи в том же JSON, который использует CLI. Postman-сценарии входят в передачу; автоматические HTTP-проверки используют TestClient; итог также включает README/инструкции и выпуск проверенной версии.

Основание `B_AGREED`: старый COURSE (`bfa2eecc^`) устанавливает эту B и договор; прямой мандат позволяет менять внутреннюю дидактическую организацию при сохранении входа и конечного продукта. Нового согласования цели не требуется.

### Интерфейс BLOCK_9 — HTTP-договор (тип: теория/исследование)

- **Роль/B:** дать личную модель обмена до кода; ученик сам разбирает знакомую операцию Planner на стороны, запрос и ответ, затем строит согласованные method/path/данные.
- **Ожидаемая A:** предметные операции и Python/JSON по плану главы 2; личное освоение не подтверждено. Входная проба — описать команду и прочитать запись Task. HTTP считать новым.
- **Механизмы:** client/server, request/response, method, URL/path, headers, body, status, Content-Type, resource/collection/item, endpoint, path/query/body. Объяснение и безопасная проба предшествуют самостоятельному разбору. Не вводить сервер, FastAPI, Pydantic или Postman как известные.
- **Критерий:** самостоятельно разобрать незнакомый обмен, расположить данные и объяснить разницу `204` без body, отсутствующего item `404` и пустого list `200`.
- **Передача:** BLOCK_10 получает договор всех восьми endpoint; до первого запроса ученик объясняет новый пример. При ошибке повторить модельный request/response до запуска.
- **Продукт:** прежний Planner остаётся без изменений; растёт самостоятельное чтение HTTP.
- **Нагрузка:** пять последовательных тем/практик по интерфейсу; BLOCK_9 выбирает и обосновывает дополнительные подзанятия.
- **Риск/A:** фактический выход главы 2 может разойтись; диагностировать и восстановить только нужный предметный/JSON контекст.

### Интерфейс BLOCK_10 — наблюдение и интеграция (тип: проектный)

- **Роль/B:** сначала наблюдать обмен Postman, затем добавить к тому же Planner рабочие чтение и создание.
- **Ожидаемая A:** BLOCK_9 — план, не освоенный факт; проектный вход главы 2 также проверяется перед применением.
- **Механизмы:** Postman/request-response; FastAPI route и Uvicorn; OpenAPI/Swagger; маршрут вызывает существующий service; schema и query. Дать пробу каждого нового механизма до самостоятельного соединения. Никакой DB, второго service, списка задач или storage.

- **Нагрузка:** пять дней группируют диагностику/наблюдение, сервер/route, чтение, выборку, создание; каждое новое звено сначала объясняется.
