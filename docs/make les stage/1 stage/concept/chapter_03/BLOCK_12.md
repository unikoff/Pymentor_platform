### A: что приходит из блока 11

**Планируемая, не подтверждённая личным выполнением A:** BLOCK_11 из принятой рамки должен передать полный ручной CRUD и матрицу его поведения. Если проверка не проходит, зафиксировать конкретный дефект и восстановить вход блока 11 до автоматизации; здесь не переписывать отсутствующий CRUD.

**Снимок проекта:** материалы главы 3 в `backend/content/materials/chapter_03/block_12/` показывают существующие файлы обоих поколений уроков. ### B: наблюдаемый результат

К концу блока ученик самостоятельно:

1. Создаёт HTTP-проверки настоящего FastAPI app через TestClient и отдельный тестовый JSON; понимает, что клиент не запускает TCP-сервер, но вызывает настоящий ASGI app.
2. Проверяет ответы и изменения состояния по договору CRUD, включая `201`, `204` без body, `404`, `422` без частичного эффекта, прежний id при PUT и применение `false` при PATCH.

4. Различает HTTP-тест поведения маршрута, unit-тест прикладного правила и связанный сценарий нескольких операций; сохраняет границы `route → service → JsonStorage` и прежнего CLI.
5. Повторяет установку и проверки по README в чистом окружении, не открывая рабочий JSON тестам и не публикуя личные данные; обозначает версию проверенного кода и фактический объём передачи.

Проверка B — демонстрация в существующем Planner: изолированный набор тестов, прежняя ручная коллекция/API и CLI на том же рабочем JSON, чистая установка и пройденная инструкция. Успех тестов не выдаётся за доказательство production readiness, транзакционности JSON или фактически освоенного навыка до выполнения учеником.

### Границы продукта

Сохраняются тот же проект и все восемь endpoint, общий PlannerService/JsonStorage/JSON и прежний CLI; поля задачи, схемы, фильтрация, порядок `filter → sort по id → limit`, ограничения входа, коды ответов и правила ошибок остаются из COURSE. Тестовый JSON отделён от рабочего; fixture существует на тест/сценарий, а не пересоздаётся на каждый HTTP-запрос. Не вводить SQLite/SQLAlchemy, auth, пользователей, async, dependency injection, middleware, Docker, CI/CD, облачный deploy, нагрузочные тесты, второй CRUD, второй service или новое состояние приложения. Упоминание APIRouter ограничено организацией уже существующих маршрутов.

### Замороженный HTTP-контракт

| Операция | Ответ и гарантия, которую сохраняют тесты |
|---|---|
| `GET /health` | `200`; проверяет ответ приложения, не заменяет доступность настоящего сервера. |
| `GET /tasks` | `200`; `is_done=None`, `sort_desc=False`, `limit=10`; limit 1–50; filter → sort по id → limit, без мутации источника. |
| `GET /tasks/{task_id}` | `200` для существующей записи; `404` для корректного отсутствующего id; неразбираемый path — `422`. |
| `GET /stats` | `200`; `total/open/done` считаются по всему общему JSON, независимо от query списка. |
| `POST /tasks` | `201`; обязательны title/priority; trim и длина title 1–120, priority 1–5; id и `is_done=False` задаёт сервер. |
| `PUT /tasks/{task_id}` | `200`; полная форма title/priority/is_done, id остаётся прежним, отсутствующий id не превращается в создание. |
| `PATCH /tasks/{task_id}` | `200`; меняются только переданные поля; пропуск/null сохраняет поле, явный `false` применяется; пустой PATCH допустим. |
| `DELETE /tasks/{task_id}` | `204` без body; удалён только выбранный объект, повторное чтение отсутствующего id даёт `404`. |

Публичный `TaskRead` содержит ровно `id/title/priority/is_done`; внутреннее `tags` остаётся в прежней модели и JSON, не удаляется при обновлении. Новый id равен `1` для пустого источника, иначе `max(текущих id)+1`; после удаления максимальный id может использоваться снова. Не ужесточать Pydantic extra/type coercion и не менять поведение CLI под видом тестовой чистки. Ответная валидация после сохранения сама по себе не откатывает уже выполненную запись.

## 3. Паспорта занятий

Во всех паспортах формат основной практики — **изменение существующего проекта**. Проверочные тесты должны автозапускаться командой проекта; ручные Postman/CLI-прогоны дополняют HTTP-тесты только там, где это указано. Если одна из обязательных A не подтверждена в конкретной выдаче, применить входную проверку из раздела 1 до выполнения зависимой практики.

### День 1 — первый автоматический запрос

#### 56. Первый HTTP-тест

**1. Тема и роль.** Как проверять FastAPI app повторяемым запросом, не поднимая сервер? Это первая автоматизация ручной приёмки и опора для безопасного изменения проекта.

**2. A и источник/статус.** Планируемая: ручной API-контракт блока 11 и знакомые `pytest`/`assert` из предыдущего маршрута. Источник навыка — исторический `docs/concept/chapter_03/BLOCK_12.md`, где сказано о знакомом pytest, но навык ученика проверить коротким запуском до работы. Реализация TestClient не заявлена знакомой; если нужный CRUD не проходит входной smoke, сначала восстановить A блока 11.

**3. B.** Ученик объясняет разницу между тестовым клиентом ASGI app и внешним HTTP-клиентом, сам создаёт один запрос к существующему `GET /health`, проверяет статус и поле ответа.

**4. Механизмы по порядку.** Вспомнить arrange → действие → assertion на простой функции; объяснить, что FastAPI app является объектом приложения, TestClient вызывает его обработчики без запуска Uvicorn/TCP, а response содержит status и body. Показать минимальный пример одного GET и разобрать неуспешный status assertion. Затем ученик создаёт собственный HTTP-тест. Не включать fixture-изоляцию, mocks и весь CRUD в первое знакомство.

**5. Самостоятельная практика / формат.** В существующем `tests/test_api.py` подключить настоящий app и TestClient; выполнить `GET /health`; самостоятельно проверить status `200` и ожидаемое публичное значение ответа. Не заменить app функцией-заглушкой и не запускать вручную отдельный сервер как обязательную часть этого теста.

**6. Результат / передача.** Команда тестов находит тест, получает настоящий response и проходит две проверки. Ученик может указать, что именно было вызвано без TCP и что всё ещё является настоящим кодом приложения. Результат передаётся 56.1 для изоляции состояния.

**7. Теория.** **1400–1700 слов**: первое знакомство с TestClient и границей ASGI требует объяснить, что он заменяет и чего не подменяет, но один endpoint и знакомый assert ограничивают число новых механизмов.

#### 56.1. Изоляция данных HTTP-теста

**1. Тема и роль.** Как запустить тест повторно, не читая и не повреждая рабочий `data/tasks.json`? Урок делает безопасным расширение HTTP-проверок.

**2. A и источник/статус.** Планируемая B занятия 56: ученик вызывает приложение через TestClient и проверяет response. `tmp_path` и подготовка тестовых данных указаны историческим блоком среди привычных pytest-приёмов, но перед использованием проверить, что ученик умеет читать временный путь; если нет — дать короткое объяснение и безопасную пробу здесь. Фактический путь пользовательского JSON на учебном проекте пока проверяется.

**3. B.** Ученик объясняет разницу рабочего и тестового источника; сам задаёт отдельный путь JsonStorage/сервису для теста, запускает два независимых теста и показывает, что рабочий файл и состояние второго теста не зависят от первого.

**4. Механизмы по порядку.** Сначала показать, как увидеть, какой JSON открыл сервис; объяснить временную директорию `tmp_path`, fixture setup/teardown и срок жизни function-scoped fixture. Затем безопасно проверить один тестовый путь, перезапустить тест и убедиться в исходной чистоте. Только после этого ученик связывает fixture сервиса и TestClient. Клиент закрывается до очистки пути; новые данные не создаются на каждый request внутри одного сценария.

**5. Самостоятельная практика / формат.** В том же проекте собрать fixture тестового JsonStorage/PlannerService из существующего `build_service` и подключить его к app тем способом, который принят в коде; сохранить/восстановить выбранный `app.state.planner`. Написать два теста с разным исходным набором; один тест делает запись, второй начинает с собственного состояния. После прогона проверить, что рабочий JSON не менялся.

**6. Результат / передача.** Повторный и раздельный запуск дают одинаковое начальное состояние, записи остаются в временных файлах, рабочий JSON прежний; каждый request одного тестового сценария видит накопленные изменения. Эта fixture служит основой для матрицы операций в 57.

**7. Теория.** **1500–1900 слов**: изоляция объединяет временный путь, lifetime fixture, зависимость fixture и состояние app; краткая безопасная проба должна показать и очистку, и отличие нового клиента от нового хранилища.

### День 2 — проверяемое поведение и организация маршрутов

#### 57. Проверки операций API

**1. Тема и роль.** Перевести ограниченную ручную матрицу CRUD в компактные автоматические проверки поведения, не превращая тест в копию приложения.

**2. A и источник/статус.** Планируемая: проверенная изоляция 56.1 и переданный вручную контракт блока 11. Проверить успешные ручные сценарии до выдачи; в частности, серверный id при POST и реальный прежний id при PUT. Формулировки и восемь endpoint — `COURSE.md`, `chapter-03-frame-v1`.

**3. B.** Ученик самостоятельно выбирает данные и проверяет запрос, статус, нужные поля ответа и наблюдаемое изменение через последующее чтение; объясняет, почему одного успешного status недостаточно.

**4. Механизмы по порядку.** Повторить Arrange → Act → Assert на `GET`; объяснить `response.status_code`, `response.json()`, различие полного body и выбранных публичных полей. Поэтапно добавить `POST` (`201`, серверные поля), `GET item`, PUT (полная форма, прежний id), PATCH (только переданные поля, `false`) и DELETE (`204`, body отсутствует). Проверять состояние отдельным чтением там, где response сам не доказывает запись. Не открывать новую тему ошибок и query-границ раньше 58.

**5. Самостоятельная практика / формат.** В изолированных тестах проекта написать по одному различимому сценарию для чтения, создания, полной замены, частичного изменения и удаления. Для изменяющих действий сохранить фактический id из ответа POST; проверить повторным GET/списком нужное состояние. Не использовать один жёсткий id для всех сред и не вычислять ожидаемый id вместо фактического договора.

**6. Результат / передача.** Тесты подтверждают коды ответа и изменённые/сохранённые поля; PUT оставляет id прежним, PATCH применяет `false` и сохраняет непереданные поля, DELETE возвращает пустой 204. Матрица становится защитой для переноса router в 57.1.

**7. Теория.** **1500–1900 слов**: несколько операций имеют разные доказательства (ответ, последующее чтение, отсутствие body), но используют уже подготовленный шаблон теста и данные, поэтому достаточно разобрать контрастные случаи, а не повторять HTTP с нуля.

#### 57.1. Маршруты в APIRouter

**1. Тема и роль.** Как вынести HTTP-обработчики в модуль router, сохранив публичный API? Организационное изменение должно быть проверяемым и не создавать новый продукт.

**2. A и источник/статус.** Планируемая B 57: базовая матрица операций проходит до реорганизации. Наличие прежнего `app/api.py` и текущей структуры маршрутов проверить в checkout; исторический BLOCK и рамка COURSE описывают APIRouter как ещё не изученную тему, а не уже завершённый рефакторинг.

**3. B.** Ученик показывает route module с существующими обработчиками и отдельным `APIRouter`; подключает его к единственному FastAPI app. Проверки подтверждают те же paths, методы, схемы и коды ответов.

**4. Механизмы по порядку.** Разобрать, что `APIRouter` собирает handlers, `prefix` добавляет часть пути, `tags` группируют документацию, `include_router` регистрирует их в приложении. На коротком демонстрационном route проследить итоговый URL и показать, как двойной prefix создаёт другой адрес. Затем безопасно перенести один endpoint и прогнать тест; после этой пробы переносить связанные операции. Не добавлять второй app, новый service, dependency injection или новую архитектурную схему.

**5. Самостоятельная практика / формат.** В существующем проекте вынести согласованный набор `/tasks` обработчиков и HTTP-helper в router-модуль; подключить его в прежнем app. Ученик сам проверяет итоговые route paths и исправляет import/prefix только в пределах переноса.
