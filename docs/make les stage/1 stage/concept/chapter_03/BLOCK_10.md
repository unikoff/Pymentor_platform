## 1. Назначение, A→B и границы

### A — что должно быть на входе

1. **HTTP-модель — планируемая A, не факт освоения.** Принятая строка BLOCK_9 в [COURSE.md](COURSE.md) задаёт самостоятельное объяснение client/server, request/response, method, path, headers, body, status и различий path/query/body. До первого запроса ученик должен разобрать новый запрос и предсказать результат. Если проверка не пройдена, восстановить модель и безопасно разобрать пример прежде, чем открывать Postman. BLOCK_9 пока не подтверждён как пройденный.
2. **Planner из главы 2 — запланированная проектная опора, состояние конкретной копии не проверено.** Источники: COURSE главы 2, BLOCK_8, материалы `backend/content/materials/chapter_02/block_08/`, включая задачу, `PlannerService`, `JsonStorage`, CLI и запуск проекта. Перед интеграцией найти фактический checkout, запустить CLI, прочитать существующие операции и установить реальный путь рабочего JSON. Код, который виден в текущем репозитории, сам по себе не подтверждает прохождение материала учеником или состояние его личного проекта.
3. **Рабочее окружение — не проверено до диагностики.** Проверить проектную `.venv`, импорты CLI, существующий способ сборки сервиса и доступность Postman. Недостающую проектную опору восстановить до API-практики; не заменять старый Planner новым примером.

### B — наблюдаемое приращение

Ученик самостоятельно отправляет и разбирает запросы в Postman, поднимает FastAPI на существующем проекте, подключает маршруты к прежнему `PlannerService`, читает список/статистику/задачу, применяет выборку `filter → sort by id → limit` с HTTP defaults и bounds и создаёт задачу через JSON `POST`. Сравнивает результат API с CLI и проверяет тот же JSON после перезапуска. Ожидаемое состояние кода, а не уже существующий факт.

### Границы продукта

- Один Planner и один `PlannerService`, один `JsonStorage`, один рабочий JSON и прежний CLI. API вызывает те же предметные операции; он не читает и не пишет JSON напрямую.
- Запланированные маршруты этого блока: `GET /health`, `GET /tasks`, `GET /tasks/{task_id}`, `GET /stats`, `POST /tasks`. Контракт списка: `is_done=None`, `sort_desc=False`, `limit=10`; допустимый `limit` — 1–50; порядок — filter → sort by id → limit. API-default не меняет полный список прежнего CLI.
- Публичное представление задачи: `id`, `title`, `priority`, `is_done`; внутренние `tags` сохраняются. Статистика относится ко всему хранилищу, не к отфильтрованной странице.
- `POST` использует существующее создание и сохраняет через тот же storage. Этот блок не берёт на себя нормализацию/ограничения входа, схемы ответов, PUT/PATCH/DELETE, автоматические тесты или перестройку слоёв — это дальнейшие договоры COURSE.
- Не вводить второй список задач, фиктивный storage, отдельный Planner, ручную сериализацию, DB, async, auth, offset/cursor или произвольную сортировку.

### Межблочные условия

- **Вход BLOCK_9 → BLOCK_10 (предложение до F-проверки):** ученик объясняет состав нового HTTP-запроса и может предсказать, какие данные находятся в path, query и body. Поставщик — планируемая B блока 9; проверка перед первым запросом — разобрать незнакомый пример. При провале повторить модельный обмен, не считать запланированный урок доказательством.
- **Выход BLOCK_10 → BLOCK_11 (предложение до F-проверки):** ручные GET/POST работают через один сервис и JSON; ученик сравнил их с CLI, сохранил рабочие Postman-запросы и объясняет путь `route → service → storage`. Поставщик — планируемая B этого блока; BLOCK_11 проверяет smoke-сценарий и состояние данных перед изменением схем.

## 4. Полные паспорта

### 46. Первый запрос в Postman — основное занятие дня 1

1. **Тема и роль.** Увидеть HTTP как сообщение, которое клиент отправляет серверу; освоить Postman на Echo прежде, чем тестировать Planner. Подготавливает проверяемое чтение ответа.
2. **A и источник/статус.** BLOCK_9 HTTP-модель — планируется; поставщик и условие входной проверки указаны выше. Если ученик не различает method, URL, query и response, модель объясняется и пробуется на бумажном/текстовом примере до Postman. Код проекта для этой пробы не нужен.
3. **Наблюдаемая B.** Ученик объясняет роли Postman и Echo, самостоятельно настраивает Echo environment и отправляет GET; называет method, адрес и query и показывает их в ответе. Прямо говорит, что Echo не читает Planner.
4. **Механизмы по порядку.** Клиент/сервер и request/response из входной A → Postman как ручной клиент → environment/base URL → GET и URL/query → status/body ответа → Echo отражает входные данные. До кнопки Send — безопасно предсказать запрос и ответ. Отложены собственный сервер, JSON-body и изменение задачи.

5. **Самостоятельная практика и формат.** В существующем API добавить POST, не писать append/id/save вручную. Отправить корректный POST, взять фактический id из ответа и сверить GET item, полный список/выборку, stats и CLI; повторить чтение после рестарта. Отправить пропущенное поле/неверный тип и допустимо сформированный, но недействительный по правилам Task payload; обе ошибки не должны добавить задачу. Сбой записи отдельно не симулировать и атомарный откат не обещать. Повтор POST — отдельное создание.
6. **Результат/передача.** Новый объект виден в том же JSON через API и CLI после перезапуска; response имеет 201, id server-side, `is_done=False`, без публичного `tags`. Отказы не добавляют запись. Следующему блоку передаётся ручной GET/POST smoke и доказательство общего service/storage; перед новыми изменениями следующий блок проверит его ещё раз.
7. **Диапазон видимой теории: 1300–1800 слов.** Это интеграционный шаг с побочным эффектом: нужно заранее объяснить точку сохранения и три разных класса исхода. Ранее подготовленные схема и GET уменьшают повтор, но не заменяют безопасный разбор состояния до/после.

## 5. Локальная приёмка, статус и handoff

### Проверка A→B и полноты

- **N_expected = 10**: пять основных занятий и пять обязательных подзанятий; **N_accepted = 10/10** по наличию полной карты и семи смысловых полей, включая диапазон/причину для каждого.
- Последовательность: HTTP-модель (условная входная проверка) → клиентский запрос/JSON → запуск сервера → чтение через прежний service → item → выборка в service → query-границы → схема body → создание через тот же service. Перед каждым новым механизмом указаны первое объяснение и безопасная проба; самостоятельное изменение данных стоит после чтения и проверки схемы.
- Все части B покрыты действиями с критериями: Postman/Echo; запуск/health/Swagger; GET list/stats/item; filter/sort/limit/query; Pydantic-вход; POST, отказ без мутации, CLI/JSON после рестарта.
- Первая проверка перед фактическим проведением: HTTP A BLOCK_9; затем диагностика CLI/service/storage/path JSON и окружения. Личное освоение не подтверждается этим концептом. Если вход не соответствует, восстановить необходимую операцию до её первого использования.
- Основные практики — UI Postman, редактор/интерпретатор и изменение существующего проекта. Документация и объяснение не подменяют обязательную проектную практику.
- **Сложный переход новичка:** «знает request/response после блока 9 → получает безопасную пробу Echo → создаёт собственный health → рассматривает swagger → подключает прежний service только на чтение → добавляет item/выборку → изучает входную схему → выполняет мутацию через прежнее создание». Критическая проверка общего JSON/CLI идёт до и после POST; поэтому endpoint не становится первым местом знакомства сразу с FastAPI и storage.

### Содержательные решения при переработке

- Сохранены как центральные операции: Postman/Echo, FastAPI/Uvicorn, Swagger, общий Planner, GET/list/stats/item, фильтрация/сортировка/limit, Pydantic body и POST.
- Разнесены ранее сцепленные скачки: безопасное освоение Postman отделено от FastAPI; health отделён от Planner; list/stats отделены от item; логика выборки — от HTTP query; модель входа — от POST.
- Усилен контроль инварианта: один service/storage/JSON, сверка API с CLI после перезапуска, отдельные причины 404/422, отказ до мутации и отсутствие публичных tags.
- Старые материалы `51` и `56` не теряются физически и не переназначаются чужим ID; их содержание перенесено в новые целевые паспорта. Фактическое выключение лишних runtime-страниц/ссылок — будущая работа владельца каталога после общего F; в Stage 1 не производится.

### Итоговый договор следующему блоку

BLOCK_11 получает ожидаемую, но ещё не подтверждённую здесь фактически, рабочую связку GET/POST поверх прежнего Planner, Postman smoke, сохранённый общий JSON и сравнение с CLI.
