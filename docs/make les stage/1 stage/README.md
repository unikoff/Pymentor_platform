## Quickstart координатора в текущем чате

1. Указать точные `{курс}`, `{глава}`, `{создать/переработать/продолжить}`, **четыре глобальных номера блоков в порядке курса**, целевую B главы и основание её проектирования, аудиторию и входную A, ограничения, проверяемые источники, существующие MD/ID и разрешённые пути. Сверить, какой `docs/concept/chapter_<глава>/` действительно канонический: похожие имена `chapter_01` и `chapter_01new` не взаимозаменяемы.
2. Явно выбрать `$pymentor-stage1-beta` и загрузить его **текст**, оба TOML, локальные README/AGENTS/RUN_TEMPLATE, затем методички C/B/F перед соответствующим проходом. Вести запуск в исходном чате координатора; не создавать отдельный чат для самого оркестратора. Сверить эффективную политику текущей задачи, фактические инструменты, разрешённый пул/effort и admission; явно заданное пользователем предпочтение Web соблюдать при доступном маршруте. Не закреплять в Stage 1 отдельную модель, reasoning или лимит параллельности. Создать **один** `docs/stage-runs/<run-id>/RUN.md` с пятью каноническими MD и владельцами; при продолжении использовать существующий RUN и сверять активные задания.
3. В одном задании выполни C1–C4, зафиксируй принятую рамку COURSE и FRAME_VERSION, затем B1–B4 для каждого из четырёх BLOCK. Сохраняй одного активного писателя на файл; четыре блока не требуют четырёх чатов.
4. После 4/4 в том же задании выполни F1–F3: сверь все паспорта, переходы, покрытие B, три стыка и два края; собери существенные замечания, исправь пакетом и проверь затронутое. STAGE_COMPLETE только при обязательных PASS. Stage 2/3 запускаются отдельно по мандату.

**Идентичность при переработке:** отображаемые `display_number`, `title`, название блока и место урока в программе — **изменяемые атрибуты**, а не устойчивый идентификатор. Для сопоставления бери существующий `lesson_id` и канонический identity source **из авторитетной реализации**; отдельно фиксируй отображаемые номер/название, учебный порядок и физический путь. В `backend/content/catalog.py` `lesson_id` создаётся из относительного source path: `backend/content/identity.py` применяет `_lesson_identity_source()` (включая алиасы) и хеширует результат в `_stable_lesson_id()`. ID независим от **позиции**, но **зависит от канонического пути**; не конструируй ID из текущего display_number. Например, прежний «03» может стать «03.1–03.3», а последующие номера сдвинуться: сохрани ID и пути **существующих** уроков, оформи таблицу соответствия старых/новых отображаемых реквизитов. Для **нового запланированного занятия без runtime `lesson_id`** в паспорте допустима буквальная запись **«ID требует назначения по действующей схеме»** с владельцем реализации и следующим этапом проверки/создания mapping при включении урока в каталог; это **штатная будущая зависимость, не блокер Stage 1 и не BETA_GAP**. Чистое переименование исправляет отображение и ссылки согласно этой карте; вставка, удаление или перестановка **заново проверяет** последовательность, prerequisite и все A→B, рост сложности, N-опись, COURSE↔BLOCK и три межблочных стыка. Обычные физические пути сохранять: их перенос/переименование может сменить хеш и `lesson_id`. Если перенос нужен, **отдельно уполномоченный владелец реализации** должен добавить/проверить alias/identity mapping и миграцию прогресса. Stage 1 лишь фиксирует эту зависимость и не меняет физические файлы, routes, progress ID, таблицы алиасов или миграции. `BETA_GAP: LESSON_IDENTITY_UNVERIFIED` применяй **только к уже существующему/реализованному уроку**, для которого `lesson_id` ожидается, но его canonical identity source/alias нельзя подтвердить; указать минимальный недостающий mapping, не придумывать ID и не менять схему приложения.

Стартовый запрос для текущего чата координатора: `$pymentor-stage1-beta. Выполни только Stage 1: курс {…}, глава {…}, режим {…}, глобальные блоки {№1, №2, №3, №4}, канонические COURSE/BLOCK пути {…}, B и мандат {…}, входная A/источники {…}, границы записи {пять MD и RUN}. Не создавай отдельный чат координатора, PLAN/уроки/TSX и не запускай Stage 2/3.`

## Автономность координатора и распределение работы

- Корневой координатор остаётся в чате, где запущен Stage 1. Он выбирает канонические входы по источникам, ведёт единственный RUN, принимает рамку перед стартом B и подтверждает итоговый gate; не дублирует каждый проход исполнителя и не перепроверяет активные чаты по таймеру.
- Полный Stage 1 можно выполнить одним исполнителем в одном чате. При действительно необходимом делегировании назначай области записи без конкурирующих писателей; не дроби подэтапы на сообщения.
- Исполнители решают обычные пробелы по COURSE, RUN и исходным материалам без вопросов пользователю. Фиксируй кратко только допущение, которое меняет смысл или стык. Если источник не разрешает существенный конфликт, координатор ставит `DECISION_REQUIRED` только затронутым строкам/файлам, предлагает безопасный вариант и продолжает независимые назначения. Пользовательский вопрос допустим только для решения цели/границ, которое нельзя восстановить или безопасно выбрать по источникам.
- Используй завершение/событие для получения результатов; не требуй регулярных отчётов, не держи отдельного наблюдателя и не запускай автоматический второй review. Дополнительный специалист нужен при конкретном противоречии, пропущенном критерии или высоком риске, а не по умолчанию.
- Модель, effort, доступное число исполнителей и admission определяются центральной политикой и текущим запросом. Этот комплект не задаёт свой пул или локальный потолок. Выполняй явное предпочтение маршрута из текущего запроса, если он разрешён и доступен; фактические ID/модель фиксируй только после подтверждения инструментом. Не обещай бесплатность или неограниченный параллелизм.

**Один Stage 1 RUN = одна глава, один `COURSE.md` и ровно четыре `BLOCK_N.md`.** Если запрос охватывает несколько глав, корневой координатор ведёт отдельный RUN на каждую главу с собственным COURSE, четырьмя блоками, N-описью и gate; независимые главы могут идти параллельно в пределах effective policy. Не смешивать файлы/статусы глав в одном RUN и не останавливать независимую главу из-за локального blocker другой. Это проектная методическая стадия: составление маршрута и паспортов, **без** подробных планов занятий, кода, запуска уроков и доказательства фактического освоения. Концепция главы сохраняет связь с курсом/крупной частью курса: одна глава не заменяет общую цель курса.

## Вход, источники, файлы и опись

Вход: `{курс, глава, создать/переработать, четыре точных номера блоков в порядке курса, согласованные A/B главы и ограничения, источники, существующие концепты, разрешённая запись, журнал продолжения}`. Сначала выявить канонические пути: существующая [директория концептов](../../concept/) содержит `chapter_01`, `chapter_01new`, `chapter_02` и др., но одноимённые главы **не взаимозаменяемы без основания**. В обычном случае результаты — один `docs/concept/chapter_<глава>/COURSE.md` и четыре `BLOCK_<глобальный номер>.md` той же главы; номера файлов берутся из утверждённой карты, не обязательно 1–4. Не создавать альтернативные копии, не редактировать реальные концепты при простом изменении этих инструкций.

Исходное подтверждённое знание ученика, действительное состояние проекта, существование опубликованного урока, намерение концепта и исторический план — **разные виды свидетельства**. Статус каждой существенной A: **подтверждена** (доказательство), **планируется** (точный предшествующий B + место подготовки + условие будущей проверки), **не проверена** (какое свидетельство получить), **не подготовлена** (исправление до первого обязательного действия или незакрытая приёмка). Планируемая B предшественника не подтверждает фактическое освоение навыка.

**Совместимость словаря A между источниками и Stage 2 P1.** Исходные «освоено/подтверждено» соответствуют **подтверждена** только при свидетельстве самостоятельного применения; «объяснялось/упоминалось» само по себе **не** равно подтверждению. «Только запланировано» может стать **планируется** лишь при названной предыдущей B, точном месте объяснения **и самостоятельного применения** и условии проверки до обязательного использования. При отсутствии такого поставщика требуемая опора **не подготовлена**. «Неизвестно/не проверено» остаётся **не проверена**, пока не получено свидетельство. В COURSE/BLOCK и [P1 Stage 2](../2%20stage/01_PLAN_FRAME.md) сохраняй исходные формулировки и передавай **смысл, источник и условие проверки**, не переименовывай механически исторические строки и не добавляй enum/поле приложения.

До делегации внеси **пять целевых MD**, известное соответствие `lesson_id ↔ canonical identity source / alias ↔ прежний и текущий display_number / title ↔ порядок ↔ физический путь` и текущую паспортную опись в **один журнал главы** `docs/stage-runs/<run-id>/RUN.md` по [шаблону](RUN_TEMPLATE.md). После разработки карт уточни полную N-опись: **ровно пять основных учебных дней на блок** (всего **20 основных**) плюс **все обязательные подзанятия**. Каждое обязательное занятие имеет отдельный паспорт. Номера — строки, сортировка `(день, подномер)`, не float; сохрани публичные ID, старые номера и совместимость. N не уменьшать из-за отсутствия файла или незакрытого паспорта.

Исторические отчёты COURSE, BLOCK и upstream-приёмки объясняют прежнее редактирование методичек, но не заменяют фактические доказательства A.

## Порядок работы, границы и зависимые переходы

1. **C1–C4 / один владелец COURSE.** Определить роль главы в целом курсе, A со статусами и источниками, проверяемые понимание/самостоятельное действие/результат B, сквозной накопительный проект или другой результат, **четыре** роли блоков и их входы/выходы. Проверить покрытие B, допустимость предпосылок, нагрузку и версии. Только после `FRAME_ACCEPTED` передать всем блокам одну принятую версию `COURSE.md`.
2. **B1–B4 ×4.** В том же чате по принятой рамке последовательно составь каждый BLOCK с пятью днями, обязательными подзанятиями и семью полями паспорта; локально проверь зависимости. Проектная B соседа остаётся планируемой опорой, не доказанным освоением.
3. **F1–F3 / единая приёмка.** После наличия всех **четырёх** `BLOCK_LOCAL_READY` нормализовать содержание, проверить покрытие B главы, переходы каждого занятия и **три внутренних стыка блоков**, внешнюю A первого и B четвёртого, постепенность нагрузки/сложности, отсутствие внезапной необходимости неизвестной технологии, сохранность ID и полноту описи. Исправления адресуются **единственному владельцу** затронутого MD, после правок повторно проверить соответствующие переходы и версии. Нельзя циклически требовать взаимную финальную приёмку соседних черновиков до локального B4.
4. **Итог.** `STAGE_COMPLETE` только при принятом COURSE, **4/4** блоках, `N_accepted=N_expected` обязательных паспортах, всех обязательных документальных F1–F3 PASS, актуальных хешах и отсутствии препятствующих `FAIL/BLOCKED/NOT_CHECKED`. Иначе `STAGE_INCOMPLETE` с точным остатком. Проектная приёмка допускает будущую A при корректно названных условиях последующей проверки, но **не** означает runtime PASS урока или подтверждённую успеваемость ученика.

**Семь полей паспорта:** тема и назначение, A с источником, проверяемая B, порядок механизмов, самостоятельная практика, выход и переход, необходимая глубина теории с предметной причиной. Числовой диапазон необязателен; новое объясняется до обязательного применения. Паспорт не подменяет подробный PLAN и готовый материал.

## Роли, допуск, владение, восстановление

Координатор может сам выполнить всю главу в исходном чате: рамка C → четыре блока B → общая приёмка F. Подэтапы не требуют отдельных назначений или передач. При действительно обоснованном делегировании действует один активный писатель на файл; не создавать наблюдателей и циклы status ping.

Модель, reasoning effort и число параллельных исполнителей задаются эффективной политикой и временными ограничениями текущей задачи, а не этим Stage 1 комплектом. Если пользователь явно предпочёл Web-чаты, соблюдай это в пределах доступного пула. В профилях Stage 1 `model` и `model_reasoning_effort` намеренно не заданы: Codex разрешает их от явных параметров spawn, затем `[agents]` defaults, затем настроек родительского агента ([официальное описание custom agents](https://learn.chatgpt.com/docs/agent-configuration/subagents)). Если Web-маршрут после одной точечной диагностики не имеет доступа к назначенным файлам, используй Luna для этих заданий только если текущая политика/пул это разрешают и workspace доступен; иначе пометь только их как `BLOCKED` и продолжай независимые главы/файлы без вопроса пользователю. Перед dispatch проверь фактический маршрут, права и admission. Число слотов/очередь бери только из runtime или доверенного hook; не закрепляй лимит, не объявляй бесплатность и не обещай неограниченную параллельность.

**Два маршрута делегирования (проверить живую схему и результат):**

1. **Web-чат исполнителя (основной при явном предпочтении пользователя)** — `create_thread(model, thinking, prompt, target)` с разрешёнными effective policy моделью/effort и **переданным текстом** Skill/AGENTS/применимого TOML `developer_instructions`/методички/brief. У `create_thread` **нет** `agent_type`; роль исполняется по переданному тексту, если runtime не подтвердил иное. Создавай только назначенные рабочие чаты внутри авторизованной оркестрации. Зафиксируй фактический ID/модель/effort; не утверждай регистрацию TOML через `create_thread`.
2. **Native multi-agent** — `multi_agent_v1.spawn_agent(agent_type, model?, reasoning_effort?)`: если Web-предпочтение отсутствует либо этот маршрут выбран эффективной политикой и доступен, передать нужный `agent_type`. Явно передавать модель/effort только для требуемого per-run override; иначе оставить их унаследованными из эффективных defaults/родительского агента. Прочитанный TOML **не** является доказательством регистрации или выбора модели. Проверить фактический ответ, worker ID, конфигурацию и границы записи.

Если native-роль не зарегистрирована, передай **полный текст инструкций профиля** исполнителю через доступный Web-маршрут, обозначив это как *роль по переданным инструкциям*. Если доступный пул/effort или маршрут не подтверждён, не симулируй dispatch: отметь реальное ограничение для зависимых назначений и продолжи независимые части. Стоимость/бесплатность Web и успех полного пилота не предполагаются.

Один физический файл имеет одного одновременного писателя; один исполнитель может последовательно вести COURSE и четыре BLOCK. Исправления объединяй в один пакет и проверяй затронутые зависимости.

После прерывания **сначала** прочитай прежний RUN, действующие MD/diff и состояние уже выданных задач. Не создавать дубликат работающего исполнителя, начинать с первого подтверждённо незавершённого прохода. Изменённая рамка отменяет только зависимые подтверждения. Блокер зависимого блока не прекращает независимую работу других блоков, но препятствует `STAGE_COMPLETE`.
