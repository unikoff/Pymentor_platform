## N-опись обязательных паспортов

После B2 перечислить **все** обязательные занятия и подзанятия, в том числе ещё не готовые: **5 основных дней × 4 = 20 основных + обязательные подзанятия**. `N_expected` не снижать из-за отсутствующего паспорта. Отображаемый номер хранить **строкой** (`6`, `6.1`, `6.10`), сортировать по установленному учебному порядку `(день, подномер)`, **не** вычислять из него стабильный ключ/публичный ID/физический путь. В действующем backend ID формируется из хеша canonical source path после `_lesson_identity_source()` и алиасов: независимость от позиции **не означает независимости от пути**. Для **существующего реализованного** занятия фиксировать `lesson_id` из реализации, canonical identity source/alias, текущие display-number/title, порядок и путь. Для **нового запланированного** занятия допускается `ID требует назначения по действующей схеме`, указать владельца реализации и этап проверки/создания mapping при реализации; отсутствие runtime ID само по себе **не Stage 1 blocker и не BETA_GAP**.

ID/схему не изобретать.
- Подтверждённая A — доказанное **самостоятельное** действие; планируемая A — предыдущая B, место объяснения, собственной пробы и будущая проверка; `не проверена` / `не подготовлена` остаются явно обозначенными. Состояние проекта и обученность ученика не смешивать.
- Семь полей: тема/назначение; A/источник; наблюдаемая B; порядок механизмов; собственная практика с обязательным форматом; выход/критерий/переход; диапазон **видимой** теории с предметной причиной. Новый паспорт без поля 7 — FAIL; только доказанный legacy допускает явный резерв P1/P4 без выдачи его за исходный диапазон.
