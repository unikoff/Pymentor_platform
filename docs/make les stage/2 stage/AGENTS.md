# AGENTS.md — stage 2 / PLAN

**Один агент = одно занятие = полный stage (P1–P4 или M1–M5).** Одному исполнителю запрещено назначать 2–3 занятия, диапазон для исполнения или личную очередь. Общая очередь массива принадлежит только Coordinator. Для каждого следующего занятия запускается отдельный агент; после результата или блокера текущий агент останавливается. Исправления/RESUME того же занятия можно вернуть его исполнителю. Опись массива принадлежит Coordinator; каждый исполнитель работает только над одним назначенным занятием и завершает его целиком. Это правило заменяет прежнюю схему постоянных очередей на агента.

Применяй эти правила при явно порученном выполнении stage 2. При редактировании документации не запускай создание планов автоматически. Общие правила: [BATCH_WORKFLOW.md](../BATCH_WORKFLOW.md), [AGENTS родительской папки](../AGENTS.md).

При явно порученном массовом запуске применим [Skill pymentor-stage-batch](../../../.agents/skills/pymentor-stage-batch/SKILL.md) и профиль [pymentor_plan_worker](../../../.codex/agents/pymentor-plan-worker.toml), если текущая effective task policy допускает эту роль. Они не задают постоянную личную очередь; чтение TOML само по себе не доказывает регистрацию или запуск. **Действующую модель, бюджет, режим, слоты и полномочия** получай из effective task policy исходного оркестратора; не копируй временные значения в методики и не меняй конфигурацию через stage 2.

**Единственный оркестратор — исходный чат пользователя.** Web-исполнитель работает в назначенном scope, не создаёт другого оркестратора, чаты или рекурсивные делегации. Желаемая модель в текстовом файле не подтверждает фактический runtime. Если Skill не обнаружен автоматически, считай действительными только инструкции, реально прочитанные доступным инструментом.

- Исходный чат — Coordinator: сохраняет опись N и назначает по одному занятию. Исполнитель получает один MD и проходит весь P1–P4, затем останавливается; следующее занятие получает отдельное назначение. Не создавай постоянные контексты, личные очереди или отдельного агента для интеграции без явного назначения. Coordinator принимает компактные результаты и проверяет N/N, не повторяя P4 без конкретного дефекта.
- Модель, режим, лимиты и способ исполнения определяются effective task policy и общим протоколом. Исполнитель не расширяет scope и не создаёт постоянный pool или параллельные назначения.
- Coordinator сохраняет полный массив, действующие паспорта, A/B, формат практики, диапазон теории и разрешённые MD; отсутствующие подзанятия остаются в N. Исполнитель получает одно назначение, без личной очереди.
- Один исполнитель последовательно доводит один MD через [P1](01_PLAN_FRAME.md), [P2](02_THEORY_ROUTE.md), [P3](03_PRACTICE_ROUTE.md), [P4](04_PLAN_ACCEPTANCE.md). Не дели одновременную запись одного плана между P-проходами.
- **До записи выбери CREATE, REWORK или RESUME** по состоянию реального целевого файла. При REWORK диагностируй наблюдаемые пробелы A → B, порядок предпосылок и доказательность самостоятельной практики; составь короткий план адресных улучшений. Не превращай P1–P4 в четыре одинаковые повторные проверки. Если доказанных дефектов нет, сохрани хорошие разделы (`KEEP`), не подменяй содержательную работу квотой изменений.
- **Результаты проходов различны:** P1 — корректная рамка цели и крупных действий; P2 — проверяемая последовательность объяснений, независимых примеров и первых применений; P3 — самостоятельные действия с локальными критериями, реальным ростом самостоятельности и различающими случаями; P4 — итоговый учебный путь плюс сравнение дефектов и улучшений при переработке. У P4 должно быть содержательное доказательство результата, а не только отметки чек-листов.
- В планировании подачи для MAIN сохраняй ограничение **не более двух подряд читаемых абзацев** без содержательного интерактива **или** учебного визуала. Проверяй также **соседство самих вставок**: `TrueFalse → Note → TrueFalse` с почти одинаковыми вопросами не исправляется заменой названий компонентов. Выбирай предсказание, трассировку, объяснение, исправление или визуал по реальной учебной функции; не навязывай механическое чередование и не вставляй украшения ради ритма.
- Разрешены назначенные MD-планы. Паспорта/концепты, TSX, практика, shared/CSS и StudyHub не меняются по одному факту запуска PLAN. При противоречии сохраняй независимую часть и точную зависимость, не меняй B самовольно.
- Сохраняй строковый номер, ID, исходное имя, YouTube-комментарий побайтно и на прежнем месте. Не создавай копии плана по проходам.
- A имеет явный статус; планируемая A прослеживается к предыдущему B/месту подготовки и не объявляется освоенной. Новый паспорт без диапазона не получает унаследованный fallback по одному отсутствию числа.
- Ответственный Web сам проверяет **сохранённый** MD по P4: концепт/проект, объяснения до действий, самостоятельность, критерии практики, соседние переходы, ясность и отсутствие заглушек. При REWORK показывает компактно `было → дефект → стало → наблюдаемый учебный результат` **по существенным исправлениям**, при CREATE — покрытие B, при KEEP — проверенное основание сохранить исходное. Его итоговый статус, пути и обязательные проверки достаточны для штатной приёмки исходным оркестратором. Дополнительная предметная проверка нужна при противоречии, сбое, недостающем свидетельстве или запросе пользователя. Runtime ещё не созданного занятия не требуется.
- Web автономно устраняет исправимые замечания внутри текущего запуска. Один компактный журнал ведёт назначенный владелец; не требуй SHA и отдельных отчётов на каждом проходе. Исполнитель возвращает компактную сводку по назначенному занятию или блокеру; обязательные evidence не ограничены квотой слов; исходный оркестратор сверяет поля и N/N. STAGE_COMPLETE только при PLAN_ACCEPTED всех N из N; локальные P1–P3 не считаются финальной приёмкой.
- Заверши stage 2 и передай список принятых планов для отдельного stage 3. Не запускай stage 3 автоматически.

Перед началом прочитай [README](README.md), AGENTS и применимые role/skill для текущего назначения. Нужные P-методики и первичные источники изучи до первой зависящей от них правки; не перечитывай неизменённые источники на каждом P. При REWORK сначала фиксируй конкретный дефект, затем сразу правь затронутый текст/маршрут; P4 сохраняет полный итоговый acceptance. Runtime проверяй при входе и повторно только после изменения среды или ошибки.
