# P3. Подробный маршрут самостоятельной практики

**Назначение.** Третий проход создания внутреннего плана занятия Pymentor. Преврати рамку A → B и разработанную в P2 теорию в **подробный маршрут действий самого ученика**: что ему дано, с чем он работает, что пишет/меняет/объясняет самостоятельно, что проверяет после каждого шага и как все шаги доказывают B. Запиши результат в **тот же назначенный Markdown-план**, обычно в `backend/content/materials/`. Готовые задания, TSX, код решения, подсказки, скрытые тесты и выдачу создаёт этап MAIN.

**Когда запускать.** После [P1 — рамка](01_PLAN_FRAME.md) и [P2 — теория](02_THEORY_ROUTE.md), если их относящиеся к практике результаты сохранены. Применяй также для адресного ремонта маршрута практики в уже существующем MD, если контроль обнаружил пропущенный шаг, необученную конструкцию, ложную самостоятельность или неопределённый критерий. Принятый ранее план не переписывай полностью: сопоставь его с текущим паспортом и восполни только реально недостающее. Для одного занятия проходы P1 → P2 → P3 → [P4 — приёмка](04_PLAN_ACCEPTANCE.md) последовательны.

**Локальный итог P3:** PRACTICE_DRAFT — плановый маршрут практики детализирован и проверен по критериям ниже. Это полноценный результат этого прохода, **но не статус принятого целиком MD-плана** и тем более не готового урока. Итоговую приёмку выполняет P4. **Планируемая A** допустима для проектирования, если привязана к конкретной предыдущей B и указан способ проверить её до выдачи занятия. Если обязательная A **не проверена или не подготовлена** и без неё нельзя обосновать действие, передай частичный результат с конкретным блокером; не объявляй ни весь маршрут, ни занятие принятым.

**Режимы:** в `CREATE` сконструируй маршрут из критериев B и теории P2; в `REWORK` прочти прежние задания/действия и выяви, какие уже требуют самостоятельного решения, а какие лишь повторяют факт, копируют образец или меняют числа при той же операции; в `RESUME` продолжи только незавершённые действия. Для содержательной правки достаточно компактного следа `старое действие → почему не доказывало B → новая операция ученика → какой результат это проверит`. Для уже хорошего маршрута зафиксируй `KEEP` без косметической замены типа задания.

## 1. Входной контракт и приоритет источников

В начале установи **один** курс, блок, номер занятия **строкой** (например, `13.1` не преобразуется в число), заголовок, назначенный абсолютный или подтверждённый относительно корня репозитория путь целевого `.md`, цель запроса и область разрешённых изменений. Точный путь устанавливается по запросу, действующему паспорту и существующим материалам, а не по догадке. Один запуск работает с одним планом. Если файл уже есть, используй его актуальное содержимое и P1/P2 из текущего назначения; полный первичный просмотр выполняется один раз, повторное чтение нужно только при изменении файла или пробеле в доказательстве.

Проверь ровно необходимые источники:

1. **Паспорт:** полный `docs/concept/<курс>/BLOCK_N.md`, применимый `COURSE.md` и явно заданные там A → B, обязательные/ознакомительные темы, запреты будущих тем, формат практики и диапазон **учитываемой видимой TSX-теории** с источником. Паспорт определяет цель, но не подтверждает фактическое обучение. Сверяй актуальную редакцию.
2. **План P1/P2:** сохранённые «Место в маршруте», «Точка A», «Точка B», «Границы», `00`, разделы объяснения и предварительный последний блок «Что мы будем делать в практике». Подробная теория обязана объяснять нужный механизм **до** первого самостоятельного действия. В P3 разрешено точечно поправить объяснение/опору/порядок **в том же MD**, если обнаружена дыра.
3. **Реальная A:** фактически пройденные занятия, выданная практика и `C:\Project Python\studyhub\STUDYHUB_LEARNINGS.md` в доступной версии маршрута; для проектной задачи — относящиеся к началу данного занятия файлы/контракты [StudyHub](https://github.com/unikoff/studyhub). Код в современном HEAD может опережать ученика. Наличие темы в паспорте, готового кода или старого плана не свидетельствует об освоении.
4. **Связность:** результат B предыдущего занятия, требование следующего занятия и фактическая версия проекта только в объёме, нужном для самостоятельных действий. Подготовленную в ещё не проведённом предыдущем уроке опору называй **планируемой**. Отсутствующий следующий паспорт отметь для P4, не придумывай его.

Для каждого используемого знания различай **четыре статуса**: (а) подтверждено объяснением **и** самостоятельной работой в выданном занятии; (б) планируется в конкретной предыдущей B с указанием места подготовки/применения и будущей проверкой перед выдачей; (в) не проверено — укажи источник доказательства и зависимые действия; (г) не подготовлено — сначала добавь допустимую подготовку в текущую теорию или зафиксируй нужную правку паспорта. Для состояния проекта отдельно укажи проверенный входной снимок либо что состояние планируется/не проверено. Не смешивай образовательную A с наличием кода в репозитории.

При расхождении источников **цель и обязательный формат** бери из действующего паспорта, а **фактически освоенную A и состояние проекта** устанавливай по выданной практике и относящемуся к началу урока снимку. Назови конкретное противоречие, его влияние на действия и требуемое подтверждение; не повышай статус A по одному упоминанию в плане. Если разногласие затрагивает только один шаг, продолжай проектировать независимые шаги, оставив зависимый условным.

**Проверка до записи.** Убедись, что P1/P2 определили B, источник формата практики и последовательность объяснений. Новый паспорт без диапазона теории остаётся пробелом для **полной** приёмки, но можно спроектировать независимую практику; не подставляй резерв. Для явно унаследованного паспорта без восстановимого диапазона допускается только помеченный временный резерв: минимум 1000 слов, для первого знакомства ориентир 1400–2000, со ссылкой на признак наследования. Обоснованный паспортом диапазон ниже 1000 допустим без повторного согласования, включая конкретно подготовленную будущую A. В P3 не вычисляй TSX-объём. Обязательный формат практики переноси **буквально**, включая `script`/`solve`, если задана автопроверка.

Если рамка/теория не готовы, сначала восстанови их в пределах текущего плана, когда это узкая адресная правка, или обозначь конкретно отсутствующий вход и какие действия пока нельзя корректно спроектировать. Не выдавай отсутствие входа за успешный P3; независимые шаги выполни. При непреодолимой неоднозначности личности занятия/файла не создавай второй кандидат.

## 2. Разложи B на доказуемые самостоятельные действия

**Начинай с проверяемой B, а не с перечня тем или количества упражнений.** Выпиши из паспорта, что ученик должен (1) объяснить, (2) сделать собственными действиями, (3) изменить в проекте, если применимо, и (4) продемонстрировать в результате. Разложи на минимально достаточные крупные действия. Каждое должно производить **свой** проверяемый промежуточный результат, а последний собирать результаты в общую B.

Для каждого действия определяй одновременно:

| Поле планового действия | Что записать в MD |
| --- | --- |
| **Вход** | Известные ученику данные, текущее состояние программы/объекта, уже полученные результаты, допустимая техническая заготовка. |
| **Объект** | Конкретный файл/функция/значение/список/фрагмент программы или предмет исследования; что изменяем, а что сохраняем. |
| **Предыдущая опора** | Номер учебного раздела, где **до действия** объяснён механизм и его запись, либо точная прежняя A со статусом и источником; для будущей A — предыдущая B и условие проверки до выдачи. |
| **Самостоятельная работа** | Какая конструкция/решение/объяснение остаётся за учеником; какой фрагмент разрешено дать готовым технически и почему. |
| **Локальный критерий** | Что **после этого шага**, ещё без будущих действий, можно увидеть: состояние, вывод, эффект в проекте, объяснение различающего случая. |

Для входа и объекта укажи, **откуда у ученика появляются** исходные данные, заготовка или состояние проекта: ранее сохранённый результат, явная подготовка в этом уроке либо конкретная предыдущая B. Если их пока нет, обозначь место получения и условие готовности; не выдумывай существующий файл, функцию или выданный шаблон. Для локального критерия укажи доступный ученику способ наблюдения **сразу после действия** (вывод в интерпретаторе, значение, состояние файла, проверка прежнего поведения, объяснение случая). Не делай промежуточный результат зависимым от будущего runner, теста или ещё не написанного шага.

Добавь к пяти полям **место затруднения и границу помощи**, если они существенны: что теория обязана подготовить, что ученик выберет/запишет самостоятельно, где допускается возврат к опоре. Самостоятельность не означает работу без открытой теории, но готовый алгоритм в пояснении нельзя выдавать за самостоятельное решение. Если заготовка уже содержит конструкцию, которую B требует **написать**, замени её на данные/точку входа либо выдели отдельное действие с самостоятельной записью. Сохранённый MD должен быть достаточен автору MAIN, чтобы написать корректное условие и обратную связь **без догадки о смысле действия**.

Пример масштаба записи (только если такая цель предусмотрена паспортом):

> Вход: ученик знает цикл `for` и имеет список отметок с договорёнными значениями; данные берутся из уже подготовленной части урока. Объект: вычисляемое количество подходящих отметок. Опора: раздел 03 объясняет счётчик, изменение состояния за итерацию и отличие элемента от индекса. Самостоятельно: ученик создаёт собственный цикл и обновление счётчика; заготовка даёт только входные данные и точку вывода. Локальный результат: для списка без совпадений счётчик равен нулю, для списка с несколькими совпадениями учитываются все, исходный список не изменяется. Итоговое использование счётчика в следующем действии пока не является критерием этого шага.

Такой план **не содержит готового кода цикла, полного алгоритма, текста задания или набора скрытых тестов**. Упоминание `for` и номеров разделов в примере условно: в реальном MD они должны соответствовать текущему паспорту и теории.

### Прогрессия практики: изменяется способ рассуждения

После пяти полей построй **минимальную посильную лестницу** от первого опыта с механизмом к B. Сравни не количество заданий или их названия, а то, что реально делает ученик и сколько решения оставлено ему. Возможные ступени: `предсказать эффект на понятном примере → объяснить причинную связь или найти ошибку → самостоятельно выбрать и записать конструкцию → соединить части в существующем проекте/задаче → применить к немного изменённым условиям`. Это **набор вариантов, не квота**: не добавляй все ступени ради разнообразия и не навязывай кодовый перенос устному формату. Каждый следующий шаг должен опираться на проверенное предыдущим наблюдение; если скачок слишком велик, добавь один объяснённый промежуточный опыт или уменьши объём решения, оставленного новичку.

**Содержательное разнообразие.** Разные компоненты могут предъявлять одну и ту же простую операцию «угадать True/False». Два задания вида «есть ли `handle_*`?» и «проходит ли команда через `run()`?» почти не проверяют работу со состоянием. При цели «проследить выполнение команды» второй шаг полезнее построить как трассировку `команда → вызов → изменение или отсутствие изменения списка → результат`, а затем попросить предсказать эффект **другого допустимого сценария** и объяснить расхождение. В одном другом уроке повторение True/False может быть оправдано **двумя различающими заблуждениями**; не запрещай тип компонента механически. Предметную точность проверяй по актуальному коду и паспорту; не предполагай, что каждый `handle_*` существует.

**Проверка подмены практики:** если изменить только имена и числа, а тот же ученик с тем же приёмом без выбора получает ответ, это вариант закрепления, но не автоматическое свидетельство новой B. Новая когнитивная операция (объяснить, диагностировать, спроектировать, адаптировать) нужна **там, где её требует B**. Если сложность увеличена, назови, какая ранее подготовленная предпосылка позволяет её пройти. Не считай прямой запуск готового примера доказательством умения написать конструкцию.

## 3. Проверь двунаправленную связь «теория ↔ практика»

Сделай внутреннюю трассировку для каждого обязательного действия:

1. Из действия **назад**: перечисли все используемые понятия и синтаксис, включая стартовую заготовку, скобки, аргументы, служебные значения, правила изменения состояния, окружение редактора/терминала. Для каждого найди точное место **ранее** в том же MD, подтверждённую выданную A или конкретную проектную предыдущую B. Термин, лишь упомянутый в тексте, ещё не подготовлен.
2. Из каждого **нового механизма вперёд**: покажи первое небольшое самостоятельное применение и результат после объяснения. Не допускай ситуации «объяснили цикл, а ученик только меняет текст внутри заранее готового цикла», если B требует цикл **написать**.
3. Для трудного перехода поставь короткую ступень: небольшое изменение/наблюдение → собственная запись конструкции → композиция знакомых шагов; усложняй помощь постепенно. Связный пример в теории должен быть **на другом сюжете**, чтобы не раскрывать маршрут решения итоговой задачи. MAIN напишет этот пример полностью.
4. Для переходов между разделами проверь, что промежуточный результат реально служит входом следующего действия. Исключи циклические зависимости: шаг 1 не должен требовать результат шага 3, а проверка шага 2 — знания, впервые появляющегося в подсказке будущего задания.
5. Для каждого обязательного блока теории найди осмысленное применение/объяснение в маршруте практики либо укажи, что тема ознакомительная и не входит в B. Исключи бессодержательное повторение ранее освоенного и внезапное требование будущей технологии.

При пробеле **исправь внутри того же MD** ближайший раздел теории/порядок шагов/локальную опору и заново проверь затронутые действия. Допускается добавить подготовительное действие, если оно укладывается в цели и не становится новой обязательной темой. Не перекладывай новое знание в подсказку, скрытый тест, эталон или решение этапа MAIN. Служебные мысли о том, почему материал пока не выдаётся, оставляй в плановых метаданных, а не в будущей ученической речи.

## 4. Выбери маршрут по обязательному формату паспорта

**Проект.** Найди действительное состояние части проекта **перед уроком**, её роль и операцию, ради которой новое знание необходимо. Спланируй цепочку **объяснили механизм → ученик изменил конкретную существующую часть → проверил сохранённую возможность**. Назови объект изменения, собственное решение ученика, зависимые места, прежнее поведение, которое сохранится, и отличие нового поведения. Проверка регрессии сопровождает созидательную работу, не заменяет её. Не планируй параллельный искусственный мини-проект, копирующий существующий.

**Интерпретатор или редактор.** Укажи, что ученик **сам записывает или меняет** и какой вывод/состояние должен увидеть; какое объяснение уже позволяет предсказать результат. Если ожидаемый эффект заведомо незнаком, явно спроектируй исследование **до** разбора, а не тест знания, которого ещё нет. Не выдавай просмотр готовой программы за кодовую практику, если B требует написания.

**Устный разбор.** Назови различаемый механизм, последовательность рассуждения и конкретные случаи, между которыми ученик обоснованно выбирает. Критерий — проверяемый вывод **с причиной**, а не согласие с образцом. Устный вопрос может **дополнять**, но не отменять предписанные паспортом кодовые действия.

**Автопроверка.** Если обязательна, укажи предусмотренный паспортом тип `script` или `solve` и наблюдаемый контракт результата (например, stdout, возвращаемое значение, изменение состояния) **только согласно предметной задаче**. Для stdout заранее уточни значимые пробелы, строки, порядок и окончания строк, где они существенны. Для вычислительного результата определи входы и эффект на существенных случаях. Не вставляй в план тестовые тела, ожидаемые готовые решения, форматы хранения `manual.py`/`code_tasks.py` или новое API платформы: их валидность и закрытость проверяются на MAIN. Формат с автопроверкой не заменяй ручным списком.

Смешанный маршрут допустим, если паспорт требует комбинацию. Разделяй **обязательное B** и дополнительный перенос/исследование; добровольный шаг не может быть предварительным условием для перехода дальше.

## 5. Зафиксируй договор данных, состояний и крайних случаев

Определи предметные инварианты, без которых автор задания не сможет проверить B. Для накопленного счётчика — что он считает, когда начинается с нуля и когда меняется; для выбора элемента — что при отсутствии, одном и нескольких совпадениях; для пустого входа — допустимо ли отсутствие действия/вывода; для сортировки — требуется ли порядок, и если порядок не гарантирован, не тестируй его. Конкретные случаи выбирай **по цели урока**, не заставляй новичка обрабатывать ещё не изученные исключения.

Для каждого существенного действия укажи:

- нормальный случай с ожидаемым наблюдаемым эффектом;
- хотя бы один **различающий или граничный** случай, если без него неверный алгоритм выглядел бы верным; перечисли значимые случаи «пусто / отсутствует / несколько» только там, где они влияют на цель;
- границы свободы: если разрешён любой способ вывода/имени/структуры, проверка должна принимать все такие способы; иначе назови фиксированный объект, контракт и причину;
- поведение сохранённой части проекта и независимость критерия текущего шага от будущих шагов;
- по необходимости проверку переноса: небольшой изменённый вход, объяснение причины или применение на ближайшем следующем занятии. Не назначай новую обязательную задачу механически.

Показательный дефект: «найти элемент» без ответа, что делать, когда элементов нет, делает тест и учебный результат произвольными; «показать все совпадения» без проверки двух совпадений допускает алгоритм, останавливающийся на первом. Исправление P3 — определить **договор и случаи**, оставив сами тесты и точные сообщения MAIN. Исключи «магические» требования, не объяснённые до проверки.

## 6. Запиши маршрут в том же MD

В последнем пронумерованном учебном разделе **«Что мы будем делать в практике»** запиши:

1. **Формат и исходную опору:** из паспорта, с конкретным входным состоянием ученика/проекта и обозначением статуса A. Что даётся технически готовым, а что необходимо сделать.
2. **Цель практики:** как её выполнение демонстрирует обещанную B, включая именно требуемую самостоятельность.
3. **Связанный последовательный список «действие → локальный результат»** по крупным шагам; в каждой записи явно должны считываться все пять полей из раздела 2 и номера подготовивших разделов. Для планируемой опоры — точная предыдущая B и условие проверки перед выдачей.
4. **Пояснение после связанного списка:** как действия связаны, где возвращаться к соответствующим объяснениям и как накопленные частные результаты образуют B. Для проекта добавь проверку прежних возможностей; для автопроверки — тип/контракт. Дополнительный перенос обозначь отдельно как необязательный.
5. **Только нужные точечные правки к прежним разделам того же MD:** опоры рядом с первым объяснением, самостоятельное микро-применение, смена порядка, исправление ошибочного статуса A или обоснованной передачи. Не подменяй P2 полной новой редакцией без дефекта.

В `00. Вступление` уже должен находиться маршрут «Точка старта → Новый вопрос → Результат» с пояснением **после** него. Сохраняй этот список, не переноси и не дублируй. В последнем блоке аналогично нужен связанный маршрут действий с пояснением после него. PLAN описывает смысл этих двух групп и их место, MAIN реализует их общим визуальным компонентом `LinkedNotes variant="connected"`. Не добавляй служебную «передачу дальше» как новый учебный раздел. Обычно учебных разделов от `00` до практики примерно 7–10, но учебный маршрут определяет количество, а не квота.

Сохрани уже имеющиеся заголовки, номер строкой, ID, актуальное содержательное и пользовательские правки; YouTube-комментарий вида `<!-- youtube: ... -->` оставь **побайтно неизменным и в исходном положении**. Если комментария не было, не придумывай. Ссылку на действующий концепт поддерживай относительно самого MD, проверяя её фактическое разрешение. Не вставляй заполнители `{...}`, псевдо-задания вместо реальных действий или необязательные отдельные draft-файлы. Служебное краткое состояние можно передавать в существующем разделе плана/сообщении, не вводя поля приложения, обязательную машиночитаемую схему или sidecar.

**Возобновление после прерывания или адресного замечания:** опирайся на сохранённый MD, а не на сообщение о предыдущем статусе. Сверь уже записанные действия по **объекту → самостоятельной операции → локальному результату** с текущей B и источниками; сохрани годные действия и уточни только неполные или конфликтующие. Обновляй существующий последний связанный список и пояснение к нему **на месте**, не создавай вторую группу практики, дубль шага или повторный `00`. После правки перепроверь цепь от изменённого действия до B; если изменился вход или порядок, проверь также зависимые шаги.

## 7. Локальная приёмка, ремонт и передача P4

После сохранения **перечитай именно финальный MD**, затем одним проходом проверь:

1. Для **каждого** обязательного действия есть пять определённых опор, доступный или честно планируемый источник входа, предварительное объяснение **включая синтаксис заготовки**, собственная работа ученика, наблюдаемый доступным способом результат текущего шага, нормальный и необходимый различающий случай; нет опоры на будущую технику.
2. При чтении **от B к шагам** покрыты все обещанные способности и обязательные темы. При чтении **от каждого нового механизма к первому действию** есть постепенный рост самостоятельности. Шаг с изменением текста внутри готового цикла не выдан за самостоятельное написание цикла.
   Для переработанного маршрута сравни старую и новую **собственную операцию ученика**, а также уровень подсказки на первой и последней обязательных ступенях. Покажи один различающий случай, на котором теперь видно освоение обещанной B; если доказательства улучшения нет, не называй переформулирование прогрессией.
3. Промежуточная проверка возможна **до** следующего шага, общий критерий действительно доказывает B; помощь не раскрывает решение. Предписанный формат сохранён, `script`/`solve` не заменён неподходящей практикой; проект имеет конкретное изменение и регрессионную проверку; дополнительные действия явно факультативны.
4. Договор входов/выходов, состояний и существенных случаев однозначен, свобода выбора совместима с проверкой; неизвестное ученику сначала объясняется либо честно помечено входной зависимостью.
5. Изменён только назначенный MD, чужие правки и YouTube-комментарий сохранены; просматривай scoped diff и актуальные файлы. Ссылки на будущий MAIN — из этой директории `../../manual/LESSON_AUTHORING_GUIDE.md`; для реализации в frontend из `docs/make les stage/2 stage/` относительный путь `../../../frontend/`. Фактическую готовность TSX/runner/публичного API в P3 не проверяй и не заявляй.

**При провале** исправь точное место в MD и снова пройди затронутую трассировку (при смене порядка — все зависимые шаги). Не зацикливай P2 ↔ P3; точечная правка теории в P3 — допустимый ремонт. Если для правки нужен **иной A → B, объём/формат или обязательная тема** вопреки действующему паспорту, назови расхождение и предложение изменения паспорта; выполняй вне MD только в уже разрешённой пользователем области, иначе передай владельцу концепта конкретный блокер. Если журнал/репозиторий/сосед недоступны, подготовь независимые действия и зафиксируй **что именно** не проверено, влияющие шаги и способ подтвердить, не выдавая предположение за факт.

**Передача P4:** один путь к сохранённому MD, номер занятия и источник паспорта; отметка «P3 локально готов» либо «частично: действие N / недостающая A / нужный источник»; существенные исправления соседних разделов этого же MD; какая A подтверждена, какая планируется и должна быть подтверждена перед выдачей, какие проверки выполнены/недоступны. Источник истины — **актуальный файл и источники**, не прежняя переписка и не ярлык статуса.

P3 прекращает работу после проверенного подробного маршрута, даже если полный план ещё ждёт P4. P4 проверит соответствие паспорту, соседям, шаблону и всему маршруту; MAIN подготовит TSX, точные задания, подсказки, эталоны и тесты. [Авторская методичка](../../manual/LESSON_AUTHORING_GUIDE.md) применяется после окончательной приёмки плана.
