# Stage 2 — план заданных занятий за одно задание

[Выбор skill и готовые запросы запуска](../START.md)


Один исходный чат получает одно сообщение с курсом и объёмом Stage 2 и самостоятельно доводит весь названный массив до приёмки или точных локальных блокеров. P1–P4 — внутренние шаги одного задания, а не отдельные части, исполнители, чаты, сообщения, handoff, черновые файлы или согласования. Не создавай агентов для уроков или шагов без прямого поручения пользователя; если параллельный режим явно заказан, исходный чат отвечает за итоговый набор и приёмку. Явное ограничение пользователем на один шаг, анализ, запрет запуска или staging имеет приоритет.

## Шаги
1. Восстанови полный объём N и для каждого занятия подтверди строковый номер, действующий паспорт COURSE/BLOCK, точный путь MD и область записи. У существующего занятия сверь стабильный ID и identity source; для нового занятия без runtime ID зафиксируй, что идентификатор требует назначения по действующей схеме на этапе интеграции, не выдумывая ID и не считая его отсутствие автоматическим дефектом плана. Не пропускай отсутствующие занятия и не угадывай идентичность. Установи A и источник каждой существенной опоры как подтверждённую, планируемую, непроверенную или неподготовленную; цель B, границы и формат бери из действующего паспорта.
2. Для каждого занятия в одном MD совместно спроектируй путь объяснения и практики от B: что дано, что ученик делает самостоятельно, что наблюдает, где до действия объяснена необходимая конструкция, чем различить правильный и ошибочный случай. Содержательное сохраняй, при REWORK исправляй подтверждённый дефект; допустим KEEP. Степень детализации достаточна для реализации другим автором и зависит от сложности: не разворачивай заново хороший план ради шаблона. Пример не раскрывает решение практики; темы будущих занятий не становятся обязательными.
3. Проверь один раз сохранённый план каждого занятия на окончательной версии: идентичность, A→B, подготовку каждого обязательного действия, самостоятельность, формат и локальный результат, ближайшие переходы, работающие ссылки и сохранность пользовательских правок и YouTube-комментария. Устрани дефекты в разрешённой области и перепроверь затронутое. Планируемую A не называй освоенной; отсутствующий будущий сосед не блокирует готовую текущую B сам по себе.

При планировании визуального объяснения зафиксируй его учебную функцию и нужные ориентиры, а не обязательный вид или количество карточек. Для действий в реальном интерфейсе предусмотрены узнаваемый ориентир, действие и наблюдаемый результат; полезные существующие скриншоты и пояснения сохраняй как опору, если они нужны ученику. Для упражнения выбирай текстовые фрагменты, когда нужно упорядочить смысловые действия, и код, когда проверяется именно синтаксис или поведение кода. Фактический вид, читаемость и адаптивность проверяются только после реализации на Stage 3.

Промежуточные FRAME_DRAFT/THEORY_DRAFT/PRACTICE_DRAFT не являются обязательными артефактами или сообщениями; при прерывании продолжай по фактическому состоянию файла. PLAN_ACCEPTED только после полной проверки текущего плана, не по P1/P2, статике будущей реализации или сообщению. STAGE_COMPLETE только при N/N принятых планах и отсутствии обязательных блокеров; иначе STAGE_INCOMPLETE с ID и остатками. При массиве и длительной работе веди один компактный RUN: полный перечень N, пути/ключи, состояние каждого плана, версии проверок и блокеры. Возобновляй существующий RUN; создавай его только в разрешённой области. Если запись журнала запрещена, сохрани доступную сводку в ответе и обозначь ограничение восстановления. Не создавай отчёт на каждый шаг. TSX, выдача, runner и браузер ещё не подтверждаются принятым планом. Stage 3 запускай только если пользователь его заказал и gate выполнен.
