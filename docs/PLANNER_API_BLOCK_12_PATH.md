# Сквозной путь блока 12: сборка, проверка и выпуск Planner API, занятия 63-68

## Зачем существует блок

В предыдущем блоке ученик разобрал поведение ресурса tasks: сервер проверяет входные данные, сам выдаёт id, хранит текущее состояние и по разным правилам создаёт, читает, заменяет, частично изменяет и удаляет задачу. Это уже не набор несвязанных HTTP-методов. У ресурса появился жизненный цикл.

Но рабочий прототип ещё не равен проекту, который можно отдать другому разработчику. В одном файле быстро становится трудно найти маршрут. Ручная проверка не защищает от регрессии. Временное состояние между тестами делает результат случайным. А код без инструкции нельзя воспроизвести на чистой машине.

Блок 12 превращает уже известное поведение в небольшой, но цельный продукт. Он не добавляет новую предметную область и не расширяет Planner API ради количества функций. Его задача проще и важнее: сохранить один понятный HTTP-контракт, разложить ответственность по местам, доказать поведение тестами и оформить результат так, чтобы его можно было запустить без автора.

## Исходная точка

До начала блока в проекте уже есть:

- запущенное FastAPI-приложение;
- health endpoint и первый набор endpoint для tasks;
- понимание method, path, query, request body, response и HTTP status;
- Pydantic-валидация входа и ошибка 422;
- правила server-owned id и in-memory state;
- предметная разница между create, get, replace, patch и delete;
- тренировочная CRUD-цепочка в интерпретаторе.

При этом ученик ещё не обязан иметь идеальную файловую структуру. Его конечные endpoint могут находиться в main.py, а ручные проверки могут жить только в Swagger или Postman. Это нормальная стартовая точка блока. Сначала важно, что поведение понятно. Затем его можно безопасно вынести из одного файла и закрепить.

После занятия 68 у ученика есть версия Planner API v1.0.0 с одним ресурсом tasks, предсказуемым HTTP-контрактом и воспроизводимым способом проверки.

| Область | Итоговый результат |
| --- | --- |
| HTTP-контракт | Один согласованный набор маршрутов, request и response schemas, status codes и ошибок |
| Структура | main.py собирает приложение, router обрабатывает HTTP, CRUD хранит прикладные правила, storage владеет состоянием |
| Тесты | TestClient проверяет успешные и ошибочные сценарии независимо друг от друга |
| Ручная приёмка | Postman collection позволяет повторить пользовательский путь от create до 404 после delete |

Внешний результат должен быть небольшим и законченным:

~~~text
GET    /health
GET    /tasks
POST   /tasks
GET    /tasks/{task_id}
PUT    /tasks/{task_id}
PATCH  /tasks/{task_id}
DELETE /tasks/{task_id}
GET    /stats
~~~

Если в ранних занятиях у GET /tasks уже согласованы query-параметры, например поиск, фильтр или limit, они сохраняются как часть существующего контракта. Блок 12 не придумывает новые query-параметры и не меняет их смысл.

## Граница блока

Это финал третьего курса про HTTP и первый FastAPI API. Он сознательно не добавляет:

- SQLite, SQLAlchemy, migrations или другую постоянную базу данных;
- Depends, Annotated, configuration из environment;
- cookies, sessions, JWT и users;
- async database drivers, background tasks и очереди;
- Docker, облачный деплой или нагрузочное тестирование.

Состояние остаётся в памяти и исчезает при перезапуске процесса. Это не дефект учебного проекта. Так ученик может увидеть границу между HTTP API и механизмом хранения. В следующем курсе storage будет заменён на SQLite и SQLAlchemy, но публичный контракт tasks не должен от этого сломаться.

## Главный принцип: поведение сначала, устройство после

Нельзя начать блок с абстрактной папки routers и предложить ученику перенести туда непонятный код. Сначала у него есть известное поведение ресурса. Затем он делает четыре последовательных шага:

~~~text
известный CRUD-контракт
  -> безопасное выделение router
  -> тест, который фиксирует прежнее поведение
  -> явная спецификация и разделение ролей
  -> сквозная проверка полного жизненного цикла
  -> воспроизводимый релиз
~~~

Так рефакторинг не выглядит как магия. Ученик видит причину каждого нового файла: файл нужен не потому, что так принято, а потому, что он отделяет одну понятную обязанность от другой.

## Единый контракт финального проекта

До рефакторинга нужно договориться не только о названиях функций, но и о наблюдаемом поведении API.

| Операция | Method и path | Вход | Успех | Ошибка |
| --- | --- | --- | --- | --- |
| Проверка сервиса | GET /health | Нет | 200 и простой JSON status | Нет в учебной версии |
| Список | GET /tasks | Уже согласованные query-параметры, если они есть | 200 и список TaskRead | 422 для неверного query-параметра, если он валидируется |
| Создание | POST /tasks | TaskCreate | 201 и новый TaskRead | 422, состояние не меняется |
| Чтение одной задачи | GET /tasks/{task_id} | path id | 200 и TaskRead | 404 |
| Полная замена | PUT /tasks/{task_id} | TaskReplace | 200 и полностью новый TaskRead | 404 или 422 |
| Частичное изменение | PATCH /tasks/{task_id} | TaskPatch | 200 и изменённый TaskRead | 404 или 422 |
| Удаление | DELETE /tasks/{task_id} | path id | 204 без response body | 404 |
| Сводка | GET /stats | Нет | 200 и согласованный расчёт | Нет новых ошибок |

### Решение о схемах update

Полная замена и частичное изменение не могут опираться на одну расплывчатую модель. В финальном проекте нужны отдельные роли.

| Schema | Кто и для чего её использует |
| --- | --- |
| TaskCreate | Клиент отправляет данные новой задачи. id и is_done не принадлежат входу. |
| TaskRead | Сервер показывает завершённую запись с id, title, priority и is_done. |
| TaskReplace | Клиент отправляет все изменяемые поля для PUT. Отсутствующее поле не должно сохранять старое значение молча. |
| TaskPatch | Клиент отправляет только те изменяемые поля, которые хочет изменить. Поле, которого нет в body, остаётся прежним. |

В текущем материале встречается optional TaskUpdate. При точечной переработке его нельзя одновременно объяснять как схему полного PUT. Безопасный выбор такой: ввести TaskReplace и TaskPatch явно, а имя TaskUpdate убрать из финального публичного контракта. Это связывает теорию, OpenAPI, ручную практику и автопроверку в одну модель.

## Архитектура: простая цепочка зависимостей

Финальная структура не должна имитировать большой production-проект. Её цель: сделать путь запроса читаемым и не допустить обратных импортов.

~~~text
app/main.py
  -> app/routers/tasks.py
       -> app/crud/tasks.py
            -> app/storage/memory.py

app/routers/tasks.py
  -> app/schemas/task.py
~~~

| Слой | Ответственность | Чего в нём быть не должно |
| --- | --- | --- |
| main.py | Создать FastAPI app, подключить router, оставить общую сборку | SQL, алгоритмы CRUD, длинные endpoint functions |
| routers/tasks.py | Прочитать HTTP request, вызвать прикладную операцию, вернуть response или HTTPException | Владение списком задач, выдача id, повторяющаяся бизнес-логика |
| schemas/task.py | Описать входные и выходные Pydantic models | Глобальный список задач, FastAPI decorators |
| crud/tasks.py | Реализовать create, list, get, replace, patch, delete и прикладные правила | APIRouter, Request, Response, HTTPException |
| storage/memory.py | Владеть in-memory collection и следующим id | HTTP status codes и Pydantic request parsing |
| tests/test_tasks.py | Проверить публичный контракт через TestClient | Скрытый доступ к реализации вместо пользовательского сценария |

В этой версии допустим простой in-memory storage. Важно только, чтобы storage и CRUD не импортировали FastAPI. Тогда позже можно поменять память на базу данных, не переписывая router и внешний API.

## Паспорта уроков

### 63. APIRouter, prefix, tags и include_router

**Роль в цепочке.** Ученик впервые проводит рефакторинг работающего API. Он не пишет новый CRUD и не меняет бизнес-правила. Его цель: сделать main.py местом сборки, а tasks router местом HTTP-маршрутов ресурса.

**Теория должна дать.**

- Начать с знакомой проблемы: маленький файл удобен, но в нём трудно увидеть границы, когда routes, создание app и детали tasks лежат рядом.
- Объяснить APIRouter как отдельную папку с маршрутами одного ресурса. Аналогия допустима: это не новый магазин, а отдельная стойка внутри того же магазина. Внешний адрес для клиента остаётся тем же.
- Показать смысл prefix. Router хранит общую часть /tasks один раз, а endpoint добавляет только свою часть.
- Показать tags как подписи групп в Swagger. Они помогают читать документацию, но не меняют URL и не являются авторизацией.
- Разобрать include_router как точку сборки: app знает, какие routers подключены, но не должен содержать их внутренние операции.
- Ясно назвать границу: import direction идёт от main к router, а не наоборот. Перенос endpoint не должен создавать циклический import.

**Интерактив в теории.**

1. Предложить предсказать URL: router с prefix /tasks и handler с path /{task_id} даёт какой внешний path.
2. Дать два варианта main.py и спросить, в каком случае путь /tasks исчезнет после переноса.
3. Показать фрагмент Swagger до и после tags и спросить, изменился ли HTTP-контракт.

**Практика.** Ручная. Ученик создаёт app/routers/tasks.py, переносит уже работающие endpoint, подключает router в main.py, открывает /docs и повторяет существующие requests. В задании должны быть отдельно названы инварианты: те же methods, paths, status codes и JSON forms.

**Подсказки.** Сначала предложить вынести router и один endpoint. Затем напомнить, что prefix задаётся один раз. Последняя подсказка может предложить временно убрать include_router и увидеть 404, после чего вернуть подключение. Полный файл router в подсказке не показывается.

**Не добавлять.** Новые endpoint, users, dependencies, database, изменение response schema.

**Мостик.** После переноса интерфейс надо защитить от случайного изменения. Следующий урок проверяет его как клиент, а не как автор кода.

### 64. Тесты FastAPI через TestClient

**Роль в цепочке.** Ученик учится проверять API без запущенного Uvicorn и браузера. Это не урок о pytest целиком. Это урок о том, что публичный контракт можно повторить автоматически.

**Теория должна дать.**

- Начать с реальной причины: Swagger полезен для исследования, но человек может забыть сценарий или посмотреть не на тот response.
- Объяснить TestClient простым языком. Он отправляет request прямо приложению в тесте и даёт response, как будто его получил клиент.
- Разложить любой API-test на четыре части: arrange состояния, act request, assert status, assert body или заметный side effect.
- Объяснить, почему status и JSON проверяются отдельно. Response может иметь 201, но вернуть неправильные поля.
- Рассказать о независимости тестов. Память переживает запросы, поэтому каждый тест должен начинаться с известного состояния. Это не особенность pytest, а свойство in-memory state.
- Показать разные типы contract cases: happy path, 404, 422 и отсутствие side effect после невалидного POST.

**Интерактив в теории.**

1. Дать response с status 201, но без id, и спросить, почему тест только на status недостаточен.
2. Показать два запуска одного и того же теста с общим storage и предложить найти причину нестабильности.
3. Попросить соотнести client.get, client.post и параметр json с HTTP request, который уже знаком из Postman.

**Практика.** Ручная. Ученик добавляет tests/test_tasks.py и проверяет минимум health, list, успешный POST, GET отсутствующей задачи и невалидный POST. Каждый кейс проверяет status и нужную часть body. Отдельно он доказывает, что повторный запуск набора тестов даёт тот же результат.

**Подсказки.** Первая напоминает импорт app и создание TestClient. Вторая предлагает начать с одного GET /health. Последняя указывает, что test state нужно сбрасывать в согласованной точке, а не надеяться на порядок запуска тестов.

**Не добавлять.** Моки внешних сервисов, async tests, database fixtures, coverage target, параметризацию ради синтаксиса.

**Мостик.** Теперь можно не бояться структурного изменения. Но до большой перестройки нужно точно зафиксировать, что входит в финальную версию и какие слои имеют право знать друг о друге.

### 65. Финальный проект 1: контракт и архитектура Planner API

**Роль в цепочке.** Это точка решения перед сборкой. Ученик не копирует ещё один вариант CRUD. Он превращает уже увиденные ответы и тесты в короткую спецификацию, по которой можно проверить будущую реализацию.

**Теория должна дать.**

- Начать с привычной ситуации: если сначала хаотично разносить файлы, можно получить красивую структуру с разными правилами в каждом endpoint.
- Объяснить API contract как обещание между сервером и клиентом. В нём важны не внутренние names functions, а method, path, вход, status, response и error.
- Объяснить сценарий пользователя через жизненный цикл одной задачи. Клиент создаёт задачу, получает id, читает её, заменяет, частично меняет, удаляет и убеждается в 404.
- Разобрать разницу PUT и PATCH на конкретном наборе полей. PUT означает полную новую форму ресурса, PATCH означает список только нужных изменений.
- Показать минимальную схему зависимостей. У каждого файла одна основная обязанность. Router не выдаёт id, storage не выбирает HTTP status.
- Показать границу финала. In-memory storage подходит для этого курса, а база, login и production deploy относятся к последующим этапам.

**Интерактив в теории.**

1. Дать body для PATCH с одним полем и спросить, какие поля должны остаться прежними.
2. Дать body для PUT без обязательного поля и спросить, почему сервер не должен угадывать старое значение.
3. Попросить разложить три действия по слоям: выбрать status 404, выдать новый id, проверить min_length title.

**Практика.** Ручная. Ученик пишет docs/final-api-contract.md с таблицей endpoint, schemas, success status и error status. Затем рисует короткую схему зависимостей main, router, crud, storage и schemas. Документ сверяется с уже работающим OpenAPI и тестами.

**Подсказки.** Сначала предложить заполнить один POST endpoint полностью. Затем напомнить, что 204 не имеет body. Последняя подсказка просит найти в документе место, где optional update schema ошибочно используется как PUT.

**Не добавлять.** Новые бизнес-функции, tags, pagination, database, авторизацию. Документ фиксирует согласованное, а не проектирует следующий курс.

**Мостик.** У ученика есть чертёж. В следующем уроке он переносит существующие правила в файлы снизу вверх, сохраняя этот чертёж неизменным.

### 66. Финальный проект 2: schemas, storage, crud и routers

**Роль в цепочке.** Ученик собирает проект из частей с одной обязанностью. Он не должен переносить код механически. Каждый перенос отвечает на вопрос, почему этому правилу не место в соседнем слое.

**Теория должна дать.**

- Начать с результата предыдущего урока: контракт уже известен, поэтому новая структура не имеет права его менять.
- Объяснить подход снизу вверх. Сначала данные и правила без HTTP, затем тонкий router, затем сборка app.
- Показать storage как владельца состояния. Он хранит collection и знает next id, но не знает о request или status 404.
- Показать CRUD как набор прикладных операций. Он умеет найти, создать, заменить, частично изменить и удалить запись, но не импортирует FastAPI.
- Показать router как переводчика между HTTP и операцией. Router читает path и body, вызывает CRUD, превращает отсутствие записи в 404 и выбирает response model.
- Объяснить, почему schema не равна storage record автоматически. Schema описывает договор с внешним клиентом, storage может иметь свой простой внутренний формат.

**Интерактив в теории.**

1. Попросить выбрать слой для next_id и объяснить, почему это не router.
2. Показать функцию CRUD с HTTPException внутри и спросить, какую зависимость она нарушает.
3. Дать две стрелки imports и попросить найти недопустимую: router -> crud или crud -> router.

**Практика.** Ручная. Ученик создаёт schemas/task.py, storage/memory.py, crud/tasks.py и routers/tasks.py, оставляет main.py короткой точкой сборки и переносит известные правила по одному. После каждого переноса он запускает уже существующие tests и делает маленький commit только после зелёного результата.

**Подсказки.** Первая предлагает начать с TaskCreate, TaskRead, TaskReplace и TaskPatch. Вторая предлагает вынести state и next id до router. Последняя напоминает: если crud импортирует FastAPI, ответственность смешалась.

**Не добавлять.** Repository pattern, dependency injection, ORM, class hierarchy, singleton container. Эти абстракции не помогают понять текущую цепочку.

**Мостик.** Структура собрана, но отдельные endpoint и отдельные tests ещё не доказывают, что один и тот же id проходит весь жизненный цикл. Следующий урок связывает операции в один trace.

### 67. Финальный проект 3: полная CRUD-логика

**Роль в цепочке.** Это не повтор уроков 59-62. Там ученик изучал каждое правило по отдельности. Здесь он проверяет их взаимодействие на одной последовательности действий и на одном состоянии.

**Теория должна дать.**

- Начать с простой мысли: API проверяют не только одиночным запросом. Клиент работает с ресурсом во времени, а ошибка в одном шаге проявляется на следующем.
- Рассказать о жизненном цикле resource: create создаёт id, get подтверждает существование, replace задаёт полное новое состояние, patch меняет только выбранные поля, delete убирает запись, следующий get получает 404.
- Отдельно сопоставить domain result и HTTP result. Чистая операция сообщает, что запись найдена, изменена или удалена. Router переводит это в 200, 201, 204 или 404.
- Показать, почему копии важны в интерпретаторе. Задание не должно менять начальный список так, чтобы следующий запуск видел старые данные.
- Объяснить, что ответ 204 означает успешное удаление без JSON body. Его нельзя проверять как обычный TaskRead.

**Интерактив в теории.**

1. Дать trace create -> patch -> get и спросить, какие поля обязаны сохраниться после patch.
2. Дать trace replace -> get и спросить, почему значения, отсутствующие в полной замене, не могут незаметно остаться от старой записи.
3. Попросить предсказать последний status после delete -> get.
4. Показать две цепочки с одним и тем же initial_items и спросить, почему их результаты не должны зависеть от порядка запуска.

**Практика.** Основная практика в интерпретаторе. Она принимает исходные задачи и operations, создаёт копию состояния и возвращает results вместе с итоговыми items. В одном связном сценарии ученик проходит create, get, replace, patch, delete и ошибку отсутствующего id. Затем тот же путь сверяется с реальным API через TestClient или Postman.

**Обязательная правка текущей автопрактики.** Сейчас задача 67 покрывает create, get, patch и delete, но не содержит replace. Это противоречит названию урока, его теории и финальному контракту. При переработке в operations нужно добавить действие replace:

- оно принимает id и полный набор изменяемых полей;
- оно заменяет все изменяемые значения, а не сливает часть data со старой записью;
- при найденной задаче возвращает наблюдаемый результат со status 200;
- при отсутствии задачи возвращает status 404 и не меняет items;
- отдельный test доказывает различие replace и patch.

При этом автопрактика не должна заниматься HTTP imports или запуском FastAPI. Она проверяет чистую логику и последовательность. Реальный HTTP путь остаётся в ручной проверке проекта.

**Подсказки.** Первая предлагает обработать operations по порядку. Вторая напоминает, что create получает новый id, а get возвращает копию. Последняя различает replace и patch: первый работает с полной формой, второй меняет только переданные поля. Полное решение не приводится.

**Не добавлять.** Новые endpoint, фильтры, базы данных, retry logic. Урок доказывает уже утверждённый контракт.

**Мостик.** Логика и HTTP-путь проверены. Последний урок смотрит на проект глазами человека, который не участвовал в его написании.

### 68. Финальный проект 4: Postman, тесты, README и GitHub Release

**Роль в цепочке.** Ученик завершает не набор файлов, а воспроизводимый результат. Задача урока не в том, чтобы научить всем возможностям GitHub. Он показывает базовый профессиональный критерий: другой человек может повторить запуск и убедиться, что проект делает заявленное.

**Теория должна дать.**

- Начать с живой ситуации: "у меня работает" не помогает тому, кто впервые клонирует repository.
- Разобрать два независимых вида проверки. Postman повторяет внешний путь клиента. TestClient быстро проверяет договор в коде. Один не отменяет другой.
- Объяснить collection как сохранённую последовательность запросов, а не как скриншот Swagger. В ней должен быть сценарий, где id из POST используется дальше.
- Объяснить независимые tests и fixture как способ получать известный starting state. Не нужно углубляться в сложную pytest-архитектуру.
- Показать структуру учебного README: что это за API, требования, установка, запуск, docs, tests, список endpoint, ограничение in-memory state.
- Объяснить маленький релиз: чистый working tree, проверенные tests, понятный commit, tag. GitHub Release возможен только после этого, а не вместо проверки.

**Интерактив в теории.**

1. Дать два README и попросить найти отсутствующий шаг, из-за которого новый разработчик не сможет запустить сервер.
2. Попросить расставить actions в правильном порядке: POST, сохранить id, GET by id, PATCH, DELETE, GET by id.
3. Показать 204 и спросить, почему Postman-test не должен ожидать JSON task.
4. Спросить, какой факт доказывает tag, а какой доказывают зелёные tests.

**Практика.** Ручная. Ученик создаёт или обновляет Postman collection, выполняет сквозной CRUD-путь, запускает TestClient tests дважды, дописывает README и только после успешной приёмки делает commit и release tag. Если GitHub Release доступен и пользователь сам решил его создать, в описание попадает только проверенная информация о v1.0.0.

**Подсказки.** Первая предлагает начать с README и чистой установки. Вторая напоминает сохранить id, созданный POST. Последняя даёт чек-лист приемки: install, run, docs, Postman, pytest, граница in-memory state.

**Не добавлять.** Обещания production readiness, Docker, cloud deploy, persistent storage, безопасность users. README честно называет эти темы следующими этапами.

**Переход дальше.** Ученик закончил API с временным storage и защищённым контрактом. Следующий курс отвечает на другой вопрос: как сохранить тот же ресурс между перезапусками процесса, не разрушив routes, schemas и tests.
