### `41`. Адрес и метод запроса

1. **Тема и роль.** Первый шаг от знакомого локального Planner к сообщению отдельному серверу. Ученик понимает стороны обмена, адрес и намерение; пока не выбирает методы для всех операций и не отправляет запрос.

6. **Выход, критерий и переход.** Возвращены ровно согласованные значения, ученик объяснил, где находятся клиент, сервер и состояние Planner. `41.1` использует готовые method/path и добавляет headers/body; до этого перехода проверить, что ученик не принимает словарь за отправленный HTTP-запрос.

### `41.1`. Заголовки и тело запроса

1. **Тема и роль.** Продолжить модель request, объяснив, зачем в сообщении отдельно хранятся метаданные и содержимое.
2. **A и источник/статус.** Method/path из `41` — планируемая опора; фактическое освоение не доказано. До выдачи проверить, что ученик сам собрал учебную пару и может объяснить её поля. Python-словарь и условие проверки `None`/пустого значения заявлены в планируемом выходе главы 2, личное применение не проверено; восстановить на маленьких независимых примерах до редактора.
3. **Наблюдаемая B.** Самостоятельно формирует словарь request с правильными headers, сохраняет body и отличает отсутствующее тело от пустого JSON-объекта.
4. **Механизмы по порядку.** Request состоит из стартовой строки/метаданных и body; здесь нужен учебный словарь частей. `Accept` сообщает желаемый формат ответа, `Content-Type` — формат переданного body; их роли различны. Для `None` тело отсутствует, `{}` — передан пустой объект. Словарь Python — модель, JSON — представление, HTTP — передача; сериализацию и сеть отложить. Объяснить каждый header, показать 2 безопасных примера, затем дать самостоятельную функцию.

Ученик пишет сборку заголовков `Accept: application/json`, `Planner-Client-Version` и `Content-Type` только при наличии body; возвращает точные ключи `method`, `path`, `headers`, `body`. Сам проверяет отсутствие тела, `{}`, обычный body и другой переданный method/path; ничего не отправляет и не меняет.
6. **Выход, критерий и переход.** Заголовки соответствуют назначению, body сохранено, `None` и `{}` различимы. `42` начинает с уже собранного request и объясняет, где увидеть исход обработки; до него проверить именно различение формы тела.
7. **Теория: 1200–1600 слов.** Четыре новых части модели и сходные headers требуют контраста; знакомый Python-словарь может сократить объяснение только после входной проверки. Примеры ограничены двумя формами body, без сетевой отправки и преждевременной Pydantic.

### `42.1`. Тело ответа и Content-Type

1. **Тема и роль.** Завершить первую модель response: status, headers и возможное содержимое.
2. **A и источник/статус.** Status и request из `41.1`/`42` — планируемая A; до фактической выдачи проверить самостоятельную сборку request и выбор status на новом случае. 3. **Наблюдаемая B.** Самостоятельно собирает `status`, `headers`, `body`, включая `Content-Type` при JSON-теле; сохраняет разницу между отсутствующим телом и `{}`.
4. **Механизмы по порядку.** `Content-Type` описывает тело ответа; код статуса не заменяет body. Успешный ответ может содержать объект, пустой список или не содержать body. Для `204` тела нет; `{}` остаётся переданным JSON-объектом. `X-Request-ID` относится к сообщению и не является id задачи. Объяснение → разбор пары примеров → безопасная проба с входом `None`/`{}` → самостоятельная функция.
5. **Самостоятельная практика и формат.** Автопроверяемый редактор `solve(status, body, request_id)` существующего ключа `42.1`. Ученик формирует headers с request ID, добавляет JSON content type только при имеющемся body, возвращает точную модель. Проверяет `200` с объектом, `200` с `{}`, `404` с телом ошибки и `204` с `None`; статус передан готовым, создавать задачу и искать item не нужно.
6. **Выход, критерий и переход.** Модель не теряет статус/body, заголовок типа добавлен только по предусмотренному правилу; ученик объясняет `None`/`{}` и неприменимость чтения JSON при `204`. `43` использует понимание сообщений для выбора метода; перед ним проверить знание difference status/body.
7. **Теория: 1200–1600 слов.** Продолжается знакомство с новыми response-полями; нужны различающие случаи `204` и пустого JSON и роль request ID. Знакомый словарь — только условная опора, поэтому диапазон не опускается ниже 1000.

## 4. Неизменяемая карта Planner и локальная приёмка

| Метод/путь | Расположение входа | Ожидаемый исход по принятому COURSE |
|---|---|---|
| `GET /health` | нет | `200`, короткое состояние сервиса |
| `GET /tasks` | query: `is_done`, `sort_desc`, `limit` (optional) | `200` + список; пустой список тоже `200`; filter → sort id → limit; defaults `None`, `False`, `10`, limit 1–50 |

| `PATCH /tasks/{task_id}` | path + только переданные изменяемые поля | `200` + полная запись после изменений; отсутствующий item — `404` |
