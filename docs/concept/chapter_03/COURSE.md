## 2. Цель B и проверяемые результаты

B сохраняет **Planner API v1.0.0** в том же проекте. Ученик объясняет путь запроса от клиента через HTTP-границу и сервис к общему JSON, добавляет и проверяет HTTP-интерфейс, передаёт воспроизводимую версию. FastAPI/Uvicorn публикуют OpenAPI/Swagger. CLI и API используют те же PlannerService, JsonStorage и JSON; API не заводит второй CRUD или авторитетный список.

| Результат | Объясняет | Самостоятельно делает | Сохраняемый инвариант | Наблюдаемая проверка |

### Неизменяемый API-договор

| Метод/путь | Вход и успех | Требование |
| --- | --- | --- |
| `GET /health` | без входа → `200` | Состояние сервиса |
| `GET /tasks` | optional `is_done`, `sort_desc`, `limit` → `200` + список | `is_done=None`, `sort_desc=False`, `limit=10`, диапазон 1–50; filter → sort по id → limit; пустой список — `200` |
| `GET /tasks/{task_id}` | path id → `200` + задача | Отсутствующий item — `404` |
| `GET /stats` | без входа → `200` + сводка | Всё storage, независимо от list-фильтров |
| `POST /tasks` | body `title`, `priority` → `201` | Сервер назначает id и `is_done=False` |
| `PUT /tasks/{task_id}` | полная изменяемая форма → `200` | Полная замена, прежний id; отсутствующий item — `404` |
| `PATCH /tasks/{task_id}` | только переданные изменяемые поля → `200` | Пропуск поля не равен переданному `false`; отсутствующий item — `404` |
| `DELETE /tasks/{task_id}` | path id → `204`, без тела | Удаление; отсутствующий item — `404` |

Публичный Task содержит `id/title/priority/is_done`; `tags` остаётся внутри модели/JSON. Для title: trim, непустое значение, 1–120 символов после trim; priority 1–5. Невалидный запрос — `422` без изменения состояния. API сохраняет задачи в том же JSON, который использует CLI. Postman-сценарии входят в передачу; автоматические HTTP-проверки используют TestClient; итог также включает README/инструкции и выпуск проверенной версии.

Основание `B_AGREED`: старый COURSE (`bfa2eecc^`) устанавливает эту B и договор; прямой мандат позволяет менять внутреннюю дидактическую организацию при сохранении входа и конечного продукта. Нового согласования цели не требуется.

## 3. Содержание, изменения и границы

Причинный порядок переработан вокруг циклов «предсказать → безопасно попробовать → объяснить расхождение → применить к Planner → сверить состояние». Сначала диагностика предметного проекта и моделирование HTTP без сервера; затем Postman на безопасном примере и, после прогноза ученика, собственный `/health`. Далее API строится вертикальными срезами: чтение и фильтрация, затем создание; каждый срез сразу сверяется с CLI/JSON и перезапуском. После этого вводятся ограничения и операции изменения, каждая сначала проверяется вручную на положительном и отрицательном случае. TestClient появляется после ручной матрицы как автоматизация уже понятного договора; изоляция, регрессия CLI и clean handoff завершают путь. Новые средства не вводятся одновременно с первой сложной интеграцией: сначала объяснение и малая самостоятельная проба, затем применение к накопительному Planner.
