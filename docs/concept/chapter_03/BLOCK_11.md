### Порядок, рост самостоятельности и условные стыки

Сначала POST-вход получает безопасную нормализацию и ограничения, после чего оформляются схемы и проверяется настоящее сохранение. Только затем создаются service-level операции PUT и PATCH; их безопасная проба предшествует HTTP-маршрутам. Отдельное подзанятие `54.1` делает семантику пропуска, `null` и `false` наблюдаемой до регистрации PATCH. DELETE использует уже имеющийся service. Финальный smoke интегрирует ранее созданное, а не впервые учит API.

**Вход от BLOCK_10 (условный, окончательно сверит F1–F3):** необходимы работающие GET/POST и ручная проверка общей записи через прежний сервис/JSON/CLI → поставщик BLOCK_10 → перед первым изменением ученик повторяет smoke и показывает тот же объект после нового запуска. Фактическая A ученика не подтверждена. При провале зависимые проектные практики ждут восстановления входа, самостоятельные схемные упражнения остаются планируемыми.

**Выход к BLOCK_12 (предложение, окончательно сверит F1–F3):** полный ручной контракт восьми endpoint, в том числе 422 без мутации, 404, PUT с прежним id, PATCH с skip/null/false и DELETE 204 без body → поставщик этот блок → BLOCK_12 воспроизводит smoke до TestClient и использует тестовый путь данных. От BLOCK_12 не требуется быть завершённым для локального B4.

### `51` · Очистка входной строки — основное занятие дня 1

**Идентичность.** Текущий физический материал `backend/content/materials/chapter_03/block_11/51 - Очистка входной строки.md`; canonical source `HTTP, API и FastAPI - Planner API/51 - Очистка входной строки.md`; вычисленный по `_stable_lesson_id()` ID `lesson-3795384d9e6fccf65e6daded`. Alias создаётся через `PLANNER_API_MODULE_LABELS`/`LESSON_SOURCE_ALIASES`.

1. **Тема и роль.** Научиться очищать только строковый `title` на HTTP-входе перед предметными ограничениями. Это первая небольшая правка к готовому POST и опора для `51.1`; не менять доменную Task или CLI.
2. **A, источник, статус.** Планируется: предыдущая B из COURSE/BLOCK_10 — POST передаёт вход в существующий Planner и сохраняет JSON. До изменения проверить маршрут, POST, CLI и реальный файл; отдельно увидеть структуру TaskCreate. Личный навык не проверен. HTTP before-validator новый.
3. **Наблюдаемая B.** Ученик объясняет, почему очистка должна предшествовать проверке длины, сам добавляет before-validator, получает сохранённый `"Разобрать API"` из ввода с краевыми пробелами и безопасно передаёт неподходящий тип стандартной проверке Pydantic.
4. **Механизмы по порядку.** Входная модель и обычная проверка типа → объяснение before-validator как преобразования сырого значения → безопасная проба на отдельной строке: предсказать `.strip()` и отказ для числа → только затем самостоятельная правка TaskCreate. Показать, почему `.strip()` до проверки типа даёт неверный отказ. Не добавлять здесь min/max length, priority limits, новый POST или доменную нормализацию.
5. **Самостоятельная практика и формат.** После безопасной пробы ученик самостоятельно пишет валидатор в TaskCreate текущего Planner; через прежний POST отправляет обычную строку и строку с пробелами, затем нестроковый raw input. Он сопоставляет status, очищенное значение и файл; не редактирует данные напрямую и не вводит новый service.
6. **Результат, критерий и передача.** POST продолжает возвращать 201 и сохраняет очищенное название; нестроковое значение завершается обычным отказом схемы, не AttributeError/500; на `51.1` передаётся та же нормализующая схема. Если общий POST/JSON на входе не подтверждён, практику отложить до восстановления A.
7. **Видимая теория: 1200–1600 слов.** Нужны новый Pydantic before-validator, порядок сырого типа и преобразования, безопасный отказ и отличие HTTP-границы от доменных правил; одной короткой подсказки недостаточно, но длина и диапазон priority вынесены в `51.1`.

### `51.1` · Ограничения и ошибка 422 — обязательное подзанятие дня 1

**Идентичность.** Единственный текущий урок-поставщик: физический source `backend/content/materials/chapter_03/block_11/57 - Pydantic-валидация и ошибка 422.md`; canonical source `HTTP, API и FastAPI - Planner API/57 - Pydantic-валидация и ошибка 422.md`; сохранённый ID `lesson-c75ffe58ef0405d3f5a16ab8`; frontend index → `Lesson57`, display override → `51.1`. 1. **Тема и роль.** Задать границы чистого title и priority и читать отказ 422 как ответ до предметного действия. Это не повтор валидации типа, а проверка значения после очистки.
2. **A, источник, статус.** Планируется: `51` самостоятельно очищает title; проверить код и граничный успешный POST до применения ограничений. Источник — этот паспорт и цель COURSE; выполнение учеником не подтверждено.
3. **Наблюдаемая B.** Ученик сам применяет длину очищенного title 1–120 и priority 1–5; предсказывает и наблюдает 422 на пустом/слишком длинном title и priority 0/6; доказывает равенство состояния до/после отказа.
4. **Механизмы по порядку.** Сначала безопасно разобрать готовые примеры уже очищенного значения: title 1/120 принимается, 0/121 отклоняется, priority 1/5 принимается, 0/6 отклоняется; затем объяснить Field limits, порядок до handler/service, форму 422 loc/type/msg и отделить validation error от ошибки сервиса.
5. **Самостоятельная практика и формат.** После разбора ученик сам задаёт ограничения и проверяет на текущем POST title длиной 1 и 120, пустую строку, raw-строку длиннее 120 только за счёт крайних пробелов, а также чистую длину 121 и priority 1, 5, 0, 6. 6. **Результат, критерий и передача.** Границы принимаются/отклоняются по очищенному значению; все невалидные запросы дают 422 до мутации, успешная запись сохраняется прежним POST. Дальше `52` переносит эти правила в TaskCreate без изменения поведения.
