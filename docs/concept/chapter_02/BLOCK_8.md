### Точка A блока

Ученик понимает функции и передачу состояния, исключения, импорты, пакет, пути/JSON, классы и экземпляры, методы, dataclass, независимые tags и композицию. Он уже умеет выполнять прямые проверки с assert, но системное знакомство с pytest ещё предстоит.

В проекте по принятому маршруту:

- функциональные операции и CLI работают со словарями; все прежние команды и перезапуск действуют;
- один рабочий `data/tasks.json`, загрузка до меню, сохранение после реального изменения через callback;
- валидаторы и прикладные/файловые ошибки уже объяснены; плохой снимок не превращается в пустую базу;
- в `app.models` подготовлена одна dataclass Task с `id/title/priority/is_done/tags`, методами и to_dict/from_dict;
- Task пока не включена в операции и рабочий storage; старые полные четырёхпольные записи принимаются её конвертером;
- нет PlannerService и объектов storage. Их появление является изменением устройства работающего приложения, не первым появлением сохранения.

Это подтверждает наличие учебных исходников, не их принятие, выдачу или освоение. ### Точка B блока

Persistent Planner сохраняет исходный корень и историю, добавляет, читает, ищет, завершает и удаляет задачи, показывает статистику. Все обработчики используют один PlannerService. Сервис получает storage, выполняет действие на актуальном наборе и сохраняет только успешное изменение. Обычный запуск использует JsonStorage; MemoryStorage применяется как объяснённая альтернатива и зависимость для проверок.

Итоговый договор:

| Компонент | Обязанность и результат |
| --- | --- |
| `app.models.Task` | Одна задача, прежние правила, методы изменения, независимые tags, явные конвертеры |
| `app.storage.JsonStorage(path)` | `load() -> list[Task]`, `save(tasks)`; путь задан сборкой, чтение/запись и ошибки остаются внутри роли хранения |
| `app.storage.MemoryStorage(tasks=None)` | Тот же load/save; свой контейнер с явно объяснёнными общими ссылками на Task |
| `app.services.PlannerService(storage)` | Координация предметного действия; нет input, печати, выбора типа storage или второго постоянного списка |
| `app.cli` | Разбор команды/ввода, вызов сервиса, представление и сообщения; нет собственного CRUD и JSON-IO |
| `app.main.build_service(storage=None)` | При None создаёт JsonStorage для одного рабочего пути, при явной зависимости использует её; импорт/сборка не начинают input или запись |
| `tests/` | Проверки модели, сервиса, договоров storage и CLI; файлы изолированы через tmp_path |
| README и проверенная версия | Воспроизводимые запуск/тесты, архитектура, ограничения, порядок создания и сохранения данных |

Итоговые методы сервиса заданы картой курса:

| Метод | Результат и важный эффект |
| --- | --- |
| `add_task(title, priority, tags=None)` | Создаёт Task с назначенным id и False, сохраняет набор, возвращает Task |
| `list_tasks()` | Актуальный список Task; чтение без save |
| `get_task(task_id)` | Task либо TaskNotFoundError |
| `mark_done(task_id)` | Возвращает Task; сохраняет переход в выполненное, повтор не создаёт запись и не требует нового save |
| `delete_task(task_id)` | Удаляет существующую задачу, сохраняет набор, возвращает None; неизвестный id даёт TaskNotFoundError |
| `search_tasks(query)` | Совпадения без изменения данных; пустой очищенный фрагмент даёт [] |
| `get_statistics()` | `all/open/done`, all = open + done; процент вычисляется из этой сводки, для пустого набора 0.0 |

Новая задача получает 1 в пустом наборе, иначе максимум **текущих** id + 1. Удаление не перенумеровывает соседей. Это не обещание пожизненной уникальности удалённых id: удалённый максимальный номер может использоваться снова. Существующие алгоритмы не заменяются новым счётчиком без отдельного требования.

### Границы и честные ограничения

- Новая возможность delete вводится в 37.2. Остальные операции переносятся, а не реализуются заново ради новой архитектуры.
- Tags сохраняются как часть модели/JSON; новых команд управления метками не требуется.
- Нет HTTP, FastAPI, Pydantic, схем запросов, базы, async, конкурентной записи, UI, TaskBoard или абстрактного Storage-фреймворка.
- Наследование не является условием заменяемости; достаточно одинакового объяснённого поведения load/save. ABC/Protocol не нужны.
- Копия списка в MemoryStorage не копирует каждую Task. Изменение общей Task может быть видно до save; модель не обладает транзакционной изоляцией.
- Неверный ввод не должен менять данные или вызывать save. Отказ записи после мутации не означает гарантированный откат памяти; запись через w не становится атомарной от наличия класса.
- Программа работает в принятом учебном режиме последовательного доступа. Согласование одновременных writers принадлежит будущему расширению, не скрытой приёмке этой главы.

### 36.1. Хранение через JSON

**Основная тема и назначение.** Собрать настройку пути и файловое поведение в один компонент; перестать считать список длительной сессии источником истины.

**A.** Функциональные load/save возвращают/принимают Task и поддерживают новый/старый формат. Сохранение пока уведомляется callback из CLI.


Статус A: **планируется** из результата 36; источник — паспорт 36 этого BLOCK и COURSE §4. Перед выдачей сверить, что функции load/save уже работают с Task и старым JSON; пока ученик не показал это самостоятельно, не считать освоенным.
**B.** `JsonStorage(path)` имеет load/save; каждое действие получает актуальный набор. Постоянный список CLI и активное callback-сохранение больше не участвуют в пути данных.

**Предпочтительный объём будущей учитываемой видимой TSX-теории:** 950–1300 слов (от раздела `00` до обзора практики, не включая обзор; содержательные объяснения интерактивов учитывать один раз, практику не квотировать). **Основание нижней границы ниже 1000:** классы, `Task`, конвертеры и функциональные JSON load/save уже запланированы в блоках 6–7 и применяются в занятии 36 (факт проверить до выдачи). Здесь новичку нужны новые связи `self.path → load/save`, передача одного объекта, актуальное чтение на действие, сохранение только изменения и прежние ошибки; два различающих примера и ограничения записи раскрываются без повторного курса JSON и ООП.

**Темы в порядке изучения:**

1. Объект хранит настройку path, методы используют её; создание JsonStorage не открывает файл и не запускает меню.
2. Новый метод повторяет договор готового IO, не копирует параллельную файловую реализацию.
3. `load → выполнить действие → save при изменении`; чтение не сохраняет. На одну команду нет второго случайного чтения для того же результата.
4. Сборка выбирает путь/объект, CLI передаёт зависимость. Ни storage, ни операция не импортируют main ради настроек.
5. Ошибки и ограничения `w` сохраняются после переноса; класс сам по себе не создаёт транзакцию.

Формат самостоятельной практики: **изменение существующего проекта** с проверкой чтения/записи через два объекта и перезапуск.

**Основная практика, проект:**

1. Перенести load_tasks/save_tasks в JsonStorage.load/save, сохранив проверку снимка, преобразования и StorageError с причиной. Общие чистые помощники можно оставить, второго публичного файлового пути не оставлять.
2. Временно сделать существующие прикладные функции storage-aware: они получают storage и загружают набор для действия, используют прежние алгоритмы, сохраняют только изменение. Это переходный слой до переноса в service.
3. CLI получает storage вместо постоянного списка. Обработчики вызывают переходные операции; on_change не подключается и не выполняет вторую запись. Удалить заменённое владение состоянием; оставшиеся временные параметры окончательно убрать в 37.2.
4. Прочитать данные через один объект, изменить через другой объект с тем же путём и снова прочитать через первый: видны актуальные данные, нет startup-кеша.
5. Проверить перезапуск, старые записи, неверный ввод, неизвестный id и повторное done без save. Проверочный путь явный, рабочий JSON не повреждается экспериментом.

**Выход и переход.** Обычный продукт остаётся persistent, но его зависимость узкая и явная. Далее второй вариант storage проверяет заменяемость этого договора.

### 37. MemoryStorage и JSON

**Основная тема и назначение.** Показать заменяемость хранения и объяснить владельцев контейнера и объектов, не подменяя сохранение новым in-memory проектом.

**B.** MemoryStorage реализует тот же договор. Те же операции работают с обоими storage; обычный запуск остаётся JSON.

**Предпочтительный объём будущей учитываемой видимой TSX-теории:** 950–1350 слов (от `00` до обзора практики, исключая обзор; объясняющие разборы интерактивов учитывать один раз, практику не квотировать). **Основание нижней границы ниже 1000:** по маршруту до занятия 37 уже запланированы объяснение и применение классов, композиции, ссылок и поверхностной копии, а в 36.1 — самостоятельная работа с `Task` и договором `JsonStorage.load/save`; фактическое освоение проверить перед выдачей. Новичку здесь нужны отдельные различающие примеры для `None`/`[]`, трёх границ копирования списка и общей ссылки на `Task`, затем сравнение операций в памяти и JSON. Диапазон покрывает эти механизмы и проверку прогноза без повторного курса ООП/JSON, наследования и транзакций.

**Темы в порядке изучения:**

1. Совместимость поведения важнее общего предка; одинаковые названия недостаточны без совпадения типов и ошибок.
2. Начальный набор опционален, None отличается от переданного контейнера. MemoryStorage хранит копию внешнего списка.

4. Task внутри остаются общими объектами: вызов mark_done на загруженной Task может быть виден сразу. Не обещать глубокую копию или rollback.
5. Память полезна для быстрых изолированных проверок, но новый независимый MemoryStorage не восстанавливает завершённую сессию.

Формат самостоятельной практики: **изменение существующего проекта**; оба storage прогоняются через один прикладной сценарий.

**Основная практика, проект:**

1. Добавить MemoryStorage рядом с JsonStorage, не удаляя файловый вариант; использовать один договор list[Task].
2. Проверить внешнюю копию начального контейнера, возвращаемого контейнера и контейнера save. Отдельно показать общую ссылку на Task и объяснить границу защиты.

4. Проверить, что сборка выбирает один storage, не синхронизирует одновременно память и файл и не использует память как второй кеш.

**Выход и переход.** Зависимость заменяема на выполненных действиях. Теперь их координацию можно постепенно собрать в сервисе.

### 37.1. Чтение через сервис

**Основная тема и назначение.** Дать сервису конкретную роль и начать с не меняющих данные сценариев. Не создавать новый CRUD ради названия класса.

**A.** Оба storage работают, переходные функции читают актуальный набор; Task и алгоритмы готовы.


Статус A: **планируется** из 36.1 и 37; источники — паспорта этих занятий и COURSE §4. Условие проверки: ученик самостоятельно использует оба storage с одними и теми же storage-aware операциями и объясняет общий договор до переноса чтения.
**B.** PlannerService(storage) предоставляет list_tasks/get_task/search_tasks/get_statistics. Читающие команды используют его, статистика имеет целевой договор all/open/done.

**Темы в порядке изучения:**

2. Одно действие читает актуальные Task, не сохраняет и не просит input. Get отличается от низкоуровневого find по отказу.
3. Перенос алгоритма и изменение публичного договора отдельно: TaskNotFoundError, [], all/open/done. Прикладной id проверяется прежним валидатором до поиска: неверный тип/неположительное значение даёт ValueError, допустимый отсутствующий номер даёт TaskNotFoundError. Bool не принимается как id 1/0.
4. Процент берётся из новой сводки, для пустого набора 0.0; знакомый вывод CLI не должен сломаться из-за старых ключей.
5. Переходный смешанный этап допустим только с точной границей: читающие команды через service, изменения ещё через прежние функции, оба используют **один и тот же объект storage**.

Формат самостоятельной практики: **изменение существующего проекта**; переходные функции и команды проверяются на памяти и JSON.

**Основная практика, проект:**

1. Добавить сервис и перенести четыре алгоритма чтения из существующих операций, не писать вторые циклы поиска/статистики без причины.

3. Один раз перейти от total/completed/left к all/open/done, обновить расчёт процента и вывод всех потребителей.
4. На этом шаге явно передавать CLI service и тот же storage для ещё не перенесённых изменений. Временное подключение описать, не прятать запись за service.storage или вторым экземпляром памяти.
5. Проверить пустую/непустую сводку, неизвестный id, поиск и чтение после изменения, выполненного прежним путём. Чтение не вызывает save.

**Предпочтительный объём будущей учитываемой видимой TSX-теории:** 1400–1800 слов (от начала `00` до обзора практики, не включая обзор; объясняющую обратную связь интерактивов учитывать один раз, практику не квотировать). **Основание:** `Task`, `load/save`, два storage и прежние алгоритмы уже подготовлены в занятиях 36–37 (факт освоения проверить перед выдачей); новичку здесь нужны различающие примеры взаимодействия объектов, актуального чтения, отказов `get_task`, пустого поиска, `all/open/done` и временной связи CLI с одним storage, без повтора основ ООП/JSON и преждевременного переноса изменений.

### 37.2. CLI вызывает сервис

**Основная тема и назначение.** Завершить рабочий продукт до введения тестов и финальной приёмки. Delete является единственной новой пользовательской операцией этого шага.
