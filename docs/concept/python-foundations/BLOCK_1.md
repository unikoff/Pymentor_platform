# Блок 1. Первый код, инструменты, история и данные

Концепт следует [общей карте Python Foundations](COURSE.md) и [методичке для концептов блоков](../BLOCK_CONCEPT_AUTHORING.md). Он задаёт маршрут первого блока; материалы занятий синхронизируются с паспортами. Первую публикацию выполняют по инструкции в локальном занятии, её устройство разбирают на следующем шаге.

## 1. Назначение, контекст, A → B и границы блока

### Назначение

Дать новичку первые самостоятельные действия и понятные объяснения к ним: выполнить короткую программу, перенести её на свой компьютер, сохранить историю, получить проект из GitHub и перейти от готового текста к значениям и вычислениям.

Основной вопрос блока: как превратить понятное намерение в небольшой работающий файл и доказать, что именно этот файл выполняется, изменяется и сохраняется?

### Точка A

- Программного проекта и истории Git ещё нет. Не предполагаем ранее написанный код, установленный Python или опыт терминала.
- Ученик умеет пользоваться обычными окнами компьютера и браузером, но расширение файла, текущую папку, команду и интерпретатор ещё нужно объяснить.
- Обзор курса мог показать цель Console StudyHub Planner. Это ориентация, а не освоенные переменные, функции или Git.
- Возможность самостоятельно пройти занятия не должна зависеть от того, что наставник расшифрует команду, настроит запуск или объяснит неожиданное слово.

Это A первого блока из COURSE.md. Не переносим сюда знания, которые появятся только в конце главы.

### Точка B

Ученик:

1. Пишет небольшой прямолинейный Python-код и объясняет его выполнение, вывод и простую ошибку.
2. Запускает сохранённый `main.py` из правильной папки выбранным Python; отличает код файла от команд терминала.
3. Различает значение, имя и четыре базовых типа; понимает переприсваивание и порядок использования имён.
4. Получает текст через `input`, явно преобразует подходящий числовой текст и выполняет простую арифметику.
5. Разделяет сохранение файла, подготовку изменений, локальный коммит и отправку истории. Может прочитать status/diff и выбрать следующий шаг.
6. Имеет один проект, локальную историю, опубликованную копию и проверенный clone той же истории.
7. Может самостоятельно изменить знакомую часть программы, проверить результат и сохранить осмысленную версию.

Выход проекта: один `studyhub-console/main.py`, `.gitignore` и история. Файл показывает понятный стартовый экран, использует именованные значения и рассчитывает учебное время. Это начало будущего Planner, **не готовое приложение для хранения задач**.

К следующему блоку передаются запуск, базовые значения, текстовый ввод и вычисления. Строковые методы, сравнения, ветвления и циклы ещё не изучены. Копия из GitHub не является отдельным новым проектом.

### Границы содержания

Вводим `print`, комментарий, базовую запись текста, имена, `str/int/float/bool`, `type`, арифметику, `input`, `int/float/str`, первые сообщения об ошибках, локальные инструменты, простое окружение и Git одного автора.

Не требуем `def`, `return`, `solve`, словари, списки задач, индексы, f-строки, строковые методы, `if`, циклы, обработчики, исключения через `try/except`, JSON, классы или тестовые библиотеки. Знакомство с готовой функцией `print` не означает умение определять собственную функцию.

Название текущей ветки нужно для отправки истории. Создание нескольких веток, merge-конфликты, rebase, pull requests, переписывание истории и релиз не входят в B блока.

### Накопление одного результата

- В первом занятии код выполняется в платформе. В локальном шаге его переносят один раз, не создают другую программу с несвязанными строками.
- Затем развивается тот же `main.py`. Небольшие изменения текста и комментариев в Git-занятиях используют только уже знакомый Python.
- Введение переменных заменяет повторяющиеся литералы понятными именами. Это улучшение существующего экрана, не новый пустой файл.
- В вычислениях к нему добавляется небольшой расчёт учебного времени. Он ещё не изображает настоящую статистику отсутствующих задач.
- Проверочный clone хранит ту же историю и подключён к тому же remote. Писать новые возможности продолжают только в исходной рабочей папке.

### Рабочая структура к концу блока

```text
studyhub-console/
  main.py       # стартовый экран, значения и вычисление времени
  .gitignore    # исключения восстановимых/служебных файлов
  .git/         # история, которой управляет Git
  .venv/        # локальное окружение, не часть коммитов
```

Для уже начатого прохождения сохраняются фактические имя папки и история. Не заставлять переносить работу в `python-block-1`, удалять чужие файлы или пересоздавать `.git`. README готового приложения, пакеты проекта и несколько Python-модулей пока не нужны.

### Правила распределения практики

Основная Git-практика выполняется с реальными файлами и Git. Разбор готового status/diff поддерживает её, но не заменяет создание и чтение своей истории. Python-редактор платформы не считается доступом к терминалу компьютера ученика.

В Python-исследованиях допустимы короткие отдельные запуски редактора. В устойчивый `main.py` входят понятные рабочие изменения; намеренно сломанные примеры исследуются отдельно или исправляются до сохранения проверяемой версии.

Определения функций, невидимые импорты и новый синтаксис не должны быть ценой автопроверки. Если данные выдаёт платформа, это явно указано. Если задача требует ввода пользователя, это отдельный локальный сценарий с объяснённым `input`.

## 3. Подробные паспорта занятий

### 1. Как Python выполняет программу

**Основная тема и назначение.** Различить текст программы, его выполнение и результат. Первый успех должен состоять из понятного действия, а не из предварительной настройки нескольких инструментов.

**Точка A.** Ученик не писал код. Есть доступ к материалу и редактору платформы; местная установка Python ещё не требуется.

**Точка B.** Ученик самостоятельно пишет несколько `print`, предсказывает их порядок, объясняет роль кавычек и комментария, находит одну простую ошибку и снова получает ожидаемый вывод.

**Необходимые темы, в порядке изучения:**

1. Программа как точная инструкция исполнителю. Отделить написанное намерение от того, что реально задано кодом; использовать небольшую бытовую аналогию, не требуя знания компьютера изнутри.
2. Python как язык и интерпретатор как программа, выполняющая этот язык. Кнопка платформы запускает подготовленную среду; это ещё не доказывает установку Python на компьютере ученика.
3. Готовое действие `print`: слово, круглые скобки, передаваемый текст и наблюдаемый вывод. Назвать его готовой функцией без требования определять собственную.
4. Прямые кавычки задают границы текста. Кавычки в записи не появляются в выводе; текст без кавычек рассматривается как имя. Не требовать полной темы переменных для исправления такого случая.
5. Последовательность простых инструкций, переход на следующую строку и завершение после последней. Перестановка меняет результат; Python не восстанавливает задуманный порядок.
6. Комментарий `#`, пустая строка кода и пустая строка вывода. Показать различие, не объявляя комментарий исполняемой командой.
7. Одна синтаксическая ошибка и одна ошибка при выполнении. В прямолинейном скрипте SyntaxError может помешать начать выполнение, а NameError остановить его после уже выполненных строк. Не обобщать это на любые динамически исполняемые программы.
8. Как прочитать сообщение: найти последнюю строку и соответствующий фрагмент, исправить одну причину и запустить снова. Полная теория traceback появится позже.

**Основная практика.** Короткие исследования и собственная программа в редакторе, без `def solve`, `return`, имён переменных и системных команд внутри Python-кода.

- Начать с одного своего текстового сообщения. После запуска изменить только текст и проверить, что изменился именно вывод.
- До запуска предсказать результат трёх знакомых `print`, затем поменять местами две строки и объяснить разницу.
- Закомментировать одну строку, предсказать оставшийся вывод, вернуть её. Исследование не выполняется одновременно с карточкой, проверяющей строгие три строки.
- Найти и исправить по одной ошибке в отдельных примерах: типографские кавычки, незакрытая скобка либо слово без кавычек. Не требовать поиска трёх разных причин в первом самостоятельном запуске.
- Написать стартовый экран из трёх строк: StudyHub, Начинаем обучение, Программа запущена. Это основа, которую следующий шаг переносит в локальный файл.

**Проверяемый результат.** Точный экран написан самим учеником; он может заранее назвать порядок и объяснить, почему одна строка исчезла после комментария. Правильный вывод не получен фиксированной готовой оболочкой функции.

**Выход и переход.** Есть рабочий короткий код и понимание запуска в платформе. Дальше нужно сохранить и выполнить именно его на своём компьютере; не считаем локальные инструменты уже установленными.

### 2. Терминал, репозиторий и первый запуск своего проекта

**Основная тема и назначение.** Перенести знакомую программу на компьютер и сразу сохранить её в собственном проекте на GitHub. Главная изучаемая механика: файл, текущая папка, интерпретатор и окружение.

**Точка A.** В платформе работает стартовый экран из трёх print. Установка Python, редактор, PowerShell, Git и учётная запись GitHub ещё не подготовлены.

**Точка B.** Репозиторий создан до main.py. Файл выполняется локально и Python из .venv; исходник и .gitignore закоммичены и отправлены в свою ветку GitHub. Ученик подтверждает файл и идентификатор коммита в браузере. Выполненные Git-команды пока не считаются понятыми.

**Необходимые темы и действия, в порядке изучения:**

1. Роли Проводника, редактора, PowerShell и Python. Код пишут в файле, команды вводят в терминале.
2. Проверка или установка Python по актуальной инструкции, один основной редактор и Git for Windows с Git Credential Manager. После установки открыть новый терминал и проверить версии.
3. Войти в GitHub, создать один пустой репозиторий studyhub-console без README, .gitignore и лицензии, скопировать его HTTPS-адрес.
4. Создать локальную папку проекта, перейти в неё и выполнить git init -b main до создания main.py. Задать локальные имя и email автора. Для продолжающего ученика сохранить существующую папку, ветку, историю и remote.
5. Создать main.py в этом корне, перенести знакомый экран из платформы, сохранить в UTF-8. Объяснить имя файла, расширение и скрытое .txt.
6. Get-Location, Get-ChildItem и Set-Location, затем pwd/dir/cd. Раскрыть относительный путь, кавычки в абсолютном пути и команду python main.py.
7. Исследовать неправильную папку и сохранённую версию текста. Исправлять путь и сохранение файла; проект заново не создавать.
8. Создать .venv, запустить её Python напрямую и выбрать его в редакторе. Активация необязательна; при блокировке использовать .\.venv\Scripts\python.exe main.py.
9. Создать .gitignore по готовому содержимому, затем выполнить готовую последовательность status/add/commit/remote/push. Завершить вход в браузере при первом push, включая второй фактор, если он включён.
10. Проверить свою ветку на GitHub, main.py, .gitignore и совпадение commit ID с git rev-parse HEAD. .venv остаётся на компьютере.

**Особенность этого занятия.** По решению автора курса Git здесь используется как готовая пошаговая инструкция. Дать команды и точные действия с окнами авторизации, без объяснения устройства Git, staging, remote и флагов. Их смысл раскрывается в следующем занятии на уже выполненном опыте. Для Python, пути и окружения полноценное объяснение сохраняется. Это исключение для первого запуска, а не общий принцип авторинга.

**Основная практика.**

- Подготовить инструменты и создать свой репозиторий перед main.py.
- Перенести прежний экран, подтвердить локальный запуск и исправить запуск из родительской папки.
- Создать и выбрать .venv, повторить запуск тем же файлом.
- По готовым командам записать и отправить исходник и .gitignore; завершить авторизацию.
- Найти фактический коммит и его файлы в собственной ветке GitHub. Одна ссылка или успешный вход не заменяют проверку отправки.

**Проверяемый результат.** Один проект запускается локально и опубликован с первым рабочим коммитом. Папка окружения не включена. Ученик объясняет локальный запуск, но ещё не обязан объяснять Git-команды.

**Выход и переход.** Передаются main.py, .venv, .gitignore, локальная история, origin, ветка и опубликованный коммит. Следующее занятие разбирает, что именно сделали команды, и позволяет повторить цикл осознанно.

### 3. Git и GitHub: разбор первой публикации

**Основная тема и назначение.** Объяснить уже выполненный путь от создания репозитория до публикации. Перейти от готовой инструкции к самостоятельному выбору следующего действия.

**Точка A.** У ученика есть запускаемый main.py, .venv, .gitignore, первый локальный и опубликованный коммит, настроенный origin и выполненная авторизация. Он пользовался Git по рецепту, но ещё не понимает устройство истории.

**Точка B.** Ученик объясняет роли каждого действия и самостоятельно сохраняет следующую знакомую правку: запуск, status/diff, add, staged diff, commit, push и проверка нового коммита на GitHub. Исходная история продолжается.

**Необходимые темы, в порядке изучения:**

1. Вспомнить выполненную публикацию. Git хранит локальную историю; GitHub хранит отправленную историю. Python отдельно запускает main.py.
2. Создание проекта на GitHub и git init в локальном корне. Init создаёт .git, не устанавливает Python и не публикует файл. main — имя начальной ветки.
3. Имя и email автора относятся к подписи коммита. Авторизация через Git Credential Manager разрешает отправку на GitHub; эти действия уже выполнены и не настраиваются повторно без причины.
4. Разделить сохранение файла, подготовку и коммит. git add выбирает содержимое на момент команды, а git commit записывает подготовленное содержимое в локальную историю.
5. Понять назначение .gitignore и правила для .venv/, __pycache__/ и *.pyc. Правило не удаляет файл и не перестаёт отслеживать уже записанный файл.
6. Использовать базовые проверки: git status перечисляет состояния файлов; git diff показывает рабочую правку относительно индекса; git diff --staged показывает выбранное содержимое относительно последнего коммита. Подробные комбинации статусов и правку после add разбирает следующий шаг.
7. Читать сообщение, ID и git log --oneline. Коммит содержит подготовленное содержимое, а не все изменения автоматически. Чистый status не проверяет программу.
8. Проверить HTTPS-адрес, origin и имя локальной ветки. git push -u origin main отправляет коммиты и запоминает upstream; адрес и связь уже настроены.
9. Проверить результат в браузере: владелец, репозиторий, ветка, commit ID и содержимое main.py. Сохранение, локальный коммит и публикация дают разные результаты.

**Основная практика.**

- По своей истории, remote и .gitignore объяснить действия предыдущего занятия. Ответ сформулировать самостоятельно.
- Изменить одно знакомое сообщение в существующем main.py, сохранить и запустить. Новые конструкции Python не требуются.
- Просмотреть status и оба diff на соответствующих этапах, выбрать main.py и проверить подготовленную строку.
- Создать следующий коммит. До push проверить, что GitHub показывает прежнюю опубликованную версию.
- Отправить новую запись и сопоставить идентификатор и текст на GitHub с локальной версией. Первый коммит сохранить.

**Проверяемый результат.** Есть объяснение первой публикации и следующая рабочая версия в той же локальной и удалённой истории. Ученик различает подпись и вход, файл и коммит, commit и push; окружение исключено.

**Выход и переход.** Базовый полный цикл понятен и повторён. В части о состояниях исследуем правку после add и снятие подготовки; в части о remote углубляем диагностику существующей отправки.

### 3.1. Состояния файлов, staging и diff

**Основная тема и назначение.** Выбирать, какую версию записать, на основании состояния, а не запомненной последовательности команд. Новое здесь: разные версии одного файла и границы сравнения.

**Точка A.** Есть начальный и следующий опубликованный коммит, ignore и знакомый полный цикл. Здесь углубляются локальные состояния.

**Точка B.** Ученик объясняет untracked/modified/staged, различает рабочий и подготовленный diff, прогнозирует правку после add и может снять подготовку без потери рабочего текста. История продолжается проверенной версией.

**Необходимые темы, в порядке изучения:**

1. Отслеживаемый файл и новый untracked. Сохранение через редактор не включает новый файл в историю; состояние ignore отличается от отсутствия файла на диске.
2. Для уже отслеживаемого файла различить неизменённый, изменённый рабочий текст и подготовленные изменения. Файл может одновременно иметь staged и unstaged правки, а не находиться всегда в одном из четырёх взаимоисключающих состояний.
3. Add фиксирует выбранное содержимое на момент подготовки, не «прикрепляет живой файл». Правка после add не попадает автоматически в следующий коммит.
4. `git diff` сравнивает рабочий вариант с подготовленным, `git diff --staged` подготовленный с последним коммитом. Знак плюс/минус показывает изменение строки, не оценку её качества. Обычный diff не является просмотром содержимого всех untracked-файлов.
5. Читать путь, контекст и изменённые строки. Сначала простая замена знакомого сообщения, затем комментарий; не применять здесь неизвестный Python ради интересного diff.
6. При пустом diff решить, что уже подготовлено, что не изменено или что ещё не отслеживается, сверив status. Пустое сравнение само по себе не доказывает потерю правки.
7. `git restore --staged main.py` после уже существующего первого коммита снимает подготовку и сохраняет рабочий текст. Отличить от restore без этого флага, которое может потерять незаписанные правки; destructive restore не является обязательным опытом.
8. Проверка программы, выбранный набор, осмысленная цель и новый коммит. Не требовать одинаковой фразы сообщения, если ученик понятно назвал реальное изменение.
9. Новая запись истории и незаписанная правка являются разными результатами. Новая версия не гарантирует, что все текущие изменения вошли в неё.

Состояния сверяются с [Pro Git: запись изменений](https://git-scm.com/book/en/v2/Git-Basics-Recording-Changes-to-the-Repository), безопасное снятие подготовки с [git restore](https://git-scm.com/docs/git-restore), граница ignore с [gitignore](https://git-scm.com/docs/gitignore). Это техническая опора автора, а не поручение ученику искать объяснение в документации.

**Основная практика.** Контролируемый опыт на `main.py` в той же истории; небольшие разборы готового вывода поддерживают самостоятельное действие.

- До редактирования назвать текущую версию по log. Изменить одну знакомую строку, проверить Python-вывод и прочитать рабочий diff.
- Подготовить файл и предсказать, какое сравнение станет пустым, а какое покажет правку. Проверить оба и status.
- Добавить вторую небольшую рабочую правку после add. До коммита определить, какая из двух войдёт в историю сейчас; проверить различие двух diff. Не считать слово modified достаточным объяснением.
- Снять подготовку только этого файла и убедиться, что обе правки остались на диске. После выбора нужного итогового содержимого вновь подготовить, проверить и сохранить рабочую версию.
- Повторить уже без полного списка команд: изменить знакомый комментарий, проверить и записать следующую осмысленную версию. Это шаг уменьшения поддержки, не повтор инициализации.
- Разобрать status для untracked, modified, staged и staged+modified; сопоставить состояние со следующим действием. Untracked можно исследовать на подготовленном примере, не создавая лишний пустой файл в постоянном проекте.
- По одному неправильному выводу объяснить, почему commit ничего не записал или почему новая рабочая строка не оказалась в сохранённой версии. Решение должно опираться на фактическое состояние.

**Проверяемый результат.** Есть продолжение истории, рабочие правки не потеряны. Ученик правильно прогнозирует содержание будущего коммита после правки уже staged-файла и отличает снятие подготовки от стирания текста. Точное количество учебных сообщений не заменяет эти проверки.

**Выход и переход.** Локальный цикл теперь осознанный. Следующий шаг отправляет именно эту историю в удалённый репозиторий, а не создаёт другой проект или вручную загружает файлы через браузер.

### 3.2. GitHub, remote, авторизация и push

**Основная тема и назначение.** Опубликовать существующие версии и доказать, что удалённая копия соответствует коммиту, а не несохранённому состоянию редактора.

**Точка A.** Рабочий проект, основная ветка и несколько локальных коммитов уже есть. Понятны staged/unstaged, выбор содержимого и сообщения истории. Remote, авторизация и upstream настроены при первом локальном запуске; следующий полный цикл уже объяснён и выполнен.

**Точка B.** Проверены существующие remote и upstream; следующая версия отправлена и найдена на GitHub. Ученик отделяет идентичность автора от права отправки, локальный коммит от опубликованного и вывод status от реального состояния сервера.

**Необходимые темы, в порядке изучения:**

1. Удалённая копия позволяет получить версии с другого места и показать результат. Она не запускает приложение и не получает каждую правку редактора автоматически.
2. Учётная запись, видимость репозитория и авторизация. Имя автора/email в Git не дают права push; приватность проекта и email осознанно выбирается до публикации.
3. Почему при первой публикации создали пустой репозиторий для подключения локальной истории. Автоматически добавленный README/ignore создаёт другую начальную историю; для первого опыта её не создавать. Если репозиторий уже непустой, не требовать force или внезапного разрешения конфликтов.
4. HTTPS-адрес, заменяемые поля примера и локальное имя remote `origin`. Origin является сохранённым адресом, а не GitHub-паролем, веткой или папкой.
5. Проверка `git remote -v`, владельца и имени проекта. Новый адрес связывается один раз; если origin уже существует, сначала прочитать его, не повторять add и не удалять настройки наугад.
6. Локальная `main`, удалённая ветка и связь upstream. На первом push объяснить смысл `-u` как запоминания направления для последующих отправок, а не изучать полную модель ветвления.
7. Один основной путь HTTPS-авторизации через credential manager с браузерным входом. Автору нужно объяснить ожидаемые окна и завершение входа; обычный пароль аккаунта не подставляется в Git HTTPS. Токены и SSH не изучаются как обязательные параллельные маршруты.
8. Push отправляет уже созданные коммиты. Незакоммиченная правка не окажется на GitHub; успешный вход ещё не доказывает завершившуюся отправку.
9. Подтверждение результата: сообщение об успешной отправке, ветка на GitHub, идентификатор нужного коммита и содержимое файла. Чистый status может быть при неотправленных коммитах.
10. Ошибки адреса, прав, авторизации, отсутствия коммитов или upstream различаются. Не исправлять все одинаковым force-push и не просить прикладывать credentials к доказательству.

Способы входа сверяются с [официальной документацией GitHub](https://docs.github.com/en/authentication/keeping-your-account-and-data-secure/about-authentication-to-github). Remote и направление отправки с [Pro Git: удалённые репозитории](https://git-scm.com/book/en/v2/Git-Basics-Working-with-Remotes). Будущий урок должен содержать объяснение и безопасный путь первого входа прямо на платформе.

**Основная практика.** Публикация того же проекта и проверка двух разных моментов его истории.

- Проверить видимость, автора/email и существующий репозиторий studyhub-console. Новый проект не создавать.
- Прочитать уже сохранённый HTTPS-адрес через remote -v и проверить направление отправки основной ветки.
- Проверить настроенный upstream; при необходимости завершить повторную авторизацию. Отправить следующую версию и проверить нужную ветку, историю и main.py.
- В исходной папке изменить только знакомое сообщение или комментарий. До commit/push предсказать, что сейчас видно локально и что пока останется на GitHub.
- Сохранить проверенную локальную версию; показать, что отсутствие рабочих изменений не равно публикации. Отправить её обычным push и подтвердить новый идентификатор/текст на GitHub.
- Разобрать сообщения «origin уже существует», «нет upstream» и «нет доступа». По каждому назвать проверяемую настройку; не требовать специально портить реальную авторизацию.

**Проверяемый результат.** На GitHub видна ожидаемая ветка и новый фактический коммит, исходный проект не заменён другим. Ученик объясняет момент появления правки в интернете; документы/скриншоты не содержат токенов и других секретов.

**Выход и переход.** Есть проверенная удалённая история. Дальше нужно получить её заново и выполнить файл независимо от исходного каталога. Само наличие ссылки ещё не доказывает эту возможность.

### 3.3. Clone и получение своего проекта заново

**Основная тема и назначение.** Проверить, что публикация содержит нужный код и историю, а локальные инструменты можно восстановить. Дополнительно увидеть линейное обновление копии без обучения конфликтам.

**Точка A.** Есть опубликованная версия, один remote, рабочий локальный проект и `.venv`. Ученик уже знает путь, запуск и commit/push, но clone/fetch/pull ещё необходимо объяснить.

**Точка B.** Чистая проверочная копия получена из того же remote, работает на своём окружении и принимает линейное обновление. Ученик различает скачанную историю и обновлённые рабочие файлы; единственный основной каталог разработки сохранён.

**Необходимые темы, в порядке изучения:**

1. Clone получает репозиторий с исходными файлами и историей; это не init ещё одного несвязанного проекта и не перенос папки Проводником.
2. Исходный рабочий каталог и проверочная копия. Проверочную папку разместить рядом, не внутри исходного репозитория; перед каждым действием назвать активный путь.
3. Clone настраивает origin и получает основную ветку удалённого проекта. Имя проверочной папки на компьютере не меняет адрес remote.
4. Исходный код и восстановимые инструменты. Ignore и отсутствие `.venv` после clone означают ожидаемое исключение; нельзя считать окружение частью опубликованного кода или копировать его между каталогами.
5. Создание окружения по уже освоенному способу и запуск именно файла clone. Совпадение запуска проверяется по сохранённому коду/идентификатору, а не по открытому рядом старому терминалу.
6. История сервера, сведения о ней в копии и рабочая версия могут отличаться. Status использует известные локально сведения; без обращения к серверу не обещает актуальность remote.
7. Fetch получает сведения об удалённой истории, не применяет их к рабочему файлу. Pull получает и интегрирует обновление; в нашем опыте используется `--ff-only` для продолжения без расходящихся локальных коммитов.
8. Fast-forward объяснить как продвижение по уже существующей единственной линии. Если линии разошлись, команда отказывает: конфликты, merge и force не становятся неожиданным дополнительным заданием.
9. Не удалять исходную папку ради доказательства восстановления. Не начинать параллельно писать возможности в двух клонах; проверочная копия не меняет основную опору следующего занятия.

Получение и ограничения обновления сверяются с [Pro Git: remotes](https://git-scm.com/book/en/v2/Git-Basics-Working-with-Remotes) и [git pull](https://git-scm.com/docs/git-pull). В уроке не полагаться на меняющиеся defaults pull: объяснить выбранный явный режим.

**Основная практика.** Один независимый запуск и контролируемое обновление копии.

- Предсказать, какие файлы появятся после clone и чего не будет. Из родительского каталога клонировать свой remote в соседний `studyhub-console-check`; исходный проект сохранить.
- Проверить путь, origin, ветку и последний идентификатор. Сравнить их с опубликованной версией; не выполнять init внутри clone.
- Создать окружение именно проверочной копии и запустить её `main.py`. После выбора другой папки редактор не должен незаметно запускать старый файл.
- Вернуться в основной каталог, изменить знакомое сообщение стартового экрана, проверить новый вывод Python, сделать и отправить коммит. В проверочной копии новых локальных коммитов/правок не создавать. Для этого опыта выбрать видимую правку, а не только комментарий, чтобы последующее обновление можно было проверить и по запуску.
- До обновления сравнить новый серверный текст со старым файлом clone. Выполнить fetch; проверить известное отставание по status/log, убедиться, что рабочий текст и запуск ещё прежние.
- Выполнить pull в явно объяснённом fast-forward-режиме. Проверить новый идентификатор и новый вывод; не делать дополнительный коммит только за скачивание уже созданной версии.
- Разобрать ошибку «папка назначения не пуста» и «нет доступа». Не удалять содержимое существующей папки и не публиковать приватный проект автоматически ради доступности.
- Вернуться к исходной рабочей папке. Назвать, где продолжится проект и почему проверочный clone не означает новый продукт.

**Проверяемый результат.** Копия получена без файлов исходной папки и выполняется своим интерпретатором. До pull рабочая версия не изменилась от одного fetch, после pull совпадает с опубликованной. В обоих каталогах продолжена одна история, а не два независимо инициализированных проекта.

**Выход и переход.** Получение исходников подтверждено, Git-цикл завершён. Дальше Python-файл в основном проекте получает переменные; новые правки уже можно проверять, сохранять и публиковать знакомым способом.

### 4. Переменные и базовые типы

**Основная тема и назначение.** Связать понятные имена с текущими значениями, чтобы управлять данными вместо многократного повторения литералов. Git служит освоенным средством фиксации, не новой темой этого занятия.

**Точка A.** Ученик знает текст в кавычках, вывод, порядок выполнения, локальный запуск и сохранение версии. Присваивание и типы ещё не изучены; списков задач и условий нет.

**Точка B.** Ученик объявляет и читает имена, переприсваивает значения, выбирает `str/int/float/bool`, исследует тип и различает имя от буквального текста. Стартовый экран своего файла использует понятные переменные.

**Необходимые темы, в порядке изучения:**

1. Когда повторяемый текст и безымянные значения мешают изменению программы. Переменная нужна для смысла данных и их использования, а не ради заполнения обязательной таблицы.
2. Значение справа, имя слева и действие присваивания. Имя связывается со значением; коробка является входной аналогией, а не обещанием независимого копирования любых будущих объектов.
3. Присваивание не печатает. `print(name)` получает текущее значение, `print("name")` обычный текст. Связать это с уже знакомыми кавычками.
4. Определение до использования и последовательность выполнения; опечатка, регистр и NameError. Не вводить область видимости функций, которых ещё нет.
5. Переприсваивание и чтение текущего значения в каждой точке. Ранее присвоенные данные не превращаются в автоматический журнал программы; историю исходного кода при этом хранит Git.
6. Четыре типа через реальные роли: текст, количество, дробная величина, признак да/нет. `5` и `"5"`, True и `"True"`, точка в дробном литерале имеют разный смысл.
7. Понятные имена, snake_case, допустимое начало, пробелы/дефис и резервирование имён готовых действий. Не называть переменную `print` или `type`, чтобы не ломать уже изученные инструменты.
8. `type(value)` как готовая диагностика с понятным результатом; вложенный вызов сначала получает обозначение типа, затем передаёт его `print`. Запись `.__name__` и устройство атрибутов не являются обязательной самостоятельной целью.
9. Платформа может заранее задать source-имена. Их значение надо прочитать, а не заменить константой из примера; это не пользовательский `input` и не скрытые созданные задачи.

**Основная практика.** Исследование значений в редакторе плюс реальная правка основного файла.

- До запуска предсказать результат нескольких присваиваний и двух чтений одного имени. После изменить только последнее присваивание и объяснить, что осталось прежним.
- Найти ошибку в печати имени внутри кавычек, использовании до объявления и несовпадающем регистре. Исправлять примеры по одному, не требуя первого самостоятельного разбора трёх сбоев сразу.
- Создать значения четырёх типов и самостоятельно объяснить выбранный смысл. Прочитать вывод `type` и различить внешне похожий числовой текст/число и текстовый/логический флаг.
- В поддерживающей карточке получить заданные платформой `source_title/source_priority/source_progress/source_done`, присвоить свои `title/priority/progress/is_done`, вывести и объяснить значения/типы. Не строить здесь словарь задачи и не подставлять фиксированный ожидаемый вывод.
- В своём `main.py` дать имя названию проекта и использовать его в стартовом экране; добавить `version`, `progress_percent`, `is_ready` как явно учебные метаданные. Процент пока задаётся вручную и не обещает статистику ещё не созданных задач.
- Изменить одно значение, предсказать вывод и подтвердить запуском. Зафиксировать проверенную правку обычным Git-циклом в исходной рабочей папке, без нового репозитория.

**Проверяемый результат.** Ученик самостоятельно читает текущее значение, не печатает имя вместо данных и может отличить четыре типа без обязательной непрозрачной записи. Изменение названия в одном месте меняет его повторные использования в программе. Условий и вычисляемого прогресса для этой приёмки не требуется.

**Выход и переход.** Появилась опора для вычислений: имена имеют значения и типы. Следующий шаг объясняет операции и ввод, а не впервые спрашивает, что значит имя без кавычек.

### 5. Числа, вычисления и преобразование ввода

**Основная тема и назначение.** Записать понятное числовое правило и применить его к разным значениям, включая текст из настоящего ввода. Расчёт учебной сессии поддерживает будущий Planner, но ещё не является его предметной статистикой.

**Точка A.** Понятны имена, присваивание, типы, `print`, локальный запуск и Git. `input`, арифметика и преобразования должны быть объяснены до самостоятельной практики; проверки через `if` ещё не доступны.

**Точка B.** Ученик переводит словесное правило в арифметику, различает три вида деления, получает строку ввода, явно преобразует её и вычисляет результат. Может объяснить неподходящий тип/содержимое и деление на ноль, не скрывая ошибки.

**Необходимые темы, в порядке изучения:**

1. Операция получает значения и даёт новое значение; присваивание связывает результат с именем. Начать с `+`, `-`, `*`, `/`, знакомых количеств и единиц измерения.
2. Правило словами и промежуточные имена. Количество занятий умножается на минуты одного занятия; один запланированный перерыв добавляется отдельно, не за каждое занятие по неозвученному правилу.
3. Скобки и порядок действий, общий итог против деления только последнего слагаемого. Ошибочная формула может выполняться без сообщения Python.
4. Правую часть вычисляют до переприсваивания, например при увеличении счётчика. Здесь разобрать такой пример из прежнего урока переменных, после знакомства с `+`.
5. `/` для обычного деления, `//` для целой части и `%` для остатка. На неотрицательных минутах объяснить полные часы и остаток; не сводить `//` в общем случае к отбрасыванию знака/дроби при отрицательных числах. Проценты и знак остатка не одно и то же.
6. Тип результата: обычное деление целых даёт float, а целые положительные минуты и делитель 60 позволяют получить целые часы/остаток. Не требовать искусственно получать денежную точность через float.
7. `input` показывает приглашение, ждёт ввод и возвращает строку. Enter и завершение ввода не являются строкой Python-кода; числовая запись в поле не меняет str на int автоматически.
8. `int`, `float`, `str`, промежуточная переменная для сырого ввода. Преобразование создаёт результат, а не тайно меняет исходный текст. Строковая запись дроби использует точку; преобразование числового float к int не заменяет правильную обработку произвольного текста.
9. Сравнить соединение двух строк через `+` со сложением двух чисел. Смешанные str/int не приводятся автоматически; `bool` вводить в сложное преобразование здесь не нужно.
10. TypeError, ValueError, ZeroDivisionError как разные причины. Исправить конкретный вход/тип/делитель и снова проверить. `try/except`, проверка диапазона и повторный запрос появятся позже; ошибки нельзя скрыть заданием «не должно падать на любом вводе».
11. Роль платформенных входных переменных: в автопроверке они меняются без `input`, а локальный пользователь вводит через терминал. Одна формула применима в обоих случаях; процессы получения входа различаются.

**Основная практика.** Сначала небольшие исследования в редакторе, затем расчёт в своём `main.py` без функций и ветвления.

- Проговорить две числовые формулы и предсказать результат с разным расположением скобок. Найти пример, который выдаёт неправильное число без traceback, исправить только причинную часть.
- В поддерживающем задании использовать имеющиеся `raw_lessons`, `minutes_per_lesson`, `break_minutes`: преобразовать количество занятий и получить учебные/общие минуты. Значения приходят от платформы; подменять их своими нельзя.
- Дополнить исследование делением общего времени на полные часы и остаток. Проверить минуты 0, 59, 60, 61 как входы отдельного короткого опыта, не заменять ими накопленные данные проекта. Ожидания для каждой границы ученик формулирует до запуска.
- В локальном файле сохранить имеющееся название/стартовый экран, получить количество занятий через `input`, преобразовать и рассчитать время. Длительность занятия и один перерыв пока заданы понятными переменными; выводить итоговые минуты, полные часы и остаток отдельными строками, без f-строк из следующего блока.
- Повторить локальный запуск с другим допустимым количеством. При нулевом количестве и нулевом перерыве результат должен быть нулевым; если перерыв задан отдельно ненулевым, он входит в сумму по выбранному правилу, а не исчезает из-за ещё не изученного условия.
- В отдельных примерах прочитать ошибку от смешения str/int, неподходящего текста для int и нулевого делителя. После одного исправления проверить рабочий результат; не оставлять сломанный фрагмент в основном файле.
- Объяснить, почему готовая строка от платформы не является собственным чтением пользователя. Проверить основной файл и сохранить/отправить его новую осмысленную версию.

**Проверяемый результат.** На разных допустимых входах применяется одна формула; нет фиксированного ответа. Для неотрицательного времени остаток меньше 60, часы и остаток восстанавливают исходные минуты. Ученик объясняет, на каком шаге input-текст стал числом, и различает три причины ошибочного примера. Устойчивый ввод любого содержимого пока не обещается.

**Выход и переход.** Один файл теперь использует данные и вычисляет. Следующий блок получает существующий проект и исследует текст, форматирование, сравнения и управление сценарием. Мы не передаём ему готовые условия, методы строк или модель задач как будто они уже изучены.
