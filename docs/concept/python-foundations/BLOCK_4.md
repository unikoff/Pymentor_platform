# Блок 4. Работающий Console StudyHub Planner и передача проекта

Концепт следует [общей карте курса](COURSE.md), [методичке блоков](../BLOCK_CONCEPT_AUTHORING.md) и результатам [блока 1](BLOCK_1.md), [блока 2](BLOCK_2.md), [блока 3](BLOCK_3.md). Здесь определены последовательность, содержание и проверяемые результаты будущих занятий. Это не готовый учебник и не отчёт о внедрении: материалы курса, практика, TSX и код платформы не изменяются.

## 1. Назначение, контекст, A → B и границы блока

### Назначение

Собрать из уже понятных данных, функций и командного сценария первый законченный Console StudyHub Planner. Каждое проектное занятие добавляет одну связанную возможность или одну необходимую гарантию. Финальная работа проверяет накопленный продукт, а не впервые создаёт его.

Основной вопрос: как провести пользовательский ввод через проверку и предметное действие к наблюдаемому результату, сохранив общий список и прежние принятые задачи?

Теорию нужно раскрыть существенно подробнее текущих кратких проектных примеров. Новичку нужны механизм, смысл, границы и разбор причин ошибок. Полный листинг Planner не заменяет объяснение и самостоятельную работу. Небольшие исследования поддерживают основную локальную практику; успешный `solve` сам по себе не доказывает работоспособность приложения.

### Точка A: целевой вход, а не предположение о текущих материалах

После освоения предыдущих блоков есть один основной `studyhub-console`, прежний `main.py`, выбранный Python, локальное окружение, `.gitignore`, репозиторий и remote. У продолжающего ученика сохраняется фактический корень. Новая папка разработки, повторный `git init` и новая история не нужны.

В файле работает промежуточный диалог `calc/exit`: реальный ввод длительностей, расчёт времени и повтор команд. Есть постоянные компоненты:

- `normalize_title(raw_title)` возвращает строку после `strip`, сохраняя регистр и внутренние пробелы; пробельное название превращается в пустую строку.
- `create_task(task_id, title, priority)` получает уже назначенный положительный id, очищенное непустое название и проверенный priority. Возвращает новый полный словарь с `is_done=False`, без ввода, печати, выбора id или добавления в список.
- `format_task(task)` возвращает строку со всеми четырьмя смыслами полей; не печатает и не меняет словарь.
- `calculate_study_minutes(durations)` выделяет уже изученный расчёт. Он не является статистикой задач.

Ученик понимает условия, нормализацию команды, прямой `for`, накопление, `while`, `break/continue`, список словарей, общие ссылки, `def`, параметры, `return`, `None`, локальные имена и диагностику. Знает, что параметр не клонирует объект, а возврат словаря может передать тот же объект.

На входе **нет** принятого пользователем списка задач, назначения id, устойчивого числового запроса, `add/find/done/search/stats`, законченного README и проверки передачи готового Planner. Подготовленные записи из редактора не являются базой приложения.

### Точка B

Ученик самостоятельно запускает и объясняет Planner, последовательно создаёт несколько задач, читает список и конкретную запись, завершает найденную задачу, ищет по названию, получает сводку и штатно выходит. При ошибочном вводе понимает причину отказа и видит сохранность прежних данных.

В том же проекте работают ровно `add`, `list`, `find`, `done`, `search`, `stats`, `exit`. Один список живёт между итерациями одного запуска. Есть проверенные функции, инструкция, осмысленная история и опубликованная версия, воспроизведённая из чистой копии. Ученик способен изменить знакомую часть и проверить, что остальное осталось рабочим.

После выхода пользовательские задачи исчезают. Git сохраняет программу, не значения списка в запущенном процессе. Это ограничение объясняется до первой задачи и подтверждается повторным запуском. Следующая глава развивает тот же результат, а не начинает новый Planner.

### Единый договор данных и поведения

| Часть | Договор всего блока |
| --- | --- |
| Задача | Ровно `id`, `title`, `priority`, `is_done`; полная модель во всех обычных примерах и проверках |
| Id | Положительный int; пустой набор даёт 1, иначе максимум текущих id + 1. Не индекс, не `len + 1`, не последняя позиция |
| Стабильность | Существующие id не меняются при чтении, поиске или завершении; глобальная уникальность между перезапусками не обещается |
| Title | Непустой результат `normalize_title`; человеческий регистр и внутренние пробелы сохраняются |
| Priority | Int от 1 до 5 включительно; проверяется до добавления |
| Новая запись | Отдельный объект, `is_done=False`; прежние карточки не переписываются |
| Источник данных | Один `tasks` в `run`, до `while`; передаётся операциям, не заменяется на каждой итерации |
| Добавление | Сначала все проверенные значения, затем назначение id, готовая фабрика и один append |
| Чтение | Вывод, поиск и статистика сохраняют длину, порядок, id и все поля |
| Поиск id | Полная исходная запись либо `None`; отсутствие проверяется до доступа к полям |
| Завершение | Только найденный `is_done` становится True. Повтор не создаёт новой записи и не ведёт отдельный счётчик выполнений |
| Поиск title | Очистка запроса, сравнение без регистра, все совпадения в исходном порядке; пустой запрос возвращает пустой список |
| Сводка | `total`, `completed`, `left`, равенство `total = completed + left`; отдельно процент с округлением до одного знака, пустой набор 0.0 |
| Отказ ввода | Сообщение и повтор именно соответствующего поля; ни новой записи, ни изменения прежних до допустимого ответа |
| Отсутствующий id | Корректное число может не обозначать задачу: сообщение и возврат в меню, без повторного принудительного выбора существующей |
| Выход | `exit` на командном приглашении, без новых вопросов и действий после завершения |

Для числового ввода принимается строка, которую успешно преобразует `int` после очистки и которая проходит предметные границы. `+5` допустим, `5.0` не является целочисленной строкой; `-1` преобразуется, но не проходит диапазон. Нельзя считать любой успешно преобразованный int подходящим priority или id.

Не обещать отмену каждого вложенного вопроса: в этой версии `exit` действует в меню; на числовом вопросе это ошибочная строка и вопрос повторяется. `Ctrl+C` остаётся аварийным прекращением, не сохранением данных или штатной отменой. EOF, KeyboardInterrupt, собственные исключения и универсальные валидаторы вне цели.

### Переход от учебного calc к Planner

Перед изменением проверить прежний `calc/exit`, функции и текущую рабочую версию. Затем **осознанно заменить командный сценарий**, а не стереть файл и скопировать готовый другой проект. Новый `run` использует знакомый цикл и нормализацию; остаются прежние постоянные функции модели, стартовый экран и история.

Процедурная ветка `calc` перестаёт быть активной частью интерфейса; её прежнее поведение доступно в истории. `calculate_study_minutes` сохраняется как уже изученный вспомогательный компонент, но не вызывается под видом `stats` и не добавляет восьмую команду. Не оставлять два независимо запускаемых меню и не складывать `durations` в `tasks`.

Это объявленное изменение назначения интерфейса, не случайная регрессия. Старые гарантии очистки, форматирования, фабрики, запуска и Git сохраняются; старый набор `calc/exit` намеренно заменён новым набором по общей карте. Прежняя версия служит точкой сравнения, не вторым рабочим продуктом.

### Ответственность компонентов

Все постоянные определения остаются в прежнем `main.py` до вызова управляющего сценария. Имена новых функций фиксируют один договор, не требуют по обёртке на каждую строку.

| Компонент | Вход → результат | Что меняет или выводит | Место появления |
| --- | --- | --- | --- |
| Прежние normalize_title/create_task/format_task | Прежние контракты блока 3 | Не получают новых скрытых обязанностей | Уже на входе |
| `show_menu()` | Нет предметного входа → None | Печатает только реализованные команды | 16; перечень расширяется по карте |
| `run()` | Один запуск → None | Создаёт tasks один раз, читает команды, выбирает действие, завершает цикл | 16 |
| `show_tasks(tasks)` | Список полных записей → None | Читает/печатает, не меняет данные; сначала пустота/число, затем полный просмотр | 16 → 17.1, одна функция |
| `read_title()` | Реальные ответы input → очищенный непустой str | Повторяет вопрос и печатает причину отказа; tasks не получает | 16.1 |
| `read_priority()` | Реальные ответы input → int 1–5 | Только ввод/проверка/повтор | 16.1 |
| `read_task_id()` | Реальные ответы input → положительный int | Проверяет запись числа, не существование задачи | 16.1 |
| `get_next_id(tasks)` | Полные записи → следующий положительный int | Чтение без мутации, простой for/if | 17 |
| `add_task(tasks, title, priority)` | Уже проверенные данные → новая принятая задача | Вызывает get_next_id/create_task, один append в исходный список; без input/print | 17 |
| `find_task(tasks, task_id)` | Список и допустимый id → исходная запись либо None | Чтение без изменения | 18 |
| `mark_task_done(tasks, task_id)` | Список и допустимый id → bool наличия задачи | Использует find_task; меняет только найденный флаг, без печати | 18 |
| `search_tasks(tasks, query)` | Список и str → новый список найденных записей | Исходные записи общие, не копии; сам поиск их не меняет | 18.1 |
| `build_statistics(tasks)` | Список → словарь total/completed/left | Читает текущие обязательные is_done, не кеширует и не меняет | 18.2 |
| `completion_percent(statistics)` | Согласованная сводка → float | Отдельная формула по той же сводке; 0.0 при total=0 | 18.2 |

У `mark_task_done` True означает «задача найдена и теперь выполнена», включая уже выполненную; False означает отсутствие. Не называть результат признаком нового перехода: старый пример смешивает эти смыслы. Интерфейс сообщает нейтральное подтверждение состояния, статистика считается из флагов, не из числа True-ответов.

`completion_percent` получает уже построенную сводку, чтобы процент и счётчики имели одну опору без повторного алгоритма подсчёта. Это уточнение границы новой функции, не изменение четырёх полей задачи или цели курса. Дополнительный `count_done` не обязателен; при его обоснованном выделении подсчёт не дублировать в других местах.

Ввод/печать в меню могут оставаться небольшими ветками знакомого `if/elif`. Для `add` оправдан `handle_add(tasks)`: связывает два запроса, предметную операцию и подтверждение. Не навязывать новую систему диспетчеризации, классы handler или отдельные файлы. Побочный эффект функции явно называется; `return` не превращает её автоматически в чистую.

Вне блока: удаление, редактирование других полей, JSON, файлы хранения, ООП, базы данных, HTTP/FastAPI, pytest, пакетная архитектура, новые поля и обязательные Git-ветки/релизы. `.env` можно разобрать как пример риска публикации, но создавать этот файл или подключать библиотеку ради примера не нужно.

### Накопление и формат основной практики

В 16 рабочий list показывает пустое состояние; общий список пока действительно пуст. `show_tasks` также может сообщать фактическое число записей при непустом входе, но ещё не обещает полный просмотр. В 17 пользователь впервые добавляет данные и сразу видит добавленную карточку через прежний formatter. В 17.1 та же show_tasks получает полный обход; это новое поведение просмотра, а не переписывание созданных функций.

Дальше в меню остаются все уже реализованные команды: после добавления доступны add/list/exit; после адресного поиска ещё find/done; после текстового поиска ещё search; после сводки ещё stats. Никаких пунктов «успешно» без настоящего действия.

Основная практика находится в прежнем локальном проекте, включая реальные последовательные ответы человека. Редактор платформы проверяет небольшой контракт на явно исследовательских значениях. Он не получает доступ к компьютеру ученика и не заменяет проверку живого CLI. Подготовленные наборы с необычными id допустимы только для исследования функции, не как зашитая рабочая база.

Канонический компонент ученик реализует один раз. Если runner требует solve, адаптер и связь с компонентом нужно предоставить при реализации задания, не требовать второго алгоритма с другой моделью. Тесты проверяют и результат, и оговорённый эффект. После проверенного проектного шага применяется знакомый Git-цикл; количество коммитов не подменяет доказательство поведения.

## 3. Подробные паспорта занятий

### 16. Каркас меню и жизненный цикл

**Основная тема и назначение.** Превратить освоенный повтор команд в управление настоящим Planner. Главная новая инженерная мысль: состояние живёт дольше одной итерации, а меню показывает только существующие действия. Это не повтор первого while.

**Точка A.** Запускается прежний calc/exit; постоянные normalize_title/create_task/format_task и вспомогательный расчёт определены в main.py. Понятны условие, цикл и передача списка. Нет состояния задач, run для Planner и реальных команд просмотра/добавления.

**Точка B.** В том же файле работает один `run`, создающий пустой tasks до цикла. Команда list показывает нормальное пустое состояние, exit завершает сценарий, неверный ввод возвращает к вопросу без изменения данных. Ученик объясняет владельца списка и разницу между итерацией и процессом.

**Необходимые темы, строго по порядку.** Опоры: def/вызов, while, if/elif, break/continue, len, очистка команды, переданный объект. Новое: ответственность управляющего сценария и жизненный цикл общего состояния.

1. Назначение интерфейса и состояние. Зачем пользователю повторяемый выбор; сравнить обычное действие и дальнейший возврат к приглашению. Ошибка: считать показ меню выполнением команд. Проверка: по ответам list/неизвестная/exit назвать реальные действия.
2. Один запуск, несколько итераций, один список. Связать с durations, который обновлялся на отдельный calc: здесь данные должны пережить смену команды. Ошибка: tasks внутри while или новой функции каждого действия. Проверка: разобрать две схемы размещения и объяснить потерю записей, не реализуя add заранее.
3. Функция run как владелец цикла и списка. Создание до while, определения до вызова, один вызов в конце файла. Ошибка: оставить старый командный цикл после нового или запускать run из самого тела. Проверка: указать единственный маршрут старта/выхода.
4. Show_menu печатает только list/exit; команда очищается через strip/lower при каждом input. Опора из блока 2, новое место применения. Ошибка: признать все будущие команды действующими, а затем вызвать неопределённую функцию. Проверка: сравнить план продукта и фактический набор.
5. Show_tasks как чтение состояния. Пустой список является нормальным, не нужна первая запись; при непустом входе пока допустима честная сводка количества. Ошибка: tasks[0] на пустоте или очистка ради вывода. Проверка: предсказать длину до/после двух чтений.
6. Неизвестная команда и штатный выход. Полная ветка отказа, возврат к вопросу, break ближайшего командного цикла. Ошибка: действие после отказа или вопросы после exit. Проверка: трасса с пустой строкой, ошибкой и выходом, включая строки после цикла.

**План практики, подробно и по шагам.** Основной формат проектный; трасса служит подготовкой, не заменяет запуск.

1. Открыть существующий main.py и запустить прежний calc/exit. Назвать постоянные функции и показать рабочую версию в истории. Результат: проверенная опора до изменения управления.
2. По знакомому короткому примеру предсказать поведение двух итераций, если список создаётся внутри/до цикла. Сопоставить результат с прежней независимостью durations; не добавлять демонстрационные задачи в рабочий файл.
3. В main.py организовать один run. Перенести знакомый командный цикл в него, заменить активную calc-ветку новым сценарием по разделу 1; сохранить функции. Результат: один маршрут запуска, а не два меню подряд.
4. Создать tasks один раз до while, добавить show_menu для list/exit и show_tasks с понятным пустым случаем. Передать исходный список аргументом. Результат: повторное list сообщает пустоту; не нужны новая фабрика и хранение.
5. Настроить нормализацию каждой команды, явный отказ и выход. Запустить list, пустую команду, неизвестную, list, exit. Следующий шаг получает работающий цикл без сломанного ввода команд.
6. Проверить diff, отсутствие несуществующих обработчиков и ошибочных опытов; сохранить рабочее изменение прежней истории. Не выполнять init и не менять remote.

**Проверки и ошибочные случаи.** Немедленный exit; list дважды; `  LiSt  `; пустая/пробельная/неизвестная команда, включая delete; возврат к меню после отказа. tasks остаётся пустым, функции модели сохраняют контракты. Проверить definitions/call и отсутствие вторичного запуска. Сохранность между итерациями пока подтверждается местом создания и исследованием; реальное накопление станет проверяемым после add. Не выдавать пустой list за доказательство сохранения ещё не созданных пользовательских записей.

**Подсказка к практике.** Найти границы старого командного цикла; отдельно отметить место, выполняемое один раз, и место каждой новой попытки. Сравнить число созданий списка с числом вызовов run. Печать вариантов сама не должна получать input или менять tasks.

**Результат и переход.** В main.py остаются один run, show_menu, начальный show_tasks и прежние компоненты; каталог/история прежние. Меню живое, но задач ещё нет. Следующий шаг добавляет устойчивые запросы полей, не переписывает цикл.

### 16.1. Ввод данных и границы отказа

**Основная тема и назначение.** Отделить ошибочную запись значения от недопустимого предметного значения. Пользователь должен иметь возможность исправить ввод без остановки приложения и без повреждения общего состояния. Обработка ValueError впервые изучается именно здесь.

**Точка A.** Есть run/list/exit, пустой tasks, normalize_title, функции и известные сравнения. Ученик видел ValueError при int и умеет его диагностировать, но не писал обработчик. Нет read_title/read_priority/read_task_id и нет add, который мог бы принять данные.

**Точка B.** Три функции ввода в прежнем файле возвращают только подходящие значения; неверный ответ повторяет текущий вопрос. Ни одна не создаёт карточку и не меняет tasks. Ученику понятны области try, except, continue и return.

**Необходимые темы, строго по порядку.** Опоры: input возвращает str, normalize_title, int, границы, цикл, return. Новое: узкий перехват ValueError и договор повторного запроса.

1. Граница ввода. Зачем отделять сырой ответ, очищенное значение, преобразование и принятие. На простой анкете сравнить «не число» и «число вне разрешённого диапазона». Ошибка: считать strip полноценной проверкой. Проверка: классифицировать четыре разных ответа по месту отказа.
2. Title: нормализация прежней функцией, проверка непустоты, сохранение регистра. Ошибка: default «Без названия», lower/title для человеческого текста или возврат пустой строки. Проверка: пробельный ответ, затем название с SQL и внутренними пробелами.
3. Числовое преобразование. Объяснить, что int('abc') прерывает текущий путь, а int('-1') даёт число. Связать с изученной ошибкой, не заменять int на float/int с обрезанием дроби. Проверка: предсказать судьбу `3`, ` 5 `, `+5`, `5.0`, `abc`, пустоты и `-1`.
4. Try/except ValueError: защищаем конкретное преобразование, при неуспехе не получаем годное число, сообщаем и спрашиваем снова. Ошибка: широкий except вокруг всего меню, пустой pass, использование старого/неприсвоенного числа после отказа. Проверка: проследить путь ошибочный текст → исправленный ответ.
5. Проверка диапазона после успешного преобразования. Priority 1–5, id больше нуля. Ошибка: объединить разные правила или считать корректный id обязательно существующей записью. Проверка: отдельно разобрать 0/1/5/6 для priority и 0/1/999 для id.
6. Return завершает текущий запрос, не приложение. Цикл запроса получает новый input при отказе; весь числовой вопрос не повторяет title. Ошибка: вернуть None как допустимый priority или выйти из run. Проверка: трасса функции и вызвавшего её кода.
7. Граница гарантии. Tasks отсутствует в параметрах запросов; они имеют явный эффект ввода/сообщения, но не изменения данных. Exit действует пока только в меню. Проверка: назвать, где у каждого компонента input, return и владелец будущего изменения.

**План практики, подробно и по шагам.** Постоянные функции в main.py; отдельная короткая проверка обработки в редакторе допустима, но не подменяет настоящие ответы.

1. В редакторе проследить маленький обработчик преобразования на двух строках, найти слишком широкий try и устаревшее значение после ошибки. Результат: понятен защищённый участок до самостоятельного проектного кода.
2. Открыть main.py, добавить read_title с вызовом существующего normalize_title. В знакомой интерактивной оболочке после штатного выхода из run вызвать запрос; сначала ввести пробелы, затем допустимое название. Результат: возвращён очищенный исходный регистр.
3. Добавить read_priority с отдельными путями ошибки int и ошибки диапазона. Тем же способом последовательно ввести текст, 0, 6, 1. Наблюдать повтор одного приглашения и конечный int 1. Используется уже понятный механизм title-повтора, но новое правило числового отказа.
4. Добавить read_task_id с положительной границей. Проверить 0, отрицательное, дробную строку, затем допустимый id. Результат: функция принимает число независимо от наличия карточки; будущий find получит именно int.
5. По возвратам показать type и сохранить значение вызывающего кода; не напечатанный текст вместо return. Удалять рабочие функции не нужно, а исследовательские ответы не вшиваются в main.py.
6. Запустить обычный run: прежние list/ошибка/exit работают, в меню нет фиктивного read/add. Сохранить проверенные компоненты. В следующем шаге handle_add действительно использует эти функции, а не переписывает валидацию.

**Проверки и ошибочные случаи.** Title пустой/пробельный/название с краями; priority текст, пустота, 5.0, -1, 0, 1, 5, 6; id текст, 0, -1, положительный. После неверного ответа нет возврата недопустимого значения и никакого изменения tasks. Не использовать наивный isdigit как универсальное обоснование успешного int. ### 18.2. Статистика и проверка согласованности

**Основная тема и назначение.** Превратить текущее состояние задач в понятную сводку. Считать не число команд, а факты списка; объяснить пустоту, единицу измерения процента и согласованность нескольких показателей.

**Точка A.** Есть принятые задачи, завершение, все виды чтения, len/for/if/накопление и арифметика. Is_done всегда обязательный bool. Stats ещё нет; не существует скрытого completed, обновляемого на каждую команду. Round в обязательной практике вводится здесь.

**Точка B.** Stats показывает total/completed/left и отдельно процент по одному актуальному состоянию. Пустота даёт 0/0/0 и 0.0, после add/done сводка меняется правильно, повтор done не завышает completed. Сводка не меняет задачи.

**Необходимые темы, строго по порядку.** Опоры: len, накопитель, обязательный ключ, bool, деление и словарь результата. Новое: предметные счётчики, производные значения и округлённый процент.

1. Данные против событий интерфейса. Total считает записи, completed считает True-флаги, left оставшиеся записи. Ошибка: увеличить completed после любого успешного done. Проверка: две команды одной задаче не создают два выполненных объекта.
2. Подсчёт текущего списка прямым for. Начальное значение до обхода; доступ к обязательному is_done, а не fallback неполной модели. Ошибка: пересчитать только matches от search или обнулить счётчик внутри цикла. Проверка: трасса полного набора с несовпадающим результатом поиска.
3. Сводка как новый словарь результатов, не новая форма задачи. Total=completed+left, completed не больше total, числа неотрицательные. Ошибка: второе независимое правило left даёт несогласованность. Проверка: пустой/смешанный/полностью завершённый набор.
4. Процент как доля completed/total, умноженная на 100. Отличить 0.5 от 50.0 и float от текстового знака %. Ошибка: делить до проверки total=0 или применять //. Проверка: 1 из 2 и 2 из 3, затем пустота.
5. Отдельная completion_percent получает ту же сводку. Round(value, 1) возвращает округлённое число, не изменяет исходные данные; числовое округление и форматирование текста различаются. Для наших случаев 1/3 даёт 33.3, 2/3 даёт 66.7. Ошибка: int округляет не по этому договору или процент хранится в записи задачи. Проверка: прогноз числа и тип результата, не изучение всей двоичной арифметики.
6. Подключение stats и отсутствие кеша. Построить сводку на запрос, вычислить процент по ней, печатать снаружи. Ошибка: число осталось от прошлого вызова или берётся из учебного calculate_study_minutes. Проверка: add/done/stats в одном процессе и неизменность после двух stats.

**План практики, подробно и по шагам.** В main.py появляются две функции по одному договору и последняя предметная команда.

1. На короткой трассе полных задач проследить completed и объяснить равенство счётчиков. Найти ошибку счётчика событий и обнуления внутри цикла, подобрать различающий сценарий.
2. Добавить build_statistics(tasks), вернуть ровно total/completed/left. Проверить пустой, смешанный и завершённый исследовательские наборы без печати/мутации. Эти наборы не заменяют реальные данные run.
3. Добавить completion_percent(statistics) по уже согласованной сводке. Обработать total=0 до формулы, вернуть 0.0; проверить 0%, 50.0, 33.3, 66.7, 100.0. Не менять контракт фабрики, задачи или build_statistics ради процента.

**Проверки и ошибочные случаи.** Нулевой total до деления; границы 0/100; дробные доли; total=completed+left во всех состояниях. Повторный done и неизвестный id ничего не прибавляют к completed; отказ add ничего не прибавляет к total до допустимых ответов. Stats/list/search не меняют записи. **Подсказка к практике.** Определить, что считается одним выполненным объектом. Сначала получить три согласованных числа, затем отдельно решить пустой случай процента. Каждый запрос stats заново читает текущие флаги; ответ done не является единицей для накопителя.

**Результат и переход.** Все операции Planner уже реализованы и проверены, в файле нет параллельных списков/счётчиков событий. Есть build_statistics и отдельный процент по её результату. Следующее занятие описывает готовое поведение и публикацию, не достраивает пропущенные операции.
