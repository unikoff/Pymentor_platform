# Python Foundations: общая концепция первой главы

Курс «Основы Python и мышление программиста» вводит в программирование с нуля и приводит к первому работающему Console StudyHub Planner. Здесь формируется не коллекция выученных команд, а способность понять задачу, написать небольшой код, проверить его и объяснить результат.

Концепт составлен по [методичке общей концепции](../CONCEPT_AUTHORING.md). Он задаёт вход, выход и обязательное содержание блоков 1–4. Подробные карты блоков нужно создавать следующим шагом по [методичке для блоков](../BLOCK_CONCEPT_AUTHORING.md), сохраняя договорённости этого файла.

Это целевой маршрут переработки. Теория, практика и привязки платформы пока не изменены. Дробные номера обозначают необходимые дополнительные учебные шаги, а не уже существующие занятия.

## 1. Контекст до главы: исходная точка A

### Для кого предназначена глава

Ученик впервые встречается с Python, терминалом и Git. Он может пользоваться браузером и файлами, но не обязан понимать установку интерпретатора, расширения файлов, текущую директорию, кавычки в команде, ошибку запуска или устройство репозитория.

Нельзя считать знакомыми слова «параметр», «метод», «объект», «ветка», «окружение», «индекс» и «состояние». Их нужно вводить там, где они становятся нужны. Наличие взрослого наставника не является обязательной предпосылкой: ученик должен получить объяснения на платформе.

### Начальная опора проекта

На входе проекта ещё нет. Первое занятие позволяет безопасно попробовать Python в редакторе платформы. Затем ученик создаёт локальную папку и `main.py`; после этого именно они развиваются до Console Planner.

Git подключается к уже созданному файлу. На каждом следующем блоке сохраняется тот же корень и история. Учебные эксперименты допустимы в редакторе платформы, но не должны вытеснять или обнулять основной результат.

## 2. Цель и итог: точка B

### Что ученик должен понимать

1. Код выполняется по правилам языка. Отступы, значения и порядок действий определяют поведение, а не намерение автора.
2. Ввод, вычисление, изменение данных и вывод являются разными действиями. `print` и `return` не взаимозаменяемы.
3. Тип значения влияет на допустимые операции. Ввод цифр через `input` не создаёт число автоматически.
4. Условие выбирает действие, цикл повторяет действие, коллекция хранит данные, функция выделяет понятную обязанность.
5. Список и словарь могут изменяться. Передача данных функции не означает создание независимой копии.
6. Ошибка является наблюдаемым событием с причиной. Её можно воспроизвести, локализовать и проверить после исправления.
7. Сохранение файла, Git-коммит и отправка истории на GitHub являются разными действиями. Чистый репозиторий не доказывает правильность программы.

### Что ученик должен самостоятельно делать

- Запускать Python-файл в правильном окружении и папке, отличать Python-команду от команды терминала.
- Читать небольшой код, предсказывать его выполнение и проверять предположение запуском.
- Получать и нормализовать ввод, вычислять значения, проверять условия и обходить данные.
- Создавать функции с понятными входами, результатами и изменениями состояния.
- Читать простую ошибку и исправлять причину, не скрывая её случайным запасным значением.
- Развивать собственный проект небольшими шагами, проверять прежние возможности после изменения.
- Создавать осмысленные коммиты, читать diff и историю, публиковать и получать свой проект из GitHub.
- Объяснять путь данных и самостоятельно менять знакомую часть программы без полного готового решения.

### Конечный продукт

**Console StudyHub Planner** запускается из терминала и позволяет добавить задачу, вывести список, получить задачу по id, отметить её выполненной, найти задачи по части названия, показать статистику и выйти из меню.

Есть единая модель, функции с ясными обязанностями, устойчивый ввод, README и осмысленная Git-история. Проект можно получить из репозитория и запустить по инструкции без ручного копирования кода из уроков.

Данные находятся в памяти одного запуска. После выхода они исчезают: это честное ограничение первой главы. Git сохраняет исходный код, а не содержимое работающего списка задач. Файловое хранение станет следующим развитием того же проекта, а не исправлением якобы сломанной установки.

### Неизменный договор первого Planner

| Часть | Требование для концептов всех блоков |
| --- | --- |
| Рабочая папка | Один существующий `studyhub-console`; у уже проходящего ученика сохраняется его фактический корень |
| Основная программа | Один `main.py`; функции появляются после их изучения, без ранней архитектуры пакетов |
| Модель задачи | Словарь с `id`, `title`, `priority`, `is_done`; во всех примерах и проверках одинаковые ключи |
| Title | Строка, очищенная по краям, непустая; регистр пользовательского названия сохраняется |
| Priority | Целое число от 1 до 5; крайние значения допустимы |
| Id | Положительный целый, не позиция в списке; 1 для пустого набора, иначе максимум текущих id + 1 |
| Новая задача | `is_done=False`; создание не меняет уже существующие карточки |
| Изменения состояния | Добавление и завершение меняют общий список или его словарь; это объяснённый контракт, не скрытая мутация |
| Чтение | Вывод, поиск и статистика не изменяют исходные записи |
| Поиск по id | Возвращает существующую карточку либо `None`; отсутствие не приводит к обращению к полям `None` |
| Поиск по названию | Очищенный фрагмент без учёта регистра; все совпадения в исходном порядке; пустой запрос даёт пустой результат |
| Завершение | Меняет только найденную задачу; повторное завершение не увеличивает число выполненных повторно |
| Статистика | `total`, `completed`, `left`; `total = completed + left`. Процент вычисляется отдельно, округляется до одного знака после запятой, при пустом списке равен 0.0 |
| Интерфейс | Команды `add`, `list`, `find`, `done`, `search`, `stats`, `exit`; появляются в рабочем меню по мере реализации |
| Ошибочный ввод | Объяснённое сообщение и повтор соответствующего вопроса либо возвращение к меню по договору конкретного действия; данные не меняются при отказе |
| Хранение | Один список, созданный до цикла меню и передаваемый функциям; не новый список на каждой итерации |

Стабильность id означает, что существующая задача не получает новый номер после чтения или изменения соседей. Это не обещание глобальной уникальности между отдельными запусками программы.

## 3. Содержание, границы и необходимые изменения

### Глубину объяснений нужно существенно увеличить

Эта глава должна стать полноценным введением для новичка, а не краткой памяткой знакомых разработчику команд. При создании концепта каждого блока необходимо прямо заложить **значительно более подробную теорию и больше практического закрепления**, чем сейчас. Не ограничивать содержание прежним размером занятия или прежними пятью занятиями блока.

Необходимая глубина определяется тем, что ученик способен понять механизм и применить его без поиска недостающего определения в интернете. Количество текста само по себе не является приёмкой.

В карты блоков нужно включить следующие содержательные опоры:

- В запуске: файл, сохранённый текст, интерпретатор, редактор, терминал, текущая папка и отличие ошибки поиска файла от ошибки Python.
- В данных: значение, имя, тип, присваивание и повторное использование; различие текста `"3"` и числа `3`.
- В строках: индекс, граница среза, неизменяемость, результат метода и отдельное правило нормализации. Не требовать индексации пустой строки без объяснения.
- В логике: сравнение, boolean, границы диапазона, порядок проверок и причина выбора одной ветки. Небольшие таблицы случаев важнее сложных выражений в одну строку.
- В циклах: состояние до первого шага, текущий элемент, изменение накопителя, выход и пустой вход. Для `while` отдельно показать, кто и когда меняет условие продолжения.
- В коллекциях: элемент и индекс, ключ и значение, изменение объекта, второе имя того же объекта и граница поверхностной копии.
- В функциях: определение и вызов, параметр и аргумент, локальное имя, возвращённое значение, `None`, печать и побочный эффект. Каждое различие нужно применить, не только назвать.
- В ошибках: место проявления и исходная причина, чтение traceback, минимальное воспроизведение, исправление и повторная проверка.
- В проекте: почему нужна конкретная операция, какие данные она получает, что возвращает или меняет и кто затем использует результат.

Для закрепления нужны не только вопросы с выбором ответа. В общей карте предусматриваются чтение трассы, предсказание вывода, изменение одного условия, поиск причины ошибки, написание собственного небольшого фрагмента и применение в проекте. Подробное оформление этих упражнений остаётся задачей концептов блоков и существующей методологии занятий.

Полные реализации проектных функций не являются заменой теории. Теория объясняет общую модель на небольших примерах, а точные шаги самостоятельной работы, наводки и раскрываемые решения относятся к практике.

### Отдельный маршрут первого знакомства с Git

Git нужно изучить достаточно подробно, чтобы ученик выбирал действие по состоянию проекта, а не повторял ритуал `add/commit/push`. Разделить нынешнее занятие на четыре последовательных шага внутри первого блока:

| Место | Что обязательно понять | Основная работа и наблюдаемый результат |
| --- | --- | --- |
| **3. Git и первая локальная версия** | Git и GitHub не одно и то же; репозиторий, рабочие файлы, подготовленные изменения и история; настройка автора не является входом в GitHub | Проверить установку, создать историю в существующей папке, подготовить `.gitignore` до добавления, выбрать `main.py` и создать первый локальный коммит |
| **3.1. Изменения, diff и осмысленные коммиты** | Untracked/modified/staged, `git diff` и `git diff --staged`, повторное изменение после `add`, сообщение и идентификатор коммита | Сделать две небольшие работающие версии; перед каждой показать, какие строки войдут в коммит. Исследовать изменение после staging и безопасно убрать файл только из staging, сохранив рабочую правку |
| **3.2. GitHub и отправка своей истории** | Удалённый репозиторий, `origin`, локальная ветка, её связь с удалённой; commit ещё не опубликован; авторизация отличается от имени автора | Создать пустой удалённый репозиторий, проверить адрес, отправить существующую историю; затем изменить программу, создать следующий коммит и подтвердить его появление на GitHub |
| **3.3. Получение проекта и диагностика обычных ошибок** | Clone получает репозиторий с историей; `.venv` создаётся локально; fetch получает сведения, а pull интегрирует изменения; чистое рабочее дерево не означает отправленную историю | Клонировать свой проект в отдельную проверочную папку, запустить и сравнить историю. Пройти линейное обновление без расходящихся изменений и объяснить случаи «не тот каталог», «не подготовил файл», «не отправил коммит», «неверный remote» |

Во всех четырёх шагах изменяется и исследуется тот же простой Python-проект. Для изучения Git не нужны функции, коллекции, второй выдуманный продукт или сложный скрипт: достаточно знакомого запуска и небольшого изменения текста.

Дополнительные требования к будущему концепту первого блока:

1. Сначала освоить сохранение на компьютере, затем подключать сеть. Недоступность GitHub не отменяет уже полученную локальную историю.
2. Установка, имя автора, приватность email и авторизация получают разные объяснения. Не предлагать пароль аккаунта как обычный пароль для Git HTTPS и не помещать секреты в URL, файл или демонстрационный вывод.
3. Начинать с добавления конкретных файлов. Перед массовым добавлением проверять `.gitignore` и staged diff. Правило ignore не удаляет уже отслеживаемый файл из истории.
4. На примере после существующего первого коммита показать `git restore --staged`: это снятие с подготовки, не удаление рабочего текста. Не выдавать `restore` рабочего файла, `reset --hard`, `clean` и force-push за универсальное исправление.
5. Первые отправки выполняются из одного основного рабочего каталога. Проверочный clone не становится вторым параллельным местом написания проекта. Обновление показывается на чистой копии через fast-forward, без неожиданного разрешения конфликтов.
6. В каждом шаге есть действие ученика, чтение результата и объяснение причины. «Вставьте все команды и покажите ссылку» недостаточно.
7. После Git-введения небольшие осмысленные коммиты продолжаются по всему курсу. В финальном блоке Git применяется к передаче законченного проекта, а не изучается заново с `git init`.

Объяснения состояний и staging сверяются с [Pro Git: запись изменений](https://git-scm.com/book/en/v2/Git-Basics-Recording-Changes-to-the-Repository); снятие с подготовки и риск потери рабочих изменений с [Pro Git: отмена действий](https://git-scm.com/book/en/v2/Git-Basics-Undoing-Things); удалённая история с [Pro Git: remotes](https://git-scm.com/book/en/v2/Git-Basics-Working-with-Remotes); способы входа с [официальной документацией GitHub](https://docs.github.com/en/authentication/keeping-your-account-and-data-secure/about-authentication-to-github). Ссылки служат проверке авторского материала, а не заменяют объяснение на платформе.

### Что входит и что оставляем дальше

Тот же репозиторий, рабочий Console Planner, единая модель задачи, функции, история, README и понимание ограничений. Следующая глава углубляет контракты функций, работу с изменяемыми данными и организацию программы, затем добавляет файловое хранение, объекты и проверки.

Не переносить в эту главу JSON, storage, классы и pytest только ради ускоренной сборки дальнейшего проекта. Но и не начинать следующий этап с нового пустого Planner: он должен улучшать уже проверенный результат. [Первое переходное занятие следующего курса](../../../backend/learning/course_content/deeper/block_05/21%20-%20Переход%20от%20первого%20месяца,%20разбираем%20Console%20Planner.md) сейчас содержит лишь заголовок; при переработке ему потребуется реальный разбор полученного здесь проекта.

### Как использовать концепт дальше

На основе этого файла последовательно создать `BLOCK_1.md`–`BLOCK_4.md` в этой папке. Каждый должен уточнить карту и паспорта занятий, взять свою A/B из раздела 4, раскрыть перечисленные предпосылки и назвать конкретные действия практики. Пустые концепты блоков сейчас не создавать: наличие заголовка не равно разработанной карте.

Перед реальным добавлением дробных занятий потребуется согласовать идентификаторы, порядок, привязки практики и frontend. Сейчас [загрузчик](../../../backend/learning/content.py), [каталоги практики](../../../backend/learning/course_content/foundations/__init__.py), [проверка каталогов](../../../backend/learning/practice_helpers.py) и [frontend-привязки](../../../frontend/src/lessons/python-foundations/index.ts) опираются на целые номера: простой файл `03.1` не гарантирует отдельную корректную выдачу. Нужны отдельные идентичности и числовой порядок частей, сохранение прежних привязок и прогресса; дробь не должна превращаться в ещё одно занятие с ключом `3`.

Также при переработке выдачи блока 4 нужно учесть: наличие code tasks сейчас исключает manual practice в загрузчике. Проектные задания не должны существовать только в тексте теории и исчезать из практики. Изменение этой выдачи относится к реализации занятий, не к созданию данного концепта.

### Критерии готовности будущих концептов блоков

- [ ] Учтён нулевой опыт ученика; предпосылки объясняются до применения.
- [ ] Теория существенно углублена по механизмам и границам, а не раздута повторами или готовыми ответами.
- [ ] Git имеет четыре последовательных начальных шага и затем применяется на своём проекте.
- [ ] Проект, папка, история и договор данных не меняются произвольно между блоками.
- [ ] Дополнительные занятия имеют конкретное место, назначение и проверяемый результат.
- [ ] У каждого блока есть вход, обязательное содержание, накопленный результат и переход дальше.
- [ ] В блоке 4 последовательность соответствует реальным зависимостям, каждая операция появляется до финала.
- [ ] Подтверждаются самостоятельность и воспроизводимость, не только прохождение маленьких автопроверок.
- [ ] Финал достигает прежней цели первого Planner без переноса технологий следующих глав.
