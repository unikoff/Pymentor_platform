Концепт продолжает [общую карту курса](COURSE.md), [первый блок](BLOCK_1.md) и [второй блок](BLOCK_2.md). Структура соответствует [методичке для концептов блоков](../BLOCK_CONCEPT_AUTHORING.md). ## 1. Назначение, контекст, A → B и границы блока

### Назначение

Подготовить данные и небольшие понятные компоненты для сборки Console StudyHub Planner. Ученик переходит от отдельных значений и управляемого сценария к структуре записи, общему изменяемому состоянию и функциям с явными обязанностями.

Главный вопрос: как представить несколько задач, передать их между действиями и понять, какой результат вернулся, какие данные изменились и где искать причину ошибки?

### Точка A

Целевой вход соответствует выходу блока 2, а не предполагаемому окончанию всей главы:

- Есть прежний `studyhub-console/main.py`, выбранный Python, окружение, `.gitignore` и одна история с remote. У продолжающего ученика сохраняется фактический каталог.
- Изучены значения, типы, присваивание, преобразования, ввод и арифметика первого блока.
- Понятны строки, `len`, индекс и срез строки, новый результат метода, `strip/lower/upper`, f-строка.
- Изучены сравнения, логические правила, `if/elif/else`, прямой `for`, `range`, накопление, `while`, `break/continue` и достижимый выход.
- Простой список встречался как последовательность: порядок, элемент, длина, пустой набор. Это **не** знакомство с его изменением, копированием или вложенными словарями.
- В проекте есть учебный диалог `calc/exit`, расчёт времени с введёнными длительностями, нормализованные команды и повтор пустого названия. Это ещё не меню задач.
- Числовой ввод имеет явно ограниченный договор. Защита от любого текста через обработчик исключения не освоена.

Собственные функции, `return`, локальные имена вызова, словари, полная модель коллекций и ссылки на изменяемые объекты на входе отсутствуют. Слова «функция» и «результат метода» в прежних объяснениях не означают освоение этих механизмов.

### Точка B

Ученик:

1. Выбирает list, tuple или set по требованиям, не внедряет все структуры в Planner без необходимости.
2. Создаёт и читает единую задачу, понимает обязательные ключи, типы и предметные ограничения.
3. Обходит список словарей, различает позицию и id, понимает текущую запись и изменяет выбранный объект без случайной замены соседей.
4. Отличает второе имя от копии, внешнюю копию списка от копирования его записей; объясняет наблюдаемое общее состояние.
5. Определяет и вызывает функцию, сопоставляет параметры с аргументами, получает и использует результат; отличает print, return и None.
6. Различает локальное переприсваивание и изменение переданного объекта. По контракту знает, что функция возвращает и что изменяет.
7. Соединяет небольшие функции, отделяет ввод/вывод от правил, сохраняет в прежнем проекте постоянные компоненты для следующего блока.
8. Воспроизводит ошибку, читает traceback, ищет исходную причину, проверяет исправление и прежние рабочие сценарии.

Выход соответствует COURSE.md: **согласованная модель, понятные функции, передача состояния и диагностика**. Полное CLI-меню и соединение всех операций ещё предстоят.

### Неизменный договор модели

| Поле | Тип и смысл | Требование |
| --- | --- | --- |
| `id` | Положительный int, идентичность задачи | Не индекс и не порядковый номер вывода; существующая запись сохраняет id |
| `title` | Str, пользовательское название | Очистить края, сохранить регистр, непустота проверяется до создания принятой записи |
| `priority` | Int | От 1 до 5 включительно |
| `is_done` | Bool | Новая запись получает False; это не строка и не ключ done |

Во всех примерах **модели Planner** используются все четыре поля. Частичный словарь допустим только как явно обозначенное воспроизведение дефекта, не нормальная модель. В общих упражнениях словарь настроек может иметь другие ключи, но он не называется задачей.

`done` может быть именем будущей команды. Это не основание заменить поле `is_done`. `tags`, `deadline`, `category`, строковые статусы и дополнительные сущности не входят в договор первой главы. Теги допускаются только в отдельном упражнении о множестве, не как новое поле проекта.

Назначение следующего id, поиск по нему и связь с добавлением остаются блоку 4. Здесь id явно передаётся в создание; не вводим новый генератор или глобальный счётчик. Один объект задачи не является всем списком.

### Постоянные компоненты и границы ответственности

| Компонент | Вход → результат | Изменение/вывод | Когда появляется |
| --- | --- | --- | --- |
| `format_task(task)` | Полная задача → строка с id, title, priority и понятным состоянием | Не меняет словарь, не печатает; вызывающий код отвечает за print | 13 |
| `create_task(task_id, title, priority)` | Назначенный положительный id, уже очищенный непустой title и проверенный priority → новый полный словарь | Новый объект на каждый вызов; не меняет чужие записи, не спрашивает ввод, не выбирает id | 13.1 |
| `normalize_title(raw_title)` | Str → строка после strip | Не меняет регистр; пробельная строка даёт пустую, не «Без названия»; не печатает и не принимает запись автоматически | 14 |

Последний компонент не добавляет новую предметную возможность и не меняет цель курса: он именует уже написанное накопление из calc. Три функции модели прямо требуются общей картой. Договор каждого компонента сохраняется при дальнейшей интеграции.

В конце нет реализованных add/find/done/search/stats, скрытого CRUD, класса, JSON, файлового storage, pytest или новой архитектуры пакетов. Нет обязательного `assert`, import, глобального состояния, изменяемых аргументов по умолчанию и перехвата исключений. Ручные проверки через знакомые вызовы/вывод достаточны; try/except впервые применяется в согласованном шаге 16.1 блока 4.

### Накопление проекта без преждевременной сборки меню

1. В calc используются реально введённые длительности. В 11 они становятся списком `durations`; для каждой новой сессии список создаётся заново. Это данные расчёта, не будущий общий список задач.
2. В 12/12.1 полные задачи исследуются в редакторе как явно подготовленные учебные значения. Они не вшиваются в рабочий main.py как поддельное состояние приложения и не появляются в командах add/list.
3. В 13 постоянный format_task сохраняется в прежнем файле, определения располагаются до командного сценария. Функция проверяется отдельно; сам факт её наличия не запускает новый пункт меню.
4. В 13.1 добавляется одна постоянная фабрика. Следующий блок будет её вызывать, а не повторять тот же словарь другим именем.
5. В 14 очистка названия сессии использует общий normalize_title, а известное накопление выделяется в calculate_study_minutes. Ввод и итоговый print остаются обязанностью вызывающего сценария.
6. В 15 проверяются эти же функции и прежний calc/exit. Публикуется рабочий код, а не намеренно испорченный учебный пример.

Не заставлять ученика три раза писать одну функцию: в теории полный ответ, в runner второй ответ под именем solve, в проекте третий под предметным именем. Теория даёт модель на небольшом примере; основной компонент реализуется один раз, а адаптер solve при необходимости является предоставленной оболочкой проверки. Дополнительный вызов нужен для новой гарантии, не для повторного набора решения.

## 3. Подробные паспорта занятий

### 11. Коллекции: порядок, изменение и уникальность

**Основная тема и назначение.** Выбирать способ хранения по поведению данных и отличать изменение объекта от создания нового значения. Полный новичок должен объяснить последствия операции, а не только перечислить три типа.

**Точка A.** Есть прямой обход простого списка и range, строки, len, if и накопление. Список ещё не изменяли, принадлежность/копию/идентичность/None не изучали. Проект вводит длительности, но не хранит их списком.

**Точка B.** Ученик выбирает list/tuple/set, изменяет список осознанно, различает alias и верхнюю копию, получает новый текст из списка строк. Реально введённые длительности calc остаются доступными для просмотра и последующего выделения расчёта.

**Необходимые темы, в порядке изучения:**

1. Зачем хранить несколько значений после ввода и обходить их снова. Порядок, повторы и изменение являются отдельными требованиями; числа в одной переменной не заменяют коллекцию исходных данных.
2. Список как упорядоченный изменяемый объект. Индекс/срез/len, допустимая позиция и пустой набор; связать с известными строками, но показать различие изменяемости. Отдельно объяснить bool коллекции: пустая ложна, непустая истинна; список из одного False не становится пустым.
3. Принадлежность через in/not in как отдельный вопрос. Отличить значение элемента от его позиции и от слова in в записи for.
4. Append одного объекта, замена по индексу, pop по позиции и remove первого совпадения по значению. Пояснить вход, изменение и результат каждой операции, пустой pop и отсутствующее remove; до применения проверки уже объяснены.
5. Метод может менять объект и не выдавать полезного результата. Минимальный None; опасность присвоить результат append обратно списку. Pop, напротив, отдаёт удалённое значение. Свою функцию пока не определяем.
6. Два имени одного объекта, переприсваивание и мутация. Развести `==` и `is/is not`: одинаковое содержимое не доказывает один объект. Copy создаёт новый внешний список; вложенные данные будут разобраны после словаря.
7. Tuple: порядок, повторы, невозможность заменить позицию, пустой и одноэлементный кортеж. Фиксированы позиции, а не обязательно вся будущая вложенная структура. Для Planner отдельный tuple не требуется.
8. Set: уникальность, принадлежность, изменяемый набор с добавлением простых значений, пустой set(). Нет гарантированного порядка отображения и индекса; использовать строки/числа, не требовать хешируемость словаря. `{}` пока обозначить как другую структуру, подробно следующая тема.
9. Split создаёт список строк, join получает строки и разделитель. Это новый материал после списка, не предполагаемая тема прежнего блока. Рассмотреть пустой результат и TypeError при попытке join чисел без преобразования; сначала короткие строки без большой истории парсинга.
10. Пара в tuple и простая распаковка двух значений; затем enumerate как готовый источник пары позиции и элемента. Сравнить с известным счётчиком, не вводить распаковку звёздочкой или протокол итератора. Эта опора нужна items в следующем занятии.
11. Минимальный результат выбора: list сохраняет порядок и позволяет менять набор; tuple сохраняет порядок и фиксирует позиции; set выражает уникальность без пользовательского порядка. Не представлять одно как универсальную замену остальных.

**Пока нельзя требовать.** Словарь задачи, функция solve, return, глубокую копию, генератор, list comprehension, библиотеку collections, try/except или внедрение тегов/статусов в Planner.

**Основная практика.** От наблюдения объектов к реальным данным прежнего расчёта.

- Предсказать список после append, замены, pop и remove. Для одинаковых элементов показать удаление первого совпадения; для отсутствующего значения выбрать заранее объяснённую проверку.
- Сравнить alias и copy на простых значениях. Отдельно переприсвоить одно имя и изменить общий объект; подтвердить прогноз содержимым и is, без печати адресов памяти.
- Исследовать результат append и pop. Найти потерю переменной после присваивания None и исправить причину, а не заменить данные новым списком.
- Для одной последовательности с повторами сравнить list, tuple и set по свойствам. Индекс множества не использовать, порядок его печати не включать в ожидаемый ответ.
- Согласовать текущую карточку 11 как script: она действительно меняет заданный список. Три структуры можно проверить короткими независимыми действиями; не называть их обязательной моделью проекта. Уникальность с порядком оставить дополнительным опытом после явного объяснения всех нужных операций, без solve.
- Написать короткий опыт split/join и сопоставить ручной счётчик с enumerate. Эти исследования отвечают за новые механизмы; они не являются ещё одной задачей на уникальные теги.
- В calc создать durations для текущей сессии, добавить по одному реально введённому числу, показать их в исходном порядке. Сохранить накопление, итог с одним перерывом и часы/остаток. При следующем calc прежние длительности не подмешиваются.
- Проверить 0, 1 и 2 введённых занятия. При нуле не обращаться к первой позиции. Сохранить рабочую версию в прежней истории.

**Наблюдаемый результат.** Операции соответствуют своей роли, совпадение значений не смешивается с общей ссылкой, множество не обещает порядок. В проекте отображаются реальные длительности, а не заготовленный список; прежняя формула и независимость сессий сохранены.

**Выход и переход.** Есть понятные коллекции и минимальная модель объекта. Словарь добавит именованные поля, а не ещё одну попытку запомнить позиции списка.

### 12. Словарь и договор одной задачи

**Основная тема и назначение.** Представить одну запись именованными полями и понимать договор производителя и потребителя данных. До списка записей и функции нужно научиться читать и создавать одну полную задачу.

**Точка A.** Изучены список/кортеж/множество, принадлежность, пары и распаковка; известны None, сравнения, if и строки. Словарь и его ключи вводятся впервые. Проектного хранилища задач пока нет.

**Точка B.** Ученик создаёт полную задачу, читает обязательный ключ, меняет поле и отличает ошибку модели от допустимого отсутствия данных. Единые поля готовы для будущих функций.

**Необходимые темы, в порядке изучения:**

1. Позиция списка и имя поля решают разные задачи. Аналогия с анкетой помогает объяснить ключ, значение и обязательность, но словарь сам не проверяет заполнение анкеты.
2. `{}`, пары ключ:значение, уникальный ключ, повторный ключ и перезапись. Ключ как строка не является одноимённой переменной; значение может браться из неё.
3. Полный договор id/title/priority/is_done, типы и ограничения. Словарь не гарантирует их автоматически. Id не выводится из позиции; создание новой записи пока использует явно заданное положительное значение.
4. Обязательный доступ через [], KeyError и место создания дефектных данных. Исправить создателя словаря с неправильным ключом, а не маскировать отсутствующие данные запасным значением.
5. In проверяет ключи, не значения. Затем keys/values/items; для пары items используется уже объяснённая распаковка. Словарь сохраняет порядок добавления ключей, но ключ не превращается в числовую позицию списка. Обход словаря для диагностики отличается от вывода модели в заданном формате.
6. Get с явным default и без него; отсутствие даёт None, чтение не создаёт ключ. Сравнить отсутствие с существующим False/0. Не считать get универсально безопасной бизнес-логикой.
7. Пример необязательного поля только в отдельном учебном словаре настроек. У задачи priority и is_done обязательны, поэтому значения по умолчанию не ремонтируют её договор.
8. Присваивание ключу добавляет или заменяет; pop удаляет и возвращает. Исследование изменения общей анкеты не разрешает удалять обязательные поля принятой задачи или добавлять новые сущности в программу.
9. Верхняя копия одного словаря: второе имя остаётся alias, copy создаёт другой внешний объект. Для четырёх простых полей копия позволяет независимо изменить флаг; вложенные структуры изучаются следующим шагом.

**Пока нельзя требовать.** Свою функцию, возвращаемое значение solve, обработчик исключения, генерацию id, поиск задачи, поле done, tags/deadline/category как часть модели. None уже вводится здесь как значение, но собственное неявное возвращение ещё не изучено.

**Основная практика.** Редактор и одна полная запись; исходный main.py не заполняется тестовыми задачами.

- Создать задачу из явно заданных task_id, title и priority, с is_done=False. Прочитать все поля; объяснить, откуда взялись ключи и откуда значения.
- Заменить только флаг на заданный bool и подтвердить сохранность id/title/priority. Это упражнение изменения словаря, не готовая команда done.
- Заменить карточку 12: четыре поля, is_done вместо done, согласованные данные/условия/эталон и вывод. Не оставить старую проверку трёх полей после изменения теории.
- Предсказать результат повторного ключа и проверки принадлежности. На отдельном словаре настроек сравнить []/get, отсутствие ключа и явно существующее ложное значение; показать отсутствие мутации от get.
- Найти KeyError из-за неправильного производителя или опечатки. Восстановить договор, не добавлять без основания новый ключ и не заменять priority условной единицей.
- Сравнить alias и копию полной плоской задачи; изменить флаг копии и объяснить, какой объект изменён. Не требовать ещё неизвестного обхода списка словарей ради проверки одной записи.

**Наблюдаемый результат.** Создана одна согласованная запись, типы и ключи не перепутаны, чтение не изменяет словарь. Пустое состояние/отсутствие ключа разобраны на подходящем примере; дефект обязательного поля остаётся дефектом, а не нормализуется молча.

**Выход и переход.** Модель одной задачи понятна. Следующее занятие добавляет несколько таких записей и вложенное общее состояние, не меняя форму каждой из них.

### 12.1. Список словарей и границы копирования

**Основная тема и назначение.** Соединить два освоенных контейнера и увидеть, что внешний список и его записи являются разными объектами. Это обязательный мост к изменению переданных данных в функциях.

**Точка A.** Понятны полный словарь задачи, ключи, list, прямой for, alias, copy и is. Функций ещё нет; ни одна функция не вызывается ради объяснения ссылок.

**Точка B.** Ученик читает список полных задач, понимает переменную цикла, меняет выбранную запись и различает три степени независимости: alias, копия списка, новые словари в новом списке.

**Необходимые темы, в порядке изучения:**

1. Внешний список хранит элементы, каждый элемент является словарём. Len списка считает записи, len словаря считает поля. Пустой список и один пустой словарь не одинаковы.
2. Прямой for передаёт текущий словарь переменной цикла. Ключ читается у этой записи; переменная цикла не становится индексом, новой независимой записью или всем списком.
3. Позиции 0/1, отображаемые номера 1/2 и id 10/20 на одном примере. Перестановка списка не перенумеровывает id и не меняет смысл конкретного поля.
4. Второе имя записи и изменение её поля видны через список. Переприсваивание переменной цикла другой записи не заменяет элемент списка автоматически. Если заменяется позиция списка, это отдельное действие.
5. Чтение и подсчёт открытых/выполненных записей не меняют их. Использовать известные for/if/накопитель, не писать функции статистики или новую модель статуса.
6. Внешняя copy отделяет список, но сохраняет ссылки на словари. Append к копии и изменение её существующей записи дают разные последствия для оригинала.
7. Новый список отдельных копий каждого словаря для нашей плоской модели. Объяснить предел: если появится вложенный изменяемый объект внутри записи, ещё один уровень останется общим; не обещать универсальную глубокую независимость.
8. Фиксированный tuple также не замораживает вложенный словарь. Короткий контраст уточняет изученную неизменяемость позиций, не добавляет tuple в Planner.
9. Отсутствующая позиция и отсутствующий ключ являются разными нарушениями. Нормальная запись полная, намеренно испорченная относится только к исследованию; не копировать её в постоянный проект.

**Пока нельзя требовать.** Def/return, lookup по id как готовый компонент, CRUD-меню, deepcopy/import, списковое включение, JSON, assert или защиту любого внешнего ввода.

**Основная практика.** Исследования двух полных задач с id 10 и 20; данные явно учебные, не состояние живого Planner.

- Обойти список и вывести поля каждой записи. До запуска указать текущий словарь на каждом шаге; проверить пустой список и одну запись.
- Посчитать выполненные записи, не меняя флаги. Проверить разные сочетания bool и показать исходные словари после чтения.
- Взять второе имя первой записи, изменить её is_done и предсказать содержимое списка. Сосед и все id должны сохраниться.
- Сравнить изменение поля переменной цикла с её переприсваиванием. Подтвердить, что результат зависит от действия над объектом, а не от самого имени task.
- В отдельных запусках сравнить alias списка и copy списка. После append к внешней копии оригинальная длина прежняя; после изменения общего словаря его флаг виден в обеих коллекциях. Проверить внешние и внутренние объекты через is.
- Самостоятельно получить новый список отдельных копий записей знакомым for/append/copy, без готового включения. Изменить один скопированный флаг и подтвердить независимость плоских исходных записей.
- Найти ошибочное обещание «copy полностью защищает все данные» и объяснить границу на коротком вложенном примере. Не требовать реализации рекурсивного копирования.

**Наблюдаемый результат.** Ученик показывает отдельные объекты и общие ссылки, различает id и позицию, сохраняет соседние записи. Чтение не меняет данные; копирование не даёт выдуманной гарантии глубокого клонирования.

**Выход и переход.** Передача словаря функции дальше не является неожиданной новой формой данных. Теперь можно дать поведению имя и обсуждать контракт входа/результата отдельно от устройства записи.

### 13. Функция: определение, вызов и результат

**Основная тема и назначение.** Первый собственный инструмент: назвать знакомое преобразование, передать конкретные данные и получить результат для дальнейшего использования. Не пытаться заодно создать все операции приложения.

**Точка A.** Есть полная задача и список таких задач, строки, условия, копии и знакомые готовые методы. Def, параметры, вызов собственной функции и return впервые объясняются здесь.

**Точка B.** Ученик самостоятельно определяет/вызывает функцию, получает строку из format_task(task) и показывает её снаружи. Функция сохранена в прежнем main.py и не зависит от скрытого глобального title.

**Необходимые темы, в порядке изучения:**

1. Зачем именовать правило и проверять отдельно. Аналогия с инструментом помогает увидеть вход/выход, но определение не запускает тело само.
2. Def, имя, параметры, двоеточие и тело. Вызов со скобками; определение должно быть исполнено до нужного вызова. Вызов без параметров также требует скобки.
3. Параметр как имя текущего входа и аргумент как переданное значение. Начать с короткого строкового примера, затем передать уже известный словарь. Позиционный порядок и количество аргументов, объяснимый TypeError.
4. Вход в тело и возврат управления месту вызова. Return отдаёт значение и завершает текущий вызов, не всё приложение. Не выдавать return за замену break в общем случае.
5. Присвоить результат, использовать его в следующем выражении, показать через print. Print предназначен человеку; вывод внутри функции не становится её полезным результатом.
6. Минимум локальности: параметр/внутреннее имя принадлежат вызову, снаружи получается только явно переданный результат. Подробные повторные вызовы и изменение объектов следующая тема.
7. Неявный None и return без значения. Здесь достаточно базового контраста с напечатанной строкой; исследование нескольких путей и потребителя будет в 13.1.
8. Контракт formatter: получает полную задачу, выводит в строке все четыре смысла, преобразует bool в понятный текст состояния, не меняет данные и не печатает. Например, `[10] Изучить SQL | приоритет: 3 | открыта` является формой результата, а не готовой реализацией.
9. Проверка функции своего файла без другого проекта: интерактивная оболочка Python и режим `-i` после выполнения main.py. Объяснить команду запуска выбранного Python с этим флагом, командный exit приложения перед переходом в оболочку, приглашение `>>>`, ввод вызова, повтор и завершение оболочки. Команда терминала и Python-вызов вводятся в разные места; это новая техника, не подразумеваемая предпосылка.
10. Постоянные определения располагаются до существующего командного сценария. Подготовленные записи для проверки вводятся в оболочке/редакторе, не вшиваются как рабочая база main.py. Модульные импорты и защитный блок `__name__` пока не нужны.

**Пока нельзя требовать.** Фабрику всех операций, глубокое исследование мутации параметров, keyword-only аргументы, рекурсию, декораторы, аннотации как обязательное условие, обработчик исключения или целое меню задач.

**Основная практика.** Короткие вызовы, один постоянный formatter и проверка его контракта.

- Предсказать, будет ли вывод при одном определении; вызвать функцию дважды с разными аргументами и объяснить момент исполнения тела.
- Сопоставить параметры/аргументы; исправить вызов с отсутствующим аргументом на отдельном маленьком примере. Не выдавать полное тело formatter как подсказку в теории.
- Написать format_task(task) для полной модели, получить строку в переменную, затем вывести её снаружи. Состояние отображения не добавляется новым ключом status.
- Проверить две разные задачи, оба bool и границы priority 1/5; исходные поля остаются прежними. Формат содержит id, а не номер элемента списка.
- Заменить карточку 13 согласованным заданием на этот formatter. При сохранении режима solve предоставить адаптер проверки; ученик пишет предметный компонент, не два независимых formatter с разными моделями.
- Сохранить функцию в прежнем main.py, проверить её тем же поведением через объяснённую интерактивную оболочку после штатного exit приложения. Подготовленные данные не сохранять в рабочем коде; calc/exit продолжают работать.

**Наблюдаемый результат.** Функция определена и вызвана самим учеником, возвращаемая строка не равна побочному выводу. В файле один formatter с понятным контрактом, словарь не меняется, старый сценарий запуска сохранён.

**Выход и переход.** Базовый вызов освоен. Следующее занятие исследует его состояние и результат на нескольких путях, а не ещё раз просит написать тот же текст карточки.

### 13.1. Результат функции, локальные имена и состояние

**Основная тема и назначение.** Понять, что происходит с данными и именами во время вызова. Это опора для передачи общего списка в блоке 4, для обработки None и для создания независимых задач.

**Точка A.** Есть format_task, def/вызов/параметры/return, базовый None и модель общих объектов из 12.1. Подробное локальное переприсваивание и мутация аргумента ещё не исследовались.

**Точка B.** Ученик различает результат, вывод и изменение аргумента; объясняет несколько независимых вызовов и локальные имена. Постоянный create_task создаёт отдельный полный словарь для каждого набора проверенных значений.

**Необходимые темы, в порядке изучения:**

1. Место вызова получает результат, а не последнюю выполненную команду и не автоматически все внутренние имена. Вызов с print может одновременно что-то показать и вернуть None.
2. Полный путь return, раннее завершение, путь без return и return без значения. После возврата вызывающий код продолжается; при попытке использовать None как строку/число нужно восстановить договор, не придумать запасной результат.
3. Отдельные локальные имена каждого вызова. Одинаковое имя снаружи и внутри не является одной общей переменной; глобальный объект может при этом оставаться общим, если его передали аргументом.
4. При вызове параметр связывается с переданным объектом, а объект автоматически не клонируется. Локальное переприсваивание параметра и изменение поля/append этого объекта дают разные наблюдаемые результаты.
5. Функция может явно менять список/словарь и возвращать None по контракту. Контраст: функция с новым верхним объектом требует использовать её результат; от одного имени или return копия не появляется.
6. Независимость нового словаря на каждом вызове фабрики. Равное содержимое и один объект различаются; словарь не должен накапливаться в скрытом внешнем имени.
7. Create_task принимает task_id/title/priority и возвращает ровно id/title/priority/is_done. Входные данные уже проверены; фабрика не читает терминал, не назначает следующий id, не добавляет запись в список и не печатает успех.
8. Значение None у отсутствующего результата не равно пустой допустимой коллекции. В будущем поиск может вернуть None, поэтому перед чтением полей нужен предусмотренный путь; алгоритм поиска пока не реализуется.
9. Проверка контракта отдельно по двум каналам: возвращённое значение и состояние исходных объектов. Видимая правильная строка не доказывает отсутствие нежелательной мутации.

**Пока нельзя требовать.** Global/nonlocal, замыкания, изменяемые default-аргументы, генерацию id, try/except, полный find/done, автоматическую глубокую копию или проверку через ещё не изученную тестовую библиотеку.

**Основная практика.** Трассы маленьких исследовательских функций и одна постоянная фабрика.

- Предсказать вывод и сохранённый результат для функции с return, только print и веткой без return. Показать отдельно оба канала, а не назвать вывод результатом по умолчанию.
- Проследить два последовательных вызова с одинаковым локальным именем. Найти NameError при чтении внутреннего имени снаружи и исправить передачу результата.
- На подготовленных списке/словаре сравнить локальное переприсваивание параметра, изменение общего объекта и изменение копии. До запуска назвать ожидаемое состояние вызывающего кода, затем проверить его. Эти функции являются опытами, не новыми обработчиками Planner.
- Самостоятельно написать create_task с согласованным договором. На разных проверенных title/priority/id проверить точные четыре поля и is_done=False; не давать полный литерал фабрики как готовый ответ.
- Создать через одну фабрику две задачи. Изменить флаг первой и подтвердить неизменность второй; сравнить идентичность. Снова вызвать фабрику с теми же аргументами: содержимое может совпасть, объект должен быть новым.
- Если в исследовательской оболочке уже есть список задач, проверить, что один вызов фабрики сам не добавляет в него запись: список не является её входом или скрытой внешней зависимостью. Отдельно подтвердить отсутствие печати внутри фабрики. Само создание объекта не равно принятию задачи в приложении.
- Сохранить create_task в прежнем main.py и проверить через уже объяснённую оболочку; не добавить исследования мутации в рабочие команды. Проверить прежний calc и formatter.

**Наблюдаемый результат.** Ученик объясняет None, локальность и общий объект, отдельно проверяет эффект и возврат. Две созданные задачи независимы, все поля совпадают с моделью, фабрика не имеет скрытой обязанности чтения или добавления.

**Выход и переход.** Подготовлена предпосылка блока 4: общий список при вызове остаётся общим, возвращённое значение не заменяется печатью, отсутствие результата нельзя использовать как найденную запись. Декомпозиция дальше распределяет эти обязанности между уже понятными компонентами.

### 14. Декомпозиция: соединение правил без скрытых эффектов

**Основная тема и назначение.** Разделить знакомый сценарий по обязанностям и соединить функции без дублирования правил. Эффекты не запрещаются: их нужно размещать там, где они обещаны контрактом.

**Точка A.** Есть formatter, фабрика, понятный вызов и результат, общие/независимые объекты. В calc реально собраны durations; накопление и интерфейс работают. Normalize_title ещё не выделен в постоянную функцию.

**Точка B.** Ученик соединяет очистку, проверку известных значений, создание и форматирование; ввод/печать остаются снаружи. В calc знакомая сумма и очистка используются как функции, прежнее поведение не меняется.

**Необходимые темы, в порядке изучения:**

1. Декомпозиция начинается с ответственности, не с требования по функции на каждую строку. Назвать отдельные причины изменения: получить данные, очистить, проверить, создать, изменить состояние, показать.
2. Контракт: входы, результат, эффект и допустимые границы. Данные и чтение из input различаются; правило должно получать явное значение, а не тайно ждать пользователя.
3. Normalize_title делает ровно strip. Пустота является результатом очистки, не основанием выдумать название. Смена регистра не нужна проекту; прежний человеческий регистр сохраняется.
4. Проверка перед принятием: непустой очищенный title, priority 1–5, положительный назначенный id. Можно использовать знакомые выражения или небольшие обоснованные проверки; не собирать новый универсальный валидатор/обработчик ввода.
5. Композиция: результат очистки передаётся в create_task, результат фабрики в format_task, строка выводится вызывающим кодом. Не смешать одну задачу, строку и список; не создавать второй вариант модели внутри управляющей функции.
6. Функция вычисления зависит от явных аргументов и не меняет их. Для функции изменения договор другой: общий объект меняется осознанно, а вывод всё равно может оставаться у интерфейса. Слова «чистая» не означают обязательное копирование при любой операции приложения.
7. Скрытая глобальная зависимость и переданный список. Перенос в параметр делает вход видимым, но сам по себе не отменяет мутацию; каждый эффект всё равно проверяется.
8. Копия как обещание конкретного контракта. Для плоской задачи обновлённая копия сохраняет все четыре поля и не меняет исходный словарь; фильтрация новым списком может по-прежнему содержать исходные объекты. Это применение 12.1/13.1, не новое обещание глубокого копирования.
9. Выделение известной суммы durations в calculate_study_minutes. Интерфейс собирает ввод, функция считает, вызывающий код добавляет один перерыв и выводит минуты/часы/остаток. Бизнес-правило не меняется из-за появления def.

**Пока нельзя требовать.** Готовое add-меню, следующий id, handler-архитектуру, классы, модули/импорты проекта, искусственную чистоту всех операций, фильтр по полю done, новый вариант normalize через title() или try/except.

**Основная практика.** Реальная переработка прежнего файла и отдельная проверка композиции модели.

- Для имеющегося calc указать ввод, правило и вывод. Объяснить, что следует выделить и что останется в управляющем сценарии; не превращать один понятный print в отдельный бессодержательный helper.
- Написать normalize_title один раз. Проверить сохранение SQL/README и внутренних пробелов; пробельный ввод даёт пустую строку. Использовать функцию при чтении названия сессии, сохранив уже написанный повтор пустого названия.
- Выделить calculate_study_minutes из прежнего накопления по реально введённым durations. Не оставить вторую параллельную реализацию суммы в calc. Для пустого списка результат 0, исходный список не меняется.
- На проверенных учебных значениях последовательно применить normalize_title, существующий create_task и существующий format_task; вывести строку снаружи. Подобрать неверную пустоту/приоритет и показать отказ **до** создания принятой записи знакомым if, без исключений и без фиктивного списка задач.
- Переработать карточку 14 под такую композицию. Убрать обязательный title(), добавить task_id и is_done, синхронизировать ожидаемые словари и вызовы. Адаптер runner не диктует другую фабрику или второй normalize.
- В коротком дополнительном опыте сравнить явно изменяющую функцию и возвращаемую копию. Проверить оригинал после вызова, а не выбирать копию всегда потому, что она объявлена «хорошей». Один экземпляр задачи не становится полноценным CRUD-приложением.

**Наблюдаемый результат.** Постоянные normalize_title/create_task/format_task согласованы, правила не дублируются, пользовательский регистр сохранён. Реальный calc использует выделенные функции и работает как раньше. Ученик может отдельно назвать возвращаемое значение, изменение состояния и владельца print.

**Выход и переход.** Есть компонентный набор и связанный реальный сценарий. Ошибка теперь может проявляться у потребителя результата; следующее занятие учит проследить её обратно к производителю, не писать приложение заново.

### 15. Отладка данных и цепочки вызовов

**Основная тема и назначение.** Использовать ошибку как наблюдение о нарушенном правиле. Сначала установить причину, затем изменить её и подтвердить результат, не маскируя дефект запасным значением.

**Точка A.** Известны данные, условия, циклы, функции, None, локальные имена и контракты. Простые ошибки уже встречались; чтение цепочки traceback и организованная регрессия ещё не освоены.

**Точка B.** Ученик читает сообщение/путь вызовов, уменьшает воспроизведение, отличает симптом от причины и проверяет исходный, обычный и граничный случай. В постоянном проекте остаётся исправленный код без диагностики и подавления ошибок.

**Необходимые темы, в порядке изучения:**

1. Ошибка синтаксиса, ошибка выполнения и логически неверный результат. Последний может не иметь traceback; одинаковый цвет сообщения не означает одинаковую причину.
2. Последняя строка traceback, тип/сообщение, кадры своего файла, путь вызова функции и место проявления. Потребитель результата может сломаться из-за дефекта производителя.
3. SyntaxError и структура прямого файла: двоеточие, кавычки, скобки, отступ и строка выше указателя. При такой ошибке файл может не начать исполняться; не обещать вывод строк «до неё».
4. NameError: опечатка, порядок и локальность. TypeError: неподходящая операция/тип или вызов. ValueError: неподходящее содержание допустимого типа. Оба ошибочных примера в сравнении остаются ошибочными, предпочтительного среди них нет.
5. IndexError против KeyError, пустой набор против неполной модели. Get/default может скрыть договор и привести к следующему TypeError от None; восстановить обязательное поле у создателя.
6. Наблюдение фактического значения и type через временный print. Keys/items уже изучены; отладочная печать не становится частью формата карточки или результата solve.
7. Минимальное воспроизведение: оставить только данные и вызовы, сохраняющие дефект. Уменьшение примера не означает создать второй планировщик или удалить основной проект.
8. Одна гипотеза, одно причинное исправление, повтор того же входа. Следующая проявившаяся ошибка могла быть скрыта первой; это не обязательно новая поломка от исправления.
9. Проверка обычных и граничных сценариев, состояния исходных объектов и соседнего поведения. Затем убрать DEBUG, сравнить diff и проверить рабочий запуск.
10. Почему нельзя прятать непонятный дефект: понятный отказ по договору отличается от случайного значения или молчания. Обработчик исключений остаётся следующему блоку; код с try/except/pass здесь не является обязательным материалом для исправления.

**Пока нельзя требовать.** Try/except, pytest/unittest, logging, дебаггер IDE, файловое хранение, защиту любых внешних типов или реализацию всех возможностей Planner.

**Основная практика.** Контролируемые ошибки в редакторе плюс регрессионная проверка постоянных компонентов.

- Прочитать подготовленный traceback вызова formatter на намеренно неполной записи. Назвать строку проявления и источник пропущенного поля; восстановить полную модель, не переписать format_task на молчаливый default.
- Сохранить маленькую основу карточки 15, но не выдавать обе точные правки в самом условии. Сначала ученик исследует опечатку, затем после первого исправления обнаруживает смешение str/int; приводит свидетельство, выполняет известное преобразование и повторяет запуск. Проверка результата не сводится к print готового числа.
- На отдельных опытах различить потерянный return и локальное имя снаружи. Подобрать минимальный вход, найти контракт функции и исправить именно его; не использовать None как «ноль по умолчанию».
- Исследовать логический дефект без исключения: смену регистра названия, сброс суммы не на том уровне или изменение оригинала при обещанной копии. Показать, какая проверка результата/состояния отличает верный вариант.
- После выбранного исправления выполнить ошибочный, обычный и граничный случай. Для модели проверить все четыре поля, для чтения исходную запись, для фабрики независимость двух объектов.
- Проверить собственный main.py: calc на 0/1/2 занятиях, два независимых запуска расчёта в одном процессе, пустое название, неизвестная команда и exit. Для числовых полей использовать текущий ограниченный договор, не объявлять ValueError исправленным во всём интерфейсе.
- Удалить только собственную временную диагностическую печать, повторить ожидаемый вывод, посмотреть diff и сохранить проверенную версию. Намеренно сломанные примеры не остаются запускаемыми путями основной программы.
