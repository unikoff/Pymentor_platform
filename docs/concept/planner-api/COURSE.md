# Planner API: общая концепция курса

Курс развивает существующий Persistent Planner: к готовым модели, сервису, JSON-хранилищу и CLI добавляется синхронный HTTP API. Концепт составлен по [методичке](../CONCEPT_AUTHORING.md) и задаёт общую карту блоков 9–12. Подробные концепты блоков вынесены в отдельные файлы. Текущие номера и количество занятий служат ориентиром для переработки; необходимое содержание важнее прежней разбивки.

Это целевой маршрут. Его принятие не означает, что существующие теория и практика уже переработаны.

## 1. Контекст до курса: исходная точка A

### Что ученик уже освоил

Предыдущий курс углубляет Python и завершает Persistent Planner. К его концу ученик должен уметь:

- разносить программу по модулям, пользоваться импортами, функциями и объектами;
- описывать модель `Task` через `dataclass`, защищать правила данных и понимать изменяемые объекты;
- отделять операции `PlannerService` от хранения, соединять роли через композицию и согласованный контракт;
- использовать MemoryStorage для работы в памяти и JsonStorage для сохранения и восстановления задач;
- обрабатывать ожидаемые исключения, сохраняя состояние при ошибке;
- проверять отдельные правила и взаимодействие компонентов через pytest, включая временные файлы;
- оформлять запуск, архитектуру, приёмку и проверенную версию проекта через README и Git.

### С каким результатом он приходит

Persistent Planner имеет модель, сервис, два варианта хранения и тонкий CLI. Пользователь может добавлять, читать, искать, завершать и удалять задачи, получать статистику. С JsonStorage данные переживают создание нового экземпляра приложения. Итоговая практика проверяет рабочие и ошибочные сценарии, документацию и воспроизводимость.

Эта исходная точка подтверждается [финальной теорией предыдущего курса](../../../frontend/src/lessons/python-deeper/block8.tsx) и [проектной практикой](../../../backend/learning/rich_practice.py), а не только названием курса. Знакомство с pytest не означает, что ученик уже умеет тестировать HTTP API; наличие Python-модели не означает знания Pydantic.

### Какая новая потребность появляется

CLI работает рядом с пользователем. Чтобы с приложением мог общаться отдельный клиент по сетевому договору, нужны сообщения HTTP, адреса операций, проверка входа и определённая форма ответа. Ученик должен понять эту границу и построить её самостоятельно.

Учебная HTTP-часть называется **Planner API**, но это второй интерфейс того же проекта. Сохраняются существующие корень репозитория, app/models.py, app/services.py, app/storage.py, CLI и безопасная точка сборки build_service. Не создаём отдельный `studyhub-api` с копиями модели и операций и не переименовываем папку ради нового этапа.

CLI и API используют PlannerService с JsonStorage, указывающим на один рабочий `data/tasks.json`. В занятии про первое чтение ученик первым заданием создаёт данные через готовый CLI, а затем GET-маршруты читают результаты из этого проекта. Не пишет JSON руками, не объявляет второй список tasks и не загружает одноразовый снимок при старте сервера.

В памяти находятся объекты, полученные для конкретного действия, не второй источник истины. Каждое действие использует имеющийся договор load/save; новый экземпляр сервиса и перезапуск читают тот же файл. `tags` сохраняется в существующей Task и JSON, но не входит в публичный четырёхпольный ответ API. Добавление веб-интерфейса не удаляет старые поля данных.

## 2. Цель и итог: точка B

После курса ученик может разработать, проверить и объяснить небольшой REST API для задач. Он понимает путь от запроса клиента до изменения состояния и ответа; умеет отличить ошибочный ввод, отсутствующий ресурс и успешное действие; может передать другому человеку воспроизводимый проект.

Итоговый **Planner API v1.0.0**:

- запускается через FastAPI и Uvicorn, имеет Swagger UI и OpenAPI;
- поддерживает полный жизненный цикл задачи через существующий сервис и общий JSON-файл, доступный CLI;
- разделяет входные схемы и публичный ответ, проверяет данные до изменения состояния;
- сохраняет готовые модель, сервис, хранилище и CLI; HTTP-схемы и маршруты добавляются рядом, без второй реализации CRUD;
- проверяется HTTP-сценариями через Postman и автоматическими тестами через TestClient;
- имеет README, инструкции запуска и проверки, а также выпуск, соответствующий проверенной версии.

### Согласованный объём продукта

| Операция | Маршрут | Успешный результат |
| --- | --- | --- |
| Проверка сервиса | `GET /health` | `200`, состояние сервиса |
| Список задач | `GET /tasks` | `200`, список с фильтром, сортировкой и ограничением |
| Одна задача | `GET /tasks/{task_id}` | `200`, полная запись |
| Статистика | `GET /stats` | `200`, сводка по всему текущему хранилищу |
| Создание | `POST /tasks` | `201`, новая полная запись |
| Полная замена | `PUT /tasks/{task_id}` | `200`, полная запись с прежним `id` |
| Частичное изменение | `PATCH /tasks/{task_id}` | `200`, полная запись с применёнными изменениями |
| Удаление | `DELETE /tasks/{task_id}` | `204`, без тела ответа |

Запись содержит `id`, `title`, `priority`, `is_done`. При создании клиент обязательно передаёт `title` и `priority`; сервер назначает `id` и начальное `is_done=False`. `TaskCreate` описывает создание, `TaskRead` полный ответ, `TaskUpdate` обязательные изменяемые поля PUT, а `TaskPatch` отдельный частичный вход. Пропущенное поле PATCH сохраняется; явно переданное `false` применяется.

Для HTTP-входа заголовок очищается по краям и остаётся непустым; диапазон длины составляет 1–120 символов, приоритет от 1 до 5. Проверка длины до очистки не заменяет запрета строки из одних пробелов. Ошибочный вход даёт `422` без изменения состояния; корректный идентификатор отсутствующей задачи даёт `404`.

Для списка сохраняются `is_done=None`, `sort_desc=False`, `limit=10` и допустимый диапазон `limit` 1–50. Выборка выполняется в порядке фильтр → сортировка по `id` → ограничение. Она не меняет хранилище, а статистика не зависит от выбранных фильтров. Это договор итогового продукта; промежуточная реализация должна явно показывать, какая его часть уже работает.

## 3. Содержание, границы и необходимые изменения

### Что требуется изучить

1. **HTTP как договор.** Клиент и сервер, запрос и ответ, методы, URL, заголовки, тело, Content-Type, статусы, ресурс и адрес операции; различие path, query и body.
2. **Первое работающее приложение.** Отправка реального запроса, запуск сервера, роль FastAPI и Uvicorn, регистрация обработчика, Swagger/OpenAPI, передача данных из HTTP в обычную Python-функцию.
3. **Вход и существующий проект.** BaseModel, ограничения полей, чтение ошибок, направления схем, серверные поля; обращение маршрутов к PlannerService и JsonStorage, видимость сохранённых изменений после перезапуска; создание, чтение, два вида изменения и удаление.
4. **Качество и передача продукта.** HTTP-тесты и изоляция состояния, группировка маршрутов, разделение ответственности и зависимостей, регрессия, сквозная приёмка, документация и выпуск.

Связь между запросом, схемой, предметной операцией и хранилищем является обязательным содержанием. Эти роли должны быть понятны до их совместного применения. Python, JSON и pytest используются как знакомые основы; новая часть объясняет именно их роль на HTTP-границе.

### Что меняется при переработке

| Решение | Причина и целевой результат |
| --- | --- |
| Сохранить фундамент HTTP и итоговый договор одного ресурса | Ученик понимает механизм, затем реализует тот же согласованный продукт |
| Применить поиск и выборку в настоящих маршрутах блока 10 | Изученный path/query становится поведением сервера в том же блоке |
| Использовать готовые операции PlannerService и добавлять недостающие по ходу занятий | GET читает созданный CLI файл; первый POST реально сохраняет задачу, PUT/PATCH расширяют тот же сервис |
| Убрать временный список и отдельный API-проект | Код и данные предыдущего курса продолжаются, а не заменяются ручным контрольным набором |
| Дополнить переходы между схемами, состоянием и HTTP-ответом | Убрать скрытые предпосылки и объяснить, где завершается каждая ответственность |
| Убрать повторное написание создания и отдельную обязательную имитацию готового API | Повтор заменяется применением результата, проверкой или осмысленным рефакторингом |
| Перестроить финальный блок вокруг проверки и улучшения существующего приложения | Архитектура и тесты работают с уже наблюдаемым поведением; финал принимает накопленное |
| Сократить повторное введение знакомых Python-моделей, JSON-хранения и pytest | Освободить место для нового знания о HTTP, валидации и проверке API |

При составлении концептов блоков можно добавить недостающие темы, разделить перегруженные или объединить повторяющиеся занятия. Конкретные перестановки и число занятий определяются после карты необходимых знаний. Они не меняют конечный продукт и не добавляют новые сущности ради практики.

### Что остаётся за границами курса

- База данных, SQLite, SQLAlchemy, транзакции и миграции.
- Пользователи, авторизация, сессии, JWT и права доступа.
- Асинхронность, фоновые задачи, очереди и WebSocket.
- Docker, CI/CD, production deployment, Redis и оптимизация под нагрузкой.
- Новые поля и ресурсы HTTP API: `description`, теги, сроки, учебные материалы и другие функции будущего StudyHub. Уже существующий tags в модели/JSON не удаляется.

HTTP-приложение синхронное, JSON уже обеспечивает сохранение после перезапуска. Работа CLI и API с одним файлом проверяется последовательно, без одновременных записей. JsonStorage не объявляется безопасным многопользовательским или многопроцессным хранилищем; остаются ограничения конкуренции, размера данных и файловых операций. Не добавляем блокировки или транзакции скрыто ради этого этапа.

### Блок 9: понять взаимодействие до сервера

Центральный вопрос: как два участника договариваются об операции и её результате? Ученик связывает знакомые действия над задачей с HTTP-сообщением и может объяснить, какую информацию клиент передаёт и что ожидает в ответ.

Здесь оправданы отдельные упражнения на чтение и разбор сообщений. Они формируют модель взаимодействия. Итогом становится согласованный начальный договор Planner API. Механизм Pydantic и автоматический `422` не предполагаются уже известными; их вводит работа с FastAPI в следующих блоках. Подробная карта занятий и практики задана в [концепте блока 9](BLOCK_9.md).

### Блок 10: сделать договор наблюдаемым

Центральный вопрос: как сообщение доходит до существующей прикладной операции и превращается в ответ? Ученик сначала видит настоящий запрос в клиенте, затем добавляет API-модуль к своему Planner, сохраняя CLI и его данные. Первый контролируемый сетевой опыт может использовать echo-сервис; дальнейшие сохранённые запросы проверяют собственный API.

Поиск по path и выборка по query уже здесь подключены к серверу. Ученик наблюдает результат через Swagger/Postman, включая различие неверного path-значения и отсутствующего id. Для этого в блоке вводятся проверка типов параметров, ограничения `Query` и минимальное применение `HTTPException` для `404`; эти предпосылки не откладываются до общего разбора ошибок. Список и статистика используют общий источник данных. Изолированная функция без работающего маршрута не является выходом этого блока.

В первом занятии с чтением первое задание выполняется через CLI: подготовить один рабочий JSON с несколькими задачами. Затем GET /tasks и GET /stats вызывают готовый сервис, item использует его get_task, а query добавляет полезную выборку поверх этого же источника.

Последний слой блока принимает body через TaskCreate и сразу вызывает существующий add_task: успешный POST сохраняет задачу и возвращает полный четырёхпольный ответ с `201`. TaskRead как явная схема response_model появляется в следующем блоке. Временный echo с `200` не нужен. Подробная карта занятий и практики задана в [концепте блока 10](BLOCK_10.md).

### Блок 11: завершить жизненный цикл ресурса

Центральный вопрос: какие данные сервер принимает, каким состоянием владеет и как меняет его по договору? Ученик усиливает вход, разделяет направления схем и постепенно реализует операции над одним набором задач.

Созданная запись сразу видна через уже работающие list/get и статистику. Полная замена и частичный вход получают разные схемы. Удалённая запись больше не находится. Неверные данные и отсутствующий объект дают предсказуемый ответ без повреждения состояния. После каждой новой операции приложение сохраняет предыдущие возможности.

Выход блока является настоящим CRUD API с ручной HTTP-проверкой. Архитектура ещё может быть минимальной, но роли входа, операций и хранения уже понятны. Отдельные алгоритмические упражнения помогают исследовать механизм, а обязательный проектный результат не откладывается до блока 12. Подробная карта занятий и практики задана в [концепте блока 11](BLOCK_11.md).

### Блок 12: защитить и передать уже работающее

Центральный вопрос: как убедиться, что приложение можно безопасно менять и запускать без его автора? Ученик переносит опыт pytest на проверку HTTP-договора, обеспечивает известное начальное состояние тестов и защищает важные сценарии.

Группировка через APIRouter и разделение схем, операций, хранения и точки сборки выполняются над работающим приложением. Публичные пути, статусы и форма задачи сохраняются; регрессионные проверки подтверждают это при реорганизации. Спецификация уточняет уже применяемый договор, а не создаёт новый набор операций.

Сквозной сценарий проводится на реальном API и входит в его проверки. Финальная работа повторяет запуск, клиентские запросы, тесты и документацию, затем фиксирует доказанный выпуск. Она не начинает заново CRUD и не заменяет его ещё одной самостоятельной программой. Подробная карта занятий и практики задана в [концепте блока 12](BLOCK_12.md).

## 5. Проверка итога и продолжение

Общая цель достигнута, если ученик может:

1. Запустить приложение в чистом окружении по README и объяснить роли клиента, сервера, обработчика, схемы, операций и хранения.
2. Через HTTP создать задачу, увидеть её в списке и по id, полностью заменить, частично изменить, удалить и получить `404` при последующем чтении.
3. Проверить выборку и статистику: фильтр, направление сортировки и допустимый `limit` дают ожидаемый результат, а исходное состояние не меняется.
4. Объяснить и воспроизвести `201`, `200`, `204`, `404`, `422`; показать пустой body у DELETE и сохранность состояния после ошибочного ввода, включая пробельный заголовок.
5. Запустить HTTP-тесты с независимым состоянием и повторить результат; подтвердить, что рефакторинг не изменил публичный договор.
6. Передать README, согласованную спецификацию, Postman-коллекцию и проверенную версию, по которым другой человек воспроизведёт основные сценарии.

Проверяется не только работа кода, но и понимание: ученик объясняет, почему сервер назначает id, почему схемы входа и ответа отличаются, где возникает ошибка и какая часть приложения отвечает за изменение состояния.

Следующий курс получает **работающий и проверяемый Planner с CLI, HTTP API и JSON**, а не незавершённую сборку. Данные уже сохраняются после перезапуска. Новая потребность: заменить файловое хранение таблицами, запросами, связями и транзакционными возможностями SQLite/SQLAlchemy. Известные HTTP-сценарии и проверки становятся опорой этого перехода. Поля, маршруты и правила не переизобретаются скрыто при замене памяти на базу данных.

Для дальнейшей работы по каждому блоку из этой карты берутся его исходная опора, обязательные темы, роль в проекте и проверяемый выход. На их основе составляются отдельные концепты блоков; подробный план занятий в этом файле не задаётся.
