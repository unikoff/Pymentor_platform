# Блок 12. Проверяемый и воспроизводимый Planner API

Концепт составлен по [методичке для блоков](../BLOCK_CONCEPT_AUTHORING.md), продолжает [блок 11](BLOCK_11.md) и завершает маршрут [общей концепции курса](COURSE.md). Это план переработки, не утверждение, что существующие теория и практика уже изменены. Итоговый продукт и HTTP-договор сохраняются.

## 1. Назначение, контекст и A → B блока

### Назначение

Превратить уже работающий API в проект, который можно безопасно менять, проверять и передавать другому человеку. Новые возможности этого блока относятся к качеству разработки, а не к новым операциям над задачами.

Главный вопрос: чем подтвердить, что API делает обещанное, продолжает делать это после рефакторинга и запускается без помощи автора?

### Точка A

- В существующем Planner работают все восемь HTTP-операций: health, list/query, item, stats, POST, PUT, PATCH, DELETE. Отдельного проекта с копией ядра нет.
- TaskCreate, TaskRead, полная TaskUpdate и отдельная TaskPatch уже используются в настоящих маршрутах. Вход нормализуется и проверяется до записи.
- Готовые Task, PlannerService и JsonStorage продолжаются из прошлого проекта. HTTP-handlers находятся в app/api.py, CLI и build_service остаются в app/main.py; app.state.planner хранит выбранный сервис.
- Созданное и изменённое видно через последующие GET и stats. DELETE действительно удаляет запись и возвращает пустой `204`.
- CLI подготовил один рабочий data/tasks.json, API читает и изменяет его через сервис. Есть сохранённая Planner collection/environment и ручная приёмка, включая persistence после restart.
- Из прошлого курса знакомы pytest, assert, подготовка данных и проверка Python-функций. TestClient, группировка через APIRouter и проверка HTTP-договора пока не изучены.

Вход берётся из нового концепта блока 11, не из прежней схемы «алгоритмы пока только в интерпретаторе». Если при будущей переработке какой-то маршрут не работает, это незавершённый результат предыдущего блока, а не дополнительная задача на первую сборку CRUD здесь.

### Точка B

Ученик самостоятельно:

1. Проверяет реальное приложение через TestClient, различает статус, body и изменение состояния.
2. Создаёт независимые тесты с явным начальным состоянием; один сценарий не оставляет данные следующему.
3. Выделяет tasks-router без смены путей, схем, query-правил и статусов; доказывает перенос прежними тестами.
4. Защищает границы входа, отсутствие ресурса, копирование и согласованность общего состояния.
5. Проверяет взаимодействие всех операций на одном id и отделяет такую проверку от теста отдельного правила.
6. Воспроизводит установку, запуск и приёмку из чистого окружения, оформляет проверенную версию Planner API v1.0.0.

Выход: тот же Planner с CLI, синхронным API и JSON, но с проверенными импортами, HTTP-тестами, сохранёнными запросами, README и версией проверенного кода. Следующий курс улучшает уже постоянное файловое хранение, не впервые сохраняет задачи.

### Границы и ограничения

Не добавляем SQLite, SQLAlchemy, пользователей, авторизацию, Depends, middleware, async, Docker, CI/CD, облачный deploy, нагрузочные тесты или новые поля задачи. «Зависимости» в архитектурной части означают направление Python-импортов и используемые пакеты, не изучение FastAPI dependency injection.

Рабочие данные остаются в одном JSON и переживают restart/reload. Fixtures защищают рабочий файл от тестов, не дают JsonStorage транзакционность или безопасных конкурентных писателей. Чистая установка и GitHub Release не означают production deployment.

Все основные занятия проектные. Ученик пишет тесты, меняет организацию существующего кода и проверяет передачу проекта. Короткий эксперимент с импортом или копией допустим дополнительно; новый `solve`, заново реализующий CRUD, не является обязательным финалом.

### Неизменный договор продукта

| Часть | Правило, которое сохраняем и проверяем |
| --- | --- |
| Публичная задача | Ровно id/title/priority/is_done; прежний tags остаётся в доменной Task и JSON, update его не удаляет |
| Вход создания | Обязательные title/priority; сервер назначает id и is_done=False |
| HTTP-title и priority | Сначала очистка краёв title, затем длина 1–120; priority 1–5. Обычная проверка Pydantic, не неявный strict-режим; старый CLI не ужесточается скрыто |
| PUT | Полная TaskUpdate: title, priority, is_done обязательны; id сохраняется |
| PATCH | Отдельная TaskPatch; пропуск/null не меняют поле, явный false применяется. Пустой PATCH допустим |
| Id | Пустой источник даёт 1, иначе max текущих id + 1. Удалённый максимальный id может использоваться снова |
| Список | is_done=None, sort_desc=False, limit=10; limit 1–50; filter → sort по id → limit, без мутации источника |
| Статистика | total/open/done по всему источнику, независимо от query списка |
| Ошибки | Невалидный вход `422` до действия; корректный отсутствующий id с корректным body `404`, без upsert |
| Ответы | Чтение/PUT/PATCH `200`, настоящее создание `201`, удаление `204` без body |

Не ужесточаем extra-поля, преобразование типов, PATCH-null или правила id незаметно под названием «улучшение тестов». HTTP-ограничения проверяются на своей границе, старые модель/CLI не изменяются скрыто. Response-validation не откатывает уже выполненное save.

### Состояние теста и состояние ручной приёмки

Ручная практика продолжает один рабочий JSON, созданный/заполненный через CLI. Не объявляем seed-список и не очищаем файл для получения знакомых id или stats. Исходные счётчики берутся из текущего CLI; все изменения выполняются последовательно.

Автотест использует существующий JsonStorage с отдельным путём через уже знакомый tmp_path. Это безопасная изоляция теста, не второй учебный проект и не файл для ручного переноса. Запуск pytest никогда не очищает рабочий data/tasks.json и не подменяет JSON-хранение списком или MemoryStorage.

Function-scoped fixture собирает PlannerService через существующий build_service с тестовым JsonStorage. Перед TestClient она сохраняет рабочий app.state.planner и устанавливает тестовый сервис, после завершения восстанавливает выбранный сервис. Все handlers обращаются к текущему app.state, не к импортированному однажды глобальному списку. Client-fixture зависит от service-fixture явно и закрывает клиент до её teardown.

Каждый тест получает собственный JSON. Несколько запросов одного сценария накапливают изменения в нём; не очищаем файл перед каждым request. Unit-тесты используют тот же сервис без обязательного TestClient. Новый экземпляр сервиса с тем же тестовым путём нужен для проверки persistence, а новый клиент сам по себе не означает новое состояние.

Query-набор заполняется существующими операциями сервиса, при необходимости служебная fixture готовит Task через известный storage-контракт. Ожидания выводятся из id/состояний реально подготовленных Task; перестановка результата чтения не сохраняется обратно. Не берём данные предыдущего теста и не выдаём его файл за рабочий.

## 3. Паспорта занятий

### 63. Тесты FastAPI через TestClient и независимое состояние

**Основная тема и назначение.** Перенести проверку знакомого поведения из ручного клиента в повторяемый тест. Защитить готовое приложение до изменения его структуры.

**A.** HTTP и CLI работают через общий JSON; pytest и файловый tmp_path уже знакомы. HTTP-тестов и безопасной подмены рабочего сервиса для них ещё нет.

**B.** Небольшой набор независимых тестов проверяет все восемь операций. Каждый тест получает явное состояние, а несколько запросов внутри него взаимодействуют с одними данными.

**Необходимые темы, в порядке изучения:**

1. TestClient получает настоящее ASGI-приложение и проверяет HTTP-границу без ручного запуска Uvicorn. Это не проверка открытого TCP-порта или доступности сервера из Postman.
2. pytest запускает обычные test-функции; HTTPX нужен TestClient. Объяснить установку в окружение проекта и запуск `python -m pytest`, не надеяться на pytest из прошлого виртуального окружения.
3. Arrange/act/assert для API: состояние, request, status, body, последующее наблюдение. `json=` передаёт тело, `params=` задаёт query.
4. Независимость JSON-файлов разных тестов и сохранение между запросами одного теста. Новый клиент не очищает файл; reset перед каждым запросом разрушает жизненный цикл.
5. Fixture, conftest.py, function scope, зависимость fixtures, знакомый tmp_path, передача тестового сервиса в app.state.planner и восстановление после yield. Клиент закрывается до восстановления, рабочий JSON не затрагивается.
6. `response.json()` подходит JSON-ответу, `response.content` проверяет пустой DELETE. Ошибки реализации не маскируются режимом клиента или безусловным ожиданием `200`.

Механика клиента и HTTPX сверяется по [Testing FastAPI](https://fastapi.tiangolo.com/tutorial/testing/); подготовка и завершение fixtures по [описанию fixtures](https://docs.pytest.org/en/stable/explanation/fixtures.html) и [справочнику pytest](https://docs.pytest.org/en/latest/reference/reference.html#pytest.fixture).

**Основная практика.** В существующем проекте подготовить pytest/httpx, tests/conftest.py и tests/test_api.py. Импортировать тот же app из app.api; тестовый сервис собрать через прежний build_service(JsonStorage(path)), не создавать FastAPI-дубль.

- Настроить новый тестовый JSON на каждый тест и fixture передачи его сервиса в app.state.planner. Рабочий сервис восстанавливается после теста, содержимое рабочего файла не меняется; запросы сценария используют один тестовый файл.
- Проверить health, пустые list и stats. POST проверить по `201`, всем четырём полям, серверному id и is_done=False; последующий GET подтверждает запись.
- В отдельных тестах подготовить свою задачу через POST и проверить полноценный PUT, PATCH с явным false и DELETE с пустым `204`. Не брать id из результата другого теста.
- Проверить отсутствующий item с `404` и хотя бы один невалидный POST с `422`; после отказа чтение и stats подтверждают сохранность состояния.
- Запустить набор целиком дважды, затем выбранные тесты отдельно и в другом порядке явно заданными pytest node ids. Объяснить, почему два запуска в новых процессах сами по себе не доказывают независимость тестов внутри одного процесса.

Не переписывать CRUD, не добавлять HTTP-reset endpoint, не очищать рабочий файл и не заменять JsonStorage Mock/списком. Подробные границы и единый жизненный цикл будут отдельными результатами дальше.

**Выход и переход.** Проверки воспроизводимы и не требуют запущенного сервера. Следующий шаг переносит HTTP-handlers под защитой этого набора.

### 64. APIRouter, prefix, tags и include_router

**Основная тема и назначение.** Отделить группу маршрутов от точки сборки, сохранив внешний интерфейс. Новое устройство должно быть незаметно клиенту.

**A.** Handlers ещё в app/api.py; PlannerService, Task/JsonStorage и CLI сохранены. Базовые HTTP-тесты проходят до переноса.

**B.** Шесть tasks-операций находятся в подключённом router. Точные пути, методы, входы, ответы и состояние прежние; неизменность подтверждена тестами и сохранёнными запросами.

**Необходимые темы, в порядке изучения:**

1. APIRouter собирает path operations, но не создаёт второй сервер и не реализует отсутствующий CRUD.
2. Prefix и локальный path вместе образуют публичный URL. `/tasks` плюс пустой локальный путь сохраняет `/tasks`; локальный `/` дал бы `/tasks/`.
3. Include_router подключает операции к app. Декоратор на неподключённом router ещё не делает путь доступным.
4. Tags группируют Swagger, не добавляют Task.tags, не меняют права и HTTP-адрес.
5. API подключает router, router знает HTTP-схемы и вызывает выбранный PlannerService. Через Request.app.state.planner он получает текущий сервис без импорта app из api и без циклов. Объяснить минимальный Request до применения; body по-прежнему типизируется Pydantic, не читается вручную.
6. Redirect может скрыть случайную смену URL: проверять запросы с `follow_redirects=False`, а не принимать итоговый `200` после перенаправления за прежний договор.

Роль APIRouter/prefix/tags сверяется по [Bigger Applications](https://fastapi.tiangolo.com/tutorial/bigger-applications/); Request по [FastAPI Request](https://fastapi.tiangolo.com/advanced/using-request-directly/), доступ к app.state по [Starlette Applications](https://starlette.dev/applications/#accessing-the-app-instance). Depends и другая система конфигурации не вводятся.

**Основная практика.** Создать app/routers/__init__.py и tasks.py. Перенести готовые handlers и HTTP-перевод ожидаемого отсутствия, подключить router один раз в app/api.py. Старый app/main.py остаётся CLI.

- У router общий prefix `/tasks`. Для collection GET/POST локальный путь пустой, для item-операций `/{task_id}`. Не повторять prefix при include_router.
- Переносить по одному рабочему handler, удаляя прежнюю регистрацию после переноса. Не оставлять два конкурирующих обработчика одного method/path.
- Схемы импортируются из schemas.py, выбранный сервис берётся через Request.app.state.planner. GET /health и GET /stats остаются короткими handlers api.py; новое ядро и новый storage не создаются.
- После каждого завершённого переноса запускать базовые тесты. В них зафиксировать прямые ответы `/tasks` без redirect, сохранить `201`, TaskRead, полный PUT, PATCH и пустой `204`.
- Сверить `/docs`, `/openapi.json` и Postman: все восемь операций зарегистрированы, tasks сгруппированы, запросы не требуют новых путей.

Не переносить схемы и storage ещё раз, не добавлять новый app-factory, dependency injection или ресурсы. Цель достигается переносом HTTP-границы, не переименованием всего дерева.

**Выход и переход.** Структура стала понятнее, договор и тесты сохранились. Следующий шаг расширяет проверку от обычных успешных запросов до существенных границ.

### 65. Контракт API: границы, ошибки и регрессия

**Основная тема и назначение.** Превратить известный договор в исполняемые примеры. Не ограничиваться ответом «обычная задача создаётся» и не подменять тестирование написанием нового ТЗ.

**A.** Все маршруты организованы и защищены базовыми тестами. Ограничения title/priority, PUT/PATCH, query и ожидаемые ошибки уже изучены.

**B.** Существенные границы и отказы проверяются автоматически. Ошибка доказана не только кодом ответа, но и сохранностью прежних данных; OpenAPI соответствует текущим схемам.

**Необходимые темы, в порядке изучения:**

1. Классы примеров: обычное значение, допустимая граница, выход за неё, отсутствие, неправильный тип. Не требуется перебор всех комбинаций всех полей.
2. Регрессия как нарушение обещанного поведения после изменения. Конкретный тест нужен для конкретного риска, не ради количества assert или процента coverage.
3. Небольшая `pytest.mark.parametrize`: один проверяемый механизм, несколько именованных входов. Сложные генераторы, плагины и property-based testing не вводятся.
4. Ошибка input `422`, корректное отсутствие `404` и ошибка программы имеют разные причины. Не заучивать целиком текст библиотечной ошибки; проверять status и смысловой источник loc.
5. Запрет частичного эффекта: сравнение данных до и после неверного POST/PUT/PATCH. Проверка одного total не замечает испорченный title или is_done.
6. OpenAPI описывает зарегистрированные формы, тесты проверяют поведение. Документация схемы сама по себе не доказывает фактическую запись, порядок query или сохранение false.

Параметризация выбирается по [документации pytest](https://docs.pytest.org/en/stable/how-to/parametrize.html). Она вводится ради читаемой матрицы случаев, не как самостоятельная новая система проверки.

**Основная практика.** Добавить tests/test_contract.py, используя существующие state/client fixtures и настоящие маршруты.

- Для title проверить пустую строку, одни пробелы, чистую длину 1/120/121, очистку краёв и неподходящий тип; для priority границы 1/5 и отказы 0/6/нечисловой строки. Дополнительно сырой title длиннее 120 за счёт пробелов по краям, но с допустимым чистым значением, должен пройти: сначала проверяется чистое значение, не сырая длина.
- Для PUT проверить обязательность всех трёх изменяемых полей и сохранение id. Для PATCH проверить пропуск, явный null, пустой body и явный false; неправильный title не игнорируется молча.
- На существующей задаче зафиксировать запись и stats, отправить невалидные POST/PUT/PATCH, затем доказать, что содержимое не изменилось. Для обновления использовать действительный id, чтобы не смешивать две причины отказа.
- Для отсутствующего корректного id проверить GET/PUT/PATCH/DELETE с `404`, передавая корректное body. Отдельно неправильный path даёт `422`; при одновременно неправильном body не требовать специального приоритета ошибок.
- Проверить defaults query, оба is_done/sort_desc, limit=1/50 и отказы 0/51/неразбираемого значения. Подготовить реальные задачи в тестовом JsonStorage через готовый сервис, определить ожидаемые id из результатов, проверить filter → sort → limit. Файл и общая stats не меняются; жёсткие [1,7]/[9,7] и рабочая 5/3/2 не требуются.
- Сверить в OpenAPI пути и успешные статусы. У TaskCreate обязательны title/priority, у TaskUpdate все три изменяемых поля, у TaskRead все четыре публичных; у TaskPatch нет обязательных полей. Не сравнивать весь JSON побайтно и не требовать одну конкретную раскладку внутренних schema refs.

Короткую таблицу проверяемых обещаний можно добавить к README, но отдельный final-api-contract.md не является главным результатом. Старое временное echo с `200` и лабораторный DELETE-словарь в итоговых ожиданиях недопустимы.

**Выход и переход.** Внешние границы защищены без смены договора. Следующий шаг объясняет и проверяет, какие внутренние роли обеспечивают эти гарантии.

### 66. Границы слоёв и тесты прикладного ядра

**Основная тема и назначение.** Проверить, что понятная структура существует не только в названиях файлов. Тест обычной операции должен отделять прикладной дефект от ошибки HTTP-перевода.

**A.** Готовы прежние Task/PlannerService/JsonStorage/CLI, HTTP-схемы/router и тесты. Операции уже существуют и не нуждаются в новом написании.

**B.** Прежний сервис проверяется обычными Python-вызовами. Чтение не сохраняет JSON, обновление действительно сохраняет Task с tags, HTTP остаётся в router, импорты не замыкаются.

**Необходимые темы, в порядке изучения:**

1. Unit-проверка правила сервиса и HTTP-проверка взаимодействия отвечают разным вопросам. Знакомый pytest дополняет прежние tests/test_services.py, не начинает тестирование с нуля.
2. Build_service выбирает готовый storage; CLI/API переводят разные виды ввода; schemas проверяют HTTP-форму; PlannerService выполняет действие; JsonStorage сохраняет Task. Наличие нового файла не подтверждает обязанность автоматически.
3. API/router обращаются к сервису, service к договору storage/модели. Services/storage не импортируют api/router, HTTPException, Request или Response. CLI не получает второй алгоритм создания.
4. Доменная Task, её tags, публичная четырёхпольная проекция и JSON различаются. Чтение/изменение полученного объекта без save не должно незаметно менять файл; не навязываем прежнему MemoryStorage новый договор глубокого копирования.
5. Подготовленный вход методов PlannerService и непроверенный клиентский JSON различаются. Unit-тест использует действующие сигнатуры сервиса, не HTTP-словарь со status/items.
6. Рефакторинг не меняет поведение. Исправляем конкретное смешение роли под тестами, не вводим абстракции или пакеты только ради «красивой архитектуры».

**Основная практика.** Дополнить существующие tests/test_services.py и storage-тесты с реальным JsonStorage(tmp_path). Использовать прежние операции/сигнатуры, не писать второй CRUD.

- Проверить правило id для пустого источника и набора с пропусками; server-owned поля и полную форму созданной записи. Не обещать историческую уникальность после удаления максимального id.
- Проверить list/get/select и публичные проекции: без save файл не меняется, query не сохраняет перестановку/ограничение, stats считает весь JSON. Через новый сервис с тем же путём проверить persistence.
- Проверить, что replace/patch сохраняют результат вместе с прежним tags, отсутствие не создаёт item, delete удаляет выбранный id и не теряет соседние записи. DTO не заменяет полный JSON-формат Task.
- Проверить одинаковое состояние, наблюдаемое последовательными вызовами разных операций. Каждый тест получает свои данные; клиентская запись для другого теста не является скрытым arrange.
- Проследить импорты и путь запроса в реальных файлах. Если есть второй список, CRUD-дубль или HTTP в services.py, исправить этот конкретный дефект и повторить unit/HTTP-тесты. При верных границах результатом остаются новые проверки, не искусственный перенос.

Не вводить второй PlannerService, TaskBoard, repository-интерфейс, Mock-storage или универсальные контейнеры. Устное объяснение слоёв дополняет написанные проверки.

**Выход и переход.** Прикладные гарантии и направление зависимостей проверены. Следующий шаг проверяет их совместную работу в длинном HTTP-сценарии.

### 67. Сквозная приёмка: один ресурс через весь API

**Основная тема и назначение.** Показать, что отдельно правильные действия образуют правильный пользовательский путь. Новое умение состоит в проверке взаимодействия, не ещё одной реализации тех же действий.

**A.** Есть базовые HTTP-тесты, проверки границ и ядра. Все методы работают над одним источником; collection уже содержит отдельные запросы.

**B.** Один автоматический HTTP-сценарий прослеживает одну задачу от создания до отсутствия. Изменения наблюдаются через разные чтения и общую stats; ошибки в середине не разрушают путь.

**Необходимые темы, в порядке изучения:**

1. Сценарий во времени отличается от набора независимых проверок. Arrange выполняется один раз, id передаётся из фактического ответа, не вычисляется тестом вместо сервера.
2. Ответ записи и последующее чтение являются разными доказательствами. Красивый response может скрыть изменение копии без сохранения.
3. Контроль соседней записи выявляет слишком широкое действие. Query и stats дают другие представления того же состояния, не новые источники.
4. Ожидаемая ошибка в середине является частью успешного теста, если состояние и следующие действия правильны. Идемпотентное отсутствие после DELETE не требует одинаковых статусов повторов.
5. Автотест и Postman проверяют разные границы: приложение с изолированным тестовым JSON и сервер с рабочим файлом. Сценарий общий, пути к данным и исходная stats разные; pytest не очищает файл Uvicorn.

**Основная практика.** Добавить tests/test_workflow.py с одним связанным сценарием на реальном app через TestClient. Использовать пустое состояние и две создаваемые задачи: контрольную соседнюю и основную.

- Создать соседнюю задачу и основную с title, требующим очистки. Получить `201`, сохранить оба фактических id, проверить две полные записи, list и stats 2/2/0.
- Найти основную по id и query. Полным PUT изменить title/priority/is_done=True: id прежний, соседняя запись прежняя, stats 2/1/1.
- Отправить неправильное обновление и неполный PUT. После `422` основная запись, соседняя и stats остаются прежними.
- PATCH только с is_done=False сохраняет остальные поля и возвращает stats 2/2/0. Проверить прежние title/priority через GET; null/пустой PATCH не ломают путь.
- DELETE основной возвращает пустой `204`; stats становится 1/1/0. GET, повторный DELETE и корректные PUT/PATCH по удалённому id дают `404`. Между ними не создавать новую задачу: правило max текущих id допускает повторное использование удалённого максимума.
- Убедиться, что соседняя запись читается без изменений, health отвечает, query и stats согласованы. Повторить тест отдельно и в составе общего набора.
- Повторить путь через прежнюю Planner collection на работающем Uvicorn и JSON из CLI. Снять baseline N/O/D: после двух созданий N+2/O+2/D, завершения основной N+2/O+1/D+1, PATCH false N+2/O+2/D, удаления основной N+1/O+1/D. Проверить CLI и restart; фактические id не заменять фиксированными.

Postman не требует самостоятельного изучения JavaScript. Значения id можно перенести в environment вручную; готовый script допустим только как объяснённый вспомогательный инструмент. Не превращать collection в новую реализацию CRUD.

**Выход и переход.** Полный путь подтверждён кодом и внешним клиентом, прежние операции не переписаны. Последнее занятие проверяет, сможет ли этот результат воспроизвести другой человек.

## 4. Приёмка блока и переход к следующему курсу

### Сохранённая поверхность API

| Endpoint | Успех | Обязательная гарантия |
| --- | --- | --- |
| `GET /health` | `200`, status=ok | Сборка приложения и прежний простой ответ сохранены |
| `GET /tasks` | `200`, list[TaskRead] | Точный путь без redirect; defaults и filter → sort → limit сохранены |
| `GET /tasks/{task_id}` | `200`, TaskRead | Отсутствие `404`, неразбираемый path `422`; id не равен позиции |
| `GET /stats` | `200`, total/open/done | Подсчёт по всему общему источнику |
| `POST /tasks` | `201`, TaskRead | Серверные поля, реальная запись, вход проверен до действия |
| `PUT /tasks/{task_id}` | `200`, TaskRead | Полная форма, прежний id, отсутствие не превращается в создание |
| `PATCH /tasks/{task_id}` | `200`, TaskRead | Непереданное/null сохраняется, false применяется, результат записан |
| `DELETE /tasks/{task_id}` | `204`, без body | Выбранный ресурс удалён, соседние сохранены, последующее отсутствие `404` |

### Разные доказательства, не шесть одинаковых заданий

| Результат | Что доказывает | Чего не доказывает сам по себе |
| --- | --- | --- |
| Базовые HTTP-тесты | Методы, ответы и фактические действия приложения | Все границы и независимость без подготовленного состояния |
| Регрессионные проверки | Конкретные допустимые/недопустимые случаи и сохранность при отказе | Правильность каждого внутреннего слоя |
| Unit-тесты ядра | Отдельные правила, копии и действия над общим состоянием | HTTP-status, routing или запуск сервера |
| Связанный HTTP-workflow | Взаимодействие операций на одном ресурсе и источник stats | Доступность настоящего TCP-сервера |
| Postman-приёмка | Реальный запущенный сервер и сохранённые клиентские запросы | Независимость автоматических тестов |
| Чистая установка и версия | Воспроизводимость заявленного commit и инструкции | Устойчивое хранение или production readiness |

### Критерии готовности

- Все восемь операций проходят прежний договор до и после APIRouter. Нет дубликатов регистрации или скрытого `/tasks/` вместо `/tasks`.
- Fixtures дают отдельный JsonStorage/tmp_path на тест, не на request; рабочий JSON не меняется. Тесты проходят отдельно, вместе и в другом порядке; query-данные подготовлены в своём тесте.
- Проверены обычные случаи, важные границы, `404`/`422` и отсутствие частичного эффекта. Не зафиксированы случайные strict/extra-требования или полный текст ошибок библиотек.
- Unit-проверки используют прежние PlannerService/JsonStorage, HTTP-проверки настоящий app. Нет второго CRUD, Mock/MemoryStorage вместо файловой границы или самостоятельного seed-проекта.
- Workflow включает и полный PUT, и частичный PATCH с false, пустой `204`, сохранность соседнего item и stats. Удалённый максимум не проверяется после нового создания как будто историческая уникальность гарантирована.
- Каждый урок добавляет гарантию или улучшает передачу существующего проекта. Финал не повторяет реализацию маршрутов или первую сборку слоёв.
- Clean install, tests, документация и импорт collection повторены по инструкции. Релиз относится к проверенному commit; непроведённые внешние действия не заявлены выполненными.
- Ограничения JSON и нового SQL-хранения названы честно. MD/TSX/выдача практики будут синхронизированы при реализации концепта; сейчас они не объявлены переработанными.

### Что получает следующий курс

Следующий курс получает Planner API v1.0.0 как HTTP-часть прежнего Planner: Task/PlannerService/JsonStorage/CLI, рабочий JSON, четыре публичных поля, router, воспроизводимую установку и набор проверок.

Данные уже сохраняются после restart. Новая потребность: заменить ограниченное файловое хранение таблицами, ORM-моделью, SQL-запросами, связями и транзакционными возможностями SQLite/SQLAlchemy. Здесь эти механизмы не реализуются.

HTTP-договор и существующие сервисные границы становятся опорой перехода с JSON на SQL. Адаптируются хранение/операции и подготовка тестовой БД; не обещаем замену одного import без работы. Внешние сценарии, статусы, схемы и CLI не переизобретаются скрыто.

Курс закончен одним проверяемым проектом. Дальше он получает новое качество хранения, а не ещё один стартовый сервер и ещё одну реализацию того же CRUD.
