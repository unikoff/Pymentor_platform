Основной вопрос: как отдельная программа сообщает серверу своё намерение и понимает полученный результат?

### Точка A

- Ученик завершил Persistent Planner: модель Task, PlannerService, MemoryStorage, JsonStorage и CLI.

- Он понимает разделение интерфейса, прикладных правил и хранения внутри локальной программы. Сетевой договор, HTTP-методы, статусы и маршруты пока не изучены.

### Точка B

Ученик самостоятельно:

1. Объясняет ответственность клиента и сервера, источник актуального состояния и полный путь одного действия.
2. Читает request и response, различает адрес, метод, заголовки, тело и статус.
3. Выбирает HTTP-метод по смыслу действия, различает полную и частичную замену.
4. Различает ресурс, collection, item и endpoint; собирает согласованные method + path.
5. Размещает идентификатор в path, настройки чтения в query, данные изменения в body. Понимает, что роль поля зависит от операции.
6. Связывает запрос с ожидаемым успешным ответом и отличает отсутствие объекта, пустую коллекцию и ошибку сервера.

Проверяемый результат: выполненные упражнения с учебными Python-моделями сообщений, выбором метода, маршрута и источников данных плюс объяснение их смысла. На выходе есть начальный договор Planner API, выраженный картой и примерами. Обязательные Markdown-документы вместо основной практики больше не нужны.

### Границы

Это теоретический и исследовательский блок. Отдельные упражнения здесь оправданы: они формируют понимание, которое будет применяться в одном проекте начиная со следующего блока.

Python-словарь в практике является учебной моделью, а не сообщением, уже отправленным по сети. Внутри HTTP-примеров используем JSON-запись, внутри кода Python сохраняем его собственные типы и синтаксис.

## 3. Паспорта занятий

### 45. Почему CLI недостаточно: клиент и сервер

**Основная тема и назначение.** Плавный переход от локальной программы к взаимодействию отдельных программ. Не объявлять CLI плохим: показать его назначение и новую потребность в общем серверном договоре.

**A.** Готовый Persistent Planner и знакомый путь CLI → service → storage. Ученик ещё не знает устройство HTTP-сообщений.

**B.** Может объяснить, зачем новому API отдельный клиент, кто отвечает за окончательную проверку данных и почему локальная копия результата не заменяет состояние сервера.

**Необходимые темы, в порядке изучения:**

1. Локальный вызов функции и обращение к отдельному приложению; граница процесса без подробностей транспорта.
2. Клиент формулирует намерение и показывает результат. Он может помогать проверкой формы, но сервер повторно защищает собственные правила.
3. Сервер принимает намерение, применяет правила и управляет доступом к своему состоянию. Он не зависит от устройства конкретного клиентского интерфейса.
4. Клиент и сервер могут работать на одном компьютере. `localhost` и порт нужны для ориентации, не для настройки сетевой инфраструктуры.
5. Request и response как сообщения; полный путь создания задачи, включая ошибочный ввод. Структуру этих сообщений пока не требуем.
6. Два разных клиента используют один договор. Старый JSON-файл не становится общим сетевым интерфейсом нового приложения.

**Основная практика.** Устный разбор с заданными сценариями, который можно выполнить самостоятельно, проговорив объяснение без наставника. Документ, серверный код и номера HTTP-статусов не требуются.

- Сначала сравнить чтение списка в старом CLI и в будущем отдельном клиенте: кто принимает действие, где находятся правила и данные, как возвращается результат.
- Затем разобрать создание задачи: клиент получает ввод, сервер проверяет его, выполняет предметное действие и возвращает результат. Назвать последствия неуспешной проверки: запись не появляется, клиент получает объяснимый отказ.
- После этого рассмотреть браузер и бот, обращающиеся к одному серверу. Объяснить, почему правила нельзя независимо поддерживать только внутри каждого клиента.
- Исправить два ошибочных решения: клиент напрямую читает серверный файл задач; сервер считается обязанным знать расположение кнопок конкретного клиента.

**Выход и переход.** Ученик различает роли, может пройти весь сценарий без пропуска серверной проверки и не требует прямого доступа клиента к хранению. Следующий шаг уточняет, какую информацию должно содержать сообщение клиента.

### 46. HTTP request: адрес, метод, headers и body

**Основная тема и назначение.** Сообщение клиента содержит разные по назначению части. Собрать их в одну понятную модель, не подменяя HTTP обычным вызовом локальной функции.

**A.** Известны участники и путь взаимодействия; знакомы словари, условия, строки и JSON.

**B.** Ученик читает структуру request и собирает её из готовых значений, понимая роль заголовков и разницу между отсутствующим и пустым телом.

**Необходимые темы, в порядке изучения:**

1. URL как адрес назначения: схема, host, при необходимости порт и path. Адрес сервиса отличается от пути к файлу на компьютере.
2. Method сообщает намерение, path выбирает адрес операции. Для начала достаточно примеров GET и POST; полный выбор методов будет отдельной темой.
3. Headers описывают сообщение. `Accept` сообщает предпочтительный формат ответа, `Content-Type` формат отправленного тела; они не заменяют друг друга.
4. Body содержит данные операции. В принятом договоре чтение списка не переносит туда новую задачу; создание использует JSON с данными задачи.
5. Отсутствие body и пустой JSON-объект различаются. Условие по наличию не должно зависеть от того, пуст ли словарь.
6. Python-модель, JSON и настоящее HTTP-сообщение являются разными представлениями. Сериализация и отправка остаются за клиентом будущего блока.

**Основная практика.** Сохранить `solve(method, path, client_version, body)` в интерпретаторе. Вход: короткая запись `get`, `post` или `patch`, готовый path, версия клиента и словарь body либо `None`. Метод передан намеренно: задача не проверяет ещё не изученный полный выбор по действиям.

- Собрать headers с `Accept: application/json` и учебным `Planner-Client-Version` из переданной версии.
- Для присутствующего JSON-body добавить `Content-Type: application/json`, в том числе когда передан пустой словарь.
- Вернуть модель с ключами `method`, `path`, `headers`, `body`. Короткую запись метода привести к верхнему регистру до составления сообщения; path и body не менять.
- Не отправлять request, не печатать результат и не проверять предметную корректность переданных данных.

Проверяемые случаи: чтение без тела, пустой JSON-объект, заполненное тело создания, другой path с переданным PATCH. Заголовок версии используется только для обучения метаданным, не добавляется как обязательное требование будущего API.

**Выход и переход.** Собранная модель сохраняет смысл всех частей и различает `None` и `{}`. Ученик может объяснить каждый ключ. Следующий шаг изучает ответ на это сообщение.

### 47. HTTP response: status, headers, body и Content-Type

**Основная тема и назначение.** Ответ сообщает исход действия и его представление. Наличие текста или данных само по себе ещё не объясняет, успешна ли операция.

**A.** Ученик знает request и заголовки формата, умеет собирать учебный словарь сообщения.

**B.** Читает response в порядке status → допустимость и формат body → данные; различает успешный ответ с данными, успех без тела и ошибку.

**Необходимые темы, в порядке изучения:**

1. Response как отдельное сообщение. `print`, Python-словарь и реально полученный HTTP-ответ не являются одним и тем же.
2. Группы статусов: основной акцент на 2xx, 4xx и 5xx; 1xx и 3xx достаточно обозначить для чтения общей карты, без заучивания кодов.
3. `200` для успешного результата, `201` для создания, `204` для успеха без body. Пустой JSON-объект не равен отсутствующему телу.
4. `400` как общий пример некорректного запроса, `404` как отсутствие искомого ресурса, `500` как проблема сервера. Не обещать эти коды для любой ошибочной ситуации.
5. Body может представлять объект, коллекцию или ошибку. `Content-Type` помогает клиенту понять формат; сообщение ошибки также может быть JSON.
6. Request id помогает связать обработку сообщения, но не является id задачи. В нашем упражнении он передан готовым, его генерация и логирование не реализуются.

**Основная практика.** Сохранить `solve(status, body, request_id)` в интерпретаторе. Входы уже согласованы: статус задан, body является JSON-объектом в виде Python-словаря либо отсутствует. Для `204` заранее передан `None`.

- Добавить учебный `X-Request-ID` из `request_id` в headers.
- Для существующего JSON-body добавить `Content-Type: application/json`. В этой модели без body этот заголовок не добавляется.
- Вернуть точные ключи `status`, `headers`, `body`, не выбирая новый статус и не подменяя данные.
- Не создавать ресурс, не искать задачу и не обрабатывать исключения: упражнение изучает форму ответа.

Проверяемые случаи: `200` и `201` с JSON, `404` с JSON-ошибкой, `204` без тела, `200` с пустым объектом. Статус не нужно определять по содержимому body. Наличие `X-Request-ID` в модели не означает, что этот механизм уже добавлен в Planner API.

**Выход и переход.** Ученик различает отсутствие body и пустое представление, понимает назначение статуса и заголовков. Теперь можно связать форму сообщений с конкретным смыслом действий.

### 48. Методы GET, POST, PUT, PATCH, DELETE

**Основная тема и назначение.** Method выбирается по намерению и договору, а не по привычке отправлять всё через POST.

**A.** Известны части request/response и знакомы действия Planner. Полная и частичная замена ещё не предполагаются освоенными HTTP-механизмами.

**B.** Ученик выбирает метод для чтения, создания, полной замены, частичного изменения и удаления, объясняет различие PUT/PATCH и задуманный эффект повторного запроса.

**Необходимые темы, в порядке изучения:**

1. GET читает представление; для нашего API чтение не изменяет задачи.
2. POST в договоре Planner создаёт новую запись. Это использование в нашем продукте, а не утверждение, что HTTP допускает только такую роль POST.
3. PUT заменяет полное изменяемое представление выбранной задачи; id остаётся идентичностью ресурса. Для Planner передаются title, priority и is_done.
4. PATCH передаёт только изменяемые поля. Пропущенное поле сохраняется; явно переданное `false` является изменением, а не отсутствием значения.
5. DELETE удаляет выбранный ресурс. Не требовать создания, обновления или удаления данных в практике этого занятия.
6. Безопасность метода по назначению не равна защите доступа. Идемпотентность относится к задуманному эффекту, а не одинаковым ответам или выполнению строго один раз. Повтор DELETE может дать другой статус при том же эффекте; PATCH зависит от содержания изменения.

**Основная практика.** Сохранить `solve(action)` в интерпретаторе. На входе одно из шести известных действий: `list`, `get`, `create`, `replace`, `update`, `delete`; `update` здесь означает частичное изменение.

- Собрать таблицу `methods`, связывающую действия с методами из теории.
- Вернуть выбранный метод в верхнем регистре для каждого известного входа.
- Не добавлять пути, body, статусы и изменения состояния. Обработка неизвестного действия не требуется.

Проверяются все шесть действий. Чтение списка и объекта имеет одинаковый метод; полная и частичная замена разные. Разбор повторов остаётся объяснением семантики, не заданием на retries или ключи идемпотентности.

**Выход и переход.** Осмысленная таблица методов и понимание PUT/PATCH. Следующий шаг добавляет адрес ресурса, не заставляя заново решать выбор метода.

### 49. REST: ресурс, endpoint и URL

**Основная тема и назначение.** Связать метод с понятным публичным адресом. Ресурс и его представление не равны Python-классу или файлу хранения.

**A.** Ученик может выбрать метод для шести действий и знает форму request/response. Ещё не требуется распределять все входы по path/query/body.

**B.** Может отличить collection от item и получить согласованный method + path для каждого действия в пределах начальной карты Planner API.

**Необходимые темы, в порядке изучения:**

1. REST как архитектурный стиль; ресурсный подход и согласованные способы взаимодействия. HTTP с JSON сам по себе не объясняет все ограничения REST; здесь изучаем полезные для этого API соглашения, не полный архитектурный стандарт.
2. Ресурс tasks и публичное представление с id, title, priority, is_done. Tags остаются в прошлом продукте, не становятся новой задачей этого курса.
3. `/tasks` как collection и `/tasks/{task_id}` как выбранный item. Идентификатор нужен для адреса, но не доказывает существование записи.
4. URL, path и endpoint различаются. Для выбора обработчика в нашей карте важна пара method + path; одинаковый path может использоваться с разными методами.
5. Имена ресурсов в path вместо названий кнопок и функций. Отсутствие необходимости публиковать путь к серверному JSON-файлу.
6. `GET /health` проверяет сервис, `GET /stats` читает агрегаты по задачам. Это не повод вводить сущности Health или Stats и придумывать для них CRUD.

**Основная практика.** Новое упражнение `solve(action, task_id)` в интерпретаторе. В заготовке дана готовая таблица методов из предыдущей практики с GET для `health` и `stats`; её не требуется переписывать. Допустимые действия известны. Для item-действий передан целый id; для остальных `None`.

- Выбрать collection path для `list` и `create`.
- Выбрать item path с переданным идентификатором для `get`, `replace`, `update`, `delete`.
- Отдельно выбрать технические пути для `health` и `stats`.
- Вернуть словарь с ключами `method` и `path`, используя готовый метод и построенный адрес.
- Не разбирать произвольный URL, не проверять наличие задачи, не запускать router и не придумывать `404` для просто переданного id.

Проверяются восемь действий, разные item-id и одинаковый collection path у чтения и создания при разных методах. Достаточно знакомых условий и форматирования строк, без новых библиотек. Это модель выбора адреса, а не реализация маршрутизации FastAPI.

**Выход и переход.** Полная адресная карта без утечки файлов и внутренних классов. Ученик объясняет, почему метод и путь дополняют друг друга. Следующий шаг добавляет значения запроса и ожидания ответа.

### 50. Path, query, body и контракт API

**Основная тема и назначение.** Контракт связывает адрес, действие, расположение входов и ожидаемый ответ. Это завершение HTTP-модели, а не начало реализации хранения и CRUD.

**A.** Ученик знает участников, request/response, методы и адресную карту. Умеет работать с готовыми словарями, не изучал FastAPI-параметры и Pydantic-валидацию.

**B.** Собирает учебное описание запроса для известной операции, размещает значения по их роли и объясняет, какой ответ предусмотрен договором. Не смешивает клиентские данные с полями, которыми владеет сервер.

**Необходимые темы, в порядке изучения:**

1. Path выбирает item, query настраивает чтение collection, body передаёт данные создания или изменения. Headers остаются метаданными сообщения.
2. Обязательный item-id и optional query решают разные задачи. Отсутствие фильтра не является запросом только незавершённых задач.
3. Для списка предусмотрены is_done, sort_desc и limit. При отсутствии параметров серверный договор использует `None`, `False`, `10`; диапазон limit 1–50. Здесь описываем назначение, не реализуем валидацию или выборку.
4. Роль is_done зависит от операции: в GET это фильтр, в PUT/PATCH новое состояние задачи. Явное `false` нельзя потерять при отборе переданных значений.
5. POST передаёт title и priority; id и начальное is_done назначает сервер. PUT передаёт полную изменяемую форму, PATCH только переданные поля. Публичный ответ и вход создания различаются.
6. Успех и форма ответа входят в договор: объект, список, статистика или отсутствие тела. Пустой список возвращается с `200`, отсутствие item с `404`, удаление с `204` без body.
7. `400` остаётся общим HTTP-примером. Не записывать его как обязательный ответ будущего Planner API на ошибки полей: целевой курс использует `422`, механизм и точные правила которого изучаются позже с FastAPI/Pydantic.

**Основная практика.** Новое упражнение `solve(action, task_id, values)` в интерпретаторе. Заготовка уже содержит готовую функцию выбора method + path из предыдущей практики; упражнение самодостаточно и не требует импорта из другого занятия. Ученик добавляет только распределение данных.

- На входе известное действие, нужный для него id и словарь переданных значений. Все значения допустимы по типам и предметным ограничениям; неизвестных полей и явного `null` во входе нет.
- Для `list` разместить переданные is_done, sort_desc, limit в query. Не заполнять отсутствующие параметры автоматически: defaults относятся к поведению сервера, а не обязательным полям клиентского запроса.
- Для `create` сформировать body из title и priority, не добавляя серверные поля.
- Для `replace` использовать полный переданный body с title, priority, is_done. Для `update` только реально переданные поля этой формы; во входе есть хотя бы одно изменение.
- Для `get`, `delete`, `health`, `stats` использовать готовый path без query и body. Переданный item-id не дублировать в теле.
- Вернуть модель с точными ключами `method`, `path`, `query`, `body`. Query является словарём, при отсутствии body используется `None`. Не выполнять сетевой запрос, фильтрацию, генерацию id или изменение задачи.

Проверяемые случаи: список без параметров; список с `is_done=False`, sort_desc и limit; создание; полная замена; частичное изменение только `is_done=False`; чтение и удаление item; health и stats без входов. Отдельно проверить, что переданные values не меняются. В этой модели query хранит Python-значения; строковое кодирование URL выполняет реальный клиент следующего блока.

**Дополнительный устный разбор.** По двум готовым парам request-response объяснить результат: пустая collection с `200` против отсутствующего item с `404`; успешный DELETE с `204` против ответа создания с `201` и полной записью. Ученик описывает действия клиента, включая невозможность читать JSON-body у `204`. Сборка словаря не выдаётся за доказательство реального существования этих операций.

**Выход и переход.** Ученик умеет представить запрос и ожидаемый ответ по согласованной карте. Следующий блок переводит эту модель в реальные сообщения клиента и работающие маршруты, а не повторяет проектирование с нуля.

## 4. Приёмка блока и переход к следующему

### Начальный договор, который переносится дальше

Это карта будущих возможностей, а не утверждение, что сервер уже написан. Она служит общей опорой упражнений и последующей реализации.

| Endpoint | Вход | Ожидаемый успех |
| --- | --- | --- |
| `GET /health` | Без входов | `200`, короткое состояние сервиса |
| `GET /tasks` | Optional query: is_done, sort_desc, limit | `200`, список публичных задач, включая пустой список |
| `GET /tasks/{task_id}` | Path: task_id | `200`, одна публичная задача |
| `GET /stats` | Без входов | `200`, агрегаты по всему текущему хранилищу, независимо от query списка |
| `POST /tasks` | Body: title, priority | `201`, полная созданная запись с серверными id и is_done |
| `PUT /tasks/{task_id}` | Path: task_id; полный body: title, priority, is_done | `200`, полная запись с прежним id |
| `PATCH /tasks/{task_id}` | Path: task_id; переданные изменяемые поля body | `200`, полная запись с применёнными изменениями |
| `DELETE /tasks/{task_id}` | Path: task_id | `204`, без body |

Для корректного id отсутствующего item предусмотрен `404`. Подробные ограничения полей и ошибки валидации вводятся в будущих блоках; здесь нельзя подменять их общим обещанием `400`. Карта не расширяет продукт: один ресурс задач, без новых полей, пользователей и вариантов хранения.

### Критерии готовности

- Ученик объясняет ответственность сторон и один полный сценарий, не смешивая интерфейс клиента с правилами сервера.
- Учебные модели request/response корректно различают отсутствие body и пустой JSON-объект; метод, статус и значения не подменяются.
- Методы выбираются по смыслу, PUT и PATCH не смешиваются. Разница между идемпотентным эффектом и одинаковым response понятна.
- Адресная карта включает все восемь операций. Item-id влияет на path, а не на предположение о наличии объекта.
- Входы размещены по роли; явный `False` сохранён. Данные для фильтра не выданы за изменение задачи, серверный id не назначается клиентом.
- Ожидаемый response объясним: коллекция отличается от item, `200` с пустым списком от `404`, `201` от `204`.
- Практика не зависит от сети, сторонних сервисов или ручного создания документов. Готовый код предыдущих упражнений при необходимости включён в заготовки, а не требуется как неизвестный импорт.
- Ни один результат не называется работающим API до запуска настоящего сервера.

Блок 10 получает ученика, который понимает смысл отправляемых сообщений и начальную карту API. Его первая новая задача: увидеть настоящий обмен через HTTP-клиент, затем запустить собственное приложение и сделать договор наблюдаемым.

Самостоятельные Python-модели из этого блока не становятся модулями проекта и не импортируются в FastAPI. Переносится понимание, предметный договор и проверяемые примеры. Начиная с проектной части следующего блока основные занятия расширяют существующий Planner: сначала CLI подготавливает рабочий JSON, затем HTTP подключает чтение, создание, обновление, удаление и проверку качества к тому же сервису.
