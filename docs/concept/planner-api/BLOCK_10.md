# Блок 10. HTTP-интерфейс существующего Planner

Концепт составлен по [методичке для блоков](../BLOCK_CONCEPT_AUTHORING.md), продолжает [блок 9](BLOCK_9.md) и реализует [общую концепцию курса](COURSE.md). Это план переработки: к готовому проекту добавляется API, старые модель, сервис, JSON и CLI не заменяются прототипом.

## 1. Назначение, контекст и A → B блока

### Назначение

Связать HTTP с уже работающим Planner. Сначала наблюдаем запрос в клиенте, затем запускаем веб-интерфейс проекта, читаем созданные CLI данные и добавляем создание через HTTP.

Главный вопрос: как запрос приходит к существующему сервису и как его результат становится ответом?

### Точка A

- Из блока HTTP понятны клиент/сервер, методы, статусы, path/query/body и карта Planner API.
- В прежнем проекте есть Task, PlannerService, JsonStorage, MemoryStorage, CLI, тесты и безопасный build_service.
- Add/list/get/mark_done/delete/search/get_statistics работают через load/save. Статистика сервиса использует all/open/done.
- Веб-сервер, Pydantic и HTTP-разбор входа ещё не реализованы. Знакомые Python-аннотации сами по себе не являются runtime-проверкой.
- Корень проекта, app/main.py и его запуск CLI сохраняются. Нельзя требовать новую папку с копиями ядра.

### Точка B

В том же проекте работают health, GET /tasks, GET /stats, item, query и настоящий POST. CLI подготовил один рабочий JSON; GET читает его через сервис, POST сохраняет туда же. Перезапуск API не уничтожает задачи.

Ученик объясняет границы HTTP → сервис → JSON, различает 404/422 и видит результат операций другим интерфейсом. Полные PUT/PATCH/DELETE по HTTP остаются следующему блоку; TaskRead как отдельная response_model тоже ещё не введена.

### Границы и накопление результата

Не объявляем глобальный tasks, не создаём MemoryStorage вместо рабочего JsonStorage и не делаем снимок JSON при старте. Список, полученный в ходе load, является результатом чтения, а не новым источником истины.

Новые постоянные части здесь: postman и app/api.py. CLI остаётся в app/main.py; его не перезаписывают FastAPI-приложением. JSON открывает только прежний storage, не каждый handler. Доменная Task и её tags сохраняются; HTTP публикует только id/title/priority/is_done.

APIRouter, response_model, TestClient, Depends, SQLAlchemy, авторизация и async ещё не нужны. HTTPException/Query вводятся до применения. Для доступа к выбранному сервису достаточно одного app.state.planner; это объект PlannerService, не контейнер-копия задач.

Работа с JSON последовательная. CLI и API не должны одновременно изменять файл; безопасная конкурентная запись здесь не обещается.

### Что меняется

Текущая опора: [прежний план](../../PLANNER_API_BLOCK_10_PATH.md), [TSX](../../../frontend/src/lessons/planner-api/block10.tsx) и [практика блока](../../../backend/learning/course_content/planner_api/block_10/manual.py). Их старые прототипы ещё предстоит привести к этому маршруту.

- Первое задание первого предметного GET-занятия создаёт JSON через существующий CLI, не словари по таблице.
- Item использует готовый get_task, не вторую функцию поиска.
- Query расширяет сервис новым правилом выборки; прежний list_tasks и CLI не теряют полное чтение.
- Первый POST сразу вызывает add_task и возвращает 201 после сохранения. Двухпольного echo на маршруте ресурса нет.
- Убираются фиксированные seed-id, обязательная сводка 5/3/2 и ручное редактирование JSON ради опыта.

Для исследования нужны разные priority и оба состояния is_done; достаточно нескольких записей. Id назначает сервис. Ожидания выводят из фактического списка и статистики CLI, а не требуют заранее заданные id или число задач.

В API используется одна явная проекция Task → id/title/priority/is_done. Не возвращаем все внутренние поля через Task.to_dict, не удаляем tags из сохранённой модели. Переименование all → total выполняется только в HTTP-ответе статистики, сохраняя прежний get_statistics и CLI.

Основная практика path/query проектная. При реализации следует согласовать [manual.py](../../../backend/learning/course_content/planner_api/block_10/manual.py), [code_tasks.py](../../../backend/learning/course_content/planner_api/block_10/code_tasks.py), MD и TSX: старые code tasks не должны перекрывать проектные карточки в [загрузчике](../../../backend/learning/content.py). Этот концепт сам по себе выдачу заданий не меняет.

## 3. Паспорта занятий

### 51. Postman: отправляем запрос вручную

**Основная тема и назначение.** Увидеть настоящий HTTP через готовый клиент, пока собственного сервера нет. Echo отражает переданное сообщение, но не реализует Planner и не сохраняет задачи.

**A.** Понятны request/response и расположение данных. Проект Planner с CLI уже есть, сохранённые HTTP-запросы ещё не подготовлены.

**B.** Ученик отправляет GET и POST, находит переданные значения в ответе и сохраняет воспроизводимый набор без секретов. Понимает отличие ответа сервиса от ошибки соединения.

**Необходимые темы, в порядке изучения:**

1. Postman как HTTP-клиент, а не собственный сервер. Method, URL, Params, Headers, Body и область response.
2. Отличие учебной Python-модели от отправленного сообщения. Query в URL является строковым представлением, которое принимающий сервер может преобразовать по своему договору.
3. Роль Echo: показывать полученные query и JSON, не проверять бизнес-правила новой задачи. POST с `200` здесь не доказывает создание ресурса.
4. Чтение status, заголовков и body; поиск отражённых значений, а не только проверка наличия красивого JSON.
5. Collection сохраняет запросы, environment задаёт `base_url`. Полный сценарий включает method, path, данные и ожидаемую форму ответа, не только адрес сервера.
6. Запросы используют вымышленные учебные данные. Экспорты не содержат credentials, токенов и личных данных; интерфейс и способ сохранения объясняются для используемого режима Postman.

**Основная практика.** Работа через Postman с настоящими GET и POST. Добавить только папку `postman` в существующий проект Planner, сохранив имеющиеся файлы. Не требовать старых Markdown-документов и не создавать сервер до следующего занятия.

- Создать учебную collection и Echo environment с `base_url=https://postman-echo.com`.
- Отправить GET на `/get` с `is_done=false` и `limit=2` через Params. Найти отражённые значения и объяснить, что Echo получил строки, а не уже отфильтровал задачи.
- Отправить POST на `/post` с учебным JSON title и priority. Проверить формат запроса, статус и отражённое тело.
- Сохранить оба запроса и повторно выполнить их без ручного восстановления URL и body.
- Экспортировать collection/environment в подготовленную папку. Объяснить разницу между сохранённым запросом и несохранённым состоянием окна.

Дополнительные post-response scripts допустимы только как разобранный готовый инструмент. Самостоятельное написание JavaScript и изучение отдельного языка не являются обязательным результатом занятия. Ошибку транспорта или недоступность Echo не называем ошибкой Planner.

Эта роль Echo и отправка параметров соответствуют [документации клиента Postman](https://learning.postman.com/docs/use/send-requests/create-requests/request-basics) и [описанию передачи параметров и body](https://learning.postman.com/docs/sending-requests/create-requests/parameters/).

**Выход и переход.** Есть реальные отправленные сообщения и сохранённый клиентский набор. Следующий шаг добавляет сервер в тот же каталог, но для Planner создаются его собственные пути и ожидания ответа.

### 52. Первое FastAPI-приложение, Uvicorn и Swagger

**Основная тема и назначение.** Добавить сетевой вход, не разрушая знакомый локальный. FastAPI описывает маршруты, Uvicorn принимает запросы, CLI продолжает выполнять команды.

**A.** Есть рабочий Planner, его окружение и клиентский набор Postman. HTTP-точки входа проекта ещё нет.

**B.** Новый app/api.py отвечает на health; старый app/main.py по-прежнему запускает CLI без побочных эффектов от импорта.

**Необходимые темы, в порядке изучения:**

1. Два интерфейса одного ядра и разные точки запуска. Не создаём новую Task или репозиторий.
2. FastAPI, декоратор и обычный def-handler; JSON из возвращённого Python-значения.
3. Uvicorn и строка модуля/объекта app.api:app, запуск из корня проекта.
4. Swagger/OpenAPI показывают реально зарегистрированные операции, не все планы.
5. Ошибка запуска, HTTP 404 и 405 имеют разные причины; health не доказывает готовность предметных операций.

**Основная практика.** В существующем окружении установить FastAPI/Uvicorn, дополнить manifest и создать app/api.py с app и GET /health.

- Запустить `python -m uvicorn app.api:app --reload`; открыть health, docs и openapi.json.
- Проверить прежний `python -m app.main`: CLI не заменён и не запускается от импорта api.
- Создать Planner collection и Local environment с адресом своего сервера, сохранить health.
- Проверить неизвестный path и неподдерживаемый method, различив 404/405 и ошибку транспорта.

Не добавлять список задач или ещё одно хранилище на этом шаге. Главное новое поведение находится в постоянном API-модуле.

**Выход и переход.** У проекта два безопасных входа. Следующий шаг использует CLI для подготовки данных и подключает предметное чтение к тому же ядру.

### 53. GET-endpoints и ответы FastAPI

**Основная тема и назначение.** HTTP читает не демонстрационный список, а результат уже созданного Planner. Показать один источник данных и разные способы наблюдения.

**A.** Есть CLI, JsonStorage, add/list/get_statistics и health в app/api.py. Предметные HTTP-маршруты ещё не подключены.

**B.** Один JSON заполнен через CLI. GET /tasks и GET /stats читают его через тот же сервис; перезапуск не стирает записи, GET не сохраняет их обратно.

**Необходимые темы, в порядке изучения:**

1. JSON хранит данные между процессами; обычный список из памяти CLI не передаётся Uvicorn.
2. Готовый build_service выбирает JsonStorage и путь. Повторно не реализуем load/save, файловую сериализацию и CLI.
3. App.state.planner хранит выбранный PlannerService. Сервис получает актуальные задачи через storage при действии, не из снимка старта.
4. Доменная Task и публичный ответ различаются. Проекция содержит четыре API-поля; tags остаётся в модели и файле.
5. Get_statistics возвращает all/open/done; HTTP-адаптер публикует total/open/done, не меняя старый CLI-договор.
6. Пустая collection даёт 200 и [], отсутствие файла следует прежнему storage-договору. Повреждённый файл не принимается за пустое состояние и не перезаписывается.

Роль app.state сверяется по [Starlette Applications](https://starlette.dev/applications/#storing-state-on-the-app-instance). Здесь нужен один сервис, не новая система хранения или Depends.

**Основная практика.** Два последовательных задания в существующем проекте.

**Задание 1. Создать один рабочий JSON через CLI.**

- Запустить готовый CLI с JsonStorage и установить, какой data/tasks.json использует build_service.
- Через команды add добавить несколько учебных задач с разными title/priority, через done завершить часть. Для дальнейшей выборки нужны хотя бы две открытые и одна завершённая задача.
- Получить список и stats через CLI, записать фактические id и исходные счётчики. JSON создаёт/изменяет storage; руками файл не заполнять.
- Если данные уже существуют, не удалять их: добавить нужные задачи в тот же файл. Не создавать второй fixture/seed JSON рядом и не копировать его содержимое в Python.
- Завершить CLI и снова запустить его: задачи прочитаны из того же файла.

**Задание 2. Подключить GET /tasks и GET /stats к проекту.**

- В app/api.py использовать прежний build_service и сохранить сервис в app.state.planner. Не объявлять глобальный tasks и не кешировать результат load.
- GET /tasks вызывает list_tasks и возвращает проекцию реальных Task. GET /stats вызывает get_statistics и переводит all в total.
- Сравнить оба HTTP-ответа с фактическими list/stats CLI; не требовать 5/3/2 или заранее выданные id.
- После GET убедиться, что содержимое рабочего JSON не изменено. После restart/reload повторить запросы: данные сохраняются.
- Последовательно добавить/завершить задачу через CLI и снова выполнить GET без пересборки данных. API видит актуальный файл, не стартовый список.
- Сохранить requests в прежней Planner collection. Health и CLI продолжают работать.

Не добавлять storage-класс, новую модель задач, список словарей по таблице или повторный алгоритм статистики. GET-handler не открывает файл самостоятельно.

**Выход и переход.** API уже исследует результат своего проекта. Следующий шаг читает конкретную Task через существующую прикладную операцию.

### 54. Path-параметры и поиск объекта

**Основная тема и назначение.** Превратить id из HTTP-адреса в вызов готового get_task, отличая неверный вход от ожидаемого отсутствия.

**A.** Данные подготовлены CLI в одном JSON, работают health/list/stats. Поиск по id уже реализован в PlannerService.

**B.** GET /tasks/{task_id} возвращает реальную Task как публичный ответ; отсутствующий корректный id даёт 404, неразбираемый id 422.

**Необходимые темы, в порядке изучения:**

1. Имя path-параметра и аргумент handler, автоматический разбор task_id: int до вызова функции.
2. Идентичность не равна индексу. Id берётся из фактического ответа CLI/API.
3. Service.get_task и TaskNotFoundError уже существуют; HTTP-адаптер переводит ожидаемую ошибку в HTTPException 404.
4. Ошибка storage не является отсутствующей задачей. Не ловить любой Exception как 404.
5. Возвращаем проекцию Task; чтение не вызывает save и не удаляет старые поля файла.

**Основная практика.** В app/api.py добавить настоящий item-route и подключить app.state.planner.get_task(task_id).

- Использовать реальный id одной задачи из первого задания, проверить 200 и её поля.
- Выбрать отсутствующий корректный id из фактического набора; перевести TaskNotFoundError в 404 с detail Task not found.
- Неразбираемый path должен дать 422 до поиска. Не заменять отсутствие None с успешным 200.
- Сравнить файл, list и stats до/после чтений и отказов; CLI всё ещё видит те же записи.
- Сохранить успешный и ошибочные запросы в прежней collection.

Не писать find_task над отдельным списком, если готовый get_task уже решает задачу. Это новая HTTP-граница, не новая реализация поиска.

**Выход и переход.** Item и collection читают один проект. Далее добавляется управляемое представление списка, не новый источник.

### 55. Query-параметры, фильтрация, сортировка и границы

**Основная тема и назначение.** Настроить представление реальных данных, сохранив исходные Task, файл и прежний CLI.

**A.** Есть list/item/stats через сервис и JSON; ограничения query ещё не подключены. Текстовый search_tasks не является фильтром is_done.

**B.** GET /tasks применяет filter → sort по id → limit к результату сервиса. Файл и общая статистика не изменяются.

**Необходимые темы, в порядке изучения:**

1. Query разбирается в Python-типы; is_done=None отличается от явного False.
2. Defaults HTTP: None/False/10, limit 1–50. Query проверяет диапазон до действия, неверный вход даёт 422 без «исправления».
3. Постоянный select_tasks в PlannerService использует готовое list_tasks; выборка не сохраняется и не заменяет источник.
4. Сначала фильтр, потом сортировка, потом limit. Sorted/отдельный результат не переставляет исходное состояние.
5. Старый CLI-list остаётся полным: HTTP-default limit=10 не навязывается прежнему list_tasks.
6. Get_statistics считает все задачи, не текущую выборку. Публичная проекция не меняет доменную модель.

**Основная практика.** Добавить в существующий сервис select_tasks с optional is_done/sort_desc/limit и подключить проверенные query к тому же GET.

- Сервис использует list_tasks, без нового JSON-reader и дополнительной коллекции. Отсутствующий limit на прикладной границе может означать полное чтение; HTTP передаёт свой проверенный limit.
- По реальным CLI-данным определить открытые/завершённые id, ожидаемые возрастающий/убывающий порядок и первые элементы.
- Проверить is_done=false/true, оба sort_desc и limit=1/50. На наборе с несколькими открытыми убедиться, что ограничение не предшествует фильтру.
- Проверить limit=0/отрицательный/51/нечисловую строку и неверный is_done: 422, без изменения файла.
- После выборок повторить полный CLI-list, item и stats. В файле сохранились все задачи и tags; stats относится ко всему проекту.
- Дополнить collection. Не подставлять прежние [1,7]/[9,7] как обязательные id рабочих данных.

Если готовый сервис уже поддерживает такую выборку, переиспользовать её. Не добавлять offset/cursor, произвольную сортировку или новые поля.

**Выход и переход.** Query работает в проекте и не портит данные. Следующий шаг подключает существующее создание к JSON-body HTTP.

### 56. Pydantic BaseModel и request body

**Основная тема и назначение.** Структурированный HTTP-вход становится вызовом уже готового add_task. Входная схема не заменяет Task, а model_dump не заменяет save.

**A.** Веб-часть умеет читать; CLI уже создаёт и сохраняет Task. BaseModel и приём body ещё не изучены.

**B.** POST /tasks принимает TaskCreate, вызывает сервис, сохраняет Task в том же JSON и возвращает 201 с полной публичной записью. Ошибка входа не записывает данные.

**Необходимые темы, в порядке изучения:**

1. BaseModel, обязательные title: str/priority: int, связывание типизированного аргумента с JSON-body.
2. Body-ошибка обязательности/типа даёт 422 до handler. Обычное преобразование типов не равно strict-режиму.
3. Поля схемы создания и серверные поля результата различаются. Id и начальный is_done назначает прежний add_task.
4. Известные инварианты Task продолжают работать. На этом шаге ожидаемый ValueError именно от add_task переводится в 422; ограниченная обработка не превращает StorageError и программные ошибки в клиентский отказ.
5. Отказ не должен вызывать save; 201 объявляется только для действительно созданной и сохранённой записи.
6. Model_dump нужен для представления входа, не для записи файла. Дополнительные client id/is_done не управляют записью; не требовать rejection extra-поля без настройки.

**Основная практика.** В app/api.py объявить первую TaskCreate и добавить POST /tasks поверх app.state.planner.add_task.

- Модель содержит обязательные title/priority. Field, специальный before-validator, TaskRead и TaskUpdate пока не вводятся.
- Из проверенного payload вызвать готовое создание, вернуть проекцию созданной Task с 201. Не писать ещё один расчёт id, append или JsonStorage.save в handler.
- Проверить корректное создание: GET item/list/stats и затем CLI подтверждают новую запись. После перезапуска Task остаётся в файле.
- Отсутствующий priority и нечисловая строка дают 422 на body-границе. Пробельный title и недопустимый priority отклоняет прежняя модель/сервис с переводом ValueError в 422, без изменения файла.
- Проверить Swagger-схему и сохранить настоящий POST в Planner collection. Повтор успешного POST создаёт ещё одну запись, не повторяет echo.
- Не объявлять выполненным новое HTTP-ограничение длины 120: оно вместе с Field/нормализацией появится следующим шагом.

**Выход и переход.** Чтение и создание уже работают поверх существующего проекта. Следующий блок усиливает HTTP-валидацию и схемы ответа, затем добавляет недостающие обновления в тот же сервис.
