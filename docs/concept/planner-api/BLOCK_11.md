# Блок 11. Проверенный вход и полный CRUD существующего Planner

Концепт составлен по [методичке](../BLOCK_CONCEPT_AUTHORING.md), продолжает [блок 10](BLOCK_10.md) и уточняет [общую концепцию](COURSE.md). Это план переработки материалов, не заявление об уже изменённых занятиях. Рабочие CLI, сервис и JSON продолжаются; отдельный API-CRUD не создаётся.

## 1. Назначение, контекст и A → B блока

### Назначение

Усилить HTTP-договор поверх готового ядра и добавить недостающие способы изменения. Новые технологии используются в своём проекте: Pydantic проверяет вход и ответ, PlannerService выполняет действие, JsonStorage сохраняет Task.

### Точка A

- В существующем Planner сохранены Task, PlannerService, JsonStorage, CLI и прежние тесты.
- Веб-часть находится в app/api.py, выбранный сервис в app.state.planner; оба интерфейса обращаются к одному рабочему data/tasks.json.
- Работают health, list/query, item, stats и настоящий POST с 201. Создание уже вызывает add_task и сохраняет полный объект.
- TaskCreate пока проверяет обязательность/типы; старые инварианты Task защищают непустой title и priority 1–5. Обработчик переводит ожидаемые доменные ошибки в HTTP, не скрывая StorageError.
- Четыре API-поля являются проекцией Task; tags остаётся в модели и JSON. Данные не сбрасываются после restart/reload.
- Понятны 404/422, Query и HTTPException. Response_model, дополнительные ограничения Field, before-validator, PUT/PATCH-схемы ещё не изучены.

### Точка B

Ученик проверяет HTTP-вход до действия, разделяет TaskCreate/TaskRead/TaskUpdate/TaskPatch, реализует PUT/PATCH в существующем сервисе и подключает уже готовое удаление. Все восемь операций используют тот же JSON; CLI видит изменения API и наоборот.

Создание, поиск, JsonStorage и выдача id не написаны второй раз. Полное HTTP-обновление меняет только разрешённые поля, сохраняя id и прежний tags. Новый API не превращает файлы проекта в четырёхпольный формат вместо существующего.

### Границы

Не добавляем временный tasks, новый MemoryStorage для запуска, crud.py со второй реализацией сервиса, новые сущности, Depends, APIRouter, SQLAlchemy, auth, async или TestClient.

JSON уже изучен и работает. Пределы этого этапа: последовательная работа, отсутствие транзакций/безопасных конкурентных записей и ограничения файлового хранения. Перезапуск сохраняет файл; он не требует создавать записи заново.

Чтение получает актуальные данные через прежний load/save-договор. Нельзя сохранить список старта в модуле API и выполнять следующие операции по нему вместо JsonStorage.

### Что меняется по сравнению с прежним планом

Источник сравнения: [старый план](../../PLANNER_API_BLOCK_11_PATH.md), [TSX](../../../frontend/src/lessons/planner-api/block11.tsx) и [практика блока](../../../backend/learning/course_content/planner_api/block_11/manual.py).

- Вход уже содержит настоящий POST, не echo. Создание не откладывается до конца блока.
- Тема «хранилище в памяти» заменяется исследованием настоящего JSON-сохранения и server-owned id. JsonStorage не реализуется повторно.
- Роль прикладного ядра принадлежит готовому PlannerService, не новому crud-модулю.
- PUT/PATCH расширяют тот же сервис; DELETE подключает существующий delete_task.
- Убираются seed-таблицы, id=10 и фиксированная stats 5/3/2. Ожидания исходят из текущего файла.
- Все основные задания проектные, а не solve над отдельными списками.

### Общий договор

| Часть | Правило |
| --- | --- |
| Источник | Один рабочий JSON через существующий JsonStorage, не модульный список |
| Доменная Task | Существующие id/title/priority/is_done/tags и инварианты сохраняются |
| Публичная запись | Только id/title/priority/is_done; tags не удаляется из файла |
| HTTP-вход | Чистый title 1–120, priority 1–5; обычная Pydantic-конверсия, не неявный strict |
| Создание | Готовый add_task; id=1 на пустом источнике, иначе max текущих id+1; is_done=False |
| PUT | TaskUpdate: title/priority/is_done обязательны; id и непубличные поля сохраняются |
| PATCH | TaskPatch: пропуск/null не меняют поле, false применяется; пустой PATCH допустим |
| Query | None/False/10, limit 1–50, filter → sort по id → limit, без save |
| Ошибки | Вход 422 до изменения; корректный отсутствующий id с корректным body 404; StorageError не маскируется |

Ограничение HTTP-title до 120 добавляется входной схемой; прежние доменные проверки не удаляются и CLI не ужесточается скрыто. TaskRead описывает форму ответа, не фильтрует содержимое JSON-файла.

Дополнительный клиентский id/is_done не становится серверным. Unknown extra-поле при стандартной настройке модели не обязано давать 422. Rule max текущих id допускает повтор удалённого максимума; историческую уникальность не обещаем.

Новые постоянные части здесь: schemas.py и недостающие методы существующего services.py. CLI, build_service, модели, storage и данные не переносятся в новый проект. Источник практики [manual.py](../../../backend/learning/course_content/planner_api/block_11/manual.py) должен быть согласован с [code_tasks.py](../../../backend/learning/course_content/planner_api/block_11/code_tasks.py), MD/TSX и [загрузчиком](../../../backend/learning/content.py) при реализации карты.

## 3. Паспорта занятий

### 57. Pydantic-валидация и ошибка 422

**Основная тема и назначение.** Типизированный body может нарушать правила входа. Уточнить HTTP-границы до обращения к сервису, сохранив настоящую запись на успехе.

**A.** TaskCreate и POST уже работают через add_task/JSON. Известны доменные инварианты и перевод ожидаемого ValueError в 422.

**B.** TaskCreate нормализует title и проверяет чистую длину/priority до handler. Успех остаётся 201 с сохранённой Task, не превращается обратно в echo.

**Необходимые темы, в порядке изучения:**

1. Тип, обязательность и ограничение значения решают разные задачи. Field с min/max_length и ge/le не заменяет действие сервиса.
2. Очистка краёв до проверки длины: строка пробелов недопустима, raw-длина не равна чистой.
3. Field_validator before, декоратор, classmethod и возвращаемое значение. Сырой тип проверяется прежде strip; неподходящий тип даёт ошибку входа, не AttributeError/500.
4. Чтение loc/type/msg без заучивания полного библиотечного текста.
5. HTTP-проверка не отменяет инварианты Task для CLI и других вызовов. Повторно реализовывать add_task не требуется.

**Основная практика.** Усилить существующую TaskCreate и повторить запросы к тому же POST.

- Проверить пустой/пробельный title, чистую длину 121, priority 0/6, отсутствующие поля и неподходящий тип: 422, JSON не изменён.
- Проверить чистую длину 1/120, границы priority 1/5 и очистку краёв. Raw-title длиннее 120 только из-за краевых пробелов с допустимым чистым значением проходит.
- После успешного 201 прочитать запись API и CLI, затем после restart. Не ограничиваться непосредственным ответом POST.
- Сравнить содержимое файла и stats до/после отказа, не только число задач. Обновить сохранённые запросы.

**Выход и переход.** Вход точнее проверен, рабочее сохранение осталось. Далее разделяются HTTP-схемы входа и ответа.

### 58. Разные схемы: вход и публичный ответ

**Основная тема и назначение.** Данные клиента, доменная Task, JSON-формат и публичная запись имеют разные роли.

**A.** Работает входная валидация и реальный POST 201. Ответы уже проецируют четыре поля из Task, сохраняя tags в проекте.

**B.** TaskCreate и TaskRead находятся в schemas.py, response_model защищает публичные ответы. JSON и CLI не меняют формат.

**Необходимые темы, в порядке изучения:**

1. TaskCreate содержит title/priority, TaskRead все четыре API-поля, существующая Task остаётся доменной моделью.
2. Response_model проверяет/фильтрует ответ; неправильный серверный ответ не клиентский 422 и не автоматический rollback.
3. DTO/model_dump не записывают файл. JsonStorage продолжает использовать Task.to_dict/from_dict со старыми полями.
4. Импорт схем сохраняет нормализацию; TaskUpdate появляется вместе с PUT, не заранее как пустая архитектура.
5. OpenAPI описывает реальные маршруты и направление моделей.

**Основная практика.** Создать app/schemas.py, перенести TaskCreate с её правилами и добавить TaskRead.

- Применить list[TaskRead] к GET /tasks, TaskRead к item и уже работающему POST с 201.
- Проверить формы документации, query, отказ item и нормализующий POST.
- Убедиться, что TaskRead/публичная проекция не вырезает tags из существующих JSON-записей и CLI.
- Проверить, что серверные поля не задаются входной моделью. Не ожидать 422 для extra-ключа без отдельной настройки.
- Не менять успешный POST на 200 и не создавать искусственный id ради response_model.

**Выход и переход.** HTTP-формы явны, существующий файл и модель сохранены. Далее подтверждается, где происходит реальное сохранение и выдача id.

### 59. JSON-хранилище и серверные идентификаторы

**Основная тема и назначение.** Исследовать действующий путь создания и доказать его сохранение за пределами одного процесса.

**A.** POST вызывает готовый add_task; JsonStorage и правило id изучены раньше. API и CLI уже используют один путь к данным.

**B.** Ученик прослеживает payload → service → Task → save → ответ, подтверждает server-owned поля и persistence новым экземпляром проекта.

**Необходимые темы, в порядке изучения:**

1. Следующий id определяет существующий сервис по фактическим записям, не длина списка и не клиентский ввод.
2. Pydantic-вход, Task и сохранённая запись различаются. HTTP-handler не знает JSON-сериализацию.
3. Сохранение должно завершиться до успеха операции; response 201 сам по себе не доказывает файл.
4. Общий абсолютный путь и новый load на действие важнее общего Python-объекта между процессами.
5. Max текущих id допускает повтор удалённого максимума. JSON не получает транзакционность или безопасных конкурентных писателей автоматически.
6. Ошибка чтения/записи не является пустым новым проектом; не ловить StorageError как 422/404 и не затирать файл.

**Основная практика.** Продолжить существующее создание и дополнить его проверки, не реализовать JsonStorage или id второй раз.

- Через POST создать две задачи, сохранить фактические id, увидеть их через GET и CLI. Сравнить с прежними записями, не требовать id=10.
- Проверить server-owned id/is_done при extra-полях клиента и сохранение только объявленных входных значений.
- В имеющиеся сервисные pytest-проверки добавить/уточнить id и чтение тем же JsonStorage из нового экземпляра сервиса. Не писать FastAPI-дубль или solve; для автоматического теста использовать привычный tmp_path, не рабочий файл.
- Перезапустить API и подтвердить созданные данные и неизменность соседних записей/tags. После последовательной CLI-команды следующий GET получает актуальный файл.
- Если обнаружены кеш старта, другой path или append в handler, убрать эту конкретную подмену и вернуть готовый add_task как единственное создание.

**Выход и переход.** Сохранение и идентичность подтверждены для настоящего проекта. Далее закрепляются общие обязанности сервиса и интерфейсов.

### 60. Единый PlannerService для CLI и API

**Основная тема и назначение.** Прикладное ядро остаётся одним, несмотря на второй интерфейс. Улучшение структуры не должно означать второй набор функций CRUD.

**A.** Готовы service/storage/model, HTTP чтение/создание, query и проверки JSON. CLI продолжает пользоваться теми же операциями.

**B.** Общие правила и ошибки имеют одну реализацию. Добавлены проверки новой select_tasks и сохранности прежних контрактов CLI, нет слоя-дубля.

**Необходимые темы, в порядке изучения:**

1. CLI переводит текст, API HTTP; оба вызывают PlannerService. Services не импортирует FastAPI или JsonStorage-сериализацию.
2. JsonStorage владеет файлом; точка сборки выбирает путь/объекты; API state хранит сервис, не задачи.
3. TaskNotFoundError/ValueError/StorageError имеют разные причины. HTTP-граница переводит ожидаемое, не подавляет программную ошибку.
4. Select_tasks добавляет новое представление, не меняет старое list_tasks. Статистика all и внешнее total не требуют двух алгоритмов.
5. Возвращённый объект и запись файла различаются; изменение без save не должно выдавать себя за сохранённую операцию.
6. Знакомые unit-тесты сервиса проверяют новые правила без запуска Uvicorn; TestClient вводится позже.

**Основная практика.** Дополнить существующие tests/test_services.py и проверить реальные файлы проекта.

- Проверить select_tasks на данных собственного тестового JsonStorage: filter → sort → limit, явный false, неизменность файла и полный прежний list_tasks.
- Проверить list/get/get_statistics после сохранения новым экземпляром сервиса; выборка не становится источником статистики.
- Проверить направление импортов и границы API/CLI. Если копии поиска, статистики или add_task остались в handler, заменить их вызовом готового сервиса.
- Общую публичную проекцию и перевод ожидаемого отсутствия оформить один раз в HTTP-части, если там возникли повторения. Не вводить универсальную систему ошибок.
- Повторить CLI и HTTP на рабочем JSON, сохранив старые форматы команд/полей. Не создавать crud.py, новый service или MemoryStorage для запуска вместо JSON.

**Выход и переход.** Один проверенный сервис обслуживает оба интерфейса. Теперь в него добавляются действительно недостающие операции полного и частичного обновления.

### 61. PUT и PATCH: полная и частичная замена

**Основная тема и назначение.** Два договора изменения расширяют существующий PlannerService, а не обрабатывают очередной учебный список.

**A.** Есть реальное создание/чтение и сохранение. Mark_done умеет завершить Task, но не заменяет произвольный PUT или PATCH с false.

**B.** TaskUpdate/TaskPatch и новые replace_task/patch_task сохраняют изменения в том же JSON, оставляя id/tags и непереданные значения.

**Необходимые темы, в порядке изучения:**

1. Полная TaskUpdate требует title/priority/is_done; TaskPatch разрешает пропуск/null.
2. Exclude_unset и exclude_none по нашему договору отбирают эффективные поля. False сохраняется, exclude_defaults не подменяет этот механизм.
3. Полный HTTP-вход заменяет все три изменяемых поля, не все поля доменной Task: id и tags не относятся к клиентскому update.
4. Создание проверенной новой версии до save, без частичного сохранения при ошибке. Использовать прежнюю Task и её инварианты.
5. Отсутствие вызывает TaskNotFoundError и HTTP 404, не upsert. Body с ошибкой остаётся 422, приоритет над одновременно неверным id не придумывается.
6. Обновление должно попасть в JSON; красивого ответа с изменённой копией недостаточно.

**Основная практика.** Добавить DTO в schemas.py и недостающие методы в существующий services.py, затем подключить PUT/PATCH в api.py.

- Использовать уже созданную Task, сделать полный PUT и проверить через новый load/CLI/GET. Id и прежние tags сохранены, все три публичных изменяемых поля заменены.
- Неполный/невалидный PUT даёт 422 без изменения файла. В сервисных тестах отказ не приводит к save.
- После is_done=True применить PATCH только is_done=False: прежние title/priority/id/tags сохранены, общая stats отражает изменение.
- Проверить PATCH title с очисткой, пустой body и null как неизменность, пробельный title как 422.
- Для корректного отсутствующего id и корректного body получить 404 без новой записи.
- Сохранить всю доменную Task через прежний storage-контракт, не массив TaskRead.model_dump и не список из модуля API.

**Выход и переход.** Новые обновления уже работают в проекте и переживают перезапуск. Далее HTTP получает готовое прикладное удаление.

### 62. DELETE, 204 и HTTPException

**Основная тема и назначение.** Добавить HTTP-представление готового delete_task и честно показать отсутствие ресурса после сохранённого удаления.

**A.** CLI умеет удалять; API умеет создавать/читать/обновлять. Все операции пользуются общим service/JSON.

**B.** DELETE удаляет через прежний сервис, возвращает пустой 204; CLI/GET подтверждают отсутствие и сохранность остальных задач.

**Необходимые темы, в порядке изучения:**

1. Операция delete уже существует; HTTP выбирает статус, не storage и не новый учебный алгоритм pop.
2. Успешный 204 не содержит объект, массив или JSON null; использовать пустой Response, без TaskRead к этому успеху.
3. TaskNotFoundError превращается в 404, неправильный path в 422 до действия; StorageError не маскируется.
4. Повторное удаление без нового создания сохраняет отсутствие, хотя возвращает другой статус.
5. Сохранение удаления в JSON и последующий новый load являются доказательством, не один ответ DELETE.

**Основная практика.** Подключить DELETE /tasks/{task_id} к app.state.planner.delete_task.

- Создать учебную Task через готовый POST, выполнить PUT/PATCH и удалить по фактическому id. Получить пустой Response со статусом 204.
- Проверить отсутствие через GET, CLI и после restart; не пытаться json-разобрать пустое тело.
- Повторный DELETE и GET дают 404, неверный path 422. Между проверками удалённого максимума не создавать новую Task.
- Убедиться, что соседние записи и tags сохранены; stats меняется по фактическому набору, не фиксированной таблице.
- Пройти полный HTTP-путь и сохранить запросы в прежней collection. Delete_task и JSON-сериализация не переписаны.

**Выход и переход.** Весь HTTP CRUD работает в существующем Planner. Далее защищаем его TestClient, организуем маршруты и передаём воспроизводимую версию.

### Сквозная приёмка

Перед началом снять фактическую статистику N/O/D через CLI. Создать одну открытую Task: N+1/O+1/D. Полным PUT завершить её: N+1/O/D+1. PATCH false: N+1/O+1/D. DELETE возвращает исходные счётчики. Ошибки в середине не меняют запись или файл.

После записи подтвердить результат чтением API, CLI и новым экземпляром сервиса/перезапуском. Не очищать файл для получения знакомых id. Контроль соседних записей включает их непубличные tags. Не создавать новую Task между удалением максимального id и проверками 404 по нему.
