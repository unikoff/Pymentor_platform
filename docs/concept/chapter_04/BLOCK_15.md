### Точка B блока = A16

**Понимание и самостоятельные действия.** Ученик может проследить запрос/команду от входа до SQL, показать границу предметной валидации, транзакции и ресурса. **Рабочий продукт.** Один PlannerService и полный SqlTaskRepository обслуживают прежние API/CLI. Одна Session выделяется на запрос или отдельную CLI-команду, Engine и фабрика переиспользуются. Запись подтверждается до ответа/сообщения об успехе; ошибка до commit приводит к отмене и освобождению ресурса. Предметные и HTTP-правила сохранены.

**Источник данных.** Оба интерфейса используют один DATABASE_URL и одну SQLite-базу. Прежние задачи перенесены без смены id и потери полей. **Проверки.** Есть изолированные проверки предметных операций, маршрутов, CLI, переноса и связанного сценария между интерфейсами. **Что остаётся блоку 16.** Углубление классификации ошибок хранения и безопасного HTTP 503, расширенные проверки отказов, наблюдение SQL и доказанное улучшение запросов, сквозная приёмка и воспроизводимая передача. Это полировка уже работающего продукта, не первое появление rollback, CRUD, поиска или удаления JSON. Миграции схемы остаются за пределами всей главы.

### Общие решения и ограничения для паспортов

1. **Штатный источник до 75 только JSON.** SQL-проверки 71–74.1 выполняются на отдельной файловой SQLite-fixture. Частичный override допускается только в тесте готовой операции; неполный SQL-репозиторий не становится default и не обращается к JSON ради недостающего метода.
2. **Один сервис и один набор маршрутов.** Не создаём второй PlannerService, новые TaskCreate/TaskRead, демонстрационный POST или SQL в endpoint. Сохраняем текущие имена методов сервиса и согласованный в 69–69.1 договор репозитория.
3. **Владелец транзакции определяется в 71.** Сервис охватывает целое изменение, начиная до первого SQL-чтения для этого изменения. Репозиторий выполняет запросы/flush, но не commit отдельных частей; get_db и CLI-контекст закрывают ресурс, не подтверждают запись после ответа. Понятный отказ/успех важнее дополнительного архитектурного слоя.
4. **Минимальная связь сервиса с транзакцией.** Развить build_service передачей простой фабрики контекста изменения, условное имя `write_scope`: SQL-сборка связывает её с Session.begin, сервис использует её вокруг изменяющего сценария. Это небольшая зависимость, не отдельный универсальный UnitOfWork/DI-container. До 75.1 JSON-сборка допускает объяснённый nullcontext, не обещающий JSON транзакционность. В 75.1 переходная JSON-сборка удаляется; модель Task не импортирует SQLAlchemy.
5. **Begin не вставляется после первого SELECT.** Чтение может запустить autobegin. План операции должен охватывать выбор текущей записи, предметное изменение и flush одной областью. Тестовые вызовы сервиса используют свежий ресурс на действие; нельзя скрыть ошибку повторным begin или commit случайной чужой работы.
6. **Успех только после commit.** Репозиторий может получить id после flush и материализовать Task, но сервис не возвращает успех, пока его область изменения не завершилась. Обычная Task на выходе не зависит от истёкших ORM-атрибутов. Отказ до commit проверяем повторным чтением; rollback не обещает отменить уже успешный commit.
7. **Id не становится новым бизнес-правилом.** Новую запись создаёт БД, не SELECT max(id)+1. Требуются положительность и отсутствие конфликта с существующими строками. Непрерывность номеров и вечное запрещение повторного использования удалённого id не были прежним договором и здесь не добавляются.
8. **Схема уже достаточна.** tags и title_normalized присутствуют с 67.1. Не добавляем created_at, Category, владельца, уникальность title, offset-pagination, индексы или миграции ради очередного упражнения.
9. **JSON как формат остаётся.** HTTP и JSON-колонка tags не являются старым файловым backend. Отдельный импортёр использует обычное чтение JSON и предметные валидаторы, не зависит от удаляемого app/storage.py.
10. **Переход не маскирует потерю данных.** При финальном импорте API/CLI остановлены, снимок сохранён, цель проверена. После новых SQL-записей старый JSON не является безопасным откатом. Не вводим постоянную синхронизацию, двойную запись и автоматическое восстановление из устаревшего файла.

## 3. Подробные паспорта занятий

### 71. Создание и ID из БД

#### Основная тема и назначение

Соединить изученную ORM-запись с существующим предметным сценарием добавления. Ученик впервые получает SQL create продукта, а не повторяет создание учебной строки или endpoint с готовым commit внутри.

#### Точка A

- **Знания:** достигнута B14; известны Session, flush/commit/rollback, mapping, get_db и override. Серверный id знаком из JSON, но механизм назначения id таблицей ещё не применялся в add_task.
- **Компоненты:** готовые TaskRow, task_from_row, SqlTaskRepository.list/get, PlannerService с договором репозитория, build_service и тестовый provider. Есть исходная таблица с title_normalized и tags.
- **Рабочее состояние:** полный JSON-адаптер сохраняет прежние операции; обычный POST работает с JSON. SQL create отсутствует, и передача SQL-сервиса всему приложению ещё недопустима.
- **Опора:** текущие add_task, TaskCreate и TaskRead уже существуют. В POST обязательны title и priority; id генерируется сервером, is_done начинается с False, HTTP не вводит tags. Default=2 предметной модели не делает priority необязательным в существующей HTTP-схеме. Прямой сервисный вызов может передать существующие внутренние tags.
- **Пробел до практики:** нужна явная связь границы изменения сервиса с Session.begin и проверка предметных значений до подтверждения. Нельзя требовать SQL PUT/PATCH, статистику, поиск или глобальное переключение.

#### Точка B

- **Понимание:** ученик объясняет, почему max(id)+1 не переносится как SQL-алгоритм, почему id после flush ещё не доказывает успех, и кто подтверждает целый сценарий.
- **Изменение:** SqlTaskRepository.create добавляет строку с нормализованным title, прежним priority, False, независимыми tags и title_normalized. Реальный id получен от БД; Task не создаётся с фиктивным id=0.
- **Сервис:** add_task использует тот же договор, прежние валидаторы и область изменения, завершённую до возврата результата. Для SQL передаётся небольшой write_scope из сборки; SQL не попадает в handler/Task.
- **Наблюдаемый результат:** существующий POST с SQL-override возвращает 201 и прежние четыре поля; новая Session на том же тестовом файле читает все пять предметных полей и техническую колонку.
- **Сохранённое и отсутствующее:** JSON default, остальные операции и схемы не изменены. SQL create/list/get готовы; SQL replace/update/delete/select/search/statistics ещё нет.

#### Необходимые темы в порядке изучения

1. Восстановить существующий add_task и распределение HTTP-/предметной валидации. Назвать поля, которые клиент не назначает.
2. Целочисленный primary key SQLite, назначение id при вставке, явный id импорта против обычного создания. Не обещать сплошную последовательность и не требовать AUTOINCREMENT как новое правило продукта.
3. Применение уже изученных валидаторов к входу до записи: title/priority/tags проверяются без невалидной Task-заглушки; после flush формируется Task с настоящим id.
4. Граница изменяющего сценария: простая фабрика контекста, начало до первого SQL, flush в репозитории, завершение в сервисе, rollback при отказе. nullcontext временной JSON-сборки объяснить до использования, не выдавая его за транзакцию.
5. Получение обычной Task внутри ресурса; почему готовый объект в памяти не равен подтверждённой записи. Ошибка commit запрещает 201/успешное CLI-сообщение.
6. Узкий SQL-override существующего POST и get по id. Недостающие методы не компенсируются fallback; подробная классификация ошибок БД остаётся блоку 16.

#### Основная практика

1. В существующих crud.py/services.py/main.py добавить SQL create и согласовать передачу области изменения. Не создавать новую модель задачи или новый маршрут.
2. На изолированной базе выполнить прямой add_task с tags и существующий POST без tags. Проверить нормализацию заголовка, независимость тегов, сохранение явно переданного priority и реальные положительные id. POST без обязательного priority должен сохранить прежний 422, а не получить новый default.
3. Прочитать обе записи новым ресурсом. Повторить создание с одинаковым title: прежняя программа не запрещала совпадающие названия.
4. Проверить неправильные title/priority/tags прямого вызова и 422 HTTP-входа. На контролируемом отказе до commit убедиться, что строка не сохранилась и не получен ложный успех.
5. Использовать подготовленный импортёр на отдельной fixture для старых id, затем создать новую задачу. Новый id не конфликтует с текущими строками; тест не требует непрерывной нумерации.

#### Выход и переход

Приёмка: существует SQL create того же продукта, ответ подтверждён независимым чтением, запись имеет атомарную границу, JSON-путь не сломан. A71.1 получает созданные строки и работающие SQL create/list/get. Следующий шаг меняет существующую запись, не повторяет основы Session и не создаёт таблицу заново.

### 71.1. PUT: замена задачи

#### Основная тема и назначение

Перенести прежнюю полную замену публичных полей на адресную SQL-операцию. Научить обновлять запись, не создавая её заново и не стирая внутренние данные, отсутствующие в HTTP.

#### Точка A

- **Знания:** SQL create/list/get и транзакционная граница из 71 готовы; различие PUT/PATCH знакомо из прежнего API. Ученик знает id/tags и технический заголовок.
- **Компоненты:** прежние replace_task и TaskUpdate, mapping и поле title_normalized; SQL replace отсутствует. Полный JSON PUT уже сохраняет id и tags.
- **Данные:** на тестовой базе есть как минимум выбранная задача с непустыми tags и соседняя запись. SQL-сервис возвращает обычную Task, не ORM наружу.
- **Default:** приложение остаётся на JSON. Через override можно проверять только уже реализованные SQL-операции и новую замену.
- **Чего нельзя требовать:** частичный update, удаление, SQL-фильтрация и новая публичная операция редактирования tags. Инварианты текущей записи нельзя менять ради примера ORM.

#### Точка B

- **Понимание:** ученик отличает замену публичного состояния существующей строки от delete+insert и создания нового id.
- **Изменение:** SqlTaskRepository.replace обновляет выбранную запись; сервис проверяет допустимость итоговой Task до изменения ORM-состояния. Сохраняются id и копия прежних tags.
- **Связанные данные:** title_normalized обновляется вместе с нормализованным title в той же транзакции; priority/is_done получают переданные значения без потери False.
- **Проверяемое поведение:** PUT возвращает 200 и прежнюю форму, новая Session видит замену; неизвестный id даёт 404, ошибочный ввод не меняет исходную строку/соседей.
- **Граница готовности:** SQL create/get/list/replace готовы, PATCH/done/delete/выборка/статистика/поиск впереди. Штатный источник остаётся JSON.

#### Необходимые темы в порядке изучения

1. Договор PUT: набор обязательных публичных полей, неизменность id и сохранение данных вне HTTP-схемы.
2. Выбор строки по id внутри области изменения; отсутствие строки переводит сервис в TaskNotFoundError, HTTP в прежний 404.
3. Подготовка валидного нового состояния до присваивания ORM-полей; не допускать autoflush наполовину изменённой записи при следующем SELECT.
4. Изменение атрибутов загруженной TaskRow и flush; не заменять таблицу полным снимком и не делать delete+insert.
5. title/title_normalized как связанная пара; tags не стираются отсутствующим полем. Для JSON-колонки присваивание списка и inplace-мутация имеют разный механизм отслеживания.
6. Материализация результата и commit до ответа; повторная замена и независимое чтение, без новой схемы и миграций.

#### Основная практика

1. Продолжить crud.py: реализовать SQL replace и связать его с прежним replace_task/PUT. Публичную схему не переписывать.
2. Заменить title/priority/is_done задачи с тегами, проверить id/tags/technical title и неизменность соседней записи в новой Session.
3. Повторить замену с is_done=False и одинаковым title другой задачи: ложное значение применяется, совпадающий title допустим.
4. Проверить неизвестный id, недостающие обязательные поля HTTP, недопустимое значение и контролируемый отказ до commit. Старые значения сохраняются, ложного 200 нет.
5. Повторно выполнить SQL create/get из 71 и прежние JSON-проверки изменённой границы. Не требовать ещё не написанный PATCH.

#### Выход и переход

Приёмка: адресная замена сохраняет внутренние данные и не пересоздаёт задачу; два связанных заголовка согласованы. A72 получает работающий механизм записи валидного состояния, который можно переиспользовать при частичном изменении вместо копирования PUT целиком.

### 72. PATCH: выбор полей

#### Основная тема и назначение

Сохранить прежний смысл частичного обновления при смене хранения. Основная сложность не в новом SQL-синтаксисе, а в различении отсутствия значения, null, False и настоящего изменения.

#### Точка A

- **Знания:** известен существующий TaskPatch и model_dump с exclude_unset/exclude_none; PUT на SQL уже работает. Это закрепление договора, не первое знакомство с Pydantic.
- **Компоненты:** patch_task существует на репозиторной границе, SQL update ещё не готов. Есть общая транзакционная область и безопасная замена выбранной записи.
- **Данные:** задача имеет известные title/priority/is_done/tags и нормализованный технический заголовок. Вход PATCH может быть пустым или содержать null/False.
- **Правило на входе:** отсутствующие поля и явный null игнорируются, False применяется. Пустой PATCH известного id возвращает текущую задачу; неизвестного id не становится успешной пустой операцией.
- **Предел:** не вводить новый merge-patch стандарт, очистку поля через null, редактирование tags по HTTP или дополнительный маршрут done.

#### Точка B

- **Понимание:** ученик объясняет результат каждого варианта payload и не использует truthiness вместо проверки присутствия значения.
- **Изменение:** SQL update обслуживает прежний patch_task; новое состояние вычисляется из текущей Task и только разрешённых переданных значений, затем записывается адресно.
- **Данные:** непереданные поля, id и tags сохранены; title_normalized меняется только вместе с title. Пустой/полностью null PATCH не генерирует UPDATE, но проверяет существование задачи.
- **Приёмка:** ответ 200 соответствует новой Session; 404/422 и отказ до commit не оставляют частичного изменения. PUT/create остаются рабочими.
- **Следующие пробелы:** SQL done/delete и запросные select/statistics/search ещё не реализованы; рабочий backend не переключён.

#### Необходимые темы в порядке изучения

1. Прежняя цепочка HTTP payload → словарь изменений → сервис; различие пропущенного значения, None и False.
2. Формирование полной проверенной Task из текущего состояния, а не заполнение непереданных полей default-значениями.
3. Общая запись валидного состояния из 71.1: переиспользовать, не смешивать договоры PUT и PATCH и не допускать двух commit.
4. Пустая операция: отсутствие UPDATE не означает отсутствие чтения/проверки id; ресурс и начатое чтение корректно завершаются.
5. Связанная техническая колонка и сохранение tags; неправильные значения проверяются до изменения строки.

#### Основная практика

1. Добавить SQL update к существующему договору и подключить прежний patch_task, не меняя TaskPatch и exclude_none-смысл.
2. По отдельности изменить title, priority и is_done=False. После каждого нового ресурса сравнить все поля с ожидаемым состоянием, включая неизменившиеся.
3. Проверить `{}`, payload только с null и смесь null/False. Для известных id нет лишней записи, для неизвестных прежний 404.
4. Проверить неверный title/priority и отказ до commit: прежняя запись и технический заголовок остаются целыми. Отдельно подтвердить сохранность tags.
5. Повторить PUT после PATCH и PATCH после PUT, чтобы результат одного сценария стал входом другого без второго списка и кеша.

#### Выход и переход

Приёмка: SQL PATCH соответствует прежним правилам и не портит состояние. Следующий шаг получает обычные Task, общий update и транзакционную область; done сможет применить прежний метод модели, а не заново изобретать бизнес-логику завершения.

### 72.1. Задача: done и delete

#### Основная тема и назначение

Достроить изменяющие SQL-сценарии продукта: завершение через существующий сервис и адресное удаление. Разобрать повтор команды и отсутствие объекта, сохраняя привычные правила API/CLI.

#### Точка A

- **Знания:** SQL create/replace/update и безопасный транзакционный путь готовы. Ученик знает Task.mark_done и существующие mark_done/delete_task.
- **Интерфейсы:** HTTP уже имеет DELETE; завершение доступно через прежний PATCH и CLI done. CLI delete уже существует. Новый endpoint завершения не нужен.
- **Данные:** есть несколько задач, одна завершённая и одна открытая, у каждой собственные tags. SQL done/delete ещё не доведены до приёмки.
- **Пределы:** список/stats/search на SQL ещё не готовы; основная проверка изменений использует get/list репозитория и новые Session, а не отсутствующие query-операции.
- **Источник:** обычное приложение пока JSON, SQL проверяется изолированно. Не удалять рабочие данные ради эксперимента.

#### Точка B

- **Изменение:** mark_done использует прежнюю предметную Task и общий SQL update. Повторное done завершённой задачи возвращает её без повторного изменения.
- **Удаление:** SqlTaskRepository.delete удаляет выбранную строку в области сценария; сервис не перезаписывает таблицу и не закрывает ресурс раньше завершения.
- **HTTP:** прежний DELETE даёт 204 с пустым body; следующий GET и повторный DELETE отсутствующего id дают прежний 404. Некорректный path-id по-прежнему отклоняется HTTP-валидацией.
- **Данные:** соседи, их tags и технические поля не затронуты; новая Session подтверждает завершение/отсутствие удалённой строки. Ошибка до commit сохраняет исходную запись.
- **Готовность:** изменяющие SQL-операции полны, но select/statistics/search ещё отсутствуют. Достроенный CRUD не означает завершённое переключение приложения.

#### Необходимые темы в порядке изучения

1. Повторное завершение против повторного удаления: прежний результат двух сценариев различается; не объявлять DELETE idempotence обещанием одинакового статуса каждого ответа.
2. Повторное применение Task.mark_done и общего update; проверка is_done до необходимости изменения.
3. Session.delete загруженной строки, flush/commit и последующее отсутствие; изменение памяти не доказывает удаление.
4. Неизвестный id, предметная ошибка и существующий перевод HTTP. Удалять соседние строки и «исправлять» ошибку очисткой таблицы нельзя.
5. Результат delete_task остаётся None, handler возвращает пустой Response; не сериализовать удалённый ORM-объект в ответ.

#### Основная практика

1. Довести SQL mark_done через существующие сервис/Task/update. Дважды завершить одну задачу и проверить отсутствие повторного UPDATE при втором вызове.
2. Добавить SQL delete и использовать существующий DELETE. Проверить 204/пустое содержимое, последующий get/404 и повторный delete/404.
3. После операций новой Session прочитать соседей и полную пятёрку их полей. Сравнить технический заголовок выбранной завершённой задачи с исходным.
4. На отдельной fixture проверить отмену удаления/завершения до commit. Запись не исчезает и не становится завершённой после отказа.
5. Вызвать существующие CLI-handlers done/delete напрямую с SQL-сервисом в подготовленном контексте, сохраняя сообщения. Полный run с новым ресурсом на каждую команду появится в 74.

#### Выход и переход

Приёмка: create/read/replace/update/done/delete подтверждены на SQL с прежними правилами. A73 получает реальные данные, которые уже можно адресно изменять; теперь запросы списка/статистики отражают накопленное состояние, а не работают с отдельным временным списком.

### 73. SQL-фильтр и сводка

#### Основная тема и назначение

Перенести фильтрацию, порядок, ограничение и подсчёт с полной загрузки таблицы на осмысленные SQL-запросы. Договор публичной выборки остаётся прежним; новый формат пагинации не добавляется.

#### Точка A

- **Знания:** простые WHERE/ORDER BY/LIMIT изучались в SQL, select/scalars применены в list/get. Агрегатный запрос и его скалярный результат ещё нужно объяснить.
- **Компоненты:** SQL CRUD полон, но методы репозитория select/statistics не реализованы. get_selection/get_selected_tasks и HTTP /stats уже работают через тот же сервис на JSON.
- **Договор:** фильтр is_done необязателен, порядок по id, направление sort_desc, HTTP limit default 10 в пределах 1–50. Прикладной select_tasks допускает прежний limit=None без искусственного HTTP-ограничения.
- **Данные:** на одной тестовой базе есть задачи разного состояния с известными id, созданные существующими SQL-операциями. Требуется проверять фильтрацию до ограничения, а не произвольные пять записей во втором проекте.
- **Предел:** SQL search ещё нет; JOIN, GROUP BY по новой сущности, offset и индексы не требуются.

#### Точка B

- **Выборка:** SqlTaskRepository.select применяет WHERE, устойчивый ORDER BY и затем LIMIT; None означает прежнее отсутствие соответствующего ограничения. Получаются обычные Task.
- **Статистика:** statistics считает задачи в БД без materialization всех Task; возвращает all/open/done как целые числа, включая нули для пустой таблицы.
- **Интерфейсы:** прежние GET `/tasks` и `/stats` проходят через существующие selection/service; HTTP сохраняет total/open/done, статусы и ограничения query.
- **Понимание:** ученик объясняет разницу между результатом модели и скалярным агрегатом, порядок фильтра/limit и отличие отсутствующего фильтра от False.
- **Граница:** полный SQL CRUD/выборка/статистика готовы; только search из предметного договора ещё не завершён. JSON default сохраняется.

#### Необходимые темы в порядке изучения

1. Восстановить старую Python-выборку и её семантику: сначала фильтр, затем порядок, затем срез.
2. SQLAlchemy-выражения WHERE, asc/desc и LIMIT; None против False. Параметры остаются значениями, не конкатенацией SQL.
3. Отсутствие LIMIT для прежнего сервисного вызова и HTTP limit с валидацией; не переносить ограничение 10 на CLI list молча.
4. COUNT, условный подсчёт/CASE и получение скалярных значений: выбрать понятный небольшой агрегат, объяснив все используемые выражения до практики. Не требовать GROUP BY/HAVING/подзапросы ради простой статистики.
5. Пустая таблица и нули; подсчёт открытых из общего/завершённых при соблюдённых bool-данных. Согласованный результат внутри одного запроса предпочтителен сложной серии несвязанных чтений.
6. Проверка назначения запроса без полного урока профилирования: WHERE/ORDER/LIMIT присутствуют в запросе, stats не создаёт предметные объекты. Углублённое наблюдение будет в 77.

#### Основная практика

1. Реализовать select/statistics в существующем crud.py и связать с прежними методами сервиса; новый endpoint не писать.
2. Создать через готовый SQL-сервис на изолированной базе известные открытые/завершённые задачи. Предсказать результат фильтра/направления/limit, затем сравнить с GET и прямым сервисным вызовом.
3. Проверить отсутствующий фильтр, is_done=False, limit=1, границы HTTP 1/50, неизвестное/некорректное query и limit=None сервиса. Данных должно хватать, чтобы обнаружить ошибочный limit до фильтра.
4. Проверить stats пустой базы, смешанного состояния, после add/done/delete. HTTP total соответствует внутреннему all, open+done=all, типы чисел сохранены.
5. Защитить проверкой отсутствие вызова полного list ради фильтрации/статистики. Не добавлять сложные лимиты количества SQL-запросов, события/бенчмарки, которые ещё не объяснены.

#### Выход и переход

Приёмка: результаты прежние, основная работа выполнена SQL, пустая база корректна. A73.1 получает полную запросную основу и уже заполненный title_normalized, но не готовый поиск; его семантика разбирается отдельным шагом.

### 73.1. Поиск в SQL-базе

#### Основная тема и назначение

Перенести существующий буквальный поиск на SQL без незаметной смены поведения для русского текста и специальных символов. Использовать предусмотренную исходной схемой колонку, не добавлять миграцию по ходу занятия.

#### Точка A

- **Знания:** WHERE, select/scalars и параметры знакомы; известно назначение title_normalized, но функция SQL-поиска ещё не применялась.

#### Точка B

- **Изменение:** SqlTaskRepository.search выполняет параметризованный SQL-поиск буквальной подстроки по title_normalized, возвращает прежние Task; не загружает все строки для Python-фильтра.

- **Данные:** создание, PUT/PATCH и импорт дают согласованные title/title_normalized; после переименования старый фрагмент больше не находит задачу, новый находит.
- **Договор:** пустой/пробельный запрос, русский/латинский регистр, кавычки, `%` и `_` ведут себя по прежним правилам; дубликаты заголовков допустимы.
- **Готовность:** SQL-репозиторий реализует полный текущий предметный договор. Рабочая сборка ещё JSON; следующий шаг готовит полноценный CLI-run, не дополнительные SQL-методы.

4. Техническая копия нормализованного заголовка и все пути её записи; не делать backfill и не добавлять колонку в населённую таблицу.
5. Параметры для пользовательского фрагмента; пустой запрос отклоняет/обрабатывает прежний слой. Порядок результата сделать явным по id, не обещать неупорядоченный SQL как порядок вставки.

#### Основная практика

#### Выход и переход

### 74. CLI и ресурс команды

#### Основная тема и назначение

Развить существующий интерактивный CLI так, чтобы длительный run не удерживал одну Session. Обработчики и их предметные действия сохраняются; меняется место получения сервиса для текущей команды.

#### Точка A

- **Знания:** полный SQL-репозиторий готов; контекст SQL-сервиса из 70.1 и транзакционная область сервиса из 71 объяснены. Callback-таблица CLI и execute_command известны.
- **Код:** существующий run принимает готовый service, возвращает его; COMMAND_HANDLERS содержит add/list/find/done/delete/search/stats. Меню и read/write-инъекции уже позволяют тестировать диалог.
- **Проблема:** один готовый SQL-service на весь run удержал бы Session между командами и мог пережить закрытие. Подготовленный одиночный контекст ещё не встроен в повторяющийся ввод.
- **Default:** main запускает JSON-сборку. SQL CLI пока разрешён только в изолированной проверке; переключение обычного запуска впереди.
- **Ограничение:** не добавлять CLI PUT/PATCH, новую командную систему, FastAPI Depends, async или собственный container ради ресурса.

#### Точка B

- **Изменение:** run получает понятную фабрику ресурсного контекста сервиса и открывает его на одну распознанную предметную команду. Handlers и execute_command переиспользуются, их сообщения/валидация сохраняются.
- **Ресурсы:** Engine/SessionFactory живут в сборке, отдельная Session заканчивается после команды при успехе/ошибке. Неизвестная команда и exit не требуют обращения к БД.
- **Результат:** SQL CLI на тестовой базе создаёт, читает, ищет, считает, завершает и удаляет реальные задачи; следующий вызов видит подтверждённый результат предыдущего.
- **Совместимость:** обычный main до 75 использует временную JSON-фабрику над тем же источником. Это переходная сборка, не пользовательский флаг backend. Возвращать из run последний сервис с закрытой Session нельзя; возврат/тесты пересогласованы явно.
- **Граница:** все компоненты SQL API/CLI готовы, но общего допуска к переключению ещё нет. Старый JSON продолжает оставаться источником штатных данных.

#### Необходимые темы в порядке изучения

1. Длительный цикл против короткой команды: ресурс не должен жить всё время ожидания следующих команд. Не оставлять открытую транзакцию во время повторного ввода.
2. Фабрика контекста как знакомый callback; сборка через прежний build_service с явно полученным ресурсом.
3. Сначала распознавание команды/exit, затем контекст для handler. Предметная транзакция начинается внутри сервисного вызова после получения ввода, не на всё меню.
4. Завершение ресурса после handler и ошибки; успешное сообщение выводится только после успешного сервиса/commit.
5. Контракт run: старый возвращаемый service не переносить в новый ресурсный путь. Выбрать простое завершение без возврата закрытого SQL-сервиса; обновить потребителей/fixtures, не сохранить второй legacy-run.
6. Подготовка временного JSON-контекста без БД-транзакций; исчезновение этого моста в 75.1. Подробная диагностика недоступности хранения будет в 76.

#### Основная практика

1. Изменить существующие run/main и связанную сборку: фабрика контекста выдаёт service текущей команде, а не всему циклу. Переиспользовать handlers/execute_command, не написать новую CLI-программу.
2. Подготовить SQL-run на отдельном DATABASE_URL и сценарий add → list → find → done → stats → search → delete → exit с read/write-fixtures. Проверять реальные данные, не список внутри тестовой команды.
3. Наблюдать, что разные команды получают разные Session; после каждой ресурс освобождён, а новая команда читает сохранённое. Ресурс не становится глобальным через callback-замыкание.
4. Проверить повторный done, неизвестный id, неверный ввод/повтор ввода, неизвестную команду и exit. Неизвестная команда/выход не создают Session, ошибочная операция не приводит к ложному сообщению об успехе.
5. Повторить прежний JSON-run через переходную фабрику: источник/команды прежние. Явно обновить тесты возврата run и не использовать закрытый сервис для финальной проверки; читать через новый контекст.

#### Выход и переход

Приёмка: SQL CLI полноценно применяет тот же сервис с новой областью на действие; штатный JSON не переключён. A74.1 получает оба подготовленных интерфейса и полный репозиторий, чтобы проверить их совместно на одном SQL-файле до изменения рабочих данных.

### 74.1. Готовность к переходу

#### Основная тема и назначение

Собрать доказательства готовности накопленного SQL-пути. Это интеграционная практика на уже работающем коде, а не очередное финальное задание «напишите весь Planner».

- **Знания и код:** реализованы все SQL-операции, транзакции сервиса, HTTP-подмена и ресурс на CLI-команду. Импортёр проверен отдельно в 70.2.

### 75. Переход на SQLite

#### Основная тема и назначение

Применить подготовленный SQL-путь к настоящему накопленному проекту. Объяснить переключение как управляемую смену источника истины, а не замену одного импорта в случайном handler.

#### Точка A

- **Готовность:** весь SQL-код и связанный сценарий прошли допуск 74.1. Схема/импортёр и ресурсные сборки обоих интерфейсов уже созданы.
- **Авторитетные данные:** действующий JSON мог измениться после репетиции. Именно он, а не старая тестовая БД, содержит окончательный набор до остановки.

- **Предварительная граница:** нельзя допустить новых записей в старый источник после снятия снимка, частичного переключения интерфейсов или импорта поверх непустой цели.

#### Точка B

- **Данные:** после остановки API/CLI сохранена отдельная копия последнего JSON, он проверен и импортирован одной транзакцией в согласованную пустую SQLite-цель. Набор id и все пять предметных полей совпадают, technical title корректен.
- **Сборка:** обычный get_planner получает SQL-сервис текущей Session через get_db; CLI default получает новый SQL-контекст на команду. Оба используют тот же DATABASE_URL и build_service, не app.state с живой Session/сервисом на весь процесс.
- **Рабочий результат:** вновь запущенные API и CLI видят общий SQLite-результат; API создаёт, CLI читает/завершает, новый API-запрос и новый запуск видят изменение.
- **Граница источника:** обычные операции больше не читают/сохраняют старый файл. Он остаётся архивом; старые backend-классы могут пока лежать в коде без активных потребителей до 75.1.
- **Осознанное восстановление:** до первого нового SQL-изменения процедура может быть остановлена без расходящихся новых данных; после изменений старый снимок нельзя просто включить обратно. Нет автоматического возврата или синхронизации.

#### Необходимые темы в порядке изучения

1. Репетиция против окончательного снимка; почему «перенесли вчера» не значит «перенесли актуальные данные».
2. Остановка всех писателей, резервная копия, проверка явных путей, пустая цель и прежняя исходная схема. Несовпадение/непустая цель приводят к остановке, не автоматическому удалению БД.

4. Одновременная смена штатной сборки: get_db/SQL-provider и CLI-контекст, прежние selection/dependencies/настройки preferences. App.state может хранить Settings/фабрику, не текущую Session.
5. Commit до успешного ответа и сообщения; новый ресурс/новый процесс как проверка состояния, не чтение объекта прежней Session.
6. Границы восстановления: старый JSON перестаёт быть актуальным после SQL-записей. Не обещать сохранность данных при простом возврате старого config.

#### Основная практика

1. Первое задание: остановить обычные API и CLI и убедиться, что запись в прежний JSON прекращена. Сохранить отдельную резервную копию, явно назвать её источник и время снимка.

5. В новом запуске выполнить API add → CLI find/done → API get/stats, затем CLI search через существующие точки входа. Проверить новые id и состояние после остановки/нового запуска; файл JSON от этих действий не меняется. Отдельный HTTP search-route не создавать.

#### Выход и переход

A75.1 получает уже работающий DB Planner и неиспользуемый переходный код. Следующее занятие удаляет его после поиска потребителей, а не повторяет перенос или переключение.

### 75.1. Убираем JSON-backend

#### Основная тема и назначение

Завершить переход архитектуры: убрать старый рабочий путь и доказать, что готовый продукт не зависит от прежнего файла или случайных тестовых fixtures. Оставить формат JSON и отдельный инструмент импорта там, где они нужны.

#### Точка A

- **Рабочее состояние:** штатные API/CLI уже используют одну SQLite-базу; данные перенесены, CRUD/запросы/перезапуск проверены. Допуск к удалению не основывается на одной успешной операции.
- **Остатки:** в коде ещё могут быть JsonTaskRepository, JsonStorage/MemoryStorage, app/storage.py, JSON_PATH, адаптация storage в build_service и временный JSON-контекст. Они больше не должны иметь runtime-потребителей.
- **Тесты:** часть старых fixtures и проверок может ещё импортировать файловое хранение или проверять его save-count. Это зависимость тестовой архитектуры, а не причина держать старый backend в приложении.
- **Не удаляемое:** Task.from_dict/обычная JSON-сериализация, tags JSON-колонка, HTTP JSON, проверяемый отдельный import_tasks.py и сохранённая архивная копия.
- **Граница:** нельзя просто удалить весь JSON-код поиском по слову. Подробный безопасный 503 и расширенная диагностика относятся к следующему блоку, но fallback запрещён уже сейчас.

#### Точка B

- **Код:** старые storage-классы/адаптер и лишний app/storage.py удалены после устранения потребителей. Build_service принимает ресурс SQL-сборки; нет legacy storage-параметра, backend-флага и отдельной файловой ветки.
- **Настройки:** Settings и `.env.example` больше не содержат JSON_PATH; рабочий источник задаётся DATABASE_URL. Настройки APP_NAME/COOKIE_SECURE и прежние config-проверки сохраняются.
- **Тесты:** основной сервис/API/CLI проверяется на SQLite с короткими Session. Тесты специфического файлового backend удалены или заменены проверками нужного сохранённого поведения; проверки старого формата закреплены за импортёром.
- **Независимость:** приложение работает без прежнего JSON; DB-отказ не создаёт/не читает его, не включает MemoryStorage и не возвращает ложный успех. Импортёр запускается отдельно с явным источником.
- **Передача:** B15 достигнута полностью: работающий SQL-продукт без переходного пути. A16 не получает «надо ещё доделать поиск/CLI/JSON-очистку» как скрытую обязанность.

#### Необходимые темы в порядке изучения

1. Поиск потребителей: runtime, сборка, config, fixtures, примеры запуска; удалить зависимость прежде файла, а не спрятать импорт в try/except.
2. Различие файлового backend, формата HTTP, JSON-колонки и импортёра. Архив не является default-источником или fallback.
3. Перенос смысла тестов: сохранение после нового ресурса, отсутствие изменения при ошибке, повторная команда, независимость tags вместо привязки к числу JsonStorage.save.
4. Изоляция DB-fixtures и настройка среды; отсутствие общего кешированного SQL-сервиса в API/CLI.
5. Контролируемая недоступность БД: отсутствие успешной записи/fallback и освобождение ресурса. Классификацию SQL-исключений/HTTP 503 углубить в 76, не обещать её готовность здесь.
6. Отдельное сохранение импорта старого формата без зависимости от app/storage.py; отсутствие переписывания схемы/данных во время очистки.

#### Основная практика

1. Найти все потребители старых классов, JSON_PATH и переходных фабрик/параметров; разделить их на runtime, тесты и архив/формат. Удалить только старый backend и его сборку.
2. Перевести оставшиеся service/API/CLI-fixtures на изолированную базу и Session на действие. Сохранить проверки прежней семантики; не оставлять MemoryStorage обязательным runtime-компонентом ради unit-тестов.
3. На отдельной приёмочной среде убрать старый файл из ожидаемого места, не стирая резервную копию рабочих данных. В новых процессах пройти CRUD, выборку, поиск, статистику, CLI и preferences; результат хранится только в SQLite.
4. На контролируемом DB-отказе проверить отсутствие успешного ответа/сообщения, новой JSON-записи, чтения архива и in-memory fallback. Не ломать рабочую базу ради теста и не утверждать, что уже успешный commit отменяется.
5. Отдельно запустить импортёр на явной тестовой копии старого формата в пустую тестовую цель: он остаётся полезным без удалённого storage.py. Повторный запуск на непустой цели по-прежнему безопасно отклоняется.
6. Обновить минимальные примеры запуска/настройки, затронутые удалением backend; полная чистая установка/README-передача остаётся 80. Проверить отсутствующие импорты и неиспользуемые legacy-ветки.

#### Выход и переход

Приёмка: один SQL-путь, отсутствующий старый файл не влияет на работу, известный DB-отказ не запускает fallback, импорт отдельный и независимый. Блок 16 получает готовый продукт для углубления надёжности и наблюдения запросов, а не дополнительный финальный CRUD или скрытую смену backend.

### Проверяемые критерии B15

1. SqlTaskRepository реализует полный согласованный договор, а PlannerService остаётся единственным местом предметных сценариев. Endpoint не делает SQL/commit; CLI не импортирует FastAPI Depends.
2. Изменение охватывает чтение текущей строки, предметную проверку и запись одной областью. Нет commit каждой внутренней операции, позднего commit после yield и ложного успешного результата при отказе до commit.
3. Результат каждого изменения подтверждён новым ресурсом; ошибки не оставляют частичную запись. Начальные проверки отмены уже выполнены, хотя расширенные случаи относятся к 76.1.
4. Идентификатор нового объекта назначает БД, импорт сохраняет прежние id; новая запись не конфликтует с перенесёнными. Непрерывные номера и запрет их повторного использования не обещаны.
5. PUT/PATCH/done/delete соответствуют прежним правилам, tags и соседи не теряются, title_normalized согласован со всеми путями записи/импорта.
6. Выборка/статистика/поиск выполняют нужную работу SQL без полного снимка таблицы для последующей Python-обработки. Схема не менялась, миграции не изучались.
7. Engine/SessionFactory общие для сборки, Session короткая на запрос/команду. Нет SQL-сервиса с давно закрытым/общим ресурсом в app.state или в run; overrides восстанавливаются.
8. Переключение выполнено после допуска на точном окончательном снимке при остановке записей. Импорт сравнен по всем данным, а не только по числу строк; непустая цель не перезаписана.
9. Обычные API/CLI используют одну SQLite-базу, изменения одного видны другому и после нового запуска. Прежний JSON не изменяется и не используется как рабочий источник.
10. JsonTaskRepository, прежние storage-классы, JSON_PATH и переходные параметры/ветки удалены из runtime. Без старого файла продукт работает, DB-отказ не включает fallback. Импортёр остаётся отдельным явным инструментом.
