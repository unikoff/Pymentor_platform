Проверены исходники и выполнена автоматическая проверка функций без верхнеуровневого запуска меню: передача/возврат списка, независимые обычные запуски, add/done/list/stats, неизвестная команда, exit и диагностическая обёртка. - один `main.py`, вызов `run()` на верхнем уровне, список только в памяти. Файлового хранения, пакета, модели Task и сервиса пока нет.

Понимание механизмов отдельно подтверждать по материалам и действиям ученика: коммит сам по себе не доказывает изученность темы.

### Точка A блока

Ученик завершил целевой маршрут блока 5: знает договор функции, позиционные и именованные аргументы, default, ссылки и мутацию, сбор/распаковку, функции как значения, замыкания и ручную обёртку. Он умеет проследить путь команды через обработчик и операцию. Все прежние команды работают с одним явно переданным списком.

`except ValueError` уже встречался в числовых читателях, но устройство исключений ещё не изучено системно. Импорты, безопасная точка запуска, пути, файлы и JSON не считаются знакомыми только потому, что существующие примеры их используют.

### Точка B блока

Тот же функциональный Planner становится модульным и сохраняет данные:

1. Числовой ввод использует общий `read_int`; проверки диапазонов сохраняют предметный смысл и прежние сообщения.
2. Правила данных проверяются не только в CLI: неверная задача отклоняется до добавления или изменения списка. Неизвестный id прикладного обращения имеет объяснённую ошибку `TaskNotFoundError`.
3. Рабочие компоненты находятся в пакете `app`, импорт не начинает меню. Запуск: `python -m app.main` из корня репозитория.
4. `app.main` задаёт один рабочий путь `data/tasks.json`, загружает список и передаёт его в CLI. `app.storage` получает путь аргументом, не выбирает другой файл скрыто.
5. Функции `load_tasks(path)` и `save_tasks(path, tasks)` читают и записывают полный список словарей с исходными четырьмя полями. После успешного изменения используется один callback сохранения.
6. Новый процесс восстанавливает задачи, созданные через CLI, их id, приоритеты и состояние. Читающие команды и неверный ввод не вызывают запись.
7. Весь загруженный снимок проверяется до начала меню. Повреждение, неправильная форма и проблема доступа дают наблюдаемый отказ, не тихое восстановление `[]`.

Это уже рабочее функциональное хранение, не заглушка будущего JsonStorage. Классы storage, PlannerService, pytest, HTTP и база данных здесь не вводятся.

### Неизменяемые границы

- Сохраняются корень проекта, история Git, команды `add/list/find/done/search/stats/exit`, правила поиска, формат карточки и поля `is_done`, а не `done`.
- `find_task` может сохранить результат `dict | None`; новый прикладной договор вводится явно, не подменяет все пустые результаты исключениями.
- Удаление не является входной возможностью и не добавляется в этом блоке. `tags` появятся вместе с подготовкой объектной модели позже.
- Обучение файлам допускает короткий безопасный эксперимент. Он не становится промежуточной текстовой базой заголовков Planner.
- Нет второго рабочего списка, отдельной ручной JSON-базы или повторной сборки приложения в финале.
- Для изолированной проверки ошибок разрешён отдельный учебный путь к копии данных. Это проверочный экземпляр файла, не второй продукт и не замена рабочего хранения.
- Не обещать транзакционность записи через `w`, автоматический откат памяти, безопасную конкурентную запись или восстановление повреждённого файла без участия пользователя.

## 3. Паспорта занятий

### 28. Исключение и traceback своей цепочки

**Основная тема и назначение.** Учиться объяснять отказ по фактическим вызовам, а не лечить любую ошибку перехватом. Диагностика использует работающий проект, не новую лабораторию вместо него.

**A.** Известны вызовы, возврат и диагностическая обёртка; реальные readers уже ловят `ValueError` от `int`. Явный `raise` и полное устройство `try` ещё впереди.

**B.** Ученик находит тип, сообщение, место возникновения и цепочку распространения; различает обработанный неверный ввод и неперехваченную ошибку договора вызова.

**Темы в порядке изучения:**

1. Ошибка исполнения, остановка текущего пути и отсутствие обычного результата. Отличить от синтаксической ошибки до запуска.
2. Последняя строка traceback и кадры своего кода; место проявления не всегда является источником неверного значения.
3. Последовательность вызовов и возвратов при отказе. Обёртка добавляет кадр, но не устраняет причину.
4. `ValueError`, `TypeError`, `KeyError` как разные наблюдаемые категории, не набор универсальных обработчиков.
5. Почему неверная строка в текущем reader не завершает программу; найти уже существующую границу перехвата.
6. Минимальное воспроизведение, гипотеза и проверка; исправлять договор/данные, не подавлять симптом.

**Основная практика, свой проект:**

1. В штатном CLI ввести текст вместо приоритета и id; найти преобразование и существующий перехват. Объяснить отсутствие необработанного traceback.
2. До введения безопасного импорта временно заменить конечный `run()` наблюдательным вызовом собственной `traced_format_task` с заведомо неполной записью. Проследить `KeyError`, кадры и отсутствие сообщения успешного завершения обёртки.
3. Выделить минимальную причину: отсутствие конкретного обязательного поля. Повторить вызов с полной настоящей записью, не добавляя default к полю, которое обязан предоставить вызывающий код.
4. Вернуть штатный запуск, проверить обычные карточки и отсутствие искусственного дефекта в diff. Не коммитить ошибочную запись или наблюдательный вызов.

**Выход и переход.** Диагностика опирается на свой код и правильный договор. Следующий шаг раскрывает уже встречавшийся конкретный перехват и устраняет повтор ввода.

### 29. Конкретный `try/except` и общий числовой ввод

**Основная тема и назначение.** Отделить преобразование ввода от предметного диапазона. Новое понимание исключений сразу используется для рефакторинга readers.

**A.** `read_priority` и `read_task_id` повторяют цикл `input → int → except ValueError`. Положительность id и диапазон приоритета различаются.

**B.** Общая `read_int(prompt)` отвечает за получение целого, прежние readers используют её и сохраняют свои ограничения и сообщения.

**Темы в порядке изучения:**

1. Как `try` выполняется до отказа, как выбирается соответствующий `except`, что происходит при отсутствии подходящего перехвата.
2. Маленький `try` вокруг ожидаемо опасного преобразования, а не вокруг всей команды.
3. `except ValueError` не лечит программный `NameError` и не должен скрывать его через `Exception`.
4. После обработанного отказа нужно выбрать повтор, результат или завершение; недопустима переменная, которая не получила значения.
5. Успешное преобразование ещё не означает допустимый приоритет/id. Общая механика и предметные ограничения имеют разные владельцы.

**Основная практика, проект:**

1. Сравнить текущие readers и выделить повторяющуюся часть в `read_int(prompt)`: повторять ввод до успешного преобразования, возвращать целое, сохранять сообщение о неверном числе.
2. Переработать `read_priority/read_task_id` как пользователей этой функции. Их циклы диапазонов остаются осмысленными; повтор преобразования удаляется.
3. Проверить последовательности «текст → число вне диапазона → допустимое число» для обеих команд; ни один неудачный ввод не добавляет запись.
4. В коротком примере найти слишком широкий `try`, где случайный дефект воспринимается как ошибка пользователя. Объяснить, почему изменение границы правильнее общего перехвата.

**Выход и переход.** Общий ввод реально заменяет повтор кода. Далее правила нужно защитить и при вызове функций без CLI.

### 30. `raise`, `else`, `finally` и правила модели

**Основная тема и назначение.** Сделать договор создания данных самостоятельным: прямой вызов функции не должен обходить правила, проверяемые только читателем ввода.

**A.** Известны конкретный перехват и четыре поля задачи. `create_task` пока возвращает словарь без полной самостоятельной проверки.

**B.** Создание задачи проверяет значения до возврата, `add_task` не выполняет `append` при отказе. CLI сообщает ожидаемую ошибку значения, но не скрывает дефект программы.

**Темы в порядке изучения:**

1. Обычное отсутствие результата и нарушение обязательного правила. `raise ValueError` прекращает текущий успешный путь.
2. Чистая проверка до эффекта: нормализовать название, проверить непустоту, положительный id, приоритет 1–5 и ожидаемые типы до создания/добавления.
3. Ввести необходимый минимум `isinstance`/проверки типа до практики. Аннотация не заменяет проверку; полный случай `bool` как числа подробно разбирается в 35.1.
4. Общие `validate_title`, `validate_priority`, `validate_task_id`: корректное значение возвращается в согласованном виде, неверное даёт `ValueError`. `normalize_title` переиспользуется, не пишется заново.
5. `else` выполняется после успешного `try`; `finally` выполняется при разных исходах, но не означает успешный результат. Возврат из `finally` может скрыть отказ.
6. Изучить `else/finally` в коротком исследовании. Не добавлять фиктивное освобождение ресурсов в CLI, когда ресурсов ещё нет.

**Основная практика, проект и исследование:**

1. Добавить объяснённые чистые валидаторы и вызвать их из реальной `create_task` до построения полной записи. Найти потребителей; не создавать вторую модель или фабрику для упражнений.
2. Прямо вызвать фабрику с корректным названием с пробелами, пустым названием, неверным приоритетом/id и неправильным типом. Корректная задача сохраняет четыре поля и исходный смысл.
3. Проверить `add_task` при отказе: длина, прежние записи и следующий вычисляемый id не меняются. Ожидаемый `ValueError` в `handle_add` превращается в сообщение без ложной карточки успеха.
4. Предсказать порядок вывода небольшого `try/except/else/finally` при успехе и отказе; найти пример, где `finally` маскирует ошибку. Не переносить CLEANUP в проект.

**Выход и переход.** Правила доступны не только при ручном вводе и действуют до мутации. Далее разбирается конкретный прикладной отказ для неизвестного id.

### 30.1. Собственная ошибка и обязательное получение задачи

**Основная тема и назначение.** Различить поиск, где отсутствие нормально, и действие, которому существующая задача необходима. Узкое знакомство с классом ошибки не считается пройденным ООП.

**A.** `find_task(tasks, task_id)` возвращает словарь или `None`; `mark_task_done` возвращает признак найденной задачи. Понятны `raise` и граница CLI.

**B.** Введены `TaskNotFoundError` и `get_task(tasks, task_id)`. Прикладное чтение/завершение имеют явный отказ, интерфейс сохраняет понятное сообщение и неизменность данных.

**Темы в порядке изучения:**

1. Собственный тип различает смысл отказа без анализа текста сообщения.
2. Минимальный `class TaskNotFoundError(Exception)`, наследование готового поведения, `pass`, создание экземпляра с сообщением и перехват по типу. Всё это объяснить до требования написать код.
3. Не вводить сейчас `self`, сложный конструктор, иерархию моделей или сервисные классы.
4. `get_task` переиспользует `find_task`: отсутствие превращается в ошибку обязательного получения; низкоуровневый поиск не теряет прежний договор.
5. Распространение до интерфейса и `except ... as error`; технический тип отдельно от пользовательского сообщения.
6. Сохранение причины через `raise ... from ...` исследовать на малом примере. Применение к ошибкам хранения находится в 35.2.

**Основная практика, проект:**

1. Добавить тип ошибки и одну функцию `get_task`; не писать второй цикл поиска.
2. Перевести `handle_find` и путь завершения на обязательное получение. При необходимости `mark_task_done` использует `get_task`: успешный прежний результат сохраняется, отказ неизвестного id меняется явно с `False` на исключение. Обновить всех потребителей одновременно.
3. В обработчиках перехватить конкретный прикладной отказ, сохранить сообщение «Задача не найдена» и продолжение меню. Не ловить весь `Exception` вокруг цикла.
4. Проверить существующий/неизвестный id, повторное завершение, отсутствие изменения при отказе; объяснить разницу `find_task` и `get_task`.

**Выход и переход.** Один механизм поиска и объяснённый слой обязательного получения. Типы ошибок уже созданы, поэтому далее можно разнести их и операции по модулям без скрытой новизны.

### 31. Модули, `import` и безопасный запуск

**Основная тема и назначение.** Перенести рабочие компоненты, не переписывая их и не меняя набор команд. Разделение следует реальным обязанностям.

**A.** В одном файле есть модель-словарь, валидаторы, операции, тип ошибки, CLI и диагностика. Импорт пока начинает `run`.

**B.** Функции перенесены в модули, связи выражены импортами; импорт main и нижних модулей не читает ввод и не печатает меню.

**Темы в порядке изучения:**

1. Модуль как файл с собственным пространством имён; отличие имени файла и имени импортируемого объекта.
2. `import module` и `from module import name`, обращения к имени, минимальная причина ненайденного модуля.
3. Верхний уровень выполняется при первом обычном импорте в процессе; определения функций не запускают их тела. Создание обёртки не должно выполнять CLI.
4. `__name__` при запуске и импорте, защитное условие точки входа.
5. Направление зависимости и последовательный перенос: нижние компоненты не импортируют main для получения списка.
6. Стандартная и сторонняя библиотека; `functools.wraps` теперь объясняется как импортируемый помощник для метаданных знакомой обёртки. Его применение не меняет предметный договор.

**Основная практика, проект:**

1. Разнести реальные компоненты в `validators.py`, `models.py`, `operations.py`, `errors.py`; в main пока оставить CLI. Валидаторы и ошибки не импортируют main; операции используют модель и ошибки.
2. Переносить одну группу за раз, обновляя вызовы импортами. Старые копии удалять после подключения, не оставлять две работающие реализации.
3. Защитить запуск `run`; проверить `python -c "import main"` и импорты новых модулей без меню/ввода, затем обычный `python main.py`.
4. Если диагностика сохраняется отдельно, перенести её в `diagnostics.py` и объяснённо добавить `wraps`; не активировать её для всех функций.
5. Проверить прежние команды и прямые вызовы валидаторов. Не добавлять JSON или storage-заглушку, чтобы оправдать количество файлов.

**Выход и переход.** Модульный код действительно импортируем, а функциональные операции ещё не названы готовым сервисом. Следующий шаг упорядочивает те же модули в пакет.

### 33. Отделить CLI от сборки

**Основная тема и назначение.** Выбрать владельца начального состояния до подключения файла. Создание компонентов и чтение пользовательской команды имеют разные обязанности.

**Основная практика, проект:**

Затем оставить в `app.main` функцию запуска: создать пустой список и передать в уже готовый `run`; сохранить защищённую точку входа.

### 34. Файл как ресурс: путь, режим, `with`, UTF-8

**Основная тема и назначение.** Понять чтение/запись до JSON и предотвратить путаницу формата с ресурсом. Это одно информационное занятие с осмысленным экспериментом.

**A.** Известны import, стандартная библиотека, функции и строки. Путь, файловый объект, кодировка и методы Path объясняются впервые.

**B.** Ученик выбирает безопасный путь, различает `r/w/a`, понимает закрытие ресурса и может объяснить перезапись файла.

**Темы в порядке изучения:**

1. Память процесса и файл; путь не является содержимым. Относительный путь зависит от cwd, не от местонахождения любого исходника.
2. `Path`, соединение частей, `__file__`, `resolve`, `parent`, создание каталога. Использование готового объекта библиотеки не считается изучением собственной объектной модели; методы объяснить как доступные операции.
3. Рабочий путь будущего приложения вычисляется в сборке от корня проекта; нельзя менять cwd для поиска данных или независимо заводить путь в CLI.
4. `r` читает существующее, `w` создаёт/обнуляет, `a` дописывает. Снимок не является журналом добавлений.
5. `with` управляет временем открытия и закрытия при разных исходах. Это не гарантия атомарной записи.
6. Текст, UTF-8, кириллица, отсутствие против отказа доступа. Полный перевод ошибок хранения находится в 35.2.

**Основная практика, безопасный эксперимент:**

1. В явно выделенном учебном файле, не `data/tasks.json`, записать и прочитать короткий русский текст. До запуска предсказать результат.
2. Повторить запись через `w`, затем сравнить с `a`; объяснить, почему полный снимок нельзя дописывать как ещё один документ.
3. Сравнить относительный путь и путь, построенный от расположения учебного модуля, при смене cwd. Не требовать запуска пакета из произвольной папки без объяснения поиска пакета.
4. Исследовать чтение отсутствующего файла и закрытие после `with`. Не писать `save_titles/load_titles` как новую возможность Planner.

**Выход и переход.** Механика IO понятна, рабочие данные не затронуты экспериментом. Далее сохраняется полный смысл настоящих задач, а не только строки заголовков.

### 34.1. JSON-представление настоящих задач

**Основная тема и назначение.** Подготовить обратимый формат данных отдельно от политики сохранения. Созданный компонент нужен ближайшему проектному шагу.

**A.** В своём CLI можно получить итоговый список через `run`; задача имеет четыре поля. Пути и файлы уже объяснены, JSON впервые вводится здесь.

**B.** В `app.storage` есть `encode_tasks(tasks)` и `decode_tasks(text)` для полного JSON-представления; их договор используется затем в файловых функциях. Это не параллельное хранилище.

**Темы в порядке изучения:**

1. Сериализация значения в текст и десериализация обратно; восстановленные контейнеры не обязаны быть теми же объектами.
2. Объект/массив/строка/число/логическое/null в JSON и их соответствие dict/list/str/числам/bool/None. `true` не является Python-идентификатором `True` в файле.
3. `dumps/loads` работают со строкой, `dump/load` с файловым объектом. Выбрать одну реализацию, не поддерживать две независимые рабочие схемы.
4. UTF-8, `ensure_ascii=False`, читаемые отступы; внешний вид текста и сохранение значений имеют разные критерии.
5. Полные поля и исходные id: не пересоздавать записи через фабрику с новыми номерами и сброшенным `is_done`.
6. Синтаксически правильный JSON ещё не доказывает правильность модели; подробная проверка формы получает место 35.1.

**Основная практика, проект:**

1. Создать задачи через свой CLI, одну завершить и получить итоговый список. Не готовить отдельный ручной список вместо них.
2. Добавить строковые преобразования в реальный `app.storage`, импортируя json. Пока не подключать IO к меню.
3. Пройти список → JSON-текст → список; сравнить четыре поля, кириллицу, id, приоритеты и статус. Объяснить равенство данных без ожидания одинаковой идентичности.
4. Исследовать различие `true/True`, пустой список и неправильную JSON-кавычку. Ошибки запускать отдельно от нормального сценария.

**Выход и переход.** Компонент формата проверен на своих данных. Новый процесс пока не обещает восстановление: это будет конкретным результатом следующего занятия.

### 35. Подключить загрузку и сохранение после изменения

**Основная тема и назначение.** Начать реально пользоваться одним JSON, а не ограничиться примером round trip или сохранением только на exit.

**A.** Готовы сборка, CLI с явным состоянием, JSON-преобразования, callbacks и замыкания. Каждая возможность Planner уже работает до файлового подключения.

**B.** `load_tasks(path)` и `save_tasks(path, tasks)` подключены к запуску; удачные add/done сохраняются до сообщения успеха, новый процесс читает накопленные данные.

**Темы в порядке изучения:**

1. Загрузка до меню, один список сессии, полный снимок после изменения. Чтение не требует сохранения.
2. Единственный рабочий путь `data/tasks.json` задаёт `app.main`, вычисляя его от расположения пакета и корня, не от случайного cwd.
3. Отсутствующий файл даёт первый пустой запуск; при первой записи создаётся родительский каталог. Только конкретное отсутствие является нормой, не любой отказ IO.
4. Callback `on_change(tasks)` сообщает о реально выполненном изменении; замыкание связывает известный путь с `save_tasks`.
5. Согласованное расширение договора: `run(tasks=None, on_change=None)` и обработчики получают необязательный callback. Вызов `run()` без хранения остаётся возможным.
6. Завершение уже выполненной задачи не является новым изменением. Прежний признак «найдена» не подменять молча признаком «изменилась».
7. Сохранение после каждого изменения не равно транзакции. Детальный пользовательский договор отказа записи вводится в 35.2; до него ошибку нельзя превращать в успех.

**Основная практика, проект:**

1. Реализовать файловые функции в `app.storage`, переиспользуя `encode_tasks/decode_tasks`. Чтение только `r`, запись полного снимка `w`, UTF-8; сериализовать до открытия на перезапись, чтобы отказ преобразования сам не обнулил файл.
2. В сборке выбрать путь, загрузить список, создать настроенный callback и передать оба в CLI. Нижние модули не импортируют main ради пути.
3. Расширить обработчики единым необязательным `on_change`; читающие принимают его для единой формы вызова, но не вызывают. `handle_add` уведомляет после успешного добавления; `handle_done` проверяет прежний статус и уведомляет только при переходе в выполненное. Ошибка id или значения не вызывает callback.
4. Таблица команд по-прежнему хранит функции; run передаёт список и callback при вызове. Нет сохранения при построении таблицы или на любой неизвестной команде.
5. Через CLI добавить две задачи с кириллицей, завершить одну, выйти и запустить новый процесс. Проверить list/find/search/stats, статусы и следующий id при добавлении третьей.
6. Сравнить файл до/после читающих команд, неправильного ввода, неизвестного id, повторного done и exit без изменений: повторной записи нет. Факт вызова callback можно отдельно наблюдать известной диагностикой, без новых инструментов тестирования.

**Выход и переход.** Данные реально сохраняются по проектному сценарию. Следующий шаг не реализует сохранение снова, а проверяет, что восстановленное содержимое допустимо.

### 35.1. Проверить форму восстановленного состояния

**Основная тема и назначение.** Разделить валидный JSON и валидный снимок Planner; не допустить частичного восстановления, случайных default и повторных id.

**A.** Работает перезапуск на корректных собственных данных, есть валидаторы и полная модель словаря. Синтаксис JSON не проверяет прикладной смысл.

**B.** `validate_loaded_tasks` проверяет весь снимок до передачи CLI и перед записью. Любой неверный элемент отклоняет набор целиком; рабочий файл не «чинится» побочным сохранением.

**Темы в порядке изучения:**

1. Уровни проверки: корень, запись, обязательные поля, типы, значения, согласованность набора.
2. Корень list, элементы dict; полный договор `id/title/priority/is_done`, без обязательных будущих tags. Лишние поля этого четырёхпольного формата отклоняются, расширение схемы позднее согласуется отдельно.
3. id и priority являются целыми, не bool; `True` участвует в числовой модели Python, поэтому обычная проверка int недостаточна. До практики объяснить точный `type` либо явное исключение bool.
4. Положительный id, диапазон 1–5, непустое нормализованное строковое название, точный bool у статуса. Чтение не должно скрыто обрезать/заменять испорченные данные.
5. Уникальность id проверить понятным проходом и уже знакомым контейнером, не требовать новой сложной конструкции.
6. Проверка всего набора до публикации состояния: пропуск плохих записей скрывает потерю данных. Неверный корень не превращается в `[]`.

**Основная практика, проект:**

1. Добавить проверку в storage, переиспользуя чистые правила модели там, где договор совпадает. Для чтения сравнить заголовок с нормализованным результатом, не переписывать оригинал молча.
2. Подключить её после декодирования до передачи run; проверить исходящие данные до открытия `w`.
3. На отдельном учебном пути к копии снимка по одному проверить неверный корень, не-словарь, отсутствующий статус, строковый приоритет, bool вместо id, пустое название, недопустимый диапазон и повтор id. Точное место отказа должно быть понятно.
4. Убедиться, что ни один отказ не запускает меню с частичным набором и не записывает исправленную «пустую базу». Восстановить корректную копию и повторить чтение.

**Выход и переход.** Договор снимка проверяется целиком. Далее синтаксические, прикладные и файловые ошибки объединяются в понятную границу хранения, не смешиваются с ошибками предметного действия.

### 35.2. Ошибки хранения и сохранность данных

**Основная тема и назначение.** Честно сообщать о неудаче и не уничтожать данные из-за удобного default. Финал укрепляет уже работающий путь, а не впервые собирает его.

**A.** Есть рабочие загрузка/запись, проверка снимка, собственный тип прикладной ошибки и известное сохранение причины. Ограничения режима `w` объяснены.

**B.** Введён `StorageError`, ожидаемые отказы переводятся в него с причиной. Сборка останавливает запуск при плохом чтении; неудачное сохранение не выдаётся за успех и не вызывает повторную автоматическую перезапись.

**Темы в порядке изучения:**

1. `FileNotFoundError` при открытии выбранного файла для чтения, `JSONDecodeError`, ошибка формы снимка и `OSError` имеют разный исходный смысл.
2. Только отсутствие выбранного файла при загрузке даёт `[]`; отсутствие каталога при записи обрабатывается созданием папки, а не возвратом успеха. Отказ доступа, каталог вместо файла и повреждение не являются первым пустым запуском.
3. Короткие границы перехвата: переводить ожидаемый отказ соответствующей операции, не ловить весь код через `Exception`.
4. `StorageError` и `raise ... from error` сохраняют причину; CLI получает понятное сообщение, технический источник остаётся доступен для диагностики.
5. При отказе загрузки menu не запускается, сохранение не вызывается. При отказе записи память уже могла измениться: это не автоматический rollback.
6. Для простого учебного режима отказ записи завершает текущую сессию через границу сборки с сообщением о несохранённом изменении. Нет ложной карточки успеха, продолжения обычной работы или автоматического save в `finally`/на exit.
7. Режим `w` способен оставить частичный файл при сбое записи. Резервная копия и ручное восстановление нужны до разрушительных экспериментов; атомарная замена, блокировки и конкурентность не являются тайными требованиями.

**Основная практика, проект:**

1. Добавить `StorageError` в `app.errors`, перевести ожидаемые ошибки чтения, формы и записи внутри storage; не перехватывать случайные NameError/TypeError всей программы как «ошибку диска».
2. В сборке обрабатывать только этот договор вокруг загрузки и сессии. После плохого чтения не запускать CLI; после отказа callback остановить сессию и сообщить, что сохранение не подтверждено. Успешные сообщения обработчиков идут только после завершившегося callback.
3. На учебной копии данных сравнить отсутствие файла, повреждённый JSON, корректный JSON неверной формы и путь к каталогу вместо файла. Убедиться, что повреждённое содержимое осталось нетронутым и не заменено `[]`.
4. Без изменения системных прав проверить запись в путь, занятый каталогом, через отдельно настроенный диагностический запуск. Ошибка наблюдаема, успех не печатается, повторная запись при выходе не выполняется. Рабочий путь не повреждать.
5. После восстановления корректного файла пройти два штатных запуска с add/done, чтением, ошибочным вводом и статистикой. Убедиться, что обычный путь сохранения не сломан защитой.

**Выход и переход.** Функциональный Persistent Planner работает с одним JSON и имеет честные ограничения. Следующий блок вводит обычный класс Task и готовит объектную модель рядом с действующим путём, не ломая этот CLI раньше согласованной миграции.
