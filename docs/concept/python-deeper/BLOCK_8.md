### Точка A блока

Ученик понимает функции и передачу состояния, исключения, импорты, пакет, пути/JSON, классы и экземпляры, методы, dataclass, независимые tags и композицию. Он уже умеет выполнять прямые проверки с assert, но системное знакомство с pytest ещё предстоит.

В проекте по принятому маршруту:

- в `app.models` подготовлена одна dataclass Task с `id/title/priority/is_done/tags`, методами и to_dict/from_dict;
- Task пока не включена в операции и рабочий storage; старые полные четырёхпольные записи принимаются её конвертером;

### Точка B блока

Persistent Planner сохраняет исходный корень и историю, добавляет, читает, ищет, завершает и удаляет задачи, показывает статистику. Все обработчики используют один PlannerService. Сервис получает storage, выполняет действие на актуальном наборе и сохраняет только успешное изменение. Обычный запуск использует JsonStorage; MemoryStorage применяется как объяснённая альтернатива и зависимость для проверок.

Итоговый договор:

| Компонент | Обязанность и результат |
| --- | --- |
| `app.models.Task` | Одна задача, прежние правила, методы изменения, независимые tags, явные конвертеры |
| `app.storage.JsonStorage(path)` | `load() -> list[Task]`, `save(tasks)`; путь задан сборкой, чтение/запись и ошибки остаются внутри роли хранения |
| `app.storage.MemoryStorage(tasks=None)` | Тот же load/save; свой контейнер с явно объяснёнными общими ссылками на Task |
| `app.services.PlannerService(storage)` | Координация предметного действия; нет input, печати, выбора типа storage или второго постоянного списка |
| `app.cli` | Разбор команды/ввода, вызов сервиса, представление и сообщения; нет собственного CRUD и JSON-IO |
| `app.main.build_service(storage=None)` | При None создаёт JsonStorage для одного рабочего пути, при явной зависимости использует её; импорт/сборка не начинают input или запись |
| `tests/` | Проверки модели, сервиса, договоров storage и CLI; файлы изолированы через tmp_path |
| README и проверенная версия | Воспроизводимые запуск/тесты, архитектура, ограничения, порядок создания и сохранения данных |

Итоговые методы сервиса заданы картой курса:

| Метод | Результат и важный эффект |
| --- | --- |
| `add_task(title, priority, tags=None)` | Создаёт Task с назначенным id и False, сохраняет набор, возвращает Task |
| `list_tasks()` | Актуальный список Task; чтение без save |
| `get_task(task_id)` | Task либо TaskNotFoundError |
| `mark_done(task_id)` | Возвращает Task; сохраняет переход в выполненное, повтор не создаёт запись и не требует нового save |
| `delete_task(task_id)` | Удаляет существующую задачу, сохраняет набор, возвращает None; неизвестный id даёт TaskNotFoundError |
| `search_tasks(query)` | Совпадения без изменения данных; пустой очищенный фрагмент даёт [] |
| `get_statistics()` | `all/open/done`, all = open + done; процент вычисляется из этой сводки, для пустого набора 0.0 |

Новая задача получает 1 в пустом наборе, иначе максимум **текущих** id + 1. Удаление не перенумеровывает соседей. Это не обещание пожизненной уникальности удалённых id: удалённый максимальный номер может использоваться снова. Существующие алгоритмы не заменяются новым счётчиком без отдельного требования.

### Границы и честные ограничения

- Новая возможность delete вводится в 40.2. Остальные операции переносятся, а не реализуются заново ради новой архитектуры.
- Tags сохраняются как часть модели/JSON; новых команд управления метками не требуется.
- Нет HTTP, FastAPI, Pydantic, схем запросов, базы, async, конкурентной записи, UI, TaskBoard или абстрактного Storage-фреймворка.
- Наследование не является условием заменяемости; достаточно одинакового объяснённого поведения load/save. ABC/Protocol не нужны.
- Копия списка в MemoryStorage не копирует каждую Task. Изменение общей Task может быть видно до save; модель не обладает транзакционной изоляцией.
- Неверный ввод не должен менять данные или вызывать save. Отказ записи после мутации не означает гарантированный откат памяти; запись через w не становится атомарной от наличия класса.
- Программа работает в принятом учебном режиме последовательного доступа. Согласование одновременных writers принадлежит будущему расширению, не скрытой приёмке этой главы.

## 3. Паспорта занятий

### 39. Включить Task в существующий Planner

**Основная тема и назначение.** Провести согласованную замену внутреннего представления, сохранив пользовательский смысл и накопленные данные.

**A.** Готова Task с методами, конвертерами и tags. Функциональный CLI/storage работают на словарях; полный старый JSON и перезапуск проверены ранее.

**B.** Действующие операции и показ используют Task, функциональный load возвращает объекты, save выдаёт записи. Старые записи читаются, новые содержат tags.

**Темы в порядке изучения:**

1. Внутренний объект и запись на диске имеют разные роли; смена представления не меняет назначение id или команды.
2. Список потребителей: создание, поиск, завершение, поиск по title, статистика, карточка, IO. Частичная миграция создаёт смешанный набор.
3. Обращение к атрибутам и готовым методам вместо ключей; известные циклы подходят, не нужен новый next/генератор.
4. Схема снимка меняется согласованно: прежние обязательные поля сохраняются, отсутствие tags в старой полной записи допустимо, остальные дефекты отклоняются.
5. Восстановление использует from_dict, не фабрику с новым id; запись использует to_dict, не __dict__/str/asdict как обход подготовленного договора.

**Основная практика, проект:**

1. На копии собственных данных обозначить все потребители словаря, затем перевести рабочую цепочку целиком на Task. Общие правила и алгоритмы переиспользовать.
2. Заменить создание записи на готовую Task; подключить mark_done и чтение полей. Прежний договор низкоуровневой операции меняется только там, где это необходимо, все вызовы обновляются вместе.
3. Перевести функциональные load/save и проверку всего снимка на объекты/готовые конвертеры. По-прежнему проверять уникальность id всего набора, а не только отдельную Task.
4. Удалить ненужную словарную фабрику и обращения к ключам в предметных операциях. Файловые записи остаются словарями как внешний формат, не удаляются ради «чистого ООП».
5. Пройти add/list/find/search/done/stats и перезапуск, проверить старую запись и новую запись с tags. Не добавлять delete и не собирать storage/service здесь.

**Выход и переход.** Task стала действующей моделью. Следующий шаг переносит уже работающий IO в объект, а не начинает JSON заново.

### 39.1. JsonStorage вокруг готового хранения

**Основная тема и назначение.** Собрать настройку пути и файловое поведение в один компонент; перестать считать список длительной сессии источником истины.

**A.** Функциональные load/save возвращают/принимают Task и поддерживают новый/старый формат. Сохранение пока уведомляется callback из CLI.

**B.** `JsonStorage(path)` имеет load/save; каждое действие получает актуальный набор. Постоянный список CLI и активное callback-сохранение больше не участвуют в пути данных.

**Темы в порядке изучения:**

1. Объект хранит настройку path, методы используют её; создание JsonStorage не открывает файл и не запускает меню.
2. Новый метод повторяет договор готового IO, не копирует параллельную файловую реализацию.
3. `load → выполнить действие → save при изменении`; чтение не сохраняет. На одну команду нет второго случайного чтения для того же результата.
4. Сборка выбирает путь/объект, CLI передаёт зависимость. Ни storage, ни операция не импортируют main ради настроек.
5. Ошибки и ограничения `w` сохраняются после переноса; класс сам по себе не создаёт транзакцию.

**Основная практика, проект:**

1. Перенести load_tasks/save_tasks в JsonStorage.load/save, сохранив проверку снимка, преобразования и StorageError с причиной. Общие чистые помощники можно оставить, второго публичного файлового пути не оставлять.
2. Временно сделать существующие прикладные функции storage-aware: они получают storage и загружают набор для действия, используют прежние алгоритмы, сохраняют только изменение. Это переходный слой до переноса в service.
3. CLI получает storage вместо постоянного списка. Обработчики вызывают переходные операции; on_change не подключается и не выполняет вторую запись. Удалить заменённое владение состоянием; оставшиеся временные параметры окончательно убрать в 40.2.
4. Прочитать данные через один объект, изменить через другой объект с тем же путём и снова прочитать через первый: видны актуальные данные, нет startup-кеша.
5. Проверить перезапуск, старые записи, неверный ввод, неизвестный id и повторное done без save. Проверочный путь явный, рабочий JSON не повреждается экспериментом.

**Выход и переход.** Обычный продукт остаётся persistent, но его зависимость узкая и явная. Далее второй вариант storage проверяет заменяемость этого договора.

### 40. MemoryStorage и один договор

**Основная тема и назначение.** Показать заменяемость хранения и объяснить владельцев контейнера и объектов, не подменяя сохранение новым in-memory проектом.

**A.** JsonStorage работает через load/save, операции получают storage. Классы, композиция, ссылки и поверхностная копия знакомы.

**B.** MemoryStorage реализует тот же договор. Те же операции работают с обоими storage; обычный запуск остаётся JSON.

**Темы в порядке изучения:**

1. Совместимость поведения важнее общего предка; одинаковые названия недостаточны без совпадения типов и ошибок.
2. Начальный набор опционален, None отличается от переданного контейнера. MemoryStorage хранит копию внешнего списка.
3. load и save копируют контейнер; append/удаление элемента полученного списка не меняют внутренний список без save.
4. Task внутри остаются общими объектами: вызов mark_done на загруженной Task может быть виден сразу. Не обещать глубокую копию или rollback.
5. Память полезна для быстрых изолированных проверок, но новый независимый MemoryStorage не восстанавливает завершённую сессию.

**Основная практика, проект:**

1. Добавить MemoryStorage рядом с JsonStorage, не удаляя файловый вариант; использовать один договор list[Task].
2. Проверить внешнюю копию начального контейнера, возвращаемого контейнера и контейнера save. Отдельно показать общую ссылку на Task и объяснить границу защиты.
3. Передать память тем же переходным операциям и выполнить add/find/search/done/stats. Сравнить предметный результат с JSON на изолированном пути.
4. Проверить, что сборка выбирает один storage, не синхронизирует одновременно память и файл и не использует память как второй кеш.

**Выход и переход.** Зависимость заменяема на выполненных действиях. Теперь их координацию можно постепенно собрать в сервисе.

### 40.1. PlannerService и перенос чтения

**Основная тема и назначение.** Дать сервису конкретную роль и начать с не меняющих данные сценариев. Не создавать новый CRUD ради названия класса.

**A.** Оба storage работают, переходные функции читают актуальный набор; Task и алгоритмы готовы.

**B.** PlannerService(storage) предоставляет list_tasks/get_task/search_tasks/get_statistics. Читающие команды используют его, статистика имеет целевой договор all/open/done.

**Темы в порядке изучения:**

5. Переходный смешанный этап допустим только с точной границей: читающие команды через service, изменения ещё через прежние функции, оба используют **один и тот же объект storage**.

**Основная практика, проект:**

3. Один раз перейти от total/completed/left к all/open/done, обновить расчёт процента и вывод всех потребителей.
4. На этом шаге явно передавать CLI service и тот же storage для ещё не перенесённых изменений. Временное подключение описать, не прятать запись за service.storage или вторым экземпляром памяти.
5. Проверить пустую/непустую сводку, неизвестный id, поиск и чтение после изменения, выполненного прежним путём. Чтение не вызывает save.

**Выход и переход.** Сервис имеет полезный завершённый кусок, но ещё не объявляется единым владельцем всех операций. Следующий шаг заканчивает перенос и удаляет переходные связи.

**Выход и переход.** Пользовательский продукт полностью работает. Далее тесты защищают готовый код, а не прикрывают будущие заглушки.

### 41. Первые автоматические тесты настоящего продукта

### 41.1. Свежая fixture и параметризация

**Основная тема и назначение.** Сделать проверки независимыми и читаемыми. Разные тесты не должны наследовать задачи от соседнего теста.

**A.** Есть простые тесты с явной подготовкой памяти и сервиса; повтор подготовки заметен.

**B.** Используются свежие function-scoped fixtures, понятные небольшие наборы вариантов одного правила. Старые тесты сохранили смысл.

**Темы в порядке изучения:**

**Выход и переход.** Подготовка изолирована и понятна. Теперь можно дать каждому файловому тесту собственный ресурс.

### 41.2. Файловая интеграция через tmp_path

**Выход и переход.** Работающий файловый путь защищён тестами. Далее проверяемость расширяется на общение с пользователем.

### 42. SOLID и тестируемая CLI-граница

**Основная тема и назначение.** Применить архитектурные принципы как диагностику собственного кода и выделить проверяемое действие из цикла общения.

**A.** Продукт работает через один service, накоплены тесты модели/операций/storage. Функции как зависимости знакомы, ввод/вывод пока напрямую связаны с input/print.

**B.** Обработка одной команды отделена от run-цикла, чтение/вывод передаются явно; смешанные обязанности устранены в пределах существующего договора.

**Темы в порядке изучения:**

1. SRP: причина изменения каждой роли; service не должен выбирать файл или печатать карточку.
2. OCP и LSP: второй storage подключается через прежний договор, одинаковый синтаксис с разным смыслом не является заменяемостью.
3. ISP: потребителю нужны load/save, не весь интерфейс файловой системы; DIP: зависимость выбирает сборка, а не сам сервис.
4. Пять принципов не требуют пяти новых классов/файлов. Обосновывать конкретную правку наблюдаемым смешением ролей.
5. Одно действие и цикл имеют разные задачи; известные callbacks позволяют передать read/write без нового framework.
6. Предложенный договор `execute_command(service, command, read=input, write=print)` возвращает признак продолжения сессии; exit завершает цикл, неизвестная команда сообщает и продолжает. Строка команды нормализуется в одном явно выбранном месте.

**Основная практика, проект:**

1. На своём коде назвать по одному реальному примеру роли/замены зависимости; не искать искусственное нарушение каждого принципа.
2. Выделить execute_command из run, сохранив таблицу действий, команды и ошибки. Run читает очередную команду и принимает решение о продолжении по результату.
3. Передать read/write в readers и обработчики; убрать прямые input/print из проверяемой ветки. Готовые предметные методы не меняются.
4. StorageError не превращать в успешное продолжение: прежняя граница сборки останавливает сессию, ошибки данных/id дают сообщение одной команды.
5. Запустить прежние тесты и ручной CLI. Новые функции подготовки не создают второй сервис или список.

**Выход и переход.** Граница одной команды стала проверяемой без подмены глобального input. Следующий шаг добавляет автоматические проверки этой реальной границы.

### 42.1. Регрессия команд, сохранений и безопасной сборки

**Основная тема и назначение.** Защитить связи между вводом, вызовом service, выводом и изменением, а не тестировать только строки в отрыве от данных.

**Выход и переход.** Договор продукта проверен от одной команды до данных и сохранения. Далее остаётся сквозное прохождение накопленного, не новая реализация.

### 43. Сквозная приёмка накопленного проекта

**Основная тема и назначение.** Установить, что все части работают вместе и результаты переносятся между экземплярами. Полный продукт уже готов к этому шагу.

**Темы в порядке изучения:**

4. Восстановление новым service и реальный новый процесс имеют разную силу подтверждения; последний проверяется при передаче.

**Основная практика, проект:**

1. На явно выбранном учебном JSON через реальный CLI выполнить add двух задач → list/find/search → done одной → delete другой → stats. Сверить поля, вывод и записи.
2. Создать новый service на том же пути; проверить сохранённый статус, число задач и следующий id. Delete не перенумеровывает оставшуюся задачу.
3. Проверить неверный ввод/id, повторное done, неизвестную команду и отдельный отказ хранения на копии файла. Нормальный путь не повреждать экспериментом.
4. Пройти весь набор тестов. При найденном расхождении добавить узкий воспроизводящий тест, исправить источник и повторить затронутый сценарий.
5. Если дефектов нет, зафиксировать результат приёмки без косметического переписывания модели/storage или фиктивного нового коммита.

**Выход и переход.** Подтверждён один законченный продукт, а не новый собранный прототип. Следующий шаг проверяет, сможет ли другой человек получить и запустить эту версию.

### 44. Воспроизводимость и передача проекта

**Основная тема и назначение.** Передать проверенный код и понимание архитектуры; выпуск не является деплоем и не добавляет новый функционал.

## 4. Приёмка, удаление переходных связей и передача

### Сквозная приёмка B

- [ ] Вход соответствует завершённым блокам 6–7, а не более раннему локальному снимку или только названиям файлов.
- [ ] Одна Task реально используется всем приложением; старые записи совместимы, новые сохраняют tags независимо от внешнего списка.
- [ ] Обычный запуск выбирает один JsonStorage с одним data/tasks.json; память является отдельной выбранной зависимостью, не кешем.
- [ ] Каждое действие читает актуальные данные, service не держит постоянный startup-список, CLI не реализует собственный CRUD.
- [ ] Все семь методов сервиса соответствуют таблице договора; повтор done не вызывает лишнего save, delete неизвестного id не меняет данные.
- [ ] Ошибки значения/id и чтение не сохраняют снимок; отказ записи не выдаётся за успех и не обещает откат, которого нет.
- [ ] Build_service использует явно переданное storage, default создаёт JSON; импорт/сборка не запускают input или запись.
- [ ] Tests защищают модель, память, service, файл и CLI; свежие fixtures и tmp_path не затрагивают рабочие данные.
- [ ] Новое storage/service действительно восстанавливает данные, а отдельный процесс в проверочной копии подтверждает перезапуск.
- [ ] README и зависимости позволяют воспроизвести запуск/тесты принятой версии; рабочая папка не заменена проверочным клоном.
- [ ] Нет LegacyTask, второго Planner, дублированных CRUD/сохранений, постоянного xfail отсутствующей функциональности и технологий будущей главы.

### Передача в третью главу

B этого блока совпадает с A Planner API: Task/dataclass, PlannerService, MemoryStorage и JsonStorage, тонкий CLI, безопасная build_service, рабочий JSON, pytest и воспроизводимая версия. Ученик сможет добавить сетевой интерфейс к тем же компонентам, а не переносить неподготовленный скрипт в новый репозиторий.

Тесты моделей/операций не считаются знанием HTTP-тестов; Task не является схемой Pydantic. Ни ограничения HTTP-входа, ни полное/частичное обновление, ни веб-запуск не добавляются в эту главу под видом уже освоенного договора.
