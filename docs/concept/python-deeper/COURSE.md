# Python Deeper: общая концепция второй главы

Курс «Python глубже, файлы и структура небольшого проекта» превращает уже работающий Console Planner в Persistent Planner. Ученик не начинает другую программу: он делает прежние операции понятнее, сохраняет задачи между запусками, меняет представление модели, выделяет роли и защищает результат тестами.

Основной принцип главы: **изучили механизм → переработали конкретную часть Planner → проверили прежние возможности**. Проверка сопровождает изменение, а не постоянно заменяет его. Существенно переписать функцию, модуль или слой допустимо, если понятны причина, новый результат и сохраняемое поведение; начинать второй Planner для этого не нужно.

Концепт составлен по [общей методичке](../CONCEPT_AUTHORING.md). Это целевая карта переработки, а не описание уже внедрённых изменений. По ней далее создаются концепты блоков по [методичке для блоков](../BLOCK_CONCEPT_AUTHORING.md). Здесь определены границы, зависимости, изменения проекта и результаты занятий; готовые тексты уроков и решения практики сюда не входят.

### Что реально является предыдущей опорой

Первая глава вводит запуск Python, значения и преобразования, строки, сравнения, условия, циклы, списки и словари, простые функции, результат и изменение состояния, поиск причины ошибки. В проектной теории есть меню, создание записи со стабильным id, отображение, поиск, завершение и статистика. Финальная ручная практика требует запустить собственный Console Planner, выполнить пользовательский сценарий и передать код с README через GitHub.

Но между теорией, заданиями и новым концептом первой главы остаются различия:

| Подтверждённая опора или пробел | Как использовать на входе второй главы |
| --- | --- |

**Точка A главы:** ученик работает в своём существующем репозитории, запускает консольную программу и умеет объяснить простые операции над списком словарей. Имеются функции создания, поиска, изменения статуса и подсчёта; есть пользовательские сценарии и исходная версия. После завершения процесса задачи исчезают. Организация может оставаться одним `main.py`; нет гарантии знания пакетов, объектов собственной модели или автоматических тестов.

В 21 вход подтверждается запуском, а не галочками курса: пустой список; две добавленные задачи; поиск известного/неизвестного id; завершение и повтор завершения; поиск по названию, если реализован; статистика; неизвестная команда и exit. Для каждого фиксируются результат и изменение данных. Отсутствующая обещанная операция восстанавливается по материалам первой главы до зависимых шагов, с явным обозначением пробела. Это не повод заново писать весь Planner.

В новой траектории сохраняется договор первой главы: очищенный непустой title с пользовательским регистром, priority 1–5, положительный id, `is_done=False` у новой записи, чтение без изменения, поиск подстроки без учёта регистра. Пока удаление не изучено, не обещаем его в меню. Процент завершения, если реализован, не исчезает при смене структуры статистики.

### Что не нужно предполагать

Функция с известным `return` ещё не означает знания аргументов по умолчанию, замыкания или декоратора. Словарь задачи не является экземпляром собственной Task. Имя папки не делает её пакетом. Знакомство с Git не означает установленного pytest. Ученик не обязан помнить импорты стандартной библиотеки, схемы файлов, типы ошибок хранения или механизм `classmethod`.

## 2. Цель, точка B и итоговый проект

### Учебный результат

После главы ученик умеет самостоятельно менять небольшой Python-проект, объясняя вход, результат, побочный эффект и владельца состояния. Он понимает функции как интерфейсы; объектную модель как сочетание состояния и поведения; файловое хранение как отдельную границу; тест как проверяемое ожидание. Выбор класса или dataclass обоснован задачей, а не правилом «всё нужно сделать объектом».

**Точка B:** тот же Planner работает через тонкий CLI, модель Task, PlannerService и заменяемые MemoryStorage/JsonStorage. JSON сохраняет задачи после перезапуска. Известные ошибки имеют понятную реакцию без молчаливого сброса данных. Есть unit- и integration-тесты, воспроизводимый запуск, README, контрольный сценарий и проверенная версия.

Эта цель продолжает существующую программу второй главы и соответствует входу [следующей главы](../planner-api/COURSE.md): там появится HTTP-интерфейс над теми же моделью, сервисом и рабочим JSON. Здесь API ещё не реализуется.

### Договор итогового Planner

| Часть | Обязательный результат |
| --- | --- |
| История проекта | Существующий корень и Git-история. Название Persistent Planner описывает новую версию прежней программы; новую папку/репозиторий не создаём |
| Модель | Task с `id`, `title`, `priority`, `is_done`; добавление `tags` объяснено в 38.1 и сохраняется в JSON. Других сущностей и полей здесь нет |
| Инварианты | Допустимые id/title/priority/статус и список строк tags; проверки создания и поддерживаемых изменений. Ошибочный запрос не оставляет принятую некорректную задачу |
| Операции | `add_task`, `list_tasks`, `get_task`, `mark_done`, `delete_task`, `search_tasks`, `get_statistics`. Прежние add/list/find/done/search/stats/exit остаются доступны; delete добавляется по ходу главы |
| Id | Для пустого набора 1, иначе максимум текущих id + 1; не индекс/длина. Удаление не перенумеровывает оставшиеся задачи. Это не обещание никогда не использовать удалённый максимальный id повторно |
| Статистика | Финальная форма сервиса `all/open/done`, с `all = open + done`, согласована с текущим финальным заданием. Переход с `total/completed/left` первой главы выполняется один раз в 40, без второго алгоритма. Смысл счётчиков и известный процент сохраняются |
| Хранение | Единый договор `load() -> list[Task]`, `save(tasks)`. Путь приходит в JsonStorage; service не открывает файл и не выбирает тип хранения |
| Источник данных | JsonStorage с одним рабочим `data/tasks.json` в обычном запуске; MemoryStorage выбирается отдельно для теста/исследования, не живёт рядом как второй кеш приложения |
| Ошибки | ValueError для неверного значения модели, TaskNotFoundError для неизвестного id сервисной операции, StorageError для ожидаемой проблемы хранения. Пустая поисковая выборка остаётся обычным результатом |
| CLI | Только чтение/разбор, вызов существующих операций и сообщения. Внутри нет JSON, назначения id или копии списка всех задач |
| Сборка | Импортируемая `build_service(storage=None)`; default выбирает JsonStorage и известный путь, переданная зависимость используется без замены. Импорт не запускает меню и не создаёт файл |
| Проверки | pytest для модели, сервиса и обоих storage; файловые тесты используют `tmp_path`. CLI проверяется отдельно от реального бесконечного input-цикла |
| Передача | README, зависимости, команды запуска/тестов, ограничение JSON, чистая проверочная копия и версия v2.0.0 после успешной приёмки |

JSON хранит список полных записей, а не только названия. Внутри приложения после миграции находятся Task, на диске остаётся представление из поддерживаемых JSON-значений. Новый экземпляр JsonStorage читает сохранённый результат предыдущего, не начальный снимок в глобальной переменной.

Для концептов блоков закрепить итоговые прикладные контракты. Это целевые сигнатуры, не утверждение, что все они уже реализованы у входящего ученика:

| Операция | Вход → результат | Эффект и отсутствие |
| --- | --- | --- |
| `add_task(title, priority, tags=None)` | Данные новой задачи → созданная Task | load, назначение id, создание корректной модели, save. ValueError до принятия записи; возвращаемая задача содержит назначенный id |
| `list_tasks()` | Без пользовательского входа → список Task | Только load. Пустой набор даёт []; новый контейнер не означает независимость всех объектов |
| `get_task(task_id)` | Допустимый id → Task | Чтение; неизвестный id даёт TaskNotFoundError, не пустую Task |
| `mark_done(task_id)` | Допустимый id → найденная Task с is_done=True | Метод модели и save; повтор не добавляет запись/выполнение. Неизвестный id не вызывает save. Это другой результат, чем bool низкоуровневой функции первой главы |
| `delete_task(task_id)` | Допустимый id → None после успешного удаления | save нового набора, без перенумерации. Неизвестный id даёт TaskNotFoundError; CLI строит подтверждение по исходному запросу, не ждёт bool |
| `search_tasks(query)` | Очищенный фрагмент → список совпавших Task | Без изменения. Пустой фрагмент даёт []; сравнение без учёта регистра, исходный title/порядок сохранены |
| `get_statistics()` | Без пользовательского входа → all/open/done | Читает текущее состояние; одна сводка, без независимого счётчика переходов. Процент вычисляется из неё |

Список объектов для ответа или сохранения является результатом текущего действия, не вторым постоянным состоянием приложения. Известные алгоритмы поиска/подсчёта можно продолжать через for; генератор, next или новый синтаксис не становятся скрытым условием переноса в сервис.

Публичные поля dataclass не становятся автоматически защищёнными от любых прямых присваиваний. Договор модели гарантируется конструктором, декодированием и объяснёнными методами изменения. Код сервиса использует эти методы. Не обещать строгую защиту произвольного внешнего `task.priority = ...`, если выбранная реализация её не обеспечивает.

## 3. Необходимое содержание, границы и изменения материалов

### Обязательное применение механизма к проекту

Для обычного проектного занятия основной результат состоит в новой версии существующего кода или в новых автоматических проверках этого кода. Фразы «изучить функцию», «посмотреть текущую реализацию», «проверить три случая» и «исправить, если найдётся ошибка» сами по себе не задают переработку. Автор концепта блока должен назвать конкретное изменение и объяснить, почему изученная тема делает его возможным.

В паспорте такого занятия зафиксировать:

1. **Прежняя опора.** Какая часть Planner уже работает, где находится её код и какое ограничение мешает следующему шагу. Не приписывать прошлому занятию будущую реализацию.
2. **Новый механизм.** Что ученик должен понять до изменения: например, контракт функции, передача состояния, импорт, преобразование JSON или метод объекта.
3. **Переработка.** Какие существующие функции, вызовы, представление данных или границы ролей меняются. Что переносится и переиспользуется; какая старая реализация после переноса удаляется. Нельзя оставлять новый вариант только в solve, а приложение продолжать запускать через прежний.
4. **Накопленный результат.** Что теперь реально возможно или устроено лучше: общий обработчик, явная зависимость, импорт без меню, восстановление данных, одна модель или автоматически проверяемый договор. Новый документ без такого результата недостаточен.
5. **Регрессия.** Какие прежние команды, поля, сообщения и эффекты должны сохраниться; какие внутренние сигнатуры меняются намеренно и где обновляются их потребители. Проверять новую возможность вместе со старой, а не только отдельно написанный пример.

Рефакторинг может быть существенным по общему объёму. Последовательность и контрольные точки нужны для понимания и поиска причины поломки, а не для ограничения работы несколькими строками. Можно полностью заменить устройство обработчиков, внутреннюю модель или слой хранения, если старые возможности продолжают работать и не появляется параллельная база/вторая архитектура.

**Если конкретная часть уже хорошо построена**, не возвращать её к плохому варианту ради упражнения и не писать аналог под другим именем. Сопоставить её с целевым договором, показать реальное применение нового механизма и выполнить следующий ещё не сделанный шаг этой карты, если его предпосылки уже изучены. Если подходящего изменения пока нет, оставить короткое подтверждение и явно отметить, что переработка в этом месте уже выполнена: не выдавать проверку за новый функциональный результат и не изобретать лишнюю возможность ради diff. При адаптации карты пересчитать долю занятий с изменениями.

Отдельные занятия на подтверждение состояния допустимы и заранее названы: **21** даёт исходную точку, **28** разбирает реальную ошибку, **43** принимает готовый продукт, **44** проверяет передачу и выпуск. Они не служат шаблоном для остальных проектных занятий. Информационные **25, 27, 34, 36** исследуют механизм; ближайший проектный шаг применяет его, не копируя учебную заготовку в новый продукт.

### Последовательность понимания ООП

ООП начинается с неудобства в знакомом проекте: поля и правила одной задачи разбросаны по функциям, любая запись легко становится неполной, действия над состоянием повторяют соглашения. Класс помогает собрать связанные данные и поведение, но сам по себе не проверяет значения и не решает хранение.

| Шаг и место | Что нужно объяснить, а не только показать | Применение и проверка понимания |
| --- | --- | --- |
| Объектная модель, 36 | Словарь остаётся хорошим представлением данных; класс описывает вид объектов, экземпляр является конкретным объектом. Вызов Task создаёт экземпляр; __init__ инициализирует его. Имя self не получает копию объекта | Сравнить две задачи, проследить создание/ссылку, объяснить различие параметра и `self.title`. В 36.1 перенести прежнюю модель в приложение |
| Поля экземпляра/класса, 36–37 | Атрибут конкретного экземпляра, общий атрибут класса и поиск атрибута не одно и то же. Общий изменяемый список опасен; переназначение имени не меняет соседнюю Task | Предсказание изменения двух объектов, устранение общего состояния; реальные задачи сохраняют независимость. Нужен отдельный разбор выбора: словарь для внешнего JSON-представления; функция для самостоятельного преобразования; обычный класс для явного контроля состояния/жизненного цикла; dataclass для модели с повторяющимся кодом полей; сервис для связанного прикладного сценария. Не превращать каждую helper-функцию в класс и не считать dataclass заменой объяснения ООП.

Наследование предметных классов здесь изучается как ограниченный контраст композиции: отношение «является», обязательность совместимого поведения, причина не делать цепочку Task → Storage → Service. Собственные исключения используют простое наследование встроенного типа после отдельного объяснения. Множественное наследование, ABC/Protocol и сложные иерархии не требуются для этого Planner.

### Границы содержания и практики

В главу входят углублённые функции, callable/замыкание/обёртка, исключения, модули и пакеты, файловые операции/JSON, объектная модель и умеренное проектирование, pytest и передача проекта. `functools`, pathlib, json и dataclasses объясняются как конкретные стандартные модули, когда их используют. Установка pytest в прежнюю `.venv` и запись зависимости объясняются до первого запуска тестов.

Здесь нет FastAPI/Pydantic, сетевых запросов, базы данных/ORM, пользователей, асинхронности, Docker, CI/CD или production deployment. Нет нового продукта вместо Planner, TaskBoard, сроков, description и учебных ресурсов. Единственное расширение данных `tags` уже входит в текущий финал; оно объясняется до практики и остаётся внутренним полем модели/JSON. Команд управления тегами добавлять не требуется.

Основная проектная практика работает с уже созданными функциями, задачами и историей. Короткий опыт в интерпретаторе имеет проверяемый смысл: увидеть вызов, ссылку, ошибку или преобразование. Это не второй Planner и не новая база приложения. Предсказание вывода, трассировка состояния, поиск ошибки и небольшой самостоятельный diff поддерживают основную работу, а не заменяют её.

До pytest допустимы объяснённые точечные assert и ручные контрольные сценарии. Assert не заменяет проверку внешнего ввода. С 41 проверки становятся тестами существующего кода. `tmp_path` создаёт изолированный тестовый файл, а не второй ученический проект. Рабочий JSON никогда не удаляется/портится ради скрытого теста; намеренно плохие данные готовятся на отдельном явно учебном пути.

Service может сохранять набор объектов только после успешной проверки. MemoryStorage копирует внешний контейнер, но не гарантирует изоляцию всех полей общей Task: отдельно проверить эту границу и не выдавать её за транзакцию. JsonStorage преобразует представление и не предоставляет сервису приватный файловый кеш.

JsonStorage не является конкурентной БД. Операции CLI и будущего API будут проверяться последовательно. Fail-closed при повреждённом чтении не равен атомарной записи при отключении питания: режим w может повредить файл при сбое в середине сохранения. Объяснить ограничения и резервное копирование; не обещать недоказанную транзакционность и не добавлять молча блокировки/атомарные механизмы вне этой карты.

## 5. Приёмка результата и переход к следующей главе

### Проверяемый итог ученика

1. В прежнем репозитории есть работающий Persistent Planner, а не второй продукт рядом с Console Planner. Можно показать накопление: baseline → безопасные функции → пакет → JSON → Task → dataclass → storage/service → тесты/передача.
2. На отсутствующем рабочем файле первый запуск даёт пустое состояние; через CLI создаются две задачи, проходят поиск, завершение и удаление. Новый процесс восстанавливает оставшуюся запись, её id/title/priority/is_done/tags.
3. Прежние чтение/поиск/статистика не меняют данные. Title сохраняет регистр, неизвестный id даёт объяснённый отказ, повтор done не удваивает счётчики. Delete не меняет id соседей.
4. Неверный title/priority не добавляет принятую запись. На отдельном учебном файле битый JSON/неверная форма даёт StorageError; ошибка не вызывает save и не заменяет содержимое на []. Ошибка записи не объявляется универсально обратимой.
5. Одни операции service выполняются с MemoryStorage и JsonStorage через общий договор. Можно объяснить копию контейнера/общую Task и ограничение каждого способа; нет второго источника состояния в CLI.
6. Ученик объясняет создание экземпляра, self, поле экземпляра/атрибут класса, вызов метода и переход состояния; может выбрать dict/function/class/dataclass и обосновать выбор. Dataclass не заменяет объяснение инварианта, annotations не считаются валидатором.
7. Проверки tags показывают отдельные списки и защиту на границе dict/Task. Старый четырёхпольный JSON поддерживается по названному правилу, произвольно повреждённые записи не «ремонтируются» незаметными defaults.
8. `python -m pytest -q` проходит независимо от порядка; unit-тесты используют свежую память, integration-тесты временные пути. Импорт и build_service не начинают input и не создают рабочий JSON.
9. CLI-граница проверяется без ручного бесконечного цикла; приёмка дополняет unit-тесты новым риском, а не копиями одинакового assert.
10. Проверочная копия запускается по README, проходит тесты и пользовательский сценарий. Известны путь данных, зависимость pytest, способ запуска, ограничение JSON и состояние публикации. Тег/Release не выдаётся за production deployment.

### Что получает следующая глава

Planner API получает прежний корень, пакет app, Task с сериализацией, PlannerService с полным набором операций, оба storage, тонкий CLI, импортируемую build_service, один рабочий JSON и тесты. HTTP не потребует заново писать add/find/done/delete или напрямую открывать файл в маршруте.

Внешнее API-представление может содержать четыре предметных поля, как предусмотрено следующей концепцией; это не разрешение удалить tags из сохранённой модели. Сервисная статистика all/open/done уже готова для маршрута. Сеть, HTTP-семантика, FastAPI и Pydantic остаются новыми знаниями следующей главы, а не скрытыми предпосылками текущей.

### Приёмка самой карты

- A отделена от запланированного выхода первой главы и подтверждается реальным контрольным запуском; пробелы названы и имеют точку восстановления.
- В карте 32 занятия, 28 проектных: **87,5%**. Даже без четырёх специальных П остаются 24 занятия с переработкой кода/автоматических проверок: **75%**. При изменении фактической карты обе доли пересчитываются; проверка без изменения не маскируется под него.
- Для обычного П названы прежняя часть, новый механизм, конкретная переработка, результат и регрессия. Существенная замена допустима; уже подходящий компонент переиспользуется, не реализуется повторно под другим именем.
- Нет последовательности из двух информационных занятий; после Path и смысла объекта следует применение в ближайшем занятии. Ранние 22–24 уже меняют работающий Planner, а не ждут модулей или финального блока.
- Все четыре блока дают несколько последовательных результатов в основном проекте. Первое файловое состояние появляется в 35, объекты включаются в 36.1, полный service/CLI готов к 40.1.
- __init__/self изучаются до миграции, classmethod до переноса from_dict, инварианты до dataclass, load/save до service, pytest/fixture/tmp_path до соответствующих обязательных тестов.
- Важные перестановки имеют причину и проверяемый результат; нет нового репозитория, второй базы задач, повторной фабрики или возвращения к пустому финальному каркасу.
- Последние занятия улучшают границы, проверяют и передают готовое. Они не начинают заново архитектуру и не концентрируют всю реализацию в одной практике.

Итоговая линия: **сохранить понятное поведение → сделать зависимости явными → научиться видеть ошибки → сохранить реальные данные → понять и применить объекты → выделить заменяемые роли → проверить и передать тот же проект**.
