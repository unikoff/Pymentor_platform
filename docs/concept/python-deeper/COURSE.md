# Python Deeper: общая концепция второй главы

Курс «Python глубже, файлы и структура небольшого проекта» продолжает Console Planner из первой главы и доводит его до состояния, которое требуется на входе в третью главу. Основная линия: **углубить функции и CLI → разделить программу на модули и сохранить данные → понять и подготовить объектную модель → перевести приложение на модель, сервис и storage → проверить и передать готовый проект**.

Концепт следует [общей методичке](../CONCEPT_AUTHORING.md). Распределение содержания по блокам 5–8 принято из задания пользователя. Перечень тем не считается готовым порядком: ниже задан самостоятельный маршрут с небольшими последовательными изменениями. Подробные концепты блоков создаются по [методичке для блоков](../BLOCK_CONCEPT_AUTHORING.md).

Это целевой маршрут переработки. Наличие карты не означает, что занятия и практики уже изменены. Номера служат опорой для последующего планирования; дробные части обозначают необходимые дополнительные занятия, а не обязательство вместить несколько первых знакомств в одну встречу.

## 1. Контекст до главы и подтверждённая точка A

### Источники и состояние проекта

Исходную опору сверять по [концепции первой главы](../python-foundations/COURSE.md), [её финальному блоку](../python-foundations/BLOCK_4.md), [реальным занятиям](../../../frontend/src/lessons/python-foundations/block_04/) и каталогам [manual](../../../backend/learning/course_content/chapter_01/block_04/manual.py) / [code](../../../backend/learning/course_content/chapter_01/block_04/code_tasks.py).

Для проверки фактического проекта использовать последовательный репозиторий [unikoff/studyhub](https://github.com/unikoff/studyhub). При этой переработке прочитана его локальная копия с соответствующим origin: HEAD `383c212bda040269b497ea9c504ffd474dfe3248`, «Занятие 20: формат карточки». Проверены исходники и история, не проведено интерактивное прохождение программы. Это снимок для восстановления A; актуальность удалённой ветки отдельным fetch не проверялась.

В этом снимке:

- один `main.py`, функции `normalize_title`, `create_task`, `get_next_id`, `add_task`, `find_task`, `mark_task_done`, `search_tasks`, `build_statistics`, `completion_percent`, `format_task`;

- команды add/list/find/done/search/stats/exit работают с одним списком текущего запуска; файлового хранения, собственной Task, сервиса и тестов нет;
- `run()` вызывается на верхнем уровне. Безопасный импорт предстоит объяснить и реализовать;
- в истории уже есть работа с Git и проверка clone. Наличие коммита не доказывает знание каждого понятия: это отдельно сверяется с учебными материалами.

Не требовать повторного создания этих функций. Если собственный проект ученика отличается, в первом занятии установить его реальные возможности и согласовать необходимые различия. В частности, старые карточки с `done` не являются основанием добавлять второй флаг рядом с `is_done`.

### Что ученик знает, а что предстоит изучить

Ученик знаком со значениями, строками, логикой, условиями, циклами, списками и словарями, простыми функциями, параметрами и `return`. Он способен проследить изменение списка и выполнить основные команды Planner. В первой главе был небольшой опыт traceback и обработки неверного числового ввода.

Эта опора не означает понимания областей видимости, изменяемых default, функций как объектов, замыканий, декораторов, устройства исключений, импортов, файлов, собственной объектной модели и pytest. Эти механизмы вводятся здесь до применения. Git продолжается в той же истории; новое занятие не требует нового репозитория.

**Точка A:** один работающий консольный Planner с задачами в памяти и функциями над списком словарей. Пользователь может добавить, показать, найти, завершить задачу, искать по названию и получить статистику. После завершения процесса данные исчезают. Код может находиться в одном файле; архитектура с объектами и автоматические проверки ещё не построены.

В начале подтвердить пустое состояние, две добавленные задачи, чтение по id, поиск, повторное завершение, статистику, ошибочный ввод, неизвестную команду и exit. Удаление не считать уже изученной возможностью. Отсутствие обещанной операции отметить как пробел и восстановить до зависимого шага, сохраняя остальной проект.

## 2. Цель, точка B и итоговый проект

### B определяется входом в третью главу

Цель взята из раздела «Контекст до курса: исходная точка A» [концепции Planner API](../planner-api/COURSE.md). К началу HTTP-обучения должны быть готовы **Task, PlannerService, MemoryStorage, JsonStorage, тонкий CLI, безопасная сборка, один рабочий JSON и тесты**. Третья глава добавляет другой интерфейс к этим компонентам.

Вторая глава должна дать не только исходники, но и понимание: ученик объясняет создание и состояние объектов, ответственность модели и сервиса, договор хранения, обработку ожидаемых ошибок, изоляцию тестов и путь от команды до сохранённого изменения. Наличие класса само по себе не считается освоенным ООП.

**Точка B:** существующий Persistent Planner добавляет, читает, ищет, завершает и удаляет задачи, рассчитывает статистику. CLI вызывает один сервис. Сервис использует заменяемое storage; обычный запуск сохраняет данные в JSON. Модель и компоненты проверены через pytest, запуск воспроизводится по README, импорт не начинает пользовательский сценарий.

### Обязательный договор на выходе

| Компонент | Что требуется к началу третьей главы |
| --- | --- |
| Корень и история | Тот же репозиторий. Пакет `app` появляется внутри него; название Persistent Planner обозначает развитие прежней программы |
| `app/models.py` | Одна Task через dataclass: `id`, `title`, `priority`, `is_done`, независимые `tags`; правила создания, объяснённые методы изменения и преобразование в/из словаря |
| `app/services.py` | Один PlannerService с add/list/get/done/delete/search/statistics. В нём координация действия, а не `input`, печать или открытие файла |
| `app/storage.py` | MemoryStorage и JsonStorage с единым договором `load() -> list[Task]`, `save(tasks)`. Тип хранения выбирается при сборке |
| `app/cli.py` | Чтение и разбор команды, вызов сервиса, форматирование и понятные сообщения. Нет своего долговременного списка задач или второго CRUD |
| `app/main.py` | Импортируемая `build_service(storage=None)` и точка запуска. Переданная зависимость применяется; default выбирает JsonStorage |
| Рабочие данные | Один `data/tasks.json`; путь задаётся в сборке и передаётся storage. Новый процесс читает сохранённое состояние |
| Ошибки | Неверные значения модели дают ValueError, неизвестный id предметной операции даёт TaskNotFoundError, ожидаемая проблема хранения даёт StorageError |
| Проверки | pytest для модели, сервиса, обоих storage и границы CLI; файловая интеграция через `tmp_path`, без изменения рабочего JSON |
| Передача | README, зависимости, команды запуска и тестов, контрольный сценарий, ограничения файла и проверенная версия в Git |

Сохранить названия подтверждённых функций, пока меняется только их место. Переход от функциональных операций к методам сервиса выполнять явно и обновлять всех потребителей. Не переименовывать всё приложение ради общего стиля.

| Итоговая операция сервиса | Вход, результат и важный эффект |
| --- | --- |
| `add_task(title, priority, tags=None)` | Создаёт и возвращает Task с назначенным id; после проверки сохраняет набор |
| `list_tasks()` | Возвращает текущие Task, пустой набор даёт []; чтение не сохраняет данные |
| `get_task(task_id)` | Возвращает Task либо поднимает TaskNotFoundError |
| `mark_done(task_id)` | Возвращает завершённую Task, сохраняет изменение; повтор не создаёт новую запись |
| `delete_task(task_id)` | Удаляет найденную запись, сохраняет набор, возвращает None; неизвестный id является ошибкой |
| `search_tasks(query)` | Возвращает совпадения без изменения данных; пустой очищенный фрагмент даёт [] |
| `get_statistics()` | Возвращает `all/open/done`, где all = open + done. Знакомый процент вычисляется по этой сводке |

Это целевой договор, не описание уже готовых методов ученика. Старые `find_task -> None`, `mark_task_done -> bool` и `total/completed/left` преобразуются в блоке 8; сообщения CLI и смысл пользовательских действий сохраняются.

Title очищается по краям и сохраняет пользовательский регистр; priority находится в диапазоне 1–5; id положительный, уникальный в текущем наборе; новая задача имеет `is_done=False`. Поиск сравнивает названия без учёта регистра. Для пустого набора следующий id равен 1, иначе максимум текущих id + 1. Удаление не перенумеровывает соседей; это правило не обещает пожизненную уникальность удалённых id.

Tags остаются внутренними метками модели и JSON. Их независимость и назначение нужно объяснить до задания. Новую систему команд тегов не добавлять. Старые четырёхпольные записи читать по явному правилу совместимости; отсутствующие обязательные поля не восстанавливать произвольными defaults.

HTTP, FastAPI, Uvicorn, Pydantic, схемы запросов, маршруты и HTTP-тесты принадлежат третьей главе. Полное и частичное обновление задач могут расширить сервис там; второй главе достаточно перечисленных исходных операций. Ограничения HTTP-входа, включая длину title, не вводить здесь под видом уже действующих правил модели.

## 3. Содержание, границы и изменения текущих материалов

### Принцип проектного движения

**Изучили механизм → переработали конкретную часть Planner → проверили прежние возможности.** Для обычного проектного занятия назвать прежний компонент, новое понимание, конкретное изменение, накопленный результат и регрессию. Допустимо существенно переписать слой с объяснённой причиной; уже хорошо построенную функцию повторно реализовывать не нужно.

В блоке 7 отдельный проектный результат может быть подготовленной и проверенной моделью в настоящем пакете. Это намеренный этап перед миграцией блока 8. Не обещать, что CLI уже использует эту модель. Подготовка не означает создание второго законченного Planner: прежние правила переиспользуются, новые классы не получают отдельный цикл меню или собственную базу.

Каждому новому механизму дать содержательную теорию для первого знакомства: какую проблему решает, как работает по шагам, что меняет в данных, где ошибаются, как увидеть результат. Сначала исследование понятия, затем ограниченное самостоятельное применение. Концепт блока задаёт этот порядок, а автор урока раскрывает объяснение. Готовую реализацию практики не подменять теорией.

Упражнения в интерпретаторе полезны для вызовов, ссылок, областей видимости, обёрток и объектов. Они имеют конкретный вопрос и наблюдаемый результат. Временный учебный пример не объявлять новой функцией продукта. После исследования применять механизм к прежнему проекту там, где это оправдано.

В блоке 6 собственное исключение требует узкого объяснения `class MyError(Exception): pass`: наследуемый тип позволяет различить ошибку. До упражнения объяснить этот механизм и создание исключения. Это не полноценный урок собственной объектной модели и не основание считать известными self, поля и методы.

В блоке 7 обязательно развести обычный класс и dataclass. Аннотации не проверяют вход автоматически; @dataclass не создаёт инварианты и не защищает любые прямые присваивания. В основном варианте правила обеспечивают конструктор и методы изменения; property использовать для вычисляемого представления. Полные setters разобрать как альтернативу, не обещать их автоматическое сохранение после dataclass.

Наследование объяснить как ограниченный контраст композиции и уже встречавшийся механизм исключений. Нужны смысл «является» и «использует», совместимость поведения и причина выбора для Planner. Иерархии задач, множественное наследование, ABC/Protocol, DI-фреймворк и архитектура на вырост не входят в цель.

Прежние алгоритмы переносятся, а не изобретаются заново. Наследование не является условием замены storage. MemoryStorage может копировать контейнер, сохраняя общие ссылки на Task: проверять и объяснять этот договор, не обещать независимость каждого объекта. Изменение после успешной валидации и отсутствие save при неверном входе не равны откату любого сбоя записи.

Сервис не нуждается в новом синтаксисе генераторов/next только ради короткой записи. Известные циклы подходят. Диспетчер не требует argparse или framework; проверяемость достигается уже знакомой передачей функций и отделением одного действия от бесконечного общения.

## 5. Приёмка результата и переход к третьей главе

### Приёмка проекта

1. В той же истории Git виден путь: Console Planner → структурированный CLI → пакет → JSON → подготовленная модель → миграция → service/storage → тесты. Не появился второй продукт с копией пользовательских операций.
2. Обычный запуск использует JsonStorage. Две задачи создаются через CLI; поиск, завершение, удаление и статистика работают; новый процесс восстанавливает оставшееся состояние с id/title/priority/is_done/tags.
3. Чтение и поиск не изменяют данные; пользовательский регистр title и известный процент сохраняются. Неизвестный id имеет понятный отказ; повтор done не удваивает счётчики.
4. Неверные значения не принимаются в модель и не сохраняются. На учебном пути повреждённый JSON/неверная схема дают StorageError и не становятся новым пустым состоянием. Ограничение сбоя записи описано честно.
5. Один сервис выполняет одинаковые операции с MemoryStorage и JsonStorage. CLI не содержит второй долговременной базы, JSON-IO или собственного алгоритма назначения id.
6. Ученик объясняет класс/экземпляр, __init__/self, поля класса/объекта, метод и изменение состояния, назначение dataclass и пределы валидации. Он может обосновать, почему словарь остаётся на внешней границе.
7. Независимость tags подтверждена для двух задач и на границе сериализации; старые полные записи совместимы по известному правилу.
8. Тесты модели и предметных операций, файловой интеграции и одной CLI-команды повторяемы и независимы. Временные файлы не являются вторым ученическим проектом.
9. Импорт app.main и вызов build_service не начинают меню и не пишут рабочий файл. Переданная зависимость действительно используется, включая пустое MemoryStorage.
10. Проверочный clone запускается по README; зависимости, данные и ограничения описаны. Версия относится к проверенному коду; Release не называется production deployment.
