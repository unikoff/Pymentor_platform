## 1. Контекст до главы: исходная точка A

### Кто приходит на курс

Ученик впервые видит программирование. Предполагаем только способность открыть платформу, читать понятный текст и редактировать его. Не предполагаем знания терминала, расширений файлов, Git, установки Python, функций, переменных или математического смысла программных операторов.

На входе нет проекта, исходного кода ученика и истории Git. Python сначала выполняется в подготовленной среде платформы. Назначение редактора, кнопки запуска, области вывода и проверки нужно объяснить до первого задания.

Ученик должен получать на платформе объяснение всех предпосылок практики. Помощь преподавателя может поддерживать обучение, но не должна быть обязательным способом узнать, что значит команда или почему код не работает.

### Почему прежний путь перестраивается

В прежнем первом блоке после первых `print` быстро появляются локальный файл, окружение, публикация и Git. Эти действия одновременно требуют новых понятий языка, файловой системы, инструментов и истории. Далее один шаг объединяет много механизмов: переменные и несколько типов; арифметика и ввод; длина, индексы, методы и форматирование; логика и короткое вычисление.

Новый путь сначала даёт ученику устойчивое понимание Python на небольших программах. Установка и Git появляются после того, как знакомый код уже можно читать и проверять. Проект начинается один раз, когда нужная языковая опора сформирована, и развивается в том же репозитории.

Замедление достигается размером самостоятельного шага и повторным применением, а не только более длинным текстом. После знакомства с механизмом нужны наблюдение, небольшое изменение и перенос на другой случай. Затем механизм снова используется через несколько занятий с меньшей помощью.

## 2. Цель главы и неизменный итог B

### Знания и самостоятельные действия

К завершению главы ученик способен:

1. Прочитать небольшой Python-код и проследить значения, выбранные ветви, повторения и вызовы функций.
2. Выбрать базовый тип и коллекцию, объяснить ссылку на изменяемый объект и отличие изменения объекта от переприсваивания имени.
3. Выделить функцию по понятной ответственности, передать данные через параметры, вернуть результат и отличить это от вывода человеку.
4. Найти простую причину ошибки, воспроизвести её, исправить и повторно проверить прежний сценарий.
5. Запустить свой локальный файл выбранным Python; отличить исходный код, команды терминала, интерпретатор и редактор.
6. Сохранить осмысленную проверенную версию через status/diff/staging/commit, отправить её на GitHub и получить проект заново через clone.
7. Самостоятельно пользоваться готовым Planner, объяснить путь ввода к результату и изменить знакомую часть с проверкой сохранённых возможностей.

Эти навыки формируются постепенно. Наличие команды в листинге или успешное копирование инструкции не подтверждает самостоятельного понимания.

### Договор итогового проекта по точному коммиту

Продукт называется StudyHub Planner. Это консольная программа без сторонних Python-пакетов. Основная реализация находится в одном `main.py`; функции определены до прямого вызова `run()` в конце. Данные живут только в памяти текущего запуска.

| Часть B | Фиксированное состояние и поведение |
| --- | --- |
| Модель задачи | Новый словарь с `id`, `title`, `priority`, `is_done`. Id положительный целый, title непустой после очистки краёв, priority целый 1–5, новая задача имеет `is_done=False` |
| Общие данные | Один список `tasks` создаётся внутри `run()` до цикла. Функции получают его явно; он сохраняет изменения между командами одного запуска |
| Команды | Ровно `add`, `list`, `find`, `done`, `search`, `stats`, `exit`. Команда очищается через `strip().lower()`. Неизвестная команда выводит сообщение и возвращает к меню |
| Добавление | Id равен максимуму текущих id плюс один, для пустого списка 1. Подготовленные значения передаются фабрике; одна новая запись добавляется в общий список |
| Название и приоритет | Запрос названия повторяется до непустой очищенной строки. Числовой ввод преобразуется через `int`; неправильный текст даёт сообщение и повтор вопроса, неподходящий диапазон тоже отклоняется |
| Поиск id | Положительный целый id ищется среди записей. Возвращается исходный словарь или `None`; отсутствие проверяется до обращения к полям |
| Завершение | Меняется только `is_done` найденной задачи. Функция сообщает успех/отсутствие через bool. Повторное завершение найденной задачи допустимо |
| Поиск названия | Очищенный фрагмент ищется без учёта регистра через `lower` и подстроку `in`. Возвращаются все совпадения в исходном порядке. Пустой фрагмент даёт пустой список; интерфейс отдельно сообщает о пустом запросе |
| Статистика | `total`, `completed`, `left`, где `total = completed + left`. Процент вычисляется отдельно, округляется до одного знака; для пустого набора равен `0.0` |
| Карточка | Строка вида `[id] title | приоритет: priority | состояние`; состояние словами `выполнена` или `не завершена`. Регистр человеческого названия сохраняется |
| Пустые случаи | List сообщает о пустом списке; неизвестный корректный id не ломает программу; поиск без совпадений даёт понятный результат; пустая статистика не делит на ноль |
| Выход | `exit` действует в меню. Выход не сохраняет задачи; после нового запуска список пуст. Отмена любого вложенного запроса не входит в договор |
| Передача | README описывает реальные возможности, Python 3.12, запуск, команды, контрольный сценарий и ограничения. `.gitignore` исключает локальное окружение и Python-артефакты |

Непустой title и допустимые числовые значения проверяются в функциях пользовательского ввода. В целевом коде `create_task` и `add_task` получают подготовленные аргументы; не приписывать им самостоятельную универсальную валидацию произвольных вызовов.

### Как сохраняется точка B

- «20» в названии коммита означает историческую версию. Новая глава не обязана состоять из двадцати занятий или заканчиваться новым занятием 20.
- Совпадение требуется по данным, компонентам, ответственности, поведению, способу запуска и ограничениям. История ученика и текст промежуточных коммитов могут отличаться.
- Сохраняем один main.py и простые функции. Классы, dataclass, пакеты архитектуры, JSON/CSV, БД, API и новые команды относятся к дальнейшему развитию.
- Не оставляем в финале активный calc, второе меню, новые поля задачи, демонстрационные задачи при старте и прототипы вместо готовых возможностей.
- Примеры и улучшения учебного пути не превращаются в расширение продукта. Тема может быть важной для понимания Python, но не обязана добавить ещё одну команду Planner.

## 3. Необходимое содержание, темп и изменения материалов

### Принцип освоения

Новый механизм изучается через понятную потребность, назначение, пошаговую работу и небольшое наблюдение. Практика затем проверяет его на самостоятельном действии. Не считать объяснением один термин, синтаксическую таблицу или готовую реализацию задания.

Уменьшаем помощь постепенно: готовый короткий пример → изменение одной части → исправление понятной причины → самостоятельное решение похожего случая → использование в накопленном результате. Прогноз вывода, трасса значений и объяснение ошибки дополняют выполнение кода.

Повторные применения распределяются по маршруту. Например, привязка имени возвращается в строковых методах и изменяемых списках; None возвращается в результате функции и поиске; булево условие возвращается в ветви, цикле и проверке ввода. При каждом возврате появляется новая роль знакомого механизма.

Каждому существенному различию нужно учебное пространство: имя/объект, длина/индекс, чтение/изменение, print/return, текст/число, ошибка преобразования/недопустимый диапазон, сохранение файла/коммит/push. Разбивку на занятия определяем по этому пространству, а не по старому числу тем.

Если позднее платформа получит подготовленный ввод, его можно использовать после отдельного объяснения, сохраняя A/B; нынешнюю интерактивную возможность нельзя предполагать существующей.

Пример с четырьмя полями до проекта может исследовать словарь, но не объявляется готовой моделью/функцией приложения. Самостоятельный интерфейс появляется только после подготовки вызовов и управления.

### Что изменить в прежнем маршруте

| Текущее решение | Решение новой главы и причина |
| --- | --- |
| Установка и публикация сразу после первых print | Перенести в блок 3. Ученик сначала понимает язык и может отличить проблему кода от проблемы инструментов |
| Git выполняется сначала по большой инструкции, затем объясняется | Перед каждым действием дать нужную модель состояния. Первый минимальный commit/push объяснить на маленьком известном файле, дальше углубить стадии |

### Блок 1. Устойчивое понимание базовых значений

**A1:** нет опыта кода. **B1:** ученик запускает и объясняет небольшой последовательный скрипт с базовыми типами, текстом, вычислениями и булевыми проверками.

Необходимые смысловые шаги:

1. Первый print и понимание редактора/запуска/результата. Затем отдельное закрепление порядка нескольких инструкций и простого исправления.
2. Имя и значение, присваивание до чтения. Затем переприсваивание, диагностика типа и правильная модель привязки на неизменяемых объектах.
3. Строка и её операции. Затем позиция/фрагмент и методы, которые дают новый результат. Не обещать, что метод обязательно меняет исходное значение.
4. Целочисленные выражения, смысл видов деления, дробные значения и округление. Затем явное преобразование подходящего текста и понятное сообщение через f-строку.
5. Булевы ответы, сравнения и границы. Затем составные правила и объяснённая цепочка сравнений. None как отсутствие, отличное от нуля/False/пустого текста.
6. Самостоятельный небольшой скрипт на новом случае с возвращением к прежним механизмам. Никаких ветвлений или функций ради оформления этой проверки.

Метод объясняется простым действием, связанным со значением, через точку и скобки. Не начинать ООП ради upper/strip. Для чисел нужны операции и полезные готовые функции; int/float/round/abs не называть методами. Числовой метод показывать только там, где его результат уже понятен и полезен конкретному наблюдению.

**Наблюдаемые результаты:** свой вывод; трасса имён; обработанная строка с сохранённым исходником; вычисление на новых данных; объяснимые граничные bool; проверка отсутствия. Привязка, копия и scope получают хуки, а не требования полноценно разобраться в памяти и областях видимости.

Подробный [BLOCK_1.md](BLOCK_1.md) раскрывает этот маршрут в 16 занятиях. Преобразования и оформление сообщения разделены; None изучается до самостоятельного итогового скрипта. Это распределение сохраняет A1/B1 и границы блока, не фиксируя общую длину главы.

### Блок 2. Управляемая программа и наборы данных

**A2:** ровно B1. **B2:** ученик на платформе может самостоятельно написать небольшой скрипт с выбором, изменением коллекции, поиском/накоплением и конечным повторением.

Последовательность внутри блока:

1. **Выбор пути.** Сначала if/else, условие bool, отступ и только выбранная ветвь. Затем elif, порядок проверок, пересекающиеся условия и разумная вложенность. Практика требует не переписать синтаксис, а выбрать верный результат на границах и объяснить, какая ветвь выполняется.
2. **Условия с текстом и пустотой.** До их применения объяснить in для подстроки и нужную глубину truthiness. Показать, что непустая строка `"False"` не является bool False. Не подменять сравнение диапазона неявной истинностью числа.
3. **Список.** Назначение нескольких значений, порядок, индекс, чтение/изменение, len/in, добавление/удаление. Выбрать нужные append/extend/insert/pop/remove с объяснением результата и эффекта; None от некоторых методов использовать как знакомую опору. Затем два имени общего списка и независимая простая копия. Не смешивать поверхностную копию со всеобщей независимостью вложенных данных.
4. **Tuple и set.** Tuple как упорядоченная неизменяемая структура, пара и простая распаковка; set как уникальные элементы и проверка принадлежности, без позиции и обещанного порядка вывода. Объяснить add/remove/discard и основные объединение/пересечение/разность на наблюдении, а не каталоге методов. Полезные split/join теперь могут опираться на список.
5. **Словарь.** Ключ и значение, чтение/запись, добавление/удаление, отсутствие ключа и get, keys/values/items. Затем список словарей, изменение одной записи и граница поверхностной копии. Не вводить ещё фабрику через def или окончательный интерфейс Task.
6. **For.** Текущий элемент уже знакомой последовательности, строка/список/словарь, range и невключённая правая граница. Затем счётчик, накопитель, поиск/ранняя остановка и максимум. Break/continue объяснить по пути выполнения. Items и распаковка опираются на уже объяснённую пару, а не появляются неожиданно.
7. **While.** Условие проверяется перед проходом, тело меняет состояние, есть достижимый выход. Сначала конечный счётчик, затем повтор до нужного состояния и while True с объяснённым break. Бесконечный дефект не запускать как обязательную задачу, которая требует ждать таймаута.
8. **Связанное применение.** На заданных в редакторе данных выбрать/изменить запись, получить итог и объяснить повторение. Это учебный скрипт; не объявлять его новым репозиторием или уже готовым Planner.

Пункты задают зависимость, а не количество занятий. If/elif, изменение списка/копия, обход/накопление, конечный while/выход могут потребовать разных занятий. Простая новая модель должна получить самостоятельное применение до следующей крупной модели.

**Практика:** прогноз выбранной ветви, трасса коллекции до/после действия, сравнение похожих операций, исправление причины, поиск/накопление на новых исходных данных и самостоятельная сборка небольшого скрипта. Конкретные данные и доступные операции описаны; задачи выполняются на платформе.

**Передача B2 = A3:** ученик понимает общий список и вложенную запись, None как отсутствие, bool, цикл и изменение состояния. Он не умеет автоматически определять функции, возвращать результат, ловить исключения, работать с terminal/Git или читать локальный ввод. Эти предпосылки впервые формируются дальше.

### Блок 3. Функции, ошибки и один настоящий репозиторий

**A3:** ровно B2; есть понятный язык, но локального проекта нет. **B3:** собственный репозиторий StudyHub, локально запускаемый main.py с подготовленными реальными компонентами, понимание функций/ошибок/ввода и самостоятельного цикла Git.

#### Сначала смысл функций и ошибок

Короткая начальная часть ещё может работать на платформе. Из знакомой повторяющейся логики показать потребность в функции: определение, вызов, параметры/аргументы, отдельный запуск тела, результат и return. Print сообщает человеку, return передаёт результат вызывающему коду; это различие проверяется использованием результата в следующем вычислении. Неявный None объясняется до задания, где забытый return становится причиной ошибки.

Далее раскрыть локальное имя, аргумент и общий изменяемый объект. Одноимённые локальные/внешние переменные не являются автоматически одним состоянием; передача списка не создаёт копии. Параметры и явный результат предпочтительнее скрытой глобальной коллекции. Global/nonlocal, сложные сигнатуры, декораторы, рекурсия и изменяемые значения по умолчанию не нужны для этой B.

Разбор ошибок идёт с уже знакомых случаев к новой глубине: syntax error, ошибка выполнения и неверная логика без исключения; типичные NameError/TypeError/ValueError/IndexError/KeyError/ZeroDivisionError; traceback и строка своего кода; воспроизведение, минимальная причина, исправление и повтор прежнего сценария. Слова bug/fix/bugfix/debug/reproduce/regression объясняются по действию, а не отдельным словарём для заучивания.

Повтор слова «ошибки» в исходном описании не создаёт два одинаковых занятия. Первое знакомство формирует диагностику, последующее применение проверяет функции и реальный проект. Debugger VS Code изучается только после среды и запуска; он помогает увидеть значения и шаги, не заменяя их понимание.

#### Перенос знакомого языка на компьютер

Отдельные шаги установки объясняют роли Python, VS Code, расширения Python, файла .py, рабочей папки и терминала. Дать последовательность скачать → установить → проверить выбранный интерпретатор → открыть папку → сохранить/запустить файл. Команду PowerShell нельзя выдавать за Python-код; открытый редактор не доказывает запуск нужного файла.

До использования `.venv` объяснить локальное окружение и его роль, показав воспроизводимую команду выбранной версии Python. Сторонние библиотеки здесь не нужны. Ученик должен уметь различить неверный путь, несохранённый файл, другой интерпретатор и ошибку самой программы.

#### Git на одной истории StudyHub

Порядок должен позволять понять каждое действие до самостоятельного применения:

Нет активного меню calc, списка введённых пользователем задач и готовых add/find/done/search/stats. Исследовательский вывод/вызовы могут временно показывать компоненты; в блоке 4 их заменяет один рабочий запуск, функции сохраняются.

**Передача B3 = A4:** доступно ровно это состояние, без предположения, что готовые операции уже лежат в main.py. Ученик знает input/try-except/цикл/функции и Git; следовательно, способен строить интерфейс по шагам.

### Блок 4. Постепенная сборка первого Planner

**A4:** ровно B3. **B4 = B главы:** все компоненты и сценарии точного snapshot, без расширения продукта и без накопленного технического учебного мусора.

Сначала раскрыть продукт с точки зрения пользователя: зачем список задач, что значит задача/приоритет/состояние, какие команды появятся, как выглядит история одного запуска и почему данные пока исчезают после выхода. После этого показать план возможностей, а не готовый исходник.

| Проектный этап | Опора | Основное изменение | Наблюдаемый результат |
| --- | --- | --- | --- |
| 1. Каркас и состояние запуска | Функции, while, ввод, коллекции, существующие компоненты B3 | Создать run, общий tasks до цикла, show_menu и маршрутизацию к понятным временным действиям; реализовать минимальные list/exit | Меню повторяется, неизвестная команда понятна, выход достижим. Нереализованные действия явно обозначены заглушками, не сообщают ложный успех |
| 2. Подготовка ввода для добавления | Strip/int, try-except и повтор из блока 3 | Read_title и read_priority: повтор вопроса до допустимого значения | Непустой текст и priority 1–5; данные пока не меняются при отказе. Read_task_id вводится позже, перед find, а не третьим валидатором без потребности |
| 3. Добавление | Готовая фабрика, список/append, for/максимум | Get_next_id, add_task, handle_add в существующем меню | Реальные задачи накапливаются; id не является индексом; показ использует готовый formatter |
| 4. Полный вывод | Накопленные записи и formatter | Довести show_tasks до вывода всех текущих задач и пустого случая | Список показывает реальные записи и их состояние; чтение не меняет данные |
| 5. Поиск id | Список словарей, None, возвращаемый результат | Read_task_id, find_task, handle_find | Корректный id даёт запись или сообщение об отсутствии; неверный числовой ввод повторяет вопрос |
| 6. Завершение | Достигнутый find и изменение словаря | Mark_task_done, handle_done | Меняется только найденная задача; повторное done не увеличивает число выполненных второй раз |
| 7. Поиск названия | Подстрока, lower/strip, обход и новый список | Search_tasks, handle_search, повторное использование show_tasks | Все совпадения в исходном порядке, без мутации задач; пустой фрагмент и отсутствие совпадений объяснены |
| 8. Статистика | Счётчик/накопление, bool и дробные вычисления | Build_statistics, completion_percent и подключение stats | Счётчики согласованы после настоящих add/done, пустой набор безопасен; calculate_study_minutes не переименован в статистику |

Эти этапы не обязаны соответствовать одному занятию каждый. Ввод, назначение id, новый алгоритм и его подключение могут требовать нескольких самостоятельных шагов. При этом следующее занятие получает фактический результат предыдущего: find не применяется до его создания, done использует тот же поиск, статистика читает реальные накопленные задачи.

Не разрабатывать новый formatter/фабрику для каждой команды и не создавать постороннюю копию tasks для демонстрации возможности. Ошибочные/пустые случаи можно проверять на контролируемых данных того же приложения. Перед новым действием проверить уже работающие сценарии; проверка сопровождает развитие, а не заменяет его.

Теория раскрывает смысл конкретной ответственности и механизм, необходимый в текущем шаге: например, максимум существующих id, поиск с результатом None, передача исходного словаря, счётчики по состоянию. Уже освоенные def/if/for коротко актуализируются; заново писать весь учебник про них не нужно.

Git сопровождает значимые изменения: сделали возможность → проверили → посмотрели diff → commit → push. Продолжается один remote и история. README появляется как проверяемая инструкция к достигнутому продукту; он не обещает будущую БД и не меняет исходный договор.

## 5. Приёмка главы и переход к дальнейшему курсу

### Проверка стыков A → B

| Стык | Что передаём | Чего не предполагаем |

| B1 = A2 | Значения, строки/числа, bool/None, сравнения, логические выражения, самостоятельный script | Ветви, коллекции, циклы, def/return, input и инструменты |

В паспортах нужно различать согласованную целевую точку A и факт её достижения. Проверять навыки по выданной практике и журналу StudyHub, имена/код по состоянию перед нужным учебным шагом. Более поздний коммит подтверждает возможный результат, но не изученность ученика в раннем уроке.

### Что проверить у готового проекта

1. На пустом запуске list и stats дают правильные результаты, find/done неизвестного id не падают, exit завершает работу.
2. Add создаёт две самостоятельные записи с настоящими id, очищенными названиями и разными допустимыми приоритетами. Изменение исходного ввода меняет результат, а не выбирает заранее зашитую задачу.
3. Проверены пустое название, неправильный числовой текст, priority 0/1/5/6, id 0/отрицательный/положительный. До допустимого ввода нет частичного добавления; после ошибки задаётся нужный вопрос.
4. List показывает обе задачи. Find возвращает нужную; done меняет только её. Повтор done не создаёт запись и не приводит к лишнему завершённому счётчику.
5. Search на русском и латинском тексте соблюдает очистку и регистр, возвращает все совпадения по порядку; пустота и отсутствие совпадения не путаются. Исходные названия и записи не переписываются.
6. Stats для двух задач с одной выполненной даёт total 2, completed 1, left 1 и 50.0%; после изменений отражает текущее состояние, не отдельный накопленный счётчик событий.
7. Формат карточки совпадает по смыслу и виду с snapshot; форматирование возвращает строку и не изменяет запись.
8. Неизвестная команда возвращает к меню. После exit и нового запуска нет прежних задач; в коде не добавлены демонстрационные данные и файловое сохранение.
9. Все функции итоговой таблицы имеют нужную ответственность и имена. В частности, нет новой постоянной архитектуры, второго активного меню, delete/edit, тегов и альтернативного storage.
10. README позволяет из чистого checkout подготовить выбранный Python/окружение и запустить этот результат. Git не содержит .venv и локальных артефактов; опубликован нужный checkpoint, а не только несохранённые рабочие изменения.

Это ручная предметная приёмка с наблюдением поведения и проверкой компонентов. Pytest, автоматическая тестовая архитектура и новые зависимости не становятся скрытым требованием первой главы. Проверка готового финала не должна впервые создавать пропущенные функции.

### Продолжение после фиксированного финала

Следующая глава получает именно StudyHub `383c212b…` по договору, а не более зрелую новую модель. Он умеет работать с задачами, но хранит их только в памяти, имеет один файл и простые функции. Дальнейшие функции/ошибки/модули/хранение и ООП развивают этот результат в своём порядке.

Новый курс не переносит обязательную часть B в следующую главу. Необходимая потребность в будущем хранении возникает естественно после проверки исчезновения задач, но сама технология в эту B не добавляется.

Количество занятий не фиксируется старым диапазоном 1–20. Каждый блок получает столько шагов, сколько нужно для новой модели, её наблюдения и самостоятельного применения. Увеличение объёма оправдывается конкретным снятым скачком сложности; отдельный урок на каждый метод не обязателен.
