# Точечные правки: PR в блоке 3

> Заменяет предыдущий расширенный план. Изменить материалы только занятий **13.1 и 13.2** курса 01.2. Сейчас обновлены концепты и паспорта правок; сами уроки и практика ещё не изменены.

## Решение

PR достаточно один раз объяснить и показать в занятии 13.2 на реальном изменении normalize_title. Затем оставить одну памятку о дальнейшей работе:

| Формат обучения | Как публикуем код дальше |
| --- | --- |
| Самостоятельно, подписка без ментора | Проверяем код, commit и push прямо в main |
| С ментором | Работаем в develop, отправляем изменения через PR в main и передаём ссылку ментору для ревью |

Оба формата имеют одну Python-программу и одинаковую функциональную точку B. Ссылка на PR, наличие ментора, его ответ и merge не становятся общими условиями зачёта практики или открытия следующих уроков.

**Всего четыре небольших паспорта в двух занятиях.** Не переносить теорию staging в 13, не переписывать Python-задачи 13.2 и не добавлять PR в каждую практику. Обязательные первый/второй PR по блокам, merge в 15.1/20.1 и дополнительные команды синхронизации из прежнего плана отменены. Блок 4 возвращён к прежнему концепту.

## П1. Занятие 13.1: закрепить имя основной ветки

**Место:** [Markdown-план 13.1](../../../backend/learning/course_content/chapter_01/block_03/13.1%20-%20Отправляем%20код%20на%20GitHub.md), конец раздела «02. Проверяем origin и фактическую ветку», перед «03. Первый push и upstream»; [Lesson13_1.tsx](../../../frontend/src/lessons/chapter_01/block_03/Lesson13_1.tsx), между Section 02 и 03.

**A → B:** есть первый локальный commit и свой пустой remote → основная ветка учебного проекта называется main, опубликована и проверена. Develop и PR здесь ещё не нужны.

**Что сделать:** добавить один короткий абзац: «В дальнейшем основную ветку проекта будем называть main. Сначала проверим фактическое имя; если оно другое и собственная ветка ещё не опубликована, переименуем её». Объяснить условную команду `git branch -m main` и повторную проверку имени. Если main уже существует, не перезаписывать её. Основной пример первого push показать для main; общий смысл проверки реальной ветки, upstream, доступа и SHA сохранить.

**Смежное место:** в [manual.py](../../../backend/learning/course_content/chapter_01/block_03/manual.py), ключ "13.1", при необходимости уточнить пример основной ветки в существующем шаге публикации. Новое задание не добавлять.

**Приёмка:** ученик заканчивает обычную публикацию main и понимает, что произвольное имя ветки из общего примера не нужно копировать в свой проект.

**Размер:** один поясняющий абзац и согласование основного примера; объём и цель занятия сохраняются.

## П2. Занятие 13.2: выбрать режим до первой правки

**Место:** [Markdown-план 13.2](../../../backend/learning/course_content/chapter_01/block_03/13.2%20-%20Название%20задачи%20и%20Git.md), перед разделом «03. Рабочий файл и первый diff»; [Lesson13_2.tsx](../../../frontend/src/lessons/chapter_01/block_03/Lesson13_2.tsx), перед Section 03 «Рабочее изменение видно в diff».

**A → B:** исходный main.py опубликован в main → ученик знает, в какой ветке выполняет уже существующую работу по normalize_title.

**Что вставить:** короткую карточку с двумя вариантами. Самостоятельно — остаёмся в main. С ментором — из чистой опубликованной main один раз создаём рабочую ветку:

```text
git switch -c develop
git branch --show-current
```

До команды простыми словами объяснить: ветка — линия работы в том же репозитории; отдельная папка и второй проект не создаются. Если develop уже есть, используется `git switch develop`, а не повторное создание. Выбор делается до первой проектной правки, чтобы дальнейшие commits сразу попали в нужную ветку.

**Приёмка:** самостоятельный читатель может продолжить прежнее занятие в main; читатель с ментором делает то же изменение в develop. Никому не требуется повторно писать функцию или менять репозиторий.

**Размер:** одна карточка, короткое объяснение ветки и два варианта команды. Новые практические задания не нужны.

## П3. Занятие 13.2: один блок о PR с полной инструкцией

**Место:** в том же Markdown — после раздела «05. Безопасно снять подготовку и сохранить нужную версию», перед «06. Что мы будем делать в практике»; в Lesson13_2.tsx — после Section 05, перед Section 06.

**Оформление:** отдельная вставка «PR и проверка кода», при необходимости Section с номером 05.1. Существующие разделы 01–05, их объяснения diff/staging и обзор практики сохраняются.

**A → B:** знакомы commit/push, выбор ветки и проверяемое изменение normalize_title → ученик понимает PR; с ментором прямо в ходе занятия создаёт реальную заявку, самостоятельно продолжает прямую публикацию main. Инструкция не откладывается на новое домашнее задание.

**Содержание вставки, по порядку:**

1. Кратко объяснить PR: предложение внести изменения из одной ветки в другую, чтобы до слияния можно было увидеть diff, обсудить код и получить ревью. Push публикует commits, PR показывает предложение; открытие заявки само не изменяет main. PR и команда git pull — разные вещи.
2. Взять тот же проверенный commit с normalize_title из текущего занятия. Если он ещё не создан, завершить обычный показанный путь save → проверка → stage → commit, не создавать дополнительный файл или фиктивную правку ради PR.
3. Для менторского варианта выполнить первый `git push -u origin develop`; пояснить, что -u сохраняет связь develop с её веткой на origin. Для самостоятельного варианта остаётся обычный `git push` в уже настроенную main.
4. Открыть свой репозиторий на GitHub: Pull requests → New pull request. Если доступен Compare & pull request, это альтернативный вход.
5. Выбрать **base: main**, **compare: develop**. Прочитать направление: предлагаем изменения из develop в main. До создания посмотреть ожидаемые commits и строки diff; если различий нет, проверить наличие и публикацию нового commit, а не придумывать лишний файл.
6. Заполнить понятный заголовок и короткое описание: что изменилось и как проверили. Нажать Create pull request. На открытой странице проверить Open, направление и Files changed.
7. Скопировать именно URL вида `https://github.com/OWNER/REPO/pull/NUMBER` и передать ментору через договорённый канал. Для приватного репозитория у ментора должен быть доступ; это правило только менторского формата, не причина требовать аккаунт ментора у каждого подписчика.
8. Один раз объяснить дальнейшую работу: исправления и новые commits в develop обновляют тот же открытый PR после push. После Merged для следующей проверки открывается новый PR. Слияние и необходимое согласование веток сопровождает ментор; эти операции не становятся новой обязательной темой остальных занятий.
9. Закончить памяткой: «С ментором следующие изменения отправляем на проверку через develop и PR. Если занимаетесь самостоятельно, проверяйте код и отправляйте commits сразу в main. Ожидать ревью для продолжения курса не нужно».

**Минимальная проверка понимания внутри текста:** один вопрос «Изменится ли main сразу после push в develop?» с пояснением. Достаточно одного такого интерактива; отдельный набор PR-заданий не нужен.

**Приёмка:** в менторском проходе создан настоящий PR на существующее изменение и передана ссылка. Самостоятельный проход не содержит требования создать PR, назначить ревьюера или дождаться ответа. Приёмка Python-практики в обоих случаях остаётся прежней.

**Размер:** ориентир 500–800 слов новой прозы плюс команды и веб-шаги. Обновлённый паспорт 13.2 задаёт 2200–3000 слов для всего занятия. Не раздувать блок историей Git Flow, fork, настройкой защиты main, squash/rebase, отдельной лекцией о merge или новыми сроками ревью.

## П4. Практика 13.2: одна оговорка о первом push

**Точное место:** [manual.py блока 3](../../../backend/learning/course_content/chapter_01/block_03/manual.py), `MANUAL_PRACTICE["13.2"]`, последнее задание **«Снять staging без потери текста и опубликовать итог»**, его `hint` и пояснение к финальному `git push` в `answer`.

**Проблема:** текущая подсказка рассчитывает на уже настроенную удалённую ветку. Для main это верно, для впервые созданной develop upstream ещё может отсутствовать.

**Правка:** добавить одно пояснение перед финальной отправкой: «Используйте выбранный в теории режим: для настроенной main — git push; для первого push develop — git push -u origin develop. После сохранения этой связи достаточно git push». У первого develop-push отсылка ведёт к готовой инструкции П3. Пример команды должен быть подписан по режиму, а не предлагать выполнить обе отправки подряд.

**Приёмка:** первый push новой develop не упирается в неизвестный upstream; само задание, staged diff, требования к функции, ответы по Python и автоматические задачи сохраняются. PR-ссылка и одобрение ментора не добавляются в requirements/checks/result практики.

**Размер:** одно пояснение к существующему шагу. В остальных практиках такой текст не повторять.

## Что остаётся за рамками этих правок

Занятия 12.1–13, 14–15.1 и весь блок 4 не требуют переработки ради PR. Занятие 15.1 уже умеет проверять фактическую опубликованную ветку с нужным checkpoint: main при самостоятельной работе, develop в менторском формате, если изменения ещё не слиты. Требовать merge или ожидание ментора для его прохождения не нужно.

Реестры, track ID, номера уроков, импорты, прогресс, формы сдачи, code_tasks.py и исходники StudyHub не меняются. Дополнительные напоминания о PR в каждом уроке или обязанности открывать заявку после каждой задачи не вводятся.
