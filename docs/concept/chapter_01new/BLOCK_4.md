## 3. Паспорта занятий

### 16. Запускаем каркас Planner

**Основная тема и назначение.** Сохранить отдельный урок перехода от демо компонентов к одному пользовательскому циклу.

**Точка A.** B3: один main.py с четырьмя функциями, средой/историей и навыками input/try/while; run/задач/menu нет.

**Точка B.** Run владеет одним tasks до цикла; show_menu/minimal show_tasks дают list пустоты и exit, будущие действия честно обозначены.

**Проверка предпосылок.** Опора: B3 (15.1), функции/while/input (11–11.1, 10.1, 15). Новое: run/общий список/маршрутизация; остальные операции честно временные.

**Предпочтительный объём теории.** **1800–2400 слов** учитываемого текста. Новый пользовательский цикл и время жизни общего состояния; маршрутизация и границы временных ветвей.

**Необходимые темы в порядке изучения.**

1. Цель Planner: add/list/find/done/search/stats/exit, одна история пользователя и память текущего процесса.
2. Run координирует; tasks до while, не внутри каждой итерации и не global.
3. Команда strip().lower(), допустимое имя, знакомые if/elif; неизвестная даёт сообщение/continue.
4. Exit в меню даёт break; show_menu печатает. Минимальная show_tasks различает пустой список и ещё не подключённый полный вывод: при непустом входе честно сообщает о временном ограничении, не называет реальные задачи пустотой. После добавления её расширит урок 17.1.
5. Заменить только демо-участок, сохранить четыре функции и один прямой run() в конце; никаких вызовов несуществующих handlers.

**Порядок частей без скачка сложности.**

1. Краткая история пользователя и замена демо минимальным run/list/exit.
2. Показать tasks до цикла и несколько повторений без новых операций.
3. Затем обработка неизвестной/нормализованной команды и честные временные ветви.

**Основная практика.** Основной локальный StudyHub; инструменты/исследования работают в той же истории, не создают второй продукт.

1. Создать каркас в прежнем файле, проверить неизвестную/list/exit и нормализацию команды.
2. Остальные будущие действия пометить временными сообщениями без ложного успеха.
3. Проследить жизнь списка и проверить сохранённые компоненты. До использования -i объяснить выполнение run, штатный exit и появление >>>.

Подготовка: до выполнения каждой части разобрать соответствующую тему выше; опора перечислена в A. Пример объяснения и самостоятельные данные различаются. Не требовать ещё не названные конструкции.

**Выход и переход.** Маленький самостоятельный шаг: Пройти list/неизвестную команду/exit и показать, где список создаётся один раз. Следующая тема: «Проверяем ввод задачи». Проверить прежние рабочие компоненты; значимое изменение сохранить через status/diff → commit → push после объяснения нужного действия.

### 17. Добавляем первую задачу

**Основная тема и назначение.** Объединить три прежних занятия в одну возможность, внутри последовательно проверить helper, эффект и интерфейс.

**Точка A.** Readers/factory/formatter готовы, меню add временная; list пока минимальная.

**Точка B.** Get_next_id/add_task/handle_add подключены, пользовательские записи накапливаются в одном tasks без частичного добавления.

**Проверка предпосылок.** Опора: максимум/list/фабрика/readers (9.1, 6.1–8.1, 14, 16.1). Новое: правило id/одно добавление/handler; полный list ещё не обещается.

**Предпочтительный объём теории.** **2100–2700 слов** учитываемого текста. Id/операция/handler связаны впервые в работающую возможность; алгоритм и эффект проверяются до подключения.

**Необходимые темы в порядке изучения.**

1. Id отличается от индекса/len; максимум положительных id со стартом 0, пустота → 1, иначе max+1.
2. Add_task получает подготовленные title/priority: helper → factory → один append → return той же записи.
3. Return append даёт None, локальная замена tasks не меняет общий список; copy не нужна.
4. Handle_add сначала получает оба допустимых аргумента, только потом меняет tasks и печатает formatter.
5. Run передаёт свой список; операция не читает/не печатает и не добавляет универсальную проверку произвольных вызовов.

**Порядок частей без скачка сложности.**

1. Один helper id: проследить максимум и пустоту на контролируемых аргументах.
2. Затем add_task: один вызов, один append, возвращённая запись.
3. После проверки операции подключить handler и настоящие два add; не просить писать сразу три функции из памяти.

**Основная практика.** Основной локальный StudyHub; инструменты/исследования работают в той же истории, не создают второй продукт.

1. Реализовать get_next_id, коротко проверить [] и несмежные/неупорядоченные id через реальные factory-записи.

Подготовка: до выполнения каждой части разобрать соответствующую тему выше; опора перечислена в A. Пример объяснения и самостоятельные данные различаются. Не требовать ещё не названные конструкции.

**Выход и переход.** Маленький самостоятельный шаг: Добавить две реальные задачи одним запуском и объяснить назначение разных id/момент append. Следующая тема: «Показываем список задач». ### 17.1. Показываем список задач

**Основная тема и назначение.** Сохранить отдельную завершённую возможность чтения реального состояния.

**Точка A.** Add работает, show_tasks минимальная, formatter готов.

**Точка B.** Та же show_tasks выводит все записи по порядку или пустое сообщение без изменения данных.

**Проверка предпосылок.** Опора: for/formatter/реальный add (9, 14, 17). Новое: расширенный show_tasks; done ещё не считается реализованной возможностью.

**Предпочтительный объём теории.** **1000–1500 слов** учитываемого текста. Узкое развитие показа на известных for/formatter; объяснить пустой случай и границу чтения вместо повторного учебника циклов.

**Необходимые темы в порядке изучения.**

1. Пустота нормальна, ранний return после сообщения.
2. Прямой for получает словарь; format_task возвращает, show_tasks печатает.
3. Id берётся из записи, не enumerate/позиции; чтение не append и не сортировка.
4. Расширить существующее определение, не добавить дубль с тем же именем.

### Как подавать материал новичку

Следовать [правилам темпа общей главы](COURSE.md#как-провести-новичка-через-каждый-шаг): объяснение → рабочий пример → маленькое изменение → самостоятельный шаг. Проверка готовности в каждом паспорте — ориентир для локальной помощи, не экзамен на скорость. Дополнительные детали не требуются следующей практикой молча.

### Правила последующего авторства

1. A следующего занятия — накопленный выход предыдущего, а не будущий исходник целиком. Концепт задаёт план, но не доказывает внедрение/освоение.
2. Сохранить теорию назначения и механизма, типичные ошибки, прогноз/трассу/исправление/самостоятельное действие. Сокращены уроки и дубли, не объяснения новичку.
3. Основная практика проверяет только объяснённое. Не превращать каждый короткий эксперимент или проверку прежней функции в отдельное занятие.
4. Модельные операции, ввод и вывод имеют названные роли. Не добавлять новый продукт/схему/технологию ради объединения.
5. Продолжается один repo/main.py. Краткие контрольные аргументы проверяют настоящую функцию, не заменяют основной tasks. Секреты и локальные служебные файлы не публикуются, destructive Git-команды не нужны.
6. При локальной проверке объяснить `-i`, выход из run и `>>>` до использования; локальный tasks не становится доступным снаружи сам. Наблюдать его debugger или проверять функции краткими явно заданными аргументами, без return tasks/globals ради проверки.
7. При внедрении согласовать стабильные идентификаторы, порядок, frontend, каталоги практики, ссылки и сохранение прогресса. Таблица прежних номеров служит миграции концептов, не командой перезаписать пользовательский прогресс.
