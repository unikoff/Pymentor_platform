# C2.2.4 — устранение Redis I/O под блокировкой сессий

## Дополнение PYM-435 · 06.11.2026

Реализован и локально проверяется вариант идемпотентного входа для изолированного PostgreSQL/Redis: клиент использует один идентификатор операции для ограниченного числа повторов и сохраняет его с хешем email в `sessionStorage` до получения результата; пароль и токен сессии туда не записываются. Если `sessionStorage` недоступен, новый режим отказывает до отправки данных входа, поскольку безопасно восстановить неизвестный результат после перезагрузки нельзя. Старый SQLite-режим использует прежний вход без автоматического повтора.

Для нового пути пароль проверяется и при повторе; token выводится с HMAC из отдельного секретного ключа, идентификатора операции и случайного идентификатора поколения аккаунта. SQL фиксирует результат операции вместе с созданием и вытеснением сессии. Redis без действующей SQL-сессии не авторизует; восстановление ключа Redis допускается только для подтверждённой операции. На локальном тестовом API обязателен `PYMENTOR_TEST_LOGIN_RECOVERY_KEY` — 32 случайных байта в hex, одинаковых для процессов на время повторов; это тестовая настройка, не инструкция для production. Секрет нельзя помещать в frontend, исходники или Jira.

Проверены синтетические повторы, потеря подтверждения SQL commit, отказ Redis до фиксации, параллельные повторы, принудительный отзыв, logout и повторное использование числового ID аккаунта. Проверены тестовым HTTP-клиентом оба режима; живой браузерный E2E и production не проверялись. После удаления и пересоздания аккаунта новый токен отличается от старого. Это не доказывает защиту при восстановлении старой резервной копии: независимый журнал и политика его хранения остаются в PYM-426.

**PYM-435: локальная приёмка завершена 06.11.2026.** На одноразовой PostgreSQL/Redis и синтетической SQLite прошли 33 проверки нового входа и двух режимов, включая параллельные запросы через два процесса и фактически отброшенный прокси HTTP-ответ. Отдельно прошли 10 проверок клиента и 24 проверки старого SQLite API. Сбой до SQL commit и потеря его подтверждения моделировались в тесте; это не испытание отказа реального VPS. Старые лабораторные `xfail` относятся к прежнему входу без идентификатора операции и не являются доказательством работы нового пути.

Граница с PYM-426: UUID поколения уже исключает повторное использование старого токена новым аккаунтом, а отдельный ключ Redis без SQL-сессии не даёт доступ. Удаление оставшихся Redis-ключей, персональных данных, аналитики и защита восстановления из backup относятся к PYM-426 и не считаются реализованными этой задачей. Маркеры операций входа сохраняются до удаления аккаунта: это предотвращает ошибочное повторное создание старой операции, но приводит к накоплению записей; безопасная политика ограниченного хранения пока не реализована. Эти ограничения не означают готовность Core 2.0 к релизу или переходу на VPS.

Принципы: [AWS — безопасные повторы идемпотентных запросов](https://aws.amazon.com/builders-library/making-retries-safe-with-idempotent-APIs/) и [OWASP — управление сессиями](https://cheatsheetseries.owasp.org/cheatsheets/Session_Management_Cheat_Sheet/). Применимость к конкретной реализации подтверждается только тестами проекта.

Ниже сохранено исходное исследование прежнего варианта входа без идентификатора операции; актуальное состояние нового варианта описано выше. `reconcile` и synthetic importer обращаются к Redis вне write-блокировки. Результаты замеров [PYM-188](https://platformpy.atlassian.net/browse/PYM-188) находятся в `c2-2-4-measurements.md`. Новый режим пока не считается готовым к релизу.

## Обязательное поведение

- Legacy SQLite и её сессии не меняются. Изменение сначала предназначено для изолированного PostgreSQL/Redis режима.
- SQL остаётся обязательным источником проверки: ключ Redis без действительной SQL-сессии не разрешает доступ. Одновременно активно не более трёх SQL-сессий пользователя.
- Решение владельца: если четвёртый вход не удался из-за недоступного Redis, три прежних действующих сеанса сохраняются.
- Redis I/O не выполняется при удержании SQL write lock; ожидание и отмена ограничены по времени. При отказе Redis или SQL доступ не выдаётся на основании одного источника.

Сейчас в экспериментальном login создан отдельный Redis namespace подготовленных ключей, который старый полный `replace` не удаляет. Аутентификация проверяет оба namespace и затем SQL; logout после SQL commit адресно отзывает оба ключа. При сбое до SQL-активации ключ может остаться до истечения TTL, но сам по себе доступа не даёт. Это изменение внутреннего контракта проекции: её содержимое может временно отличаться от SQL. TTL ключа начинается до SQL-активации и может закончиться раньше срока SQL-сессии на время ожидания; поведение на длительной задержке требует отдельной проверки. Старые и новые PG/Redis writers не признаны совместимыми; работающий legacy SQLite режим остаётся изолированным. Уборка осиротевших ключей при удалении аккаунта включена в PYM-426.

## Кандидат для реализации и проверки

Рассмотреть отдельную краткоживущую операцию входа `pending`, которая не является активной сессией и не вытесняет старые. Проверить пароль; короткой SQL-транзакцией зафиксировать операцию и повторно проверить пользователя; закрыть транзакцию. Вне SQL write lock идемпотентно подготовить **только новый** ключ Redis с ограниченным сроком действия. При подтверждённой ошибке Redis или потерянном ответе не активировать вход; оставить прежние SQL-сессии и Redis-ключи. Подготовленный ключ без SQL-сессии не авторизует.

После подтверждённой подготовки Redis повторно заблокировать пользователя на время короткой SQL-транзакции; проверить актуальность пароля, срок и состояние операции, перечитать текущие активные сессии, применить лимит и записать активацию в одном commit. Только после подтверждённого commit выдавать cookie. Фоновое восстановление не должно активировать `pending` самостоятельно. Уборка истёкших операций и ключей должна быть адресной, идемпотентной и не затрагивать активные сеансы.

Другой исследуемый вариант — создать неактивный `pending` при login, сохранив прежние активные сессии, и активировать его с вытеснением старейшей только после первого защищённого запроса с полученной cookie. Это не реализовано. Потерянное тело ответа не доказывает, что браузер не получил cookie: корректная гарантия относится к отсутствию принятого сервером запроса с ней. Кроме того, Redis может исчезнуть между проверкой ключа и SQL commit активации; этот вариант сам по себе не гарантирует сохранность всех трёх сессий при любом сбое Redis. Потребуются обработка logout без активации pending, конкуренции и отзыва, раздельные TTL, предел числа pending и проверка совместимости пользовательского входа: текущий frontend считает пользователя вошедшим после login 200. Все читатели сессий должны понимать новое состояние; смешанные старые/new writers не поддерживаются без отдельного доказательства. Проверки и выбор решения относятся к PYM-435.

Нельзя просто перенести нынешний `replace_user_sessions` за commit: запоздалый снимок одной операции может удалить ключ успешно вошедшего параллельного пользователя. `reconcile_user` и локальный importer тоже обращаются к Redis под SQL lock и должны участвовать в одном согласованном протоколе. Импорт сохраняет условие остановки изменений исходного пользователя; маркер импорта и вставка его сеансов фиксируются атомарно. Смешанные старые и новые PostgreSQL/Redis writers нельзя считать совместимыми без отдельной проверки; это не относится к изолированному legacy SQLite режиму.

## Неизвестный результат

Если соединение оборвалось после SQL commit, но до получения ответа клиентом, по одному сетевому таймауту нельзя определить, была ли активирована новая сессия. Нельзя безусловно восстанавливать вытесненную сессию: параллельно мог пройти logout или другой вход. Для прозрачного восстановления потребовались бы устойчивый идентификатор операции, проверка состояния и безопасный контракт повтора. Один `operation_id` не должен заменять секрет сессии; digest не позволяет восстановить исходный cookie. Способ безопасного повтора и граница ответственности клиента пока не утверждены и не реализованы; предварительное исправление подтверждённого отказа Redis может сохранять существующую неопределённость SQL commit без заявления, что она решена.

Даже после подтверждённой подготовки ключ Redis может исчезнуть из-за сбоя или eviction. Нужна отдельная проверка восстановления по запросу: SQL read, Redis запись вне SQL транзакции и повторная SQL-проверка перед выдачей доступа. Срок ключа не продлевается при повторе. Это кандидат, а не подтверждённый контракт или готовая работа.

## Приёмка

Для полной приёмки проверить на изолированных PostgreSQL/Redis:

1. Три действующие сессии сохраняются при подтверждённом отказе Redis, потере ответа после записи и отмене до активации.
2. При задержке Redis другая транзакция может получить пользовательский row lock; после timeout/cancellation соединения возвращены в пулы.
3. Конкурентные login/login, login/logout, login/import и import/import из отдельных процессов; одновременно не более трёх активных SQL-сессий, marker импорта не дублируется.
4. Сбои до и после каждой фазы, неизвестный результат SQL commit, повтор операции, непродление TTL, коллизия digest, Redis restart и потеря ключа; ни один отозванный или несохранённый SQL-токен не авторизуется.
5. Пользовательские API-контракты и legacy-режим остаются совместимыми. Нагрузочные сценарии и отсутствие утечек повторяются; решения о staging и сервере принимаются отдельно.
