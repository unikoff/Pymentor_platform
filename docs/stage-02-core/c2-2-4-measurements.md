# C2.2.4 — локальные измерения

Статус: **в работе**, приёмка PYM-188 не выполнена. Дополняет сохранённый `c2-2-4-local-baseline.md` и не изменяет его.

## 05.11.2026 — пределы соединений и отмена

Использована только отдельно созданная и восстановленная disposable PostgreSQL 16.15 из PYM-189; тестовые данные. Перед запуском проверены метки, образ, отдельный том, loopback-порт и identity базы. Источник копии был остановлен. Действующая SQLite не подключалась.

- Фактически считанные параметры PostgreSQL: `max_connections=100`, `superuser_reserved_connections=3`, `statement_timeout=0`, `lock_timeout=0`. Нули означают отсутствие серверного ограничения; они требуют отдельного решения в рамках PYM-188 и не являются рекомендованными настройками для сервера.
- В одном Python-процессе созданы две пары sync/async engine с параметрами local dual harness: каждый пул `3+0`, ожидание 3 секунды. При одновременном заполнении четырёх пулов PostgreSQL показала **12** подключений роли приложения. Это воспроизведение бюджетов пулов, а не запуск двух pod или replica.
- Четвёртая заявка в заполненном sync-пуле получила timeout через **3,000 с**, в async-пуле — через **3,016 с**. Отмена тестового долгого async SELECT вернула соединение: после последующего успешного `SELECT 1` число выданных соединений в этом пуле было **0**.
- Это отдельный краткий пробный замер, не длительная проверка отсутствия утечек и не оценка throughput, p95/p99, CPU/RAM или ёмкости системы. Значения серверного лимита относятся только к этому локальному контейнеру.

### Ограничение обычного списка администратору

При увеличении набора с 500 до 3000 синтетических пользователей одиночный вызов `/api/admin/users` без фильтров занял соответственно 32,88 и 140,45 мс; число SQL-запросов оставалось 6 sync + 1 async. В прежнем коде все пользователи и их квоты загружались до ограничения ответа 100 записями. Теперь только при пустом поиске и значениях `all` для обоих фильтров SQL сразу выбирает первые 100 по ID; при любом фильтре прежний порядок «фильтр до ограничения» сохранён.

После изменения тот же одиночный вызов на наборе 3000 синтетических пользователей занял 47,60 мс, ответ и число SQL-запросов по размеру/количеству совпали. Это два одиночных замера, не устойчивый p95. На SQLite и на disposable PostgreSQL отдельно проверены порядок первых 100, поиск пользователя с русским именем за пределами первой сотни и фильтрация по квоте до ограничения.

Отдельно на disposable PostgreSQL прошли **6 тестов конкурентного бронирования и блокировок** с собственными синтетическими пользователями и слотами; реальные Telegram-сообщения не отправлялись.

Позже сняты `EXPLAIN (ANALYZE, BUFFERS, FORMAT JSON)` именно с фактических sync SELECT, собранных при вызовах API каталога/прогресса, календаря, слотов, списка пользователей и обзора. До изменения основной запрос списка вернул из PostgreSQL 3026 синтетических строк (`Index Scan`); после — 100 (`Limit`). В отдельных планах время этого SQL составило 0,319 и 0,050 мс соответственно. Разница полного HTTP-запроса включает также передачу, создание Python-объектов и расчёт квот и не равна разнице времени одного SQL. Полные планы с параметрами-заглушками и обезличенными синтетическими значениями: `evidence/c224-actual-api-plans.json`. Async-запросы авторизации отдельно учтены счётчиком, но в этот набор планов не включены.

## Локальные ограничения и единичные запросы API

В opt-in `dual_local` для sync и async PostgreSQL заданы `statement_timeout=3s` и `lock_timeout=1s`; legacy-конфигурация не менялась. На disposable PG `SHOW` подтвердил параметры для обоих типов соединения. Синтетическая блокировка была прервана через заданный лимит, долгий `SELECT` остановлен, после проверки async-пул вернул все выданные соединения. У asyncpg также действует клиентский `command_timeout=3s`; какой из двух трёхсекундных таймеров сработает первым, зависит от ситуации. Эти пороги тестовые и не являются конфигурацией production.

Подставной обработчик очереди уведомлений подтвердил на одном синтетическом событии: в момент вызова отправки из пула не было выданных соединений, а соединений app-роли со статусом `idle in transaction` не наблюдалось. Реальная отправка не выполнялась. Такой сценарий не доказывает поведение всех сетевых путей.

При чтении кода найдены пути, которые выполняли Redis I/O под SQL-блокировкой пользователя: `AsyncIdentitySessions.login`, `reconcile_user` и локальный importer. В локальном экспериментальном режиме сетевые вызовы вынесены за write-блокировку во всех трёх путях. Восстановление добавляет ключи, а не заменяет полную проекцию устаревшим снимком; при изменении трёх последних сеансов во время восстановления оно делает не более трёх попыток и затем отказывает без удаления сессий. При отказе Redis исторический избыток сеансов не нормализуется до успешной публикации.

Решение владельца: если четвёртый вход не удался из-за недоступного Redis, три прежних сеанса должны сохраняться. Это исключает упрощённый вариант с вытеснением старой сессии до подтверждения Redis.

Два дефекта входа сначала воспроизведены на disposable PostgreSQL/Redis: во время задержки Redis пользовательская строка оставалась заблокированной; при потере ответа после Redis-записи один из трёх старых сеансов мог исчезнуть из Redis до успешного восстановления. Новый локальный login подготавливает отдельный ключ Redis до SQL-блокировки и активирует сеанс только после подтверждения. Интеграционные сценарии `backend/tests/test_c224_session_network_guard.py` проверяют отказ, отмену, коллизию, row lock, восстановление, импорт и гонку с logout. Проект протокола и неопределённость результата после потери ответа SQL описаны в `c2-2-4-session-protocol.md`.

После проверки состава БД (500 созданных синтетических пользователей) и изоляции Docker/Redis выполнен один последовательный проход FastAPI TestClient. Все семь ответов вернули HTTP 200; слушатели SQLAlchemy считали вызовы отдельно для sync и async engine:

| Сценарий | Sync SQL | Async SQL | Один ответ, мс |
|---|---:|---:|---:|
| Вход ученика | 0 | 6 | 262,71 |
| Каталог и прогресс | 3 | 1 | 43,38 |
| Календарь | 2 | 1 | 14,57 |
| Список слотов | 4 | 1 | 20,01 |
| Вход администратора | 0 | 6 | 187,22 |
| Список пользователей администратора | 6 | 1 | 32,88 |

Значения — одиночные наблюдения внутри процесса без сетевой нагрузки; они не показывают p95, пропускную способность или результат при двух репликах. После изменений входа, восстановления и локальных таймаутов выполнен **251 тест успешно, один пропущен** на изолированных PostgreSQL/Redis и синтетических данных. Пропущен тест перезапуска другого, заранее именованного контейнера Redis: его нельзя подменять нашим тестовым контейнером. Вместо него отдельно перезапущен наш помеченный временный Redis без сохранения данных: пока гейт потерян, доступ запрещён; после готовности Redis `reconcile` восстанавливает синтетическую сессию. Первый прогон выявил необходимость ждать готовности Redis после рестарта; после сверки состояния и добавления ожидания повтор прошёл.

После доработок отдельно пройдены **26 проверок** legacy-авторизации, API-контракта, практики и административных сценариев с временной SQLite в памяти. Первоначальный запуск в песочнице не смог стартовать вложенный интерпретатор (ошибка доступа); повтор с разрешённым доступом прошёл полностью. Реальные базы не использовались для этих тестов.

## Сравнение процессов и исправление Redis-пула

Проверен короткий локальный HTTP-профиль: `GET /api/user/me`, 8 параллельных запросов, по 96 запросов в каждом из трёх повторов. Сначала работал один отдельный процесс Uvicorn, затем два; у обоих общие тестовые PostgreSQL и Redis. Это два **процесса на одной машине**, не Kubernetes pods и не нагрузка всей платформы.

В первом и повторном прогонах с одним процессом наблюдались HTTP 503. Отдельная инструментированная проверка связала два таких ответа с `redis.exceptions.MaxConnectionsError`: в тестовом режиме неблокирующий пул Redis на шесть соединений сразу отказывал части параллельных запросов. Вариант с двумя процессами в этих коротких прогонах ошибок не показал.

Для экспериментального `RedisSessionStore` заменён пул на ограниченно ожидающий: при занятости всех соединений клиент ждёт не дольше настроенного `socket_timeout`, затем сохраняется fail-closed ошибка. Размер пула не увеличен; закрытие клиента закрывает принадлежащий ему пул. Legacy-режим не менялся. Отдельные тесты проверяют ожидание, таймаут и восстановление пула.

После исправления одинаковый профиль выполнен повторно:

| Процессы | Повторы | Успешные ответы | Диапазон p95 | Диапазон успешных ответов/с |
|---|---:|---:|---:|---:|
| 1 | 3 × 96 | 288 из 288 | 88,5–111,4 мс | 110,3–112,7 |
| 2 | 3 × 96 | 288 из 288 | 104,7–111,9 мс | 105,2–110,7 |

При этом фиксированном небольшом профиле два процесса не показали прироста; измерение не определяет предел сервиса. Индивидуальные p50/p95/p99, ошибки и throughput сохранены в `evidence/c224-before-redis-pool.json` и `evidence/c224-after-redis-pool.json`. Другие маршруты, долгосрочная стабильность и реальные ноды здесь не измерены.

Отдельный повтор после исправления измерил именно реальные процессы приложения через psutil, не вспомогательный Windows launcher: один процесс занимал в конце повторов 110–112 МиБ RSS, два процесса вместе — 219–221 МиБ. За каждый короткий повтор (примерно 0,8–0,9 с) сумма CPU времени составила соответственно 36–46% и 37–59% одного логического ядра. Все 576 запросов этого повтора также вернули 200. Это не peak RSS и не размер всей системы: память/CPU PostgreSQL, Redis, Docker и самой машины в этих значениях не учтены. Первоначальные показатели launcher были распознаны как ошибочные и не используются. Подробный повтор — `evidence/c224-worker-resource-sample.json`.

После последующего изменения login профиль `/api/user/me` повторён: все 576 запросов также вернули 200, результаты в `evidence/c224-after-login-change.json`. Это не нагрузочный тест самого login и не доказательство работы `reconcile`/импорта.

После переработки входа, восстановления и импорта выполнен ещё один короткий профиль: поровну запросов к сессии, каталогу, календарю и списку слотов, по 8 одновременно и три повтора по 96 запросов на каждый вариант. Один и два отдельных локальных процесса вернули **576 успешных ответов из 576**. Для одного процесса суммарная скорость повторов была 85,0–87,8 ответа/с и общий p95 128,8–160,3 мс; для двух — 87,7–92,6 ответа/с и p95 123,6–138,8 мс. Конечный RSS процессов составлял 113,5–115,2 и 222,7–224,8 МиБ соответственно. В каждом повторе на отдельный маршрут приходилось всего 24 наблюдения, поэтому его p95/p99 нестабильны. Полные обезличенные результаты: `evidence/c224-mixed-process-load.json`. Создание брони, админские операции, сеть к Telegram, долгие прогоны и расход PostgreSQL/Redis этот профиль не покрывает.

Отдельный повтор смешанного профиля с мониторингом Docker тоже вернул 576/576 успешных ответов. Пересекающиеся по времени с запросами выборки показали у контейнера PostgreSQL 40–65 МиБ и 0,01–18,63% CPU, у Redis — 5,1–5,7 МиБ и 0,32–1,08% CPU. Docker усредняет за интервал, который может включать старт/остановку; мониторинг сам добавляет нагрузку. Эти диапазоны не являются пиковыми значениями или требованиями к VPS. Block I/O в `docker stats` накопительный с запуска контейнера, поэтому по этим выборкам расход I/O самого прогона не определён. Таймстампы и необработанные показания: `evidence/c224-mixed-container-resources.json`.

Ещё один повтор со счётчиками `pg_stat_database` показал для всей тестовой БД разницу 5 прочитанных блоков и 30 266 попаданий в буферы. В эти значения входят подготовка синтетического пользователя, проверки, оба варианта и сам мониторинг; статистика PostgreSQL обновляется с задержкой. Это не измерение дисковой задержки и не гарантированный расход I/O при другой нагрузке. До/после и отдельные показания: `evidence/c224-mixed-db-counters.json`.

При отдельном повторе того же смешанного профиля соединения app-роли опрашивались каждые 0,2 секунды: во время трёх коротких повторов одного процесса 12 выборок показали по 6 соединений; для двух процессов 12 выборок показали от 10 до 12. Отдельное соединение мониторинга в app-счётчик не включено. Это выборочный наблюдаемый максимум, а не гарантия отсутствия кратких пиков. Результаты запросов и временные метки: `evidence/c224-mixed-connections.json`.

Для одного тестового процесса верхняя граница подключений его sync и async пулов — 3 + 3 = 6; для двух — 12. В данном опыте фоновые отправители отключены. Если отдельно запустить **один** аналогично настроенный тестовый worker, нужно дополнительно заложить до 3 sync-соединений; отдельный мигратор и мониторинг — ещё по одному. При локальном `max_connections=100` и трёх superuser-reserved такой расчёт оставляет 86 или 80 соединений соответственно. Это пример бюджета тестового профиля, не измеренное потребление worker и не настройка production: дополнительные процессы и другие потребители уменьшают остаток.

В последующем опыте на отдельной пустой тестовой БД действительно запущен один процесс `notifications.worker` одновременно с одним и затем двумя процессами API. При выборочном опросе PostgreSQL каждые 50 мс наблюдалось соответственно не более **7 и 13** соединений app-роли, из них worker — **1**; установленные верхние границы пулов API и worker составляют **9 и 15**, без отдельного соединения наблюдателя. На мигратора и мониторинг по-прежнему заложено ещё по одному соединению; миграция одновременно с этим прогоном не запускалась. Worker обрабатывал только синтетическое событие, сетевой sender и process lock были подменены, внешние Python-сокеты закрыты; реальная доставка и блокировка worker этим не проверялись. Два процесса API — не Kubernetes pods. Полный результат и профиль запросов: `evidence/c224-worker-budget.json`.

Отдельный профиль административных чтений попеременно вызывал список пользователей без фильтров и обзор: 8 параллельных запросов, 3 × 96 для каждого варианта на синтетическом наборе из 3000+ пользователей. Все 576 ответов были успешны. Один процесс показал 51,8–58,7 ответа/с и общий p95 168,7–244,2 мс; два процесса — 71,5–80,4 ответа/с и p95 143,5–173,1 мс. Конечный RSS процессов — около 114 и 225 МиБ, а CPU за краткие повторы — около 100% и 157–176% одного логического ядра соответственно. Это локальное измерение двух чтений, не гарантия производительности админки на сервере. Подробно по маршрутам: `evidence/c224-admin-process-load.json`.

| После оптимизации | 2 | 78,2–95,0 | 143,5–173,1 | 171,0–266,0 | 71,5–80,4 |

Это сравнение смеси двух административных чтений, а не время одной функции; фоновые условия и точный набор из-за дополнительного синтетического аккаунта могли немного отличаться. Данные до изменения: `evidence/c224-admin-baseline-load.json`, после — `evidence/c224-admin-process-load.json`.

Повтор того же профиля с мониторингом до и после дал максимумы **6** подключений app-роли при одном процессе и **12** при двух; опрос выполнялся каждые 0,2 с. В выборках Docker PostgreSQL занимала примерно 49–60 МиБ при одном процессе и 42–74 МиБ при двух; Redis — 3,3–4,3 МиБ. CPU PostgreSQL колебался примерно от 5% до 63% одного ядра в пересекающихся интервалах; интервалы включают переходы между процессами и мониторинг. Прочитанных с диска блоков `pg_stat_database` в обоих коротких прогонах не зафиксировано: это тёплый кэш, не оценка холодного запуска или дисковой нагрузки. До/после, интервалы, CPU, память и счётчики: `evidence/c224-admin-baseline-resources.json` и `evidence/c224-admin-after-resources.json`.

Дополнительно в тех же административных профилях измерена длительность получения соединения из SQLAlchemy-пула. В каждом варианте и каждом из трёх повторов было по 96 обращений к sync и async пулам; ошибок получения не было. Для sync-пула диапазон p95 по повторам до/после составил **207–245 / 71–74 мс** при одном процессе и **37–131 / 3–23 мс** при двух. Для async-пула — **0,05–10,73 / 2,05–3,64 мс** при одном и **0,04–6,10 / 0,03–3,64 мс** при двух. Признак заполненного пула — моментальная проверка при начале получения, а длительность включает сам путь получения соединения и может включать создание нового; это приближение, не чистое серверное время ожидания. Результаты по каждому повтору, включая max/p99 и количество заполнений: `evidence/c224-admin-baseline-pools.json`, `evidence/c224-admin-after-pools.json`.

## Дальше

Три последовательных локальных цикла отдельно заняли все три соединения sync- и async-пулов, проверили отказ четвёртому запросу примерно через три секунды, отмену ожидающего подключения и выполняющегося async-запроса. После каждого цикла оба пула показали ноль выданных соединений, а монитор PostgreSQL — ноль активных или оставленных открытыми транзакций app-роли; последующий `SELECT 1` прошёл в обоих пулах. Результат: `evidence/c224-pool-series-result.json`. Это короткая проверка восстановления, а не длительный soak-тест.

Для `GET /api/user/me` отдельно снят план фактического async SELECT: на малом синтетическом наборе PostgreSQL выбрал последовательное чтение 46 сессий; один локальный `EXPLAIN ANALYZE` занял 0,039 мс. Это не доказательство производительности на большом числе сессий; план с удалёнными значениями — `evidence/c224-async-auth-plans.json`.

Дополнительно выполнено синтетическое создание брони через HTTP: ответ 200, всего перехвачено 7 SELECT, 1 SHOW, 1 UPDATE и 1 INSERT в sync/async слоях. Для семи SELECT сохранены планы `EXPLAIN ANALYZE`; два запроса с `FOR UPDATE` повторялись только в отдельных коротких транзакциях с rollback. Данные — `evidence/c224-booking-write-plans.json`; отправка уведомлений была отключена. Такой одиночный сценарий не является нагрузочным тестом записи.

Проверка конфигурации Telegram раньше удерживала после чтения авторизации соединение с БД во время внешнего вызова. Теперь читающая транзакция завершается перед проверкой, а настройка повторно загружается под блокировкой после ответа. Проверки без сети прошли на SQLite в памяти и на изолированном PostgreSQL: во время подставного вызова занятых sync-соединений было 0 и записей ещё не было; после него настройка успешно сохранена. Отправка уведомлений из outbox в отдельно проверенном сценарии также происходила без занятого соединения. Реальные сообщения не отправлялись.

Финальная нагрузочная приёмка после полного async wiring остаётся за PYM-252. Проверенные процессы работают локально на одной машине; несколько Kubernetes-подов, физические серверы и production-профиль не проверены.
