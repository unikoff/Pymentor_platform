# Проект runbook: переход с SQLite на PostgreSQL в C5.6

Связанные задачи: [PYM-190](https://platformpy.atlassian.net/browse/PYM-190), [C5.6 / PYM-56](https://platformpy.atlassian.net/browse/PYM-56), [PYM-426](https://platformpy.atlassian.net/browse/PYM-426), [PYM-435](https://platformpy.atlassian.net/browse/PYM-435). Статус: **проект, не инструкция к исполнению**. Реальный сервер, источник и окно обслуживания в этой работе не проверялись; команды переключения намеренно не заданы. Пока пользователь не дал отдельное поручение на C5, старый production продолжает работать.

## Решения и проверки до назначения окна

- Установить точные текущие конфигурации и пути базы, всех процессов записи, фоновых обработчиков, файлов контента и внешних уведомлений. Наличие локального `backend/test.db` не доказывает, что он является серверной базой.
- Завершить и проверить importer с транзакционными границами, повтором после прерываний, обработкой конфликтов, явной политикой timestamp и сессионным контрактом. Добиться соответствия контрольных сумм и сценариев на отдельном, защищённом согласованном снимке; синтетический прототип не заменяет импортёр.
- Согласовать резервирование, срок жизни копий и журнал удалений; проверить восстановление и очистку/восстановление производных данных согласно PYM-426. Подтвердить безопасную обработку сессий по PYM-435 и запрещать совместную запись старых/новых writers в один набор данных до отдельной проверки.
- Назначить владельцев подтверждения источника, freeze, проверки целевой БД, уведомлений и восстановления. Согласовать допустимый простой после полноценной локальной репетиции и отдельно подтвердить ресурсы и замеры нового сервера. При отсутствии любого решения переход не начинать.

## Порядок окна после отдельного разрешения

1. Подтвердить наблюдаемый источник, состояние сервиса и всех writers; проверить успешное восстановление актуальных backup в отдельное место. Проверить конфигурацию целевого отдельного PostgreSQL/Redis, права, свободное место и неизменённый источник.
2. Закрыть новую запись для всех обнаруженных writers, включая фоновые процессы; дождаться завершения транзакций и зафиксировать время начала остановки. Выполнить согласованный финальный SQLite snapshot через Online Backup API с проверкой целостности. Сохранить его независимо от целевой БД.
3. Выполнить утверждённый importer; сверить количества, нормализованные логические значения, ID и связи, уникальность, sequence, роли, данные пользователей, прогресс, бронирования, сессии и состояние outbox. При неизвестной timezone, нарушении FK, несовпадении, неполном журнале удалений или неустановленном источнике остановиться до открытия нового writer; не исправлять данные автоматически.
4. Провести согласованный smoke на целевом окружении с контролируемыми тестовыми пользователями и без неконтролируемой доставки уведомлений. Явно отметить начало первой пользовательской записи в PostgreSQL и время её открытия. Затем включать обработчики и наблюдение по отдельному утверждённому плану.

## При отклонении

До первой записи в PostgreSQL: сохранить журналы и целевую среду для диагностики; вернуться к старому writer только после проверки, что все новые записи и внешние эффекты отсутствуют. После первой записи: PostgreSQL остаётся authoritative, запись останавливается, приоритет — исправление и повторная проверка. Возврат на старую SQLite без проверенного обратного переноса/replay запрещён, поскольку он может потерять новые записи и продублировать внешние действия. Такой обратный перенос пока не реализован и не проверен.

## Фактические данные этого этапа

Проверены только локальные синтетические snapshot/частичный перенос и отдельный backup/restore PostgreSQL; результаты — `c2-3-1-migration-strategy.md` и `c2-2-5-postgres-runbook.md`. Ни производственное окно, ни итоговое время, ни реальная доставка, ни полноценный cutover этими проверками не подтверждены.
