# ADR: уведомления лендингов через backend Pymentor

**Статус:** принято для этапа 06
**Дата:** 2026-10-27

## Контекст

Текущая `BookingNotificationOutbox` содержит обязательные поля записи на занятие: слот, имя, email, дата и время. `backend/notifications/delivery.py` уже обеспечивает durable outbox, атомарный lease, ограниченные retry/backoff, сохранение ошибок и очистку отправленных записей. Отправитель в `backend/notifications/telegram.py` выбирает только два booking event type и использует одну платформенную пару bot credentials. Локальный dispatcher вызывает этот же worker. В Helm notification worker сейчас выключен.

Попытка расширить booking-таблицу под лендинги оставила бы для каждого события фиктивные booking-поля и смешала бы разных получателей. Отдельная независимая очередь или второй worker продублировали бы lease, retry и эксплуатационные команды.

## Решение

1. Сохранить booking outbox, producer, formatter и его контракт без изменения. Добавить отдельные таблицы `landings`, `landing_telegram_configs`, `landing_notification_outbox` и per-destination delivery cooldown.
2. Хранить стабильный landing ID, уникальный slug, активность и версию в реестре. При bootstrap существующий `/backend` регистрируется идемпотентно под ID `pymentor-backend`; уже существующая запись с этим slug сохраняет свой ID и настройки. Каждая смена Telegram destination создаёт неизменяемую версию с `secret_ref`, chat ID и проверенным именем бота.
3. Хранить token только во внешнем Secret. Runtime-переменная `PYMENTOR_LANDING_BOT_CREDENTIALS` содержит JSON map `alias -> token`; в БД и API попадает только alias. Helm читает map из ключа существующего runtime Secret. Конфигурация проверяется через Telegram `getMe` и `getChat`; проверка не отправляет сообщение.
4. Landing event хранит ссылку на `landing_id` и конкретный `destination_config_id`, версию контракта, event ID и payload digest. Значение token и chat ID в outbox не копируются. Замена текущего destination не меняет адресата уже созданного события.
5. Расширить существующие `drain_notifications`, retry/backoff, lease, process lock, retention и CLI, чтобы обслуживать обе таблицы. Worker чередует очереди, чтобы активная booking-очередь не вытесняла landing events. Не запускать отдельную очередь.
6. Единственный разрешённый тип события v1: `telegram_connection_test.v1`, payload `{}`. Его может поставить только авторизованный администратор; требуется UUID `Idempotency-Key`, одинаковый повтор возвращает исходное событие, конфликтующий payload отклоняется. Ограничение — три теста за час на лендинг и тело запроса до 2 KiB.
7. Публичные lead/CTA/purchase события не принимать. В текущем объёме нет согласованного источника, состава персональных данных, текста consent и срока хранения заявки. Первая статическая страница не зависит от event endpoint и не загружает учебные данные.
8. Схему расширять аддитивно через существующий повторяемый `Base.metadata.create_all`; таблицы не переименовывать и старые строки не мигрировать. Helm оставляет worker выключенным по умолчанию и предоставляет явный флаг для его включения после подготовки секрета и проверки очереди.

## Доставка и отказоустойчивость

Гарантия — **at-least-once**, не exactly-once. Если Telegram принял сообщение, но ответ потерялся или timeout пришёл после принятия, повторная отправка может создать дубль. Автоматические повторы ограничены существующим лимитом и backoff; permanent failure хранится с безопасным типом ошибки. Администратор видит статус без payload/secret и может вручную повторить failed event не более трёх раз.

Неотправленный event привязан к исходной config version. Для плановой ротации надо оставить прежний versioned secret alias, пока события этой версии не завершены. При экстренном отзыве token события старой версии завершатся permanent failure; новая конфигурация не перенаправляет их автоматически.

Успешно отправленные события удаляются по retention после 30 дней; failed события сохраняются для диагностики. Откат старого приложения безопасен: оно игнорирует новые таблицы. Удалять таблицы при rollback нельзя.

## Что нужно согласовать перед публичной заявкой

Нужны: конкретный источник (форма/событие воронки), минимальные поля, обязательный consent, срок хранения и защита от повторной/автоматической отправки. До этого API не принимает visitor data и не отправляет в Telegram клики по CTA.
