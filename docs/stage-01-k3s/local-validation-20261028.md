# Локальная проверка этапа 01 — 28.10.2026

## Доступная локальная версия

Собранный frontend временно запущен на `http://127.0.0.1:18081/`; версия разработчика — на `http://127.0.0.1:18080/`. Оба адреса работают только на этом компьютере, пока запущены соответствующие процессы. Backend использует отдельную временную SQLite-базу, загрузка `.env`, уведомления и публичный Runner отключены.

Проверены отображение карты занятий в браузере и HTTP-сценарий через frontend: регистрация синтетического пользователя, вход, `/api/user/me`, каталог, выход и ожидаемый `401` после выхода. Это проверка локальных процессов, а не контейнерного или Kubernetes-развёртывания.

## Проверки исходников и конфигурации

- Frontend: TypeScript и Vite production build прошли; результат записан во временный каталог, проектный `frontend/dist` не перезаписывался.
- Core baseline: `1 passed`, включая контракт API и сценарий авторизации/обучения.
- Полный backend-набор: `158 passed`, `5 skipped`, `7 failed`, `556 subtests passed`. Ошибки относятся к расхождению текущего поведения бронирований и ожиданий теста, а также к учебным заданиям и их тестовым контрактам. Соответствующие исходники уже содержали незакоммиченные изменения; эти изменения не исправлялись автоматически.
- Исправление подготовки локальных образов: пять проверок прошли с имитацией Docker, включая отсутствие RepoDigest, изменение ID образа и отказ до создания кластера при отсутствии образа. Синтаксис shell-скриптов проверен.
- Helm `v4.3.1`: lint и template прошли для четырёх профилей. В локальном шаблоне проверены отдельные теги образов и три frontend-реплики; схема ожидаемо отклоняет две Core-реплики.

## Что мешает повторить кластерный прогон

Docker Desktop `4.97.0` установлен для текущего пользователя из официального установщика с действительной подписью Docker Inc. Движок не запустился: Docker и Ubuntu-24.04 WSL сообщают `Wsl/Service/CreateInstance/CreateVm/HCS/ERROR_NO_SYSTEM_RESOURCES` (у Docker — `RegisterDistro/CreateVm`). Пробы с временным лимитом WSL 5 и 3 ГиБ и перезапуском остановленной WSL результата не дали; исходный `.wslconfig` восстановлен побайтно. Точная причина отказа Windows пока не установлена.

Подготовлены и проверены по опубликованным SHA-256 временные бинарники Helm `v4.3.1`, k3d `v5.9.0` и kubectl `v1.37.1`. До восстановления WSL/Docker не выполнены сборка контейнерных образов, живой запуск k3d, проверка нод и подов или изменение числа работающих реплик. Исправление bootstrap и масштабирование frontend пока подтверждены только изолированными тестами и рендерингом Helm.

После восстановления Docker следует собрать оба образа, запустить локальный профиль из [runbook](operations/core-k3s-local.md), проверить маршруты и PVC, затем увеличить frontend с двух до трёх реплик и вернуть исходное значение. Core остаётся одной репликой с SQLite; его независимое горизонтальное масштабирование требует следующего этапа с подходящей базой и проверкой совместимости.

## Дополнительный живой прогон k3d — 28.10.2026

Docker Desktop и WSL запустились после освобождения ресурсов. Оба образа приложения собраны из текущего рабочего дерева. В локальном `k3d-pymentor-local-multinode` запущены три Ready-узла K3s v1.37.1+k3s1; Helm release `pymentor`, namespace `pymentor`. Core 1/1, frontend увеличен с 2/2 до 3/3 через Helm, каждая frontend-реплика расположена на отдельном узле; PVC SQLite Bound. После масштабирования главная страница и каталог API ответили 200; регистрация, вход, проверка сессии и выход синтетического пользователя ответили 200, проверка после выхода — 401. Браузер отобразил карту занятий. Адрес текущего стенда: http://pymentor.localhost:28081/ .

Для запуска использована временная копия bootstrap-скрипта без ограничений памяти контейнеров узлов: при вызове k3d из Ubuntu через Docker Desktop его монтирование `/root/.config/k3d/.../meminfo` недоступно движку. Копия удалена после завершения; постоянный bootstrap по-прежнему требует исправления для этой конфигурации. Ограничения ресурсов приложений в Helm не менялись. На `helm upgrade --reuse-values` обнаружена несовместимость с null-значениями digest в проверке схемы; повторный upgrade с `--reset-values`, профилем и явными локальными тегами прошёл. Эти особенности нужно устранить до утверждения повторяемости запуска.

В сборке frontend `npm audit` сообщил о 4 high-уязвимостях зависимостей сборки; critical-порог сборки пройден, но проблемы требуют отдельной оценки перед релизом. Проверка горизонтального масштабирования Core не выполнялась: профиль и схема ограничивают его одной репликой из-за SQLite. Автомасштабирование и реальные многосерверные отказоустойчивость/нагрузочная способность не проверены. Предыдущие 7 ошибок backend-тестов остаются открытыми. Старая платформа и VPS не изменялись.

## Проверка сценария одного VPS

Для первого сервера предполагается один серверный узел K3s, на котором одновременно работают control plane и workloads, одна реплика Core с SQLite и frontend; отдельный worker-узел для этого не обязателен. Это целевая схема для дальнейшего развёртывания, не проверка реального VPS.

На текущем локальном k3d зарегистрирован синтетический пользователь, Core перезапущен через rollout, затем вход и `/api/user/me` успешно повторены: данные пережили перезапуск. В момент сразу после rollout один запрос получил `no available server`, следующая попытка прошла; единственная реплика не обеспечивает непрерывную доступность при перезапуске. Команда штатного SQLite backup создала копию, отдельное чтение копии и `PRAGMA integrity_check` дали `ok`; восстановление приложения из копии и хранение вне хоста в этом прогоне не проверялись.

Повторный backend-прогон: 158 passed, 5 skipped, 7 failed, 556 subtests passed. Одна ошибка — расхождение по отображению прошедших бронирований; остальные связаны с учебными материалами и контрактами проверки задач. Нужны предметная проверка и исправление, влияние на инфраструктуру Kubernetes этими тестами не установлено. `npm audit --omit=dev` вернул 0 уязвимостей; ранее показанные 4 high относятся к дереву зависимостей разработки, а не к npm production dependencies. Это не является полным аудитом контейнерного образа или всей платформы.

Для публичного запуска ещё нужны реальные DNS, TLS, секреты, безопасная настройка ingress, резервные копии вне сервера с проверкой восстановления, проверка интеграций и нагрузки. `runner.enabled=false`: локальный кластер не позволяет считать публичное исполнение пользовательского Python безопасным или проверенным. Production values содержат заглушку домена и не развёртывались.
