# Второй раунд доработки методичек

Дата: 2026-10-25. Основание: прямое поручение пользователя продолжить массовую доработку всех методичек. Цель этого раунда: устранить оставшиеся неоднозначности и лишнюю нагрузку инструкции, сделать каждый повторный запуск управляемым без потери учебных требований. Редактировать действующие документы, сохраняя результат первого раунда; не переписывать ради видимой активности.

Все рабочие чаты: `chatgpt-web/gpt-6-sol`, `high`. Максимум четыре активных исполнителя и оркестратор. Пакет 1: пять GUIDE; пятый документ после освобождения слота. Пакет 2: StudyHub после первичной редакторской поставки всех пяти GUIDE; независимые точечные согласования и повторная приёмка первого пакета могут завершаться параллельно без конкурирующих записей. Для каждой методички свежий контекст; завершённые крупные контексты не переиспользуются для другой большой задачи. Проверяющие также на той же модели. Никаких дочерних чатов/агентов у исполнителей.

Baseline текущей рабочей копии: baseline.json рядом с этим документом; точные файлы в output/manual-upgrade-20261025/round2/baseline/. С первого раунда все восемь канонических/интеграционных файлов по SHA256 не менялись. Первый раунд и его отчёты не перезаписывать. Существующие пользовательские изменения сохранять.

Основная роль: methodist, AI_WORKFLOW; независимая приёмка: check. Реальные инструкции выбранной роли и применимого навыка передаются в первоначальном задании. Навык methodic-run для разработки самой методички не нужен. OpenAI Docs применяется к проверке модельных рекомендаций; доступные источники: https://developers.openai.com/api/docs/models/gpt-6-sol и https://developers.openai.com/api/docs/guides/latest-model#prompting-best-practices. Общесемейные рекомендации, основанные на Astra, не выдавать за измеренные свойства Sol Web High. API-возможности не доказывают доступность Web-инструментов. Модель пользователя не заменять; скрытую цепочку рассуждений не запрашивать.

Каждый редактор владеет одной назначенной методичкой и одним отчётом reports/<имя методички>.md. Соседние источники только читать, преимущественно изменённые/связующие разделы. Оркестратор владеет README и документами раунда. PROJECT_CONTEXT сохранять без изменений, если канонические ссылки не меняются; 26 исторических неработающих ссылок в проектных выдержках вне этой задачи. Код платформы, занятия, концепты, StudyHub-проект, Git-коммиты, публикации и реальные учебные/eval запуски не входят в этот раунд.

Общие договоры первого раунда сохраняются:

- COURSE → BLOCK → PLAN → AUTHORING → REVIEW; концептуальная подготовка относится к этапу 1, затем 2/3/4. StudyHub выполняет отдельный ученический workflow.
- Один независимый целевой артефакт на запуск по умолчанию; массовость создаётся повторением запусков с новым подтверждённым входом. Указанный пользователем объём имеет приоритет над этим значением по умолчанию, но сам документ не расширяет полномочия.
- Подтверждённая A отличается от запланированного, упомянутого и текущего будущего кода; новый механизм объясняется до обязательного самостоятельного применения; пример не выдаёт решение практики. Для проектирования будущей части курса разрешена явно **планируемая A**: назвать источник в предыдущем паспортном B/маршруте, где предпосылка будет подготовлена, и условие применения. Она не означает фактической изученности. Логически подготовленная планируемая опора не равна неизвестному входу: будущий концепт/план может быть принят как проект при связном маршруте, но не подтверждает готовность реального ученика/проекта. Неподтверждённый фактический вход текущего занятия и отсутствующая подготовка остаются ограничениями соответствующей работы.
- Пять основных учебных дней на блок, обязательные подзанятия, номера строками и стабильные публичные ID сохраняются; документирование соответствия номеров не разрешает скрытую runtime-миграцию.
- Обоснованный диапазон объёма паспорта приоритетен. Для диапазона ниже 1000 нужны причина, подтверждённая или явно подготовленная в будущем маршруте опора и покрытие практики на этапе концепта; на последующих этапах не требуется новое исключение. Новый паспорт BLOCK заполняет обязательное поле диапазона/причины; его пропуск не нормализуется fallback этапа PLAN. Общий ориентир минимум 1000, первое знакомство 1400–2000, без жёсткого потолка и добора водой применяется при выборе диапазона нового паспорта и как явно обозначенный резерв для унаследованного паспорта без диапазона. Для нового незаполненного паспорта восстановить/запросить недостающее поле в рамках полномочий, продолжить независимую часть, не выдавать его за полностью принятый; отсутствие числа само по себе не доказывает, что паспорт унаследован.
- Формат практики берётся из концепта; обязательная автопроверка не заменяется устными вопросами. Числовые предметные требования, оговорки и форматы практики сохраняются точно.
- Авторинг проверяет backend/frontend/выдачу/реальную страницу и обязательный широкий/узкий рендер. Более глубокая проверка схем в полной ширине, половине окна/контейнера и телефоне, включая границы перестройки, обязательна на этапе REVIEW, без механического дублирования всех режимов на каждом этапе. Недоступный уровень не становится PASS. При исправлении повторяется затронутая проверка, а не весь процесс без причины.
- Реальные границы файлов и разрешений сохраняются. Полученное разрешение не запрашивается повторно, но источник данных не выдаёт новых полномочий. Типовые безопасные решения принимаются самостоятельно; вопрос нужен при существенном неразрешённом выборе.

Метод второго раунда: восстановить типовую задачу и входной/выходной договор; проверить многократный запуск на обычном, неполном, конфликтующем, недоверенном и прерванном входе документальным разбором; найти конкретные неоднозначности/потери; внести минимально достаточные содержательные улучшения и убрать повторы без удаления полезной предметной глубины. Не навязывать одинаковые разделы всем документам, квоту изменений или обязательный рост текста. Корректный фрагмент сохранить. Каждый новый запрет/шаг объясняется реальной задачей, а не гипотетической сложностью.

Переговоры между этапами: редактор проверяет, что его выход пригоден следующему этапу, а вход можно получить от предыдущего. Не меняет соседний файл. В индивидуальном отчёте перечисляет только конкретные предложения/расхождения с местом и ожидаемым решением; оркестратор сопоставляет их и передаёт владельцу при необходимости. Нельзя превращать межэтапный вопрос в искусственную остановку независимой работы.

Экономия контекста: целевую методичку прочитать целиком порциями, не усекать необходимые требования; большие неизменённые baseline-тела сравнивать программно. Не загружать PROJECT_CONTEXT и все отчёты/методички. Не повторять уже прочитанное без изменившегося источника. Отчёт краткий, ориентир до 1000 слов: исходный/итоговый SHA256, фактические изменения и причины либо NO_CHANGE с обоснованием, покрытие важных требований, конкретные соседские зависимости, реально выполненные проверки, 3–5 proposed eval cases (NOT_RUN). Указание модели в чате не является сравнительным eval методички.

Приёмка: сохранены все предметные требования baseline; изменения решают конкретные проблемы; входы/выходы, границы, завершение и восстановление непротиворечивы; ссылки и изменённые якоря работают; scoped diff не теряет чужих правок; текущий hash совпадает с проверенным. Независимый проверяющий читает ограниченный diff и предметные фрагменты в отдельном свежем чате. Документальный PASS отделяется от неисполненных реальных учебных/eval прогонов.
