1. `README.md` — BETA-баннер с границей готовности, явный `$pymentor-stage1-beta` и профили, quickstart из нового корневого чата, точные C×1/B×4/F×1, два реальных маршрута dispatch (`spawn_agent` с `agent_type`; `create_thread` **без** него), честный fallback переданных TOML-инструкций; максимум 5 Web/browser turns **во всей среде** с чужими слотами. Дополнено правилом устойчивой идентичности урока при изменении отображаемого номера/названия или порядка.
2. `AGENTS.md` — краткий локальный контракт Skill/двух ролей, область пяти MD + RUN, один писатель, источники и статусы A/B, полная приёмка 1 COURSE + 4 BLOCK + N/N без автостарта stage 2/3 и без новых approval на авторскую конкретизацию B в мандате. Добавлена обязательная карта `lesson_id ↔ canonical identity source/alias ↔ display_number/title ↔ порядок ↔ физический путь` для существующих уроков; для новых предусмотрена отложенная регистрация ID.
3. `RUN_TEMPLATE.md` — единая очередь/владельцы, `FRAME_VERSION`, C/B/F статусы, все 20 основных + обязательные подзанятия, критерии F1–F3 и handoff; версии на существенных границах, без hash-журнала каждого микрошагa. Опись и реестр переименований разделяют существующий ID, отображаемые атрибуты, учебный порядок и исходный путь; `<№1>…<№4>` обозначают позицию в списке четырёх фактических глобальных номеров, а не номера 1–4.

**Правило переработки:** `display_number`, `title`, имя блока и порядок уроков можно менять отдельно от идентичности при сохранении канонического identity source. **Проверено чтением реализации:** `backend/content/catalog.py:191-194` передаёт относительный source path в `_stable_lesson_id()`; `backend/content/identity.py:366-398` сначала нормализует путь через `_lesson_identity_source()`/алиасы, затем получает `lesson-<sha256[:24]>`. Поэтому `lesson_id` независим от позиции, **но зависит от канонического пути**. Существующим и мигрируемым урокам необходимо сохранить фактический ID, путь и алиасы; неизвестное соответствие критичной существующей идентичности отмечается `BETA_GAP: LESSON_IDENTITY_UNVERIFIED`. **Новое запланированное занятие без runtime ID — другой случай:** в паспорте указывают «ID требует назначения по действующей схеме» / «ID ещё не присвоен; назначение по действующей реализации позже», ссылку для трассировки `глава → блок → паспорт → строковый номер`, будущего владельца реализации и этап проверки/создания mapping. Это штатная отложенная зависимость, **сама по себе не BETA_GAP и не препятствие для `FRAME_ACCEPTED`, `BLOCK_LOCAL_READY`, `STAGE_COMPLETE` или передачи в Stage 2** при выполнении остальных требований. Handoff в Stage 2 содержит существующий ID, если он присвоен, либо явное отложенное назначение с трассировкой и владельцем. Вставка/удаление/перестановка требует перепроверки prerequisites, A→B, сложности, N-описи, COURSE↔BLOCK и трёх межблочных стыков. Если необходимо изменить физический source path, только отдельно уполномоченный владелец реализации проверяет alias/identity mapping и миграцию прогресса; Stage 1 их не выполняет.

**Синхронизация с методичками основного оркестратора:** `02_BLOCK_CONCEPT.md` закрепляет строку «ID требует назначения по действующей схеме» для нового урока, сохранение прежней идентичности при смене display-реквизитов и отдельный перенос пути; `03_CHAPTER_ACCEPTANCE.md` проверяет идентичность паспортов, строковые номера, зависимости и условную отложенную выдачу ID при приёмке; `BLOCK_CONCEPT_GUIDE.md` сохраняет совместимый якорь для Stage 2 и разделение display-порядка, identity source и миграционной зависимости. Эти методички и диспетчер не редактировались в рамках DOCS.
