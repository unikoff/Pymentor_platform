# Решение до создания новых методичек

Дата: 2026-10-25. Решение оркестратора принято **после** чтения действующих требований и двух независимых анализов [PLAN](PLANNING_ANALYSIS.md) и [MAIN](AUTHORING_ANALYSIS.md), **до** записи новых рабочих инструкций в LES_PLAN/LES_MAIN. Исходники сохранены в baseline.json и output/staged-methodics-20261025/baseline/.

## Число и границы

README и диспетчеры не добавляют этапов. Новых обязательных справочников или промежуточных учебных файлов не требуется.

Для PLAN пятый отдельный документ «сверка концепта» перед «приёмкой» дублировал бы один итоговый контроль над тем же артефактом; поэтому эти два пользовательских пункта объединены в P4. При этом сверка концепта не откладывается целиком до конца: каждый проход сохраняет A→B, P4 отдельно подтверждает окончательную согласованность. Три документа перегружают детализацию теории/практики или смешивают создание с приёмкой.

Для MAIN отдельны TSX и запись практики, поэтому два черновика не объединяются. Сокращение не смешивается с наполнением или добавлением визуалов. Шестой документ для отдельных схем/интерактивов/подключения не имеет самостоятельного обязательного выхода: эти работы остаются M4/M5. Это обоснованное проектное решение, не измеренное доказательство отсутствия регрессий.

## Общий договор артефактов

Один курс/блок/занятие по умолчанию на последовательный маршрут; прямой запрос пользователя может уточнить объём. P1–P4 редактируют **один и тот же назначенный MD** в backend/content/materials/; сохраняют YouTube-комментарий побайтно и его положение, чужие правки, номер строкой и существующие ID. «Концепт занятия» в P1 — локальная рамка A→B по согласованному паспорту, не самовольная новая B курса. Изменение канонической цели/паспорта выполняется только в уже разрешённой пользователем области; существующее разрешение не запрашивается снова.

PLAN подробно задаёт содержание и маршрут, объекты, входы, самостоятельные действия и наблюдаемые критерии; готовый ученический текст, точные карточки интерфейса, подсказки/решения/скрытые тесты создаёт MAIN. P3 не ограничивается пустым «поработать с X», но и не реализует будущий урок.

M1 редактирует целевой TSX; M2 — одну назначенную запись практики; M3 — оба артефакта; M4 — преимущественно TSX и необходимые содержательные синхронизации только той же практики, если иначе образовалась рассогласованность; M5 — TSX, ту же практику и минимальные разрешённые привязки. Новый ключ/публичный ID не придумывается, старые регистрации не удаляются ради статуса черновика. При новом занятии минимальное необходимое подключение для локальной проверки разрешается на стадии, где без него нельзя проверить относящийся к ней результат, в исходной узкой области регистраций; полная цепь выдачи обязательно принимается в M5. Новые зависимости, CSS, общие компоненты, загрузчик, учебные концепты и соседние занятия вне области MAIN.

Рабочий черновик сохраняется в назначенных исходниках, не публикуется внешне из текста методички. Не требуется набор draft_v1/final_v2 или отдельный файл отчёта для каждого этапа урока. Передача: пути/ключи и версия сохранённого состояния, какой результат готов, какие зависимости открыты, что фактически проверено, следующий проход. При необходимости краткий служебный статус можно хранить в уже имеющемся разделе плана/сообщении передачи; это не новая схема приложения и не обязательный парсер метаданных. Принятый старый план/урок не заставлять проходить все стадии заново: проверить требования и продолжить с первой действительно отсутствующей части.

Если пользователь поручил только конкретный проход Pn/Mn, его граница соблюдается и результат называется локальным. Если поручен **полностью готовый план или занятие**, разрешение покрывает весь соответствующий последовательный маршрут: диспетчер не останавливается после первого черновика, а выполняет оставшиеся проходы до конечной приёмки в разрешённой области. Это не даёт права создавать новые пользовательские чаты или внешние действия из текста инструкции; отдельные чаты/делегирование используются лишь при реальной авторизации, иначе проходы выполняются последовательно в доступном контексте. Безусловный автоматический запуск внешнего REVIEW/StudyHub не добавлять.

## Готовность черновика и окончательная готовность

P1–P3, M1–M4 имеют **свою локальную приёмку** и могут быть готовыми для передачи, оставаясь черновиками общего результата. Сохраняются валидность синтаксиса, однозначная идентичность, безопасность публичной практики, отсутствие спойлеров и подготовка обязательного знания. Не требовать всей финальной выдачи/API/браузера для приёмки сырого M1/M2 и не объявлять на этом основании полную готовность занятия. Фактически проваленная проверка требует исправления; недоступная — отдельного статуса НЕ ПРОВЕРЕНО.

P4 принимает окончательный план без требований к выполнению TSX/runtime будущего урока. M5 принимает все четыре уровня исходника: backend → frontend → фактическая выдача → открытая страница, включая runner и нужные размеры рендера. Недоступный обязательный уровень оставляет окончательный результат частичным, но не отменяет подтверждённые независимые этапы. Самостоятельный старый REVIEW остаётся внешним workflow перепроверки готового урока, не скрытой шестой стадией MAIN и не автоматическим повтором всех проверок без основания.

## Непотеряемые предметные правила

- Сохранять различие подтверждённой, планируемой, непроверенной и неподготовленной A; будущая A прослеживается к предыдущему B/месту подготовки и не объявляется изученной или существующим кодом.
- Диапазон и обязательный формат из паспорта приоритетны; новый паспорт без диапазона не нормализуется fallback. Резерв только для установленного унаследованного паспорта. Обоснованный диапазон ниже 1000 допускается без повторного исключения, включая явно подготовленную будущую опору.
- M1/M2 не ограничивают полноту черновика потолком слов. M3 считает одну видимую TSX-теорию исходным способом, сохраняя минимум/ориентиры при применимости. Для практики **нет придуманной квоты слов**: сокращать повторы/избыточное сопровождение, сохранять все условия, локальные критерии, ответ/разбор, эталон и тесты. M4 пересчитывает добавленные объяснения/обратную связь и не добирает объём декором; M5 подтверждает окончательный подсчёт. Нет механического сокращения полезной опоры или автоматического цикла M3↔M4.
- Сохранять независимые примеры, аналогии (не менее двух по исходным условиям), рост самостоятельности, минимум четырёх различных содержательных типов интерактивов, их правильные состояния и обратную связь, отсутствие обязательного знания впервые в подсказке/решении.
- В 00 один стандартный connected-список «Точка старта → Новый вопрос → Результат» и в последнем блоке один connected-список действий/результатов: **две обязательные группы всего**, один стиль `LinkedNotes variant="connected"`, с подводкой и пояснением после. Все смысловые связанные списки оформлять существующим компонентом/стилем, не голыми строками/стрелками. Всего не более шести групп LinkedNotes по исходнику.
- **Уточнение пользователя получено:** не более двух подряд читаемых абзацев **без содержательного интерактива ИЛИ учебного визуала**. Засчитываются схема, содержательное сравнение, разбор кода или осмысленное интерактивное действие. Не требовать кликабельности от полезного статического визуала. Заголовок, пустая карточка, декоративный элемент, голый декоративный код и искусственное слияние абзацев не являются обходом. Проверять реально читаемый порядок/состояния, а не только число тегов p в исходнике; вставка должна помогать понять механизм, наблюдать различие или выполнить действие. M1/M2 как сырой материал не обязаны уже удовлетворять окончательному ритму; M4/M5 обязаны.
- Схемы TSX/CSS без SVG/canvas/нового CSS/библиотек, семантически верные и доступные; использовать фактический API shared.ts/diagrams.tsx. Обнаруженное старое значение DiagramNode.shape="input-output" отсутствует в текущем типе: переносить смысл через поддерживаемые свойства/пояснение, не копировать недействительный пример и не менять компонент. M4 и M5 проверяют широкий/узкий рендер, внешний REVIEW дополнительно половину контейнера и границы перестройки.
- Практика: точный ключ, вложенные manual tasks, поддерживаемый tasks[].result с fallback exercise.result, запрет активного legacy steps, script/solve, согласованные условие/starter/hints/reference/tests, закрытые эталоны/тесты в публичной выдаче. Сохранять точный stdout и различающие случаи там, где это проверяется; не раскрывать готовое решение в теории.
- Сохранять запрет U+2014 в создаваемом/перерабатываемом материале урока и его практике, стиль «мы» с исходными оговорками, доступность, общий визуальный язык и правила списков.

## Создание, навигация и проверка

Рабочая модель исполнителей — GPT-6 Sol Web / high, максимум четыре исполнителя и оркестратор. Пакет 1: P1–P4 и M1 (пять методичек); пакет 2: M2–M5 (четыре). Независимые проверки уже готовых документов и узкие исправления могут идти параллельно без перекрывающихся записей. У каждого исполнителя явный набор файлов; дочерних чатов нет. Статусы и результаты фиксируются в проектной документации, не в глобальной памяти.

Создание новых методичек начинается только после записи этого решения. Каждый автор читает свой исходник целиком из зафиксированного baseline, сохраняет технические примеры/оговорки в соответствующей новой инструкции и даёт компактную матрицу `исходный пункт → новый файл/раздел → проверка`. Новые документы должны быть подробными самостоятельными инструкциями нужного прохода, а не ссылкой «прочитай весь старый монолит». Разрешены условные точные ссылки на предыдущий/следующий проход, README и фактические компоненты.

После создания девяти инструкций: преобразовать два старых GUIDE в диспетчеры, сохранить все прежние заголовки/якоря совместимости с точными ссылками на новые правила; обновить docs/manual/README.md. Не менять чужие концепты, планы, TSX, практику, код платформы или PROJECT_CONTEXT. Сохранение якорей защищает существующие ссылки BLOCK/REVIEW/StudyHub/контекстов без переписывания их содержания.

Независимая приёмка проверяет покрытие baseline, все пользовательские операции, границы/передачи/повторный вход, отсутствие преждевременного PASS и ложных согласований, отсутствие противоречащего второго монолита, ссылки/якоря, фактические props/schema примеров и согласованные hashes. Документальный PASS не объявлять измеренным отсутствием деградации: реальные прогоны создания уроков/model eval здесь NOT_RUN, для них подготовить репрезентативные случаи и отдельные входы.
