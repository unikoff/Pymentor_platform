# Принятое разбиение stage 1 — 25.10.2026

Решение принято оркестратором **до создания новых методичек**, по независимым ARCHITECTURE_PROPOSAL.md и WORKFLOW_PROPOSAL.md. CONTRACT_REVIEW.md уточняет предметное покрытие; он не разрешает самовольную смену этой схемы.

**Актуализация runtime-политики — 27.10.2026.** Этот файл фиксирует разбиение методик и владение артефактами, а не текущий пул моделей/effort/слоты. Упоминание ниже «до пяти Web-чатов, только GPT-6 Sol Web High» — историческое ограничение разработки 25.10.2026; оно не действует как настройка Stage 1. Для запуска используй центральную effective policy и явный override текущей задачи. Не задавай второй пул или потолок в документации Stage 1. Предпочтение Web и набор моделей из пользовательского запроса 27.10 применяются только к этой оркестрации, не становятся будущим default; фактический маршрут и admission подтверждай в runtime.

**Три рабочие методички** в плоской папке `docs/make les stage/1 stage/`:

| Канонический файл | Применение | Внутренние проходы и результат |
| --- | --- | --- |
| `01_CHAPTER_CONCEPT.md` | Один раз на главу | C1 вход/A/B → C2 четыре роли блоков и предпосылки → C3 договоры переходов/проект/нагрузка → C4 приёмка FRAME_ACCEPTED. Один COURSE.md, достаточный для проектирования блоков. |
| `02_BLOCK_CONCEPT.md` | Один одинаковый цикл **ровно четыре раза** | B1 договор блока → B2 пять основных дней и обязательные подзанятия → B3 паспорта/практический результат/опоры → B4 локальная приёмка BLOCK_LOCAL_READY. Один BLOCK_N.md на повтор. |
| `03_CHAPTER_ACCEPTANCE.md` | Один раз после четырёх локально готовых блоков | F1 нормализация → F2 все межблочные/межурочные переходы и сложность → F3 исправления/повтор затронутых проверок и CHAPTER_STAGE1_ACCEPTED. Готовый вход отдельного stage 2. |

Почему не больше: карта блока и паспорта относятся к одному артефакту и одному владельцу; нормализация является первым проходом общей приёмки. Почему не меньше: финальный стык зависит от четырёх файлов, тогда как каждый локальный блок должен разрабатываться без ожидания приёмки соседнего черновика.

Старые COURSE_CONCEPT_GUIDE.md и BLOCK_CONCEPT_GUIDE.md остаются короткими совместимыми диспетчерами с исходными заголовками/якорями; рабочая норма находится только в трёх numbered-файлах. README, папочный AGENTS.md и RUN_TEMPLATE.md описывают запуск, передачу контекста, один журнал главы и роли; это не дополнительные методички.

Исторические владельцы разработки: ARCH писал только 01 и свой отчёт; CONTRACT — только 02 и свой отчёт; отдельный ACCEPTANCE_WRITER — только 03 и свой отчёт; WORKFLOW — README/AGENTS/RUN_TEMPLATE/два dispatcher и свой отчёт. Независимая проверка была отдельным Web-чатом; исправления возвращались владельцам. Эти назначения и модельные ограничения описывают создание комплекта, а не рабочий Stage 1 прогон. В рабочем прогоне применяются текущие роли/профили, один писатель на файл и effective policy.

Принцип сохранения: все значимые исходные нормы переходят из baseline, включая семь полей паспорта, формат практики, диапазон теории с причиной, статусы A, пять основных дней и обязательные подзанятия, строковые номера и прежние ID. Паспорт дополняется ясным смыслом/механизмом/действием/критерием, но не готовым PLAN/теорией/тестами. Метаданные приёмки и журнал — документация процесса, не новые поля приложения.

При исполнении будущего stage 1: глава FRAME_ACCEPTED → четыре параллельных BLOCK_LOCAL_READY на одной версии рамки → F1/F2/F3 → CHAPTER_STAGE1_ACCEPTED и STAGE_COMPLETE только по актуальным свидетельствам. Изменившийся договор снимает лишь зависимые подтверждения. Для проектной приёмки планируемая A допустима при трассируемом месте подготовки и условии проверки; она не становится фактическим освоением. Дальнейшие stage 2/3 автоматически не запускаются. Реальные концепты и уроки в текущей разработке методичек не изменяются.
