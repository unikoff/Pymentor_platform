# C1.1.3 — границы Core и поэтапная эволюция

**Статус:** принято как целевая архитектура и план перехода; это не описание уже развернутых модулей, брокера, ingress-контроллера или sandbox.  
**Дата:** 27.10.2026  
**Основание:** [инвентаризация Core](core-inventory.md) и [регрессионный baseline](core-baseline.md). Они описывают checkout и изолированный тестовый сценарий, а не production/deployed состояние.

## Решение

Pymentor Core развивается как **модульный монолит**: один deployable backend и одна точка входа HTTP; бизнес-границы задаются владением данными и зависимостями модулей внутри приложения, а не отдельными сетевыми сервисами. Существующий FastAPI backend — исходная система. Разделение ниже является целевым ownership-контрактом; оно не утверждает, что в коде уже есть пакеты с такими именами.

| Модуль | Owned data и ответственность | Текущая опора / граница |
| --- | --- | --- |
| **Identity** | Учетные записи, credential/password hash, session state и проверка подлинности. Выдаёт principal/claims; не владеет курсами или прогрессом. | Сейчас `users` и `sessions` в `backend/db/models.py`, auth endpoints в `backend/routers/accounts/router.py`; Redis API в `backend/db/session.py` по инвентаризации активно не подтверждён. Сохранить текущие user IDs, хеши и cookie-поведение. |
| **Catalog** | Опубликованная структура курсов, уроков, задач, их стабильные публичные ID и ревизии контента. | Сейчас материалы в `backend/content`, клиентские lesson data в `frontend/src/lessons`, выдача через `backend/routers/courses/router.py`. Каталог остаётся исходниками/текущим источником контента; CMS и массовое создание курсов вне scope. |
| **Learning** | Доступ к учебному материалу, навигация и прогресс уроков. Владеет `UserLessonProgress`; бизнес-правило явного завершения урока остаётся здесь. | Сейчас course router/service и `UserLessonProgress` в `backend/db/models.py`. Успешный submit смешанного урока сам по себе не завершает его; baseline закрепляет отдельный `/complete`. |
| **Practice** | Отправка решения и результат проверки, ревизия задания, изоляция/ресурсы выполнения. Не владеет идентичностью пользователя, курсом или прогрессом урока. | Сейчас submit проходит через `backend/routers/courses/service.py` в `backend/content/practice/runner`; `UserTaskProgress` хранит последнюю зачтённую ревизию, а отдельная история всех попыток не подтверждена. Runner не считается безопасной sandbox: M3 gate обязателен до недоверенного запуска. |
| **Access** | Решение о доступе к course/lesson на основе principal и данных подписки/плана; единое применение правил к чтению и операциям. Не копирует учетную запись или прогресс. | Текущие subscription-поля принадлежат модели пользователя, а ограничения видны в course service. Перенос владения entitlement отдельной сущности потребует совместимой миграции; этот ADR не меняет схему. |
| **Admin** | Административные операции Core над существующими пользователями/курсами и диагностикой; не получает вторую копию данных. | Сейчас `/admin` router в `backend/routers/admin/router.py`. Проверка прав остаётся обязательной на сервере; frontend visibility не является авторизацией. |

Будущие **Analytics** и **AI Mentor** не входят в Core и в этот scope. Им не предоставляется прямое владение таблицами Core. Если интеграция понадобится, сначала определить отдельный контракт чтения/события и права; наличие этих компонентов, API, агентов и runtime этим ADR не заявляется. Будущие agents не являются механизмом HA и не заменяют эксплуатационное восстановление.

## Вход, идентификаторы и контракты

- Целевой единый внешний ingress направляет браузерный трафик к отдельному frontend deployment, а `/api` — к Core. Сегодня подтверждены FastAPI в `backend/main.py`, роутеры `/admin`, `/user`, `/learning` и раздача frontend; внешний reverse proxy или Kubernetes Ingress в целевом окружении этим не подтверждены. Внутренние модули Core вызываются внутри процесса.
- Расширения ingress зарезервированы только как **возможные будущие маршруты**: `/analytics/*`, `/mentor/*` либо отдельные host/path rules после принятия отдельного ADR. Они не означают реализованные endpoints, DNS, сервисы или deploy units. Пока расширение не утверждено, неизвестные пути не должны проксироваться в вымышленные компоненты.
- Контракты между модулями используют стабильные `user_id`, `course_id`, `lesson_id`, `task_id` как идентификаторы-ссылки/значения, а не ORM-объекты чужого модуля. `user_id` и `course_id` — **placeholders типов и границ** в этом ADR, не утверждение о новой схеме/формате: при реализации сохраняются текущие public IDs и ключи, пока compatibility review не докажет безопасную эволюцию. Авторитетный lookup и права остаются у модуля-владельца.
- Запрос с аутентификацией несёт проверенный server-side principal и минимальные claims: `sub` (существующий user ID), `roles`/`is_admin`, `subscription`/entitlement context при необходимости, `iat`/`exp` только если их задаёт фактический механизм. Сейчас baseline доказывает cookie-session и `is_admin` в ответе; он **не доказывает JWT или передачу claims между сервисами**. Claims нельзя принимать от клиента без проверки; Access повторно применяет authorization к ресурсу.
- События — зарезервированный формат для будущей интеграции, не брокер и не гарантия доставки. При появлении асинхронного потребителя событие получает `event_type`, явную major/minor `schema_version`, `event_id`, `occurred_at`, producer и payload с IDs; изменения должны быть additive для старых читателей либо выпускаться как новая major-версия с планом смешанных версий. Сначала определить транзакционную границу и восстановление: нельзя обещать exactly-once. Если событие следует за commit в SQL, потребуются доказуемая доставка/повтор и идемпотентный consumer (например, transactional outbox при подтверждённой необходимости). До такого решения события не публикуются и брокер не разворачивается.
- Табличное владение логическое: компоненты пока работают в одном приложении/БД. Запись в данные другого владельца должна проходить через его операцию/сервисный интерфейс, а не через произвольный импорт моделей. Нет отдельной базы на модуль и нет распределённой транзакции.

## Этапы и exit gates

Этапы — проверяемые целевые состояния. Успешный gate не означает автоматического перехода или разрешения production cutover. Релизы, удовлетворяющие только Core scope, остаются **Core-only release**.

### M1 — локальный K3s, SQLite, один writer

Цель: воспроизводимо запустить Core в локальном K3s с SQLite и ровно одним приложением/writer. SQLite-файл и его backup/restore путь должны быть определены; второй writer/реплика к тому же SQLite файлу не допускается. Никакие Analytics, AI Mentor, брокер, отдельные сервисы или курсная CMS не разворачиваются.

**Exit gate M1:**

1. Манифесты запускают один Core endpoint; readiness проверяет готовность приложения и БД без скрытой миграции/побочного запуска worker на каждый probe.
2. Core regression baseline проходит на изолированной тестовой БД и сохранены сравнимые API/response fixtures; текущий курс и его public IDs, login/session, доступ и progress flow не теряют совместимость.
3. SQLite остаётся одним writer; подтверждены каталог тома, права, backup и restore drill на непроизводственной копии. Успех backup-команды без restore-проверки не достаточен.
4. Подтверждены конфигурация, остановка и повторный запуск без потери/дублирования durable Core state. Нельзя считать локальный K3s доказательством HA или production-ready.

### M2 — локальный PostgreSQL, две реплики приложения

Цель: локальный PostgreSQL как единственная БД Core и две stateless app replicas за единым HTTP ingress. Это переход БД и способа запуска, а не дробление на сервисы. SQLite → PostgreSQL перенос сохраняет user IDs, password hashes, sessions (если формат совместим), subscription/access state, бронирования, progress и связи с public content IDs.

**Exit gate M2:**

1. До переключения зафиксированы источник, снимок/backup и сверка строк/связей/уникальности. Миграция и повторный запуск проверены на копии; rollback boundary и способ восстановить записи, появившиеся после cutover, документированы.
2. Миграция проходит с учётом совместимости старого и нового кода: определить поддерживаемые версии приложения/схемы, порядок expand → migrate/backfill → переключение чтения/записи → contract. Деструктивный contract допустим только после доказательства, что старые writers/читатели выведены. Backfill должен быть возобновляемым и сверяемым при параллельных обновлениях; блокировки и окно обслуживания подтверждаются на конкретных версиях PostgreSQL/миграционного инструмента, а не предполагаются.
3. Проверены FK/unique constraints, конкурентные обновления progress и сессий, транзакции каждого бизнес-flow, соединительный pool при двух replicas; нет зависимости на локальный lock-файл или общий SQLite-файл для корректности.
4. На двух репликах пройдены API baseline и restart/termination одного экземпляра: committed состояние читается через другой экземпляр, незавершённый запрос имеет определённый результат/повтор. Проверено восстановление PostgreSQL из backup на непроизводственной среде.
5. Измеренная нагрузка и ресурсы записаны для заявленного локального профиля. В требованиях нет чисел RPS/latency для M2, поэтому выдуманный порог не устанавливается; до измерений масштабируемость отмечается как неизвестная.

### M3 — sandbox на каждый run

Цель: каждый запуск пользовательского кода выполняется в отдельной, ограниченной sandbox-среде с заданными лимитами CPU, памяти, времени, диска/вывода и политикой сети/секретов. Один процесс/поток или контейнер без доказанной изоляции не удовлетворяет этому gate. Выполнение отделено от веб-процесса; запуск не получает неограниченное окружение хоста. M3 требует durable submissions, transactional outbox, надёжную очередь и ограниченный пул workers; конкретная технология определяется в C3.1.1.

**Exit gate M3:**

1. Модель угроз и security boundary проверены для целевой ОС/runtime: недоступны host filesystem, credentials и запрещённая сеть; лимиты реально применяются, а превышение приводит к ограниченному завершению и очистке ресурсов.
2. Текущие task revision и API semantics сохранены: устаревшая ревизия отклоняется до исполнения; результат проверки не подменяет отдельное завершение mixed-practice урока.
3. Run имеет корреляционный ID и однозначное durable/ephemeral состояние. Timeout, отмена клиента, падение runner и повтор запроса не создают неограниченные дубли/занятые навсегда ресурсы. Если запуск асинхронный, отдельно определить идемпотентность, lease/ack, ограниченные retry/backpressure, cleanup и сверку неизвестного результата; не заявлять exactly-once.
4. Проверены adversarial/resource-limit сценарии и восстановление после завершения процесса на безопасном непроизводственном окружении. До прохождения M3 запуск недоверенного кода остаётся блокером публичного безопасного выпуска (P0 по inventory).
5. Для M3 необходимо выполнить realistic **1000 active VUs** на текущем курсе и оценить результат в C3.6: сохранить сценарий/профиль нагрузки, длительность и распределение запросов, версию/ресурсы, latency/error/saturation, пределы БД и runner, повторяемый прогон и проверку целостности состояния. До evidence это цель для измерения, не обещание ёмкости одного VPS.

## Релиз и эксплуатационные ограничения

- Core-only release включает только подтверждённые Core маршруты и модули. Модульность не требует отдельного deployment или сетевого API.
- Один VPS остаётся **single point of failure**: две реплики приложения не защищают от потери VPS, его диска, сети или локально размещённой БД. Нужны внешняя копия backup и проверенный restore для приемлемого восстановления; это снижает риск потери данных, но не превращает один VPS в HA.
- Ни M1, ни M2, ни M3 сами по себе не дают разрешения на production. Production cutover возможен только после отдельного **C3.6.6 GO** и выполнения его условий. Пока GO отсутствует, статус production cutover — не разрешён этим ADR.
- Реальные объёмы данных, нагрузка и SLO в предоставленных материалах не заданы. Выбор PostgreSQL/двух replicas задан этапом M2, а не доказанным bottleneck; 1000 VUs нельзя вывести из количества replicas.

## Альтернатива и почему она дороже сейчас

Набор отдельных сервисов Identity/Catalog/Learning/Practice/Access/Admin с брокером увеличил бы число сетевых отказов, контрактов и независимых релизов. Текущая система — одно FastAPI приложение, существующие SQL-модели и SQLite-файл; baseline проверяет flow через реальные auth/course routers и общую тестовую БД. Данные не показывают независимые команды, отдельные SLO, измеренную нагрузку или потребность в независимом масштабировании этих доменов. Поэтому меньший рабочий вариант — внутренние границы модульного монолита, PostgreSQL как единое хранилище на M2 и sandbox-per-run для изоляции на M3. Пересмотр разделения возможен при evidence о конфликтующих требованиях масштабирования/доступности или независимом владении.

## Проверки и неизвестное

ADR сверяется с `docs/core-inventory.md` и `docs/core-baseline.md`. Реализация границ и развёртываний не заявлена; перед каждым gate нужны проверки, перечисленные выше. Ключевые пути-основания: `backend/main.py`, `backend/core/web.py`, `backend/db/engine.py`, `backend/db/models.py`, auth/course/admin routers, `backend/routers/courses/service.py`, `backend/content/practice/runner/` и `frontend/src/lessons/`.

**Неизвестно по имеющимся данным:** реальный deployment и ingress, активная БД/её размер и конфигурация, production traffic/SLO, фактические backup/restore, поддерживаемая версия PostgreSQL/K3s, политика сетевого доступа sandbox и условия C3.6.6. Эти пункты — входные evidence для gates, а не предположения ADR.
