# Создание и переработка занятий Pymentor

Рабочая инструкция для GPT-6 Luna / xhigh. Результат: цельное интерактивное занятие, которое объясняет тему новичку и готовит к самостоятельной практике. Экономь на повторных чтениях, служебных документах и отчётах, не на объяснениях в занятии.

## 1. Задача и границы

Из запроса возьми курс, блок, занятие, ожидаемый результат и разрешённые файлы. Прямой запрос важнее этой методички.

- Меняй только запрошенные материалы. При режиме «только теория» практика служит входом и остаётся неизменной. При режиме «теория и практика» можно переработать её каталог.
- Не меняй соседние занятия, концепты, загрузчики, общие компоненты и стили платформы, зависимости, идентификаторы и прогресс без разрешения. Необходимые стили схемы текущего занятия допустимы по разделу 8 в пределах разрешённых файлов. Сохраняй чужие правки; не коммить и не пушь без запроса.
- Не создавай отчётные файлы, реестры или дубликаты методички. Если нужных данных нет, восстанови их из доступных источников; не выдумывай состояние проекта.
- Расхождение вне области правок обозначь в итоге. Вопрос нужен, только если без решения нельзя сохранить согласованные A → B; понятная задача не требует нового согласования.

Пример запроса для запуска:

```text
Переработай занятие {номер} глава {глава}, блок {блок}.
Режим: {только теория / теория и практика}.
Разрешённые файлы: {пути или материалы этого занятия}.
Цель: результат паспорта в docs/concept/{глава}/BLOCK_{блок}.md.
Работай по docs/CONTENT_AUTHORING.md. В конце дай краткий отчёт.
```

## 2. Контекст и порядок работы

1. **Контекст.** Прочитай в `docs/concept/<курс>/COURSE.md` A, B, границы и роль нужного блока; в `BLOCK_N.md` карту и паспорт занятия. Затем изучи его реальные Markdown, видимый TSX и выдаваемую практику. Предыдущее и следующее занятия проверяй только в части предпосылок и передачи результата.
2. **План.** Зафиксируй A → B: уже объяснённое и созданное → новое понимание и изменение → проверяемый итог. Составь короткий план разделов, примеров, аналогий и типов интерактивов. Выбери связь или механизм для изображения по разделу 8. Для каждого требования практики найди прежнюю опору либо место нового объяснения, независимого примера и проверки понимания.
3. **Правки.** Напиши цельную теорию и практический переход; саму практику меняй только в разрешённом режиме. Сохраняй точные и полезные старые фрагменты, но не приклеивай новые пояснения к противоречивой структуре.
4. **Сверка.** Сопоставь теорию, доступные задания и видимый интерфейс. Если изменён результат практики, проверь ближайшее задание, которое его использует, даже если оно не следующее.
5. **Приёмка.** Выполни раздел 9, исправь найденное в пределах запроса, просмотри diff и остановись, когда результат готов. Повторяй только затронутые проверки; при изменении входов или результатов заново пройди всю цепочку практики.

Запланированное не считай уже изученным. Паспорт задаёт цель, реальные материалы подтверждают предпосылки. При отсутствии паспорта восстанови короткие рабочие заметки по источникам и [правилам концепта блока](concept/BLOCK_CONCEPT_AUTHORING.md), без создания документа. Не перепроектируй курс по [методичке общей концепции](concept/CONCEPT_AUTHORING.md), если это не запрошено.

Читай источники один раз и по нужным фрагментам: сначала поиск точного пути, ключа или компонента, затем его контекст. Найди TSX по привязке курса, не по старому имени файла блока; при монолитном файле читай только нужное занятие. Загрузчик и правила подключения изучай при неясной выдаче или изменении привязок; старые примеры и эталоны открывай только для конкретного вопроса. Не проверяй название модели и её настройки при разработке каждого занятия. Внешние источники нужны при фактической неопределённости или прямом запросе, не вместо чтения проекта. Работай одним агентом, без параллельной повторной разработки одного материала.

### Отдельный файл занятия и привязка

В [python-foundations/index.ts](../frontend/src/lessons/python-foundations/index.ts) карта `pages` связывает точный backend `source_file` с компонентом занятия. Текущая структура: `python-foundations/block_01/Lesson01.tsx`, дробное занятие `block_01/Lesson03_1.tsx` с экспортом `Lesson03_1`; обзор в `block_00/LearningRoadmap.tsx` и `MonthTheory.tsx`. Общие детали импортируются из `../../shared`, изображения, если ещё используются, находятся в `images/` соответствующего блока.

- При переработке меняй уже подключённый файл одного занятия. Не возвращай занятия в общий `block1.tsx`, не создавай вторую копию и не редактируй соседние файлы ради поиска нужного текста. Сохраняй имя экспорта, `module` и публичные ключи.
- При создании нового занятия используй отдельный файл в папке нужного блока по принятому именованию. Подключи импорт и запись `pages` в `index.ts` только в разрешённой области; ключ должен совпасть с реальным `source_file`, включая дробный номер и имя Markdown. Новый файл без привязки не считается доступным на платформе. Порядок и прогресс не выводи из имени TSX и не меняй ради разбиения файлов.
- Другие курсы могут ещё иметь монолитные файлы блоков. Сначала проверь их `index.ts` и существующую структуру; не переноси весь курс на отдельные файлы без запроса. Пояснения, данные схемы и специфичные компоненты текущего занятия держи рядом с ним; универсальные детали бери из `shared.tsx`, без переноса предметных текстов урока в общий набор.

## 3. Теория: объяснение прежде применения

Теория раскрывает тему, а не пересказывает ТЗ. Для центрального понятия объясни: что это, зачем нужно, как работает, за что отвечает и чего не делает, с чем путают, где применяют и какую роль оно играет здесь. Для вспомогательного термина достаточно определения и назначения. Свяжи объяснения в рассказ, не семь одинаковых анкет.

Порядок для каждого нового механизма: **назначение → работа по шагам на независимом примере → типичные ошибки и причины → проверка понимания → применение в проекте**.

- Все необходимые знания появляются до задания. Новое понятие нельзя впервые объяснить только в условии, подсказке или проверочном ответе. Знакомое кратко напомни; недостающую предпосылку объясни в пределах темы.
- Перед кодом назови вопрос, после него или в пошаговом разборе объясни вход, изменения, результат и причину. Первый пример показывает один новый механизм. Завершённый код должен работать; фрагмент и псевдокод помечай. Подготовленную трассировку не называй реальным запуском.
- Пример независим от целевой задачи: если смена имён превращает его в готовый ответ, измени сценарий. Полные решения и технические подсказки к задаче остаются в практике.
- Для каждого нового абстрактного механизма дай простую аналогию рядом с точным объяснением. В полноценном занятии минимум две содержательные аналогии в разных местах. Назови соответствие частей и границу сравнения, затем вернись к механизму и примеру.
- Новый термин, сокращение или английскую кнопку поясни при первом использовании. Основное объяснение должно быть на платформе, без обязательного поиска в Google. Внешняя ссылка дополняет, не закрывает пробел.
- Применение и ограничения описывай точно. Не называй решение универсальным правилом или «стандартом production» без подтверждения. Если технология не используется в проекте, объясни зачем она упомянута и не добавляй её в практику без основания.

Проектный маршрут: **изучили механизм → переработали конкретную часть существующего Planner → проверили прежние возможности**. Не создавай второй проект, временный дубль готового слоя или повторную реализацию ради задания. Проверка сопровождает изменение, не заменяет его. Для исследовательского занятия допускается небольшой независимый опыт с честным познавательным результатом, без обещания новой возможности Planner.

### Два обязательных связанных раздела

**Вступление 00.** Это первый раздел занятия, не обзор курса в `block_00`. Плавная подводка → ровно три пункта «Точка старта → Новый вопрос → Результат» → связный поясняющий абзац после списка. Покажи, как реальная прежняя опора вызывает новый вопрос и ведёт к B; не начинай с незнакомого термина или большой схемы.

**«Что мы будем делать в практике».** Заключительный раздел теории: короткая подводка → последовательность «действие от лица мы + наблюдаемый результат» → 1–2 поясняющих абзаца после списка. Укажи связь с изученной механикой, готовую опору, крупный путь работы, доказательство результата и границы. Для проекта заверши проверкой прежних возможностей; для исследования назови проверяемое понимание. Это обзор, не алгоритм решения и не замена ТЗ.

Оба списка в TSX: `LinkedNotes variant="connected" items={[{ title, description }, ...]}`. В Markdown: нумерованные пункты с жирной меткой и пояснением в том же пункте. Текст после списка объясняет связь, а не повторяет подписи. Обе группы входят в общий лимит шести `LinkedNotes`.

## 4. Объём

Минимум **1000 слов теории**, целевой ориентир первого знакомства **1400–2000**, не потолок. Не добирай объём повторениями и не сокращай объяснение новой темы ради экономии токенов.

Считай одну реально видимую версию по frontend-привязке: TSX, иначе Markdown. Граница: от раздела 00 до обзора практики, без самого обзора и последующего итога.

- Включай прозу, определения, аналогии, разборы, пояснения списков и сравнений: `Lead`, `p`, `Callout`, `LinkedNotes.description`, поясняющий столбец `MethodGrid`; отдельно считай объясняющую обратную связь `explanation` и `StepThrough.note`, без дублей.
- Исключай заголовки, метки, hero, код, вывод, подписи схем, проверочные вопросы, варианты ответов, кнопки, практику, подсказки, решения, тесты, видео, навигацию и разметку. Связующий вопрос в обычной прозе учитывается. Техническое имя внутри объяснения учитывается, кодовый блок нет.
- Слово: последовательность букв или цифр; внутренние дефис и подчёркивание не разделяют слово. Сначала выдели учитываемый текст, потом считай. Число слов всего TSX-файла не подходит.
- Зафиксируй «основной текст + разборы интерактивов = всего». Проверочный ответ уточняет известное, а не впервые даёт обязательное знание.
- Отклонение от цели объясни кратко. Ниже 1000 допустимо только отмеченное исключение с причиной, ранее раскрытой опорой и полным покрытием практики; «сложная тема» и «хочется короче» не причины.

Основа порогов: замер шести видимых занятий блока 9 по [страницам занятий и привязкам](../frontend/src/lessons/planner-api/index.ts), 02.10.2026. Итоги 45–50: 1895, 625, 1062, 1234, 761, 911 слов; медиана 986,5. Минимум округлён выше середины, цель ориентирована на развёрнутое объяснение. Старые примеры показывают подачу, не автоматически соответствуют новым правилам голоса, списков и объёма. При расхождении следуй методичке, не копии урока.

## 5. Интерактивы и язык

В полноценном занятии минимум **четыре осмысленных интерактива разных учебных типов**, распределённых по теме, не пачкой в конце. Тип определяется действием, не названием компонента; четыре варианта выбора ответа не дают четыре типа.

Используй [shared.tsx](../frontend/src/lessons/shared.tsx):

- прогноз и трассировка: `PredictOutput`, `StepThrough`;
- причина ошибки: `BugHunt`;
- выбор и сравнение: `QuizCard`, `TrueFalse`, `CompareSolutions`;
- роли и порядок: `MatchPairs`, `CodeSequence`;
- самостоятельное объяснение: `RecallCard`, `FlipCards`;
- исследование механики: `FillBlank`, `SliceExplorer`, `BranchExplorer`, `TerminalDemo`.

Каждый интерактив проверяет уже объяснённую мысль, имеет подготовку и разбор ошибки, не выдаёт решение практики и не блокирует чтение. В технической теме планируй содержательный поиск ошибки; не придумывай её ради карточки. Обычный `CodeBlock` сохраняй там, где действие ничего не добавляет. Кодовые примеры, схемы и интерактивы не имеют общего числового потолка: убирай бессмысленные повторы, не полезные компоненты.

Голос всего авторского текста занятия: **«мы посмотрели», «разберём», «проверим», «сделаем»**. Это относится к теории, вопросам, инструкциям, комментариям и учебным сообщениям кода, практике, подсказкам, ответам и переходам. Без «ты/вы», «ученик сделает», «откройте». Исключение: ТЗ описывает поведение готового результата по разделу 7. Нейтральное определение «сервер принимает запрос» допустимо; не вставляй «мы» механически. Точные имена кода, протокольные сообщения и подписи интерфейса сохраняй.

Пиши спокойно, живо, профессионально: короткие предложения, активные глаголы, простые аналогии, без канцелярита и «магии». Длинное тире U+2014 запрещено. Номер занятия остаётся в названии, файле и ключе, но в учебном рассказе используй «предыдущее», «это», «следующее занятие».

Проверяй и стандартные сообщения компонентов. Например, `CodeSequence.incorrectExplanation` по умолчанию начинается с «Проверьте»; переопредели его в занятии от «мы». Если текстового параметра нет, отметь проблему, не меняй общий компонент вне запроса.

## 6. Списки и оформление

Используй [существующие стили](../frontend/src/styles.css) и компоненты, без нового синтаксиса и локальной дизайн-системы.

- Последовательность двух и более пунктов оформляй списком, не обычными строками, `<br />` или разрозненными абзацами. Связное рассуждение оставляй прозой.
- Три и более пары «метка + пояснение» в TSX оформляй `LinkedNotes`, не стеком `h3/p`. Для зависимости шагов `variant="connected"`; для параллельных ролей или вариантов карточный вид по умолчанию. Перед группой назови общую мысль.
- На занятие максимум **шесть групп LinkedNotes**, включая оба вида, вступление и переход к практике. Это не лимит других компонентов; не обходи его переименованием лишней группы.
- Простое перечисление: `ul/li`; порядок: `ol/li`. Сравнение по одинаковым признакам: `MethodGrid rows={[[термин, пояснение], ...]}`, двухколоночная сетка. Не превращай независимые роли в ложную последовательность.
- Markdown: плоские `1. ...` и `- ...`, каждый пункт отдельной строкой, пустая строка до и после списка. Код в тройных обратных кавычках; поддерживаются заголовки, абзацы, жирный текст и встроенный код. Текущий [MarkdownView](../frontend/src/main.tsx) не поддерживает таблицы, вложенные списки, сырой HTML и JSX как нужные визуальные элементы. Сравнения в Markdown оформляй плоским списком, не таблицей или пробелами.
- Ритм: вопрос → объяснение → наблюдение → действие → разбор. Связанные вставки могут идти подряд под общей подводкой и разбором. Не делай карточку из каждого абзаца, не удаляй полезные вставки ради преобладания текста.
- Единая ширина `--content-width`, подпись кода внутри рамки, колонки на узком экране становятся одной. Шкала `--space-*`: 4, 8, 12, 16, 20, 24, 32, 40, 48 px; обычно 16–20 внутри мысли, 24–32 между компонентами, 32 между разделами. Расстояние задавай в одном месте, не складывай родительский `gap` и внешние `margin`; новые отступы без причины не вводи.

## 7. Практика и подключение

Этот раздел применяй к изменениям практики только когда они разрешены; иначе используй для проверки существующей выдачи.

### Условия и форматы

Задача даёт один законченный результат, следующая использует достигнутое. Контекст упражнения объясни один раз. Ориентир условия: 3–4 коротких предложения и 0–3 необходимых ограничения, не обязательная квота. Назови действие, исходную опору, результат и важные границы. Не навязывай цикл, порядок строк или временные имена, если это не учебная цель.

**Стиль ТЗ: описывай уже реализованное поведение.** В постановке и требованиях называй субъект, действие и результат: «Функция возвращает копию задачи; исходный список не изменяется», «Неподходящий тип `title` отклоняет Pydantic, а не приводит к `AttributeError`». Используй утвердительную форму настоящего времени: «возвращает», «сохраняет», «отклоняет». Это описание готового состояния, не отчёт о выполнении. Не пиши «сделаем», «добавьте», «должна будет» или «нужно проверить» вместо требования. Для исследования: «Результат разбора содержит прогноз вывода и объяснение причины». Входы, ошибки и ограничения называй только существенные для этой задачи; алгоритм решения не раскрывай. Голос «мы» остаётся в подводке, подсказке и разборе.

Не повторяй требование в описании, условиях и проверках. Подсказка помогает с трудным местом без полной реализации. Устное условие не сообщает готовый вывод. Тесты проверяют только заявленные и объяснённые требования.

**Ответ содержит решение и его разбор.** После самостоятельной попытки покажи рабочий вариант кода, команды или конкретный устный ответ. Затем объясни ключевые действия: как вход превращается в результат, почему выбрана эта конструкция и как обработан заявленный ошибочный случай. В `answer.code` находится реализация, в `explanation/steps` её разбор, в `checks` проверка результата. «Проверим тип, маршрут и статус» без самого решения не считается ответом. Для поиска ошибки нужны исправление и причина; для прогноза вывода нужен точный вывод и объяснение. Не переноси решение в условие, теорию или подсказку; скрытый редакторный эталон не публикуй в обход существующего интерфейса.

- Проект, несколько файлов, инструменты или архитектура: ручные карточки `manual.py`.
- Изолированная функция или короткая программа с проверяемым результатом: `code_tasks.py`.
- Информационная тема: предпочтительно исследование в интерпретаторе; устный разбор допустим по концепту. Не заменяй практику формальным README или самопроверкой «поняли ли тему».

Ручной формат:

```python
{
    "title": "Название упражнения", "task": "Общая цель.",
    "tasks": [{
        "title": "Действие и результат", "task": "Что получим и зачем.",
        "requirements": ["Существенное условие"],
        "hint": "Следующий ход мысли без решения.",
        "answer": {
            "explanation": "Почему решение работает.",
            "steps": ["Шаг разбора"], "code": "# Рабочее решение",
            "checks": ["Проверка результата"],
        },
    }],
    "result": "Наблюдаемый итог.",
}
```

Используй вложенные `tasks`, не старое внешнее `steps`. Ответ открывается по запросу. Для устного ответа нужен образец вывода с аргументами; пустые поля и код опусти. `result` не начинай с «Готово, если»: подпись добавляет интерфейс. Отдельную плашку «без автоматической проверки» не добавляй.

Редакторный формат:

```python
{
    "title": "Результат", "level": "easy", "mode": "solve",
    "prompt": "Короткая цель.",
    "contract": {"given": "Что дано.", "todo": "Что получим.", "check": "Важные случаи."},
    "requirements": {"items": ["Необходимое ограничение"]},
    "hints": ["Опора", "Уточнение", "Локальная проверка"],
    "starter_code": "def solve(value):\n    pass\n",
    "tests": [{"name": "Сценарий", "args": [...], "expected": ...}],
    "reference_code": "# Внутреннее рабочее решение",
}
```

`solve`: имя функции, аргументы и возвращаемое значение. `script`: вход и точный вывод, проверка через `"assert": "stdout"`; форму тестов сверяй с действующим примером. Стартовый код без ответа, 2–3 подсказки без полной реализации, эталон и скрытые тесты не попадают в публичную выдачу. Необязательные `given_items/todo_items/check_items` нужны только для настоящего списка, обычно 1–3 пункта, без дубля коротких полей. Обязательную конструкцию Python сначала объясни и назови в условии.

## 8. Учебные схемы в TSX и CSS

При создании занятия с нуля или его полной переработке **создай схему прямо в занятии средствами TSX и CSS**, если взаимодействие частей, движение данных, изменение состояния или сравнение проще понять визуально. Одна схема показывает одну главную связь. До неё объясни, что рассматриваем; после объясни порядок чтения и вывод. Если схема не помогает теме, кратко обоснуй отсутствие; декоративные схемы и квота не нужны.

Исходная SVG-схема или другой визуальный образец не предполагаются. Проектируй по смыслу занятия: назначение → узлы → связи «откуда → куда → что означает» → адаптивная раскладка → реализация → приёмка. SVG, canvas и координатная отрисовка для учебных схем не используются. При переработке замени схему затронутого занятия на TSX/CSS с сохранением верного учебного смысла; соседние материалы и их старые файлы не меняй. Уже соответствующую кодовую схему можно сохранить. Содержательная растровая иллюстрация допустима отдельно, но не заменяет блок-схему.

### Общие компоненты схем

Сначала используй экспортируемые детали из [shared.tsx](../frontend/src/lessons/shared.tsx) и их существующие стили. Прочитай пояснения и типы нужных компонентов один раз; не выдумывай свойства и не копируй их реализацию в занятие.

- `Diagram(caption, orientation?)` задаёт рамку и подпись; `DiagramFlow(label, orientation?)` задаёт поток. `orientation`: `horizontal` или `vertical`; для вертикальной схемы согласуй ориентацию рамки и потока.
- `DiagramNode(title, shape?, children?)` представляет узел. `shape`: `process`, `terminator`, `decision`, `input-output`, `database`, `subprocess`. Выбирай форму по роли, не для украшения; пояснение и код передавай через `children`.
- `DiagramArrow(label, direction?, lineStyle?)` создаёт подписанное соединение. `direction`: `forward`, `backward`, `both`; `lineStyle`: `solid`, `dashed`. Два наконечника `both` обозначают одну двустороннюю связь, но не заменяют два разных пути запроса и ответа.
- `DiagramBranches(label)` и `DiagramBranch(label)` группируют исходы; `DiagramLane(title)` задаёт дорожку участника, `DiagramGroup(title)` объединяет связанные узлы. Эти контейнеры сами не рисуют линии от условия до результатов: нужные соединители и дорожки входят в композицию явно.
- `DiagramExchange(forward, reverse)` показывает два отдельно подписанных встречных пути, обратный пунктирный. Используй, когда этот стиль соответствует смыслу; если нужны иные стили, собери пути из общих деталей.
- `DiagramNote(title?, children)` даёт заметку, `DiagramLegend(items)` легенду с элементами `{ label, symbol }`. `DiagramTrack(label, items, activeIndex?)` показывает упорядоченные отметки с текущим шагом; по умолчанию активен последний. Это вспомогательная шкала, не замена требуемым узлам и стрелочным соединениям.

Минимальная композиция в отдельном файле занятия внутри `block_NN`:

```tsx
import { Diagram, DiagramFlow, DiagramNode, DiagramArrow } from "../../shared";

<Diagram caption="Передача кода на выполнение">
  <DiagramFlow label="От редактора к интерпретатору">
    <DiagramNode title="Редактор"><p>Хранит исходный код</p></DiagramNode>
    <DiagramArrow label="передаёт код" />
    <DiagramNode title="Интерпретатор"><p>Выполняет команды</p></DiagramNode>
  </DiagramFlow>
</Diagram>
```

Это фрагмент JSX внутри компонента занятия, не самостоятельный файл. Для другого расположения файла проверь относительный путь импорта. Готовые детали дают формы и оформление, но не гарантируют правильную геометрию каждой композиции: проверь стыки, ветвления, обратные пути и мобильную перестройку по критериям ниже. Если детали не покрывают нужный маршрут, добавь только ограниченную текущим занятием композицию и допустимые стили; общий API без разрешения не меняй.

### Смысл и подписи

- Каждый этап, состояние или участник представлен отдельным видимым узлом. Названия, порядок действий и связи соответствуют объяснению; не добавляй участников и переходов, которых нет в процессе.
- Используй русский язык для учебных подписей и пояснений. Точные имена кода, команды и протокольные обозначения сохраняй. Ограничения «только английский» и «1–3 слова» нет: текст должен быть достаточным для понимания, но узел не содержит абзацы теории.
- Подпись стоит рядом со своим узлом или линией; подписи ветвей однозначно относятся к своим ветвям. Равные роли находятся на одном уровне, расположение не создаёт ложную последовательность или принадлежность.
- Убирай точки в конце подписей и пояснений внутри схемы. Сохраняй точки внутри кода, имён файлов и там, где предложение продолжается.

### Непрерывные соединения

- Между связанными узлами проходит видимая непрерывная линия со стрелочным наконечником. Символ `→`, подпись, отступ или набор несоединённых значков линию не заменяют.
- Линия начинается у границы исходного узла и заканчивается у границы целевого; остриё касается целевого узла. Видимая линия стыкуется с основанием наконечника без зазора, не проходит через открытый наконечник и не выступает за остриё. Наконечник завершает соединение, а не лежит поверх продолжающейся линии.
- Обратный ответ, возврат управления и действительно двустороннюю связь показывай отдельными линиями. Простое сравнение независимых вариантов не требует выдуманного обмена. Пунктир используй для обратного пути только когда он помогает различить направления; маршрут остаётся цельным и прослеживаемым.
- У каждой ветви своя линия от точки выбора до результата. Возвраты и обходы проходят по отдельным дорожкам; несколько входов имеют различимые точки крепления. Не проводи линии через текст и посторонние узлы; избегай пересечений и неоднозначных стыков.
- Толщина линии и размер наконечника согласованы. На короткой связи наконечник не занимает основную длину. При тесноте перестрой раскладку или уменьши наконечник; не уменьшай текст до нечитаемого размера.

### Раскладка, оформление и доступность

- Используй CSS-поток, flex или grid. Узлы и дорожки соединителей занимают предусмотренные места в раскладке; высота узла учитывает переносы текста. Не собирай схему из блоков с фиксированными координатами. Локальное позиционирование декоративного наконечника внутри соединителя допустимо, если оно не задаёт расположение всей схемы.
- На широком экране выбери естественное направление чтения, обычно слева направо. На узком перестрой узлы и соединители вместе; простая последовательность может стать вертикальной. Ветви и возвраты сохраняют своих получателей, подписи и направление. Нельзя заменять линии значками, скрывать важные связи или менять только расположение узлов.
- На мобильном экране нет горизонтальной прокрутки, обрезанных узлов, наложений текста на линии и слишком мелких подписей. Предусмотри внутренние поля и зазоры у текста; при тесноте измени раскладку, перенеси строку или сократи подпись без потери смысла.
- Сохраняй визуальный язык проекта: спокойный тёмный фон, контрастные узлы, светлый текст, заметные соединители. Используй существующие токены и стили; смысл не зависит только от цвета. Без новой дизайн-системы, 3D, свечения и декоративных эффектов.
- Узлы, рамки и соединители собирай из общих `Diagram*`; небольшие специфичные композиции допустимы рядом с текущим занятием, без дублирования общих деталей. Разрешены необходимые стили, ограниченные схемой текущего занятия; размещай их по принятой в проекте схеме подключения CSS. Не меняй общие правила и компоненты платформы, не добавляй библиотеки или универсальный движок ради одной схемы.
- Используй семантическую структуру с понятной подписью и доступным текстовым описанием шагов, ветвей и возвратов. Например, `figure/figcaption` и связанное описание через `aria-describedby`; порядок DOM соответствует смыслу. Декоративные CSS-стрелки скрывай от скринридера через `aria-hidden="true"` на их контейнере, а смысл передавай текстом. Не скрывай вместе с декором значимые подписи.
- В Markdown сохрани согласованное текстовое объяснение и разбор схемы; не вставляй неподдерживаемые HTML/JSX и не делай скриншот основной версией. Если у занятия нет TSX-представления, проверь существующий путь подключения и границы разрешённых правок; не меняй загрузчик молча и обозначь недостающую интеграцию.

### Приёмка и обязательная перепроверка

1. **Проверь реализацию.** Выполни доступные проектные проверки TypeScript и CSS для затронутых файлов. Синтаксическая корректность не подтверждает внешний вид; новых инструментов проверки ради схемы не добавляй.

4. **Исправь и повтори.** После исправления повторно осмотри оба размера и выполни затронутые проверки. Схема принята только при выполнении всех критериев выше. Фраза модели «проверено» и успешная сборка не заменяют визуальный осмотр. Если просмотр или проверка недоступны, назови конкретную непроверенную часть.
