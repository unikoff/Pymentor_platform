# Сквозной путь Planner API: переход из курса 2 в курс 3

Этот документ связывает готовый Persistent Planner из занятий 39-44 с началом третьего курса. Он фиксирует замысел блока 9 и служит опорой для последующей точечной переработки уроков 45-50 и их практики.

Ученик не переносит CLI-приложение в FastAPI одной большой правкой. Сначала он понимает, какую задачу решает HTTP, затем учится читать и проектировать договор между клиентом и сервером. Только после этого в следующем блоке появятся Postman, FastAPI и первый настоящий endpoint.

## Исходная точка

К началу третьего курса ученик завершил Persistent Planner:

- \`Task\` хранит корректное состояние одной задачи;
- \`MemoryStorage\` и \`PlannerService\` разделяют хранение и прикладные правила;
- pytest защищает in-memory ядро;
- \`JsonStorage\` сохраняет задачи между запусками;
- CLI вызывает service и не управляет JSON напрямую;
- README и приёмочные сценарии объясняют готовый продукт.

Этот результат не нужно переписывать в блоке 9. Он нужен как знакомый предметный сценарий: пользователь хочет показать задачи, открыть одну задачу, создать, изменить или удалить её. Меняется не предметная область, а граница общения с приложением.

## Результат блока 9

После занятий 45-50 ученик ещё не пишет FastAPI-приложение. Он умеет объяснить и зафиксировать начальный HTTP-контракт Planner API:

- почему клиент не читает файл задач и не решает бизнес-правила;
- из каких частей состоят request и response;
- почему действие, method, ресурс и URL связаны, но не являются одним и тем же;
- где находятся идентификатор ресурса, настройки чтения и передаваемые данные;
- какие method, path, success status и error status ожидаются у основных операций с задачами.

Осязаемый итог блока состоит из двух документов:

\`\`\`text
docs/
  client-server-boundary.md  # роли и один полный путь запроса
  planner-api-v1.md          # начальный внешний контракт
\`\`\`

Второй документ начинается в занятии 49 и завершается в занятии 50. Он станет исходной точкой для реальных запросов в следующем блоке. Не создавайте отдельный документ для каждого урока и не копируйте один и тот же контракт в нескольких местах.

## Общий сценарий блока

\`\`\`text
Пользователь хочет увидеть или изменить задачу
  -> клиент формирует HTTP request
  -> сервер понимает договор request
  -> сервер применяет правила и работает с данными
  -> сервер формирует HTTP response
  -> клиент показывает результат
\`\`\`

Пока это модель взаимодействия, а не работающий сервер. В блоке 9 нет FastAPI, Pydantic, Postman, \`requests\`, raw sockets, SQL и нового хранения. JSON можно назвать как распространённый формат тела, но не нужно учить сериализацию заново: она была разобрана во втором курсе и здесь не является результатом практики.

## Паспорта занятий

### 45. Почему CLI недостаточно: клиент и сервер

**Роль в пути.** Это плавный переход между курсами. Ученик видит, что CLI и будущий API решают одну предметную задачу, но работают на разных границах. CLI находится рядом с пользователем и процессом Python. API даёт другим программам единый договор общения с сервером.

**Теория должна объяснить.**

- чем локальная команда отличается от запроса по сети;
- почему браузер, мобильное приложение, бот или другой backend не должны импортировать \`PlannerService\` и читать \`tasks.json\`;
- что клиент отвечает за намерение и отображение результата, а сервер отвечает за проверку, предметные правила и доступ к данным;
- один полный путь создания задачи: клиент, request, server, service, storage, response, клиент;
- что разделение не делает приложение автоматически сложнее. Оно позволяет заменить один клиент другим без переноса правил в каждый интерфейс.

**Практика.** Ручная. Карточки должны последовательно зафиксировать пять пользовательских действий, границы ролей, запрещённые обязанности клиента и сервера, а затем один полный маршрут создания задачи. Работа заканчивается \`docs/client-server-boundary.md\`. Код Persistent Planner на этом уроке не меняется.

**Не вводить.** FastAPI, decorators, endpoint-функции, реальные HTTP-клиенты и детали URL. Слово \`request\` можно использовать как обещание следующего урока, но не требовать собрать его байты вручную.

### 46. HTTP request: адрес, method, headers и body

**Роль в пути.** Ученик получает точную модель сообщения, которое клиент отправляет серверу. Это первый урок, где интерпретатор уместен: структура request детерминирована, её можно честно проверить скрытыми тестами и она не требует запущенного сервера.

**Теория должна объяснить.**

- request как сообщение с намерением, а не как вызов функции внутри одного процесса;
- method, адрес назначения, path, headers и body;
- зачем \`Content-Type\` сообщает формат тела, а \`Accept\` выражает ожидаемый формат ответа;
- почему GET обычно не несёт данные новой задачи в body, а создание или изменение обычно несёт;
- разницу между учебной моделью request в словаре Python и настоящим запросом по сети.

**Практика.** Одно изолированное задание в интерпретаторе. Ученик собирает модель request из готовых \`method\`, \`path\`, версии клиента и optional body. Автопроверка должна проверять request без body и request с JSON body. Это упражнение проверяет смысл частей request, а не умение открыть сеть.

**Не вводить.** Query-параметры как предметная тема, реальные URL с портами, Postman и FastAPI. Их место определено в следующих занятиях и блоках.

### 47. HTTP response: status, headers, body и Content-Type

**Роль в пути.** Ученик завершает request-response пару. Он понимает, что \`return\` серверной функции превращается в наблюдаемый договор: status сообщает исход, headers добавляют метаданные, body передаёт представление результата.

**Теория должна объяснить.**

- разницу между успешным результатом и успешным status code;
- базовые группы 2xx, 4xx и 5xx без заучивания длинного списка чисел;
- смысл 200, 201, 204, 400, 404 и 500 для будущего Planner API;
- почему 204 не содержит body;
- почему JSON body и \`Content-Type: application/json\` должны быть согласованы;
- что идентификаторы запроса и технические headers существуют в production, но пока не являются новой способностью Planner API.

**Практика.** Одно изолированное задание в интерпретаторе. Ученик собирает учебную модель response для 200 или 201 с body, 404 с JSON-ошибкой и 204 без body. Автопроверка проверяет, что body не подменяется пустым словарём и что header формата появляется только при body.

**Не вводить.** Глобальные exception handlers, FastAPI \`HTTPException\`, Pydantic-ошибки и реальный logging. Эти механики появятся только после того, как ученик увидит настоящий сервер.

### 48. Методы GET, POST, PUT, PATCH, DELETE

**Роль в пути.** Ученик связывает намерение пользователя с семантикой HTTP. Он не добавляет в API все методы ради полноты. Он учится объяснять, почему один method подходит действию лучше другого.

**Теория должна объяснить.**

- GET как чтение без изменения состояния;
- POST как создание нового ресурса;
- PUT как полная замена известного ресурса;
- PATCH как частичное изменение;
- DELETE как удаление;
- разницу между безопасностью и идемпотентностью простыми словами;
- почему повторный DELETE или PUT требует заранее описанного договором поведения.

**Практика.** Одно задание в интерпретаторе с проверяемым соответствием \`list\`, \`get\`, \`create\`, \`replace\`, \`update\`, \`delete\` и HTTP methods. В теории до задания должны быть разобраны все шесть действий и отдельно показана разница PUT/PATCH. Условие не требует HTTP-запроса и не притворяется настоящим router.

**Не вводить.** Endpoint-декораторы, URL-параметры и CRUD-реализацию. Это предмет следующего занятия и будущих блоков.

### 49. REST: ресурс, endpoint и URL

**Роль в пути.** Ученик превращает список действий в карту внешнего API. REST объясняется как полезный стиль проектирования, который делает договор читаемым, а не как обязательная религия архитектуры.

**Теория должна объяснить.**

- что \`Task\` становится ресурсом API, а \`/tasks\` обозначает collection;
- чем collection отличается от одного item, например \`/tasks/{task_id}\`;
- чем отличаются resource, endpoint, URL, path и HTTP method;
- почему путь обычно называет ресурс существительным, а действие выражает method;
- где REST помогает, а где не стоит искусственно встраивать действие в URL;
- что \`GET /health\` полезен для сервиса, но не является ресурсом задач.

**Практика.** Ручная. Ученик создаёт начало \`docs/planner-api-v1.md\`: коротко называет ресурс \`tasks\`, записывает collection и item paths, затем составляет route map для \`GET /health\`, чтения списка и одной задачи, создания, полной и частичной замены, удаления. Для каждой строки он указывает только method, path и цель. Это проектное решение нельзя честно свести к одному скрытому ответу редактора.

**Не вводить.** Path и query как правила передачи данных. В этом уроке \`/{task_id}\` можно видеть как форму item path, но детальное распределение входных данных намеренно остаётся на следующее занятие.

### 50. Path, query, body и контракт API

**Роль в пути.** Это контрольная точка блока. Ученик превращает route map в применимый договор, по которому другой человек сможет отправить request без чтения исходников. После этого в следующем блоке появятся реальные HTTP-клиенты и FastAPI.

**Теория должна объяснить.**

- path как выбор конкретного ресурса, например task id;
- query как настройку чтения или выборки, например фильтр статуса и \`limit\`;
- body как данные для создания, полной замены или частичного изменения;
- почему одно и то же поле может играть разные роли в разных requests;
- минимальные части контракта: method, path, path/query/body inputs, success status, response shape и ожидаемые ошибки;
- разницу между обязательным path-параметром, optional query и полем body.

**Практика.** Ручная. Ученик дополняет тот же \`docs/planner-api-v1.md\`. Для каждого route из предыдущего занятия он указывает источник каждого входа и success status. Затем добавляет не менее трёх коротких примеров: чтение collection с query, создание задачи с body и изменение конкретной задачи по path. Для ошибок достаточно зафиксировать 404 для отсутствующей задачи и 400 как общий пример некорректного запроса. Валидация 422 ещё не появляется, потому что Pydantic будет изучаться позже.

**Не вводить.** Реальные schemas, Swagger, OpenAPI, FastAPI parameters и validation. После завершения документа ученик должен быть готов не к написанию framework-кода наугад, а к осмысленному запуску настоящего API в следующем блоке.

## Почему форматы практики распределены именно так

Интерпретатор нужен там, где есть один проверяемый результат и он не зависит от запущенного окружения:

- в 46 ученик строит учебную структуру request;
- в 47 ученик строит учебную структуру response;
- в 48 ученик выбирает method по уже разобранному действию.

Ручная практика нужна там, где ученик принимает архитектурное или продуктовое решение и обязан объяснить его смысл:

- в 45 он проводит границу между клиентом и сервером;
- в 49 он проектирует карту ресурсов и routes;
- в 50 он завершает договор входов и ответов.

Если при точечной переработке 49 или 50 появится маленькая детерминированная проверка, её можно сделать отдельным интерактивом или разогревом в интерпретаторе. Она не должна подменять основной проектный результат. Нельзя проверять качество API-контракта только совпадением словаря с одним скрытым шаблоном.

## Правила непрерывности

1. Блок 9 строит внешний договор, а не новый Persistent Planner и не рабочий FastAPI-сервер.
2. Каждый урок добавляет одну новую мыслительную модель. Пройденные термины используются в примерах, но не объясняются заново как центральная тема.
3. Задание в интерпретаторе всегда изолировано. Оно не требует сети, установленного пакета, файлов проекта или догадки о скрытой архитектуре.
4. Ручная практика расширяет один из двух документов блока. Она не создаёт набор несвязанных заметок.
5. Теория объясняет все понятия, которые проверяет практика. Если code task требует \`Content-Type\`, \`None\`, \`PUT\` или \`query\`, эти идеи должны быть понятны до открытия редактора.
6. В 45-50 не появляются FastAPI, Postman, Pydantic, OpenAPI и CRUD-реализация. Они не являются "следующим маленьким шагом" внутри блока 9.
7. Документ \`planner-api-v1.md\` считается готовым только если другой человек может по нему собрать корректные request и понять ожидаемые success и error responses.
