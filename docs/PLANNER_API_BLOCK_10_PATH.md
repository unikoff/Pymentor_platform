# Сквозной путь блока 10: первый работающий Planner API, занятия 51-56

## Зачем существует блок

Блок 9 дал ученику договор HTTP на бумаге. Блок 10 делает этот договор наблюдаемым. Сначала ученик отправляет настоящие request через готовый HTTP-клиент. Затем он запускает первый FastAPI-сервер, видит Swagger и получает первые JSON responses. В конце блока API впервые принимает request body через Pydantic.

Это не блок полного CRUD. Его задача уже и важнее: ученик должен перестать воспринимать FastAPI как набор decorators и увидеть путь от сообщения клиента до функции сервера.

## Исходная точка

После занятия 50 ученик уже понимает:

- почему клиент не должен читать данные сервера напрямую;
- как устроены request и response;
- чем отличаются method, resource, endpoint, path, query и body;
- зачем нужны GET, POST, PUT, PATCH и DELETE;
- как выглядит начальный HTTP-контракт Planner API.

Но он ещё не отправлял настоящий request, не запускал HTTP-сервер и не использовал framework. В репозитории нет проекта studyhub-api, FastAPI, Pydantic-модели, OpenAPI-схемы и API-тестов.

## Результат блока

После занятия 56 у ученика есть первый локальный API-проект:

~~~text
studyhub-api/
  app/
    main.py
  requirements.txt или pyproject.toml
  postman/
    http-lab.collection.json
~~~

Он умеет:

- отправить GET и POST на безопасный echo-сервис через Postman;
- объяснить роли URL, query, headers, JSON body, status и response;
- запустить Uvicorn из корректной директории;
- открыть GET /health и автоматическую документацию;
- получить временный список задач и статистику через GET;
- объяснить выбор item и collection, правила query и границы limit;
- принять первый JSON body через TaskCreate и увидеть 201 или 422.

После блока ещё нет:

- устойчивого storage.py и генератора id;
- полноценного POST, который сохраняет задачу;
- законченного item endpoint в проектной структуре;
- отдельной схемы ответа, схем PUT и PATCH;
- собственного router-пакета, TestClient-тестов и финального README;
- базы данных, JSON persistence, авторизации и async.

Это честная контрольная точка. API уже живёт как сервер и умеет принимать вход, но его прикладная CRUD-логика появится в блоке 11.

## Две связанные линии практики

В блоке идут два разных, но согласованных пути.

| Линия | Что делает ученик | Зачем это нужно |
| --- | --- | --- |
| Проектная | Использует Postman, запускает FastAPI и меняет studyhub-api | Видит настоящий HTTP и получает воспроизводимый сервер |
| Лабораторная | Решает чистые задачи в интерпретаторе | Без инфраструктуры тренирует поиск item и обработку collection |

Лабораторная задача не является вторым проектом. Она использует ту же форму записи задачи и те же будущие правила:

~~~text
id: int
title: str
priority: int
is_done: bool
~~~

Если задача в интерпретаторе возвращает копию item или создаёт новый список, последующий CRUD-слой обязан сохранить этот смысл. Если будущий API должен действовать иначе, сначала меняется раннее упражнение и теория, а не добавляется исключение в поздний урок.

## Паспорта уроков

### 51. Postman: отправляем request вручную

**Роль в цепочке.** Ученик впервые сам становится клиентом API. Echo-сервис нужен потому, что собственного сервера ещё нет. Он безопасно показывает, что именно ушло в request и что пришло обратно.

**Теория должна дать.**

- роль HTTP-клиента и отличие клиента от сервера;
- части окна Postman: method, URL, Params, Headers, Body, response;
- environment и base_url как способ не копировать адрес по всем request;
- порядок чтения response: status, headers, body, а не только красивый JSON;
- разницу между collection и отдельным несохранённым request;
- почему export collection не должен содержать токены и личные данные.

**Практика.** Ручная, на echo-сервисе. Сначала GET с двумя query-параметрами, затем POST с JSON body. Для обоих request ученик проверяет status, URL и отражённые сервером данные. После этого добавляет два простых Postman test, сохраняет collection и экспортирует её в проект.

**Не вводить.** Собственный FastAPI, auth headers, реальные production API, чужие credentials и сложные pre-request scripts.

**Мостик.** В следующем уроке Postman переключится с echo base_url на локальный Uvicorn-сервер, но навыки сборки и чтения request останутся теми же.

### 52. Первое FastAPI-приложение, Uvicorn и Swagger

**Роль в цепочке.** Здесь появляется отдельный API-проект и самая маленькая работающая серверная граница. Ученик должен увидеть все части запуска, а не только скопировать одну строку с decorator.

**Теория должна дать.**

- что создаёт объект FastAPI app;
- что endpoint связывает method и path с Python-функцией;
- что Uvicorn это ASGI-сервер, который принимает HTTP и вызывает app;
- почему команда запуска зависит от текущей директории и import path;
- что Swagger UI и OpenAPI создаются из объявленного приложения, а не пишутся вручную;
- как отличить ошибку запуска, ошибку импорта, 404 и успешный JSON response.

**Практика.** Ручная. Карточки идут в таком порядке: создать isolated project, установить зависимости, объявить app, добавить GET /health, запустить Uvicorn, проверить endpoint и /docs, затем намеренно воспроизвести одну безопасную ошибку запуска и объяснить её. В конце фиксируется одна команда запуска и dependency file.

**Не вводить.** Список задач, CRUD, Pydantic-схемы, APIRouter, database и production deployment. Health endpoint существует только как проверяемая граница старта.

**Мостик.** Следующий урок оставляет запуск неизменным и добавляет read-only данные. Ученик уже не тратит внимание на инфраструктуру, а наблюдает HTTP-поведение endpoints.

### 53. GET endpoints и ответы FastAPI

**Роль в цепочке.** Ученик получает первую полезную поверхность API. Он видит, что endpoint не обязан принимать input, чтобы быть частью контракта: GET читает текущее состояние и возвращает JSON.

**Теория должна дать.**

- GET как read-only запрос и почему он не должен менять список задач;
- разницу между Python list/dict и JSON response;
- временный in-memory список как учебное состояние процесса;
- стабильную форму ответа collection и вычисление stats;
- связь между return value, status 200 и Content-Type;
- почему data resets after restart и почему это пока ожидаемое ограничение.

**Практика.** Ручная. В существующее app добавляются два предсказуемых endpoint: GET /tasks и GET /stats. Ученик проверяет их через Swagger и Postman, меняет исходный список, заранее прогнозирует новый stats response, затем возвращает контрольное состояние. Проверяются status, JSON body и отсутствие user input.

**Не вводить.** Path и query parameters, создание новых задач, автоматическую генерацию id, Pydantic и отдельный storage. Один список в main.py сейчас допустим как временная модель для изучения read-only request.

**Мостик.** Lesson 54 берёт ту же форму одной задачи и учит выбрать item. Lesson 55 берёт collection и учит менять именно выборку, не меняя сам источник.

### 54. Path-параметры и поиск объекта

**Роль в цепочке.** Ученик соединяет URL одного item с обычной Python-логикой поиска. Это подходящее место для интерпретатора: функция поиска имеет один ясный договор и может быть проверена без работающего сервера.

**Теория должна дать.**

- разницу между collection path и item path;
- path parameter как значение, выбранное из URL;
- преобразование path к ожидаемому типу;
- разницу между 422 для некорректного представления id и 404 для корректного id, который не найден;
- зачем helper возвращает copy найденной записи;
- why one search rule should later be reused instead of being copied into several endpoints.

**Практика.** Интерпретатор вызывает чистую функцию со списком словарей задач и task_id. Ученик находит item, возвращает его copy и получает None для отсутствующего id или пустой collection. Условие и тесты не должны требовать импортов FastAPI, HTTPException или изменять входной list.

**Граница формата.** Теория может показать будущий item endpoint как карту применения, но практика честно называется лабораторной проверкой search rule. Пока она не должна обещать, что маршрут уже добавлен в project files.

**Не вводить.** response_model, схемы TaskRead, общий CRUD module и router extraction. Эти уровни потребуют следующих контрактов.

### 55. Query-параметры, фильтрация, сортировка и границы

**Роль в цепочке.** Ученик понимает, что один GET /tasks может дать разные представления одной collection. Query меняет выборку, а не ресурс и не источник состояния.

**Теория должна дать.**

- optional filter is_done и значение None как отсутствие фильтра;
- последовательность filter, sort, limit;
- why query does not create a new URL for every combination;
- why limit has a server-side boundary;
- разницу между сортировкой данных и изменением storage;
- production context: pagination, allowed sort fields and predictable tie breakers.

**Практика.** Интерпретатор работает с одной явной подзадачей: копиями задач, фильтром is_done, сортировкой по id и limit в диапазоне 1-50. Автопроверка проверяет отсутствие фильтра, оба направления сортировки и границы limit. Исходный list не меняется.

**Граница формата.** Если теория говорит о search text, offset или arbitrary sort fields, она не должна требовать их в текущем editor task без отдельного договора и тестов. Эта практика закрепляет только filter, sort and limit.

**Не вводить.** SQL pagination, database indexes, dynamic ORM columns и сложные query models. Они принадлежат последующим этапам.

### 56. Pydantic BaseModel и request body

**Роль в цепочке.** Ученик впервые видит, что сервер получает не сырой dict из JSON, а проверенный объект входного контракта. Это подготавливает безопасный POST, но ещё не завершает CRUD.

**Теория должна дать.**

- problem with unstructured dict input;
- BaseModel как описание входных данных;
- binding body parameter to endpoint;
- required fields, primitive type conversion and built-in validation;
- разницу между принятым body, 201 и 422 до логики endpoint.
- model_dump как controlled conversion for later storage logic;
- why client does not set id and is_done on create.

**Практика.** Ручная. Ученик добавляет TaskCreate with title and priority, POST /tasks with 201, a valid Swagger request and two invalid requests. Он проверяет, что при невалидном body тело endpoint не запускается. Временный response допустим, потому что storage and stable id belong to block 11.

**Не вводить.** Field constraints such as min_length or ge/le, custom validators, separate TaskRead or TaskUpdate, real CRUD storage and a final POST implementation. Урок 57 расширит validation, а урок 58 разделит contracts.

## Правила непрерывности

1. В 51 Postman обращается только к echo-сервису. Нельзя требовать работающий FastAPI до урока 52.
2. В 52 health endpoint доказывает запуск, но не превращается в урок по CRUD.
3. В 53 данные временные и read-only. Нельзя раньше времени добавлять генератор id или запись через POST.
4. В 54 и 55 задания в интерпретаторе используют ту же предметную форму, что и следующий CRUD, но не требуют сетевой среды.
5. В 54 404 и 422 должны быть разделены словами, примерами и проверками. Корректный id, которого нет, не является ошибкой типа.
6. В 55 все параметры имеют один явно названный порядок обработки. Фильтр, сортировка и limit не должны менять исходное storage.
7. В 56 FastAPI уже может дать 422 за missing field или incompatible type. Предметные constraints и подробный error contract появляются только в 57.
8. Никакая практика блока не импортирует Persistent Planner, JsonStorage или CLI. Новый API-проект остаётся отдельным продуктом.

## Путь наблюдаемого запроса к концу блока

~~~text
Postman or Swagger
  -> POST /tasks with JSON body
  -> FastAPI matches endpoint
  -> Pydantic builds TaskCreate or returns 422
  -> endpoint returns a temporary 201 response

Следующий блок
  -> validation rules
  -> server-owned storage and id
  -> real create, read, update and delete
~~~

Ученик должен уметь назвать место, где остановится невалидный request, и объяснить, почему эта остановка происходит раньше прикладной CRUD-логики.

## Синхронизация представлений

Видимый урок показывает React-компонент из frontend/src/lessons/planner-api/block10.tsx. Markdown-файлы 51-56 являются отдельным представлением, а практика находится в rich_practice.py или rich_code_tasks.py. При точечной переработке одного занятия нужно синхронизировать:

1. Markdown и видимый React-урок;
2. заголовок, центральный вопрос и итог урока;
3. практику, подсказки, answer или hidden tests;
4. карту блока и следующий урок;
5. placeholder для YouTube-видео.

Урок не готов, если хороший текст находится только в Markdown, а ученик видит старый TSX, или если code task проверяет термин, которого нет в теории.

## Критерий готовности блока

Блок готов, если ученик может:

1. собрать и повторно отправить GET и POST request в Postman;
2. с нуля запустить studyhub-api и проверить GET /health;
3. открыть Swagger и объяснить, откуда взялся /docs;
4. предсказать JSON response GET /tasks и GET /stats;
5. объяснить разницу между path id неверного типа и отсутствующим item;
6. выполнить лабораторные правила поиска и query без изменения исходного list;
7. отправить валидный и невалидный POST body и объяснить 201 и 422;
8. назвать следующие способности блока 11, не пытаясь добавить их в текущий API заранее.
