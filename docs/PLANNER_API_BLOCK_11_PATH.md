## Общий концепт блока

Ученик уже видел HTTP-запрос и ответ, запустил FastAPI, прочитал GET-маршруты и передал JSON в `TaskCreate`. Но принять JSON ещё не значит создать задачу. Пока приложение лишь возвращает проверенные входные поля, а временный `POST /tasks` отвечает `200`. У него нет созданной записи с серверным `id`.

Новая задача блока — перейти от «сервер понимает сообщение» к «сервер знает правила ресурса». Порядок принципиален: сначала уточняем, какой вход допустим, затем отделяем вход от выхода, после этого разбираем изменение состояния и весь жизненный цикл задачи. На каждом шаге ученик должен понимать, **кто владеет данными, когда они меняются и чем это можно доказать**. Это подготовка к рабочему CRUD API, а не обещание собрать его уже в 59–62.

Начало после блока 10:

- В `studyhub-api` работают `GET /health`, `GET /tasks`, `GET /stats` над временными данными; `TaskCreate` впервые принимает body. Временный `POST /tasks` возвращает `TaskCreate` и `200`, но ничего не сохраняет.
- Упражнение 54 уже дало чистое правило поиска по `id`; упражнение 55 — фильтр, сортировку по `id` и `limit`. Эти правила **ещё не подключены** к публичным маршрутам.
- Ученик знает назначение path, query, body и базовых HTTP-кодов. Он ещё не изучил ограничение полей через `Field`, границы схем, правила server-owned state и алгоритмы CRUD.

После блока остаются **два разных, честно названных результата**:

| Где работает ученик | Реальный результат к концу 62 | Чего там ещё нет |
| --- | --- | --- |
| Проект `studyhub-api`, уроки 57–58 | `TaskCreate` с ограничениями; схемы `TaskCreate`, `TaskUpdate`, `TaskRead`; проверенный ответ существующего GET; задокументированные случаи 422 и граница временного POST | Реального создания, `201`, CRUD-маршрутов, `APIRouter` и тестов |
| Интерпретатор, уроки 59–62 | Проверенные чистые алгоритмы создания, чтения, полной и частичной замены, удаления над одним форматом записи | Общего хранилища между запусками упражнений, работающих HTTP endpoints и переноса кода в проект |

Именно **практика 63** переносит правила 54–55 и 59–62 в работающий API: сначала собирает CRUD в `app/main.py` и проверяет HTTP-сценарий, затем выносит уже работающие маршруты в `APIRouter`. База данных, авторизация и файловая persistence сюда не входят. Память процесса исчезает при перезапуске — это свойство учебного этапа, не скрытая ошибка.

### Единый предметный и HTTP-договор

| Объект или правило | Договор для всех уроков |
| --- | --- |
| Запись задачи | Ровно `id: int`, `title: str`, `priority: int`, `is_done: bool`; `description`, `note`, `tags` не являются полями Planner API этой версии |
| `TaskCreate` | Клиент обязательно передаёт `title` и `priority`; `id` и начальный `is_done=False` задаёт сервер |
| `TaskRead` | Сервер возвращает все четыре поля после настоящего создания или чтения полной записи |
| `TaskUpdate` | Полный PUT: `title`, `priority`, `is_done` обязательны, `id` сохраняется из path/записи |
| `TaskPatch` | Частичный PATCH: эти же три поля можно опустить; отсутствие поля означает «не менять», явный `null` в текущем учебном договоре тоже не меняет поле, а явное `false` означает «установить false» |
| Ограничения и нормализация | `title` длиной 1–120, `priority` от 1 до 5. Создание и изменение заголовка очищают края через `strip()`; если после очистки ничего не осталось, состояние не меняется и HTTP-граница позднее отвечает 422 |
| Идентификатор | Для пустой коллекции `1`, иначе `max(id) + 1`; внутренние пропуски среди **сохранившихся** записей не заполняются. Клиентский `id` не управляет этим правилом |
| Чтение коллекции | Упражнение 55 задаёт `is_done: bool | None = None`, `sort_desc: bool = False`, `limit: int = 10` с диапазоном 1–50; фильтр → сортировка по `id` → ограничение, без мутации исходного списка. В HTTP это появится только в 63 |
| HTTP-граница | `422` — недопустимый вход, `404` — корректный `id` отсутствующей записи, `204` — успешный DELETE без body; `201` — только после настоящего создания полной записи в 63 |

Не скрывайте разницу между `Field(min_length=1)` и «непустой после `strip()`». Одни пробелы проходят проверку длины строки. В 57 ученик изучает **структурную проверку** Pydantic; в 59 — **предметную нормализацию** и причину запрета пустого результата. В редакторе 59–61 заголовок по договору уже непустой после очистки: там проверяется алгоритм, а не HTTP-валидация. При интеграции в 63 пробельный ввод отклоняется с 422 **до изменения состояния**. Не описывайте `Field(min_length=1)` как уже решивший этот случай и не добавляйте в автотест редактора ошибочный ввод без определённого формата ошибки.

`TaskUpdate` — намеренно выбранное имя полной PUT-схемы. В 58 она содержит три **обязательных** изменяемых поля. В 61 впервые появляется отдельная `TaskPatch` с полями, которые можно опустить. Не переименовывайте `TaskUpdate` в `TaskReplace` и не делайте её частичной схемой.

У правила `max(id)+1` есть честное ограничение: если удалить запись с самым большим `id`, следующий create может снова выдать этот номер; после удаления всех записей счёт начинается с 1. Поэтому не называйте такую схему глобально монотонной или безопасной для ссылок на удалённые задачи. Здесь она совпадает с существующим упражнением и позволяет изучить операцию; в production выдачу идентификаторов поручают надёжному счётчику/БД. Это стоит проговорить в 59 и вспомнить в итоговых ограничениях API, а не обещать невозможное.

### Как пользоваться паспортами ниже

Для каждой практической карточки или условия редактора автор составляет внутреннюю карту: результат → необходимое знание → где это объяснено → независимый пример → интерактив → подсказка → проверка. Если звено отсутствует, сначала исправьте урок. Интерактивы должны проверять разные операции мышления: предсказать результат, найти нарушение, выбрать границу ответственности, объяснить причину ошибки. Для 59–62 указывайте в `given`/`todo`/`check` сигнатуру, вход, результат, запрет мутации, кейсы проверки; давайте 2–3 возрастающие подсказки, не раскрывая `reference_code` или тесты. В теории можно показать похожий, но не идентичный пример. Эти правила уточняют, а не заменяют [методологию](CONTENT_AUTHORING.md).

## Паспорта уроков

### 57. Pydantic-валидация и ошибка 422

**Вход и новый смысл.** `BaseModel` и временный POST уже знакомы. Теперь ученик узнаёт, что «JSON удалось разобрать» и «данные подходят для задачи» — разные утверждения. Результат урока: существующий вход отсекает часть ошибочных запросов до запуска обработчика; ученик умеет прочесть объяснение ошибки и повторить проверку.

**Как написать теорию.** Начните с человеческой ситуации: форма заявки может содержать все поля и всё равно не подходить по правилам. На независимом примере (например, бронирование с количеством мест) отделите отсутствие поля, несовместимый тип и значение вне диапазона. Только затем покажите `Field` на `TaskCreate`: обязательные `title` (1–120 символов) и `priority` (1–5). Объясните, что `Field` не меняет имя поля и не создаёт значение по умолчанию. Покажите путь `request body → проверка Pydantic/FastAPI → обработчик` и анатомию `detail`: `loc` указывает место, `type` вид ошибки, `msg` человекочитаемое сообщение. Не требуйте запоминать точный текст `msg` или все коды `type`; учите искать смысл. Уточните, что пробелы удовлетворяют `min_length=1`, а очистка и проверка после неё придут на следующем алгоритмическом шаге. На production-примере объясните, зачем сервер проверяет ввод независимо от фронтенда и почему отклонённый вход не должен менять данные.

**Интерактивы.** Дайте минимум три разных проверки: классифицировать body с пропущенным `priority`, пустым `title` и значением `priority=0`; по фрагменту `detail` определить поле и причину; предсказать, появится ли отладочный маркер обработчика при `422` и при валидном запросе. Отдельный вопрос про строку из пробелов проверит границу `min_length`, не превращая её в неожиданную ловушку практики.

**Как построить ручную практику.** Разбейте на три или четыре карточки, а не на один длинный список команд:

1. Уточнить **существующую** `TaskCreate` через `Field`, не создавать новую модель рядом. Критерий: оба поля остаются обязательными; границы заданы явно.
2. Исследовать четыре ошибки (отсутствующий/пустой `title`, `priority=0/6`) и один валидный граничный случай. Для каждого сохранить body, HTTP-статус, значимые `loc`/`type`/`msg` в `docs/validation-cases.md`. Проверять смысл ответа, а не дословный текст, зависящий от версии библиотеки.
3. Доказать, что ошибочный body не запускает функцию: временный маркер внутри handler появляется у валидного запроса и отсутствует у невалидного; после опыта маркер убрать. **Не использовать неизменность числа задач как основное доказательство:** нынешний POST не меняет список даже при успехе, поэтому такой тест ничего не доказывает.
4. Кратко сформулировать, что `Field` уже решает и чего пока не решает: пробельный заголовок ещё нуждается в нормализации, а создание записи ещё не реализовано.

В подсказках направляйте к `Field`, `/docs` и поиску `detail`, но не давайте готовый класс или заполненную таблицу. В разборе после попытки покажите, почему «ошибка до handler» отличается от проверки внутри него. **Доказательство шага:** воспроизводимый набор из пяти запросов и исчезающий/появляющийся маркер. **Не вводить:** новые CRUD-маршруты, ручной `422`, custom validators, общий exception handler. **Мост:** проверенный вход нельзя автоматически использовать как полный ответ клиенту.

### 58. Разные схемы: create, read и update

**Вход и новый смысл.** Ученик уже знает, какие поля допустимы на входе. Теперь он отделяет *намерение клиента* от *полной записи сервера* и понимает, почему одна Pydantic-модель не может честно описывать оба направления. Это урок о контрактах, не о создании CRUD.

**Как написать теорию.** Начните с независимого примера заказа: покупатель задаёт состав, система выдаёт номер и статус. На нём объясните владельца поля и различие input/output. Затем перейдите к `TaskCreate` (`title`, `priority`), `TaskRead` (четыре поля) и полной `TaskUpdate` (`title`, `priority`, `is_done` обязательны, `id` не в body). Объясните `response_model` как проверку и публичное обещание формы ответа, но не как генератор отсутствующих данных. Если временный POST возвращает только входные поля, `TaskRead` на нём преждевременна: это ошибка ответа сервера, а не ожидаемый `422` на неверный запрос. Отдельно обсудите, что произойдёт с лишним клиентским `id`: наблюдаемое поведение Pydantic нужно зафиксировать; даже если поле игнорируется, клиент не получает власть над серверным идентификатором. `TaskPatch` пока назовите будущим отдельным контрактом, не смешивая её с полным PUT. Production-мотив: изменение внутренней модели не должно незаметно ломать ответ внешнему клиенту.

**Интерактивы.** Попросите распределить поля между request и response; предсказать результат `response_model=TaskRead` на нынешнем POST; отличить полную замену с обязательным `is_done` от частичного изменения без этого поля; по показанному OpenAPI определить, почему неиспользуемая `TaskUpdate` там пока не видна.

**Как построить ручную практику.** Четыре отдельные карточки:

1. Перенести известную `TaskCreate` в `app/schemas.py`, сохранить ограничения и обязательность `priority`, добавить полную `TaskUpdate` и `TaskRead`. Результат проверяется импортом моделей; ни одного второго набора схем в `main.py`.
2. Подключить `list[TaskRead]` к существующему `GET /tasks`, которому уже доступны четыре поля. Проверить форму реального ответа и `/docs`.
3. Оставить временный POST с `response_model=TaskCreate` и статусом `200`. Проверить, что он возвращает только вход и не создаёт `id`. Не предлагать `TaskRead`/`201` до интеграции 63.
4. Отправить body с лишним `id`, описать фактический исход и принятую политику лишних полей в `docs/api-contract.md`; отдельно зафиксировать будущие направления `TaskUpdate` и `TaskPatch`. Не требовать увидеть `TaskUpdate` в OpenAPI без PUT-маршрута.

Подсказки должны возвращать к вопросу «кто прислал поле и кто его назначает?», а не выдавать три готовых класса. **Доказательство шага:** GET соответствует полной `TaskRead`, POST остаётся честным временным ответом, схемы не смешаны. **Не вводить:** генерацию `id`, добавление в список, PATCH-маршрут, финальную пакетную архитектуру. **Мост:** форма будущей записи определена; следующий шаг выясняет, как она появляется в памяти.

### 59. Хранилище в памяти и генерация идентификатора

**Вход и новый смысл.** Схемы определили форму, но ещё не ответили, где живут записи. Ученик впервые отделяет состояние задач от входного body и создаёт **одну полную запись** по правилам сервера. Это ещё не POST-маршрут проекта.

**Как написать теорию.** На независимом примере очереди заявок объясните состояние в памяти процесса: список живёт, пока жив процесс; перезапуск уничтожает его. Затем разберите, почему клиент не выбирает `id`, почему `len(tasks)+1` ошибается при пропусках и почему `max(id)+1` даёт следующий номер в этой учебной модели. Покажите разницу между созданием нового списка, копированием вложенных словарей и мутацией исходного списка; на простом примере дайте ученику самому заметить общий объект. Объясните, что `strip()` меняет представление заголовка и что после очистки строку надо считать недопустимой, если она пустая. Не приписывайте эту проверку одному лишь `Field` из предыдущего урока. В продакшене идентификатор и долговечность обычно обеспечивает БД; здесь память и `max+1` позволяют увидеть правило до появления SQLAlchemy.

**Интерактивы.** Предложите предсказать `next_id` для пустого списка и `id=2,7`; найти скрытую мутацию при добавлении в исходный `tasks`; сопоставить исходный и очищенный `title`; объяснить, что произойдёт после перезапуска процесса. Кейс из одних пробелов вынесите в отдельную проверку границы: предметное правило требует отклонения, но HTTP-ответ будет подключён позже.

**Как построить задачу в интерпретаторе.** В `given` явно дайте `solve(tasks, title, priority)`, четыре поля каждой исходной записи, допустимые `priority` и заголовок, непустой **после** `strip()`; объясните, что запрос уже прошёл соответствующие проверки. В `todo` попросите вернуть `created` и `items`: новый список копий, новый `id`, очищенный `title`, заданный `priority`, `is_done=False`. В `check` объявите пустую коллекцию, обычную последовательность, пропуск `id`, сохранность входного списка и его словарей. Отдельно покажите в теории, что при реальной интеграции заголовок из одних пробелов будет отвергнут **до** записи; не подсовывайте такой вход в автотест без согласованного возвращаемого результата ошибки. Подсказки: сначала источник `id`, затем отличие копии списка от копий записей, затем локальная проверка мутации. **Доказательство шага:** запись построена целиком и исходное состояние не изменилось. **Не вводить:** FastAPI imports, Response, JSON-файл, постоянный счётчик между запусками редактора. **Мост:** готовое правило создания становится входом для чтения того же состояния.

Пошаговая линия практики: (1) определить новое состояние, не трогая вход; (2) выбрать `id` по известному правилу и очистить допустимый заголовок; (3) собрать **полную** запись и вернуть её вместе с новым списком; (4) проверить пустой список, пропуск `id` и неизменность исходных объектов. Автор не вставляет эти действия готовыми строками кода в условие: ученик самостоятельно выбирает реализацию.

### 60. CRUD: создать, получить список и найти по id

**Вход и новый смысл.** Правило создания уже известно; поиск одного элемента разобран в 54. Новый вопрос: как получить **список и конкретную запись из одного состояния после создания**, не собрав три несовместимые версии данных. Урок связывает операции, а не заново изобретает выдачу `id`.

**Как написать теорию.** Возьмите независимый пример каталога билетов: после добавления запись должна быть видна и в списке, и по номеру. Объясните коллекцию и item как два чтения одного источника, порядок «создали → получили обновлённую коллекцию → нашли элемент», `None` как отсутствие в чистой функции и будущий перевод отсутствия в 404 на HTTP-границе. Покажите, почему list/get не должны менять состояние и почему возвращаемая копия защищает запись от изменения снаружи. Свяжите это с лабораторным поиском 54, но не повторяйте всю теорию path-параметров. Уточните: нынешний `GET /tasks` в проекте пока читает временные данные; совместное состояние create/list/get существует только внутри упражнения.

**Интерактивы.** Дайте trace со старым `id` и новым `id` и попросите предсказать найденную запись; предложите найти ошибку «get читает исходный список, а list — обновлённый»; попросите отличить `None` в доменной функции от HTTP 404; предложите проверить, затронул ли возврат копии исходную запись.

**Как построить задачу в интерпретаторе.** Сохраните сквозной результат `created`, `items`, `found`, но **не заставляйте ученика повторно писать** копирование, `max(id)+1` и `strip()` из 59. Дайте проверенную функцию создания как готовый helper в `starter_code` (без импорта из другого занятия) и обозначьте её в `given`; ученик вызывает её и реализует только согласованное чтение списка и поиск `lookup_id`. Переиспользуйте правило поиска 54 как знание, но решение чтения пусть ученик напишет сам. В `check` покажите поиск только что созданной записи, прежней записи, отсутствующего `id`, неизменность входа и независимость возвращённой копии. Одинаковая форма записи во всех кейсах обязательна. Подсказки ведут к вопросу «из какого списка ищем?», затем к копированию результата. **Доказательство шага:** create/list/get читают один итоговый набор и не меняют исходный. **Не вводить:** PUT, PATCH, DELETE, `HTTPException`, настоящий роутер. **Мост:** найденную запись далее можно изменять двумя принципиально разными способами.

Пошаговая линия практики: (1) получить новое состояние через **данный** helper создания; (2) сформировать чтение всей обновлённой коллекции; (3) найти `lookup_id` именно в ней; (4) сравнить поиск нового, старого и отсутствующего `id`, убедиться, что исходный список не изменился. Центральная проверка — единый источник истины, а не повторное вычисление `next_id`.

Если редактор проверяет элементы синтаксиса через `requirements`, перестройте и эти ограничения: от ученика больше нельзя требовать `strip`, вычисления `next_id` или `append`, выполненных внутри данного helper. Проверять нужно только новое чтение и согласованность результата.

### 61. PUT и PATCH: полная и частичная замена

**Вход и новый смысл.** Запись уже можно создать и найти. Теперь ученик должен различить два разных намерения: заменить все изменяемые поля или изменить только перечисленные. Повторно проектировать create/list/get не нужно.

**Как написать теорию.** Сначала на независимом примере карточки профиля объясните полную анкету и просьбу поменять только телефон. Затем покажите полный PUT через `TaskUpdate`: каждый раз нужны `title`, `priority`, `is_done`; `id` остаётся прежним. Для PATCH введите отдельную `TaskPatch`: отсутствующее поле сохраняется, переданное конкретное значение применяется. Разберите наглядно четыре случая `is_done`: поле отсутствует; передано `false`; передано `true`; передано `null`. В нынешнем учебном варианте `null` означает «не менять» и отбрасывается перед алгоритмом, а `false` обязательно остаётся командой. Нельзя проверять наличие через истинность значения — `false` тоже команда. Для границы Pydantic объясните, зачем перед передачей данных в алгоритм нужны `model_dump(exclude_unset=True, exclude_none=True)` и что каждый параметр исключает. Упомяните, что реальный PUT/PATCH будет добавлен только при интеграции, а сейчас алгоритм получает уже подготовленный словарь. В production политика `null` может быть другой, но здесь она должна быть одной и той же в схеме, примерах, тестах и HTTP-маршруте; гонки и версии ресурса не разбираются.

**Интерактивы.** Предложите предсказать результат PUT и PATCH для одной и той же полной записи; найти ошибку в `if payload.get("is_done")`; сравнить PATCH с `{}`, `{"is_done": null}` и `{"is_done": false}`; выбрать, какая схема отклонит неполное тело PUT. Используйте только четыре поля канонической задачи, без случайного `note` или `description`.

**Как построить задачу в интерпретаторе.** В `given` зафиксируйте `solve(task, method, payload)`: `task` уже существует, payload для PUT полный, для PATCH содержит ноль или больше разрешённых полей и уже прошёл входную проверку. В `todo` попросите вернуть новую полную запись: PUT собирает её из прежнего `id` и всех изменяемых полей нового тела; PATCH копирует исходную запись и применяет **только присутствующие ключи** подготовленного словаря. Заголовок при передаче очищается; пробельный заголовок не включайте в «валидный payload» автотеста без отдельного договора ошибки. `null` исключается на границе Pydantic до вызова чистого алгоритма, но его поведение проверяется в интерактиве и позднее в HTTP-тесте. В `check` укажите: полный PUT меняет все три изменяемых поля; неполный PUT не проходит схему на будущей HTTP-границе; PATCH одного поля сохраняет два других; PATCH с явным `false` действительно выключает `is_done`; пустой PATCH ничего не меняет; исходный словарь не мутирует. Не доказывайте различие через удаление несуществующего «старого поля `note`»: оно противоречит установленной форме задачи. Подсказки идут от вопроса «какие ключи присутствуют?» к проверке сохранности `id` и `false`. **Доказательство шага:** два обновления дают предсказуемо разные результаты из одного исходного состояния. **Не вводить:** БД, nested PATCH, optimistic locking, HTTP-декораторы. **Мост:** после обновления остаётся научиться удалять запись и не путать отсутствие с успешным удалением.

Пошаговая линия практики: (1) прочитать контракт полного и частичного payload; (2) для PUT собрать полную новую запись с прежним `id`; (3) для PATCH применить только присутствующие разрешённые ключи к копии; (4) сравнить исходную и обе новые записи, отдельно прогнать `false`, пустой PATCH и попытку неполного PUT на уровне схемы. Не дайте ученику ложный тест, который проходит только за счёт постороннего поля.

Неполный PUT и `null` проверяются у схемы/HTTP-границы, а не скрытым тестом чистой `solve`, которой по договору передают уже подготовленные данные. В автопроверке редактора оставьте только то, что реально можно проверить по её входу и результату.

### 62. DELETE, 204 и HTTPException

**Вход и новый смысл.** Ученик умеет создать, прочитать и изменить запись. Удаление замыкает жизненный цикл: после успешного удаления тот же `id` уже не находится. Впервые особенно заметна разница между *предметным результатом* («удалено»/«не найдено») и *HTTP-формой ответа*.

**Как написать теорию.** Через независимый пример списка бронирований объясните удаление выбранного элемента, а не очистку всего списка. Разберите три состояния: корректный существующий `id` — удаляем один item; корректный, но отсутствующий `id` — ничего не меняем и сообщаем об отсутствии; неразбираемый path `id` — вход отклоняет FastAPI до поиска. Покажите, почему успешный HTTP DELETE отвечает `204` **без тела**, а отсутствие переводится в `404`; это не то же самое, что непредвиденная ошибка сервера. Объясните, что общий принцип поиска/отсутствия позволяет GET, PUT, PATCH и DELETE согласованно выдавать 404, но `get_task_or_404` — помощник будущего HTTP-слоя, не функция чистого storage. Для учебного алгоритма остаются копии списка и записей. В production удаление может иметь дополнительные правила, но soft delete и аудит не входят в этот этап.

**Интерактивы.** Предскажите список после удаления среднего элемента; различите 404 и 422 для двух `id`; найдите ошибку в ответе `204` с JSON body; определите, почему повторный DELETE той же задачи не может снова означать «запись найдена» в утверждённом договоре.

**Как построить задачу в интерпретаторе.** `solve(tasks, task_id)` получает коллекцию из **полных четырёхпольных** записей. Внутри отделите создание `remaining` и флага `deleted` от учебного сопоставления с `status`. Если сохраняете текущий формат `{"deleted", "status", "items"}`, прямо скажите в `given`, что `status` — метка ожидаемого будущего HTTP-исхода **в проверке**, а не поле хранилища или body ответа 204. В `todo` попросите вернуть копии оставшихся задач и один из исходов; в `check` укажите удаление существующего `id`, отсутствующий `id`, пустой список, сохранность исходного списка/словарей и отсутствие удалённого `id` в `items`. Не используйте двухпольные тестовые записи, которых в этом API не бывает. Подсказки ведут от выбора записи к проверке того, что исходные данные не изменились. **Доказательство шага:** после успеха задача не находится, при 404 коллекция прежняя, а в публичном API 204 не несёт body. **Не вводить:** FastAPI import в алгоритме, `HTTPException` в storage, БД или отдельную систему ошибок. **Мост:** следующий блок переносит эту цепочку в настоящий HTTP API и только затем раскладывает по файлам.

Пошаговая линия практики: (1) найти целевой `id`, не мутируя вход; (2) сформировать список остальных записей; (3) отдельно определить предметный исход «удалено»/«не найдено» и его учебный HTTP-код; (4) проверить успешный, повторный и отсутствующий `id`, включая пустую коллекцию. После упражнения в теории ещё раз отделите возвращённый словарь тренажёра от настоящего HTTP-ответа `204` без тела.

Повторный DELETE здесь означает **второй вызов с `items` первого результата** в локальном эксперименте или интерактиве; он не возникает сам собой между независимыми запусками редактора. Скрытые тесты одиночной `solve` проверяют найденный, отсутствующий и пустой случаи.

## Критерии готовности концепта и будущего блока

Концепт годится для написания занятий, если для каждого из них автор может ответить без догадок: что уже существует; какое **одно новое поведение** ученик осваивает; на каком независимом примере оно объяснено; какой результат и крайний случай проверяет практика; что остаётся для следующего занятия. В любом ученическом упражнении все новые методы и понятия сначала получают объяснение, а полный ответ остаётся в подсказке/разборе, не в теории.

Сам блок будет готов только после отдельной переработки теории и практики, когда ученик сможет объяснить путь `422 → схемы → создание → чтение → PUT/PATCH → DELETE`, различить реальные возможности проекта и тренажёр, показать неизменность исходных данных, отличить 404 от 422 и 204 от 200 с body, а также передать согласованные алгоритмы в контрольную точку 63 без повторного проектирования CRUD. Пока обновлён **только этот авторский концепт**, не сами занятия.
