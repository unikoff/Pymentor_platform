# C2.2.5 — локальная PostgreSQL и проверка восстановления

Задача: [PYM-189](https://platformpy.atlassian.net/browse/PYM-189). Эта инструкция предназначена только для **новой локальной базы с синтетическими данными**. Не подключайте к ней рабочую SQLite, действующий сервер или настоящих пользователей.

## Что проверено локально 05.11.2026

- PostgreSQL 16.15 запущена в отдельных контейнерах и томах Docker Desktop; подключения только на `127.0.0.1:57152`.
- Чистые миграции Alembic применены и повторно запущены без изменений; ревизия `c216_import_marker`. Роль миграций и отдельная роль приложения не обладают правами администратора PostgreSQL. Проверено, что приложение не может создавать объекты в `public` или изменять `alembic_version`.
- В отдельном ручном прогоне синтетическая резервная копия восстановлена в новый том при остановленном источнике. Сравнены структура, ограничения и данные всех 17 таблиц; после восстановления прошли вход, календарь и каталог. Новый режим PostgreSQL/Redis также прошёл пользовательские сценарии с отдельной ролью приложения.
- Контрольные суммы схемы и синтетического содержимого исходного экземпляра сохранены в `evidence/c225-synthetic-source-hashes.json`; совпадение восстановленного экземпляра проверено до smoke-тестов, которые добавляют тестовые сессии.
- Повторяемый скрипт `scripts/c225_local_pg_lab.py` отдельно прошёл создание, миграцию, резервирование и восстановление с проверкой тестовых данных и ограничений роли. В процессе проверена возможность безопасно продолжить восстановление после остановки источника при отсутствии целевого тома. Частичные тестовые тома сохранены для диагностики.

Это локальная проверка, не развёртывание staging/production и не проверка производительности. Новый режим остаётся тестовым; существующий режим с SQLite сохраняется.

## Повторение в PowerShell

Нужны запущенный Docker Desktop, установленный Python с зависимостями `requirements-dual-local.txt` и доступный локально закреплённый в скрипте образ PostgreSQL. Откройте PowerShell в корне этой рабочей копии. Порт `57152` должен быть свободен: скрипт остановится, если он занят, и не будет трогать чужой контейнер.

Задайте новый идентификатор каждого опыта — 8–48 латинских букв, цифр и дефисов. Например:

```powershell
$RunId = 'local-example-001'
python scripts/c225_local_pg_lab.py create $RunId
python scripts/c225_local_pg_lab.py migrate $RunId
python scripts/c225_local_pg_lab.py backup $RunId
python scripts/c225_local_pg_lab.py restore $RunId
python scripts/c225_local_pg_lab.py status $RunId
```

`create` создаёт отдельные том и контейнер, пользователей миграции и приложения. `migrate` применяет схему. `backup` записывает архив вне репозитория. `restore` сначала останавливает только созданный этим запуском источник и создаёт другой том; он не восстанавливает копию поверх исходника. `status` показывает состояние, не изменяя его. Команды выполняются по очереди; при ошибке остановитесь и проверьте журнал, не используйте другие тома и не запускайте те же мутации вслепую. Если журнал остался на `restore-stopping-source`, повторная команда `restore` разрешена только после проверки, что источник остановлен и целевые ресурсы не созданы: скрипт дополнительно проверяет эти условия.

Скрипт сохраняет секреты и журнал в `%LOCALAPPDATA%\Pymentor\c225\<RunId>` и создаёт ограничительные ACL для каталога на Windows. Не прикладывайте секреты, архив и полные подключения к отчётам. Файлы окружения и переменные доступны процессам с соответствующими правами ОС; это не промышленное хранилище секретов. Контейнеры и тома автоматически не удаляются.

Без дополнительных синтетических записей пример выше резервирует пустую схему. Проверка реальных данных приложения здесь не предусмотрена. Для полноценной приёмки отдельно сравните данные, ограничения и работу приложения на изолированной тестовой копии, как в описанном локальном прогоне.

## Будущий staging и VPS

Локальный loopback работает без TLS. Для staging потребуется отдельное хранилище секретов, TLS с проверкой сертификата и CA, ограничения сети и отдельные роли/базы Core и Analytics. На VPS резервные копии должны храниться вне узла, с шифрованием, мониторингом и периодическим проверенным восстановлением. PITR требует отдельной настройки WAL и базовых копий. Срок хранения backup и правила удаления данных ещё не определены владельцем и оставлены в [PYM-426](https://platformpy.atlassian.net/browse/PYM-426); месячный срок для готовых решений к backup не относится.
