# PYM-191: локальный проект повторного переноса сессий

Статус: **в работе**. Сквозной synthetic прогон уже перенёс две SQL-сессии и проверил их через Redis и PostgreSQL, но существующий `import_legacy_sessions` при неизвестном результате SQL commit не умеет доказать, что найденные строки относятся к той же операции. Повтор по одному `session_import_markers.user_id` небезопасен: маркер используется и другими операциями, а при удалении пользователя удаляется каскадом.

## Граница синтетического эксперимента

Цель — отдельная одноразовая lab с зафиксированным снимком, подтверждённым отсутствием обычных writers и работающих consumers, отключённым login app-role и изолированным префиксом Redis. Источник остаётся read-only. Никакого подключения к пользовательской SQLite или серверу; при сомнительном состоянии lab остаётся на карантине.

Персональные значения и токены не выводить в отчёты и не сохранять в контрольном marker. Маркер операции должен содержать только идентичность синтетического snapshot/версии и идентификатор субъекта, а его запись, фактические session rows и текущий `session_import_markers` — фиксироваться одной SQL-транзакцией. Права app-role на изменение контрольного marker должны быть исключены и проверены отдельно.

## Предлагаемое решение неизвестного SQL commit

Под SQL-блокировкой пользователя заново проверить marker и **все** ожидаемые поля session rows:

- marker отсутствует, SQL-сессии отсутствуют и per-user marker ещё не consumed: допустима подготовка новой операции;
- marker соответствует тому же snapshot/операции, все ожидаемые строки идентичны и per-user marker присутствует: SQL-часть уже выполнена;
- любой другой набор, несовпадение marker, строки без marker либо consumed без доказательства операции: остановка без перезаписи.

После неопределённого commit сначала дождаться прекращения старого SQL backend, затем перечитать состояние под теми же блокировками. Retry допустим только после доказательства полного rollback либо точного совпадения уже зафиксированной операции. Один marker без сверки строк не является доказательством. Отдельные проверки TTL и полноты источника обязательны повторно на границе операции; чистый compatibility guard их сам не обеспечивает.

Redis не участвует в SQL-транзакции. Перед SQL записью следует подготовить и проверить gates вне write lock; после доказанной SQL-части — проверить их наличие. Возможность безопасного добавления отсутствующей проекции ограничена замороженной тестовой миграцией и должна учитывать logout, истечение, потерю Redis и отсутствие внешнего отзыва. Общую автоматическую реконструкцию в работающей системе этот план не разрешает. Stale Redis key без SQL-строки не должен авторизовать.

## Остающиеся границы

- Текущий legacy SQL проверяет наличие токена без проверки возраста; новый experimental путь применяет 30 дней и максимум три сессии. При неподтверждённом сроке, несовместимом возрасте или большем количестве нужно остановиться, а не молча отбросить записи.
- Numeric user ID может быть повторно использован после удаления аккаунта. До согласованного жизненного идентификатора и журнала удаления PYM-426 нельзя считать контрольный marker защитой от восстановления удалённого субъекта или повторного использования ID.
- Этот протокол не исправляет PYM-435: login при потере подтверждения commit может вытеснить прежний сеанс до доставки cookie. Также остаётся окно исчезновения Redis gate после предварительной проверки и до SQL commit.
- Копирование outbox не даёт гарантии отсутствия повторной доставки. Все не-`sent` записи консервативно требуют сверки; текущий аудит не управляет реальными workers и не подтверждает доставку.

## Доказательства, которые ещё нужны

Отказы до commit, после фактического commit с потерянным ответом и при исчезновении Redis; доказанный rollback и успешный commit должны классифицироваться по marker и каждой строке. Проверить чужой/отсутствующий marker, подмену одного поля, удаление и повторный вход, параллельные операции, TTL на границе и cleanup только своего Redis-префикса. На завершение требуется фактический PostgreSQL/Redis и отдельное ревью; unit-тестов и фиктивного транспорта недостаточно.

На отдельной замороженной synthetic lab `scripts/c232_session_gate_recovery_probe.py` удалил **один собственный существовавший** Redis gate, подтвердил отказ аутентификации, сверил SQL-сессию и marker, выполнил `reconcile_user`, повторно сверил SQL и подтвердил аутентификацию. В конце известные ключи тестового префикса удалены и проверены, lab остановлена. В этом опыте была одна сессия на пользователя и обычные writers были отключены; это не доказывает безопасность восстановления после Redis-only отзыва или при конкурирующих операциях и не закрывает PYM-435.

Дополнительный сценарий PYM-435: если Redis перестаёт отвечать **после** подготовки ключа четвёртого входа, SQL-транзакция всё ещё может вытеснить старую сессию, хотя новой во время сбоя воспользоваться нельзя. `backend/tests/test_c435_redis_after_prepare.py` воспроизвёл это на синтетических PostgreSQL и Redis как ожидаемую ошибку (`xfail`); четыре других адресных сценария подтвердили сохранение прежних сессий при отказе до подготовки и потере ответа подготовки. Требование пользователя сохранять прежние сеансы при неудавшемся входе этим полностью не выполнено; миграцию и выпуск нового режима считать безопасными нельзя до исправления и повторной проверки. Тест имитировал сбой ответов через подмену адаптера, не останавливая Redis.
