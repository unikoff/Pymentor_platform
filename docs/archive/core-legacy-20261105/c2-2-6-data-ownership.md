# PYM-207 / C2.2.6 — фактическая матрица владения данными

Локальная сверка исходников и исторического PostgreSQL baseline от 2026-11-05. Это описание текущего кода, а не утверждение сроков хранения, backup-политики или уже работающей интеграции с Analytics. В обычном запуске legacy и новый режим изолированы; развернутого Analytics нет. Jira: [PYM-207](https://platformpy.atlassian.net/browse/PYM-207).

## Границы и call/data flow

- Legacy API использует ORM-модели в `backend/db/models.py`; учётные записи, посещения, прогресс и бронирования читаются/пишутся существующими роутерами и сервисами. SQLAlchemy `Base` объявлен в `backend/db/engine.py`.
- Календарный поток: `backend/routers/accounts/activity.py:12-108` сохраняет максимум одну строку на пользователя и локальную дату (`uq_user_activity_day`); `:111-155` вычисляет streak из этих дат и недельный счетчик завершений из `user_lesson_progress`. Admin overview независимо агрегирует `user_activity_days` и `user_lesson_progress` в `backend/routers/admin/service.py:204-262,352-416`.
- Прогресс — Core state: `backend/routers/courses/progress.py:46-76,79-163` читает/записывает completion урока и последнюю завершенную revision задачи; каталоги/lesson response потребляют их в `backend/routers/courses/service.py:77-188,224-240`. Содержимое отправленного кода в этих моделях не хранится.
- Удаление в текущем admin-потоке — одна SQL-транзакция: `backend/routers/admin/service.py:498-534` снимает student_id с занятых слотов, удаляет Session, activity, lesson/task progress и quota, затем User. Здесь нет аналитического consumer, tombstone или consumer acknowledgment.
- В новом экспериментальном auth-потоке SQL `sessions` является авторитетным, Redis — проекцией/фильтром. Login сначала подготавливает отдельный ключ Redis, затем после подтверждения выполняет короткую SQL-транзакцию активации; сам ключ без SQL-сессии доступа не даёт. `reconcile` восстанавливает проекцию из SQL; при неудачной подготовке прежние SQL-сессии сохраняются. Маркер `session_import_markers` предотвращает повторный импорт отозванных legacy-сессий; подготовленный ключ после ошибки может сохраняться до TTL. Подробности и ограничения, включая неизвестный исход SQL commit: `c2-2-4-session-protocol.md`. Это локальный тестовый режим, не доказательство общего dual-write между legacy и новым стеком.

### Политика доступа для будущего Analytics

PYM-207 задаёт Core как единственного authoritative writer для перечисленных текущих наборов. Analytics не получает прямой SQL/FK доступ к Core; будущая доставка — отдельный versioned allowlist contract и отдельные схемы/права, пока не реализованные. Не передавать пароли/hash, bearer sessions/digests, secrets, submitted code, email/username, chat IDs или необработанные payload без отдельного решения о необходимости. Для агрегатов, откуда удаляется пользовательский вклад, требуется пересчёт/исключение вклада, а не сохранение индивидуальной строки под видом агрегата.

## Удаление, доставка и восстановление: реальные инварианты и разрывы

1. Нормальный account-delete путь в текущем коде блокирует удаляемого user row на PostgreSQL, освобождает его slots и удаляет его session/activity/progress/quota в одном commit. Следовательно, calendar, learner progress и повторное бронирование не должны видеть эту user-linked запись после успешного commit. Источник: `backend/routers/admin/service.py:507-532`.
2. Частичный отказ: будущий consumer может уже принять событие account deletion, затем import/replay старого completion/activity event или восстановление старого backup может вернуть личный вклад. Текущий код не имеет consumer acknowledgment, deletion marker/tombstone, replay fence либо restore reconciliation; в текущем runtime Analytics вообще нет. Поэтому инвариант «не воскресить удалённые данные» пока не доказан и является обязательным M2 контрактным gate, а не свойством текущей системы.
3. Пропажа Redis при auth delete/revoke: SQL и Redis не являются одной транзакцией. В auth prototype SQL считается authoritative и authenticate дополнительно проверяет SQL; logout удаляет SQL до попытки revoke Redis (`backend/identity/async_sessions.py:237-259`). Account-delete flow в `admin/service.py` удаляет SQL session rows, но прямой вызов Redis reconcile/revoke не найден. Проверить/зафиксировать поведение нового режима до его включения в сценарий удаления; нельзя выводить это из обычного logout.
4. Outbox retry/recovery уже имеет локальный механизм, но только для Telegram delivery. Worker хранит pending/processing state и чистит sent rows старше 30 дней (`backend/notifications/delivery.py:174-229,248-350,539-562`). Это не решает будущую Analytics доставку, account deletion propagation или backup restore.
5. `booking_notification_outbox` хранит снимки username/email и не содержит надежного user_id; `delete_user` не очищает эти записи. В изолированной SQLite в памяти удаление синтетического пользователя оставило одну созданную для него outbox-строку. Это подтверждает кодовый разрыв, но не доказывает наличие таких строк в реальных базах. Нужен отдельный совместимый план: определить личность событий без неоднозначного удаления по одному email, обрабатывать старые строки, транзакционно согласовать удаление с claim/lease worker и учесть уже отправленные сообщения Telegram. Запрещается автоматически удалять исторические записи до сверки и решения о безопасном восстановлении.

## Что проверено / что не проверено

- Прочитаны фактические модели, baseline `c222_initial_pg`, session marker revision `c216`, календарный/progress/admin/booking/auth/notification paths и PYM-207 с текущим описанием и связями.
- Проверен статический call/data flow и текст миграций; документ не предполагает отсутствующие `attempts`, raw event, Analytics или deletion tables.
- Выполнен синтетический сценарий account deletion в SQLite `:memory:`: user удалён, snapshot в outbox остался. Существующие проверки auth/admin/progress выполнены отдельно. Миграции и реальные БД не изменялись; Analytics не развернут, поэтому delivery/parity не подтверждены фактическим consumer.
- Точные retention для backup/tombstones/logs намеренно оставлены открытыми с владельцами и M2 gate. Аналитическая схема/consumer контракт и размер/нагрузка не предоставлены, поэтому их физическую модель и масштаб нельзя проверить.
