# Инфраструктура массовых stage Pymentor

**Актуальная процедура скорости/качества:** [итог и проверки](speed-quality-20261026/ACCEPTANCE.md), [аудит задержек](speed-quality-20261026/AUDIT.md). Авторы делают по одному уроку; общая интеграция и общие checks выполняются на итоговом наборе один раз. LOCAL_READY не равен COMPLETE. Процедура — в актуальном BATCH_WORKFLOW, прежние режимы ниже исторические.

**Уточнение назначения:** один Web-агент получает ровно одно занятие и весь его stage; личные очереди из нескольких занятий отменены. Общую очередь ведёт только исходный Coordinator, запускающий отдельных агентов в пределах лимита. Исправления одного занятия можно вернуть прежнему владельцу.

**Актуальное обновление 26.10.2026:** [итог и проверки](upgrade-20261026/ACCEPTANCE.md). Используются native Web-исполнители, централизованная effective policy, адресный REWORK и проверка содержательных улучшений. Ниже сохранена история подготовки; прежний GO_TO_PILOT не подтверждает завершение реально запущенного Stage 3.

**Текущий режим — доверительная лёгкая оркестрация:** [итог обновления](light-orchestration/ACCEPTANCE.md). Исходный чат управляет прогоном до конца; постоянные Web-исполнители сами проходят очереди, проверяют и исправляют результат. Оркестратор принимает короткие отчёты и обрабатывает исключения. [Сборщик задания](../../scripts/build_dispatch.py) передаёт инструкции программно без загрузки полного payload в контекст оркестратора. Этот режим заменяет прежние требования повторной содержательной приёмки и тяжёлой отчётности в исходном чате.

**Последняя проверка перед пилотом, 25.10.2026:** [GO_TO_PILOT для stage 2/3](preflight-20261025/READY.md). Целевой оркестратор GPT-6 Luna / xhigh и рабочий GPT-6 Sol Web / high подтверждены каталогом; согласованы глобальный предел пяти активных Web-запросов, восстановление и конечная приёмка. Учебные stage по-прежнему NOT_RUN.

Создано 25.10.2026 по запросу подготовить последующее делегирование. Учебные stage и реальные занятия в ходе настройки не запускались.

Оба проектных профиля фиксируют `model = "chatgpt-web/gpt-6-sol"` и `model_reasoning_effort = "high"`. Общие роли `materials`, `check` и skill `methodic-run` сохранены. Глобальная конфигурация не заменялась. Пять параллельных занятий используют пять экземпляров нужного профиля; новый профиль на каждое занятие не создаётся.

Подробная процедура остаётся в [BATCH_WORKFLOW.md](../make%20les%20stage/BATCH_WORKFLOW.md), учебные требования — в методичках [stage 2](../make%20les%20stage/2%20stage/README.md) и [stage 3](../make%20les%20stage/3%20stage/README.md). Skill и профили ссылаются на эти источники и не создают вторую полную копию методик.

## Будущий запуск

В том же чате, где пользователь запускает прогон, вызови `$pymentor-stage-batch` и укажи **один stage**, курс/главу/блоки/номера, источники, разрешённые пути и при продолжении журнал. Этот чат остаётся единственным оркестратором; создавать или форкать другой чат для переноса управления автоматически нельзя. Готовые промпты находятся в README соответствующего stage. Само наличие этих файлов не начинает обработку. Если Skill не обнаружен, прочитай его инструкции поддерживаемым способом в текущем контексте.

Перед делегированием оркестратор проверяет фактический каталог и принятые настройки модели. Нативные роли используют TOML-профили; отдельные пользовательские Web-чаты создаются по прямому запросу с явными `model`/`thinking` и передачей фактических инструкций профиля. Загрузка текста роли не называется её регистрацией. Для нативного `spawn_agent` параметр усилия берётся из живой схемы (`reasoning_effort`), а не переносится из TOML вслепую.

Сейчас подключены **stage 2 и stage 3**. Остальные stage подключаются позже явным соответствием «stage → профиль → источники/проходы → конечная приёмка». Skill не присваивает им правила PLAN/MAIN автоматически и не запускает все стадии цепочкой.

## Проверки и пределы подтверждения

- [DISCOVERY.json](DISCOVERY.json): фактический read-only запрос Codex CLI 0.160.0 `skills/list` обнаружил `pymentor-stage-batch` как включённый Skill со scope `repo`, без ошибок его загрузки. Не вызывались `thread/start`, `turn/start` или модель.
- Два TOML разобраны Python `tomllib`; проверены имена, обязательные поля, точные Web/High и реальные root-relative источники.
- Штатный skill-валидатор был вызван, но в доступных Python отсутствует PyYAML. Выполнены альтернативные структурные проверки и фактическое обнаружение Skill клиентом; установка зависимостей не выполнялась.
- Файлы ролей созданы в поддерживаемом проектном каталоге `.codex/agents/`. Их появление в живом каталоге текущего чата и реальный запуск новых профилей **не подтверждены**; `config/read` не является списком standalone-ролей. Проверка рабочего запуска относится к будущей задаче, когда будет задан учебный массив.
- [Независимая приёмка](ACCEPTANCE.md) разделяет структуру файлов, анализ сценариев и реальное исполнение; учебная эффективность и параллельный продуктовый прогон не измерялись.

Документальная и структурная приёмка завершена с PASS. [Окончательная сверка](VALIDATION.json) подтверждает совпадение SHA-256 трёх артефактов с независимым отчётом и отсутствие отсутствующих локальных адресатов. Это не проверка фактического запуска новых рабочих профилей.

Отчёты авторов: [Skill](REPORT_SKILL.md), [PLAN](REPORT_PLAN_AGENT.md), [MAIN](REPORT_LESSON_AGENT.md). В репозитории сохранены итоговые отчёты и контрольные суммы подготовки. Учебные stage не запускались.
