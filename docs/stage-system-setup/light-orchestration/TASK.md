# Задание: снизить расход контекста оркестратора

Пользователь сообщил: оркестратор израсходовал около 25% на первые пять планов. Это наблюдение пользователя, не наша телеметрия. Нужно изменить действующие инструкции, а не обещать измеренное сокращение. Учебные stage сейчас не запускать.

## Новый режим по умолчанию

- Дополнение пользователя: чат, в котором запущен прогон, и есть единственный оркестратор до конца. Не создавать и не форкать отдельный чат-оркестратор, не переносить управление в другой чат автоматически. Выбор/смена модели выполняется в том же чате доступным способом; фиксировать фактическую настройку, не выдавать желаемую за действующую. Недоступность Skill/профиля решается поддерживаемым явным чтением инструкций в текущем контексте, а не обязательным созданием нового оркестратора. Ведущий Web-исполнитель из пятёрки — только ограниченный подготовитель/интегратор, не второй оркестратор и не создатель чатов. Другой оркестратор возможен только по отдельному прямому запросу пользователя.

- Luna/xhigh — диспетчер. Основу работы выполняет GPT-6 Sol Web / High. Предметная работа, чтение источников, подготовка полной описи N и очередей, P1–P4/M1–M5, проверки и исправления делегированы Web.
- Один ведущий Web-исполнитель из тех же пяти готовит опись и очереди, затем работает как обычный исполнитель. В конце ему же поручается необходимая сверка массива. Новых агентов сам он не создаёт.
- До пяти постоянных Web-контекстов; каждый получает очередь, выполняет по одному занятию последовательно и сам берёт следующее независимое назначенное занятие. Не создавать новый чат и не повторять bootstrap на каждый урок. Глобально максимум пять активных Web/browser turns, включая проверяющих и интеграторов.
- Убрать обязательный барьер между пятёрками, если его не требуют зависимости. Никакой работы за пределами исходного массива. Заблокированное занятие остаётся в N; независимая работа продолжается.
- Полная автономия в разрешённой области. Не согласовывать каждый проход и исправление. Один физический общий файл имеет одного владельца на рабочую порцию; остальные готовят дельты. Оркестратор передаёт их без повторного содержательного анализа. Не расширять права внешней переписки.
- Оркестратор не читает промежуточные файлы, диалоги и комментарии, пока исполнитель работает. Ожидание по курсорам; в его контекст возвращать лишь завершение, ошибку или запрос вмешательства. Не отправлять работающему чату повторные «статус?» и «продолжай».
- По умолчанию достаточно итогового отчёта ответственного Web: охват, статус, выходные пути/ключи, обязательные проверки, остатки. Оркестратор сверяет эти поля и N/N, принимает результат, не воспроизводя P4/M5 и не перечитывая каждый MD/TSX. Углубление только при конкретном противоречии, сбое, недостающей обязательной проверке или прямом запросе пользователя; также делегируется Web. Автоматический второй проверяющий на каждый урок запрещён как обычный режим.
- Качество не снижать: PLAN_ACCEPTED только после P4; COMPLETE stage 3 — M5 и четыре фактических PASS. Выполняет и подтверждает их Web. Непроверенное не становится PASS.
- Настройки/доступы проверять один раз на запуск/контекст, повторять при реальной ошибке или изменении. Принятые инструментом явные model/high и ID — свидетельство настройки; не нужны повторные каталоги для каждого урока.
- Один компактный журнал: очередь → исполнитель → выполнено/блокер → результаты/проверки. Не требовать отдельные отчёты и SHA для каждого прохода. Fingerprint нужен для конфликта, восстановления или технической привязки доказательств, а не как ритуал после каждого действия.
- Обычный отчёт исполнителя после назначенной порции (например до пяти уроков), конца очереди или блокера: не более 150 слов плюс компактная таблица при необходимости. Корневой чат получает сводки, не сырые логи и полный bootstrap.
- Нужные AGENTS/роль/skill передаются один раз на постоянный контекст поддерживаемым вложением или полным содержимым; учебные методички исполнитель читает сам. При программной передаче не выводить большой payload в контекст оркестратора.

## Разделение записи

- CORE: `.agents/skills/pymentor-stage-batch/`, `docs/make les stage/{AGENTS.md,BATCH_WORKFLOW.md,RUN_TEMPLATE.md}`, собственный `CORE.md` здесь.
- PLAN: `.codex/agents/pymentor-plan-worker.toml`, `docs/make les stage/2 stage/{AGENTS.md,README.md}`, собственный `PLAN.md` здесь.
- MAIN: `.codex/agents/pymentor-lesson-worker.toml`, `docs/make les stage/3 stage/{AGENTS.md,README.md}`, собственный `MAIN.md` здесь.
- Позднее существующий RUNTIME выполняет одну конечную проверку согласованности, только после трёх результатов, без промежуточного надзора. Пишет `ACCEPTANCE.md` здесь.

Не трогать девять методичек, реальные планы/уроки, backend/frontend, глобальные конфиги и старые отчёты. Сохранить пользовательские правки. При недоступной записи protected-пути подготовить точный pending здесь с исходным SHA, не обходить ограничения.

## Полезный инструмент CORE

Один небольшой стандартнобиблиотечный `scripts/build_dispatch.py`: принимает stage, файл назначения очереди и выходной JSON; читает проектный TOML через tomllib; проверяет точный Web/high и непустое назначение; собирает `{model,thinking,prompt}` из фактических инструкций профиля и назначения. Опционально принимает путь выбранного worker-skill. Не вызывает модель, не создаёт чаты, не добавляет полномочий. Не пакует весь Skill оркестратора каждому worker. Родитель читает JSON инструментом и передаёт prompt программно в create_thread, не печатая payload. Проверить нормальную сборку обоих stage и отрицательные случаи на изолированных fixtures здесь, без установки зависимостей и настоящих уроков. Новая app-схема или крупный harness не нужны.

Все авторы: перечитать актуальные исходники, точечно согласовать их с новым режимом. Существующие skill-creator/OpenAI Docs и role-инструкции уже были переданы в исходном контексте ваших чатов; недостающее получить из доступного живого каталога. Итог каждого — до 150 слов, фактически выполненные проверки, конкретные остатки, без обещания процента экономии.
