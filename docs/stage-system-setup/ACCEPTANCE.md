## SCENARIO_REVIEW

Каждый сценарий проверен **по тексту фактических инструкций**, без создания учебных файлов, исполнителей и пользовательских чатов. Уровень свидетельства во всех пунктах ниже — `VERIFIED: documented decision`, `NOT_TESTED: runtime outcome`.

### A. Stage 2: семь паспортных занятий главы, включая строковые подномера, часть MD отсутствует

**Ожидаемое решение:** восстановить все семь паспортных идентичностей (основные и обязательные подзанятия), номера вроде `13` и `13.1` хранить строками, отсутствующие MD включить в `N_expected=7` и создать в разрешённых целевых путях во время **будущего** санкционированного запуска. Один журнал, первая волна до пяти разных занятий, вторая до двух; A→B и зависимые действия синхронизируются по готовности. Каждый MD проходит P1→P4 у одного владельца и учитывается в `N_accepted` только после предметного `PLAN_ACCEPTED`. Если не хватает обязательного паспорта или диапазона нового паспорта, конкретная строка остаётся непринятой; N не сокращается, независимая работа продолжается. Stage 3 автоматически не начинается.

**Противоречия:** между проверенными инструкциями по этому сценарию не обнаружены. **Выход:** `7/7 STAGE_COMPLETE` только при семи действительных P4; иначе `STAGE_INCOMPLETE` с каждой причиной и версией. Это прогноз решения, не фактически созданные 7 MD.

### B. Stage 3: шесть занятий с принятыми планами; две практики в одном `manual.py`; браузер недоступен, runner доступен

**Ожидаемое решение:** `N_expected=6`, волны до пяти и затем одно занятие с учётом зависимостей. Каждое проходит M1→M5; для физического `manual.py` назначен **один** текущий владелец записи и очередь двух дельт, с перечитыванием версии перед интеграцией и повторной проверкой после неё. Выполняются доступные проверки backend, frontend, API/выдачи и runner. Недоступность браузера оставляет уровень «открытая страница/runner», включая ширины и визуальные состояния, в `НЕ ПРОВЕРЕНО`, даже если runner дал PASS по задачам. Затронутые уроки — `PARTIAL`/`BLOCKED` по конкретной зависимости; общий итог — `STAGE_INCOMPLETE`, если нет четырёх актуальных PASS для **каждого** урока.

**Противоречия:** нет разрешения подменять проверку страницы сборкой или одним runner; оснований объявить `6/6 COMPLETE` нет. **Выход:** журнал интеграции и непроверенных уровней, точное условие продолжения после восстановления браузера.

### C. Пользователь просит только улучшить README stage 2

**Ожидаемое решение:** редактирование соответствующего README в заданном объёме, без паспортной описи, диспетчеризации, журнала учебного запуска, MD и делегатов. `description` Skill прямо исключает редактирование методичек, а stage 2 `AGENTS.md` не считает редактирование инструкций началом создания планов.

**Противоречия:** не выявлены. **Выход:** исправленный README и обычная проверка его ссылок; статус `STAGE_COMPLETE` неприменим.

### D. Прерванный запуск: журнал сообщает о пяти выданных исполнителях; часть активна, в общем файле чужая правка

**Ожидаемое решение:** открыть прежний журнал, выяснить **реальное** состояние пяти заданий и активных ID, проверить текущий diff и SHA-256 общего файла. До установления исхода предыдущей выдачи **не создавать дубликатов**. Установить единственного владельца записи и очередь, сохранить чужую правку, адаптировать ещё не интегрированные дельты к новой версии, проверить результат после сохранения; потерявшие актуальность подтверждения повторить только в затронутой части. Продолжать с первого действительно неполного прохода, сохраняя принятые работы и N.

**Противоречия:** не выявлены; журнал о пяти выдачах сам по себе не доказывает пять активных процессов или завершённость. **Выход:** обновлённый один журнал, реальные состояния/владение/хеши, адресные исправления и `STAGE_COMPLETE` либо честный `STAGE_INCOMPLETE` по факту.

### E. Профили новые и отсутствуют в каталоге; пользователь явно просит отдельные Web-чаты, `create_thread` имеет `model`/`thinking`, но не `agent_type`

**Ожидаемое решение:** явный запрос позволяет создавать пользовательские чаты. Прочитать фактические `developer_instructions` из нужного TOML и передать как содержимое через поддерживаемый механизм; для `create_thread` указать `model="chatgpt-web/gpt-6-sol"` и `thinking="high"`, проверить ответ инструмента/ID. **Не передавать несуществующий `agent_type`, не называть полученный чат зарегистрированным `pymentor_*_worker` и не считать пересланный текст настройкой уровня developer.** Для нативной делегации использовать её собственную живую схему (`reasoning_effort` для `spawn_agent`). Если Web/High невозможно задать или подтвердить, остановить зависимую диспетчеризацию с конкретным блокером.

**Противоречия:** исправленное различие полей TOML / `spawn_agent` / `create_thread` согласуется с протоколом; фактический запуск отдельного чата не производился. **Выход:** подтверждённые пользовательские чаты либо явный блокер, без ложного заявления о регистрации локальной роли.
