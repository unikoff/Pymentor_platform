# Кандидат: меньше повторного контекста Coordinator

Источник: чат `01a1798a-8456-72a0-9cc7-e90d0d41a459`, ход `01a179df-8243-7e70-9f78-2c471dda897e`, дата разбора 27.10.2026; [журнал](../../stage-runs/20261026-block05-continuation/RUN.md). Пользователь считает скорость и качество улучшившимися, сообщает расход около 20% пятичасовой квоты Terra и сам прервал запуск. Эта цифра предоставлена пользователем; отдельная телеметрия токенов по операциям недоступна.

Факты истории: 43:38 elapsed, статус interrupted; 14 spawn, 49 wait, 5 sendInput, 11 closeAgent и 11 команд. Параметры model/effort в назначениях не равны независимой телеметрии фактически отработавшей модели. Число вызовов не доказывает лишний расход/простой; реальная длительность каждого native wait и распределение токенов неизвестны. Прошлый аудит фиксировал отдельный четырёхчасовой прерванный запуск: задачи и условия не полностью сопоставлены, поэтому численный выигрыш новой процедуры не доказан.

В журнале десять уроков LOCAL_READY, интеграция и проверки M5 ещё не завершены. Зафиксированы девять перенесённых ключей, а после потери интегратора оркестратор проверял недостающую запись урока 21; последняя известная сверка дельты и каталога дала `False`. Нельзя считать этот ключ интегрированным или Stage 3 принятым без новой фактической проверки. Рабочее дерево общее и содержит изменения других задач; они не приписываются автоматически этому ходу.

Удачные элементы: отдельный автор на урок, локальная предметная готовность, параллельная интеграция готовых дельт, одна общая финальная приёмка и сохранение blockers. Оставить скорость и качество важнее минимального числа действий.

Кандидаты на экономию контекста: общую повторяющуюся часть назначений хранить один раз в проектном контексте запуска; передавать на урок только различия при подтверждённом доступе к инструкциям. Использовать многоточечный event wait и не выводить одинаковые полные логи, сохраняя конкретные ошибки/evidence. Перед восстановлением интегратора сверять только соответствующий ключ/версию. Эти изменения не являются fine-tuning модели и не гарантируют экономию.

Сравнительный pilot — NOT_RUN: на сопоставимом массиве фиксировать реальное время, измеримые токены/квоту при доступности, coverage P4/M5, качество и количество повторных правок. Считать candidate, а не подтверждённым улучшением до проверки; локальные примеры и чужие приватные данные не переносить в глобальную память.

## Новый кейс: вопросы Coordinator остановили зависимые решения

Источник: чат `01a17a1f-b711-76e3-a94c-af9b8cb8cbf6`, ход `01a17cc7-9f54-7aa3-9af9-6664224ca870`, дата разбора 27.10.2026; пользователь запрашивал Stage 2 и Stage 3 для 44 занятий главы 2, блоки 5–8. Ход длился 109 минут и был прерван пользователем. Это длительность всего хода, а не чистое время ожидания или доказательство неэффективности модели. Токены/квота по вызовам не измерены.

Наблюдение: P4 обнаружил отсутствующие диапазоны объёма в канонических концептах. Координатор дважды запросил разрешение менять эти концепты; пользователь оба раза разрешил минимальные исправления. Сохранённый RUN противоречив: таблица показывает 44/44 `PLAN_ACCEPTED` и пять Stage 3 авторов в работе, а раздел исключений одновременно сообщает о повторном P4 для 43 уроков и закрытом Stage 3 gate. Точный фактический момент запуска Stage 3 относительно повторного P4 из этих записей не доказан.

Кандидат на правило: Coordinator в именованном курсе/главе/блоке сам устраняет обычный локальный пробел по каноническим источникам и совместимым принятым примерам, выбирает минимальное обратимое решение и фиксирует только существенное допущение в существующем RUN. Запрос пользователя допустим лишь для реального конфликта цели, прав, приватности, безопасности, необратимого действия или отсутствия безопасного варианта; ожидание не блокирует независимые уроки. Исполнитель не расширяет собственный файловый scope.

Для стадий 2→3 нужна одна вычисляемая gate-проверка: текущие поурочные строки RUN — источник истины; после влияющей правки только зависимые уроки возвращаются в `P4_RECHECK`, их Stage 3 не стартует до нового `PLAN_ACCEPTED`. Уже независимые уроки продолжаются. Если пользователь явно заказал оба stage, переход после N/N автоматический; дополнительное подтверждение не требуется. Это правило устраняет подтверждённую неоднозначность журнала, но его влияние на будущий простой запуска пока не измерено.

Статус рецепта: CANDIDATE, один кейс; независимое повторное применение и matched-сравнение NOT_RUN. Не считать 109 минут, ответы пользователя или число назначений метрикой качества, экономии токенов либо скорости без подходящего baseline.

## Новый кейс: возобновление поверило устаревшему RUNNING

Источник: тот же чат `01a17a1f-b711-76e3-a94c-af9b8cb8cbf6`; прерванный ход `01a17cc7-9f54-7aa3-9af9-6664224ca870` создал пять Stage 3 назначений в конце, затем возобновлённый ход `01a17dca-58ca-7311-8a40-671a7b5c0253` длился 4 ч 38 мин 38 с и был прерван. По проверенным thread ID все пять исполнителей имели статус `interrupted`; в их ходах сохранились только исходные назначения, без ответа ассистента или инструментальных действий. Следовательно, подтверждённых результатов от этой пятёрки нет. Точная причина прерывания worker-чатов по доступной истории не установлена.

Поведение Coordinator в возобновлённом ходе: 209 вызовов `wait` с пустым списком получателей и 52 повторяющихся сообщения об отсутствии изменений; он не сверил пять child thread ID и продолжал описывать их как работающих. При этом сохранённый manifest всё ещё отмечал пятёрку `RUNNING`, а 39 уроков — `QUEUED`. Другой сохранённый RUN содержал конфликт: 44/44 `PLAN_ACCEPTED` в таблице, но 43 возврата в P4 и закрытый gate в исключениях. Эти расхождения не позволяют достоверно утверждать, что Stage 3 фактически прошёл gate или выполнил работу.

Коррекция процесса: `RUNNING` трактуется как последняя запись, не как живой статус; при каждом возобновлении точные worker ID и их артефакты сверяются, пустой wait не вызывается, а прерванный исполнитель получает статус `INTERRUPTED`. Новый исполнитель получает только подтверждённый незакрытый остаток одного урока. Статусы и назначения в исходном manifest не менялись; Stage 3 не возобновлялся. Причина самого сбоя child-процессов и фактический расход токенов остаются неизвестны.
