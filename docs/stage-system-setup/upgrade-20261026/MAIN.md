Основной вход и локальный протокол: [AGENTS.md](../../make%20les%20stage/3%20stage/AGENTS.md), [README.md](../../make%20les%20stage/3%20stage/README.md). **Входной контракт:** принятые P-планы/паспорт B, подтверждённая A, диапазон/ключи/идентичность, оригинальные TSX и практика (если существуют), актуальные требования компонентов, разрешённая область записи и доступность проверок. Два режима: `CREATE` для отсутствующего урока и `REWORK` для существующего. Без подтверждённого принятого плана этап не подменяет stage 2. Автор проверяет исходную версию и сохраняет работающие части; при REWORK формулирует до редактуры проблему и измеримый на уровне задания критерий улучшения.

**Маршрут ученика:** цель B и проверка → объяснение терминов простыми словами с точным именем/механизмом → различающий пример → проба с обратной связью → самостоятельное действие в практике → проверяемый результат. Для REWORK обязателен адресный `ДО → ПОСЛЕ` с исходным недостатком, улучшенной единицей/задачей и сохранённой сильной частью; для CREATE — цепь B → содержание → действие → критерий без фиктивного baseline. Экспертная оценка посильности не равна измеренному приросту знаний.

**Неприкосновенные контракты:** P1, P2, P3, P4 и `PLAN_ACCEPTED`, M1–M5 и `COMPLETE`, четыре фактические проверки M5 (`backend`, `frontend`, `API`, `open page + runner`), скрытые тесты, все ID/строковые номера/`source_file`, ключи и поля практики `manual.py` / `code_tasks.py`, два обязательных `LinkedNotes variant="connected"` (в `00` и финале), максимум шесть групп, минимум четыре **различных содержательных действия**, чтение ≤2 абзацев без содержательного интерактива **или** учебного визуала. Последняя норма не запрещает соседние учебные компоненты; связность важнее автоматической чередовалки. Недоступные обязательные уровни остаются `PARTIAL` и `STAGE_INCOMPLETE`, а не фиктивным PASS.

### Пример `ДО → ПОСЛЕ` (методический, не результат запуска урока)

**ДО:** `TrueFalse(is_done)` просит угадать факт → промежуточная `Note` называет `run()` и `handle_*` без объяснения ответственности по настоящему коду → второй `TrueFalse` проверяет тот же факт; практическое действие не различает два состояния.

**ПОСЛЕ:** на реальном исходнике объясняется, **кто** и **при каком условии** изменяет состояние, затем один видимый сценарий сравнивает два входа и объясняет оба исхода; практика просит самостоятельно реализовать или проверить изменение и показывает, какой тест отличает корректное решение. Второй интерактив допустим, если проверяет **другое следствие** той же задачи. Нельзя утверждать, что реальная функция `run()` меняет `is_done`, не проверив конкретный код. Сохранить точные корректные определения и полезный оригинальный пример.
