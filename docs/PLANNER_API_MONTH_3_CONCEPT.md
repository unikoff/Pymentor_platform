# Концепт месяца 3: HTTP, API и FastAPI, Planner API

## Назначение месяца

Третий месяц переводит ученика от локального консольного приложения к синхронному HTTP API. Это не перенос готового Persistent Planner в другую папку и не набор отдельных упражнений по FastAPI. Ученик строит новый продукт, Planner API v1, на знакомой предметной области задач и постепенно меняет границу общения с программой.

В начале месяца пользователь запускает CLI рядом с кодом. В конце месяца любой HTTP-клиент может создать, прочитать, обновить и удалить задачу через стабильный договор. Сервер проверяет вход, управляет in-memory состоянием, возвращает понятные статусы и покрыт автоматическими тестами.

## Граница между курсами

~~~text
Курс 2
  Persistent Planner
  CLI + JsonStorage + pytest
  данные переживают перезапуск

Курс 3
  Planner API v1
  HTTP + FastAPI + Pydantic + in-memory storage + TestClient
  данные намеренно исчезают после restart

Курс 4
  FastAPI + SQLite + SQLAlchemy
  API получает настоящую базу данных, транзакции и миграции
~~~

Persistent Planner остаётся знакомым доменным примером и архитектурной исходной точкой. Его Python-файлы, JSON-хранилище и CLI не импортируются в новый API-проект. В третьем курсе ученик осваивает другой тип границы. Отсутствие persistence здесь является осознанным ограничением, а не недоделанной возможностью.

## Конечный продукт

К завершению месяца существует отдельный проект studyhub-api со следующими свойствами:

- запускается одной документированной командой Uvicorn;
- имеет GET /health, Swagger UI и OpenAPI-схему;
- хранит задачи в памяти процесса;
- поддерживает список, одну задачу, статистику, создание, полную замену, частичное обновление и удаление;
- принимает вход через Pydantic-схемы и возвращает отдельные response-схемы;
- даёт 404 для отсутствующей задачи, 422 для ошибки валидации и 204 без body для успешного удаления;
- разделён на schemas, storage, crud, routers и точку сборки приложения;
- проверяется Postman-коллекцией и TestClient-тестами;
- имеет README, предсказуемую структуру и GitHub Release.

Контракт финального API:

| Method | Path | Смысл | Успех | Важные ошибки |
| --- | --- | --- | --- | --- |
| GET | /health | Проверить, что приложение отвечает | 200 | 500 только при непредвиденной проблеме |
| GET | /tasks | Получить collection, при необходимости с query-настройками | 200 | 422 для некорректных query |
| GET | /tasks/{task_id} | Получить один item | 200 | 404, 422 |
| GET | /stats | Получить агрегаты по текущему in-memory состоянию | 200 | 500 только при непредвиденной проблеме |
| POST | /tasks | Создать задачу | 201 | 422 |
| PUT | /tasks/{task_id} | Полностью заменить представление задачи | 200 | 404, 422 |
| PATCH | /tasks/{task_id} | Изменить только переданные поля | 200 | 404, 422 |
| DELETE | /tasks/{task_id} | Удалить задачу | 204 без body | 404, 422 |

У задачи есть server-managed id, пользовательские title и priority, а также is_done. Значения, правила и точная форма схем не должны меняться между уроком, практикой, OpenAPI, Postman и тестами.

## Блок 9. HTTP как договор, занятия 45-50

Цель блока: ученик умеет проектировать внешний договор до того, как начинает писать FastAPI-код. Здесь нельзя создавать приложение, устанавливать framework или вручную отправлять реальные запросы. Иначе HTTP превращается в набор магических decorators.

| Занятие | Новая способность | Формат практики | Артефакт и граница |
| --- | --- | --- | --- |
| 45. Клиент и сервер | Разделять роль интерфейса, сервера и источника истины | Ручная проектная практика | client-server-boundary.md; Persistent Planner не меняется |
| 46. HTTP request | Читать method, адрес, headers и body как части одного сообщения | Интерпретатор | Изолированная модель request без сети |
| 47. HTTP response | Читать status, headers, body и Content-Type как результат операции | Интерпретатор | Изолированная модель response, включая 204 без body |
| 48. HTTP methods | Выбирать GET, POST, PUT, PATCH, DELETE по семантике | Интерпретатор | Проверяемое соответствие действия и method |
| 49. REST и routes | Разделять ресурс, collection, item, endpoint, URL и method | Ручная проектная практика | Начало planner-api-v1.md с route map |
| 50. Path, query, body | Размещать входы в корректной части request и описывать contract | Ручная проектная практика | Завершён planner-api-v1.md |

Блок 9 не должен повторять JSON-сериализацию второго курса. Здесь JSON является форматом body, а не задачей хранения. Он также не вводит Pydantic и 422 как следствие framework-валидации. Сначала ученик понимает общий HTTP-договор, затем встречает конкретный механизм FastAPI.

Подробная карта блока хранится в [PERSISTENT_PLANNER_39_44_PATH.md](PERSISTENT_PLANNER_39_44_PATH.md).

## Блок 10. Первый работающий сервер, занятия 51-56

Цель блока: сделать невидимый протокол наблюдаемым. Ученик сначала отправляет два реальных request через HTTP-клиент, затем запускает свой сервер и постепенно подключает первые публичные операции.

| Занятие | Новая способность | Формат практики | Что остаётся после урока |
| --- | --- | --- | --- |
| 51. Postman | Собирать, отправлять и сохранять request, читать response | Ручная практика на echo-сервисе | Безопасная Postman collection без секретов |
| 52. FastAPI, Uvicorn, Swagger | Запускать приложение, понимать app, endpoint, server и документацию | Ручная проектная практика | studyhub-api, GET /health, воспроизводимый запуск |
| 53. GET endpoints | Возвращать collection и stats как JSON, не меняя состояние | Ручная проектная практика | GET /tasks и GET /stats над временными данными |
| 54. Path-параметр и item | Выбирать одну задачу и различать 200, 404 и 422 | Интерпретатор | Проверяемая функция поиска, которая позже войдёт в CRUD-логику |
| 55. Query-параметры | Последовательно фильтровать, искать, сортировать и ограничивать collection | Интерпретатор | Проверяемый pipeline выборки без изменения исходного списка |
| 56. BaseModel и body | Принимать валидный JSON до тела endpoint и возвращать 201 | Ручная проектная практика | Первый TaskCreate и POST-граница |

Логика блока:

~~~text
Postman видит настоящий HTTP
  -> FastAPI создаёт серверную точку входа
  -> GET показывает read-only состояние
  -> path и query объясняют выборку данных
  -> BaseModel защищает создание до CRUD-логики
~~~

Задания в интерпретаторе 54 и 55 не должны быть оторванными головоломками. Они формулируют точные правила будущего crud слоя: поиск не меняет collection, функция возвращает копию, фильтры выполняются в согласованном порядке, границы limit предсказуемы. В последующих ручных уроках эти правила переносятся в настоящий API без изменения их смысла.

В 56 достаточно первого валидного body и 201. Диапазоны полей, детальное чтение 422 и разделение схем принадлежат следующему блоку. Не пытайтесь дать всю Pydantic-теорию в одном уроке.

## Блок 11. Вход, состояние и CRUD, занятия 57-62

Цель блока: сделать API предметно корректным. Сначала ученик усиливает входной контракт, затем хранит задачи на стороне сервера и по частям собирает полный жизненный цикл ресурса.

| Занятие | Новая способность | Формат практики | Что остаётся после урока |
| --- | --- | --- | --- |
| 57. Валидация и 422 | Описывать обязательность, типы и границы данных, читать error detail | Ручная проектная практика | TaskCreate с правилами и documented validation cases |
| 58. Разные схемы | Разделять создание, обновление и ответ сервера | Ручная проектная практика | TaskCreate, TaskUpdate, TaskRead, response_model |
| 59. In-memory storage | Владеть серверным состоянием, выдавать id, создавать безопасную запись | Интерпретатор | Контракт storage для добавления задачи |
| 60. Первая половина CRUD | Согласовать create, list и get через общий источник данных | Интерпретатор | Чистые операции create/list/get с единым поиском |
| 61. PUT и PATCH | Отличать полную замену от изменения присланных полей | Интерпретатор | Две не смешанные операции обновления |
| 62. DELETE и ошибки | Удалять item, использовать единый 404 helper и 204 без body | Интерпретатор | Завершённая алгоритмическая CRUD-цепочка |

Здесь особенно важны четыре границы:

1. TaskCreate не принимает id и не позволяет клиенту управлять серверным состоянием.
2. TaskRead описывает то, что сервер обещает вернуть, а не форму входного JSON.
3. TaskUpdate или отдельная схема PATCH описывает только разрешённые входы конкретной операции.
4. Storage и CRUD не знают о FastAPI. Они возвращают данные или сообщают предметную проблему, а HTTP-перевод остаётся на границе router.

Урок 56 впервые знакомит с BaseModel. Урок 57 не начинает его заново. Он углубляет только ограничения, детали 422 и отсутствие изменения состояния после невалидного request. Урок 58 не повторяет валидацию. Он решает следующую проблему: одно и то же поле имеет разный смысл во входе и в ответе.

Алгоритмические задачи 59-62 обязаны использовать те же имена полей, правила id, нормализацию title, status codes и поведение 404, которые позже появятся в итоговом API. Тогда интерпретатор становится безопасным тренажёром перед интеграцией, а не параллельной программой.


Урок 65 не должен заново объяснять HTTP или создавать другой список endpoints. Его задача: собрать уже изученные решения в единую спецификацию и остановить расползание scope. Урок 66 не меняет status, paths или schemas. Урок 67 не изобретает новые действия. Урок 68 не добавляет feature, а проверяет существующий публичный результат.

## Единый путь данных

К концу месяца ученик должен уметь объяснить весь путь без пропусков:

~~~text
HTTP client
  -> method + path + query + body
  -> FastAPI router
  -> Pydantic input schema
  -> CRUD rule
  -> in-memory storage
  -> TaskRead response schema
  -> status + JSON response
~~~

Для 404 путь останавливается в момент, когда CRUD не находит item. Router переводит этот факт в HTTP-ответ. Для 422 endpoint не должен начинать CRUD-операцию: FastAPI и Pydantic останавливают request на входной границе. Для 204 ответ завершается без body после успешного удаления.

## Карта форматов практики

| Формат | Занятия | Почему он выбран |
| --- | --- | --- |
| Ручная проектная практика | 45, 49-53, 56-58, 63-66, 68 | Результат зависит от решения, структуры проекта, документации, работающего приложения или внешнего клиента |
| Интерпретатор с автопроверкой | 46-48, 54-55, 59-62, 67 | Результат детерминирован, не требует сети и проверяет одну конкретную механику до интеграции |

Правило для интерпретатора: он проверяет одну функцию или один сценарий с заранее понятным договором. Он не имитирует весь FastAPI, не просит ученика угадать внутреннюю архитектуру и не становится заменой реальному проекту.

Правило для ручной практики: каждая карточка даёт один законченный инженерный результат. Условие называет цель и причину, requirements перечисляет проверяемые факты, hint возвращает к идее, а answer остаётся разбором после попытки. Практика продолжает один studyhub-api, а документы блока 9 расширяются вместо создания копий.

## Педагогические правила месяца

1. Каждый урок начинается с результата предыдущего. Не используйте будущие terms как уже известные.
2. Теория сначала объясняет абстрактную идею, её production-смысл и ограничения, затем спокойно связывает её с Planner API.
3. У каждого урока есть раздел «Что мы будем делать в практике». Он описывает глобальный результат, но не дублирует готовое решение.
4. В подробном уроке есть минимум четыре интерактива разных типов: прогноз, выбор, поиск ошибки, восстановление цепочки, сопоставление ролей или самопроверка.
5. Code task возможен только после объяснения всех требуемых конструкций, типов данных и граничных случаев.
6. Одинаковые понятия не переизобретаются. Например, 56 вводит BaseModel, 57 углубляет validation, 58 разделяет contracts.
7. Отдельный учебный словарь Python в интерпретаторе не должен незаметно стать второй моделью проекта. Его форма обязана совпадать с последующим API-contract или явно отличаться как независимый пример.
8. Теория доступна в React-компонентах frontend/src/lessons/planner-api, а Markdown служит отдельным представлением. При точечной переработке синхронизируйте оба источника, практику и карту курса.

## Что не входит в месяц

- SQLite, SQLAlchemy, транзакции, миграции и persistent database;
- authentication, users, sessions, JWT, roles и permissions;
- async endpoints, background tasks, WebSocket и очереди;
- Docker, CI/CD и production deployment;
- pagination уровня database и оптимизация запросов;
- полиморфная доменная модель, tags, due dates и новые product features.

Эти темы не запрещены навсегда. Они вынесены в следующие курсы, чтобы ученик сначала понял чистую HTTP-границу и lifecycle одного ресурса.

## Критерий готовности месяца

Месяц готов, если ученик может с чистого окружения:

1. запустить API и открыть /docs;
2. объяснить путь одного POST от JSON body до response;
3. отправить create, list, get, PUT, PATCH и DELETE запросы;
4. предсказать 201, 200, 204, 404 и 422 в соответствующих сценариях;
5. показать, что невалидный request не меняет in-memory storage;
6. запустить TestClient-тесты два раза подряд без зависимости от их порядка;
7. по README повторить запуск и ограничение, что данные исчезают после restart;
8. объяснить, почему следующий курс заменит in-memory storage на SQLite, не переписывая HTTP-договор с нуля.

Если один из этих пунктов требует внешнего поиска базового понятия, работа начинается не с финального урока, а с места, где это понятие впервые должно было появиться.
