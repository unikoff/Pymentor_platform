**Условие завершения:** файл сохранён и принят по разделу 5. При неподтверждённом входе подготовь независимую часть и явно назови, что мешает принять зависимую.

## 3. Теория

- Составь примерно **7–10 пронумерованных учебных блоков**, включая `00. Вступление` и последний блок про практику. Служебные разделы шаблона в этот счёт не входят. Отклоняйся в обе стороны, если это улучшает путь; не дели одну мысль и не добавляй повторы ради количества.
- В `00` задай плавную подводку, связанный список **Точка старта → Новый вопрос → Результат** и пояснение связи после списка. Это маршрут данного занятия.
- Каждый средний блок раскрывает один шаг: что и зачем объяснить, как работает механизм, порядок понятий и переход дальше. Для нового или сложного механизма обозначь независимый пример и типичную путаницу; детали разработает этап 3.
- Планируй теорию от понятия и назначения к механизму, затем к применению в нашем проекте. Сохраняй содержательную теорию: точная копия действий практики не объясняет технологию.
- Пиши конкретные указания: вместо «подробнее о хранении» назови роли, данные, операции и порядок объяснения. Сокращай повторы и служебный текст, сохраняя механизм, зависимости и результат; объём сам по себе не подтверждает полноту.

## 4. Практика

- Последний учебный блок называется **«Что мы будем делать в практике»**. Укажи формат, исходную опору и общий результат. Затем задай связанный список **действие → наблюдаемый результат** в порядке работы и пояснение после него.
- Для каждого действия назови конкретный объект изменения или исследования и подготовивший его блок теории либо прежний навык. Это крупные шаги работы, достаточные для составления заданий на этапе 3.
- Для проекта придерживайся цепочки **изучили механизм → изменили конкретную часть существующего проекта → проверили прежние возможности**. Укажи причину переработки, что изменится и что сохранится. Проверка сопровождает изменение; не заменяй ею проектную работу, предусмотренную концептом.
- Для исследования в интерпретаторе или устного разбора назови механизм, действие и подтверждаемый вывод. Короткий опыт допустим; отдельный макет не должен дублировать уже работающий проект.

## 5. Приёмка и завершение

После сохранения отдельно проверь готовый файл, начиная с практики:

- **Подготовка действий:** для каждого шага практики найдено место объяснения или подтверждённый прежний навык. Вход доступен ученику, результат наблюдаем и соответствует B.
- **Соответствие концепту:** курс, блок, название, A → B, обязательные темы и границы сохранены. Уже освоенное, планируемое и непроверенное различимы; новой технологии или функции вне маршрута нет.
- **Полнота разметки:** от `00` до практики идёт последовательная нумерация и содержательные шаги раздела 3. Оба связанных списка имеют пояснение после них; служебная передача дальше не превращается в ещё один учебный блок.
- **Файл:** шаблон заполнен без фигурных заготовок, относительная ссылка на концепт ведёт к существующему файлу, прежний YouTube-комментарий сохранён. Diff содержит только разрешённую правку и не теряет чужое содержание вне задачи.

**Дополнительная проверка связности:** одним коротким проходом сверь «B предыдущего → A текущего» и «B текущего → потребность следующего». ## Концепция курса — выбранный контекст

Источник: `docs/concept/chapter_04/COURSE.md`.

### Цель и итог главы

Глава строит воспроизводимый синхронный Planner на FastAPI, SQLite и SQLAlchemy: от явных настроек и сборки через ресурс Session и транзакции к SQL CRUD, импорту имеющихся задач, надёжным отказам, наблюдению запросов и чистой передаче результата. Целевой продукт использует один SQLite путь для API и CLI, сохраняет существующий предметный договор и запускается из чистого checkout по README.

### Архитектурная траектория и границы

- Настройки и `DATABASE_URL` → Engine/SessionFactory → короткоживущая Session на HTTP-запрос или CLI-команду → единый сервис и SQL-репозиторий.
- Транзакционная граница принадлежит сценарию сервиса; репозиторий не подтверждает части операции. HTTP и CLI используют один адрес базы, но независимые короткие ресурсы.
- Переход данных в SQL выполняется явно и проверяемо. Импорт прежнего JSON — отдельная команда, не startup, не fallback и не постоянная синхронизация. Инициализация схемы явная; `create_all` не является миграцией и не чинит несовместимую существующую схему.
- Сохраняются CRUD, выборки, статистика и внешние договоры Planner. Не добавляются ради учебного финала новые сущности, endpoints, индексы, асинхронность или deployment.
- Отказы классифицируются по причине: известная недоступность хранилища может стать безопасным 503, прежние 404/422 сохраняются, неизвестная ошибка остаётся серверной. `IntegrityError` не означает автоматически пользовательский конфликт; `OperationalError` не всегда означает временную недоступность.
- Диагностика SQL включается осознанно, по умолчанию выключена, не раскрывает параметры, секреты, содержимое пользовательских данных или путь к БД. Автоматический повтор неопределённо завершившегося create недопустим.
- Следующая глава сначала вводит изменение уже существующей схемы, затем пользователя/владение и контроль доступа. В текущей главе не считаются готовыми миграции, отношения, `User`/`owner_id`, login, серверная сессия/JWT или авторизация. Cookie настроек представления не является аутентификацией.

### Проверка готовности главы и передача

Итог должен быть воспроизводим из чистого checkout: README ведёт через окружение, настройки, явную исходную схему, API/CLI и тесты; нет секретов или рабочих данных в передаваемом Git-составе. Оба интерфейса работают с одной базой, а отдельный импорт не запускается автоматически. Передача следующей главе точно описывает имеющиеся модель/таблицу задач, SQL операции, сборку ресурсов, интерфейсы и проверки, не приписывая продукту миграции или авторизацию.

### Назначение и опора A→B

Блок 16 (занятия 100–105) делает уже переключённый на SQLite Planner надёжным, наблюдаемым и воспроизводимым. Его A — целевой результат B15: один SQL-путь, полный CRUD/query/CLI, сохранённые данные и отсутствие JSON-backend. При создании планов фактическое достижение A нужно отдельно подтвердить по состоянию проекта/StudyHub до занятия; паспорт задаёт цель, но не доказывает её.

B блока — безопасная классификация известных отказов, проверенные rollback/commit и восстановление независимой операции, управляемое безопасное SQL-наблюдение, обоснованная узкая оптимизация либо доказанная достаточность запроса и чистая воспроизводимая передача продукта. Исходная схема и публичный договор сохраняются; JSON fallback не возвращается.

### Маршрут шести занятий

1. **100 — Ошибка БД и граница ответственности:** известная причина отказа переводится в безопасный HTTP/CLI результат; не смешивать с ошибками ввода и неизвестными внутренними сбоями.
2. **101 — Проверки отказов и восстановление работы:** изолированно проверить connect/query/flush/commit, rollback, закрытие ресурса и следующую независимую операцию; после успешного commit исключение не доказывает отмену.
3. **102 — Какие SQL-запросы делает Planner:** управляемо наблюдать реальные запросы, отличать запрос приложения от seed/DDL и не раскрывать параметры.
4. **103 — Обоснованное улучшение запросов:** использовать конкретное наблюдение/план запроса; улучшить только доказанную лишнюю работу или защитить узко проверкой достаточный запрос. Не обещать ускорение без данных и не менять схему ради упражнения.
5. **104 — Сквозная проверка готового продукта:** проверить обычные API/CLI и ранее собранные компоненты после доработок, без повторной реализации уже готового.
6. **105 — Передача работающего DB Planner:** чистый checkout, README, явная исходная схема, окружение, оба интерфейса и тесты; точно описать границу следующей главы.

### Инварианты при составлении планов

- A/B паспорта и фактическое состояние до занятия должны быть явно разделены: запланированное не выдавать за изученное или реализованное.
- Сохраняются поля и поведение прежнего Planner, транзакционная и ресурсная границы, один SQL backend, отдельный явный импорт JSON и исходная схема. Нет миграций, нового индекса/колонки, auth или пользовательского владения.
- Известные ошибки переводятся по причине и в правильном слое. Не проглатывать неизвестные исключения, не выдавать ложный успех/пустой результат и не включать fallback. Операция до commit должна откатываться; успешный commit не отменяется последующим исключением.
- Все проверки отказов выполняются только на изолированной временной БД/Session/Engine. Не повреждать и не чистить рабочие данные; временные подмены и listeners/loggers восстанавливать.
- Не раскрывать SQL параметры, пользовательские данные, секреты, `.env`, путь к БД или traceback клиенту. SQL диагностируется только при явном включении.

## 3. Теория: объяснение прежде применения

Теория раскрывает тему, не пересказывает ТЗ. Центральное понятие объясни по смыслу: что это, зачем нужно, как работает, за что отвечает и чего не делает, с чем путают, где применяют и какую роль оно играет здесь. Вспомогательному термину достаточно определения и назначения. Это связный рассказ, не одинаковая анкета к каждому слову.

Порядок для каждого нового механизма: **назначение → работа по шагам на независимом примере → типичные ошибки и причины → проверка понимания → применение в проекте**.

- Все необходимые знания появляются до задания. Новое понятие нельзя впервые объяснить только в условии, подсказке или проверочном ответе. Знакомое кратко напомни; недостающую предпосылку объясни в пределах темы.
- Перед кодом назови вопрос, после него или в пошаговом разборе объясни вход, изменения, результат и причину. Первый пример показывает один новый механизм. Завершённый код должен работать; фрагмент и псевдокод помечай. Подготовленную трассировку не называй реальным запуском.
- Пример независим от целевой задачи: если смена имён превращает его в готовый ответ, измени сценарий. Полные решения и технические подсказки к задаче остаются в практике.
- Для каждого нового абстрактного механизма дай простую аналогию рядом с точным объяснением. В полноценном занятии минимум две содержательные аналогии в разных местах. Назови соответствие частей и границу сравнения, затем вернись к механизму и примеру.
- Новый термин, сокращение или английскую кнопку поясни при первом использовании. Основное объяснение должно быть на платформе, без обязательного поиска в Google. Внешняя ссылка дополняет, не закрывает пробел.
- Применение и ограничения описывай точно. Не называй решение универсальным правилом или «стандартом production» без подтверждения. Если технология не используется в проекте, объясни зачем она упомянута и не добавляй её в практику без основания.

Проектный маршрут: **изучили механизм → переработали конкретную часть существующего Planner → проверили прежние возможности**. Не создавай второй проект, временный дубль готового слоя или повторную реализацию ради задания. Проверка сопровождает изменение, не заменяет его. Для исследовательского занятия допускается небольшой независимый опыт с честным познавательным результатом, без обещания новой возможности Planner.

### Два обязательных связанных раздела

**Вступление 00.** Это первый раздел занятия, не обзор курса в `block_00`. Плавная подводка → ровно три пункта «Точка старта → Новый вопрос → Результат» → связный поясняющий абзац после списка. Покажи, как реальная прежняя опора вызывает новый вопрос и ведёт к B; не начинай с незнакомого термина или большой схемы. Связь с курсом раскрывай прямо в тексте этого вступления. Не используй `TheoryBridge` как начальную плашку «Связь с курсом», перед вступлением `00` или вместо него; не выноси в неё блок «Важно не перепутать» из начального контекста.

**«Что мы будем делать в практике».** Заключительный раздел теории: короткая подводка → последовательность «действие от лица мы + наблюдаемый результат» → 1–2 поясняющих абзаца после списка. Укажи связь с изученной механикой, готовую опору, крупный путь работы, доказательство результата и границы. Для проекта заверши проверкой прежних возможностей; для исследования назови проверяемое понимание. Это обзор, не алгоритм решения и не замена ТЗ.

Оба списка в TSX: `LinkedNotes variant="connected" items={[{ title, description }, ...]}`. Текст после списка объясняет связь, не повторяет подписи. Обе группы входят в лимит раздела 6.

## 4. Объём

Минимум **1000 слов теории**, целевой ориентир первого знакомства **1400–2000**, не потолок. Не добирай объём повторениями и не сокращай объяснение новой темы ради экономии токенов.

Считай одну реально видимую TSX-теорию по frontend-привязке: от раздела 00 до обзора практики, без самого обзора и последующего итога. Markdown-fallback сначала устрани: это сбой привязки, не успешная альтернативная версия этапа 3.

- Включай прозу, определения, аналогии, разборы, пояснения списков и сравнений: `Lead`, `p`, `Callout`, `LinkedNotes.description`, поясняющий столбец `MethodGrid`; отдельно считай объясняющую обратную связь `explanation` и `StepThrough.note`, без дублей.
- Исключай заголовки, метки, hero, код, вывод, подписи схем, проверочные вопросы, варианты ответов, кнопки, практику, подсказки, решения, тесты, видео, навигацию и разметку. Связующий вопрос в обычной прозе учитывается. Техническое имя внутри объяснения учитывается, кодовый блок нет.
- Слово: последовательность букв или цифр; внутренние дефис и подчёркивание не разделяют слово. Сначала выдели учитываемый текст, потом считай. Число слов всего TSX-файла не подходит.
- Зафиксируй «основной текст + разборы интерактивов = всего». Проверочный ответ уточняет известное, а не впервые даёт обязательное знание.
- Отклонение от цели объясни кратко. Ниже 1000 допустимо только отмеченное исключение с причиной, ранее раскрытой опорой и полным покрытием практики; «сложная тема» и «хочется короче» не причины.

Пороги являются требованиями Pymentor, не свойствами модели. Основа: замер шести видимых [занятий блока 9](../frontend/src/lessons/chapter_03/index.ts), 02.10.2026, медиана 986,5 слов. Старые примеры помогают с подачей, но не автоматически соответствуют текущим правилам.

## 5. Интерактивы и язык

На полноценное занятие минимум **четыре осмысленных интерактива разных учебных типов**, распределённых по теме. Тип определяется действием: четыре выбора ответа не дают четыре типа.

Используй [shared.tsx](../frontend/src/lessons/shared.tsx):

- прогноз и трассировка: `PredictOutput`, `StepThrough`;
- причина ошибки: `BugHunt`;
- выбор и сравнение: `QuizCard`, `TrueFalse`, `CompareSolutions`;
- роли и порядок: `MatchPairs`, `CodeSequence`;
- самостоятельное объяснение: `RecallCard`, `FlipCards`;
- исследование механики: `FillBlank`, `SliceExplorer`, `BranchExplorer`, `TerminalDemo`.

У каждого интерактива есть объяснённая опора, понятный вопрос и разбор ошибки. Он не раскрывает решение практики и не блокирует чтение. В технической теме включай содержательный поиск ошибки, не искусственную ошибку ради квоты. `CodeBlock` подходит там, где взаимодействие ничего не добавляет. Общего потолка примеров, схем и интерактивов нет; убирай бессмысленные повторы.

Голос всего авторского текста занятия: **«мы посмотрели», «разберём», «проверим», «сделаем»**. Это относится к теории, вопросам, инструкциям, комментариям и учебным сообщениям кода, практике, подсказкам, ответам и переходам. Без «ты/вы», «ученик сделает», «откройте». Исключение: ТЗ описывает поведение готового результата по разделу 7. Нейтральное определение «сервер принимает запрос» допустимо; не вставляй «мы» механически. Точные имена кода, протокольные сообщения и подписи интерфейса сохраняй.

Пиши спокойно, живо, профессионально: короткие предложения, активные глаголы, простые аналогии, без канцелярита и «магии». Абсолютный запрет на U+2014 действует во всех местах, перечисленных в начале методички. Номер занятия остаётся в названии, файле и ключе, но в учебном рассказе используй «предыдущее», «это», «следующее занятие».

Проверяй и стандартные сообщения компонентов. Например, `CodeSequence.incorrectExplanation` по умолчанию начинается с «Проверьте»; переопредели его в занятии от «мы». Если текстового параметра нет, отметь проблему, не меняй общий компонент вне запроса.

## 6. Списки и оформление

Используй [существующие стили](../frontend/src/styles.css) и компоненты, без нового синтаксиса и локальной дизайн-системы.

- Последовательность двух и более пунктов оформляй списком, не обычными строками, `<br />` или разрозненными абзацами. Связное рассуждение оставляй прозой.
- Три и более пары «метка + пояснение» в TSX оформляй `LinkedNotes`, не стеком `h3/p`. Для зависимости шагов `variant="connected"`; для параллельных ролей или вариантов карточный вид по умолчанию. Перед группой назови общую мысль.
- На занятие максимум **шесть групп LinkedNotes**, включая оба вида, вступление и переход к практике. Это не лимит других компонентов; не обходи его переименованием лишней группы.
- Простое перечисление: `ul/li`; порядок: `ol/li`. Сравнение по одинаковым признакам: `MethodGrid rows={[[термин, пояснение], ...]}`, двухколоночная сетка. Не превращай независимые роли в ложную последовательность.
- Ритм: вопрос → объяснение → наблюдение → действие → разбор. Связанные вставки могут идти подряд под общей подводкой и разбором. Не делай карточку из каждого абзаца, не удаляй полезные вставки ради преобладания текста.
- Единая ширина `--content-width`, подпись кода внутри рамки, колонки на узком экране становятся одной. Шкала `--space-*`: 4, 8, 12, 16, 20, 24, 32, 40, 48 px; обычно 16–20 внутри мысли, 24–32 между компонентами, 32 между разделами. Расстояние задавай в одном месте, не складывай родительский `gap` и внешние `margin`; новые отступы без причины не вводи.

## 7. Практика и подключение

При создании или полной переработке **заново составь практику по плану и новой теории и замени точную запись занятия**. Проверка старого задания не заменяет эту работу. Сохрани ключ; прежний вариант и legacy-дубликат не остаются активными. Современный внешний вид ручной практики включается форматом данных, не правкой CSS.

### Условия и форматы

Задача даёт один законченный результат, следующая использует достигнутое. Контекст упражнения объясни один раз. Ориентир условия: 3–4 коротких предложения и 0–3 необходимых ограничения, не обязательная квота. Назови действие, исходную опору, результат и важные границы. Не навязывай цикл, порядок строк или временные имена, если это не учебная цель.

**Стиль ТЗ: описывай уже реализованное поведение.** В постановке и требованиях называй субъект, действие и результат: «Функция возвращает копию задачи; исходный список не изменяется», «Неподходящий тип `title` отклоняет Pydantic, а не приводит к `AttributeError`». Используй утвердительную форму настоящего времени: «возвращает», «сохраняет», «отклоняет». Это описание готового состояния, не отчёт о выполнении. Не пиши «сделаем», «добавьте», «должна будет» или «нужно проверить» вместо требования. Для исследования: «Результат разбора содержит прогноз вывода и объяснение причины». Входы, ошибки и ограничения называй только существенные для этой задачи; алгоритм решения не раскрывай. Голос «мы» остаётся в подводке, подсказке и разборе.

Не повторяй требование в описании, условиях и проверках. Подсказка помогает с трудным местом без полной реализации. Устное условие не сообщает готовый вывод. Тесты проверяют только заявленные и объяснённые требования.

**Ответ содержит решение и его разбор.** После самостоятельной попытки покажи рабочий вариант кода, команды или конкретный устный ответ. Затем объясни ключевые действия: как вход превращается в результат, почему выбрана эта конструкция и как обработан заявленный ошибочный случай. В `answer.code` находится реализация, в `explanation/steps` её разбор, в `checks` проверка результата. «Проверим тип, маршрут и статус» без самого решения не считается ответом. Для поиска ошибки нужны исправление и причина; для прогноза вывода нужен точный вывод и объяснение. Не переноси решение в условие, теорию или подсказку; скрытый редакторный эталон не публикуй в обход существующего интерфейса.

- Проект, несколько файлов, инструменты или архитектура: ручные карточки `manual.py`.
- Изолированная функция или короткая программа с проверяемым результатом: `code_tasks.py`.
- Информационная тема: предпочтительно исследование в интерпретаторе; устный разбор допустим по концепту. Не заменяй практику формальным README или самопроверкой «поняли ли тему».

Ручной формат:

```python
{
    "title": "Название упражнения", "task": "Общая цель.",
    "tasks": [{
        "title": "Действие и результат", "task": "Что получим и зачем.",
        "requirements": ["Существенное условие"],
        "hint": "Следующий ход мысли без решения.",
        "answer": {
            "explanation": "Почему решение работает.",
            "steps": ["Шаг разбора"], "code": "# Рабочее решение",
            "checks": ["Проверка результата"],
        },
    }],
    "result": "Наблюдаемый итог.",
}
```

Используй **вложенные `tasks`, не внешнее legacy `steps`**. `tasks` включает современные карточки, навигацию, подсказку, ответ и отметку выполнения; только внешнее `steps` показывает старый checklist. Убери прежний внешний список целиком. `answer.steps` является разбором решения и допустим: не путай его с legacy-полем. Ответ открывается по запросу; для устного нужен вывод с аргументами, пустые поля/код опусти. `result` без «Готово, если», подпись добавляет UI. Плашка «без автоматической проверки» не нужна.

Редакторный формат:

```python
{
    "title": "Результат", "level": "easy", "mode": "solve",
    "prompt": "Короткая цель.",
    "contract": {"given": "Что дано.", "todo": "Что получим.", "check": "Важные случаи."},
    "requirements": {"items": ["Необходимое ограничение"]},
    "hints": ["Опора", "Уточнение", "Локальная проверка"],
    "starter_code": "def solve(value):\n    pass\n",
    "tests": [{"name": "Сценарий", "args": [...], "expected": ...}],
    "reference_code": "# Внутреннее рабочее решение",
}
```

Примеры выше показывают поля, не готовые задания: заполнители замени содержимым. `solve`: имя функции, аргументы и возвращаемое значение. `script`: вход/точный вывод, проверка через `"assert": "stdout"`; форму тестов сверяй с действующим примером. Стартовый код без ответа, 2–3 подсказки без полной реализации; эталон и скрытые тесты не попадают в публичную выдачу. `given_items/todo_items/check_items` только для настоящего списка, обычно 1–3 пункта, без дубля коротких полей. Обязательную конструкцию сначала объясни и назови в условии.

## 8. Учебные схемы в TSX и CSS

При создании занятия с нуля или его полной переработке **создай схему прямо в занятии средствами TSX и CSS**, если взаимодействие частей, движение данных, изменение состояния или сравнение проще понять визуально. Одна схема показывает одну главную связь. До неё объясни, что рассматриваем; после объясни порядок чтения и вывод. Если схема не помогает теме, кратко обоснуй отсутствие; декоративные схемы и квота не нужны.

Исходная SVG-схема или другой визуальный образец не предполагаются. Проектируй по смыслу занятия: назначение → узлы → связи «откуда → куда → что означает» → адаптивная раскладка → реализация → приёмка. SVG, canvas и координатная отрисовка для учебных схем не используются. При переработке замени схему затронутого занятия на TSX/CSS с сохранением верного учебного смысла; соседние материалы и их старые файлы не меняй. Уже соответствующую кодовую схему можно сохранить. Содержательная растровая иллюстрация допустима отдельно, но не заменяет блок-схему.

### Общие компоненты схем

Сначала используй экспортируемые детали из [shared.tsx](../frontend/src/lessons/shared.tsx) и их существующие стили. Прочитай пояснения и типы нужных компонентов один раз; не выдумывай свойства и не копируй их реализацию в занятие.

- `Diagram(caption, orientation?)` задаёт рамку и подпись; `DiagramFlow(label, orientation?)` задаёт поток. `orientation`: `horizontal` или `vertical`; для вертикальной схемы согласуй ориентацию рамки и потока.
- `DiagramNode(title, shape?, children?)` представляет узел. `shape`: `process`, `terminator`, `decision`, `input-output`, `database`, `subprocess`. Выбирай форму по роли, не для украшения; пояснение и код передавай через `children`.
- `DiagramArrow(label, direction?, lineStyle?)` создаёт подписанное соединение. `direction`: `forward`, `backward`, `both`; `lineStyle`: `solid`, `dashed`. Два наконечника `both` обозначают одну двустороннюю связь, но не заменяют два разных пути запроса и ответа.
- `DiagramBranches(label)` и `DiagramBranch(label)` группируют исходы; `DiagramLane(title)` задаёт дорожку участника, `DiagramGroup(title)` объединяет связанные узлы. Эти контейнеры сами не рисуют линии от условия до результатов: нужные соединители и дорожки входят в композицию явно.
- `DiagramExchange(forward, reverse)` показывает два отдельно подписанных встречных пути, обратный пунктирный. Используй, когда этот стиль соответствует смыслу; если нужны иные стили, собери пути из общих деталей.
- `DiagramNote(title?, children)` даёт заметку, `DiagramLegend(items)` легенду с элементами `{ label, symbol }`. `DiagramTrack(label, items, activeIndex?)` показывает упорядоченные отметки с текущим шагом; по умолчанию активен последний. Это вспомогательная шкала, не замена требуемым узлам и стрелочным соединениям.

Минимальная композиция в отдельном файле занятия внутри `block_NN`:

```tsx
import { Diagram, DiagramFlow, DiagramNode, DiagramArrow } from "../../shared";

<Diagram caption="Передача кода на выполнение">
  <DiagramFlow label="От редактора к интерпретатору">
    <DiagramNode title="Редактор"><p>Хранит исходный код</p></DiagramNode>
    <DiagramArrow label="передаёт код" />
    <DiagramNode title="Интерпретатор"><p>Выполняет команды</p></DiagramNode>
  </DiagramFlow>
</Diagram>
```

Это JSX внутри компонента, не самостоятельный файл. Проверь относительный импорт. Готовые детали дают оформление, не доказательство геометрии: стыки, ветвления, возвраты и мобильную перестройку проверяй ниже. Небольшая композиция в текущем TSX допустима на существующих стилях; границы правок заданы разделом 1.

### Смысл и подписи

- Каждый этап, состояние или участник представлен отдельным видимым узлом. Названия, порядок действий и связи соответствуют объяснению; не добавляй участников и переходов, которых нет в процессе.
- Используй русский язык для учебных подписей и пояснений. Точные имена кода, команды и протокольные обозначения сохраняй. Ограничения «только английский» и «1–3 слова» нет: текст должен быть достаточным для понимания, но узел не содержит абзацы теории.
- Подпись стоит рядом со своим узлом или линией; подписи ветвей однозначно относятся к своим ветвям. Равные роли находятся на одном уровне, расположение не создаёт ложную последовательность или принадлежность.
- Убирай точки в конце подписей и пояснений внутри схемы. Сохраняй точки внутри кода, имён файлов и там, где предложение продолжается.

### Непрерывные соединения

- Между связанными узлами проходит видимая непрерывная линия со стрелочным наконечником. Символ `→`, подпись, отступ или набор несоединённых значков линию не заменяют.
- Линия начинается у границы исходного узла и заканчивается у границы целевого; остриё касается целевого узла. Видимая линия стыкуется с основанием наконечника без зазора, не проходит через открытый наконечник и не выступает за остриё. Наконечник завершает соединение, а не лежит поверх продолжающейся линии.
- Запрос/ответ и возврат управления показывай отдельными путями. `both` допустим для одной действительно двусторонней связи, не заменяет разные процессы. Простое сравнение независимых вариантов не требует выдуманного обмена. Пунктир помогает различить направления, не скрывает маршрут.
- У каждой ветви своя линия от точки выбора до результата. Возвраты и обходы проходят по отдельным дорожкам; несколько входов имеют различимые точки крепления. Не проводи линии через текст и посторонние узлы; избегай пересечений и неоднозначных стыков.
- Толщина линии и размер наконечника согласованы. На короткой связи наконечник не занимает основную длину. При тесноте перестрой раскладку или уменьши наконечник; не уменьшай текст до нечитаемого размера.

### Раскладка, оформление и доступность

- Используй CSS-поток, flex или grid. Узлы и дорожки соединителей занимают предусмотренные места в раскладке; высота узла учитывает переносы текста. Не собирай схему из блоков с фиксированными координатами. Локальное позиционирование декоративного наконечника внутри соединителя допустимо, если оно не задаёт расположение всей схемы.
- На широком экране выбери естественное направление чтения, обычно слева направо. На узком перестрой узлы и соединители вместе; простая последовательность может стать вертикальной. Ветви и возвраты сохраняют своих получателей, подписи и направление. Нельзя заменять линии значками, скрывать важные связи или менять только расположение узлов.
- На мобильном экране нет горизонтальной прокрутки, обрезанных узлов, наложений текста на линии и слишком мелких подписей. Предусмотри внутренние поля и зазоры у текста; при тесноте измени раскладку, перенеси строку или сократи подпись без потери смысла.
- Сохраняй визуальный язык проекта: спокойный тёмный фон, контрастные узлы, светлый текст, заметные соединители. Используй существующие токены и стили; смысл не зависит только от цвета. Без новой дизайн-системы, 3D, свечения и декоративных эффектов.
- Узлы, рамки и соединители собирай из общих `Diagram*`; небольшие специфичные композиции допустимы прямо в TSX текущего занятия, без дублирования общих деталей. Используй существующие стили и классы. CSS на этапе 3 read-only: если схему нельзя корректно оформить доступными стилями, укажи требуемую CSS-правку как отдельную задачу. Не меняй общие правила и компоненты платформы, не добавляй библиотеки или универсальный движок ради одной схемы.
- Используй семантическую структуру с понятной подписью и доступным текстовым описанием шагов, ветвей и возвратов. Например, `figure/figcaption` и связанное описание через `aria-describedby`; порядок DOM соответствует смыслу. Декоративные CSS-стрелки скрывай от скринридера через `aria-hidden="true"` на их контейнере, а смысл передавай текстом. Не скрывай вместе с декором значимые подписи.

### Приёмка и обязательная перепроверка

1. **Проверь реализацию.** Выполни доступные проектные проверки TypeScript и CSS для затронутых файлов. Синтаксическая корректность не подтверждает внешний вид; новых инструментов проверки ради схемы не добавляй.

3. **Пройди механизм.** Проследи каждую связь от источника до результата и сверь с текстом занятия. Направления, ветви и возвраты однозначны; схема понятна без исходного образца. Проверь доступное текстовое описание и логичный порядок чтения без декоративных стрелок.
4. **Исправь и повтори.** После исправления повторно осмотри оба размера и выполни затронутые проверки. Схема принята только при выполнении всех критериев выше. ## 2. Цель, точка B и итоговый проект

Ученик проходит путь от работающего JSON-backed FastAPI к одному синхронному Planner на SQLite/SQLAlchemy. Он понимает не только вызовы библиотеки, но и путь данных, ответственность слоёв, время жизни ресурсов и границу завершённой операции.

**B главы:** API и CLI обращаются к одной настроенной SQLite-базе через общее прикладное ядро. Все прежние операции работают; существующие задачи перенесены без потери id и внутренних полей. Ошибки не превращаются в ложный успех, не оставляют частично сохранённое изменение и не раскрывают внутренности БД клиенту. Выборка, сортировка, поиск и статистика выполняются запросами, а не загрузкой и перезаписью всей таблицы. Есть явная инициализация исходной схемы, изолированные проверки и понятный запуск. Файлового JSON-backend, настройки его выбора и автоматического возврата к нему в рабочем приложении больше нет.

Миграции схемы, Alembic и изменение уже созданных таблиц изучаются в следующей главе. Здесь один раз проектируем исходную схему, создаём её явной командой и используем без дальнейших изменений. Однократный **перенос прежних задач из JSON** остаётся необходимой частью перехода на БД; это не занятие о миграциях схемы.

Итоговый проект дополнительно умеет использовать централизованные настройки, внедрение зависимостей и небольшую cookie-настройку представления. Cookie не является аутентификацией. Пользователи, владение задачами и защитные механизмы остаются следующей главе.

Основной принцип работы: **изучили механизм → переработали конкретную часть Planner → проверили прежние возможности**. Проверка сопровождает изменение, но не заменяет проектное действие во всех занятиях. Финал принимает уже собранную систему, а не впервые соединяет её части.

## 3. Необходимое содержание, границы и решения по материалам

### Архитектурная траектория

1. Завершить понятную организацию FastAPI: настройки, зависимости, типизированные параметры, headers и cookie. Рабочее хранение пока JSON.

3. Заменить контракт полного файлового снимка контрактом предметных запросов. Подготовить SQL-реализацию за тем же `PlannerService`, защитить её проверками и переключить оба интерфейса без раздвоения данных.
4. Углубить обработку ошибок, наблюдение SQL и обоснованное улучшение запросов. Убрать переходные обходы и передать готовую основу следующей главе, не добавляя сюда управление изменениями схемы.

### Решения, которые нельзя оставлять скрытыми

- **Отдельная папка базы:** `app/DBase/`. `engine.py` содержит сборку Engine из настроек; `models.py` содержит общий Base и ORM-модель `TaskRow`; `session.py` появляется после знакомства с Session и содержит фабрику. Подключение этих файлов не создаёт таблицы автоматически. Исходная схема создаётся явной командой через Base.metadata.create_all; существующие данные не удаляются при повторном запуске. Команда не исправляет несовместимую старую схему: такая ситуация требует остановки и понятного сообщения, не удаления файла БД. `DBase` пишется одинаково во всех импортах, в том числе на Linux.
- **Три разных представления:** Pydantic-схема описывает HTTP-вход/ответ, существующая `Task` описывает предметное состояние, `TaskRow` описывает таблицу. Не называем три разных класса просто `Task` и не дублируем прикладные правила в роутере. Различие объясняется до преобразований между ними.
- **ORM-схема сохраняет данные:** `id`, `title`, `priority`, `is_done`, `tags`. Обязательные значения, primary key и диапазон priority защищаются объяснёнными ограничениями таблицы; String(120) сам по себе не объявляется проверкой длины в SQLite. Для имеющегося списка тегов достаточно JSON-колонки SQLite через SQLAlchemy, это не прежний файловый JsonStorage. Присваивание нового списка объясняется отдельно от незаметной для обычной JSON-колонки мутации на месте. Не вводим Category, новые публичные поля или уникальность title ради демонстрации библиотеки.
- **Операции хранения:** нынешний `load/save` всего списка непригоден как основной SQL-контракт. В 85–86 вводится временный JsonTaskRepository поверх прежнего JsonStorage. Сначала существующий сервис переводится на новый контракт чтения, затем изменения; оба шага продолжают работать с тем же файлом. Старые обращения к storage внутри сервиса удаляются после второго шага. Это одна поэтапная переработка границы, не второй Planner. Прикладные правила остаются в одном сервисе; SqlTaskRepository реализует тот же набор операций без полного снимка таблицы.
- **Расположение запросов:** `app/routers/tasks/` является HTTP-пакетом с `router.py` и схемами. SQL-репозиторий относится к границе хранения, поэтому в занятии 87 он создаётся в `app/DBase/repositories.py` рядом с engine, Session и ORM-моделью. `app/repositories.py` сохраняет JSON-адаптер. Ни SQL-репозиторий, ни HTTP-маршрут не дублируют обязанности другого слоя.
- **Session и транзакция:** Engine и фабрика переиспользуются, Session нет. В API ресурс выделяется на запрос; в CLI на отдельную команду, не на весь бесконечный цикл. Роутер не делает SQL/commit, репозиторий не фиксирует отдельные кусочки бизнес-операции. Сервис определяет границу изменения: запись завершается commit до успешного ответа, ошибка ведёт к rollback. Закрытие Session в зависимости освобождает ресурс, а не выполняет поздний commit после отправки ответа.
- **Одна точка сборки:** развиваем существующий `build_service`, не создаём параллельные версии сервиса. После переключения он собирает `PlannerService` с SQL-репозиторием и явно полученным ресурсом. HTTP-зависимость и CLI-область команды используют одну конфигурацию базы. CLI не вызывает FastAPI Depends и не удерживает давно закрытую Session.
- **Подготовка не равна переключению:** SQL-операции сначала проверяются через изолированную БД и подмену зависимости существующих маршрутов. Штатный JSON-путь остаётся целиком активным до занятия 98. Не разрешаем обычному GET читать SQLite, пока обычный POST пишет в JSON. Проверка SQL-пути означает выполненную предметную операцию с повторным чтением из БД, а не только импорт нового класса.
- **Переход данных:** отдельная явно запускаемая команда читает сохранённый JSON, полностью проверяет записи и переносит их одной транзакцией только в пустую целевую таблицу. Сохраняет id, значения и tags; старые записи без tags получают прежнее совместимое значение `[]`. Проверяет повторы id и заполняет техническое поле поиска. Повторный запуск на непустой таблице прекращается без изменений. Команда не зависит от прежнего JsonStorage: обычное чтение JSON и существующие валидаторы достаточны. Это не постоянная синхронизация двух хранилищ и не неограниченная перезапись рабочей базы.
- **Переключение:** на время финального импорта остановлены API и CLI. Сделана резервная копия JSON; затем оба интерфейса переводятся на одну базу. Нельзя после новых записей в SQLite просто вернуться к старому JSON и объявить это безопасным откатом. Восстановление требует остановки и согласованной копии актуальных данных.
- **Поиск не меняет смысл:** прежний search ищет буквальную подстроку после Python lower, в том числе в русских названиях. SQLite LIKE/lower нельзя автоматически считать эквивалентом этого поведения. Поэтому title_normalized входит в исходную схему в 81: это объяснённая техническая копия заголовка после того же Python lower, не новое поле задачи в HTTP. В 90–92 и при импорте она заполняется и обновляется вместе с title; в 95 применяется SQL-поиск буквальной подстроки. Не нужен ни поздний backfill, ни изменение схемы, ни загрузка всей таблицы в Python для штатного поиска.
- **Завершение JSON-перехода:** после переключения убираются JsonTaskRepository, JsonStorage/MemoryStorage из рабочего приложения, их провайдеры, JSON_PATH и выбор backend из настроек/точек запуска. Если app/storage.py остался без потребителей, файл удаляется, а не сохраняется «на всякий случай». Проверки прежнего формата относятся к отдельной команде переноса данных; старые тесты JSON-backend не заставляют держать его в новой рабочей архитектуре. Резервная копия старого JSON может храниться отдельно как архив, но приложение её не читает.
- **JSON как формат не запрещён:** HTTP-ответы и запросы остаются JSON; уже имеющиеся tags могут храниться в JSON-колонке SQLite. Убирается именно файл как рабочее хранилище задач и возможность обхода БД, а не формат обмена данными.

**Проект на входе.** `app/main.py:build_service` собирает PlannerService над JsonStorage. `app/core/config.py` содержит JSON_PATH, APP_NAME и COOKIE_SECURE; путь JSON привязан к корню проекта. API получает сервис через get_planner/PlannerDep, в CLI запускается прежний run. API и CLI используют один файл и прежние предметные операции. `app/routers/tasks/crud.py` пока пустой. DBase, DATABASE_URL, ORM-модели, фабрики Session и get_db ещё нет.

**Данные и сохранённые правила.** Task содержит id, title, priority, is_done и внутренние tags. Id положительный целый, priority в диапазоне 1–5, заголовок не пустой, tags не разделяют один список между задачами. Старые четырёхпольные JSON-записи без tags поддерживаются. В HTTP tags не становятся новым публичным полем. Поиск использует буквальную подстроку после Python `strip().lower()` для запроса и `lower()` для заголовка; статистика сервиса имеет all/open/done, HTTP переводит all в total.

**Чего нельзя предполагать.** Ученик ещё не знает SQL, таблиц, Engine, ORM, Session, транзакций, генераторной зависимости с yield и жизненного цикла SQL-ресурса. Он не обязан уметь заменить файловое хранение запросами или объяснить SQLite-поиск. Всё это впервые вводится здесь до применения.

### Точка B блока = A15

**Понимание.** Ученик различает файл JSON, таблицу, предметную Task, ORM TaskRow, Engine, фабрику Session, отдельную Session и транзакцию. Может объяснить, почему flush не равен commit, почему закрытие не подтверждает запись и зачем операциям нужны rollback и явная область ресурса.

**Готовые компоненты.** Созданы DBase/engine.py, DBase/models.py, DBase/session.py и явная команда первоначального создания таблицы. Исходная схема содержит все прежние данные и технический title_normalized. Есть преобразование строки в обычную Task, SQL-чтение списка/по id, тестовая сборка SQL-сервиса, get_db и ресурсная область для будущей CLI-команды. Есть проверенный отдельный импорт старых данных в пустую базу.

**Изменение работающего проекта.** PlannerService использует операции репозитория, а не прямые load/save. Полный переходный JsonTaskRepository работает поверх того же JsonStorage, без второго файла и кеша снимка. Все прежние API/CLI-операции продолжают читать и изменять один JSON. SQL-проверки используют отдельную тестовую базу и не становятся штатным маршрутом пользователя.

**Что ещё предстоит.** Полный SQL CRUD, SQL-фильтрация/агрегаты/поиск и штатные ресурсные области CLI реализуются в блоке 15. Переключение обоих интерфейсов происходит в 98, удаление JSON-backend в 99. Подготовленный SqlTaskRepository в B14 намеренно неполный: его нельзя объявлять готовой заменой JSON для всего сервиса.

### Границы и решения, общие для всех паспортов

1. **Не смешивать источники.** До общего переключения обычный POST и обычный GET работают с JSON. SQL демонстрируется отдельным тестом существующего компонента, не новым «учебным» API и не скрытым backend-переключателем.
2. **Не вводить миграции схемы.** Здесь только исходная схема и create_all для отсутствующих таблиц. Не изучаем Alembic, revision, upgrade и изменение населённой таблицы. Несовпадение схемы диагностируем, не исправляем автоматическим удалением данных.
3. **Не переписывать продукт.** Сохраняем Task, PlannerService, маршруты, схемы, CLI-команды, настройки и preferences. Не добавляем TaskBoard, Category, created_at или новые пользовательские возможности ради ORM.
4. **Тестовая база является изоляцией, а не вторым проектом.** Для проектных SQL-проверок используем файл SQLite в tmp_path и созданную там исходную схему. `:memory:` нужен только короткому исследованию SQL. Не переносим его без объяснения в многосоединительный TestClient.
5. **Ресурс и транзакция имеют разные границы.** Engine и фабрика повторно используются; Session не глобальна и не разделяется между параллельными запросами. Репозиторий чтения не делает commit. В будущем запись подтверждается в предметном сценарии до успешного ответа, не отложенным commit после yield.
6. **Данные сохраняют смысл.** Не обрезаем старые CLI-заголовки под HTTP-лимит, не меняем id, не теряем tags, не вводим уникальность заголовков. title_normalized хранит Python `title.lower()`, но не появляется в Task/HTTP. Это подготовка прежнего поиска, не новая модель задачи.
7. **Реальное поведение проверяем реальным инструментом.** Симулятор Session допустим лишь как обсуждение модели; основная приёмка использует SQLAlchemy и повторное чтение из независимой Session. Не учим, что Session.close всегда делает объект навсегда непригодным: это не универсальное правило SQLAlchemy.

### Проверяемые критерии B14

1. Ученик объясняет ограничения файлового снимка и читает/изменяет небольшую SQL-таблицу с параметрами. SQLite не объявляется автоматическим решением любой конкуренции.
2. Engine выбирает предсказуемый адрес, исходная таблица создаётся явно, текущие config/preferences не сломаны. Нет случайной рабочей БД от другой cwd и DDL при каждом запросе.
3. Схема сразу включает прежние пять полей и title_normalized; нет потерянных tags, новых пользовательских полей, нового ограничения исторических заголовков или подготовки миграций.
4. add/flush/commit/refresh и rollback/close различаются; независимое чтение подтверждает успех и отсутствие частичной записи при отказе. Проверка не заменена симулятором флагов.
5. Mapping возвращает обычную Task, доступную после Session. Отсутствие id и копии tags проверены; служебный заголовок не выходит в HTTP.
6. Сервис перешёл на операции репозитория без прямых load/save. Все прежние операции, ошибки, выборка, поиск, статистика и внутренние tags сохранены полным JSON-адаптером.
7. SQL list/get действительно читают SQLite; неполная реализация не включена как default и не использует JSON-fallback. Не заявлена приёмка ещё не написанных SQL search/stats/CRUD.
8. Тестовый GET по id проходит через прежние provider/service/route/schema с отдельной Session. Освобождение при успехе/ошибке и восстановление overrides проверены; CLI-контекст не зависит от FastAPI.
9. Импорт сохраняет все данные и id, требует пустой цели и одну транзакцию, не портит источник, не оставляет частичную запись. Старый формат принят по прежним правилам, плохие данные не исправляются молча.
10. Обычные API и CLI всё ещё используют один JSON. Работа без ошибок на тестовой SQL-копии не называется завершённым переходом. В концепте и будущей приёмке нет миграций схемы.

### B14 = A15: точный договор

Следующий блок получает **тот же работающий Planner на JSON с новым репозиторным договором** и подготовленную SQL-инфраструктуру. Есть таблица/модель, Engine/SessionFactory, mapping, SQL list/get, ресурсные области и самостоятельный импорт. Ничего из этого не нужно создавать повторно только ради первого SQL POST.

В следующем блоке ещё нужно реализовать SQL create с серверным id, затем PUT/PATCH/done/delete, выборку, статистику и поиск; подготовить настоящий ресурс на CLI-команду и доказать полный набор операций. SQL-сценарий записи должен подтвердиться до успешного HTTP-ответа. Это не задача get_db и не обязанность каждой мелкой операции репозитория независимо сделать commit.

В 98 записи через оба интерфейса останавливаются, выбирается актуальный снимок, выполняется перенос в согласованную пустую цель и штатная сборка обоих интерфейсов переключается вместе. Репетиционная база из 89 не считается актуальной автоматически; непустую цель не очищают без отдельного осознанного действия. В 99 удаляется переходный файловый backend, а импортёр остаётся отдельным инструментом. Эта последовательность гарантирует, что A15 не предполагает ни полного SQL CRUD, ни уже отключённого JSON.
