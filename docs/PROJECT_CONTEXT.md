## Концепция курса — выбранный контекст

Источник: `docs/concept/chapter_04/COURSE.md`.

### Цель и итог главы

Глава строит воспроизводимый синхронный Planner на FastAPI, SQLite и SQLAlchemy: от явных настроек и сборки через ресурс Session и транзакции к SQL CRUD, импорту имеющихся задач, надёжным отказам, наблюдению запросов и чистой передаче результата. Целевой продукт использует один SQLite путь для API и CLI, сохраняет существующий предметный договор и запускается из чистого checkout по README.

### Архитектурная траектория и границы

- Настройки и `DATABASE_URL` → Engine/SessionFactory → короткоживущая Session на HTTP-запрос или CLI-команду → единый сервис и SQL-репозиторий.
- Транзакционная граница принадлежит сценарию сервиса; репозиторий не подтверждает части операции. HTTP и CLI используют один адрес базы, но независимые короткие ресурсы.
- Переход данных в SQL выполняется явно и проверяемо. Импорт прежнего JSON — отдельная команда, не startup, не fallback и не постоянная синхронизация. Инициализация схемы явная; `create_all` не является миграцией и не чинит несовместимую существующую схему.
- Сохраняются CRUD, выборки, статистика и внешние договоры Planner. Не добавляются ради учебного финала новые сущности, endpoints, индексы, асинхронность или deployment.
- Отказы классифицируются по причине: известная недоступность хранилища может стать безопасным 503, прежние 404/422 сохраняются, неизвестная ошибка остаётся серверной. `IntegrityError` не означает автоматически пользовательский конфликт; `OperationalError` не всегда означает временную недоступность.
- Диагностика SQL включается осознанно, по умолчанию выключена, не раскрывает параметры, секреты, содержимое пользовательских данных или путь к БД. Автоматический повтор неопределённо завершившегося create недопустим.
- Следующая глава сначала вводит изменение уже существующей схемы, затем пользователя/владение и контроль доступа. В текущей главе не считаются готовыми миграции, отношения, `User`/`owner_id`, login, серверная сессия/JWT или авторизация. Cookie настроек представления не является аутентификацией.

### Проверка готовности главы и передача

Итог должен быть воспроизводим из чистого checkout: README ведёт через окружение, настройки, явную исходную схему, API/CLI и тесты; нет секретов или рабочих данных в передаваемом Git-составе. Оба интерфейса работают с одной базой, а отдельный импорт не запускается автоматически. Передача следующей главе точно описывает имеющиеся модель/таблицу задач, SQL операции, сборку ресурсов, интерфейсы и проверки, не приписывая продукту миграции или авторизацию.

### Назначение и опора A→B

Блок 16 (занятия 100–105) делает уже переключённый на SQLite Planner надёжным, наблюдаемым и воспроизводимым. Его A — целевой результат B15: один SQL-путь, полный CRUD/query/CLI, сохранённые данные и отсутствие JSON-backend. При создании планов фактическое достижение A нужно отдельно подтвердить по состоянию проекта/StudyHub до занятия; паспорт задаёт цель, но не доказывает её.

B блока — безопасная классификация известных отказов, проверенные rollback/commit и восстановление независимой операции, управляемое безопасное SQL-наблюдение, обоснованная узкая оптимизация либо доказанная достаточность запроса и чистая воспроизводимая передача продукта. Исходная схема и публичный договор сохраняются; JSON fallback не возвращается.

### Маршрут шести занятий

1. **100 — Ошибка БД и граница ответственности:** известная причина отказа переводится в безопасный HTTP/CLI результат; не смешивать с ошибками ввода и неизвестными внутренними сбоями.
2. **101 — Проверки отказов и восстановление работы:** изолированно проверить connect/query/flush/commit, rollback, закрытие ресурса и следующую независимую операцию; после успешного commit исключение не доказывает отмену.
3. **102 — Какие SQL-запросы делает Planner:** управляемо наблюдать реальные запросы, отличать запрос приложения от seed/DDL и не раскрывать параметры.
4. **103 — Обоснованное улучшение запросов:** использовать конкретное наблюдение/план запроса; улучшить только доказанную лишнюю работу или защитить узко проверкой достаточный запрос. Не обещать ускорение без данных и не менять схему ради упражнения.
5. **104 — Сквозная проверка готового продукта:** проверить обычные API/CLI и ранее собранные компоненты после доработок, без повторной реализации уже готового.
6. **105 — Передача работающего DB Planner:** чистый checkout, README, явная исходная схема, окружение, оба интерфейса и тесты; точно описать границу следующей главы.

### Инварианты при составлении планов

- A/B паспорта и фактическое состояние до занятия должны быть явно разделены: запланированное не выдавать за изученное или реализованное.
- Сохраняются поля и поведение прежнего Planner, транзакционная и ресурсная границы, один SQL backend, отдельный явный импорт JSON и исходная схема. Нет миграций, нового индекса/колонки, auth или пользовательского владения.
- Известные ошибки переводятся по причине и в правильном слое. Не проглатывать неизвестные исключения, не выдавать ложный успех/пустой результат и не включать fallback. Операция до commit должна откатываться; успешный commit не отменяется последующим исключением.
- Все проверки отказов выполняются только на изолированной временной БД/Session/Engine. Не повреждать и не чистить рабочие данные; временные подмены и listeners/loggers восстанавливать.
- Не раскрывать SQL параметры, пользовательские данные, секреты, `.env`, путь к БД или traceback клиенту. SQL диагностируется только при явном включении.
- Следующая глава начинается с управления изменением населённой схемы и затем вводит User/ownership/access; cookie предпочтений не является login-сессией.

### Приёмка B16

Принимается только результат, где сохранён единый SQLite путь для API/CLI и прежний внешний договор; отказы не превращаются в успех, 409 или JSON fallback; rollback и граница commit подтверждены; диагностика безопасна и отключена по умолчанию; улучшение обосновано фактическим запросом без изменения схемы; тесты изолированы от рабочих данных; чистый checkout проходит README. ### BLOCK_14.md — выбранный контекст

Источник: `docs/concept/chapter_04/BLOCK_14.md`.

**Назначение и границы.** Блок 14 (занятия 78–89) подготавливает переход от файлового Planner к SQL-хранилищу без преждевременной смены рабочего backend. До общего переключения обычные API и CLI продолжают работать через JSON; исследовательские SQL-опыты изолированы, а интеграционные проверки используют отдельную SQLite-базу. Не добавляются миграции, новые продуктовые сущности и скрытая синхронизация источников. Сохраняются модель `Task`, сервис, маршруты, схемы и настройки. `title_normalized` хранит результат `title.lower()`, но не попадает в `Task` или HTTP.

**Точка A → B.** На входе есть рабочий JSON Planner, известные операции и проверенные настройки, но нет SQLAlchemy-хранилища. На выходе подготовлена исходная схема и SQL-инфраструктура, пройдено чтение/изменение через слой хранения, ресурсные проверки и однократный явный импорт JSON. Это подготовка для дальнейшей реализации операций и переключения; само наличие паспорта не подтверждает, что занятия или операции фактически пройдены.

**Маршрут занятий.**

1. **78 — Почему одного JSON становится мало:** исследовать load/save и объяснить ограничения файлового снимка, не повреждая рабочий файл.
2. **79 — SQLite и минимальный SQL:** на данных в памяти понять таблицы, строки, параметры, выборки и адресные изменения.
3. **80 — Engine и адрес базы:** добавить явные настройки адреса и воспроизводимое подключение, не переключая API/CLI.
4. **81 — ORM-модель и исходная схема:** описать `TaskRow`, сохранить прежние модели/контракты и явно создать проверяемую исходную схему.
5. **82 — Session: первая сохранённая запись:** различить `add`, `flush`, `commit`, `refresh` и увидеть запись в независимой Session.
6. **83 — Транзакция, отмена и закрытие:** проверить реальный отказ, rollback и последующую успешную операцию на изолированной базе.
7. **84 — SELECT и преобразование результата:** читать ORM-строки и преобразовывать в обычную `Task`, не выдавая ORM наружу.
8. **85 — Новая граница хранения: чтение:** ввести JSON-адаптер и перенести чтение, сохранив прежний источник данных.
9. **86 — Новая граница хранения: изменения:** перенести существующие записи через адаптер, не включая SQL в штатный поток.
10. **87 — SQL-репозиторий чтения:** создать SQL-репозиторий рядом с моделью и проверить `list/get` без commit.
11. **88 — Ресурс на запрос и на команду:** проверить область ресурса для HTTP и подготовить ресурсный контекст CLI.
12. **89 — Однократный перенос прежних задач:** импортировать копию JSON в пустую тестовую базу одной транзакцией, отдельной командой.

**Критерии для последующих планов.** Каждое действие опирается на подтверждённый навык или объясняется до применения. План отделяет подтверждённое состояние до урока от цели паспорта. ### Что ученик действительно приносит

После предыдущей главы есть один Persistent Planner, который в репозитории называется StudyHub Planner. HTTP API и CLI используют один прикладной сервис и `data/tasks.json`. JSON уже сохраняет данные после перезапуска. Нельзя объяснять будущую базу как первое появление persistence.

Ученик знаком с функциями, модулями, обычными классами, `dataclass`, композицией, исключениями, JSON, pytest, Git, HTTP, FastAPI, Pydantic и APIRouter. Он уже применяет path/query/body, схемы создания и обновления, HTTP-ошибки и независимые API-тесты. Подробное понимание Depends, конфигурации среды, SQL и SQLAlchemy ещё не считается достигнутым.

Подтверждённые роли и возможности:

| Часть | Фактическое состояние |
| --- | --- |
| `app/api.py` | Создаёт FastAPI, собирает сервис через `build_service()`, хранит его в `app.state.planner`, подключает роутер; содержит `/health` и `/stats` |
| `app/main.py` | Содержит `build_service(storage=None)`, устойчивый путь к JSON и запуск CLI |
| `app/models.py` | Содержит предметную `Task`: `id`, `title`, `priority`, `is_done`, `tags`, правила и преобразование в запись |
| `app/services.py` | Один `PlannerService`: добавление, чтение, выборка, поиск, статистика, PUT/PATCH, завершение и удаление |
| `app/storage.py` | `MemoryStorage` и `JsonStorage`; сервис использует `load()` и `save()` целого списка |
| HTTP API | GET списка и одной задачи, POST, PUT, PATCH, DELETE; `/stats` и `/health` |
| CLI | `add`, `list`, `find`, `done`, `search`, `stats`, `exit`; не переписывается новым продуктом |
| Проверки | Тесты модели, хранения, сервиса, CLI, HTTP-контракта и сквозного сценария; API-fixture подменяет сервис и использует отдельный JSON через `tmp_path` |

Внешняя форма HTTP-задачи имеет четыре поля: `id`, `title`, `priority`, `is_done`. Внутренние `tags` уже существуют в модели и JSON, хотя не входят в HTTP-схемы. Они не исчезают при замене хранения. Создание получает серверный id; приоритет находится в диапазоне 1–5. HTTP-заголовок задачи ограничен 120 символами, а предметный валидатор сейчас не вводит этот максимум для всех источников данных. Нельзя молча распространить HTTP-ограничение на старые CLI-записи при импорте.

Известный договор сохраняется: положительный path-id, фильтр `is_done`, сортировка по id, `limit` по умолчанию 10 в диапазоне 1–50; статусы 200/201/204/404/422. PATCH игнорирует отсутствующие поля и явный `null`, но применяет `False`; пустой PATCH не меняет задачу. PUT сохраняет прежние внутренние теги. DELETE возвращает пустой body. HTTP-статистика называет число всех задач `total`, прикладной сервис сейчас использует ключ `all`.

## 2. Цель, точка B и итоговый проект

Ученик проходит путь от работающего JSON-backed FastAPI к одному синхронному Planner на SQLite/SQLAlchemy. Он понимает не только вызовы библиотеки, но и путь данных, ответственность слоёв, время жизни ресурсов и границу завершённой операции.

**B главы:** API и CLI обращаются к одной настроенной SQLite-базе через общее прикладное ядро. Все прежние операции работают; существующие задачи перенесены без потери id и внутренних полей. Ошибки не превращаются в ложный успех, не оставляют частично сохранённое изменение и не раскрывают внутренности БД клиенту. Выборка, сортировка, поиск и статистика выполняются запросами, а не загрузкой и перезаписью всей таблицы. Есть явная инициализация исходной схемы, изолированные проверки и понятный запуск. Файлового JSON-backend, настройки его выбора и автоматического возврата к нему в рабочем приложении больше нет.

Миграции схемы, Alembic и изменение уже созданных таблиц изучаются в следующей главе. Здесь один раз проектируем исходную схему, создаём её явной командой и используем без дальнейших изменений. Однократный **перенос прежних задач из JSON** остаётся необходимой частью перехода на БД; это не занятие о миграциях схемы.

Итоговый проект дополнительно умеет использовать централизованные настройки, внедрение зависимостей и небольшую cookie-настройку представления. Cookie не является аутентификацией. Пользователи, владение задачами и защитные механизмы остаются следующей главе.

Основной принцип работы: **изучили механизм → переработали конкретную часть Planner → проверили прежние возможности**. Проверка сопровождает изменение, но не заменяет проектное действие во всех занятиях. Финал принимает уже собранную систему, а не впервые соединяет её части.

### Решения, которые нельзя оставлять скрытыми

- **Отдельная папка базы:** `app/DBase/`. `engine.py` содержит сборку Engine из настроек; `models.py` содержит общий Base и ORM-модель `TaskRow`; `session.py` появляется после знакомства с Session и содержит фабрику. Подключение этих файлов не создаёт таблицы автоматически. Исходная схема создаётся явной командой через Base.metadata.create_all; существующие данные не удаляются при повторном запуске. Команда не исправляет несовместимую старую схему: такая ситуация требует остановки и понятного сообщения, не удаления файла БД. `DBase` пишется одинаково во всех импортах, в том числе на Linux.
- **Три разных представления:** Pydantic-схема описывает HTTP-вход/ответ, существующая `Task` описывает предметное состояние, `TaskRow` описывает таблицу. Не называем три разных класса просто `Task` и не дублируем прикладные правила в роутере. Различие объясняется до преобразований между ними.
- **ORM-схема сохраняет данные:** `id`, `title`, `priority`, `is_done`, `tags`. Обязательные значения, primary key и диапазон priority защищаются объяснёнными ограничениями таблицы; String(120) сам по себе не объявляется проверкой длины в SQLite. Для имеющегося списка тегов достаточно JSON-колонки SQLite через SQLAlchemy, это не прежний файловый JsonStorage. Присваивание нового списка объясняется отдельно от незаметной для обычной JSON-колонки мутации на месте. Не вводим Category, новые публичные поля или уникальность title ради демонстрации библиотеки.
- **Операции хранения:** нынешний `load/save` всего списка непригоден как основной SQL-контракт. В 85–86 вводится временный JsonTaskRepository поверх прежнего JsonStorage. Сначала существующий сервис переводится на новый контракт чтения, затем изменения; оба шага продолжают работать с тем же файлом. Старые обращения к storage внутри сервиса удаляются после второго шага. Это одна поэтапная переработка границы, не второй Planner. Прикладные правила остаются в одном сервисе; SqlTaskRepository реализует тот же набор операций без полного снимка таблицы.
- **Расположение запросов:** `app/routers/tasks/` является HTTP-пакетом с `router.py` и схемами. SQL-репозиторий относится к границе хранения, поэтому в занятии 87 он создаётся в `app/DBase/repositories.py` рядом с engine, Session и ORM-моделью. `app/repositories.py` сохраняет JSON-адаптер. Ни SQL-репозиторий, ни HTTP-маршрут не дублируют обязанности другого слоя.
- **Session и транзакция:** Engine и фабрика переиспользуются, Session нет. В API ресурс выделяется на запрос; в CLI на отдельную команду, не на весь бесконечный цикл. Роутер не делает SQL/commit, репозиторий не фиксирует отдельные кусочки бизнес-операции. Сервис определяет границу изменения: запись завершается commit до успешного ответа, ошибка ведёт к rollback. Закрытие Session в зависимости освобождает ресурс, а не выполняет поздний commit после отправки ответа.
- **Одна точка сборки:** развиваем существующий `build_service`, не создаём параллельные версии сервиса. После переключения он собирает `PlannerService` с SQL-репозиторием и явно полученным ресурсом. HTTP-зависимость и CLI-область команды используют одну конфигурацию базы. CLI не вызывает FastAPI Depends и не удерживает давно закрытую Session.
- **Подготовка не равна переключению:** SQL-операции сначала проверяются через изолированную БД и подмену зависимости существующих маршрутов. Штатный JSON-путь остаётся целиком активным до занятия 98. Не разрешаем обычному GET читать SQLite, пока обычный POST пишет в JSON. Проверка SQL-пути означает выполненную предметную операцию с повторным чтением из БД, а не только импорт нового класса.
- **Переход данных:** отдельная явно запускаемая команда читает сохранённый JSON, полностью проверяет записи и переносит их одной транзакцией только в пустую целевую таблицу. Сохраняет id, значения и tags; старые записи без tags получают прежнее совместимое значение `[]`. Проверяет повторы id и заполняет техническое поле поиска. Повторный запуск на непустой таблице прекращается без изменений. Команда не зависит от прежнего JsonStorage: обычное чтение JSON и существующие валидаторы достаточны. Это не постоянная синхронизация двух хранилищ и не неограниченная перезапись рабочей базы.
- **Переключение:** на время финального импорта остановлены API и CLI. Сделана резервная копия JSON; затем оба интерфейса переводятся на одну базу. Нельзя после новых записей в SQLite просто вернуться к старому JSON и объявить это безопасным откатом. Восстановление требует остановки и согласованной копии актуальных данных.
- **Поиск не меняет смысл:** прежний search ищет буквальную подстроку после Python lower, в том числе в русских названиях. SQLite LIKE/lower нельзя автоматически считать эквивалентом этого поведения. Поэтому title_normalized входит в исходную схему в 81: это объяснённая техническая копия заголовка после того же Python lower, не новое поле задачи в HTTP. В 90–92 и при импорте она заполняется и обновляется вместе с title; в 95 применяется SQL-поиск буквальной подстроки. Не нужен ни поздний backfill, ни изменение схемы, ни загрузка всей таблицы в Python для штатного поиска.
- **Завершение JSON-перехода:** после переключения убираются JsonTaskRepository, JsonStorage/MemoryStorage из рабочего приложения, их провайдеры, JSON_PATH и выбор backend из настроек/точек запуска. Если app/storage.py остался без потребителей, файл удаляется, а не сохраняется «на всякий случай». Проверки прежнего формата относятся к отдельной команде переноса данных; старые тесты JSON-backend не заставляют держать его в новой рабочей архитектуре. Резервная копия старого JSON может храниться отдельно как архив, но приложение её не читает.
- **JSON как формат не запрещён:** HTTP-ответы и запросы остаются JSON; уже имеющиеся tags могут храниться в JSON-колонке SQLite. Убирается именно файл как рабочее хранилище задач и возможность обхода БД, а не формат обмена данными.

**Понимание.** Ученик различает файл JSON, таблицу, предметную Task, ORM TaskRow, Engine, фабрику Session, отдельную Session и транзакцию. Может объяснить, почему flush не равен commit, почему закрытие не подтверждает запись и зачем операциям нужны rollback и явная область ресурса.

### Границы и решения, общие для всех паспортов

1. **Не смешивать источники.** До общего переключения обычный POST и обычный GET работают с JSON. SQL демонстрируется отдельным тестом существующего компонента, не новым «учебным» API и не скрытым backend-переключателем.
2. **Не вводить миграции схемы.** Здесь только исходная схема и create_all для отсутствующих таблиц. Не изучаем Alembic, revision, upgrade и изменение населённой таблицы. Несовпадение схемы диагностируем, не исправляем автоматическим удалением данных.
3. **Не переписывать продукт.** Сохраняем Task, PlannerService, маршруты, схемы, CLI-команды, настройки и preferences. Не добавляем TaskBoard, Category, created_at или новые пользовательские возможности ради ORM.
4. **Тестовая база является изоляцией, а не вторым проектом.** Для проектных SQL-проверок используем файл SQLite в tmp_path и созданную там исходную схему. `:memory:` нужен только короткому исследованию SQL. Не переносим его без объяснения в многосоединительный TestClient.
5. **Ресурс и транзакция имеют разные границы.** Engine и фабрика повторно используются; Session не глобальна и не разделяется между параллельными запросами. Репозиторий чтения не делает commit. В будущем запись подтверждается в предметном сценарии до успешного ответа, не отложенным commit после yield.
6. **Данные сохраняют смысл.** Не обрезаем старые CLI-заголовки под HTTP-лимит, не меняем id, не теряем tags, не вводим уникальность заголовков. title_normalized хранит Python `title.lower()`, но не появляется в Task/HTTP. Это подготовка прежнего поиска, не новая модель задачи.
7. **Реальное поведение проверяем реальным инструментом.** Симулятор Session допустим лишь как обсуждение модели; основная приёмка использует SQLAlchemy и повторное чтение из независимой Session. Не учим, что Session.close всегда делает объект навсегда непригодным: это не универсальное правило SQLAlchemy.

### Проверяемые критерии B14

1. Ученик объясняет ограничения файлового снимка и читает/изменяет небольшую SQL-таблицу с параметрами. SQLite не объявляется автоматическим решением любой конкуренции.

5. Mapping возвращает обычную Task, доступную после Session. Отсутствие id и копии tags проверены; служебный заголовок не выходит в HTTP.
6. Сервис перешёл на операции репозитория без прямых load/save. Все прежние операции, ошибки, выборка, поиск, статистика и внутренние tags сохранены полным JSON-адаптером.
7. SQL list/get действительно читают SQLite; неполная реализация не включена как default и не использует JSON-fallback. Не заявлена приёмка ещё не написанных SQL search/stats/CRUD.
8. Тестовый GET по id проходит через прежние provider/service/route/schema с отдельной Session. Освобождение при успехе/ошибке и восстановление overrides проверены; CLI-контекст не зависит от FastAPI.
9. Импорт сохраняет все данные и id, требует пустой цели и одну транзакцию, не портит источник, не оставляет частичную запись. Старый формат принят по прежним правилам, плохие данные не исправляются молча.
10. Обычные API и CLI всё ещё используют один JSON. Работа без ошибок на тестовой SQL-копии не называется завершённым переходом. В концепте и будущей приёмке нет миграций схемы.

### Знания и самостоятельные действия

К завершению главы ученик способен:

1. Прочитать небольшой Python-код и проследить значения, выбранные ветви, повторения и вызовы функций.
2. Выбрать базовый тип и коллекцию, объяснить ссылку на изменяемый объект и отличие изменения объекта от переприсваивания имени.
3. Выделить функцию по понятной ответственности, передать данные через параметры, вернуть результат и отличить это от вывода человеку.
4. Найти простую причину ошибки, воспроизвести её, исправить и повторно проверить прежний сценарий.
5. Запустить свой локальный файл выбранным Python; отличить исходный код, команды терминала, интерпретатор и редактор.
6. Сохранить осмысленную проверенную версию через status/diff/staging/commit, отправить её на GitHub и получить проект заново через clone.
7. Самостоятельно пользоваться готовым Planner, объяснить путь ввода к результату и изменить знакомую часть с проверкой сохранённых возможностей.

Эти навыки формируются постепенно. Наличие команды в листинге или успешное копирование инструкции не подтверждает самостоятельного понимания.

### Договор итогового проекта по точному коммиту

Продукт называется StudyHub Planner. Это консольная программа без сторонних Python-пакетов. Основная реализация находится в одном `main.py`; функции определены до прямого вызова `run()` в конце. Данные живут только в памяти текущего запуска.

| --- | --- |

| Общие данные | Один список `tasks` создаётся внутри `run()` до цикла. Функции получают его явно; он сохраняет изменения между командами одного запуска |
| Команды | Ровно `add`, `list`, `find`, `done`, `search`, `stats`, `exit`. Команда очищается через `strip().lower()`. Неизвестная команда выводит сообщение и возвращает к меню |
| Добавление | Id равен максимуму текущих id плюс один, для пустого списка 1. Подготовленные значения передаются фабрике; одна новая запись добавляется в общий список |

| Завершение | Меняется только `is_done` найденной задачи. Функция сообщает успех/отсутствие через bool. Повторное завершение найденной задачи допустимо |
| Поиск названия | Очищенный фрагмент ищется без учёта регистра через `lower` и подстроку `in`. Возвращаются все совпадения в исходном порядке. Пустой фрагмент даёт пустой список; интерфейс отдельно сообщает о пустом запросе |

### BLOCK_6.md — выбранный контекст блока

**Назначение и накопление.** Путь блока: разобрать отказ → укрепить функции → разнести существующий код по модулям/пакету и отделить CLI → представить реальные задачи в JSON → подключить загрузку и сохранение → проверить целостность снимка и ошибки хранения. Проверка сопровождает изменение и не подменяет работу в Planner.

**Точка A.** Прежние операции работают через структурированный CLI и один список. В концепте для входа подтверждены `run(tasks=None)`, обработчики и callback-диспетчер, диагностическая обёртка и поля задачи; перед конкретным планом всё равно проверять соответствующую версию проекта и учебные материалы. `except ValueError` уже мог встречаться, но устройство исключений системно не считается изученным. Импорты, безопасный запуск, пути, файлы и JSON не считать знакомыми только из наличия примеров.

**Точка B.** Тот же функциональный Planner находится в `app`, безопасно импортируется и запускается как `python -m app.main`. Общий `read_int` сохраняет предметные диапазоны и сообщения; неверные значения отклоняются до изменения списка; неизвестный id получает явный `TaskNotFoundError`. Один рабочий путь `data/tasks.json` задаёт сборка и передаёт `app.storage`; функции `load_tasks(path)` / `save_tasks(path, tasks)` работают с полным списком исходных четырёхпольных словарей. После успешного изменения используется один callback. Новый процесс восстанавливает данные; чтение и неверный ввод файл не записывают. Весь снимок проверяется до меню; повреждение, неверная форма и проблема доступа дают наблюдаемый отказ, а не тихое `[]`.

Удаление и `tags` не вводятся в блоке 6. Не добавлять второй рабочий список, ручную JSON-базу или повторную сборку приложения в финале.
