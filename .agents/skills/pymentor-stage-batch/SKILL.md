# Массовый Stage 2/3

Исходный чат остаётся единственным Coordinator. Один исполнитель получает **ровно одно занятие и весь его stage**, исправления/RESUME этого занятия допустимы; список из нескольких уроков одному автору запрещён. Опись и общая интеграция — отдельные служебные задания, а не дополнительные оркестраторы.

Модель, усилие и доступная параллельность — из effective policy центрального `C:/Users/Unik/.codex/orchestrator.toml` и явного override текущей задачи. Порядок: `C:/Users/Unik/.codex/skills/orchestrate-codex/references/settings.md`. Здесь нет отдельного жёсткого лимита: применяй фактически доступные слоты и не обходи runtime admission/hooks. Native профили [PLAN](../../../.codex/agents/pymentor-plan-worker.toml) и [MAIN](../../../.codex/agents/pymentor-lesson-worker.toml) закреплены за Sol Web/high; при несовместимой policy нужен разрешённый маршрут с реально доступными инструкциями, а не ложное объявление модели. Spawn ID не доказывает telemetry модели; доверие hooks не следует из наличия файла.

Канон запуска: [BATCH_WORKFLOW](../../../docs/make%20les%20stage/BATCH_WORKFLOW.md), [общий AGENTS](../../../docs/make%20les%20stage/AGENTS.md), [Stage 2](../../../docs/make%20les%20stage/2%20stage/README.md), [Stage 3](../../../docs/make%20les%20stage/3%20stage/README.md). Не загружай все источники в root: работник читает относящиеся к своему действию документы один раз, перечитывает изменённое или недостающий фрагмент.

## Самостоятельные решения и делегирование

Работай так, будто пользователь не отвечает во время прогона. Не задавай ему рутинные вопросы о форматировании, диапазоне примеров, локальной правке, доступном источнике или следующем безопасном шаге. Сначала проверь канонический COURSE/BLOCK, принятый план, точечный соседний материал и применимые правила; затем выбери минимальное обратимое решение, сохраняющее B, предпосылки и закрытые тесты. Существенное допущение пометь как допущение и кратко запиши в существующий RUN с источником и затронутыми ID. Не журналируй очевидные решения.

Coordinator сам разрешает обычную неоднозначность и координирует владельцев общих файлов. В явно названном курсе/главе/блоке он может внести минимальную обратимую правку непосредственного источника, необходимую для запрошенного stage, только если она подтверждена курсом или действительно сопоставимым принятым материалом и не меняет B, предпосылки или обязательный формат. Автор урока пишет лишь назначенные ему пути; расширение его scope назначает только Coordinator. Если безопасного доказуемого решения нет, пометь только зависимые ID `DECISION_REQUIRED`/`BLOCKED`, сообщи один точный вопрос без ожидания ответа и продолжай независимые занятия. Не завершай stage при обязательном незакрытом блокере.

Делегируй: (1) содержательную работу и локальные проверки — ровно одному исполнителю на занятие и весь stage; (2) инвентаризацию — только если текущей описи нет/она изменилась; (3) общие записи и финальные общие checks — одному интегратору; (4) независимый review — только при конкретном риске/противоречии. Coordinator сохраняет effective policy, границы запуска, разрешение cross-lesson/source изменений, решения по конфликтам, stage-gate, финальную N/N приёмку и сообщение пользователю. Не создавай отдельных исполнителей для каждого P/M-прохода, дублирующих ревьюеров или статусных наблюдателей.

1. Установи запрошенные stage, диапазон и разрешённые файлы. Используй существующую достоверную опись; при её отсутствии собери одну компактную опись N, ID, источники/A–B, цели и зависимости. Отдельный preflight-агент не обязателен. Не задерживай готовые независимые занятия из-за чужого неполного входа; незавершённые остаются в N.
2. Выдай каждому автору один lesson ID, его пути, CREATE/REWORK/RESUME, наблюдаемый дефект или цель B, конкретный ожидаемый результат и доступные проверки. [build_dispatch.py](../../../scripts/build_dispatch.py) пакует native assignment без чтения полного payload root. Один автор проходит P1–P4 либо M1–M5, без новых делегатов на каждый проход.

   Для массива с одинаковыми входами сохрани один короткий общий контекст запуска в RUN или соседнем файле: запрос, источники/revision, общие границы записи, средовые ограничения и критерии. В личное назначение передай путь и различия конкретного урока: ID, целевые пути, дефект/цель и владение. Роль и skill должны быть реально доступны исполнителю через поддерживаемый выбор или чтение; ссылка не доказывает загрузку. Если чтение файла недоступно, передай нужное содержание явно. Это кандидат на сокращение дублирования; эффект на токены ещё не измерен.
3. Сначала содержательная работа. Для REWORK прочитать достаточные источники → исправить объяснение/практику → проверить эффект. Не делать отдельные исследование, план приёмки и набор отчётов перед первой правкой. В назначении задавай ориентир первого сохранённого смыслового результата; время учитывай по фактическим timestamp, отделяя задержку модели/инструмента от работы. Отсутствие прогресса требует конкретного блокера, а не новой перепроверки.
4. Автор проверяет только своё изменённое и возвращает `PLAN_ACCEPTED`, `LOCAL_READY`, `PARTIAL` или `BLOCKED` с путями и одним примером результата. `LOCAL_READY` в Stage 3 значит: предметные M1–M5 и доступные локальные проверки завершены, общие уровни M5 ещё ожидаются; это не COMPLETE. Объяснение, практика и перенос знания оцениваются отдельно от сборки; KEEP хорошего материала допустим. Исполнитель не спрашивает пользователя: при рутинной неопределённости фиксирует лучший обоснованный вариант, а при внешнем конфликте сообщает Coordinator точный остаток и продолжает независимую часть.
5. Когда готовы артефакты, один назначенный владелец интегрирует общие файлы и выполняет общие backend/frontend/build/API проверки **один раз на итоговом наборе**, с поурочным покрытием. Осмотр страницы и прогон каждой обязательной задачи остаются поурочными, но браузер/runner поднимаются один раз на среду. Все четыре уровня M5 обязательны; общий PASS можно сослать на несколько уроков лишь при доказанном покрытии, одинаковой версии и зависимостях. Подробности — канон протокола.
6. Root принимает итог и N/N один раз; не повторяет работу исполнителя и не назначает второго ревьюера по умолчанию. При дефекте — адресный REWORK с ожидаемым эффектом, повторить только затронутые проверки. Не повторять успешный тест на неизменном наборе. Средовой отказ — одна диагностика и воспроизводимый blocker, доступное редактирование продолжается; ложный PASS запрещён.

Один [RUN](../../../docs/make%20les%20stage/RUN_TEMPLATE.md): поурочный статус — источник истины; итоговые числа и gate вычисляются из него, не дублируются вручную в противоречивом тексте. Ожидай событиями/одним multi-wait, без статусных ping и чтения промежуточных диалогов. Неизвестный исход spawn сначала сверяется; переназначение только после подтверждения terminal. Изменение P4-источника возвращает только зависимые ID на P4 и удерживает их Stage 3 до повторного принятия. Если пользователь в одном запросе явно заказал последовательность Stage 2 → Stage 3, после P4 всех N переходи автоматически; незапрошенный stage и внешнюю публикацию не запускай. `STAGE_COMPLETE` только при N/N, P4 либо всех четырёх M5 PASS на итоговых версиях.

При каждом возобновлении Coordinator сверяет сохранённые строки RUN с фактическим состоянием каждого указанного worker ID. `RUNNING` в файле — только последнее записанное состояние, не доказательство, что чат всё ещё работает. Для каждой строки зафиксируй одно из трёх: подтверждённо активен, завершён/прерван или состояние пока неизвестно; завершение результата отдельно подтверждается артефактом и нужными checks. Сначала проверь артефакт владельца и остаток его задания, затем решай, что продолжать.

`wait_agent`/event wait вызывай только с точными ID, которые только что подтверждены активными. Пустой список получателей — не ожидание: выполни сверку статусов. Если все исполнители завершены, прерваны или неизвестны, не повторяй wait и не объявляй их работающими. Прерванный исполнитель не считается ни успешным, ни автоматически перезапускаемым: сохрани его готовую дельту, а новый отдельный исполнитель получает только незавершённую часть одного урока. Не переназначай работу активного или уже готового автора. После wait без события проверь, что его получатели всё ещё активны, прежде чем ждать снова; не отправляй повторяющиеся сообщения о неизменном состоянии.

Для нескольких подтверждённо работающих агентов используй один многоточечный wait и обрабатывай готовое событие сразу, без ожидания волны. Не печатай полный payload, отчёты или логи в контекст root, когда достаточно статуса, путей, остатка и ссылки на evidence; конкретный FAIL и обязательные условия не обрезай. После прерывания интегратора проверь точный ключ и версию перед повтором; неизвестный перенос не равен успешному. Сверка `False` остаётся дефектом интеграции, а не COMPLETE.
