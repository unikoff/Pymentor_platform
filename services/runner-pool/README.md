# Preview runner pool (lab)

This directory preserves the tested result-channel v10 lab source. It is an experimental private broker, not a production deployment or a distributed coordinator. Do not expose it to untrusted clients directly: HTTP has no authentication or TLS. The caller and network boundary must enforce access, admission and transport protection. Kubernetes control-plane access, the coordinator identity, the runner image and gVisor are trusted; submitted code is untrusted and executes in a disposable sandbox. No test here proves the isolation boundary.

The supervisor requires a non-root PID 1 in a private PID namespace and fails closed unless its procfs and process-limit probes succeed. Each Job uses gVisor, no service-account token, a read-only root filesystem and dropped capabilities. The supervisor kills and reaps descendants before exposing a random abstract Unix socket for the result; the coordinator checks the Pod UID before reading. CRI logs carry readiness markers rather than submission results. These properties depend on the actual cluster runtime and configuration.

## Image and configuration

Build with this directory as context: `docker build -t preview-pool .` (requires locally available pinned bases or registry access). Both base images and the sandbox runner image are pinned by digest. The image runs `pool_service.py` as UID/GID 10001 and listens on port 8088. Supply `POOL_NAMESPACE=runner-pool-lab-20261109` and the coordinator Pod's `POD_UID` via the Kubernetes downward API. The namespace is hard-coded in the manager; the service refuses another value. The coordinator checks Pods labeled `app=preview-pool-broker` in namespace `pymentor` and requires only its own UID before orphan recovery. This is a startup guard, not a distributed lock: run exactly one coordinator and reserve the lab namespace exclusively, since recovery deletes matching `app=pool-lab` Jobs.

The coordinator needs Kubernetes permissions for that Pod listing and, in the lab namespace, creating/listing/deleting Jobs, reading/waiting for Pods and logs, and Pod attach/exec. Sandboxes use service account `pool-sandbox`; provision it, the required RBAC, gVisor runtime class and network isolation separately. Pool settings are hard-coded: 3 sandboxes, 120s maximum age, 15 admitted requests; `/health/live` and `/health/ready` report broker state. POST `/api/learning/interpreter/run` accepts JSON `code` (1–8000 characters, up to 32000 UTF-8 bytes; request body at most 40000 bytes). Each sandbox is used once. The manager caps result transport at 250000 UTF-8 bytes; the service checks response fields at 12000 characters. Timeouts and other limits are in the source.

Local contract checks: `python -B -m unittest discover -s tests -v`. They do not start a server, execute submitted code, build an image, contact Kubernetes, or validate runtime isolation, recovery or production readiness.
